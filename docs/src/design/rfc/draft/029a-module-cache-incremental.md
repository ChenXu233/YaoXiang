# RFC-029a: 模块缓存与增量重编译

## 摘要

落实 RFC-029「子 RFC 规划」中预留的 029a 行：在已稳定的编排器（`compile_project`）之上，
给编译器补上**分层缓存与增量重编译**。核心是三层缓存模型——进程内分析结果（L1）、
会话内模块级（L2）、跨进程磁盘（L3）——配统一的键与失效原则和强制度量钩子，
收敛当前四处互不相通的缓存散点（#251 P0-6 审计发现）。

## 动机

### 宿主与边界依据

RFC-029（已接受）明确将本主题划出自身边界，并预留了本子 RFC 的槽位：

> **不包含**：缓存、文件监听、热重载、增量重编译、跨包循环依赖处理。
> —— RFC-029 §核心原则

| 子 RFC  | 能力               | 前提       |
| ------- | ------------------ | ---------- |
| 029a    | 模块缓存与增量重编译 | 编排器稳定 |

前提「编排器稳定」已满足：编排器随 RFC-029 落地并经 #232/#243/#244/#245 交付验证。

### 当前问题（#251 P0-6 审计 + 2026-09-07 实证）

**缓存散点互不相通**：

| 已有                      | 层          | 实际消费方   | 问题                                   |
| ------------------------- | ----------- | ------------ | -------------------------------------- |
| `VALIDATE_CACHE`（validate.rs） | 进程内      | 仅 formatter | CLI `check`/`run` 与编排器都不走它     |
| Z3Backend 查询缓存        | 检查会话    | 证明管道     | 无失效规则与预算设计（RFC-009a 一句话） |
| `DocumentCache`（util/cache.rs，RFC-017） | LSP 会话    | LSP          | 与 CLI 编译面完全不通                  |
| `~/.yaoxiang/cache`（RFC-014） | 磁盘        | 包下载       | 与编译无关                             |
| 代码缓存（RFC-028）       | 运行时      | JIT          | 非编译期层                             |

**多入口重复全链路（实证）**：

- `check_files_with_diagnostics` 循环内**每文件新建 `Compiler`**（`src/util/diagnostic/mod.rs`）：
  同进程校验 19 个库层文件，std 嵌入链被重复 typecheck 19 遍；
- runtime-error 类测试文件走 `check` + `run` 两个子进程，全链路做两遍；
- 借用检查 `fast_path_check` 每次写操作独立做全图 BFS，无结果缓存（#251 P0-6 审计原始发现，
  RFC-009a L611 仅一句「一次 BFS 结果可缓存供同一令牌的多次查询复用」，无机制设计）。

### 成本解剖（--version 基线法，2026-09-07 实测）

| 探针                                       | 耗时   | 差值含义               |
| ------------------------------------------ | ------ | ---------------------- |
| `yaoxiang --version`                       | ~50 ms | 进程 spawn + CLI 初始化 |
| 裸文件 `check`（无 std 导入）              | ~60 ms | 前端编译 ≈ 10 ms        |
| `std.test` 链文件 `check`                  | ~80 ms | 嵌入 std 链 ≈ +20 ms   |

测试回路 170 文件实测 9.8 s ≈ 58 ms/文件：**~85% 是进程生命周期成本，编译本身仅 ~10 ms，
std 链每文件 +20 ms**。由此定位本 RFC 的收益主战场：

1. **同进程多入口复用**（L1/L2）——消灭重复的前端链路与 std 链编译；
2. **跨进程 std 链消除**（L3）——子进程模型下唯一合法的缓存收益通道；
3. 进程 spawn 的 ~50 ms/文件**不在缓存射程内**——子进程隔离是 RFC-036 §6 的设计选择，
   本 RFC 不推翻（见非目标）。

## 提案

### 核心设计：三层缓存模型

#### L1 进程内分析结果缓存（生命周期 = 单次检查会话）

- `validate_source` 收编为**前端验证唯一入口**：`check_files_with_diagnostics`、
  编排器逐文件 typecheck、LSP 诊断全部改走它（现状仅 formatter 消费）；
- 键 = FNV-1a 内容哈希（validate.rs 既有实现），值 = `ValidateResult`（诊断 + AST）；
- 借用 BFS unsafe 集缓存：落实 RFC-009a 的设计句，生命周期 = 单函数检查会话，
  与 #290/#292 借用检查实现对齐；
- Z3 查询缓存（RefCell + 查询哈希）收编进同一原则，补失效与预算说明。

#### L2 会话内模块级缓存（生命周期 = 单次编排）

- 编排器的 Registry 与各模块验证结果按 **(模块路径, 内容哈希)** 缓存，
  同进程第二次 `compile_project` 直接命中；
- std 嵌入源（`yx_sources` include_str!）内容恒定 → 每进程编译一次，N 个导入文件共享；
- 失效：本模块源哈希变化即失效；依赖变化沿 `use` 图传播（第三波落地）。

#### L3 跨进程磁盘缓存（生命周期 = 跨 run）

- 位置 `~/.yaoxiang/cache/compile/`，与 RFC-014 下载缓存同根不同段；
- 键 = **(内容哈希, 编译器版本, 语义配置指纹)**；产物为模块字节码
  （复用 `BytecodeFile` 魔数格式）；
- 版本或指纹不匹配 = 整体 miss 重编——**不做跨模块失效传播**（保守整键失效）。

### 键与失效统一原则（#293 缺口 4）

- 键强度：内容哈希 > 结构哈希 > 版本号。L1/L2 用内容哈希（源码即身份），
  L3 在其上加编译器版本与配置指纹守卫；
- 失效传播只存在于 L2 依赖图内；L3 整键失效，不追踪模块间依赖；
- **构造期拒绝**：键不齐（缺哈希/缺版本）拒绝写入缓存，宁可 miss 不落旧产物——
  与诊断 i18n 缺翻译拒绝编译同一原则。

### 度量钩子（#289 对齐）

```rust
pub struct CacheStats {
    pub hits: u64,
    pub misses: u64,
    pub cached_bytes: u64,
}
```

- `check --json` 与 `test --json` 的 summary 附 `cache` 字段（分层命中率）；
- **强制门槛：不可观测的缓存不许合入**——防止「缓存了但没人命中」的静默腐烂。

### 增量重编译边界（#293 缺口 2）

- **文件级起步**：沿 `use` 图判定脏文件，仅重编脏文件及其下游；与 RFC-017 的
  LSP 文件级缓存统一演进（DocumentCache 迁为 L1+L2 的消费方，而非独立体系）；
- **函数级增量明确不做**（RFC-017 已声明该简化，几毫秒的全文件解析不值得增量化）。

## 详细设计

### 与 RFC-029 编排流程对接

```text
RFC-029 编排流程（已落地）：

  发现源文件 → 构建 Registry → 逐文件 typecheck → 整体编译

本 RFC 插入点：

  发现源文件 → [L2] 按路径+哈希查 Registry/验证结果缓存
                    ├─ 命中 → 复用
                    └─ miss → 构建（并回填）
  逐文件 typecheck → [L1] validate_source 唯一入口（内容哈希查/回填）
  整体编译 → 产物 → [L3] 序列化落盘（带版本守卫），下次进程直接加载
```

### 测试回路预期收益（量化）

| 场景                                   | 现状            | 029a 后              | 依赖层 |
| -------------------------------------- | --------------- | -------------------- | ------ |
| 同进程 runner（yx_runner 模式）19 库文件 | std 链 19×20 ms | 1×20 ms + 19 次命中   | L1+L2  |
| 子进程 runner（`yaoxiang test`）        | std 链 20 ms/文件 | 命中后 ≈ 0          | L3     |
| 借用检查大函数                         | O(V²) BFS       | 单会话内复用          | L1     |
| 进程 spawn（每文件 ~50 ms）            | 不变            | 不变（非目标）        | —      |

## 与现有系统关系

- **RFC-029**：宿主。029a 是其「子 RFC 规划」表的兑现；
- **RFC-009a**：L611 设计句的机制化（BFS 缓存，L1 层）；
- **RFC-017**：DocumentCache 收编为 L1+L2 消费方，缓存策略单源；
- **RFC-014**：磁盘目录分工——`cache/` 下载段 vs 本 RFC `cache/compile/` 段；
- **RFC-028**：JIT 代码缓存属运行时层，不在本 RFC 管辖；
- **RFC-031**：优化 pass 的调度属 Pass 管理器；本 RFC 缓存的是 pass 链路的输入输出，
  两者正交；
- **RFC-036**：测试子进程隔离模型维持不变，L3 是其唯一跨进程收益通道；
- **#251/#290/#292**：审计来源与借用检查实现（BFS 缓存消费方）；
- **#289**：度量钩子的可观测性对齐；
- **#247**：`use` 追踪发现（按需发现）叠加在 L2 依赖图之上，属纯性能优化。

## 实施策略

1. **第一波（落地即收益）**：`validate_source` 统一入口化（check/编排器/LSP 三消费方接入）、
   借用 BFS 会话缓存、度量钩子最小版；
2. **第二波**：L2 会话模块缓存（std 嵌入单次编译 + Registry 复用）；
3. **第三波**：L3 磁盘缓存（std 优先——嵌入源内容稳定，命中率恒定）+
   沿 `use` 图的文件级增量重编译 + LSP 缓存统一。

## 非目标

- 函数级增量解析（RFC-017 既有裁决）；
- JIT / 运行时缓存（RFC-028）；
- 推翻测试回路的子进程隔离（RFC-036 §6 设计选择）；
- 跨包失效传播（RFC-029 边界外）；
- 进程 spawn 成本优化（非缓存议题）。
