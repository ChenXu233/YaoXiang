# RFC-029g: 移除 pub 关键字与自动绑定

> 编号说明：RFC-029 子 RFC 规划已将 029b 预留给「文件监听与热重载」，029c（重导出）已删除不复用，029a/029d/029e/029f 均已占用，本 RFC 取下一个空闲编号 029g。

## 摘要

将 RFC-029「无可见性机制」的裁定执行到底：删除 `pub` 关键字与 pub 自动绑定，方法形式收敛为显式组合（`Point.method: (self: &Point) -> T = {...}`），并在语言层面最终裁定**不设可见性机制**——将来若生态需要，正确切口是**包边界**（同包自由、跨包按声明，走 manifest 导出面），而非模块边界关键字。

## 动机

### 规格冲突已由实现单方面裁决

RFC-029（2026-07-30 决议）明文「没有 `pub`，没有 `private`，没有 `export`，没有可见性机制」，决策表记录「`pub` 关键字：不要」。语言参考 modules.md 却长期在教「pub 导出、默认私有」。实现跟随 RFC-029（`is_pub` 不参与导出判定，非 pub 顶层绑定同样可被导入）；modules.md 的导出规则一节已重写为实际语义，但 pub 关键字与自动绑定的课文仍在，规格漂移源未除。

### pub 的两个真实语义都是空载

**自动绑定**（pub 函数首参为同文件具体类型时绑为方法）：

- std 全部 31 处 pub 无一满足门槛——list 系列首参是 `A: Type` 泛型参数、json 系列首参是 Ref 形态、其余是类型定义；
- 全仓 `.yx` 语料（测试、示例、文档）pub 出现 0 次（std 之外）；
- 仓库实际使用的方法形式全部是显式组合，且显式形式表达力严格更强（RFC-004 多位置绑定、单位绑定）。

**死码豁免**（`is_pub` 且豁免开关开启且无引用池时，pub 项当可达根）：

- Bin 角色已不豁免（029f Phase 1：无包外消费者，未使用即报）；
- Internal 角色豁免已收紧为引用池判定；
- Script/Lib 角色维持绝对豁免——Script 单文件本就不存在「别处的使用者」，豁免保护的是不存在的读者；Lib 的豁免是 029f「宁漏报」的分发边界策略。pub 删除后，两者统一落入 029f 对非 pub 项的既有机制：Lib 按包内引用池判定，Script 按单文件引用判定，行为收紧且更精准。

**`env.exports` 死表**：typecheck 环境按「显式方法、pub 顶层绑定、类型定义」灌入的导出集合，连同 `is_exported`/`is_visible` 两个访问器，生产代码零读取方——真正的导出面是模块注册表的 `ModuleInfo.exports`（use 解析、E1043、LSP 均读它）。

### 可见性机制的价值裁定

- YaoXiang 类型是透明记录（无私有字段），可见性的经典价值「不变量保护」不存在；
- 「收敛 API 面」价值需外部消费者才成立，当前生态为零；
- 将来若需要，切口是**包边界**而非模块边界关键字——模块边界与文件绑定，粒度过细，且与「module = record」模型冲突（可见性会成为 record 上的锁，破坏透明性）。

## 提案

### 删除面

| 位置 | 内容 |
|------|------|
| lexer/parser | `pub` 关键字与语法分支（含 use 花括号条目内的 pub 跳过） |
| AST | `is_pub` 字段 ×2（含测试 fixture 同步） |
| formatter | pub 前缀回显 |
| checker | `auto_bind_to_type`、`collect_exports` 的 pub 分支（显式方法分支保留） |
| dead_code | `is_exported` 字段与 `exempt_pub` 豁免分支 |
| LSP | semantic tokens 的 Public modifier |
| ir_gen | `is_pub` 忽略绑定清理 |
| std | 31 处 pub 前缀（list 25 / json 4 / option 1 / result 1） |
| typecheck 环境 | `exports` 死表与 `is_exported`/`is_visible` 访问器删除 |
| 诊断文案 | W1xxx 系列 help 中「pub 是对外接口」表述（zh 源修改，译文走 bot） |
| 语言参考 | modules.md §3.2–3.3 再收敛；syntax.md 关键字表；warning-codes.md 豁免表述；language-overview.md |
| RFC-029 | 落地注「AST `is_pub` 不动」补推翻标注；子 RFC 规划表登记 029g |

### 行为变化（如实记录）

| 角色 | 现状 | 删除后 |
|------|------|--------|
| Bin | pub 不豁免 | 不变（按引用池判定） |
| Internal | pub 走引用池 | 不变 |
| Lib | pub 绝对豁免（宁漏报） | 收紧：按包内引用池判定，包内未使用的顶层绑定报 W1001 |
| Script | pub 绝对豁免 | 收紧：未使用的顶层绑定报 W1001（与普通绑定一致） |

嵌入 std 与 vendor 依赖的内部警告已有「仅对本项目文件呈现」门控，std 删除 pub 不会把死码告警混入消费方输出。

### 保留不变

- 显式方法组合（`Type.method:`）完整保留——这是唯一的方法形式；
- use 四种形态与 record 解构语义不变；
- E1043 模块导出报错路径不变。

## 权衡

**得**：删除一条从未兑现设计意图的语法路径；关键字表、AST、checker、dead_code、LSP 五处机制收敛；规格与实现零分歧。

**失**：包作者「尚未被包内消费的 API」从绝对不报变为可报 W1001。此收紧与 029f 对非 pub Lib 项的处理一致，属既有方向的延伸而非新策略。

## 替代方案

- **保留 pub 作纯装饰**：否——装饰性关键字违反「语法承载语义」原则，且持续产生规格漂移面（本次冲突即其恶果）。
- **只删自动绑定、保留死码豁免**：否——豁免服务的是不存在的 pub 语义，留下它就得留下关键字。
- **引入真可见性机制**：否——价值裁定不成立（透明记录 + 零外部消费者），且正确切口在包边界。
