# 代码编写规则（Coding Rules）

> **本文是 YaoXiang 代码变更规则的唯一权威本体。** 精确描述规则，不含现状诊断与历史论证。
> 历史事故证据与决策理由见 [08-maintenance-mechanism.md](architecture/08-maintenance-mechanism.md)（2026-10 诊断记录，随 RFC-039 归档）；外部惯例参照（Go / rustc 等）同见该文档。
> 执行入口：[HOWTO.md](HOWTO.md)（动工自检）→ 本文（规则）→ PR 模板（提交时强制）。

## 第一部分：三条禁令

### 禁令一：不得生造

新增任何 `pub` 类型 / 枚举 / 常量表 / 概念之前，以下四条判据**全部通过**才算合规。任一命中即违规：

| 判据 | 规则 |
| --- | --- |
| A. 职责重叠 | 新增项与既有某项变体名重合 ≥ 半数且职责重叠 → 违规 |
| B. 调用点不足 | 新增 `pub` 项调用点 < 2（仅定义处 + 唯一调用处）→ 违规；无法证明它是概念而非局部实现 |
| C. 需要消歧别名 | 需要 `use … as XxxBinOp` 式别名才能区分同语义项 → 违规 |
| D. 靠同义词表弥合 | 靠手写字符串匹配弥合差异 → 违规，必须改为穷举或显式转换 |

### 禁令二：不得职责累积

一个模块只承担一类职责。不设行数 / 体积 / 文件大小门禁——规模问题由职责分离解决，不由数字解决。

| 判据 | 规则 |
| --- | --- |
| A. 职责类别 | 新增代码不属于目标模块**已有的职责类别**（第 2 类及以上）→ 违规，新建模块或把该职责现有代码一并搬走。**人工判断，不可机器化** |
| B. 绕过权威源 | 新增表项但未更新唯一权威源（绕过权威表手写副本）→ 违规 |
| C. 边界侵蚀 | 新增任一跨层依赖（L2→L3、L4→L1/L2）、`include!`、`pub(crate)` 跨层泄漏 → 违规。**可机器化，由 CI 检查** |

### 禁令三：该重构不补丁

| 判据 | 规则 |
| --- | --- |
| A. 同义重复 | 同一行为在 ≥2 处出现（别名 / 转换 / 阶段接线 / 错误映射）→ 违规，必须提到共享层 |
| B. 扇出过大 | 一次修改要同步改 ≥3 处已有的同义映射 → **判定为架构变更**，停工，走设计文档流程 |
| C. 新增入口 | 新增"第 N 个入口 / 表项"而非登记进声明式阶段表 → 违规 |

## 第二部分：决策程序（D0–D4）

每次代码变更按序过五道闸。每道是可判定的布尔条件，**命中即止**：

```
D0  门禁    本次改动是否触碰任何一张已存在的表（错误码/opcode/类型/入口阶段）？
             ├─ 是 → 能指出该表的唯一权威实现模块吗？
             │        ├─ 能 → 继续
             │        └─ 不能 → ⛔ 停止。先建立权威源
             └─ 否 → 继续
                    ↓
D1  防生造   去掉新概念后，能否用「既有概念 + 参数」表达同样的语义？
             ├─ 能 → ⛔ 禁止新增。理由记入 PR
             └─ 不能 → 继续
                    ↓
D2  防并行   新概念是否与某既有概念同语义（变体名重合 ≥ 半数）？
             ├─ 是 → 有 From/TryFrom 转换且机检吗？
             │        ├─ 有 → 继续
             │        └─ 无 → ⛔ 合并为一份（禁止用 import 别名区分）
             └─ 否 → 继续
                    ↓
D3  补丁?    依次判定，命中即止：
             1) 同一行为需在 ≥2 处复制？        → 是 → ⛔ 必须提到共享层
             2) 需要新增"第 6 个入口"？         → 是 → ⛔ 禁止手工接线，改为登记进阶段表
             3) 一次修改要改 ≥3 处同义映射？   → 是 → ⛔ 判定为架构变更，停工走设计文档
             4) 以上皆否                       → 允许局部补丁，但必须附带回归测试
                    ↓
D4  职责?    本次新增代码属于目标模块已有的职责类别吗？
             ├─ 否（第 2 类及以上）→ ⛔ 新建模块，或把该职责的现有代码一并搬过去
             └─ 是 → 合规
```

**取舍判据（贯穿 D0–D4）**：方案否决理由**只能**基于**正确性**与**可读性**；"改动面大小""是否引入新机制""实现成本"**不构成否决理由**。与禁令一并行不悖——禁令一约束「概念是否重复」，本条约束「取舍理由是否成立」：以改动面或新机制为由否决方案者，review 直接打回。

需要用户拍板的取舍（架构选择、语义偏差、登记/不登记、破坏性变更、排序插队），按仓库根 `AGENTS.md`「请求用户裁决时（强制）」给全四件：情况+证据、逐项优缺点、明确推荐+代价、破坏性点名。

**语义修正的分流（RFC-039 D59）**：D0–D4 全保留；额外多一步「错误类型」标注——**A/B/C 三类**（旧行为**非成功**：崩溃/爆栈、静默失败、静默错配、静默不动作、静默给错答案）**可随重构顺路修**，条件是**先红后绿 + 不改变「原先成功」程序的对外表现 + 同提交登记 + 基线同提交再生与人工 review**；**D/E/F 三类**（改变原先成功程序的可观察行为、对外契约表、RFC 级设计变更）**必须先经用户裁决**。判据展开见 [07 §语义修正的分流判据](architecture/07-equivalence-oracle.md) 与 RFC-039 决议登记 D59；PR 必填块增一行「错误类型（A–F）」。

## 第三部分：红线（review 必打回）

1. **不看的代码不改**——没有打开过被改文件、没有 grep 过相关引用点，不许动它
2. **核心功能不留待实现遗留**——不许新增 `todo!()`、`unimplemented!`、`Vec::new() // Not implemented yet` 式静默丢弃、无限期"独立 issue"。发现即修，或登记进当前阶段任务
3. **不删测试、不放宽判据换绿灯**——做不到是实现缺陷，如实报告并重新评估，不是修改判据的理由。**测试的准入与退役按第七部分**：只有三扇门（条款 / 病史 / 证明）一扇都过不了才可退役，「因为红了就删」永远打回
4. **不用 import 别名弥合同语义概念**
5. **不新增 `include!`、不新增跨层反向依赖、`pub(crate)` 跨层泄漏只许减不许增**
6. **PR 必填块必须如实填写**——D0 权威源模块名写不出 = 没查，直接打回；「错误类型（A–F，按 D59）」漏标或与改动实际不符，同样打回

## 第四部分：机器与人工的分工

**机械问题交给工具，review 只看非机械问题。**

| 类别 | 执行者 |
| --- | --- |
| 格式、lint、表一致性、边界侵蚀（禁令二 C）、测试接线、跨层依赖 | 工具：`cargo fmt` / `clippy` / `build.rs` 门禁 / `scripts/ci/check-*.py` |
| 职责类别判定（禁令二 A）、D3 的"补丁 or 架构变更"判断、豁免理由 | 人工：PR 必填块 + review |

**更正就地写入正文，不留新旧对照**：发现文档或注释与事实不符时，直接把正文改成事实、删掉旧表述；不得保留旧文本再附「修订注记」「原为…现改为…」这类对照——读者不该先读到错的、再读到对的。更正的**过程证据**（红→绿、前后 diff、裁决号）写进提交信息或 WBS 历史实录（`09a`），不写进被更正的那段正文。历史实录（`09a`）与工作令/变更清单（如 `02` §改动清单）不受此限。

## 第五部分：豁免机制

- 机器判据的豁免一律用 `// reason: <理由>` 行内注释
- 豁免数量本身进门禁报告，review 时逐条过目
- 豁免是**例外凭证**不是**惯例**；同类豁免出现第 2 次时，正确动作是改规则或改判据，不是加第 3 条豁免

## 第六部分：代码审查清单

每个 PR 的 review 按此逐条过：

- [ ] **D0** 是否触碰了任何一张表？该表的唯一权威实现模块是哪个？
- [ ] **D1** 新概念能否用既有概念 + 参数表达？不能的话理由写在哪？
- [ ] **D2** 是否与既有概念同语义？转换在哪里？是否需要 import 别名？
- [ ] **D3** 同一行为是否在 ≥2 处出现？是否新增了入口而非登记进阶段表？是否要改 ≥3 处同义映射？
- [ ] **D4** 本次新增代码属于目标模块已有的职责类别吗？
- [ ] **静默通道** 「登记-消费」型机制（一方登记数据、另一方消费，如 SemanticDB、proof_calls、义务账本）的生产端与消费端**直驱**测试是否同批交付？消费端测试手工构造登记数据而生产端无直驱证据 = 机制表面存在、数据流从未发生，打回（已三例：proof_calls、RFC-039 D54、RFC-039 D55）
- [ ] **边界** 是否被侵蚀？新增跨层依赖 / `include!` / `pub(crate)` 跨层泄漏？
- [ ] **检查准入** 新增的测试 / 门禁过了第七部分三扇门中的哪一扇？依据写在哪？（过了**证明**门的，还要回答：换一个正确的替代实现，它会不会红？）
- [ ] **分工** 机械问题是否已由工具兜住？review 是否只花在非机械问题上？

## 第七部分：检查与测试的准入与退役

**绿灯什么也不证明。** 检查只有否定性的认识价值——它证明的是「这一次，它没有在这个点上错」。一条检查值不值得存在，只看它守的是不是一条**已被写明的性质**；答不上来的，不是安全性，是给守规矩的人加税。

### 7.1 唯一校验：换一个正确的替代实现，它会不会红

| 结果 | 含义 | 处置 |
| --- | --- | --- |
| 会红 | 它冻的是**实现选择**（渲染文本、消息措辞、精确行号、内部结构形状） | 特征化，**不进门禁** |
| 不会红 | 它守的是**性质** | 合法检查 |

任何「把当前输出整体冻下来」的检查（全量快照、逐字节比对），在换一个正确实现后必然红——它按定义进不了这一关。

推论：测试的原子单位不是「一条测试」，是**一个可证伪的区分**。同一代码路径、同一类输入、同一断言意图写 N 条，增量信息为零；「本仓有几千条测试」这个数字本身不构成任何证据。

### 7.2 准入：三扇门

新检查必须通过以下**至少一扇**，并把依据写进测试文件头部注释或提交说明：

| 门 | 要交什么 |
| --- | --- |
| **条款** | 指名 SPEC / RFC 的哪一条 |
| **病史** | 指名一次真实故障：哪次改动、哪个缺陷、当时怎么暴露的 |
| **证明** | ① 性质是什么；② 为什么它**必须**成立（与实现选择无关）；③ 为什么这条测试是它最便宜的观察点 |

三扇门**不等价**：条款是外部约束，可能写得含糊；病史只覆盖发生过的那一次；**证明覆盖整个性质类**，因此最耐时间——它的价值不在抓到过什么，而在它挡的是一类违反。

第三扇门必须有牙齿。「这是不变量」谁都会说，而绝大多数这么被说出来的东西冻的其实是当前实现。三扇门共用一个校验（7.1）：换一个正确的替代实现它就会红的，退回特征化——它不是证明，是伪装成证明的冻结。

### 7.3 退役：举证责任倒置

存量检查按 7.2 过一遍：**能过任意一扇的留下；一扇都过不了的，删。** 不设「观察期」「降级为提示」「标记为特征化后保留」——三者都是在给说不清依据的东西续命。

- **删除不是不可逆操作**：历史在 git 里，需要时按提交取回。正因为它可回取，「先删、需要时再捞」优于「一律留着」；
- 删除按批次做，每批一个提交、可整体 revert；
- 每批在 [09a](architecture/09a-wbs-history.md) 登记「删了什么、按哪扇门判的、有无替代覆盖」。

### 7.4 成本纪律

成本与正当性无关。成本要可测（用仓库既有的 `cost:` 资源画像标记），要进门禁预算。**不得用「CI 并行所以无所谓」当理由**——并行省的是墙钟，不省每个人本地自检的时间，而后者才是每天付的。

### 7.5 与红线第 3 条的分界

红线第 3 条针对**动机**（为让 CI 变绿而改判据），本部分针对**成本收益**（这条检查值不值），两者不冲突。

**冲突时的裁决顺序（强制）**：① 它现在红，是因为**实现错了**还是**判据错了**？② 答不上来时，不得删除、也不得改判据；③ 若是「判据错了」，退役走 7.3，不是改断言。
