# 文档规则（docs-rules）

> 本文是文档规则的**本体**；动工前自检入口是
> [HOWTO.md](./HOWTO.md)（统一手册，第二节是改文档部分）。本文与
> [coding-rules.md](./coding-rules.md) 同级：coding-rules 管代码，本文管文档。

## 0. 三条禁令（文档版）

镜像 coding-rules 的三条禁令，review 同样按此打回：

1. **不得生造**：新增术语、新增文档类型之前，先证明它与既有概念不重复——查
   [docs/glossary.json](https://github.com/ChenXu233/yaoxiang/blob/main/docs/glossary.json)、查 §1 分类表、grep 既有文档。
2. **不得职责累积**：一篇文档只属于一个象限、只服务一种受众。在教程里塞参考表、在参考里写设计动机，都是职责累积。
3. **该重构不补丁**：同一内容出现 ≥2 处复制、一个目录混入两种受众、一次修改触及 ≥3 处同义表述——停手，先调整结构，再写内容。

## 1. 分类规则：六个顶级目录，六种受众

文档站点按 [Diátaxis](https://diataxis.fr/) 的四个象限组织用户文档，外加两个面向仓库自身的目录：

| 目录           | 象限               | 受众       | 读者的问题                     | 文档形态         |
| -------------- | ------------------ | ---------- | ------------------------------ | ---------------- |
| `tutorial/`    | 教程（学习导向）   | 初学者     | 「带我做出第一个东西」         | 循序渐进的课程   |
| `guide/`       | 指南（任务导向）   | 使用者     | 「我要完成 X，怎么做」         | 步骤清单         |
| `reference/`   | 参考（信息导向）   | 使用者     | 「X 的准确含义是什么」         | 查表式描述       |
| `explanation/` | 阐释（理解导向）   | 好奇者     | 「为什么这样设计」             | 论述             |
| `dev/`         | —（Diátaxis 之外） | 贡献者     | 「我要改这个仓库，守什么规矩」 | 规则、架构、流程 |
| `rfc/`         | —（语言治理）      | 语言设计者 | 「这个特性怎么定的、怎么提案」 | 提案 + 状态目录  |

`blog/` 是时间性的对外叙事，`archive/` 是排除发布的冷库，两者不参与分类。

### 判定决策树

1. 读者是语言或工具的**使用者**吗？
   - 是 → 他想**学会**（tutorial）、想**做成**（guide）、想**查证**（reference）、想**理解**（explanation）
   - 否 → 2
2. 读者要**修改编译器或仓库**吗？ → `dev/`
3. 读者在**评审或提交语言特性**吗？ → `rfc/`

一篇文档答不出唯一答案，说明它在服务两种受众——拆开，各归各位。

### 易混边界（实证）

| 内容                                          | 归宿                          | 易错放                                 |
| --------------------------------------------- | ----------------------------- | -------------------------------------- |
| `yx check` 的命令行用法                       | `reference/check-command.md`  | dev/design/check/                      |
| `yx check` 的设计规范（零误报原则、增量机制） | `dev/design/check/`           | reference/                             |
| 格式化规则条文（实现行为规范）                | `dev/design/formatter/`       | reference/                             |
| `yx format` 的命令行用法                      | `reference/format-command.md` | dev/design/formatter/                  |
| 语言理念、宣言（常青论述）                    | `explanation/`                | blog/（blog 是时间性的）               |
| 编译器架构与施工表                            | `dev/architecture/`           | explanation/（它是操作手册，不是论述） |
| 特性提案与定案记录                            | `rfc/`                        | dev/（RFC 的受众不止贡献者）           |

## 2. 语言风格（维基式写作）

本节参考维基百科格式手册的核心精神，适用于全部目录；人称与语气按象限微调（§2.4）。

### 2.1 主动语态优先

- 写「编译器报告 E1001」，不写「E1001 被编译器报告」。
- 被动语态只在行为者未知或不重要时使用。
- 检验方法：句子里出现「被」「由」「是通过」时，问一次「谁做的」。答得出来，就改成主动语态。

### 2.2 确定的陈述句

- 写「yx check 不生成代码」，不写「yx check 可能不会生成代码」。
- 事实必须断言。不确定的内容只有两种合法写法：
  - 给出确定的条件：「启用 `--watch` 时，yx check 只重检查受影响的文件」。
  - 删掉，验证之后再写。
- 禁用模糊词：可能、也许、大概、基本上、某种程度上。「应该」只允许表示义务（「你应该运行测试」），不允许表示推测。

### 2.3 现在时态

- 写「解析器拒绝空模块」，不写「解析器将会拒绝空模块」。文档描述的是当前版本的行为。
- 例外：`rfc/draft/` 与 `rfc/review/` 描述尚未实现的提案时用「将」；提案落地后改回现在时。

### 2.4 人称

- `reference/`、`explanation/`、`rfc/`：无人称陈述（「该函数返回 Result」）。
- `tutorial/`、`guide/`：第二人称「你」（「你运行 yx new」）。
- `dev/`：规则条文无人称，操作指引可用「你」。
- 任何目录都不用「我们」：「我们推荐」写成「推荐」。

### 2.5 一句一意

- 一句话只断言一件事；两个断言就写两个句子。
- 三个以上并列事实用列表，不用长句。

### 2.6 术语一致

- 同一概念全站只有一个名字。前文写「所有权」，后文不换成「所属权」。
- 新增术语先查 docs/glossary.json 与既有文档的用法。
- 术语首次出现给出定义或链接到定义。

### 2.7 客观中立

- 不写「非常简单」「只需」「轻松」。读者卡住时，这些词是嘲讽。
- 不写营销词：强大、优雅、无缝。用可验证的事实替代：「编译期单态化，无运行时开销」。
- 比较其他语言时陈述行为差异，不评价优劣。

### 2.8 可验证性

- 每个行为断言必须能由代码或测试证实；证实不了的断言不许写。
- 代码示例必须可执行：CI（`scripts/ci/check-docs-examples.py`）会运行它们。无法执行的示例标注
  `<!-- docs-example: skip -->` 并给出理由。

## 3. 结构与机械规则

- **frontmatter**：`title` 必填（侧边栏生成依赖它），`description` 推荐。
- **标题**：每篇一个 H1，正文从 H2 开始，不跳级。
- **链接**：站内链接一律使用指向目标文件的相对路径，不使用站点绝对路径。构建配置
  `ignoreDeadLinks: false`，死链会使构建失败。
- **移动文件 = 改 URL**：必须同步全站引用、两个侧边栏配置、en/ 镜像、引用了该路径的脚本与 AGENTS.md。完整流程见
  [HOWTO.md](./HOWTO.md) 第二节「移动文档六同步」。
- **格式**：表格对齐、围栏空行由 prettier（`docs/.prettierrc.json`）与 markdownlint 强制。
- **中英镜像**：zh 是源，en 由翻译工作流同步。新增/移动 zh 文件后，en 侧路径必须一致。

## 4. 目录索引页的职责

每个顶级目录的 `index.md`
回答两个问题：「这个目录收什么、不收什么」。索引页指向本规则，不重复维护内容清单——手写清单必然过时（RFC 状态的唯一权威是
`rfc/TRACKING.md`，由脚本生成，同理）。
