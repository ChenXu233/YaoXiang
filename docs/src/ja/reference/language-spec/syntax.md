# 文法仕様

この文書はYaoXiangプログラミング言語の文法仕様を定義するものであり、語彙構造、文法規則、演算子の優先順位を含む。

---

## 第一章：語彙構造

### 1.1 ソースファイル

YaoXiangのソースファイルはUTF-8エンコーディングを使用しなければならない。ソースファイルは通常 `.yx`
を拡張子とする。

### 1.2 トークン分類

| カテゴリ   | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語定義済み予約語               | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り記号 | 文法区切り                       | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiangはごく少数のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として使用することはできない。

### 1.4 予約語

YaoXiangの「予約語」は3層に分かれており、それぞれパーサー（parser）と型検査器（type
checker）が異なる段階で識別する。

#### 1.4.1 リテラル予約語

パーサーが独立したトークンとして持つリテラル識別子で、通常の識別子としては使用できない。

| 識別子  | 所属型 | 説明                                                                                     |
| ------- | ------ | ---------------------------------------------------------------------------------------- |
| `Type`  | —      | メタ型キーワード                                                                         |
| `true`  | Bool   | ブール真値                                                                               |
| `false` | Bool   | ブール偽値                                                                               |
| `void`  | Void   | Voidリテラル（Unit値）。小文字の`void`は値リテラル；大文字の`Void`は型名（§1.4.3参照）。 |

#### 1.4.2 コンストラクタ式

以下のコンストラクタはパターンマッチングと式の文脈でパーサーによって認識される。

| コンストラクタ | 所属型 | 説明                   |
| -------------- | ------ | ---------------------- |
| `some(T)`      | Option | Option値バリアント構築 |
| `ok(T)`        | Result | Result成功バリアント   |
| `err(E)`       | Result | Resultエラーバリアント |

#### 1.4.3 組み込み型名

以下の型名は型検査器に事前登録されており、インポートなしでも型の位置で使用できる。パーサーはこれらを通常の識別子として扱う——**予約語ではないため、ローカルバインディングでshadow可能（非推奨）**。

| 型名     | 論理的対応   | 説明                                                                                                                    |
| -------- | ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤（真/Unit） | ゼロフィールド積型、ちょうど1つの居住者（`void`リテラル、§1.4.1参照）                                                   |
| `Never`  | ⊥（偽/空型） | ゼロバリアント和型、居住者ゼロ。`Never`値を生成する式は存在しない。`Never <: T` がすべての`T`に対して成立（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                            |
| `Float`  | —            | 浮動小数点数                                                                                                            |
| `Bool`   | —            | ブール値：`true` / `false`                                                                                              |
| `Char`   | —            | Unicode文字                                                                                                             |
| `String` | —            | 文字列                                                                                                                  |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、後続の文字は文字、数字、またはアンダースコアである。識別子は大文字小文字を区別する。

特殊な識別子：

- `_` はプレースホルダとして使用され、値を無視することを表す
- アンダースコアで始まる識別子はプライベートメンバーを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // ターゲット型注釈がArray(T, N)の場合、リテラルは固定長配列になる
```

> #299/#300：Setにはリテラル文法はなく、ランタイム表現もない——集合型は計画中、必要性が生じた時点でDictパターンに従って補完する（std.set +
> HeapValue::Set）。List/Dictリテラルの着地点は文脈型注釈によって決定される：素のリテラルと`List(T)`注釈は可変長リストに、`Array(T, N)`注釈が直接リテラルに作用する場合は固定長配列になる。暗黙のList→Array変換は禁止。
>
> Arrayリテラルセマンティクス（#300）：
>
> - 要素数はNと等しくなければならない。等しくない場合はコンパイル時にE1002；空リテラルに非ゼロNを組み合わせた場合も拒否
> - 各要素の型はTと互換でなければならない。互換でない場合はコンパイル時にE1002
> - Nの文法形式：整数リテラル（負可）または定数名のみ。複合式（例：`2+1`）は解析段階で拒否
> - Nがシンボル定数（関数のconst引数、例：`Array(Int, n)`）の場合、要素数検査は精化型段階まで延期
> - v1のネスト配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否、層ごとに明示的に構築する必要がある；再帰的な着地点は今後のバージョンに委ねる

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **#299
> §3 行動の厳格化（移行記録）**：反復変数の文法は本来`'for' Identifier 'in'`だが、旧実装ではpatternが完全なpratt解析を行っていた——`'in'`が中置演算子として登録された後、
> `x`が`in items`をmembership式として飲み込んでいた。修正後は非識別子patternが直接解析失敗となり、旧実装のように`_`へのフォールバック（エラーの静かな飲み込み）は行われない。影響範囲：従来解析可能だった`[x for (a, b) in pairs]`のような記述は現在エラーになる——この形式は元々定義された振る舞いがなく（変数は常に`_`）、厳格化の方向は正しい。意味的な移行コストはない。

#### 1.6.6 メンバー検査

```
Membership  ::= Expr 'in' Expr
```

> #299
> §3：`in`は二項関係演算子で、`Bool`を返す——命中すれば`true`、未命中なら`false`で、エラーを出さない。意味の分割：`[]`はアサートして存在を確認し値を取る（失敗時にエラー）、
> `in`は存在を問う（未命中は通常の`false`）。右被演算子の対象：List / Array / Dict(キー集合) / Tuple
> / String(部分文字列) /
> Range(区間)。`in`は第一級ホール述語であり、精化型段階でコンパイル時に証明可能な命題の基底となる。（#300 決定4：Setは右被演算子リストから除外——Setにはランタイム表現がない、§1.6.4参照）

### 1.7 コメント

```
// 単行コメント

/* 複数行コメント
   複数行に渡ることができる */
```

### 1.8 インデント規則

コードは4スペースのインデントを使用しなければならず、Tab文字の使用は禁止。これは強制的な文法規則である。

## 第二章：文法規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強い結合を持つ：呼び出しとメンバーアクセスより低く、すべての二項演算子より高い。したがって
> `!a == b` ≡
> `(!a) == b`（Zig式のセマンティクス）；`!`は純粋な単項演算であり、短絡制御フローには参加せず、
> `and`/`or`キーワード（短絡）と直交する（RFC-010 権威ある定義）。

> **Range結合度（#299 §3 / #300 F項）**：`..` 結合度 (6,
> 7)——左6は加算（7）より低く、右7は加算を飲み込むが同級の`..`は飲み込まない。変更前後の対照：
>
> | 式           | 変更前（レベル1、右結合）                                                          | 変更後（(6,7)、左結合）                                         |
> | ------------ | ---------------------------------------------------------------------------------- | --------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10`（`in`右被演算子レベル4、`..`レベル1では飲み込めず、実際には解析不能） | `x in (1..10)`——区間全体が`in`の右被演算子                      |
> | `0..n+2`     | `(0..n)+2`（右結合の罠：上限が食べられる、`for`ループで直接E3004）                 | `0..(n+2)`——上限は算術式                                        |
> | `a == b..c`  | `a == (b..c)`（`..`レベル1 < `==`レベル3、最初から全体）                           | `a == (b..c)`——**意味不変**、`..`は依然として比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                                         | `1..(2*3)`——上限は算術式                                        |
> | `a..b..c`    | `a..(b..c)`（右結合チェーン、意味のないRangeの入れ子）                             | `(a..b)..c`——**step形式**（`c`はステップ、#300 I項）            |
>
> 純効果：複合上限`for i in 0..n+2`は「解析成功だがE3004」から「直接使用可能」に；
> `x in 1..10`は「解析不能」から「区間チェック」に；`a..b..c`は「無意味な入れ子」から「step成分」に。レベル6は`+`（レベル5）と`<<`（レベル7）の間に位置し、数学的慣例に従う：区間は強い結合の構造であり、上限は当然完全な算術式である。

### 2.3 関数呼び出し

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier ':' Expr
```

### 2.4 メンバーアクセス

```
MemberAccess::= Expr '.' Identifier
```

### 2.5 インデックスアクセス

```
IndexAccess ::= Expr '[' Expr ']'
```

### 2.6 型変換

```
TypeCast    ::= Expr 'as' TypeExpr
```

### 2.7 条件式

```
IfExpr      ::= 'if' Expr Block ('else' 'if' Expr Block)* ('else' Block)?
```

### 2.8 パターンマッチング

```
MatchExpr   ::= 'match' Expr '{' MatchArm+ '}'
MatchArm    ::= Pattern ('|' Pattern)* ('if' Expr)? '=>' Expr ','
Pattern     ::= Literal
              | Identifier
              | Wildcard
              | StructPattern
              | TuplePattern
              | EnumPattern
              | OrPattern
```

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt間の区切りと改行動作（`;`明示的区切り、改行終端、続行例外、行頭`(`/`[`は絶対にマージしない）は[RFC-038](../design/rfc/draft/038-statement-termination.md)で定義されている。

**統一セマンティクス**：すべての`{}`ブロックのreturnセマンティクスは一貫している。

| ブロック種別 | returnセマンティクス | デフォルト戻り値 |
| ------------ | -------------------- | ---------------- |
| 通常の `{}`  | 値を返す             | Void             |
| `unsafe {}`  | 型定義を返す         | Void             |
| `spawn {}`   | 結果を返す           | Void             |

**核心原則**：

- `{}`内の`return`は常にその内容を一階層上のスコープに返す
- `return`がない場合のデフォルトは`Void`を返す
- 式形式`= expr`は直接値を返す

```yaoxiang
// 通常の{}ブロック：returnは値を返す
result = {
    x = compute()
    return x  // 一階層上のスコープに値を返す
}

// unsafe {}ブロック：returnは型定義を返す
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    return SqliteDb  // 一階層上のスコープに型定義を返す
}

// spawn {}ブロック：returnは結果を返す
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    return (result1, result2)  // 一階層上のスコープに結果を返す
}
```

### 2.10 ラムダ式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?`演算子は後置演算子で、優先順位は`.`と同レベル。`Result(T, E)`型に対して：

- `Ok(v)`の場合、値`v`を抽出して実行を継続
- `Err(e)`の場合、エラーを上位に伝播（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時は値を抽出し、失敗時は上位に伝播
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..`は範囲値を作成する（#300 I項：Rangeは第一級値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Rangeは値である：バインド、受け渡し、メンバー判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step形式（第三引数、デフォルトは1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **stepセマンティクス**：`a..b..c`において`c`はステップ。`c = 0`のリテラルはコンパイル時に拒否；動的な`c`はランタイムゼロチェック（E6001ファミリ、#301エラーシステム実装後にResultに格上げ）。
> `c < 0`は有効で、区間方向は符号に従って反転する（`10..0..(-2)`は降順）。

### 2.13 ref式

```
RefExpr     ::= 'ref' Expr
```

`ref`は共有保持を作成する。コンパイラは自動的にRc（単一タスク）またはArc（タスク間）を選択し、ユーザは実装詳細を気にする必要はない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク間：コンパイラが自動的にArcを選択
```

### 2.14 unsafe式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe`ブロックは不透明型の定義と生ポインタの操作に使用する。`return`を使用して一階層上のスコープに型定義を返す。

**セマンティクス**：

- `unsafe {}`内では型定義と生ポインタの操作が可能
- 返された型は`unsafe {}`外で使用可能
- 型のフィールドアクセスにはunsafe権限が必要

```yaoxiang
// unsafeブロック内で不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDbはunsafeブロック外で使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各`{}`ブロックはスコープを作成する
- 内側スコープは外側スコープの変数にアクセス可能
- 外側スコープは内側スコープの変数にアクセス不可
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // xはこのスコープ内で可視
}
// xはこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// resultは関数外では不可視
```

**変数宣言とシャドウィング**：

- `x = value`：スコープチェーンに沿って外側に`x`を探索し、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的な新規可変宣言、外側と同名は禁止
- 同一スコープ内で同じ名前は一度しか宣言できない

> **詳細な定義**：スコープの完全な規則、変数宣言とシャドウィング機構の詳細については[モジュールシステム仕様](./modules.md#第四章作用域)を参照。

## 第三章：文

### 3.1 文の分類

```
Stmt        ::= LetStmt
              | ExprStmt
              | ReturnStmt
              | BreakStmt
              | ContinueStmt
              | IfStmt
              | MatchStmt
              | WhileStmt
              | ForStmt
              | SpawnStmt
```

### 3.2 変数宣言

```
LetStmt     ::= ('mut')? Identifier (':' TypeExpr)? '=' Expr
```

### 3.3 return文

```
ReturnStmt  ::= 'return' Expr?
```

**セマンティクス**：`return`はコードブロックから値を返すために使用する。`return`がない場合、コードブロックはデフォルトで`Void`を返す。

### 3.4 break文

```
BreakStmt   ::= 'break'
```

**セマンティクス**：それを囲む最も内側の`while`/`for`ループを直ちに終了し、制御フローをそのループ体の後に移す。

- **直近の1層のみ脱出**：`break`は常それを囲む最も内側のループに作用する。ネストしたループで複数層を一度に脱出する必要がある場合は、内側ループを関数として抽出し`return`で返すか、フラグ変数を使用する（#314 最終決定：break/continueはラベルなし；将来的にループラベルを導入する場合、ループ宣言側の文法に従いRFCプロセスで裁决し、証明管道の多出口設計と共に決定する）
- **ループ体内でのみ有効**：`break`は`while`/`for`ループ体内（体内にネストしたブロック/if/matchを含む）でのみ使用可能で、ループ外で出現した場合はコンパイルエラー（E1102
  `'break' outside of a loop`）
- **停止性証明に影響しない**：`while`ループは依然として停止性を証明できなければならない（decreases計量）；`break`は停止性議論に参加せず、
  `while true { break }`は受理されない
- **借用セマンティクス**：breakの制御フロー辺はRFC-009aの逆方向BFS活性分析の構造的切断に参加する（脱出した反復は逆辺活性導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループ後に移動、i == 3
    }
}

// ネストループ：breakは内側のみ脱出
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側ループのみ終了
    }
    j = j + 1                  // 外側反復の各ラウンドでここに実行が到達
}
```

### 3.5 continue文

```
ContinueStmt::= 'continue'
```

**セマンティクス**：現在の反復の残りの文をスキップし、それを囲む最も内側のループの次のラウンドに直接入る——
`while`は条件再評価に戻り、`for`は次の要素を取得する。

- **直近の1層のみに作用**：`break`と同様、ラベルなし（#314）
- **ループ体内でのみ有効**：ループ外で出現した場合はコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 以下の累算をスキップ、n == 3はカウントされない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

#### 3.9.1 セマンティクス：各反復は新しい値をバインドする

YaoXiangのforループのセマンティクスは従来言語と異なる：**各反復は新しい値をバインドし、同じ変数を変更するのではない**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行プロセス**：

| 反復  | ループ変数の振る舞い                                                       |
| ----- | -------------------------------------------------------------------------- |
| 1回目 | 新規バインド`i = 1`を作成、ループ体実行、1を出力                           |
| 2回目 | 新規バインド`i = 2`を作成（前のバインドは破棄済み）、ループ体実行、2を出力 |
| 3回目 | 新規バインド`i = 3`を作成、ループ体実行、3を出力                           |
| 4回目 | 新規バインド`i = 4`を作成、ループ体実行、4を出力                           |
| 終了  | ループ体終了、バインド破棄                                                 |

**要点**：各反復終了後、その反復で作成されたバインドは破棄される。次の反復は完全に新しいバインドであり、前の反復のバインドとは一切関係がない。

#### 3.9.2 for と for mut の違い

| 文法                | ループ変数の可変性 | 説明                           |
| ------------------- | ------------------ | ------------------------------ |
| `for i in 1..5`     | 不変               | ループ体内でバインドを変更不可 |
| `for mut i in 1..5` | 可変               | ループ体内でバインドを変更可能 |

```yaoxiang
// 合法：各反復で新しい値をバインド、変更不要
for i in 1..5 {
    print(i)  // iの値を読み取り
}

// エラー：不変バインド、変更不可
for i in 1..5 {
    i = i + 1  // エラー：不変バインドは変更不可
}

// 合法：for mut を使用すればバインド変更が許可される
for mut i in 1..5 {
    i = i + 1  // 変更可能
}
```

#### 3.9.3 シャドウィング検査

YaoXiangは変数のシャドウィングを禁止する。forループ変数は外側スコープの変数と同名にできない。

```yaoxiang
// エラー：iは外部で既に宣言されている
i = 10
for i in 1..5 {
    print(i)
}

// 正解：異なる変数名を使用
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される。詳細は[4.3 シャドウィング規則](./modules.md#43-遮蔽规则)を参照。

#### 3.9.4 他の言語との比較

| 言語     | forループ変数のセマンティクス              |
| -------- | ------------------------------------------ |
| YaoXiang | 各反復で新しい値をバインド                 |
| Rust     | 同じ変数を変更（mutが必要）                |
| Python   | 同じ変数を変更（mut不要）                  |
| C/C++    | 同じ変数を変更（ポインタまたは参照が必要） |

**設計理由**：YaoXiangがバインドセマンティクスを採用するのは以下の理由による：

1. **自然言語の意味に沿う**
   自然言語では、「集合の各要素xについて」は各xが独立した個体であることを意味する。YaoXiangの
   `for i in 1..5`
   は「1から5の各iについて」と読め、各反復のiは完全に新しいバインドであり、人間の直感的な理解と一致する。

2. **偶発的な変更の回避**
   デフォルトで不変なバインドセマンティクスは、ループ体内で偶発的にループ変数を変更できないことを意味する。複雑なループ体内のどこかで
   `i = ...` と誤って書いて追跡困難なバグを引き起こす心配がない。

3. **高性能ソリューションへの近道**
   反復間で実際に変数を再利用する必要がある場合（例：アキュムレータ、キャッシュ）、`for mut`
   で宣言すれば可変バインドモードに切り替えられる。これは暗黙の共有状態より明確である——意図は構文で明示的に表現され、ランタイム動作に隠されない。

### 3.10 spawn文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawnブロック**：明示的に並行実行領域を宣言し、ブロック内の式が並行実行される。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawnループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawnブロックは外側変数をキャプチャする**（RFC-024 §2.3、値キャプチャセマンティクス）：

- ブロック本体が外側変数を参照 =
  **値Moveキャプチャ**：値はspawn作成時点でクロージャ環境にスナップショットされ、ブロック本体はenv経由で読み取る（LoadUpvalue）
- **プリミティブ型**（Int/Float/Bool/Char）は値をコピーし、外側変数は影響を受けない
- **ハンドル型**（Struct/String/Listなど）のスナップショット = ハンドルコピー、底层オブジェクトを共有；Embeddedランタイム（デフォルト）では同一スレッド同一ヒープで、ハンドルは有効
- 複数タスク間の共有には明示的に`ref`が必要（§2.13、コンパイラが自動的にRc/Arcを選択）
- ブロック内で`return`が参照する外側変数も同様にキャプチャされる

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2は値キャプチャ、result == 6
}
```
