# 構文仕様

本文書は YaoXiang プログラミング言語の構文仕様を定義する。字句構造、構文規則、演算子の優先順位を含む。

---

## 第一章：字句構造

### 1.1 ソースファイル

YaoXiang のソースファイルは UTF-8 エンコーディングを使用しなければならない。ソースファイルの拡張子は通常
`.yx` である。

### 1.2 トークンの分類

| 種別       | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語定義済みの予約語             | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り記号 | 構文区切り                       | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiang は極めて少数のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として使用することはできない。

### 1.4 予約語

YaoXiang の「予約語」は 3 層に分かれ、それぞれパーサ（parser）と型検査器（type
checker）が異なる段階で識別する：

#### 1.4.1 リテラル予約語

パーサが独立したトークンとして持つリテラル識別子は、通常の識別子として使用できない：

| 識別子  | 所属型 | 説明                                                                                        |
| ------- | ------ | ------------------------------------------------------------------------------------------- |
| `Type`  | —      | メタ型キーワード                                                                            |
| `true`  | Bool   | ブール真値                                                                                  |
| `false` | Bool   | ブール偽値                                                                                  |
| `void`  | Void   | Void リテラル（Unit 値）。小文字 `void` は値リテラル；大文字 `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 バリアント名

バリアント名は**パターン**文脈ではパーサが識別し（裸名は scrutinee 型のバリアント集合によって判定される、§2.8 参照）、**式**文脈ではバリアントを構成する際に型限定が必要となる——`Result(Int, String).ok(5)`、`Option(T).some(v)`、`Color.green()`（RFC-010 レコード型と型：バリアントコンストラクタは型定義内の関数型フィールドであり、裸名の
`ok(5)` はコンストラクタ呼び出しではない）。

| バリアント名 | 所属型 | 説明                    |
| ------------ | ------ | ----------------------- |
| `some(T)`    | Option | Option 値バリアント構成 |
| `ok(T)`      | Result | Result 成功バリアント   |
| `err(E)`     | Result | Result エラーバリアント |

#### 1.4.3 組み込み型名

以下の型名は型検査器に事前登録されており、インポートなしで型位置で使用可能。パーサはこれらを通常の識別子として扱う——**予約語ではなく、局所バインディングで shadow 可能（非推奨）**。

| 型名     | 論理的対応   | 説明                                                                                                                               |
| -------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤（真/Unit） | ゼロフィールドの積型で、唯一の住人（`void` リテラル、§1.4.1 参照）を有する                                                         |
| `Never`  | ⊥（偽/空型） | ゼロバリアントの和型で、住人がゼロ。`Never` 値を生成する式は存在しない。`Never <: T` はすべての `T` に対して成立する（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                                       |
| `Float`  | —            | 浮動小数点数                                                                                                                       |
| `Bool`   | —            | ブール値：`true` / `false`                                                                                                         |
| `Char`   | —            | Unicode 文字                                                                                                                       |
| `String` | —            | 文字列                                                                                                                             |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、以降の文字は文字、数字、またはアンダースコアである。識別子は大文字小文字を区別する。

特殊な識別子：

- `_` はプレースホルダとして用いられ、値を無視することを表す
- アンダースコア始まりの識別子はプライベートメンバーを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // ターゲット型注釈が Array(T, N) の場合、リテラルは固定長配列に決着
```

> **辞書リテラルは少なくとも一つのキーと値のペアを要求する**：`{}`
> **は**空辞書**ではない**——空ブロック（値
> `Void`、参照：[§2.9](#_2-9-ブロック式)）である。空辞書にはコンストラクタ `dict.new()`
> を使用すること：
>
> ```yaoxiang
> empty = dict.new()                  // ✅ 空辞書
> d = { "a": 1 }                       // ✅ 辞書リテラル
> wrong = {}                           // ❌ これは辞書ではなく、空ブロック（Void）である
> ```
>
> **判定基準は内容**：`Dict` 文法は少なくとも一つの `String ':' Expr` を要求し、`{}`
> には判断材料となる内容がないため、ブロック構造のゼロ形態を取る。非空形態は内容が自己記述する（`{ "k": v }`
> はキーと値のペアを持つ → 辞書）——これは `f = { 5 }` が関数ではなく `Int`
> 値であることと同源である：**型は内容によって決定される**。

> Set にはリテラル文法もランタイム表現も存在しない——集合型は計画中であり、要件が発生した際に Dict パターンに従って補完する（std.set +
> HeapValue::Set）。List/Dict リテラルは、文脈型注記によって決定される：裸リテラルと `List(T)`
> 注記は拡張可能リストに決着し；`Array(T, N)`
> 注記がリテラルに直接作用する場合は固定長配列に決着する。List→Array の暗黙的変換は禁止。
>
> Array リテラルセマンティクス：
>
> - 要素数は N と一致しなければならず、不一致の場合はコンパイル時 E1002；空リテラルに非ゼロ N を割り当てる場合も拒否される
> - 各要素の型は T と互換でなければならず、不一致の場合はコンパイル時 E1002
> - N の文法形式：整数リテラル（負数可）または定数名のみ；複合式（例：`2+1`）は解析時に拒否される
> - N がシンボル定数（関数の const パラメータ、例：`Array(Int, n)`）の場合、個数検査は精化型フェーズに延期される
> - v1 のネストした配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否され、層ごとに明示的に構築する必要がある；再帰的な決着は後続バージョンに持ち越される

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **挙動の厳格化（移行記録）**：反復変数の文法は元から `'for' Identifier 'in'`
> だが、旧実装では pattern が完全な pratt 解析を行っていた——`'in'` が中置演算子として登録された後、
> `x` は `in items`
> を membership 式として飲み込んでいた。修正後は非識別子 pattern の解析が直接失敗し、旧実装のように
> `_` にフォールバックしなくなった（エラーの無音吸収）。影響範囲：以前は解析できていた
> `[x for (a, b) in pairs]`
> のような記述は現在エラーとなる——この形式は定義された挙動を持たず（変数は常に
> `_`）、厳格化の方向は正しく、意味的な移行コストはない。

#### 1.6.6 メンバー検査

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子で、`Bool` を返す——ヒットすれば `true`、ヒットしなければ `false`
> で、エラーは発生しない。意味の分割：`[]` は存在をアサートして値を取り出す（失敗でエラー）、 `in`
> は存在を問い合わせる（未ヒットは通常の `false`）。右オペランドの範囲：List / Array /
> Dict(キー集合) / Tuple / String(部分文字列) / Range(区間)。`in`
> は一級のホール述語であり、精化型フェーズではコンパイル時に証明可能な命題の基底となる。（Set は右オペランドリストから除外——Set にはランタイム表現がない、§1.6.4 参照）

### 1.7 コメント

```
// 単一行コメント

/* 複数行コメント
   複数行にまたがることができる */
```

### 1.8 インデント規則

コードは 4 スペースのインデントを使用しなければならず、Tab 文字の使用は禁止されている。これは強制的な構文規則である。

## 第二章：構文規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強く結合する：呼び出しとメンバアクセスの直下のみであり、すべての二項演算子より高い。したがって
> `!a == b` ≡ `(!a) == b`（Zig 式セマンティクス）；`!`
> は純粋な単項演算であり、短絡制御フローには参加せず、 `and`/`or`
> キーワード（短絡）と直交する（RFC-010 権威定義）。

> **Range の結合力**：`..` の結合力 (6, 7)——左 6 は加算（7）より低く、右 7 は加算を吸収するが同級の
> `..` は吸収しない。変更前後の対照：
>
> | 式           | 変更前（レベル 1、右結合）                                                                  | 変更後（(6,7)、左結合）                                                    |
> | ------------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10`（`in` の右オペランドレベル 4、`..` レベル 1 では吸収できず、実際には解析不可） | `x in (1..10)`——区間全体が `in` の右オペランド                             |
> | `0..n+2`     | `(0..n)+2`（右結合の落とし穴：上限が食べられ、`for` ループは直接 E3004）                    | `0..(n+2)`——上限は算術式                                                   |
> | `a == b..c`  | `a == (b..c)`（`..` レベル 1 < `==` レベル 3、本来は全体）                                  | `a == (b..c)`——**セマンティクス不変**、`..` は依然として比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                                                  | `1..(2*3)`——上限は算術式                                                   |
> | `a..b..c`    | `a..(b..c)`（右結合チェーン、意味のない Range の入れ子）                                    | `(a..b)..c`——**step 形式**（`c` はステップ幅）                             |
>
> 純効果：複合上限 `for i in 0..n+2` が「解析成功だが E3004」から「直接使用可能」に； `x in 1..10`
> が「解析不可」から「区間検査」に；`a..b..c` が「意味のない入れ子」から「step 成分」に。レベル 6 は
> `+`（レベル 5）と
> `<<`（レベル 7）の間に位置し、数学的慣習に従う：区間は強く結合する構文であり、上限は当然完全な算術式となる。

### 2.3 関数呼び出し

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

名前付き引数は `name = value` 形式（RFC-010 §関数定義、RFC-011
§構成形式）。位置引数は名前付き引数の前に置かなければならない；順序指定された引数は名前付き引数内で任意の順序で配置可能：

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // 位置形式
add(a = 3, b = 5)  // 名前付き形式
add(b = 5, a = 3)  // 順序は任意
add(3, b = 5)      // 混在、位置が前
```

名前付き引数の名前が間違っている場合は **E1014**、同じ仮引数が位置と名前の両方で指定された場合は
**E1015**、個数が一致しない場合は **E1010**（RFC-013）。

### 2.4 メンバアクセス

```
MemberAccess::= Expr '.' Identifier
```

### 2.5 インデックスアクセス

```
IndexAccess ::= Expr '[' Expr ']'
```

> **三層セマンティクス（RFC-011b）**：`a[i]` は `a`
> の型によって分岐する——① 組み込みコンテナ（List/Vec/Array/Dict/Tuple）はネイティブインデックス命令を経由（高速パス）；②
> `Index` インターフェースを実装したユーザー型はその `index`
> メソッドにディスパッチされる（型本体内で `Index(Grid, Int, Float)` のインスタンス化 + `Grid.index`
> メソッド）；③ RFC-004 の `f[0]`
> 位置バインディングはバインディング宣言にのみ存在し、本文法は経由しない。多次元インデックス
> `a[0, 1]` のキーはタプルとしてパックされる。`Index` を実装していない他の型は型レベルで拒否される。

### 2.6 型変換

```
TypeCast    ::= Expr 'as' TypeExpr
```

### 2.7 条件式

```
IfExpr      ::= 'if' Expr Block ('else' 'if' Expr Block)* ('else' Block)?
```

### 2.8 パターンマッチング

```
MatchExpr   ::= 'match' Expr '{' MatchArm+ '}'
MatchArm    ::= Pattern ('|' Pattern)* ('if' Expr)? '=>' Expr ','
Pattern     ::= Literal
              | Identifier
              | Wildcard
              | StructPattern
              | TuplePattern
              | EnumPattern
              | OrPattern
```

> **バリアント分解のバリアント集合要件**（RFC-010b）：`EnumPattern`（`ok(v)`、`some(x)`
> 等のバリアント名は scrutinee によって判定）は、scrutinee の型が**バリアント集合が含まれる和型**であることを要求する。バリアント集合は型定義または
> `use` インポートによってのみ検査器に入る——`Result`/`Option` は `std.result`/`std.option`
> で定義されており、使用前に `use std.result` / `use std.option`
> が必要である（モジュール全体とグループ `use std.{...}`
> の二つの形式は同等の効力を持つ）；それ以外の場合、バリアント分解は E1002 を報告する。網羅性判定も同源：フォールバックアームは網羅性を免除し、フォールバックアームがない場合はバリアント集合を完全に照合する。

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt 間の区切りと改行の挙動（`;`
> による明示的な区切り、改行による終端、継続行の例外、行頭 `(`/`[` は決して結合しない）は
> [RFC-038](../../design/rfc/accepted/038-statement-termination.md) で定義される。

#### 2.9.1 `{` の三つの形式

`{` は式位置に**正確に三つの解釈**を持ち、**内容**によって一度だけ判定される：

| 形式             | 記法              | 型           | 例               |
| ---------------- | ----------------- | ------------ | ---------------- |
| **空ブロック**   | `{}`              | `Void`       | `x: Void = {}`   |
| **辞書リテラル** | `{ "k": v, ... }` | `Dict(K, V)` | `d = { "a": 1 }` |
| **ブロック**     | `{ Stmt* Expr? }` | 末尾式の型   | `y = { 1 + 1 }`  |

**判定順序**：

1. `{}`（内容なし）→ **空ブロック**、値 `Void`
2. 最初の要素が `String ':' Expr` のキーと値のペア → **辞書リテラル**
3. その他 → **ブロック**、値は末尾式によって与えられる

> **なぜ `{}` は空辞書ではないか**：空辞書の「空」は自己記述できない（`Dict(K, V)`
> にも空ブロックにもなり得る）、そして辞書文法 [§1.6.4](#_1-6-4-コレクション)
> は少なくとも一つのキーと値のペアを要求する。判断材料となる内容がない場合、ブロック構造のゼロ形態を取る：これは
> `unsafe {}` / `spawn {}` と一致し、特例を導入しない。空辞書には `dict.new()` を使用する。
>
> **なぜ関数には注記が必要か**：`f = { stmt }`
> は**値**（末尾式の型）であり、関数ではない。関数を定義するには Fn 注記を明記する：`f: () -> Int = { 5 }`。これは辞書と同じ原則に従う：**型は内容によって決定され**、注記の存在与否によって決定される。（この規則は
> [RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md) 付録 D を参照。）

**統一セマンティクス**：すべての `{}` ブロックの値は**末尾式**によって与えられ、`return` は `Never`
型の非局所的退出である。

| ブロック型  | 値の出口 | 空ブロック `{}` |
| ----------- | -------- | --------------- |
| 通常の `{}` | 末尾式   | `Void`          |
| `unsafe {}` | 末尾式   | `Void`          |
| `spawn {}`  | 末尾式   | `Void`          |

**核心原則**（詳細は [RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md)
を参照）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**の場合、ブロックの値は `Void`；`Void` が欲しい場合は明示的に `Void` と書く
- **`return` は最も近い関数境界を退出する**（すべてのブロックを貫通し、ブロックに「返さない」）、型
  `Never`；`Never <: T`

> は任意の型に対して成立する（爆発原理）ため、任意の戻り型の位置に配置可能

- 式形式 `= expr` は値を直接与える

```yaoxiang
// 通常の {} ブロック：末尾式が値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式が型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式が結果を与える
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // ブロックの値
}

// return：ブロックを貫通し、関数を退出する
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if を貫通し、関数本体を退出する
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数かブロック値か？

`name = { ... }`
は関数定義（RFC-007「空パラメータの最簡」）にもブロック値バインディングにもなり得る。**注記優先、デフォルトは関数**によって判定する（RFC-010a 付録 D）：

| ケース              | 結果           | 例                                 |
| ------------------- | -------------- | ---------------------------------- |
| 値が Lambda（`=>`） | 関数           | `f = () => 5` → `f()` = 5          |
| 注記が関数型        | 関数           | `f: () -> Int = { 5 }` → `f()` = 5 |
| 注記が非関数型      | **ブロック値** | `x: Int = { 5 }` → `x` = 5         |
| 注記なし            | 関数           | `f = { 5 }` → `f()` = 5            |

**注記即是型**：`x: Int = ...` は `x` が `Int` であることを宣言する。よって `{ ... }` は `Int`
として評価される； `f: () -> Int = ...` は `f` が関数であることを宣言する。よって `{ ... }`
は関数本体である。

`{ ... }` を即座に評価したい場合、**ターゲット型を記述するだけでよい**（新しい構文は不要）：

```yaoxiang
// ブロック値：即座に評価
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：注記なしの場合はデフォルト
f = { 5 }        // f() = 5
```

#### ネストした関数型：カリー化か、関数を返すか？

`->` の右側のネストした関数型には二つの読み方があり、**括弧**によって区別される（RFC-004）：

| 記述                            | 意味           | 呼び出し            |
| ------------------------------- | -------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **カリー化**   | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **関数を返す** | `g(1)` で関数を得る |

根拠：**注記即是型**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int`
を宣言する。よって `g(1)` は「次のパラメータ」ではなく、**その関数そのもの**でなければならない。

```yaoxiang
// カリー化：二段のパラメータを層ごとに渡す
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数を返す：外側は一段のパラメータで、返されるのが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返された関数は変数に保存でき、受け渡しも可能
```

括弧なしのネストした `Fn` はすべてカリー化（RFC-011 の型パラメータ形式を含む）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型検査**：括弧は戻り型を宣言し、body はその型を生成しなければならない。
`f: () -> (() -> Int) = { 7 }` は誤り——期待される型は `() -> Int` だが、実際の型は `Int`
である（E1002）。

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子で、優先順位は `.` と同レベル。`Result(T, E)` 型に対して：

- `Ok(v)` の場合、値 `v` を抽出して実行を継続する
- `Err(e)` の場合、エラーを上位に伝播する（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時は値を抽出し、失敗時は上位に伝播
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は範囲値を作成する（Range は一級値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値：バインド、受け渡し、メンバー判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step 形式（第三成分、デフォルト 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **step セマンティクス**：`a..b..c` において `c` はステップ幅である。`c = 0`
> のリテラルはコンパイル時に拒否される；動的な `c`
> の場合はランタイムゼロチェック（E6001 系統；エラーシステムが実装された後に Result に格上げ）。
> `c < 0` は合法であり、区間方向は符号に従って反転する（`10..0..(-2)` は減少）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref`
は共有所有を作成する。コンパイラは自動的に Rc（単一タスク）または Arc（タスク間）を選択し、ユーザーは実装詳細を気にする必要がない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク間：コンパイラが自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型の定義と生ポインタの操作に使用される。`return`
を使用して、型定義を上位スコープに返す。

**セマンティクス**：

- `unsafe {}` 内では型の定義と生ポインタの操作が可能
- 返された型は `unsafe {}` 外で使用可能
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロック内で不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外で使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックはスコープを作成する
- 内側のスコープは外側のスコープの変数にアクセス可能
- 外側のスコープは内側のスコープの変数にアクセス不可
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で可視
}
// x はこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数外では不可視
```

**変数宣言とシャドウイング**：

- `x = value`：スコープチェーンを外側に辿って x を検索し、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的な新規可変宣言、外側と同名は禁止
- 同一スコープ内で同じ名前を宣言できるのは一度だけ

> **詳細定義**：スコープの完全な規則、変数宣言とシャドウイングの仕組みについては
> [モジュールシステム仕様](./modules.md#第四章作用域) を参照。

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**セマンティクス**：`return`
は**非局所的退出**であり、最も近い**関数境界**を退出する（すべてのブロックを貫通する——`if` / `while`
/ `for` / `match` / 裸ブロック / `spawn` / `unsafe`
を含む）、値を呼び出し手に渡す。これはブロックに「返さない」。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'`
に対して成立する（爆発原理、参照： [型システム §2.2](./type-system.md)）。よって `return`
は任意の戻り型の位置に配置可能であり、追加の規則制約は不要。

**ブロック評価との関係**：ブロックの値は常に**末尾式**である（§2.9 参照）。`{ return n }`
はブロックとして値が `n` で型 `Never` である；同時に `return`
の作用は関数を退出すること。**二つの事象は同時に成立し**、爆発原理によって共存する。

`return` と末尾式は共同で「早期リターン」を成立させ、`return`
が関数を特指する追加の規則は不要である——参照：
[RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md)。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通し、関数を退出する（型 Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**セマンティクス**：所在する最も内側の `while`/`for`
ループを即座に終了し、制御フローをそのループ本体の後へ遷移する。

- **直近の一層のみを出る**：`break`

> は常にそれを含む最も内側のループに作用する。ネストしたループで複数層を一度に飛び出す必要がある場合は、内側のループを関数に抽出して
> `return`
> で返すか、フラグ変数を使用する（break/continue にはラベルがない；将来ループラベルを導入する場合は、ループ宣言側の構文に従って RFC プロセスを経るものとし、証明パイプラインの複数出口設計とともに判断する）

- **ループ体内のみ**：`break` は `while`/`for`

> ループ体内（本体内にネストしたブロック/if/match を含む）にのみ出現可能、ループ外に出現するとコンパイルエラー（E1102
> `'break' outside of a loop`）

- **停止性証明に影響しない**：`break`

> は停止性の議論に参加しない——測度を提供せず、測度の減少ステップを構成しない；ループの停止義務は
> `break`
> とは無関係であり、精化型によってトリガーされる（[type-system §8.4](./type-system.md#84-terminates停止測度述語)
> 参照）

- **借用セマンティクス**：break の制御フロー辺は RFC-009a の逆方向 BFS 活性分析の構造的切断に参加する（飛び出したイテレーションは逆辺活性の導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループの後へ遷移、i == 3
    }
}

// ネストしたループ：break は内側のみを出る
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側のループのみを終了
    }
    j = j + 1                  // 外側の各イテレーションはここで実行される
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**セマンティクス**：現在のイテレーションの残りの文をスキップし、所在する最も内側のループの次のラウンドに直接入る——
`while` は条件の再評価に戻り、`for` は次の要素を取得する。

- **直近の一層のみに作用**：`break` と同様、ラベルなし
- **ループ体内のみ**：ループ外に出現するとコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 以下の累算をスキップ、n == 3 は集計されない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block

#### 3.9.1 セマンティクス：各イテレーションは新しい値をバインドする

YaoXiang の for ループセマンティクスは従来の言語と異なる：**各イテレーションは同じ変数を変更するのではなく、新しい値をバインドする**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行プロセス**：

| イテレーション | ループ変数の挙動                                                                          |
| -------------- | ----------------------------------------------------------------------------------------- |
| 1 回目         | 新しいバインディング `i = 1` を作成し、本体実行、1 を出力                                 |
| 2 回目         | 新しいバインディング `i = 2` を作成（以前のバインディングは破棄済み）、本体実行、2 を出力 |
| 3 回目         | 新しいバインディング `i = 3` を作成し、本体実行、3 を出力                                 |
| 4 回目         | 新しいバインディング `i = 4` を作成し、本体実行、4 を出力                                 |
| 終了           | 本体終了、バインディング破棄                                                              |

**要点**：各イテレーション終了後、そのイテレーションで作成されたバインディングは破棄される。次のイテレーションは完全に新しいバインディングであり、前のイテレーションのバインディングとは関係がない。

#### 3.9.2 for と for mut の違い

| 構文                | ループ変数の可変性 | 説明                                   |
| ------------------- | ------------------ | -------------------------------------- |
| `for i in 1..5`     | 不変               | ループ本体内でバインディングを変更不可 |
| `for mut i in 1..5` | 可変               | ループ本体内でバインディングを変更可能 |

```yaoxiang
// 合法：各イテレーションで新しい値をバインドするため、変更は不要
for i in 1..5 {
    print(i)  // i の値を読み取る
}

// エラー：不変バインディングは変更不可
for i in 1..5 {
    i = i + 1  // エラー：不変バインディングは変更不可
}

// 合法：for mut を使用すればバインディングの変更が可能
for mut i in 1..5 {
    i = i + 1  // 変更可能
}
```

#### 3.9.3 シャドウイングチェック

YaoXiang は変数のシャドウイングを禁止する。for ループ変数は外側スコープの変数と同名にできない：

```yaoxiang
// エラー：i はすでに外部で宣言されている
i = 10
for i in 1..5 {
    print(i)
}

// 正しい：異なる変数名を使用
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される。詳細は
[4.3 シャドウイング規則](./modules.md#43-シャドウイング規則) を参照。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数のセマンティクス             |
| -------- | ------------------------------------------ |
| YaoXiang | 各イテレーションで新しい値をバインド       |
| Rust     | 同じ変数を変更（mut が必要）               |
| Python   | 同じ変数を変更（mut 不要）                 |
| C/C++    | 同じ変数を変更（ポインタまたは参照が必要） |

**設計理由**：YaoXiang がバインディングセマンティクスを採用するのは：

1. **自然意味論に沿う**
   自然言語では「集合の各要素 x について」は各 x が独立した個体であることを意味する。YaoXiang の
   `for i in 1..5`
   は「1 から 5 の各 i について」と読まれ、各イテレーションの i は完全に新しいバインディングであり、人間の直感的理解と一致する。

2. **偶発的な変更を防ぐ**
   デフォルトで不変なバインディングセマンティクスは、ループ本体内で偶発的にループ変数を変更できない。複雑なループ本体内のどこかで誤って
   `i = ...` と書いてしまっても、追跡困難なバグが発生する心配がない。

3. **高性能なソリューションが容易**
   イテレーション間で実際に変数を再利用する必要がある場合（例：アキュムレータ、キャッシュ）、`for mut`

> を使用するだけで可変バインディングモードに切り替えられる。これは暗黙的な共有状態よりも明確である——意図は構文によって明示的に表現され、ランタイムの挙動に隠されない。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：並行実行領域を明示的に宣言し、ブロック内の式は並行実行される。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側の変数をキャプチャする**（RFC-024 §2.3、値キャプチャセマンティクス）：

- ブロック本体が外側変数を参照する =

> **値 Move キャプチャ**：値は spawn 作成時点でクロージャ環境にスナップショットされ、ブロック本体は env を介して読み取る（LoadUpvalue）

- **プリミティブ**（Int/Float/Bool/Char）は値をコピーし、外側変数は影響を受けない
- **ハンドル型**（Struct/String/List 等）のスナップショット = ハンドルコピー、底层オブジェクトを共有；Embedded ランタイム（デフォルト）では同一スレッド同一ヒープ、ハンドルは有効
- 複数タスク間の共有には明示的な `ref` が必要（§2.13、コンパイラが自動的に Rc/Arc を選択）
- ブロック内の `return` が参照する外側変数も同様にキャプチャされる

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 は値キャプチャ、result == 6
}
```

### 3.11 プログラムエントリとトップレベル文

ソースファイルはコンパイラの観点で二つの役割を持つ。**`yaoxiang.toml`
の存在与否によって決定される**：

| 役割       | 判定                                         | プログラム本体                                                    |
| ---------- | -------------------------------------------- | ----------------------------------------------------------------- |
| **Script** | 単一ファイルを直接実行、`yaoxiang.toml` なし | **トップレベル文**（記述順に実行）；`main` は通常のバインディング |
| **Bin**    | `yaoxiang.toml` が存在                       | **`main` 関数**；トップレベルに実行可能な文は記述不可             |

#### Script：トップレベル文がプログラム

マニフェストがない場合、ファイルは「スクリプト」であり、**トップレベル文が記述順に実行される**：

```yaoxiang
use std.io
io.println("hello")          // 直接実行
x: Int = { 42 }              // トップレベルバインディング：ランタイム初期化
io.println(x)                // 42
```

このモードでは `main` は**特別ではない**——通常のバインディングに過ぎない。`main`
を実行させたい場合は明示的に呼び出す必要がある：

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← この行が必須
```

> **なぜ `main` を自動的に呼び出さないのか？**
> トップレベル文がすでにプログラム本体である。ここで暗黙的に `main` を呼び出すと、明示的に `main()`
> を記述したスクリプトは二回実行されることになる。二つの規則は共存できないため、Script モードでは「トップレベル文」のみが実行エントリとなる。

#### Bin：`main` がエントリ

マニフェストがある場合、ファイルは「実行可能ターゲット」であり、この場合：

- `main`
  を定義しなければならず、それは関数でなければならない（シグネチャはゼロ引数呼び出し可能であること）
- トップレベルに実行可能な文は記述不可——プログラム本体は `main` そのものである

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

`main` の欠落または `main` が関数でないことはコンパイルエラーである（前者：`main`
がない場合すべての関数は到達不能；後者：値バインディングは呼び出されない）。

> **ライブラリファイル**：他のファイルに `use` されるファイル、または `[lib].path` / `[exports]`
> が指すファイルは `main` を要求しない——これらはプログラムエントリではない。

#### トップレベルバインディングの初期化

トップレベルバインディングの初期化値は**ランタイムで評価され**、コンパイル時定数であることは要求されない：

```yaoxiang
answer: Int = { 42 }              // ブロック値
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // 関数呼び出し
```

初期化は**依存順**で実行され、記述順には依存しない：

```yaoxiang
derived: Int = base * 3           // 後で宣言された base を参照
base: Int = 7                     // 先に初期化（トポロジカルソート）
```

循環依存はコンパイルエラーである（環上の名前が列挙される）：

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // エラー：a → b → a
```

> **設計根拠**：RFC-029f（ファイル役割モデル）、RFC-010a 付録 D（ブロックバインディング判定）。
