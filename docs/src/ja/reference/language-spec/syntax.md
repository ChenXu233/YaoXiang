# 文法仕様

本文書は YaoXiang プログラミング言語の文法仕様を定義する。字句構造、文法規則、演算子の優先順位を含む。

---

## 第一章：字句構造

### 1.1 ソースファイル

YaoXiang のソースファイルは UTF-8 エンコーディングでなければならない。ソースファイルの拡張子は通常
`.yx` である。

### 1.2 字句要素の分類

| カテゴリ   | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語の予約語                     | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り記号 | 文法上の区切り                   | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiang はごく少数のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として使用することはできない。

### 1.4 予約語

YaoXiang の「予約語」は 3 階層に分かれ、それぞれパーサと型検査器が異なる段階で識別する：

#### 1.4.1 リテラル予約語

パーサが独立したトークンとして持つリテラル識別子は、通常の識別子として使用できない：

| 識別子  | 所属型 | 説明                                                                                            |
| ------- | ------ | ----------------------------------------------------------------------------------------------- |
| `Type`  | —      | メタ型キーワード                                                                                |
| `true`  | Bool   | 真の値                                                                                          |
| `false` | Bool   | 偽の値                                                                                          |
| `void`  | Void   | Void リテラル（Unit 値）。小文字の `void` は値リテラル；大文字の `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 コンストラクタ式

以下のコンストラクタはパターンマッチと式の文脈でパーサにより認識される：

| コンストラクタ | 所属型 | 説明                                |
| -------------- | ------ | ----------------------------------- |
| `some(T)`      | Option | Option の値バリアントコンストラクタ |
| `ok(T)`        | Result | Result の成功バリアント             |
| `err(E)`       | Result | Result のエラーバリアント           |

#### 1.4.3 組み込み型名

以下の型名は型検査器に事前登録されており、インポートなしでも型位置で使用できる。パーサはこれらを通常の識別子として扱う——**予約語ではないため、ローカルバインディングでシャドウイング可能（推奨されない）**。

| 型名     | 論理的対応   | 説明                                                                                                                 |
| -------- | ------------ | -------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤（真/Unit） | ゼロフィールドの積型、ちょうど 1 つの居住者（`void` リテラル、§1.4.1 参照）                                          |
| `Never`  | ⊥（偽/空型） | ゼロバリアントの和型、居住者ゼロ。`Never` 型の式は存在しない。`Never <: T` はすべての `T` に対して成立（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                         |
| `Float`  | —            | 浮動小数点数                                                                                                         |
| `Bool`   | —            | 真偽値：`true` / `false`                                                                                             |
| `Char`   | —            | Unicode 文字                                                                                                         |
| `String` | —            | 文字列                                                                                                               |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、後続の文字は文字、数字、またはアンダースコアである。識別子は大文字小文字を区別する。

特殊識別子：

- `_` はプレースホルダとして使用され、値を無視することを表す
- アンダースコアで始まる識別子はプライベートメンバを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // ターゲット型注釈が Array(T, N) の場合リテラルは固定長配列に落ちる
```

> **辞書リテラルは少なくとも 1 つのキーと値のペアを要求する**：`{}`
> は**空辞書ではない**——空ブロック（値 `Void`、 [§2.9](#_2-9-ブロック式)
> 参照）である。空の辞書はコンストラクタ `dict.new()` を使用すること：
>
> ```yaoxiang
> empty = dict.new()                  // ✅ 空辞書
> d = { "a": 1 }                       // ✅ 辞書リテラル
> wrong = {}                           // ❌ これは辞書ではなく、空ブロック（Void）
> ```
>
> **判定基準は内容**：`Dict` 文法は少なくとも 1 つの `String ':' Expr` を要求し、`{}`
> は内容が空のため、ブロック構造のゼロ形態が選択される。非空形態は内容が自己記述する（`{ "k": v }`
> はキーと値のペアを持つ → 辞書）——これは `f = { 5 }` が関数ではなく `Int`
> 値であることと同源である：**型は内容により決定される**。

> Set にはリテラル文法もランタイム表現もない——コレクションタイプの計画において、要件が発生次第 Dict パターンに倣って補完する（std.set +
> HeapValue::Set）。List/Dict リテラルの落点は文脈型注釈により決定される：素のリテラルと `List(T)`
> 注釈は拡張可能リストに落ち；`Array(T, N)`
> 注釈がリテラルに直接作用する場合は固定長配列に落ちる。暗黙の List→Array 変換は禁止。
>
> Array リテラルセマンティクス：
>
> - 要素数は N と一致しなければならず、不一致はコンパイル時に E1002；空リテラルに非ゼロ N も同様に拒否
> - 各要素の型は T と互換でなければならず、不一致はコンパイル時に E1002
> - N の文法形態：整数リテラル（負可）または定数名のみ；複合式（例：`2+1`）はパース時に拒否
> - N がシンボル定数（関数の const 引数、例：`Array(Int, n)`）の場合、要素数の検証は精化型フェーズまで延期
> - v1 のネスト配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否され、層ごとに明示的に構築する必要がある；再帰落点は将来のバージョンに持ち越し

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **挙動の厳格化（移行記録）**：反復変数の文法は元から `'for' Identifier 'in'`
> だが、旧実装では pattern が完全な pratt 解析を経由していた——`'in'`
> が中置演算子として登録された後、`x` が `in items`
> をメンバシップ式として吸収していた。修正後は非識別子 pattern は直接パース失敗となり、旧実装のように
> `_` にフォールバック（静かにエラーを吸収）することはなくなった。影響範囲：以前パース可能だった
> `[x for (a, b) in pairs]`
> のような書き方は現在エラーになる——この形式には定義された動作がなかった（変数は常に
> `_`）、厳格化の方向は正しく、意味的移行コストはない。

#### 1.6.6 メンバシップテスト

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子であり、`Bool` を返す——ヒットすれば `true`、ミスすれば
> `false`、エラーは発生しない。意味的分割：`[]` は存在をアサートして値を取り出す（失敗でエラー）、
> `in` は存在を問う（ミスは正常な `false`）。右被演算子のカバレッジ：List / Array / Dict(キーセット)
> / Tuple / String(部分文字列) / Range(区間)。`in`
> は第一級ホール述語であり、精化型フェーズでコンパイル時に証明可能な命題の基底となる。（Set は右被演算子リストから除外——Set にはランタイム表現がない、§1.6.4 参照）

### 1.7 コメント

```
// 単行コメント

/* 複数行コメント
   複数行に渡ることができる */
```

### 1.8 インデント規則

コードは 4 スペースのインデントを使用しなければならず、Tab 文字の使用は禁止。これは強制的な文法規則である。

## 第二章：文法規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強い結合を持つ：呼び出しとメンバアクセスのみより低く、すべての二項演算子より高い。したがって
> `!a == b` ≡ `(!a) == b`（Zig 風セマンティクス）；`!`
> は純粋な単項演算であり、短絡制御フローには参加せず、`and`/`or`
> キーワード（短絡）と直交する（RFC-010 の権威ある定義）。

> **Range の結合力**：`..` の結合力は (6,
> 7)——左 6 は加算（5）未満、右 7 は加算を吸収するが同レベルの `..` は吸収しない。変更前後の対比：
>
> | 式           | 変更前（レベル 1、右結合）                                                                    | 変更後（(6,7)、左結合）                                            |
> | ------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
> | `x in 1..10` | `x in 1..10`（`in` の右被演算子レベル 4、`..` のレベル 1 では吸収できず、実際にはパース不可） | `x in (1..10)`——区間全体が `in` の右被演算子として機能             |
> | `0..n+2`     | `(0..n)+2`（右結合の罠：上界が食べられ、`for` ループで直接 E3004）                            | `0..(n+2)`——上界は算術式                                           |
> | `a == b..c`  | `a == (b..c)`（`..` のレベル 1 < `==` のレベル 3、必然的に全体）                              | `a == (b..c)`——**意味は不変**、`..` は依然として比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                                                    | `1..(2*3)`——上界は算術式                                           |
> | `a..b..c`    | `a..(b..c)`（右結合の連鎖、意味のない Range の入れ子）                                        | `(a..b)..c`——**step 形式**（`c` はステップ）                       |
>
> 純効果：複合上界 `for i in 0..n+2` が「パース成功だが E3004」から「直接使用可能」に；`x in 1..10`
> が「パース不可」から「区間チェック」に；`a..b..c`
> が「無意味な入れ子」から「step 成分」に。レベル 6 は `+`（レベル 5）と
> `<<`（レベル 7）の間に位置し、数学的慣例に合致：区間は強く結合する構造であり、上界は当然完全な算術式である。

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt 間の区切りと改行の振る舞い（`;`
> による明示的な区切り、改行による終端、継続行の例外、行頭の `(`/`[` は決してマージされない）は
> [RFC-038](../design/rfc/draft/038-statement-termination.md) で定義される。

#### 2.9.1 `{` の 3 つの形態

`{` は式位置にちょうど 3 つの解釈を持ち、**内容により一度に判定される**：

| 形態             | 記法              | 型           | 例               |
| ---------------- | ----------------- | ------------ | ---------------- |
| **空ブロック**   | `{}`              | `Void`       | `x: Void = {}`   |
| **辞書リテラル** | `{ "k": v, ... }` | `Dict(K, V)` | `d = { "a": 1 }` |
| **ブロック**     | `{ Stmt* Expr? }` | 末尾式の型   | `y = { 1 + 1 }`  |

**判定順序**：

1. `{}`（内容なし）→ **空ブロック**、値 `Void`
2. 最初の要素が `String ':' Expr` のキーと値のペア → **辞書リテラル**
3. それ以外 → **ブロック**、値は末尾式により与えられる

> **なぜ `{}` は空辞書ではないのか**：空辞書の「空」は自己記述できない（`Dict(K, V)`
> にも空ブロックにもなり得る）、一方辞書文法 [§1.6.4](#_1-6-4-コレクション)
> は少なくとも 1 つのキーと値のペアを要求する。内容の根拠がない場合、ブロック構造のゼロ形態を取る：これは
> `unsafe {}` / `spawn {}` と一致し、特例を導入しない。空辞書には `dict.new()` を使用すること。
>
> **なぜ関数には注釈が必要なのか**：`f = { stmt }`
> は**値**（末尾式の型）であり、関数ではない。関数を定義するには Fn 注釈を明示する：`f: () -> Int = { 5 }`。これは辞書と同じ原則である：**型は内容により決定され**、注釈の存在有無により決定されるのではない。（この規則は RFC-010a 付録 D 裁決 C の「注釈なし → デフォルトで関数」を置き換える、正誤表参照。）

**統一セマンティクス**：すべての `{}` ブロックの値は**末尾式**により与えられ、`return` は `Never`
型の非局所的退出である。

| ブロック型  | 値の出口 | 空ブロック `{}` |
| ----------- | -------- | --------------- |
| 通常の `{}` | 末尾式   | `Void`          |
| `unsafe {}` | 末尾式   | `Void`          |
| `spawn {}`  | 末尾式   | `Void`          |

**核となる原則**（詳細は [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)
参照）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**の場合、ブロックの値は `Void`；`Void` が欲しいなら明示的に `Void` と書く
- **`return`
  は最も近い関数境界を退出する**（すべてのブロックを貫通する、ブロックに「戻す」ことはない）、型は
  `Never`；`Never <: T` は任意の方に対して成立（爆発原理）、したがって任意の方を返す位置に出現可能
- 式の形式 `= expr` は直接値を与える

```yaoxiang
// 通常の {} ブロック：末尾式が値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式が型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式が結果を与える（⚠️ 未実装、#365 参照；現状は return が必要）
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    return (result1, result2)   // ブロックの値
}

// return：ブロックを貫通し、関数を退出する
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if と関数本体を貫通し、関数を退出
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数かブロック値か？

`name = { ... }`
は関数定義（RFC-007「最小空引数」）にもブロック値バインディングにもなり得る。**注釈優先、デフォルトで関数**の裁決に従う（RFC-010a 付録 D）：

| ケース              | 結果           | 例                                 |
| ------------------- | -------------- | ---------------------------------- |
| 値が Lambda（`=>`） | 関数           | `f = () => 5` → `f()` = 5          |
| 注釈が関数型        | 関数           | `f: () -> Int = { 5 }` → `f()` = 5 |
| 注釈が非関数型      | **ブロック値** | `x: Int = { 5 }` → `x` = 5         |
| 注釈なし            | 関数           | `f = { 5 }` → `f()` = 5            |

**注釈が型を決める**：`x: Int = ...` は `x` が `Int` であることを宣言するので、`{ ... }` は `Int`
に評価される； `f: () -> Int = ...` は `f` が関数であることを宣言するので、`{ ... }`
は関数本体である。

`{ ... }` を即座に評価したい場合、**ターゲット型を書けばよい**（新しい文法は不要）：

```yaoxiang
// ブロック値：即座に評価
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：注釈なし、デフォルトで関数
f = { 5 }        // f() = 5
```

#### ネストした関数型：カリー化か、関数を返すのか？

`->` の右側のネストした関数型には 2 つの読み方があり、**括弧**で区別される（RFC-004）：

| 書き方                          | 意味           | 呼び出し            |
| ------------------------------- | -------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **カリー化**   | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **関数を返す** | `g(1)` で関数を得る |

根拠：**注釈が型を決める**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int`
を宣言するので、 `g(1)` は「次の引数」ではなく**その関数でなければならない**。

```yaoxiang
// カリー化：2 段階の引数を層ごとに渡す
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数を返す：外側に 1 段階の引数、返ってくるのが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返ってきた関数は変数に保存したり、渡したりできる
```

括弧なしのネストした `Fn` はすべてカリー化（RFC-011 の型引数形式を含む）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型検査**：括弧が返り型を宣言し、body はその型を生成しなければならない。`f: () -> (() -> Int) = { 7 }`
はエラー——期待は `() -> Int`、実際は `Int`（E1002）。

### 2.10 ラムダ式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子で、優先順位は `.` と同じ。`Result(T, E)` 型に対して：

- `Ok(v)` の場合、値 `v` を抽出して続行
- `Err(e)` の場合、エラーを上位に伝播する（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時に値を抽出、失敗時に上位に伝播
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は範囲値を作成する（Range は第一級値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値：バインド、受け渡し、メンバ判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step 形式（第三成分、デフォルト 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **step セマンティクス**：`a..b..c` の `c` はステップ。`c = 0` のリテラルはコンパイル時に拒否；動的
> `c` の場合はランタイムゼロチェック（E6001 ファミリ；エラーシステムの実装後 Result に格上げ）。
> `c < 0` は合法、区間方向は符号に応じて反転（`10..0..(-2)` は降順）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref`
は共有所有を作成する。コンパイラは自動的に Rc（単一タスク）または Arc（タスク横断）を選択し、ユーザは実装の詳細を考慮する必要がない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク横断：コンパイラが自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型の定義と生ポインタの操作に使用される。`return`
を使用して、型定義を 1 つ上のスコープに返す。

**セマンティクス**：

- `unsafe {}` 内で型を定義し、生ポインタを操作できる
- 返される型は `unsafe {}` の外側で使用可能
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロック内で不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外で使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックはスコープを作成する
- 内側スコープは外側スコープの変数にアクセスできる
- 外側スコープは内側スコープの変数にアクセスできない
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で可視
}
// x はこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数の外では不可視
```

**変数宣言とシャドウイング**：

- `x = value`：スコープチェーンを外側に辿って x を検索、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的な新しい可変宣言、外側と同名は禁止
- 同じスコープ内で同じ名前を宣言できるのは 1 回のみ

> **詳細定義**：スコープの完全な規則、変数宣言とシャドウイングの機構については
> [モジュールシステム仕様](./modules.md#第四章作用域) を参照。

### 3.1 文の分類

Stmt        ::= LetStmt
              | ExprStmt

              | ContinueStmt
              | IfStmt
              | MatchStmt

              | ForStmt
              | SpawnStmt
```

### 3.2 変数宣言

```
LetStmt     ::= ('mut')? Identifier (':' TypeExpr)? '=' Expr
```

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**セマンティクス**：`return`
は**非局所的退出**であり、最も近い**関数境界**を退出する（すべてのブロックを貫通する——`if` / `while`
/ `for` / `match` / 素のブロック / `spawn` / `unsafe`
を含む）。値を呼び出し元に渡す。ブロックに「戻す」ことはない。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'`
に対して成立（爆発原理、[型システム §2.2](./type-system.md) 参照）、したがって `return`
は任意の方を返す位置に出現可能で、追加の規則による制約は不要。

**ブロック評価との関係**：ブロックの値は常に**末尾式**である（§2.9 参照）。`{ return n }`
はブロックとして値が `n`、型 `Never`；同時に `return`
の作用は関数の退出。**両方のことが同時に成立し**、爆発原理により共存する。

`return` と末尾式により「早期 return」が成立し、`return` が関数を特に指す追加規則は不要——詳細は
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md) を参照。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通し、関数を退出（型 Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**セマンティクス**：含まれている最も内側の `while`/`for`
ループを即座に終了し、制御フローをそのループ本体の後ろに移す。

- **直近の 1 層のみを出る**：`break`

> は常にそれを含む最も内側のループに作用する。ネストしたループで複数層を一度に抜け出す必要がある場合、内側ループを関数として抽出し
> `return`
> で返すか、フラグを使用する（break/continue にはラベルがない；将来ループラベルを導入する場合、ループ宣言側の文法に従い RFC プロセスで進め、証明パイプラインの多出口設計とともに裁決する）

- **ループ体内のみ**：`break` は `while`/`for`

> ループ体内（体内にネストしたブロック/if/match を含む）にのみ出現可能、ループ外に出現するとコンパイルエラー（E1102
> `'break' outside of a loop`）

- **停止性証明に影響しない**：`while`
  ループは依然として停止が証明可能（decreases 計量）でなければならない；`break`
  は停止性論証に参加せず、`while true { break }` は受理されない
- **借用セマンティクス**：break の制御フロー辺は RFC-009a の逆方向 BFS 活性分析の構造的切断に参加する（抜け出したイテレーションは逆辺活性導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループの後に移動、i == 3
    }
}

// ネストしたループ：break は内側のみを出る
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側ループのみを終了
    }
    j = j + 1                  // 外側の各イテレーションはここまで実行される
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**セマンティクス**：このイテレーションの残りの文をスキップし、含まれている最も内側のループの次のラウンドに直接入る——`while`
は条件再評価に戻り、`for` は次の要素を取得する。

- **直近の 1 層のみに作用**：`break` と同様、ラベルなし
- **ループ体内のみ**：ループ外に出現するとコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 以下の累算をスキップ、n == 3 はカウントされない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

### 3.9 for 文

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 セマンティクス：各イテレーションは新しい値をバインドする

YaoXiang の for ループセマンティクスは従来言語と異なる：**各イテレーションは同じ変数を変更するのではなく、新しい値をバインドする**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行プロセス**：

| イテレーション | ループ変数の振る舞い                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------- |
| 1 回目         | 新しいバインディング `i = 1` を作成、ループ本体実行、1 を表示                                   |
| 2 回目         | 新しいバインディング `i = 2` を作成（以前のバインディングは破棄済み）、ループ本体実行、2 を表示 |
| 3 回目         | 新しいバインディング `i = 3` を作成、ループ本体実行、3 を表示                                   |
| 4 回目         | 新しいバインディング `i = 4` を作成、ループ本体実行、4 を表示                                   |
| 終了           | ループ本体終了、バインディング破棄                                                              |

**要点**：各イテレーション終了後、そのイテレーションで作成されたバインディングは破棄される。次のイテレーションは完全に新しいバインディングであり、前のイテレーションのバインディングとは一切関係がない。

#### 3.9.2 for と for mut の違い

| 文法                | ループ変数の可変性 | 説明                                     |
| ------------------- | ------------------ | ---------------------------------------- |
| `for i in 1..5`     | 不変               | ループ体内でバインディングを変更できない |
| `for mut i in 1..5` | 可変               | ループ体内でバインディングを変更可能     |

```yaoxiang
// 合法：各イテレーションで新しい値をバインド、変更不要
for i in 1..5 {
    print(i)  // i の値を読み取る
}

// エラー：不変バインディング、変更不可
for i in 1..5 {
    i = i + 1  // エラー：不変バインディングを変更できない
}

// 合法：for mut を使用すればバインディングの変更が許可される
for mut i in 1..5 {
    i = i + 1  // 変更許可
}
```

#### 3.9.3 シャドウイングチェック

YaoXiang は変数のシャドウイングを禁止する。for ループ変数は外側スコープの変数と同名にできない：

```yaoxiang
// エラー：i は既に外部で宣言されている
i = 10
for i in 1..5 {
    print(i)
}

// 正しい：異なる変数名を使用
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される。詳細は
[4.3 シャドウイング規則](./modules.md#43-遮蔽规则) を参照。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数のセマンティクス             |
| -------- | ------------------------------------------ |
| YaoXiang | 各イテレーションで新しい値をバインド       |
| Rust     | 同じ変数を変更（mut が必要）               |
| Python   | 同じ変数を変更（mut 不要）                 |
| C/C++    | 同じ変数を変更（ポインタまたは参照が必要） |

**設計理由**：YaoXiang がバインディングセマンティクスを採用するのは：

1. **自然言語セマンティクスにより合致**
   自然言語では、「コレクションの各要素 x について」は各 x が独立した個体であることを意味する。YaoXiang の
   `for i in 1..5`
   は「1 から 5 の各 i について」と読まれ、各イテレーションの i は完全に新しいバインディングであり、これは人間の直感的理解と一致する。

2. **偶発的な変更を回避**
   デフォルトで不変なバインディングセマンティクスは、ループ体内で偶発的にループ変数を変更できないことを意味する。複雑なループ体内のどこかで誤って
   `i = ...` と書いて追跡困難なバグが発生する心配がない。

3. **高性能なソリューションに手が届く**
   イテレーション間で変数を実際に再利用する必要がある場合（例：アキュムレータ、キャッシュ）、`for mut`
   を宣言すれば可変バインディングモードに切り替えられる。これは暗黙の共有状態よりも明確である——意図は構文で明示的に表現され、ランタイムの振る舞いに隠されるのではない。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：並行領域を明示的に宣言し、ブロック内の式が並行実行される。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側変数をキャプチャする**（RFC-024 §2.3、値キャプチャセマンティクス）：

- ブロック本体が外側変数を参照 =
  **Move 値キャプチャ**：値は spawn 作成時点でクロージャ環境にスナップショットされ、ブロック本体は env 経由（LoadUpvalue）で読み取る
- **プリミティブ**（Int/Float/Bool/Char）は値をコピーし、外側変数は影響を受けない
- **ハンドル型**（Struct/String/List 等）のスナップショット = ハンドルのコピー、基礎オブジェクトを共有；Embedded ランタイム（デフォルト）は同じスレッド同じヒープで、ハンドルが有効
- 複数タスク間での共有には明示的な `ref` が必要（§2.13、コンパイラが自動的に Rc/Arc を選択）
- ブロック内の `return` が参照する外側変数も同様にキャプチャされる

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 値キャプチャ、result == 6
}
```

### 3.11 プログラムエントリポイントとトップレベル文

コンパイラの視点では、ソースファイルには 2 つの役割があり、**`yaoxiang.toml`
の存在により決定される**：

| 役割       | 判定                                       | プログラム本体                                                    |
| ---------- | ------------------------------------------ | ----------------------------------------------------------------- |
| **Script** | 単一ファイル直接実行、`yaoxiang.toml` なし | **トップレベル文**（記述順に実行）；`main` は通常のバインディング |
| **Bin**    | `yaoxiang.toml` あり                       | **`main` 関数**；トップレベルに実行可能文は不可                   |

#### Script：トップレベル文がプログラム

manifest がない場合、ファイルは「スクリプト」であり、**トップレベル文は記述順に実行される**：

```yaoxiang
use std.io
io.println("hello")          // 直接実行
x: Int = { 42 }              // トップレベルバインディング：ランタイム初期化
io.println(x)                // 42
```

このモードでは `main` は**特別ではない**——単なる通常のバインディングである。`main`
を実行させるには明示的に呼び出す必要がある：

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← この行が必須
```

> **なぜ `main` を自動呼び出ししないのか？** トップレベル文がすでにプログラム本体である。暗黙的に
> `main` を呼び出すと、明示的に `main()`
> と書いたスクリプトは 2 回実行される。両方の規則は共存できないため、Script では「トップレベル文」という単一の実行エントリポイントのみとなる。

#### Bin：`main` がエントリポイント

manifest がある場合、ファイルは「実行可能ターゲット」であり、この場合：

- `main` の定義が必須、かつ関数でなければならない（シグネチャはゼロ引数で呼び出し可能であること）
- トップレベルに実行可能文は不可——プログラム本体が `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

`main` の欠落または `main` が関数でない場合はどちらもコンパイルエラー（前者：`main`
がない場合すべての関数が到達不能；後者：値バインディングは呼び出されない）。

> **ライブラリファイル**：他のファイルから `use` されるファイル、または `[lib].path` / `[exports]`
> が指すファイルは `main` を必要としない——これらはプログラムエントリポイントではない。

#### トップレベルバインディングの初期化

トップレベルバインディングの初期化値は**ランタイムに評価され**、コンパイル時定数であることは要求されない：

```yaoxiang
answer: Int = { 42 }              // ブロック値
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // 関数呼び出し
```

初期化は**依存順**に実行され、記述順には依存しない：

```yaoxiang
derived: Int = base * 3           // 後方宣言の base を参照
base: Int = 7                     // 先に初期化（トポロジカルソート）
```

循環依存はコンパイルエラー（環上の名前が列挙される）：

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // エラー：a → b → a
```

> **設計根拠**：RFC-029f（ファイル役割モデル）、RFC-010a 付録 D（ブロックバインディング裁決）。

### A.3 match 文法
