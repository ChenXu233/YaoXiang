# 文法仕様

このドキュメントは YaoXiang プログラミング言語の文法仕様を定義する。字句構造、文法規則、演算子の優先順位を含む。

---

## 第一章：字句構造

### 1.1 ソースファイル

YaoXiang のソースファイルは UTF-8 エンコーディングを使用しなければならない。ソースファイルの拡張子は通常
`.yx` である。

### 1.2 字句要素の分類

| カテゴリ   | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語で予約された語               | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り子   | 文法上の区切り                   | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiang は極めて少数のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として使用することはできない。

### 1.4 予約語

YaoXiang の「予約語」は3つの層に分かれ、それぞれパーサ（parser）と型検査器（type
checker）が異なる段階で識別する：

#### 1.4.1 リテラル予約語

パーサが独立したトークンとして持つリテラル識別子は、通常の識別子として使用できない：

| 識別子  | 所属型 | 説明                                                                                            |
| ------- | ------ | ----------------------------------------------------------------------------------------------- |
| `Type`  | —      | メタ型キーワード                                                                                |
| `true`  | Bool   | ブール真値                                                                                      |
| `false` | Bool   | ブール偽値                                                                                      |
| `void`  | Void   | Void リテラル（Unit 値）。小文字の `void` は値リテラル；大文字の `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 コンストラクタ式

以下のコンストラクタは、パターンマッチングと式の文脈でパーサによって識別される：

| コンストラクタ | 所属型 | 説明                      |
| -------------- | ------ | ------------------------- |
| `some(T)`      | Option | Option の値バリアント構築 |
| `ok(T)`        | Result | Result の成功バリアント   |
| `err(E)`       | Result | Result のエラーバリアント |

#### 1.4.3 組み込み型名

以下の型名は型検査器にあらかじめ登録されており、インポートなしでも型の位置で使用できる。パーサはこれらを通常の識別子として扱う——**予約語ではなく、ローカル束縛によるシャドウイングが可能（非推奨）**。

| 型名     | 論理的対応   | 説明                                                                                                                                         |
| -------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤（真/Unit） | ゼロフィールドの積型で、ちょうど1つの居住者を持つ（`void` リテラル、§1.4.1 参照）                                                            |
| `Never`  | ⊥（偽/空型） | ゼロバリアントの和型で、居住者を持たない。`Never` 型の値を生成する式は存在しない。`Never <: T` はすべての `T` に対して成立する（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                                                 |
| `Float`  | —            | 浮動小数点数                                                                                                                                 |
| `Bool`   | —            | ブール値：`true` / `false`                                                                                                                   |
| `Char`   | —            | Unicode 文字                                                                                                                                 |
| `String` | —            | 文字列                                                                                                                                       |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、後続の文字は文字、数字、またはアンダースコアである。識別子は大文字小文字を区別する。

特別な識別子：

- `_` はプレースホルダとして使用され、値を無視することを表す
- アンダースコアで始まる識別子はプライベートメンバーを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // 対象型アノテーションが Array(T, N) のときリテラルは固定長配列に落ちる
```

> Set にはリテラル文法も実行時表現もない——コレクション型の計画中、必要が発生した時点で Dict のパターンに合わせて補完する（std.set +
> HeapValue::Set）。List/Dict リテラルの落点は文脈型アノテーションによって決まる：素のリテラルと
> `List(T)` アノテーションは可成長リストに落ち；`Array(T, N)`
> アノテーションがリテラルに直接作用する場合は固定長配列に落ちる。暗黙の List→Array 変換は禁止。
>
> Array リテラルの意味：
>
> - 要素数は N と等しくなければならない。等しくない場合はコンパイル時 E1002；空リテラルに非ゼロ N を付けた場合も拒否される
> - 各要素の型は T と互換でなければならず、適合しない場合はコンパイル時 E1002
> - N の文法形式：整数リテラル（負数可）または定数名のみ；複合式（例えば `2+1`）は解析時に拒否される
> - N がシンボル定数（関数の const パラメータ、例えば
>   `Array(Int, n)`）の場合、要素数の検査は型精化段階まで延期される
> - v1 ではネストされた配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否され、層ごとに明示的に構築する必要がある；再帰的な落点は将来のバージョンに委ねる

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **挙動の厳格化（移行記録）**：反復変数の文法は本来 `'for' Identifier 'in'`
> だが、旧実装では pattern が完全な pratt 解析を通っていた——`'in'` が中置演算子として登録された後、
> `x` は `in items`
> を membership 式として飲み込んでしまう。修正後は非識別子 pattern の解析が直接失敗し、旧実装のように
> `_` にフォールバック（エラーを静かに飲み込む）ことはなくなった。影響範囲：以前解析できていた
> `[x for (a, b) in pairs]`
> という書き方は現在エラーになる——この形式には定義された挙動が一度もなかった（変数は常に
> `_`）、厳格化の方向は正しく、意味的な移行コストはない。

#### 1.6.6 メンバー検査

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子で、`Bool` を返す——命中すれば `true`、外れれば
> `false`、エラーは出ない。意味の切り分け：`[]` は存在をアサートして値を取り出す（失敗でエラー）、
> `in` は存在を問い合わせる（外れるのは正常な `false`）。右オペランドの対応範囲：List / Array /
> Dict(キー集合) / Tuple / String(部分文字列) / Range(区間)。`in`
> は一階のホーア述語であり、型精化段階でコンパイル時に証明可能な命題の基底となる。（Set は右オペランドのリストから除外——Set には実行時表現がない、§1.6.4 参照）

### 1.7 コメント

```
// 単一行コメント

/* 複数行コメント
   複数行に渡ることができる */
```

### 1.8 インデント規則

コードは4つのスペースでインデントしなければならず、Tab 文字の使用は禁止されている。これは強制的な文法規則である。

## 第二章：文法規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強く結合する：呼び出しとメンバアクセスのみより低く、すべての二項演算子より高い。したがって
> `!a == b` ≡ `(!a) == b`（Zig 式の意味論）；`!`
> は純粋な単項演算であり、短絡制御フローに参加せず、`and`/`or`
> キーワード（短絡）に対して直交する（RFC-010 での権威ある定義）。
>
> **Range の結合力**：`..` の結合力は (6,
> 7)——左 6 は加算（7）より低く、右 7 は加算を飲み込むが同位の `..` は飲み込まない。変更前後の対照：
>
> | 式           | 変更前（レベル 1、右結合）                                                                  | 変更後（(6,7)、左結合）                                            |
> | ------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
> | `x in 1..10` | `x in 1..10`（`in` の右オペランドレベル 4、`..` レベル 1 では飲み込めず、実際には解析不能） | `x in (1..10)`——区間全体が `in` の右オペランドになる               |
> | `0..n+2`     | `(0..n)+2`（右結合の罠：上界が飲み込まれ、`for` ループで直接 E3004）                        | `0..(n+2)`——上界は算術式になる                                     |
> | `a == b..c`  | `a == (b..c)`（`..` レベル 1 < `==` レベル 3、自然に全体）                                  | `a == (b..c)`——**意味は不変**、`..` は依然として比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                                                  | `1..(2*3)`——上界は算術式になる                                     |
> | `a..b..c`    | `a..(b..c)`（右結合の連鎖、意味のない Range の入れ子）                                      | `(a..b)..c`——**step 形式**（`c` はステップ幅）                     |
>
> 純効果：複合上界 `for i in 0..n+2` が「解析成功だが E3004」から「直接使用可能」に； `x in 1..10`
> が「解析不能」から「区間検査」に；`a..b..c` が「意味のない入れ子」から「step 成分」に。レベル 6 は
> `+`（レベル 5）と
> `<<`（レベル 7）の間に位置し、数学的慣習に従う：区間は強く結合する構造であり、上界は当然完全な算術式である。

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt 間の区切りと改行の挙動（`;`
> による明示的な区切り、改行による終端、続き行の例外、行頭の `(`/`[` は決してマージされない）は
> [RFC-038](../design/rfc/draft/038-statement-termination.md) で定義される。

**統一的な意味論**：すべての `{}` ブロックの値は**末尾式**によって与えられる。`return` は `Never`
型の非局所脱出である。

| ブロック型  | 値の出口 | 空ブロック `{}` |
| ----------- | -------- | --------------- |
| 通常の `{}` | 末尾式   | `Void`          |
| `unsafe {}` | 末尾式   | `Void`          |
| `spawn {}`  | 末尾式   | `Void`          |

**核心原則**（詳細は [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md) 参照）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**である場合、ブロックの値は `Void` になる；`Void` が欲しいなら明示的に `Void`
  と書く
- **`return`
  は最も近い関数境界を脱出する**（すべてのブロックを貫通し、ブロックに「返す」ことはない）、型は
  `Never`；`Never <: T`
  は任意の型に対して成立する（爆発原理）ため、任意の戻り型の位置に現れることができる
- 式形式 `= expr` は直接値を与える

```yaoxiang
// 通常の {} ブロック：末尾式が値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式が型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式が結果を与える
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // ブロックの値
}

// return：ブロックを貫通し、関数を脱出する
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if と関数本体を貫通し、関数を脱出する
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数か、ブロック値か？

`name = { ... }`
は関数定義（RFC-007「空引数の最簡」）にも、ブロック値束縛にもなり得る。**アノテーション優先、デフォルトは関数**という裁定に従う（RFC-010a 付録D）：

| 場合                     | 結果           | 例                                 |
| ------------------------ | -------------- | ---------------------------------- |
| 値が Lambda（`=>`）      | 関数           | `f = () => 5` → `f()` = 5          |
| アノテーションが関数型   | 関数           | `f: () -> Int = { 5 }` → `f()` = 5 |
| アノテーションが非関数型 | **ブロック値** | `x: Int = { 5 }` → `x` = 5         |
| アノテーションなし       | 関数           | `f = { 5 }` → `f()` = 5            |

**アノテーション即型**：`x: Int = ...` は `x` が `Int` であることを宣言し、そのとき `{ ... }`
の評価値は `Int` になる； `f: () -> Int = ...` は `f` が関数であることを宣言し、そのとき `{ ... }`
は関数本体になる。

`{ ... }` をその場で評価したいなら、**対象の型を書くだけでよい**（新しい文法は不要）：

```yaoxiang
// ブロック値：即時評価
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：アノテーションなしはデフォルト
f = { 5 }        // f() = 5
```

#### ネストされた関数型：カリー化か、関数を返すか？

`->` の右側にあるネストされた関数型には2つの読み方があり、**括弧**で区別する（RFC-004）：

| 書き方                          | 意味           | 呼び出し            |
| ------------------------------- | -------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **カリー化**   | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **関数を返す** | `g(1)` で関数を得る |

根拠：**アノテーション即型**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int`
を宣言しているため、 `g(1)` は**その関数でなければならない**。「次の引数」ではなく。

```yaoxiang
// カリー化：2段の引数を層ごとに与える
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数を返す：外側に1段の引数、返ってくるのが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返ってきた関数は変数に格納も、受け渡しも可能
```

括弧なしのネストされた `Fn` はすべてカリー化（RFC-011 の型パラメータ形式を含む）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型検査**：括弧は戻り型を宣言し、body はその型を生成しなければならない。
`f: () -> (() -> Int) = { 7 }` は誤り——期待される型は `() -> Int`、実際に得られたのは
`Int`（E1002）。

### 2.10 Lambda 式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子で、優先順位は `.` と同位である。`Result(T, E)` 型に対して：

- `Ok(v)` の場合は値 `v` を取り出して実行を続ける
- `Err(e)` の場合はエラーを上位に伝播する（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時は値を取り出し、失敗時は上位に伝播
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は範囲値を作成する（Range は一階の値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値：束縛、受け渡し、メンバ判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step 形式（第3成分、デフォルトは 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **step の意味論**：`a..b..c` の `c` はステップ幅。`c = 0`
> のリテラルはコンパイル時に拒否される；動的な `c`
> は実行時にゼロ検査される（E6001 ファミリー；エラーシステムの実装後 Result に格上げ）。 `c < 0`
> は合法で、区間の方向は符号に応じて反転する（`10..0..(-2)` は減少）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref`
は共有の保有を作成する。コンパイラは自動的に Rc（単一タスク）または Arc（タスク間）を選択し、ユーザは実装の詳細を気にする必要がない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク間：コンパイラが自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型の定義と生ポインタの操作に使用される。`return`
を使って型定義を上のスコープに返す。

**意味論**：

- `unsafe {}` 内では型定義と生ポインタの操作が可能
- 返される型は `unsafe {}` 外でも使用可能
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロック内で不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外でも使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックはスコープを作成する
- 内側のスコープは外側のスコープの変数にアクセスできる
- 外側のスコープは内側のスコープの変数にアクセスできない
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で見える
}
// x はこのスコープ外では見えない

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数の外では見えない
```

**変数宣言とシャドウイング**：

- `x = value`：スコープチェーンを外側にたどって x を探し、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的に新しい可変変数を宣言し、外側と同名を禁止
- 同じスコープ内で同じ名前を宣言できるのは一度だけ

> **詳細な定義**：スコープの完全な規則、変数宣言とシャドウイング機構の詳細は
> [モジュールシステム仕様](./modules.md#第四章作用域) を参照。

### 3.1 文の分類

```
              | SpawnStmt
```

### 3.2 変数宣言

```
LetStmt     ::= ('mut')? Identifier (':' TypeExpr)? '=' Expr
```

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**意味論**：`return` は**非局所脱出**であり、最も近い**関数境界**を脱出する（`if` / `while` / `for`
/ `match` / 素のブロック / `spawn` / `unsafe`
を含むすべてのブロックを貫通する）。値を呼び出し元に渡す。**ブロックに「返す」わけではない**。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'`
に対して成立する（爆発原理、[型システム §2.2](./type-system.md) 参照）ため、`return`
は追加の規則なしに任意の戻り型の位置に現れることができる。

**ブロック評価との関係**：ブロックの値は常に**末尾式**である（§2.9 参照）。ブロックとしての
`{ return n }` の値は `n` で、型は `Never`；同時に `return`
の作用は関数の脱出である。**この2つの事象は同時に成立し**、爆発原理によって共存する。

`return` と末尾式は共同して「早期 return」を成立させ、`return`
が関数を指すという追加の規則を必要としない——詳細は
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md) 参照。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通し、関数を脱出する（型 Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**意味論**：それを含む最も内側の `while`/`for`
ループを直ちに終了し、制御フローをそのループ本体の後へ移す。

- **直近の1層のみ脱出**：`break`
  は常にそれを含む最も内側のループに作用する。ネストされたループで複数層を一度に飛び出す必要がある場合は、内側のループを関数として抽出し
  `return`
  で戻るか、フラグ変数を使用する（break/continue にはラベルがない；将来ループラベルが導入される場合、ループ宣言側の文法に従い RFC プロセスに沿って、証明パイプラインの多出口設計と共に裁定される）
- **ループ本体内のみ**：`break` は `while`/`for`
  ループ本体内にのみ（本体内にネストされたブロック/if/match を含む）現れ、ループ外にあるとコンパイルエラー（E1102
  `'break' outside of a loop`）
- **停止性証明に影響しない**：`while`
  ループは依然として停止が証明可能でなければならない（decreases 計量）；`break`
  は停止性の論証に参加せず、`while true { break }` は受理されない
- **借用意味論**：break の制御フロー辺は RFC-009a の逆向き BFS 活性分析の構造的切断に参加する（飛び出した反復は逆辺の活性導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループ後へ移行、i == 3
    }
}

// ネストされたループ：break は内側のみを脱出する
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側のループのみを終了する
    }
    j = j + 1                  // 外側の各反復でここまで実行される
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**意味論**：今回の反復で残りの文をスキップし、それを含む最も内側のループの次のラウンドへ直接進む——
`while` は条件の再評価へ戻り、`for` は次の要素を取り出す。

- **直近の1層のみに作用**：`break` と同様、ラベルなし
- **ループ本体内のみ**：ループ外にあるとコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 以下の累算をスキップ、n == 3 は加算されない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

### 3.9 for 文

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 意味論：各反復は新しい値を束縛する

YaoXiang の for ループの意味論は従来の言語とは異なる：**各反復は新しい値を束縛するものであり、同じ変数を変更するものではない**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行過程**：

| 反復  | ループ変数の挙動                                                              |
| ----- | ----------------------------------------------------------------------------- |
| 1回目 | 新しい束縛 `i = 1` を作成し、ループ本体を実行、1 を表示                       |
| 2回目 | 新しい束縛 `i = 2` を作成し（前の束縛は破棄済み）、ループ本体を実行、2 を表示 |
| 3回目 | 新しい束縛 `i = 3` を作成し、ループ本体を実行、3 を表示                       |
| 4回目 | 新しい束縛 `i = 4` を作成し、ループ本体を実行、4 を表示                       |
| 終了  | ループ本体の終了とともに束縛を破棄                                            |

**要点**：各反復が終了すると、その反復で作成された束縛は破棄される。次の反復は完全に新しい束縛であり、前の反復の束縛とは一切関係がない。

#### 3.9.2 for と for mut の違い

| 文法                | ループ変数の可変性 | 説明                             |
| ------------------- | ------------------ | -------------------------------- |
| `for i in 1..5`     | 不変               | ループ本体内で束縛を変更できない |
| `for mut i in 1..5` | 可変               | ループ本体内で束縛を変更できる   |

```yaoxiang
// 合法：各反復で新しい値を束縛し、変更は不要
for i in 1..5 {
    print(i)  // i の値を読み取る
}

// 誤り：不変束縛は変更できない
for i in 1..5 {
    i = i + 1  // 誤り：不変束縛は変更できない
}

// 合法：for mut を使用すれば束縛の変更が許可される
for mut i in 1..5 {
    i = i + 1  // 変更が許可される
}
```

#### 3.9.3 シャドウイング検査

YaoXiang は変数のシャドウイングを禁止する。for ループ変数は外側のスコープの変数と同名にすることはできない：

```yaoxiang
// 誤り：i はすでに外側で宣言されている
i = 10
for i in 1..5 {
    print(i)
}

// 正しい：異なる変数名を使用する
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される。詳細は
[4.3 シャドウイング規則](./modules.md#43-遮蔽规则) を参照。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数の意味論                         |
| -------- | ---------------------------------------------- |
| YaoXiang | 各反復で新しい値を束縛する                     |
| Rust     | 同じ変数を変更する（mut が必要）               |
| Python   | 同じ変数を変更する（mut 不要）                 |
| C/C++    | 同じ変数を変更する（ポインタまたは参照が必要） |

**設計理由**：YaoXiang が束縛意味論を採用するのは以下の理由による：

1. **自然な意味論により適合する**
   自然言語では、「コレクションの各要素 x について」は各 x が独立した個体であることを意味する。YaoXiang の
   `for i in 1..5`
   は「1 から 5 の各 i について」と読まれ、各反復の i は完全に新しい束縛であり、人類の直感的理解と一致する。

2. **偶発的な変更を避ける**
   デフォルトで不変な束縛意味論は、ループ本体内で偶発的にループ変数を変更することができない。複雑なループ本体内のどこかで誤って
   `i = ...` と書いてしまい、追跡困難なバグを引き起こす心配がない。

3. **高性能なソリューションに手が届く**
   反復間で変数を再利用することが実際に必要になった場合（例えばアキュムレータやキャッシュ）、`for mut`
   で宣言すれば可変束縛モードに切り替えられる。これは暗黙の共有状態よりも明確である——意図は実行時の挙動に隠れるのではなく、文法によって明示的に表現される。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：並行実行領域を明示的に宣言し、ブロック内の式を並行実行する。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側の変数をキャプチャする**（RFC-024 §2.3、値キャプチャ意味論）：

- ブロック本体が外側の変数を参照する =
  **Move 値キャプチャ**：値は spawn 作成時点でクロージャ環境にスナップショットされ、ブロック本体は env 経由で読み取る（LoadUpvalue）
- **プリミティブ**（Int/Float/Bool/Char）は値をコピーし、外側の変数は影響を受けない
- **ハンドル型**（Struct/String/List など）のスナップショット = ハンドルのコピー、基盤となるオブジェクトを共有する；Embedded ランタイム（デフォルト）は同じスレッドで同じヒープを使い、ハンドルは有効
- 複数タスク間で共有するには明示的な `ref` が必要（§2.13、コンパイラが自動的に Rc/Arc を選択）
- ブロック内の `return` が参照する外側の変数も同様にキャプチャされる

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 は値キャプチャ、result == 6
}
```

### 3.11 プログラムエントリとトップレベル文

ソースファイルはコンパイラの視点では2つの役割を持つ。**`yaoxiang.toml` の有無によって決定される**：

| 役割       | 判定                                         | プログラムの本体                                        |
| ---------- | -------------------------------------------- | ------------------------------------------------------- |
| **Script** | 単一ファイルを直接実行、`yaoxiang.toml` なし | **トップレベル文**（記述順に実行）；`main` は通常の束縛 |
| **Bin**    | `yaoxiang.toml` が存在                       | **`main` 関数**；トップレベルに実行可能文は許可されない |

#### Script：トップレベル文がプログラム

マニフェストがない場合、ファイルは「スクリプト」であり、**トップレベル文が記述順に実行される**：

```yaoxiang
use std.io
io.println("hello")          // 直接実行
x: Int = { 42 }              // トップレベル束縛：実行時に初期化
io.println(x)                // 42
```

このモードでは `main` は**特別ではない**——単なる通常の束縛である。`main`
を実行させたい場合は明示的に呼び出す必要がある：

```yaoxiang
use std.io
main = { io.println("only runs if called") }

main()                       // ← この行を書かなければならない
```

> **なぜ `main` を自動的に呼び出さないのか？**
> トップレベル文がすでにプログラムの本体である。さらに暗黙的に `main` を呼び出すと、明示的に
> `main()`
> と書いたスクリプトは2回実行されることになる。2つの規則は共存できないため、Script では「トップレベル文」のみが実行エントリとなる。

#### Bin：`main` がエントリ

マニフェストがある場合、ファイルは「実行可能ターゲット」であり、このとき：

- `main`
  を定義しなければならず、それは関数でなければならない（シグネチャはゼロ引数で呼び出し可能であること）
- トップレベルには実行可能文は許可されない——プログラムの本体は `main` そのものである

```yaoxiang
main = {
    print("hello")
}
```

`main` が欠落しているか、`main` が関数でない場合はいずれもコンパイルエラー（前者は：`main`
がないとき全関数が到達不能；後者：値の束縛は呼び出されない）。

> **ライブラリファイル**：他のファイルに `use` されるファイル、または `[lib].path` / `[exports]`
> が指すファイルは `main` を要求しない——これらはプログラムのエントリではない。

#### トップレベル束縛の初期化

トップレベル束縛の初期化値は**実行時に評価**され、コンパイル時定数である必要はない：

```yaoxiang
answer: Int = { 42 }              // ブロック値
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // 関数呼び出し
```

初期化は**依存順序**で実行され、記述順には依存しない：

```yaoxiang
derived: Int = base * 3           // 後で宣言された base を参照
base: Int = 7                     // 先に初期化（トポロジカルソート）
```

循環依存はコンパイルエラー（環上の名前が列挙される）：

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // エラー：a → b → a
```

> **設計根拠**：RFC-029f（ファイル役割モデル）、RFC-010a 付録D（ブロック束縛裁定）。
