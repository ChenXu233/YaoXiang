# 语法仕様

本文書は YaoXiang プログラミング言語の文法仕様を定義するものであり、字句構造、文法規則、演算子の優先順位を含む。

---

## 第一章：字句構造

### 1.1 ソースファイル

YaoXiang のソースファイルは UTF-8 エンコーディングを使用しなければならない。ソースファイルの拡張子は通常
`.yx` である。

### 1.2 トークンの分類

| 種類       | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語で事前に定義された予約語     | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り子   | 構文の区切り記号                 | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiang は極めて少数のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として用いることはできない。

### 1.4 予約語

YaoXiang の「予約語」は三層に分かれ、それぞれパーサ（parser）と型検査器（type
checker）が異なる段階で識別する：

#### 1.4.1 リテラル予約語

パーサが独立したトークンとして持つリテラル識別子であり、通常の識別子としては使用できない：

| 識別子  | 所属する型 | 説明                                                                                            |
| ------- | ---------- | ----------------------------------------------------------------------------------------------- |
| `Type`  | —          | メタタイプキーワード                                                                            |
| `true`  | Bool       | ブール真値                                                                                      |
| `false` | Bool       | ブール偽値                                                                                      |
| `void`  | Void       | Void リテラル（Unit 値）。小文字の `void` は値リテラル；大文字の `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 コンストラクタ式

以下のコンストラクタはパターンマッチと式の文脈でパーサに認識される：

| コンストラクタ | 所属する型 | 説明                        |
| -------------- | ---------- | --------------------------- |
| `some(T)`      | Option     | Option 値変体コンストラクタ |
| `ok(T)`        | Result     | Result 成功変体             |
| `err(E)`       | Result     | Result エラー変体           |

#### 1.4.3 組み込み型名

以下の型名は型検査器に事前登録されており、インポートなしでも型位置で使用できる。パーサはこれらを通常の識別子として扱う——**予約語ではないため、ローカル束縛によるシャドウイングが可能（推奨されない）**。

| 型名     | 論理的対応   | 説明                                                                                                                       |
| -------- | ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤（真/Unit） | ゼロフィールドの積型で、唯一の住人を有する（`void` リテラル、§1.4.1 参照）                                                 |
| `Never`  | ⊥（偽/空型） | ゼロ変体和型、ゼロ住人。`Never` 型の値を生成する式は存在しない。`Never <: T` はあらゆる `T` に対して成立する（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                               |
| `Float`  | —            | 浮動小数点数                                                                                                               |
| `Bool`   | —            | ブール値：`true` / `false`                                                                                                 |
| `Char`   | —            | Unicode 文字                                                                                                               |
| `String` | —            | 文字列                                                                                                                     |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、続く文字は文字、数字、またはアンダースコアとすることができる。識別子は大文字小文字を区別する。

特殊な識別子：

- `_` はプレースホルダとして用いられ、値の無視を表す
- アンダースコアで始まる識別子はプライベートメンバーを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // 目標型注釈が Array(T, N) の場合、リテラルは固定長配列に落定する
```

> **辞書リテラルは少なくとも一つのキーと値のペアを要求する**：`{}`
> は**空辞書ではない**——これは空ブロック（値 `Void`、 [§2.9](#_2-9-ブロック式)
> 参照）である。空辞書には `dict.new()` コンストラクタを使用すること：
>
> ```yaoxiang
> empty = dict.new()                  // ✅ 空辞書
> d = { "a": 1 }                       // ✅ 辞書リテラル
> wrong = {}                           // ❌ これは辞書ではなく、空ブロック（Void）である
> ```
>
> **判定は内容による**：`Dict` 文法は少なくとも一つの `String ':' Expr` を要求し、`{}`
> は判断材料となる内容を持たないため、ブロック構造のゼロ形態を取る。非空形態は内容によって自己記述される（`{ "k": v }`
> はキーと値のペアを持つ → 辞書）——これは `f = { 5 }` が関数ではなく `Int`
> 値であるのと同じ原理である：**型は内容によって決定される**。

> Set にはリテラル文法もランタイム表現も存在しない——集合型は計画段階であり、ニーズが発生した際に Dict のパターンに従って補完する（std.set +
> HeapValue::Set）。List/Dict リテラルの落点は文脈の型注釈によって決定される：裸のリテラルと
> `List(T)` 注釈は拡張可能なリストに落定する；`Array(T, N)`
> 注釈がリテラルに直接作用する場合は固定長配列に落定する。List→Array の暗黙的変換は禁止されている。
>
> Array リテラルのセマンティクス：
>
> - 要素数は N と等しくなければならず、等しくない場合はコンパイル時に E1002；空リテラルに非ゼロ N を指定した場合も同様に拒否される
> - 各要素の型は T と互換でなければならず、互換性がない場合はコンパイル時に E1002
> - N の文法形式：整数リテラル（負の値も可）または定数名のみ；複合式（例：`2+1`）は解析段階で拒否される
> - N がシンボル定数（関数の const パラメータ、例：`Array(Int, n)`）の場合、要素数検査は型精化段階まで延期される
> - v1 のネストされた配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否され、各層を明示的に構築する必要がある；再帰的な落点は将来のバージョンに委ねられる

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **動作の厳格化（移行記録）**：反復変数の文法は本来 `'for' Identifier 'in'`
> であるが、旧実装では pattern が完全な pratt 解析を行っていた——`'in'`
> が中置演算子として登録された後、 `x` は `in items`
> を membership 式として飲み込んでいた。修正後は非識別子 pattern は直接解析に失敗し、旧実装のように
> `_` にフォールバック（エラーを静かに吸収）しなくなった。影響範囲：これまで解析可能だった
> `[x for (a, b) in pairs]`
> のような記述は今後エラーを報告する——この形式には定義された動作が一度も存在しなかった（変数は常に
> `_` であった）、厳格化する方向は正しいものであり、意味的な移行コストは発生しない。

#### 1.6.6 メンバー検査

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子であり、`Bool` を返す——ヒットすれば `true`、ヒットしなければ `false`
> であり、エラーを報告しない。意味の切り分け：`[]`
> は要素の存在をアサートして値を取り出す（失敗時にエラー報告）、 `in`
> は要素が存在するかを問い合わせる（未ヒットは正常な `false`）。右オペランドの被覆：List / Array /
> Dict(キー集合) / Tuple / String(部分文字列) / Range(区間)。`in`
> は第一級のホーア述語であり、型精化段階ではコンパイル時に証明可能な命題の基底となる。（Set は右オペランドのリストから除外される——Set にはランタイム表現が存在しない、§1.6.4 参照）

### 1.7 コメント

```
// 単一行コメント

/* 複数行コメント
   複数行に渡ることができる */
```

### 1.8 インデント規則

コードは 4 つのスペースでインデントしなければならず、Tab 文字の使用は禁止されている。これは強制的な構文規則である。

## 第二章：構文規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強く結合する：呼び出しとメンバアクセスのみより低く、すべての二項演算子より高い。したがって
> `!a == b` ≡ `(!a) == b`（Zig 式のセマンティクス）；`!`
> は純粋な単項演算であり、短絡制御フローには参加せず、`and`/`or`
> キーワード（短絡）とは直交する（RFC-010 による権威ある定義）。

> **Range の結合力**：`..` の結合力は (6,
> 7)——左 6 は加算（7）より低く、右 7 は加算を吸収するが同級の `..` は吸収しない。変更前後の対照：
>
> | 式           | 変更前（レベル 1、右結合）                                                                  | 変更後（(6,7)、左結合）                                                      |
> | ------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10`（`in` の右オペランドレベル 4、`..` レベル 1 では吸収できず、実際には解析不可） | `x in (1..10)`——区間全体が `in` の右オペランド                               |
> | `0..n+2`     | `(0..n)+2`（右結合の罠：上限が奪われ、`for` ループが直接 E3004）                            | `0..(n+2)`——上限は算術式                                                     |
> | `a == b..c`  | `a == (b..c)`（`..` レベル 1 < `==` レベル 3、当然全体）                                    | `a == (b..c)`——**セマンティクスは不変**、`..` は依然として比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                                                  | `1..(2*3)`——上限は算術式                                                     |
> | `a..b..c`    | `a..(b..c)`（右結合のチェーン、意味のない Range のネスト）                                  | `(a..b)..c`——**step 形式**（`c` はステップ）                                 |
>
> 純効果：複合上限 `for i in 0..n+2` が「解析成功だが E3004」から「直接使用可能」に； `x in 1..10`
> が「解析不可」から「区間チェック」に；`a..b..c`
> が「無意味なネスト」から「step 成分」に。レベル 6 は `+`（レベル 5）と
> `<<`（レベル 7）の間に位置し、数学的慣例に従う：区間は強く結合する構造であり、上限は当然完全な算術式である。

### 2.3 関数呼び出し

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

名前付き実引数は `name = value` の形式を用いる（RFC-010 §関数定義、RFC-011
§構築形式）。位置実引数は名前付き実引数より前に置かなければならない；順序で指定された引数は名前付き実引数内で任意の順序に配置できる：

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // 位置式
add(a = 3, b = 5)  // 名前付き式
add(b = 5, a = 3)  // 順序は任意
add(3, b = 5)      // 混在、位置が前
```

名前付き実引数の名前が誤っている場合は **E1014**
を、同じ仮引数が位置と名前付きの両方で指定された場合は **E1015** を、個数が一致しない場合は
**E1010** を報告する（RFC-013）。

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt 間の区切りと改行の振る舞い（`;`
> による明示的な区切り、改行による終端、続行の例外、行頭の `(`/`[` は決して連結されない）は
> [RFC-038](../design/rfc/draft/038-statement-termination.md) で定義される。

#### 2.9.1 `{` の三つの形態

式位置における `{` は厳密に三つの解釈のみを持ち、**内容**によって一度だけ判定される：

| 形態             | 表記              | 型           | 例               |
| ---------------- | ----------------- | ------------ | ---------------- |
| **空ブロック**   | `{}`              | `Void`       | `x: Void = {}`   |
| **辞書リテラル** | `{ "k": v, ... }` | `Dict(K, V)` | `d = { "a": 1 }` |
| **ブロック**     | `{ Stmt* Expr? }` | 末尾式の型   | `y = { 1 + 1 }`  |

**判定順序**：

1. `{}`（内容なし）→ **空ブロック**、値 `Void`
2. 最初の要素が `String ':' Expr` のキーと値のペア → **辞書リテラル**
3. それ以外 → **ブロック**、値は末尾式によって与えられる

> **なぜ `{}` は空辞書ではないのか**：空辞書の「空」は自己記述できない（それは `Dict(K, V)`
> でもあり得、空ブロックでもあり得る）、一方、辞書文法 [§1.6.4](#_1-6-4-コレクション)
> は少なくとも一つのキーと値のペアを要求する。判断材料となる内容がない場合はブロック構造のゼロ形態を取る：これは
> `unsafe {}` / `spawn {}` と一致しており、特別な例外を導入しない。空辞書には `dict.new()`
> を用いる。
>
> **なぜ関数には注釈が必要なのか**：`f = { stmt }`
> は**値**（末尾式の型）であり、関数ではない。関数を定義するには Fn 注釈を明示する：`f: () -> Int = { 5 }`。これは辞書と同じ原則である：**型は内容によって決定され**、注釈の存在与否によっては決定されない。（この規則は
> [RFC-010a](./design/rfc/accepted/010a-tail-expression-and-return.md) 付録 D を参照。）

**統一されたセマンティクス**：すべての `{}` ブロックの値は**末尾式**によって与えられ、`return` は
`Never` 型の非局所的退出である。

| ブロック型  | 値の出口 | 空ブロック `{}` |
| ----------- | -------- | --------------- |
| 通常の `{}` | 末尾式   | `Void`          |
| `unsafe {}` | 末尾式   | `Void`          |
| `spawn {}`  | 末尾式   | `Void`          |

**核心原則**（詳細は [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md) 参照）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**の場合、ブロックの値は `Void` になる；`Void` を望むなら明示的に `Void` と書く
- **`return`
  は最も近い関数境界を退出する**（すべてのブロックを貫通し、ブロックに「返さない」）、型は
  `Never`；`Never <: T`

> は任意の型に対して成立する（爆発原理）ため、任意の戻り型の位置に現れ得る

- 式形式 `= expr` は直接値を与える

```yaoxiang
// 通常の {} ブロック：末尾式が値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式が型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式が結果を与える
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // ブロックの値
}

// return：ブロックを貫通し、関数を退出する
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if と関数本体を貫通し、関数を退出する
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数か、ブロックの値か？

`name = { ... }`
は関数定義（RFC-007「空パラメータ最簡」）にも、ブロックの値束縛にもなり得る。**注釈優先、デフォルトは関数**の裁定による（RFC-010a 付録 D）：

| 場合                | 結果             | 例                                 |
| ------------------- | ---------------- | ---------------------------------- |
| 値が Lambda（`=>`） | 関数             | `f = () => 5` → `f()` = 5          |
| 注釈が関数型        | 関数             | `f: () -> Int = { 5 }` → `f()` = 5 |
| 注釈が非関数型      | **ブロックの値** | `x: Int = { 5 }` → `x` = 5         |
| 注釈なし            | 関数             | `f = { 5 }` → `f()` = 5            |

**注釈が型を決定する**：`x: Int = ...` は `x` が `Int` であることを宣言する。したがって `{ ... }` は
`Int` として評価される； `f: () -> Int = ...` は `f` が関数であることを宣言する。したがって
`{ ... }` は関数本体である。

`{ ... }` をその場で評価したい場合、**目標型を書けばよい**（新しい構文は不要）：

```yaoxiang
// ブロックの値：即座に評価される
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：注釈なしではデフォルトで関数
f = { 5 }        // f() = 5
```

#### ネストされた関数型：カリー化か、関数を返すのか？

`->` の右側にあるネストされた関数型には二つの読み方があり、**括弧**で区別される（RFC-004）：

| 記述                            | 意味           | 呼び出し            |
| ------------------------------- | -------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **カリー化**   | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **関数を返す** | `g(1)` で関数を得る |

根拠：**注釈が型を決定する**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int`
を宣言する。したがって `g(1)`
は**その関数そのもの**でなければならず、「次のパラメータの続き」ではない。

```yaoxiang
// カリー化：二段のパラメータを逐次与える
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数を返す：外側の一段のパラメータを与え、返されるのが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返された関数は変数に保存したり、渡したりできる
```

括弧なしのネストされた `Fn` はすべてカリー化とされる（RFC-011 の型パラメータ形式を含む）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型検査**：括弧が戻り型を宣言する。body はその型を生成しなければならない。
`f: () -> (() -> Int) = { 7 }` は誤りである——期待される型は `() -> Int` であるが、実際の型は `Int`
である（E1002）。

### 2.10 Lambda 式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子であり、優先順位は `.` と同位である。`Result(T, E)` 型に対して：

- `Ok(v)` の場合、値 `v` を取り出して実行を継続する
- `Err(e)` の場合、エラーを上位に伝播する（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時は値を取り出し、失敗時は上位に伝播する
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は範囲値を生成する（Range は一級値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値である：束縛、受け渡し、メンバー判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step 形式（第三成分、デフォルト 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **step のセマンティクス**：`a..b..c` において `c` はステップである。`c = 0`
> のリテラルはコンパイル時に拒否される；動的な `c`
> の場合はランタイムゼロチェック（E6001 ファミリ；エラーシステムの実装後に Result に格上げ）。
> `c < 0` は合法であり、区間方向は符号に応じて反転する（`10..0..(-2)` は降順）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref`
は共有所有を生成する。コンパイラは自動的に Rc（単一タスク）または Arc（タスク横断）を選択し、ユーザーは実装の詳細を考慮する必要がない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク横断：コンパイラが自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型の定義と生ポインタの操作に使用される。`return`
を使用して型定義を上位スコープに返す。

**セマンティクス**：

- `unsafe {}` 内で型を定義し、生ポインタを操作できる
- 返された型は `unsafe {}` 外で使用可能
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロック内で不透明型を定義する
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外で使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックがスコープを作成する
- 内側のスコープは外側のスコープの変数にアクセスできる
- 外側のスコープは内側のスコープの変数にアクセスできない
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で可視
}
// x はこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数の外では不可視
```

**変数宣言とシャドウイング**：

- `x = value`：スコープチェーンに沿って外側に x を検索し、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的な新しい可変宣言、外側と同名は禁止
- 同じスコープ内で任意の名前の宣言は一度のみ

> **詳細な定義**：スコープの完全な規則、変数宣言とシャドウイング機構の詳細については
> [モジュールシステム仕様](./modules.md#第四章スコープ) を参照。

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**セマンティクス**：`return`
は**非局所的退出**であり、最も近い**関数境界**を退出する（すべてのブロック——`if` / `while` / `for` /
`match` / 裸ブロック / `spawn` / `unsafe`
を含む——を貫通する）、値を呼び出し元に渡す。これは「ブロックに返す」ものではない。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'` に対して成立する（爆発原理、
[型システム §2.2](./type-system.md) 参照）ため、`return`
は追加の規則制約なしに任意の戻り型の位置に現れることができる。

**ブロック評価との関係**：ブロックの値は常に**末尾式**である（§2.9 参照）。`{ return n }`
はブロックとして値が `n`、型は `Never` である；同时に `return`
の作用は関数を退出すること。**二つの事象が同時に成立し**、爆発原理によって共存する。

`return` と末尾式が共同して「早期リターン」を成立させ、`return`
が関数を特に指す追加規則は不要となる——詳細は
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md) を参照。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通し、関数を退出する（型は Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**セマンティクス**：それを囲む最も内側の `while`/`for`
ループを直ちに終了し、制御フローをそのループ本体の後へ移す。

- **直近の一層のみを出る**：`break`

> は常にそれを含む最も内側のループに作用する。ネストされたループで複数層を一度に飛び出す必要がある場合は、内側のループを関数として抽出し
> `return`
> で返すか、フラグ変数を使用する（break/continue にはラベルがない；将来ループラベルを導入する場合、ループ宣言側の構文に従って RFC プロセスを進める）

- **ループ本体内に限定**：`break` は `while`/`for`

> ループ本体内（本体内にネストされたブロック/if/match を含む）にのみ出現でき、ループ外で出現するとコンパイルエラーとなる（E1102
> `'break' outside of a loop`）

- **停止性証明に影響しない**：`while`
  ループは依然として停止が証明されなければならない（decreases 測度）；`break`

> は停止性の論証に参加せず、`while true { break }` は受理されない

- **借用セマンティクス**：break の制御フロー辺は RFC-009a の逆 BFS 活性分析の構造的切断に参加する（飛び出した反復は逆辺の活性導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループの後へ移動し、i == 3
    }
}

// ネストされたループ：break は内側のみを出る
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側のループのみを終了する
    }
    j = j + 1                  // 外側の各反復はここで実行される
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**セマンティクス**：現在の反復内の残りの文をスキップし、それを囲む最も内側のループの次のラウンドに直接入る——
`while` は条件の再評価に戻り、`for` は次の要素を取り出す。

- **直近の一層のみに作用する**：`break` と同じで、ラベルを持たない
- **ループ本体内に限定**：ループ外で出現するとコンパイルエラーとなる（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 以下の累算をスキップし、n == 3 は加算されない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

### 3.9 for 文

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block

#### 3.9.1 セマンティクス：各反復は新しい値を束縛する

YaoXiang の for ループのセマンティクスは従来言語とは異なる：**各反復は新しい値を束縛し、同じ変数を変更するのではない**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行プロセス**：

| 反復   | ループ変数の振る舞い                                                                            |
| ------ | ----------------------------------------------------------------------------------------------- |
| 1 回目 | 新しい束縛 `i = 1` を作成し、ループ本体が実行され、1 を出力                                     |
| 2 回目 | 新しい束縛 `i = 2` を作成し（以前の束縛はすでに破棄されている）、ループ本体が実行され、2 を出力 |
| 3 回目 | 新しい束縛 `i = 3` を作成し、ループ本体が実行され、3 を出力                                     |
| 4 回目 | 新しい束縛 `i = 4` を作成し、ループ本体が実行され、4 を出力                                     |
| 終了   | ループ本体が終了し、束縛が破棄される                                                            |

**要点**：各反復が終了すると、その回の反復で作成された束縛は破棄される。次の反復は完全に新しい束縛であり、前の反復の束縛とは関係がない。

#### 3.9.2 for と for mut の違い

| 構文                | ループ変数の可変性 | 説明                             |
| ------------------- | ------------------ | -------------------------------- |
| `for i in 1..5`     | 不変               | ループ本体内で束縛を変更できない |
| `for mut i in 1..5` | 可変               | ループ本体内で束縛を変更できる   |

```yaoxiang
// 合法：各反復が新しい値を束縛するため、変更は不要
for i in 1..5 {
    print(i)  // i の値を読み取る
}

// エラー：不変束縛は変更できない
for i in 1..5 {
    i = i + 1  // エラー：不変束縛は変更できない
}

// 合法：for mut を使用すれば束縛の変更が許可される
for mut i in 1..5 {
    i = i + 1  // 変更が許可される
}
```

#### 3.9.3 シャドウイング検査

YaoXiang は変数のシャドウイングを禁止する。for ループ変数は外側スコープの変数と同名にすることはできない：

```yaoxiang
// エラー：i はすでに外部で宣言されている
i = 10
for i in 1..5 {
    print(i)
}

// 正しい：異なる変数名を使用する
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される。詳細は
[4.3 シャドウイング規則](./modules.md#43-シャドウイング規則) を参照。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数のセマンティクス                 |
| -------- | ---------------------------------------------- |
| YaoXiang | 各反復が新しい値を束縛する                     |
| Rust     | 同じ変数を変更する（mut が必要）               |
| Python   | 同じ変数を変更する（mut 不要）                 |
| C/C++    | 同じ変数を変更する（ポインタまたは参照が必要） |

**設計理由**：YaoXiang が束縛セマンティクスを採用する理由は以下の通り：

1. **自然なセマンティクスに合致する**
   自然言語では、「集合の各要素 x について」は各 x が独立した個体であることを意味する。YaoXiang の
   `for i in 1..5`
   は「1 から 5 の各 i について」と読まれ、各反復の i は完全に新しい束縛である。これは人間の直感的な理解と一致する。

2. **偶発的な変更を防ぐ**
   デフォルトの不変束縛セマンティクスは、ループ本体内でループ変数を偶発的に変更できないことを意味する。複雑なループ本体内のどこかで誤って
   `i = ...` と書いて追跡困難なバグを引き起こす心配がない。

3. **高性能ソリューションに手が届く**
   反復間で変数を再利用する必要がある場合（例：アキュムレータ、キャッシュ）、`for mut`

> を使用すれば可変束縛モードに切り替えられる。これは暗黙の共有状態よりも明確である——意図は構文で明示的に表現され、ランタイムの振る舞いに隠されることはない。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：並行領域を明示的に宣言し、ブロック内の式を並行実行する。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側の変数をキャプチャする**（RFC-024 §2.3、値キャプチャのセマンティクス）：

- ブロック本体が外側の変数を参照する =

> **Move 値キャプチャ**：値は spawn 作成時点でクロージャ環境にスナップショットされ、ブロック本体は env 経由で読み取る（LoadUpvalue）

- **プリミティブ型**（Int/Float/Bool/Char）は値コピーされ、外側の変数は影響を受けない
- **ハンドル型**（Struct/String/List など）のスナップショット = ハンドルコピー、基礎となるオブジェクトを共有する；Embedded ランタイム（デフォルト）では同一スレッド同一ヒープのため、ハンドルは有効
- 複数タスク間の共有には明示的な `ref` が必要（§2.13、コンパイラが自動的に Rc/Arc を選択）
- ブロック内の `return` が参照する外側の変数も同様にキャプチャされる

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 は値キャプチャされ、result == 6
}
```

### 3.11 プログラムエントリとトップレベル文

ソースファイルはコンパイラの視点では二つの役割を持ち、**`yaoxiang.toml` の存在によって決定される**：

| 役割       | 判定                                         | プログラムの主体                                              |
| ---------- | -------------------------------------------- | ------------------------------------------------------------- |
| **Script** | 単一ファイルを直接実行、`yaoxiang.toml` なし | **トップレベル文**（記述順に実行）；`main` は通常の束縛       |
| **Bin**    | `yaoxiang.toml` が存在する                   | **`main` 関数**；トップレベルに実行可能な文を置いてはならない |

#### Script：トップレベル文がプログラムである

マニフェストがない場合、ファイルは「スクリプト」であり、**トップレベル文は記述順に実行される**：

```yaoxiang
use std.io
io.println("hello")          // 直接実行
x: Int = { 42 }              // トップレベルの束縛：ランタイム初期化
io.println(x)                // 42
```

このモードでは `main` は**特別ではない**——単なる通常の束縛である。`main`
を実行させたい場合は、明示的に呼び出す必要がある：

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← この行を必ず書く
```

> **なぜ `main` を自動的に呼び出さないのか？**
> トップレベル文がすでにプログラムの主体である。その上で暗黙的に `main` を呼び出すと、明示的に
> `main()`
> と書いたスクリプトが二度実行されることになる。二つの規則は共存できないため、Script では「トップレベル文」という単一の実行エントリのみが存在する。

#### Bin：`main` がエントリである

マニフェストがある場合、ファイルは「実行可能ターゲット」であり、この場合：

- `main`
  を定義しなければならず、それは関数でなければならない（シグネチャはゼロ引数で呼び出し可能でなければならない）
- トップレベルには実行可能な文を許可しない——プログラムの主体が `main` である

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

`main` の欠落または `main` が関数でないことはいずれもコンパイルエラーである（前者の場合：`main`
がないときはすべての関数が到達不能；後者の場合：値束縛は呼び出されない）。

> **ライブラリファイル**：他のファイルに `use` されるファイル、または `[lib].path` / `[exports]`
> が指すファイルは `main` を要求しない——これらはプログラムのエントリではない。

#### トップレベル束縛の初期化

トップレベル束縛の初期化値は**ランタイムで評価され**、コンパイル時定数である必要はない：

```yaoxiang
answer: Int = { 42 }              // ブロックの値
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // 関数呼び出し
```

初期化は**依存順序**で実行され、記述順序には依存しない：

```yaoxiang
derived: Int = base * 3           // 後述の base を参照
base: Int = 7                     // 先に初期化される（トポロジカルソート）
```

循環依存はコンパイルエラーである（環上の名前が列挙される）：

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // エラー：a → b → a
```

> **設計根拠**：RFC-029f（ファイル役割モデル）、RFC-010a 付録 D（ブロック束縛裁定）。
