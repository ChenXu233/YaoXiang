# 構文仕様

本文書は YaoXiang プログラミング言語の構文仕様を定義するものであり、字句構造、構文規則、演算子の優先順位を含む。

---

## 第一章：字句構造

### 1.1 ソースファイル

YaoXiang のソースファイルは UTF-8 エンコーディングを使用しなければならない。ソースファイルの拡張子は通常
`.yx` である。

### 1.2 トークンの分類

| カテゴリ   | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語定義の予約語                 | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り子   | 構文の区切り                     | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiang はごく少量のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として使用することはできない。

### 1.4 予約語

YaoXiang の「予約語」は 3 層に分かれており、それぞれパーサ（parser）と型検査器（type
checker）が異なる段階で識別する：

#### 1.4.1 リテラル予約語

パーサが独立したトークンとして持つリテラル識別子は、通常の識別子としては使用できない：

| 識別子  | 所属する型 | 説明                                                                                            |
| ------- | ---------- | ----------------------------------------------------------------------------------------------- |
| `Type`  | —          | メタ型キーワード                                                                                |
| `true`  | Bool       | ブール真値                                                                                      |
| `false` | Bool       | ブール偽値                                                                                      |
| `void`  | Void       | Void リテラル（Unit 値）。小文字の `void` は値リテラル；大文字の `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 コンストラクタ式

以下のコンストラクタはパターンマッチングと式の文脈でパーサにより識別される：

| コンストラクタ | 所属する型 | 説明                      |
| -------------- | ---------- | ------------------------- |
| `some(T)`      | Option     | Option の値バリアント構築 |
| `ok(T)`        | Result     | Result の成功バリアント   |
| `err(E)`       | Result     | Result のエラー変種       |

#### 1.4.3 組み込み型名

以下の型名は型検査器により事前登録されており、インポートなしでも型の位置で使用できる。パーサはこれらを通常の識別子として扱う——**予約語ではなく、ローカルバインディングでシャドウィング可能（推奨されない）**。

| 型名     | 論理的対応   | 説明                                                                                                                         |
| -------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤（真/Unit） | 零フィールドの積型、ちょうど 1 つの居住者（`void` リテラル、§1.4.1 参照）                                                    |
| `Never`  | ⊥（偽/空型） | 零バリアントの和型、零居住者。`Never` 値を生成する式は存在しない。`Never <: T` がすべての `T` について成立する（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                                 |
| `Float`  | —            | 浮動小数点数                                                                                                                 |
| `Bool`   | —            | ブール値：`true` / `false`                                                                                                   |
| `Char`   | —            | Unicode 文字                                                                                                                 |
| `String` | —            | 文字列                                                                                                                       |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、後続の文字は文字、数字、またはアンダースコアである。識別子は大文字小文字を区別する。

特別な識別子：

- `_` はプレースホルダとして使われ、何らかの値を無視することを表す
- アンダースコア始まりの識別子はプライベートメンバを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // ターゲット型アノテーションが Array(T, N) のときリテラルは固定長配列に落ちる
```

> **辞書リテラルは少なくとも 1 つのキーと値のペアを要求する**：`{}`
> **は**空辞書**ではない**——空ブロック（値 `Void`、 [§2.9](#_2-9-ブロック式)
> 参照）である。空の辞書には `dict.new()` を使う：
>
> ```yaoxiang
> empty = dict.new()                  // ✅ 空辞書
> d = { "a": 1 }                       // ✅ 辞書リテラル
> wrong = {}                           // ❌ これは辞書ではなく、空ブロック（Void）
> ```
>
> **判定基準は内容**：`Dict` 文法は少なくとも 1 つの `String ':' Expr` を要求し、`{}`
> には判定材料がないため、ブロック構造の零形式を取る。非空形式は内容が自己記述する（`{ "k": v }`
> はキーと値のペアを持つ → 辞書）——これは `f = { 5 }` が関数ではなく `Int`
> 値であることと同源である：**型は内容により決定される**。

> Set にはリテラル文法も実行時表現も存在しない——集合型は計画中であり、要件が出現した際に Dict パターンに従って補完する（std.set +
> HeapValue::Set）。List/Dict リテラルの落点はコンテキスト型アノテーションにより決定される：素のリテラルと
> `List(T)` アノテーションは可成長リストに落ちる；`Array(T, N)`
> アノテーションが直接リテラルに作用すれば固定長配列に落ちる。暗黙の List→Array 変換は禁止。
>
> Array リテラルセマンティクス：
>
> - 要素数は N と等しくなければならない。等しくない場合はコンパイル時 E1002；空リテラルに非零 N の場合も同様に拒否
> - 各要素の型は T と互換でなければならない。適合しない場合はコンパイル時 E1002
> - N の文法形式：整数リテラル（負も可）または定数名のみ；複合式（例：`2+1`）は解析時に拒否
> - N がシンボル定数（関数の const パラメータ、例：`Array(Int, n)`）の場合、要素数の検査は型の精化段階まで遅延
> - v1 ネストした配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時拒否、層ごとに明示的に構築する必要がある；再帰的な落点は将来のバージョンに先送り

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **挙動の厳格化（移行記録）**：反復変数の文法は元から `'for' Identifier 'in'`
> だが、旧実装では pattern が完全な pratt 解析を走らせていた——`'in'`
> を中置演算子として登録した結果、 `x` は `in items`
> を membership 式として飲み込んでいた。修正後は非識別子 pattern は直接解析失敗となり、旧実装のように
> `_` にフォールバック（静かにエラーを吸収）しない。影響範囲：これまで解析可能だった
> `[x for (a, b) in pairs]`
> のような書き方は現在エラーになる——この形式には定義された挙動がそもそも存在せず（変数は常に
> `_`）、厳格化の方向は正しく、意味的な移行コストはない。

#### 1.6.6 メンバシップ検査

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子であり、`Bool` を返す——命中すれば `true`、未命中なら `false`
> でエラーを出さない。意味の分割：`[]` は存在をアサートして値を取り出す（失敗時にエラー）、 `in`
> は存在を問い合わせる（未命中は正常な `false`）。右オペランドのカバー：List / Array /
> Dict(キー集合) / Tuple / String(部分文字列) / Range(区間)。`in`
> は一階ホール述語であり、型の精化段階でコンパイル時証明可能命題の基底となる。（Set は右オペランドのリストから除外——Set には実行時表現がない、§1.6.4 参照）

### 1.7 コメント

```
// 単行コメント

/* 複数行コメント
   複数行に渡ることができる */
```

### 1.8 インデント規則

コードは 4 スペースのインデントを使用しなければならず、Tab 文字の使用は禁止。これは強制的な構文規則である。

## 第二章：構文規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強く結合する：呼び出しとメンバアクセスのみより低く、すべての二項演算子より高い。したがって
> `!a == b` ≡ `(!a) == b`（Zig 式のセマンティクス）；`!`
> は純粋な単項演算であり、短絡制御フローには参加せず、`and`/`or`
> キーワード（短絡評価）とは直交する（RFC-010 が権威的な定義）。

> **Range の結合の強さ**：`..` の結合力は (6,
> 7)——左の 6 は加算（7）より低く、右の 7 は加算を吸収するが同レベルの `..`
> は吸収しない。変更前後の対照：
>
> | 式           | 変更前（レベル 1、右結合）                                                                      | 変更後（(6,7)、左結合）                                            |
> | ------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
> | `x in 1..10` | `x in 1..10`（`in` の右オペランドはレベル 4、`..` のレベル 1 では吸収できず、実質的に解析不能） | `x in (1..10)`——区間全体が `in` の右オペランド                     |
> | `0..n+2`     | `(0..n)+2`（右結合の落とし穴：上界が食べられ、`for` ループが直接 E3004）                        | `0..(n+2)`——上界は算術式                                           |
> | `a == b..c`  | `a == (b..c)`（`..` のレベル 1 < `==` のレベル 3、自然に全体）                                  | `a == (b..c)`——**意味は不変**、`..` は依然として比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                                                      | `1..(2*3)`——上界は算術式                                           |
> | `a..b..c`    | `a..(b..c)`（右結合の連鎖、無意味な Range の入れ子）                                            | `(a..b)..c`——**ステップ形式**（`c` はステップ）                    |
>
> 純効果：複合上界 `for i in 0..n+2` が「解析成功だが E3004」から「直接使用可能」に； `x in 1..10`
> が「解析不能」から「区間検査」に；`a..b..c`
> が「無意味な入れ子」から「ステップ成分」に。レベル 6 は `+`（レベル 5）と
> `<<`（レベル 7）の間に位置し、数学的慣習に従う：区間は強く結合する構文であり、上界は当然完全な算術式である。

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt 間の区切りと改行の挙動（`;`
> による明示的区切り、改行による終端、続行の例外、行頭の `(`/`[` は決してマージされない）は
> [RFC-038](../design/rfc/draft/038-statement-termination.md) で定義される。

#### 2.9.1 `{` の 3 つの形式

`{` は式の位置にちょうど 3 つの解釈を持ち、**内容**により一度に判定される：

| 形式             | 記法              | 型           | 例               |
| ---------------- | ----------------- | ------------ | ---------------- |
| **空ブロック**   | `{}`              | `Void`       | `x: Void = {}`   |
| **辞書リテラル** | `{ "k": v, ... }` | `Dict(K, V)` | `d = { "a": 1 }` |
| **ブロック**     | `{ Stmt* Expr? }` | 末尾式の型   | `y = { 1 + 1 }`  |

**判定順序**：

1. `{}`（内容なし）→ **空ブロック**、値 `Void`
2. 最初の要素が `String ':' Expr` のキーと値のペア → **辞書リテラル**
3. それ以外 → **ブロック**、値は末尾式により与えられる

> **なぜ `{}` は空辞書ではないか**：空辞書の「空」は自己記述できない（`Dict(K, V)`
> でもあり得、空ブロックでもあり得る）、そして辞書文法 [§1.6.4](#_1-6-4-コレクション)
> は少なくとも 1 つのキーと値のペアを要求する。判定材料がない場合はブロック構造の零形式を取る：これは
> `unsafe {}` / `spawn {}` と一致し、特例を導入しない。空辞書には `dict.new()` を使う。
>
> **なぜ関数にはアノテーションが必要か**：`f = { stmt }`
> は**値**（末尾式の型）であり、関数ではない。関数を定義したい場合は Fn アノテーションを明記する：`f: () -> Int = { 5 }`。これは辞書と同じ原則である：**型は内容により決定される**もので、アノテーションの存在により決定されるものではない。（この規則は RFC-010a 付録 D 裁定 C の「アノテーションなし → デフォルトで関数」を置き換える、誤り訂正参照。）

**統一セマンティクス**：すべての `{}` ブロックの値は**末尾式**により与えられ、`return` は `Never`
型の非局所的退出である。

| ブロック種別 | 値の出口 | 空ブロック `{}` |
| ------------ | -------- | --------------- |
| 通常の `{}`  | 末尾式   | `Void`          |
| `unsafe {}`  | 末尾式   | `Void`          |
| `spawn {}`   | 末尾式   | `Void`          |

**核心原則**（詳しくは [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)
参照）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**の場合ブロックの値は `Void`；`Void` を望むなら明示的に `Void` と書く
- **`return`
  は最も近い関数の境界を退出する**（すべてのブロックを貫通し、ブロックに「返さない」）、型は
  `Never`；`Never <: T`

> は任意の型について成立する（爆発原理）ので、任意の戻り型の位置に現れ得る

- 式形式 `= expr` は直接値を与える

```yaoxiang
// 通常の {} ブロック：末尾式が値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式が型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式が結果を与える
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // ブロックの値
}

// return：ブロックを貫通し、関数を退出する
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if と関数本体を貫通し、関数を退出
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数か、ブロック値か？

`name = { ... }`
は関数定義（RFC-007「ゼロ引数最簡」）にも、ブロック値バインディングにもなり得る。**アノテーション優先、デフォルトは関数**の裁定（RFC-010a 付録 D）に従う：

| 場合                     | 結果           | 例                                 |
| ------------------------ | -------------- | ---------------------------------- |
| 値が Lambda（`=>`）      | 関数           | `f = () => 5` → `f()` = 5          |
| アノテーションが関数型   | 関数           | `f: () -> Int = { 5 }` → `f()` = 5 |
| アノテーションが非関数型 | **ブロック値** | `x: Int = { 5 }` → `x` = 5         |
| アノテーションなし       | 関数           | `f = { 5 }` → `f()` = 5            |

**アノテーションが型を表す**：`x: Int = ...` は `x` が `Int` であることを宣言するので、`{ ... }` は
`Int` に評価される； `f: () -> Int = ...` は `f` が関数であることを宣言するので、`{ ... }`
は関数本体である。

`{ ... }` を即座に評価したいなら、**ターゲット型を書けばよい**（新しい構文は不要）：

```yaoxiang
// ブロック値：即座に評価
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：アノテーションなし、デフォルト
f = { 5 }        // f() = 5
```

#### ネストした関数型：カリー化か、関数を返すか？

`->` の右側のネストした関数型には 2 つの読み方があり、**括弧**により区別される（RFC-004）：

| 書き方                          | 意味           | 呼び出し      |
| ------------------------------- | -------------- | ------------- |
| `(a: Int) -> (b: Int) -> Int`   | **カリー化**   | `f(1)(2)`     |
| `(a: Int) -> ((b: Int) -> Int)` | **関数を返す** | `g(1)` は関数 |

根拠：**アノテーションが型を表す**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int`
を宣言するので、 `g(1)` はその関数でなければならない、「次のパラメータの続き」ではない。

```yaoxiang
// カリー化：2 段のパラメータを逐次与える
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数を返す：外側は 1 段のパラメータ、返されるのが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返された関数は変数に格納したり、渡したりできる
```

括弧なしのネストした `Fn` は一律カリー化（RFC-011 の型パラメータ形式を含む）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型検査**：括弧は戻り型を宣言する。body はその型を生成しなければならない。
`f: () -> (() -> Int) = { 7 }` は誤り——期待される型は `() -> Int`、実際に得られるのは
`Int`（E1002）。

### 2.10 Lambda 式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子であり、優先順位は `.` と同レベルである。`Result(T, E)` 型に対して：

- `Ok(v)` のとき値 `v` を抽出して実行を続ける
- `Err(e)` のときエラーを上位に伝播する（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時は値を抽出し、失敗時は上位に伝播
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は範囲値を作成する（Range は一級値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値：バインド、受け渡し、メンバ判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// ステップ形式（第 3 成分、デフォルト 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **ステップのセマンティクス**：`a..b..c` の `c` はステップ。`c = 0`
> のリテラルはコンパイル時拒否；動的な `c`
> は実行時零チェック（E6001 系統；エラーシステム実装後 Result に格上げ）。 `c < 0`
> は合法、区間方向は符号に応じて反転する（`10..0..(-2)` は減少）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref`
は共有所有を作成する。コンパイラは自動的に Rc（単一タスク）または Arc（タスク間）を選択し、ユーザは実装の詳細を気にする必要がない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク間：コンパイラが自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型の定義と生ポインタの操作に使用する。`return`
を使って型定義を上位スコープに返す。

**セマンティクス**：

- `unsafe {}` 内で型を定義し、生ポインタを操作できる
- 返された型は `unsafe {}` 外で利用できる
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロック内で不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外で利用できる
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックはスコープを作成する
- 内側のスコープは外側のスコープの変数にアクセスできる
- 外側のスコープは内側のスコープの変数にアクセスできない
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で可視
}
// x はこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数外では不可視
```

**変数宣言とシャドウィング**：

- `x = value`：スコープチェーンを遡って外側に x を検索し、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的な新しい可変宣言、外側と同名を禁止
- 同一スコープ内で任意の名前の宣言は 1 回のみ

> **詳細定義**：スコープの完全な規則、変数宣言とシャドウィング機構について詳しくは
> [モジュールシステム仕様](./modules.md#第四章作用域) を参照。

### 3.1 文の分類

```
Stmt        ::= LetStmt
              | ExprStmt
              | ReturnStmt
              | BreakStmt
              | ContinueStmt
              | IfStmt
              | MatchStmt
              | WhileStmt
              | ForStmt
              | SpawnStmt
```

### 3.2 変数宣言

```
LetStmt     ::= ('mut')? Identifier (':' TypeExpr)? '=' Expr
```

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**セマンティクス**：`return`
は**非局所的退出**であり、最も近い**関数の境界**を退出する（すべてのブロック——`if` / `while` / `for`
/ `match` / 素のブロック / `spawn` / `unsafe`
を含む——を貫通する）、値を呼び出し元に渡す。ブロックに「返す」わけではない。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'`
について成立する（爆発原理、[型システム §2.2](./type-system.md) 参照）ので、`return`
は任意の戻り型の位置に現れ得る、追加規則の制約は不要。

**ブロック評価との関係**：ブロックの値は常に**末尾式**である（§2.9 参照）。`{ return n }`
をブロックとして見ると、その値は `n` で型は `Never`；同時に `return`
の作用は関数の退出である。**2 つの事象が同時に成立する**のは爆発原理により共存する。

`return` と末尾式が相まって「早期リターン」を実現する、`return`
が関数を特に指す追加規則は不要——[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)
参照。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通し、関数を退出（型 Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**セマンティクス**：含まれる最も内側の `while`/`for`
ループを直ちに終了し、制御フローをそのループ本体の後へ移す。

- **最も内側の 1 層のみを出る**：`break`

> は常にそれを含む最も内側のループに作用する。ネストしたループで複数層を一度に抜け出す必要がある場合は、内側のループを関数として抽出し
> `return`
> で返すか、フラグ変数を使う（break/continue はラベルを取らない；将来ループラベルを導入する場合は、ループ宣言側の構文に従い RFC の流程を経る、これは証明パイプラインの複数出口設計と合わせて裁定する）

- **ループ本体内に限定**：`break` は `while`/`for`

> ループ本体内（本体内にネストしたブロック/if/match を含む）にのみ現れ、ループ外に出現するとコンパイルエラー（E1102
> `'break' outside of a loop`）

- **停止性証明に影響しない**：`while`
  ループは依然として停止が証明可能でなければならない（decreases 測度）；`break`

> は停止性の論証に参加しないため、`while true { break }` は受理されない

- **借用セマンティクス**：break の制御フロー辺は RFC-009a の逆 BFS 活性分析の構造的切断に参加する（飛び出した反復は逆辺活性の導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループ後へ、i == 3
    }
}

// ネストしたループ：break は内側のみを終了
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側ループのみを終了
    }
    j = j + 1                  // 外側の各反復でここに実行が到達
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**セマンティクス**：その反復の残りの文をスキップし、含まれる最も内側のループの次のラウンドに直接入る——
`while` は条件の再判定へ戻り、`for` は次の要素を取る。

- **最も内側の 1 層のみに作用**：`break` と同じ、ラベルなし
- **ループ本体内に限定**：ループ外に出現するとコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 下の累算をスキップ、n == 3 は加算されない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

IfStmt      ::= 'if' Expr Block ('else' 'if' Expr Block)* ('else' Block)?

### 3.8 while 文

### 3.9 for 文

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 セマンティクス：各反復は新しい値をバインドする

YaoXiang の for ループのセマンティクスは従来言語と異なる：**各反復は新しい値をバインドするものであり、同じ変数を変更するものではない**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行過程**：

| 反復   | ループ変数の挙動                                                                      |
| ------ | ------------------------------------------------------------------------------------- |
| 1 回目 | 新しいバインド `i = 1` を作成し、ループ本体を実行、1 を表示                           |
| 2 回目 | 新しいバインド `i = 2` を作成（以前のバインドは破棄済み）、ループ本体を実行、2 を表示 |
| 3 回目 | 新しいバインド `i = 3` を作成し、ループ本体を実行、3 を表示                           |
| 4 回目 | 新しいバインド `i = 4` を作成し、ループ本体を実行、4 を表示                           |
| 終了   | ループ本体終了、バインド破棄                                                          |

**要点**：各反復終了後、その反復で作成されたバインドは破棄される。次の反復はまったく新しいバインドであり、前の反復のバインドとは一切関係がない。

#### 3.9.2 for と for mut の違い

| 構文                | ループ変数の可变性 | 説明                                 |
| ------------------- | ------------------ | ------------------------------------ |
| `for i in 1..5`     | 不変               | ループ本体内でバインドを変更できない |
| `for mut i in 1..5` | 可変               | ループ本体内でバインドを変更できる   |

```yaoxiang
// 合法：各反復で新しい値をバインドする、変更は不要
for i in 1..5 {
    print(i)  // i の値を読む
}

// エラー：不変バインド、変更不可
for i in 1..5 {
    i = i + 1  // エラー：不変バインドは変更不可
}

// 合法：for mut を使えば変更可能
for mut i in 1..5 {
    i = i + 1  // 変更可能
}
```

#### 3.9.3 シャドウィング検査

YaoXiang は変数のシャドウィングを禁止する。for ループ変数は外側スコープの変数と同名にできない：

```yaoxiang
// エラー：i はすでに外側で宣言済み
i = 10
for i in 1..5 {
    print(i)
}

// 正しい：異なる変数名を使う
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される、詳しくは
[4.3 シャドウィング規則](./modules.md#43-遮蔽规则) 参照。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数のセマンティクス         |
| -------- | -------------------------------------- |
| YaoXiang | 各反復で新しい値をバインド             |
| Rust     | 同じ変数を変更（mut が必要）           |
| Python   | 同じ変数を変更（mut 不要）             |
| C/C++    | 同じ変数を変更（ポインタか参照が必要） |

**設計理由**：YaoXiang がバインドセマンティクスを採用するのは：

1. **より自然なセマンティクスに合致**：自然言語では「集合の各要素 x について」は各 x が独立した個体であることを意味する。YaoXiang の
   `for i in 1..5`
   は「1 から 5 の各 i について」と読まれ、各反復の i はまったく新しいバインドであり、人間の直感的な理解と一致する。

2. **偶発的な変更を回避する**：デフォルトで不変なバインドセマンティクスは、ループ本体内でループ変数を偶発的に変更できないことを意味する。複雑なループ本体内のどこかで誤って
   `i = ...` と書いて追跡困難なバグを引き起こす心配がない。

3. **高性能なアプローチが手の届くところに**：反復間で変数を再利用することが実際に必要な場合（例：アキュムレータ、キャッシュ）、`for mut`

> を宣言すれば可変バインドモードに切り替えられる。これは暗黙の共有状態より明瞭である——意図は構文により明示的に表現され、実行時の挙動に隠されているのではない。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：並行実行領域を明示的に宣言し、ブロック内の式を並行実行する。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側の変数をキャプチャする**（RFC-024 §2.3、値キャプチャのセマンティクス）：

- ブロック本体が外側の変数を参照 =

> **Move 値キャプチャ**：値は spawn の作成時点でクロージャ環境にスナップショットされ、ブロック本体は env を経由して読む（LoadUpvalue）

- **プリミティブ型**（Int/Float/Bool/Char）は値をコピーし、外側の変数は影響を受けない
- **ハンドル型**（Struct/String/List など）のスナップショット = ハンドルのコピー、基礎となるオブジェクトを共有；Embedded ランタイム（デフォルト）では同一スレッド同一ヒープなので、ハンドルは有効
- 複数タスク間で共有するには明示的な `ref` が必要（§2.13、コンパイラが Rc/Arc を自動選択）
- ブロック内の `return` が参照する外側の変数も同様にキャプチャされる

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 は値キャプチャ、result == 6
}
```

### 3.11 プログラム入口とトップレベル文

ソースファイルはコンパイラの視点で 2 つの役割を持ち、**`yaoxiang.toml` の存在により決定される**：

| 役割       | 判定                                         | プログラム本体                                              |
| ---------- | -------------------------------------------- | ----------------------------------------------------------- |
| **Script** | 単一ファイルを直接実行、`yaoxiang.toml` なし | **トップレベル文**（記述順に実行）；`main` は通常のバインド |
| **Bin**    | `yaoxiang.toml` が存在                       | **`main` 関数**；トップレベルに実行可能文は不可             |

#### Script：トップレベル文がプログラム

manifest がない場合、ファイルは「スクリプト」であり、**トップレベル文は記述順に実行される**：

```yaoxiang
use std.io
io.println("hello")          // 直接実行
x: Int = { 42 }              // トップレベルバインド：実行時に初期化
io.println(x)                // 42
```

このモードでは `main` は**特別ではない**——単なる通常のバインドである。`main`
を実行させたい場合は明示的に呼び出す必要がある：

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← この行が必須
```

> **なぜ `main` を自動呼び出ししないのか？**
> トップレベル文はすでにプログラム本体である。ここでさらに暗黙的に `main` を呼び出すと、明示的に
> `main()`
> と書いたスクリプトは 2 回実行される。2 つの規則は共存できないため、Script には「トップレベル文」という 1 つの実行入口しかない。

#### Bin：`main` が入口

manifest がある場合、ファイルは「実行可能ターゲット」であり、このとき：

- `main` を定義しなければならず、それは関数でなければならない（シグネチャはゼロ引数呼び出し可能）
- トップレベルに実行可能文は許されない——プログラム本体は `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

`main` の欠落や `main` が関数でないことはいずれもコンパイルエラー（前者は：`main`
がないとき全関数が到達不能；後者は：値バインディングは呼び出されない）。

> **ライブラリファイル**：他のファイルに `use` されるファイル、または `[lib].path` / `[exports]`
> で指されるファイルは `main` を要求しない——これらはプログラム入口ではない。

#### トップレベルバインディングの初期化

トップレベルバインディングの初期化値は**実行時に評価**され、コンパイル時定数であることは要求されない：

```yaoxiang
answer: Int = { 42 }              // ブロック値
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // 関数呼び出し
```

初期化は**依存順**で実行され、記述順には依存しない：

```yaoxiang
derived: Int = base * 3           // 後で宣言された base を参照
base: Int = 7                     // 先に初期化（トポロジカルソート）
```

循環依存はコンパイルエラー（環上の名前が列挙される）：

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // エラー：a → b → a
```

> **設計根拠**：RFC-029f（ファイル役割モデル）、RFC-010a 付録 D（ブロックバインディング裁定）。

### A.2 エラー処理

```
Expr '?'              // エラー伝播（Result 型）
```

### A.3 match 構文

```
match value {
    pattern1 => expr1,
    pattern2 if guard => expr2,
    _ => default_expr,
}
```
