# 構文規範

このファイルでは、YaoXiang プログラミング言語の構文規範を定義します。字句構造、構文規則、演算子の優先順位を含みます。

---

## 第1章：字句構造

### 1.1 ソースファイル

YaoXiang ソースファイルは UTF-8 エンコーディングを使用する必要があります。ソースファイルは通常 `.yx` を拡張子とします。

### 1.2 字句トークンの分類

| カテゴリ | 説明                 | 例                          |
| -------- | -------------------- | --------------------------- |
| 識別子   | 文字またはアンダースコアで開始 | `x`, `_private`, `my_var` |
| キーワード | 言語が予約する単語   | `Type`, `pub`, `use`        |
| リテラル | 固定値               | `42`, `"hello"`, `true`     |
| 演算子   | 演算記号             | `+`, `-`, `*`, `/`          |
| 区切り子 | 構文区切り           | `(`, `)`, `{`, `}`, `,`     |

### 1.3 キーワード

YaoXiang は非常に少数のキーワードを定義します：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはどのようなコンテキストでも特別な意味を持ち、識別子として使用できません。

### 1.4 予約語

YaoXiang の「予約語」は3階層あり、パーサー（parser）と型チェッカー（type checker）が異なる段階で識別します：

#### 1.4.1 リテラル予約語

パーサーが独立したトークンを持つリテラル識別子は、通常の識別子として使用できません：

| 識別子  | 所属型 | 説明                                                                               |
| ------- | ------ | ---------------------------------------------------------------------------------- |
| `Type`  | —      | メタ型キーワード                                                                   |
| `true`  | Bool   | 真理値の真                                                                         |
| `false` | Bool   | 真理値の偽                                                                         |
| `void`  | Void   | Void リテラル（Unit 値）。小文字 `void` は値リテラル；大文字 `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 構築子式

以下の構築子は、パターン照合と式のコンテキストでパーサーによって識別されます：

| 構築子    | 所属型  | 説明               |
| --------- | ------- | ------------------ |
| `some(T)` | Option  | Option 値バリアント構築 |
| `ok(T)`   | Result  | Result 成功バリアント |
| `err(E)`  | Result  | Result エラーバリアント  |

#### 1.4.3 組み込み型名

以下の型名は型チェッカーが事前登録しており、インポートなしで型位置で使用できます。パーサーはこれらを通常の識別子として扱います——**予約語ではないため、局部束縛でシャドウできます（推奨はしません）**。

| 型名    | 論理対応          | 説明                                                                                                    |
| ------- | ----------------- | ------------------------------------------------------------------------------------------------------- |
| `Void`  | ⊤（真/Unit）      | ゼロフィールド積型，刚好一个居留者（`void` リテラル、§1.4.1 参照）                                            |
| `Never` | ⊥（偽/空型）      | ゼロバリアントと型、ゼロの居留者。任何式も `Never` 値を生成できません。`Never <: T` は全ての `T` に対して成立（爆発原理）。 |
| `Int`   | —                 | 符号付き整数                                                                                            |
| `Float` | —                 | 浮動小数点数                                                                                            |
| `Bool`  | —                 | 真理値：`true` / `false`                                                                                |
| `Char`  | —                 | Unicode 文字                                                                                            |
| `String`| —                 | 文字列                                                                                                  |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、後続の文字は文字、数字、またはアンダースコアを使用できます。識別子は大小文字を区別します。

特別な識別子：

- `_` はプレースホルダーとして使用され、ある値を無視することを示します
- アンダースコアで始まる識別子はプライベートメンバを示します

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // ターゲット型注釈が Array(T, N) の場合リテラルは固定長配列に落ちる
```

> **辞書は少なくとも1つのキーと値のペアが必要です**：`{}` は空辞書ではありません——それは空ブロック（値 `Void`、[§2.9](#_2-9-块表达式)参照）。空辞書は構築子 `dict.new()` を使用してください：
>
> ```yaoxiang
> empty = dict.new()                  // ✅ 空辞書
> d = { "a": 1 }                       // ✅ 辞書リテラル
> wrong = {}                           // ❌ これは辞書ではなく空ブロック（Void）
> ```
>
> **判定基準は内容**：`Dict` 文法では少なくとも1つの `String ':' Expr` が必要、`{}` には内容がなく判断材料がないため、ブロック構造のゼロ形態を採用。非空形態は内容で自己記述（`{ "k": v }` はキーと値のペアを持つ → 辞書）——これは `f = { 5 }` が関数ではなく `Int` 値であるのと同じ原理：**型は内容で決まる**。

> Set にはリテラル文法もランタイム表現もありません——集合型は計画中で、需要が発生したら Dict パターンに従って補完（std.set + HeapValue::Set）。List/Dict リテラルの着地点はコンテキスト型注釈で決定：裸のリテラルと `List(T)` 注釈は可変長リストに落ち、`Array(T, N)` 注釈はリテラルに直接将作用して固定長配列に落ちる。暗黙の List→Array 変換は禁止です。
>
> Array リテラルのセマンティクス：
>
> - 要素数は N と等しくなければならず、異なる場合はコンパイル時 E1002；空リテラルと非ゼロ N も同様に拒否
> - 各要素の型は T と互換性がなければならず、適合しない場合はコンパイル時 E1002
> - N の文法形態：整数リテラル（負数も可）または定数名のみ；複合式（例：`2+1`）はパース時に拒否
> - N がシンボル定数（関数の const パラメータ、例：`Array(Int, n)`）の場合、要素数チェックは精製型段階まで延期
> - v1 ネスト配列リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否、逐層明示的構築が必要；再帰的な着地点は将来のバージョンで検討

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **動作の厳格化（移行記録）**：反復変数の文法自体は常に `'for' Identifier 'in'` ですが、旧実装では pattern が完全な Pratt 解析を通じて、`'in'` が中置演算子として登録された後、`x` は `in items` を membership 式として飲み込んでいました。修正後、非識別子 pattern は直接解析に失敗し、旧実装のように `_` にフォールバックして（静かにエラーを飲み込む）ことはなくなりました。影響範囲：以前解析可能だった `[x for (a, b) in pairs]` のような記述は今はエラーになります——この形態は明確に定義された動作を持っておらず（変数は常に `_`）、厳格化は正しく、セマンティクスの移行コストはありません。

#### 1.6.6 メンバーシップ検査

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子で、`Bool` を返します——一致は `true`、不一致は `false`、エラーは発生しません。セマンティクスの区分：`[]` は存在をアサートして値を取得（失敗はエラー）、`in` は存在するかを質問（不一致は正常な `false`）。右オペランドの対応：List / Array / Dict(キーセット) / Tuple / String(部分文字列) / Range(区間)。`in` は第一級のホア述語であり、精製型段階でコンパイル時証明可能な命題の基盤となります。（Set は右オペランドリストから除外——Set にはランタイム表現がない、§1.6.4 参照）

### 1.7 コメント

```
// 単一行コメント

/* 複数行コメント
   複数行にまたがることもできます */
```

### 1.8 インデント規則

コードは4スペースのインデントを使用する必要があります。Tab 文字の使用は禁止です。これは強制的な構文規則です。

## 第2章：構文規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                         | 結合性 |
| -------- | ------------------------------ | ------ |
| 1        | `()` `[]` `.` `?`              | 左から右 |
| 2        | `as`                           | 左から右 |
| 3        | 単項前置 `!` `-` `+`           | 右から左 |
| 4        | `*` `/` `%`                    | 左から右 |
| 5        | `+` `-`                        | 左から右 |
| 6        | `..`                           | 左から右 |
| 7        | `<<` `>>`                      | 左から右 |
| 8        | `&` `\|` `^`                   | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=`    | 左から右 |
| 10       | `and` `or`                     | 左から右 |
| 11       | `if...else`                    | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`        | 右から左 |

> **単項前置演算子**（`!` `-` `+`）の緊縛力：呼び出しとメンバアクセスよりも低く、すべての二項演算子よりも高い。したがって `!a == b` ≡ `(!a) == b`（Zig 式のセマンティクス）；`!` は純粋な単項演算子であり、短絡制御流に関与せず、`and`/`or` キーワード（短絡）とは直交（RFC-010 権威定義）。

> **Range の緊縛力**：`..` の緊縛力は (6, 7)——左は 6 で加算（7）より低く、右は 7 で同レベルの `..` を飲み込まない。変更前後の比較：
>
> | 式           | 変更前（レベル 1、右結合）                                               | 変更後 ((6,7)、左結合）                          |
> | ------------ | ------------------------------------------------------------------------ | ------------------------------------------------ |
> | `x in 1..10` | `x in 1..10`（`in` の右オペランドはレベル 4、`..` はレベル 1 で飲み込めず、実際にはパース不可） | `x in (1..10)`——区間全体が `in` の右オペランド |
> | `0..n+2`     | `(0..n)+2`（右結合の罠：上界が食べられる、`for` ループは直接 E3004）    | `0..(n+2)`——上界は算術式                       |
> | `a == b..c`  | `a == (b..c)`（`..` のレベル 1 < `==` のレベル 3で自然に全体）           | `a == (b..c)`——**セマンティクスは不変**、`..` は比較レベルより高い |
> | `1..2*3`     | `(1..2)*3`                                                               | `1..(2*3)`——上界は算術式                       |
> | `a..b..c`    | `a..(b..c)`（右結合チェーン、無意味な Range のネスト）                   | `(a..b)..c`——**step 形態**（`c` はステップ値） |
>
> 净効果：複合上界 `for i in 0..n+2` は「解析成功だが E3004」から「直接使用可能」に；`x in 1..10` は「解析不可」から「区間検査」に；`a..b..c` は「無意味なネスト」から「step 成分」に。レベル 6 は `+`（レベル 5）と `<<`（レベル 7）の間に位置し、数学的慣例：区間は緊縛力の高い構造であり、上界は当然ながら完全な算術式です。

### 2.3 関数呼び出し

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

名前付き実引数は `name = value` を使用（RFC-010 §関数定義、RFC-011 §構築形式）。位置実引数は名前付き実引数の前に配置する必要があります；順序指定パラメータは名前付き実引数内で自由に排列できます：

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // 位置式
add(a = 3, b = 5)  // 名前式
add(b = 5, a = 3)  // 順序は任意
add(3, b = 5)      // 混在、位置が前
```

名前付き実引数のスペルミスは **E1014**、同一パラメータが位置と名前で同時に指定されると **E1015**、個数が一致しないと **E1010**（RFC-013）。

### 2.4 メンバーアクセス

```
MemberAccess::= Expr '.' Identifier
```

### 2.5 インデックスアクセス

```
IndexAccess ::= Expr '[' Expr ']'
```

> **三層の意味論（RFC-011b）**：`a[i]` は `a` の型に応じて分流——① 組み込みコンテナ（List/Vec/Array/Dict/Tuple）はネイティブインデックス命令（高速パス）；② `Index` インターフェースを実装したユーザ型は対応する `index` メソッドにディスパッチ（型体内 `Index(Grid, Int, Float)` インスタンス化 + `Grid.index` メソッド）；③ RFC-004 の `f[0]` 位置束縛は束縛宣言にのみ存在し、本文法を通らない。多次元インデックス `a[0, 1]` のキーはタプルとしてパックされる。`Index` を実装していない他の型は型層で拒否される。

### 2.6 型キャスト

```

### 2.7 条件式

```

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文終端規則**：Stmt 間の区切りと改行の動作（`;` 明示的区切り、改行終端、続行例外、行頭の `(`/`[` はマージしない）は [RFC-038](../../design/rfc/accepted/038-statement-termination.md) で定義されます。

#### 2.9.1 `{` の3つの形態

`{` が式位置にある場合、的解释は正確に三つあり、**内容**で一度に判定されます：

| 形態             | 記法                 | 型           | 例                 |
| ---------------- | -------------------- | ------------ | ------------------ |
| **空ブロック**   | `{}`                 | `Void`       | `x: Void = {}`     |
| **辞書リテラル**  | `{ "k": v, ... }`    | `Dict(K, V)` | `d = { "a": 1 }`   |
| **ブロック**     | `{ Stmt* Expr? }`    | 末尾式の型    | `y = { 1 + 1 }`    |

**判定順序**：

1. `{}`（内容なし）→ **空ブロック**、値 `Void`
2. 最初の要素が `String ':' Expr` キーと値のペア → **辞書リテラル**
3. その他 → **ブロック**、値は末尾式で与えられる

> **なぜ `{}` は空辞書ではないのか**：空辞書の「空」は自己記述できません（`Dict(K, V)` の場合も空ブロックの場合もある）。辞書の文法 [§1.6.4](#_1-6-4-集合) では少なくとも1つのキーと値のペアが必要です。判断材料がない場合はブロック構造のゼロ形態を採用：`unsafe {}` / `spawn {}` と同じであり、特殊事例を導入しません。空辞書は `dict.new()` を使用します。
>
> **なぜ関数には注釈が必要なのか**：`f = { stmt }` は**値**（末尾式の型）であり、関数ではありません。関数を定義するには Fn 注釈を明示：`f: () -> Int = { 5 }`。これは辞書と同じ原則：**型は内容で決まり**、注釈の存在有無では決まらない。（この規則は [RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md) 付録 D を参照。）

**統一的意味論**：すべての `{}` ブロックの値は**末尾式**によって与えられ、`return` は `Never` 型の非局所的脱出です。

| ブロック型   | 値の出口  | 空ブロック `{}` |
| ------------ | --------- | --------------- |
| 通常 `{}`    | 末尾式    | `Void`          |
| `unsafe {}`  | 末尾式    | `Void`          |
| `spawn {}`   | 末尾式    | `Void`          |

**基本原則**（詳細：[RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md)）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**の場合、ブロック値は `Void`；`Void` が欲しい場合は明示的に `Void` と書く
- **`return` は最も近い関数境界を脱出**（すべてのブロックを貫通、「ブロックに戻る」ことはない）、型 `Never`；`Never <: T` は任意の型に対して成立（爆発原理）、したがって `return` は任意の戻り型の位置に表示可能
- 式形式 `= expr` は直接値を与える

```yaoxiang
// 通常 {} ブロック：末尾式で値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式で型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式で結果を与える
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // ブロックの値
}

// return：ブロックを貫通、関数を脱出
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if と関数本体を貫通、関数を脱出
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数かブロック値か？

`name = { ... }` は関数の定義（RFC-007「引数なし最简单的形」）の場合とブロック値束縛の場合があります。**注釈優先、デフォルトは関数**で裁定（RFC-010a 付録D）：

| 情形               | 結果     | 例                                    |
| ------------------ | -------- | ------------------------------------- |
| 値が Lambda（`=>`）| 関数     | `f = () => 5` → `f()` = 5            |
| 注釈が関数型        | 関数     | `f: () -> Int = { 5 }` → `f()` = 5   |
| 注釈が関数型でない  | **ブロック値** | `x: Int = { 5 }` → `x` = 5        |
| 注釈なし            | 関数     | `f = { 5 }` → `f()` = 5              |

**注釈即型**：`x: Int = ...` が `x` を `Int` と宣言するなら、`{ ... }` は `Int` として評価される；`f: () -> Int = ...` が `f` を関数と宣言するなら、`{ ... }` は関数本体である。

`{ ... }` をその場で評価したい場合は、**対象型を書くだけ**（新しい構文は不要）：

```yaoxiang
// ブロック値：その場で評価
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：注釈なしデフォルト
f = { 5 }        // f() = 5
```

#### ネスト関数型：カリー化か関数返しか？

`->` の右側のネスト関数型には**括弧**で区別される2つの読み方があります（RFC-004）：

| 書き方                           | 意味         | 呼び出し        |
| -------------------------------- | ------------ | --------------- |
| `(a: Int) -> (b: Int) -> Int`    | **カリー化** | `f(1)(2)`       |
| `(a: Int) -> ((b: Int) -> Int)`  | **関数返し** | `g(1)` で関数取得 |

根拠：**注釈即型**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int` を宣言しているため、`g(1)` は**その関数そのもの**でなければならず、「次のパラメータ」ではありません。

```yaoxiang
// カリー化：2段階パラメータを逐層与える
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数返し：外側1段階パラメータ、返されたものが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返された関数は変数に格納・渡せる
```

括弧なしのネスト `Fn` はすべてカリー化（含める RFC-011 の型パラメータ形式）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型チェック**：括弧が戻り型を宣言しており、body はその型を生成する必要があります。`f: () -> (() -> Int) = { 7 }` はエラー——期待 `() -> Int`、実際は `Int`（E1002）。

### 2.10 Lambda 式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子で、優先順位は `.` と同レベル。`Result(T, E)` 型に対して：

- `Ok(v)` の場合、値 `v` を抽出して続行
- `Err(e)` の場合、錯誤を上方向に伝播（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時値を展開、失敗時上方向に伝播
    transform(validated)
}
```

### 2.12 Range 式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は Range 値を作成します（Range は第一級値であり、構文糖ではありません）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値：束縛、传递、成员判断 가능
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step 形態（第三成分、デフォルト 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **step のセマンティクス**：`a..b..c` の `c` はステップ値です。`c = 0` リテラルはコンパイル時に拒否；動的な `c` はランタイムでゼロチェック（E6001 系列；錯誤システムが実装されたら Result に昇格）。`c < 0` は有効で、区間の方向は符号に応じて反転（`10..0..(-2)` は递减）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref` は共有所有を作成します。コンパイラは自動的に Rc（単一タスク）または Arc（跨タスク）を選択し、ユーザーは実装詳細を気にする必要はありません。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // 跨タスク：コンパイラは自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型和裸ポインタの操作を定義するために使用されます。`return` を使用して型定義を上位スコープに戻します。

**セマンティクス**：

- `unsafe {}` では型と裸ポインタを操作できる
- 返された型は `unsafe {}` の外で使用可能
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロックで不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 裸ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外で使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックはスコープを作成します
- 内側スコープは外側スコープの変数にアクセスできます
- 外側スコープは内側スコープの変数にアクセスできません
- 変数宣言は「代入優先」原則に従います

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で可視
}
// x はこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数外では不可視
```

**変数の宣言とシャドウイング**：

- `x = value`：スコープチェーンを外向きに検索、発見すれば代入、発見できなければ新規宣言
- `mut x = value`：明示的な新規可変宣言、外側と同名を禁止
- 同一スコープ内で任意の名前を宣言できる回数は1回のみ

> **詳細定義**：スコープの完全な規則、変数宣言とシャドウイングのメカニズムについては [モジュールシステム規範](./modules.md#第四章作用域) を参照してください。

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**意味論**：`return` は**非局所的脱出**であり、最も近い**関数境界**を脱出（if / while / for / match / 裸ブロック / `spawn` / `unsafe` を含むすべてのブロックを貫通）、値を呼び出し元に渡します。**「ブロックに戻らない」** 点に注意してください。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'` に対して成立（爆発原理、[型システム §2.2](./type-system.md) 参照）、したがって `return` は任意の戻り型の位置に表示可能であり、追加の規則制約は不要です。

**ブロック評価との関係**：ブロックの値は常に**末尾式**です（§2.9 参照）。`{ return n }` をブロックとして、その値は `n`、型は `Never`；同時に `return` の効果は関数を脱出すること。**这两件事同時成立**、爆発原理により共存可能。

`return` と末尾式の共同作用により「早期リターン」が成立します，`return` に「関数特有の」追加規則は不要——[RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md) を参照してください。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通、関数を脱出（型 Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**意味論**： 포함된 가장 안쪽의 `while`/`for` 루프를 즉시 종료하고、制御流をそのループ体以降に移动させます。

- **最も内側のみを脱出**：`break` は常に含む最も内側のループに作用します。ネストループで複数層を脱出する必要がある場合、内側ループを関数に抽出し `return` を使用するか、フラグを使用してください（break/continue にはラベルがない；将来的にループラベルを導入する場合、ループ宣言側の構文で RFC プロセスに従い、証明パイプラインの複数出口設計と並行して裁定されます）
- **ループ体内のみ許可**：`break` は `while`/`for` ループ体内（含めて体内でネストされたブロック/if/match）でのみ表示可能であり、ループ外で表示するとコンパイルエラー（E1102 `'break' outside of a loop`）
- **終了性証明に影響しない**：`break` は終了性議論に関与しません——測度を提供せず、測度の递减ステップ，也不能构成测度的递减ステップ；ループの終了義務と `break` には関係がなく、精製型によってトリガーされます（[type-system §8.4](./type-system.md#84-terminates终止测度谓词) 参照）。
- **借用セマンティクス**：break の制御流エッジは RFC-009a 逆方向 BFS 活性分析の構造的切断に関与します（脱出する反復はバックエッジ活性導出に関与しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御流がループ以降に移動、i == 3
    }
}

// ネストループ：break は内側のみ脱出
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側ループのみを終了
    }
    j = j + 1                  // 外側ループの各反復でここに到達
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**意味論**：現在の反復の残りの文をスキップし、最も内側の包含ループの次の反復に直接進入——`while` は条件の再判定に戻り、`for` は次の要素を取得します。

- **最も内側にのみ作用**：break と同様に、ラベルなし
- **ループ体内のみ許可**：ループ外で表示するとコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 下の累算をスキップ、n == 3 は加算されない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

### 3.9 for 文

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 意味論：各反復は新しい値の束縛

YaoXiang の for ループの意味論は従来の言語とは異なります：**各反復は新しい値の束縛であり、同じ変数を変更するものではありません**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行プロセス**：

| 反復  | ループ変数の動作                                         |
| ----- | -------------------------------------------------------- |
| 第1回 | 新規束縛 `i = 1` を作成、ループ体実行、1 を出力         |
| 第2回 | 新規束縛 `i = 2` を作成（以前の束縛は破棄済み）、ループ体実行、2 を出力 |
| 第3回 | 新規束縛 `i = 3` を作成、ループ体実行、3 を出力         |
| 第4回 | 新規束縛 `i = 4` を作成、ループ体実行、4 を出力         |
| 終了  | ループ体終了、束縛破棄                                   |

**要点**：各反復終了後、その反復で作成された束縛は破棄されます。次の反復は新しい束縛であり、前回の反復の束縛とは無関係です。

#### 3.9.2 for と for mut の違い

| 構文                | ループ変数の可変性 | 説明                 |
| ------------------- | ------------------ | -------------------- |
| `for i in 1..5`     | 不変               | ループ体内で束縛を変更不可 |
| `for mut i in 1..5` | 可変               | ループ体内で束縛を変更可能 |

```yaoxiang
// 有効：各反復が新しい束縛を作成するため、変更は不要
for i in 1..5 {
    print(i)  // i の値を読み取る
}

// 錯誤：束縛は不変、変更不可
for i in 1..5 {
    i = i + 1  // 錯誤：不変束縛は変更不可
}

// 有効：for mut を使用すれば束縛の変更を許可
for mut i in 1..5 {
    i = i + 1  // 許可
}
```

#### 3.9.3 シャドウイングチェック

YaoXiang は変数のシャドウイングを禁止しています。for ループ変数は外側スコープの変数と同じ名前にできません：

```yaoxiang
// 錯誤：i はすでに外部で宣言済み
i = 10
for i in 1..5 {
    print(i)
}

// 正確：異なる変数名を使用
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用されます。[4.3 シャドウイング規則](./modules.md#43-遮蔽规则) を参照してください。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数の意味論               |
| -------- | ------------------------------------ |
| YaoXiang | 各反復が新しい束縛を作成             |
| Rust     | 同じ変数を変更（mut が必要）         |
| Python   | 同じ変数を変更（mut 不要）           |
| C/C++    | 同じ変数を変更（ポインタまたは参照が必要） |

**設計理由**：YaoXiang が束縛セマンティクスを選択した理由は：

1. **より自然なセマンティクス** 自然言語では「集合の各要素 x について」は、各 x が独立した存在であることを意味します。YaoXiang の `for i in 1..5` は「1 から 5 の各 i について」と読み、各反復の i はまったく新しい束縛であり、人間の直感的な理解と一致します。

2. **偶発的な変更を回避** デフォルトで不変の束縛セマンティクスは、ループ体内でループ変数を偶発的に変更できないことを意味します。複雑なループ体の中で誤って `i = ...` と書いて追跡困難なバグが発生する心配がありません。

3. **高性能ソリューションが簡単に利用可能** 反復間で変数を再利用する必要がある場合（例：アキュムレータ、キャッシュ）、`for mut` を使用すれば可変束縛モードに切り替えることができます。これは暗黙の共有状態よりも明確です——意図は構文で明示的に表現され、ランタイム動作に隠されません。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：并发領域を明示的に宣言し、ブロック内式は并发に実行されます。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側変数をキャプチャ**（RFC-024 §2.3、値キャプチャセマンティクス）：

- ブロック体が外側変数を参照 = **Move 値キャプチャ**：値が spawn 作成点でスナップショットされ、クロージャ環境にコピーされ、ブロック体は env を通じて読み取り（LoadUpvalue）
- **プリミティブ**（Int/Float/Bool/Char）は値をコピーし、外側変数には影響しない
- **ハンドラ型**（Struct/String/List など）のスナップショット = ハンドラコピー、基盤オブジェクトを共有；Embedded ランタイム（デフォルト）は同一スレッド同一ヒープ、ハンドラが有効
- 複数タスク間での共有には明示的な `ref` が必要（§2.13、コンパイラが自動的に Rc/Arc を選択）
- ブロック内の `return` が参照する外側変数も同様にキャプチャ

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 の値キャプチャ、result == 6
}
```

### 3.11 プログラム入口とトップレベル文

ソースファイルはコンパイラにとって2つの役割があり、**`yaoxiang.toml` の存在是否で决定**されます：

| 役割       | 判定                           | プログラムの主体                                    |
| ---------- | ------------------------------ | ------------------------------------------------- |
| **Script** | 単一ファイル直接実行、`yaoxiang.toml` なし | **トップレベル文**（記述順に実行）；`main` は通常の束縛 |
| **Bin**    | `yaoxiang.toml` 存在           | **`main` 関数**；トップレベルに実行可能文を不可    |

#### Script：トップレベル文がプログラム

manifest がない場合、ファイルは「スクリプト」であり、**トップレベル文は記述順に実行**されます：

```yaoxiang
use std.io
io.println("hello")          // 直接実行
x: Int = { 42 }              // トップレベル束縛：ランタイム初期化
io.println(x)                // 42
```

このモードでは `main` は**特殊ではありません**——それは単なる束縛です。`main` を実行するには、明示的に呼び出す必要があります：

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← この行を書く必要がある
```

> **なぜ `main` を自動呼び出ししないのか？** トップレベル文はすでにプログラムの本体です。もし `main` を暗黙的に呼び出すと、`main()` を明示的に書いたスクリプトが2回実行されます。2つの規則は共存できません。したがって Script モードでは「トップレベル文」という1つの実行エントリのみが存在します。

#### Bin：`main` がエントリポイント

manifest がある場合、ファイルは「実行可能ターゲット」であり，此刻：

- `main` を定義する必要があり、それは関数でなければならない（署名がゼロパラメータ呼び出し可能であること）
- トップレベルに実行可能文を許可しない——プログラムの本体は `main` である

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

`main` がない、または `main` が関数でない場合はコンパイルエラー（前者の場合：`main` がないときすべての関数に到达不能；後者の場合：値束縛は呼び出されない）。

> **ライブラリファイル**：他のファイルから `use` されるファイル、または `[lib].path` / `[exports]` が指すファイルは `main` を要求しない——プログラムエントリポイントではない。

#### トップレベル束縛の初期化

トップレベル束縛の初期化値は**ランタイムで評価**され、コンパイル時定数である必要はありません：

```yaoxiang
answer: Int = { 42 }              // ブロック値
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // 関数呼び出し
```

初期化は**依存順序**で実行され、記述順序とは無関係です：

```yaoxiang
derived: Int = base * 3           // 後で宣言された base を参照
base: Int = 7                     // 先に初期化（トポロジカルソート）
```

循環依存はコンパイルエラーです（環上の名前が列表されます）：

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // エラー：a → b → a
```

> **設計根拠**：RFC-029f（ファイル役割モデル）、RFC-010a 付録D（ブロック束縛裁定）。
