# 文法仕様

本文件は YaoXiang プログラミング言語の文法仕様を定義する。字句構造、文法規則、演算子の優先順位を含む。

---

## 第一章：字句構造

### 1.1 ソースファイル

YaoXiang ソースファイルは UTF-8 エンコーディングを使用しなければならない。ソースファイルの拡張子は通常
`.yx` である。

### 1.2 字句単位の分類

| カテゴリー | 説明                             | 例                        |
| ---------- | -------------------------------- | ------------------------- |
| 識別子     | 文字またはアンダースコアで始まる | `x`, `_private`, `my_var` |
| キーワード | 言語で定義された予約語           | `Type`, `pub`, `use`      |
| リテラル   | 固定値                           | `42`, `"hello"`, `true`   |
| 演算子     | 演算記号                         | `+`, `-`, `*`, `/`        |
| 区切り記号 | 文法上の区切り                   | `(`, `)`, `{`, `}`, `,`   |

### 1.3 キーワード

YaoXiang は極めて少量のキーワードを定義する：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

これらのキーワードはあらゆる文脈で特別な意味を持ち、識別子として使用することはできない。

### 1.4 予約語

YaoXiang の「予約語」は 3 層に分かれており、それぞれパーサー（parser）と型チェッカー（type
checker）が異なる段階で識別する。

#### 1.4.1 リテラル予約語

パーサーが独立したトークンとして持つリテラル識別子は、通常の識別子として使用できない：

| 識別子  | 所属型 | 説明                                                                                        |
| ------- | ------ | ------------------------------------------------------------------------------------------- |
| `Type`  | —      | メタ型キーワード                                                                            |
| `true`  | Bool   | ブール真値                                                                                  |
| `false` | Bool   | ブール偽値                                                                                  |
| `void`  | Void   | Void リテラル（Unit 値）。小文字 `void` は値リテラル；大文字 `Void` は型名（§1.4.3 参照）。 |

#### 1.4.2 コンストラクタ式

以下のコンストラクタはパターンマッチと式の文脈でパーサーにより認識される：

| コンストラクタ | 所属型 | 説明                      |
| -------------- | ------ | ------------------------- |
| `some(T)`      | Option | Option 値バリアントの構築 |
| `ok(T)`        | Result | Result 成功バリアント     |
| `err(E)`       | Result | Result エラーバリアント   |

#### 1.4.3 組み込み型名

以下の型名は型チェッカーにより事前登録されており、import なしでも型の位置で使用できる。パーサーはこれらを通常の識別子として扱う——**予約語ではないため、ローカルバインディングで shadow 可能（推奨されない）**。

| 型名     | 論理的対応   | 説明                                                                                                                                       |
| -------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `Void`   | ⊤（真/Unit） | 零フィールドの積型で、唯一の居住者（`void` リテラル、§1.4.1 参照）を持つ。                                                                 |
| `Never`  | ⊥（偽/空型） | 零バリアントの和型で、居住者を持たない。`Never` 型の値を生成する式は存在しない。`Never <: T` はすべての `T` に対して成立する（爆発原理）。 |
| `Int`    | —            | 符号付き整数                                                                                                                               |
| `Float`  | —            | 浮動小数点数                                                                                                                               |
| `Bool`   | —            | ブール値：`true` / `false`                                                                                                                 |
| `Char`   | —            | Unicode 文字                                                                                                                               |
| `String` | —            | 文字列                                                                                                                                     |

### 1.5 識別子

識別子は文字またはアンダースコアで始まり、後続の文字は文字、数字、またはアンダースコアが使用できる。識別子は大文字小文字を区別する。

特殊識別子：

- `_` はプレースホルダとして使われ、値を無視することを表す
- アンダースコアで始まる識別子はプライベートメンバーを表す

### 1.6 リテラル

#### 1.6.1 整数

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 浮動小数点数

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 文字列

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 コレクション

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // ターゲット型注釈が Array(T, N) の場合、リテラルは固定長配列に落ちる
```

> Set にはリテラル文法はなく、実行時表現もない——集合型は計画中であり、ニーズが発生した時点で Dict のパターンに従って補完する（std.set +
> HeapValue::Set）。List/Dict リテラルの落点は文脈型注釈によって決定される：素のリテラルと `List(T)`
> 注釈は可成長リストに落ちる；`Array(T, N)`
> 注釈が直接リテラルに作用する場合は固定長配列に落ちる。暗黙の List→Array 変換は禁止。
>
> Array リテラルの意味論：
>
> - 要素数は N と等しくなければならない。等しくない場合はコンパイル時 E1002；空リテラルに非零 N を組み合わせる場合も拒否される
> - 各要素の型は T と互換でなければならない。互換でない場合はコンパイル時 E1002
> - N の文法形式：整数リテラル（負数可）または定数名のみ；複合式（例：`2+1`）は解析時に拒否される
> - N がシンボリック定数（関数の const パラメータ、例：`Array(Int, n)`）の場合、要素数の検査は型精化フェーズまで延期される
> - v1 のネストした Array リテラル（`Array(Array(Int,2),2) = [[1,2],[3,4]]`）はコンパイル時に拒否され、階層ごとに明示的に構築する必要がある；再帰的な落点は以降のバージョンに持ち越す

#### 1.6.5 リスト内包表記

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **挙動の厳格化（移行記録）**：反復変数の文法は元から `'for' Identifier 'in'`
> だが、旧実装では pattern が完全な pratt 解析を行っていた——`'in'` が中置演算子として登録された後、
> `x` は `in items`
> を membership 式として取り込んでしまう。修正後は非識別子 pattern の解析が直接失敗するようになり、旧実装のように
> `_` にフォールバックする（エラーを静かに飲み込む）ことはなくなった。影響範囲：以前
> `[x for (a, b) in pairs]`
> のような書き方が解析できていたが、現在ではエラーになる——この形式は元々定義された動作を持たず（変数は常に
> `_`）、厳格化する方向は正しく、意味論的な移行コストはない。

#### 1.6.6 メンバーシップ検査

```
Membership  ::= Expr 'in' Expr
```

> `in` は二項関係演算子で、`Bool` を返す——ヒットすれば `true`、ヒットしなければ `false`
> でエラーは発生しない。意味論の分割：`[]` は存在をアサートして値を取り出す（失敗でエラー）、 `in`
> は存在を問い合わせる（未ヒットは通常の `false`）。右被演算子のカバー：List / Array /
> Dict(キー集合) / Tuple / String(部分文字列) / Range(区間)。`in`
> は一階ホーア述語であり、型精化フェーズでコンパイル時に証明可能な命題の基底となる。（Set は右被演算子リストから除外——Set には実行時表現がない、§1.6.4 参照）

### 1.7 コメント

```
// 単一行コメント

/* 複数行コメント
   複数行に渡ることができる */
```

### 1.8 インデント規則

コードは 4 スペースのインデントを使用しなければならず、Tab 文字の使用は禁止されている。これは強制的な構文規則である。

## 第二章：構文規則

### 2.1 式の分類

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 演算子の優先順位

| 優先順位 | 演算子                      | 結合性   |
| -------- | --------------------------- | -------- |
| 1        | `()` `[]` `.` `?`           | 左から右 |
| 2        | `as`                        | 左から右 |
| 3        | 単項前置 `!` `-` `+`        | 右から左 |
| 4        | `*` `/` `%`                 | 左から右 |
| 5        | `+` `-`                     | 左から右 |
| 6        | `..`                        | 左から右 |
| 7        | `<<` `>>`                   | 左から右 |
| 8        | `&` `\|` `^`                | 左から右 |
| 9        | `==` `!=` `<` `>` `<=` `>=` | 左から右 |
| 10       | `and` `or`                  | 左から右 |
| 11       | `if...else`                 | 右から左 |
| 12       | `=` `+=` `-=` `*=` `/=`     | 右から左 |

> **単項前置演算子**（`!` `-`
> `+`）は強く結合する：呼び出しとメンバーアクセスより低く、すべての二項演算子より高い。したがって
> `!a == b` ≡ `(!a) == b`（Zig 式意味論）；`!`
> は純粋な単項演算で、短絡制御フローには参加せず、`and`/`or`
> キーワード（短絡）とは直交する（RFC-010 が権威的な定義）。

> **Range の結合強度**：`..` の結合強度は (6,
> 7)——左 6 は加算（7）より低く、右 7 は加算を取り込むが同レベルの `..`
> は取り込まない。変更前後の対比：
>
> | 式           | 変更前（レベル 1、右結合）                                                                  | 変更後（(6,7)、左結合）                                        |
> | ------------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10`（`in` の右被演算子レベル 4、`..` のレベル 1 では取り込めず、実際には解析不可） | `x in (1..10)`——区間全体が `in` の右被演算子に                 |
> | `0..n+2`     | `(0..n)+2`（右結合の罠：上界が食べられ、`for` ループで直接 E3004）                          | `0..(n+2)`——上界は算術式                                       |
> | `a == b..c`  | `a == (b..c)`（`..` のレベル 1 < `==` のレベル 3、必然的に全体）                            | `a == (b..c)`——**意味論は不変**、`..` は比較レベルより依然高い |
> | `1..2*3`     | `(1..2)*3`                                                                                  | `1..(2*3)`——上界は算術式                                       |
> | `a..b..c`    | `a..(b..c)`（右結合の連鎖、無意味な Range のネスト）                                        | `(a..b)..c`——**step 形式**（`c` がステップ）                   |
>
> 純効果：複合上界 `for i in 0..n+2` は「解析成功だが E3004」から「直接使用可能」に； `x in 1..10`
> は「解析不可」から「区間チェック」に；`a..b..c`
> は「無意味なネスト」から「step 成分」に。レベル 6 は `+`（レベル 5）と
> `<<`（レベル 7）の間に位置し、数学的慣習に従う：区間は強く結合する構造であり、上界は自然な完全な算術式になる。

### 2.9 ブロック式

```
Block       ::= '{' Stmt* Expr? '}'
```

> **文の終端規則**：Stmt 間の区切りと改行の挙動（`;`
> による明示的な区切り、改行による終端、行継続の例外、行頭の `(`/`[` は決して結合しない）は
> [RFC-038](../design/rfc/draft/038-statement-termination.md) で定義される。

**統一意味論**：すべての `{}` ブロックの値は**末尾式**によって与えられ、`return` は `Never`
型の非局所的退出である。

| ブロック型  | 値の出口 | 空ブロック `{}` |
| ----------- | -------- | --------------- |
| 通常の `{}` | 末尾式   | `Void`          |
| `unsafe {}` | 末尾式   | `Void`          |
| `spawn {}`  | 末尾式   | `Void`          |

**核心原則**（詳細は [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md) 参照）：

- **ブロックの値 = 末尾式**（最後の式）、唯一の出口、例外なし
- 末尾が**代入文**の場合、ブロックの値は `Void`；`Void` を望むなら明示的に `Void` と書く
- **`return`
  は最も近い関数境界を退出する**（すべてのブロックを貫通する、ブロックに「返す」のではない）、型は
  `Never`；`Never <: T`

> は任意の型に対して成立する（爆発原理）ため、任意の戻り型位置に現れ得る

- 式形式 `= expr` は直接値を与える

```yaoxiang
// 通常の {} ブロック：末尾式が値を与える
result = {
    x = compute()
    x                // ブロックの値
}

// unsafe {} ブロック：末尾式が型定義を与える
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // ブロックの値
}

// spawn {} ブロック：末尾式が結果を与える
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // ブロックの値
}

// return：ブロックを貫通し、関数を退出する
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // if と関数本体を貫通し、関数を退出する
    }
    n * 2            // 末尾式
}
```

#### `name = { ... }` は関数か、ブロック値か？

`name = { ... }`
は関数定義（RFC-007「空パラメータ最簡」）にも、ブロック値バインディングにもなり得る。**注釈優先、デフォルトは関数**で裁定する（RFC-010a 付録D）：

| 状況                | 結果           | 例                                 |
| ------------------- | -------------- | ---------------------------------- |
| 値が Lambda（`=>`） | 関数           | `f = () => 5` → `f()` = 5          |
| 注釈が関数型        | 関数           | `f: () -> Int = { 5 }` → `f()` = 5 |
| 注釈が非関数型      | **ブロック値** | `x: Int = { 5 }` → `x` = 5         |
| 注釈なし            | 関数           | `f = { 5 }` → `f()` = 5            |

**注釈は即ち型**：`x: Int = ...` は `x` が `Int` であることを宣言するので、`{ ... }` は `Int`
に評価される； `f: () -> Int = ...` は `f` が関数であることを宣言するので、`{ ... }`
は関数本体である。

`{ ... }` をその場で評価したい場合、**ターゲット型を書けばよい**（新しい文法は不要）：

```yaoxiang
// ブロック値：即座に評価
x: Int = {
    y = 5
    y            // x = 5
}

// 関数：注釈なしではデフォルトで関数
f = { 5 }        // f() = 5
```

#### ネストした関数型：カリー化か、関数を返すか？

`->` の右側にあるネストした関数型には 2 通りの読み方があり、**括弧**で区別される（RFC-004）：

| 書き方                          | 意味           | 呼び出し            |
| ------------------------------- | -------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **カリー化**   | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **関数を返す** | `g(1)` で関数を得る |

根拠：**注釈は即ち型**。`g: (a: Int) -> ((b: Int) -> Int)` は `g(1) : (b: Int) -> Int`
を宣言するので、 `g(1)` はその関数で**なければならない**、つまり「次のパラメータ」ではなく。

```yaoxiang
// カリー化：パラメータを 2 段階で与える
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// 関数を返す：外側のパラメータ 1 つで、返されるのが関数
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // 返された関数は変数に保存したり、渡したりできる
```

括弧なしのネストした `Fn` はすべてカリー化（RFC-011 の型パラメータ形式を含む）：

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // カリー化
identity(5)      // → 5
```

**型検査**：括弧は戻り型を宣言するので、body はその型を生成しなければならない。
`f: () -> (() -> Int) = { 7 }` は誤り——期待される型は `() -> Int` だが、実際は `Int`
が得られる（E1002）。

### 2.10 ラムダ式

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 エラー伝播演算子

```
ErrorPropagate ::= Expr '?'
```

`?` 演算子は後置演算子で、優先順位は `.` と同レベルである。`Result(T, E)` 型に対して：

- `Ok(v)` の場合、値 `v` を抽出して実行を続ける
- `Err(e)` の場合、エラーを上位に伝播する（`return Err(e)`）

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // 成功時は値を抽出し、失敗時は上位に伝播
    transform(validated)
}
```

### 2.12 範囲式

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` は範囲値を作成する（Range は一階値であり、構文糖ではない）。

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range は値：バインド、受け渡し、メンバー判定
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// step 形式（第 3 成分、デフォルト 1）
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **step の意味論**：`a..b..c` の `c` はステップ長。`c = 0`
> のリテラルはコンパイル時に拒否される；動的な `c`
> の零検査は実行時に行われる（E6001 ファミリー；エラーシステムの実装後に Result に格上げ）。 `c < 0`
> は合法で、区間の方向は符号に応じて反転する（`10..0..(-2)` は降順）。

### 2.13 ref 式

```
RefExpr     ::= 'ref' Expr
```

`ref`
は共有保持を作成する。コンパイラが自動的に Rc（単一タスク）または Arc（タスク間）を選択し、ユーザーは実装の詳細を気にする必要はない。

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // タスク間：コンパイラが自動的に Arc を選択
```

### 2.14 unsafe 式

```
UnsafeExpr  ::= 'unsafe' Block
```

`unsafe` ブロックは不透明型の定義と生ポインタの操作に使用される。`return`
を使用して型定義を上位スコープに返す。

**意味論**：

- `unsafe {}` 内で型を定義し、生ポインタを操作できる
- 返された型は `unsafe {}` 外でも使用可能
- 型のフィールドアクセスには unsafe 権限が必要

```yaoxiang
// unsafe ブロック内で不透明型を定義
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // 生ポインタ
    }
    return SqliteDb
}

// SqliteDb は unsafe ブロック外でも使用可能
db = sqlite3_open("test.db")
```

### 2.15 スコープ

**基本規則**：

- 各 `{}` ブロックがスコープを作成する
- 内側スコープは外側スコープの変数にアクセスできる
- 外側スコープは内側スコープの変数にアクセスできない
- 変数宣言は「代入優先」原則に従う

```yaoxiang
// ブロックスコープ
{
    x = 10
    // x はこのスコープ内で可視
}
// x はこのスコープ外では不可視

// 関数スコープ
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result は関数外では不可視
```

**変数宣言とシャドウィング**：

- `x = value`：スコープチェーンを外側に沿って x を検索し、見つかれば代入、見つからなければ新規宣言
- `mut x = value`：明示的に新しい可変宣言を意味し、外側と同名は禁止
- 同じスコープ内で同じ名前は 1 回しか宣言できない

> **詳細定義**：スコープの完全な規則、変数宣言とシャドウィング機構の詳細については
> [モジュールシステム仕様](./modules.md#第四章作用域) を参照。

## 第三章：文

### 3.1 文の分類

```
Stmt        ::= LetStmt
              | ExprStmt
              | ReturnStmt
              | BreakStmt
              | ContinueStmt
              | IfStmt
              | MatchStmt
              | WhileStmt
              | ForStmt
              | SpawnStmt
```

### 3.2 変数宣言

```
LetStmt     ::= ('mut')? Identifier (':' TypeExpr)? '=' Expr
```

### 3.3 return 文

```
ReturnStmt  ::= 'return' Expr?
```

**意味論**：`return`
は**非局所的退出**であり、最も近い**関数境界**を退出する（すべてのブロック——`if` / `while` / `for` /
`match` / 裸ブロック / `spawn` / `unsafe`
を含む——を貫通する）、呼び出し側に値を渡す。**「ブロックに返す」のではない**。

**型**：`return e : Never`（`e : T`）。`Never <: T'` は任意の `T'` に対して成立する（爆発原理、
[型システム §2.2](./type-system.md) 参照）ため、`return`
は任意の戻り型位置に現れ得て、追加規則による制約は不要。

**ブロック評価との関係**：ブロックの値は常に**末尾式**である（§2.9 参照）。`{ return n }`
をブロックとすると、その値は `n`、型は `Never`；同時に `return`
の作用は関数を退出すること。**両方の事象が同時に成立し**、爆発原理によって共存する。

`return` と末尾式が組み合わさって「早期 return」を成立させ、関数を特化する `return`
の追加規則は不要となる——詳細は [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)
を参照。

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // if を貫通し、関数を退出する（型 Never）
    }
    n * factorial(n - 1)  // 末尾式 = ブロックの値
}
```

### 3.4 break 文

```
BreakStmt   ::= 'break'
```

**意味論**：最も内側の `while`/`for`
ループを直ちに終了し、制御フローをそのループ本体の後に移動する。

- **直近の 1 層のみ脱出**：`break`

> は常にそれを含む最も内側のループに作用する。ネストしたループで複数層を一度に脱出する必要がある場合は、内側ループを関数として抽出し
> `return`
> で返すか、フラグ変数を使用する（break/continue にはラベルがない；将来ループラベルを導入する場合は、ループ宣言側の文法に従って RFC 流程を踏み、証明パイプラインの多出口設計と共に裁定する）

- **ループ体内のみ**：`break` は `while`/`for`

> ループ体内（体内にネストしたブロック/if/match を含む）にのみ出現でき、ループ外に出現した場合はコンパイルエラー（E1102
> `'break' outside of a loop`）

- **停止性証明に影響しない**：`while`
  ループは依然として停止が証明可能でなければならない（decreases 計量）；`break`

> は停止性の論証に参加せず、`while true { break }` は受理されない

- **借用意味論**：break の制御フロー辺は RFC-009a の逆向き BFS 活性分析の構造的切断に参加する（脱出した反復は逆辺活性の導出に参加しない）

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // 制御フローはループの後に移動、i == 3
    }
}

// ネストしたループ：break は内側のみ終了
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // 内側ループのみ終了
    }
    j = j + 1                  // 各外側反復でここまで実行される
}
```

### 3.5 continue 文

```
ContinueStmt::= 'continue'
```

**意味論**：この反復の残りの文をスキップし、最も内側のループの次の反復に直接入る—— `while`
は条件の再評価に戻り、`for` は次の要素を取り出す。

- **直近の 1 層のみに作用**：`break` と同様、ラベルなし
- **ループ体内のみ**：ループ外に出現した場合はコンパイルエラー（E1102）

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // 以下の累算をスキップ、n == 3 はカウントされない
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

IfStmt      ::= 'if' Expr Block ('else' 'if' Expr Block)* ('else' Block)?

### 3.9 for 文

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 意味論：各反復は新しい値をバインドする

YaoXiang の for ループ意味論は伝統的な言語とは異なる：**各反復は新しい値をバインドし、同じ変数を変更するのではない**。

```yaoxiang
// 例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**実行過程**：

| 反復   | ループ変数の挙動                                                                                    |
| ------ | --------------------------------------------------------------------------------------------------- |
| 1 回目 | 新しいバインディング `i = 1` を作成し、ループ本体を実行、1 を表示                                   |
| 2 回目 | 新しいバインディング `i = 2` を作成し（以前のバインディングは破棄済み）、ループ本体を実行、2 を表示 |
| 3 回目 | 新しいバインディング `i = 3` を作成し、ループ本体を実行、3 を表示                                   |
| 4 回目 | 新しいバインディング `i = 4` を作成し、ループ本体を実行、4 を表示                                   |
| 終了   | ループ本体終了、バインディング破棄                                                                  |

**要点**：各反復が終了すると、その反復で作成されたバインディングは破棄される。次の反復は完全に新しいバインディングであり、前の反復のバインディングとは関係がない。

#### 3.9.2 for と for mut の違い

| 文法                | ループ変数の可変性 | 説明                                     |
| ------------------- | ------------------ | ---------------------------------------- |
| `for i in 1..5`     | 不変               | ループ体内でバインディングを変更できない |
| `for mut i in 1..5` | 可変               | ループ体内でバインディングを変更できる   |

```yaoxiang
// 合法：各反復で新しい値をバインド、変更は不要
for i in 1..5 {
    print(i)  // i の値を読み取る
}

// エラー：不変バインディング、変更不可
for i in 1..5 {
    i = i + 1  // エラー：不変バインディングを変更できない
}

// 合法：for mut を使うとバインディングの変更が許可される
for mut i in 1..5 {
    i = i + 1  // 変更が許可される
}
```

#### 3.9.3 シャドウィング検査

YaoXiang は変数のシャドウィングを禁止する。for ループ変数は外側スコープの変数と同名にできない：

```yaoxiang
// エラー：i は既に外側で宣言されている
i = 10
for i in 1..5 {
    print(i)
}

// 正しい：異なる変数名を使用
i = 10
for j in 1..5 {
    print(j)
}
```

この規則はすべてのコードブロックに適用される。詳細は
[4.3 シャドウィング規則](./modules.md#43-遮蔽规则) を参照。

#### 3.9.4 他の言語との比較

| 言語     | for ループ変数の意味論                     |
| -------- | ------------------------------------------ |
| YaoXiang | 各反復で新しい値をバインド                 |
| Rust     | 同じ変数を変更（mut が必要）               |
| Python   | 同じ変数を変更（mut 不要）                 |
| C/C++    | 同じ変数を変更（ポインタまたは参照が必要） |

**設計根拠**：YaoXiang がバインディング意味論を採用する理由：

1. **より自然な意味論に適合**
   自然言語では、「集合内の各要素 x について」は各 x が独立した個体であることを意味する。YaoXiang の

> `for i in 1..5`
> は「1 から 5 の中の各 i について」と読まれ、各反復の i は完全に新しいバインディングであり、人間の直感的理解と一致する。

2. **偶発的な変更を回避**

> デフォルトで不変なバインディング意味論は、ループ体内で偶発的にループ変数を変更できない。複雑なループ体内のどこかで誤って
> `i = ...` と書いてしまい、追跡困難なバグを引き起こす心配がない。

3. **高性能な解決策に手が届く**
   反復間で変数を再利用する必要がある場合（例：累算器、キャッシュ）、`for mut`

> を使用すれば可変バインディングモードに切り替えられる。これは暗黙的な共有状態より明確である——意図は構文で明示的に表現され、実行時の挙動に隠されることはない。

### 3.10 spawn 文

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn ブロック**：並行実行領域を明示的に宣言し、ブロック内の式が並行実行される。

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn ループ**：データ並列ループ。

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn ブロックは外側の変数を捕捉する**（RFC-024 §2.3、値捕捉意味論）：

- ブロック本体が外側変数を参照する =

> **値 Move 捕捉**：値は spawn 作成時点でクロージャ環境にスナップショットされ、ブロック本体は env 経由で読み取る（LoadUpvalue）

- **プリミティブ**（Int/Float/Bool/Char）は値をコピーし、外側変数は影響を受けない
- **ハンドル型**（Struct/String/List など）のスナップショット = ハンドル複製、基盤オブジェクトを共有；Embedded ランタイム（デフォルト）は同一スレッド同一ヒープで、ハンドルは有効
- 複数タスク間で共有するには明示的な `ref` が必要（§2.13、コンパイラが自動的に Rc/Arc を選択）
- ブロック内の `return` が参照する外側変数も同様に捕捉される

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 の値捕捉、result == 6
}
```
