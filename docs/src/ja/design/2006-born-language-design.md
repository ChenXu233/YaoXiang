# 2006年生まれの言語設計観

> Rustが孕育され始めた時、私はちょうど生を受けた。Rustが成熟した時、私は青年期を迎えていた。そしてこれからの十年間、まさに私たち世代のための言語を創造する時だ。

## 序論：世代間使命の継承

2006年は、Rustプログラミング言語が誕生した年であり、私がこの世に生を受けた年でもある。19年後、YaoXiang（爻象）の設計と実装を始めた時、私はこれが単なる時間の偶然ではなく、世代間使命の継承だと気づいた。

Rustは2000年代のペインポイントを解決した：メモリ安全性、並行性安全性。それはC/C++の泥沼の中で格闘した世代のエンジニアが提示した答えだ。しかし、どの世代にもそれぞれ特有の問題があり、どの世代にもそれぞれのツールが必要だ。

本文は技術仕様書ではなく、世代間の宣言書である。答えるべき問いは：**なぜ私たちの世代の開発者たちは独自の言語を必要とするのか？YaoXiangは私たちの要求にいかに応えるのか？**

## 一、世代間の隔絶感——なぜ既存の言語は「水土に合わない」と感じるのか

### 1.1 那些那些「直感に反する」設計

私が初めてRustを学んだ時、その借用チェッカーにひどく苦しめられた。メモリ安全性の重要性は理解できるが、なぜ単純な文字列結合にこれほど煩雑なライフタイム注釈が必要なのか理解できなかった。后来（のち）、私は気づいた。**Rustの設計者たちは異なる時代に生きていたのだ**と。

彼らの思考パターンは：

- 「メモリ安全性は意図的に解決すべき問題だ」
- 「並行性は慎重に対処すべき怪物だ」
- 「型システムはエラーを捕捉するためのツールだ」

一方、私の思考パターンは：

- 「メモリ安全性は言語がデフォルトで提供すべきものではないのか？」
- 「並行性は呼吸のように自然なことではないのか？」
- 「型システムは問題を探求するための足場になれないのか？」

これはRustへの批判ではない。Rustはその時代において革命的だった。しかし**ある世代の「デフォルト」は、前世代にとっての「贅沢品」なのだ**。

### 1.2 「空気」と「障害」

私たちの世代の成長環境はマルチコアCPU、クラウドネイティブ、モバイルインターネットの世界だ。私たちにとって：

- マルチコアプロセッサは「空気」——シングルコアの制約を経験したことがない
- 非同期プログラミングは「空気」——同期ブロッキングをデフォルトモデルとしたことがない
- 分散システムは「空気」——ローカルファーストの設計思想を経験したことがない

プログラミング言語のチュートリアルを開くと、著者が「なぜ並行プログラミングを学ぶ必要があるのか」を延々と説明しているのを見た時、私たちの心の中のOSはこうだ：**「それは自明のことではないのか？なぜ学ぶ必要がある？」**

これが世代間の隔絶感だ。**前世代が「学ぶ」必要があったものは、私たちにとっては「本能」だ。**

### 1.3 AI時代の「文盲」困境

AIプログラミングアシスタントを使い始めた時、さらに深い問題に気づいた：**既存の言語の設計はAIを考慮したことがなかった。**

- 構文の曖昧さがAIに幻覚を生じさせる
- 暗黙のルールがAIに行動を推測させない
- 型システムの境界の曖昧さがAIに誤った型の提案をさせる

私はAIがPythonのリスト内包表記とC++のラムダ式を混同し、Rustの`impl Trait`とTypeScriptのジェネリクスを混同するのを目撃した。これはAIの問題ではなく、**言語設計がAI時代に備えていなかったという問題だ。**

### 2.2 並行性は私たちの「母語」

スレッドプールを手動で管理する時代を経験したことがない。初めて並行コードを書いた時、使用したのはJavaScriptの`async/await`だった。后来（のち）、Rustの`async/await`を学んだ時、なぜ単純な「待機」操作にこれほど複雑な`Future`
traitと`Pin`、`Context`が必要なのか驚いた。

**並行性にとって、特性ではなくデフォルト状態なのだ。**
マルチタスクオペレーティングシステムが私たちにとって「空気」であるのと同じだ。

だからこそ、YaoXiangが「並作（spawn）モデル」を採用する時、これはイノベーションではなく、**私たちの本能を言語に符号化することだ。**

```yaoxiang
# YaoXiangの並作構文：並行性はデフォルトであり、明示的ではない
fetch_user(Int) -> User spawn = (id) => { ... }
fetch_posts(User) -> Posts spawn = (user) => { ... }

main() -> Void = () => {
    user = fetch_user(1)     # 自動的に並列実行
    posts = fetch_posts(user) # userの完了を自動的に待ってから並列実行

    print(posts.title)       # postsの準備完了を自動的に待つ
}
```

これは「簡素化」ではなく、**私たちの認知モデルを復元することだ。**

## 三、YaoXiangの設計応答——新世代のために設計された言語

### 3.1 すべてが型：圏論的世界観

YaoXiangの中核設計哲学は**「すべてが型」**だ。これは技術的選択ではなく、**世界観の選択**だ。

YaoXiangの世界では：

- 値は型のインスタンス
- 型自身も型のインスタンス（メタタイプ）
- 関数は入力型から出力型への写像
- モジュールは型の名前空間の組み合わせ

```yaoxiang
# 型としての値
MyList = List(Int)    # MyListは現在、型の値である

# 依存型：型は値に依存する
type Vector[T, n: Nat] = vector(T, n)

# 型の パターンマッチ
describe_type(type) -> String = (t) => {
    match t {
        Point(x, y) -> "Point with x=" + x + ", y=" + y
        ok(value) -> "Ok value"
        _ -> "Other type"
    }
}
```

この設計は何に応えるのか？それは私たちの世代の**数学的美**への追求に応える。私たちが数学を学ぶ時に触れた集合論と圏論が告げる：**型は最高層の抽象だ**。なぜそれを徹底しないのか？

### 3.2 並作モデル：並行性を空気にする

YaoXiangの並作モデル（Concurrency Model）は**従来の非同期プログラミングに対する範例の転換だ。**

従来の非同期プログラミングはこうだ：

```rust
// Rust
async fn fetch_data(url: &str) -> Result<Data, Error> {
    let response = reqwest::get(url).await?;
    response.json().await
}
```

理解する必要があるのは：

- `async`/`await` 構文
- `Future` trait
- `Pin` と `Unpin`
- ランタイム（tokio/async-std）
- タスクスケジューラ

YaoXiangの並作モデルはこうだ：

```yaoxiang
# 並作関数：必要なのは spawn マーカーのみ
fetch_data(String) -> JSON spawn = (url) => {
    HTTP.get(url).json()
}

# 並作ブロック：明示的な並列化
compute_all(Int, Int) -> (Int, Int, Int) spawn = (a, b) => {
    (x, y, z) = spawn {
        heavy_calc(a),
        heavy_calc(b),
        another_calc(a, b)
    }
    (x, y, z)
}

# 並作ループ：データ並列化
parallel_sum(Int) -> Int spawn = (n) => {
    total = spawn for i in 0..n {
        fibonacci(i)
    }
    total
}
```

これは簡素化ではなく、**問題再定義**だ。従来の非同期プログラミングが問うのは「非ブロッキングコードを同期コードのように見せるにはどうするか？」YaoXiangが問うのは「なぜ非同期と同期を区別する必要があるのか？」

**並行性が空気になった時、構文上の差異は消える。**

### 3.3 AIフレンドリーな構文設計

YaoXiangの設計はAIコード生成のニーズを考慮している。これは「AIが理解できる」程度の表面的な話ではなく、「AIが設計に参加する」深い考察だ。

**設計原則：**

1. **厳密に構造化、曖昧さのない構文** - AIが構文の曖昧さにより幻覚を生じない
2. **ASTが明確、位置特定が容易** - AIがコード位置を正確に特定できる
3. **意味が明確、隠れた振る舞いがない** - AIがコードの振る舞いを正しく推測できる
4. **コードブロックの境界が明確** - AIがスコープを誤解しない
5. **型情報が完全** - AIが正しい型提案を行える

```yaoxiang
# コードブロックの境界を明確にする
function_name(Params) -> ReturnType = (params) => {
    # 関数本体
}

# 括弧の省略を禁止（曖昧さ排除）
foo(T) -> T = (x) => x

# 4スペースインデントを必須（構造明確）
if condition {
    do_something()
} else {
    do_other()
}
```

これは単なるスタイルガイドではなく、**AI協働のために設計された言語インフラだ。**

## 四、具体的な設計判断の背後にある世代的思考

### 4.1 なぜ「コンストラクタ＝型」を選択するのか？

YaoXiangの型定義は統一して`コンストラクタ`構文を使用する。異なるバリアントが異なるコンストラクタ関数に対応する：

```yaoxiang
# ゼロ引数コンストラクタ（enumスタイル）
type Color = { red: () -> Color, green: () -> Color, blue: () -> Color }

# 複数引数コンストラクタ（構造体スタイル）
type Point = Point(x: Float, y: Float)

# ジェネリックコンストラクタ
type Result[T, E] = { ok: (T) -> Result[T, E], err: (E) -> Result[T, E] }
```

これは何に応えるのか？**型システムは統一されるべきであり、分裂されるべきではない**、という要求に応える。

Javaでは、`class`、`enum`、`interface`がある。Rustでは、`struct`、`enum`、`trait`がある。TypeScriptでは、`interface`、`type`、`class`がある。

なぜ型にこれほど多くの形式があるのか？**型は型であり、区別は型の形式ではなく値の形式であるべきだ。**

### 4.2 なぜGCを捨て、所有権モデルを採用するのか？

YaoXiangはGCではなくRustスタイルの所有権モデルを採用した。

```yaoxiang
# デフォルトで不変参照
process(ref Data) -> Void = (data) => {
    # data は読み取り専用
}

# 可変参照
modify(mut Data) -> Void = (data) => {
    # data を変更可能
}

# 所有権の移転
consume(Data) -> Void = (data) => {
    # data の所有権が移転される
}
```

これは単なるパフォーマンスの選択ではなく、**哲学的選択**だ。

私たちの世代は環境关心（かんしん）し、資源効率を关心する。**「無限のメモリ」は当たり前だとは考えていない。**
私たちはクラウドサービスの請求書を見ており、すべてのバイトにコストがかかることを知っている。

同時に、私たちはGCの「Stop the
World」停止に煩わされたくない。スムーズなユーザー体験に慣れ、リアルタイムシステムの応答性に慣れている。

所有権モデルが私たちに与えるもの：**ゼロコスト抽象 + 確定的なパフォーマンス + メモリ安全性。**

### 4.3 なぜカリー化が中核構文なのか？

YaoXiangはカリー化を通じてオブジェクトメソッド呼び出しに類似した構文糖衣を実現している。

```yaoxiang
# 中核関数定義
distance(Point, Point) -> Float = (a, b) => {
    dx = a.x - b.x
    dy = a.y - b.y
    (dx * dx + dy * dy).sqrt()
}

# メソッド構文糖衣のバインディング
Point.distance(_) = distance(self, _)

# 呼び出し方法
p1 = Point(3.0, 4.0)
p2 = Point(1.0, 2.0)
d1 = distance(p1, p2)     # 直接呼び出し
d2 = p1.distance(p2)      # メソッド構文
```

これは何に応えるのか？それは**関数型プログラミングの純粋さを望みつつ、オブジェクト指向の直感性も保ちたい**という要求に応える。

私たちの世代はプログラミングを学ぶ時、多くの場合Pythonから始め、后来（のち）JavaScriptに触れる。`obj.method()`の呼び出し方法に慣れているが、関数型プログラミングのエレガンスも欣赏（しょうさん）する。

カリー化により、両者は**同じコインの裏表**となる。

## 五、技術を超える——世代的視点の文化的意義

### 5.1 私たちには独自の声が必要だ

プログラミング言語設計は長らく「先輩」たちの言説領域だった。Linus
Torvaldsは21歳でLinuxを始め、Graydon HoareがRustを設計した時、彼はすでにシニアエンジニアだった。

しかし、どの世代にもそれぞれ独特の洞察がある。**若者が問題を見る角度が異なることは、欠陥ではなく価値だ。**

私がYaoXiangを設計する時、C/C++の歴史的包袱（ふくろ）がない。既存システムに「適合」する必要はなく、「ネイティブ」に新システムを設計できる。

### 5.2 オープンソース協業の新しい範例

私たちの世代が理解するオープンソース協業とは：

- メーリングリストではなく、Discordコミュニティ
- 公式ドキュメントではなく、インタラクティブチュートリアル
- カンファレンス講演ではなく、ライブコーディング
- 特許保護ではなく、開放的協業

YaoXiangは初日からオープンソースだ。これは理想主義のためではなく、**これが私たちの世代の仕事のやり方だ。**

### 5.3 AI原生時代のために設計する

現在の言語は2000年代のために設計されている（シングルコア、ローカル、人手記述）。YaoXiangは2030年代のために設計されている（マルチコア、分散、人機共著）。

これは誇張ではなく、**緊迫した現実**だ。

AIはプログラミングのあらゆる环节（リンク）を変えている。コード生成、コードレビュー、デバッグ支援、ドキュメント作成——AIは開発者のデフォルトのパートナーになりつつある。

**AIを考慮しない言語は、活字印刷機を考慮しないフォント設計のようなものだ——それは時代遅れで不器用に映るだろう。**
