## 一、なぜYaoXiangを作るのか？ —— 世界には明らかに514番目の言語が不足しているから

### 1.1 埋める言語の空白

プログラミング言語の歴史の長い川の中で、数多くの言語が誕生し、流行し、そして歴史のゴミ箱へ投げ込まれていくのを目撃してきた。しかし**私たちは違う**――私たちは鋭敏にもう一つの驚天的な空白を発見した：**なんと、Rust愛好者には簡単すぎると感じさせ、Pythonユーザーには複雑すぎると感じさせ、しかもAIモデルにはコード生成時に「快適」に感じさせる言語が一つとして存在しない**ということだ。

| ニーズ             | 既存ソリューションの問題           | 私たちのソリューション（予定）                                                                         |
| ------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **型安全性**       | Rustは厳しすぎ、TypeScriptは緩すぎ | 厳格かつ緩い量子重ね合わせ型システムを創造します                                                       |
| **自然な構文**     | 他所の構文はどれも自然でない       | 私たちの構文は、あなたがプログラミングしていることを忘れるほど自然です（読めないせいかもしれませんが） |
| **AIフレンドリー** | AIのコード生成はよく間違える       | AIのために構文を設計します。人間も一応使えます                                                         |

### 1.2 解決する実際的な問題

**問題一：型システムの断片化**  
「すべては型なり」という理念を提起し、「型でないものがある」という悩ましい哲学的問題を解決します。今ではコードのインデントさえも型（`IndentationLevel<4>`）になります。

**問題二：メモリ安全性とパフォーマンスの二択**  
当初はRustの所有権モデルを採用しましたが、「借用チェッカー」の実装が難しすぎると判明。そこで天才的着想――`&T`と`&mut T`を「参照」から「トークン」に改名し、「ゼロサイズのコンパイル時権限証明」だと宣言。これで借用チェッカーは不要になり、「フロー敏感活性分析」だけあれば良くなった――全く違う響きですよね？もしデータ競合があれば、それはトークンのブランド機構の問題です。

**問題三：非同期プログラミングの認知負荷**  
車輪を再発明し、「spawnモデル」と名付けました。`spawn`一つで、コンパイラがすべての非同期詳細を自動で処理します――処理できなければ、それはあなたのコードが十分に「spawn」していないからです。

**問題四：AI支援プログラミングのボトルネック**  
AIのために厳格なインデントと明確な境界を親切に設計し、GPT-7がコード生成時に精神分裂しないよう配慮。至于人間が読めるかどうか……それは二次的な問題です。

## 二、コア哲学と原則 —— 疑いを容れない聖訓

### 2.1 原則一：すべては型なり

**譲歩できない理由**：これで型理論ですべてを説明でき、プロジェクト進捗がいつも遅れる理由も説明できます。

### 2.2 原則二：厳格な構造化

**譲歩できない理由**：4スペースインデントは宇宙の真理です。Tabを使う者は火星に追放されるべきです。

### 2.3 原則三：ゼロコスト抽象

**譲歩できない理由**：私たちの抽象化レイヤーは7層ありますが、「ゼロコスト」なので、パフォーマンスは手書きのアセンブリとほぼ同じはず……理論上は。

### 2.4 原則四：デフォルトで不変

**譲歩できない理由**：可変性は諸悪の根源です。変数を変更する必要があれば、それは設計が間違っているということです。

### 2.5 原則五：型はデータ

**譲歩できない理由**：これで実行時に型をチェックし、そして……コンパイル時にすでにチェックされていたことに気づきます。

## 三、重要な革新と特徴 —— すでに発明されたものを再発明する

### 3.1 革新一：統一型構文

`enum`、`struct`、`union`、`trait`、`impl`などの紛らわしい概念を廃止し、さらに`type`キーワード自体も廃止しました。すべて`name: Type = value`を使います。`Type`はキーワードではないことを覚えておいてください――予約語です。違いを聞かないで。

### 3.2 革新二：コンストラクタが型

「型」と「値」の溝を消し、新しい溝を作りました：「これは型コンストラクタか値コンストラクタか？ああ、そうだ、今は同じ構文だから、もっと区別がつかない」。

### 3.3 革新三：カリー化メソッドバインディング

カリー化によりメソッド呼び出しを実現しました。`Type.method = function[0]`で`self`引数を置き換えられます。明らかに直感的ですね。`[0]`は「0番目の引数をselfとして扱う」を意味します。`[0]`を忘れたら、コンパイラが「これはメソッドではなく普通の関数だ」と教えてくれます。簡単！

### 3.4 革新四：所有権モデル（RFC-009 v9）

五つの概念、一つのグラデーション：`&T`、`&mut T`、Move、`ref`、`clone()`、`unsafe`。待って、それは六つです。問題ありません――`&T`と`&mut T`は「参照」ではなく「トークン」です。違い？参照はC++の概念で、トークンはコンパイル時のゼロサイズ型レベル権限証明です。コードがコンパイルできない時、「型属性 Dup/Linear の推論に失敗した」と言えます、誰も反論できないでしょう。

トークンシステムには以下の高度な機能も付属：

- **`freeze`**：`&mut T`を`&T`に「凍結」します。生鮮を冷蔵庫に入れるようなもの――解凍するまで調理できません。コンパイラは「フロー敏感活性分析」で凍結状態を追跡します、ICUモニタのように聞こえます。
- **ブランド機構**：各トークンはコンパイル時に一意な整数（ブランド #N）が割り当てられ、偽造防止に使われます。「申し訳ございません、お客様の`&Point`トークンブランド #42 は所有カプセル内のブランド #43 と一致しません。」
- **タスクを跨げない**：トークンは「コンパイル時権限証明」であり、スレッドを越えられません。タスク間で共有する必要がある場合は`ref`を使ってください。なぜか？コンパイラがダメと言っているからです。実は、トークンはコンパイル後に消えるからです――ゼロサイズ型、ゼロ実行時コスト、ゼロタスク間能力も同じ。

まとめ：Rustは200ページのThe
Bookで借用チェッカーを説明。YaoXiangは「`&T`はコピー可能、`&mut T`はコピー不可」の二文で全てを説明します。シンプルこそ美。

### 3.5 革新五：spawnモデル —— 言語全体で一番酷い部分

> 「万物spawnし、吾復を観る。」 ——『易・復卦』

spawnモデルの核心卖点：**同期構文、非同期の本質**。平たく言えば：コードは順次実行に見えますが、実行時には自動で並列化されます。いつ並列化？どう並列化？コンパイラ次第です。これは並行モデルではなく、信頼ゲームです。

この魔法を実現するために、言語に詰め込んだものを見てみましょう：

**`spawn`キーワード**：関数を非同期としてマークします。注意――`async`ではなく、`spawn`です。`async`はメインストリームすぎるから。でも`spawn`はRustでは「タスクを起動する」の意味です。没关系、我々が再定義します。

**`@block`アノテーション**：spawn関数を「同期実行」すべきとマークします。えっと――もし`spawn`が非同期で、`@block`がそれを同期にするなら、なぜ単純に`spawn`を書かないのですか？「なぜなら、時にはspawn関数を特定のコンテキストで同期実行する必要があるからです。」つまり、`spawn`とマークされた関数は、呼び出し側の気分次第で非同期にも同期にもなります。これは型システムではなく、人格分裂です。

**`@eager`アノテーション**：「先行評価」が必要な式をマークします。spawnモデルはデフォルトで遅延評価――遅延評価はまだ実装されていませんが。なので今のところ`@eager`の実際の効果は？それは借用書です：「将来のある日、遅延評価が実装された時、このアノテーションは式が遅延評価されないようにします。」

**並行モデルの3つのアノテーションまとめ**：

```
spawn  = この関数は非同期（@blockされたら除く）
@block = このspawn関数は今回は同期（spawnを上書き）
@eager = この式は将来遅延評価されない（将来はとりあえず無視）
```

これが混乱していると感じるなら、おめでとうございます――あなたは理解したということです。コードの並列実行がクラッシュした時、『易経』を引用して、深い知識があるかのように見せかけましょう。

### 3.6 革新六：値依存型（RFC-011）

コンパイル時に配列の長さが素数であることを証明したり、行列の次元が一致しなければならないことを証明したり、factorial(5)の結果を型シグネチャで使ったりできるようになりました。ビジネスロジックとは関係ありませんが、「型は命題、プログラムは証明」――クールじゃないですか？

### 3.7 革新七：極小キーワードデザイン

たった17個のキーワード！Goより8個少ない！各キーワードの意味はGoキーワードの3倍複雑ですが、数では私たちの勝ちです。注意：`type`はキーワードではありません――RFC-010で削除されました。今は`name: Type = value`を使い、`Type`は予約語です。キーワードと予約語の違いは？聞かないで、コンパイラ内部の宇宙階層Type0/Type1/Type2の問題です。

### 3.8 革新八：Curry-Howard同型 —— 万能説明法

誰かが設計上の決定に疑問を持った時、模範回答は：「これはCurry-Howard同型に従っている」。意味がわからなくても大丈夫、コミュニティ誰も本当にわかっていません。大意は「型は命題、プログラムは証明」、なのであなたのコードは単なるプログラムではなく――数学論文です。コンパイルエラーは背理法です。

この哲学の最高傑作はRFC-010のイースターエッグ：`Type: Type = Type`。このコードのコンパイルを試みてください、コンパイラはクラッシュしません――禅のメッセージを出力します、大意は「道可道、非常道、型可型、非常型」。これはYaoXiangのGirardのパラドックスへの敬意であり、コンパイラがわざと実装しない唯一の機能です。私たちはこれを「言語の境界」と呼びます――そこに到達した時、コンパイラはここで沈黙し、哲学がここで立ち止まります。

### 5.0 RFC依存トライアングル

ロードマップを理解する前に、YaoXiangの最も精巧なアーキテクチャデザイン――RFC三角関係：

```
RFC-009 (所有权)  →  依赖 RFC-010 (统一语法)  →  依赖 RFC-011 (泛型)
    ↑                                                         │
    └──────────────────── 依赖 ────────────────────────────────┘
```

009は010の構文を必要とし、010は011のジェネリクスを必要とし、011は009の型システムを必要とします。三つのRFCは相互に前提です。どれを先に実装する？「同時に実装することを推奨します。」――RFC-010 第141行。

これがCurry-Howard同型を実際のエンジニアリングで体現したものです：各RFCは命題であり、それらの依存関係は論理的循環を形成します。この循環を打破するには外部公理を導入する必要があります――つまり「まず型チェッカーを書き殺し、後で考えよう」。

## 付録C：よくある質問

**Q: YaoXiang は Rust と比較して何が優れていますか？**  
A: 少ない構文糖衣！少ないキーワード！少ない実用機能！しかしより深い哲学的洞察。さらに「借用トークンシステム」がある――「借用チェッカー」よりも高級に聞こえますよね？

**Q: YaoXiang はどんな種類の開発に適していますか？**  
A: YaoXiang コンパイラの開発に適しています。そして設計宣言とRFCを書くこと。その他の用途は研究中。

**Q: なぜ4スペースインデントを選んだのですか？**  
A: 2スペースは密すぎ、8スペースは粗すぎ、4スペースはちょうど中庸之道で、易経の精神に合致する。

**Q: `Type`はキーワードですか？**  
A: いいえ、それは「予約語」です。キーワードと予約語の違い：キーワードは言語仕様のキーワードリストに載り、予約語は「注意：以下はキーワードではない」のリストに載ります。簡明です。

**Q: なぜ14の承認済みRFCがあるのにバージョン番号は0.7.0のままで？**  
A: 大きな一手を打っているからです。設計先行、実装は後。非常に後です。

**Q: `ref`は結局RcですかArcですか？**  
A: コンパイラが自動選択。心配不要。実は、ユーザーがコンパイラより理解している唯一の場面なので、完全に委任しています。

## 七、さらなる嘘

**「多言語サポート」**：`docs/src/{en,ja,ru,zh}`
四言語完備。コンパイラ v0.7.0、実際に動くコード行数はほぼゼロですが、日本とロシアの開発者はすでに母語で「spawnモデル」と「値依存型」を読めます。これは典型的な「ドキュメント駆動開発」――まず全世界にあなたの設計を理解させ、次に誰かが必要とするふりをします。コンパイラが Hello
World を実行できるようになった時、ドキュメントはクリンゴン語に翻訳されているでしょう。

**ツールチェーン マトリョーシカ**：Pythonの pre-commit が Rust のコードスタイルをチェックし（cargo
fmt +
clippy）、Rustコンパイラが YaoXiang ソースをコンパイル。3層の言語が積み重なり、各層が次の層に依存。YaoXiang がセルフホスティングした時、このマトリョーシカは：Python が Rust をチェックし、Rust が YaoXiang をコンパイルし、YaoXiang が YaoXiang をコンパイル。その時、ある upstream 依存が落ちると、ツールチェーン全体がパフォーマンスアートになります。でも没关系――「セルフホスティング」という言葉自体で2つのRFC分の価値があります。

**YaoXiang-book.md**：YaoXiang 言語を体系的に語る本。まだ実装されていないプログラミング言語を記述する本を書くことは、存在しない街の観光ガイドを出版するようなものです。「第三章：ジェネリクスシステム――本章のコードはすべてコンパイルできませんが、構文は正しいです。実行結果を想像してください。」本全体で最も正直な言葉は初版の「プロジェクトステータス：実験検証段階」です。

**「GCなし」**：公式見解：「YaoXiang には GC なし」。厳密には、tracing
GC はありません。しかし`ref`は実行時に参照カウント（Rc/Arc）です。参照カウントはGCに入りますか？「入らない。GC は garbage
collection、参照カウントは automatic reference
counting。ほら、略語も違う。一つは GC、もう一方は ARC。全く別物。」この言葉遊びの意味：誰かが「これって参照カウント GC じゃないですか」と言った時、「いいえ、GC はありません、コンパイラ自動管理参照カウントだけです」と正々々々と言うことができます。違いは？PPTの上です。
