# RFC-027a: 終端検査の証明関数フォールバック

## 概要

RFC-027 決定記録に预留された再審議条項を兑现する：四種の自動戦略では終端証明をカバーできない**非構造的再帰**（gcd 類の非直接的な減少、相互再帰）に対し、**証明関数のフォールバック**を提供する——測度と証明はどちらも通常の YaoXiang 関数であり、新たな構文はゼロ、型検査器が検証する。メカニズムの位置付けは**精化型証明プロトコルの一応用**である：証明側には新たなメカニズム・ゼロ（RFC-027 既設の Unproven フォールバック通路をそのまま再利用）、新規なのはコンパイラ側の呼び出し点義務生成と一つの命題アンカーのみ。全自動優先原則は不変：自動戦略が依然として第一経路であり、ユーザーの介入は Unproven の後にのみ発生する。適用範囲も同時に裁定（2026-09-14）：終端検査は**コンパイル時評価**（依存追跡トリガ）のみを対象とし、実行時コードには終端証明を要求しない——RFC-027
§6.7 スコープ表原文を採択し、現行実装の全量検査はこれに従って絞り込む。

## 動機

### ホスト資格と改訂範囲

RFC-027 は子 RFC スロットを预留していなかった（RFC-029 が 029a を预留するパターンと異なる）。本子 RFC のホスト資格は、RFC-027 決定記録自体の再審議条項に由来する：

> どの戦略によっても終端を証明できないループは、コンパイラが直接エラーを出力する——これはハード安全性哲学であり、欠陥ではない。**もし将来に現実のシナリオ（学術的構成ではない）で四種の戦略のいずれもカバーできないアルゴリズムがあれば、再度議論する。**
> —— RFC-027 決定記録

本 RFC はまさにその「再審議」の正式な载体である。これは記録済みの決定を**覆すものではない**——条項自体が決定の一部であり、それを起動することは設計通りに決定が機能することである；条項の予期された行使である。

RFC-027 への改訂範囲は正確に四箇所に限定される：

| 改訂点                            | 原記録                                                    | 改訂後                                                                                                                                                                             |
| --------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| §7「半自動注釈に余地を残さない」  | 終端検査は完全に閉鎖                                      | 「**注釈構文**の余地はなし」に絞り込む——証明関数フォールバックは注釈ではない（新たな構文位置なし、関数定義に付随しない）、「コンパイル時述語に新たなキーワードなし」と同一の世界観 |
| 決定記録「Unproven → 直接エラー」 | 終端領域は唯一フォールバックのない証明領域                | 「Unproven → 証明関数を提供可能」に変更——正当性領域（述語 Unproven → 証明関数、RFC-027 §証明関数）と同じ動作に揃える                                                               |
| §6.8 エラーメッセージ             | 「コンパイラが解析可能な反復パターンを使用してください」  | 「または測度関数と終端証明関数を提供してください」を追記                                                                                                                           |
| §7 適用範囲                       | 「ループ」位置の限定なし、実装は全再帰/ループの無条件検査 | **コンパイル時評価**（依存追跡トリガ）と明確化、§6.7 スコープ表と整合；実行時コードは終端証明を要求しない（設計裁定 2026-09-14）                                                   |

**改訂しない**部分：四種自動戦略の優先地位、全自動優先原則、ハード安全性哲学のその他内容（Disproved は依然としてコンパイルエラー + 反例；正当性領域の動作はゼロ変化）。

### 現状の問題（2026-09-14 実測、v0.7.14 後 dev）

1. **スコープ偏差：文書はコンパイル時、実装は全量を検査**。RFC-027
   §6.7 スコープ表は「ランタイム呼び出し（型位置ではない）は終端検査不要」と明記；現行の
   `TerminationChecker`
   はすべての再帰とループを無条件に通過する（`checker.rs:405`）——純粋にランタイム用途の非構造的再帰が直接コンパイル失敗し、解析可能な測度を持たない
   `while`
   同样に拒否される。本 RFC は設計裁定（2026-09-14）に従い絞り込む：終端検査はコンパイル時評価のみに奉仕し、義務は依存追跡によってトリガされる。

2. **コンパイル時位置の非構造的再帰にフォールバックがない**。`termination.rs` は現在 Phase
   1：戦略 3（有界増加/減少）、再帰引数の直接減少（`factorial(n-1)`）、`for`
   ループの自然終端。戦略 1/2/4 は未着地（RFC-027 既定拡張）。非構造的再帰がコンパイル時評価に入った場合（例：述語体内での呼び出し）、義務を閉じることができない：

   ```yaoxiang
   gcd: (a: Int, b: Int) -> Int = {
       if b == 0 { return a }
       return gcd(b, a % b)
   }
   ```

   再帰引数 `(b, a % b)`
   は引数の直接的な減少ではない——現在はエラーを出し、反復パターンへの書き換えを要求する。gcd は可読性を損なわずに「解析可能な反復パターン」に書き換えられない；マージソート分割、相互再帰（偶数/奇数判定）、木巡回も同断。これらは実在のアルゴリズムであり、学術的構成ではない——**再審議条項の発動条件が成立する**。

3. **証明領域のフォールバックが非対称**。RFC-027 の正当性命題（`Positive(b)`、`IsMax`
   等の述語）は Unproven の際に証明関数フォールバックを持つ；終端性はコンパイル時証明領域で唯一、Unproven 即死の領域である。同一世界観下でこの非対称に原則的な理由はない。

4. **基盤整備済み**。#292 は Z3 バックエンドを実際に接通した（`ConstExpr` → SMTLib →
   Unsat/Sat 判定リンク）。再帰呼び出し点の測度減少義務 `measure(args') < measure(args)`
   は一階線形算術命題であり、まさにこのリンクが開通した決定可能フラグメント内に収まる——同一パイプラインを再利用し、新たなバックエンドは追加しない。

## 提案

### 中核設計

**位置付け：本 RFC は新たな証明メカニズムを追加するものではなく、精化型証明プロトコルの一応用である。**
RFC-027 は「証明関数とは YaoXiang 関数であり、その戻り型は表明される命題である」と既に確立した——命題とは述語適用であり、述語適用とは精化型である。終端証明の人間側は終始この既設通路を辿る（Unproven
→ 証明関数を書く → 型検査器が検証 →
witness 消去）、正当性領域と完全に同一のプロトコルである。新規面は三件に収束する：

1. **測度関数**——通常のコンパイル時関数、入力は被測関数と同じシグネチャ、`Int` または `Int`
   のタプル（辞書順）を返す。注釈ではなく、関数定義に付随せず、参照可能・単体テスト可能な一級関数。
2. **呼び出し点義務生成**——コンパイラが `f`
   の関数本体から各再帰呼び出し点の減少義務を抽出する。これが唯一の新コンパイラロジックである：呼び出し点の実際引数は関数本体内にあり、義務（意味制約）はコンパイラが代筆しなければならず、人間が代筆することはできない——さもなければ証明は実際のコードに紐付かない（設計哲学第 3 条を参照）。
3. **終端命題
   `Terminates(f, m)`**——**コンパイラが関数本体を代筆する精化述語**：その「制約内容」は上記の義務集合であり、そのシグネチャは
   `(f, m)`
   を結びつけるアンカーに過ぎない。内蔵の必要性はここだけにとどまり、メカニズム的には何ら新しいものはない。関数と測度の両方を型に入れるのは測度のみではない：相互再帰では
   `is_even`/`is_odd` のシグネチャは同じで、測度による発見だけでは曖昧さが生じる（例を参照）。

証明関数の三つの役割は位置付けから自然に導出される：測度 `m` を `f`
に明示的に束縛する（発見アンカー、あらゆる注釈構文を代替）；残余義務に discharge 位置を提供する（本体 = 証明空間）；全称量化で
`f` の引数名を保持する（本体中で `a`、`b`
を参照して事実を記述できる）。構文の落点詳細は「詳細構文」、完全な走査は「例」を参照。

### 例

#### エンドツーエンド詳解：gcd

```yaoxiang
-- 被測関数（正当性領域は通常通り：引数精化、ガード、再帰呼び出し）
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

-- 測度：通常関数（単体テスト可、再利用可）
gcd_measure: (a: Int, b: Int) -> Int = { b }

-- 証明関数：空本体——全義務は SMT により自動閉鎖
gcd_proof: (a: Int, b: Int) -> Terminates(gcd, gcd_measure) = { }
```

起動前提：以下の義務は `gcd`
がコンパイル時評価に入ったとき（依存追跡命中、例：述語体内での呼び出し）にのみ生成・消費される；`gcd`
がランタイム呼び出しのみで使われる場合はいかなる終端証明も要求されない。

コンパイラが `gcd_proof` を処理する全過程：

1. **シグネチャ検証**：証明関数の引数は `gcd`
   の仮引数と**基底型**で一つずつ照合する（`Int`、`Int`）。仮引数の精化（`b >= 0`）は証明関数のシグネチャで重複しない——コンパイラが義務コンテキストとして既に保持しており、証明関数の本体と義務はこのコンテキスト内で検証される。
2. **整礎性義務**：`gcd_measure(a, b) >= 0`、すなわち `b >= 0`——仮引数の精化 `NonNegative(b)`
   から直接導出。測度の境界に新たなメカニズムは不要で、引数の精化制約そのものである（精化型の意味論的条件が整礎性上で実現される）。
3. **呼び出し点義務生成**：唯一の再帰呼び出し点 `gcd(b, a % b)`、経路ガード
   `b != 0`、`gcd_measure(b, a % b) < gcd_measure(a, b)` を生成；測度の本体に代入して展開すると
   `a % b < b`。
4. **SMT 判定**：義務の否定 `b != 0 ∧ a % b >= b`
   が充足不能であることを検証——線形算術 + モジュロ公理、ミリ秒級 → Proved。
5. **受理**：本体が空、残余義務の discharge 不要。`gcd`
   の終端が証明される；測度と証明関数は witness 消去により、実行時バイナリには入らない。

#### 非空本体：残余義務は証明済み補題を参照

呼び出し点の減少がコンパイラに見えない事実に依存する場合（以下の例では `step`
の本体が依存モジュール内にあり、義務生成に対してはブラックボックス）、人間はその事実を**証明済み述語の参照**として本体に記述する——裸の式、Assert 文ではない：

```yaoxiang
step: (n: Int) -> Int = { ... }

loop_x: (n: NonNegative(n)) -> Void = {
    if n == 0 { return () }
    return loop_x(step(n))
}

x_measure: (n: Int) -> Int = { n }

-- step 定義モジュール内でエクスポートされる証明済みの事後条件（正当性領域、通常述語、定義箇所で証明済み）：
step_decreases: (n: Int) -> Type = { n >= 1 ==> step(n) < n }

-- 終端証明 = 当該補題の参照（証明済み述語の参照 = その確立済み証明の適用、Curry-Howard）：
x_proof: (n: Int) -> Terminates(loop_x, x_measure) = {
    step_decreases(n)
}
```

検証過程：義務 `x_measure(step(n)) < x_measure(n)`（ガード `n != 0`、コンテキスト `n >= 0`）は
`loop_x` の属するモジュールで独立に閉じることができない → 非空本体を発見 → 表明 `step_decreases(n)`
が証明済み述語のインスタンスであることをアサート、検証パス → 補題として残余義務を閉じる。本体中で直接
`step(n) < n`
と書けば、検証器は誠実に Unproven を報告する——事実は追跡可能な証明済みの出所に由来しなければならない。

#### 相互再帰：SCC ごとに義務を収集

```yaoxiang
is_even: (n: NonNegative(n)) -> Bool = { if n == 0 { return true }  return is_odd(n - 1) }
is_odd:  (n: NonNegative(n)) -> Bool = { if n == 0 { return false } return is_even(n - 1) }

nat: (n: Int) -> Int = { n }

is_even_proof: (n: Int) -> Terminates(is_even, nat) = { }
is_odd_proof:  (n: Int) -> Terminates(is_odd, nat) = { }
```

義務は SCC ごとに収集され、関数横断エッジの義務は
`m_callee(callee_args) < m_caller(caller_args)`——ここでは `nat(n - 1) < nat(n)`、ガード
`n != 0`、両関数がそれぞれ閉ループする。両関数のシグネチャは同じで、測度による発見だけでは対象を区別できない——これが
`Terminates(f, m)` が二引数である直接的な理由である。

#### 負例：測度が厳密に減少しない

```yaoxiang
loop_forever: (n: Int) -> Int = { return loop_forever(n) }
loop_proof: (n: Int) -> Terminates(loop_forever, nat) = { }
```

義務 `nat(n) < nat(n)` すなわち `n < n`、その否定は常に充足可能（Sat、モデル
`n = 0`）→ コンパイルエラー **E4022**（測度が厳密に減少しない）、反例は `loop_proof`
を指す。`loop_proof` を削除すると、自動戦略が失敗し証明関数もない →
**E4021**（終端を証明できない、`Terminates` 証明関数の提供を提示）。

### 構文変更

**なし。** 本 RFC はいかなる構文、キーワード、注釈位置も追加しない。既存の系列との対照：

| 世代                | ユーザー側表現                         | 構文キャリア             |
| ------------------- | -------------------------------------- | ------------------------ |
| RFC-022（既に廃止） | `//! decreases: n` コメント注釈        | コメント規約、型検査なし |

## 設計哲学：発見と検証の分離

本 RFC のメカニズム選択は一つの原理から導出される：**終端検査 = 见证発見 + 见证検証、両者の難易度は著しく異なり、分離が必須である。**

| 役割                                                               | 担い手                                                                 | 難易度                                                                               |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 発見（測度と証明の合成）                                           | 四種の自動戦略（機械、制限テンプレート）または人間の証明関数（無制限） | 一般に**決定不能**（停止問題に帰着）——測度を常に見つけられるアルゴリズムは存在しない |
| 検証（固定候補に対する呼び出し点ごとの `m(args') < m(args)` 照合） | SMT（RFC-009a パイプライン）                                           | 決定可能（一階線形算術）、ミリ秒級                                                   |

「決定不能に発見し、決定可能に検証する」——構造的に P/NP の witness/verifier 分離と同型だが、それよりさらに極端である：発見側は困難ではなく、数学的に常に解があるとは限らない；検証側は固定候補に対し完全に機械的である。RFC-027「Unproven を誠実に報告する」と人間のフォールバックは、これにより工学的妥協ではなく、この境界の直接的な帰結である。

三つの帰結が本 RFC の設計制約を構成する：

1. **証明者を信用しなくても問題ない。**
   健全性はすべて検証器に宿る：測度やアサーションを誤れば、SMT が Sat と判定し、E4022 が反例付きで差し戻す——人間は証明できないだけで、誤った証明はできない。Disproved は依然として構成的である（反例モデルを与える）：検証器は NP 検証器よりさらに半歩多く、反論にも証拠を与える。
2. **洞察を検証可能なアーティファクトとして凍結する。**
   人間の知的労働は一度証明関数として書かれれば、機械が検査可能な証明書となり、毎回コンパイルで再検証され、永久に退行を防ぐ（proof-carrying）。
3. **命題はコンパイラ、証明は人間に帰属する。**
   義務（「何が証明されたと見なすか」）はコンパイラが関数本体から生成しなければならない；人間に制約まで書かせると、自分の検収基準を自分で書くことになり、証明書は実際に書かれたコードを証明しなくなる。

四種の自動戦略はこれにより統一的に説明される：それらは**见证合成の制限テンプレート列**である——自動測度合成は文献上、制約求解下のテンプレート列挙に他ならない（線形ランク関数合成が先例）。戦略拡張 = テンプレートの拡張；テンプレート外の発見は人間が担当；検証器は常に同一の SMT。「測度推論を行わない」という非目標の理論形態もここにある：汎用測度推論は発見の決定不能側に属し、その境界（テンプレート）を約定するしかできず、完全性を約束することはできない。

## 詳細設計

### 詳細構文

証明関数に特化した構文はない——これは「コンパイル時述語定義」を別の用途で使うだけである。三つの落点を一つずつ固定する：

**戻り型：述語適用、実引数は関数参照。** `Terminates(gcd, gcd_measure)`
は既存の精化の型位置での適用（`f(x: Positive(x))`、`-> (result: IsMax(T, arr, result))`）と同型；関数名は名前による束縛（RFC-010）に従う通常の束縛であり、既存の述語実引数規則「リテラル、変数（名前による束縛）、型適用」に収まる。唯一の規則レベルの補足：E1092 実引数形態判定に「**関数参照はコンパイル時定数形態に属する**」を追加——規則文面を改めるのみで、文法は変更しない。

**引数：`f` の基底型をミラー、全称量化。** 引数名と基底型を `f`
の仮引数と一つずつ照合し、一致しなければコンパイルエラー（E1093 同族を再利用または登録表に従い新規追加、実装時に決定）。仮引数の精化は重複しない——精化とガード仮定はコンパイラが義務コンテキストとして注入する。全称量化は述語定義自体の引数意味論そのものである（`Positive: (x: Int) -> Type = { x > 0 }`
の `x` 同样に全称量化）。ゼロ引数形式は否决された：残余義務が `f`
の引数名を参照し、本体中で名前が書ける必要がある。

**本体：証明空間、裸のブール式。** 述語定義本体 `{ x > 0 }`
と同一のプロトコル——本体内の各項目は True と表明される裸の式。空本体は合法で、多くのシナリオでそうなる（義務はすべて SMT が閉じる）；非空のアサーションは検証後に補題として残余義務に与えられる；アサーションの合法な出所は証明済み述語の適用である（「非空本体」の例を参照）。

**発見と束縛。** 自動合成に失敗した `f`
に対し、コンパイラは同じモジュールと可視インポート内で戻り型が `Terminates(f, _)`
の形の関数を走査する；戻り型により発見し、名前には依存しない（`f_proof`
は自然な慣習に過ぎない）。複数の候補がある場合、義務がすべてグリーンになる最初のものを採用（宣言順）；すべて失敗すれば最初の反例を出力する。前方参照は合法：発見は検査段階で発生し、宣言順序に依存しない。

**ランタイム表現。** 証明関数は純粋なコンパイル時エンティティであり、RFC-027
CompileTime パターンの witness 消去を踏襲する——測度と証明関数のどちらも実行時バイナリには入らない。

### 起動範囲：使用位置の詳細化

終端義務が**いつ**要求されるかは、RFC-027 既存の依存追踪が答える（それは VC 生成のトリガであり、独立した検証メカニズムではない）：

- **根**：コンパイル時位置——型索引、述語本体、定数評価。コンパイラはこれらのコードを自分で実行する必要があり、全量性は承重要件である。
- **伝播**：呼び出しグラフに沿って根から外向きに拡散し、命中した関数が終端を要求される——自動戦略が証明するか、環境に
  `Terminates` 証明書が存在する。
- **ランタイム呼び出しは決してトリガしない**——RFC-027
  §6.7 スコープ表原文を採択；ランタイムの無限ループはユーザープログラムの動作であり、コンパイラの安全境界ではない。

消費者にとって、これが「この関数は終端可能」の落点である：関数型構文には全体属性位置がなく（引数位置と戻り値位置はあるが、関数自体にはない）、したがって「この関数は終端可能」は定義箇所で型に書き込まれるのではなく、**各コンパイル時使用点**で検査される——環境に証明書が存在すれば満たされる。設計裁定（2026-09-14）：現行実装の無条件全量検査はこれに従って絞り込む。

### 義務生成

関数 `f` と測度 `m`
に対し、コンパイラは二組の一階線形算術義務を生成し、再帰呼び出し点ごと（SCC 内の関数横断呼び出しを含む）に展開する；関数横断エッジの義務は
`m_callee(callee_args) < m_caller(caller_args)`、メンバーが同一測度を共有する場合は同一測度の減少に退化する：

1. **整礎性**：`m(args) >= 0`——測度は自然数上にあり、引数型の境界から導出；導出できなければ残余義務に入る。
2. **厳密減少**：各呼び出し点 `m(callee_args) < m(caller_args)`
   を**経路ガード**下で判定（ガードはその呼び出し点が属する分岐条件から取得、RFC-009a 経路条件収集を再利用）。

**辞書順の展開**：`m` がタプル `(m₁, …, mₖ)`
を返す場合、義務は辞書順比較に従い選言鎖に展開される——`(m₁' < m₁) ∨ (m₁' == m₁ ∧ m₂' < m₂) ∨ …`。展開は義務生成側で行われ、SMT 側は線形フラグメントを保ち、解法器の辞書順ネイティブサポートに依存しない。

**測度関数自身の有界性**：`m`
はコンパイル時評価可能（定数畳み込み）または構造再帰で証明可能でなければならない——終端問題を未証明の別の関数に再帰的に委ねることを禁止する（無限回帰の防止）。病的な測度は既存の E4012（定数再帰過深）と構造検査で阻止される。

### 判定パイプライン

パイプラインは依存追踪命中時にのみ実行される（「起動範囲」を参照）；ランタイムコードはこのパイプラインに入らない。`TerminationChecker`
を五段階に拡張し、前三段階は RFC-027 現行/既定パス、本 RFC は後二段階のみを追加する：

```
1. 構造再帰が直接証明可能（現行ロジック、Regression なし）
2. 自動測度合成：四戦略を順次試行（戦略 1/2/4 は RFC-027 計画通り着地、本 RFC はインターフェースを预留）
3. 合成成功 → 義務 SMT 判定 → Proved
4. 合成失敗（Unproven）→ 証明関数を検索（戻り型が Terminates(f, _) の形）：
     a. 発見 → その測度 m で義務生成 → SMT 判定
     b. 残余義務 → 証明関数本体内のアサーションとして検証（正当性領域の証明関数プロトコルと同じ）
5. 証明関数なし / 証明関数の義務も失敗 → コンパイルエラー（E4021 / E4022）
```

**証明関数の発見ドメイン**：同一モジュール内定義、または `import`
で見えるエクスポート——既存の可視性規則に従い、グローバル魔法的検索はしない。同一 `f`
に対する複数の候補 `Terminates(f, _)`
がある場合、義務がすべてグリーンになる最初のものを採用、複数失敗時は最初の反例を出力（決定的な順序：宣言順）。

**`Terminates` の内蔵性宣言**：これは述語体系に対して特例である——その「アサーション」はコンパイラが
`f`
の関数本体から生成し、RFC-027 の述語構文では表現できない。これは意図的な唯一の内蔵命題であり、理由はトレードオフ節に記録される。

### 後方互換性

- 此前コンパイル成功したプログラム：動作ゼロ変化（前三级パイプラインがフォールバックより先に実行）。
- 此前コンパイル失敗したプログラム：コンパイル時終端義務で失敗していたものは、測度と証明関数を補足すれば通過可能になる——これは再審議条項が授権する緩和であり、「元からエラー」だったプログラムにのみ影響する。
- スコープ絞り込みの影響：此前終端検査で拒否されていた**ランタイム**プログラム（非構造的再帰、解析可能な測度のないループ）は新範囲下では直接コンパイル成功する——意図的な緩和（設計裁定 2026-09-14）、緩和のみであり厳格化はなし；コンパイル時位置の失敗面は不変（依然としてフォールバックで救済可能）。
- 既存のテストコーパス（構造再帰正例、非構造負例）の期待出力は不変、非構造負例のエラーコード/メッセージのみ新コードに従って更新。

## トレードオフ

### 利点

- **新構文ゼロ**：Dafny の `decreases`
  インライン注釈との対照で、本設計は構文空間を占拠しない；測度は単体テスト可能な一級関数である。
- **証明領域の動作整合**：終端領域が正当性領域と一致する Unproven フォールバックを補い、「ハード安全性哲学」が「証明できなければ拒否」から「証明できなければプログラマに委ねる」へと進化する——RFC-027 全文の世界観と一致。
- **基盤再利用**：義務は線形算術であり、#292 が既に接通したパイプラインを辿り、新バックエンド・新判定ロジック族なし。
- **条項兑现即ガバナンス**：再審議は子 RFC 形式で痕跡を残し、決定記録の監査可能性を維持。

### 欠点とリスク

- **記述負担**：二件組（測度 + 証明関数）は単一インライン注釈より冗長。許容——フォールバックは低頻度経路であり、その代わり測度が再利用可能・テスト可能。
- **`Terminates`
  は本体をコンパイラが代筆する唯一の述語**：「述語本体はすべてユーザーが書ける」という純粋性から逸脱する。理由：呼び出し点の実際引数は関数本体内にあり、ライブラリ述語は原理的に参照できない；内蔵面は命題名一つに収束し、メカニズムはゼロ追加（中核設計と設計哲学を参照）。
- **戦略 1/2/4 未着地期間中、フォールバックが早すぎる可能性がある**：Phase
  1 自動面が狭く、より多くの関数が証明関数経路に落ちる。緩和：四戦略着地後、フォールバック面は自動的に狭まる；証明関数を先行させることは無駄ではなく、戦略アップグレード後も残余義務の discharge 担体として機能し続ける。
- **反例品質**：Sat 反例は非線形ガードに対して直感的でない可能性がある。既知の制限として記録し、反例提示は RFC-013 診断メッセージ規範に従って反復する。

## 非目標

- 構文/キーワード/注釈位置を追加しない。
- 測度自動合成の汎用化拡張を行わない（四戦略は RFC-027 既定計画を維持、射程外はフォールバックへ）。
- RFC-009a と命題を聯合求解しない（それぞれ独立判定、バックエンドを共有）。
- 依存型レベルの全域性検証（totality checking）を行わない。
- ループの証明関数フォールバックを行わない：ループは匿名構造であり、`Terminates(f, m)`
  で指称するすべがなく、ループ計量変数は mut 局所量であって引数ではないため、証明関数の引数ミラー規則が失效する。範囲内ループは自動戦略を維持する——コンパイル時コードはコンパイラ自身が実行するコードであり、ハードラインは承重箇所に保持する。将来に実在のニーズがあれば、ループ注釈構文により別途子 RFC を立てる。
- 測度推論を実装しない（関数本体からの測度推測は戦略 1/2/4 の射程に属し、本 RFC は明示的測度のみを消費する——設計哲学末段の理論境界を参照）。
