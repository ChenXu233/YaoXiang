# RFC-029a: モジュールキャッシュと増分再コンパイル

## 要約

RFC-029「サブ RFC 計画」内で预留された 029a 行を履行する：安定済みのオーケストレータ（`compile_project`）の上に、コンパイラに**階層キャッシュと増分再コンパイル**を補う。中核は三層キャッシュモデル——プロセス内解析結果（L1）、セッション内モジュールレベル（L2）、プロセス間ディスク（L3）——に統一されたキーと無効化原則、強制的な計測フックを組み合わせ、現在互いに通じない四箇所のキャッシュ散在点（#251
P0-6 監査で発見）を収束させる。

## 動機

### ホストと境界の根拠

RFC-029（受理済み）は本テーマを自身の境界外として明確に切り出し、本サブ RFC のスロットを预留している：

> **含まない**：キャッシュ、ファイル監視、ホットリロード、増分再コンパイル、パッケージ間循環依存処理。——
> RFC-029 §中核原則

| サブ RFC | 能力                                   | 前提                 |
| -------- | -------------------------------------- | -------------------- |
| 029a     | モジュールキャッシュと増分再コンパイル | オーケストレータ安定 |

前提「オーケストレータ安定」はすでに満たされている：オーケストレータは RFC-029 履行とともに提供され、#232/#243/#244/#245 のデリバリー検証を経ている。

### 現状の問題（#251 P0-6 監査 + 2026-09-07 実証）

**キャッシュ散在点は互いに通じない**：

| 既存                                      | レイヤ         | 実際の消費側           | 問題                                                   |
| ----------------------------------------- | -------------- | ---------------------- | ------------------------------------------------------ |
| `VALIDATE_CACHE`（validate.rs）           | プロセス内     | formatter のみ         | CLI `check`/`run` とオーケストレータはどちらも通らない |
| Z3Backend クエリキャッシュ                | 検査セッション | 証明パイプライン       | 無効化ルールと予算設計なし（RFC-009a 一文のみ）        |
| `DocumentCache`（util/cache.rs、RFC-017） | LSP セッション | LSP                    | CLI コンパイル面と完全に通じない                       |
| `~/.yaoxiang/cache`（RFC-014）            | ディスク       | パッケージダウンロード | コンパイルと無関係                                     |
| コードキャッシュ（RFC-028）               | ランタイム     | JIT                    | コンパイル期レイヤではない                             |

**複数入口での全パイプライン重複（実証）**：

- `check_files_with_diagnostics` ループ内で**ファイル毎に新規
  `Compiler`**（`src/util/diagnostic/mod.rs`）：同プロセスで 19 のライブラリ層ファイルを検査すると、std 埋め込みチェーンが 19 回重複して typecheck される；
- runtime-error 類のテストファイルは `check` + `run`
  の二つの子プロセスを経由し、全パイプラインを二度行う；
- 借用検査 `fast_path_check` は書き込み操作毎に独立に全グラフ BFS を行い、結果キャッシュがない（#251
  P0-6 監査の原本発見、RFC-009a
  L611 には「一度の BFS 結果はキャッシュして同一トークンの複数クエリで再利用可能」という一文のみ、機構設計なし）。

### コスト解剖（--version ベースライン法、2026-09-07 実測）

| プローブ                            | 耗时   | 差分の意味                       |
| ----------------------------------- | ------ | -------------------------------- |
| `yaoxiang --version`                | ~50 ms | プロセス spawn + CLI 初期化      |
| 素の `check`（std インポートなし）  | ~60 ms | フロントエンドコンパイル ≈ 10 ms |
| `std.test` チェーンファイル `check` | ~80 ms | std チェーン埋め込み ≈ +20 ms    |

テスト回路 170 ファイル実測 9.8 s ≈ 58
ms/ファイル：**~85% はプロセスライフサイクルコスト、コンパイル自体は約 10
ms のみ、std チェーンはファイル毎に +20 ms**。これにより本 RFC の効果主戦場を定位する：

1. **同プロセス複数入口の再利用**（L1/L2）——重複するフロントエンドパイプラインと std チェーンコンパイルを撲滅；
2. **プロセス間 std チェーンの除去**（L3）——子プロセスモデル下で唯一合法的なキャッシュ効果経路；
3. プロセス spawn の ~50 ms/ファイルは**キャッシュの射程外**——子プロセス隔離は RFC-036
   §6 の設計選択であり、本 RFC は覆さない（非目標を参照）。

## 提案

### コア設計：三層キャッシュモデル

#### L1 プロセス内解析結果キャッシュ（ライフサイクル = 単一検査セッション）

- `validate_source`
  を**フロントエンド検証の唯一入口**として収編する：`check_files_with_diagnostics`、オーケストレータのファイル毎 typecheck、LSP 診断はすべてこれを経由する（現状は formatter のみが消費）；
- キー = FNV-1a 内容ハッシュ（validate.rs の既存実装）、値 = `ValidateResult`（診断 + AST）；
- 借用 BFS
  unsafe 集合キャッシュ：RFC-009a の設計文を履行、ライフサイクル = 単一関数検査セッション、#290/#292 借用検査実装と整合；
- Z3 クエリキャッシュ（RefCell + クエリハッシュ）を同一原則に収編し、無効化と予算の説明を補足。

#### L2 セッションモジュールレベルキャッシュ（ライフサイクル = 単一オーケストレーション）

- オーケストレータの Registry と各モジュールの検証結果を **(モジュールパス, 内容ハッシュ)**
  でキャッシュし、同プロセスの二回目の `compile_project` で直接ヒット；
- std 埋め込みソース（`yx_sources`
  include_str!）内容が恒定 → プロセス毎に一度コンパイルし、N 個のインポートファイルで共有；
- 無効化：本モジュールのソースハッシュ変化で即座に無効化；依存変化は `use`
  グラフに沿って伝播（第三波で履行）。

#### L3 プロセス間ディスクキャッシュ（ライフサイクル = ラン間）

- 位置 `~/.yaoxiang/cache/compile/`、RFC-014 ダウンロードキャッシュと同根異セグメント；
- キー =
  **(内容ハッシュ、コンパイラバージョン、意味設定フィンガープリント)**；産物はモジュールバイトコード（`BytecodeFile`
  マジックナンバー形式を再利用）；
- バージョンまたはフィンガープリントが不一致 = 全体 miss 再コンパイル——**モジュール間無効化伝播は行わない**（保守的なキー全体無効化）。

### キーと無効化の統一原則（#293 ギャップ 4）

- キー強度：内容ハッシュ > 構造ハッシュ > バージョン番号。L1/L2 は内容ハッシュ（ソースコードが即ち身元）、L3 はその上にコンパイラバージョンと設定フィンガープリントでガード；
- 無効化伝播は L2 依存グラフ内にのみ存在；L3 はキー全体無効化、モジュール間依存を追跡しない；
- **構築期拒否**：キーが揃わない（ハッシュ欠如/バージョン欠如）場合はキャッシュへの書き込みを拒否、miss になっても古い産物を残さない——診断 i18n の翻訳欠如でコンパイルを拒否する原則と同一。

### 計測フック（#289 整合）

```rust
pub struct CacheStats {
    pub hits: u64,
    pub misses: u64,
    pub cached_bytes: u64,
}
```

- `check --json` と `test --json` の summary に `cache` フィールドを付与（階層ヒット率）；
- **強制閾値：観測不可能なキャッシュはマージを許可しない**——「キャッシュされたが誰もヒットしない」という静かな腐敗を防止。

### 増分再コンパイル境界（#293 ギャップ 2）

- **ファイルレベルから着手**：`use`
  グラフに沿ってダーティファイルを判定し、ダーティファイルとその下流のみを再コンパイル；RFC-017 の LSP ファイルレベルキャッシュと統一的に進化（DocumentCache は L1+L2 の消費側へと移行、独立した体系ではなく）；
- **関数レベル増分は明確に行わない**（RFC-017 ですでに簡略化が宣言済み、数ミリ秒の全ファイル解析は増分化する価値がない）。

## 詳細設計

### RFC-029 オーケストレーションフローとの接続

```text
RFC-029 オーケストレーションフロー（履行済み）：

  ソースファイル発見 → Registry 構築 → ファイル毎 typecheck → 全体コンパイル

本 RFC 挿入点：

  ソースファイル発見 → [L2] パス+ハッシュで Registry/検証結果キャッシュ照会
                    ├─ ヒット → 再利用
                    └─ miss → 構築（かつ書き戻し）
  ファイル毎 typecheck → [L1] validate_source 唯一入口（内容ハッシュ照会/書き戻し）
  全体コンパイル → 産物 → [L3] シリアライズしてディスクに保存（バージョンガード付き）、次回プロセスで直接ロード
```

### テスト回路期待効果（定量化）

| シナリオ                                                    | 現状                        | 029a 後                  | 依存層 |
| ----------------------------------------------------------- | --------------------------- | ------------------------ | ------ |
| 同プロセスランナー（yx_runner モード）19 ライブラリファイル | std チェーン 19×20 ms       | 1×20 ms + 19 回ヒット    | L1+L2  |
| 子プロセスランナー（`yaoxiang test`）                       | std チェーン 20 ms/ファイル | ヒット後 ≈ 0             | L3     |
| 借用検査大関数                                              | O(V²) BFS                   | 単一セッション内で再利用 | L1     |
| プロセス spawn（ファイル毎 ~50 ms）                         | 変化なし                    | 変化なし（非目標）       | —      |

## 既存システムとの関係

- **RFC-029**：ホスト。029a はその「サブ RFC 計画」表の履行；
- **RFC-009a**：L611 設計文の機構化（BFS キャッシュ、L1 層）；
- **RFC-017**：DocumentCache は L1+L2 消費側として収編、キャッシュ戦略は単一ソースに；
- **RFC-014**：ディスクディレクトリ分担——`cache/` ダウンロードセグメント vs 本 RFC `cache/compile/`
  セグメント；
- **RFC-028**：JIT コードキャッシュはランタイム層、本 RFC の管轄外；
- **RFC-031**：最適化パスのスケジューリングは Pass 管理器の管轄；本 RFC がキャッシュするのは pass パイプラインの入出力、両者は直交；
- **RFC-036**：テスト子プロセス隔離モデルは維持、L3 はその唯一のプロセス間効果経路；
- **#251/#290/#292**：監査ソースと借用検査実装（BFS キャッシュ消費側）；
- **#289**：計測フックの観測可能性整合；
- **#247**：`use` 追跡発見（オンデマンド発見）は L2 依存グラフ上に重畳、純粋な性能最適化。

## 実施戦略

1. **第一波（履行すれば即座に効果）**：`validate_source`
   統一入口化（check/オーケストレータ/LSP 三消費側接続）、借用 BFS セッションキャッシュ、計測フックの最小版；
2. **第二波**：L2 セッションモジュールキャッシュ（std 埋め込み単一コンパイル + Registry 再利用）；
3. **第三波**：L3 ディスクキャッシュ（std 優先——埋め込みソース内容安定、ヒット率恒定）+ `use`
   グラフに沿ったファイルレベル増分再コンパイル + LSP キャッシュ統一。

## 非目標

- 関数レベル増分解析（RFC-017 既存裁決）；
- JIT / ランタイムキャッシュ（RFC-028）；
- テスト回路の子プロセス隔離の覆し（RFC-036 §6 設計選択）；
- パッケージ間無効化伝播（RFC-029 境界外）；
- プロセス spawn コスト最適化（キャッシュ議題ではない）。
