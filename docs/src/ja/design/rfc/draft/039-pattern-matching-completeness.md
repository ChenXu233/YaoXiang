# RFC-039: パターンマッチング完全化

## 概要

`match`
のパターンマッチングを、現在の「リテラルのみ + ワイルドカード」から完全な能力へと補完する:Union バリアントパターン(ペイロードバインディングを含む)、構造体/タプルパターン、Or パターンとガードの IR 着地、および網羅性チェック(E1030/E1031 を空のスタブから実際のコード生成コードへと転換)。本 RFC は
`Error { kind: ErrorKind, message }`
進化ロードマップ(RFC-013「ランタイムエラー値とコード貫通」進化セクション) の前置であるが、動機は独立している――パターンマッチングは汎用的な言語能力であり、変種を持つすべての型に奉仕する。

## 動機

### 現状の実証(2026-09-03、v0.7.12 コード)

1. **IR 層でリテラルのパターンのみが実在する**。AST は完全なパターン集合(`src/frontend/core/parser/ast.rs:578`:Wildcard
   / Identifier / Literal / Tuple / Struct / Union / Or / Guard)をすでに定義しており、パーサは
   `ok(v)`、`err(e)`
   などの変種パターンを解析可能(`Pattern::Union`)である。しかし、IR 生成(`src/middle/core/ir_gen.rs:5330`
   以降)は `Literal`
   分岐のみ実装しており、その他のパターンはスタブに落ちる――定数 0 をロードして等価比較に参加し、**決してマッチしない**;しかも scrutinee がちょうど 0 のときに**誤ってマッチ**してスタブアームに入ってしまう(潜在的な誤動作)。
2. **stdlib.md の `match ok(v)/err(e)` 例は紙の上の能力**。仕様文書(§1.3
   Result)が示す変種分解の書き方は実際には実行できない;`?`
   演算子の実装は match の脱糖を通らないため、これが覆い隠されている。テストコーパスには変種分解のユースケースがゼロ(`match.yx`
   / `pattern_matching.yx` はリテラルとワイルドカードのみをカバー)。
3. **網羅性チェックが空でぶら下がっている**。E1030(Pattern non-exhaustive)、E1031(Unreachable
   pattern)はコード表に登録されているが発行箇所がない――match セマンティクスがまだ定まっていない。
4. **エラー処理の進化がブロックされている**。ランタイム `Error` 値は現在 `{code, message}`
   の文字列コードを唯一のプログラマブル判定契約としている(RFC-013);構造化モデリング(`match e.kind { file_not_found(path) => ... }`)は本 RFC の変種分解とペイロードバインディングに依存している。

### 設計目標

- **変種分解が使える**:`match r { ok(v) => ..., err(e) => ... }`
  と、ユーザー定義の変種集合(レコード風 sum type)の分解が 3 つの実行パスで意味的に一貫している。
- **網羅性を信頼できる**:E1030/E1031 が実際に発行され、match の分岐漏れはコンパイルエラーとなる。
- **スタブの除去**：「0 をロードしてマッチしない/誤マッチする」というプレースホルダ動作を削除し、未対応のパターンはコンパイル時にエラーを報告し、誤ったパスに静かに進まないようにする。

## 提案(スケッチレベル、本文の充实を待つ)

| 能力                                    | 説明                                                                                                                                           |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Union バリアントパターン                | `VariantName` / `VariantName(binding)` によるマッチ + ペイロードの arm スコープへのバインディング                                              |
| Struct / Tuple パターン                 | フィールドパターン、タプルパターンの着地(AST は既存、IR を補完)                                                                                |
| Or パターンと Guard                     | `p1 \| p2` と `p if cond` の評価順序とバインディング規則                                                                                       |
| 網羅性チェック                          | E1030 の分岐漏れ、E1031 の到達不能、対象範囲は変種集合(Result/Option は現在 core 所属;判定は所属に依存しない、RFC-011b フェーズ 2 で std 移行) |
| Identifier パターンのセマンティクス確認 | 現状の構文における裸の識別子がバインディングなのか変種比較なのか、決定が必要(ワイルドカード `_` との関係)                                      |

### オープンな問題

- [ ] Identifier パターン:新しい変数をバインドするのか、それとも既存の値とマッチするのか?(Rust セマンティクス vs 既存の YaoXiang コーパス挙動)
- [ ] 網羅性の適用境界:動的インポート/インターフェースメソッドが返す変種集合はどのように網羅性判定に参加するのか?
- [ ] non_exhaustive のような属性が必要か(将来の std 変種集合拡張がユーザーの match を破壊する範囲に影響)?
- [ ] 修正前の過渡期において、スタブの 0 ロード誤マッチをまずコンパイルエラーとして報告するか?
