# RFC-039: パターン照合の完全化

## 概要

`match`
のパターン照合を、現在の「リテラルのみ + ワイルドカード」から完全な能力へと補完する：Union バリアントパターン（ペイロード束縛を含む）、構造体/タプルパターン、Or パターンとガードの IR 着地、および網羅性検査（E1030/E1031 を空の保留コードから実発火コードへ）。本 RFC は
`Error { kind: ErrorKind, message }`
進化路線（RFC-013「ランタイムエラー値とコード貫通」進化節）の前置であるが、動機は独立している——パターン照合は汎用的な言語能力であり、バリアントを持つすべての型に資するものである。

## 動機

### 現状の実証（2026-09-03、v0.7.12 コード）

1. **IR 層ではリテラルのパターンのみが実在する**。AST は完全なパターン集合を定義済み（`src/frontend/core/parser/ast.rs:578`：Wildcard
   / Identifier / Literal / Tuple / Struct / Union / Or / Guard）であり、パーサは `ok(v)`、`err(e)`
   類のバリアントパターン（`Pattern::Union`）を解析できる；しかし IR 生成（`src/middle/core/ir_gen.rs:5330`
   以降）は `Literal`
   分岐のみを実装し、その他のパターンはスタブに落ちる——定数 0 をロードして等価比較に参加し、**決してマッチしない**；しかも scrutinee がちょうど 0 の場合、スタブ arm に**誤マッチ**する（潜在的な誤動作）。
2. **stdlib.md の `match ok(v)/err(e)` 例は机上だけの能力である**。規範文書（§1.3
   Result）が示すバリアント分解の書き方は実際には実行できない；`?`
   演算子の実装は match の脱糖を経由しないため、この点が覆い隠されている。テストコーパスにはバリアント分解の用例がゼロである（`match.yx`
   / `pattern_matching.yx` はリテラルとワイルドカードのみをカバーする）。
3. **網羅性検査が空で保留されている**。E1030（Pattern non-exhaustive）、E1031（Unreachable
   pattern）はコード表に登録されているが、発火点がない——match のセマンティクスが未確定である。
4. **エラー処理の進化がブロックされている**。ランタイムの `Error` 値は現在 `{code, message}`
   の文字列コードを唯一のプログラマブルな判定契約としている（RFC-013）；構造化モデリング（`match e.kind { file_not_found(path) => ... }`）は本 RFC のバリアント分解とペイロード束縛に依存する。

### 設計目標

- **バリアント分解が利用可能**：`match r { ok(v) => ..., err(e) => ... }`
  とユーザー定義バリアント集合（レコード風 sum
  type）の分解が、3 つの実行パスでセマンティクスが一致する。
- **網羅性に依存可能**：E1030/E1031 が実際に発火し、match の分岐漏れはコンパイルエラーとなる。
- **スタブの除去**：「0 をロードして決してマッチしない/誤マッチする」というプレースホルダ動作を削除し、未対応パターンは静かに誤動作するのではなくコンパイル時にエラーとする。

## 提案（骨格レベル、本文充实待ち）

| 能力                                    | 説明                                                                                          |
| --------------------------------------- | --------------------------------------------------------------------------------------------- |
| Union バリアントパターン                | `VariantName` / `VariantName(binding)` のマッチ + ペイロードの arm スコープへの束縛           |
| Struct / Tuple パターン                 | フィールドパターン、タプルパターンの着地（AST 既存、IR で補完）                               |
| Or パターンと Guard                     | `p1 \| p2` と `p if cond` の評価順序と束縛規則                                                |
| 網羅性検査                              | E1030 分岐漏れ、E1031 到達不能、スコープはバリアント集合をカバー（組込 Result/Option を含む） |
| Identifier パターンのセマンティクス確定 | 現構文中の裸の識別子が束縛かバリアント比較か、定案が必要（ワイルドカード `_` との関係）       |

### 開放的な問題

- [ ] Identifier パターン：新しい変数を束縛するのか、既存の値にマッチするのか？（Rust のセマンティクス vs 既存の YaoXiang コーパスの挙動）
- [ ] 網羅性の適用境界：動的インポート/インタフェースメソッドが返すバリアント集合は、網羅性判定にどう参加するか？
- [ ] non_exhaustive 類の属性は必要か（std のバリアント集合拡張がユーザーの match に与える破壊半径に影響する）？
- [ ] 修正前の過渡期において、スタブの 0 ロード誤マッチをまずコンパイルエラーとして報告するか？

## 関連
