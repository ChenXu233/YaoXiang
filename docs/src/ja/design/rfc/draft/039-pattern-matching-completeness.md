# RFC-039: パターンマッチングの完全化

## 概要

`match`
のパターンマッチングを現在の「リテラル + ワイルドカードのみ」から完全な能力へと補完する：Union バリアントパターン（ペイロードバインディングを含む）、構造体/タプルパターン、Or パターンとガードの IR への実装、および網羅性検査（E1030/E1031 を空コードから実発行へと転換）。本 RFC は
`Error { kind: ErrorKind, message }`
進化路線（RFC-013「ランタイムエラー値とコード貫通」進化節）の前提となるが、動機は独立している——パターンマッチングは汎用的な言語能力であり、バリアントを持つすべての型に役立つ。

## 動機

### 現状の実証（2026-09-03、v0.7.12 コード）

1. **IR 層ではリテラルのパターンのみが実在する**。AST は完全なパターン集合（`src/frontend/core/parser/ast.rs:578`：Wildcard
   / Identifier / Literal / Tuple / Struct / Union / Or / Guard）を定義しており、パーサは
   `ok(v)`、`err(e)`
   のようなバリアントパターン（`Pattern::Union`）を解析可能である。しかし IR 生成（`src/middle/core/ir_gen.rs:5330`
   以降）は `Literal`
   分岐のみを実装しており、残りのパターンはスタブに落ちる——定数 0 をロードして等価比較に参加するだけで、**永遠にマッチしない**；しかも scrutinee がちょうど 0 の場合、**誤マッチ**してスタブアームに入ってしまう（潜在的な誤動作）。

2. **stdlib.md の `match ok(v)/err(e)` 例は紙の上の能力である**。仕様文書（§1.3
   Result）が示すバリアント分解の書き方は実際には動作しない；`?`
   演算子の実装は match の脱糖を経由しないため、この点が覆い隠されている。テストコーパスにはバリアント分解の用例がゼロである（`match.yx`
   / `pattern_matching.yx` はリテラルとワイルドカードのみをカバー）。

3. **網羅性検査が空である**。E1030（Pattern non-exhaustive）、E1031（Unreachable
   pattern）はコード表に登録されているが発行ポイントがない——match のセマンティクスが定まっていない。

4. **エラー処理の進化がブロックされている**。ランタイムの `Error` 値は現在、`{code, message}`
   文字列コードを唯一のプログラマブルな判定契約（RFC-013）としている；構造化モデリング（`match e.kind { file_not_found(path) => ... }`）は本 RFC のバリアント分解とペイロードバインディングに依存している。

### 設計目標

- **バリアント分解が使える**：`match r { ok(v) => ..., err(e) => ... }`
  とユーザー定義のバリアント集合（レコード風の直和型）の分解が 3 つの実行パスで意味的に一貫している。
- **網羅性に依存できる**：E1030/E1031 が実際に発行され、match の分岐漏れはコンパイルエラーになる。
- **スタブを除去する**：「0 をロードしてマッチしない/誤マッチする」というプレースホルダ動作を削除し、未対応パターンはコンパイル時にエラーを報告する。黙って誤った動作に進むことを許さない。

## 提案（骨子レベル、本文の充実待ち）

| 能力                                    | 説明                                                                                                        |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Union バリアントパターン                | `VariantName` / `VariantName(binding)` のマッチ + ペイロードバインディングを arm のスコープへ               |
| Struct / Tuple パターン                 | フィールドパターン、タプルパターンの実装（AST 既存、IR を補完）                                             |
| Or パターンと Guard                     | `p1 \| p2` と `p if cond` の評価順序とバインディング規則                                                    |
| 網羅性検査                              | E1030 分岐漏れ、E1031 到達不能、対象はバリアント集合をカバー（組み込み Result/Option を含む）               |
| Identifier パターンのセマンティクス確認 | 現在の構文で裸の識別子がバインディングなのかバリアント比較なのか、確定が必要（ワイルドカード `_` との関係） |

### オープン問題

- [ ] Identifier パターン：新しい変数をバインドするのか、既存の値とマッチするのか？（Rust のセマンティクス vs 既存の YaoXiang コーパスの挙動）
- [ ] 網羅性の適用境界：動的インポート/インターフェースメソッドが返すバリアント集合はどのように網羅性判定に参加するのか？
- [ ] non_exhaustive のような属性が必要か（std のバリアント集合拡張がユーザーの match に与える破壊半径に影響）？
- [ ] 修正前の過渡期において、スタブの 0 ロード誤マッチをまずコンパイルエラーとして報告するか？
