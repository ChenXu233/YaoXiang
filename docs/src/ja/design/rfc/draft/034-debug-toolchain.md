# RFC-034: 統一デバッグツールチェーン

## 概要

YaoXiang に統一デバッグツールチェーンを導入する。核心的な設計は**一箇所からの生成、三種類の利用**：コンパイルフロントエンドがソースコードの位置、変数名、型情報を一等市民として YaoXiang IR に埋め込み、インタープリタ、JIT、LLVM の3つのバックエンドが同じメタデータを消費する。ユーザーが `yaoxiang run --debug` で DAP（Debug Adapter Protocol）サーバーを起動し、VS Code が stdio 経由で接続することで、ブレークポイント、ステップ実行、変数検査、コールスタック、式評価、並行デバッグの統一体験を得る——底層の実行エンジンがどれであっても。

## 動機

### なぜこの機能が必要なのか

現在 YaoXiang プログラムの錯誤を排查する手段は非常に原始的である：

```yaoxiang
io.println("DEBUG: x = " + x.to_string())
io.println("DEBUG: entered branch A")
```

3つの致命的な問題がある：

1. **コンパイラ開発のセルフホストが阻害**：YaoXiang で YaoXiang コンパイラを書くが、コンパイラを書く 사람은自分が書いたコードをデバッグできない。セルフホスト段階での対話的デバッグ手段の欠如は袋小路である。
2. **3つのエンジン、ゼロデバッグ**：インタープリタ、JIT、LLVM はそれぞれ独立して実行し、問題が発生した場合はユーザーが stdout に `ALL TESTS PASSED` が表示されるかどうかを確認するしかない。アサーション失敗？何行目か、変数の値は何か分からない。
3. **並行はブラックボックス**：`spawn` で複数のタスクを作成したが、どのタスクが落ちた？変数は誰に move された？全是的に推測するしかない。

### 設計目標

- **統一体験**：インタープリタで止まるブレークポイントは、JIT でも止まり、LLVM でも一貫したソースコードマッピングが得られる。ユーザーは底層のエンジン差異を意識しなくてよい。
- **一箇所からの生成**：デバッグメタデータが IR と共に流れ、繰り返し定義せず、2つのマッピングを維持する必要がない。
- **非侵入**：`yaoxiang run --debug` 一つのパラメータで、このパラメータを追加しない場合はコンパイルと実行の動作が完全に変わらない。
- **DAP 標準**：VS Code エコシステムに直接接続し、エディタプロトコルを再発明しない。

## 提案

### 核心的な設計

アーキテクチャ概要：

```
┌──────────────────────────────────────────────────────┐
│                    VS Code / エディター                │
│              DAP Client (launch.json)                 │
└────────────────────────┬─────────────────────────────┘
                         │ stdio
┌────────────────────────▼─────────────────────────────┐
│                 DAP サーバー (yx-core)                   │
│  ┌─────────┐  ┌──────────┐  ┌───────────────────┐    │
│  │ セッション管理 │  │ ブレークポイント管理  │  │ 式評価エンジン     │    │
│  └─────────┘  └──────────┘  └───────────────────┘    │
└────────────────────────┬─────────────────────────────┘
                         │ クエリ/制御
┌────────────────────────▼─────────────────────────────┐
│                  ランタイムデバッグインターフェース (trait)                 │
│  pause / resume / step / get_frames / eval / ...    │
└────┬──────────────────┬──────────────────┬──────────┘
     │                  │                  │
┌────▼────┐    ┌───────▼───────┐    ┌─────▼──────┐
│ インタープリタ   │    │ JIT (RFC-028)│    │ LLVM AOT   │
│ IRメタデータを直接消費  │    │ 軽量デバッグ表を生成     │    │ IRメタデータ    │
│       │    │     │    │ → DWARF   │
└─────────┘    └───────────────┘    └────────────┘
```

**重要な設計上の決定事項**：

1. **DAP サーバーとランタイムは trait で分離**。サーバーは底層がインタープリタか JIT かを関知しない——`DebugEngine` trait を介して命令を送信するのみ。各エンジンが同じ trait を独立して実装する。
2. **`yaoxiang run --debug` はインタープリタの使用を強制**。デバッグには制御可能性が必要で、性能は不要。LLVM モードでは DWARF を生成して事後遡及（core dump / crash report）に使用し、対話的デバッグは行わない。
3. **`yaoxiang run` から入口検出ロジックを再利用**。新しいサブコマンドを導入せず、心智モデルは「デバッグモードでプログラムを実行する」のみ。

### IR デバッグメタデータ

既存の YaoXiang IR にメタデータを付加し、新しい IR 種を追加しない。すべてのメタデータは**コンパイルフロントエンド**の一箇所で生成され、バックエンドの消費は読み取り専用である：

| メタデータ           | 付着点            | 説明                         |
| ---------------- | ----------------- | ---------------------------- |
| `SourceLocation` | 各 IR ノード      | ソースファイル:行番号:列番号             |
| `VarName`        | 変数宣言/束縛ノード | ソースコード内の変数名               |
| `TypeAnnotation` | 変数/式ノード   | 推論された型（コンパイル時述語を含む） |
| `ScopeBoundary`  | ブロック/関数入口出口   | 変数スコープのライフサイクル         |
| `SpanInfo`       | spawn ノード        | spawn ブロック内のタスク境界           |

### 起動フロー

```
yaoxiang run --debug file.yx
    │
    ├── Phase 1: コンパイル（デバッグメタデータ付き）
    │   ├── 解析 → AST
    │   ├── 型チェック + コンパイル時述語検証
    │   └── IR への降級（デバッグメタデータ付加）
    │
    ├── Phase 2: インタープリタエンジンの使用
    │   └── --debug モードでは --release に関わらず、インタープリタを使用
    │
    ├── Phase 3: DAP サーバーの起動
    │   ├── stdio 転送チャネルの初期化
    │   ├── VS Code attach を待機
    │   ├── attach 成功後、プログラム入口で一時停止
    │   └── 対話デバッグループへ移行
    │
    └── Phase 4: プログラム終了 / デバッグセッション終了 → 終了
```

### 各モードの違い

| モード                     | デバッグ方法                                                         |
| ------------------------ | ---------------------------------------------------------------- |
| `yaoxiang run --debug`   | インタープリタ強制、全機能 DAP 対話デバッグ                                  |
| `yaoxiang run --release` | DWARF 生成、事後遡及用（core dump / crash report）、DAP 起動なし |
| `yaoxiang run`（通常）   | デバッグメタデータなし、デバッグサポートなし                                         |

## 詳細な設計

### 1. ブレークポイント

```
ブレークポイント種類：
├── ソースコード行ブレークポイント    → コンパイルフロントエンドが位置メタデータを生成、バックエンドがクエリしてマッチ
├── 関数入口ブレークポイント  → 関数呼び出し時にトリガー（第二段階）
├── 条件ブレークポイント      → 式評価が true の時にトリガー
└── データブレークポイント      → 変数が変更された時にトリガー（第二段階）
```

**ソースコード行ブレークポイントの中核ロジック**：

```
VS Code が送信: "file.yx:42 にブレークポイントを設定"
    │
DAP サーバー:
    ├── IR 中の SourceLocation == (file.yx, 42) の全ノードをクエリ
    ├── ランタイムに転送: "これらの IR アドレスで一時停止"
    └── ランタイムが返答: ブレークポイント ID

プログラムが IR ノードに到達 → ランタイムがチェック: このノードはブレークポイントリストにあるか？
    ├── 通常ブレークポイント → 一時停止、DAP サーバーに通知
    └── 条件ブレークポイント → 条件式を評価 → true のみ一時停止
```

**3つのエンジン実装**：

|              | インタープリタ                    | JIT                     | LLVM                       |
| ------------ | ------------------------- | ----------------------- | -------------------------- |
| ブレークポイント挿入方式 | 実行ループ中で IR ノード ID をチェック | JIT がマシンコードに `int3` を挿入 | LLVM DWARF + ハードウェアブレークポイントを利用 |
| 条件ブレークポイント評価 | 式を直接解釈                | 条件式を一時 JIT コンパイル | DWARF 式スタック + 評価      |
| 性能オーバーヘッド     | 各 IR ノードでテーブル参照が1回増    | ブレークポイント箇所のみオーバーヘッド          | ほぼゼロオーバーヘッド（ハードウェアブレークポイント）     |

### 2. ステップ実行

```
Step Over    → 現在の行を実行、関数呼び出し内部をスキップして次の行で停止
Step Into    → 現在の行の関数呼び出し内部に入る
Step Out     → 現在の関数が戻るまで実行
Continue     → 次のブレークポイントまたはプログラム終了まで実行を再開
```

**実装ロジック**：ステップ操作は本質的に**一時的なブレークポイント**である。ユーザーが明示的に設定したブレークポイントと同じ機構を共有し、2つのシステムではなく、1つのシステムの2つの使用方法である。

```
Step Over:
    現在のソースコード行番号 = query_line(frame)
    → 次の行に一時ブレークポイントを設定
    → 現在の行が関数呼び出しの場合: 呼び出し点の後に一時ブレークポイントを設定
    → Continue → 一時ブレークポイントにヒット → 削除 → 一時停止

Step Into:
    現在の呼び出し対象の最初の行の実行可能位置
    → 関数本体の最初の IR ノードのソースコード位置を見つける
    → 一時ブレークポイントを設定 → Continue → ヒット → 一時停止

Step Out:
    現在のスタックフレームの戻りアドレス
    → caller の次の行を見つける
    → 一時ブレークポイントを設定 → Continue → ヒット → 一時停止
```

**一時ブレークポイントの4つのエッジケース処理**：

1. **並行帰属**：一時ブレークポイントは現在のタスク ID にバインドされ、他のタスクがヒットした場合は直接無視される。
2. **spawn ブロックの Step Over**：spawn 外部で Step Over すると spawn ブロック全体を跑了し、その後へジャンプする。spawn 内部に入ってデバッグするには Step Into を使用する。
3. **一時ブレークポイント未ヒット**：看門狗タイムアウト（30秒間ブレークポイントヒットなし）→ 強制一時停止 → VS Code に通知。同時にプログラム終了イベントをリスン → 即座にクリーンアップ。
4. **同一行に複数の IR ノード**：Step Over の一時ブレークポイントは `ignore_current_line` をマークし、ヒット後にソースコード行番号が現在の行番号と等しい場合は → 無視して続行。

### 3. 変数の検査とスコープ

```
VS Code が要求: "現在のフレームの変数リスト"
    │
DAP サーバー:
    ├── 現在の一時停止点の IR ノードをクエリ
    ├── 現在の ScopeBoundary 内の変数束縛を走査
    │   └── 各束縛について返す: (名前, 型, ランタイム値参照)
    └── VariablesResponse をアセンブル → VS Code
```

**スコープの階層化**：

```
┌─ Globals ───────────────────────────┐
│  モジュールレベル束縛: 定数、型エイリアス、グローバル   │
├─ Locals ────────────────────────────┤
│  現在の関数内で可視のローカル変数           │
│  ├── 引数 (関数パラメータ)                │
│  └── ローカル束縛 (let / 代入)          │
├─ Captured ──────────────────────────┤
│  spawn ブロック / クロージャがキャプチャした外部変数      │
│  所有権状態を表示: move済み / ref 共有  │
└────────────────────────────────────┘
```

**エンジン差異**：

| エンジン   | 変数値の取得                                                       |
| ------ | ---------------------------------------------------------------- |
| インタープリタ | VM スタックフレームとヒープを直接読む。各値はメモリにはっきりした表現がある                     |
| JIT    | レジスタとスタック上の値 → JIT コンパイル時に「変数 → レジスタ/スタックスロット」マッピングテーブルを記録する必要がある |
| LLVM   | DWARF の `.debug_info` セクション → `DW_AT_location` → LLDB がネイティブサポート     |

**特殊型の表示**：コンパイル時述語が精化された型はデバッグに価値のある情報を表示する：

```
x: Positive(x)  →  表示 "Int (x > 0 = True)"
y: Sorted(y)    →  表示 "Array(Int) (ソート保証)"
result: T       →  ランタイムの具体的な型を表示
```

### 4. コールスタック

```
DAP 要求: StackTrace
    │
返答:
┌──────────────────────────────────┐
│ #0  process_item()  file.yx:42  │  ← 現在の一時停止点
│     locals: item = "hello"       │
│     spawn タスク ID: task-3        │
├──────────────────────────────────┤
│ #1  main()          file.yx:67  │  ← caller
│     locals: data = ["hello", ...]│
├──────────────────────────────────┤
│ #2  <entry>         file.yx:1   │  ← ルート
└──────────────────────────────────┘
```

各フレームは記録する：関数シグネチャ、呼び出し位置（ソースファイル+行番号）、ローカル変数（遅延評価）、spawn コンテキスト（タスク ID）。

インタープリタと JIT はそれぞれフレームリンクリストを維持する。フレームはゼロコストで取得できるものではない——しかしデバッグモードはゼロオーバーヘッドを追求しない。

### 5. 式評価（Watch / REPL）

ユーザーがブレークポイントで任意の YaoXiang 式を入力する：

```
Watch: x + y         → 計算結果を返す
Watch: items[2].name → 複雑な構造にアクセス
Watch: f(x)          → 関数を呼び出す（副作用リスクあり）
```

**評価戦略**：

```
ユーザー入力式
    │
├── コンパイラフロントエンドが式を解析
├── 現在のフレームコンテキストで型チェック
├── 変数値を現在のフレームから取得（読み取り専用参照）
├── 式を独立したマイクロプログラムとして実行
│   └── 外部変数の変更は不允许
│   └── spawn は不允许
│   └── IO は不允许（またはオプションで有効）
└── 結果値を返す → 元のフレーム状態は完全に不变
```

**インタープリタは天然サンドボックス**：式評価は新しいサンドボックスを作成するのではなく——インタープリタ本身就是サンドボックスである。式評価只是一時的にフレームを push し、使用后就销毁。通常の実行と同じ VM と共有するが、副作用をコミットしない。

**関数呼び出しの評価**：デフォルトで許可するが、ユーザーに「この式には副作用がある可能性があります」と警告し、ユーザーの確認後に実行する。

**エンジン差異**：

| エンジン   | 式評価                                          |
| ------ | --------------------------------------------------- |
| インタープリタ | 既存の eval コードパスを再利用、現在フレーム環境を注入              |
| JIT    | 式を一時コンパイル → 現在のフレームにリンク → 実行 → 臨時代碼を破棄 |
| LLVM   | サポート外——LLVM モードでは対話デバッグを行わない                       |

### 6. 並行デバッグ

**タスクモデルの可視性**：

DAP の `threads` コンセプトは YaoXiang の `spawn` タスクにマッピングされる。各タスクは独自のスタックフレームリンクリストと実行状態を持つ。

```
┌─ Threads ───────────────────────────┐
│  ● task-1  main()     file.yx:10   │ ← 現在フォーカス中
│  ▶ task-2  fetch()    file.yx:34   │ ← 実行中
│  ⏸ task-3  process()  file.yx:56   │ ← ブレークポイントで一時停止
│  ◼ task-4  write()    終了済み         │
└────────────────────────────────────┘
```

**並行コンテキストでのブレークポイント**：

| 一時停止モード           | 動作                        | 適用シナリオ               |
| ------------------ | --------------------------- | ---------------------- |
| `stop-all`（デフォルト） | 1つのタスクがヒット → 全タスク一時停止 | データ競合、グローバル状態のデバッグ |
| `stop-this-only`   | ヒットしたタスクのみ一時停止、他は続行    | 独立タスクロジックのデバッグ       |

**spawn ブロックのステップセマンティクス**：

```
spawn {          // Step Over → spawn ブロック全体を跑了
    task_a()     // Step Into → task_a に入る
    task_b()     // 並列実行、個別の step の影響を受けない
}
```

### 7. DAP プロトコルマッピング

#### 第一段階：コア要求

| DAP 要求            | YaoXiang セマンティクス                                         |
| ------------------- | ----------------------------------------------------- |
| `initialize`        | 能力ネゴシエーション：ブレークポイント、ステップ、変数、スタックフレームをサポート                  |
| `launch` / `attach` | YaoXiang プログラムの起動/アタッチ（`--debug` は attach モード） |
| `setBreakpoints`    | ソースコード行ブレークポイントの設定                                        |
| `configurationDone` | ブレークポイント準備完了、実行開始                                    |
| `threads`           | 全アクティブ spawn タスクリストを返す                           |
| `stackTrace`        | 指定タスクのスタックフレームリストを返す                                |
| `scopes`            | 現在フレームの変数スコープを返す                                |
| `variables`         | 指定スコープの変数リストを返す                              |
| `continue`          | 実行を再開                                              |
| `next`              | Step Over                                             |
| `stepIn`            | Step Into                                             |
| `stepOut`           | Step Out                                              |
| `pause`             | 全タスクを中断                                              |
| `evaluate`          | 現在フレームで式を評価                                        |
| `disconnect`        | デバッグセッションを終了                                          |

#### 第二段階：拡張要求

| DAP 要求                  | YaoXiang セマンティクス            |
| ------------------------- | ------------------------ |
| `setFunctionBreakpoints`  | 関数名ブレークポイント               |
| `setExceptionBreakpoints` | エラー/panic 時に一時停止        |
| `dataBreakpointInfo`      | データブレークポイント（変数変更トリガー） |

## 実装策略

### フェーズゼロ：インフラ（前置き）

**目標**：コンパイルフロントエンドがデバッグメタデータを IR に付加する。

| コンポーネント        | 改动                                                            |
| ----------- | --------------------------------------------------------------- |
| IR 定義     | `SourceLocation`、`VarName`、`TypeAnnotation` などのメタデータフィールドを追加 |
| Parser      | 各 AST ノードにソースコード位置を記録                                       |
| TypeChecker | 型情報を IR ノードに付着                                          |
| テスト        | IR dump が位置と変数情報を含むことを検証                                 |

**ランタイムは涉及しない。**

**實施進捗（2026-09-17）**：

| 交付項目 | ステータス | 實施形態 |
| --- | --- | --- |
| ソースコード位置 | 完了 | 全76個の `Instruction` バリアントが `span` フィールドを持つ；`span()` メソッドは意図的にワイルドカードアームを設定せず新的バリアントが span を漏らすとコンパイル失敗。位置は40/41命令をカバー |
| 変数名 | 完了 | `LocalSlot { name, ty, scope_depth }` が `FunctionBody::Code::locals` に所属；`register_local` は生成期に就地書き込む。`.42` デバッグセクション v2 が名前を持ち、v1 成果物は後方互換で読み取り可能。 |
| グローバルスロット名 | 完了 | `.42` デバッグセクション v3 が「スロット番号 → トップレベル束縛名」テーブルを持つ。トップレベル束縛は `Operand::Global` を経由し任何の関数のローカル名テーブルになく、このテーブルがなければ数値でしか報告できず変数名を報告できない。v1/v2 成果物は空テーブルで読み取りを補完 |
| 型情報 | 部分 | スロットには `ty` が含まれる；`TypeAnnotation` 独立メタデータは未実装 |
| dump 可視性 | 完了 | `dump` が命令ごとに `; <file>:<line>:<col>` を出力し、`locals: 名前@スロット` をリスト |

上記のテーブルに實施されたデータ形態はフェーズ一と直接接続：DAP のブレークポイント解決は `debug_map` を消費し、変数パネルは `local_names`（名前）と `locals`（型）を消費する。

### 第一段階：インタープリタ DAP MVP

**目標**：`yaoxiang run --debug file.yx` でブレークポイント設定、ステップ実行、変数検査が可能。

| コンポーネント                        | 改动                                                                             |
| --------------------------- | -------------------------------------------------------------------------------- |
| DAP サーバー (yx-core 新モジュール) | stdio 転送層、コアループ要求処理、ブレークポイントマネージャー（ソースコード行 → IR ノードマッピング）                   |
| ランタイムデバッグ trait (yx-core)  | `DebugEngine` trait 定義（pause, resume, step, get_frames, eval, get_variables） |
| インタープリタ                      | 実行ループ中断ブレークポイントチェック、一時停止/再開機構、フレームリンクリスト維持、`InterpreterDebugEngine` 実装     |
| CLI                         | `yaoxiang run --debug` パラメータ                                                    |

**受入基準**：`tests/yaoxiang/` 下の任意の `.yx` ファイルに対して、VS Code でブレークポイント設定、Step Over、変数値の検査が可能。

### 第二段階：高度なデバッグ能力

**目標**：式評価、関数ブレークポイント、並行デバッグ、例外ブレークポイント。

| コンポーネント           | 改动                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| 式評価エンジン | マイクロプログラムコンパイル（parser + typechecker の再利用）、一時フレームの VM への push、副作用分離      |
| 並行デバッグ       | spawn タスクリストマッピング、ブレークポイントのタスク ID バインディング、stop-all / stop-this-only 一時停止戦略 |
| 関数/例外ブレークポイント  | `setFunctionBreakpoints`、`setExceptionBreakpoints` マッピング                |
| VS Code 拡張   | デフォルトの `launch.json` テンプレートを提供                                           |

### 第三段階：JIT デバッグ & LLVM DWARF

**目標**：JIT エンジンが DAP を再利用し、LLVM が DWARF を生成してクラッシュ遡及に使用。

| コンポーネント | 改动                                                                                |
| ---- | ----------------------------------------------------------------------------------- |
| JIT  | `DebugEngine` trait の実装、コンパイル時に変数→レジスタマッピングテーブルを生成、ランタイムフレームリンクリスト、式の一時コンパイル |
| LLVM | IR デバッグメタデータ → LLVM `DILocation` / `DISubprogram` → DWARF（DAP 対話なし）           |

```

    ↓
フェーズ一（インタープリタ DAP MVP）  ← ここから使用可能
    ↓

    ↓

```

### リスク

| リスク                     | 緩和                                                                  |
| ------------------------ | --------------------------------------------------------------------- |
| インタープリタ一時停止機構の複雑さ   | 複雑な状態機械ではなくシンプルな channel/signal を使用、一時停止は fetch の次の命令を阻止するだけ |
| 式評価の型安全性     | 既存の typechecker を再利用、読み取り専用参照、副作用をコミットしない                          |
| DAP プロトコルの詳細             | debugpy / delve の実装を参照、プロトコルは成熟している                             |
| 並行デバッグの stop-all ロック | タイムアウト機構 + 強制一時停止                                                   |

## トレードオフ

### メリット

- **一箇所からの生成**：デバッグメタデータは1回のみ生成され、3つのエンジンが共有。「インタープリタのデバッグ情報は正しいが LLVM のそれは間違っている」という情况不会出现
- **非侵入**：`--debug` 一つのパラメータで、このパラメータを追加しない場合の動作が完全に変わらない
- **DAP 標準**：VS Code エコシステムに直接接続し、カスタムエディタプロトコルやデバッガ UI を必要としない
- **インタープリタ優先**：デバッグは本質的にインタープリタに適している——柔軟性、制御可能性、式評価がシンプル。LLVM モードで対話デバッグを行わないのは最も現実的な選択

### デメリット

- **デバッグモードの性能が悪い**：インタープリタは JIT/LLVM より大幅に遅い。しかしデバッグには性能が不要——誰もデバッグモードで本番ワークロードを走らせることを期待しない
- **LLVM デバッグが制限される**：AOT コンパイルでは対話デバッグできず、GDB/LLDB + DWARF のみ使用可能。ただしこれはトレードオフ：LLVM モードではそもそもデバッグ動作の違いが存在しないべき
- **並行一時停止の複雑さ**：stop-all セマンティクスのインタープリタ実装は全アクティブタスクを走査する必要がある

### 代替案

| 案                           | 为什么不選択                                                       |
| ------------------------------ | ------------------------------------------------------------------ |
| 3つのエンジンがそれぞれ DAP を実装           | 3倍の作業、3套のバグ。「良い趣味」に違反                                   |
| DWARF のみ使用、自前の DAP なし       | インタープリタと JIT には DWARF の概念がなく、LLDB は VM 内部に入れない                  |
| Python pdb のようなコマンドラインデバッガ | VS Code 体験はコマンドラインデバッガを圧倒する                                       |
| DAP を LSP プロセスに押し込む           | ライフサイクルが完全に異なる——LSP はプロジェクトに付随し、DAP はデバッグセッションに付随。プロセス分離はハード要件 |
