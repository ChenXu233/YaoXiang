# RFC-034: 統一デバッガツールチェーン

## 概要

YaoXiang に統一されたデバッガツールチェーンを導入する。中心となる設計は**一つのソース、三つのコンシューマ**：コンパイルフロントエンドがソース位置、変数名、型情報を YaoXiang
IR に第一級市民として埋め込み、インタプリタ、JIT、LLVM の三つのバックエンドが同一のメタデータをそれぞれ消費する。ユーザーは
`yaoxiang run --debug` で DAP（Debug Adapter Protocol）サーバを起動し、VS
Code が stdio 経由で接続する。これにより、ブレークポイント、ステップ実行、変数表示、コールスタック、式評価、並行デバッグを、基盤となる実行エンジンの種類を問わず統一的に体験できる。

## 動機

### なぜこの機能が必要か

現在の YaoXiang プログラムのエラーを調査する手段は非常に原始的である：

```yaoxiang
io.println("DEBUG: x = " + x.to_string())
io.println("DEBUG: entered branch A")
```

致命的な問題が三つある：

1. **コンパイラのセルフホスティングが阻害される**：YaoXiang で YaoXiang コンパイラを書いているが、コンパイラを書く人が自分のコードをデバッグできない。セルフホスティング段階で対話的なデバッグ手段が欠如しているのは行き詰まりである。
2. **三つのエンジン、ゼロのデバッグ**：インタプリタ、JIT、LLVM がそれぞれ独立して動作し、問題が起きた場合ユーザーは
   `ALL TESTS PASSED`
   が stdout に出力されたかを確認するしかない。アサーション失敗？どの行か、変数の値は何かが分からない。
3. **並行処理はブラックボックス**：`spawn`
   で複数のタスクが作成されるが、どのタスクが停止したか？変数が誰に move されたか？すべて運に頼って推測するしかない。

### 設計目標

- **統一された体験**：インタプリタで動作するブレークポイントは、JIT でも動作し、LLVM でも一貫したソースマッピングを持つ。ユーザーは基盤のエンジンの違いを意識しない。
- **一つのソース**：デバッグメタデータは IR と共に流れ、重複定義せず、二重のマッピングを維持しない。
- **ゼロインパクト**：`yaoxiang run --debug`
  という一つの引数で済み、この引数を付けない場合のコンパイルと実行の動作は完全に変わらない。
- **DAP 標準**：VS Code エコシステムに直接対応し、エディタプロトコルを再発明しない。

## 提案

### 中心となる設計

アーキテクチャ概要：

```
┌──────────────────────────────────────────────────────┐
│                    VS Code / エディタ                  │
│              DAP Client (launch.json)                 │
└────────────────────────┬─────────────────────────────┘
                         │ stdio
┌────────────────────────▼─────────────────────────────┐
│                 DAP サーバ (yx-core)                   │
│  ┌─────────┐  ┌──────────┐  ┌───────────────────┐    │
│  │ セッション管理 │  │ ブレークポイント管理 │  │ 式評価エンジン     │    │
│  └─────────┘  └──────────┘  └───────────────────┘    │
└────────────────────────┬─────────────────────────────┘
                         │ クエリ/制御
┌────────────────────────▼─────────────────────────────┐
│                  ランタイムデバッグインタフェース (trait) │
│  pause / resume / step / get_frames / eval / ...    │
└────┬──────────────────┬──────────────────┬──────────┘
     │                  │                  │
┌────▼────┐    ┌───────▼───────┐    ┌─────▼──────┐
│ インタプリタ │    │ JIT (RFC-028)│    │ LLVM AOT   │
│ IRメタデータ │    │ 軽量デバッグ  │    │ IRメタデータ │
│ を直接消費  │    │ テーブル生成  │    │ → DWARF   │
└─────────┘    └───────────────┘    └────────────┘
```

**重要な設計上の決定**：

1. **DAP サーバとランタイムは trait で疎結合**。サーバは基盤がインタプリタか JIT かを関知しない——`DebugEngine`
   trait を介して命令を下すだけである。各エンジンは同じ trait を独立して実装する。
2. **`yaoxiang run --debug`
   はインタプリタの使用を強制する**。デバッグには制御可能性が必要であり、性能は必要ない。LLVM モードでは DWARF を生成して事後トレース（core
   dump / crash report）にのみ使用し、対話的デバッグは行わない。
3. **`yaoxiang run`
   からエントリポイント発見ロジックを再利用**。新しいサブコマンドを導入せず、心のモデルは「プログラムをデバッグモードで実行する」となる。

### IR デバッグメタデータ

既存の YaoXiang
IR にメタデータを付加し、新しい IR 種別は追加しない。すべてのメタデータは**コンパイルフロントエンド**で一箇所生成され、バックエンドの消費は読み取り専用である：

| メタデータ       | 付加位置                | 説明                                   |
| ---------------- | ----------------------- | -------------------------------------- |
| `SourceLocation` | 各 IR ノード            | ソースファイル:行番号:列番号           |
| `VarName`        | 変数宣言/束縛ノード     | ソースコード内の変数名                 |
| `TypeAnnotation` | 変数/式ノード           | 推論された型（コンパイル時述語を含む） |
| `ScopeBoundary`  | ブロック/関数の入口出口 | 変数スコープのライフサイクル           |
| `SpanInfo`       | spawn ノード            | spawn ブロック内のタスク境界           |

### 起動フロー

```
yaoxiang run --debug file.yx
    │
    ├── Phase 1: コンパイル（デバッグメタデータ付き）
    │   ├── 構文解析 → AST
    │   ├── 型検査 + コンパイル時述語の検証
    │   └── IR への降格（デバッグメタデータを付加）
    │
    ├── Phase 2: インタプリタエンジンの使用
    │   └── --debug モードでは --release の有無に関わらずインタプリタを使用
    │
    ├── Phase 3: DAP サーバの起動
    │   ├── stdio トランスポートチャネルの初期化
    │   ├── VS Code の attach を待機
    │   ├── attach 成功後、プログラム入口で一時停止
    │   └── 対話的デバッグループに移行
    │
    └── Phase 4: プログラム終了 / デバッグセッション終了 → 終了
```

### 各モードの差異

| モード                   | デバッグ方式                                                         |
| ------------------------ | -------------------------------------------------------------------- |
| `yaoxiang run --debug`   | インタプリタ強制、フル機能 DAP 対話的デバッグ                        |
| `yaoxiang run --release` | DWARF 生成、事後トレース用（core dump / crash report）、DAP 起動なし |
| `yaoxiang run`（通常）   | デバッグメタデータなし、デバッグサポートなし                         |

## 詳細設計

### 1. ブレークポイント

```
ブレークポイント種別：
├── ソース行ブレークポイント   → コンパイルフロントエンドが位置メタデータを生成、バックエンドがクエリで照合
├── 関数入口ブレークポイント  → 関数呼び出し時に発火（第二段階）
├── 条件付きブレークポイント  → 式の評価結果が true のときに発火
└── データブレークポイント    → 変数が変更されたときに発火（第二段階）
```

**ソース行ブレークポイントの中心ロジック**：

```
VS Code 送信: "file.yx:42 にブレークポイントを設定"
    │
DAP サーバ：
    ├── IR 内のすべての SourceLocation == (file.yx, 42) のノードを照会
    ├── ランタイムに転送: "これらの IR アドレスで一時停止"
    └── ランタイムが応答: ブレークポイント ID

プログラムが IR ノードを実行 → ランタイムがチェック: このノードはブレークポイントリストにあるか？
    ├── 通常ブレークポイント → 一時停止、DAP サーバに通知
    └── 条件付きブレークポイント → 条件式を評価 → true の場合のみ一時停止
```

**三つのエンジンの実装**：

|                              | インタプリタ                           | JIT                                    | LLVM                                                   |
| ---------------------------- | -------------------------------------- | -------------------------------------- | ------------------------------------------------------ |
| ブレークポイント挿入方式     | 実行ループ内で IR ノード ID をチェック | JIT が機械語に `int3` を挿入           | LLVM DWARF + ハードウェアブレークポイントを利用        |
| 条件付きブレークポイント評価 | 式を直接解釈実行                       | 条件式を一時的に JIT コンパイル        | DWARF 式スタック + 評価                                |
| 性能オーバーヘッド           | 各 IR ノードで追加のテーブル参照       | ブレークポイント箇所のみオーバーヘッド | ほぼゼロオーバーヘッド（ハードウェアブレークポイント） |

### 2. ステップ実行

```
Step Over    → 現在の行を実行し、関数呼び出し内部をスキップして次の行で停止
Step Into    → 現在の行の関数呼び出し内部に進入
Step Out     → 現在の関数が戻るまで実行
Continue     → 次のブレークポイントまたはプログラム終了まで実行を再開
```

**実装ロジック**：ステップ操作は本質的に**一時的ブレークポイント**である。ユーザーが明示的に設定したブレークポイントと同じ機構を共有し、二つのシステムではなく一つのシステムの二つの使い方である。

```
Step Over：
    現在のソース行番号 = query_line(frame)
    → 次の行に一時的ブレークポイントを設定
    → 現在の行が関数呼び出しの場合：呼び出し箇所の後に一時的ブレークポイントを設定
    → Continue → 一時的ブレークポイントにヒット → 削除 → 一時停止

Step Into：
    現在の呼び出し対象の最初の実行可能行
    → 関数本体の最初の IR ノードのソース位置を見つける
    → 一時的ブレークポイントを設定 → Continue → ヒット → 一時停止

Step Out：
    現在のスタックフレームのリターンアドレス
    → caller の次の行を見つける
    → 一時的ブレークポイントを設定 → Continue → ヒット → 一時停止
```

**一時的ブレークポイントの四つの境界ケース処理**：

1. **並行性の帰属**：一時的ブレークポイントは現在のタスク ID に紐付けられ、他のタスクがヒットしても無視する。
2. **spawn ブロックの Step Over**：spawn の外側で Step
   Over を押すと、spawn ブロック全体を最後まで実行し、その後へジャンプする。spawn 内部のデバッグに入るには Step
   Into を使用すべきである。
3. **一時的ブレークポイントがヒットしない**：ウォッチドッグタイムアウト（30 秒間ブレークポイントヒットなし）を設定 → 強制一時停止 →
   VS Code に通知。同時にプログラム終了イベントを監視 → 即座にクリーンアップ。
4. **同一行に複数の IR ノード**：Step Over の一時的ブレークポイントに `ignore_current_line`
   フラグを設定。ヒットした後、ソース行番号が現在の行番号と等しい場合 → 無視して続行。

### 3. 変数検査とスコープ

```
VS Code リクエスト: "現在のフレームの変数リスト"
    │
DAP サーバ：
    ├── 現在の一時停止点の IR ノードを照会
    ├── 現在の ScopeBoundary 内の変数束縛を走査
    │   └── 各束縛を返却: (名前, 型, ランタイム値参照)
    └── VariablesResponse を組み立て → VS Code
```

**スコープの階層**：

```
┌─ Globals ───────────────────────────┐
│  モジュールレベル束縛: 定数、型エイリアス、グローバル   │
├─ Locals ────────────────────────────┤
│  現在の関数内で可視のローカル変数           │
│  ├── パラメータ（関数パラメータ）                │
│  └── ローカル束縛（let / 代入）          │
├─ Captured ──────────────────────────┤
│  spawn ブロック / クロージャが捕捉した外部変数      │
│  所有権状態を表示: move 済み / ref 共有  │
└─────────────────────────────────────┘
```

**エンジンの差異**：

| エンジン     | 変数値の取得                                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| インタプリタ | VM スタックフレームとヒープを直接読み取る。各値はメモリ上に明確な表現を持つ                                             |
| JIT          | レジスタとスタック上の値 → JIT コンパイル時に「変数 → レジスタ/スタックスロット」マッピングテーブルを記録する必要がある |
| LLVM         | DWARF の `.debug_info` セクション → `DW_AT_location` → LLDB ネイティブサポート                                          |

**特殊型の表示**：コンパイル時述語がデバッグに有用な情報を精錬して表示する：

```
x: Positive(x)  →  "Int (x > 0 = True)" と表示
y: Sorted(y)    →  "Array(Int) (ソート保証)" と表示
result: T       →  ランタイムの具体的な型を表示
```

### 4. コールスタック

```
DAP リクエスト: StackTrace
    │
応答：
┌──────────────────────────────────┐
│ #0  process_item()  file.yx:42  │  ← 現在の一時停止点
│     locals: item = "hello"       │
│     spawn タスク ID: task-3        │
├──────────────────────────────────┤
│ #1  main()          file.yx:67  │  ← caller
│     locals: data = ["hello", ...]│
├──────────────────────────────────┤
│ #2  <entry>         file.yx:1   │  ← ルート
└──────────────────────────────────┘
```

各フレームが記録する内容：関数シグネチャ、呼び出し位置（ソースファイル+行番号）、ローカル変数（遅延評価）、spawn コンテキスト（タスク ID）。

インタプリタと JIT はそれぞれフレームリンクリストを保持する。フレームの取得はゼロコストではない——しかしデバッグモードはゼロオーバーヘッドを追求しない。

### 5. 式評価（Watch / REPL）

ユーザーはブレークポイントで任意の YaoXiang 式を入力する：

```
Watch: x + y         → 計算結果を返す
Watch: items[2].name → 複雑な構造にアクセス
Watch: f(x)          → 関数を呼び出す（副作用リスクあり）
```

**評価戦略**：

```
ユーザーが式を入力
    │
├── コンパイラフロントエンドが式を構文解析
├── 現在のフレームコンテキストで型検査を実施
├── 変数値を現在のフレームから取得（読み取り専用参照）
├── 式を独立したマイクロプログラムとして実行
│   └── 外部変数の変更を許可しない
│   └── spawn を許可しない
│   └── IO を許可しない（またはオプションで有効化）
└── 結果の値を返す → 元のフレーム状態は完全に不変
```

**インタプリタは自然なサンドボックス**：式評価は新しいサンドボックスを作成しない——インタプリタ自体がサンドボックスである。式評価は単に一時的にフレームを push し、破棄するだけである。通常の実行と同じ VM を共有するが、いかなる副作用もコミットしない。

**関数呼び出し評価**：デフォルトで許可するが、「この式は副作用がある可能性がある」とユーザーに警告し、確認後に実行する。

**エンジンの差異**：

| エンジン     | 式評価                                                                    |
| ------------ | ------------------------------------------------------------------------- |
| インタプリタ | 既存の eval コードパスを再利用し、現在のフレーム環境を注入                |
| JIT          | 式を一時的にコンパイル → 現在のフレームにリンク → 実行 → 一時コードを破棄 |
| LLVM         | サポート対象外——LLVM モードは対話的デバッグを行わない                     |

### 6. 並行デバッグ

**タスクモデルの可視性**：

DAP の `threads` 概念は YaoXiang の `spawn`
タスクにマッピングされる。各タスクは独自のスタックフレームリンクリストと実行状態を持つ。

```
┌─ Threads ───────────────────────────┐
│  ● task-1  main()     file.yx:10   │ ← 現在フォーカス中
│  ▶ task-2  fetch()    file.yx:34   │ ← 実行中
│  ⏸ task-3  process()  file.yx:56   │ ← ブレークポイントで停止
│  ◼ task-4  write()    終了済み         │
└─────────────────────────────────────┘
```

**並行コンテキストでのブレークポイント**：

| 一時停止モード           | 動作                                            | 適用シナリオ                         |
| ------------------------ | ----------------------------------------------- | ------------------------------------ |
| `stop-all`（デフォルト） | 一つのタスクがヒット → すべてのタスクを一時停止 | データ競合、グローバル状態のデバッグ |
| `stop-this-only`         | ヒットしたタスクのみ一時停止、他は継続          | 独立したタスクロジックのデバッグ     |

**spawn ブロックのステップセマンティクス**：

```
spawn {          // Step Over → spawn ブロック全体を最後まで実行
    task_a()     // Step Into → task_a に進入
    task_b()     // 並列実行、個別の step の影響を受けない
}
```

### 7. DAP プロトコルマッピング

#### 第一段階：コアリクエスト

| DAP リクエスト      | YaoXiang セマンティクス                                                            |
| ------------------- | ---------------------------------------------------------------------------------- |
| `initialize`        | 能力ネゴシエーション：ブレークポイント、ステップ、変数、スタックフレームをサポート |
| `launch` / `attach` | YaoXiang プログラムの起動/アタッチ（`--debug` は attach モード）                   |
| `setBreakpoints`    | ソース行ブレークポイントの設定                                                     |
| `configurationDone` | ブレークポイント準備完了、実行開始                                                 |
| `threads`           | すべてのアクティブな spawn タスクリストを返す                                      |
| `stackTrace`        | 指定されたタスクのスタックフレームリストを返す                                     |
| `scopes`            | 現在のフレームの変数スコープを返す                                                 |
| `variables`         | 指定されたスコープの変数リストを返す                                               |
| `continue`          | 実行を再開                                                                         |
| `next`              | Step Over                                                                          |
| `stepIn`            | Step Into                                                                          |
| `stepOut`           | Step Out                                                                           |
| `pause`             | すべてのタスクを中断                                                               |
| `evaluate`          | 現在のフレームで式を評価                                                           |
| `disconnect`        | デバッグセッションを終了                                                           |

#### 第二段階：拡張リクエスト

| DAP リクエスト            | YaoXiang セマンティクス                  |
| ------------------------- | ---------------------------------------- |
| `setFunctionBreakpoints`  | 関数名ブレークポイント                   |
| `setExceptionBreakpoints` | エラー/panic 発生時に一時停止            |
| `dataBreakpointInfo`      | データブレークポイント（変数変更で発火） |

## 実装戦略

### フェーズゼロ：インフラ（全フェーズの前段）

**目標**：コンパイルフロントエンドがデバッグメタデータを IR に付加する。

| コンポーネント | 変更内容                                                                       |
| -------------- | ------------------------------------------------------------------------------ |
| IR 定義        | `SourceLocation`、`VarName`、`TypeAnnotation` などのメタデータフィールドを追加 |
| Parser         | 各 AST ノードがソース位置を記録                                                |
| TypeChecker    | 型情報を IR ノードに付加                                                       |
| テスト         | IR dump に位置と変数情報が含まれることを検証                                   |

**ランタイムには関与しない。**

**実装進捗（2026-09-17）**：

| 成果物      | 状態 | 実装形式                                                                                                                                                                                                         |
| ----------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ソース位置  | 完了 | 76 個の全 `Instruction` バリアントが `span` フィールドを保持；`span()` メソッドは意図的にワイルドカードアームを設定せず、新規バリアントが span を欠落させるとコンパイル失敗。位置は 40/41 命令をカバー           |
| 変数名      | 完了 | `LocalSlot { name, ty, scope_depth }` を `FunctionBody::Code::locals` にアタッチ；`register_local` が生成時にその場で書き込みを実施。`.42` デバッグセクション v2 は名前を保持し、v1 産物は後方互換で読み取り可能 |
| 型情報      | 一部 | スロットには既に `ty` が含まれる；`TypeAnnotation` の独立メタデータは未実装                                                                                                                                      |
| dump 可視性 | 完了 | `dump` が各命令の `; <file>:<line>:<col>` を出力し、`locals: 名前@スロット` をリストアップ                                                                                                                       |

上記表で実装されたデータ形式はフェーズ一に直接接続する：DAP のブレークポイント解析は `debug_map`
を消費し、変数パネルは `local_names`（名前）と `locals`（型）を消費する。

### フェーズ一：インタプリタ DAP MVP

**目標**：`yaoxiang run --debug file.yx` でブレークポイント設定、ステップ実行、変数表示が可能。

| コンポーネント                      | 変更内容                                                                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| DAP サーバ (yx-core 新規モジュール) | stdio トランスポート層、コアリクエスト処理、ブレークポイントマネージャ（ソース行 → IR ノードマッピング）                 |
| ランタイムデバッグ trait (yx-core)  | `DebugEngine` trait 定義（pause, resume, step, get_frames, eval, get_variables）                                         |
| インタプリタ                        | 実行ループ内のブレークポイントチェック、一時停止/再開メカニズム、フレームリンクリスト保守、`InterpreterDebugEngine` 実装 |
| CLI                                 | `yaoxiang run --debug` 引数                                                                                              |

**受け入れ基準**：`tests/yaoxiang/` 下の任意の `.yx` ファイルに対して、VS
Code でブレークポイント設定、Step Over、変数値表示が可能であること。

### フェーズ二：高度なデバッグ機能

**目標**：式評価、関数ブレークポイント、並行デバッグ、例外ブレークポイント。

| コンポーネント            | 変更内容                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| 式評価エンジン            | マイクロプログラムコンパイル（parser + typechecker 再利用）、VM への一時的フレーム push、副作用隔離      |
| 並行デバッグ              | spawn タスクリストマッピング、ブレークポイントのタスク ID 紐付け、stop-all / stop-this-only 一時停止戦略 |
| 関数/例外ブレークポイント | `setFunctionBreakpoints`、`setExceptionBreakpoints` のマッピング                                         |
| VS Code 拡張              | デフォルトの `launch.json` テンプレートを提供                                                            |

### フェーズ三：JIT デバッグ & LLVM DWARF

**目標**：JIT エンジンが DAP を再利用、LLVM がクラッシュトレース用の DWARF を生成。

| コンポーネント | 変更内容                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| JIT            | `DebugEngine` trait 実装、コンパイル時の変数 → レジスタマッピングテーブル生成、ランタイムフレームリンクリスト、式の一時的コンパイル |
| LLVM           | IR デバッグメタデータ → LLVM `DILocation` / `DISubprogram` → DWARF（DAP 対話なし）                                                  |

### 依存関係

```
フェーズゼロ（IR メタデータ）
    ↓
フェーズ一（インタプリタ DAP MVP）  ← ここから使い始められる
    ↓
フェーズ二（高度な機能）
    ↓
フェーズ三（JIT + LLVM DWARF）
```

### リスク

| リスク                                  | 緩和策                                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| インタプリタ一時停止メカニズムの複雑さ  | 複雑な状態機械ではなく単純な channel/signal を使用。一時停止とは次の命令の fetch を禁止するだけ |
| 式評価の型安全性                        | 既存の typechecker を再利用、読み取り専用参照、副作用をコミットしない                           |
| DAP プロトコルの詳細                    | debugpy / delve の実装を参照。プロトコルは成熟している                                          |
| 並行デバッグの stop-all による livelock | タイムアウトメカニズム + 強制一時停止                                                           |

## トレードオフ

### 利点

- **一つのソース**：デバッグメタデータは一度だけ生成され、三つのエンジンで共有する。「インタプリタのデバッグ情報は正しいが LLVM の情報は誤っている」という事態は発生しない
- **ゼロインパクト**：`--debug` という一つの引数で済み、付けない場合の動作は完全に変わらない
- **DAP 標準**：VS
  Code エコシステムに直接接続し、カスタムエディタプロトコルやデバッガ UI を必要としない
- **インタプリタ優先**：デバッグは本質的にインタプリタに適している——柔軟、制御可能、式評価が簡単。LLVM モードで対話的デバッグを行わないのは最も実用的な選択

### 欠点

- **デバッグモードの性能が低い**：インタプリタは JIT/LLVM より大幅に遅い。しかしデバッグに性能は不要——誰もデバッグモードで本番負荷を処理することを期待していない
- **LLVM デバッグが制限される**：AOT コンパイルは対話的デバッグができず、GDB/LLDB +
  DWARF のみ使用可能。しかしこれはトレードオフ：LLVM モードではそもそもデバッグ動作の違いがあってはならない
- **並行一時停止が複雑**：インタプリタでの stop-all セマンティクスの実装にはすべてのアクティブタスクの走査が必要

### 代替案

| 代替案                                    | 採用しない理由                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 三つのエンジンそれぞれが DAP を実装       | 作業量三倍、バグ三倍。「良い趣味」に違反                                                                                 |
| DWARF のみ使用、自前の DAP は作らない     | インタプリタと JIT には DWARF 概念がなく、LLDB は VM 内部に入れない                                                      |
| Python pdb に倣ったコマンドラインデバッガ | VS Code の体験はコマンドラインデバッガよりはるかに優れている                                                             |
| DAP を LSP プロセスに詰め込む             | ライフサイクルが根本的に異なる——LSP はプロジェクトに追随し、DAP はデバッグセッションに追随する。プロセス分離はハード要件 |
