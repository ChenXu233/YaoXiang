# RFC-034: 統一デバッグツールチェーン

## 要約

YaoXiang に統一されたデバッグツールチェーンを導入する。中心となる設計は**一つの源、三つの消費**：コンパイルフロントエンドがソース位置、変数名、型情報を第一級市民として YaoXiang
IR に埋め込み、インタープリタ、JIT、LLVM の三つのバックエンドがそれぞれ同一のメタデータを消費する。ユーザーは
`yaoxiang run --debug` で DAP（Debug Adapter Protocol）サーバを起動し、VS
Code が stdio 経由で接続し、ブレークポイント、ステップ、変数参照、コールスタック、式評価、並行デバッグの統一された体験を得る——基盤となる実行エンジンの種類を問わない。

## 動機

### なぜこの機能が必要なのか？

現在、YaoXiang プログラムのエラーを調査する手段は非常に原始的である：

```yaoxiang
io.println("DEBUG: x = " + x.to_string())
io.println("DEBUG: entered branch A")
```

三つの致命的な問題：

1. **コンパイラ開発のブートストラップが阻害される**：YaoXiang で YaoXiang コンパイラを書いているが、コンパイラを書く人が自分のコードをデバッグできない。ブートストラップ段階で対話的なデバッグ手段がないことは袋小路である。
2. **三つのエンジン、ゼロデバッグ**：インタープリタ、JIT、LLVM がそれぞれ独立して動作し、問題が起きた場合ユーザーは stdout に
   `ALL TESTS PASSED`
   が現れるかどうかを確認するしかない。アサーション失敗？ どの行で起きたか、変数の値は何かがわからない。
3. **並行処理はブラックボックス**：`spawn`
   で複数のタスクが作成されるが、どのタスクがハングしたのか？ 変数が誰に move されたのか？ すべて運任せの推測である。

### 設計目標

- **統一された体験**：インタープリタで動作するブレークポイントは JIT でも動作し、LLVM でも一貫したソースマッピングを持つ。ユーザーは基盤エンジンの違いを意識しない。
- **一つの源**：デバッグメタデータは IR と共に流れ、重複定義せず、二重のマッピングを維持しない。
- **ゼロ侵襲**：`yaoxiang run --debug`
  一つの引数で済み、この引数を付けない場合、コンパイルと実行の動作は完全に変わらない。
- **DAP 標準**：VS Code エコシステムに直接接続し、エディタプロトコルやデバッガ UI を再発明しない。

## 提案

### 中核設計

アーキテクチャ概要：

```
┌──────────────────────────────────────────────────────┐
│                    VS Code / エディタ                   │
│              DAP Client (launch.json)                 │
└────────────────────────┬─────────────────────────────┘
                         │ stdio
┌────────────────────────▼─────────────────────────────┐
│                 DAP サーバ (yx-core)                   │
│  ┌─────────┐  ┌──────────┐  ┌───────────────────┐    │
│  │ セッション │  │ ブレークポイント │  │ 式評価エンジン   │    │
│  │ 管理     │  │ 管理      │  │                 │    │
│  └─────────┘  └──────────┘  └───────────────────┘    │
└────────────────────────┬─────────────────────────────┘
                         │ クエリ/制御
┌────────────────────────▼─────────────────────────────┐
│                  ランタイムデバッグインターフェース (trait) │
│  pause / resume / step / get_frames / eval / ...    │
└────┬──────────────────┬──────────────────┬──────────┘
     │                  │                  │
┌────▼────┐    ┌───────▼───────┐    ┌─────▼──────┐
│ インタープリタ │    │ JIT (RFC-028)│    │ LLVM AOT   │
│ IRメタデータ │    │ 軽量デバッグ  │    │ IRメタデータ │
│ 直接消費  │    │ テーブル生成  │    │ → DWARF   │
└─────────┘    └───────────────┘    └────────────┘
```

**重要な設計上の決定**：

1. **DAP サーバとランタイムは trait により疎結合**。サーバは基盤がインタープリタか JIT かを気にしない——`DebugEngine`
   trait を通じて命令を出すだけである。各エンジンは同じ trait を独立して実装する。
2. **`yaoxiang run --debug`
   は強制的にインタープリタを使用**。デバッグには制御可能性が必要であり、性能は不要である。LLVM モードでは DWARF を生成して事後トレース（core
   dump / crash report）のみを行い、対話的デバッグは行わない。
3. **`yaoxiang run`
   のエントリポイント発見ロジックを再利用**。新しいサブコマンドを導入せず、心のモデルは「プログラムをデバッグモードで実行する」。

### IR デバッグメタデータ

既存の YaoXiang
IR にメタデータを付加し、IR の種類を新規追加しない。すべてのメタデータは**コンパイルフロントエンド**で一箇所で生成され、バックエンドの消費は読み取り専用：

| メタデータ       | 付加点                  | 説明                                   |
| ---------------- | ----------------------- | -------------------------------------- |
| `SourceLocation` | 各 IR ノード            | ソースファイル:行番号:列番号           |
| `VarName`        | 変数宣言/束縛ノード     | ソースコード中の変数名                 |
| `TypeAnnotation` | 変数/式ノード           | 推論された型（コンパイル時述語を含む） |
| `ScopeBoundary`  | ブロック/関数の入口出口 | 変数スコープのライフサイクル           |
| `SpanInfo`       | spawn ノード            | spawn ブロック内のタスク境界           |

### 起動フロー

```
yaoxiang run --debug file.yx
    │
    ├── フェーズ 1: コンパイル（デバッグメタデータ付き）
    │   ├── 解析 → AST
    │   ├── 型検査 + コンパイル時述語検証
    │   └── IR への降格（デバッグメタデータ付加）
    │
    ├── フェーズ 2: インタープリタエンジンの使用
    │   └── --debug モードでは --release かどうかにかかわらずインタープリタを使用
    │
    ├── フェーズ 3: DAP サーバ起動
    │   ├── stdio トランスポート層の初期化
    │   ├── VS Code の attach を待機
    │   ├── attach 成功後、プログラムエントリで一時停止
    │   └── 対話的デバッグループへ移行
    │
    └── フェーズ 4: プログラム終了 / デバッグセッション終了 → 終了
```

### モードごとの違い

| モード                   | デバッグ方法                                                         |
| ------------------------ | -------------------------------------------------------------------- |
| `yaoxiang run --debug`   | インタープリタ強制、フル機能の DAP 対話デバッグ                      |
| `yaoxiang run --release` | DWARF 生成、事後トレース用（core dump / crash report）、DAP 起動せず |
| `yaoxiang run`（通常）   | デバッグメタデータなし、デバッグサポートなし                         |

## 詳細設計

### 1. ブレークポイント

```
ブレークポイントタイプ：
├── ソース行ブレークポイント → コンパイルフロントエンドが位置メタデータを生成、バックエンドがマッチングをクエリ
├── 関数入口ブレークポイント → 関数呼び出し時にトリガ（第二フェーズ）
├── 条件付きブレークポイント → 式の評価結果が true のときにトリガ
└── データブレークポイント → 変数が変更されたときにトリガ（第二フェーズ）
```

**ソース行ブレークポイントの中核ロジック**：

```
VS Code 送信: "file.yx:42 にブレークポイントを設定"
    │
DAP サーバ：
    ├── IR 内のすべての SourceLocation == (file.yx, 42) のノードをクエリ
    ├── ランタイムに転送: "これらの IR アドレスで一時停止"
    └── ランタイム返却: ブレークポイント ID

プログラムが IR ノードに到達 → ランタイムチェック: このノードはブレークポイントリストにあるか？
    ├── 通常ブレークポイント → 一時停止、DAP サーバに通知
    └── 条件付きブレークポイント → 条件式を評価 → true の場合のみ一時停止
```

**三つのエンジンの実装**：

|                              | インタープリタ                         | JIT                                    | LLVM                                                   |
| ---------------------------- | -------------------------------------- | -------------------------------------- | ------------------------------------------------------ |
| ブレークポイント挿入方法     | 実行ループ内で IR ノード ID をチェック | JIT が機械語に `int3` を挿入           | LLVM DWARF + ハードウェアブレークポイントを利用        |
| 条件付きブレークポイント評価 | 式を直接解釈実行                       | 条件式を一時的に JIT コンパイル        | DWARF 式スタック + 評価                                |
| パフォーマンスオーバーヘッド | 各 IR ノードで追加のテーブル検索       | ブレークポイント箇所のみオーバーヘッド | ほぼゼロオーバーヘッド（ハードウェアブレークポイント） |

### 2. ステップ実行

```
Step Over    → 現在の行を実行、関数呼び出し内部をスキップ、次の行で停止
Step Into    → 現在の行の関数呼び出し内部に入る
Step Out     → 現在の関数が戻るまで実行
Continue     → 次のブレークポイントまたはプログラム終了まで実行を再開
```

**実装ロジック**：ステップ操作は本質的に**テンポラリブレークポイント**である。ユーザーが明示的に設定したブレークポイントと同じ機構を共有し、二つのシステムではなく、一つのシステムの二つの使用方法である。

```
Step Over:
    現在のソース行番号 = query_line(frame)
    → 次の行にテンポラリブレークポイントを設定
    → 現在の行が関数呼び出しの場合：呼び出し点以降にテンポラリブレークポイントを設定
    → Continue → テンポラリブレークポイントヒット → 削除 → 一時停止

Step Into:
    現在の呼び出しターゲットの最初の実行可能行
    → 関数本体の最初の IR ノードのソース位置を特定
    → テンポラリブレークポイント設定 → Continue → ヒット → 一時停止

Step Out:
    現在のスタックフレームのリターンアドレス
    → caller の次の行を特定
    → テンポラリブレークポイント設定 → Continue → ヒット → 一時停止
```

**テンポラリブレークポイントの四つの境界ケース処理**：

1. **並行性の帰属**：テンポラリブレークポイントは現在のタスク ID にバインドされ、他のタスクがヒットした場合は無視する。
2. **Step Over spawn ブロック**：spawn の外側で Step
   Over を押すと spawn ブロック全体を完了し、後続にジャンプする。spawn 内部のデバッグに入るには Step
   Into を使用する。
3. **テンポラリブレークポイントがヒットしない**：ウォッチドッグタイムアウト（30 秒間いかなるブレークポイントもヒットしない）を設定 → 強制一時停止 →
   VS Code に通知。同時にプログラム終了イベントを監視 → 即座にクリーンアップ。
4. **同一行に複数の IR ノード**：Step Over のテンポラリブレークポイントに `ignore_current_line`
   をマークし、ヒット時にソース行番号が現在の行番号と等しい場合 → 無視、継続。

### 3. 変数検査とスコープ

```
VS Code リクエスト: "現在のフレームの変数リスト"
    │
DAP サーバ：
    ├── 現在の一時停止点の IR ノードをクエリ
    ├── 現在の ScopeBoundary 内の変数束縛を走査
    │   └── 各束縛返却: (名前, 型, ランタイム値参照)
    └── VariablesResponse を組み立て → VS Code
```

**スコープ階層**：

```
┌─ Globals ───────────────────────────┐
│  モジュールレベル束縛: 定数、型エイリアス、グローバル   │
├─ Locals ────────────────────────────┤
│  現在の関数内で可視のローカル変数       │
│  ├── パラメータ (関数パラメータ)        │
│  └── ローカル束縛 (let / 代入)          │
├─ Captured ──────────────────────────┤
│  spawn ブロック / クロージャが捕捉した外部変数 │
│  所有権状態を表示: 既に move / ref 共有   │
└─────────────────────────────────────┘
```

**エンジンによる違い**：

| エンジン       | 変数値取得                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------------- |
| インタープリタ | VM スタックフレームとヒープを直接読み取る。各値はメモリに明確な表現を持つ                                             |
| JIT            | レジスタとスタック上の値 → JIT コンパイル時に「変数 → レジスタ/スタックスロット」マッピングテーブルを記録する必要あり |
| LLVM           | DWARF の `.debug_info` セクション → `DW_AT_location` → LLDB ネイティブサポート                                        |

**特殊型の表示**：コンパイル時述語が精錬した型はデバッグに価値のある情報を表示する：

```
x: Positive(x)  →  "Int (x > 0 = True)" と表示
y: Sorted(y)    →  "Array(Int) (ソート保証)" と表示
result: T       →  ランタイムの具体的な型を表示
```

### 4. コールスタック

```
DAP リクエスト: StackTrace
    │
返却：
┌──────────────────────────────────┐
│ #0  process_item()  file.yx:42  │  ← 現在の一時停止点
│     locals: item = "hello"       │
│     spawn タスク ID: task-3      │
├──────────────────────────────────┤
│ #1  main()          file.yx:67  │  ← caller
│     locals: data = ["hello", ...]│
├──────────────────────────────────┤
│ #2  <entry>         file.yx:1   │  ← ルート
└──────────────────────────────────┘
```

各フレームは以下を記録：関数シグネチャ、呼び出し位置（ソースファイル+行番号）、ローカル変数（遅延評価）、spawn コンテキスト（タスク ID）。

インタープリタと JIT はそれぞれ独自のフレームリンクリストを維持する。フレーム取得はゼロコストではない——しかしデバッグモードはゼロオーバーヘッドを追求しない。

### 5. 式評価（Watch / REPL）

ユーザーがブレークポイントで任意の YaoXiang 式を入力：

```
Watch: x + y         → 計算結果を返却
Watch: items[2].name → 複雑な構造にアクセス
Watch: f(x)          → 関数を呼び出し（副作用リスクあり）
```

**評価戦略**：

```
ユーザーが式を入力
    │
├── コンパイラフロントエンドが式を解析
├── 現在のフレームコンテキストで型検査
├── 変数値を現在のフレームから取得（読み取り専用参照）
├── 式を独立したマイクロプログラムとして実行
│   └── 外部変数の変更は許可しない
│   └── spawn は許可しない
│   └── IO は許可しない（またはオプションで有効化）
└── 結果値を返却 → 元のフレーム状態は完全に不変
```

**インタープリタは自然なサンドボックス**：式評価は新しいサンドボックスを作成しない——インタープリタ自体がサンドボックスである。式評価は単にフレームを一時的に push し、使用後に破棄する。通常の実行と同一の VM を共有するが、いかなる副作用もコミットしない。

**関数呼び出し評価**：デフォルトで許可するが、「この式は副作用がある可能性がある」とユーザーに警告し、ユーザーの確認後に実行する。

**エンジンによる違い**：

| エンジン       | 式評価                                                                    |
| -------------- | ------------------------------------------------------------------------- |
| インタープリタ | 既存の eval コードパスを再利用、現在のフレーム環境を注入                  |
| JIT            | 式を一時的にコンパイル → 現在のフレームにリンク → 実行 → 一時コードを破棄 |
| LLVM           | サポート対象外——LLVM モードは対話デバッグを行わない                       |

### 6. 並行デバッグ

**タスクモデルの可視性**：

DAP の `threads` 概念は YaoXiang の `spawn`
タスクにマッピングされる。各タスクは独自のスタックフレームリンクリストと実行状態を持つ。

```
┌─ Threads ───────────────────────────┐
│  ● task-1  main()     file.yx:10   │ ← 現在フォーカス
│  ▶ task-2  fetch()    file.yx:34   │ ← 実行中
│  ⏸ task-3  process()  file.yx:56   │ ← ブレークポイントで一時停止
│  ◼ task-4  write()    終了済み      │
└─────────────────────────────────────┘
```

**並行コンテキストでのブレークポイント**：

| 一時停止モード           | 動作                                            | 適用シナリオ                         |
| ------------------------ | ----------------------------------------------- | ------------------------------------ |
| `stop-all`（デフォルト） | 一つのタスクがヒット → すべてのタスクが一時停止 | データ競合、グローバル状態のデバッグ |
| `stop-this-only`         | ヒットしたタスクのみ一時停止、他は継続          | 独立したタスクロジックのデバッグ     |

**spawn ブロックのステップセマンティクス**：

```
spawn {          // Step Over → spawn ブロック全体を完了
    task_a()     // Step Into → task_a に入る
    task_b()     // 並行実行、個別のステップの影響を受けない
}
```

### 7. DAP プロトコルマッピング

#### 第一フェーズ：コアリクエスト

| DAP リクエスト      | YaoXiang セマンティクス                                                            |
| ------------------- | ---------------------------------------------------------------------------------- |
| `initialize`        | 能力ネゴシエーション：ブレークポイント、ステップ、変数、スタックフレームをサポート |
| `launch` / `attach` | YaoXiang プログラムの起動/アタッチ（`--debug` は attach モード）                   |
| `setBreakpoints`    | ソース行ブレークポイントの設定                                                     |
| `configurationDone` | ブレークポイント準備完了、実行開始                                                 |
| `threads`           | すべてのアクティブな spawn タスクのリストを返却                                    |
| `stackTrace`        | 指定されたタスクのスタックフレームリストを返却                                     |
| `scopes`            | 現在のフレームの変数スコープを返却                                                 |
| `variables`         | 指定されたスコープの変数リストを返却                                               |
| `continue`          | 実行を再開                                                                         |
| `next`              | Step Over                                                                          |
| `stepIn`            | Step Into                                                                          |
| `stepOut`           | Step Out                                                                           |
| `pause`             | すべてのタスクを中断                                                               |
| `evaluate`          | 現在のフレームで式を評価                                                           |
| `disconnect`        | デバッグセッションを終了                                                           |

#### 第二フェーズ：拡張リクエスト

| DAP リクエスト            | YaoXiang セマンティクス                  |
| ------------------------- | ---------------------------------------- |
| `setFunctionBreakpoints`  | 関数名ブレークポイント                   |
| `setExceptionBreakpoints` | エラー/panic 時に一時停止                |
| `dataBreakpointInfo`      | データブレークポイント（変数変更トリガ） |

## 実装戦略

### フェーズゼロ：インフラストラクチャ（全フェーズに先行）

**目標**：コンパイルフロントエンドがデバッグメタデータを IR に付加する。

| コンポーネント | 変更                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| IR 定義        | `SourceLocation`、`VarName`、`TypeAnnotation` などのメタデータフィールドを新規追加 |
| Parser         | 各 AST ノードがソース位置を記録                                                    |
| TypeChecker    | 型情報を IR ノードに付加                                                           |
| テスト         | IR dump に位置と変数情報が含まれることを検証                                       |

**ランタイムには触れない。**

**実装進捗（2026-09-17）**：

| 成果物               | 状態 | 実装形式                                                                                                                                                                                                                                                                               |
| -------------------- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ソース位置           | 完了 | 76 個の `Instruction` バリアントすべてが `span` フィールドを保持；`span()` メソッドは意図的にワイルドカードアームを持たず、新規バリアントで span 漏れがあればコンパイル失敗。位置は 40/41 命令をカバー                                                                                 |
| 変数名               | 完了 | `LocalSlot { name, ty, scope_depth }` を `FunctionBody::Code::locals` に装着；`register_local` 生成時にその場で書き込み。`.42` デバッグセクション v2 は名前を保持、v1 産物は後方互換で読み取り                                                                                         |
| グローバルスロット名 | 完了 | `.42` デバッグセクション v3 は「スロット番号 → トップレベル束縛名」テーブルを保持。トップレベル束縛は `Operand::Global` 経由であり、いかなる関数の局所名テーブルにも存在しないため、このテーブルがなければ数値しか報告できず変数名を報告できない。v1/v2 産物は空テーブルで読み取り補完 |
| 型情報               | 一部 | スロットには既に `ty` を含む；`TypeAnnotation` 独立メタデータは未実装                                                                                                                                                                                                                  |
| dump 可視性          | 完了 | `dump` は各命令に `; <file>:<line>:<col>` を出力し、`locals: 名前@スロット` を列挙                                                                                                                                                                                                     |

上表で実装されたデータ形式はフェーズ 1 と直接接続する：DAP のブレークポイント解析は `debug_map`
を消費し、変数パネルは `local_names`（名前）と `locals`（型）を消費する。

**目標**：`yaoxiang run --debug file.yx` でブレークポイント設定、ステップ、変数参照が可能。

| コンポーネント                      | 変更                                                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| DAP サーバ (yx-core 新規モジュール) | stdio トランスポート層、コアリクエスト処理、ブレークポイントマネージャ（ソース行 → IR ノードマッピング）                 |
| ランタイムデバッグ trait (yx-core)  | `DebugEngine` trait 定義（pause, resume, step, get_frames, eval, get_variables）                                         |
| インタープリタ                      | 実行ループ内のブレークポイントチェック、一時停止/再開メカニズム、フレームリンクリスト維持、`InterpreterDebugEngine` 実装 |

Code でブレークポイント設定、Step Over、変数値表示が可能。

**目標**：式評価、関数ブレークポイント、並行デバッグ、例外ブレークポイント。

### リスク

| リスク                                   | 緩和策                                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| インタープリタ一時停止メカニズムの複雑さ | 複雑な状態機械ではなく単純な channel/signal を使用、一時停止は次の命令を fetch させないだけ |
| 式評価の型安全性                         | 既存の typechecker を再利用、読み取り専用参照、副作用をコミットしない                       |
| DAP プロトコルの細部                     | debugpy / delve の実装を参考に、プロトコルは成熟している                                    |
| 並行デバッグの stop-all ライブロック     | タイムアウトメカニズム + 強制一時停止                                                       |

## トレードオフ

### 利点

- **一つの源**：デバッグメタデータは一度だけ生成、三つのエンジンで共有。「インタープリタのデバッグ情報は正しいが LLVM は誤っている」が起こらない
- **ゼロ侵襲**：`--debug` 一つの引数、この引数を付けない場合の動作は完全に変わらない
- **DAP 標準**：VS Code エコシステムに直接接続、カスタムエディタプロトコルやデバッガ UI が不要
- **インタープリタ優先**：デバッグは本質的にインタープリタに適している——柔軟、制御可能、式評価がシンプル。LLVM モードで対話デバッグを行わないことが最も务实的な選択

### 欠点

- **デバッグモードの性能が低い**：インタープリタは JIT/LLVM より大幅に遅い。しかしデバッグに性能は不要——誰も debug モードで本番負荷を走らせない
- **LLVM デバッグの制限**：AOT コンパイルは対話デバッグ不可、GDB/LLDB +
  DWARF のみ。しかしこれはトレードオフ：LLVM モードではそもそもデバッグ動作の違いがあるべきではない
- **並行一時停止の複雑さ**：インタープリタ上の stop-all セマンティクスはすべてのアクティブタスクの走査が必要

### 代替案

| 代替案                                | 選択しない理由                                                                                                 |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 三つのエンジンそれぞれが DAP を実装   | 三倍の作業、三セットのバグ。「良き品味」に違反                                                                 |
| DWARF のみ使用、自前の DAP なし       | インタープリタと JIT には DWARF 概念がない、LLDB は VM 内部に入れない                                          |
| Python pdb 風のコマンドラインデバッガ | VS Code の体験はコマンドラインデバッガを圧倒的に凌駕                                                           |
| DAP を LSP プロセスに詰め込む         | ライフサイクルが完全に異なる——LSP はプロジェクトに追従、DAP はデバッグセッションに追従。プロセス分離は硬性要件 |
