## 概要

YaoXiang に**演算子オーバーロード**能力を補完し、`a + b` / `a == b` / `a[i]` / `e?`
をユーザ定義型で実装できるようにし、RFC-011 に既に書き込まれた `T: Add + Multiply + Zero`
制約を**紙上の能力**から実装可能なメカニズムへと変える。

設計は**三層の責務分離**を採用する：固定の演算子→メソッドマッピングテーブル（Layer
0）、名前でディスパッチするベース（Layer 1、既存の `method_bindings`
を再利用）、インターフェース契約層（Layer
2、ジェネリクス制約用）。演算子の**優先順位と結合性は言語で固定**し、ユーザはセマンティクスのみをオーバーロードする。

初回スコープ：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` `Try`
の 8 つのインターフェース。新しいキーワードも新しい構文構造も導入しない。

## 動機

### なぜこの特性が必要か

#### 1. RFC-011 の中核的例がこれに依存しているが、現状では紙上の能力に過ぎない

RFC-011（受け入れ済み）は 8 箇所で演算子名を型制約として使用している：

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

これは RFC-011 の「値依存型 + コンパイル時次元検証」の看板例である。しかし**全 RFC を通じて `Add` /
`Multiply` がどこから来るか、`+`
がどうそれらにバインドされるかを定義した文書は一編もない**。`T: Add`
は現在、履行できないアサーションに過ぎない。

#### 2. ユーザ定義型は基本演算に参加できない（実測）

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

連動する帰結として：`list.contains(list_of_structs, p)` は**完全に使用不能**である——内部で `==`
に依存しているため。

#### 3. `?` は型名をコンパイラに固着させ、`Result` の std 帰属を阻んでいる

`?` の実装は型名とバリアント番号の両方をハードコードしている：

```rust
// typecheck：Result 型をハードコードで構築
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen：group 名と variant 番号をハードコード
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

これにより `Result` は core に残らざるを得ない。`?`
を**インターフェース駆動**に変更すれば、そのインターフェースを実装するあらゆる型（ユーザ定義型を含む）が
`?` を使用でき、`Result` を std に帰属させることができる。

#### 4. ユーザ定義コンテナはインデックス化できない

`Index` の型検査はハードコードされたホワイトリストである：

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// それ以外 → 「型層で認識されないコンテナは黙って拒否」
```

ユーザがコンテナ型を定義すると、`c[0]` は一律エラーとなる。

### 既存の半製品の基盤

調査の結果、機構は**大部分が既に存在**し、欠けているのは接続である：

| 機構                                                            | 位置                                        | ステータス                           |
| --------------------------------------------------------------- | ------------------------------------------- | ------------------------------------ |
| インターフェース宣言 `(Self: Type) -> Type`                     | RFC-011a Phase 1                            | ✅ 実行可能                          |
| インターフェースインスタンス化 `Animal(Dog)` + 外部メソッド宣言 | RFC-011a Phase 2–3                          | ✅ 実行可能                          |
| メソッドディスパッチ `method_bindings["Type.method"]`           | `expressions.rs:1299`                       | ✅ 実行可能                          |
| 関連型（= インターフェース型パラメータ）                        | RFC-011 §3.1；RFC-011a でこの方式が採用済み | ✅ 機構は確定                        |
| 型族評価 `AssociatedTypeDef`                                    | `dependent_types.rs`                        | ✅ 本番用例 `std.assert` の `IsTrue` |
| `Equal` / `Dup` / `Clone` / `Debug` trait                       | `trait_data.rs` に登録済み                  | ⚠️ `Equal` は**消費箇所ゼロ**        |
| 演算子 → メソッド名マッピング                                   | —                                           | ❌ 存在しない                        |

**結論**：これはゼロから特性を構築するのではなく、既存の部品を接続して文書化する作業である。

## 提案

### 中核設計：三層の責務分離

```
Layer 0  固定マッピングテーブル（言語レベル定数、ユーザは変更不可）
         + → add    == → equal    [] → index    ? → residual
         │  コンパイル時に組み込み、型推論には参加せず、ユーザに非公開
         ▼
Layer 1  ディスパッチベース（名前でメソッドを検索し呼び出し）  ← 既存機構を再利用
         method_bindings["Point.add"]
         ▼
Layer 2  インターフェース契約（ジェネリクス制約用）
         Add / Equal / Index / Try …
         T: Add 制約を成立させ、演算子の許可ゲートとなる
```

**階層化の理由**：

- **Layer 0 と 1 は演算子を「使える」ようにし**、Layer
  2 は演算子を「制約できる」ようにする。統合すると、`add` という名前のあらゆるメソッドが `+`
  で呼ばれることになり、RFC-011 の `T: Add` と演算子が乖離する。
- **Layer 1 は新規に造らない**：`method_bindings` は既に `Type.method`
  キーで表引きしており（フィールド検索失敗後のフォールバックパス）、演算子も同じ経路を通せばよい。
- **Layer
  2 はゲートである**：演算子を許可する前に**必ず**対応するインターフェースを実装しているかを確認する必要がある（§「なぜインターフェースの実装が必須か」を参照）。

### Layer 0：固定マッピングテーブル

| 演算子            | インターフェース                                  | メソッド   | 初回 |
| ----------------- | ------------------------------------------------- | ---------- | ---- |
| `+`               | `Add`                                             | `add`      | ✅   |
| `-`               | `Subtract`                                        | `subtract` | ✅   |
| `*`               | `Multiply`                                        | `multiply` | ✅   |
| `/`               | `Divide`                                          | `divide`   | ✅   |
| `%`               | `Modulo`                                          | `modulo`   | ✅   |
| `==` `!=`         | `Equal`                                           | `equal`    | ✅   |
| `[]`              | `Index`                                           | `index`    | ✅   |
| `?`               | `Try`                                             | `residual` | ✅   |
| `<` `<=` `>` `>=` | —（ネイティブ命令として保持）                     | —          | ❌   |
| `and` `or`        | —（短絡は言語セマンティクスでオーバーロード不可） | —          | ❌   |
| ビット演算 5 個   | —                                                 | —          | ❌   |
| 単項 `-` `!`      | —                                                 | —          | ❌   |

**インターフェース名は短縮形ではなく完全綴りを使用**する（`Multiply` であって `Mul`
ではない）：RFC-011 本文の `T: Add + Multiply + Zero`
と整合させ、**既に受け入れ済みの RFC を変更しない**。

**`%` は `Modulo`
セマンティクスを採用**する（数学的剰余、結果の符号は除数に従う）。現在の実装の remainder 挙動（`-7 % 3`
は現在 `-1`
を返す）ではない。これは**意図的なセマンティック修正**である——名前がセマンティクスを数学的剰余に固定する。

### Layer 2：インターフェース定義

#### 算術インターフェース

```yaoxiang
Add: (Self: Type, R: Type) -> Type = {
    add: (self: &Self, other: &R) -> Self
}

Subtract: (Self: Type, R: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> Self
}

Multiply: (Self: Type, R: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> Self
}

Divide: (Self: Type, R: Type) -> Type = {
    divide: (self: &Self, other: &R) -> Self
}

Modulo: (Self: Type, R: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> Self
}
```

`R` は右オペランドの型であり、左右の型が異なることを許容する（例：`Int + Float`）。戻り値は `Self`
に固定される（`&Self` 借用レシーバ、RFC-009 の借用トークンと RFC-011a のレシーバ規約を参照）。

#### 等価インターフェース

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` は暗黙に `Dup` を要求する**：`==`
のセマンティクスは「2 つの値を比較する」ことであり、双方が読み取り可能である必要がある。リニア型（`Dup`
でない）の値は一度しか読めず、比較に参加できない。RFC-009 は既にこの因果連鎖を提示している：

> **因果関係を逆にすることはできない：凍結が原因であり、Dup が結果である。**

したがって `Equal` 実装の前提は `Self` が `Dup`
属性を持つことである。これを満たさない場合、コンパイラは `Equal` のインスタンス化を拒否する。

#### インデックスインターフェース

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value`
は関連型のメンバではなく型パラメータとして表現**：RFC-011a のオープン問題は「関連型はジェネリクスインターフェースのパラメータを通じて実現する」と決定済みである（`Iterator: (Item: Type) -> Type`
が同型の先例）、`type` メンバ構文を導入する必要はない。

**マルチポジションインデックスはタプル化 + オーバーロード**で実現し、可変長インターフェースは導入しない：

```yaoxiang
// 1 次元コンテナ
List(T) を Index(List(T), Int, T) としてインスタンス化           → arr[0]

// 多次元コンテナ
Grid    を Index(Grid, Tuple(Int, Int), Float) としてインスタンス化 → g[0, 1]
//                    └─ Key はタプル

// 2 つのインスタンス化のシグネチャが異なる → RFC-011a のオーバーロード規則に従って共存
```

#### 伝播インターフェース

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    residual: (self: &Self) -> E
}
```

`T`（成功型）と `E`（エラー型）はいずれもインターフェース型パラメータである。

**`?` の型規則**：

```yaoxiang
// f: () -> Result(T, E)
// 関数本体の残り部分は Result(U, E) を要求する（エラー型は一致しなければならない）
x = f()?        // x: T、以下と等価：
                //   match f() {
                //       ok(v)  => v
                //       err(e) => return err(e)
                //   }
```

エラー型が一致しない場合はコンパイルエラー（既存の `E1083`
に対応）；外側関数の戻り型が伝播可能型でない場合は `E1081` を報告；式が `Try` を実装していない場合は
`E1082` の文言を差し替える（"Result" という具体名を挙げない）。

### 例

#### ユーザ定義型の算術と等価

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point),
    Equal(Point, Point)
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

Point.equal: (self: &Point, other: &Point) -> Bool =
    self.x == other.x and self.y == other.y

main = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   // Point(4.0, 6.0)
    println(a == b)             // false
    println(a == a)             // true
}
```

#### カスタムコンテナのインデックス

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### `Result` を std へ帰属させる（設計目標）

`Result` が `Try` を実装すれば、`?` は型名のハードコードに依存しなくなる：

```yaoxiang
// std.result 内（core での特別判定は不要）
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E),
    Try(Result(T, E), T, E)
}

Result.residual: (T: Type, E: Type)(self: &Result(T, E)) -> E =
    match self {
        ok(_) => abort_invalid_residual(),   // ok 経路は residual に到達しないはず
        err(e) => e
    }
```

#### ジェネリクス制約がついに履行可能に

```yaoxiang
// RFC-011 の例がついに実装可能になる
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

### 構文の変更

**新しい構文も新しいキーワードもない**。すべての能力は既存の機構の組み合わせで実現される：

| 能力                           | 再利用する既存機構                               |
| ------------------------------ | ------------------------------------------------ |
| インターフェース宣言           | RFC-011a Phase 1                                 |
| インターフェースインスタンス化 | RFC-011a Phase 2（`Dog: { Animal(Dog) }`）       |
| メソッド実装                   | RFC-011a Phase 3（外部宣言 `Point.add`）         |
| 関連型                         | RFC-011 §3.1（インターフェース型パラメータ）     |
| マルチポジションインデックス   | 既存のタプル化解析 + RFC-011a オーバーロード規則 |
| 演算子の優先順位               | **言語で固定**、ユーザによる定義は開放しない     |

## 詳細設計

### 型システムへの影響

**新規インターフェース**（Layer 2）：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
`Try`。

**登録済み trait の再利用**：`Equal` は既に `trait_data.rs`
に登録されているが**消費箇所がゼロ**である（`==` は現状、`unify` 後に `Bool`
を返すハードコードのみ）。本 RFC はこれを `==` の実契約として接続する。

**`Dup` 前置制約**：`Equal` のインスタンス化時に `Self` が `Dup` であるかを検査する。`Dup` /
`Linear` 属性は RFC-009 により推論される（`&T` 凍結 ⇒ Dup；`&mut T` 排他 ⇒ Linear）。

**制約解決**：`T: Add` の解決 = `T` が `Add`
インターフェースをインスタンス化しているかを調べること。機構は RFC-011a のコンパイル時型収集を再利用し、新しいソルバは導入しない。

### ランタイム挙動

**ランタイムオーバーヘッドはゼロ**：演算子はコンパイル時に呼び出し対象を決定する（静的ディスパッチ）。基本型（`Int`/`Float`/`String`/`List`）に対しては**ネイティブ命令の高速パス**を保持し、インターフェースディスパッチを経由しない。

`?` のランタイム挙動は変わらない（展開 + 早期リターン）。判定根拠が「型名 == "Result"」から「型が
`Try` を実装している」に変わるだけである。

### コンパイラの変更

| コンポーネント                       | 変更                                                                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `typecheck/inference/expressions.rs` | `infer_binary` のホワイトリストを「ネイティブ高速パス + インターフェース照会」の二経路に改修；`Index` / `Try` のインターフェース照会を新規追加 |
| 同上（`Try` 分岐）                   | `MonoType::make_result` のハードコードを削除、`Try` インスタンス化の照会に変更                                                                 |
| `middle/core/ir_gen.rs`              | `Expr::Try` から `group: "Result"` のハードコードを削除；`Expr::Index` にインターフェースディスパッチ分岐を追加                                |
| `typecheck/types/trait_data.rs`      | 8 つのインターフェースについて `Int` / `Float` / `String` / `List` などのデフォルトインスタンス化を登録                                        |
| 新規                                 | Layer 0 のマッピングテーブル定数 + 演算子→インターフェースの照会関数                                                                           |
| 診断                                 | `E1082` の文言を "requires Result" から "requires Try" に変更（`E1081` / `E1083` は既存踏襲）                                                  |

### 後方互換性

**基本型の演算は不変**：`1 + 2`、`"a" + "b"`、`[1] + [2]`、`1 < 2`
はすべてネイティブ経路を保持し、挙動も性能も変わらない。

**`%` のセマンティクスが変更**：`-7 % 3` は `-1`（remainder）から
`2`（modulo）に変わる。これは**意図的な修正**であり、移行ガイドに注記が必要。既存のテストコーパスに負数の
`%` に依存する用例はない（確認済み）。

**`f[0]` ポジションバインディングは不変**：`distance[0]`
は RFC-004 のコンパイラ組み込み機能であり、**`Index`
インターフェースを経由しない**ため影響を受けない。

**`?` は既存コードに対して透過的**：`Result` に `Try` インスタンス化を追加すれば、既存の `?`
の用法は完全に同一の挙動を維持する。

## トレードオフ

### 利点

- **RFC-011 を履行する**：`T: Add + Multiply + Zero`
  が紙上から実装可能なものとなり、既に受け入れ済みの RFC 本文は変更不要
- **`Result` の core 拘束を解除する**：`?` をインターフェース化すれば `Result`
  を std に帰属でき、階層化目標を引き継ぐ
- **実測で見つかった欠陥を修正する**：`Point == Point` が動作するようになり、`list.contains`
  が構造体に対して使用できない問題も連動して解消
- **新構文ゼロ**：すべて RFC-011a の既存機構を再利用し、parser の構文規則には触れない（RFC-036 の新構文ゼロ原則に従う）
- **ランタイムオーバーヘッドゼロ**：静的ディスパッチ + 基本型のネイティブ高速パス
- **ユーザ定義コンテナが利用可能**：`Box(T)[0]` は「一律エラー」から「使用可能」へ

### 欠点

- **`%` のセマンティクス変更は破壊的変更**：セマンティクス上の理由は明確だが、移行ガイドが必要
- **`Equal` の暗黙の `Dup` 要求により一部型が拒否される**：リニア型の値は `==`
  に参加できない、これはセマンティクス上正しいことの代償だが、ユーザには意外に感じられる可能性があり、明確な診断情報が必要
- **インターフェースインスタンス化は明示的コスト**：各演算子に対しインターフェースインスタンス化 1 行とメソッド 1 つを書く必要がある。RFC-011a の構文上、暗黙の推論は不可能である（引き換えに
  `Self` 型パラメータに魔法がない）

## 代替案

### 案 A：Layer 1 のみ実装（メソッド名によるディスパッチ）でインターフェース層は作らない

`+` は `add` という名前のメソッドが存在するかを調べるだけで、`Add`
インターフェースの実装は要求しない。

**却下理由**：RFC-011 の `T: Add`
制約が演算子から乖離する——制約はインターフェースを調べ、演算子はメソッド名を調べるため、両者が矛盾する答えを返しうる。さらにコンパイル時に「`+`
を加算不可能な型に使用」に対して正確な診断を提供できない。

### 案 B：コンストラクタ構文 `Ok(x)` / `Some(x)` を導入して `?` 問題を解決する

`?` をインターフェース化せず、和型にコンストラクタ構文を追加する。

**却下理由**：RFC-010（受け入れ済み）と衝突する。RFC-010 は「和型はレコード型で統一して表現し、**2 セットの構文は不要**」と明記し、`|`
構文を明示的に廃止している。コンストラクタ構文の導入は第二の表現を導入することになる。さらにこれは
`?` のみを解決し、`Point == Point` やカスタムコンテナのインデックスは解決しない。

### 案 C：比較演算子も初回からインターフェース化する（`Ordering` を導入）

`<` `<=` `>` `>=` を `Compare` インターフェース化し、3 値の `Ordering` を返す。

**却下理由**：`<`
は YaoXiang において既に**第一級 IR 命令**である（`Instruction::Lt/Le/Gt/Ge`）。インターフェース化すると基本型が迂回を強いられる。さらに
`Ordering` を導入すると、`Ordering` 自身の比較/ソート、浮動小数点 `NaN` の `PartialOrd` vs `Ord`
など一連の問題が派生し、独立した RFC の規模になる。現状の実測で顕在化した要件（`Point == Point`、`list.contains`）は
**`Equal` のみ**で十分である。

### 案 D：演算子名を短縮形で命名する（`Add` インターフェースのメソッドは `add`、インターフェースは `Mul`）

**却下理由**：RFC-011 本文には既に `T: Add + Multiply + Zero`
と書かれており、短縮形を採用するには受け入れ済み RFC を変更する必要がある。

## 実装戦略

### 依存関係

| 依存                                    | ステータス  | 本 RFC のどの部分に影響するか                                                  |
| --------------------------------------- | ----------- | ------------------------------------------------------------------------------ |
| RFC-011a インターフェース機構 Phase 1–3 | ✅ 実装済み | Layer 2 の基盤（実測で動作確認済み）                                           |
| RFC-010 レコード式構築経路              | ❌ 未実装   | **`?` の構築側**（`Result` 値が構築できなければ `Try` を完全にテストできない） |
| RFC-039 バリアント分解                  | ❌ 紙上     | `Result.residual` の `match` 記法                                              |
| RFC-009 `Dup`/`Linear` 推論             | 一部        | `Equal` の前置制約検査                                                         |

### フェーズ分け

**インターフェース依存関係**（設計上の制約であり、スケジュールではない）に基づき 2 グループに分ける：

**フェーズ 1 — RFC-010/039 に依存しない**：

- Layer 0 マッピングテーブル + Layer 1 ディスパッチ接続
- `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` の 7 インターフェース
- `Equal` ⇒ `Dup` 前置制約
- 基本型のネイティブ高速パスを維持
- **効果**：`Point + Point`、`Point == Point`、`Box(T)[0]` のすべてが利用可能

**フェーズ 2 — RFC-010 / RFC-039 に依存**：

- `Try` インターフェース + `?` のインターフェース化
- `Result` を core から std へ移管
- **ブロック理由**：`Result` 値の構築（RFC-010）と分解（RFC-039）が必要

### リスク

| リスク                                                                 | 緩和策                                                                                                                 |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `%` のセマンティクス変更が既存ユーザコードを破壊する                   | 移行ガイド + テストコーパスに負数 `%` 依存の用例がないことを確認済み                                                   |
| インターフェースインスタンス化の明示的コストがユーザに煩雑と感じられる | 診断情報で「X インターフェースの実装が必要」と通知し、インスタンス化の例を提示                                         |
| 基本型の二重経路（ネイティブ + インターフェース）が不整合になる        | ゲート：`Int` 等がインターフェースを実装する場合、そのメソッドのセマンティクスはネイティブ命令と一致しなければならない |
| Layer 2 ゲートにより既存コードがコンパイル失敗する                     | `Equal` は現状消費箇所ゼロであり、接続後に影響を受けるのは元々エラーになっていた用法のみ                               |

## 他の RFC との連携

本 RFC の位置付けは**消費側の要求提起者**であり、連携一貫性を担保するために以下の RFC を同期的に更新する必要がある（改訂は承認済み）：

| RFC                         | 更新が必要な内容                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------- |
| **RFC-011**（受け入れ済み） | §制約 にて `Add` / `Multiply` 等が RFC-011b で定義・実装されることを明記                          |
| **RFC-010**（受け入れ済み） | 「レコードフィールドがそのままコンストラクタである」ことの実装要件を明確化——`?` フェーズ 2 の前提 |
| **RFC-039**（ドラフト）     | 構築と分解は対でなければならない；網羅性検査の `std` バリアント集合の扱い                         |
| **RFC-009**（受け入れ済み） | `Equal` ⇒ `Dup` 前置を §型属性 にて相互参照                                                       |

## 付録A：調査証拠

以下の実測はすべて **0.8.0**（`target/debug/yaoxiang-rs.exe`）上で再現した。

### A.1 インターフェース機構の利用可否（本 RFC の基盤）

| 能力                                                                               | 実測                                                                 |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| インターフェース宣言 `Animal: (Self: Type) -> Type = {...}`                        | ✅ 定義可能                                                          |
| インターフェースインスタンス化 + 外部メソッド `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ 実行可能、出力正常                                                |
| インターフェースインスタンス化 + **内部**メソッド宣言                              | ❌ `E1097`（フィールドとメソッドが名前空間を共有することによる衝突） |
| メソッドディスパッチ `d.speak()`                                                   | ✅ 実行可能                                                          |

**注**：`E1097`
は演算子メソッドが**外部宣言**形式（`Point.add: (self: &Point, ...)`）でなければならないことを意味する。RFC-011a の例と一致している。

### A.2 演算子の現状

| 式                                     | 現状                                                          |
| -------------------------------------- | ------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]`    | ✅ ハードコードされたホワイトリスト（Int/Float/String/List）  |
| `Point(1,2) == Point(1,2)`             | ❌ `E6007`（Struct 上で Eq が成立しない）                     |
| `f[0]`（関数ポジションバインディング） | ⚠️ バインディング宣言内でのみ有効、式として使用すると `E3006` |
| `arr[0, 1]`（マルチポジション）        | ✅ タプル化、`list([1, 2])`                                   |
| `-7 % 3`                               | `-1`（remainder、modulo ではない）                            |

### A.3 `?` のハードコード箇所

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

両箇所ともインターフェース照会への変更が必要。

## 付録C：用語集

| 用語                     | 定義                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| Layer 0                  | 演算子 → メソッド名の固定マッピングテーブル、言語レベル定数、ユーザは変更不可                   |
| Layer 1                  | `Type.method` キーで表引きして呼び出すディスパッチベース                                        |
| Layer 2                  | インターフェース契約層、ジェネリクス制約の根拠を提供し、同時に演算子の許可ゲートとなる          |
| ネイティブ高速パス       | 基本型（Int/Float/String/List）が保持するハードコードの演算経路で、インターフェースを経由しない |
| ポジションバインディング | RFC-004 の `f[0]` 構文、関数の引数位置をメソッドにバインドする、コンパイル時挙動                |
