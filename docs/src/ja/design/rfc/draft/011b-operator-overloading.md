## 概要

YaoXiang に**演算子オーバーロード**能力を補完し、`a + b` / `a == b` / `a[i]` / `e?`
をユーザ定義型で実装可能にする。これにより RFC-011 に既記載された `T: Add + Multiply + Zero`
制約を**机上の能力**から実装可能なメカニズムへと昇格させる。

設計は**三層の責務分離**を採用する：固定の演算子→メソッドマッピングテーブル（Layer
0）、名前でディスパッチする基層（Layer 1、既存の `method_bindings`
を再利用）、インタフェース契約層（Layer
2、ジェネリクス制約用）。演算子の**優先度と結合性は言語固定**であり、ユーザはセマンティクスのみをオーバーロードする。

初回対象範囲：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` `Try`
の8つのインタフェース。新規キーワード導入なし、新規構文構造導入なし。

## 動機

### なぜこの特性が必要か

#### 1. RFC-011 の中心的な例がこれに依存しているが、現状は机上の能力

RFC-011（承認済み）は8箇所で演算子名を型制約として使用している：

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

これは RFC-011「値依存型 + コンパイル時次元検証」の看板例である。しかし**全 RFC 中、いかなる文書も
`Add` / `Multiply` がどこから来るのか、`+`
がそれらにどうバインドされるのかを定義していない**。`T: Add`
は現状、履行できないアサーションに過ぎない。

#### 2. ユーザ定義型が基本演算に参加できない（実測済み）

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

連動する帰結：`list.contains(list_of_structs, p)` は**完全に使用不能**となる — 内部で `==`
に依存しているためである。

#### 3. `?` が型名をコンパイラにハードコードしており、`Result` の std 移行を阻む

`?` の実装は型名とバリアント番号を同時にハードコードしている：

```rust
// typecheck：ハードコードによる Result 型の構築
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen：グループ名とバリアント番号のハードコード
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

これにより `Result` は core に残留せざるを得ない。`?`
を**インタフェース駆動**に変更すれば、当該インタフェースを実装する任意の型（ユーザ定義型を含む）が
`?` を使用可能となり、`Result` を std 配下に置ける。

#### 4. ユーザ定義コンテナがインデックスできない

`Index` の型検査はハードコードされたホワイトリストである：

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// 上記以外 → "型レベルで認識しないコンテナは黙って拒否する"
```

ユーザが任意のコンテナ型を定義すると、`c[0]` は一律エラーとなる。

### 既存の半完成基礎

調査の結果、メカニズムの**大部分は既に存在し**、不足しているのは結線のみである：

| メカニズム                                                    | 位置                                  | 状態                                 |
| ------------------------------------------------------------- | ------------------------------------- | ------------------------------------ |
| インタフェース宣言 `(Self: Type) -> Type`                     | RFC-011a Phase 1                      | ✅ 実行可能                          |
| インタフェースインスタンス化 `Animal(Dog)` + 外部メソッド宣言 | RFC-011a Phase 2–3                    | ✅ 実行可能                          |
| メソッドディスパッチ `method_bindings["Type.method"]`         | `expressions.rs:1299`                 | ✅ 実行可能                          |
| 関連型（= インタフェースの型パラメータ）                      | RFC-011 §3.1；RFC-011a は本方式を採択 | ✅ メカニズム確定                    |
| 型族評価 `AssociatedTypeDef`                                  | `dependent_types.rs`                  | ✅ 本番用例 `std.assert` の `IsTrue` |
| `Equal` / `Dup` / `Clone` / `Debug` trait                     | `trait_data.rs` に登録済み            | ⚠️ `Equal` は**消費箇所ゼロ**        |
| 演算子 → メソッド名マッピング                                 | —                                     | ❌ 不在                              |

**結論**：これはゼロから機能を起こすのではなく、既存部品を結線し文書化する作業である。

## 提案

### 中核設計：三層責務分離

```
Layer 0  固定マッピングテーブル（言語レベル定数、ユーザ変更不可）
         + → add    == → equal    [] → index    ? → residual
         │  コンパイル時に内蔵、型推論には参加しない、ユーザに非公開
         ▼
Layer 1  ディスパッチ基層（名前でメソッドを検索し呼び出す）  ← 既存メカニズムを再利用
         method_bindings["Point.add"]
         ▼
Layer 2  インタフェース契約（ジェネリクス制約用）
         Add / Equal / Index / Try …
         T: Add 制約を成立させ、演算子の通行ゲートとして機能する
```

**階層化の理由**：

- **Layer 0 と 1 が演算子を「使える」ようにする**。Layer
  2 が演算子を「制約できる」ようにする。統合すると、`add` という名前の任意のメソッドが `+`
  で呼ばれることになり、RFC-011 の `T: Add` と演算子が乖離する。
- **Layer 1 は新規実装しない**：`method_bindings` は既に `Type.method`
  キーでルックアップしている（フィールド検索失敗後のフォールバック経路）。演算子も同じ経路を通せばよい。
- **Layer
  2 はゲートである**：演算子の通行前には**必ず**対応インタフェースの実装を確認する必要がある（§「なぜインタフェース実装が必須か」参照）。

### Layer 0：固定マッピングテーブル

| 演算子            | インタフェース                                    | メソッド   | 初回対象 |
| ----------------- | ------------------------------------------------- | ---------- | -------- |
| `+`               | `Add`                                             | `add`      | ✅       |
| `-`               | `Subtract`                                        | `subtract` | ✅       |
| `*`               | `Multiply`                                        | `multiply` | ✅       |
| `/`               | `Divide`                                          | `divide`   | ✅       |
| `%`               | `Modulo`                                          | `modulo`   | ✅       |
| `==` `!=`         | `Equal`                                           | `equal`    | ✅       |
| `[]`              | `Index`                                           | `index`    | ✅       |
| `?`               | `Try`                                             | `residual` | ✅       |
| `<` `<=` `>` `>=` | —（ネイティブ命令として保持）                     | —          | ❌       |
| `and` `or`        | —（短絡は言語セマンティクス、オーバーロード不可） | —          | ❌       |
| ビット演算 5 個   | —                                                 | —          | ❌       |
| 単項 `-` `!`      | —                                                 | —          | ❌       |

**インタフェース名は短縮形ではなく完全綴り**（`Mul` ではなく `Multiply`）：RFC-011 本文の
`T: Add + Multiply + Zero` との整合性を保つため、**承認済み RFC を変更しない**。

**`%` は `Modulo`
セマンティクスを採用**（数学的剰余、結果の符号は除数に従う）。現在の実装は remainder 動作（`-7 % 3`
は現状 `-1`
を返す）であり、これは**意図的なセマンティクス修正**である — 名称が数学的剰余として意味を固定する。

### Layer 2：インタフェース定義

#### 算術インタフェース

```yaoxiang
Add: (Self: Type, R: Type) -> Type = {
    add: (self: &Self, other: &R) -> Self
}

Subtract: (Self: Type, R: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> Self
}

Multiply: (Self: Type, R: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> Self
}

Divide: (Self: Type, R: Type) -> Type = {
    divide: (self: &Self, other: &R) -> Self
}

Modulo: (Self: Type, R: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> Self
}
```

`R` は右オペランド型であり、左右異型を許容する（例：`Int + Float`）。戻り値型は固定で `Self`
（`&Self` は受信側借用、RFC-009 借用トークンと RFC-011a 受信側規約を参照）。

#### 等価インタフェース

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` は暗黙に `Dup` を要求する**：`==`
のセマンティクスは「2つの値を比較する」ことであり、双方が読み取り可能である必要がある。線形型（`Dup`
非保有）の値は一度しか読めず、比較に参加できない。RFC-009 は既に以下の因果連鎖を示している：

> **因果関係を逆転させてはならない：凍結が原因であり、Dup は結果である。**

したがって `Equal` の実装前提は `Self` が `Dup` 属性を保有することであり、非保有の型に対する `Equal`
インスタンス化はコンパイラが拒否する。

#### インデックスインタフェース

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value`
は関連型のメンバではなく型パラメータとして扱う**：RFC-011a のオープンイシューは「関連型はジェネリクスのインタフェース型パラメータで実現する」と決着済み（`Iterator: (Item: Type) -> Type`
が同型の先例）、`type` メンバ構文を導入する必要はない。

**複数位置インデックスはタプル詰め + オーバーロードで実現**し、可変長引数インタフェースは導入しない：

```yaoxiang
// 1次元コンテナ
List(T) は Index(List(T), Int, T) をインスタンス化           → arr[0]

// 多次元コンテナ
Grid    は Index(Grid, Tuple(Int, Int), Float) をインスタンス化  → g[0, 1]
//                    └─ Key はタプル

// 2つのインスタンス化シグネチャが異なる → RFC-011a のオーバーロード規則で共存
```

#### エラー伝播インタフェース

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    residual: (self: &Self) -> E
}
```

`T`（成功型）と `E`（エラー型）は共にインタフェースの型パラメータである。

**`?` の型規則**：

```yaoxiang
// f: () -> Result(T, E)
// 関数の残り本体は Result(U, E) を要求する（エラー型は一致必須）
x = f()?        // x: T、以下と等価：
                //   match f() {
                //       ok(v)  => v
                //       err(e) => return err(e)
                //   }
```

エラー型が不一致の場合はコンパイルエラー（既存の `E1083`
に対応）。外側関数の戻り型が伝播可能型でない場合は `E1081` を報告。式が `Try` を実装していない場合は
`E1082` の文言を差し替える（"Result" という具体名を挙げるのではなく）。

### 例

#### ユーザ定義型の算術と等価

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point),
    Equal(Point, Point)
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

Point.equal: (self: &Point, other: &Point) -> Bool =
    self.x == other.x and self.y == other.y

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   // Point(4.0, 6.0)
    println(a == b)             // false
    println(a == a)             // true
}
```

#### ユーザ定義コンテナのインデックス

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### `Result` を std 配下に移す（設計目標）

`Result` が `Try` を実装することで、`?` は型名ハードコードへの依存を解消する：

```yaoxiang
// std.result 内（core での特例分岐不要）
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E),
    Try(Result(T, E), T, E)
}

Result.residual: (T: Type, E: Type)(self: &Result(T, E)) -> E =
    match self {
        ok(_) => abort_invalid_residual(),   // ok 経路では residual に到達しない
        err(e) => e
    }
```

#### ジェネリクス制約がついに履行可能に

```yaoxiang
// RFC-011 の例がついに実装可能になる
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

### 構文変更

**新規構文なし、新規キーワードなし**。すべての能力は既存メカニズムの組み合わせで実現される：

| 能力                         | 再利用する既存メカニズム                           |
| ---------------------------- | -------------------------------------------------- |
| インタフェース宣言           | RFC-011a Phase 1                                   |
| インタフェースインスタンス化 | RFC-011a Phase 2（`Dog: { Animal(Dog) }`）         |
| メソッド実装                 | RFC-011a Phase 3（外部宣言 `Point.add`）           |
| 関連型                       | RFC-011 §3.1（インタフェース型パラメータ）         |
| 複数位置インデックス         | 既存のタプル詰め解析 + RFC-011a オーバーロード規則 |
| 演算子優先度                 | **言語固定**、ユーザカスタマイズ不可               |

## 詳細設計

### 型システムへの影響

**新規インタフェース**（Layer 2）：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
`Try`。

**登録済み trait の再利用**：`Equal` は既に `trait_data.rs`
に登録されているが**消費箇所ゼロ**である（`==` は現状 `unify` 後のハードコードで `Bool`
を返すのみ）。本 RFC はこれを `==` の実契約として結線する。

**`Dup` 前提制約**：`Equal` インスタンス化時に `Self` が `Dup` を持つか検査する。`Dup` / `Linear`
属性は RFC-009 が導出する（`&T` 凍結 ⇒ Dup；`&mut T` 排他 ⇒ Linear）。

**制約解決**：`T: Add` の解決 = `T` が `Add`
インタフェースをインスタンス化しているかの照合。メカニズムは RFC-011a のコンパイル時型収集を再利用し、新規ソルバは導入しない。

### ランタイム挙動

**ランタイムオーバーヘッドゼロ**：演算子はコンパイル時に呼出先を確定する（静的ディスパッチ）。基本型（`Int`/`Float`/
`String`/`List`）には**ネイティブ命令のファストパスを保持**し、インタフェース経由のディスパッチは行わない。

`?` のランタイム挙動は不変（展開 + 早期 return）であり、判定基準が「型名 == "Result"」から「型が
`Try` を実装」へ変わるのみ。

### コンパイラ変更

| コンポーネント                       | 変更                                                                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `typecheck/inference/expressions.rs` | `infer_binary` のホワイトリストを「ネイティブファストパス + インタフェース照会」の二経路に変更；`Index` / `Try` のインタフェース照会を追加 |
| 同上（`Try` 分岐）                   | `MonoType::make_result` ハードコードを撤去、`Try` インスタンス化照会に置換                                                                 |
| `middle/core/ir_gen.rs`              | `Expr::Try` の `group: "Result"` ハードコードを撤去；`Expr::Index` にインタフェースディスパッチ分岐を追加                                  |
| `typecheck/types/trait_data.rs`      | 8 つのインタフェースのデフォルトインスタンス化（`Int` / `Float` / `String` / `List` 等）を登録                                             |
| 新規                                 | Layer 0 マッピングテーブル定数 + 演算子→インタフェース照会関数                                                                             |
| 診断                                 | `E1082` 文言を "requires Result" から "requires Try" に変更（`E1081`/`E1083` は流用）                                                      |

### 後方互換性

**基本型演算は不変**：`1 + 2`、`"a" + "b"`、`[1] + [2]`、`1 < 2`
はすべてネイティブ経路を保持し、挙動も性能も変わらない。

**`%` セマンティクスの変更**：`-7 % 3` は `-1`（remainder）から
`2`（modulo）へ変わる。これは**意図的な修正**であり、移行ガイドでの明記が必要。既存テストコーパスに負数
`%` に依存する用例は存在しない（確認済み）。

**`f[0]` 位置バインディングは不変**：`distance[0]` は RFC-004 のコンパイラ内蔵能力であり、**`Index`
インタフェースを経由しない**ため影響を受けない。

**`?` は既存コードに対して透過的**：`Result` に `Try` インスタンス化を補えば、既存の `?`
使用法は挙動が完全一致する。

## トレードオフ

### 利点

- **RFC-011 を履行する**：`T: Add + Multiply + Zero`
  を机上から実装可能へ昇格、承認済み RFC 本文に手を入れない
- **`Result` の core 拘束を解消**：`?` インタフェース化により `Result`
  を std 配下に移せ、階層化目標を引き継ぐ
- **実測上の欠陥を修復**：`Point == Point` が使用可能となり、`list.contains`
  の構造体非対応も連動して解消
- **新規構文ゼロ**：すべて RFC-011a 既存メカニズムを再利用し、parser の構文規則に触れない（RFC-036 ゼロ構文変更原則を遵守）
- **ランタイムオーバーヘッドゼロ**：静的ディスパッチ + 基本型ネイティブファストパス
- **ユーザ定義コンテナが使用可能に**：`Box(T)[0]` が「一律エラー」から「使用可能」へ

### 欠点

- **`%` セマンティクス変更は破壊的変更**：正当な意味的理由があるにせよ、移行ガイドが必要
- **`Equal` の暗黙的 `Dup` 依存は一部型を拒否する**：線形型の値は `==`
  できない。セマンティクス上は正しい帰結だが、ユーザには奇異に映る可能性があり、明確な診断情報が求められる
- **インタフェースインスタンス化は明示的コスト**：各演算子に対し 1 行のインタフェースインスタンス化と 1 つのメソッド実装が必要。RFC-011a の構文上、暗黙導出は不可能（引き換えに
  `Self` 型パラメータに魔法がない）

## 代替案

### 案 A：Layer 1 のみ実装（メソッド名ディスパッチ）、インタフェース層は実装しない

`+` は単に `add` というメソッドが存在するかを照会し、`Add` インタフェース実装を要求しない。

**却下理由**：RFC-011 の `T: Add`
制約が演算子から乖離する — 制約はインタフェースを照会し、演算子はメソッド名を照会するため、両者が不一致の答えを返しうる。また「`+`
を加算不可能な型に適用」に対する正確なコンパイル時診断を提供できない。

### 案 B：コンストラクタ構文 `Ok(x)` / `Some(x)` を導入して `?` 問題を解決

`?` をインタフェース化せず、和型にコンストラクタ構文を追加する。

**却下理由**：RFC-010（承認済み）と衝突する。RFC-010 は「和型の表現には統一してレコード型を使用し、
**2 セットの構文は不要**」と明記し、`|`
構文を明示的に廃止している。コンストラクタ導入は第二の表現セットを導入することになる。しかも `?`
のみを解決し、`Point == Point` とユーザ定義コンテナインデックスは未解決のまま残される。

### 案 C：比較演算子も初回対象に追加（`Ordering` 導入）

`<` `<=` `>` `>=` を `Compare` インタフェース化し、3 値 `Ordering` を返す。

**却下理由**：`<`
は YaoXiang において既に**第一級 IR 命令**（`Instruction::Lt/Le/Gt/Ge`）であり、インタフェース化により基本型は迂回を強制される。さらに
`Ordering` を導入すると、`Ordering` 自身の比較・順序付け、浮動小数点 `NaN` における `PartialOrd` vs
`Ord`
など一連の問題が連鎖し、独立 RFC 規模の議論となる。現在実測で露見した要件（`Point == Point`、`list.contains`）は**`Equal`
のみ**で充足可能。

### 案 D：演算子名に短縮形を使用（`Add` インタフェースのメソッドは `add`、インタフェースは `Mul`）

**却下理由**：RFC-011 本文に既に `T: Add + Multiply + Zero`
と記載されており、短縮形採用は承認済み RFC の変更を伴う。

## 実装戦略

### 依存関係

| 依存                                  | 状態        | 本 RFC への影響箇所                                                  |
| ------------------------------------- | ----------- | -------------------------------------------------------------------- |
| RFC-011a インタフェース機構 Phase 1–3 | ✅ 実装済み | Layer 2 の基礎（実測実行可能）                                       |
| RFC-010 レコード式構築経路            | ❌ 未実装   | **`?` の構築側**（`Result` 値を構築できなければ `Try` 完全検証不能） |
| RFC-039 バリアント分解                | ❌ 紙面     | `Result.residual` の `match` 記法                                    |
| RFC-009 `Dup`/`Linear` 導出           | 一部        | `Equal` の前提制約検査                                               |

### 段階分け

**インタフェース依存順**（設計上の制約であり、スケジュールではない）で 2 グループに分割：

**段階 1 — RFC-010/039 に依存しない**：

- Layer 0 マッピングテーブル + Layer 1 ディスパッチ結線
- `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` の 7 インタフェース
- `Equal` ⇒ `Dup` 前提制約
- 基本型ネイティブファストパスの保持
- **効果**：`Point + Point`、`Point == Point`、`Box(T)[0]` がすべて使用可能

**段階 2 — RFC-010 / RFC-039 に依存**：

- `Try` インタフェース + `?` のインタフェース化
- `Result` を core から std へ移設
- **ブロック理由**：`Result` 値の構築（RFC-010）と分解（RFC-039）が必要

### リスク

| リスク                                              | 緩和策                                                                                           |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `%` セマンティクス変更が既存ユーザコードを破壊      | 移行ガイド + テストコーパスに負数 `%` 依存がないことを事前確認                                   |
| インタフェースインスタンス化の明示的コストが煩雑    | 診断情報で「X インタフェースの実装が必要」と明示しインスタンス化例を提示                         |
| 基本型の二経路（ネイティブ + インタフェース）不整合 | ゲート：`Int` 等はインタフェースを実装するが、メソッドのセマンティクスはネイティブ命令と一致必須 |
| Layer 2 ゲートにより既存コードがコンパイル失敗      | `Equal` は現状消費箇所ゼロ、結線により影響を受けるのは元々エラーだった用法のみ                   |

## 他の RFC との協調

本 RFC の位置付けは**消費側要求の提案者**であり、協調一貫性確保のため以下の RFC を同期更新する必要がある（改訂は承認済み）：

| RFC                     | 更新内容                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------ |
| **RFC-011**（承認済み） | §制約 にて `Add` / `Multiply` 等が RFC-011b により定義・実装される旨を明記           |
| **RFC-010**（承認済み） | 「レコードフィールドがコンストラクタを兼ねる」の実装要件を明確化 — `?` 段階 2 の前提 |
| **RFC-039**（ドラフト） | 構築と分解は対でなければならない；`std` のバリアント集合に対する網羅性検査の扱い     |
| **RFC-009**（承認済み） | `Equal` ⇒ `Dup` 前提を §型属性 に相互参照リンクとして記載                            |

## 付録A：調査エビデンス

以下の実測はすべて **0.8.0**（`target/debug/yaoxiang-rs.exe`）上で再現。

### A.1 インタフェース機構の可用性（本 RFC の基礎）

| 能力                                                                             | 実測                                                     |
| -------------------------------------------------------------------------------- | -------------------------------------------------------- |
| インタフェース宣言 `Animal: (Self: Type) -> Type = {...}`                        | ✅ 定義可能                                              |
| インタフェースインスタンス化 + 外部メソッド `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ 実行可能、出力正常                                    |
| インタフェースインスタンス化 + **内部**メソッド宣言                              | ❌ `E1097`（フィールドとメソッドが名前空間を共有し衝突） |
| メソッドディスパッチ `d.speak()`                                                 | ✅ 実行可能                                              |

**注**：`E1097`
は演算子メソッドを**外部宣言形態**（`Point.add: (self: &Point, ...)`）で記述する必要があることを意味する。RFC-011a の例と一致する。

### A.2 演算子の現状

| 式                                  | 現状                                                          |
| ----------------------------------- | ------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]` | ✅ ハードコードホワイトリスト（Int/Float/String/List）        |
| `Point(1,2) == Point(1,2)`          | ❌ `E6007`（Struct 上で Eq 不成立）                           |
| `f[0]`（関数位置バインディング）    | ⚠️ バインディング宣言内でのみ有効、式として使用すると `E3006` |
| `arr[0, 1]`（複数位置）             | ✅ タプル詰め、`list([1, 2])`                                 |
| `-7 % 3`                            | `-1`（remainder、modulo ではない）                            |

### A.3 `?` のハードコード位置

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

両箇所をインタフェース照会に置き換える必要がある。

## 付録C：用語集

| 用語                   | 定義                                                                            |
| ---------------------- | ------------------------------------------------------------------------------- |
| Layer 0                | 演算子 → メソッド名の固定マッピングテーブル、言語レベル定数、ユーザ変更不可     |
| Layer 1                | `Type.method` キーでルックアップし呼び出すディスパッチ基層                      |
| Layer 2                | インタフェース契約層、ジェネリクス制約の根拠を提供し、演算子の通行ゲートとなる  |
| ネイティブファストパス | 基本型（Int/Float/String/List）専用のハードコード演算経路、インタフェース非経由 |
| 位置バインディング     | RFC-004 の `f[0]` 構文、関数の引数位置をメソッドとして束縛するコンパイル時挙動  |
