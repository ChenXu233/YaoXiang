# RFC-009a: トークンライフタイム分析——ホーア証明パイプラインに基づく

> **親 RFC**: [RFC-009: 所有権モデル設計](../accepted/009-ownership-model.md)
>
> **依存**:
> [RFC-027: コンパイル時述語と統一静的検証](../accepted/027-compile-time-evaluation-types.md)
>
> **前提条件**:
> RFC-027 は承認済みであること。本 RFC の全ての機構（証明パイプライン、SMT フォールバック、パス条件収集）は RFC-027 の実装に依存する。
>
> **本 RFC は RFC-009
> §「トークン競合検出：フロー敏感活性分析」（第 663-684 行）を修正し、置換する。**

## 要約

RFC-009 第 684 行は、トークン競合検出が「……NLL を必要としない」と主張している。結論は正しいが、論拠は誤っている。

「トークンは値であり、線形追跡で十分」というわけではない。**トークン活性はホーア論理の命題であり、専用のフロー敏感分析ではない**ためである。

`{conflicting_tokens 全て死亡} op {WriteToken 安全取得}` —— 同じ

`{P} op {Q}`
は、型検査・述語検証と RFC-027 の証明パイプラインを共有する。新しい分析フレームワークはない。一つのパイプライン、複数の命題。

---

## 動機

### RFC-009 の混同

RFC-009 は二つの問題を混同している：

1. **線形追跡**（Move 後使用不可）—— `{v 未 move} use(v) {型一致}`。型検査器が既に持つ。
2. **トークンライフタイム相互作用**（子トークン生存 → 親トークン停止 → 子トークン死亡 → 親トークン復活）——

   `{conflicting_tokens 全て死亡} write(data) {安全}`。**活性分析**が必要であり、線形追跡ではない。

### 現状コードの実情

| コンポーネント                             | 状態                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| `BorrowChecker`                            | IR を線形走査し、明示的な `Borrow`/`Release` 命令に受動的に応答する      |
| `ControlFlowAnalyzer::analyze_instruction` | 空実装（`control_flow.rs:145-153`）                                      |
| `liveness_analysis`                        | 存在するが Drop 挿入のみに使用され、トークン競合には接続されていない     |
| Release 挿入                               | Call 命令の後にハードコード——純粋に字句スコープ（`ir_gen.rs:2734-2736`） |

**ユーザー可視の結果**：

```yaoxiang
data = vec![1, 2, 3]
view = &data              # 创建 ReadToken
x = view.total_count      # view 的最后使用
data.push(4)              # ❌ Release(view) 尚未执行，ReadToken "活着"
```

### なぜ書き直しが必要か

旧版（009a
v1）は「DAG で NLL を代替」するナラティブを用い、不要な新概念（保守的分岐規則、ループ特殊処理）を導入した。核心的矛盾が明確にされていない：**借用検査は独立したシステムではなく、ホーア命題の一形態である。**

## 核心設計

### 全てはホーアなり

```
型検査：    { x: Int }         x + 1         { result: Int }
借用検査：  { view 死亡 }      data.push(4)  { WriteToken 取得成功 }
述語検証：  { y > 0 }          divide(x, y)  { result: Int }
バックエッジ切断：{ i == n }   次のループ    { cond == false }
```

同じ形式
`{P} op {Q}`。コンパイラは各操作に対して事前命題 P を生成し、証明パイプラインに送り検証する。

**借用検査とユーザー述語は同じパイプラインを共有する。**
違いは命題を生成するのが誰か、証明できなかったときにどう扱うかのみ。

### 二類の述語、一つのパイプライン

|            | ユーザー述語              | システム述語（借用）                  |
| ---------- | ------------------------- | ------------------------------------- |
| 命題生成   | プログラマー（型注釈）    | コンパイラ（ブランド木 + 所有権規則） |
| 証明提供   | コンパイラ + プログラマー | **コンパイラ全自動**                  |
| 証明失敗   | 証明関数を書くか再構築    | コードを再構築（扉は開いているが稀）  |
| 可視性     | シグネチャ可視            | 暗黙的、型シグネチャを汚染しない      |
| 学習コスト | 使うときだけ学ぶ          | ゼロ                                  |

**システム述語の証明はプログラマーに証明関数を開かない——コンパイラが全自動で行う。**
証明失敗時にはユーザーがコードを再構築する。

**三種の失敗モード、同じ検証エンジン。**
型命題の証明失敗 → コンパイルエラー（回避不可）。借用命題の証明失敗 → コンパイルエラー、コード再構築（回避不可）。ユーザー述語の証明失敗 → コンパイルエラー、証明関数を書ける（回避可能）。失敗戦略は異なるが、検証エンジンは同じ——SMT ソルバー + コンパイラカーネル推論規則。違いは「証明失敗時に誰が証明を補完する責任を持つか」のみ——コンパイラはプログラマーの借用証明の記述を拒否する（借用命題の証明戦略は構造解析 +
SMT であり、プログラマーの介入は不要）が、ユーザー述語の証明関数は受け入れる。これはパイプラインが非統一なのではなく、命題分類による責任境界が異なるだけである。

これは Rust の `'a` とは異なる：`'a`
は必修科目、証明関数は選択科目——大多数のユーザーは生涯で選択科目の扉に遭遇しない。

### 借用命題：コンパイラ自動生成

ユーザーが `data.push(4)` と書くと、コンパイラは次の命題を自動生成する：

```
WriteToken(data, node) 取得可能
  = forall t in conflicting_tokens(data): t は node で死亡
  = forall t in brand_tree.children(data): forward_reachable(node) ∩ consumers(t) == ∅
```

**三つの規則、特殊ケースなし：**

1. **ブランド木**（RFC-009
   §2.7）が「誰と誰が競合するか」に答える：プレフィックス一致、O(depth)、深さ ≤ 3
2. **消費者リスト**（DAG 構築時に自動収集）が「トークンを最後に消費するのは誰か」に答える
3. **前方到達性**が「消費者がまだ実行可能か」に答える：構造切断 + 論理切断

### 前方到達性：消費者から逆方向に

トークン T の各消費者 C に対して：

```
C から出発し、DAG を逆方向 BFS。
エッジは切断される、次のいずれかの場合：
  1. break エッジ（構造切断）
  2. パス条件 ⇒ !loop_cond が SMT で真と証明される（論理切断、RFC-027 パイプライン）

切断されていない全エッジに沿って逆方向に伝播する（バックエッジを含む、バックエッジは活性を前のイテレーションに伝播する）。
到達可能な全ノードをマーク → unsafe。
```

クエリ：書込操作がノード W に → W ∉ unsafe → 安全。

**「保守的分岐規則」の発明は不要。「ループ内保守的生存」も不要。一つの逆方向 BFS + 二つの切断規則。**

### 証明戦略：高速経路優先、SMT フォールバック

```
各書込操作でトークンが必要
  │
  ├→ 高速経路：DAG 構造解析（95%+ のシナリオをカバー）
  │     │
  │     ├→ ブランド木プレフィックス一致 → 競合トークン発見（O(depth)）
  │     ├→ 逆方向 BFS、break がバックエッジを切断
  │     └→ 横断可能なバックエッジなし → 直接 Proved / Disproved 判定
  │
  └→ 低速経路：SMT 論理切断（高速経路が横断可能なバックエッジに遭遇したときのみ）
        │
        ├→ バックエッジ起点にパス条件あり → SMT で path_cond ⇒ !loop_cond を判定
        │     ├→ Proved → 論理切断 → 高速経路に降格して続行
        │     └→ Disproved / Unproven → バックエッジ横断 → unsafe マーク
        │
        └→ バックエッジ起点にパス条件なし → バックエッジを直接横断
```

**高速経路カバー**：線形コード、if/else、ループ + break、パス条件なしの while。
**低速経路カバー**：while ループ体内、パス条件がループ終了を示唆するとき。
**非カバー**：実行時条件が静的に証明不能 → バックエッジ横断 → unsafe
→ コンパイルエラー（ユーザー再構築）。

SMT は主力ではなく、安全網である。RFC-027 のユーザー述語とは異なる：ユーザー述語は SMT が主力；借用システム述語は構造解析が主力、SMT は構造解析が届かない辺境のみを補完する。

> **正誤表（2026-08-17、SMT 位置づけ修正）**：SMT は**精度層であり、健全性依存ではない**。借用システム述語の健全な判定は高速経路（区間 + 逆方向 BFS +
> break 切断）が完全に担う；SMT 論理切断は「ループ境界を持つ合法プログラムを通過させるか」を決定するのみ。SMT が利用不可 / タイムアウト / 未実装（RFC-027
> impl:
> in_progress）の場合、フォールバック = バックエッジ横断 = 保守的拒否、拒否すべきものは依然として必ず拒否される。
> **SMT なしの場合の保守度 = ループ内の借用 + 書込みを一律拒否、Rust NLL と同等**
> （Rust のプロダクション借用検査も同様に SMT を持たない）。SMT の実装は純粋な精度向上であり、健全性主線の delivery をブロックしない。

## ユースケース分析

### 線形コード

```yaoxiang
data = vec![1, 2, 3]        # 节点 1
view = &data                # 节点 2：消费 data，生产 ReadToken(#1)
x = view.total_count        # 节点 3：消费 view（= #1 的最后一个消费者）
data.push(4)                # 节点 4：需要 WriteToken(data)
```

逆方向 BFS を
`view.total_count`（ノード 3）から開始 → ノード 3 は #1 の最後の消費者 → ノード 4 > ノード 3
→ ノード 4 は unsafe にない → ✅

### if/else：特殊規則なし

```yaoxiang
view = &data
if cond {
    use(view)               # then 分支消费 view
} else {
    do_something_else()     # 不碰 view
}
data.push(4)                # view 的最后消费者在 if 内 → if 之后无消费者 → ✅
```

if/else は DAG の一つの複合ノード。内部消費はこのノードに帰属する。分岐状態をマージしない。保守的集計をしない。**後続に消費者がいるかは整数比較。**

> **明確化（#264 後）**：「分岐状態をマージしない」は**借用活性**（ブランド消費者逆方向 BFS）にのみ適用される。
> **move 状態**（変数所有権）は別の解析：per-CFG-node 前方向データフロー（#264、NLL/Polonius スタイル）、分岐合流時に**保守的 meet**（いずれかの分岐で Moved
> → 合流 Moved）、リテラルで到達不能な分岐（`if false`）は不参加。両者は階層化される：借用活性は「後続消費者がいるか」を見、move 解析は「変数が既に move されている可能性」を見る。

### 戻り値エスケープを伴う if/else

```yaoxiang
view = &data
result = if cond {
    view                     # view 逃逸到 result
} else {
    something_else
}
use(result)                  # 间接消费 view
data.push(4)                 # view 仍有消费者（use(result)）
                             # → push 在 unsafe → ❌ 正确报错
```

view は戻り値でエスケープ → `use(result)` が view の消費者 → `push` から逆方向に `use(result)`
に到達可能 → unsafe。

### ループ：break がバックエッジを切断

```yaoxiang
view = &data
loop {
    use(view)                # consumer
    if is_last {
        data.push(4)         # 写操作
        break                # ← 结构切断
    }
}
```

逆方向 BFS を `use(view)` から → バックエッジ → 前方向に `data.push(4)` まで → `break` に遭遇 →
**切断** → `data.push(4)` は unsafe にない → ✅

break なしの場合：

```yaoxiang
view = &data
loop {
    use(view)
    data.push(4)             # 无 break 切断 → 回边可穿越 → 下一轮 use(view) 可达
                             # → push 在 unsafe → ❌ 正确报错
}
```

### while：SMT 論理切断

```yaoxiang
view = &data
mut i: UpTo(n) = 0
while i < n {
    use(view)                # consumer
    i += 1
    if i == n {
        data.push(4)         # 路径条件：i == n
    }
}
```

逆方向 BFS を `use(view)` から → バックエッジ → `data.push(4)` まで → パス条件 `i == n` をチェック →
SMT クエリ：`i == n ⇒ !(i < n)`？→ Proved → **論理切断** → `data.push(4)` は unsafe にない → ✅

> 正誤表（2026-08-17）：`i == n` は書込ノード（if 分岐内の
> `data.push(4)`）自身のパス条件であり、判定対象は書込ノードである（§パス条件収集の正誤表規則 1 を参照）。

## 本質：ブランド ID こそが `'a`

「`'a` は不要」とは言わない。「`#42` こそが `'42`」と言う。

| Rust                       | YaoXiang                                | 等価性                                |
| -------------------------- | --------------------------------------- | ------------------------------------- |
| `'a`                       | `#42`                                   | コンパイル時ライフタイム識別子        |
| `'a: 'b` outlives 制約     | `#42` は `#42.field_x` のプレフィックス | 文字列プレフィックス比較 = 半順序関係 |
| NLL 活性伝播（CFG 不動点） | 逆方向 BFS（DAG）                       | 共に到達可能性計算                    |
| Polonius fact              | SMT 論理切断                            | 共にパス条件推論                      |
| 制約システム不動点求解     | ブランド木プレフィックス一致 + BFS      | 異なる符号化、同一問題                |

**我々は新しい解析を発明したのではなく、`'a` を型シグネチャ層から証明層に降ろしただけである。**
ブランド ID が行うことは `'a`
と完全に同一——借用の同一性マーク、派生関係の追跡、競合判定。唯一の違い：`'a`
はユーザーが書いた型シグネチャにある；`#42` はコンパイラ内部にある。

これは恥ずべきことではない。Curry-Howard は型は命題、プログラムは証明と述べる。`'a`
は命題の一部ではなく、証明戦略の一部である。Rust は証明戦略を命題シグネチャに書き込んだ。我々はそのあるべき場所に戻した。

### 言語設計制約が排除したもの

| 複雑性の出所                    | 回避？ | 理由                                                       |
| ------------------------------- | ------ | ---------------------------------------------------------- |
| 変数シャドーイング              | ✅     | 言語で禁止——一つの名前は同じものを指し続ける               |
| クロスイテレーション借用        | ✅     | 各イテレーションで新バインド——イテレーション間が自然に分離 |
| `'a` ライフタイム注釈           | ✅     | ブランドパス = `#42.field_x`、コンパイラが推論             |
| 名前付きライフタイム + 制約伝播 | ✅     | ブランドパスプレフィックス比較が明示的制約集合を代替       |
| 借用グラフ制約求解（Polonius）  | ✅     | ブランド木プレフィックス一致 + DAG 消費者クエリ            |
| ループ体内借用活性伝播          | ❌     | Rust と同じく処理が必要——逆方向 BFS + 論理切断を使用       |
| 条件分岐保守性                  | ❌     | Rust と同じ——SMT が証明可能なものをカバー、残り保守的拒否  |

### なぜ DAG が成立するか

YaoXiang の三つの言語設計制約が DAG 解析を成立させる：

- **変数シャドーイングなし**——一つの名前は同じものを指し続けるため、再バインド間追跡不要
- **for 各イテレーション新バインド**——イテレーション間が自然に分離、クロスイテレーション借用なし
- **構造化並行性**——タスク境界が明確、クロスタスク活性伝播不要

これらの制約は Rust
CFG 不動点反復の主要複雑性源を排除する。DAG が CFG より「高度」なのではなく、**より単純な言語設計がより単純な解析を可能にする**。

## 詳細設計

### システム述語一覧

コンパイラは以下の命題を自動生成し、RFC-027 証明パイプラインに送る：

| システム述語      | トリガ時機                     | 命題形式                                      |
| ----------------- | ------------------------------ | --------------------------------------------- |
| `borrow_conflict` | WriteToken(v) を必要とするとき | `forall t ∈ conflicting(v): dead_at(t, node)` |
| `use_after_move`  | 変数 v を使用                  | `¬moved(v)`                                   |
| `use_after_drop`  | 変数 v を使用                  | `¬dropped(v)`                                 |
| `double_drop`     | Drop(v)                        | `¬dropped(v)`                                 |
| `mut_violation`   | 不変変数 v へ書込              | `is_mut(v)`                                   |

既存の `BorrowChecker`、`MoveChecker`、`DropChecker`、`MutChecker` は
**命題生成器になる**——消えるのではなく、役割を変える。これらは命題を生成し、パイプラインが検証する。

### ブランド木

RFC-009 §2.7 のブランド機構をブランド木として形式化する。

**トークン意味論——コピー優先ではなく凍結優先**：

`&T` と `&mut T` の本質的違いは「コピー可能かどうか」ではなく、「同時書込を許すかどうか」である：

```
ReadToken(T)：  読み取り専用権限を付与し、同時にソースデータ T を凍結する——この期間中
               任意の WriteToken(T) は取得不可。凍結が ReadToken の第一義的意味論である。
               Dup（コピー可能）は凍結の帰結：データは凍結済（突然変異可能性なし）なので、
               複数の読み取り専用ビューが自然に安全。

WriteToken(T)： 排他的読み書き権限を付与。書込が存在するため、他のトークン（読み・書きいずれも）
               は共存不可。Dup を実装しない（線形型）のは排他性の帰結。
```

**因果関係**：

```
ReadToken 存在 → ソースデータ凍結 → 複数読み取り専用が安全 → Dup
                      ↓
              WriteToken 拒否（borrow_conflict システム述語が強制）
```

ではなく：

```
ReadToken は Dup を持つ → 複数持てる → ついでに競合をチェック  ← 因果転倒
```

```
BrandTree:
  nodes: Map<BrandId, BrandNode>

BrandNode:
  id: BrandId               # "#42"、"#42.field_x"
  kind: ReadToken | WriteToken
  source_var: Operand
  parent: Option<BrandId>   # 派生関係の親ノード
  children: Set<BrandId>    # 派生子トークン
  consumers: Set<NodeId>    # このトークンを消費する DAG ノード
  ref_count: usize          # ReadToken 凍結期間中の安全コピー数
```

**競合判定**——凍結が保証する実行メカニズム：

```rust
fn conflicts(a: &BrandId, b: &BrandId) -> bool {
    // 冲突条件：同源 + 至少一方是写 + 品牌路径重叠
    // 这意味着：
    //   1. ReadToken vs ReadToken → 无冲突（都是只读，无突变）
    //   2. WriteToken vs ReadToken → 冲突（写破坏了读的冻结保证）
    //   3. WriteToken vs WriteToken → 冲突（两个写不可共存）
    a.source() == b.source()
        && (a.is_write() || b.is_write())
        && (a.is_prefix_of(b) || b.is_prefix_of(a))
}
```

文字列プレフィックス比較 O(depth)、深さ ≤ 3。定数レベル。

### 逆方向 BFS 活性解析

> **正誤表（2026-08-17、#251
> P0-6 監査）**：以下のアルゴリズムに「トークン作成時刻」次元を追加。原版は DAG ノードの全順序が暗黙に「借用が書込より前」という仮定に依存しており、「書込先、借用後」の合法順序（§2.4 意味論：パラメータトークンは呼出終了時解放）をカバーしない——監査の実測でこのシナリオが誤って報告された（#290）。トークン活性は**区間**
> `[created_at, last_use]`
> であり、逆方向到達可能集合ではない；書込操作はトークンの活性区間内でのみ競合を構成する。

```
アルゴリズム：check_borrow(token, node, dag, brand_tree)

入力：
  token: チェック対象の WriteToken
  node:  書込操作が位置する DAG ノード

出力：Proved | Disproved

アルゴリズム：
  # 高速経路：逆方向 BFS
  unsafe = empty_set
  queue = brand_tree.consumers(token)

  while queue not empty:
    cur = queue.pop()
    unsafe.add(cur)

    for each pred in dag.predecessors(cur):
      # 構造切断：break は横断しない
      if pred が break エッジ:
        continue

      # バックエッジ → SMT フォールバックが必要かチェック
      if pred がバックエッジ:
        path_cond = 書込ノード node のパス条件   # 正誤表：判定対象は書込ノード自身の条件
        loop_cond = ループ条件
        # まず構造的に切断可能かチェック（対応する break がパスを切断済 → ここに来ない）
        # 次にパス条件を見る
        if path_cond が空でない:
          result = smt_fallback(path_cond, loop_cond)   # ← 低速経路
          if result == Proved:
            continue                    # 論理切断
        # パス条件なし、または SMT が証明失敗 → バックエッジを横断
        # fall through

      if pred ∉ unsafe:
        queue.push(pred)

  # 判定（正誤表：作成時刻区間を追加）
  # 書込先、借用後：node < created_at(token) → 書込時点でトークン未存在 → Safe
  if node ∈ unsafe and created_at(token) ≤ node:
    return Disproved
  else:
    return Proved


smt_fallback(path_cond, loop_cond):
  # バックエッジ + パス条件ありの場合のみ呼び出し
  # RFC-027 証明パイプラインを使用し、同じ SMT ソルバー、同じ予算を共有
  return smt.prove(path_cond ⇒ !loop_cond)
  # Proved → 論理切断
  # Disproved / Unproven → 切断しない、バックエッジ横断（保守的拒否）
  # 正誤表（2026-08-17）：SMT 利用不可/タイムアウト/未実装 = Disproved 分岐——
  # SMT は精度にのみ影響（合法プログラムが通過するか）、健全性には影響しない
  # （拒否すべきは必ず拒否される）；SMT なしの保守度 = ループ内借用 + 書込を
  # 一律拒否、Rust NLL と同等。
```

BrandNode にフィールド追加（正誤表）：

```
BrandNode:
  ...
  created_at: NodeId         # トークン作成ノード（正誤表：borrow 区間の左端点）
```

O(N)、ここで SMT 呼び出し回数 = バックエッジ数 × パス条件付きバックエッジの割合。実際のコードでは SMT 呼び出しは極めて稀——`while`
ループ体内でパスを細分化した型変数を持つ場合にのみ発生する。

### パス条件収集

RFC-027 §3.2-3.3 の既存機構が提供する：

- **if ガード**：`if y > 0` → true 分岐に `y > 0` をプッシュ
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **代入**：`i += 1`、コンパイラは変数値域情報を維持
- **while cond**：ループ体内に `cond == true` をプッシュ

各 DAG ノードはパス条件集合を運ぶ。逆方向 BFS がバックエッジを横断するとき、バックエッジ起点のパス条件を取り、SMT が次のループ入口条件を除外するかを判定する。

> **正誤表（2026-08-17、伝播規則補完）**：原版はパス条件がバックエッジ起点にどう伝播するかを定義しておらず、ユースケース「while +
> SMT 論理切断」の `i == n` は原アルゴリズムでは再現不能。規則を補う：
>
> 1. **パス条件は書込ノード自身に付着する**：分岐内書込操作 W はその分岐条件を運ぶ（`if i == n { W }`
>    → path_cond(W) = `i == n`）。逆方向 BFS がバックエッジを横断するとき、SMT が判定するのは
>    `path_cond(W) ⇒ !loop_cond`
>    である（W に到達できるパスは必然的にループを退出する → 次の consumer 到達不能 → 切断）、バックエッジノードのパス条件ではない。
> 2. **join での保守的クリア**：if/else 合流点は分岐内パス条件を運ばない（両分岐条件の選言は通常判定不能のため、直接クリア）。合流点後の書込操作の path_cond は空 → バックエッジ横断。
> 3. **パス条件の意味化**：path_cond は ConstExpr（RFC-027
>    §3.2 意味論）であり、ソーステキストではない；smt_cut はこれを SMT 制約に翻訳して求解する。
> 4. **パス条件なし → バックエッジを直接横断**（unsafe）、SMT 呼び出しなし。

### RFC-027 とのインタフェース

借用システム述語とユーザー述語は同じ証明パイプラインを共有する——違いは**主力証明戦略**のみ：

| クエリ種別   | 命題出所           | 主力戦略                     | フォールバック       |
| ------------ | ------------------ | ---------------------------- | -------------------- |
| 型等式       | 型検査器           | 構造等価                     | —                    |
| ユーザー述語 | プログラマー型注釈 | SMT                          | プログラマー証明関数 |
| 借用競合     | コンパイラ自動生成 | **DAG 構造解析（高速経路）** | SMT 論理切断         |

借用検査における SMT ソルバーの役割：**主力ではなく、安全網である。**
while バックエッジが論理切断を必要とするときのみ呼び出される。大多数の借用検査は高速経路で完了——O(N) 逆方向 BFS、SMT コストゼロ。

### NLL とイテレーション境界

> **正誤表（2026-08-17、区間モデル補完）**：トークン活性は**区間** `[created_at, last_use]`
> であり、逆方向到達可能集合ではない。`created_at` = トークン作成ノード；`last_use`
> = 消費者解析の最大消費ノード。書込操作 W とトークン T の競合の必要十分条件：`conflicts(T, W) ∧ created_at(T) ≤ node(W)`
> `∧ node(W) が last_use(T) に前方到達可能`（逆方向 BFS 判定）。「書込先、借用後」の合法順序（§2.4：パラメータトークンは呼出終了時解放）は
> `created_at(T) ≤ node(W)`
> で直接排除され、特殊規則は不要。このモデルにより §トレードオフ利点 5「アルゴリズムが非保守的」という宣言が全ての順序で成立する。

**トークン死亡時刻 = 最後の使用点（NLL）、字句スコープ末尾ではない。**

これは消費者解析の自然な帰結：消費者の位置がトークンの最後の使用を定義する。`use(v)` は `v`
の消費者 → `v` は `use(v)` の直後に死亡。トークンライフタイムを早期終了させるための追加の `{}` や
`drop()` は不要。

**ループイテレーション境界はトークンコピーの死亡線である。** 三つの規則：

```
規則 1：ループ内で宣言された変数は各イテレーション終了時に自動死亡。
        for の各イテレーションは新バインド（言語設計保証）、loop も同様。

規則 2：ブランド木の ref_count はループ頭でループ外で作成されたコピーのみを計上する。
        ループ内 Dup が生成した新コピーの ref_count はイテレーション境界でゼロクリア。

規則 3：逆方向 BFS がバックエッジを横断するとき、現在のイテレーションの活性情報を運ばない。
        ループ頭での ref_count（つまりループ外のコピー）のみを運ぶ。
```

実例：

```yaoxiang
view = &data                          # 循环头：ref_count = 1，consumer = use(view)
loop {
    v2: &Point = view                 # 循环内 Dup → ref_count = 2
    use(v2)                           # consumer：v2 的最后使用 → v2 死亡 → ref_count = 1
    data.push(4)                      # ✅ 安全！v2 已死，只剩 view（ref_count = 1，非写冲突）
    # 迭代边界：规则 3——不携带 v2 进入下一轮。下一轮迭代开始时 v2 被新绑定重新创建。
}
```

この設計は追加の「ループ内保守的生存」規則を必要としない。逆方向 BFS は消費者から出発し、消費者がループ体内にある → 活性が現在のイテレーション内に制限される → バックエッジが横断しない。RFC-009a
§ユースケース分析のループ例と完全に一致する。

### `?` エラー伝播とスコープ駆動 Release

`?`
は早期 return——スコープの通常出口に加えてもう一つの退出パスがある。トークンはこのパス上でも解放されなければならず、解放順序の誤りは UB である。

**Release 命令はスコープ解析により生成され、Call の後にハードコードされるのではない。**

コンパイラは各スコープに対して出口点リストを維持する：

- `}`（スコープ通常終了）
- `?`（エラー伝播、早期 return）
- 明示的 `return`

各出口点で、宣言の逆順（LIFO）でそのスコープ内の全アクティブトークンの Release 命令を挿入する。ブランド木の親子関係が派生トークンのカスケード解放を自動処理する：

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)    # 返回子令牌 &Float + 父令牌 &Point
}

fn use_case(p: Point) -> Result<(), Error> = {
    (x_ref, p_ref) = p.get_x()?   # 如果 ? 传播：
    # 品牌树知道 x_ref 是 p_ref 的派生（#42.field_x 是 #42 的前缀）
    # 释放顺序：x_ref（子）→ p_ref（父）→ LIFO 自动满足
    p.modify()                     # WriteToken——所有 ReadToken 已释放
    Ok(())
}
```

実装位置：`ir_gen.rs` に保持、スコープ駆動に変更——新しい compiler pass は導入しない。

| 競合判定 | O(1) | トークンが必要なとき毎回 | | DAG 消費者クエリ | O(1)
| トークンが必要なとき毎回 | | 逆方向 BFS（高速経路） | O(N) | トークンが必要なとき毎回、N
= ブロック内ノード数 | | SMT 論理切断（フォールバック） | ~1ms |
**極めて稀**——while + パス条件の場合のみ |

> 正誤表（2026-08-17）：上表の複雑度は設計見積もりであり、実測は未実施；「~1ms」「極めて稀」は量級予測と見なすべきで、実装着地後に可観測性データで校正する。

**SMT フォールバックのトリガ条件は極めて厳しい**：(1)
while ループ、(2) ループ体内に書込操作、(3) 書込操作後にループ終了を判定可能なパス条件、(4) コンパイラがその条件に依存してバックエッジ切断する必要、を同時に満たす必要がある。実コードでの比率は 1% を遥かに下回る。残りの借用検査は全て高速経路で完了する。

RFC-027 ユーザー述語との関係：ユーザー述語は SMT が主力、借用システム述語は構造解析が主力。両者は同じ SMT ソルバーと予算上限（RFC-027
§8）を共有するが、借用システム述語は SMT 予算をほとんど消費しない。

線形コード → バックエッジなし → レイヤ 1 O(N) で即座に結果。ループ + パス条件 →
SMT 呼び出し、線形算術ミリ秒レベル（RFC-027 予算 100ms）。一度の BFS 結果はキャッシュされ、同じトークンの複数クエリで再利用される。

### エラーメッセージ設計

**核心原則：エラーメッセージにはユーザーが書いた記号のみが出現する。**

Rust の借用関連エラーは二種類に分類される：

**変数レベルエラー**：E0597（生存期間不足）、E0502（可変+不変の同時借用）、E0499（複数回可変借用）。Rust は既に模範——変数名+行番号、`'a`
は出現しない。YaoXiang の精度は同等。情報は全てブランド木にある：トークン作成点、消費者位置、要求点。

**シグネチャレベルエラー**：E0623（lifetime mismatch）、E0106（missing lifetime
specifier）、E0477（required lifetime 不満足）。`'a`
を中心に展開される。YaoXiang には**この種のエラーは存在しない**——シグネチャに `'a`
がない。「報告できない」のではなく、ユーザーが書かなかったものを報告しない。

関数内競合例：

```
错误：`data` 被冻结，不能获取可变权限
 --> src/main.yx:5:9
2 |     view = &data
  |            ----- `data` 被冻结（只读令牌创建在此处）
4 |         use(view)
  |             ---- `view` 在此处仍在使用，冻结未解除
5 |         data.push(4)
  |         ^^^^ 此处需要可变权限
```

（Rust E0499 と同等の精度——変数名+行番号、ブランド ID は出現しない。）

関数間エスケープ例：

```
错误：`num`（第 4 行）持有的数据来源之一是 `default_str`（第 3 行），
但 `default_str` 在第 6 行失效，`num` 在第 5 行仍在被使用。

考虑：将 `default_str` 的声明提前到调用方，或使用 `ref default_str` 共享持有。
```

（Rust E0597 と同等の精度。ブランド要約は `num`
に二つのソースパスがあることを知る——コンパイラ内に既存、メッセージ措辞は使用可能。）

## トレードオフ

### 利点

1. **型シグネチャにライフタイムを含まない**：`#42` こそが
   `'42`——同じ情報、ブランド木に符号化、型シグネチャに露出しない。この点は反証不能：Rust で 3 つの参照パラメータを持つジェネリック型がいくつの
   `'a` パラメータを必要とするか、YaoXiang で必要とするかを数えてみよ。答えは 3 vs 0。

2. **概念統一**：借用検査とユーザー述語は同じ証明パイプラインを共有——`{P} op {Q}`、パイプラインが P を検証。Curry-Howard 一致。

3. **新分析フレームワークゼロ**：新しい分析フレームワークを導入しない。ユーザーは「借用検査器」の存在を感知しない——「型検査器」の実装詳細をユーザーが感知しないように。

4. **エラーメッセージはユーザーが書いた記号のみを含む**：エラー分類が一つの次元分少なくなる（E0623、E0106、E0477——全て
   `'a` 中心）。変数レベルエラーは Rust と同等の精度。

5. **アルゴリズム非保守的**：逆方向 BFS + break 切断 +
   SMT 論理切断。「ループ内保守的生存」不要。「分岐保守的マージ」不要。

### 欠点

1. **新発明ではない**：ブランド ID が行うことは `'a`
   と完全に同一——コンパイラ内部の制約求解複雑度は消えておらず、符号化方式が「変数名+制約集合」から「ブランドパス+プレフィックス一致」に変わっただけ。エンドユーザーへの違いはシグネチャに
   `'a` を書かないことのみ。

2. **全新実装**：ブランド木はコード中に概念のみ存在、ゼロから実装する必要あり。BorrowChecker、ControlFlowAnalyzer を置換。

3. **SMT 依存**：論理切断は Z3 に依存（RFC-027 で既に導入、新依存なし）。ただし借用検査はほぼトリガしない——while + パス条件の場合のみ呼び出し。

4. **極少数パターンで再構築が必要**：コンパイラ自動証明でカバーできないクロス分岐借用は、ユーザーがコードを再構築する必要がある。Rust の
   `'a` フォールバックとは異なる：Rust は `'a`
   を筆として持つ（注釈で通過可能）；YaoXiang のフォールバック（証明関数）は MVP ではない。

      クロスイテレーション意味論**——NLL を採用：トークンは最後の使用後死亡。ループ内バインドのコピーはイテレーション境界で死亡、逆方向 BFS はクロスイテレーション活性を運ばない。詳細は §NLL とイテレーション境界。
- [x] **`?`
      エラー伝播パス上のトークン解放順序**——Release はスコープ解析駆動（ir_gen.rs に保持）。各スコープ出口点（`}`、`?`、明示的 return）で LIFO によりアクティブトークンを解放。ブランド木親子関係がカスケード解放を自動処理。詳細は §`?`
      エラー伝播とスコープ駆動 Release。
