# RFC-009a: トークンライフタイム解析——ホーア証明パイプラインに基づく

> **親 RFC**: [RFC-009: 所有権モデル設計](../accepted/009-ownership-model.md)
>
> **依存**:
> [RFC-027: コンパイル時述語と統一静的検証](../accepted/027-compile-time-evaluation-types.md)
>
> **前提条件**:
> RFC-027 が承認済みであること。本 RFC のすべての機構（証明パイプライン、SMT フォールバック、経路条件収集）は RFC-027 の実装に依存する。
>
> **本 RFC は RFC-009 §「トークン競合検出：フロー依存活性解析」（第 663-684 行）を修正・置換する。**

## 概要

RFC-009 第 684 行はトークン競合検出は「NLL を必要としない」と主張している。結論は正しいが、論拠が誤っている。

「トークンは値であり、線形追跡で十分だから」ではない。**トークン活性はホーア論理の命題であり、専用のフロー依存解析ではないからだ。**

`{conflicting_tokens すべて死亡} op {WriteToken 安全取得}` —— 同じ
`{P} op {Q}`、型検査、述語検証と RFC-027 の証明パイプラインを共有する。新しい解析フレームワークはない。一本のパイプラインで複数の命題を扱う。

---

## 動機

### RFC-009 の混同

RFC-009 は二つの問題を混同している：

1. **線形追跡**（Move 後の使用不可）——
   `{v が move されていない} use(v) {型が一致}`。型検査器に既に存在する。
2. **トークンライフタイム相互作用**（子トークン生存 → 親トークン停止 → 子トークン死亡 → 親トークン復活）——
   `{conflicting_tokens すべて死亡} write(data) {安全}`。**活性解析**が必要であり、線形追跡ではない。

### 現在のコードの実情

| コンポーネント                             | 状態                                                                           |
| ------------------------------------------ | ------------------------------------------------------------------------------ |
| `BorrowChecker`                            | IR を線形スキャンし、明示的な `Borrow`/`Release` 命令に受動的に応答            |
| `ControlFlowAnalyzer::analyze_instruction` | 空実装（`control_flow.rs:145-153`）                                            |
| `liveness_analysis`                        | 存在するが Drop 挿入のみに使用され、トークン競合には接続されていない           |
| Release 挿入                               | Call 命令の後にハードコード——純粋にレキシカルスコープ（`ir_gen.rs:2734-2736`） |

**ユーザー可視の結果**：

```yaoxiang
data = vec![1, 2, 3]
view = &data              # ReadToken を作成
x = view.total_count      # view の最後の使用
data.push(4)              # ❌ Release(view) まだ実行されていない、ReadToken「生存中」
```

### なぜ書き直す必要があるか

前版（009a
v1）は「DAG が NLL を置き換える」という語り口で、不要な新概念（保守的分岐規則、ループ特殊処理）を導入した。核心的矛盾を明確にしていない：**借用検査は独立したシステムではなく、ホーア命題の一形態である。**

## 中核設計

### すべてがホーア

```
型検査：  { x: Int }        x + 1        { result: Int }
借用検査：{ view 死亡済み } data.push(4)  { WriteToken 取得成功 }
述語検証：{ y > 0 }         divide(x, y)  { result: Int }
ループ辺切断：{ i == n }    次のループ     { cond == false }
```

同じ形式
`{P} op {Q}`。コンパイラは各操作に対し前置命題 P を生成し、証明パイプラインに送って検証する。

**借用検査とユーザー述語は同じパイプラインを共有する。**
違いは命題を生成するのが誰か、証明できないときの扱いだけ。

### 二種類の述語、一本のパイプライン

|            | ユーザー述語              | システム述語（借用）                  |
| ---------- | ------------------------- | ------------------------------------- |
| 命題生成   | プログラマー（型注釈）    | コンパイラ（ブランド木 + 所有権規則） |
| 証明提供   | コンパイラ + プログラマー | **コンパイラが完全自動**              |
| 証明失敗時 | 証明関数を書くか再構築    | コードを再構築（門は開くがほぼ不要）  |
| 可視性     | シグネチャに見える        | 暗黙的、型シグネチャを汚染しない      |
| 学習コスト | 使うときだけ学ぶ          | ゼロ                                  |

**システム述語の証明にはプログラマに証明関数を開かない——コンパイラが完全自動で行う。**
証明できない場合はユーザーがコードを再構築する。

**三つの失敗モード、同一の検証エンジン。**
型命題が証明できない → コンパイルエラー（回避不可）。借用命題が証明できない → コンパイルエラー、コード再構築（回避不可）。ユーザー述語が証明できない → コンパイルエラー、証明関数を書ける（回避可能）。失敗戦略は異なるが、検証エンジンは同じ——SMT ソルバー + コンパイラ内核推論規則。違いは「証明できないときに誰が証明を補うか」だけ——コンパイラはプログラマの借用証明を書くことを拒否する（借用命題の証明戦略は構造解析 +
SMT であり、プログラマの介入は不要）一方、ユーザー述語の証明関数は受け入れる。これはパイプラインの不整合ではなく、命題クラス間の責任境界が異なるだけ。

これは Rust の `'a` とは異なる：`'a`
は必修科目、証明関数は選択科目——大多数のユーザーは生涯、選択科目の門にさえ触れない。

### 借用命題：コンパイラが自動生成

ユーザーが `data.push(4)` と書く。コンパイラが自動で命題を生成：

```
WriteToken(data, node) 取得可能
  = forall t in conflicting_tokens(data): t は node 時点で死亡
  = forall t in brand_tree.children(data): forward_reachable(node) ∩ consumers(t) == ∅
```

**三つの規則、ゼロの特例：**

1. **ブランド木**（RFC-009
   §2.7）が「誰と誰が競合するか」に答える：プレフィックス一致、O(depth)、深さ ≤ 3
2. **コンシューマーリスト**（DAG 構築時に自動収集）が「トークンを最後に消費するのは誰か」に答える
3. **前方到達可能性**が「コンシューマーがまだ実行可能か」に答える：構造的切断 + 論理的切断

### 前方到達可能性：コンシューマーから逆方向へ

トークン T の各コンシューマー C に対し：

```
C から出発し、DAG を逆方向 BFS。
辺を切断するのは、以下の場合：
  1. break である（構造的切断）
  2. 経路条件 ⇒ !loop_cond が SMT で真と証明される（論理的切断、RFC-027 パイプライン）

切断されていない辺を逆方向に伝播（バックエッジを含む、バックエッジは活性を前イテレーションに伝播）。
到達可能なすべてのノードをマーク → unsafe。
```

クエリ：書込み操作がノード W にある → W ∉ unsafe → 安全。

**「保守的分岐規則」を発明する必要はない。「ループ保守生存」を発明する必要もない。一つの逆方向 BFS + 二つの切断規則。**

### 証明戦略：ファーストパス優先、SMT がフォールバック

```
トークンを必要とする各書込み操作
  │
  ├→ ファーストパス：DAG 構造解析（95% 以上のシナリオをカバー）
  │     │
  │     ├→ ブランド木プレフィックス一致 → 競合トークンを特定（O(depth)）
  │     ├→ 逆方向 BFS、break がバックエッジを切断
  │     └→ 横断可能なバックエッジなし → 直接 Proved / Disproved 判定
  │
  └→ スローパス：SMT 論理的切断（ファーストパスが横断可能なバックエッジに遭遇したときのみ）
        │
        ├→ バックエッジ起点に経路条件あり → SMT が path_cond ⇒ !loop_cond を判定
        │     ├→ Proved → 論理的切断 → ファーストパスに降格して継続
        │     └→ Disproved / Unproven → バックエッジ横断 → unsafe にマーク
        │
        └→ バックエッジ起点に経路条件なし → バックエッジ直接横断
```

**ファーストパスのカバー範囲**：線形コード、if/else、loop + break、経路条件なしの while。
**スローパスのカバー範囲**：while ループ体内、経路条件がループ終了を示唆する場合。
**カバー外**：実行時条件が静的に証明できない → バックエッジ横断 → unsafe
→ コンパイルエラー（ユーザー再構築）。

SMT は主力ではなくセーフティネット。RFC-027 のユーザー述語とは異なる：ユーザー述語は SMT を主力とする；借用システム述語は構造解析を主力とし、SMT は構造解析が届かない端補完のみ。

## ユースケース解析

### 線形コード

```yaoxiang
data = vec![1, 2, 3]        # ノード 1
view = &data                # ノード 2：data を消費、ReadToken(#1) を生成
x = view.total_count        # ノード 3：view を消費（= #1 の最後のコンシューマー）
data.push(4)                # ノード 4：WriteToken(data) を必要とする
```

`view.total_count`（ノード 3）から逆方向 BFS
→ ノード 3 は #1 の最後のコンシューマー → ノード 4 > ノード 3 → ノード 4 は unsafe に入らない → ✅

### if/else：特殊規則なし

```yaoxiang
view = &data
if cond {
    use(view)               # then 分岐で view を消費
} else {
    do_something_else()     # view に触れない
}
data.push(4)                # view の最後のコンシューマーは if 内 → if 後のコンシューマーなし → ✅
```

if/else は DAG の複合ノード。内部消費はこのノードに帰属する。分岐状態をマージしない。保守的判定をしない。**後にコンシューマーがあるかどうかは整数比較。**

> **明確化（#264 後）**：「分岐状態をマージしない」は**借用活性**（ブランドコンシューマー逆方向 BFS）のみを指す。
> **move 状態**（変数所有権）は別系統の解析：per-CFG-node 前向きデータフロー（#264、NLL/Polonius 風）、分岐合流時に**保守的 meet**（いずれかの分岐で Moved
> → 合流点 Moved）、リテラルに到達不能な分岐（`if false`）は参加しない。両者は層別化：借用活性は「後続コンシューマーがあるか」を見、move 解析は「変数が既に転送された可能性はあるか」を見る。

### 戻り値のエスケープを伴う if/else

```yaoxiang
view = &data
result = if cond {
    view                     # view が result にエスケープ
} else {
    something_else
}
use(result)                  # view を間接的に消費
data.push(4)                 # view にまだコンシューマーがいる（use(result)）
                             # → push が unsafe → ❌ 正しくエラー
```

view が戻り値でエスケープ → `use(result)` が view のコンシューマー → `push` から逆方向に進むと
`use(result)` に到達可能 → unsafe。

### ループ：break がバックエッジを切断

```yaoxiang
view = &data
loop {
    use(view)                # コンシューマー
    if is_last {
        data.push(4)         # 書込み操作
        break                # ← 構造的切断
    }
}
```

`use(view)` から逆方向 BFS → バックエッジ → 前方方向に進んで `data.push(4)` に到達 → `break`
に遭遇 → **切断** → `data.push(4)` は unsafe に入らない → ✅

break がない場合：

```yaoxiang
view = &data
loop {
    use(view)
    data.push(4)             # break による切断なし → バックエッジが横断可能 → 次のイテレーションで use(view) に到達可能
                             # → push が unsafe → ❌ 正しくエラー
}
```

### while：SMT 論理的切断

```yaoxiang
view = &data
mut i: UpTo(n) = 0
while i < n {
    use(view)                # コンシューマー
    i += 1
    if i == n {
        data.push(4)         # 経路条件：i == n
    }
}
```

`use(view)` から逆方向 BFS → バックエッジ → `data.push(4)` に進む → 経路条件 `i == n` をチェック →
SMT クエリ：`i == n ⇒ !(i < n)` ？→ Proved → **論理的切断** → `data.push(4)` は unsafe に入らない →
✅

## 本質：ブランド ID は `'a` そのもの

「`'a` は必要ない」とは言わない。「`#42` こそが `'42` だ」と言う。

| Rust                       | YaoXiang                                | 等価性                                |
| -------------------------- | --------------------------------------- | ------------------------------------- |
| `'a`                       | `#42`                                   | コンパイル時ライフタイム識別子        |
| `'a: 'b` outlives 制約     | `#42` は `#42.field_x` のプレフィックス | 文字列プレフィックス比較 = 半順序関係 |
| NLL 活性伝播（CFG 不動点） | 逆方向 BFS（DAG）                       | どちらも到達可能性計算                |
| Polonius fact              | SMT 論理的切断                          | どちらも経路条件推論                  |
| 制約システム不動点求解     | ブランド木プレフィックス一致 + BFS      | 異なるエンコーディング、同じ問題      |

**新しい解析を発明したのではない。`'a` を型シグネチャ層から証明層に降ろしただけ。** ブランド ID は
`'a`
と完全に同じことを行う——借用のアイデンティティをマークし、派生関係を追跡し、競合を判定する。違いは一つだけ：`'a`
はユーザーが書く型シグネチャにある；`#42` はコンパイラの内部にある。

これは恥ずべきことではない。Curry-Howard によれば型は命題であり、プログラムは証明である。`'a`
は命題の一部ではなく、証明戦略の一部だ。Rust は証明戦略を命題シグネチャに書き込んだ。我々はそのあるべき場所に戻す。

### 言語設計制約が排除したもの

| 複雑性の出所                    | 排除したか | 理由                                                             |
| ------------------------------- | ---------- | ---------------------------------------------------------------- |
| 変数シャドーイング              | ✅         | 言語で禁止——ある名前は同じものを指し続ける                       |
| for 跨ぎ借用                    | ✅         | 各イテレーションで新バインディング——イテレーション間は自然に分離 |
| `'a` ライフタイム注釈           | ✅         | ブランドパス = `#42.field_x`、コンパイラが推論                   |
| 名前付きライフタイム + 制約伝播 | ✅         | ブランドパスプレフィックス比較が明示的制約集合を代替             |
| 借用グラフ制約求解（Polonius）  | ✅         | ブランド木プレフィックス一致 + DAG コンシューマークエリ          |
| ループ体内借用活性伝播          | ❌         | Rust と同じ処理が必要——逆方向 BFS + 論理的切断で対応             |
| 条件分岐保守性                  | ❌         | Rust と同じ——SMT が証明可能な部分をカバーし、残りは保守的拒否    |

### なぜ DAG で可能か

YaoXiang の三つの言語設計制約が DAG 解析を可能にする：

- **変数シャドーイングなし**——ある名前は同じものを指し続けるため、再バインディング跨ぎ追跡不要
- **for の各イテレーションは新バインディング**——イテレーション間が自然に分離され、跨ぎ借用が存在しない
- **構造化並行性**——タスク境界が明確で、跨ぎタスク活性伝播不要

これらの制約が Rust
CFG 不動点反復の主要な複雑性出所を排除した。DAG が CFG より「高度」なのではなく、よりシンプルな言語設計がよりシンプルな解析を可能にする。

## 詳細設計

### システム述語一覧

コンパイラが以下の命題を自動生成し、RFC-027 証明パイプラインに送る：

| システム述語      | 発動タイミング       | 命題形式                                      |
| ----------------- | -------------------- | --------------------------------------------- |
| `borrow_conflict` | WriteToken(v) 必要時 | `forall t ∈ conflicting(v): dead_at(t, node)` |
| `use_after_move`  | 変数 v 使用時        | `¬moved(v)`                                   |
| `use_after_drop`  | 変数 v 使用時        | `¬dropped(v)`                                 |
| `double_drop`     | Drop(v)              | `¬dropped(v)`                                 |
| `mut_violation`   | 不変変数 v への書込  | `is_mut(v)`                                   |

既存の `BorrowChecker`、`MoveChecker`、`DropChecker`、`MutChecker` は
**命題生成器になる**——消えるのではなく、役割を変える。命題を生成し、パイプラインが命題を検証する。

### ブランド木

RFC-009 §2.7 のブランド機構をブランド木として形式化する。

**トークン意味論——凍結優先、コピー非優先**：

`&T` と `&mut T` の本質的違いは「コピー可能か」ではなく「同時書込みを許すか」：

```
ReadToken(T)： 読取専用権限を付与し、ソースデータ T を同時に凍結する——
              この間 WriteToken(T) は取得不可。凍結が ReadToken の第一義的意味論。
              Dup（コピー可能）は凍結の帰結：データは凍結済み（突然変異可能性なし）なので、
              複数の読取専用ビューは自然に安全。

WriteToken(T)：排他的な読書き権限を付与する。書込みが存在するため、他のトークン（読取・書取いずれも）は共存不可。
              Dup を実装しない（線形型）のは排他性の帰結。
```

**因果関係**：

```
ReadToken 存在 → ソースデータ凍結 → 複数の読取専用が安全 → Dup
                       ↓
              WriteToken は拒否される（borrow_conflict システム述語が強制）
```

ではなく：

```
ReadToken は Dup を持つ → 複数持てる → ついでに競合チェック  ← 因果倒置
```

```
BrandTree:
  nodes: Map<BrandId, BrandNode>

BrandNode:
  id: BrandId               # "#42"、"#42.field_x"
  kind: ReadToken | WriteToken
  source_var: Operand
  parent: Option<BrandId>   # 派生関係の親ノード
  children: Set<BrandId>    # 派生子トークン
  consumers: Set<NodeId>    # そのトークンを消費する DAG ノード
  ref_count: usize          # ReadToken 凍結期間中の安全コピー数
```

**競合判定**——凍結保証の実行メカニズム：

```rust
fn conflicts(a: &BrandId, b: &BrandId) -> bool {
    // 競合条件：同一ソース + 少なくとも一方が書込み + ブランドパス重複
    // つまり：
    //   1. ReadToken vs ReadToken → 競合なし（両方読取専用、突然変異なし）
    //   2. WriteToken vs ReadToken → 競合（書込みが読取りの凍結保証を破壊）
    //   3. WriteToken vs WriteToken → 競合（二つの書込みは共存不可）
    a.source() == b.source()
        && (a.is_write() || b.is_write())
        && (a.is_prefix_of(b) || b.is_prefix_of(a))
}
```

O(depth) 文字列プレフィックス比較、深さ ≤ 3。定数級。

### 逆方向 BFS 活性解析

```
アルゴリズム：check_borrow(token, node, dag, brand_tree)

入力：
  token: 検査対象の WriteToken
  node:  書込み操作が位置する DAG ノード

出力：Proved | Disproved

アルゴリズム：
  # ファーストパス：逆方向 BFS
  unsafe = empty_set
  queue = brand_tree.consumers(token)

  while queue が空でない：
    cur = queue.pop()
    unsafe.add(cur)

    for each pred in dag.predecessors(cur)：
      # 構造的切断：break は横断しない
      if pred が break 辺：
        continue

      # バックエッジ → SMT フォールバックが必要かチェック
      if pred がバックエッジ：
        path_cond = pred 時点の経路条件
        loop_cond = ループ条件
        # まず構造的に切断可能か確認（対応する break がすでにパスを切断 → ここに到達しない）
        # 次に経路条件を見る
        if path_cond が空でない：
          result = smt_fallback(path_cond, loop_cond)   # ← スローパス
          if result == Proved：
            continue                    # 論理的切断
        # 経路条件なし or SMT 証明失敗 → バックエッジを横断
        # fall through

      if pred ∉ unsafe：
        queue.push(pred)

  # 判定
  if node ∈ unsafe：
    return Disproved
  else：
    return Proved


smt_fallback(path_cond, loop_cond)：
  # バックエッジ + 経路条件ありの場合のみ呼び出し
  # RFC-027 証明パイプラインを使用、同じ SMT ソルバー、同じ予算を共有
  return smt.prove(path_cond ⇒ !loop_cond)
  # Proved → 論理的切断
  # Disproved / Unproven → 切断しない、バックエッジを横断
```

O(N)、ここで SMT 呼び出し回数 = バックエッジ数 × 経路条件付きバックエッジの比率。実際のコードでは SMT 呼び出しは非常に稀——`while`
ループ体内で経路条件が精化された型変数を持つ場合にのみ発動。

### 経路条件収集

RFC-027 §3.2-3.3 の既存機構で提供される：

- **if ガード**：`if y > 0` → true 分岐に `y > 0` をプッシュ
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **代入**：`i += 1`、コンパイラが変数の値域情報を維持
- **while cond**：ループ体内に `cond == true` をプッシュ

各 DAG ノードは経路条件集合を保持する。逆方向 BFS のバックエッジ時、バックエッジ起点の経路条件を取得し、SMT が次のループ入口条件を除外するかを判定。

### RFC-027 とのインターフェース

借用システム述語とユーザー述語は同じ証明パイプラインを共有する——違いは**主力証明戦略**：

| クエリ種別   | 命題ソース           | 主力戦略                           | フォールバック         |
| ------------ | -------------------- | ---------------------------------- | ---------------------- |
| 型等価       | 型検査器             | 構造等価                           | —                      |
| ユーザー述語 | プログラマーの型注釈 | SMT                                | プログラマーの証明関数 |
| 借用競合     | コンパイラ自動生成   | **DAG 構造解析（ファーストパス）** | SMT 論理的切断         |

借用検査における SMT ソルバーの役割：**主力ではなくセーフティネット。**
while バックエッジが論理的切断を必要とするときのみ呼び出される。ほとんどの借用検査はファーストパスで完了する——O(N) 逆方向 BFS、SMT オーバーヘッドゼロ。

### 既存コードとの関係

| 既存コンポーネント                  | 処理                                                    |
| ----------------------------------- | ------------------------------------------------------- |
| `BorrowChecker`                     | `BorrowPredicateEmitter` に変更——借用のホーア命題を生成 |
| `MoveChecker`                       | `MovePredicateEmitter` に変更——`¬moved(v)` 命題を生成   |
| `DropChecker`                       | 同上——Drop 関連命題を生成                               |
| `MutChecker`                        | 同上——`is_mut(v)` 命題を生成                            |
| `ControlFlowAnalyzer`               | 不要——パイプラインが統一処理                            |
| `liveness_analysis`                 | 維持——Drop 挿入には依然変数活性情報が必要               |
| `ir_gen.rs` の Release ハードコード | 削除——Release 位置は DAG コンシューマー解析が駆動       |

### NLL と反復境界

**トークン死亡時点 = 最終使用点（NLL）、レキシカルスコープ末尾ではない。**

これはコンシューマー解析の自然な帰結：コンシューマーの位置がトークンの最終使用を定義する。`use(v)`
は `v` のコンシューマー → `v` は `use(v)`
の直後に死亡する。トークンライフタイムを早期終了させるための追加の `{}` や `drop()` は不要。

**ループ反復境界がトークンコピーの死亡線である。** 三つの規則：

```
規則 1：ループ内で宣言された変数は各イテレーション終了時に自動死亡する。
        for の各イテレーションは新バインディング（言語設計保証）、loop も同様。

規則 2：ブランド木の ref_count はループ頭でループ外で作成されたコピーのみを計上する。
        ループ内 Dup で生成された新コピーの ref_count は反復境界でゼロクリア。

規則 3：逆方向 BFS がバックエッジを横断するとき、現在イテレーションの活性情報を持ち越さない。
        ループ頭の ref_count のみを持ち越す（つまり：ループ外のコピー）。
```

インスタンス：

```yaoxiang
view = &data                          # ループ頭：ref_count = 1、consumer = use(view)
loop {
    v2: &Point = view                 # ループ内 Dup → ref_count = 2
    use(v2)                           # コンシューマー：v2 の最終使用 → v2 死亡 → ref_count = 1
    data.push(4)                      # ✅ 安全！v2 は死亡済み、view のみ残る（ref_count = 1、書込み競合なし）
    # 反復境界：規則 3——v2 を次イテレーションに持ち越さない。次イテレーション開始時、v2 は新バインディングで再作成。
}
```

この設計は追加の「ループ保守生存」規則を必要としない。コンシューマーから逆方向 BFS を開始し、コンシューマーがループ体内にある → 活性が現在イテレーション内に制限される → バックエッジを横断しない。RFC-009a
§ユースケース解析のループ例と完全に一致する。

### `?` エラー伝播とスコープ駆動 Release

`?`
は早期 return——スコープの正常終了パスに加え、追加の退出パスがある。トークンはこのパス上でも解放される必要があり、解放順序が誤れば UB になる。

**Release 命令はスコープ解析により生成され、Call の後にハードコードされるのではない。**

コンパイラは各スコープに対し出口点リストを維持する：

- `}`（スコープ正常終了）
- `?`（エラー伝播、早期 return）
- 明示的 `return`

各出口点で、宣言の逆順（LIFO）でそのスコープ内のすべてのアクティブトークンの Release 命令を挿入する。ブランド木の親子関係が派生トークンのカスケード解放を自動処理する：

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)    # 子トークン &Float + 親トークン &Point を返す
}

fn use_case(p: Point) -> Result<(), Error> = {
    (x_ref, p_ref) = p.get_x()?   # ? が伝播する場合：
    # ブランド木は x_ref が p_ref の派生（#42.field_x は #42 のプレフィックス）であることを知っている
    # 解放順序：x_ref（子）→ p_ref（親）→ LIFO 自動満足
    p.modify()                     # WriteToken——すべての ReadToken は解放済み
    Ok(())
}
```

実装位置：`ir_gen.rs` に維持、スコープ駆動に変更——新しい compiler pass は導入しない。

| 操作                             | 複雑度 | 発動頻度                                   |
| -------------------------------- | ------ | ------------------------------------------ |
| ブランド木競合判定               | O(1)   | トークン必要時ごと                         |
| DAG コンシューマークエリ         | O(1)   | トークン必要時ごと                         |
| 逆方向 BFS（ファーストパス）     | O(N)   | トークン必要時ごと、N = ブロック内ノード数 |
| SMT 論理的切断（フォールバック） | ~1ms   | **極めて稀**——while + 経路条件時のみ       |

**SMT フォールバックの発動条件は極めて厳しい**：(1)
while ループ (2) ループ体内に書込み操作あり (3) 書込み操作後にループ終了を判定できる経路条件あり (4) コンパイラがその条件に依存してバックエッジを切断する必要あり、を同時に満たす必要がある。実際のコードでの比率は 1% を遥かに下回る。それ以外の借用検査はすべてファーストパスで完了する。

RFC-027 ユーザー述語との関係：ユーザー述語は SMT を主力とし、借用システム述語は構造解析を主力とする。両者は同じ SMT ソルバーと予算上限（RFC-027
§8）を共有するが、借用システム述語は SMT 予算をほぼ消費しない。

線形コード → バックエッジなし → 層 1 O(N) 即座に結果。ループ + 経路条件 →
SMT 呼び出し、線形算術でミリ秒級（RFC-027 予算 100ms）。一度の BFS 結果は同一トークンの複数クエリで再利用できるようにキャッシュ可能。

### エラーメッセージ設計

**中核原則：エラーメッセージにはユーザーが書いたシンボルだけを表示する。**

Rust の借用関連エラーは二種類：

**変数レベルエラー**：E0597（生存期間不足）、E0502（可変+不変の同時借用）、E0499（複数可変借用）。Rust はすでに模範——変数名 + 行番号、`'a`
は現れない。YaoXiang は精度同等。情報はブランド木にすべてある：トークン作成点、コンシューマー位置、要求点。

**シグネチャレベルエラー**：E0623（lifetime mismatch）、E0106（missing lifetime
specifier）、E0477（required lifetime 不満足）。`'a` をめぐる。YaoXiang には
**この種のエラーは存在しない**——シグネチャに `'a`
がないから。「報告できない」のではなく、ユーザーが書いたことのないものを報告しない。

関数内競合の例：

```
エラー：`data` は凍結されており、可変権限を取得できません
 --> src/main.yx:5:9
2 |     view = &data
  |            ----- `data` は凍結されました（読取専用トークンはここで作成）
4 |         use(view)
  |             ---- `view` はここでまだ使用中、凍結は解除されていません
5 |         data.push(4)
  |         ^^^^ ここで可変権限が必要
```

（Rust E0499 と同等の精度——変数名 + 行番号、ブランド ID は現れない。）

関数間エスケープの例：

```
エラー：`num`（4 行目）が保持するデータソースの一つは `default_str`（3 行目）ですが、
`default_str` は 6 行目で失効し、`num` は 5 行目でまだ使用中です。

検討：`default_str` の宣言を呼び出し側に移動するか、`ref default_str` で共有保持を使用してください。
```

（Rust E0597 と同等の精度。ブランド要約は `num`
に二つのソースパスがあることを知っている——コンパイラ内に既存、エラー文言に使用可能。）

## RFC-009 本文の修正

RFC-009 §「トークン競合検出：フロー依存活性解析」を更新：

1. 「必要ないもの：……NLL」を削除——結論が誤りだからではなく、論拠が誤りだから（「トークンは値であり、線形追跡で十分」）
2. 層 1 / 層 2 移行案は維持、完全な解決策は本 RFC を参照
3. 明確化：ブランド ID（`#42`）こそが
   `'a`——情報は完全に同じ、エンコーディングが異なる。新しい解析を発明したのではなく、ライフタイムを型層から証明層に降ろした

## トレードオフ

### 利点

1. **型シグネチャにライフタイムを含まない**：`#42` は `'42`
   そのもの——同じ情報、ブランド木にエンコードされ、型シグネチャに露出しない。この点は反証不可：Rust で 3 つの参照パラメータを持つジェネリック型にいくつの
   `'a` パラメータが必要かを数え、YaoXiang で必要数を数える。答えは 3 対 0。

2. **概念の統一**：借用検査とユーザー述語は同じ証明パイプラインを共有——`{P} op {Q}`、パイプラインが P を検証。Curry-Howard と一致。

3. **新しい解析フレームワークゼロ**：新しい解析フレームワークを導入しない。ユーザーは「借用検査器」の存在を認識しない——「型検査器」の実装詳細を認識しないのと同様。

4. **エラーメッセージはユーザーが書いたシンボルだけを含む**：エラー分類の次元が一個減る（E0623、E0106、E0477——すべて
   `'a` をめぐる）。変数レベルエラーは Rust と同精度。

5. **アルゴリズムは保守的でない**：逆方向 BFS + break 切断 +
   SMT 論理的切断。「ループ内保守生存」は不要。「分岐保守マージ」は不要。

### 欠点

1. **新しい発明ではない**：ブランド ID は `'a`
   と完全に同じことを行う——コンパイラ内部の制約求解複雑度は消えておらず、エンコーディング方式が「変数名 + 制約集合」から「ブランドパス + プレフィックス一致」に変わっただけ。エンドユーザーへの違いはシグネチャに
   `'a` を書かない点のみ。

2. **全新実装**：ブランド木はコード中に概念のみ存在、ゼロから実装する必要あり。BorrowChecker、ControlFlowAnalyzer は置換される。

3. **SMT 依存**：論理的切断は Z3 に依存（RFC-027 ですでに導入、新規依存は追加しない）。しかし借用検査はほぼ発動しない——while + 経路条件時のみ呼び出される。

4. **極少数のパターンは再構築が必要**：コンパイラの自動証明がカバーできない跨ぎ分岐借用は、ユーザーがコードを再構築する必要あり。Rust の
   `'a` フォールバックとは異なる：Rust には `'a`
   という筆がある（注釈すれば通る）；YaoXiang のフォールバック（証明関数）は MVP ではない。

---

## 代替案

| 代替案                           | 採用しない理由                                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 完全な Rust NLL を実装           | YaoXiang の設計制約（シャドーイングなし、for 新バインディング）が NLL の主要複雑性出所をすでに排除しており、CFG 不動点は不要 |
| 現在維持（ハードコード Release） | 不十分——ユーザーがトークンスコープを手動管理する必要あり                                                                     |
| spawn ブロックのみで解析         | 不十分——非 spawn コードでのトークン使用が大多数                                                                              |
| GC による借用検査の代替          | 言語設計原則違反——YaoXiang は GC なし                                                                                        |
