# RFC-009a: トークン生存期間分析——ホーア証明パイプラインに基づく

> **親 RFC**: [RFC-009: 所有権モデル設計](../accepted/009-ownership-model.md)
>
> **依存**:
> [RFC-027: コンパイル時述語と統一静的検証](../accepted/027-compile-time-evaluation-types.md)
>
> **前提条件**:
> RFC-027 が承認済みであること。本 RFC のすべての機構（証明パイプライン、SMT フォールバック、経路条件収集）は RFC-027 の実装に依存する。
>
> **本 RFC は RFC-009
> §「トークン競合検出：フロー依存活性分析」（第 663-684 行）を修正し、置換する。**

## 概要

RFC-009 の第 684 行は、トークン競合検出が「NLL を……必要としない」と主張している。結論は正しいが、論拠は誤りである。

「トークンが値であり、線形追跡で十分だから」ではない。**トークン活性はホーア論理の命題であり、特化したフロー依存分析ではないから**である。

`{conflicting_tokens すべて死亡} op {WriteToken 安全取得}` —— 同じ `{P} op {Q}`
であり、型検査、述語検証と RFC-027 の証明パイプラインを共有する。新しい分析フレームワークはない。一本のパイプライン、多様な命題。

---

## 動機

### RFC-009 の混同

RFC-009 は二つの問題を混同している：

1. **線形追跡**（Move 後の使用不可）——
   `{v が move されていない} use(v) {型一致}`。型検査器が既に持つ。
2. **トークン生存期間相互作用**（子トークン生存 → 親トークン停止 → 子トークン死亡 → 親トークン復活）——
   `{conflicting_tokens すべて死亡} write(data) {安全}`。**活性分析**が必要であり、線形追跡ではない。

### 現状コードの実態

| コンポーネント                             | 状態                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| `BorrowChecker`                            | IR を線形走査し、明示的な `Borrow`/`Release` 命令に受動的に応答          |
| `ControlFlowAnalyzer::analyze_instruction` | 空実装（`control_flow.rs:145-153`）                                      |
| `liveness_analysis`                        | 存在するが Drop 挿入にのみ使用され、トークン競合には未接続               |
| Release 挿入                               | Call 命令の後にハードコード——純粋に語彙スコープ（`ir_gen.rs:2734-2736`） |

**ユーザ可視の結果**：

```yaoxiang
data = vec![1, 2, 3]
view = &data              # ReadToken を作成
x = view.total_count      # view の最後の使用
data.push(4)              # ❌ Release(view) がまだ実行されていないため、ReadToken が「生存中」
```

### なぜ書き直すのか

前版（009a
v1）は「DAG による NLL 置換」ナラティブを用い、不要な新概念（保守的分岐規則、ループ特殊処理）を導入した。核心的矛盾を明確にしなかった：**借用検査は独立したシステムではない——ホーア命題の一形態である。**

## 中核設計

### すべてはホーア

```
型検査：   { x: Int }        x + 1        { result: Int }
借用検査： { view 死亡 }     data.push(4)  { WriteToken 取得成功 }
述語検証： { y > 0 }         divide(x, y)  { result: Int }
後退辺切断：{ i == n }        次のループ    { cond == false }
```

同じ形式
`{P} op {Q}`。コンパイラは各操作に対して前置命題 P を生成し、証明パイプラインに投入して検証する。

**借用検査とユーザ述語は同じパイプラインを共有する。**
違いは命題の生成元と、証明できなかったときの扱いだけである。

### 二種類の述語、一本のパイプライン

|            | ユーザ述語              | システム述語（借用）                         |
| ---------- | ----------------------- | -------------------------------------------- |
| 命題生成   | プログラマ（型注釈）    | コンパイラ（ブランド木 + 所有権規則）        |
| 証明提供   | コンパイラ + プログラマ | **コンパイラ全自動**                         |
| 証明失敗時 | 証明関数を書くか再構成  | コード再構成（門は存在するがほぼ使われない） |
| 可視性     | シグネチャに見える      | 暗黙的、型シグネチャを汚染しない             |
| 学習コスト | 使うときに初めて学ぶ    | ゼロ                                         |

**システム述語の証明はプログラマに証明関数を開かない——コンパイラが全自動処理する。**
証明できない場合、ユーザはコードを再構成する。

**三つの失敗モード、同一の検証エンジン。**
型命題が証明できない → コンパイルエラー（回避不可）。借用命題が証明できない → コンパイルエラー、コード再構成（回避不可）。ユーザ述語が証明できない → コンパイルエラー、証明関数を記述可能（回避可能）。失敗戦略は異なるが、検証エンジンは同一——SMT ソルバ + コンパイラカーネル推論規則。違いは「証明できないときに誰が証明を補う責任を持つか」のみ——コンパイラはプログラマの代わりに借用証明を書かない（借用命題の証明戦略は構造分析 +
SMT であり、プログラマの介入は不要）が、プログラマ記述のユーザ述語証明関数は受け入れる。これはパイプラインの不整合ではなく、命題カテゴリごとの責任境界が異なるだけである。

これは Rust の `'a` とは異なる：Rust では `'a`
は必修科目、証明関数は選択科目——大多数のユーザは一生選択科目の門にすら触れない。

### 借用命題：コンパイラ自動生成

ユーザが `data.push(4)` と書くと、コンパイラは自動的に命題を生成する：

```
WriteToken(data, node) が取得可能
  = forall t in conflicting_tokens(data): t は node で死亡済み
  = forall t in brand_tree.children(data): forward_reachable(node) ∩ consumers(t) == ∅
```

**三つの規則、ゼロの特例：**

1. **ブランド木**（RFC-009 §2.7）が「誰と誰が競合するか」に答える：接頭辞一致、O(depth)、深さ ≤ 3
2. **コンシューマリスト**（DAG 構築時に自動収集）が「トークンを最後に消費したのは誰」に答える
3. **前方到達可能性**が「コンシューマがまだ実行可能か」に答える：構造的切断 + 論理的切断

### 前方到達可能性：コンシューマから逆方向に歩く

トークン T の各コンシューマ C に対して：

```
C から出発し、DAG を逆方向に BFS。
辺が切断されるのは、次の場合：
  1. break である（構造的切断）
  2. 経路条件 ⇒ !loop_cond が SMT で真と証明される（論理的切断、RFC-027 パイプライン）

切断されていないすべての辺を逆方向に伝播する（後退辺を含む、後退辺は活性を前のイテレーションに伝播する）。
到達可能なすべてのノードをマーク → unsafe。
```

クエリ：書込み操作がノード W にある → W ∉ unsafe → 安全。

**「保守的分岐規則」を発明する必要はない。「ループの保守的生存」を発明する必要もない。逆 BFS + 二つの切断規則だけである。**

### 証明戦略：高速パス優先、SMT がフォールバック

```
トークンを必要とする各書込み操作
  │
  ├→ 高速パス：DAG 構造分析（95%+ のシナリオをカバー）
  │     │
  │     ├→ ブランド木接頭辞一致 → 競合トークンを特定（O(depth)）
  │     ├→ 逆 BFS、break で後退辺を切断
  │     └→ 横断可能な後退辺なし → 直接 Proved / Disproved を判定
  │
  └→ 低速パス：SMT 論理的切断（高速パスが横断可能後退辺に遭遇したときのみ）
        │
        ├→ 後退辺の起点に経路条件あり → SMT が path_cond ⇒ !loop_cond を判定
        │     ├→ Proved → 論理的切断 → 高速パスに降格して続行
        │     └→ Disproved / Unproven → 後退辺横断 → unsafe にマーク
        │
        └→ 後退辺の起点に経路条件なし → 後退辺を直接横断
```

**高速パスのカバー範囲**：線形コード、if/else、loop + break、経路条件なしの while。
**低速パスのカバー範囲**：while ループ体内、経路条件がループ終了を示唆する場合。
**カバー外**：実行時条件を静的に証明できない → 後退辺横断 → unsafe
→ コンパイルエラー（ユーザが再構成）。

SMT は主力ではなく、安全網である。RFC-027 のユーザ述語とは異なる：ユーザ述語は SMT を主力とする；借用システム述語は構造分析を主力とし、SMT は構造分析が到達できない辺縁のみを補完する。

> **訂正（2026-08-17、SMT 位置付け修正）**：SMT は
> **精度層であり、健全性依存ではない**。借用システム述語の健全な判定は完全に高速パス（区間 + 逆 BFS +
> break 切断）が担う；SMT 論理的切断は「ループ境界における合法プログラムを通過させるか」だけを決定する。SMT が利用不可 / タイムアウト / 未実装（RFC-027
> impl:
> in_progress）でも、フォールバック = 後退辺横断 = 保守的拒否であり、拒否すべきものは必ず拒否される。**SMT 不在時の保守度 = ループ内の借用+ 書込みを一律拒否**であり、Rust
> NLL と同等（Rust のプロダクション借用検査も同様に SMT を持たない）。SMT の実装は純粋な精度向上であり、健全性主線のリリースをブロックしない。

## ユースケース分析

### 線形コード

```yaoxiang
data = vec![1, 2, 3]        # ノード 1
view = &data                # ノード 2：data を消費し、ReadToken(#1) を生成
x = view.total_count        # ノード 3：view を消費（= #1 の最後のコンシューマ）
data.push(4)                # ノード 4：WriteToken(data) が必要
```

逆 BFS を
`view.total_count`（ノード 3）から開始 → ノード 3 は #1 の最後のコンシューマ → ノード 4 > ノード 3
→ ノード 4 は unsafe ではない → ✅

### if/else：特殊規則なし

```yaoxiang
view = &data
if cond {
    use(view)               # then 分岐で view を消費
} else {
    do_something_else()     # view に触れない
}
data.push(4)                # view の最後のコンシューマが if 内 → if の後にコンシューマなし → ✅
```

if/else は DAG の一つの複合ノードである。内部消費はこのノードに帰属する。分岐状態をマージしない。保守的合議を行わない。**後にコンシューマがいるかどうかは整数比較。**

> **明確化**：「分岐状態をマージしない」は**借用活性**（ブランドコンシューマ逆 BFS）にのみ適用される。
> **move 状態**（変数所有権）は別の分析：per-CFG-node 前向きデータフロー（NLL/Polonius 風）、分岐合流時に**保守的 meet**（いずれかの分岐で Moved なら合流点も Moved）、リテラル到達不能分岐（`if false`）は参加しない。両者は階層化されている：借用活性は「後続コンシューマがいるか」を見、move 分析は「変数がすでに転送された可能性」を見る。

### 戻り値による if/else エスケープ

```yaoxiang
view = &data
result = if cond {
    view                     # view が result にエスケープ
} else {
    something_else
}
use(result)                  # view を間接消費
data.push(4)                 # view にまだコンシューマがいる（use(result)）
                             # → push は unsafe 内 → ❌ 正しくエラー
```

view は戻り値経由でエスケープ → `use(result)` は view のコンシューマ → `push` から逆方向に到達可能 →
unsafe。

### ループ：break による後退辺切断

```yaoxiang
view = &data
loop {
    use(view)                # consumer
    if is_last {
        data.push(4)         # 書込み操作
        break                # ← 構造的切断
    }
}
```

逆 BFS を `use(view)` から開始 → 後退辺 → 前方に歩いて `data.push(4)` に到達 → `break` に遭遇 →
**切断** → `data.push(4)` は unsafe ではない → ✅

break がない場合：

```yaoxiang
view = &data
loop {
    use(view)
    data.push(4)             # break 切断なし → 後退辺が横断可能 → 次のイテレーションの use(view) が到達可能
                             # → push は unsafe → ❌ 正しくエラー
}
```

### while：SMT 論理的切断

```yaoxiang
view = &data
mut i: UpTo(n) = 0
while i < n {
    use(view)                # consumer
    i += 1
    if i == n {
        data.push(4)         # 経路条件：i == n
    }
}
```

逆 BFS を `use(view)` から開始 → 後退辺 → `data.push(4)` に到達 → 経路条件 `i == n` をチェック →
SMT クエリ：`i == n ⇒ !(i < n)`？→ Proved → **論理的切断** → `data.push(4)` は unsafe ではない → ✅

> 訂正（2026-08-17）：`i == n` は書込みノード（if 分岐内の
> `data.push(4)`）自身の経路条件であり、判定対象は書込みノードである（§経路条件収集訂正規則 1 参照）。

## 本質：ブランド ID は `'a` そのもの

「`'a` は必要ない」とは言わない。「`#42` とは `'42` である」と言う。

| Rust                       | YaoXiang                        | 等価性                        |
| -------------------------- | ------------------------------- | ----------------------------- |
| `'a`                       | `#42`                           | コンパイル時生存期間識別子    |
| `'a: 'b` outlives 制約     | `#42` は `#42.field_x` の接頭辞 | 文字列接頭辞比較 = 半順序関係 |
| NLL 活性伝播（CFG 不動点） | 逆 BFS（DAG）                   | どちらも到達可能性計算        |
| Polonius 事実              | SMT 論理的切断                  | どちらも経路条件推論          |
| 制約システム不動点求解     | ブランド木接頭辞一致 + BFS      | 異なる符号化、同じ問題        |

**我々は新しい分析を発明したのではない。`'a` を型シグネチャ層から証明層に降ろしただけである。**
ブランド ID が行うことは `'a`
と完全に同一——借用のアイデンティティをマークし、派生関係を追跡し、競合を判定する。違いは一つだけ：Rust では
`'a` がユーザ記述の型シグネチャにある；YaoXiang では `#42` がコンパイラ内部にある。

これは恥ずべきことではない。Curry-Howard は型は命題、プログラムは証明と言う。`'a`
は命題の一部ではなく、証明戦略の一部である。Rust は証明戦略を命題シグネチャに書き込んだ。我々をあるべき場所に戻したのである。

### 言語設計制約が排除したもの

| 複雑性の出所                   | 回避したか | 理由                                                          |
| ------------------------------ | ---------- | ------------------------------------------------------------- |
| 変数シャドーイング             | ✅         | 言語で禁止——同じ名前は常に同じものを指す                      |
| クロスイテレーション借用       | ✅         | 各イテレーションで新バインド——イテレーション間が自然に分離    |
| `'a` 生存期間注釈              | ✅         | ブランドパス = `#42.field_x`、コンパイラが推論                |
| 名前付き生存期間 + 制約伝播    | ✅         | ブランドパスの接頭辞比較が明示的制約集合を置換                |
| 借用グラフ制約求解（Polonius） | ✅         | ブランド木接頭辞一致 + DAG コンシューマクエリ                 |
| ループ体内借用活性伝播         | ❌         | Rust と同様に処理が必要——逆 BFS + 論理的切断で対応            |
| 条件分岐保守性                 | ❌         | Rust と同様——SMT が証明可能な範囲をカバーし、残りは保守的拒否 |

### なぜ DAG が実現可能か

YaoXiang の三つの言語設計制約が DAG 分析を可能にする：

- **変数シャドーイングなし**——同じ名前は常に同じものを指し、再バインド間の追跡不要
- **for は各イテレーションで新バインド**——イテレーション間が自然に分離され、クロスイテレーション借用が存在しない
- **構造化並行性**——タスク境界が明確で、タスク間活性伝播が不要

これらの制約が Rust
CFG 不動点反復の主要な複雑性出所を排除する。DAG が CFG より「高級」なのではなく、**より単純な言語設計がより単純な分析を許容する**のである。

## 詳細設計

### システム述語リスト

コンパイラは以下の命題を自動生成し、RFC-027 証明パイプラインに投入する：

| システム述語      | 発火タイミング       | 命題形式                                      |
| ----------------- | -------------------- | --------------------------------------------- |
| `borrow_conflict` | WriteToken(v) が必要 | `forall t ∈ conflicting(v): dead_at(t, node)` |
| `use_after_move`  | 変数 v を使用        | `¬moved(v)`                                   |
| `use_after_drop`  | 変数 v を使用        | `¬dropped(v)`                                 |
| `double_drop`     | Drop(v)              | `¬dropped(v)`                                 |
| `mut_violation`   | 不変変数 v に書込み  | `is_mut(v)`                                   |

既存の `BorrowChecker`、`MoveChecker`、`DropChecker`、`MutChecker`
**は命題生成器になる**——消えるのではなく、役割を変える。彼らが命題を生成し、パイプラインが命題を検証する。

### ブランド木

RFC-009 §2.7 のブランド機構をブランド木として形式化する。

**トークンセマンティクス——凍結優先、コピー非優先**：

`&T` と `&mut T`
の本質的な違いは「コピー可能かどうか」ではなく、「同時書込みを許すかどうか」である：

```
ReadToken(T)：  読み取り専用権限を付与し、ソースデータ T を同時に凍結する——
               この期間中、いかなる WriteToken(T) も取得不可。凍結は ReadToken の
               第一義的セマンティクスである。Dup（コピー可能）は凍結の帰結：
               データはすでに凍結されており（突然変異の可能性なし）、複数の
               読み取り専用ビューは自然に安全。

WriteToken(T)： 排他的な読み書き権限を付与する。書込みが存在するため、他の
               いかなるトークン（読み取りまたは書込み）も共存不可。
               Dup を実装しない（線形型）のは排他性の帰結。
```

**因果関係**：

```
ReadToken 存在 → ソースデータ凍結 → 複数読み取り専用が安全 → Dup
                       ↓
               WriteToken 拒否（borrow_conflict システム述語が強制）
```

以下ではない：

```
ReadToken は Dup を持つ → 複数存在可能 → ついでに競合をチェック  ← 因果逆転
```

```
BrandTree:
  nodes: Map<BrandId, BrandNode>

BrandNode:
  id: BrandId               # "#42"、"#42.field_x"
  kind: ReadToken | WriteToken
  source_var: Operand
  parent: Option<BrandId>   # 派生関係の親ノード
  children: Set<BrandId>    # 派生子トークン
  consumers: Set<NodeId>    # 当該トークンを消費する DAG ノード
  ref_count: usize          # ReadToken 凍結期間中の安全コピー数
```

**競合判定**——凍結保証の実行メカニズム：

```rust
fn conflicts(a: &BrandId, b: &BrandId) -> bool {
    // 競合条件：同ソース + 少なくとも一方が書込み + ブランドパス重複
    // これは以下を意味する：
    //   1. ReadToken vs ReadToken → 競合なし（両方読み取り専用、突然変異なし）
    //   2. WriteToken vs ReadToken → 競合（書込みが読み取りの凍結保証を破る）
    //   3. WriteToken vs WriteToken → 競合（二つの書込みは共存不可）
    a.source() == b.source()
        && (a.is_write() || b.is_write())
        && (a.is_prefix_of(b) || b.is_prefix_of(a))
}
```

O(depth) 文字列接頭辞比較、深さ ≤ 3。定数級。

### 逆 BFS 活性分析

> **訂正（2026-08-17 監査）**：以下のアルゴリズムに「トークン作成時刻」次元を追加。原文は DAG ノード全順序が「借用が書込みより前」を暗黙に仮定しており、「書込み先、借用後」の合法順序（§2.4 セマンティクス：引数トークンは呼び出し終了時に解放）をカバーしていなかった——監査実測でこのシナリオが誤報された。トークン活性は**区間**
> `[created_at, last_use]`
> であり、逆到達可能集合ではない；書込み操作はトークンの活性区間内でのみ競合を構成する。

```
アルゴリズム：check_borrow(token, node, dag, brand_tree)

入力：
  token: チェック対象の WriteToken
  node:  書込み操作が位置する DAG ノード

出力：Proved | Disproved

アルゴリズム：
  # 高速パス：逆 BFS
  unsafe = empty_set
  queue = brand_tree.consumers(token)

  while queue not empty:
    cur = queue.pop()
    unsafe.add(cur)

    for each pred in dag.predecessors(cur):
      # 構造的切断：break は横断しない
      if pred が break 辺:
        continue

      # 後退辺 → SMT フォールバックが必要かチェック
      if pred が後退辺:
        path_cond = 書込みノード node の経路条件   # 訂正：判定対象は書込みノード自身の条件
        loop_cond = ループ条件
        # まず構造的に切断可能か確認（対応する break がすでにパスを切断 → ここには来ない）
        # 次に経路条件を確認
        if path_cond が空でない:
          result = smt_fallback(path_cond, loop_cond)   # ← 低速パス
          if result == Proved:
            continue                    # 論理的切断
        # 経路条件なし または SMT 証明失敗 → 後退辺を横断
        # fall through

      if pred ∉ unsafe:
        queue.push(pred)

  # 判定（訂正：作成時刻区間を追加）
  # 書込み先、借用後：node < created_at(token) → 書込み時点でトークンはまだ存在しない → Safe
  if node ∈ unsafe and created_at(token) ≤ node:
    return Disproved
  else:
    return Proved


smt_fallback(path_cond, loop_cond):
  # 後退辺 + 経路条件ありの場合のみ呼び出し
  # RFC-027 証明パイプラインを使用、同じ SMT ソルバ、同じ予算を共有
  return smt.prove(path_cond ⇒ !loop_cond)
  # Proved → 論理的切断
  # Disproved / Unproven → 切断せず、後退辺を横断（保守的拒否）
  # 訂正（2026-08-17）：SMT が利用不可/タイムアウト/未実装 = Disproved 分岐——
  # SMT は精度にのみ影響し（合法プログラムを通過させるか）、健全性には影響しない
  # （拒否すべきものは必ず拒否される）；SMT 不在時の保守度 = ループ内の借用+
  # 書込みを一律拒否、Rust NLL と同等。
```

BrandNode にフィールド追加（訂正）：

```
BrandNode:
  ...
  created_at: NodeId         # トークン作成ノード（訂正：借用区間の左端点）
```

O(N)、ここで SMT 呼び出し回数 = 後退辺数 × 経路条件を持つ後退辺の比率。実コードでは SMT 呼び出しは非常に稀——`while`
ループ体内、精化型変数を持つ経路条件があるときにのみ発火する。

### 経路条件収集

RFC-027 §3.2-3.3 の既存機構が提供する：

- **if ガード**：`if y > 0` → true 分岐に `y > 0` をプッシュ
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **代入**：`i += 1`、コンパイラが変数の値域情報を保守
- **while cond**：ループ体内に `cond == true` をプッシュ

各 DAG ノードは経路条件集合を運ぶ。逆 BFS が後退辺に遭遇したとき、後退辺の起点の経路条件を取得し、SMT が次のループ入口条件を除外するか判定する。

> **訂正（2026-08-17、伝播規則補完）**：原文は経路条件が後退辺起点にどう伝播するかを定義しておらず、ユースケース「while +
> SMT 論理的切断」の `i == n` が原文アルゴリズムでは再現不能であった。規則を追加：
>
> 1. **経路条件は書込みノード自身に付着する**：分岐内書込み操作 W はその分岐条件を運ぶ（`if i == n { W }`
>    → path_cond(W) = `i == n`）。逆 BFS が後退辺を横断するとき、SMT が判定するのは
>    `path_cond(W) ⇒ !loop_cond`（W に到達する経路は必然的にループを終了する → 次のイテレーションの consumer は到達不能 → 切断）であり、後退辺ノードの経路条件ではない。
> 2. **合流での保守的クリア**：if/else 合流点は分岐内経路条件を運ばない（両分岐条件の選言は通常判定不能のため、直接クリア）。合流点後の書込み操作の path_cond は空 → 後退辺横断。
> 3. **経路条件の意味化**：path_cond は ConstExpr（RFC-027
>    §3.2 セマンティクス）であり、ソーステキストではない；smt_cut がそれを SMT 制約に翻訳して求解する。
> 4. **経路条件なし → 後退辺を直接横断**（unsafe）、SMT 呼び出しなし。

### RFC-027 とのインターフェース

借用システム述語とユーザ述語は同じ証明パイプラインを共有する——違いは**主力証明戦略**のみ：

| クエリ種別 | 命題ソース         | 主力戦略                     | フォールバック       |
| ---------- | ------------------ | ---------------------------- | -------------------- |
| 型等式     | 型検査器           | 構造的等価性                 | —                    |
| ユーザ述語 | プログラマの型注釈 | SMT                          | プログラマの証明関数 |
| 借用競合   | コンパイラ自動生成 | **DAG 構造分析（高速パス）** | SMT 論理的切断       |

借用検査における SMT ソルバの役割：**主力ではなく、安全網である。**
while 後退辺が論理的切断を必要とするときのみ呼び出される。大多数の借用検査は高速パスで完了——O(N) 逆 BFS、SMT コストゼロ。

### NLL とイテレーション境界

> **訂正（2026-08-17、区間モデル補完）**：トークン活性は**区間** `[created_at, last_use]`
> であり、逆到達可能集合ではない。`created_at` = トークン作成ノード；`last_use`
> = コンシューマ分析の最大消費ノード。書込み操作 W とトークン T の競合の必要十分条件：
> `conflicts(T, W) ∧ created_at(T) ≤ node(W) ∧ node(W) が前方到達 last_use(T)`
> （逆 BFS で判定）。「書込み先、借用後」の合法順序（§2.4：引数トークンは呼び出し終了時に解放）は
> `created_at(T) ≤ node(W)`
> によって直接排除され、いかなる特殊規則も不要。このモデルにより§トレードオフ長所 5「アルゴリズムは保守的でない」という宣言がすべての順序で成立する。

**トークン死亡時刻 = 最後の使用点（NLL）、語彙スコープ末尾ではない。**

これはコンシューマ分析の自然な帰結である：コンシューマの位置がトークンの最後の使用を定義する。`use(v)`
は `v` のコンシューマ → `v` は `use(v)` の直後に死亡する。トークン生存期間を早期終了させるための追加
`{}` や `drop()` は不要。

**ループイテレーション境界はトークンコピーの死亡線である。** 三つの規則：

```
規則 1：ループ内で宣言された変数は各イテレーション終了時に自動死亡。
        for の各イテレーションは新バインド（言語設計保証）、loop も同様。

規則 2：ブランド木の ref_count はループ頭でループ外で作成されたコピーのみを計上。
        ループ内 Dup が生み出した新コピーは、ref_count がイテレーション境界でゼロになる。

規則 3：逆 BFS が後退辺を横断するとき、現在のイテレーションの活性情報を運搬しない。
        ループ頭の ref_count（すなわち：ループ外のコピー）のみ運搬する。
```

実例：

```yaoxiang
view = &data                          # ループ頭：ref_count = 1、consumer = use(view)
loop {
    v2: &Point = view                 # ループ内 Dup → ref_count = 2
    use(v2)                           # consumer：v2 の最後の使用 → v2 死亡 → ref_count = 1
    data.push(4)                      # ✅ 安全！v2 は死亡済み、view のみ残る（ref_count = 1、書込み競合なし）
    # イテレーション境界：規則 3——v2 を次のイテレーションに持ち越さない。次のイテレーション開始時、v2 は新バインドで再作成される。
}
```

この設計は追加の「ループ保守的生存」規則を必要としない。逆 BFS はコンシューマから出発し、コンシューマがループ体内にある → 活性が現在のイテレーション内に限定される → 後退辺は横断されない。RFC-009a
§ユースケース分析のループ例と完全に一致する。

### `?` エラー伝播とスコープ駆動 Release

`?`
は早期リターン——スコープの正常出口に加えてもう一つの脱出パスである。トークンはこのパス上でも解放される必要があり、解放順序の誤りは UB となる。

**Release 命令はスコープ分析が生成し、Call の後にハードコードされるのではない。**

コンパイラは各スコープに対して出口点リストを保守する：

- `}`（スコープの正常終了）
- `?`（エラー伝播、早期 return）
- 明示的な `return`

各出口点で、宣言の逆順（LIFO）で当該スコープ内の全アクティブトークンの Release 命令を挿入する。ブランド木の親子関係が派生トークンのカスケード解放を自動処理する：

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)    # 子トークン &Float + 親トークン &Point を返す
}

fn use_case(p: Point) -> Result<(), Error> = {
    (x_ref, p_ref) = p.get_x()?   # ? が伝播する場合：
    # ブランド木は x_ref が p_ref の派生（#42.field_x は #42 の接頭辞）であることを知っている
    # 解放順序：x_ref（子）→ p_ref（親）→ LIFO 自動満足
    p.modify()                     # WriteToken——全 ReadToken 解放済み
    Ok(())
}
```

実装場所：`ir_gen.rs` に保持、スコープ駆動に変更——新しいコンパイラパスを導入しない。

| 競合判定 | O(1) | トークン必要時ごと | | DAG コンシューマクエリ | O(1) | トークン必要時ごと |
| 逆 BFS（高速パス） | O(N) | トークン必要時ごと、N = ブロック内ノード数 | |
SMT 論理的切断（フォールバック） | ~1ms | **極めて稀**——while + 経路条件時のみ |

> 訂正（2026-08-17）：上表の複雑度は設計見積もりであり、実測値ではない；「~1ms」「極めて稀」は量級期待として扱うべきであり、実装展開後に可観測性データで較正する。

**SMT フォールバックの発火条件は非常に厳しい**：(1)
while ループ (2) ループ体内に書込み操作 (3) 書込み操作の後に経路条件がループ終了を判定可能 (4) コンパイラがその条件に依存して後退辺を切断する必要がある、の同時成立。実コードでの比率は 1% をはるかに下回る。残りのすべての借用検査は高速パスで完了する。

RFC-027 ユーザ述語との関係：ユーザ述語は SMT を主力とし、借用システム述語は構造分析を主力とする。両者は同じ SMT ソルバと予算上限（RFC-027
§8）を共有するが、借用システム述語は SMT 予算をほとんど消費しない。

線形コード → 後退辺なし → レイヤ 1 O(N) で即座に結果。ループ + 経路条件 →
SMT 呼び出し、線形算術でミリ秒級（RFC-027 予算 100ms）。一度の BFS 結果は同一トークンの複数クエリで再利用できるようにキャッシュ可能。

### エラーメッセージ設計

**中核原則：エラーメッセージはユーザが書いたシンボルだけを表示する。**

Rust の借用関連エラーは二分類される：

**変数レベルエラー**：E0597（生存期間不足）、E0502（可変+不変同時借用）、E0499（複数可変借用）。Rust はすでに模範——変数名+行番号、`'a`
は現れない。YaoXiang は精度で同等。情報はすべてブランド木にある：トークン作成点、コンシューマ位置、要求点。

**シグネチャレベルエラー**：E0623（lifetime mismatch）、E0106（missing lifetime
specifier）、E0477（required lifetime 不満足）。`'a`
を中心に展開される。YaoXiang には**この種のエラーは存在しない**——シグネチャに `'a`
がない。「報告できない」のではなく、ユーザが書いていないものを報告しない。

関数内競合の例：

```
エラー：`data` は凍結されており、可変権限を取得できません
 --> src/main.yx:5:9
2 |     view = &data
  |            ----- `data` はここで凍結されました（読み取り専用トークンが作成）
4 |         use(view)
  |             ---- `view` はここでまだ使用中、凍結は解除されていません
5 |         data.push(4)
  |         ^^^^ ここで可変権限が必要です
```

（Rust E0499 と同等の精度——変数名+行番号、ブランド ID は現れない。）

関数間エスケープの例：

```
エラー：`num`（4 行目）が保持するデータの一つは `default_str`（3 行目）に由来しますが、
`default_str` は 6 行目で失効するのに対し、`num` は 5 行目でまだ使用中です。

検討：`default_str` の宣言を呼び出し側に前倒すか、`ref default_str` で共有保持を使用してください。
```

（Rust E0597 と同等の精度。ブランド要約は `num`
に二つのソースパスがあることを知っている——コンパイラ内に既存、エラー措辞で使用可能。）

## トレードオフ

### 長所

1. **型シグネチャに生存期間を含まない**：`#42` とは `'42`
   のこと——同じ情報、ブランド木に符号化、型シグネチャに露出しない。この点は反証不能：Rust で 3 つの参照引数を持つジェネリック型に何個の
   `'a` パラメータが必要かを数え、YaoXiang で必要な個数と比較すればよい。答えは 3 vs 0。

2. **概念の統一**：借用検査とユーザ述語は同じ証明パイプラインを共有——`{P} op {Q}`、パイプラインが P を検証。Curry-Howard と一致。

3. **新しい分析フレームワークゼロ**：新しい分析フレームワークを導入しない。ユーザは「借用検査器」の存在を意識しない——「型検査器」の実装细节を意識しないのと同じ。

4. **エラーメッセージはユーザが書いたシンボルだけを含む**：エラー分類が一つまるごと削減される（E0623、E0106、E0477——すべて
   `'a` 関連）。変数レベルエラーは Rust と同等の精度。

5. **アルゴリズムが保守的でない**：逆 BFS + break 切断 +
   SMT 論理的切断。「ループ内の保守的生存」が不要。「分岐の保守的マージ」が不要。

### 短所

1. **新しい発明ではない**：ブランド ID が行うことは `'a`
   と完全に同一——コンパイラ内部の制約求解の複雑性は消えておらず、符号化方式が「変数名+制約集合」から「ブランドパス+接頭辞一致」に変わっただけである。エンドユーザへの差異は、シグネチャに
   `'a` を書かなくてよい点のみ。

2. **全新実装**：ブランド木はコード中に概念のみ存在し、ゼロから実装する必要あり。BorrowChecker、ControlFlowAnalyzer は置換される。

3. **SMT 依存**：論理的切断は Z3 に依存する（RFC-027 で導入済み、新規依存なし）。しかし借用検査はほとんど発火しない——while + 経路条件のときのみ呼び出される。

4. **極めて稀なパターンには再構成が必要**：コンパイラの自動証明がカバーできない分岐間借用は、ユーザがコードを再構成する必要がある。Rust
   `'a` のフォールバックとは異なる：Rust には `'a`
   という筆がある（注釈すれば通る）；YaoXiang のフォールバック（証明関数）は MVP ではない。
