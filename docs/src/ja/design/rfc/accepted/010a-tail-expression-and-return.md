# RFC-010a: 末尾式の評価と return セマンティクス

> **参考**:
>
> - [RFC-010: 統一型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   依存駆動計算ユニット
> - [RFC-007: 関数定義構文統一方案](./007-function-syntax-unification.md)
>   — コードブロック返却ルール、早期リターン
> - [RFC-038: 文終端と改行規則](038-statement-termination.md) — 文と式の改行挙動
> - [言語仕様 §型システム](/reference/language-spec/type-system.md) — `Never` 爆発原理

## 概要

`return` とブロック評価のセマンティクスを統一し、RFC-007 と RFC-010 の間の記述衝突を解消する。

**三つの自己無撞着な規則**を提案する：ブロックの値は末尾式と等しい（唯一の出口）；`return` は型
`Never` の**非局所脱出**である（関数を脱出し、ブロックに「値を返さない」）；`else` のない `if` は
`Void` を取る。

`return` とブロック評価は言語レベルで二分割**しない**——`{ return n }` はブロックとしてその値が
`n`（型 `Never`）であり、同時に `return`
の作用は関数を脱出することであり、二つの事柄は**爆発原理**（`Never <: T`）によって共存する。RFC-007 の「早期リターン」と RFC-010 の「ブロックは値を持つ」はこの三つの規則の帰結であり、矛盾する特例ではない。

新しい構文なし、新しいキーワードなし。

## 動機

### 記述衝突

playground のフィボナッチ例が一つのセマンティクスの相違を露呈した：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // この return は「if の」それとも「関数の」？
  }
  return fib(n - 1) + fib(n - 2)
}
```

二つの承認済み RFC は**逆方向の**推論を与える：

| RFC                     | 記述                                                                                                 | 推論セマンティクス                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **RFC-007**（承認済み） | `factorial` を例に、タイトルを**「早期リターン：return を使う」**と記述：`if n <= 1 { return 1 }`    | `return` は `if` と関数本体を貫通し、**関数に戻る** |
| **RFC-010**（承認済み） | 「`{}` は依存駆動計算ユニット…`return` で明示的に値を返す」；`spawn { return c }` はタスク結果を返す | `return` は**この `{}`** に値を渡す                 |

RFC-010 に従えば、`if n <= 1 { return 1 }` の波括弧は計算ユニットであり、`return 1`
がそれに渡す値は 1 となり、`if`
文の値は破棄され、次の行が必ず実行される——**fib は無限再帰する**。RFC-007 に従えば正しい。

### 根本原因：`return` という語の二重職務

- **RFC-007 はそれで「関数を脱出する」**を表現する——制御フローの概念
- **RFC-010 はそれで「このブロックの値である」**を表現する——評価の概念

評価を表現するのに制御フローのキーワードを使うのは範疇錯誤（category
error）である。一語で二つの職務を担う以上、どのように調整しても片方が犠牲になる。

### 下流ドキュメントの誤った拡大解釈

`docs/src/reference/language-spec/syntax.md` は RFC-010 の「`{}`
ブロック」を**すべての波括弧**に拡大した：

- §2.9：「`{}` 内の `return`
  は**常に内容を一つ上のスコープに返す**」（さらに「統一セマンティクス：すべての `{}`
  ブロック」と称する）
- §3.3：「`return` は**コードブロックから値を返す**」

しかし RFC-010 の原文が定義しているのは**三つの値を持つブロック**（`= {}` / `spawn {}` /
`unsafe {}`）であり、 **`if` / `while` / `for` / `match` の波括弧には一切触れていない**。

### 実装の現状

| 挙動                                   | 現状                                      |
| -------------------------------------- | ----------------------------------------- |
| `if n == 0 { return 7 } … return 8`    | 関数脱出（`h(0) = 7`）                    |
| `f = { n + 1 }`                        | 末尾式が使える（`5` を返す）              |
| `x = { y = 5; y }`（生ブロック末尾式） | `E3006` 変数未解決（#343 参照）           |
| `f: () -> Int = { if c {5} else {6} }` | `void` を返す、末尾式が捨てられる（#344） |
| `f: () -> Int = { "s" }`               | 静的にコンパイル通過（#345 参照）         |
| `x = if c { 19 }`（`else` なし）       | `19`（`Void` であるべき、#346 参照）      |
| `v = unsafe { 42 }`                    | `void`（#347 参照）                       |
| `y = if c { 111 } else { 222 }`        | 使用可能（`if` を式として）               |

## 提案

### 三つの規則

```
① ブロックの値 = 末尾式（唯一の出口）
   代入文の値は Void；空ブロック {} の値は Void
② return : (T) -> Never
   非局所脱出：最も近い関数境界を脱出する
③ else なしの if → Void
```

**この三つで「早期リターン」が導出され、`return` が関数を特指する追加規則は不要である。**

### 規則 ①：ブロックの値

ブロックの**最後の文/式**がブロックの値である（末尾式）。これは**「末尾式がなければ Void」ではない**——空でないブロックは常に末尾式を持ち（末尾の文そのものがそれ）、空ブロック
`{}` の値は `Void` である。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 代入を末尾式とする → ブロックの値は Void
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Void を望むなら明示的に書く
c = {
    log(x)
    Void                 // 明示的な Void
}
```

**設計判断基準（機構と保護の分離）**：

- **言語規則は機構のみを与える**：末尾の文がブロックの値、規則は唯一で曖昧さなし
- **保護は型検査が提供する**：関数が `-> Int`
  を宣言しているのに末尾式の型が一致しない → コンパイルエラー
- **言語は「意図の誤り」を防がない**：末尾式の型がたまたま返却型と一致しても意味が意図と異なる場合、それは作者の疏忽であり、言語には判断しようがない。**意図の誤り防止は言語規則に依拠しない。**
- **返却したくないなら明示的に `Void` と書く**

これは RFC-010 の「`= { ... }` は `return` を必須とし、さもなければ `Void`
を返す」を置き換え、またその設計根拠「末尾式が戻り値かどうかの曖昧さを排除するために明示的な
`return` が必要」をも置き換える。

### 規則 ②：`return` は非局所脱出

`return` の型は `Never` である（零コンストラクタ、住む値がない）。そのセマンティクス：

- **最も近い関数境界を脱出し、値を呼び出し手に渡す**
- **あらゆるブロックを貫通する**——（存在すれば）`if` / `while` / `for` / `match` / 生ブロック /
  `spawn` / `unsafe`

`return` は「ブロックに値を返さない」。`{ return n }` はブロックとしてその値が
`n`（末尾式規則に従う）、 **型は `Never`** であり、同時に `return`
の作用は関数を脱出することである。**二つの事柄が同時に成立する。**

### 規則 ③：`else` なしの `if`

```yaoxiang
x = if c { 19 }        // else なし
```

条件が偽のとき評価できる分岐がないため、`Void` を取る。よってこの `if` の値型は `Void`（あるいは
`Void` 以外の位置では使用不可）。

値が必要なら明示的に両分岐を補う：

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` は共存の技術的基盤

`Never <: T` は任意の型 `T` に対して成立する（爆発原理、言語仕様 §型システム 参照）。したがって：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → この if の値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体 `{ return n }` の値は `Never`
- この `if` の唯一の分岐が `Never` ⇒ `if` の値は `Never`
- `Never`
  型の文は**シーケンスをここで中止する**ことを意味する——後続の文は「順次実行される次の一行」ではない
- そして `Never` は任意の型に縮退可能（爆発原理）なので、ブロック全体は `-> Int` を満たす

**「早期リターン」はここから自然に導出される**：`Never`
がシーケンスを中止 + 爆発原理による縮退可能。

## 詳細設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block)：
  空ブロック                   → Void
  { ...; e }                  → 型(e)
  { ...; s }（s が文）        → Void          // 代入の値は Void
```

### `return` の型規則

```
return e : Never        where e : T

// Never <: T' が任意の T' に対して成立するため、return は任意の返却型の位置に現れることができる
```

**`return` の合法性を制約する追加規則は不要**——爆発原理がすでに網羅している。これにより「`return` が
`X` を返す関数内に現れうるか」という問いは消滅する。

### 多分岐の合流

```
join(A, B)：
  A : Never なら  → B
  B : Never なら  → A
  それ以外      → A、B が互換であることを要求（同一型または到達可能な共通上界）
```

`if` / `match` の多分岐は `join` に従って合流する。`return` を含む分岐は型が `Never`
であるため合流に参加しない。

### RFC-007 との一貫性

RFC-007 の例は**完全に本 RFC に適合し**、改訂は不要である：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never 分岐、join で無視される
    return n * factorial(n - 1)     // 関数脱出
}
```

「早期リターン」は特例ではなく、規則 ①②と爆発原理の**帰結**である。

### RFC-010 との相違と改訂要求

RFC-010 の定義は本 RFC に従ってすでに改訂済みであり、相違は次の通り：

| RFC-010 の原条項                                                   | 現行定義                                                      |
| ------------------------------------------------------------------ | ------------------------------------------------------------- |
| 「`= { ... }` は `return` を必須とし、さもなければ `Void` を返す」 | ブロックの値 = 末尾式；空ブロック → `Void`                    |
| 設計根拠「末尾式の曖昧さを排除するため明示的な `return` が必要」   | 成立しない——末尾式は曖昧さを生まず、`return` はそれを妨げない |
| 三箇所の `return c` / `return SqliteDb` 例                         | 末尾式による記法（`spawn` / `unsafe` の値出口を統一）         |

**RFC-010 の核となる設計（`{}` を依存駆動計算ユニットとする）は不変**であり、値出口が `return`
から末尾式に変わるだけである。

### 視点の統一（設計原則）

`if` / `while`
の波括弧は**命令型の制御本体であると同時に宣言型の評価ユニットでもある**——これは**視点の差であり、二種の言語構造ではない**。したがって：

- **言語レベルで二分割しない**「制御流体」と「評価ユニット」
- すべてのブロックは同一の評価規則（共通用 規則 ①）を共有する
- `return` が唯一の例外機構であり、その例外性は構文特例ではなく `Never` の型論的性質に由来する

これにより宣言型と Python 式記法が自然に共存する：

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## トレードオフ

### 利点

- **RFC 衝突の解消**：RFC-007 と RFC-010 は矛盾から帰結関係に変わり、いずれも犠牲にする必要がない
- **規則数最小**：三つの規則 + 一つの型論的性質（爆発原理）、特例なし
- **`return` の意味が一意**：関数を脱出する。「ブロックの値 / 関数の値」間で帰属を判断する必要なし
- **視点の統一**：命令型と宣言型が共存し、言語レベルで二分割されない
- **成熟した言語との一致**：Rust もまた「末尾式 + `return : !`」で両機構を共存させている
- **新構文ゼロ**：キーワード追加なし、parser 構文規則の変更なし

### 欠点

- **末尾式が値となることによる「誤返却」リスク**：末尾行を消し忘れたとき、戻り値が静かに変わる
  - 緩和：型検査が型不一致を捕捉する；言語は意図の誤り防止を約束しない（設計判断基準 参照）
- **下流ドキュメントの同期改訂が必要**：承認済みドキュメントの例を書き換える必要がある
- **文終端との相互作用を明確にする必要**：改行で終端される末尾式も依然としてブロックの値か（開放問題 参照）

## 代替案

### 案 A：`return` に二重職務を残し、所属ブロック型でディスパッチする

関数本体 `= {}` 内の `return` は関数に帰属；`spawn {}` / `unsafe {}` 内はブロックに帰属；`if {}`
/ 生ブロック内は？

**否决理由**：`if`
の帰属は裁定不能——これがまさに元の衝突である。さらにユーザに「どのブロックが誰に帰属するか」を記憶させる必要があり、原則的根拠がない（なぜ
`if` は関数に帰属し生ブロックは自分に帰属するのか）。

### 案 B：厳格なブロック返却（`return` は常に現在のブロックに帰属）

**否决理由**：**機能欠如**。`return` はネストしたブロックから関数を早期脱出できず、guard
clause（`if err { return }`）が完全に書けなくなり、関数を層々ネストした式としてしか書けなくなる。

### 案 C：ブロックの値に新しいキーワード（`give x` / `yield x`）

**否决理由**：RFC-036 の**構文変更ゼロ**原則に違反する（新キーワード追加が必須）、さらにユーザは二つの概念（`return`
脱出 + `give` 評価）を学ぶ必要がある。末尾式案は新概念ゼロである。

### 案 D：RFC-010 の原案を維持する（明示的な `return` を必須とする）

**否决理由**：RFC-007 との衝突は調和不能（動機 参照）。さらに実装はすでに末尾式パスで動作している。

## 下流ドキュメントの改訂について

本 RFC の定義は下流ドキュメントの権威あるセマンティクスとなっており、関連ドキュメントはすべて同期済みである（廃止された記述は残していない）。

| `y = if c { 111 } else { 222 }`                   | `111`                                |
| `while { if i==2 { return 42 } }`                 | `42`（ループを貫通）                 |
| ネストした `{ { return 5 } return 1 }`            | `5`（生ブロックを貫通）              |

## 付録C：用語集

| 用語             | 定義                                                                             |
| ---------------- | -------------------------------------------------------------------------------- |
| 末尾式           | ブロック内で値を生産する最後の式、ブロックの値はその式                           |
| 非局所脱出       | 外側の評価ユニットを貫通し、関数境界に直接作用する制御フロー転移（`return`）     |
| 爆発原理         | `Never <: T` が任意の `T` に対して成立し、`Never` を任意の型に縮退可能とする原理 |
| 値を持つブロック | `= {}` / `spawn {}` / `unsafe {}`——値出口は末尾式                                |
| join             | 多分岐の合流規則、`Never` 分岐は合流に参加しない                                 |

## 付録D：関数 / ブロック値の曖昧さ裁定

### 問題

`name = { ... }`
は二つの承認済み RFC で異なるものとして定義されてきた：RFC-007（関数構文）は関数を扱い（「空引数最簡」`name = { return ... }`）、RFC-010
/ 010a はブロック値を扱う（`= {}`
は値を持つブロック、値は末尾式）。同じ構文位置に二套のセマンティクスは、実装上 `callable_parts()`
がブロックを 0 引数関数として登録する一方、`generate_block_ir`
はブロック値として取り出す——二層の理解が一致しない。

### 裁定：内容が型を決定する

同一の原則が辞書とブロックを貫くべきである：

| 情形                        | 結果           | 根拠                                          |
| --------------------------- | -------------- | --------------------------------------------- |
| `value` が `Lambda`（`=>`） | 関数           | `=>` は明示的な関数コンストラクタ             |
| アノテーションが `Fn`       | 関数           | 関数型を宣言している                          |
| アノテーションが非 `Fn` 型  | ブロック値     | アノテーションがそのまま型（`x: Int = {..}`） |
| **アノテーションなし**      | **内容で推論** | **型は内容により決定される**                  |

```yaoxiang
x: Int = { y = 5; y }      // ブロック値：x = 5（アノテーションは非 Fn）
f: () -> Int = { 5 }       // 関数：f() = 5（アノテーションは Fn）
f = { 5 }                  // 値：f = 5（アノテーションなし → 内容推論）
f = {}                     // 値：f = Void（空ブロック）
b = () => 5                // 関数：明示的な lambda
d = { "a": 1 }             // 値：Dict（内容が自己記述的）
```

**なぜ「アノテーションなしは既定で関数」としないのか**：そうすると `f = { 5 }`
は関数であり、`d = { "a": 1 }` は辞書となる——同じアノテーションなしの位置の同じ `{`
が異なる範疇のものを与える。かつて検討された三つの根拠はいずれも成立しない：

1. 既存コードのゼロ変更——移行コストは支払い可能（211 ファイル、704 箇所）であり、セマンティクスの根拠ではない
2. 関数定義は高頻度、ブロック値は低頻度——頻度は型規則ではない
3. RFC-007 は承認済み、改訂は本 RFC より重い——誤ったものは「重い」という理由で正しくはならない

**型は内容により決定され**、アノテーションの存在与否を見ない。アノテーションは依然として型を宣言する（`f: () -> Int`）が、「アノテーション欠席」だからといって既定値を押し付けることはない。

### `{}` の帰属

`Dict` 文法は少なくとも一つのキーを要求し、`{}`
は内容の根拠がないため、ブロック構造の零形態を取る → 空ブロック、値 `Void`。空辞書は `dict.new()`
を使う。詳細は spec [§2.9.1](../../../reference/language-spec/syntax.md) を参照。

### 伴う実装修正

1. **アノテーションは値取得を決定しない**：`generate_function_ir` などの三箇所がかつて
   `return_type != Void` を末尾式の値取得の閾値として使用しており、その結果アノテーションなしの
   `f = { 5 }` の末尾式が静かに破棄され `Void`
   を返していた。アノテーションは*検査*が必要か否かを決めるだけであり、*評価*が必要か否かは決めない。
2. **`callable_parts()` は無条件にブロックを呑み込まない**：分岐は
   `Expr::block_binding_is_function(アノテーション, 値)` により統一的に判定される。
