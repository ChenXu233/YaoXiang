# RFC-010a: 末尾式の評価と return セマンティクス

> **参考**:
>
> - [RFC-010: 統一型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   依存駆動計算ユニット
> - [RFC-007: 関数定義構文統一方案](./007-function-syntax-unification.md)
>   — コードブロック返却規則、早期 return
> - [RFC-038: 文の終端と改行規則](038-statement-termination.md) — 文と式の改行挙動
> - [言語仕様 §型システム](/reference/language-spec/type-system.md) — `Never` 爆発原理

## 概要

`return` とブロック評価のセマンティクスを統一し、RFC-007 と RFC-010 の間の記述矛盾を解消する。

**三つの自己無撞着な規則**を提案する：ブロックの値は末尾式（唯一の出口）に等しい；`return` は型
`Never` の**非局所脱出**（関数を脱出し、ブロックに「値を返さない」）；`if` に `else` がない場合は
`Void` とする。

`return` とブロック評価は**言語レベルで二分しない**——`{ return n }` はブロックとして値が `n`（型
`Never`）であると同時に、`return`
の作用は関数の脱出であり、二つの事象は**爆発原理**（`Never <: T`）によって共存する。RFC-007 の「早期 return」と RFC-010 の「ブロックに値がある」はこの三つの規則の帰結であり、矛盾する特例ではない。

新しい構文もキーワードもない。

## 動機

### 記述の衝突

playground のフィボナッチ例がセマンティクスの分岐を露呈した：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // この return は「if のものか、関数のものか？」
  }
  return fib(n - 1) + fib(n - 2)
}
```

既に承認された二つの RFC は**逆方向**の推論を与える：

| RFC                     | 記述                                                                                                 | 推論セマンティクス                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **RFC-007**（承認済み） | `factorial` を例に、タイトルを**「早期 return：return の使用」**と書く：`if n <= 1 { return 1 }`     | `return` は `if` と関数本体を貫通し、**関数に戻る** |
| **RFC-010**（承認済み） | 「`{}` は依存駆動計算ユニット…`return` で明示的に値を返す」；`spawn { return c }` はタスク結果を返す | `return` は**この `{}` 自身に**値を返す             |

RFC-010 によれば、`if n <= 1 { return 1 }` の波括弧は計算ユニットであり、`return 1`
がそれに与える値は 1 であるから、`if`
文の値は捨てられ、次の行が必ず実行される——**fib は無限再帰**する。RFC-007に従えば正しい。

### 根本原因：`return` という語の二重職務

- **RFC-007 は「関数の脱出」を表すために使う**——制御フローの概念
- **RFC-010 は「このブロックの値はこれである」を表すために使う**——評価の概念

制御フローのキーワードで評価を表すのは範疇エラー（category
error）である。一語が二職務を担う以上、如何に調整してもどちらかが犠牲になる。

### 下流ドキュメントによる誤った拡大解釈

`docs/src/reference/language-spec/syntax.md` は RFC-010 の「`{}`
ブロック」を**すべての波括弧**に拡大した：

- §2.9：「`{}` 内の `return`
  は**常にその内容を一つ上のスコープに返す**」（さらに「統一セマンティクス：すべての `{}`
  ブロック」と称する）
- §3.3：「`return` は**コードブロックから値を返す**ために使われる」

しかし RFC-010 原本が定義しているのは**三種の値を持つブロック**（`= {}` / `spawn {}` /
`unsafe {}`）であり、**`if` / `while` / `for` / `match` の波括弧には一切言及していない**。

### 実装の現状

| 挙動                                     | 現状                                      |
| ---------------------------------------- | ----------------------------------------- |
| `if n == 0 { return 7 } … return 8`      | 関数の脱出（`h(0) = 7`）                  |
| `f = { n + 1 }`                          | 末尾式が使える（`5` を返す）              |
| `x = { y = 5; y }`（裸ブロックの末尾式） | `E3006` 変数未解決（#343 参照）           |
| `f: () -> Int = { if c {5} else {6} }`   | `void` を返す（末尾式が捨てられる、#344） |
| `f: () -> Int = { "s" }`                 | 警告なくコンパイル成功（#345 参照）       |
| `x = if c { 19 }`（`else` なし）         | `19`（`Void` であるべき、#346 参照）      |
| `v = unsafe { 42 }`                      | `void`（#347 参照）                       |
| `y = if c { 111 } else { 222 }`          | 使える（`if` を式として）                 |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx`
はかつて「末尾式はもはや暗黙的に return されない」と主張していたが、当該ケースを網羅していなかったためテストは赤くならなかった。当該ファイルは
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx` に置き換えられた。

## 提案

### 三つの規則

```
① ブロックの値 = 末尾式（唯一の出口）
   代入文の値は Void；空ブロック {} の値は Void
② return : (T) -> Never
   非局所脱出：最も近い関数境界を脱出する
③ if に else がない → Void
```

**この三つで「早期 return」が導出され、`return` が関数のみを指すとする追加規則は不要である。**

### 規則 ①：ブロックの値

ブロックの**最後の文/式**がブロックの値である（末尾式）。これは**「末尾式がなければ Void」ではない**——非空ブロックは常に末尾式を持ち（末尾の文自体が末尾式である）、空ブロック
`{}` の値は `Void` である。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 代入を末尾式にすると → ブロックの値は Void
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Void を望むなら明示的に書く
c = {
    log(x)
    Void                 // 明示的な Void
}
```

**設計判断（機構と保護の分離）**：

- **言語規則は機構のみを与える**：末尾の文がブロックの値であり、規則は唯一・無曖昧
- **保護は型検査が提供**：関数宣言 `-> Int` に対し末尾式の型が一致しない場合 → コンパイルエラー
- **言語は「意図の誤り」を防がない**：末尾式の型がたまたま返り型と一致するが意味は本意でないという場合、それは作者の不注意であり、言語には判断できない。**意図の誤り防止に言語規則を依拠しない。**
- **値を返したくなければ明示的に `Void` と書く**

これは RFC-010 の「`= { ... }` は必ず `return` を使うこと、さもなければ `Void`
を返す」を置き換え、またその設計理由「末尾式が返り値か否かの曖昧さを解消するために明示的な `return`
が必要」も無効化する。

### 規則 ②：`return` は非局所脱出である

`return` の型は `Never` である（零コンストラクタ、住む値がない）。そのセマンティクス：

- **最も近い関数境界を脱出し、値を呼び出し元に渡す**
- **あらゆるブロックを貫通する**——`if` / `while` / `for` / `match` / 裸ブロック / `spawn` /
  `unsafe`（存在すれば）

`return` は「ブロックに値を返す」ものではない。`{ return n }` はブロックとして末尾式規則により値が
`n`（型 `Never`）であり、同時に `return` の作用は関数の脱出である。**二つの事象は同時に成立する。**

### 規則 ③：`if` に `else` がない場合

```yaoxiang
x = if c { 19 }        // else なし
```

条件が偽のとき評価すべき分岐がないため、`Void` を取る。よってこの `if` の値型は `Void`（あるいは非
`Void` 位置では使用不可）。

値が必要なら明示的に両分岐を補完する：

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` は共存の技術的基礎である

`Never <: T` は任意の型 `T` に対し成立する（爆発原理、言語仕様 §型システム 参照）。したがって：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → 当該 if の値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体 `{ return n }` の値は `Never`
- この `if` の唯一分岐が `Never` ⇒ `if` の値は `Never`
- `Never`
  型の文は**シーケンスがここで停止する**ことを意味する——後続の文は「順次実行される次行」ではない
- 一方 `Never` は任意の型に縮退可能（爆発原理）なので、ブロック全体として `-> Int` を満たす

**「早期 return」はここから自然に導かれる**：`Never` によるシーケンス停止 + 爆発原理による縮退可能。

## 詳細設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block)：
  空ブロック                → Void
  { ...; e }              → 型(e)
  { ...; s }（s は文）    → Void          // 代入の値は Void
```

### `return` の型規則

```
return e : Never        where e : T

// Never <: T' が任意の T' に対し成立するため、return は任意の返り型の位置に現れることができる
```

**`return`
の合法性を制約する追加規則は不要である**——爆発原理がすでにカバーする。これにより「`return` が返り型
`X` の関数に現れうるか」という問いが消滅する。

### 多分岐の結合

```
join(A, B)：
  もし A : Never  → B
  もし B : Never  → A
  そうでなければ  → A、B が互換であることを要求（同一型または到達可能な共通上界）
```

`if` / `match` の多分岐は `join` で結合する。`return` を含む分岐は型が `Never`
であるため結合に参加しない。

### RFC-007 との一貫性

RFC-007 の例は**完全に本 RFC に適合し、修正不要**である：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never 分岐、join で無視される
    return n * factorial(n - 1)     // 関数の脱出
}
```

「早期 return」は特例ではなく、規則 ① ② と爆発原理からの**帰結**である。

### RFC-010 との相違と修正要求

RFC-010 は三箇所を訂正する必要がある（正誤表方式で、「下流ドキュメントの修正要求」を参照）：

| RFC-010 節                                                             | 訂正後                                                  |
| ---------------------------------------------------------------------- | ------------------------------------------------------- |
| 「`= { ... }` は必ず `return` を使うこと、さもなければ `Void` を返す」 | ブロックの値 = 末尾式；空ブロック → `Void`              |
| 設計理由「明示的な `return` で末尾式の曖昧さを解消する必要」           | 廃止——末尾式は曖昧さを生まず、`return` はそれを妨げない |
| 三箇所の `return c` / `return SqliteDb` の例                           | 末尾式に変更（`spawn` / `unsafe` の値出口を統一）       |

**RFC-010 の核心設計（依存駆動計算ユニットとしての `{}`）は不変**であり、値出口のみ `return`
から末尾式に変わる。

### 視点の統一（設計原則）

`if` / `while`
の波括弧は**命令的制御体であると同時に宣言的評価ユニットでもある**——これは**視点の差であり、二つの言語コンストラクタではない**。よって：

- 言語レベルで「制御流体」と「評価ユニット」を**二分しない**
- すべてのブロックは同一の評価規則（規則 ①）を共有する
- `return` は唯一の例外機構であり、その例外性は `Never` の型論的性質に由来し、構文上の特例ではない

これにより宣言的書き方と Python 流の書き方が自然に共存する：

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## トレードオフ

### 利点

- **RFC 間の衝突を解消**：RFC-007 と RFC-010 は矛盾関係から帰結関係になり、いずれも犠牲にならない
- **規則数が最少**：三つの規則 + 一つの型論的性質（爆発原理）、特例なし
- **`return` の意味が唯一**：関数の脱出。「ブロックの値 / 関数の値」間で帰属を判断する必要がなくなる
- **視点が統一**：命令的と宣言的が共存し、言語層で二分されない
- **成熟した言語と一致**：Rust も同様に「末尾式 + `return : !`」で両機構を共存させている
- **新構文ゼロ**：キーワードを追加せず、parser の構文規則も変えない

### 欠点

- **末尾式が値になることによる「誤返り」リスク**：末尾行を消し忘れた場合、返り値が静かに変わる
  - 緩和：型検査が型不一致を捕捉する；言語は意図の誤り防止を約束しない（設計判断参照）
- **RFC-010 に正誤表が必要**：既に承認された文書の例を書き換える必要がある
- **裸ブロックの末尾式は未実装**：現在はコンパイラの内部エラー（独立した問題）
- **文終端との相互作用を明確化する必要**：改行終端された末尾式が依然としてブロックの値であるか（オープン問題参照）

## 代替案

### 案 A：`return` に二重職務を保持し、所在ブロックの型でディスパッチ

関数本体 `= {}` の `return` は関数に帰属；`spawn {}` / `unsafe {}` ではブロックに帰属；`if {}`
/ 裸ブロックではどこに？

**却下理由**：`if`
の帰属を決定不能——まさに元の衝突そのもの。またユーザーは「どのブロックが誰のものか」を記憶する必要があり、原則的根拠がない（なぜ
`if` は関数で裸ブロックは自身なのか）。

### 案 B：厳格なブロック返却（`return` は常に現在のブロックに帰属）

**却下理由**：**機能欠落**。`return` はネストされたブロックから関数を早期脱出できなくなり、guard
clause（`if err { return }`）が完全に書けなくなる。関数を何重にもネストされた式として書くことしかできなくなる。

### 案 C：ブロックの値に新キーワード（`give x` / `yield x`）

**却下理由**：RFC-036 の**構文変更ゼロ原則**に違反し（新キーワードの追加が必要）、さらにユーザーは二つの概念を学ばねばならない（`return`
は脱出 + `give` は評価）。末尾式案は新概念ゼロ。

### 案 D：RFC-010 原本を保持（明示的な `return` を必須とする）

**却下理由**：RFC-007 との衝突を調和不能（動機参照）。また実測済み実装は既に末尾式ルートを採っている。

- [ ] 空ブロック `{}` を関数本体とし返り型が `Void` でない場合の診断文言

## 付録 A：実測証拠

以下はすべて 0.8.0 で再現。

| コード                                            | 実測                                 |
| ------------------------------------------------- | ------------------------------------ |
| `h: (n)->Int = { if n==0 { return 7 } return 8 }` | `h(0)=7`, `h(1)=8`                   |
| `f: (n)->Int = { n + 1 }`                         | `5`（末尾式が使える）                |
| `f: ()->Int = { if c {5} else {6} }`              | `void`（`5` であるべき、#344 参照）  |
| `f: ()->Int = if c {5} else {6}`                  | `5`                                  |
| `f: ()->Int = { match ... }`                      | 正しい                               |
| `f: ()->Int = { while ...; i }`                   | 正しい                               |
| `{ y = 5; y }` をバインディング式として           | `E3006`（#343 参照）                 |
| `f: ()->Int = { "s" }`                            | 警告なく通る（#345 参照）            |
| `x = if c { 19 }`（`else` なし）                  | `19`（`Void` であるべき、#346 参照） |

| `while { if i==2 { return 42 } }`                 | `42`（ループを貫通）                 |

## 付録 C：用語集

| 用語         | 定義                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| 末尾式       | ブロック内で最後に値を生成する式、ブロックの値そのもの                       |
| 非局所脱出   | 外側の評価ユニットを横切り、直接関数境界に作用する制御フロー転送（`return`） |
| 爆発原理     | `Never <: T` が任意の `T` に対し成立し、`Never` を任意の型に縮退可能とする   |
| 有値ブロック | `= {}` / `spawn {}` / `unsafe {}`——値出口は末尾式                            |
| join         | 多分岐の結合規則、`Never` 分岐は結合に参加しない                             |

## 付録 D：関数 / ブロック値の曖昧さ裁定（裁定 C）

> **正誤表（2026-09-19）：裁定 C の注釈なし行は覆された。**
>
> ユーザー裁定：**「内容が型を決定する」（読み方 B）に統一**、理由は同一原則を辞書とブロックで貫くため：
>
> > B に統一すれば、`{}` が自然に位置づけられる。
>
> **現行規則**
>
> | 状況                        | 結果           | 根拠                                |
> | --------------------------- | -------------- | ----------------------------------- |
> | `value` が `Lambda`（`=>`） | 関数           | `=>` は明示的な関数コンストラクタ   |
> | 注釈が `Fn`                 | 関数           | 関数型を宣言                        |
> | 注釈が非 `Fn` 型            | ブロック値     | 注釈がそのまま型（`x: Int = {..}`） |
> | **注釈なし**                | **内容で推論** | **型は内容により決定**              |
>
> 重要な変更：`f = { 5 }` は現在**値** `5`（`Int`）であり、もはや関数ではない。
>
> ```yaoxiang
> x: Int = { y = 5; y }      // ブロック値：x = 5（注釈は非 Fn）
> f: () -> Int = { 5 }       // 関数：f() = 5（注釈は Fn）
> f = { 5 }                  // 値：f = 5（注釈なし → 内容で推論）
> f = {}                     // 値：f = Void（空ブロック）
> b = () => 5                // 関数：明示的 lambda
> d = { "a": 1 }             // 値：Dict（内容が自己記述的）
> ```
>
> **なぜ裁定 C を覆したか**
>
> 裁定 C の元来の根拠（「注釈なしの場合はデフォルトで関数」）は**実装便宜志向**である：
>
> 1. ~~既存コードの改変がゼロ~~——移行コストは許容可能（211 ファイル、704 箇所）であり、意味的依据ではない
> 2. ~~関数定義が高頻度、ブロック値が低頻度~~——頻度は型規則ではない
> 3. ~~RFC-007 は承認済みで、改訂はこちらより高コスト~~——誤ったものを「高いコスト」のために正しいことにしない
>
> 本当の問題は**一貫性のなさ**である：`f = { 5 }` は関数だが、`d = { "a": 1 }` は辞書——同じ `{`
> が同じ注釈なし位置で異なる范畴のものを与える。裁定 C が自認した「コスト」はまさにこの亀裂である：「`f = { 5 }`
> において `f` は関数であって `5` ではない…『波括弧は値なり』という直観に反する」。
>
> 現行規則は亀裂を解消する：**型は内容により決定**され、注釈の有無を見ない。注釈は依然として型を宣言するが（`f: () -> Int`）、「注釈不在」を理由にデフォルト値を課さない。
>
> **`{}` の位置づけ**
>
> B に統一すれば `{}` は自然に落ち着く：`Dict` 文法は少なくとも一つのキーを要求し、`{}`
> は内容の拠り所がない、よってブロック構造の零形態を取る → 空ブロック、値 `Void`。空辞書は
> `dict.new()` を使う。詳細は spec [§2.9.1](../.../reference/language-spec/syntax.md) を参照。
>
> **不変の局所**
>
> 付録 D の以降の二項目（「注釈は値取りを決定しない」、「`callable_parts()`
> は無条件にブロックを呑まなくなる」）は依然有効；後者は現在 `Expr::block_binding_is_function`
> で実装されるが、その注釈なし分岐は上表の変更に伴い既に変わっている。

### 問題（歴史的背景）

`name = { ... }` は既に承認された二つの RFC により異なるものとして定義されていた：

| RFC                 | 定義                                              |
| ------------------- | ------------------------------------------------- |
| RFC-007（関数構文） | 関数。「最簡空参」`name = { return ... }`         |
| RFC-010 / 010a      | ブロック値。「`= {}` は有値ブロック、値は末尾式」 |

同一構文位置に二セットの意味論があり、実装上 `callable_parts()`
がブロックを 0 引数関数として登録する一方、 `generate_block_ir`
はブロック値として値を取る——二層の理解が不整合であった。

### 元の裁定：注釈優先、デフォルトは関数（**廃止済み**）

| 状況                        | 結果           | 根拠                                |
| --------------------------- | -------------- | ----------------------------------- |
| `value` が `Lambda`（`=>`） | 関数           | `=>` は明示的な関数コンストラクタ   |
| 注釈が `Fn`                 | 関数           | 関数型を宣言                        |
| 注釈が非 `Fn` 型            | **ブロック値** | 注釈がそのまま型（`x: Int = {..}`） |
| 注釈なし                    | **関数**       | デフォルト；RFC-007「最簡空参」     |

**重要：ブロック値セマンティクスは新構文に依拠しない。** `{ ... }`
を即時評価したいなら目的型を書く：

```yaoxiang
x: Int = { y = 5; y }      # ブロック値：x = 5（注釈は非 Fn）
f: () -> Int = { 5 }       # 関数：f() = 5（注釈は Fn）
f = { 5 }                  # 関数：f() = 5（注釈なし、デフォルトは関数）  # ← この行は廃止
b = () => 5                # 関数：式本体 lambda
```

### 元の根拠（**無効**）

注釈は**そもそも型を宣言している**：`x: Int = ...` は `x` が `Int` であることを意味し、`{...}` は
`Int` 値である；`f: () -> Int = ...` は `f` が関数であることを意味し、`{...}`
は関数本体である。**型指向であって、新規則の発明ではない。**

注釈なしの場合にデフォルトで関数とするのは、以下の理由による：

1. 既存コードの改変がゼロ（リポジトリ内、注釈なしの `name = { `
   バインディングは合計 203 箇所、すべて `main`）
2. 関数定義が高頻度、ブロック値が低頻度
3. RFC-007 は承認済みで、改訂はこちらより高コスト

### コスト（既知・受容）

`f = { 5 }` において `f` は**関数**であり、`5`
ではない。これは「波括弧は値なり」という直観に反する——しかしそれはまさにRFC-007 が承認した定義であり、**注釈が脱出の出口である**：`f: Int = { 5 }`
と書けば値が得られる。

### 裁定と同時の実装欠陥修正

1. **注釈は値取りを決定しない**（根本原因 1）：`generate_function_ir` 等の三箇所が
   `return_type != Void` を末尾式の値取り閾値として使っており、注釈なしの `f = { 5 }`
   で末尾式が警告なく捨てられ、 `Void`
   を返していた。注釈は*チェック*要不要を決めるだけで、*評価*要不要を決めてはならない。
2. **`callable_parts()` はもはや無条件にブロックを呑まない**：分岐は
   `Expr::block_binding_is_function(注釈, 値)` で統一的に判定する。
