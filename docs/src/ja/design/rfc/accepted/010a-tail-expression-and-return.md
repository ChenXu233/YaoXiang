# RFC-010a: 末尾式の評価と return の意味論

> **参考**:
>
> - [RFC-010: 統一型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   の依存駆動計算ユニット
> - [RFC-007: 関数定義構文の統一方案](./007-function-syntax-unification.md)
>   — コードブロックの返却ルール、早期リターン
> - [RFC-038: 文の終端と改行ルール](038-statement-termination.md) — 文と式の改行挙動
> - [言語仕様 §型システム](/reference/language-spec/type-system.md) — `Never` の爆発原理

## 概要

`return` とブロック評価の意味論を統一し、RFC-007 と RFC-010 の間の記述上の衝突を解消する。

**三つの自己無撞着なルール**を提案する: ブロックの値は末尾式と等しい（唯一の出口）；`return` は型が
`Never` の**非局所退出**（関数を抜ける、「ブロックに返す」のではない）；`if` に `else` がない場合は
`Void` を取る。

`return` とブロック評価は**言語レベルで二分されない**——`{ return n }` をブロックとして見ればその値は
`n`（型 `Never`）であり、同時に `return`
の作用は関数を抜けることであり、二つは**爆発原理**（`Never <: T`）によって共存する。RFC-007 の「早期リターン」と RFC-010 の「ブロックは値を持つ」はこの三つのルールの帰結であり、矛盾する特例ではない。

新しい構文もキーワードもなし。

## 動機

### 記述の衝突

playground のフィボナッチ例が意味論の分岐を露呈した:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // この return は「if の」ものか「関数の」ものか？
  }
  return fib(n - 1) + fib(n - 2)
}
```

二つの受領済 RFC が**逆の**導出を与える:

| RFC                   | 記述                                                                                                 | 導出される意味論                                    |
| --------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **RFC-007**（受領済） | `factorial` を例に、タイトルを**「早期リターン: return の使用」**と書く: `if n <= 1 { return 1 }`    | `return` は `if` と関数本体を貫通し、**関数に戻る** |
| **RFC-010**（受領済） | 「`{}` は依存駆動計算ユニット…`return` で明示的に値を返す」；`spawn { return c }` はタスク結果を返す | `return` は**この `{}`** に値を返す                 |

RFC-010 によれば、`if n <= 1 { return 1 }` の波括弧は計算ユニットであり、`return 1`
がその値を 1 にすれば、`if`
文の値は捨てられ、次の行が必ず実行される——**fib は無限再帰**となる。RFC-007 によれば正しい。

### 根本原因: `return` という語の二重職務

- **RFC-007 はこれで「関数を抜ける」**——制御フローの概念
- **RFC-010 はこれで「このブロックの値はこれ」**——評価の概念

制御フローのキーワードで評価を表現するのは範疇錯誤（category
error）である。一語で二つの職務を担う以上、どちらか一方が常に犠牲になる。

### 下流ドキュメントによる誤った拡張解釈

`docs/src/reference/language-spec/syntax.md` は RFC-010 の「`{}`
ブロック」を**すべての波括弧**に拡張している:

- §2.9: 「`{}` 内の `return`
  は**常に内容を一つ上位的スコープに返す**」（さらに「統一意味論: すべての `{}` ブロック」と称する）
- §3.3: 「`return` は**コードブロックから値を返す**」

しかし RFC-010 の原文が定義しているのは**三つの値を持つブロック**（`= {}` / `spawn {}` /
`unsafe {}`）であり、**`if` / `while` / `for` / `match` の波括弧には一切触れていない**。

### 実装の現状

| 挙動                                     | 現状                                      |
| ---------------------------------------- | ----------------------------------------- |
| `if n == 0 { return 7 } … return 8`      | 関数を抜ける（`h(0) = 7`）                |
| `f = { n + 1 }`                          | 末尾式が使える（5 を返す）                |
| `x = { y = 5; y }`（裸ブロックの末尾式） | `E3006` 変数未解決（#343 を参照）         |
| `f: () -> Int = { if c {5} else {6} }`   | `void` を返し、末尾式が捨てられる（#344） |
| `f: () -> Int = { "s" }`                 | 沈黙してコンパイルを通る（#345 を参照）   |
| `x = if c { 19 }`（`else` なし）         | `19`（`Void` であるべき、#346 を参照）    |
| `v = unsafe { 42 }`                      | `void`（#347 を参照）                     |
| `y = if c { 111 } else { 222 }`          | 使える（`if` を式として使用）             |

はかつて「末尾式はもはや暗黙的に返されない」と主張していたが、そのケースを網羅しておらず、テストが赤くならなかった。このファイルは
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx` に置き換えられた。

## 提案

### 三つのルール

```
① ブロックの値 = 末尾式（唯一の出口）
   代入文の値は Void；空ブロック {} の値は Void
② return : (T) -> Never
   非局所退出: 最も近い関数境界を抜ける
③ else のない if → Void
```

**この三つで「早期リターン」は十分導出され、`return` が特に関数を指す追加ルールは不要。**

### ルール ①: ブロックの値

ブロックの**最後の文/式**がすなわちブロックの値（末尾式）である。これは**「末尾式がなければ Void」ではない**——空でないブロックは常に末尾式を持ち（最後にある文そのものが末尾式）、空ブロック
`{}` の値は `Void`。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 代入を末尾式に → ブロックの値は Void
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Void を望むなら明示的に書く
c = {
    log(x)
    Void                 // 明示的な Void
}
```

**設計判断基準（機構と保護の分離）**:

- **言語ルールは機構だけを与える**: 最後の文がすなわちブロックの値で、ルールは唯一・無曖昧
- **保護は型検査が提供する**: 関数が `-> Int`
  と宣言されているのに末尾式の型が一致しない → コンパイルエラー
- **言語は「意図の誤り」を防がない**: 末尾式の型がたまたま戻り型と一致したが意味は意図と異なる、という場合は作者のうっかりであり、言語には判断できない。**言語ルールで意図の誤りを防ごうとはしない。**
- **返したくないなら明示的に `Void` と書け**

これは RFC-010 の「`= { ... }` では必ず `return` を使うこと、なければ `Void`
を返す」を置き換え、またその設計理由「明示的な `return`
で『最後の式が戻り値かどうか』の曖昧さを排除する」も無効化する。

### ルール ②: `return` は非局所退出

`return` の型は `Never`（コンストラクタを持たず、値を持てない）。その意味論:

- **最も近い関数境界を抜け**、値を呼び出し元に渡す
- **すべてのブロックを貫通する**——（存在すれば）`if` / `while` / `for` / `match` / 裸ブロック /
  `spawn` / `unsafe`

`return` は「ブロックに返す」のではない。`{ return n }` をブロックとして見れば、その値は
`n`（末尾式ルール）、**型 `Never`**；同時に `return`
の作用は関数を抜けること。**二つのことが同時に成立する。**

### ルール ③: `else` のない `if`

```yaoxiang
x = if c { 19 }        // else なし
```

条件が偽のとき評価すべき分岐がないため、`Void` を取る。したがってこの `if` の値型は `Void`（または非
`Void` 位置では使用不可）。

値が必要なときは明示的に両分岐を揃える:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` は共存の技術的基礎

`Never <: T` は任意の型 `T` に対して成立する（爆発原理、言語仕様 §型システムを参照）。したがって:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → この if の値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体 `{ return n }` の値は `Never`
- この `if` の唯一の分岐が `Never` ⇒ `if` の値は `Never`
- `Never` 型の文は**シーケンスがここで停止する**ことを意味する——後続の文は「順次実行の次」ではない
- そして `Never` は任意の型に縮退可能（爆発原理）なので、ブロック全体は `-> Int` を満たす

**「早期リターン」はここから自然に導出される**: `Never`
によるシーケンス停止 + 爆発原理による縮退可能性。

## 詳細設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block)：
  空ブロック              → Void
  { ...; e }             → 型(e)
  { ...; s }（s は文）   → Void          // 代入の値は Void
```

### `return` の型ルール

```
return e : Never        where e : T

// Never <: T' は任意の T' について成立するため、return は任意の戻り型の位置に現れ得る
```

**`return` の合法性を制約する追加ルールは不要**——爆発原理がすでにカバーする。これにより「`return` は
`X` を返す関数の中に書けるか」這種の問いは消滅する。

### 多分岐の結合

```
join(A, B)：
  A : Never ならば  → B
  B : Never ならば  → A
  そうでなければ    → A、B の互換性を要求（同一型または到達可能な共通上界）
```

`if` / `match` の多分岐は `join` で結合される。`return` を含む分岐は型が `Never`
なので結合に参加しない。

### RFC-007 との一貫性

RFC-007 の例は**本 RFC に完全準拠**し、修正不要:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never 分岐、join で無視される
    return n * factorial(n - 1)     // 関数を抜ける
}
```

「早期リターン」は特例ではなく、ルール ①② と爆発原理の**帰結**である。

### RFC-010 との相違と改訂要求

RFC-010 の定義は本 RFC に従って改訂された。相違点:

| RFC-010 旧条項                                                     | 現行定義                                                        |
| ------------------------------------------------------------------ | --------------------------------------------------------------- |
| 「`= { ... }` では必ず `return` を使う、なければ `Void` を返す」   | ブロックの値 = 末尾式；空ブロック → `Void`                      |
| 設計理由「明示的な `return` で末尾式の曖昧さを排除する必要がある」 | 成立しない——末尾式は曖昧さを生まず、`return` はそれに干渉しない |
| 三箇所の `return c` / `return SqliteDb` 例                         | 末尾式での書き方（`spawn` / `unsafe` の値出口を統一）           |

**RFC-010 の中心設計（`{}` を依存駆動計算ユニットとする）は不変**で、値出口が `return`
から末尾式に変わるだけ。

### 視点の統一（設計原則）

`if` / `while`
の波括弧は**命令的な制御体であり、かつ宣言的な評価ユニットでもある**——これは**視点の差であって、二つの異なる言語構文ではない**。したがって:

- 言語レベルで「制御流体」と「評価ユニット」を二分しない
- すべてのブロックは同じ評価ルール（ルール ①）を共有する
- `return` が唯一の例外機構であり、その例外性は `Never` の型論的性質に由来し、構文上の特例ではない

これにより宣言的と Python 的な書き方が自然に共存する:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## トレードオフ

### 利点

- **RFC の衝突を解消**:
  RFC-007 と RFC-010 は矛盾する関係から帰結する関係に変わり、どちらかを犠牲にする必要がない
- **ルール数が最少**: 三つのルール + 一つの型論的性質（爆発原理）、特例なし
- **`return` の意味が唯一**: 関数を抜ける。「ブロックの値 / 関数の値」の間で帰属を判断する必要なし
- **視点の統一**: 命令的と宣言的が共存し、言語レベルで二分しない
- **成熟した言語と一致**: Rust も同様に「末尾式 + `return : !`」で二つの機構を共存させている
- **新構文ゼロ**: キーワード追加なし、parser の構文ルール変更なし

### 欠点

- **末尾式が値になることの「誤返却」リスク**: 最終行を消し忘れたとき戻り値が静かに変わる
  - 緩和策: 型不一致は型検査で捕捉；言語は意図の誤り防止を約束しない（設計判断基準を参照）
- **下流ドキュメントの同期改訂が必要**: 受領済ドキュメントの例を書き換える必要がある
- **文の終端との相互作用を明確化する必要**: 改行で終端する末尾式もブロックの値であり続けるか（オープン問題を参照）

## 代替案

### 案 A: `return` の二重職務を保持し、所在ブロックの型でディスパッチ

関数本体 `= {}` の `return` は関数に帰属；`spawn {}` / `unsafe {}` ではブロックに帰属；`if {}`
/ 裸ブロックでは？

**否決理由**: `if`
の帰属は裁定不能——これがまさに元の衝突。さらに「どのブロックが誰に帰属するか」をユーザに記憶させる必要があり、原則的根拠がない（なぜ
`if` は関数に帰属し、裸ブロックは自分に帰属するのか）。

### 案 B: 厳格なブロック返却（`return` は常に現在のブロックに帰属）

**否決理由**: **機能欠落**。`return`
は決してネストしたブロックから関数を早期脱出できず、ガード節（`if err { return }`）は完全に書けず、関数を層々ネストした式としてしか書けなくなる。

### 案 C: ブロックの値に新キーワード（`give x` / `yield x`）

**否決理由**:
RFC-036 の**構文変更ゼロ原則**に違反（新キーワード追加が必要）、さらにユーザは二つの概念（`return`
退出 + `give` 評価）を学ぶ必要がある。末尾式案は新概念ゼロ。

### 案 D: RFC-010 の原状維持（明示的な `return` 必須）

**否決理由**:
RFC-007 との衝突は調停不能（動機を参照）。また実測された実装はすでに末尾式経路を採っている。

## 下流ドキュメントの改訂

本 RFC の定義が下流ドキュメントの権威ある意味論となった；関連ドキュメントは同期済（廃止された記述は残されていない）。

## 付録 C: 用語集

| 用語             | 定義                                                                         |
| ---------------- | ---------------------------------------------------------------------------- |
| 末尾式           | ブロック内で最後に値を生成する式、ブロックの値そのもの                       |
| 非局所退出       | 外側の評価ユニットを横切り、直接関数境界に作用する制御フロー遷移（`return`） |
| 爆発原理         | `Never <: T` が任意の `T` について成立し、`Never` を任意の型に縮退可能とする |
| 値を持つブロック | `= {}` / `spawn {}` / `unsafe {}`——値出口は末尾式                            |
| join             | 多分岐結合ルール、`Never` 分岐は結合に参加しない                             |

## 付録 D: 関数 / ブロック値曖昧さの裁定

### 問題

`name = { ... }` はかつて二つの受領済 RFC で別物として定義されていた:
RFC-007（関数構文）は関数を扱い（「空引数最簡」`name = { return ... }`）、RFC-010 /
010a はブロック値を扱う（`= {}`
は値を持つブロック、値は末尾式）。同じ構文位置に二套の意味論があり、実装上 `callable_parts()`
がブロックを 0 引数関数として登録する一方、`generate_block_ir`
はブロック値として値を取る——二層の理解が一致していない。

### 裁定: 内容が型を決定する

同じ原則はディクショナリとブロックにも貫かれるべき:

| 場合                     | 結果             | 根拠                                |
| ------------------------ | ---------------- | ----------------------------------- |
| `値` が `Lambda`（`=>`） | 関数             | `=>` は明示的な関数コンストラクタ   |
| 注釈が `Fn`              | 関数             | 関数型を宣言している                |
| 注釈が非 `Fn` 型         | ブロック値       | 注釈がそのまま型（`x: Int = {..}`） |
| **注釈なし**             | **内容から推論** | **型は内容によって決まる**          |

```yaoxiang
x: Int = { y = 5; y }      // ブロック値: x = 5（注釈は非 Fn）
f: () -> Int = { 5 }       // 関数: f() = 5（注釈が Fn）
f = { 5 }                  // 値: f = 5（注釈なし → 内容から推論）
f = {}                     // 値: f = Void（空ブロック）
b = () => 5                // 関数: 明示的 lambda
d = { "a": 1 }             // 値: Dict（内容が自己記述的）
```

**「注釈なしデフォルトで関数」としない理由**: そうすると `f = { 5 }` は関数で、`d = { "a": 1 }`
はディクショナリ——同じ無注釈位置で同じ `{`
が異なる範疇のものを与える。検討された三つの理由はどれも成立しない:

1. 既存コードのゼロ変更——移行コストは支払可能（211 ファイル、704 箇所）、意味論的根拠ではない
2. 関数定義は高頻度、ブロック値は低頻度——頻度は型ルールではない
3. RFC-007 は受領済、改訂コストが本 RFC より高い——誤ったものを「コストが高い」という理由で正しくなんとかする

**型は内容によって決定され**、注釈の有無をみない。注釈は依然として型を宣言する（`f: () -> Int`）が、「注釈が欠けている」ことをもってデフォルト値を押し付けることはない。

### `{}` の位置付け

`Dict` 文法は少なくとも一つのキーを要求し、`{}`
は内容の根拠がないため、ブロック構造のゼロ形態を取る → 空ブロック、値 `Void`。空ディクショナリは
`dict.new()` を使う。詳細は spec [§2.9.1](../.../reference/language-spec/syntax.md) を参照。

### 伴う実装修正

1. **注釈が取値を決めてはならない**: `generate_function_ir` など三箇所でかつて `return_type != Void`
   を末尾式の取値閾値として使っており、注釈なしの `f = { 5 }` の末尾式が静かに捨てられ `Void`
   を返していた。注釈は*検査*の必要性を決めるだけで、*評価*の必要性を決めてはならない。
2. **`callable_parts()` は無条件にブロックを呑み込まない**: 振り分けは
   `Expr::block_binding_is_function(注釈, 値)` で統一的に判定する。
