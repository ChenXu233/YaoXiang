# RFC-010a: 末尾式の評価と return セマンティクス

> **参照**:
>
> - [RFC-010: 統一型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   依存駆動計算ユニット
> - [RFC-007: 関数定義構文統一方案](./007-function-syntax-unification.md)
>   — コードブロック返却規則、早期リターン
> - [RFC-038: 文の終端と改行規則](038-statement-termination.md) — 文と式の改行動作
> - [言語仕様 §型システム](/reference/language-spec/type-system.md) — `Never` 爆発原理

## 概要

`return` とブロック評価のセマンティクスを統一し、RFC-007 と RFC-010 の間の記述矛盾を解消する。

**三つの自己無撞着な規則**を提案する：ブロックの値は末尾式と等しい（唯一の出口）；`return` は型
`Never` の**非局所的退出**である（関数を退出させ、ブロックに「値を返さない」）；`if` に `else`
がない場合は `Void` を取る。

`return` とブロック評価は**言語レベルで二分されない**——`{ return n }` はブロックとしてその値が
`n`（型 `Never`）であり、同時に `return`
の作用は関数を退出させることであり、この二つは**爆発原理**（`Never <: T`）によって共存する。RFC-007 の「早期リターン」と RFC-010 の「ブロックは値を持つ」はこの三つの規則の帰結であり、矛盾する特例ではない。

新しい構文なし、新しいキーワードなし。

## 動機

### 記述の矛盾

playground のフィボナッチ例がセマンティクスの相違を露呈した：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // この return は「if の」か「関数の」か？
  }
  return fib(n - 1) + fib(n - 2)
}
```

二件の承認済み RFC が**逆方向**の推論を与える：

| RFC                     | 記述                                                                                                         | 推導されるセマンティクス                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| **RFC-007**（承認済み） | `factorial` を例に、タイトルは**「早期リターン：return の使用」**と書かれている：`if n <= 1 { return 1 }`    | `return` は `if` と関数本体を貫通し、**関数に戻る** |
| **RFC-010**（承認済み） | 「`{}` は依存駆動計算ユニット…`return` を使用して明示的に値を返す」；`spawn { return c }` はタスク結果を返す | `return` は**この `{}`** に値を返す                 |

RFC-010 に従えば、`if n <= 1 { return 1 }` の波括弧は計算ユニットであり、`return 1`
はそれに値 1 を与えるため、`if`
文の値は破棄され、次の行が必ず実行される——**fib は無限再帰**になる。RFC-007 によれば正しい。

### 根本原因：`return` 一語の二職

- **RFC-007 は「関数の退出」を表現するために使用**——制御フローの概念
- **RFC-010 は「このブロックの値」を表現するために使用**——評価の概念

制御フローキーワードで評価を表現することは範疇錯誤（category
error）である。一語で二職を担うと、どのように調整してもどちらかが犠牲になる。

### 下流ドキュメントの誤った拡大解釈

`docs/src/reference/language-spec/syntax.md` は RFC-010 の「`{}`
ブロック」を**すべての波括弧**に拡大した：

- §2.9：「`{}` 内の `return` は**常に内容を上位スコープに返す**」（「統一セマンティクス：すべての
  `{}` ブロック」とも称す）
- §3.3：「`return` は**コードブロックから値を返す**ために使用される」

一方、RFC-010 の原文で定義されているのは**三種類の値を持つブロック**（`= {}` / `spawn {}` /
`unsafe {}`）であり、**通篇で `if` / `while` / `for` / `match` の波括弧には触れていない**。

### 実装の現状

| 振る舞い                               | 現状                                   |
| -------------------------------------- | -------------------------------------- |
| `if n == 0 { return 7 } … return 8`    | 関数退出（`h(0) = 7`）                 |
| `f = { n + 1 }`                        | 末尾式が利用可能（`5` を返す）         |
| `x = { y = 5; y }`（生ブロック末尾式） | `E3006` 変数が未解析（#343 を参照）    |
| `f: () -> Int = { if c {5} else {6} }` | `void` を返し、末尾式が破棄（#344）    |
| `f: () -> Int = { "s" }`               | 静的にコンパイルを通過（#345 を参照）  |
| `x = if c { 19 }`（`else` なし）       | `19`（`Void` であるべき、#346 を参照） |
| `v = unsafe { 42 }`                    | `void`（#347 を参照）                  |
| `y = if c { 111 } else { 222 }`        | 利用可能（`if` を式として使用）        |

はかつて「末尾式はもはや暗黙的に返されない」と主張していたが、そのケースを網羅していなかったため、テストは失敗しなかった。このファイルは
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx` に置き換えられた。

## 提案

### 三つの規則

```
① ブロックの値 = 末尾式（唯一の出口）
   代入文の値は Void；空ブロック {} の値は Void
② return : (T) -> Never
   非局所的退出：最も近い関数の境界を退出する
③ if に else なし → Void
```

**この三つで「早期リターン」を十分に推論でき、`return` が関数を特称する追加規則は不要である。**

### 規則 ①：ブロックの値

ブロックの**最後の文/式**がブロックの値である（末尾式）。これは**「末尾式がなければ Void」ではない**——非空ブロックは常に末尾式を持ち（最後の文自体が末尾式である）、空ブロック
`{}` の値は `Void` である。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 代入を末尾にすると → ブロックの値は Void
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Void を望むなら明示的に書く
c = {
    log(x)
    Void                 // 明示的な Void
}
```

**設計判断基準（機構と保護の分離）**：

- **言語規則は機構のみを提供する**：最後の文がブロックの値であり、規則は唯一で曖昧さがない
- **保護は型検査が提供する**：関数が `-> Int` を宣言し末尾式の型が一致しない場合 → コンパイルエラー
- **言語は「意図の誤り」を防がない**：末尾式の型がたまたま戻り型と一致するが意味が本意でない場合、それは作者の疏忽であり、言語には判断できない。**意図の誤り防止は言語規則に依らない。**
- **戻りたくない場合は明示的に `Void` と書く**

これは RFC-010 の「`= { ... }` は `return` を使う必要があり、さもなくば `Void`
を返す」を置き換え、その設計理由「明示的な `return`
が必要であり『最後の式が戻り値かどうか』の曖昧さを解消する」も置き換える。

### 規則 ②：`return` は非局所的退出

`return` の型は `Never` である（零構築子、居住可能な値がない）。そのセマンティクス：

- **最も近い関数の境界を退出**し、値を呼び出し元に渡す
- **すべてのブロックを貫通する**——（あれば）`if` / `while` / `for` / `match` / 生ブロック / `spawn`
  / `unsafe`

`return` はブロックに「値を返さない」。`{ return n }` をブロックとして見ると、その値は
`n`（末尾式規則）、**型 `Never`** である；同時に `return`
の作用は関数を退出させることである。**二つは同時に成立する。**

### 規則 ③：`if` に `else` がない

```yaoxiang
x = if c { 19 }        // else なし
```

条件が偽のとき評価可能な分岐がないため、`Void` を取る。したがってこの `if` の値型は `Void`
である（あるいは `Void` でない位置には使用できない）。

値が必要な場合は明示的に両分岐を補う：

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` は共存の技術的基盤

`Never <: T` は任意の型 `T` について成立する（爆発原理、言語仕様 §型システム を参照）。したがって：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → この if の値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体 `{ return n }` の値は `Never` である
- この `if` の唯一の分岐が `Never` ⇒ `if` の値は `Never` である
- `Never`
  型の文は**シーケンスがここで停止する**ことを意味する——後続の文は「順次実行される次の一行」ではない
- 一方 `Never` は任意の型に縮退可能（爆発原理）であるため、ブロック全体が `-> Int` を満たす

**「早期リターン」はここから自然に導かれる**：`Never`
によるシーケンス停止 + 爆発原理による縮退可能性。

## 詳細設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block)：
  空ブロック              → Void
  { ...; e }              → 型(e)
  { ...; s }（s は文）    → Void          // 代入の値は Void
```

### `return` の型規則

```
return e : Never        where e : T

// Never <: T' は任意の T' について成立するため、return は任意の戻り型の位置に出現できる
```

**`return` の合法性を制約する追加規則は不要**——爆発原理がすでに網羅している。これにより「`return` が
`X` を返す関数に出現できるか」のような問題は消える。

### 多分岐の結合

```
join(A, B)：
  A : Never のとき  → B
  B : Never のとき  → A
  それ以外          → A と B が互換（同一型または共通の到達可能な上界）であることを要求
```

`if` / `match` の多分岐は `join` で結合される。`return` を含む分岐は型が `Never`
であるため結合に参加しない。

### RFC-007 との一貫性

RFC-007 の例は**完全に本 RFC に適合し**、改訂は不要：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never 分岐、join で無視される
    return n * factorial(n - 1)     // 関数退出
}
```

「早期リターン」は特例ではなく、規則 ① ② と爆発原理の**帰結**である。

### RFC-010 との相違と改訂要求

RFC-010 は三箇所の改訂が必要（正誤表方式、「下流ドキュメントの改訂要求」を参照）：

| RFC-010 の条項                                                         | 改訂後                                                  |
| ---------------------------------------------------------------------- | ------------------------------------------------------- |
| 「`= { ... }` は `return` を使う必要があり、さもなくば `Void` を返す」 | ブロックの値 = 末尾式；空ブロック → `Void`              |
| 設計理由「明示的な `return` で末尾式の曖昧さを解消」                   | 廃止——末尾式は曖昧さを生まず、`return` はそれを妨げない |
| 三箇所の `return c` / `return SqliteDb` の例                           | 末尾式に変更（`spawn` / `unsafe` の値出口を統一）       |

**RFC-010 の核心設計（`{}` を依存駆動計算ユニットとする）は変わらず**、値出口が `return`
から末尾式に変わるだけである。

### 視点の統一（設計原則）

`if` / `while`
の波括弧は**命令型の制御体であると同時に宣言型の評価ユニットでもある**——これは**視点の差であり、二つの言語構造ではない**。したがって：

- **言語レベルで「制御流体」と「評価ユニット」を二分しない**
- すべてのブロックが同じ評価規則（規則 ①）を共有する
- `return` は唯一の例外機構であり、その例外性は `Never` の型論的性質に由来し、構文の特例ではない

これにより宣言型と Python 式の書き方が自然に共存する：

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }   // ⚠️ 末尾式出口はまだ未実装、#365 を参照；現状は `spawn { return fetch("a") }` と書く必要がある
```

## トレードオフ

### 利点

- **RFC の矛盾を解消**：RFC-007 と RFC-010 は矛盾関係から帰結関係に変わり、どちらかを犠牲にする必要がない
- **規則数が最少**：三つの規則 + 一つの型論的性質（爆発原理）、特例なし
- **`return` の意味が唯一**：関数を退出する。「ブロック値 / 関数値」間で帰属を判断する必要がなくなる
- **視点の統一**：命令型と宣言型が共存し、言語レベルで二分しない
- **成熟した言語と一致**：Rust もまた「末尾式 + `return : !`」で二つの機構を共存させている
- **新構文ゼロ**：キーワードを追加せず、parser の構文規則を変更しない

### 欠点

- **末尾式がそのまま値になることに「誤った戻り」のリスクがある**：最終行を削除し忘れたとき戻り値が静かに変わる
  - 緩和：型検査が型不一致を遮断する；言語は意図誤り防止を約束しない（設計判断基準を参照）
- **RFC-010 に正誤表が必要**：承認済みドキュメントの例を書き換える必要がある
- **生ブロックの末尾式は未実装**：現在はコンパイラの内部エラー（本設計とは独立）
- **文の終端との相互作用を明確にする必要**：改行終端の末尾式が依然としてブロックの値であるか（オープン問題を参照）

## 代替案

### 案 A：`return` は二職を保持し、所在ブロックの型でディスパッチする

関数本体 `= {}` 内の `return` は関数に帰属；`spawn {}` / `unsafe {}` 内ではブロックに帰属；`if {}`
/ 生ブロック内ではどこに？

**否决理由**：`if`
の帰属は裁定不能——これがまさに元の矛盾である。さらにユーザーが「どのブロックが誰に帰属するか」を記憶する必要があり、原則的根拠がない（なぜ
`if` は関数に帰属し、生ブロックは自分に帰属するのか）。

### 案 B：厳格なブロックリターン（`return` は常に現在のブロックに帰属）

**否决理由**：**機能が欠如**。`return`
はネストされたブロックから関数を早期退出できず、ガード節（`if err { return }`）は完全に書けず、関数を階層的にネストされた式として書くしかない。

### 案 C：ブロックの値に新しいキーワードを使用（`give x` / `yield x`）

**否决理由**：RFC-036 の**構文変更ゼロ**原則に違反する（新しいキーワードを追加する必要がある）、さらにユーザーは二つの概念（`return`
退出 + `give` 評価）を学ぶ必要がある。末尾式案では新概念ゼロである。

### 案 D：RFC-010 をそのまま保持（明示的な `return` が必須）

**否决理由**：RFC-007 との矛盾は调和不能（動機を参照）。さらに実測された実装はすでに末尾式のパスに進んでいる。

を返す」という一文は本 RFC と矛盾し、すでに正誤表方式で改訂済み（RFC-007 の関数の形式的定義は変更なし）——上表の最終行を参照。

## オープン問題

      `(`/`[`
      は決してマージされない」などの規則と併せて確認が必要）——実測済み：改行終端の末尾式（行頭 `(` /

## 付録A：実測エビデンス

| コード                                            | 実測                            |
| ------------------------------------------------- | ------------------------------- |

## 付録B：設計決定記録

| 決定事項                | 決定                                                                   | 理由                                           | 日付       |
| ----------------------- | ---------------------------------------------------------------------- | ---------------------------------------------- | ---------- |
| `return` セマンティクス | 関数退出、型 `Never`；ブロックに値を返さない                           | 一語の二職という範疇錯誤を解消                 | 2026-09-15 |
| ブロックの値出口        | 末尾式（唯一の出口）                                                   | 規則数が最少；Rust と一致                      | 2026-09-15 |
| 末尾式なし              | 存在しない（非空ブロックは常に末尾式を持つ；空ブロック `{}` → `Void`） | `Void` を望むなら明示的に `Void` と書く        | 2026-09-15 |
| 代入の値                | `Void`                                                                 | 代入は文であり値生成ではない                   | 2026-09-15 |
| `if` に `else` なし     | `Void`                                                                 | 条件偽のとき評価可能な分岐がない               | 2026-09-15 |
| 機構と保護の分業        | 言語は機構を提供、型検査は保護を提供                                   | 言語は「意図の誤り」を防ぐことを約束しない     | 2026-09-15 |
| 制御流体 / 評価ユニット | 言語レベルで二分せず、視点の差とみなす                                 | 命令型と宣言型が共存し、原則なき特例を回避     | 2026-09-15 |
| 誤った例の扱い          | 削除し、正誤表ブロックに保持しない                                     | 利用可能に見える誤コードを保持すると誤解を招く | 2026-09-15 |

## 付録C：用語集

| 用語             | 定義                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| 末尾式           | ブロック内で最後に値を生成する式、ブロックの値そのもの                         |
| 非局所的退出     | 外側の評価ユニットを貫通し、関数の境界に直接作用する制御フロー転送（`return`） |
| 爆発原理         | `Never <: T` は任意の `T` について成立し、`Never` を任意の型に縮退可能にする   |
| 値を持つブロック | `= {}` / `spawn {}` / `unsafe {}`——値出口は末尾式                              |
| join             | 多分岐結合規則、`Never` 分岐は結合に参加しない                                 |

## 付録D：関数 / ブロック値曖昧さ裁定（裁定 C）

> **正誤表（2026-09-19）：裁定 C の無注釈行はすでに覆された。**
>
> ユーザー裁定：**「内容が型を決定」（読み方 B）に統一**、理由は同じ原則が辞書とブロックに貫かれるべきだから：
>
> > B に統一すれば、`{}` は自然に定位置を占める。
>
> **現行規則**
>
> | 状況                        | 結果             | 根拠                                |
> | --------------------------- | ---------------- | ----------------------------------- |
> | `value` が `Lambda`（`=>`） | 関数             | `=>` は明示的な関数構築子           |
> | 注釈が `Fn`                 | 関数             | 関数型を宣言した                    |
> | 注釈が `Fn` 以外の型        | ブロック値       | 注釈がそのまま型（`x: Int = {..}`） |
> | **無注釈**                  | **内容から推論** | **型は内容により決定**              |
>
> 重要な変化：`f = { 5 }` は現在**値** `5`（`Int`）であり、もはや関数ではない。
>
> ```yaoxiang
> x: Int = { y = 5; y }      // 块值：x = 5（注解非 Fn）
> f: () -> Int = { 5 }       // 函数：f() = 5（注解是 Fn）
> f = { 5 }                  // 值：f = 5（无注解 → 内容推断）
> f = {}                     // 值：f = Void（空块）
> b = () => 5                // 函数：显式 lambda
> d = { "a": 1 }             // 值：Dict（内容自描述）
> ```
>
> **なぜ裁定 C を覆したか**
>
> 裁定 C の原論拠（「無注釈時はデフォルトで関数」）は**実装上の便宜志向**：
>
> 1. ~~既存コードは変更不要~~——移行コストは支払可能（211 ファイル、704 箇所）、意味的依据ではない
> 2. ~~関数定義は高頻度、ブロック値は低頻度~~——頻度は型規則ではない
> 3. ~~RFC-007 は承認済みで、改訂は本 RFC 改訂より高コスト~~——誤ったものは「コストが高い」からといって正しくはならない
>
> 真の問題は**不一致**である：`f = { 5 }` は関数だが、`d = { "a": 1 }` は辞書——同じ `{`
> が同じ無注釈位置で異なる範疇のものを与える。裁定 C が自認する「コスト」とはまさにこの亀裂：
>
> > 「`f = { 5 }` で `f` は関数であり `5` ではない……『波括弧は値である』という直感に反する」。
>
> 現行規則は亀裂を解消する：**型は内容により決定され**、注釈の有無を見ない。注釈は依然として型を宣言するが（`f: () -> Int`）、「注釈の欠落」によってデフォルト値を課すことはない。
>
> **`{}` の落位**
>
> B に統一した後 `{}` は自然に定まる：`Dict` 文法は少なくとも一つのキーを要求し、`{}`
> は依拠すべき内容がないため、ブロック構造の零形態を取る → 空ブロック、値 `Void`。空辞書は
> `dict.new()` を使用。詳細は spec [§2.9.1](../.../reference/language-spec/syntax.md) を参照。
>
> **不変の部分**
>
> 付録 D の後続二条（「注釈は取値を決定しない」、「`callable_parts()`
> はもはや無条件にブロックを呑まない」）は依然として有効；後者は現在
> `Expr::block_binding_is_function`
> によって実装されているが、その無注釈分は上表に従ってすでに変更されている。

### 問題（歴史的背景）

`name = { ... }` は同時に二件の承認済み RFC によって異なるものとして定義されている：

| RFC                 | 定義                                                  |
| ------------------- | ----------------------------------------------------- |
| RFC-007（関数構文） | 関数。「無パラメータ最簡」`name = { return ... }`     |
| RFC-010 / 010a      | ブロック値。「`= {}` は値を持つブロック、値は末尾式」 |

同一の構文位置に二組のセマンティクスがあり、実装上 `callable_parts()`
はブロックを 0 引数関数として登録し、一方 `generate_block_ir`
はブロック値として取り扱う——二層の理解が一致していない。

### 原裁定：注釈優先、デフォルトは関数（**すでに廃止**）

| 状況                        | 結果           | 根拠                                    |
| --------------------------- | -------------- | --------------------------------------- |
| `value` が `Lambda`（`=>`） | 関数           | `=>` は明示的な関数構築子               |
| 注釈が `Fn`                 | 関数           | 関数型を宣言した                        |
| 注釈が `Fn` 以外の型        | **ブロック値** | 注釈がそのまま型（`x: Int = {..}`）     |
| 無注釈                      | **関数**       | デフォルト；RFC-007「無パラメータ最簡」 |

**要点：ブロック値のセマンティクスは新構文に依らない。** `{ ... }`
を即座に評価したい場合は対象型を記述する：

```yaoxiang
x: Int = { y = 5; y }      # 块值：x = 5（注解非 Fn）
f: () -> Int = { 5 }       # 函数：f() = 5（注解是 Fn）
f = { 5 }                  # 函数：f() = 5（无注解，默认函数）  # ← 此行已废止
b = () => 5                # 函数：表达体 lambda
```

### 原論拠（**すでに失效**）

注釈は**そもそも型を宣言する**：`x: Int = ...` は `x` が `Int` であることを示し、`{...}` は `Int`
値である； `f: () -> Int = ...` は `f` が関数であることを示し、`{...}`
は関数本体である。**型指向であり、新しい規則の発明ではない。**

無注釈時はデフォルトで関数、理由は：

1. 既存コードは変更不要（リポジトリ内の無注釈の `name = { ` バインディングは合計 203 箇所、すべて
   `main`）
2. 関数定義は高頻度、ブロック値は低頻度
3. RFC-007 は承認済み、改訂は本 RFC 改訂より高コスト

### コスト（既知で受容）

`f = { 5 }` で `f` は**関数**であって `5`
ではない。これは「波括弧は値である」という直感に反する——しかしこれはまさに RFC-007 が承認した定義であり、**注釈が脱出出口である**：`f: Int = { 5 }`
と書けば値を得る。

### 裁定が同時に修正した実装上の欠陥

1. **注釈は取値を決定しない**（根本原因 1）：`generate_function_ir` など三箇所で
   `return_type != Void` を末尾式の取値门槛として使用しており、無注釈の `f = { 5 }`
   の末尾式が静かに破棄され、 `Void`
   が返される。注釈は*検査*の要否を決定するだけで、*評価*の要否を決定しない。
2. **`callable_parts()` はもはや無条件にブロックを呑まない**：分流は
   `Expr::block_binding_is_function(注釈, 値)` によって統一的に判定される。
