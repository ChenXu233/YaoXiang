# RFC-010a: 末尾式評価と return セマンティクス

> **参考**:
>
> - [RFC-010: 統一型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   依存駆動計算ユニット
> - [RFC-007: 関数定義構文統一案](./007-function-syntax-unification.md)
>   — コードブロック返却規則、早期 return
> - [RFC-038: 文終端と改行規則](038-statement-termination.md) — 文と式の改行挙動
> - [言語仕様 §型システム](/reference/language-spec/type-system.md) — `Never` の爆発原理

## 概要

`return` とブロック評価のセマンティクスを統一し、RFC-007 と RFC-010 の間の表現衝突を解消する。

**三つの自己無撞着な規則**を提案する：ブロックの値は末尾式と等しい（唯一の出口）；`return` は型
`Never` を持つ**非局所脱出**（関数を脱出し、ブロックに「値を返さない」）；`if` に `else`
がない場合は `Void`。

`return` とブロック評価は**言語レベルで二分されない**——`{ return n }` はブロックとして値 `n`（型
`Never`）を持ち、同時に `return`
の作用は関数を脱出する。二つの事象は**爆発原理**（`Never <: T`）により共存する。RFC-007 の「早期 return」と RFC-010 の「ブロックは値を持つ」はこの三つの規則の帰結であり、矛盾する特例ではない。

新しい構文も新しいキーワードもなし。

## 動機

### 表現衝突

playground のフィボナッチ例がセマンティクスの分岐を露呈した：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // この return は「if のもの」か「関数のもの」か？
  }
  return fib(n - 1) + fib(n - 2)
}
```

二つの受領済 RFC が**逆方向**の導出を与えている：

| RFC                   | 表現                                                                                                 | 導出されるセマンティクス                            |
| --------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **RFC-007**（受領済） | `factorial` を例に、タイトルを**「早期 return：`return` を使う」**と記述：`if n <= 1 { return 1 }`   | `return` は `if` と関数本体を貫通し、**関数に戻る** |
| **RFC-010**（受領済） | 「`{}` は依存駆動計算ユニット…`return` で明示的に値を返す」；`spawn { return c }` はタスク結果を返す | `return` は**この `{}`** に値を返す                 |

RFC-010 に従えば、`if n <= 1 { return 1 }` の波括弧は計算ユニットで、`return 1`
がその値として 1 を返すと、 `if`
文の値は破棄され、次の行が必ず実行される——**fib は無限再帰する**。RFC-007 ならば正しい。

### 根本原因：`return` という語の二重職務

- **RFC-007 は「関数を脱出する」ために使う**——制御フローの概念
- **RFC-010 は「このブロックの値はこれである」ために使う**——評価の概念

制御フローのキーワードで評価を表現することは範疇錯誤（category
error）である。一語が二つの職務を担っている以上、如何に調整しても片側が犠牲になる。

### 下流ドキュメントの誤った拡大解釈

`docs/src/reference/language-spec/syntax.md` は RFC-010 の「`{}`
ブロック」を**すべての波括弧**に拡大している：

- §2.9：「`{}` 内の `return`
  は**常に内容を上位スコープに返す**」（さらに「統一セマンティクス：すべての `{}`
  ブロック」と称する）
- §3.3：「`return` は**コードブロックから値を返す**ために使う」

しかし RFC-010 の原文が定義するのは**三種の値を持つブロック**（`= {}` / `spawn {}` /
`unsafe {}`）であり、**`if` / `while` / `for` / `match` の波括弧には一切触れていない**。

### 実装の現状

| 挙動                                   | 現状                                 |
| -------------------------------------- | ------------------------------------ |
| `if n == 0 { return 7 } … return 8`    | 関数脱出（`h(0) = 7`）               |
| `f = { n + 1 }`                        | 末尾式が機能する（`5` を返す）       |
| `x = { y = 5; y }`（生ブロック末尾式） | `E3006` 変数未解決（#343 参照）      |
| `f: () -> Int = { if c {5} else {6} }` | `void` を返す、末尾式が破棄（#344）  |
| `f: () -> Int = { "s" }`               | 静的にコンパイル通過（#345 参照）    |
| `x = if c { 19 }`（`else` なし）       | `19`（`Void` であるべき、#346 参照） |
| `v = unsafe { 42 }`                    | `void`（#347 参照）                  |
| `y = if c { 111 } else { 222 }`        | 機能する（`if` が式として）          |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx`
はかつて「末尾式はもはや暗黙に return されない」と主張していたが、そのケースをカバーしておらず、テストが赤くならなかった。同ファイルは
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx` に置き換えられた。

## 提案

### 三つの規則

```
① ブロックの値 = 末尾式（唯一の出口）
   代入文の値は Void；空ブロック {} の値は Void
② return : (T) -> Never
   非局所脱出：最も近い関数境界から脱出する
③ if に else なし → Void
```

**この三つで「早期 return」が導出可能であり、`return` が関数専用であるとする追加規則は不要。**

### 規則 ①：ブロックの値

ブロックの**最後の文/式**がそのままブロックの値となる（末尾式）。これは「末尾式がなければ Void」ではない——非空ブロックは常に末尾式を持つ（末尾の文自体が末尾式である）、空ブロック
`{}` の値は `Void` である。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 代入を末尾式にすると → ブロックの値は Void
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Void を望むなら明示する
c = {
    log(x)
    Void                 // 明示的な Void
}
```

**設計判断（機構と保護の分離）**：

- **言語規則は機構のみ与える**：末尾の文がブロックの値、規則は唯一で曖昧さなし
- **保護は型検査が提供する**：関数宣言 `-> Int` に対し末尾式の型が一致しない → コンパイルエラー
- **言語は「意図の誤り」を防がない**：末尾式の型がたまたま返却型と一致しても意味が意図と異なれば、それは作者の不注意であり、言語には判定できない。**意図の誤りは言語規則で防がない。**
- **返したくないなら明示的に `Void` と書く**

これは RFC-010 の「`= { ... }` は必ず `return` を使うこと、さもなければ `Void`
を返す」、およびその設計理由「末尾式が戻り値か否かの曖昧さを解消するために明示的な `return`
が必要」を置き換える。

### 規則 ②：`return` は非局所脱出

`return` の型は `Never`（ゼロ構築子、居住可能な値なし）。そのセマンティクス：

- **最も近い関数境界を脱出**し、値を呼び出し元に渡す
- **すべてのブロックを貫通**する——（存在すれば）`if` / `while` / `for` / `match` / 生ブロック /
  `spawn` / `unsafe`

`return` は「ブロックに値を返さない」。`{ return n }` はブロックとして値 `n`（末尾式規則）、**型
`Never`**；同時に `return` の作用は関数を脱出する。**二つの事象が同時に成立する。**

### 規則 ③：`if` に `else` がない場合

```yaoxiang
x = if c { 19 }        // else なし
```

条件が偽のとき評価すべき分岐がないため、`Void` を取る。したがってこの `if` の値型は
`Void`（あるいは非 `Void` の位置では使用不可）。

値が必要なときは明示的に二分岐を揃える：

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` は共存の技術的基盤

`Never <: T` は任意の型 `T` に対して成立する（爆発原理、言語仕様 §型システム 参照）。したがって：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → この if の値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体 `{ return n }` の値は `Never`
- この `if` の唯一分岐が `Never` ⇒ `if` の値は `Never`
- `Never`
  型の文は**シーケンスがここで停止する**ことを意味する——後続の文は「順次実行される次行」ではない
- そして `Never` は任意の型に還元可能（爆発原理）なので、ブロック全体は `-> Int` を満たす

**「早期 return」はここから自然に導かれる**：`Never` がシーケンスを停止 + 爆発原理による還元。

## 詳細設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block)：
  空ブロック                    → Void
  { ...; e }              → 型(e)
  { ...; s }（s は文）     → Void          // 代入の値は Void
```

### `return` の型規則

```
return e : Never        where e : T

// Never <: T' は任意の T' で成立するため、return は任意の返却型の位置に現れ得る
```

**`return` の正当性を制約する追加規則は不要**——爆発原理がすでにカバーする。これにより「`return` は
`X` を返す関数に書けるか」这种問いは消滅する。

### 多分岐の結合

```
join(A, B)：
  A : Never なら  → B
  B : Never なら  → A
  それ以外        → A、B が互換（同一型または到達可能な共通上界）を要求
```

`if` / `match` の多分岐は `join` で結合する。`return` を含む分岐は型 `Never`
のため結合に参加しない。

### RFC-007 との一貫性

RFC-007 の例は**完全に本 RFC に従い**、改訂不要：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never 分岐、join で無視される
    return n * factorial(n - 1)     // 関数脱出
}
```

「早期 return」は特例ではなく、規則 ① ② と爆発原理の**帰結**である。

### RFC-010 との差異および改訂要求

RFC-010 は三か所改訂が必要（正誤表の形で、「下流ドキュメントへの改訂要求」参照）：

| RFC-010 条項                                                           | 改訂後                                                  |
| ---------------------------------------------------------------------- | ------------------------------------------------------- |
| 「`= { ... }` は必ず `return` を使うこと、さもなければ `Void` を返す」 | ブロックの値 = 末尾式；空ブロック → `Void`              |
| 設計理由「末尾式の曖昧さを解消するために明示的な `return` が必要」     | 廃止——末尾式は曖昧さを生まず、`return` はそれを妨げない |
| 三か所の `return c` / `return SqliteDb` の例                           | 末尾式に変更（`spawn` / `unsafe` の値出口を統一）       |

**RFC-010 の核心設計（`{}` を依存駆動計算ユニットとする）は不変**、値出口が `return`
から末尾式に変わるのみ。

### 視点の統一（設計原則）

`if` / `while`
の波括弧は**命令的制御本体であると同時に宣言的評価ユニットでもある**——これは**視点の差であり、二種の言語構造ではない**。したがって：

- **言語レベルで「制御流体」と「評価ユニット」を二分しない**
- すべてのブロックは同一の評価規則（規則 ①）を共有する
- `return` は唯一の例外機構であり、その例外性は `Never`
  の型論的性質から来るもので、構文上の特例ではない

これにより宣言的と Python 流の書き方が自然に共存する：

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## トレードオフ

### 利点

- **RFC 間の衝突を解消**：RFC-007 と RFC-010 が矛盾関係から帰結関係に変わり、いずれも犠牲にならない
- **規則数が最少**：三つの規則 + 一つの型論的性質（爆発原理）、特例なし
- **`return` の意味が一意**：関数を脱出する。「ブロック値 / 関数値」の間で帰属を判断する必要なし
- **視点の統一**：命令的と宣言的が共存し、言語レベルで二分されない
- **成熟した言語と一致**：Rust も同様に「末尾式 + `return : !`」で二つの機構を共存させる
- **新構文ゼロ**：キーワードを追加せず、parser の構文規則も変えない

### 欠点

- **末尾式がそのまま値になることによる「誤った return」のリスク**：末尾行を消し忘れたとき戻り値が静かに変わる
  - 緩和策：型検査が型の不一致を捕捉；言語は意図の誤りを防がないと約束する（設計判断参照）
- **RFC-010 に正誤表が必要**：受領済ドキュメントの例を書き換える必要
- **生ブロック末尾式が未実装**：現在はコンパイラの内部エラー（本設計とは独立）
- **文終端との相互作用を明確化する必要**：改行で終端する末尾式もブロックの値となるか（オープン問題参照）

## 代替案

### 案 A：`return` に二重職務を残し、属するブロック型でディスパッチ

関数本体 `= {}` の `return` は関数に帰属；`spawn {}` / `unsafe {}` のはブロックに帰属；`if {}`
/ 生ブロックのは？

**却下理由**：`if`
の帰属を決定できない——これがまさに元の衝突である。さらにユーザに「どのブロックが誰のものか」を記憶させる必要があり、原則的根拠がない（なぜ
`if` は関数で生ブロックは自分なのか）。

### 案 B：厳格なブロック返却（`return` は常に現在のブロックに帰属）

**却下理由**：**機能欠落**。`return`
はネストされたブロックから関数を早期脱出できなくなり、ガード節（`if err { return }`）が一切書けなくなる。関数を何重にもネストされた式として書くしかなくなる。

### 案 C：ブロック値に新キーワード（`give x` / `yield x`）

**却下理由**：RFC-036 の**構文変更ゼロ**原則に違反（新キーワードが必要）、かつユーザが二つの概念（`return`
で脱出 + `give` で評価）を学ぶ必要。末尾式案は新概念ゼロ。

### 案 D：RFC-010 の原状維持（明示的な `return` を必須）

**却下理由**：RFC-007 との衝突は調和不能（動機参照）。さらに実測された実装はすでに末尾式経路を歩んでいる。

| `h: (n)->Int = { if n==0 { return 7 } return 8 }` | `h(0)=7`, `h(1)=8`                   |
| `f: (n)->Int = { n + 1 }`                         | `5`（末尾式が機能する）              |
| `f: ()->Int = { if c {5} else {6} }`              | `void`（`5` であるべき、#344 参照）  |
| `f: ()->Int = if c {5} else {6}`                  | `5`                                  |
| `f: ()->Int = { match ... }`                      | 正しい                               |
| `f: ()->Int = { while ...; i }`                   | 正しい                               |
| `{ y = 5; y }` を束縛式として使用                 | `E3006`（#343 参照）                 |
| `f: ()->Int = { "s" }`                            | 静的に通過（#345 参照）              |
| `x = if c { 19 }`（`else` なし）                  | `19`（`Void` であるべき、#346 参照） |
| `v = unsafe { 42 }`                               | `void`（#347 参照）                  |
| `y = if c { 111 } else { 222 }`                   | `111`                                |
| `while { if i==2 { return 42 } }`                 | `42`（ループを貫通）                 |
| ネスト `{ { return 5 } return 1 }`                | `5`（生ブロックを貫通）              |

## 付録 D：関数 / ブロック値曖昧さの裁定（裁定 C）

### 問題

`name = { ... }` は二つの受領済 RFC で異なるものとして定義されている：

| RFC                 | 定義                                                  |
| ------------------- | ----------------------------------------------------- |
| RFC-007（関数構文） | 関数。「ゼロ引数最簡」`name = { return ... }`         |
| RFC-010 / 010a      | ブロック値。「`= {}` は値を持つブロック、値は末尾式」 |

同一構文位置に二つのセマンティクスがあり、実装上 `callable_parts()`
がブロックを 0 引数関数として登録し、`generate_block_ir`
がブロック値として取得する——二層の理解に矛盾がある。

### 裁定：アノテーション優先、デフォルトは関数

| 状況                        | 結果           | 根拠                                          |
| --------------------------- | -------------- | --------------------------------------------- |
| `value` が `Lambda`（`=>`） | 関数           | `=>` は明示的な関数構築子                     |
| アノテーションが `Fn`       | 関数           | 関数型を宣言している                          |
| アノテーションが非 `Fn` 型  | **ブロック値** | アノテーションは型そのもの（`x: Int = {..}`） |
| アノテーションなし          | **関数**       | デフォルト；RFC-007「ゼロ引数最簡」           |

**要点：ブロック値セマンティクスは新構文に依存しない。** `{ ... }`
をその場で評価したいなら目標型を書く：

```yaoxiang
x: Int = { y = 5; y }      # ブロック値：x = 5（アノテーションが非 Fn）
f: () -> Int = { 5 }       # 関数：f() = 5（アノテーションが Fn）
f = { 5 }                  # 関数：f() = 5（アノテーションなし、デフォルト関数）
b = () => 5                # 関数：式本体ラムダ
```

### 根拠

アノテーションは**そもそも型を宣言している**：`x: Int = ...` は `x` が `Int`
であることを述べており、`{...}` は `Int` 値である； `f: () -> Int = ...` は `f`
が関数であることを述べており、`{...}` は関数本体である。**型主導であり、新規則の発明ではない。**

アノテーションなしのデフォルトが関数である理由：

1. 既存コードへの変更ゼロ（リポジトリ内アノテーションなしの `name = { ` 束縛は計 203 か所、すべて
   `main`）
2. 関数定義が高頻度、ブロック値は低頻度
3. RFC-007 は受領済、変更コストはこちらの方が高い

### 既知かつ受容されるコスト

`f = { 5 }` において `f` は**関数**であり `5`
ではない。これは「波括弧は値である」という直感に反する——しかしこれは RFC-007 受領済の定義であり、**アノテーションが脱出口である**：`f: Int = { 5 }`
と書けば値が得られる。

### 同時に修正される実装欠陥

1. **アノテーションが値の取得を決定すべきではない（根本原因 1）**：`generate_function_ir` 等三か所で
   `return_type != Void` を末尾式の値取得の閾値として使用しており、アノテーションなしの `f = { 5 }`
   の末尾式が静かに破棄され `Void`
   を返す原因となっている。アノテーションは検査の要否を決定するだけで、値取得の必要性を決定するわけではない。
2. **`callable_parts()` は無条件にブロックを飲み込まない**：分岐は
   `Expr::block_binding_is_function(アノテーション, 値)` で統一的に判定する。
