# RFC-010a: 末尾式評価とreturnのセマンティクス

> **参考**:
>
> - [RFC-010: 統合型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   依存駆動計算ユニット
> - [RFC-007: 関数定義構文統合方案](./007-function-syntax-unification.md) — コードブロックの返値ルール、早期リターン
> - [RFC-038: 文終端と改行ルール](038-statement-termination.md) — 文と式の改行動作
> - [言語仕様 §タイプシステム](../../../../reference/language-spec/type-system.md) — `Never` 爆発原理

## 概要

`return` とブロック評価のセマンティクスを統一し、RFC-007とRFC-010間の記述的矛盾を解消する。

**3つの自己整合ルール**を提案する：ブロックの値は末尾式に等しい（唯一の出入口）；`return` は型 `Never` の**非局所脱出**（関数から脱出、「ブロックに戻らない」）；`if` に`else`がない場合は`Void`を取る。

`return`とブロック評価は**言語レベルでは二分されない**—`{ return n }`はブロックとしてその値は`n`（型`Never`）であり、同時に`return`の作用は関数の終了である。2つのことは**爆発原理**（`Never <: T`）により共存する。RFC-007の「早期リターン」とRFC-010の「ブロックは値を持つ」はこの3ルールの帰結であり、矛盾した特例ではない。

新しい構文なし、新しいキーワードなし。

## 動機

### 記述的矛盾

playgroundのフィボナッチ例がセマンティクスの分岐を露呈した：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // このreturnは「ifの」か「関数の」か？
  }
  return fib(n - 1) + fib(n - 2)
}
```

2つの承認済みRFCが異なる**逆方向**の推論を示している：

| RFC                   | 記述                                                                                  | 推論されるセマンティクス                                  |
| --------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------- |
| **RFC-007**（承認済み） | `factorial`を例に、タイトルは**「早期リターン：returnを使用」**：`if n <= 1 { return 1 }`  | `return`は`if`と関数本体を貫通、**関数に戻る** |
| **RFC-010**（承認済み） | 「`{}`は依存駆動計算ユニット…`return`で明示的に値を返す」；`spawn { return c }`はタスク結果を返す | `return`は**この`{}`**に値を与える               |

RFC-010によれば、`if n <= 1 { return 1 }`の中括弧は計算ユニットであり、`return 1`がそれに与える値は1で、`if`文の値は捨てられ、次の行が必ず実行される—**fibは無限再帰する**。RFC-007によれば正しい。

### 根本原因：`return`の一語二役

- **RFC-007では「関数から脱出」を表す**——制御フロー概念
- **RFC-010では「このブロックの値はこれ」を表す**——評価概念

制御フローのキーワードで評価を表すのは範疇錯誤（category error）である。一語で二つの役割を担うと、どう調整してもどちらかが犠牲になる。

### 下流ドキュメントへの誤った拡大解釈

`docs/src/reference/language-spec/syntax.md`はRFC-010の「`{}`ブロック」を**すべての中括弧**に拡大解釈している：

- §2.9：「`{}`内の`return`は**常に内容を上一スコープに返す**」（「統一セマンティクス：すべての`{}`ブロック」と称）
- §3.3：「`return`は**コードブロックから値を返す**ために使用」

しかしRFC-010の原文が定義しているのは**3種類の値ブロック**（`= {}` / `spawn {}` / `unsafe {}`）であり、**`if` / `while` / `for` / `match`の中括弧には一切触れていない**。

### 実装現状

| 動作                                   | 現状                              |
| -------------------------------------- | --------------------------------- |
| `if n == 0 { return 7 } … return 8`    | 関数終了（`h(0) = 7`）            |
| `f = { n + 1 }`                        | 末尾式が使用可能（`5`を返す）          |
| `x = { y = 5; y }`（ベアブロック末尾式）     | `E3006` 変数が解決されない（#343参照）     |
| `f: () -> Int = { if c {5} else {6} }` | `void`を返す、末尾式が捨てられる（#344） |
| `f: () -> Int = { "s" }`               | コンパイルを静かに通過（#345参照）           |
| `x = if c { 19 }`（elseなし）         | `19`（`Void`であるべき、#346参照） |
| `v = unsafe { 42 }`                    | `void`（#347参照）                 |
| `y = if c { 111 } else { 222 }`        | 使用可能（`if`は式として機能）        |

## 提案

### 3つのルール

```
① ブロックの値 = 末尾式（唯一の出入口）
   代入文の値はVoid；空ブロック{}の値はVoid
② return : (T) -> Never
   非局所脱出：最も近い関数境界を脱出
③ if elseなし → Void
```

**これだけで「早期リターン」が導出される。`return`が関数を指すという追加ルールは不要。**

### ルール①：ブロックの値

ブロックの**最後の文/式**がブロックの値（末尾式）である。これは「末尾式がない場合はVoid」ではない—空でないブロックは必ず末尾式を持つ（最後の文自体がそうである）。空ブロック`{}`の値は`Void`。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 末尾式が代入 → ブロックの値はVoid
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Voidしたい場合は明示的に書く
c = {
    log(x)
    Void                 // 明示的なVoid
}
```

**設計判断基準（メカニズムと保護の分離）**：

- **言語ルールはメカニズムのみを提供**：末尾文がブロックの値、ルールは一意で曖昧さがない
- **保護は型チェックで提供**：関数宣言`-> Int`で末尾式の型が一致しない場合はコンパイルエラー
- **言語は「意図の誤り」を防がない**：末尾式の型が偶然返値型と一致しても意味が意図通りでなければ、それは作者の過誤であり言語では判断できない。**言語ルールで意図の誤りを防ぐことはできない。**
- **値を返したくない場合は明示的に`Void`を書く**

これはRFC-010の「`= { ... }`は必ず`return`を使用し否则返回`Void`」に代わり、その設計上の根拠「末尾式が返値かどうかの曖昧さを解消するには明示的な`return`が必要」も取代する。

### ルール②：`return`は非局所脱出

`return`の型は`Never`（零コンストラクタ、値を持てない）である。そのセマンティクス：

- **最も近い関数境界を脱出**し、値を呼び出し元に渡す
- **すべてのブロックを貫通**——（存在すれば）`if` / `while` / `for` / `match` / ベアブロック / `spawn` / `unsafe`

`return`は「ブロックに戻らない」。`{ return n }`はブロックとしてその値は`n`（末尾式ルール）であり、**型`Never`**である。同時に`return`の作用は関数の終了である。**2つのことが同時に成立する。**

### ルール③：`if`にelseがない場合

```yaoxiang
x = if c { 19 }        // elseなし
```

条件が偽の場合に評価可能な分支がなく、`Void`を取る。故にこの`if`の値の型は`Void`（または非`Void`位置では使用不可）。

値が必要な場合は明示的に2分支を補充する：

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never`は共存の技術的基盤

`Never <: T`は任意の型`T`に対して成立する（爆発原理、言語仕様§タイプシステム参照）。因而：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → そのifの値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体`{ return n }`の値は`Never`
- その`if`の唯一の分支が`Never` ⇒ `if`の値は`Never`
- `Never`型の文は**シーケンスがここで中断**することを意味する——次の文は「順序実行される次の一文」ではない
- `Never`は任意の型にrollable（爆発原理）ため、ブロック全体は`-> Int`を満たす

**「早期リターン」はここから自然に導出される**：`Never`がシーケンスを中断 + 爆発原理で任意の型にrollable。

## 詳細な設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block):
  空ブロック                  → Void
  { ...; e }                  → 型(e)
  { ...; s }（sは文）        → Void          // 代入の値はVoid
```

### `return`の型ルール

```
return e : Never        where e : T

// Never <: T'は任意のT'に対して成立するため、returnは任意の返値型の位置に現れることができる
```

**`return`の適法性を制約する追加ルールは不要**——爆発原理が既にカバーしている。これにより「`return`は返値`X`の関数内で使用できるか」というような質問が消える。

### 複数分支のマージ

```
join(A, B):
  A : Never であれば → B
  B : Never であれば → A
  それ以外          → A、Bの互換性が必要（同じ型または共通の上界に到達可能）
```

`if` / `match`の複数分支は`join`でマージする。`return`を含む分支は型が`Never`のためマージに参加しない。

### RFC-007との整合性

RFC-007の例は**本RFCに完全に準拠**しており、修正不要：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never分支、マージで無視される
    return n * factorial(n - 1)     // 関数終了
}
```

「早期リターン」は特例ではなく、ルール① ②と爆発原理の**帰結**である。

### RFC-010との差異と修正要件

RFC-010の定義は本RFCに従って修正済みであり、差異は以下の通り：

| RFC-010の原文                                   | 現行定義                                        |
| ------------------------------------------------ | ----------------------------------------------- |
| 「`= { ... }`は必ず`return`を使用し否则返回`Void`」 | ブロックの値 = 末尾式；空ブロック → `Void`                |
| 設計根拠「末尾式の曖昧さを解消するには明示的な`return`が必要」     | 成立しない——末尾式は曖昧さを生まない，`return`はそれを妨げない   |
| 3箇所の`return c` / `return SqliteDb`の例         | 末尾式構文に書き換え（`spawn` / `unsafe`の値出口を統一） |

**RFC-010の中核設計（`{}`は依存駆動計算ユニット）は変更なし**。値出口を`return`から末尾式に変更しただけである。

### 視点の統一（設計原則）

`if` / `while`の中括弧は**命令型制御体であると同時に宣言型計算ユニット**でもある——これは**視点の違いであり、2つの言語構成要素ではない**。因而：

- **言語レベルで「制御フロー体」と「計算ユニット」を二分しない**
- すべてのブロックは同一の計算ルールを共有（ルール①）
- `return`は唯一の例外メカニズムであり、その例外性は構文上の特例ではなく`Never`の型論的性質に由来する

これにより宣言型とPython的な書き方が自然に共存する：

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## トレードオフ

### 利点

- **RFC間の競合を解消**：RFC-007とRFC-010は矛盾から推論関係に変わり、どちらかを犠牲にする必要がない
- **最少ルール数**：3つのルール + 1つの型論的性質（爆発原理）、特例なし
- **`return`の意味が一意**：関数を脱出。「ブロック値 / 関数値」のどちらに帰属するかを判断する必要がない
- **視点の統一**：命令型と宣言型が共存し、言語レベルで二分しない
- **成熟した言語との整合性**：Rust同样是「末尾式 + `return : !`」で両メカニズムを共存させる
- **新構文ゼロ**：キーワードを追加せず、parserの構文ルールを変更しない

### 欠点

- **末尾式が値には「誤って返す」リスクがある**：末尾行を消し忘れたときに返値が静かに変わる
  - 緩和：型チェックが型の不一致を検出；言語は「意図の誤り」の防止を約束しない（設計判断基準参照）
- **下流ドキュメントの同期修正が必要**：承認済みドキュメントの例を書き換える必要がある
- **文終端との相互作用の明確化が必要**：改行で終端した末尾式がブロック値であり続けるかどうか（開放問題参照）

## 代替案

### 案A：`return`は二役を保持し、所在ブロックの種類で振り分け

関数本体`= {}`内の`return`は関数に従属；`spawn {}` / `unsafe {}`内は一切块に従属；`if {}` / ベアブロック内はどうする？

**否決理由**：`if`の帰属は裁定不能——これがまさに元の競合の原因である。「どのブロックが誰に従属するか」をユーザーに覚えてもらう必要があり、原則的な根拠がない（なぜ`if`は関数に従属でベアブロックは自分に従属なのか）。

### 案B：厳密なブロック返値（`return`は常に現在のブロックに従属）

**否決理由**：**機能が欠落**する。`return`はネストしたブロックから早期に関数を脱出できなくなり、guard clause（`if err { return }`）は一切書けなくなり、関数を层层ネストした式として書くしかない。

### 案C：ブロックの値に新しいキーワードを使用（`give x` / `yield x`）

**否決理由**：RFC-036の**ゼロ構文変更**原則に違反する（新キーワードの追加が必要）。また、`return`が脱出 + `give`が評価という2つの概念をユーザーに学ぶ必要がある。末尾式方案は新概念ゼロで済む。

### 案D：RFC-010を現状維持（必ず明示的な`return`）

**否決理由**：RFC-007との競合は調和不能である（動機参照）。また、実装は既に末尾式パスに移行している。

| 末尾式なし          | 存在しない（空でないブロックは必ず末尾式を持つ；空ブロック`{}` → `Void`） | `Void`したい場合は明示的に`Void`を書く          | 2026-09-15 |
| 代入の値            | `Void`                                           | 代入は文であり値生成ではない                   | 2026-09-15 |
| `if` elseなし      | `Void`                                           | 条件偽の場合は評価可能な分支がない                 | 2026-09-15 |
| メカニズムと保護の分担    | 言語はメカニズムを提供し、型チェックは保護を提供                       | 言語は「意図の誤り」の防止を約束しない               | 2026-09-15 |
| 制御フロー体 / 計算ユニット | 言語レベルで二分せず、視点の違いとして扱う                     | 命令型と宣言型の共存を実現し、原則のない特例を避ける | 2026-09-15 |
| 錯誤示例の処理      | そのまま削除し、錯誤コードをそのまま残さない                           | 使用可能な错误コードをそのまま残すと誤解を招く         | 2026-09-15 |

## 付録C：用語集

| 用語       | 定義                                                         |
| ---------- | ------------------------------------------------------------ |
| 末尾式   | ブロック内の最後の値生成式で、ブロックの値はこれに等しい                       |
| 非局所脱出 | 外側の計算ユニットを貫通し、関数境界に直接作用する制御フロー転送（`return`） |
| 爆発原理   | `Never <: T`は任意の`T`に対して成立し、`Never`を任意の型にrollableにする   |
| 値ブロック     | `= {}` / `spawn {}` / `unsafe {}`——値出口は末尾式          |
| join       | 複数分支のマージルールで、`Never`分支はマージに参加しない                       |

## 付録D：関数 / ブロック値の曖昧さの裁定

### 問題

`name = { ... }`は2つの承認済みRFCで異なるものとして定義されていた：RFC-007（関数構文）はそれを関数（「空引数最短形」`name = { return ... }`）として扱い、RFC-010 / 010aはそれをブロック値（`= {}`は値ブロック、値は末尾式）として扱った。同一の構文位置に2套のセマンティクスが并存し、実装では`callable_parts()`がブロックを0引数関数として登録し、`generate_block_ir`はブロック値として値を取得する——2層の理解が不整合である。

### 裁定：内容が型を決定する

同一の原則が辞書とブロックに贯穿すべきである：

| 情形                        | 結果       | 根拠                          |
| --------------------------- | ---------- | ----------------------------- |
| `value`は`Lambda`（`=>`） | 関数       | `=>`は明示的な関数コンストラクタ         |
| 注釈は`Fn`                 | 関数       | 関数型を宣言している                |
| 注釈は非`Fn`型          | ブロック値       | 注釈が型である（`x: Int = {..}`） |
| **注釈なし**                  | **内容で推論** | **型は内容で決定される**        |

```yaoxiang
x: Int = { y = 5; y }      // ブロック値：x = 5（注釈は非Fn）
f: () -> Int = { 5 }       // 関数：f() = 5（注釈はFn）
f = { 5 }                  // 値：f = 5（注釈なし → 内容で推論）
f = {}                     // 値：f = Void（空ブロック）
b = () => 5                // 関数：明示的なlambda
d = { "a": 1 }             // 値：Dict（内容は自己記述的）
```

**なぜ「注釈なしはデフォルトで関数」ではないか**：そうすると`f = { 5 }`は関数で`d = { "a": 1 }`は辞書になる——同じ`{`が同じ注釈なし位置で異なる範疇のものを生じる。3つのかつて考慮された理由はすべて成立しない：

1. 存量コードはゼロ変更——移行コストは支払える（211ファイル、704箇所）が、セマンティクスの根拠ではない
2. 関数定義は高频、ブロック値は低周波——頻度は型のルールではない
3. RFC-007は既に承認されており、これを改めるのは本RFCを改めるよりコストが高い——間違ったものを「コストが高い」ことを理由に正しいものにしない

**型は内容で決定され**、注釈の有無を見ない。注釈は依然として型を宣言し（`f: () -> Int`）、しかし「注釈の不在」を理由にデフォルト値を適用しない。

### `{}`の落ち處き

`Dict`構文は少なくとも1つのキーを要求し、`{}`には内容による判断基準がないため、ブロック構造の零形態を取る → 空ブロック、値`Void`。
空辞書は`dict.new()`を使う。spec [§2.9.1](../../../reference/language-spec/syntax.md)を参照。

### 付随する実装修正

1. **注釈は値取得を決定しない**：`generate_function_ir`などの3箇所は`return_type != Void`を末尾式の値取得のしきい値として使っていたため、注釈なしの`f = { 5 }`は末尾式が静かに捨てられ、`Void`を返す原因となっていた。注釈は*チェックするかどうか*を決定するだけで、*評価するかどうか*を決定しない。
2. **`callable_parts()`はブロックを無条件に飲み込まない**：`Expr::block_binding_is_function(注釈, 値)`が统一的に分流判定を行う。
