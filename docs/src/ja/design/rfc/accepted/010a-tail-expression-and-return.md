# RFC-010a: 末尾式の評価と return セマンティクス

> **参考**:
>
> - [RFC-010: 統一型構文](./010-unified-type-syntax.md) — `name: type = value` モデル、`{}`
>   依存駆動計算ユニット
> - [RFC-007: 関数定義構文統一方案](./007-function-syntax-unification.md)
>   — コードブロック返却ルール、早期 return
> - [RFC-038: 文終端と改行ルール](038-statement-termination.md) — 文と式の改行動作
> - [言語仕様 §型システム](../../../reference/language-spec/type-system.md) — `Never` 爆発原理

## 概要

`return` とブロック評価のセマンティクスを統一し、RFC-007 と RFC-010 の表現衝突を解消する。

提案するのは**三つの自己無撞着なルール**である：ブロックの値は末尾式と等しい（唯一の出口）；`return`
は型が `Never` である**非局所脱出**（関数を脱出し、ブロックに「返す」のではない）；`if` に `else`
がない場合は `Void` を取る。

`return` とブロック評価は**言語レベルで二分されない**——`{ return n }` はブロックとしてその値が
`n`（型 `Never`）であり、同時に `return`
の作用は関数を退出することである。この二つは**爆発原理**（`Never <: T`）によって共存する。RFC-007 の「早期 return」と RFC-010 の「ブロックに値がある」はこれら三つのルールの帰結であり、矛盾する特例ではない。

新しい構文もキーワードもない。

## 動機

### 表現衝突

playground のフィボナッチ例はセマンティクスの分岐を露呈した：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // この return は「if のもの」か「関数のもの」か？
  }
  return fib(n - 1) + fib(n - 2)
}
```

二つの受諾済 RFC は**逆方向**の推論を与える：

| RFC                   | 表現                                                                                                       | 推論セマンティクス                                  |
| --------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **RFC-007**（受諾済） | `factorial` を例に、タイトルは**「早期 return：return の使用」**：`if n <= 1 { return 1 }`                 | `return` は `if` と関数本体を貫通し、**関数に戻る** |
| **RFC-010**（受諾済） | 「`{}` は依存駆動計算ユニット…`return` を用いて明示的に値を返す」；`spawn { return c }` はタスク結果を返す | `return` は**この `{}`** に値を返す                 |

RFC-010 によれば、`if n <= 1 { return 1 }` の波括弧は計算ユニットであり、`return 1`
がその値として 1 を与えると、`if`
文の値は破棄され、次の行が必ず実行される——**fib は無限再帰**する。RFC-007 によれば正しい。

### 根本原因：`return` という語の一語二職

- **RFC-007 はこれを用いて「関数を退出する」**——制御フローの概念
- **RFC-010 はこれを用いて「このブロックの値はこれである」**——評価の概念

制御フローのキーワードで評価を表現することは範疇錯誤（category
error）である。一語が二職を兼ねる以上、如何に調整してもどちらかが犠牲になる。

### 下流ドキュメントの誤った拡張解釈

`docs/src/reference/language-spec/syntax.md` は RFC-010 の「`{}`
ブロック」を**全ての波括弧**に拡張した：

- §2.9：「`{}` 中の `return`
  は**常にその内容を上位スコープに返す**」（さらに「統一セマンティクス：全ての `{}`
  ブロック」と称する）
- §3.3：「`return` は**コードブロックから値を返す**ために用いる」

しかし RFC-010 の原文が定義しているのは**三種類の値を持つブロック**（`= {}` / `spawn {}` /
`unsafe {}`）であり、**通篇で `if` / `while` / `for` / `match` の波括弧には触れていない**。

### 実装現状

| 挙動                                     | 現状                                      |
| ---------------------------------------- | ----------------------------------------- |
| `if n == 0 { return 7 } … return 8`      | 関数退出（`h(0) = 7`）                    |
| `f = { n + 1 }`                          | 末尾式が使える（`5` を返す）              |
| `x = { y = 5; y }`（裸ブロックの末尾式） | `E3006` 変数未解決（#343 参照）           |

| `x = if c { 19 }`（`else` なし）         | `19`（`Void` であるべき、#346 参照）      |
| `v = unsafe { 42 }`                      | `void`（#347 参照）                       |
| `y = if c { 111 } else { 222 }`          | 使用可能（`if` を式として）               |

## 提案

### 三つのルール

```
① ブロックの値 = 末尾式（唯一の出口）
   代入文の値は Void；空ブロック {} の値は Void
② return : (T) -> Never
   非局所脱出：直近の関数境界を退出する
③ if に else なし → Void
```

**この三つで「早期 return」を十分に推論でき、`return` が関数を特称する追加ルールは不要である。**

### ルール ①：ブロックの値

ブロックの**最後の文/式**がすなわちブロックの値（末尾式）である。これは**「末尾式がなければ Void」ではない**——非空ブロックは常に末尾式を持つ（末尾の文そのものがそれである）、空ブロック
`{}` の値は `Void`。

```yaoxiang
// 末尾式がブロックの値を決定する
a = {
    x = compute()        // 代入文 → Void
    x * 2                // 末尾式 → ブロックの値
}

// 代入を末尾式とする → ブロックの値は Void
b = {
    x = compute()
    log(x)               // 代入文 → Void
}

// Void を望むなら明示的に書く
c = {
    log(x)
    Void                 // 明示的な Void
}
```

**設計判断基準（機構と保護の分離）**：

- **言語ルールは機構のみを与える**：末尾の文がすなわちブロック値、ルールは唯一で曖昧さがない
- **保護は型検査が提供する**：関数宣言 `-> Int` に対して末尾式の型が不一致 → コンパイルエラー
- **言語は「意図の誤り」を防がない**：末尾式の型がたまたま戻り型と一致したが意味は本意でない場合、それは作者の疏忽であり、言語には判断できない。**言語ルールで意図の誤りを防ぐことに頼らない。**
- **返したくないなら明示的に `Void` と書く**

これは RFC-010 の「`= { ... }` は `return` を必須とし、さもなくば `Void`
を返す」を置き換え、またその設計理由「末尾式が戻り値かどうかの曖昧さを解消するには明示的な `return`
が必要」をも置き換える。

### ルール ②：`return` は非局所脱出

`return` の型は `Never`（ゼロ構築子、居住可能な値を持たない）。そのセマンティクス：

- **直近の関数境界を退出**し、値を呼び出し元に渡す
- **あらゆるブロックを貫通する**——（存在すれば）`if` / `while` / `for` / `match` / 裸ブロック /
  `spawn` / `unsafe`

`return` はブロックに「値を返さない」。`{ return n }` はブロックとしてその値が
`n`（末尾式ルール）であり、**型は `Never`**；同時に `return`
の作用は関数を退出することである。**二つの事象が同時に成立する。**

### ルール ③：`if` に `else` なし

```yaoxiang
x = if c { 19 }        // else なし
```

条件が偽のとき評価すべき分岐がないため、`Void` を取る。したがってこの `if` の値型は
`Void`（あるいは非 `Void` 位置には使用不可）。

値が必要なときは明示的に両分岐を補う：

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` は共存の技術的基礎

`Never <: T` は任意の型 `T` に対して成立する（爆発原理、言語仕様 §型システム 参照）。したがって：

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // 末尾式 : Never
  }                       // → この if の値 : Never
  fib(n - 1) + fib(n - 2) // → ブロックの値 : Int
}
```

- 分岐本体 `{ return n }` の値は `Never`
- この `if` の唯一の分岐は `Never` ⇒ `if` の値は `Never`
- `Never`
  型の文は**シーケンスがここで停止すること**を意味する——後続の文は「順次実行される次の一文」ではない
- 一方 `Never` は任意の型に縮約可能（爆発原理）であり、したがってブロック全体が `-> Int` を満たす

**「早期 return」はこれにより自然に推論される**：`Never`
がシーケンスを停止し + 爆発原理により縮約可能。

## 詳細設計

### ブロックと末尾式の形式化

```
Block        ::= '{' Stmt* '}'                     // 空ブロック → Void
               | '{' Stmt* Expr '}'                // 値 = Expr
Expr         ::= ...
               | Return                            // 型 Never
Stmt         ::= Assignment | ExprStmt | ...

値(Block)：
  空ブロック                    → Void
  { ...; e }                   → 型(e)
  { ...; s }（s は文）         → Void          // 代入の値は Void
```

### `return` の型ルール

```
return e : Never        where e : T

// Never <: T' は任意の T' に対して成立するため、return は任意の戻り型の位置に登場可能
```

**`return` の合法性を制約する追加ルールは不要**——爆発原理が既に網羅している。これにより「`return` が
`X` を返す関数の中に現れて良いか」このような問題は消滅する。

### 多分岐マージ

```
join(A, B)：
  もし A : Never  → B
  もし B : Never  → A
  そうでなければ  → A、B が互換であることを要求（同一型または到達可能な共通上界）
```

`if` / `match` の多分岐は `join` によってマージされる。`return` を含む分岐はその型が `Never`
であるためマージに参加しない。

### RFC-007 との一貫性

RFC-007 の例は**本 RFC に完全準拠**し、改訂を要しない：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Never 分岐、join で無視される
    return n * factorial(n - 1)     // 関数退出
}
```

「早期 return」は特例ではなく、ルール ①② と爆発原理の**帰結**である。

### RFC-010 との差異及び改訂要求

RFC-010 の定義は本 RFC に従い既に改訂済みであり、差異は以下の通り：

| RFC-010 の原条文                                                 | 現行定義                                                      |
| ---------------------------------------------------------------- | ------------------------------------------------------------- |
| 「`= { ... }` は `return` を必須とし、さもなくば `Void` を返す」 | ブロックの値 = 末尾式；空ブロック → `Void`                    |
| 設計理由「末尾式の曖昧さを解消するには明示的な `return` が必要」 | 成立しない——末尾式は曖昧さを生まず、`return` はそれを妨げない |
| 三箇所の `return c` / `return SqliteDb` 例                       | 末尾式による書き方（`spawn` / `unsafe` の値出口を統一）       |

**RFC-010 の中核設計（`{}` を依存駆動計算ユニットとする）は不変**であり、単に値出口が `return`
から末尾式に変わるのみである。

### 視点の統一（設計原則）

`if` / `while`
の波括弧は**命令型制御体であると同時に宣言型評価ユニットでもある**——これは**視点の違いであり、二つの言語構造ではない**。したがって：

- **言語レベルで「制御流体」と「評価ユニット」を二分しない**
- 全てのブロックは同じ評価ルール（ルール ①）を共有する
- `return` は唯一の例外機構であり、その例外性は `Never` の型論的性質に由来し、構文上の特例ではない

これにより declarative な書き方と Python 流の書き方が自然に共存する：

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## トレードオフ

### 利点

- **RFC 衝突の解消**：RFC-007 と RFC-010 は矛盾から帰結関係となり、いずれも犠牲にする必要がない
- **ルール数が最少**：三つのルール + 一つの型論的性質（爆発原理）、特例なし
- **`return` の意味が唯一**：関数を退出する。もはや「ブロック値 / 関数値」間で帰属を判断する必要なし
- **視点の統一**：命令型と宣言型が共存し、言語レベルで二分されない
- **成熟した言語との一致**：Rust も同様に「末尾式 + `return : !`」で二つの機構を共存させている
- **新構文ゼロ**：キーワード追加なし、parser の構文ルール変更なし

### 欠点

- **末尾式が値となることに「誤返却」のリスク**：最終行の削除忘れ時、戻り値が静かに変わる
  - 緩和策：型不一致を型検査が遮断；言語は意図の誤りの防止を約束しない（設計判断基準参照）
- **下流ドキュメントの同期改訂が必要**：受諾済ドキュメントの例を書き換える必要がある
- **文終端との相互作用を明確化する必要**：改行で終端される末尾式が依然としてブロックの値であるか（オープン問題参照）

## 代替案

### 案 A：`return` の一語二職を保持し、所在ブロック型により振り分け

関数本体 `= {}` 中の `return` は関数に帰属；`spawn {}` / `unsafe {}` 中ではブロックに帰属；`if {}`
/ 裸ブロック中ではどこに？

**否決理由**：`if`
の帰属を決着できない——これこそが元の衝突である。またユーザが「どのブロックが誰に帰属するか」を記憶する必要があり、原則的根拠がない（なぜ
`if` は関数に帰属し裸ブロックは自分に帰属するのか）。

### 案 B：厳格なブロック返却（`return` は常に現在のブロックに帰属）

**否決理由**：**機能欠如**。`return`
はネストしたブロックから関数を早期退出することが永遠にできず、guard 節（`if err { return }`）は完全に書けず、関数を何重にもネストした式として書くしかない。

### 案 C：ブロックの値に新キーワード（`give x` / `yield x`）

**否決理由**：RFC-036 の**構文変更ゼロ**原則に違反（新規キーワード追加が必須）、またユーザは二つの概念（`return`
退出 + `give` 評価）を学ばねばならない。末尾式案は新概念ゼロ。

### 案 D：RFC-010 の原状維持（明示的な `return` を必須）

**否決理由**：RFC-007 との衝突を調和できない（動機参照）。また実測された実装は既に末尾式の経路を歩んでいる。

## 下流ドキュメントの改訂

本 RFC の定義は下流ドキュメントの権威あるセマンティクスとなっている；関連ドキュメントは全て同期済み（既に廃止された表現は残していない）。

| `while { if i==2 { return 42 } }`                 | `42`（ループを貫通）                 |
| ネスト `{ { return 5 } return 1 }`                | `5`（裸ブロックを貫通）              |

| 用語             | 定義                                                                               |

| 末尾式           | ブロック中で最後に値を生成する式、ブロックの値すなわちこれ                         |

## 付録 D：関数 / ブロック値曖昧性裁定

### 問題

`name = { ... }`
はかつて二つの受諾済 RFC で異なるものとして定義されていた：RFC-007（関数構文）は関数を扱い（「空引数最簡」`name = { return ... }`）、RFC-010
/ 010a はブロック値を扱う（`= {}`
は値を持つブロック、値は末尾式）。同一構文位置に二組のセマンティクスがあり、実装上
`callable_parts()` がブロックを 0 引数関数として登録する一方、`generate_block_ir`
はブロック値として値を取り——二層の理解が不一致であった。

### 裁定：内容により型が決まる

同一の原則が辞書とブロックに貫かれるべきである：

| 場合                        | 結果                   | 根拠                                |
| --------------------------- | ---------------------- | ----------------------------------- |
| `value` が `Lambda`（`=>`） | 関数                   | `=>` は明示的な関数構築子           |
| 注釈が `Fn`                 | 関数                   | 関数型を宣言している                |
| 注釈が非 `Fn` 型            | ブロック値             | 注釈がすなわち型（`x: Int = {..}`） |
| **注釈なし**                | **内容により型を推論** | **型は内容により決まる**            |

```yaoxiang
x: Int = { y = 5; y }      // ブロック値：x = 5（注釈は非 Fn）
f: () -> Int = { 5 }       // 関数：f() = 5（注釈は Fn）
f = { 5 }                  // 値：f = 5（注釈なし → 内容により推論）
f = {}                     // 値：f = Void（空ブロック）
b = () => 5                // 関数：明示的な lambda
d = { "a": 1 }             // 値：Dict（内容が自己記述的）
```

**「注釈なしなら既定で関数」としない理由**：そうすると `f = { 5 }` は関数、`d = { "a": 1 }`
は辞書となり——同じ無注釈位置で同じ `{`
が異なる範疇のものを与えることになる。かつて検討された三つの理由はどれも成立しない：

1. 既存コードのゼロ変更——移行コストは支払可能（211 ファイル、704 箇所）、セマンティクスの根拠ではない
2. 関数定義が高頻度、ブロック値が低頻度——頻度は型ルールではない
3. RFC-007 は受諾済で、改訂コストは本 RFC より高い——誤ったものは「高い」という理由で正しくならない

**型は内容により決まり**、注釈の有無を見ない。注釈は依然として型を宣言する（`f: () -> Int`）が、「注釈がない」ことをもって既定値を押し付けることはない。

### `{}` の落位

`Dict` 文法は少なくとも一つのキーを要求し、`{}`
は内容により判断する根拠がないため、ブロック構造のゼロ形態を取る → 空ブロック、値 `Void`。空辞書は
`dict.new()` を用いる。詳細は spec [§2.9.1](../../../reference/language-spec/syntax.md) 参照。

### 伴う実装修正

1. **注釈は値取りを決定しない**：`generate_function_ir` など三箇所はかつて `return_type != Void`
   を末尾式の値取りの閾値として用い、無注釈の `f = { 5 }` の末尾式を静かに破棄し `Void`
   を返していた。注釈は*検査*すべきかのみを決定し、*評価*すべきかは決定しない。
2. **`callable_parts()` はブロックを無条件に呑まない**：分流は
   `Expr::block_binding_is_function(注釈, 値)` に統一して判定させる。
