# RFC-010b: パターンマッチングの完全化（バリアント分解と網羅性）

> 本文書は
> [RFC-010](../accepted/010-unified-type-syntax.md)（統一型構文）のサブ RFC である。バリアントの宣言・構築呼び出し形態とランタイム tagged
> union 表現（`variant_id`
> 宣言順序——本RFCの網羅性検査におけるバリアント集合入力を含む）は RFC-010 の〔レコード和型バリアント構築（権威定義）〕節で定義される；本文書はそのミラー側、すなわち match 分解と網羅性検査を担う。構築と分解は対になるため、共に RFC-010 に帰属する。
>
> 旧番号 RFC-039（2026-09-03 起稿）；2026-09-25 に所有者の決定により RFC-010 サブ RFC へと統合・改称 RFC-010b、追跡 issue は #330 のまま。本文は 2026-09-27 に充実、実装と合致（head
> e368958f）；同日所有者確認により承認（accepted）。

## 概要

`match`
のパターンマッチングを「リテラル+ワイルドカードのみ」から完全な能力へと拡張する：バリアント分解（ゼロペイロードとマルチペイロードを含む）、構造体/タプルパターン、OR パターンとガード、識別子束縛セマンティクスの確定、および網羅性検査（E1030/E1031 を空コードから実発火へ）。本 RFC は
`Error { kind: ErrorKind, message }`
進化路線（RFC-013「ランタイムエラー値とコード貫通」進化節）の前提となるが、動機は独立している——パターンマッチングは汎用言語機能であり、バリアントを持つすべての型に資する。

## 動機

### 現状の実証（2026-09-03、v0.7.12 コード；2026-09-27 すべて解消）

1. **IR 層ではリテラルのパターンのみが実在する**。AST には完全なパターン集合が定義されているが、IR 生成は
   `Literal`
   分岐のみを実装しており、その他のパターンはスタブに落ちる——定数 0 をロードして等価比較に参加し、決してマッチしない；さらに scrutinee がたまたま 0 の場合、誤ってスタブアームにマッチする。
2. **stdlib.md の `match ok(v)/err(e)` 例は机上能力に過ぎない**。
3. **網羅性検査は空吊り**。E1030/E1031 はコード表に登録されているが、発火箇所がない。
4. **エラー処理の進化がブロックされている**（RFC-013 の構造化エラー建模はバリアント分解に依存）。

### 設計目標

- **バリアント分解が利用可能**：`match r { ok(v) => ..., err(e) => ... }`
  およびユーザ定義バリアント集合の分解が、すべての実行経路で意味的に一貫している。
- **網羅性に依存可能**：E1030/E1031 が実発火し、match の分岐漏れはコンパイルエラーとなる。
- **スタブの除去**：未対応パターンはコンパイル時にエラーとし、誤って静かに通過させない（#330 セーフネット——この過渡方策は実装期間中に段階的に実エンコーディングへ置換され、最終的にスタブはすべて除去される）。

## 提案（2026-09-27 確定・実装済み）

| 能力                          | 状態 | 説明                                                                                              |
| ----------------------------- | ---- | ------------------------------------------------------------------------------------------------- |
| Union バリアントパターン      | ✅   | `Variant` / `Variant(binding)` / マルチペイロード `make(a, b)` + ペイロード束縛をアームスコープへ |
| Struct / Tuple パターン       | ✅   | フィールドパターン（短縮束縛 / `名: 子パターン`）、タプルパターン；宣言フィールドは完全網羅必須   |
| OR パターンと Guard           | ✅   | `p1 \| p2` と `pat if cond`：代替レベルの失敗連鎖、ガード失敗は次アームへ                         |
| 網羅性検査                    | ✅   | E1030 分岐漏れ、E1031 到達不能、スコープはバリアント集合を網羅                                    |
| Identifier パターンの意味確定 | ✅   | **束縛**と確定（後述節参照）                                                                      |

## 設計決定

### Identifier パターン：束縛、代入ではなく、比較でもない

`match x { y => ... }` の素の識別子 `y`
は**束縛**と確定する——新しい名前を導入して被マッチ値を受け取り、常にマッチする（名前付きワイルドカードと等価）。三つの根拠：

1. **構造論証**：パターン位置の識別子は本質的に二つの役割を持つ——判別位置（`ok(v)` の
   `ok`、バリアント表と照合）とリーフ位置（`ok(v)` の
   `v`、束縛）。パラメータ表（lambda）にはリーフ位置しかなく曖昧さはない；素の識別子は判別位置に立つと同時にリーフ位置に似ており、曖昧さが生じる。YaoXiang には静的バリアント表がある：判別名は「表引きヒット」で裁決される（パターン頭が scrutinee バリアント集合の名前またはリテラル → 判別；引かぬ素の名前 → 束縛）、Rust 式の大文字小文字規約は不要。
2. **値比較の退行性**：「パターン中の既束縛名は等価を表す」（単一化セマンティクス）は単一代入伝統の所産；可変言語では「束縛済みか否か」を静的に判定できず、このセマンティクスは成立しない。YaoXiang の変数は再代入可能（`mut`）であり、Rust の立法に倣う。
3. **既存値とのマッチ要求はガードに帰属**：`n if n == threshold`（ガードが実装されるまでは if 連鎖で記述）。

**束縛は代入ではない**（2026-09-27 に所有者と整合した口径）：パターン束縛は**新しい名前**を導入し、アーム内スコープに属し、外層の同名変数を覆い隠す（シャドウィング）、アームを抜ければ消滅する（検証：外層
`v = 999` は `some(v)` マッチ後もそのまま）；代入は既存名前を書き換える（E2010/`mut`
の法体系）。両者は本言語に併存し概念的に分離されている、`=` は名前の既存有無で分岐し（spec
§4.3 代入優先）、パターン位置は束縛側にのみ属する。

### match は式であり、代入文ではない

`match` はヒットしたアームの値（式全体の値）を産出する、`v = match ...`
は単に通常の束縛構文がそれを受け取るだけである。網羅性検査の牙は「アームは値を産出せねばならない」ことに由来する：形状漏れ = 代入側が値を得ない = コンパイルエラー（E1030）；文形態の switch の分岐漏れは黙過しかない。

### アームのセマンティックモデルと実装

アーム = **表札付き単一引数関数**：`some(v) => body` ≈
`λv.body`、実引数が some 形状のときのみ呼び出される；束縛セマンティクスは「左辺がパラメータ位置である」ことに由来。lambda と
`=>`
を同源で共用する。実装上アームは**クロージャではない**：IR 再帰パターンコンパイラ（`compile_pattern`）がテスト連鎖（VariantTag/LoadField/Eq +
JmpIfNot）とペイロード抽出（VariantPayload）をインライン発射し、ヒットすればアーム本体へ降下し、失敗すれば次アームへジャンプ——呼び出しコストはゼロ。

### OR パターンとガード

- `p1 | p2`：代替を順に試行；非末尾代替の失敗 → 次代替、ヒット → ペイロード抽出後、直接アーム本体へ；末尾代替の失敗 → 次アーム。**各代替の束縛名集合は一致しなければならない**（E1033）、同名束縛はアームレベル事前割当レジスタを共有する（本体が読み出す値はヒットした代替が書き込んだ値である）。
- `pat if cond`：パターンヒット後に `cond`
  を評価する（**パターン束縛はガードに対して可視**）、偽なら次アームへ。ガード条件は `Bool`
  を産出せねばならない。**ガード付きアームは網羅性カバーに算入しない**（ガードはヒットしない可能性がある、Rust と同規）、ただしガード付きの重複バリアントアームは到達可能（前アームの細分化である）。

### 構造体パターン

`Point { x, y: b }`：フィールド短縮束縛は同名を束縛、`名: 子パターン`
は再帰。**宣言フィールドは完全網羅必須**
（E1034 フィールド欠落）、未知フィールドは拒否（E1042）、同フィールドの重複は E1032。 `..`
フィールド省略とジェネリック構造体パターンは未対応（オープン問題参照）。

### バリアント分解（RFC-010 構築と対称）

| 構築                               | 分解               | ペイロード表現                                                                                |
| ---------------------------------- | ------------------ | --------------------------------------------------------------------------------------------- |
| `Result(Int, String).ok(5)`        | `ok(v)`            | 単一ペイロード：直接束縛                                                                      |
| `Pair.make(3, 4)`                  | `make(a, b)`       | マルチペイロード：Tuple でパック、位置分解                                                    |
| `Color.red()` / `Option(T).none()` | `red()` / `none()` | ゼロペイロード：`pattern: None`、アリティ検査（ペイロード付きバリアントへの `ok()` はエラー） |

ペイロード型 = バリアント引数を scrutinee 型実引数で置換（宣言順序）；ネストパターン（`ok(some(v))`
で和型を跨ぐ、`Point { pos: Tuple(a, b) }` で構造体を跨ぐ）はサブ型で再帰。

### 網羅性と到達可能性

- **E1030（分岐漏れ、全網羅）**：**すべての型**の scrutinee——フォールスルーアームなしなら被覆を検査する。和型：バリアント集合を無ガード Union アームで完全網羅せねばならない（ガード付きアームは算入しない、ガードはヒットしない可能性がある）；非和型：値域は開放（Int/String/Char 等）、リテラルアームでの網羅は不可能、**フォールスルーアーム必須**。列挙可能例外：Bool の true+false 両リテラルアームで網羅；Void は居住可能値なし、vacuously 網羅。（2026-09-27 所有者確定：フォールスルーなしの match は「他の値は発生しない」ことの暗黙仮定である——暗黙が許されぬ場所では暗黙とせず、仮定は
  `_` と書かねばならない。）
- **E1031（到達不能）**：フォールスルーアーム（無条件ヒットする不可駁パターン：Identifier/Wildcard/Tuple/Struct、ガードなし）の後の任意のアーム；無ガードの重複バリアントアーム、重複リテラルアーム。

### 診断

| コード | 意味                                                                         |
| ------ | ---------------------------------------------------------------------------- |
| E1030  | パターンの網羅不足（欠落バリアントを列挙）                                   |
| E1031  | 到達不能パターン（フォールスルーアームの後 / 重複バリアント / 重複リテラル） |
| E1032  | パターン重複束縛（同一パターン内で同名束縛が複数回出現）                     |
| E1033  | OR パターン束縛不一致（各代替の束縛名集合が異なる）                          |
| E1034  | 構造体パターンにフィールド欠落                                               |
| E3008  | IR 層セーフネットとして保持（防御的分岐、通常プログラムでは到達不能）        |

### 代入/lambda との境界（混同防止備忘）

- パターン束縛 ≠ 代入：新名導入 vs 既存名書換（E2010/`mut`）；
- OR パターン ≈
  lambda 適用の拡張（セマンティックモデル）、実装はインラインジャンプで、クロージャ呼び出しではない；
- リテラルパターンは Eq + 条件ジャンプ連鎖へコンパイル——「if/elif の最適化形式」という直感はリテラルで成立し、match での増分は形状判定と分解束縛である。

## 実装落点

- parser：`parse_pattern`（バリアント呼び出し再構成 / 構造体パターン `Ident { .. }`
  分岐 / ネスト OR パターン復元）、`parse_match` の OR パターン収束 + ガード（`no_fat_arrow`
  フラグで `=>` を lambda 中置として扱わない）
- typecheck：`check_match_expr` でアームループ統一 + `check_pattern`
  再帰検査器（束縛登録、ガード Bool 検証、網羅性会計）
- ir_gen：`compile_pattern` 再帰パターンコンパイラ + `sum_type_variants` ミラーがペイロード型と
  `sum_type_param_names` を運ぶ（ペイロード型は scrutinee 実引数で置換）
- コーパス：`02-type-system/pattern_destructure.yx`、`pattern_or_guard.yx`；単体テスト E1030/E1031/E1032/E1033/E1034（rfc011b.rs）

## オープン問題

- [x] Identifier パターン：新変数束縛か既存値マッチか？→
      **束縛**（判別位置はバリアント表引きで裁決、大文字小文字規約なし）；既存値マッチはガードに帰属。
- [x] 網羅性の適用境界：→
      **全網羅**（2026-09-27 所有者確定）——非和型もフォールスルーアームなしなら E1030、列挙可能例外は Bool 両リテラルと Void のみ。
- [x] 修正前の過渡期、スタブの 0 ロード誤マッチをまずコンパイルエラーとすべきか？→ イエス（#330 セーフネット）、すべて実エンコーディングに置換済み。
- [ ] 構造体パターンの `..`
      フィールド省略（部分フィールド + フォールスルー）は必要か？（フィールド網羅規則に影響）
- [ ] ジェネリック構造体パターン（`Box { v, n }` を `Box(Int)`
      値に）は未定——現在 typecheck前段で拒否。
- [ ] non_exhaustive 様属性（std バリアント集合拡張がユーザ match に与える破壊半径）は未定。
