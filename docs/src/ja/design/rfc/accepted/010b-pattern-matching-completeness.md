# RFC-010b: パターンマッチング完全化（バリアント分解と網羅性）

> 本文書は
> [RFC-010](../accepted/010-unified-type-syntax.md)（統一型構文）のサブ RFC である。バリアントの宣言、構築呼び出し形式とランタイム tagged
> union 表現（`variant_id`
> 宣言順——本本文書の網羅性検査へのバリアント集合入力を含む）は RFC-010〔レコード式和型のバリアント構築（権威ある定義）〕節で定義される；本文書はその鏡像側を担う：match 分解と網羅性検査。構築と分解は対でなければならないため、同じく RFC-010 に属する。
>
> 元の番号は RFC-039（2026-09-03 起稿）；2026-09-25 に所有者決定により RFC-010 のサブ RFC へ統合、番号を RFC-010b に改め、追跡 issue は #330 のまま。本体は 2026-09-27 に充実し実装と共に確定（head
> e368958f）；同日、所有者確認により正式採用（accepted）。

## 概要

`match`
のパターンマッチングを「リテラル＋ワイルドカードのみ」から完全な能力へと補完する：バリアント分解（ゼロペイロードと複数ペイロードを含む）、構造体/タプルパターン、or パターンとガード、識別子バインディング意味の確定、そして網羅性検査（E1030/E1031 を空コードから実発火へ）。本 RFC は
`Error { kind: ErrorKind, message }`
進化路線（RFC-013「ランタイムエラー値とコード貫通」進化節）の前提となるが、動機は独立している——パターンマッチングは汎用言語能力であり、バリアントを持つすべての型に資する。

## 動機

### 現状実証（2026-09-03、v0.7.12 コード；2026-09-27 全て解消）

1. **IR 層でリテラルのパターンのみが実在する**。AST は完全なパターン集合を定義しているが、IR 生成は
   `Literal`
   分岐のみを実装し、その他のパターンはスタブに落ちる——定数 0 を読み込んで等価比較に参加し、決してマッチしない；しかも scrutinee がちょうど 0 の場合は誤ってスタブ arm へマッチしてしまう。
2. **stdlib.md の `match ok(v)/err(e)` 例は机上能力である**。
3. **網羅性検査が空振り**。E1030/E1031 はコード表に登録されているが発火点がない。
4. **エラー処理進化がブロックされる**（RFC-013 構造化エラー建模はバリアント分解に依存）。

### 設計目標

- **バリアント分解が利用可能**：`match r { ok(v) => ..., err(e) => ... }`
  とユーザー定義バリアント集合の分解がすべての実行経路で意味的に一貫している。
- **網羅性に依存可能**：E1030/E1031 が実発火し、match の分岐漏れはコンパイルエラー。
- **スタブ除去**：未対応パターンはコンパイル時にエラー、黙って誤動作しない（#330 セーフティネット——この過渡的戦略は実装期に段階的に実エンコーディングへ置換され、最終的にスタブは全て除去される）。

## 提案（2026-09-27 確定・実装化）

| 能力                        | 状態 | 説明                                                                                                        |
| --------------------------- | ---- | ----------------------------------------------------------------------------------------------------------- |
| Union バリアントパターン    | ✅   | `Variant` / `Variant(binding)` / 複数ペイロード `make(a, b)` + ペイロードバインディングは arm スコープへ    |
| Struct / Tuple パターン     | ✅   | フィールドパターン（短縮バインディング / `名: 副パターン`）、タプルパターン；宣言フィールドの完全網羅が必要 |
| Or パターンと Guard         | ✅   | `p1 \| p2` と `pat if cond`：代替レベルの失敗連鎖、ガード失敗は次腕へ                                       |
| 網羅性検査                  | ✅   | E1030 分岐漏れ、E1031 到達不能、スコープはバリアント集合を網羅                                              |
| Identifier パターン意味確定 | ✅   | **バインディング**と確定（以下節参照）                                                                      |

## 設計判断

### Identifier パターン：バインディングであり、代入でも比較でもない

`match x { y => ... }` の裸の識別子 `y`
は**バインディング**と確定する——新しい名前を導入してマッチ対象の値を受け取り、常にマッチする（名前の付いたワイルドカードと同値）。三つの根拠：

1. **構造論証**：パターン位置における識別子は二つの役割を持つ——判別位置（`ok(v)` の
   `ok`、バリアント表と照合）と葉位置（`ok(v)` の
   `v`、バインディング）。引数リスト（lambda）は葉位置のみなので曖昧さはない；裸の識別子は判別位置に立ってしかも葉位置に見えるため、曖昧さが生じる。YaoXiang は静的バリアント表を持つ：判別名は「表引き命中」により裁定される（パターンヘッドが scrutinee のバリアント集合内の名前またはリテラル → 判別；表引きに失敗した裸名 → バインディング）。Rust 式の大文字小文字規約は不要。
2. **値比較の退化性**：「パターン内の既バインド名は等価を表す」（ユニフィケーション意味論）は単一代入伝統の産物である；可変言語では「バインド済みか否か」を静的に判定できず、この意味論は成立しない。YaoXiang の変数は再代入可能（`mut`）、Rust の立法に従う。
3. **既存値マッチの要求はガードへ**：`n if n == threshold`（ガード落地前に if 連鎖を書く）。

**バインディングは代入ではない**（2026-09-27 に所有者と整合した方針）：パターンバインディングは**新しい名前**を導入し、腕内スコープで外側同名変数をシャドウし、腕を出れば消える（検証：外側
`v = 999` は `some(v)` 命中後もそのまま）；代入は既に存在する名前を書き換える（E2010/`mut`
の法制）。両者は本言語に共存し概念的に分離されており、 `=` は名前の既存有無で分岐する（spec
§4.3 代入優先）、パターン位置はバインディング側に属するのみ。

### match は式であり、代入文ではない

`match` はマッチした腕の値（式全体の値）を産出する。`v = match ...`
は単に通常のバインディング構文がそれを受け取るだけ。網羅性検査の牙は「腕は必ず値を出す」から来る：形状漏れ = 代入側が値を得ない = コンパイルエラー（E1030）；文形態の switch 分岐漏れは黙過しかできない。

### 腕の意味モデルと実装

腕 = **表札付き単引数関数**：`some(v) => body` ≈
`λv.body`、実引数が some 形状のときのみ呼び出される；バインディング意味論は「左辺は引数位置」から来る。lambda と
`=>`
を共有する点で同根。実装上、腕は**クロージャではない**：IR 再帰パターンコンパイラ（`compile_pattern`）がインラインでテスト連鎖（VariantTag/LoadField/Eq +
JmpIfNot）とペイロード抽出（VariantPayload）を発射し、命中で腕本体に落ち、失敗で次腕へジャンプ——呼び出しオーバーヘッドゼロ。

### or パターンとガード

- `p1 | p2`：代替を順に試行；非末尾代替が失敗 → 次代替、命中 → ペイロード抽出後直接腕本体へ；末尾代替が失敗 → 次腕。**各代替のバインディング名集合は一致しなければならない**（E1033）、同名のバインディングは腕レベルの事前割当レジスタを共有する（本体が読み取るのは命中した代替が書き込んだ値である）。
- `pat if cond`：パターン命中後に `cond`
  を評価する（**パターンバインディングはガードに見える**）、偽なら次腕へ。ガード条件は `Bool`
  を産出さなければならない。**ガード付き腕は網羅性カバレッジに算入されない**（ガードは命中しない可能性がある、Rust と同規）、ただしガード付きの重複バリアント腕は到達可能（前腕の細分化）。

### 構造体パターン

`Point { x, y: b }`：フィールド短縮バインディングで同名を、`名: 副パターン` は再帰。
**宣言フィールドの完全網羅が必要**（E1034 フィールド不足）、未知フィールドは拒絶（E1042）、同一フィールドの重複は E1032 を報告。`..`
フィールド省略とジェネリック構造体パターンは未対応（オープン問題参照）。

### バリアント分解（RFC-010 構築と対称）

| 構築                               | 分解               | ペイロード表現                                                                                |
| ---------------------------------- | ------------------ | --------------------------------------------------------------------------------------------- |
| `Result(Int, String).ok(5)`        | `ok(v)`            | 単一ペイロード：直接バインディング                                                            |
| `Pair.make(3, 4)`                  | `make(a, b)`       | 複数ペイロード：Tuple でパッケージ、位置ごとに分解                                            |
| `Color.red()` / `Option(T).none()` | `red()` / `none()` | ゼロペイロード：`pattern: None`、アリティ検査（ペイロード付きバリアントでの `ok()` はエラー） |

ペイロード型 = バリアント引数を scrutinee 型の実引数で置換（宣言順）；ネストパターン（`ok(some(v))`
和型横断、`Point { pos: Tuple(a, b) }` 構造体横断）は副型で再帰。

### 網羅性と到達性

- **E1030（分岐漏れ）**：和型 scrutinee のみ。フォールバック腕なし時、バリアント集合は無ガード Union 腕で完全網羅されねばならない。ガード付き腕は算入されない（ガードが非命中の可能性）。
- **E1031（到達不能）**：フォールバック腕（無条件命中する非反駁可能パターン：Identifier/
  Wildcard/Tuple/Struct、ガードなし）の後のあらゆる腕；無ガードの重複バリアント腕、重複リテラル腕。
- **非和型 scrutinee**：値域は開放的、E1030 を行わない（全リテラル腕 + フォールバックなしの寛容意味論を許可、現状維持）；E1031 は通常通り。

### 診断

| コード | 意味                                                                        |
| ------ | --------------------------------------------------------------------------- |
| E1030  | パターン列挙不足（欠落バリアントを列挙）                                    |
| E1031  | 到達不能パターン（フォールバック腕の後 / 重複バリアント / 重複リテラル）    |
| E1032  | パターンの重複バインディング（同一パターン内に同名のバインディングが複数）  |
| E1033  | or パターン内のバインディング不一致（各代替のバインディング名集合が異なる） |
| E1034  | 構造体パターンでフィールド不足                                              |
| E3008  | IR 層セーフティネット保留（防御的分岐、通常プログラムは到達不能）           |

### 代入/lambda との境界（混同防止メモ）

- パターンバインディング ≠ 代入：新名導入 vs 既有名書換（E2010/`mut`）；
- or パターン ≈ lambda 適用の拡張（意味モデル）、実装はインライン jump、クロージャ呼び出しではない；
- リテラルパターンは Eq + 条件 jump 連鎖へコンパイル——「if/elif の最適化形」という直感はリテラルに対し成立、match の増分は形状判断と分解バインディング。

## 実装箇所

- parser：`parse_pattern`（バリアント呼び出し再構成 / 構造体パターン `Ident { .. }`
  分岐 / ネスト or パターン復元）、`parse_match` or パターン収束 + ガード（`no_fat_arrow` フラグで
  `=>` を lambda 中置に使わない）
- typecheck：`check_match_expr` 統一腕ループ + `check_pattern`
  再帰検査器（バインディング登録、ガード Bool 検証、網羅性計上）
- ir_gen：`compile_pattern` 再帰パターンコンパイラ + `sum_type_variants` 鏡像がペイロード型と
  `sum_type_param_names`（ペイロード型は scrutinee 実引数で置換）を携帯
- コーパス：`02-type-system/pattern_destructure.yx`、`pattern_or_guard.yx`；単体テスト E1030/E1031/E1032/E1033/E1034（rfc011b.rs）

## オープン問題

- [x] Identifier パターン：変数バインディングか既存値マッチか？→
      **バインディング**（判別位置はバリアント表引きで裁定、大文字小文字規約なし）；既存値マッチはガードへ。
- [x] 網羅性の適用境界：→ バリアント集合の網羅は和型のみ；非和型は値域開放的で E1030 しない。
- [x] 修復前の過渡期、stub の 0 読み込み誤マッチをまずコンパイルエラー化するか？→ はい（#330 セーフティネット）、全て実エンコーディングに置換済み。
- [ ] 構造体パターン `..`
      フィールド省略（一部フィールド + フォールバック）の必要性？（フィールド網羅規則に影響）
- [ ] ジェネリック構造体パターン（`Box { v, n }` を `Box(Int)`
      値に）は未定——現時点でtypecheck 前段で拒絶。
- [ ] non_exhaustive 風属性（std バリアント集合拡張がユーザ match の破壊半径）は未定。
