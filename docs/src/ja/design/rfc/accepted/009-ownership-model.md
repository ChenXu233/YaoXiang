# RFC-009: 所有権モデルの設計

## 要約

本文書は YaoXiang プログラミング言語の**所有権モデル（Ownership Model）**を定義する。

**コア設計——5つの概念、1つのグラデーション**：

```
覗く/その場で変更   持ち去る       共有保持        複製する         システムレベル
    │              │              │              │              │
   &T            Move           ref          clone()        unsafe
  &mut T         ゼロコピー      コンパイラ自動  明示的ディープコピー  *T
  ゼロサイズトークン  デフォルト    Rc/Arcを選択              ユーザー責任
  型属性で自然に
  権限を推論
```

- **Move（デフォルト）**：代入/引数/戻り値 = 所有権移転、ゼロコピー、RAII による自動解放
- **`&T` / `&mut T`（借用トークン）**：ゼロサイズのコンパイル時トークン型。`&T`
  は複製可能（共有読み取り）、`&mut T`
  は線形（排他的可変）。権限は型属性から自然に推論され、特別なルールは不要。戻り値や構造体フィールドにも格納可能。
- **`ref`
  キーワード**：スコープを越えて共有。コンパイラが自動的に Rc（タスクを跨がない）か Arc（タスクを跨ぐ）を選択
- **`clone()`**：明示的ディープコピー
- **`unsafe` + `*T`**：生ポインタ、システムレベルのエスケープハッチ

**除去された複雑性**：

- ❌ ライフタイム `'a` なし
- ❌ 独立した借用検査フレームワークなし（借用衝突はホーア命題に次元削減され、型検査と証明パイプラインを共有）
- ❌ GC なし
- ❌「エスケープ禁止」のような特別ルールなし（トークンは通常の型であり、スコープは型システムで統一的に処理される）
- ❌ ユーザーが Rc/Arc の違いを知る必要はない（コンパイラが自動選択）

> **プログラミングの負担**：`&T` は複製可能、`&mut T`
> は複製不可——2つの型属性のみ、特別なルールはゼロ、すべてコンパイラが自動化。
> **パフォーマンス保証**：Move はゼロコスト、トークンはゼロコスト（ゼロサイズ型、コンパイル後に消滅）、ref は必要に応じたコストのみ、GC ポーズなし。

## 動機

### なぜ所有権モデルが必要なのか？

| 言語         | メモリ管理             | 問題                                                     |
| ------------ | ---------------------- | -------------------------------------------------------- |
| C/C++        | 手動管理               | メモリリーク、ダングリングポインタ、二重解放             |
| Java/Python  | GC                     | レイテンシの変動、メモリオーバーヘッド、予測不能なポーズ |
| Rust         | 所有権 + 借用検査      | ライフタイム `'a` の学習曲線が急峻                       |
| **YaoXiang** | **Move + Token + ref** | **シンプルで、決定論的で、GC なし**                      |

### 設計目標

```yaoxiang
# 1. デフォルトは Move（ゼロコピー）
p = Point(1.0, 2.0)
p2 = p                         # Move、p はもう読めない

# 2. &T / &mut T 借用トークン（ゼロコスト、型属性が自然に権限を推論）
print_info(p2)                 # コンパイラが &Point トークンを自動作成、使用後解放
shift(p2, 1.0, 1.0)           # コンパイラが &mut Point トークンを自動作成

# 3. ref = 共有（コンパイラが Rc/Arc を自動選択）
shared = ref p2                # スコープを越えて保持
spawn { use(shared) }          # コンパイラ：タスクを跨ぐ → Arc

# 4. clone() = 明示的コピー
backup = p2.clone()            # ディープコピー、独立

# 5. unsafe + *T = システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Rust との核心的な違い

| 特性             | Rust                                      | YaoXiang                                                            |
| ---------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| デフォルトの意味 | 借用 `&T`（明示的に `.clone()` が必要）   | **Move（値渡し、ゼロコピー）**                                      |
| 借用             | `&T`/`&mut T`、戻り値可、ライフタイム必要 | **`&T`/`&mut T` ゼロサイズトークン、Dup/Linear 型属性が自然に推論** |
| 共有メカニズム   | `Arc::new()` + 手動 Weak                  | **`ref` キーワード（コンパイラが Rc/Arc を自動選択）**              |
| コピー           | `clone()`                                 | `clone()`                                                           |
| 生ポインタ       | `*T`                                      | `*T`                                                                |
| ライフタイム     | `'a`                                      | ❌ なし                                                             |
| 借用検査         | 大域的な推論                              | **型検査器が借用命題を自動生成し、証明パイプラインで統一検証**      |
| 循環参照         | 手動 Weak                                 | **タスク終了時に統一解放 / タスク跨ぎ lint / 標準ライブラリ Weak**  |

## 提案

### 1. Move（デフォルトの所有権移転）

```yaoxiang
# ルール：代入 / 引数 / 戻り値 = Move、ゼロコピー

p: Point = Point(1.0, 2.0)
p2 = p                           # Move、p はもう読めない

# 変数は再代入可能（Python スタイル、シャドウイングなし）
p = Point(3.0, 4.0)              # p を再束縛、型は一致しなければならない

# 関数の引数：Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Move で返す
}

# 関数の戻り値：Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Move で返す、ゼロコピー
}
```

**特徴**：

- ゼロコピー（コンパイラがポインタを移動）
- 移動後、元の束縛は読めない（コンパイルエラー）
- RAII：スコープ終了時に自動解放
- 関数シグネチャ `(T) -> T` 自体がドキュメント——T を消費し、T を返す

### 2. &T / &mut T（借用トークン）

**核心原則：`&T` と `&mut T`
はゼロサイズのコンパイル時トークン型である。これらは「参照」ではなく、「アクセス権限の型レベル証明」。**

#### 2.1 2つの型属性

```
&T      →  ゼロサイズ、ソースデータを凍結（ReadToken 生存中は WriteToken 禁止）、
          凍結保証のもとで複数の読み取りビューが安全 → 複製可能（Dup）
&mut T  →  ゼロサイズ、排他的読み書き（WriteToken 生存中は他のいかなるトークンも禁止）、
          排他的アクセスでは複製が無意味 → 線形（Non-Dup）
```

**因果関係を逆転させてはならない：凍結が原因、Dup が結果。**
データが凍結される（突然変異の可能性がない）からこそ、複数の読み取りビューが安全であり、Dup が実現可能なのである。Dup を定義とし、衝突検査を「追加のパッチ」と位置づければ、設計は誤っている。

#### 2.2 基本使用

```yaoxiang
# メソッド側：引数型を宣言し、必要な権限を決定
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # &Point トークンが読み取り権限を付与
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # &mut Point トークンが書き込み権限を付与
    self.y = self.y + dy
}

# 呼び出し側：コンパイラが借用または Move を自動選択
p = Point(1.0, 2.0)
p.print()                          # コンパイラが &Point トークンを自動作成
p.shift(1.0, 1.0)                  # コンパイラが &mut Point トークンを自動作成
p.print()                          # OK、前のトークンは shift 呼び出し終了と共に解放済み

# 自由関数も同様
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # 2つの &Point トークンが共存——Dup 型
}
d = distance(p, p2)
```

#### 2.3 なぜ「エスケープ禁止」が不要なのか

RFC-009 v8 では `&T`/`&mut T`
に対して3つの特別ルールを課していた——引数にのみ使える、戻り値にできない、構造体に格納できない。これは「借用」概念にパッチを当てていた。

トークンシステムにはこれらのルールは不要。トークンは**通常の型**であり、他のすべての型と同じスコープルールに従う。

**参照の返却——自然にサポート**：

```yaoxiang
# ✅ トークンは戻り値と共に伝播
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # 子トークンと親トークンを一緒に返す
}

# 使用
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # トークンを呼び出し元に返す
print(px_ref)               # OK、トークンはまだスコープ内
```

**構造体への格納——自然にサポート**：

```yaoxiang
# ✅ 構造体はフィールドとしてトークンを保持
Window: Type = {
    target: Point,
    view: &Point,      # トークンフィールド——target への読み取りビューを保持
}

# view のトークンは target から派生、Window は両方の所有権を保持
# Window が存在する限り、view トークンは有効
```

#### 2.3 クロージャと Lambda の明示的引数

Lambda は関数値——スコープ外に戻したり、格納したり、現在のスコープ外に渡したりできる。したがって Lambdaは**外側のローカル変数を暗黙的にキャプチャしない**。外側のデータが必要な場合は、明示的な引数として渡す：

```yaoxiang
# ✅ Lambda は明示的引数を使用
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } はこのルールの影響を受けない——spawn は即座に実行される並行ブロックで、親タスクはブロックして待機する
shared = ref data
spawn { use(shared) }

# ❌ Lambda は外側の変数を暗黙的にキャプチャできない
x = 42
f = () => { x + 1 }  # コンパイルエラー：x はスコープ内にない

# ✅ 正しい方法：明示的に引数で渡す
f = (x) => { x + 1 }
f(x)

# ✅ 正しい方法その2：コンテキストを作成時点で固定（カリー化）——クロージャは引数のみを取り、キャプチャしない
gt: (t: Int) -> (x: Int) -> Bool = (x) => x > t
evens = list.filter(nums, gt(threshold))
```

> 補足（2026-08-17）：コンテキスト依存の正しい解はカリー化による固定であり、キャプチャではない。クロージャがエスケープした後、その定義箇所のスコープは死んでいる可能性があるため、暗黙的キャプチャは許されない。しかし呼び出し点（作成点）のスコープは必ず生存しており、コンテキストはその時点で値として固定されクロージャに入れば安全である。SPEC
> §12.3 を参照。

**spawn { } は関数値ではない。**
spawn でマークされたブロックは if/while 本体と同様に——即座に実行され、親スタックフレームが生存中に完了する。spawn 本体は普通に外側の変数にアクセスできる。

**タスクを跨ぐ——トークンはスレッドを越えられない**：

```yaoxiang
# ❌ トークンはタスク境界を跨げない
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ コンパイルエラー：トークンはタスクを跨いで渡せない
}

# これは特別なルールではない——トークンはコンパイル時の権限証明であり、タスクを跨ぐ共有には ref を使用すること
# タスクを跨いで共有する必要がある場合は、ref を使用すること
```

**トークンは ref できない**：

```yaoxiang
# ❌ トークンは権限証明であり、所有権ではない
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ コンパイルエラー：&T は所有可能な型ではない
}
```

#### 2.4 トークンのライフサイクル

トークンのライフサイクルは**通常のスコープルール**によって決定され、ライフタイムパラメータは不要：

- 関数の引数内のトークン：呼び出し中生存し、呼び出し終了後に解放
- 戻り値のトークン：所有権を呼び出し元に移転
- 構造体に格納されたトークン：構造体と共に生存

コンパイラは `'a`
注釈を必要としない、なぜならトークンは**値**であり、値のライフサイクルは所有権システム（Move/RAII）によって統一管理されるからだ。**借用問題を所有権問題に次元削減する。**

#### 2.5 トークン衝突検出

トークン衝突検出は**ホーア論理の命題**であり、独立したフロー依存解析ではない。

```
{衝突する ReadToken すべてが死んでいる} write(data) {WriteToken 安全に取得}
```

型検査やユーザー述語検証と RFC-027 の証明パイプラインを共有する。コンパイラが借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を自動生成し、パイプラインに送って検証する。パイプラインは Proved
/ Disproved / Unproven を返す。

```yaoxiang
# ❌ &mut トークンは線形であり、複製できない
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move、p はもう読めない
    p.x = 10.0                      # ❌ コンパイルエラー：WriteToken は既に移動済み
}

# ✅ &T トークンは Dup 型であり、自由に複製可能
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK、&T は Dup 型
    print(p.x)                      # OK
    print(p2.x)                     # OK、2つの読み取り専用トークンが共存
}
```

**借用検査は消えていない——次元が下がったのだ。** 既存の `BorrowChecker` は
`BorrowPredicateEmitter`（命題生成器）となり、生成された借用命題は他の型命題と同じ証明パイプラインを共有する。これは型検査器の概念と完全に平行する：型検査器は型等価命題を生成し、借用命題生成器は借用命題を生成し、同一のパイプラインが検証する。詳細は
[RFC-009a](../accepted/009a-borrow-proof-pipeline.md) を参照。

#### 2.7 コンパイラ内部：ブランド機構

ユーザーはブランドに一切触れない。コンパイラが内部で各トークンにコンパイル時一意識別子を割り当てる：

```
ユーザーが見るもの     コンパイラ内部表現
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #N はコンパイル時一意の整数
&mut Point     →  WriteToken(Point, #M)   // #M はコンパイル時一意の整数
```

ブランドの用途：

- **偽造防止**：トークンは所有者からのみ取得でき、凭空には生成できない
- **関連追跡**：`&Point` から `&Float`（フィールドアクセス）を派生するとき、`&Float`
  は派生ブランド（`#N.field_x`）を携带し、コンパイラは親トークンまで追跡可能
- **衝突検出**：同源の `WriteToken` と派生 `ReadToken` は同時にアクティブになれない

ブランドは単態化とインライン化後に完全に消滅し、生成される機械語には存在しない。**ランタイムオーバーヘッドはゼロ。**

#### 2.8 自動借用選択ルール

呼び出し側のコンパイラは以下の優先順位で自動選択する：

```
1. 実参の後にまだ使用がある場合 → トークン作成を優先（メソッドシグネチャに応じて &T または &mut T）
2. 実参が今後使用されない場合 → Move
3. マッチング優先順位：&T < &mut T < Move
```

```yaoxiang
# 例：自動選択
p = Point(1.0, 2.0)
p.print()        # print は &self を宣言 → コンパイラが &Point トークンを作成
p.shift(1.0, 1.0) # shift は &mut self を宣言 → コンパイラが &mut Point トークンを作成
p2 = p           # Move、p はもう使用されない
```

#### 2.9 RFC-009 v8 乞食版借用との比較

| 特性                     | 乞食版借用 (v8)                     | 借用トークン (v9)                                 |
| ------------------------ | ----------------------------------- | ------------------------------------------------- |
| 参照の返却               | ❌ ハードコードで禁止               | ✅ トークンが戻り値と共に伝播                     |
| 構造体への格納           | ❌ ハードコードで禁止               | ✅ トークンを構造体フィールドに                   |
| Lambda 明示的引数        | ❌ ハードコードで禁止               | ✅ Lambda は明示的引数を使用                      |
| 特別ルール               | 3条（引数のみ/戻り値不可/格納不可） | 0条——型属性が自然に推論                           |
| 借用検査                 | 専用の交叉借用検査                  | 型検査器のフロー依存活性分析                      |
| ライフタイム注釈         | 不要                                | 不要                                              |
| ランタイムオーバーヘッド | ゼロ                                | ゼロ（ゼロサイズ型、コンパイル後消滅）            |
| エラーメッセージ         | "借用はエスケープできない"          | "WriteToken(#3) は既に移動済み"（通常の型エラー） |
| ユーザーメンタルモデル   | "借用"の特別な地位を理解する        | `&T` は複製可能、`&mut T` は複製不可              |

### 3. ref キーワード（コンパイラによる自動最適化）

`ref` はスコープを越えて共有する唯一の方法。内部実装が Rc か Arc かをユーザーが知る必要はない。

#### 3.1 基本使用

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # 共有、コンパイラが実装を自動選択

# タスクを跨いで共有
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # コンパイラ：タスクを跨ぐ → Arc
    spawn { use(data) }           # コンパイラ：タスクを跨ぐ → Arc
}

# 単一タスクで共有
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # コンパイラ：タスクを跨がない → Rc
}
```

**ユーザーメンタルモデル**：`ref` = 共有保持。それで十分。

#### 3.2 コンパイラのエスケープ解析：Rc vs Arc

```
ref のデータフロー解析：

他のタスクにエスケープしない → Rc（非アトミック参照カウント、オーバーヘッド低）
他のタスクにエスケープする   → Arc（アトミック参照カウント、スレッドセーフ）
```

#### 3.3 環検出戦略

```
タスク内環 → 静かに許可。
  ├── 各タスクには明確なライフサイクル境界がある——タスク終了時にすべてのリソース（ref 環を含む）が統一解放される。
  ├── 長期稼働サービスはリクエスト/接続ごとに子タスクを作成すべき——子タスク終了時に自動回収され、累積リークは発生しない。
  ├── ref は常に生存し、セマンティクスは混じりけがない。
  └── ユーザーはタスク内で双方向強参照（例：グラフ計算の中間状態）を構築する権利を持つ。

タスク跨ぎ環 → lint（デフォルト warn、設定可能）。
  ├── プログラムの動作は正しく、実際にリークはしない（親タスク終了時に子タスクのリソースがすべて解放される）。
  ├── しかし、タスクを跨ぐ強参照は所有権境界が曖昧であることを意味し、立ち止まって再考する価値がある。
  ├── デフォルトは warn レベルで、コンパイルは成功するが警告が表示される。
  └── チームはプロジェクト設定で deny にでき、CI 品質ゲートに組み込める。
```

**Lint レベル**（Rust clippy に類似）：

| レベル               | 動作                               | シナリオ               |
| -------------------- | ---------------------------------- | ---------------------- |
| `allow`              | チェックしない                     | 個人プロジェクト       |
| `warn`（デフォルト） | コンパイル成功、警告あり           | 開発段階               |
| `deny`               | コンパイル失敗                     | チーム CI 品質ゲート   |
| `forbid`             | コンパイル失敗、オーバーライド不可 | 組織レベルの強制ルール |

```yaoxiang
# タスク内環：静かに許可、双方向強参照
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # 環。タスク終了時に統一解放。
}

# タスク跨ぎ環：lint（デフォルト warn）
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: タスクを跨ぐ循環参照
    }
}
```

**プロジェクト設定例**：

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # タスク跨ぎ環は CI で直接拒否
```

| 環タイプ          | 動作                    | 理由                                   |
| ----------------- | ----------------------- | -------------------------------------- |
| タスク内 ref 環   | チェックしない          | ユーザーの権限、タスク終了時に統一解放 |
| タスク跨ぎ ref 環 | lint（デフォルト warn） | 再考を促す、設定で deny 可能           |

#### 3.4 Weak：標準ライブラリで提供

```yaoxiang
use std.weak

# 上級ユーザーが明示的に選択
a.next = ref b
b.prev = std.weak.new(a.next)   # ユーザーがどの方向が弱いかを明示的に制御
```

**`Weak` は言語組み込みではなく、標準ライブラリ型である。** 日常的には `ref`
を使えば十分。メモリを細かく制御したい上級ユーザーが手動で `Weak` を導入する。

> は言語キーワードでありモジュールではない；モジュールパスは `std.weak`
> に統一され、構築/昇格エントリは `std.weak.new` / `std.weak.upgrade`）。初稿で想定していた
> `std.rc.Weak` は実装されず、本改訂を優先する。

#### 3.5 借用トークン vs ref

|            | `&T` / `&mut T`                                                      | `ref`                                   |
| ---------- | -------------------------------------------------------------------- | --------------------------------------- |
| 役割       | 覗く/その場で変更                                                    | 共有保持                                |
| 範囲       | トークン値のスコープに従う                                           | スコープを越える                        |
| コスト     | ゼロオーバーヘッド（ゼロサイズ型）                                   | Rc または Arc（コンパイラが選択）       |
| エスケープ | 可（トークンは戻り値/構造体/クロージャで伝播）                       | 元々エスケープ用に設計されている        |
| タスク跨ぎ | 不可（トークンはコンパイル時権限証明であり、タスクを跨いで渡せない） | 可（コンパイラが Arc を自動選択）       |
| 環形成     | 関与しない                                                           | タスク内は静かに許可、タスク跨ぎは lint |

### 4. clone() —— 明示的コピー

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # ディープコピー
# p と p2 は独立し、互いに影響しない
```

**使用すべき場面**：元の値を保持する必要があり、Move でも共有もしっくりこないシナリオ。

### 5. unsafe + 生ポインタ（システムレベルプログラミング）

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # 生ポインタ
    (*ptr).x = 0.0                # デリファレンス（ユーザーが安全を保証）
    ptr2 = ptr + 1                # ポインタ演算
}
```

**制限**：

- `unsafe` ブロック内でのみ使用可能
- ユーザーはダングリングや解放後使用がないことを保証する
- FFI、メモリ操作などのシステムレベルプログラミングに使用

### 6. 所有権グラデーション全体像

```
  借用トークン（ゼロコスト）     Move（ゼロコスト）      共有（必要に応じたコスト）    コピー
   │                      │                  │                │
  &T 複製可能トークン        デフォルトの所有権移転     ref Rc/Arc       clone()
  &mut T 線形トークン      チェーン消費リフロー       コンパイラ自動選択      明示的ディープコピー
   │                      │                  │                │
  トークン値スコープ内           スコープ内           スコープを越える         いつでも
  戻り値可/構造体に格納可        T -> T リフロー        ref タスク跨ぎ → Arc  独立コピー
  ゼロサイズコンパイル後消滅        T -> Void 消費       ref タスク跨ぎなし → Rc
  ゼロサイズコンパイル後消滅                          タスク内環は静かに
                                            タスク跨ぎ環は lint
                                            標準ライブラリ Weak でエスケープ
```

## 総合例

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T：読み取り専用トークン
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T：可変トークン
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move：消費してリフロー
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # 持ち去り、変更、返す
    }

    # 参照を返す：トークンが戻り値と共に伝播
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Lambda 明示的引数
double: (x: Int) -> Int = (x) => x * 2

# 総合使用
p = Point(1.0, 2.0)
p.print()                           # &Point トークン
p.shift(1.0, 1.0)                   # &mut Point トークン
p = p.scale(2.0)                    # Move → リフロー
shared = ref p                      # ref で共有
spawn { use(shared) }

# clone で独立コピー
backup = p.clone()

# タスク内環：静かに許可
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # 環、タスク終了時に統一解放

# unsafe システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## 型システム制約

### Dup 型属性

`Dup`（Duplicable）はコンパイラが自動管理する型属性であり、**シャローコピー**を意味する：代入/引数渡し時にコピーされるのはハンドル/トークンであり、底层データは共有される。これは Move（所有権移転）や Clone（明示的ディープコピーで独立コピー作成）と3段階のグラデーションを成す。

**Dup と Clone は直交する概念**——Dup はハンドルをコピーしてデータを共有し、Clone は独立コピーを作成する。1つの型が Dup と Clone の両方をサポートすることも、 片方のみをサポートすることも可能。

| 型            | Dup                                                            | Clone | 説明                                       |
| ------------- | -------------------------------------------------------------- | ----- | ------------------------------------------ |
| `&T`          | ✅（トークンをコピー、複数のビューが同じデータを指す）         | ✅    | 読み取り専用トークン                       |
| `ref T`       | ✅（参照カウント+1、ヒープデータを共有）                       | ✅    | 共有保持（コンパイラが Rc/Arc を自動選択） |
| String, Bytes | ✅（内部参照カウント、ハンドルをコピーして底层 buffer を共有） | ✅    | 文字列/バイト                              |
| `&mut T`      | ❌（線形、排他的）                                             | ❌    | 可変トークン                               |
| `*T`          | ❌                                                             | ❌    | 生ポインタ                                 |
| struct        | 派生（すべてのフィールドが Dup の場合に自動派生）              | ✅    | 構造体                                     |

**プリミティブ値型**（Int, Float, Bool,
Char）の代入動作はコンパイラ組み込みの値コピーであり、2つの値は完全に独立しており、シャローコピーではない。これらは Dup 型属性ではなく、コンパイラのネイティブ処理に属する。

## パフォーマンス分析

| 操作                    | コスト   | 説明                                                         |
| ----------------------- | -------- | ------------------------------------------------------------ |
| Move                    | ゼロ     | ポインタ移動                                                 |
| `&T` / `&mut T`         | ゼロ     | ゼロサイズ型、コンパイル後消滅、ランタイムオーバーヘッドゼロ |
| `ref`（タスク跨ぎなし） | 低       | Rc にコンパイル、非アトミック操作                            |
| `ref`（タスク跨ぎ）     | 中       | Arc にコンパイル、アトミック操作                             |
| `clone()`               | 型による | 小オブジェクトは高速、大オブジェクトは低速                   |
| `unsafe + *T`           | ゼロ     | 直接メモリ操作                                               |

### 比較

| 言語         | 共有メカニズム         | メモリ管理       | 環処理                                                     | 複雑度 |
| ------------ | ---------------------- | ---------------- | ---------------------------------------------------------- | ------ |
| Rust         | Arc / Mutex + 借用検査 | コンパイル時検査 | 手動 Weak                                                  | 高     |
| Go           | chan / pointer         | GC               | GC                                                         | 低     |
| C++          | shared_ptr             | RAII             | weak_ptr                                                   | 中     |
| **YaoXiang** | **ref + 借用トークン** | **RAII**         | **タスク境界解放 / タスク跨ぎ lint / 標準ライブラリ Weak** | **低** |

## トレードオフ

### 利点

1. **統一**：`&T`/`&mut T` は通常の型であり、特別な言語機能ではない。RFC-010 の `name: type = value`
   と完全に一致する
2. **シンプル**：ライフタイムなし、借用検査は型システム命題に次元削減。`&T` は複製可能、`&mut T`
   は複製不可——2つの型属性のみ
3. **強力**：参照の返却、構造体への格納、クロージャキャプチャが可能——表現能力は Rust と同レベル
4. **コンパイラのスマートさ**：ref が Rc/Arc を自動選択、呼び出し側が借用を自動選択
5. **決定論的**：ref は生存を保証し、密かに弱参照にはならない
6. **高性能**：Move はゼロコピー、トークンはゼロコスト（ゼロサイズ型、コンパイル後消滅）
7. **柔軟**：`unsafe + *T` でシステムレベルプログラミングをサポート

### 欠点

1. **ジェネリックブランドパラメータの伝染**：トークンはブランド識別子を携带し、参照を返す関数のシグネチャに追加のジェネリックパラメータが現れる
2. **ref のランタイムオーバーヘッド**：アトミック操作にはコストがある（ただしこれは共有の必然的な代償）
3. **unsafe のリスク**：ユーザーが正しさを保証しなければならない
4. **タスク跨ぎ環は lint でありコンパイルエラーではない**：Rust のようにコンパイルエラーとならず、デフォルトは warn であり、CI 品質ゲートとして deny を設定するにはチームの構成が必要

### トークン衝突検出：ホーア論理命題

トークン衝突検出の完全なソリューションは
[RFC-009a: トークンライフタイム解析——ホーア証明パイプラインに基づく](../accepted/009a-borrow-proof-pipeline.md)
を参照。核心：

**トークン活性はホーア論理命題である。**
`{衝突する ReadToken すべてが死んでいる} write(data) {WriteToken 安全に取得}`——型検査やユーザー述語検証と RFC-027 の証明パイプラインを共有する。コンパイラが借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を自動生成し、パイプラインが Proved
/ Disproved / Unproven を返す。

**借用検査は消えていない——次元が下がったのだ。** `BorrowChecker` は `BorrowPredicateEmitter`
となり、命題を生成し検査を実行する。これは「型検査器」の概念と完全に平行する：型検査器は型等価命題を生成し、借用命題生成器は借用命題を生成し、同一のパイプラインが検証する。

**ブランド ID（`#42`）が `'a` そのものだ。** 情報は完全に同じ、エンコーディングが異なる。`'a`
は型シグネチャで可視、`#42`
はコンパイラ内部。新しい解析を発明したのではなく、ライフタイムを型層から証明層に降ろしたのだ。

**アルゴリズム概要**（詳細は RFC-009a）：

- ブランドツリーのプレフィックス一致 → 衝突トークンの特定（O(depth)、深さ ≤ 3）
- 逆方向 BFS → 消費者から出発、break で逆辺を切断、構造解析で 95%+ のシナリオをカバー（高速パス）
- SMT 論理切断 → while + パス条件の場合のみ呼び出し（低速パス、極めて稀）
