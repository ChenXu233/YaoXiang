# RFC-009: 所有権モデル設計

## 摘要

このドキュメントはYaoXiangプログラミング言語の**所有権モデル（Ownership Model）**を定義します。

**コア設計——5つの概念、1つの梯度**：

```
ちょっと見る/その場で変更     持ち去る           共有保持         コピーを作成        システムレベル
    │              │              │              │              │
   &T            Move           ref          clone()        unsafe
  &mut T         ゼロコピー    コンパイラ自動      明示的深コピー     *T
  ゼロサイズトークン       デフォルト          Rc/Arcを選択                ユーザ責任
  型属性の自然な
  権限導出
```

- **Move（デフォルト）**：代入/引数渡/返り値 = 所有権移動、ゼロコピー、RAII自動解放
- **`&T` / `&mut T`（借用トークン）**：ゼロサイズのコンパイル時トークン型。`&T` は複製可能（共有読み取り専用）、`&mut T`
  は線形（排他的可変）。権限は型属性から自然に導出され、特殊ルールは不要。返り値可能、構造体に格納可能。
- **`ref` キーワード**：スコープ間共有。コンパイラがRc（タスクを跨がない）かArc（タスクを跨ぐ）を自動選択
- **`clone()`**：明示的深コピー
- **`unsafe` + `*T`**：裸ポインタ、システムレベル脱出ハッチ

**削減された複雑さ**：

- ❌ ライフタイム `'a` なし
- ❌ 独立した借用検査フレームワークなし（借用競合はホア命题に次元削減され、型検査と証明パイプラインを共有）
- ❌ GCなし
- ❌ 「エスケープ禁止」などの特殊ルールなし（トークンは普通の種類、スコープは型システムで統一処理）
- ❌ ユーザーがRc/Arcの違いを知る必要なし（コンパイラが自動選択）

> **プログラミング負担**：`&T` は複製可能、`&mut T` は複製不可——型の属性2つ、特殊ルール0つ、コンパイラが完全自動化。
> **パフォーマンス保証**：Moveゼロオーバーヘッド、トークンゼロオーバーヘッド（ゼロサイズ型、コンパイル後に消滅）、refはオンデマンド払い、标准GC一時停止なし。

## 動機

### なぜ所有権モデルが必要か？

| 言語         | メモリ管理               | 問題                               |
| ------------ | ---------------------- | ---------------------------------- |
| C/C++        | 手動管理               | メモリリーク、野ポインタ、二重解放         |
| Java/Python  | GC                     | 遅延波动、メモリオーバーヘッド、予測不能の一時停止 |
| Rust         | 所有権 + 借用検査      | ライフタイム `'a` 学習曲線が険しい         |
| **YaoXiang** | **Move + Token + ref** | **シンプル、决定的、GCなし**              |

### 設計目標

```yaoxiang
# 1. デフォルトMove（ゼロコピー）
p = Point(1.0, 2.0)
p2 = p                         # Move、pはこれ以上読めない

# 2. &T / &mut T借用トークン（ゼロオーバーヘッド、型属性が自然に権限を導出）
print_info(p2)                 # コンパイラが自動的に&Pointトークンを作成、使用後即解放
shift(p2, 1.0, 1.0)           # コンパイラが自動的に&mut Pointトークンを作成

# 3. ref = 共有（コンパイラが自動的にRc/Arcを選択）
shared = ref p2                # スコープを跨いで保持
spawn { use(shared) }          # コンパイラ：タスクを跨ぐ → Arc

# 4. clone() = 明示的コピー
backup = p2.clone()            # 深コピー、独占

# 5. unsafe + *T = システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Rustとのコアな違い

| 特性     | Rust                              | YaoXiang                                                  |
| -------- | --------------------------------- | --------------------------------------------------------- |
| デフォルトセマンティクス | 借用 `&T`（明示的`.clone()`必要）    | **Move（値渡し、ゼロコピー）**                                |
| 借用     | `&T`/`&mut T`、返り値可能、ライフタイム必要 | **`&T`/`&mut T`ゼロサイズトークン、Dup/Linear型属性が自然に権限を導出** |
| 共有機構 | `Arc::new()` + 手動Weak          | **`ref`キーワード（コンパイラが自動的にRc/Arcを選択）**                   |
| コピー     | `clone()`                         | `clone()`                                                 |
| 裸ポインタ   | `*T`                              | `*T`                                                      |
| ライフタイム | `'a`                              | ❌ なし                                                     |
| 借用検査 | グローバル導出                          | **型検査器が自動的に借用命題を生成、証明パイプラインが統一検証**          |
| 循環参照 | 手動Weak                         | **タスク終了で統一解放 / タスク間lint / 標準ライブラリWeak**          |

## 提案

### 1. Move（デフォルト所有権移動）

```yaoxiang
# ルール：代入 / 引数渡 / 返り値 = Move、ゼロコピー

p: Point = Point(1.0, 2.0)
p2 = p                           # Move、pはこれ以上読めない

# 変数は再代入可能（Python風、シャドウイングなし）
p = Point(3.0, 4.0)              # pは再バインド、型は一貫している必要がある

# 関数引数：Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Move返り値
}

# 関数返り値：Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Move返り値、ゼロコピー
}
```

**特徴**：

- ゼロコピー（コンパイラがポインタを移動）
- 移動後元のバインディングは読めない（コンパイルエラー）
- RAII：スコープ終了で自動解放
- 関数シグネチャ`(T) -> T`自体がドキュメント——Tを消費し、Tを返す

---

### 2. &T / &mut T（借用トークン）

**コア原則：`&T`と`&mut T`はゼロサイズのコンパイル時トークン型です。これは「参照」ではなく、「アクセス権限の型レベル証明」です。**

#### 2.1 2つの型属性

```
&T      →  ゼロサイズ、ソースデータを凍結（ReadToken生存期間中はWriteTokenを禁止）、
          凍結保証下で複数読み取り専用ビューは安全 → 複製可能（Dup）
&mut T  →  ゼロサイズ、排他的読み書き（WriteToken生存期間中は他のトークンをすべて禁止）、
          排他アクセス下でコピーは無意味 → 線形（非Dup）
```

**因果関係は逆転不可：凍結が理由で、Dupが結果。** `&T`がDupを実装しているから共存できるのではなく、データが冻结されているから（突然変異の可能性がない）、複数読み取り専用ビューが安全であり、Dupが実装できるのです。Dupを定義として、競合検査を「追加のパッチ」とするなら、設計が間違っています。

#### 2.2 基本使用

```yaoxiang
# メソッド側：引数型を宣言し、必要な権限を決定
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # &Pointトークンが読み取り権限を付与
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # &mut Pointトークンが書き込み権限を付与
    self.y = self.y + dy
}

# 呼び出し側：コンパイラが自動的に借用かMoveを選択
p = Point(1.0, 2.0)
p.print()                          # コンパイラが自動的に&Pointトークンを作成
p.shift(1.0, 1.0)                  # コンパイラが自動的に&mut Pointトークンを作成
p.print()                          # OK、前のトークンはshift呼び出し終了時に解放済み

# 自由関数も同理
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # 2つの&Pointトークンが共存——Dup型
}
d = distance(p, p2)
```

#### 2.3 なぜ「エクスポート禁止」が不要か

RFC-009 v8では`&T`/`&mut T`に3つの特殊ルールを設けていました——引数にしか使えない、返り値不可、構造体に格納不可。これは「借用」概念へのパッチ当てです。

トークンシステムではこれらのルールは不要です。トークンは**普通の種類**であり、他の型と同じスコープルールに従います。

**参照を返す——自然にサポート**：

```yaoxiang
# ✅ トークンは返り値と共に伝播
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # サブトークンとペアレントトークンが一緒に返る
}

# 使用
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # トークンが呼び出し元に返される
print(px_ref)               # OK、トークンはまだスコープ内
```

**構造体に格納——自然にサポート**：

```yaoxiang
# ✅ 構造体がトークンをフィールドとして携带
Window: Type = {
    target: Point,
    view: &Point,      # トークンフィールド——targetへの読み取り専用ビューを保持
}

# viewのトークンはtargetから派生、Windowは両方の所有権を保持
# Windowが存在する限り、viewトークンは有効
```

#### 2.3 クロージャとLambdaの明示的引数

Lambdaは関数値——返され、格納され、現在のスコープから出されることができます。因此、Lambdaは**外側ローカル変数を暗黙的にキャプチャしません**。外側データが必要な場合、明示的な引数として渡します：

```yaoxiang
# ✅ Lambdaは明示的引数を使用
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } はこのルールの影響を受けない——spawnは即座に実行される并发ブロック、親タスクがブロッキング等待
shared = ref data
spawn { use(shared) }

# ❌ Lambdaは外側変数を暗黙的にキャプチャできない
x = 42
f = () => { x + 1 }  # コンパイルエラー：xはスコープ内にない

# ✅ 正しい方法：明示的に引数を渡す
f = (x) => { x + 1 }
f(x)

# ✅ 正しい方法其二：コンテキストは作成点で固化（カリー化）——クロージャは引数のみ取り、キャプチャしない
gt: (t: Int) -> (x: Int) -> Bool = (x) => x > t
evens = list.filter(nums, gt(threshold))
```

> 補足（2026-08-17）：コンテキスト依存の正解はカリー化による固化であり、キャプチャではない。クロージャがエスケープした後、その定義處スコープが死んでいる可能性があるため、暗黙的キャプチャは不可；但し呼び出し點（作成點）スコープは必ず生存するため、コンテキストがその點で値として固化されクロージャに入るのは安全。SPEC §12.3参照。

**spawn { }は関数値ではない。** spawnがマークするblockはif/while bodyと同じように——即座に実行され、親スタックフレームが生存する間に完了する。spawn bodyは外側変数に正常にアクセスできる。

**タスクを跨ぐ——トークンは糸を通せない**：

```yaoxiang
# ❌ トークンはタスク境界を跨げない
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ コンパイルエラー：トークンはタスクを跨げない
}

# これは特殊ルールではない——トークンはコンパイル時の権限証明、タスク間共有にはrefを使用
# タスク間を跨いで共有が必要な場合はrefを使用
```

**トークンはrefにできない**：

```yaoxiang
# ❌ トークンは権限証明であり、所有権ではない
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ コンパイルエラー：&Tは所有可能的型ではない
}
```

#### 2.4 トークンのライフサイクル

トークンのライフサイクルは**通常のスコープルール**で決定され、ライフタイムパラメータは不要です：

- 関数引数内のトークン：呼び出し期間生存、呼び出し終了で解放
- 返されるトークン：所有権が呼び出し元に移動
- 構造体に格納されたトークン：構造体と共に生存

コンパイラは`'a`注釈を必要としません。なぜならトークンは**値**であり、値のライフサイクルは所有権システム（Move/RAII）で統一管理されるからです。**借用問題を所有権問題に次元削減する。**

#### 2.5 トークン競合検出

トークン競合検出は**ホア論理命題**であり、独立したフロー感受分析ではありません。

```
{競合するReadTokenがすべて死亡} write(data) {WriteTokenの安全的取得}
```

型検査、用户谓詞検証とRFC-027の証明パイプラインを共有します。コンパイラは自動的に借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を生成し、パイプラインに送って検証します。パイプラインはProved
/ Disproved / Unprovenを返します。

```yaoxiang
# ❌ &mutトークンは線形なので、コピー不可
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move、pはこれ以上読めない
    p.x = 10.0                      # ❌ コンパイルエラー：WriteTokenは既に移動済み
}

# ✅ &TトークンはDup型なので、自由に関学できる
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK、&TはDup型
    print(p.x)                      # OK
    print(p2.x)                     # OK、2つの読み取り専用トークンが共存
}
```

**借用検査は消えたのではなく、次元削減された。** 既存の`BorrowChecker`は`BorrowPredicateEmitter`（命題生成器）に変わり、生成された借用命題と他の型命題が同じ証明パイプラインを共有します。これは型検査器の概念と完全に並行しています：型検査器が型等式命題を生成し、借用命題生成器が借用命題を生成し、同じパイプラインが検証します。詳細設計は[RFC-009a](../accepted/009a-borrow-proof-pipeline.md)を参照。

#### 2.7 コンパイラ内部：ブランド機構

ユーザーはブランドに触れる必要はありません。コンパイラは内部で各トークンにコンパイル時一意識別子を割り当てます：

```
ユーザーが見るもの         コンパイラ内部表現
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #Nはコンパイル時一意の整数
&mut Point     →  WriteToken(Point, #M)   // #Mはコンパイル時一意の整数
```

ブランドの用途：

- **偽造防止**：トークンは所有者カプセルからのみ取得でき凭空構築不可
- **関連追踪**：从`&Point`から`&Float`を派生（フィールドアクセス）する際、`&Float`は派生ブランド（`#N.field_x`）を携带し、コンパイラは親トークンを追踪できる
- **競合検出**：同一来源の`WriteToken`と派生の`ReadToken`は同時に生存不可

ブランドは単態化とインライン化後に完全に消え、生成されたマシンコードには存在しません。**ゼロランタイムオーバーヘッド。**

#### 2.8 自動借用選択ルール

呼び出し側コンパイラは以下の優先順位で自動選択します：

```
1. 実引数が以降も使用される場合 → トークン作成を優先（&Tまたは&mut T、メソッドシグネチャによる）
2. 実引数が以降使用されない場合 → Move
3. 優先マッチング順序：&T < &mut T < Move
```

```yaoxiang
# 示例：自動選択
p = Point(1.0, 2.0)
p.print()        # printは&selfを宣言 → コンパイラが&Pointトークンを作成
p.shift(1.0, 1.0) # shiftは&mut selfを宣言 → コンパイラが&mut Pointトークンを作成
p2 = p           # Move、pはもう使用しない
```

#### 2.9 RFC-009 v8乞丐版借用との比較

| 特性            | 乞丐版借用 (v8)                     | 借用トークン (v9)                            |
| --------------- | --------------------------------- | ---------------------------------------- |
| 参照を返す        | ❌ ハードコードで禁止                     | ✅ トークンは返り値と共に伝播                      |
| 構造体に格納        | ❌ ハードコードで禁止                     | ✅ トークンは構造体フィールドとして                    |
| Lambda明示的引数 | ❌ ハードコードで禁止                     | ✅ Lambdaは明示的引数を使用                   |
| 特殊ルール        | 3つ（引数にしか使えない/返り値不可/格納不可） | 0つ——型属性が自然に権限を導出                    |
| 借用検査        | 専用相互借用検査                  | 型検査器のフロー感受活性分析                 |
| ライフタイム注釈    | 不要                            | 不要                                   |
| ランタイムオーバーヘッド      | ゼロ                                | ゼロ（ゼロサイズ型、コンパイル後に消滅）             |
| エラーメッセージ        | "借用はエスケープできない"                    | "WriteToken(#3)は既に移動済み"（通常の型エラー） |
| ユーザーのメンタルモデル    | "借用"の特殊地位を理解する必要があります              | `&T`は複製可能、`&mut T`は複製不可           |

### 3. refキーワード（コンパイラの自動最適化）

`ref`はスコープを跨いで共有する唯一の方法です。底层がRcかArcかは、ユーザーが気にする必要はありません。

#### 3.1 基本使用

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # 共有、コンパイラが自動的に実装を選択

# タスクを跨いで共有
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # コンパイラ：タスクを跨ぐ → Arc
    spawn { use(data) }           # コンパイラ：タスクを跨ぐ → Arc
}

# 単一タスク内で共有
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # コンパイラ：タスクを跨がない → Rc
}
```

**ユーザーのメンタルモデル**：`ref` = 共有保持。それでいい。

#### 3.2 コンパイラのエスケープ分析：Rc vs Arc

```
refのデータフロー分析：

他のタスクにエスケープしない → Rc（非原子参照カウント、低オーバーヘッド）
他のタスクにエスケープする   → Arc（原子参照カウント、スレッドセーフ）
```

#### 3.3 環検出戦略

```
タスク内環 → 黙って許可。
  ├── 各タスクには明確なライフタイム境界がある——タスク終了時にすべてのリソース（ref環を含む）が統一解放される。
  ├── 長期実行サービスはリクエスト/接続ごとに子タスクを作成すべき——子タスク終了で自動回収され、蓄積リークしない。
  ├── refは常にライブを保ち、意味論に偽りがない。
  └── ユーザーはタスク内で双方向強参照を構築する権利がある（例：グラフ計算の中間状態）。

タスク間環 → lint（デフォルトwarn、構成可能）。
  ├── プログラムの動作は正しい、本当のリークはしない（親タスク終了時に子タスクリソースがすべて解放される）。
  ├── しかしタスク間強参照は所有権境界が曖昧であることを意味し、一度立ち止まって再考する価値がある。
  ├── デフォルトwarnレベル、コンパイル成功だがヒントがある。
  └── チームはプロジェクト構成でdenyに設定でき、CI品質ゲートに組み込める。
```

**Lintレベル**（Rust clippyに類似）：

| レベル           | 動作               | シナリオ           |
| -------------- | ------------------ | -------------- |
| `allow`        | 検査しない             | 個人プロジェクト       |
| `warn`（デフォルト） | コンパイル成功、ヒントあり   | 開発段階       |
| `deny`         | コンパイル失敗           | チームCI品質ゲート |
| `forbid`       | コンパイル失敗、上書き不可 | 組織レベル強制ルール |

```yaoxiang
# タスク内環：黙って許可、双方向強参照
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # 環。タスク終了時に統一解放。
}

# タスク間環：lint（デフォルトwarn）
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: タスク間循環参照
    }
}
```

**プロジェクト設定例**：

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # タスク間環はCI上で直接拒否
```

| 環タイプ        | 動作              | 原因                         |
| ------------- | ----------------- | ---------------------------- |
| タスク内ref環 | 検査しない          | ユーザーの権限、タスク終了で統一解放 |
| タスク間ref環 | lint（デフォルトwarn） | 再考を促唆、denyに構成可能    |

#### 3.4 Weak：標準ライブラリ提供

```yaoxiang
use std.weak

# 上級ユーザーが明示的に選択
a.next = ref b
b.prev = std.weak.new(a.next)   # ユーザーがどの方向を弱くするか明示的に制御
```

**`Weak`は言語組み込みではなく、標準ライブラリ型です。** 日常的には`ref`だけで十分です。メモリを精密に制御したい上級ユーザーは手動で`Weak`を導入します。

> 2026-08-03改訂：独立した`std.weak`モジュールとして実装（`std.rc`は存在しない——`ref`は言語キーワード而非モジュール；
> モジュールパスは統一して`std.weak`、構築/アップグレード入口は`std.weak.new` / `std.weak.upgrade`）。
> 初稿で设想した`std.rc.Weak`は実現されず、本改訂を正とする。

#### 3.5 借用トークン vs ref

|        | `&T` / `&mut T`                              | `ref`                       |
| ------ | -------------------------------------------- | --------------------------- |
| 何をするか | ちょっと見る/その場で変更                                | 共有保持                    |
| 範囲   | トークン値のスコープに伴随                             | スコープを跨ぐ                    |
| コスト   | ゼロオーバーヘッド（ゼロサイズ型）                         | RcまたはArc（コンパイラ選択）       |
| エスケープ   | 可能（トークンは返り値/構造体/クロージャと共に伝播）           | そもそもエスケープするためのもの          |
| タスクを跨ぐ | 不可（トークンはコンパイル時の権限証明、タスクを跨げない） | 可（コンパイラが自動的にArcを選択）      |
| 環形成   | 関係なし                                       | タスク内は無視、タスク間をlint |

### 4. clone() —— 明示的コピー

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # 深コピー
# pとp2は独立，互相不影響
```

**いつ使うか**：元の値を保持する必要があり、Moveも共有も適さないシナリオ。

### 5. unsafe + 裸ポインタ（システムレベルプログラミング）

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # 裸ポインタ
    (*ptr).x = 0.0                # 逆参照（ユーザーが安全を保証）
    ptr2 = ptr + 1                # ポインタ演算
}
```

**制限**：

- `unsafe`ブロック内でのみ使用可能
- ユーザーはダングリング、使用後解放しないことを保証しない
- FFI、メモリ操作などシステムレベルプログラミングに使用

### 6. 所有権梯度総覧

```
  借用トークン（ゼロオーバーヘッド）     Move（ゼロオーバーヘッド）      共有（オンデマンド払い）    コピー
   │                      │                  │                │
  &T 複製可能トークン        デフォルト所有権移動     ref Rc/Arc       clone()
  &mut T 線形トークン      チェーン消費回流       コンパイラ自動選択      明示的深コピー
   │                      │                  │                │
  トークン値スコープ           スコープ内           スコープを跨ぐ         いつでも
  返り値/構造体格納可能        T -> T 回流        ref タスクを跨ぐ → Arc  独立コピー
  ゼロサイズコンパイル後に消滅        T -> Void 消費     ref タスクを跨がない → Rc
  ゼロサイズコンパイル後に消滅                          タスク内環は無視
                                            タスク間環はlint
                                            標準ライブラリWeak脱出
```

## 総合示例

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T：読み取り専用トークン
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T：可変トークン
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move：消費回流
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # 持ち去り、変更して、戻す
    }

    # 参照を返す：トークンは返り値と共に伝播
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Lambda 明示的引数
double: (x: Int) -> Int = (x) => x * 2

# 総合使用
p = Point(1.0, 2.0)
p.print()                           # &Pointトークン
p.shift(1.0, 1.0)                   # &mut Pointトークン
p = p.scale(2.0)                    # Move → 回流
shared = ref p                      # ref共有
spawn { use(shared) }

# clone 独立コピー
backup = p.clone()

# タスク内環：黙って許可
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # 環、タスク終了時に統一解放

# unsafe システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## 型システム制約

### Dup型属性

`Dup`（Duplicable）はコンパイラが自動管理する型属性で、意味は**シャローコピー**：代入/引数渡時にコピーするのはハンドラ/トークンで、底层データは共有します。これはMove（所有権移動）やClone（明示的深コピー、独立コピーを作成）とは異なる3段階梯度をなします。

**DupとCloneは直交する概念**——Dupはハンドラをコピーしてデータを共有し、Cloneは独立コピーを作成します。ある型はDupとCloneの両方をサポートすることも、片方のみサポートすることもできます。

| 型          | Dup                                         | Clone | 説明                            |
| ------------- | ------------------------------------------- | ----- | ------------------------------- |
| `&T`          | ✅（トークンをコピー、複数ビューが同じデータを指す）        | ✅    | 読み取り専用トークン                        |
| `ref T`       | ✅（参照カウント+1、共有ヒープデータ）                | ✅    | 共有保持（コンパイラが自動的にRc/Arcを選択） |
| String, Bytes | ✅（内部参照カウント、ハンドラをコピーして底层bufferを共有） | ✅    | 文字列/バイト                     |
| `&mut T`      | ❌（線形、排他）                            | ❌    | 可変トークン                        |
| `*T`          | ❌                                          | ❌    | 裸ポインタ                          |
| struct        | 派生（すべてのフィールドがDupの場合自動派生）         | ✅    | 構造体                          |

**原語値型**（Int, Float, Bool,
Char）の代入動作はコンパイラが組み込みで値コピー——2つの値が完全に独立しており、シャローコピーではありません。これらはDup型属性には屬さず、コンパイラのネイティブ処理です。

## パフォーマンス分析

| 操作              | コスト   | 説明                                 |
| ----------------- | ------ | ------------------------------------ |
| Move              | ゼロ     | ポインタ移動                             |
| `&T` / `&mut T`   | ゼロ     | ゼロサイズ型、コンパイル後に消滅、ゼロランタイムオーバーヘッド |
| `ref`（タスクを跨がない） | 低     | Rcにコンパイル、非原子操作                |
| `ref`（タスクを跨ぐ）   | 中     | Arcにコンパイル、原子操作                 |
| `clone()`         | 型による | 小さいオブジェクトは速い、大きいオブジェクトは遅い                   |
| `unsafe + *T`     | ゼロ     | 直接メモリ操作                             |

| Rust         | Arc / Mutex + 借用検査 | コンパイル時検査 | 手動Weak                                    | 高     | |
| Go           | chan / pointer         | GC         | GC                                           | 低     | |
| C++          | shared_ptr             | RAII       | weak_ptr                                     | 中     | |

## トレードオフ

### メリット

1. **統一**：`&T`/`&mut T`は普通の種類であり、特殊言語機能ではない。RFC-010の`name: type = value`と完全に一致
2. **シンプル**：ライフタイムなし、借用検査は型システム命題に次元削減。`&T`は複製可能、`&mut T`は複製不可——型の属性2つ
3. **強力**：参照を返す、構造体に格納する、クロージャがキャプチャする——Rustと同等の表現力
4. **コンパイラ知能**：refが自動的にRc/Arcを選択、呼び出し側で自動的に借用を選択
5. **確定的**：refは常にライブを保ち、そっとWeak参照に変わらない
6. **高性能**：Moveゼロコピー、トークンゼロオーバーヘッド（ゼロサイズ型、コンパイル後に消滅）
7. **柔軟**：`unsafe + *T`がシステムレベルプログラミングをサポート

### デメリット

1. **泛形ブランドパラメータ伝染**：トークンはブランド識別子を携带し、参照を返す関数シグネチャに追加の泛形パラメータが体现される
2. **refランタイムオーバーヘッド**：原子操作にはコストがある（しかしこれは共有の必然的代償）
3. **unsafeリスク**：ユーザーは正確性を保証する必要がある
4. **タスク間環はlint而非コンパイルエラー**：Rust那样にコンパイルエラーとはならない、デフォルトwarn、チームがdenyを構成しないと品質ゲートにならない

### トークン競合検出：ホア論理命題

トークン競合検出の完全方案は[RFC-009a: トークンライフ期分析——ホア証明パイプラインに基づく](../accepted/009a-borrow-proof-pipeline.md)を参照。核心ポイント：

**トークン活性はホア論理命題です。**
`{競合するReadTokenがすべて死亡} write(data) {WriteTokenが安全的に取得}`——型検査、ユーザー谓詞検証とRFC-027の証明パイプラインを共有。コンパイラは自動的に借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を生成し、パイプラインはProved
/ Disproved / Unprovenを返す。

**借用検査は消えたのではなく、次元削減された。** `BorrowChecker`は`BorrowPredicateEmitter`に変わり、检查ではなく命題を生成する。これは「型検査器」の概念と完全に並行している：型検査器が型等式命題を生成し、借用命題生成器が借用命題を生成し、同じパイプラインが検証する。

**ブランドID（`#42`）こそが`'a`です。** 情報は完全に同じで、エンコーディングが異なる。`'a`は型シグネチャで見える、`#42`はコンパイラ内部にある。新しい分析を発明したのではなく、ライフタイムを型層から証明層に座次削減したのだ。

**アルゴリズム概要**（詳細RFC-009a参照）：

- ブランドツリー前方一致マッチング → 競合トークンの確定（O(depth)、深さ ≤ 3）
- 逆方向BFS → 消費者から出発、breakがバックエッジを切断、構造分析は95%+シナリオをカバー（ファーストパス）
- SMT論理切断 → while + パス条件がある場合のみ呼び出し（スローウォール、非常にまれ）
