# RFC-009: 所有権モデル設計

## 要約

本文書はYaoXiangプログラミング言語の**所有権モデル（Ownership Model）**を定義する。

**コア設計——五つの概念、一つのグラデーション**：

```
覗く/その場で変更   奪う        共有保持      複製する        システムレベル
    │              │              │              │              │
   &T            Move           ref          clone()        unsafe
  &mut T         ゼロコピー      コンパイラが   明示的な       *T
  ゼロサイズ     デフォルト    自動でRc/Arc   ディープコピー  ユーザー責任
  トークン                      を選択
  型属性から
  自然に権限
  導出
```

- **Move（デフォルト）**：代入/引数渡し/戻り値 = 所有権移転、ゼロコピー、RAII自動解放
- **`&T` /
  `&mut T`（借用トークン）**：ゼロサイズのコンパイル時トークン型。`&T`は複製可能（共有読み取り）、`&mut T`は線形（排他的書き込み）。権限は型属性から自然に導出され、特別なルールは不要。戻り値や構造体への保存も可能。
- **`ref`キーワード**：スコープを跨いで共有。コンパイラが自動でRc（タスクを跨がない）かArc（タスクを跨ぐ）を選択
- **`clone()`**：明示的なディープコピー
- **`unsafe` + `*T`**：生ポインタ、システムレベルのエスケープハッチ

**取り除かれた複雑さ**：

- ❌ ライフタイム`'a`なし
- ❌ 独立した借用検査フレームワークなし（借用衝突はホーア命題に次元削減、型検査と証明パイプラインを共有）
- ❌ GCなし
- ❌「エスケープ禁止」などの特殊ルールなし（トークンは通常の型、スコープは型システムで統一処理）
- ❌ ユーザーはRc/Arcの区別を知る必要がない（コンパイラが自動選択）

> **プログラミング負担**：`&T`は複製可能、`&mut T`は複製不可——二つの型属性、ゼロの特殊ルール、コンパイラ完全自動。
> **パフォーマンス保証**：Moveはゼロコスト、トークンはゼロコスト（ゼロサイズ型、コンパイル後に消滅）、refは必要な時だけコスト、GCの一時停止なし。

## 動機

### なぜ所有権モデルが必要か？

| 言語         | メモリ管理             | 問題                                                 |
| ------------ | ---------------------- | ---------------------------------------------------- |
| C/C++        | 手動管理               | メモリリーク、ダングリングポインタ、二重解放         |
| Java/Python  | GC                     | レイテンシ変動、メモリオーバーヘッド、予測不能な停止 |
| Rust         | 所有権 + 借用検査      | ライフタイム`'a`の学習曲線が急峻                     |
| **YaoXiang** | **Move + Token + ref** | **シンプル、決定的、GCなし**                         |

### 設計目標

```yaoxiang
# 1. デフォルトはMove（ゼロコピー）
p = Point(1.0, 2.0)
p2 = p                         # Move、pはこれ以上読めない

# 2. &T / &mut T 借用トークン（ゼロコスト、型属性から自然に権限導出）
print_info(p2)                 # コンパイラが自動で&Pointトークンを作成、使い終わったら解放
shift(p2, 1.0, 1.0)           # コンパイラが自動で&mut Pointトークンを作成

# 3. ref = 共有（コンパイラが自動でRc/Arcを選択）
shared = ref p2                # スコープを跨いで保持
spawn { use(shared) }          # コンパイラ：タスクを跨ぐ → Arc

# 4. clone() = 明示的コピー
backup = p2.clone()            # ディープコピー、独自所有

# 5. unsafe + *T = システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Rustとの核心的な違い

| 機能                     | Rust                                        | YaoXiang                                                            |
| ------------------------ | ------------------------------------------- | ------------------------------------------------------------------- |
| デフォルトセマンティクス | 借用`&T`（明示的な`.clone()`が必要）        | **Move（値渡し、ゼロコピー）**                                      |
| 借用                     | `&T`/`&mut T`、戻り値可能、ライフタイム必要 | **`&T`/`&mut T`ゼロサイズトークン、Dup/Linear型属性から自然に導出** |
| 共有メカニズム           | `Arc::new()` + 手動Weak                     | **`ref`キーワード（コンパイラが自動でRc/Arcを選択）**               |
| コピー                   | `clone()`                                   | `clone()`                                                           |
| 生ポインタ               | `*T`                                        | `*T`                                                                |
| ライフタイム             | `'a`                                        | ❌ なし                                                             |
| 借用検査                 | グローバルに導出                            | **型検査器が自動で借用命題を生成、証明パイプラインで統一検証**      |
| 循環参照                 | 手動Weak                                    | **タスク終了時に統一解放 / タスク跨ぎはlint / 標準ライブラリWeak**  |

## 提案

### 1. Move（デフォルトの所有権移転）

```yaoxiang
# ルール：代入 / 引数渡し / 戻り値 = Move、ゼロコピー

p: Point = Point(1.0, 2.0)
p2 = p                           # Move、pはこれ以上読めない

# 変数は再代入可能（Pythonスタイル、シャドウイングなし）
p = Point(3.0, 4.0)              # pを再バインド、型は一貫している必要あり

# 関数引数：Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Moveで返す
}

# 関数の戻り値：Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Moveで返す、ゼロコピー
}
```

**特徴**：

- ゼロコピー（コンパイラがポインタを移動）
- 移動後、元のバインディングは読み取り不可（コンパイルエラー）
- RAII：スコープ終了時に自動解放
- 関数シグネチャ`(T) -> T`自体がドキュメント——Tを消費、Tを返す

---

### 2. &T / &mut T（借用トークン）

**核心原則：`&T`と`&mut T`
はゼロサイズのコンパイル時トークン型である。これらは「参照」ではなく、「アクセス権限の型レベル証明」である。**

#### 2.1 二つの型属性

```
&T      →  ゼロサイズ、元データを凍結（ReadToken生存中はWriteToken禁止）、
          凍結保証により複数の読み取り専用ビューが安全 → 複製可能（Dup）
&mut T  →  ゼロサイズ、排他的読み書き（WriteToken生存中は他のトークンすべて禁止）、
          排他的アクセス下では複製が無意味 → 線形（非Dup）
```

**因果関係は逆転不可：凍結が原因、Dupが結果。**
`&T`がDupを実装しているから共存できる——のではない。データが凍結されている（変異可能性がない）ため、複数の読み取り専用ビューが安全であり、Dupが実現できる。Dupを定義とし、衝突検査を「追加のパッチ」と考えると、設計を誤る。

#### 2.2 基本的な使用法

```yaoxiang
# メソッド側：引数型を宣言し、必要な権限を決定
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # &Pointトークンが読み取り権限を付与
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # &mut Pointトークンが書き込み権限を付与
    self.y = self.y + dy
}

# 呼び出し側：コンパイラが自動で借用またはMoveを選択
p = Point(1.0, 2.0)
p.print()                          # コンパイラが自動で&Pointトークンを作成
p.shift(1.0, 1.0)                  # コンパイラが自動で&mut Pointトークンを作成
p.print()                          # OK、前のトークンはshift呼び出し終了と共に解放済み

# 自由関数も同様
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # 二つの&Pointトークンが共存——Dup型
}
d = distance(p, p2)
```

#### 2.3 なぜ「エスケープ禁止」が不要か

RFC-009
v8は`&T`/`&mut T`に三つの特殊ルールを課した——引数にのみ使用可、戻り値不可、構造体に保存不可。これは「借用」概念にパッチを当てていた。

トークンシステムにはこれらのルールは不要。トークンは**通常の型**であり、他のすべての型と同じスコープルールに従う。

**参照を返す——自然にサポート**：

```yaoxiang
# ✅ トークンは戻り値と共に伝播
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # 子トークンと親トークンを一緒に返す
}

# 使用
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # トークンが呼び出し元に返される
print(px_ref)               # OK、トークンはまだスコープ内
```

**構造体に保存——自然にサポート**：

```yaoxiang
# ✅ 構造体がトークンをフィールドとして保持
Window: Type = {
    target: Point,
    view: &Point,      # トークンフィールド——targetへの読み取り専用ビューを保持
}

# viewのトークンはtargetから派生、Windowは両方の所有権を保持
# Windowが存在する限り、viewトークンは有効
```

#### 2.3 クロージャとラムダの明示的引数

ラムダは関数値——現在のスコープ外に戻したり、保存したり、渡したりできる。したがってラムダは
**外側のローカル変数を暗黙的にキャプチャしない**。外側のデータが必要な場合は、明示的な引数として渡す：

```yaoxiang
# ✅ ラムダは明示的な引数を使用
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { }はこのルールの影響を受けない——spawnは即座に実行される並行ブロック、親タスクはブロックして待機
shared = ref data
spawn { use(shared) }

# ❌ ラムダは外側の変数を暗黙的にキャプチャできない
x = 42
f = () => { x + 1 }  # コンパイルエラー：xはスコープ内にない

# ✅ 正しい方法：明示的に引数で渡す
f = (x) => { x + 1 }
f(x)
```

**spawn { }は関数値ではない。** spawnでマークされたブロックはif/while
bodyと同じ——即座に実行され、親スタックフレームが生存中に完了する。spawn
bodyは外側の変数に通常通りアクセスできる。

**タスクを跨ぐ——トークンはスレッドを通過できない**：

```yaoxiang
# ❌ トークンはタスク境界を跨げない
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ コンパイルエラー：トークンはタスクを跨いで渡せない
}

# これは特殊ルールではない——トークンはコンパイル時の権限証明、タスクを跨ぐ共有はrefを使用
# タスクを跨ぐ共有が必要な場合は、refを使用
```

**トークンはrefできない**：

```yaoxiang
# ❌ トークンは権限証明であり、所有権ではない
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ コンパイルエラー：&Tは所有可能な型ではない
}
```

#### 2.4 トークンのライフタイム

トークンのライフタイムは**通常のスコープルール**によって決定され、ライフタイムパラメータは不要：

- 関数引数内のトークン：呼び出し中生存、呼び出し終了後に解放
- 返されるトークン：所有権を呼び出し元に移転
- 構造体に保存されたトークン：構造体と共に生存

コンパイラは`'a`
アノテーションを必要としない。トークンは**値**であり、値のライフタイムは所有権システム（Move/RAII）で統一管理される。**借用問題を所有権問題に次元削減。**

#### 2.5 トークン衝突検出

トークン衝突検出は**ホーア論理命題**であり、独立したフロー敏感解析ではない。

```
{衝突するReadTokenがすべて死亡} write(data) {WriteTokenが安全に取得される}
```

型検査やユーザー述語検証とRFC-027の証明パイプラインを共有。コンパイラが借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を自動生成し、パイプラインに送って検証する。パイプラインはProved
/ Disproved / Unprovenを返す。

```yaoxiang
# ❌ &mutトークンは線形であり、複製できない
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move、pはこれ以上読めない
    p.x = 10.0                      # ❌ コンパイルエラー：WriteTokenは既に移動済み
}

# ✅ &TトークンはDup型、自由に複製可能
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK、&TはDup型
    print(p.x)                      # OK
    print(p2.x)                     # OK、二つの読み取り専用トークンが共存
}
```

**借用検査は消えていない——次元削減されたのだ。** 既存の`BorrowChecker`は
`BorrowPredicateEmitter`（命題生成器）となり、生成された借用命題は他の型命題と同じ証明パイプラインを共有する。これは型検査器の概念と完全に平行：型検査器は型等価命題を生成し、借用命題生成器は借用命題を生成し、同じパイプラインで検証される。詳細は
[RFC-009a](../accepted/009a-borrow-proof-pipeline.md)を参照。

#### 2.7 コンパイラ内部：ブランド機構

ユーザーはブランドに決して触れない。コンパイラが内部で各トークンにコンパイル時一意識別子を割り当てる：

```
ユーザーが見るもの    コンパイラ内部表現
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #Nはコンパイル時一意整数
&mut Point     →  WriteToken(Point, #M)   // #Mはコンパイル時一意整数
```

ブランドの用途：

- **偽造防止**：トークンは所有者カプセルからのみ取得可能、凭空には構築できない
- **関連追跡**：`&Point`から`&Float`（フィールドアクセス）を派生する際、`&Float`
  は派生ブランド（`#N.field_x`）を携带し、コンパイラが親トークンまで追跡可能
- **衝突検出**：同源の`WriteToken`と派生`ReadToken`は同時にアクティブになれない

ブランドは単態化とインライン化後に完全に消滅し、生成される機械語には存在しない。**ランタイムオーバーヘッドゼロ。**

#### 2.8 自動借用選択ルール

呼び出し側コンパイラは以下の優先順位で自動選択する：

```
1. 実引数が後に使用される場合 → トークン作成を優先（メソッドシグネチャに応じて&Tまたは&mut T）
2. 実引数が後に使用されない場合 → Move
3. 優先マッチング順序：&T < &mut T < Move
```

```yaoxiang
# 例：自動選択
p = Point(1.0, 2.0)
p.print()        # printが&selfを宣言 → コンパイラが&Pointトークンを作成
p.shift(1.0, 1.0) # shiftが&mut selfを宣言 → コンパイラが&mut Pointトークンを作成
p2 = p           # Move、pは使用されない
```

#### 2.9 RFC-009 v8 簡素化借用との比較

| 機能                       | 簡素化借用 (v8)                     | 借用トークン (v9)                              |
| -------------------------- | ----------------------------------- | ---------------------------------------------- |
| 参照を返す                 | ❌ ハードコードで禁止               | ✅ トークンは戻り値と共に伝播                  |
| 構造体に保存               | ❌ ハードコードで禁止               | ✅ トークンを構造体フィールドに                |
| ラムダの明示的引数         | ❌ ハードコードで禁止               | ✅ ラムダは明示的引数を使用                    |
| 特殊ルール                 | 3つ（引数のみ/戻り値不可/保存不可） | 0つ——型属性から自然に導出                      |
| 借用検査                   | 専用の交差借用検査                  | 型検査器のフロー敏感活性分析                   |
| ライフタイムアノテーション | 不要                                | 不要                                           |
| ランタイムオーバーヘッド   | ゼロ                                | ゼロ（ゼロサイズ型、コンパイル後に消滅）       |
| エラーメッセージ           | 「借用はエスケープできない」        | 「WriteToken(#3)は移動済み」（通常の型エラー） |
| ユーザーのメンタルモデル   | 「借用」の特殊地位を理解            | `&T`は複製可能、`&mut T`は複製不可             |

### 3. refキーワード（コンパイラの自動最適化）

`ref`はスコープを跨いで共有する唯一の方法。内部実装がRcかArcか、ユーザーは気にする必要がない。

#### 3.1 基本的な使用法

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # 共有、コンパイラが自動で実装を選択

# タスクを跨ぐ共有
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # コンパイラ：タスクを跨ぐ → Arc
    spawn { use(data) }           # コンパイラ：タスクを跨ぐ → Arc
}

# 単一タスク共有
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # コンパイラ：タスクを跨がない → Rc
}
```

**ユーザーのメンタルモデル**：`ref` = 共有保持。それで十分。

#### 3.2 コンパイラのエスケープ解析：Rc vs Arc

```
refのデータフロー解析：

他のタスクにエスケープしない → Rc（非アトミック参照カウント、低オーバーヘッド）
他のタスクにエスケープ     → Arc（アトミック参照カウント、スレッドセーフ）
```

#### 3.3 循環検出戦略

```
タスク内循環 → 静かに許可。
  ├── 各タスクには明確なライフタイム境界がある——タスク終了時、すべてのリソース（ref循環を含む）が統一解放される。
  ├── 長期実行サービスはリクエスト/接続ごとに子タスクを作成すべき——子タスク終了時に自動回収され、累積リークしない。
  ├── refは常に生存し、セマンティクスは混じりけがない。
  └── ユーザーはタスク内で双方向強参照を構築する権限を持つ（例：グラフ計算の中間状態）。

タスク跨ぎ循環 → lint（デフォルトはwarn、設定可能）。
  ├── プログラムの動作は正しく、実際にリークはしない（親タスク終了時に子タスクのリソースがすべて解放される）。
  ├── しかしタスク跨ぎの強参照は所有権境界が曖昧であることを意味し、立ち止まって再考する価値がある。
  ├── デフォルトはwarnレベル、コンパイルは通るがヒントが表示される。
  └── チームはプロジェクト設定でdenyに設定し、CI品質ゲートに組み込める。
```

**Lintレベル**（Rust clippyと同様）：

| レベル               | 動作                       | シナリオ               |
| -------------------- | -------------------------- | ---------------------- |
| `allow`              | チェックしない             | 個人プロジェクト       |
| `warn`（デフォルト） | コンパイル通過、ヒントあり | 開発段階               |
| `deny`               | コンパイル失敗             | チームCI品質ゲート     |
| `forbid`             | コンパイル失敗、上書き不可 | 組織レベルの強制ルール |

```yaoxiang
# タスク内循環：静かに許可、双方向強参照
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # 循環。タスク終了時に統一解放。
}

# タスク跨ぎ循環：lint（デフォルトはwarn）
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: タスク跨ぎ循環参照
    }
}
```

**プロジェクト設定例**：

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # タスク跨ぎ循環はCIで直接拒否
```

| 循環タイプ        | 動作                     | 理由                                   |
| ----------------- | ------------------------ | -------------------------------------- |
| タスク内ref循環   | チェックしない           | ユーザーの権限、タスク終了時に統一解放 |
| タスク跨ぎref循環 | lint（デフォルトはwarn） | 再考を促す、設定でdeny可能             |

#### 3.4 Weak：標準ライブラリ提供

```yaoxiang
use std.weak

# 上級ユーザーが明示的に選択
a.next = ref b
b.prev = std.weak.new(a.next)   # ユーザーが明示的にどの方向を弱くするかを制御
```

**`Weak`は言語組み込みではなく、標準ライブラリ型である。**
日常的には`ref`で十分。メモリを細かく制御したい上級ユーザーが手動で `Weak`を導入する。

> 2026-08-03 改訂：独立した`std.weak`モジュールとして実装（`std.rc`は存在しない——`ref`は言語キーワードでありモジュールではない；モジュールパスは`std.weak`に統一、構築/昇格エントリは`std.weak.new`
> / `std.weak.upgrade`）。初稿で想定していた`std.rc.Weak`は未実装、本改訂を優先する。

#### 3.5 借用トークン vs ref

|            | `&T` / `&mut T`                                                | `ref`                                  |
| ---------- | -------------------------------------------------------------- | -------------------------------------- |
| 機能       | 覗く/その場で変更                                              | 共有保持                               |
| 範囲       | トークン値のスコープに従う                                     | スコープを跨ぐ                         |
| コスト     | ゼロコスト（ゼロサイズ型）                                     | RcまたはArc（コンパイラが選択）        |
| エスケープ | 可（トークンは戻り値/構造体/クロージャで伝播）                 | 元々エスケープ用                       |
| タスク跨ぎ | 不可（トークンはコンパイル時権限証明、タスクを跨いで渡せない） | 可（コンパイラが自動でArcを選択）      |
| 循環形成   | 関与しない                                                     | タスク内は静かに許可、タスク跨ぎはlint |

### 4. clone() —— 明示的コピー

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # ディープコピー
# pとp2は独立しており、相互に影響しない
```

**使用時期**：元の値を保持する必要があり、Moveや共有が適さないシナリオ。

### 5. unsafe + 生ポインタ（システムレベルプログラミング）

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # 生ポインタ
    (*ptr).x = 0.0                # 逆参照（ユーザーが安全性を保証）
    ptr2 = ptr + 1                # ポインタ演算
}
```

**制限**：

- `unsafe`ブロック内でのみ使用可能
- ユーザーはダングリングなし、使用後の解放なしを保証
- FFI、メモリ操作などのシステムレベルプログラミングに使用

### 6. 所有権グラデーション概要

```
  借用トークン（ゼロコスト）     Move（ゼロコスト）      共有（必要時のみコスト）    コピー
   │                      │                  │                │
  &T 複製可能トークン        デフォルト所有権移転     ref Rc/Arc       clone()
  &mut T 線形トークン      チェーン消費戻り       コンパイラ自動選択    明示的ディープコピー
   │                      │                  │                │
  トークン値スコープ           スコープ内           スコープを跨ぐ         いつでも
  戻り値/構造体保存可        T -> T 戻り        ref タスク跨ぎ → Arc  独立コピー
  ゼロサイズコンパイル後消滅        T -> Void 消費     ref タスク跨なし → Rc
  ゼロサイズコンパイル後消滅                          タスク内循環静かに許可
                                            タスク跨ぎ循環lint
                                            標準ライブラリWeakで脱出
```

## 包括的例

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T：読み取り専用トークン
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T：可変トークン
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move：消費して戻る
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # 奪って、変更して、返す
    }

    # 参照を返す：トークンは戻り値と共に伝播
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# ラムダの明示的引数
double: (x: Int) -> Int = (x) => x * 2

# 包括的な使用
p = Point(1.0, 2.0)
p.print()                           # &Pointトークン
p.shift(1.0, 1.0)                   # &mut Pointトークン
p = p.scale(2.0)                    # Move → 戻る
shared = ref p                      # ref共有
spawn { use(shared) }

# clone独立コピー
backup = p.clone()

# タスク内循環：静かに許可
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # 循環、タスク終了時に統一解放

# unsafeシステムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## 型システム制約

### Dup型属性

`Dup`（Duplicable）はコンパイラが自動管理する型属性であり、意味は**シャローコピー**である：代入/引数渡し時にはハンドル/トークンがコピーされ、基盤データは共有される。これはMove（所有権移転）およびClone（明示的ディープコピー、独立コピー作成）と三段階のグラデーションを形成する。

**DupとCloneは直交する概念**——Dupはハンドルをコピーしてデータを共有、Cloneは独立コピーを作成。一つの型がDupとCloneの両方をサポートすることも、 하나만
지원할 수도 있다。

| 型            | Dup                                                    | Clone | 説明                                       |
| ------------- | ------------------------------------------------------ | ----- | ------------------------------------------ |
| `&T`          | ✅（トークン複製、複数のビューが同じデータを指す）     | ✅    | 読み取り専用トークン                       |
| `ref T`       | ✅（参照カウント+1、ヒープデータを共有）               | ✅    | 共有保持（コンパイラが自動でRc/Arcを選択） |
| String, Bytes | ✅（内部参照カウント、ハンドル共有で基盤bufferを共有） | ✅    | 文字列/バイト                              |
| `&mut T`      | ❌（線形、排他的）                                     | ❌    | 可変トークン                               |
| `*T`          | ❌                                                     | ❌    | 生ポインタ                                 |
| struct        | 派生（すべてのフィールドがDupの場合に自動派生）        | ✅    | 構造体                                     |

**プリミティブ値型**（Int, Float, Bool,
Char）の代入動作はコンパイラ内蔵の値複製——二つの値は完全に独立しており、シャローコピーではない。これらはDup型属性には属さず、コンパイラのネイティブ処理である。

## パフォーマンス分析

| 操作                    | コスト   | 説明                                                         |
| ----------------------- | -------- | ------------------------------------------------------------ |
| Move                    | ゼロ     | ポインタ移動                                                 |
| `&T` / `&mut T`         | ゼロ     | ゼロサイズ型、コンパイル後消滅、ランタイムオーバーヘッドゼロ |
| `ref`（タスク跨ぎなし） | 低       | Rcにコンパイル、非アトミック操作                             |
| `ref`（タスク跨ぎ）     | 中       | Arcにコンパイル、アトミック操作                              |
| `clone()`               | 型による | 小オブジェクトは高速、大オブジェクトは低速                   |
| `unsafe + *T`           | ゼロ     | 直接メモリ操作                                               |

### 比較

| 言語         | 共有メカニズム         | メモリ管理       | 循環処理                                                 | 複雑度 |
| ------------ | ---------------------- | ---------------- | -------------------------------------------------------- | ------ |
| Rust         | Arc / Mutex + 借用検査 | コンパイル時検査 | 手動Weak                                                 | 高     |
| Go           | chan / pointer         | GC               | GC                                                       | 低     |
| C++          | shared_ptr             | RAII             | weak_ptr                                                 | 中     |
| **YaoXiang** | **ref + 借用トークン** | **RAII**         | **タスク境界解放 / タスク跨ぎlint / 標準ライブラリWeak** | **低** |

## トレードオフ

### 利点

1. **統一**：`&T`/`&mut T`は通常の型であり、特殊な言語機能ではない。RFC-010の`name: type = value`と完全に一致
2. **シンプル**：ライフタイムなし、借用検査は型システム命題に次元削減。`&T`は複製可能、`&mut T`は複製不可——二つの型属性
3. **強力**：参照の返し、構造体保存、クロージャキャプチャが可能——表現能力はRustと同等
4. **コンパイラの賢さ**：refが自動でRc/Arcを選択、呼び出し側が自動で借用を選択
5. **決定性**：refは生存を保証、密かに弱参照にはならない
6. **高性能**：Moveゼロコピー、トークンゼロコスト（ゼロサイズ型、コンパイル後消滅）
7. **柔軟性**：`unsafe + *T`でシステムレベルプログラミングをサポート

### 欠点

1. **ジェネリックブランドパラメータの伝染**：トークンがブランド識別子を携带し、参照を返す関数のシグネチャに追加のジェネリックパラメータが現れる
2. **refのランタイムオーバーヘッド**：アトミック操作にはコストがある（ただしこれは共有の本質的な代償）
3. **unsafeのリスク**：ユーザーが正確性を保証しなければならない
4. **タスク跨ぎ循環はlintであり、コンパイルエラーではない**：Rustのようにコンパイルエラーとならず、デフォルトはwarn、denyに設定してチームの品質ゲートとする必要がある

### トークン衝突検出：ホーア論理命題

トークン衝突検出の完全な方案は
[RFC-009a: トークンライフタイム解析——ホーア証明パイプラインに基づく](../accepted/009a-borrow-proof-pipeline.md)を参照。核心要点：

**トークン活性はホーア論理命題である。**
`{衝突するReadTokenがすべて死亡} write(data) {WriteTokenが安全に取得される}`——型検査、ユーザー述語検証とRFC-027の証明パイプラインを共有。コンパイラが借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を自動生成し、パイプラインがProved
/ Disproved / Unprovenを返す。

**借用検査は消えていない——次元削減されたのだ。** `BorrowChecker`は
`BorrowPredicateEmitter`に変わり、検査を実行する代わりに命題を生成する。これは「型検査器」の概念と完全に平行：型検査器は型等価命題を生成し、借用命題生成器は借用命題を生成し、同じパイプラインで検証される。

**ブランドID（`#42`）は`'a`である。**
情報は完全に同じ、エンコーディングが異なる。`'a`は型シグネチャで見えるが、`#42`
はコンパイラ内部にある。新しい解析を発明したのではなく、ライフタイムを型層から証明層に降ろしたのである。

**アルゴリズム概要**（詳細はRFC-009a）：

- ブランドツリーのプレフィックスマッチング → 衝突トークンの決定（O(depth)、深さ ≤ 3）
- 逆方向BFS
  → 消費者から出発、breakでバックエッジを切断、構造解析で95%以上のシナリオをカバー（高速パス）
- SMT論理切断 → while + パス条件の組み合わせ時のみ呼び出し（低速パス、極めて稀）
