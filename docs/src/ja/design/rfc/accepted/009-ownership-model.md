# RFC-009: 所有権モデル設計

## 概要

本文書は YaoXiang プログラミング言語の**所有権モデル（Ownership Model）**を定義する。

**中核設計——5つの概念、1つのグラデーション**：

```
のぞき見/その場で変更   持ち去り           共有保持          コピー            システムレベル
    │              │              │              │              │
   &T            Move           ref          clone()        unsafe
  &mut T         ゼロコピー      コンパイラ自動  明示的ディープコピー  *T
  ゼロサイズトークン  デフォルト    Rc/Arc を選択              ユーザー責任
  型属性が権限を
  自然に推論
```

- **Move（デフォルト）**：代入/引数渡し/戻り値 = 所有権移転、ゼロコピー、RAII による自動解放
- **`&T` / `&mut T`（借用トークン）**：ゼロサイズのコンパイル時トークン型。`&T`
  は複製可能（共有読み取り専用）、`&mut T`
  は線形（排他的可変）。権限は型属性によって自然に推論され、特別なルールは不要。戻り値として返したり、構造体に格納したりできる。
- **`ref`
  キーワード**：スコープを越えて共有する。コンパイラが自動的に Rc（タスク越えなし）か Arc（タスク越え）を選択する
- **`clone()`**：明示的なディープコピー
- **`unsafe` + `*T`**：生ポインタ、システムレベルのエスケープハッチ

**取り除かれた複雑性**：

- ❌ ライフタイム `'a` なし
- ❌ 独立した借用検査フレームワークなし（借用競合はホーア命題に次元を下げ、型検査と証明パイプラインを共有）
- ❌ GC なし
- ❌ 「エスケープ禁止」などの特殊ルールなし（トークンは通常の型であり、スコープは型システムで統一処理）
- ❌ ユーザーが Rc/Arc の違いを知る必要がない（コンパイラが自動選択）

> **プログラミング負担**：`&T` は複製可能、`&mut T`
> は複製不可——2 つの型属性、0 の特殊ルール、コンパイラ全自動。
> **パフォーマンス保証**：Move はゼロオーバーヘッド、トークンはゼロオーバーヘッド（ゼロサイズ型でコンパイル後に消滅）、ref は必要に応じたコスト、GC ポーズなし。

## 動機

### なぜ所有権モデルが必要か？

| 言語         | メモリ管理             | 問題                                                   |
| ------------ | ---------------------- | ------------------------------------------------------ |
| C/C++        | 手動管理               | メモリリーク、ダングリングポインタ、二重解放           |
| Java/Python  | GC                     | レイテンシ変動、メモリオーバーヘッド、予測不能なポーズ |
| Rust         | 所有権 + 借用検査      | ライフタイム `'a` の学習曲線が急峻                     |
| **YaoXiang** | **Move + Token + ref** | **シンプルで決定論的、GC なし**                        |

### 設計目標

```yaoxiang
# 1. デフォルトは Move（ゼロコピー）
p = Point(1.0, 2.0)
p2 = p                         # Move、p は再読込不可

# 2. &T / &mut T 借用トークン（ゼロオーバーヘッド、型属性が権限を自然に推論）
print_info(p2)                 # コンパイラが &Point トークンを自動生成し、使用後解放
shift(p2, 1.0, 1.0)           # コンパイラが &mut Point トークンを自動生成

# 3. ref = 共有（コンパイラが Rc/Arc を自動選択）
shared = ref p2                # スコープを越えて保持
spawn { use(shared) }          # コンパイラ：タスク越え → Arc

# 4. clone() = 明示的コピー
backup = p2.clone()            # ディープコピー、独立

# 5. unsafe + *T = システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Rust との主な違い

| 機能                     | Rust                                      | YaoXiang                                                               |
| ------------------------ | ----------------------------------------- | ---------------------------------------------------------------------- |
| デフォルトセマンティクス | 借用 `&T`（明示的に `.clone()` が必要）   | **Move（値渡し、ゼロコピー）**                                         |
| 借用                     | `&T`/`&mut T`、戻り可能、ライフタイム必要 | **`&T`/`&mut T` ゼロサイズトークン、Dup/Linear 型属性が自然に推論**    |
| 共有機構                 | `Arc::new()` + 手動 Weak                  | **`ref` キーワード（コンパイラが Rc/Arc を自動選択）**                 |
| コピー                   | `clone()`                                 | `clone()`                                                              |
| 生ポインタ               | `*T`                                      | `*T`                                                                   |
| ライフタイム             | `'a`                                      | ❌ なし                                                                |
| 借用検査                 | グローバル推論                            | **型検査器が借用命題を自動生成し、証明パイプラインで統一検証**         |
| 循環参照                 | 手動 Weak                                 | **タスク終了時に一括解放 / タスク越えは lint / 標準ライブラリの Weak** |

## 提案

### 1. Move（デフォルトの所有権移転）

```yaoxiang
# ルール：代入 / 引数渡し / 戻り値 = Move、ゼロコピー

p: Point = Point(1.0, 2.0)
p2 = p                           # Move、p は再読込不可

# 変数は再代入可能（Python 風、シャドウィングなし）
p = Point(3.0, 4.0)              # p の再束縛、型は同一である必要あり

# 関数引数：Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Move で返す
}

# 関数の戻り値：Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Move で返す、ゼロコピー
}
```

**特徴**：

- ゼロコピー（コンパイラがポインタを移動）
- 移動後、元の束縛は読み取り不可（コンパイルエラー）
- RAII：スコープ終了時に自動解放
- 関数シグネチャ `(T) -> T` 自体がドキュメント——T を消費し、T を返す

---

### 2. &T / &mut T（借用トークン）

**基本原則：`&T` と `&mut T`
はゼロサイズのコンパイル時トークン型である。これらは「参照」ではなく、「アクセス権限の型レベル証明」である。**

#### 2.1 2 つの型属性

```
&T      →  ゼロサイズ、ソースデータを凍結（ReadToken 生存中は WriteToken 禁止）、
          凍結保証の下で複数の読み取り専用ビューが安全 → 複製可能（Dup）
&mut T  →  ゼロサイズ、排他的読み書き（WriteToken 生存中は他のすべてのトークン禁止）、
          排他的アクセス下では複製が無意味 → 線形（非 Dup）
```

**因果関係を逆転させてはならない：凍結が原因であり、Dup は結果である。** `&T`
が Dup を実装しているから共存できる——のではなく、データが凍結されている（変異可能性がない）ため、複数の読み取り専用ビューが安全であり、Dup が実現できる。Dup を定義とし、競合検査を「追加のパッチ」と捉えるなら、設計を誤っている。

#### 2.2 基本的な使い方

```yaoxiang
# メソッド側：引数型を宣言し、必要な権限を決定する
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # &Point トークンが読み取り権限を付与
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # &mut Point トークンが書き込み権限を付与
    self.y = self.y + dy
}

# 呼び出し側：コンパイラが借用または Move を自動選択
p = Point(1.0, 2.0)
p.print()                          # コンパイラが &Point トークンを自動生成
p.shift(1.0, 1.0)                  # コンパイラが &mut Point トークンを自動生成
p.print()                          # OK、前のトークンは shift 呼び出し終了で解放済み

# 自由関数も同様
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # 2 つの &Point トークンが共存——Dup 型
}
d = distance(p, p2)
```

#### 2.3 「エスケープ禁止」が不要な理由

RFC-009 v8 は `&T`/`&mut T`
に対して 3 つの特殊ルールを課していた——引数にのみ使える、戻り値にできない、構造体に格納できない。これは「借用」概念にパッチを当てていた。

トークンシステムにはこれらのルールは不要。トークンは**通常の型**であり、他のすべての型と同じスコープルールに従う。

**参照を返す——自然にサポート**：

```yaoxiang
# ✅ トークンは戻り値とともに伝播する
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # 子トークンと親トークンを一緒に返す
}

# 使用
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # トークンは呼び出し元に返る
print(px_ref)               # OK、トークンはまだスコープ内
```

**構造体に格納——自然にサポート**：

```yaoxiang
# ✅ 構造体はトークンをフィールドとして保持できる
Window: Type = {
    target: Point,
    view: &Point,      # トークンフィールド——target への読み取り専用ビューを保持
}

# view のトークンは target から派生し、Window は両方の所有権を保持する
# Window が存在する限り、view トークンは有効
```

#### 2.3 クロージャと Lambda の明示的引数

Lambda は関数値——スコープ外に戻したり、格納したり、現在のスコープ外に送出したりできる。したがって Lambdaは**外側のローカル変数を暗黙的にキャプチャしない**。外側のデータが必要な場合は、明示的な引数として渡す：

```yaoxiang
# ✅ Lambda は明示的引数を使用
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } はこのルールの影響を受けない——spawn は即時実行される並行ブロックであり、親タスクはそれを待ってブロックされる
shared = ref data
spawn { use(shared) }

# ❌ Lambda は外側の変数を暗黙的にキャプチャできない
x = 42
f = () => { x + 1 }  # コンパイルエラー：x はスコープ外

# ✅ 正しい方法：明示的に引数で渡す
f = (x) => { x + 1 }
f(x)

# ✅ 正しい方法その 2：コンテキストを作成時点で固定化（カリー化）——クロージャは引数のみを取り、キャプチャしない
gt: (t: Int) -> (x: Int) -> Bool = (x) => x > t
evens = list.filter(nums, gt(threshold))
```

> 補足（2026-08-17）：コンテキスト依存の正解はカリー化による固定化であり、キャプチャではない。クロージャがエスケープした後、その定義箇所のスコープは既に死んでいる可能性があるため、暗黙的にキャプチャしてはならない。しかし、呼び出し点（作成点）のスコープは必ず生存しているため、コンテキストがその時点で値として固定化されてクロージャに入るのは安全である。SPEC
> §12.3 を参照。

**spawn { } は関数値ではない。** spawn でマークされたブロックは if/while
body と同様に——即時実行され、親スタックフレームの生存中に完了する。spawn
body は外側の変数に通常通りアクセスできる。

**タスク越え——トークンはスレッド境界を渡れない**：

```yaoxiang
# ❌ トークンはタスク境界を越えて渡せない
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ コンパイルエラー：トークンはタスクを越えて渡せない
}

# これは特殊ルールではない——トークンはコンパイル時の権限証明であり、タスク越え共有には ref を使用すること
# タスク越え共有が必要な場合は、ref を使用すること
```

**トークンは ref できない**：

```yaoxiang
# ❌ トークンは権限証明であり、所有権ではない
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ コンパイルエラー：&T は所有可能な型ではない
}
```

#### 2.4 トークンのライフタイム

トークンのライフタイムは**通常のスコープルール**によって決定され、ライフタイムパラメータは不要：

- 関数引数内のトークン：呼び出し中に生存し、呼び出し終了で解放
- 戻り値のトークン：所有権を呼び出し元に移転
- 構造体に格納されたトークン：構造体とともに生存

コンパイラは `'a`
注釈を必要としない。なぜならトークンは**値**であり、値のライフタイムは所有権システム（Move/RAII）で統一管理されるからだ。**借用問題を所有権問題に次元を下げる。**

#### 2.5 トークン競合検出

トークン競合検出は**ホーア論理命題**であり、独立したフロー依存解析ではない。

```
{競合する ReadToken がすべて死んでいる} write(data) {WriteToken は安全に取得可能}
```

型検査やユーザー述語検証と RFC-027 の証明パイプラインを共有する。コンパイラが借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を自動生成し、パイプラインに送る。パイプラインは Proved
/ Disproved / Unproven を返す。

```yaoxiang
# ❌ &mut トークンは線形であり、複製できない
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move、p は再読込不可
    p.x = 10.0                      # ❌ コンパイルエラー：WriteToken は既に移動済み
}

# ✅ &T トークンは Dup 型であり、自由に複製できる
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK、&T は Dup 型
    print(p.x)                      # OK
    print(p2.x)                     # OK、2 つの読み取り専用トークンが共存
}
```

**借用検査は消えていない——次元が下がった。** 既存の `BorrowChecker` は
`BorrowPredicateEmitter`（命題ジェネレータ）となり、生成された借用命題は他の型命題と同じ証明パイプラインを共有する。これは型検査器の概念と完全にパラレル：型検査器は型等価命題を生成し、借用命題ジェネレータは借用命題を生成し、同じパイプラインで検証する。詳細設計は
[RFC-009a](../accepted/009a-borrow-proof-pipeline.md) を参照。

#### 2.7 コンパイラ内部：ブランド機構

ユーザーがブランドに触れることは決してない。コンパイラが内部で各トークンにコンパイル時一意識別子を割り当てる：

```
ユーザーが見るもの       コンパイラ内部表現
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #N はコンパイル時一意な整数
&mut Point     →  WriteToken(Point, #M)   // #M はコンパイル時一意な整数
```

ブランドの用途：

- **偽造防止**：トークンは所有者のカプセルからのみ取得でき、凭空に構築できない
- **関連追跡**：`&Point` から `&Float`（フィールドアクセス）を派生するとき、`&Float`
  は派生ブランド（`#N.field_x`）を携带し、コンパイラは親トークンまで追跡できる
- **競合検出**：同源の `WriteToken` と派生の `ReadToken` は同時にアクティブになれない

ブランドは単態化とインライン化の後で完全に消滅し、生成される機械語には存在しない。**実行時オーバーヘッドはゼロ。**

#### 2.8 自動借用選択ルール

呼び出し側コンパイラは以下の優先順位で自動選択する：

```
1. 実引数がその後も使用される → トークン（&T または &mut T、メソッドシグネチャによる）の生成を優先
2. 実引数がその後使用されない → Move
3. 優先マッチ順：&T < &mut T < Move
```

```yaoxiang
# 例：自動選択
p = Point(1.0, 2.0)
p.print()        # print は &self を宣言 → コンパイラが &Point トークンを生成
p.shift(1.0, 1.0) # shift は &mut self を宣言 → コンパイラが &mut Point トークンを生成
p2 = p           # Move、p は使用されない
```

#### 2.9 RFC-009 v8 ミニマル借用との比較

| 機能                     | ミニマル借用 (v8)                  | 借用トークン (v9)                                  |
| ------------------------ | ---------------------------------- | -------------------------------------------------- |
| 参照の戻り               | ❌ ハードコードで禁止              | ✅ トークンが戻り値とともに伝播                    |
| 構造体への格納           | ❌ ハードコードで禁止              | ✅ トークンを構造体フィールドとして使用            |
| Lambda の明示的引数      | ❌ ハードコードで禁止              | ✅ Lambda は明示的引数を使用                       |
| 特殊ルール               | 3 つ（引数のみ/戻り不可/格納不可） | 0——型属性による自然な推論                          |
| 借用検査                 | 専用の交差借用検査                 | 型検査器のフロー依存活性分析                       |
| ライフタイム注釈         | 不要                               | 不要                                               |
| 実行時オーバーヘッド     | ゼロ                               | ゼロ（ゼロサイズ型、コンパイル後に消滅）           |
| エラーメッセージ         | 「借用はエスケープ不可」           | 「WriteToken(#3)は既に移動済み」（通常の型エラー） |
| ユーザーのメンタルモデル | 「借用」の特殊性を理解する         | `&T` は複製可能、`&mut T` は複製不可               |

### 3. ref キーワード（コンパイラによる自動最適化）

`ref` はスコープを越えて共有する唯一の方法。内部実装が Rc か Arc かをユーザーが知る必要はない。

#### 3.1 基本的な使い方

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # 共有、コンパイラが実装を自動選択

# タスク越え共有
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # コンパイラ：タスク越え → Arc
    spawn { use(data) }           # コンパイラ：タスク越え → Arc
}

# 単一タスク内共有
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # コンパイラ：タスク越えなし → Rc
}
```

**ユーザーのメンタルモデル**：`ref` = 共有保持。それだけ。

#### 3.2 コンパイラの escape 解析：Rc vs Arc

```
ref のデータフロー解析：

他タスクにエスケープしない → Rc（非アトミック参照カウント、低オーバーヘッド）
他タスクにエスケープする   → Arc（アトミック参照カウント、スレッドセーフ）
```

#### 3.3 循環検出戦略

```
タスク内循環 → 静かに許可。
  ├── 各タスクには明確なライフサイクル境界がある——タスク終了時にすべてのリソース（ref 循環を含む）が一括解放される。
  ├── 長時間実行されるサービスはリクエスト/接続ごとに子タスクを作成すべき——子タスク終了で自動回収され、累積リークはしない。
  ├── ref は常に生存し続け、セマンティクスは水増しなし。
  └── ユーザーはタスク内で双方向の強参照（たとえばグラフ計算の中間状態）を構築する権利を持つ。

タスク越え循環 → lint（デフォルト warn、設定可能）。
  ├── プログラムの動作は正しく、実際にリークはしない（親タスク終了時に子タスクのリソースがすべて解放される）。
  ├── しかし、タスク越え強参照は所有権境界が曖昧であることを意味し、立ち止まって再考する価値がある。
  ├── デフォルトは warn レベルで、コンパイルは成功するがヒントが表示される。
  └── チームはプロジェクト設定で deny にでき、CI 品質ゲートに組み込める。
```

**Lint レベル**（Rust clippy 風）：

| レベル               | 動作                               | シナリオ             |
| -------------------- | ---------------------------------- | -------------------- |
| `allow`              | チェックしない                     | 個人プロジェクト     |
| `warn`（デフォルト） | コンパイル成功、ヒント表示         | 開発段階             |
| `deny`               | コンパイル失敗                     | チーム CI 品質ゲート |
| `forbid`             | コンパイル失敗、オーバーライド不可 | 組織レベル強制ルール |

```yaoxiang
# タスク内循環：静かに許可、双方向強参照
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # 循環。タスク終了時に一括解放。
}

# タスク越え循環：lint（デフォルト warn）
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: タスク越えの循環参照
    }
}
```

**プロジェクト設定例**：

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # タスク越え循環は CI で即座に拒否
```

| 循環タイプ          | 動作                    | 理由                                   |
| ------------------- | ----------------------- | -------------------------------------- |
| タスク内 ref 循環   | チェックしない          | ユーザーの権限、タスク終了時に一括解放 |
| タスク越え ref 循環 | lint（デフォルト warn） | 再考を促す、設定で deny 可能           |

#### 3.4 Weak：標準ライブラリで提供

```yaoxiang
use std.weak

# 上級ユーザーが明示的に選択
a.next = ref b
b.prev = std.weak.new(a.next)   # ユーザーがどちらの方向を弱にするか明示的に制御
```

**`Weak` は言語組み込みではなく、標準ライブラリ型である。** 日常的には `ref`
で十分。メモリを細かく制御したい上級ユーザーが手動で `Weak` を導入する。

> 2026-08-03 改訂：独立した `std.weak` モジュールとして実装（`std.rc` は存在しない——`ref`
> は言語キーワードでありモジュールではない；モジュールパスは `std.weak`
> に統一され、構築/アップグレードのエントリは `std.weak.new` /
> `std.weak.upgrade`）。初稿で想定されていた `std.rc.Weak` は実装されなかった、本改訂が優先される。

#### 3.5 借用トークン vs ref

|            | `&T` / `&mut T`                                                    | `ref`                                   |
| ---------- | ------------------------------------------------------------------ | --------------------------------------- |
| 機能       | のぞき見/その場で変更                                              | 共有保持                                |
| 範囲       | トークン値とともに伝播                                             | スコープ越え                            |
| コスト     | ゼロオーバーヘッド（ゼロサイズ型）                                 | Rc または Arc（コンパイラが選択）       |
| エスケープ | 可（トークンは戻り値/構造体/クロージャで伝播）                     | 元々エスケープ目的                      |
| タスク越え | 不可（トークンはコンパイル時権限証明であり、タスク境界を渡れない） | 可（コンパイラが Arc を自動選択）       |
| 循環       | 関係しない                                                         | タスク内は静かに許可、タスク越えは lint |

### 4. clone() —— 明示的コピー

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # ディープコピー
# p と p2 は独立し、互いに影響しない
```

**いつ使うか**：元の値を保持する必要があり、Move も共有も適さないシナリオ。

### 5. unsafe + 生ポインタ（システムレベルプログラミング）

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # 生ポインタ
    (*ptr).x = 0.0                # デリファレンス（ユーザーが安全を保証）
    ptr2 = ptr + 1                # ポインタ演算
}
```

**制約**：

- `unsafe` ブロック内でのみ使用可能
- ユーザーはダングリング、解放後使用がないことを保証する
- FFI、メモリ操作などのシステムレベルプログラミングに使用

### 6. 所有権のグラデーション概要

```
  借用トークン（ゼロオーバーヘッド）     Move（ゼロオーバーヘッド）      共有（必要に応じたコスト）    コピー
   │                      │                  │                │
  &T 複製可能トークン        デフォルトの所有権移転     ref Rc/Arc       clone()
  &mut T 線形トークン      消費して返すチェーン       コンパイラが自動選択      明示的ディープコピー
   │                      │                  │                │
  トークン値のスコープ内           スコープ内           スコープ越え         いつでも
  戻り/構造体格納可能        T -> T 戻り        ref タスク越え → Arc  独立コピー
  ゼロサイズでコンパイル後消滅        T -> Void 消費     ref タスク越えなし → Rc
  ゼロサイズでコンパイル後消滅                          タスク内循環は静かに
                                            タスク越え循環は lint
                                            標準ライブラリの Weak で脱出
```

## 総合例

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T：読み取り専用トークン
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T：可変トークン
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move：消費して返す
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # 持ち去り、変更し、返す
    }

    # 参照を返す：トークンは戻り値とともに伝播
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Lambda の明示的引数
double: (x: Int) -> Int = (x) => x * 2

# 総合的な使用
p = Point(1.0, 2.0)
p.print()                           # &Point トークン
p.shift(1.0, 1.0)                   # &mut Point トークン
p = p.scale(2.0)                    # Move → 戻り
shared = ref p                      # ref 共有
spawn { use(shared) }

# clone で独立コピー
backup = p.clone()

# タスク内循環：静かに許可
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # 循環、タスク終了時に一括解放

# unsafe システムレベル
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## 型システム制約

### Dup 型属性

`Dup`（Duplicable：複製可能）はコンパイラが自動管理する型属性であり、意味は**シャローコピー**：代入/引数渡し時にはハンドル/トークンがコピーされ、基底データが共有される。これは Move（所有権移転）や Clone（明示的ディープコピーによる独立コピー）と合わせて 3 段階のグラデーションを形成する。

**Dup と Clone は直交する概念**——Dup はハンドルをコピーしてデータを共有し、Clone は独立したコピーを生成する。1 つの型が Dup と Clone の両方をサポートすることも、その一方のみをサポートすることもできる。

| 型            | Dup                                                            | Clone | 説明                                       |
| ------------- | -------------------------------------------------------------- | ----- | ------------------------------------------ |
| `&T`          | ✅（トークンを複製、複数の視点が同じデータを指す）             | ✅    | 読み取り専用トークン                       |
| `ref T`       | ✅（参照カウント+1、ヒープデータを共有）                       | ✅    | 共有保持（コンパイラが Rc/Arc を自動選択） |
| String, Bytes | ✅（内部参照カウント、ハンドルをコピーして基底 buffer を共有） | ✅    | 文字列/バイト                              |
| `&mut T`      | ❌（線形、排他）                                               | ❌    | 可変トークン                               |
| `*T`          | ❌                                                             | ❌    | 生ポインタ                                 |
| struct        | 派生（すべてのフィールドが Dup のとき自動派生）                | ✅    | 構造体                                     |

**プリミティブ値型**（Int, Float, Bool,
Char）の代入動作はコンパイラ組み込みの値コピーであり、2 つの値は完全に独立しており、シャローコピーではない。これらは Dup 型属性には属さず、コンパイラのネイティブ処理である。

## パフォーマンス分析

| 操作                    | コスト   | 説明                                                       |
| ----------------------- | -------- | ---------------------------------------------------------- |
| Move                    | ゼロ     | ポインタ移動                                               |
| `&T` / `&mut T`         | ゼロ     | ゼロサイズ型、コンパイル後に消滅、実行時オーバーヘッドなし |
| `ref`（タスク越えなし） | 低       | Rc にコンパイル、非アトミック操作                          |
| `ref`（タスク越え）     | 中       | Arc にコンパイル、アトミック操作                           |
| `clone()`               | 型による | 小オブジェクトは高速、大オブジェクトは低速                 |
| `unsafe + *T`           | ゼロ     | 直接メモリ操作                                             |

### 比較

| 言語         | 共有機構               | メモリ管理       | 循環処理                                                       | 複雑度 |
| ------------ | ---------------------- | ---------------- | -------------------------------------------------------------- | ------ |
| Rust         | Arc / Mutex + 借用検査 | コンパイル時検査 | 手動 Weak                                                      | 高     |
| Go           | chan / pointer         | GC               | GC                                                             | 低     |
| C++          | shared_ptr             | RAII             | weak_ptr                                                       | 中     |
| **YaoXiang** | **ref + 借用トークン** | **RAII**         | **タスク境界解放 / タスク越えは lint / 標準ライブラリの Weak** | **低** |

## トレードオフ

### メリット

1. **統一**：`&T`/`&mut T` は通常の型であり、特殊な言語機能ではない。RFC-010 の `name: type = value`
   と完全に一致する
2. **シンプル**：ライフタイムなし、借用検査は型システム命題に次元を下げる。`&T` は複製可能、`&mut T`
   は複製不可——2 つの型属性
3. **強力**：参照の返却、構造体への格納、クロージャのキャプチャが可能——表現能力は Rust と同等
4. **コンパイラの賢さ**：ref が Rc/Arc を自動選択、呼び出し側が借用を自動選択
5. **決定論的**：ref は生存し続け、密かに弱参照にはならない
6. **高性能**：Move はゼロコピー、トークンはゼロオーバーヘッド（ゼロサイズ型、コンパイル後に消滅）
7. **柔軟**：`unsafe + *T` がシステムレベルプログラミングをサポート

### デメリット

1. **ジェネリックブランドパラメータの伝染**：トークンはブランド識別子を携带し、参照を返す関数のシグネチャに追加のジェネリックパラメータが現れる
2. **ref の実行時オーバーヘッド**：アトミック操作にはコストがある（しかしこれは共有の必然的な代償）
3. **unsafe のリスク**：ユーザーが正確性を保証しなければならない
4. **タスク越え循環は lint であり、コンパイルエラーではない**：Rust のようにコンパイルエラーとはならず、デフォルトは warn、チームが deny に設定して初めて品質ゲートとなる

## 代替案

| 案                      | 選択しない理由                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------- |
| GC                      | 実行時オーバーヘッドがあり、停止を予測できない                                         |
| Rust 借用チェッカ       | ライフタイム `'a` が必要、学習曲線が急                                                 |
| 純粋な Move             | 並行共有を処理できない                                                                 |
| 生ポインタなし          | システムレベルプログラミングができない                                                 |
| Rc/Arc をユーザーに公開 | 実装詳細をユーザーに押し付け、認知負荷を増やす                                         |
| ミニマル借用（v8）      | エスケープ禁止の方針がクロージャキャプチャ、参照の返却などの重要な表現能力を犠牲にする |

### トークン競合検出：ホーア論理命題

トークン競合検出の完全なソリューションは
[RFC-009a: トークンライフタイム解析——ホーア証明パイプラインに基づく](../accepted/009a-borrow-proof-pipeline.md)
を参照。中核要点：

**トークン活性はホーア論理命題である。**
`{競合する ReadToken がすべて死んでいる} write(data) {WriteToken は安全に取得可能}`——型検査やユーザー述語検証と RFC-027 の証明パイプラインを共有する。コンパイラが借用命題（`borrow_conflict`、`use_after_move`、`use_after_drop`、`mut_violation`）を自動生成し、パイプラインが Proved
/ Disproved / Unproven を返す。

**借用検査は消えていない——次元が下がった。** `BorrowChecker` は `BorrowPredicateEmitter`
となり、命題を生成する検査ではなくなる。これは「型検査器」の概念と完全にパラレル：型検査器は型等価命題を生成し、借用命題ジェネレータは借用命題を生成し、同じパイプラインで検証する。

**ブランド ID（`#42`）は `'a` そのものである。** 情報は完全に同じで、エンコーディングが異なる。`'a`
は型シグネチャで見えるが、`#42`
はコンパイラ内部にある。新しい解析を発明したのではなく、ライフタイムを型層から証明層に下げたのだ。

**アルゴリズム概要**（詳細は RFC-009a を参照）：

- ブランドツリーのプレフィックスマッチ → 競合トークンの特定（O(depth)、深さ ≤ 3）
- 逆 BFS
  → 消費者から出発、break でバックエッジを切断、構造解析が 95%+ のシナリオをカバー（高速パス）
- SMT 論理切断 → while + パス条件のときのみ呼び出し（低速パス、極めて稀）
