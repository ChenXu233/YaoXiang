# RFC-029f: コンパイルターゲットの役割とインポート面セマンティクス

## 概要

RFC-029「子 RFC 計画」の拡張スロット（029b–029e は占有済、029f へ繰下げ）の実現：ソースファイルに対し
**コンパイルターゲットの役割モデル**（Script / Bin / Lib / Test /
Internal の 5 種類）およびその**インポート面セマンティクス**を定義する——マニフェストなしの場合はエントリの到達性によって推論（ゼロコンフィグ）、マニフェストありの場合は
`[lib]` / `[[bin]]` /
`[exports]`（RFC-015 で既に定義されたフィールド）で明示的に宣言する。四つの未確定セマンティクスを埋める：他パッケージからのインポート面をどう算出するか、デッドコード警告の pub 免除適用範囲（#321 決定 B）、`[exports]`
と Registry 到達性の関係、そして RFC-014b の
`[binaries]`（事前コンパイル配布成果物）と bin 役割ソースファイルの名詞曖昧性解消。

## 動機

### ホストと境界の根拠

RFC-029（採択済）のエントリ選択と可視性決定は本 RFC の直接の上流である：

> **エントリファイル選択**の優先順位：1. `[run].main` 2. `[[bin]]` の最初の項目の `path` 3.
> `src/main.yx`（規約上のデフォルト）。—— RFC-029 §パッケージ間循環：再説

> **可視性**：存在しない。スコープ + 配布境界がすべてのシナリオをカバーし、新たなキーワードは不要。——
> RFC-029 §設計決定記録（2026-07-30）

第二条は本 RFC の設計上のレッドラインである：インポート面セマンティクスは
**新たな可視性キーワードを導入してはならず**、「配布境界」（ファイル役割 + 宣言エクスポート面）によってのみ担われる。

四つの消費者がそれぞれ同じ壁にぶつかっている：

| 消費者                                                     | ぶつかった壁                                                                                                                                                                                                    |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 デッドコード警告                                      | 決定 B「pub = 対外インターフェースは警告しない」が採用されたのは、「本物の対外」と「対外のように見える」を区別する役割モデルがないため；bin 内で未使用 pub を警告するかどうか（案 A）は今まで保留               |
| RFC-014c ワークスペース（審査中、#113）                    | メンバーパッケージ相互に `use` する際のインポート面をどう算出するか——`[exports]`、`[lib]` 単一ファイル、それとも全 pub ファイル——**本文中にセマンティクス条文が一つもない**                                     |
| RFC-015 構成システム（採択済）                             | `[lib]` / `[[bin]]` / `[exports]` フィールドは定義済みだが、RFC-029 がエントリ優先順位を消費している以外は、他のフィールドのセマンティクス（特に `[exports]` と Registry 到達性の関係）が誰にも整合されていない |
| RFC-037 パッケージング / RFC-029a キャッシュ（草案、#293） | パッケージング成果物の選択、増分再コンパイルのキャッシュ単位境界、いずれも役割モデルを必要とする                                                                                                                |

### 現状の問題

**四つのセマンティクス空白**（2026-09-12 棚卸、014/014a/014b/014c/015/029 全文章で確認）：

1. **他パッケージからのインポート面が未定義**。014c のメンバーパッケージ相互参照の例にはディレクトリ構造（`src/lib.yx`）しかなく、
   `use utils.helper`
   で何が取得できるかについて一切条文がない。現在の暗黙ルールは「当該パッケージの全トップレベル pub ファイル」——内部実装ファイルも名前空間に引きずり込まれ、依存境界は有名無実。
2. **デッドコードの pub 免除に適用範囲がない**。#321 決定 B の「pub は警告しない」は単一ファイルスクリプトでは過度に保守的（スクリプトには外部消費者がおらず、pub に意味がない）であり、複数ファイルプロジェクトのエントリファイルでは逆に過度に寛容（誰も import しないルートファイルの pub はデッドコード）。役割モデルがなければ、A/B 両案の分割線が引けない。
3. **三つのエクスポート概念に整合がない**。`[exports]`（015、パス写像）、`[lib]`（015、単一ファイルパス）、Registry 到達性（029、エントリから use 経由で到達可能）——三者の関係が包含関係なのか、等価関係なのか、それぞれ独立なのか、条文がない。
4. **名詞衝突**。RFC-014b の `[binaries]`
   は**事前コンパイル配布成果物**（.so/exe ダウンロード優先戦略）であり、「bin ターゲット（ソースコード役割）」とは全く別のレイヤー。014c が実装された暁には両者が同画面に表示されることは必定で、早めに曖昧性解消しないと継続的に誤解が生じる。

**実証：B 決定の保守性は既に実際の苦痛**。#321
M2 のふりかえり記録：デフォルト構成下で W1001–W1005 全体が静かにされている構造的原因是「すべての pub が対外インターフェース扱いされている」——これはモデル欠如の補完動作であり、終局状態ではない。

## 提案

### 中核設計：ファイル役割モデル

**役割はファイルレベル属性**（015 のフィールド粒度と一致：`[lib]` は単一ファイル、`[[bin]]`
はファイルリスト、`[exports]` はファイル写像）であり、パッケージレベルのスイッチではない。

| 役割         | 判定                                                                                                                                       | セマンティクス                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bin**      | `[run].main` / `[[bin]].path` が指すファイル；または（マニフェストなしの場合）`main` を含み、どのファイルからも `use` されていないファイル | プログラムエントリ。`main` という名前の**バインディング**の存在を要求し、値・関数いずれでも可：関数 main はエントリ時に引数なしで呼び出され、値 main は初期化時に評価されて即実行される（評価結果が関数値でも再呼び出しされない）。`main` 欠落はコンパイルエラー（E3020）；トップレベルに実行可能文があってはならない。その `pub` は**デッドコードとして警告され得る**（パッケージ外消費者がいない）；`main` は到達性のルート |
| **Lib**      | `[exports]` 写像が指すファイル；または `[lib].path`；または（マニフェストなしの場合）他のファイルから `use` されているファイル             | 配布境界。その `pub` は**デッドコード警告を免除**（パッケージ外消費者が見えないため、見逃しを許容）；これを通じてエクスポートされたシンボルはパッケージ間で見える                                                                                                                                                                                                                                                             |
| **Test**     | RFC-036 のテストファイル規則が命中したファイル（`tests/` ディレクトリ、`*_test.yx` などの既存規約）；`[[test]]` 明示宣言は**設けない**     | テストコード。デッドコード判定に参加しない；その参照は被テストコードの到達性ルートに加算される                                                                                                                                                                                                                                                                                                                                |
| **Internal** | パッケージにマニフェストがあるとき、エクスポート面にも main も含まないファイル                                                             | パッケージ内実装。`pub` は第二段階まで免除（パッケージ内 use グラフ到達性で厳格化、bin 役割コーパス検証を前提とする）；パッケージ外 `use` **不可達**                                                                                                                                                                                                                                                                          |
| **Script**   | 単一ファイル直接実行（`run foo.yx`）されるファイル                                                                                         | **エントリ概念なし**。トップレベル文（バインディング初期化を含む）は記述順にそのままプログラム本体；`main` は通常のバインディングで**自動呼び出しされない**——実行したいなら `main()` と書く。Registry は std のみ                                                                                                                                                                                                             |

**判定優先順位**：マニフェスト明示宣言 > エントリ到達性推論 >
036 テスト規約。明示宣言は常に勝つ——推論は宣言がないときのデフォルトに過ぎない。

### エントリ判定

役割モデルはデッドコード解析だけでなく、**エントリ判定も駆動する**。各役割のエントリ規則：

| 役割                           | エントリ規則                                                                                                                                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Script**（マニフェストなし） | **エントリ概念なし**。トップレベル文（バインディング初期化を含む）は記述順にそのままプログラム本体；`main` は通常のバインディングで**自動呼び出しされない**——実行したいなら `main()` と書く                                   |
| **Bin**（マニフェストあり）    | `main` という名前の**バインディング**の存在を要求（値・関数いずれでも可：値 main は初期化時評価、関数 main はエントリ時引数なし呼び出し）；`main` 欠落はコンパイルエラー（E3020）。トップレベルに実行可能文があってはならない |
| **Lib / Internal / Test**      | `main` は要求されない（これらはエントリではない）                                                                                                                                                                             |

**Script と Bin のエントリは相互排他的でなければならない**：「Script では `main`
は特別扱いしない」と「Bin では `main`
はエントリ」は同時に成立しない——もし Script がトップレベル文を実行しつつ暗黙的に `main`
を呼ぶなら、明示的に `main()`
と書いたスクリプトが二重実行される（#356）。したがって Script の実行入口は一つだけ：トップレベル文。

**役割判定とエントリ判定の違い**（実装注記）：エントリ判定は「役割」ではなく「有無マニフェスト」（`find_project_root().is_some()`）を使う。理由：役割分類は「誰がこのファイルを消費するか」を答える（デッドコード解析に資する）；マニフェストがあるのに
`main`
のないファイルは分類上は Internal であり（他のファイルから use されない、合理的）、しかしユーザがそれをエントリとして実行した場合、エントリが必要となる。二つの問いは別であり、判定基準も自ずと異なる。

**値 `main` の実行形式**（#388 決定）：関数は既に値である（型レイヤで統一）ため、エントリ判定は
**バインディング存在性**で行い、呼び出し可能性ではない——値 main と関数 main は評価戦略が異なるだけ。値 main はエントリ呼び出しを行わない（#356 二重実行防止：初期化とエントリ呼び出しは絶対に重ねない）、Script と同じ実行形式；その評価は初期化シーケンスの一部：グローバルバインディングのトポロジカル順に実行し、独立バインディングはソース順に実行する。したがって Script のトップレベル文を
`main = { ... }`
に包んで Bin に移行する**ことは順序保存移行ではない**——散らばった文は記述順に実行され、バインディング初期化はトポロジカル順；先行が必要な初期化は
`main` に明示的に依存させること。 `main: Int = 5`
のような呼び出し不能な値 main は合法だが、観察効果のないプログラムである（Rust の空 `fn main() {}`
に対応）。

詳細は `docs/src/reference/language-spec/syntax.md` §3.11 を参照。

### 例

```toml
# yaoxiang.toml（フィールドはすべて RFC-015 で定義済み、本 RFC は新たな構成面を追加しない）
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← 他パッケージ可視性を決めるのはこれであり、pub ではない
```

```yaoxiang
# src/cli.yx（Bin 役割）
pub unused_fn = (x: Int) => x    # ← W1001 として警告され得る：bin にはパッケージ外消費者がいない
main: () -> Void = { ... }

# src/lib.yx（Lib 役割、エクスポート面上）
pub api_fn = ...                 # ← 警告されない：パッケージ外消費者から見えない

# src/other.yx（Internal 役割、エクスポート面上にない）
pub semi_api = ...               # ← 第二段階まで免除（見逃し許容）、その時点で use グラフで厳格化
```

### インポート面セマンティクス

他パッケージ `use pkg.x` の解決順序（最初にヒットしたものが有効）：

1. `[exports]` 写像が存在 → インポート面 = 写像に列挙されたファイル集合、`x`
   はこれらのファイルのトップレベルバインディングに存在しなければならない；
2. そうでなく `[lib].path` が存在 → インポート面 = その単一ファイル；
3. どちらもなし（マニフェストなし依存、パス依存ベアディレクトリ）→
   **現状維持**：全トップレベルファイルがインポート可能（既存挙動互換、絞り込みは別途検討）。

**ワークスペースメンバ**：エクスポート面はメンバーパッケージ自身のマニフェストのみで定義され、ワークスペースルートがメンバーエクスポート面を上書きまたは拡張することはできない——メンバー自己完結は 014c の中核設計であり、ルート上書きはカプセル化を破壊する。

Registry 到達性との関係（029 との整合）：`[exports]`/`[lib]`
は**他パッケージ解決の合法起点集合**を定義する；起点が確定した後、Registry は引き続き 029 の「エントリから
`use` 経由で到達可能」によって拡張する——エクスポートファイル自身が `use`
で取り込んだ内部ファイルはリンクと共に進入するが、新たな他パッケージ起点を生成することはない。

### 既存計画との境界

| 隣接                                               | 境界                                                                                                                                                                                                                        |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-029d「CLI `--entry` エントリ上書き」（計画中） | 029f は役割モデルを定義；029d はそれを消費する——`--entry` は Bin 役割の CLI レベル上書き手段                                                                                                                                |
| RFC-014b `[binaries]`                              | **名詞曖昧性解消**：`[binaries]` は事前コンパイル配布成果物（ダウンロード優先戦略）、`[[bin]]` はソースコード役割宣言。前者は依存パッケージのマニフェストに存在し、後者は本パッケージのマニフェストに存在し、入れ替わらない |
| RFC-014c ワークスペース                            | メンバーパッケージ相互参照のインポート面 = 本 RFC の解決順序；ワークスペース調整機構（members、共有 lockfile）は引き続き 014c                                                                                               |
| RFC-036 テスト                                     | Test 役割判定は 036 の既存ファイル規則を直接採用し、新たな規約を追加しない                                                                                                                                                  |
| #321 デッドコード                                  | 決定 B（pub は一律免除）は明示的に「target なし時の過渡的セマンティクス」に降格；Bin 役割の pub 警告は本 RFC が案 A を実現する形態                                                                                          |

## 詳細設計

### 役割判定アルゴリズム（オーケストレーター内）

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. 明示レイヤ：マニフェスト宣言優先
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. 推論レイヤ：宣言がない箇所はエントリ到達性で
    for f in files where role[f] 未定:
        if f が ≥1 個の非自身ファイルから use されている: role[f] = Lib
        elif f が main を含み、他ファイルが use していない: role[f] = Bin
        else:                            role[f] = Internal

    # 3. テストレイヤ：036 規則命中 → Test（Lib/Internal を上書き、明示 Bin は上書きしない）
    apply_rfc036_test_rules(files, &role)

    # 単一ファイル直接実行：モデル全体をバイパス、挙動は不変
    if no manifest and single_file:      all Script
```

### コンパイラ変更

- `frontend/config.rs`：マニフェスト解析で `[exports]`
  → 役割表への写像を追加（フィールド解析は 015 既存）。
- `frontend/module/orchestrator.rs`：Registry 構築前に役割分類段階を挿入；他パッケージ解決はインポート面順に従って
  `use` ターゲットを検証、越界は既存の `module_not_found`
  系で報告（エラーコードは追加せず、メッセージに「エクスポート面にない」ヒントを追加）。
- `typecheck/passes/dead_code.rs`：エントリ点集合を「main + 全 pub」から「main +
  Lib 役割ファイルの pub」に変更（Bin は即時警告可能；Internal は第二段階まで免除、Phase
  2 は実装戦略を参照）。
- LSP（RFC-017）：補完/ホバーの「インポート可能項目」をインポート面でフィルタ；`main`
  欠落診断は Bin 役割ファイルにのみ報告。

### ランタイム挙動

変化なし。役割モデルは純粋なコンパイル時/解析時セマンティクスであり、IR と実行に影響しない。

### 後方互換性

- マニフェストなしプロジェクト：挙動は完全に不変（推論レイヤが現状を再現——use されているものは Lib、main を含むものは Bin）。デッドコード警告の増分は Bin ファイルのみ：誰も import しないルートファイルの unused
  pub が静默状態から W1001 になる——これは #321 案 A の予期挙動であり、破壊ではない。
- マニフェストありプロジェクト：`[exports]`
  が宣言済みの場合、インポート面が「全 pub ファイル」から宣言面に絞り込まれる。**これが唯一の挙動絞り込み点**：他人パッケージの内部ファイルに依存しているコードが
  `module_not_found`
  で報告され始める。パッケージエコシステムが未確立である現状（029：「現在サードパーティパッケージエコシステムなし」）では破壊面ゼロ；それでもマイナーバージョンで過渡期を設ける（越界はまず警告、後にエラー）。

## トレードオフ

### 利点

- 新規構成面ゼロ：フィールドはすべて 015 既存、本 RFC はセマンティクスを補完するだけ。
- 新規キーワードゼロ：インポート面は配布境界が担い、029「可視性存在せず」決定と同型。
- 四つの消費者（#321 / 014c / 029a / 037）を一度にモデル化し、それぞれが壁にぶつかる状況を解消。
- マニフェストなし経路はゼロコスト：スクリプト言語のゼロコンフィグ遺伝子を完全に保持。

### 欠点

- 役割推論（use されていれば Lib）は「エントリファイルがツールファイルを use する」典型形態でツールファイルを Lib と判定し、その pub が免除される——理想粒度より粗い。これは見逃し方向への意図的選択であり、絞り込みには use グラフ上の呼び出し方向解析が必要、第一版では行わない。
- `[exports]` によるインポート面絞り込みは破壊的セマンティクス絞り込みである（過渡期あり）。

## 代替案

| 案                                         | 説明                                                                          | 不採用理由                                                                                                                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トップレベル RFC-040                       | 新たなトップレベル番号を割り当てる                                            | モジュール図セマンティクス（インポート面/到達性/エントリ）はすべて 029 領域、分割すると同一対象に対するトップレベル文書が二つできる；029b–029e スロットパターンも確立済   |
| 014c に取り込み                            | ワークスペースの一節とする                                                    | 依存方向が逆：言語レイヤ（029x）がセマンティクスを定義し、パッケージレイヤ（014x）がセマンティクスを消費する。014c はまだ審査中、途中で範囲拡大するとその実装を遅延させる |

## 実装戦略

### 段階分け

- **Phase 1**：役割分類 + インポート面解決 + Bin pub 警告可能（Internal/Test は免除維持）
- **Phase 2**：Internal
  pub を「パッケージ内 use グラフで不可達なら警告可能」に厳格化——前提条件は Phase
  1 実装後の Bin 役割警告コーパス検証で誤報告コールバックがないこと；トリガーで即時実施、スケジュールは設定しない

### 依存関係

- 前提：RFC-029 オーケストレーター（実装済）、RFC-015 マニフェストフィールド（定義済）。
- 依存される側：#321（Bin
  pub 警告可能）、RFC-014c（インポート面）、RFC-029a（役割をキャッシュ単位境界として）、RFC-037（成果物選択）、RFC-029d（`--entry`
  上書き）。
- RFC-014c との実装順序：014c 審査通過前に、029f のインポート面順序をまず確定させ、014c は参照によって消費することで、審査途中での範囲拡大を避ける。

### リスク

- 役割推論とユーザ直感のずれ（上述トレードオフ第一条）→ 増分挙動はすべて警告形式（ブロッキングしない）で提示、いつでも disable 可能。
- `[exports]` 絞り込みの過渡期管理 → マイナーバージョン内でまず警告。

## 未解決問題

草案段階の三項目はすべて決定済（2026-09-13、決定は付録Bと本文に記載）、未決なし：

      2 参照）
- [x] `[[test]]` 明示宣言 →
      **決定**：導入せず、Test 役割は 036 規則のみで判定；036 に将来明示宣言の必要が生じれば 036 自体が拡張する
- [x] ワークスペースルートがメンバーエクスポート面を上書き →
      **決定**：許可せず、メンバー自己完結は 014c の中核設計であり、ルート上書きはカプセル化を破壊する
