# RFC-029f: コンパイルターゲットロールとインポート面のセマンティクス

## 概要

RFC-029「子 RFC 計画」の拡張スロットを実現（029b–029e は占有済み、029f に順延）：ソースファイルに**コンパイルターゲットロールモデル**（Script
/ Bin / Lib / Test /
Internal の 5 種類）とその**インポート面のセマンティクス**を定義する——manifest がない場合はエントリの到達性から推測（ゼロコンフィグ）、manifest がある場合は
`[lib]` / `[[bin]]` /
`[exports]`（RFC-015 で定義済みのフィールド）に従って明示的に宣言する。4 つの空白セマンティクスを埋める：他パッケージのインポート面の計算基準、デッドコード警告の pub 免除適用範囲（#321 決定 B）、`[exports]`
と Registry 到達可能性の関係、そして RFC-014b
`[binaries]`（プリコンパイル配布成果物）と bin ロールソースファイルの用語曖昧性の解消。

## 動機

### ホストと境界の根拠

RFC-029（承認済み）のエントリ選択と可視性決定は本 RFC の直接の上流である：

> **エントリファイル選択**優先度：1. `[run].main` 2. `[[bin]]` 第 1 項の `path` 3.
> `src/main.yx`（規約デフォルト）。—— RFC-029 §パッケージ間循環：再説

> **可視性**：存在しない。スコープ + 配布境界がすべてのシナリオをカバーし、新しいキーワードは不要。——
> RFC-029 §設計決定記録（2026-07-30）

第 2 条は本 RFC の設計レッドラインである：インポート面のセマンティクスは**新しい可視性キーワードを導入してはならず**、「配布境界」（ファイルロール + 宣言エクスポート面）のみがそれを担う。

4 つの消費者がそれぞれ同じ壁にぶつかっている：

| 消費者                                                         | 衝突点                                                                                                                                                                                                    |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 デッドコード警告                                          | 決定 B「pub = 外部インターフェースには決して警告しない」は「本物の対外」と「対外のように見える」を区別するロールモデルがないため；bin 内で未使用 pub を警告するか（案 A）は未だ保留                       |
| RFC-014c ワークスペース（レビュー中、#113）                    | メンバーパッケージ相互 `use` 時のインポート面の基準——`[exports]`、`[lib]` 単一ファイル、それとも全 pub ファイル——**本文にセマンティクス条文が一切ない**                                                   |
| RFC-015 設定システム（承認済み）                               | `[lib]` / `[[bin]]` / `[exports]` フィールドは定義済みだが、RFC-029 がエントリ優先度を消費した以外、他のフィールドのセマンティクス（特に `[exports]` と Registry 到達可能性の関係）は誰も整合させていない |
| RFC-037 パッケージング / RFC-029a キャッシュ（ドラフト、#293） | パッケージング成果物の選択、増分再コンパイルのキャッシュユニット境界、いずれもロールモデルが前提となる                                                                                                    |

### 現状の問題

**4 つのセマンティクス空白**（2026-09-12 棚卸し、014/014a/014b/014c/015/029 全本文を確認）：

1. **他パッケージのインポート面が未定義**。014c のメンバーパッケージ相互参照の例にはディレクトリ構造（`src/lib.yx`）しかなく、`use utils.helper`
   で何が取得できるかの条文がない。現在の暗黙ルールは「このパッケージの全トップレベル pub ファイル」——内部実装ファイルもネームスペースに引きずり込まれ、依存境界が形骸化している。
2. **デッドコード pub 免除の適用範囲がない**。#321 決定 B の「pub は決して警告しない」は単一ファイルスクリプトでは過度に保守的（スクリプトには外部消費者がなく、pub は無意味）、多ファイルプロジェクトのエントリファイルでは逆に過度に緩い（誰も import しないルートの pub はデッドコード）。ロールモデルがなければ、A/B 両案の分割線が引けない。
3. **3 つのエクスポート概念が整合していない**。`[exports]`（015、パスマッピング）、`[lib]`（015、単一ファイルパス）、Registry 到達可能性（029、エントリから use 経由で到達）——3 者が包含関係か等価関係か独立かは条文がない。
4. **用語衝突**。RFC-014b の `[binaries]`
   は**プリコンパイル配布成果物**（.so/exe のダウンロード優先戦略）であり、「bin ターゲット（ソースコードロール）」とは完全に別レイヤーの概念である。014c 落地後、両者は必ず同一画面に現れるため、早期に曖昧性を解消しないと誤解が継続する。

**実証：決定 B の保守性は既に実際の痛点**。#321
M2 レトロスペクティブ記録：デフォルト設定下で W1001–W1005 ファミリ全体がサイレントになる構造的原因はまさに「すべての pub が対外インターフェース扱いされる」——これはモデル欠如の補償行動であって、終局状態ではない。

## 提案

### 中核設計：ファイルロールモデル

**ロールはファイルレベルの属性**（015 のフィールド粒度と一致：`[lib]` は単一ファイル、`[[bin]]`
はファイルリスト、`[exports]` はファイルマッピング）であり、パッケージレベルのスイッチではない。

| ロール       | 判定                                                                                                                                     | セマンティクス                                                                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bin**      | `[run].main` / `[[bin]].path` が指すファイル；または（manifest なし時）`main` を含み、どのファイルからも `use` されていないファイル      | プログラムエントリ。その `pub` は**デッドコードとして警告され得る**（パッケージ外消費者がいない）；`main` は到達可能性ルート                                                     |
| **Lib**      | `[exports]` マッピングがヒットするファイル；または `[lib].path`；または（manifest なし時）他ファイルの `use` で参照されているファイル    | 配布境界。その `pub` は**デッドコードから免除**（パッケージ外消費者が見えないため、見逃しを許容）；これを経由してエクスポートされたシンボルは他パッケージから可視                |
| **Test**     | RFC-036 テストファイルルールがヒットするファイル（`tests/` ディレクトリ、`*_test.yx` 等の既存規約）；`[[test]]` 明示的宣言は**設けない** | テストコード。デッドコード判定に参加しない；その参照は被テストコードの到達可能性ルートに加算される                                                                               |
| **Internal** | パッケージに manifest がある時、エクスポート面にも main も含まないファイル                                                               | パッケージ内実装。`pub` は第 2 フェーズまで免除（パッケージ内 use グラフの到達可能性に基づき收紧、 Bin ロールのコーパス検証を前提とする）；パッケージ外 `use` からは**到達不能** |
| **Script**   | 単一ファイル直接実行（`run foo.yx`）のファイル                                                                                           | 動作は今日と完全に同一：Registry は std のみ、デッドコード pub セマンティクスの変更なし                                                                                          |

**判定優先度**：manifest 明示的宣言 > エントリ到達性推測 >
036 テスト規約。明示的宣言が常に勝つ——推測は宣言がない時のデフォルトに過ぎない。

### 例

```toml
# yaoxiang.toml（フィールドはすべて RFC-015 で定義済み、本 RFC は新設定面を追加しない）
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← 他パッケージ可視性を決定するのはこれであり、pub ではない
```

```yaoxiang
# src/cli.yx（Bin ロール）
pub unused_fn = (x: Int) => x    # ← W1001 として警告され得る：bin にはパッケージ外消費者がいない
main: () -> Void = { ... }

# src/lib.yx（Lib ロール、エクスポート面にある）
pub api_fn = ...                 # ← 決して警告されない：パッケージ外消費者が見えない

# src/other.yx（Internal ロール、エクスポート面にない）
pub semi_api = ...               # ← 第 2 フェーズまで免除（見逃しを許容）、その時点で use グラフに基づき收紧
```

### インポート面のセマンティクス

他パッケージ `use pkg.x` の解決順序（最初にヒットしたものが有効）：

1. `[exports]` マッピングが存在 → インポート面 = マッピングが列挙するファイル集合、`x`
   はこれらのファイルのトップレベルバインディングに存在しなければならない；
2. そうでなく `[lib].path` が存在 → インポート面 = その単一ファイル；
3. どちらもなし（manifest なしの依存、パス依存の裸ディレクトリ）→
   **現状維持**：全トップレベルファイルがインポート可能（既存動作と互換、收紧は別途議論）。

**ワークスペースメンバー**：エクスポート面はメンバーパッケージ自身の manifest のみで定義され、ワークスペースルートはメンバーのエクスポート面を覆ったり拡張したりしてはならない——メンバー自己完結は 014c の中核設計であり、ルートによる上書きはカプセル化を破壊する。

Registry 到達可能性との関係（029 と整合）：`[exports]`/`[lib]`
は**他パッケージ解決の合法起点集合**を定義する；起点が確定した後、Registry は引き続き 029 の「エントリから
`use` 経由で到達」に従って拡張する——エクスポートファイル自身が `use`
した内部ファイルはリンクに伴って入るが、新たな他パッケージ起点を生成しない。

### 既存計画との境界画定

| 隣接 RFC                                           | 境界                                                                                                                                                                                                                      |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-029d「CLI `--entry` エントリ上書き」（計画中） | 029f がロールモデルを定義；029d がそれを消費する——`--entry` は Bin ロールの CLI レベル上書き手段                                                                                                                          |
| RFC-014b `[binaries]`                              | **用語曖昧性解消**：`[binaries]` はプリコンパイル配布成果物（ダウンロード優先戦略）、`[[bin]]` はソースコードロール宣言。前者は依存パッケージの manifest に存在し、後者は本パッケージの manifest に存在し、相互に交換不可 |
| RFC-014c ワークスペース                            | メンバーパッケージ相互参照のインポート面 = 本 RFC の解決順序；ワークスペース調整メカニズム（members、共有 lockfile）は引き続き 014c                                                                                       |
| RFC-036 テスト                                     | Test ロール判定は 036 の既存ファイルルールを直接採用、新規約を追加しない                                                                                                                                                  |
| #321 デッドコード                                  | 決定 B（pub 一律免除）を「target なし時の過渡セマンティクス」に明示的に降格；Bin ロールの pub 警告は本 RFC による案 A の実現形態                                                                                          |

## 詳細設計

### ロール判定アルゴリズム（オーケストレーター内）

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. 明示レイヤ：manifest 宣言を優先
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. 推測レイヤ：宣言がない箇所はエントリ到達性に従う
    for f in files where role[f] 未定:
        if f が ≥1 個の非自身ファイルに use されている:  role[f] = Lib
        elif f が main を含み他ファイルが use していない: role[f] = Bin
        else:                              role[f] = Internal

    # 3. テストレイヤ：036 ルールヒット → Test（Lib/Internal を覆う、明示的 Bin は覆わない）
    apply_rfc036_test_rules(files, &role)

    # 単一ファイル直接実行：モデル全体をバイパス、動作不変
    if no manifest and single_file:      all Script
```

### コンパイラー変更

- `frontend/config.rs`：manifest 解析に `[exports]`
  → ロールテーブルのマッピングを追加（フィールド解析は 015 に既存）。
- `frontend/module/orchestrator.rs`：Registry 構築前にロール分類フェーズを挿入；他パッケージ解決はインポート面順序に従って
  `use` ターゲットを検証し、範囲外は既存の `module_not_found`
  ファミリで報告（エラーコードは追加せず、メッセージに「エクスポート面にない」のヒントを追加）。
- `typecheck/passes/dead_code.rs`：エントリポイント集合を「main + 全 pub」から「main +
  Lib ロールファイルの pub」に変更（Bin は即座に警告可能；Internal は第 2 フェーズまで免除、Phase
  2 は実装戦略を参照）。
- LSP（RFC-017）：補完/ホバーの「インポート可能項目」をインポート面でフィルタ；`main`
  欠如診断は Bin ロールファイルのみに報告。

### ランタイム動作

変更なし。ロールモデルは純粋にコンパイル時/解析時のセマンティクスであり、IR と実行に影響しない。

### 後方互換性

- manifest なしプロジェクト：動作は完全に不変（推測レイヤは現状を再現——use されるものは Lib、main を含むものは Bin）。デッドコード警告の増分は Bin ファイルのみ：誰も import しないルートの未使用 pub がサイレントから W1001 になる——これは #321 案 A の期待動作であり、破壊ではない。
- manifest ありプロジェクト：`[exports]`
  が宣言済みの場合、インポート面が「全 pub ファイル」から宣言面へ收紧される。**これが唯一の動作收紧点**：他人のパッケージ内部ファイルに依存するコードが
  `module_not_found`
  を報告し始める。パッケージエコシステムがまだ確立されていない（029：「現在サードパーティパッケージエコシステムなし」）ことを鑑みると、破壊面はゼロ；それでもマイナー バージョンの過渡期を設ける（範囲外は先に警告、後でエラー）。

## トレードオフ

### 利点

- 新規設定面ゼロ：フィールドはすべて 015 で定義済み、本 RFC はセマンティクスのみを補完。
- 新規キーワードゼロ：インポート面は配布境界が担い、029「可視性不存在」決定と同型。
- 4 つの消費者（#321 / 014c / 029a /
  037）を一度にモデリング、それぞれが個別に壁にぶつかることはなくなる。
- manifest なしパスはゼロコスト：スクリプト言語のゼロコンフィグ遺伝子を完全に保持。

### 欠点

- ロール推測（use されたら Lib）は「エントリファイルがユーティリティファイルを use する」一般的形態でユーティリティファイルを Lib と判定し、その pub を免除する——理想粒度より緩い。これは見逃し許容方向の意図的選択であり、收紧には use グラフ上の呼び出し方向分析が必要、第 1 版では実施しない。
- `[exports]` によるインポート面の收紧は破壊的なセマンティクス收紧である（過渡期はあるが）。

## 代替案

| 案                                      | 説明                                                                                      | 不採用の理由                                                                                                                                                                                   |
| --------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トップレベル RFC-040                    | 新たにトップレベル番号を振る                                                              | モジュールグラフのセマンティクス（インポート面/到達可能性/エントリ）はすべて 029 の領地、トップレベルに分けると同一対象に 2 つのトップレベル文書が並ぶ；029b–029e のスロットパターンも既に確立 |
| 014c に取り込み                         | workspace の一セクションとして                                                            | 依存方向が逆：言語層（029x）がセマンティクスを定義し、パッケージ層（014x）が消費する。014c はまだレビュー中で、途中で範囲を広げるとその落地を遅延させる                                        |
| 案 A そのまま（#321 メニュー）          | manifest で `[[bin]]`/`[[lib]]` target を強制して初めてデッドコードセマンティクスを有効化 | 狭いスライス（main を持つルートファイルの未使用 pub）のために強制設定を導入；本 RFC の推測レイヤでゼロコンフィグで同等の利益を得る                                                             |
| 純粋エントリ推測（manifest レイヤなし） | 015 フィールドを消費しない                                                                | `[exports]` は既に 015 承認済みフィールドであり、他パッケージのインポート面はこれを回避できない；定義しないことは 014c に空白を残すことになる                                                  |

## 実装戦略

### フェーズ分け

- **Phase 1**：ロール分類 + インポート面解決 + Bin pub 警告可能（Internal/Test は引き続き免除）
- **Phase 2**：Internal
  pub を「パッケージ内 use グラフで到達不能なら警告可能」に收紧——前提条件は Phase
  1 落地後に Bin ロールの警告コーパス検証で誤報コールバックがないこと；トリガーされ次第実施、スケジュールは設けない

### 依存関係

- 前提：RFC-029 オーケストレーター（落地済み）、RFC-015 manifest フィールド（定義済み）。
- 被依存：#321（Bin
  pub 警告可能）、RFC-014c（インポート面）、RFC-029a（ロールをキャッシュユニット境界として）、RFC-037（成果物選択）、RFC-029d（`--entry`
  上書き）。
- RFC-014c との落地順序：014c のレビュー承認前に、029f のインポート面順序を先に確定し、014c は参照形式で消費する。レビュー途中での範囲拡張を避ける。

### リスク

- ロール推測とユーザー直感との乖離（前出トレードオフ第 1 条）→ 増分動作はすべて警告（ブロックしない）形式で提示、いつでも無効化可能。
- `[exports]` 收紧の過渡期管理 → マイナーバージョン内で先に警告。

## オープン問題

ドラフト段階の 3 項目はすべて決定済み（2026-09-13、決議は付録 B と本文に記録）、未決事項なし：

- [x] Internal pub を收紧するか →
      **決定**：第 2 フェーズでパッケージ内 use グラフの到達可能性に基づき收紧、Bin ロールコーパス検証を前提とする（実装戦略 Phase
      2 参照）
- [x] `[[test]]` 明示的宣言 →
      **決定**：導入しない、Test ロールは 036 ルールのみで判定；036 将来自明宣言の必要性が出た場合は 036 自身が拡張
- [x] ワークスペースルートによるメンバーエクスポート面上書き →
      **決定**：許可しない、メンバー自己完結は 014c の中核設計、ルート上書きはカプセル化を破壊する

## 付録 B：設計決定記録

> **訂正（2026-09-17）：ロールモデルがエントリセマンティクスを駆動**
>
> 本 RFC は 5 つのロールと「誰がエントリか」の意味を定義したが（Bin 行の「`main`
> は到達可能性ルート」）、初版実装はロールを**デッドコード警告**にのみ使用し、エントリ検索はロールと無関係だった——`find_entry_point`
> が `main`
> を見つけられないと 0 を返し、**関数テーブルの最初の関数をサイレント実行**する。トップレベルバインディング再構築（T4）でロールモデルをエントリ判定に接続、具体的なルールは以下の通り：
>
> | ロール                      | エントリルール                                                                                                                                                                          |
> | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
> | **Script**（manifest なし） | **エントリ概念なし**。トップレベル文（バインディング初期化含む）は記述順がそのままプログラム本体；`main` は通常のバインディング、**自動呼び出ししない**——実行したいなら `main()` と書く |
> | **Bin**（manifest あり）    | `main` を要求し関数でなければならない；さもなければコンパイルエラー（E3020 main 欠如 / E3021 main が関数でない）。トップレベルに実行可能文を置いてはならない                            |
> | **Lib / Internal / Test**   | `main` を要求しない（これらはエントリではない）                                                                                                                                         |
>
> **本 RFC 初版記述との 2 つの差異**：
>
> 1. 初版 Script 行は「動作は今日と完全に同一」と書いていた。今日の動作には 2 つのサイレント欠陥があり、いずれも T4 で修正された：①
>    `main`
>    がない時に関数テーブルの最初の関数を実行する；② トップレベル文が E3005 実行不可を報告する。現在の Script のトップレベル文は**実行可能**であり、これは現状維持ではなく新機能である。
> 2. 「Script 下で `main` は特殊扱いしない」と「Bin 下で `main`
>    はエントリ」は**相互排他**でなければならない：Script がトップレベル文を実行しつつ暗黙に `main`
>    を呼び出すと、明示的に `main()`
>    と書いたスクリプトが二重実行される（#356）。よって Script にはただ 1 つの実行エントリ——トップレベル文——しかない。
>
> **ロール判定とエントリ判定の違い**（実装注記）：エントリ判定は「manifest の有無」（`find_project_root().is_some()`）を用い、`roles::classify()`
> は用いない。理由：classify は「このファイルが誰に消費されるか」に答える（デッドコード分析に奉仕する）；manifest があるのに
> `main`
> がないファイルは classify では Internal（他ファイルに use されない、理にかなう）が、ユーザーがそれをエントリとして走らせた場合、エントリがなければならない。2 つの問題は異なり、判定基準も自ずと異なる。
>
> 詳細は `docs/src/reference/language-spec/syntax.md` §3.11 を参照。

## 付録 C：用語集

| 用語                           | 定義                                                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------------------------------- |
| ロール（Role）                 | ソースファイルのコンパイルターゲット身份：Script / Bin / Lib / Test / Internal                       |
| インポート面（Import Surface） | 他パッケージ `use` 時の合法解析起点ファイル集合、`[exports]`/`[lib]` 宣言または推測で決定            |
| 配布境界                       | 029 用語：パッケージの対外露出範囲；本 RFC はこれを暗黙的（全 pub ファイル）からインポート面に精緻化 |
| Script 態                      | manifest なし単一ファイル直接実行のバイパス形態、すべての動作は現状と同一                            |
