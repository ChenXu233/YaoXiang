# RFC-029f: コンパイルターゲットロールとインポート面セマンティクス

## 概要

RFC-029「子RFC計画」の延長スロット（029b–029eは占有済み、029fに順送り）の履行：ソースファイルに対して**コンパイルターゲットロールモデル**（Script
/ Bin / Lib / Test /
Internalの5種類）およびその**インポート面セマンティクス**を定義する——manifestがない場合はエントリの到達性から推測（ゼロコンフィグ）、manifestがある場合は`[lib]`
/ `[[bin]]` /
`[exports]`（RFC-015で定義済みのフィールド）で明示宣言する。4つの宙ぶらりんセマンティクスを埋める：クロスパッケージのインポート面の算出基準、デッドコード警告の`pub`免除の適用範囲（#321決定案B）、`[exports]`とRegistryの到達性の関係、およびRFC-014b
`[binaries]`（プリコンパイル配布物）とbinロールソースファイルの名称の曖昧性解消。

## 動機

### ホストと境界の根拠

RFC-029（承認済み）のエントリ選択と可視性に関する決定は本RFCの直接の上流である：

> **エントリファイル選択**の優先順位：1. `[run].main` 2. `[[bin]]`の最初の項目の`path` 3.
> `src/main.yx`（規約上のデフォルト）。—— RFC-029 §パッケージ間循環：再論

> **可視性**：存在しない。スコープ + 配布境界がすべてのシナリオをカバーし、新しいキーワードは必要ない。——
> RFC-029 §設計決定記録（2026-07-30）

2つ目は本RFCの設計上のレッドラインである：インポート面セマンティクスは**新しい可視性キーワードを導入してはならず**、「配布境界」（ファイルロール + 明示エクスポート面）でのみ担う。

4つの消費者がそれぞれ同じ壁にぶつかった：

| 消費者                                                       | 衝突点                                                                                                                                                                                              |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 デッドコード警告                                        | 決定案B「pub = 対外インターフェースは決して報告しない」は「真の対外」と「対外のように見える」を区別するロールモデルがないため；bin内の未使用pubを報告するかどうか（案A）は今まで保留                |
| RFC-014cワークスペース（レビュー中、#113）                   | メンバーパッケージが相互に`use`する際、インポート面をどう算出するか——`[exports]`、`[lib]`単一ファイル、それともすべてのpubファイル——**本文中にセマンティクス条文が一つもない**                      |
| RFC-015設定システム（承認済み）                              | `[lib]` / `[[bin]]` / `[exports]`フィールドは定義済みだが、RFC-029がエントリ優先順位を消費した以外、他のフィールドのセマンティクス（特に`[exports]`とRegistryの到達性の関係）は誰も整合させていない |
| RFC-037パッケージング / RFC-029aキャッシュ（ドラフト、#293） | パッケージング成果物の選択、インクリメンタル再コンパイルのキャッシュユニット境界、いずれもロールモデルが前提として必要                                                                              |

### 現状の問題

**4つのセマンティクス空白**（2026-09-12 棚卸し、014/014a/014b/014c/015/029の全文を確認）：

1. **クロスパッケージインポート面が未定義**。014cのメンバーパッケージ相互参照の例にはディレクトリ構造（`src/lib.yx`）しかなく、`use utils.helper`で何が取得できるかについて何の条文もない。現在の暗黙ルールは「このパッケージのすべてのトップレベルpubファイル」——内部実装ファイルも名前空間に取り込まれ、依存境界は名ばかりである。
2. **デッドコードpub免除に適用範囲がない**。#321決定案Bの「pubは決して報告しない」は単一ファイルスクリプトでは過度に保守的で（スクリプトには外部消費者がおらず、pubは無意味）、複数ファイルプロジェクトのエントリファイルでは逆に過度に寛容である（誰もimportしないルートファイルのpubはデッドコード）。ロールモデルがないため、案A/Bの切り分け線が引けない。
3. **3つのエクスポート概念が誰も整合させていない**。`[exports]`（015、パスマッピング）、`[lib]`（015、単一ファイルパス）、Registry到達性（029、エントリからuseに沿って到達可能）——3者の関係が包含関係か、等価関係か、それぞれ独立か、条文がない。
4. **名称衝突**。RFC-014bの`[binaries]`は**プリコンパイル配布物**（.so/exeダウンロード優先戦略）であり、「binターゲット（ソースコードロール）」とは完全に異なる層である。014cが実装された後、両者は必ず同じ画面に出現し、早めに曖昧性を解消しなければ誤解が続く。

**実証：決定案Bの保守性はすでに実際の痛点である**。#321
M2のレトロスペクティブ記録：デフォルト設定下でW1001–W1005の全ファミリーが沈黙している構造的原因は、まさに「すべてのpubが対外インターフェースとして扱われている」こと——これはモデル欠如の補償行動であり、終着点ではない。

## 提案

### 中核設計：ファイルロールモデル

**ロールはファイルレベルの属性である**（015のフィールド粒度と一致：`[lib]`は単一ファイル、`[[bin]]`はファイルリスト、`[exports]`はファイルマッピング）、パッケージレベルのスイッチではない。

| ロール       | 判定                                                                                                                                     | セマンティクス                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bin**      | `[run].main` / `[[bin]].path`が指すファイル；または（manifestがない場合）`main`を含み、どのファイルからも`use`されていないファイル       | プログラムエントリ。その`pub`は**デッドコードとして報告可能**（パッケージ外消費者がいない）；`main`は到達性ルート                                                  |
| **Lib**      | `[exports]`マッピングがヒットしたファイル；または`[lib].path`；または（manifestがない場合）他のファイルの`use`から参照されているファイル | 配布境界。その`pub`は**デッドコード判定を免除**（パッケージ外消費者には不可、見逃しを許容）；それを経由してエクスポートされたシンボルはクロスパッケージで可視      |
| **Test**     | RFC-036のテストファイルルールがヒットしたファイル（`tests/`ディレクトリ、`*_test.yx`等の既存規約）；**`[[test]]`明示宣言は設けない**     | テストコード。デッドコード判定に参加しない；その参照は被テストコードの到達性ルートに算入                                                                           |
| **Internal** | パッケージにmanifestがある場合、エクスポート面にもmainにも含まれないファイル                                                             | パッケージ内実装。`pub`は第二フェーズまで免除（パッケージ内useグラフの到達性に基づき收紧、をBinロールのコーパス検証を前提とする）；パッケージ外`use`は**到達不能** |
| **Script**   | 単一ファイル直接実行（`run foo.yx`）のファイル                                                                                           | 動作は今日と完全に一致：Registryはstdのみ、デッドコードpubのセマンティクス変化なし                                                                                 |

**判定優先順位**：manifest明示宣言 > エントリ到達性推測 >
036テスト規約。明示宣言は常に勝つ——推測は宣言がない場合のデフォルトに過ぎない。

### 例

```toml
# yaoxiang.toml（字段全部是 RFC-015 已定义的，本 RFC 不新增配置面）
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← 决定跨包可见性的是它，不是 pub
```

```yaoxiang
# src/cli.yx（Bin 角色）
pub unused_fn = (x: Int) => x    # ← W1001 可报：bin 无包外消费者
main: () -> Void = { ... }

# src/lib.yx（Lib 角色，在导出面上）
pub api_fn = ...                 # ← 永不报：包外消费者不可见

# src/other.yx（Internal 角色，不在导出面）
pub semi_api = ...               # ← 豁免至二阶段（宁漏报），届时按 use 图收紧
```

### インポート面セマンティクス

クロスパッケージ`use pkg.x`の解決順序（最初にヒットしたものが有効）：

1. `[exports]`マッピングが存在する → インポート面 = マッピングに記載されたファイルの集合、`x`はこれらのファイルのトップレベルバインディングに存在しなければならない；
2. そうでない場合、`[lib].path`が存在する → インポート面 = その単一ファイル；
3. どちらも存在しない（manifest依存なし、パス依存の生ディレクトリ）→
   **現状維持**：すべてのトップレベルファイルがインポート可能（既存動作と互換、收紧は別途議論）。

**ワークスペースメンバー**：エクスポート面はメンバーパッケージ自身のmanifestのみで定義され、workspaceルートはメンバーのエクスポート面をオーバーライドまたは拡張してはならない——メンバー自己完結は014cの核心設計であり、ルートオーバーライドはカプセル化を破壊する。

Registryの到達性との関係（029との整合）：`[exports]`/`[lib]`が定義するのは**クロスパッケージ解決の正当な始点集合**である；始点が決定された後、Registryは引き続き029の「エントリから`use`に沿って到達可能」に従って拡張される——エクスポートファイル自身が`use`で取り込んだ内部ファイルはリンクに従って取り込まれるが、新たなクロスパッケージ始点は生成しない。

### 既存計画との境界

| 隣接                                                            | 境界                                                                                                                                                                                                            |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-029d「CLI `--entry`によるエントリオーバーライド」（計画中） | 029fがロールモデルを定義；029dがそれを消費する——`--entry`はBinロールのCLIレベルオーバーライド手段                                                                                                               |
| RFC-014b `[binaries]`                                           | **名称の曖昧性解消**：`[binaries]`はプリコンパイル配布物（ダウンロード優先戦略）、`[[bin]]`はソースコードロール宣言。前者は依存パッケージのmanifestに存在し、後者は本パッケージのmanifestに存在し、相互交換不可 |
| RFC-014cワークスペース                                          | メンバーパッケージ相互参照のインポート面 = 本RFCの解決順序；workspaceの調整メカニズム（members、共有lockfile）は引き続き014cに帰属                                                                              |
| RFC-036テスト                                                   | Testロール判定は036の既存ファイルルールを直接採用し、新たな規約を追加しない                                                                                                                                     |
| #321デッドコード                                                | 決定案B（pubを一律免除）を明示的に「ターゲットがない場合の過渡的セマンティクス」に降格；Binロールのpub報告可能は本RFCで案Aを実現する形態                                                                        |

## 詳細設計

### ロール判定アルゴリズム（オーケストレーター内）

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. 显式层：manifest 声明优先
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. 推断层：无声明处按入口可达性
    for f in files where role[f] 未定:
        if f 被 ≥1 个非自身文件 use:      role[f] = Lib
        elif f 含 main 且无其他文件 use 它: role[f] = Bin
        else:                             role[f] = Internal

    # 3. 测试层：036 规则命中 → Test（覆盖 Lib/Internal，不覆盖显式 Bin）
    apply_rfc036_test_rules(files, &role)

    # 单文件直跑：整个模型旁路，行为不变
    if no manifest and single_file:      all Script
```

### コンパイラー変更

- `frontend/config.rs`：manifest解析に`[exports]`
  → ロールテーブルのマッピングを追加（フィールド解析は015で既存）。
- `frontend/module/orchestrator.rs`：Registry構築前にロール分類フェーズを挿入；クロスパッケージ解決はインポート面順に従って`use`ターゲットを検証し、範囲外は既存の`module_not_found`ファミリーで報告（新たなエラーコードは追加せず、メッセージに「エクスポート面にない」のヒントを追加）。
- `typecheck/passes/dead_code.rs`：エントリポイント集合を「main + すべてpub」から「main +
  Libロールファイルのpub」に変更（Binは即座に報告可能；Internalは第二フェーズまで免除、Phase
  2は実装戦略を参照）。
- LSP（RFC-017）：補完/ホバーの「インポート可能項目」をインポート面でフィルタリング；`main`欠落診断はBinロールファイルに対してのみ報告。

### ランタイム動作

変化なし。ロールモデルは純粋にコンパイル時/解決時のセマンティクスであり、IRと実行に影響しない。

### 後方互換性

- manifestなしプロジェクト：動作は完全に不変（推測層が現状を再現——`use`されているものはLib、`main`を含むものはBin）。デッドコード警告の追加はBinファイルのみ：誰もimportしないルートファイルの未使用pubが沈黙からW1001に変化する——これは#321案Aの期待動作であり、破壊ではない。
- manifestありプロジェクト：`[exports]`が宣言されている場合、インポート面が「すべてのpubファイル」から宣言面に收紧される。**これが唯一の動作收紧点**：他人パッケージの内部ファイルに依存するコードは`module_not_found`を報告し始める。パッケージエコシステムがまだ確立していない（029：「現在サードパーティパッケージエコシステムはない」）ため、破壊面ゼロ；それでもマイナーバージョン移行期間を設ける（範囲外はまず警告、エラーは後）。

## トレードオフ

### 利点

- 新規コンフィグ面ゼロ：フィールドはすべて015で定義済み、本RFCはセマンティクスのみを補完。
- 新規キーワードゼロ：インポート面は配布境界が担い、029「可視性は存在しない」決定と同形。
- 4つの消費者（#321 / 014c / 029a /
  037）を一度にモデル化し、それぞれが別々の壁にぶつかることはなくなる。
- manifestなしパスはゼロコスト：スクリプト言語のゼロコンフィグ遺伝子を完全に保持。

### 欠点

- ロール推測（`use`されている＝Lib）は「エントリファイルがツールファイルを`use`する」という一般的な形態でツールファイルをLibと判定し、そのpubが免除される——理想粒度より広い。これは見逃し許容方向の意図的な選択であり、收紧にはuseグラフ上の呼び出し方向分析が必要で、初版では行わない。
- `[exports]`によるインポート面の收紧は破壊的なセマンティック收紧である（移行期間はあるが）。

## 代替案

| 案                                 | 説明                                                                                    | 不採用の理由                                                                                                                                                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トップレベルRFC-040                | 新たにトップレベル番号を割り当てる                                                      | モジュールグラフセマンティクス（インポート面/到達性/エントリ）はすべて029の領域であり、トップレベルを分けると同一オブジェクトに対して2つのトップレベル文書が作成される；さらに029b–029eのスロットパターンが既に確立 |
| 014cに含める                       | workspaceの一セクションとして                                                           | 依存方向が逆：言語層（029x）がセマンティクスを定義し、パッケージ層（014x）がセマンティクスを消費する。014cはまだレビュー中で、途中で範囲を拡大するとその実装が滞る                                                  |
| 案Aそのまま（#321メニュー）        | manifestが`[[bin]]`/`[[lib]]`ターゲットを強制して初めてデッドコードセマンティクスが適用 | 狭いスライス（mainを持つルートファイルの未使用pub）のために強制コンフィグを導入；本RFCの推測層はゼロコンフィグで同等の効果を得る                                                                                    |
| 純粋エントリ推測（manifest層なし） | 015フィールドを消費しない                                                               | `[exports]`はすでに015で承認されたフィールドであり、クロスパッケージインポート面はこれを回避できない；定義しないことは014cに空白を残すことと同義                                                                    |

## 実装戦略

### 段階分け

- **Phase 1**：ロール分類 + インポート面解決 + Bin pub報告可能（Internal/Testは免除を維持）
- **Phase 2**：Internal pubを「パッケージ内useグラフで到達不能なら報告可能」に收紧——前提条件はPhase
  1実装後、Binロール警告コーパス検証で誤報がないことの確認；トリガー次第で実施、タイムテーブルは設けない

### 依存関係

- 前提：RFC-029オーケストレーター（実装済み）、RFC-015 manifestフィールド（定義済み）。
- 依存される側：#321（Bin
  pub報告可能）、RFC-014c（インポート面）、RFC-029a（キャッシュユニット境界としてのロール）、RFC-037（成果物選択）、RFC-029d（`--entry`オーバーライド）。
- RFC-014cとの実装順序：014cのレビュー承認前に、029fのインポート面順序を先に確定し、014cは参照方式で消費し、レビュー途中での範囲拡大を避ける。

### リスク

- ロール推測とユーザーの直感とのずれ（前述のトレードオフ第一条）→ すべての追加動作を警告（ブロックしない）形式で提示し、いつでも無効化可能とする。
- `[exports]`收紧の移行期間管理 → マイナーバージョン内ではまず警告。

## 未解決問題

ドラフト段階の3項目はすべて決定済み（2026-09-13、決議は付録Bと本文に記載）、未決事項なし：

- [x] Internal pubを收紧するかどうか →
      **決定**：第二フェーズでパッケージ内useグラフの到達性に基づき收紧、Binロールコーパス検証を前提とする（実装戦略Phase
      2参照）
- [x] `[[test]]`明示宣言 →
      **決定**：導入しない、Testロールは036ルールのみで判定；036が将来明示宣言を必要とする場合は036自身が拡張する
- [x] workspaceルートによるメンバーエクスポート面のオーバーライド →
      **決定**：許可しない、メンバー自己完結は014cの核心設計であり、ルートオーバーライドはカプセル化を破壊する

## 付録B：設計決定記録

> **訂正（2026-09-17）：ロールモデルがエントリセマンティクスを駆動する**
>
> 本RFCは5つのロールと「誰がエントリか」の意味を定義したが（Bin行の「`main`は到達性ルート」）、初版実装ではロールを**デッドコード警告**にのみ使用し、エントリ検索は常にロールと無関係であった——`find_entry_point`が`main`を見つけられないと0を返し、**関数テーブルの最初の関数を静かに実行する**。トップレベルバインディング再構築（T4）により、ロールモデルがエントリ判定に接続され、具体的なルールは以下の通り：
>
> | ロール                     | エントリルール                                                                                                                                                                                 |
> | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
> | **Script**（manifestなし） | **エントリ概念なし**。トップレベル文（バインディング初期化を含む）は記述順にプログラム本体となる；`main`は通常のバインディングであり、**自動呼び出しされない**——実行したい場合は`main()`と書く |
> | **Bin**（manifestあり）    | `main`を要求し、関数でなければならない；さもなければコンパイルエラー（E3020 main欠落 / E3021 mainが関数でない）。トップレベルに実行可能文は許されない                                          |
> | **Lib / Internal / Test**  | `main`を要求しない（これらはエントリではない）                                                                                                                                                 |
>
> **本RFC初版記述との2つの相違点**：
>
> 1. 初版Script行には「動作は今日と完全に一致」と書かれていた。今日の動作には2つの静かな欠陥が含まれており、いずれもT4で修正された：①
>    `main`がないときに関数テーブルの最初の関数を実行する；② トップレベル文がE3005で実行不可と報告される。現在のScriptのトップレベル文は**実行可能**であり、これは現状維持ではなく新たな能力である。
> 2. 「Script下で`main`は特別扱いされない」と「Bin下で`main`はエントリ」は**相互排他**でなければならない：Scriptがトップレベル文を実行しつつ暗黙的に`main`を呼び出すと、明示的に`main()`を書いたスクリプトが二重実行される（#356）。したがってScriptにはトップレベル文という1つの実行入口しかない。
>
> **ロール判定とエントリ判定の違い**（実装注記）：エントリ判定は「manifestの有無」（`find_project_root().is_some()`）を使用し、`roles::classify()`は使用しない。理由：classifyは「このファイルが誰に消費されるか」に答える（デッドコード分析に役立つ）；manifestがあるのに`main`がないファイルはclassifyではInternalとなる（他ファイルから`use`されないため妥当）、しかしユーザーがそれをエントリとして実行する場合、エントリが必要である。2つの問題は異なるため、判定基準も異なる。
>
> 詳細は`docs/src/reference/language-spec/syntax.md` §3.11を参照。

| 用語                           | 定義                                                                                                      |
