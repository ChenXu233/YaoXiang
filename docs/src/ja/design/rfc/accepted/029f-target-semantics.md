# RFC-029f: コンパイルターゲット役割とインポート面セマンティクス

## 概要

RFC-029「子 RFC 規劃」の延長スロット（029b–029e は占有済み、029f に順延）の実現：ソースファイルに対して**コンパイルターゲット役割モデル**（Script
/ Bin / Lib / Test /
Internal の 5 種類）とその**インポート面セマンティクス**を定義する——manifest がない場合はエントリ到達性から推測（ゼロ設定）、manifest がある場合は
`[lib]` / `[[bin]]` /
`[exports]`（RFC-015 で既に定義されたフィールド）によって明示的に宣言する。4 項目の空白セマンティクスを埋める：他パッケージのインポート面の算出基準、デッドコード警告の pub 免除適用範囲（#321 決定 B）、`[exports]`
と Registry 到達性の関係、および RFC-014b
`[binaries]`（事前コンパイル配布成果物）と bin 役割ソースファイルの名称の曖昧性解消。

## 動機

### ホストと境界の根拠

RFC-029（受け入れ済み）のエントリ選択と可視性決定は本 RFC の直接の上流である：

> **エントリファイル選択**優先順位：1. `[run].main` 2. `[[bin]]` 第一項の `path` 3.
> `src/main.yx`（規約デフォルト）。—— RFC-029 §パッケージ間循環：再説

> **可視性**：存在しない。スコープ + 配布境界が全シナリオをカバーし、新しいキーワードを必要としない。——
> RFC-029 §設計決定記録（2026-07-30）

第二項は本 RFC の設計の赤線である：インポート面セマンティクスは**新しい可視性キーワードを導入してはならず**、「配布境界」（ファイル役割 + 宣言エクスポート面）のみが担うべきである。

4 つの消費者がそれぞれ同じ壁にぶつかっている：

| 消費者                                                     | 衝突点                                                                                                                                                                                                      |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 デッドコード警告                                      | 決定 B「pub = 外部インターフェースには決して報告しない」は「真の外部」と「外部のように見える」を区別する役割モデルがないため；bin 内で未使用の pub を報告するかどうか（方案 A）が今に至まで保留             |
| RFC-014c ワークスペース（審査中、#113）                    | メンバーパッケージ相互の `use` 時のインポート面基準——`[exports]`、`[lib]` 単一ファイル、それとも全 pub ファイル——**本文にセマンティクス条文が一切ない**                                                     |
| RFC-015 設定システム（受け入れ済み）                       | `[lib]` / `[[bin]]` / `[exports]` フィールドは定義済みだが、RFC-029 がエントリ優先順位を消費した以外、その他のフィールドのセマンティクス（特に `[exports]` と Registry 到達性の関係）は誰も整合させていない |
| RFC-037 パッケージング / RFC-029a キャッシュ（草案、#293） | パッケージング成果物の選択、増分再コンパイルのキャッシュユニット境界、いずれも役割モデルを前提とする                                                                                                        |

### 現在の問題

**4 項目のセマンティクス空白**（2026-09-12 棚卸、014/014a/014b/014c/015/029 全文で確認）：

1. **他パッケージのインポート面が未定義**。014c のメンバーパッケージ相互参照の例にはディレクトリ構造（`src/lib.yx`）しかなく、`use utils.helper`
   で何が取得できるかの条文がない。現在の暗黙ルールは「このパッケージの全トップレベル pub ファイル」——内部実装ファイルも名前空間に引きずり込まれ、依存境界は名ばかりである。
2. **デッドコード pub 免除の適用範囲がない**。#321 決定 B の「pub は決して報告しない」は単一ファイルスクリプトでは過度に保守的（スクリプトには外部消費者がなく、pub は無意味）であり、複数ファイルプロジェクトのエントリファイルでは過度に緩い（誰も import しないルートファイルの pub はデッドコード）。役割モデルがなければ、A/B 両案の分割線が引けない。
3. **3 つのエクスポート概念が整合されていない**。`[exports]`（015、パス写像）、`[lib]`（015、単一ファイルパス）、Registry 到達性（029、エントリから use 経由で到達可能）——3 者の包含関係、等価関係、あるいは各々が独立か、条文がない。
4. **名詞衝突**。RFC-014b の `[binaries]`
   は**事前コンパイル配布成果物**（.so/exe ダウンロード優先戦略）であり、「bin ターゲット（ソースコード役割）」とは完全に別レイヤーのものである。014c 実装後は両者が同画面に必ず出現する。早急に曖昧性を解消しないと誤解が継続的に発生する。

**実証：B 決定の保守性は既に実際の痛点**。#321
M2 復盤記録：デフォルト設定下で W1001–W1005 全族が静寂である構造的原因はまさに「全 pub が外部インターフェース扱い」——これはモデル欠如の補填動作であり、終状態ではない。

## 提案

### 中核設計：ファイル役割モデル

**役割はファイルレベル属性**である（015 のフィールド粒度と一致：`[lib]` は単一ファイル、`[[bin]]`
はファイルリスト、`[exports]` はファイル写像）、パッケージレベルスイッチではない。

| 役割         | 判定                                                                                                                                      | セマンティクス                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bin**      | `[run].main` / `[[bin]].path` が指すファイル；または（manifest がない場合）`main` を含み、どのファイルからも `use` されていないファイル   | プログラムエントリ。その `pub` は**デッドコード報告可**（パッケージ外消費者がない）；`main` は到達性ルート                                                      |
| **Lib**      | `[exports]` 写像に命中するファイル；または `[lib].path`；または（manifest がない場合）他のファイルの `use` によって参照されているファイル | 配布境界。その `pub` は**デッドコード免除**（パッケージ外消費者が見えない、過小報告を優先）；それを介してエクスポートされたシンボルは他パッケージで可視         |
| **Test**     | RFC-036 テストファイル規則に命中するファイル（`tests/` ディレクトリ、`*_test.yx` 等の既存規約）；`[[test]]` 明示的宣言は**設けない**      | テストコード。デッドコード判定に参加しない；その参照は被測定コードの到達性ルートに加算                                                                          |
| **Internal** | パッケージに manifest がある場合、エクスポート面にも main も含まないファイル                                                              | パッケージ内実装。`pub` はフェーズ 2 まで免除（パッケージ内 use グラフ到達性により厳格化、Bin 役割コーパス検証を前提とする）；パッケージ外 `use` は**到達不能** |
| **Script**   | 単一ファイル直接実行（`run foo.yx`）のファイル                                                                                            | 動作は今日と完全に一致：Registry は std のみ、デッドコード pub セマンティクスの変化なし                                                                         |

**判定優先順位**：manifest 明示的宣言 > エントリ到達性推測 >
036 テスト規約。明示的宣言は常に優先——推測は宣言がない場合のデフォルトのみ。

### 例

```toml
# yaoxiang.toml（フィールドは全て RFC-015 で既に定義済み、本 RFC は新しい設定面を追加しない）
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← 他パッケージ可視性を決定するのはこれであり、pub ではない
```

```yaoxiang
# src/cli.yx（Bin 役割）
pub unused_fn = (x: Int) => x    # ← W1001 報告可：bin にはパッケージ外消費者がない
main = { ... }

# src/lib.yx（Lib 役割、エクスポート面上）
pub api_fn = ...                 # ← 決して報告しない：パッケージ外消費者から見えない

# src/other.yx（Internal 役割、エクスポート面外）
pub semi_api = ...               # ← フェーズ 2 まで免除（過小報告優先）、その時点で use グラフに従って厳格化
```

### インポート面セマンティクス

他パッケージの `use pkg.x` の解析順序（最初に命中したものが有効）：

1. `[exports]` 写像が存在する → インポート面 = 写像に列挙されたファイル集合、`x`
   はこれらのファイルのトップレベルバインディングに存在しなければならない；
2. それ以外で `[lib].path` が存在する → インポート面 = その単一ファイル；
3. どちらもなし（manifest 依存なし、パス依存の裸ディレクトリ）→
   **現状維持**：全トップレベルファイルがインポート可能（既存動作と互換、絞り込みは別途議論）

**ワークスペースメンバー**：エクスポート面はメンバーパッケージ自身の manifest によってのみ定義され、workspace ルートはメンバーエクスポート面をカバーまたは拡張してはならない——メンバー自己完結は 014c の中核設計であり、ルートカバーはカプセル化を破壊する。

Registry 到達性との関係（029 と整合）：`[exports]`/`[lib]`
は**他パッケージ解析の合法な起点集合**を定義する；起点が確定した後、Registry は引き続き 029 の「エントリから
`use` 経由で到達可能」に従って拡張する——エクスポートファイル自身が `use`
で取り込んだ内部ファイルはリンクと共に進入するが、新たな他パッケージ起点を生成しない。

### 既存計画との境界画定

| 隣接                                                       | 境界                                                                                                                                                                                                                |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-029d「CLI `--entry` エントリオーバーライド」（計画中） | 029f は役割モデルを定義；029d はそれを消費する——`--entry` は Bin 役割の CLI レベルオーバーライド手段                                                                                                                |
| RFC-014b `[binaries]`                                      | **名詞曖昧性解消**：`[binaries]` は事前コンパイル配布成果物（ダウンロード優先戦略）、`[[bin]]` はソースコード役割宣言。前者は依存パッケージの manifest に存在し、後者は本パッケージ manifest に存在し、相互交換不可 |
| RFC-014c ワークスペース                                    | メンバーパッケージ相互参照のインポート面 = 本 RFC 解析順序；workspace 調整メカニズム（members、共有 lockfile）は引き続き 014c に帰属                                                                                |
| RFC-036 テスト                                             | Test 役割判定は 036 の既存ファイル規則を直接採用、新しい規約を追加しない                                                                                                                                            |
| #321 デッドコード                                          | 決定 B（pub 一律免除）は明示的に「target がない場合の過渡セマンティクス」に降格；Bin 役割の pub 報告可は本 RFC による方案 A の実現形態                                                                              |

## 詳細設計

### 役割判定アルゴリズム（オーケストレーター内）

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. 明示層：manifest 宣言優先
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. 推測層：宣言がない箇所はエントリ到達性に従う
    for f in files where role[f] 未定:
        if f が ≥1 個の非自身ファイルに use されている: role[f] = Lib
        elif f が main を含み、他のファイルが use していない: role[f] = Bin
        else:                             role[f] = Internal

    # 3. テスト層：036 規則に命中 → Test（Lib/Internal を上書き、明示的 Bin は上書きしない）
    apply_rfc036_test_rules(files, &role)

    # 単一ファイル直接実行：モデル全体をバイパス、動作不変
    if no manifest and single_file:      all Script
```

### コンパイラ変更

- `frontend/config.rs`：manifest 解析が `[exports]`
  → 役割表の写像を補完（フィールド解析は 015 で既存）。
- `frontend/module/orchestrator.rs`：Registry 構築前に役割分類段階を挿入；他パッケージ解析はインポート面順序に従って
  `use` ターゲットを検証、境界外は既存 `module_not_found`
  族（エラーコードを追加しない、メッセージに「エクスポート面にない」ヒントを追加）。
- `typecheck/passes/dead_code.rs`：エントリ点集合を「main + 全 pub」から「main +
  Lib 役割ファイルの pub」に変更（Bin は即座に報告可；Internal はフェーズ 2 まで免除、Phase
  2 は実装戦略を参照）。
- LSP（RFC-017）：補完/ホバーの「インポート可能項目」はインポート面でフィルタ；`main`
  欠落診断は Bin 役割ファイルに対してのみ報告。

### ランタイム動作

変化なし。役割モデルは純粋なコンパイル時/解析時セマンティクスであり、IR と実行に影響しない。

### 後方互換性

- manifest なしプロジェクト：動作は完全に不変（推測層が現状を復元——use されるものは Lib、main を含むものは Bin）。デッドコード警告の増分は Bin ファイルのみ：誰も import しないルートファイルの unused
  pub が静寂から W1001 に変化——これは #321 方案 A の予期される動作であり、破壊ではない。
- manifest ありプロジェクト：`[exports]`
  が宣言済みの場合、インポート面が「全 pub ファイル」から宣言面へ絞り込み。
  **これが唯一の動作絞り込み点**：他人的パッケージの内部ファイルに依存するコードは
  `module_not_found`
  を報告し始める。パッケージエコシステムがまだ確立されていない（029：「現在サードパーティパッケージエコシステムなし」）ため、破壊面がゼロ；それでもマイナーバージョンの過渡期を設定（境界外は先に警告、後にエラー）。

## トレードオフ

### 利点

- 新規設定面ゼロ：フィールドは全て 015 で既に定義済み、本 RFC はセマンティクスを補完するのみ。
- 新規キーワードゼロ：インポート面は配布境界が担い、029「可視性不存在」決定と同型。
- 4 つの消費者（#321 / 014c / 029a / 037）を一度にモデリング、それぞれ別々の壁にぶつからない。
- manifest なしパスのコストゼロ：スクリプト言語のゼロ設定遺伝子が完全に保持される。

### 欠点

- 役割推測（use されれば Lib）は「エントリファイルがユーティリティファイルを use する」一般的な形態でユーティリティファイルを Lib と判定し、その pub を免除する——理想粒度より広い。これは過小報告方向の意図的選択であり、厳格化には use グラフ上の呼び出し方向分析が必要、初回実装では行わない。
- `[exports]` によるインポート面絞り込みは破壊的なセマンティクス厳格化（過渡期はあるが）。

## 代替案

| 方案                                | 説明                                                                      | 不採用理由                                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トップレベル RFC-040                | 新たにトップレベル番号を割り当てる                                        | モジュール図セマンティクス（インポート面/到達性/エントリ）は全て 029 の領域、トップレベルに分けると同一対象に 2 つのトップレベル文書が生じる；また 029b–029e スロットパターンが既に確立 |
| 014c に組み込む                     | workspace の一節とする                                                    | 依存方向が逆：言語層（029x）がセマンティクスを定義、パッケージ層（014x）がセマンティクスを消費。014c はまだ審査中、途中で範囲を拡大するとその実装を遅らせる                             |
| 方案 A 原様（#321 メニュー）        | manifest 強制で `[[bin]]`/`[[lib]]` target のみデッドコードセマンティクス | 狭い切片（main 付きルートファイルの unused pub）に強制設定を導入；本 RFC の推測層はゼロ設定で同等の利益を得る                                                                           |
| 純粋エントリ推測（manifest 層なし） | 015 フィールドを消費しない                                                | `[exports]` は既に 015 で受け入れ済みフィールド、他パッケージインポート面はそれを避けられない；定義しないことは 014c に空白を残すことと同義                                             |

## 実装戦略

### 段階分け

- **Phase 1**：役割分類 + インポート面解析 + Bin pub 報告可（Internal/Test は引き続き免除）
- **Phase 2**：Internal
  pub を「パッケージ内 use グラフ到達不能なら報告可」に厳格化——前提条件は Phase
  1 実装後 Bin 役割警告コーパス検証で誤報コールバックがないこと；トリガー即時実行、スケジュールは設定しない

### 依存関係

- 前提：RFC-029 オーケストレーター（既に実装）、RFC-015 manifest フィールド（既に定義）。
- 被依存：#321（Bin
  pub 報告可）、RFC-014c（インポート面）、RFC-029a（役割をキャッシュユニット境界として）、RFC-037（成果物選択）、RFC-029d（`--entry`
  オーバーライド）。
- RFC-014c との実装順序：014c 審査通過前、029f のインポート面順序が先に定稿すべき、014c は参照方式で消費、審査途中での範囲拡大を避ける。

### リスク

- 役割推測とユーザー直感の偏差（上述トレードオフ第一条）→ 全増分動作を警告（非ブロッキング）形式で提示、随時無効化可能。
- `[exports]` 絞り込みの過渡期管理 → マイナーバージョン内で先に警告。

## 開放問題

草案段階の 3 項目は全て定案済み（2026-09-13、決議は付録 B と本文に収録）、未決事項なし：

- [x] Internal pub を厳格化するかどうか →
      **定案**：フェーズ 2 でパッケージ内 use グラフ到達性に従って厳格化、Bin 役割コーパス検証を前提とする（実装戦略 Phase
      2 参照）
- [x] `[[test]]` 明示的宣言 →
      **定案**：導入しない、Test 役割は 036 規則のみで判定；036 に将来明示的宣言の必要性が生じた場合はその時点で拡張
- [x] workspace ルートによるメンバーエクスポート面カバー →
      **定案**：許可しない、メンバー自己完結は 014c の中核設計、ルートカバーはカプセル化を破壊する

## 付録 C：用語集

| 用語                           | 定義                                                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 役割（Role）                   | ソースファイルのコンパイルターゲット識別：Script / Bin / Lib / Test / Internal                       |
| インポート面（Import Surface） | 他パッケージの `use` 時に合法な解析起点となるファイル集合、`[exports]`/`[lib]` 宣言または推測による  |
| 配布境界                       | 029 用語：パッケージの外部露出範囲；本 RFC はそれを暗黙的（全 pub ファイル）からインポート面に精確化 |
| Script 態                      | manifest なし単一ファイル直接実行のバイパス形態、全動作が現状と一致                                  |
