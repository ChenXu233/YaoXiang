# RFC-029: モジュール意味論システム

## 概要

モジュールシステムをコンパイルパイプラインに接続し、複数ファイルコンパイルを実現する。

**中核定義**：モジュール = ある `.yx`
ファイルのすべてのトップレベルバインディング。モジュールの型 = それらのバインディングの型（推論される）。
`use` = record 分解。`pub` も `private` も `export` も、可視性メカニズムもない。

**中核原則**：

- 型チェッカーは事前構築された ModuleRegistry のみを照会し、ディスクには触れない
- パッケージ内のファイルは単一のコンパイルユニット（AST 連結）にマージされ、パッケージ内の循環参照は自然に許可される
- Registry はオンデマンドでロード：エントリから `use` 経由で到達可能なモジュールだけを装填

**含まないもの**：キャッシュ、ファイル監視、ホットリロード、インクリメンタル再コンパイル、パッケージをまたぐ循環依存の処理。

## 動機

### 現状の問題

1. **コンパイラは単一ファイルのみ対応**：`Pipeline::run(name, source)`
   は文字列を受け取り、ファイル間の依存を処理できない
2. **`use` は std モジュールのみ解決可能**：ローカルファイル間の `use` はすべて "Unknown
   variable" を報告する（#232）
3. **モジュールリゾルバの配置が誤っている**：唯一のパス解決ロジックは
   `package/source/module_resolver.rs` にあり、`frontend/module/resolver.rs`
   は実際にはコンパイル時の述語正規化（RFC-027）

### 設計目標

- 1つのプロジェクトで複数の `.yx` ファイルをコンパイル可能
- `use` 文の意味が明確：record 分解であり、特殊なメカニズムではない
- 単一ファイルは引き続き動作し、`yaoxiang.toml` を要求しない
- パイプライン（`Pipeline`）はゼロ変更、複数ファイル対応はオーケストレーション層の責務
- 新しいキーワード、AST ノード、概念を導入しない

## 提案

### 1. モジュール = バインディングの record

**モジュール**とは、ある `.yx` ファイルのすべてのトップレベルバインディングである。

```yaoxiang
// math/geometry.yx
Point: Type = { x: Float, y: Float }
distance: (a: Point, b: Point) -> Float = { ... }
```

このモジュールの中身は `{ Point: Type, distance: (Point, Point) -> Float }` である。

モジュールは特殊なエンティティではない。`name: type = value`
モデルのインスタンスである — たまたまファイル境界上で定義された record。モジュールの型はバインディングから推論され、明示的な注釈は決して必要ない。

`use` によって取り込まれるバインディング**もまた**モジュール内容の一部である：

```yaoxiang
// math/mod.yx
use geometry.{Point, distance}
```

`math` モジュールの中身 = `{ Point: Type, distance: (Point, Point) -> Float }`。外側で
`use math.{Point}` で取得可能。`use math.geometry.{Point}`
でも取得可能。二つのパスは同じバインディングを指す。

### 2. use = record 分解

すべての `use` 形式は record フィールドアクセス + バインディングである：

```yaoxiang
use math.geometry.{Point, distance}
```

は、以下と等価である：

```yaoxiang
Point = math.geometry.Point
distance = math.geometry.distance
```

| 構文                | 意味                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| `use path.{item}`   | `path` record の `item` フィールドを取得し、現在のスコープにバインド |
| `use path.{a, b}`   | 複数のフィールドを取得                                               |
| `use path`          | `path` record 自体を取得し、最後のセグメント名にバインド             |
| `use path as alias` | `path` record 自体を取得し、`alias` にバインド                       |

#### 存在しない構文

- ~~`use path.*`~~：ワイルドカードインポート。不要、明示的にバインディングを列挙する。
- ~~`from path use item`~~：Python 式。採用しない。
- ~~`use path.{item as alias}`~~：波括弧内エイリアス。Phase 4 で任意、#232 をブロックしない。

#### インポート衝突

同名のバインディングは直接エラー：

```
名前 `Point` が衝突：
  math.geometry.Point
  graphics.shapes.Point
別の名前またはモジュールエイリアスを使用してください。
```

### 3. 可視性：存在しない

**本 RFC はいかなる可視性メカニズムも導入しない。**
すべてのトップレベルバインディングは、パスを書き出せるすべてのコードから可視である。

これは意図的な設計判断であり、漏れではない。

#### 設計根拠

| 表現したいこと   | 方法                       | メカニズム |
| ---------------- | -------------------------- | ---------- |
| 「これは API」   | 公開パッケージに置く       | 配布       |
| 「これは内部」   | 公開しないパッケージに置く | 配布       |
| 「これは関数内」 | 関数本体に書く             | スコープ   |

三層すべて既存のメカニズム：パッケージ、ファイル、スコープ。新しいものは不要。

#### なぜ `pub` を採用しないか

- 他の人に使われたくないものは、トップレベルに置くべきではない（ローカルスコープに置く）
- 複数ファイルで共有するヘルパー関数は、公開しない独立のパッケージに置く
- 「防げるか」と「合図があるべきか」は別の問題である。現段階ではサードパーティのエコシステムがなく、合図は無意味
- ドアに鍵はかけない。ドアを使うのが礼儀、塀を越えるのが自由。言語は礼儀に干渉しない

#### 将来

エコシステムが成熟して強制的な境界が必要になった場合、独立した RFC で導入可能。制限の追加は後方互換的である（デフォルト公開 → 明示的に内部とマーク）。しかし本 RFC はこの方向を前提とせず、また到来を約束するものでもない。

### 4. パス解決

#### モジュールパス → ファイル

```
use math.geometry.{Point}
```

検索順序：

1. **Registry に登録済みモジュール**：`math.geometry` が既に Registry にある → 直接使用
2. **標準ライブラリ**：`std` または `std.*` → 組み込みモジュール
3. **インポータの所在ディレクトリ**：`<importer_dir>/math/geometry.yx`（ローカルモジュール優先）
4. **プロジェクトルート**（最も近い `yaoxiang.toml` の祖先）：`<project_root>/math/geometry.yx`
5. **vendor ディレクトリ**：`.yaoxiang/vendor/<pkg>-*/src/`（将来）

ファイル位置の試行順序：

```
base/name.yx
base/name/mod.yx
```

最初に見つかった時点で停止。両方が同時に存在 → エラー：

```
モジュールパス曖昧：`math.geometry` が同時に一致：
  src/math/geometry.yx
  src/math/geometry/mod.yx
一方を削除してください。
```

同一モジュールキーが**二つのルート**でそれぞれ一つのファイルにヒットし、双方とも参照される場合（例：`tests/lib.yx`
と `<root>/lib.yx`
がそれぞれ tests/ エントリとルートエントリから参照される） → 同様に曖昧エラーを報告し、サイレントシャドウィングは行わない。

> 2026-08-03 改訂（#247 / RFC-036 駆動）：発見と解決を実装に従って分離。発見は `use` を辿る（本 RFC
> §5 既定プロトコル）方式进行、初版実装のディレクトリ再帰を置換 — 無関係ファイルのコンパイルエラーが実行をブロックせず、`yaoxiang test`
> のテストファイル隔離が初めて成立する。二ルートルールにおける「インポータディレクトリ優先」は同ディレクトリプロジェクトの挙動不変を保証し、「プロジェクトルート フォールバック」はサブディレクトリエントリ（例：`tests/foo_test.yx`）がプロジェクトルートモジュールをインポート可能にする。`src/`
> レイアウト（RFC-014 パッケージ）は vendor 層とともに実装され、ローカル二重ルートに影響しない。

#### mod.yx = ディレクトリ入口（規約）

`mod.yx` はディレクトリの入口ファイルである。`use math` 時に `src/math/mod.yx` をロードする。

これは**規約であり、強制ではない**。ユーザは直接 `use math.geometry`
で子ファイルに透過的にアクセス可能。 `mod.yx`
は「推奨入口」（表札）であり、「唯一の入口」（鍵）ではない。

#### 統一リゾルバ

現在唯一のパス解決ロジックは `package/source/module_resolver.rs` にある。これを
`frontend/module/resolver.rs` に移動する（現状名実不一致の述語正規化ファイルを置き換え、述語正規化は
`frontend/core/types/eval/` に移動）。

### 5. プロジェクトコンパイルフロー

#### パス A：AST マージ

パッケージ内の全ファイルは**単一のコンパイルユニット**にマージされる。パイプラインはゼロ変更。

```
オーケストレータ（Pipeline の上）：
  1. 入口ファイルを決定
  2. 入口ファイルの use 文を解析（use 行のみ読み取り、関数本体は解析しない）
  3. use パスを辿ってファイルを発見、キューに追加
  4. キュー内のファイルについて、それらの use 文を解析
  5. キューが空になるまで 3-4 を繰り返す（オンデマンド発見）
  6. 発見された全ファイルを順次完全に解析 → 複数の AST
  7. 一つの Module にマージ（すべてのトップレベル items を連結、Span は元ファイルを保持）
  8. Pipeline::run() に投入（パイプラインは複数ファイルを知らない）
```

#### パッケージ内循環参照：許可

全ファイルが単一の AST にマージされるため、パッケージ内のファイル相互 `use`
は同一ファイル内の相互参照と等価：

```yaoxiang
// tree.yx
use node.{Node}
Tree: Type = { root: Node }

// node.yx
use tree.{Tree}
Node: Type = { value: Int, parent: Tree }
```

マージ後は一つの AST 内で相互参照する二つの型定義となる。コンパイラは元来これをサポートしている。

#### パッケージ間循環：後回し

パッケージは配布単位であり、パッケージ間にはトポロジカル順序が必要。現状サードパーティパッケージエコシステムがなく、処理しない。遭遇時は直接エラーを報告すればよい。

#### 入口ファイルの選択

優先順位：

1. `[run].main`（yaoxiang.toml）
2. `[[bin]]` 第一項の `path`
3. `src/main.yx`（規約デフォルト）

`yaoxiang.toml`
なしの場合：与えられたファイルを直接コンパイル。Registry には std のみ。これは「単一ファイルモード」ではなく、「発見結果が空という自然な結果」である。

#### Registry のオンデマンドロード

Registry の内容 = 入口から `use`
経由で到達可能なすべてのモジュール。到達不能なモジュールは解析されず、登録されず、存在しない。
**これは最適化ではなく、定義である。**

### 6. std モジュールとユーザモジュールの同質性

typecheck にとって、`use std.io.{println}` と `use math.geometry.{Point}` の操作は完全に同一：

1. Registry でモジュール record を探す
2. フィールドを取得
3. 現在のスコープにバインド

出所（Std / User / Vendor）はメタデータであり、解決ロジックに影響しない。native 関数の特殊処理は IR
gen / codegen 層に延期。

## 実装戦略

### Phase 1：パス解決の統一

1. 述語正規化を `frontend/module/resolver.rs` から `frontend/core/types/eval/` へ移動
2. `package/source/module_resolver.rs` のパス解決ロジックを `frontend/module/resolver.rs` へ移行
3. モジュールパス曖昧検出（`name.yx` と `name/mod.yx` の同時存在 → エラー）

### Phase 2：複数ファイルオーケストレータ

4. `frontend/module/orchestrator.rs` を新規作成
5. オンデマンド発見を実装（入口から use を辿る再帰）
6. AST マージを実装（複数ファイル items を連結、Span に元ファイル）
7. `compiler.rs` に `compile_project(project_root)` を追加し、オーケストレータを呼び出し

### Phase 3：use 名前解決

8. typecheck の `process_use_stmt` を Registry 照会に変更（std のみ照会から脱却）
9. インポート衝突検出（同名エラー）
10. E2E テスト：複数ファイルプロジェクトのローカルモジュール `use`

### Phase 4（任意、#232 をブロックしない）

11. `use path.{item as alias}` 波括弧内エイリアス
12. vendor ディレクトリ解決（RFC-014 と連動）

### 依存関係

- RFC-014（パッケージマネージャ）— `yaoxiang.toml` フィールド、vendor ディレクトリ構造（Phase
  4 で必要）
- 他の前置依存なし

## 設計決定記録

| 決定                         | 結論                                        | 日付       | 根拠                                                                      |
| ---------------------------- | ------------------------------------------- | ---------- | ------------------------------------------------------------------------- |
| モジュールとは何か           | ファイルトップレベルバインディングの record | 2026-07-30 | RFC-010 `name: type = value` 統一モデル                                   |
| `use` セマンティクス         | record 分解                                 | 2026-07-30 | 新メカニズムを導入せず、既存 record セマンティクスを再利用                |
| 可視性                       | 存在しない                                  | 2026-07-30 | スコープ + 配布境界が全シナリオをカバー、新キーワード不要                 |
| `pub` キーワード             | 採用しない                                  | 2026-07-30 | 「使われたくなければトップレベルに置かない / そのパッケージを公開しない」 |
| mod.yx セマンティクス        | ディレクトリ入口（規約、非強制）            | 2026-07-30 | Python `__init__.py` モデル：ドアに鍵はかけない                           |
| モジュール型注釈             | 不要                                        | 2026-07-30 | 内部バインディングは既に型を持つ、注釈は冗長                              |
| パッケージ内循環             | 許可（AST マージ）                          | 2026-07-30 | パス A：パイプラインゼロ変更、Rust crate 内モデル                         |
| パッケージ間循環             | 暫定未処理                                  | 2026-07-30 | サードパーティエコシステムなし、遭遇時エラー報告で十分                    |
| Registry ロード              | オンデマンド（到達可能モジュールのみ）      | 2026-07-30 | 最適化ではなく定義                                                        |
| 単一ファイル vs プロジェクト | 同一メカニズム                              | 2026-07-30 | Registry の内容は異なるが、検索ロジックは同一                             |
