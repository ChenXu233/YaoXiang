# RFC-029: モジュール意味論システム

## 概要

モジュールシステムをコンパイルパイプラインに接続し、マルチファイルコンパイルを実現する。

**核心定義**：モジュール = 1 つの `.yx`
ファイルのすべての最上位バインディング。モジュールの型 = それらのバインディングの型（推論）。 `use`
= record 分解。`pub` も `private` も `export` も可視性メカニズムも存在しない。

**核心原則**：

- 型検査器は事前構築された ModuleRegistry のみを照会し、ディスクには触れない
- パッケージ内ファイルは単一のコンパイルユニットに統合され（AST 連結）、パッケージ内循環参照は自然に許可される
- Registry はオンデマンドでロードされる：エントリから `use`
  に沿って到達可能なモジュールのみを装填する

**含まない**：キャッシュ、ファイル監視、ホットリロード、インクリメンタル再コンパイル、パッケージ間循環依存処理。

## 動機

### 現状の問題

1. **コンパイラは単一ファイルのみをサポート**：`Pipeline::run(name, source)`
   は文字列を受け取り、ファイル間依存を処理できない
2. **`use` は std モジュールのみ解析可能**：ローカルファイル間の `use` はすべて「Unknown
   variable」を報告する
3. **モジュールリゾルバが間違った場所に配置**：唯一のパス解析ロジックは
   `package/source/module_resolver.rs` にあり、`frontend/module/resolver.rs`
   は実際にはコンパイル時の述語正規化（RFC-027）である

### 設計目標

- 1 つのプロジェクトで複数の `.yx` ファイルをコンパイル可能
- `use` 文の意味論が明確：record 分解であり、特殊メカニズムではない
- 単一ファイルは引き続き動作し、`yaoxiang.toml` を要求しない
- パイプライン（`Pipeline`）の変更はゼロ、マルチファイルサポートはオーケストレーション層の役割
- 新キーワード、新 AST ノード、新概念を導入しない

## 提案

### 1. モジュール = record of bindings

**モジュール**とは、1 つの `.yx` ファイルのすべての最上位バインディングである。

```yaoxiang
// math/geometry.yx
Point: Type = { x: Float, y: Float }
distance: (a: Point, b: Point) -> Float = { ... }
```

このモジュールの内容は `{ Point: Type, distance: (Point, Point) -> Float }` である。

モジュールは特殊な存在ではない。`name: type = value`
モデルのインスタンス——ファイル境界上で定義された record にすぎない。モジュールの型はバインディングから推論され、明示的なアノテーションは決して必要ない。

`use` で導入されたバインディングもモジュール内容の一部である：

```yaoxiang
// math/mod.yx
use geometry.{Point, distance}
```

`math` モジュールの内容 = `{ Point: Type, distance: (Point, Point) -> Float }`。外部で
`use math.{Point}` しても取得できる。`use math.geometry.{Point}`
しても取得できる。両パスは同じバインディングを指す。

### 2. use = record 分解

すべての `use` 形式は record フィールドアクセス + バインディングである：

```yaoxiang
use math.geometry.{Point, distance}
```

は以下と等価である：

```yaoxiang
Point = math.geometry.Point
distance = math.geometry.distance
```

| 構文                | セマンティクス                                                       |
| ------------------- | -------------------------------------------------------------------- |
| `use path.{item}`   | `path` record の `item` フィールドを取得し、現在のスコープにバインド |
| `use path.{a, b}`   | 複数のフィールドを取得                                               |
| `use path`          | `path` record 自体を取得し、最後のセグメント名にバインド             |
| `use path as alias` | `path` record 自体を取得し、`alias` にバインド                       |

#### 存在しない構文

- ~~`use path.*`~~：ワイルドカードインポート。不要。バインディングを明示的に列挙する。
- ~~`from path use item`~~：Python 式。採用しない。
- ~~`use path.{item as alias}`~~：中括弧内エイリアス。Phase
  4 でオプションであり、メインラインはブロックしない。

#### インポート競合

同名のバインディングは直接エラーとなる：

```
名前 `Point` が競合：
  math.geometry.Point
  graphics.shapes.Point
異なる名前またはモジュールエイリアスを使用してください。
```

### 3. 可視性：存在しない

**本 RFC はいかなる可視性メカニズムも導入しない。**
すべての最上位バインディングは、パスを記述できるすべてのコードから可視である。

これは意図的な設計決定であり、漏れではない。

#### 設計根拠

| 表現したいこと     | 方法                   | メカニズム |
| ------------------ | ---------------------- | ---------- |
| 「これは API だ」  | 公開パッケージに配置   | 配布       |
| 「これは内部用だ」 | 非公開パッケージに配置 | 配布       |
| 「これは関数内だ」 | 関数本体に記述         | スコープ   |

3 層すべてが既存メカニズム：パッケージ、ファイル、スコープ。新しいものは不要。

#### なぜ `pub` を必要としないか

- 他の人に使われたくないものは、最上位に置くべきではない（ローカルスコープに置く）
- 複数ファイルで共有するヘルパー関数は、独立した非公開パッケージに配置する
- 「防げるかどうか」と「シグナルが必要かどうか」は別問題である。現段階ではサードパーティエコシステムがなく、シグナルは無意味
- ドアに鍵はかけない。ドアを歩くのが礼儀、塀を登るのは自由。言語は礼儀を問わない

#### 将来

エコシステムが成熟して強制境界が必要になった場合、独立した RFC で導入できる。制限の追加は後方互換である（デフォルト公開 → 明示的に内部としてマーク）。ただし本 RFC はこの方向を前提とせず、その到来も約束しない。

### 4. パス解決

#### モジュールパス → ファイル

```
use math.geometry.{Point}
```

検索順序：

1. **Registry に登録済みモジュール**：`math.geometry` が既に Registry に存在する → 直接使用
2. **標準ライブラリ**：`std` または `std.*` → 組み込みモジュール
3. **インポータのディレクトリ**：`<importer_dir>/math/geometry.yx`（ローカルモジュール優先）
4. **プロジェクトルート**（最も近い `yaoxiang.toml` の祖先）：`<project_root>/math/geometry.yx`
5. **vendor ディレクトリ**：`.yaoxiang/vendor/<pkg>-*/src/`（将来）

ファイル位置特定の試行順序：

```
base/name.yx
base/name/mod.yx
```

最初に見つかったもので停止する。両方が同時に存在 → エラー：

```
モジュールパスが曖昧：`math.geometry` が同時に一致：
  src/math/geometry.yx
  src/math/geometry/mod.yx
一方を削除してください。
```

同じモジュールキーが 2 つのルートでそれぞれ 1 つのファイルにヒットし、両方が参照される場合（例：`tests/lib.yx`
と `<root>/lib.yx` がそれぞれ `tests/`
エントリとルートエントリから参照される）→ 同様に曖昧エラーを報告し、静かにシャドーイングしない。

> 2026-08-03 改訂（RFC-036 駆動）：発見と解決は実装に従って着地する。発見は `use`
> に沿って追跡（本 RFC
> §5 既定プロトコル）し、初版実装のディレクトリ再帰に代わる——無関係ファイルのコンパイルエラーはもはや実行をブロックせず、`yaoxiang test`
> のテストファイル隔離が成立する。双根ルール中の「インポータディレクトリ優先」は同ディレクトリプロジェクトの挙動を保証する；「プロジェクトルートフォールバック」はサブディレクトリエントリ（例：`tests/foo_test.yx`）がプロジェクトルートモジュールをインポートできるようにする。`src/`
> レイアウト（RFC-014 パッケージ）は vendor 層で一括処理され、ローカル双根には影響しない。

#### mod.yx = ディレクトリエントリ（規約）

`mod.yx` はディレクトリのエントリファイルである。`use math` で `src/math/mod.yx` をロードする。

これは**規約であり、強制ではない**。ユーザは直接 `use math.geometry` でサブファイルに透過できる。
`mod.yx` は「推奨エントリ」（表札）であり、「唯一のエントリ」（鍵）ではない。

#### 統一リゾルバ

現在唯一のパス解析ロジックは `package/source/module_resolver.rs` にある。これを
`frontend/module/resolver.rs` に移す（現在の名ばかりの述語正規化ファイルを置き換え、述語正規化は
`frontend/core/types/eval/` へ移動）。

### 5. プロジェクトコンパイルフロー

#### パス A：AST 統合

パッケージ内すべてのファイルを**単一のコンパイルユニット**に統合する。パイプライン変更はゼロ。

```
オーケストレータ（Pipeline の上位）：
  1. エントリファイルを決定
  2. エントリファイルの use 文を解析（use 行のみ読み取り、関数本体は解析しない）
  3. use パスに沿ってファイルを発見し、キューに追加
  4. キュー内のファイルの use 文を解析
  5. キューが空になるまで 3-4 を繰り返す（オンデマンド発見）
  6. 発見されたすべてのファイルを1つずつ完全に解析 → 複数の AST
  7. 1 つの Module に統合（すべての最上位 items を連結、Span はソースファイルを保持）
  8. Pipeline::run() に供給（パイプラインは複数ファイルを知らない）
```

#### パッケージ内循環参照：許可

すべてのファイルが単一 AST に統合されるため、パッケージ内ファイルの相互 `use`
は同一ファイル内の相互参照と等価である：

```yaoxiang
// tree.yx
use node.{Node}
Tree: Type = { root: Node }

// node.yx
use tree.{Tree}
Node: Type = { value: Int, parent: Tree }
```

統合後は 1 つの AST 内の 2 つの相互参照する型定義になる。コンパイラは元々これをサポートしている。

#### パッケージ間循環：後回し

パッケージは配布単位であり、パッケージ間にはトポロジカル順序が必要である。現在サードパーティパッケージのエコシステムがなく、暫定的に処理しない。遭遇した場合は直接エラーで十分。

#### エントリファイル選択

優先順位：

1. `[run].main`（`yaoxiang.toml`）
2. `[[bin]]` の最初の項目の `path`
3. `src/main.yx`（デフォルト規約）

`yaoxiang.toml`
なしの場合：与えられたファイルを直接コンパイルする。Registry には std のみ。これは「単一ファイルモード」ではなく、「発見結果が空であることの自然な結果」である。

#### Registry のオンデマンドロード

Registry の内容 = エントリから `use`
に沿って到達可能なすべてのモジュール。到達不能なモジュールは解析されず、登録されず、存在しない。
**これは最適化ではなく、定義である。**

### 6. std モジュールとユーザーモジュールは同質

型検査にとって、`use std.io.{println}` と `use math.geometry.{Point}` の操作は完全に同じである：

1. Registry でモジュール record を見つける
2. フィールドを取得する
3. 現在のスコープにバインドする

ソース（Std / User /
Vendor）はメタデータであり、解析ロジックには影響しない。native 関数の特殊処理は IR gen /
codegen 層に延期する。

- ~~`frontend/module/cache.rs`~~ — 存在しない、サブ RFC 029a に属する

## 実装戦略

### Phase 1：統一パス解決

1. 述語正規化を `frontend/module/resolver.rs` から `frontend/core/types/eval/` へ移動
2. `package/source/module_resolver.rs` のパス解決ロジックを `frontend/module/resolver.rs` へ移行
3. モジュールパス曖昧検出（`name.yx` と `name/mod.yx` が同時に存在 → エラー）

### Phase 2：マルチファイルオーケストレータ

4. `frontend/module/orchestrator.rs` を新規作成
5. オンデマンド発見を実装（エントリから `use` に沿って再帰）
6. AST 統合を実装（マルチファイル items 連結、Span はソースファイルを含む）
7. `compiler.rs` に `compile_project(project_root)` を追加し、オーケストレータを呼び出す

### Phase 3：use 名前の解決

8. 型検査の `process_use_stmt` を Registry 照会に変更（std のみ照会ではなくなる）
9. インポート競合検出（同名でエラー）
10. E2E テスト：マルチファイルプロジェクトでローカルモジュールを `use`

### Phase 4（オプション、メインラインをブロックしない）

11. `use path.{item as alias}` 中括弧内エイリアス
12. vendor ディレクトリ解決（RFC-014 と連携）

### 依存関係

- RFC-014（パッケージマネージャ）— `yaoxiang.toml` フィールド、vendor ディレクトリ構造（Phase
  4 で必要）
- 他の前提依存なし
