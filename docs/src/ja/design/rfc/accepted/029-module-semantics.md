# RFC-029: モジュール意味論システム

## 概要

モジュールシステムをコンパイルパイプラインに接続し、複数ファイルコンパイルを実現する。

**核心定義**：モジュール =
`.yx`ファイルのすべてのトップレベルバインディング。モジュールの型 = それらのバインディングの型（推論）。
`use` = record分解。`pub`も`private`も`export`も、可視性機構も存在しない。

**核心原則**：

- 型検査器は事前構築されたModuleRegistryのみを照会し、ディスクには触れない
- パッケージ内ファイルは単一コンパイルユニットに統合される（AST連結）、パッケージ内循環参照は自然に許可される
- Registryは必要に応じてロード：エントリから`use`で到達可能なモジュールのみを装填

**含まないもの**：キャッシュ、ファイル監視、ホットリロード、インクリメンタル再コンパイル、パッケージ横断循環依存処理。

## 動機

### 現状の問題

1. **コンパイラは単一ファイルのみ対応**：`Pipeline::run(name, source)`は文字列一つを受け取るだけで、ファイル横断依存を処理できない
2. **`use`はstdモジュールのみ解決可能**：ローカルファイル間の`use`はすべて "Unknown
   variable" と報告される（#232）
3. **モジュールリゾルバの位置が誤っている**：唯一のパス解決ロジックは`package/source/module_resolver.rs`にあり、`frontend/module/resolver.rs`は実際にはコンパイル時述語正規化（RFC-027）である

### 設計目標

- 一つのプロジェクトが複数の`.yx`ファイルをコンパイルできること
- `use`文の意味が明確：record分解、特殊機構ではない
- 単一ファイルは引き続き動作し、`yaoxiang.toml`を要求しない
- パイプライン（`Pipeline`）はゼロ変更、複数ファイル対応はオーケストレーション層の責務
- 新しいキーワード、新しいASTノード、新しい概念を導入しない

## 提案

### 1. モジュール = バインディングのrecord

一つの**モジュール**は、`.yx`ファイルのすべてのトップレベルバインディングである。

```yaoxiang
// math/geometry.yx
Point: Type = { x: Float, y: Float }
distance: (a: Point, b: Point) -> Float = { ... }
```

このモジュールの中身は`{ Point: Type, distance: (Point, Point) -> Float }`である。

モジュールは特殊な存在ではない。`name: type = value`モデルのインスタンスの一つであり、たまたまファイル境界上で定義されたrecordに過ぎない。モジュールの型はバインディングから推論され、明示的な型注釈は決して必要ない。

`use`で導入されるバインディングもモジュール内容の一部である：

```yaoxiang
// math/mod.yx
use geometry.{Point, distance}
```

`math`モジュールの中身 =
`{ Point: Type, distance: (Point, Point) -> Float }`。外部で`use math.{Point}`とすれば取得できる。`use math.geometry.{Point}`でも取得できる。二つのパスは同じバインディングを指す。

### 2. use = record分解

すべての`use`形式はrecordフィールドアクセス + バインディングである：

```yaoxiang
use math.geometry.{Point, distance}
```

は以下に等価である：

```yaoxiang
Point = math.geometry.Point
distance = math.geometry.distance
```

| 構文                | セマンティクス                                                    |
| ------------------- | ----------------------------------------------------------------- |
| `use path.{item}`   | `path` recordの`item`フィールドを取得し、現在のスコープにバインド |
| `use path.{a, b}`   | 複数フィールドを取得                                              |
| `use path`          | `path` record自体を取得し、最後のセグメント名にバインド           |
| `use path as alias` | `path` record自体を取得し、`alias`にバインド                      |

#### 存在しない構文

- ~~`use path.*`~~：ワイルドカードインポート。必要ない、バインディングを明示的に列挙する。
- ~~`from path use item`~~：Python風。採用しない。
- ~~`use path.{item as alias}`~~：波括弧内エイリアス。Phase 4でオプション、#232をブロックしない。

#### インポート衝突

同名のバインディングは直接エラー：

```
名前`Point`が衝突：
  math.geometry.Point
  graphics.shapes.Point
別の名前またはモジュールエイリアスを使用してください。
```

### 3. 可視性：存在しない

**本RFCはいかなる可視性機構も導入しない。**
すべてのトップレベルバインディングは、パスを書き記せるすべてのコードから可視である。

これは意図的な設計判断であり、漏れではない。

#### 設計根拠

| 表現したいこと       | やり方                     | 機構     |
| -------------------- | -------------------------- | -------- |
| "これはAPI"          | 公開するパッケージに置く   | 配布     |
| "これは内部のもの"   | 公開しないパッケージに置く | 配布     |
| "これは関数内のもの" | 関数本体に書く             | スコープ |

三層すべて既存機構：パッケージ、ファイル、スコープ。新しいものは不要。

#### なぜ`pub`が不要か

- 他の人に使われたくないものは、トップレベルに置くべきではない（ローカルスコープに置く）
- 複数ファイルで共有するヘルパー関数は、公開しない独立したパッケージに置く
- "防げるか"と"シグナルが必要か"は別の問題。現段階にはサードパーティエコシステムがなく、シグナルは無意味
- ドアに鍵はかけない。ドアを使うのは礼儀、壁を登るのは自由。言語は礼儀を相手にしない

#### 将来

エコシステムが成熟し強制境界が必要になった場合、独立したRFCで導入可能。制限の追加は後方互換（デフォルト公開 → 明示的に内部とマーク）。ただし本RFCはこの方向を予見せず、その到来も約束しない。

### 4. パス解決

#### モジュールパス → ファイル

```
use math.geometry.{Point}
```

検索順序（唯一のルール）：

1. **Registry登録済みモジュール**：`math.geometry`が既にRegistryにある → 直接使用
2. **標準ライブラリ**：`std`または`std.*` → 組み込みモジュール
3. **プロジェクトsrcディレクトリ**：`<project_root>/src/math/geometry.yx`
4. **vendorディレクトリ**：`.yaoxiang/vendor/<pkg>-*/src/`（将来）

ファイル位置の試行順序：

```
base/name.yx
base/name/mod.yx
```

最初に見つかったもので停止。両方が同時に存在 → エラー：

```
モジュールパスが曖昧：`math.geometry`が同時に一致：
  src/math/geometry.yx
  src/math/geometry/mod.yx
一方を削除してください。
```

#### mod.yx = ディレクトリエントリ（規約）

`mod.yx`はディレクトリのエントリファイルである。`use math`時、`src/math/mod.yx`をロードする。

これは**規約であり、強制ではない**。ユーザーは直接`use math.geometry`でサブファイルに透過できる。
`mod.yx`は「推奨エントリ」（表札）であり、「唯一のエントリ」（鍵）ではない。

#### 統一リゾルバ

現在唯一のパス解決ロジックは`package/source/module_resolver.rs`にある。これを`frontend/module/resolver.rs`に移動する（現在の名実不一致の述語正規化ファイルを置換し、述語正規化は`frontend/core/types/eval/`へ移動）。

### 5. プロジェクトコンパイルフロー

#### パスA：AST統合

パッケージ内の全ファイルは**単一コンパイルユニット**に統合される。パイプラインはゼロ変更。

```
オーケストレータ（Pipelineの上）：
  1. エントリファイルを決定
  2. エントリファイルのuse文を解析（use行のみ読み取り、関数本体は解析しない）
  3. useパスに沿ってファイルを発見し、キューに追加
  4. キュー内のファイルについて、それらのuse文を解析
  5. キューが空になるまで3-4を繰り返し（オンデマンド発見）
  6. 発見したファイルを一つずつ完全に解析 → 複数のAST
  7. 一つのModuleに統合（すべてのトップレベルitemsを連結、Spanはソースファイルを保持）
  8. Pipeline::run()に投入（パイプラインは複数ファイルのことを知らない）
```

#### パッケージ内循環参照：許可

すべてのファイルが一つのASTに統合されるため、パッケージ内のファイルが互いに`use`することは同じファイル内の相互参照と等価である：

```yaoxiang
// tree.yx
use node.{Node}
Tree: Type = { root: Node }

// node.yx
use tree.{Tree}
Node: Type = { value: Int, parent: Tree }
```

統合後は一つのAST内で相互参照する二つの型定義になる。コンパイラは元来これをサポートしている。

#### パッケージ間循環：後回し

パッケージは配布単位であり、パッケージ間にはトポロジカル順序が必要。現状サードパーティパッケージエコシステムがないため、暫定的に未対応。遭遇したら直接エラーでよい。

#### エントリファイル選択

優先順位：

1. `[run].main`（yaoxiang.toml）
2. `[[bin]]`の最初の項目の`path`
3. `src/main.yx`（規約デフォルト）

`yaoxiang.toml`がない時：与えられたファイルを直接コンパイル。Registryにはstdのみ。これは「単一ファイルモード」ではなく、「発見結果が空であることの自然な結果」。

#### Registryオンデマンドロード

Registryの内容 = エントリから`use`で到達可能なすべてのモジュール。到達不能なモジュールは解析されず、登録されず、存在しない。
**これは最適化ではなく、定義である。**

### 6. stdモジュールとユーザーモジュールは同質

typecheckにとって、`use std.io.{println}`と`use math.geometry.{Point}`の操作は完全に同一：

1. Registryでモジュールrecordを見つける
2. フィールドを取得
3. 現在のスコープにバインド

出所（Std / User / Vendor）はメタデータであり、解決ロジックに影響しない。native関数の特殊処理はIR
gen / codegen層に延期。

- ~~`frontend/module/cache.rs`~~ — 存在しない、サブRFC 029aに属する

## 実装戦略

### Phase 1：パス解決の統一

1. 述語正規化を`frontend/module/resolver.rs`から`frontend/core/types/eval/`へ移動
2. `package/source/module_resolver.rs`のパス解決ロジックを`frontend/module/resolver.rs`へ移行
3. モジュールパス曖昧性検出（`name.yx`と`name/mod.yx`が同時存在 → エラー）

### Phase 2：複数ファイルオーケストレータ

4. `frontend/module/orchestrator.rs`を新規作成
5. オンデマンド発見を実装（エントリからuseに沿って再帰）
6. AST統合を実装（複数ファイルitemsを連結、Spanにソースファイル）
7. `compiler.rs`に`compile_project(project_root)`呼び出しを追加

### Phase 3：use名前解決

8. typecheckの`process_use_stmt`をRegistry照会に変更（stdのみではなく）
9. インポート衝突検出（同名でエラー）
10. E2Eテスト：複数ファイルプロジェクトでのローカルモジュール`use`

### Phase 4（オプション、#232をブロックしない）

11. `use path.{item as alias}`波括弧内エイリアス
12. vendorディレクトリ解決（RFC-014と連動）

### 依存関係

- RFC-014（パッケージマネージャ）— `yaoxiang.toml`フィールド、vendorディレクトリ構造（Phase
  4で初めて必要）
- 他の前置依存なし

| 決定                         | 結論                                       | 日付       | 根拠                                                                     |
| ---------------------------- | ------------------------------------------ | ---------- | ------------------------------------------------------------------------ |
| モジュールとは何か           | ファイルトップレベルバインディングのrecord | 2026-07-30 | RFC-010 `name: type = value`統一モデル                                   |
| `use`セマンティクス          | record分解                                 | 2026-07-30 | 新機構を導入せず、既存recordセマンティクスを再利用                       |
| 可視性                       | 存在しない                                 | 2026-07-30 | スコープ + 配布境界が全シナリオをカバー、新キーワード不要                |

| モジュール型注釈             | 不要                                       | 2026-07-30 | 内部バインディングはすでに型を持つ、注釈は冗長                           |
