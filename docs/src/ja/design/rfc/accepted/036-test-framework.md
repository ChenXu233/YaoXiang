# RFC-036: std.test テストフレームワークと yaoxiang test コマンド

## 概要

YaoXiang 向けに標準テストフレームワーク `std.test` モジュールと `yaoxiang test`
CLI サブコマンドを導入する。テストファイルは通常の `.yx` ファイルであり、子プロセスの exit
code で全体の合格/不合格を判定する。ファイル内部では複数のテスト関数をサポートし、アサーション失敗は
`Err` 値で表現される（値意味論）。スイートが per-test の判定を収集する（§7）。`std.test`
モジュールは純粋な YaoXiang で実装され、初の dogfooding ライブラリである。`yaoxiang test`
は CLI ツールであり、编译器機能ではない — parser、IR、バイトコード、実行器に一切変更を加えない。

## 動機

### なぜテストフレームワークが必要か？

現在の YaoXiang のテストカバレッジは Rust 側の `#[test]` と `tests/`
統合テストに依存している。これは以下を意味する：

1. 標準ライブラリ（std.math / std.list / std.dict / std.convert /
   std.io）のユニットテストが YaoXiang で記述できない
2. `#117 標準ライブラリ各モジュールのユニットテストカバレッジ`
   が、利用可能なテスト基盤がないためブロックされている
3. 言語機能の回帰テスト（例：RFC-032 spawn セマンティクスの変更）に自動化された手段がない

### キー制約

- **17 キーワード鉄則**：新しいキーワードや構文構造を導入しない
- **コンパイラ変更ゼロ**：parser、IR、バイトコード、実行器に触れない
- **セルフホスティング優先**：テストライブラリは YaoXiang で記述され、初の dogfooding ライブラリとなる

## アーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI 層:  yaoxiang test [--filter --fail-fast --json ...]    │
│              │                                               │
│  発見層:    读取 yaoxiang.toml → [tool.test] patterns         │
│              デフォルト: tests/**/*.yx                              │
│              │                                               │
│  実行層:    対毎ファイル: yaoxiang run <file>                    │
│              検査 exit code → 串行実行                        │
│              │                                               │
│  報告層:    PASS/FAIL → 彙総                                  │
│              サポート --json / --verbose / --fail-fast            │
│                                                              │
│  断言層:    std.test (純粋 YaoXiang、自挙)                      │
│              底層: std.assert.assert                          │
│              診断: f"Expected {expected}, got {actual}"       │
└──────────────────────────────────────────────────────────────┘
```

### 中核原則

1. **テストフレームワークはコンパイラ機能ではなく、CLI ツールである** — `yaoxiang run`
   はすでに「テスト実行」が可能であり、`yaoxiang test`
   は単にすべてのファイルを実行し、レポートを表示するヘルパーに過ぎない
2. **コンパイラ変更ゼロ** — `@test`
   アノテーションスキャン、バイトコードメタデータセグメント、実行器特殊入口を導入しない
3. **セルフホスティング** — `std.test` モジュールは純粋な YaoXiang で実装され、基盤能力は
   `std.assert` / `std.result` から得られる
4. **テストファイルは通常の `.yx` ファイルである** — ファイルは子プロセスとして実行され、exit
   code で全体の合格/不合格を判定する
5. **アサーション失敗は事象ではなく値である** — テスト関数は `Result` を返し、アサーション失敗は
   `Err`
   で表現される。スイートが per-test の判定を収集する（§7）。プロセスレベルの abort はランタイムガードのみに属し、テストアサーションには使用されない

## 詳細設計

### 1. CLI 設計

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      テストファイルまたはディレクトリを指定（デフォルト：yaoxiang.toml から読み取り、それ以外は tests/）

Options:
  --filter <NAME>     ファイル名に <NAME> を含むテストのみ実行
  --fail-fast         最初の失敗で停止
  --verbose, -v       各テストの詳細な stdout/stderr を表示
  --list              テストファイルを列挙するだけで実行しない
  --no-progress       進捗出力を表示しない（ヘッダーと PASS 行）。FAIL 詳細とサマリは保持（CI シナリオ）
  --json              JSON 形式で結果を出力（CI 統合用）
```

#### 出力フォーマット

**デフォルト出力**（per-test 判定はファイル内スイート収集から取得、§7 参照）：

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**JSON 出力**（`--json`）：

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- 失敗ファイルは追加で `exit_code` と
  `stderr`（ANSI を剥がした子プロセス診断、CI フォレンジック用）を保持する `--verbose` と `--json`
  を組み合わせた場合、全ファイルが `stdout` / `stderr` を保持する
- `--no-progress`
  は進捗出力（ヘッダーと PASS 行）のみを抑制する。FAIL 詳細とサマリは常に出力され、失敗を静かにしない。`--list`
  はテストファイルパスを 1 行ずつ出力し、実行はしない
- 各ファイルに `kind`（behavior / compile-error / runtime-error /
  invalid、§8.2）を付加し、summary に `by_kind`
  実行カウントを付加する（固定 4 キー、skipped は含まない）。人間向けサマリには `Categories:`
  カテゴリ分布行を付加する
- ファイル内の per-test `tests`
  配列は §7 のスイート収集に由来し、値化モデルが実装されて初めて有効になる（#319）

### 2. yaoxiang.toml 設定

`[tool.test]` の下に配置し、RFC-015 の `[tool.*]` サードパーティ拡張規約に準拠する：

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# 将来の拡張:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- デフォルト `patterns = ["tests/**/*.yx"]` — ユーザーは設定不要で即座に利用開始
- 単一ファイルモード（`yaoxiang test foo.yx`）は直接実行し、設定を読み取らない
- 将来的に独立リポジトリへ分割される可能性がある（`[tool.test]` の位置は変更なし）

### 3. std.test モジュール（純粋な YaoXiang）

```yaoxiang
// std/test.yx — 純粋な YaoXiang テストアサーションライブラリ（値意味論の標準形態、2026-09-03 実装）
// 初の dogfooding ライブラリ：YaoXiang のテストライブラリは YaoXiang で書かれている。

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not は assert_false と同体；assert_err / assert_err_code は §8.1 参照
```

- アサーション関数は**値意味論**である：`Result(Void, String)` を返し、失敗は `Err(診断情報)`
  で表現される。プロセスの abort は行わない —
  §7 のスイートがこれに基づいて per-test の判定を収集する。`std.assert.assert`
  のプロセスレベル abort セマンティクスはランタイムガード用に保持され、テストアサーション経路には入らない。Ok のペイロードは
  `Void`（type-system.md 仕様上の unit；`()` は空の Tuple であり、両者は混用しない —
  2026-09-03 確定）である
- **関数ファミリー 7 個（2026-09-03 実装済み、abort 移行版は削除）**：値化版 `assert_eq` /
  `assert_ne` / `assert_true` / `assert_false` + `assert_not` （assert_false と同体、`!assert`
  単項形態への置換用）+ `assert_err`（§8.1）
  - `assert_err_code`（§8.1 エラーコードアサーション）
- `assert_eq` / `assert_ne` は **Any 注釈パラメータ** を使用 — `==`/`!=`
  と f-string 補間は Any 上で正常に動作し、ジェネリクスシステムに依存しない。なお、パラメータは**明示的に注釈付けしなければならない**：注釈なしのパラメータは native ジェネリクス
  `&Result(T, E)` の呼び出しチェックを通過しない（R1 プローブ実証）
- `assert_false` / `assert_not` は否定を `cond == false` で表現する（`not`
  単項構文は未実装のため、安定後に移行可能；`!assert` 単項形態も同じ依存関係を持つ、§8.1 参照）
- ブロック本体 + 明示的 `return`
  形態：if 式の then 腕の型がチェックで破棄されるため、両腕 Result の if 式はチェックの盲点であり、実装側で回避している
- `std.test` は native コードに一切依存せず、純粋な YaoXiang で実装される

### 4. 標準ライブラリロード機構（キー設計）

**フェーズ 1：バイナリ埋め込み**

`std/test.yx`（および今後 YaoXiang で書かれるすべての標準ライブラリモジュール）はビルド時にバイナリに埋め込まれる：

```rust
// build.rs またはビルドスクリプト、自動的に生成
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // ソースコードテキスト
    // 今後追加
];
```

モジュールシステム（RFC-029、2026-08-02 完全に実装済み）が接続点を提供する：Registry は native モジュールとソースモジュールの両方を保持し、orchestrator が複数ファイルの編成を担当する。`use std.test`
の解決順序：

1. まず Rust の native モジュールを検索（既存メカニズム、例：`std.assert`）
2. ヒットしない場合、埋め込まれた `STD_YX_FILES`
   を検索 — ヒットすれば**仮想パス**（例：`<std>/test.yx`）を seed モジュールとして orchestrator に注入し、通常のフロントエンドパイプライン（parse
   → typecheck → IR）を通す
3. ヒットしない場合、ファイルシステム探索（ユーザーモジュール）

埋め込まれたソースモジュール内部の `use std.assert` は、resolver によって通常通り native
registry に解決される —
native モジュールとソースモジュールは Registry に共存し、種類をまたいだ依存関係が自然に成立する。埋め込みモジュールは**オンデマンドでコンパイル**される：import されたときのみパイプラインに入る。

利点：

- 単一ファイルモードでも `use std.test` が動作する
- 標準ライブラリのバージョンがバイナリと厳密にバインドされ、バージョンのミスマッチが発生しない
- ユーザーが標準ライブラリパスを設定する必要がない

**将来：ファイルシステム標準ライブラリ**

YaoXiang のプロジェクトモードが成熟した後、標準ライブラリはファイルシステム形式に変更される。詳細は RFC-014 の更新を参照。

### 5. 探索と実行

**前提条件（2026-08-02 レビュー決議）**：CLI `run` を orchestrator に接続する。現状、CLI `run`
は単一ファイルパイプライン（`run_file_with_diagnostics`）を通り、ユーザーモジュールのインポートを解析できない。しかし
`yaoxiang test`
の子プロセスモデルは CLI の機能を継承し、テストファイルがプロジェクトモジュールをインポートすることは中心的なシナリオである。したがってフェーズ 1 では、まず CLI
`Run` のソースコード分岐を
`run_project`（orchestrator、ディレクトリ再帰探索）に委譲する；#247（use に沿ったオンデマンド探索）はその後、純粋なパフォーマンス最適化として重ね合わせる。import がない単一ファイルは orchestrator の挙動と等価であり、バイトコード分岐は変わらない。

**探索フェーズ**：

1. `[PATHS]` が指定されていれば、指定されたパスを直接使用する
2. そうでなければ、`yaoxiang.toml` の `[tool.test].patterns` を読み取る
3. 設定がない場合、デフォルト `tests/**/*.yx`
4. `--filter` を適用してフィルタする（ファイル名による包含）
5. 探索範囲がそのままテストの階層化となる（§9）：デフォルトの patterns は言語可用性コーパスのみをカバーする。ライブラリテスト層（例：`src/std/tests/`）は明示的なパスまたはパッケージ設定によって探索され、デフォルトスキャンには混ざらない

**実行フェーズ**：

1. 各ファイルに対して、ヘッダー指令に従ってディスパッチ実行する（指令文法は §8.2 参照、`src/util/test_markers.rs`
   で解析、yx_runner と共有）：
   - 振る舞いテスト：`yaoxiang run --debug-info <file>` 子プロセス（`--debug-info`
     はランタイムエラーにソースコードを付加する — 2026-08-02 実証で stack trace が `file:line:col`
     を出力）；`// mode:` で子プロセスの `--runtime` モードを宣言
   - コンパイル時拒否系：単一ステップで `yaoxiang check <file>`
   - ランタイム失敗系：`check`（必ず成功）+ `run`（必ず失敗）の 2 ステップ
2. `// skip: <理由>` のファイルは実行をスキップし、レポートの skipped にカウントされる
3. 判定と期待コードの比較は §8.2 の判定マトリクスに従う；指令解析が失敗した場合は実行せずに直接 FAIL（構築期拒否）
4. レポート用に stdout/stderr をキャプチャする
5. シリアル実行のみ（フェーズ 1）、将来 `--parallel` をサポート予定
6. `--fail-fast` の場合、最初の FAIL で即座に停止する

### 6. テスト分離

テスト分離はプロセスレベルの境界によって自然に実現される：

- 各テストファイルは独立した子プロセスで実行される
- 各子プロセスは独立した Heap、Frame、NativeContext を持つ
- あるテストファイルのパニックが他のテストファイルに影響することはない
- 追加の独立 Heap コンテキスト機構は不要

### 7. スイートと複数テスト（値化モデル）

1 つのテストファイルに複数のテストを含め得る。ファイル内の編成方法（2026-09-03 実装済み）：

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- 各テストは `Result(Void, String)` を返すゼロ引数関数である；アサーション失敗は `Err`
  で表現され（§3 値意味論アサーションファミリー）、プロセスを中断しない — 後続のテストは通常通り実行される
- `test.suite`
  が順次呼び出して収集する：テストが Ok でない場合、名前と診断を記録し、Ok の場合は静かに通過する。すべて実行した後、いずれかの Err があれば
  `std.assert.assert` で中止し、失敗の詳細を付記する（`N of M test(s) failed` + 各項目の
  `[FAIL] 名前: 診断`）— ファイルの終了コードは非 0 になる（§5 の判定は変わらない）。ここでの abort はテストバイナリのランタイムガードであり、アサーション経路ではない。全 Ok なら静かに 0 で終了する
- トップレベルのテスト関数は**クロージャ形式で登録**される（`("name", () => test_fn())`）：トップレベル関数名を値として参照することは現在サポートされない（IR 層の制限、`E3006`）— クロージャ本体からグローバル関数を呼び出すことには影響しない
- runner はファイルのみを見、関数レベルのスキャンは行わない：per-test 判定は完全にスイート内収集に由来し、ファイル内部の構造は runner に対して透過的である — コンパイラ変更ゼロの原則は影響を受けない
- 明示的に採用しない：プロセス内 catch 境界（17 キーワード鉄則）；runner による関数単位のエントリ呼び出し（§8.2 コンパイル失敗など内部シナリオのみ）
- API 形態は確定済み（2026-09-03、#319）：`suite(tests: List((String, () -> Result(Void, String)))) -> Void`；重複名はチェックしない（名前はレポート表示のみ）；`--filter`
  はファイル名でフィルタし、スイート内のテスト名は認識しない

### 8. ネガティブテスト（期待される失敗）3 層設計

ネガティブテストは失敗が発生する層によって分割され、各層に帰属する：

#### 8.1 値レベルの反転（汎用、ユーザー向け）

被テスト操作が `Result` を返し、テストは通常のアサーションで期待される失敗を表現する：

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// またはワンライナー（コードは std Error キャリアにのみ存在し、E は Error に固定）：
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code`
  は値意味論ファミリーに含まれて実装済み（2026-09-03、§3）； `!assert`
  単項形態は not 構文の落地を待って提供する（`assert_false` の `cond == false` と同じ制約）
- エラーコードアサーションは、`Error` 値が機械可読な `code` フィールドを運ぶことに依存する — #323
  M4 で実装済み： `Error = { code, message }`（native `error_new(code, message)`）、読み取りは
  `result.unwrap_err(r)` でキャリアを取得し、`result.code(e)` / `result.message(e)`
  アクセサでアクセスする（設計段階で見積もっていた `error_new_with_code`
  命名、コード定数のエクスポート、`err.code`
  フィールドアクセスは採用されず — 言語に Struct フィールドアクセスがなく、コード定数もエクスポートされていない）
- Result 化の推進（#301、#316）に伴い、失敗する可能性のある操作が順次 `Result`
  を返し、コーパス内のファイルレベルネガティブマーカーはファイル内アサーションに移行する

#### 8.2 ファイルレベルネガティブ指令（言語設計者の内部使用のみ）

コンパイルは全ファイルまるごと全か無かであり、ファイル内で「この行はコンパイルされるべきでない」を表現できない。ランタイム失敗も同様にファイルレベル表現を必要とする（例：スイートに必ず失敗するテストを含む）。ファイルの先頭で**構造化指令**により期待を宣言し、runner は期待カテゴリに応じて**ディスパッチ判定**する（2026-09-03 ディスパッチ確定；2026-09-06 指令文法確定・実装）。

ヘッダー指令文法（`// key: value`、先頭 16 行以内、厳格なトークンマッチ）：

```text
// expect: compile-error E1002 [E1003 ...]   コンパイル時拒否テスト
// expect: runtime-error E6003 [...]         ランタイム失敗テスト
// skip: <理由>                              実行をスキップ、skipped にカウント
// mode: embedded|standard|full              子プロセスの --runtime モード（run ステップのみ消費）
```

- `expect:` 指令なし = 振る舞いテスト。`expect:` は期待の**唯一の宣言**である — 2026-09-06 確定で
  `[test:error]` ブールマーカーと中文 `预期:`
  散文からのコード抽出を廃止：ブールマーカーと期待行は 2 つの疎結合な事実であり、規律で一貫性を保つことは必然的に崩れる；英文の厳格なトークン文法は runner による機械的解析を可能にし（kind とコードは共に固定トークン、コードの後に余分なトークンがあれば解析失敗）、解析失敗 = 実行せずに直接 FAIL
  — 指令宣言エラーの静かな劣化経路は存在しない（構築期拒否）
- **コンパイルエラー系**：単一ステップで `check` — 必ず失敗し、出力にすべての `[EXXXX]`
  を含むこと；コンパイル成功 =
  FAIL（報告されるべきものが報告されない）、拒否されてもコードが一致しない =
  FAIL。構文エラー（E1xxx 解析段階）と意味エラー（E2xxx+）は独立したカテゴリを設定しない — 期待コード自体が段階を固定する
- **ランタイムエラー系**：2 ステップ判定 — `check` は必ず**成功**（コンパイル時は無罪）、`run`
  は必ず失敗し出力にすべての `[EXXXX]` を含む。コンパイル時に爆発 =
  FAIL（コンパイルエラー系と方向が逆の重要判定、「コンパイルが予期せず成功し、ランタイムが偶然失敗」の見逃しを防止）
- 業界と同形：Rust compiletest `//~ ERROR`、Go `// ERROR "regexp"`、GCC `dg-error`、Clang
  `expected-error`
  はすべて fixture のコメント内で期待を宣言し、harness が双方向比較を行う；これらが行レベルのアンカーを使うのは、複数診断コンパイラが同一ファイル内の複数の期待を区別する必要があるためで、本コンパイラは最初のエラーで停止し、1 ファイル 1 診断であるため、ファイルレベルがコンパイラの現実に同形となる — エラー回復が実装された後、文法に行アンカー形態を追加できる（Cranelift
  filetests のファイルヘッダー指令 + 関数レベルの期待は同じ混合形態）
- 既知のレンダリング負債：parse 段階の診断は現在 Debug 形式で出力される（`code: "E0012"` ではなく
  `[E0012]`
  ではなく）、コードスキャンは両方の形式を受け入れる；診断レンダリングの統一後に厳格な形式を取り戻す
- **本リポジトリのコーパスにのみ対応するもので、ユーザーテストフレームワークの一部ではない**；ダブル runner 判定規約は取りまとめ済み（2026-09-03、#319）：yx_runner（cargo
  test）と `yaoxiang test` は `src/util/test_markers.rs`
  を共有してヘッダー指令を解析し、06-compile-errors のディレクトリ規約は廃止。レポート層はカテゴリカウントを提供する：人間向けサマリには
  `Categories:` 行、JSON summary には `by_kind`（behavior / compile-error / runtime-error /
  invalid、skipped は別途）、各ファイルには `kind` を付加

#### 8.3 ランタイムハード失敗（Result 化に帰属）

独立した機構は設けない — 失敗する操作は言語の方向性に従って `Result`
を返し（#301、#316）、テストは §8.1 表現に統一される。プロセスレベルの abort（アサーション違反、ランタイム引数誤りなど）は Result 化の進展に伴い徐々に値に集約され、テストフレームワークはそれ専用のセマンティクスを提供しない。（注意：§8.2 の「ランタイムエラー系」マーカー判定は、runner による**まだ Result 化できない操作**のファイルレベル検証チャネルであり、本節のセマンティクス方向と矛盾しない — 後者は終点で、前者は移行期のチャネル）

### 9. テスト体系の階層化：言語コーパスとライブラリテスト（2026-09-03 確定）

テストは**被テスト対象**によって 2 層に分けられ、それぞれに帰属と保守担当がある。マーキングシステム（§8.2）とアサーションライブラリ（§3）は両層で共通である：

**第 1 層：言語可用性コーパス（`tests/yaoxiang/`）**

- 被テスト対象は**言語自体**
  — パーサ、型システム、モジュール、並行性、所有権、コンパイル時拒否、ランタイムセマンティクス；ディレクトリは言語仕様章に従って編成
- std はコーパス内で**アサーションツール**としてのみ使用され（`std.assert` /
  `std.test`）、テスト対象とはならない — ライブラリの API 振る舞いは言語可用性に属さない
- コーパス内では §8 に従って振る舞いテスト / コンパイル時拒否テスト / ランタイム失敗テストの 3 類型にディスパッチされる

**第 2 層：ライブラリテスト（ライブラリと共に）**

- 被テスト対象は**ライブラリの公開 API 契約**（例：`list.push` の振る舞い、`result.code`
  のセマンティクス）
- テストは**ライブラリ自身のパッケージ内**に書かれる：std のパッケージは `src/std/`
  そのものであり、yx レベルのテストは `src/std/tests/` に属する（実装本体と同じ場所）；`std.test`
  自身のテストもそこにある（std.test で std.test をテストする、セルフホスティングの閉ループ）
- 将来ユーザーパッケージも同じ慣例に従う：テストはパッケージ内、パッケージの `[tool.test]`
  で発見（RFC-014 パッケージ管理のテストレイアウトの予行演習）
- デフォルト patterns では発見されない（デフォルトの `tests/**/*.yx`
  は言語層のみをカバー）：ライブラリテスト層は明示的なパス（`yaoxiang test src/std/tests`）またはパッケージ設定で発見される；CI は階層別に実行

移行注記：現在 `tests/yaoxiang/07-std/` にあるライブラリテストはこのモデルに従って `src/std/tests/`
に移行する；移行時に個別に甄別する — 純粋な API 振る舞いのものは移行し、被テスト対象が実際には言語境界であるもの（例：native
`&T` 自動借用）はコーパス層に残し、対応する仕様章に分類する

- `yaoxiang test` が基本的に使用可能
