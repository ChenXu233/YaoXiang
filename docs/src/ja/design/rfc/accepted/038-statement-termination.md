# RFC-038: 文の終端と改行ルール

## 概要

YaoXiangの**文の終端ルール**を定義する：**改行を主境界**とし、**括弧の閉じ・行末の二項演算子・行頭の
`.`（チェーン継続）**を明示的な継続の例外とする；行頭の `(` `[`
は**決して前の文に統合されない**。`;` は明示的な区切り文字として保持される（単一行複数文）。

本RFCは同時に `syntax.md`
が文の終端記号を一度も定義していないという規範の空白を補い、parser が行頭の `(` `[` `.`
を前の文の接尾辞として吸収してしまう欠陥を修正する（#258）。

## 動機

### なぜこの機能が必要なのか？

YaoXiang の `;` は完全にオプション（parser 内に 14 箇所の
`skip(Semicolon)`）だが、**改行は文の境界として一度も定義されていない**：lexer は改行を破棄し、parser の文の境界の唯一の判定は「式の Pratt ループが自然に停止する」——すなわち「次のトークンが式を継続できるか」。これにより：

1. **動作が自己矛盾**：改行の後に identifier/リテラル → 正常に終端；改行の後に `(` `[` `.`
   → 前の式の接尾辞として吸収（呼び出し/インデックス/フィールドアクセス）
2. **合法的な文が静かに破壊される**：`(c, d) = (3, 4)` の分解が `1(c, d) = (3, 4)`
   になり、誤解を招く E1001 を報告；`f()(2)`、`1[99]` はエラーすら報告せず、文が直接消える
3. **規範の空白**：`syntax.md` §2.9 `Block ::= '{' Stmt* Expr? '}'`
   は Stmt 間の区切りを定義していない；§1.2 区切り文字表には `( ) { } ,` のみ

### 現在の問題

| ブロック内コード            | 現在の AST                                       | 結果                          |
| --------------------------- | ------------------------------------------------ | ----------------------------- |
| `x = 1` ⏎ `(c, d) = (3, 4)` | `Assign x = BinOp(Assign, Call(1,[c,d]), Tuple)` | E1001 が無実の `c` を指す     |
| `x = f()` ⏎ `(2)`           | `Call(Call(f),[2])`                              | **静かに**（文が消える）      |
| `x = 1` ⏎ `[99]`            | `Index(1,99)`                                    | **静かに**                    |
| `x = 1` ⏎ `.println("hi")`  | `Call(Field(1),["hi"])`                          | E1053                         |
| `x = 1 +` ⏎ `2`             | `BinOp(Add)`                                     | ✅ 合法（ただし規範根拠なし） |
| `x = (1,` ⏎ `2)`            | `Tuple`                                          | ✅ 合法（ただし規範根拠なし） |

## 提案

### 中核設計

**主ルール：改行は文を終端する。**

**継続の例外（3 グループ、すべて主流言語の先例あり）：**

| #   | 例外                        | ルール                                                        | 先例         |
| --- | --------------------------- | ------------------------------------------------------------- | ------------ |
| 1   | **括弧が閉じられていない**  | `(` `[` `{` の深さ > 0 のとき、改行は終端しない（暗黙の継続） | Python/Scala |
| 2   | **行末の二項演算子**        | 行が二項演算子で終わる → 継続                                 | Swift/Scala  |
| 3   | **行頭の `.` チェーン継続** | 行頭が `.` で前行が identifier/`)`/`]` で終わる → 継続        | Swift        |

**決して統合しない（JS 最大の教訓を学ぶ）：**

- 行頭の `(`、`[` → **常に新しい文を開始する**。JS の有名な落とし穴（`a\n(b)` → `a(b)`
  呼び出し）は YaoXiang で特に危険：タプル分解
  `(a, b) = ...`、spawn、タプルリテラルはすべて括弧で始まる文。
- 行頭の二項/単項演算子（`+` `-` `*`
  など）→ 新しい文を開始する。行末演算子の継続は一般的な折り返しスタイルをすでにカバーしている；行頭演算子の継続（Scala
  3 の前置演算子）は単項/中置の曖昧さを導入するため採用しない。折り返しが必要な場合は括弧で囲む。

**`;` は保持**：明示的な区切り文字、単一行複数文で使用（Kotlin/Swift と同款）。

### 例

```yaoxiang
// 改行が文を終端する（ほとんどのコード）
a = 1
b = 2

// 継続：行末の二項演算子
total = a +
    b + c

// 継続：括弧が閉じられていない
t = (1,
     2)
io.println(
    "hi")

// 継続：行頭の .（チェーン呼び出し）
result = list.map(x => x * 2)
    .filter(x => x > 10)
    .sum()

// 決して統合しない：行頭の ( は独立した分解文
x = f()
(c, d) = (3, 4)      // ✅ 分解、f()(c, d) ではない

// 決して統合しない：行頭の [ は独立したリスト
x = 1
[1, 2, 3]            // ✅ 独立した式文

// 単一行複数文：セミコロン
a = 1; b = 2
```

### 構文の変化

`syntax.md` §2.9 の後に追加：

```
StatementTerminator ::= ';' | Newline        （以下の継続の例外を除く）
継続の例外（改行は終端しない）：
  - '(' '[' '{' の深さ > 0
  - 行末が二項演算子
  - 行頭が '.' かつ前行が Identifier | ')' | ']' で終わる
決して統合しない：行頭の '(' '[' は常に新しい文
```

| 以前                                              | 以後                                                                       |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| `Block ::= '{' Stmt* Expr? '}'`（区切り定義なし） | `Block ::= '{' (Stmt StatementTerminator)* Expr? '}'`                      |
| 改行に地位なし、行頭の `(` `[` `.` が吸収される   | 改行が終端；行頭の `(` `[` は決して統合されない；行頭の `.` は明示的な継続 |
| `;` はオプションだが意味が曖昧                    | `;` = 明示的な区切り（単一行複数文）、`;` の後に改行可                     |

## 詳細設計

### 文の終端判定（parser ルール）

式の Pratt ループ内で、後置演算子（`(` 呼び出し、`[` インデックス、`.`
フィールドアクセス）適用前にチェック：

```
continuation(prev_expr, op_token) =
    prev_expr 終了行 == op_token 開始行        // 同行：通常の後置
    || (op_token == '.' かつ prev_expr が Identifier/')'/']' で終わる)  // 行頭 . チェーン
    || 括弧の深さ > 0                            // 閉じられていない括弧内
```

満たさない → 式終了、新しい文を開始。中置二項演算子は行チェックに参加しない（行末演算子 = 継続、天然に正しい）。

### 構文の影響範囲

- `parse_expression`
  の後置分岐に行番号チェックを追加（Span 自带の行番号を利用、lexer の token ストリームの変更は不要）
- 文解析箇所で `;` と新しい行境界を消費（`skip(Semicolon)` の意味論を保持）
- ブロック終了 `}`、ファイル終端 EOF は天然に文を終端、追加処理不要
- **NEWLINE トークンを導入しない**（代替案の方案 B 参照）——Span の行番号で十分、変更が最小

### コンパイラの変更

| コンポーネント                               | 変更                                                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `src/frontend/core/parser/parser_state.rs`   | `parse_expression` の後置演算子行チェック                                                              |
| `src/frontend/core/parser/statements/*.rs`   | 文境界消費ロジックの微調整                                                                             |
| `docs/src/reference/language-spec/syntax.md` | §2.9 の後に「文の終端ルール」セクションを追加                                                          |
| テスト                                       | `tests/yaoxiang/01-syntax/` に改行/継続の用例を追加；`06-compile-errors/` に行頭吸収の回帰テストを追加 |

### 後方互換性

- **ほとんどの既存コードは変更不要**：identifier/リテラルで始まる行、行末演算子折り返し、括弧内改行はすべて現状と一致
- **動作変化点**（すべてバグ修正方向）：
  - `f()(2)` / `1[99]` / `1.println()`
    の改行跨ぎ吸収が「静か/エラー」から「2 行の独立した文」に——正しい意味論
  - 行頭 `.` が「吸収（エラー）」から「明示的チェーン継続」に——新機能
- リスク：「跨行吸収」に依存する合法コード（例：`f()\n(2)` が返り値関数の呼び出しを意図）が `f()` +
  `(2)`
  の 2 文になる場合がある。このようなコードは元々意味的に誤りまたは極めて稀で、RFC レビューの際に確認が必要

## トレードオフ

### 利点

- **ルールが少なく直感に合う**：2 つの主ルール +
  3 グループの例外、すべて主流言語で検証済みの実践から
- **静かなエラーの解消**：`f()(2)`、`1[99]` などが静かに吸収されなくなり、文の境界が予測可能
- **チェーン呼び出しに親切**：行頭 `.` 継続が Swift/業界標準スタイルに揃う
- **lexer 変更ゼロ**：Span 行番号方案の最小侵襲

### 欠点

- 行頭二項演算子継続（Scala 3 式）は未対応——括弧で囲んで折り返しが必要、一部のスタイルが制限される
- 行頭 `.` 継続の判定は「前行が identifier/`)`/`]` で終わる」に依存、ルールを文書化する必要あり

## 代替案

| 方案                             | 説明                                                        | 選択しない理由                                                                                     |
| -------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **A. Span 行番号認識（本提案）** | parser の後置演算子が行番号をチェック                       | ✅ 採用：変更が最小、ルールが明確                                                                  |
| **B. Go 式自動挿入セミコロン**   | lexer の nlsemi 状態機械、行末の特定トークン後に `;` を挿入 | `{` 行末を強制、行頭の `.`/演算子を禁止、チェーンスタイルを犠牲；YaoXiang の自由スタイルに合わない |
| **C. セミコロン強制**            | すべての文に `;` 必須                                       | セミコロンオプションの既存エコシステムとテストファイル現状に違反                                   |
| **D. 現状維持**                  | ルールなし、トークン駆動                                    | #258 の欠陥が継続、文が静かに消える                                                                |

## 実装戦略

### 依存関係

- 外部依存なし；#258（本 RFC の実装 issue）に関連
- RFC-010（統一型構文）とは直交：文の終端は parser 層ルール、型文法に関与しない

### リスク

- 行頭 `.` チェーンと「行頭 `.` 独立文」の境界：`.foo()` は独立した文になれない（`.`
  は合法な文の開始ではない）、よって継続判定に曖昧さなし
- 既存テストが吸収動作に依存する場合、一つ一つ確認が必要（期待：なし——吸収はすべてバグシナリオ）

## 開放的な問題

- [ ] 行頭二項演算子継続（Scala
      3 式）をサポートする価値はあるか？（@ChenXu233：非支持の傾向、括弧で囲めば十分）
- [ ] `;` 後の改行は空文と等価か？既存 parser の `skip(Semicolon)`
      の後の改行は自然に継続、特殊処理不要
- [ ] 「未使用式結果警告」（Swift 式）を吸収の追加セーフガードとして導入するか？独立 RFC で議論

| 言語       | 方案                                  | 行頭 `(`              | チェーン `.` | 行頭演算子                 | 評価                                       |
| ---------- | ------------------------------------- | --------------------- | ------------ | -------------------------- | ------------------------------------------ |
| Go         | lexer 自動挿入セミコロン（2 ルール）  | ✅ 安全               | ❌ 禁        | ❌ 禁                      | 最も確定、チェーンスタイルを犠牲           |
| JavaScript | ASI 3 ルール + restricted productions | ❌ **有名な落とし穴** | 可           | ⚠️ 落とし穴                | **反面教材**（`a\n(b)` → 呼び出し）        |
| Python     | NEWLINE 硬境界 + 括弧暗黙継続         | ✅ 安全               | ❌ 括弧必要  | ❌ 括弧必要                | 最も予測可能、継続が最も弱い               |
| Kotlin     | SEMI = セミコロンまたは改行           | ✅ 安全               | ✅           | ❌（末尾 lambda 落とし穴） | 良いがルールが深い                         |
| Swift      | 改行終端 + スペースルール             | ✅ 安全               | ✅           | ✅ スペース防護            | **本提案に最も近い**                       |
| Scala 3    | nl token + 領域ルール + 前置演算子    | ✅                    | ✅           | ✅                         | 最も完全だが最も複雑、過剰エンジニアリング |

**本提案 = Go の確定性 × Python の括弧継続 × Swift の行頭 `.`
チェーン**。Swift が理想に最も近い；Scala
3 が最も完全だがルールが重すぎる——人間に親切なのはルールが最も完全であることではなく、**ルールが少なくそれぞれのルールが直感に合うこと**。
