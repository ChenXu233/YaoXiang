# RFC-008：Runtime 並行モデルとスケジューラ疎結合設計

> **⚠️ 整合性に関する補足**：本文書は
> [RFC-024 新並行モデル](../../../reference/language-spec/concurrency.md)
> と整合済みです。旧来のプログラム全体 DAG 分析、`@block`/`@eager` 注釈、L1/L2/L3 階層モデルは
> `spawn {}` ブロック並列プリミティブに置き換えられました。DAG 分析は現在 `spawn {}`
> ブロック内部のみに作用します。

> **参考**:
>
> - [RFC-011: ジェネリクスシステム設計](./011-generic-type-system.md)
> - [並行モデル仕様（RFC-024）](../../../reference/language-spec/concurrency.md)

## 概要

本文書は Runtime アーキテクチャの重要な設計を定義する：

1. **実行時 3 層アーキテクチャ**：Embedded（即時実行） → Standard（spawn + DAG スケジューリング） →
   Full（ワークスティーリング）
2. **コンパイルと実行の分離**：コンパイルフェーズは完全に同一で、違いは実行時の実行方式のみ
3. **デュアルバックエンドモデル**：VM（開発・デバッグ）と LLVM AOT（本番リリース）、動作は完全一致
4. **スケジューラ = 静的ライブラリ**：AOT コンパイル時にスケジューラが exe にリンクされ、約 200-500KB、GC なし
5. **同期はスケジューリングの特例に過ぎない**：num_workers=1 が同期モード

### 重要な明確化：これは Java ではない

```
Java:    .java → .class → JVM（インタプリタ/JIT + GC）        ← 常に仮想マシンが必要
YaoXiang 開発: .yx → IR → VM 実行（高速イテレーション、ステップデバッグ）
YaoXiang 本番: .yx → IR → LLVM → ネイティブ exe（スケジューラが内部にリンク）

VM は開発ツールであり、実行時の本質ではない。Go の go run vs go build と同じ。
最終 exe = あなたのネイティブコード + スケジューラ静的ライブラリ + 反射メタデータ。インタプリタも JIT も GC もない。
```

## 動機

### 中核となる矛盾

| 矛盾                     | 説明                                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| 透明性 vs 制御性         | spawn ブロックは明示的な並行制御を提供し、通常のコードは逐次実行される                   |
| 中核 vs オプション       | spawn は中核となる並列プリミティブ、WorkStealing は num_workers>1 の高度な機能           |
| シングルスレッド vs 並行 | シングルスレッドモードでは並行が非同期として現れ、同期はスケジューリングの特例に過ぎない |

## 提案

### 1. Runtime 3 層アーキテクチャ

```
┌──────────────────────────────────────────────────────────────────┐
│                  コンパイルフェーズ（全モード共通）                       │
│                                                                  │
│  Source Code → Lexer → Parser → TypeCheck → Codegen → IR        │
│                                                                  │
│  ⚠️ 同一の構文解析、型検査、コード生成、IR 出力                       │
└──────────────────────────────────────────────────────────────────┘
                               │
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
┌──────────────────┐ ┌───────────────┐ ┌──────────────────┐
│ 🟢 Embedded      │ │ 🔵 Standard   │ │ 🟣 Full          │
│ 即時実行器        │ │ spawn + DAG   │ │ Full スケジューラ     │
│ 同期実行         │ │ spawn ブロック内並行 │ │ 並列最適化         │
│ spawn 非対応    │ │ 自動並行      │ │ ワークスティーリング         │
└──────────────────┘ └───────────────┘ └──────────────────┘
```

| フェーズ       | Embedded | Standard             | Full                    |
| -------------- | -------- | -------------------- | ----------------------- |
| コンパイル     | 同一     | 同一                 | 同一                    |
| 実行モード     | 同期     | spawn ブロック内並行 | 並行                    |
| メモリ使用量   | 低       | 中                   | 高                      |
| 並行能力       | なし     | spawn ブロック内     | spawn ブロック内 + 並行 |
| spawn サポート | ❌       | ✅                   | ✅                      |
| DAG 分析       | なし     | spawn ブロック内     | spawn ブロック内        |
| WorkStealer    | なし     | なし                 | ✅                      |

**Embedded
Runtime**：WASM/ゲームスクリプト/ルールエンジン向け。即時実行器、spawn 非対応、高性能・低フットプリント。

**Standard Runtime**：Web サービス/データパイプライン向け。`spawn {}`
ブロックをサポートし、spawn ブロック内で DAG 分析と自動並列化を実行。num_workers=1 がシングルスレッド非同期。

**Full Runtime**：科学計算/大規模並列計算向け。Standard + WorkStealer によるロードバランシング。

### 2. スケジューラ疎結合：ジェネリクス + 注入

基本原則：VM は具体的なスケジューラに直接依存せず、ジェネリックパラメータ `[S]` を通じて呼び出す。

```yaoxiang
# スケジューラインターフェース定義
Scheduler: Type = {
    spawn: (Task) -> TaskId,
    await: (TaskId) -> Result,
    spawn_with_deps: (Task, List(TaskId)) -> TaskId,
    await_all: (List(TaskId)) -> List(Result),
    stats: () -> SchedulerStats,
}

# シングルスレッドスケジューラ
SingleThreadScheduler: Scheduler = {
    spawn: (task) => { task_queue.push(task); generate_task_id() },
    await: (task_id) => { ... },
    spawn_with_deps: (task, deps) => { ... },
    await_all: (task_ids) => { ... },
    stats: () => { queue_size: task_queue.len() },
}

# マルチスレッドスケジューラ
MultiThreadScheduler: Scheduler = {
    spawn: (task) => { work_queue.push(task); generate_task_id() },
    await: (task_id) => { wait_for_completion(task_id) },
    spawn_with_deps: (task, deps) => { ... },
    await_all: (task_ids) => { ... },
    stats: () => { workers: get_worker_stats() },
}

# VM はジェネリクスでスケジューラを使用
create_vm: [S: Scheduler](scheduler: S) -> VM = (scheduler) => {
    VM(scheduler: scheduler, memory: create_memory(), dag: create_dag())
}
```

**中核となるポイント**：

- コンパイル時ポリモーフィズム、実行時オーバーヘッドゼロ
- Trait オブジェクト不要
- ジェネリック型制約 `[S: Scheduler]` は RFC-011 で既に定義済み

### 3. 同期 = スケジューリングの特例

```
❌ 誤解：スケジューラを無効化する
✅ 正しい：単一 worker のスケジューラを使用する

num_workers = 1 → シングルスレッド非同期スケジューリング
num_workers > 1 → マルチスレッド並列スケジューリング

同じスケジューラインターフェース、異なるのは設定のみ。特殊ケースを排除。
```

### 4. DAG の位置付け

> **重要な変更**：DAG 分析はプログラム全体に作用しなくなり、`spawn {}`
> ブロック内部でのみ実行される。通常コード（spawn ブロック外）は逐次実行され、DAG 分析は不要。

| 階層             | spawn サポート | DAG 分析範囲     | 説明                         |
| ---------------- | -------------- | ---------------- | ---------------------------- |
| Core Runtime     | ✅             | spawn ブロック内 | 並行中核                     |
| Standard Runtime | ✅             | spawn ブロック内 | spawn + DAG スケジューリング |
| Embedded Runtime | ❌             | なし             | 即時実行、並行なし           |

### 5. ボトムアップ実行モデル（spawn ブロック内）

> **重要な変更**：ボトムアップ DAG 分析は `spawn {}`
> ブロック内部でのみ実行され、プログラム全体に対する DAG 分析は廃止された。

```
ユーザーコード（spawn ブロック内並行）：
    (a, b) = spawn {
        fetch(url0),
        fetch(url1)
    }
    print(a)

コンパイル時分析（spawn ブロック内ボトムアップ）：
    fetch(url0) と fetch(url1) は相互依存なし → 並列実行可能
    spawn ブロック外の print(a) → 逐次実行、spawn の完了を待機

実行時スケジューリング（spawn ブロック内はリーフから開始）：
    fetch(url0) ┐
                ├→ 並列実行
    fetch(url1) ┘
    print(a)                       ← spawn ブロック外、逐次実行
```

**中核となるポイント**：

- ボトムアップ依存分析は `spawn {}` ブロック内部のみに限定
- spawn ブロック内で依存関係のないタスクは並列実行
- spawn ブロック外のコードは逐次実行され、spawn ブロックの完了を待機

### 6. コンパイルモデル：デュアルバックエンド + 静的リンクランタイム

#### 6.1 2 つのバックエンド、1 つの動作

```
                      ┌─────────────────────┐
                      │  コンパイルフロントエンド（統一） │
                      │  Lexer → Parser     │
                      │  → TypeCheck        │
                      │  → spawn ブロック内 DAG 分析│
                      │  → エスケープ分析        │
                      │  → 環検出            │
                      └──────────┬──────────┘
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
        ┌───────────────────┐     ┌───────────────────┐
        │  VM バックエンド（開発）  │     │ LLVM バックエンド（本番）  │
        │                   │     │                   │
        │  IR/バイトコード生成    │     │  ネイティブコード生成     │
        │  VM インタプリタ実行    │     │  ランタイム静的ライブラリリンク│
        │  ステップデバッグ対応       │     │  .exe 出力         │
        │  高速イテレーション          │     │  インタプリタオーバーヘッドゼロ  │
        └───────────────────┘     └───────────────────┘
                 │                         │
                 ▼                         ▼
            動作は完全一致                 動作は完全一致
```

**VM バックエンド**：開発時に使用。コード変更 → 即時実行 → ステップデバッグ → 高速イテレーション。最終 exe と動作は完全一致。

**LLVM バックエンド**：リリース時に使用。AOT コンパイルでネイティブコードを生成し、スケジューラを静的ライブラリとしてリンク。インタプリタも JIT もない。

#### 6.2 スケジューラ = 静的ライブラリ、仮想マシンではない

```
最終 exe の内部構造：

┌────────────────────────────────────────────┐
│  あなたのコード（ネイティブマシンコード）            │
│  ├── コンパイル時に決定済みの DAG 実行計画        │
│  ├── インライン化された Move/ref/clone 操作    │
│  └── RAII 解放コード                       │
├────────────────────────────────────────────┤
│  ランタイム静的ライブラリ（~200-500KB）          │
│  ├── スレッドプール（固定サイズ = num_workers）   │
│  ├── イベントループ（libuv / io_uring）         │
│  ├── ワークスティーリングキュー（Full Runtime のみ）  │
│  ├── メモリアロケータ（jemalloc / mimalloc）    │
│  └── 反射メタデータ（オンデマンドロード、常駐しない）  │
├────────────────────────────────────────────┤
│  存在しないもの：                              │
│  ❌ バイトコードインタプリタ                     │
│  ❌ JIT コンパイラ                          │
│  ❌ GC                                  │
│  ❌ 仮想マシン                                │
└────────────────────────────────────────────┘
```

比較：

| 言語             | Java                 | Go                | YaoXiang                           |
| ---------------- | -------------------- | ----------------- | ---------------------------------- |
| コンパイル成果物 | バイトコード         | ネイティブコード  | ネイティブコード                   |
| 実行方式         | JVM インタプリタ/JIT | 直接実行          | 直接実行                           |
| ランタイムサイズ | ~200MB（JVM）        | ~1-2MB（GC 含む） | **~200-500KB（GC なし）**          |
| メモリ管理       | GC                   | GC                | **RAII（決定的）**                 |
| 反射             | 常駐メモリ           | 常駐メモリ        | **exe 内保存、オンデマンドロード** |

#### 6.3 なぜスケジューラの性能は一定か

**重要な洞察**：作業の大半はコンパイル時に完了し、実行時は「実行」のみを行う。

```
コンパイル時（一度だけ、ランタイムに含まれない）：
    ├── spawn ブロック内 DAG 分析：誰が何に依存するか
    ├── トポロジカルソート：spawn ブロック内の実行順序を決定
    ├── 並列可能タスクの特定：spawn ブロック内依存関係のないサブツリー
    ├── エスケープ分析：ref → Rc か Arc
    ├── 環検出：自動的に Weak に降格またはエラー報告
    └── インライン化：小関数は直接展開

実行時（毎実行、データ構造は固定）：
    ├── コンパイル時に決定された spawn ブロック DAG 順序でタスクをスレッドプールにディスパッチ
    ├── I/O に遭遇 → 現在のタスクを中断し、イベントループに処理を委譲
    ├── タスク準備完了 → レディキューに戻す
    └── 以上。
```

**スケジューラ自体は固定サイズのデータ構造**：スレッドプール、イベントループ、ワークキュー。動的成長なし、自適応再最適化なし、GC スキャンなし。動作は完全に予測可能。

コンパイル時に spawn ブロック内の「何をスケジューリングするか」はすでに計算済みで、実行時は「実行」のみ。これは tokio とは異なる――tokio は実行時に動的に Future チェーンを構築する。YaoXiang の DAG は静的で、spawn ブロック内に限定される。

#### 6.4 反射：保存するが常駐しない

反射メタデータはコンパイル時に生成され、exe の独立したセクションに保存される。プログラム起動時にはロードされない。最初の反射要求時に、オンデマンドで mmap によりメモリにロードされる。以下と同様である：

```
exe レイアウト：
  .text     ← あなたのコード
  .rodata   ← 定数
  .reflect  ← 反射メタデータ（型情報、関数シグネチャなど）
              mmap オンデマンドロード、アクセスしなければメモリを消費しない
```

**トレードオフ**：exe サイズが大きくなる（反射データを含む）が、実行時にアクセスしなければメモリ消費はゼロ。最初のアクセス時にロード遅延あり（JIT ウォームアップに類似）、以降はオーバーヘッドゼロ。

## トレードオフ

### 利点

- **明確な階層化**：Embedded / Standard / Full の 3 層
- **コンパイルの再利用**：フロントエンドコードは完全に共有
- **ジェネリクスによる疎結合**：コンパイル時ポリモーフィズム、オーバーヘッドゼロ
- **一貫性**：同期はスケジューリングの特例に過ぎない
- **組み込みフレンドリー**：高性能 + 低メモリ + 高速起動

### 欠点

- **初期の複雑さ**：スケジューラインターフェースと複数のランタイムバリアントの定義が必要
- **コンパイル時のバインド**：スケジューラ型はコンパイル時に決定される

| スケジューラ性能           | コンパイル時に DAG 分析完了、実行時は実行のみ             | 2026-05-11 |
| DAG 範囲整合               | DAG 分析は spawn ブロック内のみ、RFC-024 と整合           | 2026-06-05 |
| 3 層アーキテクチャ更新     | Embedded は spawn なし、Standard は spawn サポート        | 2026-06-05 |
