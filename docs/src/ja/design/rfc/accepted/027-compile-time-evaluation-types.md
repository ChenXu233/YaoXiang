# RFC-027：コンパイル時述語と統一静的検証

> **参考**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統一型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024：spawn ブロックベースの並行モデル](../accepted/024-concurrency-model.md)
>
> **置き換え**：[RFC-022: ホーア論理静的検証サポート（仕様注釈と仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止済

## 要約

本文は YaoXiang に**コンパイル時述語**を第一級市民として導入し、すべてのコンパイル時静的検証を一つの**証明パイプライン**に統一することを提案する。コンパイル時述語はアドオンの仕様注釈ではなく、それ自体が関数である。Type を返す関数は型位置で使用でき、コンパイラがコンパイル時に呼び出して戻り値を検査する。型は命題であり、コンパイル時評価は証明である。

**核心的論点**：型検査がコンパイル時に唯一行う仕事は証明項の構築と検証である。型の等価、トークン競合、依存型簡約、コンパイル時述語評価、ホーア論理含意——すべてコンパイル時証明パイプライン内の異なる型検査であり、同一のパイプラインを共有する。SMT ソルバは型検査器のアクセラレーションモジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返したとき、プログラマは YaoXiang 関数を証明として書く——型検査器は任意の関数の戻り型を検証するのとまったく同じ方法でそれを検証する。すべてが YaoXiang コードであり、すべてが型検査器によって検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 は仕様を `//!` 注釈形式として設計した：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← これは型と独立した注釈
    //! ensures: ExistsMax(result, arr[0..n])   ← これは型と独立した注釈
}
```

これは Curry-Howard 同型の根本的誤りを犯している：**仕様と型を二層に分裂させる**ことである。注釈は型ではない。注釈は型検査に参加しない。注釈は「外部ツール」のメンタルモデルである。

白書には明確に記載されている：

> "`//!` 注釈はない。独立した仕様言語もない。すべては型システム内にある。"

### 現在の問題

- RFC-022 の `//!` 注釈は type system から独立したアドオン構文
- 仕様型と通常型は二系統であり、概念の冗長を生む
- Debug Build 検証 / Release Build 無視の分裂パターンが統一性を破壊する
- SMT ソルバは従来の認識では外部ツールとして位置づけられるが、YaoXiang では型検査器のアクセラレーションモジュールとして内蔵する
- 型検査、借用検証、コンパイル時述語検査、マクロ展開はそれぞれ異なるパスを通る

### 正しいメンタルモデル

型検査は次のような関数として抽象化できる：

```
verify : Program → Proved | Disproved(Model) | Unproven
```

すべてのコンパイル時検査——単純な型一致、借用競合検出、コンパイル時述語検証——はこの関数のサブタスクである。これらは同一の証明パイプラインを共有し、差異は証明項の複雑さと構築戦略のみにある。

コンパイラが Unproven を返したとき、プログラマは証明関数を提供する——その関数の戻り型は証明すべき命題に等しい。型検査器がそれを検証する。これは通常の型検査と同じ操作である。

## 提案

### 1. `{}` は証明空間：型はアサーション、検証は型検査

YaoXiang の `{}`
はコンパイル時証明空間である。その中のすべてはアサーションであり、コンパイラは各項目が True であることを保証する——自動証明されるか、プログラマが証明関数を提供するかのいずれかである。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  コンパイラが x は Float、y は Float であることを保証

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  コンパイラが data は Array(T) であることを保証
```

**generics はコンパイル時述語の特殊例である。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          パラメータは署名位置    {} 内にはアサーションのみ
#          コンパイラは呼び出し時に x > 0 を検証

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      パラメータは署名位置  コンパイラは type_of(T) == Type、type_of(data) == Array(T) を検証
```

同じパターン：`name: (params) -> Type = { アサーション }`。コンパイラは「型アサーション」と「値アサーション」を区別しない——すべて証明パイプライン内の評価対象である。

**ループ不変条件を個別に書く必要はない。変数上の型注釈が Floyd-Hoare 不変条件そのものになる。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照——s の型が i に依存することをコンパイラに伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラが検証：s_new == sum(arr[0..i+1])
        i += 1       # i 変更 → s の依存再検証をトリガ：s は SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度の検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新値が型注釈を満たすか。証明パイプラインが帰納ステップを検証したすべての反復が自動的にカバーされる。`: decreases`
も、`: Invariant` も、帰納証明も不要——コンパイラは帰納を各代入の局所 VC に分解する。

### 2. 前置/後置条件：パラメータ型と戻り型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures`
を廃止する。コンパイル時述語はパラメータまたは戻りの型注釈として用いる。

**パラメータ側は関数呼び出しである。**
コンパイル時述語は Type を返す関数であり、パラメータ側の使用方法はそれを呼び出すことである——`factorial(5)`
と同じである。戻り値側は新しい概念を導入する：戻り値仮引数。

```yaoxiang
# 前置条件：パラメータ型で明示的にコンパイル時述語を呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在の仮引数名、Positive にパラメータとして渡される
#                       コンパイラは呼び出し点で実引数値を抽出し、b に代入し、Positive(実引数) を検証
#                       例：divide(10, 2) → Positive(2) = { 2 > 0 } を検証 → True
#                       例：divide(10, 0) → Positive(0) = { 0 > 0 } を検証 → False → コンパイルエラー

# 後置条件：戻り値仮引数 + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は戻り値仮引数、値は return で提供される
#                                            コンパイラは return 点で戻り値を代入し、後置条件を検証
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要なルール**：

- **パラメータ側**：`b: Positive(b)` —— `b`
  は現在の仮引数名、Positive にパラメータとして渡される。関数呼び出し構文、暗黙的機構なし。
- **戻り側**：`-> (result: IsMax(T, arr, result))` —— `result` は戻り値仮引数、値は `return`
  文で提供される。`result`
  は型署名内にのみ存在し、述語からのみ参照され、関数本体スコープに入らず、呼び出し側にも現れない。
- **戻り値仮引数はオプション**：後置条件がない場合は書かない。署名は通常の関数と完全に同一（`-> Int`）。
- **統一性**：パラメータと戻り値仮引数は同じ概念——`仮引数名: 述語呼び出し(仮引数名)`。差異は値が呼び出し側から提供されるか、`return`
  から提供されるかのみ。

### 3. パス条件伝播：ランタイム値のコンパイル時検証

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマが明示的に渡す。ランタイム値が精化型パラメータに入るとき、コンパイラはパス条件収集と SMT 含意判定を通じて検証を完了する——プログラマが明示的に証明を渡す必要はない。

#### 3.1 明示的関数呼び出し

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマが明示的に渡す——関数呼び出しそのもの、暗黙的機構なし。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。束縛位置（パラメータ宣言、変数宣言、戻り型）に現れるとき、プログラマは明示的に既に束縛された変数名を渡す：

```yaoxiang
b: Positive(b)
// b は現在の仮引数として宣言済み、Positive(b) は関数呼び出し
// 正規化後：b: { b > 0 }
```

コンパイラが暗黙的にパラメータを埋める必要はない——`b: Positive(b)` は `f(5)`
と同じく、関数呼び出しである。`b` はパラメータ名として束縛され、その型注釈 `Positive(b)` は `b`
自身を参照する——これは依存型の標準パターンであり、暗黙的展開ルールではない。

**RFC-010 の `self` との統一**：RFC-010 は `self`
がキーワードではなく単なるパラメータ名の慣習であることを確立した（「`p`、`this`、`x`
と書いても完全に同じ効果」）。`b: Positive(b)`
は同じ機構を共有する——パラメータ名は型注釈内で参照可能。`self` は `self: Point` の位置に現れ、`b` は
`b: Positive(b)`
の位置に現れる。両者の型注釈はパラメータ自身を参照する。差異は型注釈の複雑さにのみあり、機構は完全に同一——名前が束縛された後、型はこの名前に依存できる。

戻り型も同様に明示的関数呼び出しを使用する：

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は戻り値仮引数、Sorted(result) は関数呼び出し
//                        コンパイラは return 点で戻り値を result に代入し、Sorted(戻り値) を検証
```

局所変数宣言にも同様に適用される：

```yaoxiang
let x: Positive(x) = 5
// x は 5 に束縛、Positive(5) → { 5 > 0 } → True → 通過

// let y: Positive(y) = 0
// y は 0 に束縛、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 パス条件収集

ランタイム値が条件分岐に現れるとき、コンパイラは自動的にパス条件を収集し、現在のスコープの**仮定集合**を形成する。これらの仮定はコンパイル時 Bool 評価の背景知識として検証に参加する。

```yaoxiang
if y > 0 {
    // コンパイラはこの分岐内で自動的に仮定を取得：{ y > 0 }
    let result = divide(x, y)
    // 検証条件：(y > 0) ⇒ (y > 0)
    // 証明パイプラインが含意成立を判定 → Proved
} else {
// この分岐の仮定：{ !(y > 0) }
// divide(x, y) を呼び出す場合、検証条件は !(y > 0) ⇒ y > 0
    // 証明パイプラインが含意不成立を判定 → Disproved
}
```

これはコンパイラが特別パターンをハードコードするものではない——コンパイル時証明パイプラインの自然な振る舞いである。呼び出し点の型検査ごとに、パイプラインに次が送られる：

```
{背景仮定} ⇒ {検証対象}
```

証明パイプラインが含意性を判定する。Proved → 通過、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未解決命題。背景仮定は現在のプログラム点のパス条件に由来する。

#### 3.3 仮定スタック

コンパイラは制御フロー解析時に各基本ブロックに対して仮定集合を維持する：

- **if-ガード**：`if y > 0` → true 分岐に `y > 0` をプッシュ、false 分岐に `!(y > 0)`
  をプッシュ（else が使用されている場合）
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **論理結合**：`if x > 0 and y < 10` → 分岐内に `x > 0` と `y < 10` をプッシュ
- **関数前置条件**：`divide(a, b)` 呼び出し時、`b` が `Positive`
  を満たす証拠は現在の仮定からのものか、実引数自身の精化型注釈（`b` が `Positive`
  と注釈されていればその型は `b > 0` を運ぶ）からのもの
- **代入**：`let z = y` のとき、`y` 上の既存の精化条件が `z` に伝播する

すべての仮定はコンパイル時証明パイプラインに入る。SMT アクセラレーションパスに入るとき、SMT-LIB 背景アサーションに翻訳される。

#### 3.4 静的証拠なしはコンパイルエラー

プログラマが直接次のように書いた場合：

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム点には `y > 0` の仮定がなく、実引数 `y` 自身にも `Positive`
型注釈がない。検証条件は：

```
{} ⇒ { y > 0 }
```

パイプラインが `Disproved`（含意不成立）を返す → コンパイルエラー：

> `divide` 呼び出しにおいて引数 `b` が `Positive` を満たすことを証明できない。`y`
> は関数入力に由来し、証明済みの境界がない。if 分岐ガードで呼び出すことを検討：`if y > 0 { divide(x, y) }`。

YaoXiang は静的証拠を提供せずにランタイム値が精化型パラメータに直接入ることを許さない。これは制限ではない——これはハード安全哲学の核心である。コンパイラが静的に証明できないコードは、合格してはならない。

#### 3.5 統一パイプラインとの関係

パス条件伝播は追加の機構ではない。それはコンパイル時証明パイプラインの制御フロー解析上の直接の拡張である：

| 段階                 | 責務                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| パス条件収集         | コンパイラの制御フロー解析段階、各基本ブロックに仮定集合を注釈                                                                       |
| 検証条件生成         | 検証が必要な型制約に遭遇したとき、パス条件 + 実引数型情報をマージ                                                                    |
| 証明パイプライン評価 | コンパイラカーネル → SMT アクセラレーション → Proved / Disproved / Unproven を得る                                                   |
| 結果                 | `Proved` → 通過；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未解決命題（プログラマは証明関数を提供可能） |

新しい部品はない。特別なルールもない。パス条件は証明パイプラインの背景知識——型の等価、借用制約と同一パイプライン、同一予算システムを共有する。

### 4. コンパイル時証明パイプライン

すべてのコンパイル時検査は同一のパイプラインを共有する。パイプラインの核心操作は**型検査**である——証明項の型が証明すべき命題に等しいかを検査する。すべてが型検査である。

```
コンパイル時に Bool 式の評価が必要（即ち、証明項を構築する必要）
        │
        ├── 型の等価（T1 == T2）
        │   → コンパイラが直接判定（構造的等価性）
        │
        ├── トークン競合条件（!conflicting(tokens)）
        │   → フロー敏感生存解析（Dup/Linear 属性追跡）
        │
        ├── 依存型簡約（n + m 化簡）
        │   → コンパイル時項書き換えシステム（βδι-簡約）
        │
        ├── コンパイル時述語（x > 0、forall...）
        │   → コンパイラ自身 + SMT アクセラレーションモジュール
        │
        └── ホーア論理含意式（P ⇒ Q）
            → コンパイラ + SMT アクセラレーションモジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル通過
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未解決命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を書く（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル通過
                  │
                  ▼
            検証失敗 → コンパイルエラー：「証明が成立しない」
```

#### 4.1 証明結果：三値代数

コンパイル時評価は三つの結果を返す——これは停止問題の必然的帰結であり、証明論の自然な分画である：

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項が構築済み、型検査通過。コンパイル継続。
- **Disproved(M)** → 停止、反例 M が存在。コンパイルエラー + 反例 + ソースコード位置。
- **Unproven**
  → 与えられたリソース上限内で証明が構築されず。コンパイルエラー + 未解決命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言うのは命題が偽であることと同義ではない——現在の自動証明能力を超えているだけである。これは正直さであり、欠陥ではない。

予算のハード制限は停止問題の工学的解である。ノブは提供しない——提供すれば「あなたのプログラムは停止すると思いますか」とユーザに尋ねることになり、ユーザにもコンパイラにもわからない。

#### 4.2 Unproven の後：プログラマが証明を書く

コンパイラが Unproven を返したとき、プログラマは**証明関数**を書くことができる——戻り型が証明すべき命題に等しい YaoXiang 関数である。型検査器がこの関数を検証する——`add(a, b): Int`
を検証するのとまったく同じ機構で。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼の根）
```

SMT ソルバは独立した信頼境界ではなく、**型検査器のアクセラレーションモジュール**である。SMT が証明を見つけるのを助けるが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返したとき、コンパイラはその結果を型検査器が検証可能な証明項に再構成する。再構成が失敗した場合（SMT の推論ステップがコンパイラカーネルの推論規則を超える場合）、Unproven にフォールバックする——プログラマは手動で証明関数を書くことができる。

```yaoxiang
# 命題：コンパイラが自動証明できない精化属性
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明：プログラマが戻り型として上の命題を持つ関数を書く
# 型検査器がこの関数を検証する——add(a,b): Int を検証するのと完全に一致
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラはここで検証：関数本体の型 = FirstIsMin(T, arr)
    ...
}
```

AI も不要、Coq へのエクスポートも不要、新しい概念も不要。**コンパイル時に自動証明できない属性 → プログラマが YaoXiang コードで証明を書く → 型検査器が検証。**
プロセス全体はスムーズな勾配である——コンパイラが簡単な証明を代行し、頭は難しさに残す。

#### 4.3 パイプライン内の階層的依存

上の評価器は同一インターフェースを共有するが、評価順序が存在する。型の等価は後続解析すべての前提条件であり；所有権/トークン検査は型情報に依存し；精化述語検証は前二層の結果に依存する。コンパイラは層ごとに評価し、基盤層で失敗した式は上層に入らない——型エラーのあるプログラムでソルバ予算を浪費するのを避ける。

```
評価順序（同一パイプライン、階層的スケジューリング）
├── 第 0 層：型の等価（T1 == T2）
│   └── 構造的単一化 → 失敗すれば後続は無意味、直接 Disproved を返す
├── 第 1 層：所有権/トークン競合
│   └── フロー敏感生存解析 → 失敗すればメモリ安全が成立せず、直接 Disproved を返す
└── 第 2 層：精化述語/ホーア含意
    └── コンパイラ自身 → SMT アクセラレーション → Proved / Disproved / Unproven を得る
```

各層は依然として `Proved/Disproved/Unproven`
を返し、同一インターフェースと同一予算システムを共有する。

### 5. 三層関数統一

| 階層             | 実行時機     | 入力  | 出力 | 例                                             |
| ---------------- | ------------ | ----- | ---- | ---------------------------------------------- |
| 値レベル関数     | ランタイム   | 値    | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時 | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時 | 値    | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

すべて同じ `name: type = value`
構文を使用する。コンパイル時述語と型コンストラクタは同一のコンパイル時証明パイプラインを通る——`{}`
は証明空間である。

### 6. ループ：Floyd-Hoare 検証条件生成

ループは個別の `: Invariant(...)` や `: decreases(...)`
注釈を必要としない。変数上のコンパイル時述語型注釈が Floyd-Hoare 風のアサーションを定義する——コンパイラは型注釈から検証条件を生成し、証明パイプラインが各代入が型を保持するかを検査する。

核心的機構：各代入操作は Hoare 三つ組 `{P} x := e {Q}` に対応し、検証条件は `P ⇒ Q[e/x]`
である。コンパイラはループ本体に対して一度の検証条件を生成する——証明パイプラインが帰納ステップを検証したすべての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照；初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証：0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラはループ本体に対して一度の VC を生成。前提：s は SumUpTo(arr, i) を満たし、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]：
        #   検証義務：s_new は SumUpTo(arr, i) を満たす（現在 i は不変）
        #   s_new = s_old + arr[i] を代入：
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮説 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える：
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT：線形算術、ミリ秒オーダー → Proved
        #
        # i += 1：
        #   i 変更 → 依存グラフで s の型注釈が i を参照 → 再検証をトリガ
        #   新たな検証目標：s は SumUpTo(arr, i_new) を満たす
        #   即ち s == sum(arr[0..i_new])、上ステップで保証される → Proved
        s += arr[i]
        i += 1
    }
    return s  # このとき s: SumUpTo(arr, arr.len)、即ち s == sum(arr[0..arr.len])
}
```

ループ不変条件は変数上の型注釈そのもの——プログラマは型を書き、コンパイラは帰納ステップを検査する。コンパイラは不変条件を「発見」する必要も、自動的に「帰納を行う」必要もない——帰納証明を各代入操作の局所検証条件に分解し、証明パイプラインに分割して征服させる。

#### 6.1 依存追跡：可変変数上の依存型

上述の機構の前提は：コンパイラが `s` の型注釈 `SumUpTo(arr, i)` が `i`
を参照していることを知っていること——`i` が変更されたとき、`s`
の型制約もそれに応じて変化する。これはコンパイラが**変数間の型依存グラフ**を維持することを必要とする。

**データ構造**：

```
TypeDepGraph: Map<VarName, Set<VarName>>
# キーは依存される変数、値は型注釈内でその変数を参照する変数の集合
# 例：{ i: {s}, j: {s, t}, ... }
```

**構築**：型検査器が `mut v: Pred(... x ...) = init` を処理するとき、`Pred(...)`
引数内の自由変数参照を解析する。引数が現在のスコープ内の他の可変変数 `x`
を参照する場合、依存グラフに `x → v` を記録する。

**トリガ**：依存される変数 `x` が代入されるとき、コンパイラは：

1. 依存グラフで `x` に依存するすべての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` に対して、検証条件を生成：`v の現在値が更新後の型 Pred(... x_new ...) を満たすか`
3. VC を証明パイプラインに送る

**代入順序に敏感**：依存追跡は正しい代入順序を自然に強制する。`SumUpTo(arr, i)` を例に取ると：

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証 → True

# 誤った順序——コンパイラが拒否
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証
              # s はまだ更新されていない、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー：変数 s は型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**合成依存**：一つの変数が複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は `x` と `y`
の両方に同時に依存する——いずれの変更も再検証をトリガする。

**証明パイプラインとの関係**：依存追跡は VC 生成のトリガであり、独立した検証機構ではない。それは「いつ VC を生成する必要があるか」に答え、証明パイプラインは「VC が成立するか」に答える。

### 7. 停止性検査

**適用範囲：精化型。**
停止性は独立したスイッチではなく、**検証モード**の一部である：型が精化された（`Refined { base, constraint }`）瞬間、それが注釈する計算は検証モードに入り、モード内で停止性が要求される；精化されていない通常型は検証モードに入らず、停止義務を生成しない。

ここから二つの帰結が得られる：

- **ループ**：生の `while`
  は検証モードに入らない；計量変数が精化注釈を持つ（例：`i: UpTo(n)`）とき検証モードに入り、停止の証明が必要。
- **再帰**：関数署名が精化を持つ（パラメータ精化または戻り型に精化を含む）とき検証モードに入り、各再帰呼び出し点の測度が厳密に減少することの証明が必要。

モード内では全自動優先：コンパイラがまず自動的に測度を探求し、証明できるものは通過する；探求できずかつ明示的に測度が与えられていない場合はコンパイルエラー。**注釈構文の抜け道はない**——測度と停止命題は型位置に書かれ、`decreases`
系の新構文を導入しない。測度と明示的フォールバックの形態は §6.9 を参照。

#### 6.1 設計原則

コンパイラは二箇所から停止証明に必要な情報を自動抽出する：

1. **変数型注釈**：精化型内の境界制約（例：`UpTo(n)` は上界 `n` と下界 `0` を与える）
2. **ループ本体の操作**：各反復で変数に加えられる操作

コンパイラは優先順位に従って四つの計量合成戦略を試し、見つかれば停止する。四つの戦略は**測度探求の制限されたテンプレート列**であり、入力は精化制約（戦略 1–4 すべて「有界型の変数」を起点とする）であり、「コンパイル時評価されるコード」ではない；これらは §6.9 の明示的測度と同じ事柄の自動と手動の二面である。

> **測度探求は推論ではなく探求である。**
> 探求はテンプレート（線形ランク、違反カウント、有界パターン、乗法スケール）のみを列挙し、存在解を保証しない——汎用測度推論は一般に決定不能（停止問題に帰着）。したがってテンプレートの外側はプログラマが明示的に測度を与える必要があり（§6.9）、さもないとコンパイルエラーとなる。

#### 6.2 戦略 1：線形ランク関数の自動合成

変数が線形境界注釈を持つとき、コンパイラは候補線形測度を列挙し SMT 検証する。

```
入力：
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（上下界を持つ変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム：
  1. 型注釈から各変数の境界を抽出：[low_i, high_i]
  2. 候補測度を列挙：v_i, u_i - v_i, v_i - v_j 等の線形結合
  3. 各候補測度 m に対して：
     - SMT が m ≥ 0 を検証（型境界から導出）
     - ループ本体の各実行パスについて、SMT が m' < m を検証（厳密減少）
  4. 条件を満たす線形結合を見つける → 停止が証明される
```

適用範囲：任意の変数が線形式（`v = a·v + b`）で代入され、有界型注釈を持つループ。`i += const`、`i -= const`、および二分探索風の区間収縮を含む：

```yaoxiang
# 二分探索：low = mid + 1 または high = mid
# 計量 high - low は二つのパスでともに厳密減少
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2：述語違反カウント——目標型から自動抽出度量 <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在の状態：実験的戦略、Phase 3 実装時に実際の実現可能性に応じて含めるかどうかを判断する。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効であり、非隣接操作（クイックソート partition、ヒープソート sift-down）は自動証明できない。適用境界は下表参照。Phase
> 3 で実現不可能と検証された場合、この戦略は削除されるか将来の作業に格下げされる。

核心的洞察：**ユーザが書いた仕様はコンパイラの推論材料である。**
コンパイラは「ソートとは何か」を内蔵する必要がない——`Sorted`
の定義を読み、定義から自動的に測度を抽出する。

```
入力：
  目標型：Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体の操作：隣接要素交換

アルゴリズム：
  1. 述語定義を解析：forall i in range: cond(i, arr)
  2. 自動生成計量：violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作が計量に与える影響を分析：
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の三対のみに影響
     - arr[j] > arr[j+1]（述語違反）の場合、交換後この対は述語を満たす
     - violation_count は少なくとも 1 減少
  4. 上界：n·(n-1)/2（最大隣接逆順数）、下界：0
  → 停止が証明される
```

**現在の適用範囲**：

| アルゴリズム   | 操作モード | 戦略 2 で証明可能？ | 理由                                          |
| -------------- | ---------- | :-----------------: | --------------------------------------------- |
| バブルソート   | 隣接交換   |         ✅          | violation_count は各交換で厳密減少            |
| 挿入ソート     | 隣接移動   |         ✅          | 各シフトが一つの違反対を解消                  |
| 選択ソート     | 非隣接交換 |         ❌          | 単一交換が violation_count を増加させる可能性 |
| クイックソート | partition  |         ❌          | 非隣接交換、単調減少を保証しない              |
| ヒープソート   | sift-down  |         ❌          | 木構造操作、violation_count は非単調          |

**補完的戦略**：クイックソートの場合、`low < high`
区間収縮は戦略 1（線形ランク関数）でカバーできる——外層 partition 再帰、各反復で区間が半分になる。戦略 1 と戦略 2 は補完的に適用範囲をカバーし、ほとんどの実用アルゴリズムの停止性は両者のいずれかで証明可能。ただし戦略 2 の汎用化（非隣接操作、木構造操作）は依然として未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3：有界増分/減分パターン

`v += const`（正の定数）、変数が上界型注釈を持つ → 計量 `upper_bound - v` は毎回 `const`
減少し、下界は 0。これは戦略 1 の縮退情況で、コンパイラは最初に迅速に処理する。

#### 6.5 戦略 4：乗法スケール計量テンプレート

`v *= const`（const > 1）、変数が上下界型注釈を持つ。コンパイラは対数計量テンプレート
`ceil(log_const(upper/v))` を内蔵し、毎回 const 倍するごとに計量が 1 減少する。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラが自動推論：計量 ceil(log₂(n/i))、毎回 2 倍するごとに計量が 1 減少
    i *= 2
}
```

#### 6.6 停止性と正当性の分離

停止性証明と正当性証明は独立している：

- **停止性**：上記の四戦略がループが有限ステップで終了することを自動証明する；探求できない場合はプログラマが型位置に測度を与える（§6.9）
- **正当性**：ループ本体が目標型に向かって進行しているかは、コンパイル時証明パイプラインが検証条件を通じて検査する

両方が通過 → コンパイル通過。停止性は証明されたが正当性が失敗 → コンパイルエラー + 反例。正当性は証明されたが停止性が証明できない → コンパイルエラー、分析不能な変数または操作を指摘する。両方失敗 → コンパイルエラーが二つの失敗原因を別々に報告する。

#### 6.7 再帰関数の停止性検査

精化署名を持つ再帰関数について、コンパイラは各再帰呼び出し点の仮引数減少を検査する：

```yaoxiang
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)  // コンパイラが探求：(b, a % b) の整礎順序測度が減少 → 停止
}
```

仮引数減少は最強の自動パス（構造的再帰）である。探求できない場合、プログラマが型位置に明示的に測度を与える（§6.9）。

#### 6.8 ハード境界

`i = f(i)` かつ `f`
が非可逆、閉じていない、単調性を一切保持しない——数学的に自動停止証明が不可能。コンパイルエラー：

> このループは自動停止証明ができない。ループ変数が分析不能な関数 `f`
> に依存している。コンパイラが分析可能な反復パターンを使用するか、このループに名前を付け、型位置に測度を提供してください（§6.9）。

これはコンパイラの失敗ではない。静的に安全性を証明できないコードは、コンパイルを通過してはならない。たとえ明示的測度を与えても、SMT により真と判定されなければ通過しない——測度の書き方が誤っていれば反例で返され、人間は証明できないだけで、誤って証明することはできない。

#### 6.9 明示的測度：`Terminates`

自動探求で測度が見つからない場合、プログラマは測度を**型位置**に書く——`Positive(b)`、`IsMax(T, arr, result)`
と同じ機構（述語適用）であり、新構文はゼロ：

```yaoxiang
// 測度：通常関数、ユニットテスト可能、再利用可能、ランタイムに参加しない
gcd_measure: (a: Int, b: Int) -> Int = { b }

// 停止成分が関数自身の型位置に育つ
gcd: Terminates((a: Int, b: Int) -> Int, gcd_measure) = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

// ループ：束縛名がアンカー、測度は名前によりスコープ内の量を取得
loop: (n: Int) -> Int = {
    mut i = 0
    acc: Terminates(n - i) = while i < n {
        i = i + 1
    }
    return acc
}
```

ループでの理由：`Terminates(m)` が精化するのはループ本体の末尾式の値の型であり、アンカーは束縛名
`acc` が提供する——ループはこうして指示可能になり、「無名構造は指示不能」という死角はなくなる。

**`Terminates` は組み込み述語**であり、`Int`、`Never`
と同じ中核プリミティブに属する。これは**コンパイラが関数本体を代筆する唯一**の述語である——そのアサーション（「各再帰呼び出し点/ループバックエッジの測度が厳密減少する」）は計算構造の中に育ち、ユーザが書く述語は関数本体やループ本体を参照できないため、「構文」節の述語定義構文では表現できない。組み込み面はこの一つの名前に収束する。

**アリティ**。`Terminates(FnType, m)` と `Terminates(m)`
は同じ述語の二つのアリティであり、二つの異なる構造ではない：

| 形態                    | アンカー       | 用途                                     |
| ----------------------- | -------------- | ---------------------------------------- |
| `Terminates(m)`         | 所在束縛の名前 | 自己再帰関数、ループ——デフォルト形態     |
| `Terminates(FnType, m)` | 明示的関数型   | 相互再帰などアンカーが一意でないシナリオ |

両者本質的に同一：停止義務は常に「精化が位置する型位置に注釈される計算」に落ちる。

**測度は戻り型を制限しない。**
測度は任意型の式であってよく（自然数を強制しない）；その上の「厳密減少」は当該型で利用可能な整礎順序によって与えられる。測度が整礎であるか（例：`Int`
を返すとき `>= 0`
か）は**独立した義務**であり、減少義務と同様に精化推論または SMT に委ねられる；両方が推論できない場合、診断は**直接拒否せず**、検査方向を提案する（測度の下界が成立するか、再帰パラメータが本当にその方向に進んでいるか）。

**自動探求との関係**：明示的測度は別のパイプラインではなく、探求失敗後の入力である。測度を与えた後も同一の SMT が減少と整礎性を検証する；成立しなければエラーと反例を添付する。

義務生成、判定パイプライン、診断方向、相互再帰の測度共有（SCC）等の実装機構は
[RFC-027a: 停止性検査の明示的測度](../review/027a-termination-explicit-measure.md) を参照。

### 8. SMT ソルバ：型検査器のアクセラレーションモジュール

SMT ソルバは従来の言語では外部ツール（F\* が Z3 を呼ぶ、Dafny が Z3 を呼ぶ）。YaoXiang ではそれは**型検査器の一つのアクセラレーションモジュール**である——コンパイラカーネル自体が直接判定できない場合のみ呼び出される。SMT が証明を見つけるのを助けるが、証明を検証するのは型検査器である。

**信頼モデル**：型検査器は唯一の信頼の根である。SMT ソルバはアクセラレーションモジュール——証明を見つけるのを助けるが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny の路線と一致——Z3 が誤る確率はコンパイラ自身のバグ率より低く、これは工学上の実務的選択である）。真の信頼性の懸念は SMT 翻訳層に制御される——翻訳にバグがあれば、コンパイラは他のテストで露呈する。

**インターフェース**：コンパイラ内部は SMT-LIB
2.6 標準フォーマットに翻訳し、特定のソルバ API に縛られない。SMT-LIB は ISO 標準であり、Z3、CVC5、MathSAT、Yices すべてネイティブサポートする。

**デフォルトバックエンド**：Z3（MIT ライセンス、最も広範な文書化とコミュニティ検証）。CVC5 は SMT-LIB 互換の代替——ユーザはコンパイル時フラグで切り替え可能。

「汎用ソルバ抽象層」は作らない——SMT-LIB が抽象層である。将来 CVC5 が特定理論でブレークスルーを達成した場合、切り替えはバイナリを交換するだけでよく、コンパイラコードの変更は不要。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造的等価性、単純算術、
        │   定数畳み込み後の自明な式）
        │   → 直接 Proved / Disproved を返す
        │
        └── コンパイラカーネルが直接判定不能（限量子、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB フォーマットに翻訳
            → Z3/CVC5 に送信（予算制限付き）
            → 戻り値：unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**ソルバ予算——ハード制限、スタック深度のように**：

| 予算次元                 | デフォルト値 | 説明                                                                                                                                           |
| ------------------------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| ソルバステップ数         | 10,000       | Z3 は線形算術に対し通常百ステップ以内。10,000 ステップで実用述語の 99% をカバー。                                                              |
| 時間                     | 100ms        | 単一述語が 100ms を超える = ユーザがコンパイル時プログラムを書いているのではなく型注釈を書いている。100ms × 50 述語 = 5 秒コンパイル時間上限。 |
| 限量子インスタンス化深度 | 3            | 三層入れ子限量子が実際のパターンをカバー。これを超えると大抵は論理の練習問題を書いている。                                                     |

予算超過は Unproven を返し、コンパイルエラー + 述語位置 + 消費量。降格なし、ランタイムチェックなし、silent
pass なし。

**なぜこれが実用可能か**：工学上、実用述語の 95% は線形算術である——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——すべて決定可能フラグメント内にあり、SMT ソルバは这类問題に対しミリ秒オーダーで返す。予算を超える複雑な述語に遭遇した場合、プログラマは証明関数を書けばよい。

依存型は SMT 呼び出し前に事前簡約を行う：`factorial(5)` は直接コンパイル時評価で `120`
となり、`append([1,2], [3])` は直接評価で `[1,2,3]`
となる。これらの決定論的な値計算は SMT 予算を消費しない。

プログラマは SMT の存在を知る必要がない。メンタルモデルは：**コンパイラが証明できれば通過、できなければエラー——コンパイラができなければ、関数で証明して見せることができる。**

### 9. コンパイル時述語合成

コンパイル時述語は Type を返す関数であり、合成は関数合成を通じて自然に実現される：

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算安全性

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラが Positive(2) = { 2 > 0 } を検証 → True
# result = divide(10, 0)  # ❌ コンパイラが Positive(0) = { 0 > 0 } を検証 → False
```

#### 9.2 配列アクセス安全性

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラが InBounds(1, arr) = { 0 <= 1 and 1 < 3 } を検証 → True
# y = get(arr, 5)  # ❌ コンパイラが InBounds(5, arr) = { 0 <= 5 and 5 < 3 } を検証 → False
```

#### 9.3 ソート正当性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ：コンパイラの VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 分派パイプライン：コンパイル時とランタイムの統一分派

`assert` と `Assert` は同じ精化型プリミティブの二面である。分派パイプライン `dispatch`
は**述語の自由変数がコンパイル時に参照可能か**に基づいて自動的にコンパイル時証明とランタイム検査のいずれかに分派する：

| 判拠                                                                        | モード          | 振る舞い                                                                                  |
| --------------------------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------- |
| すべての自由変数がコンパイル時既知（generics パラメータ、コンパイル時定数） | **CompileTime** | 証明パイプラインに入る：Proved → 消去、Disproved → コンパイルエラー、Unknown → 証明を要求 |
| 自由変数がランタイム由来（関数パラメータ、外部入力、mut 変数）              | **Runtime**     | ランタイム check を挿入し、フロー敏感仮定集合 Γ に精化事実を注入                          |

**要点**：「判らない」≠「反証」。CompileTime モードでの Unknown は証明を要求し（silent 降格なし）、Runtime モードでは命題はそもそもコンパイル時に真偽を持たない——prover がどれほど強くても「ユーザが負数を入力したかもしれない」に対し恒真証明は書けないため、ランタイム check は唯一の sound な選択である。これは prover が弱いからではなく、理論的必然である。

### 12. フロー敏感仮定集合 Γ：最強後置条件伝播

コンパイラはフロー敏感（flow-sensitive）仮定集合 Γ を維持し、各制御フロー点で既知の成立命題を追跡する。

**SP（最強後置条件）伝播**：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**：`mut`
変数が再代入された後、当該変数に関するすべての仮定が Γ から削除される：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

これは soundness のハード要求である——変数の値が変われば、旧仮定は無効になる。

**分岐合流**：IF/ELSE または match 分支が合流するとき、Γ は各分岐仮定の交差集合を取る。すべてのパスで成立する命題のみが分岐の外に持ち出される。

### 13. 消去モデルの明確化：witness 消去 ≠ check 消去

RFC-027 の「精化型はランタイムで**完全に消去される**」という論断は **proof
witness（証明トークン）**を指す——コンパイル時に検証された証明項は実行時コードを生成しない。ただし Runtime モードで dispatch が挿入する**ランタイム check**
は保持される——それは値レイヤで実行される Bool 検査であり、型レイヤの witness ではない。

まとめ：witness 消去、check 保持。二つの事柄は衝突せず、RFC-027 の原論断は変わらない。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以降 (本 RFC)                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語をパラメータ型として `(b: Positive(b))`                                                |
| `//! ensures: ExistsMax(result, arr)` | 戻り型に戻り値仮引数を使用 `-> (result: IsMax(T, arr, result))`                                        |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変条件                                                   |
| `//! decreases: n`                    | 測度は精化型位置に書く（`Terminates`）；コンパイラがまず自動探求、探求できない場合のみ明示的提供を要求 |
| 仕様は注釈                            | 仕様は type system                                                                                     |

### 構文

**コンパイル時述語に新しいキーワードはない。** `{}`
は証明空間であり、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数そのもの——`name: (params) -> Type = { アサーション }`。使用は関数呼び出し——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証するアサーション
# 既存の関数/型構文を使用し、新たな BNF 規則は不要
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**述語適用の実引数はコンパイル時定数の形式**でなければならない——literal、変数（名前による束縛）、型適用（再帰的抽出）、または**コンパイル時指示可能な関数参照**（関数名）。実引数形式が定数式に変換できない場合は
**E1092**、実引数の個数が述語宣言の仮引数の個数と一致しない場合は **E1093**
を報告する。実引数は位置により仮引数リストに束縛され、述語のアリティは宣言により決定される——`Positive(x)`
は一引数、`IsMax(T, arr, result)` は三引数、`Terminates(m)` と `Terminates(FnType, m)`
は一引数と二引数——精化制約は**決して silent に破棄されない**（以前は変換不能な実引数が制約を無音消失させ、違反する束縛が silent 通過していた）。

**新しい構文概念：戻り値仮引数**——`-> (name: Type)` の `name` は戻り値仮引数。

戻り値仮引数は YaoXiang が既存の関数構文に導入する**唯一の構文概念**である。その意味：

- `name` の値は `return` 文により提供される
- `name`
  は型署名内にのみ存在し、後置条件述語から参照される（例：`-> (result: IsMax(T, arr, result))`）
- `name` は関数本体スコープに入らず、呼び出し側にも現れない
- 戻り値仮引数は**オプション**——後置条件がない場合、署名は通常関数と完全に一致（`-> Int`）し、追加負担を導入しない

これを導入する理由：後置条件は「関数が返そうとしている値」を参照する必要がある。戻り値仮引数がない場合、コンパイラは特別な規則（暗黙的変数
`$result` や `__retval__`
など）によってのみ述語に戻り値を参照させることができる。戻り値仮引数により、この参照が明示化される——これは単なる仮引数であり、値の提供元が呼び出し側ではなく
`return` であるだけである。

**証明関数**は新しい概念ではない——戻り型がアサートされる命題である YaoXiang 関数そのもの。コンパイラが Unproven を返したとき、プログラマは証明関数を提供し、型検査器が任意の関数の戻り型を検証するのと完全に同じ方法で検証する。新しい構文もキーワードもルールも必要ない。

> **両者の境界。**
> 正当性領域（述語 Unproven）は**本体**で証明を補う：戻り型が証明すべき命題である関数を書く。停止領域（§6.9）は**型位置**で測度を補う：`Terminates(測度)`
> を束縛または関数署名の型として書く。前者は「証明できない命題を証明として書く」、後者は「探求できない測度を明示宣言する」——機構は同一（いずれも精化型適用）であり、落とし所が異なる。停止領域は
> `_proof` 関数を**書く必要がない**。

### 型システムへの影響

- **型宇宙**：コンパイル時述語は Type₂ 層に位置する——値を受け取り Type を返す関数で、型コンストラクタと同層
- **generics 相互作用**：コンパイル時述語は generics パラメータを取れる、 例：`NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **ownership 相互作用**：コンパイル時述語内の式は所有権規則に従い、読み取りのみで書き込み不可
- **type inference**：コンパイル時述語のパラメータは HM 型推論に参加する

### ランタイム表現

コンパイル時述語のランタイム処理は**dispatch 分派結果に従う**：

- **CompileTime モード**（すべての自由変数がコンパイル時既知）：証明通過後、witness トークンは完全に消去される。`Positive: (x: Int) -> Type = { x > 0 }`——パラメータ
  `b: Positive(5)` のランタイム表現は `Int`。精化条件 `{ 5 > 0 }` は通過済み、消去される。
- **Runtime モード**（ランタイム自由変数が存在）：ランタイム check を保持——値レイヤで Bool 検査を実行し、フロー敏感仮定集合 Γ に注入。詳細は §11
  dispatch 分派パイプラインと §13 消去モデルの明確化を参照。

コンパイル時述語を型位置に置く（例：`f(x: Positive(x))`）ことはラッパ型を生成せず、余分なメモリを割り当てない。ただし
`x` がランタイム入力由来の場合、**ランタイム Bool 検査が挿入される**。

**`ref`
との相互作用制約**：コンパイル時述語は不変借用または所有権が既に移譲済みの値のみを参照できる。可変借用を参照するコンパイル時述語は、コンパイラがコンパイル時に検証結果がランタイムでも成立することを保証できない——此类の用法は直接コンパイルエラーとなる。

### コンパイラ変更

1. **パーサ**：コンパイル時述語は標準関数構文を使用し、追加の解析規則不要
2. **コンパイル時証明パイプライン**：Proved/Disproved/Unproven 戻りインターフェースを統一、自動戦略選択
3. **SMT アクセラレーションモジュール**：SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**：推論規則の実装——構造的等価性、βδι-簡約、全称量詞導入/除去。これは唯一の信頼の根であり、SMT とプログラマの証明はともにこれを介して検証される
5. **検証条件生成**：WP/SP 計算 + ループ不変条件証明義務
6. **エラーレポート**：反例フォーマット化 + 未解決命題レポート + ソースコード位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用しないコードは完全に変化なし
- ✅ コンパイル時述語は CompileTime モードでランタイムオーバーヘッドゼロ、Runtime モードでは必要な Bool 検査のみ保持
- ⚠️ RFC-022 の `//!`
  構文はもはやサポートされない——しかし 022 はかつて実装されたことがなく、移行負担はない

## トレードオフ

### 利点

- **Curry-Howard 同型の完全実現**：型は命題、プログラムは証明、`name: Proposition = Proof`
- **統一性**：コンパイル時述語と通常関数は完全に同じ構文を使用し、概念分裂なし
- **SMT 透明**：プログラマは SMT の存在を知る必要がなく、メンタルモデルは型検査と一致
- **漸進的採用**：一つのコンパイル時述語から始め、徐々にカバレッジを拡大可能
- **最小ランタイムオーバーヘッド**：CompileTime モードはオーバーヘッドゼロ、Runtime モードは必要な Bool 検査のみ保持

### 欠点

- **コンパイル時間**：SMT 求解がコンパイル時間を増加させるが、予算のハード制限により上限は制御可能
- **自動証明の境界**：一階線形算術を超える複雑な述語はプログラマが証明関数を書く必要がある。これは言語の欠陥ではなく、停止問題の必然的帰結である。コンパイラは False/True を偽報告せず、Unproven を正直に報告する
- **学習曲線**：効果的なコンパイル時述語と証明関数の記述には Curry-Howard 同型の基本直感の理解が必要
- **実装複雑性**：コンパイル時証明パイプラインの統一は慎重な設計が必要

### リスク緩和

- SMT ソルバ予算のハード制限（ステップ数 10,000 / 時間 100ms
  / インスタンス化深度 3）、予算超過は Unproven を返す
- 依存型事前簡約：決定論的な値計算を先に消費し、SMT は非決定的部分のみを処理
- Unproven は終点ではない：正当性領域は証明関数を書く（戻り型が命題）、停止領域は型位置に測度を与える（§6.9）——いずれも型検査器が検証
- 増分検証：変更モジュールのみ検証
- 明確なエラーメッセージ + 反例表示 + 予算消費レポート + 未解決命題 + 提案（コンパイラが提供可能な場合）

## 代替案

| 案                                       | 選択しない理由                                                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| RFC-022：`//!` 注釈式仕様                | 仕様と型が分裂し、Curry-Howard 同型に違反                                                                                 |
| 独立仕様ファイル（例：CVL）              | 仕様とコードが分離し、保守コストを増加                                                                                    |
| ランタイムアサーションのみ               | 静的正当性保証が不可能                                                                                                    |
| 外部証明支援ツール（例：Coq）            | コンパイラと切断され、独立した証明言語と信頼境界が必要。YaoXiang の選択：証明は YaoXiang コード、型検査器は唯一の信頼の根 |
| **本案：コンパイル時述語を第一級市民に** | ✅                                                                                                                        |

## 実装戦略

### 段階区分

| 段階        | 内容                                                                                                                        |
| ----------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Phase 1** | コンパイラカーネル：構造的等価性 + βδι-簡約 + 全称量詞導入/除去。単純算術述語（`x > 0`、`arr.len > 0`）をサポート           |
| **Phase 2** | SMT-LIB 翻訳層 + Z3/CVC5 統合。パイプラインが Proved/Disproved/Unproven を返す。Unproven 時にプログラマの証明関数をサポート |
| **Phase 3** | ループ不変条件 VC 生成 + 停止性検査（測度探求四戦略 + `Terminates` 明示的測度、§6、§6.9）                                   |
| **Phase 4** | 増分検証 + キャッシュ + IDE サポート                                                                                        |

### 依存関係

- RFC-009: 所有権モデル — コンパイル時述語内の式は所有権規則に従う

## オープン問題

- [x] **wasm32 ターゲットの Z3 可用性**：wasm 下に Z3 はない（SMT コードはすべて
      `cfg(not(target_arch = "wasm32"))` で除外）。影響範囲と降格方向：- `ownership.rs` の `smt_cut`
      は常に `false` を返す → バックエッジ横断 →
      **保守的拒否**（sound 方向、絞込み減少のみ）- 停止性検査戦略 1、述語第 2b/3 級を全体的にスキップ現在**到達不能**：`TypeEnvironment::predicate_defs`
      は本番では決して填充されず（テストのみ）、`parser` は `MonoType::Refined`
      を生成しないため、精化述語パスは本番に存在しない；停止戦略 1 の注入点（`TerminationChecker::with_solver`）は本番では決して呼ばれず、native も実行しない。したがって wasm と native の**実際の振る舞いの差は
      `smt_cut`
      の精度にのみあり**、soundness には影響しない。将来 wasm で Z3 を有効にする場合、案と代価は issue
      #376 を参照（結論：Z3 を主 wasm に組み込むのではなく、JS 側 Z3 インスタンスを優先する——後者は emcc ビルド体系の交換が必要で、生成物が 3
      MB から約 20 MB に膨らむ）。
- [x] **SMT ソルバ選択**：デフォルト Z3（MIT ライセンス、最も広範に検証）。CVC5 は SMT-LIB 互換の代替で、コンパイラフラグで切り替え。コンパイラ内部は SMT-LIB
      2.6 標準フォーマットに翻訳——SMT-LIB が抽象層であり、カスタム汎用ソルバインターフェースは作らない。
- [x] **ソルバ予算の具体的数値**：ステップ数 10,000 / 時間 100ms
      / 限量子インスタンス化深度 3。コンパイラ内部で固定、knob なし。実際の使用で本当に不十分であることが証明された場合（「ユーザが書き間違えた」ではなく）、調整する。
- [x] **限量子のサポート範囲**：言語レベルでは限量子の階数を制限しない。コンパイル時述語は Type パラメータを受け取る——Type は関数型を含む——そのため高階限量子は型システムの自然な帰結であり、特殊構文は不要。SMT ソルバは一階限量子（forall/exists、交互入れ子サポート、予算深度 3 により制限）を自動判定可能。高階限量子：SMT は Unproven を返し、コンパイラは「本述語は自動証明範囲外、証明関数を提供してください」と指示する。プログラマは戻り型が該命題に等しい YaoXiang 関数を書く——型検査器がその関数を検証する。外部エクスポート不要、AI 不要、対話的証明モード不要。すべてが YaoXiang コード、すべてが型検査器により検証される。
- [x] **反例フォーマット**：ソースコード変数名を直接 SMT 変数名として使用（モジュール接頭辞を付加して衝突回避）。Z3 モデルが返されたとき、変数名で逆引き。出力フォーマット：変数名 = 具体値 + ソースコード位置 + 述語定義位置。複雑なマッピング層は作らない。
- [x] ~~**`ref` スマートポインタとのコンパイル時述語相互作用？**~~
      → 決定済：コンパイル時述語は不変借用または所有権移譲済みの値のみを許可。可変借用の値はコンパイル時述語に出現できない。
- [x] **`forall` 述語違反カウント測度の非隣接操作への拡張？**
      → 拡張しない。現在の適用範囲（隣接交換、隣接移動）は戦略 1（線形ランク関数）で補完的にカバーされる——クイックソートの外層区間収縮は戦略 1 がフォールバックし、ヒープソートは戦略 1（配列インデックスパターン）がフォールバックする。どの戦略でも停止を証明できないループは、コンパイラが直接エラー報告する——これはハード安全哲学であり、欠陥ではない。将来、非学術的真実のシナリオがあり四戦略でカバーできないアルゴリズムがあれば、再議論する。→
      **再議論がトリガされた（2026-09-14、#318）**：非構造的再帰（gcd 類の非直接減少、相互再帰、マージ partition）——これは本条項が予期していた現実のシナリオであり、測度探求のテンプレート列が自動的に拿下できず、可読性を損なわない形で分析可能な反復パターンに書き直すこともできない。結論：ハード安全哲学は不変（測度の書き方が誤れば SMT の反例で返される、人間は証明できないだけで誤証明はできない）が、「探求できなければ拒否」を「探求できなければプログラマが型位置に明示的測度を与えられる」に緩和——§6.9 参照。
- [x] **線形ランク関数の列挙組み合わせ爆発**：候補列挙上限は 3 個の有界変数。≤3 の場合、すべての線形結合を列挙し SMT で逐一検証。>3 の場合、単変数計量のみ試行（`v_i`、`u_i - v_i`）、失敗すれば直接コンパイルエラー——「ループに >3 個の有界変数があり、コンパイラが多変量計量を自動合成できない」と指示。これは工学的妥協ではなく、プログラマにより単純なループを書くことを促すものである。
