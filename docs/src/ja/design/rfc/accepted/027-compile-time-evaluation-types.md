# RFC-027：コンパイル時述語と統一静的検証

> **参考**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統一型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024: spawn ブロックに基づく並行モデル](../accepted/024-concurrency-model.md)
>
> **置き換え**：[RFC-022: ホーア論理静的検証サポート（仕様注釈と仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止済み

## 概要

本文は YaoXiang に**コンパイル時述語**を一級市民として導入し、全てのコンパイル時静的検証を**証明パイプライン**に統一することを提案する。コンパイル時述語は外部仕様注釈ではなく——それ自体が関数である。Type を返す関数は型位置で使用可能であり、コンパイラがコンパイル時に呼び出して戻り値をチェックする。型が命題であり、コンパイル時評価が証明である。

**核心的論点**：型検査がコンパイル時に唯一行うことは、証明項の構築と検証である。型等式、トークン衝突、依存型簡約、コンパイル時述語評価、ホーア論理含意——全てがコンパイル時証明パイプライン内の異なる型検査であり、同じパイプラインを共有する。SMT ソルバーは型検査器の加速モジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返したとき、プログラマは YaoXiang 関数を証明として書く——型検査器は任意の関数の戻り型を検証するのとまったく同じ方法でそれを検証する。すべてが YaoXiang コードであり、すべてが型検査器によって検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 は仕様を `//!` 注釈形式として設計していた：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← これは型と独立した注釈
    //! ensures: ExistsMax(result, arr[0..n])   ← これは型と独立した注釈
}
```

これは Curry-Howard 同型の根本的な誤りを犯している：**仕様と型を二層に分裂させている**。注釈は型ではない。注釈は型検査に参加しない。注釈は「外部ツール」のメンタルモデルである。

白書には明確に書かれている：

> "`//!` 注釈はない。独立した仕様言語はない。すべてが型システム内にある。"

### 現在の問題

- RFC-022 の `//!` 注釈は型システムと独立した外部構文である
- 仕様型と通常型は二つの体系であり、概念の冗長を生む
- Debug Build 検証 / Release Build 無視の分裂モデルが統一性を破壊する
- SMT ソルバーは従来の認識では外部ツールとして位置づけられるが、YaoXiang では型検査器の加速モジュールとして内蔵する
- 型検査、借用検証、コンパイル時述語検査、マクロ展開がそれぞれ異なる経路を辿る

### 正しいメンタルモデル

型検査は次のような関数として抽象化できる：

```
verify : Program → Proved | Disproved(Model) | Unproven
```

全てのコンパイル時検査——単純な型マッチング、借用衝突検出、コンパイル時述語検証——がこの関数のサブタスクである。それらは同じ証明パイプラインを共有し、証明項の複雑さと構築戦略のみが異なる。

コンパイラが Unproven を返したとき、プログラマは証明関数を提供する——その関数の戻り型は証明対象の命題に等しい。型検査器がそれを検証する。これは通常の型検査と同じ操作である。

## 提案

### 1. `{}` は証明空間：型がアサーション、検証が型検査

YaoXiang の `{}`
はコンパイル時証明空間である。内部のすべてがアサーションであり、コンパイラは各項目が True であることを保証する——自動証明されるか、プログラマが証明関数を提供するかのいずれかである。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  コンパイラが x が Float であること、y が Float であることを保証

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  コンパイラが data が Array(T) であることを保証
```

**ジェネリクスはコンパイル時述語の特殊ケースである。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          署名の引数          {} 内にはアサーションのみ
#          コンパイラがコンパイル時に呼び出す際 x > 0 を検証

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      署名の引数           コンパイラが type_of(T) == Type、type_of(data) == Array(T) を検証
```

同じパターン：`name: (params) -> Type = { アサーション }`。コンパイラは「型アサーション」と「値アサーション」を区別しない——両方とも証明パイプライン内の評価対象である。

**ループ不変条件を個別に書く必要はない。変数上の型注釈がそのまま Floyd-Hoare 不変条件である。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照——コンパイラに s の型が i に依存することを伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラが検証：s_new == sum(arr[0..i+1])
        i += 1       # i 変更 → s の依存再検証をトリガ：s が SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新しい値が型注釈を満たすか。証明パイプラインが帰納ステップの成立を検証すれば、全ての反復が自動的にカバーされる。`: decreases`
も `: Invariant` も帰納証明も不要——コンパイラは帰納を各代入の局所 VC に分解する。

### 2. 事前/事後条件：引数型と戻り型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures`
を廃止する。コンパイル時述語は引数または戻りの型注釈として機能する。

**引数側は関数呼び出しである。**
コンパイル時述語は Type を返す関数であり、引数側での使用方法はそれを呼び出すことである——`factorial(5)`
と同じである。戻り値側は新しい概念を導入する：戻り値仮引数である。

```yaoxiang
# 事前条件：引数型内で明示的にコンパイル時述語を呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在の仮引数名、Positive に引数として渡される
#                       コンパイラが呼び出し点で実引数値を抽出し、b に代入し、Positive(実引数) を検証
#                       例：divide(10, 2) → Positive(2) = { 2 > 0 } を検証 → True
#                       例：divide(10, 0) → Positive(0) = { 0 > 0 } を検証 → False → コンパイルエラー

# 事後条件：戻り値仮引数 + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は戻り値仮引数、値は return によって提供される
#                                            コンパイラが return 点で戻り値を代入し、事後条件を検証
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要なルール**：

- **引数側**：`b: Positive(b)` —— `b` は現在の仮引数名で、`Positive`
  に引数として渡される。関数呼び出し構文、暗黙のルールはゼロ。
- **戻り側**：`-> (result: IsMax(T, arr, result))` —— `result` は戻り値仮引数、値は `return`
  文によって提供される。`result`
  は型署名内にのみ存在し、述語によってのみ参照され、関数本体スコープには入らず、呼び出し側にも現れない。
- **戻り値仮引数はオプション**：事後条件がない場合は書かず、署名は通常の関数と完全に一致する（`-> Int`）。
- **統一性**：引数と戻り値仮引数は同じ概念——`仮引数名: 述語呼び出し(仮引数名)`——違いは値が呼び出し側から提供されるか
  `return` から提供されるかのみ。

### 3. パス条件伝播：ランタイム値のコンパイル時検証

コンパイル時述語が束縛位置で使用される際、引数はプログラマが明示的に渡す。ランタイム値が精化型引数に入るとき、コンパイラはパス条件収集と SMT 含意判定によって検証を完了する——プログラマが明示的に証明を渡す必要はない。

#### 3.1 明示的関数呼び出し

コンパイル時述語が束縛位置で使用される際、引数はプログラマが明示的に渡す——関数呼び出しそのもの、暗黙のルールはゼロ。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。それが束縛位置（引数宣言、変数宣言、戻り型）に現れるとき、プログラマは既に束縛された変数名を明示的に渡す：

```yaoxiang
b: Positive(b)
// b は現在の仮引数として既に宣言されている、Positive(b) は関数呼び出し
// 正格化後：b: { b > 0 }
```

コンパイラが暗黙的に引数を埋める必要はない——`b: Positive(b)` は `f(5)`
と同じく、関数呼び出しである。`b` は引数名として束縛され、その型注釈 `Positive(b)` は `b`
自身を参照する——これは依存型の標準パターンであり、暗黙の展開ルールではない。

**RFC-010 の `self` との統一**：RFC-010 は `self`
がキーワードではなく、単なる引数名の慣習であることを確立した（"`p`、`this`、`x`
と書いても効果は完全に同じ"）。`b: Positive(b)`
も同じメカニズムを共有する——引数名は型注釈内で参照可能。`self` は `self: Point` の位置に現れ、`b` は
`b: Positive(b)`
の位置に現れる。両者の型注釈は引数自身を参照する。違いは型注釈の複雑さだけで、メカニズムは完全に同じ——名前が束縛されれば、型はその名前に依存できる。

戻り型も同様に明示的関数呼び出しを使用する：

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は戻り値仮引数、Sorted(result) は関数呼び出し
//                        コンパイラが return 点で戻り値を result に代入し、Sorted(戻り値) を検証
```

ローカル変数宣言にも同様に適用される：

```yaoxiang
let x: Positive(x) = 5
// x が 5 として束縛される、Positive(5) → { 5 > 0 } → True → 通過

// let y: Positive(y) = 0
// y が 0 として束縛される、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 パス条件収集

ランタイム値が条件分岐に現れるとき、コンパイラは自動的にパス条件を収集し、現在のスコープの**仮定集合**を形成する。これらの仮定は、コンパイル時 Bool 評価の背景知識として検証に参加する。

```yaoxiang
if y > 0 {
    // コンパイラがこの分岐内で自動的に取得する仮定：{ y > 0 }
    let result = divide(x, y)
    // 検証条件：(y > 0) ⇒ (y > 0)
    // 証明パイプラインが含意成立を判定 → Proved
} else {
// この分岐の仮定：{ !(y > 0) }
// divide(x, y) を呼び出す場合、検証条件は !(y > 0) ⇒ y > 0
    // 証明パイプラインが含意不成立を判定 → Disproved
}
```

これはコンパイラがハードコードした特殊パターンではなく、コンパイル時証明パイプラインの自然な振る舞いである。型検査の各呼び出し点で、パイプラインに以下が送信される：

```
{背景仮定} ⇒ {検証対象}
```

証明パイプラインが含意性を判定する。Proved → 通過、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未証明命題。背景仮定は現在のプログラム点のパス条件に由来する。

#### 3.3 仮定スタック

コンパイラは制御流を解析する際、各基本ブロックに対して仮定集合を維持する：

- **if ガード**：`if y > 0` → true 分岐に `y > 0` をプッシュ、false 分岐に `!(y > 0)`
  をプッシュ（else が使用されている場合）
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **論理結合**：`if x > 0 and y < 10` → 分岐内に `x > 0` と `y < 10` をプッシュ
- **関数事前条件**：`divide(a, b)` を呼び出す際、`b` が `Positive`
  の証拠を持つ必要があるが、その証拠は現在の仮定に由来するか、実引数自身の精化型注釈に由来する（`b`
  が `Positive` として既に注釈されていれば、その型が `b > 0` を運ぶ）
- **代入**：`let z = y` のとき、`y` 上の既存の精化条件が `z` に伝播する

全ての仮定がコンパイル時証明パイプラインに入る。SMT 加速パスに入るとき、それらは SMT-LIB 背景アサーションに翻訳される。

#### 3.4 静的証拠なしの場合はコンパイルエラー

プログラマが直接以下のように書いた場合：

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム点に `y > 0` の仮定がなく、実引数 `y` 自身にも `Positive` 型注釈がない。検証条件は：

```
{} ⇒ { y > 0 }
```

パイプラインが `Disproved`（含意不成立）を返す → コンパイルエラー：

> `divide` 呼び出しにおいて引数 `b` が `Positive` を満たすことを証明できない。`y`
> は関数入力に由来し、証明済みの境界がない。if 分岐ガードを用いた呼び出しを検討してください：`if y > 0 { divide(x, y) }`。

YaoXiang は静的証拠を提供せずにランタイム値が直接精化型引数に入ることを許容しない。これは制限ではなく、硬直した安全性哲学の中核である。コンパイラが静的に証明できないコードは、コンパイルを通過できない。

#### 3.5 統一パイプラインとの関係

パス条件伝播は追加のメカニズムではない。それはコンパイル時証明パイプラインの制御流解析における直接の拡張である：

| 段階                 | 責務                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| パス条件収集         | コンパイラの制御流解析段階、各基本ブロックに仮定集合を注釈                                                                           |
| 検証条件生成         | 検証が必要な型制約に遭遇したとき、パス条件 + 実引数型情報をマージ                                                                    |
| 証明パイプライン評価 | コンパイラカーネル → SMT 加速 → Proved / Disproved / Unproven を得る                                                                 |
| 結果                 | `Proved` → 通過；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未証明命題（プログラマは証明関数を提供可能） |

新しい部品はない。特別なルールもない。パス条件は証明パイプラインの背景知識である——型等式、借用制約と同じパイプライン、同じ予算システムを共有する。

### 4. コンパイル時証明パイプライン

全てのコンパイル時検査は同じパイプラインを共有する。パイプラインの核心操作は**型検査**である——証明項の型が証明対象の命題に等しいかを検査する。すべてが型検査である。

```
コンパイル時に Bool 式の評価が必要（即ち：証明項を構築する必要がある）
        │
        ├── 型等式（T1 == T2）
        │   → コンパイラが直接判定（構造等価）
        │
        ├── トークン衝突条件（!conflicting(tokens)）
        │   → フロー敏感活性解析（Dup/Linear 属性追跡）
        │
        ├── 依存型簡約（n + m 簡約）
        │   → コンパイル時項書換システム（βδι-簡約）
        │
        ├── コンパイル時述語（x > 0, forall...）
        │   → コンパイラ自身 + SMT 加速モジュール
        │
        └── ホーア論理含意（P ⇒ Q）
            → コンパイラ + SMT 加速モジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル通過
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未証明命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を書く（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル通過
                  │
                  ▼
            検証失敗 → コンパイルエラー：「証明が成立しない」
```

#### 4.1 証明結果：三値代数

コンパイル時評価は三つの結果を返す——これは停止問題の必然的な帰結であり、証明論の自然な分類である：

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項が構築済み、型検査通過。コンパイル継続。
- **Disproved(M)** → 停止、反例 M が存在。コンパイルエラー + 反例 + ソースコード位置。
- **Unproven**
  → 与えられたリソース上限内で証明が構築されなかった。コンパイルエラー + 未証明命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言うのは命題が偽であることと同義ではない——単に現在の自動証明能力を超えているだけである。これは正直さであり、欠陥ではない。

予算の硬制限は停止問題の工学的解である。ノブは提供しない——提供するということは「あなたのプログラムが停止すると思うか」とユーザーに問うことになり、ユーザーは知らず、コンパイラも知らない。

#### 4.2 Unproven の後：プログラマが証明を書く

コンパイラが Unproven を返したとき、プログラマは**証明関数**を書くことができる——戻り型が証明対象の命題に等しい YaoXiang 関数である。型検査器がこの関数を検証する——`add(a, b): Int`
を検証するのとまったく同じメカニズムで。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼の根）
```

SMT ソルバーは独立した信頼境界ではなく、**型検査器の加速モジュール**である。SMT は証明発見を助けるが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返したとき、コンパイラはその結果を型検査器が検証可能な証明項に再構成する。再構成が失敗した場合（SMT の推論ステップがコンパイラカーネルの推論規則を超える場合）、Unproven にフォールバックする——プログラマは手動で証明関数を書くことができる。

```yaoxiang
# 命題：コンパイラが自動証明できない精化属性
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明：プログラマが関数を書き、戻り型が上の命題
# 型検査器がこの関数を検証する——add(a,b): Int を検証するのと完全に一致
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラがここで検証：関数本体の型 = FirstIsMin(T, arr)
    ...
}
```

AI も不要、Coq へのエクスポートも不要、新しい概念も不要。**コンパイル時に自動証明できない属性 → プログラマが YaoXiang コードで証明を書く → 型検査器が検証。**
プロセス全体は滑らかなグラデーションである——コンパイラが簡単な証明を代行し、難しいものをプログラマに残す。

#### 4.3 パイプライン内の階層的依存

上記の評価器は同じインターフェースを共有するが、評価順序が存在する。型等式は全ての後続解析の前提条件である；所有権/トークン検査は型情報に依存する；精化述語検証は前二層の結果に依存する。コンパイラは層ごとに評価し、底层で失敗した式は上層に進まない——型エラーがあるプログラム上で求解予算を浪費することを避ける。

```
評価順序（同一パイプライン、階層的スケジューリング）
├── 第 0 層：型等式（T1 == T2）
│   └── 構造ユニフィケーション → 失敗なら後続は無意味、直接 Disproved を返す
├── 第 1 層：所有権/トークン衝突
│   └── フロー敏感活性解析 → 失敗ならメモリ安全性が不成立、直接 Disproved を返す
└── 第 2 層：精化述語/ホーア含意
    └── コンパイラ自身 → SMT 加速 → Proved / Disproved / Unproven を得る
```

各層は依然として `Proved/Disproved/Unproven`
を返し、同じインターフェースと同じ予算システムを共有する。

### 5. 三層関数の統一

| 階層             | 実行タイミング | 入力  | 出力 | 例                                             |
| ---------------- | -------------- | ----- | ---- | ---------------------------------------------- |
| 値レベル関数     | ランタイム     | 値    | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時   | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時   | 値    | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

全て同じ `name: type = value`
構文を使用する。コンパイル時述語と型コンストラクタは同じコンパイル時証明パイプラインを辿る——`{}`
が証明空間である。

### 6. ループ：Floyd-Hoare 検証条件生成

ループは個別の `: Invariant(...)` や `: decreases(...)`
注釈を必要としない。変数上のコンパイル時述語型注釈が Floyd-Hoare スタイルのアサーションを定義する——コンパイラが型注釈から検証条件を生成し、証明パイプラインが各代入が型を保持するかを検査する。

核心メカニズム：各代入操作は Hoare 三項組 `{P} x := e {Q}` に対応し、検証条件は `P ⇒ Q[e/x]`
である。コンパイラはループ本体に対して一度検証条件を生成する——証明パイプラインが帰納ステップの成立を検証すれば、全ての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照；初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証：0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラがループ本体に対して一度 VC を生成。前提：s は SumUpTo(arr, i) を満たし、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]：
        #   検証義務：s_new が SumUpTo(arr, i) を満たす（現在の i は不変）
        #   s_new = s_old + arr[i] を代入：
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮説 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える：
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT：線形算術、ミリ秒級 → Proved
        #
        # i += 1：
        #   i 変更 → 依存グラフで s の型注釈が i を参照している → 再検証をトリガ
        #   新しい検証対象：s が SumUpTo(arr, i_new) を満たす
        #   即ち s == sum(arr[0..i_new])、上一步で保証済み → Proved
        s += arr[i]
        i += 1
    }
    return s  # このとき s: SumUpTo(arr, arr.len)、即ち s == sum(arr[0..arr.len])
}
```

ループ不変条件は変数上の型注釈そのものである——プログラマが型を書き、コンパイラが帰納ステップを検査する。コンパイラは不変条件を「発見」する必要も、帰納を「自動実行」する必要もない——帰納証明を各代入操作の局所検証条件に分解し、証明パイプラインに分割して委ねる。

#### 6.1 依存追跡：可変変数上の依存型

上記のメカニズムの前提は、コンパイラが `s` の型注釈 `SumUpTo(arr, i)` が `i`
を参照していることを知っていることである——`i` が変更されたとき、`s`
の型制約もそれに応じて変化する。これにはコンパイラが**変数間の型依存グラフ**を維持する必要がある。

**データ構造**：

```
TypeDepGraph: Map<VarName, Set<VarName>>
# キーは被依存変数、値は型注釈内でその変数を参照している変数の集合
# 例：{ i: {s}, j: {s, t}, ... }
```

**構築**：型検査器が `mut v: Pred(... x ...) = init` を処理するとき、`Pred(...)`
引数内の自由変数参照を解析する。引数が現在のスコープ内の他の可変変数 `x`
を参照している場合、依存グラフに `x → v` を記録する。

**トリガ**：被依存変数 `x` が代入されたとき、コンパイラは：

1. 依存グラフ内で `x` に依存する全ての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` について、検証条件を生成：`v の現在値が更新後の型 Pred(... x_new ...) を満たすか`
3. VC を証明パイプラインに送信

**代入順序依存性**：依存追跡は正しい代入順序を自然に強制する。`SumUpTo(arr, i)` を例に取る：

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証 → True

# 誤った順序——コンパイラが拒否
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証
              # s はまだ更新されていない、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー：変数 s が型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**組み合わせ依存**：一つの変数が複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は `x` と
`y` の両方に同時に依存する——いずれの変更も再検証をトリガする。

**証明パイプラインとの関係**：依存追跡は VC 生成のトリガであり、独立した検証メカニズムではない。それは「いつ VC を生成する必要があるか」に答え、証明パイプラインが「VC が成立するか」に答える。

### 7. 停止性検査

**適用範囲：コンパイル時評価。**
停止性検査はコンパイル時評価に関わるループと再帰（依存追跡によってトリガされるもの）にのみ適用される——コンパイラ自身が実行するコードは完全に証明可能でなければならない；ランタイムコードは停止証明を必要としない（§6.7 スコープ表）。範囲内のコンパイル時評価は全自動優先：コンパイラが証明できるループは通過し、自動戦略で証明できないものは直接コンパイルエラーを報告する——プログラマはコンパイラにループの停止性を自動分析させなければならない。**注釈構文**の抜け道はない（`decreases`
系の注釈を導入しない、未対応は常に構文位置であり、関数ではない）。

> **改訂（RFC-027a、2026-09-14）**：① 適用範囲をコンパイル時評価に明確化——原文は「ループ」の位置を限定しておらず、§6.7 スコープ表と曖昧性があり、実装層の無条件全量検査はこれにより絞り込まれる。② 自動戦略で証明できない停止義務について、プログラマは測度関数と停止証明関数（`Terminates`）をフォールバックとして提供可能——いずれも通常の YaoXiang 関数であり、新しい構文はゼロ、型検査器が検証する。全自動優先原則は変わらず、フォールバックは Unproven の後にのみ発生する。詳細は
> [RFC-027a: 停止性検査の証明関数フォールバック](../draft/027a-termination-proof-fallback.md)
> を参照。

#### 6.1 設計原則

コンパイラは二箇所から停止証明に必要な情報を自動抽出する：

1. **変数型注釈**：精化型内の境界制約（例：`UpTo(n)` は上界 `n` と下界 `0` を提供）
2. **ループ本体操作**：各反復で変数に適用される操作

コンパイラは優先順位に従って四つの測度合成戦略を試行し、一つを見つければ停止する。

#### 6.2 戦略 1：線形ランク関数の自動合成

変数に線形境界注釈がある場合、コンパイラは候補線形測度を列挙し SMT で検証する。

```
入力：
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（境界を持つ変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム：
  1. 型注釈から各変数の境界を抽出：[low_i, high_i]
  2. 候補測度を列挙：v_i, u_i - v_i, v_i - v_j 等の線形結合
  3. 各候補測度 m について：
     - SMT が m ≥ 0 を検証（型境界から導出）
     - ループ本体の各実行パスについて、SMT が m' < m を検証（厳密減少）
  4. 条件を満たす線形結合が見つかる → 停止が証明される
```

カバレッジ範囲：任意の変数が線形式（`v = a·v + b`）に代入され、境界型注釈を持つループ。`i += const`、`i -= const`、および二分探索型の区間収縮を含む：

```yaoxiang
# 二分探索：low = mid + 1 または high = mid
# 測度 high - low は二つのパスで厳密に減少
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2：述語違反カウント——目標型からの自動測度抽出 <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在の状態：実験的戦略、Phase 3 実装時に実際の実現可能性に応じて含有を決定。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効だが、非隣接操作（クイックソート partition、ヒープソート sift-down）は自動証明できない。カバレッジ境界は下表の通り。Phase
> 3 検証で実現不可能と判断された場合、この戦略は削除されるか将来の作業に格下げされる。

核心的な洞察：**ユーザーが書いた仕様がコンパイラの推論素材である。**
コンパイラは「ソートとは何か」を内蔵する必要はない——`Sorted`
の定義を読み、定義から自動的に測度を抽出する。

```
入力：
  目標型：Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体操作：隣接要素の交換

アルゴリズム：
  1. 述語定義を解析：forall i in range: cond(i, arr)
  2. 自動的に測度を生成：violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作の測度への影響を解析：
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の三対のみに影響
     - arr[j] > arr[j+1]（述語違反）の場合、交換後にこの対は述語を満たす
     - violation_count は少なくとも 1 減少
  4. 上界：n·(n-1)/2（最大隣接逆序数）、下界：0
  → 停止が証明される
```

**現在のカバレッジ範囲**：

| アルゴリズム   | 操作パターン       | 戦略 2 で証明可能？ | 理由                                        |
| -------------- | ------------------ | :-----------------: | ------------------------------------------- |
| バブルソート   | 隣接交換           |         ✅          | violation_count は各交換で厳密減少          |
| 挿入ソート     | 隣接移動           |         ✅          | 各シフトで違反対を一つ解消                  |
| 選択ソート     | 非隣接交換         |         ❌          | 単一交換で violation_count が増加する可能性 |
| クイックソート | パーティション分割 |         ❌          | 非隣接交換、単調減少を保証しない            |
| ヒープソート   | sift-down          |         ❌          | ツリー操作、violation_count は非単調        |

**補完戦略**：クイックソートの場合、`low < high`
の区間収縮は戦略 1（線形ランク関数）でカバー可能——外層のパーティション再帰では毎回区間が半分になる。戦略 1 と戦略 2 は補完的にカバーを提供し、実際のアルゴリズムの大多数の停止性はどちらか一方で証明可能である。ただし戦略 2 の一般化（非隣接操作、ツリー操作）は依然として未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3：有界増減パターン

`v += const`（正の定数）、変数が上界型注釈を持つ → 測度 `upper_bound - v` は毎回 `const`
ずつ減少し、下界は 0。これは戦略 1 の縮退ケースであり、コンパイラが最初に高速処理する。

#### 6.5 戦略 4：乗算スケール測度テンプレート

`v *= const`（const > 1）、変数が上下界型注釈を持つ。コンパイラは対数目度テンプレート
`ceil(log_const(upper/v))` を内蔵し、毎回 const 倍すると測度が 1 減少する。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラが自動推論：測度 ceil(log₂(n/i))、毎回 2 倍すると測度が 1 減少
    i *= 2
}
```

#### 6.6 停止性と正当性の分離

停止性証明と正当性証明は独立している：

- **停止性**：上記四つの戦略がループが有限ステップで終了することを自動証明
- **正当性**：ループ本体が目標型に向かって進行するかは、コンパイル時証明パイプラインが検証条件を通じて検査

両方通過 → コンパイル通過。停止性は証明されたが正当性が失敗 → コンパイルエラー + 反例。正当性は証明されたが停止性を証明できない → コンパイルエラー、分析不能な変数または操作を示す。両方失敗 → コンパイルエラーが二つの失敗理由を別々に報告する。

#### 6.7 再帰関数の停止検査

コンパイル時評価が必要な再帰関数について、コンパイラは引数の減少を検査する：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # コンパイラの解析：n-1 < n → 減少 → 停止
}

# コンパイル時使用——コンパイラが factorial のコンパイル時停止を保証
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120、コンパイル時に完了
```

| シナリオ                                    | 振る舞い         |
| ------------------------------------------- | ---------------- |
| コンパイラが再帰減少を解析可能（例：`n-1`） | コンパイル時評価 |
| 減少しない/減少を判定不能                   | コンパイルエラー |
| ランタイム呼び出し（型位置ではない）        | 停止検査不要     |

#### 6.8 硬境界

`i = f(i)` であり、`f`
が不可逆、不閉、いずれの単調性も保持しない——数学的に自動停止証明は不可能。コンパイルエラー：

> このループの自動停止証明ができない。ループ変数が解析不能な関数 `f`
> に依存する。コンパイラが解析可能な反復パターンを使用するか、測度関数と停止証明関数を提供してください（RFC-027a を参照）。

これはコンパイラの失敗ではない。静的に安全性を証明できないコードは、コンパイルを通過できない。

### 8. SMT ソルバー：型検査器の加速モジュール

SMT ソルバーは従来の言語では外部ツールである（F\* が Z3 を呼び出す、Dafny が Z3 を呼び出す、等）。YaoXiang では、**型検査器の加速モジュール**である——コンパイラカーネル自身が直接判定できない場合のみ呼び出される。SMT は証明発見を助けるが、証明を検証するのは型検査器である。

**信頼モデル**：型検査器が唯一の信頼の根である。SMT ソルバーは加速モジュールである——証明発見を助けるが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny 路線と一致——Z3 が誤る確率はコンパイラ自身のバグ率より低く、これは工学的実用主義の選択である）。真の不信頼性制御は SMT 翻訳層にある——翻訳にバグがあれば、コンパイラは他のテストで露呈する。

**インターフェース**：コンパイラ内部は SMT-LIB
2.6 標準形式に翻訳し、特定のソルバー API に束縛しない。SMT-LIB は ISO 標準であり、Z3、CVC5、MathSAT、Yices 全てがネイティブサポートする。

**デフォルトバックエンド**：Z3（MIT ライセンス、最も広範な文書とコミュニティ検証）。CVC5 は SMT-LIB 互換の代替——ユーザーはコンパイル時にコンパイラフラグで切り替え可能。

「汎用ソルバー抽象層」は作らない——SMT-LIB が抽象層である。未来に CVC5 が特定理論でブレークスルーを達成した場合、切り替えにはバイナリを差し替えるだけでよく、コンパイラコードの変更は不要。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造等価、単純算術、
        │   定数畳み込み後の自明な式）
        │   → 直接 Proved / Disproved を返す
        │
        └── コンパイラカーネルが直接判定不能（量化子、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB 形式に翻訳
            → Z3/CVC5 に送信（予算制限付き）
            → 戻り値：unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**求解予算——硬制限、スタック深度のように**：

| 予算次元                 | デフォルト値 | 説明                                                                                                                                 |
| ------------------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 求解ステップ数           | 10,000       | Z3 は線形算術に対して通常百ステップ以内。10,000 ステップで実際の述語の 99% をカバー。                                                |
| 時間                     | 100ms        | 単一述語が 100ms を超える = ユーザーが型注釈ではなくコンパイル時プログラムを書いている。100ms × 50 述語 = 5 秒のコンパイル時間上限。 |
| 量化子インスタンス化深度 | 3            | 三層のネスト量化子が実際のパターンをカバー。三層超は大抵論理パズル。                                                                 |

予算超過時は Unproven を返し、述語位置 + 消費量でコンパイルエラー。降格なし、ランタイムチェックなし、サイレントパスなし。

**なぜこれが実現可能か**：工学的に実際の述語の 95% は線形算術である——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——全て決定可能フラグメント内であり、SMT ソルバーは这类の問題にミリ秒で応答する。予算を超える複雑な述語の稀少なケースに遭遇した場合、プログラマは証明関数を書けばよい。

依存型は SMT 呼び出し前に一層の事前簡約を行う：`factorial(5)` は直接コンパイル時評価で `120`
となり、`append([1,2], [3])` は直接評価で `[1,2,3]`
となる。これらの確定的な値計算は SMT 予算を消費しない。

プログラマは SMT の存在を知る必要はない。メンタルモデルは：**コンパイラが証明できれば通過、できなければエラー——コンパイラができないなら、証明関数を書いて見せる。**

### 9. コンパイル時述語の組み合わせ

コンパイル時述語は Type を返す関数であり、組み合わせは関数組み合わせで自然に実現される：

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算の安全性

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラが Positive(2) = { 2 > 0 } を検証 → True
# result = divide(10, 0)  # ❌ コンパイラが Positive(0) = { 0 > 0 } を検証 → False
```

#### 9.2 配列アクセスの安全性

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラが InBounds(1, arr) = { 0 <= 1 and 1 < 3 } を検証 → True
# y = get(arr, 5)  # ❌ コンパイラが InBounds(5, arr) = { 0 <= 5 and 5 < 3 } を検証 → False
```

#### 9.3 ソートの正当性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ：コンパイラの VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 分派パイプライン：コンパイル時とランタイムの統一分派

`assert` と `Assert` は同じ精化型プリミティブの二面である。分派パイプライン `dispatch`
は**述語の自由変数がコンパイル時に到達可能か**によって自動的にコンパイル時証明とランタイム検査のいずれかに分派する：

| 判定基準                                                               | モード          | 振る舞い                                                                              |
| ---------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------- |
| 全ての自由変数がコンパイル時既知（ジェネリクス引数、コンパイル時定数） | **CompileTime** | 証明パイプラインへ：Proved → 消去、Disproved → コンパイルエラー、Unknown → 証明を要求 |
| 自由変数がランタイム由来（関数引数、外部入力、mut 変数）               | **Runtime**     | ランタイム check を挿入し、フロー敏感仮定集合 Γ に精化事実を注入                      |

**重要**：「判定不能」≠「反証」。CompileTime モードで Unknown は証明を要求する（暗黙の降格はしない）、Runtime モードでは命題はコンパイル時に真偽を持たない——prover がいくら強くても「ユーザーが負数を入力した可能性がある」に対する恒真証明は書けないため、ランタイム check が唯一の sound な選択である。これは prover の能力不足ではなく、理論的必然である。

### 12. フロー敏感仮定集合 Γ：最強後置条件伝播

コンパイラはフロー敏感（flow-sensitive）仮定集合 Γ を維持し、各制御点において既知の成立する命題を追跡する。

**SP（最強後置条件）伝播**：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**：`mut` 変数が再代入された後、その変数に関する全ての仮定が Γ から除去される：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

これは soundness の硬直した要件である——変数の値が変われば、旧仮定は無効になる。

**分岐合流**：IF/ELSE または match 分岐が合流するとき、Γ は各分岐の仮定の交差を取る。全てのパスで成立する命題のみが分岐外へ持ち出される。

### 13. 消去モデルの明確化：witness 消去 ≠ check 消去

RFC-027 の「精化型はランタイムに**完全消去される**」という論断が指すのは **proof
witness（証明トークン）**である——コンパイル時に検証済みの証明項は実行時コードを生成しない。ただし Runtime モードで dispatch が挿入する
**ランタイム check**
は保持される——これは値レベルで実行される Bool 検査であり、型レベルの witness ではない。

まとめ：witness は消去、check は保持。二つの事柄は衝突せず、RFC-027 の原論断は変わらない。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以後 (本 RFC)                                                   |
| ------------------------------------- | --------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語を引数型として使用 `(b: Positive(b))`           |
| `//! ensures: ExistsMax(result, arr)` | 戻り型に戻り値仮引数を使用 `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変条件            |
| `//! decreases: n`                    | コンパイラが測度関数を全自動導出                                |
| 仕様は注釈                            | 仕様は型システム                                                |

### 構文

**コンパイル時述語に新しいキーワードはない。** `{}`
は証明空間であり、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数である——`name: (params) -> Type = { アサーション }`。使用時は関数呼び出しである——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証するアサーション
# 既存の関数/型構文を使用、新たな BNF 規則は不要
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**述語適用の実引数はコンパイル時定数形式でなければならない**——リテラル、変数（名前で束縛）、単一引数型適用（再帰的抽出）。実引数形式が定数式に変換できない場合は
**E1092**、実引数の個数が述語のパラメータと一致しない場合は **E1093**
を報告する——精化制約は**決して静かに破棄されない**（以前、変換不能な実引数が制約を無音で消滅させ、制約違反の束縛が無音で通過していた）。

**新しい構文概念：戻り値仮引数**——`-> (name: Type)` 内の `name` は戻り値仮引数である。

戻り値仮引数は YaoXiang が既存の関数構文に導入する**唯一の構文概念**である。その意味は：

- `name` の値は `return` 文によって提供される
- `name`
  は型署名内にのみ存在し、事後条件述語によって参照される（例：`-> (result: IsMax(T, arr, result))`）
- `name` は関数本体スコープに入らず、呼び出し側にも現れない
- 戻り値仮引数は**オプション**——事後条件がない場合、署名は通常の関数と完全に一致し（`-> Int`）、追加の負担を導入しない

導入の理由：事後条件は「関数が返そうとしている値」を参照する必要がある。戻り値仮引数がない場合、コンパイラは述語が戻り値を参照できるように特別なルール（暗黙変数
`$result` や `__retval__`
など）を使用しなければならない。戻り値仮引数はこの参照を明示化する——単なる仮引数であり、値の提供元が呼び出し側ではなく
`return` であるというだけである。

**証明関数**は新しい概念ではない——戻り型がアサート対象の命題である YaoXiang 関数である。コンパイラが Unproven を返したとき、プログラマは証明関数を提供し、型検査器は任意の関数の戻り型を検証するのと完全に同じ方法でそれを検証する。新しい構文、新しいキーワード、新しいルールは不要。

### 型システムへの影響

- **型宇宙**：コンパイル時述語は Type₂ 層に位置する——値を受け取り Type を返す関数、型コンストラクタと同じ階層
- **ジェネリクスとの相互作用**：コンパイル時述語はジェネリクス引数を取れる、 例：`NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **所有権との相互作用**：コンパイル時述語内の式は所有権ルールを遵守し、読み取りのみ可能で書き込みはできない
- **型推論**：コンパイル時述語のパラメータは HM 型推論に参加する

### ランタイム表現

コンパイル時述語はランタイムに**dispatch 分派結果に従って処理される**：

- **CompileTime モード**（全ての自由変数がコンパイル時既知）：証明通過後、witness（証明トークン）は完全に消去される。`Positive: (x: Int) -> Type = { x > 0 }`——引数
  `b: Positive(5)` のランタイム表現は `Int` そのものである。精化条件 `{ 5 > 0 }`
  は通過済み、消去される。
- **Runtime モード**（ランタイム自由変数が存在）：ランタイム check を保持する——値レベルで Bool 検査を実行し、フロー敏感仮定集合 Γ に注入する。詳細は §11
  dispatch 分派パイプラインと §13 消去モデル明確化を参照。

コンパイル時述語を型位置に置く（例：`f(x: Positive(x))`）ことはラッパ型を生成せず、余分なメモリを割り当てない。ただし
`x` がランタイム入力に由来する場合、**ランタイム Bool 検査が挿入される**。

**`ref`
との相互作用制約**：コンパイル時述語は不変借用または所有権が既に移動済みの値のみを参照できる。可変借用を参照するコンパイル時述語は、コンパイラがコンパイル時に検証結果がランタイムでも成立することを保証できないため、そのような用法は直接コンパイルエラーを報告する。

### コンパイラ変更

1. **パーサー**：コンパイル時述語は標準的な関数構文を使用し、追加の解析ルールは不要
2. **コンパイル時証明パイプライン**：Proved/Disproved/Unproven 戻りインターフェースを統一、自動戦略選択
3. **SMT 加速モジュール**：SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**：推論規則の実装——構造等価、βδι-簡約、全称量化子の導入/除去。これが唯一の信頼の根であり、SMT とプログラマの証明はこれを通じて検証される
5. **検証条件生成**：WP/SP 計算 + ループ不変条件証明義務
6. **エラー報告**：反例フォーマット + 未証明命題レポート + ソースコード位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用しないコードは完全に変更なし
- ✅ コンパイル時述語は CompileTime モードでランタイムオーバーヘッドゼロ、Runtime モードでは必要な Bool 検査のみ保持
- ⚠️ RFC-022 の `//!` 構文はサポートされない——ただし 022 は一度も実装されておらず、移行負担はない

## トレードオフ

### 利点

- **Curry-Howard 同型の完全な実現**：型が命題、プログラムが証明、`name: Proposition = Proof`
- **統一性**：コンパイル時述語と通常の関数は完全に同じ構文を使用し、概念分裂なし
- **SMT 透過性**：プログラマは SMT の存在を知る必要がなく、メンタルモデルは型検査と一致
- **漸進的採用**：一つのコンパイル時述語から開始し、徐々にカバレッジを拡大可能
- **最小ランタイムオーバーヘッド**：CompileTime モードはオーバーヘッドゼロ、Runtime モードは必要な Bool 検査のみ保持

### 欠点

- **コンパイル時間**：SMT 求解がコンパイル時間を増加させるが、予算硬制限により上限は制御可能
- **自動証明の境界**：一階線形算術を超える複雑な述語はプログラマの証明関数を必要とするかもしれない。これは言語の欠陥ではなく、停止問題の必然的な帰結である。コンパイラは Unproven を偽って True/False と報告するのではなく、正直に報告する
- **学習曲線**：効果的なコンパイル時述語と証明関数の記述には Curry-Howard 同型の基本的直感の理解が必要
- **実装複雑性**：コンパイル時証明パイプラインの統一には慎重な設計が必要

### リスク軽減

- SMT 求解予算硬制限（ステップ数 10,000 / 時間 100ms
  / インスタンス化深度 3）、予算超過時は Unproven を返す
- 依存型事前簡約：確定的な値計算を先に処理し、SMT は非確定部分のみを処理
- Unproven は袋小路ではない：プログラマは証明関数を書くことができ、型検査器が検証する——任意の関数の戻り型を検証するのと一致
- 増分検証：変更されたモジュールのみを検証
- 明確なエラーメッセージ + 反例表示 + 予算消費レポート + 未証明命題 + 提案（コンパイラが提供可能な場合）

## 代替案

| 代替案                                       | 選択しない理由                                                                                                              |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| RFC-022：`//!` 注釈式仕様                    | 仕様と型が分裂し、Curry-Howard 同型に違反                                                                                   |
| 独立仕様ファイル（例：CVL）                  | 仕様とコードが分離し、保守コストが増加                                                                                      |
| ランタイムアサーションのみ                   | 静的正当性保証が不可能                                                                                                      |
| 外部証明アシスタント（例：Coq）              | コンパイラから切断され、独立した証明言語と信頼境界が必要。YaoXiang の選択：証明は YaoXiang コード、型検査器が唯一の信頼の根 |
| **本方案：コンパイル時述語を一級市民として** | ✅                                                                                                                          |

      2.6 標準形式への翻訳を目標とする——SMT-LIB が抽象層であり、カスタム汎用ソルバーインターフェースは作らない。
- [x] **求解予算の具体値**：ステップ数 10,000 / 時間 100ms
      / 量化子インスタンス化深度 3。コンパイラ内部で固定、ノブは提供しない。実際の使用で本当に不十分であることが証明された場合（"ユーザーが書き間違えた"ではなく）、調整する。
- [x] **量化子サポート範囲**：言語レベルでは量化子の階数を制限しない。コンパイル時述語は Type 引数を受け入れる——Type は関数型を含む——したがって高階量化子は型システムの自然な帰結であり、特別な構文は不要。SMT ソルバーは一階量化子（forall/exists、交差ネストサポート、予算深度 3 で制限）を自動判定可能。高階量化子：SMT は Unproven を返し、コンパイラは「この述語は自動証明範囲外、証明関数を提供してください」とヒントする。プログラマは戻り型がその命題に等しい YaoXiang 関数を書く——型検査器がその関数を検証する。外部エクスポート不要、AI 不要、対話的証明モード不要。すべてが YaoXiang コード、すべてが型検査器で検証される。
- [x] **反例フォーマット**：ソースコード変数名を直接 SMT 変数名として使用（モジュール接頭辞を追加して衝突回避）。Z3 モデルが返されるとき、変数名で逆引き。出力形式：変数名 = 具体値 + ソースコード位置 + 述語定義位置。複雑なマッピング層は作らない。
- [x] ~~**`ref` スマートポインタとのコンパイル時述語の相互作用？**~~
      → 決定済み：コンパイル時述語は不変借用または所有権が既に移動済みの値のみを許可する。可変借用の値はコンパイル時述語に出現できない。
- [x] **`forall` 述語違反カウント測度の非隣接操作への拡張？**
      → 拡張しない。現在のカバレッジ範囲（隣接交換、隣接移動）は戦略 1（線形ランク関数）で補完的にカバーされる——クイックソートの外層区間収縮は戦略 1 が担当し、ヒープソートは戦略 1（配列インデックスパターン）が担当する。どの戦略でも停止を証明できないループは、コンパイラが直接エラーを報告する——これは硬直した安全性哲学であり、欠陥ではない。将来、実際のシナリオ（学術的構成ではない）のアルゴリズムが四つの戦略でもカバーできない場合、再議論する。→
      **再議論がトリガされた（2026-09-14、#318）**：非構造的再帰（gcd 系の非直接的減少、相互再帰、マージソート分割）は本条項が予期した実際のシナリオである——現在のパイプラインは自動停止証明ができず、可読性を損なわない形で解析可能な反復パターンに書き換えることもできない。結論：全自動優先は不変；Unproven の後に証明関数フォールバックを追加——測度と停止証明はどちらも通常の YaoXiang 関数であり、新しい構文はゼロ、型検査器が検証する。詳細は
      [RFC-027a: 停止性検査の証明関数フォールバック](../draft/027a-termination-proof-fallback.md)
      に着地。
- [x] **線形ランク関数列挙の組み合わせ爆発**：候補列挙上限は 3 個の有界変数。≤3 の場合、全ての線形結合を列挙し SMT で一つずつ検証。>3 の場合、単一変数測度（`v_i`、`u_i - v_i`）のみを試行し、失敗時は直接コンパイルエラーを報告する——「ループに 3 を超える有界変数があり、コンパイラが多変数測度を自動合成できない」とプログラマに示す。これは工学的妥協ではなく、プログラマにより単純なループを書くことを強制するものである。
