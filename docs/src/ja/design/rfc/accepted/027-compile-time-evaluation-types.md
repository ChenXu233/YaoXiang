# RFC-027：コンパイル時述語と統合静的検証

> **参考**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統合型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリックシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024：spawnブロックに基づく並行モデル](../accepted/024-concurrency-model.md)
>
> **取代**：[RFC-022: ホア論理静的検証サポート（仕様コメントと仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止

## 概要

本稿では、YaoXiang に**コンパイル時述語**を一級市民として導入し、すべてのコンパイル時静的検証を一本の**証明パイプライン**に統一することを提案する。コンパイル時述語は外部に付加された仕様コメントではない——それは関数である。Type を返す関数であり、型位置で使用でき、コンパイル時にコンパイラが呼び出して戻り値を検査する。型は命題であり、コンパイル時評価は証明である。

**核心的主張**：型検査におけるコンパイル時の唯一の仕事は、証明項の構築と検証である。型等式、トークン衝突、依存型簡約、コンパイル時述語評価、ホア論理含意——这些都是编译期证明管道中的不同类型检查，共享同一条管道。SMT 求解器は型検査器の加速モジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返した場合、プログラマは YaoXiang 関数を証明として書く——型検査器は任意の関数の戻り値型を検証するのと同じ方法でそれを検証する。すべてが YaoXiang コードであり、すべてが型検査器によって検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 では、仕様を `//!` コメント形式で設計していた：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← これは型から独立したコメント
    //! ensures: ExistsMax(result, arr[0..n])   ← これは型から独立したコメント
}
```

これは Curry-Howard 同型の根本的な誤りを犯している：**仕様と型を二層に分裂させる**。コメントは型ではない。コメントは型検査に参加しない。コメントは「外部ツール」のメンタルモデルである。

白書では明確に述べられている：

> "`//!` コメントはない。独立した仕様言語はない。すべては型システム内で完結する。"

### 現状の問題

- RFC-022 の `//!` コメントは型システムから独立した外部構文
- 仕様型と普通型是两套体系，造成概念冗余
- Debug Build 検証 / Release Build 忽略の分裂パターンが統一性を破壊
- SMT 求解器は伝統的に外部ツールとして定位——YaoXiangでは型検査器の加速モジュールとして内置
- 型検査、借用語検証、コンパイル時述語検査、マクロ展開が各自異なる経路を辿る

### 正しいメンタルモデル

型検査は一つの関数として抽象化できる：

```
verify : Program → Proved | Disproved(Model) | Unproven
```

すべてのコンパイル時検査——简单类型匹配、借用語衝突検出、コンパイル時述語検証——都是这个函数的子任务。它们共享同一条证明管道，区别仅在于证明项复杂度和构造策略。

When the compiler returns Unproven, the programmer provides a proof function—the return type of that function equals the proposition to be proved. The type checker verifies it. This is the same operation as regular type checking.

## 提案

### 1. `{}` は証明空間である：型は表明であり、検証は型検査である

YaoXiang の `{}`
はコンパイル時証明空間である。里面的的一切都是断言，编译器保证每一项为 True——要么自动证明，要么由程序员提供证明函数。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  编译器保证 x 是 Float，y 是 Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  编译器保证 data 是 Array(T)
```

**generics はコンパイル時述語の特殊ケースである。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          参数在签名处          {} 内只有断言
#          编译器在编译期调用时验证 x > 0

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      参数在签名处           编译器验证 type_of(T) == Type，type_of(data) == Array(T)
```

同一个模式：`name: (params) -> Type = { 断言 }`。编译器不区分"类型断言"和"值断言"——都是证明管道中的求值目标。

**循环不变式不需要单独写。変数上の型注釈が Floyd-Hoare 不変式である。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈が i を参照——コンパイラに s の型が i に依存することを伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラ検証：s_new == sum(arr[0..i+1])
        i += 1       # i 変更→s の依存再検証トリガー：s は SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度だけ検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新たな値が型注釈を満たすか。証明パイプラインが帰納段成立后を検証すれば、すべての反復が自動的にカバーされる。`: decreases` 不要、`: Invariant` 不要、帰納証明不要——コンパイラが帰納を各代入の局所 VC に分解する。

### 2. 前置/後置条件：パラメータ型と戻り値型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures` を捨てる。コンパイル時述語はパラメータまたは戻り値の型注釈として使用する。

**パラメータ側は関数呼び出しである。** コンパイル時述語は Type を返す関数であり、パラメータ側での使用方式是呼び出す——`factorial(5)` 一样。戻り値側に新しい概念が導入される：戻り値仮引数。

```yaoxiang
# 前置条件：パラメータ型中でコンパイル時述語を明示的に呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在の仮引数名で、Positive の引数に渡される
#                       コンパイラは呼び出し点で実引数値を抽出し、b に代入して Positive(実引数) を検証
#                       例：divide(10, 2) → Positive(2) = { 2 > 0 } → True を検証
#                       例：divide(10, 0) → Positive(0) = { 0 > 0 } → False → コンパイルエラー

# 後置条件：戻り値仮引数 + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は戻り値仮引数で、値は return で提供される
#                                            コンパイラは return 点で戻り値を代入して後置条件を検証
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要な規則**：

- **パラメータ側**：`b: Positive(b)` —— `b` は現在の仮引数名で、`Positive` の引数に渡される。関数呼び出し構文、ゼロ暗黙。
- **戻り側**：`-> (result: IsMax(T, arr, result))` —— `result` は戻り値仮引数で、値は `return` 文で提供される。`result` は型シグネチャ内にのみ存在し、後置条件述語から参照され、関数本体スコープには入らず、呼び出し元にも現れない。
- **戻り値仮引数はオプション**：後置条件がない場合は書かず、シグネチャは普通関数と完全に一致（`-> Int`）。
- **統一性**：パラメータと戻り値仮引数は同じ概念——`仮引数名: 述語呼び出し(仮引数名)`、区别仅在于值由呼び出し元が提供するか `return` が提供するかなし。

### 3. パス条件伝播：ランタイム値のコンパイル時検証

コンパイル時述語が束縛位置で使用される場合、パラメータはプログラマが明示的に渡す。実行時値が精製型パラメータに入る時、コンパイラはパス条件収集と SMT 含意判定を通じて検証を完了する—— programmer does not need to explicitly pass proof.

#### 3.1 明示的関数呼び出し

コンパイル時述語が束縛位置で使用される時、パラメータはプログラマが明示的に渡す——就是関数呼び出し、ゼロ暗黙。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。束縛位置（パラメータ宣言、変数宣言、戻り値型）に出現する時、プログラマは既に束縛された変数名を明示的に渡す：

```yaoxiang
b: Positive(b)
// b は現在の仮引数として既に宣言済み、Positive(b) は関数呼び出し
// 正規化後：b: { b > 0 }
```

コンパイラが暗黙的にパラメータを埋める必要はない——`b: Positive(b)` と `f(5)` は同じ、関数呼び出しである。`b`
をパラメータ名として束縛し、その型注釈 `Positive(b)` が `b`
自身を参照——这是依赖类型的标准模式，不是隐式展开规则。

**RFC-010 `self` との統一**：RFC-010 は `self` がキーワードではなく、ただのパラメータ名の慣例であることを確立した（「`p`、`this`、`x` と書いても効果は完全に同じ」）。`b: Positive(b)`
は同一个机制を共有する——パラメータ名が型注釈で参照可能。`self` が `self: Point` の位置に出現し、`b` が `b: Positive(b)`
の位置に出現，两者都在型注釈中引用参数自身。区别仅在于型注釈の复杂度、机制完全相同——名前が束縛された後、型は、その名前依存できる。

返回类型同样使用显式関数呼び出し：

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は戻り値仮引数、Sorted(result) は関数呼び出し
//                        コンパイラは return 点で戻り値を result に代入して Sorted(戻り値) を検証
```

同样适用于局部变量声明：

```yaoxiang
let x: Positive(x) = 5
// x を 5 として束縛、Positive(5) → { 5 > 0 } → True → 通過

// let y: Positive(y) = 0
// y を 0 として束縛、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 パス条件収集

実行時値が条件分支中出现时，编译器自动收集パス条件，形成当前作用域の**仮定集合**。这些假设作为编译期 Bool 求值的背景知识参与验证。

```yaoxiang
if y > 0 {
    // コンパイラは[this branch]で自動的に仮定を得る：{ y > 0 }
    let result = divide(x, y)
    // 検証条件：(y > 0) ⇒ (y > 0)
    // 証明パイプラインは含意成立と判断 → Proved
} else {
// このbranchの仮定：{ !(y > 0) }
// divide(x, y) を呼び出すなら、検証条件は !(y > 0) ⇒ y > 0
    // 証明パイプラインは含意不成立と判断 → Disproved
}
```

这不是编译器写死特殊模式——这是编译期证明管道的自然行为。毎回型検査呼び出し点がパイプラインに送信：

```
{背景仮定} ⇒ {検証目標}
```

証明パイプラインは含意性を判断する。Proved → 通過、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未解決命題。背景仮定は現在のプログラム点のパス条件から得られる。

#### 3.3 仮定スタック

コンパイラは制御フロー分析時、各基本ブロックに対して仮定集合を管理する：

- **if-guard**：`if y > 0` → true 分岐に `y > 0` をプッシュ、false 分岐に `!(y > 0)` をプッシュ（else を使用した場合）
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **論理結合**：`if x > 0 and y < 10` → 分岐内に `x > 0` と `y < 10` をプッシュ
- **関数前置条件**：`divide(a, b)` 呼び出し時、`b` が `Positive`
  を満たす証拠は現在の仮定から得られるか、実引数自身の精製型注釈から得られる（`b` が既に `Positive` で注釈付けられていればその型は `b > 0` を運ぶ）
- **代入**：`let z = y` の時、`y` 上の既存の精製条件が `z` に伝わる

すべての仮定がコンパイル時証明パイプラインに入る。SMT 高速パスに 入る時、SMT-LIB 背景表明に翻訳する。

#### 3.4 静的証拠 없ければコンパイルエラー

Progurammer が直接書く場合：

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム点に `y > 0` の仮定がなく、実引数 `y` 自身も `Positive` 型注釈がない。検証条件：

```
{} ⇒ { y > 0 }
```

パイプラインは `Disproved`（含意不成り立ち）を返す → コンパイルエラー：

> パラメータ `b` が `divide` 呼び出しで `Positive` を満たすことを証明できません。 `y`
> は関数入力而来、証明された境界がありません。if branch guard での呼び出しを検討：`if y > 0 { divide(x, y) }`。

YaoXiang は実行時値が静的証拠なしに精製型パラメータに打入ることを許可しない。これは制限ではない——这是硬安全哲学的核心。凡编译器无法静态 prove 的代码，不得通过编译。

#### 3.5 統一パイプラインとの関係

パス条件伝播は追加の mechanism ではない。它はコンパイル時証明パイプラインが制御フロー分析上に自然に拡張されたもの：

| 段階         | 責務                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| パス条件収集 | コンパイラの制御フロー分析段階で、各基本ブロックに仮定集合を注釈付け                                                             |
| 検証条件生成 | 型制約を検証する必要がある時に、パス条件 + 実引数型情報をマージ                                                      |
| 証明パイプライン評価 | コンパイラカーネル → SMT 高速化 → Proved / Disproved / Unproven を得出                                               |
| 結果         | `Proved` → 通過；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未解決命題（プログラマは証明関数を提供可能） |

新部品なし。特殊規則なし。パス条件就是証明パイプラインの背景知識——和类型等式、借用語制約が同じパイプラインを共有し、同じ予算システムを使用。

### 4. コンパイル時証明パイプライン

すべてのコンパイル時検査は同一个パイプラインを共有する。パイプラインの核心操作は**型検査**——证明项的类型是否等于待证明的命题を検証すること。すべてが型検査である。

```
コンパイル時に Bool 式を評価する必要がある時（つまり：証明項を構成する必要がある時）
        │
        ├── 型等式（T1 == T2）
        │   → コンパイラが直接判定（構造同値）
        │
        ├── トークン衝突条件（!conflicting(tokens)）
        │   → フロー感受性生存分析（Dup/Linear 属性追跡）
        │
        ├── 依存型簡約（n + m 簡約）
        │   → コンパイル時項書き換え系（βδι-簡約）
        │
        ├── コンパイル時述語 (x > 0, forall...)
        │   → コンパイラ本体 + SMT アクセラレーションモジュール
        │
        └── ホア論理含意式（P ⇒ Q）
            → コンパイラ + SMT 加速モジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル通過
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未解決命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を書く（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル通過
                  │
                  ▼
            検証失敗 → コンパイルエラー：「証明不成立」
```

#### 4.1 証明結果：三値代数

コンパイル時評価は三种の結果を返す——这是停机问题的必然结论，也是证明论的自然分割：

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項構築済み、型検査通過。コンパイル続行。
- **Disproved(M)** → 停止、反例 M 存在。コンパイルエラー + 反例 + ソース位置。
- **Unproven** → 与えられたリソース上限内で証明が構成できなかった。コンパイルエラー + 未解決命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言不等于命题为假——只是超出了当前自动证明的能力。これは正直であり、欠陥ではない。

予算の hard limit は停止問題のエンジニアリング解である。Knob を与えない——与えてしまえば「あなたのプログラムは停止すると思いますか」とユーザーに訊くことになるが、ユーザーは知らず、コンパイラも知らない。

#### 4.2 Unproven の後：プログラマが証明を書く

コンパイラが Unproven を返す時、Progurammer は**証明関数**を書くことができる——就是 YaoXiang 関数で、その戻り値型は証明対象の命題に等しい。型検査器は这个関数を検証する——と它是検証 `add(a, b): Int` は同じ mechanism。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼根源）
```

SMT 求解器は独立した信頼境界ではない——它是**型検査器の加速モジュール**である。SMT は証明の発見を支援するかもしれいが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返した時、コンパイラは結果を型検査器が検証可能な証明項に再構成する。再構成に失敗した場合（SMT の推論ステップがコンパイラカーネルの推論規則を超える）、Unproven に后退——Progurammer は手動で証明関数を書ける。

```yaoxiang
# 命題：コンパイラが自動証明できない精製プロパティ
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明：Progurammer は戻り値型が上記の命題である関数を書く
# 型検査器はこの関数を検証——と add(a,b): Int の検証が完全に一致
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラはここで検証：関数体の型 = FirstIsMin(T, arr)
    ...
}
```

AI 不要。Coq へのエクスポート不要。新概念不要。**コンパイル時に自動証明できないプロパティ → Progurammer が YaoXiang コードで証明を書く → 型検査器が検証。**
全体は滑らかなグラデーション——コンパイラが簡単な証明を引き受け、難しいものは人間の頭に 맡せる。

#### 4.3 パイプライン内の階層的依存

以上の評価器は同一インターフェースを共有するが評価順序が存在する。型等式はすべての後続分析の前提条件である；所有権/トークン検査は型情報に依存する；精製述語検証は前三層の結果に依存する。コンパイラは階層的に評価し、底辺で失敗した式は上層に入らない——型エラーがあるプログラムで求解予算を無駄にすることを避ける。

```
評価順序（同一パイプライン、階層的スケジューリング）
├── 第 0 層：型等式（T1 == T2）
│   └── 構造単一化 → 失敗なら後続は無意味、直接 Disproved を返す
├── 第 1 層：所有権/トークン衝突
│   └── フロー感受性生存分析 → 失敗ならメモリ安全不成立、直接 Disproved を返す
└── 第 2 層：精製述語/ホア含意
    └── コンパイラ自身 → SMT 加速 → Proved / Disproved / Unproven を得出
```

每一層仍返回 `Proved/Disproved/Unproven`，共享同一インターフェースと同一予算システム。

### 5. 三層関数の統一

| 階層       | 実行タイミング | 入力    | 出力 | 例                                           |
| ---------- | -------- | ------- | ---- | ---------------------------------------------- |
| 値級関数   | 実行時   | 値      | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時   | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時   | 値      | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

すべてが同一の `name: type = value` 構文を使用する。コンパイル時述語と型コンストラクタは同一のコンパイル時証明パイプラインを辿る——`{}`
は証明空間である。

### 6. ループ：Floyd-Hoare 検証条件生成

ループには個別の `: Invariant(...)` または `: decreases(...)`
注釈が不要である。変数上のコンパイル時述語型注釈が Floyd-Hoare スタイルの表明を定義する——コンパイラは型注釈から検証条件を生成し、証明パイプラインが各代入が型を保持するか検証する。

核心 mechanism：各代入操作は Hoare 三要素 `{P} x := e {Q}` に対応し、検証条件は `P ⇒ Q[e/x]` である。コンパイラはループ本体に対して一度だけ検証条件を生成する——証明パイプラインが帰納段成立后を検証すれば、すべての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈が i を参照；初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証：0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラはループ本体に対して一度だけ VC を生成。前提：s は SumUpTo(arr, i)、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]：
        #   検証義務：s_new は SumUpTo(arr, i) を満たす（現在の i は不変）
        #   s_new = s_old + arr[i] を代入：
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮説 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える：
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT：線形算術、ミリ秒単位 → Proved
        #
        # i += 1：
        #   i 変更 → 依存グラフで s の型注釈が i を参照 → 再検証トリガー
        #   新しい検証目標：s は SumUpTo(arr, i_new) を満たす
        #   即ち s == sum(arr[0..i_new])、前ステップで保証済み → Proved
        s += arr[i]
        i += 1
    }
    return s  # この時 s: SumUpTo(arr, arr.len)、即ち s == sum(arr[0..arr.len])
}
```

ループ不変式は変数上の型注釈である——Progurammer が型を書き、コンパイラが帰納段を検査する。コンパイラは不変式を「発見」する必要も、「自動帰納」をするする必要もない——它把归纳证明分解为每个代入操作の局所検証条件，将其交给证明パイプライン各个击破。

#### 6.1 依存追跡：可变変数上の依存型

上記の mechanism の前提：コンパイラは `s` の型注釈 `SumUpTo(arr, i)` が `i` を参照することを知っている——`i` が変更された時、`s` の型制約も変化する。これにはコンパイラが**変数間の型依存グラフ**を維持する必要がある。

**データ構造**：

```
TypeDepGraph: Map<VarName, Set<VarName>>
# 鍵は依存される変数、値は해당変数内の型注釈で参照された変数の集合
# 例：{ i: {s}, j: {s, t}, ... }
```

**構築**：型検査器が `mut v: Pred(... x ...) = init` を処理する時、`Pred(...)`
のパラメータ内の自由変数参照を解析する。パラメータ内に現在のスコープ内の他の可变変数 `x` への参照がある場合、依存グラフに `x → v` を記録する。

**トリガー**：依存される変数 `x` が代入された時、コンパイラ：

1. 依存グラフで `x` に依存するすべての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` に対して、検証条件を生成：`v の現在値是否满足更新後の型 Pred(... x_new ...)`
3. VC を証明パイプラインに送信

**代入順序感受性**：依存追跡は自然な正しい代入順序を実施する。`SumUpTo(arr, i)` を例に：

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → 再検証 s は SumUpTo(arr, i_new) を満たす → True

# 誤った順序——コンパイラが拒否
i += 1        # i 変更 → 再検証 s は SumUpTo(arr, i_new) を満たす
              # s はまだ更新されておらず、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー：変数 s は型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**組み合わせ依存**：一つの変数は複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は `x` と `y` に同時に依存する——いずれかの変更が再検証をトリガーする。

**証明パイプラインとの関係**：依存追跡は VC 生成のトリガーであり、独立した検証 mechanism ではない。それは「いつ VC を生成する必要があるか」に答え、証明パイプラインは「VC が成立するか」に答える。

### 7. 終了検査

**適用範囲：精製型。**
終了可能性は独立したスイッチではなく、**検証モード**の一部である：型が精製されると（`Refined { base, constraint }`）、その型で注釈された計算は検証モードに入り、モード内で終了可能性を要求する；精製されていない普通型は検証モードに入らず、終了義務を生成しない。

由此得两条推論：

- **ループ**：素の `while` は検証モードに入らない；度量変数に精製注釈がある場合（`i: UpTo(n)` など）、検証モードに入り、終了を証明する必要がある。
- **再帰**：関数シグネチャに精製がある場合（パラメータ精製または戻り値型に精製を含む）、検証モードに入り、各再帰呼び出し点で測度が厳密递减することを証明する必要がある。

モード内で全自动优先：コンパイラはまず測度を自動探索し、証明できれば通過；探索できず測度を明示的に指定しなければコンパイルエラー。**注釈構文の口を开けない**——測度と終了命題は型位置に書き、`decreases` 類いの新しい構文を導入しない。測度と明示的なフォールバックの形は §6.9 を参照。

#### 6.1 設計原則

コンパイラは二箇所から終了証明に必要な情報を自動的に抽出する：

1. **変数型注釈**：精製型内の境界制約（例：`UpTo(n)` が上限 `n` と下限 `0` を提供）
2. **ループ本体操作**：各反復で変数に加えられる操作

コンパイラは優先順位に従って四つの測度合成戦略 пытается を試み、見つかれば停止する。四戦略は**測度探索の受限テンプレートシーケンス**であり、入力は精製制約（戦略 1–4 はすべて「有界型の変数」を起点とする）であり、「コンパイル時評価されるコード」ではない；它们は §6.9 の明示的測度の自動と手動の两面である。

> **測度探索は探索であり、推論ではない。**
> 探索はテンプレート（線形階数、違反カウント、有界パターン、乗法スケール）のみを列挙し、解の存在を保証しない——一般的な測度推論は一般に決定不能（停止問題に帰着）。因此、テンプレート外の情形は Progurammer が明示的に測度を提供する必要がある（§6.9）、そうでなければコンパイルエラー。

#### 6.2 戦略 1：線形階数関数の自動合成

変数が線形境界注釈を持つ時、コンパイラは候補線形測度を列挙して SMT 検証する。

```
入力：
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（上下境界のある変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム：
  1. 型注釈から各変数の境界を抽出：[low_i, high_i]
  2. 候補測度を列挙：v_i, u_i - v_i, v_i - v_j、などの線形結合
  3. 各候補測度 m に対して：
     - SMT で m ≥ 0 を検証（型境界から導出）
     - ループ本体の各実行パスに対して、SMT で m' < m を検証（厳密递减）
  4. 条件を満たす線形結合が見つかる → 終了証明完了
```

カバー範囲：任意変数が線形式（`v = a·v + b`）で代入され、有界型注釈を持つループ。包括
`i += const`、`i -= const`、および二分探索式の区間収縮：

```yaoxiang
# 二分探索：low = mid + 1 または high = mid
# 測度 high - low は両パスで厳密递减
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2：述語違反カウント——目標型から自動抽出測度 <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在ステータス：実験的戦略、フェーズ 3 実装時に実際の実行可能性に応じて含めるかを決定。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効であり、非隣接操作（クイックソート partition、ヒープソート sift-down）の自動証明は不能。カバー境界は下の表を参照。フェーズ 3 で検証が実行不可能な場合、この戦略は削除または将来の改善に格下げされる。

核心の洞察：**ユーザーが書いた仕様はコンパイラの推論の素材である。** コンパイラは「ソートとは何か」を内置する必要はない——它は `Sorted` の定義を読み、定義から自動的に測度を抽出する。

```
入力：
  目標型：Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体の操作：隣接要素の交換

アルゴリズム：
  1. 述語定義を解析：forall i in range: cond(i, arr)
  2. 測度を自動生成：violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作が測度に与える影響を分析：
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の三ペアのみに影響
     - arr[j] > arr[j+1]（述語違反）なら、交換後このペアは述語を満たす
     - violation_count が少なくとも 1 減少
  4. 上限：n·(n-1)/2（最大隣接逆順数）、下限：0
  → 終了証明完了
```

**現在カバー範囲**：

| アルゴリズム     | 操作モード       | 戦略 2 で証明可能？ | 理由                             |
| -------- | -------------- | :-------------: | -------------------------------- |
| バブルソート | 隣接交換       |       ✅        | violation_count 各交換で厳密递减 |
| 挿入ソート | 隣接移動       |       ✅        | 各シフトで一つの違反ペア消除           |
| 選択ソート | 非隣接交換     |       ❌        | 一回の交換で violation_count が増加する可能性 |
| クイックソート | partition 分区 |       ❌        | 非隣接交換、単調递减を保証しない       |
| ヒープソート   | sift-down      |       ❌        | 木操作、violation_count 非単調   |

**補完戦略**：クイックソートに対しては、`low < high`
区間収縮は戦略 1（線形階数関数）でカバー可能——外層の partition 再帰、每次区間半減。戦略 1 と戦略 2 は互补覆盖し、実際のアルゴリズムの終了可能性はほとんどの場合两者のいずれかで証明可能である。しかし戦略 2 の一般化（非隣接操作、木操作）は依然として未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3：有界増減パターン

`v += const`（正数）、変数に上限型注釈がある → 測度 `upper_bound - v` が毎回 `const` 递减、下限 0。これは戦略 1 の退化 case であり、コンパイラが最先頭で迅速に処理する。

#### 6.5 戦略 4：乗法スケール測度テンプレート

`v *= const`（const > 1）、変数に上下界型注釈がある。コンパイラは内置対数測度テンプレート
`ceil(log_const(upper/v))`、每次乘 const で測度が 1 減少。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラが自動導出：測度 ceil(log₂(n/i))、每次 2 倍で測度が 1 減少
    i *= 2
}
```

#### 6.6 終了可能性と正確性の分離

終了可能性証明と正確性証明は独立している：

- **終了可能性**：以上の四つの戦略がループが有限ステップで退出することを自動証明する；探索できない時は Progurammer が型位置に測度を提供する（§6.9）
- **正確性**：ループ本体が目標型に向かって進行するかは、コンパイル時証明パイプラインが検証条件を通じて検査する

两者都通过 → コンパイル通過。終了証明済みだが正確性失敗 → コンパイルエラー + 反例。正確性証明済みだが終了可能性を証明できない → コンパイルエラー、分析できない変数または操作を指摘。两者都失敗 → コンパイルエラー分别报告两项失敗原因。

#### 6.7 再帰関数の終了検査

精製署名を持つ再帰関数に対して、コンパイラは各再帰呼び出し点で仮引数が递减することを検査する：

```yaoxiang
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)  // コンパイラが探索：(b, a % b) の適定序測度递减 → 終了
}
```

仮引数递减は最强の自動パス（構造再帰）である。探索できない時は、Progurammer が型位置に明示的に測度を提供する（§6.9）。

#### 6.8 ハード境界

`i = f(i)` かつ `f` が逆変換不能、閉じていない、単調性を保持しない——数学的に自動終了証明不可能。コンパイルエラー：

> このループは自動終了証明できません。ループ変数は分析不能な関数 `f` に依存しています。
> コンパイラが分析できる反復パターンを使用するか、そのループに名前を付けて型位置に測度を提供してください（§6.9）。

これはコンパイラの失敗ではない。凡静态的に证明できない安全コードは、通过不允许。即使提供显式测度，也必须经 SMT 判定为真才能通过——测度写得不对会被反例打回，人只能证不出来，不能证错。

#### 6.9 明示的測度：`Terminates`

自動探索で測度が見つからない時、Progurammer は測度を**型位置**に書く——`Positive(b)`、`IsMax(T, arr, result)`
と同じ mechanism（述語適用）、ゼロ新構文：

```yaoxiang
// 測度：普通の関数、単体テスト可能、再利用可、実行時に参加しない
gcd_measure: (a: Int, b: Int) -> Int = { b }

// 終了分量靠在関数自身の型位置
gcd: Terminates((a: Int, b: Int) -> Int, gcd_measure) = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

// ループ：束縛名がアンカー、測度は名前でスコープ内の量を得る
loop: (n: Int) -> Int = {
    mut i = 0
    acc: Terminates(n - i) = while i < n {
        i = i + 1
    }
    return acc
}
```

ループ这里的理由：`Terminates(m)` 精製はループ本体末尾式の値型を精製するものであり、アンカーは束縛名 `acc`
を提供する——因此ループは参照可能になり、「匿名構造が参照不能」という死角がなくなる。

**`Terminates` は内置述語**であり、`Int`、`Never`
と同じコアプリミティブである。これは唯一**コンパイラが関数本体を代筆する**述語である——その表明（「各再帰呼び出し点/ループバックエッジの測度が厳密递减」）は計算構造に組み込まれており、ユーザーが書いた述語は関数本体またはループ本体を参照できないため、「構文」節の述語定義構文では表現できない。内面向きは这个名字に收敛する。

**元数**。`Terminates(FnType, m)` と `Terminates(m)` は同一个述語の二つの元数であり、二つの構造ではない：

| 形態                    | アンカー           | 用途                       |
| ----------------------- | -------------- | -------------------------- |
| `Terminates(m)`         | 所在束縛の名前 | 自己再帰関数、ループ——デフォルト形態 |
| `Terminates(FnType, m)` | 明示的関数型   | 相互再帰などアンカーが一意でないシナリオ   |

两者本质同一：終了義務は常に「精製がある型位置で注釈されたその計算」に落ちる。

**測度は戻り値型を制限しない。**
測度は任意の型の式である（自然数に強制されない）；その上の「厳密递减」は当該型に利用可能な適定序から与えられる。測度が良基かどうか（例：`Int` を返す時に `>= 0` かどうか）は**独立した義務**であり、递减義務と同様に精製導出または SMT に委ねる；两者とも導出できない時、診断は**直接拒否せず**、代わりに方向を提案する（測度在下界成立かどうか、再帰パラメータがその方向に本当に進んでいるかどうか）。

**自動探索との関係**：明示的測度は別の管线ではなく、探索失敗後の入力である。測度を与えた後も同一の SMT で递减と良基性を検証する；成立しなければエラーメッセージと反例が付いて返る。

義務生成、判定管线、診断方向、相互再帰の測度共有（SCC）などの実装 mechanism は
[RFC-027a: 終了検査の明示的測度](../review/027a-termination-explicit-measure.md) を参照。

### 8. SMT 求解器：型検査器の加速モジュール

SMT 求解器は従来の言語では外部ツールである（例：F\* が Z3、Dafny が Z3 を呼び出す）。YaoXiang では，它是**型検査器の加速モジュール**である——コンパイラカーネル自身が直接判定できない時のみ呼び出される。SMT は証明の発見を支援するかもしれいが、証明を検証するのは型検査器である。

**信頼モデル**：型検査器は唯一の信頼根源である。SMT 求解器は加速モジュール——它は証明の発見を支援するが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny ルートと同じ——Z3 がエラーを出す確率はコンパイラ自身のバグ率より低く、工学的現実的な選択である）。本当の信頼性の制御は SMT 翻訳層にある——翻訳にバグがあれば、コンパイラは他のテストでそれを露呈する。

**インターフェース**：コンパイラ内部は SMT-LIB
2.6 標準フォーマットに翻訳し、特定求解器 API にバインドしない。SMT-LIB は ISO 標準であり、Z3、CVC5、MathSAT、Yices がすべてネイティブにサポートする。

**デフォルトバックエンド**：Z3（MIT ライセンス、最も広範なドキュメントとコミュニティ検証）。CVC5 を SMT-LIB 互換の代替として——ユーザーはコンパイル時にコンパイラフラグで切り替え可能。

「汎用求解器抽象化層」を作らない——SMT-LIB が抽象化層である。未来もし CVC5 が特定の理論でブレイクスルーを果たせば、切り替えはバイナリ交換だけで済み、コンパイラコードを変更する必要がない。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造同値、简单算术、
        │   定数畳み込み後の自明な公式）
        │   → 直接 Proved / Disproved を返す
        │
        └── コンパイラカーネルが直接判定不能（量化子、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB フォーマットに翻訳
            → Z3/CVC5 に送信（予算制限付き）
            → 戻り値：unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**求解予算——ハードリミット、スタック深度のように**：

| 予算次元       | デフォルト値 | 説明                                                                                      |
| -------------- | ------ | ----------------------------------------------------------------------------------------- |
| 求解ステップ数       | 10,000 | Z3 は線形算術に対しては通常数百ステップ。10,000ステップで実際の述語の99%をカバー。                               |
| 時間           | 100ms  | 单述語が 100ms を超える = ユーザーはコンパイル時プログラム而非型注釈を書いている。100ms × 50 述語 = 5 秒コンパイル時間上限。 |
| 量化子インスタンス深度 | 3      | 三層嵌套量化子が実際のパターンをカバー。三層を超える大半は論理練習問題を解いている。                                  |

予算超えは Unproven を返し、コンパイルエラー + 述語位置 + 消費量を通知。デグレードなし、実行時検査なし、サイレントパスなし。

**为什么这实际可行**：エンジニアリングでは実際の述語の95%は線形算術である——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——これらはすべて決定可能断片内にあり、SMT 求解器は这类問題に対してミリ秒级で返す。予算超えの複雑な述語に出くわしても、Progurammer は証明関数を書けばよい。

依存型は SMT 呼び出し前に一层事前簡約を行う：`factorial(5)` は直接コンパイル時評価で `120` になり、`append([1,2], [3])`
は直接評価で `[1,2,3]` になる。这些确定性的値計算は SMT 予算を消費しない。

Progurammer は SMT の存在を知っておく必要はない。メンタルモデル：**コンパイラが証明できれば通過、できなければエラー——もしコンパイラができなければ、証明を代わりに書く関数を提供できる。**

### 9. コンパイル時述語の組み合わせ

コンパイル時述語は Type を返す関数であり、組み合わせは関数合成で自然に実現する：

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算安全

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラは Positive(2) = { 2 > 0 } → True を検証
# result = divide(10, 0)  # ❌ コンパイラは Positive(0) = { 0 > 0 } → False を検証
```

#### 9.2 配列アクセス安全

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラは InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True を検証
# y = get(arr, 5)  # ❌ コンパイラは InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False を検証
```

#### 9.3 ソート正確性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ：コンパイラによる VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 配送パイプライン：コンパイル時と実行時の統一配送

`assert` と `Assert` は同一个精製型プリミティブの両面である。配送パイプライン `dispatch`
は**述語の自由変数がコンパイル時に到達可能かどうかに応じて**自動的にコンパイル時証明か実行時検査かを決定する：

| 判据                                                   | モード            | 動作                                                                |
| ------------------------------------------------------ | --------------- | ------------------------------------------------------------------- |
| すべての自由変数がコンパイル時に既知（ジェネリックパラメータ、コンパイル時定数）         | **CompileTime** | 証明パイプラインに進む：Proved → 消去、Disproved → コンパイルエラー、Unknown → 証明を要求 |
| 実行時から来た自由変数が存在（関数パラメータ、外部入力、mut 変数） | **Runtime**     | 実行時 check を挿入し、フロー感受性仮定集合 Γ に精製事実を注入                   |

**鍵**：「判できない」≠「証偽」。CompileTime モードで Unknown は証明を要求する（サイレントデグレードなし）、Runtime モードでは命題はコンパイル時に真でも偽でもない—— prover がどんなに強くても「ユーザーが負数を入力したかもしれない」の恒真証明は書けない、実行時 check が唯一の sound な選択である。これは prover が不够ではなく、理論的必然である。

### 12. フロー感受性仮定集合 Γ：最强後置条件伝播

コンパイラはフロー感受性（flow-sensitive）仮定集合 Γ を維持し、各制御フローポイントで既知成立の命題を追跡する。

**SP（最强後置条件）伝播**：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**：`mut` 変数が再代入後、その変数を含むすべての仮定が Γ から削除される：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

这是 soundness の hard 要件——変数値が変化すれば、古い仮定は無効である。

**分岐合流**：IF/ELSE または match 分岐がマージする時、Γ は各分岐の仮定の交集を取る。すべてのパスで成立する命題のみが分岐から持ち出される。

### 13. 消去モデル澄清：witness 消去 ≠ check 消去

RFC-027 の「精製型は実行時に**完全に消去**される」という論断が指す的是 **proof
witness（証明トークン）**——コンパイル時に検証された証明項は実行時コードを生成しない。しかし Runtime モードで dispatch が挿入する
**実行時 check** は保持される——它是值层面执行的 Bool 检查であり、型层面的 witness ではない。

まとめ：witness 消去、check 保持。二つのことが冲突ではなく、RFC-027 の元論点は不变である。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以後 (本 RFC)                                                                |
| ------------------------------------- | ---------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語をパラメータ型として使用 `(b: Positive(b))`                                    |
| `//! ensures: ExistsMax(result, arr)` | 戻り値型に戻り値仮引数を使用 `-> (result: IsMax(T, arr, result))`                  |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変式                               |
| `//! decreases: n`                    | 測度は精製型位置にでも書く（`Terminates`）；コンパイラがまず自動探索、探索できなければ明示的に要求 |
| 仕様はコメント                            | 仕様は型システム                                                               |

### 構文

**コンパイル時述語には新しいキーワードがない。** `{}`
は証明空間であり、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数である——`name: (params) -> Type = { 表明 }`。使用时就是関数呼び出し——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証する表明
# 既存の関数/型構文を使用、新しい BNF 規則不要
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**述語適用の実引数はコンパイル時定数形態でなければならない**——リテラル、変数（名前束縛による）、型適用（再帰抽出）、または**コンパイル時に参照可能な関数参照**（関数名）。実引数形態を定数式に変換できない場合は
**E1092**、実引数個数と述語宣言の仮引数個数が一致しない場合は
**E1093** を報告。実引数は位置で仮引数リストに束縛され、述語元数は宣言で決まる——`Positive(x)` 一元、`IsMax(T, arr, result)`
三元、`Terminates(m)` と `Terminates(FnType, m)`
の一元と二元——精製制約は**決してサイレントにドロップされない**（従来は変換不能な実引数により制約が音もなく消え、制約に違反する束縛がサイレントに通過していた）。

**新しい構文概念：戻り値仮引数**——`-> (name: Type)` において `name` は戻り値仮引数である。

戻り値仮引数は YaoXiang が既存の関数構文に導入する**唯一の構文概念**である。そのセマンティクス：

- `name` の値は `return` 文で提供される
- `name` は型シグネチャ内にのみ存在し、後置条件述語から参照される（`-> (result: IsMax(T, arr, result))`）
- `name` は関数本体スコープに入らず、呼び出し元にも現れない
- 戻り値仮引数は**オプション**——後置条件がない時はシグネチャは普通関数と完全に一致（`-> Int`）、追加負担なし

導入の理由：後置条件は「関数が返す値」を参照する必要がある。戻り値仮引数がない場合、コンパイラは特殊規則（暗黙変数
`$result` や `__retval__` など）でのみ述語に戻り値を参照させることができる。戻り値仮引数はこの参照を明示化する——只是一个仮引数であり、値は
`return` 而不是呼び出し元から提供されるだけである。

**証明関数**は新しい概念ではない——就是 YaoXiang 関数であり、その戻り値型は証明対象の命題である。コンパイラが Unproven を返す時、Progurammer は証明関数を提供し、型検査器は任意の関数戻り値型を検証するのと同じ方法でそれを検証する。新しい構文、新しいキーワード、新しい規則が不要である。

> **両者の境界。**
> 正確性域（述語 Unproven）は**本体**内で証明を補完する：戻り値型が証明対象の命題である関数を書く。終了域（§6.9）は**型位置**で測度を補完する：束縛または関数シグネチャの型として
> `Terminates(測度)` を書く——前者は「証明できない命題に証明を書く」、後者は「探索できない測度を明示的に宣言する」——机制同一（いずれも精製型適用）、落点異なる。終了域は **_proof** 関数を書く必要がない。

### 型システムへの影響

- **型宇宙**：コンパイル時述語は Type₂ 層に位置する——値を受け取って Type を返す関数であり、型コンストラクタと同じレベル
- **ジェネリック相互作用**：コンパイル時述語はジェネリックパラメータを持てる（例：`NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`）
- **所有権相互作用**：コンパイル時述語内の式は所有権規則に従い、読めるが書けない
- **型推論**：コンパイル時述語のパラメータは HM 型推論に参加する

### ランタイム表現

コンパイル時述語は実行時に **dispatch 配送結果に応じて処理**される：

- **CompileTime モード**（すべての自由変数がコンパイル時に既知）：証明通過後 witness（証拠トークン）が完全に消去される。`Positive: (x: Int) -> Type = { x > 0 }`——パラメータ
  `b: Positive(5)` の実行時表現は単なる `Int` である。精製条件 `{ 5 > 0 }` は既に通過、消去される。
- **Runtime モード**（実行時の自由変数が存在）：実行時 check を保持——値层面で Bool 检查を実行し、フロー感受性仮定集合 Γ に注入。詳細については §11
  dispatch 配送パイプラインと §13 消去モデル澄清を参照。

コンパイル時述語を型位置に使用する（`f(x: Positive(x))` など）は包装型を生成せず、追加メモリを割り当てない。しかし `x`
が実行時入力由来の場合、**実行時 Bool 检查が挿入される**。

**`ref` との相互作用制約**：コンパイル時述語は不変借用または所有権が既に移動された値のみを参照できる。可変借用を参照するコンパイル時述語は、コンパイル時に検証結果が実行時仍然成立することをコンパイラが保証できない——この使用法は直接コンパイルエラーを報告する。

### コンパイラの変更

1. **パーサ**：コンパイル時述語は標準関数構文を使用、追加解析規則不要
2. **コンパイル時証明パイプライン**：統合 Proved/Disproved/Unproven 戻りインターフェース、自動策略選択
3. **SMT 加速モジュール**：SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**：推論規則実装——構造同値、βδι-簡約、全称量化子導入/消去。 这是唯一的信頼根源、SMT と Progurammer 証明はここですべて検証される
5. **検証条件生成**：WP/SP 計算 + ループ不変式証明義務
6. **エラー報告**：反例フォーマット化 + 未解決命題報告 + ソース位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用していないコードは完全に不变
- ✅ コンパイル時述語は CompileTime モードでゼロ実行時オーバーヘッド、Runtime モードでは必要な Bool 检查のみ保持
- ⚠️ RFC-022 の `//!` 構文はもうサポートしない——しかし 022 は実装されたことがなく、移行負担なし

## トレードオフ

### 利点

- **Curry-Howard 同型の完全兑现**：型は命題、プログラムは証明、`name: Proposition = Proof`
- **統一性**：コンパイル時述語と普通関数は完全に同一の構文を使用し、概念分裂なし
- **SMT 透過性**：Progurammer は SMT の存在を知っておく必要がなく、メンタルモデルは型検査と一致する
- **漸進的採用**：一つのコンパイル時述語から開始して，逐步增加覆盖
- **最小実行時オーバーヘッド**：CompileTime モードでゼロオーバーヘッド、Runtime モードでは必要な Bool 检查のみ保持

### 欠点

- **コンパイル時間**：SMT 求解がコンパイル時間を增加させるが、予算 hard limit が上限を保証
- **自動証明の限界**：一階線形算術を超える複雑な述語は、Progurammer が証明関数を書く必要があるかもしれない。これは言語の欠陥ではない——这是停止問題の必然的結論である。コンパイラは Unproven を正直に報告而非偽って True/False を報告
- **学習曲線**：効果的なコンパイル時述語と証明関数を書くには Curry-Howard 同型の基本直観を理解する必要がある
- **実装複雑度**：コンパイル時証明パイプラインの統一には精心した設計が必要

### リスク緩和

- SMT 求解予算の hard limit（ステップ数 10,000 / 時間 100ms / インスタンス深度 3）、予算超えは Unproven を返す
- 依存型事前簡約：確定的な値計算は先に処理し、SMT は非確定部分のみを処理する
- Unproven は袋小路ではない：正确性域は証明関数を書く（戻り値型が命題）、終了域は型位置に測度を提供する（§6.9）——两者均由型検査器が検証する
- 増分検証：変更されたモジュールのみを検証
- 明確なエラーメッセージ + 反例展示 + 予算消費レポート + 未解決命題 + 提案（如果コンパイラが提供可能なら）

## 代替案

| 方案                               | 为什么不选择                                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| RFC-022：`//!` コメント式仕様          | 仕様と型が分裂し、Curry-Howard 同型に違反                                                                      |
| 独立仕様ファイル（如 CVL）             | 仕様とコードが分離し、保守コストを増加                                                                            |
| 実行時アサーションのみ                   | 静的正確性を保証できない                                                                                          |
| 外部証明アシスタント（如 Coq）             | コンパイラと分離し、独立した証明言語と信頼境界が必要。YaoXiang の選択：証明は YaoXiang コードであり、型検査器は唯一の信頼根源 |
| **本方案：コンパイル時述語作为一等市民** | ✅                                                                                                          |

## 実装戦略

### 段階划分

| 段階       | 内容                                                                                               |

| **段階 1** | コンパイラカーネル：構造同値 + βδι-簡約 + 全称量化子導入/消去。简单算术述語（`x > 0`、`arr.len > 0`）をサポート    |

## 未解決の問題

- [x] **SMT 求解器の選択**：デフォルト Z3（MIT ライセンス、最も広範に検証）。CVC5 を SMT-LIB 互換の代替とし、コンパイラフラグで切り替え。コンパイラ内部の翻訳先は SMT-LIB
      2.6 標準フォーマット——SMT-LIB が抽象化層であり、カスタム汎用求解器インターフェースを作らない。
- [x] **求解予算の具体値**：ステップ数 10,000 / 時間 100ms
      / 量化子インスタンス深度 3。コンパイラ内部で固定し、knob を与えない。実際の使用で真实なユースケースが不足していることが証明されれば（「ユーザーが間違えた」のではなく）、調整する。
- [x] **量化子サポート範囲**：言語レベルでは量化子の次数を制限しない。コンパイル時述語は Type パラメータを受け入れる——Type には関数型が含まれる——因此高階量化子は型システムの自然な帰結であり、特殊構文が不要。SMT 求解器は一階量化子（forall/exists、交差嵌套をサポート、予算深度 3 で制限）を自動判定可能。高階量化子：SMT が Unproven を返し、コンパイラは「この述語は自動証明範囲を超えている、証明関数を提供してください」と提示する。Progurammer は戻り値型がその命題に等しい YaoXiang 関数を書く——型検査器がその関数を検証する。外部エクスポート不要、AI 不要、対話型証明モード不要。すべてが YaoXiang コードであり、すべてが型検査器によって検証される。
- [x] **反例フォーマット**：ソース変数名は SMT 変数名として直接使用（モジュールプレフィックスで衝突回避）。Z3 モデルが返す時に変数名で逆引き。出力形式：変数名 = 具体値 + ソース位置 + 述語定義位置。複雑なマッピング層を作らない。
- [x] ~~**`ref` スマートポインタとのコンパイル時述語の相互作用？**~~
      → 既に決定：コンパイル時述語は不変借用または既に移動された所有権のみを許可する。可変借用の値はコンパイル時述語に出現できない。
- [x] **`forall` 述語違反カウント測度の非隣接操作への拡張？**
      → 拡張しない。現在のカバー範囲（隣接交換、隣接移動）は戦略 1（線形階数関数）で互补カバー——クイックソート外層区間收缩は戦略 1 で底上げ、ヒープソートは戦略 1（配列インデックスパターン）で底上げ。任何戦略でも終了を証明できないループは、コンパイラが直接エラーを報告——这是硬安全哲学であり、欠陥ではない。未来に真实なシナリオ（非学術的構成）のアルゴリズムで四つの戦略すべてがカバーできない場合は、再議論する。→
      **再議論がトリガーされた（2026-09-14、#318）**：非構造再帰（gcd 類非直接递减、相互再帰、マージ分区）が本条項の予想した真实なシナリオである——測度探索のテンプレートシーケンスは自動では処理できず、可読性を損なわず分析可能な反復パターンに書き換え不可。結論：硬安全哲学は不变（測度が間違っていれば SMT 反例で打ち返され人間は証明失敗のみで証明間違いは不可）だが、「探索できなければ拒否」を「探索できなければ Progurammer が型位置に明示的に測度を提供可能」に緩和——§6.9 を参照。
- [x] **線形階数関数列挙组合爆発**：候補列挙上限は 3 つの有界変数。≤3 の時はすべての線形結合を列挙して SMT が個別に検証。>3 の時は単変数測度のみを試す（`v_i`、`u_i - v_i`）、失敗すれば直接コンパイルエラー——Progurammer に「ループに >3 個の有界変数がある、コンパイラは多変数測度を自動合成できない」と提示。これはエンジニアリング妥协ではない——Progurammer に より簡単なループを書くよう強制する。
