# RFC-027: コンパイル時述語と統一静的検証

> **参考文献**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統一型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024: spawn ブロックベースの並行モデル](../accepted/024-concurrency-model.md)
>
> **置換**：[RFC-022: ホーア論理静的検証サポート（仕様コメントと仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止

## 概要

本文では、YaoXiang に**コンパイル時述語**を一級市民として導入し、すべてのコンパイル時静的検証を一つの**証明パイプライン**に統一することを提案する。コンパイル時述語は外部仕様コメントではなく——それ自体が関数である。Type を返す関数は型位置で使用でき、コンパイラはコンパイル時にそれを呼び出し戻り値をチェックする。型が命題であり、コンパイル時評価が証明である。

**核心的論点**：コンパイル時の型検査の唯一の仕事は証明項の構築と検証である。型等価、トークン衝突、依存型簡約、コンパイル時述語評価、ホーア論理含意——すべてコンパイル時証明パイプライン内の異なる型検査であり、同じパイプラインを共有する。SMT ソルバーは型検査器の加速モジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返すとき、プログラマは YaoXiang 関数を証明として記述する——型検査器は任意の関数の戻り型を検証するのとまったく同じ方法でそれを検証する。すべてが YaoXiang コードであり、すべてが型検査器によって検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 は仕様を `//!` コメント形式で設計していた：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← これは型とは独立したコメント
    //! ensures: ExistsMax(result, arr[0..n])   ← これは型とは独立したコメント
}
```

これは Curry-Howard 同型の根本的な誤りを犯している：**仕様と型を二層に分裂させること**。コメントは型ではない。コメントは型検査に参加しない。コメントは「外部ツール」のメンタルモデルである。

白書は明確に述べている：

> "`//!` コメントはない。独立した仕様言語はない。すべてが型システム内にある。"

### 現在の問題

- RFC-022 の `//!` コメントは型システムとは独立した外部構文
- 仕様型と通常型は二体系であり、概念の冗長性を生む
- Debug Build 検証 / Release Build 無視の分裂パターンが統一性を破壊する
- SMT ソルバーは従来の認識では外部ツールとして位置付けられる——YaoXiang では型検査器の加速モジュールとして内蔵される
- 型検査、借用の検証、コンパイル時述語検査、マクロ展開はそれぞれ異なる経路を辿る

### 正しいメンタルモデル

型検査は次のように抽象化できる：

```
verify : Program → Proved | Disproved(Model) | Unproven
```

すべてのコンパイル時検査——単純な型マッチング、借用衝突検出、コンパイル時述語検証——はこの関数のサブタスクである。それらは同じ証明パイプラインを共有し、違いは証明項の複雑さと構築戦略のみにある。

コンパイラが Unproven を返したとき、プログラマは証明関数を提供する——その関数の戻り型は証明されるべき命題に等しい。型検査器がそれを検証する。これは通常の型検査と同じ操作である。

## 提案

### 1. `{}` は証明空間：型がアサート、検証が型検査

YaoXiang の `{}`
はコンパイル時証明空間である。その中のすべてがアサートであり、コンパイラは各項目が True であることを保証する——自動証明されるか、プログラマが証明関数を提供するかのいずれかである。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  コンパイラは x が Float、y が Float であることを保証

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  コンパイラは data が Array(T) であることを保証
```

**ジェネリクスはコンパイル時述語の特殊ケースである。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          パラメータはシグネチャで  {} 内にはアサートのみ
#          コンパイラはコンパイル時に呼び出し x > 0 を検証

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      パラメータはシグネチャで  コンパイラは type_of(T) == Type、type_of(data) == Array(T) を検証
```

同じパターン：`name: (params) -> Type = { アサート }`。コンパイラは「型アサート」と「値アサート」を区別しない——どちらも証明パイプライン内の評価目標である。

**ループ不変条件は別途書く必要はない。変数上の型注釈こそが Floyd-Hoare 不変条件である。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照——コンパイラに s の型が i に依存することを伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラ検証：s_new == sum(arr[0..i+1])
        i += 1       # i 変更 → s 依存再検証をトリガー：s は SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新値が型注釈を満たすか。証明パイプラインが帰納ステップの成立を検証した後、すべての反復が自動的にカバーされる。`: decreases`
も、`: Invariant` も、帰納証明も不要——コンパイラは帰納を各代入の局所 VC に分解する。

### 2. 事前/事後条件：パラメータ型と戻り型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures`
を廃止する。コンパイル時述語はパラメータまたは戻り値の型注釈として機能する。

**パラメータ側は関数呼び出し。**
コンパイル時述語は Type を返す関数であり、パラメータ側での使用方法はそれを呼び出すこと——`factorial(5)`
と同じ。戻り値側は新しい概念を導入する：戻り値仮引数。

```yaoxiang
# 事前条件：パラメータ型で明示的にコンパイル時述語を呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在の仮引数名、Positive にパラメータとして渡される
#                       コンパイラは呼び出し点で実引数値を抽出し、b に代入し、Positive(実引数) を検証
#                       例：divide(10, 2) → Positive(2) = { 2 > 0 } を検証 → True
#                       例：divide(10, 0) → Positive(0) = { 0 > 0 } を検証 → False → コンパイルエラー

# 事後条件：戻り値仮引数 + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は戻り値仮引数、値は return によって提供される
#                                            コンパイラは return ポイントで戻り値を代入し、事後条件を検証
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要なルール**：

- **パラメータ側**：`b: Positive(b)` —— `b` は現在の仮引数名で、`Positive`
  のパラメータとして渡される。関数呼び出し構文、暗示的展開ゼロ。
- **戻り値側**：`-> (result: IsMax(T, arr, result))` —— `result` は戻り値仮引数で、値は `return`
  文によって提供される。`result`
  は型シグネチャ内にのみ存在し、述語からのみ参照され、関数本体のスコープには入らず、呼び出し側にも現れない。
- **戻り値仮引数はオプション**：事後条件がない場合は記述せず、シグネチャは通常関数と完全に一致する（`-> Int`）。
- **統一性**：パラメータと戻り値仮引数は同じ概念である——`仮引数名: 述語呼び出し(仮引数名)`、違いは値が呼び出し側から提供されるか
  `return` から提供されるかのみ。

### 3. パス条件伝播：ランタイム値のコンパイル時検証

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマによって明示的に渡される。ランタイム値が精錬型パラメータに入るとき、コンパイラはパス条件収集と SMT 含意判定を通じて検証を完了する——プログラマが明示的に証明を渡す必要はない。

#### 3.1 明示的関数呼び出し

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマによって明示的に渡される——関数呼び出しであり、暗示的展開はゼロである。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。束縛位置（パラメータ宣言、変数宣言、戻り型）に現れるとき、プログラマは明示的に既に束縛された変数名を渡す：

```yaoxiang
b: Positive(b)
// b は現在の仮引数として既に宣言されている、Positive(b) は関数呼び出し
// 正格化後：b: { b > 0 }
```

コンパイラが暗黙的にパラメータを埋める必要はない——`b: Positive(b)` は `f(5)`
と同じく関数呼び出しである。`b` はパラメータ名として束縛され、その型注釈 `Positive(b)` は `b`
自身を参照する——これは依存型の標準パターンであり、暗黙的展開ルールではない。

**RFC-010 の `self` との統一**：RFC-010 は `self`
がキーワードではなく、単にパラメータ名の慣習（"`p`、`this`、`x`
と書いても完全に同じ効果"）であることを確立している。`b: Positive(b)`
は同じメカニズムを共有する——パラメータ名は型注釈内で参照できる。`self` は `self: Point`
の位置に現れ、`b` は `b: Positive(b)`
の位置に現れ、両者の型注釈はパラメータ自身を参照する。違いは型注釈の複雑さのみであり、メカニズムは完全に同じ——名前が束縛された後、型はこの名前に依存できる。

戻り型も同様に明示的関数呼び出しを使用する：

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は戻り値仮引数、Sorted(result) は関数呼び出し
//                        コンパイラは return ポイントで戻り値を result に代入し、Sorted(戻り値) を検証
```

ローカル変数宣言にも同様に適用される：

```yaoxiang
let x: Positive(x) = 5
// x は 5 に束縛される、Positive(5) → { 5 > 0 } → True → 合格

// let y: Positive(y) = 0
// y は 0 に束縛される、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 パス条件収集

ランタイム値が条件分岐に現れるとき、コンパイラは自動的にパス条件を収集し、現在のスコープの**仮定集合**を形成する。これらの仮定は、コンパイル時 Bool 評価の背景知識として検証に参加する。

```yaoxiang
if y > 0 {
    // コンパイラはこの分岐内で自動的に仮定を取得：{ y > 0 }
    let result = divide(x, y)
    // 検証条件：(y > 0) ⇒ (y > 0)
    // 証明パイプラインが含意成立を判定 → Proved
} else {
// この分岐の仮定：{ not (y > 0) }
// divide(x, y) を呼び出す場合、検証条件は not (y > 0) ⇒ y > 0
    // 証明パイプラインが含意不成立を判定 → Disproved
}
```

これはコンパイラがハードコードされた特殊パターンを書くことではない——これはコンパイル時証明パイプラインの自然な動作である。型検査呼び出しポイントは毎回パイプラインに以下を送信する：

```
{背景仮定} ⇒ {検証目標}
```

証明パイプラインが含意性を判定する。Proved → 合格、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未解決命題。背景仮定は現在のプログラム地点のパス条件から来る。

#### 3.3 仮定スタック

コンパイラは制御フロー解析において、各基本ブロックに対して仮定集合を維持する：

- **if ガード**：`if y > 0` → true 分岐に `y > 0` をプッシュ、false 分岐に `not (y > 0)`
  をプッシュ（else を使用する場合）
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **論理結合**：`if x > 0 and y < 10` → 分岐内に `x > 0` と `y < 10` をプッシュ
- **関数事前条件**：`divide(a, b)` を呼び出すとき、`b` が `Positive`
  の証拠を持つ必要がある。それは現在の仮定から来るか、実引数自身の精錬型注釈から来る（`b` が
  `Positive` として注釈付けされている場合、その型は `b > 0` を運ぶ）
- **代入**：`let z = y` のとき、`y` 上の既存の精錬条件が `z` に伝播する

すべての仮定がコンパイル時証明パイプラインに入る。SMT 加速パスに入るとき、SMT-LIB 背景アサーションに翻訳される。

#### 3.4 静的証拠なしはコンパイルエラー

プログラマが直接以下のように書いた場合：

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム地点には `y > 0` の仮定がなく、実引数 `y` 自身にも `Positive`
型注釈がない。検証条件は：

```
{} ⇒ { y > 0 }
```

パイプラインは `Disproved`（含意不成立）を返す → コンパイルエラー：

> パラメータ `b` が `divide` 呼び出しで `Positive` を満たすことを証明できない。`y`
> は関数入力から来ており、証明済みの境界がない。if 分岐ガード呼び出しの使用を検討：`if y > 0 { divide(x, y) }`。

YaoXiang は静的証拠を提供せずにランタイム値が精錬型パラメータに直接入ることを許可しない。これは制限ではなく——これはハード安全性哲学の中核である。コンパイラが静的に証明できないコードは、コンパイルを通してはならない。

#### 3.5 統一パイプラインとの関係

パス条件伝播は追加のメカニズムではない。これはコンパイル時証明パイプラインの制御フロー解析上の直接の拡張である：

| 段階                 | 責務                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| パス条件収集         | コンパイラ制御フロー解析段階、各基本ブロックに仮定セットを注釈                                                                       |
| 検証条件生成         | 検証が必要な型制約に遭遇したとき、パス条件 + 実引数型情報をマージ                                                                    |
| 証明パイプライン評価 | コンパイラカーネル → SMT 加速 → Proved / Disproved / Unproven を得る                                                                 |
| 結果                 | `Proved` → 合格；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未解決命題（プログラマは証明関数を提供可能） |

新しい部品はない。特殊なルールもない。パス条件は証明パイプラインの背景知識である——型等価、借用制約と同じパイプライン、同じ予算システムを共有する。

### 4. コンパイル時証明パイプライン

すべてのコンパイル時検査は同じパイプラインを共有する。パイプラインの核心操作は**型検査**である——証明項の型が証明されるべき命題と等しいかをチェックする。すべてが型検査である。

```
コンパイル時に Bool 式を評価する必要がある（即ち：証明項を構築する必要がある）
        │
        ├── 型等価（T1 == T2）
        │   → コンパイラが直接判定（構造等価）
        │
        ├── トークン衝突条件（!conflicting(tokens)）
        │   → フロー敏感活性解析（Duplicate/Linear 属性追跡）
        │
        ├── 依存型簡約（n + m 簡約）
        │   → コンパイル時項書き換えシステム（βδι-簡約）
        │
        ├── コンパイル時述語（x > 0, forall...）
        │   → コンパイラ自身 + SMT 加速モジュール
        │
        └── ホーア論理含意（P ⇒ Q）
            → コンパイラ + SMT 加速モジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル成功
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未解決命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を記述（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル成功
                  │
                  ▼
            検証失敗 → コンパイルエラー："証明が成立しない"
```

#### 4.1 証明結果：三値代数

コンパイル時評価は三つの結果を返す——これは停止問題の必然的結論であり、証明論の自然な分割でもある：

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項が構築済み、型検査合格。コンパイル続行。
- **Disproved(M)** → 停止、反例 M が存在。コンパイルエラー + 反例 + ソースコード位置。
- **Unproven**
  → 与えられたリソース上限内で証明が構築されていない。コンパイルエラー + 未解決命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言うのは命題が偽であることと同義ではない——現在の自動証明能力を超えているだけである。これは正直なことであり、欠陥ではない。

予算ハード制限は停止問題の工学的解である。ノブは提供しない——提供すれば「あなたのプログラムは停止すると思うか」とユーザーに尋ねることになり、ユーザーもコンパイラも知らない。

#### 4.2 Unproven の後：プログラマが証明を記述

コンパイラが Unproven を返すとき、プログラマは**証明関数**を記述できる——これは YaoXiang 関数であり、その戻り型は証明されるべき命題に等しい。型検査器がこの関数を検証する——`add(a, b): Int`
を検証するのとまったく同じメカニズムで。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼ルート）
```

SMT ソルバーは独立した信頼境界ではなく——**型検査器の加速モジュール**である。SMT は証明を見つけるのを手伝うが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返すとき、コンパイラはその結果を型検査器が検証可能な証明項に再構成する。再構成が失敗した場合（SMT の推論ステップがコンパイラカーネルの推論規則を超える）、Unproven にフォールバックする——プログラマは手動で証明関数を記述できる。

```yaoxiang
# 命題：コンパイラが自動証明できない精錬属性
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明：プログラマが関数を記述し、戻り型は上記の命題
# 型検査器がこの関数を検証する——add(a,b): Int の検証と完全に一致
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラはここで検証：関数本体の型 = FirstIsMin(T, arr)
    ...
}
```

AI も不要、Coq へのエクスポートも不要、新しい概念も不要。**コンパイル時に自動証明できない属性 → プログラマが YaoXiang コードで証明を記述 → 型検査器が検証。**
プロセス全体は滑らかなグラデーションである——コンパイラが簡単な証明を代行し、難しいものは頭を使う。

#### 4.3 パイプライン内の階層的依存

上記の評価器は同じインターフェースを共有するが、評価順序が存在する。型等価はすべての後続解析の前提条件；所有権/トークン検査は型情報に依存する；精錬述語検証は前 2 層の結果に依存する。コンパイラは層ごとに評価し、基盤層で失敗した式は上位層に入らない——型エラーのあるプログラムで解決予算を浪費することを避ける。

```
評価順序（同一パイプライン、階層的スケジューリング）
├── 第 0 層：型等価（T1 == T2）
│   └── 構造単一化 → 失敗なら後続は無意味、直接 Disproved を返す
├── 第 1 層：所有権/トークン衝突
│   └── フロー敏感活性解析 → 失敗ならメモリ安全性が成立しない、直接 Disproved を返す
└── 第 2 層：精錬述語/ホーア含意
    └── コンパイラ自身 → SMT 加速 → Proved / Disproved / Unproven を得る
```

各層は依然として `Proved/Disproved/Unproven`
を返し、同じインターフェースと同じ予算システムを共有する。

### 5. 三層関数の統一

| 階層             | 実行タイミング | 入力  | 出力 | 例                                             |
| ---------------- | -------------- | ----- | ---- | ---------------------------------------------- |
| 値レベル関数     | ランタイム     | 値    | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時   | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時   | 値    | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

すべて同じ `name: type = value`
構文を使用。コンパイル時述語と型コンストラクタは同じコンパイル時証明パイプラインを経る——`{}`
は証明空間である。

### 6. ループ：Floyd-Hoare 検証条件生成

ループは個別の `: Invariant(...)` や `: decreases(...)`
注釈を必要としない。可変変数上のコンパイル時述語型注釈が Floyd-Hoare スタイルのアサーションを定義する——コンパイラは型注釈から検証条件を生成し、証明パイプラインが各代入が型を維持するかをチェックする。

核心メカニズム：各代入操作は Hoare 三つ組 `{P} x := e {Q}` に対応し、検証条件は `P ⇒ Q[e/x]`
である。コンパイラはループ本体に対して一度検証条件を生成する——証明パイプラインが帰納ステップの成立を検証した後、すべての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照；初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証：0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラはループ本体に対して一度 VC を生成。前提：s は SumUpTo(arr, i) を満たし、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]：
        #   検証義務：s_new は SumUpTo(arr, i) を満たす（現在 i は不変）
        #   s_new = s_old + arr[i] を代入：
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮説 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える：
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT：線形算術、ミリ秒オーダー → Proved
        #
        # i += 1：
        #   i 変更 → 依存図で s の型注釈が i を参照 → 再検証をトリガー
        #   新しい検証目標：s は SumUpTo(arr, i_new) を満たす
        #   即ち s == sum(arr[0..i_new])、前ステップで保証済み → Proved
        s += arr[i]
        i += 1
    }
    return s  # この時点で s: SumUpTo(arr, arr.len)、即ち s == sum(arr[0..arr.len])
}
```

ループ不変条件は変数上の型注釈である——プログラマが型を記述し、コンパイラが帰納ステップをチェックする。コンパイラは不変条件を「発見」する必要も、自動的に「帰納を行う」必要もない——帰納証明を各代入操作の局所検証条件に分解し、証明パイプラインに分割して委ねる。

#### 6.1 依存追跡：可変変数上の依存型

上記メカニズムの前提は、コンパイラが `s` の型注釈 `SumUpTo(arr, i)` が `i`
を参照していることを知っていることである——`i` が変更されたとき、`s`
の型制約もそれに応じて変化する。これにはコンパイラが**変数間の型依存グラフ**を維持する必要がある。

**データ構造**：

```
TypeDepGraph: Map<VarName, Set<VarName>>
# キーは依存される変数、値は型注釈内でその変数を参照している変数の集合
# 例：{ i: {s}, j: {s, t}, ... }
```

**構築**：型検査器が `mut v: Pred(... x ...) = init` を処理するとき、`Pred(...)`
パラメータ内の自由変数参照を解析する。パラメータが現在のスコープ内の他の可変変数 `x`
を参照する場合、依存図に `x → v` を記録する。

**トリガー**：依存される変数 `x` が代入されるとき、コンパイラ：

1. 依存図内で `x` に依存するすべての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` について、検証条件を生成：`v の現在値が更新された型 Pred(... x_new ...) を満たすか`
3. VC を証明パイプラインに送る

**代入順序依存**：依存追跡は正しい代入順序を自然に強制する。`SumUpTo(arr, i)` を例に：

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証 → True

# 誤った順序——コンパイラが拒否
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証
              # s はまだ更新されていない、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー：変数 s は型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**組み合わせ依存**：1 つの変数が複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は `x` と
`y` の両方に同時に依存する——いずれの変更も再検証をトリガーする。

**証明パイプラインとの関係**：依存追跡は VC 生成のトリガーであり、独立した検証メカニズムではない。それは「いつ VC を生成する必要があるか」に答え、証明パイプラインは「VC が成立するか」に答える。

### 7. 停止性検査

コンパイル時完全自動。コンパイラが証明できるループは通過し、証明できないものは直接コンパイルエラーを報告する——プログラマはコンパイラにループの停止性を自動解析させなければならない。半自動注釈のための余地は設けない。

#### 6.1 設計原則

コンパイラは 2 箇所から停止証明に必要な情報を自動抽出する：

1. **変数型注釈**：精錬型内の境界制約（例：`UpTo(n)` は上界 `n` と下界 `0` を与える）
2. **ループ本体操作**：各反復で変数に適用される操作

コンパイラは優先順位に従って 4 つの度量合成戦略を試し、見つかれば停止する。

#### 6.2 戦略 1：線形ランク関数自動合成

変数に線形境界注釈がある場合、コンパイラは候補線形度量を列挙し SMT 検証する。

```
入力：
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（境界を持つ変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム：
  1. 型注釈から各変数の境界を抽出：[low_i, high_i]
  2. 候補度量を列挙：v_i, u_i - v_i, v_j, 等の線形結合
  3. 各候補度量 m について：
     - SMT 検証 m ≥ 0（型境界から導出）
     - ループ本体の各実行パスについて、SMT 検証 m' < m（厳密減少）
  4. 条件を満たす線形結合を見つける → 停止証明済み
```

カバー範囲：変数が線形式（`v = a·v + b`）に代入され、境界型注釈を持つ任意のループ。`i += const`、`i -= const`、および二分探索型の区間収縮を含む：

```yaoxiang
# 二分探索：low = mid + 1 または high = mid
# 度量 high - low は両パスで厳密に減少
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2：述語違反カウント——目標型から自動抽出度量 <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在の状態：実験的戦略、段階 3 実装時に実際の実現可能性に応じて含有を決定。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効だが、非隣接操作（クイックソート partition、ヒープソート sift-down）は自動証明できない。カバー境界は下表参照。段階 3 検証が実現不可能と判明した場合、この戦略は削除されるか将来の作業に降格される。

核心的洞察：**ユーザー記述の仕様がコンパイラ推論の素材。**
コンパイラは「ソートとは何か」を内蔵する必要はない——`Sorted`
の定義を読み、定義から自動的に度量を抽出する。

```
入力：
  目標型：Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体操作：隣接要素交換

アルゴリズム：
  1. 述語定義を解析：forall i in range: cond(i, arr)
  2. 自動生成度量：violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作が度量に与える影響を分析：
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の 3 対のみに影響
     - arr[j] > arr[j+1]（述語違反）の場合、交換後この対は述語を満たす
     - violation_count は少なくとも 1 減少
  4. 上界：n·(n-1)/2（最大隣接逆序数）、下界：0
  → 停止証明済み
```

**現在のカバー範囲**：

| アルゴリズム   | 操作パターン   | 戦略 2 で証明可能？ | 理由                                    |
| -------------- | -------------- | :-----------------: | --------------------------------------- |
| バブルソート   | 隣接交換       |         ✅          | violation_count は交換ごとに厳密減少    |
| 挿入ソート     | 隣接移動       |         ✅          | 各シフトが違反対を 1 解消               |
| 選択ソート     | 非隣接交換     |         ❌          | 単一交換で violation_count 増加の可能性 |
| クイックソート | partition 分割 |         ❌          | 非隣接交換、単調減少を保証しない        |
| ヒープソート   | sift-down      |         ❌          | ツリー操作、violation_count は非単調    |

**補完戦略**：クイックソートの場合、`low < high`
区間収縮は戦略 1（線形ランク関数）でカバーできる——外層の partition 再帰、各反復で区間が半分になる。戦略 1 と戦略 2 は補完的にカバーし、実際のアルゴリズムの大多数はどちらかで停止性を証明できる。ただし戦略 2 の汎用化（非隣接操作、ツリー操作）は依然として未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3：有界増減パターン

`v += const`（正の定数）、変数が上界型注釈を持つ → 度量 `upper_bound - v` は毎回 `const`
ずつ減少、下界 0。これは戦略 1 の縮退ケースであり、コンパイラは最初に高速処理する。

#### 6.5 戦略 4：乗法的スケール度量テンプレート

`v *= const`（const > 1）、変数が上下界型注釈を持つ。コンパイラは対数目量テンプレート
`ceil(log_const(upper/v))` を内蔵し、毎回 const を掛けると度量が 1 減少する。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラが自動推論：度量 ceil(log₂(n/i))、毎回 2 を掛けると度量が 1 減少
    i *= 2
}
```

#### 6.6 停止性と正当性の分離

停止性証明と正当性証明は独立している：

- **停止性**：上記の 4 つの戦略がループが有限ステップで終了することを自動証明
- **正当性**：ループ本体が目標型に向かって進むかは、コンパイル時証明パイプラインが検証条件チェックで判定

両方が通過 → コンパイル成功。停止性は証明されたが正当性が失敗 → コンパイルエラー + 反例。正当性は証明されたが停止性が証明できない → コンパイルエラーで分析不能な変数または操作を指摘。両方が失敗 → コンパイルエラーで 2 つの失敗理由を別々に報告。

#### 6.7 再帰関数の停止検査

コンパイル時に評価が必要な再帰関数について、コンパイラはパラメータの減少をチェックする：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # コンパイラ解析：n-1 < n → 減少 → 停止
}

# コンパイル時使用——コンパイラは factorial のコンパイル時停止を保証
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120、コンパイル時完了
```

| シナリオ                                    | 動作             |
| ------------------------------------------- | ---------------- |
| コンパイラが再帰減少を分析可能（例：`n-1`） | コンパイル時評価 |
| 減少しない / 減少判定不能                   | コンパイルエラー |
| ランタイム呼び出し（型位置でない）          | 停止検査不要     |

#### 6.8 ハード境界

`i = f(i)` かつ `f`
が不可逆、閉じていない、単調性を保持しない——数学的に自動停止証明は不可能。コンパイルエラー：

> このループは自動停止証明ができない。ループ変数が分析不能な関数 `f`
> に依存している。コンパイラが分析可能な反復パターンを使用してください。

これはコンパイラの失敗ではない。静的に安全性を証明できないコードは、コンパイルを通してはならない。

### 8. SMT ソルバー：型検査器の加速モジュール

SMT ソルバーは従来の言語では外部ツール（F\* が Z3 を呼び出す、Dafny が Z3 を呼び出す）である。YaoXiang では、**型検査器の加速モジュール**である——コンパイラカーネル自身が直接判定できない場合のみ呼び出される。SMT は証明を見つけるのを手伝うが、証明を検証するのは型検査器である。

**信頼モデル**：型検査器が唯一の信頼ルート。SMT ソルバーは加速モジュールである——証明を見つけるのを手伝うが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny 路線と一致——Z3 が誤る確率はコンパイラ自身のバグ率より低く、これは工学的実務的選択）。真の信頼性制御は SMT 翻訳層にある——翻訳にバグがあれば、コンパイラは他のテストで露呈する。

**インターフェース**：コンパイラ内部で SMT-LIB
2.6 標準形式に翻訳し、特定のソルバー API に縛られない。SMT-LIB は ISO 標準であり、Z3、CVC5、MathSAT、Yices すべてネイティブサポート。

**デフォルトバックエンド**：Z3（MIT ライセンス、最も広範なドキュメントとコミュニティ検証）。CVC5 は SMT-LIB 互換の代替——ユーザーはコンパイル時にコンパイラフラグで切り替え可能。

「汎用ソルバー抽象層」は作成しない——SMT-LIB が抽象層である。将来 CVC5 が特定理論でブレークスルーを達成した場合、切り替えはバイナリを交換するだけでよく、コンパイラコードの変更は不要。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造等価、単純算術、
        │   定数畳み込み後の平凡な公式）
        │   → 直接 Proved / Disproved を返す
        │
        └── コンパイラカーネルが直接判定不能（量詞、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB 形式に翻訳
            → Z3/CVC5 に送信（予算制限付き）
            → 戻り値：unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**ソルバー予算——ハード制限、スタック深度のように**：

| 予算次元               | デフォルト値 | 説明                                                                                                                           |
| ---------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| ソルバーステップ       | 10,000       | Z3 は線形算術に対して通常 100 ステップ以内。10,000 ステップで実用述語の 99% をカバー。                                         |
| 時間                   | 100ms        | 単一述語が 100ms 超 = ユーザーが型注釈ではなくコンパイル時プログラムを書いている。100ms × 50 述語 = 5 秒のコンパイル時間上限。 |
| 量詞インスタンス化深度 | 3            | 3 層ネスト量詞で実用パターンをカバー。3 層超は論理パズルを書いている可能性が高い。                                             |

予算超過は Unproven を返し、コンパイルエラー + 述語位置 + 消費量。降格なし、ランタイムチェックなし、サイレント合格なし。

**なぜこれが実際に可能か**：工学的に実用述語の 95% は線形算術である——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——すべて決定可能フラグメント内にあり、SMT ソルバーはこのような問題に対してミリ秒オーダーで返す。予算を超える複雑な述語の稀なケースに遭遇した場合、プログラマは証明関数を記述すればよい。

依存型は SMT 呼び出し前に事前簡約層を経る：`factorial(5)`
は直接コンパイル時に 120 に評価され、`append([1,2], [3])` は直接 `[1,2,3]`
に評価される。これらの確定的な値計算は SMT 予算を消費しない。

プログラマは SMT の存在を知る必要はない。メンタルモデルは：**コンパイラが証明できれば通過、できなければエラー——コンパイラがわからない場合は、証明する関数を書いて見せる。**

### 9. コンパイル時述語の組み合わせ

コンパイル時述語は Type を返す関数であり、組み合わせは関数組み合わせで自然に実現される：

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算安全性

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラ検証 Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ コンパイラ検証 Positive(0) = { 0 > 0 } → False
```

#### 9.2 配列アクセス安全性

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラ検証 InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ コンパイラ検証 InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 ソート正当性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ：コンパイラ VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 分派パイプライン：コンパイル時とランタイムの統一分派

`assert` と `Assert` は同じ精錬型原語の二面である。分派パイプライン `dispatch`
は**述語の自由変数がコンパイル時に到達可能か**によって、コンパイル時証明とランタイムチェックのいずれを採るかを自動決定する：

| 基準                                                                           | モード          | 動作                                                                                |
| ------------------------------------------------------------------------------ | --------------- | ----------------------------------------------------------------------------------- |
| すべての自由変数がコンパイル時既知（ジェネリックパラメータ、コンパイル時定数） | **CompileTime** | 証明パイプラインへ：Proved → 消去、Disproved → コンパイルエラー、Unknown → 証明要求 |
| 自由変数がランタイムから来る（関数パラメータ、外部入力、mut 変数）             | **Runtime**     | ランタイム check を挿入し、フロー敏感仮定セット Γ に精錬事実を注入                  |

**重要**：「判定不能」≠「反証」。CompileTime モードの Unknown は証明を要求する（暗黙の降格なし）、Runtime モードでは命題はコンパイル時に真偽を持たない——prover がどれほど強くても「ユーザーが負数を入力したかもしれない」に対して恒真証明は書けない、ランタイム check が唯一の sound な選択である。これは prover が弱いからではなく、理論的必然である。

### 12. フロー敏感仮定セット Γ：最強後件条件伝播

コンパイラはフロー敏感（flow-sensitive）仮定セット Γ を維持し、各制御フロー点で既知の成立する命題を追跡する。

**SP（最強後件条件）伝播**：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**：`mut`
変数が再代入された後、その変数に関するすべての仮定が Γ から削除される：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

これは soundness のハード要求である——変数の値が変わったため、旧仮定は無効。

**分岐合流**：IF/ELSE または match 分岐が合流するとき、Γ は各分岐の仮定の交差を取る。すべてのパスで成立する命題のみが分岐外に渡される。

### 13. 消去モデル明確化：witness 消去 ≠ check 消去

RFC-027 の「精錬型はランタイムに**完全消去**される」という主張は、**proof
witness（証明トークン）**を指す——コンパイル時に検証済みの証明項はランタイムコードを生成しない。ただし Runtime モードで dispatch が挿入する
**ランタイム check**
は保持される——これは値レベルで実行される Bool チェックであり、型レベルの witness ではない。

まとめ：witness 消去、check 保持。2 つの事柄は競合せず、RFC-027 の元の主張は不変である。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以後（本 RFC）                                                  |
| ------------------------------------- | --------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語はパラメータ型として `(b: Positive(b))`         |
| `//! ensures: ExistsMax(result, arr)` | 戻り型は戻り値仮引数を使用 `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変条件            |
| `//! decreases: n`                    | コンパイラ全自動導出度量関数                                    |
| 仕様はコメント                        | 仕様は型システム                                                |

### 構文

**コンパイル時述語に新しいキーワードはない。** `{}`
は証明空間であり、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数である——`name: (params) -> Type = { アサート }`。使用時は関数呼び出し——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証するアサート
# 既存関数/型構文を使用、新規 BNF ルール不要
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**新規構文概念：戻り値仮引数**——`-> (name: Type)` の `name` は戻り値仮引数。

戻り値仮引数は YaoXiang が既存関数構文に導入する**唯一の構文概念**。そのセマンティクス：

- `name` の値は `return` 文から提供される
- `name`
  は型シグネチャ内にのみ存在し、事後条件述語から参照される（例：`-> (result: IsMax(T, arr, result))`）
- `name` は関数本体のスコープに入らず、呼び出し側にも現れない
- 戻り値仮引数は**オプション**——事後条件がないときシグネチャは通常関数と完全に一致する（`-> Int`）、追加負担なし

導入理由：事後条件は「関数が返そうとしている値」を参照する必要がある。戻り値仮引数がない場合、コンパイラは述語に戻り値を参照させるために特殊ルール（暗黙変数
`$result` や `__retval__`
など）に頼るしかない。戻り値仮引数はこの参照を明示化する——それは単なる仮引数であり、値が呼び出し側ではなく
`return` から提供される点が異なる。

**証明関数**は新しい概念ではない——それは YaoXiang 関数であり、その戻り型はアサートされる命題である。コンパイラが Unproven を返すとき、プログラマは証明関数を提供し、型検査器は任意の関数の戻り型を検証するのとまったく同じ方法でそれを検証する。新しい構文、新しいキーワード、新しいルールは不要。

### 型システムへの影響

- **型宇宙**：コンパイル時述語は Type₂ 層に位置する——値を受け取り Type を返す関数、型コンストラクタと同じ階層
- **ジェネリクス相互作用**：コンパイル時述語はジェネリックパラメータを取れる、例：`NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **所有権相互作用**：コンパイル時述語内の式は所有権ルールに従い、読み取りのみ、書き込み不可
- **型推論**：コンパイル時述語のパラメータは HM 型推論に参加する

### ランタイム表現

コンパイル時述語はランタイムに**dispatch 分派結果に応じて処理される**：

- **CompileTime モード**（すべての自由変数がコンパイル時既知）：証明通過後、witness トークンは完全に消去される。`Positive: (x: Int) -> Type = { x > 0 }`——パラメータ
  `b: Positive(5)` のランタイム表現は `Int` そのもの。精錬条件 `{ 5 > 0 }` は通過済み、消去。
- **Runtime モード**（ランタイム自由変数が存在）：ランタイム check を保持——値レベルで Bool チェックを実行し、フロー敏感仮定セット Γ に注入。詳細 §11
  dispatch 分派パイプラインと §13 消去モデル明確化参照。

コンパイル時述語を型位置に置く（例：`f(x: Positive(x))`）はラッパー型を生成せず、追加メモリを割り当てない。ただし
`x` がランタイム入力から来る場合、**ランタイム Bool チェックが挿入される**。

**`ref`
との相互作用制約**：コンパイル時述語は不変借用または所有権が既に移動された値のみ参照できる。可変借用を参照するコンパイル時述語は、コンパイラがコンパイル時に検証結果がランタイムでも成立することを保証できない——このような使用法は直接コンパイルエラーを報告する。

### コンパイラ変更

1. **パーサー**：コンパイル時述語は標準関数構文を使用、追加解析ルール不要
2. **コンパイル時証明パイプライン**：Proved/Disproved/Unproven 戻りインターフェース統一、自動戦略選択
3. **SMT 加速モジュール**：SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**：推論規則実装——構造等価、βδι-簡約、全称量詞導入/除去。これが唯一の信頼ルートであり、SMT とプログラマ証明はどちらもこれを通じて検証される
5. **検証条件生成**：WP/SP 計算 + ループ不変条件証明義務
6. **エラー報告**：反例フォーマット化 + 未解決命題レポート + ソースコード位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用しないコードは完全に不変
- ✅ コンパイル時述語は CompileTime モードでランタイムオーバーヘッドゼロ、Runtime モードで必要な Bool チェックのみ保持
- ⚠️ RFC-022 の `//!` 構文はサポートされない——ただし 022 は一度も実装されておらず、移行負担なし

## トレードオフ

### 利点

- **Curry-Howard 同型を完全に実現**：型が命題、プログラムが証明、`name: Proposition = Proof`
- **統一性**：コンパイル時述語と通常関数は完全に同じ構文を使用、概念分裂なし
- **SMT 透過的**：プログラマは SMT の存在を知る必要がなく、メンタルモデルは型検査と一致
- **漸進的採用**：1 つのコンパイル時述語から始めて、カバレッジを段階的に拡大可能
- **最小ランタイムオーバーヘッド**：CompileTime モードゼロオーバーヘッド、Runtime モードは必要な Bool チェックのみ保持

### 欠点

- **コンパイル時間**：SMT ソルバーがコンパイル時間を増加させるが、予算ハード制限が上限を制御可能に保証
- **自動証明境界**：一階線形算術を超える複雑な述語はプログラマの証明関数を必要とする可能性。これは言語欠陥ではなく——停止問題の必然的結論である。コンパイラは True/False を偽装せず、Unproven を誠実に報告する
- **学習曲線**：効果的なコンパイル時述語と証明関数の記述には Curry-Howard 同型の基本直感の理解が必要
- **実装複雑性**：コンパイル時証明パイプラインの統一には精巧な設計が必要

### リスク軽減

- SMT ソルバー予算ハード制限（ステップ 10,000 / 時間 100ms
  / インスタンス化深度 3）、予算超過は Unproven を返す
- 依存型事前簡約：確定的な値計算を先に消費、SMT は非確定部分のみを処理
- Unproven は行き止まりではない：プログラマは証明関数を記述可能、型検査器が検証——任意の関数の戻り型検証と一致
- 増分検証：変更モジュールのみ検証
- 明確なエラーメッセージ + 反例表示 + 予算消費レポート + 未解決命題 + 提案（コンパイラが提供可能な場合）

| **本方案：コンパイル時述語を一級市民として** | ✅                                                                                                                      |

## 未解決問題

- [x] **SMT ソルバー選択**：デフォルト Z3（MIT ライセンス、最も広範に検証済み）。CVC5 は SMT-LIB 互換代替としてコンパイラフラグで切り替え。コンパイラ内部翻訳目標は SMT-LIB
      2.6 標準形式——SMT-LIB が抽象層、カスタム汎用ソルバーインターフェースは作成しない。
- [x] **ソルバー予算の具体値**：ステップ 10,000 / 時間 100ms
      / 量詞インスタンス化深度 3。コンパイラ内部固定、ノブなし。実際使用中に実際のユースケースで不十分と証明された場合（「ユーザーが間違って書いた」ではなく）調整する。
- [x] **量詞サポート範囲**：言語レベルで量詞階数を制限しない。コンパイル時述語は Type パラメータを受け取る——Type は関数型を含む——したがって高階量詞は型システムの自然な帰結であり、特殊構文は不要。SMT ソルバーは一階量詞（forall/exists、予算深度 3 制限内で交互ネストサポート）を自動判定可能。高階量詞：SMT は Unproven を返し、コンパイラは「この述語は自動証明範囲外、証明関数を提供してください」と通知。プログラマは戻り型が命題に等しい YaoXiang 関数を記述する——型検査器がその関数を検証する。外部エクスポート不要、AI 不要、対話的証明モード不要。すべてが YaoXiang コード、すべてが型検査器で検証。
- [x] **反例フォーマット**：ソース変数名を直接 SMT 変数名として使用（モジュール接頭辞で衝突回避）。Z3 モデル返送時に変数名で逆引き。出力形式：変数名 = 具体値 + ソースコード位置 + 述語定義位置。複雑なマッピング層は作成しない。
- [x] ~~**`ref` スマートポインタとのコンパイル時述語相互作用？**~~
      → 決定済み：コンパイル時述語は不変借用または所有権が既に移動された値のみ許可。可変借用された値はコンパイル時述語に現れない。
- [x] **`forall` 述語違反カウント度量の非隣接操作への拡張？**
      → 拡張しない。現在のカバー範囲（隣接交換、隣接移動）は戦略 1（線形ランク関数）で補完カバーされる——クイックソート外層区間収縮は戦略 1 が担当、ヒープソートは戦略 1（配列インデックスパターン）が担当。どの戦略でも停止性を証明できないループは、コンパイラが直接エラーを報告する——これはハード安全性哲学であり、欠陥ではない。将来（非学術構築の）実シナリオアルゴリズムで 4 戦略すべてがカバーできない場合、再議論する。
- [x] **線形ランク関数列挙の組み合わせ爆発**：候補列挙上限は 3 つの有界変数。≤3 の場合、すべての線形結合を列挙し SMT で逐一検証。>3 の場合、単一変数度量（`v_i`、`u_i - v_i`）のみ試行、失敗時は直接コンパイルエラー——「ループに >3 つの有界変数があり、コンパイラが多変数度量を自動合成できない」とプログラマに通知。これは工学的妥協ではなく——より単純なループを書くことをプログラマに強制するものである。
