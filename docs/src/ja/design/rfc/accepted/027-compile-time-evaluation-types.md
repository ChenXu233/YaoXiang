# RFC-027：コンパイル時述語と統一静的検証

> **参考**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統一型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024：spawn ブロックベースの並行モデル](../accepted/024-concurrency-model.md)
>
> **置き換え**：[RFC-022: ホーア論理静的検証サポート（仕様コメントと仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止済み

## 概要

本文は YaoXiang に**コンパイル時述語**を一級市民として導入し、すべてのコンパイル時静的検証を単一の**証明パイプライン**に統一することを提案する。コンパイル時述語は外部仕様のコメントではなく、それ自体が関数である。Type を返す関数は型位置で使用でき、コンパイラがコンパイル時に呼び出して戻り値を検証する。型が命題であり、コンパイル時評価が証明である。

**核心的論点**：型検査がコンパイル時に行う唯一の作業は、証明項の構築と検証である。型等価性、トークン競合、依存型簡約、コンパイル時述語評価、ホーア論理含意——すべては同じコンパイル時証明パイプライン内の異なる型検査であり、単一のパイプラインを共有する。SMT ソルバは型検査器の加速モジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返すとき、プログラマは YaoXiang 関数を証明として記述する——型検査器は他の関数の戻り型を検証するのと完全に同じ方法でそれを検証する。すべてが YaoXiang コードであり、すべてが型検査器によって検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 は仕様を `//!` コメント形式として設計していた：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← 型とは独立したコメント
    //! ensures: ExistsMax(result, arr[0..n])   ← 型とは独立したコメント
}
```

これは Curry-Howard 同型の根本的な誤りを犯している：**仕様と型を二つの層に分裂させる**こと。コメントは型ではない。コメントは型検査に参加しない。コメントは「外部ツール」のメンタルモデルである。

ホワイトペーパーは明確に述べている：

> "`//!` コメントはない。独立した仕様言語もない。すべてが型システムの中にある。"

### 現在の問題

- RFC-022 の `//!` コメントは型システムから独立した外部構文
- 仕様型と通常の型は二体系であり、概念的な冗長性を生む
- Debug Build 検証 / Release Build 無視の分裂モデルが統一性を破壊する
- SMT ソルバは従来の認識では外部ツールとして位置づけられている——YaoXiang はそれを型検査器の加速モジュールとして内蔵する
- 型検査、借用検証、コンパイル時述語検査、マクロ展開がそれぞれ異なる経路を辿る

### 正しいメンタルモデル

型検査は関数として抽象化できる：

```
verify : Program → Proved | Disproved(Model) | Unproven
```

すべてのコンパイル時検査——単純な型マッチング、借用競合検出、コンパイル時述語検証——はこの関数のサブタスクである。それらは同じ証明パイプラインを共有し、違いは証明項の複雑さと構築戦略のみにある。

コンパイラが Unproven を返すとき、プログラマは証明関数を提供する——その関数の戻り型は証明すべき命題と等しい。型検査器がそれを検証する。これは通常の型検査と同じ操作である。

## 提案

### 1. `{}` は証明空間：型がアサーション、検証が型検査

YaoXiang の `{}`
はコンパイル時証明空間である。その中にあるものはすべてアサーションであり、コンパイラは各項目が True であることを保証する——自動証明されるか、プログラマが証明関数を提供するかのいずれかである。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  コンパイラは x が Float であること、y が Float であることを保証する

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  コンパイラは data が Array(T) であることを保証する
```

**ジェネリクスはコンパイル時述語の特殊ケースである。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          シグネチャでのパラメータ    {} 内にはアサーションのみ
#          コンパイラはコンパイル時に呼び出して x > 0 を検証する

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      シグネチャでのパラメータ    コンパイラは type_of(T) == Type、type_of(data) == Array(T) を検証する
```

同じパターン：`name: (params) -> Type = { アサーション }`。コンパイラは「型アサーション」と「値アサーション」を区別しない——どちらも証明パイプライン内の評価対象である。

**ループ不変条件は別途記述する必要がない。変数上の型注釈がそのまま Floyd-Hoare 不変式である。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照する——s の型が i に依存することをコンパイラに伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラ検証：s_new == sum(arr[0..i+1])
        i += 1       # i 変更→s の依存再検証をトリガー：s は SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度だけ検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新しい値が型注釈を満たすか。証明パイプラインが帰納ステップの成立を検証すれば、すべての反復が自動的にカバーされる。`: decreases`
も、`: Invariant` も、帰納証明も必要ない——コンパイラは帰納を各代入の局所 VC に分解する。

### 2. 事前/事後条件：パラメータ型と戻り型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures`
を廃止する。コンパイル時述語はパラメータまたは戻り値の型注釈として機能する。

**パラメータ側は関数呼び出しである。**
コンパイル時述語は Type を返す関数であり、パラメータ側での使用方法はそれを呼び出すこと——`factorial(5)`
と同じである。戻り値側は新しい概念を導入する：戻り値仮パラメータ。

```yaoxiang
# 事前条件：パラメータ型で明示的にコンパイル時述語を呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在の仮パラメータ名、Positive の引数として渡される
#                       コンパイラは呼び出し点で実引数値を抽出し、b に代入し、Positive(実引数) を検証する
#                       例：divide(10, 2) → Positive(2) = { 2 > 0 } を検証 → True
#                       例：divide(10, 0) → Positive(0) = { 0 > 0 } を検証 → False → コンパイルエラー

# 事後条件：戻り値仮パラメータ + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は戻り値仮パラメータ、値は return によって提供される
#                                            コンパイラは return 点で戻り値を代入し、事後条件を検証する
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要なルール**：

- **パラメータ側**：`b: Positive(b)` —— `b` は現在の仮パラメータ名であり、`Positive`
  の引数として渡される。関数呼び出し構文、ゼロ暗黙。
- **戻り値側**：`-> (result: IsMax(T, arr, result))` —— `result` は戻り値仮パラメータであり、値は
  `return` 文によって提供される。`result`
  は型シグネチャ内にのみ存在し、述語によってのみ参照され、関数本体のスコープには入らず、呼び出し側にも現れない。
- **戻り値仮パラメータはオプション**：事後条件がない場合は記述せず、シグネチャは通常の関数と完全に一致する（`-> Int`）。
- **統一性**：パラメータと戻り値仮パラメータは同じ概念である——`仮パラメータ名: 述語呼び出し(仮パラメータ名)`。違いは値が呼び出し側から提供されるか、`return`
  から提供されるかのみ。

### 3. パス条件伝播：実行時値のコンパイル時検証

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマが明示的に渡す。実行時値が精錬型パラメータに入るとき、コンパイラはパス条件収集と SMT 含意判定を通じて検証を完了する——プログラマが明示的に証明を渡す必要はない。

#### 3.1 明示的な関数呼び出し

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマが明示的に渡す——関数呼び出しであり、暗黙性ゼロ。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。束縛位置（パラメータ宣言、変数宣言、戻り型）に現れるとき、プログラマは明示的に既に束縛されている変数名を渡す：

```yaoxiang
b: Positive(b)
// b は現在の仮パラメータとして既に宣言されており、Positive(b) は関数呼び出し
// 正規化後：b: { b > 0 }
```

コンパイラが暗黙的にパラメータを埋める必要はない——`b: Positive(b)` は `f(5)`
と同じく、関数呼び出しである。`b` はパラメータ名として束縛され、その型注釈 `Positive(b)` は `b`
自身を参照する——これは依存型の標準パターンであり、暗黙の展開ルールではない。

**RFC-010 の `self` との統一**：RFC-010 は `self`
がキーワードではなく、パラメータ名の慣習に過ぎないと確立した（"`p`、`this`、`x`
と書いても効果は完全に同じ"）。`b: Positive(b)`
は同じメカニズムを共有する——パラメータ名は型注釈内で参照可能。`self` は `self: Point`
の位置に現れ、`b` は `b: Positive(b)`
の位置に現れる。両者の型注釈はどちらもパラメータ自身を参照する。違いは型注釈の複雑さのみであり、メカニズムは完全に同じである——名前が束縛された後、型はその名前に依存できる。

戻り型も同様に明示的な関数呼び出しを使用する：

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は戻り値仮パラメータ、Sorted(result) は関数呼び出し
//                        コンパイラは return 点で戻り値を result に代入し、Sorted(戻り値) を検証する
```

局所変数宣言にも同様に適用される：

```yaoxiang
let x: Positive(x) = 5
// x は 5 に束縛され、Positive(5) → { 5 > 0 } → True → 通過

// let y: Positive(y) = 0
// y は 0 に束縛され、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 パス条件収集

実行時値が条件分岐に現れるとき、コンパイラは自動的にパス条件を収集し、現在のスコープの**仮定集合**を形成する。これらの仮定はコンパイル時 Bool 評価の背景知識として検証に参加する。

```yaoxiang
if y > 0 {
    // コンパイラはこの分岐内で自動的に仮定を取得：{ y > 0 }
    let result = divide(x, y)
    // 検証条件：(y > 0) ⇒ (y > 0)
    // 証明パイプラインは含意が成立すると判定 → Proved
} else {
// この分岐の仮定：{ !(y > 0) }
// divide(x, y) を呼び出す場合、検証条件は !(y > 0) ⇒ y > 0
    // 証明パイプラインは含意しないと判定 → Disproved
}
```

これはコンパイラが特定のモードをハードコードしているわけではない——これはコンパイル時証明パイプラインの自然な動作である。各型検査呼び出し点はパイプラインに以下を送信する：

```
{背景仮定} ⇒ {検証対象}
```

証明パイプラインは含意性を判定する。Proved → 通過、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未解決命題。背景仮定は現在のプログラム点のパス条件から得られる。

#### 3.3 仮定スタック

コンパイラは制御フロー解析において、各基本ブロックに対して仮定集合を維持する：

- **if-guard**：`if y > 0` → true 分岐に `y > 0` をプッシュ、false 分岐に `!(y > 0)`
  をプッシュ（else を使用する場合）
- **match パターン**：`if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **論理結合**：`if x > 0 and y < 10` → 分岐内に `x > 0` と `y < 10` をプッシュ
- **関数事前条件**：`divide(a, b)` を呼び出すとき、`b` が `Positive`
  の証拠を持つことは、現在の仮定、または実引数自身の精錬型注釈（`b` が `Positive`
  として既に注釈されている場合、その型は `b > 0` を運ぶ）から得られる
- **代入**：`let z = y` のとき、`y` 上の既存の精錬条件が `z` に伝播する

すべての仮定はコンパイル時証明パイプラインに入る。SMT 加速パスに入るとき、SMT-LIB 背景アサーションに変換される。

#### 3.4 静的証拠なしはコンパイルエラー

プログラマが直接以下のように書いた場合：

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム点に `y > 0` の仮定がなく、実引数 `y` 自身にも `Positive` 型注釈がない。検証条件は：

```
{} ⇒ { y > 0 }
```

パイプラインは `Disproved`（含意しない）を返す → コンパイルエラー：

> パラメータ `b` が `divide` 呼び出しで `Positive` を満たすことを証明できない。`y`
> は関数入力から来ており、証明済みの境界がない。if 分岐ガードを使用して呼び出すことを検討：`if y > 0 { divide(x, y) }`。

YaoXiang は、実行時値が静的証拠を提供せずに精錬型パラメータに直接入ることを許可しない。これは制限ではなく、ハード安全性哲学の中核である。コンパイラが静的に証明できないコードは、コンパイルを通過できない。

#### 3.5 統一パイプラインとの関係

パス条件伝播は追加メカニズムではない。これは制御フロー解析におけるコンパイル時証明パイプラインの直接的な拡張である：

| 段階                 | 責務                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| パス条件収集         | コンパイラの制御フロー解析段階、各基本ブロックに仮定集合を注釈                                                                       |
| 検証条件生成         | 検証が必要な型制約に遭遇したとき、パス条件 + 実引数型情報をマージ                                                                    |
| 証明パイプライン評価 | コンパイラカーネル → SMT 加速 → Proved / Disproved / Unproven を得る                                                                 |
| 結果                 | `Proved` → 通過；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未解決命題（プログラマは証明関数を提供可能） |

新しい部品はない。特別なルールもない。パス条件は証明パイプラインの背景知識である——型等価性、借用制約と同じパイプライン、同じ予算システムを共有する。

### 4. コンパイル時証明パイプライン

すべてのコンパイル時検査は同じパイプラインを共有する。パイプラインの核心操作は**型検査**である——証明項の型が証明すべき命題と等しいかを検査する。すべてが型検査である。

```
コンパイル時に Bool 式の評価が必要（即ち：証明項の構築が必要）
        │
        ├── 型等価性（T1 == T2）
        │   → コンパイラが直接判定（構造同値）
        │
        ├── トークン競合条件（!conflicting(tokens)）
        │   → フロー感度活性解析（Dup/Linear 属性追跡）
        │
        ├── 依存型簡約（n + m 簡約）
        │   → コンパイル時項書き換えシステム（βδι-簡約）
        │
        ├── コンパイル時述語（x > 0, forall...）
        │   → コンパイラ自身 + SMT 加速モジュール
        │
        └── ホーア論理含意式（P ⇒ Q）
            → コンパイラ + SMT 加速モジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル通過
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未解決命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を記述（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル通過
                  │
                  ▼
            検証失敗 → コンパイルエラー："証明が成立しない"
```

#### 4.1 証明結果：三値代数

コンパイル時評価は三つの結果を返す——これは停止問題の必然的な帰結であり、証明論の自然な分類である：

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項が構築済み、型検査通過。コンパイル継続。
- **Disproved(M)** → 停止、反例 M が存在。コンパイルエラー + 反例 + ソース位置。
- **Unproven**
  → 与えられたリソース上限内で証明が構築されなかった。コンパイルエラー + 未解決命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言うことは命題が偽であることと同義ではない——単に現在の自動証明能力を超えているだけである。これは正直さであり、欠陥ではない。

予算のハード制限は停止問題の工学的解決である。ノブは提供しない——提供すれば「あなたのプログラムは停止すると思いますか」とユーザーに問うことになり、ユーザーは知らず、コンパイラも知らない。

#### 4.2 Unproven の後：プログラマが証明を記述

コンパイラが Unproven を返すとき、プログラマは**証明関数**を記述できる——つまり YaoXiang 関数であり、その戻り型は証明すべき命題と等しい。型検査器はこの関数を検証する——`add(a, b): Int`
を検証するのと同じメカニズムである。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼の根）
```

SMT ソルバは独立した信頼境界ではなく、**型検査器の加速モジュール**である。SMT は証明を見つけるのを手伝うが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返すとき、コンパイラはその結果を型検査器が検証可能な証明項に再構成する。再構成が失敗した場合（SMT の推論ステップがコンパイラカーネルの推論規則を超える）、Unproven にフォールバックする——プログラマは手動で証明関数を記述できる。

```yaoxiang
# 命題：コンパイラが自動証明できない精錬属性
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明：プログラマが関数を記述し、戻り型が上記の命題
# 型検査器がこの関数を検証する——add(a,b): Int を検証するのと完全に同じ
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラはここで検証する：関数本体の型 = FirstIsMin(T, arr)
    ...
}
```

AI も、Coq へのエクスポートも、新しい概念も不要。**コンパイル時に自動証明できない属性 → プログラマが YaoXiang コードで証明を記述 → 型検査器が検証。**
プロセス全体はスムーズな勾配である——コンパイラが簡単な証明を代行し、難しいものはプログラマの頭に任せる。

#### 4.3 パイプライン内の階層的依存

上記の評価器は同じインターフェースを共有するが、評価順序が存在する。型等価性はすべての後続分析の前提条件；所有権/トークン検査は型情報に依存；精錬述語検証は前二層の結果に依存。コンパイラは層ごとに評価し、基盤層で失敗した式は上層に入らない——型エラーのあるプログラムで求解予算を浪費することを避ける。

```
評価順序（同じパイプライン、階層的スケジューリング）
├── 第 0 層：型等価性（T1 == T2）
│   └── 構造単一化 → 失敗すれば後続は無意味、直接 Disproved を返す
├── 第 1 層：所有権/トークン競合
│   └── フロー感度活性解析 → 失敗すればメモリ安全性が成立しない、直接 Disproved を返す
└── 第 2 層：精錬述語/ホーア含意
    └── コンパイラ自身 → SMT 加速 → Proved / Disproved / Unproven を得る
```

各層は依然として `Proved/Disproved/Unproven`
を返し、同じインターフェースと同じ予算システムを共有する。

### 5. 三層関数の統一

| 階層             | 実行時期     | 入力  | 出力 | 例                                             |
| ---------------- | ------------ | ----- | ---- | ---------------------------------------------- |
| 値レベル関数     | 実行時       | 値    | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時 | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時 | 値    | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

すべて同じ `name: type = value`
構文を使用。コンパイル時述語と型コンストラクタは同じコンパイル時証明パイプラインを辿る——`{}`
は証明空間である。

### 6. ループ：Floyd-Hoare 検証条件生成

ループは個別の `: Invariant(...)` や `: decreases(...)`
注釈を必要としない。変数上のコンパイル時述語型注釈が Floyd-Hoare 風のアサーションを定義する——コンパイラは型注釈から検証条件を生成し、証明パイプラインが各代入が型を保持するかをチェックする。

核心的メカニズム：各代入操作は Hoare 三つ組 `{P} x := e {Q}` に対応し、検証条件は
`P ⇒ Q[e/x]`。コンパイラはループ本体に対して一度だけ検証条件を生成する——証明パイプラインが帰納ステップの成立を検証すれば、すべての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照；初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証：0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラはループ本体に対して一度 VC を生成。前提：s は SumUpTo(arr, i) を満たす、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]：
        #   検証義務：s_new は SumUpTo(arr, i) を満たす（現在の i は不変）
        #   s_new = s_old + arr[i] を代入：
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮説 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える：
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT：線形算術、ミリ秒レベル → Proved
        #
        # i += 1：
        #   i 変更 → 依存図で s の型注釈が i を参照 → 再検証をトリガー
        #   新しい検証目標：s は SumUpTo(arr, i_new) を満たす
        #   即ち s == sum(arr[0..i_new])、上記ステップで保証される → Proved
        s += arr[i]
        i += 1
    }
    return s  # このとき s: SumUpTo(arr, arr.len)、即ち s == sum(arr[0..arr.len])
}
```

ループ不変条件は変数上の型注釈そのものである——プログラマが型を記述し、コンパイラが帰納ステップを検査する。コンパイラは不変条件を「発見」する必要も、帰納を「自動的に行う」必要もない——帰納証明を各代入操作の局所検証条件に分解し、証明パイプラインに分割して征服を委ねる。

#### 6.1 依存追跡：可変変数上の依存型

上記メカニズムの前提は、コンパイラが `s` の型注釈 `SumUpTo(arr, i)` が `i`
を参照していることを知っていることである——`i` が変更されるとき、`s`
の型制約もそれに応じて変化する。これにはコンパイラが**変数間の型依存グラフ**を維持する必要がある。

**データ構造**：

```
TypeDepGraph: Map<VarName, Set<VarName>>
# キーは依存される変数、値は型注釈でその変数を参照している変数の集合
# 例：{ i: {s}, j: {s, t}, ... }
```

**構築**：型検査器が `mut v: Pred(... x ...) = init` を処理するとき、`Pred(...)`
引数内の自由変数参照を解析する。引数が現在のスコープ内の他の可変変数 `x`
を参照している場合、依存グラフに `x → v` を記録する。

**トリガー**：依存される変数 `x` が代入されるとき、コンパイラは：

1. 依存グラフで `x` に依存するすべての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` に対して検証条件を生成：`v の現在の値が更新された型 Pred(... x_new ...) を満たすか`
3. VC を証明パイプラインに送る

**代入順序感度**：依存追跡は正しい代入順序を自然に強制する。`SumUpTo(arr, i)` を例に取る：

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすか再検証 → True

# 間違った順序——コンパイラが拒否
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすか再検証
              # s はまだ更新されていない、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー：変数 s は型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**組合せ依存**：一つの変数が複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は `x` と `y`
の両方に同時に依存する——いずれの変更も再検証をトリガーする。

**証明パイプラインとの関係**：依存追跡は VC 生成のトリガーであり、独立した検証メカニズムではない。これは「いつ VC を生成する必要があるか」に答え、証明パイプラインは「VC が成立するか」に答える。

### 7. 停止性検査

コンパイル時全自動。コンパイラが証明できるループは通過し、証明できないものは直接コンパイルエラーを報告する——プログラマはコンパイラにループの停止性を自動解析させなければならない。半自動注釈のための逃げ道はない。

#### 6.1 設計原則

コンパイラは二箇所から停止証明に必要な情報を自動抽出する：

1. **変数型注釈**：精錬型内の境界制約（`UpTo(n)` のように上界 `n` と下界 `0` を与える）
2. **ループ本体の操作**：各反復で変数に適用される操作

コンパイラは優先順位に従って四つの度量合成戦略を試行し、一つが見つかれば停止する。

#### 6.2 戦略 1：線形ランク関数の自動合成

変数に線形境界注釈がある場合、コンパイラは候補線形度量を列挙し SMT で検証する。

```
入力：
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（境界を持つ変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム：
  1. 型注釈から各変数の境界を抽出：[low_i, high_i]
  2. 候補度量を列挙：v_i, u_i - v_i, v_i - v_j などの線形結合
  3. 各候補度量 m に対して：
     - SMT が m ≥ 0 を検証（型境界から導出）
     - ループ本体の各実行パスについて、SMT が m' < m を検証（厳密減少）
  4. 条件を満たす線形結合を発見 → 停止性が証明される
```

カバレッジ範囲：任意の変数が線形式（`v = a·v + b`）で代入され、境界型注釈を持つループ。`i += const`、`i -= const`、および二分探索型区間収縮を含む：

```yaoxiang
# 二分探索：low = mid + 1 または high = mid
# 度量 high - low は両方のパスで厳密に減少する
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2：述語違反カウント——目標型から自動的に度量を抽出 <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在の状態：実験的戦略、フェーズ 3 実装時に実際の実現可能性に応じて含有を決定する。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効だが、非隣接操作（クイックソート partition、ヒープソート sift-down）は自動証明できない。カバレッジ境界は以下の表を参照。フェーズ 3 検証で実現不可能と判明した場合、この戦略は削除されるか将来作業に格下げされる。

核心的洞察：**ユーザー記述の仕様がコンパイラ推論の素材である。**
コンパイラは「ソートとは何か」を内蔵する必要はない——`Sorted`
の定義を読み、その定義から自動的に度量を抽出する。

```
入力：
  目標型：Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体の操作：隣接要素の交換

アルゴリズム：
  1. 述語定義を解析：forall i in range: cond(i, arr)
  2. 自動的に度量を生成：violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作が度量に与える影響を解析：
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の三対のみに影響
     - arr[j] > arr[j+1]（述語違反）の場合、交換後この対は述語を満たす
     - violation_count は少なくとも 1 減少
  4. 上界：n·(n-1)/2（最大隣接逆序数）、下界：0
  → 停止性が証明される
```

**現在のカバレッジ範囲**：

| アルゴリズム   | 操作パターン   | 戦略 2 で証明可能？ | 理由                                        |
| -------------- | -------------- | :-----------------: | ------------------------------------------- |
| バブルソート   | 隣接交換       |         ✅          | violation_count は各交換で厳密減少          |
| 挿入ソート     | 隣接移動       |         ✅          | 各シフトで違反対が一つ解消される            |
| 選択ソート     | 非隣接交換     |         ❌          | 単一交換で violation_count が増加する可能性 |
| クイックソート | partition 分割 |         ❌          | 非隣接交換、単調減少を保証しない            |
| ヒープソート   | sift-down      |         ❌          | ツリー操作、violation_count が非単調        |

**補完戦略**：クイックソートの場合、`low < high`
区間収縮は戦略 1（線形ランク関数）でカバーできる——外層の partition 再帰、各反復で区間が半減。戦略 1 と戦略 2 は補完的にカバーを提供し、実際のアルゴリズムの大部分の停止性は両者のいずれかで証明できる。ただし戦略 2 の汎用化（非隣接操作、ツリー操作）は依然として未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3：有界増減パターン

`v += const`（正常数）、変数が上界型注釈を持つ → 度量 `upper_bound - v` は毎回 `const`
だけ減少し、下界 0。これは戦略 1 の縮退ケースであり、コンパイラは最初に高速処理する。

#### 6.5 戦略 4：乗法スケーリング度量テンプレート

`v *= const`（const > 1）、変数が上下界型注釈を持つ。コンパイラは対数量度テンプレート
`ceil(log_const(upper/v))` を内蔵し、毎回 const を掛けると度量が 1 減少する。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラが自動推論：度量 ceil(log₂(n/i))、毎回 2 倍で度量が 1 減少
    i *= 2
}
```

#### 6.6 停止性と正当性の分離

停止性証明と正当性証明は独立している：

- **停止性**：上記四つの戦略がループが有限ステップで退出することを自動証明
- **正当性**：ループ本体が目標型に向かって進展するか、コンパイル時証明パイプラインが検証条件を通じて検査

両方が通過 → コンパイル通過。停止性は証明されたが正当性が失敗 → コンパイルエラー + 反例。正当性は証明されたが停止性を証明できない → コンパイルエラー、解析不能な変数または操作を示す。両方失敗 → コンパイルエラーが二つの失敗理由を別々に報告。

#### 6.7 再帰関数の停止性検査

コンパイル時評価が必要な再帰関数に対して、コンパイラは引数の減少を検査する：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # コンパイラ解析：n-1 < n → 減少 → 停止
}

# コンパイル時使用——コンパイラは factorial のコンパイル時停止を保証する
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120、コンパイル時に完了
```

| シナリオ                                     | 動作             |
| -------------------------------------------- | ---------------- |
| コンパイラが再帰減少（`n-1` など）を解析可能 | コンパイル時評価 |
| 減少しない/減少を判定できない                | コンパイルエラー |
| 実行時呼び出し（型位置でない）               | 停止性検査不要   |

#### 6.8 ハード境界

`i = f(i)` で `f` が非可逆、非閉、非単調——数学的に自動停止証明は不可能。コンパイルエラー：

> このループは自動停止証明ができない。ループ変数が解析不能な関数 `f`
> に依存している。コンパイラが解析可能な反復パターンを使用してください。

これはコンパイラの失敗ではない。静的に安全性を証明できないコードは、コンパイルを通過できない。

### 8. SMT ソルバ：型検査器の加速モジュール

SMT ソルバは従来の言語では外部ツールである（F\* が Z3 を呼び出し、Dafny が Z3 を呼び出すなど）。YaoXiang では、**型検査器の加速モジュール**である——コンパイラカーネル自身が直接判定できない場合のみ呼び出される。SMT は証明を見つけるのを手伝うが、証明を検証するのは型検査器である。

**信頼モデル**：型検査器が唯一の信頼の根。SMT ソルバは加速モジュールである——証明を見つけるのを手伝うが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny の路線と一致——Z3 が誤る確率はコンパイラ自身のバグ率より低く、これは工学的実用選択）。真の信頼性の制御は SMT 翻訳層にある——翻訳にバグがあれば、コンパイラは他のテストで露呈する。

**インターフェース**：コンパイラ内部は SMT-LIB
2.6 標準形式に変換し、特定のソルバ API に縛られない。SMT-LIB は ISO 標準であり、Z3、CVC5、MathSAT、Yices すべてネイティブサポート。

**デフォルトバックエンド**：Z3（MIT ライセンス、最も広範なドキュメントとコミュニティ検証）。CVC5 は SMT-LIB 互換の代替——ユーザーはコンパイル時にコンパイラフラグで切り替え可能。

「汎用ソルバ抽象層」は作らない——SMT-LIB が抽象層である。将来 CVC5 が特定理論でブレークスルーを達成した場合、切り替えはバイナリ交換のみであり、コンパイラコードの変更は不要。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造同値、簡単な算術、
        │   定数畳み込み後の自明な公式）
        │   → 直接 Proved / Disproved を返す
        │
        └── コンパイラカーネルが直接判定不能（量化子、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB 形式に変換
            → Z3/CVC5 に送信（予算制限付き）
            → 戻り値：unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**求解予算——スタック深度のようなハード制限**：

| 予算次元                 | デフォルト値 | 説明                                                                                                                                 |
| ------------------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 求解ステップ数           | 10,000       | Z3 は線形算術に対して通常百ステップ以内。10,000 ステップで実用的述語の 99% をカバー。                                                |
| 時間                     | 100ms        | 単一述語が 100ms を超える = ユーザーが型注釈ではなくコンパイル時プログラムを書いている。100ms × 50 述語 = 5 秒のコンパイル時間上限。 |
| 量化子インスタンス化深度 | 3            | 三層のネスト量化子が実際のパターンをカバー。三層を超えるとほぼ確実に論理パズルを記述している。                                       |

予算超過は Unproven を返し、コンパイルエラー + 述語位置 + 消費量。降格なし、実行時検査なし、サイレントパスなし。

**なぜこれが実際に可能か**：工学的に 95% の実用的述語は線形算術である——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——すべて決定可能断片内にあり、SMT ソルバは这类の問題に対してミリ秒で返す。予算を超える少数の複雑な述語に遭遇した場合、プログラマは証明関数を記述すればよい。

依存型は SMT 呼び出し前に事前簡約層を経る：`factorial(5)` は直接コンパイル時評価で `120`
に、`append([1,2], [3])` は直接評価で `[1,2,3]`
になる。これらの決定論的値計算は SMT 予算を消費しない。

プログラマは SMT の存在を知る必要がない。メンタルモデルは：**コンパイラが証明できれば通過、できなければエラー——コンパイラができなければ、証明関数を記述して見せることができる。**

### 9. コンパイル時述語の合成

コンパイル時述語は Type を返す関数であり、合成は関数合成を通じて自然に実現される：

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算安全性

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラが Positive(2) = { 2 > 0 } を検証 → True
# result = divide(10, 0)  # ❌ コンパイラが Positive(0) = { 0 > 0 } を検証 → False
```

#### 9.2 配列アクセス安全性

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラが InBounds(1, arr) = { 0 <= 1 and 1 < 3 } を検証 → True
# y = get(arr, 5)  # ❌ コンパイラが InBounds(5, arr) = { 0 <= 5 and 5 < 3 } を検証 → False
```

#### 9.3 ソート正当性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ：コンパイラ VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 分派パイプライン：コンパイル時と実行時の統一分派

`assert` と `Assert` は同じ精錬型プリミティブの二面である。分派パイプライン `dispatch`
は**述語の自由変数がコンパイル時に到達可能か**によって自動的にコンパイル時証明と実行時検査のいずれかに決定する：

| 判定基準                                                                       | モード          | 動作                                                                                  |
| ------------------------------------------------------------------------------ | --------------- | ------------------------------------------------------------------------------------- |
| すべての自由変数がコンパイル時既知（ジェネリクスパラメータ、コンパイル時定数） | **CompileTime** | 証明パイプラインへ：Proved → 消去、Disproved → コンパイルエラー、Unknown → 証明を要求 |
| 自由変数が実行時に由来する（関数パラメータ、外部入力、mut 変数）               | **Runtime**     | 実行時 check を挿入し、フロー感度仮定集合 Γ に精錬事実を注入                          |

**重要**：「判定不能」≠「反証」。CompileTime モードの Unknown は証明を要求する（静的に降格しない）、Runtime モードでは命題はコンパイル時に真偽を持たない——prover がどれほど強くても「ユーザーが負数を入力したかもしれない」に対して恒真証明を書くことはできず、実行時 check が唯一の sound な選択である。これは prover が不十分なわけではなく、理論的必然である。

### 12. フロー感度仮定集合 Γ ：最強後置条件伝播

コンパイラはフロー感度（flow-sensitive）仮定集合 Γ を維持し、各制御フロー点で成立が知られている命題を追跡する。

**SP（最強後置条件）伝播**：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**：`mut`
変数が再代入された後、その変数に関するすべての仮定が Γ から削除される：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

これは soundness のハード要件である——変数の値が変化すれば、古い仮定は無効。

**分岐合流**：IF/ELSE または match 分岐が合流するとき、Γ は各分岐の仮定の交差を取る。すべてのパスで成立する命題のみが分岐外に引き継がれる。

### 13. 消去モデルの明確化：witness 消去 ≠ check 消去

RFC-027 の「精錬型は実行時に**完全に消去される**」という論点は **proof
witness（証明トークン）**を指している——コンパイル時に検証済みの証明項は実行時コードを生成しない。ただし Runtime モードで dispatch が挿入する
**実行時 check** は保持される——これは値層で実行される Bool 検査であり、型層の witness ではない。

まとめ：witness は消去、check は保持。二つの事柄は矛盾せず、RFC-027 の元の論点は変わらない。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以後 (本 RFC)                                                         |
| ------------------------------------- | --------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語をパラメータ型として `(b: Positive(b))`               |
| `//! ensures: ExistsMax(result, arr)` | 戻り型に戻り値仮パラメータを使用 `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変式                    |
| `//! decreases: n`                    | コンパイラ全自動導出度量関数                                          |
| 仕様はコメント                        | 仕様は型システム                                                      |

### 構文

**コンパイル時述語に新しいキーワードはない。** `{}`
は証明空間であり、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数である——`name: (params) -> Type = { アサーション }`。使用時は関数呼び出し——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証するアサーション
# 既存関数/型構文を使用し、新規 BNF ルール不要
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**述語適用の実引数はコンパイル時定数形式でなければならない**——リテラル、変数（名前による束縛）、または単一パラメータ型適用（再帰的抽出）。実引数形式が定数式に変換できない、または実引数の数が述語パラメータと一致しない場合、**E1092**
コンパイルエラーを報告する——精錬制約は**決して静かに破棄されない**（#263：以前に変換不能な実引数により制約が音もなく消え、制約に違反する束縛が静かに通過していた）。

**新規構文概念：戻り値仮パラメータ**——`-> (name: Type)` の `name` は戻り値仮パラメータ。

戻り値仮パラメータは YaoXiang が既存の関数構文に導入する**唯一の構文概念**である。その意味：

- `name` の値は `return` 文によって提供される
- `name`
  は型シグネチャ内にのみ存在し、事後条件述語によって参照される（例：`-> (result: IsMax(T, arr, result))`）
- `name` は関数本体のスコープに入らず、呼び出し側にも現れない
- **戻り値仮パラメータはオプション**——事後条件がない場合、シグネチャは通常の関数と完全に一致し（`-> Int`）、追加負担は発生しない

導入理由：事後条件は「関数が返そうとしている値」を参照する必要がある。戻り値仮パラメータがない場合、コンパイラは述語に戻り値を参照させるために特別なルール（暗黙変数
`$result` や `__retval__`
など）を使用せざるを得ない。戻り値仮パラメータはこの参照を明示化する——単なる仮パラメータであり、値が呼び出し側ではなく
`return` から提供される点が異なる。

**証明関数**は新しい概念ではない——YaoXiang 関数であり、その戻り型はアサートされる命題である。コンパイラが Unproven を返すとき、プログラマは証明関数を提供し、型検査器は他の関数の戻り型を検証するのと完全に同じ方法でそれを検証する。新しい構文、新しいキーワード、新しいルールは不要。

### 型システムへの影響

- **型宇宙**：コンパイル時述語は Type₂ 層に位置する——値を受け取り Type を返す関数、型コンストラクタと同じ層
- **ジェネリクスとの相互作用**：コンパイル時述語はジェネリクスパラメータを取れる、例：`NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **所有権との相互作用**：コンパイル時述語内の式は所有権ルールに従い、読み取りのみ可能、書き込み不可
- **型推論**：コンパイル時述語のパラメータは HM 型推論に参加

### 実行時表現

コンパイル時述語は実行時に**dispatch 分派結果に従って処理される**：

- **CompileTime モード**（すべての自由変数がコンパイル時既知）：証明通過後、witness トークンは完全に消去される。`Positive: (x: Int) -> Type = { x > 0 }`——パラメータ
  `b: Positive(5)` の実行時表現は `Int`。精錬条件 `{ 5 > 0 }` は通過済み、消去。
- **Runtime モード**（実行時自由変数が存在）：実行時 check を保持——値層で Bool 検査を実行し、フロー感度仮定集合 Γ に注入。詳細は §11
  dispatch 分派パイプラインと §13 消去モデル明確化を参照。

コンパイル時述語を型位置に配置する（例：`f(x: Positive(x))`）ことはラッパ型を生成せず、追加メモリを割り当てない。ただし
`x` が実行時入力に由来する場合、**実行時** Bool 検査が挿入される。

**`ref`
との相互作用制約**：コンパイル時述語は不変借用または所有権が既に移動された値のみを参照できる。可変借用を参照するコンパイル時述語は、コンパイラが実行時に検証結果が依然として成立することをコンパイル時に保証できない——这类の用法は直接コンパイルエラーを報告する。

### コンパイラ変更

1. **パーサ**：コンパイル時述語は標準関数構文を使用、追加解析ルール不要
2. **コンパイル時証明パイプライン**：統一 Proved/Disproved/Unproven 戻り値インターフェース、自動戦略選択
3. **SMT 加速モジュール**：SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**：推論規則実装——構造同値、βδι-簡約、全称量化子導入/除去。これが唯一の信頼の根であり、SMT とプログラマ証明はすべてこれを通じて検証される
5. **検証条件生成**：WP/SP 計算 + ループ不変式証明義務
6. **エラー報告**：反例フォーマット + 未解決命題レポート + ソース位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用しないコードは完全に変更なし
- ✅ コンパイル時述語は CompileTime モードでゼロ実行時オーバーヘッド、Runtime モードで必要な Bool 検査のみ保持
- ⚠️ RFC-022 の `//!` 構文はサポートされない——ただし 022 は一度も実装されたことがなく、移行負担なし

## トレードオフ

### 利点

- **Curry-Howard 同型の完全実現**：型が命題、プログラムが証明、`name: 命題 = 証明`
- **統一性**：コンパイル時述語と通常関数は完全に同じ構文を使用、概念分裂なし
- **SMT 透過性**：プログラマは SMT の存在を知る必要がない、メンタルモデルは型検査と一致
- **漸進的採用**：一つのコンパイル時述語から始めて、徐々にカバレッジを拡大可能
- **最小実行時オーバーヘッド**：CompileTime モードはゼロオーバーヘッド、Runtime モードは必要な Bool 検査のみ保持

### 欠点

- **コンパイル時間**：SMT 求解がコンパイル時間を増加させるが、予算のハード制限が上限を制御可能に保つ
- **自動証明の境界**：一階線形算術を超える複雑な述語はプログラマに証明関数の記述を要求する可能性がある。これは言語の欠陥ではなく、停止問題の必然的な帰結である。コンパイラは True/False を偽って報告するのではなく、Unproven を正直に報告する
- **学習曲線**：効果的なコンパイル時述語と証明関数の記述には Curry-Howard 同型の基本的な直感の理解が必要
- **実装複雑性**：コンパイル時証明パイプラインの統一には精巧な設計が必要

### リスク軽減

- SMT 求解予算のハード制限（ステップ数 10,000 / 時間 100ms
  / インスタンス化深度 3）、予算超過は Unproven を返す
- 依存型事前簡約：決定論的値計算を先に処理し、SMT は非決定的部分のみを処理
- Unproven は死路ではない：プログラマは証明関数を記述でき、型検査器が検証する——他の関数の戻り型を検証するのと一致
- 増分検証：変更モジュールのみを検証
- 明確なエラーメッセージ + 反例表示 + 予算消費レポート + 未解決命題 + 提案（可能な場合）

| **本方案：コンパイル時述語を一級市民に** | ✅                                                                                                                    |

## 未解決問題

- [x] **SMT ソルバ選択**：デフォルト Z3（MIT ライセンス、最も広範に検証済み）。CVC5 は SMT-LIB 互換代替、コンパイラフラグで切り替え。コンパイラ内部翻訳目標は SMT-LIB
      2.6 標準形式——SMT-LIB が抽象層であり、カスタム汎用ソルバインターフェースは作らない。
- [x] **求解予算の具体値**：ステップ数 10,000 / 時間 100ms
      / 量化子インスタンス化深度 3。コンパイラ内部固定、ノブは提供しない。実際の使用で不十分が証明された場合（「ユーザーが間違えた」ではなく）、調整する。
- [x] **量化子サポート範囲**：言語層で量化子の階数は制限しない。コンパイル時述語は Type パラメータを受け取る——Type は関数型を含む——したがって高階量化子は型システムの自然な帰結であり、特殊構文は不要。SMT ソルバは一階量化子を自動判定可能（forall/exists、交差ネストをサポート、予算深度 3 による制限）。高階量化子：SMT は Unproven を返し、コンパイラは「この述語は自動証明範囲を超えている、証明関数を提供してください」と指示。プログラマは戻り型がその命題と等しい YaoXiang 関数を記述する——型検査器がその関数を検証する。外部エクスポート不要、AI 不要、対話的証明モード不要。すべてが YaoXiang コード、すべてが型検査器によって検証される。
- [x] **反例フォーマット**：ソース変数名を直接 SMT 変数名として使用（モジュール接頭辞で衝突回避）。Z3 モデル戻り値を変数名で逆引き。出力形式：変数名 = 具体的値 + ソース位置 + 述語定義位置。複雑なマッピング層は作らない。
- [x] ~~**`ref` スマートポインタとコンパイル時述語の相互作用？**~~
      → 決定済み：コンパイル時述語は不変借用または所有権移動済みの値のみを許可。可変借用の値はコンパイル時述語に出現できない。
- [x] **`forall` 述語違反カウント度量の非隣接操作への拡張？**
      → 拡張しない。現在のカバレッジ範囲（隣接交換、隣接移動）は戦略 1（線形ランク関数）で補完的にカバーされる——クイックソート外層区間収縮は戦略 1 が担当し、ヒープソートは戦略 1（配列インデックスパターン）が担当。どの戦略でも停止性を証明できないループは、コンパイラが直接エラーを報告する——これはハード安全性哲学であり、欠陥ではない。将来、実シナリオ（学術的構成ではなく）のアルゴリズムが四つの戦略すべてでカバーできない場合、改めて議論する。
- [x] **線形ランク関数列挙の組合せ爆発**：候補列挙上限は 3 つの有界変数。≤3 の場合、すべての線形結合を列挙し SMT で一つずつ検証。>3 の場合、単一変数度量（`v_i`、`u_i - v_i`）のみ試行し、失敗すれば直接コンパイルエラーを報告——「ループに >3 の有界変数があり、コンパイラが多変量度量を自動合成できない」とプログラマに指示。これは工学的妥協ではなく、プログラマにより単純なループを書かせるための強制である。
