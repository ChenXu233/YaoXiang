# RFC-027：コンパイル時述語と統一静的検証

> **参考文献**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統一型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリックシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024: spawn ブロックに基づく並行モデル](../accepted/024-concurrency-model.md)
>
> **置換対象**：[RFC-022: ホーア論理静的検証サポート（仕様コメントと仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止済み

## 概要

本文書では、YaoXiang に**コンパイル時述語**を一級市民として導入し、すべてのコンパイル時静的検証を一つの**証明パイプライン**に統一することを提案する。コンパイル時述語は外付けの仕様コメントではなく、関数そのものである。Type を返す関数は型位置で使用でき、コンパイラはコンパイル時にそれを呼び出し、返り値を検査する。型は命題、コンパイル時評価は証明である。

**中核的主張**：型検査がコンパイル時に行う唯一の作業は、証明項の構築と検証である。型等式、トークン競合、依存型簡約、コンパイル時述語評価、ホーア論理含意——すべてはコンパイル時証明パイプライン内の異なる型検査であり、同じパイプラインを共有する。SMT ソルバーは型検査器の加速モジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返したとき、プログラマは YaoXiang 関数を証明として記述する——型検査器は、通常の関数の返り値を検証するのと完全に同じ方法でそれを検証する。すべては YaoXiang コードであり、すべては型検査器により検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 は仕様を `//!` コメント形式として設計していた：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← これは型と独立したコメント
    //! ensures: ExistsMax(result, arr[0..n])   ← これは型と独立したコメント
}
```

これは Curry-Howard 同型の根本的な誤りを犯している：**仕様と型を二つの層に分裂させること**。コメントは型ではない。コメントは型検査に参加しない。コメントは「外部ツール」のメンタルモデルである。

ホワイトペーパーは明確に述べている：

> "`//!` コメントはない。独立した仕様言語はない。すべては型システム内にある。"

### 現状の問題

- RFC-022 の `//!` コメントは型システムと独立した外付け構文である
- 仕様型と通常の型は二つの体系であり、概念の冗長を生む
- Debug Build 検証 / Release Build 無視の分裂パターンが統一性を損なう
- SMT ソルバーは従来の認識では外部ツールとして位置付けられるが、YaoXiang では型検査器の加速モジュールとして内蔵される
- 型検査、借用検証、コンパイル時述語検査、マクロ展開がそれぞれ異なるパスを通る

### 正しいメンタルモデル

型検査は関数として抽象化できる：

```
verify : Program → Proved | Disproved(Model) | Unproven
```

すべてのコンパイル時検査——単純な型照合、借用競合検出、コンパイル時述語検証——はこの関数のサブタスクである。これらは同じ証明パイプラインを共有し、証明項の複雑さと構築戦略のみが異なる。

コンパイラが Unproven を返したとき、プログラマは証明関数を提供する——その関数の返り値型が証明すべき命題と等しい。型検査器がそれを検証する。これは通常の型検査と同一の操作である。

## 提案

### 1. `{}` は証明空間：型はアサーション、検証は型検査

YaoXiang の `{}`
はコンパイル時証明空間である。その中のすべてはアサーションであり、コンパイラは各項目が True であることを保証する——自動的に証明されるか、プログラマが証明関数を提供するかのいずれかである。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  コンパイラは x が Float、y が Float であることを保証

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  コンパイラは data が Array(T) であることを保証
```

**ジェネリックはコンパイル時述語の特殊ケースである。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          パラメータはシグネチャで  {} 内にはアサーションのみ
#          コンパイラはコンパイル時呼び出し時に x > 0 を検証

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      パラメータはシグネチャで   コンパイラは type_of(T) == Type、type_of(data) == Array(T) を検証
```

同じパターン：`name: (params) -> Type = { アサーション }`。コンパイラは「型アサーション」と「値アサーション」を区別しない——どちらも証明パイプライン内の評価対象である。

**ループ不変条件を別途記述する必要はない。変数上の型注釈がそのまま Floyd-Hoare 不変条件である。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照——s の型が i に依存することをコンパイラに伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラ検証：s_new == sum(arr[0..i+1])
        i += 1       # i 変更 → s の依存再検証をトリガー：s は SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新しい値が型注釈を満たすか。証明パイプラインが帰納段階を検証すれば、すべての反復が自動的にカバーされる。
`: decreases` も、`: Invariant` も、帰納証明も不要——コンパイラは帰納を各代入の局所 VC に分解する。

### 2. 事前/事後条件：パラメータ型と返り値型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures`
を廃止する。コンパイル時述語はパラメータまたは返り値の型注釈として機能する。

**パラメータ側は関数呼び出しである。**
コンパイル時述語は Type を返す関数であり、パラメータ側での使用方法はそれを呼び出すことである——`factorial(5)`
と同じである。返り値側は新しい概念を導入する：返り値仮パラメータ。

```yaoxiang
# 事前条件：パラメータ型で明示的にコンパイル時述語を呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在の仮パラメータ名、Positive の引数として渡される
#                       コンパイラは呼び出し点で実引数値を抽出し、b に代入し、Positive(実引数) を検証
#                       例：divide(10, 2) → Positive(2) = { 2 > 0 } を検証 → True
#                       例：divide(10, 0) → Positive(0) = { 0 > 0 } を検証 → False → コンパイルエラー

# 事後条件：返り値仮パラメータ + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は返り値仮パラメータ、値は return で提供
#                                            コンパイラは return 点で返り値を代入し、事後条件を検証
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要ルール**：

- **パラメータ側**：`b: Positive(b)` —— `b` は現在の仮パラメータ名、`Positive`
  の引数として渡される。関数呼び出し構文、暗黙的規則ゼロ。
- **返り値側**：`-> (result: IsMax(T, arr, result))` —— `result` は返り値仮パラメータ、値は `return`
  文で提供される。`result`
  は型シグネチャ内にのみ存在し、述語によってのみ参照され、関数本体スコープには入らず、呼び出し側にも現れない。
- **返り値仮パラメータはオプション**：事後条件がない場合は記述せず、シグネチャは通常の関数と完全に一致する（`-> Int`）。
- **統一性**：パラメータと返り値仮パラメータは同じ概念である——`仮パラメータ名: 述語呼び出し(仮パラメータ名)`、値が呼び出し側から提供されるか
  `return` から提供されるかの違いのみ。

### 3. 経路条件伝播：実行時値のコンパイル時検証

コンパイル時述語が束縛位置で使用される場合、パラメータはプログラマが明示的に渡す。実行時値が精錬型パラメータに入るとき、コンパイラは経路条件収集と SMT 含意判定を通じて検証を完了する——プログラマが明示的に証明を渡す必要はない。

#### 3.1 明示的関数呼び出し

コンパイル時述語が束縛位置で使用される場合、パラメータはプログラマが明示的に渡す——関数呼び出しそのもの、暗黙的規則ゼロ。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。これが束縛位置（パラメータ宣言、変数宣言、返り値型）に現れるとき、プログラマは既に束縛された変数名を明示的に渡す：

```yaoxiang
b: Positive(b)
// b は現在の仮パラメータとして宣言済み、Positive(b) は関数呼び出し
// 正規化後：b: { b > 0 }
```

コンパイラが暗黙的にパラメータを埋める必要はない——`b: Positive(b)` は `f(5)`
と同じく、関数呼び出しそのものである。`b` がパラメータ名として束縛され、その型注釈 `Positive(b)` が
`b` 自身を参照している——これは依存型の標準パターンであり、暗黙的展開ルールではない。

**RFC-010 の `self` との統一**：RFC-010 は `self`
がキーワードではなく単なるパラメータ名の慣習であることを確立した（「`p`、`this`、`x`
と書いても効果は完全に同じ」）。`b: Positive(b)`
も同じメカニズムを共有する——パラメータ名は型注釈内で参照可能。`self` は `self: Point`
の位置に現れ、`b` は `b: Positive(b)`
の位置に現れ、両者の型注釈はパラメータ自身を参照する。型注釈の複雑さが異なるだけで、メカニズムは完全に同じである——名前が束縛された後、型はその名前に依存できる。

返り値型も同様に明示的関数呼び出しを使用する：

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は返り値仮パラメータ、Sorted(result) は関数呼び出し
//                        コンパイラは return 点で返り値を result に代入し、Sorted(返り値) を検証
```

局所変数宣言にも同様に適用される：

```yaoxiang
let x: Positive(x) = 5
// x は 5 に束縛、Positive(5) → { 5 > 0 } → True → 通過

// let y: Positive(y) = 0
// y は 0 に束縛、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 経路条件収集

実行時値が条件分岐に現れるとき、コンパイラは自動的に経路条件を収集し、現在のスコープの**仮定集合**を形成する。これらの仮定は、コンパイル時 Bool 評価の背景知識として検証に参加する。

```yaoxiang
if y > 0 {
    // コンパイラはこの分岐内で自動的に仮定を取得：{ y > 0 }
    let result = divide(x, y)
    // 検証条件：(y > 0) ⇒ (y > 0)
    // 証明パイプラインが含意成立を判定 → Proved
} else {
// この分岐の仮定：{ !(y > 0) }
// divide(x, y) を呼び出す場合、検証条件は !(y > 0) ⇒ y > 0
    // 証明パイプラインが含意不成立を判定 → Disproved
}
```

これはコンパイラがハードコードした特殊パターンではない——これはコンパイル時証明パイプラインの自然な振る舞いである。型検査の呼び出し点ごとに、パイプラインに以下が送信される：

```
{背景仮定} ⇒ {検証対象}
```

証明パイプラインが含意性を判定する。Proved → 通過、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未証明命題。背景仮定は現在のプログラム点の経路条件から来る。

#### 3.3 仮定スタック

コンパイラは制御フロー解析において、各基本ブロックに対して仮定集合を維持する：

- **if-ガード**：`if y > 0` → true 分岐は `y > 0`
  をプッシュ、false 分岐は（else を使用する場合）`!(y > 0)` をプッシュ
- **match パターン**：`if let Some(v) = opt` → 分岐内で `opt == Some(v)` をプッシュ
- **論理結合**：`if x > 0 and y < 10` → 分岐内で `x > 0` と `y < 10` をプッシュ
- **関数事前条件**：`divide(a, b)` を呼び出すとき、`b` が `Positive`
  の証拠を持つことは、現在の仮定から来るか、実引数自身の精錬型注釈（`b` が `Positive`
  と注釈されている場合、その型は `b > 0` を運ぶ）から来る
- **代入**：`let z = y` のとき、`y` 上の既存の精錬条件が `z` に伝播する

すべての仮定がコンパイル時証明パイプラインに入る。SMT 加速パスに入るとき、SMT-LIB 背景アサーションに変換される。

#### 3.4 静的証拠なしはコンパイルエラー

プログラマが直接以下のように書いた場合：

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム点には `y > 0` の仮定がなく、実引数 `y` 自身にも `Positive`
型注釈がない。検証条件は：

```
{} ⇒ { y > 0 }
```

パイプラインは `Disproved`（含意不成立）を返す → コンパイルエラー：

> パラメータ `b` が `divide` 呼び出しで `Positive` を満たすことを証明できない。`y`
> は関数入力から来ており、証明済みの境界がない。if 分岐ガードの使用を検討：`if y > 0 { divide(x, y) }`。

YaoXiang は、実行時値が静的証拠を提供せずに精錬型パラメータに直接入ることを許可しない。これは制限ではなく、硬い安全哲学の中核である。コンパイラが静的に証明できないコードは、コンパイルを通過できない。

#### 3.5 統一パイプラインとの関係

経路条件伝播は追加のメカニズムではない。これは制御フロー解析におけるコンパイル時証明パイプラインの直接的な延長である：

| 段階                 | 責任                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 経路条件収集         | コンパイラの制御フロー解析段階で、各基本ブロックに仮定集合を注釈付ける                                                               |
| 検証条件生成         | 検証が必要な型制約に遭遇したとき、経路条件 + 実引数型情報を結合                                                                      |
| 証明パイプライン評価 | コンパイラカーネル → SMT 加速 → Proved / Disproved / Unproven を取得                                                                 |
| 結果                 | `Proved` → 通過；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未証明命題（プログラマは証明関数を提供可能） |

新しい部品はない。特殊なルールもない。経路条件は証明パイプラインの背景知識である——型等式、借用制約と同じパイプライン、同じ予算システムを共有する。

### 4. コンパイル時証明パイプライン

すべてのコンパイル時検査は同じパイプラインを共有する。パイプラインの中核操作は**型検査**である——証明項の型が証明すべき命題と等しいかを検査する。すべては型検査である。

```
コンパイル時に Bool 式評価が必要（すなわち、証明項の構築が必要）
        │
        ├── 型等式（T1 == T2）
        │   → コンパイラが直接判定（構造等価）
        │
        ├── トークン競合条件（!conflicting(tokens)）
        │   → フロー感応生存性解析（Dup/Linear 属性追跡）
        │
        ├── 依存型簡約（n + m 簡約）
        │   → コンパイル時項書き換えシステム（βδι-簡約）
        │
        ├── コンパイル時述語（x > 0, forall...）
        │   → コンパイラ自身 + SMT 加速モジュール
        │
        └── ホーア論理含意（P ⇒ Q）
            → コンパイラ + SMT 加速モジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル通過
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未証明命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を記述（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル通過
                  │
                  ▼
            検証失敗 → コンパイルエラー："証明が成立しない"
```

#### 4.1 証明結果：三値代数

コンパイル時評価は三つの結果を返す——これは停止問題の必然的な結論であり、証明論の自然な分割でもある：

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項が構築済み、型検査通過。コンパイル継続。
- **Disproved(M)** → 停止、反例 M が存在。コンパイルエラー + 反例 + ソース位置。
- **Unproven**
  → 与えられたリソース上限内で証明が構築されなかった。コンパイルエラー + 未証明命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言うのは命題が偽であることを意味しない——現在の自動証明能力を超えているだけである。これは正直なことであり、欠陥ではない。

予算の硬い制限は停止問題の工学的解決である。ノブは提供しない——提供することは「あなたのプログラムは停止すると思いますか」とユーザーに問うことになり、ユーザーは知らず、コンパイラも知らない。

#### 4.2 Unproven の後：プログラマが証明を記述

コンパイラが Unproven を返したとき、プログラマは**証明関数**を記述できる——つまり、返り値型が証明すべき命題と等しい YaoXiang 関数である。型検査器がこの関数を検証する——`add(a, b): Int`
を検証するのと全く同じメカニズムで。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼の根）
```

SMT ソルバーは独立した信頼境界ではなく、**型検査器の加速モジュール**である。SMT は証明を見つけるのを手伝うが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返したとき、コンパイラはその結果を型検査器が検証可能な証明項に再構成する。再構成が失敗した場合（SMT の推論ステップがコンパイラカーネルの推論ルールを超える）、Unproven にフォールバックする——プログラマは手動で証明関数を記述できる。

```yaoxiang
# 命題：コンパイラが自動証明できない精錬属性
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明：プログラマが関数を記述し、返り値型が上の命題
# 型検査器がこの関数を検証する——add(a,b): Int の検証と完全に一致
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラはここで検証：関数本体の型 = FirstIsMin(T, arr)
    ...
}
```

AI は不要、Coq へのエクスポートは不要、新しい概念は不要。**コンパイル時に自動証明できない属性 → プログラマが YaoXiang コードで証明を記述 → 型検査器が検証。**
プロセス全体はスムーズなグラデーションである——コンパイラが簡単な証明を代行し、難しいものはプログラマに任せる。

#### 4.3 パイプライン内の階層的依存

以上の評価器は同じインターフェースを共有するが、評価順序が存在する。型等式はすべての後続解析の前提条件である；所有権/トークン検査は型情報に依存する；精錬述語検証は前二つの結果に依存する。コンパイラは層ごとに評価し、基盤層で失敗した式は上層に進まない——型エラーがあるプログラムで求解予算を浪費することを避ける。

```
評価順序（同じパイプライン、階層的スケジューリング）
├── 第 0 層：型等式（T1 == T2）
│   └── 構造ユニフィケーション → 失敗すれば以降は無意味、Disproved を直接返す
├── 第 1 層：所有権/トークン競合
│   └── フロー感応生存性解析 → 失敗すればメモリ安全性が成立しない、Disproved を直接返す
└── 第 2 層：精錬述語/ホーア含意
    └── コンパイラ自身 → SMT 加速 → Proved / Disproved / Unproven を取得
```

各層は依然として `Proved/Disproved/Unproven`
を返し、同じインターフェースと同じ予算システムを共有する。

### 5. 三層関数の統一

| 階層             | 実行タイミング | 入力  | 出力 | 例                                             |
| ---------------- | -------------- | ----- | ---- | ---------------------------------------------- |
| 値レベル関数     | 実行時         | 値    | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時   | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時   | 値    | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

すべて同じ `name: type = value`
構文を使用する。コンパイル時述語と型コンストラクタは同じコンパイル時証明パイプラインを通る——`{}`
は証明空間である。

### 6. ループ：Floyd-Hoare 検証条件生成

ループは別途の `: Invariant(...)` や `: decreases(...)`
注釈を必要としない。変数上のコンパイル時述語型注釈が Floyd-Hoare 風のアサーションを定義する——コンパイラは型注釈から検証条件を生成し、証明パイプラインが各代入が型を保持するかを検査する。

中核メカニズム：各代入操作は Hoare 三つ組 `{P} x := e {Q}` に対応し、検証条件は
`P ⇒ Q[e/x]`。コンパイラはループ本体に対して一度検証条件を生成する——証明パイプラインが帰納段階を検証すれば、すべての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照；初期化時 i=0、検証：0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証：0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラはループ本体に対して一度 VC を生成。前提：s は SumUpTo(arr, i) を満たし、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]：
        #   検証義務：s_new は SumUpTo(arr, i) を満たす（現在の i は不変）
        #   s_new = s_old + arr[i] を代入：
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮定 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える：
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT：線形算術、ミリ秒単位 → Proved
        #
        # i += 1：
        #   i 変更 → 依存図で s の型注釈が i を参照 → 再検証をトリガー
        #   新しい検証目標：s は SumUpTo(arr, i_new) を満たす
        #   すなわち s == sum(arr[0..i_new])、上の一手で保証される → Proved
        s += arr[i]
        i += 1
    }
    return s  # このとき s: SumUpTo(arr, arr.len)、すなわち s == sum(arr[0..arr.len])
}
```

ループ不変条件は変数上の型注釈そのものである——プログラマは型を記述し、コンパイラは帰納段階を検査する。コンパイラは不変条件を「発見」する必要も、帰納を「自動実行」する必要もない——帰納証明を各代入操作の局所検証条件に分解し、証明パイプラインに分割して委ねる。

#### 6.1 依存追跡：可変変数上の依存型

上記のメカニズムの前提は、コンパイラが `s` の型注釈 `SumUpTo(arr, i)` が `i`
を参照していることを知っていることである——`i` が変更されたとき、`s`
の型制約もそれに応じて変化する。これにはコンパイラが**変数間の型依存グラフ**を維持する必要がある。

**データ構造**：

```
TypeDepGraph: Map<VarName, Set<VarName>>
# キーは依存される変数、値は型注釈内でその変数を参照している変数の集合
# 例：{ i: {s}, j: {s, t}, ... }
```

**構築**：型検査器が `mut v: Pred(... x ...) = init` を処理するとき、`Pred(...)`
引数内の自由変数参照を解析する。引数が現在のスコープ内の他の可変変数 `x`
を参照している場合、依存図に `x → v` を記録する。

**トリガー**：依存される変数 `x` が代入されたとき、コンパイラは：

1. 依存図で `x` に依存するすべての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` について、検証条件を生成：`v の現在の値が更新された型 Pred(... x_new ...) を満たすか`
3. VC を証明パイプラインに送る

**代入順序に敏感**：依存追跡は正しい代入順序を自然に強制する。`SumUpTo(arr, i)` を例に：

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすか再検証 → True

# 誤った順序——コンパイラが拒否
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすか再検証
              # s はまだ更新されていない、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー：変数 s は型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**組み合わせ依存**：一つの変数は複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は `x` と
`y` の両方に同時に依存する——いずれの変更も再検証をトリガーする。

**証明パイプラインとの関係**：依存追跡は VC 生成のトリガーであり、独立した検証メカニズムではない。「いつ VC を生成する必要があるか」に答え、「VC が成立するか」は証明パイプラインが答える。

### 7. 停止性検査

コンパイル時完全自動。コンパイラが証明できるループは通過し、証明できないものは直接コンパイルエラーを報告する——プログラマはループの停止性をコンパイラが自動解析できるようにしなければならない。半自動注釈のための余地は作らない。

#### 6.1 設計原則

コンパイラは二箇所から停止性証明に必要な情報を自動抽出する：

1. **変数の型注釈**：精錬型内の境界制約（例：`UpTo(n)` は上界 `n` と下界 `0` を与える）
2. **ループ本体の操作**：各反復で変数に適用される操作

コンパイラは優先度に従って四つの度量合成戦略を試し、見つかれば停止する。

#### 6.2 戦略 1：線形ランク関数の自動合成

変数に線形境界注釈がある場合、コンパイラは候補となる線形度量を列挙し SMT で検証する。

```
入力：
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（境界を持つ変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム：
  1. 型注釈から各変数の境界を抽出：[low_i, high_i]
  2. 候補度量を列挙：v_i, u_i - v_i, v_i - v_j などの線形結合
  3. 各候補度量 m について：
     - SMT が m ≥ 0 を検証（型境界から導出）
     - ループ本体の各実行パスについて、SMT が m' < m を検証（厳密減少）
  4. 条件を満たす線形結合を発見 → 停止性が証明される
```

カバー範囲：任意の変数が線形式（`v = a·v + b`）に代入され、境界型注釈を持つループ。`i += const`、`i -= const`、および二分探索のような区間収縮を含む：

```yaoxiang
# 二分探索：low = mid + 1 または high = mid
# 度量 high - low は二つのパスで厳密減少
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2：述語違反カウント——目標型から自動抽出度量 <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在の状態：実験的戦略、Phase 3 実装時に実際の実現可能性に応じて含めるかを決定する。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効だが、非隣接操作（クイックソート partition、ヒープソート sift-down）は自動証明できない。カバレッジ境界は以下の表の通り。Phase
> 3 で実現不可能と検証された場合、この戦略は削除されるか将来の作業に降格される。

中核的な洞察：**ユーザーが記述した仕様がコンパイラの推論の素材である。**
コンパイラは「ソートとは何か」を内蔵する必要はない——`Sorted`
の定義を読み、定義から自動的に度量を抽出する。

```
入力：
  目標型：Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体の操作：隣接要素の交換

アルゴリズム：
  1. 述語定義を解析：forall i in range: cond(i, arr)
  2. 度量を自動生成：violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作が度量に与える影響を解析：
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の三対にのみ影響
     - もし arr[j] > arr[j+1]（述語違反）、交換後この対は述語を満たす
     - violation_count は少なくとも 1 減少
  4. 上界：n·(n-1)/2（最大隣接逆序数）、下界：0
  → 停止性が証明される
```

**現在のカバー範囲**：

| アルゴリズム   | 操作パターン | 戦略 2 で証明可能？ | 理由                                     |
| -------------- | ------------ | :-----------------: | ---------------------------------------- |
| バブルソート   | 隣接交換     |         ✅          | violation_count は各交換で厳密減少       |
| 挿入ソート     | 隣接移動     |         ✅          | 各シフトで違反対が一つ解消される         |
| 選択ソート     | 非隣接交換   |         ❌          | 単一交換で violation_count が増加し得る  |
| クイックソート | partition    |         ❌          | 非隣接交換、単調減少を保証しない         |
| ヒープソート   | sift-down    |         ❌          | ツリー操作、violation_count は単調でない |

**補完的戦略**：クイックソートの場合、`low < high`
区間収縮は戦略 1（線形ランク関数）でカバーできる——外側の partition 再帰で、各反復で区間が半分になる。戦略 1 と戦略 2 は補完的にカバーし、ほとんどの実際のアルゴリズムの停止性は両者のいずれかで証明できる。ただし戦略 2 の一般化（非隣接操作、ツリー操作）は依然として未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3：有界増減パターン

`v += const`（正の定数）、変数に上界型注釈がある → 度量 `upper_bound - v` は毎回 `const`
ずつ減少し、下界は 0。これは戦略 1 の退化ケースであり、コンパイラは最初に高速処理する。

#### 6.5 戦略 4：乗法的スケール度量テンプレート

`v *= const`（const > 1）、変数に上下界型注釈がある。コンパイラは対数度量テンプレート
`ceil(log_const(upper/v))` を内蔵し、毎回 const を掛けると度量が 1 減少する。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラは自動推論：度量 ceil(log₂(n/i))、毎回 2 倍で度量が 1 減少
    i *= 2
}
```

#### 6.6 停止性と正当性の分離

停止性証明と正当性証明は独立している：

- **停止性**：上記四つの戦略がループの有限ステップ終了を自動証明
- **正当性**：ループ本体が目標型に向かって進むかは、コンパイル時証明パイプラインが検証条件で検査

両方が通過 → コンパイル通過。停止性は証明されたが正当性が失敗 → コンパイルエラー + 反例。正当性は証明されたが停止性が証明できない → コンパイルエラーで解析できない変数や操作を指摘。両方が失敗 → コンパイルエラーで二つの失敗理由を別々に報告。

#### 6.7 再帰関数の停止性検査

コンパイル時に評価する必要がある再帰関数について、コンパイラは引数の減少を検査する：

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # コンパイラ解析：n-1 < n → 減少 → 停止
}

# コンパイル時に使用——コンパイラは factorial のコンパイル時停止を保証
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120、コンパイル時に完了
```

| シナリオ                                     | 振る舞い         |
| -------------------------------------------- | ---------------- |
| コンパイラが再帰減少を解析可能（`n-1` など） | コンパイル時評価 |
| 減少しない/減少判定不可                      | コンパイルエラー |
| 実行時呼び出し（型位置でない）               | 停止性検査不要   |

#### 6.8 硬い境界

`i = f(i)` で `f`
が可逆でない、閉じていない、単調性を保持しない——数学的に自動停止証明は不可能。コンパイルエラー：

> このループは自動停止証明ができない。ループ変数が解析不可能な関数 `f`
> に依存している。コンパイラが解析可能な反復パターンを使用してください。

これはコンパイラの失敗ではない。静的に安全性を証明できないコードは、コンパイルを通過できない。

### 8. SMT ソルバー：型検査器の加速モジュール

SMT ソルバーは従来の言語では外部ツールである（F\* が Z3 を呼び出し、Dafny が Z3 を呼び出すなど）。YaoXiang では、それは**型検査器の加速モジュール**である——コンパイラカーネル自身が直接判定できない場合にのみ呼び出される。SMT は証明を見つけるのを手伝うが、証明を検証するのは型検査器である。

**信頼モデル**：型検査器が唯一の信頼の根である。SMT ソルバーは加速モジュールである——証明を見つけるのを手伝うが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny のアプローチと一致——Z3 が誤る確率はコンパイラ自身のバグ率より低く、これは工学的に実用的な選択である）。真の信頼性の制御は SMT 翻訳層にある——翻訳にバグがあれば、コンパイラは他のテストで露呈する。

**インターフェース**：コンパイラ内部は SMT-LIB
2.6 標準形式に変換し、特定のソルバー API に束縛されない。SMT-LIB は ISO 標準であり、Z3、CVC5、MathSAT、Yices がすべてネイティブサポートしている。

**デフォルトバックエンド**：Z3（MIT ライセンス、最も広範なドキュメントとコミュニティ検証）。CVC5 は SMT-LIB 互換の代替として——ユーザーはコンパイル時にコンパイラフラグで切り替え可能。

「汎用ソルバー抽象層」は作らない——SMT-LIB が抽象層である。将来 CVC5 が特定の理論でブレークスルーを達成した場合、切り替えはバイナリを置き換えるだけで済み、コンパイラコードの変更は不要。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造等価、単純な算術、
        │   定数畳み込み後の自明な式）
        │   → Proved / Disproved を直接返す
        │
        └── コンパイラカーネルが直接判定不能（量詞、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB 形式に変換
            → Z3/CVC5 に送信（予算制限付き）
            → 返り値：unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**求解予算——硬い制限、スタック深度のように**：

| 予算次元               | デフォルト | 説明                                                                                                                                 |
| ---------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 求解ステップ数         | 10,000     | Z3 は線形算術に対して通常百ステップ以内。10,000 ステップで実際の述語の 99% をカバー。                                                |
| 時間                   | 100ms      | 単一述語が 100ms を超える = ユーザーが型注釈ではなくコンパイル時プログラムを書いている。100ms × 50 述語 = 5 秒のコンパイル時間上限。 |
| 量詞インスタンス化深度 | 3          | 三層のネスト量詞で実際のパターンをカバー。これを超えると論理学の演習問題を記述している可能性が高い。                                 |

予算超過は Unproven を返し、コンパイルエラー + 述語位置 + 消費量。降格なし、実行時検査なし、サイレントパスなし。

**なぜこれが実際に機能するか**：工学的に実際の述語の 95% は線形算術である——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——すべて決定可能フラグメント内にあり、SMT ソルバーは这类の問題にミリ秒単位で応答する。予算を超える複雑な述詞の稀少なケースに遭遇した場合、プログラマは証明関数を記述すればよい。

依存型は SMT 呼び出し前に事前簡約の層を経る：`factorial(5)` は直接コンパイル時評価で `120`
になり、`append([1,2], [3])` は直接評価で `[1,2,3]`
になる。これらの確定的な値計算は SMT 予算を消費しない。

プログラマは SMT の存在を知る必要はない。メンタルモデルは：**コンパイラが証明できれば通過、できなければエラー——コンパイラがわからない場合、関数を記述して証明を見せればよい。**

### 9. コンパイル時述語の組み合わせ

コンパイル時述語は Type を返す関数であり、組み合わせは関数合成を通じて自然に実現される：

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算の安全性

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラが Positive(2) = { 2 > 0 } を検証 → True
# result = divide(10, 0)  # ❌ コンパイラが Positive(0) = { 0 > 0 } を検証 → False
```

#### 9.2 配列アクセスの安全性

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラが InBounds(1, arr) = { 0 <= 1 and 1 < 3 } を検証 → True
# y = get(arr, 5)  # ❌ コンパイラが InBounds(5, arr) = { 0 <= 5 and 5 < 3 } を検証 → False
```

#### 9.3 ソートの正当性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ：コンパイラ VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 分岐パイプライン：コンパイル時と実行時の統一分岐

`assert` と `Assert` は同じ精錬型原語の二つの側面である。分岐パイプライン `dispatch`
は**述語の自由変数がコンパイル時にアクセス可能かどうか**に応じて、コンパイル時証明と実行時検査のどちらを行うかを自動決定する：

| 判断基準                                                                       | モード          | 振る舞い                                                                            |
| ------------------------------------------------------------------------------ | --------------- | ----------------------------------------------------------------------------------- |
| すべての自由変数がコンパイル時既知（ジェネリックパラメータ、コンパイル時定数） | **CompileTime** | 証明パイプラインへ：Proved → 消去、Disproved → コンパイルエラー、Unknown → 証明要求 |
| 自由変数に実行時から来るものがある（関数パラメータ、外部入力、mut 変数）       | **Runtime**     | 実行時 check を挿入し、フロー感応仮定集合 Γ に精錬事実を注入                        |

**重要**：「判定不能」≠「反証」。CompileTime モードの Unknown は証明を要求する（暗黙的降格なし）、Runtime モードでは命題はコンパイル時には真偽すら持たない——prover がどれほど強力でも「ユーザーが負数を入力したかもしれない」に対する恒真証明は書けないため、実行時 check が唯一の sound な選択である。これは prover が弱いからではなく、理論的必然である。

### 12. フロー感応仮定集合 Γ：最強後条件伝播

コンパイラはフロー感応（flow-sensitive）仮定集合 Γ を維持し、各制御フロー点で既知の命題を追跡する。

**SP（最強後条件）伝播**：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**：`mut`
変数が再代入された後、その変数に関するすべての仮定が Γ から除去される：

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

これは soundness の硬い要求である——変数の値が変われば、古い仮定は無効になる。

**分岐合流**：IF/ELSE または match 分岐が合流するとき、Γ は各分岐の仮定の交差を取る。すべてのパスで成立する命題のみが分岐の外に持ち出される。

### 13. 消去モデル明確化：witness 消去 ≠ check 消去

RFC-027 の「精錬型は実行時に**完全に消去される**」という主張は **proof
witness（証明トークン）**を指している——コンパイル時に検証された証明項は実行時コードを生成しない。ただし Runtime モードで dispatch が挿入する
**実行時 check**
は保持される——これは値レベルで実行される Bool 検査であり、型レベルの witness ではない。

要約：witness は消去、check は保持。二つのことは競合せず、RFC-027 の元の主張は変わらない。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以後 (本 RFC)                                                           |
| ------------------------------------- | ----------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語をパラメータ型として `(b: Positive(b))`                 |
| `//! ensures: ExistsMax(result, arr)` | 返り値型で返り値仮パラメータを使用 `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変条件                    |
| `//! decreases: n`                    | コンパイラによる度量関数の完全自動導出                                  |
| 仕様はコメント                        | 仕様は型システム                                                        |

### 構文

**コンパイル時述語に新しいキーワードはない。** `{}`
は証明空間であり、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数である——`name: (params) -> Type = { アサーション }`。使用時は関数呼び出し——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証するアサーション
# 既存の関数/型構文を使用し、新しい BNF ルールを追加する必要はない
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**述語適用の実引数はコンパイル時定数の形式である必要がある**——リテラル、変数（名前による束縛）または単一引数型適用（再帰的に抽出）。実引数形式が定数式に変換できない場合は
**E1092**、実引数の個数が述語パラメータと一致しない場合は **E1093**
を報告する——精錬制約は**決して静かに破棄されない**（#263：以前、変換不可能な実引数が制約を無音で消失させ、制約に違反する束縛が無音で通過していた）。

**新しい構文概念：返り値仮パラメータ**——`-> (name: Type)` において `name` は返り値仮パラメータ。

返り値仮パラメータは YaoXiang が既存の関数構文に導入する**唯一の構文概念**である。そのセマンティクス：

- `name` の値は `return` 文で提供される
- `name`
  は型シグネチャ内にのみ存在し、事後条件述語によって参照される（例：`-> (result: IsMax(T, arr, result))`）
- `name` は関数本体スコープには入らず、呼び出し側にも現れない
- 返り値仮パラメータは**オプション**——事後条件がない場合、シグネチャは通常の関数と完全に一致する（`-> Int`）、追加の負担なし

導入の理由：事後条件は「関数が返そうとしている値」を参照する必要がある。返り値仮パラメータがない場合、コンパイラは特殊なルール（暗黙的変数
`$result` や `__retval__`
など）によってのみ述語が返り値を参照できるようにできる。返り値仮パラメータはこの参照を明示化する——これは単なる仮パラメータであり、値が
`return` から提供されるか呼び出し側から提供されるかのみが異なる。

**証明関数**は新しい概念ではない——これは返り値型がアサートされる命題と等しい YaoXiang 関数である。コンパイラが Unproven を返したとき、プログラマは証明関数を提供し、型検査器は任意の関数の返り値型を検証するのと完全に同じ方法でそれを検証する。新しい構文、新しいキーワード、新しいルールは不要。

### 型システムへの影響

- **型ユニバース**：コンパイル時述語は Type₂ 層に位置する——値を受け取り Type を返す関数で、型コンストラクタと同じ階層
- **ジェネリックとの相互作用**：コンパイル時述語はジェネリックパラメータを取れる、たとえば
  `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **所有権との相互作用**：コンパイル時述語内の式は所有権ルールに従い、読み取りのみ可能で書き込み不可
- **型推論**：コンパイル時述語のパラメータは HM 型推論に参加する

### 実行時表現

コンパイル時述語の実行時表現は **dispatch 分岐結果に従って処理される**：

- **CompileTime モード**（すべての自由変数がコンパイル時既知）：証明通過後、witness トークンは完全に消去される。`Positive: (x: Int) -> Type = { x > 0 }`
  ——パラメータ `b: Positive(5)` の実行時表現は単なる `Int` である。精錬条件 `{ 5 > 0 }`
  は通過済み、消去。
- **Runtime モード**（実行時自由変数が存在する）：実行時 check を保持——値レベルで Bool 検査を実行し、フロー感応仮定集合 Γ に注入。詳細は §11
  dispatch 分岐パイプラインと §13 消去モデル明確化を参照。

コンパイル時述語を型位置に置く（例：`f(x: Positive(x))`）ことはラッパー型を生成せず、追加メモリを割り当てない。ただし
`x` が実行時入力から来る場合、**実行時** Bool 検査が挿入される。

**`ref`
との相互作用制約**：コンパイル時述語は不変借用または所有権が既に转移された値のみを参照できる。可変借用を参照するコンパイル時述語は、コンパイラがコンパイル時に検証結果が実行時にも成立することを保証できない——このような使用法は直接コンパイルエラーを報告する。

### コンパイラの修正

1. **パーサ**：コンパイル時述語は標準関数構文を使用し、追加の解析ルールは不要
2. **コンパイル時証明パイプライン**：Proved/Disproved/Unproven 返り値インターフェースの統合、自動戦略選択
3. **SMT 加速モジュール**：SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**：推論ルールの実装——構造等価、βδι-簡約、全称量詞導入/除去。これが唯一の信頼の根であり、SMT とプログラマの証明はすべてこれを通じて検証される
5. **検証条件生成**：WP/SP 計算 + ループ不変条件証明義務
6. **エラー報告**：反例フォーマット + 未証明命題レポート + ソース位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用しないコードは完全に不変
- ✅ コンパイル時述語は CompileTime モードでゼロ実行時オーバーヘッド、Runtime モードでは必要な Bool 検査のみを保持
- ⚠️ RFC-022 の `//!` 構文はサポートされない——ただし 022 は一度も実装されておらず、移行負担なし

## トレードオフ

### 利点

- **Curry-Howard 同型の完全な実現**：型は命題、プログラムは証明、`name: Proposition = Proof`
- **統一性**：コンパイル時述語と通常の関数は完全に同じ構文を使用し、概念の分裂なし
- **SMT 透明性**：プログラマは SMT の存在を知る必要がなく、メンタルモデルは型検査と一致
- **漸進的採用**：一つのコンパイル時述語から始めて、カバレッジを段階的に拡大可能
- **最小実行時オーバーヘッド**：CompileTime モードはゼロオーバーヘッド、Runtime モードは必要な Bool 検査のみを保持

### 欠点

- **コンパイル時間**：SMT 求解がコンパイル時間を増加させるが、予算の硬い制限が上限を制御可能に保つ
- **自動証明の境界**：一階線形算術を超える複雑な述語はプログラマの証明関数を必要とする場合がある。これは言語の欠陥ではなく、停止問題の必然的な結論である。コンパイラは False/True を偽って報告するのではなく、Unproven を正直に報告する
- **学習曲線**：効果的なコンパイル時述語と証明関数の記述には Curry-Howard 同型の基本的な直感の理解が必要
- **実装の複雑さ**：コンパイル時証明パイプラインの統合は慎重な設計が必要

### リスク軽減

- SMT 求解予算の硬い制限（ステップ数 10,000 / 時間 100ms
  / インスタンス化深度 3）、予算超過は Unproven を返す
- 依存型の事前簡約：確定的な値計算を先に処理し、SMT は非決定的部分のみを処理
- Unproven は行き止まりではない：プログラマは証明関数を記述でき、型検査器が検証——任意の関数の返り値型の検証と一致
- 増分検証：変更されたモジュールのみを検証
- 明確なエラーメッセージ + 反例表示 + 予算消費レポート + 未証明命題 + 提案（コンパイラが提供可能な場合）

| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| RFC-022：`//!` コメント式仕様                | 仕様と型を分裂させ、Curry-Howard 同型に違反                                                                                     |

| **本方案：コンパイル時述語を一級市民として** | ✅                                                                                                                              |

## オープンな問題

- [x] **SMT ソルバーの選択**：デフォルト Z3（MIT ライセンス、最も広範に検証済み）。CVC5 は SMT-LIB 互換代替として、コンパイラフラグで切り替え。コンパイラ内部は SMT-LIB
      2.6 標準形式への変換を目標とする——SMT-LIB が抽象層であり、カスタム汎用ソルバーインターフェースは作らない。
- [x] **求解予算の具体値**：ステップ数 10,000 / 時間 100ms
      / 量詞インスタンス化深度 3。コンパイラ内部で固定、ノブは提供しない。実際の使用で本当に不十分であることが証明された場合（"ユーザーが間違って書いた" ではなく）再調整。
- [x] **量詞サポートの範囲**：言語レベルでは量詞階数を制限しない。コンパイル時述語は Type パラメータを受け取る——Type は関数型を含む——したがって高階量詞は型システムの自然な帰結であり、特殊構文は不要。SMT ソルバーは一階量詞（forall/exists、ネストサポート、予算深度 3 で制限）を自動判定可能。高階量詞：SMT は Unproven を返し、コンパイラは「この述語は自動証明の範囲外です、証明関数を提供してください」と促す。プログラマは返り値型が当該命題と等しい YaoXiang 関数を記述する——型検査器がその関数を検証する。外部エクスポート不要、AI なし、対話的証明モードなし。すべては YaoXiang コード、すべては型検査器が検証。
- [x] **反例フォーマット**：ソース変数名を直接 SMT 変数名として使用（モジュールプレフィックスを付加して衝突回避）。Z3 モデル返り値時に変数名で逆検索。出力形式：変数名 = 具体的な値 + ソース位置 + 述語定義位置。複雑なマッピング層は作らない。
- [x] ~~**`ref` スマートポインタとコンパイル時述語の相互作用？**~~
      → 決定済み：コンパイル時述語は不変借用または既に転移された所有権の値のみを許可する。可変借用される値はコンパイル時述語に現れない。
- [x] **`forall` 述語違反カウント度量の非隣接操作への拡張？**
      → 拡張しない。現在のカバー範囲（隣接交換、隣接移動）は戦略 1（線形ランク関数）で補完的にカバーされる——クイックソートの外側区間収縮は戦略 1 がカバー、ヒープソートは戦略 1（配列インデックスパターン）がカバー。どの戦略でも停止性を証明できないループは、コンパイラが直接エラーを報告する——これは硬い安全哲学であり、欠陥ではない。将来、実際のシナリオ（学術的構築ではなく）のアルゴリズムが四つの戦略すべてでカバーできないことが判明した場合、再議論する。
- [x] **線形ランク関数列挙の組み合わせ爆発**：候補列挙の上限は 3 つの有界変数。≤3 の場合、すべての線形結合を列挙し SMT で一つずつ検証。>3 の場合、単一変数度量（`v_i`、`u_i - v_i`）のみを試行し、失敗すれば直接コンパイルエラーを報告——「ループに >3 個の有界変数があり、コンパイラが複数変数度量を自動合成できない」とプログラマに促す。これは工学的妥協ではなく、プログラマにより単純なループを書かせるための強制である。
