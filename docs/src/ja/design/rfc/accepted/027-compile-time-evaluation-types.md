# RFC-027: コンパイル時述語と統一静的検証

> **参考**:
>
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)
> - [RFC-010: 統一型構文 - name: type = value モデル](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリックシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-024: spawn ブロックに基づく並行モデル](../accepted/024-concurrency-model.md)
>
> **置き換え**:
> [RFC-022: ホーア論理静的検証サポート（仕様コメントと仕様型）](../deprecated/022-hoare-logic-static-verification.md)
> — 廃止済み

## 概要

本文は YaoXiang に**コンパイル時述語**を一級市民として導入し、すべてのコンパイル時静的検証を単一の**証明パイプライン**に統一することを提案する。コンパイル時述語は外付けの仕様注释ではない——それは関数そのもの。Type を返す関数は型位置で使用でき、コンパイラがコンパイル時に呼び出して戻り値を検証する。型が命題、コンパイル時評価が証明。

**核心的主張**: 型検査がコンパイル時に行う唯一の仕事は証明項の構築と検証である。型等価、トークン衝突、依存型簡約、コンパイル時述語評価、ホーア論理蕴含——すべてコンパイル時証明パイプライン内の異なる型検査であり、同じパイプラインを共有する。SMT ソルバーは型検査器の加速モジュールであり、独立した信頼境界ではない。コンパイラが Unproven を返したとき、プログラマは YaoXiang 関数を証明として書く——型検査器は任意の関数の戻り型を検証するのと同じ方法でそれを検証する。すべてが YaoXiang コード、すべてが型検査器で検証される。

## 動機

### なぜ RFC-022 を廃止するのか？

RFC-022 は仕様を `//!` コメント形式で設計していた:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← これは型と独立したコメント
    //! ensures: ExistsMax(result, arr[0..n])   ← これは型と独立したコメント
}
```

これは Curry-Howard 同型の根本的な誤りを犯している:**仕様と型を二層に分裂させる**。コメントは型ではない。コメントは型検査に参加しない。コメントは「外部ツール」のメンタルモデル。

白書には明確に書かれている:

> 「`//!` コメントはない。独立した仕様言語はない。すべて型システム内にある。」

### 現在の問題

- RFC-022 の `//!` コメントは型システムと独立した外付け構文
- 仕様型と通常型は二系統であり、概念の冗長を生む
- Debug Build 検証 / Release Build 無視の分裂モデルが統一性を破壊する
- SMT ソルバーは従来の認識では外部ツールとして位置付けられる——YaoXiang はそれを型検査器の加速モジュールとして内蔵する
- 型検査、借用検証、コンパイル時述語検査、マクロ展開がそれぞれ別のパスを取る

### 正しいメンタルモデル

型検査は次のような関数として抽象化できる:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

すべてのコンパイル時検査——単純な型マッチ、借用衝突検出、コンパイル時述語検証——はこの関数のサブタスクである。証明項の複雑さと構築戦略のみが異なり、同じ証明パイプラインを共有する。

コンパイラが Unproven を返したとき、プログラマは証明関数を提供する——その関数の戻り型は証明対象の命題に等しい。型検査器がそれを検証する。これは通常の型検査と同一の操作である。

## 提案

### 1. `{}` は証明空間: 型がアサート、検証が型検査

YaoXiang の `{}`
はコンパイル時証明空間である。その中のすべてがアサートであり、コンパイラは各項目が True であることを保証する——自動証明されるか、プログラマが証明関数を提供するかのいずれか。

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  コンパイラは x が Float、y が Float であることを保証

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  コンパイラは data が Array(T) であることを保証
```

**ジェネリックはコンパイル時述語の特例である。**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          パラメータはシグネチャ     {} 内にはアサートのみ
#          コンパイラがコンパイル時呼び出し時に x > 0 を検証

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      パラメータはシグネチャ    コンパイラは type_of(T) == Type、type_of(data) == Array(T) を検証
```

同じパターン:
`name: (params) -> Type = { アサート }`。コンパイラは「型アサート」と「値アサート」を区別しない——どちらも証明パイプライン内の評価対象。

**ループ不変条件を別途書く必要はない。変数上の型注釈が Floyd-Hoare 不変式そのもの。**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照——s の型が i に依存することをコンパイラに伝える
    mut i: UpTo(arr.len) = 0     # 初期化時 i=0、検証: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # コンパイラ検証: s_new == sum(arr[0..i+1])
        i += 1       # i 変更 → s の依存再検証をトリガ: s は SumUpTo(arr, i_new) を満たす
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

コンパイラはループ本体に対して一度検証条件を生成する——帰納仮説（型注釈）→ 代入操作 → 新値が型注釈を満たすか。証明パイプラインが帰納ステップを検証した段階で、すべての反復が自動的にカバーされる。`: decreases`
も、`: Invariant` も、帰納証明も不要——コンパイラは帰納を各代入の局所 VC に分解する。

### 2. 事前/事後条件: パラメータ型と戻り型上のコンパイル時述語

RFC-022 の `//! requires`/`//! ensures`
を廃止する。コンパイル時述語はパラメータまたは戻りの型注釈として機能する。

**パラメータ側は関数呼び出し。**
コンパイル時述語は Type を返す関数であり、パラメータ側の使用方法はそれを呼び出すこと——`factorial(5)`
と同じ。戻り値側は新しい概念を導入する: 戻り値パラメータ。

```yaoxiang
# 事前条件: パラメータ型内で明示的にコンパイル時述語を呼び出す
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b は現在のパラメータ名、Positive の引数として渡される
#                       コンパイラは呼び出し点で実引数値を抽出し、b に代入、Positive(実引数) を検証
#                       例: divide(10, 2) → Positive(2) = { 2 > 0 } を検証 → True
#                       例: divide(10, 0) → Positive(0) = { 0 > 0 } を検証 → False → コンパイルエラー

# 事後条件: 戻り値パラメータ + コンパイル時述語
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result は戻り値パラメータ、値は return によって提供される
#                                            コンパイラは return 点で戻り値を代入、事後条件を検証
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**重要なルール**:

- **パラメータ側**: `b: Positive(b)` —— `b` は現在のパラメータ名、`Positive`
  の引数として渡される。関数呼び出し構文、暗黙の規則ゼロ。
- **戻り値側**: `-> (result: IsMax(T, arr, result))` —— `result` は戻り値パラメータ、値は `return`
  文で提供される。`result`
  は型シグネチャ内にのみ存在し、述語からのみ参照され、関数本体のスコープには入らず、呼び出し側にも現れない。
- **戻り値パラメータはオプション**: 事後条件がない場合は書かず、シグネチャは通常関数と完全に一致する（`-> Int`）。
- **統一性**: パラメータと戻り値パラメータは同じ概念——`パラメータ名: 述語呼び出し(パラメータ名)`、値が呼び出し側から提供されるか
  `return` から提供されるかのみが異なる。

### 3. パス条件伝播: ランタイム値のコンパイル時検証

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマが明示的に渡す。ランタイム値が精錬型パラメータに入るとき、コンパイラはパス条件収集と SMT 蕴含判断を通じて検証を完了する——プログラマが明示的に証明を渡す必要はない。

#### 3.1 明示的関数呼び出し

コンパイル時述語が束縛位置で使用されるとき、パラメータはプログラマが明示的に渡す——関数呼び出しそのもの、暗黙の規則ゼロ。

`Positive: (x: Int) -> Type = { x > 0 }`
はコンパイル時述語コンストラクタである。それが束縛位置（パラメータ宣言、変数宣言、戻り型）に現れるとき、プログラマは既に束縛された変数名を明示的に渡す:

```yaoxiang
b: Positive(b)
// b は現在のパラメータとして宣言済み、Positive(b) は関数呼び出し
// 正規化後: b: { b > 0 }
```

コンパイラが暗黙にパラメータを埋める必要はない——`b: Positive(b)` は `f(5)` と同じ、関数呼び出し。`b`
がパラメータ名として束縛され、その型注釈 `Positive(b)` が `b`
自身を参照している——これは依存型の標準パターンであり、暗黙の展開規則ではない。

**RFC-010 の `self` との統一**: RFC-010 は `self`
がキーワードではなく単なるパラメータ名の慣習であることを確立した（「`p`、`this`、`x`
と書いても完全に同じ効果」）。`b: Positive(b)`
も同じメカニズムを共有する——パラメータ名は型注釈内で参照可能。`self` は `self: Point`
の位置に現れ、`b` は `b: Positive(b)`
の位置に現れる。両者の型注釈はパラメータ自身を参照する。型注釈の複雑さのみが異なり、メカニズムは完全に同じ——名前が束縛された後、型はその名前に依存できる。

戻り型も明示的関数呼び出しを使用する:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result は戻り値パラメータ、Sorted(result) は関数呼び出し
//                        コンパイラは return 点で戻り値を result に代入、Sorted(戻り値) を検証
```

局所変数宣言にも同様に適用される:

```yaoxiang
let x: Positive(x) = 5
// x は 5 に束縛、Positive(5) → { 5 > 0 } → True → 合格

// let y: Positive(y) = 0
// y は 0 に束縛、Positive(0) → { 0 > 0 } → False → コンパイルエラー
```

#### 3.2 パス条件収集

ランタイム値が条件分岐に現れるとき、コンパイラはパス条件を自動的に収集し、現在のスコープの**仮説集合**を形成する。これらの仮説はコンパイル時 Bool 評価の背景知識として検証に参加する。

```yaoxiang
if y > 0 {
    // コンパイラは true 分岐内で自動的に仮説を取得: { y > 0 }
    let result = divide(x, y)
    // 検証条件: (y > 0) ⇒ (y > 0)
    // 証明パイプラインは蕴含成立を判定 → Proved
} else {
// この分岐の仮説: { !(y > 0) }
// divide(x, y) を呼び出す場合、検証条件は !(y > 0) ⇒ y > 0
    // 証明パイプラインは蕴含不成立を判定 → Disproved
}
```

これはコンパイラが特別モードをハードコードしているのではない——これはコンパイル時証明パイプラインの自然な動作である。型検査の呼び出し点が毎回パイプラインに送信する:

```
{背景仮説} ⇒ {検証対象}
```

証明パイプラインは蕴含性を判定する。Proved → 合格、Disproved → コンパイルエラー + 反例、Unproven
→ コンパイルエラー + 未解決命題。背景仮説は現在のプログラム点のパス条件に由来する。

#### 3.3 仮説スタック

コンパイラは制御フロー解析において、各基本ブロックに対して仮説集合を維持する:

- **if-ガード**: `if y > 0` → true 分岐に `y > 0` をプッシュ、false 分岐に `!(y > 0)`
  をプッシュ（else が使用されている場合）
- **match パターン**: `if let Some(v) = opt` → 分岐内に `opt == Some(v)` をプッシュ
- **論理結合**: `if x > 0 and y < 10` → 分岐内に `x > 0` と `y < 10` をプッシュ
- **関数事前条件**: `divide(a, b)` を呼び出すとき、`b` が `Positive`
  の証拠を持つのは、現在の仮説からのものか、実引数自身の精錬型注釈からのもの（`b` が既に `Positive`
  と注釈されていれば、その型は `b > 0` を運ぶ）
- **代入**: `let z = y` のとき、`y` 上の既存の精錬条件が `z` に伝播する

すべての仮説がコンパイル時証明パイプラインに入る。SMT 加速パスに入るとき、SMT-LIB 背景アサーションに翻訳される。

#### 3.4 静的証拠なしはコンパイルエラー

プログラマが直接以下のように書いた場合:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

現在のプログラム点に `y > 0` の仮説がなく、実引数 `y` 自身にも `Positive` 型注釈がない。検証条件は:

```
{} ⇒ { y > 0 }
```

パイプラインは `Disproved`（蕴含なし）を返す → コンパイルエラー:

> パラメータ `b` が `divide` 呼び出しで `Positive` を満たすことが証明できません。`y`
> は関数入力から来ており、証明済みの境界がありません。if 分岐ガードで呼び出すことを検討してください:
> `if y > 0 { divide(x, y) }`。

YaoXiang は静的証拠を提供せずにランタイム値が精錬型パラメータに直接入ることを許可しない。これは制限ではなく——これはハード安全哲学の中核である。コンパイラが静的に証明できないコードは、コンパイルを通過することはできない。

#### 3.5 統一パイプラインとの関係

パス条件伝播は追加のメカニズムではない。これはコンパイル時証明パイプラインの制御フロー解析上の直接の延長である:

| 段階                 | 職責                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| パス条件収集         | コンパイラ制御フロー解析段階、各基本ブロックに仮説集合を注釈付け                                                                     |
| 検証条件生成         | 検証が必要な型制約に遭遇したとき、パス条件 + 実引数型情報をマージ                                                                    |
| 証明パイプライン評価 | コンパイラカーネル → SMT 加速 → Proved / Disproved / Unproven を得る                                                                 |
| 結果                 | `Proved` → 合格；`Disproved` → コンパイルエラー + 反例；`Unproven` → コンパイルエラー + 未解決命題（プログラマは証明関数を提供可能） |

新しいコンポーネントはない。特別な規則もない。パス条件は証明パイプラインの背景知識に過ぎない——型等価、借用制約と同じパイプライン、同じ予算システム。

### 4. コンパイル時証明パイプライン

すべてのコンパイル時検査が同じパイプラインを共有する。パイプラインの核心操作は**型検査**である——証明項の型が証明対象の命題に等しいか検査する。すべてが型検査。

```
コンパイル時に Bool 式の評価が必要（つまり証明項の構築が必要）
        │
        ├── 型等価（T1 == T2）
        │   → コンパイラが直接判定（構造等価）
        │
        ├── トークン衝突条件（!conflicting(tokens)）
        │   → フロー敏感活性解析（共有参照/線形属性追跡）
        │
        ├── 依存型簡約（n + m 簡約）
        │   → コンパイル時項書き換えシステム（βδι-簡約）
        │
        ├── コンパイル時述語（x > 0, forall...）
        │   → コンパイラ自身 + SMT 加速モジュール
        │
        └── ホーア論理蕴含式（P ⇒ Q）
            → コンパイラ + SMT 加速モジュール
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → コンパイル成功
             │ Disproved│  → コンパイルエラー + 反例
             │ Unproven │  → コンパイルエラー + 未解決命題
             └────┬─────┘
                  │
                  ▼
         プログラマが証明関数を書く（YaoXiang コード）
                  │
                  ▼
         型検査器が検証 ──→ Proved ──→ コンパイル成功
                  │
                  ▼
            検証失敗 → コンパイルエラー: "証明が成立しない"
```

#### 4.1 証明結果: 三値代数

コンパイル時評価は三つの結果を返す——これは停止問題の必然的帰結であり、証明論の自然な分画でもある:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → 停止、証明項構築済み、型検査合格。コンパイル続行。
- **Disproved(M)** → 停止、反例 M 存在。コンパイルエラー + 反例 + ソース位置。
- **Unproven**
  → 与えられたリソース上限内で証明構築できず。コンパイルエラー + 未解決命題 + 予算消費レポート。

**Unproven ≠ False。**
コンパイラが「証明できない」と言うことは命題が偽であることと同義ではない——現在の自動証明能力を超えているだけ。これは正直さであり、欠陥ではない。

予算のハード制限は停止問題の工学的解である。ノブは提供しない——提供した瞬間に「あなたのプログラムは停止すると思いますか」とユーザーに尋ねることになり、ユーザーは答えを知らないし、コンパイラも知らない。

#### 4.2 Unproven の後: プログラマが証明を書く

コンパイラが Unproven を返したとき、プログラマは**証明関数**を書くことができる——戻り型が証明対象の命題に等しい YaoXiang 関数。型検査器はこの関数を検証する——`add(a, b): Int`
を検証するのと同じメカニズムで。

```
命題  = 型
証明  = プログラム（その型の値）
検証  = 型検査（唯一の信頼ルート）
```

SMT ソルバーは独立した信頼境界ではない——それは**型検査器の加速モジュール**である。SMT は証明発見を助けるが、証明を検証するのは常に型検査器である。SMT が
`unsat`
を返したとき、コンパイラはその結果を型検査器が検証可能な証明項に再構成する。再構成が失敗した場合（SMT の推論ステップがコンパイラカーネルの推論規則を超える）、Unproven にフォールバック——プログラマは手動で証明関数を書くことができる。

```yaoxiang
# 命題: コンパイラが自動証明できない精錬属性
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# 証明: プログラマが関数を書き、戻り型が上記の命題
# 型検査器がこの関数を検証——add(a,b): Int を検証と完全に同じ
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # コンパイラはここで検証: 関数本体の型 = FirstIsMin(T, arr)
    ...
}
```

AI も不要、Coq へのエクスポートも不要、新しい概念も不要。**コンパイル時に自動証明できない属性 → プログラマが YaoXiang コードで証明を書く → 型検査器が検証。**
プロセス全体は滑らかな勾配である——コンパイラが簡単な証明を行い、脳を難しい証明に回す。

#### 4.3 パイプライン内の階層的依存

上記の評価器は同じインターフェースを共有するが、評価順序が存在する。型等価はすべての後続分析の前提条件；所有権/トークン検査は型情報に依存；精錬述語検証は前二層の結果に依存。コンパイラは層ごとに評価し、底层で失敗した式は上层に入らない——型エラーのあるプログラムで求解予算を浪費するのを避ける。

```
評価順序（同じパイプライン、階層的スケジューリング）
├── 第 0 層: 型等価（T1 == T2）
│   └── 構造単一化 → 失敗なら後続は無意味、直接 Disproved を返す
├── 第 1 層: 所有権/トークン衝突
│   └── フロー敏感活性解析 → 失敗ならメモリ安全が成立しない、直接 Disproved を返す
└── 第 2 層: 精錬述語/ホーア蕴含
    └── コンパイラ自身 → SMT 加速 → Proved / Disproved / Unproven を得る
```

各層は依然として `Proved/Disproved/Unproven` を返し、同じインターフェースと予算システムを共有する。

### 5. 三層関数の統一

| 階層             | 実行タイミング | 入力  | 出力 | 例                                             |
| ---------------- | -------------- | ----- | ---- | ---------------------------------------------- |
| 値レベル関数     | ランタイム     | 値    | 値   | `add: (a: Int, b: Int) -> Int = a + b`         |
| 型コンストラクタ | コンパイル時   | 型/値 | Type | `List: (T: Type) -> Type = { data: Array(T) }` |
| コンパイル時述語 | コンパイル時   | 値    | Type | `Positive: (x: Int) -> Type = { x > 0 }`       |

すべて同じ `name: type = value`
構文を使用。コンパイル時述語と型コンストラクタは同じコンパイル時証明パイプラインを通る——`{}`
が証明空間。

### 6. ループ: Floyd-Hoare 検証条件生成

ループは個別の `: Invariant(...)` や `: decreases(...)`
注釈を必要としない。変数上のコンパイル時述語型注釈が Floyd-Hoare 風のアサートを定義する——コンパイラは型注釈から検証条件を生成し、各代入が型を保持するか証明パイプラインが検査する。

核心メカニズム: 各代入操作は Hoare 三つ組 `{P} x := e {Q}` に対応し、検証条件は
`P ⇒ Q[e/x]`。コンパイラはループ本体に対して一度検証条件を生成する——証明パイプラインが帰納ステップを検証した段階で、すべての反復が自動的にカバーされる。

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # 注釈は i を参照；初期化時 i=0、検証: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # 検証: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # コンパイラはループ本体に対して一度 VC を生成。前提: s は SumUpTo(arr, i) を満たし、i は UpTo(arr.len) を満たす。
        #
        # s += arr[i]:
        #   検証義務: s_new は SumUpTo(arr, i) を満たす（現在の i は不変）
        #   s_new = s_old + arr[i] を代入:
        #     s_old + arr[i] == sum(arr[0..i+1]) が必要
        #     帰納仮定 s_old == sum(arr[0..i]) から、両辺に arr[i] を加える:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   コンパイラ + SMT: 線形算術、ミリ秒オーダー → Proved
        #
        # i += 1:
        #   i 変更 → 依存図で s の型注釈が i を参照 → 再検証をトリガ
        #   新しい検証対象: s は SumUpTo(arr, i_new) を満たす
        #   つまり s == sum(arr[0..i_new])、前ステップで保証済み → Proved
        s += arr[i]
        i += 1
    }
    return s  # このとき s: SumUpTo(arr, arr.len)、つまり s == sum(arr[0..arr.len])
}
```

ループ不変式は変数上の型注釈そのもの——プログラマは型を書き、コンパイラは帰納ステップを検査する。コンパイラは不変式を「発見」する必要も、「自動的に帰納を行う」必要もない——帰納証明を各代入操作の局所検証条件に分解し、証明パイプラインに分割して委ねる。

#### 6.1 依存追跡: 可変変数上の依存型

上記のメカニズムの前提は: コンパイラが `s` の型注釈 `SumUpTo(arr, i)` が `i`
を参照していることを知っていること——`i` が変更されたとき、`s`
の型制約もそれに応じて変化する。これにはコンパイラが**変数間の型依存グラフ**を維持する必要がある。

**データ構造**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# キーは被依存変数、値は型注釈内でその変数を参照している変数の集合
# 例: { i: {s}, j: {s, t}, ... }
```

**構築**: 型検査器が `mut v: Pred(... x ...) = init` を処理するとき、`Pred(...)`
引数内の自由変数参照を解析する。引数が現在のスコープ内の他の可変変数 `x`
を参照している場合、依存グラフに `x → v` を記録する。

**トリガ**: 被依存変数 `x` が代入されたとき、コンパイラは:

1. 依存グラフで `x` に依存するすべての変数 `{v₁, v₂, ...}` を検索
2. 各 `v` に対して検証条件を生成: `v の現在値が更新後の型 Pred(... x_new ...) を満たすか`
3. VC を証明パイプラインに送る

**代入順序依存**: 依存追跡は正しい代入順序を自然に強制する。`SumUpTo(arr, i)` の例:

```yaoxiang
# 正しい順序
s += arr[i]   # s_new は SumUpTo(arr, i+1) を満たす
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証 → True

# 間違った順序——コンパイラが拒否
i += 1        # i 変更 → s が SumUpTo(arr, i_new) を満たすかを再検証
              # s はまだ更新されていない、s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → コンパイルエラー: 変数 s が型 SumUpTo(arr, i_new) を満たさない
s += arr[i]   # 到達不能
```

**組合せ依存**: 1 つの変数が複数の変数に依存できる。型注釈 `{ v: Int; v == x + y }` は同時に `x` と
`y` の両方に依存する——どちらの変更も再検証をトリガする。

**証明パイプラインとの関係**: 依存追跡は VC 生成のトリガであり、独立した検証メカニズムではない。「いつ VC を生成する必要があるか」に答え、「VC が成立するか」に答えるのは証明パイプラインである。

### 7. 停止性検査

コンパイル時完全自動。コンパイラが証明できるループは通過、証明できないループは直接コンパイルエラーを報告——プログラマはコンパイラにループの停止性を自動解析させなければならない。半自動注釈の余地は提供しない。

#### 6.1 設計原則

コンパイラは 2 箇所から停止性証明に必要な情報を自動抽出する:

1. **変数型注釈**: 精錬型内の境界制約（`UpTo(n)` のような上界 `n` と下界 `0`）
2. **ループ本体の操作**: 各反復で変数に適用される操作

コンパイラは優先順位に従って 4 種のメトリック合成戦略を試行し、見つかれば停止する。

#### 6.2 戦略 1: 線形ランク関数の自動合成

変数に線形境界注釈がある場合、コンパイラは候補線形メトリックを列挙し SMT 検証する。

```
入力:
  変数 v₁: UpTo(u₁), v₂: UpTo(u₂), ...（境界のある変数）
  ループ条件 cond
  ループ本体内の代入集合

アルゴリズム:
  1. 型注釈から各変数の境界を抽出: [low_i, high_i]
  2. 候補メトリックを列挙: v_i, u_i - v_i, v_i - v_j, などの線形結合
  3. 各候補メトリック m について:
     - SMT が m ≥ 0 を検証（型境界から導出）
     - ループ本体の各実行パスについて、SMT が m' < m を検証（厳密減少）
  4. 条件を満たす線形結合を発見 → 停止性証明済み
```

カバレッジ範囲: 任意の変数が線形式（`v = a·v + b`）に代入され、境界型注釈を持つループ。`i += const`、`i -= const`、および二分探索型の区間収縮を含む:

```yaoxiang
# 二分探索: low = mid + 1 または high = mid
# メトリック high - low は両方のパスで厳密減少
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 戦略 2: 述語違反カウント——目標型から自動抽出メトリック <span style="color:orange">【実験的戦略】</span>

> ⚠️ **現在の状態: 実験的戦略、Phase 3 実装時に実際の実現可能性に基づいて含有を決定する。**
> この戦略は隣接交換操作（バブルソート、挿入ソート）に有効だが、非隣接操作（クイックソート partition、ヒープソート sift-down）は自動証明できない。カバレッジ境界は以下の表を参照。Phase
> 3 で実現不可能と検証された場合、この戦略は削除されるか将来の作業に降格される。

核心的洞察:**ユーザーの仕様がコンパイラの推論素材である。**
コンパイラに「ソートとは何か」を内蔵する必要はない——`Sorted`
の定義を読み、定義から自動的にメトリックを抽出する。

```
入力:
  目標型: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  ループ本体操作: 隣接要素の交換

アルゴリズム:
  1. 述語定義を解析: forall i in range: cond(i, arr)
  2. メトリックを自動生成: violation_count = |{ i | ¬cond(i, arr) }|
  3. 操作のメトリックへの影響を解析:
     - 隣接交換 arr[j], arr[j+1] = arr[j+1], arr[j]
     - インデックス j-1, j, j+1 の三対のみに影響
     - arr[j] > arr[j+1]（述語違反）の場合、交換後にこの対は述語を満たす
     - violation_count は少なくとも 1 減少
  4. 上界: n·(n-1)/2（最大隣接逆順数）、下界: 0
  → 停止性証明済み
```

**現在のカバレッジ範囲**:

| アルゴリズム   | 操作パターン   | 戦略 2 で証明可能？ | 理由                                        |
| -------------- | -------------- | :-----------------: | ------------------------------------------- |
| バブルソート   | 隣接交換       |         ✅          | violation_count は各交換で厳密減少          |
| 挿入ソート     | 隣接移動       |         ✅          | 各シフトが違反ペアを 1 つ解消               |
| 選択ソート     | 非隣接交換     |         ❌          | 単一交換で violation_count が増加する可能性 |
| クイックソート | partition 分区 |         ❌          | 非隣接交換、単調減少を保証しない            |
| ヒープソート   | sift-down      |         ❌          | ツリー操作、violation_count は非単調        |

**補完戦略**: クイックソートの場合、`low < high`
区間収縮は戦略 1（線形ランク関数）でカバーできる——外層 partition 再帰、各反復で区間が半減。戦略 1 と戦略 2 は補完的にカバーを提供し、実際のアルゴリズムの大部分の停止性は両者のいずれかで証明できる。ただし、戦略 2 の一般化（非隣接操作、ツリー操作）は未解決問題である。

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 戦略 3: 有界増分/減分パターン

`v += const`（正の定数）、変数に上界型注釈あり → メトリック `upper_bound - v` が各反復で `const`
ずつ減少、下界 0。これは戦略 1 の縮退ケースで、コンパイラは最初に高速処理する。

#### 6.5 戦略 4: 乗法スケーリングメトリックテンプレート

`v *= const`（const > 1）、変数に上下界型注釈あり。コンパイラは対数メトリックテンプレート
`ceil(log_const(upper/v))` を内蔵し、各乗算で const メトリックが 1 減少。

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # コンパイラ自動推論: メトリック ceil(log₂(n/i))、各 2 乗でメトリックが 1 減少
    i *= 2
}
```

#### 6.6 停止性と正当性の分離

停止性証明と正当性証明は独立している:

- **停止性**: 上記 4 種の戦略がループが有限ステップで終了することを自動証明
- **正当性**: ループ本体が目標型に向かって進むかは、コンパイル時証明パイプラインが検証条件で検査

両方が合格 → コンパイル成功。停止性証明済みだが正当性失敗 → コンパイルエラー + 反例。正当性証明済みだが停止性証明不能 → コンパイルエラーで解析不能な変数または操作を指示。両方失敗 → コンパイルエラーで 2 つの失敗理由を別々に報告。

#### 6.7 再帰関数の停止性検査

コンパイル時評価が必要な再帰関数について、コンパイラはパラメータの減少を検査する:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # コンパイラ解析: n-1 < n → 減少 → 停止
}

# コンパイル時使用——コンパイラは factorial がコンパイル時に停止することを保証
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120、コンパイル時に完了
```

| シナリオ                                     | 動作             |
| -------------------------------------------- | ---------------- |
| コンパイラが再帰減少を解析可能（`n-1` など） | コンパイル時評価 |
| 減少しない/減少の判定不能                    | コンパイルエラー |
| ランタイム呼び出し（型位置でない）           | 停止性検査不要   |

#### 6.8 ハード境界

`i = f(i)` で `f` が非可逆、非閉、非単調性保持——数学的に自動停止性証明が不可能。コンパイルエラー:

> このループは自動停止性証明ができません。ループ変数が解析不能な関数 `f`
> に依存しています。コンパイラが解析可能な反復パターンを使用してください。

これはコンパイラの失敗ではない。静的に安全性を証明できないコードは、コンパイルを通過することはできない。

### 8. SMT ソルバー: 型検査器の加速モジュール

SMT ソルバーは従来の言語では外部ツール（F\* が Z3 を呼び出す、Dafny が Z3 を呼び出す）。YaoXiang では、それは**型検査器の加速モジュール**である——コンパイラカーネル自身が直接判定できない場合にのみ呼び出される。SMT は証明発見を助けるが、証明を検証するのは型検査器である。

**信頼モデル**: 型検査器が唯一の信頼ルート。SMT ソルバーは加速モジュールである——証明発見を助けるが、SMT は独立した信頼境界ではない。コンパイラは Z3 の
`unsat`
結果を信頼する（F\*/Dafny 路線と一致——Z3 が誤る確率はコンパイラ自身のバグ率より低く、工学的実用選択）。真の信頼性の懸念は SMT 翻訳層で制御される——翻訳にバグがあれば、コンパイラは他のテストで露出する。

**インターフェース**: コンパイラ内部で SMT-LIB
2.6 標準形式に翻訳し、特定のソルバー API に束縛しない。SMT-LIB は ISO 標準で、Z3、CVC5、MathSAT、Yices すべてネイティブサポート。

**デフォルトバックエンド**:
Z3（MIT ライセンス、最も広範な文書とコミュニティ検証済み）。SMT-LIB 互換の代替として CVC5——ユーザーはコンパイル時にコンパイラフラグで切り替え可能。

「汎用ソルバー抽象層」は作らない——SMT-LIB が抽象層。未来に CVC5 が特定理論でブレークスルーを達成した場合、切り替えはバイナリを交換するだけで、 compiler コードの変更は不要。

```
コンパイル時 Bool 式
        │
        ├── コンパイラカーネルが直接判定可能（構造等価、単純算術、
        │   定数畳み込み後の自明な式）
        │   → 直接 Proved / Disproved を返す
        │
        └── コンパイラカーネルが直接判定不能（量化子、記号変数）
            → 依存型事前簡約（factorial(5) → 120）
            → SMT-LIB 形式に翻訳
            → Z3/CVC5 に送信（予算制限付き）
            → 戻り値: unsat → Proved  │  sat + モデル → Disproved  │  unknown → Unproven
```

**求解予算——スタック深度のようなハード制限**:

| 予算次元                 | デフォルト値 | 説明                                                                                                                           |
| ------------------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 求解ステップ数           | 10,000       | Z3 は線形算術に対して通常百ステップ以内。10,000 ステップで実際の述語の 99% をカバー。                                          |
| 時間                     | 100ms        | 単一述語が 100ms 超 = ユーザーは型注釈ではなくコンパイル時プログラムを書いている。100ms × 50 述語 = 5 秒のコンパイル時間上限。 |
| 量化子インスタンス化深度 | 3            | 三層のネスト量化子が実際のパターンをカバー。これを超えると論理パズルを書いている可能性が高い。                                 |

予算超過は Unproven を返し、コンパイルエラー + 述語位置 + 消費量。降格なし、ランタイムチェックなし、サイレント合格なし。

**なぜこれが実用的か**: 工学的に実際の述語の 95% は線形算術——`x > 0`、`arr.len > 0`、`0 <= idx < arr.len`——すべて決定可能フラグメント内、SMT ソルバーはミリ秒オーダーで返す。予算を超える複雑な述詞の稀なケースに遭遇した場合、プログラマは証明関数を書くだけでよい。

依存型は SMT 呼び出し前に事前簡約層を経る: `factorial(5)` は直接コンパイル時評価で `120`
に、`append([1,2], [3])` は直接 `[1,2,3]`
に評価される。これらの決定論的値計算は SMT 予算を消費しない。

プログラマは SMT の存在を知る必要がない。メンタルモデルは:**コンパイラが証明できれば合格、できなければエラー——コンパイラが不得手なら、関数を書いて証明を示せる**。

### 9. コンパイル時述語の組合せ

コンパイル時述語は Type を返す関数であり、組合せは関数合成を通じて自然に実現される:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. コード例

#### 9.1 除算の安全性

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ コンパイラは Positive(2) = { 2 > 0 } を検証 → True
# result = divide(10, 0)  # ❌ コンパイラは Positive(0) = { 0 > 0 } を検証 → False
```

#### 9.2 配列アクセスの安全性

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ コンパイラは InBounds(1, arr) = { 0 <= 1 and 1 < 3 } を検証 → True
# y = get(arr, 5)  # ❌ コンパイラは InBounds(5, arr) = { 0 <= 5 and 5 < 3 } を検証 → False
```

#### 9.3 ソートの正当性

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... ソートアルゴリズム実装 ...
    return result
}
```

#### 9.4 ループ: コンパイラ VC 生成

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. dispatch 分派パイプライン: コンパイル時とランタイムの統一分派

`assert` と `Assert` は同じ精錬型原語の両面である。分派パイプライン `dispatch`
は**述語の自由変数がコンパイル時に到達可能か**に基づいて、コンパイル時証明とランタイムチェックのいずれを行うかを自動決定する:

| 判定基準                                                               | モード          | 動作                                                                                |
| ---------------------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------- |
| すべての自由変数がコンパイル時既知（汎用パラメータ、コンパイル時定数） | **CompileTime** | 証明パイプラインへ: Proved → 削除、Disproved → コンパイルエラー、Unknown → 証明要求 |
| 自由変数がランタイムに由来（関数パラメータ、外部入力、mut 変数）       | **Runtime**     | ランタイム check を挿入し、フロー敏感仮説集合 Γ に精錬事実を注入                    |

**核心**：「判定不能」≠「反証」。CompileTime モードの Unknown は証明を要求し（暗黙の降格なし）、Runtime モードでは命題はコンパイル時には真偽の概念さえない——「ユーザーが負数を入力した可能性がある」に対して prover がどれだけ強くとも恒真証明を書くことはできず、ランタイム check が唯一の sound な選択である。これは prover の能力不足ではなく、理論的必然性である。

### 12. フロー敏感仮説集合 Γ : 最も強い後置条件伝播

コンパイラはフロー敏感（flow-sensitive）仮説集合 Γ を維持し、各制御フロー点で既知の成立命題を追跡する。

**SP（最も強い後置条件）伝播**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP 伝播
```

**mut 変数の kill set**: `mut`
変数が再代入された後、その変数に関するすべての仮説が Γ から削除される:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 が kill される
```

これは soundness のハード要件である——変数の値が変化すれば、旧仮説は無効になる。

**分岐合流**:
IF/ELSE または match 分岐が合流するとき、Γ は各分岐の仮説の交差を取る。すべての経路で成立する命題のみが分岐外に持ち出される。

### 13. 削除モデルの明確化: witness 削除 ≠ check 削除

RFC-027 の「精錬型はランタイムに**完全削除**」という主張は **proof
witness（証明トークン）**を指している——コンパイル時に検証済みの証明項はランタイムコードを生成しない。ただし、Runtime モードで dispatch が挿入する
**ランタイム check**
は保持される——値レベルで実行される Bool チェックであり、型レベルの witness ではない。

要約: witness は削除、check は保持。2 つの事象は衝突せず、RFC-027 の元の主張は変わらない。

## 詳細設計

### 構文変更

| 以前 (RFC-022)                        | 以後 (本 RFC)                                                       |
| ------------------------------------- | ------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | コンパイル時述語はパラメータ型として `(b: Positive(b))`             |
| `//! ensures: ExistsMax(result, arr)` | 戻り型は戻り値パラメータを使用 `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | 変数上のコンパイル時述語型注釈——Floyd-Hoare 不変式                  |
| `//! decreases: n`                    | コンパイラ全自動メトリック関数導出                                  |
| 仕様はコメント                        | 仕様は型システム                                                    |

### 構文

**コンパイル時述語に新しいキーワードはない。** `{}`
は証明空間で、既存の型定義構文と完全に一致する。コンパイル時述語は Type を返す関数そのもの——`name: (params) -> Type = { アサート }`。使用は関数呼び出し——`Positive(b)`、`IsMax(T, arr, result)`。

```bnf
# コンパイル時述語 = Type を返す関数、{} 内はコンパイラが検証するアサート
# 既存の関数/型構文を使用し、新しい BNF 規則は不要
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**述語適用の実引数はコンパイル時定数形式である必要がある**——リテラル、変数（名前による束縛）、または単一引数型適用（再帰的抽出）。実引数形式が定数式に変換できない場合は
**E1092** を報告、実引数の個数が述語パラメータと一致しない場合は **E1093**
を報告する——精錬制約は**決して静かに破棄されない**（以前は変換不能な実引数が制約を無音で消失させ、制約違反の束縛を静かに通過させていた）。

**新しい構文概念: 戻り値パラメータ**——`-> (name: Type)` の `name` は戻り値パラメータ。

戻り値パラメータは YaoXiang が既存の関数構文に導入する**唯一の構文概念**である。そのセマンティクス:

- `name` の値は `return` 文で提供される
- `name` は型シグネチャ内にのみ存在し、事後条件述語から参照される（例:
  `-> (result: IsMax(T, arr, result))`）
- `name` は関数本体のスコープに入らず、呼び出し側にも現れない
- 戻り値パラメータは**オプション**——事後条件がない場合、シグネチャは通常関数と完全に一致する（`-> Int`）、追加の負担なし

導入理由: 事後条件は「関数が返そうとしている値」を参照する必要がある。戻り値パラメータがない場合、コンパイラは述語に戻り値を参照させるために特別な規則（暗黙の変数
`$result` や `__retval__`
など）を通じてのみ実現できる。戻り値パラメータはこの参照を明示化する——単なるパラメータであり、値が呼び出し側ではなく
`return` によって提供される点が異なる。

**証明関数**は新しい概念ではない——戻り型がアサートされる命題に等しい YaoXiang 関数である。コンパイラが Unproven を返したとき、プログラマは証明関数を提供し、型検査器は任意の関数の戻り型を検証するのと同じ方法で検証する。新しい構文、新しいキーワード、新しい規則は不要。

### 型システムへの影響

- **型宇宙**: コンパイル時述語は Type₂ 層に位置する——値を受け取り Type を返す関数で、型コンストラクタと同じ階層
- **ジェネリックとの相互作用**: コンパイル時述語は汎用パラメータを取れる、たとえば
  `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **所有権との相互作用**: コンパイル時述語内の式は所有権規則に従い、読み取りのみ可能、書き込み不可
- **型推論**: コンパイル時述語のパラメータは HM 型推論に参加する

### ランタイム表現

コンパイル時述語のランタイム処理は **dispatch 分派結果**に従う:

- **CompileTime モード**（すべての自由変数がコンパイル時既知）: 証明通過後、witness トークンは完全削除。`Positive: (x: Int) -> Type = { x > 0 }`
  ——パラメータ `b: Positive(5)` のランタイム表現は単なる `Int`。精錬条件 `{ 5 > 0 }`
  は通過済み、削除。
- **Runtime モード**（ランタイムの自由変数存在）: ランタイム check を保持——値レベルで Bool チェックを実行し、フロー敏感仮説集合 Γ に注入。詳細は §11
  dispatch 分派パイプラインと §13 削除モデル明確化を参照。

コンパイル時述語を型位置に置く（例:
`f(x: Positive(x))`）ことはラッパ型を生成せず、余分なメモリを割り当てない。ただし `x`
がランタイム入力に由来する場合、**ランタイム Bool チェックが挿入される**。

**`ref`
との相互作用制約**: コンパイル時述語は不変借用または所有権が既に移動された値のみを参照できる。可変借用を参照するコンパイル時述語は、コンパイラが検証結果がランタイムにも成立することを保証できない——このような使用法は直接コンパイルエラー。

### コンパイラ変更

1. **パーサ**: コンパイル時述語は標準関数構文を使用し、追加の解析規則は不要
2. **コンパイル時証明パイプライン**: 統一された Proved/Disproved/Unproven 戻りインターフェース、自動戦略選択
3. **SMT 加速モジュール**: SMT-LIB 2.6 翻訳層、デフォルトバックエンド Z3、CVC5 代替
4. **型検査器カーネル**: 推論規則の実装——構造等価、βδι-簡約、全称量化子導入/消去。これが唯一の信頼ルートで、SMT とプログラマ証明はこれを通じて検証される
5. **検証条件生成**: WP/SP 計算 + ループ不変式証明義務
6. **エラー報告**: 反例フォーマット化 + 未解決命題レポート + ソース位置関連付け

### 後方互換性

- ✅ コンパイル時述語を使用しないコードは完全に不変
- ✅ コンパイル時述語は CompileTime モードでランタイムオーバーヘッドゼロ、Runtime モードで必要な Bool チェックのみ保持
- ⚠️ RFC-022 の `//!` 構文はサポートされない——ただし 022 は一度も実装されておらず、移行負担なし

## トレードオフ

### 利点

- **Curry-Howard 同型の完全な実現**: 型が命題、プログラムが証明、`name: Proposition = Proof`
- **統一性**: コンパイル時述語と通常関数は完全に同じ構文を使用し、概念分裂なし
- **SMT 透明性**: プログラマは SMT の存在を知る必要がなく、メンタルモデルは型検査と一致
- **漸進的採用**: 1 つのコンパイル時述語から始めて、徐々に対象を拡張可能
- **最小ランタイムオーバーヘッド**:
  CompileTime モードゼロオーバーヘッド、Runtime モード必要な Bool チェックのみ

### 欠点

- **コンパイル時間**: SMT 求解がコンパイル時間を増加させるが、予算ハード制限が上限を制御可能に保つ
- **自動証明境界**: 一階線形算術を超える複雑な述語はプログラマの証明関数を必要とする可能性がある。これは言語の欠陥ではなく——停止問題の必然的帰結である。コンパイラは Unproven を正直に報告し、True/False を偽装しない
- **学習曲線**: 効果的なコンパイル時述語と証明関数の記述には Curry-Howard 同型の基本直感の理解が必要
- **実装複雑性**: コンパイル時証明パイプラインの統一には精巧な設計が必要

### リスク緩和

- SMT 求解予算ハード制限（ステップ数 10,000 / 時間 100ms
  / インスタンス化深度 3）、予算超過で Unproven を返す
- 依存型事前簡約: 決定論的値計算を先に処理し、SMT は非決定的部分のみを処理
- Unproven は行き止まりではない: プログラマは証明関数を記述可能で、型検査器が検証——任意の関数の戻り型を検証と一致
- 増分検証: 変更モジュールのみを検証
- 明確なエラーメッセージ + 反例表示 + 予算消費レポート + 未解決命題 + 提案（コンパイラが提供可能な場合）

      → 決定済み: コンパイル時述語は不変借用または既に所有権が移動された値のみを許可。可変借用された値はコンパイル時述語に現れない。
- [x] **`forall` 述語違反カウントメトリックの非隣接操作への拡張？**
      → 拡張しない。現在のカバレッジ範囲（隣接交換、隣接移動）は戦略 1（線形ランク関数）で補完的にカバーされる——クイックソートの外層区間収縮は戦略 1 が対応、ヒープソートは戦略 1（配列インデックスパターン）が対応。どの戦略でも停止性を証明できないループは、コンパイラが直接エラー報告——これはハード安全哲学であり、欠陥ではない。将来、非学術的に実際のシナリオで 4 つの戦略すべてでカバーできないアルゴリズムがあれば、再議論する。
- [x] **線形ランク関数列挙の組合せ爆発**: 候補列挙上限は 3 つの有界変数。≤3 の場合、すべての線形結合を列挙し SMT で一つずつ検証。>3 の場合、単一変数メトリック（`v_i`、`u_i - v_i`）のみ試行し、失敗したら直接コンパイルエラー——「ループに >3 の有界変数があり、コンパイラが多変数メトリックを自動合成できません」とプログラマに指示。これは工学的妥協ではなく——より単純なループを書くようプログラマに強制する。
