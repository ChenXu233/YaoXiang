# RFC-011a: インターフェース実装と動的ディスパッチ

> **親RFC**: [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
>
> **本RFCはRFC-011 §2.1-2.4のインターフェース制約部分を補足・代替します。**

## 概要

RFC-011はジェネリクスシステムを定義しましたが、インターフェースの実装メカニズムについては詳しく説明していません。本文書では以下を補足します：

1. **インターフェース宣言**：インターフェースはパラメータ化型——`(Self: Type) -> Type`であり、実装時に具体的な型を渡す
2. **メソッド実装**：内部宣言と外部宣言の両方をサポート
3. **オーバーロードルール**：シグネチャが異なる場合はオーバーロードを許可し、シグネチャが同じ場合はエラー（オーバーライド禁止）
4. **デフォルト値**：フィールドの後に直接`= value`と記述
5. **動的ディスパッチ**：コンパイル時の型収集 + インターフェースマッチング、vtableなし

**コア設計**：

```yaoxiang
# 接口定义（参数化类型，Self 是显式类型参数）
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# 类型定义（内部声明）
Dog: Type = {
    x: Int = 10,
    Animal(Dog),  # 接口实例化，Self ↦ Dog
    speak: (self: &Dog) -> String = "Woof",
}

# 外部声明（重载）
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# 异构容器（动态分发）
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
```

**レシーバ表記規約**（訂正 2026-08-30、RFC-009の所有権セマンティクスに準拠）：

- メソッドのレシーバはシグネチャセマンティクスに従う：`&Self`
  = 借用（インターフェースのデフォルト規約——メソッド呼び出しはレシーバを消費しない）、`&mut Self`
  = 可変借用、値渡し`Self` = レシーバの消費（Move、RFC-009）。
- impl側シグネチャの`Self`はimpl型のエイリアス：インターフェースの`speak: (self: &Self)`はimplの`(self: &Dog)`
  / `(self: &Self)`とマッチする（Self↦impl型置換後完全に一致、§3）。
- 歴史的な例の値渡しレシーバ表記（`(self: Self)`）は借用を意味しており、本文書では明示的な`&Self`に統一移行されました。値渡し表記は今後「消費」セマンティクスのみを保持し、混在させません。

**除去された複雑性**：

- ❌ `impl`キーワードなし
- ❌ `Self`マジックキーワードなし（`Self`は明示的な型パラメータで、`T`と変わらない）
- ❌ `dyn Trait + 'a`注釈なし
- ❌ vtableなし（コンパイル時型収集 + 列挙型ラッパー）
- ❌ オーバーライドなし（オーバーロードルール統一）

## 動機

### RFC-011の不備

RFC-011はジェネリクスシステムを定義しましたが、以下については詳しく説明していません：

| 問題                     | 説明                                                     |
| ------------------------ | -------------------------------------------------------- |
| インターフェース宣言構文 | 型がインターフェースを実装していることをどう宣言するか？ |
| メソッド実装位置         | 内部宣言か外部宣言か？                                   |
| オーバーロードルール     | 同名のメソッドをどう処理するか？                         |
| デフォルト値構文         | フィールドにどうデフォルト値を設定するか？               |
| 動的ディスパッチ         | 異種コンテナをどう実装するか？                           |

### 設計目標

1. **簡潔**：`impl`キーワードが不要
2. **柔軟**：メソッド実装は内部・外部の両方をサポート
3. **統一**：オーバーロードルールを一貫させる
4. **便利**：デフォルト値構文が簡潔
5. **ゼロコスト**：vtableなし、コンパイル時型収集

### Rustとの比較

| 特性                 | Rust                           | YaoXiang                           |
| -------------------- | ------------------------------ | ---------------------------------- |
| インターフェース宣言 | `impl Animal for Dog { ... }`  | `Dog: Type = { Animal(Dog), ... }` |
| メソッド実装         | `impl`ブロック内               | 内部または外部                     |
| オーバーロード       | サポートなし                   | サポート（シグネチャが異なる場合） |
| デフォルト値         | `#[default]`が必要             | 直接`= value`と記述                |
| 異種コンテナ         | `Vec<Box<dyn Animal + 'a>>`    | `List(Animal)`                     |
| 動的ディスパッチ     | vtable検索                     | コンパイル時型収集                 |
| Selfキーワード       | マジックキーワード、暗黙の量化 | 明示的な型パラメータ、Tと対等      |

## 提案

### 1. インターフェース宣言

**コアルール**：インターフェースはパラメータ化型`(Self: Type) -> Type`であり、`Self`は明示的な型パラメータで、マジックキーワードではありません。実装時にはインターフェースを呼び出して具体的な型を渡します。

```yaoxiang
# 接口定义（与 RFC-011 泛型类型完全一致）
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# 类型声明实现接口
Dog: Type = {
    x: Int,
    Animal(Dog),  # 实例化接口，Self ↦ Dog
}
```

**コンパイラ処理**：

1. `Animal(Dog)`が`(Self: Type) -> Type`のインスタンス化呼び出しであることを識別
2. `Self ↦ Dog`置換を実行：`Animal(Dog)`を展開→`{ speak: (self: &Dog) -> String }`
3. `Dog`が要求されるすべてのメソッドを提供しているか確認（シグネチャマッチング）
4. パスした場合→実装証明を生成
5. 失敗した場合→コンパイルエラー

**展開等価**：

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),  # 展开为 Animal 的方法，保留来源标记
}

# 等价于（保留来源信息）
Dog: Type = {
    x: Int,
    speak: (self: &Dog) -> String,  # 来自 Animal，Self 已替换为 Dog
}
```

**なぜソースマークが必要か**：

- 直接展開するとソース情報が失われる
- ソースマークは実装証明の生成に使用される
- ランタイムは証明を通じて正しいメソッドを見つける

#### 1.1 Self型パラメータと型チェックのタイミング

`Self`はインターフェースの明示的な型パラメータであり、マジックキーワードではありません。`Animal: (Self: Type) -> Type`と`List: (T: Type) -> Type`は同じもの——`(Type) -> Type`型コンストラクタです。

**型チェックのタイミング**：

- **インターフェース定義時**：`{ speak: (self: &Self) -> String }`の`Self`は抽象型パラメータで、構文チェックのみが行われます。
- **インスタンス化地点**：`Animal(Dog)`時に`Self ↦ Dog`を実行し、展開後に完全な型チェック（シグネチャマッチング、メソッド存在性）を行います。

これにより、RFC-011で`Self`が暗黙のマジックキーワードであった問題を回避します——`Self`は型定義に出現せず、インターフェースのパラメータリストに一度だけ出現し、`T`と完全に対等です。

#### 1.2 フィールド名とメソッド名の名前空間

型のフィールド名とメソッド名は同じ名前空間を共有します。インターフェース展開後、インターフェースメソッド名が型フィールド名と衝突する場合、**コンパイルエラー**になります：

```yaoxiang
Drawable: (Self: Type) -> Type = {
    x: (self: &Self) -> Int,    // 方法叫 x
}

Point: Type = {
    x: Int,                     // 字段也叫 x
    Drawable(Point),            // ❌ 编译错误：Drawable 要求方法 x，与字段 x 冲突
}
```

フィールドアクセス`point.x`とメソッド呼び出し`point.x()`は構文上区別できません。名前空間を統一することで曖昧さを避けます。

### 2. メソッド実装

**コアルール**：メソッド実装は内部宣言と外部宣言の両方がサポートされています。

#### 2.1 内部宣言

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # 方法实现在内部
}
```

#### 2.2 外部宣言

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),
}

# 方法实现在外部
Dog.speak: (self: &Dog) -> String = "Woof"
```

#### 2.3 混合宣言

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # 部分方法在内部
}

# 部分方法在外部
Dog.play: (self: &Dog) -> Void = { ... }
```

**コンパイラ処理**：

1. すべての定義（内部と外部）を収集
2. シグネチャでグループ化（オーバーロード）
3. オーバーライドがないか確認（エラー）
4. インターフェースの完全性を確認
5. 実装証明を生成

### 3. オーバーロードとオーバーライド

**コアルール**：

- シグネチャが異なる → オーバーロード → 許可
- シグネチャが同じ → オーバーライド → エラー

#### 3.1 オーバーロード（許可）

```yaoxiang
# 参数类型不同，允许重载
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"
```

#### 3.2 オーバーライド（禁止）

```yaoxiang
# 签名完全相同，禁止覆盖
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ 报错：覆盖不允许
```

**エラーメッセージ**：

```
错误：Dog.speak(self: &Dog) -> String 重复定义
  --> 文件2:5:1
  |
5 | Dog.speak: (self: &Dog) -> String = "Bark"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 重复定义
  |
  --> 文件1:3:1
  |
3 | Dog.speak: (self: &Dog) -> String = "Woof"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 第一个定义
```

#### 3.3 ルールの統一

**内部宣言と外部宣言は同じオーバーロード/オーバーライドルールに従います**：

```yaoxiang
# 内部声明
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

# 外部声明（重载，允许）
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# 外部声明（覆盖，禁止）
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ 报错
```

### 4. デフォルト値

**コアルール**：フィールドの後に直接`= value`と記述し、コンストラクタを省きます。

```yaoxiang
Dog: Type = {
    x: Int = 10,  # 默认值
    y: Int = 20,  # 默认值
    Animal(Dog),
}
```

**コンパイラが生成するコンストラクタ**：

```yaoxiang
# 所有字段都有默认值 → 生成无参构造函数
Dog.new: () -> Dog = { x: 10, y: 20 }

# 部分字段有默认值 → 生成部分参数构造函数
Dog.new: (x: Int) -> Dog = { x: x, y: 20 }
Dog.new: (y: Int) -> Dog = { x: 10, y: y }

# 全参数构造函数
Dog.new: (x: Int, y: Int) -> Dog = { x: x, y: y }
```

**外部宣言のデフォルト値**：

```yaoxiang
Dog: Type = {
    x: Int,
    y: Int,
    Animal(Dog),
}

# 外部声明默认值
Dog.x: Int = 10
Dog.y: Int = 20
```

**内部宣言と等価**です。

### 5. コンパイラ実装

#### 5.1 インターフェース記述子

```rust
// 编译器内部：接口描述符
struct InterfaceDescriptor {
    name: String,
    self_param: TypeParam,     // Self 类型参数
    methods: Vec<MethodSignature>,
}
```

#### 5.2 型定義

```rust
// 编译器内部：类型定义
struct TypeDefinition {
    name: String,
    fields: Vec<Field>,
    interface_instantiations: Vec<InterfaceInstantiation>,
}

// 接口实例化（Self ↦ ConcreteType）
struct InterfaceInstantiation {
    interface: InterfaceId,
    self_type: TypeId,          // Self 被替换为的具体类型
    methods: HashMap<MethodId, FunctionBody>,
}
```

#### 5.3 実装証明

```rust
// 编译器内部：实现证明
struct ImplementationProof {
    type_id: TypeId,
    interface_id: InterfaceId,
    methods: Vec<MethodPointer>,
}
```

#### 5.4 コンパイルフロー

```
1. 解析类型定义，收集接口实例化声明（Animal(Dog)）
2. 对每个接口实例化执行 Self ↦ ConcreteType 替换
3. 展开接口方法签名，检查签名匹配
4. 收集所有方法定义（内部和外部）
5. 按签名分组（重载）
6. 检查覆盖（报错）
7. 检查接口完整性
8. 生成实现证明
```

### 6. 動的ディスパッチ

**コア設計**：コンパイル時型収集 + インターフェースマッチング、vtableなし。

#### 6.1 異種コンテナ

`Animal`は`(Self: Type) -> Type`です。`List(Animal)`は未インスタンス化のインターフェース型コンストラクタを**存在型**（existential）として使用します：`∃S. Animal(S)`——「ある型Sが存在し、SはAnimal(S)を実装する」。

```yaoxiang
# 接口定义
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# 类型定义
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

Cat: Type = {
    y: Int,
    Animal(Cat),
    speak: (self: &Cat) -> String = "Meow",
}

# 异构容器 — Animal 未实例化 = 存在类型
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
animals[1].speak()  # "Meow"
```

**所有権セマンティクス**：異種コンテナへの配置はMoveセマンティクス（RFC-009）です。`Dog.new()`は`AnimalGroup::Dog`列挙型バリアントに移動され、元の変数は使用できなくなります。

```yaoxiang
dog = Dog.new()
animals: List(Animal) = [dog]
# dog.speak()  ← ❌ 编译错误：dog 已被 move
```

#### 6.2 コンパイル時型収集

**コア戦略：所有権追跡、インクリメンタル構築。**
コンパイル時にインターフェースを実装するすべての型をスキャンするのではなく、各`List(Animal)`の**所有権操作地点**でインクリメンタルに収集します：

```yaoxiang
// 构造点
animals: List(Animal) = [Dog.new()]       // AnimalGroup = { Dog(Dog) }

// append 点
animals.append(Cat.new())                  // 编译器在 append 处看到 Cat → 扩展为 { Dog, Cat }
animals.append(Bird.new())                 // 再扩展 { Dog, Cat, Bird }
```

**コンパイラ処理**（インクリメンタル）：

1. `List(Animal)`が初めて構築される地点に遭遇 → 初期列挙型を生成（現在のコンパイルユニット内で既知のすべての構築型）
2. `append` / `push`
   / インデックス代入のたびに → 値型が列挙型にすでに含まれているか確認；含まれていなければ列挙型バリアントを拡張
3. 最終列挙型に対してモノモーフィック`match`ディスパッチコードを生成
4. コンパイルユニット間：LTO（リンク時最適化）に依存して列挙型バリアントをマージ。`Animal`は存在型としてコンパイルユニット境界を渡る際、各ユニットは部分的な列挙型バリアントを生成し、リンクフェーズで完全な列挙型にマージされます。

**自動生成される列挙型**：

```yaoxiang
# 编译器自动生成（用户不感知）
AnimalGroup: Type = {
    Dog(Dog),
    Cat(Cat),
    Bird(Bird),    # ← append(Bird.new()) 触发增量扩展
}

# List(Animal) 内部等价于 List(AnimalGroup)
```

#### 6.3 インターフェースマッチングチェック

**重要な洞察**：インターフェースマッチングはコンパイル時チェックであり、型が動的にロードされるプラグインから来る場合でも同様です。

```yaoxiang
# 插件系统
plugin = load_plugin("bird.so")

# 编译器检查：plugin.create_bird() 返回类型必须实现 Animal
bird: Animal = plugin.create_bird()  # 编译期检查，存在类型

# 放入异构容器 —— append 点触发枚举扩展
animals: List(Animal) = [Dog.new(), Cat.new()]
animals.append(bird)                 # 编译器：(1) 验证 bird 实现了 Animal (2) 扩展枚举
```

**コンパイラ処理**：

1. `append`引数の戻り値型を確認
2. その型が対象インターフェースを実装しているかを検証
3. パスした場合 → 列挙型を拡張し、配置を許可
4. 失敗した場合 → コンパイルエラー

#### 6.4 ランタイムディスパッチ

**呼び出しフロー（コンパイル時列挙型match、ImplementationProofはすでに消去済み）：**

```
animals[0].speak()
  ↓
编译器生成的 match:
  match animals[0] {
    AnimalGroup.Dog(d) => d.speak(),
    AnimalGroup.Cat(c) => c.speak(),
    AnimalGroup.Bird(b) => b.speak(),
  }
```

**ブランド投影**（RFC-009aとのインタラクション）：matchのパターンバインディング`AnimalGroup.Dog(d)`はブランドツリーに`#animals[0].Dog`サブブランドを生成し、フィールド投影（`#42.field_x`）と等価です。`d.speak()`が作成する`ReadToken(d)`ブランドチェーンは`animals → animals[0] → d → ReadToken(d)`であり、借用チェッカーはブランドツリーのプレフィックスマッチングで競合を検証します。

**インデックスアクセスの型**：`animals[0]`は`&AnimalGroup`（コンパイラ生成の列挙型）を返します。ユーザーは`&mut Animal`を直接取得できません。可変アクセスはインターフェースメソッドを通じて間接的に実装されます（例：`animals[0].mutate()`は内部で`AnimalGroup::Dog(d) => d.mutate()`に展開されます）。

**vtableとの比較**：

|                          | vtable（Rust）                    | コンパイル時列挙型（YaoXiang）           |
| ------------------------ | --------------------------------- | ---------------------------------------- |
| 検索方法                 | vtableポインタ → メソッドポインタ | 列挙型match → 直接呼び出し               |
| ランタイムオーバーヘッド | 1回の間接アドレス指定             | branch（CPU分岐予測で最適化可能）        |
| コンパイル時生成         | vtable                            | 列挙型 + match                           |
| ユーザー注釈             | `dyn Trait + 'a`が必要            | 不要                                     |
| ImplementationProof      | 該当なし                          | コンパイル時消去、ランタイムに存在しない |

**YaoXiangの優位性**：

- ブランド注釈が不要
- コンパイル時型安全
- ユーザーに透過的（`dyn Animal`を書く必要なし）
- ImplementationProofは純粋にコンパイル時の概念で、ランタイムオーバーヘッドゼロ

#### 6.5 制限とスコープ

**当期（単一コンパイルユニット）：**
完全サポート。所有権追跡がすべての`append`/構築地点をカバーし、列挙型がインクリメンタルに構築されます。

**コンパイルユニット間：**
LTO（リンク時最適化）に依存して列挙型バリアントをマージ。`Animal`は存在型（`∃S. Animal(S)`）としてコンパイルユニット境界を渡ります。各ユニットは部分的な列挙型バリアントを生成し、リンクフェーズでマージされます。

**サポート対象外：**
ランタイム動的型（完全なダックタイピング）。型の集合はコンパイル時に完全に既知です。

#### 6.6 実装ノート（フェーズ3、v1で実装済み）

§6のセマンティクス（異種コンテナ、コンパイル時メンバーシップチェック、実際の型によるディスパッチ、コンパイル時に閉じられた型集合）はすべて実装済みで、実装形態はメカニズム層で以下のように具体化されています：

- **型収集**：`ImplementationProof`に基づいてコンパイルユニット全体で実装型セットを一度に収集し、§6.2の「所有権操作地点ごとのインクリメンタル収集」を置き換えます。単一コンパイルユニット内では両者は意味的に等価です（余分な死バリアントは無害）；インクリメンタル収集の価値はクロスユニットシナリオにあり、v2に分類されます（以下参照）。
- **表現**：コンパイラが`Animal$Group`バリアント型を合成し、純粋なIR/バイトコード/ランタイム成果物（命令`CreateVariant`/`VariantTag`/`VariantPayload`、ランタイム値`RuntimeValue::Enum`）。MonoTypeは認識しません——typecheckレイヤーのユーザー可視型は依然としてインターフェース名です。存在型の位置に入る各具象値は自動的にバリアント値にラップされます（統一された不透明表現、§6.4セマンティクス）。
- **ラッピング地点**：typecheckが「具象 vs 存在」判定の位置（注釈付きlet/呼び出し実引数/return/リストリテラル要素）でターゲット付きウォークスルーを行い、spanキー強制テーブルを生成；IR生成はspanに従ってラッピングを注入。ラッピング漏れはランタイムガードによって明示的に拒否されます（`VariantTag`/`VariantPayload`検証値が名前付きグループのバリアント値である必要がある）、最悪の場合テストフェーズで明示的なランタイムエラーが発生し、誤ったデータが静かに生成されることは決してありません。
- **ディスパッチ**：バリアント番号比較ジャンプチェーン、各アームはペイロードをアンラップした後、具体的なメソッドを静的に呼び出します；RFC-004再バインディング形式（`Type.method = fn[n]`）はバインディング位置に従って再配置された後、ディスパッチに参加します。
- **分離**：レガシートレイト制約（`Drawable: Type = {..}`形式、ジェネリックパラメータなし）はバリアントディスパッチを経由せず、動作は変更されません。

**v1境界（後続フェーズ）**：クロスユニットLTOバリアントマージ（§6.5）；Group値へのパターンマッチング（バリアントパターンに対するmatchのIRサポートに依存）；リフレクションインタラクション；コンテナへのMoveセマンティクス；`Any`/型変数経由フローと推論ラムダ境界（フォールバック = ランタイムガード）。

## トレードオフ

### 利点

1. **簡潔**：`impl`キーワードが不要
2. **柔軟**：メソッド実装は内部・外部の両方をサポート
3. **統一**：オーバーロードルールが一貫
4. **便利**：デフォルト値構文が簡潔
5. **ゼロコスト**：vtableなし、コンパイル時型収集
6. **型安全**：インターフェースマッチングはコンパイル時チェック
7. **ユーザーに透過的**：`dyn Animal + 'a`を書く必要なし

### 欠点

1. **制限**：ランタイム動的型（完全なダックタイピング）をサポートしない
2. **コンパイル時オーバーヘッド**：各インターフェースに対して列挙型バリアントとmatchディスパッチコードを生成する必要がある
3. **型集合**：コンパイル時に完全に既知である必要がある（単一コンパイルユニット内）

### 緩和策

1. **プラグインシステム**：コンパイル時インターフェースマッチングチェックでサポート
2. **型集合**：所有権追跡、インクリメンタル構築——各`append`/構築地点で収集、グローバルスキャンではない
3. **コンパイルユニット間**：列挙型バリアント集合をリンク時にマージ、リンク時モノモーフィゼーションとメカニズムを共有

## 代替案

| 案                       | 採用しない理由                           |
| ------------------------ | ---------------------------------------- |
| `impl`キーワード         | 構文の複雑さが増す                       |
| vtable（`dyn Trait`）    | ブランド注釈（`'a`）が必要               |
| 完全なダックタイピング   | ランタイムオーバーヘッド、型安全ではない |
| 列挙型ラッピング（手動） | ユーザー負担が大きい                     |

## RFC-009との関係

**ブランドとインターフェース実装**：

- インターフェース実装は型層にあり、ブランドには関与しない
- ブランドは借用証明層にある（RFC-009a）
- 両者は直交しており、互いに影響しない

**動的ディスパッチとブランド**：

- 動的ディスパッチは実装証明を使用し、ブランド注釈は不要
- 実装証明はコンパイル時に生成され、ランタイム検索はゼロ
- `dyn Trait + 'a`の複雑さを回避

**異種コンテナの所有権**：

- `List(Animal)`への配置はMoveセマンティクス（RFC-009）、元の変数はアクセス不可
- インデックスアクセス`animals[0]`は`&AnimalGroup`（コンパイラ生成の列挙型）を返し、ブランド投影チェーンは`animals → animals[0] → enum_variant → field`
- 可変アクセスはインターフェースメソッドを通じて間接的に実装され、`&mut AnimalGroup`をユーザーに公開しない

## インターフェース継承

インターフェースは他のインターフェースを含むことができます。**新しい構文を導入しません**——型がインターフェースを宣言するのと同じ構文位置を使用します：

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                       # Pet 继承 Animal — 无新关键字
    name: (self: &Self) -> String,
}

# Dog 实现 Pet 时，必须同时满足 Animal 和 Pet 的所有方法
Dog: Type = {
    x: Int,
    Pet(Dog),
    speak: (self: &Dog) -> String = "Woof",  # 来自 Animal
    name: (self: &Dog) -> String = "Buddy",  # 来自 Pet
}
```

**設計原則：**
継承は存在しますが、乱用は推奨されません。主な組み合わせ方は複数のインターフェースインスタンス化（`Dog: Type = { Animal(Dog), Pet(Dog), ... }`）によるものです。型はそれが満たすすべてのインターフェースを直接宣言でき、継承ツリーを通じて表現する必要はありません。インターフェース継承は明確な「is-a」階層がある場合にのみ使用します。

**コンパイラ処理：**
継承チェーンを展開します。`Pet(Self)`を`{ Animal(Self) のすべてのメソッド, name: ... }`に展開。`Dog`が`Pet(Dog)`を宣言するとき、`Self ↦ Dog`で、コンパイラは`Dog`が`Animal(Dog)`と`Pet(Dog)`のすべてのメソッドを同時に満たすことを検証します。

**インターフェース継承におけるSelf置換**：`Pet: (Self: Type) -> Type = { Animal(Self), ... }`では、`Animal(Self)`の`Self`は`Pet`の`Self`パラメータであり、遅延置換されます。`Dog`が`Pet(Dog)`を実装するとき、`Self ↦ Dog`、`Animal(Self)`は`Animal(Dog)`になります。これはジェネリック関数のパラメータ渡しセマンティクスと完全に一致します。

## デフォルトメソッド実装

インターフェースはメソッドのデフォルト実装を提供できます。実装型はオーバーライドするか、デフォルト実装を継承するかを選択できます：

```yaoxiang
fmt: (Self: Type) -> Type = {
    display: (self: &Self) -> String,                      # 必须实现
    debug: (self: &Self) -> String = self.display(),       # ✅ 引用同接口方法
    summary: (self: &Self) -> String = f"<{self.name}>",  # ❌ 编译错误：self.name 不在 fmt 里
}
```

**コア制約：インターフェースは上位実装を仮定できません。**
デフォルトメソッドは同じインターフェースで宣言されたメソッドのみを参照できます。具体的な型のフィールドや他のインターフェースメソッドはデフォルトメソッドには見えません——インターフェースは閉じた契約であり、実装型のポケットに手を伸ばすことはできません。この制約に違反すると**インターフェース定義時**に直接エラーが報告されます。

**継承は下位実装を仮定できます：**
インターフェース`Pet(Self)`が`Animal(Self)`を継承するとき、`Pet`のデフォルトメソッドは`Animal`で宣言されたメソッドを使用できます——継承しているため、保証されているからです。

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                                              # 继承
    name: (self: &Self) -> String,
    introduce: (self: &Self) -> String = self.name() + " says " + self.speak(),  # ✅ speak 来自继承的 Animal
}
```

**コンパイル時動作：** 型がインターフェースを実装するとき、各メソッドについて：

1. 型が提供している → 型のメソッドを使用
2. 型が提供していない、インターフェースにデフォルトがある → コンパイラがデフォルト実装を型にインライン化（vtableオーバーヘッドゼロ）
3. 型が提供していない、インターフェースにデフォルトがない → コンパイルエラー

**設計原則：** デフォルトメソッドは`Copy`/`Clone`の自動派生メカニズムに似ています——コンパイラが必要に応じて自動生成し、ユーザーはオーバーライドできます。`virtual`/`override`/`super`キーワードを導入しません。

## オープンな問題

- [x] ~~インターフェース継承（インターフェースは他のインターフェースを継承できる）~~
      → サポート、新しい構文なし。`Pet: (Self: Type) -> Type = { Animal(Self), ... }`
- [x] ~~デフォルトメソッド実装（インターフェースはデフォルト実装を提供できる）~~
      → サポート、Copy自動派生に類似。インターフェースが本体を提供、コンパイラはオンデマンドでインライン化
- [x] ~~Selfを暗黙のマジックキーワードとして扱う~~
      → 排除。`Self`は明示的な型パラメータ、インターフェースは`(Self: Type) -> Type`
- [ ] インターフェース制約の高度な使用法（関連型、GAT）—— 関連型はジェネリックインターフェースパラメータで実装（`Container: (Self: Type, T: Type) -> Type`）、GATはさらなる設計が必要
- [ ] クロージャとのインタラクション（クロージャがインターフェースを実装）—— 初期戦略：クロージャはインターフェースを直接実装できず、wrapper型が必要。匿名型のインターフェース実装は今後のRFCに先送り
