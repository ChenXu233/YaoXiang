# RFC-011a: インターフェース実装と動的ディスパッチ

> **親 RFC**: [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
>
> **本 RFC は RFC-011 §2.1-2.4 のインターフェース制約部分を補完し、置換する。**

## 概要

RFC-011 はジェネリクスシステムを定義したが、インターフェース実装メカニズムを詳細には規定していない。本ドキュメントは以下を補完する：

1. **インターフェース宣言**：インターフェースはパラメータ化型——`(Self: Type) -> Type`
   であり、実装時に具体的な型を渡す
2. **メソッド実装**：内部宣言と外部宣言の両方をサポート
3. **オーバーロードルール**：シグネチャが異なればオーバーロードを許可し、シグネチャが同じ場合はエラー（オーバーライド禁止）
4. **デフォルト値**：フィールドの直後に `= value` を記述
5. **動的ディスパッチ**：コンパイル時の型収集 + インターフェースマッチング、vtable なし

**コア設計**：

```yaoxiang
# インターフェース定義（パラメータ化型、Self は明示的な型パラメータ）
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# 型定義（内部宣言）
Dog: Type = {
    x: Int = 10,
    Animal(Dog),  # インターフェースのインスタンス化、Self ↦ Dog
    speak: (self: &Dog) -> String = "Woof",
}

# 外部宣言（オーバーロード）
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# 異種コンテナ（動的ディスパッチ）
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
```

**レシーバのスペル規約**（正誤表 2026-08-30、RFC-009 所有権セマンティクスと連携）：

- メソッドレシーバはシグネチャセマンティクスに従う：`&Self`
  = 借用（インターフェースのデフォルト規約——メソッド呼び出しはレシーバを消費しない）、 `&mut Self`
  = 可変借用、値渡し `Self` = レシーバを消費（Move、RFC-009）。
- impl 側シグネチャの `Self` は impl 型のエイリアス：インターフェース `speak: (self: &Self)` とimpl
  `(self: &Dog)` / `(self: &Self)` の両方がマッチする（Self↦impl 型への置換後、完全に一致、§3）。
- 歴史的な例の値渡しレシーバのスペル（`(self: Self)`）は借用を意味していたが、本ドキュメントでは明示的な
  `&Self` に統一移行済み；値渡しのスペルは今後「消費」セマンティクスのみを保持し、混在しない。

**除去される複雑性**：

- ❌ `impl` キーワードなし
- ❌ `Self` マジックキーワードなし（`Self` は明示的な型パラメータであり、`T` と同じ）
- ❌ `dyn Trait + 'a` 注釈なし
- ❌ vtable なし（コンパイル時の型収集 + 列挙型ラッパー）
- ❌ オーバーライドなし（オーバーロードルールで統一）

## 動機

### RFC-011 の不足

RFC-011 はジェネリクスシステムを定義したが、以下を詳細には規定していない：

| 問題                     | 説明                                                     |
| ------------------------ | -------------------------------------------------------- |
| インターフェース宣言構文 | 型がインターフェースを実装していることをどう宣言するか？ |
| メソッド実装の位置       | 内部宣言か外部宣言か？                                   |
| オーバーロードルール     | 同名メソッドの処理方法は？                               |
| デフォルト値の構文       | フィールドのデフォルト値設定方法は？                     |
| 動的ディスパッチ         | 異種コンテナの実現方法は？                               |

### 設計目標

1. **簡潔**：`impl` キーワードが不要
2. **柔軟**：メソッド実装は内部・外部両方をサポート
3. **統一**：オーバーロードルールが一貫
4. **便利**：デフォルト値構文が簡潔
5. **ゼロオーバーヘッド**：vtable なし、コンパイル時の型収集

### Rust との比較

| 特性                 | Rust                           | YaoXiang                           |
| -------------------- | ------------------------------ | ---------------------------------- |
| インターフェース宣言 | `impl Animal for Dog { ... }`  | `Dog: Type = { Animal(Dog), ... }` |
| メソッド実装         | `impl` ブロック内              | 内部または外部                     |
| オーバーロード       | サポートなし                   | サポート（シグネチャが異なる場合） |
| デフォルト値         | `#[default]` が必要            | 直接 `= value` を記述              |
| 異種コンテナ         | `Vec<Box<dyn Animal + 'a>>`    | `List(Animal)`                     |
| 動的ディスパッチ     | vtable 検索                    | コンパイル時の型収集               |
| Self キーワード      | マジックキーワード、暗黙の量化 | 明示的な型パラメータ、T と同等     |

## 提案

### 1. インターフェース宣言

**コアルール**：インターフェースはパラメータ化型 `(Self: Type) -> Type` であり、`Self`
は明示的な型パラメータであり、マジックキーワードではない。実装時はインターフェースを呼び出し、具体的な型を渡す。

```yaoxiang
# インターフェース定義（RFC-011 ジェネリック型と完全に同じ）
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# 型宣言によるインターフェースの実装
Dog: Type = {
    x: Int,
    Animal(Dog),  # インターフェースのインスタンス化、Self ↦ Dog
}
```

**コンパイラの処理**：

1. `Animal(Dog)` が `(Self: Type) -> Type` のインスタンス化呼び出しであることを識別
2. `Self ↦ Dog` 置換を実行：`Animal(Dog)` を展開 → `{ speak: (self: &Dog) -> String }`
3. `Dog` が要求されるすべてのメソッドを提供しているかチェック（シグネチャ一致）
4. パスした場合 → 実装証明を生成
5. 失敗した場合 → コンパイルエラー

**展開の等価性**：

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),  # Animal のメソッドに展開、出典マークを保持
}

# 以下と等価（出典情報を保持）
Dog: Type = {
    x: Int,
    speak: (self: &Dog) -> String,  # Animal 由来、Self は Dog に置換済み
}
```

**なぜ出典マークが必要か**：

- 直接展開すると出典情報が失われる
- 出典マークは実装証明の生成に使用される
- ランタイムは証明を通じて正しいメソッドを見つける

#### 1.1 Self 型パラメータと型検査のタイミング

`Self`
はインターフェースの明示的な型パラメータであり、マジックキーワードではない。`Animal: (Self: Type) -> Type`
と `List: (T: Type) -> Type` は同じもの——`(Type) -> Type` 型コンストラクタ。

**型検査のタイミング**：

- **インターフェース定義時**：`{ speak: (self: &Self) -> String }` の `Self`
  は抽象的な型パラメータであり、構文チェックのみを行う。
- **インスタンス化点**：`Animal(Dog)` 時に `Self ↦ Dog`
  を実行し、展開後に完全な型チェック（シグネチャ一致、メソッド存在）を行う。

これは RFC-011 における `Self` を暗黙のマジックキーワードとする問題を回避する——`Self`
は型定義には現れず、インターフェースのパラメータリストに一度だけ現れ、`T` と完全に同等である。

#### 1.2 フィールド名とメソッド名の名前空間

型のフィールド名とメソッド名は同じ名前空間を共有する。インターフェース展開後、インターフェースメソッド名と型フィールド名が衝突した場合、**コンパイルエラー**となる：

```yaoxiang
Drawable: (Self: Type) -> Type = {
    x: (self: &Self) -> Int,    // メソッド名 x
}

Point: Type = {
    x: Int,                     // フィールド名も x
    Drawable(Point),            // ❌ コンパイルエラー：Drawable はメソッド x を要求するが、フィールド x と衝突
}
```

フィールドアクセス `point.x` とメソッド呼び出し `point.x()`
は構文上区別できない。統一名前空間で曖昧さを回避する。

### 2. メソッド実装

**コアルール**：メソッド実装は内部宣言と外部宣言の両方をサポートする。

#### 2.1 内部宣言

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # メソッド実装は内部
}
```

#### 2.2 外部宣言

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),
}

# メソッド実装は外部
Dog.speak: (self: &Dog) -> String = "Woof"
```

#### 2.3 混合宣言

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # 一部のメソッドは内部
}

# 一部のメソッドは外部
Dog.play: (self: &Dog) -> Void = { ... }
```

**コンパイラの処理**：

1. すべての定義を収集（内部と外部）
2. シグネチャでグループ化（オーバーロード）
3. オーバーライドがあるかチェック（エラー）
4. インターフェースの完全性をチェック
5. 実装証明を生成

### 3. オーバーロードとオーバーライド

**コアルール**：

- シグネチャが異なる → オーバーロード → 許可
- シグネチャが同じ → オーバーライド → エラー

#### 3.1 オーバーロード（許可）

```yaoxiang
# 引数の型が異なる、オーバーロードを許可
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"
```

#### 3.2 オーバーライド（禁止）

```yaoxiang
# シグネチャが完全に同じ、オーバーライドを禁止
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ エラー：オーバーライドは許可されない
```

**エラーメッセージ**：

```
エラー：Dog.speak(self: &Dog) -> String の重複定義
  --> ファイル2:5:1
  |
5 | Dog.speak: (self: &Dog) -> String = "Bark"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 重複定義
  |
  --> ファイル1:3:1
  |
3 | Dog.speak: (self: &Dog) -> String = "Woof"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 最初の定義
```

#### 3.3 ルールの統一

**内部宣言と外部宣言は同じオーバーロード/オーバーライドルールに従う**：

```yaoxiang
# 内部宣言
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

# 外部宣言（オーバーロード、許可）
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# 外部宣言（オーバーライド、禁止）
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ エラー
```

### 4. デフォルト値

**コアルール**：フィールドの直後に `= value` を記述し、コンストラクタを省略する。

```yaoxiang
Dog: Type = {
    x: Int = 10,  # デフォルト値
    y: Int = 20,  # デフォルト値
    Animal(Dog),
}
```

**コンパイラが生成するコンストラクタ**：

```yaoxiang
# すべてのフィールドにデフォルト値あり → 引数なしコンストラクタを生成
Dog.new: () -> Dog = { x: 10, y: 20 }

# 一部のフィールドにデフォルト値あり → 一部引数コンストラクタを生成
Dog.new: (x: Int) -> Dog = { x: x, y: 20 }
Dog.new: (y: Int) -> Dog = { x: 10, y: y }

# 全引数コンストラクタ
Dog.new: (x: Int, y: Int) -> Dog = { x: x, y: y }
```

**外部宣言のデフォルト値**：

```yaoxiang
Dog: Type = {
    x: Int,
    y: Int,
    Animal(Dog),
}

# 外部宣言のデフォルト値
Dog.x: Int = 10
Dog.y: Int = 20
```

**内部宣言と等価**。

### 5. コンパイラの実装

#### 5.1 インターフェース記述子

```rust
// コンパイラ内部：インターフェース記述子
struct InterfaceDescriptor {
    name: String,
    self_param: TypeParam,     // Self 型パラメータ
    methods: Vec<MethodSignature>,
}
```

#### 5.2 型定義

```rust
// コンパイラ内部：型定義
struct TypeDefinition {
    name: String,
    fields: Vec<Field>,
    interface_instantiations: Vec<InterfaceInstantiation>,
}

// インターフェースインスタンス化（Self ↦ ConcreteType）
struct InterfaceInstantiation {
    interface: InterfaceId,
    self_type: TypeId,          // Self が置換された具体的な型
    methods: HashMap<MethodId, FunctionBody>,
}
```

#### 5.3 実装証明

```rust
// コンパイラ内部：実装証明
struct ImplementationProof {
    type_id: TypeId,
    interface_id: InterfaceId,
    methods: Vec<MethodPointer>,
}
```

#### 5.4 コンパイルフロー

```
1. 型定義を解析し、インターフェースインスタンス化宣言を収集（Animal(Dog)）
2. 各インターフェースインスタンス化に対して Self ↦ ConcreteType 置換を実行
3. インターフェースメソッドシグネチャを展開し、シグネチャ一致をチェック
4. すべてのメソッド定義を収集（内部と外部）
5. シグネチャでグループ化（オーバーロード）
6. オーバーライドをチェック（エラー）
7. インターフェースの完全性をチェック
8. 実装証明を生成
```

### 6. 動的ディスパッチ

**コア設計**：コンパイル時の型収集 + インターフェースマッチング、vtable なし。

#### 6.1 異種コンテナ

`Animal` は `(Self: Type) -> Type` である。`List(Animal)`
はインスタンス化されていないインターフェース型コンストラクタを**存在型**（existential）として使用する：`∃S. Animal(S)`——「ある型 S が存在し、S は Animal(S) を実装している」。

```yaoxiang
# インターフェース定義
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# 型定義
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

Cat: Type = {
    y: Int,
    Animal(Cat),
    speak: (self: &Cat) -> String = "Meow",
}

# 異種コンテナ — Animal はインスタンス化されない = 存在型
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
animals[1].speak()  # "Meow"
```

**所有権セマンティクス**：異種コンテナへの格納は Move セマンティクス（RFC-009）。`Dog.new()` は
`AnimalGroup::Dog` 列挙型バリアントに移動され、元の変数は使用不可になる。

```yaoxiang
dog = Dog.new()
animals: List(Animal) = [dog]
# dog.speak()  ← ❌ コンパイルエラー：dog はすでに move されている
```

#### 6.2 コンパイル時の型収集

**コア戦略：所有権追跡、インクリメンタル構築。**
コンパイル時にインターフェースを実装するすべての型をスキャンするのではなく、各 `List(Animal)`
の**所有権操作点**でインクリメンタルに収集する：

```yaoxiang
// 構築点
animals: List(Animal) = [Dog.new()]       // AnimalGroup = { Dog(Dog) }

// append 点
animals.append(Cat.new())                  // コンパイラが append 箇所で Cat を検出 → { Dog, Cat } に拡張
animals.append(Bird.new())                 // さらに { Dog, Cat, Bird } に拡張
```

**コンパイラの処理**（インクリメンタル）：

1. `List(Animal)`
   が最初に構築される箇所に遭遇 → 初期列挙型を生成（現在のコンパイルユニット内で既知のすべての構築型）
2. `append` / `push`
   / インデックス代入のたびに → 値の型が列挙型に既にあるかチェック；なければ列挙型バリアントを拡張
3. 最終的な列挙型に対して単態化 `match` ディスパッチコードを生成
4. コンパイルユニット間：LTO（リンク時最適化）に依存して列挙型バリアントをマージ。`Animal`
   は存在型としてコンパイルユニット境界を越えて渡されるため、各ユニットは部分列挙型バリアントを生成し、リンクフェーズで完全な列挙型にマージされる。

**自動生成される列挙型**：

```yaoxiang
# コンパイラが自動生成（ユーザーは認識しない）
AnimalGroup: Type = {
    Dog(Dog),
    Cat(Cat),
    Bird(Bird),    # ← append(Bird.new()) がインクリメンタル拡張をトリガー
}

# List(Animal) は内部的に List(AnimalGroup) と等価
```

#### 6.3 インターフェースマッチングチェック

**重要な洞察**：インターフェースマッチングはコンパイル時チェックであり、型が動的にロードされるプラグインから来る場合でも同様である。

```yaoxiang
# プラグインシステム
plugin = load_plugin("bird.so")

# コンパイラチェック：plugin.create_bird() の戻り型は Animal を実装しなければならない
bird: Animal = plugin.create_bird()  # コンパイル時チェック、存在型

# 異種コンテナに格納 — append 点が列挙型拡張をトリガー
animals: List(Animal) = [Dog.new(), Cat.new()]
animals.append(bird)                 // コンパイラ：(1) bird が Animal を実装していることを検証 (2) 列挙型を拡張
```

**コンパイラの処理**：

1. `append` 引数の戻り型をチェック
2. その型が対象インターフェースを実装しているかを検証
3. パスした場合 → 列挙型を拡張、格納を許可
4. 失敗した場合 → コンパイルエラー

#### 6.4 ランタイムディスパッチ

**呼び出しフロー（コンパイル時列挙型 match、ImplementationProof はすでに消去済み）：**

```
animals[0].speak()
  ↓
コンパイラ生成の match:
  match animals[0] {
    AnimalGroup.Dog(d) => d.speak(),
    AnimalGroup.Cat(c) => c.speak(),
    AnimalGroup.Bird(b) => b.speak(),
  }
```

**ブランド射影**（RFC-009a との相互作用）：match のパターン束縛 `AnimalGroup.Dog(d)`
はブランドツリーに `#animals[0].Dog`
子ブランドを生成し、フィールド射影（`#42.field_x`）と等価である。`d.speak()` が作成する
`ReadToken(d)` ブランドチェーンは `animals → animals[0] → d → ReadToken(d)`
であり、借用チェッカーはブランドツリーのプレフィックスマッチングで競合を検証する。

**インデックスアクセスの型**：`animals[0]` は
`&AnimalGroup`（コンパイラ生成の列挙型）を返す。ユーザーは `&mut Animal`
を直接取得できない。可変アクセスはインターフェースメソッドを介して間接的に実現される（例：`animals[0].mutate()`
は内部的に `AnimalGroup::Dog(d) => d.mutate()` に展開される）。

**vtable との比較**：

|                          | vtable（Rust）                     | コンパイル時列挙型（YaoXiang）           |
| ------------------------ | ---------------------------------- | ---------------------------------------- |
| 検索方法                 | vtable ポインタ → メソッドポインタ | 列挙型 match → 直接呼び出し              |
| ランタイムオーバーヘッド | 一回の間接アドレス指定             | branch（CPU 分岐予測で最適化可能）       |
| コンパイル時生成         | vtable                             | 列挙型 + match                           |
| ユーザー注釈             | `dyn Trait + 'a` が必要            | 不要                                     |
| ImplementationProof      | 該当なし                           | コンパイル時消去、ランタイムに存在しない |

**YaoXiang の優位性**：

- ブランド注釈が不要
- コンパイル時の型安全性
- ユーザーに透過的（`dyn Animal` の記述不要）
- ImplementationProof は純粋にコンパイル時の概念であり、ランタイムオーバーヘッドゼロ

#### 6.5 制限と範囲

**当期（単一コンパイルユニット）：** 完全サポート。所有権追跡がすべての
`append`/構築点をカバーし、列挙型をインクリメンタルに構築する。

**コンパイルユニット間：** LTO（リンク時最適化）に依存して列挙型バリアントをマージ。`Animal`
は存在型（`∃S. Animal(S)`）としてコンパイルユニット境界を越えて渡される。各ユニットは部分列挙型バリアントを生成し、リンクフェーズでマージされる。

**非サポート：**
ランタイム動的型（完全なダックタイピング）。型集合はコンパイル時に完全に既知である。

#### 6.6 実装ノート（#307 フェーズ 3、v1 で実装済み）

§6 のセマンティクス（異種コンテナ、コンパイル時メンバチェック、実際の型によるディスパッチ、型集合のコンパイル時クローズ）はすべて実装済みであり、実装形態は機構レベルで以下のように具体化されている：

- **型収集**：`ImplementationProof`
  に基づいてコンパイルユニット全体に対して一度に実装型集合を収集し、§6.2 の「各所有権操作点でのインクリメンタル収集」を置き換える。単一コンパイルユニット内では両者は意味的に等価（余分な死バリアントは無害）；インクリメンタル収集の価値はユニット間シナリオにあり、v2 に分類される（下記参照）。
- **表現**：コンパイラが `Animal$Group`
  バリアント型を合成し、純粋な IR/バイトコード/ランタイム成果物（命令
  `CreateVariant`/`VariantTag`/`VariantPayload`、ランタイム値
  `RuntimeValue::Enum`）であり、MonoType は認識しない——typecheck 層でユーザーに見える型は依然としてインターフェース名。存在型の位置に入る各具象値は自動的にバリアント値にラップされる（統一された不透明表現、§6.4 セマンティクス）。
- **ラップ点**：typecheck が「具象 vs 存在」判定の位置（注釈付き let/呼び出し実引数/return/リストリテラル要素）で指向的 walk を実行し、span キー強制表を生成；IR 生成は span に従ってラップを注入。ラップ漏れはランタイムガードが大きく拒否し（`VariantTag`/`VariantPayload`
  検証値が名前付きグループのバリアント値である必要がある）、最悪の場合テスト段階で明示的なランタイムエラーが発生し、誤ったデータを静かに生成することはない。
- **ディスパッチ**：バリアント番号比較ジャンプチェーン、各アームがペイロードをアンラップ後に静的呼び出し；RFC-004 リバインド形式（`Type.method = fn[n]`）はバインド位置に従って並べ替えた後、ディスパッチに参加する。
- **分離**：レガシートレイト制約（`Drawable: Type = {..}`
  形式、ジェネリックパラメータなし）はバリアントディスパッチを経由せず、動作は不変。

**v1 境界（後続フェーズ）**：ユニット間 LTO バリアントマージ（§6.5）；Group 値に対するパターンマッチング（バリアントパターンに対する match の IR サポートに依存）；リフレクションとの相互作用；コンテナへの Move セマンティクス；`Any`/型変数経由フローと推論型ラムダ境界（フォールバック = ランタイムガード）。

## トレードオフ

### 利点

1. **簡潔**：`impl` キーワードが不要
2. **柔軟**：メソッド実装は内部・外部両方をサポート
3. **統一**：オーバーロードルールが一貫
4. **便利**：デフォルト値構文が簡潔
5. **ゼロオーバーヘッド**：vtable なし、コンパイル時の型収集
6. **型安全**：インターフェースマッチングはコンパイル時チェック
7. **ユーザーに透過的**：`dyn Animal + 'a` の記述不要

### 欠点

1. **制限**：ランタイム動的型（完全なダックタイピング）はサポートされない
2. **コンパイル時オーバーヘッド**：各インターフェースに対して列挙型バリアントと match ディスパッチコードを生成する必要がある
3. **型集合**：コンパイル時に完全に既知でなければならない（単一コンパイルユニット内）

### 緩和策

1. **プラグインシステム**：コンパイル時のインターフェースマッチングチェックでサポート
2. **型集合**：所有権追跡、インクリメンタル構築——各
   `append`/構築点で収集し、グローバルスキャンではない
3. **コンパイルユニット間**：リンク時最適化で列挙型バリアント集合をマージ、リンク時単態化とメカニズムを共有

| 案                     | 採用しない理由                         |
| ---------------------- | -------------------------------------- |
| `impl` キーワード      | 構文の複雑さが増加                     |
| vtable（`dyn Trait`）  | ブランド注釈（`'a`）が必要             |
| 完全なダックタイピング | ランタイムオーバーヘッド、型安全でない |
| 列挙型ラップ（手動）   | ユーザー負担が大きい                   |

## RFC-009 との関係

**ブランドとインターフェース実装**：

- インターフェース実装は型レイヤーにあり、ブランドには関与しない
- ブランドは借用証明レイヤーにある（RFC-009a）
- 両者は直交し、相互に影響しない

**動的ディスパッチとブランド**：

- 動的ディスパッチは実装証明を使用し、ブランド注釈を必要としない
- 実装証明はコンパイル時に生成され、ランタイム検索はゼロ
- `dyn Trait + 'a` の複雑性を回避

**異種コンテナの所有権**：

- `List(Animal)` への格納は Move セマンティクス（RFC-009）であり、元の変数はアクセス不可
- インデックスアクセス `animals[0]` は
  `&AnimalGroup`（コンパイラ生成の列挙型）を返し、ブランド射影チェーンは
  `animals → animals[0] → enum_variant → field`
- 可変アクセスはインターフェースメソッドを介して間接的に実現され、`&mut AnimalGroup`
  をユーザーに公開しない

## インターフェース継承

インターフェースは他のインターフェースを含むことができる。**新しい構文は導入しない**——型がインターフェースを宣言するのと完全に同じ構文位置を使用する：

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                       # Pet は Animal を継承 — 新しいキーワードなし
    name: (self: &Self) -> String,
}

# Dog が Pet を実装する際、Animal と Pet のすべてのメソッドを同時に満たす必要がある
Dog: Type = {
    x: Int,
    Pet(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Animal 由来
    name: (self: &Dog) -> String = "Buddy",  # Pet 由来
}
```

**設計原則：**
継承は存在するが、濫用は推奨されない。主な組み合わせ方法は複数のインターフェースインスタンス化による（`Dog: Type = { Animal(Dog), Pet(Dog), ... }`）。ある型は、継承ツリーで表現することなく、それが満たすすべてのインターフェースを直接宣言できる。インターフェース継承は明確な「is-a」階層がある場合にのみ使用する。

**コンパイラの処理：** 継承チェーンを展開。`Pet(Self)` を
`{ Animal(Self) のすべてのメソッド, name: ... }` に展開。`Dog` が `Pet(Dog)`
を宣言するとき、`Self ↦ Dog` で、`Dog` が `Animal(Dog)` と `Pet(Dog)`
のすべてのメソッドを同時に満たすことを検証する。

**インターフェース継承における Self 置換**：`Pet: (Self: Type) -> Type = { Animal(Self), ... }`
において、`Animal(Self)` の `Self` は `Pet` の `Self` パラメータである——遅延置換される。`Dog` が
`Pet(Dog)` を実装するとき、`Self ↦ Dog`、`Animal(Self)` は `Animal(Dog)`
になる。これはジェネリック関数の引数渡しセマンティクスと完全に一致する。

## デフォルトメソッド実装

インターフェースはメソッドのデフォルト実装を提供できる。実装型は上書きまたはデフォルト実装の継承を選択できる：

```yaoxiang
fmt: (Self: Type) -> Type = {
    display: (self: &Self) -> String,                      # 実装必須
    debug: (self: &Self) -> String = self.display(),       # ✅ 同じインターフェース内のメソッドを参照
    summary: (self: &Self) -> String = f"<{self.name}>",  # ❌ コンパイルエラー：self.name は fmt 内にない
}
```

**コア制約：インターフェースは上位実装を仮定できない。**
デフォルトメソッドは同じインターフェース内で宣言されたメソッドのみを参照できる。具体的な型のフィールドや他のインターフェース内のメソッドはデフォルトメソッドには見えない——インターフェースは閉じた契約であり、実装型のポケットに手を伸ばすことはできない。この制約に違反した場合、**インターフェース定義時**に直接エラーになる。

**継承は下位実装を仮定できる：** インターフェース `Pet(Self)` が `Animal(Self)`
を継承するとき、`Pet` のデフォルトメソッドは `Animal`
で宣言されたメソッドを使用できる——継承しているため、存在が保証される。

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                                              # 継承
    name: (self: &Self) -> String,
    introduce: (self: &Self) -> String = self.name() + " says " + self.speak(),  # ✅ speak は継承した Animal 由来
}
```

**コンパイル時の動作：** 型がインターフェースを実装するとき、各メソッドについて：

1. 型が提供する → 型のメソッドを使用
2. 型が提供しない、インターフェースにデフォルトあり → コンパイラがデフォルト実装を型にインライン化（vtable オーバーヘッドゼロ）
3. 型が提供しない、インターフェースにデフォルトなし → コンパイルエラー

**設計原則：** デフォルトメソッドは `Copy`/`Clone`
の自動派生メカニズムに類似している——コンパイラが必要に応じて自動生成し、ユーザーは上書き可能。`virtual`/`override`/`super`
キーワードは導入しない。

## オープン問題

- [x] ~~インターフェース継承（インターフェースは他のインターフェースを継承できる）~~
      → サポート、新しい構文なし。`Pet: (Self: Type) -> Type = { Animal(Self), ... }`
- [x] ~~デフォルトメソッド実装（インターフェースはデフォルト実装を提供できる）~~
      → サポート、Copy 自動派生に類似。インターフェースが本体を提供、コンパイラが必要に応じてインライン化
- [x] ~~Self を暗黙のマジックキーワードとする~~ → 排除。`Self`
      は明示的な型パラメータ、インターフェースは `(Self: Type) -> Type`
- [ ] インターフェース制約の高度な使い方（関連型、GAT）—— 関連型はジェネリックインターフェースパラメータで実現（`Container: (Self: Type, T: Type) -> Type`）、GAT はさらなる設計が必要
- [ ] クロージャとの相互作用（クロージャがインターフェースを実装）—— 初期戦略：クロージャはインターフェースを直接実装できない、wrapper 型が必要。匿名型のインターフェース実装は後続の RFC に委ねる
