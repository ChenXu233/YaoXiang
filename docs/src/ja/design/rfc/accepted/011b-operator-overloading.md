## 概要

YaoXiang に**演算子オーバーロード**能力を補完し、`a + b` / `a == b` / `a[i]` / `e?`
をユーザー定義型で実装可能にし、RFC-011 に既に書き込まれた制約構文中の**演算子制約**（`T: Add + Multiply`）を
**紙上の能力**から着地可能な機構にする（同句中の `Zero`
は演算子ではないため対象外、オープン問題参照）。

設計は**三層の責務分離**を採用する：固定の演算子→メソッドマッピング表（Layer
0）、名前でディスパッチする基層（Layer 1、既存の `method_bindings`
を再利用）、インターフェース契約層（Layer
2、ジェネリクス制約用）。演算子の**優先度と結合性は言語固定**とし、ユーザーはセマンティクスのみをオーバーロードする。

初回範囲：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
の七つのインターフェース。算術インターフェースは**三つの型パラメータ** `(Self, R, O)`
を採用する——結果型 `O` を明示化することで、`1 + 2.5`（`Float` を返す）や
`point * 2.0`（スケール）といった異型演算を表現可能。`Equal`
は**デフォルトで自動派生**（全フィールドが比較可能なレコードは自動的にフィールド単位の `==`
を獲得）、明示的インスタンス化で上書き可能。

`Try`（`?`
のインターフェース化）はフェーズ 2 に全面移動：RFC-010（コンストラクト）と RFC-010b（分解）の着地に依存し、なおかつインターフェースの形状が未確定（オープン問題参照）。

**新しい構文なし、新しいキーワードなし**。すべて RFC-011a の既存機構（インターフェース宣言 / インスタンス化 / 外部メソッド宣言 / オーバーロード）を再利用する。

## 動機

### なぜこの機能が必要か

#### 1. RFC-011 の中核例がこれに依存し、現状は「実現不可能」よりもさらに悪い

RFC-011（受理済み）は 8 箇所で演算子名を型制約として使用している：

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

RFC 全体を通じて `Add` / `Multiply` がどこから来るのか、`+`
がそれらにどうバインドされるのかを定義したものは一つもない。実測で確認した現状はさらに悪い：`T: Add`
は**今日直接コンパイルエラーになる**——制約解決が旧 trait 表（`trait_data.rs`）を問い合わせるが、その表には
`Add` がない。制約名 `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut`
も同じく宙に浮いている（本 RFC での処理は「他の RFC との協調」参照）。

#### 2. ユーザー定義型が基本演算に参加できない（実測）

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

連鎖的な結果：`list.contains(list_of_structs, p)` は**完全に使用不能**——内部で `==`
に依存している。一方、`(1, 2) == (1, 2)` と `[1] == [1]`
はランタイムの要素単位比較で**常に利用可能**——構造体のみが唯一の穴。

#### 3. `?` が型名をコンパイラーに直付けし、`Result` の std 帰属を阻む

`?` の実装は型名とバリアント番号の両方をハードコードしている：

```rust
// typecheck：Result 型生成のハードコード
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen：グループ名とバリアント番号のハードコード
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

このため `Result` は core に留まる必要がある。`?`
を**インターフェース駆動**に変更すれば、当該インターフェースを実装する任意の型（ユーザー定義を含む）を
`?` が使用でき、`Result` を std に帰属可能（RFC-013 には既に「std ライブラリの
`Result(T, Error)`」の位置付けがある）。

これは問題の一側面に過ぎない：`ok(...)` / `err(...)` / `some(...)`
のコンストラクト記法も現在パーサーに直付けされている（言語仕様 §1.4.2 で「パーサーによって認識されるコンストラクタ」として列挙）。「`Result`
の std 帰属」には `?`
とコンストラクタの**両側を同時に解く**必要があり、ともに本 RFC のフェーズ 2 に属する。

#### 4. ユーザー定義コンテナがインデックス化できない

`Index` の型検査はハードコードされたホワイトリスト：

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// その他 → "型層で認識されないコンテナは寧ろ拒絶し黙殺しない"
```

ユーザーが任意のコンテナ型を定義すると、`c[0]` は一律エラーになる。

#### 5. `%` の実装が既刊ドキュメントに違反する

実測で `-7 % 3` は
`-1`（切り捨て剰余）を返す。しかし言語リファレンスの演算子優先度表（`reference/index.md`）には既に「`* / %`
乗除**モジュロ**」と書かれている——ドキュメントが約束しているのはモジュロで、実装が提供しているのは剰余。これは設計変更ではなく、**実装がドキュメントに違反する欠陥**であり、本 RFC で併せて修正する。

### 既存の半完成基盤

調査の結果、機構は**ほとんどが既に存在し**、欠けているのは結線だけであることが判明：

| 機構                                                            | 位置                                                                                                                   | 状態                                                              |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| インターフェース宣言 `(Self: Type) -> Type`                     | RFC-011a Phase 1                                                                                                       | ✅ 実行可能                                                       |
| インターフェースインスタンス化 `Animal(Dog)` + 外部メソッド宣言 | RFC-011a Phase 2–3                                                                                                     | ✅ 実行可能（単体テストあり）                                     |
| メソッドディスパッチ `method_bindings["Type.method"]`           | `expressions.rs`（`environment.rs` で登録、`expressions.rs` の呼び出し解析とフィールドフォールバック経路で問い合わせ） | ✅ 実行可能                                                       |
| 関連型（= インターフェースの型パラメータ）                      | RFC-011 §3.1；RFC-011a はこの方式を採択済み                                                                            | ✅ 機構確定                                                       |
| 型族評価 `AssociatedTypeDef`                                    | `dependent_types.rs`                                                                                                   | ✅ 本番ユースケース `std.assert` の `IsTrue`                      |
| `Equal` / `Dup` / `Clone` / `Debug` trait                       | `trait_data.rs` に登録済み                                                                                             | ⚠️ `Equal` は消費点ゼロ；旧自動派生はシグネチャ登録のみで実装なし |
| 演算子 → メソッド名マッピング                                   | —                                                                                                                      | ❌ 存在しない                                                     |

**結論**：これはゼロから機能を作るのではなく、既存の部品を結線しかつ文書化する作業である。

## 提案

### 中核設計：三層の責務分離

```
Layer 0  固定マッピング表（言語レベル定数、ユーザー変更不可）
         + → add    == → equal    [] → index    ? → residual
         │  コンパイル時に組み込まれ、型推論に参加せず、ユーザーに公開しない
         ▼
Layer 1  ディスパッチ基層（名前でメソッドを検索し呼び出す）        ← 既存機構を再利用
         method_bindings["Point.add"]
         ▼
Layer 2  インターフェース契約（ジェネリクス制約用）
         Add / Equal / Index / Try …
         T: Add 制約を有効化し、演算子の通行条件としても機能
```

**階層化の根拠**：

- **Layer 0 と 1 は演算子を「使える」ようにし、Layer
  2 は演算子を「制約できる」ようにする**。これらを統合すると、`add` という名前の任意のメソッドが `+`
  で呼び出されることになり、RFC-011 の `T: Add` が演算子と切り離される。
- **Layer 1 は新規実装しない**：`method_bindings` は既に `Type.method`
  キーで表引きしており（フィールド検索失敗後のフォールバック経路）、演算子も同じ経路を通ればよい。
- **Layer
  2 は通行条件**：演算子の通行前に**必ず**型が対応インターフェースを実装していることを確認する（§Equal の自動派生例外を参照——導出と登録は同じ判定基準）。

### 名前と登録：二つの独立した経路

**演算子が問い合わせるのは「インターフェース実装登録表」で、通常の名前解決を経由しない。**

- 登録表はコアが所有し、二つの登録を集約する：コアが基本型に対して行うデフォルト登録（`Add(Int, Int, Int)`
  等）、およびユーザーの型体内で書かれたインターフェースインスタンス化（`Add(Point, Point, Point)`）。実装コードが物理的にどのモジュールにあっても、登録は同じ表に集約され、`+`
  / `==` / `[]` はこの表のみを参照する。
- ローカルモジュールで `Add` という名前の**同名のバインディング**（例：RFC-011
  §5.2 の Peano 型レベル加算
  `Add: (A: Type, B: Type) -> Type = match ...`）が定義されていても、それは**名前検索経路**を通るだけで、モジュール内の
  `Add`
  という名前の解決にのみ影響し、**登録表には触らず、演算子の可用性にも影響しない**。同名で別物、互いにシャドウイングしない。

これは同時に「RFC-011 の型レベル `Add` と本 RFC のインターフェース `Add`
は衝突するか」という問いにも答える：衝突しない。型レベル `Add`
は純粋に型レベルでの計算（Zero/Succ は型であり値ではないため、`Zero + Succ(...)`
のような値演算は決して存在しない）であり、値レベルの演算子インターフェースとは同じ名前の二つの層である。

### Layer 0：固定マッピング表

| 演算子            | インターフェース                                  | メソッド        | 初回        |
| ----------------- | ------------------------------------------------- | --------------- | ----------- |
| `+`               | `Add`                                             | `add`           | ✅          |
| `-`               | `Subtract`                                        | `subtract`      | ✅          |
| `*`               | `Multiply`                                        | `multiply`      | ✅          |
| `/`               | `Divide`                                          | `divide`        | ✅          |
| `%`               | `Modulo`                                          | `modulo`        | ✅          |
| `==` `!=`         | `Equal`                                           | `equal`         | ✅          |
| `[]`              | `Index`                                           | `index`         | ✅          |
| `?`               | `Try`（四メソッド、フェーズ 2 で確定）            | `is_failure` 等 | ✅ 着地済み |
| `<` `<=` `>` `>=` | —（ネイティブ命令として保持）                     | —               | ❌          |
| `and` `or`        | —（短絡は言語セマンティクス、オーバーロード不可） | —               | ❌          |
| ビット演算 5 種   | —                                                 | —               | ❌          |
| 単項 `-` `!`      | —                                                 | —               | ❌          |

**インターフェース名は省略形ではなく完全綴り**（`Mul` ではなく `Multiply`）：RFC-011 本文の
`T: Add + Multiply + Zero` との一貫性を保ち、**受理済み RFC を改変しない**。

**`%` は `Modulo`
セマンティクス**を採用（数学的モジュロ、結果の符号は除数に従う）。動機節で前述した通り、現在の remainder 実装は既刊ドキュメント（`reference/index.md`「乗除モジュロ」）に違反しており、本条は欠陥修正として扱い、互換期間は設けない。

現状備考：`%` の型検査ホワイトリストは現状 Int/Float のみ（`+`
の Int/Float/String/List ホワイトリストとは異なる）、付録 A.2 に実測記録あり。

### Layer 2：インターフェース定義

#### 算術インターフェース（三つの型パラメータ）

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

三つの型パラメータはそれぞれ以下の役割を担う：

- `Self`：左オペランドの型（レシーバ、`&Self`
  で借用、RFC-009 の借用トークンと RFC-011a のレシーバ規約を参照）；
- `R`：右オペランドの型——**左右で異型を許容**；
- `O`：**結果型**、明示的に宣言。

**結果型を明示的なパラメータでなければならない理由**（`-> Self` 固定ではなく）：

1. `Self` 固定だと `Add(Int, Float)` のメソッドは `Int` を返さねばならず、`1 + 2.5`
   を正しく表現できない；
2. 結果型を明示化することで、RFC-011 §8.3 の昇格型族
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }`
   と本 RFC のインターフェース登録が**同じ表の二つの視点**になる——コアの `Add(Int, Float, Float)`
   登録は `(Int, Float) => Float`
   の行そのものであり、ユーザーのインスタンス化のたびにこの表に行が追加される；
3. `Index` インターフェースは元々三パラメータ `(Self, Key, Value)` で、戻り型 `Value`
   がパラメータ——算術インターフェースに `O`
   を補うと、演算子インターフェースファミリの形状が揃い、`Self` 固定の方がむしろ異端になる。

**コアのデフォルト登録**（ネイティブ命令経路、メソッド呼び出しを経由しない）：`Add(Int, Int, Int)`、`Add(Int, Float, Float)`、
`Add(Float, Int, Float)`、`Add(Float, Float, Float)`、`Add(String, String, String)`（連結）、
`Add(List(T), List(T), List(T))`（要素連結）等、五つの算術インターフェースは基本型に対して同様。`1 + 2.5`
は現在のコンパイルエラー（ホワイトリストは両側同型を要求）から、`3.5: Float`
を返す正当な演算になる。

**制約構文糖衣**：`T: Add` ≜ `Add(T, T, T)`
が登録済み——同型自己複合、結果もその型。RFC-011 の行列乗法例で `a * b + c` は全行程型 `T`
であり、まさにこの意味を要求している。`T: Equal` も同様 ≜ `Equal(T, T)`。

**異型例**——ベクトルスケーリング：

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### 等価インターフェース（デフォルトで自動派生）

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` はデフォルトで自動派生**、規則五条：

1. **デフォルト派生**：レコード型を定義する際、全フィールドが比較可能（基本型、`String`、またはそれ自体が比較可能なレコード/タプル/リストで、かつ
   `&mut` フィールドを含まない）であれば、コンパイラが自動的に**フィールド単位比較**の `==`
   を生成し、ネイティブコード経路を通り、ユーザー可視メソッドは生成されない。ユーザーが自分で書いた型は自然に比較可能、いかなる儀式も不要。
2. **明示的オーバーライド**：型本体に `Equal(Point, Point)` と `Point.equal`
   メソッドを記述した場合、ユーザー版が使われる（例：許容誤差付き浮動小数点比較）、自動派生は行われない。
3. **フィールドが比較不能な場合**：自動派生は失敗し、`==`
   は使用不能、診断がどのフィールドが原因かを示す；この場合もユーザーは手動で `Equal`
   カスタム比較を記述可能（例：関数フィールドは名前で比較）。
4. **前提条件**：`&mut T`
   線形トークン（フィールド再帰）を含む型は比較に参加しない——線形トークンは一度読むと消費され、二つの値を同時に取り出して比較できない。前提は「線形性」であり「Dup」ではないことに注意：プリミティブ値型（Int/Float/Bool/Char）は RFC-011
   §2.4 により Dup に属さない（これらはコンパイラー組み込み値コピー）。Dup を前提にすると
   `Point { x: Float, y: Float }` が誤って拒否される。
5. **制約と同判定基準**：`T: Equal` の解決と `==`
   の通行は同じ「登録表検索または構造導出」規則に従う——制約と演算子は常に同じ答えを出す。

**一貫性の根拠**：`(1, 2) == (1, 2)` と `[1] == [1]`
は今日既にランタイムの要素単位比較を通っており（`executor.rs`
の比較ホワイトリストは Tuple/List/Array を含む）、レコード型のみが除外される唯一の複合型。自動派生は新たな暗黙のデフォルトではなく、言語内部の既存挙動を最後のピースに補完するものである。

**旧機構の撤収**：`trait_data.rs` 中の `Equal`
旧自動派生（シグネチャ登録のみ、実装コードなし、消費点ゼロ）を停止；`Equal`
の全判定（基本型デフォルト登録、構造導出、明示的インスタンス化）はインターフェース登録表を通す。旧 trait 表は Clone/Dup/Debug の既存責務を保持（名前と演算子インターフェースは重複しない、将来の統一は別途議論）。

#### インデックスインターフェース

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value`
は関連型メンバーではなく型パラメータ**：RFC-011a のオープン問題は「関連型はジェネリクスのインターフェースパラメータで実装する」とすでに確定（`Iterator: (Item: Type) -> Type`
が同型の先例）、`type` メンバー構文を導入する必要はない。

**所有権に関する注記**：`index` は `&Self` から借用しつつ完全な `Value` を返す。標準ライブラリの
`list.get: (&Vec(A), Int) -> A`
は既に同じ形であり、本インターフェースは**std の現状と同待遇**；移動セマンティクス要素型に対する「借用から完全な値を取り出す」の正確なセマンティクスは、RFC-009 の全面的施行時に統一して処理し、本 RFC では新ルールを発明しない。

**複数位置インデックスはタプルのパッキング + オーバーロードで実現、可変引インターフェースは導入しない**：

```yaoxiang
// 一次元コンテナ
List(T) が Index(List(T), Int, T) をインスタンス化                 → arr[0]

// 多次元コンテナ
Grid    が Index(Grid, Tuple(Int, Int), Float) をインスタンス化    → g[0, 1]
//                    └─ Key はタプル

// 二つのインスタンス化シグネチャは異なる → 共存
```

**同型の同名インターフェースは複数のインスタンス化を許可**し、注入するメソッドのシグネチャで区別、RFC-011a のメソッドレベルオーバーロード規則に従って共存する。RFC-011a のオーバーロード規定はメソッドレベルまでの明示だが、本条はその上にインスタンス化レベルの規則を補う：同名インターフェースインスタンス化の共存の可否は、展開後のメソッドシグネチャが衝突するかどうかで決まり（衝突時は E1097、フィールド/メソッド名前空間規則と同源）。

#### 伝播インターフェース Try（フェーズ 2 で確定・着地済み）

`?` のインターフェース化名称は `Try`、四メソッドの形状（2026-09-22 フェーズ 2 で確定）：

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    is_failure: (self: &Self) -> Bool,
    success:    (self: &Self) -> T,
    residual:   (self: &Self) -> E,
    from_error: (E) -> Self,
}
```

- **セマンティクス分担**：`is_failure` は成否判定、`success` は成功ペイロード取得、`residual`
  は失敗ペイロード取得、`from_error` は異型伝播の橋渡し（`f()?` の `T` ≠ 外層 `U` の場合、`E`
  から失敗値を再構築）。`?`
  の lowering は統一的に四メソッド呼び出しチェーンを生成する——`is_failure(t)` が真なら
  `Ret from_error(residual(t))`、そうでなければ式の値は
  `success(t)`；バリアント検査シーケンスを手書きすることはもうない、`Result` / `Option`（std
  yx 実装）とユーザー定義 Try 型が同じ経路を通る。
- **デッドコード分岐**：`success` の失敗側と `residual` の成功側は契約上到達不能、実装は
  `assert(false)` で発散（`assert` は `Never` を返し、爆発原理 `Never <: T` で通行、type-system.md
  §2.2）。
- **検査**：typecheck はインターフェース実装登録表を検索（Self 位は名目一致、抽象エントリは scrutinee 実引数でインスタンス化）；外側関数の戻り型も
  `Try` を実装し、`E`
  位が失敗値を受け取れなければならない（E1081/E1082/E1083 のセマンティクスが連動してインターフェース化される）。
- **`Result` の std 帰属**：`Result` / `Option` の型定義と Try 実装を `std/result.yx` /
  `std/option.yx`（純粋 YaoXiang）に移行、ネイティブの `ok`/`err`
  コンストラクタは退役——バリアントコンストラクト構文 `Result(T, E).ok(v)`
  が唯一のコンストラクト経路（コンストラクタ直付けの問題は parser 特殊判定の退役とともに解決）。Option の Try 残余型は
  `Void` を取る（Rust Try 実験の NoneT セマンティクスに対応）。

### 例

#### ユーザー定義型：算術と等価がそのまま使える

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false —— Equal は自動派生、インスタンス化不要
    println(a == a)             # true
}
```

#### カスタム等価（自動派生を上書き）

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# 浮動小数点比較に許容誤差を付与、フィールド単位自動派生を上書き
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### カスタムコンテナのインデックス

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### ジェネリクス制約がついに着地可能

```yaoxiang
// RFC-011 の例がここにきて初めて着地可能
// T: Add ≜ Add(T, T, T) が登録済み；T: Multiply ≜ Multiply(T, T, T) が登録済み
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

（RFC-011 の看板例 `T: Add + Multiply + Zero` の `Zero` / `One`
は本 RFC の範囲外——これらは定数メンバーであり演算子ではない、「レシーバなしインターフェースメンバー」は RFC-011a に先例がなく、オープン問題参照。）

### 構文変更

**新しい構文なし、新しいキーワードなし**。全能力は既存機構の組み合わせで実現：

| 能力                           | 再利用する既存機構                                                  |
| ------------------------------ | ------------------------------------------------------------------- |
| インターフェース宣言           | RFC-011a Phase 1                                                    |
| インターフェースインスタンス化 | RFC-011a Phase 2（`Dog: { Animal(Dog) }`）                          |
| メソッド実装                   | RFC-011a Phase 3（外部宣言 `Point.add`）                            |
| 関連型                         | RFC-011 §3.1（インターフェースの型パラメータ）                      |
| 複数位置インデックス           | 既存のタプルパッキング解析 + インスタンス化レベルオーバーロード規則 |
| 演算子優先度                   | **言語固定**、ユーザーがカスタマイズ可能としない                    |

## 詳細設計

### 型システムへの影響

**新規インターフェース**（Layer 2）：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal`
`Index`（`Try` はフェーズ 2）。

**インターフェース実装登録表**：演算子判定の中枢。コアのデフォルト登録（基本型）とユーザーインスタンス化（`check_interface_instantiation`
が生成する `ImplementationProof`）を集約し、`+` / `==` / `[]` の通行検査と `T: Add`
制約解決（`bounds.rs` の
`check_trait_bounds`）は**同じ表を問い合わせる**——「制約は可と判定、演算子は不可と言う」隙間は存在しない。

**`Equal`
の構造導出**：登録表の上に構造規則を重ねる（全フィールドが比較可能 ⇒ 比較可能）、基本型はコア登録がフォールバック、帰納的に閉包。旧
`trait_data.rs` の `Equal` 登録と旧自動派生を停止。

**演算子クエリと名前解決の分離**：`+`
等の演算子は登録表のみを問い合わせ、通常の名前解決を通らない；ローカル同名のバインディング（型レベル
`Add` ファミリ等）は演算子に影響しない（§名前と登録参照）。

**オーファン規則**：演算子実装は型の**定義モジュール**にのみ記述可能——`Int`
の定義はコアにあるため、`Int` の登録はコアのみが行える；`Point`
の定義はユーザーモジュールにあるため、その定義者のみが登録可能。すべての型に同じ規則が、内蔵型に特別扱いはない。

### ランタイム挙動

**ランタイムオーバーヘッドゼロ**：演算子はコンパイル時に呼び出し対象を決定（静的ディスパッチ）。基本型（`Int`/`Float`/`String`/`List`）には**ネイティブ命令ファストパス**を保持し、インターフェースディスパッチを経由しない；自動派生された構造体
`==` はネイティブのフィールド単位比較を生成；`Any`（動的型）位置の `==` / `!=`
は既存のランタイム比較を保持（RFC-036 テストフレームワーク `assert_eq`
がこの挙動に依存、影響なし）。

**`%` セマンティクスの修正**：`-7 % 3` は `-1`（切り捨て剰余）から
`2`（数学的モジュロ）に変更。インタプリタ（`checked_rem`）、定数畳み込み（`a % b`）、バイトコード（`I64_REM`）の三箇所を同期的に修正。

### コンパイラー変更

| コンポーネント                       | 変更                                                                                                                                                                                                                |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `typecheck/inference/expressions.rs` | `infer_binary` のホワイトリストを「ネイティブファストパス + 登録表クエリ」の二経路に変更；`Expr::Index` のホワイトリストにインターフェースクエリ分岐を追加                                                          |
| `typecheck/inference/bounds.rs`      | `check_trait_bounds` で演算子インターフェース名はインターフェース登録表を問い合わせる（`Equal` は構造導出を含む）                                                                                                   |
| `typecheck/checker.rs`               | `Equal` の構造導出を新規追加（レコード定義後）；インスタンス化レベルオーバーロード規則（同名のインターフェース複数インスタンス化はメソッドシグネチャにより共存）                                                    |
| `middle/core/ir_gen.rs`              | `Expr::Index` にメソッド呼び出しディスパッチ分岐を追加；明示的 `equal` なしの構造体 `==` はネイティブのフィールド単位比較を生成；`Mod` 命令を数学的モジュロに変更                                                   |
| インターフェース登録表（新規）       | Layer 0 マッピング表定数 + 演算子→インターフェースクエリ関数 + コアデフォルト登録（`Int`/`Float`/`String`/`List` 等）                                                                                               |
| `trait_data.rs`                      | `Equal` 登録と旧自動派生を停止（`Clone`/`Dup`/`Debug` は現状維持）                                                                                                                                                  |
| 診断                                 | `Equal` の前提（線形トークン）不充足は `E1101`（型がインターフェースを実装していない）ファミリを再利用；`E1081`/`E1082` の文言から「Result」の文字を除去（フェーズ 2 で `Try` 着地時に RFC-013 手順に従い三者同期） |

### 後方互換性

**基本型の演算は不変**：`1 + 2`、`"a" + "b"`、`[1] + [2]`、`1 < 2`
はすべてネイティブ経路を保持、挙動と性能は不変。

**`1 + 2.5` はコンパイルエラーから正当な式へ**：コアの `Add(Int, Float, Float)`
登録後、以前はホワイトリストに拒否されていた混合算術が使用可能、`Float`
を返す。これは新規能力であり、既存コードへの影響なし。

**`%` セマンティクスの修正**：`-7 % 3` は `-1` から `2`
に変更。**欠陥修正**と位置付け（ドキュメントは既にモジュロを約束、動機 §5 参照）、互換期間は設けない；既存テストコーパスに負数の
`%` に依存する用例はない（確認済み）。

**構造体 `==` はランタイムエラーから使用可能に**：以前は `Struct == Struct`
は一律 E6007 ランタイムエラー、結線後は自動派生でそのまま使用可能——悪い状態から良い状態へ、既存の正当なコードへの影響なし。

**`Any` の `==` は影響なし**：動的型位置はランタイム比較を保持（RFC-036 の `assert_eq`
アサートファミリが依存、以前も以後も可能）。

**`f[0]` 位置バインディングは不変**：`distance[0]`
は RFC-004 のコンパイラー組み込み能力であり、**`Index` インターフェースを経由せず**、影響なし。

**`?` は既存コードに対し透過的**（フェーズ 2）：`Result` に `Try` インスタンス化を補うと、既存の `?`
の挙動は完全に同一。

## トレードオフ

### 利点

- **RFC-011 の演算子制約を着地**：`T: Add + Multiply`
  を紙上（実際にはコンパイルエラー）から着地可能に変更、受理済み RFC 本文には触れない
- **`Result` の core バインドを解除**（フェーズ 2）：`?` とコンストラクタのインターフェース化により
  `Result` は std に帰属可能、RFC-013 の既存位置付けと整合
- **実測欠陥を修復**：`Point == Point` がそのまま使え、構造体に対する `list.contains`
  の使用不能も連動して修復
- **新構文ゼロ**：すべて RFC-011a の既存機構を再利用、parser の構文規則に触れない
- **ランタイムオーバーヘッドゼロ**：静的ディスパッチ + 基本型のネイティブファストパス
- **ユーザー定義コンテナが使用可能**：`Box(T)[0]` は「一律エラー」から使用可能に
- **言語内部の整合性**：Tuple/List は既に要素単位比較、レコード型も補完；算術インターフェースの三パラメータと Index の形状が揃う；RFC-011
  §8.3 の昇格表とインターフェース登録表が合一

### 欠点

- **`Equal`
  の自動派生は暗黙のデフォルト**：将来「レコードはデフォルトで比較可能」を撤回は破壊的変更。この立場を受け入れる——Tuple/List の既存挙動と一致、かつ明示的インスタンス化で常に上書き可能
- **`Equal` の前提が線形トークンを含む型を拒否する**：`&mut` フィールドを含む型は `==`
  不可、これは意味的に正しいことの代償、明瞭な診断が必要（どのフィールドかを明示）
- **インターフェースインスタンス化は明示的コスト**：算術演算子ごとにインスタンス化 1 行 + メソッド 1 つの記述が必要（`Equal`
  は免除——自動派生）。RFC-011a の構文は暗黙導出を許さない（引き換えに `Self`
  型パラメータに魔法がない）
- **`%` セマンティクスの修正は挙動変更**：欠陥修正と位置付けられても、移行説明での明示は必要

## 代替案

### 案 A：Layer 1 のみ（メソッド名によるディスパッチ）を実装し、インターフェース層は作らない

`+` は `add` というメソッドが存在するかどうかのみを問い合わせ、`Add`
インターフェースの実装を要求しない。

**却下理由**：RFC-011 の `T: Add`
制約が演算子と切り離される——制約はインターフェースを問い合わせるが、演算子はメソッド名を問い合わせ、両者が矛盾する答えを返す可能性がある。また「`+`
が加算不可能な型に使われた」をコンパイル時に正確に診断することもできない。

### 案 B：コンストラクタ構文 `Ok(x)` / `Some(x)` を導入して `?` 問題を解決

`?` のインターフェース化をせず、和型にコンストラクタ構文を追加する。

**却下理由**：RFC-010（受理済み）と衝突。RFC-010 は「和型の表現には統一してレコード型を使い、**二組の構文は不要**」と明確に規定し、`|`
構文を明示的に廃止している。コンストラクタの導入は二組目の表現を導入することになる。しかもこれは `?`
のみを解決し、`Point == Point` やカスタムコンテナのインデックスは解決しない。

### 案 C：比較演算子も初回にインターフェース化（`Ordering` の導入）

`<` `<=` `>` `>=` を `Compare` インターフェースで実装し、三値 `Ordering` を返す。

**却下理由**：`<`
は YaoXiang では既に**第一級 IR 命令**（`Instruction::Lt/Le/Gt/Ge`）であり、インターフェース化すると基本型が迂回を強いられる。さらに
`Ordering` を導入すると、`Ordering` 自身の比較/ソート、浮動小数点 `NaN` の `PartialOrd` vs `Ord`
等の一連の問題が派生し、独立 RFC の規模になる。現在の実測で露呈しているニーズ（`Point == Point`、`list.contains`）には**`Equal`
のみ**で十分。

### 案 D：演算子名は省略形（`Add` インターフェースのメソッドは `add`、インターフェース名は `Mul`）

**却下理由**：RFC-011 本文には既に `T: Add + Multiply + Zero`
と書かれている、省略形を使うと受理済み RFC を改変することになる。

### 案 E：`Equal` は明示的インスタンス化のみ、自動派生なし

**却下理由**：ユーザーが自分で書いた型が `==` できないのは体験上容認不能；しかも
`(1, 2) == (1, 2)`、`[1] == [1]`
は今日既に要素単位比較であり、レコード型のみが除外されているのは元から不整合。明示的インスタンス化は上書き手段として残し、カスタムニーズにも応じる。

### 案 F：算術インターフェースの戻り型は `-> Self` 固定

**却下理由**：`Add(Int, Float)` のメソッドは `Int` を返すよう強制され、`1 + 2.5`
を正しく表現できない；ベクトルスケーリング `Multiply(Point, Float)` も同様に記述できない。RFC-011
§8.3 の昇格型族 `(Int, Float) => Float` には着地点がなくなる。三パラメータ `(Self, R, O)` は
`Index(Key, Value)` と形状が揃う。

## 実装戦略

### 依存関係

| 依存                                    | 状態        | 本 RFC への影響箇所                                                           |
| --------------------------------------- | ----------- | ----------------------------------------------------------------------------- |
| RFC-011a インターフェース機構 Phase 1–3 | ✅ 着地済み | Layer 2 の地基（実測動作確認済み）                                            |
| RFC-010 レコード式コンストラクト経路    | ✅ 着地済み | **フェーズ 2**：`?` のコンストラクト側 + コンストラクタ parser 特殊判定の撤収 |
| RFC-010b バリアント分解                 | ✅ 着地済み | **フェーズ 2**：`Result.residual` の `match` 記法、網羅性                     |
| RFC-009 線形トークン推論                | 一部        | `Equal` の前提制約検査                                                        |

### 段階分け

**インターフェース依存**（設計上の制約、順序ではない）に基づき二グループに分ける：

**フェーズ 1 — RFC-010/010b に依存しない**：

- Layer 0 マッピング表 + インターフェース実装登録表 + Layer 1 ディスパッチ結線
- `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
  の七つのインターフェース（三型パラメータ形式）
- `Equal` の自動派生 + 線形前提制約 + 制約解決の登録表経由化
- `%` セマンティクスの修正（インタプリタ/定数畳み込み/バイトコードの三箇所）
- `Any` 位置の `==` はランタイム比較を保持
- **効果**：`Point + Point`、`Point == Point`（無儀式）、`Box(T)[0]`、`1 + 2.5`、`T: Add`
  制約がすべて使用可能

**フェーズ 2 — RFC-010 / RFC-010b に依存、着工前に `Try` 形状の確定が必要**：

- `Try` インターフェース形状の確定（オープン問題参照）
- `?`
  のインターフェース化 + コンストラクタ（`ok`/`err`/`some`）の parser 特殊判定撤収、RFC-010 レコードコンストラクト経路に変更
- `Result` を core から std へ移行（RFC-013 の既存位置付けに基づく）

### リスク

| リスク                                             | 緩和策                                                                             |
| -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `%` セマンティクスの変更が既存ユーザーコードに影響 | 欠陥修正と位置付け + テストコーパスに負数 `%` 依存がないことを確認済み             |
| `Equal` 自動派生の暗黙デフォルトの将来撤回困難     | 立場確定：Tuple/List の既存挙動と一致、明示的インスタンス化で上書き可能            |
| 基本型の二経路（ネイティブ + 登録）不整合          | ゲート：コア登録のセマンティクスはネイティブ命令と一致（同じ表の二つの視点）       |
| 登録表クエリがコンパイルを遅延化                   | 型名でのインデックス化 + インスタンス化結果のキャッシュ（RFC-011a proof を再利用） |
| インスタンス化レベルオーバーロードが曖昧性を導入   | メソッドレベルオーバーロードと同規則：シグネチャ衝突なら E1097                     |

## 他の RFC との協調

本 RFC の位置付けは**消費側要求の提起者**であり、以下 RFC の同期更新が必要（改訂許可取得済み）：

| RFC                              | 更新内容                                                                                                                                                                                                                                                |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011**（受理済み）          | §制約箇所に `Add` / `Multiply` が 011b で定義・着地される旨を注記（`T: Add` ≜ `Add(T, T, T)`）；`Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` を宙に浮いた制約名として注記（後続 RFC を待つ）；§8.3 昇格型族がインターフェース登録表と合一する旨を注記 |
| **RFC-010**（受理済み）          | 「レコードフィールドがコンストラクタである」の着地要件を明確化——フェーズ 2 のコンストラクタ parser 特殊判定撤収の前提                                                                                                                                   |
| **RFC-010b**（草案、元 RFC-039） | コンストラクトと分解は対でなければならない；網羅性判定は `Result` の core/std 帰属に依存しない（011b フェーズ 2 で移行）                                                                                                                                |
| **RFC-009**（受理済み）          | §型属性で交差参照：`Equal` の前提は「`&mut` 線形トークンを含まない」（Dup ではない）                                                                                                                                                                    |
| **RFC-013**（受理済み）          | フェーズ 2 着地時：`E1081` / `E1082` 文言から「Result」文字を除去；`Equal` 前提診断は `E1101` ファミリを再利用——RFC-013 手順に従い三者同期（codes/*.rs ↔ locales ↔ コード表）                                                                           |
| **RFC-018**（受理済み）          | `%` を数学的モジュロに変更後、`Mod → srem/urem` のマッピング表が無効化、`srem` + 符号修正（または `sdiv`+`mul`+`sub` 合成）に変更が必要、加えて「モジュロ/剰余」用語混在の修正                                                                          |
| **RFC-036**（受理済み）          | 変更不要。関係を明示：`Any` 位置の `==` はランタイム比較を保持、`assert_eq` アサートファミリはゲート影響なし                                                                                                                                            |

> `Result` の std 帰属の根拠：RFC-013 には既に「std ライブラリの
> `Result(T, Error)`」と位置付けられ、RFC-014 の階層化で std はコアソースに帰属する。本 RFC のフェーズ 2 はその着地経路の一つであり、他の番号は引用しない。

## オープン問題

- [x] ~~`Modulo` のセマンティクス修正に互換期間を設けるべきか？~~ →
      **クローズ**：言語リファレンスには既に「乗除モジュロ」と明記、現状の remainder 実装は既刊ドキュメント違反、欠陥修正として扱い、互換期間を設けない（2026-09-22）
- [x] ~~ユーザーは既存型に対して演算子実装を追加できるか（オーファン規則）？~~ →
      **確定**：演算子実装は型の定義モジュールにのみ記述可能。`Int`
      の定義はコアにあるため、コアのみが登録可能；ユーザーは自分の型のみ登録可能。すべての型に同じ規則、内蔵型に特別扱いなし（2026-09-22）
- [ ] `Index` は可変インデックスを区別すべきか（Rust の `IndexMut`
      相当）？（初回は読み取りのみ；可変インデックスは RFC-009 の `WriteToken`
      を伴い、RFC-011a には既に `&mut Self` レシーバの先例あり、後続に回す）
- [ ] 複数位置インデックスの Key はタプルパッキング（現状）か複数引数（Swift 風）か？（タプルパッキングを継続、parser 変更なし）
- [ ] `Zero` / `One`
      の形式：定数メンバーは演算子ではない、「レシーバなしインターフェースメンバー」は RFC-011a に先例なく、単独確定が必要で、その上で RFC-011 の
      `T: Add + Multiply + Zero` 全句が着地可能
- [ ] `Try` インターフェースの完全な形状：`?`
      には成否判定、成功ペイロード取得、失敗パスの外層戻り値生成の三つが必要、単一メソッド
      `residual` では不足；コンストラクタ parser 特殊判定の撤収とともに、フェーズ 2 着工前に確定
- [ ] `?T` 前置型（RFC-026 FFI ヌル許容注釈、RFC-018）と `e?` 後置演算子が `?`
      記号を共有：位置が異なる（型位置 vs 式位置）ので衝突しない、文書での明示で足りる
- [ ] `PartialOrd` /
      `Ordering`（比較演算子のインターフェース化）：独立 RFC、本 RFC では明確に扱わない

## 付録 A：調査証拠

以下の実測はすべて **0.8.0**（`target/debug/yaoxiang-rs.exe`）で再現。

### A.1 インターフェース機構の可用性（本 RFC の地基）

| 能力                                                                               | 実測                                                     |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| インターフェース宣言 `Animal: (Self: Type) -> Type = {...}`                        | ✅ 定義可能                                              |
| インターフェースインスタンス化 + 外部メソッド `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ 実行可能、出力正常（`tests/rfc011a.rs` に単体テスト） |
| インターフェースインスタンス化 + **内部**メソッド宣言                              | ❌ `E1097`（フィールドとメソッドの名前空間衝突）         |
| メソッドディスパッチ `d.speak()`                                                   | ✅ 実行可能                                              |

**注**：`E1097`
により、演算子メソッドは**外部宣言**形式（`Point.add: (self: &Point, ...)`）を使う必要があり、RFC-011a の例と一致する。`method_bindings`
の登録は `environment.rs`（`add_method_binding`）、問い合わせは `expressions.rs`
の呼び出し対象解析とフィールド検索失敗フォールバック経路。

### A.2 演算子の現状

| 式                                  | 現状                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]` | ✅ ハードコードホワイトリスト（Int/Float/String/List、**両側同型を要求**）                |
| `1 + 2.5`（Int + Float）            | ❌ コンパイルエラー（ホワイトリストは両側同型を要求）                                     |
| `-7 % 3`                            | `-1`（切り捨て剰余；`%` ホワイトリストは Int/Float のみ、`+` のホワイトリストとは異なる） |
| `Point(1,2) == Point(1,2)`          | ❌ `E6007`（Eq が Struct 上でランタイム失敗）                                             |
| `(1,2) == (1,2)` / `[1] == [1]`     | ✅ ランタイムの要素単位比較（Struct のみが唯一の穴）                                      |
| Any 位置の `a == b`（`assert_eq`）  | ✅ ランタイム比較（RFC-036 実証）                                                         |
| `f[0]`（関数位置バインディング）    | ⚠️ バインディング宣言内でのみ有効、式として使用すると `E3006`                             |
| `arr[0, 1]`（複数位置）             | ✅ タプルパッキング、`list([1, 2])`                                                       |

### A.3 `?` とコンストラクタのハードコード位置

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

コンストラクタ側：`ok(T)` / `err(E)` / `some(T)` はパーサーで認識（言語仕様 `syntax.md` §1.4.2）；
`std/result.rs` の `is_ok` / `unwrap` 等は `variant_id 0/1` でパターンマッチ。「`Result`
の std 帰属」は両側（`?` + コンストラクタ）を同時に解く必要があり、ともにフェーズ 2 に属する。

## 付録 C：用語集

| 用語                       | 定義                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Layer 0                    | 演算子→メソッド名の固定マッピング表、言語レベル定数、ユーザー変更不可                                                    |
| Layer 1                    | `Type.method` キーで表引きし呼び出すディスパッチ基層                                                                     |
| Layer 2                    | インターフェース契約層、ジェネリクス制約の根拠を提供し、演算子の通行条件でもある                                         |
| インターフェース実装登録表 | コアのデフォルト登録とユーザーインスタンス化を集約する実装総表；演算子クエリと制約解決の唯一の判定基準、名前解析と無関係 |
| ネイティブファストパス     | 基本型に保持されるハードコード演算経路、インターフェースディスパッチを経由しない                                         |
| 位置バインディング         | RFC-004 の `f[0]` 構文、関数の引数位置をメソッドにバインドするコンパイル時挙動                                           |
| 自動派生                   | 全フィールドが比較可能なレコードに対しコンパイラが生成するフィールド単位 `==`、明示的インスタンス化で上書き可能          |
