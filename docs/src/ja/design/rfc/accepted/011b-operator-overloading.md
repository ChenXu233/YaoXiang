## 概要

YaoXiang に**演算子オーバーロード**能力を補完し、`a + b` / `a == b` / `a[i]` / `e?`
をユーザ定義型で実装可能にする。これにより、RFC-011 に既に書き込まれた制約構文中の**演算子制約**（`T: Add + Multiply`）を
**紙の上の能力**から実装可能な機構へと変える（同一文中の `Zero`
は演算子ではないため、未解決問題を参照）。

設計は**三層の責務分離**を採用する：固定の演算子→メソッドマッピング表（Layer
0）、名前でディスパッチする基盤（Layer 1、既存の `method_bindings`
を再利用）、インターフェース契約層（Layer
2、ジェネリクス制約用）。演算子の**優先順位と結合性は言語の固定**とし、ユーザはセマンティクスのみをオーバーロードする。

第1弾の範囲：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
の7つのインターフェース。算術インターフェースは**3つの型パラメータ** `(Self, R, O)`
を採用する——結果型 `O` を明示化することで、`1 + 2.5`（`Float` を返す）や
`point * 2.0`（スケーリング）のような異型演算を表現可能にする。`Equal`
は**デフォルトで自動派生**され（全フィールドが比較可能なレコードは自動的にフィールド毎の `==`
を取得）、明示的なインスタンス化で上書き可能。

`Try`（`?`
のインターフェース化）はフェーズ2に全体移動する：これは RFC-010（構築）と RFC-010b（分解）に依存し、インターフェースの形状がまだ確定していないため（未解決問題を参照）。

**新しい構文も新しいキーワードもなく**、すべて RFC-011a の既存機構（インターフェース宣言 / インスタンス化 / 外部メソッド宣言 / オーバーロード）を再利用する。

## 動機

### なぜこの機能が必要か

#### 1. RFC-011 の中心的な例がこれに依存しており、現状は「実現不可能」よりも悪い

RFC-011（受理済み）は8箇所で演算子名を型制約として使用している：

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

RFC 群の中に `Add` / `Multiply` の出所や、`+`
がそれらにどうバインドされるかを定義した文書は一つもない。実測で現状がより悪いことを確認：`T: Add`
は**今日、直接コンパイルエラー**になる——制約解決が旧 trait 表（`trait_data.rs`）を照会するが、その表に
`Add` がない。制約名 `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut`
likewise 宙に浮いている（本 RFC での処理は「他の RFC との協調」を参照）。

#### 2. ユーザ定義型が基本演算に参加できない（実測済み）

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

連鎖的后果：`list.contains(list_of_structs, p)` は**完全に使用不能**——内部で `==`
に依存している。一方 `(1, 2) == (1, 2)` と `[1] == [1]`
はランタイムの要素毎比較で**常に使用可能**——構造体が唯一の欠落箇所。

#### 3. `?` が型名をコンパイラに直結させ、`Result` の std 帰属を阻む

`?` の実装は型名とバリアント番号を同時にハードコードしている：

```rust
// typecheck：ハードコードで Result 型を構築
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen：グループ名とバリアント番号をハードコード
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

これにより `Result` は core に留まらざるを得ない。`?`
を**インターフェース駆動**に変更すれば、当該インターフェースを実装する任意の型（ユーザ定義を含む）を
`?` で使用でき、`Result` は std に帰属できる（RFC-013 には既に「std ライブラリ
`Result(T, Error)`」という方針がある）。

これは問題の一側面にすぎない：`ok(...)` / `err(...)` / `some(...)`
構築構文も現在はパーサに直結されている（言語仕様§1.4.2 で「パーサが認識するコンストラクタ」として列挙）。「`Result`
を std に帰属」させるには `?`
とコンストラクタの**両方を一緒に解く**必要があり、いずれも本 RFC のフェーズ2に含まれる。

#### 4. ユーザ定義コンテナがインデックス化できない

`Index` の型検査はハードコードされたホワイトリスト：

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[1].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// その他 → "型レベルで認識できないコンテナは沈黙せず拒否"
```

ユーザが任意のコンテナ型を定義しても、`c[0]` は一律エラーになる。

#### 5. `%` の実装が既刊ドキュメントに違反している

実測で `-7 % 3` は `-1`
を返す（切り捨て剰余）。しかし言語リファレンスの演算子優先順位表（`reference/index.md`）には既に「`* / %`
乗除**モジュロ**」と書かれている——ドキュメントが約束しているのはモジュロで、実装は剰余。これは設計変更ではなく、**実装がドキュメントに違反する欠陥**であり、本 RFC で合わせて修正する。

### 既存の半完成基礎

調査により機構は**大部分既に存在**し、欠けているのは配線であることが判明：

| 機構                                                            | 場所                                                                                                             | 状態                                                          |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| インターフェース宣言 `(Self: Type) -> Type`                     | RFC-011a Phase 1                                                                                                 | ✅ 実行可能                                                   |
| インターフェースインスタンス化 `Animal(Dog)` + 外部メソッド宣言 | RFC-011a Phase 2–3                                                                                               | ✅ 実行可能（ユニットテストあり）                             |
| メソッドディスパッチ `method_bindings["Type.method"]`           | `expressions.rs`（`environment.rs` で登録、`expressions.rs` の呼び出し解決とフィールドフォールバック経路で照会） | ✅ 実行可能                                                   |
| 関連型（= インターフェース型パラメータ）                        | RFC-011 §3.1；RFC-011a でこの方式が既に採用                                                                      | ✅ 機構確定                                                   |
| 型族評価 `AssociatedTypeDef`                                    | `dependent_types.rs`                                                                                             | ✅ 本番ユースケース `std.assert` の `IsTrue`                  |
| `Equal` / `Dup` / `Clone` / `Debug` trait                       | `trait_data.rs` に登録済み                                                                                       | ⚠️ `Equal` は消費箇所ゼロ；旧自動派生は署名のみ登録で実装なし |
| 演算子 → メソッド名マッピング                                   | —                                                                                                                | ❌ 存在しない                                                 |

**結論**：これはゼロから機能を作るのではなく、既存の部品を配線しかつ文書化する作業である。

## 提案

### 中核設計：三層の責務分離

```
Layer 0  固定マッピング表（言語レベル定数、ユーザ変更不可）
         + → add    == → equal    [] → index    ? → residual
         │  コンパイル時に組み込み、型推論に参加せず、ユーザに非公開
         ▼
Layer 1  ディスパッチ基盤（名前でメソッドを検索し呼び出し）        ← 既存機構を再利用
         method_bindings["Point.add"]
         ▼
Layer 2  インターフェース契約（ジェネリクス制約用）
         Add / Equal / Index / Try …
         T: Add 制約を成立させ、演算子の通過条件として機能
```

**階層化の理由**：

- **Layer 0 と 1 が演算子を「使える」ようにし**、Layer
  2 が演算子を「制約できる」ようにする。統合すると `add` という名前のメソッドがすべて `+`
  で呼ばれてしまい、RFC-011 の `T: Add` が演算子から乖離する。
- **Layer 1 は新規作成しない**：`method_bindings` は既に `Type.method`
  キーで検索しており（フィールド検索失敗後のフォールバック経路）、演算子も同じ経路を通せばよい。
- **Layer
  2 は通過条件**：演算子は通過前に**必ず**型が対応インターフェースを実装していることを確認する必要がある（§Equal の自動派生例外を参照——派生と登録は同じ判定基準）。

### 名前と登録：二つの独立したチャネル

**演算子は「インターフェース実装登録表」を照会し、通常の名前解決は通らない。**

- 登録表はコアが所有し、二つの登録を集約する：コアが基本型に対して行うデフォルト登録（`Add(Int, Int, Int)`
  など）と、ユーザが型体内で記述するインターフェースインスタンス化（`Add(Point, Point, Point)`）。実装コードが物理的にどのモジュールにあっても、登録は同じ表に集約され、`+`
  / `==` / `[]` はこの表のみを参照する。
- ローカルモジュールで `Add` という名前の**同名バインディング**を定義しても（例：RFC-011
  §5.2 の Peano 型レベル加算
  `Add: (A: Type, B: Type) -> Type = match ...`）、これは**名前検索チャネル**を通るため、当該モジュール内の
  `Add`
  という名前の解決にのみ影響し、**登録表には触れず、演算子の可用性にも影響しない**。同名で別物、互いに隠蔽しない。

これは同時に「RFC-011 の型レベル `Add` と本 RFC のインターフェース `Add`
は衝突するか」という問いに答える：衝突しない。型レベル `Add`
は純粋に型レベルの計算（Zero/Succ は型であって値であり、`Zero + Succ(...)`
のような値演算は決して発生しない）であり、値レベルの演算子インターフェースとは、同一名前を持つ二つの異なるレベルである。

### Layer 0：固定マッピング表

| 演算子            | インターフェース                                        | メソッド          | 第1弾       |
| ----------------- | ------------------------------------------------------- | ----------------- | ----------- |
| `+`               | `Add`                                                   | `add`             | ✅          |
| `-`               | `Subtract`                                              | `subtract`        | ✅          |
| `*`               | `Multiply`                                              | `multiply`        | ✅          |
| `/`               | `Divide`                                                | `divide`          | ✅          |
| `%`               | `Modulo`                                                | `modulo`          | ✅          |
| `==` `!=`         | `Equal`                                                 | `equal`           | ✅          |
| `[]`              | `Index`                                                 | `index`           | ✅          |
| `?`               | `Try`（4メソッド、フェーズ2で確定）                     | `is_failure` など | ✅ 実装済み |
| `<` `<=` `>` `>=` | —（ネイティブ命令として保持）                           | —                 | ❌          |
| `and` `or`        | —（短絡評価は言語セマンティクスで、オーバーロード不可） | —                 | ❌          |
| ビット演算 5種    | —                                                       | —                 | ❌          |
| 単項 `-` `!`      | —                                                       | —                 | ❌          |

**インターフェース名は略語ではなくフルスペル**（`Mul` ではなく `Multiply`）：RFC-011 本文の
`T: Add + Multiply + Zero` との一貫性を保つため、**受理済み RFC は変更しない**。

**`%` は `Modulo`
セマンティクス**を採用する（数学的モジュロ、結果の符号は除数に追従）。動機セクションで現在の剰余実装が既刊ドキュメント（`reference/index.md`「乗除モジュロ」）に違反していることを確認済みであり、本条は欠陥修正として処理し、互換期間は設けない。

現状備考：`%` の型検査ホワイトリストは現在 Int/Float のみであり（`+`
の Int/Float/String/List ホワイトリストとは異なる）、付録 A.2 に実測記録がある。

### Layer 2：インターフェース定義

#### 算術インターフェース（3つの型パラメータ）

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

3つの型パラメータはそれぞれ以下の役割を担う：

- `Self`：左オペランド型（レシーバ、`&Self`
  で借用、RFC-009 借用トークンと RFC-011a レシーバ規約を参照）；
- `R`：右オペランド型——**左右で異型を許可**；
- `O`：**結果型**、明示的に宣言。

**なぜ結果型を明示的なパラメータにする必要があるのか**（`-> Self` で固定しない理由）：

1. `Self` で固定すると `Add(Int, Float)` のメソッドは `Int` を返さなければならず、`1 + 2.5`
   を正しく表現できない；
2. 結果型を明示化することで、RFC-011 §8.3 の昇格型族
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }`
   と本 RFC のインターフェース登録が**同一表の二つの視点**となる——コア登録 `Add(Int, Float, Float)`
   が `(Int, Float) => Float` の行そのものであり、ユーザの各インスタンス化はこの表への行追加となる；
3. `Index` インターフェースは元々3パラメータ `(Self, Key, Value)` で、戻り型 `Value`
   がパラメータ——算術インターフェースに `O`
   を加えると、演算子インターフェースファミリの形状が統一され、`Self` で固定する方がむしろ異質。

**コアデフォルト登録**（ネイティブ命令パス、メソッド呼び出しを経由しない）：`Add(Int, Int, Int)`、`Add(Int, Float, Float)`、
`Add(Float, Int, Float)`、`Add(Float, Float, Float)`、`Add(String, String, String)`（連結）、
`Add(List(T), List(T), List(T))`（要素連結）など。5つの算術インターフェースは基本型に対して同様。`1 + 2.5`
は現在のコンパイルエラー（ホワイトリストが両側同型を要求）から、`3.5: Float`
を返す合法な演算に変わる。

**制約構文糖衣**：`T: Add` ≜ `Add(T, T, T)`
が登録済み——同型自己複合、結果もその型。RFC-011 行列乗法例の `a * b + c` の全工程で型が `T`
であることが、まさにこの意味を要求する。`T: Equal` likewise ≜ `Equal(T, T)`。

**異型例**——ベクトルスケーリング：

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### 等価インターフェース（デフォルト自動派生）

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` はデフォルトで自動派生**される、ルールは5条：

1. **デフォルト派生**：レコード型を定義する際、全フィールドが比較可能（基本型、`String`、またはそれ自体が比較可能なレコード/タプル/リストを含み、`&mut`
   フィールドを含まない）であれば、コンパイラが**フィールド毎比較**の `==`
   を自動生成し、ネイティブコードパスを経由し、ユーザ可視のメソッドを生成しない。ユーザが書いた型は自然な比較が可能で、儀式は不要。
2. **明示的オーバーライド**：型本体に `Equal(Point, Point)` を書き `Point.equal`
   メソッドを提供すれば、ユーザのバージョンを使用し（例：許容誤差付き浮動小数点比較）、自動派生は行わない。
3. **フィールドが比較不可能な場合**：自動派生は失敗し、`==`
   は使用不可、診断はどのフィールドが原因かを示す；この場合でもユーザは手動で `Equal`
   を記述可能（例：関数フィールドを名前で比較）。
4. **前提条件**：`&mut T`
   線形トークン（フィールド再帰）を含む型は比較に参加しない——線形トークンは一度読むと消費され、2つの値を同時に取り出せない。注意すべき点は「線形性」が前提であり「Dup」ではない点：プリミティブ値型（Int/Float/Bool/Char）は RFC-011
   §2.4 により Dup に属さず（これらはコンパイラ組み込みの値コピー）、Dup を前提とすると
   `Point { x: Float, y: Float }` は誤って拒否される。
5. **制約と同じ判定基準**：`T: Equal` の解決と `==`
   の通過は同じ「登録表照会または構造派生」ルールを辿る——制約と演算子は常に同じ答えを出す。

**一貫性の根拠**：`(1, 2) == (1, 2)` と `[1] == [1]` は今日もランタイムの要素毎比較（`executor.rs`
の比較ホワイトリストに Tuple/List/Array を含む）を経由しており、レコード型のみが除外された複合型である。自動派生は新しい暗黙のデフォルトではなく、言語内部の既存挙動を最後のピースまで補完するものである。

**旧機構の退役**：`trait_data.rs` の `Equal`
の旧自動派生（署名登録のみ、実装コードなし、消費箇所ゼロ）を停止；`Equal`
の全判定（基本型のデフォルト登録、構造派生、明示的インスタンス化）はインターフェース登録表経由となる。旧 trait 表は Clone/Dup/Debug の既存职责を保持（名前が演算子インターフェースと重複しないため、将来的な統合は別途議論）。

#### インデックスインターフェース

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value`
は関連型メンバーではなく型パラメータ**：RFC-011a の未解決問題は「関連型はジェネリクスパラメータで実装する」と確定済み（`Iterator: (Item: Type) -> Type`
が同型の先例）、`type` メンバー構文を導入する必要はない。

**所有権に関する説明**：`index` は `&Self` 借用から完全な `Value` を返す。標準ライブラリの
`list.get: (&Vec(A), Int) -> A`
は既に同じ形式であり、本インターフェースは**std の現状と同待遇**；移動セマンティクスの要素型に対する「借用から完全な値を取り出す」の正確なセマンティクスは、RFC-009 の全面的施行時に統一処理され、本 RFC はこのために新しいルールを発明しない。

**複数位置インデックスはタプル詰め + オーバーロード**で実現し、可変長インターフェースは導入しない：

```yaoxiang
// 1次元コンテナ
List(T) が Index(List(T), Int, T) をインスタンス化         → arr[0]

// 多次元コンテナ
Grid    が Index(Grid, Tuple(Int, Int), Float) をインスタンス化  → g[0, 1]
//                    └─ Key はタプル

// 2つのインスタンス化シグネチャが異なる → 共存可能
```

**同一型の同名インターフェースは複数のインスタンス化を許可**し、注入されたメソッドのシグネチャで区別し、RFC-011a のメソッドレベルオーバーロード規則に従って共存する。RFC-011a のオーバーロードは明示的にメソッドレベルまでだが、本条はインスタンス化レベルの規則を補足する：同名インターフェースインスタンス化の共存の合法性は、展開後のメソッドシグネチャの衝突有無で決定される（衝突は E1097、フィールド/メソッド名前空間規則と同じ源）。

#### 伝播インターフェース Try（フェーズ2で確定し実装済み）

`?` のインターフェース化におけるインターフェース名は
`Try`、4メソッドの形状（2026-09-22 フェーズ2確定）：

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    is_failure: (self: &Self) -> Bool,
    success:    (self: &Self) -> T,
    residual:   (self: &Self) -> E,
    from_error: (E) -> Self,
}
```

- **セマンティック分担**：`is_failure` は成否判定、`success` は成功ペイロード取得、`residual`
  は失敗ペイロード取得、`from_error` は型横断伝播の橋渡し（`f()?` の `T` ≠ 外側の `U` のとき `E`
  から失敗値を再構築）。`?`
  の lowering は統一して4メソッド呼び出しチェーンを生成する——`is_failure(t)` が真なら
  `Ret from_error(residual(t))`、そうでなければ式の値は
  `success(t)`；バリアント検査シーケンスを手書きすることはもうなく、`Result` / `Option`（std
  yx 実装）とユーザ定義 Try 型は同じ経路を通る。
- **デッドコード分岐**：`success` の失敗アームと `residual` の成功アームは契約上到達不能、実装は
  `assert(false)` で発散する（`assert` は `Never` を返し、爆発原理 `Never <: T`
  が通過させ、type-system.md §2.2）。
- **検査**：typecheck はインターフェース実装登録表を照会し（Self 位は名目マッチング、抽象エントリは scrutinee 実引数でインスタンス化）；外側関数の戻り型も
  `Try` を実装し `E`
  位が失敗値を受け取れなければならない（E1081/E1082/E1083 のセマンティクスがインターフェース化される）。
- **`Result` を std に帰属**：`Result` / `Option` の型定義と Try 実装を `std/result.yx` /
  `std/option.yx`（純粋な YaoXiang）に移行し、ネイティブ `ok`/`err`
  コンストラクタを退役させる——バリアント構築構文 `Result(T, E).ok(v)`
  が唯一の構築経路となる（コンストラクタ直結問題はパーサ特例判定の退役とともに解決）。Option の Try 残余型は
  `Void` を取る（Rust Try 実験の NoneT セマンティクスに対応）。

### 例

#### ユーザ定義型：算術と等価が開梱

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false —— Equal 自動派生、インスタンス化不要
    println(a == a)             # true
}
```

#### カスタム等価（自動派生を上書き）

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# 浮動小数点比較に許容誤差、フィールド毎自動派生を上書き
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### カスタムコンテナのインデックス化

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### ジェネリクス制約がついに実現可能に

```yaoxiang
// RFC-011 の例がついに実装可能
// T: Add ≜ Add(T, T, T) が登録済み；T: Multiply ≜ Multiply(T, T, T) が登録済み
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

（RFC-011 の看板例 `T: Add + Multiply + Zero` における `Zero` / `One`
は本 RFC の範囲外——これらは定数メンバであって演算子ではなく、「レシーバなしインターフェースメンバ」は RFC-011a に先例がないため、未解決問題を参照）

### 構文変更

**新しい構文も新しいキーワードもない**。すべての能力は既存機構の組み合わせによる：

| 能力                           | 再利用する既存機構                                            |
| ------------------------------ | ------------------------------------------------------------- |
| インターフェース宣言           | RFC-011a Phase 1                                              |
| インターフェースインスタンス化 | RFC-011a Phase 2（`Dog: { Animal(Dog) }`）                    |
| メソッド実装                   | RFC-011a Phase 3（外部宣言 `Point.add`）                      |
| 関連型                         | RFC-011 §3.1（インターフェース型パラメータ）                  |
| 複数位置インデックス           | 既存のタプル詰め解析 + インスタンス化レベルオーバーロード規則 |
| 演算子優先順位                 | **言語固定**、ユーザカスタマイズは開放しない                  |

## 詳細設計

### 型システムへの影響

**新規インターフェース**（Layer 2）：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal`
`Index`（`Try` はフェーズ2）。

**インターフェース実装登録表**：演算子判定の中枢。コアデフォルト登録（基本型）とユーザインスタンス化（`check_interface_instantiation`
が生成する `ImplementationProof`）を集約し、`+` / `==` / `[]` の通過検査と `T: Add`
制約解決（`bounds.rs` の
`check_trait_bounds`）が**同一表を照会**する——「制約は通ると言い、演算子は通らないと言う」ような隙間は存在しない。

**`Equal`
の構造派生**：登録表の上に構造ルール（全フィールドが比較可能 ⇒ 比較可能）を重ね、基本型はコア登録がフォールバックとなり、再帰的に閉じる。旧
`trait_data.rs` の `Equal` 登録と旧自動派生は停止。

**演算子照会と名前解決の分離**：`+`
などの演算子は登録表のみを照会し、通常の名前解決は通らない；ローカル同名バインディング（例：型レベル
`Add` ファミリ）は演算子に影響しない（§名前と登録を参照）。

**オーファンルール**：演算子実装は**型の定義モジュール**にのみ書ける——`Int`
の定義はコアにあるため、`Int` の登録はコアのみが書ける；`Point`
の定義はユーザモジュールにあるため、定義者のみが登録できる。すべての型が同じ規則に従い、組み込み型に特権はない。

### ランタイム挙動

**ランタイムオーバーヘッドゼロ**：演算子はコンパイル時に呼び出し対象を決定する（静的ディスパッチ）。基本型（`Int`/`Float`/`String`/`List`）は**ネイティブ命令ファストパス**を保持し、インターフェースディスパッチを経由しない；自動派生された構造体
`==` はネイティブのフィールド毎比較を生成；`Any`（動的型）位置の `==` / `!=`
は既存のランタイム比較を保持（RFC-036 テストフレームワーク `assert_eq`
がこの挙動に依存しており、影響なし）。

**`%` セマンティクス修正**：`-7 % 3` は `-1`（切り捨て剰余）から
`2`（数学的モジュロ）に変更。インタプリタ（`checked_rem`）、定数畳み込み（`a % b`）、バイトコード（`I64_REM`）の3か所を同期して修正。

### コンパイラ変更

| コンポーネント                       | 変更                                                                                                                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `typecheck/inference/expressions.rs` | `infer_binary` ホワイトリストを「ネイティブファストパス + 登録表照会」の二経路に変更；`Expr::Index` ホワイトリストにインターフェース照会分岐を追加                                                   |
| `typecheck/inference/bounds.rs`      | `check_trait_bounds` は演算子インターフェース名についてインターフェース登録表を照会（`Equal` は構造派生を含む）                                                                                      |
| `typecheck/checker.rs`               | `Equal` 構造派生（レコード定義後）を追加；インスタンス化レベルオーバーロード規則（同名インターフェースの複数インスタンス化をメソッドシグネチャで共存）                                               |
| `middle/core/ir_gen.rs`              | `Expr::Index` にメソッド呼び出しディスパッチ分岐を追加；明示的 `equal` がない構造体 `==` はネイティブのフィールド毎比較を生成；`Mod` 命令を数学的モジュロに変更                                      |
| インターフェース登録表（新規）       | Layer 0 マッピング表定数 + 演算子→インターフェース照会関数 + コアデフォルト登録（`Int`/`Float`/`String`/`List` など）                                                                                |
| `trait_data.rs`                      | `Equal` 登録と旧自動派生を停止（`Clone`/`Dup`/`Debug` は現状維持）                                                                                                                                   |
| 診断                                 | `Equal` 前提（線形トークン）不満足は `E1101`（型がインターフェースを実装していない）族を再利用；`E1081`/`E1082` 文言から "Result" 表記を削除（フェーズ2で `Try` 実装時、RFC-013 手順に従い三者同期） |

### 後方互換性

**基本型演算は不変**：`1 + 2`、`"a" + "b"`、`[1] + [2]`、`1 < 2`
はすべてネイティブパスを保持し、挙動と性能は不変。

**`1 + 2.5` がコンパイルエラーから合法へ**：コア登録 `Add(Int, Float, Float)`
後、以前ホワイトリストに拒否されていた混合算術が使用可能になり、`Float`
を返す。これは新規能力であり、既存コードへの影響はない。

**`%` セマンティクス修正**：`-7 % 3` が `-1` から `2`
へ。**欠陥修正**と定性する（ドキュメントが既にモジュロを約束、動機 §5 参照）、互換期間は設けない；既存テストコーパスに負数
`%` に依存する用例はない（確認済み）。

**構造体 `==` がランタイムエラーから使用可能へ**：以前 `Struct == Struct`
は一律 E6007 ランタイムエラー、配線後は自動派生で使用可能に——悪い状態から良い状態へ、既存の合法コードへの影響はない。

**`Any` の `==` は影響なし**：動的型位置はランタイム比較を保持（RFC-036 の `assert_eq`
アサートファミリが依存、以前使用可能、今後も使用可能）。

**`f[0]` 位置バインディングは不変**：`distance[0]` は RFC-004 のコンパイラ組み込み能力で、**`Index`
インターフェースを通らず**、影響なし。

**`?` は既存コードに対して透過的**（フェーズ2）：`Result` に `Try`
インスタンス化を追加すれば、既存の `?` 使用法の挙動は完全に同じ。

## トレードオフ

### 利点

- **RFC-011 の演算子制約を実現**：`T: Add + Multiply`
  を紙の上（実際にはコンパイルエラー）から実装可能にし、受理済み RFC 本文は変更しない
- **`Result` の core バインドを解除**（フェーズ2）：`?` とコンストラクタをインターフェース化した後
  `Result` は std に帰属可能、RFC-013 の既存方針と整合
- **実測された欠陥を修正**：`Point == Point` を開梱で実現、構造体に対して使用不能だった
  `list.contains` も合わせて修正
- **新構文ゼロ**：すべて RFC-011a の既存機構を再利用し、パーサ構文規則に触れない
- **ランタイムオーバーヘッドゼロ**：静的ディスパッチ + 基本型のネイティブファストパス
- **ユーザ定義コンテナが使用可能**：`Box(T)[0]` が「一律エラー」から使用可能に
- **言語内部の一貫性**：Tuple/List は既に要素毎比較、レコード型が追いつく；算術インターフェースの3パラメータが Index の形状と統一；RFC-011
  §8.3 昇格表とインターフェース登録表が合一

### 欠点

- **`Equal`
  自動派生は暗黙のデフォルト**：将来「レコードはデフォルトで比較可能」を撤回することは破壊的変更になる。この立場を受け入れる——Tuple/List の既存挙動と一貫しており、明示的インスタンス化で常に上書き可能
- **`Equal` 前提が線形トークンを含む型を拒否する**：`&mut` フィールドを含む型は `==`
  不可、これは意味的に正しいことの代償として、明確な診断（どのフィールドかを示す）が必要
- **インターフェースインスタンス化は明示的コスト**：算術演算子ごとに1行のインスタンス化と1つのメソッドを書く必要がある（`Equal`
  は免除——自動派生）。RFC-011a の構文が暗黙的派生を許さない（代わりに `Self`
  型パラメータに魔法がない）
- **`%` セマンティクス修正は挙動変更**：欠陥修正と定性するものの、移行ガイドに注記が必要

## 代替案

### 案 A：Layer 1 のみを行う（メソッド名ディスパッチ）、インターフェース層なし

`+` は `add` というメソッドがあるかどうかのみを照会し、`Add` インターフェースの実装を要求しない。

**否決理由**：RFC-011 の `T: Add`
制約が演算子から乖離する——制約はインターフェースを照会し、演算子はメソッド名を照会する両者が一貫しない答えを出す可能性がある。また「`+`
を加算不可能な型に適用」について、コンパイル時に正確な診断を提供できない。

### 案 B：`?` 問題を解決するためにコンストラクタ構文 `Ok(x)` / `Some(x)` を導入

`?` をインターフェース化せず、和型にコンストラクタ構文を追加する。

**否決理由**：RFC-010（受理済み）と衝突する。RFC-010 は「和型の表現に統一してレコード型を使用し、**2 セットの構文は不要**」と明記し、
`|` 構文を明示的に廃止している。コンストラクタ導入は第2の表現を導入することになる。またこれは `?`
のみを解決し、`Point == Point` やカスタムコンテナのインデックス化は解決しない。

### 案 C：比較演算子も第1弾でインターフェース化（`Ordering` を導入）

`<` `<=` `>` `>=` を `Compare` インターフェース経由で3値 `Ordering` を返すようにする。

**否決理由**：`<`
は YaoXiang ですでに**一等 IR 命令**（`Instruction::Lt/Le/Gt/Ge`）であり、インターフェース化すると基本型が迂回を強いられる。また
`Ordering` を導入すると、`Ordering` 自身の比較/ソート、浮動小数点 `NaN` の `PartialOrd` vs `Ord`
など一連の問題を伴い、独立 RFC の規模になる。現在の実測で露呈したニーズ（`Point == Point`、`list.contains`）は**`Equal`
のみ**で必要十分。

### 案 D：演算子名を略語にする（`Add` インターフェースのメソッドは `add`、インターフェースは `Mul`）

**否決理由**：RFC-011 本文に既に `T: Add + Multiply + Zero`
と書かれているため、略語使用は受理済み RFC の変更を伴う。

### 案 E：`Equal` は明示的インスタンス化のみ、自動派生なし

**否決理由**：ユーザが書いた型が `==` できないのは体験として受け入れがたい；さらに
`(1, 2) == (1, 2)`、`[1] == [1]`
は既に要素毎比較であり、レコード型のみが除外されている現状自体が不整合。明示的インスタンス化は上書き手段として残し、カスタムニーズに対応する。

### 案 F：算術インターフェースの戻り型を `-> Self` で固定

**否決理由**：`Add(Int, Float)` のメソッドは `Int` を返すことを強いられ、`1 + 2.5`
を正しく表現できない；ベクトルスケーリング `Multiply(Point, Float)`
likewise 記述できない。また RFC-011 §8.3 の昇格型族 `(Int, Float) => Float`
が実装場所を失う。3パラメータ `(Self, R, O)` は `Index(Key, Value)` と形状が統一される。

## 実装戦略

### 依存関係

| 依存                                    | 状態        | 本 RFC への影響                                                  |
| --------------------------------------- | ----------- | ---------------------------------------------------------------- |
| RFC-011a インターフェース機構 Phase 1–3 | ✅ 実装済み | Layer 2 の基盤（実測で実行可能を確認）                           |
| RFC-010 レコード式構築パス              | ❌ 未実装   | **フェーズ2**：`?` の構築側 + コンストラクタパーサ特例判定の退役 |
| RFC-010b バリアント分解                 | ❌ 紙の上   | **フェーズ2**：`Result.residual` の `match` 記法、網羅性         |
| RFC-009 線形トークン推論                | 一部        | `Equal` の前提制約検査                                           |

### フェーズ分割

**インターフェース依存**（設計上の制約であり、スケジュールではない）で2グループに分割：

**フェーズ1 — RFC-010/010b に依存しない**：

- Layer 0 マッピング表 + インターフェース実装登録表 + Layer 1 ディスパッチ配線
- `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
  の7インターフェース（3型パラメータ形式）
- `Equal` 自動派生 + 線形前提制約 + 制約解決の登録表経由化
- `%` セマンティクス修正（インタプリタ/定数畳み込み/バイトコードの3か所）
- `Any` 位置 `==` のランタイム比較保持
- **効果**：`Point + Point`、`Point == Point`（儀式不要）、`Box(T)[0]`、`1 + 2.5`、`T: Add`
  制約がすべて使用可能

**フェーズ2 — RFC-010 / RFC-010b に依存、着工前に `Try` 形状を確定**：

- `Try` インターフェース形状確定（未解決問題を参照）
- `?`
  インターフェース化 + コンストラクタ（`ok`/`err`/`some`）パーサ特例判定を退役、RFC-010 レコード構築パス経由に変更
- `Result` を core から std に移行（RFC-013 の既存方針に基づく）

### リスク

| リスク                                           | 緩和策                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `%` セマンティクス変更が既存ユーザコードに影響   | 欠陥修正と定性 + テストコーパスに負数 `%` 依存がないことを確認済み                   |
| `Equal` 自動派生の暗黙デフォルトを将来撤回困難   | 立場確定：Tuple/List の既存挙動と一貫、明示的インスタンス化で上書き可能              |
| 基本型の二重パス（ネイティブ + 登録）の不整合    | ゲート条件：コア登録のセマンティクスはネイティブ命令と一致必須（同一表の二つの視点） |
| 登録表照会によるコンパイル低速化                 | 型名によるインデックス + インスタンス化結果のキャッシュ（RFC-011a proof を再利用）   |
| インスタンス化レベルオーバーロードが曖昧性を導入 | メソッドレベルオーバーロードと同規則：シグネチャ衝突は E1097                         |

## 他の RFC との協調

本 RFC の位置づけは**消費側の要求提起者**であり、以下 RFC を同期更新して整合性を保証する必要がある（改訂権限を取得済み）：

| RFC                              | 更新内容                                                                                                                                                                                                                                                |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011**（受理済み）          | §制約箇所に `Add` / `Multiply` が 011b で定義・実装されることを注記（`T: Add` ≜ `Add(T, T, T)`）；`Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` を宙に浮く制約名として标注（後続 RFC 待ち）；§8.3 昇格型族がインターフェース登録表と合一することを注記 |
| **RFC-010**（受理済み）          | 「レコードフィールドがコンストラクタである」の実装要件を明確化——フェーズ2のコンストラクタパーサ特例判定退役の前提                                                                                                                                       |
| **RFC-010b**（草案、元 RFC-039） | 構築と分解はペアでなければならない；網羅性判定は `Result` の core/std 帰属に依存しない（011b フェーズ2 で移行）                                                                                                                                         |
| **RFC-009**（受理済み）          | §型属性箇所に相互参照：`Equal` の前提は「`&mut` 線形トークンを含まない」（Dup ではない）                                                                                                                                                                |
| **RFC-013**（受理済み）          | フェーズ2 実装時：`E1081` / `E1082` 文言から "Result" 表記を削除；`Equal` 前提診断は `E1101` 族を再利用——RFC-013 手順に従い三者同期（codes/*.rs ↔ locales ↔ コード表）                                                                                  |
| **RFC-018**（受理済み）          | `%` を数学的モジュロに変更すると、`Mod → srem/urem` マッピング表が無効化、`srem` + 符号修正（または `sdiv`+`mul`+`sub` 合成）に変更が必要、「モジュロ/剰余」用語の混用も修正                                                                            |
| **RFC-036**（受理済み）          | 変更不要。関係性を注記：`Any` 位置の `==` はランタイム比較を保持、`assert_eq` アサートファミリはゲートの影響を受けない                                                                                                                                  |

> `Result` を std に帰属させる根拠：RFC-013 は既に「std ライブラリ
> `Result(T, Error)`」と位置づけており、RFC-014 の階層化で std はコアソースに含まれる。本 RFC フェーズ2 はその実装パスの一つであり、他の番号を参照しない。

- [x] ~~ユーザは既存型に演算子実装を追加できるか（オーファンルール）？~~ →

      の定義はコアにあるため、コアのみが登録可能；ユーザは自分の型にのみ登録可能。すべての型が等しく扱われ、組み込み型に特権はない（2026-09-22）

- [ ] 複数位置インデックスの Key はタプル詰め（現状）か複数引数（Swift スタイル）か？（タプル詰めを維持、パーサは変更しない）
- [ ] `Zero` / `One`
      の形式：定数メンバは演算子ではなく、「レシーバなしインターフェースメンバ」は RFC-011a に先例がなく、別途確定後に RFC-011 の
      `T: Add + Multiply + Zero` 全句がようやく実現可能
- [ ] `Try` インターフェースの完全形状：`?`
      には成否判定、成功ペイロード抽出、失敗パスからの外側戻り値生成の3つが必要で、単一メソッドの

- [ ] `?T` 接頭辞型（RFC-026 FFI の nullable 注釈、RFC-018）と `e?` 接尾辞演算子が `?`
      記号を共有：位置が異なる（型位置 vs 式位置）ため衝突は構成せず、文書化説明で十分
- [ ] `PartialOrd` /
      `Ordering`（比較演算子のインターフェース化）：独立 RFC、本 RFC では明示的に行わない

## 付録A：調査エビデンス

以下の実測はすべて **0.8.0**（`target/debug/yaoxiang-rs.exe`）で再現済み。

### A.1 インターフェース機構の可用性（本 RFC の基盤）

| 能力                                                                               | 実測                                                               |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| インターフェース宣言 `Animal: (Self: Type) -> Type = {...}`                        | ✅ 定義可能                                                        |
| インターフェースインスタンス化 + 外部メソッド `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ 実行可能、正しい出力（`tests/rfc011a.rs` にユニットテストあり） |
| インターフェースインスタンス化 + **内部**メソッド宣言                              | ❌ `E1097`（フィールドとメソッドの名前空間衝突）                   |
| メソッドディスパッチ `d.speak()`                                                   | ✅ 実行可能                                                        |

**注**：`E1097`
は演算子メソッドが**外部宣言**形式（`Point.add: (self: &Point, ...)`）を使用しなければならないことを意味し、RFC-011a の例と一致する。`method_bindings`
の登録は `environment.rs`（`add_method_binding`）、照会は `expressions.rs`
の呼び出しターゲット解決とフィールド検索失敗フォールバック経路。

### A.2 演算子の現状

| 式                                  | 現状                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]` | ✅ ハードコードホワイトリスト（Int/Float/String/List、**両側同型を要求**）                |
| `1 + 2.5`（Int + Float）            | ❌ コンパイルエラー（ホワイトリストが両側同型を要求）                                     |
| `-7 % 3`                            | `-1`（切り捨て剰余；`%` ホワイトリストは Int/Float のみ、`+` のホワイトリストとは異なる） |
| `Point(1,2) == Point(1,2)`          | ❌ `E6007`（Eq が Struct 上でランタイム失敗）                                             |
| `(1,2) == (1,2)` / `[1] == [1]`     | ✅ ランタイム要素毎比較（Struct のみが欠落）                                              |
| Any 位置の `a == b`（`assert_eq`）  | ✅ ランタイム比較（RFC-036 で実証）                                                       |
| `f[0]`（関数位置バインディング）    | ⚠️ バインディング宣言内でのみ有効、式として使用すると `E3006`                             |
| `arr[0, 1]`（複数位置）             | ✅ タプル詰め、`list([1, 2])`                                                             |

### A.3 `?` とコンストラクタのハードコード位置

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

コンストラクタ側：`ok(T)` / `err(E)` / `some(T)` はパーサが認識（言語仕様 `syntax.md` §1.4.2）；
`std/result.rs` の `is_ok` / `unwrap` などは `variant_id 0/1` パターンでマッチング。「`Result`
を std に帰属」させるには両側（`?` + コンストラクタ）を一緒に解く必要があり、いずれもフェーズ2に含まれる。

| 意思決定                                   | 決定                                                                                                         | 理由                                                                                                                             | 日付       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| アーキテクチャ                             | 三層分離（マッピング表 / ディスパッチ基盤 / インターフェース契約）                                           | 統合すると RFC-011 制約と演算子が乖離する                                                                                        | 2026-09-15 |

| `%` インターフェース名                     | `Modulo`（数学的モジュロ）                                                                                   | 名前がセマンティクスを固定する                                                                                                   | 2026-09-15 |

| 関連型                                     | インターフェース型パラメータを使用、`type` メンバー構文は導入しない                                          | RFC-011a でこの方式が確定済み（`Iterator: (Item: Type)`）                                                                        | 2026-09-15 |
| メソッドバインディングとインデックスの統一 | 概念統一、インターフェースはコンテナインデックスのみ担当                                                     | 位置バインディングのキーはコンパイル時定数、結果型は型族評価が必要でユーザ実装不可                                               | 2026-09-15 |

| ビット演算 / 単項演算子                    | 第1弾では行わない                                                                                            | カスタム型には稀、YAGNI                                                                                                          | 2026-09-15 |

| `Equal` 派生                               | デフォルト自動派生 + 明示的インスタンス化で上書き；制約解決は同じ判定基準                                    | 「自分の型が == できない」は受け入れがたい；Tuple/List は既に要素毎比較、Struct のみが欠落                                       | 2026-09-22 |

## 付録C：用語集

| 用語                       | 定義                                                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Layer 0                    | 演算子 → メソッド名の固定マッピング表、言語レベル定数、ユーザ変更不可                                                |
| Layer 1                    | `Type.method` キーで検索し呼び出すディスパッチ基盤                                                                   |
| Layer 2                    | インターフェース契約層、ジェネリクス制約の根拠を提供し、同時に演算子の通過条件                                       |
| インターフェース実装登録表 | コアデフォルト登録とユーザインスタンス化を集約する実装総表；演算子照会と制約解決の唯一の判定基準、名前解決とは無関係 |
| ネイティブファストパス     | 基本型が保持するハードコード演算パス、インターフェースディスパッチを経由しない                                       |
| 位置バインディング         | RFC-004 の `f[0]` 構文、関数パラメータ位置をメソッドにバインド、コンパイル時挙動                                     |
| 自動派生                   | コンパイラが全フィールド比較可能なレコードに対して生成するフィールド毎 `==`、明示的インスタンス化で上書き可能        |
