## 概要

YaoXiang に**演算子オーバーロード**能力を補完し、`a + b` / `a == b` / `a[i]` / `e?`
をユーザ定義型が実装できるようにする。また、RFC-011 に既に書き込まれた制約構文中の**演算子制約**（`T: Add + Multiply`）を、**紙の上の能力**から実装可能な機構にする（同文中の
`Zero` は演算子に属さないため、オープンクエスチョン参照）。

設計は**3 層役割分離**を採用する：固定された演算子→メソッド対応表（Layer
0）、名前によるディスパッチ基盤（Layer 1、既存の `method_bindings`
を再利用）、インタフェース契約層（Layer
2、ジェネリクス制約用）。演算子の**優先順位と結合性は言語固定**とし、ユーザは意味論のみをオーバーロードする。

初回対象範囲：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
の 7 つのインタフェース。算術インタフェースは**3 つの型パラメータ** `(Self, R, O)`
を採用する——結果型 `O` を明示化することで、`1 + 2.5`（`Float` を返す）や
`point * 2.0`（スケーリング）のような異型演算を表現可能にする。`Equal`
は**既定で自動派生**し（全フィールドが比較可能なレコードは自動的にフィールド単位の `==`
を獲得）、明示的なインスタンス化で上書き可能。

`Try`（`?`
のインタフェース化）全体はフェーズ 2 に移す：RFC-010（構築）と RFC-010b（分解）の実装に依存し、インタフェース形状も未確定のため（オープンクエスチョン参照）。

**新構文なし、新キーワードなし**。すべて RFC-011a の既存機構（インタフェース宣言 / インスタンス化 / 外部メソッド宣言 / オーバーロード）を再利用する。

## 動機

### なぜこの機能が必要か

#### 1. RFC-011 の中核例がこれに依存し、現状は「実現不可能」よりも悪い

RFC-011（受入済）は 8 箇所で演算子名を型制約として使用している：

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

RFC 全般で `Add` / `Multiply` がどこから来るのか、`+`
がどうそれらに束縛されるのかを定義した文書は一つもない。実測により現状はさらに悪い：`T: Add`
は**本日現在、直接コンパイルエラー**になる——制約解決が旧 trait 表（`trait_data.rs`）を検索するが、表に
`Add` が無い。制約名 `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut`
も同様に宙に浮いている（本 RFC での処理は「他の RFC との連携」参照）。

#### 2. ユーザ定義型が基本演算に参加できない（実測）

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

連帯する后果：`list.contains(list_of_structs, p)` は**完全に使用不能**——内部が `==`
に依存しているため。一方、`(1, 2) == (1, 2)` と `[1] == [1]`
は実行時の要素単位比較で**常に使用可能**——構造体のみが唯一の欠落箇所。

#### 3. `?` が型名をコンパイラに焼き付け、`Result` の std 帰属を阻む

`?` の実装は型名とバリアント番号の両方をハードコードしている：

```rust
// typecheck：硬编码构造 Result 类型
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen：硬编码 group 名与 variant 编号
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

これにより `Result` は core に残らざるを得ない。`?`
を**インタフェース駆動**に変更すれば、インタフェースを実装するすべての型（ユーザ定義型を含む）が `?`
を使用でき、`Result` は std に帰属可能になる（RFC-013 には既に「std ライブラリ
`Result(T, Error)`」の位置付けがある）。

なお、これは問題の一半にすぎない：`ok(...)` / `err(...)` / `some(...)`
の構築構文も現在パーサに焼き付けられている（言語仕様 §1.4.2 で「パーサが認識するコンストラクタ」として列挙）。「Result の std 帰属」には
`?` とコンストラクタの**両方を同時に解く**必要があり、いずれも本 RFC のフェーズ 2 に帰属する。

#### 4. ユーザ定義コンテナがインデックス不可

`Index` の型検査はハードコードされたホワイトリスト：

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// 其余 → "类型层不认的容器宁拒不静默"
```

ユーザがコンテナ型を定義すると、`c[0]` はすべてエラーになる。

#### 5. `%` の実装が公開済みドキュメントに違反

実測では `-7 % 3` は
`-1`（切り捨て余り）を返す。しかし言語リファレンスの演算子優先順位表（`reference/index.md`）には既に「`* / %`
乗除は**剰余**」と書かれている——ドキュメントは剰余を約束しているが、実装は余りを返している。これは設計変更ではなく、**実装がドキュメントに違反する欠陥**であり、本 RFC で併せて修正する。

### 既存の半完成基盤

調査の結果、機構は**大部分既に存在**し、欠けているのは配線のみである：

| 機構                                                          | 位置                                                                                                             | 状態                                                            |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| インタフェース宣言 `(Self: Type) -> Type`                     | RFC-011a Phase 1                                                                                                 | ✅ 動作可能                                                     |
| インタフェースインスタンス化 `Animal(Dog)` + 外部メソッド宣言 | RFC-011a Phase 2–3                                                                                               | ✅ 動作可能（単体テストあり）                                   |
| メソッドディスパッチ `method_bindings["Type.method"]`         | `expressions.rs`（`environment.rs` で登録、`expressions.rs` の呼び出し解析とフィールドフォールバック経路で検索） | ✅ 動作可能                                                     |
| 関連型（= インタフェース型パラメータ）                        | RFC-011 §3.1；RFC-011a がこの方式を採用                                                                          | ✅ 機構確定                                                     |
| 型族評価 `AssociatedTypeDef`                                  | `dependent_types.rs`                                                                                             | ✅ 本番ユースケース `std.assert` の `IsTrue`                    |
| `Equal` / `Dup` / `Clone` / `Debug` trait                     | `trait_data.rs` に登録済み                                                                                       | ⚠️ `Equal` 消費点ゼロ、旧自動派生はシグネチャ登録のみで実装なし |
| 演算子 → メソッド名マッピング                                 | —                                                                                                                | ❌ 存在しない                                                   |

**結論**：これはゼロから機能を作るのではなく、既存部品を配線し文書化するものである。

## 提案

### 中核設計：3 層役割分離

```
Layer 0  固定対応表（言語レベル定数、ユーザ変更不可）
         + → add    == → equal    [] → index    ? → residual
         │  コンパイル時組み込み、型推論に参加せず、ユーザに公開しない
         ▼
Layer 1  ディスパッチ基盤（名前でメソッド検索し呼び出し）        ← 既存機構を再利用
         method_bindings["Point.add"]
         ▼
Layer 2  インタフェース契約（ジェネリクス制約用）
         Add / Equal / Index / Try …
         T: Add 制約を成立させ、演算子の許可条件としても機能
```

**階層化の理由**：

- **Layer 0 と 1 で演算子を「使える」ようにし**、Layer
  2 で演算子を「制約できる」ようにする。統合すると、`add` という名前のあらゆるメソッドが `+`
  で呼ばれることになり、RFC-011 の `T: Add` と演算子が乖離する。
- **Layer 1 は新規作成しない**：`method_bindings` は既に `Type.method`
  キーで表検索しており（フィールド検索失敗時のフォールバック経路）、演算子も同じ経路を通せばよい。
- **Layer
  2 は許可条件**：演算子を通す前に**必ず**型が対応インタフェースを実装していることを確認する（`Equal`
  の自動派生例外を参照——導出と登録は同じ判定基準）。

### 名前と登録：2 つの独立した経路

**演算子が検索するのは「インタフェース実装登録表」であり、通常の名前解決を経由しない。**

- 登録表はコアが所有し、2 つの登録を統合する：コアが基本型に対して行う既定登録（`Add(Int, Int, Int)`
  等）と、ユーザが型本体内で記述するインタフェースインスタンス化（`Add(Point, Point, Point)`）。実装コードが物理的にどのモジュールに存在するかに関わらず、登録は同一の表に集約され、`+`
  / `==` / `[]` はこの表のみを参照する。
- ローカルモジュールで `Add` という名前の**同名バインディング**（例えば RFC-011
  §5.2 の Peano 型レベル加算
  `Add: (A: Type, B: Type) -> Type = match ...`）は**名前検索経路**を通り、そのモジュール内の `Add`
  という名前の解決にのみ影響し、**登録表には触れず、演算子の可用性にも影響しない**。同名で異物、互いにシャドウイングしない。

これは同時に「RFC-011 の型レベル `Add` と本 RFC のインタフェース `Add`
が衝突するか」に対する答えでもある：衝突しない。型レベル `Add`
は純粋に型レベルの計算であり（Zero/Succ は型であって値ではないため、`Zero + Succ(...)`
という値演算は決して存在しない）、値レベルの演算子インタフェースとは同一名の異なるレイヤーである。

### Layer 0：固定対応表

| 演算子            | インタフェース                            | メソッド        | 初回      |
| ----------------- | ----------------------------------------- | --------------- | --------- |
| `+`               | `Add`                                     | `add`           | ✅        |
| `-`               | `Subtract`                                | `subtract`      | ✅        |
| `*`               | `Multiply`                                | `multiply`      | ✅        |
| `/`               | `Divide`                                  | `divide`        | ✅        |
| `%`               | `Modulo`                                  | `modulo`        | ✅        |
| `==` `!=`         | `Equal`                                   | `equal`         | ✅        |
| `[]`              | `Index`                                   | `index`         | ✅        |
| `?`               | `Try`（4 メソッド、フェーズ 2 で確定）    | `is_failure` 等 | ✅ 実装済 |
| `<` `<=` `>` `>=` | —（ネイティブ命令を維持）                 | —               | ❌        |
| `and` `or`        | —（短絡は言語意味論、オーバーロード不可） | —               | ❌        |
| ビット演算 5 個   | —                                         | —               | ❌        |
| 単項 `-` `!`      | —                                         | —               | ❌        |

**インタフェース名は短縮形ではなく完全綴り**（`Mul` ではなく `Multiply`）：RFC-011 本文の
`T: Add + Multiply + Zero` と整合させ、**受入済 RFC を変更しない**。

**`%` は `Modulo`
意味論**（数学的剰余、結果符号は除数に従う）を採用。動機セクションで現在の余り実装が公開済みドキュメント（`reference/index.md`「乗除剰余」）に違反していることを確認済であり、本項目はバグ修正として扱い、互換期間は設けない。

現状注記：`%` の型検査ホワイトリストは現状 Int/Float のみである（`+`
の Int/Float/String/List ホワイトリストとは異なる）、付録 A.2 に実測記録がある。

### Layer 2：インタフェース定義

#### 算術インタフェース（3 つの型パラメータ）

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

3 つの型パラメータはそれぞれ以下の役割を担う：

- `Self`：左オペランド型（レシーバ、`&Self`
  借用、RFC-009 借用トークンと RFC-011a レシーバ規約参照）；
- `R`：右オペランド型——**左右で異型を許容**；
- `O`：**結果型**、明示的に宣言。

**なぜ結果型を明示的なパラメータにしなければならないのか**（`-> Self` 固定ではなく）：

1. `Self` 固定にすると `Add(Int, Float)` のメソッドは `Int` を返さなければならず、`1 + 2.5`
   を正しく表現できない；
2. 結果型を明示化すると、RFC-011 §8.3 の昇格型族
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }`
   と本 RFC のインタフェース登録は**同一の表の 2 つの見方**になる——コア登録 `Add(Int, Float, Float)`
   がまさに `(Int, Float) => Float`
   の行であり、ユーザのインスタンス化ごとにこの表に行を追加する形になる；
3. `Index` インタフェースは元々 3 パラメータ `(Self, Key, Value)` で、戻り型 `Value`
   がパラメータ——算術インタフェースに `O`
   を加えることで、演算子インタフェースファミリ全体の形状が統一され、`Self`
   固定の方がむしろ異端になる。

**コア既定登録**（ネイティブ命令経路、メソッド呼び出しを経由しない）：`Add(Int, Int, Int)`、`Add(Int, Float, Float)`、
`Add(Float, Int, Float)`、`Add(Float, Float, Float)`、`Add(String, String, String)`（連結）、
`Add(List(T), List(T), List(T))`（要素連結）等、5 つの算術インタフェースが基本型に対して同様。`1 + 2.5`
は現在のコンパイルエラー（ホワイトリストが両側同型を要求）から、`3.5: Float`
を返す合法な演算になる。

**制約構文糖衣**：`T: Add` ≜ 登録済
`Add(T, T, T)`——同型の自己複合、結果もその型。RFC-011 の行列乗算例で `a * b + c` 全体を通じて型が
`T` であることが要求されているのも、まさにこの意味。`T: Equal` も同様 ≜ `Equal(T, T)`。

**異型例**——ベクトルのスケーリング：

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### 等価インタフェース（既定で自動派生）

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` は既定で自動派生**、規則は 5 つ：

1. **既定派生**：レコード型定義時、全フィールドが比較可能（基本型、`String`、またはそれ自体が比較可能なレコード/タプル/リストであり、`&mut`
   フィールドを含まない）であれば、コンパイラが自動的に**フィールド単位比較**の `==`
   を生成し、ネイティブコード経路で実行され、ユーザ可視メソッドは生成されない。ユーザが書いた型は自然に比較可能となり、儀式は一切不要。
2. **明示的オーバーライド**：型本体に `Equal(Point, Point)` を記述し `Point.equal`
   メソッドを提供した場合、ユーザの版（例えば許容差付き浮動小数点比較）を使用し、自動派生は行わない。
3. **フィールドが比較不能な場合**：自動派生は失敗し、`==`
   は使用不可、診断でどのフィールドが原因かを示す；この場合でもユーザは手動で `Equal`
   を記述してカスタム比較（例えば関数フィールドを含む場合は名前で比較）できる。
4. **前置条件**：`&mut T`
   線形トークン（フィールド再帰）を含む型は比較に参加しない——線形トークンは一度読むと消費されるため、2 つの値を同時に取り出して比較できない。前提は「非線形」であり「Dup」ではないことに注意：原始値型（Int/Float/Bool/Char）は RFC-011
   §2.4 により Dup に属さない（これらはコンパイラ組み込みの値コピーである）、Dup を前提とすると
   `Point { x: Float, y: Float }` が誤って拒否される。
5. **制約共通判定基準**：`T: Equal` の解決と `==`
   の許可は同一の「登録検索または構造導出」規則に従う——制約と演算子は常に同じ答えを出す。

**一貫性の根拠**：`(1, 2) == (1, 2)` と `[1] == [1]`
は本日現在既に実行時の要素単位比較であり（`executor.rs`
の比較ホワイトリストに Tuple/List/Array を含む）、レコード型のみが排除された唯一の複合型である。自動派生は新しい暗黙の既定を追加するのではなく、言語内部の既存挙動を最後の 1 ピースに補完するものである。

**旧機構の廃止**：`trait_data.rs` 中の `Equal`
の旧自動派生（シグネチャ登録のみ、実装コードなし、消費点ゼロ）を停止；`Equal`
の全判定（基本型の既定登録、構造導出、明示的インスタンス化）はインタフェース登録表を経由する。旧 trait 表は Clone/Dup/Debug の既存职责を維持する（名前が演算子インタフェースと重複しないため、将来的な統一は別途検討）。

#### インデックスインタフェース

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value`
は関連型メンバではなく型パラメータとして**：RFC-011a のオープンクエスチョンは「関連型はジェネリックインタフェースパラメータで実現する」と確定済（`Iterator: (Item: Type) -> Type`
が同型の先例）、`type` メンバ構文を導入する必要はない。

**所有権に関する説明**：`index` は `&Self` 借用から完全な `Value` を返す。標準ライブラリの
`list.get: (&Vec(A), Int) -> A`
が既に同じ形態であり、本インタフェースは**std の現状と同待遇**；移動意味論の要素型に対する「借用から完全値を取り出す」正確な意味論は、RFC-009 の全面的施行時に統一処理され、本 RFC はこのために新たなルールを発明しない。

**複数位置インデックスはタプル詰め合わせ + オーバーロードで実現**、可変長引数インタフェースは導入しない：

```yaoxiang
// 一维容器
List(T) 实例化 Index(List(T), Int, T)                   → arr[0]

// 多维容器
Grid    实例化 Index(Grid, Tuple(Int, Int), Float)       → g[0, 1]
//                    └─ Key 是元组

// 两个实例化签名不同 → 共存
```

**同一型の同名インタフェースは複数のインスタンス化を許可**し、その注入メソッドのシグネチャで区別し、RFC-011a のメソッドレベルオーバーロード規則に従って共存する。RFC-011a のオーバーロード規定はメソッドレベルまで明示されており、本条はその上にインスタンス化レベルの規則を追加する：同名インタフェースインスタンス化の共存の合法性は、展開後のメソッドシグネチャの衝突有無で決定される（衝突なら E1097、フィールド/メソッド名前空間規則と同源）。

#### 伝播インタフェース Try（フェーズ 2 で確定・実装済）

`?` のインタフェース化インタフェース名は `Try`、4 メソッド形状（2026-09-22 フェーズ 2 確定）：

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    is_failure: (self: &Self) -> Bool,
    success:    (self: &Self) -> T,
    residual:   (self: &Self) -> E,
    from_error: (E) -> Self,
}
```

- **意味論の分業**：`is_failure` が成否判定、`success` が成功ペイロード取得、`residual`
  が失敗ペイロード取得、`from_error` が型間伝播の橋渡し（`f()?` の `T` ≠ 外側 `U` のときに `E`
  から失敗値を再構築）。`?` の lowering は 4 メソッド呼び出し連鎖を一律に生成する——`is_failure(t)`
  が真なら `Ret from_error(residual(t))`、そうでなければ式の値は
  `success(t)`；バリアント検査シーケンスを手書きすることはなくなり、`Result` / `Option`（std
  yx 実装）とユーザ定義 Try 型は同じ経路を通る。
- **デッドコード分岐**：`success` の失敗側と `residual` の成功側は契約上到達不能、実装は
  `assert(false)` で発散させる（`assert` は `Never` を返し、爆発原理 `Never <: T`
  で通過、type-system.md §2.2）。
- **検査**：typecheck はインタフェース実装登録表を検索（Self 位は名目一致、抽象エントリは scrutinee 実引数でインスタンス化）；外側関数の戻り型も
  `Try` を実装し `E`
  位で失敗値を受容できる必要がある（E1081/E1082/E1083 の意味論もインタフェース化される）。
- **Result を std へ帰属**：`Result` / `Option` の型定義と Try 実装を `std/result.yx` /
  `std/option.yx`（純粋 YaoXiang）に移行し、ネイティブ `ok`/`err`
  コンストラクタは廃止——バリアント構築構文 `Result(T, E).ok(v)`
  が唯一の構築経路（コンストラクタ焼き付け問題はパーサ特例廃止と共に解決）。Option の Try 残余型は
  `Void` を取る（Rust の Try 実験の NoneT 意味論に対応）。

### 例

#### ユーザ定義型：算術と等価が即座に使用可能

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false —— Equal 自动派生，无需实例化
    println(a == a)             # true
}
```

#### カスタム等価（自動派生をオーバーライド）

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# 浮点比较带容差，覆盖逐字段自动派生
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### カスタムコンテナインデックス

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### ジェネリクス制約がついに実現可能

```yaoxiang
// RFC-011 的示例从此可落地
// T: Add ≜ Add(T, T, T) 已登记；T: Multiply ≜ Multiply(T, T, T) 已登记
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

（RFC-011 の看板例 `T: Add + Multiply + Zero` 中の `Zero` / `One`
は本 RFC の範囲外——これらは定数メンバであり演算子ではない、「レシーバなしのインタフェースメンバ」は RFC-011a に先例がないため、オープンクエスチョン参照。）

### 構文変更

**新構文なし、新キーワードなし**。すべての能力は既存機構の組み合わせで構成される：

| 能力                         | 再利用する既存機構                                                  |
| ---------------------------- | ------------------------------------------------------------------- |
| インタフェース宣言           | RFC-011a Phase 1                                                    |
| インタフェースインスタンス化 | RFC-011a Phase 2（`Dog: { Animal(Dog) }`）                          |
| メソッド実装                 | RFC-011a Phase 3（外部宣言 `Point.add`）                            |
| 関連型                       | RFC-011 §3.1（インタフェース型パラメータ）                          |
| 複数位置インデックス         | 既存のタプル詰め合わせ解析 + インスタンス化レベルオーバーロード規則 |
| 演算子優先順位               | **言語固定**、ユーザによるカスタムは開放しない                      |

## 詳細設計

### 型システムへの影響

**新規インタフェース**（Layer 2）：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal`
`Index`（`Try` はフェーズ 2）。

**インタフェース実装登録表**：演算子の判定中枢。コア既定登録（基本型）とユーザインスタンス化（`check_interface_instantiation`
が生成する `ImplementationProof`）を集約し、`+` / `==` / `[]` の許可検査と `T: Add`
制約解決（`bounds.rs` の
`check_trait_bounds`）は**同一の表を検索**する——「制約は可能と言うが演算子は不可と言う」隙間は存在しない。

**`Equal`
の構造導出**：登録表の上に構造規則を追加（全フィールド比較可能 ⇒ 比較可能）、基本型はコア登録がフォールバックを担い、再帰的に閉じる。旧
`trait_data.rs` の `Equal` 登録と旧自動派生は停止。

**演算子クエリと名前解決の分離**：`+`
等の演算子は登録表のみを検索し、通常の名前解決を行わない；ローカル同名バインディング（例えば型レベル
`Add` ファミリ）は演算子に影響しない（§名前と登録参照）。

**オーファン規則**：演算子実装は**型の定義モジュール**にのみ記述可能——`Int`
の定義はコアにあるため、`Int` の登録はコアのみが記述可能；`Point`
の定義はユーザモジュールにあるため、定義者のみが登録可能。すべての型が同一規則に従い、組み込み型に特権はない。

### 実行時挙動

**実行時オーバーヘッドゼロ**：演算子はコンパイル時に呼び出し先を決定する（静的ディスパッチ）。基本型（`Int`/`Float`/`String`/`List`）に対しては**ネイティブ命令ファストパス**を維持し、インタフェースディスパッチを経由しない；自動派生された構造体の
`==` はネイティブなフィールド単位比較を生成；`Any`（動的型）位置の `==` / `!=`
は既存の実行時比較を維持する（RFC-036 テストフレームワークの `assert_eq`
がこの挙動に依存しており、影響なし）。

**`%` 意味論修正**：`-7 % 3` は `-1`（切り捨て余り）から
`2`（数学的剰余）に変更。インタプリタ（`checked_rem`）、定数畳み込み（`a % b`）、バイトコード（`I64_REM`）の 3 箇所を同期して修正。

### コンパイラ変更

| コンポーネント                       | 変更                                                                                                                                                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `typecheck/inference/expressions.rs` | `infer_binary` ホワイトリストを「ネイティブファストパス + 登録表クエリ」の二段に変更；`Expr::Index` ホワイトリストにインタフェースクエリ分岐を追加                                                           |
| `typecheck/inference/bounds.rs`      | `check_trait_bounds` で演算子インタフェース名はインタフェース登録表を検索（`Equal` は構造導出を含む）                                                                                                        |
| `typecheck/checker.rs`               | `Equal` 構造導出（レコード定義後）を追加；インスタンス化レベルオーバーロード規則（同名インタフェースの複数インスタンス化はメソッドシグネチャで共存）                                                         |
| `middle/core/ir_gen.rs`              | `Expr::Index` にメソッド呼び出しディスパッチ分岐を追加；明示的 `equal` なしの構造体 `==` はネイティブなフィールド単位比較を生成；`Mod` 命令を数学的剰余に変更                                                |

| 診断                                 | `Equal` 前置（線形トークン）不充足は `E1101`（型がインタフェースを実装していない）族を再利用；`E1081`/`E1082` 文言から "Result" の字句を除去（フェーズ 2 で `Try` 実装に合わせ、RFC-013 手順に従い三者同期） |

### 後方互換性

**基本型の演算は不変**：`1 + 2`、`"a" + "b"`、`[1] + [2]`、`1 < 2`
はすべてネイティブ経路を維持し、挙動と性能は不変。

**`1 + 2.5` はコンパイルエラーから合法へ**：コア登録 `Add(Int, Float, Float)`
により、ホワイトリストで拒否されていた混合算術が使用可能になり、`Float`
を返す。これは新規能力であり、既存コードへの影響はない。

**`%` 意味論修正**：`-7 % 3` は `-1` から `2`
に変更。**バグ修正**と位置付け（ドキュメントは早くから剰余を約束、動機 §5 参照）、互換期間は設けない；既存テストコーパスに負数の
`%` に依存する用例はない（確認済）。

**構造体 `==` は実行時エラーから使用可能へ**：これまで `Struct == Struct`
は一律 E6007 実行時エラーだったものが、配線後は自動派生で使用可能になる——壊れ状態から良状態への変化であり、既存の合法コードへの影響はない。

**`Any` の `==` は影響なし**：動的型位置は実行時比較を維持（RFC-036 の `assert_eq`
アサーション族が依存、これまでは使用可能、これ以降も使用可能）。

**`f[0]` 位置結合は不変**：`distance[0]` は RFC-004 のコンパイラ組み込み能力であり、**`Index`
インタフェースを経由せず**、影響なし。

**`?` は既存コードに対して透過的**（フェーズ 2）：`Result` に `Try` インスタンス化を追加後、既存の
`?` の挙動は完全に一致する。

## トレードオフ

### 利点

- **RFC-011 の演算子制約を実現**：`T: Add + Multiply`
  が紙の上（実際にはコンパイルエラー）から実装可能になり、受入済 RFC 本文は変更しない
- **`Result` の core 依存を解除**（フェーズ 2）：`?` とコンストラクタのインタフェース化後、`Result`
  は std に帰属可能となり、RFC-013 の既存位置付けと整合
- **実測欠陥を修正**：`Point == Point` が即座に使用可能、連動して `list.contains`
  の構造体に対する使用不能も修正
- **新構文ゼロ**：すべて RFC-011a の既存機構を再利用し、パーサ構文規則には触れない
- **実行時オーバーヘッドゼロ**：静的ディスパッチ + 基本型ネイティブファストパス
- **ユーザ定義コンテナが使用可能**：`Box(T)[0]` は「一律エラー」から使用可能へ
- **言語内部の整合性**：Tuple/List は既に要素単位比較、レコード型が追いつく；算術インタフェースの 3 パラメータと Index の形状が統一；RFC-011
  §8.3 昇格表とインタフェース登録が一致

### 欠点

- **`Equal`
  自動派生は暗黙の既定**：将来「レコードは既定で比較可能」を撤回するには破壊的変更となる。この立場を受け入れる——Tuple/List の既存挙動と一致し、明示的インスタンス化で常にオーバーライド可能
- **`Equal` 前置は線形トークンを含む型を拒否する**：`&mut` フィールドを含む型は `==`
  不可、これは意味論的に正しいことの代償であり、明確な診断（該当フィールドの指摘）が必要
- **インタフェースインスタンス化は明示的コスト**：算術演算子ごとにインスタンス化を 1 行 + メソッド 1 つの記述が必要（`Equal`
  は免除——自動派生）。RFC-011a の構文上、暗黙的導出は不可能（引き換えに `Self`
  型パラメータには魔法がない）
- **`%` 意味論修正は挙動変更**：バグ修正と位置付けられるが、移行説明に注記が必要

## 代替案

### 案 A：Layer 1 のみ実装（メソッド名によるディスパッチ）、インタフェース層は実装しない

`+` は `add` という名前のメソッドがあるかどうかのみを検索し、`Add`
インタフェースの実装を要求しない。

**却下理由**：RFC-011 の `T: Add`
制約が演算子と乖離する——制約はインタフェースを検索し、演算子はメソッド名を検索するため、両者が矛盾した答えを出す可能性がある。また「`+`
が加算不能な型に使われた」に対するコンパイル時の正確な診断が提供できない。

### 案 B：コンストラクタ構文 `Ok(x)` / `Some(x)` を導入して `?` 問題を解決

`?` をインタフェース化せず、和型にコンストラクタ構文を追加する。

**却下理由**：RFC-010（受入済）と衝突する。RFC-010 は「和型の表現には統一してレコード型を使用し、**2 つの構文は不要**」と明確に規定し、`|`
構文を明示的に廃止している。コンストラクタ導入は第二の表現を導入することになる。また `?`
のみを解決し、`Point == Point` やカスタムコンテナインデックスは解決しない。

### 案 C：比較演算子も初回でインタフェース化（`Ordering` 導入）

`<` `<=` `>` `>=` は `Compare` インタフェースを通り、3 値 `Ordering` を返す。

**却下理由**：`<`
は YaoXiang では既に**一級 IR 命令**（`Instruction::Lt/Le/Gt/Ge`）であり、インタフェース化により基本型が迂回を強いられる。また
`Ordering` を導入すると、`Ordering` 自身の比較/ソート、浮動小数点 `NaN` の `PartialOrd` vs `Ord`
など一連の問題が派生し、独立 RFC の規模となる。現在の実測で露わになった要件（`Point == Point`、`list.contains`）には
`Equal` のみで十分。

### 案 D：演算子名は短縮形（`Add` インタフェースのメソッドは `add` で、インタフェースは `Mul`）

**却下理由**：RFC-011 本文に既に `T: Add + Multiply + Zero`
と書かれており、短縮形を使うと受入済 RFC を変更する必要がある。

### 案 E：`Equal` は明示的インスタンス化のみ、自動派生なし

**却下理由**：ユーザが書いた型が `==` できないという体験は受け入れられない；さらに
`(1, 2) == (1, 2)`、`[1] == [1]`
本日現在既に要素単位比較であり、レコード型のみが排除されており、元々整合していない。明示的インスタンス化は上書き手段として残し、カスタム要件も両立させる。

### 案 F：算術インタフェースの戻り型を `-> Self` 固定

**却下理由**：`Add(Int, Float)` のメソッドは `Int` を返すことを強制され、`1 + 2.5`
を正しく表現できない；ベクトルスケーリング `Multiply(Point, Float)`
も同様に記述できない。また RFC-011 §8.3 の昇格型族 `(Int, Float) => Float`
が実装場所を喪失する。3 パラメータ `(Self, R, O)` は `Index(Key, Value)` と形状が統一される。

## 実装戦略

### 依存関係

| 依存                                  | 状態      | 本 RFC への影響箇所                                         |
| ------------------------------------- | --------- | ----------------------------------------------------------- |
| RFC-011a インタフェース機構 Phase 1–3 | ✅ 実装済 | Layer 2 の基盤（実測で動作確認済）                          |
| RFC-010 レコード式構築経路            | ❌ 未実装 | **フェーズ 2**：`?` の構築側 + コンストラクタパーサ特例廃止 |
| RFC-010b バリアント分解               | ❌ 紙の上 | **フェーズ 2**：`Result.residual` の `match` 記述、網羅性   |
| RFC-009 線形トークン推論              | 部分      | `Equal` の前置制約検査                                      |

### フェーズ分け

**インタフェース依存**（設計上の制約、スケジュールではない）で 2 グループに分割：

**フェーズ 1 — RFC-010/010b に依存しない**：

- Layer 0 対応表 + インタフェース実装登録表 + Layer 1 ディスパッチ配線
- `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
  7 つのインタフェース（3 型パラメータ形態）
- `Equal` 自動派生 + 線形前置制約 + 制約解決を登録表経由に切替
- `%` 意味論修正（インタプリタ/定数畳み込み/バイトコードの 3 箇所を含む）
- `Any` 位置の `==` は実行時比較を維持
- **効果**：`Point + Point`、`Point == Point`（儀式不要）、`Box(T)[0]`、`1 + 2.5`、`T: Add`
  制約がすべて使用可能

**フェーズ 2 — RFC-010 / RFC-010b に依存、開始前に `Try` 形状を確定する必要あり**：

- `Try` インタフェース形状の確定（オープンクエスチョン参照）
- `?`
  のインタフェース化 + コンストラクタ（`ok`/`err`/`some`）パーサ特例廃止、RFC-010 レコード構築経路への切替
- `Result` を core から std へ移行（RFC-013 の既存位置付けに基づく）

### リスク

| リスク                                         | 緩和策                                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------------------- |
| `%` 意味論変更が既存ユーザコードに影響         | バグ修正と位置付け + テストコーパスに負数 `%` 依存がないことを確認済             |
| `Equal` 自動派生の暗黙既定を将来撤回困難       | 立場確定：Tuple/List の既存挙動と一致、明示的インスタンス化で上書き可能          |
| 基本型の二重経路（ネイティブ + 登録）不整合    | ゲート：コア登録の意味論はネイティブ命令と一致する必要（同一表の 2 視点）        |
| 登録表クエリがコンパイルを遅延                 | 表は型名でインデックス + インスタンス化結果キャッシュ（RFC-011a proof を再利用） |
| インスタンス化レベルオーバーロードが曖昧性導入 | メソッドレベルオーバーロードと同規則：シグネチャ衝突なら E1097                   |

## 他の RFC との連携

本 RFC の位置付けは**消費側要求の提案者**であり、連携整合性確保のため以下の RFC を同期更新する必要がある（改訂権限取得済）：

| RFC                                  | 更新内容                                                                                                                                                                                                                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011**（受入済）                | §制約箇所で `Add` / `Multiply` が 011b で定義・実装されることを明記（`T: Add` ≜ `Add(T, T, T)`）；`Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` を宙に浮いた制約名として注記（後続 RFC で対応）；§8.3 昇格型族はインタフェース登録表と一致することを明記 |
| **RFC-010**（受入済）                | 「レコードフィールドがコンストラクタとなる」の実装要件を明確化——フェーズ 2 のコンストラクタパーサ特例廃止の前提                                                                                                                                           |
| **RFC-010b**（ドラフト、旧 RFC-039） | 構築と分解はペアでなければならない；網羅性判定は `Result` の core/std 帰属に依存しない（011b フェーズ 2 で移行）                                                                                                                                          |
| **RFC-009**（受入済）                | §型属性箇所で相互参照：`Equal` 前置は「`&mut` 線形トークンを含まない」（Dup ではない）                                                                                                                                                                    |
| **RFC-013**（受入済）                | フェーズ 2 実装時：`E1081` / `E1082` 文言から "Result" の字句を除去；`Equal` 前置診断は `E1101` 族を再利用——RFC-013 手順に従い三者同期（codes/*.rs ↔ locales ↔ コード表）                                                                                 |
| **RFC-018**（受入済）                | `%` を数学的剰余に変更後、`Mod → srem/urem` マッピング表が無効化、`srem` + 符号修正（または `sdiv`+`mul`+`sub` 合成）に変更が必要、加えて「剰余/余り」用語の混用を是正                                                                                    |
| **RFC-036**（受入済）                | 変更不要。関係明記：`Any` 位置の `==` は実行時比較を維持、`assert_eq` アサーション族はゲートの影響を受けない                                                                                                                                              |

> `Result` を std へ帰属させる根拠：RFC-013 で既に「std ライブラリ
> `Result(T, Error)`」と位置付け済み、RFC-014 の階層化で std はコアソースに含める。本 RFC フェーズ 2 はその実装経路の 1 つであり、他の番号は引用しない。

## オープンクエスチョン

- [x] ~~`Modulo` の意味論修正に互換期間が必要か？~~ →
      **クローズ**：言語リファレンスには早くから「乗除剰余」と明記されており、現在の余り実装は公開済みドキュメントに違反、バグ修正として扱い、互換期間は設けない（2026-09-22）
- [x] ~~ユーザは既存型に演算子実装を追加できるか（オーファン規則）？~~ →
      **確定**：演算子実装は型の定義モジュールにのみ記述可能。`Int`
      の定義はコアにあるため、コアのみが登録可能；ユーザは自分の型にのみ登録可能。すべての型が平等に扱われ、組み込み型に特権はない（2026-09-22）
- [ ] `Index` は可変インデックスを区別すべきか（Rust の `IndexMut`
      相当）？（初回は読み取り専用；可変インデックスは RFC-009 の `WriteToken`

- [ ] 複数位置インデックスの Key をタプル詰め合わせ（現状）にするか、複数パラメータ（Swift 風）にするか？（タプル詰め合わせを踏襲し、パーサは変更しない）
- [ ] `Zero` / `One`
      の形態：定数メンバは演算子ではなく、「レシーバなしのインタフェースメンバ」は RFC-011a に先例がないため別途確定が必要で、それにより RFC-011 の
      `T: Add + Multiply + Zero` 全文が実現可能になる
- [ ] `Try` インタフェースの完全形状：`?`
      には成否判定、成功ペイロード抽出、失敗パスの外側戻り値生成の 3 つが必要で、単一メソッドの
      `residual` では不十分；コンストラクタパーサ特例廃止と共に、フェーズ 2 開始前に確定
- [ ] `?T` 接頭辞型（RFC-026 FFI ナル可能注釈、RFC-018）と `e?` 接尾辞演算子で `?`
      記号を共有：位置が異なる（型位 vs 式位）ため衝突ではなく、文章での説明で足りる
- [ ] `PartialOrd` /
      `Ordering`（比較演算子のインタフェース化）：独立 RFC、本 RFC では明示的に実施しない

## 付録 A：調査証拠

以下の実測はすべて **0.8.0**（`target/debug/yaoxiang-rs.exe`）で再現した。

### A.1 インタフェース機構の可用性（本 RFC の基盤）

| 能力                                                                             | 実測                                                       |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| インタフェース宣言 `Animal: (Self: Type) -> Type = {...}`                        | ✅ 定義可能                                                |
| インタフェースインスタンス化 + 外部メソッド `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ 動作可能、出力正（`tests/rfc011a.rs` に単体テストあり） |
| インタフェースインスタンス化 + **内部**メソッド宣言                              | ❌ `E1097`（フィールドとメソッドで名前空間共有の衝突）     |
| メソッドディスパッチ `d.speak()`                                                 | ✅ 動作可能                                                |

**注**：`E1097`
は演算子メソッドが**外部宣言**形態（`Point.add: (self: &Point, ...)`）でなければならないことを意味し、RFC-011a の例と一致する。`method_bindings`
の登録は `environment.rs`（`add_method_binding`）にあり、検索は `expressions.rs`
の呼び出しターゲット解析とフィールド検索失敗時のフォールバック経路にある。

### A.2 演算子の現状

| 式                                  | 現状                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]` | ✅ ハードコードホワイトリスト（Int/Float/String/List、**両側同型を要求**）                |
| `1 + 2.5`（Int + Float）            | ❌ コンパイルエラー（ホワイトリストが両側同型を要求）                                     |
| `-7 % 3`                            | `-1`（切り捨て余り；`%` ホワイトリストは Int/Float のみ、`+` のホワイトリストとは異なる） |
| `Point(1,2) == Point(1,2)`          | ❌ `E6007`（Struct 上で Eq が実行時失敗）                                                 |
| `(1,2) == (1,2)` / `[1] == [1]`     | ✅ 実行時要素単位比較（Struct のみが欠落）                                                |
| Any 位置 `a == b`（`assert_eq`）    | ✅ 実行時比較（RFC-036 で実証）                                                           |
| `f[0]`（関数位置結合）              | ⚠️ 結合宣言内でのみ有効、式として使用すると `E3006`                                       |
| `arr[0, 1]`（複数位置）             | ✅ タプル詰め合わせ、`list([1, 2])`                                                       |

### A.3 `?` とコンストラクタのハードコード箇所

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

コンストラクタ側：`ok(T)` / `err(E)` / `some(T)` はパーサが認識（言語仕様 `syntax.md` §1.4.2）；
`std/result.rs` の `is_ok` / `unwrap` 等は `variant_id 0/1`
でパターンマッチ。「Result を std へ帰属」には両側（`?` + コンストラクタ）の同時解決が必要、いずれもフェーズ 2 に帰属する。

## 付録 C：用語集

| 用語                     | 定義                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Layer 0                  | 演算子 → メソッド名の固定対応表、言語レベル定数、ユーザ変更不可                                                |
| Layer 1                  | `Type.method` キーで表検索し呼び出すディスパッチ基盤                                                           |
| Layer 2                  | インタフェース契約層、ジェネリクス制約の根拠を提供し、同時に演算子の許可条件となる                             |
| インタフェース実装登録表 | コア既定登録とユーザインスタンス化を統合した実装総表；演算子クエリと制約解決の唯一の判定基準、名前解決と無関係 |
| ネイティブファストパス   | 基本型が維持するハードコード演算経路、インタフェースディスパッチを経由しない                                   |
| 位置結合                 | RFC-004 の `f[0]` 構文、関数パラメータ位置をメソッドに結合するコンパイル時挙動                                 |
| 自動派生                 | コンパイラが全フィールド比較可能なレコードに対し生成するフィールド単位 `==`、明示的インスタンス化で上書き可能  |
