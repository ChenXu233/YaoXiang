## 概要

YaoXiang に**演算子オーバーロード**能力を補完し、`a + b` / `a == b` / `a[i]` / `e?`
をユーザー定義型で実装可能にする。また、RFC-011 ですでに書き込まれた制約構文中の**演算子制約**（`T: Add + Multiply`）を
**紙上の能力**から実動可能な機構へ転換する（同一文中の `Zero`
は演算子に該当しないため、未解決問題を参照）。

設計は**三層の責務分離**を採用する。固定の演算子→メソッドマッピング表（Layer
0）、名前でディスパッチする基層（Layer 1、既存の `method_bindings`
を再利用）、インターフェース契約層（Layer
2、ジェネリクス制約用）。演算子の**優先順位と結合性は言語固定**であり、ユーザーはセマンティクスのみをオーバーロードする。

初回対象範囲：`Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
の七つのインターフェース。算術インターフェースは**三つの型パラメータ** `(Self, R, O)`
を採用する。すなわち結果型 `O` を明示化することで、`1 + 2.5`（`Float` を返す）や
`point * 2.0`（スケーリング）といった異型演算を表現可能にする。`Equal`
は**デフォルトで自動導出**され（全フィールドが比較可能なレコードは自動的にフィールド単位の `==`
を取得）、明示的なインスタンス化で上書き可能。

`Try`（`?`
のインターフェース化）は全体としてフェーズ 2 へ移す。RFC-010（構築）と RFC-039（分解）の着地に依存し、またインターフェースの形状が未確定であるため（未解決問題参照）。

**新構文なし、新キーワードなし**。すべて RFC-011a の既存機構（インターフェース宣言 / インスタンス化 / 外部メソッド宣言 / オーバーロード）を再利用する。

## 動機

### なぜこの機能が必要か

#### 1. RFC-011 の中心的例がこれに依存しており、現状は「履行不能」よりも深刻

RFC-011（承認済み）は 8 箇所で演算子名を型制約として使用している:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

全 RFC 中、`Add` / `Multiply` がどこから来るのか、`+`
がどうバインドされるのかは一切定義されていない。実測で確認した現状はさらに深刻で、`T: Add`
は**今日、直接コンパイルエラーになる**。制約解決が旧トレイト表（`trait_data.rs`）を照会するが、その表には
`Add` が存在しない。制約名 `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut`
もまた宙に浮いている（本 RFC での扱いは「他の RFC との協調」参照）。

#### 2. ユーザー定義型が基本演算に参加できない（実測）

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

連鎖的影響：`list.contains(list_of_structs, p)` は**完全に使用不能**となる。内部で `==`
に依存しているためである。一方、`(1, 2) == (1, 2)` と `[1] == [1]`
はランタイムの要素ごと比較で**常に利用可能**であり、構造体は唯一の穴となっている。

#### 3. `?` が型名をコンパイラーに固定しており、`Result` の std 帰属を阻む

`?` の実装は型名とバリアント番号を同時にハードコードしている:

```rust
// typecheck：結果型をハードコード構築
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen：グループ名とバリアント番号をハードコード
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

これにより `Result` は core に留まる必要がある。`?`
を**インターフェース駆動**に変更すれば、そのインターフェースを実装するあらゆる型（ユーザー定義を含む）が
`?` で使用可能となり、`Result` を std に帰属させることができる（RFC-013 にはすでに「std ライブラリ
`Result(T, Error)`」の位置付けがある）。

ただしこれは問題の一側面にすぎない。`ok(...)` / `err(...)` / `some(...)`
といった構築構文も現在はパーサーに固定されている（言語仕様 §1.4.2 で「パーサーが認識するコンストラクタ」として列挙）。「`Result`
の std 帰属」には `?`
とコンストラクタを**両側同時に解放**する必要があり、ともに本 RFC のフェーズ 2 に属する。

#### 4. ユーザー定義コンテナがインデックス化できない

`Index` の型検査はハードコードされたホワイトリストである:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// その他 → "型層が認識しないコンテナは黙って拒否せず明示"
```

ユーザーが任意のコンテナ型を定義しても、`c[0]` は一律エラーになる。

#### 5. `%` の実装が公開済みドキュメントに違反している

実測で `-7 % 3` は
`-1`（切り捨て余り）を返す。しかし言語リファレンスの演算子優先順位表（`reference/index.md`）には「`* / %`
乗除**剰余**」と明記されている。ドキュメントは剰余を約束しているのに、実装は余りを返している。これは設計変更ではなく、**実装がドキュメントに違反する欠陥**であり、本 RFC で併せて修正する。

### 既存の半完成基盤

調査の結果、機構の**大半はすでに存在**し、欠けているのは配線のみである:

| 機構                                                            | 位置                                                                                                           | 状態                                                      |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| インターフェース宣言 `(Self: Type) -> Type`                     | RFC-011a フェーズ 1                                                                                            | ✅ 実行可能                                               |
| インターフェースインスタンス化 `Animal(Dog)` + 外部メソッド宣言 | RFC-011a フェーズ 2–3                                                                                          | ✅ 実行可能（単体テストあり）                             |
| メソッドディスパッチ `method_bindings["Type.method"]`           | `expressions.rs`（`environment.rs` で登録、`expressions.rs` 呼び出し解析とフィールドフォールバック経路で照会） | ✅ 実行可能                                               |
| 関連型（= インターフェース型パラメータ）                        | RFC-011 §3.1；RFC-011a はこの方式をすでに採用                                                                  | ✅ 機構確定                                               |
| 型族評価 `AssociatedTypeDef`                                    | `dependent_types.rs`                                                                                           | ✅ 本番ユースケース `std.assert` の `IsTrue`              |
| `Equal` / `Dup` / `Clone` / `Debug` トレイト                    | `trait_data.rs` に登録済み                                                                                     | ⚠️ `Equal` は消費箇所ゼロ；旧自動導出は署名のみで実装なし |
| 演算子 → メソッド名マッピング                                   | —                                                                                                              | ❌ 存在しない                                             |

**結論**: これはゼロから機能を起こす作業ではなく、既存部品の配線と文書化である。

## 提案

### 核心設計: 三層の責務分離

```
Layer 0  固定マッピング表（言語レベル定数、ユーザーは変更不可）
         + → add    == → equal    [] → index    ? → residual
         │  コンパイル時に組み込み、型推論に参加せず、ユーザーには公開しない
         ▼
Layer 1  ディスパッチ基層（名前でメソッドを検索し呼び出し）        ← 既存機構を再利用
         method_bindings["Point.add"]
         ▼
Layer 2  インターフェース契約（ジェネリクス制約用）
         Add / Equal / Index / Try …
         T: Add 制約を成立させ、演算子の通過条件として機能
```

**階層化の理由**:

- **Layer 0 と 1 が演算子を「使える」ようにし**、Layer
  2 が演算子を「制約できる」ようにする。統合すると、`add` という名前のメソッドがすべて `+`
  で呼ばれることになり、RFC-011 の `T: Add` が演算子から乖離する。
- **Layer 1 を新規作成しない理由**：`method_bindings` はすでに `Type.method`
  キーで表引きしており（フィールド検索失敗後のフォールバック経路）、演算子も同じ経路を通せばよい。
- **Layer
  2 は通過条件**: 演算子通過前に**必ず**型が対応インターフェースを実装していることを確認する（`Equal`
  の自動導出例外については §Equal の自動導出 を参照。導出と登録は同一の判定基準）。

### 名前と登録: 二つの独立した経路

**演算子が照会するのは「インターフェース実装登録表」であり、通常の名前解決を経由しない。**

- 登録表はコアに帰属し、二つの登録を集約する。コアが基本型に対して行うデフォルト登録（`Add(Int, Int, Int)`
  など）と、ユーザーが型本体内に記述するインターフェースインスタンス化（`Add(Point, Point, Point)`）である。実装コードが物理的にどのモジュールにあっても、登録は同一の表に集約され、`+`
  / `==` / `[]` はこの表のみを参照する。
- ローカルモジュール内で `Add` という**同名のバインディング**（たとえば RFC-011
  §5.2 のペアノ型レベル加算
  `Add: (A: Type, B: Type) -> Type = match ...`）を定義しても、それは**名前検索経路**を通るだけで、そのモジュール内の
  `Add`
  という名前の解決にのみ影響し、**登録表には触れず、演算子の可用性にも影響しない**。同名異物、相互に遮蔽しない。

これは同時に「RFC-011 の型レベル `Add` と本 RFC のインターフェース `Add`
は衝突するか」に対する回答でもある。衝突しない。型レベル `Add`
は純粋に型レベルの計算（Zero/Succ は型であって値であり、`Zero + Succ(...)`
という値演算は決して存在しない）であり、値レベルの演算子インターフェースとは同名の二つの階層である。

### Layer 0: 固定マッピング表

| 演算子            | インターフェース                                      | メソッド           | 初回          |
| ----------------- | ----------------------------------------------------- | ------------------ | ------------- |
| `+`               | `Add`                                                 | `add`              | ✅            |
| `-`               | `Subtract`                                            | `subtract`         | ✅            |
| `*`               | `Multiply`                                            | `multiply`         | ✅            |
| `/`               | `Divide`                                              | `divide`           | ✅            |
| `%`               | `Modulo`                                              | `modulo`           | ✅            |
| `==` `!=`         | `Equal`                                               | `equal`            | ✅            |
| `[]`              | `Index`                                               | `index`            | ✅            |
| `?`               | `Try`（形状未定、未解決問題参照）                     | `residual`（暫定） | ❌ フェーズ 2 |
| `<` `<=` `>` `>=` | —（ネイティブ命令として保持）                         | —                  | ❌            |
| `and` `or`        | —（短絡評価は言語セマンティクス、オーバーロード不可） | —                  | ❌            |
| ビット演算 5 個   | —                                                     | —                  | ❌            |
| 単項 `-` `!`      | —                                                     | —                  | ❌            |

**インターフェース名は省略せずフルスペルを使用**（`Multiply` ではなく `Mul` ではなく `Multiply`）:
RFC-011 本文の `T: Add + Multiply + Zero` との一貫性を保ち、**承認済み RFC を変更しない**。

**`%` は `Modulo`
セマンティクス**（数学的剰余、結果の符号は除数に従う）を採用する。動機セクションで前述したように、現在の実装は公開済みドキュメントに違反しており（`reference/index.md`「乗除剰余」）、本条は欠陥修正として扱い、互換期間は設けない。

現状備考：`%` の型検査ホワイトリストは現状 Int/Float のみであり（`+`
の Int/Float/String/List ホワイトリストとは異なる）、付録 A.2 に実測記録がある。

### Layer 2: インターフェース定義

#### 算術インターフェース（三つの型パラメータ）

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

三つの型パラメータそれぞれの役割:

- `Self`: 左オペランドの型（レシーバ、`&Self`
  で借用、RFC-009 借用トークンおよび RFC-011a レシーバ規約を参照）；
- `R`: 右オペランドの型。**左右で異種を許可**；
- `O`: **結果型**、明示的に宣言。

**なぜ結果型を明示パラメータにする必要があるのか**（`-> Self` に固定せず）:

1. `Self` に固定すると `Add(Int, Float)` のメソッドは `Int` を返さなければならず、`1 + 2.5`
   を正しく表現できない；
2. 結果型を明示化することで、RFC-011 §8.3 の昇格型族
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }`
   と本 RFC のインターフェース登録が**同一表の二つのビュー**になる。コア登録
   `Add(Int, Float, Float)` 自体が `(Int, Float) => Float`
   の行であり、ユーザーの各インスタンス化はこの表への行追加となる；
3. `Index` インターフェースは元来三パラメータ `(Self, Key, Value)` で、戻り型 `Value`
   をパラメータとする。算術インターフェースに `O`
   を補うと、演算子インターフェースファミリーの形状が統一され、`Self` 固定のほうがむしろ異端となる。

**コアデフォルト登録**（ネイティブ命令経路、メソッド呼び出しを経由しない）:
`Add(Int, Int, Int)`、`Add(Int, Float, Float)`、
`Add(Float, Int, Float)`、`Add(Float, Float, Float)`、`Add(String, String, String)`（連結）、
`Add(List(T), List(T), List(T))`（要素連結）など、五つの算術インターフェースは基本型に対して同様。`1 + 2.5`
は現在のコンパイルエラー（ホワイトリストは両側同型を要求）から、`3.5: Float`
を返す合法な演算に変わる。

**制約構文糖衣**: `T: Add` ≜ すでに登録された
`Add(T, T, T)`。同型の自己合成で、結果もその型となる。RFC-011 の行列乗法例で `a * b + c`
は全体として型 `T` であり、まさにこの意味を要求している。`T: Equal` も同様に ≜ `Equal(T, T)`。

**異種例**。ベクトルのスケーリング:

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### 等価インターフェース（デフォルトで自動導出）

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` はデフォルトで自動導出**される。規則は五つ:

1. **デフォルト導出**: レコード型を定義する際、全フィールドが比較可能（基本型、`String`、またはそれ自身が比較可能なレコード/タプル/リスト、かつ
   `&mut` フィールドを含まない）であれば、コンパイラーが**フィールド単位比較**の `==`
   を自動生成し、ネイティブコード経路で実行される。ユーザーから見えるメソッドは生成されない。ユーザーが定義した型は自然に比較可能となり、何の儀式も必要ない。
2. **明示的オーバーライド**: 型本体に `Equal(Point, Point)` を記述し `Point.equal`
   メソッドを提供した場合、ユーザー版が用いられる（たとえば浮動小数点比較にトレランスを持たせるなど）、自動導出は実行されない。
3. **フィールドが比較不能な場合**: 自動導出は失敗し、`==`
   は使用不可となり、診断がどのフィールドが障害かを明示する。このときユーザーは依然として手動で
   `Equal` を記述しカスタム比較を定義できる（たとえば関数フィールドを持つ型を名前で比較するなど）。
4. **前提条件**: `&mut T`
   線形トークン（フィールド再帰）を含む型は比較に参加しない。線形トークンは一度読むと消費されるため、二つの値を同時に取り出して比較することができない。なお前提は「線形であること」であり「Dup であること」ではない点に注意。プリミティブ値型（Int/Float/Bool/Char）は RFC-011
   §2.4 により Dup に属さない（これらはコンパイラー組み込みの値コピーである）。Dup を前提とすると
   `Point { x: Float, y: Float }` を誤って拒否することになる。
5. **制約は同一判定基準**: `T: Equal` の解決と `==`
   の通過は同じ「登録照会または構造導出」ルールに従う。制約と演算子は常に同じ答えを出す。

**一貫性の根拠**: `(1, 2) == (1, 2)` と `[1] == [1]`
は今日もランタイムの要素ごと比較で実行されており（`executor.rs`
の比較ホワイトリストは Tuple/List/Array を含む）、レコード型のみが除外された唯一の複合型である。自動導出は新たな暗黙のデフォルトではなく、言語内部の既存挙動を最後のピースまで補完するものである。

**旧機構の退役**: `trait_data.rs` の `Equal`
の旧自動導出（署名のみで実装コードなし、消費箇所ゼロ）を停止する。`Equal`
のすべての判定（基本型のデフォルト登録、構造導出、明示的インスタンス化）はインターフェース登録表経由となる。旧トレイト表は Clone/Dup/Debug の既存責務を維持する（名前が演算子インターフェースと重複しないため、将来的な統合は別途議論する）。

#### インデックスインターフェース

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` は関連型メンバーではなく型パラメータ**:
RFC-011a の未解決問題は「関連型はジェネリクスパラメータで実装する」とすでに決着している（`Iterator: (Item: Type) -> Type`
が同型の先例）、`type` メンバー構文を導入する必要はない。

**所有権の説明**: `index` は `&Self` の借用から完全な `Value` を返す。標準ライブラリの
`list.get: (&Vec(A), Int) -> A` はすでにこの形であり、本インターフェースは**
std の現状と同待遇**である。ムーブセマンティクスの要素型について「借用から完全な値を取り出す」の正確なセマンティクスは、RFC-009 の全面施行時に統一して扱われ、本 RFC はこのために新たなルールを発明しない。

**複数位置インデックスはタプルのパッキング + オーバーロードで対応**し、可変長インターフェースは導入しない:

```yaoxiang
// 1 次元コンテナ
List(T) は Index(List(T), Int, T) をインスタンス化                → arr[0]

// 多次元コンテナ
Grid    は Index(Grid, Tuple(Int, Int), Float) をインスタンス化   → g[0, 1]
//                    └─ Key はタプル

// 二つのインスタンス化シグネチャが異なる → 共存可能
```

**同一型の同名インターフェースは複数のインスタンス化を許可**し、注入されたメソッドのシグネチャで区別し、RFC-011a のメソッドレベルオーバーロード規則に従って共存する。RFC-011a のオーバーロード規定はメソッドレベルまでしかないため、本条はその上にインスタンス化レベルの規則を補完する。同名インターフェースインスタンス化の共存可否は、展開後のメソッドシグネチャの衝突有無で決定する（衝突すれば E1097。フィールド/メソッド名前空間規則と同源）。

#### エラー伝播インターフェース（フェーズ 2、形状未定）

`?` のインターフェース化対象名 `Try` の**完全な形状は未定**であり、初回には含めない。理由:

1. `?` は実際には三つのことを行う。成否判定（現在はハードコードされた variant
   0 に依存）、成功時のペイロード取り出し、失敗時には値全体を現在の関数からそのまま返す。`residual: (self: &Self) -> E`
   という単一メソッドでは三番目のことの一部しかカバーせず、現時点で固定すれば将来ほぼ確実に書き直しになる；
2. フェーズ 2 はそもそも RFC-010（`Result` 値の構築）と RFC-039（バリアント分解）の着地に依存する；
3. 付随する**コンストラクタの固定問題**（`ok` / `err` / `some`
   がパーサーで認識される、言語仕様 §1.4.2）と `?` の型名固定は同一事象の二側面であり、「`Result`
   の std 帰属」は両側面を同時に解く必要があり、いずれもフェーズ 2 の範囲である。

### 使用例

#### ユーザー定義型: 算術と等価が即座に利用可能

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false —— Equal は自動導出、インスタンス化不要
    println(a == a)             # true
}
```

#### カスタム等価（自動導出のオーバーライド）

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# 浮動小数点比較にトレランスを持たせ、フィールド単位自動導出をオーバーライド
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### カスタムコンテナのインデックス化

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### ジェネリクス制約がついに履行可能

```yaoxiang
// RFC-011 の例がこれにより着地可能
// T: Add ≜ Add(T, T, T) が登録済み；T: Multiply ≜ Multiply(T, T, T) が登録済み
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

（RFC-011 の看板例 `T: Add + Multiply + Zero` における `Zero` / `One`
は本 RFC の範囲外。これらは定数メンバーであり演算子ではなく、「レシーバのないインターフェースメンバー」は RFC-011a に先例がないため、未解決問題を参照。）

### 構文変更

**新構文なし、新キーワードなし**。すべての能力は既存機構の組み合わせで構成される:

| 能力                           | 再利用する既存機構                                                  |
| ------------------------------ | ------------------------------------------------------------------- |
| インターフェース宣言           | RFC-011a フェーズ 1                                                 |
| インターフェースインスタンス化 | RFC-011a フェーズ 2（`Dog: { Animal(Dog) }`）                       |
| メソッド実装                   | RFC-011a フェーズ 3（外部宣言 `Point.add`）                         |
| 関連型                         | RFC-011 §3.1（インターフェース型パラメータ）                        |
| 複数位置インデックス           | 既存のタプルパッキング解析 + インスタンス化レベルオーバーロード規則 |
| 演算子優先順位                 | **言語固定**、ユーザーによるカスタムは不可                          |

## 詳細設計

### 型システムへの影響

**新規インターフェース**（Layer 2）: `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal`
`Index`（`Try` はフェーズ 2）。

**インターフェース実装登録表**: 演算子の判定中枢。コアのデフォルト登録（基本型）とユーザーのインスタンス化（`check_interface_instantiation`
が生成する `ImplementationProof`）を集約し、`+` / `==` / `[]` の通過検査と `T: Add`
制約解決（`bounds.rs` の
`check_trait_bounds`）は**同一表を照会**する。「制約は可と言い、演算子は不可と言う」隙間は存在しない。

**`Equal`
の構造導出**: 登録表の上に構造規則を重ねる（全フィールドが比較可能 ⇒ 比較可能）。基本型はコア登録が下支えし、再帰的に閉じる。旧
`trait_data.rs` の `Equal` 登録と旧自動導出は停止する。

**演算子照会と名前解決の分離**: `+`
などの演算子は登録表のみを照会し、通常の名前解決を経由しない。ローカル同名のバインディング（型レベル
`Add` ファミリーなど）は演算子に影響しない（§名前と登録 参照）。

**オーファンルール**: 演算子実装は**型の定義モジュール**にのみ記述できる。`Int`
の定義はコアにあるため、`Int` の登録はコアのみが記述可能；`Point`
の定義はユーザーモジュールにあるため、定義者だけが登録可能。すべての型が同一の規則に従い、組み込み型に特権はない。

### ランタイム挙動

**ランタイムオーバーヘッドゼロ**: 演算子はコンパイル時に呼び出し対象を決定する（静的ディスパッチ）。基本型（`Int`/`Float`/`String`/`List`）は**ネイティブ命令ファストパス**を維持し、インターフェースディスパッチを経由しない。自動導出された構造体の
`==` はネイティブのフィールド単位比較を生成する。`Any`（動的型）位置の `==` / `!=`
は既存のランタイム比較を維持する（RFC-036 テストフレームワーク `assert_eq`
はこの挙動に依存しており、影響を受けない）。

**`%` セマンティクス修正**: `-7 % 3` は `-1`（切り捨て余り）から
`2`（数学的剰余）へ。インタープリター（`checked_rem`）、定数畳み込み（`a % b`）、バイトコード（`I64_REM`）の三箇所を同期して修正する。

### コンパイラー変更

| コンポーネント                       | 変更内容                                                                                                                                                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `typecheck/inference/expressions.rs` | `infer_binary` のホワイトリストを「ネイティブファストパス + 登録表照会」の二系統に；`Expr::Index` のホワイトリストにインターフェース照会分岐を追加                                                                   |
| `typecheck/inference/bounds.rs`      | `check_trait_bounds` は演算子インターフェース名についてインターフェース登録表を照会（`Equal` は構造導出を含む）                                                                                                      |
| `typecheck/checker.rs`               | `Equal` の構造導出を新規追加（レコード定義後）；インスタンス化レベルオーバーロード規則（同名インターフェースの複数インスタンス化をメソッドシグネチャで共存）                                                         |
| `middle/core/ir_gen.rs`              | `Expr::Index` にメソッド呼び出しディスパッチ分岐を追加；明示的 `equal` のない構造体の `==` はネイティブのフィールド単位比較を生成；`Mod` 命令を数学的剰余に変更                                                      |
| インターフェース登録表（新規）       | Layer 0 マッピング表定数 + 演算子→インターフェース照会関数 + コアデフォルト登録（`Int`/`Float`/`String`/`List` など）                                                                                                |
| `trait_data.rs`                      | `Equal` 登録と旧自動導出を停止（`Clone`/`Dup`/`Debug` は現状維持）                                                                                                                                                   |
| 診断                                 | `Equal` 前提（線形トークン）不充足は `E1101`（型がインターフェースを実装していない）ファミリーを再利用；`E1081`/`E1082` の文言から "Result" の文字を削除（フェーズ 2 で `Try` 着地後、RFC-013 フローに従い三者同期） |

### 後方互換性

**基本型の演算は不変**: `1 + 2`、`"a" + "b"`、`[1] + [2]`、`1 < 2`
はすべてネイティブ経路を維持し、挙動と性能は変わらない。

**`1 + 2.5` はコンパイルエラーから合法へ**: コア登録 `Add(Int, Float, Float)`
後、これまでホワイトリストに拒否されていた混合算術が利用可能となり、`Float`
を返す。これは新規能力であり、既存コードへの影響はない。

**`%` セマンティクス修正**: `-7 % 3` は `-1` から `2`
へ。**欠陥修正**と位置付ける（ドキュメントはとっくに剰余を約束している、動機 §5 参照）、互換期間は設けない。既存テストコーパスに負数
`%` 依存の用例がないことは確認済み。

**構造体の `==` はランタイムエラーから利用可能へ**: これまで `Struct == Struct`
は一律 E6007 ランタイムエラーだったが、配線後は自動導出により即座に利用可能。悪い状態から良い状態への変化であり、既存の合法コードへの影響はない。

**`Any` の `==` は影響なし**: 動的型位置はランタイム比較を維持する（RFC-036 の `assert_eq`
アサーションファミリーがこれに依存しており、これまでは利用可、以降も利用可）。

**`f[0]` 位置バインディングは不変**: `distance[0]`
は RFC-004 のコンパイラー組み込み能力であり、**`Index`
インターフェースを経由せず**、影響を受けない。

**`?` は既存コードに対して透過的**（フェーズ 2）: `Result` に `Try` インスタンス化を補えば、既存の
`?` 使用法の挙動は完全に同一。

## トレードオフ

### 利点

- **RFC-011 の演算子制約を履行**: `T: Add + Multiply`
  は紙上（実際にはコンパイルエラー）から実動可能へ、承認済み RFC 本文には触れない
- **`Result` の core バインディングを解除**（フェーズ 2）: `?`
  とコンストラクタがインターフェース化された後、`Result`
  は std に帰属可能となり、RFC-013 の既存位置付けと一致
- **実測上の欠陥を修正**: `Point == Point` が即座に利用可能となり、`list.contains`
  の構造体非対応も連鎖的に修正
- **新構文ゼロ**: すべて RFC-011a の既存機構を再利用し、パーサー構文規則には触れない
- **ランタイムオーバーヘッドゼロ**: 静的ディスパッチ + 基本型のネイティブファストパス
- **ユーザー定義コンテナが利用可能**: `Box(T)[0]` が「一律エラー」から利用可能へ
- **言語内部の一貫性**:
  Tuple/List はすでに要素単位比較済みで、レコード型が追いつく；算術インターフェースの三パラメータと Index の形状が統一；RFC-011
  §8.3 の昇格表とインターフェース登録表が合一

### 欠点

- **`Equal`
  自動導出は暗黙のデフォルト**: 将来「レコードはデフォルトで比較可能」という立場を撤回すれば破壊的変更になる。この立場は受け入れる。タプル/リストの既存挙動と一致し、また明示的インスタンス化で常にオーバーライド可能
- **`Equal` の前提が線形トークンを含む型を拒否する**: `&mut` フィールドを含む型は `==`
  を使用できない。意味的には正しいが代償であり、明確な診断（どのフィールドが該当するか）が必要
- **インターフェースインスタンス化は明示的コスト**: 算術演算子はそれぞれインスタンス化の一行とメソッド一つが必要（`Equal`
  は自動導出のため免除）。RFC-011a の構文は暗黙的導出を許さない（引き換えに `Self`
  型パラメータに魔法がない）
- **`%` セマンティクス修正は挙動変更**: 欠陥修正と位置付けるが、移行ガイドでの明記が必要

## 代替案

### 案 A: Layer 1 のみ（メソッド名によるディスパッチ）、インターフェース層なし

`+` は `add` という名前のメソッドが存在するかどうかのみを照会し、`Add`
インターフェースの実装を要求しない。

**却下理由**: RFC-011 の `T: Add`
制約が演算子から乖離する。制約はインターフェースを照会し、演算子はメソッド名を照会するため、矛盾する答えを返す可能性がある。また「`+`
を非加算型に使用しようとした場合」のコンパイル時診断を正確に提供できない。

### 案 B: `?` 問題を解決するために `Ok(x)` / `Some(x)` コンストラクタ構文を導入

`?` をインターフェース化せず、和型にコンストラクタ構文を追加する。

**却下理由**:
RFC-010（承認済み）と衝突する。RFC-010 は「和型の表現に統一してレコード型を使用し、**二系統の構文は不要**」と明確に規定し、`|`
構文を明示的に廃止している。コンストラクタの導入は第二の表現系の導入になる。また `?`
のみを解決し、`Point == Point` やカスタムコンテナのインデックス化には対応しない。

### 案 C: 比較演算子も初回にインターフェース化（`Ordering` の導入）

`<` `<=` `>` `>=` を `Compare` インターフェースで実装し、3 値の `Ordering` を返す。

**却下理由**: `<`
は YaoXiang においてすでに**第一級の IR 命令**（`Instruction::Lt/Le/Gt/Ge`）であり、インターフェース化すると基本型に迂回を強制する。さらに
`Ordering` を導入すると、`Ordering` 自身の比較/ソート、浮動小数点 `NaN` の `PartialOrd` と `Ord`
の区別など、一連の派生問題を引き起こす。独立した RFC のスコープである。現在実測で露出しているニーズ（`Point == Point`、`list.contains`）には
**`Equal` のみ**で十分。

### 案 D: 演算子名を省略形で命名（`Add` インターフェースのメソッドは `add`、インターフェースは `Mul`）

**却下理由**: RFC-011 本文はすでに `T: Add + Multiply + Zero`
と記述しており、省略形を採用するには承認済み RFC を変更する必要がある。

### 案 E: `Equal` は明示的インスタンス化のみ、自動導出なし

**却下理由**: ユーザー定義型が `==` を使用できないという体験は受け入れがたい。さらに
`(1, 2) == (1, 2)` と `[1] == [1]`
は今日すでに要素単位比較が可能で、レコード型のみが除外されており、元来一貫していない。明示的インスタンス化はオーバーライド手段として保持し、カスタムニーズに対応する。

### 案 F: 算術インターフェースの戻り型を `-> Self` に固定

**却下理由**: `Add(Int, Float)` のメソッドは `Int` を返すことを強制され、`1 + 2.5`
を正しく表現できない；ベクトルスケーリング `Multiply(Point, Float)` も同様に記述不能。RFC-011
§8.3 の昇格型族 `(Int, Float) => Float` に着地する場所が失われる。三パラメータ `(Self, R, O)` は
`Index(Key, Value)` と形状が統一される。

## 実装戦略

### 依存関係

| 依存                                       | 状態        | 本 RFC への影響                                                 |
| ------------------------------------------ | ----------- | --------------------------------------------------------------- |
| RFC-011a インターフェース機構 フェーズ 1–3 | ✅ 着地済み | Layer 2 の地基（実測で実行可能確認済み）                        |
| RFC-010 レコード構築経路                   | ❌ 未着地   | **フェーズ 2**: `?` の構築側 + コンストラクタパーサー特例の退役 |
| RFC-039 バリアント分解                     | ❌ 紙面     | **フェーズ 2**: `Result.residual` の `match` 記述、網羅性       |
| RFC-009 線形トークン推論                   | 部分        | `Equal` の前提制約検査                                          |

### 段階分け

**インターフェース依存**（設計上の制約であり、スケジュールではない）に基づき二組に分ける:

**フェーズ 1 — RFC-010/039 に依存しない**:

- Layer 0 マッピング表 + インターフェース実装登録表 + Layer 1 ディスパッチ配線
- `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
  の七つのインターフェース（三型パラメータ形態）
- `Equal` 自動導出 + 線形トークン前提制約 + 制約解決の登録表経由切替
- `%` セマンティクス修正（インタープリター/定数畳み込み/バイトコード三箇所）
- `Any` 位置の `==` はランタイム比較を維持
- **効果**: `Point + Point`、`Point == Point`（儀式不要）、`Box(T)[0]`、`1 + 2.5`、`T: Add`
  制約がすべて利用可能

**フェーズ 2 — RFC-010 / RFC-039 に依存、開始前に `Try` 形状の確定が必要**:

- `Try` インターフェース形状の確定（未解決問題参照）
- `?`
  のインターフェース化 + コンストラクタ（`ok`/`err`/`some`）パーサー特例の退役、RFC-010 のレコード構築経路への切替
- `Result` を core から std へ移行（RFC-013 の既存位置付けに基づく）

### リスク

| リスク                                           | 緩和策                                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `%` セマンティクス変更が既存ユーザーコードに影響 | 欠陥修正と位置付け + テストコーパスに負数 `%` 依存の用例がないことを確認済み                 |
| `Equal` 自動導出の暗黙デフォルトを将来撤回困難   | 立場確定: タプル/リストの既存挙動と一致、明示的インスタンス化でオーバーライド可能            |
| 基本型の二経路（ネイティブ + 登録）の不整合      | ゲート: コア登録のセマンティクスはネイティブ命令と一致しなければならない（同一表の二ビュー） |
| 登録表照会がコンパイルを低速化                   | テーブルは型名でインデックス + インスタンス化結果キャッシュ（RFC-011a proof を再利用）       |
| インスタンス化レベルオーバーロードが曖昧性を導入 | メソッドレベルオーバーロードと同規則: シグネチャ衝突は E1097                                 |

## 他の RFC との協調

本 RFC の位置付けは**消費側の要求提起者**であり、以下の一貫性確保のため関連 RFC を同期更新する必要がある（改訂権限を取得済み）:

| RFC                     | 更新内容                                                                                                                                                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011**（承認済み） | §制約箇所に `Add` / `Multiply` が 011b で定義・着地されることを注記（`T: Add` ≜ `Add(T, T, T)`）；`Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` を宙に浮いた制約名として標識（後の RFC を待つ）；§8.3 昇格型族がインターフェース登録表と合一することを注記 |
| **RFC-010**（承認済み） | 「レコードフィールドがそのままコンストラクタ」の着地要件を明確化。フェーズ 2 のコンストラクタパーサー特例退役の前提条件                                                                                                                                     |
| **RFC-039**（ドラフト） | 構築と分解はペアでなければならない；網羅性判定は `Result` の core/std 帰属に依存しない（011b フェーズ 2 で移行）                                                                                                                                            |
| **RFC-009**（承認済み） | §型属性箇所に相互参照: `Equal` の前提は「`&mut` 線形トークンを含まない」（Dup ではない）                                                                                                                                                                    |
| **RFC-013**（承認済み） | フェーズ 2 着地時: `E1081` / `E1082` 文言から "Result" を削除；`Equal` 前提診断は `E1101` ファミリーを再利用。RFC-013 フローに従い三者同期（codes/*.rs ↔ locales ↔ コード表）                                                                               |
| **RFC-018**（承認済み） | `%` が数学的剰余に変更されると、`Mod → srem/urem` マッピング表が無効になる。`srem` + 符号修正（または `sdiv`+`mul`+`sub` の合成）に変更し、「剰余/余り」用語の混用を是正                                                                                    |
| **RFC-036**（承認済み） | 変更不要。関係性を明記: `Any` 位置の `==` はランタイム比較を維持、`assert_eq` アサーションファミリーは影響を受けない                                                                                                                                        |

> `Result` の std 帰属の根拠: RFC-013 はすでに「std ライブラリ
> `Result(T, Error)`」と位置付けており、RFC-014 の階層化は std をコアソースに含めている。本 RFC のフェーズ 2 はその着地経路の一つであり、他の番号は引用しない。

## 付録A: 調査エビデンス

以下の実測はすべて **0.8.0**（`target/debug/yaoxiang-rs.exe`）で再現確認済み。

### A.1 インターフェース機構の可用性（本 RFC の地基）

| 能力                                                                               | 実測                                                         |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| インターフェース宣言 `Animal: (Self: Type) -> Type = {...}`                        | ✅ 定義可能                                                  |
| インターフェースインスタンス化 + 外部メソッド `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ 実行可能、出力正常（`tests/rfc011a.rs` に単体テストあり） |
| インターフェースインスタンス化 + **内部**メソッド宣言                              | ❌ `E1097`（フィールドとメソッドの名前空間衝突）             |
| メソッドディスパッチ `d.speak()`                                                   | ✅ 実行可能                                                  |

**注**: `E1097`
は、演算子メソッドが**外部宣言**形態（`Point.add: (self: &Point, ...)`）でなければならないことを意味する。RFC-011a の例と一致する。`method_bindings`
の登録は `environment.rs`（`add_method_binding`）で行われ、照会は `expressions.rs`
の呼び出しターゲット解析とフィールド検索失敗フォールバック経路で行われる。

### A.2 演算子の現状

| 式                                  | 現状                                                                                         |
| ----------------------------------- | -------------------------------------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]` | ✅ ハードコードホワイトリスト（Int/Float/String/List、**両側同型を要求**）                   |
| `1 + 2.5`（Int + Float）            | ❌ コンパイルエラー（ホワイトリストが両側同型を要求）                                        |
| `-7 % 3`                            | `-1`（切り捨て余り；`%` のホワイトリストは Int/Float のみで `+` のホワイトリストとは異なる） |
| `Point(1,2) == Point(1,2)`          | ❌ `E6007`（Struct に対する Eq のランタイム失敗）                                            |
| `(1,2) == (1,2)` / `[1] == [1]`     | ✅ ランタイムの要素ごと比較（Struct のみが穴）                                               |
| Any 位置の `a == b`（`assert_eq`）  | ✅ ランタイム比較（RFC-036 で実証済み）                                                      |
| `f[0]`（関数位置バインディング）    | ⚠️ バインディング宣言内でのみ有効、式として使用すると `E3006`                                |
| `arr[0, 1]`（複数位置）             | ✅ タプルパッキングで `list([1, 2])`                                                         |

### A.3 `?` とコンストラクタのハードコード位置

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

コンストラクタ側: `ok(T)` / `err(E)` / `some(T)` はパーサーで認識される（言語仕様 `syntax.md`
§1.4.2）； `std/result.rs` の `is_ok` / `unwrap` などは `variant_id 0/1`
パターンマッチに従う。「`Result`
の std 帰属」は両側（`?` + コンストラクタ）の同時解放が必要で、ともにフェーズ 2 に帰属する。

## 付録B: 設計決定記録

| 決定                                       | 決定内容                                                                          | 理由                                                                                                                  | 日付       |
| ------------------------------------------ | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------- |
| アーキテクチャ                             | 三層分離（マッピング表 / ディスパッチ基層 / インターフェース契約）                | 統合すると RFC-011 制約が演算子から乖離する                                                                           | 2026-09-15 |
| 演算子の通過条件                           | インターフェース実装が必須（Layer 2 が通過条件）                                  | `T: Add` と `+` の厳密一致を保証                                                                                      | 2026-09-15 |
| インターフェース命名                       | フルスペル（`Mul` ではなく `Multiply`）                                           | RFC-011 承認済み本文を変更しない                                                                                      | 2026-09-15 |
| `%` インターフェース名                     | `Modulo`（数学的剰余）                                                            | 名前でセマンティクスを固定                                                                                            | 2026-09-15 |
| 比較演算子                                 | 初回はインターフェース化**しない**、ネイティブ IR 命令を維持                      | すでに第一級命令；`Ordering` が一連の派生問題を引き起こす                                                             | 2026-09-15 |
| `Ordering`                                 | 初回導入しない                                                                    | 実ニーズの駆動なし、独立 RFC のスコープ                                                                               | 2026-09-15 |
| 関連型                                     | インターフェース型パラメータで実装、`type` メンバー構文は導入しない               | RFC-011a がこの方式を確定済み（`Iterator: (Item: Type)`）                                                             | 2026-09-15 |
| メソッドバインディングとインデックスの統一 | 概念は統一、インターフェースはコンテナインデックスのみを担当                      | 位置バインディングのキーはコンパイル時定数、結果型に型族評価が必要、ユーザー実装不可                                  | 2026-09-15 |
| 複数位置インデックス                       | タプルパッキング + Key 型によるオーバーロード、可変長インターフェースは導入しない | パーサーを変更しない                                                                                                  | 2026-09-15 |
| ビット演算 / 単項演算子                    | 初回は対象外                                                                      | カスタム型での使用は稀、YAGNI                                                                                         | 2026-09-15 |
| 算術インターフェース形状                   | 三型パラメータ `(Self, R, O)`；`T: Add` ≜ `Add(T, T, T)`                          | 結果型を明示化: `1 + 2.5`、スケーリングを表現可能；RFC-011 §8.3 昇格表と登録表が合一；`Index(Key, Value)` と形状統一  | 2026-09-22 |
| `Equal` 導出                               | デフォルト自動導出 + 明示的インスタンス化でオーバーライド；制約解決も同一判定基準 | 「ユーザー定義型が == を使用できない」は受け入れ不可；タプル/リストはすでに要素単位比較済みで、レコードのみが穴だった | 2026-09-22 |
| `Equal` 前提制約                           | 「`&mut` 線形トークンを含まない」、**Dup ではない**                               | RFC-011 §2.4 はプリミティブが Dup に属さないと明記、Dup を前提とすると `Point{Float,Float}` を誤って拒否する          | 2026-09-22 |
| 名前と登録の分離                           | 演算子はインターフェース実装登録表のみを照会、名前解決を経由しない                | ローカル同名のバインディング（型レベル `Add` ファミリーなど）が演算子と干渉しない；RFC-011 §5.2 例に変更不要          | 2026-09-22 |
| オーファンルール                           | 実装は型の定義モジュールに従う                                                    | すべての型が平等に扱われ、組み込み型に特権はない                                                                      | 2026-09-22 |
| `Any` の `==`                              | ランタイム比較を維持、登録表は照会しない                                          | RFC-036 `assert_eq` アサーションファミリーがすでにこの挙動に依存                                                      | 2026-09-22 |
| `Try` 形状                                 | フェーズ 2 開始前に確定を保留                                                     | `?` は三つのことを必要とし、単一メソッド `residual` では不十分；コンストラクタパーサー特例も併合して取り扱う          | 2026-09-22 |
| `%` セマンティクス位置付け                 | 欠陥修正（ドキュメントが剰余を約束済み）、互換期間なし                            | `reference/index.md`「乗除剰余」が先行証拠                                                                            | 2026-09-22 |
| `Result` の std 帰属の根拠                 | RFC-013 の既存位置付けを引用、存在しない番号は引用しない                          | RFC-013 はすでに「std ライブラリ `Result(T, Error)`」と記述                                                           | 2026-09-22 |

## 付録C: 用語集

| 用語                       | 定義                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Layer 0                    | 演算子 → メソッド名の固定マッピング表、言語レベル定数、ユーザーは変更不可                                                 |
| Layer 1                    | `Type.method` キーで表引きし呼び出すディスパッチ基層                                                                      |
| Layer 2                    | インターフェース契約層、ジェネリクス制約の根拠を提供し、同時に演算子の通過条件として機能                                  |
| インターフェース実装登録表 | コアのデフォルト登録とユーザーのインスタンス化を集約する実装総表；演算子照会と制約解決の唯一の判定基準、名前解決と独立    |
| ネイティブファストパス     | 基本型が維持するハードコード演算経路、インターフェースディスパッチを経由しない                                            |
| 位置バインディング         | RFC-004 の `f[0]` 構文、関数パラメータ位置をメソッドにバインドするコンパイル時挙動                                        |
| 自動導出                   | コンパイラーが全フィールド比較可能なレコードに対して生成するフィールド単位 `==`、明示的インスタンス化でオーバーライド可能 |
