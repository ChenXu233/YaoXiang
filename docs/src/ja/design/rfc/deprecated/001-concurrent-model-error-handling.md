# RFC-001：並作モデルとエラーハンドリングシステム

## 設計の由来

| ドキュメント                                               | 関係                 |
| ---------------------------------------------------------- | -------------------- |
| async-whitepaper                                           | 設計の源、理論的基盤 |
| [language-spec](../../../reference/language-spec/index.md) | 仕様目標             |

## 概要

YaoXiang の並作モデルを提案する：同期構文でロジックを記述し、ランタイムで自動的に並列実行する。コア機構：三層並行アーキテクチャ +
DAG 依存解析 + Result タイプシステム。

## クイック選択

| シナリオ           | 書き方                 | 説明                          |
| ------------------ | ---------------------- | ----------------------------- |
| 自動並列           | 注釈なし（デフォルト） | 並列度を最大化                |
| 同期待機           | `@eager`               | 依存関係の完了を待つ          |
| 完全シーケンシャル | `@block`               | 並行性なし、デバッグ用        |
| 局所的並列         | `spawn`                | @block スコープ内での並列実行 |

## 動機

現在の主流言語の並行モデルには明らかな欠陥がある：

| 言語       | 並行モデル          | 問題                         |
| ---------- | ------------------- | ---------------------------- |
| Rust       | async/await + tokio | 非同期の感染、学習曲線が急峻 |
| Go         | goroutine           | タイプセーフティなし         |
| Python     | asyncio             | GIL 制限                     |
| JavaScript | Promise/async       | コールバックが複雑           |

### 核心的矛盾

1. **透明性 vs 制御性**：完全透明だが制御不能 vs 完全制御可能だが不透明
2. **並行性 vs デバッグ容易性**：並行プログラムはデバッグ困難 vs デバッグ可能なプログラムは並列化が困難

## 提案

### 1. 並作モデル：三層並行アーキテクチャ

> **説明**：L1/L2/L3 はメンタルモデルであり、異なるシナリオの理解を助ける。実際の実装は一組の機構のみ：自動 DAG 解析 + 注釈による制御。

| 階層   | メンタルモデル  | 構文                   | 実行方式                                | 並列度  |
| ------ | --------------- | ---------------------- | --------------------------------------- | ------- |
| **L1** | 並行性を禁止    | `@block`               | 純粋なシーケンシャル実行                | ❌ なし |
| **L2** | @block 内の並列 | `spawn`                | @block スコープ内での制御可能な並列実行 | ⚠️ 部分 |
| **L3** | 完全並列        | デフォルト（注釈なし） | 自動 DAG 解析                           | ✅ 完全 |

#### L1: @block 同期モード

```yaoxiang
main: () -> Void @block = {
    data1 = fetch_sync("api1")
    data2 = fetch_sync("api2")
    process(data1, data2)    # 厳密な順序、並行性なし
}
```

#### L2: @block 内の制御可能な並列実行

```yaoxiang
# spawn は @block 関数内でのみ使用可能
main: () -> Void @block = {
    spawn { data1 = fetch_data("api1") }
    spawn { data2 = fetch_data("api2") }
    # すべての spawn の完了を待つ（標準ライブラリで制御）
    process(data1, data2)
}
```

#### L3: 完全透明（デフォルト）

```yaoxiang
# 注釈は不要、コンパイラが自動的に DAG を解析する
heavy_calc: (n: Int) -> Int = fibonacci(n)

auto_parallel: (n: Int) -> Int = {
    a = heavy_calc(1)    # 自動並列
    b = heavy_calc(2)    # 自動並列
    c = heavy_calc(3)    # 自動並列
    a + b + c            # 値が必要になったらすべての結果を待つ
}
```

### 2. 注釈の完全比較

| 次元         | デフォルト（注釈なし） | `@eager`           | `@block`             | `spawn`             |
| ------------ | ---------------------- | ------------------ | -------------------- | ------------------- |
| **実行方式** | 自動 DAG 解析          | 同期的に依存を待つ | 純粋なシーケンシャル | @block 内の並列実行 |
| **並列度**   | ✅ 完全                | ⚠️ 依存順序に従う  | ❌ なし              | ⚠️ 部分             |
| **DAG 構築** | ✅                     | ✅                 | ❌                   | ✅                  |

**選択ガイド**：

- 最大並列 → 注釈なし（デフォルト）
- 順序だった副作用が必要 → `@eager`
- デバッグ/初心者/クリティカルコード → `@block`
- @block 内で並列性が必要 → `spawn`

```yaoxiang
# デフォルト：並列度の最大化
calc_all: () -> Int = {
    a = heavy_calc(1)    # 自動並列
    b = heavy_calc(2)    # 自動並列
    a + b
}

# @eager：同期待機
calc_seq: () -> Int @eager = {
    a = heavy_calc(1)    # 同期実行
    b = heavy_calc(2)    # 同期実行
    a + b
}

# @block：純粋なシーケンシャル
calc_simple: () -> Int @block = {
    a = heavy_calc(1)    # 強制的に同期
    b = heavy_calc(2)    # 同期
    a + b
}

# spawn：@block 内の並列実行
calc_mixed: () -> Int @block = {
    spawn { heavy_calc(1) }
    spawn { heavy_calc(2) }
    heavy_calc(3)        # 同期
}
```

### 3. DAG 依存解析

#### 3.1 核心的原則：ボトムアップ実行

```
ユーザーコード（同期構文）：
    a = fetch(url0)
    b = fetch(url1)
    print(a)

コンパイル時解析（ボトムアップ）：
    print(a) は a を必要とする → fetch(url0) に依存
    fetch(url1) は誰も必要としない → 孤児 DAG

ランタイムスケジューリング（リーフから開始）：
    fetch(url0) → print(a)    ← 依存チェーン、順次
    fetch(url1)                ← 孤児、独立して並列
```

**重要な洞察**：「トップダウン」で Future を生成するのではなく、「ボトムアップ」で結果から逆向きに依存関係を解析する。

#### 3.2 孤児 DAG：独立した並列実行

```
メインフロー：fetch(url0) → process → print
孤児：  fetch(url1)  ← 結果が必要ない、独立して並列

スケジューラ：メインフローは依存チェーンに沿って実行、孤児は別のコアで並列実行
```

#### 3.3 リソースタイプと副作用

**核心的な考え方**：リソース操作はタイプマーカー経由で行い、DAG が自動的に依存関係を構築する。同一リソースは自動的にシリアライズされ、異なるリソースは自動的に並列化される。

**リソースタイプの境界——明確な定義**：

リソースタイプはコンパイラに組み込まれたマーカー付きタイプである。以下のタイプがコンパイラによりリソースとして識別される：

| リソースタイプ | 説明                 | コンパイラの動作                            |
| -------------- | -------------------- | ------------------------------------------- |
| `FilePath`     | ファイルシステムパス | 同一パスの操作は自動的にシリアライズ        |
| `HttpUrl`      | HTTP エンドポイント  | 同一 URL の操作は自動的にシリアライズ       |
| `DBUrl`        | データベース接続     | 同一接続の操作は自動的にシリアライズ        |
| `Console`      | 標準出力             | すべての Console 操作は自動的にシリアライズ |

ユーザー定義のリソースタイプは明示的にマークする必要がある：

```yaoxiang
Database: Resource              # 明示的にリソースタイプとしてマーク
query: (Database, String) -> Result(Row, Error)
# 引数 Database は Resource、自動的にリソース操作として識別
```

Resource マーカーなしのタイプは、コンパイラによりリソース依存として追跡されない。

**使用ルール**：

- 変数経由でリソースハンドルを渡し、DAG が自動的に順序を管理する
- リテラルで直接同一リソースを使用するのはユーザーの設計上の問題であり、言語の責任ではない

```yaoxiang
# ✅ 正しい：変数渡し、DAG が自動的にシリアライズ
filename: String = "data.txt"
File.write(filename, x)
File.write(filename, y)    # DAG がシリアライズ

# ⚠️ ユーザーの責任：リテラル
File.write("data.txt", x)
File.write("data.txt", y)  # 並列化の可能性がある、ユーザーが責任を持つ
```

#### 3.4 無限ループの処理

```
1 つのループ → 直接同期実行、ゼロスケジューリングオーバーヘッド
複数のループ → スケジューラがスライス切り替え、真の並列実行
```

### 4. Result タイプとエラーハンドリング

```yaoxiang
Result: (T: Type, E: Type) -> Type = { ok: (T) -> Self, err: (E) -> Self }

# ? 演算子で透過的に伝播
process: () -> Result(Data, Error) = {
    data = fetch_data()?
    processed = transform(data)?
    save(processed)?
}
```

### 5. DAG ノード設計

```rust
enum NodeKind {
    Task,      // タスクノード
    Value,     // 値ノード
    Control,   // 制御フローノード
}

struct Node {
    id: NodeId,
    kind: NodeKind,
    inputs: Vec<ValueNodeId>,   // 入力依存
    outputs: Vec<ValueNodeId>,  // 出力値
    span: Span,                 // ソースコードの位置
}
```

| エッジタイプ | 記号 | セマンティクス                 |
| ------------ | ---- | ------------------------------ |
| DataEdge     | →    | データ依存（値の流れ）         |
| ControlEdge  | ●    | 制御依存（シーケンシャル実行） |
| SpawnEdge    | ◎    | 並列入口（並列化の起点）       |

### 6. タイプシステム

```
Send → スレッド間を安全に転送可能
Sync → スレッド間を安全に共有可能
Arc(T) は Send + Sync を実装（スレッドセーフ参照カウント）
```

## トレードオフ

### 利点

1. **段階的な採用**：三層モデルが異なるスキルレベルに適応する
2. **自然な構文**：同期コードで並列性能を獲得
3. **コンパイル時の安全性**：Send/Sync 制約によりデータ競合を除去
4. **デバッグ可能性**：エラーグラフが明確なエラー伝播ビューを提供

### 欠点

1. **学習曲線**：DAG 依存の概念を理解する必要がある
2. **コンパイル時間**：プログラム全体の DAG 解析は遅くなる可能性がある
3. **ツールチェーンの複雑さ**：全新的デバッグおよび可視化ツールが必要

## 代替案

| 案                                | 採用しない理由                                 |
| --------------------------------- | ---------------------------------------------- |
| 明示的な async/await のみサポート | 透過的な並列化が実現不可能                     |
| 完全透過的並列化のみサポート      | ユーザーが制御権を失う                         |
| Go 風 goroutine                   | タイプセーフティなし、コンパイル時チェック不可 |
| L1 モードのみ                     | 並作モデルの核心的価値を放棄                   |

## 実装戦略

### 段階区分

1. **段階 1 (v0.1)**：@block 同期モード、基本タイプ
2. **段階 2 (v0.2)**：FlowScheduler スケジューラ
3. **段階 3 (v0.3)**：spawn ブロック、明示的並列実行
4. **段階 4 (v0.5)**：L3 完全透明、DAG 自動解析
5. **段階 5 (v0.6)**：エラーグラフ、グラフデバッガ
6. **段階 6 (v1.0)**：プロダクション利用可能な最適化

### 依存関係

- RFC-001 は外部依存なし（基礎コア）
- RFC-008（Runtime 並行モデル）→ 設計完了
- RFC-011（ジェネリクスシステム）→ 設計完了

### リスク

1. **DAG 解析性能**：プログラム全体の解析は O(n²) になる可能性があり、最適化が必要
2. **ツールチェーンの欠如**：デバッガをゼロから開発する必要がある
3. **ユーザー受容度**：透過的な並列化には良好なドキュメントが必要
