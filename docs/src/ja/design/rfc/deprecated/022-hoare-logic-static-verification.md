# RFC 022: ホーア論理静的検証サポート（仕様コメントと仕様型）[廃止]

> **参考**:
>
> - [RFC-010: 統一型構文](../accepted/010-unified-type-syntax.md)
> - [RFC-011: ジェネリクスシステム設計](../accepted/011-generic-type-system.md)
> - [RFC-009: 所有権モデル](../accepted/009-ownership-model.md)

## 摘要

本文提出为 YaoXiang 语言引入一种**霍尔逻辑静的検証機構**，允许开发者在注释中以 `//!` 或
`/*! ... !*/` の形式で前置条件、事後条件、ループ不変式を記述する。Debug
Build時に强制的な静的検証を行い、検証通过后才能进行Release Build；Release
Build時に仕様コメントを無視（ゼロオーバーヘッド）し、検証キャッシュをクリアする。仕様自体は型システムの一部とみなされ、「仕様型」（如
`Requires(P)`、`Ensures(P)`）を形成し、用户扩展可能。该设计旨在保持语言简洁的同时，为关键代码提供高可靠性保障，且与YaoXiang的统一类型模型完美融合。

## 動機

### なぜこの機能/変更が必要なのか？

YaoXiang は所有権モデル（RFC-009）と并发モデル（RFC-001）を 통해メモリ安全とスレッド安全を保証していますが、論理正しさは依然としてテストに依存しています。システムプログラミング、安全critical分野（航空宇宙、金融、OSカーネルなど）では、論理エラーが catastrophic な的后果を引き起こす可能性があります。既存の方案（Rustの借用チェックなど）は这类エラーを検出できません。ホーア論理は数学的证明手段を提供しますが、従来の形式検証ツールは独立した仕様言語と複雑な学習曲線を必要とすることが多いです。

### 現在の問題

- 論理正しさはテスト 통해서のみ検証可能、compile時に保証できない
-  критических システムコード缺乏形式検証手段
- 既存の形式検証ツールは学習曲線が急で支流プログラミング言語と分離している

## 提案

### 核心設計

我们的目标是设计一种**轻量、与语言一体**的静的検証方案：

- **Debug Build 必検証**：开发者在需要高可靠性的模块中编写仕様、Debug
  Build時に强制検証通过后才能进行Release Build
- **構文が elegante**：使用 `//!` コメント、新キーワードを導入せず、エディタが構文強調可能
- **型システムとの融合**：仕様が型的一部分になる、型チェックに参加可能、用户自定义仕様型をサポート
- **証明可能とテスト可能**：静的証明，也可降级为运行时assertion，便于渐进式采用

### 1. 仕様コメント構文

関数本体またはループ本体の先頭で、`//!`（単一行）または `/*! ... !*/`（複数行）を使用して仕様を記述します。

#### 1.1 統一仕様構文

仕様はYaoXiangの統一された `name: Type = expression` 構文モデルを採用しており、型システムと完全に融合しています：

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0
    //! ensures: GreaterOrEqual(result, arr[0..n])
    //! ensures: ExistsMax(result, arr[0..n])
    // 実装...
}
```

- 仕様本质是一个**型宣言**、右侧はブール式
- 左侧は仕様型实例（型パラメータ付き可能）
- 特殊変数 `result` を使用して戻り值を表せる

#### 1.2 ループ仕様

```yaoxiang
while i < n {
    /*! invariant: Bounds[i, n] = 0 <= i <= n
                  && SumInvariant[s, arr[0..i]] ! */
    s = s + arr[i]
    i = i + 1
}
```

#### 1.3 仕様式

仕様右侧のブール式はYaoXiang式構文を使用し、以下をサポート：

- 算術演算、比較演算、論理演算
- 量詞：`forall i in 0..n: P(i)`、`exists i in 0..n: P(i)` — 言語内置の論理構成
- 関数呼び出し（純関数である必要あり）

### 2. 仕様型システム

仕様型は本质的にYaoXiangの通常の型であり、統一構文モデルと完全に一致します。

#### 2.1 組み込み仕様型

コンパイラは以下常用的仕様型を内蔵（仕様で直接使用可能）：

```yaoxiang
// 組み込み仕様型定義
NonEmpty: (T: Type) -> Type = { len: T; len > 0 }
Positive: Type = { x: Int; x > 0 }
GreaterOrEqual: (T: Type) -> Type = { result: T, arr: Array(T); result >= arr[0] && forall i in 1..arr.len: result >= arr[i] }
Bounds: (T: Type) -> Type = { i: T, n: T; 0 <= i && i <= n }
SumInvariant: (T: Type) -> Type = { s: T, arr: Array(T); s == sum(arr[0..i]) }

// 量詞構成（言語内置、関数而非）
forall: (start: Int, end: Int, pred: (Int) -> Bool) -> Bool
exists: (start: Int, end: Int, pred: (Int) -> Bool) -> Bool
```

#### 2.2 ユーザー定義仕様型

通常の型定義と完全に一致し、ユーザーは仕様型を自定义可能：

```yaoxiang
// 正整数仕様の定義
Positive: Type = { x: Int; x > 0 }

// ソート済み配列仕様の定義
Sorted: (T: Ord) -> Type = {
    arr: Array(T);
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

// 最大値仕様の定義
ExistsMax: (T: Ord) -> Type = {
    result: T, arr: Array(T);
    exists i in 0..arr.len: result == arr[i]
    && forall j in 0..arr.len: result >= arr[j]
}
```

カスタム仕様の使用：

```yaoxiang
sqrt: (x: Positive) -> Float = {
    //! ensures: SquareRootResult(result, x) = result * result <= x && (result+1)*(result+1) > x
    // 実装...
}

binary_search: (T: Ord) -> ((arr: Sorted(Array(T)), key: T) -> Option(Index)) = {
    //! ensures: SearchResult(result, arr, key)
    // 実装...
}
```

仕様型は他の型一样、支持泛型パラメータ、型constraint、型推論への参加が可能。

### 3. コンパイルモード

| モード              | 動作                                                                          | オプション                                          |
| ----------------- | ----------------------------------------------------------------------------- | --------------------------------------------- |
| **Debug Build**   | 仕様を解析し、検証条件を生成し、SMTソルバーを呼び出して証明；検証通过后才能进行Release Build | `yaoxiangc --debug source.yx`                 |
| **Release Build** | すべての `//!` コメントを無視し任何コードも生成しない；すべての検証キャッシュをクリア； агрессив最適化を有効化           | `yaoxiangc --release source.yx`               |
| **実行時チェック**    | 仕様を実行時assertionに変換し、違反時にpanic                                          | `yaoxiangc --enable-runtime-checks source.yx` |

検証モードでは、証明に失敗した場合、コンパイラはエラーを報告し、可能な反例（入力値など）を提供します。

### 4. 検証機構

コンパイラは仕様を検証条件（Verification
Conditions）に変換し、統合されたSMTソルバー（Z3など）に送信します。検証プロセスは大致如下：

1. 関数の `requires` と `ensures`、ループの `invariant` を収集
2. 各ループに対してループ不変式証明義務を生成：ループ進入前に成立、每次迭代後に維持、ループ退出後に事後条件を蕴含
3. 関数体を論理式に変換し、仕様と組み合わせて検証条件を形成
4. SMTソルバーを呼び出して充足可能性をcheck

ソルバーが `unsat`（不充足）を返した場合、仕様は成立。それ以外の場合は反例を報告。

### 5. テストとの結合

実行時チェックモードでは仕様をassertionに変換してテストに使用可能。仕様カバレッジツールを組み合わせることで、テストの仕様カバー率を評価できます。将来的には、テストから自動的に候補仕様を推論する仕様マイニングツールも検討可能。

### 6. エディタサポート

`//!` と `/*! ... !*/`
はエディタによって特別なコメントとして認識され、別の色（紫色など）が付与され、通常のコメントと区別されます。言語サーバーは仕様のホバー補完、候補提示、検証エラー報告を提供できます。

## 詳細設計

### 構文変更

| 以前           | 移行後                                 |
| -------------- | ------------------------------------ |
| 仕様コメント構文なし | `//!` と `/*! ... !*/` 仕様コメントを許可 |

### 7.1 構文拡張

既存の構文（RFC-010）を基础上、関数本体とループ本体の先頭に0条以上の `//!` または `/*! ... !*/`
コメント的出现を許可します。仕様構文は統一型構文と一致します：

```
spec_comment     ::= ('//!' spec_line) | ('/*!' spec_block '!*/')
spec_line        ::= spec_name ':' type_expr '=' expr
spec_name        ::= 'requires' | 'ensures' | 'invariant'
spec_block       ::= (spec_name ':' type_expr '=' expr ';')*
```

- 仕様本质は型宣言：`仕様名: 仕様型 = ブール式`
- `type_expr` は仕様型式（型パラメータ付き可能）
- `expr` はYaoXiang式構文を使用し、量詞をサポート

### 7.2 型検査

検証モードでは、コンパイラは仕様コメントを対応する仕様型インスタンスに変換し、関数またはループのメタデータに記録します。

### 7.3 検証条件生成

Weakest precondition または strongest
postcondition 計算を採用し、ループ不変式と組み合わせて一階述語論理式を生成します。生成されたVCはSMT-LIB形式を使用し、外部ソルバーを呼び出します。

### 7.4 エラー報告

証明に失敗した場合、ソルバーはモデル（反例）を提供する可能性があります。コンパイラはこれらの反例を 읽을 수 있는形式に変換する必要があります（例如具体的输入值），帮助用户调试。

### 7.5 ランタイムチェック

`--enable-runtime-checks` モードでは、コンパイラは仕様を `assert` 文に変換します：

- `requires`：関数入口に `assert(cond)` を挿入
- `ensures`：関数のすべての復帰点の前に `assert(cond)` を挿入（`result` 实际返回值に置き換え）
- `invariant`：ループ本体先頭に `assert(cond)` を挿入

### 7.6 既存設計との統合

- **所有権モデル**：仕様中の式は所有権ルールに従い、読み取りのみ可能（純関数）、副作用を避ける
- **ジェネリクスシステム**：仕様型はジェネリックパラメータ（`Requires(P)`など）をサポートし、ジェネリック関数/型と組み合わせ可能
- **依存型**：仕様中の值依存型（配列長さ `n` など）が自然に利用可能

### 型システムへの影響

- 仕様型はYaoXiangの通常の型であり、統一構文モデルと一致
- コンパイラは常用的仕様型を内装（`Positive`、`NonEmpty`、`GreaterOrEqual` など）
- ユーザーは通常の型定義を通じて仕様型を自定义可能
- 仕様型はジェネリックパラメータをحاتملة，支持型constraint

### ランタイム動作

- **Debug Build**：SMTソルバーを呼び出して静的検証を実行し、コンパイル時間が増加；検証成功后検証結果をキャッシュ
- **Release Build**：仕様コメントが無視され、ゼロ実行時オーバーヘッド；すべての検証キャッシュをクリア；Spanキャッシュクリアなどの агрессив 最適化を有効化
- **実行時チェックモード**：assertion文を生成し、実行時に違反を検出

### コンパイラの改修

- パーサー：仕様コメント構文を認識
- 意味解析：仕様を収集し、仕様型に変換
- 検証バックエンド：検証条件を生成し、SMTソルバーを呼び出す
- コード生成：実行時チェックモードをサポート

### 後方互換性

- ✅ 完全な後方互換性
- 仕様コメントは通常のコンパイルで無視され、既存コードに影響なし
- Release Build時に仕様が無視され、追加オーバーヘッドなし

## トレードオフ

### 利点

- **Debug Build検証**：Debug Build時に强制検証し、論理正しさを確保
- **構文が优雅**：純粋なコメント、新キーワードなし、エディタに優しい
- **型システムとの融合**：仕様は型、可拡張
- **漸進的採用**：実行時チェックから静的検証へ逐步的に移行可能
- **信頼性の向上**：テストでは見つけにくい論理エラーを検出可能

### 欠点

- **コンパイル時間**：検証モードがコンパイル時間を大幅に増加させる可能性
- **学習曲線**：効果的な仕様と量詞の記述方法を学ぶ必要がある
- **SMTソルバーの限界**：某些複雑性子は自動証明できない可能性

## 替代方案

| 方案                        | 优点           | 缺点                     |
| --------------------------- | -------------- | ------------------------ |
| 新キーワード（如 `requires`）   | 構文が直观的に明白       | 新キーワードの導入により简洁性が損なわれる |
| 独立した仕様ファイル（如 CVL）    | 仕様とコードが分离 | ファイル数が増加し、同期が困難   |
| 実行時assertionのみ                | 実装が簡単       | 静的保証がない             |
| **本方案（コメント+仕様型）** | 简洁性と機能のバランス | エディタのサポートが必要             |

## 実装戦略

### 段階区分

| 段階                     | 内容                                                                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **段階1：基礎サポート**     | パーサーを拡張し、`//!` と `/*! ... !*/` コメントを認識してASTノードに追加；検証モードで仕様を収集し、简单な検証条件（算術比較のみ）を生成；Z3ソルバーを統合 |
| **段階2：量詞サポート**     | 量詞式をサポートし、SMT-LIBの `forall`/`exists` に変換；仕様のIDE構文強調とホバー補完を提供                                                        |
| **段階3：最適化とツールチェーン** | 増分検証、検証済みモジュールのキャッシュ；仕様カバレッジレポート；仕様マイニングツール（テストから候補仕様を生成）                                                            |

### 依存関係

- RFC-009: 所有権モデル - 仕様式は純関数セマンティクスが必要
- RFC-010: 統一型構文 - 仕様型システムは型システムに基づく
- RFC-011: ジェネリクスシステム設計 - 仕様型はジェネリックパラメータをサポート

### リスク

1. **SMTソルバー統合の複雑さ**：Z3などのソルバーの統合に技術的な課題が発生する可能性があります
   - 軽減：成熟したRust Z3バインディングを使用し、対応する式タイプを段階的に拡張

2. **検証失敗のデバッグが困難**：SMTソルバーが仕様を証明できない場合、ユーザーは原因を理解するのが難しい場合があります
   - 軽減：明確なエラー情報と反例の説明を提供

3. **パフォーマンスオーバーヘッド**：検証モードがコンパイル時間を大幅に増加させる可能性があります
   - 軽減：増分検証とキャッシュメカニズムを実装
