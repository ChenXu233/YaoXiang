## 概要

本文書は RFC-001、008、018 の基础上に立ち、YaoXiang の並行生成モデルをさらに細分化・拡張し、**動的モジュールのロード**、**外部関数インターフェース（FFI）**、および**よりきめ細やかなスケジューリング最適化**といった現実的なシナリオに対応します。コア設計には以下が含まれます：

1. **動的モジュールメタデータ契約**：同一言語で書かれた動的ライブラリに対してコンパイル時の依存関係記述を提供し、メインプログラムが静的 DAG を構築できるようにしつつ、透明並行生成を維持します。
2. **FFI スケジューリングセマンティクス**：外部関数は DAG 内でデフォルトで `@block` ノードとして動作し、アノテーションにより並行スケジューリングに統合できます（FFI ツールチェーンの詳細については [RFC-021](./021-library-driven-ffi-extension.md) を参照）。
3. **呼び出しコンテキストに基づく最適化**：静的しきい値へのフォールバックに代わるものとして、コンパイラは関数内の DAG での実際の役割（消費者数、副作用など）に基づいて、その関数をインライン化するかどうか、または独立ノードとしてスケジューリングするかをインテリジェントに判断します。
4. **制御フローと DAG の統合メカニズム**：`if`、`loop` などの動的構造を Phi ノードと動的展開を通じて、データフローダイアグラムに自然に統合します。
5. **実行時スケジューラのメモリとパフォーマンス最適化**：ノードのライフサイクル管理、エリアアロケーション、ロックフリーキューなどの低コスト抽象化の実装を明確化します。

本文書は言語仕様を完善し、YaoXiang の並行生成モデルが静的全プログラム分析に対応しつつ、動的性质と外部との相互作用にも柔軟に対応できるよう設計されています。

## 動機

### 既存設計の不足

RFC-001/008/018 はエレガントな透明並行生成モデルを構築しましたが、実世界の要求に対しては依然として盲点があります：

- **動的モジュール**：プログラムがプラグインや動的リンクライブラリをサポートしている場合、メインプログラムはコンパイル時にモジュール内部の呼び出し関係や依存関係を把握できず、グローバル DAG の構築に失敗します。
- **FFI 呼び出し**：外部関数（C ライブラリなど）は完全にブラックボックスであり、その内部に並行生成、ブロッキング、副作用が含まれる可能性があります。これを通常のノードとして扱うと並行生成の安全性が壊れます。
- **小関数のスケジューリングオーバーヘッド**：RFC-001 で提案された「L1 自動フォールバック」は静的しきい値（命令数 <50）を使用し、この暗黙的なルールにより開発者は動作を予測し難く、複雑な呼び出しコンテキストに対応できません。
- **制御フローと DAG の融合**：`if`、`loop` などの動的構造が DAG 内でどのように表現されるかが不明確であり、依存関係解析の正確性に影響を与える可能性があります。
- **実行時オーバーヘッドの制御**：DAG ノード数が増加するにつれて、スケジューラのメモリ管理とパフォーマンス最適化を明確化する必要があり、ボトルネックになることを避ける必要があります。

### 目標

- 透明並行生成のコア哲学を維持しながら、動的モジュールと FFI に対して明確で安全、かつ段階的なサポートを提供します。
- スケジューリング最適化を「暗黙的なグローバルルール」から「コンテキストベースのインテリジェントな判断」に转变し、予測可能性とパフォーマンスを向上させます。
- 動的制御フローに対する DAG 表現を完善し、すべてのプログラム構造がデータフローモデルに自然に統合されるようにします。
- スケジューラのメモリ管理とパフォーマンス最適化戦略を明確化し、低コスト抽象化を実現します。

## 提案

### 1. 動的モジュールメタデータ契約

#### 1.1 契約内容

YaoXiang でコンパイルされた各動的ライブラリ（`.yxo` / プラットフォーム固有の動的ライブラリ）には、**メタデータ記述ファイル**（`.yxmeta`）が添付でなければならず、以下の内容を含みます：

- **エクスポート関数リスト**：各関数の完全な型シグネチャ（パラメータ、戻り値のリソースマーク）。
- **副作用マーク**：`@pure` / `@io` はコンパイラが自動導出し、開発者が明示的に上書きも可能。
- **リソース依存**：各パラメータがリソース型かどうか（例：`File`）、戻り値に新リソースが含まれるかどうか。
- **呼び出しグラフサマリー**（オプション）：この関数が呼び出す可能性のある他のエクスポート関数 ID。モジュール間循環依存の検出に使用。
- **所有権情報**：パラメータ的所有権セマンティクス（借用/移動）、戻り値の所有権。
- **並行生成安全性**：`Send`/`Sync` の自動導出結果。

メタデータ形式にはバイナリまたは構造化テキスト（例：MessagePack）を使用し、パーシング効率を確保します。

#### 1.2 コンパイル時処理

メインプログラムのコンパイル時に、動的モジュール関数の呼び出しを検出した場合：

1. 対応モジュールの `.yxmeta` ファイルを読込みます。
2. グローバル DAG に**プレースホルダノード**を作成し、メタデータから取得した入出力依存関係、副作用マークなどを記録します。
3. プレースホルダノードは通常のノードと同様に依存関係解析に参加し、スケジューラは事前に実行順序を計画できます。

#### 1.3 実行時バインディング

動的モジュールのロード時に：

- 実行時は実際の関数シグネチャとメタデータの一致を検証し（バージョン不一致を防止）。
- プレースホルダノードを実際の関数ポインタにバインディングします。

**サブグラフスケジューリングセマンティクスについて**：動的モジュール内部に独立したサブ DAG がある場合（例：モジュール自体が並行生成ロジックを含む場合）、そのサブグラフは**独立したスケジューリングユニット**として実行されます。その境界はモジュールのエクスポート関数によって定義されます：エクスポート関数を呼び出すとき、サブグラフは全体として実行を開始し、その関数が戻るまで続きます。サブグラフ内部のノードスケジューリングはサブグラフ自身のスケジューラが担当し（モジュール内部では標準スケジューラを継続使用可能）、サブグラフとメイン DAG の相互作用は入出力データフローに限定されます——メイン DAG のプレースホルダノードはサブグラフの開始と終了のみ关心し、内部スケジューリングには介入しません。この設計により、モジュールのカプセル化が保証されると同時に、メイン DAG の静的完全性が維持されます。

#### 1.4 安全性の保証

- 動的モジュールが契約に違反した場合（例：`@pure` を主張しながらグローバル状態を修正）、結果は開発者の責任になります（FFI の unsafe 境界と同様）。しかし同一言語であるため、実行時チェック（メモリ分離など）で安全性を強化することは可能ですが、オーバーヘッドが増加します。
- モジュール間循環依存：モジュール A が B を呼び、B が A を呼び、元データに関数呼び出し関係を宣言している場合、コンパイラは検出してエラーを報告できます；宣言していない場合、実行時にデッドロックが発生する可能があり、スケジューラが検出して panic を発生させます。

### 2. DAG 内での FFI スケジューリングセマンティクス

FFI の完全なツールチェーンサポート（動的ライブラリのロード、バインディング生成、型変換、メモリ所有権）は [RFC-021](./021-library-driven-ffi-extension.md) で定義されています。本節では DAG スケジューリングにおける FFI 呼び出しの動作のみを説明します。

#### 2.1 デフォルトスケジューリング動作

外部関数（`native("symbol")` で宣言）は DAG 内でデフォルトで **`@block` ノード** として動作します：

- DAG 並行スケジューリングに参加せず、現在のスレッドで同期的に直接実行されます。
- 実行中はスケジューラがその内部並行生成に介入しません。
- 戻り値は使用可能ですが、呼び出し自体は依存エッジを生成しません。

#### 2.2 オプションの並行生成アノテーション

開発者はアノテーションを使用して FFI 呼び出しを DAG スケジューリングに統合できます（詳細については [RFC-021 §2.2](./021-library-driven-ffi-extension.md) を参照）：

- `@pure`：通常の DAG ノードとして扱い、依存関係のない他のノードと並行実行可能。
- `@io`：リソース依存関係解析に参加し、同一リソースへの複数回の呼び出しは自動的に直列化されます。

#### 2.3 スケジューラへの影響

FFI ノードはスケジューラ内では通常のノードと同じ `TaskNode` 構造を使用し、唯一の違いは `effect` マークが `Block` であることです。スケジューラは `Block` ノードを検出すると並行スケジューリングをスキップし、直接同期的に実行します。

### 3. 呼び出しコンテキストに基づく最適化

RFC-001 の「L1 自動フォールバック」静的しきい値に代わるものとして、**コンパイラが各呼び出し点在けにおける DAG での実際のコンテキストに基づいてインテリジェントに判断**します。

#### 3.1 最適化判断の根拠

コンパイラは各関数呼び出しノードを分析します：

- **消費者数**：このノードの結果が何個のダウンストリームノードに使用されているか。1 の場合はインライン候補となり、1 より大きい場合は結果共有のために独立ノードとして保持する必要があります。
- **副作用**：ノードが `@io` 副作用を持つ場合、順序を保証するために独立ノードとして保持する必要があります。
- **計算量の推定**：命令数などのヒューリスティックを引き続き参考として使用可能ですが、硬性しきい値ではなく、インライン効果の評価のみに使用されます。
- **リソース依存**：ノードがリソース変数（例：`File`）を含み、リソース変数がアップストリームとダウンストリーム間で渡される場合、インライン化が依存チェーンを壊す可能性があるため、慎重する必要があります。

#### 3.2 インライン操作

インライン化を決定した場合：

- そのノードの計算ロジックを唯一のダウンストリームノードのコードに直接埋め込みます。
- DAG からそのノードを移除し、入力は直接ダウンストリームノードの入力になります。
- 最終的なコード生成時、インライン化された関数は独立したスケジューリングユニットを生成しません。

#### 3.3 インライン化の制限

- 再帰関数またはループ内の呼び出しは通常インライン化せず、無限展開を防ぎます。
- モジュール境界をまたぐ関数（動的モジュール、FFI）はインライン化しません。
- 開発者は `@noinline` アノテーションでインライン化を明示的に禁止したり、`@forceinline` でコンパイラにインライン化を試みるようにヒントを与えられます。

#### 3.4 観測可能性

コンパイラは最適化レポートを生成し（`--emit-optimization-report` で有効化）、以下の情報を含みます：

- **各インライン点**：インライン化された関数名、呼び出し位置、インライン化の理由（例：「唯一の消費者かつ純粋関数」）。
- **独立ノードとして保持された理由**：「複数の消費者あり」「副作用を含む」「モジュール間呼び出し」など。
- **判断統計**：インライン化総数、保持ノード数。開発者が最適化効果を評価するために使用。

レポート出力形式はテキストまたは JSON を選択し、ツールでの解析を容易にします。

### 4. 制御フローと DAG の統合

#### 4.1 条件分岐（if）の処理

**Phi ノード**（SSA 形式を借鉴）を導入して分岐マージポイントを表します：

- コンパイル時に各 `if` 式に対して以下を構築します：
  - 2つの分岐サブ DAG（それぞれ `then` と `else` に対応）。
  - 条件変数と2つの分岐の出力を入力とする Phi ノード。
- Phi ノードのセマンティクス：条件変数が準備できたら、条件値に基づいて対応する分岐の出力を選択して自身の出力とします。
- 実行時に、Phi ノードは条件変数に依存します；条件が準備できたら、動的に自身を選択した分岐のダウンストリームリストに追加し、その分岐の結果を待ちます。

サンプル DAG：

```
        cond
       /    \
  then DAG  else DAG
       \    /
        Phi
         |
      后续ノード
```

#### 4.2 ループ（loop/while）の処理

ループはフィードバックエッジを持つサブ DAG として扱い、実行時に**オンデマンドで展開**されます：

- コンパイル時にループボディを識別し、**ループテンプレート**を構築します。これには以下を含みます：
  - 条件ノード。
  - ループボディサブ DAG。
  - イテレーション間で渡される状態変数。
- 実行時に、ループ結果が必要な場合（例：ループ終了後に累積値を使用）、スケジューラは動的にイテレーションの展開を開始します：
  1. 初めて条件ノードをスケジューリングし、真であれば最初のイテレーションのサブ DAG をインスタンス化し、入力には初期状態と外部変数を含めます。
  2. イテレーション完了後に新状態を生成し снова 条件ノードを（新状態に依存して）スケジューリングし、継続するかを判断します。
  3. 条件が偽になるまで繰り返し、最後のイテレーションの出力がループ結果となります。

**複雑な例：ループ条件がループボディ内部で更新される**

```yaoxiang
let mut x = 0
while x < 10 {
    x = compute(x)  // x はループボディ内で更新される
}
```

このパターンでは、条件ノード `x < 10` は各イテレーション後に更新される `x` に依存します。DAG での表現：

- ループテンプレートには状態変数 `x` を含み、初期値は 0 です。
- 各イテレーション：まず条件ノードを実行（現在の `x` に依存）、真であれば `x = compute(x)` を実行して新しい `x` を生成し、条件で 다시 入ります。
- 実行時は上記のプロセスで動的に展開し、条件が偽になるまで続けます。

イテレーション間の依存関係は状態変数を通じて自然にデータフローを形成し、依存関係のあるイテレーションは自動的に直列化され、依存関係のないイテレーションは並列化可能（例：`map`）。

#### 4.3 無限ループの特別な処理

単一の無限ループはメイン DAG として直接同期実行されます（スケジューリングオーバーヘッドなし）；複数の無限ループはバックグラウンド DAG として、スケジューラがタイムスライスでコンテキストスイッチしながら並行実行されます。

### 5. 実行時スケジューラのメモリとパフォーマンス最適化

#### 5.1 ノードライフサイクル管理

- 各ノードは**参照カウント**（アトミック変数）を維持し、その結果を依存する消費者の数を示します。
- ノード実行完了後に結果をすべてのダウンストリームに 전달し終えたら、参照カウントがゼロになり、ノードのメモリを解放できます。
- 結果値自体も参照カウントを使用し（`Arc<T>`）、ただし最適化可能：結果を1人の消費者のみが使用する場合は、所有権を直接移動してカウントオーバーヘッドを避けます。

#### 5.2 エリアメモリアロケーション（Arena）

動的に生成された多くの短ライフサイクルノード（ループイテレーションなど）に対しては、**エリアアロケータ**を使用します：

- 1回のループ展開に対してメモリエリアを割り当てます。
- エリア内のノードは連続して割り当てられ、まとめて解放されるため、フラグメンテーションと解放オーバーヘッドが減少します。
- エリア終了時に、すべてのノードメモリを一度に回收します。

#### 5.3 ロックフリーデータ構造

- 依存カウンタ：`AtomicUsize` を使用し、`fetch_sub` でアトミックデクリメント。
- 準備完了キュー：Chase-Lev 両端キュー（各スレッドローカルキュー + ワークスティーリング）を使用し、ロック競合を減少。
- ダウンストリームリスト：作成後は読み取り専用にし、並行変更を避けます。

#### 5.4 アダプティブスケジューリング

- システムに無限ループが1つだけある場合、直接同期実行し、スケジューリングオーバーヘッドをゼロにします。
- タスク粒度とシステム負荷に応じて、並行度を動的に調整します（例：キュー長を監視してワーカースレッド数を調整）。

#### 5.5 低コスト抽象化原則

すべてのスケジューリングオーバーヘッドはタスク数に比例し、各タスクの追加オーバーヘッド（作成、エンキュー、依存関係処理）は数十ナノ秒レベルに制御されます。超細粒度タスクについては、インライン最適化（第3節）を介してスケジューリングを避けます。

## 詳細設計

### 6.1 動的モジュールメタデータ形式（草案）

```rust
// メタデータファイル構造（簡略化）
struct Metadata {
    version: u32,
    functions: Vec<FuncMeta>,
}

struct FuncMeta {
    name: String,
    signature: TypeSignature,
    effects: EffectTag,      // Pure | IO | Block
    resource_params: Vec<usize>, // パラメータインデックスリスト。リソース型であるパラメータを示す
    calls: Vec<String>,       // 呼び出す他のエクスポート関数名（オプション）
    ownership: OwnershipInfo,
    send_sync: SendSync,      // Send/Sync を満たすかどうか
}
```

### 6.2 スケジューラコアデータ構造

```rust
struct TaskNode {
    id: TaskId,
    deps: Vec<TaskId>,                // アップストリーム依存
    remaining_deps: AtomicUsize,
    inputs: Vec<Option<Value>>,
    result: Option<Value>,
    func: Executable,
    downstream: Vec<TaskId>,           // ダウンストリームノード（作成後は読み取り専用）
    effect: EffectTag,
    arena_id: Option<ArenaId>,         // 所属エリア（オプション）
}

struct Scheduler {
    ready_queues: PerThreadQueue<TaskId>, // 各スレッドローカルキュー
    global_work_stealer: WorkStealer,
    arenas: ArenaAllocator,               // エリアアロケータ
}
```

### 6.3 コンテキストベースの最適化分析

コンパイラは MIR レベルで以下のステップを実行します：

1. グローバルコールグラフとデータ依存グラフを構築します。
2. 各関数呼び出しノードに対して、その出次数（消費者数）を計算します。
3. 出次数が1で、関数が副作用なし（`@pure`）で、非再帰的な場合、「インライン候補」としてマークします。
4. ヒューリスティック（命令数など）と組み合わせてインライン効果の評価を行い、インライン化するかを決定します。
5. インライン化時に、呼び出しノードのコードをダウンストリームに埋め込み、依存関係を更新します。

### 6.4 制御フローノード表現

```rust
enum NodeKind {
    Normal(FuncId),
    Phi { cond: TaskId, then_branch: TaskId, else_branch: TaskId },
    LoopTemplate { cond: FuncId, body: FuncId, state_var: VarId },
    // ...
}
```

実行時の動的展開時に、`LoopTemplate` は一連の `Normal` ノードインスタンスを生成します。

## トレードオフ

### メリット

- **動的モジュールの安全な統合**：メタデータ契約により、動的ライブラリがメインプログラムとシームレスに並行生成モデルを共有でき、静的 DAG の完全性を維持します。
- **FFI の段階的な統合**：開発者は外部関数に対して段階的にアノテーションを追加でき、安全なフォールダウンから効率的な並行生成への移行が可能。
- **最適化予測可能性**：コンテキストベースの判断が暗黙的なしきい値に代わることで、動作が透明になり、開発者はツールを通じて最適化を理解できます。
- **制御フローの自然な統合**：Phi ノードと動的展開により、DAG がすべてのプログラム構造を表現でき、特殊構文が不要。
- **パフォーマンススケーラビリティ**：エリアアロケーション、ロックフリーキューなどの設計により、スケジューラが大規模並行生成に対応可能。

### デメリット

- **メタデータ契約によるコンパイル複雑性の増加**：動的ライブラリに対するメタデータ生成と解析が必要であり、ツールチェーンが対応必要。
- **FFI アノテーションの開発者正しさへの依存**：誤ったアノテーションはデータ競合を引き起こす可能があり、文書とツールヒントでリスクを軽減必要。
- **コンテキスト最適化分析の時間消費**：グローバル解析によりコンパイル時間が増加する可能性があり、インクリメンタルコンパイルで緩和可能。
- **動的展開による実行時オーバーヘッドの増加**：ループ展開には動的ノード生成が必要だが、エリアアロケーションで緩和可能。

## 実装戦略

### 段階的区分（優先順位提案付き）

> **実装優先順位の提案**：初期段階では完璧な実装を追求せず、シンプルな方案でシステムを動作させ、段階的に最適化することが推奨されます。例：
>
> - 参照カウントは直接 `Arc` を使用可能。
> - ロックフリーキューは成熟したライブラリ（例：crossbeam の deque）を使用可能。
> - エリアアロケーションはシンプルな bump allocator から始め、後で最適化可能。

#### 段階 1：基盤サポート（v0.7）

- [ ] FFI のデフォルト `@block` フォールダウンを実装。
- [ ] FFI が使用する `@pure`、`@io` アノテーションを追加。
- [ ] リソースラッパ型（`File` など）とその基本メソッドを実装。

#### 段階 2：動的モジュールメタデータ（v0.8）

- [ ] メタデータ形式を設計し、コンパイラが動的ライブラリ用に `.yxmeta` を生成するように修正。
- [ ] メインプログラムコンパイル時のメタデータ読込みとプレースホルダノード作成を実装。
- [ ] 実行時バインディングメカニズムを実装。

#### 段階 3：コンテキスト最適化（v0.9）

- [ ] コールグラフ分析を実装し、ノード出次数を計算。
- [ ] インライン判断とコード生成サポートを追加。
- [ ] 最適化レポート出力（含インライン点、理由など）を実装。

#### 段階 4：制御フロー DAG 統合（v0.10）

- [ ] Phi ノードと条件分岐のコンパイル時表現を実装。
- [ ] ループテンプレートと動的展開実行時を実装。
- [ ] 無限ループのバックグラウンドスケジューリングを完善。

#### 段階 5：パフォーマンス最適化（v1.0）

- [ ] エリアアロケータを実装。
- [ ] ロックフリーキューとワークスティーリングを最適化。
- [ ] ベンチマークテストとチューン。
