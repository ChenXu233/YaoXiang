## RFCライフサイクル

```
ドラフト → レビュー中 → 採用済み → 廃止（置き換え）
                            ↓
                        拒否（不承認）
```

### ステータス説明

| ステータス     | 配置先            | 説明                                           |
| -------------- | ----------------- | ---------------------------------------------- |
| **ドラフト**   | `rfc/draft/`      | 著者のドラフト、レビュー提出待ち               |
| **レビュー中** | `rfc/review/`     | コミュニティでの議論とフィードバック募集中     |
| **採用済み**   | `rfc/accepted/`   | 正式な設計文書となり、実装段階へ進む           |
| **廃止**       | `rfc/deprecated/` | かつて採用されたが、新しい設計に置き換えられた |
| **拒否**       | `rfc/rejected/`   | 拒否されたRFC文書                              |

## 文書改訂ルール

**RFC文書には正しい情報のみを含める必要があります。**
設計が変更された場合は、現在正しい意味を表現するように原文を直接修正してください。**「正誤表」ブロックを追加して修正するために誤った内容を保持してはいけません。**

「原文 + 正誤表」を保持することは最悪の書き方です。読者が途中まで読んで初めて前がすべて無効になっていることに気づき、それまでの読解コストが無駄になるだけでなく、廃止された段落を現行のセマンティクスへの参照と誤認しやすくなります。正誤表ブロックは一見慎重に映りますが、実際には整理コストを-readerに押し付けているだけです。

### 正しい対応

| 状況                                           | 対応                                                                                                       |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 実装と原文が一致しない、原文が覆された         | その段落を正しい内容に直接書き換え、元の表現を削除する                                                     |
| サンプルコードが実行できなくなった             | 実行可能な形にそのまま変更し、古いサンプルを保持しない                                                     |
| 読者に「以前はどうだったか」を伝える必要がある | **意図的にエラー比較を行う**場合のみエラー内容を保持し、「この書き方は誤りである」及び理由を直ちに注釈する |
| 設計の変遷を遡る必要がある                     | Git コミットメッセージまたは issue に記述し、RFC 本文には書かない                                          |

### 例外

以下のエラー情報は保持できます：

- **意図的に行う対比教育**：正誤対照として明確に注釈されており、エラー側には「なぜ誤りか」の説明が直ちに付記されている
- **廃止された RFC**（`rfc/deprecated/`）：歴史的記録として残す。ただし何に置き換えられたかを注釈する必要がある

### 補助手段

- RFC 上部の `status` / `updated`
  フィールドは最新の改訂時間を反映しており、本文に「今回の改訂内容」を記述する必要はない
- 実装ステータスは表の ✅ / ❌ で表現し、本文にステータスの説明を紛れ込ませない
- 完全な改訂履歴は `git log -- <ファイル>` で確認する

## RFCの提出

1. [RFC_TEMPLATE.md](RFC_TEMPLATE.md) を読んでフォーマット要件を理解する
2. [EXAMPLE_full_feature_proposal.md](EXAMPLE_full_feature_proposal.md) を参考にして書き方を学ぶ
3. 新しいファイルを作成し、`番号-説明的なタイトル.md` という名前を付ける
4. ファイルを `docs/reference/rfc/draft/` ディレクトリに配置する
5. このインデックスファイルを更新し、新しい RFC エントリを追加する
6. PR を提出してレビュープロセスに進む
