## 一、なぜ YaoXiang を作るのか？

### 1.1 埋めるべき言語の空白

プログラミング言語の歴史において、C 言語がシステムプログラミングに効率革命をもたらし、Python が誰にでも学べるプログラミング体験を創り出し、Rust がメモリ安全と性能の両立を証明し、TypeScript が大規模フロントエンドプロジェクト保守を可能にした——，无数の優秀な言語の誕生と進化を目の当たりにしてきた。しかし、今日の言語エコシステムを見渡すと、**以下の3つの核心ニーズを同時に満たす言語がまだ存在しない**という明確な空白地帯がある：

| ニーズ       | 既存のソリューションの問題                                                       |
| ------------ | -------------------------------------------------------------------------------- |
| **型安全**   | Rust は過度に厳格で、学習曲線が険しい；TypeScript はオプショナル型で、コンパイル時の保証を提供できない |
| **自然な構文**| Rust の構文は複雑で晦難；Haskell の関数型は障壁が高い；従来の静的言語は冗長で面倒 |
| **AI 対応**  | 既存の言語は構文の曖昧さ、複雑な AST、予測困難な隠れた動作が多く、AI によるコード生成と変更の精度が制限される |

YaoXiang の誕生は、この空白を埋めるためである。我々は信じる：**プログラミング言語は、強力で親しみやすく、安全で効率的、厳密でエレガントであるべき**と。

### 1.2 解決すべき実際の問題

**問題一：型システムの断片化**

今日のプログラミング言語は型システムにおいて深刻な断片化を示している。静的型付け言語はコンパイル時の絶対的な正しさを追求するが、しばしば開発効率の犠牲を伴う；動的型付け言語は柔軟性を提供するが、大規模プロジェクトでは保守の難点が露呈する。YaoXiang は「すべてを型とする」統一抽象フレームワークを提案し、型を言語設計の主軸として貫く、後付けのパッチではなく。

**問題二：メモリ安全と性能の二択**

長年にわたり、開発者はメモリ安全と実行性能の間で困難な選択を迫られてきた。GC（ゴミ収集）は開発者を解放するが、レイテンシ変動とメモリオーバーヘッドをもたらす；手動メモリ管理は効率的だが、綱渡りのように危険である。YaoXiang は Rust 流の所有権モデルを採用し、コンパイル時にデータ競合とメモリリークを消除しながら、ゼロコスト抽象を維持し、GC なしで高性能を実現する。

**問題三：非同期プログラミングの認知負荷**

現代アプリケーションはネットワークと並行処理なくしては成り立たないが、非同期プログラミングは常にプログラマの悪夢であった。コールバックのネスト、Promise のチェイン呼び出し、async/await 構文——各手法がコードの複雑性を増している。YaoXiang は非同期モデルをを再設計した：関数シグネチャの後に `spawn` マーカーを追加するだけで、コンパイラがすべての非同期詳細を自動処理し、並行プログラミングを同期コードのように自然に行う。

**問題四：AI 支援プログラミングのボトルネック**

AI が開発者のコード作成を支援し始めると、言語設計の選択が極めて重要になる。曖昧な構文ルール、暗黙の型変換、複雑な糖衣構文——かつて人間のプログラマが慣れたこれらの特徴は、AI の理解と生成の障壁となる。YaoXiang は設計当初から「AI 対応」をコアゴールとした：厳格なインデントルール、明確なコードブロック境界、曖昧さのない構文構造により、AI が正確に理解し、生成、変更できる。

### 1.3 言語の哲学的基盤

YaoXiang という名前は『易経』の「爻」と「象」に由来する。「爻」は卦を構成する基本記号であり、陰陽の変化、動静の相생을象徴する；「象」は事物の本質 внешнее表現であり、万象万物、包摂大全を表す。

この哲学思想は言語設計のすべての細部体现在されている：

- **統一性**：爻卦の単純な記号が複雑な卦を構成する如く、YaoXiang は少数のコアコンセプト（型、関数、コンストラクタ）で完全なプログラミングモデルを構築する
- **階層性**：象に先天と後天之分がある如く、YaoXiang の型システムは明確な階層構造を持ち、プリミティブ型からジェネリクスへ、値からメタ型へ
- **変化性**：陰陽の流転、変化无穷である如く、YaoXiang は依存型をサポートし、型が値の変化に伴い進化できる
- **識別可能性**：卦象が解け、万物に象がある如く、YaoXiang は完全な型リフレクション能力を提供し、ランタイム型情報が完全に利用可能
- **証明可能性**：卦象が事物の法則を解明する如く、YaoXiang の型システムは Curry-Howard 同型に従い（型は命題、プログラムは証明）、型チェックのプロセスが論理証明の検証である

## 二、コア哲学と原則

以下の設計信条は YaoXiang の基石であり、**妥協不可、違反不可**である。すべての特性提案はこれらの原則の検証を経なければならない。

### 2.1 原則一：すべてを型とす

YaoXiang の世界観において、型は最上位の抽象ユニットであり、言語を貫く核心コンセプトである。

**具体的な体现**：

- **値は型のインスタンス**：`42` は `Int` 型のインスタンス、`"hello"` は `String` 型のインスタンス
- **型自体が型である**：`Type` は言語唯一のメタ型キーワードであり、`Int` の型は `Type`
- **関数は型マッピング**：`add: (a: Int, b: Int) -> Int` は `Int × Int` から `Int` への型マッピングを記述する
- **モジュールは型の組み合わせ**：モジュールは関数と型を含む名前空間組合

**妥協不可の理由**：統一された型抽象は言語セマンティクスを簡素化し、値と型の二元論を消除し、型システムをコードの正しさの守護者而不是绊脚石とする。

### 2.2 原則二：厳格な構造化

YaoXiang の構文設計は「曖昧さのないこと、予測可能であること、易解析であること」を追求する。

**具体的なルール**：

- **強制4スペースインデント**：タブ文字の使用を禁止、コードブロック境界が一目瞭然
- **括弧は省略不可**：関数引数には括弧が必要、リスト要素にはカンマが必要
- **コードブロックには波括弧が必要**：`if`、`while`、`for` などの制御フローは `{ }` で囲む必要がある
- **キーワード数を精简**：17個のコアキーワードのみを保持、糖衣構文の氾濫を拒否

**妥協不可の理由**：厳格な構造化は三つの重要な優位性をもたらす——（1）IDE の構文ハイライトとコードフォールドがより正確；（2）AI コード生成と変更の精度が大幅に向上；（3）新規学習者がコード構造を迅速に理解できる。

### 2.3 原則三：ゼロコスト抽象

高水準の抽象はランタイムのパフォーマンスオーバーヘッドをもたらすべきではない。

**具体的な保証**：

- **単相化**：ジェネリック関数はコンパイル時に具体バージョンに展開され、仮想テーブル検索のオーバーヘッドがない
- **インライン最適化**：単純関数は自動的にインライン化され、関数呼び出しのオーバーヘッドを消除
- **スタック配置優先**：小オブジェクトはデフォルトでスタック配置、ヒープ配置は必要な場合のみ使用
- **GC なし**：所有権モデルがメモリ安全を保証し、垃圾回収器のランタイムオーバーヘッドが不要

**妥協不可の理由**：パフォーマンスはプログラミング言語の生存底线である。パフォーマンスを代償に利便性を换取する設計はすべて、 programmer への裏切りである。

### 2.4 原則四：デフォルトで不変

可変性と複雑性は影と形のように付き物である。YaoXiang はデフォルトで不変を選択し、コードをより推論しやすく理解しやすくする。

**具体的なルール**：

- 変数はデフォルトで不変であり、代入後は変更不可
- 可変が必要な場合は `mut` を明示的に宣言する必要がある
- 参照はデフォルトで不変であり、可変参照には `mut` マーカーが必要
- 所有権の移転は元のバインディングの失效を意味する

**妥協不可の理由**：不変性は並行処理安全の基礎であり、コード可読性の保障であり、関数型プログラミングの知恵の結晶である。

### 2.5 原則五：型はデータなり

型情報はコンパイル時のみに存在するのではなく、ランタイムで完全に利用可能であるべきである。

**具体的な能力**：

- ランタイム型クエリ：任意的值は型情報を取得できる
- 型リフレクション：型自体を構成して操作できる
- パターン一致による分解：型コンストラクタは直接パターン一致に使用可能
- ジェネリック特化：ランタイムでジェネリックパラメータの具体化型を取得可能

**妥協不可の理由**：完全な型リフレクション能力はメタプログラミングの基礎であり、高パフォーマンスフレームワークとツールの基石である。

## 三、鍵となる革新と特性

YaoXiang は既存の言語の優秀な特性を吸取しながらも、以下の革新的設計を提案する。

### 3.1 革新一：統一型構文

**従来の言語の型定義**は多くの場合、複数のキーワードを必要とする：

```rust
// Rust
struct Point { x: f64, y: f64 }
enum Result<T, E> { Ok(T), Err(E) }
enum Color { Red, Green, Blue }
trait Drawable { fn draw(&self, s: &Surface); }
```

**YaoXiang の統一構文**：すべてが `name: type = value`、`Type` は唯一のメタ型キーワードである。

```yaoxiang
# === レコード型 ===

Point: Type = {
    x: Float,
    y: Float,
}

# デフォルト値を持つフィールド
Point3D: Type = {
    x: Float = 0,
    y: Float = 0,
    z: Float = 0,
}

# === ジェネリック型 ===

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

# === インターフェース（フィールドがすべて関数型のレコード） ===

Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect,
}

Serializable: Type = {
    serialize: () -> String,
}

# === インターフェース実装（インターフェース名を型定義体内に入力） ===

Point: Type = {
    x: Float,
    y: Float,
    Drawable,
    Serializable,
}

# === メソッド（Type.method 構文） ===

Point.draw: (self: &Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}
```

**革新価値**：`fn`、`struct`、`enum`、`trait`、`impl` キーワードの断片化がない——一つの統一構文で全宣言をカバー。

### 3.2 革新二：コンストラクタ即ち型

**値構成と関数呼び出しは完全に同じ**：

```yaoxiang
# 型定義
Point: Type = { x: Float, y: Float }
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

# 値構成：関数呼び出しと同じ
p: Point = Point(3.0, 4.0)
opt: Option(Int) = Option.some(42)
none: Option(Int) = Option.none()

# パターン一致：直接分解
match opt {
    Option.some(value) -> print(value)
    Option.none -> print("nothing")
}
```

### 3.3 革新三：カリー化されたメソッドバインディング

YaoXiang は純粋関数型設計を採用し、カリー化を通じてオブジェクトメソッド呼び出しのような糖衣構文を実現し、`class` と `method` キーワードを導入する必要がない。

```yaoxiang
# === 型定義 ===

Point: Type = {
    x: Float,
    y: Float,
}

# コア関数：ユークリッド距離
distance: (a: Point, b: Point) -> Float = {
    dx = a.x - b.x
    dy = a.y - b.y
    return (dx * dx + dy * dy).sqrt()
}

# メソッド糖衣バインディング（[0] は第0引数位置にバインディング））
Point.distance = distance[0]

# === 使用 ===

p1 = Point(3.0, 4.0)
p2 = Point(1.0, 2.0)

# 2つの呼び出し方式是完全に等価
d1 = distance(p1, p2)     # コア関数を直接呼び出し
d2 = p1.distance(p2)      # メソッド糖衣

# カリー化用法
dist_from_p1 = p1.distance  # 部分適用、第2引数を待つ
d3 = dist_from_p1(p2)       # 2.828
```

**革新価値**：純粋関数型設計、隠れた `self` パラメータなし、関数は値として自由に传递と組合が可能。

### 3.4 革新四：並列実行モデル

> 「万物並作，吾以観復。」——《易・復卦》
>
> 並列実行モデルはここに之意を取り、プログラミングパラダイムを記述する：開発者は同期・順序的な思考でロジックを記述し、言語ランタイムは其中的計算ユニットを万物並作のように自動・効率的に並行実行させ、最終的に統一的に協調する。

**コア三原則**：

| 原則         | 説明                                   |
| ------------ | -------------------------------------- |
| **同期構文** | 目に見えるままの順序コード             |
| **並行本質** | ランタイムが自動的に並行性を抽出       |
| **統一協調** | 結果が必要な時に自動的に集約され、ロジックの正しさを保証 |

**用語体系**：

| 公式用語        | 対応構文                  | 解説                                       |
| -------------- | ------------------------- | ------------------------------------------ |
| **並列関数**   | `spawn (params) => body`    | 並列実行に参加できる計算单元を定義         |
| **並列ブロック**| `spawn { a(), b() }`        | 明示的に宣言された並行域、ブロック内任务是並行実行 |
| **並列ループ**| `spawn for x in xs { ... }` | データ並列、ループ体が全要素で並行実行     |
| **並列値**     | `Async(T)`                  | 並行中の未来値、使用時に自動待機           |
| **並列グラフ**| 遅延評価グラフ(DAG)         | 並列実行が発生する舞台、依存と並行関係を記述 |
| **並列スケジューラ**| ランタイムタスクスケジューラ | 萬物を調整し、正しいタイミングで並列実行させる知的中枢 |

> **詳細**：[RFC-001 並列実行モデル](./rfc/deprecated/001-concurrent-model-error-handling.md)

```yaoxiang
# === 並列関数 ===
# spawn マーカー付きの関数
fetch_data: (url: String) -> JSON spawn = {
    return HTTP.get(url).json()
}

# === 並列ブロック ===
# spawn { } 内の式は強制的に並行実行
compute_all: () -> (Int, Int, Int) spawn = {
    (a, b, c) = spawn {
        heavy_calc(1),    # 任務 1
        heavy_calc(2),    # 任務 2
        another_calc(3)   # 任務 3
    }
    return (a, b, c)
}

# === 自動待機 ===
main: () -> Void = {
    # 2つの独立リクエストは自動的に並行実行
    users = fetch_data("https://api.example.com/users")
    posts = fetch_data("https://api.example.com/posts")

    # 待機点は結果が必要な時に自動的に挿入
    print(users.length + posts.length)  # users と posts を自動的に待機
}
```

**スレッド安全**：

```yaoxiang
# ref キーワードはスレッド安全を自動処理（コンパイラが自動的に Rc/Arc を選択）
main: () -> Void = {
    counter = ref SafeCounter(0)

    # タスク間共有：コンパイラが自動的に Arc を選択
    spawn {
        counter.increment()
    }
    spawn {
        counter.increment()
    }
}
```

**技術文書**：

- 詳細 [RFC-001 並列実行モデル](./rfc/deprecated/001-concurrent-model-error-handling.md)

**革新価値**：非同期プログラミングの認知負荷がゼロに、コード可読性は同期コードと完全に同じ、同時に高性能並行実行の効率を得る。

### 3.5 革新五：値依存型（RFC-011）

> **状態**：設計中、部分実装

型は値に依存でき、真の型駆動開発を実現する。

```yaoxiang
# 行列型：次元はコンパイル時に確定
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
}

# コンパイル時計算：factorial(3) = 6
arr: Array(Int, factorial(3)) = Array(Int, 6)()

# コンパイル時次元検証
identity_3x3: Matrix(Float, 3, 3) = identity(Float, 3)(3)
# multiply(matrix_2x3, matrix_4x2)  # コンパイルエラー：次元の不一致
```

**革新価値**：コンパイル時により多くのエラーを捕获し、より正確な型保証を実現。

### 3.6 革新六：極限まで精简されたキーワード設計

YaoXiang はわずか17個のコアキーワードを定義し、その数は主流言語よりはるかに少ない：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

| 比較対象言語 | キーワード数 |
| ---------- | ---------- |
| YaoXiang   | **17**     |
| Rust       | 51+        |
| Python     | 35         |
| TypeScript | 64+        |
| Go         | 25         |

**革新価値**：より低い記憶負担、より一貫した構文スタイル、より解析しやすい構文構造。

### 4.2 型定義と関数

```yaoxiang
# 統一型構文：name: type = value

# レコード型
Point: Type = { x: Float, y: Float }

# ジェネリック型
Option: (T: Type) -> Type = {
```

```yaoxiang
classify: (n: Int) -> String = {

        _ if n < 0 -> "negative",
        _ -> "positive",

# 分解パターン
Point: Type = { x: Float, y: Float }
match point {
```

### 4.4 所有権モデル（RFC-009 v9）

```yaoxiang
Point: Type = { x: Float, y: Float }

# デフォルト Move（ゼロコピー）
p1 = Point(1.0, 2.0)
p2 = p1              # Move、p1 はこれ以上読めない

# &T / &mut T トークン（コンパイル時ゼロオーバーヘッド）
p2.print()           # コンパイラが自動的に &Point トークンを作成
p2.shift(1.0, 1.0)  # コンパイラが自動的に &mut Point トークンを作成

# ref：共有所有（コンパイラが自動的に Rc/Arc を選択）
shared = ref p2      # スコープ間共有

# clone()：明示的ディープコピー
backup = p2.clone()

# unsafe + 生ポインタ：システムレベル
unsafe {
    ptr: *Point = &p2
    (*ptr).x = 0.0
}
```

**所有権グラジェント**：

```
&T / &mut T    Move       ref        clone()    unsafe
    |             |          |           |          |
借用トークン     デフォルト   共有所有     ディープコピー  生ポインタ
ゼロコスト       ゼロコピー   自動Rc/Arc   明示的      システムレベル
```

## 付録C：よくある質問

**Q: YaoXiang は Rust と比較してどのような優位性がありますか？**

A:
YaoXiang は Rust のメモリ安全とゼロコスト抽象を保持するが、よりシンプルな構文とより低い認知負荷を採用している。**並列実行モデル**は Rust の `async/await` より簡潔である——1つの `spawn` マーカーのみ必要で、Future と Pin を手動管理する必要がない。「万物並作，吾以観復」、並行プログラミングを自然法則を記述するように直感的に行える。**所有権モデル**（RFC-009 v9）はライフタイム注釈の代わりに Move + &T/&mut T トークンを使用し、ボローチェッカーの代わりに型属性（Dup/Linear）を使用する。統一型構文は `enum`/`struct`/`trait`/`impl` のコンセプトの断片化を消除する。

**Q: YaoXiang はどのような種類の開発に適していますか？**

A: システムプログラミング、アプリケーション開発、Web サービス、スクリプトツール、AI 支援プログラミング。目標は универсальная プログラミング言語になることである。

**Q: なぜ4スペースインデントを選んだのですか？**

A:
4スペースは明確なコードブロックの視覚的区切りを提供し、ネスト深度の増加带来的混乱减少。これは熟考された「AI 対応」設計の決定である。

**Q: 1.0 バージョンはいつリリースされますか？**

A: v1.0 目標：プロダクション対応。リリース時間は実装進捗に依存し、詳細 [バージョン計画 RFC](./rfc/rejected/003-version-planning.md) を参照。

**Q: コアチームにはどのように連絡できますか？**

A: GitHub Discussions または Discord コミュニティチャネルを通じて。コアチームメンバーは定期的に返信する。
