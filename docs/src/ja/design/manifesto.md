## 一、なぜ YaoXiang を作るのか？

### 1.1 埋める言語の空白

プログラミング言語の歴史の長い川の中で、数多くの優れた言語の誕生と進化を目の当たりにしてきた。C 言語はシステムプログラミングの効率革命をもたらし、Python は誰もが学べるプログラミング体験を生み出し、Rust はメモリ安全性と性能が両立できることを証明し、TypeScript は大規模なフロントエンドプロジェクトを保守可能にした。しかし、今日の言語エコシステムを検証すると、依然として明らかな断層地帯が存在する——**以下の3つの核心的ニーズを同時に満たす言語は一つとしてない**。

| ニーズ              | 既存ソリューションの問題                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **型安全**          | Rust は厳格すぎ、学習曲線が急峻；TypeScript はオプショナル型であり、実行時保証を提供できない                      |
| **自然な構文**      | Rust は構文が複雑で難解；Haskell は関数型の敷居が高すぎる；従来の静的言語は冗長で煩雑                             |
| **AI フレンドリー** | 既存言語は構文の曖昧性が多く、AST が複雑で、隠れた挙動が予測しにくく、AI によるコード生成と修正の精度が制限される |

YaoXiang の誕生は、まさにこの空白を埋めるためである。私たちはこう信じている：**プログラミング言語は、強力で親しみやすく、安全で効率的、厳密で優雅であるべきである**。

### 1.2 解決する実際的な問題

**問題一：型システムの断片化**

今日のプログラミング言語は型システムにおいて深刻な断片化を示している。静的型付け言語は実行時の絶対的な正確性を追求するが、それは往々にして開発効率を犠牲にすることで達成される；動的型付け言語は柔軟性を提供するが、大規模プロジェクトでは保守困難な欠陥が露呈する。YaoXiang は「すべては型である」という統一的な抽象フレームワークを提案し、型を言語設計を貫く主軸とし、事後的に追加されたパッチではなくする。

**問題二：メモリ安全性と性能の二者択一**

長らく、開発者はメモリ安全性と実行性能の間の難しい選択を迫られてきた。GC（ガベージコレクション）は開発者を解放するが、レイテンシの変動とメモリオーバーヘッドをもたらす；手動メモリ管理は効率的だが、綱渡りと同様に危険である。YaoXiang は Rust スタイルの所有権モデルを採用し、実行時にデータ競合とメモリリークを排除しつつ、ゼロコスト抽象を維持し、GC なしで高性能を実現する。

**問題三：非同期プログラミングの認知負荷**

現代のアプリケーションはネットワークと並列処理から切り離せないが、非同期プログラミングは常にプログラマーの悪夢であった。コールバック関数のネスト、Promise のチェーン呼び出し、async/await 構文——どの方式もコードの複雑性を増大させる。YaoXiang は非同期モデルを再設計した：関数シグネチャの後に
`spawn`
マーカーを追加するだけで、コンパイラがすべての非同期の詳細を自動的に処理し、並行プログラミングを同期コードのように自然にする。

**問題四：AI 支援プログラミングのボトルネック**

AI が開発者のコード作成を支援し始めたとき、言語設計の選択が極めて重要になる。曖昧な構文規則、暗黙的な型変換、複雑な構文糖——これらは人間プログラマーがすでに慣れた特性であるが、AI の理解と生成の障害となる。YaoXiang は設計当初から「AI フレンドリー」を中核目標とする：厳格なインデント規則、明確なコードブロック境界、曖昧性のない構文構造により、AI がコードを正確に理解、生成、修正できるようにする。

### 1.3 言語の哲学的基盤

YaoXiang の名称は『易経』の「爻」と「象」に由来する。「爻」は卦象を構成する基本記号であり、陰陽の変化、動静の相生を象徴する；「象」は事物の本質外在する外在表現であり、万象万物を包括することを表す。

この哲学的思想は言語設計のすべての細部に体现される：

- **統一性**：爻卦の簡単な記号が複雑な卦象を構成するように、YaoXiang は少数の核心概念（型、関数、コンストラクタ）で完全なプログラミングモデルを構築する
- **階層性**：象に先天後天之分があるように、YaoXiang の型システムは明確な階層構造を持ち、原型から総称型、値からメタ型に至る
- **可変性**：陰陽が流転し変化无穷であるように、YaoXiang は依存型をサポートし、型の値による変化に応じた進化を可能にする
- **識別性**：卦象が解け万物に象があるように、YaoXiang は完全な型リフレクション能力を提供し、実行時の型情報は完全に利用可能である
- **証明可能性**：卦象が事物の法則を明らかにするように、YaoXiang の型システムは Curry-Howard 同型（型は命題、プログラムは証明）に従い、型検査のプロセスは論理証明の検証である

## 二、核心哲学と原則

以下の設計信条は YaoXiang の礎であり、**譲歩できず、违背できない**。あらゆる特性提案はこれらの原則の検証を経なければならない。

### 2.1 原則一：すべては型である

YaoXiang の世界観において、型は最高層の抽象ユニットであり、言語を貫く中核概念である。

**具体的な体现**：

- **値は型のインスタンス**：`42` は `Int` 型のインスタンス、`"hello"` は `String` 型のインスタンス
- **型自身も型である**：`Type` は言語唯一のメタ型キーワードであり、`Int` の型は `Type`
- **関数は型写像**：`add: (a: Int, b: Int) -> Int` は `Int × Int` から `Int` への型写像を記述する
- **モジュールは型の組み合わせ**：モジュールは関数と型を含む名前空間の組み合わせである

**譲歩できない理由**：統一された型抽象は言語意味論を簡素化し、値と型の二元対立を排除し、型システムをコード正しさの守護者とし、障害物としない。

### 2.2 原則二：厳格な構造化

YaoXiang の構文設計は「曖昧性なし、予測可能、解析容易」を追求する。

**具体的な規則**：

- **強制 4 スペースインデント**：タブ文字の使用を禁止し、コードブロックの境界が一目で分かる
- **括弧は省略不可**：関数の引数は括弧が必須、リストの要素にはコンマが必須
- **コードブロックには波括弧が必須**：`if`、`while`、`for` などの制御フローは `{ }` で囲む必要がある
- **キーワード数は精简**：17 個の核心キーワードのみを保持し、構文糖の滥造を拒否

**譲歩できない理由**：厳格な構造化は三つの重要な利点をもたらす——（1）IDE の構文ハイライトとコード折りたたみがより正確になる；（2）AI によるコード生成と修正の精度が大幅に向上する；（3）新しい学習者がコード構造を迅速に理解できる。

### 2.3 原則三：ゼロコスト抽象

高水準の抽象は実行時のパフォーマンスオーバーヘッドをもたらすべきではない。

**具体的な保証**：

- **単態化**：総称関数はコンパイル時に具体的なバージョンに展開され、仮想表の検索オーバーヘッドがない
- **インライン最適化**：単純な関数は自動的にインライン化され、関数呼び出しのオーバーヘッドが排除される
- **スタック割り当て優先**：小さなオブジェクトはデフォルトでスタックに割り当てられ、ヒープ割り当ては必要な場合にのみ使用される
- **GC なし**：所有権モデルがメモリ安全性を保証し、ガベージコレクターの実行時オーバーヘッドが不要

**譲歩できない理由**：性能はプログラミング言語の生存底线である。利便性と引き換えに性能を犠牲にするあらゆる設計は、プログラマーへの背信である。

### 2.4 原則四：デフォルト不変

可変性と複雑性は切っても切れない関係にある。YaoXiang はデフォルトを不変とし、コードをより推論しやすく理解しやすくする。

**具体的な規則**：

- 変数はデフォルトで不変、代入後に再変更不可
- 可変にする場合は明示的に `mut` を宣言する必要がある
- 参照はデフォルトで不変、可変参照には `mut` マーカーが必要
- 所有権の移動は元のバインディングを無効化する

**譲歩できない理由**：不変性は並行安全性の基礎であり、コード可読性の保障であり、関数型プログラミングの知恵の結晶である。

### 2.5 原則五：型はデータである

型情報はコンパイル時にのみ存在するべきではなく、実行時にも完全に利用可能であるべきである。

**具体的な能力**：

- 実行時の型クエリ：あらゆる値はその型情報を取得できる
- 型リフレクション：型自体を構築および操作できる
- パターンマッチによる分解：型コンストラクタは直接パターンマッチに使用可能
- 総称特化：実行時に総称パラメータの具現化された型を取得可能

**譲歩できない理由**：完全な型リフレクション能力はメタプログラミングの基礎であり、高性能フレームワークとツールの礎である。

## 三、核心的革新と特性

YaoXiang は既存言語の優れた特性を吸収しつつ、以下の革新的な設計を提案する。

### 3.1 革新一：統一型構文

**従来の言語の型定義**は往々にして複数のキーワードを必要とする：

```rust
// Rust
struct Point { x: f64, y: f64 }
enum Result<T, E> { Ok(T), Err(E) }
enum Color { Red, Green, Blue }
trait Drawable { fn draw(&self, s: &Surface); }
```

**YaoXiang の統一構文**：すべては `name: type = value` であり、`Type`
は唯一のメタ型キーワードである。

```yaoxiang
# === レコード型 ===

Point: Type = {
    x: Float,
    y: Float,
}

# デフォルト値を持つフィールド
Point3D: Type = {
    x: Float = 0,
    y: Float = 0,
    z: Float = 0,
}

# === 総称型 ===

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

# === インターフェース（フィールドがすべて関数型のレコード） ===

Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect,
}

Serializable: Type = {
    serialize: () -> String,
}

# === インターフェース実装（インターフェース名は型本体内に記述） ===

Point: Type = {
    x: Float,
    y: Float,
    Drawable,
    Serializable,
}

# === メソッド（Type.method 構文） ===

Point.draw: (self: &Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}
```

**革新的価値**：`fn`、`struct`、`enum`、`trait`、`impl`
キーワードの断片化なし——統一された一つの構文がすべての宣言をカバーする。

### 3.2 革新二：コンストラクタは型である

**値構築と関数呼び出しは完全に同一**：

```yaoxiang
# 型定義
Point: Type = { x: Float, y: Float }
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

# 値構築：関数呼び出しと同じ
p: Point = Point(3.0, 4.0)
opt: Option(Int) = Option.some(42)
none: Option(Int) = Option.none()

# パターンマッチ：直接分解
match opt {
    Option.some(value) -> print(value)
    Option.none -> print("nothing")
}
```

### 3.3 革新三：カリー化メソッドバインディング

YaoXiang は純粋関数型設計を採用し、カリー化によりオブジェクトメソッド呼び出しに類似した構文糖を実現し、`class`
や `method` キーワードを導入する必要がない。

```yaoxiang
# === 型定義 ===

Point: Type = {
    x: Float,
    y: Float,
}

# 核心関数：ユークリッド距離
distance: (a: Point, b: Point) -> Float = {
    dx = a.x - b.x
    dy = a.y - b.y
    return (dx * dx + dy * dy).sqrt()
}

# メソッド構文糖バインディング（[0] は第 0 引数位置へのバインディングを示す）
Point.distance = distance[0]

# === 使用 ===

p1 = Point(3.0, 4.0)
p2 = Point(1.0, 2.0)

# 二つの呼び出し方式は完全に等価
d1 = distance(p1, p2)     # 核心関数の直接呼び出し
d2 = p1.distance(p2)      # メソッド構文糖

# カリー化用法
dist_from_p1 = p1.distance  # 部分適用、二番目の引数を待つ
d3 = dist_from_p1(p2)       # 2.828
```

**革新的価値**：純粋関数型設計、隠れた `self` 引数なし、関数は値として自由に受け渡しと合成が可能。

### 3.4 革新四：spawn モデル

> 「万物并作、吾以観復」—— 『易・復卦』
>
> spawn モデルはこれにちなみ、プログラミングパラダイムを記述する：開発者は同期・逐次の思考でロジックを記述し、言語ランタイムはその中の計算ユニットを万物が並作するように自動的かつ高效に並行実行させ、最終的に統一的に協調させる。

**核心三原則**：

| 原則         | 説明                                         |
| ------------ | -------------------------------------------- |
| **同期構文** | 見たままの逐次コード                         |
| **並行本質** | ランタイムが自動的に並列性を抽出             |
| **統一協調** | 結果は必要時に自動収束し、論理の正しさを保証 |

**用語体系**：

| 公用語                 | 対応構文                     | 説明                                                              |
| ---------------------- | ---------------------------- | ----------------------------------------------------------------- |
| **spawn 関数**         | `spawn (params) => body`     | spawn 実行に参加可能な計算ユニットを定義                          |
| **spawn ブロック**     | `spawn { a(), b() }`         | 明示的に宣言された並行領域、ブロック内のタスクは spawn 実行される |
| **spawn ループ**       | `spawn for x in xs { ... }`  | データ並列、ループ本体はすべての要素上で spawn 実行される         |
| **spawn 値**           | `Async(T)`                   | spawn 進行中の未来値、使用時に自動待機                            |
| **spawn グラフ**       | 遅延計算グラフ(DAG)          | spawn 発生の舞台、依存関係と並列関係を記述                        |
| **spawn スケジューラ** | ランタイムタスクスケジューラ | 万物を協調させ、正しいタイミングで spawn させる智能中枢           |

> **詳細**：[RFC-001 spawn モデル](./rfc/001-concurrent-model-error-handling.md)

```yaoxiang
# === spawn 関数 ===
# spawn でマークされた関数
fetch_data: (url: String) -> JSON spawn = {
    return HTTP.get(url).json()
}

# === spawn ブロック ===
# spawn { } 内の式は強制的に並列実行される
compute_all: () -> (Int, Int, Int) spawn = {
    (a, b, c) = spawn {
        heavy_calc(1),    # タスク 1
        heavy_calc(2),    # タスク 2
        another_calc(3)   # タスク 3
    }
    return (a, b, c)
}

# === 自動待機 ===
main: () -> Void = {
    # 二つの独立したリクエストが自動的に並列実行される
    users = fetch_data("https://api.example.com/users")
    posts = fetch_data("https://api.example.com/posts")

    # 待機点は結果を必要とするときに自動挿入される
    print(users.length + posts.length)  # users と posts を自動待機
}
```

**スレッド安全性**：

```yaoxiang
# ref キーワードがスレッド安全性を自動処理（コンパイラが Rc/Arc を自動選択）
main: () -> Void = {
    counter = ref SafeCounter(0)

    # タスク間共有：コンパイラが自動的に Arc を選択
    spawn {
        counter.increment()
    }
    spawn {
        counter.increment()
    }
}
```

**技術文書**：

- 詳細は [RFC-001 spawn モデル](./rfc/accepted/001-concurrent-model-error-handling.md) を参照

**革新的価値**：非同期プログラミングの認知負荷がゼロになり、コード可読性は同期コードと完全に同じでありながら、高性能並列実行効率を獲得する。

### 3.5 革新五：値依存型（RFC-011）

> **ステータス**：設計中、一部実装済み

型は値に依存可能で、真の型駆動開発を実現する。

```yaoxiang
# 行列型：次元はコンパイル時に確定
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
}

# コンパイル時計算：factorial(3) = 6
vec: Vec(factorial(3)) = Vec(6)()

# コンパイル時次元検証
identity_3x3: Matrix(Float, 3, 3) = identity(Float, 3)(3)
# multiply(matrix_2x3, matrix_4x2)  # コンパイルエラー：次元不一致
```

**革新的価値**：コンパイル時により多くのエラーを捕捉し、より精確な型保証を実現。

### 3.6 革新六：極簡キーワード設計

YaoXiang はわずか 17 個の核心キーワードのみを定義し、その数は主流言語をはるかに下回る：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

| 比較言語   | キーワード数 |
| ---------- | ------------ |
| YaoXiang   | **17**       |
| Rust       | 51+          |
| Python     | 35           |
| TypeScript | 64+          |
| Go         | 25           |

**革新的価値**：より低い記憶负担、より一貫した構文スタイル、より解析容易な構文構造。

### 4.4 所有権モデル（RFC-009 v9）

```yaoxiang
Point: Type = { x: Float, y: Float }

# デフォルト Move（ゼロコピー）
p1 = Point(1.0, 2.0)
p2 = p1              # Move、p1 はもう読み取れない

# &T / &mut T トークン（コンパイル時ゼロコスト）
p2.print()           # コンパイラが自動的に &Point トークンを作成
p2.shift(1.0, 1.0)  # コンパイラが自動的に &mut Point トークンを作成

# ref：共有保有（コンパイラが自動的に Rc/Arc を選択）
shared = ref p2      # スコープを跨いで共有

# clone()：明示的なディープコピー
backup = p2.clone()

# unsafe + 生ポインタ：システムレベル
unsafe {
    ptr: *Point = &p2
    (*ptr).x = 0.0
}
```

**所有権グラデーション**：

```
&T / &mut T    Move       ref        clone()    unsafe
    |             |          |           |          |
借用トークン     デフォルト  共有保有    ディープコピー  生ポインタ
ゼロコスト       ゼロコピー  自動Rc/Arc  明示的       システムレベル
```

## 付録C：よくある質問

**Q: YaoXiang は Rust と比較してどのような利点がありますか？**

A:
YaoXiang は Rust のメモリ安全性とゼロコスト抽象を保持しつつ、より簡潔な構文とより低い認知負荷を採用している。**spawn モデル**は Rust の
`async/await` より簡潔で——一つの `spawn`
マークのみが必要で、Future と Pin を手動管理する必要がない。「万物并作、吾以観復」、並行プログラミングを自然の法則を記述するように直感的にする。**所有権モデル**（RFC-009
v9）は Move + &T/&mut
T トークンでライフタイム注釈を置き換え、型属性（Duplicate/Linear）で借用チェッカーを置き換える。統一型構文が
`enum`/`struct`/`trait`/`impl` の概念断片化を排除する。

**Q: YaoXiang はどのような種類の開発に適していますか？**

A: システムプログラミング、アプリケーション開発、Web サービス、スクリプティングツール、AI 支援プログラミング。汎用プログラミング言語になることが目標。

**Q: なぜ 4 スペースインデントを選択したのですか？**

A:
4 スペースは明確なコードブロック視覚的分離を提供し、ネストの深さによる混乱を減らす。これは深思熟慮された「AI フレンドリー」設計決定である。

**Q: いつ 1.0 バージョンがリリースされますか？**

A: v1.0 目標：プロダクション使用可能。リリース時期は実装进度に依存、詳細は
[バージョン計画 RFC](./rfc/003-version-planning.md) を参照。

**Q: コアチームに連絡するにはどうすればよいですか？**

A: GitHub
Discussions または Discord コミュニティチャンネル経由。コアチームメンバーが定期的に返信する。
