## 一、なぜYaoXiangを創造するのか？

### 1.1 言語の空白を埋める

プログラミング言語の歴史の長い流れの中で、数え切れないほどの優れた言語の誕生と進化を目の当たりにしてきた。C言語はシステムプログラミングの効率革命をもたらし、Pythonは誰もが学べるプログラミング体験を創出し、Rustはメモリ安全性とパフォーマンスの両立を証明し、TypeScriptは大規模フロントエンドプロジェクトを保守しやすくした。しかし、今日の言語エコシステムを审视すると、明らかな断層地帯が依然として存在する——**いかなる言語も以下の3つの核心的要求を同時に満たすことはできない**：

| 要求                | 既存ソリューションの問題                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **型安全性**        | Rustは厳しすぎ、学習曲線が急峻である；TypeScriptはオプション型であり、コンパイル時の保証を提供できない            |
| **自然な構文**      | Rustの構文は複雑で難解；Haskellの関数型は敷居が高い；従来の静的言語は冗長で煩雑                                   |
| **AI フレンドリー** | 既存言語は構文の曖昧性が多く、ASTが複雑で、隠れた挙動の予測が難しく、AIによるコード生成と修正の正確率が制限される |

YaoXiangの誕生は、まさにこの空白を埋めるためである。我々は信じる：**プログラミング言語は強力で親しみやすく、安全で効率的、厳密で優雅であるべきである**。

### 1.2 解決する実際的問題

**問題一：型システムの断片化**

今日のプログラミング言語は型システムにおいて深刻な断片化を示している。静的型付き言語はコンパイル時の絶対的な正しさを追求するが、往々にして開発効率を犠牲にすることでそれを得る；動的型付き言語は柔軟性を提供するが、大規模プロジェクトでは保守困難な欠陥が露呈する。YaoXiangは「すべてが型」という統一抽象フレームワークを提起し、型を言語設計の主軸として貫かせ、事後的なパッチではなくする。

**問題二：メモリ安全性とパフォーマンスの二者択一**

长期以来、開発者はメモリ安全性と実行性能の間で難しい選択を迫られてきた。GC（ガベージコレクション）は開発者を解放するが、遅延の変動とメモリオーバーヘッドをもたらす；手動メモリ管理は効率的だが、綱渡りのように危険である。YaoXiangはRustスタイルの所有権モデルを採用し、コンパイル時にデータ競合とメモリリークを排除しつつ、ゼロコスト抽象を維持し、GCを必要とせず高性能を実現する。

**問題三：非同期プログラミングの認知的負担**

現代アプリケーションはネットワークと並列性を欠かすことができないが、非同期プログラミングは常にプログラマーの悪夢であった。コールバック関数の入れ子、Promiseチェーン呼び出し、async/await構文——どのソリューションもコードの複雑性を増加させる。YaoXiangは非同期モデルを再設計した：関数シグネチャの後に`spawn`マーカーを追加するだけで、コンパイラがすべての非同期の詳細を自動的に処理し、並行プログラミングを同期コードと同じように自然にする。

**問題四：AI支援プログラミングのボトルネック**

AIが開発者のコード記述を補助し始めたとき、言語設計の選択は極めて重要になる。曖昧な構文ルール、暗黙の型変換、複雑な糖衣構文——これらは人間のプログラマーがすでに慣れた特性であるが、AIが理解し生成する障害となる。YaoXiangは設計の初期段階から「AI フレンドリー」を核心目標とする：厳格なインデントルール、明示的なコードブロック境界、曖昧さのない構文構造により、AIがコードを正確に理解し、生成し、修正できるようにする。

### 1.3 言語の哲学的根基

YaoXiangという名は『易経』の「爻」と「象」に由来する。「爻」は卦象を構成する基本記号であり、陰陽の変化、動静の相生の象徴である；「象」は事物の本質の外在的表現であり、万象万物、ありとあらゆるものを代表する。

この哲学的思想は言語設計の細部一つ一つに体现されている：

- **統一性**：爻卦の単純な記号が複雑な卦象を構成するように、YaoXiangは少数の核心概念（型、関数、コンストラクタ）で完全なプログラミングモデルを構築する
- **階層性**：象に先天と后天の区別があるように、YaoXiangの型システムは明確な階層構造を持ち、primitive型からジェネリクス、値からメタ型まで及ぶ
- **変化性**：陰陽が流転し変化无穷であるように、YaoXiangは依存型をサポートし、型の値に伴う進化を可能にする
- **識別可能性**：卦象が解釈でき万物が象徴できるように、YaoXiangは完全な型リフレクション能力を提供し、実行時の型情報は完全に利用可能である
- **証明可能性**：卦象が事物の法則を明らかにするように、YaoXiangの型システムはカリー＝ハワード同型対応（型は命題、プログラムは証明）に従い、型検査の過程が論理的証明の検証である

## 二、核心哲学と原則

以下の設計信条はYaoXiangの礎であり、**妥協不可、違反不可**である。いかなる特性提案もこれらの原則による検査を経なければならない。

### 2.1 原則一：すべてが型

YaoXiangの世界観において、型は最高層の抽象ユニットであり、言語を貫く核心概念である。

**具体的な体现**：

- **値は型のインスタンス**：`42`は`Int`型のインスタンス、`"hello"`は`String`型のインスタンスである
- **型自身も型である**：`Type`は言語唯一のメタ型キーワードであり、`Int`の型は`Type`である
- **関数は型写像**：`add: (a: Int, b: Int) -> Int`は`Int × Int`から`Int`への型写像を記述する
- **モジュールは型の組み合わせ**：モジュールは関数と型を含む名前空間の組み合わせである

**妥協不可の理由**：統一された型抽象は言語の意味論を簡素化し、値と型の二元対立を排除し、型システムをコードの正しさの守護者とし、障害としない。

### 2.2 原則二：厳格な構造化

YaoXiangの構文設計は「曖昧さなし、予測可能、解析容易」を追求する。

**具体的なルール**：

- **強制4スペースインデント**：タブ文字の使用を禁止し、コードブロックの境界を一目瞭然とする
- **括弧の省略不可**：関数の引数は括弧が必須、リストの要素にはカンマが必須
- **コードブロックには波括弧が必須**：`if`、`while`、`for`などの制御フローは`{ }`で囲むことが必須
- **キーワード数の簡素化**：17個の核心キーワードのみを保持し、糖衣構文の氾濫を拒否する

**妥協不可の理由**：厳格な構造化は3つの重要な利点をもたらす——（1）IDEのシンタックスハイライトとコード折りたたみがより正確になる；（2）AIによるコード生成と修正の正確率が大幅に向上する；（3）新しい学習者がコード構造を迅速に理解できる。

### 2.3 原則三：ゼロコスト抽象

高水準の抽象は実行時のパフォーマンスオーバーヘッドをもたらすべきではない。

**具体的な保証**：

- **単相化**：ジェネリック関数はコンパイル時に具象バージョンに展開され、仮想テーブル検索のオーバーヘッドがない
- **インライン化**：単純な関数は自動的にインライン化され、関数呼び出しのオーバーヘッドが排除される
- **スタック割り当て優先**：小さなオブジェクトはデフォルトでスタックに割り当てられ、ヒープ割り当ては必要な場合にのみ使用される
- **GCなし**：所有権モデルによりメモリ安全性が保証され、ガベージコレクタの実行時オーバーヘッドが不要

**妥協不可の理由**：パフォーマンスはプログラミング言語の生存の底线である。利便性のためにパフォーマンスを犠牲にするいかなる設計もプログラマーへの裏切りである。

### 2.4 原則四：デフォルト不変

可変性と複雑性は切っても切れない。YaoXiangはデフォルト不変を選択し、コードを推論と理解しやすくする。

**具体的なルール**：

- 変数はデフォルトで不変であり、代入後に再変更できない
- 可変が必要な場合は明示的に`mut`を宣言しなければならない
- 参照はデフォルトで不変であり、可変参照には`mut`マーカーが必要
- 所有権の移転は元の束縛が無効になることを意味する

**妥協不可の理由**：不変性は並行安全性の基礎であり、コード可読性の保障であり、関数型プログラミングの知恵の結晶である。

### 2.5 原則五：型はデータである

型情報はコンパイル時にのみ存在するべきではなく、実行時に完全に利用可能であるべきである。

**具体的な能力**：

- 実行時型クエリ：任意の値はその型情報を取得できる
- 型リフレクション：型自体を構築および操作できる
- パターンマッチング分解：型コンストラクタは直接パターンマッチングに使用できる
- ジェネリクス特殊化：実行時にジェネリックパラメータの実体化された型を取得できる

**妥協不可の理由**：完全な型リフレクション能力はメタプログラミングの基礎であり、高性能フレームワークとツールの礎石である。

## 三、重要な革新と特性

YaoXiangは既存言語の優れた特性を吸収しつつ、以下の革新的な設計を提起する。

### 3.1 革新一：統一型構文

**従来の言語の型定義**は往々にして複数のキーワードを必要とする：

```rust
// Rust
struct Point { x: f64, y: f64 }
enum Result<T, E> { Ok(T), Err(E) }
enum Color { Red, Green, Blue }
trait Drawable { fn draw(&self, s: &Surface); }
```

**YaoXiangの統一構文**：すべてが`name: type = value`であり、`Type`は唯一のメタ型キーワードである。

```yaoxiang
# === レコード型 ===

Point: Type = {
    x: Float,
    y: Float,
}

# デフォルト値を持つフィールド
Point3D: Type = {
    x: Float = 0,
    y: Float = 0,
    z: Float = 0,
}

# === ジェネリック型 ===

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

# === インターフェース（フィールドがすべて関数型のレコード） ===

Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect,
}

Serializable: Type = {
    serialize: () -> String,
}

# === インターフェース実装（インターフェース名は型本体内に記述） ===

Point: Type = {
    x: Float,
    y: Float,
    Drawable,
    Serializable,
}

# === メソッド（Type.method構文） ===

Point.draw: (self: &Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}
```

**革新の価値**：`fn`、`struct`、`enum`、`trait`、`impl`キーワードの断片化なし——統一された一つの構文がすべての宣言をカバーする。

### 3.2 革新二：コンストラクタは型である

**値構築と関数呼び出しは完全に同一**：

```yaoxiang
# 型定義
Point: Type = { x: Float, y: Float }
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

# 値構築：関数呼び出しと同じ
p: Point = Point(3.0, 4.0)
opt: Option(Int) = Option.some(42)
none: Option(Int) = Option.none()

# パターンマッチング：直接分解
match opt {
    Option.some(value) -> print(value)
    Option.none -> print("nothing")
}
```

### 3.3 革新三：カリー化メソッドバインディング

YaoXiangは純粋関数型設計を採用し、カリー化によりオブジェクトメソッド呼び出しに類似した糖衣構文を実現し、`class`と`method`キーワードを導入する必要がない。

```yaoxiang
# === 型定義 ===

Point: Type = {
    x: Float,
    y: Float,
}

# 核心関数：ユークリッド距離
distance: (a: Point, b: Point) -> Float = {
    dx = a.x - b.x
    dy = a.y - b.y
    return (dx * dx + dy * dy).sqrt()
}

# メソッド糖衣構文バインディング（[0]は第0引数位置へのバインディングを示す）
Point.distance = distance[0]

# === 使用 ===

p1 = Point(3.0, 4.0)
p2 = Point(1.0, 2.0)

# 二つの呼び出し方法は完全に等価
d1 = distance(p1, p2)     # 核心関数の直接呼び出し
d2 = p1.distance(p2)      # メソッド糖衣構文

# カリー化用法
dist_from_p1 = p1.distance  # 部分適用、二番目の引数を待つ
d3 = dist_from_p1(p2)       # 2.828
```

**革新の価値**：純粋関数型設計、隠れた`self`引数なし、関数すなわち値として自由に受け渡しと合成が可能。

### 3.4 革新四：spawnモデル

> 「万物并作、吾以観復。」——《易・復卦》
>
> spawnモデルはこの言葉に意を取り、プログラミングパラダイムを記述する：開発者は同期的で順序的な思考でロジックを記述し、言語ランタイムがその中の計算ユニットを万物がspawn（並作）するように自動的かつ効率的に並列実行させ、最終的に統一的に協調させる。

**核心三原則**：

| 原則               | 説明                                                         |
| ------------------ | ------------------------------------------------------------ |
| **同期構文**       | 見たものが得られたものの順序通りのコード                     |
| **並行性本質**     | ランタイムが自動的に並列性を抽出する                         |
| **統一された協調** | 結果は必要なときに自動的に集約され、論理の正しさが保証される |

**用語体系**：

| 公的用語              | 対応する構文                 | 説明                                                      |
| --------------------- | ---------------------------- | --------------------------------------------------------- |
| **spawn function**    | `spawn (params) => body`     | spawn実行に参加可能な計算ユニットを定義する               |
| **spawn block**       | `spawn { a(), b() }`         | 明示的に宣言された並行領域、ブロック内のタスクはspawn実行 |
| **spawn loop**        | `spawn for x in xs { ... }`  | データ並列、ループ本体はすべての要素上でspawn実行         |
| **spawn value**       | `Async(T)`                   | 現在spawn中の未来の値、使用時に自動待機                   |
| **spawn graph**       | 遅延計算グラフ(DAG)          | spawnが発生する舞台、依存関係と並列性を記述する           |
| **spawnスケジューラ** | ランタイムタスクスケジューラ | 万物を協調させ、正しい时机にspawnさせる知的中心           |

> **詳細**：[RFC-001 spawnモデル](./rfc/001-concurrent-model-error-handling.md)

```yaoxiang
# === spawn関数 ===
# spawnマーカー付き関数
fetch_data: (url: String) -> JSON spawn = {
    return HTTP.get(url).json()
}

# === spawnブロック ===
# spawn { }内の式は強制的に並列実行される
compute_all: () -> (Int, Int, Int) spawn = {
    (a, b, c) = spawn {
        heavy_calc(1),    # タスク1
        heavy_calc(2),    # タスク2
        another_calc(3)   # タスク3
    }
    return (a, b, c)
}

# === 自動待機 ===
main: () -> Void = {
    # 二つの独立したリクエストは自動的に並列実行される
    users = fetch_data("https://api.example.com/users")
    posts = fetch_data("https://api.example.com/posts")

    # 待機点は結果を必要とするときに自動的に挿入される
    print(users.length + posts.length)  # usersとpostsを自動待機
}
```

**スレッド安全性**：

```yaoxiang
# refキーワードがスレッド安全性を自動処理（コンパイラがRc/Arcを自動選択）
main: () -> Void = {
    counter = ref SafeCounter(0)

    # タスク間で共有：コンパイラがArcを自動選択
    spawn {
        counter.increment()
    }
    spawn {
        counter.increment()
    }
}
```

**技術ドキュメント**：

- 詳細：[RFC-001 spawnモデル](./rfc/accepted/001-concurrent-model-error-handling.md)

**革新の価値**：非同期プログラミングの認知的負担がゼロになり、コードの可読性が同期コードと完全に同じでありながら、高性能並列実行の効率を得る。

### 3.5 革新五：値依存型（RFC-011）

> **ステータス**：設計中、一部実装済み

型は値に依存可能であり、真の型駆動開発を実現する。

```yaoxiang
# 行列型：次元がコンパイル時に確定
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
}

# コンパイル時計算：factorial(3) = 6
vec: Vec(factorial(3)) = Vec(6)()

# コンパイル時次元検証
identity_3x3: Matrix(Float, 3, 3) = identity(Float, 3)(3)
# multiply(matrix_2x3, matrix_4x2)  # コンパイルエラー：次元不一致
```

**革新の価値**：コンパイル時により多くのエラーを捕捉し、より精確な型保証を実現する。

### 3.6 革新六：極限まで簡素化されたキーワード設計

YaoXiangは17個の核心キーワードのみを定義し、その数は主流言語を大きく下回る：

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

| 比較言語   | キーワード数 |
| ---------- | ------------ |
| YaoXiang   | **17**       |
| Rust       | 51+          |
| Python     | 35           |
| TypeScript | 64+          |
| Go         | 25           |

**革新の価値**：より低い記憶負担、より一貫した構文スタイル、より解析しやすい構文構造。

### 4.4 所有権モデル（RFC-009 v9）

```yaoxiang
Point: Type = { x: Float, y: Float }

# デフォルトMove（ゼロコピー）
p1 = Point(1.0, 2.0)
p2 = p1              # Move、p1は再読込不可

# &T / &mut T トークン（コンパイル時ゼロオーバーヘッド）
p2.print()           # コンパイラが自動的に&Pointトークンを作成
p2.shift(1.0, 1.0)  # コンパイラが自動的に&mut Pointトークンを作成

# ref：共有所有（コンパイラがRc/Arcを自動選択）
shared = ref p2      # スコープ間で共有

# clone()：明示的なディープコピー
backup = p2.clone()

# unsafe + 生ポインタ：システムレベル
unsafe {
    ptr: *Point = &p2
    (*ptr).x = 0.0
}
```

**所有権グラデーション**：

```
&T / &mut T    Move       ref        clone()    unsafe
    |             |          |           |          |
借用トークン   デフォルト  共有所有    ディープコピー  生ポインタ
ゼロコスト     ゼロコピー  自動Rc/Arc  明示的    システムレベル
```

## 付録C：よくある質問

**Q: YaoXiangとRustを比較した優位性は？**

A:
YaoXiangはRustのメモリ安全性とゼロコスト抽象を保持しつつ、より簡潔な構文とより低い認知的負担を採用している。**spawnモデル**はRustの
`async/await`より簡潔である——単一の`spawn`
マーカーのみが必要で、FutureとPinを手動管理する必要がない。「万物并作、吾以観復」、並行プログラミングを自然法則を記述するように直感的にする。**所有権モデル**（RFC-009
v9）はライフタイム注釈をMove + &T/&mut
Tトークンに置き換え、借用チェッカーを型属性（Duplicate/Linear）に置き換える。統一型構文は
`enum`/`struct`/`trait`/`impl`の概念の断片化を排除する。

**Q: YaoXiangはどのような開発に適しているか？**

A: システムプログラミング、アプリケーション開発、Webサービス、スクリプティングツール、AI支援プログラミング。汎用プログラミング言語となることを目標とする。

**Q: なぜ4スペースインデントを選択するのか？**

A:
4スペースは明確なコードブロック視覚的分離を提供し、ネストの深さによる混乱を減らす。深思熟慮された「AI フレンドリー」設計決定である。

**Q: 1.0バージョンはいつリリースされるか？**

A:
v1.0目標：プロダクション利用可。リリース時期は実装進度による。詳細は[バージョン計画RFC](./rfc/003-version-planning.md)を参照。

**Q: コアチームへの連絡方法は？**

A: GitHub DiscussionsまたはDiscordコミュニティチャンネル経由。コアチームメンバーが定期的に返信する。
