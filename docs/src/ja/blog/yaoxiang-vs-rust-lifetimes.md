# 「`'a`」をコンパイラに隠した

_——YaoXiangの所有権モデルに関する誠実なノート_

---

あなたが初めてこのRustコードを見たとき、本当に理解するまでにどれくらいかかりましたか？

```rust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn advance(&mut self) -> &'a str {
        let start = self.pos;
        self.pos += 1;
        &self.input[start..self.pos]
    }
}
```

「`'a`」が3つ。構造体に1つ、implブロックに2つ。それらは同じことを言っています：`Parser`は借用している`input`より長生きできない。これは正しい。Rustの安全性はこの仕組みの上に成り立っています。

しかし、私たちがこのようなコードを書くとき、よくこう考えます：**このこと、コンパイラ自身では処理できないのだろうか？**
Rustの答えは「できない」——少なくとも借用モデルを変えなければ。

**この記事は「YaoXiangがこの問題を解決した」というものではありません。「YaoXiangは別の道を試している——`'a`をコンパイラに隠し、コンパイラに書かせる。どこまで来て、まだ解決していないhardな問題は何か」という話です。**

---

## Rustがなぜ`'a`を必要とするのか

Rustの`&T`と`&mut T`はポインタです——データを指すポインタです。値を借用するということは、それへの参照を作ることです。この参照には独自のライフタイムがあります。参照が関数の境界を越えて伝播する（戻り値として、構造体に格納される）場合、コンパイラは単一の関数内で参照がどれくらい生きられるかを推論できません。プログラマが`'a`を使って「この戻り値とこの引数はライフタイムを共有する」という情報を提供する必要があります。

Rustコミュニティはそこで止まりませんでした。ライフタイム省略ルールにより、ほとんどの単純な関数は注釈が不要になりました。NLLは2018エディションで導入され、借用の有効範囲が字句スコープに縛られなくなりました。しかし、参照を構造体に格納したり、関数から返したり、クロージャにキャプチャしたりする必要がある場合——**モデル自体が、これらのシナリオではプログラマが参照間の関係を注釈する必要があると定めています。**

---

## 別の見方：借用はポインタではなくトークンである

YaoXiangのコア設計は[RFC-009（所有権モデル）](/design/rfc/accepted/009-ownership-model)に記録されています。デフォルトのセマンティクス（すべてMove）は変えず、**借用の本質**を変えています。

YaoXiangでは、`&T`と`&mut T`は**ポインタではありません**。これらは**ゼロサイズのコンパイル時トークン**——型レベルのアクセス権限の証明です。値を借用するとは、それへのポインタを作るのではなく、「それへのアクセスが許可されている」という証明を作ることです：

```
&T     →  データの不変を保証。Dup（コピー可能）を実装し、複数の読み取り専用トークンの共存は安全
&mut T →  排他的可変を保証。Dupを実装しない（線形）、同じ出所から1つしか持てない
```

Rustでは呼び出し点で`&`を書きます（`distance(&p1, &p2)`）。YaoXiangでは、コンパイラは関数のシグネチャが`&Point`を要求していることを認識し、呼び出し点で自動的にトークンを作成します——呼び出し点は`distance(p1, p2)`になります。代償として、定義者のシグネチャは`&`を宣言する必要があります。そうしないと、デフォルトのMoveが所有権を消費してしまいます：

```yaoxiang
# シグネチャに&が必要——コンパイラが&Pointを見て、呼び出し時に自動的にトークンを作成
check_dimensions: (v: &Vec3) -> Bool = { ... }
check_bounds: (v: &Vec3) -> Bool = { ... }

v = Vec3(1.0, 2.0, 3.0)
if check_dimensions(v) and check_bounds(v) {  # 毎回&Vec3トークンが自動的に作成される
    # vはまだ使用可能
}
```

Rustでは呼び出し点に`&`を書きます；YaoXiangでは定義点に`&`を書きます。注釈が消えたわけではありません——注釈の位置が変わったのです。

## ブランド機構：コンパイラに隠された`'a`

ユーザーはこれに触れることはありません——しかし、YaoXiangが実際に何をしたのかを理解するには、これを理解する必要があります。

コンパイラは内部で、各借用トークンにコンパイル時一意の番号を割り当てます：

```
ユーザーに見えるもの         コンパイラの内部表現
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)
&mut Point     →  WriteToken(Point, #M)
```

`&Point`からフィールドにアクセスして`&Float`を得るとき、後者は派生ブランドを携带します：`#N.field_x`。`&mut`トークンを別の変数にMoveするとき、コンパイラは元の変数がそれを保持していないことを知ります——これはMoveセマンティクスの基礎となる能力です。

**`#N`がすなわち`'a`です。**
プレフィックス関係——`#N`は`#N.field_x`のプレフィックス——がoutlives制約です。同じ情報。Rustのプログラマは`'a`を書き、YaoXiangのコンパイラは`#N`を書きます。

違いは推論の成功率だけです。Rustの省略ルールとNLLは約80%のシナリオをカバーします。YaoXiangの賭けは：**言語設計がコンパイラによりクリーンな入力を与えれば、もっとカバーできるのではないか？**

この賭けはいくつかの言語制約によって支えられています：

- **変数シャドーイングの禁止**——`x`はこのスコープ内で1つの身元しか持たず、コンパイラは「どの`x`のことを言っているのか」を区別する必要がない
- **明示的な`return`**——何がブロックから脱出するかは明示されており、コンパイラは「最後の行が戻り値かどうか」を推論する必要がない
- **`for`は反復ごとに新しいバインディングを作る**——反復間の変数は互いに干渉せず、コンパイラは「前の反復で何が変わったか」を追跡する必要がない

これらは「規範」ではありません。Javaのgetter/setterのような無意味な儀式とは異なり、それぞれのルールは**コンパイラが推論する必要のある情報を、プログラム内に既に書かれている情報に変える**ものです。コンパイラは「どの変数を指しているのか」「これは脱出するかどうか」「ループ変数は反復間でどう変化するか」を推測する必要がありません——答えはコードの中にあります。

## ブランドができること——Rustと同じ

トークンは通常の型であるため、通常の型のすべてのルールに従います。「参照は返せない」「参照は構造体に格納できない」「クロージャは参照をキャプチャできない」という特別な禁止はありません。**しかし、Rustも同じです——Rustは全てできます。**
違いは能力ではなく、誰が注釈を書くかです。

**参照を返す——Rustのプログラマは`'a`を書き、YaoXiangのコンパイラは`#N`を書く：**

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)
}

p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()   # トークンは呼び出し元に伝播し、コンパイラはブランド派生チェーンを追跡する
```

Rustは同じことをしますが、プログラマは入力と出力を接続するために`'a`を書く必要があります。YaoXiangでは、コンパイラはブランドパスによって自動的に派生します——`px_ref`（`#N.field_x`）は`p`（`#N`）から派生します。同じ制約、異なる記録方法。

**構造体が参照を保持する——ライフタイムパラメータなし：**

```yaoxiang
Window: Type = {
    target: Point,
    view: &Point,   # トークンフィールド、他のフィールドと区別なし
}
```

Rustでは構造体に参照フィールドがある場合、`'a`が構造体定義とすべてのimplブロックに現れる必要があります——プログラマは`Window<'a>`のライフタイム制約を明示的に注釈します。YaoXiangでは`view: &Point`に`'a`を書きませんが、ブランド番号はコンパイラ内部で同じ役割を果たします——`Window`インスタンスが破棄されると、内部のトークンも死にます。同じ保証、異なる可視性。

**クロージャのキャプチャ——Dupトークンのゼロコストコピー：**

```yaoxiang
filter_by_threshold: (items: List(Point), threshold: &Float) -> List(Point) = {
    items.filter(|p| p.x > threshold)   # thresholdトークンがクロージャにコピーされる、ゼロオーバーヘッド
}
```

`&Float`はDup（コピー可能）を実装しており、クロージャのキャプチャはゼロサイズの整数をキャプチャするのと同じです。関数呼び出しの自動借用と同じルールを共有します。ユーザーの注釈はゼロです。

## 代償：注釈はシグネチャから消える

Rustの`'a`にはよく言及される価値があります：ドキュメントでもあるということです。`fn split_at_mut<'a>(slice: &'a mut [T], mid: usize) -> (&'a mut [T], &'a mut [T])`——`'a`は読者に、返される2つのスライスが同じ元のデータを参照していることを伝えます。

実際にはこの議論の力は限定的です——ほとんどのRust初心者は`'a`をドキュメントとして読むのではなく、コンパイラが要求するおまじないとしてコピーします。しかし、公平を期すために言えば：複雑な借用シナリオでは、Rustの`'a`は少なくともデータフローを追跡する出発点を提供します。YaoXiangではブランド派生チェーンを理解する必要があります——ブランドはユーザーから見えなく、ツールチェーンに依存しますが、ツールチェーンはまだ成熟していません。

## トークン衝突検出：同じ証明パイプライン

Rustには独立した「借用チェッカー」があります。YaoXiangの**設計方向**は、借用衝突を型検査の証明パイプラインに統合することです（[RFC-027（コンパイル時述語と統一静的検証）](/design/rfc/accepted/027-compile-time-evaluation-types)）。

トークン衝突はホール命題です：

```
{ 衝突するReadTokenは死んでいる } data.push(4) { WriteTokenは安全に取得 }
```

```yaoxiang
# &mut Tは線形型——Move後、元の変数は保持しない
bad: (p: &mut Point) -> Void = {
    p2: &mut Point = p    # WriteTokenがpからp2に転送される
    p.x = 10.0            # { pがWriteTokenを保持 } p.x = 10.0 { 安全 }
}                          # → pのWriteTokenはMove済み → 反証

# &TはDup——コピー可能
good: (p: &Point) -> Void = {
    p2: &Point = p        # 読み取り専用トークンをコピー
    print(p.x)            # OK、2つの読み取り専用トークンは共存可能
}
```

型エラー、述語検証失敗と同じエラーレポートパスを共有します。2つの診断システムを学ぶ必要はありません。**しかし代償として：**
複雑なトークン衝突はRustでは慎重に言い回された借用チェッカーエラーを生成しますが、YaoXiangでは「WriteToken(#7.field_x)がWriteToken(#7)と衝突する」と表現される可能性があります——技術的には正確ですが、ブランド番号は人間の読者にとって意味がありません。エラーメッセージの説明可能性は未検証の領域です。

## `ref`キーワード：Rc/Arcの自動選択

トークンはタスクをまたぐ（スレッドをまたぐ）ことができません——それらはコンパイル時の証明であり、ランタイム値ではありません。スコープをまたぐ共有には`ref`を使用します：

```yaoxiang
shared_data = ref Point(1.0, 2.0)   # コンパイラのエスケープ解析がRcまたはArcを自動選択

spawn {
    print(shared_data.x)   # タスクをまたぐ → コンパイラがArcを選択
}
```

- spawnブロックにエスケープしない → `Rc`（非アトミック参照カウント）
- spawnブロックにエスケープする → `Arc`（アトミック参照カウント）

代償：コードを読む際、ローカルからは`ref`がRcかArcかを知ることができません。1回のリファクタリング（コードをspawnで包む）は参照カウントの実装を密かに変更する可能性があり、コンパイラからの通知はありません。パフォーマンスの変化は暗黙的です。

## 現在のhardな問題：RAIIが粗すぎる

前述したように、トークンは値であり、ライフタイムはRAIIで管理されます。しかし、通常の値のRAIIルールは：**値はスコープが終わるまで生存する。**
これはまさにRustがNLLより前に抱えていた問題です——借用は、あなたがずっと前に使用しなくなった後も、ブロック全体にわたって持続します。

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_view: &Header = data.header()    # &mut Dataから&Headerを派生
    header_info = parse_header(header_view) # ← header_viewの最後の使用
    # header_viewが関数の終わりまで生きる必要はない——
    # しかしRAIIにより}まで生きる

    data.modify(header_info)   # ❌ ReadTokenがまだ「生きて」いるため、WriteTokenがブロックされる
}
```

RustのNLLは字句スコープではなく最後の使用を分析します。YaoXiangにも同じ能力が必要です。現在進行中のソリューションは、トークン活性を証明パイプラインに接続することです——3層：

1. **高速パス**——既存のBorrowCheckerを再利用（線形スキャン、IR命令レベル）。同じ基本ブロック内でトークンの使用が完了するシナリオは直接通過
2. **構造解析**——ブランドツリーのプレフィックス一致（誰が誰と衝突するかを判断）+
   DAGコンシューマクエリ（トークンの最後のコンシューマが現在のノードより後にあるかを判断）
3. **SMTソルバ**——ループ条件など論理推論が必要な場合にのみアクティブ化

証明パイプラインインフラ（`Proved/Disproved/Unproven`の3値返却、Z3
SMTバックエンド、仮説スタック）は`src/frontend/core/typecheck/proof/`に部分的に実装されています。所有権層（`layers/ownership.rs`）はまだスケルトン——直接Provedを返し、実際のチェックは行われていません。現在埋め込み中です。

現在のバージョンのソリューションは、手動でブロックをネストしてトークンスコープを短縮することです：

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_info = {
        header_view: &Header = data.header()
        parse_header(header_view)
    }   # header_viewはブロック終了とともに解放される
    data.modify(header_info)   # ✅
}
```

これは実際の摩擦です。Rustから来た誰もがこれに遭遇します。排除できるかどうかは、パイプラインが所有権層に接続される効果次第です。

## 最も難しい問題：フォールバック

Rustの`'a`は負担であるだけでなく、フォールバックでもあります。コンパイラが推論できない場合、プログラマはライフタイム関係を注釈し、コンパイラが検証します。**あなたにはペンがあります。**

YaoXiangのフォールバックは理論的にはコンパイル時**証明関数**（RFC-027
§4.2）であるべきです：コンパイラの自動導出が失敗 → プログラマが関数を書き、戻り値の型は「トークンが衝突しない」という命題 → コンパイラがその関数の型を検証。しかし——

「トークンが衝突しない」の証明関数はどのような形をしているのでしょうか？ユーザーは型が`WriteTokenAvailable`である値をどのように構築するのでしょうか？ブランド番号`#N`と`#N.field_x`のプレフィックス関係を理解する必要があるのでしょうか？

**もし証明関数がユーザーにブランド番号の理解を要求するなら——私たちは単に`'a`を`#1`と書き換えただけです。何も省けていません。**

この問題にはまだ答えがありません。これは実験全体が最も行き詰まる可能性のある場所です。

## RFC-009の9回の反復

これは象牙の塔で考え出された設計ではありません。RFC-009は9回の大きなバージョンを経ています：

| バージョン | 主な変更点                                                                                                              | 覆された理由                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| v1–v7      | Rustの所有権モデルに基づき、消費解析、逆関数、フィールドレベルの可変性を段階的に追加                                    | 過剰設計、複雑性が制御不能                                     |
| **v8**     | 「質素な借用」——`&T`/`&mut T`は引数としてのみ使用可能、返したり、構造体に格納したり、クロージャにキャプチャしたりは不可 | 3つのハードコードされた禁止。表現力が著しく制限される          |
| **v9**     | 借用トークンシステム——`&T`/`&mut T`は通常の型で、通常のルールに従う                                                     | 特別なルールを排除するが、ブランド追跡をコンパイラ内部に沈める |

v8からv9への跳躍が真のブレークスルーです：3つの禁止から特別なルールゼロへ。しかし、v9が排除したのはユーザーから見えるルールであり、システムの内在的複雑性ではありません——ブランド機構、派生追跡、同源衝突検出、これらは依然として存在し、コンパイラの中に移っただけです。借用チェックを証明パイプラインに統合することは1つの方向ですが、実際のコードで動作するかどうか、フォールバックをどう設計するか——はまだ検証中です。

## 最後に

私たちは`'a`を消滅させていません。`#1`は`'a`です——同じ情報、異なる位置。

実験の賭けは次の通りです：言語設計の制約（シャドーイングの禁止、明示的な`return`、`for`の新しいバインディング、`{}`のDAGセマンティクス）がコンパイラによりクリーンな入力を与え、ブランド導出がRustのライフタイム省略ルールが失敗するほとんどのシナリオで自動的に成功するかもしれない。もし成功すれば——ユーザーは`'a`を書く必要がなく、注釈と省略を区別する必要がなく、借用チェッカーを学ぶ必要がありません。もし失敗すれば——あるいはフォールバック機構（証明関数）がユーザーにブランド番号の理解を要求するなら——それは単に再発明です。

作業中です。結果が出たらまた書きます。
