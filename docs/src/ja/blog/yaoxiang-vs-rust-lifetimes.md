# 私たちは `'a` をコンパイラの中に隠した

_——YaoXiang の所有権モデルに関する正直なメモ_

---

この Rust コードを見て、初めて本当に理解するまでどれくらいかかりましたか？

```rust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn advance(&mut self) -> &'a str {
        let start = self.pos;
        self.pos += 1;
        &self.input[start..self.pos]
    }
}
```

`'a` は3つ。構造体に1つ、impl ブロックに2つ。すべて同じことを言っています： Parser は借用した `input` より長く生きられない。これは正しい。Rust の安全性はこの仕組みの上に成り立っている。

しかし这类コードをを書くとき、いつも一つの念头があります：**このこと、コンパイラ自分で解決できないんですか？**
Rust の答えは「できない」——少なくとも借用モデルを変えない限りは。

**この記事は「YaoXiang がこの問題を解決した」ではありません。「YaoXiang が別の道を試みている——`'a` をコンパイラの中に隠し、コンパイラに代わりに書かせる。今どこにいるか、まだ解決れていないハードルは何か。」です。**

---

## Rust が `'a` を必要とする理由

Rust の `&T` と `&mut T` はポインタ——データへ向けたポインタ。値を借用するとは、それへの参照を作成すること。この参照には自有の生存期間がある。参照が関数境界を越えて传播する場合（返回值として、構造体に格納して）、コンパイラは单个の関数内で参照がどこまで生きられるかを推断できない——プログラム側に「この返回值はこのパラメータと生存期間を共用する」という情報を `'a` で提供してもらう必要がある。

Rust コミュニティはその場に止まらなかった。生存期間省略規則により、多くの简单な関数に标注は不要になった。NLL は 2018 版で導入され、借用は語彙的スコープに縛られなくなった。しかし参照を構造体に格納したい、関数から返回したい、闭包に捕获されたいとき——**モデル自体がこれらのシーンではプログラム側に参照同士の関係を标注してもらわざるを得ない。**

---

## 角度を変える：借用はポインタではなくトークン

YaoXiang のコアデザインは [RFC-009（所有権モデル）](/design/rfc/accepted/009-ownership-model) に記録されている。デフォルトセマンティクス（すべて Move）は変えていない代わりに、**借用の本体**を変えた。

YaoXiang では、`&T` と `&mut T` は**ポインタではない**。它们は**ゼロサイズのコンパイル時トークン**——型レベルのアクセス権限証明。値を借用するとは对它へのポインタを作成することではなく、「私がそれにアクセスする許可を得ている」という証明を作成する：

```
&T     →  データが不変であることを保証。Dup を実装（コピー可能）、複数の読み取り専用トークンの共存が安全
&mut T →  排他的可変であることを保証。Dup を実装しない（線形）、同一ソースから持てるのは一つだけ
```

Rust では调用点に `&` を書く（`distance(&p1, &p2)`）。YaoXiang では、コンパイラが関数シグネチャに `&Point` が必要であることを見ると、调用点に自動的にトークンを作成する——调用点は `distance(p1, p2)` になる。代价は定義者のシグネチャに `&` を宣言しなければならず、さもなくばデフォルトの Move が所有権を食べてしまう：

```yaoxiang
# シグネチャ中に & が必要——コンパイラが &Point を見ると、呼び出し時に自動的にトークンを作成
check_dimensions: (v: &Vec3) -> Bool = { ... }
check_bounds: (v: &Vec3) -> Bool = { ... }

v = Vec3(1.0, 2.0, 3.0)
if check_dimensions(v) && check_bounds(v) {  # 毎回自動的に &Vec3 トークンを作成
    # v は引き続き使用可能
}
```

Rust では调用点に `&` を置く；YaoXiang では定義点に `&` を置く。标注が消えたわけではない——标注の位置が変わっただけだ。

## ブランド機構：コンパイラの中に隠された `'a`

ユーザーはこれに触れない——しかし YaoXiang が何をっているのかを理解するにはこれを理解する必要がある。

コンパイラは内部で各借用トークンにコンパイル時唯一番号を割り当てる：

```
ユーザーが見るもの         コンパイラの内部表現
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)
&mut Point     →  WriteToken(Point, #M)
```

`&Point` からフィールドにアクセスして `&Float` を取得するとき、後者は派生ブランドを持つ：`#N.field_x`。`&mut` トークンを別の変数に Move するとき、コンパイラは元の変数がそれを保持しなくなったことを知っている——これが Move セマンティクスの基礎能力だ。

**`#N` は `'a` だ。** 接頭辞関係——`#N` が `#N.field_x` の接頭辞である——が outlives 制約だ。同一の情報。Rust のプログラム員が `'a` と書き、YaoXiang のコンパイラが `#N` と書く。

違いは推导成功率だけだ。Rust の省略規則と NLL は約 80% のシーンをカバーしている。YaoXiang の赌けは：**もし言語設計がコンパイラによりクリーンな入力を与えられたら、もっと多くをカバーできるだろうか？**

この赌けはいくつかの言語制約に支えられている：

- **変数のシャドウイング禁止**——`x` はこのスコープの中でただ一つのアイデンティティを持つ、コンパイラは「あなたが言っている x はどれか」を区別する必要がない
- **明示的な `return`**——什么东西がブロックから逃げるかは明記されており、コンパイラは「最後の行が返回值かどうか」を推断する必要がない
- **`for` は每次迭代新建绑定**——迭代間の変数は互いを干渉しない、コンパイラは「前回の迭代が何を変えたか」を追踪する必要がない

これらは「仕様」ではない。Java の getter/setter 那种無意味な儀式とは違う——どれも**コンパイラが推断する必要がある情報をプログラムに既に明記されている情報に変える** 것이다。コンパイラは「あなたが指している変数はどれか」、「このものは逃げたか」、「ループ変数が迭代を跨いでどう変わるか」を猜る必要がない——答えはコードの中にある。

## ブランドができること——Rust 同样に

トークンは普通タイプなので、すべて普通タイプのルールに従う。「参照は返回できない」「参照は構造体に格納できない」「闭包は参照を捕获できない」といった特別禁令はない。**しかし Rust 同样に——Rust はすべて能做到る。** 違いは能做到ることではなく、誰が标注を書くかだ。

**参照を返す——Rust のプログラム員は `'a` を書き、YaoXiang のコンパイラは `#N` を書く：**

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)
}

p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()   # トークンが呼び出し元に传播、コンパイラがブランド派生チェーンを追踪
```

Rust が同じことをする、ただプログラム員が `'a` を書いて入出力を結びつける必要がある。YaoXiang ではコンパイラがブランドパスを介して自動的に派生する——`px_ref`（`#N.field_x`）は `p`（`#N`）から派生する。同一の制約、別の記録方式。

**構造体が参照を保持——生存期間パラメータなし：**

```yaoxiang
Window: Type = {
    target: Point,
    view: &Point,   # トークンフィールド、他のフィールドとの違いはない
}
```

Rust では構造体に参照フィールドがある場合、`'a` は構造体定義とすべての impl ブロックに現れる——プログラム員が `Window<'a>` の生存期間制約を明示的に标注する。YaoXiang では `view: &Point` に `'a` を書かないが、ブランド番号はコンパイラの内部で同じ 역할을演じ続けている——`Window` インスタンスが破棄されるとき、内部のトークンもまた死ぬ。同一の保証、別の可视性。

**闭包捕获——Dup トークンのゼロコストコピー：**

```yaoxiang
filter_by_threshold: (items: List(Point), threshold: &Float) -> List(Point) = {
    items.filter(|p| p.x > threshold)   # threshold トークンが闭包内にコピー、ゼロオーバーヘッド
}
```

`&Float` は Dup を実装（コピー可能）なので、闭包把它当成一个零大小的整数来捕获。関数呼び出し時の自動借用と同一のルールを共有している。ユーザーに标注ゼロ。

## 代价：标注がシグネチャから消える

Rust の `'a` にはよくある主張される価値がある：それはドキュメンテーションでもある。`fn split_at_mut<'a>(slice: &'a mut [T], mid: usize) -> (&'a mut [T], &'a mut [T])`——`'a` は读者に二つの返回スライス参照が同一个元データであることを伝えている。

現実にはこの論点の強さは限られている——ほとんどの Rust 初学者は `'a` をドキュメンテーションとして読まず、コンパイラが要求する呪文としてコピーしている。しかし公平に言えば：複雑な借用シーンでは、Rust の `'a` は少なくともデータフローを追跡するスタート地点を与えている。YaoXiang ではブランド派生チェーンを理解する必要がある——ブランドはユーザーには見えない、これはツールチェーンに依存，而ツールチェーンはまだ成熟していない。

## トークン競合検出：同一の証明パイプライン

Rust には独立した「借用検査器」がある。YaoXiang の**設計方向**は借用競合をタイプ検査の証明パイプラインに統一することである（[RFC-027（コンパイル時述語と統合静的検証）](/design/rfc/accepted/027-compile-time-evaluation-types)）。

トークン競合は一条ホーア命題である：

```
{ 競合する ReadToken は死んでいる } data.push(4) { WriteToken は安全に取得可能 }
```

```yaoxiang
# &mut T は線形タイプ——Move 後、元の変数はそれを保持しない
bad: (p: &mut Point) -> Void = {
    p2: &mut Point = p    # WriteToken が p から p2 に转移
    p.x = 10.0            # { p は WriteToken を保持している } p.x = 10.0 { 安全 }
}                          # → p の WriteToken は Move 済み → Disproved

# &T は Dup——コピー可能
good: (p: &Point) -> Void = {
    p2: &Point = p        # 只读トークンをコピー
    print(p.x)            # OK、两个只读トークンは共存可能
}
```

型和错误、述語検証失敗は同一のエラー報告パスを共有している。あなたは2套の診断システムを学ぶ必要がない。**しかし代价は：** 複雑なトークン競合は Rust では丁寧に言い換えられた借用検査エラーを生み出す；YaoXiang では「WriteToken(#7.field_x) conflicts with WriteToken(#7)」のように表示される可能性がある——技術的には正確だが、ブランド番号は人間読者にとって意味がない。错误情報の解釈可能性は尚未検証の分野だ。

## `ref` キーワード：Rc/Arc を自動的に選択

トークンはタスク間（スレッド間）を越えられない——它们はコンパイル時の証明であり、実行時の値ではない。スコープを越えて共有するには `ref` を使う：

```yaoxiang
shared_data = ref Point(1.0, 2.0)   # コンパイラのエスケープ分析が Rc または Arc を自動的に選択

spawn {
    print(shared_data.x)   # タスクを越える → コンパイラは Arc を選択
}
```

- spawn ブロックにエスケープしない → `Rc`（非原子参照カウント）
- spawn ブロックにエスケープする → `Arc`（原子参照カウント）

代价：コードを読むとき、`ref` が Rc か Arc かを局部的に知ることはできない。一つのリファクタリング（コードを spawn に入れる）で参照カウントの実装が静かに変わる——コンパイラの警告是不会有的。性能変化は暗黙的だ。

## 現在のハードルの一つ：RAII が粗すぎる

前述したように、トークンは値であり、生存期間は RAII で管理される。しかし普通値の RAII ルールは：**値はスコープが終わるまで生き続ける。**
これはまさに Rust が NLL 之前有过的問題——借用はブロック 전체가 끝날 때까지続く，即使你已经很久不需要它了。

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_view: &Header = data.header()    # &mut Data から &Header を派生
    header_info = parse_header(header_view) # ← header_view の最後の使用
    # header_view は関数终了まで生きる必要はない——
    # しかし RAII ではそうなる }

    data.modify(header_info)   # ❌ ReadToken がまだ「生きている」、WriteToken が阻止される
}
```

Rust の NLL 分析は語彙的スコープではなく最後の使用を分析する。YaoXiang は同じ能力を必要としている。現在検討中の方案はトークン活性分析も証明パイプラインに接続すること——三層：

1. **ファーストパス**——既存の BorrowChecker を再利用（線形スキャン、IR 命令レベル）。同一基本ブロック内でトークンが使い果たされたシーンは直接通過
2. **構造分析**——ブランドツリーの接頭辞マッチング（誰が誰と競合するかを判断）+
   DAG 消費者クエリ（トークンの最後の消費者が現在のノードより後にあるかどうかを判断）
3. **SMT 求解**——ループ条件など論理的推論が必要な場合にのみアクティブ化

証明パイプラインフライチャ（`Proved/Disproved/Unproven` 三値返回、Z3 SMT バックエンド、假设スタック）は既に `src/frontend/core/typecheck/proof/` に部分的に実装されている。所有権層（`layers/ownership.rs`）はまだ骨組み——直接 Proved を返し、実際の検査はしていない。現在埋めている最中だ。

現在のバージョンの解決策は、手動でネストブロックを書いてトークンスコープを短縮すること：

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_info = {
        header_view: &Header = data.header()
        parse_header(header_view)
    }   # header_view はブロック終了伴随释放
    data.modify(header_info)   # ✅
}
```

これは реальное摩擦だ。Rust から移ってきた人都是これが当たる。这能不能消除——管道接入所有権層的效果に依存する。

## 最も難しい問題：フォールバック

Rust の `'a` は単なる负担ではない——它也是フォールバックだ。コンパイラが推断できない場合、プログラム員が生存期間関係を标注し、コンパイラが検証する。**あなたは一支のペンを持っている。**

YaoXiang のフォールバックは理論的にはコンパイル時**証明関数**であるべきだ（RFC-027 §4.2）：コンパイラが自動的に導出に失敗する → プログラム員が一个関数を書く、返回タイプが「トークンが競合しない」という命題である → コンパイラが この関数のタイプを検証する。しかし——

「トークンが競合しない」証明関数はどのようなものか？ユーザーはどのような `WriteTokenAvailable` 型の値を構築するのか？ブランド番号 `#N` と `#N.field_x` の接頭辞関係を理解する必要があるのか？

**もし証明関数がユーザーにブランド番号を理解させることを要求するなら——我々はただ `'a` を别の记法で書き直したことで、`#1` と呼ぶだけだ。何も省いていない。**

この問題にはまだ答えがない。これは整个実験が最も行き詰まる可能性のある場所だ。

## RFC-009 の九回の反復

これは象牙の塔で考え出された設計ではない。RFC-009 は九回の大きなバージョンを経た：

| バージョン | 主な変更内容                                                           | 推翻された理由                               |
| ---------- | ---------------------------------------------------------------------- | -------------------------------------------- |
| v1–v7      | Rust の所有権モデルに基づき、消費分析、逆関数、フィールドレベル可変性を徐々に追加 | 過度な設計、複雑性が制御不能になった         |
| **v8**     | 「丐版借用」——`&T`/`&mut T` はパラメータとして만 使用でき、返回や構造体への格納、闭包捕获は不可 | 三つのハードコード化された禁令。表現力が严重に制限された |
| **v9**     | 借用トークンシステム——`&T`/`&mut T` は普通タイプであり、普通ルールに従う               | 特殊ルールを解消したが、ブランド追踪をコンパイラ内部に下ろした |

v8 から v9 への躍遷は真の突破口だった：三条の禁令から零の特殊ルールへ。しかし v9 が解消したのは 用户に見えるルール，而不是系统的内在复杂性——ブランドメカニズム、派生追踪、同源競合検出は 여전히存在し，只是换到了コンパイラ内部。借用検査を証明パイプラインに統一することは方向性だが、真实のコードで通るか、フォールバックをどう設計するか——まだ検証中だ。

## 最後に

私たちは `'a` を消灭していない。`#1` は `'a` だ——同一の情報、别の位置。

実験の赌けは：言語設計制約（シャドウィング禁止、明示的 return、`for` 新規バインディング、`{}` DAG セマンティクス）がコンパイラによりクリーンな入力を与えることで、ブランド導出は Rust の生存期間省略規則が無効な大部分のシーンで自動的に成功するかもしれない。できれば——ユーザーは `'a` を書く必要がなく、标注と省略を区別する必要がなく、借用検査器を学ぶ必要がない。できなければ——或者说フォールバックメカニズム（証明関数）がユーザーにブランド番号を理解させることを要求するなら——それは単なる再发明だ。

進行中。 결과가 있으면 다시 쓴다.
