# 私たちは `'a` をコンパイラに隠した

_——YaoXiang の所有権モデルに関する正直なノート_

---

この Rust コードを見たとき、本当に理解するのにどれくらいの時間がかかりましたか？

```rust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn advance(&mut self) -> &'a str {
        let start = self.pos;
        self.pos += 1;
        &self.input[start..self.pos]
    }
}
```

3 つの `'a`。1 つは構造体に、2 つは impl ブロックにあります。すべて同じことを言っています：`Parser`
は借用している `input`
よりも長生きすることはできない。これは正しいことです。Rust の安全性はこの仕組みの上に成り立っています。

しかし、この種のコードを書くとき、よく思うことがあります：**このこと、コンパイラ自身では処理できないのか？**
Rust の答えは「できない」——少なくとも借用モデルを変更しない限りは。

**この記事の目的は「YaoXiang がこの問題を解決した」と主張することではありません。「YaoXiang が別の道を試している——`'a`
をコンパイラに隠し、コンパイラに書かせる。どこまで来たのか、まだ解決していない難題は何か」ということです。**

---

## Rust がなぜ `'a` を必要とするのか

Rust の `&T` と `&mut T`
はポインタです——データを指すポインタです。値を借用するとは、それへの参照を作成することです。この参照には独自のライフタイムがあります。参照が関数の境界を越えて伝播する場合（戻り値として、構造体に格納されるなど）、コンパイラは単一の関数内で参照がどれだけの期間生存できるかを推論できません——プログラマが
`'a` を使って「この戻り値とこの引数はライフタイムを共有する」という情報を提供する必要があります。

Rust コミュニティは立ち止まっていません。ライフタイム省略規則により、ほとんどの単純な関数は注釈なしで済みます。NLL は 2018 版で導入され、借用が字句スコープに縛られなくなりました。しかし、参照を構造体に格納したり、関数から返したり、クロージャにキャプチャしたりする必要がある場合——**モデル自体が、これらのシナリオではプログラマが参照間の関係を注釈する必要があると決定づけています。**

---

## 視点を変えて：借用はポインタではなくトークン

YaoXiang の中核的な設計は [RFC-009（所有権モデル）](../design/rfc/accepted/009-ownership-model.md)
に記録されています。デフォルトの意味論（すべて Move）は変更せず、**借用の本体**を変更しています。

YaoXiang では、`&T` と `&mut T`
は**ポインタではありません**。これらは**ゼロサイズのコンパイル時トークン**です——型レベルのアクセス権限の証明です。値を借用するとは、それへのポインタを作成することではなく、「それへのアクセスが許可されている」という証明を作成することです：

```
&T     →  保证数据不可变。实现 Dup（可复制），多个只读令牌共存安全
&mut T →  保证独占可变。不实现 Dup（线性），同一来源只能有一个
```

Rust では呼び出し点で `&`
を書きます（`distance(&p1, &p2)`）。YaoXiang では、コンパイラが関数シグネチャが `&Point`
を要求していることを見て、呼び出し点で自動的にトークンを作成します——呼び出し点は `distance(p1, p2)`
になります。代償として、定義者のシグネチャは `&`
を宣言する必要があります。そうでないとデフォルトの Move が所有権を消費してしまいます：

```yaoxiang
# 签名中需要 &——编译器看到 &Point，调用时自动创建令牌
check_dimensions: (v: &Vec3) -> Bool = { ... }
check_bounds: (v: &Vec3) -> Bool = { ... }

v = Vec3(1.0, 2.0, 3.0)
if check_dimensions(v) and check_bounds(v) {  # 每次都自动创建 &Vec3 令牌
    # v 仍然可用
}
```

Rust では `&` を呼び出し点に置きます。YaoXiang では `&`
を定義点に置きます。注釈が消えたわけではありません——注釈の位置が変わったのです。

## ブランド機構：コンパイラに隠された `'a`

ユーザーがこれに触れることは決してありません——しかし、これを理解しなければ、YaoXiang が実際に何をしているのかを理解できません。

コンパイラは内部で、各借用トークンにコンパイル時に一意な番号を割り当てます：

```
用户看到的         编译器内部表示
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)
&mut Point     →  WriteToken(Point, #M)
```

`&Point` からフィールドにアクセスして `&Float`
を得る際、後者は派生ブランドを持ちます：`#N.field_x`。`&mut`
トークンを別の変数に Move するとき、コンパイラは元の変数がもう保持していないことを知っています——これは Move セマンティクスの基本的な能力です。

**`#N` こそが `'a` です。** 接頭辞関係——`#N` は `#N.field_x`
の接頭辞——こそが outlives 制約です。同じ情報です。Rust のプログラマは `'a`
を書き、YaoXiang のコンパイラは `#N` を書きます。

違いは推論の成功率だけです。Rust の省略規則と NLL は約 80% のシナリオをカバーしています。YaoXiang の賭けは：**言語設計がコンパイラによりクリーンな入力を与えれば、より多くをカバーできるのではないか？**

この賭けは、いくつかの言語制約によって支えられています：

- **変数のシャドーイングを禁止**——`x`
  はこのスコープ内で 1 つのアイデンティティしか持たず、コンパイラは「どの x のことを言っているのか」を区別する必要がない
- **明示的な
  `return`**——ブロックから何がエスケープするかは明記されており、コンパイラは「最後の行が戻り値かどうか」を推論する必要がない
- **`for`
  は反復ごとに新しいバインディングを作成**——反復間の変数は互いに干渉せず、コンパイラは「前回の反復で何が変わったか」を追跡する必要がない

これらは「規範」ではありません。Java の getter/setter のような無意味な儀式とは異なり——各項目は**コンパイラが推論する必要のある情報をプログラム内に既に明記された情報に変えます**。コンパイラは「どの変数を指しているのか」「これがエスケープするかどうか」「ループ変数が反復をまたいでどう変化するか」を推測する必要がありません——答えはコードの中にあります。

## ブランドができること——Rust と同じ

トークンは通常の型であるため、通常の型のすべてのルールに従います。「参照を返せない」「参照を構造体に格納できない」「クロージャが参照をキャプチャできない」という特別な禁止事項はありません。**しかし Rust も同様です——Rust でもすべてできます。**
違いは能力ではなく、誰が注釈を書くかです。

**参照を返す——Rust のプログラマは `'a` を書き、YaoXiang のコンパイラは `#N` を書く：**

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)
}

p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()   # 令牌传播到调用方，编译器追踪品牌派生链
```

Rust も同じことをしますが、プログラマは入力と出力を接続するために `'a`
を書く必要があります。YaoXiang では、コンパイラはブランドパスを通じて自動的に派生します——`px_ref`（`#N.field_x`）は
`p`（`#N`）から派生します。同じ制約、異なる記録方法です。

**構造体が参照を保持する——ライフタイムパラメータなし：**

```yaoxiang
Window: Type = {
    target: Point,
    view: &Point,   # 令牌字段，和其他字段没有区别
}
```

Rust では、構造体に参照フィールドがある場合、`'a`
は構造体定義とすべての impl ブロックに現れる必要があります——プログラマは `Window<'a>`
のライフタイム制約を明示的に注釈します。YaoXiang では `view: &Point` に `'a`
は書きませんが、ブランド番号は依然としてコンパイラ内部で同じ役割を果たします——`Window`
インスタンスが破棄されると、内部のトークンも死にます。同じ保証、異なる可視性。

**クロージャのキャプチャ——Dup トークンのゼロコストコピー：**

```yaoxiang
filter_by_threshold: (items: List(Point), threshold: &Float) -> List(Point) = {
    items.filter(|p| p.x > threshold)   # threshold 令牌复制进闭包，零开销
}
```

`&Float`
は Dup（コピー可能）を実装し、クロージャはゼロサイズの整数をキャプチャするのと同じようにそれをキャプチャします。関数呼び出しの自動借用と同じルールを共有します。ユーザーの注釈はゼロです。

---

## 代償：注釈がシグネチャから消える

Rust の `'a`
にはよく挙げられる価値があります：それはドキュメントでもあるということです。`fn split_at_mut<'a>(slice: &'a mut [T], mid: usize) -> (&'a mut [T], &'a mut [T])`——`'a`
は、2 つの返されるスライスが同じ元のデータを参照していることを読者に伝えます。

現実には、この議論の説得力は限定的です——ほとんどの Rust 初心者は `'a`
をドキュメントとして読むのではなく、コンパイラが要求するおまじないとして写します。しかし公平に言えば：複雑な借用シナリオでは、Rust の
`'a`
は少なくともデータフローを追跡する出発点を提供します。YaoXiang では、ブランド派生チェーンを理解する必要があります——ブランドはユーザーから見えず、これはツールチェーンに依存しますが、ツールチェーンはまだ成熟していません。

## トークン競合検出：同じ証明パイプライン

Rust には独立した「借用チェッカー」があります。YaoXiang の**設計方向**は、借用競合を型検査の証明パイプラインに統合することです（[RFC-027（コンパイル時述語と統一静的検証）](../design/rfc/accepted/027-compile-time-evaluation-types.md)）。

トークン競合はホール論理の命題です：

```
{ 冲突的 ReadToken 已死 } data.push(4) { WriteToken 安全获取 }
```

```yaoxiang
# &mut T 是线性类型——Move 后原变量不再持有
bad: (p: &mut Point) -> Void = {
    p2: &mut Point = p    # WriteToken 从 p 转移到 p2
    p.x = 10.0            # { p 持有 WriteToken } p.x = 10.0 { 安全 }
}                          # → p 的 WriteToken 已 Move → Disproved

# &T 是 Dup——可复制
good: (p: &Point) -> Void = {
    p2: &Point = p        # 复制只读令牌
    print(p.x)            # OK，两个只读令牌共存
}
```

型エラーや述語検証失敗と同じエラー報告パスを共有します。2 つの診断システムを学ぶ必要はありません。**しかし代償として：**
複雑なトークン競合が Rust では慎重に言い回された借用チェックエラーを生成しますが、YaoXiang では「WriteToken(#7.field_x)
conflicts with
WriteToken(#7)」のように表現される可能性があります——技術的には正確ですが、ブランド番号は人間の読者にとって意味がありません。エラーメッセージの解釈可能性は、まだ検証されていない領域です。

## `ref` キーワード：Rc/Arc の自動選択

トークンはタスクをまたがる（スレッドをまたがる）ことはできません——これらはコンパイル時の証明であり、実行時の値ではありません。スコープをまたがる共有には
`ref` を使います：

```yaoxiang
shared_data = ref Point(1.0, 2.0)   # 编译器逃逸分析自动选 Rc 或 Arc

spawn {
    print(shared_data.x)   # 跨任务 → 编译器选 Arc
}
```

- spawn ブロックにエスケープしない → `Rc`（非アトミック参照カウント）
- spawn ブロックにエスケープする → `Arc`（アトミック参照カウント）

代償：コードを読むとき、ローカルだけでは `ref`
が Rc か Arc かを知ることはできません。1 回のリファクタリング（コードを spawn で包む）が参照カウントの実装を密かに変える可能性があります——コンパイラからの通知はありません。パフォーマンスの変化は暗黙的です。

## 現在の難題：RAII が粗すぎる

前に述べたように、トークンは値であり、ライフタイムは RAII によって管理されます。しかし通常の値の RAII ルールは：**値はスコープの終了まで生存する。**
これはまさに Rust が NLL 以前に抱えていた問題です——借用はブロック全体の終了まで続き、すでに使わなくなった後も続きます。

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_view: &Header = data.header()    # 从 &mut Data 派生 &Header
    header_info = parse_header(header_view) # ← header_view 的最后使用
    # header_view 没必要活到函数结束了——
    # 但 RAII 让它活到 }

    data.modify(header_info)   # ❌ ReadToken 还"活着"，WriteToken 被阻止
}
```

Rust の NLL は字句スコープではなく最終使用を分析します。YaoXiang にも同じ能力が必要です。現在進行中のアプローチは、トークン活性分析も証明パイプラインに接続することです——3 つの層：

1. **ファストパス**——既存の BorrowChecker を再利用（線形スキャン、IR 命令レベル）。同じ基本ブロック内でトークンが使われ終わったら解放されるシナリオは直接通過
2. **構造分析**——ブランドツリーの接頭辞一致（誰と誰が競合するかを判定）+
   DAG コンシューマクエリ（トークンの最後のコンシューマが現在のノードの後にあるかを判定）
3. **SMT ソルバー**——ループ条件など論理推論が必要な場合にのみ起動

証明パイプラインインフラ（`Proved/Disproved/Unproven` の 3 値返却、Z3
SMT バックエンド、仮説スタック）は `src/frontend/core/typecheck/proof/`
に部分的に実装されています。所有権層（`layers/ownership.rs`）はまだスケルトンです——直接 Proved を返し、実際のチェックを行っていません。実装中です。

現在のバージョンの解決策は、トークンのスコープを短縮するために手動でブロックをネストすることです：

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_info = {
        header_view: &Header = data.header()
        parse_header(header_view)
    }   # header_view 随块结束释放
    data.modify(header_info)   # ✅
}
```

これは実際の摩擦です。Rust から来た人なら誰でも遭遇するでしょう。解消できるかどうかは、パイプラインが所有権層に統合される効果次第です。

## 最も難しい問題：フォールバック

Rust の `'a`
は単なる負担ではありません——フォールバックでもあります。コンパイラが推論できない場合、プログラマがライフタイム関係を注釈し、コンパイラが検証します。**あなたにはペンがあります。**

YaoXiang のフォールバックは、理論上はコンパイル時の**証明関数**（RFC-027
§4.2）であるべきです：コンパイラの自動推論が失敗 → プログラマが関数を書き、戻り値の型が「トークンが競合しない」という命題になる → コンパイラがこの関数の型を検証する。しかし——

「トークンが競合しない」の証明関数はどのような形になるでしょうか？ユーザーは `WriteTokenAvailable`
という型の値をどうやって構築するのでしょうか？ブランド番号 `#N` と `#N.field_x`
の接頭辞関係を理解する必要があるのでしょうか？

**もし証明関数がユーザーにブランド番号の理解を要求するなら——私たちは単に `'a` を `#1`
と呼ぶように書き換えただけです。何も省けていません。**

この問題にはまだ答えがありません。これは実験全体が失敗する可能性が最も高い場所です。

## RFC-009 の 9 回の反復

これは象牙の塔で考え出された設計ではありません。RFC-009 は 9 回のメジャーバージョンを経ました：

| バージョン | 主な変更                                                                                                               | 覆された理由                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| v1–v7      | Rust の所有権モデルに基づき、消費分析、逆関数、フィールドレベルの可変性を徐々に追加                                    | 過剰設計、複雑性の制御不能                                           |
| **v8**     | 「乞食版借用」——`&T`/`&mut T` は引数にのみ使用でき、返したり、構造体に格納したり、クロージャにキャプチャしたりできない | 3 つのハードコードされた禁止事項。表現力が著しく制限される           |
| **v9**     | 借用トークンシステム——`&T`/`&mut T` は通常の型で、通常のルールに従う                                                   | 特別なルールを排除するが、ブランド追跡をコンパイラの内部に押し下げる |

v8 から v9 への飛躍が真のブレークスルーです：3 つの禁止事項から、特別なルールゼロへ。しかし v9 が排除したのはユーザーから見えるルールであり、システムの内在的な複雑性ではありません——ブランド機構、派生追跡、同源競合検出、これらは依然として存在し、コンパイラに移されただけです。借用チェックを証明パイプラインに統合することは 1 つの方向ですが、実際のコードで動作するか、フォールバックをどう設計するか——まだ検証中です。

## 最後に

私たちは `'a` を消したわけではありません。`#1` こそが `'a` です——同じ情報、異なる位置。

実験の賭けは：言語設計の制約（シャドーイングの禁止、明示的な return、`for`
の新しいバインディング、`{}`
の DAG セマンティクス）がコンパイラによりクリーンな入力を与え、ブランド派生が Rust のライフタイム省略規則が失敗するほとんどのシナリオで自動的に成功するかもしれない、ということです。もし成功すれば——ユーザーは
`'a`
を書く必要がなく、注釈と省略を区別する必要がなく、借用チェッカーを学ぶ必要がありません。失敗すれば——あるいはフォールバック機構（証明関数）がユーザーにブランド番号の理解を要求するなら——それは単に再発明に過ぎません。

進行中です。結果が出たらまた書きます。
