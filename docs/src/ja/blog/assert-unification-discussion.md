# 「統一」についての深夜の長談

2026年7月11日の深夜から12日の未明にかけて、私たちは六時間を一つの問題——YaoXiangの`assert`とは本来どうあるべきか——の議論に費やした。結果は予想外だった。ずっと「assertをどう実装するか」を議論していたつもりだったが、実は「型システムの土台にどんな穴があるか」を議論していた。

この記事で最終的な結論は扱わない（結論はspecにある）。扱うのは、段階的に自分の誤りに気づいていく過程と、そのたびにどう正されたかだ。

---

## なぜassertが二つあるのか

YaoXiangは二つのものを同時に開発している：

**コンパイル時の精化型** `Assert(N > 0)`を型定義に書く：

```
Bounded: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    _assert: Assert(N > 0),   // N必须大于0，否则编译失败
}
```

コンパイル時にジェネリック引数を検証する。Nが5なら通るし、Nが0ならコンパイルエラーになる。実行時のオーバーヘッドはゼロ。

**実行時アサーション** `assert(x > 0)`を関数本体に書く：

```
x = read_int()
assert(x > 0)   // 检查用户输入
```

値は外部から渡されるため、コンパイル時には分からない。失敗すればpanicする。

大文字のAssertと小文字のassert。一つはコンパイル時、一つは実行時。同じ概念の二つの姿。

最も自然な反応——最も楽な方法——は、これらを完全に独立した二つのものとして扱うことだ。Assertは精化型で証明パイプラインを通り、assertは20行のnative関数で空値を返す。互いに干渉しない。

しかしこの方法にはずっと言葉にしがたい不快感があった。両者は明らかに同じ関係にあり、「私はこの条件が成立しなければならないと断言する」という同じ意味の二面に過ぎない。ユーザーに「ここでは大文字、そこでは小文字、ここではコンパイル時チェック、そこでは実行時のみ」と覚えさせるのは認知的負債だ。言語設計において、「似ているが別々に記憶すべきもの」が一つ増えるたびに、負債を背負うことになる。

## 統一を試みて、壁にぶつかる

統一という理想は実はとても簡潔だ：

```
assert: (cond: Bool) -> Assert(cond)
```

`assert`は精化型`Assert(cond)`を返す。コンパイル時にcondの値を計算できれば、コンパイル時チェックに畳み込む（消去）；コンパイル時に計算できなければ、実行時チェックに回す。一つの関数、二つの運命。シグネチャそのものが結節点となる。

だがすぐに誰かが「根本的矛盾」を指摘した：

> `Assert(C)`はCがコンパイル時に評価可能であることを要求する。`assert(x > 0)`のxは実行時の値であり、コンパイル時には`Assert(x > 0)`を計算できない。精化型の規則に従えば、これは**コンパイルエラー**にしなければならない。しかし`assert(x > 0)`は完全に正常な実行時アサーションだ。よってシグネチャが`Assert(cond)`の統一案は成り立たない。分離しなければならない。

この論点は隙がなさそうに聞こえる。精化型が実行時の値に遭遇したらエラーになるなら、「コンパイル時アサーション」と「実行時アサーション」を同じシグネチャに押し込めることは永遠にできない。二つのもの、二つの運命、分離しよう。

**しかしそれは嘘だ。**
嘘なのは最後の「コンパイルエラーにしなければならない」という部分だ。精化型の結果は二値ではない——「証明成立」と「エラー」だけではない。三値だ：Proved（証明された）、Disproved（反証された、反例付き）、**Unproven（判定不能）**。

「判定不能」と「反証された」は全く異なる状態だ。反証されたなら報告すべきで、覆ることはない。しかし判定不能——値が実行時まで分からないから判定できない——は、まさに実行時にチェックを回すことができる。コンパイル時に判定不能であることは、コンパイル時の失敗ではなく、この命題の**自然な属性**だ。

「実行時アサーション」が何の「別の仕組み」か、コンパイル時に判定不能な命題が、実行時になって初めてチェックされるものに過ぎない。**同じ精化型、二つの運命、運命はコンパイル時に判定可能か否かという事実によって自動的に決まる。**

偽の衝突が崩れると、統一への道が開ける。しかしまず土台の一つの穴を塞ぐ必要がある。

## 一つ足りなかった型：Never（偽 / 発散 / 不可能）

統一案は`assert(false)`を「値を持ち得ない」型に還元することを要求する——「falseが真」という命題には証明がないため、それを型として使う場所では、プログラムは発散しなければならない。

そこでYaoXiangにはこの型が根本的に存在しないことに気づいた。

`Void`はある。しかし`Void`はデフォルト値を返せる——`Void`を返す関数を呼び出しても、コードはそのまま続く。`Void`には居住者がいる。Curry-Howardの対応では、値を持つ型は「真命題」（証明が一つある）であり、「偽命題」（証明がゼロ）ではない。**`Void`は常に「真⊤」であり、誰もそう呼んでいなかっただけだ。**

我々に足りないのは「偽⊥」だ：永久に居住不可能な型——`x: Never = ...`の右辺に埋められる値は一つもない。`assert(false)`、`panic`、無限ループの返り型はすべてこれであるべきだ。これがないと、`assert(false)`は合法的なデフォルトのvoid値を返し、その後のコードがそのまま実行される——アサーション失敗が正常なフローになる。精化型システム全体がその瞬間、論理的に崩壊する。

`Never`は最終的に**公理**として定められた：何からも導出されず、型システムの原初的な概念である。三つの性質がカーネルに組み込まれている——コンストラクタがゼロ、Neverはすべての型のサブタイプである（「偽からはすべてを導ける」）、関数の返り型としてその関数が発散して決して返らないことを示す。この三つを理解しなくても構わない、結論だけ知っていればよい：言語は`Never`という名前の型を内蔵しなければならず、それは値を持たず、`assert(false)`を書いた後のコードが絶対に実行されないことをシステムに伝える。

## 自分自身に偽の分類を大量生産し、自分でハマった

Neverを補った後、次は「判定不能のときどうするか」に答える番だ。この段階で、まさに教科書的な間違いを犯したため、二ラウンド分もの議論を完全に無駄にした。

**第一步：Unprovenを分割する。**

「判定不能」にはいくつかのケースがあるように見える。実行時変数に依存するもの——`x`は外部入力なので、コンパイル時には当然分からない。探索予算を超えたもの——理論的には判定可能だが、計算コストが高すぎるもの。コンテキストの前提が足りないもの——命題自体の問題ではなく、呼び出し側が十分な静的情報を提供していないもの。ゲーデル的に決定不能なもの——どれだけ時間と予算を与えても判定不可能で、理論的に不可能。

そこで四つに分割し、たくさんの名前を付け、それぞれをどう処理するかを議論した。実行時に依存するもの——実行時チェックに降格する？予算超過——予算を増やすかユーザーに証明を求めるか？前提不足——前提を補うかエラーか？決定不能——ユーザーが証明を書くしかない？

**分割し終えてから、分類が間違っていたことに気づいた。**

分類の軸を間違えた。「コンパイラが判定不能を受け取った後どうすべきか」で分類していた。しかし「どうすべきか」は推論の結果であり、分類の根拠ではない。正しい問いは：**この命題の述語は、コンパイル時に真の値を得ることができるか？**

取得できるもの——引数がジェネリック位にあり、コンパイル時に値が確定している、例えば`Bounded: (T: Type, N: Int) -> Type`のN——証明パイプラインに入る。パイプラインは三つの答えを出す：Proved（真、消去）、Disproved（偽、コンパイルエラーで永遠に覆らない）、Unknown（真の判定不能、ただしこの位置ではコンパイル時に証明する能力があるので、証明を求める）。

取得できないもの——引数が関数引数であり、値が呼び出し側から実行時に渡される、例えば`process: (n: Int) -> ...`のn——そもそも証明パイプラインに入れるべきではない。直接、実行時チェックに進む。この道にはUnprovenは存在しない、なぜなら「証明」という問題が存在しないからだ——「ユーザーが負数を入力したかもしれない」という命題の証明を書くことは不可能で、そもそも恒真ではない。

**道は二つだけ。四種が二種に、分割して出てきた余計な分類は自分を自分で回しているだけ。**

この結論が出たばかりのとき、私たちはまだ完全には信じていなかった。検証するため、私は例を出した——`process: (N: Int) -> ... { assert(N > 0) }`、ここではNはコンパイル時に既知だがproverが判定できず、「判定不能＋コンパイル時既知」という新カテゴリーであり、証明の記述を強制すべきだと言った。

**その場で覆された。**
`process`は普通の関数であり、`N`は普通の関数引数——その値は呼び出し側から来るため、コンパイル時には全く分からない。私は関数シグネチャの`N: Int`を「コンパイル時にNの値が既知」だと勘違いしていた——しかしYaoXiangでは、「コンパイル時既知」は正確に**ジェネリック引数位**に対応し、普通の関数引数位ではない。同じ書き方`N: Int`でも、型コンストラクタ（`-> Type`）ではコンパイル時定数であり、普通の関数では実行時値である。二つのN、二つの宇宙。

訂正の後、「判定不能＋コンパイル時既知」の正体が明らかになった：これは「普通の人が書いた証明器がたまたま判定できない命題」ではなく、**誰かがジェネリックコンテキストで小文字の`assert`を誤用している**——その位置ではコンパイル時に引数の値が分かるため、実行時チェックを使うべきではない。これは新しいカテゴリーではなく、精化型本来の規則そのもの：証明が必要な領域にいる以上、判定不能なら証明を提供するべきだ。

**実行時のエスケープハッチは設計不要——自然に存在する。**
まさに「値がコンパイル時に分からず、実行時になって初めてチェックする」という道のことだ。健全（実行時に実際にチェックする）、手軽（proveを書かない）、オーバーヘッドが明示的（値は元々外部から来る）。これは「proverがないから実行時が必要なのではなく」、**この種の命題はコンパイル時には真偽があり得ない**——proverがどれほど強力でも、ユーザーが条件を満たさない値を入力する可能性があり、命題自体は偽であり、真命題の証明は書けない。実行時は唯一のsoundな選択であり、理論的に必要であって、妥協ではない。

## 毎回間違えるたびに、根本原因は同じ

振り返ると、九つの誤った結論を覆した：

1. `assert`が空値`()`を返す——そうすると実行時チェックの結果がコンパイル時に伝わらず、後続のコードは条件が成立したかを知らない
2. `assert`がUnprovenを「解消」できる——違う、証明に参加せず、実行時に実際のチェックを行う
3. 実行時の命題と前提不足の命題はUnprovenの異なるサブクラス——違う、パイプラインの入口で分けられ、Unprovenは生成されない
4. RFC-027を「特殊化消去」に変更する必要がある——不要、ゼロサイズの証明トークンが消去され、実行時にはそのBoolチェックが残る
5. 不変の変数は直接コンパイル時に——違う、不変はコンパイル時に既知の値とは限らない（`x = read_int()`は不変だが、値はコンパイル時に分からない）
6. 関数引数`N: Int`はコンパイル時に既知——ジェネリック引数のみ、普通引数の値は実行時に得られる
7. proveがあれば実行時は不要——実行時入力には恒真の命題を証明できず、実行時は理論的に必要
8. 「判定不能」はデフォルトで実行時チェックに降格すべき——判定不能＋コンパイル時既知はproveを要求すべきで、降格するのは「コンパイル時に値を知らない」カテゴリー
9. 型レベルmatchは帰納法——matchは単なる場合分けであり、帰納仮説がない；真の帰納法は再帰＋停止性チェックが必要

**九つの誤りのうち、五つの根本原因は同じ：似てはいるが実は直交する二つの概念を混同している。**
不変 vs コンパイル時既知。証明トークン vs トークンを生成する計算。ジェネリック引数 vs 関数引数。場合分け vs 帰納法。判定不能 vs 反証。すべてのペアで踏んだ——不注意ではなく、概念自体の類似性が滑り込みやすくしている。

## どんな問題がissueで広く意見を募うに値するか

議論の中でissue#156を立て、タイトルは「統一の难题」とした。一つの誤った例と一つの存在しない分類が、「コミュニティの助けが必要」な問題を支えていた。核心的な矛盾は偽の衝突であり、「判定不能＋コンパイル時既知」という類型はそもそも存在しない——誤った例に偽装されていた。答えは実は議論の後半で自ずと浮上した——**「統一」の案は妥協ではなく、収束だ。「他にも第三のケースがあるかもしれない」と思った場所はすべて、最終的に既存のパスに帰着した。**

issueで助けを求めるなとは言っていない。だが先に確認すべきだ：本当にその問題の真の形態を見たのか？挙げた例は本当に割り当てたカテゴリーに属するのか？矛盾は真の矛盾か、それとも「ある前提が成立すると思い込んでいたが、実は成立しない」のか？

多くの場合、「コミュニティの意見が必要」なのは答えが遠いからではなく、**自分で作った分類に自分がハマっている**からだ。

## 本当に学んだこと

今回の議論は六時間続き、自分自身を九回覆した。最終的な成果物は新しいassert
APIではなく、釘付けにされた土台だ：`Never`は存在しなければならない（以前は誰も不在に気づかなかった）、精化型の結果は二値ではなく三値（「判定不能」≠「反証」）、コンパイル時既知 ≠ 不変、実行時チェックはproveの弱い代替ではなく唯一のsoundな選択、`assert(x > 0)`は「別のもの」ではなく値宇宙における`Assert`の別の運命。assertとAssertは同じものの二面であり、両者の違いはそれが何であるかではなく、その瞬間にコンパイラが計算できるか否かだ。

**最良の設計は追加ではなく、収束だ。** 私たちは「runtime
assert機構」を追加したのではなく、それが元々`Assert`の一面であったことに気づいた。「判定不能の処理案」を追加したのではなく、それが既にパイプライン内に位置を持っていたことに気づいた。「特別なケースを追加する必要がある」と思うたびに、まず自問しよう：これは本当に新しいものなのか、それとも既存の概念に気づかなかっただけなのか？

**分類は本質を見よ、自分がしたいことではなく。**
私たちは当初「コンパイラが何をするべきか」で四つのUnprovenサブクラスを分けた——分割後に分類法が誤りだと気づいた、「何をするべきか」は推論の結果であり分類の根拠ではないため。正しい方法は「命題がコンパイル時に真の値を持つか否か」で分けること——持てば持つ、なければない。二種、きれいで、交差なし。
