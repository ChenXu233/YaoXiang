# 「統一」への徹夜の議論

2026年7月11日の深夜から12日の未明にかけて、6時間にわたって一つの問題を議論しました——YaoXiangの`assert`到底是什么であるべきか。結果は予想外でした：ずっと「assertの実装方法を議論している」つもりでしたが，实际上は「型システムの地基に穴がいくつあるか」を議論していたのです。

この記事は最終結論（結論はspecにあります）を述べるものではなく、是如何に少しずつ自分が間違っていたことに気づき、如何に每一次引き戻されたかを述べたものです。

---

## なぜ2つのassertが存在するのか

YaoXiangでは同時に2つのものが開発されています：

**コンパイル時精化型** `Assert(N > 0)`は、型定義の中に記述します：

```
StaticArray: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    _assert: Assert(N > 0),   // Nは0より大きくなければならず、さもなくばコンパイル失敗
}
```

コンパイル時にジェネリック引数を検証します。Nが5なら通過、Nが0ならコンパイルエラー。ゼロの実行時オーバーヘッド。

**実行時アサーション** `assert(x > 0)`は、関数本体の中に記述します：

```
x = read_int()
assert(x > 0)   // ユーザー入力をチェック
```

値は外部から渡されるため、コンパイル時にはわかりません。失敗すればpanicします。

大文字のAssert、小文字のassert。一つはコンパイル時、一つ実行時。同じ概念、2つの形態。

最も自然な反応——最も楽な方法——は、これらを完全に独立した2つのものとして扱うことです：Assertは精化型で証明パイプラインを通り、assertはvoidを返す20行のnative関数。互いの領域侵犯なし。

しかしこの方案には、ずっと説明のつかない不快感がありました。これらは明らかに关联しており、同じセマンティクス——「この条件が成立.Mustしなければならない」——の两面です。「ここで大文字、あそこで小文字、ここではコンパイル時チェック、あそこでは実行時のみ」ということをユーザーに覚えておくもらうのは認知的負債です。言語設計において、「似ているが别々に覚える必要がある」ものが增えるたびに、负债が増えています。

## 統一を試み、壁にぶつかった

統一の理想は極めてシンプルです：

```
assert: (cond: Bool) -> Assert(cond)
```

`assert`は精化型`Assert(cond)`を返します。コンパイル時にcondの値が計算できれば、コンパイル時チェックに折叠（消去）されます；計算できなければ、実行時まで残されます。一つの関数、两种の運命。シグネチャ自体が接続点となります。

しかし、すぐに「根本的矛盾」を指摘されました：

> `Assert(C)`はCがコンパイル時に評価可能であることを要求します。`assert(x > 0)`のxは実行時の値——`Assert(x > 0)`はコンパイル時に計算できません。精化型の規則によれば、これは**コンパイルエラー.Must**です。しかし`assert(x > 0)`は完全に
> 정상な実行時アサーションです。 따라서シグネチャが`Assert(cond)`である統一方案は不通です。分开.Mustです。

この論点は无敵に見えます。精化型が実行時の値に出会ったらエラー，那么你永远无法把「コンパイル時アサーション」と「実行時アサーション」を同じシグネチャに入れる。两个东西、两种命运、分ましょう。

**しかしそれは偽です。**
最後の那句「.Mustコンパイルエラー」が偽です。精化型の結果は二値ではない——「証明成立」と「エラー」だけではありません。三値です：Proved（証明された）、Disproved（証明偽われた、反例付き）、**Unproven（判断不能）**。

「判断不能」と「証明偽われた」は全く别々の状態です。証明偽われたならエラーになるべきで、永遠に翻身できません。しかし判断不能——就是因为値が実行時才知道所以判断不能——恰恰是可以留到実行時に查的对象です。コンパイル時に判断できない，是この命題の**天然属性**であり、コンパイル時の失敗ではありません。

「実行時アサーション」など是什么「別のメカニズム」ではなく、コンパイル時に判断できない命題が、実行時に到达して检查を受ける
것입니다。**同じ精化型、两种の運命、運命はコンパイル時に判断できるかどうかという事実によって自動的に決定されます。**

偽の冲突が解消すれば、統一の道が開けます。しかし、まず地基の穴を一つ埋める必要があります。

## 欠けている型がある：Never（偽 / 発散 / 不可能）

統一方案は`assert(false)`が「値を持ち得ない」型に正規化することを要求します——因为「falseが真である」という命題は証明されておらず、それを使って型を構成する場は、プログラムが発散.Mustするためです。

そして我发现：YaoXiangにはこの型がそもそもありません。

`Void`はあります。しかし`Void`はデフォルト値を返せます——`Void`を返す関数を呼び出し终わっても、コードは继续実行できます。`Void`には住居民がいます。Curry-Howard対応において、値を持つ型は「真命題」（証明が一つある）であり、「偽命題」（証明がゼロ）ではありません。**`Void`は始至终「真⊤」であり、単に谁もそう呼んでいなかっただけです。**

我々に欠けているのは「偽⊥」です：一个永远不能住居する型——`x: Never = ...`の右边埋めることができる値はありません。`assert(false)`、`panic`、无限ループの返り型はすべて这里にあるべきです。これがないと、`assert(false)`は合法的なデフォルトvoid値を返して、后面的代码を実行し続けます——アサーション失敗が正常な流れになってしまいます。精化型システム全体が那一刻逻辑崩壊します。

`Never`は最終的に**公理**として定義されました：他のものから推导されるものではなく、型システムの原初概念です。三つの性質がカーネルに組み込まれています——零個のコンストラクタ、Neverはすべての型のサブタイプ（「偽からすべてが导出される」）、関数返り型として使った場合その関数は発散し永不返回することをマークする。この三つを理解必要はない、結果を知るだけで十分です：言語には`Never`という型が組み込まれている.Mustで、それは値を持さず、`assert(false)`の後那段代码が決して実行されないことをシステムが知っている必要があります。

## 自分に一堆の偽分類を作り出し、巻き込まれた

Neverを補完した後次は「判断不能の场合どうするか」に答える必要があります。このステップで、讨论整整浪费了两轮，因为犯了一个教科書級の誤りでした。

**第一步：Unprovenを分割する。**

「判断不能」はlooks
like好多种类情况がありました。実行時変数に依存する——`x`は外部入力で、コンパイル時にわかるわけがない。搜索予算超過——理论上判断可能だが、计算が高すぎて断念。前提不足——命題自体の问题ではなく、呼び出し元が十分な静的情報を提供していない。ゲーデルの不判定——時間と予算を增やしても判断不可能で、理论上不可能。

そこで四种に分割し、好多名前を付けて、それぞれ怎么处理を議論しました。実行時依存——実行時チェックに降格？予算超過——予算的增加还是要求用户提供証明？前提不足——前提を補完还是エラー？不判定——只能是用户 написать 証明吧？

**分割后发现分类错了。**

分类の軸を間違えました。按「コンパイラが判断不能になった后该怎么办」分类していました。しかし「该怎么办」は推論の結果であり、分類の根拠にはなりません。問題は这里です：**この命題の述語は、コンパイル時に真値を得られるか？**

能得到——パラメータがジェネリック位置にあり、値がコンパイル時に確定している，比如`StaticArray: (T: Type, N: Int) -> Type`のN——証明パイプラインに進みます。パイプラインは三つの答えを返します：Proved（真、消去）、Disproved（偽、コンパイルエラー永不得翻身）、Unknown（真・判断不能だが、この位置はコンパイル時に証明
가능하다ため、証明を要求する）。

得不能——パラメータが関数引数であり、値は呼び出し元の実行時入力，比如`process: (n: Int) -> ...`のn——そもそも証明パイプラインに進むべきではない。直接実行時チェックに進みます。このルートにはUnprovenは存在しません，因为「証明」という問題が存在しないからです——「ユーザーが负数を入力したかもしれない」という命題に証明を書くことは不可能です，因为それは恒真ではないからです。

**就两条路。四种变两种、拆出来的多余分类是自己绕自己。**

この結論が出たとき、我々はまだ余り信じていませんでした。验证ため、一个例を出しました——`process: (N: Int) -> ... { assert(N > 0) }`、Nはコンパイル時に已知だがproverが判断不能、「判断不能+コンパイル時已知」の新カテゴリにあり、証明の强制 написать べきとしました。

**当场推翻されました。**
`process`は обычная 関数、`N`は обычная 関数引数——その値は呼び出し元から来ものであり、コンパイル時にはわかりません。関数シグネチャ内の`N: Int`を「コンパイル時にNの値が已知」と误認していたのです——しかしYaoXiangでは「コンパイル時に已知」は**ジェネリック引数位置**に正確に対応し、обычная 関数引数に対応しません。同じ写法`N: Int`でも、型コンストラクタ（`-> Type`）ではコンパイル時定数であり、обычная 関数では実行時値。两个N、两个宇宙。

纠正之后、「判断不能+コンパイル時已知」の реальный 姿が露呈しました：「普通の人 написать
proverが偶発的に判断不能な命題」ではなく、**谁かがジェネリックコンテキスト内で小文字`assert`を误用している**——その位置ではコンパイル時にパラメータの値が既知であり、実行時チェックに進むべきではありません。これは新カテゴリではなく、これが精化型の本来ルールです：証明が必要な领域に位置する場合、判断不能なら証明を提供する.Mustです。

**実行時エスケープハッチは設計不要——它是天然存在的。**
それが「値がコンパイル時にわからず、実行時に查に行く」那条路です。健全（実行時に本当に查に行く）、便利（proveを書かなくていい）、オーバーヘッド明確（値は元々外部来源）。「我々にproverがないから実行時が必要」のではなく、**この手の命題はコンパイル時にそもそも真假の可言がない**——proverがどれだけ強くても不可能で、ユーザーが実際に条件不满の値を入力したかもしれない、命題自体が偽であり、真命題の証明は書けない。実行時は唯一soundな選択であり、理论上必要であり、妥协ではない。

## 每次走错、根源都是同一件事

振り返ると、九つの误った結論を推翻しました：

1. `assert`は空値`()`を返す——那样执行时检查の結果がコンパイル時に伝わらず、後续代码は条件が成立したことを知らない
2. `assert`はUnprovenを「消解」できる——不对，它不参与証明，它做的是実行時に実際にチェックする
3. 実行時命題と前提不足命題はUnprovenの不同サブクラス——不对，它们はパイプライン入り口で既に分开され，根本不生Unproven
4. RFC-027を「特化消去」に改变する必要がある——不用、消去されるのはサイズがゼロの証明トークンであり、実行時に保持されるのはあのBoolチェック
5. 不変変数は直接コンパイル時になる——不对、不変不等于コンパイル時に既知の値（`x = read_int()`は不変だが、値はコンパイル時にわからない）
6. 関数引数`N: Int`はコンパイル時に既知——ジェネリック引数のみがそうであり обычная 引数の値は実行時输入
7. proveがあれば実行時は不要——実行時入力には恒真の命題を証明することはできない、実行時は理论上必要
8. 「判断不能」はデフォルトで実行時チェックに降格すべき——判断不能+コンパイル時既知ならproveを要求すべきであり、降格するのは「値がコンパイル時にわからない」方
9. 型レベルmatchは归纳法——matchは只是分類討論であり、归纳仮定はない；真正的归纳には再帰+終了性チェックが必要

**九个错误里、五个根子是同一个：二つの似てるが实际上直交する概念を混同した。**
不変 vs コンパイル時既知。証明トークン vs トークンを生成する計算。ジェネリック引数 vs 関数引数。分類討論 vs 归纳法。判断不能 vs 証明偽われた。每对都踩过——不是不注意、是概念本身的相似性让它极易滑进去。

## 什么样的问题值得开issue集思广益

議論中にissue#156を開きました、タイトルは「統一の難問」。一个错误的例と存在しない分类撑起了一个「コミュニティの助けが必要」な问题。本当の矛盾は偽の冲突であり、「判断不能+コンパイル時已知」というカテゴリはそもそも存在しません——误った例が偽装したものでした。答えは議論の後半で既に浮かび上がっていました——**「統一」の方案は妥协ではなく、塌縮です。「第三の状況があるかもしれない」各場所は、最終的に既にあったルートに归属しました。**

issue求助不能するということではない。是说要先確認：この問題の реальный 姿を本当に見たことがありますか？提示した例は本当に划分したカテゴリに属していますか？矛盾は本当に矛盾ですか、それとも「某个前提が成立，认为它成立，其实不成立」ですか？

很多时候、「コミュニティの意見が必要」不是因为答えが远すぎる，是因为**自分が自分の作った分類に巻き込まれている**からです。

## 本当に学んだこと

今回の議論は6時間続き、9回自分を推翻しました。最終产物は新しいassert
APIではなく、地基に钉された一张纸です：`Never`が存在.Must（ zuvor気づかなかった欠落）、精化型结果是三値而不是二値（「判断不能」≠「証明偽われた」）、コンパイル時既知 ≠ 不変、実行時チェックはproveの弱替代而不是唯一soundな選択であり、`assert(x > 0)`は「别なもの」ではなく`Assert`が値宇宙で持ちらる另一种運命です。assertとAssertは同一物の两面——両者の区别的不是它们是谁，而是コンパイラがその瞬间に計算できるかどうかです。

**最も良い設計は新增ではなく塌縮です。** 「runtime
assertメカニズム」を新增せず、`Assert`の一面であることを発見しました。「判断不能の処理方案」を新增せず、パイプライン内に既に位置があることを発見しました。每次当你觉得自己需要「特別な場合を加える」必要があると思ったとき、まず自分に聞いてください：これは本当に新しいものか、それとも某个既に存在する概念を识别できなかっただけか？

**分類は本質を見ようで、做法を見ない。**
私たちは始め「コンパイラが何をすべきか」に従って四つのUnprovenサブクラスに分割しましたが、分割后发现分类は误りでした，因为「何をすべきか」は推論の結果であり、分類の根拠ではない。正しい方法は「命題がコンパイル時に真値を持つか」で分割——持てば持つ、持てなければ持たない。二类、清潔、交差なし。
