# **《Spawn: модель бесшовного асинхронного параллелизма на основе ленивой оценки》 Технический White Paper**

## 🏛️ 一、Основные определения: модель Spawn

**Модель Spawn**, заимствованная из «И-Цзин. Гуа Фу» («Все существа действуют сообща, и я наблюдаю их возвращение»). Это парадигма параллельного программирования, позволяющая разработчикам описывать логику синхронным, последовательным мышлением, в то время как среда выполнения языка автоматически и эффективно выполняет вычислительные единицы параллельно, как «все существа, действующие сообща», и в итоге координирует их.

### Основные принципы проектирования: ленивость по умолчанию + маркер типа spawn

| Принцип проектирования      | Описание                                                               |
| --------------------------- | ---------------------------------------------------------------------- |
| **Ленивая оценка по умолчанию** | Все функции по умолчанию ленивы (как в Haskell), возвращают Lazy[T]  |
| **Конфигурация ядер**      | Объявление `// @cores: N` в заголовке скрипта автоматически включает параллелизацию |
| **Маркер типа spawn**      | `-> T spawn` помечает функцию как строго асинхронную и параллельную, остальные опционально параллельны |
| **Смешанные режимы оценки**| `@eager` (декоратор, принудительная eager-оценка), `@auto` (декоратор, сохранение параллелизма) |
| **Автоматическая eager для Void** | Функции, возвращающие `Void`, автоматически вычисляются eagerly (побочные эффекты должны выполняться) |

### Три основных принципа

| Основной принцип | Объяснение                                                     |
| ---------------- | -------------------------------------------------------------- |
| **Синхронный синтаксис** | То, что видишь — то и получаешь: последовательный код, написанный так, как он выглядит |
| **Параллельная сущность** | Среда выполнения автоматически извлекает параллелизм, выявляет возможности параллелизма в зависимостях данных |
| **Единая координация** | Результаты автоматически собираются при необходимости, обеспечивая логическую корректность |

**Это достигается двумя фундаментальными преобразованиями:**

1. **Преобразование «потока управления» в «поток данных»**: программа рассматривается как чисто функциональный граф ленивой оценки данных
2. **Преобразование «асинхронного заражения» в «разрешение зависимостей»**: асинхронность больше не является эффектом сигнатуры функции, а становится операцией ожидания, автоматически выполняемой средой выполнения в точках зависимости данных

## 📚 二、Терминологическая система: единая карта понятий

Вокруг «Spawn» мы построили четкую, самосогласованную терминологическую систему, связывающую все проектные решения воедино:

| Официальный термин      | Соответствующий синтаксис/концепция | Объяснение                                                           |
| ----------------------- | ----------------------------------- | --------------------------------------------------------------------- |
| **Функция spawn**       | `-> T spawn`                        | Маркер типа возврата, указывающий, что это вычислительная единица, строго способная участвовать в параллельном выполнении «spawn» |
| **Блок spawn**          | `spawn { a(), b() }`                | Явно объявленная область параллелизма, задачи внутри блока будут «спауниться» |
| **Цикл spawn**          | `spawn for x in xs { ... }`         | Парадигма данныхого параллелизма, тело цикла «спаунится» на всех элементах данных |
| **Значение spawn**      | Тип прокси `Async[T]`               | «Будущее значение», находящееся в процессе спауна, автоматически ожидает завершения при использовании |
| **Граф spawn**          | Граф ленивых вычислений (DAG)       | Сцена, на которой происходит «spawn», описывает зависимости и параллельные отношения между всеми вычислительными единицами |
| **Планировщик spawn**   | Планировщик задач времени выполнения | Интеллектуальный центр, ответственный за координацию «всех существ», чтобы они «спаунились» в нужное время |
| **Граф ошибок**         | Error Graph                         | Визуализация путей распространения ошибок в параллельной среде, аналогично стеку вызовов, но показывает поток ошибок в DAG |
| **Конфликт ресурсов**   | Resource Conflict                   | Конфликт при одновременном доступе нескольких задач к одному записываемому ресурсу, обнаруживается при компиляции и автоматически сериализуется |

> **Пример технического обсуждения**: «Здесь мы используем блок spawn для параллельного вызова двух функций spawn, чтобы автоматически получить их значения spawn.»

## 三、Трёхуровневая архитектура параллелизма: прогрессивная прозрачность

### 3.1 Обзор архитектуры

Модель Spawn обеспечивает **три уровня прогрессивных абстракций параллелизма**, позволяя разработчикам с разным уровнем навыков найти подходящую модель использования:

| Уровень | Модель              | Синтаксический маркер | Способ выполнения     | Контролируемость | Сценарий применения                 |
| ------- | ------------------- | --------------------- | --------------------- | ---------------- | ------------------------------------ |
| **L1**  | `@blocking` синхрон | `@blocking`          | Полностью последовательное | Максимальная   | Отладка, обучение новичков, критический код |
| **L2**  | Явный spawn         | `spawn`               | Контролируемый разработчиком параллелизм | Средняя      | Продвинутые пользователи, тонкий контроль |
| **L3**  | Полностью прозрачный| Нет (по умолчанию)    | Автоматическая оптимальная параллелизация | Минимальная | Эксперты, автоматическая оптимизация параллелизма |

### 3.2 L1: синхронный режим `@blocking`

**Основные характеристики**: отключение всех оптимизаций параллелизма, полностью последовательное выполнение для удобства отладки и понимания.

```yaoxiang
# L1: синхронный режим @blocking (аннотация после типа возврата)
fetch_sync: (String) -> JSON @blocking = (url) => {
    HTTP.get(url).json()
}

main: () -> Void @blocking = () => {
    # Строго последовательное выполнение, без параллелизма
    data1 = fetch_sync("https://api.example.com/data1")
    data2 = fetch_sync("https://api.example.com/data2")
    process(data1, data2)
}
```

### 3.3 L2: явный параллелизм spawn

**Основные характеристики**: разработчик явно помечает параллельные единицы, сохраняя контролируемость при получении преимуществ параллелизма.

```yaoxiang
# L2: явный параллелизм spawn
fetch_data: (String) -> JSON spawn = (url) => {
    HTTP.get(url).json()
}

process_users_and_posts: () -> Void spawn = () => {
    users = fetch_data("https://api.example.com/users")
    posts = fetch_data("https://api.example.com/posts")
    # users и posts автоматически выполняются параллельно
    print(users.length.to_string())
    print(posts.length.to_string())
}

# Явный параллельный блок
compute_all: () -> (Int, Int, Int) spawn = () => {
    (a, b, c) = spawn {
        heavy_calc(1),
        heavy_calc(2),
        heavy_calc(3)
    }
    (a, b, c)
}
```

### 3.4 L3: полностью прозрачный (по умолчанию)

**Основные характеристики**: без каких-либо маркеров, компилятор автоматически анализирует зависимости и генерирует оптимальный план параллельного выполнения.

```yaoxiang
# L3: полностью прозрачный (режим по умолчанию)
heavy_calc: (Int) -> Int = (n) => {
    fibonacci(n)
}

auto_parallel: (Int) -> Int = (n) => {
    # Система автоматически анализирует: a, b, c без зависимостей, могут выполняться полностью параллельно
    a = heavy_calc(1)
    b = heavy_calc(2)
    c = heavy_calc(3)
    a + b + c
}
```

### 3.5 Ручные управляющие аннотации

| Аннотация | Поведение          | Сценарий использования             |
| --------- | ------------------ | ------------------------------------ |
| `@eager`  | Принудительная eager-оценка | Вычисления, требующие немедленного получения результата |

## 二、Основные концепции

### 2.1 Граф Spawn: сцена для «всех существ»

Все программы при компиляции преобразуются в **ориентированный ациклический граф вычислений (DAG)**, который мы называем **графом Spawn**.

| Элемент  | Описание                                                           |
| -------- | ------------------------------------------------------------------ |
| **Узел** | Представляет вычислительную единицу выражения                     |
| **Ребро**| Представляет отношение зависимости данных (A → B означает, что B зависит от результата A) |
| **Ленивость** | Узел вычисляется только тогда, когда его вывод **реально нужен** |

### 2.2 Ленивая оценка по умолчанию

Все функции по умолчанию используют стратегию **ленивой оценки**:

```yaoxiang
# Заголовок скрипта: настройка количества параллельных ядер
# @cores: 4

# Все функции по умолчанию лениво вычисляются (опционально параллельны)
heavy_computation: (Int) -> Int = (x) => {
    # Эта функция не будет выполнена немедленно
    # Выполняется только когда результат используется
    fibonacci(x)
}

main: () -> Void = () => {
    # heavy_computation возвращает Int, тип — Lazy[Int]
    result = heavy_computation(100)

    # Здесь result используется в сложении, что триггерит вычисление
    # Система автоматически находит оптимальное время для параллельного выполнения
    total = result + heavy_computation(200)
}
```

### 2.3 Аннотации смешанной оценки (стиль декораторов)

Аннотации в YaoXiang аналогичны декораторам Python (decorator), используемым для изменения поведения функций или выражений:

| Аннотация (декоратор) | Поведение                                 |
| --------------------- | ----------------------------------------- |
| `@eager`              | **Декоратор**: принудительная eager-оценка, немедленное выполнение |
| `@auto`               | **Декоратор**: сохранение параллелизма (по умолчанию, можно опустить) |

**Правило автоматической eager для Void:** Функции, возвращающие `Void`, автоматически вычисляются eagerly (без каких-либо аннотаций), потому что побочные эффекты должны выполняться.

```yaoxiang
# Декоратор @eager: принудительная eager-оценка
heavy_computation: (Int) -> Int = (x) => {
    fibonacci(x)
}

# Функции, возвращающие Void, автоматически вычисляются eagerly (функции с побочными эффектами)
log: (String) -> Void = (message) => {
    print(message)
}

main: () -> Void = () => {
    # log автоматически выполняется eagerly, потому что возвращает Void
    log("Processing started")

    # Использование @eager для принудительной eager-оценки
    @eager heavy_computation(100)
}
```

### 2.4 Значение Spawn: ленивый прокси-тип Async[T]

Любая функция, тип возврата которой помечен как `-> T spawn`, немедленно возвращает значение типа `Async[T]`, которое мы называем **значением Spawn**.

```yaoxiang
# Функция spawn: тип возврата помечен как -> JSON spawn
# Указывает, что это строго параллельно выполняемая вычислительная единица
fetch: (String) -> JSON spawn = (url) => {
    HTTP.get(url).json()
}

main: () -> Void = () => {
    # fetch возвращает значение spawn типа Async[JSON]
    # Но при использовании не требуется никакого дополнительного синтаксиса
    data = fetch("https://api.example.com")  # Async[JSON]

    # Здесь data автоматически ожидает и распаковывается в JSON
    print(data.name)  # Естественно, как синхронный код
}
```

#### Основные характеристики значений Spawn

| Характеристика       | Описание                                                                              |
| -------------------- | ------------------------------------------------------------------------------------- |
| **Прозрачность синтаксиса** | `Async[T]` является подтипом `T` в системе типов, может использоваться в любом контексте, ожидающем `T` |
| **Ожидание по требованию** | Когда необходимо использовать конкретное значение типа `T` (например, доступ к полю, арифметические операции), среда выполнения автоматически приостанавливает и ожидает |
| **Распространение ошибок** | Внутри представляет собой `Result<T, E>`, ошибки естественно распространяются по потоку данных |

### 2.7 Конструкции Spawn: от «модификатора» к «маркеру типа»

Ключевое слово `spawn` — единственный мост между синхронным мышлением и асинхронной реализацией, имеющий три семантических значения:

| Синтаксическая форма         | Официальный термин | Семантика                                               | Поведение времени выполнения                                                                         |
| :--------------------------- | :------------------ | :------------------------------------------------------ | :---------------------------------------------------------------------------------------------------- |
| **`-> T spawn`**             | Функция spawn       | Маркер типа возврата, указывающий на строго параллельную вычислительную единицу | Её вызов возвращает `Async[T]`, означающий создание узла графа spawn                                 |
| **`spawn { ... }`**          | Блок spawn          | Явно объявленная область параллелизма                  | Среда выполнения **агрессивно** выполняет выражения внутри блока как независимые задачи параллельно, неявно ожидая всех результатов в конце блока |
| **`spawn for`**              | Цикл spawn          | Цикл с данным параллелизмом                             | Преобразует тело цикла в несколько параллельных задач, автоматически выполняя шардирование данных, планирование и сбор результатов |

## 三、Принцип работы: от кода к выполнению

### 3.1 Время компиляции: построение графа Spawn

```yaoxiang
# Определение функции spawn: тип возврата помечен как spawn
fetch: (String) -> String spawn = (url) => { ... }
parse: (String) -> Model spawn = (data) => { ... }

process: () -> Report = () => {
    # Компилятор создаёт узлы графа spawn здесь
    data_a = fetch("url1")  # Узел A: Async[String]
    data_b = fetch("url2")  # Узел B: Async[String]

    # Блок spawn: явная область параллелизма
    (model_a, model_b) = spawn {
        parse(data_a),  # Узел C: зависит от A
        parse(data_b)   # Узел D: зависит от B
    }

    # Финальное слияние в узел
    generate_report(model_a, model_b)  # Узел E
}
```

**Операции компилятора:**

1. Парсинг исходного кода, построение глобального графа spawn
2. Создание вычислительного узла для каждого выражения
3. Анализ зависимостей данных, установление рёбер
4. Подграфы внутри блоков `spawn { }` и `spawn for` помечаются флагом **«параллельная оценка»**

### 4.2 Время выполнения: планировщик Spawn

Интеллектуальный **планировщик Spawn** с поддержкой work-stealing отвечает за выполнение графа spawn:

```rust
// Основная логика планировщика Spawn
impl FlowScheduler {
    fn execute_node(&self, node_id: NodeId) {
        let node = self.get_node(node_id);

        match &node.kind {
            NodeKind::AsyncCompute => {
                // Функция spawn: отправка в пул корутин
                self.submit_async(node_id);
            }
            NodeKind::ParallelBlock => {
                // Блок spawn: агрессивное параллельное выполнение всех непосредственных дочерних узлов
                self.submit_parallel(node_id);
            }
            NodeKind::DataParallel { iterator, body } => {
                // Цикл spawn: автоматическое шардирование
                self.submit_data_parallel(node_id, iterator, body);
            }
            _ => { /* Синхронное выполнение */ }
        }
    }
}
```

#### Поток выполнения

```
1. Для оценки [E] нужны [C] и [D]
2. [C] зависит от [A], [D] зависит от [B]
3. Планировщик Spawn обнаруживает, что [A] и [B] независимы → немедленное параллельное выполнение
4. После завершения [A], [B], из-за пометки блока spawn → немедленное параллельное выполнение [C] и [D]
5. После завершения [C], [D] выполняется [E]
```

**Ключевые механизмы:**

| Механизм         | Описание                                               |
| ---------------- | ------------------------------------------------------ |
| **Ленивый триггер** | Выполнение начинается с запроса финального результата, обратный поиск зависимостей |
| **Автоматическое ожидание** | При встрече с `Async[T]` автоматическая приостановка, выполнение других готовых задач |
| **Work-stealing** | Потоки крадут задачи из очередей других потоков для повышения загрузки CPU |

## 四、Детальное описание ключевых механизмов

### 4.1 Побочные эффекты и гарантии оценки

Чистая ленивая оценка может привести к тому, что побочные эффекты (например, логирование, запись) никогда не будут выполнены. Модель Spawn использует **автоматический вывод на основе типа возврата**:

| Правило        | Условие                        | Поведение                                 |
| ------------- | ------------------------------ | ---------------------------------------- |
| **Правило 1** | Функция возвращает `Void`      | **Автоматическая eager-оценка** (побочные эффекты должны выполняться) |
| **Правило 2** | Выражение с декоратором `@eager` | **Принудительная eager-оценка** независимо от типа возврата |
| **Правило 3** | Возвращает тип, отличный от Void | **Ленивая оценка** (по умолчанию)         |

```yaoxiang
# Функции, возвращающие Void, автоматически выполняются eagerly (побочные эффекты)
log: (String) -> Void = (message) => {
    print(message)
}

# Декоратор @eager: принудительная eager-оценка
cache_compute: (Int) -> Int = (x) => {
    # Даже если возвращает Int, принудительно выполняется немедленно
    expensive_calculation(x)
}

main: () -> Void = () => {
    # log автоматически выполняется eagerly (возвращает Void)
    log("Processing started")

    # @eager принудительная eager-оценка
    @eager
    cache_compute(100)

    # Обычная функция с ленивой оценкой (возвращает Int)
    result = heavy_computation(200)  # Пока не выполняется
    print(result)  # Выполняется только здесь
}
```

### 4.2 Обработка ошибок

#### Определение типа Result

```yaoxiang
# Стандартный тип Result (унифицированный синтаксис конструктора)
type Result[T, E] = ok(T) | err(E)

# Пользовательский тип ошибки
type ParseError = invalid_format | unexpected_eof | position(Int)

parse_config: (String) -> Result[Config, ParseError] = (content) => {
    if content.is_empty() {
        err(invalid_format)
    } else {
        ok(parse(content))
    }
}
```

#### Синтаксис распространения ошибок

Используется оператор `?` в стиле Rust для прозрачного распространения ошибок:

```yaoxiang
# Оператор ? в стиле Rust
process() -> Result[Data, Error] = {
    data = fetch_data()?      # Автоматическое ожидание и проверка ошибок
    processed = transform(data)?
    save(processed)?          # Ошибки автоматически распространяются вверх
}

# Обработка ошибок через pattern matching
handle_result: (Result[Int, Error]) -> String = (result) => {
    match result {
        ok(value) => "Success: " + value.to_string()
        err(e) => match e {
            network_error => "Network failed"
            parse_error => "Parse failed"
            _ => "Unknown error"
        }
    }
}
```

### 4.3 Чистые функции и синхронные гарантии `@blocking`

**Ключевой инсайт: чистые функции не блокируют!**

Потому что:

- Чистые функции не имеют I/O, только CPU-вычисления
- Даже длительные вычисления не блокируют планировщик, только занимают время CPU

**Стратегия выполнения:**

| Тип функции                      | Стратегия выполнения        | Блокирует?              |
| --------------------------------- | ---------------------------- | ----------------------- |
| Чистая функция (без I/O)         | Синхронное выполнение       | Нет (только загрузка CPU) |
| Асинхронная функция (возвращает `Async[T]`) | Асинхронное выполнение  | Нет                     |
| Функция с аннотацией `@blocking` | Синхронное выполнение, внутреннее планирование | Нет                     |

**Аннотация `@blocking`: гарантия синхронного выполнения**

Аннотация `@blocking` гарантирует синхронное выполнение функции:

- При возврате функции результат уже готов
- Если внутри есть асинхронные вызовы, они завершаются внутри
- Подходит для сценариев, требующих синхронной семантики, но с возможными внутренними асинхронными операциями

```yaoxiang
# @blocking: синхронное выполнение, внутреннее асинхронное планирование завершается перед возвратом
heavy_compute: (List[Int]) -> Int = (data) => {
    # Внутри могут быть асинхронные операции, но завершаются до возврата
    processed = data.map(x => async_transform(x))
    processed.sum()
}

# Обычная асинхронная функция: возвращает Async[T]
fetch_user: (Int) -> Async[User] = (id) => {
    database.query("SELECT * FROM users WHERE id = ?", id)
}

# Чистая функция: автоматически синхронная (без I/O)
factorial: (Int) -> Int = (n) => {
    if n <= 1 then 1 else n * factorial(n - 1)
}

main: () -> Void = () => {
    # Функция @blocking: синхронное выполнение
    result = heavy_compute([1, 2, 3, 4, 5])  # Немедленно возвращает результат
    print(result)  # 15

    # Асинхронная функция: возвращает Async[User]
    user = fetch_user(123)  # Async[User]
    print(user.name)  # Автоматически ожидает и распаковывает
}
```

**Стратегия времени выполнения:**

```rust
fn execute_function(node: &DAGNode) {
    match node.execution_mode {
        ExecutionMode::Pure => {
            // Чистая функция: синхронное выполнение
            node.execute();
        }
        ExecutionMode::Async => {
            // Асинхронная функция: отправка в async-планировщик
            async_runtime.submit(node);
        }
        ExecutionMode::Blocking => {
            // Функция @blocking: синхронное выполнение, внутреннее планирование асинхронных операций
            execute_blocking(node);
        }
    }
}

fn execute_blocking(node: &DAGNode) {
    // Выполнение тела функции
    let result = node.execute_body();

    // Сбор всех внутренних асинхронных операций
    let internal_async_ops = collect_async_ops(node);

    // Ожидание всех внутренних асинхронных операций
    if !internal_async_ops.is_empty() {
        async_runtime.wait_all(internal_async_ops);
    }

    // Возврат результата
    result
}
```

**Преимущества дизайна:**

- **Простота**: не требуется сложная система эффектов
- **Гибкость**: `@blocking` опционален, используется при необходимости синхронной семантики
- **Эффективность**: чистые функции автоматически синхронные
- **Безопасность**: главный планировщик никогда не блокируется

### 4.4 Обнаружение конфликтов ресурсов

Компилятор анализирует паттерны доступа к ресурсам во время компиляции, автоматически сериализует конфликтующие операции:

```
Матрица правил конфликта ресурсов:
╔═══════════╦══════════╦══════════╗
║   Доступ  ║   Чтение ║ Запись   ║
╠═══════════╬══════════╬══════════╣
║   Чтение  ║ Параллельно ║ Сериализовать ║
║   Запись  ║ Сериализовать ║ Сериализовать ║
╚═══════════╩══════════╩══════════╝
```

**Пример анализа времени компиляции**:

```rust
// Анализ доступа к ресурсам при компиляции
struct ResourceAccess {
```

### 4.5 Контроль параллельных гонок: гарантия атомарности через систему типов

**Основная идея: пометка данных с параллельным доступом через систему типов, компилятор проверяет корректность синхронизации.**

**Система маркеров типов:**

| Тип         | Семантика        | Безопасность параллелизма | Описание                             |
| ----------- | ---------------- | ------------------------- | ------------------------------------ |
| `T`         | Неизменяемые данные | ✅ Безопасно             | Тип по умолчанию, многократное чтение несколькими задачами без гонок |
| `Ref[T]`    | Изменяемая ссылка | ⚠️ Требуется синхронизация | Помечен как модифицируемый параллельно, компилятор проверяет использование блокировок |
| `Atomic[T]` | Атомарный тип    | ✅ Безопасно             | Низкоуровневые атомарные операции, безблокировочный параллелизм |
| `Mutex[T]`  | Обёртка мьютекса  | ✅ Безопасно             | Автоматическая блокировка/разблокировка, компилятор гарантирует |
| `RwLock[T]` | Обёртка读写锁    | ✅ Безопасно             | Оптимизация для сценариев с большим чтением и малым количеством записей |

**Гарантии безопасности типов:**

```yaoxiang
# По умолчанию неизменяемо - естественно без гонок
data: List[Int] = [1, 2, 3, 4, 5]
spawn for x in data { process(x) }  # ✅ Безопасно, только чтение без гонок

# Изменяемая ссылка - требуется синхронизация
counter: Ref[Int] = Ref.new(0)

# Ошибочный пример: доступ к Ref без блокировки (ошибка компиляции)
spawn for i in 1..10 {
    # ❌ Ошибка компиляции: Ref должен быть доступен через примитивы синхронизации
    counter.value = counter.value + i
}

# Правильный пример: использование синтаксического сахара with для автоматической блокировки
spawn for i in 1..10 {
    # ✅ Блок with автоматически получает и освобождает блокировку
    with counter.lock() {
        counter.value = counter.value + i
    }
}

# Атомарный тип - безблокировочный параллелизм
atomic_counter: Atomic[Int] = Atomic.new(0)
spawn for i in 1..10 {
    # ✅ Атомарные операции, без блокировок безопасно
    atomic_counter.fetch_add(i)
}
```

**Тип Mutex[T] - гарантия блокировки при компиляции:**

```yaoxiang
# Создание данных, обёрнутых в мьютекс
shared_state: Mutex[Map[String, Int]] = Mutex.new(Map.empty())

# Использование синтаксического сахара with (подобно defer в Go)
main: () -> Void = () => {
    spawn for i in 1..100 {
        # with автоматически получает блокировку, автоматически освобождает в конце блока
        with shared_state.lock() {
            # Критическая секция: защищена мьютексом
            current = shared_state.get("count").or(0)
            shared_state.set("count", current + 1)
        }
    }

    # Ожидание завершения всех задач
    print(shared_state.get("count"))  # 100
}
```

**Вывод типов и проверка блокировок:**

```rust
// Компилятор проверяет при компиляции
fn compile_check_locks(func: &Function) {
    for node in func.nodes {
        match node {
            NodeKind::ReadRef(ref_var) => {
                // Проверка: находится ли внутри защищённой области блокировки
                if !is_inside_lock_guard(ref_var) {
                    compile_error!("Доступ к Ref должен быть в защищённой области lock()");
                }
            }
            NodeKind::WriteRef(ref_var, _) => {
                // Двойная проверка: блокировка + единственный писатель
                if !is_inside_lock_guard(ref_var) {
                    compile_error!("Модификация Ref должна быть в защищённой области lock()");
                }
                if has_multiple_writers(func, ref_var) {
                    compile_error!("Mutex[T] может иметь только одного писателя, используйте RwLock[T]");
                }
            }
            _ => {}
        }
    }
}
```

**Преимущества дизайна:**

| Преимущество           | Описание                                               |
| ---------------------- | ------------------------------------------------------ |
| **Проверка при компиляции** | Пропущенные блокировки обнаруживаются при компиляции, а не приводят к runtime deadlocks |
| **Нулевые накладные расходы** | Обёртка Mutex не имеет накладных расходов при отсутствии конфликтов |
| **Простой синтаксис**  | Синтаксический сахар `with lock() { ... }`, автоматическое управление жизненным циклом |
| **Безопасность типов** | Ошибочное использование Ref вместо Atomic приведёт к ошибке на уровне типов |

### 7.1 Базовая функция spawn

```yaoxiang
use std.net

fetch_user: (Int) -> User spawn = (id) => {

    response.json()

    # Автоматическое параллельное выполнение (без зависимостей)
    user = fetch_user(123)      # Async[User]
    posts = fetch_posts(123)    # Async[List[Post]]

    # Автоматически ожидает и распаковывает здесь
    print(user.name)            # Естественно, как синхронный код
    print(posts.length)
}
```

```yaoxiang

    }]
    # results здесь — это List, содержащий все результаты обработки
```
