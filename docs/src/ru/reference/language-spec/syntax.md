# Спецификация синтаксиса

Данный документ определяет спецификацию синтаксиса языка программирования YaoXiang, включая
лексическую структуру, правила грамматики и приоритет операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходный файл

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Категории лексем

| Категория      | Описание                                       | Пример                    |
| -------------- | ---------------------------------------------- | ------------------------- |
| Идентификатор  | Начинается с буквы или подчёркивания           | `x`, `_private`, `my_var` |
| Ключевое слово | Предопределённые зарезервированные слова языка | `Type`, `pub`, `use`      |
| Литерал        | Фиксированное значение                         | `42`, `"hello"`, `true`   |
| Оператор       | Символ операции                                | `+`, `-`, `*`, `/`        |
| Разделитель    | Синтаксический разделитель                     | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет крайне малое количество ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют специальное значение в любом контексте и не могут использоваться как
идентификаторы.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang разделены на три уровня и распознаются парсером и type checker на
разных этапах:

#### 1.4.1 Литеральные зарезервированные слова

Идентификаторы литералов, имеющие собственный token в парсере, не могут использоваться как обычные
идентификаторы:

| Идентификатор | Принадлежность к типу | Описание                                                                                                    |
| ------------- | --------------------- | ----------------------------------------------------------------------------------------------------------- |
| `Type`        | —                     | Ключевое слово метатипа                                                                                     |
| `true`        | Bool                  | Логическое значение «истина»                                                                                |
| `false`       | Bool                  | Логическое значение «ложь»                                                                                  |
| `void`        | Void                  | Литерал Void (значение Unit). Строчное `void` — литерал значения; прописное `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Конструкторы выражений

Следующие конструкторы распознаются парсером в контексте pattern matching и выражений:

| Конструктор | Принадлежность к типу | Описание                    |
| ----------- | --------------------- | --------------------------- |
| `some(T)`   | Option                | Конструктор варианта Option |
| `ok(T)`     | Result                | Успешный вариант Result     |
| `err(E)`    | Result                | Вариант ошибки Result       |

#### 1.4.3 Имена встроенных типов

Следующие имена типов предварительно зарегистрированы type checker и могут использоваться в позиции
типа без импорта. Парсер рассматривает их как обычные идентификаторы — **не являются
зарезервированными словами, могут быть затенены локальной привязкой (не рекомендуется)**.

| Имя типа | Логическое соответствие | Описание                                                                                                                                              |
| -------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)         | Тип-произведение с нулём полей, ровно один обитатель (литерал `void`, см. §1.4.1)                                                                     |
| `Never`  | ⊥ (ложь/пустой тип)     | Тип с нулём вариантов, ноль обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` выполняется для всех `T` (принцип взрыва). |
| `Int`    | —                       | Целое число со знаком                                                                                                                                 |
| `Float`  | —                       | Число с плавающей точкой                                                                                                                              |
| `Bool`   | —                       | Логическое значение: `true` / `false`                                                                                                                 |
| `Char`   | —                       | Unicode-символ                                                                                                                                        |
| `String` | —                       | Строка                                                                                                                                                |

### 1.5 Идентификаторы

Идентификаторы начинаются с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как placeholder для обозначения игнорируемого значения
- Идентификаторы, начинающиеся с подчёркивания, обозначают приватные члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей точкой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // При аннотации целевого типа как Array(T, N) литерал становится массивом фиксированной длины
```

> **Литерал словаря требует как минимум одну пару ключ-значение**: `{}` **не является** пустым
> словарём — это пустой блок (значение `Void`, см. [§2.9](#_2-9-块表达式)). Для пустого словаря
> используйте конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ Пустой словарь
> d = { "a": 1 }                       // ✅ Литерал словаря
> wrong = {}                           // ❌ Это не словарь, а пустой блок (Void)
> ```
>
> **Критерий — содержимое**: Грамматика `Dict` требует как минимум `String ':' Expr`, `{}` не имеет
> содержимого, на которое можно опереться, поэтому берётся нулевая форма блочной структуры. Непустая
> форма самоописывается содержимым (`{ "k": v }` имеет пары ключ-значение → словарь) — это однородно
> с тем, что `f = { 5 }` является значением `Int`, а не функцией: **тип определяется содержимым**.

> Set не имеет литеральной грамматики и представления в runtime — тип коллекции запланирован, при
> появлении требований будет дополнен по модели Dict (std.set + HeapValue::Set). Точка привязки
> литералов List/Dict определяется аннотацией контекстного типа: голый литерал и литерал с
> аннотацией `List(T)` дают расширяемый список; аннотация `Array(T, N)` непосредственно к литералу
> даёт массив фиксированной длины. Запрещено неявное преобразование List→Array.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе ошибка этапа компиляции E1002; пустой литерал с
>   ненулевым N также отвергается
> - Тип каждого элемента должен быть совместим с T, иначе ошибка этапа компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отвергаются на этапе парсинга
> - Когда N является символьной константой (параметр const функции, например `Array(Int, n)`),
>   проверка количества откладывается до этапа уточнения типов
> - Вложенные литералы массивов v1 (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отвергаются на этапе
>   компиляции, требуется явное поэтапное конструирование; рекурсивная привязка остаётся для
>   последующих версий

#### 1.6.5 List comprehension

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (запись миграции)**: Грамматика переменной итерации всегда была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный парсинг Pratt — после
> регистрации `'in'` как инфиксного оператора `x` поглощал бы `in items` как выражение membership.
> После исправления неидентификаторный pattern сразу завершается с ошибкой парсинга, а не
> откатывается к `_` (тихое проглатывание ошибки), как было в старой реализации. Сфера влияния:
> выражения вроде `[x for (a, b) in pairs]`, которые ранее могли быть разобраны, теперь выдают
> ошибку — эта форма никогда не имела определённого поведения (переменная всегда была `_`),
> направление ужесточения корректно, затрат на семантическую миграцию нет.

#### 1.6.6 Проверка членства

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool` — `true` при попадании, `false` при
> непопадании, ошибки не выдаёт. Семантическое разделение: `[]` — утверждение существования и
> извлечение значения (ошибка при провале), `in` — вопрос о наличии (промах — нормальный `false`).
> Правый операнд покрывает: List / Array / Dict (набор ключей) / Tuple / String (подстрока) / Range
> (интервал). `in` — предикат первого класса Хоара, на этапе уточнения типов выступает базисом для
> доказуемых утверждений этапа компиляции. (Set исключён из списка правых операндов — Set не имеет
> представления в runtime, см. §1.6.4)

## Глава 2: Правила грамматики

### 2.1 Классификация выражений

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Операторы                   | Ассоциативность |
| --------- | --------------------------- | --------------- |
| 1         | `()` `[]` `.` `?`           | Слева направо   |
| 2         | `as`                        | Слева направо   |
| 3         | Унарный префикс `!` `-` `+` | Справа налево   |
| 4         | `*` `/` `%`                 | Слева направо   |
| 5         | `+` `-`                     | Слева направо   |
| 6         | `..`                        | Слева направо   |
| 7         | `<<` `>>`                   | Слева направо   |
| 8         | `&` `\|` `^`                | Слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=` | Слева направо   |
| 10        | `and` `or`                  | Слева направо   |
| 11        | `if...else`                 | Справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`     | Справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) сильно связывают: только ниже вызова и доступа к
> члену, выше всех бинарных операторов. Следовательно, `!a == b` ≡ `(!a) == b` (Zig-подобная
> семантика); `!` — чисто унарная операция, не участвует в короткозамыкающем потоке управления,
> ортогональна ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение RFC-010).

> **Сила связывания Range**: `..` имеет силу (6, 7) — левая 6 ниже сложения (7), правая 7 поглощает
> сложение, но не поглощает равноуровневый `..`. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, правая ассоц.)                                                                  | После изменения ((6,7), левая ассоц.)                                             |
> | ------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (правый операнд `in` — уровень 4, `..` уровня 1 не может поглотить, фактически не парсится) | `x in (1..10)` — интервал как целый правый операнд `in`                           |
> | `0..n+2`     | `(0..n)+2` (ловушка правой ассоц.: верхняя граница поглощена, цикл `for` сразу E3004)                    | `0..(n+2)` — верхняя граница — арифметическое выражение                           |
> | `a == b..c`  | `a == (b..c)` (`..` уровень 1 < `==` уровень 3, естественно целиком)                                     | `a == (b..c)` — **семантика не меняется**, `..` по-прежнему выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                               | `1..(2*3)` — верхняя граница — арифметическое выражение                           |
> | `a..b..c`    | `a..(b..c)` (правоассоц. цепочка, бессмысленный Range в Range)                                           | `(a..b)..c` — **форма со step** (`c` — шаг)                                       |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` меняется с «успешный парсинг, но E3004»
> на «сразу работает»; `x in 1..10` — с «не парсится» на «проверка интервала»; `a..b..c` — с
> «бессмысленная вложенность» на «компонент step». Уровень 6 попадает между `+` (уровень 5) и `<<`
> (уровень 7), математическая конвенция: интервал — сильно связывающая конструкция, верхняя граница
> естественно является полным арифметическим выражением.

### 2.9 Блочное выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения инструкций**: Разделение между Stmt и поведение перевода строки (явное
> разделение `;`, завершение переводом строки, исключения продолжения строки, никогда не
> объединяемые `(`/`[` в начале строки) определены в
> [RFC-038](../design/rfc/draft/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения имеет ровно три интерпретации, определяемые **содержимым** за один проход:

| Форма               | Запись            | Тип                      | Пример           |
| ------------------- | ----------------- | ------------------------ | ---------------- |
| **Пустой блок**     | `{}`              | `Void`                   | `x: Void = {}`   |
| **Литерал словаря** | `{ "k": v, ... }` | `Dict(K, V)`             | `d = { "a": 1 }` |
| **Блок**            | `{ Stmt* Expr? }` | Тип хвостового выражения | `y = { 1 + 1 }`  |

**Порядок определения**:

1. `{}` (без содержимого) → **Пустой блок**, значение `Void`
2. Первый элемент — пара `String ':' Expr` → **Литерал словаря**
3. Иначе → **Блок**, значение даётся хвостовым выражением

> **Почему `{}` не является пустым словарём**: «Пустота» пустого словаря не может быть
> самоописывающей (он мог бы быть как `Dict(K, V)`, так и пустым блоком), а грамматика словаря
> [§1.6.4](#_1-6-4-集合) требует как минимум одну пару ключ-значение. При отсутствии содержимого
> берётся нулевая форма блочной структуры: это согласуется с `unsafe {}` / `spawn {}`, без введения
> специальных случаев. Для пустого словаря используйте `dict.new()`.
>
> **Почему функции требуют аннотации**: `f = { stmt }` — это **значение** (тип хвостового
> выражения), а не функция. Чтобы определить функцию, укажите аннотацию Fn: `f: () -> Int = { 5 }`.
> Это тот же принцип, что и для словаря: **тип определяется содержимым**, а не наличием аннотации.
> (Это правило заменяет решение «без аннотации → функция по умолчанию» из приложения D решения
> RFC-010a, см. его исправление.)

**Единая семантика**: значение всех блоков `{}` даётся **хвостовым выражением**, `return` —
нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| Обычный `{}` | Хвостовое выражение | `Void`           |
| `unsafe {}`  | Хвостовое выражение | `Void`           |
| `spawn {}`   | Хвостовое выражение | `Void`           |

**Ключевые принципы** (подробности см. в
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Когда последний элемент — **инструкция присваивания**, значение блока — `Void`; если нужно `Void`,
  пишите `Void` явно
- **`return` выходит за ближайшую границу функции** (проходит сквозь все блоки, не «возвращается в
  блок»), тип `Never`; `Never <: T'` выполняется для любого `T'` (принцип взрыва), поэтому может
  появляться в любой позиции возвращаемого типа
- Выражение в форме `= expr` непосредственно даёт значение

```yaoxiang
// Обычный блок {}: значение даётся хвостовым выражением
result = {
    x = compute()
    x                // Значение блока
}

// Блок unsafe {}: хвостовое выражение задаёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // Значение блока
}

// Блок spawn {}: хвостовое выражение задаёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // Значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // Проходит сквозь if и тело функции, выходит из функции
    }
    n * 2            // Хвостовое выражение
}
```

#### Является ли `name = { ... }` функцией или значением блока?

`name = { ... }` может быть как определением функции (RFC-007 «минимальная форма без параметров»),
так и привязкой значения блока. Согласно решению «аннотация в приоритете, функция по умолчанию»
(приложение D RFC-010a):

| Случай                           | Результат          | Пример                             |
| -------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)         | Функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип   | Функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — нефункциональный тип | **Значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                    | Функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация есть тип**: `x: Int = ...` объявляет `x` как `Int`, значит `{ ... }` вычисляется в
`Int`; `f: () -> Int = ...` объявляет `f` как функцию, значит `{ ... }` — тело функции.

Чтобы `{ ... }` вычислялся сразу, просто **укажите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: без аннотации по умолчанию
f = { 5 }        // f() = 5
```

#### Вложенные функциональные типы: каррирование или возврат функции?

Правая часть `->` во вложенном функциональном типе имеет два прочтения, различаемых **скобками**
(RFC-004):

| Запись                          | Значение            | Вызов                     |
| ------------------------------- | ------------------- | ------------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **Каррирование**    | `f(1)(2)`                 |
| `(a: Int) -> ((b: Int) -> Int)` | **Возврат функции** | `g(1)` возвращает функцию |

Основание: **аннотация есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, поэтому `g(1)` должна **быть** этой функцией, а не «следующей порцией
аргументов».

```yaoxiang
// Каррирование: две порции аргументов даются последовательно
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний слой — одна порция аргументов, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // Возвращённую функцию можно сохранить в переменную, передавать
```

Необособленный скобками вложенный `Fn` всегда каррируется (включая форму с параметрами типов из
RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // Каррирование
identity(5)      // → 5
```

**Проверка типов**: Скобки объявляют тип возврата, тело должно порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка: ожидается `() -> Int`, фактически `Int` (E1002).

### 2.11 Оператор распространения ошибки

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` — постфиксный оператор с тем же приоритетом, что и `.`. Для типа `Result(T, E)`:

- При `Ok(v)` извлекает значение `v` и продолжает выполнение
- При `Err(e)` распространяет ошибку вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // При успехе извлекает значение, при неудаче распространяет вверх
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — значение: привязка, передача, проверка членства
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// Форма со step (третий компонент, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика step**: в `a..b..c` `c` — шаг. Литерал `c = 0` отвергается на этапе компиляции;
> динамический `c` без проверки в runtime (семейство E6001; после внедрения системы ошибок
> повышается до Result). `c < 0` допустим, направление интервала инвертируется по знаку
> (`10..0..(-2)` — убывание).

### 2.13 Выражение ref

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (одна задача) или Arc
(между задачами), пользователю не нужно заботиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // Между задачами: компилятор автоматически выбирает Arc
```

### 2.14 Выражение unsafe

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и работы с сырыми указателями.
Используйте `return` для возврата определения типа в вышестоящую область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует разрешения unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // Сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Область видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней области
- Внешняя область видимости не может обращаться к переменным внутренней области
- Объявление переменных следует принципу «присваивание в приоритете»

```yaoxiang
// Блочная область видимости
{
    x = 10
    // x виден в данной области видимости
}
// x не виден за пределами данной области видимости

// Область видимости функции
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не виден за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск `x` по цепочке областей видимости наружу; если найден — присваивание, иначе —
  новое объявление
- `mut x = value`: явное новое изменяемое объявление, запрещено одноимённое с внешним
- В одной области видимости любое имя может быть объявлено только один раз

> **Подробное определение**: Полные правила областей видимости, объявления и механизма затенения
> переменных см. в [Спецификации системы модулей](./modules.md#第四章作用域).

### 3.3 Инструкция return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — **нелокальный выход**, выходящий за ближайшую **границу функции**
(проходит сквозь все блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается в блок»**.

**Тип**: `return e : Never` (при `e : T`). `Never <: T'` выполняется для любого `T'` (принцип
взрыва, см. [Система типов §2.2](./type-system.md)), поэтому `return` может появляться в любой
позиции возвращаемого типа без дополнительных правил.

**Связь с вычислением блока**: значение блока всегда есть **хвостовое выражение** (см. §2.9).
`{ return n }` как блок имеет значение `n` типа `Never`; одновременно `return` выполняет действие —
выход из функции. **Оба факта верны одновременно**, сосуществуя благодаря принципу взрыва.

`return` вместе с хвостовым выражением обеспечивают «досрочный возврат» без специальных правил для
`return` относительно функции — см.
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // Проходит сквозь if, выходит из функции (тип Never)
    }
    n * factorial(n - 1)  // Хвостовое выражение = значение блока
}
```

### 3.4 Инструкция break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает ближайший цикл `while`/`for`, поток управления переходит к коду
после тела цикла.

- **Выход только на ближайший уровень**: `break` всегда действует на ближайший содержащий его цикл.
  Для выхода из нескольких уровней вложенного цикла вынесите внутренний цикл в функцию и используйте
  `return`, либо используйте флаг (break/continue без меток; если в будущем будут введены метки
  циклов, они пойдут через RFC-процесс по синтаксису со стороны объявления цикла, вместе с
  многоточечным дизайном пайплайна доказательств)
- **Только внутри цикла**: `break` может появляться только в теле цикла `while`/`for` (включая
  вложенные блоки/if/match внутри тела); появление вне цикла — ошибка компиляции (E1102
  `'break' outside of a loop`)
- **Не влияет на доказательство завершимости**: цикл `while` по-прежнему должен быть доказуемо
  завершающимся (метрика decreases); `break` не участвует в аргументации завершимости,
  `while true { break }` не будет принято
- **Семантика заимствования**: ребро потока управления break участвует в структурном разрезе
  обратного BFS-анализа живости RFC-009a (пропущенные итерации не участвуют в выводе живости
  обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // Поток управления переходит после цикла, i == 3
    }
}

// Вложенные циклы: break выходит только из внутреннего
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // Завершает только внутренний цикл
    }
    j = j + 1                  // Каждая итерация внешнего цикла доходит сюда
}
```

### 3.5 Инструкция continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся инструкции текущей итерации, сразу переходит к следующей
итерации ближайшего цикла — `while` возвращается к переоценке условия, `for` берёт следующий
элемент.

- **Действует только на ближайший уровень**: как `break`, без меток
- **Только внутри цикла**: появление вне цикла — ошибка компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // Пропускает накопление ниже, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Инструкция for

ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block

#### 3.9.1 Семантика: каждая итерация — новая привязка значения

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация создаёт новую
привязку значения, а не модифицирует ту же переменную**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Процесс выполнения**:

| Итерация   | Поведение переменной цикла                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------- |
| 1-я        | Создаётся новая привязка `i = 1`, выполняется тело, печатается 1                                  |
| 2-я        | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), выполняется тело, печатается 2 |
| 3-я        | Создаётся новая привязка `i = 3`, выполняется тело, печатается 3                                  |
| 4-я        | Создаётся новая привязка `i = 4`, выполняется тело, печатается 4                                  |
| Завершение | Тело цикла завершается, привязка уничтожается                                                     |

**Ключевой момент**: после завершения каждой итерации созданная в ней привязка уничтожается.
Следующая итерация — совершенно новая привязка, никак не связанная с предыдущей.

#### 3.9.2 Различие между for и for mut

| Синтаксис           | Изменяемость переменной цикла | Описание                                    |
| ------------------- | ----------------------------- | ------------------------------------------- |
| `for i in 1..5`     | Неизменяемая                  | Нельзя модифицировать привязку в теле цикла |
| `for mut i in 1..5` | Изменяемая                    | Можно модифицировать привязку в теле цикла  |

```yaoxiang
// Допустимо: каждая итерация привязывает новое значение, модификация не нужна
for i in 1..5 {
    print(i)  // Чтение значения i
}

// Ошибка: неизменяемая привязка, модифицировать нельзя
for i in 1..5 {
    i = i + 1  // Ошибка: нельзя модифицировать неизменяемую привязку
}

// Допустимо: for mut разрешает модификацию привязки
for mut i in 1..5 {
    i = i + 1  // Модификация разрешена
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлен снаружи
i = 10
for i in 1..5 {
    print(i)
}

// Правильно: используйте другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробности см. в
[4.3 Правила затенения](./modules.md#43-遮蔽规则).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                                 |
| -------- | -------------------------------------------------------------- |
| YaoXiang | Каждая итерация — новая привязка                               |
| Rust     | Модификация той же переменной (требуется mut)                  |
| Python   | Модификация той же переменной (mut не нужен)                   |
| C/C++    | Модификация той же переменной (требуется указатель или ссылка) |

**Обоснование дизайна**: YaoXiang использует семантику привязки по следующим причинам:

1. **Более естественная семантика** В естественном языке «для каждого элемента x в коллекции»
   означает, что каждый x — самостоятельная сущность. `for i in 1..5` в YaoXiang читается как «для
   каждого i от 1 до 5», каждая итерация i — совершенно новая привязка, что согласуется с
   человеческой интуицией.

2. **Предотвращение случайных модификаций** Неизменяемая по умолчанию семантика привязки означает,
   что в теле цикла невозможно случайно модифицировать переменную цикла. Не нужно беспокоиться о
   том, что где-то в сложном теле цикла случайно написано `i = ...` и приводит к
   трудноотслеживаемому багу.

3. **Высокопроизводительное решение под рукой** Когда действительно нужно переиспользовать
   переменную между итерациями (например, аккумулятор, кеш), используйте `for mut` для переключения
   в режим изменяемой привязки. Это яснее неявного разделяемого состояния — намерение выражается
   явно через синтаксис, а не скрывается в поведении runtime.

### 3.10 Инструкция spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn блок**: явное объявление параллельной области, выражения внутри блока выполняются
параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn цикл**: параллельный по данным цикл.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn блок захватывает переменные внешней области** (RFC-024 §2.3, семантика захвата значения):

- Тело блока ссылается на переменные внешней области = **захват значения Move**: значение снимается
  в замыкание в точке создания spawn, тело блока читает его через env (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешняя переменная не затрагивается
- **Ссылочные типы** (Struct/String/List и т.д.) снимок = копия ссылки, общий базовый объект;
  Embedded runtime (по умолчанию) — один поток, одна куча, ссылка действительна
- Для разделения между несколькими задачами требуется явный `ref` (§2.13, компилятор автоматически
  выбирает Rc/Arc)
- `return` в блоке, ссылающийся на внешние переменные, также выполняет их захват

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 захватываются по значению, result == 6
}
```

### 3.11 Точка входа программы и инструкции верхнего уровня

Исходный файл в глазах компилятора играет две роли, **определяемые наличием `yaoxiang.toml`**:

| Роль       | Определение                                              | Тело программы                                                                              |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Script** | Одиночный файл запускается напрямую, без `yaoxiang.toml` | **Инструкции верхнего уровня** (выполняются в порядке написания); `main` — обычная привязка |
| **Bin**    | Существует `yaoxiang.toml`                               | **Функция `main`**; на верхнем уровне запрещены исполняемые инструкции                      |

#### Script: инструкции верхнего уровня — это программа

Без manifest файл является «скриптом», **инструкции верхнего уровня выполняются в порядке
написания**:

```yaoxiang
use std.io
io.println("hello")          // Выполняется напрямую
x: Int = { 42 }              // Привязка верхнего уровня: инициализация в runtime
io.println(x)                // 42
```

`main` в этом режиме **не особенный** — это просто обычная привязка. Чтобы `main` запустился, его
нужно явно вызвать:

```yaoxiang
use std.io
main: () -> Void = { io.println("запускается только при вызове") }

main()                       // ← Эту строку нужно написать
```

> **Почему `main` не вызывается автоматически?** Инструкции верхнего уровня уже являются телом
> программы. Если ещё и неявно вызывать `main`, скрипт с явно написанным `main()` будет выполнен
> дважды. Оба правила не могут сосуществовать, поэтому в режиме Script есть только одна точка входа
> — «инструкции верхнего уровня».

#### Bin: `main` — точка входа

При наличии manifest файл является «исполняемой целью», в этом случае:

- `main` должен быть определён, и он должен быть функцией (сигнатура должна допускать вызов с нулём
  аргументов)
- На верхнем уровне запрещены исполняемые инструкции — тело программы и есть `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не-функция — обе ошибки компиляции (первая: без `main` все функции
недостижимы; вторая: привязка-значение не будет вызвана).

> **Файлы библиотек**: Файлы, которые `use`-ятся другими файлами, или файлы, на которые указывают
> `[lib].path` / `[exports]`, не требуют `main` — они не являются точкой входа в программу.

#### Инициализация привязок верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются в runtime**, не требуя, чтобы они были
константами этапа компиляции:

```yaoxiang
answer: Int = { 42 }              // Значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // Вызов функции
```

Инициализация выполняется в **порядке зависимостей**, независимо от порядка написания:

```yaoxiang
derived: Int = base * 3           // Ссылается на base, объявленный ниже
base: Int = 7                     // Инициализируется первым (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (с перечислением имён в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // Ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель роли файла), приложение D RFC-010a (решение о блочной
> привязке).
