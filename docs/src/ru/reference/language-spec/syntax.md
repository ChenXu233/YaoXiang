# Синтаксические спецификации

В данном документе определяются синтаксические спецификации языка программирования YaoXiang, включая лексическую структуру, синтаксические правила и приоритеты операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходные файлы

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение `.yx`.

### 1.2 Классификация лексем

| Категория | Описание               | Примеры                        |
| --------- | ---------------------- | ------------------------------ |
| Идентификатор | Начинается с буквы или подчёркивания | `x`, `_private`, `my_var` |
| Ключевое слово | Зарезервированные слова языка   | `Type`, `pub`, `use`      |
| Литерал   | Фиксированное значение | `42`, `"hello"`, `true`   |
| Оператор  | Знаки операций         | `+`, `-`, `*`, `/`        |
| Разделитель | Синтаксические разделители | `(`, `)`, `{`, `}`, `,` |

### 1.3 Ключевые слова

YaoXiang определяет минимальное количество ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют особое значение в любом контексте и не могут использоваться как идентификаторы.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang делятся на три уровня, распознаваемые парсером (parser) и проверяющим типы (type checker) на разных этапах:

#### 1.4.1 Зарезервированные слова-литералы

Литеральные идентификаторы, имеющие отдельные токены в парсере, не могут использоваться как обычные идентификаторы:

| Идентификатор | Принадлежность к типу | Описание                                                                              |
| ------------- | --------------------- | ------------------------------------------------------------------------------------- |
| `Type`        | —                     | Ключевое слово метатипа                                                               |
| `true`        | Bool                  | Логическое истинное значение                                                           |
| `false`       | Bool                  | Логическое ложное значение                                                            |
| `void`        | Void                  | Литерал Void (значение Unit). Строчная `void` — это значение-литерал; заглавная `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Конструкторы выражений

Следующие конструкторы распознаются парсером в контексте pattern matching и выражений:

| Конструктор   | Принадлежность к типу | Описание                     |
| ------------- | --------------------- | ---------------------------- |
| `some(T)`     | Option                | Вариант-конструктор значения Option |
| `ok(T)`       | Result                | Вариант успеха Result        |
| `err(E)`      | Result                | Вариант ошибки Result        |

#### 1.4.3 Имена встроенных типов

Следующие имена типов предварительно зарегистрированы проверяющим типы и могут использоваться в позиции типа без импорта. Парсер рассматривает их как обычные идентификаторы — **не как зарезервированные слова, могут быть перекрыты локальными привязками (shadow, не рекомендуется)**.

| Имя типа  | Логическое соответствие | Описание                                                                                                            |
| --------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `Void`    | ⊤ (истина/Unit)        | Тип-произведение с нулевым количеством полей, ровно один обитатель (`void` литерал, см. §1.4.1)                    |
| `Never`   | ⊥ (ложь/пустой тип)   | Тип с нулевым количеством вариантов, ноль обитателей. Ни одно выражение не может произвести значение `Never`. `Never <: T` верно для всех `T` (принцип взрыва). |
| `Int`     | —                      | Знаковое целое                                                                                                     |
| `Float`   | —                      | Число с плавающей запятой                                                                                          |
| `Bool`    | —                      | Логическое значение: `true` / `false`                                                                              |
| `Char`    | —                      | Символ Unicode                                                                                                      |
| `String`  | —                      | Строка                                                                                                             |

### 1.5 Идентификаторы

Идентификаторы начинаются с буквы или подчёркивания, последующие символы могут быть буквами, цифрами или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заполнитель, означающий игнорирование значения
- Идентификаторы, начинающиеся с подчёркивания, обозначают приватные члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей запятой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // При аннотации типа Array(T, N) литерал становится массивом фиксированной длины
```

> **Литерал словаря требует хотя бы одной пары ключ-значение**: `{}` **не является** пустым словарём — это пустой блок (значение `Void`, см. [§2.9](#_2-9-блок-выражения)). Для пустого словаря используйте конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ Пустой словарь
> d = { "a": 1 }                       // ✅ Литерал словаря
> wrong = {}                           // ❌ Это не словарь, а пустой блок (Void)
> ```
>
> **Критерий — содержимое**: грамматика `Dict` требует хотя бы одну пару `String ':' Expr`, `{}`
> не имеет содержимого, поэтому выбирается нулевая форма блочной структуры. Непустая форма описывается содержимым (`{ "k": v }` имеет пару ключ-значение → словарь) — это аналогично тому, как `f = { 5 }` является значением `Int`, а не функцией: **тип определяется содержимым**.

> Set не имеет грамматики литерала и run-time представления — тип множества запланирован, при появлении спроса будет добавлен по аналогии с Dict (std.set + HeapValue::Set). Точка назначения литералов List/Dict определяется контекстной аннотацией типа: «голый» литерал с аннотацией `List(T)` попадает в расширяемый список; аннотация `Array(T, N)` непосредственно作用于 литерала попадает в массив фиксированной длины. Неявное преобразование List→Array запрещено.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе ошибка компиляции E1002; пустой литерал с ненулевым N также отклоняется
> - Тип каждого элемента должен быть совместим с T, иначе ошибка компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя константы; составные выражения (например `2+1`) отклоняются на этапе парсинга
> - Когда N является символьной константой (параметр функции const, например `Array(Int, n)`), проверка количества элементов откладывается до этапа уточнённых типов
> - Вложенные массивные литералы (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отклоняются на этапе компиляции, требуется послойное явное построение; рекурсивная точка назначения оставлена для будущих версий

#### 1.6.5 Генератор списка (List comprehension)

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (заметка о миграции)**: грамматика итерационной переменной изначально была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный pratt-парсинг — после того как `'in'` был зарегистрирован как инфиксный оператор, `x`
> поглощал `in items`
> как выражение membership. После исправления неидентификаторный pattern сразу приводит к ошибке парсинга, вместо того чтобы в старой реализации откатываться к
> `_` (тихое поглощение ошибки). Затронутые случаи: ранее распознаваемая запись `[x for (a, b) in pairs]`
> теперь выдаёт ошибку — эта форма никогда не имела определённого поведения (переменная всегда была `_`), ужесточение корректно, без затрат на семантическую миграцию.

#### 1.6.6 Проверка принадлежности

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращает `Bool` — совпадение даёт `true`, отсутствие совпадения даёт `false`, без ошибок. Разделение семантики: `[]`
> утверждает существование и извлекает значение (неуспех вызывает ошибку), `in` спрашивает о существовании (отсутствие совпадения — нормальное `false`). Операнд справа охватывает: List /
> Array / Dict(множество ключей) / Tuple / String(подстрока) / Range(интервал). `in`
> является предикатом первого класса, на этапе уточнённых типов служит базой для доказуемых во время компиляции утверждений. (Set исключён из правого операнда — Set не имеет run-time представления, см. §1.6.4)

## Глава 2: Синтаксические правила

### 2.1 Классификация выражений

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритеты операторов

| Приоритет | Оператор                        | Ассоциативность |
| --------- | ------------------------------- | --------------- |
| 1         | `()` `[]` `.` `?`               | слева направо   |
| 2         | `as`                            | слева направо   |
| 3         | Унарный префикс `!` `-` `+`     | справа налево   |
| 4         | `*` `/` `%`                     | слева направо   |
| 5         | `+` `-`                         | слева направо   |
| 6         | `..`                            | слева направо   |
| 7         | `<<` `>>`                       | слева направо   |
| 8         | `&` `\|` `^`                    | слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=`     | слева направо   |
| 10        | `and` `or`                      | слева направо   |
| 11        | `if...else`                     | справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`         | справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) имеют тесное связывание: только ниже вызова и доступа к членам, выше всех бинарных операторов. Поэтому `!a == b`
> ≡ `(!a) == b` (семантика в стиле Zig); `!` — чисто унарная операция, не участвует в коротком замыкании потока управления, ортогональна ключевым словам `and`/`or`
> (короткое замыкание) (RFC-010 авторитетное определение).

> **Сила связывания Range**: `..` имеет силу связывания (6, 7) — левая 6 ниже сложения (7), правая 7 поглощает сложение, но не поглощает одноуровневый `..`. Сравнение до и после изменения:
>
> | Выражение          | До изменения (уровень 1, правая ассоциативность)                                           | После изменения ((6,7), левая ассоциативность)                       |
> | ------------------ | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
> | `x in 1..10`       | `x in 1..10` (`in` правый операнд уровня 4, `..` уровня 1 не может поглотить, реально не парсится) | `x in (1..10)` — интервал целиком как правый операнд `in`           |
> | `0..n+2`           | `(0..n)+2` (ловушка правой ассоциативности: верхняя граница поглощена, цикл `for` сразу E3004) | `0..(n+2)` — верхняя граница арифметическое выражение               |
> | `a == b..c`        | `a == (b..c)` (`..` уровня 1 < `==` уровня 3, естественно целиком)                         | `a == (b..c)` — **семантика без изменений**, `..` всё ещё выше уровня сравнения |
> | `1..2*3`           | `(1..2)*3`                                                                                  | `1..(2*3)` — верхняя граница арифметическое выражение               |
> | `a..b..c`          | `a..(b..c)` (правоассоциативная цепочка, бессмысленный Range в Range)                     | `(a..b)..c` — **форма step** (`c` — шаг)                            |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` из «парсится успешно, но E3004» становится «непосредственно применимо»; `x in 1..10` из «не парсится» становится «проверка интервала»; `a..b..c` из «бессмысленная вложенность» становится «компонент step». Уровень 6 находится между
> `+` (уровень 5) и `<<` (уровень 7), математическая традиция: интервал — тесно связанная конструкция, верхняя граница естественно полное арифметическое выражение.

### 2.3 Вызов функции

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

Именованные аргументы используют форму `name = value` (RFC-010 §определение функции, RFC-011
§конструктивные формы). Позиционные аргументы должны предшествовать именованным; параметры с порядковым указанием могут располагаться в любом порядке среди именованных аргументов:

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // Позиционная форма
add(a = 3, b = 5)  // Именованная форма
add(b = 5, a = 3)  // Произвольный порядок
add(3, b = 5)      // Смешанная, позиционные впереди
```

При неправильном имени именованного аргумента выдаётся **E1014**, если один и тот же параметр указан одновременно позиционно и по имени — **E1015**, при несовпадении количества — **E1010** (RFC-013).

### 2.4 Доступ к членам

```
MemberAccess::= Expr '.' Identifier
```

### 2.5 Индексный доступ

```
IndexAccess ::= Expr '[' Expr ']'
```

> **Трёхуровневая семантика (RFC-011b)**: `a[i]` разделяется по типу `a` — ① встроенные контейнеры
> (List/Vec/Array/Dict/Tuple) используют нативные индексные инструкции (быстрый путь); ② пользовательские типы, реализующие
> интерфейс `Index`, диспетчеризируют в свой метод `index` (экземпляр `Index(Grid, Int, Float)`
> в теле типа + метод `Grid.index`); ③ позиционная привязка `f[0]` из RFC-004 существует только в объявлении привязки,
> не проходит через данную грамматику. Многомерный индекс `a[0, 1]` упаковывает ключи в кортеж. Другие типы, не реализующие `Index`, отклоняются на уровне типов.

### 2.9 Блочные выражения

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения операторов**: Разделение и поведение при переносе строки между операторами Stmt (`;` явное разделение, перенос строки завершает, исключение для продолжения строки, `(`/`[` в начале строки никогда не объединяются) определяются [RFC-038](../../design/rfc/accepted/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения имеет ровно три интерпретации, определяемые **содержимым** за один проход:

| Форма             | Обозначение            | Тип           | Пример                |
| ----------------- | ---------------------- | ------------- | --------------------- |
| **Пустой блок**   | `{}`                   | `Void`        | `x: Void = {}`        |
| **Литерал словаря** | `{ "k": v, ... }`    | `Dict(K, V)`  | `d = { "a": 1 }`      |
| **Блок**          | `{ Stmt* Expr? }`      | Тип хвостового выражения | `y = { 1 + 1 }` |

**Порядок определения**:

1. `{}` (нет содержимого) → **пустой блок**, значение `Void`
2. Первый элемент — пара ключ-значение `String ':' Expr` → **литерал словаря**
3. Остальное → **блок**, значение определяется хвостовым выражением

> **Почему `{}` не является пустым словарём**: «Пустота» пустого словаря не может быть самоописательной (он может быть как `Dict(K, V)`, так и пустым блоком), а грамматика словаря [§1.6.4](#_1-6-4-коллекции)
> требует хотя бы одну пару ключ-значение. Когда нет содержимого для определения, выбирается нулевая форма блочной структуры: это согласуется с `unsafe {}` / `spawn {}`,
> не создаёт исключений. Пустой словарь использует `dict.new()`.
>
> **Почему для функции нужна аннотация**: `f = { stmt }`
> является **значением** (тип хвостового выражения), не функцией. Для определения функции пишется аннотация Fn: `f: () -> Int = { 5 }`. Это тот же принцип, что и со словарём: **тип определяется содержимым**, не наличием или отсутствием аннотации. (Это правило из
> [RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md) приложение D.)

**Единая семантика**: значение всех блоков `{}` определяется **хвостовым выражением**, `return` — это нелокальный выход типа `Never`.

| Тип блока   | Выход значения | Пустой блок `{}` |
| ----------- | -------------- | ---------------- |
| Обычный `{}` | Хвостовое выражение | `Void`    |
| `unsafe {}` | Хвостовое выражение | `Void`    |
| `spawn {}`  | Хвостовое выражение | `Void`    |

**Основной принцип** (подробнее [RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Когда в конце стоит **оператор присваивания**, значение блока `Void`; для получения `Void` пишется явное `Void`
- **`return` выходит из ближайшей границы функции** (проходит сквозь все блоки, не «возвращает блоку»), тип `Never`; `Never <: T`
  верно для любого типа (принцип взрыва), поэтому `return` может появляться в любой позиции возвращаемого типа
- Форма выражения `= expr` непосредственно даёт значение

```yaoxiang
// Обычный {} блок: хвостовое выражение даёт значение
result = {
    x = compute()
    x                // Значение блока
}

// unsafe {} блок: хвостовое выражение даёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // Значение блока
}

// spawn {} блок: хвостовое выражение даёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // Значение блока
}

// return: проходит сквозь блоки, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // Проходит сквозь if и тело функции, выход из функции
    }
    n * 2            // Хвостовое выражение
}
```

#### Является ли `name = { ... }` функцией или значением блока?

`name = { ... }`
может быть определением функции (RFC-007 «минимальная форма без параметров») или привязкой значения блока. Решение по принципу **«аннотация имеет приоритет, по умолчанию функция»** (RFC-010a приложение D):

| Ситуация               | Результат     | Пример                                 |
| ---------------------- | ------------- | -------------------------------------- |
| Значение — Lambda (`=>`) | Функция       | `f = () => 5` → `f()` = 5             |
| Аннотация — тип функции | Функция       | `f: () -> Int = { 5 }` → `f()` = 5    |
| Аннотация — не тип функции | **Значение блока** | `x: Int = { 5 }` → `x` = 5     |
| Без аннотации          | Функция       | `f = { 5 }` → `f()` = 5               |

**Аннотация — это тип**: `x: Int = ...` объявляет, что `x` — это `Int`, тогда `{ ... }` вычисляется в `Int`; `f: () -> Int = ...`
объявляет, что `f` — это функция, тогда `{ ... }` — тело функции.

Если нужно, чтобы `{ ... }` вычислялось сразу, **просто напишите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// 块值：立即求值
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: по умолчанию без аннотации
f = { 5 }        // f() = 5
```

#### Вложенные типы функций: каррирование или возврат функции?

Вложенный тип функции справа от `->` имеет два прочтения, различаемых **скобками** (RFC-004):

| Запись                             | Значение        | Вызов             |
| ---------------------------------- | --------------- | ----------------- |
| `(a: Int) -> (b: Int) -> Int`      | **Каррирование** | `f(1)(2)`        |
| `(a: Int) -> ((b: Int) -> Int)`    | **Возврат функции** | `g(1)` возвращает функцию |

Основание: **аннотация — это тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что `g(1) : (b: Int) -> Int`, поэтому
`g(1)` должен **быть** этой функцией, а не «следующей порцией параметров».

```yaoxiang
// Каррирование: две порции параметров подаются послойно
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешняя порция параметров, возвращённая才是 функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // Возвращённую функцию можно сохранить в переменную, передать
```

Вложенные `Fn` без скобок всегда означают каррирование (включая форму с параметром типа из RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // Каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют возвращаемый тип, тело должно производить этот тип. `f: () -> (() -> Int) = { 7 }` — ошибка — ожидается
`() -> Int`, фактически получен `Int` (E1002).

### 2.11 Оператор распространения ошибок

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` является постфиксным, приоритет на уровне `.`. Для типа `Result(T, E)`:

- При `Ok(v)` извлекает значение `v` и продолжает выполнение
- При `Err(e)` распространяет ошибку вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // При успехе извлекает значение, при неудаче распространяет вверх
    transform(validated)
}
```

### 2.12 Выражения диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — значение: привязка, передача, проверка членства
r = 1..10
assert.assert(5 in r, "членство")
for i in r { print(i) }

// Форма step (третья компонента, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика step**: в `a..b..c` `c` — шаг. Литерал `c = 0` отклоняется на этапе компиляции; динамический `c`
> проверяется на ноль во время выполнения (семейство ошибок E6001; после внедрения системы ошибок будет повышен до Result). `c < 0`
> допустим, направление интервала меняется на противоположное (`10..0..(-2)` убывает).

### 2.13 ref-выражение

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (однозадачность) или Arc (межзадачность), пользователю не нужно заботиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // Межзадачность: компилятор автоматически выбирает Arc
```

### 2.14 unsafe-выражение

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и операций с сырыми указателями. Использование `return` возвращает определение типа во внешнюю область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и оперировать сырыми указателями
- Возвращённые типы доступны за пределами `unsafe {}`
- Доступ к полям типа требует права unsafe

```yaoxiang
// 在 unsafe 块中定义不透明类型
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // Сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Область видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней области видимости
- Внешняя область видимости не может обращаться к переменным внутренней области видимости
- Объявление переменных следует принципу «присваивание имеет приоритет»

```yaoxiang
// Область видимости блока
{
    x = 10
    // x видна в этой области видимости
}
// x не видна за пределами этой области видимости

// 函数作用域
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не видна за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: ищет x по цепочке областей видимости наружу, находит — присваивает, не находит — объявляет заново
- `mut x = value`: явно объявляет новую изменяемую переменную, запрещено совпадение с именем во внешней области
- В одной области видимости каждое имя может быть объявлено только один раз

> **Подробное определение**: Полные правила области видимости, объявления переменных и механизма затенения описаны в [Спецификации системы модулей](./modules.md#глава-4-область-видимости).

### 3.3 Инструкция return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, выход из ближайшей **границы функции** (проходит сквозь все блоки — включая `if` / `while` / `for`
/ `match` / голый блок / `spawn` / `unsafe`), передаёт значение вызывающему. Он **не «возвращает блоку»**.

**Тип**: `return e : Never` (`e : T`). `Never <: T'` верно для любого `T'` (принцип взрыва, см.
[Система типов §2.2](./type-system.md)), поэтому `return` может появляться в любой позиции возвращаемого типа без дополнительных правил.

**Связь с вычислением блока**: Значение блока всегда **хвостовое выражение** (см. §2.9). `{ return n }` как блок имеет значение `n`, тип
`Never`; одновременно `return` выполняет выход из функции. **Оба события происходят одновременно**, сосуществуют благодаря принципу взрыва.

Совместное использование `return` и хвостового выражения делает «ранний возврат» работающим без необходимости в специальном правиле «`return` относится к функции» — см.
[RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // Проходит сквозь if, выход из функции (тип Never)
    }
    n * factorial(n - 1)  // Хвостовое выражение = значение блока
}
```

### 3.4 Инструкция break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает ближайший `while`/`for` цикл, управление передаётся после тела этого цикла.

- **Выход только из ближайшего уровня**: `break`
  всегда действует на содержащий его ближайший цикл. При необходимости выйти из нескольких уровней вложенности, выделите внутренний цикл в функцию и используйте `return`,
  или используйте флаг (break/continue без меток; если в будущем появятся метки циклов, они будут реализованы по синтаксису объявления цикла в рамках RFC-процесса, совместно с проектированием множественных выходов в конвейере доказательств)
- **Только внутри тела цикла**: `break` может появляться только внутри тела `while`/`for`
  (включая вложенные блоки/if/match внутри тела), появление вне цикла вызывает ошибку компиляции (E1102 `'break' outside of a loop`)
- **Не влияет на доказательство завершения**: `break`
  не участвует в обосновании завершения — он не предоставляет меру, не является убывающим шагом меры; обязательство по завершению цикла не связано с `break`,
  а возлагается на уточнённые типы (см. [система типов §8.4](./type-system.md#84-предикат-меры-terminatesзавершение))
- **Заимствование семантики**: управление потоком через break участвует в структурном обрыве анализа активности обратного BFS RFC-009a (вышедшие итерации не участвуют в выведении активности обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // Управление передаётся после цикла, i == 3
    }
}

// 嵌套循环：break 只出内层
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // Завершает только внутренний цикл
    }
    j = j + 1                  // Внешняя итерация выполняется каждую итерацию
}
```

### 3.5 Инструкция continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации, непосредственно переходит к следующему витку ближайшего цикла — `while` возвращается к проверке условия, `for` берёт следующий элемент.

- **Действует только на ближайший уровень**: аналогично `break`, без меток
- **Только внутри тела цикла**: появление вне цикла вызывает ошибку компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // Пропускает следующее суммирование, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Инструкция for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация связывает новое значение

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация связывает новое значение, а не модифицирует одну и ту же переменную**.

```yaoxiang
// 示例：for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Процесс выполнения**:

| Итерация | Поведение переменной цикла                                      |
| -------- | --------------------------------------------------------------- |
| Первая  | Создаётся новая привязка `i = 1`, выполняется тело, печатается 1 |
| Вторая  | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), выполняется тело, печатается 2 |
| Третья  | Создаётся новая привязка `i = 3`, выполняется тело, печатается 3 |
| Четвёртая | Создаётся новая привязка `i = 4`, выполняется тело, печатается 4 |
| Конец   | Тело цикла завершено, привязка уничтожена                       |

**Ключевой момент**: после завершения каждой итерации привязка, созданная в эту итерацию, уничтожается. Следующая итерация — это совершенно новая привязка, не имеющая никакого отношения к привязке предыдущей итерации.

#### 3.9.2 Разница между for и for mut

| Синтаксис               | Изменяемость переменной цикла | Описание                       |
| ----------------------- | ----------------------------- | ------------------------------ |
| `for i in 1..5`         | Неизменяемая                 | В теле цикла нельзя модифицировать привязку |
| `for mut i in 1..5`     | Изменяемая                   | В теле цикла можно модифицировать привязку |

```yaoxiang
// Допустимо: каждая итерация связывает новое значение, модификация не нужна
for i in 1..5 {
    print(i)  // Чтение значения i
}

// Ошибка: неизменяемая привязка, нельзя модифицировать
for i in 1..5 {
    i = i + 1  // Ошибка: нельзя модифицировать неизменяемую привязку
}

// Допустимо: использование for mut позволяет модифицировать привязку
for mut i in 1..5 {
    i = i + 1  // Допускается модификация
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может совпадать по имени с переменной во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлена снаружи
i = 10
for i in 1..5 {
    print(i)
}

// Правильно: использовать другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробнее [4.3 Правила затенения](./modules.md#43-правила-затенения).

#### 3.9.4 Сравнение с другими языками

| Язык      | Семантика переменной цикла for                 |
| --------- | ---------------------------------------------- |
| YaoXiang  | Каждая итерация связывает новое значение      |
| Rust      | Модифицирует одну и ту же переменную (нужен mut) |
| Python    | Модифицирует одну и ту же переменную (mut не нужен) |
| C/C++     | Модифицирует одну и ту же переменную (нужен указатель или ссылка) |

**Обоснование дизайна**: YaoXiang использует семантику связывания, потому что:

1. **Более соответствует естественной семантике** В естественном языке «для каждого элемента x из множества» означает, что каждый x — независимая сущность. YaoXiang `for i in 1..5`
   читается как «для каждого i от 1 до 5», i каждой итерации — совершенно новая привязка, что соответствует человеческой интуиции.

2. **Предотвращает случайные модификации**
   Семантика привязки по умолчанию неизменяемая означает, что в теле цикла невозможно случайно модифицировать переменную цикла. Не нужно беспокоиться о том, что где-то в сложном теле цикла случайно написано
   `i = ...`, вызывая трудноотслеживаемые ошибки.

3. **Высокопроизводительные решения легко доступны** Когда действительно нужно повторно использовать переменную между итерациями (например, аккумулятор, кэш), просто используйте `for mut`
   для переключения в режим изменяемой привязки. Это яснее неявного разделяемого состояния — намерение выражается синтаксически явно, а не скрывается в runtime-поведении.

### 3.10 Инструкция spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**Блок spawn**: явно объявляет границу параллелизма, выражения внутри блока выполняются параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**Цикл spawn**: цикл с data-level параллелизмом.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**Блок spawn захватывает внешние переменные** (RFC-024 §2.3, семантика захвата по значению):

- Ссылки на внешние переменные в теле блока =
  **Захват по значению Move**: значение снэпшотится в замыкание в точке создания spawn, тело читает через env (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешние переменные не затрагиваются
- **Типы-дескрипторы** (Struct/String/List и т.д.) снэпшот = копия дескриптора, разделяют нижележащий объект; Embedded runtime (по умолчанию) использует ту же нить и ту же кучу, дескриптор валиден
- Для разделения между несколькими задачами нужен явный `ref` (§2.13, компилятор автоматически выбирает Rc/Arc)
- Внешние переменные, на которые ссылается `return` внутри блока, также захватываются

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // Захват t1/t2 по значению, result == 6
}
```

### 3.11 Точка входа программы и операторы верхнего уровня

Исходный файл в глазах компилятора имеет две роли, **в зависимости от наличия `yaoxiang.toml`**:

| Роль        | Определение                          | Тело программы                                              |
| ----------- | ------------------------------------ | ---------------------------------------------------------- |
| **Script**  | Однофайловый запуск, без `yaoxiang.toml` | **Операторы верхнего уровня** (выполняются в порядке записи); `main` — обычная привязка |
| **Bin**     | Присутствует `yaoxiang.toml`        | **Функция `main`**; на верхнем уровне не должно быть исполняемых операторов |

#### Script: операторы верхнего уровня — это программа

Без manifest файл является «скриптом», **операторы верхнего уровня выполняются в порядке записи**:

```yaoxiang
use std.io
io.println("hello")          // Выполняется непосредственно
x: Int = { 42 }              // Привязка верхнего уровня: инициализация во время выполнения
io.println(x)                // 42
```

`main` в этом режиме **не особенная** — это просто обычная привязка. Чтобы `main` выполнялась, нужно вызвать её явно:

```yaoxiang
use std.io
main: () -> Void = { io.println("выполняется только при вызове") }

main()                       // ← Эта строка обязательна
```

> **Почему не автоматический вызов `main`?** Операторы верхнего уровня уже являются телом программы. Если ещё неявно вызывать `main`, скрипты с явно написанным `main()`
> будут выполняться дважды. Два правила несовместимы, поэтому в Script существует только один точка входа — «операторы верхнего уровня».

#### Bin: `main` — точка входа

С manifest файл является «исполняемой целью», в этом случае:

- `main` должен быть определён, и это должна быть функция (сигнатура должна позволять вызов без параметров)
- На верхнем уровне не допускаются исполняемые операторы — тело программы — это `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не является функцией — ошибка компиляции (первое: все функции недостижимы без `main`; второе: привязка значения не вызывается).

> **Библиотечные файлы**: Файлы, используемые другими файлами через `use`, или файлы, на которые указывают `[lib].path` / `[exports]`, не требуют
> `main` — они не являются точкой входа программы.

#### Инициализация связываний верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются во время выполнения**, не требуется быть константами времени компиляции:

```yaoxiang
answer: Int = { 42 }              // Значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // Вызов функции
```

Инициализация выполняется в **порядке зависимостей**, не зависит от порядка записи:

```yaoxiang
derived: Int = base * 3           // Ссылается на base, объявленный позже
base: Int = 7                     // Инициализируется первым (топологическая сортировка)
```

Циклическая зависимость — ошибка компиляции (будут перечислены имена в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // Ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель ролей файла), RFC-010a приложение D (разрешение привязок блоков).
