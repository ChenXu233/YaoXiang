# Спецификация синтаксиса

Этот документ определяет спецификацию синтаксиса языка программирования YaoXiang, включая
лексическую структуру, правила грамматики и приоритет операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходный файл

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Классификация лексических единиц

| Категория      | Описание                                 | Примеры                   |
| -------------- | ---------------------------------------- | ------------------------- |
| Идентификатор  | Начинается с буквы или подчёркивания     | `x`, `_private`, `my_var` |
| Ключевое слово | Предопределённое зарезервированное слово | `Type`, `pub`, `use`      |
| Литерал        | Фиксированное значение                   | `42`, `"hello"`, `true`   |
| Оператор       | Знак операции                            | `+`, `-`, `*`, `/`        |
| Разделитель    | Синтаксический разделитель               | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет минимальный набор ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют специальное значение в любом контексте и не могут использоваться в качестве
идентификаторов.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang разделены на три уровня, распознаваемых парсером (parser) и
проверщиком типов (type checker) на разных этапах:

#### 1.4.1 Литеральные зарезервированные слова

Идентификаторы литералов, имеющие собственные токены в парсере и не могущие использоваться как
обычные идентификаторы:

| Идентификатор | Тип  | Описание                                                                                                        |
| ------------- | ---- | --------------------------------------------------------------------------------------------------------------- |
| `Type`        | —    | Ключевое слово метайпа                                                                                          |
| `true`        | Bool | Логическое значение «истина»                                                                                    |
| `false`       | Bool | Логическое значение «ложь»                                                                                      |
| `void`        | Void | Литерал Void (значение Unit). Строчное `void` — это литерал значения; заглавное `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Конструкторы выражений

Следующие конструкторы распознаются парсером в контекстах сопоставления с образцом и выражений:

| Конструктор | Тип    | Описание                    |
| ----------- | ------ | --------------------------- |
| `some(T)`   | Option | Конструктор варианта Option |
| `ok(T)`     | Result | Успешный вариант Result     |
| `err(E)`    | Result | Ошибочный вариант Result    |

#### 1.4.3 Встроенные имена типов

Следующие имена типов предварительно зарегистрированы проверщиком типов и могут использоваться в
позициях типов без импорта. Парсер рассматривает их как обычные идентификаторы — **это не
зарезервированные слова, они могут быть затенены локальными привязками (не рекомендуется)**.

| Имя типа | Логический аналог   | Описание                                                                                                                                                |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)     | Тип-произведение с нулём полей, ровно один обитатель (литерал `void`, см. §1.4.1)                                                                       |
| `Never`  | ⊥ (ложь/пустой тип) | Тип с нулём вариантов и нулём обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` выполняется для всех `T` (принцип взрыва). |
| `Int`    | —                   | Знаковое целое число                                                                                                                                    |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                   |
| `Char`   | —                   | Символ Unicode                                                                                                                                          |
| `String` | —                   | Строка                                                                                                                                                  |

### 1.5 Идентификаторы

Идентификаторы начинаются с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заполнитель, обозначающий игнорируемое значение
- Идентификаторы, начинающиеся с подчёркивания, обозначают приватные члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей точкой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // При аннотации целевого типа как Array(T, N) литерал становится массивом фиксированной длины
```

> Set не имеет литеральной грамматики и не имеет представления во время выполнения — при
> проектировании типа множества, когда появится потребность, он будет дополнен по образцу Dict
> (std.set + HeapValue::Set). Куда попадают литералы List/Dict, определяется аннотацией контекстного
> типа: голый литерал и литерал с аннотацией `List(T)` становятся расширяемым списком; аннотация
> `Array(T, N)`, применённая непосредственно к литералу, делает его массивом фиксированной длины.
> Неявное преобразование List→Array запрещено.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе — ошибка компиляции E1002; пустой литерал с
>   ненулевым N также отклоняется
> - Тип каждого элемента должен быть совместим с T, иначе — ошибка компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отклоняются на этапе разбора
> - Когда N является символьной константой (const-параметр функции, например `Array(Int, n)`),
>   проверка количества откладывается до этапа уточнения типов
> - Вложенные литералы массивов версии v1 (например, `Array(Array(Int,2),2) = [[1,2],[3,4]]`)
>   отклоняются на этапе компиляции, требуется явное конструирование послойно; рекурсивное поведение
>   оставлено для будущих версий

#### 1.6.5 Генераторы списков

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (запись миграции)**: грамматика переменной итерации и так была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил через полный pratt-парсер — после
> регистрации `'in'` как инфиксного оператора `x` поглощал бы `in items` как выражение
> принадлежности. После исправления pattern, не являющийся идентификатором, сразу завершается
> неудачей при разборе, без отката к `_` (тихого проглатывания ошибки) как в старой реализации.
> Область влияния: записи вида `[x for (a, b) in pairs]`, которые раньше разбирались, теперь выдают
> ошибку — такая форма никогда не имела определённого поведения (переменная всегда была `_`),
> ужесточение корректно, без затрат на миграцию семантики.

#### 1.6.6 Проверка членства

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool` — `true` при попадании, `false` при
> непопадании, ошибки не возникает. Разделение семантики: `[]` — это утверждение существования и
> извлечение значения (ошибка при неудаче), `in` — это запрос о существовании (непопадание —
> нормальное `false`). Правый операнд покрывает: List / Array / Dict(множество ключей) / Tuple /
> String(подстрока) / Range(интервал). `in` — это предикат Хоара первого класса, на этапе уточнения
> типов служит базой для доказуемых утверждений времени компиляции. (Set исключён из списка правых
> операндов — Set не имеет представления во время выполнения, см. §1.6.4)

### 1.7 Комментарии

## Глава 2: Правила грамматики

### 2.1 Классификация выражений

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Операторы                      | Ассоциативность |
| --------- | ------------------------------ | --------------- |
| 1         | `()` `[]` `.` `?`              | Слева направо   |
| 2         | `as`                           | Слева направо   |
| 3         | Унарные префиксные `!` `-` `+` | Справа налево   |
| 4         | `*` `/` `%`                    | Слева направо   |
| 5         | `+` `-`                        | Слева направо   |
| 6         | `..`                           | Слева направо   |
| 7         | `<<` `>>`                      | Слева направо   |
| 8         | `&` `\|` `^`                   | Слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=`    | Слева направо   |
| 10        | `and` `or`                     | Слева направо   |
| 11        | `if...else`                    | Справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`        | Справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) сильно связывают: только ниже вызова и доступа к
> членам, выше всех бинарных операторов. Следовательно, `!a == b` ≡ `(!a) == b` (семантика в стиле
> Zig); `!` — чисто унарная операция, не участвует в управлении потоком с коротким замыканием,
> ортогональна ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение RFC-010).

> **Сила связывания Range**: `..` имеет силу связывания (6, 7) — левый 6 ниже сложения (7), правый 7
> поглощает сложение, но не поглощает тот же уровень `..`. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, правая ассоциативность)                                                         | После изменения ((6,7), левая ассоциативность)                                |
> | ------------ | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (правый операнд `in` уровня 4, `..` уровня 1 не может поглотить, фактически не разбирается) | `x in (1..10)` — интервал целиком как правый операнд `in`                     |
> | `0..n+2`     | `(0..n)+2` (ловушка правой ассоциативности: верхняя граница съедается, цикл `for` сразу выдаёт E3004)    | `0..(n+2)` — верхняя граница является арифметическим выражением               |
> | `a == b..c`  | `a == (b..c)` (`..` уровня 1 < `==` уровня 3, естественно целиком)                                       | `a == (b..c)` — **семантика не меняется**, `..` всё ещё выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                               | `1..(2*3)` — верхняя граница является арифметическим выражением               |
> | `a..b..c`    | `a..(b..c)` (цепочка правой ассоциативности, бессмысленный Range внутри Range)                           | `(a..b)..c` — **форма со шагом** (`c` — шаг)                                  |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` переходит от «успешный разбор, но
> E3004» к «сразу работает»; `x in 1..10` от «не разбирается» к «проверка интервала»; `a..b..c` от
> «бессмысленной вложенности» к «компоненту шага». Уровень 6 попадает между `+` (уровень 5) и `<<`
> (уровень 7), математическое соглашение: интервал — сильно связывающая конструкция, верхняя граница
> естественно является полным арифметическим выражением.

### 2.9 Блочное выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения операторов**: разделение между Stmt и поведение переноса строк (`;` как явный
> разделитель, завершение переносом строки, исключения для продолжения строки, начало строки с
> `(`/`[` никогда не объединяется) определяется в
> [RFC-038](../design/rfc/draft/038-statement-termination.md).

**Единая семантика**: значение всех блоков `{}` определяется **хвостовым выражением**, `return` —
это нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| Обычный `{}` | Хвостовое выражение | `Void`           |
| `unsafe {}`  | Хвостовое выражение | `Void`           |
| `spawn {}`   | Хвостовое выражение | `Void`           |

**Ключевые принципы** (подробности в
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Когда в конце стоит **оператор присваивания**, значение блока — `Void`; если нужно `Void` — пишите
  `Void` явно
- **`return` выходит за ближайшую границу функции** (проходит сквозь любые блоки, не «возвращается в
  блок»), тип `Never`; `Never <: T` выполняется для любого типа (принцип взрыва), поэтому может
  находиться в любой позиции возвращаемого типа
- Форма выражения `= expr` непосредственно даёт значение

```yaoxiang
// Обычный блок {}: хвостовое выражение даёт значение
result = {
    x = compute()
    x                // Значение блока
}

// Блок unsafe {}: хвостовое выражение даёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // Значение блока
}

// Блок spawn {}: хвостовое выражение даёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // Значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // Проходит сквозь if и тело функции, выходит из функции
    }
    n * 2            // Хвостовое выражение
}
```

#### `name = { ... }` — функция или значение блока?

`name = { ... }` может быть как определением функции (RFC-007 «пустой параметр — простейший
случай»), так и привязкой значения блока. Разрешение по принципу **аннотация имеет приоритет, по
умолчанию — функция** (RFC-010a, приложение D):

| Случай                            | Результат          | Пример                             |
| --------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)          | Функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип    | Функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — не-функциональный тип | **Значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                     | Функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация есть тип**: `x: Int = ...` объявляет, что `x` имеет тип `Int`, значит `{ ... }`
вычисляется в `Int`; `f: () -> Int = ...` объявляет, что `f` — функция, значит `{ ... }` — тело
функции.

Чтобы `{ ... }` вычислялся на месте, **просто напишите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: по умолчанию без аннотации
f = { 5 }        // f() = 5
```

#### Вложенные функциональные типы: каррирование или возврат функции?

Вложенный функциональный тип справа от `->` имеет два прочтения, различаемых **скобками** (RFC-004):

| Запись                          | Значение            | Вызов                   |
| ------------------------------- | ------------------- | ----------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **Каррирование**    | `f(1)(2)`               |
| `(a: Int) -> ((b: Int) -> Int)` | **Возврат функции** | `g(1)` получает функцию |

Принцип: **аннотация есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, значит `g(1)` **должна быть** той функцией, а не «следующей порцией
аргументов».

```yaoxiang
// Каррирование: две порции аргументов подаются по уровням
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний уровень — одна порция аргументов, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // Возвращённую функцию можно сохранить в переменную, передать
```

Не взятый в скобки вложенный `Fn` всегда является каррированием (включая форму с параметрами типа из
RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // Каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют тип возвращаемого значения, body должна порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка — ожидается `() -> Int`, фактически получено `Int` (E1002).

### 2.10 Лямбда-выражение

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 Оператор распространения ошибок

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` — постфиксный, с тем же приоритетом, что и `.`. Для типа `Result(T, E)`:

- При `Ok(v)` извлекается значение `v` и выполнение продолжается
- При `Err(e)` ошибка распространяется вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // Успех — извлечь значение, неудача — распространить вверх
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — это значение: привязка, передача, проверка членства
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// Форма со шагом (третий компонент, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика шага**: в `a..b..c` `c` — это шаг. Литерал `c = 0` отклоняется на этапе компиляции;
> динамический `c` проверяется во время выполнения (семейство E6001; после введения системы ошибок
> будет повышен до Result). `c < 0` допустимо, направление интервала меняется на обратное в
> зависимости от знака (`10..0..(-2)` убывает).

### 2.13 Выражение ref

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (одна задача) или Arc
(между задачами), пользователю не нужно заботиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // Между задачами: компилятор автоматически выберет Arc
```

### 2.14 Выражение unsafe

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и операций с сырыми указателями.
Использование `return` возвращает определение типа в охватывающую область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует полномочий unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // Сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Области видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней области видимости
- Внешняя область видимости не может обращаться к переменным внутренней области видимости
- Объявление переменных следует принципу «приоритет присваивания»

```yaoxiang
// Блочная область видимости
{
    x = 10
    // x виден в этой области видимости
}
// x не виден за пределами этой области видимости

// Функциональная область видимости
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не виден за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск `x` идёт наружу по цепочке областей видимости, если найден — присваивание, если
  не найден — новое объявление
- `mut x = value`: явное новое изменяемое объявление, запрещено совпадение имён с внешней областью
- В одной области видимости любое имя может быть объявлено только один раз

> **Подробное определение**: полные правила областей видимости, объявления переменных и механизма
> затенения см. в [спецификации системы модулей](./modules.md#第四章作用域).

### 3.3 Оператор return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, выходящий за ближайшую **границу функции**
(проходит сквозь любые блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается в блок»**.

**Тип**: `return e : Never` (где `e : T`). `Never <: T'` выполняется для любого `T'` (принцип
взрыва, см. [система типов §2.2](./type-system.md)), поэтому `return` может находиться в любой
позиции возвращаемого типа без дополнительных правил-ограничений.

**Отношение к вычислению блока**: значение блока всегда есть **хвостовое выражение** (см. §2.9).
`{ return n }` как блок имеет значение `n` типа `Never`; одновременно `return` действует как выход
из функции. **Оба факта верны одновременно**, сосуществование обеспечивается принципом взрыва.

`return` вместе с хвостовым выражением делают возможным «досрочный возврат» без специальных правил о
том, что `return` явно относится к функции — см.
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // Проходит сквозь if, выходит из функции (тип Never)
    }
    n * factorial(n - 1)  // Хвостовое выражение = значение блока
}
```

### 3.4 Оператор break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает самый внутренний цикл `while`/`for`, в котором находится, поток
управления переходит к коду после тела этого цикла.

- **Выход только из ближайшего слоя**: `break` всегда действует на самый внутренний содержащий его
  цикл. Во вложенных циклах, когда нужно выйти сразу из нескольких слоёв, извлеките внутренний цикл
  в функцию с `return`, либо используйте флаг (break/continue без меток; если в будущем будут
  введены метки циклов, это пойдёт через RFC-процесс по синтаксису со стороны объявления цикла,
  вместе с дизайном множественных выходов в доказательственном конвейере)
- **Только внутри цикла**: `break` может появляться только внутри тела цикла `while`/`for` (включая
  вложенные блоки/if/match), появление вне цикла — ошибка компиляции (E1102
  `'break' outside of a loop`)
- **Не влияет на доказательство завершимости**: цикл `while` по-прежнему должен быть доказуемо
  завершающимся (метрика decreases); `break` не участвует в аргументации завершимости,
  `while true { break }` не будет принято
- **Семантика заимствования**: ребро потока управления, создаваемое break, участвует в структурном
  разрезе обратного BFS-анализа живости согласно RFC-009a (пропущенные итерации не участвуют в
  выводе живости обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // Поток управления переходит к коду после цикла, i == 3
    }
}

// Вложенные циклы: break выходит только из внутреннего
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // Завершает только внутренний цикл
    }
    j = j + 1                  // На каждой итерации внешнего цикла выполнение доходит сюда
}
```

### 3.5 Оператор continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации и сразу переходит к следующей
итерации самого внутреннего цикла, в котором находится — в `while` возвращается к переоценке
условия, в `for` берётся следующий элемент.

- **Действует только на ближайший слой**: как и `break`, без меток
- **Только внутри цикла**: появление вне цикла — ошибка компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // Пропускает следующее накопление, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Оператор for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация — это новая привязка значения

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация — это новая
привязка значения, а не модификация одной и той же переменной**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Ход выполнения**:

| Итерация   | Поведение переменной цикла                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 1-я        | Создаётся новая привязка `i = 1`, выполняется тело цикла, печатается 1                                      |
| 2-я        | Создаётся новая привязка `i = 2` (предыдущая привязка уже уничтожена), выполняется тело цикла, печатается 2 |
| 3-я        | Создаётся новая привязка `i = 3`, выполняется тело цикла, печатается 3                                      |
| 4-я        | Создаётся новая привязка `i = 4`, выполняется тело цикла, печатается 4                                      |
| Завершение | Тело цикла завершается, привязка уничтожается                                                               |

**Ключевой момент**: после завершения каждой итерации созданная в этой итерации привязка
уничтожается. Следующая итерация — это совершенно новая привязка, никак не связанная с привязкой
предыдущей итерации.

#### 3.9.2 Различие между for и for mut

| Синтаксис           | Изменяемость переменной цикла | Описание                                    |
| ------------------- | ----------------------------- | ------------------------------------------- |
| `for i in 1..5`     | Неизменяемая                  | Нельзя модифицировать привязку в теле цикла |
| `for mut i in 1..5` | Изменяемая                    | Можно модифицировать привязку в теле цикла  |

```yaoxiang
// Допустимо: каждая итерация привязывает новое значение, модификация не нужна
for i in 1..5 {
    print(i)  // Чтение значения i
}

// Ошибка: неизменяемая привязка, модификация невозможна
for i in 1..5 {
    i = i + 1  // Ошибка: нельзя модифицировать неизменяемую привязку
}

// Допустимо: for mut разрешает модификацию привязки
for mut i in 1..5 {
    i = i + 1  // Модификация разрешена
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлена во внешней области
i = 10
for i in 1..5 {
    print(i)
}

// Корректно: используйте другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробности в
[4.3 правила затенения](./modules.md#43-遮蔽规则).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                                       |
| -------- | -------------------------------------------------------------------- |
| YaoXiang | Каждая итерация — новая привязка значения                            |
| Rust     | Модификация одной и той же переменной (требует mut)                  |
| Python   | Модификация одной и той же переменной (mut не требуется)             |
| C/C++    | Модификация одной и той же переменной (требует указатель или ссылку) |

**Обоснование дизайна**: YaoXiang использует семантику привязки по следующим причинам:

1. **Более соответствует естественной семантике** В естественном языке «для каждого элемента x в
   коллекции» означает, что каждый x — это отдельная сущность. `for i in 1..5` в YaoXiang читается
   как «для каждого i от 1 до 5», i в каждой итерации — это совершенно новая привязка, что
   согласуется с интуитивным пониманием человека.

2. **Избежание случайных модификаций** Семантика привязки, неизменяемой по умолчанию, означает, что
   в теле цикла нельзя случайно модифицировать переменную цикла. Не нужно беспокоиться о том, что
   где-то в сложном теле цикла случайно написано `i = ...`, что приводит к трудно отслеживаемым
   багам.

3. **Высокопроизводительное решение под рукой** Когда действительно нужно повторно использовать
   переменную между итерациями (например, аккумулятор, кэш), достаточно использовать объявление
   `for mut` для переключения в режим изменяемой привязки. Это яснее, чем неявное разделение
   состояния — намерение выражается явно через синтаксис, а не прячется в поведении во время
   выполнения.

### 3.10 Оператор spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**Блок spawn**: явно объявляет область параллелизма, выражения внутри блока выполняются параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**Цикл spawn**: параллельный по данным цикл.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**Блок spawn захватывает переменные внешней области видимости** (RFC-024 §2.3, семантика захвата по
значению):

- Тело блока ссылается на переменные внешней области = **захват значения с перемещением (Move)**:
  значение снапшотится в замыкание в точке создания spawn, тело блока читает его через env
  (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, переменные внешней области не
  затрагиваются
- **Типы-дескрипторы** (Struct/String/List и т.д.) — снапшот = копирование дескриптора, разделение
  нижележащего объекта; во встроенном (Embedded) времени выполнения (по умолчанию) один поток и одна
  куча, дескриптор действителен
- Для разделения между несколькими задачами требуется явный `ref` (§2.13, компилятор автоматически
  выбирает Rc/Arc)
- Внешние переменные, на которые ссылается `return` внутри блока, также захватываются

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // Захват t1/t2 по значению, result == 6
}
```

### 3.11 Точка входа программы и операторы верхнего уровня

С точки зрения компилятора исходный файл играет две роли, **определяемые наличием `yaoxiang.toml`**:

| Роль       | Определение                                              | Тело программы                                                                             |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Script** | Одиночный файл запускается напрямую, без `yaoxiang.toml` | **Операторы верхнего уровня** (выполняются в порядке написания); `main` — обычная привязка |
| **Bin**    | Существует `yaoxiang.toml`                               | **Функция `main`**; на верхнем уровне не должно быть исполняемых операторов                |

#### Script: операторы верхнего уровня — это программа

Без manifest-а файл является «скриптом», **операторы верхнего уровня выполняются в порядке
написания**:

```yaoxiang
use std.io
io.println("hello")          // Выполняется напрямую
x: Int = { 42 }              // Привязка верхнего уровня: инициализация во время выполнения
io.println(x)                // 42
```

В этом режиме `main` **не является специальной** — это просто обычная привязка. Чтобы `main`
запустился, его нужно вызвать явно:

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← Необходимо написать эту строку
```

> **Почему не вызывать `main` автоматически?** Операторы верхнего уровня уже являются телом
> программы. Если неявно вызывать `main` ещё раз, скрипт с явно написанным `main()` будет выполнен
> дважды. Эти два правила не могут сосуществовать, поэтому в Script есть только одна точка входа —
> «операторы верхнего уровня».

#### Bin: `main` — точка входа

При наличии manifest-а файл является «исполняемой целью», в этом случае:

- `main` должен быть определён, и он должен быть функцией (сигнатура должна позволять вызов с нулём
  аргументов)
- На верхнем уровне не допускаются исполняемые операторы — телом программы является `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не-функция — ошибка компиляции (первое: при отсутствии `main` все
функции недостижимы; второе: привязка значения не будет вызвана).

> **Файлы библиотек**: файлы, которые подключаются через `use` из других файлов, либо файлы, на
> которые указывают `[lib].path` / `[exports]`, не требуют `main` — они не являются точкой входа в
> программу.

#### Инициализация привязок верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются во время выполнения**, не требуется,
чтобы они были константами времени компиляции:

```yaoxiang
answer: Int = { 42 }              // Значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // Вызов функции
```

Инициализация выполняется **в порядке зависимостей**, независимо от порядка написания:

```yaoxiang
derived: Int = base * 3           // Ссылается на base, объявленный позже
base: Int = 7                     // Инициализируется первым (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (будут перечислены имена в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // Ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель роли файла), RFC-010a, приложение D (разрешение привязки
> блока).
