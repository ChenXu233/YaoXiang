# Спецификация синтаксиса

Этот документ определяет спецификацию синтаксиса языка программирования YaoXiang, включая
лексическую структуру, правила грамматики и приоритет операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходный файл

Исходный файл YaoXiang должен использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Классификация лексических единиц

| Категория      | Описание                      | Примеры                   |
| -------------- | ----------------------------- | ------------------------- |
| Идентификатор  | Начинается с буквы или `_`    | `x`, `_private`, `my_var` |
| Ключевое слово | Зарезервированное слово языка | `Type`, `pub`, `use`      |
| Литерал        | Фиксированное значение        | `42`, `"hello"`, `true`   |
| Оператор       | Знак операции                 | `+`, `-`, `*`, `/`        |
| Разделитель    | Синтаксический разделитель    | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет минимальный набор ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют специальное значение в любом контексте и не могут использоваться как
идентификаторы.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang разделены на три слоя, распознаваемых парсером (parser) и
проверщиком типов (type checker) на разных этапах:

#### 1.4.1 Литеральные зарезервированные слова

Идентификаторы литералов, имеющие отдельный токен в парсере и не могущие использоваться как обычные
идентификаторы:

| Идентификатор | Принадлежность к типу | Описание                                                                                                    |
| ------------- | --------------------- | ----------------------------------------------------------------------------------------------------------- |
| `Type`        | —                     | Ключевое слово метатипа                                                                                     |
| `true`        | Bool                  | Логическая истина                                                                                           |
| `false`       | Bool                  | Логическая ложь                                                                                             |
| `void`        | Void                  | Литерал Void (значение Unit). Строчный `void` — литерел значения; заглавный `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Конструкторы выражений

Следующие конструкторы распознаются парсером в контекстах сопоставления с образцом и выражений:

| Конструктор | Принадлежность к типу | Описание                    |
| ----------- | --------------------- | --------------------------- |
| `some(T)`   | Option                | Конструктор варианта Option |
| `ok(T)`     | Result                | Успешный вариант Result     |
| `err(E)`    | Result                | Вариант ошибки Result       |

#### 1.4.3 Встроенные имена типов

Следующие имена типов предварительно зарегистрированы проверщиком типов и могут использоваться в
позиции типа без импорта. Парсер рассматривает их как обычные идентификаторы — **это не
зарезервированные слова, они могут быть затенены локальными привязками (не рекомендуется)**.

| Имя типа | Логический аналог   | Описание                                                                                                                                      |
| -------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)     | Тип-произведение с нулём полей, ровно один обитатель (литерал `void`, см. §1.4.1)                                                             |
| `Never`  | ⊥ (ложь/пустой тип) | Тип с нулём вариантов и нулём обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` для любого `T` (принцип взрыва). |
| `Int`    | —                   | Знаковое целое                                                                                                                                |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                      |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                         |
| `Char`   | —                   | Символ Unicode                                                                                                                                |
| `String` | —                   | Строка                                                                                                                                        |

### 1.5 Идентификаторы

Идентификатор начинается с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заглушка, обозначающая игнорируемое значение
- Идентификаторы, начинающиеся с подчёркивания, обозначают приватные члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей точкой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // Когда целевой тип аннотирован как Array(T, N), литерал становится массивом фиксированной длины
```

> **Литерал словаря должен содержать хотя бы одну пару ключ-значение**: `{}` **не является** пустым
> словарём — это пустой блок (значение `Void`, см. [§2.9](#_2-9-блок-выражение)). Для пустого
> словаря используйте конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ пустой словарь
> d = { "a": 1 }                       // ✅ литерал словаря
> wrong = {}                           // ❌ это не словарь, а пустой блок (Void)
> ```
>
> **Критерий — содержимое**: грамматика `Dict` требует хотя бы одну пару `String ':' Expr`, `{}` не
> имеет содержимого, на которое можно опереться, поэтому берётся нулевая форма блочной структуры.
> Непустая форма самоописывается содержимым (`{ "k": v }` имеет пары ключ-значение → словарь) — это
> одного корня с тем, что `f = { 5 }` является значением `Int`, а не функцией: **тип определяется
> содержимым**.

> Множество (Set) не имеет литеральной грамматики и не имеет представления в runtime — при
> планировании типа коллекции, при появлении требований он будет дополнен по модели Dict (std.set +
> HeapValue::Set). Точка размещения литералов List/Dict определяется аннотацией контекстного типа:
> голый литерал и литерал с аннотацией `List(T)` размещаются в расширяемом списке; аннотация
> `Array(T, N)`, применённая непосредственно к литералу, размещает массив фиксированной длины.
> Неявное преобразование List→Array запрещено.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе ошибка компиляции E1002; пустой литерал с
>   ненулевым N также отклоняется
> - Тип каждого элемента должен быть совместим с T, иначе ошибка компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отклоняются на этапе разбора
> - Когда N — символьная константа (const-параметр функции, например `Array(Int, n)`), проверка
>   количества откладывается до этапа уточнения типов
> - Вложенные литералы массивов v1 (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отклоняются на этапе
>   компиляции, требуется явное послойное конструирование; рекурсивная точка размещения отложена до
>   следующих версий

#### 1.6.5 List comprehension

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (запись миграции)**: грамматика переменной итерации всегда была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный парсинг pratt — после
> регистрации `'in'` как инфиксного оператора, `x` поглощал `in items` как выражение membership.
> После исправления не-идентификаторный pattern сразу приводит к ошибке разбора, вместо fallback к
> `_` (тихого проглатывания ошибки) в старой реализации. Сфера влияния: ранее разбиравшаяся запись
> `[x for (a, b) in pairs]` теперь выдаёт ошибку — эта форма никогда не имела определённого
> поведения (переменная всегда была `_`), ужесточение корректно, без затрат на семантическую
> миграцию.

#### 1.6.6 Проверка принадлежности

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool` — `true` при попадании, `false` при
> непопадании, без ошибки. Разделение семантики: `[]` — это утверждение существования с извлечением
> значения (ошибка при неудаче), `in` — это запрос о существовании (непопадание — нормальный
> `false`). Правый операнд покрывает: List / Array / Dict (множество ключей) / Tuple / String
> (подстрока) / Range (интервал). `in` — это предикат Хоара первого класса, на этапе уточнения типов
> служит основой для доказуемых на этапе компиляции утверждений. (Set исключён из списка правых
> операндов — Set не имеет представления в runtime, см. §1.6.4)

## Глава 2: Правила грамматики

### 2.1 Классификация выражений

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Операторы                      | Ассоциативность |
| --------- | ------------------------------ | --------------- |
| 1         | `()` `[]` `.` `?`              | Слева направо   |
| 2         | `as`                           | Слева направо   |
| 3         | Унарные префиксные `!` `-` `+` | Справа налево   |
| 4         | `*` `/` `%`                    | Слева направо   |
| 5         | `+` `-`                        | Слева направо   |
| 6         | `..`                           | Слева направо   |
| 7         | `<<` `>>`                      | Слева направо   |
| 8         | `&` `\|` `^`                   | Слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=`    | Слева направо   |
| 10        | `and` `or`                     | Слева направо   |
| 11        | `if...else`                    | Справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`        | Справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) сильно связывают: уступают только вызовам и доступу
> к членам, выше всех бинарных операторов. Следовательно, `!a == b` ≡ `(!a) == b` (семантика в стиле
> Zig); `!` — чистая унарная операция, не участвует в потоке короткого замыкания, ортогональна
> ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение в RFC-010).

> **Сила связывания Range**: `..` имеет силу (6, 7) — левая 6 ниже сложения (7), правая 7 поглощает
> сложение, но не поглощает `..` того же уровня. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, прав. ассоц.)                                                             | После изменения ((6,7), лев. ассоц.)                                          |
> | ------------ | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (`in` правый операнд ур. 4, `..` ур. 1 не может поглотить, фактически не разбирается) | `x in (1..10)` — интервал целиком как правый операнд `in`                     |
> | `0..n+2`     | `(0..n)+2` (ловушка правой ассоциативности: верхняя граница съедается, `for` цикл сразу E3004)     | `0..(n+2)` — верхняя граница — арифметическое выражение                       |
> | `a == b..c`  | `a == (b..c)` (`..` ур. 1 < `==` ур. 3, естественно целиком)                                       | `a == (b..c)` — **семантика не меняется**, `..` всё ещё выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                         | `1..(2*3)` — верхняя граница — арифметическое выражение                       |
> | `a..b..c`    | `a..(b..c)` (правоассоц. цепочка, бессмысленный Range в Range)                                     | `(a..b)..c` — **форма со шагом** (`c` — шаг)                                  |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` из «успешный разбор, но E3004»
> превращается в «сразу работает»; `x in 1..10` из «не разбирается» превращается в «проверка
> интервала»; `a..b..c` из «бессмысленная вложенность» превращается в «компонент шага». Уровень 6
> находится между `+` (уровень 5) и `<<` (уровень 7), математическая конвенция: интервал — сильно
> связывающая конструкция, верхняя граница естественно является полным арифметическим выражением.

### 2.9 Блок-выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения операторов**: разделение между Stmt и поведение переноса строк (явное
> разделение `;`, завершение переносом строки, исключения для продолжения строки, никогда не
> объединять `(`/`[` в начале строки) определены в
> [RFC-038](../design/rfc/draft/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения имеет ровно три интерпретации, определяемые однократно по **содержимому**:

| Форма               | Запись            | Тип                      | Пример           |
| ------------------- | ----------------- | ------------------------ | ---------------- |
| **Пустой блок**     | `{}`              | `Void`                   | `x: Void = {}`   |
| **Литерал словаря** | `{ "k": v, ... }` | `Dict(K, V)`             | `d = { "a": 1 }` |
| **Блок**            | `{ Stmt* Expr? }` | Тип хвостового выражения | `y = { 1 + 1 }`  |

**Порядок определения**:

1. `{}` (без содержимого) → **пустой блок**, значение `Void`
2. Первый элемент — пара `String ':' Expr` → **литерал словаря**
3. Иначе → **блок**, значение даётся хвостовым выражением

> **Почему `{}` не является пустым словарём**: «пустота» пустого словаря не может самоописаться (это
> может быть как `Dict(K, V)`, так и пустой блок), а грамматика словаря [§1.6.4](#_1-6-4-коллекции)
> требует хотя бы одну пару ключ-значение. При отсутствии содержимого, на которое можно опереться,
> берётся нулевая форма блочной структуры: это согласуется с `unsafe {}` / `spawn {}`, без введения
> особых случаев. Для пустого словаря используйте `dict.new()`.
>
> **Почему функция требует аннотации**: `f = { stmt }` — это **значение** (тип хвостового
> выражения), а не функция. Чтобы определить функцию, явно укажите аннотацию Fn:
> `f: () -> Int = { 5 }`. Это тот же принцип, что и для словаря: **тип определяется содержимым**, а
> не наличием или отсутствием аннотации. (Это правило заменяет решение «без аннотации → функция по
> умолчанию» из Приложения D RFC-010a, см. его корректуру.)

**Единая семантика**: значение всех блоков `{}` определяется **хвостовым выражением**, `return` —
нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| Обычный `{}` | Хвостовое выражение | `Void`           |
| `unsafe {}`  | Хвостовое выражение | `Void`           |
| `spawn {}`   | Хвостовое выражение | `Void`           |

**Основные принципы** (подробности см. в
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Когда последний элемент — **оператор присваивания**, значение блока — `Void`; если нужен `Void`,
  напишите `Void` явно
- **`return` выходит за ближайшую границу функции** (проходит сквозь все блоки, не «возвращается
  блоку»), тип `Never`; `Never <: T`

> выполняется для любого типа (принцип взрыва), поэтому может появляться в любой позиции
> возвращаемого типа

- Форма выражения `= expr` непосредственно даёт значение

```yaoxiang
// Обычный {} блок: хвостовое выражение даёт значение
result = {
    x = compute()
    x                // значение блока
}

// unsafe {} блок: хвостовое выражение даёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // значение блока
}

// spawn {} блок: хвостовое выражение даёт результат (⚠️ ещё не реализовано, см. #365; пока нужно писать return)
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    return (result1, result2)   // значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // проходит сквозь if и тело функции, выходит из функции
    }
    n * 2            // хвостовое выражение
}
```

#### Является ли `name = { ... }` функцией или значением блока?

`name = { ... }` может быть как определением функции (RFC-007 «простейшая форма без параметров»),
так и привязкой значения блока. Согласно решению «аннотация имеет приоритет, по умолчанию функция»
(Приложение D к RFC-010a):

| Случай                            | Результат          | Пример                             |
| --------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)          | Функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип    | Функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — не функциональный тип | **Значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                     | Функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация есть тип**: `x: Int = ...` объявляет, что `x` — это `Int`, тогда `{ ... }` вычисляется в
`Int`; `f: () -> Int = ...` объявляет, что `f` — функция, тогда `{ ... }` — тело функции.

Чтобы `{ ... }` вычислялось на месте, **просто укажите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: без аннотации по умолчанию
f = { 5 }        // f() = 5
```

#### Вложенные функциональные типы: каррирование или возврат функции?

Вложенный функциональный тип справа от `->` имеет два прочтения, различаемых **скобками** (RFC-004):

| Запись                          | Значение            | Вызов               |
| ------------------------------- | ------------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **Каррирование**    | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **Возврат функции** | `g(1)` даёт функцию |

Принцип: **аннотация есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, значит `g(1)` должен **быть** этой функцией, а не «следующей порцией
аргументов».

```yaoxiang
// Каррирование: две порции аргументов по уровням
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний уровень — одна порция аргументов, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // возвращённую функцию можно сохранить в переменную, передать
```

Незаключённый в скобки вложенный `Fn` всегда каррируется (включая форму с параметрами типа из
RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют возвращаемый тип, body должен порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка — ожидается `() -> Int`, фактически получено `Int` (E1002).

### 2.10 Lambda-выражение

```
Lambda      ::= '(' ParamList? ')' '=>' Expr
            |  '(' ParamList? ')' '=>' Block
```

### 2.11 Оператор распространения ошибки

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` — постфиксный, с тем же приоритетом, что и `.`. Для типа `Result(T, E)`:

- При `Ok(v)` извлекает значение `v` и продолжает выполнение
- При `Err(e)` распространяет ошибку вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // при успехе извлекает значение, при неудаче распространяет вверх
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, а не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — это значение: можно привязывать, передавать, проверять членство
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// Форма со шагом (третий компонент, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика шага**: в `a..b..c` `c` — это шаг. `c = 0` как литерал отклоняется на этапе
> компиляции; динамический `c` проверяется во время выполнения (семейство E6001; после введения
> системы ошибок будет повышен до Result). `c < 0` допустим, направление интервала меняется в
> зависимости от знака (`10..0..(-2)` убывает).

### 2.13 ref-выражение

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (одна задача) или Arc
(между задачами), пользователю не нужно беспокоиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // между задачами: компилятор автоматически выбирает Arc
```

### 2.14 unsafe-выражение

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и операций с сырыми указателями.
Используйте `return` для возврата определения типа в вышестоящую область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует права unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Области видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней
- Внешняя область видимости не может обращаться к переменным внутренней
- Объявление переменных следует принципу «приоритет присваивания»

```yaoxiang
// Блочная область видимости
{
    x = 10
    // x виден в этой области видимости
}
// x не виден за пределами этой области видимости

// Область видимости функции
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не виден за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск `x` идёт по цепочке областей видимости наружу; если найден — присваивание,
  иначе — новое объявление
- `mut x = value`: явное новое объявление изменяемой переменной, запрещено использовать то же имя,
  что и во внешней области
- В одной области видимости любое имя может быть объявлено только один раз

> **Подробное определение**: полные правила областей видимости, объявления переменных и механизма
> затенения см. в [спецификации системы модулей](./modules.md#第四章作用域).

### 3.3 Оператор return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, выходящий за ближайшую **границу функции**
(проходит сквозь все блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается блоку»**.

**Тип**: `return e : Never` (`e : T`). `Never <: T'` выполняется для любого `T'` (принцип взрыва,
см. [система типов §2.2](./type-system.md)), поэтому `return` может появляться в любой позиции
возвращаемого типа без дополнительных правил.

**Отношение к вычислению блока**: значение блока всегда равно **хвостовому выражению** (см. §2.9).
`{ return n }` как блок имеет значение `n`, типа `Never`; в то же время действие `return` — выход из
функции. **Оба утверждения истинны одновременно**, они сосуществуют благодаря принципу взрыва.

`return` и хвостовое выражение совместно обеспечивают «досрочный возврат», без необходимости в
специальных правилах для `return`, специфичных для функции — см.
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // проходит сквозь if, выходит из функции (тип Never)
    }
    n * factorial(n - 1)  // хвостовое выражение = значение блока
}
```

### 3.4 Оператор break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает самый внутренний цикл `while`/`for`, поток управления переходит
к коду после тела цикла.

- **Выходит только из ближайшего слоя**: `break`

> всегда действует на самый внутренний цикл, его содержащий. Когда во вложенных циклах нужно выйти
> сразу из нескольких уровней, извлеките внутренний цикл в функцию и используйте `return` для
> возврата, или используйте флаг (break/continue без меток; если в будущем будут введены метки
> циклов, они пойдут по синтаксису стороны объявления цикла через процесс RFC, вместе с проектом
> многократного выхода в конвейере доказательств)

- **Только внутри тела цикла**: `break` может появляться только в теле цикла `while`/`for`

> (включая вложенные блоки/if/match), появление вне цикла — ошибка компиляции (E1102
> `'break' outside of a loop`)

- **Не влияет на доказательство завершимости**: цикл `while` всё равно должен быть доказуемо
  завершающимся (метрика decreases); `break`

> не участвует в аргументации завершимости, `while true { break }` не будет принят

- **Семантика заимствования**: ребро потока управления break участвует в структурном разрыве
  обратного BFS-анализа живости из RFC-009a (выпрыгнувшие итерации не участвуют в выводе живости
  обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // поток управления переходит после цикла, i == 3
    }
}

// Вложенные циклы: break выходит только из внутреннего
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // завершает только внутренний цикл
    }
    j = j + 1                  // каждая итерация внешнего цикла дойдёт сюда
}
```

### 3.5 Оператор continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации, сразу переходит к следующей
итерации самого внутреннего цикла — `while` возвращается к переоценке условия, `for`

> берёт следующий элемент.

- **Действует только на ближайший слой**: как и `break`, без меток
- **Только внутри тела цикла**: появление вне цикла — ошибка компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // пропускает накопление ниже, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Оператор for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация — это новая привязка значения

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация — это новая
привязка значения, а не модификация одной и той же переменной**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Процесс выполнения**:

| Итерация | Поведение переменной цикла                                                                      |
| -------- | ----------------------------------------------------------------------------------------------- |
| 1-я      | Создаётся новая привязка `i = 1`, тело цикла выполняется, печатает 1                            |
| 2-я      | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), тело выполняется, печатает 2 |
| 3-я      | Создаётся новая привязка `i = 3`, тело выполняется, печатает 3                                  |
| 4-я      | Создаётся новая привязка `i = 4`, тело выполняется, печатает 4                                  |
| Конец    | Тело цикла завершается, привязка уничтожается                                                   |

**Ключевой момент**: после завершения каждой итерации созданная в этой итерации привязка
уничтожается. Следующая итерация — это совершенно новая привязка, не имеющая никакого отношения к
привязке предыдущей итерации.

#### 3.9.2 Различие между for и for mut

| Синтаксис           | Изменяемость переменной цикла | Описание                              |
| ------------------- | ----------------------------- | ------------------------------------- |
| `for i in 1..5`     | Неизменяемая                  | В теле цикла нельзя изменять привязку |
| `for mut i in 1..5` | Изменяемая                    | В теле цикла можно изменять привязку  |

```yaoxiang
// Допустимо: каждая итерация привязывает новое значение, модификация не нужна
for i in 1..5 {
    print(i)  // чтение значения i
}

// Ошибка: неизменяемая привязка, нельзя изменять
for i in 1..5 {
    i = i + 1  // ошибка: нельзя изменять неизменяемую привязку
}

// Допустимо: использование for mut разрешает изменение привязки
for mut i in 1..5 {
    i = i + 1  // модификация разрешена
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлен снаружи
i = 10
for i in 1..5 {
    print(i)
}

// Правильно: использовать другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробности см. в
[4.3 Правила затенения](./modules.md#43-遮蔽规则).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                                       |
| -------- | -------------------------------------------------------------------- |
| YaoXiang | Каждая итерация — новая привязка значения                            |
| Rust     | Модификация одной и той же переменной (требует mut)                  |
| Python   | Модификация одной и той же переменной (без mut)                      |
| C/C++    | Модификация одной и той же переменной (требует указателя или ссылки) |

**Обоснование дизайна**: YaoXiang использует семантику привязки, потому что:

1. **Более естественная семантика** В естественном языке «для каждого элемента x в коллекции»
   означает, что каждый x — независимая сущность. `for i in 1..5`

> в YaoXiang читается как «для каждого i от 1 до 5», i каждой итерации — это совершенно новая
> привязка, что согласуется с человеческой интуицией.

2. **Избежание случайных модификаций**

> Семантика неизменяемой привязки по умолчанию означает, что в теле цикла нельзя случайно
> модифицировать переменную цикла. Не нужно беспокоиться о том, что где-то в сложном теле цикла
> случайно написано `i = ...`, что приводит к трудно отслеживаемым ошибкам.

3. **Высокопроизводительное решение под рукой** Когда действительно нужно переиспользовать
   переменную между итерациями (например, аккумулятор, кэш), используйте `for mut`

> для переключения в режим изменяемой привязки. Это яснее, чем неявное разделение состояния —
> намерение выражается явно через синтаксис, а не скрывается в поведении runtime.

### 3.10 Оператор spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn-блок**: явно объявляет параллельную область, выражения внутри блока выполняются параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn-цикл**: параллельный по данным цикл.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn-блок захватывает переменные внешней области** (RFC-024 §2.3, семантика захвата по значению):

- Тело блока ссылается на внешнюю переменную =

> **Захват значения через Move**: значение снимается в замыкание в точке создания spawn, тело блока
> читает через env (LoadUpvalue)

- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешняя переменная не затрагивается
- **Типы-дескрипторы** (Struct/String/List и т.д.) снимок = копия дескриптора, базовый объект
  разделяется; Embedded runtime (по умолчанию) — один поток, одна куча, дескриптор действителен
- Для разделения между несколькими задачами требуется явный `ref` (§2.13, компилятор автоматически
  выбирает Rc/Arc)
- `return` внутри блока, ссылающийся на внешнюю переменную, также выполняет её захват

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 захвачены по значению, result == 6
}
```

### 3.11 Точка входа в программу и операторы верхнего уровня

Исходный файл в глазах компилятора имеет две роли, **определяемые наличием `yaoxiang.toml`**:

| Роль       | Определение                                              | Тело программы                                                                             |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Script** | Одиночный файл запускается напрямую, без `yaoxiang.toml` | **Операторы верхнего уровня** (выполняются в порядке написания); `main` — обычная привязка |
| **Bin**    | Существует `yaoxiang.toml`                               | **Функция `main`**; на верхнем уровне не допускаются исполняемые операторы                 |

#### Script: операторы верхнего уровня — это программа

Без manifest файл является «скриптом», **операторы верхнего уровня выполняются в порядке
написания**:

```yaoxiang
use std.io
io.println("hello")          // выполняется напрямую
x: Int = { 42 }              // привязка верхнего уровня: инициализация во время выполнения
io.println(x)                // 42
```

`main` в этом режиме **не особенный** — это просто обычная привязка. Чтобы `main`

> запустился, нужно явно вызвать:

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← эта строка обязательна
```

> **Почему `main` не вызывается автоматически?** Операторы верхнего уровня уже являются телом
> программы. Если бы также неявно вызывался `main`, скрипт, явно вызвавший `main()`, выполнился бы
> дважды. Два правила не могут сосуществовать, поэтому в Script существует только «операторы
> верхнего уровня» как единая точка входа.

#### Bin: `main` — это точка входа

При наличии manifest файл является «исполняемой целью», в этом случае:

- Должна быть определена `main`, и это должна быть функция (сигнатура должна быть вызываемой с нулём
  аргументов)
- На верхнем уровне не допускаются исполняемые операторы — телом программы является `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не-функция — обе ошибки компиляции (первая: без `main` все функции
недостижимы; вторая: привязка значения не будет вызвана).

> **Файлы библиотек**: файлы, которые `use`-ятся другими файлами, или файлы, на которые указывают
> `[lib].path` / `[exports]`, не требуют `main` — они не являются точкой входа.

#### Инициализация привязок верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются во время выполнения**, не требуется
быть константами времени компиляции:

```yaoxiang
answer: Int = { 42 }              // значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // вызов функции
```

Инициализация выполняется в **порядке зависимостей**, независимо от порядка записи:

```yaoxiang
derived: Int = base * 3           // ссылается на base, объявленный позже
base: Int = 7                     // инициализируется первым (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (будут перечислены имена в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель ролей файла), Приложение D к RFC-010a (решение о
> привязке блока).
