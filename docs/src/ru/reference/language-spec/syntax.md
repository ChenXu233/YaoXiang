# Спецификация синтаксиса

Данный документ определяет спецификацию синтаксиса языка программирования YaoXiang, включая
лексическую структуру, правила грамматики и приоритет операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходный файл

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Классификация лексических единиц

| Категория      | Описание                                       | Примеры                   |
| -------------- | ---------------------------------------------- | ------------------------- |
| Идентификатор  | начинается с буквы или подчёркивания           | `x`, `_private`, `my_var` |
| Ключевое слово | предопределённые зарезервированные слова языка | `Type`, `pub`, `use`      |
| Литерал        | фиксированное значение                         | `42`, `"hello"`, `true`   |
| Оператор       | символ операции                                | `+`, `-`, `*`, `/`        |
| Разделитель    | синтаксический разделитель                     | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет очень мало ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют особое значение в любом контексте и не могут использоваться в качестве
идентификаторов.

### 1.4 Зарезервированные слова

«Зарезервированные слова» в YaoXiang разделены на три уровня, распознаваемые парсером и проверщиком
типов на разных этапах:

#### 1.4.1 Литеральные зарезервированные слова

Идентификаторы литералов, имеющие собственные токены в парсере и не могущие использоваться в
качестве обычных идентификаторов:

| Идентификатор | Тип  | Описание                                                                                                    |
| ------------- | ---- | ----------------------------------------------------------------------------------------------------------- |
| `Type`        | —    | ключевое слово метатипа                                                                                     |
| `true`        | Bool | логическая истина                                                                                           |
| `false`       | Bool | логическая ложь                                                                                             |
| `void`        | Void | литерал Void (значение Unit). Строчная `void` — литерал значения; прописная `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Конструкторы выражений

Следующие конструкторы распознаются парсером в контекстах сопоставления с образцом и выражений:

| Конструктор | Тип    | Описание                             |
| ----------- | ------ | ------------------------------------ |
| `some(T)`   | Option | конструктор варианта значения Option |
| `ok(T)`     | Result | вариант успеха Result                |
| `err(E)`    | Result | вариант ошибки Result                |

#### 1.4.3 Встроенные имена типов

Следующие имена типов предварительно зарегистрированы проверщиком типов и могут использоваться в
позициях типа без импорта. Парсер рассматривает их как обычные идентификаторы — **это не
зарезервированные слова, они могут быть затенены локальной привязкой (не рекомендуется)**.

| Имя типа | Логическое соответствие | Описание                                                                                                                                    |
| -------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)         | Тип-произведение с нулём полей, ровно один обитатель (литерал `void`, см. §1.4.1)                                                           |
| `Never`  | ⊥ (ложь/пустой тип)     | Тип с нулём вариантов, ноль обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` для любого `T` (принцип взрыва). |
| `Int`    | —                       | целое число со знаком                                                                                                                       |
| `Float`  | —                       | число с плавающей точкой                                                                                                                    |
| `Bool`   | —                       | логическое значение: `true` / `false`                                                                                                       |
| `Char`   | —                       | символ Unicode                                                                                                                              |
| `String` | —                       | строка                                                                                                                                      |

### 1.5 Идентификаторы

Идентификатор начинается с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заполнитель, обозначающий игнорируемое значение
- идентификаторы, начинающиеся с подчёркивания, обозначают закрытые члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей точкой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // Когда аннотация целевого типа — Array(T, N), литерал становится массивом фиксированной длины
```

> **Литерал словаря требует как минимум одну пару ключ-значение**: `{}` **не является** пустым
> словарём — это пустой блок (значение `Void`, см. [§2.9](#_2-9-блочное-выражение)). Для пустого
> словаря используйте конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ Пустой словарь
> d = { "a": 1 }                       // ✅ Литерал словаря
> wrong = {}                           // ❌ Это не словарь, а пустой блок (Void)
> ```
>
> **Критерием является содержимое**: грамматика `Dict` требует как минимум один `String ':' Expr`; у
> `{}` нет содержимого, на которое можно опереться, поэтому берётся нулевая форма блочной структуры.
> Непустая форма самоописывается содержимым (`{ "k": v }` имеет пару ключ-значение → словарь) — это
> одного корня с тем, что `f = { 5 }` является значением `Int`, а не функцией: **тип определяется
> содержимым**.

> Set не имеет ни литеральной грамматики, ни представления во время выполнения — при планировании
> типа коллекции, при появлении потребности он дополняется по модели Dict (std.set +
> HeapValue::Set). Точка размещения литералов List/Dict определяется аннотацией контекстного типа:
> голый литерал и литерал с аннотацией `List(T)` становятся расширяемым списком; аннотация
> `Array(T, N)`, применённая непосредственно к литералу, делает его массивом фиксированной длины.
> Неявное преобразование List→Array запрещено.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, при неравенстве — ошибка компиляции E1002; пустой
>   литерал с ненулевым N также отклоняется
> - Тип каждого элемента должен быть совместим с T, при несоответствии — ошибка компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отклоняются на этапе разбора
> - Когда N является символьной константой (параметр const функции, например `Array(Int, n)`),
>   проверка количества откладывается до этапа уточнения типов
> - Вложенные литералы массивов в v1 (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отклоняются на этапе
>   компиляции, требуется явное построение слой за слоем; рекурсивное размещение оставлено для
>   будущих версий

#### 1.6.5 Генераторы списков

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (запись миграции)**: грамматика переменной итерации изначально была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный разбор pratt — после
> регистрации `'in'` как инфиксного оператора `x` поглощал `in items` как выражение membership.
> После исправления pattern, не являющийся идентификатором, сразу не проходит разбор, без fallback к
> `_`, как в старой реализации (молчаливое проглатывание ошибки). Масштаб влияния: ранее
> разбиравшаяся запись вида `[x for (a, b) in pairs]` теперь выдаёт ошибку — эта форма никогда не
> имела определённого поведения (переменная всегда была `_`), направление ужесточения верное, без
> затрат на семантическую миграцию.

#### 1.6.6 Проверка членства

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool` — попадание `true`, непопадание `false`,
> ошибка не выдаётся. Семантическое разделение: `[]` утверждает существование и извлекает значение
> (при неудаче выдаёт ошибку), `in` спрашивает, существует ли (непопадание — нормальный `false`).
> Покрытие правого операнда: List / Array / Dict (набор ключей) / Tuple / String (подстрока) / Range
> (диапазон). `in` — предикат первого класса по Хоару, на этапе уточнения типов служит базой для
> доказуемых утверждений времени компиляции. (Set исключён из списка правых операндов — Set не имеет
> представления во время выполнения, см. §1.6.4)

## Глава 2: Правила грамматики

### 2.1 Классификация выражений

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Оператор                    | Ассоциативность |
| --------- | --------------------------- | --------------- |
| 1         | `()` `[]` `.` `?`           | слева направо   |
| 2         | `as`                        | слева направо   |
| 3         | унарный префикс `!` `-` `+` | справа налево   |
| 4         | `*` `/` `%`                 | слева направо   |
| 5         | `+` `-`                     | слева направо   |
| 6         | `..`                        | слева направо   |
| 7         | `<<` `>>`                   | слева направо   |
| 8         | `&` `\|` `^`                | слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=` | слева направо   |
| 10        | `and` `or`                  | слева направо   |
| 11        | `if...else`                 | справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`     | справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) тесно связывают: уступают только вызову и доступу к
> членам, выше всех бинарных операторов. Следовательно, `!a == b` ≡ `(!a) == b` (семантика в стиле
> Zig); `!` — чисто унарная операция, не участвует в управляющем потоке с коротким замыканием,
> ортогональна ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение RFC-010).

> **Связывающая сила Range**: связывающая сила `..` — (6, 7) — левая 6 ниже сложения (7), правая 7
> поглощает сложение, но не поглощает того же уровня `..`. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, правоассоциативный)                                                             | После изменения ((6,7), левоассоциативный)                                        |
> | ------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (правый операнд `in` уровня 4, `..` уровня 1 не может поглотить, фактически не разбирается) | `x in (1..10)` — диапазон целиком как правый операнд `in`                         |
> | `0..n+2`     | `(0..n)+2` (ловушка правоассоциативности: верхняя граница поглощается, цикл `for` сразу E3004)           | `0..(n+2)` — верхняя граница — арифметическое выражение                           |
> | `a == b..c`  | `a == (b..c)` (`..` уровня 1 < `==` уровня 3, естественно целиком)                                       | `a == (b..c)` — **семантика не меняется**, `..` по-прежнему выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                               | `1..(2*3)` — верхняя граница — арифметическое выражение                           |
> | `a..b..c`    | `a..(b..c)` (правоассоциативная цепочка, бессмысленный Range внутри Range)                               | `(a..b)..c` — **форма step** (`c` — шаг)                                          |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` с «разбор успешен, но E3004»
> превратилась в «сразу доступно»; `x in 1..10` с «невозможно разобрать» превратилась в «проверка
> диапазона»; `a..b..c` с «бессмысленная вложенность» превратилась в «компонент step». Уровень 6
> находится между `+` (уровень 5) и `<<` (уровень 7), математическое соглашение: диапазон — тесно
> связывающая конструкция, верхняя граница естественным образом является полным арифметическим
> выражением.

### 2.3 Вызов функции

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

Именованные аргументы записываются как `name = value` (RFC-010 §определение функций, RFC-011 §форма
конструкторов). Позиционные аргументы должны предшествовать именованным; параметры, заданные
позиционно, в именованных аргументах могут располагаться в любом порядке:

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // Позиционно
add(a = 3, b = 5)  // Именованно
add(b = 5, a = 3)  // Порядок произвольный
add(3, b = 5)      // Смешанно, позиционные впереди
```

При неправильном имени именованного аргумента выдаётся **E1014**, когда один и тот же формальный
параметр задан и позиционно, и именованно — **E1015**, при несовпадении количества — **E1010**
(RFC-013).

### 2.9 Блочное выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правило завершения операторов**: разделение между Stmt и поведение переноса строки (явное
> разделение `;`, завершение переносом строки, исключения для продолжения строки, никогда не
> объединять `(`/`[` в начале строки) определено в
> [RFC-038](../design/rfc/draft/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения имеет ровно три интерпретации, однократно определяемые **содержимым**:

| Форма               | Запись            | Тип                      | Пример           |
| ------------------- | ----------------- | ------------------------ | ---------------- |
| **Пустой блок**     | `{}`              | `Void`                   | `x: Void = {}`   |
| **Литерал словаря** | `{ "k": v, ... }` | `Dict(K, V)`             | `d = { "a": 1 }` |
| **Блок**            | `{ Stmt* Expr? }` | тип хвостового выражения | `y = { 1 + 1 }`  |

**Порядок определения**:

1. `{}` (без содержимого) → **Пустой блок**, значение `Void`
2. Первый элемент — пара `String ':' Expr` ключ-значение → **Литерал словаря**
3. Остальное → **Блок**, значение задаётся хвостовым выражением

> **Почему `{}` не пустой словарь**: «пустота» пустого словаря не может самоописаться (это может
> быть как `Dict(K, V)`, так и пустой блок), а грамматика словаря [§1.6.4](#_1-6-4-коллекции)
> требует как минимум одну пару ключ-значение. Когда нет содержимого, на которое можно опереться,
> берётся нулевая форма блочной структуры: это согласуется с `unsafe {}` / `spawn {}` и не вводит
> исключений. Для пустого словаря используется `dict.new()`.
>
> **Почему функциям нужны аннотации**: `f = { stmt }` — это **значение** (тип хвостового выражения),
> а не функция. Для определения функции укажите аннотацию Fn: `f: () -> Int = { 5 }`. Это того же
> принципа, что и словарь: **тип определяется содержимым**, а не наличием аннотации. (Это правило
> см. в [RFC-010a](./design/rfc/accepted/010a-tail-expression-and-return.md), приложение D.)

**Единая семантика**: значения всех блоков `{}` задаются **хвостовым выражением**, `return` —
нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| обычный `{}` | хвостовое выражение | `Void`           |
| `unsafe {}`  | хвостовое выражение | `Void`           |
| `spawn {}`   | хвостовое выражение | `Void`           |

**Ключевой принцип** (подробности см. в
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Когда последний оператор — **оператор присваивания**, значение блока — `Void`; если хотите `Void`,
  явно напишите `Void`
- **`return` выходит из ближайшей границы функции** (проходит сквозь любые блоки, не «возвращается
  блоку»), тип `Never`; `Never <: T` для любого типа (принцип взрыва), поэтому может появляться в
  любой позиции возвращаемого типа
- Выражение в форме `= expr` непосредственно задаёт значение

```yaoxiang
// Обычный блок {}: хвостовое выражение задаёт значение
result = {
    x = compute()
    x                // значение блока
}

// Блок unsafe {}: хвостовое выражение задаёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // значение блока
}

// Блок spawn {}: хвостовое выражение задаёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // проходит через if и тело функции, выходит из функции
    }
    n * 2            // хвостовое выражение
}
```

#### Является ли `name = { ... }` функцией или значением блока?

`name = { ... }` может быть как определением функции (RFC-007 «минимальная форма без параметров»),
так и привязкой значения блока. Решается по принципу **аннотация в приоритете, по умолчанию
функция** (RFC-010a, приложение D):

| Случай                           | Результат          | Пример                             |
| -------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)         | функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип   | функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — нефункциональный тип | **значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                    | функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация есть тип**: `x: Int = ...` объявляет, что `x` — это `Int`, значит `{ ... }` вычисляется
как `Int`; `f: () -> Int = ...` объявляет, что `f` — функция, значит `{ ... }` — тело функции.

Чтобы `{ ... }` вычислялось на месте, **просто укажите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: без аннотации по умолчанию
f = { 5 }        // f() = 5
```

#### Вложенный функциональный тип: каррирование или возврат функции?

Вложенный функциональный тип справа от `->` имеет два прочтения, различаемые **скобками** (RFC-004):

| Запись                          | Значение            | Вызов               |
| ------------------------------- | ------------------- | ------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **каррирование**    | `f(1)(2)`           |
| `(a: Int) -> ((b: Int) -> Int)` | **возврат функции** | `g(1)` даёт функцию |

Критерий: **аннотация есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, поэтому `g(1)` должно **быть** той функцией, а не «следующим сегментом
аргумента».

```yaoxiang
// Каррирование: два сегмента аргумента задаются слой за слоем
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний один сегмент аргумента, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // возвращённая функция может быть сохранена в переменную, передана
```

Не взятый в скобки вложенный `Fn` всегда является каррированием (включая форму параметров типа из
RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют возвращаемый тип, тело должно порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка — ожидается `() -> Int`, фактически получено `Int` (E1002).

### 2.11 Оператор распространения ошибки

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` — постфиксный оператор, приоритет такой же, как у `.`. Для типа `Result(T, E)`:

- при `Ok(v)` извлекает значение `v` и продолжает выполнение
- при `Err(e)` распространяет ошибку вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // при успехе извлекает значение, при неудаче распространяет вверх
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — это значение: привязка, передача, проверка членства
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// Форма step (третий компонент, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика step**: в `a..b..c` `c` — шаг. Литерал `c = 0` отклоняется на этапе компиляции;
> динамический `c` проверяется на ноль во время выполнения (семейство E6001; после внедрения системы
> ошибок повышается до Result). `c < 0` допустимо, направление диапазона меняется на противоположное
> в зависимости от знака (`10..0..(-2)` — убывающий).

### 2.13 Выражение ref

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (одна задача) или Arc
(между задачами), пользователю не нужно беспокоиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // между задачами: компилятор автоматически выбирает Arc
```

### 2.14 Выражение unsafe

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и работы с сырыми указателями.
Используйте `return`, чтобы вернуть определение типа в вышестоящую область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Возвращённый тип доступен вне `unsafe {}`
- Доступ к полям типа требует разрешения unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен вне блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Область видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней области видимости
- Внешняя область видимости не может обращаться к переменным внутренней области видимости
- Объявление переменных следует принципу «присваивание в первую очередь»

```yaoxiang
// Область видимости блока
{
    x = 10
    // x видна в данной области видимости
}
// x не видна за пределами данной области видимости

// Область видимости функции
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не видна за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск x по цепочке областей видимости наружу; если найдено — присвоить, если не
  найдено — объявить заново
- `mut x = value`: явное новое мутабельное объявление, запрещено иметь то же имя, что и во внешней
  области
- В одной области видимости любое имя может быть объявлено только один раз

> **Подробное определение**: полные правила области видимости, механизмы объявления и затенения
> переменных подробно описаны в
> [спецификации модульной системы](./modules.md#глава-4-область-видимости).

### 3.3 Оператор return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, выход из ближайшей **границы функции**
(проходит сквозь любые блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается блоку»**.

**Тип**: `return e : Never` (`e : T`). `Never <: T'` для любого `T'` (принцип взрыва, см.
[система типов §2.2](./type-system.md)), поэтому `return` может появляться в любой позиции
возвращаемого типа без дополнительных правил.

**Связь с вычислением блока**: значение блока всегда хвостовое выражение (см. §2.9). `{ return n }`
как блок имеет значение `n` типа `Never`; при этом `return` служит для выхода из функции. **Оба
факта верны одновременно** и сосуществуют благодаря принципу взрыва.

`return` и хвостовое выражение совместно обеспечивают «ранний возврат», без необходимости в
дополнительных правилах, чтобы `return` специально указывал на функцию — см.
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // проходит через if, выходит из функции (тип Never)
    }
    n * factorial(n - 1)  // хвостовое выражение = значение блока
}
```

### 3.4 Оператор break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает ближайший содержащий цикл `while`/`for`, поток управления
переходит к коду после тела этого цикла.

- **Выход только из ближайшего уровня**: `break` всегда действует на ближайший содержащий цикл. Во
  вложенных циклах, когда нужно выйти сразу из нескольких уровней, вынесите внутренний цикл в
  функцию и используйте `return`, или используйте флаг (break/continue без меток; если в будущем
  будут введены метки циклов, это будет следовать синтаксису стороны объявления цикла и процессу
  RFC, и будет решено вместе с дизайном множественных выходов конвейера доказательств)
- **Только внутри тела цикла**: `break` может появляться только внутри тела цикла `while`/`for`
  (включая вложенные блоки/if/match внутри тела); появление вне цикла вызывает ошибку компиляции
  (E1102 `'break' outside of a loop`)
- **Не влияет на доказательство завершаемости**: цикл `while` по-прежнему должен быть доказуемо
  завершаем (мера decreases); `break` не участвует в аргументации завершаемости,
  `while true { break }` не будет принят
- **Семантика заимствования**: ребро потока управления break участвует в структурном отсечении
  обратного BFS-анализа живости RFC-009a (выпрыгнувшие итерации не участвуют в выводе живости
  обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // поток управления переходит после цикла, i == 3
    }
}

// Вложенные циклы: break завершает только внутренний
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // завершает только внутренний цикл
    }
    j = j + 1                  // каждая итерация внешнего цикла выполнит это
}
```

### 3.5 Оператор continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации и сразу переходит к следующей
итерации ближайшего содержащего цикла — `while` возвращается к переоценке условия, `for` берёт
следующий элемент.

- **Действует только на ближайший уровень**: аналогично `break`, без меток
- **Только внутри тела цикла**: появление вне цикла вызывает ошибку компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // пропускает следующее накопление, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Оператор for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация — это привязка нового значения

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация — это привязка
нового значения, а не изменение одной и той же переменной**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Процесс выполнения**:

| Итерация   | Поведение переменной цикла                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------ |
| 1-я        | Создаётся новая привязка `i = 1`, тело цикла выполняется, выводится 1                                  |
| 2-я        | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), тело цикла выполняется, выводится 2 |
| 3-я        | Создаётся новая привязка `i = 3`, тело цикла выполняется, выводится 3                                  |
| 4-я        | Создаётся новая привязка `i = 4`, тело цикла выполняется, выводится 4                                  |
| Завершение | Тело цикла завершается, привязка уничтожается                                                          |

**Ключевой момент**: после каждой итерации привязка, созданная в этой итерации, уничтожается.
Следующая итерация — совершенно новая привязка, не имеющая никакого отношения к привязке предыдущей
итерации.

#### 3.9.2 Разница между for и for mut

| Синтаксис           | Мутабельность переменной цикла | Описание                                   |
| ------------------- | ------------------------------ | ------------------------------------------ |
| `for i in 1..5`     | неизменяемая                   | внутри тела цикла нельзя изменять привязку |
| `for mut i in 1..5` | изменяемая                     | внутри тела цикла можно изменять привязку  |

```yaoxiang
// Допустимо: каждая итерация привязывает новое значение, изменение не нужно
for i in 1..5 {
    print(i)  // чтение значения i
}

// Ошибка: неизменяемая привязка, нельзя изменять
for i in 1..5 {
    i = i + 1  // ошибка: нельзя изменять неизменяемую привязку
}

// Допустимо: использование for mut разрешает изменение привязки
for mut i in 1..5 {
    i = i + 1  // изменение разрешено
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлена во внешней области
i = 10
for i in 1..5 {
    print(i)
}

// Правильно: используйте другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробности см. в
[4.3 Правила затенения](./modules.md#43-правила-затенения).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                                       |
| -------- | -------------------------------------------------------------------- |
| YaoXiang | каждая итерация — новая привязка                                     |
| Rust     | изменение одной и той же переменной (требуется mut)                  |
| Python   | изменение одной и той же переменной (mut не требуется)               |
| C/C++    | изменение одной и той же переменной (требуется указатель или ссылка) |

**Обоснование дизайна**: YaoXiang принимает семантику привязки, потому что:

1. **Больше соответствует естественной семантике**. В естественном языке «для каждого элемента x в
   множестве» означает, что каждый x — независимая сущность. `for i in 1..5` в YaoXiang читается как
   «для каждого i от 1 до 5», где i в каждой итерации — совершенно новая привязка, что согласуется с
   интуитивным человеческим пониманием.

2. **Избежание случайных изменений**. Семантика неизменяемой привязки по умолчанию означает, что
   невозможно случайно изменить переменную цикла внутри тела. Не нужно беспокоиться о том, что
   где-то в сложном теле цикла случайно написано `i = ...`, что приводит к трудноотслеживаемой
   ошибке.

3. **Высокопроизводительное решение под рукой**. Когда действительно нужно повторно использовать
   переменную между итерациями (например, аккумулятор, кэш), достаточно объявить `for mut` для
   переключения в режим изменяемой привязки. Это яснее, чем неявное разделяемое состояние —
   намерение явно выражается через синтаксис, а не скрывается в поведении во время выполнения.

### 3.10 Оператор spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**Блок spawn**: явно объявляет параллельную область, выражения в блоке выполняются параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**Цикл spawn**: параллельный по данным цикл.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**Блок spawn захватывает внешние переменные** (RFC-024 §2.3, семантика захвата значения):

- Тело блока ссылается на внешнюю переменную = **захват значения по Move**: значение снапшотится в
  замыкание в точке создания spawn, тело блока читает через env (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешняя переменная не затрагивается
- **Типы-дескрипторы** (Struct/String/List и т.д.) снапшот = копирование дескриптора, совместное
  использование базового объекта; в Embedded-рантайме (по умолчанию) один поток, одна куча,
  дескриптор действителен
- Для совместного использования между несколькими задачами требуется явный `ref` (§2.13, компилятор
  автоматически выбирает Rc/Arc)
- Внешние переменные, на которые ссылается `return` в блоке, также захватываются

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 — захват значения, result == 6
}
```

### 3.11 Точка входа программы и операторы верхнего уровня

Исходный файл имеет две роли с точки зрения компилятора, **определяемые наличием `yaoxiang.toml`**:

| Роль       | Определение                                       | Тело программы                                                                             |
| ---------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Script** | запуск одного файла напрямую, без `yaoxiang.toml` | **операторы верхнего уровня** (выполняются в порядке написания); `main` — обычная привязка |
| **Bin**    | наличие `yaoxiang.toml`                           | **функция `main`**; операторы верхнего уровня не должны содержать исполняемых операторов   |

#### Script: операторы верхнего уровня и есть программа

При отсутствии manifest файл является «скриптом», **операторы верхнего уровня выполняются в порядке
написания**:

```yaoxiang
use std.io
io.println("hello")          // выполняется напрямую
x: Int = { 42 }              // привязка верхнего уровня: инициализация во время выполнения
io.println(x)                // 42
```

`main` в этом режиме **не особенный** — это всего лишь обычная привязка. Если хотите, чтобы `main`
выполнялся, его необходимо явно вызвать:

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← Необходимо написать эту строку
```

> **Почему `main` не вызывается автоматически?** Операторы верхнего уровня уже являются телом
> программы. При дополнительном неявном вызове `main` скрипт, в котором явно написан `main()`,
> выполнится дважды. Два правила не могут сосуществовать, поэтому в Script существует только одна
> точка входа — «операторы верхнего уровня».

#### Bin: `main` — точка входа

При наличии manifest файл является «исполняемым файлом», в этом случае:

- `main` должен быть определён и должен быть функцией (сигнатура должна позволять вызов с нулём
  аргументов)
- Операторы верхнего уровня не допускают исполняемых операторов — тело программы — это `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main`, не являющийся функцией, — обе ошибки компиляции (первый случай: без
`main` все функции недостижимы; второй случай: привязка значения не будет вызвана).

> **Файлы библиотек**: файлы, используемые другими файлами через `use`, или файлы, на которые
> указывают `[lib].path` / `[exports]`, не требуют `main` — они не являются точкой входа.

#### Инициализация привязок верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются во время выполнения** и не обязаны
быть константами времени компиляции:

```yaoxiang
answer: Int = { 42 }              // значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // вызов функции
```

Инициализация выполняется в **порядке зависимостей**, не завися от порядка написания:

```yaoxiang
derived: Int = base * 3           // ссылается на объявленное позже base
base: Int = 7                     // инициализируется сначала (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (будут перечислены имена в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель ролей файла), RFC-010a приложение D (решение по привязке
> блока).
