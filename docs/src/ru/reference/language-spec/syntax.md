# Спецификация синтаксиса

Данный документ определяет спецификацию синтаксиса языка программирования YaoXiang, включая
лексическую структуру, синтаксические правила и приоритет операторов.

---

## Глава I: Лексическая структура

### 1.1 Исходный файл

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Классификация лексических единиц

| Категория      | Описание                                       | Пример                    |
| -------------- | ---------------------------------------------- | ------------------------- |
| Идентификатор  | Начинается с буквы или подчёркивания           | `x`, `_private`, `my_var` |
| Ключевое слово | Предопределённые зарезервированные слова языка | `Type`, `pub`, `use`      |
| Литерал        | Фиксированное значение                         | `42`, `"hello"`, `true`   |
| Оператор       | Знак операции                                  | `+`, `-`, `*`, `/`        |
| Разделитель    | Синтаксический разделитель                     | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет крайне малое количество ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют специальное значение в любом контексте и не могут использоваться в качестве
идентификаторов.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang разделены на три уровня, которые распознаются парсером (parser) и
проверщиком типов (type checker) на разных этапах:

#### 1.4.1 Литералы-зарезервированные слова

Парсер имеет независимые токены для идентификаторов-литералов, которые не могут использоваться как
обычные идентификаторы:

| Идентификатор | Тип  | Описание                                                                                                    |
| ------------- | ---- | ----------------------------------------------------------------------------------------------------------- |
| `Type`        | —    | Ключевое слово метатипа                                                                                     |
| `true`        | Bool | Логическое истинное значение                                                                                |
| `false`       | Bool | Логическое ложное значение                                                                                  |
| `void`        | Void | Литерал Void (значение Unit). Строчное `void` — литерал значения; прописное `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Выражения-конструкторы

Следующие конструкторы распознаются парсером в контексте сопоставления с образцом и выражений:

| Конструктор | Тип    | Описание                             |
| ----------- | ------ | ------------------------------------ |
| `some(T)`   | Option | Конструктор варианта значения Option |
| `ok(T)`     | Result | Успешный вариант Result              |
| `err(E)`    | Result | Вариант ошибки Result                |

#### 1.4.3 Встроенные имена типов

Следующие имена типов предварительно зарегистрированы проверщиком типов и могут использоваться в
позиции типа без импорта. Парсер рассматривает их как обычные идентификаторы — **не являются
зарезервированными словами, могут быть затенены локальной привязкой (не рекомендуется)**.

| Имя типа | Логический аналог   | Описание                                                                                                                                              |
| -------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)     | Тип записи с нулём полей, имеющий ровно одного обитателя (литерал `void`, см. §1.4.1)                                                                 |
| `Never`  | ⊥ (ложь/пустой тип) | Тип с нулём вариантов, ноль обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` выполняется для всех `T` (принцип взрыва). |
| `Int`    | —                   | Знаковое целое число                                                                                                                                  |
| `Float`  | —                   | Вещественное число                                                                                                                                    |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                 |
| `Char`   | —                   | Символ Unicode                                                                                                                                        |
| `String` | —                   | Строка                                                                                                                                                |

### 1.5 Идентификаторы

Идентификаторы начинаются с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заполнитель, обозначающий игнорирование значения
- Идентификаторы, начинающиеся с подчёркивания, обозначают закрытые члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Вещественные числа

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // при аннотации целевого типа как Array(T, N) литерал становится массивом фиксированной длины
```

> **Литерал словаря требует как минимум одну пару ключ-значение**: `{}` **не является** пустым
> словарём — это пустой блок (значение `Void`, см. [§2.9](#_2-9-блок-как-выражение)). Для пустого
> словаря используйте конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ пустой словарь
> d = { "a": 1 }                       // ✅ литерал словаря
> wrong = {}                           // ❌ это не словарь, а пустой блок (Void)
> ```
>
> **Критерий — содержимое**: грамматика `Dict` требует как минимум одну пару `String ':' Expr`, у
> `{}` нет содержимого для опоры, поэтому берётся нулевая форма блочной структуры. Непустая форма
> описывается содержимым (`{ "k": v }` имеет пару ключ-значение → словарь) — это одного корня с тем,
> что `f = { 5 }` является значением `Int`, а не функцией: **тип определяется содержимым**.

> Множество (Set) не имеет литеральной грамматики и представления во время выполнения — в рамках
> планирования типов коллекций, при появлении требований будет добавлено по образцу Dict (std.set +
> HeapValue::Set). Куда попадают литералы List/Dict, определяется контекстной аннотацией типа: голый
> литерал и литерал с аннотацией `List(T)` становятся расширяемым списком; аннотация `Array(T, N)`,
> применённая непосредственно к литералу, даёт массив фиксированной длины. Неявное преобразование
> List→Array запрещено.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе ошибка этапа компиляции E1002; пустой литерал с
>   ненулевым N также отвергается
> - Тип каждого элемента должен быть совместим с T, иначе ошибка этапа компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отвергаются на этапе разбора
> - Когда N является символьной константой (параметр const функции, например `Array(Int, n)`),
>   проверка количества откладывается до этапа уточнения типов
> - Вложенные литералы массива в v1 (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отвергаются на этапе
>   компиляции, требуется явное послойное конструирование; рекурсивное попадание остаётся для
>   последующих версий

#### 1.6.5 Генераторы списков

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (запись миграции)**: грамматика переменной итерации и была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный pratt-разбор — после
> регистрации `'in'` как инфиксного оператора `x` поглощал `in items` как выражение принадлежности.
> После исправления неидентификаторный pattern сразу завершается с ошибкой разбора и больше не
> откатывается к `_` (тихому проглатыванию ошибки), как в старой реализации. Область влияния: запись
> вида `[x for (a, b) in pairs]`, которая раньше разбиралась, теперь вызывает ошибку — эта форма
> никогда не имела определённого поведения (переменная всегда была `_`), направление ужесточения
> верное, затрат на семантическую миграцию нет.

#### 1.6.6 Проверка членства

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool` — при попадании `true`, при непопадании
> `false`, ошибки не возникает. Разделение семантики: `[]` — это утверждение существования и
> извлечение значения (при неудаче — ошибка), `in` — это запрос о существовании (непопадание —
> нормальный `false`). Правый операнд покрывает: List / Array / Dict(набор ключей) / Tuple /
> String(подстрока) / Range(интервал). `in` — это предикат Хоара первого класса, на этапе уточнения
> типов выступающий базой для утверждений, доказуемых на этапе компиляции. (Множество Set исключено
> из списка правых операндов — Set не имеет представления во время выполнения, см. §1.6.4)

## Глава II: Синтаксические правила

### 2.1 Классификация выражений

              | BinaryOp
              | TypeCast
              | RangeExpr

              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Оператор                       | Ассоциативность |
| --------- | ------------------------------ | --------------- |
| 1         | `()` `[]` `.` `?`              | слева направо   |
| 2         | `as`                           | слева направо   |
| 3         | унарный префиксный `!` `-` `+` | справа налево   |
| 4         | `*` `/` `%`                    | слева направо   |
| 5         | `+` `-`                        | слева направо   |
| 6         | `..`                           | слева направо   |
| 7         | `<<` `>>`                      | слева направо   |
| 8         | `&` `\|` `^`                   | слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=`    | слева направо   |
| 10        | `and` `or`                     | слева направо   |
| 11        | `if...else`                    | справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`        | справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) жёстко связаны: только ниже вызова и доступа к
> члену, выше всех бинарных операторов. Поэтому `!a == b` ≡ `(!a) == b` (семантика в стиле Zig); `!`
> — чисто унарная операция, не участвует в потоке управления с коротким замыканием и ортогональна
> ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение в RFC-010).

> **Сила связывания Range**: `..` имеет силу (6, 7) — левая 6 ниже сложения (7), правая 7 поглощает
> сложение, но не поглощает `..` того же уровня. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, правоассоциативно)                                                              | После изменения ((6,7), левоассоциативно)                                         |
> | ------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (правый операнд `in` уровня 4, `..` уровня 1 не может поглотить, фактически не разбирается) | `x in (1..10)` — интервал целиком как правый операнд `in`                         |
> | `0..n+2`     | `(0..n)+2` (ловушка правоассоциативности: верхняя граница съедается, цикл `for` сразу E3004)             | `0..(n+2)` — верхняя граница — арифметическое выражение                           |
> | `a == b..c`  | `a == (b..c)` (`..` уровня 1 < `==` уровня 3, естественно целиком)                                       | `a == (b..c)` — **семантика не меняется**, `..` по-прежнему выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                               | `1..(2*3)` — верхняя граница — арифметическое выражение                           |
> | `a..b..c`    | `a..(b..c)` (правоассоциативная цепочка, бессмысленный Range в Range)                                    | `(a..b)..c` — **форма со шагом** (`c` — шаг)                                      |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` из «разбирается, но E3004» становится
> «сразу пригодна»; `x in 1..10` из «не разбирается» становится «проверка принадлежности интервалу»;
> `a..b..c` из «бессмысленной вложенности» становится «компонентом шага». Уровень 6 попадает между
> `+` (уровень 5) и `<<` (уровень 7), математический консенсус: интервал — конструкция с тесной
> связью, верхняя граница естественно является полным арифметическим выражением.

### 2.3 Вызов функции

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

Именованные аргументы записываются как `name = value` (RFC-010 §определение функций, RFC-011 §формы
конструирования). Позиционные аргументы должны предшествовать именованным; параметры, указанные
позиционно, в именованных аргументах могут располагаться произвольно:

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // позиционно
add(a = 3, b = 5)  // именованно
add(b = 5, a = 3)  // произвольный порядок
add(3, b = 5)      // смешанно, позиционные впереди
```

Неправильное имя именованного аргумента даёт ошибку **E1014**, одновременное указание формального
параметра позиционно и именованно даёт **E1015**, несовпадение количества — **E1010** (RFC-013).

### 2.4 Доступ к члену

```
MemberAccess::= Expr '.' Identifier
```

### 2.5 Индексация

```
IndexAccess ::= Expr '[' Expr ']'
```

> **Трёхуровневая семантика (RFC-011b)**: `a[i]` разветвляется по типу `a` — ① встроенные контейнеры
> (List/Vec/Array/Dict/Tuple) идут по нативной инструкции индексации (быстрый путь); ②
> пользовательские типы, реализующие интерфейс `Index`, диспетчеризуются в их метод `index`
> (инстанциация `Index(Grid, Int, Float)` внутри типа тела + метод `Grid.index`); ③ позиционное
> связывание `f[0]` из RFC-004 существует только в объявлениях привязки и не идёт по данной
> грамматике. Ключи многомерной индексации `a[0, 1]` упаковываются в кортеж. Другие типы, не
> реализующие `Index`, отвергаются на уровне типов.

### 2.9 Блок как выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения операторов**: разделение между Stmt и поведение перевода строки (`;` как
> явный разделитель, перевод строки как завершение, исключение для продолжения строки, никогда не
> сливать `(`/`[` в начале строки) определены в
> [RFC-038](../design/rfc/draft/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения допускает ровно три интерпретации, определяемые однократно по
**содержимому**:

| Форма               | Запись            | Тип                      | Пример           |
| ------------------- | ----------------- | ------------------------ | ---------------- |
| **Пустой блок**     | `{}`              | `Void`                   | `x: Void = {}`   |
| **Литерал словаря** | `{ "k": v, ... }` | `Dict(K, V)`             | `d = { "a": 1 }` |
| **Блок**            | `{ Stmt* Expr? }` | тип хвостового выражения | `y = { 1 + 1 }`  |

**Порядок определения**:

1. `{}` (без содержимого) → **пустой блок**, значение `Void`
2. Первый элемент — пара `String ':' Expr` → **литерал словаря**
3. Остальное → **блок**, значение даётся хвостовым выражением

> **Почему `{}` не является пустым словарём**: «пустота» пустого словаря не самодостаточна (это
> может быть и `Dict(K, V)`, и пустой блок), а грамматика словаря [§1.6.4](#_1-6-4-коллекции)
> требует как минимум одну пару ключ-значение. Когда не на что опереться, берётся нулевая форма
> блочной структуры: это согласуется с `unsafe {}` / `spawn {}`, без введения исключений. Для
> пустого словаря используется `dict.new()`.
>
> **Почему функциям нужна аннотация**: `f = { stmt }` — это **значение** (тип хвостового выражения),
> а не функция. Для определения функции напишите аннотацию Fn: `f: () -> Int = { 5 }`. Это тот же
> принцип, что и со словарём: **тип определяется содержимым**, а не наличием или отсутствием
> аннотации. (Это правило см. в
> [RFC-010a](./design/rfc/accepted/010a-tail-expression-and-return.md), приложение D.)

**Единая семантика**: значение всех блоков `{}` задаётся **хвостовым выражением**, `return` —
нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| Обычный `{}` | хвостовое выражение | `Void`           |
| `unsafe {}`  | хвостовое выражение | `Void`           |
| `spawn {}`   | хвостовое выражение | `Void`           |

**Ключевые принципы** (подробнее см.
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Если в конце **оператор присваивания**, значение блока `Void`; если нужно `Void` — пишите явно
  `Void`
- **`return` выходит за ближайшую границу функции** (проходит сквозь все блоки, не «возвращается в
  блок»), тип `Never`; `Never <: T` выполняется для любого типа (принцип взрыва), поэтому может
  находиться в любой позиции типа возврата
- Выражение вида `= expr` непосредственно даёт значение

```yaoxiang
// Обычный блок {}: значение даётся хвостовым выражением
result = {
    x = compute()
    x                // значение блока
}

// Блок unsafe {}: хвостовое выражение даёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // значение блока
}

// Блок spawn {}: хвостовое выражение даёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // проходит сквозь if и тело функции, выходит из функции
    }
    n * 2            // хвостовое выражение
}
```

#### `name = { ... }` — функция или значение блока?

`name = { ... }` может быть как определением функции (RFC-007 «простейшая форма без параметров»),
так и привязкой значения блока. Решение принимается по принципу **приоритет аннотации, по умолчанию
функция** (RFC-010a, приложение D):

| Случай                           | Результат          | Пример                             |
| -------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)         | функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип   | функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — нефункциональный тип | **значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                    | функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация и есть тип**: `x: Int = ...` объявляет `x` как `Int`, значит `{ ... }` вычисляется в
`Int`; `f: () -> Int = ...` объявляет `f` как функцию, значит `{ ... }` — тело функции.

Чтобы `{ ... }` вычислился сразу на месте, **просто напишите целевой тип** (новый синтаксис не
нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: без аннотации по умолчанию
f = { 5 }        // f() = 5
```

#### Вложенный функциональный тип: каррирование или возврат функции?

Вложенный функциональный тип справа от `->` имеет два прочтения, различаемых **скобками** (RFC-004):

| Запись                          | Значение            | Вызов                     |
| ------------------------------- | ------------------- | ------------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **каррирование**    | `f(1)(2)`                 |
| `(a: Int) -> ((b: Int) -> Int)` | **возврат функции** | `g(1)` возвращает функцию |

Основание: **аннотация и есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, поэтому `g(1)` должна **быть** той функцией, а не «следующей порцией
аргументов».

```yaoxiang
// Каррирование: две порции аргументов подаются поочерёдно
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний слой — одна порция аргументов, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // возвращённую функцию можно сохранить в переменную и передавать
```

Незаключённый в скобки вложенный `Fn` всегда является каррированием (включая форму с параметрами
типа из RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют тип возврата, тело должно порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка — ожидается `() -> Int`, фактически получено `Int` (E1002).

### 2.11 Оператор распространения ошибки

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` является постфиксным, приоритет совпадает с `.`. Для типа `Result(T, E)`:

- При `Ok(v)` извлекается значение `v` и выполнение продолжается
- При `Err(e)` ошибка распространяется вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // при успехе извлекается значение, при неудаче — распространение вверх
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — это значение: можно связывать, передавать, проверять членство
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// Форма со шагом (третья компонента, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика шага**: в `a..b..c` `c` — это шаг. `c = 0` как литерал отвергается на этапе
> компиляции; динамический `c` проверяется на ноль во время выполнения (семейство E6001; после
> внедрения системы ошибок будет повышен до Result). `c < 0` допустимо, направление интервала
> меняется в зависимости от знака (`10..0..(-2)` — убывание).

### 2.13 Выражение ref

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (одна задача) или Arc
(между задачами), пользователю не нужно заботиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // между задачами: компилятор автоматически выберет Arc
```

### 2.14 Выражение unsafe

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и работы с сырыми указателями.
Используйте `return`, чтобы вернуть определение типа во внешнюю область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Возвращённый тип доступен вне `unsafe {}`
- Доступ к полям типа требует права unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен вне блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Области видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости имеет доступ к переменным внешней
- Внешняя область видимости не имеет доступа к переменным внутренней
- Объявление переменных следует принципу «приоритет присваивания»

```yaoxiang
// Блочная область видимости
{
    x = 10
    // x виден в этой области видимости
}
// x не виден за пределами этой области видимости

// Область видимости функции
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не виден за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск `x` идёт по цепочке областей видимости наружу; если найдено — присваивание,
  если нет — новое объявление
- `mut x = value`: явное новое объявление изменяемой переменной, запрещено совпадение имён с внешним
  уровнем
- В одной области видимости каждое имя может быть объявлено только один раз

> **Подробное определение**: полные правила областей видимости, объявления и затенения переменных
> см. в [Спецификации модульной системы](./modules.md#第四章作用域).

### 3.3 Оператор return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, выходящий за ближайшую **границу функции**
(проходит сквозь все блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается в блок»**.

**Тип**: `return e : Never` (если `e : T`). `Never <: T'` выполняется для любого `T'` (принцип
взрыва, см. [Система типов §2.2](./type-system.md)), поэтому `return` может находиться в любой
позиции типа возврата без дополнительных правил-ограничений.

**Связь с вычислением блока**: значение блока всегда есть **хвостовое выражение** (см. §2.9).
`{ return n }` как блок имеет значение `n` типа `Never`; одновременно `return` выходит из функции.
**Оба факта верны одновременно**, что обеспечивается принципом взрыва.

`return` вместе с хвостовым выражением делает возможным «досрочный возврат» без специальных правил
для `return` применительно к функции — см.
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // проходит сквозь if, выходит из функции (тип Never)
    }
    n * factorial(n - 1)  // хвостовое выражение = значение блока
}
```

### 3.4 Оператор break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает ближайший содержащий цикл `while`/`for`, поток управления
переходит после тела цикла.

- **Выходит только на ближайший уровень**: `break` всегда действует на ближайший содержащий цикл.
  Когда во вложенных циклах нужно выйти сразу на несколько уровней, вынесите внутренний цикл в
  функцию и верните через `return`, либо используйте флаг (break/continue без меток; если в будущем
  будут введены метки циклов, это пойдёт через процесс RFC в синтаксисе на стороне объявления цикла,
  наряду с многоточечным выходом в конвейере доказательств)
- **Только внутри цикла**: `break` может находиться только в теле цикла `while`/`for` (включая
  вложенные блоки/if/match внутри тела), использование вне цикла — ошибка компиляции (E1102
  `'break' outside of a loop`)
- **Не влияет на доказательство завершимости**: цикл `while` по-прежнему должен быть доказуемо
  завершающимся (мера decreases); `break` не участвует в аргументации завершимости,
  `while true { break }` не принимается
- **Семантика заимствования**: ребро потока управления break участвует в структурном разрыве
  обратного BFS-анализа живости RFC-009a (пропущенные итерации не участвуют в выводе живости
  обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // поток управления переходит после цикла, i == 3
    }
}

// Вложенные циклы: break выходит только из внутреннего
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // завершает только внутренний цикл
    }
    j = j + 1                  // выполняется на каждой итерации внешнего цикла
}
```

### 3.5 Оператор continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации и сразу переходит к следующей
итерации ближайшего содержащего цикла — `while` возвращается к пересмотру условия, `for` берёт
следующий элемент.

- **Действует только на ближайший уровень**: то же, что и `break`, без меток
- **Только внутри цикла**: использование вне цикла — ошибка компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // пропускает накопление ниже, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12（1 + 2 + 4 + 5）
```

### 3.9 Оператор for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация — это новая привязка

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация создаёт новую
привязку, а не изменяет одну и ту же переменную**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Ход выполнения**:

| Итерация   | Поведение переменной цикла                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------- |
| 1-я        | Создаётся новая привязка `i = 1`, выполняется тело, печатается 1                                  |
| 2-я        | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), выполняется тело, печатается 2 |
| 3-я        | Создаётся новая привязка `i = 3`, выполняется тело, печатается 3                                  |
| 4-я        | Создаётся новая привязка `i = 4`, выполняется тело, печатается 4                                  |
| Завершение | Тело цикла заканчивается, привязка уничтожается                                                   |

**Ключевой момент**: после завершения каждой итерации созданная в ней привязка уничтожается.
Следующая итерация — это совершенно новая привязка, не имеющая никакого отношения к привязке
предыдущей итерации.

#### 3.9.2 Различие между for и for mut

| Синтаксис           | Изменяемость переменной цикла | Описание                              |
| ------------------- | ----------------------------- | ------------------------------------- |
| `for i in 1..5`     | неизменяемая                  | В теле цикла нельзя изменять привязку |
| `for mut i in 1..5` | изменяемая                    | В теле цикла можно изменять привязку  |

```yaoxiang
// Допустимо: каждая итерация создаёт новую привязку, изменять не нужно
for i in 1..5 {
    print(i)  // чтение значения i
}

// Ошибка: неизменяемая привязка, нельзя изменять
for i in 1..5 {
    i = i + 1  // ошибка: нельзя изменять неизменяемую привязку
}

// Допустимо: использование for mut разрешает изменение привязки
for mut i in 1..5 {
    i = i + 1  // изменение разрешено
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлена во внешней области
i = 10
for i in 1..5 {
    print(i)
}

// Правильно: используйте другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробнее см.
[4.3 Правила затенения](./modules.md#43-遮蔽规则).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                               |
| -------- | ------------------------------------------------------------ |
| YaoXiang | Каждая итерация — новая привязка                             |
| Rust     | Изменение той же переменной (требуется mut)                  |
| Python   | Изменение той же переменной (mut не требуется)               |
| C/C++    | Изменение той же переменной (требуется указатель или ссылка) |

**Обоснование дизайна**: YaoXiang использует семантику привязки, потому что:

1. **Более соответствует естественной семантике**. В естественном языке «для каждого элемента x из
   набора» означает, что каждый x — самостоятельная сущность. YaoXiang-овское `for i in 1..5`
   читается как «для каждого i от 1 до 5», i в каждой итерации — совершенно новая привязка, что
   согласуется с интуитивным человеческим пониманием.

2. **Избежание случайных изменений**. Семантика неизменяемой привязки по умолчанию означает, что в
   теле цикла нельзя случайно изменить переменную цикла. Не нужно беспокоиться о том, что где-то в
   сложном теле цикла случайно написано `i = ...`, вызывая трудноотслеживаемые ошибки.

3. **Высокопроизводительные решения под рукой**. Когда действительно нужно повторно использовать
   переменную между итерациями (например, аккумулятор, кэш), используйте `for mut` для переключения
   в режим изменяемой привязки. Это яснее, чем неявное разделение состояния — намерение выражается
   синтаксисом явно, а не скрывается в поведении во время выполнения.

### 3.10 Оператор spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn-блок**: явное объявление параллельной области, выражения внутри блока выполняются
параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn-цикл**: параллельный по данным цикл.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn-блок захватывает внешние переменные** (RFC-024 §2.3, семантика захвата значения):

- Ссылка тела блока на внешнюю переменную = **захват значения с перемещением**: значение в точке
  создания spawn снимется в среде замыкания, тело блока читает через env (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешняя переменная не затрагивается
- **Типы-дескрипторы** (Struct/String/List и т.п.) снимок = копия дескриптора, разделяют нижележащий
  объект; во встроенной среде выполнения (по умолчанию) один поток — одна куча, дескриптор
  действителен
- Для разделения между несколькими задачами требуется явный `ref` (§2.13, компилятор автоматически
  выбирает Rc/Arc)
- Внешняя переменная, на которую ссылается `return` внутри блока, также захватывается

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 захвачены по значению, result == 6
}
```

### 3.11 Точка входа в программу и операторы верхнего уровня

Исходный файл с точки зрения компилятора имеет две роли, **определяемые наличием `yaoxiang.toml`**:

| Роль       | Определение                                              | Тело программы                                                                          |
| ---------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Script** | Одиночный файл запускается напрямую, без `yaoxiang.toml` | **Операторы верхнего уровня** (выполняются в порядке записи); `main` — обычная привязка |
| **Bin**    | Существует `yaoxiang.toml`                               | **Функция `main`**; исполняемые операторы на верхнем уровне запрещены                   |

#### Script: операторы верхнего уровня и есть программа

При отсутствии manifest файл является «скриптом», **операторы верхнего уровня выполняются в порядке
записи**:

```yaoxiang
use std.io
io.println("hello")          // непосредственное выполнение
x: Int = { 42 }              // привязка верхнего уровня: инициализация во время выполнения
io.println(x)                // 42
```

`main` в этом режиме **не особенный** — это просто обычная привязка. Чтобы `main` запустился, нужно
явно его вызвать:

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← эту строку нужно написать
```

> **Почему `main` не вызывается автоматически?** Операторы верхнего уровня уже являются телом
> программы. Если ещё и неявно вызывать `main`, то скрипт с явным `main()` выполнился бы дважды. Два
> правила не могут сосуществовать, поэтому в режиме Script существует только одна точка входа —
> «операторы верхнего уровня».

#### Bin: `main` — это точка входа

При наличии manifest файл является «исполняемой целью», в этом случае:

- Должна быть определена `main`, и она должна быть функцией (сигнатура должна позволять вызов без
  аргументов)
- На верхнем уровне не допускаются исполняемые операторы — телом программы является `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не-функция — ошибка компиляции (первое: без `main` все функции
недостижимы; второе: привязка-значение не будет вызвана).

> **Файлы библиотек**: файлы, которые `use`-ятся другими файлами, или файлы, на которые указывают
> `[lib].path` / `[exports]`, не требуют `main` — они не являются точкой входа в программу.

#### Инициализация привязок верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются во время выполнения**, они не обязаны
быть константами этапа компиляции:

```yaoxiang
answer: Int = { 42 }              // значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // вызов функции
```

Инициализация выполняется в **порядке зависимостей**, независимо от порядка записи:

```yaoxiang
derived: Int = base * 3           // ссылается на base, объявленную ниже
base: Int = 7                     // инициализируется первой (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (будут перечислены имена в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // ошибка: a → b → a
```

> **Основание дизайна**: RFC-029f (модель ролей файла), RFC-010a приложение D (разрешение блочной
> привязки).
