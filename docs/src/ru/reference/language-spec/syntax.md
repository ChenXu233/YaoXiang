# Синтаксическая спецификация

Этот файл определяет синтаксическую спецификацию языка программирования YaoXiang, включая
лексическую структуру, синтаксические правила и приоритет операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходный файл

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Классификация лексических единиц

| Категория      | Описание                                          | Пример                    |
| -------------- | ------------------------------------------------- | ------------------------- |
| Идентификатор  | Начинается с буквы или подчёркивания              | `x`, `_private`, `my_var` |
| Ключевое слово | Языковые предопределённые зарезервированные слова | `Type`, `pub`, `use`      |
| Литерал        | Фиксированное значение                            | `42`, `"hello"`, `true`   |
| Оператор       | Знак операции                                     | `+`, `-`, `*`, `/`        |
| Разделитель    | Синтаксический разделитель                        | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет очень небольшое количество ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют специальное значение в любом контексте и не могут использоваться в качестве
идентификаторов.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang разделены на три слоя, распознаваемых парсером (parser) и
проверщиком типов (type checker) на разных этапах:

#### 1.4.1 Литеральные зарезервированные слова

Идентификаторы литералов, которые парсер выделяет как отдельные токены и которые не могут
использоваться как обычные идентификаторы:

| Идентификатор | Принадлежит типу | Описание                                                                                                    |
| ------------- | ---------------- | ----------------------------------------------------------------------------------------------------------- |
| `Type`        | —                | Ключевое слово метатипа                                                                                     |
| `true`        | Bool             | Логическое значение истина                                                                                  |
| `false`       | Bool             | Логическое значение ложь                                                                                    |
| `void`        | Void             | Литерал Void (значение Unit). Строчная `void` — литерал значения; заглавная `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Имена вариантов

Имена вариантов распознаются парсером в контексте **паттерна** (голые имена разрешаются по набору
вариантов типа scrutinee, см. §2.8); в контексте **выражения** конструирование варианта требует
квалификации типа — `Result(Int, String).ok(5)`, `Option(T).some(v)`, `Color.green()` (RFC-010
record type и типы: конструкторы вариантов — это поля функционального типа в определении типа, голое
имя `ok(5)` не является вызовом конструктора).

| Имя варианта | Принадлежит типу | Описание                         |
| ------------ | ---------------- | -------------------------------- |
| `some(T)`    | Option           | Конструктор value variant Option |
| `ok(T)`      | Result           | Успешный вариант Result          |
| `err(E)`     | Result           | Вариант ошибки Result            |

#### 1.4.3 Встроенные имена типов

Следующие имена типов предварительно зарегистрированы проверщиком типов и могут использоваться в
позиции типа без импорта. Парсер рассматривает их как обычные идентификаторы — **это не
зарезервированные слова, они могут быть затенены локальной привязкой (не рекомендуется)**.

| Имя типа | Логическое соответствие | Описание                                                                                                                                              |
| -------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)         | Тип-произведение с нулём полей, ровно один обитатель (литерал `void`, см. §1.4.1)                                                                     |
| `Never`  | ⊥ (ложь/пустой тип)     | Тип с нулём вариантов, ноль обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` выполняется для всех `T` (принцип взрыва). |
| `Int`    | —                       | Знаковое целое                                                                                                                                        |
| `Float`  | —                       | Число с плавающей точкой                                                                                                                              |
| `Bool`   | —                       | Логическое значение: `true` / `false`                                                                                                                 |
| `Char`   | —                       | Символ Unicode                                                                                                                                        |
| `String` | —                       | Строка                                                                                                                                                |

### 1.5 Идентификаторы

Идентификаторы начинаются с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заглушка, обозначающая игнорирование значения
- Идентификаторы, начинающиеся с подчёркивания, обозначают приватные члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей точкой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // целевая аннотация типа Array(T, N) — литерал становится массивом фиксированной длины
```

> **Литерал словаря требует как минимум одну пару ключ-значение**: `{}` — это **не** пустой словарь,
> а пустой блок (значение `Void`, см. [§2.9](#_2-9-块表达式)). Для пустого словаря используйте
> конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ Пустой словарь
> d = { "a": 1 }                       // ✅ Литерал словаря
> wrong = {}                           // ❌ Это не словарь, а пустой блок (Void)
> ```
>
> **Критерий — содержимое**: грамматика `Dict` требует как минимум одну пару `String ':' Expr`, а у
> `{}` содержимого нет, поэтому берётся нулевая форма блочной структуры. Непустая форма
> самоописываема содержимым (`{ "k": v }` имеет пару ключ-значение → словарь) — это однородно с тем,
> что `f = { 5 }` — это значение `Int`, а не функция: **тип определяется содержимым**.

> У Set нет ни литеральной грамматики, ни представления в runtime — тип множества в планах, при
> появлении требований он будет дополнен по образцу Dict (std.set + HeapValue::Set). Точка
> разрешения литералов List/Dict определяется аннотацией контекстного типа: голый литерал с
> аннотацией `List(T)` становится расширяемым списком; аннотация `Array(T, N)` непосредственно на
> литерале даёт массив фиксированной длины. Неявное преобразование List→Array запрещено.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе ошибка компиляции E1002; пустой литерал с
>   ненулевым N также отвергается
> - Тип каждого элемента должен быть совместим с T, иначе ошибка компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отвергаются на этапе разбора
> - Если N — символьная константа (const-параметр функции, как `Array(Int, n)`), проверка количества
>   откладывается до фазы уточнения типов
> - Литералы вложенных массивов v1 (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отвергаются на этапе
>   компиляции, требуется послойное явное конструирование; рекурсивное разрешение остаётся на
>   будущие версии

#### 1.6.5 List comprehension

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Поведение ужесточено (запись о миграции)**: грамматика переменной итерации изначально была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный парсинг pratt — после
> регистрации `'in'` как инфиксного оператора `x` поглощал бы `in items` как выражение membership.
> После исправления не-идентификаторный pattern напрямую не разбирается и больше не откатывается к
> `_`, как в старой реализации (тихое проглатывание ошибки). Область влияния: записи вида
> `[x for (a, b) in pairs]`, которые раньше разбирались, теперь выдают ошибку — эта форма никогда не
> имела определённого поведения (переменная всегда была `_`), направление ужесточения верно, без
> затрат на миграцию семантики.

#### 1.6.6 Проверка членства

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool`: совпадение даёт `true`, несовпадение —
> `false`, без ошибки. Разделение семантики: `[]` — утверждение наличия и извлечение значения
> (ошибка при неудаче), `in` — запрос наличия (несовпадение — нормальный `false`). Правый операнд
> покрывает: List / Array / Dict(набор ключей) / Tuple / String(подстрока) / Range(интервал). `in` —
> предикат первого класса по Хоару, на этапе уточнения типов служит основой для доказуемых во время
> компиляции утверждений. (Set исключён из списка правых операндов — у Set нет представления в
> runtime, см. §1.6.4)

## Глава 2: Синтаксические правила

### 2.1 Классификация выражений

```
Expr        ::= Literal
              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Оператор                    | Ассоциативность |
| --------- | --------------------------- | --------------- |
| 1         | `()` `[]` `.` `?`           | слева направо   |
| 2         | `as`                        | слева направо   |
| 3         | Унарный префикс `!` `-` `+` | справа налево   |
| 4         | `*` `/` `%`                 | слева направо   |
| 5         | `+` `-`                     | слева направо   |
| 6         | `..`                        | слева направо   |
| 7         | `<<` `>>`                   | слева направо   |
| 8         | `&` `\|` `^`                | слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=` | слева направо   |
| 10        | `and` `or`                  | слева направо   |
| 11        | `if...else`                 | справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`     | справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) имеют плотное связывание: только ниже вызова и
> доступа к членам, выше всех бинарных операторов. Следовательно, `!a == b` ≡ `(!a) == b` (семантика
> в стиле Zig); `!` — чисто унарная операция, не участвующая в короткозамыкающем потоке управления,
> ортогональная ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение в
> RFC-010).

> **Сила связывания Range**: `..` имеет силу связывания (6, 7) — левая 6 ниже сложения (5→7), правая
> 7 поглощает сложение, но не поглощает `..` того же уровня. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, правоассоц.)                                                                    | После изменения ((6,7), левоассоц.)                                               |
> | ------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (правый операнд `in` уровня 4, `..` уровня 1 не может поглотить, фактически не разбирается) | `x in (1..10)` — интервал целиком как правый операнд `in`                         |
> | `0..n+2`     | `(0..n)+2` (ловушка правоассоц.: верхняя граница поглощается, цикл `for` сразу выдаёт E3004)             | `0..(n+2)` — верхняя граница — арифметическое выражение                           |
> | `a == b..c`  | `a == (b..c)` (`..` уровня 1 < `==` уровня 3, естественно как целое)                                     | `a == (b..c)` — **семантика не меняется**, `..` по-прежнему выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                               | `1..(2*3)` — верхняя граница — арифметическое выражение                           |
> | `a..b..c`    | `a..(b..c)` (правоассоц. цепочка, бессмысленный Range в Range)                                           | `(a..b)..c` — **форма step** (`c` — шаг)                                          |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` переходит от «успешный разбор, но
> E3004» к «сразу доступно»; `x in 1..10` переходит от «не разбирается» к «проверка интервала»;
> `a..b..c` переходит от «бессмысленной вложенности» к «компоненту step». Уровень 6 попадает между
> `+` (уровень 5) и `<<` (уровень 7) — математическая конвенция: интервал — это плотно связывающая
> конструкция, верхняя граница естественно является полным арифметическим выражением.

### 2.3 Вызов функции

```
FnCall      ::= Expr '(' ArgList? ')'
ArgList     ::= Expr (',' Expr)* (',' NamedArg)* | NamedArg (',' NamedArg)*
NamedArg    ::= Identifier '=' Expr
```

Именованные аргументы записываются как `name = value` (RFC-010 §определение функций, RFC-011 §форма
конструкции). Позиционные аргументы должны идти перед именованными; порядок аргументов, заданных
позиционно, в именованных аргументах может быть произвольным:

```yaoxiang
add: (a: Int, b: Int) -> Int = a + b

add(3, 5)          // позиционно
add(a = 3, b = 5)  // именованно
add(b = 5, a = 3)  // произвольный порядок
add(3, b = 5)      // смешанно, позиционные впереди
```

Неверное имя в именованном аргументе выдаёт **E1014**, одновременное указание одного и того же
формального параметра позиционно и именованно — **E1015**, несоответствие количества — **E1010**
(RFC-013).

### 2.4 Доступ к членам

```
MemberAccess::= Expr '.' Identifier
```

### 2.5 Доступ по индексу

```
IndexAccess ::= Expr '[' Expr ']'
```

> **Трёхслойная семантика (RFC-011b)**: `a[i]` разветвляется по типу `a` — ① встроенные контейнеры
> (List/Vec/Array/Dict/Tuple) идут через нативную индексную инструкцию (быстрый путь); ②
> пользовательские типы, реализующие trait `Index`, диспетчеризируются к их методу `index`
> (инстанциация `Index(Grid, Int, Float)` в теле типа + метод `Grid.index`); ③ позиционное
> связывание `f[0]` из RFC-004 существует только в объявлении связывания, не проходит через эту
> грамматику. Ключи многомерного индекса `a[0, 1]` упаковываются в кортеж. Типы, не реализующие
> `Index`, отвергаются на уровне типов.

### 2.6 Преобразование типа

```
TypeCast    ::= Expr 'as' TypeExpr
```

### 2.7 Условное выражение

```
IfExpr      ::= 'if' Expr Block ('else' 'if' Expr Block)* ('else' Block)?
```

### 2.8 Сопоставление с образцом

```
MatchExpr   ::= 'match' Expr '{' MatchArm+ '}'
MatchArm    ::= Pattern ('|' Pattern)* ('if' Expr)? '=>' Expr ','
Pattern     ::= Literal
              | Identifier
              | Wildcard
              | StructPattern
              | TuplePattern
              | EnumPattern
              | OrPattern
```

> **Требование набора вариантов для деструкции вариантов** (RFC-010b): `EnumPattern` (имена
> вариантов вроде `ok(v)`, `some(x)` и т.д. разрешаются по scrutinee) требует, чтобы тип scrutinee
> был **суммой типов с присутствующим набором вариантов**. Набор вариантов попадает в проверщик
> только через определение типа или импорт `use` — `Result`/`Option` определены в
> `std.result`/`std.option`, перед использованием требуется `use std.result` / `use std.option`
> (равноправны форма единого модуля и группировки `use std.{...}`); иначе деструкция варианта выдаёт
> E1002. Проверка полноты однородна: подстановочная ветка освобождает от полноты, без неё — полная
> проверка по набору вариантов.

### 2.9 Блочное выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения операторов**: разделение между Stmt и поведение перевода строки (явное
> разделение `;`, завершение переводом строки, исключения для продолжения строки, никогда не
> объединяемые с `(`/`[` в начале строки) определены в
> [RFC-038](../../design/rfc/accepted/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения имеет ровно три интерпретации, определяемые **содержимым** за один проход:

| Форма               | Запись            | Тип                      | Пример           |
| ------------------- | ----------------- | ------------------------ | ---------------- |
| **Пустой блок**     | `{}`              | `Void`                   | `x: Void = {}`   |
| **Литерал словаря** | `{ "k": v, ... }` | `Dict(K, V)`             | `d = { "a": 1 }` |
| **Блок**            | `{ Stmt* Expr? }` | тип хвостового выражения | `y = { 1 + 1 }`  |

**Порядок разрешения**:

1. `{}` (без содержимого) → **пустой блок**, значение `Void`
2. Первый элемент — пара `String ':' Expr` ключ-значение → **литерал словаря**
3. Остальное → **блок**, значение задаётся хвостовым выражением

> **Почему `{}` — не пустой словарь**: «пустота» пустого словаря не может самоописаться (это мог бы
> быть как `Dict(K, V)`, так и пустой блок), а грамматика словаря [§1.6.4](#_1-6-4-集合) требует как
> минимум одну пару ключ-значение. При отсутствии содержимого берётся нулевая форма блочной
> структуры: это согласуется с `unsafe {}` / `spawn {}`, не вводит исключений. Для пустого словаря
> используйте `dict.new()`.
>
> **Почему функции нужна аннотация**: `f = { stmt }` — это **значение** (тип хвостового выражения),
> а не функция. Чтобы определить функцию, явно укажите аннотацию Fn: `f: () -> Int = { 5 }`. Это
> следует тому же принципу, что и словари: **тип определяется содержимым**, а не наличием аннотации.
> (Это правило см. в [RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md),
> приложение D.)

**Единая семантика**: значение всех блоков `{}` задаётся **хвостовым выражением**, `return` —
нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| Обычный `{}` | Хвостовое выражение | `Void`           |
| `unsafe {}`  | Хвостовое выражение | `Void`           |
| `spawn {}`   | Хвостовое выражение | `Void`           |

**Основные принципы** (подробности см. в
[RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Если в конце стоит **оператор присваивания**, значение блока — `Void`; если нужно `Void`, напишите
  его явно
- **`return` завершает ближайшую границу функции** (проходит сквозь все блоки, не «возвращается в
  блок»), тип `Never`; `Never <: T'` выполняется для любого `T'` (принцип взрыва), поэтому `return`
  может появляться в любой позиции возвращаемого типа без дополнительных ограничивающих правил
- Форма выражения `= expr` напрямую даёт значение

```yaoxiang
// Обычный блок {}: значение задаётся хвостовым выражением
result = {
    x = compute()
    x                // значение блока
}

// блок unsafe {}: хвостовое выражение задаёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // значение блока
}

// блок spawn {}: хвостовое выражение задаёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // проходит сквозь if и тело функции, выходит из функции
    }
    n * 2            // хвостовое выражение
}
```

#### `name = { ... }` — функция или значение блока?

`name = { ... }` может оказаться как определением функции (RFC-007 «пустые параметры — простейшая
форма»), так и связыванием значения блока. Решение — **аннотация в приоритете, по умолчанию
функция** (приложение D RFC-010a):

| Случай                           | Результат          | Пример                             |
| -------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)         | Функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип   | Функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — нефункциональный тип | **Значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                    | Функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация есть тип**: `x: Int = ...` объявляет `x` как `Int`, значит `{ ... }` вычисляется в
`Int`; `f: () -> Int = ...` объявляет `f` как функцию, значит `{ ... }` — тело функции.

Чтобы `{ ... }` вычислился на месте, **укажите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: без аннотации — по умолчанию
f = { 5 }        // f() = 5
```

#### Вложенные функциональные типы: каррирование или возврат функции?

Вложенный функциональный тип справа от `->` имеет два прочтения, различаемых **скобками** (RFC-004):

| Запись                          | Значение            | Вызов                     |
| ------------------------------- | ------------------- | ------------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **Каррирование**    | `f(1)(2)`                 |
| `(a: Int) -> ((b: Int) -> Int)` | **Возврат функции** | `g(1)` возвращает функцию |

Основание: **аннотация есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, поэтому `g(1)` должно **быть** той функцией, а не «следующим сегментом
параметров».

```yaoxiang
// Каррирование: два сегмента параметров подаются послойно
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний сегмент параметров, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // возвращённую функцию можно сохранить в переменную, передавать
```

Нескобочные вложенные `Fn` всегда трактуются как каррирование (включая форму типовых параметров из
RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют тип возврата, тело должно порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка: ожидается `() -> Int`, фактически получено `Int` (E1002).

### 2.11 Оператор распространения ошибок

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` — постфиксный, с тем же приоритетом, что и `.`. Для типа `Result(T, E)`:

- В случае `Ok(v)` извлекает значение `v` и продолжает выполнение
- В случае `Err(e)` распространяет ошибку вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // при успехе извлекает значение, при неудаче распространяет вверх
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — это значение: связывание, передача, проверка членства
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// форма step (третий компонент, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика step**: в `a..b..c` `c` — это шаг. `c = 0` как литерал отвергается на этапе
> компиляции; динамический `c` проверяется на ноль в runtime (семейство E6001; после внедрения
> системы ошибок будет повышен до Result). `c < 0` допустимо, направление интервала меняется на
> противоположное в зависимости от знака (`10..0..(-2)` убывает).

### 2.13 Выражение ref

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (в пределах одной задачи)
или Arc (между задачами), пользователю не нужно беспокоиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // между задачами: компилятор автоматически выберет Arc
```

### 2.14 Выражение unsafe

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и операций с сырыми указателями.
Используйте `return`, чтобы вернуть определение типа во внешнюю область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и оперировать сырыми указателями
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует права unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Область видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней области
- Внешняя область видимости не может обращаться к переменным внутренней области
- Объявление переменных следует принципу «присваивание в приоритете»

```yaoxiang
// Блочная область видимости
{
    x = 10
    // x видна в этой области видимости
}
// x не видна за пределами этой области видимости

// Область видимости функции
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не видна за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск `x` идёт наружу по цепочке областей видимости; если найдено — присваивание,
  иначе новое объявление
- `mut x = value`: явное новое объявление изменяемой переменной, запрещено одноимённой с внешней
- В одной области видимости любое имя может быть объявлено только один раз

> **Подробное определение**: полные правила области видимости, объявления переменных и механизм
> затенения подробно описаны в [спецификации модульной системы](./modules.md#第四章作用域).

### 3.3 Оператор return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, завершающий ближайшую **границу функции**
(проходит сквозь все блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается в блок»**.

**Тип**: `return e : Never` (`e : T`). `Never <: T'` выполняется для любого `T'` (принцип взрыва,
см. [type system §2.2](./type-system.md)), поэтому `return` может появляться в любой позиции
возвращаемого типа без дополнительных ограничивающих правил.

**Связь с вычислением блока**: значение блока всегда равно **хвостовому выражению** (см. §2.9).
`{ return n }` как блок имеет значение `n`, тип `Never`; одновременно `return` завершает функцию.
**Оба факта выполняются одновременно**, сосуществуя благодаря принципу взрыва.

`return` и хвостовое выражение вместе делают возможным «досрочный возврат» без необходимости в
специальном правиле для `return` относительно функции — см.
[RFC-010a](../../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // проходит сквозь if, завершает функцию (тип Never)
    }
    n * factorial(n - 1)  // хвостовое выражение = значение блока
}
```

### 3.4 Оператор break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает самый внутренний цикл `while`/`for`, поток управления переходит
к коду после тела этого цикла.

- **Только ближайший уровень**: `break` всегда действует на самый внутренний содержащий его цикл.
  Если во вложенных циклах нужно выйти сразу на несколько уровней, извлеките внутренний цикл в
  функцию и используйте `return`, либо примените флаг (break/continue без меток; если в будущем
  будут введены метки циклов, их синтаксис пойдёт через RFC и будет решён вместе с конструкцией
  многоточечного выхода в доказательственном конвейере)
- **Только в теле цикла**: `break` может появляться только в теле цикла `while`/`for` (включая
  вложенные блоки/if/match); появление вне цикла — ошибка компиляции (E1102
  `'break' outside of a loop`)
- **Не влияет на доказательство завершимости**: `break` не участвует в аргументе завершимости — он
  не предоставляет меру и не образует шага убывания меры; обязательство завершимости цикла не
  зависит от `break` и инициируется уточнением типа (см.
  [type-system §8.4](./type-system.md#84-terminates终止测度谓词))
- **Семантика заимствования**: ребро потока управления break участвует в структурном разрезе
  обратного BFS-анализа живости из RFC-009a (выпрыгивающие итерации не участвуют в выводе активности
  обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // поток управления переходит после цикла, i == 3
    }
}

// Вложенные циклы: break выходит только из внутреннего
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // завершает только внутренний цикл
    }
    j = j + 1                  // каждая итерация внешнего цикла достигает этой точки
}
```

### 3.5 Оператор continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации, сразу переходит к следующей
итерации самого внутреннего цикла — `while` возвращается к пересмотру условия, `for` берёт следующий
элемент.

- **Только ближайший уровень**: аналогично `break`, без меток
- **Только в теле цикла**: появление вне цикла — ошибка компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // пропускает последующее накопление, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Оператор for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация — это связывание нового значения

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация — это связывание
нового значения, а не модификация той же переменной**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Процесс выполнения**:

| Итерация   | Поведение переменной цикла                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| 1-я        | Создаётся новая привязка `i = 1`, выполняется тело цикла, печатается 1                                  |
| 2-я        | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), выполняется тело цикла, печатается 2 |
| 3-я        | Создаётся новая привязка `i = 3`, выполняется тело цикла, печатается 3                                  |
| 4-я        | Создаётся новая привязка `i = 4`, выполняется тело цикла, печатается 4                                  |
| Завершение | Тело цикла завершается, привязка уничтожается                                                           |

**Ключевой момент**: после завершения каждой итерации созданная в ней привязка уничтожается.
Следующая итерация — это совершенно новая привязка, не имеющая никакого отношения к привязке
предыдущей итерации.

#### 3.9.2 Различие между for и for mut

| Синтаксис           | Изменяемость переменной цикла | Описание                                    |
| ------------------- | ----------------------------- | ------------------------------------------- |
| `for i in 1..5`     | Неизменяемая                  | Привязку нельзя модифицировать в теле цикла |
| `for mut i in 1..5` | Изменяемая                    | Привязку можно модифицировать в теле цикла  |

```yaoxiang
// Допустимо: каждая итерация связывает новое значение, модификация не нужна
for i in 1..5 {
    print(i)  // чтение значения i
}

// Ошибка: неизменяемая привязка, модификация невозможна
for i in 1..5 {
    i = i + 1  // ошибка: неизменяемую привязку нельзя модифицировать
}

// Допустимо: использование for mut разрешает модификацию
for mut i in 1..5 {
    i = i + 1  // модификация разрешена
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлена во внешней области видимости
i = 10
for i in 1..5 {
    print(i)
}

// Правильно: используйте другое имя переменной
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробности см. в
[4.3 Правила затенения](./modules.md#43-遮蔽规则).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                               |
| -------- | ------------------------------------------------------------ |
| YaoXiang | Каждая итерация — связывание нового значения                 |
| Rust     | Модификация той же переменной (требует mut)                  |
| Python   | Модификация той же переменной (mut не нужен)                 |
| C/C++    | Модификация той же переменной (требует указатель или ссылку) |

**Обоснование дизайна**: YaoXiang использует семантику связывания, потому что:

1. **Более естественная семантика**. В естественном языке «для каждого элемента x в коллекции»
   означает, что каждый x — независимая сущность. `for i in 1..5` в YaoXiang читается как «для
   каждого i от 1 до 5», i каждой итерации — это совершенно новое связывание, что согласуется с
   человеческой интуицией.

2. **Предотвращение случайной модификации**. Семантика неизменяемого связывания по умолчанию
   означает, что переменную цикла нельзя случайно модифицировать в теле цикла. Не нужно беспокоиться
   о том, что где-то в сложном теле цикла случайно написано `i = ...`, приводящее к
   трудноотслеживаемым ошибкам.

3. **Высокопроизводительные решения под рукой**. Когда действительно нужно повторно использовать
   переменную между итерациями (например, аккумулятор, кэш), достаточно объявить `for mut`,
   переключившись на режим изменяемой привязки. Это яснее, чем неявное разделение состояния:
   намерение выражается синтаксисом явно, а не скрывается в поведении во время выполнения.

### 3.10 Оператор spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn-блок**: явное объявление параллельной области, выражения внутри блока выполняются
параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn-цикл**: цикл с параллелизмом по данным.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn-блок захватывает переменные внешней области видимости** (RFC-024 §2.3, семантика захвата
значения):

- Ссылка тела блока на переменную внешней области = **захват значения Move**: значение снимается в
  замыкание в точке создания spawn, тело блока читает через env (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешняя переменная не затрагивается
- **Типы-дескрипторы** (Struct/String/List и т.д.) — снимок = копия дескриптора, разделяет
  нижележащий объект; во встроенном runtime (по умолчанию) один поток — одна куча, дескриптор
  валиден
- Для разделения между несколькими задачами требуется явный `ref` (§2.13, компилятор автоматически
  выбирает Rc/Arc)
- `return` в блоке также захватывает внешние переменные, на которые ссылается

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 захватываются по значению, result == 6
}
```

### 3.11 Точка входа программы и операторы верхнего уровня

Исходный файл с точки зрения компилятора играет две роли, **определяемые наличием `yaoxiang.toml`**:

| Роль       | Определение                                         | Тело программы                                                                          |
| ---------- | --------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Script** | Один файл запускается напрямую, без `yaoxiang.toml` | **Операторы верхнего уровня** (выполняются в порядке записи); `main` — обычная привязка |
| **Bin**    | Существует `yaoxiang.toml`                          | **функция `main`**; исполняемые операторы на верхнем уровне запрещены                   |

#### Script: операторы верхнего уровня — это программа

Без manifest файл является «скриптом», **операторы верхнего уровня выполняются в порядке записи**:

```yaoxiang
use std.io
io.println("hello")          // непосредственное выполнение
x: Int = { 42 }              // привязка верхнего уровня: инициализация в runtime
io.println(x)                // 42
```

`main` в этом режиме **не особенный** — это просто обычная привязка. Чтобы `main` запустился, нужно
явно его вызвать:

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← эта строка обязательна
```

> **Почему `main` не вызывается автоматически?** Операторы верхнего уровня уже являются телом
> программы. Если ещё и неявно вызывать `main`, скрипт с явно написанным `main()` выполнился бы
> дважды. Два правила не могут сосуществовать, поэтому в Script существует только «операторы
> верхнего уровня» как единственная точка входа.

#### Bin: `main` — точка входа

При наличии manifest файл является «исполняемой целью», в этом случае:

- Должна быть определена `main`, и она должна быть функцией (сигнатура должна позволять вызов без
  аргументов)
- Исполняемые операторы на верхнем уровне запрещены — тело программы и есть `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не-функция — обе ошибки компиляции (первая: без `main` все функции
недостижимы; вторая: привязка значения не будет вызвана).

> **Файлы библиотек**: файлы, которые подключаются через `use` из других файлов, или файлы, на
> которые указывают `[lib].path` / `[exports]`, не требуют `main` — они не являются точками входа в
> программу.

#### Инициализация привязок верхнего уровня

Значения инициализации привязок верхнего уровня **вычисляются в runtime**, не требуя констант
времени компиляции:

```yaoxiang
answer: Int = { 42 }              // значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // вызов функции
```

Инициализация выполняется в **порядке зависимостей**, вне зависимости от порядка записи:

```yaoxiang
derived: Int = base * 3           // ссылается на base, объявленный ниже
base: Int = 7                     // инициализируется первым (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (будет выведен список имён в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель ролей файла), приложение D RFC-010a (правила привязки
> блоков).
