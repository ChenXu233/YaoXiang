# Спецификация синтаксиса

Данный документ определяет спецификацию синтаксиса языка программирования YaoXiang, включая
лексическую структуру, правила грамматики и приоритет операторов.

---

## Глава 1: Лексическая структура

### 1.1 Исходный файл

Исходные файлы YaoXiang должны использовать кодировку UTF-8. Исходные файлы обычно имеют расширение
`.yx`.

### 1.2 Классификация лексических единиц

| Категория      | Описание                                       | Примеры                   |
| -------------- | ---------------------------------------------- | ------------------------- |
| Идентификатор  | Начинается с буквы или подчёркивания           | `x`, `_private`, `my_var` |
| Ключевое слово | Предопределённые зарезервированные слова языка | `Type`, `pub`, `use`      |
| Литерал        | Фиксированное значение                         | `42`, `"hello"`, `true`   |
| Оператор       | Символ операции                                | `+`, `-`, `*`, `/`        |
| Разделитель    | Синтаксический разделитель                     | `(`, `)`, `{`, `}`, `,`   |

### 1.3 Ключевые слова

YaoXiang определяет минимальный набор ключевых слов:

```
pub    use    spawn
ref    mut    if     else
else   match  while  for    return
break  continue as     in     unsafe
```

Эти ключевые слова имеют специальное значение в любом контексте и не могут использоваться как
идентификаторы.

### 1.4 Зарезервированные слова

«Зарезервированные слова» YaoXiang разделены на три уровня, которые распознаются парсером (parser) и
проверкой типов (type checker) на разных этапах:

#### 1.4.1 Литеральные зарезервированные слова

Идентификаторы литералов, имеющие отдельный токен в парсере и не могущие использоваться как обычные
идентификаторы:

| Идентификатор | Принадлежность к типу | Описание                                                                                                    |
| ------------- | --------------------- | ----------------------------------------------------------------------------------------------------------- |
| `Type`        | —                     | Ключевое слово метатипа                                                                                     |
| `true`        | Bool                  | Логическое значение «истина»                                                                                |
| `false`       | Bool                  | Логическое значение «ложь»                                                                                  |
| `void`        | Void                  | Литерал Void (значение Unit). Строчная `void` — литерал значения; заглавная `Void` — имя типа (см. §1.4.3). |

#### 1.4.2 Конструкторы выражений

Следующие конструкторы распознаются парсером в контекстах сопоставления с образцом и выражений:

| Конструктор | Принадлежность к типу | Описание                             |
| ----------- | --------------------- | ------------------------------------ |
| `some(T)`   | Option                | Конструктор варианта значения Option |
| `ok(T)`     | Result                | Успешный вариант Result              |
| `err(E)`    | Result                | Вариант ошибки Result                |

#### 1.4.3 Встроенные имена типов

Следующие имена типов предварительно зарегистрированы проверкой типов и могут использоваться в
позиции типа без импорта. Парсер рассматривает их как обычные идентификаторы — **это не
зарезервированные слова, они могут быть затенены локальными привязками (не рекомендуется)**.

| Имя типа | Логическое соответствие | Описание                                                                                                                                              |
| -------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Void`   | ⊤ (истина/Unit)         | Тип-произведение с нулём полей, ровно один обитатель (литерал `void`, см. §1.4.1)                                                                     |
| `Never`  | ⊥ (ложь/пустой тип)     | Тип с нулём вариантов, ноль обитателей. Никакое выражение не может породить значение `Never`. `Never <: T` выполняется для всех `T` (принцип взрыва). |
| `Int`    | —                       | Знаковое целое число                                                                                                                                  |
| `Float`  | —                       | Число с плавающей точкой                                                                                                                              |
| `Bool`   | —                       | Логическое значение: `true` / `false`                                                                                                                 |
| `Char`   | —                       | Символ Unicode                                                                                                                                        |
| `String` | —                       | Строка                                                                                                                                                |

### 1.5 Идентификаторы

Идентификаторы начинаются с буквы или подчёркивания, последующие символы могут быть буквами, цифрами
или подчёркиваниями. Идентификаторы чувствительны к регистру.

Специальные идентификаторы:

- `_` используется как заглушка, обозначающая игнорируемое значение
- Идентификаторы, начинающиеся с подчёркивания, обозначают закрытые члены

### 1.6 Литералы

#### 1.6.1 Целые числа

```
Decimal     ::= [0-9][0-9_]*
Octal       ::= 0o[0-7][0-7_]*
Hex         ::= 0x[0-9a-fA-F][0-9a-fA-F_]*
Binary      ::= 0b[01][01_]*
```

#### 1.6.2 Числа с плавающей точкой

```
Float       ::= [0-9][0-9_]* '.' [0-9][0-9_]* ([eE][+-]?[0-9][0-9_]*)?
```

#### 1.6.3 Строки

```
String      ::= '"' ([^"\\] | EscapeSequence)* '"'
Escape      ::= '\\' ([nrt'"\\] | UnicodeEscape)
Unicode     ::= 'u' '{' HexDigit+ '}'
```

#### 1.6.4 Коллекции

```
List        ::= '[' Expr (',' Expr)* ']'
Dict        ::= '{' String ':' Expr (',' String ':' Expr)* '}'
Array       ::= '[' Expr (',' Expr)* ']'   // при аннотации целевого типа как Array(T, N) литерал становится массивом фиксированной длины
```

> **Литерал словаря должен содержать хотя бы одну пару ключ-значение**: `{}` **не является** пустым
> словарём — это пустой блок (значение `Void`, см. [§2.9](#_2-9-блок-выражение)). Для пустого
> словаря используйте конструктор `dict.new()`:
>
> ```yaoxiang
> empty = dict.new()                  // ✅ пустой словарь
> d = { "a": 1 }                       // ✅ литерал словаря
> wrong = {}                           // ❌ это не словарь, а пустой блок (Void)
> ```
>
> **Критерий — содержимое**: грамматика `Dict` требует хотя бы одну пару `String ':' Expr`, в `{}`
> содержимого нет, поэтому используется нулевая форма блочной структуры. Непустая форма
> самоописывается содержимым (`{ "k": v }` имеет пары ключ-значение → словарь) — это родственно
> тому, что `f = { 5 }` является значением `Int`, а не функцией: **тип определяется содержимым**.

> У Set нет грамматики литерала и нет представления в runtime — при планировании типа коллекции, при
> появлении требований будет дополнен по модели Dict (std.set + HeapValue::Set). Точка приземления
> литералов List/Dict определяется аннотацией контекстного типа: голый литерал и аннотация `List(T)`
> приземляются в расширяемый список; аннотация `Array(T, N)` действующая непосредственно на литерал,
> приземляет в массив фиксированной длины. Запрещено неявное преобразование List→Array.
>
> Семантика литерала Array:
>
> - Количество элементов должно равняться N, иначе ошибка компиляции E1002; пустой литерал с
>   ненулевым N также отвергается
> - Тип каждого элемента должен быть совместим с T, иначе ошибка компиляции E1002
> - Грамматическая форма N: только целочисленный литерал (может быть отрицательным) или имя
>   константы; составные выражения (например, `2+1`) отвергаются на этапе разбора
> - Когда N является символьной константой (const-параметр функции, например `Array(Int, n)`),
>   проверка количества откладывается до фазы уточнения типов
> - Вложенные литералы массивов v1 (`Array(Array(Int,2),2) = [[1,2],[3,4]]`) отвергаются на этапе
>   компиляции, требуется явное послойное конструирование; рекурсивная точка приземления будет
>   рассмотрена в последующих версиях

#### 1.6.5 Генераторы списков

```
ListComp    ::= '[' Expr 'for' Identifier 'in' Expr (',' Expr)* ('if' Expr)? ']'
```

> **Ужесточение поведения (запись миграции)**: грамматика переменной итерации и так была
> `'for' Identifier 'in'`, но в старой реализации pattern проходил полный pratt-разбор — после
> регистрации `'in'` как инфиксного оператора `x` поглощал бы `in items` как выражение членства.
> После исправления pattern, не являющийся идентификатором, сразу даёт сбой разбора, без запасного
> варианта к `_` (тихого поглощения ошибки), как в старой реализации. Сфера влияния: ранее
> разбиравшаяся запись `[x for (a, b) in pairs]` теперь выдаёт ошибку — у этой формы никогда не было
> определённого поведения (переменная всегда была `_`), ужесточение направлено правильно, без затрат
> на семантическую миграцию.

#### 1.6.6 Проверка членства

```
Membership  ::= Expr 'in' Expr
```

> `in` — бинарный оператор отношения, возвращающий `Bool` — `true` при попадании, `false` при
> непопадании, без ошибки. Семантическое разделение: `[]` — это утверждение существования и
> извлечение значения (ошибка при неудаче), `in` — это запрос о существовании (непопадание —
> нормальный `false`). Правый операнд покрывает: List / Array / Dict (множество ключей) / Tuple /
> String (подстрока) / Range (интервал). `in` — это предикат первого класса, на этапе уточнения
> типов служит базой для доказуемых утверждений времени компиляции. (Set исключён из списка правых
> операндов — у Set нет представления в runtime, см. §1.6.4)

## Глава 2: Правила грамматики

### 2.1 Классификация выражений

```

              | Identifier
              | FnCall
              | MemberAccess
              | IndexAccess
              | UnaryOp
              | BinaryOp
              | TypeCast
              | RangeExpr
              | ErrorPropagate
              | RefExpr
              | IfExpr
              | MatchExpr
              | Block
              | Lambda
```

### 2.2 Приоритет операторов

| Приоритет | Операторы                   | Ассоциативность |
| --------- | --------------------------- | --------------- |
| 1         | `()` `[]` `.` `?`           | Слева направо   |
| 2         | `as`                        | Слева направо   |
| 3         | Унарный префикс `!` `-` `+` | Справа налево   |
| 4         | `*` `/` `%`                 | Слева направо   |
| 5         | `+` `-`                     | Слева направо   |
| 6         | `..`                        | Слева направо   |
| 7         | `<<` `>>`                   | Слева направо   |
| 8         | `&` `\|` `^`                | Слева направо   |
| 9         | `==` `!=` `<` `>` `<=` `>=` | Слева направо   |
| 10        | `and` `or`                  | Слева направо   |
| 11        | `if...else`                 | Справа налево   |
| 12        | `=` `+=` `-=` `*=` `/=`     | Справа налево   |

> **Унарные префиксные операторы** (`!` `-` `+`) имеют плотное связывание: только ниже вызова и
> доступа к члену, выше всех бинарных операторов. Поэтому `!a == b` ≡ `(!a) == b` (семантика в стиле
> Zig); `!` — чисто унарная операция, не участвует в потоке управления с коротким замыканием,
> ортогональна ключевым словам `and`/`or` (короткое замыкание) (авторитетное определение RFC-010).

> **Сила связывания Range**: `..` имеет силу связывания (6, 7) — левая 6 ниже сложения (7), правая 7
> поглощает сложение, но не поглощает `..` того же уровня. Сравнение до и после изменения:
>
> | Выражение    | До изменения (уровень 1, прав. ассоц.)                                                                     | После изменения ((6,7), лев. ассоц.)                                          |
> | ------------ | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
> | `x in 1..10` | `x in 1..10` (`in` — правый операнд уровня 4, `..` уровня 1 не может поглотить, фактически не разбирается) | `x in (1..10)` — интервал целиком как правый операнд `in`                     |
> | `0..n+2`     | `(0..n)+2` (ловушка правой ассоциативности: верхняя граница съедается, цикл `for` сразу E3004)             | `0..(n+2)` — верхняя граница — арифметическое выражение                       |
> | `a == b..c`  | `a == (b..c)` (`..` уровня 1 < `==` уровня 3, естественно целиком)                                         | `a == (b..c)` — **семантика не меняется**, `..` всё ещё выше уровня сравнения |
> | `1..2*3`     | `(1..2)*3`                                                                                                 | `1..(2*3)` — верхняя граница — арифметическое выражение                       |
> | `a..b..c`    | `a..(b..c)` (правоассоц. цепочка, бессмысленный Range в Range)                                             | `(a..b)..c` — **форма step** (`c` — шаг)                                      |
>
> Чистый эффект: составная верхняя граница `for i in 0..n+2` из «успешный разбор, но E3004»
> становится «сразу доступной»; `x in 1..10` из «не разбирается» становится «проверкой интервала»;
> `a..b..c` из «бессмысленная вложенность» становится «компонентом step». Уровень 6 находится между
> `+` (уровень 5) и `<<` (уровень 7), математическая конвенция: интервал — плотно связываемая
> конструкция, верхняя граница естественно является полным арифметическим выражением.

### 2.9 Блочное выражение

```
Block       ::= '{' Stmt* Expr? '}'
```

> **Правила завершения операторов**: разделение между Stmt и поведение перевода строки (`;` как
> явный разделитель, завершение переводом строки, исключения для продолжения строки, начало строки
> `(`/`[` никогда не объединяется) определяются
> [RFC-038](../design/rfc/draft/038-statement-termination.md).

#### 2.9.1 Три формы `{`

`{` в позиции выражения имеет ровно три интерпретации, определяемые однократно по **содержимому**:

| Форма               | Запись            | Тип                      | Пример           |
| ------------------- | ----------------- | ------------------------ | ---------------- |
| **Пустой блок**     | `{}`              | `Void`                   | `x: Void = {}`   |
| **Литерал словаря** | `{ "k": v, ... }` | `Dict(K, V)`             | `d = { "a": 1 }` |
| **Блок**            | `{ Stmt* Expr? }` | Тип хвостового выражения | `y = { 1 + 1 }`  |

**Порядок определения**:

1. `{}` (без содержимого) → **пустой блок**, значение `Void`
2. Первый элемент — пара `String ':' Expr` → **литерал словаря**
3. Иное → **блок**, значение определяется хвостовым выражением

> **Почему `{}` не является пустым словарём**: «пустота» пустого словаря не самоописывается (это
> может быть как `Dict(K, V)`, так и пустой блок), а грамматика словаря [§1.6.4](#_1-6-4-коллекции)
> требует хотя бы одну пару ключ-значение. При отсутствии содержимого берётся нулевая форма блочной
> структуры: это согласуется с `unsafe {}` / `spawn {}`, без введения особых случаев. Для пустого
> словаря используйте `dict.new()`.
>
> **Почему функциям нужна аннотация**: `f = { stmt }` — это **значение** (тип хвостового выражения),
> а не функция. Чтобы определить функцию, нужно явно указать аннотацию Fn: `f: () -> Int = { 5 }`.
> Это тот же принцип, что и для словаря: **тип определяется содержимым**, а не наличием или
> отсутствием аннотации. (Это правило см. в
> [RFC-010a](./design/rfc/accepted/010a-tail-expression-and-return.md), приложение D.)

**Единая семантика**: значение всех блоков `{}` определяется **хвостовым выражением**, `return` —
нелокальный выход типа `Never`.

| Тип блока    | Выход значения      | Пустой блок `{}` |
| ------------ | ------------------- | ---------------- |
| Обычный `{}` | Хвостовое выражение | `Void`           |
| `unsafe {}`  | Хвостовое выражение | `Void`           |
| `spawn {}`   | Хвостовое выражение | `Void`           |

**Ключевые принципы** (подробности см. в
[RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md)):

- **Значение блока = хвостовое выражение** (последнее выражение), единственный выход, без исключений
- Если последний элемент — **оператор присваивания**, значение блока `Void`; если нужно `Void`,
  пишите `Void` явно
- **`return` выходит за ближайшую границу функции** (проходит сквозь все блоки, не «возвращается в
  блок»), тип `Never`; `Never <: T` выполняется для любого типа (принцип взрыва), поэтому может
  появляться в любой позиции возвращаемого типа
- Форма выражения `= expr` непосредственно даёт значение

```yaoxiang
// Обычный блок {}: значение задаётся хвостовым выражением
result = {
    x = compute()
    x                // значение блока
}

// Блок unsafe {}: хвостовое выражение даёт определение типа
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void
    }
    SqliteDb         // значение блока
}

// Блок spawn {}: хвостовое выражение даёт результат
(a, b) = spawn {
    result1 = fetch("url1"),
    result2 = fetch("url2")
    (result1, result2)   // значение блока
}

// return: проходит сквозь блок, выходит из функции
f: (n: Int) -> Int = {
    if n < 0 {
        return 0     // выходит из if и тела функции, завершает функцию
    }
    n * 2            // хвостовое выражение
}
```

#### `name = { ... }` — функция или значение блока?

`name = { ... }` может быть как определением функции (RFC-007 «простейшая форма без параметров»),
так и привязкой значения блока. Решение принимается по принципу **аннотация имеет приоритет, по
умолчанию функция** (RFC-010a, приложение D):

| Случай                           | Результат          | Пример                             |
| -------------------------------- | ------------------ | ---------------------------------- |
| Значение — Lambda (`=>`)         | Функция            | `f = () => 5` → `f()` = 5          |
| Аннотация — функциональный тип   | Функция            | `f: () -> Int = { 5 }` → `f()` = 5 |
| Аннотация — нефункциональный тип | **Значение блока** | `x: Int = { 5 }` → `x` = 5         |
| Без аннотации                    | Функция            | `f = { 5 }` → `f()` = 5            |

**Аннотация есть тип**: `x: Int = ...` объявляет `x` как `Int`, значит `{ ... }` вычисляется в
`Int`; `f: () -> Int = ...` объявляет `f` как функцию, значит `{ ... }` — тело функции.

Чтобы `{ ... }` вычислялся немедленно, **просто напишите целевой тип** (новый синтаксис не нужен):

```yaoxiang
// Значение блока: немедленное вычисление
x: Int = {
    y = 5
    y            // x = 5
}

// Функция: по умолчанию без аннотации
f = { 5 }        // f() = 5
```

#### Вложенные функциональные типы: каррирование или возврат функции?

Вложенный функциональный тип справа от `->` имеет два прочтения, различаемых **скобками** (RFC-004):

| Запись                          | Значение            | Вызов                     |
| ------------------------------- | ------------------- | ------------------------- |
| `(a: Int) -> (b: Int) -> Int`   | **Каррирование**    | `f(1)(2)`                 |
| `(a: Int) -> ((b: Int) -> Int)` | **Возврат функции** | `g(1)` возвращает функцию |

Основание: **аннотация есть тип**. `g: (a: Int) -> ((b: Int) -> Int)` объявляет, что
`g(1) : (b: Int) -> Int`, поэтому `g(1)` **должна быть** той функцией, а не «следующей порцией
аргументов».

```yaoxiang
// Каррирование: две порции аргументов подаются послойно
add: (a: Int) -> (b: Int) -> Int = { a + b }
add(1)(2)        // → 3

// Возврат функции: внешний уровень — одна порция аргументов, возвращается функция
adder: (n: Int) -> ((x: Int) -> Int) = (x) => x + n
adder(10)(5)     // → 15
h = adder(10)    // возвращённую функцию можно сохранить в переменную, передать
```

Нескобочный вложенный `Fn` всегда является каррированием (включая форму с параметрами типа из
RFC-011):

```yaoxiang
identity: (T: Type) -> (x: T) -> T = (x) => x   // каррирование
identity(5)      // → 5
```

**Проверка типов**: скобки объявляют тип возврата, тело должно порождать этот тип.
`f: () -> (() -> Int) = { 7 }` — ошибка — ожидается `() -> Int`, фактически получено `Int` (E1002).

            |  '(' ParamList? ')' '=>' Block
```

### 2.11 Оператор распространения ошибки

```
ErrorPropagate ::= Expr '?'
```

Оператор `?` — постфиксный, с приоритетом на уровне `.`. Для типа `Result(T, E)`:

- При `Ok(v)` извлекает значение `v` и продолжает выполнение
- При `Err(e)` распространяет ошибку вверх (`return Err(e)`)

```yaoxiang
process: (data: Data) -> Result(Data, Error) = {
    validated = validate(data)?     // при успехе извлекает значение, при неудаче распространяет
    transform(validated)
}
```

### 2.12 Выражение диапазона

```
RangeExpr   ::= Expr '..' Expr ('..' Expr)?
```

`..` создаёт значение диапазона (Range — значение первого класса, не синтаксический сахар).

```yaoxiang
for i in 0..10 { print(i) }
slice = array[0..5]

// Range — это значение: можно связывать, передавать, проверять членство
r = 1..10
assert.assert(5 in r, "membership")
for i in r { print(i) }

// Форма step (третий компонент, по умолчанию 1)
for i in 0..10..2 { print(i) }  // 0, 2, 4, 6, 8
for i in 10..0..(-2) { print(i) }  // 10, 8, 6, 4, 2
```

> **Семантика step**: в `a..b..c` `c` — это шаг. Литерал `c = 0` отвергается на этапе компиляции;
> динамический `c` проверяется в runtime (семейство E6001; после внедрения системы ошибок будет
> повышен до Result). `c < 0` допустим, направление интервала меняется в зависимости от знака
> (`10..0..(-2)` — убывающий).

### 2.13 ref-выражение

```
RefExpr     ::= 'ref' Expr
```

`ref` создаёт разделяемое владение. Компилятор автоматически выбирает Rc (одна задача) или Arc
(между задачами), пользователю не нужно беспокоиться о деталях реализации.

```yaoxiang
data = ref heavy_data
spawn { use(data) }   // между задачами: компилятор автоматически выберет Arc
```

### 2.14 unsafe-выражение

```
UnsafeExpr  ::= 'unsafe' Block
```

Блок `unsafe` используется для определения непрозрачных типов и работы с сырыми указателями.
Используйте `return`, чтобы вернуть определение типа во внешнюю область видимости.

**Семантика**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует полномочий unsafe

```yaoxiang
// Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  // сырой указатель
    }
    return SqliteDb
}

// SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")
```

### 2.15 Область видимости

**Основные правила**:

- Каждый блок `{}` создаёт область видимости
- Внутренняя область видимости может обращаться к переменным внешней области видимости
- Внешняя область видимости не может обращаться к переменным внутренней области видимости
- Объявление переменных следует принципу «приоритет присваивания»

```yaoxiang
// Область видимости блока
{
    x = 10
    // x виден в этой области видимости
}
// x не виден за пределами этой области видимости

// Область видимости функции
add: (a: Int, b: Int) -> Int = {
    result = a + b
    return result
}
// result не виден за пределами функции
```

**Объявление и затенение переменных**:

- `x = value`: поиск `x` идёт по цепочке областей видимости наружу; если найдено — присваивание,
  иначе — новое объявление
- `mut x = value`: явное новое объявление изменяемой переменной, запрещено совпадение имён с внешней
  областью
- В одной области видимости любое имя может быть объявлено только один раз

> **Подробное определение**: полные правила области видимости, объявления и затенения переменных см.
> в [Спецификации системы модулей](./modules.md#глава-4-область-видимости).

### 3.3 Оператор return

```
ReturnStmt  ::= 'return' Expr?
```

**Семантика**: `return` — это **нелокальный выход**, выходящий за ближайшую **границу функции**
(проходит сквозь все блоки — включая `if` / `while` / `for` / `match` / голые блоки / `spawn` /
`unsafe`), передавая значение вызывающему. Он **не «возвращается в блок»**.

**Тип**: `return e : Never` (при `e : T`). `Never <: T'` выполняется для любого `T'` (принцип
взрыва, см. [Система типов §2.2](./type-system.md)), поэтому `return` может появляться в любой
позиции возвращаемого типа без дополнительных правил.

**Связь с вычислением блока**: значение блока всегда равно **хвостовому выражению** (см. §2.9).
`{ return n }` как блок имеет значение `n`, тип `Never`; одновременно `return` действует как выход
из функции. **Оба факта верны одновременно**, и сосуществуют благодаря принципу взрыва.

`return` вместе с хвостовым выражением обеспечивают «досрочный возврат» без специальных правил о
`return` для функций — см. [RFC-010a](../design/rfc/accepted/010a-tail-expression-and-return.md).

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 {
        return 1          // выходит из if и функции (тип Never)
    }
    n * factorial(n - 1)  // хвостовое выражение = значение блока
}
```

### 3.4 Оператор break

```
BreakStmt   ::= 'break'
```

**Семантика**: немедленно завершает текущий самый внутренний цикл `while`/`for`, поток управления
переходит после тела цикла.

- **Только выход из ближайшего уровня**: `break` всегда действует на самый внутренний цикл,
  содержащий его. В случае вложенных циклов, когда нужно выйти сразу из нескольких уровней, вынесите
  внутренний цикл в функцию и используйте `return`, либо используйте флаг (break/continue без меток;
  если в будущем будут введены метки циклов, они пойдут по RFC-процедуре в синтаксисе объявления
  цикла, наряду с многоуровневым выходом в конвейере доказательств)
- **Только внутри цикла**: `break` может появляться только в теле цикла `while`/`for` (включая
  вложенные блоки/if/match), появление вне цикла — ошибка компиляции (E1102
  `'break' outside of a loop`)
- **Не влияет на доказательство завершимости**: цикл `while` по-прежнему должен быть доказуемо
  завершающимся (метрика decreases); `break` не участвует в аргументации завершимости,
  `while true { break }` не будет принят
- **Семантика заимствования**: ребро потока управления break участвует в структурном разрыве
  обратного BFS-анализа живости RFC-009a (выпрыгнувшие итерации не участвуют в выводе живости
  обратных рёбер)

```yaoxiang
mut i = 0
while i < 10 {
    i = i + 1
    if i == 3 {
        break              // поток управления переходит после цикла, i == 3
    }
}

// Вложенные циклы: break выходит только из внутреннего
while j < 3 {
    while k < 10 {
        if k == 2 { break }    // завершает только внутренний цикл
    }
    j = j + 1                  // каждая итерация внешнего цикла доходит сюда
}
```

### 3.5 Оператор continue

```
ContinueStmt::= 'continue'
```

**Семантика**: пропускает оставшиеся операторы текущей итерации и сразу переходит к следующей
итерации самого внутреннего цикла — `while` возвращается к переоценке условия, `for` берёт следующий
элемент.

- **Действует только на ближайший уровень**: аналогично `break`, без меток
- **Только внутри цикла**: появление вне цикла — ошибка компиляции (E1102)

```yaoxiang
mut sum = 0
mut n = 0
while n < 5 {
    n = n + 1
    if n == 3 {
        continue           // пропускает следующее накопление, n == 3 не учитывается
    }
    sum = sum + n
}
// sum == 12 (1 + 2 + 4 + 5)
```

### 3.9 Оператор for

```
ForStmt     ::= 'for' 'mut'? Identifier 'in' Expr Block
```

#### 3.9.1 Семантика: каждая итерация — новая привязка значения

Семантика цикла for в YaoXiang отличается от традиционных языков: **каждая итерация — это новая
привязка значения, а не изменение одной и той же переменной**.

```yaoxiang
// Пример: for i in 1..5
for i in 1..5 {
    print(i)
}
```

**Процесс выполнения**:

| Итерация | Поведение переменной цикла                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------- |
| 1-я      | Создаётся новая привязка `i = 1`, выполняется тело цикла, печатается 1                                  |
| 2-я      | Создаётся новая привязка `i = 2` (предыдущая привязка уничтожена), выполняется тело цикла, печатается 2 |
| 3-я      | Создаётся новая привязка `i = 3`, выполняется тело цикла, печатается 3                                  |
| 4-я      | Создаётся новая привязка `i = 4`, выполняется тело цикла, печатается 4                                  |
| Конец    | Тело цикла завершается, привязка уничтожается                                                           |

**Ключевой момент**: после каждой итерации созданная в этой итерации привязка уничтожается.
Следующая итерация — это совершенно новая привязка, никак не связанная с привязкой предыдущей
итерации.

#### 3.9.2 Различие между for и for mut

| Синтаксис           | Изменяемость переменной цикла | Описание                              |
| ------------------- | ----------------------------- | ------------------------------------- |
| `for i in 1..5`     | Неизменяемая                  | В теле цикла нельзя изменить привязку |
| `for mut i in 1..5` | Изменяемая                    | В теле цикла можно изменить привязку  |

```yaoxiang
// Допустимо: каждая итерация привязывает новое значение, изменение не нужно
for i in 1..5 {
    print(i)  // чтение значения i
}

// Ошибка: неизменяемая привязка, нельзя изменить
for i in 1..5 {
    i = i + 1  // ошибка: нельзя изменить неизменяемую привязку
}

// Допустимо: использование for mut разрешает изменение привязки
for mut i in 1..5 {
    i = i + 1  // изменение разрешено
}
```

#### 3.9.3 Проверка затенения

YaoXiang запрещает затенение переменных. Переменная цикла for не может иметь то же имя, что и
переменная во внешней области видимости:

```yaoxiang
// Ошибка: i уже объявлен во внешней области видимости
i = 10
for i in 1..5 {
    print(i)
}

// Корректно: использование разных имён переменных
i = 10
for j in 1..5 {
    print(j)
}
```

Это правило применяется ко всем блокам кода, подробности см. в
[4.3 Правила затенения](./modules.md#43-правила-затенения).

#### 3.9.4 Сравнение с другими языками

| Язык     | Семантика переменной цикла for                                   |
| -------- | ---------------------------------------------------------------- |
| YaoXiang | Каждая итерация привязывает новое значение                       |
| Rust     | Изменение одной и той же переменной (нужен mut)                  |
| Python   | Изменение одной и той же переменной (без mut)                    |
| C/C++    | Изменение одной и той же переменной (нужен указатель или ссылка) |

**Обоснование дизайна**: YaoXiang использует семантику привязки по следующим причинам:

1. **Более естественная семантика** В естественном языке «для каждого элемента x из коллекции»
   означает, что каждый x — независимая сущность. YaoXiang-овское `for i in 1..5` читается как «для
   каждого i от 1 до 5», и i в каждой итерации — совершенно новая привязка, что согласуется с
   интуитивным человеческим пониманием.

2. **Предотвращение случайных изменений** Семантика неизменяемой привязки по умолчанию означает, что
   в теле цикла нельзя случайно изменить переменную цикла. Не нужно беспокоиться о том, что где-то в
   сложном теле цикла случайно написано `i = ...`, что приводит к трудно отслеживаемым багам.

3. **Высокопроизводительное решение всегда доступно** Когда действительно нужно повторно
   использовать переменную между итерациями (например, аккумулятор, кэш), используйте `for mut` для
   переключения в режим изменяемой привязки. Это яснее, чем неявное разделяемое состояние —
   намерение выражается явно через синтаксис, а не прячется в поведении времени выполнения.

### 3.10 Оператор spawn

```
SpawnBlock  ::= '(' Pattern (',' Pattern)* ')' '=' 'spawn' '{' Expr (',' Expr)* '}'
SpawnFor    ::= Identifier '=' 'spawn' 'for' 'mut'? Identifier 'in' Expr '{' Expr '}'
SpawnStmt   ::= SpawnBlock | SpawnFor
```

**spawn-блок**: явное объявление параллельной области, выражения внутри блока выполняются
параллельно.

```yaoxiang
(result_a, result_b) = spawn {
    parse(fetch("url1")),
    parse(fetch("url2"))
}
```

**spawn-цикл**: цикл с параллелизмом по данным.

```yaoxiang
results = spawn for item in items {
    process(item)
}
```

**spawn-блок захватывает переменные внешней области** (RFC-024 §2.3, семантика захвата по значению):

- Ссылка тела блока на внешнюю переменную = **Захват значения (Move)**: значение снапшотится в
  замыкание в точке создания spawn, тело блока читает его через env (LoadUpvalue)
- **Примитивы** (Int/Float/Bool/Char) копируются по значению, внешняя переменная не затрагивается
- **Типы-дескрипторы** (Struct/String/List и т.д.) снапшот = копия дескриптора, общий базовый
  объект; в Embedded runtime (по умолчанию) один поток — одна куча, дескриптор валиден
- Для разделения между несколькими задачами необходим явный `ref` (§2.13, компилятор автоматически
  выберет Rc/Arc)
- Внешние переменные, на которые ссылается `return` в блоке, также захватываются

```yaoxiang
t1 = 1 + 1
t2 = 2 + 2
result = spawn {
    return t1 + t2    // t1/t2 захвачены по значению, result == 6
}
```

### 3.11 Точка входа и операторы верхнего уровня

Исходный файл с точки зрения компилятора имеет две роли, **определяемые наличием `yaoxiang.toml`**:

| Роль                 | Определение                                         | Основной код программы                                                                  |
| -------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Скрипт**           | Один файл запускается напрямую, без `yaoxiang.toml` | **Операторы верхнего уровня** (выполняются в порядке записи); `main` — обычная привязка |
| **Исполняемый файл** | Существует `yaoxiang.toml`                          | **Функция `main`**; исполняемые операторы на верхнем уровне запрещены                   |

#### Скрипт: операторы верхнего уровня и есть программа

Без manifest файл является «скриптом», **операторы верхнего уровня выполняются в порядке записи**:

```yaoxiang
use std.io
io.println("hello")          // выполняется напрямую
x: Int = { 42 }              // привязка верхнего уровня: инициализация во время выполнения
io.println(x)                // 42
```

`main` в этом режиме **ничем не выделен** — это просто обычная привязка. Чтобы `main` выполнился,
его нужно вызвать явно:

```yaoxiang
use std.io
main: () -> Void = { io.println("only runs if called") }

main()                       // ← эта строка обязательна
```

> **Почему `main` не вызывается автоматически?** Операторы верхнего уровня уже являются основным
> кодом программы. Если при этом неявно вызвать `main`, скрипт с явно написанным `main()` выполнится
> дважды. Эти два правила не могут сосуществовать, поэтому в режиме Скрипта существует только одна
> точка входа — «операторы верхнего уровня».

#### Исполняемый файл: `main` — это точка входа

При наличии manifest файл является «исполняемой целью», в этом случае:

- `main` должен быть определён и должен быть функцией (сигнатура должна допускать вызов с нулём
  аргументов)
- Исполняемые операторы на верхнем уровне запрещены — основной код программы это и есть `main`

```yaoxiang
main: () -> Void = {
    print("hello")
}
```

Отсутствие `main` или `main` не-функция — ошибка компиляции (первое: при отсутствии `main` все
функции недостижимы; второе: привязка значения не будет вызвана).

> **Файлы библиотек**: файлы, которые `use`-ятся другими файлами, или файлы, на которые указывает
> `[lib].path` / `[exports]`, не требуют `main` — они не являются точками входа.

#### Инициализация привязок верхнего уровня

Значение инициализации привязки верхнего уровня **вычисляется во время выполнения**, не требуется
быть константой времени компиляции:

```yaoxiang
answer: Int = { 42 }              // значение блока
inc: (Int) -> Int = (x) => x + 1
computed: Int = inc(41)           // вызов функции
```

Инициализация выполняется в **порядке зависимостей**, независимо от порядка записи:

```yaoxiang
derived: Int = base * 3           // ссылается на base, объявленный позже
base: Int = 7                     // инициализируется первым (топологическая сортировка)
```

Циклические зависимости — ошибка компиляции (будут перечислены имена в цикле):

```yaoxiang
a: Int = b + 1
b: Int = a + 1                    // ошибка: a → b → a
```

> **Обоснование дизайна**: RFC-029f (модель роли файла), RFC-010a приложение D (решение о привязке
> блока).
