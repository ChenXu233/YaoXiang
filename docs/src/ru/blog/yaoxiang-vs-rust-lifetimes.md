# Мы спрятали `'a` в компилятор

_— Честная заметка о модели владения YaoXiang_

---

Сколько времени вам потребовалось, чтобы по-настоящему понять этот код на Rust при первом взгляде?

```rust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn advance(&mut self) -> &'a str {
        let start = self.pos;
        self.pos += 1;
        &self.input[start..self.pos]
    }
}
```

Три `'a`. Одно на структуре, два в блоке `impl`. Они говорят одно и то же: `Parser` не может жить
дольше, чем `input`, который он заимствует. Это правильно. Безопасность Rust построена на этом
механизме.

Но когда мы пишем такой код, часто возникает мысль: **разве компилятор не может справиться с этим
сам?** Ответ Rust — «нет» — по крайней мере, без изменения модели заимствования.

**Эта статья не о том, что «YaoXiang решил эту проблему». Это о том, что «YaoXiang пробует другой
путь — спрятать `'a` в компилятор, чтобы компилятор писал его за вас. Как далеко мы продвинулись, и
какие сложные задачи остаются нерешёнными».**

---

## Почему Rust нуждается в `'a`

`&T` и `&mut T` в Rust — это указатели, указывающие на данные. Заимствование значения означает
создание ссылки на него. У этой ссылки есть собственное время жизни. Когда ссылка пересекает границу
функции (передаётся как возвращаемое значение, сохраняется в структуре), компилятор не может в
рамках одной функции определить, как долго ссылка проживёт — программист должен использовать `'a`,
чтобы предоставить информацию о том, что «это возвращаемое значение и этот параметр разделяют время
жизни».

Сообщество Rust не стояло на месте. Правила элизии времён жизни избавили большинство простых функций
от аннотаций. NLL, введённый в редакции 2018 года, освободил заимствования от пут лексической
области видимости. Но когда ссылки нужно сохранять в структурах, возвращать из функций, захватывать
замыканиями — **сама модель требует, чтобы программист аннотировал отношения между ссылками в этих
сценариях.**

---

## Другой угол зрения: заимствование — это не указатель, а токен

Ключевой дизайн YaoXiang записан в
[RFC-009 (Модель владения)](../design/rfc/accepted/009-ownership-model.md). Он не меняет семантику
по умолчанию (это Move), но меняет **онтологию заимствования**.

В YaoXiang `&T` и `&mut T` — **не указатели**. Это **нуль-размерные токены времени компиляции** —
доказательства прав доступа на уровне типов. Заимствование значения не создаёт указатель на него, а
создаёт «доказательство того, что мне разрешён доступ»:

```
&T     →  гарантирует, что данные иммутабельны. Реализует Dup (копируемый), несколько read-токенов могут сосуществовать безопасно
&mut T →  гарантирует исключительное право на изменение. Не реализует Dup (линейный), только один токен от одного источника
```

В Rust вы пишете `&` в точке вызова (`distance(&p1, &p2)`). В YaoXiang компилятор видит, что
сигнатура функции требует `&Point`, и автоматически создаёт токен в точке вызова — вызов
превращается в `distance(p1, p2)`. Цена в том, что определяющий должен объявить `&` в сигнатуре,
иначе Move по умолчанию съест владение:

```yaoxiang
# 签名中需要 &——编译器看到 &Point，调用时自动创建令牌
check_dimensions: (v: &Vec3) -> Bool = { ... }
check_bounds: (v: &Vec3) -> Bool = { ... }

v = Vec3(1.0, 2.0, 3.0)
if check_dimensions(v) and check_bounds(v) {  # 每次都自动创建 &Vec3 令牌
    # v 仍然可用
}
```

В Rust вы ставите `&` в точке вызова; в YaoXiang вы ставите `&` в точке определения. Аннотация не
исчезла — она переехала.

## Механизм брендов: `'a`, спрятанный в компиляторе

Пользователь никогда не соприкасается с этим — но без понимания этого нельзя понять, что именно
делает YaoXiang.

Компилятор внутри себя присваивает каждому токену заимствования уникальный идентификатор времени
компиляции:

```
用户看到的         编译器内部表示
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)
&mut Point     →  WriteToken(Point, #M)
```

Когда вы обращаетесь через `&Point` к полю и получаете `&Float`, последний несёт производный бренд:
`#N.field_x`. Когда `&mut`-токен перемещается (Move) в другую переменную, компилятор знает, что
исходная переменная его больше не держит — это базовая возможность семантики Move.

**`#N` — это и есть `'a`.** Отношение префикса — `#N` является префиксом для `#N.field_x` — это и
есть ограничение outlives. Та же информация. Программист на Rust пишет `'a`, компилятор YaoXiang
пишет `#N`.

Разница только в проценте успешного вывода. Правила элизии и NLL в Rust покрывают около 80%
сценариев. Ставка YaoXiang такова: **если дизайн языка даст компилятору более чистый вход, сможет ли
он покрыть больше?**

Эта ставка поддерживается несколькими языковыми ограничениями:

- **Запрет затенения переменных** — у `x` в этой области видимости одна идентичность, компилятору не
  нужно различать «о каком `x` вы говорите»
- **Явный `return`** — то, что выходит за пределы блока, явно прописано, компилятору не нужно
  выводить «является ли последняя строка возвращаемым значением»
- **`for` создаёт новое связывание на каждой итерации** — переменные в разных итерациях не мешают
  друг другу, компилятору не нужно отслеживать «что изменилось в прошлой итерации»

Эти правила — не «конвенции». В отличие от бессмысленного ритуала геттеров-сеттеров в Java, каждое
из них **превращает информацию, которую компилятор должен выводить, в информацию, уже записанную в
программе.** Компилятору не нужно гадать «какую переменную вы имеете в виду», «убежало ли это», «как
переменная цикла ведёт себя между итерациями» — ответы лежат в самом коде.

## Что может бренд — то же, что и Rust

Поскольку токен — это обычный тип, он подчиняется всем правилам для обычных типов. Нет специальных
запретов вроде «ссылки нельзя возвращать», «ссылки нельзя хранить в структурах», «замыкания не могут
захватывать ссылки». **Но и Rust делает то же самое — Rust всё это умеет.** Разница не в
возможностях, а в том, кто пишет аннотацию.

**Возврат ссылки — программист на Rust пишет `'a`, компилятор YaoXiang пишет `#N`:**

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)
}

p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()   # 令牌传播到调用方，编译器追踪品牌派生链
```

Rust делает то же самое, только программисту нужно написать `'a`, чтобы связать вход и выход. В
YaoXiang компилятор автоматически выводит через цепочки производных брендов — `px_ref`
(`#N.field_x`) выводится из `p` (`#N`). То же ограничение, другая запись.

**Структура хранит ссылку — без параметров времени жизни:**

```yaoxiang
Window: Type = {
    target: Point,
    view: &Point,   # 令牌字段，和其他字段没有区别
}
```

В Rust, когда структура имеет поля-ссылки, `'a` должен появиться в определении структуры и во всех
блоках `impl` — программист явно аннотирует ограничение времени жизни `Window<'a>`. В YaoXiang
`view: &Point` не пишет `'a`, но идентификатор бренда по-прежнему играет ту же роль внутри
компилятора — когда экземпляр `Window` уничтожается, внутренний токен умирает вместе с ним. Та же
гарантия, другая видимость.

**Захват замыканием — нуль-стоимостное копирование Dup-токена:**

```yaoxiang
filter_by_threshold: (items: List(Point), threshold: &Float) -> List(Point) = {
    items.filter(|p| p.x > threshold)   # threshold 令牌复制进闭包，零开销
}
```

`&Float` реализует Dup (копируемый), замыкание захватывает его так же, как захватывает
нуль-размерное целое. Тот же набор правил, что и автоматическое заимствование при вызове функций.
Ноль аннотаций от пользователя.

## Цена: аннотация исчезла из сигнатуры

Часто упоминаемая ценность `'a` в Rust — то, что он также является документацией.
`fn split_at_mut<'a>(slice: &'a mut [T], mid: usize) -> (&'a mut [T], &'a mut [T])` — `'a` говорит
читателю, что два возвращаемых среза ссылаются на одни и те же исходные данные.

В реальности сила этого аргумента ограничена — большинство новичков в Rust не читают `'a` как
документацию, а копируют его как заклинание, которое требует компилятор. Но, если быть честным: в
сложных сценариях заимствования `'a` в Rust хотя бы даёт отправную точку для отслеживания потока
данных. В YaoXiang вам нужно понимать цепочки вывода брендов — бренды невидимы для пользователя, это
зависит от инструментария, а инструментарий ещё не созрел.

## Обнаружение конфликтов токенов: тот же конвейер доказательств

В Rust есть отдельный «анализатор заимствований». **Дизайнерское направление** YaoXiang — объединить
конфликты заимствований в конвейер доказательств проверки типов
([RFC-027 (Предикаты времени компиляции и унифицированная статическая верификация)](../design/rfc/accepted/027-compile-time-evaluation-types.md)).

Конфликт токенов — это утверждение Хоара:

```
{ 冲突的 ReadToken 已死 } data.push(4) { WriteToken 安全获取 }
```

```yaoxiang
# &mut T 是线性类型——Move 后原变量不再持有
bad: (p: &mut Point) -> Void = {
    p2: &mut Point = p    # WriteToken 从 p 转移到 p2
    p.x = 10.0            # { p 持有 WriteToken } p.x = 10.0 { 安全 }
}                          # → p 的 WriteToken 已 Move → Disproved

# &T 是 Dup——可复制
good: (p: &Point) -> Void = {
    p2: &Point = p        # 复制只读令牌
    print(p.x)            # OK，两个只读令牌共存
}
```

Он разделяет один путь вывода ошибок с ошибками типов и непрохождением валидации предикатов. Вам не
нужно учить две диагностические системы. **Но цена:** сложный конфликт токенов в Rust порождает
тщательно сформулированную ошибку анализатора заимствований; в YaoXiang он может выглядеть как
«`WriteToken(#7.field_x)` conflicts with `WriteToken(#7)`» — технически точно, но идентификаторы
брендов не несут смысла для человеческого читателя. Интерпретируемость ошибок — область, которая ещё
не проверена.

## Ключевое слово `ref`: автоматический выбор Rc/Arc

Токены не могут пересекать границу задачи (между потоками) — это доказательства времени компиляции,
а не значения времени выполнения. Для совместного использования между областями видимости
используется `ref`:

```yaoxiang
shared_data = ref Point(1.0, 2.0)   # 编译器逃逸分析自动选 Rc 或 Arc

spawn {
    print(shared_data.x)   # 跨任务 → 编译器选 Arc
}
```

- Не убегает в spawn-блок → `Rc` (неатомарный подсчёт ссылок)
- Убегает в spawn-блок → `Arc` (атомарный подсчёт ссылок)

Цена: читая код, невозможно из локального контекста узнать, чем является `ref` — `Rc` или `Arc`.
Один рефакторинг (обёртывание кода в `spawn`) может молча изменить реализацию подсчёта ссылок — вы
не получите предупреждения от компилятора. Изменение производительности неявно.

## Главный вызов: RAII слишком груб

Ранее мы сказали, что токен — это значение, время жизни управляется через RAII. Но правило RAII для
обычных значений таково: **значение живёт до конца области видимости.** Это именно та проблема,
которая была у Rust до NLL — заимствование длится до конца блока, даже если вы давно его не
используете.

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_view: &Header = data.header()    # 从 &mut Data 派生 &Header
    header_info = parse_header(header_view) # ← header_view 的最后使用
    # header_view 没必要活到函数结束了——
    # 但 RAII 让它活到 }

    data.modify(header_info)   # ❌ ReadToken 还"活着"，WriteToken 被阻止
}
```

NLL в Rust анализирует последнее использование, а не лексическую область видимости. YaoXiang
нуждается в той же способности. Текущий план — также подключить анализ живости токенов к конвейеру
доказательств — три уровня:

1. **Быстрый путь** — переиспользование существующего `BorrowChecker` (линейное сканирование, на
   уровне IR-инструкций). Сценарии, где токен использован и освобождён в пределах одного базового
   блока, проходят напрямую
2. **Структурный анализ** — сопоставление префиксов в дереве брендов (определение того, кто с кем
   конфликтует) + DAG-запросы потребителей (определение того, находится ли последний потребитель
   токена после текущего узла)
3. **SMT-разрешение** — активируется только когда нужны логические рассуждения, например, для
   условий цикла

Инфраструктура конвейера доказательств (трёхзначный возврат `Proved`/`Disproved`/`Unproven`, бэкенд
Z3 SMT, стек предположений) частично реализована в `src/frontend/core/typecheck/proof/`. Слой
владения (`layers/ownership.rs`) всё ещё скелетный — он напрямую возвращает `Proved`, не выполняя
реальных проверок. Заполняется.

Текущее решение проблемы — вручную вкладывать блоки, чтобы сократить область видимости токена:

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_info = {
        header_view: &Header = data.header()
        parse_header(header_view)
    }   # header_view 随块结束释放
    data.modify(header_info)   # ✅
}
```

Это реальное трение. С ним столкнётся каждый, кто приходит из Rust. Можно ли его устранить — зависит
от того, насколько успешно конвейер удастся подключить к слою владения.

## Самый трудный вопрос: страховка

`'a` в Rust — не только бремя. Это также страховка. Когда компилятор не может вывести, программист
аннотирует отношение времён жизни, и компилятор верифицирует. **У вас есть ручка.**

Теоретическая страховка в YaoXiang должна быть **функцией-доказательством** (RFC-027 §4.2): когда
автоматический вывод компилятора терпит неудачу, программист пишет функцию, типом возврата которой
является само предложение «токены не конфликтуют», и компилятор верифицирует тип этой функции. Но —

Как должна выглядеть функция-доказательство «токены не конфликтуют»? Как пользователь конструирует
значение типа `WriteTokenAvailable`? Нужно ли ему понимать отношение префиксов между
идентификаторами брендов `#N` и `#N.field_x`?

**Если функция-доказательство требует от пользователя понимания идентификаторов брендов — мы просто
переписали `'a` под видом `#1`. Ничего не сэкономили.**

У этого вопроса пока нет ответа. Это самое вероятное место, где весь эксперимент может застрять.

## Девять итераций RFC-009

Этот дизайн не родился в башне из слоновой кости. RFC-009 прошёл через девять крупных версий:

| Версия | Ключевое изменение                                                                                                                                | Что было отвергнуто                                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| v1–v7  | Основано на модели владения Rust, с постепенным добавлением анализа потребления, обратных функций, мутабельности на уровне полей                  | Чрезмерная инженерия, сложность вышла из-под контроля                                |
| **v8** | «Урезанное заимствование» — `&T`/`&mut T` могут быть только параметрами, не могут возвращаться, храниться в структурах, захватываться замыканиями | Три жёстко закодированных запрета. Серьёзное ограничение выразительности             |
| **v9** | Система токенов заимствования — `&T`/`&mut T` — обычные типы, подчиняющиеся обычным правилам                                                      | Устранены специальные правила, но отслеживание брендов опустилось внутрь компилятора |

Скачок с v8 на v9 — настоящий прорыв: от трёх запретов к нулю специальных правил. Но v9 устранил
видимые пользователю правила, а не внутреннюю сложность системы — механизм брендов, отслеживание
вывода, обнаружение конфликтов от одного источника — всё это остаётся, просто переехало в
компилятор. Объединение проверки заимствований в конвейере доказательств — одно из направлений, но
сможет ли оно работать на реальном коде, как будет устроена страховка — всё ещё проверяется.

## В заключение

Мы не уничтожили `'a`. `#1` — это и есть `'a` — та же информация, в другом месте.

Ставка эксперимента такова: ограничения дизайна языка (запрет затенения, явный `return`, новое
связывание в `for`, семантика `{}` как DAG) дают компилятору более чистый вход, и вывод брендов,
возможно, будет автоматически успешным в большинстве сценариев, где правила элизии времён жизни Rust
отказывают. Если получится — пользователю больше не нужно писать `'a`, не нужно различать аннотацию
и элизию, не нужно учить анализатор заимствований. Если не получится — или, точнее, если механизм
страховки (функция-доказательство) потребует от пользователя понимания идентификаторов брендов — это
будет не более чем переизобретение того же самого.
