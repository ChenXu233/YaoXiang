# Мы спрятали `'a` в компилятор

_— Честная заметка о модели ownership YaoXiang_

---

Сколько времени вам понадобилось, чтобы по-настоящему понять этот код на Rust, когда вы впервые его
увидели?

```rust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn advance(&mut self) -> &'a str {
        let start = self.pos;
        self.pos += 1;
        &self.input[start..self.pos]
    }
}
```

Три `'a`. Один в структуре, два в блоке impl. Они говорят одно и то же: `Parser` не может жить
дольше, чем заимствованный `input`. Это правильно. Безопасность Rust построена на этом механизме.

Но когда мы пишем такой код, часто возникает мысль: **разве компилятор сам не может с этим
справиться?** Ответ Rust — «нет» — по крайней мере, без изменения модели заимствования.

**Эта статья не «YaoXiang решил эту проблему». Это «YaoXiang пробует другой путь — спрятать `'a` в
компилятор, чтобы компилятор писал его за вас. Как далеко мы продвинулись и какие твёрдые орешки ещё
не разгрызены».**

---

## Почему Rust нуждается в `'a`

`&T` и `&mut T` в Rust — это указатели — указатели на данные. Заимствовать значение — значит создать
ссылку на него. У этой ссылки есть своё время жизни. Когда ссылка пересекает границу функции
(возвращается как значение, сохраняется в структуре), компилятор не может в пределах одной функции
определить, как долго ссылка может жить — программист должен предоставить информацию через `'a` о
том, что «это возвращаемое значение и этот параметр разделяют время жизни».

Сообщество Rust не стояло на месте. Правила элизии времён жизни освободили большинство простых
функций от аннотаций. NLL появился в редакции 2018 года, освободив заимствования от привязки к
лексической области видимости. Но когда ссылка должна сохраняться в структуре, возвращаться из
функции, захватываться замыканием — **сама модель определяет, что эти сценарии требуют от
программиста аннотировать отношения между ссылками.**

---

## Другой угол: заимствование — это не указатель, а токен

Основной дизайн YaoXiang зафиксирован в
[RFC-009 (Модель ownership)](/design/rfc/accepted/009-ownership-model). Он не меняет семантику по
умолчанию (это Move), но меняет **онтологию заимствования**.

В YaoXiang `&T` и `&mut T` — **не указатели**. Они — **нуль-размерные токены compile-time** —
доказательства доступа на уровне типов. Заимствовать значение — значит не создать указатель на него,
а создать доказательство «мне разрешено обращаться к нему»:

```
&T     →  Гарантирует неизменяемость данных. Реализует Dup (копируемо), несколько токенов только-для-чтения сосуществуют безопасно
&mut T →  Гарантирует исключительную изменяемость. Не реализует Dup (линеен), от одного источника может быть только один
```

В Rust вы пишете `&` в точке вызова (`distance(&p1, &p2)`). В YaoXiang компилятор видит, что
сигнатура функции требует `&Point`, и автоматически создаёт токен в точке вызова — точка вызова
становится `distance(p1, p2)`. Цена — в том, что определяющий должен объявить `&` в сигнатуре, иначе
семантика Move по умолчанию съест ownership:

```yaoxiang
# В сигнатуре нужен & — компилятор видит &Point, при вызове автоматически создаёт токен
check_dimensions: (v: &Vec3) -> Bool = { ... }
check_bounds: (v: &Vec3) -> Bool = { ... }

v = Vec3(1.0, 2.0, 3.0)
if check_dimensions(v) and check_bounds(v) {  # каждый раз автоматически создаётся токен &Vec3
    # v по-прежнему доступен
}
```

В Rust вы ставите `&` в точке вызова; в YaoXiang вы ставите `&` в точке определения. Аннотации не
исчезли — изменилось их расположение.

## Механизм брендов: `'a`, спрятанный в компиляторе

Пользователь никогда не сталкивается с этим — но чтобы понять, что именно сделал YaoXiang, нужно это
понять.

Компилятор внутри назначает каждому токену заимствования уникальный номер compile-time:

```
Видимое пользователю       Внутреннее представление компилятора
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)
&mut Point     →  WriteToken(Point, #M)
```

Когда из `&Point` вы получаете доступ к полю и получаете `&Float`, последний несёт производный
бренд: `#N.field_x`. Когда вы передаёте токен `&mut` через Move другой переменной, компилятор знает,
что исходная переменная больше не владеет — это базовая возможность семантики Move.

**`#N` — это и есть `'a`.** Отношение префикса — `#N` является префиксом `#N.field_x` — это и есть
ограничение outlives. Та же информация. Программист Rust пишет `'a`, компилятор YaoXiang пишет `#N`.

Разница только в проценте успешного вывода. Правила элизии Rust и NLL покрывают около 80% сценариев.
Ставка YaoXiang: **если дизайн языка даёт компилятору более чистый ввод, может ли он покрыть
больше?**

Эта ставка поддерживается несколькими языковыми ограничениями:

- **Запрет затенения переменных** — `x` в этой области видимости имеет только одну идентичность,
  компилятору не нужно различать «о каком x ты говоришь»
- **Явный `return`** — что сбегает из блока, написано явно, компилятору не нужно выводить «является
  ли последняя строка возвращаемым значением»
- **`for` создаёт новую привязку на каждой итерации** — переменные между итерациями не влияют друг
  на друга, компилятору не нужно отслеживать «что изменилось в прошлой итерации»

Эти правила — не «спецификация». В отличие от бесполезного ритуала геттеров/сеттеров в Java, каждое
из них **превращает информацию, которую компилятор должен выводить, в информацию, уже записанную в
программе**. Компилятору не нужно гадать, «какую переменную вы имеете в виду», «сбежало ли это»,
«как переменная цикла меняется между итерациями» — ответы в коде.

## Что бренды могут — как и Rust

Поскольку токены — это обычные типы, они подчиняются всем правилам обычных типов. Никаких
специальных запретов вроде «ссылки нельзя возвращать», «ссылки нельзя хранить в структурах»,
«замыкания не могут захватывать ссылки». **Но и Rust так же может — Rust может всё это.** Разница не
в возможностях, а в том, кто пишет аннотации.

**Возврат ссылки — программист Rust пишет `'a`, компилятор YaoXiang пишет `#N`:**

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)
}

p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()   # токен распространяется к вызывающему, компилятор отслеживает цепочку производных брендов
```

Rust делает то же самое, только программист должен написать `'a`, связывающий вход и выход. В
YaoXiang компилятор автоматически производит производные через пути брендов — `px_ref`
(`#N.field_x`) производится от `p` (`#N`). То же ограничение, другая запись.

**Структура хранит ссылку — без параметра времени жизни:**

```yaoxiang
Window: Type = {
    target: Point,
    view: &Point,   # поле-токен, ничем не отличается от других полей
}
```

В Rust, когда структура имеет поле-ссылку, `'a` должен присутствовать в определении структуры и во
всех блоках impl — программист явно аннотирует ограничение времени жизни `Window<'a>`. В YaoXiang в
`view: &Point` не пишется `'a`, но номер бренда по-прежнему играет ту же роль внутри компилятора —
когда экземпляр `Window` уничтожается, внутренний токен умирает вместе с ним. Та же гарантия, другая
видимость.

**Захват замыканием — нуль-стоимостное копирование Dup-токенов:**

```yaoxiang
filter_by_threshold: (items: List(Point), threshold: &Float) -> List(Point) = {
    items.filter(|p| p.x > threshold)   # токен threshold копируется в замыкание, без накладных расходов
}
```

`&Float` реализует Dup (копируемо), и замыкание захватывает его как захватывает нуль-размерное
целое. Та же система правил, что и автоматическое заимствование при вызове функций. Ноль аннотаций
от пользователя.

## Цена: аннотации исчезли из сигнатур

У `'a` в Rust есть часто упоминаемая ценность: он также является документацией.
`fn split_at_mut<'a>(slice: &'a mut [T], mid: usize) -> (&'a mut [T], &'a mut [T])` — `'a` говорит
читателю, что оба возвращаемых среза ссылаются на одни и те же исходные данные.

В реальности сила этого аргумента ограничена — большинство начинающих Rust не читают `'a` как
документацию, а копируют как заклинание, требуемое компилятором. Но, если быть честным, в сложных
сценариях заимствования `'a` в Rust хотя бы даёт отправную точку для отслеживания потоков данных. В
YaoXiang вам нужно понимать цепочки производных брендов — бренды невидимы для пользователя, это
зависит от инструментария, а инструментарий ещё не созрел.

## Обнаружение конфликтов токенов: тот же конвейер доказательств

В Rust есть отдельный «проверщик заимствований». **Направление дизайна** YaoXiang — унифицировать
конфликты заимствований в конвейер доказательств проверки типов
([RFC-027 (Предикаты compile-time и унифицированная статическая верификация)](/design/rfc/accepted/027-compile-time-evaluation-types)).

Конфликт токенов — это утверждение Хоара:

```
{ конфликтующий ReadToken мёртв } data.push(4) { WriteToken безопасно получен }
```

```yaoxiang
# &mut T — линейный тип — после Move исходная переменная больше не владеет
bad: (p: &mut Point) -> Void = {
    p2: &mut Point = p    # WriteToken перемещается от p к p2
    p.x = 10.0            # { p владеет WriteToken } p.x = 10.0 { безопасно }
}                          # → WriteToken от p уже перемещён → Disproved

# &T — Dup, копируемо
good: (p: &Point) -> Void = {
    p2: &Point = p        # копирование токена только-для-чтения
    print(p.x)            # OK, два токена только-для-чтения сосуществуют
}
```

Общий путь сообщения об ошибках с ошибками типов, сбоями верификации предикатов. Вам не нужно
изучать две системы диагностики. **Но цена в том, что:** сложный конфликт токенов в Rust порождает
тщательно сформулированную ошибку проверки заимствований; в YaoXiang это может выглядеть как
«WriteToken(#7.field_x) conflicts with WriteToken(#7)» — технически точно, но номера брендов не
имеют смысла для человека. Объяснимость сообщений об ошибках — область, которая ещё не проверена.

## Ключевое слово `ref`: автоматический выбор Rc/Arc

Токены не могут пересекать границу задач (потоков) — это доказательства compile-time, а не значения
runtime. Для разделения между областями видимости используется `ref`:

```yaoxiang
shared_data = ref Point(1.0, 2.0)   # escape-анализ компилятора автоматически выбирает Rc или Arc

spawn {
    print(shared_data.x)   # пересекает границу задачи → компилятор выбирает Arc
}
```

- Не сбегает в блок spawn → `Rc` (неатомарный подсчёт ссылок)
- Сбегает в блок spawn → `Arc` (атомарный подсчёт ссылок)

Цена: читая код, невозможно из локального контекста узнать, `ref` — это Rc или Arc. Один рефакторинг
(оборачивание кода в spawn) может тихо изменить реализацию подсчёта ссылок — вы не получите
напоминания от компилятора. Изменение производительности неявно.

## Текущий твёрдый орешек: RAII слишком грубый

Выше мы сказали, что токены — это значения, время жизни управляется RAII. Но правила RAII для
обычных значений таковы: **значение живёт до конца области видимости.** Именно это и было проблемой
Rust до NLL — заимствование длилось до конца блока, даже если вы давно перестали им пользоваться.

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_view: &Header = data.header()    # производный &Header от &mut Data
    header_info = parse_header(header_view) # ← последнее использование header_view
    # header_view не нужно жить до конца функции —
    # но RAII держит его живым до }

    data.modify(header_info)   # ❌ ReadToken ещё «жив», WriteToken заблокирован
}
```

NLL в Rust анализирует последнее использование, а не лексическую область видимости. YaoXiang
нуждается в той же возможности. Текущее решение — подключить анализ активности токенов к тому же
конвейеру доказательств — три уровня:

1. **Быстрый путь** — повторное использование существующего BorrowChecker (линейное сканирование, на
   уровне IR-инструкций). Сценарии, где токен использован и освобождён в одном базовом блоке,
   проходят сразу
2. **Структурный анализ** — сопоставление префиксов дерева брендов (определение того, кто с кем
   конфликтует) + запросы потребителей DAG (определение того, находится ли последний потребитель
   токена после текущего узла)
3. **SMT-решатель** — активируется только тогда, когда требуются логические рассуждения, например
   для условий цикла

Инфраструктура конвейера доказательств (трёхзначный возврат `Proved/Disproved/Unproven`, бэкенд Z3
SMT, стек гипотез) уже частично реализована в `src/frontend/core/typecheck/proof/`. Слой ownership
(`layers/ownership.rs`) — это пока скелет — он напрямую возвращает Proved без фактических проверок.
Заполняем.

Решение текущей версии — ручное вложение блоков для сокращения области видимости токена:

```yaoxiang
process: (data: &mut Data) -> Void = {
    header_info = {
        header_view: &Header = data.header()
        parse_header(header_view)
    }   # header_view освобождается с окончанием блока
    data.modify(header_info)   # ✅
}
```

Это настоящее трение. Каждый, кто приходит из Rust, столкнётся с этим. Можно ли его устранить —
зависит от того, как подключение конвейера к слою ownership сработает.

## Самый сложный вопрос: запасной вариант

`'a` в Rust — это не только бремя — это также запасной вариант. Компилятор не может вывести —
программист аннотирует отношения времени жизни, компилятор проверяет. **У вас есть ручка для
бумаги.**

Теоретически запасной вариант YaoXiang должен быть **функцией-доказательством compile-time**
(RFC-027 §4.2): компилятор не может вывести автоматически → программист пишет функцию, тип возврата
которой — это утверждение «токены не конфликтуют» → компилятор проверяет тип этой функции. Но —

Как выглядит функция-доказательство «токены не конфликтуют»? Как пользователь конструирует значение
типа `WriteTokenAvailable`? Должен ли он понимать отношения префиксов между `#N` и `#N.field_x`?

**Если функция-доказательство требует от пользователя понимания номеров брендов — мы просто
переписали `'a` под видом `#1`. Ничего не сэкономили.**

На этот вопрос ответа пока нет. Это самое вероятное место, где весь эксперимент может застрять.

## Девять итераций RFC-009

Это не дизайн из башни из слоновой кости. RFC-009 прошёл через девять крупных версий:

| Версия | Ключевое изменение                                                                                                                                | Почему была отвергнута                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| v1–v7  | На основе модели ownership Rust, постепенное добавление анализа потребления, обратных функций, изменяемости на уровне полей                       | Избыточная разработка, сложность вышла из-под контроля                              |
| **v8** | «Урезанное заимствование» — `&T`/`&mut T` могут быть только параметрами, не могут возвращаться, храниться в структурах, захватываться замыканиями | Три жёстко закодированных запрета. Серьёзно ограниченная выразительность            |
| **v9** | Система токенов заимствования — `&T`/`&mut T` — обычные типы, подчиняющиеся обычным правилам                                                      | Устранены специальные правила, но отслеживание брендов погружено внутрь компилятора |

Переход от v8 к v9 — настоящий прорыв: от трёх запретов к нулю специальных правил. Но v9 устранил
видимые пользователю правила, а не внутреннюю сложность системы — механизм брендов, отслеживание
производных, обнаружение конфликтов общего происхождения — всё это по-прежнему существует, просто
перенесено в компилятор. Унификация проверки заимствований в конвейер доказательств — это
направление, но сможет ли оно работать на реальном коде и как спроектировать запасной вариант — всё
ещё проверяется.

## В заключение

Мы не уничтожили `'a`. `#1` — это `'a` — та же информация, в другом месте.

Ставка эксперимента: ограничения дизайна языка (запрет затенения, явный return, новые привязки
`for`, DAG-семантика `{}`) дают компилятору более чистый ввод, и вывод брендов, возможно, будет
автоматически успешным в большинстве сценариев, где правила элизии времён жизни Rust не справляются.
Если получится — пользователю больше не нужно писать `'a`, не нужно различать аннотации и элизию, не
нужно изучать проверщик заимствований. Если не получится — или, точнее, если механизм запасного
варианта (функция-доказательство) потребует от пользователя понимания номеров брендов — это просто
изобретение заново.

Работа продолжается. Напишем снова, когда будут результаты.
