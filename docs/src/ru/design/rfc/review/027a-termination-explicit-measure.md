# RFC-027a: Явные меры проверки завершаемости

## Краткое содержание

RFC-027 §7 определяет критерий проверки завершаемости как **рефайнд-типы** (рефайнд — это вход в
режим проверки), а §6.9 задаёт языковую форму явных мер (встроенный предикат `Terminates`, наряду с
`Int` и `Never` относится к core primitives). Оба решения являются дизайном языка, частью host RFC,
уже утверждены.

Данный под-RFC описывает механизмы реализации: как обязательства генерируются из вычислительных
структур, как организуется конвейер проверки, как выдавать **направление** диагностики при
невозможности вывода, как совместно использовать меры для взаимной рекурсии (оптимизация SCC), как
регистрировать коды ошибок. **Повторения языковой семантики нет**, только описание механизмов.

## Мотивация

### Зачем нужен под-RFC

Критерий (рефайнд-типы входят в режим проверки) и форма (`Terminates` записывается в позиции типа)
уже определены в RFC-027, гранулярность — уровень языка. Оставшиеся вопросы слишком детализированы,
их включение в host раздует основной текст:

- Откуда берутся обязательства (точки рекурсивных вызовов, обратные рёбра циклов, охранные условия
  путей)
- Как сравнивать меры, возвращающие кортежи (лексикографическое развёртывание)
- Являются ли обоснованность и строгое убывание двумя независимыми обязательствами или одним
- Как сосуществуют автоматическое исследование и явные меры в одном конвейере
- Как в взаимной рекурсии избежать повторного написания и повторной проверки одной меры
- Как выдавать **направление** вместо простого отказа при невозможности вывода

### Триггер

Направление задано #318: неструктурная рекурсия (gcd-подобная с косвенным убыванием, взаимная
рекурсия, merge-партиционирование) выходит за рамки последовательности шаблонов исследования мер
(RFC-027 §6.2–6.5 — четыре стратегии, все принимают «переменные ограниченного типа» или «целевой
тип + коммутативная операция» на вход), и не может быть переписана в анализируемую итеративную форму
без нарушения читаемости. Пункт пересмотра в секции «Открытые вопросы» RFC-027 здесь активируется.

## Предложение

### Отношение к автоматическому исследованию

Явные меры **не являются другим конвейером**, а служат входом после неудачи исследования. После
предоставления меры используется тот же SMT для проверки того же набора обязательств; при
невыполнении — ошибка с контрпримером. Приоритет полной автоматизации сохраняется: исследование
всегда выполняется первым, вмешательство пользователя происходит только после неудачи исследования.

Это определяет, что два пути совместно используют всю инфраструктуру — генерацию обязательств,
SMT-проверку, лексикографическое развёртывание, формат диагностики. Всё реализуется единожды.

### Генерация обязательств

Для функции `f` и меры `m` генерируются два **независимых** обязательства, развёрнутые по каждой
точке рекурсивного вызова (включая межфункциональные вызовы внутри SCC):

1. **Обоснованность**: `m(args) >= 0` — мера лежит на натуральных числах; если мера возвращает
   ненатуральный тип, берётся нижняя граница подходящего порядка на этом типе. Выводится из
   параметрических рефайндов, при невыводимости переходит в остаточное обязательство.
2. **Строгое убывание**: в каждой точке вызова `m(callee_args) < m(caller_args)`, проверяется под
   **охранным условием пути** — охранение берётся из условного оператора ветвления, содержащего
   данную точку вызова, с повторным использованием сбора условий пути из RFC-009a.

Два независимых, а не одно, потому что направления неудачи различаются: неудача обоснованности
указывает на неправильную область значений меры (например, `Int` может быть отрицательным), неудача
убывания — что рекурсивные параметры не движутся в нужном направлении. Диагностика требует
различения, чтобы дать правильное направление проверки (см. секцию «Диагностика»).

**Для циклов аналогично**, заменяя «точка вызова» на «обратное ребро»: на каждом пути выполнения
тела цикла `m(следующее_состояние) < m(текущее_состояние)`, охранение берётся из условия цикла и
ветвлений внутри тела.

**Лексикографическое развёртывание**: когда `m` возвращает кортеж `(m₁, …, mₖ)`, обязательство с
лексикографическим сравнением разворачивается в цепочку дизъюнктов —
`(m₁' < m₁) ∨ (m₁' == m₁ ∧ m₂' < m₂) ∨ …`. Развёртывание выполняется на **стороне генерации
обязательств**, SMT-сторона получает линейный фрагмент без зависимости от нативной поддержки
лексикографии в решателе.

**Мера сама должна вычисляться на этапе компиляции**: `m` должна быть функцией с доказательством
через константное сворачивание или структурную рекурсию — запрещено рекурсивно перекладывать задачу
завершаемости на другую недоказанную функцию (защита от бесконечной регрессии). Патологические меры
блокируются существующим E4012 (слишком глубокая константная рекурсия) и структурными проверками.

### Конвейер проверки

```
1. Параметрическое убывание (структурная рекурсия, сильнейший путь, выполняется первым)
2. Исследование меры: последовательность шаблонов из четырёх стратегий (RFC-027 §6.2–6.5), останавливается при нахождении
3. Исследование успешно → генерация обязательств → SMT-проверка → Proved
4. Исследование неудачно → проверка наличия явной меры в позиции типа (Terminates)
     Есть → генерация обязательств по мере → SMT-проверка
     Нет → E4021 (завершаемость недоказуема, с рекомендацией направления проверки)
5. Обязательство опровергнуто SMT → E4022 (мера не выполняется, с контрпримером)
```

Шаги 1–3 — утверждённый путь RFC-027, данный RFC добавляет шаг 4 и два кода ошибок. Весь конвейер
выполняется только при триггере рефайнд-типа (RFC-027 §7) — обычные типы без рефайндов не генерируют
обязательств.

### Анкоры: унарная и бинарная формы

RFC-027 §6.9 определяет две арности, данный RFC объясняет их точки применения:

| Форма                   | Анкор                   | Точка применения                                                                                                                            |
| ----------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `Terminates(m)`         | Имя содержащего binding | Форма по умолчанию в точке определения — self-recursive функции, циклы                                                                      |
| `Terminates(FnType, m)` | Явный тип функции       | Когда нужно явно указать, к какому типу функции относится мера (мера определена в другом месте, одна мера обслуживает несколько вычислений) |

Это не два разных конструкта, а две арности одного предиката: обязательство завершаемости всегда
привязывается к «тому вычислительному фрагменту, который аннотирован в позиции типа, где стоит
рефайнд». Для взаимной рекурсии **не требуется** бинарная форма — обе функции пишут свою унарную
форму, совместное использование распознаётся через SCC (см. следующую секцию).

### SCC: оптимизация совместного использования мер

Для группы взаимно рекурсивных функций (сильно связная компонента на графе вызовов), использующих
одну меру, обязательство для межфункционального ребра —
`m_callee(callee_args) < m_caller(caller_args)`, и при совместном использовании меры членами оно
вырождается в убывание по одной мере.

**Это оптимизация, а не предварительное условие корректности**: без совместного использования каждая
функция пишет свою меру и замыкается независимо — проверка проходит. Ценность SCC в том, чтобы
распознать «эта группа использует одну меру», избежав повторного написания и повторной проверки.

Требуется создание **графа вызовов на уровне функций и сбор SCC** — существующий `TypeDepGraph`
фиксирует зависимости типовых аннотаций между переменными (VC-триггеры из RFC-027 §6.1), это граф на
уровне переменных, непригодный для повторного использования.

### Примеры

#### gcd: неструктурная рекурсия

```yaoxiang
// Мера: обычная функция, может тестироваться отдельно, переиспользуется
gcd_measure: (a: Int, b: Int) -> Int = { b }

gcd: Terminates((a: Int, b: Int) -> Int, gcd_measure) = {
    if b == 0 { return a }
    return gcd(b, a % b)
}
```

Генерация обязательств:

1. **Обоснованность**: `gcd_measure(a, b) >= 0`, то есть `b >= 0` — напрямую выводится из
   параметрического рефайнда `NonNegative(b)`
2. **Строгое убывание**: единственная точка рекурсивного вызова `gcd(b, a % b)`, охранение пути
   `b != 0`, обязательство `gcd_measure(b, a % b) < gcd_measure(a, b)`; подстановка тела меры даёт
   `a % b < b`
3. **SMT**: проверяется невыполнимость отрицания `b != 0 ∧ a % b >= b` → Proved

#### Цикл: анонимный конструктив получает денотат

```yaoxiang
loop: (n: Int) -> Int = {
    mut i = 0
    acc: Terminates(n - i) = while i < n {
        i = i + 1
    }
    return acc
}
```

`Terminates(m)` рефайндит тип значения выражения в хвосте цикла, анкор предоставляется именем
binding `acc` — цикл становится **обозначаемым**, «анонимный конструктив не имеет денотата» больше
не тупик. Это также объясняет единство двух арностей: обязательство всегда привязывается к тому
вычислительному фрагменту, который аннотирован в позиции типа, где стоит рефайнд, для функций и
циклов без различий.

Обязательства: на обратном ребре `(n - i') < (n - i)`, охранение `i < n`, подстановка `i' = i + 1`
даёт `1 > 0`, всегда истинно → Proved.

#### Взаимная рекурсия: совместное использование меры через SCC

```yaoxiang
nat: (n: Int) -> Int = { n }

is_even: Terminates(nat) = {
    if n == 0 { return true }
    return is_odd(n - 1)
}
is_odd: Terminates(nat) = {
    if n == 0 { return false }
    return is_even(n - 1)
}
```

Обе функции содержат унарную форму `Terminates(nat)`. После сбора SCC распознаётся, что они
используют одну меру, обязательство для межфункционального ребра `nat(n - 1) < nat(n)` при охранении
`n != 0` всегда истинно, обе функции проверяются за один проход.

Без распознавания SCC каждая функция проверяется независимо с тем же обязательством — проверка всё
равно проходит, просто дублируется. Это подтверждает, что SCC — оптимизация.

### Диагностика

**Когда обоснованность не выводится, не отказываем, а рекомендуем направление.** Диагностика для
неудачи обязательства убывания должна отличаться: первое указывает на область значений меры, второе
— на рекурсивные параметры. Рекомендации для трёх типов неудач:

| Неудача                          | Рекомендуемое направление                                                                          |
| -------------------------------- | -------------------------------------------------------------------------------------------------- |
| Обоснованность не выводится      | Выполняется ли мера на возможных значениях как нижняя граница (например, нужна ли мера `Int >= 0`) |
| Строгое убывание опровергнуто    | Действительно ли рекурсивные параметры движутся в направлении убывания меры; с SMT-контрпримером   |
| Нет меры и исследование неудачно | Можно присвоить имя этому вычислению и предоставить меру в позиции типа (RFC-027 §6.9)             |

Представление контрпримеров по спецификации диагностических сообщений RFC-013. При нелинейных
охранениях путей SAT-контрпримеры могут быть неинтуитивными — зафиксировано как известное
ограничение, будет улучшаться с развитием RFC-013.

### Коды ошибок

Выравнивание с семейством E4xxx ошибок доказательства (E4018 — нарушение рефайнд-предиката, E4020 —
требуется доказательство функции):

| Предлагаемый код | Название                  | Триггер                                                                                          |
| ---------------- | ------------------------- | ------------------------------------------------------------------------------------------------ |
| E4021            | Завершаемость недоказуема | Исследование неудачно и в позиции типа нет явной меры (подсказка предоставить меру `Terminates`) |
| E4022            | Мера не выполняется       | Обязательство меры опровергнуто SMT (с контрпримером)                                            |

Окончательная нумерация определяется при реализации по фактическому состоянию реестра RFC-013
(корректность разрядов обеспечивается门槛 в build.rs).

### Существующий дефект диагностического слоя

В текущей реализации неудача завершаемости в области видимости сообщается как **E8001 «Внутренняя
ошибка компилятора»** (`Unproven` форматируется как ICE) — проверка завершаемости не является ICE,
занятие этого кода и вводит пользователя в заблуждение, и маскирует реальный сбой. Данный RFC
исправляет: неудача завершаемости в области видимости идёт по E4021/E4022, код ICE возвращается для
настоящих внутренних ошибок.

### Обратная совместимость

- Ранее отклонённые из-за проверки завершаемости, но **без рефайнд-аннотаций** программы: при новом
  критерии не входят в режим проверки, компилируются — намеренное смягчение, только ослабление, не
  ужесточение.
- Ранее отклонённые из-за проверки завершаемости, с **рефайнд-аннотациями** программы: после
  дописывания мер проходят.
- Positive-сценарии структурной рекурсии, существующие тесты завершаемости: ожидаемое поведение без
  изменений.

## Компромиссы

### Преимущества

- **Ноль нового синтаксиса**: мера записывается в позиции типа, повторно использует механизм
  применения рефайнд-предикатов; нет синтаксических позиций вроде `decreases`.
- **Выравнивание поведения с доменом доказательства**: домен завершаемости получает аналогичный
  fallback-канал, как домен корректности, но с другим placement — для корректности недоказуемое
  предложение пишется в **теле** как доказательственная функция, для завершаемости необнаруженная
  мера объявляется в **позиции типа**. Оба механизма едины (применение рефайнд-типа).
- **Повторное использование инфраструктуры**: обязательства — линейная арифметика плюс охранения
  путей, проходят по уже подключённому конвейеру #292, без нового backend.
- **Цикл получает денотат**: имя binding — это анкор, цикл и функция полностью изоморфны в генерации
  обязательств, не нужно проектировать частный случай для циклов.

### Недостатки и риски

- **Объём необходимой инфраструктуры не меньше, чем «разводка»**: граф вызовов на уровне функций и
  сбор SCC требуют создания с нуля, Z3 ещё не подключён к production-конвейеру. Часть SCC может быть
  отложена (это оптимизация), часть с графом вызовов из того же источника — без неё взаимная
  рекурсия требует отдельного написания мер для каждой функции — проверка проходит, но с повторной
  проверкой.
- **Явная мера — накладные расходы на низкочастотном пути**: два компонента (функция-мера +
  объявление в позиции типа) многословнее inline-аннотации. Принято — fallback низкочастотен, плюс
  мера переиспользуется и тестируется отдельно.
- **Шум от обязательства обоснованности**: при возврате мерой `Int` каждый раз требуется доказывать
  `>= 0`. Смягчение: если параметрический рефайнд уже задаёт нижнюю границу, выводится
  автоматически; при невыводимости переходит в остаточное обязательство, даётся только направление,
  не отказ.
- **Качество контрпримеров**: SAT-контрпримеры при нелинейных охранениях неинтуитивны. Известное
  ограничение.
- **`Terminates` — единственный предикат, тело которого компилятор генерирует сам**: отклонение от
  чистоты «все тела предикатов могут писаться пользователем». Обоснование: его утверждение (убывание
  меры в каждой точке вызова/обратном ребре) встроено в вычислительную структуру, пользовательский
  предикат не может сослаться на тело функции или цикла. Встроенность сводится к имени, механизм без
  нововведений.

## Альтернативные решения

- **`with decreases (b)` — inline-аннотация синтаксиса**: раннее предложение в данном issue,
  отозвано. Решение RFC-027 «никаких синтаксических аннотаций для проверки завершаемости» является
  утверждённым, inline-аннотация превращает неподдерживаемый паттерн завершаемости в синтаксическую
  позицию, а не в позицию типа, что противоречит мировоззрению «всё — функции YaoXiang, всё
  проверяется контролем типов».
- **Отдельная доказательственная функция (`gcd_proof` возвращает `Terminates(f, m)`, обнаруживается
  сканированием по типу возврата)**: ранний дизайн. Отброшено — вводит четыре класса сложности:
  «механизм обнаружения», «соглашение об именовании», «первый из нескольких кандидатов», «как
  разрешаются имена внутри тела доказательственной функции» — и всё из-за вынесения доказательства
  за пределы тела. Переход к записи в позиции типа устраняет все четыре класса.
- **Только мера в типе (`Terminates(m)`), без бинарной формы**: короче, но теряется выразительная
  позиция для «явного указания принадлежности меры» (мера определена в другом месте, одна мера
  обслуживает несколько вычислений). Две арности — это две арности одного предиката, сохранение
  практически бесплатно.
- **Без fallback, требовать переписать в анализируемую итеративную форму**: то есть текущее
  положение. gcd / merge-партиционирование / взаимная рекурсия не могут быть переписаны без
  нарушения читаемости — именно это триггер для пункта пересмотра.

## Нецелевые задачи

- Не добавлять новый синтаксис / ключевые слова / синтаксические позиции аннотаций.
- Не делать обобщённого расширения автоматического синтеза мер (четыре стратегии остаются в плане
  RFC-027, выход за рамки — через явные меры). Общий вывод мер относится к неразрешимой стороне
  «обнаружения», можно только договориться о границах шаблонов, полнота не гарантируется.
- Не объединять с RFC-009a в совместное решение предикатов заимствования (каждый проверяется
  независимо, shared backend).
- Не делать проверку тотальности (totality checking) на уровне типов зависимостей.
- Не требовать, чтобы мера возвращала натуральный тип (без стремления к механизму typeclass
  `WellFoundedRelation` из Lean) — возвращаемый тип меры не ограничен, обоснованность как
  независимое обязательство передаётся в рефайнд-вывод или SMT.

## Этапы и приёмка

- [ ] Генерация обязательств (обоснованность / строгое убывание, инъекция охранений путей,
      лексикографическое развёртывание)
- [ ] Подключение явных мер (разбор анкоров унарной и бинарной форм `Terminates`, извлечение меры из
      позиции типа)
- [ ] Подключение SMT-проверки (повторное использование конвейера #292, внедрение Z3 в production)
- [ ] Граф вызовов на уровне функций + сбор SCC (оптимизация совместного использования мер)
- [ ] Регистрация E4021/E4022 + локали на шести языках
- [ ] Исправление диагностического слоя: неудача завершаемости в области видимости переносится из
      E8001 в семейство ошибок доказательства
- [ ] E2E: positive-сценарии (gcd / цикл `Terminates(n - i)` / взаимная рекурсия `is_even`-`is_odd`)
      / negative-сценарии (мера не выполняется → E4022; без меры → E4021) / нулевая регрессия
      структурной рекурсии
- [ ] Регрессия критерия: рекурсия и циклы без рефайнд-аннотаций больше не отклоняются проверкой
      завершаемости; с рефайнд-аннотациями обязательства срабатывают как обычно
- [ ] Демонстрация приёмки: объявить меру, которая не выполняется → компиляция падает с читаемым
      контрпримером; исправить → проходит
