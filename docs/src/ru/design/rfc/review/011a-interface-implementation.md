# RFC-011a: Реализация интерфейсов и динамическая диспетчеризация

> **Родительский RFC**: [RFC-011: Проект системы обобщений](../accepted/011-generic-type-system.md)
>
> **Настоящий RFC дополняет и заменяет разделы §2.1-2.4 RFC-011, посвящённые ограничениям
> интерфейсов.**

## Резюме

RFC-011 определяет систему обобщений, но не детализирует механизм реализации интерфейсов. Настоящий
документ дополняет:

1. **Объявление интерфейсов**: интерфейс — это параметризованный тип — `(Self: Type) -> Type`, при
   реализации передаётся конкретный тип
2. **Реализация методов**: поддерживаются как внутренние, так и внешние объявления
3. **Правила перегрузки**: разные сигнатуры разрешают перегрузку, одинаковые сигнатуры приводят к
   ошибке (перекрытие запрещено)
4. **Значения по умолчанию**: после поля сразу пишется `= value`
5. **Динамическая диспетчеризация**: сбор типов на этапе компиляции + сопоставление интерфейсов, без
   виртуальных таблиц

**Ключевые проектные решения**:

```yaoxiang
# Определение интерфейса (параметризованный тип, Self — явный параметр типа)
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

# Определение типа (внутреннее объявление)
Dog: Type = {
    x: Int = 10,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
    speak: (self: Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка)
Dog.speak: (self: Dog, volume: Int) -> String = "WOOF"

# Гетерогенный контейнер (динамическая диспетчеризация)
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
```

**Устранённая сложность**:

- ❌ Нет ключевого слова `impl`
- ❌ Нет магического ключевого слова `Self` (`Self` — это явный параметр типа, ничем не отличающийся
  от `T`)
- ❌ Нет аннотаций `dyn Trait + 'a`
- ❌ Нет виртуальных таблиц (сбор типов на этапе компиляции + обёртка в enum)
- ❌ Нет перекрытия (единые правила перегрузки)

## Мотивация

### Недостатки RFC-011

RFC-011 определяет систему обобщений, но не детализирует:

| Проблема                         | Описание                                   |
| -------------------------------- | ------------------------------------------ |
| Синтаксис объявления интерфейсов | Как объявить, что тип реализует интерфейс? |
| Расположение реализации методов  | Внутреннее или внешнее объявление?         |
| Правила перегрузки               | Как обрабатывать одноимённые методы?       |
| Синтаксис значений по умолчанию  | Как задать значение поля по умолчанию?     |
| Динамическая диспетчеризация     | Как реализовать гетерогенные контейнеры?   |

### Цели проектирования

1. **Простота**: ключевое слово `impl` не требуется
2. **Гибкость**: реализация методов поддерживается и внутренне, и внешне
3. **Единообразие**: правила перегрузки согласованы
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: без виртуальных таблиц, сбор типов на этапе компиляции

### Сравнение с Rust

| Возможность                  | Rust                                  | YaoXiang                              |
| ---------------------------- | ------------------------------------- | ------------------------------------- |
| Объявление интерфейса        | `impl Animal for Dog { ... }`         | `Dog: Type = { Animal(Dog), ... }`    |
| Реализация методов           | В блоке `impl`                        | Внутренняя или внешняя                |
| Перегрузка                   | Не поддерживается                     | Поддерживается (разные сигнатуры)     |
| Значения по умолчанию        | Требуется `#[default]`                | Прямая запись `= value`               |
| Гетерогенный контейнер       | `Vec<Box<dyn Animal + 'a>>`           | `List(Animal)`                        |
| Динамическая диспетчеризация | Поиск по vtable                       | Сбор типов на этапе компиляции        |
| Ключевое слово Self          | Магическое, неявно квантифицированное | Явный параметр типа, равноправный с T |

## Предложение

### 1. Объявление интерфейса

**Ключевое правило**: интерфейс — это параметризованный тип `(Self: Type) -> Type`, где `Self`
является явным параметром типа, а не магическим ключевым словом. При реализации интерфейс вызывается
с передачей конкретного типа.

```yaoxiang
# Определение интерфейса (полностью соответствует обобщённым типам из RFC-011)
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

# Тип объявляет реализацию интерфейса
Dog: Type = {
    x: Int,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
}
```

**Обработка компилятором**:

1. Распознать `Animal(Dog)` как вызов инстанцирования `(Self: Type) -> Type`
2. Выполнить подстановку `Self ↦ Dog`: развернуть `Animal(Dog)` → `{ speak: (self: Dog) -> String }`
3. Проверить, предоставляет ли `Dog` все требуемые методы (соответствие сигнатур)
4. При успехе → сгенерировать доказательство реализации
5. При неудаче → ошибка компиляции

**Эквивалентность развёртывания**:

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),  # Развёрнуто в методы Animal с сохранением метки источника
}

# Эквивалентно (с сохранением информации об источнике)
Dog: Type = {
    x: Int,
    speak: (self: Dog) -> String,  # Из Animal, Self заменён на Dog
}
```

**Зачем нужна метка источника**:

- Прямое развёртывание теряет информацию об источнике
- Метка источника используется для генерации доказательства реализации
- Во время выполнения через доказательство находится корректный метод

#### 1.1 Параметр типа Self и момент проверки типов

`Self` — это явный параметр типа интерфейса, а не магическое ключевое слово.
`Animal: (Self: Type) -> Type` и `List: (T: Type) -> Type` — это одно и то же — конструктор типа
`(Type) -> Type`.

**Момент проверки типов**:

- **При определении интерфейса**: `Self` в `{ speak: (self: Self) -> String }` является абстрактным
  параметром типа, выполняется только синтаксическая проверка.
- **В точке инстанцирования**: при `Animal(Dog)` выполняется подстановка `Self ↦ Dog`, после
  развёртывания проводится полная проверка типов (соответствие сигнатур, наличие методов).

Это позволяет избежать проблемы `Self` как неявного магического ключевого слова в RFC-011 — `Self`
не появляется в определении типа, он встречается только один раз в списке параметров интерфейса и
полностью равноправен с `T`.

#### 1.2 Пространство имён полей и методов

Имена полей и имена методов типа разделяют одно общее пространство имён. Если после развёртывания
интерфейса имя метода интерфейса конфликтует с именем поля типа, **компиляция завершается с
ошибкой**:

```yaoxiang
Drawable: (Self: Type) -> Type = {
    x: (self: Self) -> Int,    // Метод с именем x
}

Point: Type = {
    x: Int,                     // Поле тоже с именем x
    Drawable(Point),            # ❌ Ошибка компиляции: Drawable требует метод x, конфликт с полем x
}
```

Доступ к полю `point.x` и вызов метода `point.x()` синтаксически неразличимы. Единое пространство
имён устраняет неоднозначность.

### 2. Реализация методов

**Ключевое правило**: реализация методов поддерживается и во внутреннем, и во внешнем объявлении.

#### 2.1 Внутреннее объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",  # Реализация метода внутри
}
```

#### 2.2 Внешнее объявление

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),
}

# Реализация метода снаружи
Dog.speak: (self: Dog) -> String = "Woof"
```

#### 2.3 Смешанное объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",  # Часть методов внутри
}

# Часть методов снаружи
Dog.play: (self: Dog) -> Void = { ... }
```

**Обработка компилятором**:

1. Собрать все определения (внутренние и внешние)
2. Сгруппировать по сигнатуре (перегрузка)
3. Проверить наличие перекрытий (сообщить об ошибке)
4. Проверить полноту интерфейса
5. Сгенерировать доказательство реализации

### 3. Перегрузка и перекрытие

**Ключевое правило**:

- Разные сигнатуры → перегрузка → разрешена
- Одинаковые сигнатуры → перекрытие → ошибка

#### 3.1 Перегрузка (разрешена)

```yaoxiang
# Разные типы параметров — перегрузка разрешена
Dog.speak: (self: Dog) -> String = "Woof"
Dog.speak: (self: Dog, volume: Int) -> String = "WOOF"
```

#### 3.2 Перекрытие (запрещено)

```yaoxiang
# Сигнатуры полностью совпадают — перекрытие запрещено
Dog.speak: (self: Dog) -> String = "Woof"
Dog.speak: (self: Dog) -> String = "Bark"  # ❌ Ошибка: перекрытие не допускается
```

**Сообщение об ошибке**:

```
Ошибка: повторное определение Dog.speak(self: Dog) -> String
  --> файл2:5:1
  |
5 | Dog.speak: (self: Dog) -> String = "Bark"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ повторное определение
  |
  --> файл1:3:1
  |
3 | Dog.speak: (self: Dog) -> String = "Woof"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ первое определение
```

#### 3.3 Единообразие правил

**Внутренние и внешние объявления подчиняются одинаковым правилам перегрузки/перекрытия**:

```yaoxiang
# Внутреннее объявление
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка, разрешена)
Dog.speak: (self: Dog, volume: Int) -> String = "WOOF"

# Внешнее объявление (перекрытие, запрещена)
Dog.speak: (self: Dog) -> String = "Bark"  # ❌ Ошибка
```

### 4. Значения по умолчанию

**Ключевое правило**: после поля сразу пишется `= value`, что избавляет от необходимости в
конструкторе.

```yaoxiang
Dog: Type = {
    x: Int = 10,  # Значение по умолчанию
    y: Int = 20,  # Значение по умолчанию
    Animal(Dog),
}
```

**Генерация конструктора компилятором**:

```yaoxiang
# Все поля имеют значения по умолчанию → генерируется конструктор без аргументов
Dog.new: () -> Dog = { x: 10, y: 20 }

# Часть полей имеет значения по умолчанию → генерируется конструктор с частичными аргументами
Dog.new: (x: Int) -> Dog = { x: x, y: 20 }
Dog.new: (y: Int) -> Dog = { x: 10, y: y }

# Конструктор со всеми аргументами
Dog.new: (x: Int, y: Int) -> Dog = { x: x, y: y }
```

**Внешнее объявление значений по умолчанию**:

```yaoxiang
Dog: Type = {
    x: Int,
    y: Int,
    Animal(Dog),
}

# Внешнее объявление значений по умолчанию
Dog.x: Int = 10
Dog.y: Int = 20
```

**Эквивалентно внутреннему объявлению**.

```

3. Развернуть сигнатуры методов интерфейса, проверить соответствие сигнатур

5. Сгруппировать по сигнатуре (перегрузка)
6. Проверить перекрытия (сообщить об ошибке)
7. Проверить полноту интерфейса
8. Сгенерировать доказательство реализации
```

### 6. Динамическая диспетчеризация

**Ключевое проектное решение**: сбор типов на этапе компиляции + сопоставление интерфейсов, без
виртуальных таблиц.

#### 6.1 Гетерогенный контейнер

`Animal` — это `(Self: Type) -> Type`. `List(Animal)` использует неинстанцированный конструктор типа
интерфейса как **экзистенциальный тип** (existential): `∃S. Animal(S)` — «существует некоторый тип
S, такой что S реализует Animal(S)».

```yaoxiang
# Определение интерфейса
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

# Определение типа
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",
}

Cat: Type = {
    y: Int,
    Animal(Cat),
    speak: (self: Cat) -> String = "Meow",
}

# Гетерогенный контейнер — Animal не инстанцирован = экзистенциальный тип
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
animals[1].speak()  # "Meow"
```

**Семантика владения**: помещение в гетерогенный контейнер — это семантика перемещения (Move)
(RFC-009). `Dog.new()` перемещается в вариант перечисления `AnimalGroup::Dog`, исходная переменная
становится недоступной.

```yaoxiang
dog = Dog.new()
animals: List(Animal) = [dog]
# dog.speak()  ← ❌ Ошибка компиляции: dog был перемещён (move)
```

#### 6.2 Сбор типов на этапе компиляции

**Ключевая стратегия: отслеживание владения с инкрементальным построением.** Вместо сканирования на
этапе компиляции всех типов, реализующих интерфейс, — **инкрементальный сбор в каждой точке операции
владения** в `List(Animal)`:

```yaoxiang
// Точка конструирования
animals: List(Animal) = [Dog.new()]       // AnimalGroup = { Dog(Dog) }

// Точка добавления (append)
animals.append(Cat.new())                  // Компилятор видит Cat в append → расширяет до { Dog, Cat }
animals.append(Bird.new())                 // Расширяет до { Dog, Cat, Bird }
```

**Обработка компилятором** (инкрементальная):

1. При первом конструировании `List(Animal)` → сгенерировать начальное перечисление (все известные в
   текущей единице компиляции типы-конструкторы)
2. При каждом `append` / `push` / присваивании по индексу → проверить, присутствует ли тип значения
   в перечислении; если нет — расширить варианты перечисления
3. Для итогового перечисления сгенерировать мономорфизированный `match` для диспетчеризации
4. Между единицами компиляции: полагаться на LTO (Link-Time Optimization) для объединения вариантов
   перечисления. Когда `Animal` как экзистенциальный тип передаётся через границу единицы
   компиляции, каждая единица генерирует частичный набор вариантов, а на этапе линковки они
   объединяются в полное перечисление.

**Автоматически сгенерированное перечисление**:

```yaoxiang
# Автоматически генерируется компилятором (невидимо для пользователя)
AnimalGroup: Type = {
    Dog(Dog),
    Cat(Cat),
    Bird(Bird),    # ← append(Bird.new()) вызывает инкрементальное расширение
}

# List(Animal) внутри эквивалентен List(AnimalGroup)
```

#### 6.3 Проверка соответствия интерфейсу

**Ключевое наблюдение**: проверка соответствия интерфейсу выполняется на этапе компиляции, даже если
типы приходят из динамически загружаемых плагинов.

```yaoxiang
# Система плагинов
plugin = load_plugin("bird.so")

# Проверка компилятора: возвращаемый тип plugin.create_bird() должен реализовывать Animal
bird: Animal = plugin.create_bird()  # Проверка на этапе компиляции, экзистенциальный тип

# Помещение в гетерогенный контейнер — точка append вызывает расширение перечисления
animals: List(Animal) = [Dog.new(), Cat.new()]
animals.append(bird)                 // Компилятор: (1) проверить, что bird реализует Animal (2) расширить перечисление
```

**Обработка компилятором**:

1. Проверить возвращаемый тип аргумента `append`
2. Убедиться, что этот тип реализует целевой интерфейс
3. При успехе → расширить перечисление, разрешить добавление
4. При неудаче → ошибка компиляции

#### 6.4 Диспетчеризация во время выполнения

**Поток вызова (match по перечислению на этапе компиляции, ImplementationProof стёрт):**

```
animals[0].speak()
  ↓
Сгенерированный компилятором match:
  match animals[0] {
    AnimalGroup.Dog(d) => d.speak(),
    AnimalGroup.Cat(c) => c.speak(),
    AnimalGroup.Bird(b) => b.speak(),
  }
```

**Проекция бренда** (взаимодействие с RFC-009a): привязка шаблона `match` `AnimalGroup.Dog(d)`
порождает в дереве брендов дочерний бренд `#animals[0].Dog`, эквивалентный проекции поля
(`#42.field_x`). Цепочка брендов `ReadToken(d)`, создаваемая `d.speak()`, выглядит как
`animals → animals[0] → d → ReadToken(d)`; проверщик заимствований верифицирует конфликты через
сопоставление префиксов в дереве брендов.

**Тип при доступе по индексу**: `animals[0]` возвращает `&AnimalGroup` (сгенерированный компилятором
тип перечисления); пользователь не может напрямую получить `&mut Animal`. Изменяемый доступ
осуществляется опосредованно через методы интерфейса (например, `animals[0].mutate()` внутри
разворачивается в `AnimalGroup::Dog(d) => d.mutate()`).

**Сравнение с виртуальной таблицей**:

|                                       | Виртуальная таблица (Rust)               | Перечисление на этапе компиляции (YaoXiang)                    |
| ------------------------------------- | ---------------------------------------- | -------------------------------------------------------------- |
| Способ поиска                         | Указатель на vtable → указатель на метод | match по перечислению → прямой вызов                           |
| Накладные расходы во время выполнения | Одно косвенное обращение                 | Ветвление (оптимизируется предсказателем переходов CPU)        |
| Генерация на этапе компиляции         | vtable                                   | enum + match                                                   |
| Аннотации пользователя                | Требуется `dyn Trait + 'a`               | Не требуется                                                   |
| ImplementationProof                   | Не применимо                             | Стирается на этапе компиляции, отсутствует во время выполнения |

**Преимущества YaoXiang**:

- Не требуются аннотации брендов
- Безопасность типов на этапе компиляции
- Прозрачно для пользователя (не нужно писать `dyn Animal`)
- ImplementationProof — чисто компиляционная концепция, нулевые накладные расходы во время
  выполнения

#### 6.5 Ограничения и область применения

**В пределах единицы компиляции:** полная поддержка. Отслеживание владения покрывает все точки
`append`/конструирования, перечисление строится инкрементально.

**Между единицами компиляции:** Полагается на LTO (Link-Time Optimization) для объединения вариантов
перечисления. `Animal` как экзистенциальный тип (`∃S. Animal(S)`) передаётся через границу единицы
компиляции. Каждая единица генерирует частичный набор вариантов, на этапе линковки они объединяются.

**Не поддерживается:** динамические типы времени выполнения (полностью утиная типизация). Набор
типов должен быть полностью известен на этапе компиляции.

## Компромиссы

### Преимущества

1. **Простота**: ключевое слово `impl` не требуется
2. **Гибкость**: реализация методов поддерживается и внутренне, и внешне
3. **Единообразие**: правила перегрузки согласованы
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: без виртуальных таблиц, сбор типов на этапе компиляции
6. **Безопасность типов**: проверка соответствия интерфейсу на этапе компиляции
7. **Прозрачность для пользователя**: не нужно писать `dyn Animal + 'a`

### Недостатки

1. **Ограничение**: не поддерживается динамическая типизация во время выполнения (полностью утиная
   типизация)
2. **Затраты на этапе компиляции**: для каждого интерфейса необходимо сгенерировать варианты
   перечисления и match для диспетчеризации
3. **Набор типов**: должен быть полностью известен на этапе компиляции (в пределах одной единицы
   компиляции)

### Меры по смягчению

1. **Система плагинов**: поддерживается через проверку соответствия интерфейсу на этапе компиляции
2. **Набор типов**: отслеживание владения с инкрементальным построением — сбор в каждой точке
   `append`/конструирования, а не глобальное сканирование
3. **Между единицами компиляции**: объединение наборов вариантов перечисления на этапе линковки,
   общий механизм с мономорфизацией времени линковки

## Связь с RFC-009

**Бренды и реализация интерфейсов**:

- Реализация интерфейсов находится на уровне типов, не затрагивает бренды
- Бренды находятся на уровне доказательств заимствования (RFC-009a)
- Эти два механизма ортогональны и не влияют друг на друга

**Динамическая диспетчеризация и бренды**:

- Динамическая диспетчеризация использует доказательство реализации, не требует аннотаций брендов
- Доказательство реализации генерируется на этапе компиляции, нулевой поиск во время выполнения
- Устраняет сложность `dyn Trait + 'a`

**Владение в гетерогенном контейнере**:

- Помещение в `List(Animal)` — это семантика Move (RFC-009), исходная переменная становится
  недоступной
- Доступ по индексу `animals[0]` возвращает `&AnimalGroup` (сгенерированный компилятором enum),
  цепочка проекции брендов: `animals → animals[0] → variant_enum → field`
- Изменяемый доступ опосредован через методы интерфейса, `&mut AnimalGroup` не предоставляется
  пользователю

## Наследование интерфейсов

Интерфейс может включать другой интерфейс. **Новый синтаксис не вводится** — используется та же
синтаксическая позиция, что и при объявлении интерфейса типом:

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                       # Pet наследует Animal — без новых ключевых слов
    name: (self: Self) -> String,
}

# Когда Dog реализует Pet, он должен удовлетворять всем методам и Animal, и Pet
Dog: Type = {
    x: Int,
    Pet(Dog),
    speak: (self: Dog) -> String = "Woof",  # Из Animal
    name: (self: Dog) -> String = "Buddy",  # Из Pet
}
```

**Принцип проектирования:** Наследование существует, но его чрезмерное использование не поощряется.
Основной способ композиции — через инстанцирование нескольких интерфейсов
(`Dog: Type = { Animal(Dog), Pet(Dog), ... }`). Тип может напрямую объявить все интерфейсы, которые
он реализует, без необходимости выражать это через дерево наследования. Наследование интерфейсов
используется только при наличии явной иерархии «is-a».

**Обработка компилятором:** развернуть цепочку наследования. `Pet(Self)` разворачивается в
`{ все методы Animal(Self), name: ... }`. Когда `Dog` объявляет `Pet(Dog)`, выполняется
`Self ↦ Dog`, и компилятор проверяет, что `Dog` удовлетворяет всем методам как `Animal(Dog)`, так и
`Pet(Dog)`.

**Подстановка Self при наследовании интерфейсов**: в
`Pet: (Self: Type) -> Type = { Animal(Self), ... }` `Self` в `Animal(Self)` является параметром
`Self` интерфейса `Pet` — его подстановка откладывается. Когда `Dog` реализует `Pet(Dog)`,
происходит `Self ↦ Dog`, и `Animal(Self)` становится `Animal(Dog)`. Это полностью соответствует
семантике передачи параметров в обобщённых функциях.

## Реализация методов по умолчанию

Интерфейс может предоставлять реализации методов по умолчанию. Реализующий тип может переопределить
их или унаследовать:

```yaoxiang
fmt: (Self: Type) -> Type = {
    display: (self: Self) -> String,                      # Должен быть реализован
    debug: (self: Self) -> String = self.display(),       # ✅ Ссылается на метод того же интерфейса
    summary: (self: Self) -> String = f"<{self.name}>",  # ❌ Ошибка компиляции: self.name отсутствует в fmt
}
```

**Ключевое ограничение: интерфейс не может предполагать вышестоящую реализацию.** Метод по умолчанию
может ссылаться только на методы, уже объявленные в том же интерфейсе. Поля конкретного типа или
методы других интерфейсов невидимы для метода по умолчанию — интерфейс представляет собой замкнутый
контракт и не может залезать в карман реализующего типа. Нарушение этого ограничения вызывает ошибку
**непосредственно при определении интерфейса**.

**Наследование может предполагать нижестоящую реализацию:** когда интерфейс `Pet(Self)` наследует
`Animal(Self)`, методы по умолчанию `Pet` могут использовать методы, объявленные в `Animal` —
поскольку они унаследованы, их наличие гарантировано.

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                                              # Наследование
    name: (self: Self) -> String,
    introduce: (self: Self) -> String = self.name() + " says " + self.speak(),  # ✅ speak приходит из унаследованного Animal
}
```

**Поведение на этапе компиляции:** когда тип реализует интерфейс, для каждого метода:

1. Тип предоставил → используется метод типа
2. Тип не предоставил, интерфейс имеет умолчание → компилятор встраивает реализацию по умолчанию в
   тип (нулевые накладные расходы на vtable)
3. Тип не предоставил, интерфейс не имеет умолчания → ошибка компиляции

**Принцип проектирования:** метод по умолчанию подобен механизму автогенерации `Copy`/`Clone` —
компилятор автоматически генерирует при необходимости, пользователь может переопределить. Ключевые
слова `virtual`/`override`/`super` не вводятся.

## Открытые вопросы

- [x] ~~Наследование интерфейсов (интерфейс может наследовать другие интерфейсы)~~ → Поддерживается,
      без нового синтаксиса. `Pet: (Self: Type) -> Type = { Animal(Self), ... }`
