# RFC-032: Унифицированный модификатор выражений spawn

> **В данном документе определяются синтаксис, AST/IR рефакторинг**
> `spawn`. Семантика поведения во время выполнения (гранулярность разбиения задач, ownership,
> области видимости, распространение ошибок, типы ресурсов, вложенность) описана в
> [RFC-024: Семантика параллельной модели выполнения на основе spawn](../accepted/024-concurrency-model.md).
>
> Оба RFC совместно определяют `spawn` — 024 отвечает на вопрос "что делать", 032 — на вопрос "как представить".

> **Ключевая идея**: `spawn` не должен модифицировать только блок `{}`.
> Он может модифицировать **произвольное выражение**. `spawn for`
> — это не особый синтаксис, а естественная комбинация `spawn` + выражение `for`.

## Аннотация

Расширение `spawn` с `spawn { }` (только модификация блока) до `spawn <expr>` (модификация произвольного выражения).
`Expr::SpawnFor` удаляется из AST, естественной заменой становится `Expr::Spawn { body: Expr::For { .. } }`.
Настоящий RFC выполняет только очистку AST/IR/Parser, не затрагивая систему типов.

> **Расширение типов вычислительных структур (`MonoType`) откладывается до отдельного RFC.** После удаления
> особого случая `SpawnFor` интеграция доказательного конвейера с `spawn` требует вычислительных структур,
> aware от системы типов — это общий механизм, не ограниченный spawn, и заслуживает отдельной проработки.

## Мотивация

### Зачем нужны эти изменения?

В текущей реализации `spawn for x in items { body }` — это независимая комбинация ключевых слов, а в AST
существует специальный `Expr::SpawnFor` для её представления. Это нарушает ортогональность языка:

1. **Неединообразный синтаксис**: `spawn` может модифицировать только блок `{}`, `spawn for` — жёстко закодированное исключение
2. **Отсутствие ортогональности**: комбинации `spawn while`, `spawn if` и т.д. невозможно выразить естественно

### Текущие проблемы

```rust
// Два варианта spawn в AST
Spawn { body: Box<Block>, span: Span },         // spawn { ... }
SpawnFor { var, var_mut, iterable, body, span },  // spawn for x in items { ... }
```

## Предложение

### Основной дизайн

`spawn <expr>`: `spawn` модифицирует произвольное выражение. Форма выражения определяет,
как DAG разбивает задачи.

### Ментальная модель пользователя

`spawn` = "взять это выражение и выполнить параллельно". Форма выражения определяет разбиение:

| Форма выражения                  | Поведение параллелизма             |
| -------------------------------- | ---------------------------------- |
| `spawn { a, b, c }`              | `a`, `b`, `c` независимо параллельно |
| `spawn for x in items { f(x) }`  | N итераций независимо параллельно   |
| `spawn while cond { step() }`    | Каждая итерация — независимая задача |
| `spawn if c { a } else { b }`    | Выбранная ветвь целиком в домене spawn |
| `spawn call(x)`                  | Вызов сам по себе как одна задача   |
| `spawn 42`                       | Отдельная задача                   |

Компилятор отвечает за DAG-анализ зависимостей, runtime планирует по модели GMP — независимые задачи
попадают в очередь рабочих, воркеры соревнуются за их выполнение. Полная синхронизация блокирует
до завершения всех задач.

**Отличие от Go**: `go` в Go — это "выбросить и забыть", а `spawn` в YaoXiang —
"разобрать на параллельное выполнение, дождаться полного завершения".

### Ортогональность управления потоком

| Комбинация                        | Семантика                              | Различия                             |
| --------------------------------- | -------------------------------------- | ------------------------------------ |
| `spawn for x in items { body }`   | Data parallelism: каждая итерация = независимая задача | DAG-анализ межитерационных зависимостей |
| `for x in items spawn { body }`   | Каждая итерация создаёт домен spawn    | Без межитерационного анализа         |
| `spawn while cond { body }`       | Условный параллелизм: каждая итерация = независимая задача | Межитерационные зависимости обеспечиваются условием |
| `while cond spawn { body }`       | Каждая итерация создаёт домен spawn    | Семантика отличается, но не требует особой обработки |
| `spawn if c { a } else { b }`    | Весь if-else как один домен spawn      | Выполнение выбирает ветвь по условию |
| `if c spawn { a } else { b }`    | Только одна ветвь spawn                | spawn внутри выражения if            |

### Устранённая сложность

- ❌ `Expr::SpawnFor` удалён из AST
- ❌ `SpawnForAnalysis` удалён из DAG-анализа
- ❌ `spawn for` больше не обрабатывается как комбинация ключевых слов в Parser
- ❌ `Ir::SpawnFor` удалён из IR

## Детальный дизайн

### 1. Уровень AST

**До:**

```rust
Spawn { body: Box<Block>, span: Span },         // spawn { ... }
SpawnFor { var, var_mut, iterable, body, span },  // spawn for x in items { ... }
```

**После:**

```rust
Spawn { body: Box<Expr>, span: Span },           // spawn <произвольное выражение>
```

`Expr::SpawnFor` удалён. AST для `spawn for x in items { body }`:

```rust
Expr::Spawn {
    body: Box::new(Expr::For {
        var: "x",
        iterable: items,
        body: body_block,
        ..
    })
}
```

**Особый случай IF:**

| Запись                               | Структура AST                                        |
| ------------------------------------ | ---------------------------------------------------- |
| `spawn if cond { a } else { b }`    | `Spawn { body: Expr::If { ... } }`                   |
| `if cond spawn { a } else { b }`    | `Expr::If { then: Spawn { body: {a} }, else: {b} }` |

Обе семантики различны, но обе являются естественными комбинациями, не требующими особых правил.

### 2. Уровень Parser

`spawn` имеет наименьший приоритет связывания (как `return`), поглощая всё последующее выражение:

```
spawn a + b        →  spawn (a + b)         ≠  (spawn a) + b
spawn f(x).y       →  spawn (f(x).y)
```

Изменение Parser: в `pratt/nud.rs` `spawn` больше не требует `{`, а вызывает общий парсинг выражений:

```
token spawn → parse_expr(min_precedence) → Expr::Spawn { body: expr }
```

`spawn for` больше не обрабатывается как комбинация ключевых слов — `for` обрабатывается
общим парсером выражений, порождая `Expr::For`, а `spawn` только оборачивает.

### 3. Уровень DAG-анализа

Два входа объединяются в один:

```rust
/// Унифицированный вход: диспетчеризация по виду тела выражения
fn analyze_spawn_expr(body: &Expr, ...) -> SpawnAnalysis {
    match body {
        Expr::Block(block)       => analyze_block_tasks(block, ...),
        Expr::For { .. }         => analyze_iter_tasks(IterKind::For, body, ...),
        Expr::While { .. }       => analyze_iter_tasks(IterKind::While, body, ...),
        Expr::If { .. }          => analyze_if_task(body, ...),
        _                        => single_task(body, ...),
    }
}
```

**Унифицированная структура результата:**

```rust
struct SpawnAnalysis {
    source: TaskSource,
    plan: ExecutionPlan,
}

enum TaskSource {
    /// spawn { a, b, c } — N прямых подвыражений, известных на этапе компиляции
    Explicit(Vec<TaskInfo>),
    /// spawn for/while — N задач, порождаемых итеративно во время выполнения
    Iterate {
        kind: IterKind,
        iter_var: String,
        iterable: Option<Expr>,      // есть у for, нет у while
        condition: Option<Expr>,     // есть у while, нет у for
        body: Block,
        reads: HashSet<String>,
        writes: HashSet<String>,
        resource_vars: HashSet<String>,
    },
}

enum IterKind { For, While }
```

Структура `SpawnForAnalysis` удалена.

| Вид body            | Разбиение на задачи                          |
| ------------------- | -------------------------------------------- |
| `Expr::Block`       | Прямые подвыражения → список задач           |
| `Expr::For`         | Каждая итерация → задача (data parallelism) |
| `Expr::While`       | Каждая итерация → задача                    |
| `Expr::If`          | Выбранная ветвь целиком → задача             |
| `Expr::Call` / прочее | Выражение само → задача                   |

После завершения DAG-анализа runtime планирует по модели GMP — независимые задачи
попадают в очередь рабочих, воркеры соревнуются за выполнение.

### 4. Уровень IR / Codegen

`Ir::SpawnFor` удалён. Унифицировано в `Ir::Spawn` с информацией `TaskSource`.

Трансляция HIR → IR генерирует вызовы runtime в зависимости от `SpawnAnalysis.source`:

- `TaskSource::Explicit(tasks)` → список задач, известный на этапе компиляции
- `TaskSource::Iterate { .. }` → раскрытие во время выполнения (compiler-driven, как par_iter, но с нулевой стоимостью)

### 5. Уровень Placement

Текущие две ветви объединяются:

```rust
// До
Expr::Spawn { body, .. } => self.check_block(body),
Expr::SpawnFor { body, iterable, .. } => {
    self.check_expr(iterable);
    self.check_block(body);
}

// После
Expr::Spawn { body, .. } => self.check_expr(body),   // body — это Expr, рекурсия
```

### 6. Обратная совместимость

Существующий код с `spawn for` сохраняет семантику, Parser автоматически парсит
`spawn for x in items { body }` как `Expr::Spawn { body: Expr::For }`.
Изменяется только внутреннее представление, видимое пользователем поведение неизменно.

Новый синтаксис естественно поддерживается:

```yx
spawn while has_next() {
    item = next()
    process(item)
}

spawn if use_cache {
    load_from_cache(key)
} else {
    fetch(key)
}
```

**Предупреждение о single-task spawn**: при модификации `spawn call(x)` и `spawn 42` и других
одиночных выражений DAG-анализ генерирует предупреждение компиляции:
"spawn модифицирует одиночное выражение без эффекта параллелизма". Синтаксис корректен,
но пользователю предлагается проверить намерение.

## Компромиссы

### Преимущества

1. **Синтаксическая ортогональность**: `spawn` + произвольный поток управления = естественные параллельные комбинации
2. **Устранение особых случаев**: удаление `Expr::SpawnFor` и связанного специального кода
3. **Расширяемость**: новые конструкции потока управления автоматически комбинируются с `spawn`,
   без модификации логики spawn

### Недостатки

1. **Разрушительное изменение**: внутреннее представление AST/IR меняется, требуется обновление
   всего кода, потребляющего `Expr::SpawnFor`
2. **Адаптация доказательного конвейера**: после удаления `SpawnFor` доказательный конвейер
   диспетчеризует через AST (`match body { Expr::For => ..., Expr::While => ... }`) — эта
   адаптация входит вscope данного RFC через унифицированный вход DAG

## Альтернативные решения

| Решение                                          | Почему не выбрано                                              |
| ------------------------------------------------ | --------------------------------------------------------------- |
| Сохранить `spawn for` как независимый синтаксис | Нарушает ортогональность, становится единственным особым случаем в языке |
| `spawn` только для `{}`, data parallelism через стандартную библиотеку `par_iter` | Базовые возможности языка опускаются в библиотеку, теряется компиляторный DAG-анализ и обнаружение конфликтов ресурсов |

## Типы вычислительных структур (отложено в отдельный RFC)

После удаления `SpawnFor` в данном RFC интеграция доказательного конвейера с `spawn`
сталкивается с архитектурной проблемой: доказательный конвейер работает на уровне типов и
должен знать вычислительную структуру внутри spawn (For/While/Block/If/Call), чтобы выбрать
правильную стратегию доказательства. Текущий доказательный конвейер диспетчеризует через AST,
но долгосрочное направление — кодирование вычислительных структур как вариантов `MonoType`
(`Block`/`ForExpr`/`WhileExpr`/`IfExpr`/`Call`/`Spawn`), чтобы конвейер полностью работал
на уровне типов.

Это ослабленная практическая версия [RFC-019: Типовая гомоиконичность](../draft/019-typed-homoiconicity.md) —
встроенные вычислительные структуры компилятора входят в систему типов, но пользовательский
синтаксис не открывается. Теоретическая база — ECMTT (Contextual Modal Types for Algebraic
Effects and Handlers, ICFP 2021): `Spawn<T>` соответствует модальному оператору `□`,
доказательный конвейер соответствует handler.

Этот механизм не ограничен spawn — любой effect (чистые вычисления, IO, fallible) в будущем
сможет войти в систему типов одним и тем же паттерном. spawn — первый потребитель, не единственный.

> **Отдельный RFC определит**: полную семантику 6 вариантов MonoType, стратегию адаптации
> проверки типов, унифицированный интерфейс диспетчеризации доказательного конвейера по типам,
> схему интеграции с RFC-027.

## Стратегия реализации

### Фазы разделения

1. **AST + Parser**: `Spawn { body: Box<Expr> }`, удаление `SpawnFor`
2. **Унификация DAG-анализа**: объединение входов, унификация перечисления `TaskSource`.
   Single-task spawn (`spawn call(x)`, `spawn 42`) генерирует предупреждение компиляции
3. **Адаптация IR / Codegen**: удаление `Ir::SpawnFor`, унификация пути обработки
4. **Упрощение Placement**: удаление ветви `SpawnFor`
5. **Тестирование**: все существующие тесты `spawn for` проходят

### Область влияния

| Файл/каталог                                   | Изменения                                                       |
| ---------------------------------------------- | --------------------------------------------------------------- |
| `frontend/core/parser/ast.rs`                  | body в `Spawn` — `Box<Expr>`, удаление `SpawnFor`               |
| `frontend/core/parser/pratt/nud.rs`            | Упрощение обработчика `spawn` до общего парсинга выражений     |
| `frontend/core/spawn/analysis.rs`              | Унифицированный вход, объединение `TaskSource` Explicit + Iterate |
| `frontend/core/spawn/placement.rs`             | Удаление ветви `SpawnFor`                                       |
| `middle/core/ir.rs`                            | Удаление `Ir::SpawnFor`                                         |
| `middle/` (IR gen, codegen)                    | Унификация пути spawn                                           |
| `tests/yaoxiang/04-concurrency/spawn_for.yx`  | Семантика неизменна, проверка проходит                         |

### Зависимости

- RFC-024 (модель параллельного выполнения на основе spawn-блоков) — настоящий RFC является её ортогональным расширением
- RFC-010 (унифицированный синтаксис типов) — основа унификации синтаксиса
