# RFC-032: Унифицированный модификатор выражений spawn

> **Данный документ определяет синтаксис, рефакторинг AST/IR для `spawn`**. Семантика
> runtime-поведения (гранулярность разбиения задач, ownership, области видимости, error propagation,
> типы ресурсов, вложенность) приведена в
> [RFC-024: Семантика runtime конкурентности на основе spawn](../accepted/024-concurrency-model.md).
>
> Два RFC совместно определяют `spawn` — 024 отвечает на вопрос «что делать», 032 — «как
> представить».

> **Ключевой инсайт**: `spawn` не должен модифицировать только блок `{}`. Он может модифицировать
> **произвольное выражение**. `spawn for` — не особый синтаксис — это естественная комбинация
> `spawn` + выражение `for`.

## Резюме

Расширить `spawn` с `spawn { }` (модифицирует только блок) до `spawn <expr>` (модифицирует
произвольное выражение). `Expr::SpawnFor` удаляется из AST и естественно заменяется на
`Expr::Spawn { body: Expr::For { .. } }`. Данный RFC выполняет только очистку AST/IR/Parser и не
затрагивает изменения в type system.

> **Расширение типа вычислительной структуры (`MonoType`) откладывается в отдельный RFC.** После
> удаления особого случая `SpawnFor` из данного RFC, интеграция `spawn` с proof pipeline потребует
> от type system осведомлённости о вычислительной структуре — это универсальный механизм, не
> ограниченный spawn, и заслуживает отдельного проектирования.

## Мотивация

### Зачем это изменение?

Текущая конструкция `spawn for x in items { body }` является самостоятельной комбинацией ключевых
слов, и в AST имеется специальный узел `Expr::SpawnFor` для её представления. Это нарушает
ортогональность языка:

1. **Неунифицированный синтаксис**: `spawn` может модифицировать только блок `{}`, а `spawn for` —
   жёстко закодированное исключение
2. **Отсутствие ортогональности**: комбинации `spawn while`, `spawn if` и другие не могут быть
   выражены естественно

### Текущие проблемы

```rust
// Два варианта spawn в AST
Spawn { body: Box<Block>, span: Span },         // spawn { ... }
SpawnFor { var, var_mut, iterable, body, span },  // spawn for x in items { ... }
```

## Предложение

### Основной дизайн

`spawn <expr>`: `spawn` модифицирует произвольное выражение. Форма выражения определяет, как DAG
разбивает задачи.

### Ментальная модель пользователя

`spawn` = «выполни это выражение конкурентно». Форма выражения определяет способ разбиения:

| Форма выражения                 | Поведение конкурентности              |
| ------------------------------- | ------------------------------------- |
| `spawn { a, b, c }`             | `a`, `b`, `c` независимо параллельны  |
| `spawn for x in items { f(x) }` | N итераций независимо параллельны     |
| `spawn while cond { step() }`   | Каждая итерация — отдельная задача    |
| `spawn if c { a } else { b }`   | Выбранная ветвь целиком — домен spawn |
| `spawn call(x)`                 | Сам вызов — одна задача               |
| `spawn 42`                      | Одна отдельная задача                 |

Компилятор отвечает за DAG-анализ для определения зависимостей, runtime планирует по модели GMP —
независимые задачи помещаются в рабочую очередь, worker'ы конкурируют за их выполнение. Общая
синхронизация — блокирующее ожидание завершения всех задач.

**Отличие от Go**: `go` в Go означает «запусти и забудь», тогда как `spawn` в YaoXiang означает
«разбери и выполни параллельно, дождись завершения всех, затем продолжи».

### Ортогональность потока управления

| Комбинация                      | Семантика                                                   | Различие                                                  |
| ------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| `spawn for x in items { body }` | Параллелизм по данным: каждая итерация = независимая задача | DAG-анализ зависимостей между итерациями                  |
| `for x in items spawn { body }` | Каждая итерация создаёт домен spawn                         | Без межитерационного анализа                              |
| `spawn while cond { body }`     | Условный параллелизм: каждая итерация = независимая задача  | Межитерационные зависимости обеспечиваются условием       |
| `while cond spawn { body }`     | Каждая итерация создаёт домен spawn                         | Семантика отличается, но не требует специальной обработки |
| `spawn if c { a } else { b }`   | Весь if-else — один домен spawn                             | При выполнении ветвь выбирается по условию                |
| `if c spawn { a } else { b }`   | spawn только в одной ветви                                  | Внутри выражения if обёрнут spawn                         |

### Устраняемая сложность

- ❌ `Expr::SpawnFor` удаляется из AST
- ❌ `SpawnForAnalysis` удаляется из DAG-анализа
- ❌ `spawn for` больше не обрабатывается как комбинация ключевых слов в Parser
- ❌ `Ir::SpawnFor` удаляется из IR

## Детальный дизайн

### 1. Уровень AST

**До:**

```rust
Spawn { body: Box<Block>, span: Span },         // spawn { ... }
SpawnFor { var, var_mut, iterable, body, span },  // spawn for x in items { ... }
```

**После:**

```rust
Spawn { body: Box<Expr>, span: Span },           // spawn <произвольное выражение>
```

`Expr::SpawnFor` удаляется. AST-представление `spawn for x in items { body }`:

```rust
Expr::Spawn {
    body: Box::new(Expr::For {
        var: "x",
        iterable: items,
        body: body_block,
        ..
    })
}
```

**Особый случай IF**:

| Запись                           | Структура AST                                       |
| -------------------------------- | --------------------------------------------------- |
| `spawn if cond { a } else { b }` | `Spawn { body: Expr::If { ... } }`                  |
| `if cond spawn { a } else { b }` | `Expr::If { then: Spawn { body: {a} }, else: {b} }` |

Семантика различается, но обе являются естественными комбинациями и не требуют специальных правил.

### 2. Уровень Parser

`spawn` имеет самый низкий приоритет связывания (как `return`), захватывая всё последующее
выражение:

```
spawn a + b        →  spawn (a + b)         ≠  (spawn a) + b
spawn f(x).y       →  spawn (f(x).y)
```

Изменения Parser: в `pratt/nud.rs` `spawn` больше не требует `{`, а вызывает общий парсер выражений:

```
token spawn → parse_expr(min_precedence) → Expr::Spawn { body: expr }
```

`spawn for` больше не обрабатывается как комбинация ключевых слов — `for` обрабатывается общим
парсером выражений с порождением `Expr::For`, а `spawn` только выполняет обёртывание.

### 3. Уровень DAG-анализа

Два текущих входа объединяются в один:

```rust
/// Унифицированный вход: диспетчеризация по типу body-выражения
fn analyze_spawn_expr(body: &Expr, ...) -> SpawnAnalysis {
    match body {
        Expr::Block(block)       => analyze_block_tasks(block, ...),
        Expr::For { .. }         => analyze_iter_tasks(IterKind::For, body, ...),
        Expr::While { .. }       => analyze_iter_tasks(IterKind::While, body, ...),
        Expr::If { .. }          => analyze_if_task(body, ...),
        _                        => single_task(body, ...),
    }
}
```

**Унифицированная структура результата**:

```rust
struct SpawnAnalysis {
    source: TaskSource,
    plan: ExecutionPlan,
}

enum TaskSource {
    /// spawn { a, b, c } — N прямых подвыражений, известных на этапе компиляции
    Explicit(Vec<TaskInfo>),
    /// spawn for/while — N задач порождаются итерациями в runtime
    Iterate {
        kind: IterKind,
        iter_var: String,
        iterable: Option<Expr>,      // есть у for, нет у while
        condition: Option<Expr>,     // есть у while, нет у for
        body: Block,
        reads: HashSet<String>,
        writes: HashSet<String>,
        resource_vars: HashSet<String>,
    },
}

enum IterKind { For, While }
```

Структура `SpawnForAnalysis` удаляется.

| Тип body              | Как разбивается на задачи                             |
| --------------------- | ----------------------------------------------------- |
| `Expr::Block`         | Прямые подвыражения → список задач                    |
| `Expr::For`           | Каждая итерация → одна задача (параллелизм по данным) |
| `Expr::While`         | Каждая итерация → одна задача                         |
| `Expr::If`            | Выбранная ветвь целиком → одна задача                 |
| `Expr::Call` / прочее | Само выражение → одна задача                          |

После завершения DAG-анализа runtime планирует по модели GMP — независимые задачи помещаются в
рабочую очередь, worker'ы конкурируют за их выполнение.

### 4. Уровень IR / Codegen

`Ir::SpawnFor` удаляется. Унифицируется в `Ir::Spawn`, несущий информацию о `TaskSource`.

Трансляция HIR → IR генерирует runtime-вызовы на основе `SpawnAnalysis.source`:

- `TaskSource::Explicit(tasks)` → список задач, известный на этапе компиляции
- `TaskSource::Iterate { .. }` → раскрытие в runtime (управляется компилятором, подобно par_iter, но
  с нулевыми накладными расходами)

### 5. Уровень Placement

Две текущие ветви объединяются в одну:

```rust
// До
Expr::Spawn { body, .. } => self.check_block(body),
Expr::SpawnFor { body, iterable, .. } => {
    self.check_expr(iterable);
    self.check_block(body);
}

// После
Expr::Spawn { body, .. } => self.check_expr(body),   // body — это Expr, достаточно рекурсии
```

### 6. Обратная совместимость

Семантика существующего кода `spawn for` не изменяется, Parser автоматически разбирает
`spawn for x in items { body }` как `Expr::Spawn { body: Expr::For }`. Внутреннее представление
меняется, пользовательское поведение остаётся прежним.

Новый синтаксис получается естественно:

```yx
spawn while has_next() {
    item = next()
    process(item)
}

spawn if use_cache {
    load_from_cache(key)
} else {
    fetch(key)
}
```

**Предупреждение для одно-задачного spawn**: когда `spawn` модифицирует одиночное выражение, такое
как `spawn call(x)` и `spawn 42`, DAG-анализ генерирует compile-time предупреждение: «spawn,
модифицирующий одиночное выражение, не имеет эффекта конкурентности». Синтаксис допустим, но
напоминает пользователю проверить намерение.

## Соображения

### Преимущества

1. **Ортогональность синтаксиса**: `spawn` + произвольный поток управления = естественная комбинация
   для конкурентности
2. **Устранение особых случаев**: удаление `Expr::SpawnFor` и связанного с ним специального кода
3. **Расширяемость**: будущие структуры потока управления автоматически комбинируются с `spawn` без
   изменения логики spawn

### Недостатки

1. **Ломающее изменение**: внутреннее представление AST/IR изменяется, требуется обновление всего
   кода, потребляющего `Expr::SpawnFor`
2. **Адаптация proof pipeline**: после удаления `SpawnFor` proof pipeline диспетчеризирует через AST
   (`match body { Expr::For => ..., Expr::While => ... }`) — данная адаптация выполняется в рамках
   настоящего RFC через унифицированный вход DAG

## Альтернативы

| Альтернатива                                                                                    | Почему не выбрана                                                                                                       |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Сохранить независимый синтаксис `spawn for`                                                     | Нарушает ортогональность, становится единственной особой комбинацией ключевых слов в языке                              |
| `spawn` модифицирует только `{}`, параллелизм по данным через стандартную библиотеку `par_iter` | Базовая возможность языка опускается в библиотеку, теряется compiler-level DAG-анализ и обнаружение конфликтов ресурсов |

## Тип вычислительной структуры (отложен в отдельный RFC)

После удаления `SpawnFor` из настоящего RFC, интеграция `spawn` с proof pipeline сталкивается с
архитектурной проблемой: proof pipeline работает на уровне типов и должен знать вычислительную
структуру внутри spawn (For/While/Block/If/Call), чтобы выбрать правильную стратегию доказательства.
Текущий proof pipeline диспетчеризирует через AST, но долгосрочное направление — кодирование
вычислительной структуры как вариантов `MonoType`
(`Block`/`ForExpr`/`WhileExpr`/`IfExpr`/`Call`/`Spawn`), чтобы pipeline работал полностью на уровне
типов.

Это ослабленная практическая версия
[RFC-019: Тип-уровневая гомоиконичность](../draft/019-typed-homoiconicity.md) — встроенные в
компилятор вычислительные структуры попадают в type system, но без открытия пользовательского
синтаксиса. Теоретическая основа — ECMTT (Contextual Modal Types for Algebraic Effects and Handlers,
ICFP 2021): `Spawn<T>` соответствует модальному оператору `□`, proof pipeline соответствует handler.

Данный механизм не ограничен spawn — в будущем любой effect (чистое вычисление, IO, fallible) может
попасть в type system через ту же модель. spawn — первый потребитель, но не единственный.

> **Отдельный RFC определит**: полную семантику 6 вариантов MonoType, стратегию адаптации type
> checker, унифицированный интерфейс диспетчеризации proof pipeline по типам, схему интеграции с
> RFC-027.

## Стратегия реализации

### Разбиение на этапы

1. **AST + Parser**: `Spawn { body: Box<Expr> }`, удаление `SpawnFor`
2. **Унификация DAG-анализа**: слияние входов, унификация enum `TaskSource`. Одно-задачный spawn
   (`spawn call(x)`, `spawn 42`) генерирует compile-time предупреждение
3. **Адаптация IR / Codegen**: удаление `Ir::SpawnFor`, унификация путей обработки
4. **Упрощение Placement**: удаление ветви `SpawnFor`
5. **Тестирование**: все существующие тесты `spawn for` проходят

### Область воздействия

| Файл/директория                              | Изменения                                                        |
| -------------------------------------------- | ---------------------------------------------------------------- |
| `frontend/core/parser/ast.rs`                | `Spawn` body изменён на `Box<Expr>`, удалён `SpawnFor`           |
| `frontend/core/parser/pratt/nud.rs`          | Обработчик `spawn` упрощён до общего парсера выражений           |
| `frontend/core/spawn/analysis.rs`            | Унифицированный вход, `TaskSource` объединяет Explicit + Iterate |
| `frontend/core/spawn/placement.rs`           | Удалена ветвь `SpawnFor`                                         |
| `middle/core/ir.rs`                          | Удалён `Ir::SpawnFor`                                            |
| `middle/` (IR gen, codegen)                  | Унификация путей spawn                                           |
| `tests/yaoxiang/04-concurrency/spawn_for.yx` | Семантика не изменяется, верификация прохождения                 |

### Зависимости

- RFC-024 (модель конкурентности на основе spawn-блоков) — данный RFC является её ортогональным
  расширением
- RFC-010 (унифицированный синтаксис типов) — основа для унификации синтаксиса
