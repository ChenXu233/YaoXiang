# RFC-032: Унификация модификатора выражений spawn

> **Настоящий документ определяет синтаксис `spawn` и рефакторинг AST/IR.** Семантика поведения во
> время выполнения (гранулярность декомпозиции задач, владение, область видимости, распространение
> ошибок, типы ресурсов, вложенность) приведена в
> [RFC-024: Семантика среды выполнения параллелизма на основе spawn](./024-concurrency-model.md).
>
> Два RFC совместно определяют `spawn` — 024 отвечает на вопрос «что делать», 032 — на вопрос «как
> представить».

> **Ключевая идея**: `spawn` не должен модифицировать только блок `{}`. Он может модифицировать
> **произвольное выражение**. `spawn for` — это не специальный синтаксис, а естественная комбинация
> `spawn` + выражения `for`.

## Резюме

Расширение `spawn` с `spawn { }` (модификация только блока) до `spawn <expr>` (модификация
произвольного выражения). `Expr::SpawnFor` удаляется из AST и естественно заменяется на
`Expr::Spawn { body: Expr::For { .. } }`. Данный RFC выполняет только очистку AST/IR/Parser, не
затрагивая систему типов.

> **Тип вычислительной структуры (расширение `MonoType`) откладывается в отдельный RFC.** После
> удаления особого случая `SpawnFor` в данном RFC интеграция конвейера доказательств `spawn`
> требует, чтобы система типов распознавала вычислительную структуру — это общий механизм, не
> ограниченный spawn, заслуживающий отдельной проработки.

## Мотивация

### Почему необходимо это изменение?

В настоящее время `spawn for x in items { body }` является отдельной комбинацией ключевых слов, и в
AST имеется специальный `Expr::SpawnFor` для её представления. Это нарушает ортогональность языка:

1. **Неунифицированный синтаксис**: `spawn` может модифицировать только блок `{}`, `spawn for`
   является жёстко закодированным исключением.
2. **Отсутствие ортогональности**: комбинации вроде `spawn while`, `spawn if` и т.п. не могут быть
   выражены естественно.

### Текущая проблема

```rust
// Два варианта spawn в AST
Spawn { body: Box<Block>, span: Span },         // spawn { ... }
SpawnFor { var, var_mut, iterable, body, span },  // spawn for x in items { ... }
```

## Предложение

### Основной дизайн

`spawn <expr>`: `spawn` модифицирует произвольное выражение. Форма выражения определяет, как DAG
разбивает задачи.

### Ментальная модель пользователя

`spawn` = «выполнить это выражение конкурентно». Форма выражения определяет способ разбиения:

| Форма выражения                 | Поведение параллелизма                           |
| ------------------------------- | ------------------------------------------------ |
| `spawn { a, b, c }`             | `a`, `b`, `c` выполняются независимо параллельно |
| `spawn for x in items { f(x) }` | N итераций выполняются независимо параллельно    |
| `spawn while cond { step() }`   | Каждая итерация — отдельная задача               |
| `spawn if c { a } else { b }`   | Выбранная ветвь целиком — домен spawn            |
| `spawn call(x)`                 | Сам вызов — одна задача                          |
| `spawn 42`                      | Одна отдельная задача                            |

Компилятор отвечает за анализ DAG для определения зависимостей, во время выполнения планирование
происходит по модели GMP — задачи без зависимостей помещаются в рабочую очередь, и worker'ы
конкурируют за их выполнение. Общая синхронизация — блокирующее ожидание завершения всех задач.

**Отличие от Go**: `go` в Go означает «запустить и забыть», тогда как `spawn` в YaoXiang означает
«разбить и выполнить параллельно, дождаться завершения всех частей, затем продолжить».

### Ортогональность потока управления

| Комбинация                      | Семантика                                                | Различие                                                                   |
| ------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| `spawn for x in items { body }` | Параллелизм данных: каждая итерация = отдельная задача   | Анализ зависимостей в DAG между итерациями                                 |
| `for x in items spawn { body }` | Каждая итерация создаёт домен spawn                      | Анализ между итерациями не выполняется                                     |
| `spawn while cond { body }`     | Условный параллелизм: каждая итерация = отдельная задача | Зависимости между итерациями обеспечиваются условием                       |
| `while cond spawn { body }`     | Каждая итерация создаёт домен spawn                      | Семантика отличается от вышеуказанной, но не требует специальной обработки |
| `spawn if c { a } else { b }`   | Весь if-else — один домен spawn                          | Во время выполнения выбирается ветвь по условию                            |
| `if c spawn { a } else { b }`   | spawn только в одной ветви                               | if-выражение содержит spawn внутри                                         |

### Устраняемая сложность

- ❌ `Expr::SpawnFor` удаляется из AST
- ❌ `SpawnForAnalysis` удаляется из анализа DAG
- ❌ `spawn for` больше не обрабатывается как комбинация ключевых слов в парсере
- ❌ `Ir::SpawnFor` удаляется из IR

## Детальный дизайн

### 1. Уровень AST

**Ранее:**

```rust
Spawn { body: Box<Block>, span: Span },         // spawn { ... }
SpawnFor { var, var_mut, iterable, body, span },  // spawn for x in items { ... }
```

**После:**

```rust
Spawn { body: Box<Expr>, span: Span },           // spawn <произвольное выражение>
```

`Expr::SpawnFor` удаляется. AST-представление `spawn for x in items { body }`:

```rust
Expr::Spawn {
    body: Box::new(Expr::For {
        var: "x",
        iterable: items,
        body: body_block,
        ..
    })
}
```

**Особый случай IF**:

| Запись                           | Структура AST                                       |
| -------------------------------- | --------------------------------------------------- |
| `spawn if cond { a } else { b }` | `Spawn { body: Expr::If { ... } }`                  |
| `if cond spawn { a } else { b }` | `Expr::If { then: Spawn { body: {a} }, else: {b} }` |

Семантика различается, но обе являются естественными комбинациями и не требуют специальных правил.

### 2. Уровень парсера

`spawn` имеет самый низкий приоритет связывания (аналогично `return`), поглощая всё последующее
выражение:

```
spawn a + b        →  spawn (a + b)         ≠  (spawn a) + b
spawn f(x).y       →  spawn (f(x).y)
```

Изменения в парсере: в `pratt/nud.rs` `spawn` больше не требует `{`, а вызывает общий парсер
выражений:

```
token spawn → parse_expr(min_precedence) → Expr::Spawn { body: expr }
```

`spawn for` больше не обрабатывается как комбинация ключевых слов — `for` обрабатывается общим
парсером выражений и порождает `Expr::For`, а `spawn` только выполняет обёртывание.

### 3. Уровень анализа DAG

Текущие два входа объединяются в один:

```rust
/// Унифицированный вход: диспетчеризация по типу выражения body
fn analyze_spawn_expr(body: &Expr, ...) -> SpawnAnalysis {
    match body {
        Expr::Block(block)       => analyze_block_tasks(block, ...),
        Expr::For { .. }         => analyze_iter_tasks(IterKind::For, body, ...),
        Expr::While { .. }       => analyze_iter_tasks(IterKind::While, body, ...),
        Expr::If { .. }          => analyze_if_task(body, ...),
        _                        => single_task(body, ...),
    }
}
```

**Унифицированная структура результата**:

```rust
struct SpawnAnalysis {
    source: TaskSource,
    plan: ExecutionPlan,
}

enum TaskSource {
    /// spawn { a, b, c } — N прямых подвыражений, известных на этапе компиляции
    Explicit(Vec<TaskInfo>),
    /// spawn for/while — N задач, порождаемых итерациями во время выполнения
    Iterate {
        kind: IterKind,
        iter_var: String,
        iterable: Option<Expr>,      // есть у for, отсутствует у while
        condition: Option<Expr>,     // есть у while, отсутствует у for
        body: Block,
        reads: HashSet<String>,
        writes: HashSet<String>,
        resource_vars: HashSet<String>,
    },
}

enum IterKind { For, While }
```

Структура `SpawnForAnalysis` удаляется.

| Тип body              | Способ декомпозиции на задачи                 |
| --------------------- | --------------------------------------------- |
| `Expr::Block`         | Прямые подвыражения → список задач            |
| `Expr::For`           | Каждая итерация → задача (параллелизм данных) |
| `Expr::While`         | Каждая итерация → задача                      |
| `Expr::If`            | Выбранная ветвь целиком → задача              |
| `Expr::Call` / прочее | Само выражение → задача                       |

После завершения анализа DAG планирование во время выполнения происходит по модели GMP — задачи без
зависимостей помещаются в рабочую очередь, и worker'ы конкурируют за их выполнение.

### 4. Уровень IR / Codegen

`Ir::SpawnFor` удаляется. Унифицируется до `Ir::Spawn` с информацией о `TaskSource`.

Трансляция HIR → IR генерирует вызовы среды выполнения на основе `SpawnAnalysis.source`:

- `TaskSource::Explicit(tasks)` → список задач, известных на этапе компиляции
- `TaskSource::Iterate { .. }` → разворачивается во время выполнения (управляется компилятором,
  подобно par_iter, но с нулевыми накладными расходами)

### 5. Уровень Placement

Текущие две ветви объединяются в одну:

```rust
// Ранее
Expr::Spawn { body, .. } => self.check_block(body),
Expr::SpawnFor { body, iterable, .. } => {
    self.check_expr(iterable);
    self.check_block(body);
}

// После
Expr::Spawn { body, .. } => self.check_expr(body),   // body — это Expr, достаточно рекурсии
```

### 6. Обратная совместимость

Семантика существующего кода `spawn for` не изменяется, парсер автоматически разбирает
`spawn for x in items { body }` как `Expr::Spawn { body: Expr::For }`. Внутреннее представление
изменяется, но видимое пользователем поведение остаётся прежним.

Новый синтаксис получается естественно:

```yx
spawn while has_next() {
    item = next()
    process(item)
}

spawn if use_cache {
    load_from_cache(key)
} else {
    fetch(key)
}
```

**Предупреждение об одно-задачном spawn**: когда `spawn call(x)` и `spawn 42` и подобные
модифицируют единственное выражение, анализ DAG генерирует предупреждение компиляции: «spawn,
модифицирующий одиночное выражение, не имеет эффекта параллелизма». Синтаксис допустим, но
пользователю напоминают о необходимости проверить намерение.

## Компромиссы

### Преимущества

1. **Ортогональность синтаксиса**: `spawn` + любой поток управления = естественная комбинация для
   параллелизма.
2. **Устранение особых случаев**: удаление `Expr::SpawnFor` и связанного с ним специального кода
   обработки.
3. **Расширяемость**: будущие структуры потока управления автоматически комбинируются с `spawn` без
   изменения логики spawn.

### Недостатки

1. **Критические изменения**: изменяется внутреннее представление AST/IR, необходимо обновить весь
   код, использующий `Expr::SpawnFor`.
2. **Необходима адаптация конвейера доказательств**: после удаления `SpawnFor` конвейер
   доказательств диспетчеризируется через AST
   (`match body { Expr::For => ..., Expr::While => ... }`) — эта адаптация выполняется в рамках
   данного RFC через унифицированный вход DAG.

## Альтернативы

| Альтернатива                                                                                 | Почему не выбрана                                                                                                      |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Сохранение `spawn for` как отдельного синтаксиса                                             | Нарушает ортогональность, становится единственной комбинацией ключевых слов в языке                                    |
| `spawn` модифицирует только `{}`, параллелизм данных через стандартную библиотеку `par_iter` | Возможности языка опускаются в библиотеку, теряется анализ DAG на уровне компилятора и обнаружение конфликтов ресурсов |

## Тип вычислительной структуры (откладывается в отдельный RFC)

После удаления `SpawnFor` в данном RFC интеграция конвейера доказательств `spawn` сталкивается с
архитектурной проблемой: конвейер доказательств работает на уровне типов и должен знать
вычислительную структуру внутри spawn (For/While/Block/If/Call) для выбора правильной стратегии
доказательства. В настоящее время конвейер доказательств диспетчеризируется через AST, но
долгосрочное направление заключается в кодировании вычислительной структуры как вариантов `MonoType`
(`Block`/`ForExpr`/`WhileExpr`/`IfExpr`/`Call`/`Spawn`), чтобы конвейер полностью работал на уровне
типов.

Это ослабленная практическая версия
[RFC-019: Тип-уровневая гомиконичность](./019-typed-homoiconicity.md) — встроенные в компилятор
вычислительные структуры попадают в систему типов, но без открытия пользовательского синтаксиса.
Теоретическая основа — ECMTT (Contextual Modal Types for Algebraic Effects and Handlers, ICFP 2021):
`Spawn<T>` соответствует модальному оператору `□`, а конвейер доказательств соответствует handler'у.

Этот механизм не ограничен spawn — в будущем любой effect (чистое вычисление, IO, fallible) может
войти в систему типов по той же схеме. spawn — первый потребитель, но не единственный.

> **Отдельный RFC определит**: полную семантику 6 вариантов MonoType, стратегию адаптации проверки
> типов, унифицированный интерфейс диспетчеризации конвейера доказательств по типу, схему интеграции
> с RFC-027.

## Стратегия реализации

### Разбиение на этапы

1. **AST + Parser**: `Spawn { body: Box<Expr> }`, удаление `SpawnFor`.
2. **Унификация анализа DAG**: слияние входов, объединение перечисления `TaskSource` из Explicit +
   Iterate. Одно-задачные spawn (`spawn call(x)`, `spawn 42`) порождают предупреждение компиляции.
3. **Адаптация IR / Codegen**: удаление `Ir::SpawnFor`, унификация путей обработки.
4. **Упрощение Placement**: удаление ветви `SpawnFor`.
5. **Тестирование**: все существующие тесты `spawn for` проходят успешно.

### Область влияния

| Файл/каталог                                 | Изменения                                                           |
| -------------------------------------------- | ------------------------------------------------------------------- |
| `frontend/core/parser/ast.rs`                | Поле `body` в `Spawn` меняется на `Box<Expr>`, удаляется `SpawnFor` |
| `frontend/core/parser/pratt/nud.rs`          | Обработчик `spawn` упрощается до общего парсера выражений           |
| `frontend/core/spawn/analysis.rs`            | Унифицированный вход, `TaskSource` объединяет Explicit + Iterate    |
| `frontend/core/spawn/placement.rs`           | Удаление ветви `SpawnFor`                                           |
| `middle/core/ir.rs`                          | Удаление `Ir::SpawnFor`                                             |
| `middle/` (IR gen, codegen)                  | Унификация путей spawn                                              |
| `tests/yaoxiang/04-concurrency/spawn_for.yx` | Семантика не изменяется, проверяется прохождение тестов             |

### Зависимости

- RFC-024 (модель конкурентности блоков spawn) — данный RFC является её расширением ортогональности.
- RFC-010 (унифицированный синтаксис типов) — основа для унификации синтаксиса.
