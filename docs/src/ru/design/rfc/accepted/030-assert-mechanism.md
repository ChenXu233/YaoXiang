# RFC-030: механизм assert

## Резюме

В YaoXiang вводится механизм `assert` для тестирования, проверки предусловий и runtime panic.
`assert` и компиляционный уточняющий тип `Assert(C)` (см. RFC-011 §4.3) — это **две стороны одного
уточняющего примитива** — диспетчеризация автоматически направляет их в компиляционное
доказательство или runtime-проверку в зависимости от того, доступны ли свободные переменные
предиката на этапе компиляции. `assert(false, "msg")` эквивалентно `raise`, отдельные ключевые слова
`throw`/`raise` не требуются.

## Мотивация

### Зачем нужна эта возможность?

В настоящее время E2E-тесты YaoXiang могут имитировать утверждения только через `if` +
`io.println` + `return`:

```yaoxiang
val = some_func()
if val != 42 {
    io.println("FAIL: expected 42")
    return
}
```

Такой подход имеет три проблемы:

1. **Много шаблонного кода**: каждое утверждение требует 4 строк, файлы тестов раздуваются
2. **Слабые сообщения об ошибках**: ручная конкатенация строк, отсутствует позиция в исходном коде
3. **Некомпозируемость**: невозможно пакетно регистрировать утверждения, невозможно передать их в
   качестве аргументов в тестовый фреймворк

### Текущие проблемы

- Нет единого механизма утверждений
- Тестовый код наводнён шаблоном `if` + печать + `return`
- На уровне байт-кода уже есть инструкция `Throw`, но на уровне языка она не доступна
- RFC-011 определяет компиляционный условный тип `Assert(C)`, но runtime `assert()` ещё не
  реализован

### Принципы проектирования

`assert` — это единственный пользовательский механизм panic в YaoXiang. `assert(false, "msg")`
эквивалентно `raise`, отдельное ключевое слово `throw`/`raise` не требуется. Функция `assert` сама
по себе является лучшей инкапсуляцией `if raise`.

**Никаких новых ключевых слов, никакого нового синтаксиса. Всё — вызовы функций.**

## Вариант A: native-функция

Реализовать `assert` как native-функцию, не вводя новых ключевых слов.

```yaoxiang
use std.assert.assert

main = {
    assert(1 + 1 == 2, "math is broken")
    assert(get_name() == "YaoXiang", "name mismatch")
}
```

### Перегрузка сигнатур

`assert` имеет две перегрузки:

```
// Основная сигнатура: assert — это вводящий оператор значения для Assert
assert: (cond: Bool, ?msg: String | Error) -> Assert(IsTrue(cond))
//                                       ^^^^^^^^^^^^^^^^^^^^^^^^
//                                       Возвращает уточняющий тип, а не ()
//
// IsTrue: Bool -> Type — мост от истинного значения к типу:
//   IsTrue(true)  = Void   (⊤, программа продолжается)
//   IsTrue(false) = Never  (⊥, расходимость / ошибка компиляции)
```

Фактическое поведение `assert` определяется диспетчеризацией:

- Все свободные переменные известны на этапе компиляции → **CompileTime**: компилятор вычисляет
  cond, true → стирается в Void, false → ошибка компиляции (Never необитаем)
- Присутствуют runtime-свободные переменные → **Runtime**: вставляется проверка, в
  потоко-чувствительный набор предположений Γ впрыскивается уточняющий факт

Необязательное сообщение `?msg` и перегрузка Result (см. ниже) сохраняются как полезная нагрузка
runtime raise.

#### Перегрузка 1: утверждение по условию `(Bool, ?String | Error)`

`Bool` + необязательное сообщение. Сообщение может быть значением `String` или `Error`:

```yaoxiang
assert(1 + 1 == 2)                    // без сообщения, информация panic по умолчанию
assert(1 + 1 == 2, "math is broken")   // строковое сообщение
assert(x > 0, my_error)                // непосредственно бросает значение Error
```

`assert(false, "msg")` — это эквивалент `raise`/`throw` в YaoXiang — отдельное ключевое слово не
нужно.

#### Перегрузка 2: утверждение Result `(Result)`

### Преимущества

- **Никаких изменений синтаксиса**: чистая функция, новые ключевые слова не нужны
- **Никаких новых концепций**: повторное использование существующего механизма регистрации
  native-функций
- **Высокая расширяемость**: перегрузка функций естественно поддерживает несколько сигнатур
- **Самодокументируемость**: пространство имён `std.assert` само по себе является документацией

### Недостатки

- Отсутствуют. При корректной сигнатуре типа assert компилятор может вывести мёртвый код через
  анализ достижимости функций. Дополнительный проход не требуется.

### Поведение во время выполнения

1. Вычислить первый аргумент `condition: Bool`
2. Если `true`, вернуть `Unit`
3. Если `false`, инициировать runtime panic:
   - Вывести содержимое `message` (если есть)
   - Вывести стек вызовов (в debug-режиме)
   - Завершить текущее выполнение

#### Поведение при сбое для каждой перегрузки

| Сигнатура                  | Поведение при сбое                      |
| -------------------------- | --------------------------------------- |
| `assert(false)`            | panic с информацией по умолчанию        |
| `assert(false, "msg")`     | Вывод строкового сообщения, затем panic |
| `assert(false, error_val)` | Бросить значение Error                  |
| `assert(Err(x))`           | Извлечь содержимое Err и panic          |

### Связь с компиляционным Assert

`assert` и `Assert` — **две стороны одного уточняющего примитива** — конвейер диспетчеризации
автоматически выбирает между ними по критерию «доступны ли свободные переменные предиката на этапе
компиляции»:

| Условие                                       | Диспетчеризация                      | Поведение                                                                                    |
| --------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------- |
| Все свободные переменные известны компилятору | CompileTime → конвейер доказательств | Proved → стирается, Disproved → ошибка компиляции, Unknown → требуется доказательство        |
| Есть runtime-свободные переменные             | Runtime → вставка check              | Проверка Bool + впрыскивание уточняющего факта в потоко-чувствительный набор предположений Γ |

```yaoxiang
use std.assert

# Известно на этапе компиляции (параметр дженерика) — путь CompileTime, нулевые runtime-затраты
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    length: assert.Assert(N > 0),   # N — параметр дженерика, вычисляется компилятором
}

# Runtime-значение — путь Runtime, вставляется проверка Bool
x = read_int()
assert.assert(x > 0, "expected positive")  # runtime-проверка
```

> **2026-07-12, единое решение**: предыдущий вывод о «полной независимости» заменён. `assert()` —
> это вводящий оператор значения для `Assert`, диспетчеризация выполняется автоматически.

### Изменения в компиляторе

**Парсер, AST, typecheck, IR gen изменять не требуется.**

Достаточно добавить регистрацию native-функции в `src/std/`:

1. Добавить `src/std/assert.rs`
2. Зарегистрировать `std.assert.assert` и `std.assert.Assert` (последний — компиляционный условный
   тип)
3. Внутри вызвать уже существующую инструкцию `BytecodeInstr::Throw`

### Преимущества

- **Никаких изменений синтаксиса**: чистая функция, новые ключевые слова не нужны
- **Никаких новых концепций**: повторное использование существующего механизма регистрации
  native-функций
- **Высокая расширяемость**: сигнатура функции может быть расширена до вариантов вроде `assert_eq`
  (в будущем)
- **Самодокументируемость**: пространство имён `std.assert` само по себе является документацией

### Недостатки

- ~~Неизвестно на этапе компиляции: в отличие от варианта B (ключевое слово), нельзя выполнить
  устранение мёртвого кода во время компиляции~~ → **в рамках единого решения это больше не
  актуально**. assert в режиме CompileTime идёт через конвейер доказательств, cond, известный на
  этапе компиляции, → стирается или приводит к ошибке компиляции (`assert(false)` → Never → мёртвый
  код).
- Стек вызовов доступен только в debug-режиме

## Вариант B: встроенное ключевое слово (заменено единым решением)

> Устарело. Противоречие между вариантами A и B снимается конвейером диспетчеризации — assert — это
> вводящий оператор значения для Assert, известное на этапе компиляции идёт через конвейер
> доказательств (нулевые runtime-затраты), runtime — через check. Нет необходимости выбирать между
> «функцией» и «ключевым словом». Ниже — историческая запись.

```yaoxiang
assert(1 + 1 == 2, "math is broken")
```

### Сигнатура типа

Нет отдельной сигнатуры типа — ключевое слово обрабатывается парсером.

### Поведение во время выполнения

Аналогично варианту A.

### Изменения в компиляторе

Требуются изменения в парсере, AST, typecheck, IR gen:

1. Парсер: новый вариант `Expr::Assert`
2. AST: новый узел `Expr::Assert`
3. typecheck: проверка типов аргументов
4. IR gen: генерация `BytecodeInstr::Throw`

### Преимущества

- Позиция в исходном коде известна на этапе компиляции (не зависит от debug info)
- Возможна свёртка констант на этапе компиляции: `assert(true)` → пустая операция, `assert(false)` →
  ошибка компиляции

### Недостатки

| Недостаток                           | Влияние                                                              |
| ------------------------------------ | -------------------------------------------------------------------- |
| Требует изменений парсера            | Введение нового синтаксического узла, увеличение стоимости поддержки |
| Ключевое слово не расширяемо         | Варианты вроде `assert_eq` всё равно требуют функций                 |
| Преимущества CompileTime непрактичны | См. анализ ниже                                                      |

### Сравнение

| Аспект               | Вариант A (функция) | Вариант B (ключевое слово)        |
| -------------------- | ------------------- | --------------------------------- |
| Стоимость реализации | ~20 строк           | парсер + AST + typecheck + IR gen |
| Изменения синтаксиса | Нет                 | Новое ключевое слово              |
| Расширяемость        | Перегрузка функций  | Требуются сопутствующие макросы   |
| Позиция в исходнике  | debug info          | Доступна на этапе компиляции      |
| Свёртка констант     | Требуется проход    | Доступна на этапе компиляции      |
| Runtime-затраты      | Вызов функции       | Минимальные                       |

### Реалистичные ограничения компиляционного анализа

Ключевое преимущество варианта B — компиляционный анализ — требует **прохода свёртки констант**,
чтобы быть эффективным. То есть компилятору нужно вычислить `false` в `assert(false)` на этапе
компиляции, чтобы понять, что это мёртвый код.

В YaoXiang в настоящее время нет прохода свёртки констант. Даже при использовании варианта B,
распространённые случаи вроде `assert(x > 0)` по-прежнему не могут быть проанализированы на этапе
компиляции. Анализу поддаются только литералы вроде `assert(true)` / `assert(false)`.

Следовательно, преимущества варианта B на этапе компиляции **на данном этапе теоретические, а не
практические**.

### 2026-07-05: выбор варианта A (заменено единым решением)

Реализация варианта A в 20 строк победила по соотношению ценности и стоимости. После определения
единого решения 2026-07-12 противоречие между A и B снимается конвейером диспетчеризации — assert —
это вводящий оператор значения для Assert, и больше не нужно выбирать между «функцией» и «ключевым
словом».

### 2026-07-12: определено единое решение (заменяет вывод от 2026-07-11 о «полной независимости»)

**Заключение**: `assert` и `Assert` — не два независимых механизма.
`assert: (Bool) -> Assert(IsTrue(cond))` — диспетчеризация автоматическая:

- Известно на этапе компиляции → попадает в конвейер доказательств (Proved стирается / Disproved —
  ошибка / Unknown — требуется доказательство)
- Runtime-вход → вставляется check + впрыскивание предположения в Γ

**Структура модуля**: `std.assert` единым образом несёт runtime-утверждения (`assert`) и
компиляционные уточняющие типы (`Assert`, `IsTrue`). Больше не «раздельная реализация», а две
стороны одного примитива.

### 2026-07-11: проектирование перегрузок assert

**Вопрос**: Почему `assert` нужны две перегрузки, а не единая `(Bool, ?String)`?

**Ответ**:

Runtime `assert()` — единственный пользовательский механизм panic в YaoXiang. `assert(false, "msg")`
эквивалентно `raise`/`throw` в других языках. Следовательно, он должен покрывать три сценария:

1. Условие + простое сообщение: `assert(cond, "msg")`
2. Условие + пользовательский Error: `assert(cond, my_error)`
3. Проверка Result: `assert(result)` — самая краткая запись для `if is_err { panic }`

Корректность перегрузки Result состоит в том, что это кратчайший путь распространения ошибки —
«Result должен быть Ok, иначе смерть». Не нужно сначала вызывать `.is_ok()`, а затем отдельно
обрабатывать ошибку.
