# RFC-038: Правила завершения операторов и переноса строк

## Резюме

Определяет **правила завершения операторов** в YaoXiang: **перенос строки — основная граница**, а
**закрывающая скобка, бинарный оператор в конце строки, точка `.` в начале строки (цепочечный
перенос)** — явные исключения для продолжения строки; `(` и `[` в начале строки **никогда не
объединяются с предыдущим оператором**. `;` сохраняется как явный разделитель (несколько операторов
в одной строке).

Настоящий RFC также устраняет пробел в спецификации `syntax.md`, где разделитель операторов никогда
не был определён, и исправляет дефект парсера, при котором `(` `[` `.` в начале строки поглощались
как суффикс предыдущего оператора (#258).

## Мотивация

### Зачем нужна эта возможность?

В YaoXiang `;` полностью необязателен (14 вызовов `skip(Semicolon)` в парсере), но **перенос строки
никогда не определялся как граница операторов**: лексер отбрасывает переносы строк, и единственный
критерий границы операторов в парсере — «естественная остановка цикла Pratt выражения», то есть
«может ли следующий токен продолжить выражение». Это приводит к:

1. **Внутреннему противоречию в поведении**: после перевода строки идёт identifier/литерал →
   нормальное завершение; после перевода строки идёт `(` `[` `.` → поглощается как суффикс
   предыдущего выражения (вызов/индексация/доступ к полю)
2. **Молчаливое разрушение легитимных операторов**: деструктуризация `(c, d) = (3, 4)` превращается
   в `1(c, d) = (3, 4)` с вводящей в заблуждение ошибкой E1001; `f()(2)`, `1[99]` не выдают даже
   ошибку — оператор просто исчезает
3. **Пробел в спецификации**: в `syntax.md` §2.9 `Block ::= '{' Stmt* Expr? '}'` не определён
   разделитель между Stmt; в §1.2 таблице разделителей присутствуют только `( ) { } ,`

### Текущие проблемы

| Код в блоке                 | Текущее AST                                      | Результат                              |
| --------------------------- | ------------------------------------------------ | -------------------------------------- |
| `x = 1` ⏎ `(c, d) = (3, 4)` | `Assign x = BinOp(Assign, Call(1,[c,d]), Tuple)` | E1001 указывает на невинный `c`        |
| `x = f()` ⏎ `(2)`           | `Call(Call(f),[2])`                              | **Молча** (оператор исчезает)          |
| `x = 1` ⏎ `[99]`            | `Index(1,99)`                                    | **Молча**                              |
| `x = 1` ⏎ `.println("hi")`  | `Call(Field(1),["hi"])`                          | E1053                                  |
| `x = 1 +` ⏎ `2`             | `BinOp(Add)`                                     | ✅ Легитимно (но без нормативной базы) |
| `x = (1,` ⏎ `2)`            | `Tuple`                                          | ✅ Легитимно (но без нормативной базы) |

## Предложение

### Основной дизайн

**Главное правило: перенос строки завершает оператор.**

**Исключения для продолжения строки (три группы, все с прецедентами в мейнстрим-языках):**

| #   | Исключение                                       | Правило                                                                                | Прецедент    |
| --- | ------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------ |
| 1   | **Незакрытая скобка**                            | Глубина `(` `[` `{` > 0 → перенос не завершает (неявное продолжение)                   | Python/Scala |
| 2   | **Бинарный оператор в конце строки**             | Строка заканчивается бинарным оператором → продолжение                                 | Swift/Scala  |
| 3   | **Цепочечное продолжение с `.` в начале строки** | `.` в начале строки и предыдущая строка заканчивается identifier/`)`/`]` → продолжение | Swift        |

**Никогда не объединять (урок самой известной проблемы JS):**

- `(` и `[` в начале строки → **всегда начинают новый оператор**. Знаменитая ловушка JS (`a\n(b)` →
  вызов `a(b)`) особенно опасна в YaoXiang: деструктуризация кортежей `(a, b) = ...`, spawn,
  литералы кортежей — всё это операторы, начинающиеся со скобок.
- Бинарные/унарные операторы (`+` `-` `*` и т.д.) в начале строки → начинают новый оператор.
  Продолжение через оператор в конце строки покрывает распространённые стили переноса; продолжение
  через оператор в начале строки (лидирующие операторы Scala 3) вносит неоднозначность между
  унарными и инфиксными операторами — не принимается. При необходимости переноса используйте скобки.

**`;` сохраняется**: явный разделитель, используемый для нескольких операторов в одной строке
(аналогично Kotlin/Swift).

### Примеры

```yaoxiang
// Перенос строки завершает оператор (подавляющее большинство кода)
a = 1
b = 2

// Продолжение: бинарный оператор в конце строки
total = a +
    b + c

// Продолжение: незакрытая скобка
t = (1,
     2)
io.println(
    "hi")

// Продолжение: . в начале строки (цепочечный вызов)
result = list.map(x => x * 2)
    .filter(x => x > 10)
    .sum()

// Никогда не объединять: ( в начале строки — независимый оператор деструктуризации
x = f()
(c, d) = (3, 4)      // ✅ деструктуризация, а не f()(c, d)

// Никогда не объединять: [ в начале строки — независимый список
x = 1
[1, 2, 3]            // ✅ независимый оператор-выражение

// Несколько операторов в одной строке: точка с запятой
a = 1; b = 2
```

### Изменения синтаксиса

После `syntax.md` §2.9 добавить:

```
StatementTerminator ::= ';' | Newline        (если не применимо исключение продолжения)
Исключения продолжения (перенос не завершает):
  - Глубина '(' '[' '{' > 0
  - Бинарный оператор в конце строки
  - '.' в начале строки и предыдущая строка заканчивается Identifier | ')' | ']'
Никогда не объединять: '(' '[' в начале строки всегда = новый оператор
```

| До                                                                       | После                                                                                                              |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `Block ::= '{' Stmt* Expr? '}'` (без определения разделителя)            | `Block ::= '{' (Stmt StatementTerminator)* Expr? '}'`                                                              |
| Перенос строки не имеет статуса, `(` `[` `.` в начале строки поглощаются | Перенос строки завершает; `(` `[` в начале строки никогда не объединяются; `.` в начале строки — явное продолжение |
| `;` необязателен, но семантика размыта                                   | `;` = явный разделитель (несколько операторов в строке), после `;` может идти перенос строки                       |

## Детальный дизайн

### Определение завершения оператора (правила парсера)

В цикле Pratt выражений, перед применением постфиксных операторов (вызов `(`, индексация `[`, доступ
к полю `.`):

```
continuation(prev_expr, op_token) =
    строка_окончания(prev_expr) == строка_начала(op_token)        // та же строка: нормальный постфикс
    || (op_token == '.' и prev_expr заканчивается на Identifier/')'/']')  // цепочка с . в начале
    || глубина_скобок > 0                                          // внутри незакрытых скобок
```

Не выполнено → выражение завершается, начинается новый оператор. Бинарные инфиксные операторы не
участвуют в построчной проверке (оператор в конце строки = продолжение, работает естественно).

### Область влияния на синтаксис

- В ветку постфиксных операторов `parse_expression` добавляется проверка номера строки (Span уже
  содержит номер строки, изменения лексера не требуются)
- В местах разбора операторов — логика потребления границ `;` и перевода строки (семантика
  `skip(Semicolon)` сохраняется)
- Закрывающая `}` блока и EOF естественным образом завершают оператор, дополнительной обработки не
  требуется
- **NEWLINE token не вводится** (вариант B, см. альтернативы) — достаточно номеров строк из Span,
  изменения минимальны

### Обратная совместимость

- **Подавляющее большинство существующего кода — без изменений**: строки, начинающиеся с
  identifier/литерала, переносы с оператором в конце строки, переносы внутри скобок — всё совпадает
  с текущим поведением
- **Точки изменения поведения** (все — исправления ошибок):
  - Межстрочное поглощение `f()(2)` / `1[99]` / `1.println()` переходит от «молчание/ошибка» к «два
    независимых оператора» — корректная семантика
  - `.` в начале строки переходит от «поглощение (ошибка)» к «явное цепочечное продолжение» — новая
    возможность
- Риск: если существует легитимный код, зависящий от «межстрочного поглощения» (например, `f()\n(2)`
  с намерением вызвать возвращённую функцию), он станет двумя операторами `f()` + `(2)`. Такой код
  изначально семантически ошибочен или крайне редок — требует подтверждения при ревью RFC

## Компромиссы

### Преимущества

- **Мало правил и интуитивно понятно**: два главных правила + три группы исключений, все из
  проверенной мейнстримом практики
- **Устранение молчаливых ошибок**: `f()(2)`, `1[99]` и т.п. больше не поглощаются молча, границы
  операторов предсказуемы
- **Дружелюбно к цепочечным вызовам**: продолжение с `.` в начале строки соответствует стандарту
  Swift/индустрии
- **Без изменений в лексере**: подход с номерами строк Span минимально инвазивен

### Недостатки

- Продолжение с бинарным оператором в начале строки не поддерживается (стиль Scala 3) — для переноса
  нужны скобки, ограничивает некоторые стили
- Определение продолжения с `.` в начале строки зависит от «предыдущая строка заканчивается на
  identifier/`)`/`]`» — правило требует документирования

## Стратегия реализации

### Зависимости

- Внешних зависимостей нет; связан с #258 (issue реализации настоящего RFC)
- Ортогонален RFC-010 (унифицированный синтаксис типов): завершение операторов — правило уровня
  парсера, не затрагивает грамматику типов

### Риски

- Граница между цепочечным продолжением с `.` в начале строки и «`.` в начале строки как независимый
  оператор»: `.foo()` не может быть самостоятельным оператором (`.` не является допустимым началом
  оператора), поэтому определение продолжения не вносит неоднозначности
- Существующие тесты, зависящие от поведения поглощения, требуют индивидуальной проверки (ожидается
  их отсутствие — сценарии поглощения все являются багами)

## Приложение A: Сравнительное исследование языков

| Язык       | Подход                                                  | `(` в начале строки       | Цепочечный `.`  | Оператор в начале строки     | Оценка                                               |
| ---------- | ------------------------------------------------------- | ------------------------- | --------------- | ---------------------------- | ---------------------------------------------------- |
| Go         | Автоматическая вставка `;` лексером (2 правила)         | ✅ Безопасно              | ❌ Запрещено    | ❌ Запрещено                 | Самый детерминированный, жертвует цепочечным стилем  |
| JavaScript | ASI, 3 правила + restricted productions                 | ❌ **Знаменитая ловушка** | Допустимо       | ⚠️ Ловушка                   | **Негативный пример** (`a\n(b)` → вызов)             |
| Python     | Жёсткая граница NEWLINE + неявное продолжение в скобках | ✅ Безопасно              | ❌ Нужны скобки | ❌ Нужны скобки              | Самый предсказуемый, самое слабое продолжение        |
| Kotlin     | SEMI = `;` или перевод строки                           | ✅ Безопасно              | ✅              | ❌ (ловушка trailing lambda) | Хорошо, но правила скрыты                            |
| Swift      | Перевод строки завершает + правила пробелов             | ✅ Безопасно              | ✅              | ✅ Защита пробелами          | **Ближе всего к настоящему предложению**             |
| Scala 3    | nl token + региональные правила + лидирующие операторы  | ✅                        | ✅              | ✅                           | Самый полный, но самый сложный, избыточно инженерный |

**Настоящее предложение = детерминированность Go × продолжение в скобках Python × цепочечное `.`
Swift**. Swift ближе всего к идеалу; Scala 3 наиболее полон, но правила чрезмерно тяжелы — для
человека важна не максимальная полнота правил, а **малое количество правил, каждое из которых
интуитивно понятно**.
