# RFC-029f: Семантика ролей целей компиляции и поверхности импорта

## Резюме

Реализует продлённый слот расширения RFC-029 «Планирование дочерних RFC» (слоты 029b–029e уже
заняты, далее следует 029f): определяет для исходных файлов **модель ролей целей компиляции** (пять
категорий: Script / Bin / Lib / Test / Internal) и **семантику их поверхности импорта** — при
отсутствии манифеста роль выводится по достижимости из точки входа (нулевая конфигурация), при
наличии манифеста — задаётся явно через `[lib]` / `[[bin]]` / `[exports]` (поля, уже определённые в
RFC-015). Заполняет четыре семантических пробела: по каким правилам считается поверхность
межпакетного импорта, к чему применяется исключение `pub` для предупреждения о мёртвом коде (решение
B по #321), как соотносятся `[exports]` и достижимость Registry, и устраняет терминологическую
неоднозначность между `[binaries]` RFC-014b (предкомпилированные распространяемые артефакты) и ролью
bin для исходных файлов.

## Мотивация

### Опорные документы и граничные условия

RFC-029 (принят), в части выбора точки входа и решения о видимости, является прямым предшественником
данного RFC:

> **Выбор файла точки входа**, приоритет: 1. `[run].main` 2. `path` первого элемента `[[bin]]` 3.
> `src/main.yx` (соглашение по умолчанию). — RFC-029 §Межпакетные циклы: продолжение

> **Видимость**: отсутствует. Область видимости + граница распространения покрывают все сценарии;
> новое ключевое слово не требуется. — RFC-029 §Запись проектных решений (2026-07-30)

Второй пункт — это красная линия данного RFC: семантика поверхности импорта **не должна вводить
новых ключевых слов видимости**; её несут исключительно «границы распространения» (роль файла +
объявленная поверхность экспорта).

Четыре потребителя упёрлись в одну и ту же стену:

| Потребитель                                              | Точка столкновения                                                                                                                                                                                                                                |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 Предупреждение о мёртвом коде                       | Решение B «`pub` = внешний интерфейс, никогда не сообщать» обусловлено отсутствием модели ролей, разделяющей «действительно внешний» и «лишь выглядящий внешним»; вопрос, сообщать ли о неиспользуемом `pub` в bin (вариант A), остаётся открытым |
| RFC-014c Рабочие пространства (на рассмотрении, #113)    | При взаимном `use` пакетов-членов по чему считается поверхность импорта — по `[exports]`, по единственному файлу `[lib]`, или по всем файлам с `pub` — **ни одного семантического пункта во всём тексте нет**                                     |
| RFC-015 Система конфигурации (принят)                    | Поля `[lib]` / `[[bin]]` / `[exports]` определены; кроме потреблённого RFC-029 приоритета точки входа, семантика остальных полей (особенно соотношение `[exports]` и достижимости Registry) нигде не согласована                                  |
| RFC-037 Упаковка / RFC-029a Кэширование (черновик, #293) | Выбор артефактов упаковки и граница единиц инкрементальной перекомпиляции требуют модели ролей в качестве предпосылки                                                                                                                             |

### Текущая проблема

**Четыре семантических пробела** (по состоянию на 2026-09-12, проверено сплошным просмотром
014/014a/014b/014c/015/029):

1. **Межпакетная поверхность импорта не определена**. В примере взаимного импорта пакетов-членов в
   014c указана только структура каталогов (`src/lib.yx`); что именно получает `use utils.helper` —
   никаких положений нет. Текущее неявное правило — «все файлы верхнего уровня с `pub` в пакете» —
   внутренние файлы реализации тоже втягиваются в пространство имён, и граница зависимостей
   превращается в фикцию.
2. **Нет области применения исключения `pub` для мёртвого кода**. «`pub` никогда не сообщается» из
   решения B по #321 слишком консервативно для однофайлового скрипта (у скрипта нет внешних
   потребителей, `pub` бессмысленен) и слишком либерально для файла точки входа в многофайловом
   проекте (если никто не импортирует `pub` корневого файла — это мёртвый код). Без модели ролей
   линия раздела между вариантами A и B не провести.
3. **Три концепции экспорта нигде не согласованы**. `[exports]` (015, отображение путей), `[lib]`
   (015, путь к одному файлу), достижимость Registry (029, достижимо из входа по `use`) — между ними
   отношения включения, равенства или независимости — никаких положений нет.
4. **Столкновение терминов**. `[binaries]` из RFC-014b — это **предкомпилированные распространяемые
   артефакты** (стратегия приоритета скачивания .so/exe), а «цель bin (роль исходного кода)» —
   совершенно другой уровень. После введения 014c они неизбежно появятся на одном экране; без
   скорейшего устранения неоднозначности недопонимание будет накапливаться.

**Эмпирическое подтверждение: консерватизм решения B — уже реальная боль**. Запись ретроспективы M2
по #321: структурная причина молчания всей группы W1001–W1005 в конфигурации по умолчанию именно в
том, что «все `pub` считаются внешним интерфейсом» — это компенсирующее поведение из-за отсутствия
модели, а не финальное состояние.

## Предложение

### Основная идея: модель ролей файлов

**Роль — атрибут уровня файла** (та же гранулярность, что и у полей в 015: `[lib]` — один файл,
`[[bin]]` — список файлов, `[exports]` — отображение файлов), а не переключатель уровня пакета.

| Роль         | Определение                                                                                                                                                        | Семантика                                                                                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bin**      | Файл, на который указывает `[run].main` / `[[bin]].path`; либо (при отсутствии манифеста) файл, содержащий `main` и не используемый (`use`) ни одним другим файлом | Точка входа программы. Его `pub` **может быть сообщён как мёртвый код** (нет потребителей за пределами пакета); `main` — корень достижимости                                                         |
| **Lib**      | Файл, попавший в отображение `[exports]`; либо `[lib].path`; либо (при отсутствии манифеста) файл, на который ссылается `use` из другого файла                     | Граница распространения. Его `pub` **исключён из предупреждения о мёртвом коде** (внешние потребители пакета невидимы, лучше недосообщить); символы, экспортируемые через него, видны между пакетами |
| **Test**     | Файл, удовлетворяющий правилам RFC-036 для тестовых файлов (каталог `tests/`, соглашения типа `*_test.yx` и т. п.); явное объявление `[[test]]` **не вводится**    | Тестовый код. Не участвует в анализе мёртвого кода; его ссылки считаются корнями достижимости для тестируемого кода                                                                                  |
| **Internal** | При наличии манифеста в пакете: файл, не попавший в поверхность экспорта и не содержащий `main`                                                                    | Внутрипакетная реализация. `pub` исключён до второй фазы (ужесточение по достижимости в графе `use` внутри пакета, при условии валидации на корпусе роли Bin); `use` извне пакета **недостижим**     |
| **Script**   | Файл, запускаемый напрямую как одиночный (`run foo.yx`)                                                                                                            | Поведение полностью совпадает с сегодняшним: Registry содержит только std, без изменений семантики `pub` для мёртвого кода                                                                           |

**Приоритет определения**: явное объявление в манифесте > вывод по достижимости из входа >
соглашения RFC-036 для тестов. Явное объявление всегда побеждает — вывод служит только умолчанием
при отсутствии объявления.

### Пример

```toml
# yaoxiang.toml (все поля уже определены в RFC-015; данный RFC не вводит новых конфигурационных поверхностей)
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← межпакетную видимость определяет именно оно, а не pub
```

```yaoxiang
# src/cli.yx (роль Bin)
pub unused_fn = (x: Int) => x    # ← можно сообщить W1001: у bin нет внешних потребителей
main: () -> Void = { ... }

# src/lib.yx (роль Lib, на поверхности экспорта)
pub api_fn = ...                 # ← никогда не сообщается: внешние потребители пакета невидимы

# src/other.yx (роль Internal, не на поверхности экспорта)
pub semi_api = ...               # ← исключён до второй фазы (лучше недосообщить); тогда ужесточение по графу use
```

### Семантика поверхности импорта

Порядок разрешения межпакетного `use pkg.x` (первое совпадение вступает в силу):

1. Отображение `[exports]` существует → поверхность импорта = множество файлов, перечисленных в
   отображении; `x` должен быть среди связываний верхнего уровня этих файлов;
2. Иначе существует `[lib].path` → поверхность импорта = этот единственный файл;
3. Ни того, ни другого (зависимость без манифеста, путь к голому каталогу) → **сохраняется текущее
   поведение**: импортируемы все файлы верхнего уровня (совместимость с существующим поведением,
   ужесточение — отдельный вопрос).

**Члены рабочего пространства**: поверхность экспорта определяется только собственным манифестом
пакета-члена; корень workspace не может переопределять или расширять поверхность экспорта членов —
самодостаточность членов является ключевым замыслом 014c, и переопределение на уровне корня
разрушило бы инкапсуляцию.

Соотношение с достижимостью Registry (согласовано с 029): `[exports]` / `[lib]` определяют
**множество допустимых точек отсчёта для межпакетного разрешения**; после определения точек отсчёта
Registry по-прежнему расширяется по правилу 029 «достижимо из входа по `use`» — внутренние файлы,
которые сами экспортируемые файлы подтянули через `use`, попадают в линковку, но новых межпакетных
точек отсчёта не порождают.

### Разграничение с существующими планами

| Сосед                                                                   | Граница                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-029d «CLI `--entry` — переопределение точки входа» (в планировании) | 029f определяет модель ролей; 029d потребляет её — `--entry` является средством переопределения роли Bin на уровне CLI                                                                                                                                                      |
| RFC-014b `[binaries]`                                                   | **Устранение неоднозначности**: `[binaries]` — предкомпилированные распространяемые артефакты (стратегия скачивания), `[[bin]]` — объявление роли исходного кода. Первое существует в манифесте зависимого пакета, второе — в манифесте текущего пакета; не взаимозаменяемы |
| RFC-014c Рабочие пространства                                           | Поверхность импорта при взаимном цитировании пакетов-членов = порядок разрешения из данного RFC; механизмы координации workspace (members, общий lockfile) остаются за 014c                                                                                                 |
| RFC-036 Тестирование                                                    | Определение роли Test напрямую использует существующие файловые правила 036, новых соглашений не добавляется                                                                                                                                                                |
| #321 Мёртвый код                                                        | Решение B (`pub` всегда исключён) явно понижается до «переходной семантики при отсутствии target»; возможность сообщать о `pub` в роли Bin — это форма реализации варианта A из #321 в данном RFC                                                                           |

## Детальная разработка

### Алгоритм определения роли (внутри оркестратора)

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. Явный слой: приоритет у объявлений в манифесте
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. Слой вывода: где нет объявления — по достижимости из входа
    for f in files where role[f] не определена:
        if f используется (use) ≥ 1 другим файлом:  role[f] = Lib
        elif f содержит main и никакой другой файл его не use-ит: role[f] = Bin
        else:                             role[f] = Internal

    # 3. Слой тестов: срабатывание правил 036 → Test (перекрывает Lib/Internal, но не явный Bin)
    apply_rfc036_test_rules(files, &role)

    # Однофайловый прямой запуск: вся модель обходится, поведение не меняется
    if no manifest and single_file:      all Script
```

### Изменения в компиляторе

- `frontend/config.rs`: разбор манифеста дополняется отображением `[exports]` → таблица ролей
  (разбор полей уже есть в 015).
- `frontend/module/orchestrator.rs`: перед построением Registry вставляется этап классификации
  ролей; межпакетное разрешение проверяет цель `use` согласно порядку поверхности импорта, при
  выходе за границу выдаётся ошибка из существующего семейства `module_not_found` (новые коды ошибок
  не вводятся, к сообщению добавляется подсказка «не на поверхности экспорта»).
- `typecheck/passes/dead_code.rs`: множество точек входа изменяется с «`main` + все `pub`» на
  «`main` + `pub` файлов с ролью Lib» (Bin сообщается немедленно; Internal исключён до второй фазы,
  см. Phase 2 в стратегии реализации).
- LSP (RFC-017): в автодополнении/наведении «импортируемые сущности» фильтруются по поверхности
  импорта; диагностика об отсутствии `main` выдаётся только для файлов с ролью Bin.

### Поведение во время выполнения

Без изменений. Модель ролей — чисто компиляционная/разборная семантика, не затрагивает IR и
исполнение.

### Обратная совместимость

- Проекты без манифеста: поведение полностью не меняется (слой вывода воспроизводит статус-кво —
  используемый другими — Lib, содержащий `main` — Bin). Приращение предупреждений о мёртвом коде
  только в файлах Bin: неиспользуемый `pub` корневого файла, который никто не импортирует, из тишины
  переходит в W1001 — это ожидаемое поведение варианта A из #321, а не регрессия.
- Проекты с манифестом: при объявленном `[exports]` поверхность импорта сужается с «всех
  `pub`-файлов» до объявленной поверхности. **Это единственная точка сужения поведения**: код,
  зависящий от внутренних файлов чужого пакета, начнёт получать `module_not_found`. Учитывая, что
  экосистема пакетов ещё не сложилась (029: «в настоящее время экосистемы сторонних пакетов нет»),
  поверхность разрушения нулевая; тем не менее устанавливается переходный период в один минорный
  релиз (сначала предупреждение, затем ошибка при выходе за границу).

## Компромиссы

### Преимущества

- Нулевая новая конфигурационная поверхность: все поля уже определены в 015, данный RFC лишь
  дополняет семантику.
- Нулевое новое ключевое слово: поверхность импорта несут границы распространения, что изоморфно
  решению 029 «видимость не существует».
- Четыре потребителя (#321 / 014c / 029a / 037) моделируются за один раз, и каждый перестаёт
  упираться в свою стену.
- Путь без манифеста — с нулевой стоимостью: генотип «нулевая конфигурация» скриптового языка
  сохранён целиком.

### Недостатки

- Вывод роли (используемый другими = Lib) в распространённой форме «файл точки входа `use`-ит
  утилитарный файл» оценит утилитарный файл как Lib, и его `pub` будет исключён — гранулярность шире
  идеальной. Это намеренный выбор в направлении «лучше недосообщить»; ужесточение требует анализа
  направления вызовов в графе `use`, который в первой версии не выполняется.
- Сужение поверхности импорта через `[exports]` — это семантическое ужесточение с эффектом
  разрушения (несмотря на переходный период).

## Стратегия реализации

### По фазам

- **Phase 1**: классификация ролей + разрешение поверхности импорта + возможность сообщать о `pub` в
  Bin (Internal/Test остаются исключёнными)
- **Phase 2**: ужесточение `pub` в Internal до «сообщать, если недостижимо в графе `use` внутри
  пакета» — предусловием является подтверждение отсутствия ложных срабатываний на корпусе
  предупреждений роли Bin после внедрения Phase 1; триггером служит сама валидация, без расписания

### Зависимости

- Предпосылки: оркестратор RFC-029 (уже реализован), поля манифеста RFC-015 (уже определены).
- Зависимые: #321 (сообщение о `pub` в Bin), RFC-014c (поверхность импорта), RFC-029a (роль как
  граница единиц кэширования), RFC-037 (выбор артефактов), RFC-029d (переопределение `--entry`).
- Порядок внедрения с RFC-014c: до одобрения 014c порядок разрешения поверхности импорта из 029f
  должен быть зафиксирован, а 014c потребляет его по ссылке, чтобы не расширять область в ходе
  рассмотрения.

### Риски

- Расхождение вывода роли с интуицией пользователя (первый пункт компромиссов выше) → всё приращение
  поведения представляется в форме предупреждений (без блокировки), с возможностью отключения.
- Управление переходным периодом сужения `[exports]` → в минорном релизе сначала предупреждение.

## Открытые вопросы

Все три вопроса черновика решены (2026-09-13, решения внесены в Приложение B и в основной текст),
нерешённых нет:

- [x] Ужесточать ли `pub` в Internal → **Решение**: во второй фазе ужесточить по достижимости в
      графе `use` внутри пакета, при условии валидации на корпусе роли Bin (см. Phase 2 стратегии
      реализации)
- [x] Явное объявление `[[test]]` → **Решение**: не вводить; роль Test определяется только правилами
      036; если у 036 в будущем возникнет потребность в явном объявлении, она расширит себя сама
- [x] Переопределение поверхности экспорта членов на уровне корня workspace → **Решение**: не
      допускается; самодостаточность членов — ключевой замысел 014c, переопределение на уровне корня
      разрушает инкапсуляцию

## Приложение B: Запись проектных решений

> **Опечатка (2026-09-17): модель ролей управляет семантикой точки входа**
>
> Данный RFC определяет пять ролей и значение «кто является точкой входа» (строка Bin «`main` —
> корень достижимости»), однако первоначальная реализация использовала роли только для
> **предупреждений о мёртвом коде**, и поиск точки входа оставался независимым от ролей — если
> `find_entry_point` не находил `main`, он возвращал 0 и **молча исполнял первую функцию из таблицы
> функций**. Рефакторинг привязок верхнего уровня (T4) подключил модель ролей к определению точки
> входа, конкретные правила таковы:
>
> | Роль                       | Правило точки входа                                                                                                                                                                                                                  |
> | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
> | **Script** (без манифеста) | **Понятия точки входа нет**. Операторы верхнего уровня (включая инициализацию привязок) в порядке написания составляют тело программы; `main` — обычная привязка, **не вызывается автоматически** — чтобы выполнить, пишите `main()` |
> | **Bin** (с манифестом)     | Требуется `main`, причём это должна быть функция; иначе ошибка компиляции (E3020 — нет main / E3021 — main не функция). На верхнем уровне не должно быть исполняемых операторов                                                      |
> | **Lib / Internal / Test**  | `main` не требуется (это не точки входа)                                                                                                                                                                                             |
>
> **Два расхождения с первоначальным описанием в данном RFC**:
>
> 1. В первоначальной строке Script написано «поведение полностью совпадает с сегодняшним».
>    Сегодняшнее поведение содержит два скрытых дефекта, оба исправлены в T4: ① при отсутствии
>    `main` исполняется первая функция из таблицы функций; ② операторы верхнего уровня дают E3005
>    «неисполняемое». Теперь в Script операторы верхнего уровня **исполняемы** — это новая
>    возможность, а не сохранение статус-кво.
> 2. «`main` не особенный в Script» и «`main` — точка входа в Bin» должны быть
>    **взаимоисключающими**: если Script и исполняет операторы верхнего уровня, и неявно вызывает
>    `main`, скрипт с явным `main()` выполнится дважды (#356). Поэтому в Script есть только одна
>    точка выполнения — операторы верхнего уровня.
>
> **Различие между определением роли и определением точки входа** (заметка о реализации): для
> определения точки входа используется «наличие манифеста» (`find_project_root().is_some()`), а не
> `roles::classify()`. Причина: `classify` отвечает на вопрос «кто потребляет этот файл» (для
> анализа мёртвого кода); файл с манифестом, но без `main`, в `classify` получает роль Internal (его
> не `use`-ит ни один файл, что логично), но пользователь запускает его как точку входа — и тогда
> точка входа обязана быть. Это два разных вопроса, и критерии у них разные.
>
> Подробнее см. `docs/src/reference/language-spec/syntax.md` §3.11.

## Приложение C: Глоссарий

| Термин                               | Определение                                                                                                                   |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Роль (Role)                          | Идентификатор цели компиляции исходного файла: Script / Bin / Lib / Test / Internal                                           |
| Поверхность импорта (Import Surface) | Множество файлов — допустимых точек отсчёта для межпакетного `use`; задаётся объявлениями `[exports]` / `[lib]` или выводится |
| Граница распространения              | Термин из 029: диапазон внешней экспозиции пакета; в данном RFC уточнён от неявной (все файлы с `pub`) до поверхности импорта |
| Состояние Script                     | Обходная форма прямого запуска одиночного файла без манифеста; всё поведение совпадает с текущим                              |
