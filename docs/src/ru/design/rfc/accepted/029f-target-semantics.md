# RFC-029f: Роли целей компиляции и семантика поверхности импорта

## Резюме

Реализация дополнительного слота расширения (029b–029e заняты, продолжение 029f) для RFC-029
«Планирование под-RFC»: определение **модели ролей целей компиляции** (пять категорий: Script / Bin
/ Lib / Test / Internal) и **семантики их поверхности импорта** для исходных файлов — при отсутствии
manifest вывод на основе достижимости точки входа (нулевая конфигурация), при наличии manifest —
явное объявление через `[lib]` / `[[bin]]` / `[exports]` (поля, уже определённые в RFC-015).
Заполнение четырёх пробелов в семантике: по каким правилам вычисляется поверхность межпакетного
импорта, область применения исключения `pub` для предупреждений о мёртвом коде (дело #321, решение
B), связь между `[exports]` и достижимостью Registry, а также устранение омонимии терминов между
`[binaries]` из RFC-014b (предкомпилированные артефакты распространения) и bin-ролью исходных
файлов.

## Мотивация

### Предпосылки и границы

Решения о выборе точки входа и видимости в RFC-029 (принят) являются прямым восходящим документом
для настоящего RFC:

> **Приоритет выбора файла входа**: 1. `[run].main` 2. `path` первой записи `[[bin]]` 3.
> `src/main.yx` (соглашение по умолчанию). — RFC-029 §Межпакетные циклы: продолжение

> **Видимость**: не существует. Область видимости + граница распространения покрывают все сценарии,
> новое ключевое слово не требуется. — RFC-029 §Протокол проектных решений (2026-07-30)

Второй пункт является красной линией настоящего RFC: семантика поверхности импорта **не должна
вводить новые ключевые слова видимости** и может опираться только на «границу распространения» (роль
файла + объявленная поверхность экспорта).

Четыре потребителя столкнулись с одной и той же стеной:

| Потребитель                                           | Точка столкновения                                                                                                                                                                                                                                                          |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 предупреждения о мёртвом коде                    | Решение B «`pub` = всегда экспортный интерфейс без предупреждений» принято потому, что нет модели ролей, различающей «истинно экспортный» и «выглядящий экспортным»; вопрос о том, сообщать ли о неиспользуемом `pub` внутри bin (вариант A), остаётся открытым по сей день |
| RFC-014c рабочее пространство (на рассмотрении, #113) | Когда пакеты-члены выполняют взаимный `use`, по каким правилам вычисляется поверхность импорта — `[exports]`, единственный файл `[lib]` или все `pub`-файлы — **ни одного семантического положения во всём тексте**                                                         |
| RFC-015 система конфигурации (принят)                 | Поля `[lib]` / `[[bin]]` / `[exports]` определены; за исключением приоритета точки входа, который используется в RFC-029, семантика остальных полей (особенно связь `[exports]` с достижимостью Registry) никем не согласована                                              |
| RFC-037 упаковка / RFC-029a кэш (черновик, #293)      | Выбор артефактов для упаковки, границы единиц кэширования для инкрементальной перекомпиляции — всё требует модели ролей как предпосылки                                                                                                                                     |

### Текущая проблема

**Четыре семантических пробела** (по состоянию на 2026-09-12, проверено по полным текстам
014/014a/014b/014c/015/029):

1. **Поверхность межпакетного импорта не определена**. Пример взаимного импорта пакетов-членов в
   014c содержит только структуру каталогов (`src/lib.yx`); о том, что именно доступно через
   `use utils.helper`, нет ни одного положения. Текущее неявное правило — «все `pub`-файлы верхнего
   уровня пакета» — внутренние файлы реализации также втягиваются в пространство имён, и граница
   зависимостей становится номинальной.
2. **Нет области применения исключения `pub` для мёртвого кода**. Решение B из #321 «`pub` всегда
   без предупреждений» чрезмерно консервативно для однофайлового скрипта (у скрипта нет внешних
   потребителей, `pub` бессмыслен), но чрезмерно либерально для файла входа в многофайловом проекте
   (неиспользуемый `pub` корневого файла без импортирующих — это мёртвый код). Без модели ролей
   границу между вариантами A и B провести невозможно.
3. **Три концепции экспорта не согласованы**. `[exports]` (015, отображение путей), `[lib]` (015,
   путь к одному файлу), достижимость Registry (029, от точки входа по `use`) — находятся ли они в
   отношении включения, равенства или каждая отвечает за своё, нигде не определено.
4. **Омонимия терминов**. `[binaries]` в RFC-014b — это **предкомпилированные артефакты
   распространения** (стратегия приоритета загрузки .so/exe), что полностью отличается от «bin-цели
   (роли исходного кода)». После внедрения 014c они неизбежно окажутся на одном экране, и без
   раннего устранения омонимии будут постоянно возникать недоразумения.

**Эмпирическое подтверждение: консервативность решения B — уже фактическая болезненная точка**. Из
ретроспективы #321 M2: структурной причиной того, что вся группа W1001–W1005 по умолчанию молчит,
является именно трактовка «все `pub` считаются экспортным интерфейсом» — это компенсирующее
поведение из-за отсутствия модели, а не финальное состояние.

## Предложение

### Основное проектирование: модель ролей файлов

**Роль — это атрибут уровня файла** (согласуется с гранулярностью полей 015: `[lib]` — один файл,
`[[bin]]` — список файлов, `[exports]` — отображение файлов), а не переключатель уровня пакета.

| Роль         | Определение                                                                                                                                                        | Семантика                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bin**      | Файл, на который указывает `[run].main` / `[[bin]].path`; или (при отсутствии manifest) файл, содержащий `main` и не используемый (`use`) ни в одном другом файле  | Точка входа программы. Требуется наличие **привязки** с именем `main` (значение или функция — обе формы допустимы): функция `main` вызывается с нулевыми аргументами в момент входа, значение `main` вычисляется в момент инициализации (результат вычисления, даже если это функциональное значение, более не вызывается). Отсутствие `main` — ошибка компиляции (E3020); исполняемые инструкции верхнего уровня запрещены. Её `pub` **может вызывать предупреждения о мёртвом коде** (нет внешних потребителей пакета); `main` — корень достижимости |
| **Lib**      | Файл, попавший в отображение `[exports]`; или `[lib].path`; или (при отсутствии manifest) файл, на который ссылается `use` из другого файла                        | Граница распространения. Её `pub` **освобождён от предупреждений о мёртвом коде** (внешние потребители пакета невидимы, лучше недосообщить); символы, экспортируемые через неё, видны между пакетами                                                                                                                                                                                                                                                                                                                                                   |
| **Test**     | Файл, удовлетворяющий правилам тестовых файлов RFC-036 (каталог `tests/`, `*_test.yx` и т.п. существующие соглашения); **не вводится** явное объявление `[[test]]` | Код тестов. Не участвует в анализе мёртвого кода; его ссылки считаются корнями достижимости для тестируемого кода                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Internal** | При наличии manifest в пакете: файл, не входящий в поверхность экспорта и не содержащий `main`                                                                     | Внутренняя реализация пакета. `pub` освобождён до второго этапа (ужесточение по достижимости на графе `use` внутри пакета, с предварительной валидацией на корпусе роли Bin); `use` извне пакета **недостижим**                                                                                                                                                                                                                                                                                                                                        |
| **Script**   | Файл при прямом запуске одного файла (`run foo.yx`)                                                                                                                | **Нет концепции точки входа**. Инструкции верхнего уровня (включая инициализацию привязок) выполняются в порядке записи как тело программы; `main` — обычная привязка, **не вызывается автоматически** — чтобы запустить, пишите `main()`. Registry содержит только std                                                                                                                                                                                                                                                                                |

**Приоритет определения**: явное объявление в manifest > вывод на основе достижимости точки входа >
соглашения о тестах 036. Явное объявление всегда побеждает — вывод лишь замена по умолчанию при
отсутствии объявления.

### Определение точки входа

Модель ролей используется не только для анализа мёртвого кода, но и **управляет определением точки
входа**. Правила входа для каждой роли:

| Роль                      | Правило точки входа                                                                                                                                                                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Script** (без manifest) | **Нет концепции точки входа**. Инструкции верхнего уровня (включая инициализацию привязок) выполняются в порядке записи как тело программы; `main` — обычная привязка, **не вызывается автоматически** — чтобы запустить, пишите `main()`                                                               |
| **Bin** (с manifest)      | Требуется наличие **привязки** с именем `main` (значение/функция — обе допустимы: значение `main` вычисляется в момент инициализации, функция `main` вызывается с нулевыми аргументами в момент входа); отсутствие `main` — ошибка компиляции (E3020). Исполняемые инструкции верхнего уровня запрещены |
| **Lib / Internal / Test** | Не требуют `main` (они не являются точками входа)                                                                                                                                                                                                                                                       |

**Script и Bin должны быть взаимоисключающими по точке входа**: «в Script `main` не особенный» и «в
Bin `main` — точка входа» не могут действовать одновременно — если Script выполняет и инструкции
верхнего уровня, и неявно вызывает `main`, скрипт с явным `main()` будет запущен дважды (#356).
Поэтому Script имеет только одну точку выполнения: инструкции верхнего уровня.

**Различие между определением роли и определением точки входа** (замечание по реализации): для
определения точки входа используется «наличие manifest» (`find_project_root().is_some()`), а не
`roles::classify()`. Причина: `classify` отвечает на вопрос «кто потребляет этот файл» (служит для
анализа мёртвого кода); файл с manifest, но без `main`, в `classify` получает роль Internal (его не
`use`ят другие файлы, логично), но если пользователь запускает его как точку входа, точка входа
должна быть. Это два разных вопроса — разные и критерии.

**Форма выполнения значения `main`** (решение #388): функция уже является значением (единообразно на
уровне типов), вход определяется по **наличию привязки**, а не по вызываемости — различие между
значением `main` и функцией `main` лишь в стратегии вычисления. Для значения `main` входной вызов не
устанавливается (защита от двойного запуска #356: инициализация и входной вызов никогда не
складываются), что совпадает с формой выполнения Script; его вычисление — часть последовательности
инициализации: выполнение в топологическом порядке глобальных привязок, независимые привязки — в
порядке исходного кода. Поэтому перенос Script-инструкций верхнего уровня в `main = { ... }` при
миграции в Bin **не является миграцией с сохранением порядка** — разрозненные инструкции выполняются
в порядке записи, инициализация привязок — в топологическом порядке; инициализация, которая должна
произойти первой, должна явно зависеть от `main`. `main: Int = 5` и подобные невызываемые значения
`main` — допустимая, но не имеющая наблюдаемых эффектов программа (аналог пустой `fn main() {}` в
Rust).

См. `docs/src/reference/language-spec/syntax.md` §3.11.

### Пример

```toml
# yaoxiang.toml (все поля уже определены в RFC-015, настоящий RFC не вводит новых конфигурационных поверхностей)
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← межпакетную видимость определяет именно это, а не pub
```

```yaoxiang
# src/cli.yx (роль Bin)
pub unused_fn = (x: Int) => x    # ← W1001 может сработать: у bin нет внешних потребителей
main: () -> Void = { ... }

# src/lib.yx (роль Lib, на поверхности экспорта)
pub api_fn = ...                 # ← никогда не сообщается: внешние потребители пакета невидимы

# src/other.yx (роль Internal, не на поверхности экспорта)
pub semi_api = ...               # ← освобождён до второго этапа (лучше недосообщить), тогда ужесточение по графу use
```

### Семантика поверхности импорта

Порядок разрешения межпакетного `use pkg.x` (первое совпадение вступает в силу):

1. Отображение `[exports]` существует → поверхность импорта = множество файлов, перечисленных в
   отображении, `x` должен быть среди привязок верхнего уровня этих файлов;
2. Иначе существует `[lib].path` → поверхность импорта = этот единственный файл;
3. Если ничего нет (зависимость без manifest, голый путь к каталогу как зависимость) → **сохранить
   статус-кво**: все файлы верхнего уровня импортируемы (совместимо с существующим поведением,
   ужесточение — отдельный вопрос).

**Пакеты-члены рабочего пространства**: поверхность экспорта определяется только manifest самого
пакета-члена; корень рабочего пространства не может перекрывать или расширять поверхность экспорта
членов — самодостаточность членов — ключевое проектное решение 014c, перекрытие из корня разрушило
бы инкапсуляцию.

Связь с достижимостью Registry (согласовано с 029): `[exports]`/`[lib]` определяют **множество
допустимых начальных точек для межпакетного разрешения**; после определения начальной точки Registry
по-прежнему расширяется по правилу 029 «от точки входа по `use` достижимо» — внутренние файлы,
которые сами экспортируемые файлы `use`ят, попадают в связывание, но не порождают новых межпакетных
начальных точек.

## Детальное проектирование

### Алгоритм определения роли (внутри оркестратора)

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. 显式层：manifest 声明优先
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. 推断层：无声明处按入口可达性
    for f in files where role[f] 未定:
        if f 被 ≥1 个非自身文件 use:      role[f] = Lib
        elif f 含 main 且无其他文件 use 它: role[f] = Bin
        else:                             role[f] = Internal

    # 3. 测试层：036 规则命中 → Test（覆盖 Lib/Internal，不覆盖显式 Bin）
    apply_rfc036_test_rules(files, &role)

    # 单文件直跑：整个模型旁路，行为不变
    if no manifest and single_file:      all Script
```

### Изменения в компиляторе

- `frontend/config.rs`: разбор manifest дополняется отображением `[exports]` → таблица ролей (разбор
  полей уже есть в 015).
- `frontend/module/orchestrator.rs`: перед построением Registry вставляется этап классификации
  ролей; межпакетное разрешение проверяет цель `use` по порядку поверхности импорта, при нарушении
  границы выдаётся существующее семейство `module_not_found` (новые коды ошибок не вводятся,
  сообщение дополняется подсказкой «не на поверхности экспорта»).
- `typecheck/passes/dead_code.rs`: множество точек входа изменяется с «main + все pub» на «main +
  pub файлов с ролью Lib» (Bin сообщает немедленно; Internal освобождён до второго этапа, фаза 2 —
  см. стратегию реализации).
- LSP (RFC-017): «импортируемые элементы» в автодополнении/наведении фильтруются по поверхности
  импорта; диагностика отсутствия `main` выдаётся только для файлов с ролью Bin.

### Поведение во время выполнения

Без изменений. Модель ролей — это чисто компиляционная/разборная семантика, не влияющая на IR и
выполнение.

### Обратная совместимость

- Проекты без manifest: поведение полностью не меняется (слой вывода воспроизводит статус-кво —
  используемый другими — Lib, содержащий main — Bin). Приращение предупреждений о мёртвом коде
  только в файлах Bin: неиспользуемый `pub` корневого файла без импортирующих меняется с молчания на
  W1001 — это ожидаемое поведение варианта A из #321, не поломка.
- Проекты с manifest: для тех, где `[exports]` объявлен, поверхность импорта сужается с «всех
  `pub`-файлов» до объявленной поверхности. **Это единственная точка сужения поведения**: код,
  зависящий от внутренних файлов чужого пакета, начнёт получать `module_not_found`. Учитывая, что
  экосистема пакетов ещё не сложилась (029: «в настоящее время экосистемы сторонних пакетов нет»),
  площадь поломки равна нулю; всё же устанавливается переходный период в один минорный релиз
  (сначала предупреждение, затем ошибка при выходе за границу).

## Компромиссы

### Преимущества

- Ноль новых конфигурационных поверхностей: все поля уже определены в 015, настоящий RFC лишь
  дополняет семантику.
- Ноль новых ключевых слов: поверхность импорта несёт граница распространения, что изоморфно решению
  029 «видимость не существует».
- Четыре потребителя (#321 / 014c / 029a / 037) моделируются за один раз, и больше не упираются
  каждый в свою стену.
- Путь без manifest — нулевая стоимость: ген нулевой конфигурации скриптового языка полностью
  сохранён.

### Недостатки

- Вывод ролей (используемый `use` → Lib) в распространённой форме «файл входа `use`ит утилитарный
  файл» классифицирует утилитарный файл как Lib, и его `pub` освобождается — крупнее идеальной
  гранулярности. Это намеренный выбор в направлении «лучше недосообщить», ужесточение требует
  анализа направления вызовов на графе `use`, в первой версии не делается.
- Сужение поверхности импорта через `[exports]` — семантическое ужесточение с разрушительным
  потенциалом (хотя и с переходным периодом).

## Стратегия реализации

### Поэтапность

- **Фаза 1**: классификация ролей + разрешение поверхности импорта + сообщение о `pub` в Bin
  (Internal/Test остаются освобождёнными)
- **Фаза 2**: ужесточение `pub` в Internal до «недостижим на графе `use` внутри пакета — можно
  сообщать» — предварительное условие: после внедрения фазы 1 валидация на корпусе предупреждений
  роли Bin не выявит ложных срабатываний; запуск по факту готовности, без расписания

### Зависимости

- Предпосылки: оркестратор RFC-029 (внедрён), поля manifest RFC-015 (определены).
- Зависимые: #321 (сообщение о `pub` в Bin), RFC-014c (поверхность импорта), RFC-029a (роль как
  граница единицы кэширования), RFC-037 (выбор артефактов), RFC-029d (переопределение через
  `--entry`).
- Порядок внедрения с RFC-014c: до утверждения 014c порядок поверхности импорта в 029f должен быть
  финализирован, 014c потребляет его по ссылке, чтобы избежать расширения объёма в процессе
  рассмотрения.

### Риски

- Расхождение вывода ролей с интуицией пользователя (первый пункт компромиссов выше) → всё
  инкрементальное поведение представляется в форме предупреждений (не блокирующих), возможно
  отключение.
- Управление переходным периодом сужения `[exports]` → в одном минорном релизе сначала
  предупреждение.

## Открытые вопросы

Все три пункта стадии черновика решены (2026-09-13, решения внесены в Приложение B и основной
текст), нерешённых нет:

- [x] Ужесточать ли `pub` в Internal → **Решение**: на втором этапе ужесточение по достижимости на
      графе `use` внутри пакета, с предварительной валидацией на корпусе роли Bin (см. фазу 2
      стратегии реализации)
- [x] Явное объявление `[[test]]` → **Решение**: не вводится, роль Test определяется только
      правилами 036; если у 036 в будущем возникнет потребность в явном объявлении, она расширит
      себя сама
- [x] Перекрытие поверхности экспорта членов из корня рабочего пространства → **Решение**: не
      допускается, самодостаточность членов — ключевое проектное решение 014c, перекрытие из корня
      разрушило бы инкапсуляцию
