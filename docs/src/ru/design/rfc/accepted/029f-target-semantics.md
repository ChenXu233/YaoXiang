# RFC-029f: Целевые роли компиляции и семантика поверхности импорта

## Резюме

Реализует расширенный слот (029b–029e заняты, далее 029f) из RFC-029 «Планирование под-RFC»:
определяет **модель ролей целей компиляции** (Script / Bin / Lib / Test / Internal — пять категорий)
и **семантику поверхности импорта** для исходных файлов — при отсутствии manifest вывод по
достижимости точки входа (нулевая конфигурация), при наличии manifest — явное объявление через
`[lib]` / `[[bin]]` / `[exports]` (поля, определённые в RFC-015). Заполняет четыре висящие
семантики: по чему считается поверхность межпакетного импорта, к чему применяется исключение pub для
предупреждений о мёртвом коде (решение B по #321), связь между `[exports]` и достижимостью Registry,
и устранение омонимии между `[binaries]` из RFC-014b (предкомпилированные дистрибутивные артефакты)
и исходными файлами роли bin.

## Мотивация

### Хост и граничные основания

RFC-029 (принят) — прямой предшественник данного RFC по выбору точки входа и решениям о видимости:

> **Выбор файла точки входа**, приоритет: 1. `[run].main` 2. `path` первой записи `[[bin]]` 3.
> `src/main.yx` (соглашение по умолчанию). — RFC-029 §Межпакетные циклы: продолжение

> **Видимость**: не существует. Область видимости + граница распространения покрывают все сценарии,
> новые ключевые слова не нужны. — RFC-029 §Журнал проектных решений (2026-07-30)

Второй пункт — красная линия данного RFC: семантика поверхности импорта **не должна вводить новые
ключевые слова видимости**, она может опираться только на «границу распространения» (роль файла +
объявленная поверхность экспорта).

Четыре потребителя независимо столкнулись с одной и той же стеной:

| Потребитель                                              | Точка столкновения                                                                                                                                                                                                          |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 предупреждения о мёртвом коде                       | Решение B «pub = всегда интерфейс наружу, никогда не сообщать» выбрано из-за отсутствия модели ролей для различения «реально наружу» и «выглядит как наружу»; сообщать ли о неиспользуемом pub в bin (вариант A) — отложено |
| RFC-014c рабочее пространство (на ревью, #113)           | По чему считается поверхность импорта при взаимном `use` пакетов-членов — `[exports]`, единственный файл из `[lib]`, или все pub-файлы — **ни одной семантической статьи во всём тексте**                                   |
| RFC-015 система конфигурации (принят)                    | Поля `[lib]` / `[[bin]]` / `[exports]` определены, помимо потреблённого RFC-029 приоритета точки входа, семантика остальных полей (особенно связь `[exports]` и достижимости Registry) не согласована                       |
| RFC-037 упаковка / RFC-029a кэширование (черновик, #293) | Выбор упаковываемых артефактов и граница единиц кэширования инкрементальной перекомпиляции требуют модели ролей в качестве предпосылки                                                                                      |

### Текущая проблема

**Четыре семантических пробела** (инвентаризация 2026-09-12, по полному тексту
014/014a/014b/014c/015/029):

1. **Не определена поверхность межпакетного импорта**. В примере взаимной ссылки пакетов-членов 014c
   есть только структура каталогов (`src/lib.yx`), нет ни одной статьи о том, что может получить
   `use utils.helper`. Текущее неявное правило — «все верхнеуровневые pub-файлы пакета» — внутренние
   файлы реализации тоже затягиваются в пространство имён, граница зависимостей превращается в
   фикцию.
2. **Нет области применения исключения pub для мёртвого кода**. «pub никогда не сообщается» из
   решения B по #321 излишне консервативно для однофайлового скрипта (у скрипта нет внешних
   потребителей, pub бессмысленно), но излишне либерально для файла точки входа многопроектного
   файла (никто не import-ит корневой pub — мёртвый код). Без модели ролей линия разреза вариантов
   A/B не проведётся.
3. **Три концепции экспорта не согласованы**. `[exports]` (015, отображение путей), `[lib]` (015,
   путь к одному файлу), достижимость Registry (029, от точки входа по use) — между ними отношения
   включения, равенства или независимости — нет статей.
4. **Омонимия**. `[binaries]` из RFC-014b — это **предкомпилированный дистрибутивный артефакт**
   (стратегия приоритета скачивания .so/exe), а «bin-цель (роль исходного кода)» — совершенно другой
   уровень. После введения 014c они неизбежно появятся одновременно, без скорейшего устранения
   омонимии будут постоянные недоразумения.

**Эмпирическое свидетельство: консервативность решения B — уже реальная боль**. Запись разбора M2 по
#321: структурная причина, по которой вся семья W1001–W1005 по умолчанию молчит — именно «все pub
считаются наружным интерфейсом» — это компенсирующее поведение из-за отсутствия модели, не финальное
состояние.

## Предложение

### Ключевая идея: модель ролей файлов

**Роль — атрибут уровня файла** (согласовано с гранулярностью полей 015: `[lib]` — один файл,
`[[bin]]` — список файлов, `[exports]` — отображение файлов), а не переключатель уровня пакета.

| Роль         | Определение                                                                                                                                                       | Семантика                                                                                                                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bin**      | Файл, на который указывает `[run].main` / `[[bin]].path`; или (без manifest) файл, содержащий `main` и не `use`-имый никаким другим файлом                        | Точка входа программы. Его `pub` **может сообщаться как мёртвый код** (нет внешних потребителей пакета); `main` — корень достижимости                                                                    |
| **Lib**      | Файл, попавший в отображение `[exports]`; или `[lib].path`; или (без manifest) файл, на который ссылается `use` другого файла                                     | Граница распространения. Его `pub` **освобождён от сообщений о мёртвом коде** (внешние потребители пакета не видны, лучше пропустить сообщение); символы, экспортированные через него, видимы межпакетно |
| **Test**     | Файлы, попавшие под правила тестовых файлов RFC-036 (каталог `tests/`, `*_test.yx` и другие существующие соглашения); явное объявление `[[test]]` **не вводится** | Тестовый код. Не участвует в оценке мёртвого кода; его ссылки учитываются как корни достижимости тестируемого кода                                                                                       |
| **Internal** | В пакете с manifest: файл, не входящий в поверхность экспорта и не содержащий main                                                                                | Внутрипакетная реализация. `pub` освобождён до второй фазы (сужается по достижимости use-графа пакета, с предпосылкой валидации на корпусе роли Bin); `use` снаружи пакета **недостижимо**               |
| **Script**   | Файл, запускаемый напрямую как одиночный файл (`run foo.yx`)                                                                                                      | Поведение полностью совпадает с сегодняшним: Registry содержит только std, никаких изменений семантики pub для мёртвого кода                                                                             |

**Приоритет определения**: явное объявление manifest > вывод достижимости точки входа > соглашения о
тестах 036. Явное объявление всегда побеждает — вывод лишь умолчание при отсутствии объявления.

### Пример

```toml
# yaoxiang.toml (все поля уже определены в RFC-015, данный RFC не вводит новых конфигурационных поверхностей)
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← именно это определяет межпакетную видимость, а не pub
```

```yaoxiang
# src/cli.yx (роль Bin)
pub unused_fn = (x: Int) => x    # ← W1001 может сообщаться: bin не имеет внешних потребителей
main: () -> Void = { ... }

# src/lib.yx (роль Lib, на поверхности экспорта)
pub api_fn = ...                 # ← никогда не сообщается: внешние потребители не видны

# src/other.yx (роль Internal, не на поверхности экспорта)
pub semi_api = ...               # ← освобождён до второй фазы (лучше пропустить), тогда сужается по use-графу
```

### Семантика поверхности импорта

Порядок разрешения межпакетного `use pkg.x` (первое совпадение вступает в силу):

1. Если отображение `[exports]` существует → поверхность импорта = набор файлов из отображения, `x`
   должен быть в верхнеуровневых привязках этих файлов;
2. Иначе, если существует `[lib].path` → поверхность импорта = этот единственный файл;
3. Иначе (зависимость без manifest, голая директория по пути) → **сохраняется текущее поведение**:
   импортируемы все верхнеуровневые файлы (обратная совместимость, сужение обсуждается отдельно).

**Члены рабочего пространства**: поверхность экспорта определяется только собственным manifest
пакета-члена, корень рабочего пространства не может перекрывать или расширять поверхность экспорта
члена — самоинкапсуляция членов — ключевая идея дизайна 014c, перекрытие корня нарушит инкапсуляцию.

Связь с достижимостью Registry (согласовано с 029): `[exports]`/`[lib]` определяют **множество
допустимых начальных точек межпакетного разрешения**; после определения начальных точек Registry
по-прежнему расширяется по 029 «от точки входа по `use` достижимо» — внутренние файлы, которые сама
экспортирующая сущность `use`-ит, попадают при линковке, но не порождают новых межпакетных начальных
точек.

### Разграничение с существующими планами

| Сосед                                                            | Граница                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-029d «CLI `--entry` перекрытие точки входа» (в планировании) | 029f определяет модель ролей; 029d потребляет её — `--entry` — это CLI-уровневое средство перекрытия роли Bin                                                                                                                                                              |
| RFC-014b `[binaries]`                                            | **Устранение омонимии**: `[binaries]` — предкомпилированный дистрибутивный артефакт (стратегия приоритета скачивания), `[[bin]]` — объявление роли исходного кода. Первое существует в manifest зависимого пакета, второе — в manifest текущего пакета, не взаимозаменяемы |
| RFC-014c рабочее пространство                                    | Поверхность импорта пакетов-членов = порядок разрешения из данного RFC; координация workspace (members, общий lockfile) остаётся в 014c                                                                                                                                    |
| RFC-036 тестирование                                             | Определение роли Test непосредственно заимствует существующие файловые правила 036, новых соглашений не добавляется                                                                                                                                                        |
| #321 мёртвый код                                                 | Решение B (pub всегда освобождён) явно понижается до «переходной семантики при отсутствии target»; возможность сообщения pub в роли Bin — форма реализации варианта A из #321 в данном RFC                                                                                 |

## Детальный дизайн

### Алгоритм определения роли (внутри оркестратора)

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. 显式层：manifest 声明优先
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. 推断层：无声明处按入口可达性
    for f in files where role[f] 未定:
        if f 被 ≥1 个非自身文件 use:      role[f] = Lib
        elif f 含 main 且无其他文件 use 它: role[f] = Bin
        else:                             role[f] = Internal

    # 3. 测试层：036 规则命中 → Test（覆盖 Lib/Internal，不覆盖显式 Bin）
    apply_rfc036_test_rules(files, &role)

    # 单文件直跑：整个模型旁路，行为不变
    if no manifest and single_file:      all Script
```

### Изменения в компиляторе

- `frontend/config.rs`: разбор manifest дополняется отображением `[exports]` → таблица ролей (разбор
  полей уже есть в 015).
- `frontend/module/orchestrator.rs`: перед построением Registry вставляется стадия классификации
  ролей; межпакетное разрешение проверяет цель `use` по порядку поверхности импорта, выход за
  границы сообщается существующим семейством `module_not_found` (новые коды ошибок не вводятся, в
  сообщение добавляется подсказка «не на поверхности экспорта»).
- `typecheck/passes/dead_code.rs`: множество точек входа меняется с «main + все pub» на «main + pub
  файлов роли Lib» (Bin сообщается немедленно; Internal освобождён до второй фазы, см. Phase 2 в
  стратегии реализации).
- LSP (RFC-017): «импортируемые элементы» для автодополнения/наведения фильтруются по поверхности
  импорта; диагностика отсутствия `main` выдаётся только для файлов роли Bin.

### Поведение во время выполнения

Без изменений. Модель ролей — чисто семантика времени компиляции/разрешения, не влияет на IR и
выполнение.

### Обратная совместимость

- Проекты без manifest: поведение полностью не меняется (слой вывода воспроизводит текущее состояние
  — use-имый — Lib, содержащий main — Bin). Инкремент предупреждений о мёртвом коде только в файлах
  Bin: неиспользуемый pub корневого файла, который никто не import-ит, переходит из тишины в W1001 —
  это ожидаемое поведение варианта A из #321, не поломка.
- Проекты с manifest: для пакетов с объявленным `[exports]` поверхность импорта сужается с «всех
  pub-файлов» до объявленной. **Это единственная точка сужения поведения**: код, зависящий от
  внутренних файлов чужого пакета, начнёт получать `module_not_found`. Учитывая, что экосистема
  пакетов ещё не сложилась (029: «в настоящее время нет экосистемы сторонних пакетов»), площадь
  поломки равна нулю; всё же устанавливается переходный период в один минор (сначала предупреждение,
  затем ошибка при выходе за границы).

## Компромиссы

### Преимущества

- Ноль новых конфигурационных поверхностей: все поля уже определены в 015, данный RFC только
  дополняет семантику.
- Ноль новых ключевых слов: поверхность импорта опирается на границу распространения, что изоморфно
  решению 029 «видимость не существует».
- Четыре потребителя (#321 / 014c / 029a / 037) моделируются единоразово, больше не упираются каждый
  в свою стену.
- Путь без manifest — нулевая стоимость: ген нулевой конфигурации скриптового языка полностью
  сохранён.

### Недостатки

- Вывод роли (use-имый — Lib) в распространённой форме «файл точки входа use-ит утилитарный файл»
  сделает утилитарный файл Lib, его pub освобождён — грубее идеальной гранулярности. Это осознанный
  выбор в сторону «лучше пропустить сообщение», сужение требует анализа направления вызовов в
  use-графе, в первой версии не делается.
- Сужение поверхности импорта через `[exports]` — семантическое сужение с эффектом поломки (хотя и с
  переходным периодом).

## Стратегия реализации

### Поэтапно

- **Фаза 1**: классификация ролей + разрешение поверхности импорта + возможность сообщения pub в Bin
  (Internal/Test сохраняют освобождение)
- **Фаза 2**: сужение pub в Internal до «недостижим по use-графу пакета — можно сообщать» —
  предпосылка: после введения Фазы 1 валидация на корпусе предупреждений роли Bin подтверждает
  отсутствие ложных срабатываний; срабатывание немедленно, без расписания

### Зависимости

- Предпосылки: оркестратор RFC-029 (уже внедрён), поля manifest RFC-015 (уже определены).
- Зависимые: #321 (возможность сообщения pub в Bin), RFC-014c (поверхность импорта), RFC-029a (роль
  как граница единиц кэширования), RFC-037 (выбор артефактов), RFC-029d (перекрытие `--entry`).
- Порядок внедрения с RFC-014c: до прохождения ревью 014c порядок поверхности импорта из 029f должен
  быть зафиксирован, 014c потребляет его по ссылке, чтобы избежать расширения области посреди ревью.

### Риски

- Расхождение вывода роли с интуицией пользователя (первый пункт компромиссов выше) → всё
  инкрементальное поведение представляется в форме предупреждений (не блокирующих), с возможностью
  отключения.
- Управление переходным периодом сужения `[exports]` → в минорной версии сначала предупреждение.

## Открытые вопросы

## Приложение B: Журнал проектных решений

> **Исправление (2026-09-17): модель ролей управляет семантикой точки входа**
>
> Данный RFC определил пять ролей и значение «кто является точкой входа» (строка Bin «`main` —
> корень достижимости»), но в первой реализации роль использовалась только для **предупреждений о
> мёртвом коде**, поиск точки входа всегда был независим от роли — `find_entry_point` не находил
> `main` и возвращал 0, **молча выполняя первую функцию из таблицы функций**. Рефакторинг
> верхнеуровневых привязок (T4) подключил модель ролей к определению точки входа, конкретные
> правила:
>
> | Роль                      | Правило точки входа                                                                                                                                                                                                              |
> | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
> | **Script** (без manifest) | **Понятия точки входа нет**. Инструкции верхнего уровня (включая инициализацию привязок) в порядке написания составляют тело программы; `main` — обычная привязка, **не вызывается автоматически** — для запуска пишите `main()` |
> | **Bin** (с manifest)      | требуется `main` и он должен быть функцией; иначе ошибка компиляции (E3020 нет main / E3021 main — не функция). На верхнем уровне не допускаются исполняемые инструкции                                                          |
> | **Lib / Internal / Test** | `main` не требуется (они не являются точками входа)                                                                                                                                                                              |
>
> **Два отличия от первоначального описания в данном RFC**:
>
> 1. В первоначальной строке Script написано «поведение полностью совпадает с сегодняшним».
>    Сегодняшнее поведение содержит два скрытых дефекта, оба исправлены в T4: ① при отсутствии
>    `main` выполняется первая функция из таблицы функций; ② инструкции верхнего уровня сообщают
>    E3005 как неисполняемые. Текущие инструкции верхнего уровня Script **исполняемы** — это новая
>    возможность, а не сохранение статус-кво.
> 2. «В Script `main` не особенный» и «В Bin `main` — точка входа» должны быть
>    **взаимоисключающими**: если бы Script и выполнял инструкции верхнего уровня, и неявно вызывал
>    `main`, то скрипт с явным `main()` запускался бы дважды (#356). Поэтому у Script есть только
>    одна точка выполнения — инструкции верхнего уровня.
>
> **Различие между определением роли и определением точки входа** (заметка о реализации):
> определение точки входа использует «наличие manifest» (`find_project_root().is_some()`), а не
> `roles::classify()`. Причина: classify отвечает на вопрос «кто потребляет этот файл» (служит
> анализу мёртвого кода); файл с manifest, но без `main`, в classify — Internal (его не use-ит
> другой файл, что логично), но пользователь запустил его как точку входа, и тогда точка входа
> обязана быть. Это два разных вопроса, критерии у них тоже разные.
>
> Подробнее см. `docs/src/reference/language-spec/syntax.md` §3.11.

| Термин                               | Определение                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
