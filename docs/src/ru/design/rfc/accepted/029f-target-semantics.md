# RFC-029f: Роли целей компиляции и семантика импортной поверхности

## Резюме

Реализация расширенного слота, обещанного RFC-029 «Планирование под-RFC» (слоты 029b–029e уже
заняты, далее 029f): определение для исходных файлов **модели ролей целей компиляции** (пять типов:
Script / Bin / Lib / Test / Internal) и **семантики их импортной поверхности** — при отсутствии
manifest вывод на основе достижимости из точки входа (нулевая конфигурация), при наличии manifest —
явное объявление через `[lib]` / `[[bin]]` / `[exports]` (поля, уже определённые в RFC-015).
Заполняет четыре висящие семантические лакуны: по какому принципу считается импортная поверхность
при кросс-пакетных импортах, область применения исключения `pub` для предупреждений о мёртвом коде
(решение B по #321), отношение `[exports]` к достижимости Registry, а также устранение лексической
неоднозначности между `[binaries]` из RFC-014b (предкомпилированные дистрибутивные артефакты) и
ролью bin у исходных файлов.

## Мотивация

### Основания от хост-системы и границ

RFC-029 (принят) с решениями по выбору точки входа и видимости является непосредственным предком
данного RFC:

> **Выбор файла точки входа** по приоритету: 1. `[run].main` 2. `path` первой записи `[[bin]]` 3.
> `src/main.yx` (соглашение по умолчанию). — RFC-029 §Межпакетные циклы: продолжение

> **Видимость**: не существует. Область видимости + граница дистрибуции покрывают все сценарии,
> новое ключевое слово не требуется. — RFC-029 §Запись проектных решений (2026-07-30)

Второй пункт — это красная линия данного RFC: семантика импортной поверхности **не должна вводить
новое ключевое слово видимости**; её может нести только «граница дистрибуции» (роль файла +
объявленная экспортная поверхность).

Каждый из четырёх потребителей столкнулся с одной и той же стеной:

| Потребитель                                              | Точка столкновения                                                                                                                                                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #321 Предупреждения о мёртвом коде                       | Решение B «`pub` = внешний интерфейс, никогда не сообщать» принято потому, что нет модели ролей, разделяющей «по-настоящему внешний» и «выглядящий как внешний»; сообщать ли о неиспользуемом `pub` внутри bin (вариант A) — висит в воздухе до сих пор |
| RFC-014c Рабочие пространства (на рассмотрении, #113)    | При взаимном `use` пакетов-членов по чему считается импортная поверхность — `[exports]`, единственный файл из `[lib]`, или все файлы с `pub` — **ни одного семантического положения во всём тексте**                                                    |
| RFC-015 Система конфигурации (принят)                    | Поля `[lib]` / `[[bin]]` / `[exports]` определены; кроме приоритета точки входа, потреблённого RFC-029, семантика остальных полей (особенно отношение `[exports]` к достижимости Registry) никем не согласована                                         |
| RFC-037 Упаковка / RFC-029a Кэширование (черновик, #293) | Выбор дистрибутивных артефактов и граница ячеек инкрементальной перекомпиляции требуют модели ролей как предпосылки                                                                                                                                     |

### Текущая проблема

**Четыре семантических пробела** (инвентаризация 2026-09-12, подтверждено полным просмотром
014/014a/014b/014c/015/029):

1. **Импортная поверхность при кросс-пакетных импортах не определена**. В примере взаимного импорта
   пакетов-членов в 014c есть только структура каталогов (`src/lib.yx`); что именно может получить
   `use utils.helper` — никаких положений. Текущее неявное правило — «все файлы верхнего уровня с
   `pub` пакета» — внутренние файлы реализации тоже втягиваются в пространство имён, и граница
   зависимостей фиктивна.
2. **У исключения `pub` для мёртвого кода нет области применения**. «`pub` никогда не сообщается» из
   решения B по #321 слишком консервативно для однофайлового скрипта (у скрипта нет внешних
   потребителей, `pub` бессмысленен) и слишком мягко для файла точки входа в многофайловом проекте
   (если `pub` корневого файла никто не импортирует — это мёртвый код). Без модели ролей линия
   разреза между вариантами A/B не прочерчивается.
3. **Три концепции экспорта никем не согласованы**. `[exports]` (015, отображение путей), `[lib]`
   (015, путь к одному файлу), достижимость в Registry (029, от точки входа по `use`) — между ними
   отношение включения, равенства или каждый отвечает за своё, никаких положений нет.
4. **Столкновение терминов**. `[binaries]` из RFC-014b — это **предкомпилированные дистрибутивные
   артефакты** (стратегия приоритета загрузки .so/exe), а «цель bin (роль исходного кода)» —
   совершенно другой уровень. После внедрения 014c они неизбежно окажутся на одном экране; без
   заблаговременного устранения неоднозначности недопонимание будет накапливаться.

**Эмпирическое подтверждение: консервативность решения B — уже реальная боль**. В записи
ретроспективы M2 по #321: структурная причина, по которой вся группа W1001–W1005 молчит в
конфигурации по умолчанию, именно в том, что «все `pub` считаются внешним интерфейсом» — это
компенсирующее поведение из-за отсутствия модели, а не финальное состояние.

## Предложение

### Основной замысел: модель ролей файлов

**Роль — атрибут уровня файла** (согласуется с гранулярностью полей 015: `[lib]` — один файл,
`[[bin]]` — список файлов, `[exports]` — отображение файлов), а не переключатель уровня пакета.

| Роль         | Определение                                                                                                                                                       | Семантика                                                                                                                                                                                                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bin**      | Файл, на который указывает `[run].main` / `[[bin]].path`; либо (при отсутствии manifest) файл, содержащий `main` и не используемый (`use`) ни одним другим файлом | Точка входа программы. Его `pub` **допускает сообщения о мёртвом коде** (нет внешних потребителей); `main` — корень достижимости                                                                                   |
| **Lib**      | Файл, в который попадает отображение `[exports]`; либо `[lib].path`; либо (при отсутствии manifest) файл, на который ссылается `use` из другого файла             | Граница дистрибуции. Его `pub` **исключён из сообщений о мёртвом коде** (внешние потребители пакета невидимы, лучше недосообщить); экспортируемые через него символы видны между пакетами                          |
| **Test**     | Файл, подпадающий под правила тестовых файлов RFC-036 (каталог `tests/`, соглашения вроде `*_test.yx`); **без** явного объявления `[[test]]`                      | Тестовый код. Не участвует в оценке мёртвого кода; его ссылки засчитываются как корень достижимости для тестируемого кода                                                                                          |
| **Internal** | Файл в пакете с manifest, который не входит в экспортную поверхность и не содержит `main`                                                                         | Внутренняя реализация пакета. `pub` исключён до второй фазы (с ужатием по достижимости в графе `use` внутри пакета, при предпосылке валидации на корпусе роли Bin); внешний `use` из других пакетов **недостижим** |
| **Script**   | Файл, запускаемый напрямую как один файл (`run foo.yx`)                                                                                                           | Поведение полностью совпадает с текущим: Registry содержит только std, без семантических изменений `pub` для мёртвого кода                                                                                         |

**Приоритет определения**: явное объявление в manifest > вывод по достижимости из точки входа >
соглашения 036 для тестов. Явное объявление всегда побеждает — вывод служит только умолчанием при
отсутствии объявления.

### Пример

```toml
# yaoxiang.toml (все поля уже определены в RFC-015, данный RFC не вводит новых конфигурационных поверхностей)
[lib]
path = "src/lib.yx"

[[bin]]
name = "my-cli"
path = "src/cli.yx"

[exports]
"." = "src/lib.yx"
"./internal-helper" = "src/helper.yx"   # ← именно он определяет межпакетную видимость, а не pub
```

```yaoxiang
# src/cli.yx (роль Bin)
pub unused_fn = (x: Int) => x    # ← можно сообщить W1001: у bin нет внешних потребителей
main = { ... }

# src/lib.yx (роль Lib, входит в экспортную поверхность)
pub api_fn = ...                 # ← никогда не сообщается: внешние потребители пакета невидимы

# src/other.yx (роль Internal, не входит в экспортную поверхность)
pub semi_api = ...               # ← исключён до второй фазы (лучше недосообщить), затем ужатие по графу use
```

### Семантика импортной поверхности

Порядок разрешения кросс-пакетного `use pkg.x` (первое совпадение вступает в силу):

1. Отображение `[exports]` существует → импортная поверхность = множество файлов, перечисленных в
   отображении; `x` должен находиться среди привязок верхнего уровня этих файлов;
2. Иначе существует `[lib].path` → импортная поверхность = этот единственный файл;
3. Ни того, ни другого (зависимость без manifest, либо зависимость по голому пути каталога) →
   **сохраняется текущее поведение**: импортируемы все файлы верхнего уровня (совместимость с
   существующим поведением, ужатие — отдельный вопрос).

**Члены рабочего пространства**: экспортная поверхность определяется только собственным manifest
пакета-члена; корень workspace не может переопределять или расширять экспортную поверхность члена —
самодостаточность членов — ключевой замысел 014c, переопределение из корня разрушило бы
инкапсуляцию.

Отношение с достижимостью Registry (согласовано с 029): `[exports]`/`[lib]` определяют **множество
легальных отправных точек кросс-пакетного разрешения**; после определения отправной точки Registry
по-прежнему расширяется по принципу 029 «от точки входа по `use` достижимо» — внутренние файлы,
которые сама экспортируемая поверхность подтянула через `use`, попадают в компоновку, но не
порождают новых кросс-пакетных отправных точек.

## Детальное проектирование

### Алгоритм определения ролей (внутри оркестратора)

```
fn classify(files, manifest, entry_reach) -> Map<File, Role>:
    # 1. Явный слой: объявления в manifest имеют приоритет
    for f in manifest.exports.values():  role[f] = Lib
    if manifest.lib_path:                role[lib_path] = Lib
    for b in manifest.binaries:          role[b.path] = Bin
    if manifest.run_main:                role[run_main] = Bin

    # 2. Слой вывода: без объявления — по достижимости из точки входа
    for f in files where role[f] не определена:
        if f используется (use) ≥ 1 другим файлом:  role[f] = Lib
        elif f содержит main и никакой другой файл его не use: role[f] = Bin
        else:                                          role[f] = Internal

    # 3. Слой тестов: срабатывание правил 036 → Test (перекрывает Lib/Internal, не перекрывает явный Bin)
    apply_rfc036_test_rules(files, &role)

    # Однофайловый прямой запуск: вся модель обходится, поведение не меняется
    if no manifest and single_file:      все Script
```

### Изменения в компиляторе

- `frontend/config.rs`: разбор manifest дополняется отображением `[exports]` → таблица ролей (разбор
  полей уже есть в 015).
- `frontend/module/orchestrator.rs`: перед построением Registry вставляется фаза классификации
  ролей; кросс-пакетное разрешение проверяет цель `use` согласно порядку импортной поверхности; при
  выходе за границу выдаётся ошибка из существующего семейства `module_not_found` (новый код ошибки
  не вводится, в сообщение добавляется подсказка «вне экспортной поверхности»).
- `typecheck/passes/dead_code.rs`: множество точек входа меняется с «main + все pub» на «main + pub
  файлов с ролью Lib» (для Bin можно сразу сообщать; для Internal — исключение до второй фазы; см.
  Phase 2 в стратегии реализации).
- LSP (RFC-017): в «импортируемых элементах» для автодополнения/наведения применяется фильтр по
  импортной поверхности; диагностика отсутствия `main` выдаётся только для файлов с ролью Bin.

### Поведение во время выполнения

Без изменений. Модель ролей — чисто компиляционная/разборная семантика, не влияет на IR и
исполнение.

### Обратная совместимость

- Проекты без manifest: поведение полностью не меняется (слой вывода воспроизводит текущее состояние
  — используемый файл становится Lib, содержащий main — Bin). Прирост предупреждений о мёртвом коде
  только в файлах Bin: неиспользуемый `pub` корневого файла, который никто не импортирует, переходит
  из тишины в W1001 — это ожидаемое поведение варианта A из #321, а не поломка.
- Проекты с manifest: когда `[exports]` объявлен, импортная поверхность сужается с «всех файлов с
  `pub`» до объявленной поверхности. **Это единственная точка сужения поведения**: код, зависящий от
  внутренних файлов чужого пакета, начнёт получать `module_not_found`. Учитывая, что экосистема
  пакетов ещё не сложилась (029: «в настоящее время экосистемы сторонних пакетов нет»), площадь
  поломки нулевая; тем не менее устанавливается переходный период в рамках минорной версии (сначала
  предупреждение, затем ошибка при выходе за границу).

## Компромиссы

### Достоинства

- Нулевая новая конфигурационная поверхность: все поля уже определены в 015, данный RFC только
  дополняет семантику.
- Нулевое новое ключевое слово: импортную поверхность несёт граница дистрибуции, изоморфно решению
  029 «видимости не существует».
- Четыре потребителя (#321 / 014c / 029a / 037) моделируются за один раз, каждый перестаёт биться о
  свою стену.
- Нулевая стоимость пути без manifest: ген нулевой конфигурации скриптового языка полностью
  сохранён.

### Недостатки

- Вывод ролей (файл, в который делается `use`, — Lib) в распространённой форме «файл точки входа
  делает `use` файла утилит» присвоит файлу утилит роль Lib и исключит его `pub` — крупнее идеальной
  гранулярности. Это сознательный выбор в сторону «лучше недосообщить»; ужатие требует анализа
  направления вызовов в графе `use`, в первой версии не делается.
- Сужение импортной поверхности через `[exports]` — семантическое ужатие с эффектом поломки (хотя и
  с переходным периодом).

## Стратегия реализации

### По фазам

- **Фаза 1**: классификация ролей + разрешение импортной поверхности + возможность сообщения о `pub`
  в роли Bin (Internal/Test сохраняют исключение)
- **Фаза 2**: `pub` в Internal ужато до «сообщать, если недостижимо в графе `use` внутри пакета» —
  предпосылкой служит валидация на корпусе предупреждений роли Bin после внедрения Фазы 1 без ложных
  срабатываний; запускается по готовности, без расписания по срокам

### Зависимости

- Предпосылки: оркестратор из RFC-029 (внедрён), поля manifest из RFC-015 (определены).
- Зависимые потребители: #321 (сообщения о `pub` в Bin), RFC-014c (импортная поверхность), RFC-029a
  (роль как граница ячеек кэша), RFC-037 (выбор артефактов), RFC-029d (покрытие `--entry`).
- Порядок внедрения с RFC-014c: до завершения рассмотрения 014c порядок импортной поверхности в 029f
  должен быть окончательно утверждён; 014c потребляет его по ссылке, чтобы избежать расширения
  объёма в процессе рассмотрения.

### Риски

- Расхождение вывода ролей с интуицией пользователя (первый пункт компромиссов выше) → всё
  приращение поведения представляется в форме предупреждений (без блокировки), с возможностью
  отключения в любой момент.
- Управление переходным периодом сужения `[exports]` → в пределах минорной версии сначала
  предупреждение.

## Открытые вопросы

Все три вопроса этапа черновика решены (2026-09-13, решения внесены в Приложение B и в основной
текст), нерешённых нет:

- [x] Ужать ли `pub` в Internal → **Решение**: во второй фазе ужать по достижимости в графе `use`
      внутри пакета; предпосылка — валидация на корпусе роли Bin (см. Фазу 2 стратегии реализации)
- [x] Вводить ли явное объявление `[[test]]` → **Решение**: не вводить, роль Test определяется
      только правилами 036; если у 036 в будущем возникнет потребность в явном объявлении, это
      расширение делается внутри самого 036
- [x] Может ли корень workspace переопределять экспортную поверхность членов → **Решение**: не
      допускается; самодостаточность членов — ключевой замысел 014c, переопределение из корня
      разрушило бы инкапсуляцию

## Приложение C: Глоссарий

| Термин                                 | Определение                                                                                                                          |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Роль (Role)                            | Идентичность исходного файла как цели компиляции: Script / Bin / Lib / Test / Internal                                               |
| Импортная поверхность (Import Surface) | Множество файлов — легальных отправных точек разрешения кросс-пакетного `use`, объявленное через `[exports]`/`[lib]` или выведенное  |
| Граница дистрибуции                    | Терминология 029: диапазон внешней экспозиции пакета; данный RFC уточняет её от неявной (все файлы с `pub`) до импортной поверхности |
| Состояние Script                       | Обходная форма для однофайлового прямого запуска без manifest, поведение полностью совпадает с текущим                               |

## Литература

- RFC-029 Семантика модулей (родительский RFC: выбор точки входа, решение по видимости, планирование
  под-RFC)
- RFC-015 Система конфигурации (определение полей `[lib]`/`[[bin]]`/`[exports]`)
- RFC-014b Система сборки и дистрибуция бинарных файлов (`[binaries]`, объект устранения
  неоднозначности терминов)
- RFC-014c Поддержка рабочих пространств (первый потребитель импортной поверхности, на рассмотрении)
- RFC-036 Фреймворк тестирования (источник правил роли Test)
- #321 M2 Независимый канал эмиссии кодов предупреждений (источник решения B и варианта A)
