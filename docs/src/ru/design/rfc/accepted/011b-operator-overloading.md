## Резюме

Дополнение YaoXiang возможностью **перегрузки операторов**, позволяющей определять пользовательскую
реализацию для `a + b` / `a == b` / `a[i]` / `e?` в пользовательских типах, и превращение
**ограничений по операторам** (`T: Add + Multiply`), записанных в синтаксисе ограничений из RFC-011,
из **бумажной возможности** в реально работающий механизм (`Zero` в том же предложении не является
оператором, см. открытые вопросы).

Проект использует **разделение ответственности на три слоя**: фиксированная таблица соответствия
оператор → метод (Слой 0), базовая диспетчеризация по имени (Слой 1, повторно использует
существующую `method_bindings`), слой контрактов интерфейса (Слой 2, для ограничений обобщённых
типов). **Приоритеты и ассоциативность операторов остаются фиксированными** на уровне языка,
пользователь перегружает только семантику.

Первая партия: семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`.
Арифметические интерфейсы используют **три параметра типа** `(Self, R, O)` — тип результата `O`
явный, что позволяет выражать операции над разными типами, такие как `1 + 2.5` (возвращает `Float`)
и `point * 2.0` (масштабирование). `Equal` **по умолчанию выводится автоматически** (записи, все
поля которых сравнимы, автоматически получают посимвольное `==`), явное инстанцирование может
переопределить это.

`Try` (интерфейсная реализация `?`) полностью переносится на этап 2: он зависит от внедрения RFC-010
(конструкция) и RFC-039 (деструкция), а форма интерфейса ещё не определена (см. открытые вопросы).

**Никакого нового синтаксиса, никаких новых ключевых слов** — всё повторно использует существующие
механизмы RFC-011a (объявление интерфейса / инстанцирование / объявление внешних методов /
перегрузка).

## Мотивация

### Почему необходима эта возможность

#### 1. Ключевой пример RFC-011 зависит от неё, и текущее положение хуже, чем «невыполнимо»

RFC-011 (принят) использует имена операторов как ограничения типов в 8 местах:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

Ни в одном RFC из всего комплекта не определено, откуда берутся `Add` / `Multiply` и как `+`
привязывается к ним. Практическая проверка подтверждает, что положение ещё хуже: `T: Add` **сегодня
приводит к прямой ошибке компиляции** — резолвер ограничений обращается к старой таблице trait'ов
(`trait_data.rs`), где нет `Add`. Имена ограничений `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut`
также висят в воздухе (обработку см. в разделе «Согласование с другими RFC»).

#### 2. Пользовательские типы не могут участвовать в базовых операциях (проверено на практике)

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

Сопутствующее последствие: `list.contains(list_of_structs, p)` **полностью неработоспособно** — он
внутренне зависит от `==`. При этом `(1, 2) == (1, 2)` и `[1] == [1]` посредством последовательного
сравнения элементов **всегда работают** — структуры являются единственным пробелом.

#### 3. `?` приваривает имя типа к компилятору, блокируя перенос `Result` в std

Реализация `?` одновременно жёстко прописывает имя типа и номер варианта:

```rust
// typecheck: жёстко прописанная конструкция типа Result
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen: жёстко прописанные имя группы и номер варианта
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

Это вынуждает `Result` оставаться в core. Если сделать `?` **управляемым интерфейсом**, любой тип,
реализующий этот интерфейс (включая пользовательские), сможет использоваться с `?`, и `Result`
сможет перейти в std (RFC-013 уже имеет позиционирование «`Result(T, Error)` в std-библиотеке»).

Заметьте, что это лишь половина проблемы: конструкторы `ok(...)` / `err(...)` / `some(...)` сейчас
также приварены к парсеру (спецификация языка §1.4.2 перечисляет их как «конструкторы,
распознаваемые парсером»). «Перенос `Result` в std» требует распутывания **обеих половин** — `?` и
конструкторов — вместе; обе относятся к этапу 2 настоящего RFC.

#### 4. Пользовательские контейнеры не индексируются

Проверка типов для `Index` представляет собой жёстко закодированный белый список:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[1].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// остальное → «неизвестный контейнер на уровне типов — лучше отказать, чем молчать»
```

Для любого пользовательского типа контейнера `c[0]` всегда возвращает ошибку.

#### 5. Реализация `%` нарушает опубликованную документацию

Практическая проверка показывает, что `-7 % 3` возвращает `-1` (остаток от деления с усечением).
Однако таблица приоритетов операторов в справочнике языка (`reference/index.md`) уже давно содержит
«`* / %` умножение, деление, **взятие модуля**» — документация обещает взятие модуля, а реализация
даёт остаток. Это не изменение проекта, а **дефект, в котором реализация нарушает документацию**;
настоящий RFC попутно исправляет его.

### Существующая полуфабрикатная база

Исследование показало, что большая часть механизма **уже существует** — не хватает лишь подключения:

| Механизм                                                              | Расположение                                                                                                                      | Состояние                                                                                     |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Объявление интерфейса `(Self: Type) -> Type`                          | RFC-011a Фаза 1                                                                                                                   | ✅ Работает                                                                                   |
| Инстанцирование интерфейса `Animal(Dog)` + объявление внешнего метода | RFC-011a Фазы 2–3                                                                                                                 | ✅ Работает (есть юнит-тесты)                                                                 |
| Диспетчеризация методов `method_bindings["Type.method"]`              | `expressions.rs` (регистрация в `environment.rs`, запрос в `expressions.rs` при разборе вызовов и пути fallback при поиске полей) | ✅ Работает                                                                                   |
| Ассоциированные типы (= параметры типа интерфейса)                    | RFC-011 §3.1; RFC-011a принял этот подход                                                                                         | ✅ Механизм определён                                                                         |
| Вычисление семейств типов `AssociatedTypeDef`                         | `dependent_types.rs`                                                                                                              | ✅ Рабочий пример `std.assert` с `IsTrue`                                                     |
| trait'ы `Equal` / `Dup` / `Clone` / `Debug`                           | зарегистрированы в `trait_data.rs`                                                                                                | ⚠️ `Equal` не используется; старое автовыведение только регистрирует сигнатуру без реализации |
| Соответствие оператор → имя метода                                    | —                                                                                                                                 | ❌ Не существует                                                                              |

**Вывод**: это не создание возможности с нуля, а подключение и документирование существующих
деталей.

## Предложение

### Основной проект: разделение ответственности на три слоя

```
Слой 0   Фиксированная таблица соответствия (константа уровня языка, неизменяемая пользователем)
          + → add    == → equal    [] → index    ? → residual
          │  Встроена на этапе компиляции, не участвует в выводе типов, не видна пользователю
          ▼
Слой 1   База диспетчеризации (поиск метода по имени и вызов)   ← повторное использование существующего механизма
          method_bindings["Point.add"]
          ▼
Слой 2   Контракты интерфейсов (для ограничений обобщённых типов)
          Add / Equal / Index / Try …
          Делает ограничение T: Add валидным и служит условием пропуска для оператора
```

**Обоснование разделения**:

- **Слой 0 и 1** делают оператор «пригодным к использованию», **Слой 2** делает оператор «пригодным
  для ограничений». Слияние привело бы к тому, что любой метод с именем `add` вызывался бы через
  `+`, и ограничение `T: Add` из RFC-011 оторвалось бы от оператора.
- **Слой 1 не создаётся заново**: `method_bindings` уже выполняет поиск по ключу `Type.method` (путь
  fallback после неудачного поиска поля); операторы просто идут тем же путём.
- **Слой 2 — условие пропуска**: перед пропуском оператора **необходимо** убедиться, что тип
  реализует соответствующий интерфейс (см. исключение автовыведения для `Equal` — вывод и
  регистрация представляют собой один и тот же критерий).

### Имена и регистрация: два независимых канала

**Операторы обращаются к «реестру реализаций интерфейсов», а не к обычному разрешению имён.**

- Реестр принадлежит ядру и агрегирует две точки регистрации: регистрации по умолчанию, выполняемые
  ядром для базовых типов (`Add(Int, Int, Int)` и т.д.), и инстанцирования интерфейсов, записываемые
  пользователем в теле типа (`Add(Point, Point, Point)`). Независимо от того, в каком модуле
  физически находится код реализации, регистрации стекаются в одну таблицу, и `+` / `==` / `[]`
  смотрят только в неё.
- **Локальное определение в модуле** с тем же именем `Add` (например, типоуровневое сложение Пеано
  `Add: (A: Type, B: Type) -> Type = match ...` из RFC-011 §5.2) проходит через **канал разрешения
  имён** и влияет только на разрешение имени `Add` в этом модуле, **не касаясь реестра и не влияя на
  работоспособность операторов**. Одноимённые сущности не затеняют друг друга.

Это одновременно отвечает на вопрос «конфликтует ли типоуровневый `Add` из RFC-011 с интерфейсом
`Add` из настоящего RFC»: нет, не конфликтует. Типоуровневый `Add` — это чисто типоуровневое
вычисление (`Zero`/`Succ` являются типами, а не значениями, и никогда не будет операции
`Zero + Succ(...)` над значениями), и это другое измерение того же имени на уровне значений.

### Слой 0: фиксированная таблица соответствия

| Оператор          | Интерфейс                                                | Метод                       | Первая партия |
| ----------------- | -------------------------------------------------------- | --------------------------- | ------------- |
| `+`               | `Add`                                                    | `add`                       | ✅            |
| `-`               | `Subtract`                                               | `subtract`                  | ✅            |
| `*`               | `Multiply`                                               | `multiply`                  | ✅            |
| `/`               | `Divide`                                                 | `divide`                    | ✅            |
| `%`               | `Modulo`                                                 | `modulo`                    | ✅            |
| `==` `!=`         | `Equal`                                                  | `equal`                     | ✅            |
| `[]`              | `Index`                                                  | `index`                     | ✅            |
| `?`               | `Try` (форма не определена, см. открытые вопросы)        | `residual` (предварительно) | ❌ Этап 2     |
| `<` `<=` `>` `>=` | — (зарезервировано за нативными инструкциями)            | —                           | ❌            |
| `and` `or`        | — (короткое замыкание — семантика языка, неперегружаемо) | —                           | ❌            |
| 5 побитовых       | —                                                        | —                           | ❌            |
| Унарные `-` `!`   | —                                                        | —                           | ❌            |

**Имена интерфейсов используют полную форму, а не сокращения** (`Multiply`, а не `Mul`): это
согласуется с текстом RFC-011 `T: Add + Multiply + Zero`, **без изменения уже принятого RFC**.

**`%` использует семантику `Modulo`** (математический модуль, знак результата следует за делителем).
В разделе мотивации уже подтверждено, что текущая реализация remainder нарушает опубликованную
документацию («умножение, деление, взятие модуля» в `reference/index.md`); это пункт обрабатывается
как исправление дефекта, без периода совместимости.

Замечание о текущем состоянии: белый список проверки типов для `%` сейчас содержит только Int/Float
(в отличие от белого списка `+`, содержащего Int/Float/String/List); практические записи приведены в
Приложении A.2.

### Слой 2: определения интерфейсов

#### Арифметические интерфейсы (три параметра типа)

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

Три параметра типа выполняют каждый свою функцию:

- `Self`: тип левого операнда (получатель, заимствуется через `&Self`, см. токен заимствования в
  RFC-009 и соглашение о получателе в RFC-011a);
- `R`: тип правого операнда — **левый и правый могут быть разных типов**;
- `O`: **тип результата**, объявлен явно.

**Почему тип результата должен быть явным параметром** (а не жёстко записан как `-> Self`):

1. При жёстко записанном `Self` метод `Add(Int, Float)` должен возвращать `Int`, и `1 + 2.5` не
   может быть выражено корректно;
2. Как только тип результата становится явным, семейство типов повышения
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }` из RFC-011 §8.3 и реестр
   интерфейсов из настоящего RFC **становятся двумя проекциями одной таблицы** — регистрация ядра
   `Add(Int, Float, Float)` — это в точности строка `(Int, Float) => Float`; каждое инстанцирование
   пользователя — добавление строки в эту таблицу;
3. Интерфейс `Index` и так имеет три параметра `(Self, Key, Value)`, где `Value` — тип возврата как
   параметр — арифметические интерфейсы, дополненные `O`, унифицируют форму всего семейства
   операторных интерфейсов; фиксированный `Self` был бы исключением.

**Регистрации по умолчанию в ядре** (путь нативных инструкций, не через вызов метода):
`Add(Int, Int, Int)`, `Add(Int, Float, Float)`, `Add(Float, Int, Float)`,
`Add(Float, Float, Float)`, `Add(String, String, String)` (конкатенация),
`Add(List(T), List(T), List(T))` (конкатенация элементов) и т.д.; те же пять арифметических
интерфейсов для базовых типов. `1 + 2.5` из текущей ошибки компиляции (белый список требует
одинаковых типов с обеих сторон) превращается в допустимую операцию, возвращающую `3.5: Float`.

**Синтаксический сахар для ограничений**: `T: Add` ≜ зарегистрированное `Add(T, T, T)` —
самосовмещение с одинаковыми типами, результат того же типа. В примере с матричным умножением из
RFC-011 выражение `a * b + c` повсюду имеет тип `T`, что и требует это значение. Аналогично
`T: Equal` ≜ `Equal(T, T)`.

**Пример с разными типами** — масштабирование вектора:

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### Интерфейс равенства (автовыведение по умолчанию)

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` выводится автоматически по умолчанию** по пяти правилам:

1. **Автовыведение по умолчанию**: при определении типа записи, если все поля сравнимы (базовые
   типы, `String`, или сами сравнимые записи/кортежи/списки, и нет полей `&mut`), компилятор
   автоматически генерирует **посимвольное сравнение** для `==` по нативному пути кода, не генерируя
   видимый пользователю метод. Пользовательские типы естественно сравнимы без каких-либо ритуалов.
2. **Явное переопределение**: если в теле типа записано `Equal(Point, Point)` и предоставлен метод
   `Point.equal`, используется пользовательская версия (например, сравнение Float с допуском),
   автовыведение более не применяется.
3. **Если поле несравнимо**: автовыведение не выполняется, `==` недоступно, диагностика указывает,
   какое именно поле стало препятствием; в этом случае пользователь всё ещё может вручную написать
   `Equal` с пользовательским сравнением (например, сравнивать поля-функции по имени).
4. **Предусловие**: типы, содержащие линейные токены `&mut T` (поля рекурсивно), не участвуют в
   сравнении — линейный токен расходуется при однократном чтении, и невозможно одновременно извлечь
   два значения для сравнения. Заметьте, что предусловие — «нелинейность», а не «Dup»: примитивные
   типы значений (Int/Float/Bool/Char) согласно RFC-011 §2.4 не подпадают под Dup (для них встроено
   копирование значений компилятором); если бы предусловие основывалось на Dup, то
   `Point { x: Float, y: Float }` был бы ошибочно отвергнут.
5. **Единый критерий для ограничений**: резолвинг `T: Equal` и пропуск `==` следуют одному и тому же
   правилу «проверка реестра или структурный вывод» — ограничения и операторы всегда дают один и тот
   же ответ.

**Обоснование согласованности**: `(1, 2) == (1, 2)` и `[1] == [1]` сегодня уже используют
последовательное сравнение элементов во время выполнения (белый список сравнения в `executor.rs`
включает Tuple/List/Array), записи — единственный исключённый составной тип. Автовыведение — это не
новое тихое умолчание, а восполнение последнего пробела в существующем поведении языка.

**Вывод из эксплуатации старого механизма**: старое автовыведение `Equal` в `trait_data.rs` (которое
только регистрировало сигнатуру без реализации и не имело точек потребления) выводится из
эксплуатации; все решения по `Equal` (регистрация по умолчанию для базовых типов, структурный вывод,
явное инстанцирование) идут через реестр интерфейсов. Старая таблица trait'ов сохраняет существующие
обязанности для `Clone`/`Dup`/`Debug` (имена не пересекаются с операторными интерфейсами; унификация
— вопрос отдельного обсуждения).

#### Интерфейс индексации

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` — параметр типа, а не член ассоциированного типа**: открытый вопрос в RFC-011a уже закрыт
решением «ассоциированные типы реализуются через параметры обобщённого интерфейса» (прецедент
изоморфизма: `Iterator: (Item: Type) -> Type`); вводить синтаксис членов `type` не требуется.

**Замечание о владении**: `index` возвращает полное значение `Value` из заимствования `&Self`.
`list.get: (&Vec(A), Int) -> A` в стандартной библиотеке уже имеет ту же форму; настоящий интерфейс
**обходится со std так же, как сейчас**; точная семантика «извлечения полного значения из
заимствования» для типов элементов с move-семантикой будет обработана при полном введении в действие
RFC-009; настоящий RFC не изобретает для этого новых правил.

**Многопозиционная индексация — через упаковку кортежем + перегрузку**, без введения вариативных
интерфейсов:

```yaoxiang
// Одномерный контейнер
List(T) инстанцирует Index(List(T), Int, T)                   → arr[0]

// Многомерный контейнер
Grid    инстанцирует Index(Grid, Tuple(Int, Int), Float)       → g[0, 1]
//                    └─ Key — кортеж

// Два инстанцирования с разными сигнатурами → сосуществуют
```

**Множественные инстанцирования одного и того же интерфейса с тем же именем для одного типа
допустимы**, различаясь по сигнатурам внедряемых методов и подчиняясь правилам перегрузки на уровне
методов из RFC-011a. Перегрузка в RFC-011a явно прописана только до уровня методов; настоящий пункт
дополняет её правилом на уровне инстанцирований: легитимность сосуществования одноимённых
инстанцирований интерфейса определяется тем, конфликтуют ли сигнатуры методов после раскрытия
(конфликт = E1097, что совпадает с правилами пространства имён полей/методов).

#### Интерфейс распространения (Этап 2, форма не определена)

Целевое имя интерфейса для `?` — `Try`, но **полная форма не определена**, и в первую партию он не
входит. Причины:

1. `?` фактически выполняет три действия: проверка успеха/неудачи (сейчас жёстко прописан вариант
   0), извлечение полезной нагрузки при успехе, возврат всего значения как есть из текущей функции
   при неудаче. Единственный метод `residual: (self: &Self) -> E` покрывает только часть третьего
   действия; текущее жёсткое прописывание, скорее всего, придётся переделывать;
2. Этап 2 по определению зависит от внедрения RFC-010 (конструкция `Result`) и RFC-039
   (деструктуризация вариантов);
3. Сопутствующая **проблема жёсткого прописывания конструкторов** (`ok` / `err` / `some`
   распознаются парсером, спецификация языка §1.4.2) — это вторая половина той же проблемы, что и
   жёсткое прописывание имени типа в `?`; «перенос `Result` в std» требует решения обеих половин
   вместе; обе относятся к этапу 2.

### Примеры

#### Пользовательский тип: арифметика и равенство из коробки

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false — Equal выводится автоматически, без инстанцирования
    println(a == a)             # true
}
```

#### Пользовательское равенство (переопределение автовыведения)

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# Сравнение Float с допуском, переопределяет посимвольное автовыведение
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### Индексация пользовательского контейнера

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### Обобщённые ограничения наконец-то реализуемы

```yaoxiang
// Пример из RFC-011 отныне реализуем
// T: Add ≜ Add(T, T, T) уже зарегистрировано; T: Multiply ≜ Multiply(T, T, T) уже зарегистрировано
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

(`Zero` / `One` из знакового примера RFC-011 `T: Add + Multiply + Zero` не входят в настоящий RFC —
они являются членами-константами, а не операторами; для «членов интерфейса без получателя» в
RFC-011a нет прецедента, см. открытые вопросы.)

### Синтаксические изменения

**Никакого нового синтаксиса, никаких новых ключевых слов**. Все возможности складываются из
существующих механизмов:

| Возможность                 | Используемый существующий механизм                                                   |
| --------------------------- | ------------------------------------------------------------------------------------ |
| Объявление интерфейса       | RFC-011a Фаза 1                                                                      |
| Инстанцирование интерфейса  | RFC-011a Фаза 2 (`Dog: { Animal(Dog) }`)                                             |
| Реализация метода           | RFC-011a Фаза 3 (внешнее объявление `Point.add`)                                     |
| Ассоциированные типы        | RFC-011 §3.1 (параметры типа интерфейса)                                             |
| Многопозиционная индексация | Существующий разбор упаковки кортежем + правила перегрузки на уровне инстанцирований |
| Приоритет операторов        | **Фиксирован языком**, не допускает пользовательской настройки                       |

## Детальный проект

### Влияние на систему типов

**Новые интерфейсы** (Слой 2): `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (`Try`
— этап 2).

**Реестр реализаций интерфейсов**: центральный узел принятия решений для операторов. Агрегирует
регистрации по умолчанию в ядре (для базовых типов) и пользовательские инстанцирования
(`ImplementationProof`, выдаваемые `check_interface_instantiation`); проверка пропуска для `+` /
`==` / `[]` и резолвинг ограничений `T: Add` (`check_trait_bounds` в `bounds.rs`) **обращаются к
одной и той же таблице** — не существует зазора «ограничение говорит да, оператор говорит нет».

**Структурный вывод `Equal`**: поверх реестра накладывается структурное правило (все поля сравнимы ⇒
сравнимо), базовые типы подхватываются регистрациями ядра, рекурсия замыкается. Прежняя регистрация
`Equal` в `trait_data.rs` и старое автовыведение выводятся из эксплуатации.

**Разделение запросов операторов и разрешения имён**: `+` и подобные обращаются только к реестру, не
проходя через обычное разрешение имён; локальные одноимённые привязки (например, типоуровневое
семейство `Add`) не влияют на операторы (см. §Имена и регистрация).

**Правило сирот**: реализация оператора может быть записана только в **модуле определения типа** —
определение `Int` находится в ядре, поэтому регистрировать `Int` может только ядро; определение
`Point` находится в пользовательском модуле, поэтому зарегистрировать его может только его
определитель. Все типы подчиняются одному правилу, встроенные типы не имеют привилегий.

### Поведение во время выполнения

**Нулевые накладные расходы во время выполнения**: целевой метод оператора определяется на этапе
компиляции (статическая диспетчеризация). Для базовых типов (`Int`/`Float`/`String`/`List`)
сохраняется **быстрый путь нативных инструкций**, без диспетчеризации через интерфейс; для
автовыведенного `==` структур генерируется нативное посимвольное сравнение; `==` / `!=` в позиции
`Any` (динамический тип) сохраняет существующее сравнение во время выполнения (тестовый каркас
RFC-036 `assert_eq` зависит от этого поведения и не затрагивается).

**Корректировка семантики `%`**: `-7 % 3` изменяется с `-1` (остаток от деления с усечением) на `2`
(математический модуль). Синхронно изменяются три точки: интерпретатор (`checked_rem`), свёртка
констант (`a % b`), байткод (`I64_REM`).

### Обратная совместимость

**Операции с базовыми типами не изменяются**: `1 + 2`, `"a" + "b"`, `[1] + [2]`, `1 < 2` — всё
сохраняет нативный путь, поведение и производительность неизменны.

**`1 + 2.5` из ошибки компиляции становится допустимым**: после регистрации ядра
`Add(Int, Float, Float)` смешанная арифметика, прежде отвергавшаяся белым списком, становится
доступной и возвращает `Float`. Это новая возможность, никакой существующий код не затрагивается.

**Корректировка семантики `%`**: `-7 % 3` изменяется с `-1` на `2`. Квалифицируется как
**исправление дефекта** (документация давно обещает взятие модуля, см. §5 мотивации), без периода
совместимости; в существующих тестовых материалах нет случаев, зависящих от `%` с отрицательными
числами (проверено).

**`==` структур из ошибки выполнения становится работоспособным**: прежде `Struct == Struct` всегда
давал ошибку выполнения E6007, после подключения автовыведения он сразу становится работоспособным —
от плохого к хорошему, ни один существующий допустимый код не затрагивается.

**`==` для `Any` не затрагивается**: в позиции динамического типа сохраняется сравнение во время
выполнения (семейство утверждений `assert_eq` из RFC-036 зависит от этого; прежде работало — и после
работает).

**Позиционное связывание `f[0]` не изменяется**: `distance[0]` — встроенная возможность компилятора
из RFC-004, **не проходит через интерфейс `Index`** и не затрагивается.

**`?` прозрачен для существующего кода** (этап 2): после того как `Result` получит инстанцирование
`Try`, поведение всех существующих применений `?` останется полностью идентичным.

## Компромиссы

### Преимущества

- **Реализация операторных ограничений из RFC-011**: `T: Add + Multiply` из бумажного (фактически
  ошибочного) состояния превращается в работоспособный механизм, без изменения текста уже принятого
  RFC.
- **Снятие привязки `Result` к core** (этап 2): после интерфейсификации `?` и конструкторов `Result`
  может перейти в std, что согласуется с существующим позиционированием RFC-013.
- **Исправление наблюдаемого дефекта**: `Point == Point` работает из коробки, попутно
  восстанавливается `list.contains` для структур.
- **Нулевой новый синтаксис**: всё повторно использует существующие механизмы RFC-011a, правила
  синтаксического анализатора не затрагиваются.
- **Нулевые накладные расходы во время выполнения**: статическая диспетчеризация + нативный быстрый
  путь для базовых типов.
- **Пользовательские контейнеры работоспособны**: `Box(T)[0]` из «всегда ошибка» становится
  работоспособным.
- **Внутренняя согласованность языка**: Tuple/List уже сравниваются посимвольно, записи дополняются;
  три параметра арифметических интерфейсов унифицируются по форме с `Index`; таблица повышения из
  RFC-011 §8.3 объединяется с реестром интерфейсов.

### Недостатки

- **Автовыведение `Equal` — тихое умолчание**: если в будущем потребуется отозвать «записи по
  умолчанию сравнимы», это будет ломающее изменение. Эта позиция принята — она согласуется с
  существующим поведением Tuple/List, и явное инстанцирование всегда может переопределить умолчание.
- **Предусловие `Equal` отвергает типы с линейными токенами**: типы с полями `&mut` не могут
  использовать `==`; это цена семантической корректности, требующей чёткой диагностики (с указанием
  конкретного поля).
- **Инстанцирование интерфейса — явная стоимость**: для каждого арифметического оператора нужно
  записать строку инстанцирования + метод (`Equal` освобождён — автовыведение). Синтаксис RFC-011a
  исключает неявный вывод (компенсация — отсутствие магии с параметром типа `Self`).
- **Корректировка семантики `%` — изменение поведения**: хотя оно квалифицируется как исправление
  дефекта, его всё же необходимо отметить в инструкции по миграции.

## Альтернативы

### Вариант A: только Слой 1 (диспетчеризация по имени метода), без слоя интерфейсов

`+` только проверяет, существует ли метод с именем `add`, не требуя реализации интерфейса `Add`.

**Причина отклонения**: ограничение `T: Add` из RFC-011 оторвётся от операторов — ограничение
проверяет интерфейс, оператор проверяет имя метода, и оба могут давать несогласованные ответы. Кроме
того, невозможно дать точную диагностику на этапе компиляции для «`+` применён к несложимому типу».

### Вариант B: ввести синтаксис конструкторов `Ok(x)` / `Some(x)` для решения проблемы `?`

Не интерфейсифицировать `?`, а добавить синтаксис конструкторов для типов-сумм.

**Причина отклонения**: конфликтует с RFC-010 (принят). RFC-010 явно предписывает «единообразно
использовать типы записей для выражения типов-сумм, **две парадигмы синтаксиса не нужны**» и явно
отвергает синтаксис `|`. Введение конструкторов — это появление второй парадигмы выражения. Кроме
того, это решает только `?`, но не `Point == Point` и индексацию пользовательских контейнеров.

### Вариант C: операторы сравнения тоже входят в первую партию интерфейсификации (введение `Ordering`)

`<` `<=` `>` `>=` идут через интерфейс `Compare`, возвращающий трёхзначное `Ordering`.

**Причина отклонения**: `<` уже является **инструкцией IR первого класса** в YaoXiang
(`Instruction::Lt/Le/Gt/Ge`); интерфейсификация заставит базовые типы идти обходным путём. Кроме
того, введение `Ordering` повлечёт за собой весь комплекс вопросов: сравнение/сортировка самого
`Ordering`, `PartialOrd` vs `Ord` для `NaN` во Float и т.д., что соответствует объёму отдельного
RFC. Практические потребности, выявленные на текущий момент (`Point == Point`, `list.contains`)
требуют **только `Equal`**.

### Вариант D: имена операторов в виде сокращений (метод интерфейса `Add` называется `add`, а сам интерфейс — `Mul`)

**Причина отклонения**: текст RFC-011 уже содержит `T: Add + Multiply + Zero`; использование
сокращений потребовало бы изменения уже принятого RFC.

### Вариант E: `Equal` только через явное инстанцирование, без автовыведения

**Причина отклонения**: пользовательские типы неожиданно не могут использовать `==`, что неприемлемо
с точки зрения опыта; кроме того, `(1, 2) == (1, 2)` и `[1] == [1]` уже сегодня сравниваются
посимвольно, и только записи исключены, что и так несогласовано. Явное инстанцирование сохраняется
как средство переопределения, что покрывает потребности пользовательского сравнения.

### Вариант F: тип возврата арифметических интерфейсов жёстко зафиксирован как `-> Self`

**Причина отклонения**: метод `Add(Int, Float)` будет вынужден возвращать `Int`, и `1 + 2.5` не
может быть выражено корректно; масштабирование вектора `Multiply(Point, Float)` аналогично не
выразимо. Кроме того, семейство типов повышения `(Int, Float) => Float` из RFC-011 §8.3 потеряет
место для реализации. Три параметра `(Self, R, O)` унифицируются по форме с `Index(Key, Value)`.

## Стратегия реализации

### Зависимости

| Зависимость                             | Состояние     | Влияние на настоящий RFC                                                                                    |
| --------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------- |
| Механизм интерфейсов RFC-011a, Фазы 1–3 | ✅ Внедрён    | Фундамент Слоя 2 (проверено на практике)                                                                    |
| Путь конструирования записей RFC-010    | ❌ Не внедрён | **Этап 2**: конструирование через `?` + вывод из эксплуатации специальных случаев парсера для конструкторов |
| Деструктуризация вариантов RFC-039      | ❌ На бумаге  | **Этап 2**: запись `match` для `Result.residual`, исчерпываемость                                           |
| Вывод линейных токенов RFC-009          | Частично      | Проверка предусловия `Equal`                                                                                |

### Поэтапное внедрение

По **зависимостям интерфейсов** (конструктивное ограничение, а не расписание) делится на две группы:

**Этап 1 — без зависимости от RFC-010/039**:

- Таблица соответствия Слоя 0 + реестр реализаций интерфейсов + подключение диспетчеризации Слоя 1
- Семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (форма с тремя
  параметрами типа)
- Автовыведение `Equal` + предусловие линейности + переключение резолвинга ограничений на реестр
- Корректировка семантики `%` (включая интерпретатор / свёртку констант / байткод — три точки)
- `==` в позиции `Any` сохраняет сравнение во время выполнения
- **Результат**: `Point + Point`, `Point == Point` (без ритуалов), `Box(T)[0]`, `1 + 2.5`,
  ограничение `T: Add` — всё становится работоспособным

**Этап 2 — зависит от RFC-010 / RFC-039, требует определения формы `Try` до начала работ**:

- Определение формы интерфейса `Try` (см. открытые вопросы)
- Интерфейсификация `?` + вывод из эксплуатации специальных случаев парсера для конструкторов
  (`ok`/`err`/`some`), переход на путь конструирования записей из RFC-010
- Перенос `Result` из core в std (на основе существующего позиционирования RFC-013)

### Риски

| Риск                                                              | Смягчение                                                                                                                            |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Изменение семантики `%` влияет на существующий код пользователей  | Квалифицируется как исправление дефекта + подтверждено отсутствие зависимостей от `%` с отрицательными числами в тестовых материалах |
| Тихое умолчание автовыведения `Equal` трудно отозвать в будущем   | Позиция принята: согласуется с существующим поведением Tuple/List, явное инстанцирование может переопределить                        |
| Несогласованность двойного пути базовых типов (нативный + реестр) | Контроль: семантика регистраций ядра должна совпадать с нативными инструкциями (две проекции одной таблицы)                          |
| Запросы к реестру замедляют компиляцию                            | Таблица индексируется по имени типа + кэширование результатов инстанцирования (повторное использование proof из RFC-011a)            |
| Перегрузка на уровне инстанцирований порождает неоднозначность    | Те же правила, что и для перегрузки на уровне методов: конфликт сигнатур = E1097                                                     |

## Согласование с другими RFC

Позиция настоящего RFC — **инициатор требований на стороне потребителя**; необходимо синхронно
обновить следующие RFC для обеспечения согласованности (получено разрешение на редактирование):

| RFC                    | Что необходимо обновить                                                                                                                                                                                                                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011** (принят)   | В §об ограничениях указать, что `Add` / `Multiply` определяются и реализуются в 011b (`T: Add` ≜ `Add(T, T, T)`); пометить `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` как висящие имена ограничений (для последующих RFC); в §8.3 указать, что семейство типов повышения объединяется с реестром интерфейсов |
| **RFC-010** (принят)   | Уточнить требование к реализации «поля записи являются конструкторами» — это предусловие для вывода из эксплуатации специальных случаев парсера конструкторов на этапе 2                                                                                                                                         |
| **RFC-039** (черновик) | Конструирование и деструктуризация должны идти парой; оценка исчерпываемости не зависит от принадлежности `Result` к core/std (на этапе 2 011b будет перенесён)                                                                                                                                                  |
| **RFC-009** (принят)   | В §о свойствах типов перекрёстная ссылка: предусловие `Equal` — «отсутствие линейного токена `&mut`» (не Dup)                                                                                                                                                                                                    |
| **RFC-013** (принят)   | При внедрении этапа 2: убрать слово «Result» из текстов `E1081` / `E1082`; диагностика предусловия `Equal` повторно использует семейство `E1101` — синхронизация трёх сторон по процессу RFC-013 (codes/*.rs ↔ локали ↔ таблица кодов)                                                                           |
| **RFC-018** (принят)   | После перехода `%` на математический модуль таблица соответствия `Mod → srem/urem` перестаёт работать; необходимо перейти на `srem` + коррекцию знака (или на композицию `sdiv`+`mul`+`sub`) и исправить смешение терминов «модуль/остаток»                                                                      |
| **RFC-036** (принят)   | Изменений не требуется. Указать отношение: `==` в позиции `Any` сохраняет сравнение во время выполнения; семейство утверждений `assert_eq` не затрагивается этим шлюзом                                                                                                                                          |

> Основание для переноса `Result` в std: RFC-013 уже позиционирует «`Result(T, Error)` в
> std-библиотеке», RFC-014 в своём разделении на слои относит std к основным источникам. Настоящий
> RFC, этап 2, — один из путей реализации этого; ссылки на несуществующие номера не используются.

## Открытые вопросы

- [x] ~~Нужен ли период совместимости для корректировки семантики `Modulo`?~~ → **Закрыт**:
      справочник языка уже давно указывает «умножение, деление, взятие модуля», текущая реализация
      remainder нарушает опубликованную документацию; обрабатывается как исправление дефекта, без
      периода совместимости (2026-09-22)
- [x] ~~Может ли пользователь добавить реализацию оператора для уже существующего типа (правило
      сирот)?~~ → **Решено**: реализация оператора может быть записана только в модуле определения
      типа. Определение `Int` находится в ядре, поэтому зарегистрировать его может только ядро;
      пользователь может регистрировать только собственные типы. Все типы рассматриваются одинаково,
      встроенные типы не имеют привилегий (2026-09-22)
- [ ] Должен ли `Index` различать изменяемую индексацию (аналог `IndexMut` в Rust)? (В первой партии
      только чтение; изменяемая индексация затрагивает `WriteToken` из RFC-009, при этом в RFC-011a
      уже есть прецедент получателя `&mut Self` — отложить на будущее)
- [ ] Использовать ли упаковку кортежем (текущий подход) или многопараметрическую форму (стиль
      Swift) для `Key` в многопозиционной индексации? (Сохраняем упаковку кортежем, не меняем
      парсер)
- [ ] Форма `Zero` / `One`: член-константа не является оператором; для «членов интерфейса без
      получателя» в RFC-011a нет прецедента; требуется отдельное решение, после которого выражение
      `T: Add + Multiply + Zero` из RFC-011 может быть реализовано полностью
- [ ] Полная форма интерфейса `Try`: `?` требует проверки успеха/неудачи, извлечения полезной
      нагрузки при успехе, выдачи внешнего возвращаемого значения при неудаче — три вещи; одного
      метода `residual` недостаточно; вместе с выводом из эксплуатации специальных случаев парсера
      конструкторов — определить до начала работ этапа 2
- [ ] Префиксный тип `?T` (аннотация FFI-обнуляемости из RFC-026, RFC-018) и постфиксный оператор
      `e?` используют один символ `?`: разные позиции (на уровне типа vs на уровне выражения) не
      создают конфликта — достаточно документального оформления
- [ ] `PartialOrd` / `Ordering` (интерфейсификация операторов сравнения): отдельный RFC, настоящий
      явно не делает этого

### A.3 Места жёсткого прописывания `?` и конструкторов

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

Сторона конструкторов: `ok(T)` / `err(E)` / `some(T)` распознаются парсером (спецификация языка
`syntax.md` §1.4.2); `is_ok` / `unwrap` и т.д. в `std/result.rs` выполняют сопоставление с образцом
по `variant_id 0/1`. «Перенос `Result` в std» требует решения обеих половин (`?` + конструкторы)
вместе; обе относятся к этапу 2.

| Слой 0                        | Фиксированная таблица соответствия оператор → имя метода, константа уровня языка, неизменяемая пользователем                                                                                                      |
| Слой 1                        | База диспетчеризации, выполняющая поиск по ключу `Type.method` и вызов                                                                                                                                            |
| Слой 2                        | Слой контрактов интерфейсов, предоставляющий основания для ограничений обобщённых типов и одновременно являющийся условием пропуска для операторов                                                                |
| Реестр реализаций интерфейсов | Сводная таблица реализаций, агрегирующая регистрации ядра по умолчанию и пользовательские инстанцирования; единственный критерий для запросов операторов и резолвинга ограничений, независимый от разрешения имён |
| Нативный быстрый путь         | Сохраняемый жёстко закодированный путь операций для базовых типов, не проходящий через диспетчеризацию интерфейсов                                                                                                |
| Позиционное связывание        | Синтаксис `f[0]` из RFC-004, привязывающий позиции параметров функции как методы; поведение на этапе компиляции                                                                                                   |
| Автовыведение                 | Генерируемое компилятором посимвольное `==` для записей, все поля которых сравнимы; явное инстанцирование может переопределить                                                                                    |
