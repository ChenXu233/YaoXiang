## Резюме

Дополнение YaoXiang возможностью **перегрузки операторов**, чтобы выражения `a + b` / `a == b` /
`a[i]` / `e?` могли быть реализованы для пользовательских типов, а уже записанные в RFC-011
синтаксические конструкции **ограничений по операторам** (`T: Add + Multiply`) превратились из
**возможности на бумаге** в реально работающий механизм (`Zero` в той же фразе к операторам не
относится — см. открытые вопросы).

Проект использует **разделение ответственности на три уровня**: фиксированная таблица соответствия
оператор→метод (Layer 0), база диспетчеризации по имени (Layer 1, повторно использует существующий
`method_bindings`), слой контракта интерфейса (Layer 2, для ограничений обобщений). **Приоритеты и
ассоциативность операторов остаются фиксированными на уровне языка**; пользователь перегружает
только семантику.

Объём первого этапа: семь интерфейсов — `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal`
`Index`. Арифметические интерфейсы используют **три параметра типа** `(Self, R, O)` — тип результата
`O` делается явным, что позволяет выражать операции над разнотипными операндами, такие как `1 + 2.5`
(возвращает `Float`) и `point * 2.0` (масштабирование). `Equal` **по умолчанию выводится
автоматически** (записи, все поля которых сравнимы, автоматически получают поэлементное `==`); явное
создание экземпляра может это переопределить.

`Try` (интерфейс для `?`) целиком переносится на этап 2: он зависит от принятия RFC-010
(конструирование) и RFC-010b (деконструирование), а форма интерфейса ещё не утверждена (см. открытые
вопросы).

**Никакого нового синтаксиса, никаких новых ключевых слов** — всё повторно использует уже
существующие механизмы RFC-011a (объявление интерфейса / создание экземпляра / объявление внешнего
метода / перегрузка).

## Мотивация

### Почему необходима эта возможность

#### 1. Главный пример RFC-011 зависит от неё, и ситуация хуже, чем «невыполнимое обещание»

RFC-011 (принят) в 8 местах использует имена операторов в качестве ограничений типов:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

Ни в одном из RFC ни разу не определено, откуда берутся `Add` / `Multiply` и как `+` связывается с
ними. Проверка на практике показывает, что ситуация ещё хуже: `T: Add` **сегодня приводит к прямой
ошибке компиляции** — при разрешении ограничений запрашивается старая таблица trait'ов
(`trait_data.rs`), в которой `Add` нет. Имена ограничений `Zero` / `One` / `PartialOrd` / `Fn` /
`FnMut` также повисают в воздухе (их обработка описана в разделе «Согласование с другими RFC»).

#### 2. Пользовательские типы не могут участвовать в базовых операциях (проверено)

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

Сопутствующее последствие: `list.contains(list_of_structs, p)` **полностью неработоспособна** —
внутри она зависит от `==`. При этом `(1, 2) == (1, 2)` и `[1] == [1]` через посимвольное сравнение
во время выполнения **всегда работали** — структура является единственным пробелом.

#### 3. `?` приваривает имя типа к компилятору, блокируя перенос `Result` в std

Реализация `?` одновременно жёстко прописывает имя типа и номера вариантов:

```rust
// typecheck: жёстко закодированное конструирование типа Result
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen: жёстко закодированные имя группы и номер варианта
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

Это вынуждает `Result` оставаться в core. Если бы `?` стала **управляемой интерфейсом**, любой тип,
реализующий этот интерфейс (включая пользовательские), мог бы использоваться с `?`, и `Result` можно
было бы отнести к std (в RFC-013 уже закреплена позиция «`Result(T, Error)` как библиотека std»).

Заметим, что это лишь половина проблемы: формы записи `ok(...)` / `err(...)` / `some(...)` сейчас
также приварены к парсеру (спецификация языка §1.4.2 перечисляет их как «конструкторы,
распознаваемые парсером»). «Перенос `Result` в std» требует решить **обе половины** — и `?`, и
конструкторы — что также относится к этапу 2 настоящего RFC.

#### 4. Пользовательские контейнеры не индексируются

Проверка типов для `Index` представляет собой жёстко закодированный белый список:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// иначе → "Лучше отказать в проверке, чем молча соглашаться с контейнером, не знакомым на уровне типов"
```

Для любого пользовательского контейнера `c[0]` безусловно выдаст ошибку.

#### 5. Реализация `%` нарушает уже опубликованную документацию

Проверка показывает, что `-7 % 3` возвращает `-1` (остаток от деления с усечением). Однако таблица
приоритетов операторов в справочнике языка (`reference/index.md`) уже давно утверждает «`* / %`
умножение-деление-**взятие по модулю**» — документация обещает взятие по модулю, а реализация даёт
остаток. Это не изменение дизайна, а **дефект, при котором реализация нарушает документацию**;
настоящий RFC попутно его исправляет.

### Уже имеющаяся полу-готовая база

Исследование показывает, что **большая часть механизма уже существует** — не хватает лишь
подключения:

| Механизм                                                                  | Расположение                                                                                                                | Состояние                                                                                           |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Объявление интерфейса `(Self: Type) -> Type`                              | RFC-011a Фаза 1                                                                                                             | ✅ Работает                                                                                         |
| Создание экземпляра интерфейса `Animal(Dog)` + объявление внешнего метода | RFC-011a Фазы 2–3                                                                                                           | ✅ Работает (есть юнит-тесты)                                                                       |
| Диспетчеризация методов `method_bindings["Type.method"]`                  | `expressions.rs` (регистрация в `environment.rs`, запрос в `expressions.rs` при разборе вызовов и резервном пути для полей) | ✅ Работает                                                                                         |
| Ассоциированные типы (= параметры типа интерфейса)                        | RFC-011 §3.1; RFC-011a уже принял этот подход                                                                               | ✅ Механизм утверждён                                                                               |
| Вычисление семейств типов `AssociatedTypeDef`                             | `dependent_types.rs`                                                                                                        | ✅ Рабочее применение `IsTrue` в `std.assert`                                                       |
| trait'ы `Equal` / `Dup` / `Clone` / `Debug`                               | зарегистрированы в `trait_data.rs`                                                                                          | ⚠️ `Equal` — ноль потребителей; старое автопроизводное только регистрирует сигнатуру без реализации |
| Соответствие оператор → имя метода                                        | —                                                                                                                           | ❌ Отсутствует                                                                                      |

**Вывод**: это не создание возможности с нуля, а подключение и оформление уже существующих деталей.

## Предложение

### Ключевая идея: разделение ответственности на три уровня

```
Layer 0  Фиксированная таблица соответствий (константа уровня языка, неизменяемая пользователем)
         + → add    == → equal    [] → index    ? → residual
         │  Встроена в компиляцию, не участвует в выводе типов, невидима пользователю
         ▼
Layer 1  База диспетчеризации (поиск метода по имени и вызов)        ← повторно использует существующий механизм
         method_bindings["Point.add"]
         ▼
Layer 2  Контракт интерфейса (для ограничений обобщений)
         Add / Equal / Index / Try …
         Делает ограничение T: Add работоспособным и является условием пропуска оператора
```

**Обоснование разделения**:

- **Layer 0 и 1 делают оператор «работающим»**, Layer 2 делает оператор «ограничиваемым». Слияние
  привело бы к тому, что любой метод с именем `add` вызывался бы через `+`, и ограничение `T: Add`
  из RFC-011 оторвалось бы от операторов.
- **Layer 1 не создаётся заново**: `method_bindings` уже ищет по ключу `Type.method` (резервный путь
  после неудачного поиска поля); операторы просто идут тем же путём.
- **Layer 2 — это условие пропуска**: перед пропуском оператора **необходимо** убедиться, что тип
  реализует соответствующий интерфейс (см. исключение для автопроизводного `Equal` — вывод и
  регистрация подчиняются одному и тому же критерию).

### Имена и регистрация: два независимых канала

**Оператор обращается к «реестру реализаций интерфейса», а не к обычному разрешению имён.**

- Реестр принадлежит ядру и объединяет два источника регистрации: регистрации по умолчанию,
  выполняемые ядром для базовых типов (`Add(Int, Int, Int)` и т. д.), и созданные пользователем
  экземпляры интерфейсов в теле типа (`Add(Point, Point, Point)`). Независимо от того, в каком
  модуле физически находится код реализации, регистрации стекаются в одну таблицу, и `+` / `==` /
  `[]` смотрят только на неё.
- Если в локальном модуле определено **одноимённое** с интерфейсом связывание (например, типовый
  `Add` из RFC-011 §5.2 для сложения на уровне типов Пеано
  `Add: (A: Type, B: Type) -> Type = match ...`), оно проходит через **канал разрешения имён** и
  влияет только на разрешение имени `Add` внутри этого модуля, **не касается реестра и не влияет на
  работоспособность операторов**. Одно имя, разные сущности, без взаимного затенения.

Это одновременно отвечает на вопрос «конфликтует ли типовый `Add` из RFC-011 с интерфейсом `Add` из
настоящего RFC»: нет, не конфликтует. Типовый `Add` — это чисто типовое вычисление (Zero/Succ — это
типы, а не значения, и у них никогда не будет операции над значениями вида `Zero + Succ(...)`), а
интерфейс оператора для значений — это другое прочтение того же имени на уровне значений.

### Layer 0: фиксированная таблица соответствий

| Оператор             | Интерфейс                                                  | Метод              | Первый этап    |
| -------------------- | ---------------------------------------------------------- | ------------------ | -------------- |
| `+`                  | `Add`                                                      | `add`              | ✅             |
| `-`                  | `Subtract`                                                 | `subtract`         | ✅             |
| `*`                  | `Multiply`                                                 | `multiply`         | ✅             |
| `/`                  | `Divide`                                                   | `divide`           | ✅             |
| `%`                  | `Modulo`                                                   | `modulo`           | ✅             |
| `==` `!=`            | `Equal`                                                    | `equal`            | ✅             |
| `[]`                 | `Index`                                                    | `index`            | ✅             |
| `?`                  | `Try` (четыре метода, утверждается в этапе 2)              | `is_failure` и др. | ✅ Реализовано |
| `<` `<=` `>` `>=`    | — (сохраняются нативные инструкции)                        | —                  | ❌             |
| `and` `or`           | — (короткое замыкание — семантика языка, не перегружается) | —                  | ❌             |
| 5 побитовых операций | —                                                          | —                  | ❌             |
| Унарные `-` `!`      | —                                                          | —                  | ❌             |

**Имена интерфейсов используются полностью, а не сокращённо** (`Multiply`, а не `Mul`): это
согласуется с текстом RFC-011, использующим `T: Add + Multiply + Zero`, и **не изменяет уже принятый
RFC**.

**`%` использует семантику `Modulo`** (математический модуль, знак результата совпадает со знаком
делителя). В разделе мотивации уже подтверждено, что текущая реализация остатка нарушает
опубликованную документацию (`reference/index.md`, «умножение-деление-взятие по модулю»); этот пункт
рассматривается как исправление дефекта без сохранения периода совместимости.

Замечание о текущем состоянии: в белом списке проверки типов для `%` сейчас присутствуют только
Int/Float (отличный от белого списка для `+` со значениями Int/Float/String/List); фактические
записи приведены в Приложении A.2.

### Layer 2: определения интерфейсов

#### Арифметические интерфейсы (три параметра типа)

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

Три параметра типа имеют разное назначение:

- `Self`: тип левого операнда (получатель, заимствуется как `&Self`, см. токены заимствования в
  RFC-009 и соглашение о получателе в RFC-011a);
- `R`: тип правого операнда — **левый и правый могут быть разных типов**;
- `O`: **тип результата**, объявлен явно.

**Почему тип результата должен быть явным параметром** (а не жёстко задан как `-> Self`):

1. При жёстко заданном `Self` метод `Add(Int, Float)` должен был бы возвращать `Int`, и `1 + 2.5`
   нельзя было бы выразить корректно;
2. Как только тип результата становится явным, семейство повышающих типов из RFC-011 §8.3
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }` и реестр интерфейсов
   настоящего RFC **становятся двумя взглядами на одну и ту же таблицу** — регистрация ядра
   `Add(Int, Float, Float)` — это та самая строка `(Int, Float) => Float`, а каждое создание
   экземпляра пользователем — это добавление строки в эту таблицу;
3. Интерфейс `Index` уже трёхпараметрический `(Self, Key, Value)` с типом `Value` в качестве
   параметра результата — после того, как арифметические интерфейсы получают `O`, всё семейство
   операторных интерфейсов становится однообразным по форме, а жёстко заданный `Self` оказывается
   исключением.

**Регистрации по умолчанию в ядре** (путь нативных инструкций, не через вызов метода):
`Add(Int, Int, Int)`, `Add(Int, Float, Float)`, `Add(Float, Int, Float)`,
`Add(Float, Float, Float)`, `Add(String, String, String)` (конкатенация),
`Add(List(T), List(T), List(T))` (конкатенация элементов) и т. д. — пять арифметических интерфейсов
обрабатываются аналогично для базовых типов. Выражение `1 + 2.5` из нынешней ошибки компиляции
(белый список требует одинаковых типов с обеих сторон) превращается в легальное выражение,
возвращающее `3.5: Float`.

**Синтаксический сахар для ограничений**: `T: Add` ≜ уже зарегистрировано `Add(T, T, T)` —
самосложение с одним и тем же типом, результат остаётся того же типа. В примере с матричным
умножением из RFC-011 выражение `a * b + c` на всём протяжении имеет тип `T`, что и требует этого
смысла. Аналогично `T: Equal` ≜ `Equal(T, T)`.

**Пример с разными типами** — масштабирование вектора:

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### Интерфейс равенства (автопроизводный по умолчанию)

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` по умолчанию выводится автоматически**, пять правил:

1. **Автопроизводный по умолчанию**: при определении записи, если все её поля сравнимы (базовые
   типы, `String` или сами по себе сравнимые записи/кортежи/списки, и не содержат полей `&mut`),
   компилятор автоматически генерирует **поэлементное сравнение** для `==`, идущее по пути нативного
   кода, без создания видимого пользователю метода. Типы, определённые пользователем, по умолчанию
   сравнимы без каких-либо ритуалов.
2. **Явное переопределение**: если в теле типа указано `Equal(Point, Point)` и предоставлен метод
   `Point.equal`, используется пользовательская версия (например, сравнение чисел с плавающей точкой
   с допуском), а автопроизводное не выполняется.
3. **Если поля несравнимы**: автопроизводное завершается неудачей, `==` недоступен, в диагностике
   указывается, какое именно поле стало препятствием; в этом случае пользователь всё ещё может
   вручную написать `Equal` с собственной логикой сравнения (например, для поля-функции сравнивать
   по имени).
4. **Предусловие**: типы, содержащие линейный токен `&mut T` (рекурсивно по полям), не участвуют в
   сравнении — линейный токен потребляется при однократном чтении, и одновременно извлечь два
   значения для сравнения невозможно. Заметьте, что предусловие касается «нелинейности», а не `Dup`:
   примитивные типы значений (Int/Float/Bool/Char) согласно RFC-011 §2.4 не относятся к `Dup` (для
   них компилятор имеет встроенное копирование значений); если исходить из `Dup`, то
   `Point { x: Float, y: Float }` был бы ошибочно отвергнут.
5. **Единый критерий для ограничений**: разрешение `T: Equal` и пропуск `==` идут по одному и тому
   же правилу «проверить реестр или выполнить структурный вывод» — ограничение и оператор всегда
   дают один и тот же ответ.

**Обоснование согласованности**: `(1, 2) == (1, 2)` и `[1] == [1]` сегодня уже проходят посимвольное
сравнение во время выполнения (белый список сравнения в `executor.rs` включает Tuple/List/Array), и
запись — это единственный составной тип, исключённый из этого правила. Автопроизводное — это не
новое скрытое умолчание, а восполнение уже существующего внутреннего поведения языка до последнего
пробела.

**Вывод из эксплуатации старого механизма**: старое автопроизводное для `Equal` в `trait_data.rs`
(регистрирующее только сигнатуру, без кода реализации и без потребителей) прекращается; вся логика
`Equal` (регистрации по умолчанию для базовых типов, структурный вывод, явные экземпляры)
переводится на реестр интерфейсов. Старая таблица trait'ов сохраняет существующие обязанности по
Clone/Dup/Debug (имена не пересекаются с операторными интерфейсами; вопрос их унификации будет
рассмотрен отдельно).

#### Интерфейс индексирования

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` объявлен параметром типа, а не членом ассоциированного типа**: открытый вопрос RFC-011a
уже закрыт утверждением «ассоциированные типы реализуются через параметры обобщённого интерфейса»
(`Iterator: (Item: Type) -> Type` служит аналогичным прецедентом), что не требует введения
синтаксиса члена `type`.

**Пояснение о владении**: `index` возвращает полное значение `Value`, заимствуя `&Self`. Стандартный
`list.get: (&Vec(A), Int) -> A` уже имеет ту же форму; данный интерфейс **обходится со std так же,
как сейчас**; точная семантика «извлечения полного значения из заимствования» для типов элементов с
move-семантикой будет унифицирована при полном введении в действие RFC-009, настоящий RFC не
изобретает для этого новых правил.

**Многопозиционное индексирование выполняется через упаковку в кортеж + перегрузку**, без введения
вариативного интерфейса:

```yaoxiang
// Одномерный контейнер
List(T) создаёт экземпляр Index(List(T), Int, T)                   → arr[0]

// Многомерный контейнер
Grid    создаёт экземпляр Index(Grid, Tuple(Int, Int), Float)       → g[0, 1]
//                    └─ Key является кортежем

// Два экземпляра с разными сигнатурами → сосуществуют
```

**Для одного типа допускается несколько экземпляров одноимённого интерфейса**, которые сосуществуют
по сигнатурам внедряемых методов в соответствии с правилами перегрузки на уровне методов из
RFC-011a. Перегрузка в RFC-011a явно прописана только до уровня методов; настоящий пункт добавляет
поверх него правило уровня экземпляров: легитимность сосуществования одноимённых экземпляров
интерфейса определяется тем, конфликтуют ли сигнатуры методов после раскрытия (конфликт даёт E1097,
по тем же истокам, что и правила пространства имён полей/методов).

#### Интерфейс распространения Try (утверждён и реализован на этапе 2)

Интерфейсное имя для `?` — `Try`, форма с четырьмя методами (утверждена 2026-09-22 на этапе 2):

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    is_failure: (self: &Self) -> Bool,
    success:    (self: &Self) -> T,
    residual:   (self: &Self) -> E,
    from_error: (E) -> Self,
}
```

- **Разделение обязанностей**: `is_failure` проверяет успех/неуспех, `success` извлекает полезную
  нагрузку успеха, `residual` извлекает полезную нагрузку неуспеха, `from_error` служит мостом для
  распространения через разные типы (когда `T` из `f()?` не совпадает с `U` во внешнем слое, из `E`
  заново собирается значение неуспеха). Понижение `?` единообразно порождает цепочку из четырёх
  вызовов методов — если `is_failure(t)` истинно, выполняется `Ret from_error(residual(t))`, иначе
  значение выражения равно `success(t)`; написанные вручную последовательности проверки вариантов
  более не используются, `Result` / `Option` (реализация в std yx) и пользовательские типы с `Try`
  идут по одному пути.
- **Недостижимые ветви**: ветвь неуспеха в `success` и ветвь успеха в `residual` по контракту
  недостижимы; в реализации расходятся через `assert(false)` (возвращаемое `assert` имеет тип
  `Never`, взрывной принцип `Never <: T` пропускает дальше, type-system.md §2.2).
- **Проверка**: на этапе проверки типов запрашивается реестр реализаций интерфейса (позиция `Self`
  сопоставляется по имени, абстрактные записи конкретизируются по фактическому аргументу scrutinee);
  возвращаемый тип внешней функции также должен реализовывать `Try`, и позиция `E` должна быть
  способна принять значение неуспеха (семантика E1081/E1082/E1083 переводится на интерфейс).
- **Перенос `Result` в std**: определения типов `Result` / `Option` и их реализации `Try`
  переносятся в `std/result.yx` / `std/option.yx` (на чистом YaoXiang), нативные конструкторы
  `ok`/`err` выводятся из эксплуатации — синтаксис конструирования вариантов `Result(T, E).ok(v)`
  становится единственным каналом конструирования (проблема приваренных конструкторов решается
  вместе с выводом из эксплуатации особых случаев в парсере). Остаточный тип `Try` для `Option`
  берётся как `Void` (соответствует семантике NoneT в эксперименте с Try в Rust).

### Примеры

#### Пользовательский тип: арифметика и равенство работают «из коробки»

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false — Equal выведен автоматически, без экземпляра
    println(a == a)             # true
}
```

#### Пользовательское равенство (переопределяет автопроизводное)

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# Сравнение с плавающей точкой с допуском, переопределяет поэлементное автопроизводное
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### Индексирование пользовательского контейнера

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### Ограничения обобщений наконец становятся реализуемыми

```yaoxiang
// Пример из RFC-011 теперь работоспособен
// T: Add ≜ Add(T, T, T) уже зарегистрировано; T: Multiply ≜ Multiply(T, T, T) уже зарегистрировано
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

(В показном примере `T: Add + Multiply + Zero` из RFC-011 `Zero` / `One` выходят за рамки настоящего
RFC — это константные члены, а не операторы; «члены интерфейса без получателя» не имеют прецедента в
RFC-011a, см. открытые вопросы.)

### Изменения синтаксиса

**Никакого нового синтаксиса, никаких новых ключевых слов**. Все возможности получаются комбинацией
существующих механизмов:

| Возможность                     | Используемый существующий механизм                                               |
| ------------------------------- | -------------------------------------------------------------------------------- |
| Объявление интерфейса           | RFC-011a Фаза 1                                                                  |
| Создание экземпляра интерфейса  | RFC-011a Фаза 2 (`Dog: { Animal(Dog) }`)                                         |
| Реализация метода               | RFC-011a Фаза 3 (внешнее объявление `Point.add`)                                 |
| Ассоциированные типы            | RFC-011 §3.1 (параметры типа интерфейса)                                         |
| Многопозиционное индексирование | Существующий разбор упаковки в кортеж + правила перегрузки на уровне экземпляров |
| Приоритет операторов            | **Фиксирован на уровне языка**, пользовательская настройка не допускается        |

## Подробное проектирование

### Влияние на систему типов

**Новые интерфейсы** (Layer 2): `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (`Try`
— на этапе 2).

**Реестр реализаций интерфейсов**: центральный узел проверки операторов. Объединяет регистрации по
умолчанию в ядре (для базовых типов) и экземпляры пользователя (`ImplementationProof`, выдаваемый
`check_interface_instantiation`); проверка пропуска `+` / `==` / `[]` и разрешение ограничения
`T: Add` (`check_trait_bounds` в `bounds.rs`) **запрашивают одну и ту же таблицу** — щели вида
«ограничение говорит «да», оператор — «нет»» не существует.

**Структурный вывод для `Equal`**: поверх реестра накладывается структурное правило (все поля
сравнимы ⇒ тип сравним); для базовых типов их закрывают регистрации в ядре, рекурсия замыкается.
Старая регистрация `Equal` в `trait_data.rs` и старое автопроизводное прекращаются.

**Отделение запросов по операторам от разрешения имён**: операторы вроде `+` запрашивают только
реестр и не идут по обычному разрешению имён; локальные одноимённые связывания (например, семейство
типового `Add`) не влияют на операторы (см. §Имена и регистрация).

**Правило сирот**: реализация оператора может быть записана только в **модуле, определяющем тип** —
определение `Int` находится в ядре, поэтому регистрацию для `Int` может выполнить только ядро;
определение `Point` находится в пользовательском модуле, поэтому зарегистрировать его может только
его автор. Все типы подчиняются одному правилу, встроенные типы не имеют привилегий.

### Поведение во время выполнения

**Нулевые накладные расходы времени выполнения**: цель вызова для оператора определяется на этапе
компиляции (статическая диспетчеризация). Для базовых типов (`Int`/`Float`/`String`/`List`)
сохраняется **быстрый путь нативных инструкций**, не проходящий через диспетчеризацию интерфейса;
автопроизводное структурное `==` порождает нативное поэлементное сравнение; `==` / `!=` в позиции
`Any` (динамический тип) сохраняет существующее сравнение во время выполнения (на это опирается
семейство `assert_eq` в RFC-036 — без изменений).

**Исправление семантики `%`**: `-7 % 3` изменяется с `-1` (остаток от деления с усечением) на `2`
(математический модуль). Изменения вносятся синхронно в три места: интерпретатор (`checked_rem`),
свёртка констант (`a % b`), байт-код (`I64_REM`).

### Обратная совместимость

**Операции над базовыми типами не меняются**: `1 + 2`, `"a" + "b"`, `[1] + [2]`, `1 < 2` — все
сохраняют нативный путь, поведение и производительность не меняются.

**`1 + 2.5` из ошибки компиляции становится допустимым**: после регистрации в ядре
`Add(Int, Float, Float)` смешанная арифметика, прежде отвергавшаяся белым списком, становится
доступной и возвращает `Float`. Это новая возможность, ни один существующий код не затрагивается.

**Исправление семантики `%`**: `-7 % 3` изменяется с `-1` на `2`. Квалифицируется как **исправление
дефекта** (документация давно обещала взятие по модулю, см. мотивацию §5), без периода
совместимости; существующий тестовый материал не содержит случаев, зависящих от `%` с отрицательными
числами (проверено).

**`==` для структур из ошибки времени выполнения становится работоспособным**: ранее
`Struct == Struct` безусловно приводил к ошибке E6007 во время выполнения, после подключения
автопроизводное работает — от плохого к хорошему, ни один существующий легитимный код не
затрагивается.

**`==` для `Any` не затрагивается**: позиция динамического типа сохраняет сравнение во время
выполнения (на это опирается семейство `assert_eq` в RFC-036; ранее работало, продолжает работать).

**Позиционное связывание `f[0]` не меняется**: `distance[0]` — встроенная возможность компилятора из
RFC-004, **не идёт через интерфейс `Index`**, не затрагивается.

**`?` прозрачен для существующего кода** (этап 2): после того, как `Result` получает экземпляр
`Try`, поведение существующих использований `?` остаётся полностью идентичным.

## Компромиссы

### Достоинства

- **Реализуемость ограничений операторов из RFC-011**: `T: Add + Multiply` переходит из бумажного
  состояния (фактически ошибки компиляции) в реально работающее, без изменения уже принятого текста
  RFC
- **Снятие привязки `Result` к core** (этап 2): после перевода `?` и конструкторов на интерфейсы
  `Result` может быть отнесён к std, что согласуется с устоявшейся позицией RFC-013
- **Исправление дефекта, выявленного на практике**: `Point == Point` работает «из коробки», попутно
  устраняется неработоспособность `list.contains` для структур
- **Никакого нового синтаксиса**: всё повторно использует существующие механизмы RFC-011a, не
  затрагиваются правила синтаксиса парсера
- **Нулевые накладные расходы времени выполнения**: статическая диспетчеризация + нативные быстрые
  пути для базовых типов
- **Работоспособность пользовательских контейнеров**: `Box(T)[0]` из состояния «безусловная ошибка»
  переходит в работоспособное
- **Внутренняя согласованность языка**: Tuple/List уже сравниваются поэлементно, записи восполняют
  пробел; арифметические интерфейсы с тремя параметрами однообразны по форме с `Index`; таблица
  повышения типов из RFC-011 §8.3 объединяется с реестром интерфейсов

### Недостатки

- **Автопроизводное для `Equal` — скрытое умолчание**: в будущем отзыв «записи по умолчанию
  сравнимы» станет ломающим изменением. Эта позиция принимается — она согласуется с поведением
  Tuple/List, и явное создание экземпляра всегда может это переопределить
- **Предусловие `Equal` будет отвергать типы с линейными токенами**: типы с полями `&mut` не могут
  быть `==`, что является ценой семантической корректности и требует ясной диагностики (с указанием
  конкретного поля)
- **Создание экземпляра интерфейса — явная стоимость**: для каждого арифметического оператора нужно
  написать строку экземпляра + метод (`Equal` это обходит — автопроизводное). Синтаксис RFC-011a не
  позволяет неявного вывода (компенсируется отсутствием магии с параметром типа `Self`)
- **Исправление семантики `%` — изменение поведения**: хотя оно квалифицируется как исправление
  дефекта, в инструкциях по миграции это следует отметить

## Альтернативы

### Вариант A: Только Layer 1 (диспетчеризация по имени метода), без слоя интерфейсов

`+` просто проверяет наличие метода с именем `add`, без требования реализации интерфейса `Add`.

**Основание отклонения**: ограничение `T: Add` из RFC-011 окажется оторванным от оператора —
ограничение запрашивает интерфейс, оператор — имя метода, и они могут давать противоречивые ответы.
Кроме того, это не позволит на этапе компиляции дать точную диагностику для случая «`+` применён к
несложимому типу».

### Вариант B: Введение синтаксиса конструкторов `Ok(x)` / `Some(x)` для решения проблемы `?`

Интерфейсное представление `?` не делается, вместо этого в тип-сумму добавляется синтаксис
конструкторов.

**Основание отклонения**: конфликтует с RFC-010 (принят). RFC-010 явно устанавливает «единообразное
выражение типов-сумм через записи, **без необходимости в двух синтаксисах**» и явно отвергает
синтаксис `|`. Введение конструкторов — это введение второго способа выражения. К тому же это решает
только `?`, но не решает `Point == Point` и индексирование пользовательских контейнеров.

### Вариант C: Операторы сравнения также в первом эапе (введение `Ordering`)

`<` `<=` `>` `>=` идут через интерфейс `Compare`, возвращающий трёхзначный `Ordering`.

**Основание отклонения**: `<` в YaoXiang уже является **инструкцией IR первого класса**
(`Instruction::Lt/Le/Gt/Ge`); введение интерфейса заставит базовые типы идти обходным путём. К тому
же введение `Ordering` повлечёт за собой целый пласт проблем: собственное сравнение/сортировка
`Ordering`, `PartialOrd` vs `Ord` для `NaN` в плавающей точке и т. д. — это объём самостоятельного
RFC. Потребности, выявленные на практике (`Point == Point`, `list.contains`), требуют **только
`Equal`**.

### Вариант D: Сокращённые имена для операторов (метод интерфейса `Add` называется `add`, интерфейс — `Mul`)

**Основание отклонения**: в тексте RFC-011 уже используется `T: Add + Multiply + Zero`;
использование сокращений потребует изменения уже принятого RFC.

### Вариант E: `Equal` только через явное создание экземпляра, без автопроизводного

**Основание отклонения**: неприемлемо с точки зрения удобства — собственноручно написанный тип
нельзя сравнить через `==`; при этом `(1, 2) == (1, 2)`, `[1] == [1]` сегодня уже сравниваются
поэлементно, и только записи исключены — это изначально несогласованно. Явное создание экземпляра
сохраняется как средство переопределения, что покрывает потребности пользовательской логики.

### Вариант F: Возвращаемый тип арифметических интерфейсов жёстко задан как `-> Self`

**Основание отклонения**: метод `Add(Int, Float)` будет вынужден вернуть `Int`, и `1 + 2.5` нельзя
выразить корректно; масштабирование вектора `Multiply(Point, Float)` аналогично не записывается. К
тому же таблица повышающих типов `(Int, Float) => Float` из RFC-011 §8.3 потеряет место реализации.
Форма с тремя параметрами `(Self, R, O)` согласуется с формой `Index(Key, Value)`.

## Стратегия реализации

### Зависимости

| Зависимость                            | Состояние     | Влияние на части настоящего RFC                                                                       |
| -------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------- |
| Механизм интерфейсов RFC-011a Фазы 1–3 | ✅ Реализован | Фундамент Layer 2 (на практике проверено)                                                             |
| Путь конструирования записей RFC-010   | ✅ Реализован | **Этап 2**: конструирующая сторона `?` + вывод из эксплуатации особых случаев конструкторов в парсере |
| Деконструкция вариантов RFC-010b       | ✅ Реализован | **Этап 2**: запись `match` для `Result.residual`, исчерпываемость                                     |
| Вывод линейных токенов RFC-009         | Частично      | Проверка предусловия `Equal`                                                                          |

### Разделение на этапы

По **зависимостям интерфейсов** (ограничение дизайна, а не срок), делится на две группы:

**Этап 1 — без зависимости от RFC-010/010b**:

- Таблица соответствий Layer 0 + реестр реализаций интерфейсов + подключение диспетчеризации Layer 1
- Семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (форма с тремя
  параметрами типа)
- Автопроизводное `Equal` + предусловие на линейность + перевод разрешения ограничений на реестр
- Исправление семантики `%` (в трёх местах: интерпретатор/свёртка констант/байт-код)
- Сохранение сравнения времени выполнения для позиции `Any`
- **Результат**: становятся доступны `Point + Point`, `Point == Point` (без ритуалов), `Box(T)[0]`,
  `1 + 2.5`, ограничение `T: Add`

**Этап 2 — зависит от RFC-010 / RFC-010b; до начала работ необходимо утвердить форму `Try`**:

- Утверждение формы интерфейса `Try` (см. открытые вопросы)
- Интерфейсное представление `?` + вывод из эксплуатации особых случаев конструкторов
  (`ok`/`err`/`some`) в парсере, переход на путь конструирования записей из RFC-010
- Перенос `Result` из core в std (согласно устоявшейся позиции RFC-013)

### Риски

| Риск                                                                 | Смягчение                                                                                                                      |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Изменение семантики `%` затронет существующий код                    | Квалифицируется как исправление дефекта + проверено отсутствие зависимостей от `%` с отрицательными числами в тестах           |
| Скрытое умолчание автопроизводного `Equal` в будущем трудно отозвать | Позиция утверждена: согласуется с поведением Tuple/List, явное создание экземпляра может переопределить                        |
| Расхождение двух путей базовых типов (нативный + реестр)             | Барьер качества: семантика регистраций в ядре должна совпадать с нативными инструкциями (два взгляда на одну таблицу)          |
| Запросы к реестру замедляют компиляцию                               | Таблица индексируется по имени типа + кэширование результатов создания экземпляров (повторное использование proof из RFC-011a) |
| Перегрузка на уровне экземпляров вносит неоднозначность              | Те же правила, что и для перегрузки на уровне методов: конфликт сигнатур даёт E1097                                            |

## Согласование с другими RFC

Настоящий RFC позиционируется как **инициатор требований со стороны потребителя**; для обеспечения
согласованности необходимо обновить следующие RFC (получено разрешение на правки):

| RFC                                     | Что необходимо обновить                                                                                                                                                                                                                                                                                            |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **RFC-011** (принят)                    | В разделе ограничений отметить, что `Add` / `Multiply` определяются и реализуются в 011b (`T: Add` ≜ `Add(T, T, T)`); пометить `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` как повисшие имена ограничений (ждут последующих RFC); в §8.3 отметить объединение семейства повышающих типов с реестром интерфейсов |
| **RFC-010** (принят)                    | Уточнить требование к реализации «поле записи = конструктор» — это предусловие для вывода из эксплуатации особых случаев конструкторов в парсере на этапе 2                                                                                                                                                        |
| **RFC-010b** (черновик, бывший RFC-039) | Конструирование и деконструирование должны быть парными; проверка исчерпываемости не зависит от принадлежности `Result` к core/std (на этапе 2 в 011b будет выполнен перенос)                                                                                                                                      |
| **RFC-009** (принят)                    | Перекрёстная ссылка в разделе свойств типов: предусловие `Equal` — «отсутствие линейного токена `&mut`» (а не `Dup`)                                                                                                                                                                                               |
| **RFC-013** (принят)                    | При реализации этапа 2: формулировки `E1081` / `E1082` освобождаются от слова «Result»; диагностика предусловия `Equal` переиспользует семейство `E1101` — синхронизация трёх сторон по процедуре RFC-013 (codes/*.rs ↔ locales ↔ таблица кодов)                                                                   |
| **RFC-018** (принят)                    | После перехода `%` на математический модуль таблица соответствий `Mod → srem/urem` становится недействительной, требуется заменить на `srem` + коррекцию знака (либо на композицию `sdiv`+`mul`+`sub`) и исправить смешение терминов «модуль/остаток»                                                              |
| **RFC-036** (принят)                    | Изменений не требуется. Указать отношение: `==` в позиции `Any` сохраняет сравнение времени выполнения, семейство утверждений `assert_eq` не подвержено влиянию шлюза                                                                                                                                              |

> Основание для переноса `Result` в std: в RFC-013 уже закреплена позиция «`Result(T, Error)` как
> библиотека std», в RFC-014 слоистая структура относит std к ядру исходников. Настоящий RFC, этап
> 2, — один из путей её реализации; ссылки на несуществующие номера более не используются.

      только ядро; пользователь может регистрировать только собственные типы. Все типы равноправны,
      встроенные типы не имеют привилегий (2026-09-22)

      этапе — только чтение; изменяемое индексирование затрагивает `WriteToken` из RFC-009, и в

- [ ] Упаковка многопозиционного индексирования в кортеж (текущее состояние) или переход к
      нескольким параметрам (в стиле Swift)? (Сохраняется упаковка в кортеж, парсер не изменяется)
- [ ] Форма `Zero` / `One` : константные члены — не операторы; «члены интерфейса без получателя» не
      имеют прецедента в RFC-011a и требуют отдельного утверждения, после чего вся фраза
      `T: Add + Multiply + Zero` из RFC-011 становится полностью реализуемой
- [ ] Полная форма интерфейса `Try`: для `?` требуются три вещи — проверка успеха/неуспеха,
      извлечение полезной нагрузки успеха, выдача значения неуспеха во внешний возвращаемый тип;

- [ ] Префиксный тип `?T` (аннотация обнуляемости в FFI из RFC-026, RFC-018) и постфиксный оператор

- [ ] `PartialOrd` / `Ordering` (интерфейсное представление операторов сравнения): отдельный RFC,
      настоящий RFC явно не покрывает это

### A.3 Места жёсткого кодирования `?` и конструкторов

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

Сторона конструкторов: `ok(T)` / `err(E)` / `some(T)` распознаются парсером (спецификация языка,
`syntax.md` §1.4.2); `std/result.rs` использует `is_ok` / `unwrap` и т. д. с сопоставлением по
`variant_id 0/1`. «Перенос `Result` в std» требует решения обеих половин (`?` + конструкторы), что
относится к этапу 2.

| Вывод `Equal`                                    | Автопроизводное по умолчанию + переопределение через явное создание экземпляра; одинаковый критерий для разрешения ограничений | «Собственный тип нельзя ==» неприемлемо; Tuple/List уже сравниваются поэлементно, Struct — единственный пробел                                                         | 2026-09-22 |
| Предусловие `Equal`                              | «Отсутствие линейного токена `&mut`», **а не `Dup`**                                                                           | RFC-011 §2.4 явно указывает, что примитивы не относятся к `Dup`; исходить из `Dup` — ошибочно отвергать `Point{Float,Float}`                                           | 2026-09-22 |
| Отделение имён от регистрации                    | Оператор запрашивает только реестр реализаций интерфейса, не проходит разрешение имён                                          | Локальные одноимённые связывания (типовый `Add` и др.) не мешают операторам; пример из RFC-011 §5.2 не требует изменений                                               | 2026-09-22 |
| Правило сирот                                    | Реализация следует за модулем, определяющим тип                                                                                | Все типы равноправны, встроенные типы не имеют привилегий                                                                                                              | 2026-09-22 |
| `==` для `Any`                                   | Сохранить сравнение времени выполнения, не запрашивать реестр                                                                  | На это опирается семейство утверждений `assert_eq` в RFC-036                                                                                                           | 2026-09-22 |
| Форма `Try`                                      | Утверждена: четыре метода (is_failure/success/residual/from_error) + семантика недостижимости через assert-Never; реализована  | `?` требует три вещи, одного метода `residual` недостаточно; вывод из эксплуатации особых случаев конструкторов в парсере происходит вместе с переносом `Result` в std | 2026-09-22 |
| Квалификация семантики `%`                       | Исправление дефекта (документация уже обещала модуль), без периода совместимости                                               | `reference/index.md`, «умножение-деление-взятие по модулю», служит доказательством                                                                                     | 2026-09-22 |
| Основание для переноса `Result` в std            | Ссылка на устоявшуюся позицию RFC-013, без ссылок на несуществующие номера                                                     | В RFC-013 уже записано «`Result(T, Error)` как библиотека std»                                                                                                         | 2026-09-22 |

## Приложение C: глоссарий

| Термин                        | Определение                                                                                                                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Layer 0                       | Фиксированная таблица соответствий оператор→имя метода, константа уровня языка, неизменяема пользователем                                                                             |
| Layer 1                       | База диспетчеризации: поиск и вызов по ключу `Type.method`                                                                                                                            |
| Layer 2                       | Слой контракта интерфейса, даёт основание для ограничений обобщений и одновременно является условием пропуска оператора                                                               |
| Реестр реализаций интерфейсов | Объединённая таблица регистраций по умолчанию в ядре и экземпляров пользователя; единственный критерий для запросов операторов и разрешения ограничений, не связан с разрешением имён |
| Нативный быстрый путь         | Сохраняемый для базовых типов жёстко закодированный путь выполнения операций, не проходящий через диспетчеризацию интерфейса                                                          |
| Позиционное связывание        | Синтаксис `f[0]` из RFC-004, привязывающий позиции аргументов функции как методы; поведение времени компиляции                                                                        |
| Автопроизводное               | Поэлементное `==`, автоматически генерируемое компилятором для записей, все поля которых сравнимы; может быть переопределено явным созданием экземпляра                               |
