## Резюме

Дополнение YaoXiang возможностью **перегрузки операторов**, чтобы `a + b` / `a == b` / `a[i]` / `e?`
могли быть реализованы пользовательскими типами, а **ограничения операторов** (`T: Add + Multiply`)
из синтаксиса ограничений, уже записанного в RFC-011, превратились из **бумажных возможностей** в
реализуемый механизм (`Zero` в той же фразе не относится к операторам, см. открытые вопросы).

В дизайне применяется **разделение ответственности на три уровня**: фиксированная таблица
отображения оператор→метод (Layer 0), база диспетчеризации по имени (Layer 1, повторно использующая
существующую `method_bindings`) и уровень контракта интерфейса (Layer 2, для ограничений generics).
**Приоритет и ассоциативность операторов остаются фиксированными в языке**; пользователи перегружают
только семантику.

Первая партия областей: семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal`
`Index`. Арифметические интерфейсы используют **три параметра типа** `(Self, R, O)` — тип результата
`O` делается явным, что позволяет выражать разнотипные операции вроде `1 + 2.5` (возвращает `Float`)
и `point * 2.0` (масштабирование). `Equal` **по умолчанию выводится автоматически** (записи, у
которых все поля поддерживают сравнение, автоматически получают `==` со сравнением полей); явное
инстанцирование может это переопределить.

`Try` (интерфейсификация `?`) в целом перенесён в Фазу 2: он зависит от реализации RFC-010
(конструкция) и RFC-010b (деконструкция), и форма интерфейса ещё не определена (см. открытые
вопросы).

**Никакого нового синтаксиса, никаких новых ключевых слов** — всё повторно использует существующие
механизмы RFC-011a (объявление интерфейса / инстанцирование / объявление внешнего метода /
перегрузка).

## Мотивация

### Зачем нужна эта возможность

#### 1. Главный пример RFC-011 зависит от неё, и текущее положение хуже, чем «невозможно выполнить»

RFC-011 (принят) в 8 местах использует имена операторов как type constraints:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

Во всём множестве RFC ни один документ не определяет, откуда берутся `Add` / `Multiply` и как `+`
связывается с ними. Эмпирическая проверка подтверждает, что ситуация ещё хуже: `T: Add` **сегодня
приводит к прямой ошибке компиляции** — поиск ограничений обращается к старой таблице trait-ов
(`trait_data.rs`), в которой `Add` отсутствует. Имена ограничений `Zero` / `One` / `PartialOrd` /
`Fn` / `FnMut` так же остаются висячими (об их обработке см. «Согласование с другими RFC»).

#### 2. Пользовательские типы не могут участвовать в базовых операциях (эмпирически)

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

Сопутствующее последствие: `list.contains(list_of_structs, p)` **полностью неработоспособен** —
внутри он зависит от `==`. В то же время `(1, 2) == (1, 2)` и `[1] == [1]` используют поэлементное
сравнение во время выполнения и **всегда работают** — структура является единственным пробелом.

#### 3. `?` намертво вшивает имя типа в компилятор, блокируя перенос `Result` в std

Реализация `?` одновременно жёстко кодирует имя типа и номера вариантов:

```rust
// typecheck: жёстко закодированное конструирование типа Result
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen: жёстко закодированное имя группы и номера вариантов
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

Это вынуждает `Result` оставаться в core. Если `?` перевести на **управление через интерфейс**,
любой тип, реализующий этот интерфейс (включая пользовательские), сможет использоваться с `?`, и
`Result` можно будет отнести к std (в RFC-013 уже есть позиционирование «стандартная библиотека
`Result(T, Error)`»).

Заметим, что это лишь половина проблемы: формы записи конструкторов `ok(...)` / `err(...)` /
`some(...)` сейчас тоже намертво вшиты в парсер (в спецификации языка §1.4.2 они перечислены как
«конструкторы, распознаваемые парсером»). «Перенос `Result` в std» требует решить **обе половины** —
и `?`, и конструкторы — что и делается в Фазе 2 настоящего RFC.

#### 4. Пользовательские контейнеры не индексируются

Проверка типов для `Index` представляет собой жёстко закодированный белый список:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// остальные → "контейнер, не опознанный на уровне типов, лучше явно отвергнуть"
```

Любой пользовательский контейнер — и `c[0]` гарантированно выдаёт ошибку.

#### 5. Реализация `%` нарушает опубликованную документацию

Эмпирически `-7 % 3` возвращает `-1` (остаток от деления с усечением). Однако в таблице приоритетов
операторов в справочнике языка (`reference/index.md`) уже написано «`* / %` умножение/деление **по
модулю**» — документация обещает модуль, а реализация даёт остаток. Это не изменение дизайна, а
**дефект реализации, нарушающий документацию**, который настоящий RFC исправляет попутно.

### Существующий полуфабрикат

Исследование показало, что бо́льшая часть механизма **уже на месте**, не хватает лишь подключения:

| Механизм                                                              | Расположение                                                                                                                                  | Статус                                                                                                         |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Объявление интерфейса `(Self: Type) -> Type`                          | RFC-011a Фаза 1                                                                                                                               | ✅ Работает                                                                                                    |
| Инстанцирование интерфейса `Animal(Dog)` + объявление внешнего метода | RFC-011a Фазы 2–3                                                                                                                             | ✅ Работает (есть unit-тесты)                                                                                  |
| Диспетчеризация методов `method_bindings["Type.method"]`              | `expressions.rs` (регистрация в `environment.rs`, запрос в `expressions.rs` — путь разбора вызовов и путь fallback при неудачном поиске поля) | ✅ Работает                                                                                                    |
| Associated types (= параметр типа интерфейса)                         | RFC-011 §3.1; RFC-011a уже принял этот подход                                                                                                 | ✅ Механизм определён                                                                                          |
| Вычисление type family `AssociatedTypeDef`                            | `dependent_types.rs`                                                                                                                          | ✅ Боевой пример `IsTrue` из `std.assert`                                                                      |

**Вывод**: это не создание возможности с нуля, а подключение и оформление уже существующих деталей.

## Предложение

### Основной дизайн: разделение ответственности на три уровня

```
Layer 0  Фиксированная таблица отображения (константа уровня языка, неизменяемая пользователем)
         + → add    == → equal    [] → index    ? → residual
         │  Встроена на этапе компиляции, не участвует в type inference, не доступна пользователю
         ▼
Layer 1  База диспетчеризации (поиск метода по имени и вызов)        ← повторное использование существующего механизма
         method_bindings["Point.add"]
         ▼
Layer 2  Контракт интерфейса (для ограничений generics)
         Add / Equal / Index / Try …
         Делает работающим ограничение T: Add, и одновременно служит условием допуска для оператора
```

**Обоснование разделения**:

- **Layer 0 и 1 делают оператор «пригодным к использованию»**, Layer 2 делает его «доступным для
  ограничений». Слияние привело бы к тому, что любой метод с именем `add` вызывался бы через `+`, и
  ограничение `T: Add` из RFC-011 оказалось бы оторванным от операторов.
- **Layer 1 не создаётся заново**: `method_bindings` уже ищет по ключу `Type.method` (путь fallback
  после неудачного поиска поля); оператор идёт по тому же пути.
- **Layer 2 — это условие допуска**: перед допуском оператора **необходимо** убедиться, что тип
  реализует соответствующий интерфейс (см. исключение для `Equal` — автоматический вывод и
  регистрация используют один и тот же критерий).

### Имена и регистрация: два независимых канала

**Оператор запрашивает «реестр реализаций интерфейсов», минуя обычное разрешение имён.**

- Реестр принадлежит ядру и агрегирует две регистрации: регистрации по умолчанию, выполняемые ядром
  для базовых типов (`Add(Int, Int, Int)` и т. п.), и инстанцирования интерфейсов, записываемые
  пользователем внутри тела типа (`Add(Point, Point, Point)`). Куда бы ни попал код реализации
  физически, регистрации стекаются в одну и ту же таблицу; `+` / `==` / `[]` смотрят только в неё.
- Локально определённое в модуле **одноимённое связывание** (например, типовый `Add` из §5.2
  RFC-011: `Add: (A: Type, B: Type) -> Type = match ...`) идёт по **каналу разрешения имён**, влияет
  только на разрешение имени `Add` в этом модуле, **не касается реестра и не влияет на пригодность
  оператора**. Однофамильцы не затеняют друг друга.

Это заодно отвечает на вопрос «конфликтует ли типовый `Add` из RFC-011 с интерфейсным `Add`
настоящего RFC»: нет. Типовый `Add` — это чисто типовый расчёт (Zero/Succ являются типами, а не
значениями, и никогда не возникнет выражение уровня значений вида `Zero + Succ(...)`); интерфейсный
`Add` — это уровень значений. Одно и то же имя, но разные уровни.

### Layer 0: фиксированная таблица отображения

| Оператор          | Интерфейс                                                  | Метод              | Первая партия  |
| ----------------- | ---------------------------------------------------------- | ------------------ | -------------- |
| `+`               | `Add`                                                      | `add`              | ✅             |
| `-`               | `Subtract`                                                 | `subtract`         | ✅             |
| `*`               | `Multiply`                                                 | `multiply`         | ✅             |
| `/`               | `Divide`                                                   | `divide`           | ✅             |
| `%`               | `Modulo`                                                   | `modulo`           | ✅             |
| `==` `!=`         | `Equal`                                                    | `equal`            | ✅             |
| `[]`              | `Index`                                                    | `index`            | ✅             |
| `?`               | `Try` (четыре метода, форма в Фазе 2)                      | `is_failure` и др. | ✅ Реализовано |
| `<` `<=` `>` `>=` | — (оставлены как нативные инструкции)                      | —                  | ❌             |
| `and` `or`        | — (короткое замыкание — семантика языка, не перегружается) | —                  | ❌             |
| 5 побитовых       | —                                                          | —                  | ❌             |
| Унарные `-` `!`   | —                                                          | —                  | ❌             |

**Имена интерфейсов — полные, а не сокращённые** (`Multiply`, а не `Mul`): остаёмся в согласии с
текстом RFC-011 — `T: Add + Multiply + Zero` — **не трогая уже принятый RFC**.

**`%` использует семантику `Modulo`** (математический модуль, знак результата совпадает со знаком
делителя). В разделе «Мотивация» уже подтверждено, что текущая реализация remainder нарушает
опубликованную документацию (`reference/index.md`, «умножение/деление по модулю»), этот пункт
рассматривается как исправление дефекта без периода совместимости.

Примечание о текущем состоянии: белый список проверки типов для `%` сейчас охватывает только
Int/Float (в отличие от белого списка `+` для Int/Float/String/List), практические записи см. в
Приложении A.2.

### Layer 2: определения интерфейсов

#### Арифметические интерфейсы (три параметра типа)

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

У трёх параметров типа чёткое разделение обязанностей:

- `Self`: тип левого операнда (получатель, `&Self` — заимствование, см. токены заимствования из
  RFC-009 и соглашение о получателях в RFC-011a);
- `R`: тип правого операнда — **левый и правый могут различаться**;
- `O`: **тип результата**, объявлен явно.

**Почему тип результата должен быть явным параметром** (а не жёстко зашитым `-> Self`):

1. При жёстко зашитом `Self` метод `Add(Int, Float)` был бы вынужден вернуть `Int`, и `1 + 2.5` не
   могло бы быть выражено корректно;
2. Когда тип результата сделан явным, type family повышения из §8.3 RFC-011 —
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }` — и реестр интерфейсов
   настоящего RFC **становятся двумя точками зрения на одну и ту же таблицу**: регистрация ядра
   `Add(Int, Float, Float)` — это и есть строка `(Int, Float) => Float`, а каждое инстанцирование
   пользователя добавляет строку в эту таблицу;
3. Интерфейс `Index` и так трёхпараметрический `(Self, Key, Value)` с типом возврата `Value` в
   качестве параметра — арифметические интерфейсы, получив `O`, унифицируют форму всего семейства
   операторных интерфейсов; жёстко зашитый `Self` был бы исключением.

**Регистрации по умолчанию в ядре** (нативный путь инструкций, не через вызов метода):
`Add(Int, Int, Int)`, `Add(Int, Float, Float)`, `Add(Float, Int, Float)`,
`Add(Float, Float, Float)`, `Add(String, String, String)` (конкатенация),
`Add(List(T), List(T), List(T))` (конкатенация элементов) и т. п.; пять арифметических интерфейсов
для базовых типов — аналогично. `1 + 2.5` из нынешней ошибки компиляции (белый список требует
одинаковых типов с обеих сторон) превращается в легальную операцию, возвращающую `3.5: Float`.

**Синтаксический сахар ограничения**: `T: Add` ≜ `Add(T, T, T)` зарегистрировано — самостоятельная
композиция с одинаковым типом, результат остаётся этим типом. В примере с матричным умножением из
RFC-011 у `a * b + c` тип всюду `T`, и именно это и требуется. `T: Equal` аналогично ≜
`Equal(T, T)`.

**Пример разнотипной операции** — масштабирование вектора:

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### Интерфейс равенства (автоматический вывод по умолчанию)

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` по умолчанию выводится автоматически** — пять правил:

1. **Вывод по умолчанию**: при определении record-типа, если все поля поддерживают сравнение
   (базовые типы, `String`, либо сами сравнимые записи/кортежи/списки, и не содержат полей `&mut`),
   компилятор автоматически генерирует `==` со сравнением полей за полем по нативному пути кода, без
   создания видимого пользователю метода. Пользовательский тип сравним «из коробки» без каких-либо
   формальностей.
2. **Явное переопределение**: если в теле типа записано `Equal(Point, Point)` и предоставлен метод
   `Point.equal`, используется пользовательская версия (например, сравнение с допуском для чисел с
   плавающей точкой), и автоматический вывод не выполняется.
3. **Если поля несравнимы**: автоматический вывод завершается неудачей, `==` недоступен, диагностика
   указывает, какое именно поле мешает; пользователь при этом всё ещё может вручную описать `Equal`
   с пользовательским сравнением (например, сравнивать поля-функции по имени).
4. **Предусловие**: типы, содержащие линейный токен `&mut T` (рекурсивно в полях), не участвуют в
   сравнении — линейный токен потребляется при однократном чтении, и взять два значения одновременно
   для сравнения невозможно. Заметьте, что предусловие — «нелинейность», а не «Dup»: примитивные
   типы значений (Int/Float/Bool/Char) согласно §2.4 RFC-011 не относятся к Dup (это встроенная в
   компилятор копия значений); если бы предусловие опиралось на Dup, то
   `Point { x: Float, y: Float }` был бы ошибочно отвергнут.
5. **Единый критерий ограничения**: разрешение `T: Equal` и допуск `==` идут по одному и тому же
   правилу — «проверка реестра или структурный вывод» — ограничение и оператор всегда дают
   одинаковый ответ.

**Обоснование согласованности**: `(1, 2) == (1, 2)` и `[1] == [1]` уже сегодня идут по поэлементному
сравнению во время выполнения (белый список сравнения в `executor.rs` включает Tuple/List/Array);
record — единственный исключённый составной тип. Автоматический вывод не вводит новое молчаливое
умолчание, а дополняет существующее внутреннее поведение языка до последнего пробела.

**Вывод из эксплуатации старого механизма**: старая запись `Equal` в `trait_data.rs` (которая только
регистрировала сигнатуру без реализации и не имела точек потребления) отключается; все решения по
`Equal` (регистрация по умолчанию для базовых типов, структурный вывод, явное инстанцирование) идут
через реестр интерфейсов. Старая таблица trait-ов сохраняет существующие обязанности по
Clone/Dup/Debug (имена не пересекаются с операторными интерфейсами, будущее объединение — отдельный
вопрос).

#### Интерфейс индексирования

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` — параметр типа, а не член associated type**: открытый вопрос из RFC-011a уже закрыт в
пользу «associated types через параметры обобщённого интерфейса» (`Iterator: (Item: Type) -> Type` —
изоморфный прецедент), вводить синтаксис членов `type` не нужно.

**Замечание о владении**: `index` возвращает полное `Value` из заимствования `&Self`.
`list.get: (&Vec(A), Int) -> A` в стандартной библиотеке уже имеет такую же форму; настоящий
интерфейс **получает то же обращение, что и текущее состояние std**; точная семантика «извлечения
полного значения из заимствования» для типов элементов с move-семантикой будет унифицирована при
полном применении RFC-009, и настоящий RFC не изобретает для этого новых правил.

**Многопозиционное индексирование — через упаковку в кортеж + перегрузку**, без введения интерфейса
с переменным числом аргументов:

```yaoxiang
// Одномерный контейнер
List(T) инстанцирует Index(List(T), Int, T)                   → arr[0]

// Многомерный контейнер
Grid    инстанцирует Index(Grid, Tuple(Int, Int), Float)       → g[0, 1]
//                    └─ Key — это кортеж

// Два инстанцирования с разными сигнатурами → сосуществуют
```

**Для одного типа разрешены несколько инстанцирований одноимённого интерфейса**, различающихся по
сигнатурам инжектируемых методов и сосуществующих по правилам перегрузки на уровне методов из
RFC-011a. Перегрузка в RFC-011a явно определена только до уровня методов; настоящий RFC дополняет её
правилом уровня инстанцирования: легитимность сосуществования одноимённых инстанцирований интерфейса
определяется тем, конфликтуют ли развёрнутые сигнатуры методов (конфликт → E1097, по тому же
источнику, что и правила пространства имён полей/методов).

#### Интерфейс распространения Try (форма утверждена и реализована в Фазе 2)

Интерфейсное имя для `?` — `Try`, форма с четырьмя методами (утверждена 22.09.2026 в Фазе 2):

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    is_failure: (self: &Self) -> Bool,
    success:    (self: &Self) -> T,
    residual:   (self: &Self) -> E,
    from_error: (E) -> Self,
}
```

- **Разделение семантики**: `is_failure` определяет успех/неудачу, `success` извлекает полезную
  нагрузку успеха, `residual` — нагрузку неудачи, `from_error` служит мостом для распространения
  между типами (когда `T` в `f()?` не совпадает с `U` внешнего контекста, он восстанавливает
  значение неудачи из `E`). Понижение `?` единообразно генерирует цепочку из четырёх вызовов
  методов: если `is_failure(t)` истинно, то `Ret from_error(residual(t))`, иначе выражение принимает
  значение `success(t)`; ручные последовательности проверки вариантов больше не пишутся — `Result` /
  `Option` (реализация в std) и пользовательские Try-типы проходят по одному пути.
- **Тупиковые ветви**: ветвь неудачи `success` и ветвь успеха `residual` по контракту недостижимы;
  реализация расходится через `assert(false)` (assert возвращает `Never`, принцип взрыва
  `Never <: T` пропускает, type-system.md §2.2).
- **Проверка**: typecheck запрашивает реестр реализаций интерфейсов (позиция Self — номинальное
  соответствие, абстрактные записи инстанцируются по фактическому scrutinee); тип возврата внешней
  функции также должен реализовывать `Try`, а позиция `E` должна принимать значение неудачи
  (семантика E1081/E1082/E1083 переводится на интерфейсы).
- **`Result` переносится в std**: определения типов `Result` / `Option` и реализации `Try` мигрируют
  в `std/result.yx` / `std/option.yx` (чистый YaoXiang), нативные конструкторы `ok`/`err` выводятся
  из эксплуатации — синтаксис конструирования вариантов `Result(T, E).ok(v)` становится единственным
  каналом конструирования (проблема намертво вшитых конструкторов решается вместе с выводом из
  эксплуатации специальных случаев в парсере). Остаточный тип Try для `Option` берётся как `Void`
  (соответствует семантике NoneT из эксперимента Try в Rust).

### Примеры

#### Пользовательский тип: арифметика и равенство из коробки

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false — Equal выведен автоматически, без инстанцирования
    println(a == a)             # true
}
```

#### Пользовательское равенство (переопределение автоматического вывода)

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# Сравнение чисел с плавающей точкой с допуском, переопределяет посравнение полей
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### Пользовательское индексирование контейнера

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### Ограничения generics наконец реализуемы

```yaoxiang
// Пример из RFC-011 теперь можно реализовать
// T: Add ≜ Add(T, T, T) зарегистрировано; T: Multiply ≜ Multiply(T, T, T) зарегистрировано
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

(`Zero` / `One` в показном примере RFC-011 `T: Add + Multiply + Zero` **вне области настоящего RFC**
— это член-константы, а не операторы; для «членов интерфейса без получателя» в RFC-011a нет
прецедента, см. открытые вопросы.)

**Никакого нового синтаксиса, никаких новых ключевых слов**. Все возможности — это комбинация уже
существующих механизмов:

| Возможность                     | Используемый существующий механизм                                                |
| ------------------------------- | --------------------------------------------------------------------------------- |
| Объявление интерфейса           | RFC-011a Фаза 1                                                                   |
| Инстанцирование интерфейса      | RFC-011a Фаза 2 (`Dog: { Animal(Dog) }`)                                          |
| Реализация метода               | RFC-011a Фаза 3 (внешнее объявление `Point.add`)                                  |

## Детальный дизайн

### Влияние на type system

**Новые интерфейсы** (Layer 2): `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (`Try`
— в Фазе 2).

**Реестр реализаций интерфейсов**: центральный узел принятия решений для операторов. Агрегирует
регистрации по умолчанию ядра (базовые типы) и пользовательские инстанцирования
(`ImplementationProof`, выдаваемые `check_interface_instantiation`); проверка допуска `+` / `==` /
`[]` и разрешение ограничения `T: Add` (функция `check_trait_bounds` из `bounds.rs`) **запрашивают
одну и ту же таблицу** — между «ограничение говорит — да», а «оператор говорит — нет» не может быть
зазора.

**Структурный вывод `Equal`**: поверх реестра накладывается структурное правило (все поля
поддерживают сравнение ⇒ сравнимо), базовые типы покрываются регистрациями ядра, замыкание
рекурсивно. Старая регистрация `Equal` и старый автоматический вывод из `trait_data.rs` отключаются.

**Разделение запросов операторов и разрешения имён**: операторы вроде `+` обращаются только к
реестру, минуя обычное разрешение имён; локальные одноимённые связывания (например, типовый `Add` из
§5.2 RFC-011) не влияют на операторы (см. «Имена и регистрация»).

**Правило сирот**: реализация оператора может быть записана только в **модуле, определяющем тип** —
`Int` определён в ядре, поэтому регистрацию `Int` может выполнить только ядро; `Point` определён в
пользовательском модуле, поэтому зарегистрировать его может только его определитель. Все типы
подчиняются одному правилу, встроенные типы не имеют привилегий.

### Поведение во время выполнения

**Нулевые накладные расходы во время выполнения**: цель вызова оператора определяется на этапе
компиляции (статическая диспетчеризация). Для базовых типов (`Int`/`Float`/`String`/`List`)
сохраняется **путь быстрого доступа к нативным инструкциям**, минуя диспетчеризацию через интерфейс;
автоматически выведенный `==` для структур генерирует нативное посимвольное сравнение; `==`/`!=` в
позиции `Any` (динамический тип) сохраняет существующее сравнение во время выполнения (тестовый
фреймворк RFC-036 использует `assert_eq`, который зависит от этого поведения и не затрагивается).

**Исправление семантики `%`**: `-7 % 3` меняется с `-1` (остаток с усечением) на `2` (математический
модуль). Три места — интерпретатор (`checked_rem`), constant folding (`a % b`), байт-код (`I64_REM`)
— изменяются синхронно.

### Обратная совместимость

**Операции с базовыми типами не меняются**: `1 + 2`, `"a" + "b"`, `[1] + [2]`, `1 < 2` — все
сохраняют нативный путь, поведение и производительность не меняются.

**`1 + 2.5` из ошибки компиляции становится легальным**: после регистрации ядра
`Add(Int, Float, Float)` смешанная арифметика, ранее отвергавшаяся белым списком, становится
доступной и возвращает `Float`. Это новая возможность, ни один существующий код не затрагивается.

**Исправление семантики `%`**: `-7 % 3` меняется с `-1` на `2`. Квалифицируется как **исправление
дефекта** (документация давно обещала модуль, см. §5 мотивации), без периода совместимости; в
существующем тестовом корпусе нет случаев, зависящих от `%` с отрицательными числами (проверено).

**`==` для структур из ошибки во время выполнения становится доступным**: ранее `Struct == Struct`
всегда выдавал ошибку E6007 во время выполнения; после подключения автоматически выведенный `==`
становится доступным — переход от плохого к хорошему, ни один существующий легальный код не
затрагивается.

**`==` для `Any` не затрагивается**: позиция динамического типа сохраняет сравнение во время
выполнения (семейство утверждений `assert_eq` из RFC-036 зависит от этого; ранее работало — и после
продолжает работать).

**Позиционное связывание `f[0]` не меняется**: `distance[0]` — это встроенная возможность
компилятора из RFC-004, **не идёт через интерфейс `Index`** и не затрагивается.

**`?` прозрачен для существующего кода** (Фаза 2): после добавления к `Result` инстанцирования `Try`
существующие варианты использования `?` ведут себя полностью идентично.

## Компромиссы

### Достоинства

- **Реализация операторных ограничений RFC-011**: `T: Add + Multiply` из формального (фактически —
  ошибки компиляции) становится реализуемым, без изменения уже принятого текста RFC
- **Снятие привязки `Result` к core** (Фаза 2): после перевода `?` и конструкторов на интерфейсы
  `Result` может быть отнесён к std, что согласуется с существующим позиционированием RFC-013
- **Исправление эмпирического дефекта**: `Point == Point` работает из коробки, заодно устраняется
  неработоспособность `list.contains` для структур
- **Нулевой новый синтаксис**: всё повторно использует существующие механизмы RFC-011a, правила
  синтаксиса парсера не затрагиваются
- **Нулевые накладные расходы во время выполнения**: статическая диспетчеризация + нативный быстрый
  путь для базовых типов
- **Пользовательские контейнеры пригодны к использованию**: `Box(T)[0]` из «всегда ошибка»
  становится доступным
- **Внутренняя согласованность языка**: Tuple/List уже сравниваются поэлементно, record дополняет
  это; форма арифметических интерфейсов с тремя параметрами унифицирована с `Index`; таблица
  повышения из §8.3 RFC-011 объединяется с реестром интерфейсов

### Недостатки

- **Автоматический вывод `Equal` — молчаливое умолчание**: в будущем, если потребуется отозвать
  «records по умолчанию сравнимы», это станет разрушающим изменением. Принимаем эту позицию — это
  согласуется с уже существующим поведением Tuple/List, а явное инстанцирование всегда может
  переопределить
- **Предусловие `Equal` отвергает типы с линейными токенами**: типы, содержащие `&mut`, не могут
  использовать `==` — это семантически правильно, но требует ясной диагностики (с указанием, какое
  именно поле)
- **Инстанцирование интерфейса — явная стоимость**: для каждого арифметического оператора нужно
  записать строку инстанцирования + один метод (для `Equal` сделано исключение — автоматический
  вывод). Синтаксис RFC-011a не допускает неявного вывода (что даёт «отсутствие магии» у параметра
  типа `Self`)
- **Исправление семантики `%` — изменение поведения**: хотя оно квалифицируется как исправление
  дефекта, его всё же нужно отметить в примечаниях по миграции

## Альтернативы

### Вариант A: только Layer 1 (диспетчеризация по имени метода), без уровня интерфейсов

`+` только проверяет наличие метода с именем `add`, не требуя реализации интерфейса `Add`.

**Причина отклонения**: ограничение `T: Add` из RFC-011 окажется оторванным от операторов —
ограничение запрашивает интерфейс, а оператор — имя метода, и они могут давать несовместимые ответы.
Кроме того, невозможно на этапе компиляции дать точную диагностику для «`+` применён к несложимому
типу».

### Вариант B: ввести синтаксис конструкторов `Ok(x)` / `Some(x)` для решения проблемы `?`

Не интерфейсифицировать `?`, а добавить синтаксис конструкторов для сумма-типов.

**Причина отклонения**: конфликтует с RFC-010 (принят). RFC-010 явно устанавливает «единообразное
использование record-типов для выражения сумма-типов, **две системы синтаксиса не нужны**» и явно
отвергает синтаксис `|`. Ввод конструкторов вводит вторую систему выражения. Кроме того, это решает
только `?`, но не `Point == Point` и не индексирование пользовательских контейнеров.

### Вариант C: операторы сравнения тоже в первой партии (с введением `Ordering`)

`<` `<=` `>` `>=` идут через интерфейс `Compare`, возвращающий трёхзначный `Ordering`.

**Причина отклонения**: `<` в YaoXiang уже является **IR-инструкцией первого класса**
(`Instruction::Lt/Le/Gt/Ge`); интерфейсификация заставит базовые типы идти обходным путём. Кроме
того, ввод `Ordering` потянет за собой целый набор вопросов — сравнение/сортировка самого
`Ordering`, `PartialOrd` vs `Ord` для `NaN` с плавающей точкой и т. п. — масштаба отдельного RFC.
Текущие эмпирические потребности (`Point == Point`, `list.contains`) требуют **только `Equal`**.

### Вариант D: имена операторов — сокращённые (метод интерфейса `Add` — `add`, интерфейс — `Mul`)

**Причина отклонения**: в тексте RFC-011 уже записано `T: Add + Multiply + Zero`; использование
сокращений потребовало бы изменения уже принятого RFC.

### Вариант E: `Equal` только с явным инстанцированием, без автоматического вывода

**Причина отклонения**: неприемлемо, что пользовательский тип нельзя сравнивать через `==`; кроме
того, `(1, 2) == (1, 2)` и `[1] == [1]` уже сегодня сравниваются поэлементно, а record был
единственным исключением — это и так несогласованно. Явное инстанцирование сохраняется как средство
переопределения, что учитывает потребности пользовательских сравнений.

### Вариант F: тип возврата арифметического интерфейса жёстко зашит как `-> Self`

**Причина отклонения**: метод `Add(Int, Float)` был бы вынужден вернуть `Int`, и `1 + 2.5` не могло
бы быть выражено корректно; масштабирование вектора `Multiply(Point, Float)` тоже невозможно
записать. Кроме того, type family повышения `(Int, Float) => Float` из §8.3 RFC-011 потерял бы место
для реализации. Форма с тремя параметрами `(Self, R, O)` унифицирована с `Index(Key, Value)`.

## Стратегия реализации

### Зависимости

| Зависимость                             | Статус            | Какая часть настоящего RFC затрагивается                                                                    |
| --------------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------- |
| Механизмы интерфейсов RFC-011a Фазы 1–3 | ✅ Реализовано    | Основа Layer 2 (эмпирически работает)                                                                       |
| Путь конструирования record из RFC-010  | ❌ Не реализовано | **Фаза 2**: сторона конструирования `?` + вывод из эксплуатации специальных случаев конструкторов в парсере |
| Деконструкция вариантов из RFC-010b     | ❌ На бумаге      | **Фаза 2**: запись `match` в `Result.residual`, исчерпываемость                                             |
| Вывод линейных токенов из RFC-009       | Частично          | Проверка предусловия `Equal`                                                                                |

### По фазам

Делятся на две группы по **зависимостям интерфейсов** (проектное ограничение, не расписание):

**Фаза 1 — без зависимости от RFC-010/010b**:

- Таблица отображения Layer 0 + реестр реализаций интерфейсов + подключение диспетчеризации Layer 1
- Семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (форма с тремя
  параметрами типа)
- Автоматический вывод `Equal` + предусловие линейности + перенаправление разрешения ограничений в
  реестр
- Исправление семантики `%` (три места: интерпретатор / constant folding / байт-код)
- `==` в позиции `Any` сохраняет сравнение во время выполнения
- **Результат**: `Point + Point`, `Point == Point` (без формальностей), `Box(T)[0]`, `1 + 2.5`,
  ограничение `T: Add` — всё становится доступным

**Фаза 2 — зависит от RFC-010 / RFC-010b; форма `Try` должна быть утверждена до начала работ**:

- Утверждение формы интерфейса `Try` (см. открытые вопросы)
- Интерфейсификация `?` + вывод из эксплуатации специальных случаев конструкторов
  (`ok`/`err`/`some`) в парсере, переход на путь конструирования record из RFC-010
- Перенос `Result` из core в std (согласно существующему позиционированию RFC-013)

### Риски

| Риск                                                                          | Смягчение                                                                                                                     |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Изменение семантики `%` затрагивает существующий код пользователя             | Квалифицируется как исправление дефекта + тестовый корпус проверен на отсутствие зависимостей от `%` с отрицательными числами |
| Молчаливое умолчание автоматического вывода `Equal` в будущем трудно отозвать | Позиция определена: согласуется с уже существующим поведением Tuple/List, явное инстанцирование может переопределить          |
| Несогласованность двух путей для базовых типов (нативный + реестр)            | Контроль: семантика регистраций ядра должна совпадать с нативными инструкциями (две точки зрения на одну таблицу)             |
| Запросы к реестру замедляют компиляцию                                        | Таблица индексируется по имени типа + кешируются результаты инстанцирования (повторное использование proof из RFC-011a)       |
| Перегрузка уровня инстанцирования вводит неоднозначность                      | То же правило, что и для перегрузки на уровне методов: конфликт сигнатур → E1097                                              |

## Согласование с другими RFC

Настоящий RFC позиционируется как **инициатор требований потребителя**; для обеспечения
согласованности необходимо синхронно обновить следующие RFC (получено разрешение на редактирование):

| RFC                                      | Что нужно обновить                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011** (принят)                     | В местах ограничений указать, что `Add` / `Multiply` определяются и реализуются в 011b (`T: Add` ≜ `Add(T, T, T)`); пометить `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` как висячие имена ограничений (до последующих RFC); для type family повышения в §8.3 указать, что она объединяется с реестром интерфейсов |
| **RFC-010** (принят)                     | Уточнить требование к реализации правила «поле record — это конструктор» — это предусловие для вывода из эксплуатации специальных случаев конструкторов в парсере в Фазе 2                                                                                                                                            |
| **RFC-010b** (черновик, исходно RFC-039) | Конструкция и деконструкция должны идти парой; исчерпываемость не зависит от принадлежности `Result` к core/std (миграция произойдёт в Фазе 2 011b)                                                                                                                                                                   |
| **RFC-009** (принят)                     | В месте свойств типов перекрёстная ссылка: предусловие `Equal` — «не содержит линейного токена `&mut`» (не Dup)                                                                                                                                                                                                       |
| **RFC-013** (принят)                     | При реализации Фазы 2: тексты `E1081` / `E1082` очищаются от слова «Result»; диагностика предусловия `Equal` повторно использует семейство `E1101` — по процессу RFC-013 — трёхсторонняя синхронизация (codes/*.rs ↔ locales ↔ таблица кодов)                                                                         |
| **RFC-018** (принят)                     | После переключения `%` на математический модуль таблица отображения `Mod → srem/urem` становится недействительной, нужно перейти на `srem` + коррекцию знака (или синтез `sdiv`+`mul`+`sub`) и исправить смешение терминов «модуль / остаток»                                                                         |
| **RFC-036** (принят)                     | Изменения не требуются. Указать отношение: `==` в позиции `Any` сохраняет сравнение во время выполнения, семейство утверждений `assert_eq` не затрагивается воротами                                                                                                                                                  |

> Основание для переноса `Result` в std: RFC-013 уже позиционирует «стандартная библиотека
> `Result(T, Error)`», RFC-014 своим разделением относит std к core-источникам. Фаза 2 настоящего
> RFC — один из путей её реализации; ссылки на несуществующие номера больше не используются.

- [x] ~~Нужен ли период совместимости для исправления семантики `Modulo`?~~ → **Закрыт**: в
      справочнике языка давно записано «умножение/деление по модулю», текущая реализация remainder

- [x] ~~Может ли пользователь дополнить реализацию оператора для уже существующего типа (правило

      определяющем тип. `Int` определён в ядре, поэтому зарегистрировать его может только ядро;
      пользователь может зарегистрировать только свой тип. Все типы равны, встроенные типы не имеют
      привилегий (22.09.2026)
- [ ] Нужно ли в `Index` различать изменяемое индексирование (по аналогии с `IndexMut` в Rust)? (В
      первой партии только чтение; изменяемое индексирование затрагивает `WriteToken` из RFC-009, и
      в RFC-011a уже есть прецедент получателя `&mut Self` — оставлено на будущее)
- [ ] Многопозиционное индексирование: Key упаковывается в кортеж (текущее состояние) или меняется
      на мультипараметры (стиль Swift)? (Продолжаем упаковку в кортеж, парсер не меняется)
- [ ] Форма `Zero` / `One`: член-константы — не операторы, для «членов интерфейса без получателя» в
      RFC-011a нет прецедента; после отдельного решения только и можно реализовать всю фразу
      `T: Add + Multiply + Zero` из RFC-011
- [ ] Полная форма интерфейса `Try`: для `?` нужны три вещи — определение успеха/неудачи, извлечение
      полезной нагрузки успеха, формирование значения неудачи для возврата наружу; одного метода
      `residual` недостаточно; вместе с выводом из эксплуатации специальных случаев конструкторов в
      парсере — утверждается до начала Фазы 2
- [ ] Префиксный тип `?T` (аннотация FFI-null из RFC-026, RFC-018) и постфиксный оператор `e?`
      используют один и тот же символ `?`: разные позиции (позиция типа vs позиция выражения) не
      создают конфликта, достаточно оформить это документально
- [ ] `PartialOrd` / `Ordering` (интерфейсификация операторов сравнения): отдельный RFC, настоящий
      RFC явно не делает этого

Все эмпирические данные ниже воспроизведены на **0.8.0** (`target/debug/yaoxiang-rs.exe`).

### A.1 Доступность механизма интерфейсов (основа настоящего RFC)

| Возможность                                                                     | Эмпирическая проверка                                              |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Объявление интерфейса `Animal: (Self: Type) -> Type = {...}`                    | ✅ Определяется                                                    |
| Инстанцирование интерфейса + внешний метод `Dog: { Animal(Dog) }` + `Dog.speak` | ✅ Работает, вывод корректен (есть unit-тест в `tests/rfc011a.rs`) |
| Инстанцирование интерфейса + **внутреннее** объявление метода                   | ❌ `E1097` (конфликт общего пространства имён полей и методов)     |
| Диспетчеризация метода `d.speak()`                                              | ✅ Работает                                                        |

**Примечание**: `E1097` означает, что методы операторов должны использовать форму **внешнего
объявления** (`Point.add: (self: &Point, ...)`), что согласуется с примерами RFC-011a. Регистрация
`method_bindings` происходит в `environment.rs` (`add_method_binding`), запросы — в
`expressions.rs`, в пути разбора цели вызова и в пути fallback при неудачном поиске поля.

### A.2 Текущее состояние операторов

| Выражение                               | Текущее состояние                                                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `1 + 2` / `"a" + "b"` / `[1] + [2]`     | ✅ Жёстко закодированный белый список (Int/Float/String/List, **требует одинаковых типов с обеих сторон**) |
| `1 + 2.5` (Int + Float)                 | ❌ Ошибка компиляции (белый список требует одинаковых типов с обеих сторон)                                |
| `-7 % 3`                                | `-1` (остаток с усечением; белый список `%` охватывает только Int/Float, в отличие от белого списка `+`)   |
| `Point(1,2) == Point(1,2)`              | ❌ `E6007` (Eq завершается ошибкой во время выполнения на Struct)                                          |
| `(1,2) == (1,2)` / `[1] == [1]`         | ✅ Поэлементное сравнение во время выполнения (Struct — единственный пробел)                               |
| `==` в позиции `Any` (`assert_eq`)      | ✅ Сравнение во время выполнения (эмпирически подтверждено в RFC-036)                                      |
| `f[0]` (позиционное связывание функции) | ⚠️ Легально только внутри объявления связывания, в качестве выражения — `E3006`                            |
| `arr[0, 1]` (многопозиционное)          | ✅ Упаковка в кортеж, `list([1, 2])`                                                                       |

### A.3 Места жёсткого кодирования `?` и конструкторов

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

Сторона конструкторов: `ok(T)` / `err(E)` / `some(T)` распознаются парсером (спецификация языка
`syntax.md` §1.4.2); `is_ok` / `unwrap` и т. п. в `std/result.rs` сопоставляют с образцом по
`variant_id 0/1`. «Перенос `Result` в std» требует решения **обеих половин** (`?` + конструкторы)
одновременно, обе — в Фазе 2.

| Форма `Try`                                   | Утверждена: четыре метода (is_failure/success/residual/from_error) + семантика assert-Never для тупиков; реализовано   | Для `?` нужны три вещи, одного метода `residual` недостаточно; специальные случаи конструкторов в парсере выводятся из эксплуатации вместе с переносом Result в std       | 2026-09-22 |
| Квалификация семантики `%`                    | Исправление дефекта (документация уже обещала модуль), без периода совместимости                                       | `reference/index.md` «умножение/деление по модулю» — первичное доказательство                                                                                             | 2026-09-22 |
| Основание переноса `Result` в std             | Ссылка на существующее позиционирование RFC-013, без ссылок на несуществующие номера                                   | В RFC-013 уже записано «стандартная библиотека `Result(T, Error)`»                                                                                                        | 2026-09-22 |

## Приложение C: глоссарий

| Термин                        | Определение                                                                                                                                                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Layer 0                       | Фиксированная таблица отображения оператор → имя метода, константа уровня языка, неизменяемая пользователем                                                                             |
| Layer 1                       | База диспетчеризации, ищущая по ключу `Type.method` и вызывающая                                                                                                                        |
| Layer 2                       | Уровень контракта интерфейса, дающий основания для ограничений generics, а также являющийся условием допуска оператора                                                                  |
| Реестр реализаций интерфейсов | Агрегирует регистрации по умолчанию ядра и пользовательские инстанцирования; единственный критерий для запросов операторов и разрешения ограничений, не пересекается с разрешением имён |
| Нативный быстрый путь         | Жёстко закодированный путь операций для базовых типов, минующий диспетчеризацию через интерфейс                                                                                         |
| Позиционное связывание        | Синтаксис `f[0]` из RFC-004, привязывающий позицию параметра функции как метод; поведение compile-time                                                                                  |
| Автоматический вывод          | Сгенерированный компилятором посимвольный `==` для записей, у которых все поля поддерживают сравнение; может быть переопределён явным инстанцированием                                  |
