## Резюме

Дополняет YaoXiang возможностью **перегрузки операторов**, позволяя `a + b` / `a == b` / `a[i]` /
`e?` реализовывать для пользовательских типов, и превращает **ограничения операторов**
(`T: Add + Multiply`) из синтаксиса ограничений, уже записанного в RFC-011, из **бумажной
возможности** в реализуемый механизм (`Zero` в том же предложении не является оператором, см.
открытые вопросы).

В проекте применяется **разделение обязанностей на три уровня**: фиксированная таблица соответствия
оператор→метод (уровень 0), база диспетчеризации по имени (уровень 1, переиспользует существующий
`method_bindings`), слой контракта интерфейса (уровень 2, для ограничений обобщений). **Приоритет и
ассоциативность** операторов остаются фиксированными в языке — пользователь перегружает только
семантику.

Объём первого этапа: семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`.
Арифметические интерфейсы используют **три параметра типа** `(Self, R, O)` — тип результата `O`
явный, что позволяет выражать разнотипные операции вроде `1 + 2.5` (возвращает `Float`) и
`point * 2.0` (масштабирование). `Equal` **по умолчанию выводится автоматически** (записи со всеми
сравнимыми полями автоматически получают поэлементный `==`), явное создание экземпляра может
переопределить это.

`Try` (интерфейс `?`) целиком переносится на этап 2: он зависит от принятия RFC-010
(конструирование) и RFC-010b (деконструирование), а форма интерфейса ещё не определена (см. открытые
вопросы).

**Никакого нового синтаксиса, никаких новых ключевых слов** — всё переиспользует существующие
механизмы RFC-011a (объявление интерфейса / создание экземпляра / объявление внешних методов /
перегрузка).

## Мотивация

### Зачем нужна эта возможность

#### 1. Основные примеры RFC-011 зависят от неё, и текущее состояние хуже, чем «невыполнимо»

RFC-011 (принят) использует имена операторов как ограничения типов в 8 местах:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

Ни в одном из набора RFC не определено, откуда берутся `Add` / `Multiply` и как `+` связывается с
ними. Тестирование подтверждает, что ситуация ещё хуже: `T: Add` **сегодня приводит к прямой ошибке
компиляции** — разрешение ограничений запрашивает старую таблицу trait (`trait_data.rs`), в которой
нет `Add`. Имена ограничений `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` также висят в воздухе
(обработку см. в разделе «Согласование с другими RFC»).

#### 2. Пользовательские типы не могут участвовать в базовых операциях (тест)

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

Сопутствующее последствие: `list.contains(list_of_structs, p)` **полностью неработоспособно** — оно
внутренне зависит от `==`. При этом `(1, 2) == (1, 2)` и `[1] == [1]` через посимвольное сравнение в
рантайме **всегда работают** — структура является единственным пробелом.

#### 3. `?` приваривает имя типа к компилятору, блокируя перенос `Result` в std

Реализация `?` одновременно жёстко кодирует имя типа и номер варианта:

```rust
// typecheck: жёстко кодирует конструирование типа Result
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen: жёстко кодирует имя группы и номер варианта
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

Это вынуждает `Result` оставаться в core. Если `?` сделать **управляемым через интерфейс**, любой
тип, реализовавший этот интерфейс (включая пользовательские), сможет использоваться с `?`, и
`Result` можно будет отнести к std (в RFC-013 уже есть позиционирование «std-библиотека
`Result(T, Error)`»).

Заметим, что это лишь половина проблемы: записи конструирования `ok(...)` / `err(...)` / `some(...)`
сейчас также приварены к парсеру (спецификация языка §1.4.2 перечисляет их как «конструкторы,
распознаваемые парсером»). Для «переноса `Result` в std» нужно решить **обе половины** — `?` и
конструкторы — вместе, и оба относятся к этапу 2 данного RFC.

#### 4. Пользовательские контейнеры не могут индексироваться

Проверка типов `Index` — это жёстко закодированный белый список:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// иначе → «неизвестный контейнер на уровне типов — лучше отказать, чем молча пройти»
```

Для любого пользовательского типа контейнера `c[0]` всегда приводит к ошибке.

#### 5. Реализация `%` нарушает опубликованную документацию

Тестирование показывает, что `-7 % 3` возвращает `-1` (усечённый остаток). Однако в таблице
приоритетов операторов в справочнике языка (`reference/index.md`) уже написано «`* / %`
умножение/деление **взятие модуля**» — документация обещает взятие модуля, а реализация даёт
остаток. Это не изменение дизайна, а **дефект реализации, нарушающий документацию**; данный RFC
попутно исправляет это.

### Существующая полуготовая база

Исследование показало, что **большая часть механизма уже на месте** — не хватает лишь подключения:

| Механизм                                                       | Расположение                                                                                                                        | Состояние                                                                                     |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Объявление интерфейса `(Self: Type) -> Type`                   | RFC-011a Фаза 1                                                                                                                     | ✅ работает                                                                                   |
| Создание экземпляра `Animal(Dog)` + объявление внешнего метода | RFC-011a Фазы 2–3                                                                                                                   | ✅ работает (есть юнит-тесты)                                                                 |
| Диспетчеризация методов `method_bindings["Type.method"]`       | `expressions.rs` (регистрация в `environment.rs`, запрос в `expressions.rs` при разрешении вызовов и в резервном пути поиска полей) | ✅ работает                                                                                   |
| Ассоциированные типы (= параметры типа интерфейса)             | RFC-011 §3.1; RFC-011a принял этот подход                                                                                           | ✅ механизм определён                                                                         |
| Вычисление семейств типов `AssociatedTypeDef`                  | `dependent_types.rs`                                                                                                                | ✅ рабочий пример `IsTrue` из `std.assert`                                                    |
| trait `Equal` / `Dup` / `Clone` / `Debug`                      | зарегистрированы в `trait_data.rs`                                                                                                  | ⚠️ `Equal` не используется; старое автовыведение только регистрирует сигнатуру без реализации |
| Соответствие оператор → имя метода                             | —                                                                                                                                   | ❌ отсутствует                                                                                |

**Вывод**: это не создание возможности с нуля, а подключение и оформление уже существующих деталей.

## Предложение

### Основной проект: разделение обязанностей на три уровня

```
Уровень 0  Фиксированная таблица соответствия (константа уровня языка, неизменяемая)
           + → add    == → equal    [] → index    ? → residual
           │  Встроена на этапе компиляции, не участвует в выводе типов, невидима для пользователя
           ▼
Уровень 1  База диспетчеризации (поиск метода по имени и вызов)   ← переиспользует существующий механизм
           method_bindings["Point.add"]
           ▼
Уровень 2  Контракт интерфейса (для ограничений обобщений)
           Add / Equal / Index / Try …
           Делает ограничение T: Add валидным и служит условием допуска для оператора
```

**Обоснование разделения**:

- **Уровни 0 и 1 делают оператор «работоспособным»**, уровень 2 делает оператор «ограничиваемым».
  Слияние привело бы к тому, что любой метод с именем `add` вызывался бы через `+`, и ограничение
  `T: Add` из RFC-011 оторвалось бы от операторов.
- **Уровень 1 не создаётся заново**: `method_bindings` уже выполняет поиск по ключу `Type.method`
  (резервный путь после неудачного поиска поля); операторы идут тем же путём.
- **Уровень 2 — условие допуска**: перед допуском оператор **обязан** убедиться, что тип реализует
  соответствующий интерфейс (см. исключение для автовыведения `Equal` — вывод и регистрация
  используют один и тот же критерий).

### Имена и регистрация: два независимых канала

**Оператор обращается к «реестру реализаций интерфейса», минуя обычное разрешение имён.**

- Реестр принадлежит ядру и агрегирует регистрации из двух источников: регистрации ядра по умолчанию
  для базовых типов (`Add(Int, Int, Int)` и т.д.) и экземпляры интерфейсов, записанные пользователем
  в теле типа (`Add(Point, Point, Point)`). Куда бы ни был физически помещён код реализации,
  регистрация попадает в единую таблицу, и `+` / `==` / `[]` смотрят только в неё.
- Локальное **одноимённое связывание** `Add` в модуле (например, типовый `Add` из RFC-011 §5.2 —
  типоуровневое сложение Пеано `Add: (A: Type, B: Type) -> Type = match ...`) идёт по **каналу
  разрешения имён** и влияет только на разрешение имени `Add` внутри модуля, **не касается реестра и
  не влияет на работоспособность оператора**. Одно имя — разные сущности, не затеняют друг друга.

Это одновременно отвечает на вопрос «не конфликтует ли типоуровневый `Add` из RFC-011 с интерфейсом
`Add` данного RFC»: не конфликтует. Типоуровневый `Add` — это чисто вычислительный артефакт на
уровне типов (Zero/Succ — это типы, а не значения, никогда не будет операции `Zero + Succ(...)` над
значениями), на одном уровне имён с операторным интерфейсом значений они являются разными слоями.

### Уровень 0: фиксированная таблица соответствия

| Оператор          | Интерфейс                                                | Метод              | Первый этап    |
| ----------------- | -------------------------------------------------------- | ------------------ | -------------- |
| `+`               | `Add`                                                    | `add`              | ✅             |
| `-`               | `Subtract`                                               | `subtract`         | ✅             |
| `*`               | `Multiply`                                               | `multiply`         | ✅             |
| `/`               | `Divide`                                                 | `divide`           | ✅             |
| `%`               | `Modulo`                                                 | `modulo`           | ✅             |
| `==` `!=`         | `Equal`                                                  | `equal`            | ✅             |
| `[]`              | `Index`                                                  | `index`            | ✅             |
| `?`               | `Try` (четыре метода, форма на этапе 2)                  | `is_failure` и др. | ✅ реализовано |
| `<` `<=` `>` `>=` | — (нативные инструкции сохранены)                        | —                  | ❌             |
| `and` `or`        | — (короткое замыкание — семантика языка, неперегружаемо) | —                  | ❌             |
| 5 побитовых       | —                                                        | —                  | ❌             |
| Унарные `-` `!`   | —                                                        | —                  | ❌             |

**Имена интерфейсов — полные, не сокращённые** (`Multiply`, а не `Mul`): для согласованности с
основным текстом RFC-011, где записано `T: Add + Multiply + Zero`, **без изменения уже принятого
RFC**.

**`%` использует семантику `Modulo`** (математический модуль, знак результата следует за делителем).
В разделе мотивации уже подтверждено, что текущая реализация с остатком нарушает опубликованную
документацию (`reference/index.md`, «умножение/деление взятие модуля»), данный пункт рассматривается
как исправление дефекта — без периода совместимости.

Примечание о состоянии: белый список проверки типов для `%` в настоящее время содержит только
Int/Float (отличается от белого списка для `+`, куда входят Int/Float/String/List); в приложении A.2
есть записи тестирования.

### Уровень 2: определения интерфейсов

#### Арифметические интерфейсы (три параметра типа)

```yaoxiang
Add: (Self: Type, R: Type, O: Type) -> Type = {
    add: (self: &Self, other: &R) -> O
}

Subtract: (Self: Type, R: Type, O: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> O
}

Multiply: (Self: Type, R: Type, O: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> O
}

Divide: (Self: Type, R: Type, O: Type) -> Type = {
    divide: (self: &Self, other: &R) -> O
}

Modulo: (Self: Type, R: Type, O: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> O
}
```

Три параметра типа играют разные роли:

- `Self`: тип левого операнда (получатель, заимствуется как `&Self`, см. токены заимствования
  RFC-009 и соглашение о получателе в RFC-011a);
- `R`: тип правого операнда — **левый и правый могут быть разных типов**;
- `O`: **тип результата**, объявлен явно.

**Почему тип результата должен быть явным параметром** (а не жёстко зашитым `-> Self`):

1. При жёстко зашитом `Self` метод `Add(Int, Float)` должен возвращать `Int`, и `1 + 2.5` невозможно
   выразить корректно;
2. Как только тип результата становится явным, семейство типов приведения из RFC-011 §8.3
   `Add: (A, B) -> Type = match (A, B) { (Int, Float) => Float, ... }` и реестр интерфейсов данного
   RFC **становятся двумя взглядами на одну и ту же таблицу** — запись ядра `Add(Int, Float, Float)`
   — это та же строка `(Int, Float) => Float`, а каждый пользовательский экземпляр — это добавление
   строки в таблицу;
3. Интерфейс `Index` изначально трёхпараметрический `(Self, Key, Value)`, тип возврата `Value` — это
   параметр. После того как арифметические интерфейсы получают `O`, всё семейство операторных
   интерфейсов приобретает единообразную форму, а жёстко зашитый `Self` становится исключением.

**Регистрации ядра по умолчанию** (путь нативных инструкций, не через вызов метода):
`Add(Int, Int, Int)`, `Add(Int, Float, Float)`, `Add(Float, Int, Float)`,
`Add(Float, Float, Float)`, `Add(String, String, String)` (конкатенация),
`Add(List(T), List(T), List(T))` (конкатенация элементов) и т.д.; то же для пяти арифметических
интерфейсов на базовых типах. `1 + 2.5` из текущей ошибки компиляции (белый список требует
одинаковых типов с обеих сторон) превращается в валидное выражение, возвращающее `3.5: Float`.

**Синтаксический сахар для ограничений**: `T: Add` ≜ зарегистрировано `Add(T, T, T)` —
самосовмещение с тем же типом, результат остаётся тем же типом. В примере матричного умножения из
RFC-011 `a * b + c` имеет тип `T` повсюду, что и требует именно этого смысла. `T: Equal` аналогично
≜ `Equal(T, T)`.

**Пример с разными типами** — масштабирование вектора:

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Multiply(Point, Float, Point),
}

Point.multiply: (self: &Point, other: &Float) -> Point =
    Point(self.x * other, self.y * other)

main: () -> Void = {
    p = Point(1.0, 2.0)
    q = p * 3.0              # Point(3.0, 6.0)
}
```

#### Интерфейс равенства (автовыведение по умолчанию)

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` автовыводится по умолчанию**, правила пяти:

1. **Автовыведение по умолчанию**: при определении записи, если все поля сравнимы (базовые типы,
   `String`, либо сами сравнимые записи/кортежи/списки, и нет полей `&mut`), компилятор
   автоматически генерирует **поэлементное сравнение** для `==`, идущее по пути нативного кода, без
   генерации видимого пользователю метода. Пользовательские типы сравнимы без каких-либо церемоний.
2. **Явное переопределение**: если в теле типа записано `Equal(Point, Point)` и предоставлен метод
   `Point.equal`, используется версия пользователя (например, сравнение Float с допуском), а не
   автовыведение.
3. **Когда поле несравнимо**: автовыведение завершается неудачей, `==` недоступен, диагностика
   указывает, какое именно поле стало препятствием; в этом случае пользователь всё ещё может вручную
   написать `Equal` с собственной логикой сравнения (например, для полей-функций сравнивать по
   имени).
4. **Предусловие**: типы, содержащие **линейные токены `&mut T`** (поля с рекурсией), не участвуют в
   сравнении — линейный токен потребляется при однократном чтении, и невозможно одновременно извлечь
   два значения для сравнения. Заметьте, предусловие — «нелинейность», а не «Dup»: примитивные типы
   значений (Int/Float/Bool/Char) по RFC-011 §2.4 не относятся к Dup (это встроенное в компилятор
   копирование значений); если исходить из Dup, то `Point { x: Float, y: Float }` будет ошибочно
   отвергнут.
5. **Единый критерий для ограничений**: разрешение `T: Equal` и допуск `==` идут по одному и тому же
   правилу «проверить реестр или выполнить структурный вывод» — ограничение и оператор всегда дают
   один и тот же ответ.

**Обоснование согласованности**: `(1, 2) == (1, 2)` и `[1] == [1]` уже сегодня проходят через
поэлементное сравнение в рантайме (белый список сравнения в `executor.rs` включает
Tuple/List/Array); запись — единственный исключённый составной тип. Автовыведение — не новый
негласный дефолт, а дополнение последнего недостающего фрагмента до поведения, уже существующего
внутри языка.

**Вывод из эксплуатации старого механизма**: старая авторегистрация `Equal` в `trait_data.rs`
(только сигнатура без реализации, ноль точек потребления) прекращается; вся диспетчеризация `Equal`
(регистрации ядра по умолчанию для базовых типов, структурный вывод, явные экземпляры) идёт через
реестр интерфейсов. Старая таблица trait сохраняет существующие обязанности Clone/Dup/Debug (имена
не пересекаются с операторными интерфейсами, унификация — предмет отдельного обсуждения).

#### Интерфейс индексирования

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` — параметр типа, а не член ассоциированного типа**: открытый вопрос RFC-011a уже закрыт —
«ассоциированный тип реализуется через параметр обобщённого интерфейса»
(`Iterator: (Item: Type) -> Type` служит прецедентом с той же структурой), нет нужды вводить
синтаксис членов `type`.

**Замечание о владении**: `index` возвращает полное значение `Value` из заимствования `&Self`.
Стандартный `list.get: (&Vec(A), Int) -> A` уже имеет ту же форму; данный интерфейс **получает тот
же режим, что и текущее состояние std**; точная семантика «извлечения полного значения из
заимствования» для типов элементов с move-семантикой подлежит унифицированной обработке при полном
введении в действие RFC-009; данный RFC не изобретает для этого новых правил.

**Многопозиционное индексирование достигается упаковкой в кортеж + перегрузкой**, без введения
вариативных интерфейсов:

```yaoxiang
// Одномерный контейнер
List(T) инстанцирует Index(List(T), Int, T)                   → arr[0]

// Многомерный контейнер
Grid    инстанцирует Index(Grid, Tuple(Int, Int), Float)       → g[0, 1]
//                    └─ Key — кортеж

// Два экземпляра с разными сигнатурами → сосуществуют
```

**Одноимённые интерфейсы одного типа допускают несколько экземпляров**, различающихся по сигнатурам
внедряемых методов, сосуществующих по правилам перегрузки на уровне методов из RFC-011a. Перегрузка
в RFC-011a явно определена только до уровня методов; данный пункт дополняет её правилом уровня
экземпляров: законность сосуществования одноимённых экземпляров интерфейса определяется тем,
конфликтуют ли развёрнутые сигнатуры методов (при конфликте — E1097, по аналогии с правилами
пространства имён полей/методов).

#### Интерфейс распространения Try (форма определена и реализована на этапе 2)

Интерфейсное имя для `?` — `Try`, форма с четырьмя методами (форма определена 2026-09-22 на этапе
2):

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    is_failure: (self: &Self) -> Bool,
    success:    (self: &Self) -> T,
    residual:   (self: &Self) -> E,
    from_error: (E) -> Self,
}
```

- **Разделение семантики**: `is_failure` определяет успех/неудачу, `success` извлекает успешную
  нагрузку, `residual` извлекает нагрузку неудачи, `from_error` служит мостом для межтипового
  распространения (когда `T` из `f()?` отличается от внешнего `U`, перестраивает значение неудачи из
  `E`). Понижение `?` единообразно генерирует цепочку из четырёх вызовов — если `is_failure(t)`
  истинно, то `Ret from_error(residual(t))`, иначе выражение принимает значение `success(t)`; ручная
  последовательность проверки вариантов больше не пишется, `Result` / `Option` (реализация в std на
  yx) и пользовательские типы с Try идут одним путём.
- **Тупиковые ветки**: контрактно недостижимые ветви метода `success` (при неудаче) и `residual`
  (при успехе) реализуются через расходящийся `assert(false)` (`assert` возвращает `Never`, принцип
  взрыва `Never <: T` обеспечивает прохождение, type-system.md §2.2).
- **Проверка**: typecheck обращается к реестру реализаций интерфейса (позиция Self — номинальное
  сопоставление, абстрактные элементы инстанцируются по scrutinee-фактическому аргументу); тип
  возврата внешней функции тоже должен реализовывать `Try` с возможностью `E`-позиции принять
  значение неудачи (семантика E1081/E1082/E1083 становится интерфейсной).
- **`Result` переходит в std**: определения типов `Result` / `Option` и их реализации `Try`
  переносятся в `std/result.yx` / `std/option.yx` (чистый YaoXiang), нативные конструкторы
  `ok`/`err` выводятся из эксплуатации — синтаксис конструирования варианта `Result(T, E).ok(v)`
  становится единственным каналом конструирования (проблема жёсткой привязки конструкторов решается
  вместе с выводом из эксплуатации спецслучаев парсера). Остаточный тип `Try` для `Option` берётся
  как `Void` (соответствует семантике NoneT эксперимента Try в Rust).

### Примеры

#### Пользовательский тип: арифметика и равенство работают «из коробки»

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point, Point),
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   # Point(4.0, 6.0)
    println(a == b)             # false — Equal автовыведен, без инстанцирования
    println(a == a)             # true
}
```

#### Пользовательское равенство (переопределение автовыведения)

```yaoxiang
Vec3: Type = {
    x: Float,
    y: Float,
    z: Float,
    Equal(Vec3, Vec3),
}

# Сравнение Float с допуском, переопределяет поэлементное автовыведение
Vec3.equal: (self: &Vec3, other: &Vec3) -> Bool =
    abs(self.x - other.x) < 0.000001
    and abs(self.y - other.y) < 0.000001
    and abs(self.z - other.z) < 0.000001
```

#### Пользовательский контейнер с индексированием

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### Ограничения обобщений наконец-то работают

```yaoxiang
// Пример из RFC-011 теперь реализуем
// T: Add ≜ Add(T, T, T) зарегистрировано; T: Multiply ≜ Multiply(T, T, T) зарегистрировано
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

(Из показательного примера RFC-011 `T: Add + Multiply + Zero` имена `Zero` / `One` не входят в
данный RFC — это члены-константы, а не операторы; «члены интерфейса без получателя» в RFC-011a не
имеют прецедента, см. открытые вопросы.)

## Детальный проект

### Влияние на систему типов

**Новые интерфейсы** (уровень 2): `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
(`Try` — на этапе 2).

**Реестр реализаций интерфейсов**: центральный узел диспетчеризации операторов. Агрегирует
регистрации ядра по умолчанию (для базовых типов) и пользовательские экземпляры
(`ImplementationProof` из `check_interface_instantiation`); проверка допуска `+` / `==` / `[]` и
разрешение ограничения `T: Add` (`check_trait_bounds` из `bounds.rs`) **запрашивают одну и ту же
таблицу** — не существует зазора, где «ограничение говорит да, а оператор — нет».

**Структурный вывод `Equal`**: поверх реестра накладывается структурное правило (все поля сравнимы ⇒
сравнимо), базовые типы покрываются регистрациями ядра, рекурсия замыкается. Старая регистрация
`Equal` в `trait_data.rs` и старое автовыведение прекращаются.

**Разделение запросов операторов и разрешения имён**: `+` и подобные обращаются только к реестру,
минуя обычное разрешение имён; локальные одноимённые связывания (например, типоуровневое семейство
`Add`) не влияют на операторы (см. § Имена и регистрация).

**Правило сирот**: реализация оператора может быть записана только в **модуле определения типа** —
определение `Int` в ядре, поэтому регистрацию для `Int` может делать только ядро; определение
`Point` в пользовательском модуле, поэтому зарегистрировать его может только его определитель. Все
типы подчиняются одному правилу, встроенные типы не имеют привилегий.

### Поведение в рантайме

**Нулевые накладные расходы в рантайме**: цель вызова оператора определяется на этапе компиляции
(статическая диспетчеризация). Для базовых типов (`Int`/`Float`/`String`/`List`) сохраняется
**быстрый путь нативных инструкций**, без обращения к диспетчеризации через интерфейс; для
автовыведенного `==` для структур генерируется нативное поэлементное сравнение; `==` / `!=` в
позиции `Any` (динамический тип) сохраняет существующее рантайм-сравнение (тестовый фреймворк
RFC-036 `assert_eq` зависит от этого поведения и не затрагивается).

**Исправление семантики `%`**: `-7 % 3` переходит из `-1` (усечённый остаток) в `2` (математический
модуль). Изменения синхронно вносятся в три места: интерпретатор (`checked_rem`), свёртка констант
(`a % b`), байткод (`I64_REM`).

### Обратная совместимость

**Операции над базовыми типами не меняются**: `1 + 2`, `"a" + "b"`, `[1] + [2]`, `1 < 2` — все
сохраняют нативный путь, поведение и производительность не меняются.

**`1 + 2.5` из ошибки компиляции становится валидным**: после регистрации ядра
`Add(Int, Float, Float)` становится доступным смешанная арифметика, которая ранее отвергалась белым
списком, возвращая `Float`. Это новая возможность, никакой существующий код не затрагивается.

**Исправление семантики `%`**: `-7 % 3` переходит из `-1` в `2`. Квалифицируется как **исправление
дефекта** (документация давно обещала взятие модуля, см. мотивацию §5), без периода совместимости; в
существующем тестовом корпусе нет случаев, зависящих от `%` с отрицательными числами (проверено).

**`==` для структур из ошибки рантайма становится работоспособным**: ранее `Struct == Struct` всегда
давал ошибку рантайма E6007; после подключения автовыведение делает это работоспособным — от плохого
к хорошему, никакой существующий валидный код не затрагивается.

**`==` для `Any` не затрагивается**: позиция динамического типа сохраняет рантайм-сравнение
(семейство утверждений `assert_eq` из RFC-036 зависит от этого, раньше работало — и после работает).

**Позиционное связывание `f[0]` не меняется**: `distance[0]` — встроенная в компилятор возможность
из RFC-004, **не идёт через интерфейс `Index`**, не затрагивается.

**`?` прозрачен для существующего кода** (этап 2): после того как `Result` получит экземпляр `Try`,
поведение существующих использований `?` остаётся полностью идентичным.

## Компромиссы

### Достоинства

- **Выполнение обещаний ограничений операторов из RFC-011**: `T: Add + Multiply` из бумажного (по
  сути — ошибочного) состояния превращается в реализуемый механизм, без изменения основного текста
  уже принятого RFC
- **Снятие привязки `Result` к core** (этап 2): после интерфейсного оформления `?` и конструкторов
  `Result` может быть отнесён к std, что согласуется с существующим позиционированием в RFC-013
- **Исправление дефекта из тестирования**: `Point == Point` работает из коробки, попутно устраняется
  неработоспособность `list.contains` для структур
- **Нулевой новый синтаксис**: всё переиспользует существующие механизмы RFC-011a, не затрагивает
  грамматику парсера
- **Нулевые накладные расходы в рантайме**: статическая диспетчеризация + нативный быстрый путь для
  базовых типов
- **Пользовательские контейнеры работают**: `Box(T)[0]` из «всегда ошибка» становится
  работоспособным
- **Внутренняя согласованность языка**: Tuple/List уже сравниваются поэлементно, записи дополняют;
  арифметические интерфейсы с тремя параметрами единообразны с `Index`; таблица приведения из
  RFC-011 §8.3 объединяется с реестром интерфейсов

### Недостатки

- **Автовыведение `Equal` — негласный дефолт**: если в будущем потребуется отозвать «записи по
  умолчанию сравнимы», это будет ломающее изменение. Эта позиция принимается — она согласуется с
  существующим поведением Tuple/List, а явное инстанцирование всегда может переопределить
- **Предусловие `Equal` отвергает типы с линейными токенами**: типы с полями `&mut` не могут
  использовать `==`, что является ценой семантической корректности; требуется чёткая диагностика (с
  указанием конкретного поля)
- **Создание экземпляра интерфейса — явная стоимость**: для каждого арифметического оператора нужна
  строка инстанцирования + один метод (`Equal` освобождён — автовыводится). Синтаксис RFC-011a не
  позволяет неявного вывода (компромисс в пользу того, что параметр типа `Self` — без магии)
- **Исправление семантики `%` — изменение поведения**: хотя квалифицируется как исправление дефекта,
  должно быть отмечено в инструкциях по миграции

## Альтернативы

### Вариант A: только уровень 1 (диспетчеризация по имени метода), без уровня интерфейсов

`+` только проверяет наличие метода с именем `add`, не требуя реализации интерфейса `Add`.

**Причина отклонения**: ограничение `T: Add` из RFC-011 оторвётся от операторов — ограничение
смотрит в интерфейс, оператор — в имя метода, и они могут давать несогласованные ответы. Также
невозможно дать точную диагностику на этапе компиляции для случая «`+` применён к несложимому типу».

### Вариант B: ввести синтаксис конструкторов `Ok(x)` / `Some(x)` для решения проблемы `?`

Не делать `?` интерфейсным, а добавить синтаксис конструкторов к типу-сумме.

**Причина отклонения**: конфликтует с RFC-010 (принят). RFC-010 явно устанавливает «единое
использование записей для выражения типов-сумм, **две грамматики не нужны**» и явно отвергает
синтаксис `|`. Введение конструкторов — это введение второго способа выражения. И он решает только
`?`, но не `Point == Point` и не индексирование пользовательских контейнеров.

### Вариант C: операторы сравнения тоже становятся интерфейсными на первом этапе (введение `Ordering`)

`<` `<=` `>` `>=` идут через интерфейс `Compare`, возвращающий трёхзначный `Ordering`.

**Причина отклонения**: `<` в YaoXiang уже является **инструкцией IR первого класса**
(`Instruction::Lt/Le/Gt/Ge`); интерфейсное оформление заставит базовые типы идти обходным путём. А
введение `Ordering` потянет за собой целый комплекс задач: собственные сравнение/сортировка
`Ordering`, `PartialOrd` vs `Ord` для `NaN` во Float и т.д., что соответствует отдельному RFC.
Текущие потребности, выявленные тестированием (`Point == Point`, `list.contains`), требуют **только
`Equal`**.

### Вариант D: имена операторов — сокращённые (метод интерфейса `Add` называется `add`, интерфейс — `Mul`)

**Причина отклонения**: в основном тексте RFC-011 уже записано `T: Add + Multiply + Zero`;
использование сокращений потребует изменения уже принятого RFC.

### Вариант E: `Equal` только через явное инстанцирование, без автовыведения

**Причина отклонения**: пользовательские типы оказываются неспособны к `==`, что неприемлемо
по用户体验у; к тому же `(1, 2) == (1, 2)` и `[1] == [1]` уже сегодня сравниваются поэлементно, и
только записи исключены — это и так несогласованность. Явное инстанцирование сохраняется как способ
переопределения, учитывая потребности кастомизации.

### Вариант F: тип возврата арифметического интерфейса жёстко зашит как `-> Self`

**Причина отклонения**: метод `Add(Int, Float)` будет вынужден вернуть `Int`, `1 + 2.5` невозможно
выразить корректно; масштабирование `Multiply(Point, Float)` тоже не записывается. А семейство типов
приведения `(Int, Float) => Float` из RFC-011 §8.3 теряет место реализации. Три параметра
`(Self, R, O)` единообразны с `Index(Key, Value)`.

## Стратегия реализации

### Зависимости

| Зависимость                               | Состояние         | Какую часть данного RFC затрагивает                                                                 |
| ----------------------------------------- | ----------------- | --------------------------------------------------------------------------------------------------- |
| RFC-011a механизмы интерфейсов, фазы 1–3  | ✅ реализовано    | Фундамент уровня 2 (тестировано в работе)                                                           |
| RFC-010 путь конструирования через записи | ❌ не реализовано | **Этап 2**: сторона конструирования `?` + вывод из эксплуатации спецслучаев конструкторов в парсере |
| RFC-010b деконструкция вариантов          | ❌ на бумаге      | **Этап 2**: запись `match` в `Result.residual`, исчерпываемость                                     |
| RFC-009 вывод линейных токенов            | частично          | Проверка предусловия `Equal`                                                                        |

### Поэтапный план

По **зависимостям интерфейсов** (ограничения проектирования, не расписание) делится на две группы:

**Этап 1 — не зависит от RFC-010/010b**:

- Таблица соответствия уровня 0 + реестр реализаций интерфейсов + подключение уровня 1
- Семь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` (форма с тремя
  параметрами типа)
- Автовыведение `Equal` + предусловие линейности + переключение разрешения ограничений на реестр
- Исправление семантики `%` (в трёх местах: интерпретатор / свёртка констант / байткод)
- Сохранение рантайм-сравнения `==` в позиции `Any`
- **Результат**: `Point + Point`, `Point == Point` (без церемоний), `Box(T)[0]`, `1 + 2.5`,
  ограничение `T: Add` — всё становится работоспособным

**Этап 2 — зависит от RFC-010 / RFC-010b, перед началом работ должна быть определена форма `Try`**:

- Определение формы интерфейса `Try` (см. открытые вопросы)
- Интерфейсное оформление `?` + вывод из эксплуатации спецслучаев конструкторов (`ok`/`err`/`some`)
  в парсере, переход на путь конструирования записей из RFC-010
- Перенос `Result` из core в std (на основе существующего позиционирования в RFC-013)

### Риски

| Риск                                                                | Смягчение                                                                                                                      |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Изменение семантики `%` влияет на существующий пользовательский код | Квалифицируется как исправление дефекта + проверено отсутствие зависимостей от `%` с отрицательными числами в тестовом корпусе |
| Негласный дефолт автовыведения `Equal` в будущем трудно отозвать    | Позиция определена: согласовано с существующим поведением Tuple/List, явное инстанцирование может переопределить               |
| Несогласованность двух путей базовых типов (нативный + реестр)      | Барьер: семантика регистраций ядра должна совпадать с нативными инструкциями (два взгляда на одну таблицу)                     |
| Запросы к реестру замедляют компиляцию                              | Таблица индексируется по имени типа + кэширование результатов инстанцирования (переиспользует proof из RFC-011a)               |
| Перегрузка уровня экземпляров вносит неоднозначность                | То же правило, что и для перегрузки на уровне методов: конфликт сигнатур ⇒ E1097                                               |

## Согласование с другими RFC

Данный RFC позиционируется как **инициатор требований со стороны потребителя**; следующие RFC должны
быть синхронно обновлены для согласованности (получено разрешение на правку):

| RFC                                     | Что нужно обновить                                                                                                                                                                                                                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **RFC-011** (принят)                    | В § об ограничениях отметить, что `Add` / `Multiply` определяются и реализуются 011b (`T: Add` ≜ `Add(T, T, T)`); пометить `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` как висящие имена ограничений (для последующих RFC); в §8.3 у таблицы приведения типов отметить объединение с реестром интерфейсов |
| **RFC-010** (принят)                    | Уточнить требование реализации «поле записи — это и есть конструктор» — это предусловие для вывода из эксплуатации спецслучаев конструкторов в парсере на этапе 2                                                                                                                                            |
| **RFC-010b** (черновик, бывший RFC-039) | Конструирование и деконструирование должны быть парными; исчерпываемость не зависит от принадлежности `Result` к core/std (011b на этапе 2 выполнит миграцию)                                                                                                                                                |
| **RFC-009** (принят)                    | В § о свойствах типов перекрёстная ссылка: предусловие `Equal` — «без линейных токенов `&mut`» (а не Dup)                                                                                                                                                                                                    |
| **RFC-013** (принят)                    | При реализации этапа 2: тексты `E1081` / `E1082` очищаются от слова «Result»; диагностика предусловия `Equal` повторно использует семейство `E1101` — по процедуре RFC-013 трёхсторонняя синхронизация (codes/*.rs ↔ locales ↔ таблица кодов)                                                                |
| **RFC-018** (принят)                    | После перехода `%` на математический модуль таблица соответствия `Mod → srem/urem` становится недействительной, нужно перейти на `srem` + коррекцию знака (или синтез через `sdiv`+`mul`+`sub`), и исправить смешение терминов «модуль/остаток»                                                              |
| **RFC-036** (принят)                    | Изменений не требуется. Указать связь: `==` в позиции `Any` сохраняет рантайм-сравнение, семейство утверждений `assert_eq` не затрагивается шлюзом                                                                                                                                                           |

> Основание для переноса `Result` в std: в RFC-013 уже позиционировано «std-библиотека
> `Result(T, Error)`», в RFC-014 уровневая модель относит std к основным источникам. Этап 2 данного
> RFC — один из путей его реализации; ссылки на несуществующие номера больше не используются.

- [x] ~~Может ли пользователь дополнить реализацию операторов для уже существующих типов (правило

      определения типа. Определение `Int` в ядре, поэтому зарегистрировать его может только ядро;
      пользователь может регистрировать только для своих типов. Все типы равноправны, встроенные
      типы не имеют привилегий (2026-09-22)
- [ ] Должен ли `Index` различать изменяемое индексирование (аналог `IndexMut` в Rust)? (На первом
      этапе только чтение; изменяемое индексирование затрагивает `WriteToken` из RFC-009, и в
      RFC-011a уже есть прецедент получателя `&mut Self`, оставлено на потом)
- [ ] Многопозиционное индексирование: Key упаковывается в кортеж (текущее состояние) или переходит
      на множественные аргументы (стиль Swift)? (Остаётся упаковка в кортеж, парсер не меняется)
- [ ] Форма `Zero` / `One`: член-константа — не оператор, «член интерфейса без получателя» в
      RFC-011a не имеет прецедента, требует отдельного определения, после чего предложение
      `T: Add + Multiply + Zero` из RFC-011 может быть выполнено полностью
- [ ] Полная форма интерфейса `Try`: `?` нужны три вещи — проверка успеха/неудачи, извлечение
      успешной нагрузки, формирование значения неудачи для внешнего возврата; единственного метода
      `residual` недостаточно; вместе с выводом из эксплуатации спецслучаев конструкторов в парсере,
      форма должна быть определена до начала этапа 2
- [ ] Префиксный тип `?T` (FFI-допускающая null аннотация из RFC-026, RFC-018) и постфиксный
      оператор `e?` используют символ `?`: разные позиции (в типе vs в выражении) не создают
      конфликта, достаточно текстового пояснения
- [ ] `PartialOrd` / `Ordering` (интерфейсное оформление операторов сравнения): отдельный RFC, в
      данном явно не делается

| Выражение                               | Текущее состояние                                                                                          |

### A.3 Места жёсткого кодирования `?` и конструкторов

```rust
// src/frontend/core/typecheck/inference/expressions.rs
let expected_result = MonoType::make_result(ok_ty.clone(), expected_err.clone());

// src/middle/core/ir_gen.rs
Instruction::VariantTag { group: "Result".to_string(), .. }
// variant 0 = ok, variant 1 = err
```

Сторона конструкторов: `ok(T)` / `err(E)` / `some(T)` распознаются парсером (спецификация языка
`syntax.md` §1.4.2); `is_ok` / `unwrap` и др. в `std/result.rs` выполняют сопоставление по
`variant_id 0/1`. «Перенос `Result` в std» требует решения обеих половин (`?` + конструкторы)
вместе, обе относятся к этапу 2.

| Квалификация семантики `%`                       | Исправление дефекта (документация уже обещала взятие модуля), без периода совместимости                            | `reference/index.md`, «умножение/деление взятие модуля» — первичное доказательство                                                                               | 2026-09-22 |
| Основание переноса `Result` в std                | Ссылка на существующее позиционирование в RFC-013, ссылки на несуществующие номера больше не используются          | В RFC-013 уже записано «std-библиотека `Result(T, Error)`»                                                                                                       | 2026-09-22 |

## Приложение C: глоссарий

| Термин                        | Определение                                                                                                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Уровень 0                     | Фиксированная таблица соответствия оператор → имя метода, константа уровня языка, неизменяемая                                                                               |
| Уровень 1                     | База диспетчеризации, ищущая и вызывающая по ключу `Type.method`                                                                                                             |
| Уровень 2                     | Слой контракта интерфейса, дающий основание для ограничений обобщений и одновременно являющийся условием допуска оператора                                                   |
| Реестр реализаций интерфейсов | Агрегирует регистрации ядра по умолчанию и пользовательские экземпляры; единственный критерий для запросов операторов и разрешения ограничений, не связан с разрешением имён |
| Быстрый нативный путь         | Сохраняемый жёстко закодированный путь для базовых типов, без обращения к диспетчеризации через интерфейс                                                                    |
| Позиционное связывание        | Синтаксис `f[0]` из RFC-004, привязывающий позиции параметров функции как методы, поведение этапа компиляции                                                                 |
| Автовыведение                 | Поэлементный `==`, автоматически генерируемый компилятором для записей со всеми сравнимыми полями; явное инстанцирование может переопределить                                |
