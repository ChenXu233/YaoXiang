# RFC-010a: Вычисление хвостового выражения и семантика return

> **Ссылки**:
>
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md) — модель
>   `name: type = value`, `{}` как управляемый зависимостями вычислительный блок
> - [RFC-007: Унификация синтаксиса определения функций](./007-function-syntax-unification.md) —
>   правила возврата из блоков кода, досрочный возврат
> - [RFC-038: Завершение операторов и правила перевода строки](038-statement-termination.md) —
>   поведение перевода строки в операторах и выражениях
> - [Спецификация языка §Система типов](/reference/language-spec/type-system.md) — принцип взрыва
>   для `Never`

## Резюме

Унифицировать семантику `return` и вычисления блоков, устранив конфликт формулировок между RFC-007 и
RFC-010.

Предлагаются **три самосогласованных правила**: значение блока равно его хвостовому выражению
(единственный выход); `return` — это **нелокальный выход** типа `Never` (выход из функции, а не
«возврат блоку»); `if` без `else` принимает значение `void`.

`return` и вычисление блока **не разделяются на уровне языка** — `{ return n }` как блок имеет
значение `n` (тип `Never`), и одновременно `return` осуществляет выход из функции; оба факта
сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Досрочный возврат» из RFC-007 и «блок
имеет значение» из RFC-010 являются следствиями этих трёх правил, а не противоречащими исключениями.

Никакого нового синтаксиса, никаких новых ключевых слов.

## Мотивация

### Конфликт формулировок

Пример с числами Фибоначчи из playground выявил семантическое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return — от «if» или от «функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два уже принятых RFC дают **противоположные** выводы:

| RFC                  | Формулировка                                                                                                                                                    | Выведенная семантика                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **RFC-007** (принят) | На примере `factorial`, заголовок гласит **«Досрочный возврат: использование return»**: `if n <= 1 { return 1 }`                                                | `return` проходит сквозь `if` и тело функции, **возвращаясь в функцию** |
| **RFC-010** (принят) | «`{}` — это управляемый зависимостями вычислительный блок… используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` отдаёт значение **этому `{}`**                                 |

По RFC-010 фигурные скобки в `if n <= 1 { return 1 }` образуют вычислительный блок, `return 1`
задаёт его значение как 1, тогда значение `if` отбрасывается и следующая строка выполняется
неизбежно — **fib зацикливается**. По RFC-007 же всё корректно.

### Корневая причина: двойная роль слова `return`

- **RFC-007** использует его для выражения «выхода из функции» — концепция потока управления
- **RFC-010** использует его для выражения «значение этого блока — оно» — концепция вычисления

Использовать ключевое слово потока управления для выражения вычисления — категориальная ошибка. Один
термин несёт две функции: как бы его ни настраивать, одна из сторон окажется принесена в жертву.

### Расширительное толкование в нижестоящих документах

Документ `docs/src/reference/language-spec/syntax.md` расширил «блок `{}`» из RFC-010 на **все
фигурные скобки**:

- §2.9: «`return` в `{}` **всегда возвращает содержимое во внешнюю область видимости**» (и
  «унифицированная семантика: все блоки `{}`»)
- §3.3: «`return` используется для **возврата значения из блока кода**»

При этом RFC-010 в оригинале определял только **три блока со значением** (`= {}` / `spawn {}` /
`unsafe {}`) и **нигде не затрагивал** фигурные скобки `if` / `while` / `for` / `match`.

### Текущее состояние реализации

| Поведение                                             | Состояние                                               |
| ----------------------------------------------------- | ------------------------------------------------------- |
| `if n == 0 { return 7 } … return 8`                   | Выход из функции (`h(0) = 7`)                           |
| `f = { n + 1 }`                                       | Хвостовое выражение работает (возвращает `5`)           |
| `x = { y = 5; y }` (хвостовое выражение голого блока) | `E3006` переменная не разрешена (см. #343)              |
| `f: () -> Int = { if c {5} else {6} }`                | Возвращает `void`, хвостовое выражение отброшено (#344) |
| `f: () -> Int = { "s" }`                              | Тихо проходит компиляцию (см. #345)                     |
| `x = if c { 19 }` (без `else`)                        | `19` (должен быть `Void`, см. #346)                     |
| `v = unsafe { 42 }`                                   | `void` (см. #347)                                       |
| `y = if c { 111 } else { 222 }`                       | Работает (`if` как выражение)                           |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx` ранее утверждал, что «хвостовое выражение
больше не возвращается неявно», но этот случай не покрывал, поэтому тест не провалился. Этот файл
заменён на `tests/yaoxiang/03-semantics/tail_expr_and_return.yx`.

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение (единственный выход)
   Значение оператора присваивания — Void; значение пустого блока {} — Void
② return : (T) -> Never
   Нелокальный выход: выход из ближайшей границы функции
③ if без else → Void
```

**Этих трёх достаточно, чтобы вывести «досрочный возврат», не требуя отдельного правила о
принадлежности `return` функции.**

### Правило ①: значение блока

**Последний оператор/выражение** блока и есть значение блока (хвостовое выражение). Это **не**
правило «нет хвостового выражения — Void» — непустой блок всегда имеет хвостовое выражение
(последний оператор сам им и является), пустой блок `{}` имеет значение `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Оператор присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание как хвостовое выражение → значение блока — Void
b = {
    x = compute()
    log(x)               // Оператор присваивания → Void
}

// Если нужно Void — пишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Проектный критерий (разделение механизма и защиты)**:

- **Правило языка задаёт только механизм**: последний оператор есть значение блока — правило
  единственно и недвусмысленно
- **Защита обеспечивается проверкой типов**: объявление функции `-> Int` при несоответствии типа
  хвостового выражения → ошибка компиляции
- **Язык не защищает от «ошибки намерения»**: если тип хвостового выражения случайно совпадает с
  возвращаемым типом, но семантика — не то, что задумано, это недосмотр автора, и язык не может это
  распознать. **Не полагаться на правила языка для защиты от ошибок намерения.**
- **Не хотите возвращать — пишите `Void` явно**

Это заменяет правило RFC-010 «`= { ... }` обязан использовать `return`, иначе возвращается `Void`»,
а также его обоснование «явный `return` нужен для устранения неоднозначности, является ли последнее
выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (ноль конструкторов, невозможно населить значение). Семантика:

- **Выход из ближайшей границы функции**, передача значения вызывающему
- **Проходит сквозь все блоки** — (если есть) `if` / `while` / `for` / `match` / голые блоки /
  `spawn` / `unsafe`

`return` не «возвращает значение блоку». `{ return n }` как блок имеет значение `n` (правило
хвостового выражения), **тип `Never`**; одновременно `return` выполняет выход из функции. **Оба
факта выполняются одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // Без else
```

Когда условие ложно, нет ветви для вычисления — берётся `Void`. Поэтому тип значения этого `if` —
`Void` (или его нельзя использовать в позиции, отличной от `Void`).

Если значение нужно, допишите обе ветви явно:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` выполняется для любого типа `T` (принцип взрыва, см. спецификацию языка §Система
типов). Поэтому:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → Значение этого if : Never
  fib(n - 1) + fib(n - 2) // → Значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь этого `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Оператор типа `Never` означает **прерывание последовательности в этой точке** — следующее
  выражение не «следующий выполняемый шаг»
- А поскольку `Never` сводится к любому типу (принцип взрыва), весь блок удовлетворяет `-> Int`

**«Досрочный возврат» отсюда получается естественно**: `Never` прерывает последовательность +
принцип взрыва даёт сводимость.

## Детальное проектирование

### Формализация блоков и хвостовых выражений

```
Block        ::= '{' Stmt* '}'                     // Пустой блок → Void
               | '{' Stmt* Expr '}'                // Значение = Expr
Expr         ::= ...
               | Return                            // Тип Never
Stmt         ::= Assignment | ExprStmt | ...

Значение(Block):
  Пустой блок               → Void
  { ...; e }                → Тип(e)
  { ...; s } (s — оператор) → Void         // Значение присваивания — Void
```

### Правило типизации для `return`

```
return e : Never        где e : T

// Поскольку Never <: T' для любого T', return может стоять в позиции с любым возвращаемым типом
```

**Дополнительное правило, ограничивающее допустимость `return`, не требуется** — принцип взрыва уже
всё покрывает. Это устраняет вопрос «может ли `return` стоять в функции, возвращающей `X`».

### Слияние нескольких ветвей

```
join(A, B):
  Если A : Never  → B
  Если B : Never  → A
  Иначе           → требуется совместимость A, B (один тип или достижимая общая верхняя граница)
```

Несколько ветвей `if` / `match` сливаются по правилу `join`. Ветви с `return` имеют тип `Never` и не
участвуют в слиянии.

### Совместимость с RFC-007

Примеры RFC-007 **полностью соответствуют настоящему RFC** и не требуют правки:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Ветвь Never, игнорируется join
    return n * factorial(n - 1)     // Выход из функции
}
```

«Досрочный возврат» — не исключение, а **следствие** правил ①② и принципа взрыва.

### Отличия от RFC-010 и требования к правке

В RFC-010 требуется правка трёх мест (в виде опечатки, см. «Требования к правке нижестоящих
документов»):

| Пункт RFC-010                                                                          | После правки                                                                        |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| «`= { ... }` обязан использовать `return`, иначе возвращается `Void`»                  | Значение блока = хвостовое выражение; пустой блок → `Void`                          |
| Обоснование «явный `return` нужен для устранения неоднозначности хвостового выражения» | Отменяется — хвостовое выражение неоднозначности не создаёт, `return` ему не мешает |
| Три примера `return c` / `return SqliteDb`                                             | Заменить на хвостовые выражения (единый выход значения для `spawn` / `unsafe`)      |

**Основной замысел RFC-010 (`{}` как управляемый зависимостями вычислительный блок) сохраняется**,
лишь выход значения меняется с `return` на хвостовое выражение.

### Единая перспектива (принцип проектирования)

Фигурные скобки в `if` / `while` — это **и императивное управляющее тело, и декларативная единица
вычисления** — это **различие перспектив, а не два разных синтаксических образования**. Поэтому:

- **Не разделять на уровне языка** «управляющую конструкцию» и «единицу вычисления»
- Все блоки разделяют один и тот же набор правил вычисления (правило ①)
- `return` — единственный механизм-исключение, и его исключительность проистекает из типовых свойств
  `Never`, а не из синтаксического особого случая

Это позволяет естественное сосуществование декларативного и питоноподобного стилей:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## Компромиссы

### Преимущества

- **Устраняет конфликт RFC**: RFC-007 и RFC-010 переходят из противоречия в отношение «следствие»,
  ни одна из сторон не приносится в жертву
- **Минимум правил**: три правила + одно типовое свойство (принцип взрыва), никаких исключений
- **Единственный смысл `return`**: выход из функции. Больше не нужно гадать, куда относится — к
  значению блока или к значению функции
- **Единая перспектива**: императивный и декларативный стили сосуществуют без деления на уровне
  языка
- **Согласованность со зрелыми языками**: в Rust «хвостовое выражение + `return : !`» точно так же
  сосуществуют
- **Нулевая стоимость синтаксиса**: ни новых ключевых слов, ни изменений в правилах парсера

### Недостатки

- **Риск «ложного возврата» из последнего выражения**: при забытом удалении последней строки
  возвращаемое значение тихо меняется
  - Смягчение: проверка типов перехватывает несоответствие типов; язык не обещает защиты от ошибок
    намерения (см. проектный критерий)
- **Требуется правка RFC-010**: примеры в принятом документе нужно переписать
- **Хвостовое выражение голого блока не реализовано**: в текущей версии — внутренняя ошибка
  компилятора (независимо от настоящего проекта)
- **Взаимодействие с завершением операторов требует уточнения**: остаётся ли последнее выражение,
  завершённое переводом строки, значением блока (см. открытые вопросы)

## Альтернативы

### Вариант A: `return` сохраняет двойную роль с диспетчеризацией по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` — блоку; в `if {}` /
голых блоках — кому?

**Причина отклонения**: принадлежность `if` неразрешима — в этом и заключался исходный конфликт.
Плюс пользователю нужно помнить, какие блоки кому принадлежат, без принципиального основания (почему
`if` принадлежит функции, а голый блок — себе?).

### Вариант B: Строгий возврат блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **утрата функциональности**. `return` никогда не сможет обеспечить досрочный
выход из вложенных блоков, guard clause (`if err { return }`) становится невозможным, и функцию
можно писать только как каскад вложенных выражений.

### Вариант C: Значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевых синтаксических изменений** RFC-036 (нужно новое
ключевое слово), и пользователю придётся учить два понятия (`return` для выхода + `give` для
вычисления). Вариант с хвостовым выражением не вводит новых понятий.

### Вариант D: Сохранить RFC-010 как есть (обязательный явный `return`)

**Причина отклонения**: конфликт с RFC-007 непримирим (см. мотивацию). Плюс фактическая реализация
уже пошла по пути хвостового выражения.

## Приложение D: Устранение неоднозначности функция / значение блока (решение C)

### Проблема

`name = { ... }` одновременно определено в двух принятых RFC как разные сущности:

| RFC                         | Определение                                                                  |
| --------------------------- | ---------------------------------------------------------------------------- |
| RFC-007 (синтаксис функций) | Функция. «Простейший без аргументов» — `name = { return ... }`               |
| RFC-010 / 010a              | Значение блока. «`= {}` — блок со значением, значение — хвостовое выражение» |

Одна и та же синтаксическая позиция, две семантики. В реализации `callable_parts()` регистрирует
блок как 0-аргументную функцию, а `generate_block_ir` берёт значение блока — два слоя понимания
противоречат друг другу.

### Решение: приоритет аннотации, по умолчанию — функция

| Ситуация                    | Результат          | Основание                                            |
| --------------------------- | ------------------ | ---------------------------------------------------- |
| `value` — `Lambda` (с `=>`) | Функция            | `=>` — явный конструктор функций                     |
| Аннотация — `Fn`            | Функция            | Объявлен функциональный тип                          |
| Аннотация — не `Fn`         | **Значение блока** | Аннотация = тип (`x: Int = {..}`)                    |
| Без аннотации               | **Функция**        | По умолчанию; «простейший без аргументов» из RFC-007 |

**Ключевой момент: семантика значения блока не требует нового синтаксиса.** Чтобы `{ ... }`
вычислилось на месте, достаточно указать целевой тип:

```yaoxiang
x: Int = { y = 5; y }      # Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       # Функция: f() = 5 (аннотация Fn)
f = { 5 }                  # Функция: f() = 5 (без аннотации, по умолчанию функция)
b = () => 5                # Функция: лямбда-выражение
```

### Обоснование

Аннотация **и так объявляет тип**: `x: Int = ...` говорит, что `x` — `Int`, значит `{...}` —
значение `Int`; `f: () -> Int = ...` говорит, что `f` — функция, значит `{...}` — тело функции.
**Типоориентированный подход, а не изобретение нового правила.**

Без аннотации по умолчанию — функция, потому что:

1. Нулевые изменения в существующем коде (в репозитории 203 связывания `name = { ` без аннотации —
   все `main`)
2. Определение функций — частое, значение блока — редкое
3. RFC-007 уже принят; править его дороже, чем править настоящий RFC

### Цена (известная и принятая)

В `f = { 5 }` `f` — это **функция**, а не `5`. Это противоречит интуиции «фигурные скобки =
значение» — но именно таково уже принятое определение RFC-007, и **аннотация служит аварийным
выходом**: напишите `f: Int = { 5 }` — и получите значение.

### Дефекты реализации, устраняемые одновременно с решением

1. **Аннотация не должна определять, брать ли значение** (первопричина): три места, включая
   `generate_function_ir`, используют `return_type != Void` как порог для взятия хвостового
   выражения, из-за чего в `f = { 5 }` без аннотации хвостовое выражение тихо отбрасывается и
   возвращается `Void`. Аннотация лишь определяет, нужно ли _проверять_, а не нужно ли _вычислять_.
2. **`callable_parts()` больше не заглатывает блок безусловно**: диспетчеризация поручена единому
   `Expr::block_binding_is_function(аннотация, значение)`.
