# RFC-010a: Вычисление хвостового выражения и семантика return

> **Ссылки**:
>
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md) — модель
>   `name: type = value`, `{}` как вычислительная единица, управляемая зависимостями
> - [RFC-007: Унификация синтаксиса определения функций](./007-function-syntax-unification.md) —
>   правила возврата блоков кода, досрочный возврат
> - [RFC-038: Завершение операторов и правила перевода строк](038-statement-termination.md) —
>   поведение переноса строк в операторах и выражениях
> - [Спецификация языка §Система типов](/reference/language-spec/type-system.md) — принцип взрыва
>   `Never`

## Резюме

Унифицировать семантику `return` и вычисления блоков, устранив конфликты формулировок между RFC-007
и RFC-010.

Предлагаются **три самосогласованных правила**: значение блока равно его хвостовому выражению
(единственный выход); `return` — это **нелокальный выход** типа `Never` (выход из функции, а не
«возврат блоку»); `if` без `else` даёт `Void`.

`return` и вычисление блока **не разделяются на уровне языка** — `{ return n }` как блок имеет
значение `n` (тип `Never`), и одновременно `return` выполняет выход из функции. Оба факта
сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Досрочный возврат» из RFC-007 и «блок
имеет значение» из RFC-010 — следствия этих трёх правил, а не противоречащие исключения.

Никакого нового синтаксиса, никаких новых ключевых слов.

## Мотивация

### Конфликт формулировок

Пример с Фибоначчи на playground обнажил семантическое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return — от «if» или от «функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два уже принятых RFC дают **противоположные** выводы:

| RFC                  | Формулировка                                                                                                                                                   | Выводимая семантика                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **RFC-007** (принят) | На примере `factorial`, заголовок **«Досрочный возврат: использование return»**: `if n <= 1 { return 1 }`                                                      | `return` проходит сквозь `if` и тело функции, **возвращаясь в функцию** |
| **RFC-010** (принят) | «`{}` — вычислительная единица, управляемая зависимостями…используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` отдаёт значение **этому `{}`**                                 |

По RFC-010, фигурные скобки `if n <= 1 { return 1 }` — вычислительная единица, `return 1` даёт ей
значение 1, значит значение `if` отбрасывается и следующая строка обязательно выполнится — **fib
зациклится**. По RFC-007 — корректно.

### Корневая причина: двойственная роль слова `return`

- **RFC-007 использует его для выражения «выход из функции»** — концепция потока управления
- **RFC-010 использует его для выражения «значение этого блока равно ему»** — концепция вычисления

Использовать ключевое слово потока управления для выражения вычисления — это категориальная ошибка.
Одно слово с двумя ролями — как ни настраивай, одна из сторон будет принесена в жертву.

### Расширительное ошибочное толкование в нижестоящих документах

`docs/src/reference/language-spec/syntax.md` расширил «блок `{}`» из RFC-010 на **все фигурные
скобки**:

- §2.9: «`return` в `{}` **всегда возвращает содержимое в вышестоящую область видимости**» (и
  называет это «унифицированной семантакой: все блоки `{}`»)
- §3.3: «`return` используется для **возврата значения из блока кода**»

Однако в оригинале RFC-010 определены **только три блока со значением** (`= {}` / `spawn {}` /
`unsafe {}`), и **нигде не затрагиваются** фигурные скобки `if` / `while` / `for` / `match`.

### Текущее состояние реализации

| Поведение                                             | Состояние                                              |
| ----------------------------------------------------- | ------------------------------------------------------ |
| `if n == 0 { return 7 } … return 8`                   | Выход из функции (`h(0) = 7`)                          |
| `f = { n + 1 }`                                       | Хвостовое выражение работает (возвращает `5`)          |
| `x = { y = 5; y }` (хвостовое выражение голого блока) | `E3006` переменная не разрешена (см. #343)             |
| `f: () -> Int = { if c {5} else {6} }`                | Возвращает `void`, хвостовое выражение потеряно (#344) |
| `f: () -> Int = { "s" }`                              | Тихо проходит компиляцию (см. #345)                    |
| `x = if c { 19 }` (без `else`)                        | `19` (должно быть `Void`, см. #346)                    |
| `v = unsafe { 42 }`                                   | `void` (см. #347)                                      |
| `y = if c { 111 } else { 222 }`                       | Работает (`if` как выражение)                          |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx` ранее утверждал «хвостовое выражение больше не
возвращается неявно», но не покрывал этот случай, поэтому тест не срабатывал. Файл заменён на
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx`.

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение (единственный выход)
   Значение оператора присваивания — Void; значение пустого блока {} — Void
② return : (T) -> Never
   Нелокальный выход: выход из ближайшей границы функции
③ if без else → Void
```

**Этих трёх правил достаточно, чтобы вывести «досрочный возврат»; не нужно никакого дополнительного
правила о том, что `return` относится к функции.**

### Правило ①: Значение блока

**Последний оператор/выражение** блока — это значение блока (хвостовое выражение). Это **не** «нет
хвостового выражения → Void» — непустой блок всегда имеет хвостовое выражение (сам последний
оператор и есть таковое), а пустой блок `{}` имеет значение `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Оператор присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание в хвостовой позиции → значение блока — Void
b = {
    x = compute()
    log(x)               // Оператор присваивания → Void
}

// Хотите Void — пишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Проектные критерии (разделение механизма и защиты)**:

- **Языковое правило задаёт только механизм**: последний оператор есть значение блока; правило
  единственное, без неоднозначностей
- **Защита обеспечивается проверкой типов**: функция объявляет `-> Int`, а хвостовое выражение не
  соответствует → ошибка компиляции
- **Язык не защищает от «ошибки намерения»**: если хвостовое выражение случайно соответствует
  возвращаемому типу, но семантически не то, что задумал автор, — это его недосмотр; язык не может
  это распознать. **Не полагаться на языковые правила для защиты от ошибок намерения.**
- **Не хотите возвращать — пишите явно `Void`**

Это заменяет «`= { ... }` обязан использовать `return`, иначе возвращает `Void`» из RFC-010, а также
его обоснование «необходим явный `return` для устранения неоднозначности, является ли последнее
выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (нуль конструкторов, не имеет значений, в которых можно пребывать).
Семантика:

- **Выход из ближайшей границы функции**, передача значения вызывающему
- **Проникает сквозь все блоки** — (если есть) `if` / `while` / `for` / `match` / голые блоки /
  `spawn` / `unsafe`

`return` не «возвращает значение блоку». `{ return n }` как блок имеет значение `n` (правило
хвостового выражения), **тип `Never`**; одновременно `return` выполняет выход из функции. **Оба
факта верны одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // без else
```

Когда условие ложно, вычислять нечего — берётся `Void`. Поэтому тип значения этого `if` — `Void`
(или непригоден для не-`Void` позиций).

Когда нужно значение, явно допишите обе ветви:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` выполняется для любого типа `T` (принцип взрыва, см. спецификацию языка §Система
типов). Поэтому:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → значение этого if : Never
  fib(n - 1) + fib(n - 2) // → значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь этого `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Оператор типа `Never` означает **прерывание последовательности здесь** — следующее выражение не
  «следующая выполняемая строка»
- А `Never` сводим к любому типу (принцип взрыва), поэтому весь блок удовлетворяет `-> Int`

**«Досрочный возврат» естественно выводится отсюда**: `Never` прерывает последовательность + принцип
взрыва позволяет редукцию.

## Детальное проектирование

### Формализация блоков и хвостовых выражений

```
Block        ::= '{' Stmt* '}'                     // пустой блок → Void
               | '{' Stmt* Expr '}'                // значение = Expr
Expr         ::= ...
               | Return                            // тип Never
Stmt         ::= Assignment | ExprStmt | ...

значение(Block):
  пустой блок               → Void
  { ...; e }                → тип(e)
  { ...; s } (s — оператор) → Void          // значение присваивания — Void
```

### Правило типов для `return`

```
return e : Never        где e : T

// Поскольку Never <: T' для любого T', return может стоять в любой позиции возврата
```

**Никаких дополнительных правил для ограничения допустимости `return` не нужно** — принцип взрыва
уже покрывает это. Это устраняет вопрос «может ли `return` появляться в функции, возвращающей `X`».

### Слияние нескольких ветвей

```
join(A, B):
  Если A : Never  → B
  Если B : Never  → A
  Иначе           → требуется совместимость A и B (один тип или достижимая общая верхняя граница)
```

Несколько ветвей `if` / `match` сливаются по `join`. Ветвь с `return` имеет тип `Never` и не
участвует в слиянии.

### Совместимость с RFC-007

Примеры RFC-007 **полностью соответствуют данному RFC** и не требуют пересмотра:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Ветвь Never, игнорируется join
    return n * factorial(n - 1)     // Выход из функции
}
```

«Досрочный возврат» — не исключение, а **следствие** правил ①② и принципа взрыва.

### Отличия от RFC-010 и требования к пересмотру

RFC-010 требует пересмотра в трёх местах (в виде опечатки, см. «Требования к пересмотру нижестоящих
документов»):

| Пункт RFC-010                                                               | После пересмотра                                                                          |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| «`= { ... }` обязан использовать `return`, иначе возвращает `Void`»         | Значение блока = хвостовое выражение; пустой блок → `Void`                                |
| Обоснование «явный `return` устраняет неоднозначность хвостового выражения» | Аннулировано — хвостовое выражение не порождает неоднозначности, `return` его не нарушает |
| Три примера `return c` / `return SqliteDb`                                  | Заменены на хвостовое выражение (единый выход значения для `spawn` / `unsafe`)            |

**Основной замысел RFC-010 (`{}` как вычислительная единица, управляемая зависимостями)
сохраняется** — меняется только выход значения с `return` на хвостовое выражение.

### Единая перспектива (проектный принцип)

Фигурные скобки `if` / `while` — это **и императивное управляющее тело, и декларативная
вычислительная единица** — это **разница перспектив, а не два разных языковых конструкта**. Поэтому:

- **Не разделять на уровне языка** «управляющее тело» и «вычислительную единицу»
- Все блоки разделяют одни и те же правила вычисления (правило ①)
- `return` — единственный механизм-исключение, и его исключительность проистекает из типовых свойств
  `Never`, а не из синтаксического особого случая

Это обеспечивает естественное сосуществование декларативного и питоноподобного стилей:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }   // ⚠️ Выход через хвостовое выражение ещё не реализован, см. #365; пока нужно писать `spawn { return fetch("a") }`
```

## Компромиссы

### Преимущества

- **Устраняет конфликт RFC**: RFC-007 и RFC-010 переходят из противоречия в отношение «следствие»,
  ни одна из сторон не приносится в жертву
- **Минимальное число правил**: три правила + одно типовое свойство (принцип взрыва), без исключений
- **Единственный смысл `return`**: выход из функции. Больше не нужно разбираться, «значению блока /
  значению функции» он принадлежит
- **Единая перспектива**: императивный и декларативный стили сосуществуют, без разделения на уровне
  языка
- **Согласованность со зрелыми языками**: Rust также сочетает «хвостовое выражение + `return : !`»
- **Нулевой новый синтаксис**: без новых ключевых слов, без изменения правил грамматики парсера

### Недостатки

- **«Случайный возврат» при последнем выражении**: если забыли удалить последнюю строку,
  возвращаемое значение молча меняется
  - Смягчение: проверка типов перехватывает несоответствие типов; язык не обещает защиту от ошибок
    намерения (см. проектные критерии)
- **RFC-010 требует опечатки**: примеры в принятом документе нужно переписать
- **Хвостовое выражение голого блока ожидает реализации**: сейчас это внутренняя ошибка компилятора
  (независимо от данного проекта)
- **Необходимо уточнить взаимодействие с завершением операторов**: остаётся ли выражение,
  завершённое переводом строки, значением блока (см. открытые вопросы)

## Альтернативы

### Вариант A: `return` сохраняет двойственность, диспетчеризация по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` — блоку; в `if {}` /
голых блоках — кому?

**Причина отклонения**: принадлежность `if` неразрешима — это и есть исходный конфликт. И
пользователю придётся помнить «каким блокам кто принадлежит», без принципиального основания (почему
`if` принадлежит функции, а голый блок — себе?).

### Вариант B: Строгий возврат блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **потеря функциональности**. `return` никогда не сможет досрочно выйти из
вложенного блока, guard clause (`if err { return }`) становится полностью невозможным; функцию можно
написать только как глубоко вложенное выражение.

### Вариант C: Значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевого изменения синтаксиса** из RFC-036 (требуется
новое ключевое слово), и пользователю придётся изучить две концепции (`return` для выхода + `give`
для значения). Решение с хвостовым выражением — ноль новых концепций.

### Вариант D: Сохранить RFC-010 как есть (явный `return` обязателен)

**Причина отклонения**: конфликт с RFC-007 непримирим (см. мотивацию). И фактическая реализация уже
идёт по пути хвостового выражения.

После принятия данного RFC необходимо пересмотреть следующие документы. **Ошибочные примеры должны
быть удалены, в блоках опечаток не должно оставаться кажущегося работоспособным ошибочного кода.**

| Документ                                                                     | Содержание пересмотра                                                                                    | Состояние |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------- |
| RFC-010 §Правила возврата                                                    | Заменить на правило хвостового выражения; **удалить** пример «обязателен `return`, иначе `Void`»         | ✅        |
| Раздел обоснования RFC-010                                                   | **Удалить** аргумент «явный `return` устраняет неоднозначность»                                          | ✅        |
| RFC-010 §Блок `spawn` / §Блок `unsafe` примеры                               | `return c` / `return SqliteDb` → запись через хвостовое выражение                                        | ✅        |
| RFC-010 §Пример вычислительной единицы, управляемой зависимостями            | `return b` → хвостовое выражение `b`                                                                     | ✅        |
| `language-spec/syntax.md` §2.9                                               | «`return` возвращает в вышестоящую область» → правило хвостового выражения + `return` выходит из функции | ✅        |
| `language-spec/syntax.md` §3.3                                               | «Возврат значения из блока кода» → «Выход из ближайшей границы функции, тип `Never`»                     | ✅        |
| `language-spec/type-system.md`                                               | «Функция без `return` по умолчанию возвращает `Void`» → определяется хвостовым выражением                | ✅        |
| `tests/yaoxiang/03-semantics/no_tail_expr_return.yx`                         | Утверждения и комментарии противоречат новым правилам, требуется исправление                             | ✅        |
| RFC-007 §Резюме / §Правила синтаксиса Lambda / Таблица синтаксических правил | «Обязателен `return`, иначе `Void`» → хвостовое выражение + блок опечаток с `Never`                      | ✅        |

RFC, пересмотрена в форме опечатки (формальное определение функции в RFC-007 не меняется) — см.
последнюю строку таблицы выше.

## Приложение D: Разрешение неоднозначности функция / значение блока (Решение C)

> **Опечатка (2026-09-19): строка «без аннотации» из Решения C отменена.**
>
> Пользовательское решение: **унифицировать в пользу «содержимое определяет тип» (чтение B)** по
> причине того, что один и тот же принцип должен пронизывать словари и блоки:
>
> > Унифицировать в B, `{}` естественно встаёт на место.
>
> **Действующее правило**
>
> | Ситуация                  | Результат                | Основание                            |
> | ------------------------- | ------------------------ | ------------------------------------ |
> | `value` — `Lambda` (`=>`) | Функция                  | `=>` — явный конструктор функции     |
> | Аннотация — `Fn`          | Функция                  | Объявлен функциональный тип          |
> | Аннотация — не-`Fn` тип   | Значение блока           | Аннотация есть тип (`x: Int = {..}`) |
> | **Без аннотации**         | **Вывод по содержимому** | **Тип определяется содержимым**      |
>
> Ключевое изменение: `f = { 5 }` теперь — **значение** `5` (`Int`), а не функция.
>
> ```yaoxiang
> x: Int = { y = 5; y }      // Значение блока: x = 5 (аннотация не Fn)
> f: () -> Int = { 5 }       // Функция: f() = 5 (аннотация Fn)
> f = { 5 }                  // Значение: f = 5 (без аннотации → вывод по содержимому)
> f = {}                     // Значение: f = Void (пустой блок)
> b = () => 5                // Функция: явная лямбда
> d = { "a": 1 }             // Значение: Dict (самодокументирующееся содержимое)
> ```
>
> **Почему Решение C отменено**
>
> Изначальное обоснование Решения C («без аннотации — по умолчанию функция») было ориентировано на
> **удобство реализации**:
>
> 1. ~~Сохранение совместимости с существующим кодом~~ — затраты на миграцию приемлемы (211 файл,
>    704 места), это не семантическое основание
> 2. ~~Определение функций — частое, значение блока — редкое~~ — частота не является правилом типов
> 3. ~~RFC-007 принят, изменять его дороже, чем данный RFC~~ — неправильное не становится правильным
>    из-за «дороговизны» изменения
>
> Настоящая проблема — **несогласованность**: `f = { 5 }` — функция, но `d = { "a": 1 }` — словарь —
> та же `{` в той же позиции без аннотации даёт разные категории. Именно эта «стоимость», которую
> Решение C само признаёт, и есть трещина: «`f` в `f = { 5 }` — это функция, а не `5`…что
> противоположно интуиции «фигурные скобки — это значение»».
>
> Действующее правило устраняет трещину: **тип определяется содержимым**, независимо от наличия
> аннотации. Аннотация по-прежнему объявляет тип (`f: () -> Int`), но не навязывает значение по
> умолчанию из-за своего отсутствия.
>
> **Как `{}` встаёт на место**
>
> После унификации с B `{}` естественно занимает место: грамматика `Dict` требует хотя бы один ключ,
> `{}` не имеет содержимого, на которое можно опереться, поэтому берётся нулевая форма блочной
> структуры → пустой блок, значение `Void`. Пустой словарь — через `dict.new()`. Подробности см.
> spec [§2.9.1](../.../reference/language-spec/syntax.md).
>
> **Что остаётся неизменным**
>
> Два последующих пункта Приложения D («аннотация не должна определять выбор значения»,
> «`callable_parts()` больше не безусловно поглощает блок») остаются в силе; последний теперь
> реализован через `Expr::block_binding_is_function`, просто его ветка «без аннотации» изменена в
> соответствии с таблицей выше.

### Вопрос (историческая справка)

`name = { ... }` одновременно определено двумя принятыми RFC как разные вещи:

| RFC                         | Определение                                                                  |
| --------------------------- | ---------------------------------------------------------------------------- |
| RFC-007 (синтаксис функций) | Функция. «Минимальная без параметров»: `name = { return ... }`               |
| RFC-010 / 010a              | Значение блока. «`= {}` — блок со значением, значение — хвостовое выражение» |

Одна и та же синтаксическая позиция, два набора семантик — на уровне реализации `callable_parts()`
регистрирует блок как функцию с 0 аргументов, а `generate_block_ir` берёт значение как блок-значение
— два уровня понимания не согласованы.

### Исходное решение: аннотация имеет приоритет, по умолчанию функция (**отменено**)

| Ситуация                  | Результат          | Основание                                             |
| ------------------------- | ------------------ | ----------------------------------------------------- |
| `value` — `Lambda` (`=>`) | Функция            | `=>` — явный конструктор функции                      |
| Аннотация — `Fn`          | Функция            | Объявлен функциональный тип                           |
| Аннотация — не-`Fn` тип   | **Значение блока** | Аннотация есть тип (`x: Int = {..}`)                  |
| Без аннотации             | **Функция**        | По умолчанию; «минимальная без параметров» из RFC-007 |

**Ключевой момент: семантика значения блока не требует нового синтаксиса.** Чтобы `{ ... }`
вычислилось сразу, запишите целевой тип:

```yaoxiang
x: Int = { y = 5; y }      # Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       # Функция: f() = 5 (аннотация Fn)
f = { 5 }                  # Функция: f() = 5 (без аннотации, по умолчанию функция)  # ← Эта строка отменена
b = () => 5                # Функция: лямбда-выражение
```

### Исходное обоснование (**утратило силу**)

Аннотация **и так объявляет тип**: `x: Int = ...` говорит, что `x` — это `Int`, значит `{...}` —
значение `Int`; `f: () -> Int = ...` говорит, что `f` — функция, значит `{...}` — тело функции.
**Ориентация на тип, а не изобретение нового правила.**

Без аннотации — по умолчанию функция, потому что:

1. Полная совместимость с существующим кодом (в репозитории 203 привязки `name = { ` без аннотации,
   все — `main`)
2. Определение функций — частое, значение блока — редкое
3. RFC-007 принят, изменять его дороже, чем данный RFC

### Цена (известна и принята)

В `f = { 5 }` `f` — **функция**, а не `5`. Это противоположно интуиции «фигурные скобки — это
значение» — но именно так определено в принятом RFC-007, и **аннотация — выход из положения**:
напишите `f: Int = { 5 }`, чтобы получить значение.

### Дефекты реализации, исправленные вместе с решением

1. **Аннотация не должна определять выбор значения** (корневая причина №1): в трёх местах, включая
   `generate_function_ir`, условие `return_type != Void` использовалось как порог взятия хвостового
   выражения, из-за чего хвостовое выражение в `f = { 5 }` без аннотации молча отбрасывалось и
   возвращался `Void`. Аннотация определяет только, нужна ли _проверка_, но не нужно ли
   _вычисление_.
2. **`callable_parts()` больше не безусловно поглощает блок**: диспетчеризация унифицирована через
   `Expr::block_binding_is_function(аннотация, значение)`.
