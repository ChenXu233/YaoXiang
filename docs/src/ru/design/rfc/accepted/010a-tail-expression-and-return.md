# RFC-010a: Вычисление хвостовых выражений и семантика return

## Резюме

Унификация семантики `return` и вычисления блоков, устранение противоречий в формулировках между
RFC-007 и RFC-010.

Предлагаются **три самосогласованных правила**: значение блока равно его хвостовому выражению
(единственный выход); `return` — это **нелокальный выход** типа `Never` (выход из функции, а не
«возврат блоку»); `if` без `else` принимает `Void`.

`return` и вычисление блоков **не разделяются на уровне языка** — `{ return n }` как блок имеет
значение `n` (тип `Never`), при этом действием `return` является выход из функции; оба аспекта
сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Досрочный возврат» из RFC-007 и «блок
имеет значение» из RFC-010 являются следствиями этих трёх правил, а не противоречащими друг другу
исключениями.

Никакого нового синтаксиса, никаких новых ключевых слов.

## Мотивация

### Конфликт формулировок

Пример с числами Фибоначчи в playground выявил семантическое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return — «от if» или «от функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два принятых RFC дают **противоположные** выводы:

| RFC                  | Формулировка                                                                                                                                                    | Выводимая семантика                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **RFC-007** (принят) | На примере `factorial`, заголовок **«Досрочный возврат: использование return»**: `if n <= 1 { return 1 }`                                                       | `return` проходит сквозь `if` и тело функции, **возвращаясь в функцию** |
| **RFC-010** (принят) | «`{}` — вычислительная единица, управляемая зависимостями… используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` задаёт значение **этого `{}`**                                 |

Согласно RFC-010, фигурные скобки в `if n <= 1 { return 1 }` — это вычислительная единица, и
`return 1` задаёт её значение как 1, значит значение инструкции `if` отбрасывается, и следующая
строка обязана выполниться — **fib зацикливается**. Согласно RFC-007 — корректно.

### Корневая причина: двойная роль слова `return`

- **RFC-007 использует его для выражения «выхода из функции»** — концепция потока управления
- **RFC-010 использует его для выражения «значение этого блока — оно»** — концепция вычисления

Использование ключевого слова потока управления для выражения вычисления — категориальная ошибка
(category error). Одно слово несёт две роли — как бы его ни настраивать, одна из сторон будет
принесена в жертву.

### Ошибочное расширенное толкование в нижестоящих документах

`docs/src/reference/language-spec/syntax.md` расширил «блок `{}`» из RFC-010 на **все фигурные
скобки**:

- §2.9: «`return` в `{}` **всегда возвращает содержимое в вышестоящую область видимости**» (и
  называет это «унифицированной семантикой: все блоки `{}`»)
- §3.3: «`return` используется для **возврата значения из блока кода**»

Тогда как RFC-010 в оригинале определял **три блока со значением** (`= {}` / `spawn {}` /
`unsafe {}`) и **ни разу не затрагивал** фигурные скобки в `if` / `while` / `for` / `match`.

### Текущее состояние реализации

| Поведение                                             | Состояние                                               |
| ----------------------------------------------------- | ------------------------------------------------------- |
| `if n == 0 { return 7 } … return 8`                   | Выход из функции (`h(0) = 7`)                           |
| `f = { n + 1 }`                                       | Хвостовое выражение доступно (возвращает `5`)           |
| `x = { y = 5; y }` (хвостовое выражение голого блока) | `E3006` — переменная не разрешена (см. #343)            |
| `f: () -> Int = { if c {5} else {6} }`                | Возвращает `void`, хвостовое выражение отброшено (#344) |
| `f: () -> Int = { "s" }`                              | Тихо проходит компиляцию (см. #345)                     |
| `x = if c { 19 }` (без `else`)                        | `19` (должно быть `Void`, см. #346)                     |
| `v = unsafe { 42 }`                                   | `void` (см. #347)                                       |
| `y = if c { 111 } else { 222 }`                       | Доступно (`if` как выражение)                           |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx` утверждал, что «хвостовое выражение больше не
возвращается неявно», но не покрывал этот случай, поэтому тест не падал. Этот файл заменён на
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx`.

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение (единственный выход)
   Значение инструкции присваивания — Void; значение пустого блока {} — Void
② return : (T) -> Never
   Нелокальный выход: выход за ближайшую границу функции
③ if без else → Void
```

**Этих трёх правил достаточно, чтобы вывести «досрочный возврат», без дополнительных правил о том,
что `return` относится к функции.**

### Правило ①: значение блока

**Последняя инструкция/выражение** блока — это значение блока (хвостовое выражение). Это **не** «нет
хвостового выражения ⇒ `Void`» — непустой блок всегда имеет хвостовое выражение (та самая последняя
инструкция и есть), а значение пустого блока `{}` — `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Инструкция присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание в хвостовой позиции → значение блока — Void
b = {
    x = compute()
    log(x)               // Инструкция присваивания → Void
}

// Если нужен Void — пишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Проектные основания (разделение механизма и защиты)**:

- **Языковое правило задаёт только механизм**: последняя инструкция — значение блока, правило
  единственное и недвусмысленное
- **Защита обеспечивается проверкой типов**: объявление функции `-> Int`, а тип хвостового выражения
  не совпадает — ошибка компиляции
- **Язык не защищает от «ошибок намерения»**: если тип хвостового выражения случайно совпадает с
  возвращаемым типом, но семантика не та, что задумывалась, — это недосмотр автора, язык не может
  это распознать. **Не полагаться на языковые правила для защиты от ошибок намерения.**
- **Если возвращать значение не нужно — пишите `Void` явно**

Это заменяет положение RFC-010 «`= { ... }` обязан использовать `return`, иначе возвращается
`Void`», а также его обоснование «требуется явный `return` для устранения неоднозначности, является
ли последнее выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (нуль конструкторов, значение не может существовать). Семантика:

- **Выход за ближайшую границу функции**, передача значения вызывающему
- **Проходит сквозь любой блок** — будь то `if` / `while` / `for` / `match` / голый блок / `spawn` /
  `unsafe`

`return` не «возвращает блоку». `{ return n }` как блок имеет значение `n` (правило хвостового
выражения), **тип `Never`**; одновременно действие `return` — выход из функции. **Оба утверждения
верны одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // без else
```

Когда условие ложно, нет ветви для вычисления, берётся `Void`. Следовательно, тип значения этого
`if` — `Void` (или его нельзя использовать в позиции, несовместимой с `Void`).

Когда значение нужно, явно дополните обе ветви:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` выполняется для любого типа `T` (принцип взрыва, см. спецификацию языка §type system).
Следовательно:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → значение этого if : Never
  fib(n - 1) + fib(n - 2) // → значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь этого `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Инструкция типа `Never` означает, что **последовательность здесь обрывается** — следующее
  выражение не «следующая выполняемая инструкция»
- А `Never` сводим к любому типу (принцип взрыва), значит весь блок удовлетворяет `-> Int`

**«Досрочный возврат» естественно выводится отсюда**: `Never` обрывает последовательность + принцип
взрыва позволяет сведение.

## Детальное проектирование

### Формализация блоков и хвостовых выражений

```
Block        ::= '{' Stmt* '}'                     // пустой блок → Void
               | '{' Stmt* Expr '}'                // значение = Expr
Expr         ::= ...
               | Return                            // тип Never
Stmt         ::= Assignment | ExprStmt | ...

Значение(Block):
  Пустой блок              → Void
  { ...; e }               → Тип(e)
  { ...; s } (s — инструкция) → Void        // значение присваивания — Void
```

### Правила типизации для `return`

```
return e : Never        где e : T

// Поскольку Never <: T' для любого T', return может появляться в любой позиции возвращаемого типа
```

**Никаких дополнительных правил для ограничения допустимости `return` не требуется** — принцип
взрыва уже всё покрывает. Это снимает вопрос вида «может ли `return` появиться в функции,
возвращающей `X`».

### Слияние нескольких ветвей

```
join(A, B):
  Если A : Never  → B
  Если B : Never  → A
  Иначе           → требуется совместимость A и B (один тип или достижима общая верхняя граница)
```

Несколько ветвей `if` / `match` сливаются по `join`. Ветвь с `return` не участвует в слиянии,
поскольку имеет тип `Never`.

### Совместимость с RFC-007

Примеры RFC-007 **полностью соответствуют настоящему RFC** и не требуют пересмотра:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Ветвь Never, игнорируется join
    return n * factorial(n - 1)     // Выход из функции
}
```

«Досрочный возврат» — не исключение, а **следствие** правил ① ② и принципа взрыва.

### Различия с RFC-010 и требования к пересмотру

Определения RFC-010 пересмотрены в соответствии с настоящим RFC, различия следующие:

| Исходное положение RFC-010                                                                 | Действующее определение                                                                 |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| «`= { ... }` обязан использовать `return`, иначе возвращается `Void`»                      | Значение блока = хвостовое выражение; пустой блок → `Void`                              |
| Обоснование «явный `return` необходим для устранения неоднозначности хвостового выражения» | Несостоятельно — хвостовое выражение не создаёт неоднозначности, `return` ему не мешает |
| Три примера с `return c` / `return SqliteDb`                                               | Запись через хвостовое выражение (выход значения `spawn` / `unsafe` унифицирован)       |

**Основной замысел RFC-010 (`{}` как вычислительная единица, управляемая зависимостями)
сохраняется**, лишь выход значения заменён с `return` на хвостовое выражение.

### Единая перспектива (принцип проектирования)

Фигурные скобки в `if` / `while` **одновременно являются императивным телом управления и
декларативной единицей вычисления** — это **различие перспектив, а не два разных языковых
конструкта**. Поэтому:

- **Не разделять на уровне языка** «тело управления» и «единицу вычисления»
- Все блоки используют единый набор правил вычисления (правило ①)
- `return` — единственный механизм исключения, и его исключительность проистекает из типовых свойств
  `Never`, а не из синтаксической специальной обработки

Это позволяет декларативному и питон-стилю сосуществовать естественно:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## Компромиссы

### Преимущества

- **Устранение конфликта RFC**: RFC-007 и RFC-010 из противоречия переходят в отношение «следствие»,
  жертвовать одной стороной не нужно
- **Минимум правил**: три правила + одно типовое свойство (принцип взрыва), без исключений
- **Единственный смысл `return`**: выход из функции. Больше не нужно определять, к чему относится —
  к значению блока или функции
- **Единая перспектива**: императивный и декларативный стили сосуществуют без разделения на уровне
  языка
- **Согласованность со зрелыми языками**: Rust так же совмещает «хвостовое выражение + `return : !`»
- **Нулевой новый синтаксис**: без новых ключевых слов, без изменения правил парсера

### Недостатки

- **Риск «ошибочного возврата» от последнего выражения**: при забытом удалении последней строки
  возвращаемое значение молча меняется
  - Смягчение: проверка типов перехватывает несоответствие типов; язык не обещает защиту от ошибок
    намерения (см. проектные основания)
- **Нижестоящие документы требуют синхронного пересмотра**: примеры в принятых документах нужно
  переписать
- **Необходимо уточнить взаимодействие с завершением инструкций**: остаётся ли последнее выражение,
  завершённое переводом строки, значением блока (см. открытые вопросы)

## Альтернативы

### Вариант A: `return` сохраняет двойную роль, диспетчеризация по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` — блоку; в `if {}` /
голом блоке — чему?

**Причина отклонения**: принадлежность `if` неразрешима — это и есть исходный конфликт. К тому же
пользователь должен запоминать «каким блокам что принадлежит», а принципиального основания нет
(почему `if` принадлежит функции, а голый блок — себе?).

### Вариант B: Строгий возврат блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **потеря функциональности**. `return` никогда не сможет досрочно выйти из
вложенного блока, guard clause (`if err { return }`) становится принципиально невозможен — функцию
придётся писать в виде послойно вложенных выражений.

### Вариант C: Значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевого изменения синтаксиса** из RFC-036 (требуется
новое ключевое слово), и пользователю придётся изучать две концепции (`return` для выхода + `give`
для значения). Решение с хвостовым выражением — нулевые новые концепции.

### Вариант D: Сохранить RFC-010 как есть (явный `return` обязателен)

**Причина отклонения**: конфликт с RFC-007 непримирим (см. мотивацию). К тому же фактическая
реализация уже пошла по пути хвостового выражения.

## Пересмотр нижестоящих документов

Определения настоящего RFC стали авторитетной семантикой для нижестоящих документов; соответствующие
документы синхронизированы (отменённые формулировки более не сохраняются).

## Открытые вопросы

- [x] Взаимодействие хвостового выражения с правилами завершения инструкций из RFC-038: остаётся ли
      последнее выражение, завершённое переводом строки, значением блока? (@Чэньсюй: требуется
      согласование с правилом «строка, начинающаяся с `(` / `[`, никогда не объединяется» из
      RFC-038) — проверено на практике: последние выражения, завершённые переводом строки (включая
      `(` / `[` / литералы списков в начале строки), являются значениями блока
- [x] Когда `name = { ... }` — это функция, а когда — связывание значения блока — см. Приложение D
      (тип определяется содержимым)
- [x] Конкретная форма `unsafe {}` / `spawn {}` после пересмотра — оба проверены: хвостовое
      выражение работает
- [x] Взаимодействие `join` ветвей `match` с проверкой полноты (зависит от RFC-010b) — проверено:
      ветвь `Never` не участвует в слиянии, поведение `join` для много-веточных `if` / `match`

- [x] Текст диагностики для пустого блока `{}` в качестве тела функции с не-`Void` возвращаемым

## Приложение A: Эмпирические свидетельства

Всё ниже воспроизведено на версии 0.8.0.

| Код                                               | Результат                           |
| ------------------------------------------------- | ----------------------------------- |
| `h: (n)->Int = { if n==0 { return 7 } return 8 }` | `h(0)=7`, `h(1)=8`                  |
| `f: (n)->Int = { n + 1 }`                         | `5` (хвостовое выражение доступно)  |
| `f: ()->Int = { if c {5} else {6} }`              | `void` (должно быть `5`, см. #344)  |
| `f: ()->Int = if c {5} else {6}`                  | `5`                                 |
| `f: ()->Int = { match ... }`                      | Корректно                           |
| `f: ()->Int = { while ...; i }`                   | Корректно                           |
| `{ y = 5; y }` как выражение связывания           | `E3006` (см. #343)                  |
| `f: ()->Int = { "s" }`                            | Тихо проходит (см. #345)            |
| `x = if c { 19 }` (без `else`)                    | `19` (должно быть `Void`, см. #346) |
| `v = unsafe { 42 }`                               | `void` (см. #347)                   |
| `y = if c { 111 } else { 222 }`                   | `111`                               |
| `while { if i==2 { return 42 } }`                 | `42` (выход из цикла)               |
| Вложенное `{ { return 5 } return 1 }`             | `5` (выход из голого блока)         |

## Приложение C: Глоссарий

| Термин              | Определение                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------- |
| Хвостовое выражение | Последнее выражение, производящее значение в блоке; значение блока равно ему                                    |
| Нелокальный выход   | Передача управления через внешние единицы вычисления, действующая непосредственно на границу функции (`return`) |
| Принцип взрыва      | `Never <: T` выполняется для любого `T`, что позволяет `Never` сводиться к любому типу                          |
| Блок со значением   | `= {}` / `spawn {}` / `unsafe {}` — выход значения через хвостовое выражение                                    |
| join                | Правило слияния нескольких ветвей, ветвь `Never` не участвует в слиянии                                         |

## Приложение D: Разрешение неоднозначности функция / значение блока

### Проблема

`name = { ... }` ранее определялся двумя принятыми RFC по-разному: RFC-007 (синтаксис функций)
трактовал его как функцию («кратчайшая форма без параметров» `name = { return ... }`), а RFC-010 /
010a — как значение блока (`= {}` — блок со значением, значением является хвостовое выражение). Одна
и та же синтаксическая позиция, две семантики; на уровне реализации `callable_parts()` регистрировал
блок как 0-аргументную функцию, а `generate_block_ir` брал значение по правилу блока — два уровня
понимания были несогласованы.

### Решение: тип определяется содержимым

Тот же принцип должен быть проведён через словари и блоки:

| Случай                        | Результат                | Основание                              |
| ----------------------------- | ------------------------ | -------------------------------------- |
| `value` — это `Lambda` (`=>`) | Функция                  | `=>` — явный конструктор функции       |
| Аннотация — `Fn`              | Функция                  | Объявлен функциональный тип            |
| Аннотация — не-`Fn` тип       | Значение блока           | Аннотация и есть тип (`x: Int = {..}`) |
| **Без аннотации**             | **Вывод по содержимому** | **Тип определяется содержимым**        |

```yaoxiang
x: Int = { y = 5; y }      // Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       // Функция: f() = 5 (аннотация Fn)
f = { 5 }                  // Значение: f = 5 (без аннотации → вывод по содержимому)
f = {}                     // Значение: f = Void (пустой блок)
b = () => 5                // Функция: явная лямбда
d = { "a": 1 }             // Значение: Dict (самодескриптивное содержимое)
```

**Почему не «без аннотации — по умолчанию функция»**: тогда `f = { 5 }` — функция, а
`d = { "a": 1 }` — словарь — одинаковая `{` в одинаковой позиции без аннотации даёт сущности разной
категории. Все три рассмотренных аргумента несостоятельны:

1. Существующий код не меняется — стоимость миграции допустима (211 файл, 704 места), это не
   семантический аргумент
2. Определение функции — частое, значение блока — редкое — частота не является правилом типизации
3. RFC-007 уже принят, пересмотр его дороже, чем настоящего RFC — неправильное не становится
   правильным из-за «дороговизны»

**Тип определяется содержимым**, вне зависимости от наличия аннотации. Аннотация по-прежнему
объявляет тип (`f: () -> Int`), но не навязывает значение по умолчанию из-за «отсутствия аннотации».

### Куда отнести `{}`

Грамматика `Dict` требует хотя бы один ключ; `{}` не имеет содержимого для опоры, поэтому берётся
нулевая форма блочной структуры — пустой блок, значение `Void`. Для пустого словаря используйте
`dict.new()`. Подробнее см. spec [§2.9.1](../../../reference/language-spec/syntax.md).

### Сопутствующие исправления реализации

1. **Аннотация не должна определять взятие значения**: `generate_function_ir` и ещё два места
   использовали `return_type != Void` как порог взятия значения хвостового выражения, из-за чего
   хвостовое выражение `f = { 5 }` без аннотации молча отбрасывалось, возвращался `Void`. Аннотация
   только решает, _проверять_ ли, но не решает, _вычислять_ ли.
2. **`callable_parts()` больше не глотает блок безусловно**: диспетчеризация унифицирована через
   `Expr::block_binding_is_function(аннотация, значение)`.
