# RFC-010a: Вычисление хвостового выражения и семантика return

> **Ссылки**:
>
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md) — модель
>   `name: type = value`, `{}` как зависимо-управляемая вычислительная единица
> - [RFC-007: Унификация синтаксиса определения функций](./007-function-syntax-unification.md) —
>   правила возврата блоков кода, досрочный возврат
> - [RFC-038: Завершение операторов и правила перевода строк](038-statement-termination.md) —
>   поведение операторов и выражений при переводе строк
> - [Спецификация языка §Система типов](/reference/language-spec/type-system.md) — принцип взрыва
>   `Never`

## Резюме

Унифицируется семантика `return` и вычисления блока, устраняется конфликт формулировок между RFC-007
и RFC-010.

Предлагаются **три согласованных правила**: значение блока равно его хвостовому выражению
(единственный выход); `return` — это **нелокальный выход** с типом `Never` (выход из функции, а не
«возврат в блок»); `if` без `else` принимает значение `Void`.

`return` и вычисление блока **не разделяются на уровне языка** — `{ return n }` как блок имеет
значение `n` (тип `Never`), и одновременно `return` осуществляет выход из функции; оба факта
сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Досрочный возврат» из RFC-007 и «блок
имеет значение» из RFC-010 являются следствиями этих трёх правил, а не противоречащими исключениями.

Никакого нового синтаксиса, никаких новых ключевых слов.

## Мотивация

### Конфликт формулировок

Пример с числами Фибоначчи на playground обнажил семантическое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return — «от if» или «от функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два уже принятых RFC дают **противоположные** выводы:

| RFC                  | Формулировка                                                                                                                                              | Выводимая семантика                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **RFC-007** (принят) | На примере `factorial` заголовок гласит **«Досрочный возврат: использование return»**: `if n <= 1 { return 1 }`                                           | `return` проходит сквозь `if` и тело функции, **возвращаясь в функцию** |
| **RFC-010** (принят) | «`{}` — зависимо-управляемая вычислительная единица… используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` отдаёт значение **этому `{}`**                                 |

По RFC-010 фигурные скобки в `if n <= 1 { return 1 }` — вычислительная единица, `return 1` даёт ей
значение 1, значит значение `if` отбрасывается, следующая строка обязательно выполняется — **fib
зацикливается**. По RFC-007 — работает корректно.

### Корневая причина: двойная роль слова `return`

- **RFC-007 использует его для выражения «выхода из функции»** — концепция потока управления
- **RFC-010 использует его для выражения «значение этого блока равно ему»** — концепция вычисления

Использовать ключевое слово потока управления для выражения вычисления — категориальная ошибка
(category error). Одно слово несёт две роли, и как ни настраивай, одна из сторон приносится в
жертву.

### Усугубляющее ошибочное расширение в нижестоящих документах

Документ `docs/src/reference/language-spec/syntax.md` расширил «`{}` блок» из RFC-010 до **всех
фигурных скобок**:

- §2.9: «`return` в `{}` **всегда возвращает содержимое во внешнюю область видимости**» (и называет
  это «унифицированной семантикой: все блоки `{}`»)
- §3.3: «`return` используется для **возврата значения из блока кода**»

Тогда как исходный RFC-010 определял **три вида блоков со значением** (`= {}` / `spawn {}` /
`unsafe {}`), и **нигде не затрагивал фигурные скобки `if` / `while` / `for` / `match`**.

### Текущее состояние реализации

| Поведение                                             | Текущее состояние                                       |
| ----------------------------------------------------- | ------------------------------------------------------- |
| `if n == 0 { return 7 } … return 8`                   | Выход из функции (`h(0) = 7`)                           |
| `f = { n + 1 }`                                       | Хвостовое выражение доступно (возвращает `5`)           |
| `x = { y = 5; y }` (хвостовое выражение голого блока) | `E3006` переменная не разрешена (см. #343)              |
| `f: () -> Int = { if c {5} else {6} }`                | Возвращает `void`, хвостовое выражение отброшено (#344) |
| `f: () -> Int = { "s" }`                              | Тихо проходит компиляцию (см. #345)                     |
| `x = if c { 19 }` (без `else`)                        | `19` (должно быть `Void`, см. #346)                     |
| `v = unsafe { 42 }`                                   | `void` (см. #347)                                       |
| `y = if c { 111 } else { 222 }`                       | Доступно (`if` как выражение)                           |

Файл `tests/yaoxiang/03-semantics/no_tail_expr_return.yx` ранее утверждал, что «хвостовое выражение
больше не возвращается неявно», но не покрывал этот случай, поэтому тест оставался зелёным. Этот
файл был заменён на `tests/yaoxiang/03-semantics/tail_expr_and_return.yx`.

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение (единственный выход)
   Значение оператора присваивания — Void; пустой блок {} имеет значение Void
② return : (T) -> Never
   Нелокальный выход: выход через ближайшую границу функции
③ if без else → Void
```

**Этих трёх правил достаточно, чтобы вывести «досрочный возврат»; никакого дополнительного правила о
том, что `return` — функциональный, не требуется.**

### Правило ①: значение блока

**Последний оператор/выражение** блока — это значение блока (хвостовое выражение). Это **не** «нет
хвостового выражения — значит `Void`» — непустой блок всегда имеет хвостовое выражение (сам этот
последний оператор и является им), а пустой блок `{}` имеет значение `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Оператор присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание как хвостовое выражение → значение блока Void
b = {
    x = compute()
    log(x)               // Оператор присваивания → Void
}

// Хотите Void — пишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Проектный критерий (разделение механизма и защиты)**:

- **Языковое правило даёт только механизм**: последний оператор — значение блока, правило
  единственно, без двусмысленности
- **Защита обеспечивается проверкой типов**: объявление функции `-> Int`, а тип хвостового выражения
  не совпадает → ошибка компиляции
- **Язык не защищает от «неверного намерения»**: если тип хвостового выражения случайно совпадает с
  типом возврата, но семантика не та, что задумана, — это недосмотр автора, язык не в состоянии это
  определить. **Не полагаться на языковые правила для защиты от неверных намерений.**
- **Не хотите возвращать — пишите `Void` явно**

Это заменяет правило RFC-010 «`= { ... }` обязан использовать `return`, иначе возвращается `Void`»,
а также его обоснование «требуется явный `return` для устранения неоднозначности относительно того,
является ли последнее выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (нулевой конструктор, значение не может населять). Его семантика:

- **Выход через ближайшую границу функции**, передача значения вызывающему
- **Проникновение сквозь любые блоки** — (если имеются) `if` / `while` / `for` / `match` / голые
  блоки / `spawn` / `unsafe`

`return` не «возвращает в блок». `{ return n }` как блок имеет значение `n` (правило хвостового
выражения), **тип `Never`**; одновременно действие `return` — выход из функции. **Оба факта верны
одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // Без else
```

При ложном условии вычислять нечего, берётся `Void`. Поэтому тип значения этого `if` — `Void` (или
непригоден для позиции, отличной от `Void`).

Когда значение нужно, явно допишите обе ветви:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` выполняется для любого типа `T` (принцип взрыва, см. спецификацию языка §Система
типов). Поэтому:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → Значение этого if : Never
  fib(n - 1) + fib(n - 2) // → Значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Оператор типа `Never` означает **прерывание последовательности здесь** — следующее выражение не
  «выполняется как очередной шаг»
- А `Never` сводится к любому типу (принцип взрыва), поэтому весь блок удовлетворяет `-> Int`

**«Досрочный возврат» естественно выводится отсюда**: `Never` прерывает последовательность + принцип
взрыва позволяет сведение.

## Детальное проектирование

### Формализация блоков и хвостовых выражений

```
Block        ::= '{' Stmt* '}'                     // Пустой блок → Void
               | '{' Stmt* Expr '}'                // Значение = Expr
Expr         ::= ...
               | Return                            // Тип Never
Stmt         ::= Assignment | ExprStmt | ...

значение(Block):
  пустой блок               → Void
  { ...; e }                → тип(e)
  { ...; s } (s — оператор) → Void          // Значение присваивания — Void
```

### Правило типизации для `return`

```
return e : Never        где e : T

// Поскольку Never <: T' для любого T', return может появляться в любой позиции возврата
```

**Никаких дополнительных правил для ограничения допустимости `return` не требуется** — принцип
взрыва уже покрывает. Это устраняет вопрос «может ли `return` появиться в функции, возвращающей
`X`».

### Слияние нескольких ветвей

```
join(A, B):
  Если A : Never  → B
  Если B : Never  → A
  Иначе           → требуется совместимость A, B (один тип или общая верхняя граница)
```

Несколько ветвей `if` / `match` сливаются по `join`. Ветви с `return` имеют тип `Never` и не
участвуют в слиянии.

### Согласованность с RFC-007

Примеры RFC-007 **полностью соответствуют настоящему RFC**, пересмотр не требуется:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Ветвь Never, игнорируется join
    return n * factorial(n - 1)     // Выход из функции
}
```

«Досрочный возврат» — не исключение, а **следствие** правил ①② и принципа взрыва.

### Расхождения с RFC-010 и требования к пересмотру

RFC-010 нуждается в пересмотре трёх мест (в виде опечатки корректуры, см. «Требования к пересмотру
нижестоящих документов»):

| Пункт RFC-010                                            | После пересмотра                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| «`= { ... }` обязан использовать `return`, иначе `Void`» | Значение блока = хвостовое выражение; пустой блок → `Void`                            |
| Обоснование «явный `return` устраняет неоднозначность»   | Аннулировано — хвостовое выражение не создаёт неоднозначности, `return` ему не мешает |
| Три примера `return c` / `return SqliteDb`               | Заменены на хвостовые выражения (единый выход значения для `spawn` / `unsafe`)        |

**Основной проект RFC-010 (`{}` как зависимо-управляемая вычислительная единица) остаётся
неизменным** — только выход значения меняется с `return` на хвостовое выражение.

### Единая перспектива (принцип проектирования)

Фигурные скобки `if` / `while` — это **и императивное управляющее тело, и декларативная
вычислительная единица** — это **различие перспектив, а не две языковые конструкции**. Поэтому:

- **Не разделять на уровне языка** «управляющую конструкцию» и «вычислительную единицу»
- Все блоки используют единый набор правил вычисления (правило ①)
- `return` — единственный механизм-исключение, и его исключительность проистекает из свойств теории
  типов `Never`, а не из синтаксического особого случая

Это позволяет декларативному и питоноподобному стилям сосуществовать естественно:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## Компромиссы

### Преимущества

- **Устранение конфликта RFC**: RFC-007 и RFC-010 из противоречия превращаются в отношение
  следствия, ни одна из сторон не приносится в жертву
- **Минимальное число правил**: три правила + одно свойство теории типов (принцип взрыва), без
  исключений
- **Единственное значение `return`**: выход из функции. Больше не нужно разбираться, принадлежит ли
  он «значению блока» или «значению функции»
- **Единая перспектива**: императивный и декларативный стили сосуществуют без деления на уровне
  языка
- **Согласованность со зрелыми языками**: Rust также совмещает «хвостовое выражение + `return : !`»
- **Нулевой новый синтаксис**: без новых ключевых слов, без изменения правил грамматического разбора

### Недостатки

- **Риск «ошибочного возврата» из-за последнего выражения**: забыл удалить последнюю строку —
  возвращаемое значение молча меняется
  - Смягчение: проверка типов перехватывает несоответствие; язык не обещает защиту от неверных
    намерений (см. проектный критерий)
- **RFC-010 нуждается в корректуре**: примеры в принятом документе должны быть переписаны
- **Хвостовое выражение голого блока ожидает реализации**: в настоящее время — внутренняя ошибка
  компилятора (независимо от данного проекта)
- **Необходимо уточнить взаимодействие с завершением операторов**: остаётся ли последнее выражение,
  разделённое переводом строки, значением блока (см. открытые вопросы)

## Альтернативы

### Вариант A: `return` сохраняет двойную роль, диспетчеризация по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` — блоку; в `if {}` /
голом блоке — чему?

**Причина отклонения**: принадлежность `if` неразрешима — это и есть исходный конфликт. И
пользователю пришлось бы помнить «каким блокам кто», а принципиального обоснования нет (почему `if`
принадлежит функции, а голый блок — себе?).

### Вариант B: строгий возврат блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **утрата функциональности**. `return` никогда не сможет досрочно выйти из
вложенного блока, guard clause (`if err { return }`) становится принципиально невыразимым, остаётся
только писать функцию как слой за слоем вложенные выражения.

### Вариант C: значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевого изменения синтаксиса** из RFC-036 (требуется
новое ключевое слово), и пользователю пришлось бы учить две концепции (`return` для выхода + `give`
для значения). Решение с хвостовым выражением — ноль новых концепций.

### Вариант D: сохранить RFC-010 как есть (обязательный явный `return`)

**Причина отклонения**: конфликт с RFC-007 непримирим (см. мотивацию). И фактическая реализация уже
пошла по пути хвостового выражения.

## Приложение D: Разрешение неоднозначности функция / значение блока (решение C)

> **Корректура (2026-09-19): вариант решения C для случая без аннотации отменён.**
>
> Решение пользователя: **унифицировать по «тип определяется содержимым» (прочтение B)**,
> обоснование: один и тот же принцип должен пронизывать словарь и блок:
>
> > Унифицировать в B, `{}` естественно встаёт на место.
>
> **Действующее правило**
>
> | Ситуация                  | Результат                | Основание                              |
> | ------------------------- | ------------------------ | -------------------------------------- |
> | `value` — `Lambda` (`=>`) | Функция                  | `=>` — явный конструктор функции       |
> | Аннотация — `Fn`          | Функция                  | Объявлен функциональный тип            |
> | Аннотация — не `Fn` тип   | Значение блока           | Аннотация и есть тип (`x: Int = {..}`) |
> | **Без аннотации**         | **Вывод по содержимому** | **Тип определяется содержимым**        |
>
> Ключевое изменение: `f = { 5 }` теперь — **значение** `5` (`Int`), а не функция.
>
> ```yaoxiang
> x: Int = { y = 5; y }      // Значение блока: x = 5 (аннотация не Fn)
> f: () -> Int = { 5 }       // Функция: f() = 5 (аннотация Fn)
> f = { 5 }                  // Значение: f = 5 (без аннотации → вывод по содержимому)
> f = {}                     // Значение: f = Void (пустой блок)
> b = () => 5                // Функция: явный lambda
> d = { "a": 1 }             // Значение: Dict (содержимое самоописательно)
> ```
>
> **Почему решение C отменено**
>
> Изначальное обоснование решения C («без аннотации по умолчанию функция») было ориентировано на
> удобство реализации:
>
> 1. ~~нулевые изменения существующего кода~~ — стоимость миграции приемлема (211 файл, 704 места),
>    это не семантическое обоснование
> 2. ~~определение функций — частое, значение блока — редкое~~ — частота — не правило типизации
> 3. ~~RFC-007 уже принят, менять его дороже, чем этот RFC~~ — исправление неверного не становится
>    верным из-за «дороговизны»
>
> Истинная проблема — **несогласованность**: `f = { 5 }` — функция, но `d = { "a": 1 }` — словарь —
> та же `{` в той же позиции без аннотации даёт сущности разной категории. «Цена», которую решение C
> само признавало, и есть эта трещина: «`f` в `f = { 5 }` — функция, а не `5`… вопреки интуиции
> «фигурные скобки — это значение»».
>
> Действующее правило устраняет трещину: **тип определяется содержимым**, независимо от наличия
> аннотации. Аннотация по-прежнему объявляет тип (`f: () -> Int`), но не навязывает значение по
> умолчанию из-за «отсутствия аннотации».
>
> **Куда встаёт `{}`**
>
> После унификации в B `{}` естественно встаёт на место: грамматика `Dict` требует хотя бы один
> ключ, для `{}` опираться не на что, поэтому берётся нулевая форма блочной структуры → пустой блок,
> значение `Void`. Пустой словарь — через `dict.new()`. Подробнее см. спецификацию
> [§2.9.1](../.../reference/language-spec/syntax.md).
>
> **Неизменные локальные положения**
>
> Два последующих положения Приложения D («аннотация не должна определять взятие значения»,
> «`callable_parts()` больше не безусловно поглощает блок») остаются в силе; последнее сейчас
> реализуется через `Expr::block_binding_is_function`, только его ветвь без аннотации изменилась
> согласно таблице выше.

### Проблема (исторический контекст)

`name = { ... }` одновременно определяется двумя принятыми RFC как разные сущности:

| RFC                         | Определение                                                                  |
| --------------------------- | ---------------------------------------------------------------------------- |
| RFC-007 (синтаксис функций) | Функция. «Простейшая без параметров» `name = { return ... }`                 |
| RFC-010 / 010a              | Значение блока. «`= {}` — блок со значением, значение — хвостовое выражение» |

Одна и та же синтаксическая позиция, две семантики — на уровне реализации `callable_parts()`
регистрировал блок как 0-арную функцию, тогда как `generate_block_ir` брал значение блока — два
уровня понимания рассогласованы.

### Первоначальное решение: приоритет аннотации, по умолчанию функция (**отменено**)

| Ситуация                  | Результат          | Основание                                            |
| ------------------------- | ------------------ | ---------------------------------------------------- |
| `value` — `Lambda` (`=>`) | Функция            | `=>` — явный конструктор функции                     |
| Аннотация — `Fn`          | Функция            | Объявлен функциональный тип                          |
| Аннотация — не `Fn` тип   | **Значение блока** | Аннотация и есть тип (`x: Int = {..}`)               |
| Без аннотации             | **Функция**        | По умолчанию; «простейшая без параметров» из RFC-007 |

**Ключевое: семантика значения блока не требует нового синтаксиса.** Хотите `{ ... }` вычислить на
месте — запишите целевой тип:

```yaoxiang
x: Int = { y = 5; y }      # Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       # Функция: f() = 5 (аннотация Fn)
f = { 5 }                  # Функция: f() = 5 (без аннотации, по умолчанию)  # ← Эта строка отменена
b = () => 5                # Функция: expression-lambda
```

### Первоначальное обоснование (**утратило силу**)

Аннотация **и так объявляет тип**: `x: Int = ...` говорит, что `x` — `Int`, значит `{...}` —
значение `Int`; `f: () -> Int = ...` говорит, что `f` — функция, значит `{...}` — тело функции.
**Тип-ориентированно, а не новое правило.**

Без аннотации по умолчанию функция, потому что:

1. Нулевые изменения существующего кода (в репозитории 203 безаннотационные привязки `name = { `,
   все — `main`)
2. Определение функций — частое, значение блока — редкое
3. RFC-007 уже принят, менять его дороже, чем этот RFC

### Цена (известна и принята)

`f` в `f = { 5 }` — **функция**, а не `5`. Это противоречит интуиции «фигурные скобки — значение» —
но это и есть определение, принятое в RFC-007, и **аннотация служит спасательным выходом**: запись
`f: Int = { 5 }` даёт значение.

### Дефекты реализации, исправленные тем же решением

1. **Аннотация не должна определять взятие значения** (корневая причина один): в трёх местах,
   включая `generate_function_ir`, `return_type != Void` использовался как порог взятия хвостового
   выражения, из-за чего хвостовое выражение в безаннотационном `f = { 5 }` молча отбрасывалось,
   возвращался `Void`. Аннотация определяет лишь, нужна ли _проверка_, а не нужно ли _вычисление_.
2. **`callable_parts()` больше не безусловно поглощает блок**: разветвление унифицировано через
   `Expr::block_binding_is_function(аннотация, значение)`.
