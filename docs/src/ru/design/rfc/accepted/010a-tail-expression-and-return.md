# RFC-010a: Вычисление хвостового выражения и семантика return

> **Ссылки**:
>
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md) — модель
>   `name: type = value`, зависимая от вычислений единица `{}`
> - [RFC-007: Унификация синтаксиса определения функций](./007-function-syntax-unification.md) —
>   правила возврата блока кода, досрочный возврат
> - [RFC-038: Завершение операторов и правила переноса строк](038-statement-termination.md) —
>   поведение переноса строк для операторов и выражений
> - [Спецификация языка §Система типов](/reference/language-spec/type-system.md) — принцип взрыва
>   `Never`

## Аннотация

Унифицировать семантику `return` и вычисления блока, устранить конфликты формулировок между RFC-007
и RFC-010.

Предложены **три самосогласованных правила**: значение блока равно его хвостовому выражению
(единственный выход); `return` — это **нелокальный выход** типа `Never` (выход из функции, не
«возврат блоку»); `if` без `else` принимает `Void`.

`return` и вычисление блока **не разделяются на уровне языка** — `{ return n }` как блок имеет
значение `n` (тип `Never`), в то же время `return` осуществляет выход из функции; оба факта
сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Досрочный возврат» из RFC-007 и «блок
имеет значение» из RFC-010 — следствия этих трёх правил, а не противоречащие особые случаи.

Никакого нового синтаксиса, никаких новых ключевых слов.

## Мотивация

### Конфликт формулировок

Пример Фибоначчи из playground выявил семантическое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return — от «if» или от «функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два принятых RFC дают **противоположные** выводы:

| RFC                  | Формулировка                                                                                                                                 | Выводимая семантика                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **RFC-007** (принят) | На примере `factorial`, заголовок **«Досрочный возврат: использование return»**: `if n <= 1 { return 1 }`                                    | `return` проходит сквозь `if` и тело функции, **возвращаясь в функцию** |
| **RFC-010** (принят) | «`{}` — зависимая от вычислений единица…используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` задаёт **значение этого `{}`**                                 |

Согласно RFC-010, фигурные скобки в `if n <= 1 { return 1 }` — это вычислительная единица,
`return 1` задаёт её значение 1, значит значение `if` отбрасывается, и следующая строка обязательно
выполнится — **fib зацикливается бесконечно**. Согласно RFC-007 — корректно.

### Корневая причина: двойная роль слова `return`

- **RFC-007 использует его для выражения «выход из функции»** — концепция потока управления
- **RFC-010 использует его для выражения «значение этого блока — оно»** — концепция вычисления

Использование ключевого слова потока управления для выражения вычисления — категориальная ошибка.
Одно слово с двумя ролями, как ни настраивай, одна из сторон будет принесена в жертву.

### Расширение ошибки в нижестоящей документации

`docs/src/reference/language-spec/syntax.md` расширил «блок `{}`» из RFC-010 на **все фигурные
скобки**:

- §2.9: «`return` внутри `{}` **всегда возвращает содержимое в вышестоящую область видимости**» (и
  утверждает «унифицированная семантика: все блоки `{}`»)
- §3.3: «`return` используется **для возврата значения из блока кода**»

Тогда как исходный текст RFC-010 определяет **три типа блоков со значением** (`= {}` / `spawn {}` /
`unsafe {}`), и **нигде не затрагивает фигурные скобки `if` / `while` / `for` / `match`**.

### Текущее состояние реализации

| Поведение                               | Состояние                                  |
| --------------------------------------- | ------------------------------------------ |
| `if n == 0 { return 7 } … return 8`     | Выход из функции (`h(0) = 7`)              |
| `f = { n + 1 }`                         | Хвостовое выражение работает (возврат `5`) |
| `x = { y = 5; y }` (хвост голого блока) | `E3006` переменная не разрешена (см. #343) |
| `f: () -> Int = { if c {5} else {6} }`  | Возвращает `void`, хвост отброшен (#344)   |
| `f: () -> Int = { "s" }`                | Тихо проходит компиляцию (см. #345)        |
| `x = if c { 19 }` (без `else`)          | `19` (должно быть `Void`, см. #346)        |
| `v = unsafe { 42 }`                     | `void` (см. #347)                          |
| `y = if c { 111 } else { 222 }`         | Работает (`if` как выражение)              |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx` ранее утверждал, что «хвостовое выражение
больше не возвращается неявно», но не покрывал этот случай, поэтому тест не падал. Файл заменён на
`tests/yaoxiang/03-semantics/tail_expr_and_return.yx`.

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение (единственный выход)
   Значение оператора присваивания — Void; значение пустого блока {} — Void
② return : (T) -> Never
   Нелокальный выход: выход из ближайшей границы функции
③ if без else → Void
```

**Этих трёх достаточно, чтобы вывести «досрочный возврат», без дополнительного правила о `return`
как специфическом для функции.**

### Правило ①: значение блока

**Последний оператор/выражение** блока — это значение блока (хвостовое выражение). Это **не** «нет
хвостового выражения — значит Void» — непустой блок всегда имеет хвостовое выражение (последний
оператор и есть оно), значение пустого блока `{}` — `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Оператор присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание как хвостовое выражение → значение блока Void
b = {
    x = compute()
    log(x)               // Оператор присваивания → Void
}

// Хотите Void — пишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Обоснование дизайна (разделение механизма и защиты)**:

- **Языковое правило задаёт только механизм**: последний оператор есть значение блока, правило
  единственно, без неоднозначности
- **Защита обеспечивается проверкой типов**: объявление функции `-> Int`, а тип хвостового выражения
  не совпадает → ошибка компиляции
- **Язык не защищает от «ошибки намерения»**: если тип хвостового выражения случайно совпал с
  возвращаемым типом, но семантика не та — это недосмотр автора, язык не может это определить. **Не
  полагаемся на языковые правила для защиты от ошибки намерения.**
- **Не хотите возвращать — пишите явно `Void`**

Это заменяет положение «`= { ... }` должен использовать `return`, иначе возвращает `Void`» из
RFC-010, а также обоснование «необходим явный `return` для устранения неоднозначности, является ли
последнее выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (ноль конструкторов, нечего населять). Семантика:

- **Выходит из ближайшей границы функции**, передавая значение вызывающему
- **Проходит сквозь любые блоки** — (если есть) `if` / `while` / `for` / `match` / голые блоки /
  `spawn` / `unsafe`

`return` не «возвращает блоку». `{ return n }` как блок имеет значение `n` (правило хвостового
выражения), **тип `Never`**; в то же время `return` осуществляет выход из функции. **Оба факта верны
одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // без else
```

Когда условие ложно, нет ветви для вычисления, берётся `Void`. Поэтому тип значения этого `if` —
`Void` (или его нельзя использовать в позиции, не являющейся `Void`).

Если нужно значение, явно заполните обе ветви:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` верно для любого типа `T` (принцип взрыва, см. спецификацию языка §Система типов).
Поэтому:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → значение этого if : Never
  fib(n - 1) + fib(n - 2) // → значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь этого `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Оператор типа `Never` означает **прерывание последовательности здесь** — следующее выражение — это
  не «следующая по порядку инструкция»
- А `Never` может быть приведено к любому типу (принцип взрыва), значит весь блок удовлетворяет
  `-> Int`

**«Досрочный возврат» выводится естественно**: `Never` прерывает последовательность + принцип взрыва
позволяет приведение.

## Детальный дизайн

### Формализация блока и хвостового выражения

```
Block        ::= '{' Stmt* '}'                     // пустой блок → Void
               | '{' Stmt* Expr '}'                // значение = Expr
Expr         ::= ...
               | Return                            // тип Never
Stmt         ::= Assignment | ExprStmt | ...

Значение(Block):
  пустой блок               → Void
  { ...; e }                → тип(e)
  { ...; s } (s — оператор) → Void          // значение присваивания — Void
```

### Правило типов для `return`

```
return e : Never        где e : T

// Поскольку Never <: T' верно для любого T', return может появляться в любой позиции возврата
```

**Никаких дополнительных правил для ограничения легитимности `return` не требуется** — принцип
взрыва уже покрывает. Это устраняет вопрос «может ли `return` появляться в функции, возвращающей
`X`».

### Слияние нескольких ветвей

```
join(A, B):
  если A : Never  → B
  если B : Never  → A
  иначе           → требуется совместимость A и B (один тип или достижимая общая верхняя граница)
```

Несколько ветвей `if` / `match` сливаются по `join`. Ветвь с `return` не участвует в слиянии из-за
типа `Never`.

### Согласованность с RFC-007

Пример из RFC-007 **полностью соответствует данному RFC** и не требует пересмотра:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // ветвь Never, игнорируется join
    return n * factorial(n - 1)     // выход из функции
}
```

«Досрочный возврат» — не особый случай, а **следствие** правил ①② и принципа взрыва.

### Отличия от RFC-010 и требования к пересмотру

Определение RFC-010 пересмотрено в соответствии с данным RFC, отличия следующие:

| Исходный пункт RFC-010                                                           | Текущее определение                                                                       |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| «`= { ... }` должен использовать `return`, иначе возвращает `Void`»              | Значение блока = хвостовое выражение; пустой блок → `Void`                                |
| Обоснование «явный `return` для устранения неоднозначности хвостового выражения» | Несостоятельно — хвостовое выражение не порождает неоднозначности, `return` ему не мешает |
| Три примера `return c` / `return SqliteDb`                                       | Запись через хвостовое выражение (унифицированный выход значения для `spawn` / `unsafe`)  |

**Основной дизайн RFC-010 (`{}` как зависимая от вычислений единица) не изменяется**, только выход
значения заменён с `return` на хвостовое выражение.

### Унификация перспектив (принцип дизайна)

Фигурные скобки `if` / `while` — это **и императивное управляющее тело, и декларативная
вычислительная единица** — это **различие перспектив, а не две языковые конструкции**. Поэтому:

- **Не разделяем на уровне языка** «управляющее тело» и «вычислительная единица»
- Все блоки используют одни и те же правила вычисления (правило ①)
- `return` — единственный механизм исключения, и его исключительность проистекает из типовых свойств
  `Never`, а не из синтаксического особого случая

Это позволяет декларативному и питон-стилю записи сосуществовать:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## Компромиссы

### Преимущества

- **Устранение конфликта RFC**: RFC-007 и RFC-010 переходят от противоречия к отношению следствия,
  без жертв с любой стороны
- **Минимум правил**: три правила + одно типотеоретическое свойство (принцип взрыва), без особых
  случаев
- **Единственное значение `return`**: выход из функции. Больше не нужно судить между «значением
  блока / значением функции»
- **Унификация перспектив**: императивное и декларативное сосуществуют, без разделения на уровне
  языка
- **Согласованность со зрелыми языками**: Rust так же сочетает «хвостовое выражение + `return : !`»
  для двух механизмов
- **Нулевой новый синтаксис**: без новых ключевых слов, без изменения правил парсера

### Недостатки

- **Риск «случайного возврата» из последнего выражения**: забыли удалить последнюю строку —
  возвращаемое значение тихо меняется
  - Смягчение: проверка типов перехватывает несоответствие типов; язык не обещает защиту от ошибки
    намерения (см. обоснование дизайна)
- **Нижестоящая документация требует синхронного пересмотра**: примеры в принятых документах нужно
  переписать
- **Необходимо уточнить взаимодействие с завершением операторов**: остаётся ли последнее выражение,
  завершённое переносом строки, по-прежнему значением блока (см. открытые вопросы)

## Альтернативы

### Вариант A: `return` сохраняет двойную роль, диспетчеризация по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` — блоку; в `if {}` /
голом блоке — кому?

**Причина отклонения**: принадлежность для `if` неразрешима — это и есть исходный конфликт. К тому
же пользователь должен помнить «каким блокам кто принадлежит», без принципиального основания (почему
`if` принадлежит функции, а голый блок — себе).

### Вариант B: строгий возврат блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **потеря функциональности**. `return` никогда не сможет досрочно выйти из
вложенного блока в функцию, guard clause (`if err { return }`) становится полностью невозможным,
функцию можно написать только как глубоко вложенные выражения.

### Вариант C: значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевого изменения синтаксиса** из RFC-036 (требуется
добавить новое ключевое слово), и пользователю придётся выучить два понятия (`return` для выхода +
`give` для значения). Решение с хвостовым выражением — ноль новых понятий.

### Вариант D: сохранить RFC-010 как есть (обязательный явный `return`)

**Причина отклонения**: конфликт с RFC-007 неразрешим (см. мотивацию). И фактическая реализация уже
пошла по пути хвостового выражения.

## Приложение A: Доказательства тестирования

Всё ниже воспроизведено на версии 0.8.0.

| Код                                               | Результат                           |
| ------------------------------------------------- | ----------------------------------- |
| `h: (n)->Int = { if n==0 { return 7 } return 8 }` | `h(0)=7`, `h(1)=8`                  |
| `f: (n)->Int = { n + 1 }`                         | `5` (хвостовое выражение работает)  |
| `f: ()->Int = { if c {5} else {6} }`              | `void` (должно быть `5`, см. #344)  |
| `f: ()->Int = if c {5} else {6}`                  | `5`                                 |
| `f: ()->Int = { match ... }`                      | корректно                           |
| `f: ()->Int = { while ...; i }`                   | корректно                           |
| `{ y = 5; y }` как выражение привязки             | `E3006` (см. #343)                  |
| `f: ()->Int = { "s" }`                            | Тихо проходит (см. #345)            |
| `x = if c { 19 }` (без `else`)                    | `19` (должно быть `Void`, см. #346) |
| `v = unsafe { 42 }`                               | `void` (см. #347)                   |
| `y = if c { 111 } else { 222 }`                   | `111`                               |
| `while { if i==2 { return 42 } }`                 | `42` (выход из цикла)               |

## Приложение C: Глоссарий

| Термин              | Определение                                                                                                                |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Хвостовое выражение | Последнее производящее значение выражение в блоке; значение блока равно ему                                                |
| Нелокальный выход   | Передача потока управления через внешние вычислительные единицы, действующая непосредственно на границу функции (`return`) |
| Принцип взрыва      | `Never <: T` верно для любого `T`, что позволяет приводить `Never` к любому типу                                           |
| Блок со значением   | `= {}` / `spawn {}` / `unsafe {}` — выход значения через хвостовое выражение                                               |
| join                | Правило слияния нескольких ветвей, ветви `Never` не участвуют в слиянии                                                    |

## Приложение D: Разрешение неоднозначности функции / значения блока

### Проблема

`name = { ... }` ранее определялся двумя принятыми RFC по-разному: RFC-007 (синтаксис функций)
трактовал его как функцию («нульарный минимум» `name = { return ... }`), RFC-010 / 010a — как
значение блока (`= {}` — блок со значением, значение — хвостовое выражение). Та же синтаксическая
позиция — две семантики; в реализации `callable_parts()` регистрировал блок как 0-арную функцию, а
`generate_block_ir` брал значение как значение блока — два уровня понимания не согласованы.

### Решение: содержание определяет тип

Один и тот же принцип должен пронизывать словарь и блок:

| Случай                        | Результат               | Обоснование                            |
| ----------------------------- | ----------------------- | -------------------------------------- |
| `value` — это `Lambda` (`=>`) | Функция                 | `=>` — явный конструктор функции       |
| Аннотация — `Fn`              | Функция                 | Объявлен функциональный тип            |
| Аннотация — не `Fn` тип       | Значение блока          | Аннотация и есть тип (`x: Int = {..}`) |
| **Без аннотации**             | **Вывод по содержанию** | **Тип определяется содержанием**       |

```yaoxiang
x: Int = { y = 5; y }      // Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       // Функция: f() = 5 (аннотация Fn)
f = { 5 }                  // Значение: f = 5 (без аннотации → вывод по содержанию)
f = {}                     // Значение: f = Void (пустой блок)
b = () => 5                // Функция: явная лямбда
d = { "a": 1 }             // Значение: Dict (содержание самоописательно)
```

**Почему не «без аннотации — по умолчанию функция»**: тогда `f = { 5 }` — функция, а
`d = { "a": 1 }` — словарь — та же `{` в той же позиции без аннотации даёт сущности разных
категорий. Все три ранее рассмотренных основания несостоятельны:

1. Существующий код — без изменений — стоимость миграции допустима (211 файл, 704 места), это не
   семантическое основание
2. Определение функций — частое, значение блока — редкое — частота не правило типов
3. RFC-007 принят, изменять его дороже, чем данный RFC — неправильное не становится правильным из-за
   «дороговизны»

**Тип определяется содержанием**, а не наличием аннотации. Аннотация всё ещё объявляет тип
(`f: () -> Int`), но не накладывает значение по умолчанию из-за «отсутствия аннотации».

### Место `{}`

Грамматика `Dict` требует хотя бы один ключ, `{}` не имеет содержания для опоры, поэтому берётся
нулевая форма структуры блока → пустой блок, значение `Void`. Для пустого словаря используется
`dict.new()`. Подробности см. в спецификации [§2.9.1](../.../reference/language-spec/syntax.md).

### Сопутствующие исправления реализации

1. **Аннотация не должна определять извлечение значения**: `generate_function_ir` и две другие точки
   использовали `return_type != Void` как порог извлечения хвостового выражения, в результате
   безаннотационный `f = { 5 }` тихо отбрасывал хвостовое выражение и возвращал `Void`. Аннотация
   только определяет, _проверять_ ли, а не _вычислять_ ли.
2. **`callable_parts()` больше не безусловно поглощает блок**: разделение потоков унифицировано
   через `Expr::block_binding_is_function(аннотация, значение)`.
