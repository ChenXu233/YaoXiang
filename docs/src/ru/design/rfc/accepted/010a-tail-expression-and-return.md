# RFC-010a: Вычисление хвостовых выражений и семантика return

> **Ссылки**:
>
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md) — модель
>   `name: type = value`, вычислительная единица на основе зависимостей `{}`
> - [RFC-007: Унификация синтаксиса определения функций](./007-function-syntax-unification.md) —
>   правила возврата блоков кода, досрочный возврат
> - [RFC-038: Завершение операторов и правила перевода строк](038-statement-termination.md) —
>   поведение операторов и выражений при переводе строки
> - [Спецификация языка §Система типов](/reference/language-spec/type-system.md) — принцип взрыва
>   `Never`

## Резюме

Унифицировать семантику `return` и вычисления блоков, устранить конфликты формулировок между RFC-007
и RFC-010.

Предлагаются **три самосогласованных правила**: значение блока равно его хвостовому выражению
(единственный выход); `return` — это **нелокальный выход** типа `Never` (выход из функции, а не
«возврат блоку»); `if` без `else` имеет тип `Void`.

`return` и вычисление блока **не разделяются на уровне языка** — `{ return n }` как блок имеет
значение `n` (тип `Never`), и одновременно `return` выполняет выход из функции. Оба факта
сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Досрочный возврат» из RFC-007 и «блок
имеет значение» из RFC-010 — следствия этих трёх правил, а не противоречащие исключения.

Никакого нового синтаксиса, никаких новых ключевых слов.

## Мотивация

### Конфликт формулировок

Пример с числами Фибоначчи в playground обнажил смысловое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return принадлежит «if» или «функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два принятых RFC дают **противоположные** выводы:

| RFC                  | Формулировка                                                                                                                                               | Выводимая семантика                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **RFC-007** (принят) | На примере `factorial`, заголовок — **«Досрочный возврат: использование return»**: `if n <= 1 { return 1 }`                                                | `return` проходит сквозь `if` и тело функции, **возвращаясь в функцию** |
| **RFC-010** (принят) | «`{}` — вычислительная единица на основе зависимостей…используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` задаёт значение этого `{}`                                     |

Согласно RFC-010, фигурные скобки в `if n <= 1 { return 1 }` — вычислительная единица, `return 1`
задаёт её значение как 1, значит значение `if` отбрасывается, и следующая строка обязательно
выполняется — **fib уходит в бесконечную рекурсию**. Согласно RFC-007 — поведение корректное.

### Корневая причина: двойная роль слова `return`

- **RFC-007 использует его для выражения «выхода из функции»** — концепция потока управления
- **RFC-010 использует его для выражения «значение этого блока — оно»** — концепция вычисления

Использование ключевого слова потока управления для выражения вычисления — категориальная ошибка
(category error). Слово с двумя ролями — как ни настраивай, одна из сторон будет принесена в жертву.

### Расширительное толкование в нижестоящих документах

`docs/src/reference/language-spec/syntax.md` расширил «блок `{}`» из RFC-010 на **все фигурные
скобки**:

- §2.9: «`return` в `{}` **всегда возвращает содержимое во внешнюю область видимости**» (и
  называется «унифицированная семантика: все блоки `{}`»)
- §3.3: «`return` используется для **возврата значения из блока кода**»

Оригинальный RFC-010 определял **три вида блоков со значением** (`= {}` / `spawn {}` / `unsafe {}`)
и **ни разу не касался фигурных скобок `if` / `while` / `for` / `match`**.

### Текущее состояние реализации

| Поведение                                             | Текущее состояние                                       |
| ----------------------------------------------------- | ------------------------------------------------------- |
| `if n == 0 { return 7 } … return 8`                   | Выход из функции (`h(0) = 7`)                           |
| `f = { n + 1 }`                                       | Хвостовое выражение доступно (возвращает `5`)           |
| `x = { y = 5; y }` (хвостовое выражение голого блока) | `E3006` переменная не разрешена (см. #343)              |
| `f: () -> Int = { if c {5} else {6} }`                | Возвращает `void`, хвостовое выражение отброшено (#344) |
| `f: () -> Int = { "s" }`                              | Молча проходит компиляцию (см. #345)                    |
| `x = if c { 19 }` (без `else`)                        | `19` (должно быть `Void`, см. #346)                     |
| `v = unsafe { 42 }`                                   | `void` (см. #347)                                       |
| `y = if c { 111 } else { 222 }`                       | Доступно (`if` как выражение)                           |

`tests/yaoxiang/03-semantics/no_tail_expr_return.yx` некогда утверждал, что «хвостовое выражение
больше не возвращается неявно», но не покрывал данный случай, поэтому тест не падал. Этот файл
заменён на `tests/yaoxiang/03-semantics/tail_expr_and_return.yx`.

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение (единственный выход)
   Значение оператора присваивания — Void; значение пустого блока {} — Void
② return : (T) -> Never
   Нелокальный выход: выход из ближайшей границы функции
③ if без else → Void
```

**Этих трёх правил достаточно для вывода «досрочного возврата», не требуется никакого
дополнительного правила, указывающего, что `return` относится к функции.**

### Правило ①: значение блока

**Последний оператор/выражение** блока — это значение блока (хвостовое выражение). Это **не** «нет
хвостового выражения → Void» — непустой блок всегда имеет хвостовое выражение (последний оператор
сам по себе), значение пустого блока `{}` — `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Оператор присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание как хвостовое выражение → значение блока — Void
b = {
    x = compute()
    log(x)               // Оператор присваивания → Void
}

// Хотите Void — пишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Проектный критерий (разделение механизма и защиты)**:

- **Языковое правило задаёт только механизм**: последний оператор — значение блока, правило
  единственное, без двусмысленности
- **Защита обеспечивается проверкой типов**: объявление функции `-> Int`, а тип хвостового выражения
  не совпадает → ошибка компиляции
- **Язык не защищает от «ошибки намерения»**: если тип хвостового выражения случайно совпадает с
  типом возврата, но семантика не та, что задумана, — это недосмотр автора, язык не может это
  определить. **Не полагаться на языковые правила для защиты от ошибок намерения.**
- **Не хотите возвращать — пишите `Void` явно**

Это заменяет положение RFC-010 «`= { ... }` обязывает использовать `return`, иначе возвращается
`Void`», а также его обоснование «требуется явный `return` для устранения неоднозначности, является
ли последнее выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (ноль конструкторов, нечего населить). Его семантика:

- **Выход из ближайшей границы функции**, передача значения вызывающему
- **Проходит сквозь все блоки** — (при наличии) `if` / `while` / `for` / `match` / голые блоки /
  `spawn` / `unsafe`

`return` не «возвращает значение блоку». `{ return n }` как блок имеет значение `n` (правило
хвостового выражения), **тип `Never`**; одновременно `return` выполняет выход из функции. **Оба
факта выполняются одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // без else
```

Когда условие ложно, нет ветви для вычисления, берётся `Void`. Таким образом, тип значения этого
`if` — `Void` (либо его нельзя использовать в позиции, отличной от `Void`).

Когда значение необходимо, явно задаются обе ветви:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` выполняется для любого типа `T` (принцип взрыва, см. спецификацию языка §Система
типов). Следовательно:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → Значение этого if : Never
  fib(n - 1) + fib(n - 2) // → Значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Оператор типа `Never` означает **прерывание последовательности в этой точке** — следующее
  выражение — не «следующий по порядку оператор»
- А `Never` сводится к любому типу (принцип взрыва), поэтому весь блок удовлетворяет `-> Int`

**«Досрочный возврат» естественно выводится отсюда**: прерывание последовательности через `Never` +
сводимость через принцип взрыва.

## Детальное проектирование

### Формализация блоков и хвостовых выражений

```
Block        ::= '{' Stmt* '}'                     // Пустой блок → Void
               | '{' Stmt* Expr '}'                // Значение = Expr
Expr         ::= ...
               | Return                            // Тип Never
Stmt         ::= Assignment | ExprStmt | ...

Значение(Block):
  Пустой блок                → Void
  { ...; e }                 → тип(e)
  { ...; s } (s — оператор)  → Void          // Значение присваивания — Void
```

### Правило типов для `return`

```
return e : Never        где e : T

// Поскольку Never <: T' для любого T', return может появляться в любой позиции типа возврата
```

**Никаких дополнительных правил для ограничения допустимости `return` не требуется** — принцип
взрыва уже покрывает это. Вопрос «может ли `return` появляться в функции, возвращающей `X`»
снимается сам собой.

### Слияние нескольких ветвей

```
join(A, B):
  Если A : Never  → B
  Если B : Never  → A
  Иначе           → требуется совместимость A, B (один тип или достижима общая верхняя граница)
```

Несколько ветвей `if` / `match` сливаются по `join`. Ветви с `return` не участвуют в слиянии из-за
типа `Never`.

### Совместимость с RFC-007

Примеры RFC-007 **полностью соответствуют настоящему RFC**, пересмотр не требуется:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Ветвь Never, игнорируется join'ом
    return n * factorial(n - 1)     // Выход из функции
}
```

«Досрочный возврат» — не исключение, а **следствие** правил ①② и принципа взрыва.

### Отличия от RFC-010 и требования к пересмотру

Определение RFC-010 пересмотрено в соответствии с настоящим RFC, отличия следующие:

| Исходное положение RFC-010                                                  | Текущее определение                                                                     |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| «`= { ... }` обязывает использовать `return`, иначе возвращается `Void`»    | Значение блока = хвостовое выражение; пустой блок → `Void`                              |
| Обоснование «явный `return` устраняет неоднозначность хвостового выражения» | Несостоятельно — хвостовое выражение не создаёт неоднозначности, `return` ему не мешает |
| Три примера с `return c` / `return SqliteDb`                                | Запись через хвостовое выражение (унификация выхода значения для `spawn` / `unsafe`)    |

**Основной замысел RFC-010 (`{}` как вычислительная единица на основе зависимостей) сохраняется**,
только выход значения заменён с `return` на хвостовое выражение.

### Единая перспектива (проектный принцип)

Фигурные скобки `if` / `while` — это **и императивное тело управления, и декларативная
вычислительная единица** — это **разница перспектив, а не два разных языковых конструкта**. Поэтому:

- **Не разделять на уровне языка** «тело управления» и «вычислительную единицу»
- Все блоки используют единый набор правил вычисления (правило ①)
- `return` — единственный механизм-исключение, и его исключительность вытекает из теоретико-типовых
  свойств `Never`, а не из синтаксических особенностей

Это позволяет естественное сосуществование декларативного и питоноподобного стилей:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## Компромиссы

### Достоинства

- **Устраняет конфликт RFC**: RFC-007 и RFC-010 из противоречия превращаются в отношение следствия,
  ни одна из сторон не приносится в жертву
- **Минимальное число правил**: три правила + одно теоретико-типовое свойство (принцип взрыва), без
  исключений
- **Единственное значение `return`**: выход из функции. Больше не нужно решать между «значение блока
  / значение функции»
- **Единая перспектива**: императивный и декларативный стили сосуществуют без деления на уровне
  языка
- **Согласованность со зрелыми языками**: Rust так же сочетает «хвостовое выражение + `return : !`»
  для сосуществования двух механизмов
- **Нулевой новый синтаксис**: без новых ключевых слов, без изменения правил парсера

### Недостатки

- **Риск «ошибочного возврата» из последнего выражения**: при забывании удалить последнюю строку
  возвращаемое значение молча меняется
  - Смягчение: проверка типов перехватывает несоответствие типов; язык не обещает защиту от ошибок
    намерения (см. проектный критерий)
- **Требуется синхронный пересмотр нижестоящей документации**: примеры в принятых документах нужно
  переписать
- **Необходимо уточнить взаимодействие с завершением операторов**: остаётся ли последнее выражение,
  завершённое переводом строки, значением блока (см. открытые вопросы)

## Альтернативы

### Вариант A: сохранить двойную роль `return`, диспетчеризация по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` — блоку; в `if {}` /
голом блоке — чему?

**Причина отклонения**: принадлежность для `if` неразрешима — это и есть исходный конфликт. К тому
же пользователю придётся помнить «каким блокам что принадлежит», без принципиального обоснования
(почему `if` принадлежит функции, а голый блок — себе?).

### Вариант B: строгий возврат блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **потеря функциональности**. `return` никогда не сможет выполнить досрочный
выход из функции из вложенного блока, guard clause (`if err { return }`) становится принципиально
ненаписуемым, остаётся только писать функцию как каскадно вложенные выражения.

### Вариант C: значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевых синтаксических изменений** из RFC-036 (требуется
новое ключевое слово), и пользователю придётся учить две концепции (`return` для выхода + `give` для
вычисления). Схема с хвостовым выражением — ноль новых концепций.

### Вариант D: сохранить RFC-010 в исходном виде (обязательный явный `return`)

**Причина отклонения**: неразрешимый конфликт с RFC-007 (см. мотивацию). К тому же реальная
реализация уже пошла по пути хвостового выражения.

## Приложение A: Эмпирические свидетельства

Всё ниже воспроизведено на версии 0.8.0.

| Код                                               | Измерено                            |
| ------------------------------------------------- | ----------------------------------- |
| `h: (n)->Int = { if n==0 { return 7 } return 8 }` | `h(0)=7`, `h(1)=8`                  |
| `f: (n)->Int = { n + 1 }`                         | `5` (хвостовое выражение доступно)  |
| `f: ()->Int = { if c {5} else {6} }`              | `void` (должно быть `5`, см. #344)  |
| `f: ()->Int = if c {5} else {6}`                  | `5`                                 |
| `f: ()->Int = { match ... }`                      | Корректно                           |
| `f: ()->Int = { while ...; i }`                   | Корректно                           |
| `{ y = 5; y }` как выражение привязки             | `E3006` (см. #343)                  |
| `f: ()->Int = { "s" }`                            | Молча проходит (см. #345)           |
| `x = if c { 19 }` (без `else`)                    | `19` (должно быть `Void`, см. #346) |
| `v = unsafe { 42 }`                               | `void` (см. #347)                   |
| `y = if c { 111 } else { 222 }`                   | `111`                               |
| `while { if i==2 { return 42 } }`                 | `42` (выход из цикла)               |
| Вложенный `{ { return 5 } return 1 }`             | `5` (выход из голого блока)         |

## Приложение B: Журнал проектных решений

| Решение                                  | Определение                                                                               | Обоснование                                                                                | Дата       |
| ---------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------- |

| Разделение механизма и защиты            | Язык задаёт механизм, проверка типов — защиту                                             | Язык не обещает защиту от «ошибки намерения»                                               | 2026-09-15 |

| Обработка ошибочных примеров             | Удалять напрямую, не оставлять ошибочный код                                              | Сохранение кажущегося работоспособным ошибочного кода вводит в заблуждение                 | 2026-09-15 |

## Приложение C: Глоссарий

| Термин              | Определение                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Хвостовое выражение | Последнее выражение в блоке, производящее значение; значение блока равно ему                                        |
| Нелокальный выход   | Передача управления через внешние вычислительные единицы, действующая непосредственно на границу функции (`return`) |
| Принцип взрыва      | `Never <: T` выполняется для любого `T`, что позволяет сводить `Never` к любому типу                                |
| Блок со значением   | `= {}` / `spawn {}` / `unsafe {}` — выход значения через хвостовое выражение                                        |
| join                | Правило слияния нескольких ветвей, ветви `Never` не участвуют в слиянии                                             |

## Приложение D: Разрешение неоднозначности функция / значение блока

### Проблема

`name = { ... }` был определён двумя принятыми RFC по-разному: RFC-007 (синтаксис функций) трактовал
его как функцию («простейший пустой параметр» `name = { return ... }`), RFC-010 / 010a — как
значение блока (`= {}` — блок со значением, значение — хвостовое выражение). Одна и та же
синтаксическая позиция, два набора семантики; в реализации это привело к тому, что
`callable_parts()` регистрировал блок как 0-аргументную функцию, а `generate_block_ir` в то же время
брал значение блока — два уровня понимания не согласованы.

### Решение: содержимое определяет тип

Тот же принцип должен пронизывать словари и блоки:

| Случай                        | Результат                | Обоснование                           |
| ----------------------------- | ------------------------ | ------------------------------------- |
| `value` — это `Lambda` (`=>`) | Функция                  | `=>` — явный конструктор функции      |
| Аннотация — `Fn`              | Функция                  | Объявлен функциональный тип           |
| Аннотация — не-`Fn` тип       | Значение блока           | Аннотация — это тип (`x: Int = {..}`) |
| **Нет аннотации**             | **Вывод по содержимому** | **Тип определяется содержимым**       |

```yaoxiang
x: Int = { y = 5; y }      // Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       // Функция: f() = 5 (аннотация Fn)
f = { 5 }                  // Значение: f = 5 (нет аннотации → вывод по содержимому)
f = {}                     // Значение: f = Void (пустой блок)
b = () => 5                // Функция: явная лямбда
d = { "a": 1 }             // Значение: Dict (содержимое самоописывает)
```

**Почему не использовать «нет аннотации — по умолчанию функция»**: тогда `f = { 5 }` — функция, а
`d = { "a": 1 }` — словарь, та же `{` в той же позиции без аннотации даёт сущности разных категорий.
Все три ранее рассматривавшихся довода несостоятельны:

1. Существующий код остаётся без изменений — стоимость миграции приемлема (211 файлов, 704 места),
   это не семантическое обоснование
2. Определение функций — частое, значение блока — редкое — частота не является правилом типизации
3. RFC-007 принят, его пересмотр дороже пересмотра настоящего RFC — пересмотр неправильного не
   становится правильным из-за «дороговизны»

**Тип определяется содержимым**, а не наличием аннотации. Аннотация по-прежнему объявляет тип
(`f: () -> Int`), но из-за «отсутствия аннотации» значение по умолчанию не навязывается.

### Положение `{}`

Грамматика `Dict` требует хотя бы один ключ, у `{}` нет содержимого, на которое можно опереться,
поэтому берётся нулевая форма блочной структуры → пустой блок, значение `Void`. Для пустого словаря
используется `dict.new()`. Подробности см. в спецификации
[§2.9.1](../../../reference/language-spec/syntax.md).

### Сопутствующие исправления реализации

1. **Аннотация не должна определять взятие значения**: три места в `generate_function_ir` и др.
   использовали `return_type != Void` как порог взятия хвостового выражения, из-за чего хвостовое
   выражение `f = { 5 }` без аннотации молча отбрасывалось и возвращался `Void`. Аннотация лишь
   определяет, нужна ли _проверка_, но не нужен ли _расчёт_.
2. **`callable_parts()` больше не безусловно поглощает блок**: разделение потоков унифицировано
   через `Expr::block_binding_is_function(аннотация, значение)`.
