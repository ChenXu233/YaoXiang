# RFC-010a: Вычисление хвостовых выражений и семантика return

> **Справка**:
>
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md) — модель `name: type = value`, вычисление `{}`
>   как зависимостно-управляемая единица
> - [RFC-007: Унификация синтаксиса определения функций](./007-function-syntax-unification.md) — правила возврата из блоков, ранний возврат
> - [RFC-038: Правила завершения операторов и переноса строк](038-statement-termination.md) — поведение переноса строк для операторов и выражений
> - [Спецификация языка §Типовая система](../../../../reference/language-spec/type-system.md) — принцип взрыва `Never`

## Краткое описание

Унификация семантики `return` и вычисления блоков, устранение противоречий между RFC-007 и RFC-010.

Предлагаются **три самосогласованных правила**: значение блока равно его хвостовому выражению (единственный выход); `return` — это **нелокальный выход** типа `Never` (выход из функции, не «возврат к блоку»); `if` без `else` даёт `Void`.

`return` и вычисление блоков **не разделяются на языковом уровне** — `{ return n }` как блок имеет значение `n` (тип `Never`), при этом
`return`
служит для выхода из функции. Оба действия сосуществуют благодаря **принципу взрыва** (`Never <: T`). «Ранний возврат» из RFC-007 и «блоки имеют значение» из RFC-010 являются следствиями этих трёх правил, а не противоречащими друг другу частными случаями.

Нет нового синтаксиса, нет новых ключевых слов.

## Мотивация

### Противоречие в формулировках

Пример с斐боначчи на playground выявил семантическое расхождение:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n          // Этот return «принадлежит if» или «принадлежит функции»?
  }
  return fib(n - 1) + fib(n - 2)
}
```

Два принятых RFC дают **противоположные** выводы:

| RFC                   | Формулировка                                                                                  | Выводимая семантика                                  |
| --------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------- |
| **RFC-007**（принято） | На примере `factorial`, заголовок: **«Ранний возврат: использование return»**:`if n <= 1 { return 1 }`  | `return` выходит из `if` и тела функции, **возвращается в функцию** |
| **RFC-010**（принято） | «`{}` — зависимостно-управляемая вычислительная единица… используйте `return` для явного возврата значения»; `spawn { return c }` возвращает результат задачи | `return` даёт значение **этому `{}`**               |

Согласно RFC-010, фигурные скобки `if n <= 1 { return 1 }` — это вычислительная единица, `return 1` даёт ей значение 1, тогда значение `if` отбрасывается и следующая строка обязательно выполняется — **fib уходит в бесконечную рекурсию**. Согласно RFC-007 — всё корректно.

### Корневая причина: слово `return` выполняет две роли

- **RFC-007 использует его для «выхода из функции»** — концепция потока управления
- **RFC-010 использует его для «значение этого блока равно ему»** — концепция вычисления

Использование ключевого слова потока управления для выражения значения — это категориальная ошибка (category error). Одно слово несёт две нагрузки, и какую бы настройку мы ни делали, одна сторона будет ущемлена.

### Распространение ошибок в нижестоящей документации

В `docs/src/reference/language-spec/syntax.md` расширительно истолковали «`{}` блок» из RFC-010 на **все фигурные скобки**:

- §2.9: «`return` в `{}` **всегда возвращает содержимое в вышестоящую область видимости**» (называется «унифицированная семантика: все `{}` блоки»)
- §3.3: «`return` используется для **возврата значения из блока кода**»

Однако RFC-010 определяет **три вида блоков со значением** (`= {}` / `spawn {}` / `unsafe {}`), **нигде не затрагивая фигурные скобки `if` / `while` / `for` / `match`**.

### Текущее состояние реализации

| Поведение                                   | Текущее состояние                              |
| -------------------------------------- | --------------------------------- |
| `if n == 0 { return 7 } … return 8`    | Выход из функции（`h(0) = 7`）            |
| `f = { n + 1 }`                        | Хвостовое выражение доступно（возвращает `5`）          |
| `x = { y = 5; y }`（голый блок с хвостовым выражением）     | `E3006` переменная не разрешена（см. #343）     |
| `f: () -> Int = { if c {5} else {6} }` | Возвращает `void`, хвостовое выражение отброшено（#344） |
| `f: () -> Int = { "s" }`               | Тихая компиляция（см. #345）           |
| `x = if c { 19 }`（без `else`）         | `19`（должно быть `Void`, см. #346）             |
| `v = unsafe { 42 }`                    | `void`（см. #347）                 |
| `y = if c { 111 } else { 222 }`        | Работает（`if` как выражение）          |

когда-то утверждал, что «хвостовое выражение больше не возвращает неявно», но не покрывал этот случай, поэтому тест не был красным. Этот файл заменён на

## Предложение

### Три правила

```
① Значение блока = хвостовое выражение（единственный выход）
   Значение оператора присваивания — Void; пустой блок {} имеет значение Void
② return : (T) -> Never
   Нелокальный выход: выход за ближайшую границу функции
③ if без else → Void
```

**Этих трёх правил достаточно для вывода «раннего возврата», не нужны дополнительные правила о том, что `return` относится к функции.**

### Правило ①: значение блока

**Последний оператор/выражение в блоке** — это значение блока (хвостовое выражение). Это **не** «без хвостового выражения → Void» — непустой блок всегда имеет хвостовое выражение (последний оператор сам по себе им является), а пустой блок
`{}` имеет значение `Void`.

```yaoxiang
// Хвостовое выражение определяет значение блока
a = {
    x = compute()        // Оператор присваивания → Void
    x * 2                // Хвостовое выражение → значение блока
}

// Присваивание как хвостовое выражение → значение блока — Void
b = {
    x = compute()
    log(x)               // Оператор присваивания → Void
}

// Хотите Void — напишите явно
c = {
    log(x)
    Void                 // Явный Void
}
```

**Проектный критерий (разделение механизма и защиты)**:

- **Языковое правило даёт только механизм**: последний оператор — значение блока, правило едино, однозначно
- **Защиту обеспечивает проверка типов**: функция объявлена `-> Int`, а тип хвостового выражения не совпадает → ошибка компиляции
- **Язык не защищает от «ошибок намерения»**: если тип хвостового выражения случайно совпадает с типом возврата, но семантика неверна — это упущение автора, язык не может судить. **Не языковыми правилами защищаемся от ошибок намерения.**
- **Не хотите возвращать — напишите явно `Void`**

Это заменяет формулировку RFC-010 «`= { ... }` должен использовать `return`, иначе возвращает `Void`», а также его обоснование «нужен явный `return` для устранения неоднозначности, является ли последнее выражение возвращаемым значением».

### Правило ②: `return` — нелокальный выход

Тип `return` — `Never` (нуль конструкторов, не может содержать значение). Его семантика:

- **Выходит за ближайшую границу функции**, передаёт значение вызывающей стороне
- **Пронзает любые блоки** — (если есть) `if` / `while` / `for` / `match` / голые блоки / `spawn` / `unsafe`

`return` не «возвращает к блоку». `{ return n }` как блок имеет значение `n` (правило хвостового выражения), **тип `Never`**; при этом
`return` служит для выхода из функции. **Оба действия верны одновременно.**

### Правило ③: `if` без `else`

```yaoxiang
x = if c { 19 }        // Без else
```

Когда условие ложно, нет ветви для вычисления, берём `Void`. Поэтому тип значения этого `if` — `Void` (или его нельзя использовать в позиции, требующей не-`Void`).

Когда нужно значение, явно дополните обе ветви:

```yaoxiang
x = if c { 19 } else { 20 }
```

### `Never` — техническая основа сосуществования

`Never <: T` верно для любого типа `T` (принцип взрыва, см. спецификацию языка §Типовая система). Поэтому:

```yaoxiang
fib: (n: Int) -> Int = {
  if n <= 1 {
    return n              // Хвостовое выражение : Never
  }                       // → Значение этого if : Never
  fib(nn - 1) + fib(n - 2) // → Значение блока : Int
}
```

- Значение тела ветви `{ return n }` — `Never`
- Единственная ветвь `if` имеет тип `Never` ⇒ значение `if` — `Never`
- Оператор типа `Never` означает **последовательность здесь прерывается** — следующий за ним оператор не является «следующим по порядку выполнения»
- А `Never` сводится к любому типу (принцип взрыва), поэтому весь блок удовлетворяет `-> Int`

**«Ранний возврат» получается естественно**: `Never` прерывает последовательность + принцип взрыва позволяет свести к типу.

## Детальное проектирование

### Формализация блоков и хвостовых выражений

```
Block        ::= '{' Stmt* '}'                     // Пустой блок → Void
               | '{' Stmt* Expr '}'                // Значение = Expr
Expr         ::= ...
               | Return                            // Тип Never
Stmt         ::= Assignment | ExprStmt | ...

Значение(Block)：
  Пустой блок                  → Void
  { ...; e }                  → Тип(e)
  { ...; s }（s — оператор）  → Void          // Значение присваивания — Void
```

### Типовые правила `return`

```
return e : Never        где e : T

// Поскольку Never <: T' верно для любого T', return может出现在任意ному типу возврата的位置
```

**Не нужно дополнительных правил для ограничения допустимости `return`** — принцип взрыва это покрывает. Это делает вопрос «может ли `return` появиться в функции, возвращающей `X`» бессмысленным.

### Объединение нескольких ветвей

```
join(A, B)：
  Если A : Never  → B
  Если B : Never  → A
  Иначе          → требуется совместимость A, B (один тип или общий супремум)
```

Ветви `if` / `match` объединяются по `join`. Ветви с `return` из-за типа `Never` не участвуют в объединении.

### Совместимость с RFC-007

Примеры из RFC-007 **полностью соответствуют данному RFC**, правки не требуются:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }          // Ветвь Never, игнорируется join
    return n * factorial(n - 1)     // Выход из функции
}
```

«Ранний возврат» — не частный случай, а **следствие правил ①, ② и принципа взрыва**.

### Различия с RFC-010 и требования к правке

Определения RFC-010 обновлены согласно данному RFC, различия:

| Оригинальный пункт RFC-010                                   | Текущее определение                                        |
| ------------------------------------------------ | ----------------------------------------------- |
| «`= { ... }` должен использовать `return`, иначе возвращает `Void`» | Значение блока = хвостовое выражение; пустой блок → `Void`                |
| Обоснование «нужен явный `return` для устранения неоднозначности хвостового выражения»     | Неверно — хвостовое выражение не создаёт неоднозначности, `return` его не нарушает   |
| Три примера с `return c` / `return SqliteDb`         | Запись через хвостовое выражение (единый выход значения для `spawn` / `unsafe`) |

**Ядро дизайна RFC-010 (`{}` как зависимостно-управляемая вычислительная единица) не меняется**, только выход значения переключается с `return` на хвостовое выражение.

### Унификация перспективы (принципы проектирования)

Фигурные скобки `if` / `while`
**являются одновременно императивными управляющими конструкциями и декларативными вычислительными единицами** — это **разница перспективы, а не две разные языковые конструкции**. Поэтому:

- **Не разделяем на языковом уровне** «поток управления» и «вычислительная единица»
- Все блоки используют единый набор правил вычисления (правило ①)
- `return` — единственный исключительный механизм, и его исключительность проистекает из типо-теоретических свойств `Never`, а не из синтаксических особенностей

Это позволяет декларативному и Python-подобному стилям естественно сосуществовать:

```yaoxiang
a = if input > 10 { 19 } else { 20 }
b = { x = f(); x * 2 }
c = spawn { fetch("a") }
```

## Компромиссы

### Достоинства

- **Устранение конфликта RFC**: RFC-007 и RFC-010 переходят от противоречия к отношению следствия, не нужно жертвовать ни одной стороной
- **Минимальное количество правил**: три правила + одно типо-теоретическое свойство (принцип взрыва), без исключений
- **Единственное значение `return`**: выход из функции. Больше не нужно решать, принадлежит ли значение «блоку или функции»
- **Единство перспективы**: императивный и декларативный стили сосуществуют, нет разделения на языковом уровне
- **Согласованность со зрелыми языками**: в Rust также «хвостовое выражение + `return : !`» сосуществуют
- **Нулевой новый синтаксис**: без ключевых слов, без изменений в парсере

### Недостатки

- **«Последнее выражение — значение» создаёт риск «случайного возврата»**: забыли удалить последнюю строку — значение тихо меняется
  - Смягчение: проверка типов перехватывает несоответствие типов; язык не обещает защиту от ошибок намерения (см. проектный критерий)
- **Нужна синхронизация нижестоящей документации**: примеры в принятых документах нужно переписать
- **Нужно уточнить взаимодействие с завершением операторов**: является ли последнее выражение при завершении переносом строки значением блока (см. открытый вопрос)

## Альтернативные решения

### Вариант A: `return` сохраняет две роли, распределение по типу блока

В теле функции `= {}` `return` принадлежит функции; в `spawn {}` / `unsafe {}` принадлежит блоку; в `if {}` / голом блоке — ?

**Причина отклонения**: распределение для `if` неразрешимо — это и есть исходный конфликт. При этом пользователям нужно запоминать «какие блоки кому принадлежат», нет принципиального обоснования (почему `if` принадлежит функции, а голый блок — себе).

### Вариант B: Строгий возврат из блока (`return` всегда принадлежит текущему блоку)

**Причина отклонения**: **функциональная недостаточность**. `return` никогда не сможет досрочно выйти из вложенного блока, guard clause (`if err { return }`) полностью невозможен, придётся писать функцию как вложенные друг в друга выражения.

### Вариант C: Значение блока через новое ключевое слово (`give x` / `yield x`)

**Причина отклонения**: нарушает принцип **нулевых синтаксических изменений** RFC-036 (нужно добавлять ключевое слово), плюс пользователям придётся учить две концепции (`return` для выхода + `give` для значения). Хвостовое выражение — ноль новых концепций.

### Вариант D: Сохранить RFC-010 как есть (обязательный явный `return`)

**Причина отклонения**: конфликт с RFC-007 неразрешим (см. мотивацию). К тому же реализация уже пошла по пути хвостового выражения.

## Правки в нижестоящей документации

- [x] `name = { ... }` — когда это функция, когда привязка значения блока — см. Приложение D (тип определяется содержимым)

## Приложение D: Разрешение неоднозначности функция / значение блока

### Проблема

`name = { ... }` ранее определялся двумя принятыми RFC по-разному: RFC-007 (синтаксис функций) рассматривал его как функцию
(«пустой параметр как кратчайшая форма» `name = { return ... }`), RFC-010 / 010a — как значение блока (`= {}` — блок со значением,
значение = хвостовое выражение). Одна синтаксическая позиция, два набора семантики; в реализации `callable_parts()` регистрировал блок как функцию с 0 параметров, а `generate_block_ir` извлекал значение как блок — два уровня понимания не согласованы.

### Решение: тип определяется содержимым

Единый принцип для справочников и блоков:

| Ситуация                        | Результат       | Основание                          |
| --------------------------- | ---------- | ----------------------------- |
| `value` — это `Lambda`（`=>`） | Функция       | `=>` — явный конструктор функции         |
| Аннотация — `Fn`                 | Функция       | Объявлен тип функции                |
| Аннотация — не `Fn` тип          | Значение блока       | Аннотация — это тип（`x: Int = {..}`） |
| **Без аннотации**                  | **Выводится по содержимому** | **Тип определяется содержимым**        |

```yaoxiang
x: Int = { y = 5; y }      // Значение блока: x = 5 (аннотация не Fn)
f: () -> Int = { 5 }       // Функция: f() = 5 (аннотация Fn)
f = { 5 }                  // Значение: f = 5 (без аннотации → вывод по содержимому)
f = {}                     // Значение: f = Void (пустой блок)
b = () => 5                // Функция: явный лямбда
d = { "a": 1 }             // Значение: Dict (содержимое самодостаточно)
```

**Почему не «без аннотации по умолчанию функция»**: тогда `f = { 5 }` — функция, а `d = { "a": 1 }` — словарь — в одинаковой синтаксической позиции без аннотации одно и то же `{` даёт разные категории. Три рассматривавшихся обоснования все неверны:

1. Нулевые изменения в существующем коде — затраты на миграцию посильны (211 файлов, 704 вхождения), а не семантическое основание
2. Определения функций часты, значения блоков редки — частота не определяет типовое правило
3. RFC-007 принят, менять его дороже — неверное не становится верным от дороговизны

**Тип определяется содержимым**, а не наличием аннотации. Аннотация по-прежнему объявляет тип (`f: () -> Int`),
но не налагает значение по умолчанию из-за «отсутствия аннотации».

### Попадание `{}`

Грамматика `Dict` требует минимум один ключ, `{}` без содержимого не может опереться на него, поэтому берётся нулевая форма блочной структуры → пустой блок, значение `Void`.
Пустой словарь создаётся через `dict.new()`. Подробнее см. spec [§2.9.1](../../../reference/language-spec/syntax.md).

### Сопутствующие исправления в реализации

1. **Аннотация не должна определять способ извлечения значения**: в трёх местах, включая `generate_function_ir`, использовалось `return_type != Void` как порог для извлечения хвостового выражения; это приводило к тому, что `f = { 5 }` без аннотации тихо отбрасывало хвостовое выражение и возвращало `Void`. Аннотация определяет только необходимость *проверки*, а не необходимость *вычисления*.
2. **`callable_parts()` больше не поглощает блоки безусловно**: маршрутизация передана единой функции `Expr::block_binding_is_function(аннотация, значение)`.
