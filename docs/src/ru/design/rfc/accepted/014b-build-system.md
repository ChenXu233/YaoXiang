# RFC-014b: Система сборки и распространение бинарных файлов

> Настоящий RFC является под-RFC документа
> [RFC-014: Дизайн системы управления пакетами](../accepted/014-package-manager.md).

## Решение по ревизии от 15.09.2026

Следующие решения были приняты владельцем 15.09.2026:

1. **Шлюз доверия `build.yx` (реализация открытого вопроса о «песочнице»)**: выполнение
   произвольного кода в стратегии `custom` — крупнейшая поверхность атаки на цепочку поставок в
   пакетном менеджере — `yaoxiang add` вредоносного пакета равносильно передаче всех прав `std.os`.
   Минимальная обязательная граница:
   - Перед первым выполнением `build.yx` пакета требуется интерактивное подтверждение;
   - `yaoxiang add --trust <pkg>` / `install --trust` сохраняет запись о доверии в
     `~/.yaoxiang/config.toml` (`[trust] build-scripts = ["name@version"]`);
   - В неинтерактивной среде (CI) сборка `custom` по умолчанию отклоняется, если явно не указан
     `--trust`;
   - Полный механизм песочницы продолжает исследоваться как открытый вопрос, но шлюз доверия
     является обязательным минимумом.
2. **Переупорядочение фаз**:
   `5a → 5b → 5c (cargo) → 5d ([binaries]) → 5f (bindgen, зависит от RFC-026b) → 5e (custom последним, со шлюзом доверия)`.
   Декларативный путь (cargo) идёт первым, выполнение произвольного кода — последним.
3. **Унификация распространения бинарных файлов**: `[binaries]` — единственный механизм
   распространения бинарных файлов (соответствует решению 3 из RFC-014a — `.yxpkg` содержит только
   исходный код).
4. **Кросс-компиляция**: на начальном этапе не поддерживается, мультиплатформенные артефакты
   производятся CI на нескольких хостах (в соответствии с подходом cargo-dist из RFC-037).
5. **Размер артефактов сборки**: верхний предел не устанавливается, управляется каналом
   распространения.
6. **Несовместимая версия Cargo**: предварительная проверка через `[build.requirements]` с
   сообщением об ошибке и инструкцией по установке (определено в основном тексте, без дополнительных
   механизмов).

## Резюме

Определяет механизмы сборки системы управления пакетами YaoXiang: декларативная конфигурация сборки,
стратегии сборки (cargo/cmake/custom/none), распространение предкомпилированных бинарных файлов,
проверка системных зависимостей.

## Мотивация

Некоторые пакеты — это чистый код `.yx`, не требующий сборки. Другие требуют компиляции FFI-связей
(вызов Cargo, CMake и т.д.). Необходим единый механизм, позволяющий авторам пакетов декларировать
требования к сборке, а пакетному менеджеру — автоматически их обрабатывать.

### Текущие проблемы

- Отсутствует декларация конфигурации сборки (в `yaoxiang.toml` нет секции `[build]`)
- Нет механизма распространения предкомпилированных бинарных файлов
- Сборка FFI-пакетов полностью зависит от ручных действий пользователя
- Нет проверки системных зависимостей

## Предложение

### Основной дизайн: декларативная сборка + приоритет предкомпиляции

Автор пакета декларирует требования к сборке в `yaoxiang.toml`, пакетный менеджер автоматически
принимает решения на основе декларации.

### Стратегии сборки

```rust
enum BuildStrategy {
    None,          // Чистый .yx пакет, сборка не требуется
    Cargo,         // Вызов cargo build, чтение конфигурации [build.cargo]
    Cmake,         // Вызов cmake
    Custom,        // Выполнение скрипта build.yx
}
```

Примечание: вариант `Precompiled` удалён. Наличие секции `[binaries]` автоматически активирует
поведение приоритета предкомпиляции и не требует явного объявления strategy.

### Декларация сборки в yaoxiang.toml

```toml
[package]
name = "native-foo"
version = "1.0.0"

[build]
strategy = "cargo"              # Стратегия сборки
headers = ["include/sqlite3.h"] # Опционально: C-заголовки, обрабатываемые yx-bindgen автоматически

[build.cargo]
features = ["ffi"]             # cargo build --features ffi
target = "release"             # cargo build --release

[build.requirements]
cargo = ">= 1.70"              # Инструменты, необходимые при сборке
cmake = ">= 3.20"

[build.platforms]              # Переопределения для конкретных платформ
"x86_64-unknown-linux-gnu" = { cargo-features = ["linux-ffi"] }
"x86_64-pc-windows-msvc" = { cargo-features = ["win-ffi"] }
"aarch64-apple-darwin" = { cargo-features = ["mac-ffi"] }
```

### Дерево принятия решений при установке

```
yaoxiang install foo
    │
    ├─ 1. Есть запись для текущей платформы в [binaries]?
    │     → Да: загрузить, проверить SHA-256, установить напрямую (пропуск сборки)
    │     → Нет: продолжить
    │
    ├─ 2. Загрузить пакет с исходным кодом
    │
    ├─ 3. [build].headers содержит значения?
    │     → Да: автоматически запустить yx-bindgen для генерации файлов связей
    │
    ├─ 4. Прочитать [build].strategy
    │     → "none": установить напрямую
    │     → "cargo": прочитать конфигурацию [build.cargo], собрать команду cargo build
    │     → "cmake": вызвать cmake
    │     → "custom": выполнить скрипт build.yx
    │
    └─ 5. Установить в vendor/
```

**Приоритет предкомпиляции, исходный код как запасной вариант.** Наличие `[binaries]` автоматически
запускает проверку предкомпиляции и не требует явного указания strategy.

### Подробности стратегии cargo

При `strategy = "cargo"` читается конфигурация `[build.cargo]` для составления команды:

```toml
[build]
strategy = "cargo"

[build.cargo]
features = ["ffi"]             # → cargo build --features ffi
target = "release"             # → cargo build --release

[build.platforms]              # Переопределение для платформы
"x86_64-unknown-linux-gnu" = { cargo-features = ["linux-ffi"] }
"x86_64-pc-windows-msvc" = { cargo-features = ["win-ffi"] }
"aarch64-apple-darwin" = { cargo-features = ["mac-ffi"] }
```

Фактически выполняемая команда:

```bash
# Базовый вариант
cargo build --release --features ffi

# При наличии переопределения для платформы (на примере Linux)
cargo build --release --features ffi,linux-ffi
```

### Декларация предкомпилированных бинарных файлов

```toml
# yaoxiang.toml
[binaries]
"x86_64-unknown-linux-gnu" = { url = "releases/download/v1.0.0/foo-linux-x86_64.tar.gz", sha256 = "abc123" }
"x86_64-pc-windows-msvc" = { url = "https://example.com/foo-win-x86_64.tar.gz", sha256 = "def456" }
"aarch64-apple-darwin" = { url = "releases/download/v1.0.0/foo-macos-aarch64.tar.gz", sha256 = "ghi789" }
```

**Формат URL:** поддерживаются абсолютные URL и относительные пути. Относительные пути отсчитываются
относительно адреса репозитория пакета (URL GitHub-репозитория или корневой URL реестра).

**Условия пропуска сборки:**

1. В `[binaries]` есть запись для текущей платформы
2. Проверка SHA-256 пройдена
3. Загрузка успешна

Если выполнены все три условия → сборка пропускается. Иначе → откат на сборку из исходного кода.

### Скрипт сборки build.yx

При `strategy = "custom"` выполняется `build.yx`.

**Модель выполнения (минимальная спецификация):**

- Скрипт — это обычный код `.yx` с полным доступом к `std`
- **Шлюз доверия (решение от 15.09.2026, обязательно)**: перед первым выполнением требуется
  интерактивное подтверждение, в неинтерактивной среде по умолчанию отклоняется (см. решение 1 выше)
- Рабочий каталог: корень пакета (`vendor/<pkg>-<ver>/`)
- Успех: код выхода 0
- Неудача: ненулевой код выхода, установка прерывается
- Пакетный менеджер не ограничивает поведение скрипта, только проверяет код выхода

```yx
# build.yx — скрипт сборки пакета
use std.os
use std.io

fn main() {
    let platform = os.platform()
    let arch = os.arch()

    if os.file_exists("Cargo.toml") {
        io.println("Building native extension via Cargo...")
        let result = os.exec("cargo build --release")
        if result.exit_code != 0 {
            io.println("Build failed!")
            os.exit(1)
        }
    }

    io.println("Build complete!")
}
```

### Проверка системных зависимостей

Перед установкой автоматически проверяются все `[build.requirements]`; при неудовлетворении выдаётся
ошибка:

```
Error: Build requirement not satisfied
  cargo >= 1.70 required, but cargo is not installed
  Install: https://rustup.rs
```

### Интеграция с yx-bindgen (поле headers)

`[build].headers` декларирует C-заголовки, которые должны быть обработаны yx-bindgen. Система сборки
автоматически запускает yx-bindgen для генерации файлов связей `.yx`.

```toml
[build]
strategy = "cargo"
headers = ["include/sqlite3.h", "include/json.h"]
```

Процесс сборки:

```
1. Есть предкомпилированный [binaries]? → пропустить всю сборку
2. [build].headers содержит значения? → yx-bindgen автоматически генерирует связи
3. Выполнить [build].strategy (cargo/cmake/custom)
4. Установить
```

yx-bindgen разбирает сигнатуры функций и определения типов из C-заголовков (`.h`) и автоматически
генерирует декларации связей `.yx`. Пользователю не нужно запускать его вручную — система сборки
автоматически обрабатывает это при обнаружении конфигурации `headers`.

**Связь с RFC-026:** RFC-026 определяет языковой уровень семантики `yx-bindgen` (синтаксис
`native("symbol")`, unsafe-типы). RFC-014b определяет способ его интеграции в процесс сборки
(конфигурация `headers`). Они дополняют друг друга.

### Интеграция с Cargo Workspace

Если пакет содержит FFI-код, можно одновременно определить Cargo workspace:

```
my-package/
├── yaoxiang.toml          # Конфигурация пакета YaoXiang
├── Cargo.toml             # Cargo workspace (FFI-часть)
├── src/
│   └── lib.yx             # Код YaoXiang
└── native/
    ├── Cargo.toml          # Rust FFI-код
    └── src/
        └── lib.rs
```

`yaoxiang build` автоматически обнаруживает и вызывает `cargo build` для компиляции native-части.

## Детальный дизайн

### Идентификаторы платформ

Используется формат Rust target triple (`arch-vendor-os-env`):

| Платформа              | Идентификатор               |
| ---------------------- | --------------------------- |
| Linux x86_64 (glibc)   | `x86_64-unknown-linux-gnu`  |
| Linux x86_64 (musl)    | `x86_64-unknown-linux-musl` |
| Linux ARM64            | `aarch64-unknown-linux-gnu` |
| Windows x86_64 (MSVC)  | `x86_64-pc-windows-msvc`    |
| Windows x86_64 (MinGW) | `x86_64-pc-windows-gnu`     |
| macOS ARM64            | `aarch64-apple-darwin`      |
| macOS x86_64           | `x86_64-apple-darwin`       |

Использование Rust target triple вместо упрощённого формата обусловлено:

1. Различением разных ABI на одной ОС (gnu vs musl, msvc vs gnu)
2. Совместимостью с экосистемой Rust/Cargo, снижением ошибок маппинга
3. Отсутствием необходимости менять формат при будущем расширении

### Структура каталога артефактов сборки

```
build/
└── native/
    ├── x86_64-unknown-linux-gnu/
    │   └── libfoo.so
    ├── x86_64-pc-windows-msvc/
    │   └── foo.dll
    └── aarch64-apple-darwin/
        └── libfoo.dylib
```

### Полный жизненный цикл предкомпилированного пакета

```
Разработчик:
  1. Пишет .yx-код + FFI-связи
  2. Декларирует [build] + [binaries] в yaoxiang.toml
  3. yaoxiang publish
     → автоматическая сборка мультиплатформенных бинарников в CI
     → загрузка исходного кода + предкомпилированных артефактов

Пользователь:
  yaoxiang add native-foo
    → обнаружены предкомпилированные артефакты → прямая загрузка (секунды)
    → предкомпилированные артефакты отсутствуют → загрузка исходного кода + сборка (минуты)
```

## Компромиссы

### Преимущества

- Декларативная конфигурация, пользователю не нужно разбираться в деталях сборки
- Приоритет предкомпиляции, очень быстрая установка
- Поддержка нескольких платформ с автоматическим выбором
- Бесшовная интеграция с экосистемой Cargo

### Недостатки

- Для предкомпилированных артефактов требуется поддержка CI
- Мультиплатформенная сборка увеличивает сложность релиза
- Для скриптов build.yx требуется механизм безопасности песочницы

## Альтернативы

| Вариант                                | Почему не выбран                                              |
| -------------------------------------- | ------------------------------------------------------------- |
| Распространение только исходного кода  | Пользователю нужен инструментарий сборки, высокий порог входа |
| Бинарный формат наподобие Python wheel | Излишне сложно, не нужно на раннем этапе экосистемы YaoXiang  |
| Отсутствие поддержки FFI-сборки        | Ограничивает расширяемость языка                              |

## Стратегия реализации

### Разделение на фазы

| Фаза     | Содержание                                                                                                                      | Статус                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Phase 5a | Парсинг конфигурации `[build]` + перечисление `BuildStrategy` (включая декларацию `[binaries]`, платформенные тройки)           | ✅ Завершено                                                  |
| Phase 5b | Проверка системных зависимостей (зондирование `<tool> --version` + дополнение операндов компаратора + инструкции по установке)  | ✅ Завершено                                                  |
| Phase 5c | Интеграция сборки Cargo (чтение `[build.cargo]` для составления команды + слияние переопределений платформы + изоляция scratch) | ✅ Завершено                                                  |
| Phase 5d | Загрузка предкомпилированных бинарников + проверка (целостность пакета SHA-256 + безопасная распаковка + семантика отката)      | ✅ Завершено                                                  |
| Phase 5f | Интеграция yx-bindgen (конвейер конфигурации поля `headers`; RFC-026b ещё в черновике, явная ошибка во время выполнения)        | ✅ Конвейер конфигурации завершён (генератор — вместе с 026b) |
| Phase 5e | Выполнение скрипта build.yx (**последняя реализация**, со шлюзом доверия)                                                       | ✅ Завершено                                                  |

Порядок выполнения (решение 2 от 15.09.2026): `5a → 5b → 5c → 5d → 5f → 5e`. Декларативная сборка
идёт первой, выполнение произвольного кода — последним.

**Замечания по реализации (30.09.2026, коммит см. feat/rfc014)**:

- **Двухслойное разделение артефактов**: cargo scratch (target/) через `CARGO_TARGET_DIR`
  направляется в проектный каталог `.yaoxiang/build/cargo/<pkg>/` — не попадает в каталог пакета
  vendor, иначе проверки целостности каталога раздуваются инкрементальными артефактами сборки;
  потребляемые FFI библиотеки (.so/.dll/.dylib/.a) копируются в каталог пакета vendor
  `build/native/<triple>/`. Семантика проверки целостности vendor уточняется как **целостность
  дерева исходного кода** (производные артефакты `build/` не входят в контрольные суммы).
- **Семантика отката `[binaries]`**: для текущей платформы есть запись, но «sha256 не объявлен /
  загрузка не удалась / контрольная сумма не совпала» — любое из этих условий → сообщение в stderr +
  откат на сборку из исходного кода (RFC «иначе fallback»), очистка полуготовых артефактов перед
  откатом. После прохождения проверки всего пакета выполняется безопасная распаковка (защита от
  выхода за пределы пути + ограничение общего объёма распаковки 512 МиБ, верхний предел размера
  артефактов не устанавливается — решение 5).
- **Реализация шлюза доверия (решение 1)**: записи о доверии хранятся в системе пользовательской
  конфигурации (`~/.config/yaoxiang/config.toml`, секция `[trust] build-scripts`; черновой вариант
  RFC с `~/.yaoxiang/config.toml` никогда не существовал, объединено аналогично `[cache] dir`). Три
  пути разрешения: уже записан / текущий `--trust` (**разрешение означает сохранение**, реализуя
  «add/install --trust сохраняет запись о доверии») / интерактивное подтверждение (подтверждение
  означает сохранение). В неинтерактивной среде (stdin не является терминалом) по умолчанию
  отклоняется, пропускает только `--trust`.
- **Модель выполнения build.yx**: обычный скрипт .yx, **операторы верхнего уровня и есть логика
  сборки** (семантика Script/eval; приведённый выше пример с `fn main()` — псевдокод чернового
  этапа), выполнение внутри процесса, рабочий каталог временно переключается на корень пакета
  (глобальная блокировка сериализует окно переключения). Текущий std не имеет API exec/exit — скрипт
  может содержать генеративную/файловую логику, вызовы внешних инструментов в стиле `os.exec`
  появятся по мере развития std.
- **Стратегия cmake**: перечисление и парсинг конфигурации готовы, выполнение ещё не реализовано
  (явная ошибка) — в таблицах фаз RFC отдельная фаза для cmake не указана, планирование по мере
  появления реальных потребностей.
- **Предрелизное тестирование publish** (проверка 3 из 014a) подключено в данной фазе: по умолчанию
  запускаются тесты, обнаруженные в `[tool.test]` (механизм RFC-036), при неудаче публикация
  прерывается, `--no-test` пропускает.

### Зависимости

- Зависит от RFC-014a (протокол реестра для загрузки предкомпилированных артефактов)
- Зависит от crate `sha2` (проверка целостности)
