# RFC-010: Унифицированный синтаксис типов — модель name: type = value

## Резюме

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет строчного ключевого слова `type` (но есть `Type` как
ключевое слово метайпа)**.

> **Ключевое решение**: `Type` сам по себе является типовым дженериком. `(T: Type) -> Type` означает
> «тип, принимающий параметр типа T».

| Понятие          | Написание кода                                                               |
| ---------------- | ---------------------------------------------------------------------------- |
| Переменная       | `x: Int = 42`                                                                |
| Функция          | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи       | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс        | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Дженерик-тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Дженерик-тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод            | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Дженерик-функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово метайпа в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` обозначает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` вроде `p.draw(screen)` работал, требуется явная привязка: `Point.draw = draw[0]`.
> Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он используется для
> аннотирования уровня типов; компилятор автоматически обрабатывает различение Type0, Type1,
> Type2..., что прозрачно для пользователя.

```yaoxiang
// Основной синтаксис: унификация + различение

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Тип записи
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути — тип записи, все поля которого являются функциями)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (с использованием синтаксиса Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    "Point(${self.x}, ${self.y})"
}

// Дженерик-тип ((T: Type) -> Type = дженерик-тип, принимающий параметр типа)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурная подтипизация: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Существующая система типов содержит несколько разрозненных концепций:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (другой синтаксис)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельная унификация**: одно синтаксическое правило покрывает все случаи
2. **Кратсота и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих синтаксических элементов
4. **Теоретическая элегантность**: сам тип является значением типа Type
5. **Дженерик-дружественность**: бесшовная интеграция с системой дженериков (RFC-011)

### Интеграция с системой дженериков

Унифицированная синтаксическая модель RFC-010 **органически совместима** с дизайном системы
дженериков RFC-011, параметры дженериков могут бесшовно встраиваться в унифицированную модель:

```yaoxiang
// Базовые дженерики (RFC-011 Phase 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Дженерик-функция (синтаксис RFC-023: позиция Type в сигнатуре может быть опущена, выводится автоматически при вызове)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничения типа (RFC-011 Phase 2)
clone: (value: T) -> T = value.clone()  // ограничение T: Clone переносится типом параметра

// Const-дженерики (RFC-011 Phase 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовые дженерики) — **сильная зависимость** для RFC-010
- Без базовых дженериков примеры с дженериками в RFC-010 не скомпилируются
- Рекомендация: реализовывать RFC-011 Phase 1 и RFC-010 одновременно

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила устранения неоднозначности синтаксиса:**

| Написание           | Значение               | Правило                                                     |
| ------------------- | ---------------------- | ----------------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | `: Type` явно объявлен → принудительно как тип              |
| **`f = ...`**       | Функция или переменная | Нет `: Type` → HM самостоятельно выводит функцию/переменную |

**Почему именно так?**

Синтаксис `{ ... }` сам по себе неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM самостоятельно интерпретирует `{ ... }` как блок кода, выводит как тип
  функции

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит как () -> Void
main: () -> Void = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может интерпретировать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит как функцию, а не как тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # Нет : Type, HM выводит как функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # Должен возвращать: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # Должен возвращать: Type
│
├── Дженерик-тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # Должен возвращать: Type
│
├── Дженерик-тип (множественные параметры)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # Должен возвращать: Type
│
├── Функция пространства имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # Только после явной привязки доступен синтаксис вызова через точку
│
└── Дженерик-функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # Не возвращает Type, HM выводит как функцию
```

### Уровни метайпа (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Level    | Описание                               |
| -------- | -------------------------------------- |
| `Type0`  | Обычные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)   |
| `Type2+` | Конструкторы высшего порядка           |

**Пользователь никогда не видит эти числа**, только `: Type`.

### Изоморфизм Карри-Говарда: типы как утверждения, программы как доказательства

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он является прямым
отображением изоморфизма Карри-Говарда (Curry-Howard correspondence). Этот изоморфизм раскрывает
глубокий факт: **система типов и логическая система — это две стороны одного и того же**.

| Логика (утверждение)          | Система типов (YaoXiang)            | Пример                               |
| ----------------------------- | ----------------------------------- | ------------------------------------ |
| Утверждение P                 | Тип T                               | `Int`, `Bool`                        |
| Доказательство P              | Значение типа T                     | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | Тип функции `(P) -> Q`              | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | Тип записи `{ p: P, q: Q }`         | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Дженерик-функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | Enum / tagged union                 | `Maybe: (T: Type) -> Type = { ... }` |

**Что означает `name: type = value` с точки зрения Карри-Говарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int с именем x и значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: дано доказательство a и b типа Int, можно построить доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — это утверждение, доказательство которого требует одновременного предоставления доказательства Float x и доказательства Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая согласованность = типобезопасность**: если система типов позволяет создать значение
   типа `T` без какого-либо легального представления в runtime, это подобно тому, как если бы логика
   позволяла доказать ложное утверждение — система рушится. Карри-Говард говорит нам:
   **типобезопасный язык по своей природе является согласованной логической системой**.

2. **Уровни вселенной — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (т.е. «тип типа также является типом»), возникнет парадокс Рассела (в теории типов
   он проявляется как парадокс Жирара). Иерархия YaoXiang `Type₀ : Type₁ : Type₂ : ...` гарантирует,
   что каждый тип принадлежит только определённому уровню, формируя бесконечно восходящую цепочку,
   что фундаментально предотвращает парадоксы. Это означает, что система типов YaoXiang в смысле
   Карри-Говарда является **логически согласованной**.

3. **Теоретическая основа унифицированного синтаксиса**: `name: type = value` способен охватить
   переменные, функции, типы, интерфейсы и дженерики одним синтаксисом именно потому, что все они с
   точки зрения Карри-Говарда — одно и то же: **предоставление доказательств для утверждений**.
   Переменные — свидетельства утверждений, функции — свидетельства импликаций, записи —
   свидетельства конъюнкций, дженерики — свидетельства кванторов всеобщности. Унифицированный
   синтаксис — не случайность дизайна, а естественное следствие изоморфизма Карри-Говарда.

> **Дополнительное чтение**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступным языком объясняет историю и значение изоморфизма
> Карри-Говарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типа (можно опустить)
y = 100  // выводится как Int
```

#### 2. Определение функций

**Значение блока = хвостовое выражение, `return` выходит из функции (тип `Never`)** — подробности
см. в [RFC-010a](010a-tail-expression-and-return.md).

```yaoxiang
// Форма с одним выражением
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Форма с блоком кода: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b                    // хвостовое выражение → значение блока
}

// Многострочный блок кода
calc: (x: Float, y: Float, op: String) -> Float = {
    match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }                    // match как хвостовое выражение
}

// Void-функция: хвостовое выражение — Void
print: (msg: String) -> Void = {
    console.write(msg)   // console.write : Void
}
```

#### Правила возврата

**Значение блока = хвостовое выражение (единственный выход)**:

| Написание                                          | Значение                                |
| -------------------------------------------------- | --------------------------------------- |
| `= expr` (без фигурных скобок)                     | `expr`                                  |
| `= { ...; e }` (с фигурными скобками)              | Хвостовое выражение `e`                 |
| `= { ...; s }` (последний — оператор/присваивание) | `Void` (значение присваивания — `Void`) |
| `= {}` (пустой блок)                               | `Void`                                  |

**Семантика `return`**: нелокальный выход, **выходит из ближайшей границы функции** (не
«возвращается в блок»), имеет тип `Never`. `Never <: T` выполняется для любого типа (принцип
взрыва), поэтому `return` может появляться в любой позиции возвращаемого типа.

```yaoxiang
# Одно выражение: возвращает значение напрямую
add: (a: Int, b: Int) -> Int = a + b

# Блок кода: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b
}

# Досрочный возврат: return проходит сквозь блок, выходя из функции (тип Never)
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    n * factorial(n - 1)     # хвостовое выражение
}
```

**Обоснование дизайна**: `{ ... }` — это зависимо-управляемая вычислительная единица (см. ниже), её
семантика вычисления отличается от одиночного выражения — фигурные скобки вводят многооператорный
контекст, **его значение задаётся хвостовым выражением**, без какой-либо неоднозначности вроде
«является ли последнее выражение возвращаемым значением».

#### Семантика `{}`: зависимо-управляемая вычислительная единица

`{ ... }` в YaoXiang — не просто блок кода, а **зависимо-управляемая вычислительная единица**. Эта
семантика остаётся согласованной в телах функций, инициализации переменных и в `spawn`:

**Основные правила**:

- Операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- Когда зависимости удовлетворены, выполнение происходит немедленно, при их отсутствии — блокировка
  в ожидании
- **Значение блока = хвостовое выражение** (см. правила возврата); `return` — нелокальный выход типа
  `Never`, выходит из функции

```yaoxiang
# Управление по зависимостям: b зависит от a, компилятор автоматически сортирует
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # без зависимостей → может выполниться первым
    b              # хвостовое выражение → значение блока 11
}
```

> **Отличие от одиночного выражения**: `= expr` (без фигурных скобок) — простая привязка, напрямую
> возвращающая значение; `= { ... }` (с фигурными скобками) вводит контекст зависимо-управляемого
> вычисления, допускающий многооператорный код, значение которого задаётся хвостовым выражением.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитива YaoXiang. Он использует зависимо-управляемую
семантику `{}` для автоматического распараллеливания:

- Прямые дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- Задачи с удовлетворёнными зависимостями немедленно выполняются конкурентно
- Вызывающая сторона блокируется до завершения всех дочерних задач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (не зависит от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ожидает завершения обоих
    c                         # хвостовое выражение → значение spawn
}
// Вызывающая сторона блокируется здесь, пока все задачи внутри spawn не завершатся
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> см. в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций с сырыми указателями. Он
использует семантику вычисления `{}` для передачи определения типа во внешнюю область видимости
(выход значения — хвостовое выражение):

**Основные правила**:

- В `unsafe {}` можно определять типы и оперировать сырыми указателями
- **Хвостовое выражение** задаёт значение `unsafe {}` (определение типа передаётся во внешнюю
  область видимости)
- Возвращаемый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует привилегий unsafe

```yaoxiang
# Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    SqliteDb           # хвостовое выражение → значение блока unsafe
}

# SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: доступ к полю handle требует привилегий unsafe
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов см.
> в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы, реализацию интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть любыми выражениями типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang трёхуровневая, последовательно распознаваемая на разных стадиях
компилятора:

1. **Ключевые слова** (отдельный токен парсера) — управляющие структуры и ключевые слова объявления,
   такие как `if`, `match`, `pub`, `return`
2. **Литеральные зарезервированные слова** (отдельный токен парсера) — `true`, `false`, `void`,
   `Type`, не могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные в тайп-чекере) — парсер
   рассматривает их как обычные идентификаторы, их разбором занимается тайп-чекер. **Не являются
   зарезервированными словами, могут быть затенены (не рекомендуется)**

Различие между `void` (строчное, литеральное зарезервированное слово) и `Void` (прописное, имя
встроенного типа): `void` — литерал значения (равен единственному значению Unit), `Void` — имя типа
(равен типу Unit, логически ⊤). `let x: Void = void` — легальная запись.

Предустановленные имена встроенных типов:

| Тип      | Логический аналог   | Описание                                                                                                                                                                                                                                                                                      |
| -------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевой конструктор, никакое значение не может населять этот тип. Обозначает «невозможно» — расходимость, паника, мёртвый код. `Never <: T` для любого `T` (принцип взрыва). Функция, возвращающая `Never`, никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (значение void по умолчанию). `x: Void = <по умолчанию>` — легально. Соответствует единичному элементу суммы и единичному элементу произведения — `Void` — это произведение нуля полей (Unit), `Never` — сумма нуля вариантов.                                           |
| `Int`    | —                   | Знаковое целое                                                                                                                                                                                                                                                                                |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                      |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                         |
| `Char`   | —                   | Unicode-символ                                                                                                                                                                                                                                                                                |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                        |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        (dx * dx + dy * dy).sqrt()      # хвостовое выражение
    })
}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

```yaoxiang

    bounding_box: () -> Rect

Serializable: Type = {
    serialize: () -> String

Point: Type = {

}
```

##### Определение интерфейса

**Интерфейс = тип записи, все поля которого являются функциями**

```yaoxiang
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Пустой тип/пустой интерфейс
EmptyType: Type = {}
Empty: Type = {}
```

##### Определение функций пространства имён

**Префикс `Type.name` обозначает принадлежность к пространству имён**, и ничего более. Он не
вызывает никакой неявной привязки.

```yaoxiang
// Функция пространства имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

// Вызов: это обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` — не ключевое слово, а просто конвенциональное имя параметра. Написание
> `p`, `this`, `x` полностью эквивалентно. Компилятор смотрит на тип, а не на имя параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` вроде `p.draw(screen)` работал, **требуется явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции в качестве «метода»
(подробный синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после неё доступен синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающим

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // оба способа вызова эквивалентны

// Без [0] = без привязки. Point.draw — просто псевдоним обычной функции, без синтаксиса .
Point.draw = draw       // без привязки: можно только Point.draw(p, screen)
```

**Поведение по умолчанию**: отсутствие `[n]` = ни один параметр не привязан. Пользователь должен
явно решить, какие параметры заполняются вызывающей стороной.

**Привязка нескольких позиций**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 3.0)
```

**Обратная операция** (метод в обычную функцию):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Дженерик-типы

```yaoxiang
// Базовые дженерики (RFC-011 Phase 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретизация (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // пример вызова

// Дженерик-метод (синтаксис RFC-023: параметры типа автоматически выводятся в точке вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        Maybe.Just(self.data[index])
    } else {
        Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова дженериков

Для дженерик-типов и дженерик-функций единообразно используется синтаксис `()`. `[]` не используется
ни в одном дженерик-контексте.

**Основные правила**:

1. **`()` для всего**: применение типов, вызов функций, конструирование значений — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся слева
empty: List(Int) = List()

# Вызов дженерик-функции — тип автоматически вытекает из параметров
strings = map(numbers, f)
// T=Int приходит из numbers: List(Int)
// R=String приходит из f: (Int) -> String
```

2. **Type слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. T в пустом контейнере `List()` должен браться из аннотации типа
   слева.

3. **Информацию о типе нужно записать лишь раз** — при объявлении параметра компилятор проносит её:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int записывается один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически из типов numbers и f
```

4. **Конструирование значения выводит тип из элементов**:

```yaoxiang
x = List(1, 2, 3)       // выводится как List(Int)
y = List("a", "b")      // выводится как List(String)
z = List()              // ❌ ошибка компиляции: не удаётся вывести T
z: List(Int) = List()   // ✅ T=Int берётся из аннотации слева
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис дженериков с `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и индексации.

    scale: (factor: Float) -> Transformable
}

// ======== 2. Определение типов ========

    x: Float,
    y: Float,

    surface.plot(p.x, p.y)
}

}

}

}

}

    dy = p1.y - p2.y
    (dx * dx + dy * dy).sqrt()
}

// Явная привязка — только после неё доступен синтаксис вызова через точку

Point.bounding_box = bounding_box[0]
Point.serialize = serialize[0]
Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

Rect.bounding_box = bounding_box[0]

Rect.serialize = serialize[0]

Rect.translate = translate[0]

    Rect(r.x * factor, r.y * factor, r.width * factor, r.height * factor)
}
Rect.scale = scale[0]

// ======== 4. Использование ========

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (поля-функции)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, есть ли у типа метод с тем же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатур методов
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: после удаления параметра self должно совпадать
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации времени компиляции

Тип интерфейса поддерживает прямое присваивание, компилятор автоматически выбирает оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип определяется во время компиляции, вызов без накладных расходов
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возвращаемое значение функции → конкретный тип не может быть определён во время компиляции, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Гетерогенная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегии оптимизации времени компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                         |
| -------------------------------- | --------------------- | ------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (без накладных расходов) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                |

**Правила**:

1. Когда правая часть — конструктор конкретного типа и может быть определена во время компиляции,
   генерируется IR с прямым вызовом
2. Когда тип правой части не может быть определён во время компиляции, происходит откат к механизму
   vtable
3. vtable как страховка обеспечивает корректность полиморфизма в runtime

### Изменения синтаксиса

| Раньше                                   | После                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `type Point = Point(x: Float, y: Float)` | `type Point = { x: Float, y: Float }`                                                        |
| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| Требуется ключевое слово `impl`          | Ключевое слово не требуется, имя интерфейса записывается после тела типа                     |

### Устаревший синтаксис: `|` для вариантов

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов `|` официально устарел и удалён из
> реализации.

Следующие написания **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Единообразно используются типы записей для выражения сумм (sum type). Когда все поля типа записи
являются функциями и каждая возвращает сам этот тип, он является суммой:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особых случаев**: `|` — единственная форма в BNF, не укладывающаяся в
   `name: type = value`. После удаления продукция `type_expr` полностью унифицирована, парсеру
   больше не нужно поддерживать отдельный путь и предпросмотр-откат для вариантных типов.
2. **Математическая эквивалентность**: с точки зрения изоморфизма Карри-Говарда, дизъюнкция P ⊕ Q
   соответствует сумме, эквивалентной типу записи «все поля — функции, возвращающие сам тип». Оба
   выражают одну и ту же семантику, и нет нужды в двух синтаксисах.
3. **Нулевая разрушительность**: до удаления синтаксис `|` в парсере был наполовину поддержан
   (варианты без параметров могли быть разобраны, но типы параметров терялись при мономорфизации),
   никакой пользовательский код на него не полагался.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы проходят по
   пути `Type::Struct`, специальные ветви в нижестоящих тайпчек/моно/форматтере полностью устранены.

> **Примечание**: семантические свойства суммы (конструирование вариантов, проверка полноты match,
> размещение tagged union в памяти) выводятся тайпчек-уровнем из структуры `Type::Struct` и не
> зависят от отдельного узла AST. Полная семантика конструирования вариантов приведена в следующем
> разделе [Конструирование вариантов записевых сумм (авторитетное определение)].

### Конструирование вариантов записевых сумм (авторитетное определение)

> Данный раздел раскрывает критерии распознавания из раздела [Устаревший синтаксис: `|` для
> вариантов] в полную семантику (принято 2026-09-25, предшествует issue #341 Phase 2 RFC-011b).
> Четыре решения: типо-квалифицированный вызов, варианты с нулевой нагрузкой в форме вызова функции,
> самообеспеченный вывод типа, «все или ничего» повышение имён вариантов.

#### Правило распознавания: всё или ничего

Тип записи определяется как **сумма**, когда выполняются оба следующих условия:

1. Все типы полей в теле типа являются типами функций;
2. Тип возврата каждого поля после подстановки параметров типа (`Self`/аргументы дженерика) равен
   самому этому типу записи.

Распознавание работает по принципу **«всё или ничего»**: если оно срабатывает, все поля-функции
одновременно повышаются до конструкторов вариантов; если не срабатывает — весь тип является обычной
записью (поля-функции — это поля данных, хранящие значения функций), смешанной формы «частично
варианты, частично данные» не существует. Когда требуется одновременно переносить данные и семантику
вариантов, моделируйте как два типа — запись данных и сумму, не объединяя их в одном объявлении.

#### Форма вызова: типо-квалифицированная, без голого имени

**Единственная** форма вызова конструктора вариантов — типо-квалифицированный вызов: взятие члена
варианта на значении типа и его вызов:

```yaoxiang
r1 = Result(Int, String).ok(5)   // Result(Int, String), полезная нагрузка 5
c  = Color.red()                 // вариант с нулевой нагрузкой: форма вызова функции, согласованная с сигнатурой поля
```

**Голая форма не предоставляется** (`ok(5)` не является вызовом конструктора). Причина: голая форма
зависит от ожидаемого контекстного типа для обратного вывода принадлежности к сумме и аргументов
типа, тогда как в данном языке типы должны быть явно записываемыми, вывод течёт однонаправленно из
ожидаемой позиции (та же дисциплина, что и в RFC-011a «Self — явный параметр типа, никакой магии»).
В типо-квалифицированной форме тип полностью самообеспечен, не требуя контекста. Если в будущем
голая форма будет введена, она может быть лишь разворачивающим сахаром «когда контекст однозначно
определяет», а семантическим базисом останется квалифицированная форма из данного раздела.

#### Вывод: самообеспеченный тип

После того как квалифицированное имя задаёт полные аргументы типа, сигнатура конструктора варианта
является **результатом подстановки аргументов типа в сигнатуру поля**:

```yaoxiang
Result(Int, String).ok   // : (Int) -> Result(Int, String)
```

Проверка типа полезной нагрузки — это обычная проверка аргументов вызова функции (несоответствие
даёт E1002), новых правил вывода не вводится. Конструкторы дженерик-сумм мономорфизируются
естественным образом при инстанцировании типа, отдельного механизма нет.

#### Повышение полей: имена вариантов не являются полями данных

После распознавания как суммы имена вариантов удаляются из пространства полей данных — доступ к
полю-варианту на **значении** суммы запрещён на этапе компиляции:

```yaoxiang
r1.ok    // ошибка компиляции: ok — конструктор варианта Result, а не поле данных
```

Причина: значение суммы в runtime — это tagged union (см. ниже), не несущее таблицу объявления
вариантов; разрешение доступа к полю неизбежно привело бы к тихому ошибочному переводу. Это
продолжение той же дисциплины, что и RFC-011a §1.2 (единое пространство имён полей/методов, конфликт
сообщается как ошибка). Конструирование — через типо-квалификацию (`Result.ok`), получение — через
деструкцию match (RFC-039).

#### Представление в runtime и равенство

Представление значения суммы в runtime — это tagged union:
`Enum { идентичность_типа, variant_id, полезная_нагрузка }`.

- **Идентичность типа** несёт конкретную сумму (не глобальный заполнитель) — значения из разных сумм
  несравнимы;
- **variant_id** нумеруется по **порядку объявления** варианта в теле типа, этот же порядок служит
  входными данными для проверки полноты в RFC-039;
- **Равенство** (`==`/`!=`): одинаковая идентичность типа, одинаковый variant_id, поэлементное
  равенство полезной нагрузки (рекурсивно).

#### Миграция std

`std.result` переходит на использование механизма данного раздела для определения `ok` / `err`
(нативные `result_ok` / `result_err` отходят на второй план), конструирование вариантов в `std` идёт
по тем же правилам, что и пользовательские суммы, без привилегированного канала. Демонтаж
парсер-специальных случаев `Result` / `Option` в позиции типа и специальных случаев `make_result` по
имени выполняется в рамках [RFC-011b](./011b-operator-overloading.md) Phase 2 — после
интерфейсизации `?` `Result` становится обычной std-суммой.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: авторитетная форма логических операторов — ключевые слова
> `and` / `or` + символьный унарный `!` (согласовано с таблицей приоритетов SPEC `syntax.md` §2.2).
> Данный дизайн выровнен с Zig: **управление потоком с коротким замыканием — через ключевые слова,
> чистые унарные операции — через символы**. Ранние реализации, дрейфовавшие к C-стилю `&&` / `||`,
> и промежуточное ключевое слово `not` — все удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                 | Ассоциативность | Семантика                                             |
| -------- | ------------------------------------- | --------------- | ----------------------------------------------------- |
| `!`      | 3 (унарный префикс, плотная привязка) | справа налево   | Логическое НЕ (чистая функция, без потока управления) |
| `and`    | 10                                    | слева направо   | Короткозамыкающее логическое И                        |
| `or`     | 10                                    | слева направо   | Короткозамыкающее логическое ИЛИ                      |

```yaoxiang
# Короткое замыкание: когда левая часть and равна false / левая часть or равна true, правая не вычисляется
if x != 0 and y / x > 1 { ... }   # при x == 0 деления на ноль не произойдёт

# Плотная привязка: !a == b ≡ (!a) == b (стиль Zig; в отличие от Python, где not a == b ≡ not (a == b))
!3 == 4          # false: (!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs)), вызов с последующим отрицанием
```

Следующие написания **больше не поддерживаются** (лексер сообщает об ошибке и подсказывает
соответствующее написание):

```
x && y     # ❌ удалено, используйте x and y
x || y     # ❌ удалено, используйте x or y
not x      # ❌ удалено, используйте !x (not снова становится обычным идентификатором; != не затрагивается)
```

**Обоснование дизайна** (выравнивание с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — поток управления → ключевое слово; чистая функция — операция → символ**.
   `and` / `or` изменяют порядок вычисления (правая часть пропускается по необходимости), по природе
   аналогичны `if`, поэтому используют ключевые слова; `!` выполняет чистое отрицание уже
   вычисленного операнда, по природе аналогично `-` `+`, поэтому использует символ. В YaoXiang
   распространение ошибок выполняется через `?` (§2.11), `!` конфликта нет.
2. **Плотная привязка устраняет неоднозначность**: `!` визуально «прилипает» к операнду, высокий
   приоритет очевиден; ключевое слово `not` вынуждено отделяться пробелом от операнда, и привязка к
   какой стороне (`not a == b`) легко вызывает ментальную неоднозначность.
3. **Устранение неоднозначности**: `&` несёт двойную функцию — токен заимствования (`&p` / `&mut p`,
   RFC-009) и побитовое И (SPEC §2.2 приоритет 8). Введение `&&` заставит один символ нести три
   значения. `and` / `or` / `!` визуально полностью разделяют заимствование, побитовые операции и
   логику.
4. **Прецедент**: Zig (современный системный язык той же экологической ниши) использует именно
   комбинацию ключевых слов `and` / `or` + символ `!`; Python / Lua / Ada / SQL — полностью ключевые
   слова (включая `not`), семейство C — полностью символы — YaoXiang берёт микс Zig, получая
   преимущества обоих подходов.
5. **Согласованность с Карри-Говардом**: типы как утверждения (см. раздел изоморфизма выше),
   логические связки в уточняющих типах записываются как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`) — естественное выражение утверждений; `!` как символ унарного
   отрицания соответствует ¬.

> **Реализация**: `and` / `or` на уровне IR разворачиваются в последовательности короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`), `!` разбирается как унарный с плотной привязкой
> (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Пояснения к дизайну синтаксиса: именованные функции по сути являются синтаксическим сахаром лямбд

### Ключевое понимание

**Именованные функции и лямбда-выражения — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// Эти две формы по сути полностью идентичны
add: (a: Int, b: Int) -> Int = a + b           // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, заголовок лямбды с именами
параметров становится избыточным и может быть опущен.

### Правила области видимости параметров

**Параметры затеняют внешние переменные**: область видимости параметров в сигнатуре перекрывает тело
функции, внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x затеняет внешний x, результат 20
```

### Гибкость позиции аннотации

Аннотация типа может находиться в любой из следующих позиций, **достаточно аннотации хотя бы в одном
месте**:

| Позиция аннотации         | Форма                                    | Пояснение                  |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ легально                |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но разрешено |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: сигнатура полная, заголовок лямбды опущен
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Легально: типы аннотированы в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Легально: аннотация в обоих местах
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство            | Преимущество                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------- |
| **Краткость**       | При полной сигнатуре не нужно повторять имена параметров                                 |
| **Гибкость**        | Сохранена лямбда-форма — используйте ту, которая нравится                                |
| **Согласованность** | Согласовано с шаблоном объявления переменных `x: Int = 42`                               |
| **Интуитивность**   | `name: Type = body` напрямую соответствует «с именем name, типа Type, со значением body» |

## Приложение

### Синтаксис BNF

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражение типа
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # Применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # Тип функции
       | '{' type_field* '}'                       # Тип записи/интерфейса
       | 'Type'                                    # Метатип

type_field ::= identifier ':' type_expr
             | identifier                           # Ограничение интерфейса

# Параметр дженерика: как часть типа функции, например (T: Type, R: Type) -> (...)
# Отдельное правило BNF не требуется — параметры : Type — это обычные параметры функции

# Выражение
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # Вызов функции / вызов конструктора
              | '(' expression (',' expression)* ')'              # Кортеж
              | expression '.' identifier '(' arguments? ')'    # Вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                    | Определение                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Объявление                | Оператор присваивания формы `name: type = value`                                                                    |
| Тип записи                | Тип `{ ... }` с именованными полями                                                                                 |
| Интерфейс                 | Тип записи, все поля которого являются типами функций                                                               |
| Дженерик-тип              | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                               |
| Функция пространства имён | Функция вида `Type.name`, принадлежащая пространству имён Type. Не предполагает никакой привязки                    |
| Привязка метода           | `Type.name = func[n]`, привязка позиции n функции func как вызывающего, делает доступным синтаксис `obj.name(args)` |
| Дженерик-функция          | Функция, использующая синтаксис `(T: Type)`, с параметрами типа в качестве первой группы параметров                 |
| Метатип                   | `Type`, единственный маркер уровня типа в языке                                                                     |
