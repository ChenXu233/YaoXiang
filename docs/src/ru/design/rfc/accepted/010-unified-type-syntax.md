# RFC-010: Унифицированный синтаксис типов - модель name: type = value

## Резюме

Данный RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
в качестве ключевого слова метамтипа)**.

> **Ключевая идея проектирования**: `Type` сам по себе является обобщённым (generic) типом.
> `(T: Type) -> Type` означает «тип, принимающий параметр типа T».

| Понятие            | Запись в коде                                                                |
| ------------------ | ---------------------------------------------------------------------------- |
| Переменная         | `x: Int = 42`                                                                |
| Функция            | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи         | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс          | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Обобщённый тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Обобщённый тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод              | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Обобщённая функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово метамтипа в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` обозначает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` (например, `p.draw(screen)`) работал, требуется явная привязка:
> `Point.draw = draw[0]`. Подробнее см. раздел «Пространства имён и привязка методов» ниже. Он
> используется для обозначения иерархии типов; компилятор автоматически различает Type0, Type1,
> Type2..., что прозрачно для пользователя.

```yaoxiang
// 核心语法：统一 + 区分

// 变量
x: Int = 42

// 函数（参数名在签名中）
add: (a: Int, b: Int) -> Int = a + b

// 记录类型
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// 接口（本质是字段全为函数的记录类型）
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// 方法定义（使用 Type.method 语法）
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    "Point(${self.x}, ${self.y})"
}

// 泛型类型（(T: Type) -> Type = 接受类型参数的泛型类型）
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// 使用
p: Point = Point(1.0, 2.0)
p.draw(screen)           // 语法糖 → Point.draw(p, screen)
s: Drawable = p           // 结构子类型：Point 实现 Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

В текущей системе типов существует несколько разрозненных понятий:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (различный)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Между этими понятиями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельное единство**: одно правило синтаксиса покрывает все случаи
2. **Простота и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих синтаксических элементов
4. **Теоретическая элегантность**: сам тип является значением типа Type
5. **Совместимость с дженериками**: бесшовная интеграция с системой обобщений (RFC-011)

### Интеграция с системой дженериков

Унифицированная синтаксическая модель RFC-010 **органично сочетается** с дизайном системы дженериков
RFC-011: параметры дженериков могут бесшовно встраиваться в унифицированную модель.

```yaoxiang
// 基础泛型（RFC-011 Phase 1）
List: (T: Type) -> Type = { data: Array(T), length: Int }

// 泛型函数（RFC-023 语法：签名中 Type 位置可省略，调用时自动推断）
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// 类型约束（RFC-011 Phase 2）
clone: (value: T) -> T = value.clone()  // T: Clone 约束由参数类型携带

// Const泛型（RFC-011 Phase 4）
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- Phase 1 RFC-011 (базовые дженерики) является **сильной зависимостью** для RFC-010
- Без базовых дженериков примеры с дженериками в RFC-010 не скомпилируются
- Рекомендация: Phase 1 RFC-011 и RFC-010 следует реализовать одновременно

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор проектирования, определяющий правила устранения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                                     |
| ------------------- | ---------------------- | ----------------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | Явное объявление `: Type` → принудительно тип               |
| **`f = ...`**       | Функция или переменная | Нет `: Type` → HM самостоятельно выводит функцию/переменную |

**Почему такое решение?**

Сам синтаксис `{ ... }` неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (выполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` является
  литералом типа
- **Нет** `: Type` → HM самостоятельно интерпретирует `{ ... }` как блок кода, выводит
  функциональный тип

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит () -> Void
main: () -> Void = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может интерпретировать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит как функцию, а не как тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # Нет : Type, HM выводит функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # Должен возвращать: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # Должен возвращать: Type
│
├── Обобщённый тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # Должен возвращать: Type
│
├── Обобщённый тип (несколько параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # Должен возвращать: Type
│
├── Функция в пространстве имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # Только после явной привязки доступен синтаксис с точкой
│
└── Обобщённая функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # Не возвращает Type, HM выводит функцию
```

### Иерархия метатипов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Level    | Описание                                    |
| -------- | ------------------------------------------- |
| `Type0`  | Повседневные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)        |
| `Type2+` | Конструкторы высшего порядка                |

**Пользователь никогда не видит этих чисел**, только `: Type`.

### Изоморфизм Карри-Ховарда: тип есть высказывание, программа есть доказательство

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он является прямым
отражением изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм раскрывает
глубокий факт: **система типов и логическая система — это две стороны одной и той же сущности**.

| Логика (высказывание)         | Система типов (YaoXiang)              | Пример                               |
| ----------------------------- | ------------------------------------- | ------------------------------------ |
| Высказывание P                | Тип T                                 | `Int`, `Bool`                        |
| Доказательство истинности P   | Значение типа T                       | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | Функциональный тип `(P) -> Q`         | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | Тип записи `{ p: P, q: Q }`           | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Обобщённая функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | Перечисление / tagged union           | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в рамках Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int, именуемое x, со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: дано доказательство a типа Int и доказательство b типа Int, можно построить доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — это высказывание, доказательство которого требует одновременного предоставления доказательства x типа Float и доказательства y типа Float"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = типобезопасность**: если система типов позволяет создать
   значение типа `T` без какого-либо легитимного представления во время выполнения, это подобно
   тому, как если бы логика позволяла доказать ложное высказывание — система разрушается.
   Карри-Ховард говорит нам: **типобезопасный язык по своей природе является непротиворечивой
   логической системой**.

2. **Иерархия вселенной — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (т. е. «тип типа также является типом»), возникает парадокс Рассела (в теории типов
   проявляющийся как парадокс Жирара). Стратификация YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   гарантирует, что каждый тип принадлежит определённому уровню, образуя бесконечно восходящую
   цепочку, что фундаментально предотвращает парадоксы. Это означает, что система типов YaoXiang в
   смысле Карри-Ховарда **логически непротиворечива**.

3. **Теоретическая основа унифицированного синтаксиса**: причина, по которой `name: type = value`
   может одной формой синтаксиса покрыть все понятия — переменные, функции, типы, интерфейсы,
   дженерики — состоит в том, что в рамках Карри-Ховарда все они суть одно и то же —
   **предоставление доказательства высказывания**. Переменная — это свидетельство высказывания,
   функция — свидетельство импликации, запись — свидетельство конъюнкции, дженерик — свидетельство
   квантора всеобщности. Унифицированный синтаксис — не искусственное совпадение, а естественное
   следствие изоморфизма Карри-Ховарда.

> **Дополнительное чтение**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья в доступной форме объясняет историю и значение изоморфизма
> Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// 基本语法
x: Int = 42
name: String = "Alice"
flag: Bool = true

// 类型推导（可省略）
y = 100  // 推断为 Int
```

#### 2. Определение функций

> **Исправление (2026-09-15, RFC-010a)**: в данном разделе и в разделе «Правила возврата» ниже
> изначально `return` использовался как выход из блока, что конфликтовало с семантикой досрочного
> возврата из RFC-007 (подробности см. в [RFC-010a](010a-tail-expression-and-return.md)). Теперь
> изменено: **значение блока = хвостовое выражение, `return` выходит из функции (тип `Never`)**.
> Ошибочные примеры «обязательного использования `return` для возврата значения» удалены и не
> сохраняются в данном исправлении.

```yaoxiang
// 单表达式形式
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// 代码块形式：值是尾表达式
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b                    // 尾表达式 → 块的值
}

// 多行代码块
calc: (x: Float, y: Float, op: String) -> Float = {
    match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }                    // match 作尾表达式
}

// Void 函数：尾表达式为 Void
print: (msg: String) -> Void = {
    console.write(msg)   // console.write : Void
}
```

#### Правила возврата

> **Исправление (2026-09-15, RFC-010a)**: исходное правило «`= { ... }` должен использовать
> `return`, иначе возвращается `Void`» и обоснование «требуется явный `return` для устранения
> неоднозначности относительно того, является ли последнее выражение возвращаемым значением»
> **отменено**. Хвостовое выражение не создаёт такой неоднозначности, а `return` не мешает ему (Rust
> уже подтвердил данный изоморфный дизайн).

**Значение блока = хвостовое выражение (единственный выход)**:

| Запись                                             | Значение                                |
| -------------------------------------------------- | --------------------------------------- |
| `= expr` (без фигурных скобок)                     | `expr`                                  |
| `= { ...; e }` (с фигурными скобками)              | хвостовое выражение `e`                 |
| `= { ...; s }` (последний — оператор/присваивание) | `Void` (значение присваивания — `Void`) |
| `= {}` (пустой блок)                               | `Void`                                  |

**Семантика `return`**: нелокальный выход, **выход из ближайшей границы функции** (не «возврат в
блок»), тип `Never`. `Never <: T` выполняется для любого типа (принцип взрыва), поэтому `return`
может встречаться в любой позиции возвращаемого типа.

```yaoxiang
# 单表达式：直接返回值
add: (a: Int, b: Int) -> Int = a + b

# 代码块：值是尾表达式
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b
}

# 提前返回：return 穿透块，退出函数（类型 Never）
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    n * factorial(n - 1)     # 尾表达式
}
```

> **Обоснование проектирования (исправление 2026-09-15, RFC-010a)**: `{ ... }` — это блок
> вычислений, управляемый зависимостями (см. ниже), его семантика вычисления отличается от
> одновыраженческой — фигурные скобки вводят контекст с множеством операторов, **значение которого
> задаётся хвостовым выражением**. Исходный аргумент «требуется явный `return` для устранения
> неоднозначности» отменён: хвостовое выражение не создаёт такой неоднозначности.

#### Семантика `{}`: блок вычислений, управляемый зависимостями

`{ ... }` в YaoXiang — это не просто блок кода, а **блок вычислений, управляемый зависимостями**.
Эта семантика единообразна для тел функций, инициализации переменных и `spawn`:

**Ключевые правила**:

- Операторы присваивания внутри `{}` автоматически упорядочиваются по зависимостям, а не по порядку
  записи
- При готовности зависимостей выполнение происходит немедленно, при отсутствии — блокировка с
  ожиданием
- **Значение блока = хвостовое выражение** (см. правила возврата); `return` — нелокальный выход типа
  `Never`, выход из функции

```yaoxiang
# 依赖驱动：b 依赖 a，编译器自动排序
result: Int = {
    b = a + 1      # 依赖 a → 自动排在 a 之后
    a = 10         # 无依赖 → 可以先执行
    b              # 尾表达式 → 块的值 11
}
```

> **Отличие от одновыраженческой записи**: `= expr` (без фигурных скобок) — простая привязка с
> прямым возвратом значения; `= { ... }` (с фигурными скобками) вводит контекст вычислений,
> управляемый зависимостями, с множеством операторов, значение которого задаётся хвостовым
> выражением.

#### Блоки `spawn`

`spawn { ... }` — единственная примитива параллелизма в YaoXiang. Она использует семантику
зависимостей `{}` для автоматического распараллеливания:

- Непосредственные дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные
  задачи
- Задачи с готовыми зависимостями немедленно выполняются конкурентно
- Вызывающий блокируется до завершения всех подзадач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # 任务 1
    b = fetch_data("url2")    # 任务 2（与 a 无依赖，并行执行）
    c = process(a, b)         # 依赖 a, b → 等待两者完成后执行
    c                         # 尾表达式 → spawn 的值
}
// 调用方在此阻塞，直到 spawn 块内所有任务完成
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> подробно описаны в `008-runtime-concurrency-model.md`.

#### Блоки `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и работы с сырыми указателями. Он
использует семантику вычисления `{}`, передавая определение типа во внешнюю область видимости
(значение выхода — хвостовое выражение):

**Ключевые правила**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- **Хвостовое выражение** даёт значение `unsafe {}` (определение типа передаётся во внешнюю область
  видимости)
- Возвращаемый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует привилегий unsafe

```yaoxiang
# 在 unsafe 块中定义不透明类型
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # 裸指针
    }
    SqliteDb           # 尾表达式 → unsafe 块的值
}

# SqliteDb 在 unsafe 块外可用
db = sqlite3_open("test.db")

# ❌ 编译错误：handle 字段需要 unsafe 权限
handle = db.handle

# ✅ 通过方法调用
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов
> подробно описаны в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализации интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть любыми выражениями типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang состоит из трёх уровней, последовательно распознаваемых на разных
этапах компиляции:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявления, такие как `if`, `match`, `pub`, `return`
2. **Литеральные зарезервированные слова** (отдельные токены парсера) — `true`, `false`, `void`,
   `Type`, не могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные проверщиком типов) — парсер
   рассматривает как обычные идентификаторы, интерпретация возлагается на проверщик типов. **Не
   являются зарезервированными словами, могут быть затенены (не рекомендуется)**

Различие между `void` (в нижнем регистре, литеральное зарезервированное слово) и `Void` (в верхнем
регистре, имя встроенного типа): `void` — это литерал значения (равен единственному значению Unit),
а `Void` — имя типа (равен типу Unit, логически ⊤). `let x: Void = void` является допустимым.

Предопределённые имена встроенных типов:

| Тип      | Логический аналог   | Описание                                                                                                                                                                                                                                                                                          |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевой конструктор, никакое значение не может населять этот тип. Выражает «невозможность» — расходимость, panic, мёртвый код. `Never <: T` выполняется для любого `T` (принцип взрыва). Функция, возвращающая `Never`, не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (по умолчанию значение void). `x: Void = <по умолчанию>` допустимо. Нейтральный элемент как для суммы, так и для произведения типов — `Void` — пустой тип-произведение (Unit), `Never` — пустой тип-сумма.                                                                   |
| `Int`    | —                   | Знаковое целое число                                                                                                                                                                                                                                                                              |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                          |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                             |
| `Char`   | —                   | Символ Unicode                                                                                                                                                                                                                                                                                    |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                            |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // 绑定到位置0，柯里化后 method: (b: Point) -> Float
}
// 调用：p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        (dx * dx + dy * dy).sqrt()      # 尾表达式
    })
}
// 语法：((params) => body)[position]
// 调用：p1.distance(p2) → distance(p1, p2)
```

**Интерфейс = тип записи, все поля которого являются функциями**

```yaoxiang
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect

    serialize: () -> String
}

// 空类型/空接口
EmptyType: Type = {}

```

##### Определение функций в пространстве имён

**Префикс `Type.name` обозначает принадлежность к пространству имён**, и ничего более. Он не
вызывает никакой неявной привязки.

```yaoxiang
// 命名空间函数：在 Point 命名空间下的普通函数
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

// 调用：就是普通函数调用
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` не является ключевым словом, это лишь общепринятое соглашение об именовании
> параметра. Написание `p`, `this`, `x` даёт точно такой же эффект. Компилятор смотрит на тип, а не
> на имя параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` (например, `p.draw(screen)`) работал, **требуется явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции как «метода» (подробный
синтаксис см. в RFC-004).

```yaoxiang
// 定义函数
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// 显式绑定 — 这之后才有 p.draw(screen) 语法
Point.draw = draw[0]   // 位置 0 的参数（&Point）由调用者填充

// 使用
p.draw(screen)          // 语法糖 → draw(&p, screen)
Point.draw(p, screen)   // 两种调用方式等价

// 不写 [0] = 不绑定。Point.draw 就是普通函数别名，没有 . 语法
Point.draw = draw       // 不绑定：只能 Point.draw(p, screen)
```

**Поведение по умолчанию**: без `[n]` = никакая позиция не привязывается. Пользователь должен явно
решить, какие параметры заполняются вызывающим.

**Многопозиционная привязка**:

```yaoxiang
// 绑定多个位置（自动柯里化）
Point.transform = transform_points[0, 1]
// 调用：p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// 从绑定中取出函数
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Обобщённые типы

```yaoxiang
// 基础泛型（RFC-011 Phase 1）
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// 具体实例化（RFC-023 语法）
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // 调用示例

// 泛型方法（RFC-023 语法：类型参数由调用处自动推断）
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        Maybe.Just(self.data[index])
    } else {
        Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова дженериков

Вызовы обобщённых типов и обобщённых функций унифицированы через синтаксис `()`. `[]` не
используется ни в каком обобщённом контексте.

**Ключевые правила**:

1. **`()` для всего применения**: применение типа, вызов функции, конструирование значения — всё
   через `()`

```yaoxiang
# 类型标注
numbers: List(Int) = List(1, 2, 3)

# 空容器：T 从左侧来
empty: List(Int) = List()

# 泛型函数调用——类型从参数自动流动
strings = map(numbers, f)
// T=Int 来自 numbers: List(Int)
// R=String 来自 f: (Int) -> String
```

2. **Тип слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретное значение. T для пустого контейнера `List()` должен быть получен из левой
   аннотации типа.

3. **Информация о типе записывается только один раз** — при объявлении параметров компилятор
   переносит её:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int 在左边写一次
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String 自动从 numbers 和 f 的类型来
```

4. **Конструирование значения выводит тип из элементов**:

```yaoxiang
x = List(1, 2, 3)       // 推断为 List(Int)
y = List("a", "b")      // 推断为 List(String)
z = List()              // ❌ 编译错误：无法推断 T
z: List(Int) = List()   // ✅ T=Int 来自左侧注解
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис дженериков `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

#### Полный пример

```yaoxiang
// ======== 1. 接口定义 ========
// 接口 = 字段全是函数类型的记录类型
// 接口中不需要 self 参数 — 接口只定义"去掉调用者位置后的函数签名"

Drawable: Type = {
    draw: (surface: Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

Transformable: Type = {
    translate: (dx: Float, dy: Float) -> Transformable,  // 返回接口类型，具体实现返回自己的类型
    scale: (factor: Float) -> Transformable
}

// ======== 2. 类型定义 ========

Point: Type = {
    x: Float,
    y: Float,
    Drawable,
    Serializable,
    Transformable
}

Rect: Type = {
    x: Float,
    y: Float,
    width: Float,
    height: Float,
    Drawable,
    Serializable,
    Transformable
}

// ======== 3. 方法实现（普通函数 + 显式绑定）========

// 定义函数（self 只是约定名，不是关键字）
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

bounding_box: (p: &Point) -> Rect = {
    Rect(p.x - 1, p.y - 1, 2, 2)
}

serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

translate: (p: &Point, dx: Float, dy: Float) -> Point = {
    Point(p.x + dx, p.y + dy)
}

scale: (p: &Point, factor: Float) -> Point = {
    Point(p.x * factor, p.y * factor)
}

distance: (p1: &Point, p2: &Point) -> Float = {
    dx = p1.x - p2.x
    dy = p1.y - p2.y
    (dx * dx + dy * dy).sqrt()
}

// 显式绑定 — 绑定后才有点调用语法
Point.draw = draw[0]
Point.bounding_box = bounding_box[0]
Point.serialize = serialize[0]
Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

// Rect 的方法也类似
draw: (r: &Rect, surface: Surface) -> Void = {
    surface.draw_rect(r.x, r.y, r.width, r.height)
}
Rect.draw = draw[0]

bounding_box: (r: &Rect) -> Rect = r
Rect.bounding_box = bounding_box[0]

serialize: (r: &Rect) -> String = {
    "Rect(${r.x}, ${r.y}, ${r.width}, ${r.height})"
}
Rect.serialize = serialize[0]

translate: (r: &Rect, dx: Float, dy: Float) -> Rect = {
    Rect(r.x + dx, r.y + dy, r.width, r.height)
}
Rect.translate = translate[0]

scale: (r: &Rect, factor: Float) -> Rect = {
    Rect(r.x * factor, r.y * factor, r.width * factor, r.height * factor)
}
Rect.scale = scale[0]

// ======== 4. 使用 ========

// 创建实例
p: Point = Point(1.0, 2.0)
r: Rect = Rect(0.0, 0.0, 10.0, 20.0)

// 方法调用（语法糖）
p.draw(screen)
r.draw(screen)

// 普通方法调用（直接调用）
d: Float = distance(p, Point(0.0, 0.0))

// 链式调用
p2: Point = p.translate(1.0, 1.0).scale(2.0)

// 接口赋值
drawables: List(Drawable) = [p, r]
for d in drawables {
    d.draw(screen)
}

// 泛型函数（RFC-023 语法：调用时省略类型参数，自动推断）
process_all: (items: List(T)) -> Void = {
    for item in items {
        print(item.serialize())
    }
}

process_all([p, r])
```

## Детальное проектирование

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // 对于接口的每个字段（函数字段）
    for (field_name, iface_field) in &iface.fields {
        // 检查类型是否有同名方法
        if let Some(method) = typ.methods.get(field_name) {
            // 检查方法签名是否兼容
            // 接口字段: (Surface) -> Void
            // 方法签名: (Point, Surface) -> Void
            // 比较：去掉 self 参数后应该匹配
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации времени компиляции

Интерфейсные типы поддерживают прямое присваивание; компилятор автоматически выбирает оптимальную
стратегию вызова на основе конкретного типа правого значения:

```yaoxiang
// 直接赋值具体类型 → 编译期可确定具体类型，零开销调用
d: Drawable = Circle(1)
d.draw(screen)  // 编译后：直接调用 circle_draw(screen)，无 vtable

// 函数返回值 → 编译期无法确定具体类型，使用 vtable
d: Drawable = get_shape()
d.draw(screen)  // 通过 vtable 查找方法

// 异构集合 → 使用 vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // 通过 vtable 查找方法
}
```

**Стратегии оптимизации времени компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестен            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                   |

**Правила**:

1. Когда правое значение является конструктором конкретного типа и может быть определено во время
   компиляции, генерируется IR прямого вызова
2. Когда тип правого значения не может быть определён во время компиляции, происходит откат к
   механизму vtable
3. vtable служит страховкой, гарантирующей корректность полиморфизма во время выполнения

### Изменения синтаксиса

| Ранее                                    | Впоследствии                                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `type Point = Point(x: Float, y: Float)` | `type Point = { x: Float, y: Float }`                                                        |
| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| Требуется ключевое слово `impl`          | Ключевое слово не требуется, имена интерфейсов записываются после тела типа                  |

### Устаревший: синтаксис вариантов через `|`

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов через `|` официально устарел и
> удалён из реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ Устарело
type Result(T, E) = ok(T) | err(E)             # ❌ Устарело
type Option(T) = some(T) | none                # ❌ Устарело
```

Единообразно используется тип записи для выражения типов-сумм (sum type). Когда все поля типа записи
являются функциями, возвращающими сам этот тип, он является типом-суммой:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование проектирования**:

1. **Устранение особых случаев**: `|` — единственная синтаксическая форма в BNF, не соответствующая
   `name: type = value`. После удаления продукция `type_expr` становится полностью унифицированной,
   и парсеру больше не требуется поддерживать отдельный путь и перебор с возвратом для вариантных
   типов.
2. **Математическая эквивалентность**: в рамках изоморфизма Карри-Ховарда дизъюнкция P ⊕ Q,
   соответствующая типу-сумме, эквивалентна типу записи «все поля которого — функции, возвращающие
   сам этот тип». Оба выражают одну и ту же семантику, без необходимости в двух наборах синтаксиса.
3. **Нулевая разрушительность**: до удаления синтаксис `|` в парсере поддерживался лишь частично
   (варианты без параметров могли быть разобраны, но типы параметров терялись при мономорфизации),
   ни один пользовательский код не зависел от него.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы проходят по
   пути `Type::Struct`, что устраняет специальные ветки в нижестоящих typecheck/mono/formatter.

> **Примечание**: семантические свойства типов-сумм (такие как проверка полноты match, размеченное
> размещение в памяти) выводятся на уровне typecheck из структуры `Type::Struct`, не завися от
> отдельного узла AST.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: авторитетной формой логических операторов являются
> ключевые слова `and` / `or` + символьный унарный `!` (соответствует таблице приоритетов SPEC
> `syntax.md` §2.2). Данное решение соответствует Zig: **короткозамыкающий поток управления — через
> ключевые слова, чистая унарная операция — через символ**. Ранние реализации, дрейфующие к стилю C
> (`&&` / `||`), а также промежуточное ключевое слово `not`, удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                   | Ассоциативность | Семантика                                             |
| -------- | --------------------------------------- | --------------- | ----------------------------------------------------- |
| `!`      | 3 (унарный префиксный, тесная привязка) | Справа налево   | Логическое НЕ (чистая функция, без потока управления) |
| `and`    | 10                                      | Слева направо   | Короткозамыкающее логическое И                        |
| `or`     | 10                                      | Слева направо   | Короткозамыкающее логическое ИЛИ                      |

```yaoxiang
# 短路求值：and 左侧为 false / or 左侧为 true 时，右侧不执行
if x != 0 and y / x > 1 { ... }   # x == 0 时不会除零

# 紧绑定：!a == b ≡ (!a) == b（Zig 式；与 Python 的 not a == b ≡ not (a == b) 相反）
!3 == 4          # false：(!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs))，调用后取反
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке и предлагает
соответствующую запись):

```
x && y     # ❌ Удалено, используйте x and y
x || y     # ❌ Удалено, используйте x or y
not x      # ❌ Удалено, используйте !x (not снова становится обычным идентификатором; != не затрагивается)
```

**Обоснование проектирования** (в соответствии с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — это поток управления → ключевое слово; чистая функция — это операция →
   символ**. `and` / `or` изменяют порядок вычисления (правая часть пропускается по необходимости),
   что по своей природе аналогично `if`, и потому используют ключевые слова; `!` выполняет чистое
   отрицание уже вычисленного операнда, что по своей природе аналогично `-` `+`, и потому использует
   символ. Распространение ошибок в YaoXiang использует `?` (§2.11), конфликта с `!` нет.
2. **Тесная привязка устраняет неоднозначность**: `!` визуально «прилегает» к операнду, высокий
   приоритет очевиден; ключевое слово `not` вынуждено отделяться от операнда пробелом, что вызывает
   ментальную неоднозначность относительно того, к чему оно привязано (`not a == b`).
3. **Устранение неоднозначности**: `&` несёт две роли — токен заимствования (`&p` / `&mut p`,
   RFC-009) и побитовое И (SPEC §2.2, приоритет 8). Введение `&&` приведёт к тому, что один символ
   будет нести три значения. `and` / `or` / `!` визуально полностью разделяют три понятия:
   заимствование, побитовая операция, логика.
4. **Прецедент**: Zig (системный язык той же экологической ниши) использует именно комбинацию
   ключевых слов `and` / `or` + символа `!`; Python / Lua / Ada / SQL используют полностью ключевые
   слова (включая `not`); семейство C — полностью символы. YaoXiang выбирает гибрид Zig, получая
   преимущества обоих подходов.
5. **Согласованность с Карри-Ховардом**: тип есть высказывание (см. раздел об изоморфизме выше),
   логические связки в уточняющих типах пишутся как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`), что является естественной формулировкой высказывания; `!` как
   символ унарного отрицания соответствует ¬.

> **Реализация**: `and` / `or` раскрываются на уровне IR в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`); `!` разбирается как унарный с тесной привязкой
> (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Объяснение проектирования синтаксиса: именованная функция по сути является синтаксическим сахаром для лямбды

### Основное понимание

**Именованные функции и лямбда-выражения — это одно и то же!** Единственное различие: именованная
функция даёт лямбде имя.

```yaoxiang
// 这两者本质完全相同
add: (a: Int, b: Int) -> Int = a + b           // 具名函数（推荐）
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // Lambda 形式（完全等价）
```

### Модель синтаксического сахара

```
// 具名函数 = Lambda + 名字
name: (Params) -> ReturnType = body

// 本质上是
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, имена параметров в
заголовке лямбды становятся избыточными и могут быть опущены.

### Правила области видимости параметров

**Параметры затеняют внешние переменные**: область видимости параметров в сигнатуре перекрывает тело
функции; внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // 外层变量

double: (x: Int) -> Int = x * 2  // ✅ 参数 x 覆盖外层 x，结果为 20
```

### Гибкость расположения аннотаций

Аннотации типов могут располагаться в любом из следующих мест; **требуется как минимум одна
аннотация**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ Рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ Допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ Избыточно, но допустимо |

### Полные примеры

```yaoxiang
// ✅ 推荐：签名完整，Lambda 头部省略
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ 合法：Lambda 头中标注类型
double = (x: Int) => x * 2

// ✅ 合法：两边都标注
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества проектирования

| Свойство        | Преимущество                                                                   |
| --------------- | ------------------------------------------------------------------------------ |
| **Простота**    | При полной сигнатуре нет необходимости повторять имена параметров              |
| **Гибкость**    | Сохранена лямбда-форма — используйте то, что нравится                          |
| **Единство**    | Согласуется с объявлением переменной `x: Int = 42`                             |
| **Наглядность** | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### BNF-грамматика

```bnf
program ::= statement*

statement ::= declaration | expression

# 统一声明：name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# 类型表达式
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # 类型应用
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # 函数类型
       | '{' type_field* '}'                       # 记录/接口类型
       | 'Type'                                    # 元类型

type_field ::= identifier ':' type_expr
             | identifier                           # 接口约束

# 泛型参数：作为函数类型的一部分，如 (T: Type, R: Type) -> (...)
# 无需独立的 BNF 规则——: Type 参数就是普通函数参数

# 表达式
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # 函数调用 / 构造器调用
              | '(' expression (',' expression)* ')'              # 元组
              | expression '.' identifier '(' arguments? ')'    # 方法调用
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                      | Определение                                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Объявление                  | Оператор присваивания в форме `name: type = value`                                                                    |
| Тип записи                  | Тип `{ ... }` с именованными полями                                                                                   |
| Интерфейс                   | Тип записи, все поля которого являются функциональными типами                                                         |
| Обобщённый тип              | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                 |
| Функция в пространстве имён | Функция формы `Type.name`, принадлежащая пространству имён Type. Не подразумевает никакой привязки                    |
| Привязка метода             | `Type.name = func[n]`, привязывает позицию n функции func как вызывающего, делая доступным синтаксис `obj.name(args)` |
| Обобщённая функция          | Функция, использующая синтаксис `(T: Type)`, параметры типа как первая группа параметров                              |
| Метатип                     | `Type`, единственный маркер иерархии типов в языке                                                                    |
