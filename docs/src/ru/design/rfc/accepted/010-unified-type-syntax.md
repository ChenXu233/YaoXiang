# RFC-010: Унифицированный синтаксис типов - модель name: type = value

## Аннотация

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

YaoXiang имеет только одну форму объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
как ключевое слово meta type)**.

> **Ключевая идея проектирования**: `Type` сам по себе является родовым типом. `(T: Type) -> Type`
> означает «тип, принимающий параметр типа T».

| Концепция       | Запись кода                                                                  |
| --------------- | ---------------------------------------------------------------------------- |
| Переменная      | `x: Int = 42`                                                                |
| Функция         | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| record type     | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс       | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Родовой тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Родовой тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод           | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Родовая функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово meta type в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` означает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.`, такой как `p.draw(screen)`, работал, необходима явная привязка:
> `Point.draw = draw[0]`. Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он
> используется для обозначения уровня типа; компилятор автоматически обрабатывает различие между
> Type0, Type1, Type2... прозрачно для пользователя.

```yaoxiang
// 核心语法：统一 + 区分

// 变量
x: Int = 42

// 函数（参数名在签名中）
add: (a: Int, b: Int) -> Int = a + b

// 记录类型
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// 接口（本质是字段全为函数的记录类型）
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// 方法定义（使用 Type.method 语法）
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    "Point(${self.x}, ${self.y})"
}

// 泛型类型（(T: Type) -> Type = 接受类型参数的泛型类型）
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// 使用
p: Point = Point(1.0, 2.0)
p.draw(screen)           // 语法糖 → Point.draw(p, screen)
s: Drawable = p           // 结构子类型：Point 实现 Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая type system содержит несколько разрозненных концепций:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (различный синтаксис)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Этим концепциям не хватает единства, что приводит к фрагментации синтаксиса и высокой стоимости
обучения.

### Цели проектирования

1. **Предельная унификация**: одно правило синтаксиса покрывает все случаи
2. **Простота и элегантность**: симметричная эстетика `name: type = value`
3. **Никаких новых ключевых слов**: повторное использование существующих элементов синтаксиса
4. **Теоретическая элегантность**: сам тип также является значением типа Type
5. **Generics-дружественность**: бесшовная интеграция с системой generics (RFC-011)

### Интеграция с системой generics

Унифицированная синтаксическая модель RFC-010 и система generics из RFC-011 **природно совместимы**:
параметры generics органично вписываются в унифицированную модель:

```yaoxiang
// 基础泛型（RFC-011 Phase 1）
List: (T: Type) -> Type = { data: Array(T), length: Int }

// 泛型函数（RFC-023 语法：签名中 Type 位置可省略，调用时自动推断）
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// 类型约束（RFC-011 Phase 2）
clone: (value: T) -> T = value.clone()  // T: Clone 约束由参数类型携带

// Const泛型（RFC-011 Phase 4）
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовая generics) является **сильной зависимостью** RFC-010
- Без базовой generics примеры generics из RFC-010 не смогут скомпилироваться
- Рекомендация: реализовывать RFC-011 Phase 1 синхронно с RFC-010

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор проектирования, определяющий правила разрешения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                                  |
| ------------------- | ---------------------- | -------------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | `: Type` явное объявление → принудительно тип            |
| **`f = ...`**       | Функция или переменная | Без `: Type` → HM активно выводит как функцию/переменную |

**Почему именно так?**

Сам синтаксис `{ ... }` неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (record type)
- `{ a = 1 + 1 }` может быть **блоком кода** (выполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — literal типа
- **Нет** `: Type` → HM активно интерпретирует `{ ... }` как блок кода, выводит как тип функции

```yaoxiang
# ✅ 类型构造器：有 : Type
Point: Type = { x: Float, y: Float }

# ✅ 函数：没有 : Type，HM 推断为 () -> Void
main: () -> Void = { println("Hello") }

# ❌ 错误：没有 : Type，编译器无法将 { ... } 解析为类型
Point = { x: Float, y: Float }  // HM 推断为函数，不是类型！
```

---

**Унифицированная модель: identifier : type = expression**

```
├── 变量
│   └── x: Int = 42
│
├── 函数
│   └── add: (a: Int, b: Int) -> Int = a + b  # 无 : Type，HM 推断为函数
│
├── 记录类型
│   └── Point: Type = { x: Float, y: Float }  # 必须返回： Type
│
├── 接口
│   └── Drawable: Type = { draw: (Surface) -> Void }  # 必须返回： Type
│
├── 泛型类型
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # 必须返回： Type
│
├── 泛型类型（多参数）
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # 必须返回： Type
│
├── 命名空间函数
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # 显式绑定后才有点调用语法
│
└── 泛型函数
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # 不返回 Type，HM 推断为函数
```

### Иерархия метатипов (внутреннее устройство компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Level    | Описание                               |
| -------- | -------------------------------------- |
| `Type0`  | Обычные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)   |
| `Type2+` | Конструкторы высшего порядка           |

**Пользователь никогда не видит эти числа**, он видит только `: Type`.

### Изоморфизм Карри-Ховарда: типы как утверждения, программы как доказательства

Унифицированный синтаксис `name: type = value` в YaoXiang выбран не произвольно — он является прямым
отображением изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм раскрывает
глубокий факт: **type system и логическая система — это две стороны одной и той же сущности**.

| Логика (утверждение)          | Type system (YaoXiang)             | Пример                               |
| ----------------------------- | ---------------------------------- | ------------------------------------ |
| Утверждение P                 | Тип T                              | `Int`, `Bool`                        |
| Доказательство истинности P   | Значение типа T                    | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | function type `(P) -> Q`           | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | record type `{ p: P, q: Q }`       | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Родовая функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | enum / tagged union                | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в рамках Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int, с именем x, со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: дано доказательство a и b типа Int, можно построить доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — это утверждение, доказательство которого должно одновременно предоставить доказательства x и y типа Float"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая согласованность = типобезопасность**: если type system позволяет сконструировать
   значение типа `T` без какого-либо легитимного runtime представления, это подобно тому, как в
   логике разрешают доказать ложное утверждение — система рушится. Карри-Ховард говорит нам:
   **типобезопасный язык по своей природе является логически согласованной системой**.

2. **Иерархия вселенных — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (то есть «тип типа также является типом»), возникает парадокс Рассела (в теории
   типов проявляющийся как парадокс Жирара). Расслоение в YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   гарантирует, что каждый тип принадлежит строго определённому уровню, формируя незамкнутую
   восходящую цепочку, что фундаментально устраняет парадоксы. Это означает, что type system
   YaoXiang в смысле Карри-Ховарда является **логически согласованной**.

3. **Теоретическая основа унифицированного синтаксиса**: `name: type = value` способен покрыть одним
   синтаксисом переменные, функции, типы, интерфейсы и generics именно потому, что в рамках
   Карри-Ховарда всё это — **предоставление доказательства для утверждения**. Переменная —
   свидетельство утверждения, функция — свидетельство импликации, record — свидетельство конъюнкции,
   generics — свидетельство квантора всеобщности. Унифицированный синтаксис — не искусственно
   сконструированное совпадение, а естественное следствие изоморфизма Карри-Ховарда.

> **Дополнительная литература**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступным языком объясняет историю и значение изоморфизма
> Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменной

```yaoxiang
// 基本语法
x: Int = 42
name: String = "Alice"
flag: Bool = true

// 类型推导（可省略）
y = 100  // 推断为 Int
```

#### 2. Определение функции

**Значение блока = хвостовое выражение, `return` выходит из функции (тип `Never`)** — подробности
см. в [RFC-010a](010a-tail-expression-and-return.md).

```yaoxiang
// 单表达式形式
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// 代码块形式：值是尾表达式
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b                    // 尾表达式 → 块的值
}

// 多行代码块
calc: (x: Float, y: Float, op: String) -> Float = {
    match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }                    // match 作尾表达式
}

// Void 函数：尾表达式为 Void
print: (msg: String) -> Void = {
    console.write(msg)   // console.write : Void
}
```

#### Правила возврата

**Значение блока = хвостовое выражение (единственный выход)**:

| Запись                                             | Значение                                |
| -------------------------------------------------- | --------------------------------------- |
| `= expr` (без фигурных скобок)                     | `expr`                                  |
| `= { ...; e }` (с фигурными скобками)              | Хвостовое выражение `e`                 |
| `= { ...; s }` (последний — оператор/присваивание) | `Void` (значение присваивания — `Void`) |
| `= {}` (пустой блок)                               | `Void`                                  |

**Семантика `return`**: нелокальный выход, **выходящий за границу ближайшей функции** (не «возврат в
блок»), тип `Never`. `Never <: T` справедливо для любого типа (принцип взрыва), поэтому `return`
может появляться в любой позиции возврата.

```yaoxiang
# 单表达式：直接返回值
add: (a: Int, b: Int) -> Int = a + b

# 代码块：值是尾表达式
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b
}

# 提前返回：return 穿透块，退出函数（类型 Never）
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    n * factorial(n - 1)     # 尾表达式
}
```

**Обоснование проектирования**: `{ ... }` — это управляемая зависимостями вычислительная единица
(см. ниже), семантика вычисления которой отличается от одиночного выражения — фигурные скобки вводят
контекст с несколькими операторами, **значение задаётся хвостовым выражением**, и неоднозначность в
духе «является ли последнее выражение возвращаемым значением» не возникает.

#### Семантика `{}`: управляемая зависимостями вычислительная единица

`{ ... }` в YaoXiang — не просто блок кода — это **управляемая зависимостями вычислительная
единица**. Эта семантика остаётся единообразной в телах функций, инициализации переменных и `spawn`:

**Ключевые правила**:

- Операторы присваивания внутри `{}` автоматически упорядочиваются по зависимостям, а не по порядку
  записи
- Когда зависимости удовлетворены — выполнение происходит немедленно, иначе — блокировка и ожидание
- **Значение блока = хвостовое выражение** (см. правила возврата); `return` — нелокальный выход типа
  `Never`, выходящий из функции

```yaoxiang
# 依赖驱动：b 依赖 a，编译器自动排序
result: Int = {
    b = a + 1      # 依赖 a → 自动排在 a 之后
    a = 10         # 无依赖 → 可以先执行
    b              # 尾表达式 → 块的值 11
}
```

> **Отличие от одиночного выражения**: `= expr` (без фигурных скобок) — простое связывание, напрямую
> возвращающее значение; `= { ... }` (с фигурными скобками) вводит контекст управляемых
> зависимостями вычислений, допускающий несколько операторов; значение задаётся хвостовым
> выражением.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитив YaoXiang. Она использует семантику `{}` с
управлением по зависимостям для автоматического распараллеливания:

- Непосредственные подприсваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- Задачи с удовлетворёнными зависимостями немедленно выполняются конкурентно
- Вызывающая сторона блокируется до завершения всех подзадач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # 任务 1
    b = fetch_data("url2")    # 任务 2（与 a 无依赖，并行执行）
    c = process(a, b)         # 依赖 a, b → 等待两者完成后执行
    c                         # 尾表达式 → spawn 的值
}
// 调用方在此阻塞，直到 spawn 块内所有任务完成
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> описаны в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций с сырыми указателями. Он
использует семантику вычисления `{}`, чтобы передать определение типа во внешнюю область (значение
выхода — хвостовое выражение):

**Ключевые правила**:

- В `unsafe {}` можно определять типы и оперировать сырыми указателями
- **Хвостовое выражение** задаёт значение `unsafe {}` (определение типа передаётся во внешнюю
  область)
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует полномочий unsafe

```yaoxiang
# 在 unsafe 块中定义不透明类型
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # 裸指针
    }
    SqliteDb           # 尾表达式 → unsafe 块的值
}

# SqliteDb 在 unsafe 块外可用
db = sqlite3_open("test.db")

# ❌ 编译错误：handle 字段需要 unsafe 权限
handle = db.handle

# ✅ 通过方法调用
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определения FFI-типов и привязки методов
> описаны в `ffi.md`.

#### 3. Определение типа

Определение типа — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализацию интерфейсов:

##### Базовые типы

**Record type**: список полей; типы полей могут быть любыми выражениями типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию и быть необязательными
при конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang трёхуровневая, и каждый уровень распознаётся соответствующей фазой
компилятора:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявления, такие как `if`, `match`, `pub`, `return`
2. **Зарезервированные литералы** (отдельные токены парсера) — `true`, `false`, `void`, `Type`, не
   могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные проверщиком типов) — парсер
   воспринимает как обычные идентификаторы, их разбором занимается проверщик типов. **Не являются
   зарезервированными словами и могут быть затенены (не рекомендуется)**

Отличие `void` (в нижнем регистре, зарезервированный literal) от `Void` (в верхнем регистре, имя
встроенного типа): `void` — это литерал значения (равен единственному значению Unit), `Void` — имя
типа (равен типу Unit, логически ⊤). `let x: Void = void` — допустимо.

Предопределённые имена встроенных типов:

| Тип      | Логический аналог   | Описание                                                                                                                                                                                                                                                                                                    |
| -------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Ноль конструкторов, ни одно значение не может населять этот тип. Означает «невозможно» — расходимость, паника, недостижимый код. `Never <: T` справедливо для любого `T` (принцип взрыва). Функция, возвращающая `Never`, никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (значение `void` по умолчанию). `x: Void = <по умолчанию>` допустимо. Тождественный элемент суммы, соответствующий тождественному элементу произведения — `Void` — это record type с нулём полей (Unit), `Never` — сумма типов с нулём вариантов.                                      |
| `Int`    | —                   | Целое число со знаком                                                                                                                                                                                                                                                                                       |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                                    |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                                       |
| `Char`   | —                   | Unicode-символ                                                                                                                                                                                                                                                                                              |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                                      |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // 绑定到位置0，柯里化后 method: (b: Point) -> Float
}
// 调用：p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        (dx * dx + dy * dy).sqrt()      # 尾表达式

}
// 语法：((params) => body)[position]
// 调用：p1.distance(p2) → distance(p1, p2)

**Префикс `Type.name` означает принадлежность к пространству имён**, и ничего более. Он не вызывает
никакой неявной привязки.

// 命名空间函数：在 Point 命名空间下的普通函数

}

Point.serialize: (p: &Point) -> String = {

// 调用：就是普通函数调用
Point.draw(p, screen)
Point.serialize(p)
```

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.`, такой как `p.draw(screen)`, работал, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм, делающий функцию «методом» (подробный
синтаксис см. в RFC-004).

```yaoxiang
// 定义函数
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// 显式绑定 — 这之后才有 p.draw(screen) 语法
Point.draw = draw[0]   // 位置 0 的参数（&Point）由调用者填充

// 使用
p.draw(screen)          // 语法糖 → draw(&p, screen)
Point.draw(p, screen)   // 两种调用方式等价

// 不写 [0] = 不绑定。Point.draw 就是普通函数别名，没有 . 语法
Point.draw = draw       // 不绑定：只能 Point.draw(p, screen)
```

**Поведение по умолчанию**: не указан `[n]` = ни один параметр не привязывается. Пользователь должен
явно решить, какие параметры будут заполняться вызывающей стороной.

**Привязка нескольких позиций**:

```yaoxiang
// 绑定多个位置（自动柯里化）
Point.transform = transform_points[0, 1]
// 调用：p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// 从绑定中取出函数
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Родовые типы

```yaoxiang
// 基础泛型（RFC-011 Phase 1）
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// 具体实例化（RFC-023 语法）
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // 调用示例

// 泛型方法（RFC-023 语法：类型参数由调用处自动推断）
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        Maybe.Just(self.data[index])
    } else {
        Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова generics

Вызов как родовых типов, так и родовых функций унифицированно использует синтаксис `()`. `[]` нигде
в контексте generics не используется.

**Ключевые правила**:

1. **`()` для всего**: применение типов, вызов функций, конструирование значений — всё через `()`

```yaoxiang
# 类型标注
numbers: List(Int) = List(1, 2, 3)

# 空容器：T 从左侧来
empty: List(Int) = List()

# 泛型函数调用——类型从参数自动流动
strings = map(numbers, f)
// T=Int 来自 numbers: List(Int)
// R=String 来自 f: (Int) -> String
```

2. **Тип слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. T пустого контейнера `List()` должен браться из аннотации типа слева.

3. **Информация о типе пишется только один раз** — в объявлении параметра, и компилятор
   «протаскивает» её дальше:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int 在左边写一次
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String 自动从 numbers 和 f 的类型来
```

4. **Конструирование значения — тип выводится из элементов**:

```yaoxiang
x = List(1, 2, 3)       // 推断为 List(Int)
y = List("a", "b")      // 推断为 List(String)
z = List()              // ❌ 编译错误：无法推断 T
z: List(Int) = List()   // ✅ T=Int 来自左侧注解
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис generics с `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

## Подробное проектирование

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // 对于接口的每个字段（函数字段）
    for (field_name, iface_field) in &iface.fields {
        // 检查类型是否有同名方法
        if let Some(method) = typ.methods.get(field_name) {
            // 检查方法签名是否兼容
            // 接口字段: (Surface) -> Void
            // 方法签名: (Point, Surface) -> Void
            // 比较：去掉 self 参数后应该匹配
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации на этапе компиляции

Тип интерфейса поддерживает прямое присваивание, и компилятор автоматически выбирает оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// 直接赋值具体类型 → 编译期可确定具体类型，零开销调用
d: Drawable = Circle(1)
d.draw(screen)  // 编译后：直接调用 circle_draw(screen)，无 vtable

// 函数返回值 → 编译期无法确定具体类型，使用 vtable
d: Drawable = get_shape()
d.draw(screen)  // 通过 vtable 查找方法

// 异构集合 → 使用 vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // 通过 vtable 查找方法
}
```

**Стратегии оптимизации на этапе компиляции**:

| Сценарий                         | Результат вывода типа | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                   |

**Правила**:

1. Когда правая часть — конкретный конструктор типа, известный на этапе компиляции, генерируется IR
   с прямым вызовом
2. Когда тип правой части нельзя определить на этапе компиляции, выполняется откат на механизм
   vtable
3. Резервный vtable гарантирует корректность runtime-полиморфизма

| До                                       | После                                                                                        |

### Устарело: синтаксис вариантов `|`

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов с `|` официально устарел и удалён
> из реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ 废弃
type Result(T, E) = ok(T) | err(E)             # ❌ 废弃
type Option(T) = some(T) | none                # ❌ 废弃
```

Унифицированно используйте record type для выражения и типа (sum type). Когда все поля record type —
функции, и все они возвращают сам этот тип, то это и есть sum type:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование проектирования**:

1. **Устранение частного случая**: `|` — единственный синтаксис в BNF, не укладывающийся в форму
   `name: type = value`. После удаления продукция `type_expr` становится полностью единообразной, и
   парсеру больше не нужно поддерживать отдельный путь и возвраты с предпросмотром для типов
   вариантов.
2. **Математическая эквивалентность**: в рамках изоморфизма Карри-Ховарда дизъюнкции P ⊕ Q
   соответствует sum type, эквивалентный record type, у которого все поля — функции, возвращающие
   сам тип. Семантика одна и та же — зачем иметь два синтаксиса?
3. **Нулевая разрушительность**: до удаления синтаксис `|` в парсере поддерживался лишь частично
   (варианты без параметров разбирались, но типы параметров терялись при мономорфизации); никакой
   пользовательский код на него не полагался.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы идут по пути
   `Type::Struct`, специальные ветки в нижестоящих typecheck/mono/formatter полностью устранены.

> **Примечание**: семантические свойства sum type (конструирование вариантов, проверка полноты
> pattern matching, расположение tagged union в памяти) выводятся проверщиком типов из структуры
> `Type::Struct` и не зависят от отдельного узла AST. Полная семантика конструирования вариантов
> описана ниже в разделе «Конструирование вариантов record-подобного sum type (авторитетное
> определение)».

### Конструирование вариантов record-подобного sum type (авторитетное определение)

> Данный раздел разворачивает критерии распознавания из раздела «Устарело: синтаксис вариантов `|`»
> в полную семантику (утверждено 2026-09-25, прелюдия к issue #341, этап 2 RFC-011b). Четыре
> решения: вызов с квалификацией типа, форма вызова для вариантов с нулевой нагрузкой,
> самообеспеченность вывода типа, безоговорочное повышение имён вариантов.

#### Правило распознавания: всё или ничего

Record type считается **sum type**, если выполнены оба условия:

1. Все типы полей в теле типа — функциональные типы;
2. Возвращаемый тип каждого поля после подстановки параметров типа (`Self`/аргументы generics)
   совпадает с самим этим record type.

Распознавание — **всё или ничего**: при выполнении все функциональные поля одновременно повышаются
до конструкторов вариантов; при невыполнении весь тип — обычная record type (функциональные поля —
это поля данных, хранящие значения функций), и не существует «частично вариантного, частично
data»-гибридной формы. Когда нужно одновременно нести данные и вариантную семантику, моделируйте как
record с данными и sum type как два отдельных типа, не объединяйте в одно объявление.

#### Форма вызова: квалификация типом, без голого имени

**Единственная** форма вызова конструктора варианта — вызов с квалификацией типа: взятие члена
варианта на значении типа с последующим вызовом:

```yaoxiang
r1 = Result(Int, String).ok(5)   // Result(Int, String)，载荷 5
c  = Color.red()                 // 零载荷变体：与字段签名一致的函数调用形态
```

**Голую форму не предоставляем** (`ok(5)` — не вызов конструктора). Причина: голое имя зависит от
обратного вывода ожидаемого типа в контексте, чтобы определить принадлежность к sum type и аргументы
типа, тогда как в этом языке тип должен быть явно записываемым, а вывод течёт однонаправленно из
позиции ожидания (та же дисциплина, что и в RFC-011a «Self — явный параметр типа, без магии»). В
квалифицированной форме тип полностью самообеспечен и не зависит от контекста. Если в будущем будет
введена голая форма, она может быть только «сахаром раскрытия, когда контекст однозначно определим»,
а семантическим базисом останется квалифицированная форма из данного раздела.

#### Вывод: самообеспеченность типа

Когда квалифицированное имя задаёт полные аргументы типа, сигнатура конструктора варианта — это
**сигнатура поля после подстановки аргументов типа**:

```yaoxiang
Result(Int, String).ok   // : (Int) -> Result(Int, String)
```

Проверка типа нагрузки — это обычная проверка аргументов вызова функции (несоответствие даёт E1002),
без новых правил вывода. Конструкторы родовых sum type естественно мономорфизируются при
инстанцировании типа, без отдельного механизма.

#### Повышение полей: имена вариантов — не поля данных

После распознавания как sum type имена вариантов удаляются из пространства полей данных — доступ к
полю варианта **значения** sum type отвергается на этапе компиляции:

```yaoxiang
r1.ok    // 编译错误：ok 是 Result 的变体构造器，不是数据字段
```

Причина: значение sum type в runtime — это tagged union (см. ниже), не несущий таблицу объявления
вариантов; разрешение доступа к полю неизбежно тихо исказит смысл. Это продолжение той же
дисциплины, что и RFC-011a §1.2 (единое пространство имён полей/методов, конфликт → ошибка).
Конструирование — через квалификацию типа (`Result.ok`); использование — через деструкцию в `match`
(RFC-010b).

#### Runtime-представление и равенство

Runtime-представление значения sum type — это tagged union:
`Enum { тип_identity, variant_id, payload }`.

- **Тип_identity** несёт конкретный sum type (не глобальный плейсхолдер) — значения разных sum type
  несравнимы;
- **variant_id** нумерует варианты в **порядке объявления** в теле типа; этот же порядок является
  входными данными для проверки полноты в RFC-010b;
- **Равенство** (`==`/`!=`): тип_identity совпадает, variant_id совпадает, payload поэлементно равен
  (рекурсивно).

#### Миграция std

`std.result` переходит на использование механизма данного раздела для определения `ok` / `err`
(нативные `result_ok` / `result_err` уходят в отставку), конструирование вариантов в `std` идёт по
тому же набору правил, что и пользовательские sum type, без привилегированного канала. Демонтаж
специальных проверок `Result` / `Option` в парсере на позиции типа и специальной проверки
`make_result` по имени берёт на себя [RFC-011b](./011b-operator-overloading.md) этап 2 — после
интерфейсизации `?` `Result` становится обычным sum type из std.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: авторитетная форма логических операторов — ключевые слова
> `and` / `or` + символьный унарный `!` (согласуется с таблицей приоритетов `syntax.md` §2.2 в
> SPEC). Данное проектирование выровнено с Zig: **короткое замыкание, управляющее потоком, —
> ключевые слова; чистая унарная операция — символ**. Ранние реализации, дрейфовавшие к C с `&&` /
> `||`, а также промежуточное ключевое слово `not`, были удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                   | Ассоциативность | Семантика                                                    |
| -------- | --------------------------------------- | --------------- | ------------------------------------------------------------ |
| `!`      | 3 (унарный префикс, плотное связывание) | справа налево   | Логическое отрицание (чистая функция, без потока управления) |
| `and`    | 10                                      | слева направо   | Короткое замыкание, логическое И                             |
| `or`     | 10                                      | слева направо   | Короткое замыкание, логическое ИЛИ                           |

```yaoxiang
# 短路求值：and 左侧为 false / or 左侧为 true 时，右侧不执行
if x != 0 and y / x > 1 { ... }   # x == 0 时不会除零

# 紧绑定：!a == b ≡ (!a) == b（Zig 式；与 Python 的 not a == b ≡ not (a == b) 相反）
!3 == 4          # false：(!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs))，调用后取反
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке и подсказывает
соответствующую форму):

```
x && y     # ❌ 已移除，用 x and y
x || y     # ❌ 已移除，用 x or y
not x      # ❌ 已移除，用 !x（not 恢复为普通标识符；!= 不受影响）
```

**Обоснование проектирования** (выровнено с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — поток управления → ключевое слово; чистая функция — операция → символ**.
   `and` / `or` изменяют порядок вычисления (правая сторона пропускается при необходимости), по
   природе схожи с `if` — значит ключевое слово; `!` выполняет чистое отрицание уже вычисленного
   операнда, по природе схоже с `-` `+` — значит символ. В YaoXiang error propagation использует `?`
   (§2.11), конфликта с `!` нет.
2. **Плотное связывание снимает неоднозначность**: визуально `!` «прилеплен» к операнду, высокий
   приоритет очевиден; ключевое слово `not` вынужденно отделяется пробелом от операнда, и к чему оно
   привязано (`not a == b`) легко вызывает мысленную неоднозначность.
3. **Устранение перегрузки**: `&` несёт две роли — токен заимствования (`&p` / `&mut p`, RFC-009) и
   побитовое И (SPEC §2.2, приоритет 8). Введение `&&` нагрузило бы один символ тремя значениями.
   `and` / `or` / `!` визуально полностью разделяют три концепции: заимствование, побитовые
   операции, логика.
4. **Прецедент**: Zig (современный системный язык того же экологического ниши) использует именно
   комбинацию ключевых слов `and` / `or` + символа `!`; Python / Lua / Ada / SQL используют
   полностью ключевые слова (включая `not`); семейство C — полностью символы. YaoXiang берёт гибрид
   Zig, получая преимущества обоих подходов.
5. **Согласованность с Карри-Ховардом**: типы как утверждения (см. раздел об изоморфизме выше),
   логические связки в уточняющих типах записываются как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`) — это естественная формулировка утверждений; унарное отрицание
   `!` соответствует символу ¬.

> **Реализация**: `and` / `or` на уровне IR раскрываются в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`); `!` разбирается как унарный с плотным
> связыванием (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Пояснение к дизайну синтаксиса: именованные функции по сути являются синтаксическим сахаром для лямбда-выражений

### Ключевое понимание

**Именованная функция и лямбда-выражение — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// 这两者本质完全相同
add: (a: Int, b: Int) -> Int = a + b           // 具名函数（推荐）
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // Lambda 形式（完全等价）
```

### Модель синтаксического сахара

```
// 具名函数 = Lambda + 名字
name: (Params) -> ReturnType = body

// 本质上是
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, заголовок лямбды с именами
параметров становится избыточным и может быть опущен.

### Правила области видимости параметров

**Параметр затеняет внешнюю переменную**: параметр в сигнатуре затеняет переменную из внешней
области видимости; внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // 外层变量

double: (x: Int) -> Int = x * 2  // ✅ 参数 x 覆盖外层 x，结果为 20
```

### Гибкое расположение аннотаций

Аннотации типов можно размещать в любой из следующих позиций — **достаточно аннотировать хотя бы в
одном месте**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ Рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ Допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ Избыточно, но разрешено |

### Полные примеры

```yaoxiang
// ✅ 推荐：签名完整，Lambda 头部省略
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ 合法：Lambda 头中标注类型
double = (x: Int) => x * 2

// ✅ 合法：两边都标注
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества проектирования

| Свойство            | Преимущество                                                                   |
| ------------------- | ------------------------------------------------------------------------------ |
| **Краткость**       | При полной сигнатуре не нужно повторять имена параметров                       |
| **Гибкость**        | Сохранена лямбда-форма; используйте ту, которая нравится                       |
| **Согласованность** | Та же модель, что и объявление переменной `x: Int = 42`                        |
| **Интуитивность**   | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### Синтаксис BNF

```bnf
program ::= statement*

statement ::= declaration | expression

# 统一声明：name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# 类型表达式
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # 类型应用
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # 函数类型
       | '{' type_field* '}'                       # 记录/接口类型
       | 'Type'                                    # 元类型

type_field ::= identifier ':' type_expr
             | identifier                           # 接口约束

# 泛型参数：作为函数类型的一部分，如 (T: Type, R: Type) -> (...)
# 无需独立的 BNF 规则——: Type 参数就是普通函数参数

# 表达式
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # 函数调用 / 构造器调用
              | '(' expression (',' expression)* ')'              # 元组
              | expression '.' identifier '(' arguments? ')'    # 方法调用
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                      | Определение                                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Объявление (declaration)    | Оператор присваивания формы `name: type = value`                                                                               |
| record type                 | Тип `{ ... }` с именованными полями                                                                                            |
| Интерфейс                   | record type, все поля которого — функциональные типы                                                                           |
| Родовой тип                 | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                          |
| Функция в пространстве имён | Функция формы `Type.name`, принадлежащая пространству имён Type. Не подразумевает никакой привязки                             |
| Привязка метода             | `Type.name = func[n]`: привязывает позицию n функции `func` как вызывающую сторону, делая доступным синтаксис `obj.name(args)` |
| Родовая функция             | Функция с синтаксисом `(T: Type)`, в которой параметры типа являются первой группой параметров                                 |
| meta type                   | `Type` — единственный маркер уровня типа в языке                                                                               |
