# RFC-010: Унифицированный синтаксис типов — модель name: type = value

## Резюме

Данный RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует лишь одна форма объявления:

```
identifier : type = expression
```

где `type` может быть произвольным выражением типа, а `expression` — произвольным выражением
значения. **Нет `fn`, нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем
регистре (но есть `Type` как ключевое слово метатипа)**.

> **Ключевой принцип проектирования**: `Type` сам по себе является генерик-типом.
> `(T: Type) -> Type` означает «тип, принимающий параметр-тип T».

| Концепция       | Запись в коде                                                                |
| --------------- | ---------------------------------------------------------------------------- |
| Переменная      | `x: Int = 42`                                                                |
| Функция         | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи      | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс       | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Генерик-тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Генерик-тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод           | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Генерик-функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово метатипа в языке**.

> **Пространство имён vs. привязка метода**: префикс `Type.name` обозначает **принадлежность к
> пространству имён**, и ничего более. Он не запускает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` вроде `p.draw(screen)` работал, необходима явная привязка:
> `Point.draw = draw[0]`. Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он
> используется для разметки уровней типов; компилятор автоматически обрабатывает различие Type0,
> Type1, Type2... — это прозрачно для пользователя.

```yaoxiang
// Основной синтаксис: унификация + различие

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Тип записи
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути — тип записи, все поля которого — функции)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (с использованием синтаксиса Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    "Point(${self.x}, ${self.y})"
}

// Генерик-тип ((T: Type) -> Type = генерик-тип, принимающий параметр-тип)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурное подтипирование: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Существующая система типов содержит несколько разрозненных концепций:

- синтаксис объявления переменных
- синтаксис определения функций
- синтаксис определения типов (другой синтаксис)
- синтаксис определения интерфейсов
- синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельная унификация**: одно синтаксическое правило покрывает все случаи
2. **Краткость и элегантность**: симметричная эстетика `name: type = value`
3. **Никаких новых ключевых слов**: повторное использование существующих синтаксических элементов
4. **Теоретическая элегантность**: сам тип является значением типа Type
5. **Генерик-дружественность**: бесшовная интеграция с системой generics (RFC-011)

### Интеграция с системой generics

Унифицированная синтаксическая модель RFC-010 **естественно согласуется** с дизайном системы
generics в RFC-011: параметры типов бесшовно вписываются в унифицированную модель:

```yaoxiang
// Базовые generics (RFC-011, фаза 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Генерик-функция (синтаксис RFC-023: Type в сигнатуре можно опускать, вывод при вызове)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничения типа (RFC-011, фаза 2)
clone: (value: T) -> T = value.clone()  // ограничение T: Clone переносится через тип параметра

// Const-генерики (RFC-011, фаза 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- Фаза 1 RFC-011 (базовые generics) — **сильная зависимость** для RFC-010
- Без базовых generics примеры generics из RFC-010 не скомпилируются
- Рекомендация: реализовывать фазу 1 RFC-011 и RFC-010 синхронно

## Предложение

### Ключевой принцип: конструктор типа vs. функция/переменная

**Это ключевой выбор проектирования, определяющий правила устранения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                                      |
| ------------------- | ---------------------- | ------------------------------------------------------------ |
| **`x: Type = ...`** | Конструктор типа       | явное объявление `: Type` → принудительно трактуется как тип |
| **`f = ...`**       | Функция или переменная | без `: Type` → HM активно выводит как функцию/переменную     |

**Почему такое решение?**

Синтаксис `{ ... }` сам по себе неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий Void)

**Правило устранения неоднозначности**:

- **Есть** `: Type` → принудительно разбирать как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM активно разбирает `{ ... }` как блок кода, выводит тип функции

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит как () -> Void
main: () -> Void = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может разобрать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит как функцию, а не тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # без : Type, HM выводит как функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # должен возвращать: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # должен возвращать: Type
│
├── Генерик-тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # должен возвращать: Type
│
├── Генерик-тип (много параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # должен возвращать: Type
│
├── Функция в пространстве имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # только после явной привязки доступен синтаксис через точку
│
└── Генерик-функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # не возвращает Type, HM выводит как функцию
```

### Уровни метатипов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенных `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Уровень  | Описание                               |
| -------- | -------------------------------------- |
| `Type0`  | Обычные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)   |
| `Type2+` | Конструкторы высшего порядка           |

**Пользователь никогда не видит этих чисел**, только `: Type`.

### Соответствие Карри–Ховарда: тип есть высказывание, программа есть доказательство

Унифицированный синтаксис YaoXiang `name: type = value` выбран не произвольно — он представляет
собой прямое отображение соответствия Карри–Ховарда. Это соответствие раскрывает глубокий факт:
**система типов и логическая система — это две стороны одной сущности**.

| Логика (высказывание)                 | Система типов (YaoXiang)           | Пример                               |
| ------------------------------------- | ---------------------------------- | ------------------------------------ |
| Высказывание P                        | Тип T                              | `Int`, `Bool`                        |
| Доказательство P                      | Значение типа T                    | `42: Int`, `true: Bool`              |
| P → Q (импликация)                    | Тип функции `(P) -> Q`             | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)                    | Тип записи `{ p: P, q: Q }`        | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (универсальная квантификация) | Генерик-функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)                    | Перечисление / tagged union        | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в свете Карри–Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int по имени x со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: даны доказательства Int a и b, можно сконструировать доказательство Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — высказывание, доказательство которого требует одновременного предъявления доказательств Float x и Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = безопасность типов**: если система типов позволяет
   сконструировать значение типа `T` без какого-либо легитимного представления во время выполнения,
   это подобно доказательству ложного высказывания в логике — система рушится. Карри–Ховард говорит
   нам: **язык с безопасной системой типов по своей сути является логически непротиворечивой
   системой**.

2. **Иерархия вселенных — необходимое условие**: как подробно описано ниже, разрешение `Type: Type`
   (т.е. «типом типа является тип») привело бы к парадоксу Рассела (в теории типов проявляющемуся
   как парадокс Жирара). Многоуровневая структура YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   обеспечивает, что каждый тип принадлежит определённому уровню, образуя никогда не замыкающуюся
   восходящую цепочку, что фундаментально избегает парадоксов. Это означает, что система типов
   YaoXiang **логически непротиворечива** в смысле Карри–Ховарда.

3. **Теоретическое обоснование унифицированного синтаксиса**: `name: type = value` способен одним
   синтаксисом покрыть переменные, функции, типы, интерфейсы и generics именно потому, что в свете
   Карри–Ховарда все они — одно и то же: **предоставление доказательства высказывания**. Переменная
   — свидетельство высказывания, функция — свидетельство импликации, запись — свидетельство
   конъюнкции, генерик — свидетельство универсальной квантификации. Унифицированный синтаксис — не
   случайное дизайнерское решение, а естественное следствие соответствия Карри–Ховарда.

> **Дополнительное чтение**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступно объясняет историю и значение соответствия Карри–Ховарда.

### Определение синтаксиса

#### 1. Объявление переменной

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типа (можно опускать)
y = 100  // выводится как Int
```

#### 2. Определение функций

> **Исправление (2026-09-15, RFC-010a)**: в данном разделе и в правилах возврата ниже изначально
> `return` использовался как выход из блока, что конфликтовало с семантикой досрочного возврата из
> RFC-007 (подробности см. в [RFC-010a](010a-tail-expression-and-return.md)). Теперь действует
> следующее: **значение блока = хвостовое выражение, `return` осуществляет выход из функции (тип
> `Never`)**. Ошибочные примеры «обязательного использования `return` для возврата значения» удалены
> и здесь не сохраняются.

```yaoxiang
// Одновыраженческая форма
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Блочная форма: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b                    // хвостовое выражение → значение блока
}

// Многострочный блок
calc: (x: Float, y: Float, op: String) -> Float = {
    match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }                    // match как хвостовое выражение
}

// Функция Void: хвостовое выражение имеет тип Void
print: (msg: String) -> Void = {
    console.write(msg)   // console.write : Void
}
```

#### Правила возврата

> **Исправление (2026-09-15, RFC-010a)**: прежнее правило «`= { ... }` обязывает использовать
> `return`, иначе возвращается `Void`» и аргумент «для устранения неоднозначности относительно того,
> является ли последнее выражение возвращаемым значением, нужен явный `return`» — **отменены**.
> Хвостовое выражение не создаёт такой неоднозначности, а `return` ему не мешает (Rust подтвердил
> корректность такого изоморфного дизайна).

**Значение блока = хвостовое выражение (единственный выход)**:

| Запись                                            | Значение                                |
| ------------------------------------------------- | --------------------------------------- |
| `= expr` (без фигурных скобок)                    | `expr`                                  |
| `= { ...; e }` (с фигурными скобками)             | хвостовое выражение `e`                 |
| `= { ...; s }` (на конце — оператор/присваивание) | `Void` (значение присваивания — `Void`) |
| `= {}` (пустой блок)                              | `Void`                                  |

**Семантика `return`**: нелокальный выход, **выходит за ближайшую границу функции** (а не
«возвращает в блок»), имеет тип `Never`. `Never <: T` для любого типа (принцип взрыва), поэтому
`return` может стоять в любой позиции типа возврата.

```yaoxiang
# Одновыраженческая форма: возвращается напрямую
add: (a: Int, b: Int) -> Int = a + b

# Блочная форма: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b
}

# Досрочный возврат: return проходит сквозь блок, выходит из функции (тип Never)
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    n * factorial(n - 1)     # хвостовое выражение
}
```

> **Обоснование (исправление от 2026-09-15, RFC-010a)**: `{ ... }` — это единица вычислений,
> управляемая зависимостями (см. ниже), её семантика вычисления отличается от одновыраженческой
> формы — фигурные скобки вводят многооператорный контекст, **значение которого задаётся хвостовым
> выражением**. Прежний аргумент «для устранения неоднозначности необходим явный `return`» отменён:
> хвостовое выражение не порождает такой неоднозначности.

#### Семантика `{}`: единица вычислений, управляемая зависимостями

`{ ... }` в YaoXiang — это не просто блок кода, а **единица вычислений, управляемая зависимостями**.
Эта семантика единообразна в телах функций, инициализаторах переменных и `spawn`:

**Ключевые правила**:

- операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- готовые зависимостями операторы выполняются немедленно, при отсутствии зависимостей — блокируются
  и ожидают
- **значение блока = хвостовое выражение** (см. правила возврата); `return` — нелокальный выход типа
  `Never`, выходящий из функции

```yaoxiang
# Управление зависимостями: b зависит от a, компилятор автоматически упорядочивает
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # без зависимостей → может выполняться первым
    b              # хвостовое выражение → значение блока 11
}
```

> **Отличие от одновыраженческой формы**: `= expr` (без фигурных скобок) — простое связывание,
> возвращающее значение напрямую; `= { ... }` (с фигурными скобками) вводит контекст вычислений,
> управляемый зависимостями, и допускает много операторов, значение определяется хвостовым
> выражением.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитива YaoXiang. Он использует семантику зависимостей
`{}` для автоматического распараллеливания:

- прямые дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- задачи с удовлетворёнными зависимостями немедленно исполняются параллельно
- вызывающий блокируется до завершения всех подзадач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (нет зависимостей от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ждёт их завершения
    return c                  # значение блока (выход через хвостовое выражение ещё не реализован, см. #365)
}
// здесь вызывающий блокируется до завершения всех задач в spawn-блоке
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> см. в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций над сырыми указателями.
Он использует семантику вычисления `{}`, передавая определение типов во внешнюю область видимости
(выход значения — хвостовое выражение):

**Ключевые правила**:

- в `unsafe {}` можно определять типы и работать с сырыми указателями
- **хвостовое выражение** задаёт значение `unsafe {}` (определение типов передаётся во внешнюю
  область)
- возвращаемый тип доступен за пределами `unsafe {}`
- доступ к полям типа требует права unsafe

```yaoxiang
# Определение непрозрачного типа в unsafe-блоке
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    SqliteDb           # хвостовое выражение → значение unsafe-блока
}

# SqliteDb доступен за пределами unsafe-блока
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: для доступа к полю handle требуется право unsafe
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов см.
> в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализацию интерфейсов:

##### Базовые типы

**Тип записи**: список полей, тип поля может быть любым выражением типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: у полей могут быть значения по умолчанию, при конструировании
они необязательны.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть переданы при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang состоит из трёх слоёв, распознаваемых на разных стадиях
компилятора:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявлений, такие как `if`, `match`, `pub`, `return`
2. **Литеральные зарезервированные слова** (отдельные токены парсера) — `true`, `false`, `void`,
   `Type`, не могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные тайпчекером) — парсер обрабатывает
   их как обычные идентификаторы, разрешает тайпчекер. **Не являются зарезервированными словами,
   могут быть затенены (не рекомендуется)**

Различие между `void` (строчное, литеральное зарезервированное слово) и `Void` (прописное, имя
встроенного типа): `void` — литерал значения (равен единственному значению Unit), `Void` — имя типа
(равен типу Unit, логически ⊤). `let x: Void = void` — допустимая запись.

Предустановленные имена встроенных типов:

| Тип      | Логический аналог     | Описание                                                                                                                                                                                                                                                                            |
| -------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь / пустой тип) | Ноль конструкторов, ни одно значение не может населять этот тип. Выражает «невозможное» — расходимость, паника, мёртвый код. `Never <: T` для любого `T` (принцип взрыва). Функция, возвращающая `Never`, не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина / Unit)     | Ровно один обитатель (по умолчанию значение void). `x: Void = <по умолчанию>` — допустимо. Аналог единичного элемента для типа суммы и типа произведения — `Void` — это пустой тип произведения (Unit), `Never` — пустой тип суммы.                                                 |
| `Int`    | —                     | Знаковое целое                                                                                                                                                                                                                                                                      |
| `Float`  | —                     | Число с плавающей точкой                                                                                                                                                                                                                                                            |
| `Bool`   | —                     | Логическое значение: `true` / `false`                                                                                                                                                                                                                                               |
| `Char`   | —                     | Unicode-символ                                                                                                                                                                                                                                                                      |
| `String` | —                     | Строка                                                                                                                                                                                                                                                                              |

##### Привязка методов

**Способ 1: прямое связывание внешней функции внутри тела типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        (dx * dx + dy * dy).sqrt()      # хвостовое выражение
    })
}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Имя интерфейса записывается в теле типа, компилятор автоматически проверяет реализацию**

```yaoxiang

    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

Point: Type = {

    Serializable      // реализует интерфейс Serializable
}
```

##### Определение интерфейса

**Интерфейс = тип записи, все поля которого — функции**

```yaoxiang
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Пустой тип / пустой интерфейс
EmptyType: Type = {}
Empty: Type = {}
```

##### Определение функций в пространстве имён

**Префикс `Type.name` обозначает принадлежность к пространству имён** — и ничего более. Он не
запускает никакой неявной привязки.

```yaoxiang
// Функция в пространстве имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

// Вызов: это обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Внимание**: `self` — не ключевое слово, а лишь устоявшееся имя параметра. Запись `p`, `this`,
> `x` даст абсолютно тот же эффект. Компилятор смотрит на типы, а не на имена параметров.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` вроде `p.draw(screen)` работал, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции в качестве «метода»
(подробный синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после неё доступен синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающим

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // оба способа вызова эквивалентны

// Без [0] = без привязки. Point.draw — просто псевдоним обычной функции, синтаксиса . нет
Point.draw = draw       // без привязки: только Point.draw(p, screen)
```

**Поведение по умолчанию**: отсутствие `[n]` = ни один параметр не привязан. Пользователь должен
явно решить, какие параметры будут заполняться вызывающим.

**Многопозиционная привязка**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Генерик-типы

```yaoxiang
// Базовые generics (RFC-011, фаза 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретное инстанцирование (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // пример вызова

// Генерик-метод (синтаксис RFC-023: параметры типа выводятся в точке вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        Maybe.Just(self.data[index])
    } else {
        Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова generics

Для вызова генерик-типов и генерик-функций единообразно используется синтаксис `()`. `[]` не
используется ни в одном контексте generics.

**Ключевые правила**:

1. **`()` делает всё**: применение типов, вызовы функций, конструирование значений — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся слева
empty: List(Int) = List()

# Вызов генерик-функции — тип перетекает из аргументов автоматически
strings = map(numbers, f)
// T=Int берётся из numbers: List(Int)
// R=String берётся из f: (Int) -> String
```

2. **Тип слева, значение справа**: `name: type = value` — параметры-типы объявляются слева, справа
   всегда конкретные значения. T для пустого контейнера `List()` должен браться из левой аннотации
   типа.

3. **Информацию о типе достаточно записать один раз** — при объявлении параметра компилятор
   «протаскивает» её далее:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int записан один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически берутся из типов numbers и f
```

4. **Конструирование значения выводит тип из элементов**:

```yaoxiang
x = List(1, 2, 3)       // выводится как List(Int)
y = List("a", "b")      // выводится как List(String)
z = List()              // ❌ ошибка компиляции: невозможно вывести T
z: List(Int) = List()   // ✅ T=Int берётся из левой аннотации
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис generics с `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и индексации.

// В интерфейсе параметр self не нужен — интерфейс определяет только "сигнатуру функции после удаления позиции вызывающего"

}

    scale: (factor: Float) -> Transformable
}

// ======== 2. Определения типов ========

    x: Float,
    y: Float,

}

    x: Float,
    y: Float,

    height: Float,
    Drawable,

    Transformable
}

}

}

}

}

}

Point.bounding_box = bounding_box[0]

Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

Rect.draw = draw[0]

Rect.bounding_box = bounding_box[0]

    "Rect(${r.x}, ${r.y}, ${r.width}, ${r.height})"

Rect.serialize = serialize[0]

translate: (r: &Rect, dx: Float, dy: Float) -> Rect = {
    Rect(r.x + dx, r.y + dy, r.width, r.height)
}
Rect.translate = translate[0]

scale: (r: &Rect, factor: Float) -> Rect = {
    Rect(r.x * factor, r.y * factor, r.width * factor, r.height * factor)
}
Rect.scale = scale[0]

// ======== 4. Использование ========

// Создание экземпляров

## Детальное проектирование

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (поля-функции)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, есть ли у типа метод с тем же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатур
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: должны совпасть после удаления self-параметра
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации времени компиляции

Тип интерфейса поддерживает прямое присваивание, компилятор автоматически выбирает оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип известен в compile-time, вызов с нулевыми накладными расходами
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возврат из функции → конкретный тип не известен в compile-time, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Гетерогенная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегии оптимизации времени компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                   |

**Правила**:

1. Если правая часть — конкретный конструктор типа, известный в compile-time, генерируется IR с
   прямым вызовом
2. Если тип правой части не может быть определён в compile-time, происходит откат к механизму vtable
3. vtable служит резервным механизмом, гарантирующим корректность полиморфизма во время выполнения

| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `type Point = Point(x: Float, y: Float)` | `type Point = { x: Float, y: Float }`                                                        |
| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| требуется ключевое слово `impl`          | ключевое слово не нужно, имя интерфейса записывается в теле типа                             |

### Устарело: синтаксис вариантов `|`

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов `|` официально устарел и удалён из
> реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Единообразно используются типы записей и типы сумм (sum type). Когда все поля типа записи — функции,
каждая из которых возвращает сам этот тип, он является типом суммы:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование**:

1. **Устранение особого случая**: `|` — единственная не унифицированная форма `name: type = value` в
   BNF. После удаления продукция `type_expr` становится полностью единообразной, парсеру больше не
   нужны отдельный путь и look-ahead с возвратом для типов-вариантов.
2. **Математическая эквивалентность**: в свете соответствия Карри–Ховарда дизъюнкция P ⊕ Q,
   соответствующая типу суммы, эквивалентна типу записи, «все поля которого — функции, возвращающие
   сам этот тип». Семантика одинакова, два синтаксиса не нужны.
3. **Нулевая разрушительность**: до удаления синтаксис `|` был в парсере в полуподдерживаемом
   состоянии (варианты без аргументов разбирались, но типы параметров терялись при мономорфизации),
   ни один пользовательский код от него не зависел.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы идут по пути
   `Type::Struct`, специальные ветви в нижестоящих тайпчеке / мономорфизации / форматёре полностью
   устранены.

> **Примечание**: семантические свойства типов сумм (такие как проверка полноты match, расположение
> tagged union в памяти) выводятся тайпчекером из структуры `Type::Struct` и не зависят от
> отдельного узла AST.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: авторитетная форма логических операторов — ключевые слова
> `and` / `or` + символьный унарный `!` (согласуется с таблицей приоритетов SPEC `syntax.md` §2.2).
> Дизайн выровнен с Zig: **короткое замыкание потока управления — через ключевые слова, чистые
> унарные операции — через символы**. Прежняя реализация, дрейфующая к C (`&&` / `||`), и
> промежуточное ключевое слово `not` удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                 | Ассоциативность | Семантика                                                    |
| -------- | ------------------------------------- | --------------- | ------------------------------------------------------------ |
| `!`      | 3 (унарный префикс, плотная привязка) | справа налево   | логическое отрицание (чистая функция, без потока управления) |
| `and`    | 10                                    | слева направо   | короткое замыкание логического И                             |
| `or`     | 10                                    | слева направо   | короткое замыкание логического ИЛИ                           |

```yaoxiang
# Короткое замыкание: когда левая часть and — false / левая часть or — true, правая не вычисляется
if x != 0 and y / x > 1 { ... }   # при x == 0 деления на ноль не будет

# Плотная привязка: !a == b ≡ (!a) == b (стиль Zig; в отличие от Python: not a == b ≡ not (a == b))
!3 == 4          # false: (!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs)), отрицание после вызова
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке и предлагает корректную
форму):

```
x && y     # ❌ удалено, используйте x and y
x || y     # ❌ удалено, используйте x or y
not x      # ❌ удалено, используйте !x (not снова становится обычным идентификатором; на != не влияет)
```

**Обоснование** (выравнивание с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — поток управления → ключевое слово; чистая функция — вычисление → символ**.
   `and` / `or` изменяют порядок вычисления (правая часть пропускается по необходимости), по
   характеру аналогичны `if` — значит ключевое слово; `!` выполняет чистое отрицание уже
   вычисленного операнда, по характеру аналогично `-` `+` — значит символ. Распространение ошибки в
   YaoXiang использует `?` (§2.11), `!` не конфликтует.
2. **Плотная привязка устраняет неоднозначность**: `!` визуально «прилипает» к операнду, высокий
   приоритет очевиден; ключевое слово `not` вынужденно отделяется от операнда пробелом, что
   порождает мысленную неоднозначность в выражениях вроде `not a == b`.
3. **Устранение смешения ролей**: `&` несёт двойную нагрузку — токен заимствования (`&p` / `&mut p`,
   RFC-009) и побитовое И (SPEC §2.2, приоритет 8). Введение `&&` добавило бы третье значение одному
   символу. `and` / `or` / `!` визуально полностью разделяют заимствование, побитовые и логические
   операции.
4. **Прецедент**: Zig (системный язык той же экологической ниши) — именно комбинация ключевых слов
   `and` / `or` + символа `!`; Python / Lua / Ada / SQL используют полностью ключевые слова (включая
   `not`); семейство C — полностью символы. YaoXiang берёт микс Zig и получает преимущества обоих
   подходов.
5. **Согласованность с Карри–Ховардом**: тип есть высказывание (см. раздел о соответствии выше),
   логические связки в уточнённых типах пишутся как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`) — это естественная запись высказываний; `!` как символьный
   унарный оператор отрицания соответствует ¬.

> **Реализация**: `and` / `or` на уровне IR разворачиваются в последовательность переходов с
> коротким замыканием (`a and b ≡ if a { b } else { false }`), `!` разбирается как унарный с плотной
> привязкой (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Пояснение к дизайну синтаксиса: именованная функция по сути является синтаксическим сахаром для лямбды

### Основная идея

**Именованная функция и лямбда-выражение — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// Эти две записи по сути полностью идентичны
add: (a: Int, b: Int) -> Int = a + b           // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, имена параметров в
заголовке лямбды становятся избыточными и могут быть опущены.

### Правила области видимости параметров

**Параметр затеняет внешнюю переменную**: область видимости параметра в сигнатуре перекрывает тело
функции, внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x затеняет внешний x, результат 20
```

### Гибкое расположение аннотаций

Аннотация типа может находиться в любом из следующих мест, **достаточно аннотировать хотя бы одно**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но разрешено |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: сигнатура полная, заголовок лямбды опускается
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Допустимо: типы аннотированы в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Допустимо: аннотация в обоих местах
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство            | Преимущество                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------- |
| **Краткость**       | при полной сигнатуре нет необходимости повторять имена параметров                        |
| **Гибкость**        | лямбда-форма сохранена, можно использовать ту, которая нравится                          |
| **Согласованность** | сохраняет единый шаблон с объявлением переменной `x: Int = 42`                           |
| **Интуитивность**   | `name: Type = body` напрямую соответствует «по имени name, типа Type, со значением body» |

## Приложение

### Синтаксис BNF

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражение типа
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # тип функции
       | '{' type_field* '}'                       # тип записи / интерфейса
       | 'Type'                                    # метатип

type_field ::= identifier ':' type_expr
             | identifier                           # ограничение интерфейса

# Параметры типа: как часть типа функции, например (T: Type, R: Type) -> (...)
# Отдельное правило BNF не требуется — параметры с : Type — это обычные параметры функции

# Выражение
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # вызов функции / вызов конструктора
              | '(' expression (',' expression)* ')'              # кортеж
              | expression '.' identifier '(' arguments? ')'    # вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                      | Определение                                                                                                          |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Объявление                  | Оператор присваивания в форме `name: type = value`                                                                   |
| Тип записи                  | Тип `{ ... }` с именованными полями                                                                                  |
| Интерфейс                   | Тип записи, все поля которого — типы функций                                                                         |
| Генерик-тип                 | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры-типы                                |
| Функция в пространстве имён | Функция в форме `Type.name`, принадлежащая пространству имён Type. Не подразумевает никакой привязки                 |
| Привязка метода             | `Type.name = func[n]` — привязка позиции n функции func как вызывающего, делает доступным синтаксис `obj.name(args)` |
| Генерик-функция             | Функция, использующая синтаксис `(T: Type)`, параметры-типы выступают в роли первой группы параметров                |
| Метатип                     | `Type` — единственный в языке маркер уровня типа                                                                     |
