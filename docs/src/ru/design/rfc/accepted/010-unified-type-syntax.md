# RFC-010: Унифицированный синтаксис типов - модель name: type = value

## Резюме

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть произвольным выражением типа, а `expression` — произвольным выражением
значения. **Нет `fn`, нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем
регистре (но есть `Type` как ключевое слово меta-типа)**.

> **Основная идея**: `Type` сам по себе является generics-типом. `(T: Type) -> Type` означает "тип,
> принимающий параметр типа T".

| Понятие          | Запись в коде                                                                |
| ---------------- | ---------------------------------------------------------------------------- |
| Переменная       | `x: Int = 42`                                                                |
| Функция          | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Record type      | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс        | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Generics-тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Generics-тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод            | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Generics-функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово меta-типа в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` обозначает лишь **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` вроде `p.draw(screen)` работал, необходима явная привязка:
> `Point.draw = draw[0]`. Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он
> используется для маркировки уровня типов; компилятор автоматически различает Type0, Type1,
> Type2... — это прозрачно для пользователя.

```yaoxiang
// Основной синтаксис: унификация + различение

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Record type
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути record type, все поля которого — функции)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (с использованием синтаксиса Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    "Point(${self.x}, ${self.y})"
}

// Generics-тип ((T: Type) -> Type = generics-тип, принимающий параметр типа)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурная подтипизация: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая type system содержит несколько разрозненных понятий:

- синтаксис объявления переменных
- синтаксис определения функций
- синтаксис определения типов (другой синтаксис)
- синтаксис определения интерфейсов
- синтаксис привязки методов

Между этими понятиями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельная унификация**: одно правило синтаксиса покрывает все случаи
2. **Краткость и элегантность**: симметричная эстетика `name: type = value`
3. **Никаких новых ключевых слов**: повторное использование существующих синтаксических элементов
4. **Теоретическая элегантность**: сам тип также является значением типа `Type`
5. **Generics-дружественность**: бесшовная интеграция с generics (RFC-011)

### Интеграция с generics

Унифицированная синтаксическая модель RFC-010 **органично сочетается** с дизайном generics из
RFC-011, и параметры generics естественно вписываются в унифицированную модель:

```yaoxiang
// Базовые generics (RFC-011 Phase 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Generics-функция (синтаксис RFC-023: Type в позиции сигнатуры можно опустить, вывод при вызове)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничения типов (RFC-011 Phase 2)
clone: (value: T) -> T = value.clone()  // Ограничение T: Clone переносится типом параметра

// Const generics (RFC-011 Phase 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовые generics) является **сильной зависимостью** для RFC-010
- Без базовых generics примеры generics из RFC-010 не скомпилируются
- Рекомендация: RFC-011 Phase 1 и RFC-010 реализуются синхронно

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила устранения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                              |
| ------------------- | ---------------------- | ---------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | `: Type` явное объявление → принудительно тип        |
| **`f = ...`**       | Функция или переменная | Без `: Type` → HM активно выводит функцию/переменную |

**Почему именно так?**

Сам синтаксис `{ ... }` неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (record type)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM активно интерпретирует `{ ... }` как блок кода, выводится функциональный тип

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит () -> Void
main: () -> Void = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может разобрать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит функцию, а не тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # Нет : Type, HM выводит функцию
│
├── Record type
│   └── Point: Type = { x: Float, y: Float }  # Должен вернуть: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # Должен вернуть: Type
│
├── Generics-тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # Должен вернуть: Type
│
├── Generics-тип (несколько параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # Должен вернуть: Type
│
├── Функция пространства имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # Только после явной привязки доступен синтаксис вызова через .
│
└── Generics-функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # Не возвращает Type, HM выводит функцию
```

### Иерархия меta-типов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенных `level: selfpointnum` (хранится в виде
строки, теоретически может быть бесконечной).

| Level    | Описание                                    |
| -------- | ------------------------------------------- |
| `Type0`  | Повседневные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)        |
| `Type2+` | Конструкторы высшего порядка                |

**Пользователь никогда не видит этих чисел**, только `: Type`.

### Изоморфизм Карри-Ховарда: тип есть высказывание, программа есть доказательство

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он является прямым
отображением изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм раскрывает
глубокий факт: **type system и логическая система — это две стороны одного и того же**.

| Логика (высказывание)         | Type system (YaoXiang)              | Пример                               |
| ----------------------------- | ----------------------------------- | ------------------------------------ |
| Высказывание P                | Тип T                               | `Int`, `Bool`                        |
| Доказательство P              | Значение типа T                     | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | Function type `(P) -> Q`            | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | Record type `{ p: P, q: Q }`        | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Generics-функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | Enum / tagged union                 | `Maybe: (T: Type) -> Type = { ... }` |

**Что означает `name: type = value` в свете Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int по имени x со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: по доказательствам a и b типа Int можно построить доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — это высказывание, доказательство которого требует одновременного предоставления доказательства Float x и доказательства Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = type safety**: если type system позволяет сконструировать
   значение типа `T` без какого-либо допустимого представления в runtime, это подобно тому, как если
   бы логика позволяла доказать ложное высказывание — система рушится. Карри-Ховард говорит нам:
   **язык с безопасной системой типов естественным образом является непротиворечивой логической
   системой**.

2. **Иерархия вселенных — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (то есть "тип типа тоже является типом"), возникнет парадокс Рассела (в теории типов
   он проявляется как парадокс Жирара). Расслоение YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   гарантирует, что каждый тип принадлежит только одному уровню, формируя бесконечно восходящую
   цепочку, что фундаментально предотвращает парадоксы. Это означает, что type system YaoXiang в
   смысле Карри-Ховарда является **логически непротиворечивой**.

3. **Теоретическое обоснование унифицированного синтаксиса**: `name: type = value` может одним
   синтаксисом покрыть переменные, функции, типы, интерфейсы и все концепции generics именно потому,
   что в свете Карри-Ховарда всё это — одно и то же: **предоставление доказательства для
   высказывания**. Переменная — это свидетельство высказывания, функция — свидетельство импликации,
   record — свидетельство конъюнкции, generics — свидетельство квантора всеобщности. Унифицированный
   синтаксис — не искусственно сконструированное совпадение, а естественное следствие изоморфизма
   Карри-Ховарда.

> **Дополнительное чтение**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья простым языком объясняет историю и значение изоморфизма
> Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типов (можно опустить)
y = 100  // выводится Int
```

#### 2. Определение функций

> **Исправление (2026-09-15, RFC-010a)**: в этом и нижеследующем разделе «Правила возврата»
> первоначально `return` использовался как выход значения блока, что конфликтовало с семантикой
> раннего возврата из RFC-007 (подробности см. в [RFC-010a](010a-tail-expression-and-return.md)).
> Теперь принято: **значение блока = хвостовое выражение, `return` осуществляет выход из функции
> (тип `Never`)**. Ошибочные примеры «обязательного использования `return` для возврата значения»
> удалены и в данном исправлении не сохраняются.

```yaoxiang
// Одновыраженческая форма
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Блочная форма: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b                    // хвостовое выражение → значение блока
}

// Многострочный блок
calc: (x: Float, y: Float, op: String) -> Float = {
    match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }                    // match как хвостовое выражение
}

// Void-функция: хвостовое выражение имеет тип Void
print: (msg: String) -> Void = {
    console.write(msg)   // console.write : Void
}
```

#### Правила возврата

> **Исправление (2026-09-15, RFC-010a)**: первоначальное правило «`= { ... }` требует `return`,
> иначе возвращается `Void`» и обоснование «необходим явный `return` для устранения неоднозначности
> относительно того, является ли последнее выражение возвращаемым значением» **отменено**. Хвостовое
> выражение такой неоднозначности не создаёт, а `return` ему не мешает (Rust подтвердил корректность
> такого изоморфного дизайна).

**Значение блока = хвостовое выражение (единственный выход)**:

| Запись                                             | Значение                                |
| -------------------------------------------------- | --------------------------------------- |
| `= expr` (без фигурных скобок)                     | `expr`                                  |
| `= { ...; e }` (с фигурными скобками)              | хвостовое выражение `e`                 |
| `= { ...; s }` (последний — оператор/присваивание) | `Void` (значение присваивания — `Void`) |
| `= {}` (пустой блок)                               | `Void`                                  |

**Семантика `return`**: нелокальный выход, **выходит из ближайшей границы функции** (не «возвращает
значение блоку»), тип — `Never`. `Never <: T` выполняется для любого типа (принцип взрыва), поэтому
`return` может появляться в любой позиции возвращаемого типа.

```yaoxiang
# Одновыраженческая форма: прямое возвращение значения
add: (a: Int, b: Int) -> Int = a + b

# Блочная форма: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b
}

# Досрочный возврат: return проходит сквозь блок, выходя из функции (тип Never)
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    n * factorial(n - 1)     # хвостовое выражение
}
```

> **Обоснование дизайна (исправление 2026-09-15, RFC-010a)**: `{ ... }` — это единица
> зависимостно-управляемого вычисления (см. ниже), её семантика вычисления отличается от
> одновыраженческой формы — фигурные скобки вводят многооператорный контекст, **значение которого
> определяется хвостовым выражением**. Аргумент о том, что «явный `return` необходим для устранения
> неоднозначности», отменён: хвостовое выражение такой неоднозначности не создаёт.

#### Семантика `{}`: единица зависимостно-управляемого вычисления

`{ ... }` в YaoXiang — это не просто блок кода, а **единица зависимостно-управляемого вычисления**.
Эта семантика остаётся единообразной в телах функций, инициализации переменных и в `spawn`:

**Основные правила**:

- операторы присваивания внутри `{}` автоматически упорядочиваются по зависимостям, а не по порядку
  записи
- при готовности зависимостей выполняются немедленно, при их отсутствии — блокируются в ожидании
- **значение блока = хвостовое выражение** (см. правила возврата); `return` — нелокальный выход типа
  `Never`, осуществляющий выход из функции

```yaoxiang
# Управление по зависимостям: b зависит от a, компилятор автоматически упорядочивает
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # без зависимостей → может выполниться первым
    b              # хвостовое выражение → значение блока 11
}
```

> **Отличие от одновыраженческой формы**: `= expr` (без фигурных скобок) — простая привязка,
> непосредственно возвращающая значение; `= { ... }` (с фигурными скобками) вводит контекст
> зависимостно-управляемого вычисления, допускающий несколько операторов, значение которого задаётся
> хвостовым выражением.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитива YaoXiang. Она использует
зависимостно-управляемую семантику `{}` для автоматического распараллеливания:

- непосредственные дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные
  задачи
- задачи с готовыми зависимостями выполняются конкурентно
- вызывающая сторона блокируется до завершения всех подзадач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (без зависимостей от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ждёт завершения обоих
    c                         # хвостовое выражение → значение spawn
}
// вызывающая сторона блокируется здесь до завершения всех задач внутри spawn-блока
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> см. в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций над сырыми указателями.
Он использует семантику вычисления `{}` для передачи определения типа во внешнюю область видимости
(выход значения — хвостовое выражение):

**Основные правила**:

- внутри `unsafe {}` можно определять типы и работать с сырыми указателями
- **хвостовое выражение** задаёт значение `unsafe {}` (определение типа передаётся во внешнюю
  область видимости)
- возвращаемый тип доступен за пределами `unsafe {}`
- доступ к полям типа требует полномочий unsafe

```yaoxiang
# Определение непрозрачного типа внутри unsafe-блока
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    SqliteDb           # хвостовое выражение → значение unsafe-блока
}

# SqliteDb доступен за пределами unsafe-блока
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: доступ к полю handle требует полномочий unsafe
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов см.
> в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализации интерфейсов:

##### Базовые типы

**Record type**: список полей, типы полей могут быть произвольными выражениями типов.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) // ✓
Point2() // ✗
Point2(x=1) // ✗
```

##### Встроенные типы

Система идентификаторов YaoXiang состоит из трёх уровней, распознаваемых на разных фазах
компилятора:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявлений, такие как `if`, `match`, `pub`, `return`
2. **Зарезервированные литералы** (отдельные токены парсера) — `true`, `false`, `void`, `Type`, не
   могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные в type checker) — парсер
   обрабатывает их как обычные идентификаторы, их разбором занимается type checker. **Не являются
   зарезервированными словами, могут быть затенены (не рекомендуется)**

Различие между `void` (в нижнем регистре, зарезервированный литерал) и `Void` (в верхнем регистре,
имя встроенного типа): `void` — это литерал значения (равен единственному значению Unit), `Void` —
имя типа (равен типу Unit, логическому ⊤). `let x: Void = void` — допустимая запись.

Предопределённые имена встроенных типов:

| Тип      | Логический аналог   | Описание                                                                                                                                                                                                                                                                                   |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевой конструктор, никакое значение не может населять этот тип. Означает «невозможно» — расходимость, panic, мёртвый код. `Never <: T` для любого `T` (принцип взрыва). Функция, возвращающая `Never`, никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (значение void по умолчанию). `x: Void = <по умолчанию>` допустимо. Единица суммы типов, соответствующая единице произведения — `Void` — это произведение с нулём полей (Unit), `Never` — сумма с нулём вариантов.                                                    |
| `Int`    | —                   | Целое число со знаком                                                                                                                                                                                                                                                                      |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                   |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                      |
| `Char`   | —                   | Unicode-символ                                                                                                                                                                                                                                                                             |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                     |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        (dx * dx + dy * dy).sqrt()      # хвостовое выражение
    })
}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Имя интерфейса записывается внутри тела типа, компилятор автоматически проверяет реализацию**

```yaoxiang

    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

Point: Type = {
    x: Float,
    y: Float,
    Drawable,          // реализует интерфейс Drawable
    Serializable      // реализует интерфейс Serializable
}
```

##### Определение интерфейсов

**Интерфейс = record type, все поля которого — функции**

```yaoxiang
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Пустой тип / пустой интерфейс
EmptyType: Type = {}
Empty: Type = {}
```

##### Определение функций пространства имён

**Префикс `Type.name` обозначает лишь принадлежность к пространству имён**, и ничего более. Он не
вызывает никакой неявной привязки.

```yaoxiang
// Функция пространства имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

// Вызов: это обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` — не ключевое слово, а лишь устоявшееся соглашение об именовании параметра.
> Запись `p`, `this`, `x` полностью эквивалентна. Компилятор смотрит на тип, а не на имя параметра.

##### Привязка методов (единственный способ)

Чтобы синтаксис вызова метода через `.` вроде `p.draw(screen)` работал, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции в качестве «метода»
(подробный синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после неё доступен синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающей стороной

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // оба способа вызова эквивалентны

// Без [0] = без привязки. Point.draw — просто псевдоним обычной функции, без синтаксиса .
Point.draw = draw       // без привязки: только Point.draw(p, screen)
```

**Поведение по умолчанию**: без `[n]` = ни один параметр не привязан. Пользователь должен явно
решить, какие параметры заполняются вызывающей стороной.

**Многопозиционная привязка**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Generics-типы

```yaoxiang
// Базовые generics (RFC-011 Phase 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретизация (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // пример вызова

// Generics-метод (синтаксис RFC-023: параметры типов выводятся автоматически в точке вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        Maybe.Just(self.data[index])
    } else {
        Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова generics

Для generics-типов и generics-функций используется единый синтаксис `()`. `[]` ни в одном
generics-контексте не используется.

**Основные правила**:

1. **`()` для всего**: применение типов, вызов функций, конструирование значений — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся слева
empty: List(Int) = List()

# Вызов generics-функции — типы автоматически «перетекают» из аргументов
strings = map(numbers, f)
// T=Int берётся из numbers: List(Int)
// R=String берётся из f: (Int) -> String
```

2. **Тип слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. `T` для пустого контейнера `List()` должен браться из левой аннотации
   типа.

3. **Информацию о типе нужно написать лишь однажды** — при объявлении параметров компилятор «несёт»
   её с собой:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int написан один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически берутся из типов numbers и f
```

4. **Конструирование значения с выводом типа по элементам**:

```yaoxiang
x = List(1, 2, 3)       // выводится List(Int)
y = List("a", "b")      // выводится List(String)
z = List()              // ❌ ошибка компиляции: невозможно вывести T
z: List(Int) = List()   // ✅ T=Int берётся из левой аннотации
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый generics-синтаксис `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

#### Полный пример

```yaoxiang
// ======== 1. Определение интерфейсов ========
// Интерфейс = record type, все поля которого — функции
// В интерфейсе параметр self не нужен — интерфейс задаёт лишь «сигнатуру функции после удаления позиции вызывающей стороны»

Drawable: Type = {
    draw: (surface: Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

Transformable: Type = {
    translate: (dx: Float, dy: Float) -> Transformable,  // возврат интерфейсного типа, конкретная реализация возвращает свой собственный тип
    scale: (factor: Float) -> Transformable
}

// ======== 2. Определение типов ========

Point: Type = {
    x: Float,
    y: Float,
    Drawable,
    Serializable,
    Transformable
}

Rect: Type = {
    x: Float,
    y: Float,
    width: Float,
    height: Float,
    Drawable,
    Serializable,
    Transformable
}

// ======== 3. Реализация методов (обычные функции + явная привязка) ========

// Определение функций (self — лишь устоявшееся имя, не ключевое слово)
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

bounding_box: (p: &Point) -> Rect = {
    Rect(p.x - 1, p.y - 1, 2, 2)
}

serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

translate: (p: &Point, dx: Float, dy: Float) -> Point = {
    Point(p.x + dx, p.y + dy)
}

scale: (p: &Point, factor: Float) -> Point = {
    Point(p.x * factor, p.y * factor)
}

distance: (p1: &Point, p2: &Point) -> Float = {
    dx = p1.x - p2.x
    dy = p1.y - p2.y
    (dx * dx + dy * dy).sqrt()
}

// Явная привязка — только после неё доступен синтаксис вызова через точку
Point.draw = draw[0]
Point.bounding_box = bounding_box[0]
Point.serialize = serialize[0]
Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

// Методы Rect определяются аналогично
draw: (r: &Rect, surface: Surface) -> Void = {
    surface.draw_rect(r.x, r.y, r.width, r.height)
}
Rect.draw = draw[0]

bounding_box: (r: &Rect) -> Rect = r
Rect.bounding_box = bounding_box[0]

serialize: (r: &Rect) -> String = {
    "Rect(${r.x}, ${r.y}, ${r.width}, ${r.height})"
}
Rect.serialize = serialize[0]

translate: (r: &Rect, dx: Float, dy: Float) -> Rect = {
    Rect(r.x + dx, r.y + dy, r.width, r.height)
}
Rect.translate = translate[0]

scale: (r: &Rect, factor: Float) -> Rect = {
    Rect(r.x * factor, r.y * factor, r.width * factor, r.height * factor)
}
Rect.scale = scale[0]

// ======== 4. Использование ========

// Создание экземпляров
p: Point = Point(1.0, 2.0)
r: Rect = Rect(0.0, 0.0, 10.0, 20.0)

// Вызов метода (синтаксический сахар)
p.draw(screen)
r.draw(screen)

// Обычный вызов метода (прямой вызов)

// Цепочка вызовов
p2: Point = p.translate(1.0, 1.0).scale(2.0)

// Присваивание интерфейсу
drawables: List(Drawable) = [p, r]

}

// Generics-функция (синтаксис RFC-023: параметры типов опускаются при вызове, выводятся автоматически)
process_all: (items: List(T)) -> Void = {
    for item in items {
        print(item.serialize())
    }
}

process_all([p, r])
```

## Детальное проектирование

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (поля-функции)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, что у типа есть метод с тем же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатуры метода
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: после удаления параметра self должно совпасть
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации времени компиляции

Интерфейсные типы поддерживают прямое присваивание; компилятор автоматически выбирает оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип известен на этапе компиляции, вызов без накладных расходов
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возвращаемое значение функции → конкретный тип не известен на этапе компиляции, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Гетерогенная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегии оптимизации на этапе компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                         |
| -------------------------------- | --------------------- | ------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (без накладных расходов) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                |

**Правила**:

1. Когда правая часть — конкретный конструктор типа, известный на этапе компиляции, генерируется IR
   с прямым вызовом
2. Когда тип правой части не может быть определён на этапе компиляции, происходит откат на механизм
   vtable
3. vtable служит страховкой для корректности runtime-полиморфизма

### Изменения синтаксиса

| Ранее                                    | Далее                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `type Point = Point(x: Float, y: Float)` | `type Point = { x: Float, y: Float }`                                                        |
| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| требуется ключевое слово `impl`          | ключевое слово не требуется, имя интерфейса записывается после тела типа                     |

### Устаревший: синтаксис вариантов `|`

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов `|` официально устарел и удалён из
> реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Для выражения sum type используется record type. Когда все поля record type — функции, возвращающие
сам этот тип, он и является sum type:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особого случая**: `|` — единственный синтаксис в BNF, не укладывающийся в форму
   `name: type = value`. После его удаления продукция `type_expr` становится полностью
   единообразной, и парсеру больше не нужно поддерживать отдельный путь и lookahead-откат для
   вариантных типов.
2. **Математическая эквивалентность**: в свете изоморфизма Карри-Ховарда дизъюнкция P ⊕ Q,
   соответствующая sum type, эквивалентна record type «все поля которого — функции, возвращающие сам
   этот тип». Они выражают одну и ту же семантику и не требуют двух разных синтаксисов.
3. **Нулевая разрушительность**: до удаления синтаксис `|` в парсере поддерживался лишь частично
   (варианты без параметров разбирались, но типы параметров терялись при мономорфизации), и ни один
   пользовательский код на него не полагался.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы идут по пути
   `Type::Struct`; специальные ветви в typecheck/mono/formatter полностью устранены.

> **Примечание**: семантические свойства sum type (такие как проверка exhaustive в match, размещение
> tagged union в памяти) выводятся на уровне typecheck из структуры `Type::Struct` и не зависят от
> отдельного узла AST.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: авторитетная форма логических операторов — ключевые слова
> `and` / `or` + символьный унарный `!` (согласно таблице приоритетов SPEC `syntax.md` §2.2). Дизайн
> выровнен по Zig: **для короткозамыкающего потока управления — ключевые слова, для чисто унарных
> операций — символы**. Ранние дрейфующие к C реализации `&&` / `||`, а также промежуточное ключевое
> слово `not` — все удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                 | Ассоциативность | Семантика                                                    |
| -------- | ------------------------------------- | --------------- | ------------------------------------------------------------ |
| `!`      | 3 (унарный префикс, плотная привязка) | справа налево   | Логическое отрицание (чистая функция, без потока управления) |
| `and`    | 10                                    | слева направо   | Короткозамыкающее логическое «и»                             |
| `or`     | 10                                    | слева направо   | Короткозамыкающее логическое «или»                           |

```yaoxiang
# Короткое замыкание: при false слева в and / true слева в or правая часть не выполняется
if x != 0 and y / x > 1 { ... }   # при x == 0 деления на ноль не произойдёт

# Плотная привязка: !a == b ≡ (!a) == b (в стиле Zig; в отличие от Python: not a == b ≡ not (a == b))
!3 == 4          # false: (!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs)), инверсия после вызова
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке и подсказывает правильную
запись):

```
x && y     # ❌ удалено, используйте x and y
x || y     # ❌ удалено, используйте x or y
not x      # ❌ удалено, используйте !x (not снова становится обычным идентификатором; != не затрагивается)
```

**Обоснование дизайна** (выравнивание по Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — это поток управления → ключевое слово; чистая функция — это операция →
   символ**. `and` / `or` изменяют порядок вычисления (правая часть пропускается по необходимости),
   что по природе сродни `if`, поэтому ключевое слово; `!` выполняет чистое отрицание уже
   вычисленного операнда, что по природе сродни `-` `+`, поэтому символ. Распространение ошибок в
   YaoXiang использует `?` (§2.11), `!` не конфликтует.
2. **Плотная привязка устраняет неоднозначность**: `!` визуально «прилеплен» к операнду, и его
   высокий приоритет очевиден; ключевое слово `not` вынужденно отделяется пробелом от операнда, и
   то, к чему оно привязывается (`not a == b`), легко вызывает мысленную неоднозначность.
3. **Устранение перегрузки**: `&` несёт две обязанности — токен заимствования (`&p` / `&mut p`,
   RFC-009) и побитовое «и» (SPEC §2.2 приоритет 8). Добавление `&&` заставит один символ нести три
   значения. `and` / `or` / `!` визуально полностью разделяют заимствование, побитовые и логические
   операции.
4. **Прецедент**: Zig (системный язык той же экологической ниши) использует именно комбинацию `and`
   / `or` как ключевые слова + `!` как символ; Python / Lua / Ada / SQL используют полностью
   ключевые слова (включая `not`); семейство C — полностью символы — YaoXiang берёт микс Zig,
   получая преимущества обоих подходов.
5. **Согласованность с Карри-Ховардом**: тип есть высказывание (см. раздел об изоморфизме выше), и
   логические связки в уточняющих типах естественно записываются как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`); `!` как символ унарного отрицания соответствует ¬.

> **Реализация**: `and` / `or` на уровне IR раскрываются в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`), `!` разбирается как унарный с плотной привязкой
> (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Заметки о дизайне синтаксиса: именованные функции по сути являются синтаксическим сахаром для лямбд

### Ключевое понимание

**Именованные функции и лямбда-выражения — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// Эти две записи по сути полностью идентичны
add: (a: Int, b: Int) -> Int = a + b                          // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b                 // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, заголовок лямбды с именами
параметров становится избыточным и может быть опущен.

### Правила области видимости параметров

**Параметры затеняют внешние переменные**: область видимости параметров в сигнатуре перекрывает тело
функции; внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x затеняет внешний x, результат 20
```

### Гибкое расположение аннотаций

Аннотация типа может располагаться в любом из следующих мест, **достаточно аннотации хотя бы в
одном**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ допустимо               |
| С обеих сторон            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но разрешено |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: полная сигнатура, заголовок лямбды опускается
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Допустимо: типы аннотируются в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Допустимо: аннотация с обеих сторон
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство          | Преимущество                                                                   |
| ----------------- | ------------------------------------------------------------------------------ |
| **Краткость**     | При полной сигнатуре нет нужды повторять имена параметров                      |
| **Гибкость**      | Лямбда-форма сохранена — используйте то, что вам нравится                      |
| **Единообразие**  | Сохраняет унифицированный паттерн объявления переменной `x: Int = 42`          |
| **Интуитивность** | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### БНФ грамматики

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражение типа
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # Применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # Функциональный тип
       | '{' type_field* '}'                       # Record / интерфейс
       | 'Type'                                    # Меta-тип

type_field ::= identifier ':' type_expr
             | identifier                           # Ограничение интерфейса

# Параметры generics: как часть функционального типа, напр. (T: Type, R: Type) -> (...)
# Отдельное правило БНФ не требуется — параметры : Type — это обычные параметры функций

# Выражение
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # Вызов функции / вызов конструктора
              | '(' expression (',' expression)* ')'              # Кортеж
              | expression '.' identifier '(' arguments? ')'    # Вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                    | Определение                                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Объявление                | Оператор присваивания в форме `name: type = value`                                                                                   |
| Record type               | `{ ... }` тип с именованными полями                                                                                                  |
| Интерфейс                 | Record type, все поля которого — функциональные типы                                                                                 |
| Generics-тип              | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типов                                               |
| Функция пространства имён | Функция в форме `Type.name`, принадлежащая пространству имён Type. Не предполагает никакой привязки                                  |
| Привязка метода           | `Type.name = func[n]` — привязка позиции n функции func в качестве вызывающей стороны, делающая доступным синтаксис `obj.name(args)` |
| Generics-функция          | Функция, использующая синтаксис `(T: Type)`, параметры типов — в качестве первой группы параметров                                   |
| Меta-тип                  | `Type` — единственный маркер уровня типов в языке                                                                                    |
