# RFC-010: Унифицированный синтаксис типов - модель name: type = value

## Резюме

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
как ключевое слово мезотипа)**.

> **Ключевая идея**: `Type` сам по себе является обобщённым типом. `(T: Type) -> Type` означает
> «тип, принимающий параметр типа T».

| Понятие            | Запись в коде                                                                |
| ------------------ | ---------------------------------------------------------------------------- |
| Переменная         | `x: Int = 42`                                                                |
| Функция            | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи         | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс          | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Обобщённый тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Обобщённый тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод              | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Обобщённая функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово мезотипа в языке**.

> **Пространство имён vs привязка метода**: Префикс `Type.name` означает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` вида `p.draw(screen)` работал, необходима явная привязка: `Point.draw = draw[0]`.
> Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он используется для
> обозначения уровня типов; компилятор автоматически различает Type0, Type1, Type2... — это
> прозрачно для пользователя.

```yaoxiang
// Основной синтаксис: унификация + различение

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Тип записи
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути — тип записи, все поля которого — функции)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (синтаксис Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    "Point(${self.x}, ${self.y})"
}

// Обобщённый тип ((T: Type) -> Type = обобщённый тип, принимающий параметр типа)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурная подтипизация: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая система типов содержит несколько разрозненных концепций:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (различный)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельная унификация**: одно правило синтаксиса покрывает все случаи
2. **Простота и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих элементов синтаксиса
4. **Теоретическая элегантность**: сам тип является значением типа Type
5. **Дружелюбность к дженерикам**: бесшовная интеграция с системой обобщений (RFC-011)

### Интеграция с системой обобщений

Унифицированная синтаксическая модель RFC-010 и дизайн системы обобщений RFC-011 **естественно
согласуются** — параметры обобщений органично вписываются в унифицированную модель:

```yaoxiang
// Базовые обобщения (RFC-011 Phase 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Обобщённая функция (синтаксис RFC-023: позиция Type в сигнатуре может быть опущена, вывод при вызове)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничение типа (RFC-011 Phase 2)
clone: (value: T) -> T = value.clone()  // ограничение T: Clone переносится типом параметра

// Const-обобщения (RFC-011 Phase 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовые обобщения) — **сильная зависимость** для RFC-010
- Без базовых обобщений примеры обобщений в RFC-010 не скомпилируются
- Рекомендация: RFC-011 Phase 1 и RFC-010 реализуются синхронно

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила устранения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                                     |
| ------------------- | ---------------------- | ----------------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | `: Type` объявлен явно → принудительно тип                  |
| **`f = ...`**       | Функция или переменная | Нет `: Type` → HM самостоятельно выводит функцию/переменную |

**Почему именно так?**

Синтаксис `{ ... }` сам по себе неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (выполняемый оператор, возвращающий Void)

**Правило устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM самостоятельно интерпретирует `{ ... }` как блок кода, выводится
  функциональный тип

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит () -> Void
main: () -> Void = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может интерпретировать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит функцию, а не тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # без : Type, HM выводит функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # должен возвращать: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # должен возвращать: Type
│
├── Обобщённый тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # должен возвращать: Type
│
├── Обобщённый тип (несколько параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # должен возвращать: Type
│
├── Функция в пространстве имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # только после явной привязки доступен синтаксис через точку
│
└── Обобщённая функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # не возвращает Type, HM выводит функцию
```

### Иерархия мезотипов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Level    | Описание                               |
| -------- | -------------------------------------- |
| `Type0`  | Обычные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)   |
| `Type2+` | Конструкторы высшего порядка           |

**Пользователь никогда не видит этих чисел**, только `: Type`.

### Изоморфизм Карри-Ховарда: тип есть утверждение, программа есть доказательство

Унифицированный синтаксис YaoXiang `name: type = value` — не случайный выбор: он представляет собой
прямое отображение изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм
раскрывает глубокий факт: **система типов и логическая система — это две стороны одного и того же**.

| Логика (утверждение)                  | Система типов (YaoXiang)              | Пример                               |
| ------------------------------------- | ------------------------------------- | ------------------------------------ |
| Утверждение P                         | Тип T                                 | `Int`, `Bool`                        |
| Доказательство P                      | Значение типа T                       | `42: Int`, `true: Bool`              |
| P → Q (импликация)                    | Функциональный тип `(P) -> Q`         | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)                    | Тип записи `{ p: P, q: Q }`           | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (универсальная квантификация) | Обобщённая функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)                    | Enum / tagged union                   | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в свете Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int по имени x со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: дано доказательство Int a и доказательство Int b, можно построить доказательство Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — утверждение, доказательство которого требует одновременно доказательство Float x и доказательство Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = типобезопасность**: если система типов позволяет
   сконструировать значение типа `T` без какого-либо легитимного представления во время выполнения,
   это подобно тому, как в логике позволяется доказывать ложное утверждение — система рушится.
   Карри-Ховард говорит нам: **типобезопасный язык по своей природе является непротиворечивой
   логической системой**.

2. **Иерархия вселенных — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (то есть «тип типа тоже тип»), возникает парадокс Рассела (в теории типов
   проявляющийся как парадокс Жирара). Слоистая структура YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   гарантирует, что каждый тип принадлежит только одному уровню, образуя никогда не замыкающуюся
   восходящую цепь, что фундаментально предотвращает парадоксы. Это означает, что система типов
   YaoXiang в смысле Карри-Ховарда **логически непротиворечива**.

3. **Теоретическое обоснование унифицированного синтаксиса**: причина, по которой
   `name: type = value` может одним синтаксисом покрыть переменные, функции, типы, интерфейсы и
   обобщения, заключается в том, что в свете Карри-Ховарда все они суть одно и то же —
   **предоставление доказательства для утверждения**. Переменная — свидетельство утверждения,
   функция — свидетельство импликации, запись — свидетельство конъюнкции, обобщение — свидетельство
   универсальной квантификации. Унифицированный синтаксис — не искусственно созданное совпадение, а
   естественное следствие изоморфизма Карри-Ховарда.

> **Дополнительное чтение**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступно объясняет историю и значение изоморфизма Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типа (можно опустить)
y = 100  // выводится Int
```

#### 2. Определение функций

**Значение блока = хвостовое выражение, `return` осуществляет выход из функции (тип `Never`)** —
подробности см. в [RFC-010a](010a-tail-expression-and-return.md).

```yaoxiang
// Форма с одним выражением
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Форма с блоком кода: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b                    // хвостовое выражение → значение блока
}

// Многострочный блок кода
calc: (x: Float, y: Float, op: String) -> Float = {
    match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }                    // match как хвостовое выражение
}

// Функция Void: хвостовое выражение имеет тип Void
print: (msg: String) -> Void = {
    console.write(msg)   // console.write : Void
}
```

#### Правила возврата

**Значение блока = хвостовое выражение (единственный выход)**:

| Запись                                             | Значение                                |
| -------------------------------------------------- | --------------------------------------- |
| `= expr` (без фигурных скобок)                     | `expr`                                  |
| `= { ...; e }` (с фигурными скобками)              | хвостовое выражение `e`                 |
| `= { ...; s }` (последний — оператор/присваивание) | `Void` (значение присваивания — `Void`) |
| `= {}` (пустой блок)                               | `Void`                                  |

**Семантика `return`**: нелокальный выход, **выход из ближайшей границы функции** (а не «возврат в
блок»), тип `Never`. `Never <: T` выполняется для любого типа (принцип взрыва), поэтому `return`
может находиться в любой позиции возвращаемого типа.

```yaoxiang
# Одно выражение: непосредственно возвращает значение
add: (a: Int, b: Int) -> Int = a + b

# Блок кода: значение — хвостовое выражение
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    b
}

# Досрочный возврат: return проходит сквозь блок, выходит из функции (тип Never)
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    n * factorial(n - 1)     # хвостовое выражение
}
```

**Обоснование дизайна**: `{ ... }` — это единица вычислений, управляемая зависимостями (см. ниже),
семантика вычисления которой отличается от одного выражения — фигурные скобки вводят контекст
нескольких операторов, **его значение определяется хвостовым выражением**, неоднозначность «является
ли последнее выражение возвращаемым значением» отсутствует.

#### Семантика `{}`: единица вычислений, управляемая зависимостями

`{ ... }` в YaoXiang — не просто блок кода, это **единица вычислений, управляемая зависимостями**.
Эта семантика единообразна в телах функций, инициализации переменных и `spawn`:

**Основные правила**:

- Операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- Когда зависимости готовы, выполнение начинается немедленно; при их отсутствии — блокируется до
  готовности
- **Значение блока = хвостовое выражение** (см. правила возврата); `return` — нелокальный выход типа
  `Never`, выходит из функции

```yaoxiang
# Управление зависимостями: b зависит от a, компилятор автоматически сортирует
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # без зависимостей → может выполниться первым
    b              # хвостовое выражение → значение блока 11
}
```

> **Отличие от одного выражения**: `= expr` (без фигурных скобок) — простое связывание,
> непосредственно возвращающее значение; `= { ... }` (с фигурными скобками) вводит контекст
> вычислений, управляемый зависимостями, допускает несколько операторов, его значение определяется
> хвостовым выражением.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитива в YaoXiang. Он использует семантику `{}` с
управлением зависимостями для автоматического распараллеливания:

- Прямые дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- Задачи с готовыми зависимостями немедленно выполняются параллельно
- Вызывающая сторона блокируется до завершения всех дочерних задач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (нет зависимости от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ожидает их завершения
    c                         # хвостовое выражение → значение spawn
}
// Вызывающий блокируется здесь до завершения всех задач в блоке spawn
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> см. в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций с сырыми указателями. Он
использует семантику вычисления `{}`, передавая определение типов внешней области видимости (выход
значения — хвостовое выражение):

**Основные правила**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- **Хвостовое выражение** задаёт значение `unsafe {}` (определение типов передаётся внешней области
  видимости)
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует разрешения unsafe

```yaoxiang
# Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    SqliteDb           # хвостовое выражение → значение unsafe-блока
}

# SqliteDb доступен за пределами unsafe-блока
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: поле handle требует разрешения unsafe
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов см.
> в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализации интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть произвольными выражениями типов.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang состоит из трёх слоёв, последовательно распознаваемых на разных
фазах компиляции:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявления, такие как `if`, `match`, `pub`, `return`
2. **Зарезервированные литералы** (отдельные токены парсера) — `true`, `false`, `void`, `Type`, не
   могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные в тайп-чекере) — парсер
   обрабатывает их как обычные идентификаторы, распознавание выполняет тайп-чекер. **Не являются
   зарезервированными, могут быть затенены (не рекомендуется)**

Различие между `void` (в нижнем регистре, зарезервированный литерал) и `Void` (в верхнем регистре,
имя встроенного типа): `void` — литерал значения (равен единственному значению Unit), `Void` — имя
типа (равен типу Unit, логически ⊤). Запись `let x: Void = void` допустима.

Предопределённые имена встроенных типов:

| Тип      | Логика              | Описание                                                                                                                                                                                                                                                                                    |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевой конструктор, ни одно значение не может населять этот тип. Означает «невозможно» — расходимость, паника, мёртвый код. `Never <: T` для любого `T` (принцип взрыва). Функция, возвращающая `Never`, никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (по умолчанию значение void). `x: Void = <по умолчанию>` допустимо. Единица для типов-сумм соответствует единице для типов-произведений — `Void` — это произведение с нулём полей (Unit), `Never` — сумма с нулём вариантов.                                           |
| `Int`    | —                   | Знаковое целое число                                                                                                                                                                                                                                                                        |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                    |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                       |
| `Char`   | —                   | Unicode-символ                                                                                                                                                                                                                                                                              |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                      |

##### Привязка методов

**Способ 1: прямое связывание внешней функции в теле определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        (dx * dx + dy * dy).sqrt()      # хвостовое выражение
    })
}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

##### Реализация интерфейса

**Имя интерфейса записывается в теле типа, компилятор автоматически проверяет реализацию**

```yaoxiang
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

Point: Type = {
    x: Float,
    y: Float,
    Drawable,          // реализует интерфейс Drawable
    Serializable      // реализует интерфейс Serializable
}
```

##### Определение интерфейса

**Интерфейс = тип записи, все поля которого — функции**

```yaoxiang
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Пустой тип / пустой интерфейс
EmptyType: Type = {}
Empty: Type = {}
```

##### Определение функций в пространстве имён

**Префикс `Type.name` означает принадлежность к пространству имён**, и ничего более. Он не вызывает
никакой неявной привязки.

```yaoxiang
// Функция в пространстве имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    "Point(${p.x}, ${p.y})"
}

// Вызов: обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` — не ключевое слово, а лишь устоявшееся имя параметра. Запись `p`, `this`,
> `x` работает совершенно одинаково. Компилятор смотрит на тип, а не на имя параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` вида `p.draw(screen)` работал, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции в качестве «метода»
(подробный синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после этого доступен синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающим

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // обе формы вызова эквивалентны

// Без [0] — без привязки. Point.draw — обычный псевдоним функции, без синтаксиса .
Point.draw = draw       // без привязки: только Point.draw(p, screen)
```

**Поведение по умолчанию**: отсутствие `[n]` = ни один параметр не привязан. Пользователь должен
явно решить, какие параметры заполняются вызывающим.

**Многопозиционная привязка**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 3.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Обобщённые типы

```yaoxiang
// Базовые обобщения (RFC-011 Phase 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретизация (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // Пример вызова

// Обобщённый метод (синтаксис RFC-023: параметры типа выводятся в точке вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        Maybe.Just(self.data[index])
    } else {
        Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова обобщений

Для вызова обобщённых типов и обобщённых функций единообразно используется синтаксис `()`. `[]` не
используется ни в каком обобщённом контексте.

**Основные правила**:

1. **`()` делает всё**: применение типа, вызов функции, конструирование значения — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся слева
empty: List(Int) = List()

# Вызов обобщённой функции — типы автоматически «протекают» из аргументов
strings = map(numbers, f)
// T=Int берётся из numbers: List(Int)
// R=String берётся из f: (Int) -> String
```

2. **Type слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. Для пустого контейнера `List()` `T` должен быть получен из левой
   аннотации типа.

3. **Информация о типе записывается только один раз** — в объявлении параметра, компилятор проносит
   её дальше:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int записывается один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически берутся из типов numbers и f
```

4. **Тип значения-конструктора выводится из элементов**:

```yaoxiang
x = List(1, 2, 3)       // выводится List(Int)
y = List("a", "b")      // выводится List(String)
z = List()              // ❌ ошибка компиляции: невозможно вывести T
z: List(Int) = List()   // ✅ T=Int берётся из левой аннотации
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис обобщений через `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

    scale: (factor: Float) -> Transformable

// ======== 2. Определения типов ========

}

}

}

}

    dy = p1.y - p2.y

}

// Явная привязка — только после неё доступен синтаксис вызова через точку

Point.serialize = serialize[0]
Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

Rect.bounding_box = bounding_box[0]

Rect.serialize = serialize[0]

Rect.translate = translate[0]

}
Rect.scale = scale[0]

// ======== 4. Использование ========

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (поля-функции)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, есть ли у типа метод с тем же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатуры метода
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: после удаления self-параметра должны совпасть
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации на этапе компиляции

Интерфейсный тип поддерживает прямое присваивание; компилятор автоматически выберет оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип известен на этапе компиляции, вызов с нулевыми накладными расходами
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возвращаемое значение функции → конкретный тип не может быть определён на этапе компиляции, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Разнородная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегии оптимизации на этапе компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Разнородный           | vtable                                   |

**Правила**:

1. Когда правая часть является конкретным конструктором типа и может быть определена на этапе
   компиляции, генерируется IR прямого вызова
2. Когда тип правой части не может быть определён на этапе компиляции, выполняется откат к механизму
   vtable
3. vtable служит страховкой для корректности полиморфизма во время выполнения

### Синтаксические изменения

| До                                       | После                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `type Point = Point(x: Float, y: Float)` | `type Point = { x: Float, y: Float }`                                                        |
| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| Требуется ключевое слово `impl`          | Ключевое слово не требуется, имена интерфейсов записываются в теле типа                      |

### Устаревший: синтаксис вариантов через `|`

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов через `|` официально устарел и
> удалён из реализации.

Следующие формы записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Единообразно используются типы записей для выражения и типов-сумм (sum type). Когда все поля типа
записи являются функциями, и все они возвращают сам этот тип, он является типом-суммой:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особого случая**: `|` — единственный синтаксис в BNF, не укладывающийся в форму
   `name: type = value`. После удаления продукция `type_expr` полностью унифицирована, парсеру
   больше не нужно поддерживать отдельный путь и предпросмотр с откатом для вариантных типов.
2. **Математическая эквивалентность**: в свете изоморфизма Карри-Ховарда дизъюнкция P ⊕ Q,
   соответствующая типу-сумме, эквивалентна типу записи «с полями-функциями, возвращающими сам этот
   тип». Они выражают одну и ту же семантику, иметь два синтаксиса нет необходимости.
3. **Нулевая разрушительность**: до удаления синтаксис `|` был в парсере на полпути (варианты без
   параметров разбирались, но типы параметров терялись при мономорфизации); ни один пользовательский
   код на него не полагался.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы проходят
   через путь `Type::Struct`, все специальные ветки нижестоящих тайпчека/моно/форматтера устранены.

> **Примечание**: семантические свойства типов-сумм (такие как проверка полноты match, размещение
> tagged union в памяти) выводятся слоем тайпчека из структуры `Type::Struct` и не зависят от
> отдельного узла AST.

### Логические операторы: `and` / `or` / `!` (каноническое определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: канонической формой логических операторов являются
> ключевые слова `and` / `or` + символьный унарный `!` (согласуется с таблицей приоритетов SPEC
> `syntax.md` §2.2). Этот дизайн соответствует Zig: **для короткозамыкающего потока управления
> используются ключевые слова, для чистых унарных операций — символы**. Ранние реализации `&&` /
> `||` в стиле C, а также промежуточное ключевое слово `not` были удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)               | Ассоциативность | Семантика                                             |
| -------- | ----------------------------------- | --------------- | ----------------------------------------------------- |
| `!`      | 3 (унарный префикс, сильная связка) | справа налево   | Логическое НЕ (чистая функция, без потока управления) |
| `and`    | 10                                  | слева направо   | Короткозамыкающее логическое И                        |
| `or`     | 10                                  | слева направо   | Короткозамыкающее логическое ИЛИ                      |

```yaoxiang
# Короткое замыкание: при and слева false / при or слева true правая часть не вычисляется
if x != 0 and y / x > 1 { ... }   # при x == 0 деления на ноль не произойдёт

# Сильная связка: !a == b ≡ (!a) == b (в стиле Zig; в отличие от Python: not a == b ≡ not (a == b))
!3 == 4          # false: (!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs)), вызов с последующим отрицанием
```

Следующие формы записи **больше не поддерживаются** (лексер сообщает об ошибке и подсказывает
правильный вариант):

```
x && y     # ❌ удалено, используйте x and y
x || y     # ❌ удалено, используйте x or y
not x      # ❌ удалено, используйте !x (not снова становится обычным идентификатором; != не затрагивается)
```

**Обоснование дизайна** (в соответствии с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — это поток управления → ключевое слово; чистая функция — это операция →
   символ**. `and` / `or` изменяют порядок вычисления (правая часть пропускается по необходимости),
   по своей природе аналогичны `if`, поэтому используются ключевые слова; `!` выполняет чистое
   отрицание уже вычисленного операнда, по своей природе аналогичен `-` `+`, поэтому используется
   символ. Распространение ошибок в YaoXiang использует `?` (§2.11), `!` не конфликтует.
2. **Сильная связка устраняет неоднозначность**: `!` визуально «прилипает» к операнду, высокий
   приоритет очевиден; ключевое слово `not` вынуждено отделяться пробелом от операнда, что вызывает
   когнитивную неоднозначность в отношении того, к чему оно привязано (`not a == b`).
3. **Устранение неоднозначности**: `&` несёт двойную функцию — токен заимствования (`&p` / `&mut p`,
   RFC-009) и побитовое И (SPEC §2.2, приоритет 8). Введение `&&` заставит один символ нести три
   значения. `and` / `or` / `!` визуально полностью разделяют заимствование, побитовые операции и
   логику.
4. **Прецедент**: Zig (современный системный язык того же экологического нишевого положения)
   использует именно комбинацию ключевых слов `and` / `or` + символ `!`; Python / Lua / Ada / SQL
   используют полностью ключевые слова (включая `not`), семейство C — полностью символы — YaoXiang
   берёт гибрид Zig, объединяя преимущества обоих подходов.
5. **Согласованность с Карри-Ховардом**: тип есть утверждение (см. раздел об изоморфизме выше),
   логические связки в уточняющих типах естественно записывать как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`); `!` как символ унарного отрицания соответствует ¬.

> **Реализация**: `and` / `or` на уровне IR разворачиваются в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`); `!` разбирается как унарный оператор сильной
> связки (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Объяснение дизайна синтаксиса: именованная функция — это синтаксический сахар для лямбды

### Ключевое понимание

**Именованная функция и лямбда-выражение — это одно и то же!** Единственное различие: именованная
функция даёт лямбде имя.

```yaoxiang
// Эти две записи по сути совершенно одинаковы
add: (a: Int, b: Int) -> Int = a + b           // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда в сигнатуре полностью объявлены типы параметров, имена параметров в
заголовке лямбды становятся избыточными и могут быть опущены.

### Правила области видимости параметров

**Параметры перекрывают внешние переменные**: область видимости параметров в сигнатуре перекрывает
тело функции, внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x перекрывает внешний x, результат 20
```

### Гибкое расположение аннотаций

Аннотации типов могут располагаться в любом из следующих мест, **достаточно аннотации хотя бы в
одном**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но разрешено |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: сигнатура полная, заголовок лямбды опущен
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Допустимо: типы аннотированы в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Допустимо: аннотации в обоих местах
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство          | Преимущество                                                                   |
| ----------------- | ------------------------------------------------------------------------------ |
| **Краткость**     | При полной сигнатуре не нужно повторять имена параметров                       |
| **Гибкость**      | Сохранена лямбда-форма, можно использовать любую понравившуюся                 |
| **Единообразие**  | Сохраняет унифицированный паттерн с объявлением переменной `x: Int = 42`       |
| **Интуитивность** | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### Синтаксис BNF

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражение типа
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # Применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # Функциональный тип
       | '{' type_field* '}'                       # Тип записи / интерфейс
       | 'Type'                                    # Мезотип

type_field ::= identifier ':' type_expr
             | identifier                           # Ограничение интерфейса

# Параметр обобщения: как часть функционального типа, например (T: Type, R: Type) -> (...)
# Не требует отдельного правила BNF — параметр : Type — это обычный параметр функции

# Выражение
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # Вызов функции / вызов конструктора
              | '(' expression (',' expression)* ')'              # Кортеж
              | expression '.' identifier '(' arguments? ')'    # Вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                      | Определение                                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Объявление                  | Оператор присваивания вида `name: type = value`                                                                       |
| Тип записи                  | `{ ... }` тип с именованными полями                                                                                   |
| Интерфейс                   | Тип записи, все поля которого — функциональные типы                                                                   |
| Обобщённый тип              | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                 |
| Функция в пространстве имён | Функция вида `Type.name`, принадлежащая пространству имён Type. Не предполагает никакой привязки                      |
| Привязка метода             | `Type.name = func[n]`, привязывает позицию n функции func как вызывающего, делая доступным синтаксис `obj.name(args)` |
| Обобщённая функция          | Функция, использующая синтаксис `(T: Type)`, параметры типа как первая группа параметров                              |
| Мезотип                     | `Type`, единственный маркер уровня типа в языке                                                                       |
