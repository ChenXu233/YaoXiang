# RFC-010: Унифицированный синтаксис типов - модель name: type = value

## Резюме

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
как ключевое слово для метатипа)**.

> **Ключевая идея**: `Type` сам по себе является родовым (дженерик) типом. `(T: Type) -> Type`
> означает «тип, принимающий параметр типа T».

| Понятие         | Запись в коде                                                                |
| --------------- | ---------------------------------------------------------------------------- |
| Переменная      | `x: Int = 42`                                                                |
| Функция         | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи      | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс       | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Родовой тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Родовой тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод           | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Родовая функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово метатипа в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` обозначает лишь **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` вроде `p.draw(screen)` работал, необходима явная привязка:
> `Point.draw = draw[0]`. Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он
> используется для маркировки уровня типов; компилятор автоматически обрабатывает различение Type0,
> Type1, Type2... — это прозрачно для пользователя.

```yaoxiang
// Ключевой синтаксис: унификация + различение

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Тип записи
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути тип записи, все поля которого — функции)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (синтаксис Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    return "Point(${self.x}, ${self.y})"
}

// Родовой тип ((T: Type) -> Type = родовой тип, принимающий параметр типа)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурная подтипизация: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая система типов содержит несколько разрозненных концепций:

- синтаксис объявления переменных
- синтаксис определения функций
- синтаксис определения типов (другой синтаксис)
- синтаксис определения интерфейсов
- синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельная унификация**: одно синтаксическое правило покрывает все случаи
2. **Краткость и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих элементов синтаксиса
4. **Теоретическая элегантность**: сам тип — это значение типа Type
5. **Дружелюбность к дженерикам**: бесшовная интеграция с системой дженериков (RFC-011)

### Интеграция с системой дженериков

Унифицированная синтаксическая модель RFC-010 **естественно согласуется** с дизайном системы
дженериков RFC-011, а параметры дженериков органично вписываются в унифицированную модель:

```yaoxiang
// Базовые дженерики (RFC-011 Phase 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Родовая функция (синтаксис RFC-023: позиция Type в сигнатуре может быть опущена, выводится при вызове)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничения типа (RFC-011 Phase 2)
clone: (value: T) -> T = value.clone()  // ограничение T: Clone переносится типом параметра

// Const-дженерики (RFC-011 Phase 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовые дженерики) — **сильная зависимость** для RFC-010
- Без базовых дженериков примеры с дженериками в RFC-010 не скомпилируются
- Рекомендация: реализовать RFC-011 Phase 1 и RFC-010 одновременно

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила устранения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                                     |
| ------------------- | ---------------------- | ----------------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | явное объявление `: Type` → принудительно тип               |
| **`f = ...`**       | Функция или переменная | нет `: Type` → HM самостоятельно выводит функцию/переменную |

**Почему именно так?**

Синтаксис `{ ... }` сам по себе неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM интерпретирует `{ ... }` как блок кода, выводится функциональный тип

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит () -> Void
main = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может интерпретировать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит функцию, а не тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # нет : Type, HM выводит функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # должен возвращать: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # должен возвращать: Type
│
├── Родовой тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # должен возвращать: Type
│
├── Родовой тип (несколько параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # должен возвращать: Type
│
├── Функция пространства имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # только после явной привязки доступен синтаксис с точкой
│
└── Родовая функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # не возвращает Type, HM выводит функцию
```

### Иерархия метатипов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Уровень  | Описание                                    |
| -------- | ------------------------------------------- |
| `Type0`  | Повседневные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)        |
| `Type2+` | Конструкторы более высокого порядка         |

**Пользователь никогда не видит этих номеров**, только `: Type`.

### Изоморфизм Карри-Ховарда: типы как высказывания, программы как доказательства

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он представляет собой
прямое отображение изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм
раскрывает глубокий факт: **система типов и логическая система — это две стороны одной и той же
сущности**.

| Логика (высказывание)         | Система типов (YaoXiang)           | Пример                               |
| ----------------------------- | ---------------------------------- | ------------------------------------ |
| Высказывание P                | Тип T                              | `Int`, `Bool`                        |
| Доказательство истинности P   | Значение типа T                    | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | Функциональный тип `(P) -> Q`      | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | Тип записи `{ p: P, q: Q }`        | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Родовая функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | Перечисление / tagged union        | `Maybe: (T: Type) -> Type = { ... }` |

**Что означает `name: type = value` в контексте Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int, именуемое x, со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: даны доказательства a и b типа Int, можно построить доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — высказывание, доказательство которого требует одновременного предоставления доказательств типа Float x и типа Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = безопасность типов**: если система типов позволяет
   сконструировать значение типа `T` без какого-либо законного представления во время выполнения,
   это подобно тому, как в логике позволяется доказать ложное высказывание — система рушится.
   Карри-Ховард говорит нам: **язык с безопасной системой типов по своей сути является
   непротиворечивой логической системой**.

2. **Иерархия вселенных — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (т.е. «тип типа — это тип»), возникает парадокс Рассела (в теории типов
   проявляющийся как парадокс Жирара). Стратификация YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   гарантирует, что каждый тип принадлежит только одному уровню, формируя бесконечно восходящую
   цепь, что фундаментально предотвращает парадоксы. Это означает, что система типов YaoXiang
   **логически непротиворечива** в смысле Карри-Ховарда.

3. **Теоретическое обоснование унифицированного синтаксиса**: `name: type = value` способен покрыть
   одним синтаксисом переменные, функции, типы, интерфейсы и дженерики именно потому, что в рамках
   Карри-Ховарда все они — одно и то же — **предоставление доказательства для высказывания**.
   Переменные — свидетельства высказывания, функции — свидетельства импликации, записи —
   свидетельства конъюнкции, дженерики — свидетельства квантора всеобщности. Унифицированный
   синтаксис — не искусственное совпадение, а естественное следствие изоморфизма Карри-Ховарда.

> **Дополнительная литература**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступно объясняет историю и значение изоморфизма Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типа (можно опустить)
y = 100  // выводится как Int
```

#### 2. Определение функций

```yaoxiang
// Форма с одним выражением (возвращает значение напрямую, без return)
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Форма с блоком кода (необходимо использовать return для возврата значения)
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

// Многострочный блок кода
calc: (x: Float, y: Float, op: String) -> Float = {
    return match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }
}

// Функция Void (в блоке кода return не нужен)
print: (msg: String) -> Void = {
    console.write(msg)
}
```

#### Правила возврата

Возвращаемое значение зависит от формы в правой части `=`:

| Запись                             | Возвращаемое значение                       |
| ---------------------------------- | ------------------------------------------- |
| `= expr` (без фигурных скобок)     | напрямую возвращает `expr`                  |
| `= { ... }` (с фигурными скобками) | требуется `return`, иначе возвращает `Void` |

```yaoxiang
# Одно выражение: возвращает значение напрямую, return не нужен
add: (a: Int, b: Int) -> Int = a + b

# Блок кода: требуется return для возврата значения
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

# Функция Void: return не нужен
print: (msg: String) -> Void = {
    console.write(msg)
}
```

> **Обоснование дизайна**: `{ ... }` — это вычислительная единица, управляемая зависимостями (см.
> ниже), семантика возврата которой отличается от одиночного выражения. Фигурные скобки вводят
> многооператорный контекст, поэтому необходим явный `return` для устранения неоднозначности
> «является ли последнее выражение возвращаемым значением».

#### Семантика `{}`: вычислительная единица, управляемая зависимостями

`{ ... }` в YaoXiang — это не просто блок кода, а **вычислительная единица, управляемая
зависимостями**. Эта семантика остаётся согласованной в телах функций, инициализации переменных и
`spawn`:

**Ключевые правила**:

- Операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- Как только зависимости удовлетворены, выполнение происходит немедленно; при отсутствии —
  блокировка и ожидание
- Для явного возврата значения используется `return` (см. правила возврата)

```yaoxiang
# Управление зависимостями: b зависит от a, компилятор автоматически упорядочит
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # без зависимостей → может выполняться первым
    return b       # вернёт 11
}
```

> **Отличие от одиночного выражения**: `= expr` (без фигурных скобок) — простая привязка, напрямую
> возвращающая значение; `= { ... }` (с фигурными скобками) вводит контекст вычислений, управляемый
> зависимостями, допускающий несколько операторов и явный `return`.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитивная конструкция в YaoXiang. Она использует
семантику зависимостей `{}` для автоматического распараллеливания:

- Прямые дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- Задачи с удовлетворёнными зависимостями немедленно выполняются конкурентно
- Вызывающая сторона блокируется до завершения всех дочерних задач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (нет зависимости от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ожидает завершения обоих
    return c
}
// Вызывающий код блокируется здесь до завершения всех задач в spawn-блоке
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> описаны в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций над сырыми указателями.
Он использует семантику `return` из `{}` для передачи определения типа во внешнюю область видимости:

**Ключевые правила**:

- В `unsafe {}` можно определять типы и работать с сырыми указателями
- Используйте `return` для передачи определения типа во внешнюю область видимости
- Возвращаемый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует разрешения unsafe

```yaoxiang
# Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    return SqliteDb
}

# SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: доступ к полю handle требует разрешения unsafe
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов
> описаны в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализацию интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть произвольными выражениями типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, опциональные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang имеет три уровня, распознаваемых на разных фазах компилятора:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявления, такие как `if`, `match`, `pub`, `return`
2. **Зарезервированные литералы** (отдельные токены парсера) — `true`, `false`, `void`, `Type`, не
   могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные в type checker) — парсер
   обрабатывает их как обычные идентификаторы, их разрешает проверщик типов. **Не являются
   зарезервированными словами, могут быть затенены (не рекомендуется)**

Различие между `void` (в нижнем регистре, зарезервированный литерал) и `Void` (в верхнем регистре,
имя встроенного типа): `void` — литерал значения (равен единственному значению Unit), `Void` — имя
типа (равен типу Unit, логически ⊤). `let x: Void = void` — допустимая запись.

Предопределённые имена встроенных типов:

| Тип      | Логический аналог   | Описание                                                                                                                                                                                                                                                                                                                              |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевое количество конструкторов, никакие значения не могут населять этот тип. Выражает «невозможность» — расходимость, panic, мёртвый код. `Never <: T` выполняется для любого `T` (принцип взрыва). Функция с возвратом `Never` означает, что она никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (по умолчанию значение void). `x: Void = <default>` допустимо. Соответствует нейтральному элементу суммы и нейтральному элементу произведения — `Void` — это нульарный тип-произведение (Unit), `Never` — нульарный тип-сумма.                                                                                   |
| `Int`    | —                   | Знаковое целое                                                                                                                                                                                                                                                                                                                        |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                                                              |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                                                                 |
| `Char`   | —                   | Unicode-символ                                                                                                                                                                                                                                                                                                                        |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                                                                |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        return (dx * dx + dy * dy).sqrt()
    })
}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

##### Определение функций пространства имён

**Префикс `Type.name` обозначает лишь принадлежность к пространству имён**, и ничего более. Он не
вызывает никакой неявной привязки.

```yaoxiang
// Функция пространства имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    return "Point(${p.x}, ${p.y})"
}

// Вызов: это обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` — не ключевое слово, а просто конвенциональное имя параметра. Запись `p`,
> `this`, `x` работает совершенно одинаково. Компилятор смотрит на тип, а не на имя параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` вроде `p.draw(screen)` работал, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции в качестве «метода»
(подробный синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после этого доступен синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающей стороной

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // оба способа вызова эквивалентны

// Без [0] = без привязки. Point.draw — просто псевдоним обычной функции, синтаксис с . недоступен
Point.draw = draw       // без привязки: только Point.draw(p, screen)
```

**Поведение по умолчанию**: без `[n]` = ни один параметр не привязывается. Пользователь должен явно
решить, какие параметры заполняются вызывающей стороной.

**Привязка нескольких позиций**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 3.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Родовые типы

```yaoxiang
// Базовые дженерики (RFC-011 Phase 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретизация (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    return (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // пример вызова

// Родовой метод (синтаксис RFC-023: параметры типа выводятся автоматически в точке вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        return Maybe.Just(self.data[index])
    } else {
        return Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова дженериков

Вызов родовых типов и родовых функций унифицированно использует синтаксис `()`. `[]` не используется
ни в каком контексте дженериков.

**Ключевые правила**:

1. **`()` для всего**: применение типов, вызов функций, конструирование значений — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся слева
empty: List(Int) = List()

# Вызов родовой функции — типы автоматически перетекают из аргументов
strings = map(numbers, f)
// T=Int берётся из numbers: List(Int)
// R=String берётся из f: (Int) -> String
```

2. **Тип слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. Для пустого контейнера `List()` его `T` должен браться из левой
   аннотации типа.

3. **Информацию о типе достаточно записать один раз** — в объявлении параметра, компилятор переносит
   её:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int записан один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически из типов numbers и f
```

4. **Конструирование значения с выводом типа из элементов**:

```yaoxiang
x = List(1, 2, 3)       // выводится как List(Int)
y = List("a", "b")      // выводится как List(String)
z = List()              // ❌ ошибка компиляции: невозможно вывести T
z: List(Int) = List()   // ✅ T=Int берётся из левой аннотации
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис дженериков `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и индексации.

### Алгоритм проверки интерфейса

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (функционального поля)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, есть ли у типа метод с тем же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатур методов
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: после удаления self-параметра должно совпадать
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизация на этапе компиляции

Тип интерфейса поддерживает прямое присваивание; компилятор автоматически выбирает оптимальную
стратегию вызова в зависимости от типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип известен на этапе компиляции, вызов без накладных расходов
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возвращаемое значение функции → конкретный тип не известен на этапе компиляции, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Гетерогенная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегии оптимизации на этапе компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                   |

**Правила**:

1. Когда правая часть является конструктором конкретного типа и известна на этапе компиляции,
   генерируется IR прямого вызова
2. Когда тип правой части не может быть определён на этапе компиляции, происходит откат к механизму
   vtable
3. vtable как страховка гарантирует корректность полиморфизма во время выполнения

### Изменения синтаксиса

| До                                       | После                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `type Point = Point(x: Float, y: Float)` | `type Point = { x: Float, y: Float }`                                                        |
| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| Требуется ключевое слово `impl`          | Ключевое слово не нужно, имя интерфейса записывается после тела типа                         |

### Устаревшее: синтаксис вариантов `|`

> **Объявление об устаревании (2026-07-25, issue #203)**: синтаксис вариантов `|` официально устарел
> и удалён из реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Единый способ выражения типов суммы (sum type) — через тип записи. Когда все поля типа записи
являются функциями, каждая из которых возвращает сам этот тип, он является типом суммы:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особого случая**: `|` — единственная в BNF форма синтаксиса, не являющаяся
   `name: type = value`. После удаления продукция `type_expr` полностью унифицирована, и парсеру
   больше не нужно поддерживать отдельный путь и предпросмотр с возвратом для вариантных типов.
2. **Математическая эквивалентность**: в рамках изоморфизма Карри-Ховарда дизъюнкция P ⊕ Q,
   соответствующая типу суммы, эквивалентна типу записи «все поля которого — функции, возвращающие
   сам этот тип». Они выражают одну и ту же семантику, и двух наборов синтаксиса не требуется.
3. **Нулевая разрушительность**: до удаления синтаксис `|` был в парсере на полуподдержке (варианты
   без параметров разбирались, но типы параметров терялись при мономорфизации), и никакой
   пользовательский код от него не зависел.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы идут по пути
   `Type::Struct`, специальные ветки в нижестоящих typecheck/mono/formatter полностью устранены.

> **Примечание**: семантические свойства типов суммы (такие как проверка полноты match, размещение в
> памяти tagged union) выводятся на уровне typecheck из структуры `Type::Struct` и не зависят от
> отдельного узла AST.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03, ревизия issue #251)**: авторитетной формой логических
> операторов являются ключевые слова `and` / `or` + символьный унарный `!` (согласно таблице
> приоритетов §2.2 в SPEC `syntax.md`). Данный дизайн согласован с Zig: **для короткозамыкающего
> потока управления — ключевые слова, для чистых унарных операций — символы**. Ранние реализации,
> дрейфующие к C с `&&` / `||`, а также промежуточное ключевое слово `not` — все удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                   | Ассоциативность | Семантика                                             |
| -------- | --------------------------------------- | --------------- | ----------------------------------------------------- |
| `!`      | 3 (унарный префикс, плотное связывание) | справа налево   | Логическое НЕ (чистая функция, без потока управления) |
| `and`    | 10                                      | слева направо   | Короткозамыкающее логическое И                        |
| `or`     | 10                                      | слева направо   | Короткозамыкающее логическое ИЛИ                      |

```yaoxiang
# Короткое замыкание: при and слева false / при or слева true правая часть не выполняется
if x != 0 and y / x > 1 { ... }   # при x == 0 деления на ноль не будет

# Плотное связывание: !a == b ≡ (!a) == b (в стиле Zig; в отличие от Python: not a == b ≡ not (a == b))
!3 == 4          # false: (!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs)), вызов с последующим отрицанием
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке с подсказкой
соответствующей записи):

```
x && y     # ❌ удалено, используйте x and y
x || y     # ❌ удалено, используйте x or y
not x      # ❌ удалено, используйте !x (not возвращён в статус обычного идентификатора; != не затронут)
```

**Обоснование дизайна** (согласовано с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — поток управления → ключевое слово; чистая функция — операция → символ**.
   `and` / `or` изменяют порядок вычисления (правая часть пропускается по необходимости), что по
   характеру аналогично `if` — используется ключевое слово; `!` выполняет чистое отрицание уже
   вычисленного операнда, что по характеру аналогично `-` `+` — используется символ. В YaoXiang
   распространение ошибок использует `?` (§2.11), конфликта с `!` нет.
2. **Плотное связывание устраняет неоднозначность**: `!` визуально «прилегает» к операнду, высокий
   приоритет очевиден; ключевое слово `not` вынужденно отделяется пробелом от операнда, и к чему оно
   привязывается (`not a == b`) вызывает мысленную неоднозначность.
3. **Устранение конфликта**: `&` выполняет две роли — токен заимствования (`&p` / `&mut p`, RFC-009)
   и побитовое И (приоритет 8 в SPEC §2.2). Введение `&&` заставит один символ нести три значения.
   `and` / `or` / `!` делают заимствование, побитовые операции и логику визуально полностью
   разделёнными.
4. **Прецедент**: Zig (системный язык того же экологического нишевого положения) использует именно
   комбинацию ключевых слов `and` / `or` + символ `!`; Python / Lua / Ada / SQL используют полностью
   ключевые слова (включая `not`); семейство C использует полностью символы — YaoXiang берёт микс
   Zig, получая преимущества обоих подходов.
5. **Согласованность с Карри-Ховардом**: типы суть высказывания (см. раздел об изоморфизме выше),
   логические связки в уточняющих типах записываются как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`) — это естественная запись высказываний; унарный `!` как символ
   соответствует ¬.

> **Реализация**: `and` / `or` раскрываются в IR-уровне в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`), `!` разбирается с плотным связыванием унарного
> оператора (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Пояснения к дизайну синтаксиса: именованные функции по сути являются синтаксическим сахаром для лямбда-выражений

### Ключевое понимание

**Именованные функции и лямбда-выражения — это одно и то же!** Единственное отличие: именованная
функция даёт лямбда-выражению имя.

```yaoxiang
// Эти две записи по сути полностью идентичны
add: (a: Int, b: Int) -> Int = a + b           // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = Лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, заголовок лямбда-выражения
с именами параметров становится избыточным и может быть опущен.

### Правила области видимости параметров

**Параметры перекрывают внешние переменные**: область видимости параметров в сигнатуре перекрывает
тело функции, внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x перекрывает внешний x, результат 20
```

### Гибкое расположение аннотаций

Аннотация типа может располагаться в любом из следующих мест, **достаточно аннотации хотя бы в
одном**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но разрешено |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: полная сигнатура, заголовок лямбды опускается
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Допустимо: типы в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Допустимо: аннотации в обоих местах
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство            | Преимущество                                                                   |
| ------------------- | ------------------------------------------------------------------------------ |
| **Краткость**       | При полной сигнатуре не нужно повторять имена параметров                       |
| **Гибкость**        | Сохранена лямбда-форма, используйте ту, которая нравится                       |
| **Согласованность** | Соответствует шаблону объявления переменной `x: Int = 42`                      |
| **Интуитивность**   | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### Синтаксис BNF

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражение типа
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # функциональный тип
       | '{' type_field* '}'                       # тип записи/интерфейса
       | 'Type'                                    # метатип

type_field ::= identifier ':' type_expr
             | identifier                           # ограничение интерфейса

# Параметр дженерика: как часть функционального типа, например (T: Type, R: Type) -> (...)
# Отдельное правило BNF не требуется — параметр : Type — это обычный параметр функции

# Выражение
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # вызов функции / вызов конструктора
              | '(' expression (',' expression)* ')'              # кортеж
              | expression '.' identifier '(' arguments? ')'    # вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                    | Определение                                                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Объявление                | Оператор присваивания формы `name: type = value`                                                                                    |
| Тип записи                | Тип `{ ... }` с именованными полями                                                                                                 |
| Интерфейс                 | Тип записи, все поля которого — функциональные типы                                                                                 |
| Родовой тип               | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                               |
| Функция пространства имён | Функция формы `Type.name`, принадлежащая пространству имён Type. Не предполагает никакой привязки                                   |
| Привязка метода           | `Type.name = func[n]`, привязка позиции n функции func в качестве вызывающей стороны, делающая доступным синтаксис `obj.name(args)` |
| Родовая функция           | Функция, использующая синтаксис `(T: Type)`, параметры типа выступают как первая группа параметров                                  |
| Метатип                   | `Type`, единственный маркер уровня типов в языке                                                                                    |
