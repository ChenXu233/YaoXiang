# RFC-010: Унифицированный синтаксис типов — модель name: type = value

## Резюме

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
как ключевое слово метамта-типа)**.

> **Ключевая идея**: `Type` сам по себе является дженерик-типом. `(T: Type) -> Type` означает «тип,
> принимающий параметр типа T».

| Концепция        | Написание кода                                                               |
| ---------------- | ---------------------------------------------------------------------------- |
| Переменная       | `x: Int = 42`                                                                |
| Функция          | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи       | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс        | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Дженерик-тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Дженерик-тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод            | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Дженерик-функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово метамта-типа в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` обозначает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакого неявного связывания. Чтобы синтаксис
> вызова через `.` вроде `p.draw(screen)` работал, требуется явная привязка: `Point.draw = draw[0]`.
> Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он используется для
> обозначения уровня типа, компилятор автоматически обрабатывает различие между Type0, Type1,
> Type2... прозрачно для пользователя.

```yaoxiang
// 核心语法：统一 + 区分

// 变量
x: Int = 42

// 函数（参数名在签名中）
add: (a: Int, b: Int) -> Int = a + b

// 记录类型
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// 接口（本质是字段全为函数的记录类型）
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// 方法定义（使用 Type.method 语法）
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    return "Point(${self.x}, ${self.y})"
}

// 泛型类型（(T: Type) -> Type = 接受类型参数的泛型类型）
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// 使用
p: Point = Point(1.0, 2.0)
p.draw(screen)           // 语法糖 → Point.draw(p, screen)
s: Drawable = p           // 结构子类型：Point 实现 Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая система типов содержит несколько разрозненных концепций:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (различный синтаксис)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельное единство**: одно правило синтаксиса покрывает все случаи
2. **Простота и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих синтаксических элементов
4. **Теоретическая элегантность**: сам тип является значением типа `Type`
5. **Дженерик-дружественность**: бесшовная интеграция с системой дженериков (RFC-011)

### Интеграция с системой дженериков

Унифицированная синтаксическая модель RFC-010 **естественно согласуется** с дизайном системы
дженериков RFC-011, параметры дженериков органично вписываются в унифицированную модель:

```yaoxiang
// 基础泛型（RFC-011 Phase 1）
List: (T: Type) -> Type = { data: Array(T), length: Int }

// 泛型函数（RFC-023 语法：签名中 Type 位置可省略，调用时自动推断）
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// 类型约束（RFC-011 Phase 2）
clone: (value: T) -> T = value.clone()  // T: Clone 约束由参数类型携带

// Const泛型（RFC-011 Phase 4）
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- Phase 1 RFC-011 (базовые дженерики) — **сильная зависимость** для RFC-010
- Без базовых дженериков примеры дженериков в RFC-010 не скомпилируются
- Рекомендация: Phase 1 RFC-011 реализовать одновременно с RFC-010

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила снятия синтаксической неоднозначности:**

| Написание           | Значение               | Правило                                        |
| ------------------- | ---------------------- | ---------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | Явное объявление `: Type` → принудительно тип  |
| **`f = ...`**       | Функция или переменная | Без `: Type` → HM-вывод для функции/переменной |

**Почему именно так?**

Синтаксис `{ ... }` сам по себе неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий `Void`)

**Правила снятия неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM-вывод интерпретирует `{ ... }` как блок кода, выводится тип функции

```yaoxiang
# ✅ 类型构造器：有 : Type
Point: Type = { x: Float, y: Float }

# ✅ 函数：没有 : Type，HM 推断为 () -> Void
main = { println("Hello") }

# ❌ 错误：没有 : Type，编译器无法将 { ... } 解析为类型
Point = { x: Float, y: Float }  // HM 推断为函数，不是类型！
```

---

**Унифицированная модель: identifier : type = expression**

```
├── 变量
│   └── x: Int = 42
│
├── 函数
│   └── add: (a: Int, b: Int) -> Int = a + b  # 无 : Type，HM 推断为函数
│
├── 记录类型
│   └── Point: Type = { x: Float, y: Float }  # 必须返回： Type
│
├── 接口
│   └── Drawable: Type = { draw: (Surface) -> Void }  # 必须返回： Type
│
├── 泛型类型
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # 必须返回： Type
│
├── 泛型类型（多参数）
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # 必须返回： Type
│
├── 命名空间函数
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # 显式绑定后才有点调用语法
│
└── 泛型函数
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # 不返回 Type，HM 推断为函数
```

### Уровни метамта-типа (внутреннее представление компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Уровень  | Описание                               |
| -------- | -------------------------------------- |
| `Type0`  | Обычные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)   |
| `Type2+` | Конструкторы высшего порядка           |

**Пользователь никогда не видит этих чисел**, только `: Type`.

### Изоморфизм Карри-Ховарда: тип как утверждение, программа как доказательство

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он представляет собой
прямое отображение изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм
раскрывает глубокий факт: **система типов и логическая система — это две стороны одной сущности**.

| Логика (утверждение)                  | Система типов (YaoXiang)            | Пример                               |
| ------------------------------------- | ----------------------------------- | ------------------------------------ |
| Утверждение P                         | Тип T                               | `Int`, `Bool`                        |
| Доказательство истинности P           | Значение типа T                     | `42: Int`, `true: Bool`              |
| P → Q (импликация)                    | Тип функции `(P) -> Q`              | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)                    | Тип записи `{ p: P, q: Q }`         | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (универсальная квантификация) | Дженерик-функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)                    | Enum / tagged union                 | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в рамках Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" 读作："存在一个 Int 类型的证明，名为 x，其值为 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" 读作：
// "存在一个蕴含证明：给定 Int 的证明 a 和 b，可构造 Int 的证明"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" 读作：
// "Point 是一个命题，其证明需要同时提供 Float 证明 x 和 Float 证明 y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = типобезопасность**: если система типов позволяет конструировать
   значение типа `T` без какого-либо допустимого представления во время выполнения, это подобно
   тому, как в логике разрешают доказать ложное утверждение — система рушится. Карри-Ховард говорит
   нам: **типобезопасный язык по своей сути является непротиворечивой логической системой**.

2. **Иерархия вселенной — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (то есть «тип типа тоже является типом»), возникнет парадокс Рассела (в теории типов
   проявляющийся как парадокс Жирара). Слоистая структура YaoXiang `Type₀ : Type₁ : Type₂ : ...`
   гарантирует, что каждый тип принадлежит строго определённому уровню, формируя бесконечно
   восходящую цепочку, что фундаментально устраняет парадоксы. Это означает, что система типов
   YaoXiang **логически непротиворечива** в смысле Карри-Ховарда.

3. **Теоретическое обоснование унифицированного синтаксиса**: `name: type = value` способен одной
   формой синтаксиса покрыть все концепции — переменные, функции, типы, интерфейсы, дженерики —
   именно потому, что в рамках Карри-Ховарда все они суть одно и то же — **предоставление
   доказательства для утверждения**. Переменная — свидетельство утверждения, функция — свидетельство
   импликации, запись — свидетельство конъюнкции, дженерик — свидетельство универсальной
   квантификации. Унифицированный синтаксис — не искусственное совпадение, а естественное следствие
   изоморфизма Карри-Ховарда.

> **Дальнейшее чтение**: Wadler, P. (2015). _«Propositions as Types». Communications of the ACM,
> 58(12), 75–84. Эта статья доступно объясняет историю и значение изоморфизма Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// 基本语法
x: Int = 42
name: String = "Alice"
flag: Bool = true

// 类型推导（可省略）
y = 100  // 推断为 Int
```

#### 2. Определение функций

```yaoxiang
// 单表达式形式（直接返回值，无需 return）
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// 代码块形式（必须用 return 返回值）
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

// 多行代码块
calc: (x: Float, y: Float, op: String) -> Float = {
    return match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }
}

// Void 函数（代码块内不需要 return）
print: (msg: String) -> Void = {
    console.write(msg)
}
```

#### Правила возврата

Возвращаемое значение зависит от формы в правой части `=`:

| Написание                          | Возвращаемое значение                         |
| ---------------------------------- | --------------------------------------------- |
| `= expr` (без фигурных скобок)     | Напрямую возвращает `expr`                    |
| `= { ... }` (с фигурными скобками) | Требуется `return`, иначе возвращается `Void` |

```yaoxiang
# 单表达式：直接返回值，不需要 return
add: (a: Int, b: Int) -> Int = a + b

# 代码块：必须用 return 返回值
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

# Void 函数：不需要 return
print: (msg: String) -> Void = {
    console.write(msg)
}
```

> **Обоснование дизайна**: `{ ... }` является зависимо-управляемой вычислительной единицей (см.
> ниже), её семантика возврата отличается от одиночного выражения. Фигурные скобки вводят контекст
> нескольких операторов, поэтому требуется явный `return` для устранения неоднозначности «является
> ли последнее выражение возвращаемым значением».

#### Семантика `{}`: зависимо-управляемая вычислительная единица

`{ ... }` в YaoXiang — это не просто блок кода, а **зависимо-управляемая вычислительная единица**.
Эта семантика остаётся согласованной в телах функций, инициализаторах переменных и `spawn`:

**Ключевые правила**:

- Операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- Когда зависимости готовы, выполнение происходит немедленно; при их отсутствии — блокировка и
  ожидание
- Используйте `return` для явного возврата значения (см. правила возврата)

```yaoxiang
# 依赖驱动：b 依赖 a，编译器自动排序
result: Int = {
    b = a + 1      # 依赖 a → 自动排在 a 之后
    a = 10         # 无依赖 → 可以先执行
    return b       # 返回 11
}
```

> **Отличие от одиночного выражения**: `= expr` (без фигурных скобок) — это простое связывание с
> прямым возвратом значения; `= { ... }` (с фигурными скобками) вводит контекст зависимо-управляемых
> вычислений, допускающий несколько операторов и явный `return`.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитива YaoXiang. Она использует зависимо-управляемую
семантику `{}` для автоматического распараллеливания:

- Прямые дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- Задачи с готовыми зависимостями немедленно выполняются конкурентно
- Вызывающая сторона блокируется до завершения всех дочерних задач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # 任务 1
    b = fetch_data("url2")    # 任务 2（与 a 无依赖，并行执行）
    c = process(a, b)         # 依赖 a, b → 等待两者完成后执行
    return c
}
// 调用方在此阻塞，直到 spawn 块内所有任务完成
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> описаны в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и работы с сырыми указателями. Он
использует семантику `return` в `{}` для возврата определения типа во внешнюю область видимости:

**Ключевые правила**:

- Внутри `unsafe {}` можно определять типы и работать с сырыми указателями
- Используйте `return` для возврата определения типа во внешнюю область видимости
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует прав `unsafe`

```yaoxiang
# 在 unsafe 块中定义不透明类型
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # 裸指针
    }
    return SqliteDb
}

# SqliteDb 在 unsafe 块外可用
db = sqlite3_open("test.db")

# ❌ 编译错误：handle 字段需要 unsafe 权限
handle = db.handle

# ✅ 通过方法调用
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение типов FFI и привязка методов
> описаны в `ffi.md`.

#### 3. Определение типов

Определение типа — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализацию интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть любыми выражениями типов.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang состоит из трёх слоёв, распознаваемых на разных этапах компиляции:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявления, такие как `if`, `match`, `pub`, `return`
2. **Зарезервированные литералы** (отдельные токены парсера) — `true`, `false`, `void`, `Type`, не
   могут быть обычными идентификаторами
3. **Имена встроенных типов** (предварительно зарегистрированные в тайп-чекере) — парсер
   рассматривает их как обычные идентификаторы, тайп-чекер отвечает за разрешение. **Не являются
   зарезервированными, могут быть затенены (не рекомендуется)**

Различие между `void` (в нижнем регистре, зарезервированный литерал) и `Void` (в верхнем регистре,
имя встроенного типа): `void` — литерал значения (равен единственному значению Unit), `Void` — имя
типа (равен типу Unit, логически ⊤). `let x: Void = void` — допустимо.

Предопределённые имена встроенных типов:

| Тип      | Логика              | Описание                                                                                                                                                                                                                                                                                                  |
| -------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевое количество конструкторов, ни одно значение не может населять этот тип. Обозначает «невозможно» — расходимость, panic, мёртвый код. `Never <: T` для любого `T` (принцип взрыва). Функция, возвращающая `Never`, никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (по умолчанию значение `void`). `x: Void = <по умолчанию>` допустимо. Единичный элемент для типа-суммы, соответствующий единичному элементу для типа-произведения — `Void` является типом-произведением с нулём полей (Unit), `Never` — типом-суммой с нулём вариантов.              |
| `Int`    | —                   | Знаковое целое                                                                                                                                                                                                                                                                                            |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                                  |
| `Bool`   | —                   | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                                     |
| `Char`   | —                   | Символ Unicode                                                                                                                                                                                                                                                                                            |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                                    |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // 绑定到位置0，柯里化后 method: (b: Point) -> Float
}
// 调用：p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        return (dx * dx + dy * dy).sqrt()
    })
}
// 语法：((params) => body)[position]
// 调用：p1.distance(p2) → distance(p1, p2)
```

##### Определение функций пространства имён

**Префикс `Type.name` обозначает принадлежность к пространству имён**, и ничего более. Он не
вызывает никакого неявного связывания.

```yaoxiang
// 命名空间函数：在 Point 命名空间下的普通函数
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    return "Point(${p.x}, ${p.y})"
}

// 调用：就是普通函数调用
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` не является ключевым словом, это лишь соглашение об именовании параметра.
> Запись `p`, `this`, `x` даёт совершенно одинаковый эффект. Компилятор смотрит на тип, а не на имя
> параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` вроде `p.draw(screen)` работал, **требуется явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции в качестве «метода»
(подробный синтаксис см. в RFC-004).

```yaoxiang
// 定义函数
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// 显式绑定 — 这之后才有 p.draw(screen) 语法
Point.draw = draw[0]   // 位置 0 的参数（&Point）由调用者填充

// 使用
p.draw(screen)          // 语法糖 → draw(&p, screen)
Point.draw(p, screen)   // 两种调用方式等价

// 不写 [0] = 不绑定。Point.draw 就是普通函数别名，没有 . 语法
Point.draw = draw       // 不绑定：只能 Point.draw(p, screen)
```

**Поведение по умолчанию**: не указан `[n]` = никакие параметры не привязываются. Пользователь
должен явно решить, какие параметры заполняются вызывающей стороной.

**Многопозиционная привязка**:

```yaoxiang
// 绑定多个位置（自动柯里化）
Point.transform = transform_points[0, 1]
// 调用：p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// 从绑定中取出函数
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Дженерик-типы

```yaoxiang
// 基础泛型（RFC-011 Phase 1）
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// 具体实例化（RFC-023 语法）
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    return (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // 调用示例

// 泛型方法（RFC-023 语法：类型参数由调用处自动推断）
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        return Maybe.Just(self.data[index])
    } else {
        return Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова дженериков

Вызов дженерик-типов и дженерик-функций统一 использует синтаксис `()`. `[]` не используется ни в
каком контексте дженериков.

**Ключевые правила**:

1. **`()` выполняет всё применение**: применение типов, вызов функций, конструирование значений —
   всё через `()`

```yaoxiang
# 类型标注
numbers: List(Int) = List(1, 2, 3)

# 空容器：T 从左侧来
empty: List(Int) = List()

# 泛型函数调用——类型从参数自动流动
strings = map(numbers, f)
// T=Int 来自 numbers: List(Int)
// R=String 来自 f: (Int) -> String
```

2. **Тип слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. Для пустого контейнера `List()` его `T` должен браться из аннотации
   типа слева.

3. **Информация о типе записывается только один раз** — в объявлении параметра, компилятор проносит
   её далее:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int в левой части записывается один раз
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически из типов numbers и f
```

4. **Конструирование значения выводит тип из элементов**:

```yaoxiang
x = List(1, 2, 3)       // 推断为 List(Int)
y = List("a", "b")      // 推断为 List(String)
z = List()              // ❌ 编译错误：无法推断 T
z: List(Int) = List()   // ✅ T=Int 来自左侧注解
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис дженериков `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

#### Полный пример

```yaoxiang
// ======== 1. 接口定义 ========
// 接口 = 字段全是函数类型的记录类型
// 接口中不需要 self 参数 — 接口只定义"去掉调用者位置后的函数签名"

Drawable: Type = {
    draw: (surface: Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

Transformable: Type = {
    translate: (dx: Float, dy: Float) -> Transformable,  // 返回接口类型，具体实现返回自己的类型
    scale: (factor: Float) -> Transformable
}

// ======== 2. 类型定义 ========

Point: Type = {
    x: Float,
    y: Float,
    Drawable,
    Serializable,
    Transformable
}

Rect: Type = {
    x: Float,
    y: Float,
    width: Float,
    height: Float,
    Drawable,
    Serializable,
    Transformable
}

// ======== 3. 方法实现（普通函数 + 显式绑定）========

// 定义函数（self 只是约定名，不是关键字）
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

bounding_box: (p: &Point) -> Rect = {
    return Rect(p.x - 1, p.y - 1, 2, 2)
}

serialize: (p: &Point) -> String = {
    return "Point(${p.x}, ${p.y})"
}

translate: (p: &Point, dx: Float, dy: Float) -> Point = {
    return Point(p.x + dx, p.y + dy)
}

scale: (p: &Point, factor: Float) -> Point = {
    return Point(p.x * factor, p.y * factor)
}

distance: (p1: &Point, p2: &Point) -> Float = {
    dx = p1.x - p2.x
    dy = p1.y - p2.y
    return (dx * dx + dy * dy).sqrt()
}

// 显式绑定 — 绑定后才有点调用语法
Point.draw = draw[0]
Point.bounding_box = bounding_box[0]
Point.serialize = serialize[0]
Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

// Rect 的方法也类似
draw: (r: &Rect, surface: Surface) -> Void = {
    surface.draw_rect(r.x, r.y, r.width, r.height)
}
Rect.draw = draw[0]

bounding_box: (r: &Rect) -> Rect = r
Rect.bounding_box = bounding_box[0]

serialize: (r: &Rect) -> String = {
    return "Rect(${r.x}, ${r.y}, ${r.width}, ${r.height})"
}
Rect.serialize = serialize[0]

translate: (r: &Rect, dx: Float, dy: Float) -> Rect = {
    return Rect(r.x + dx, r.y + dy, r.width, r.height)
}
Rect.translate = translate[0]

scale: (r: &Rect, factor: Float) -> Rect = {
    return Rect(r.x * factor, r.y * factor, r.width * factor, r.height * factor)
}
Rect.scale = scale[0]

// ======== 4. 使用 ========

// 创建实例
p: Point = Point(1.0, 2.0)
r: Rect = Rect(0.0, 0.0, 10.0, 20.0)

// 方法调用（语法糖）
p.draw(screen)
r.draw(screen)

// 普通方法调用（直接调用）
d: Float = distance(p, Point(0.0, 0.0))

// 链式调用
p2: Point = p.translate(1.0, 1.0).scale(2.0)

// 接口赋值
drawables: List(Drawable) = [p, r]
for d in drawables {
    d.draw(screen)
}

// 泛型函数（RFC-023 语法：调用时省略类型参数，自动推断）
process_all: (items: List(T)) -> Void = {
    for item in items {
        print(item.serialize())
    }
}

process_all([p, r])
```

## Детальный дизайн

### Алгоритм проверки интерфейсов

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // 对于接口的每个字段（函数字段）
    for (field_name, iface_field) in &iface.fields {
        // 检查类型是否有同名方法
        if let Some(method) = typ.methods.get(field_name) {
            // 检查方法签名是否兼容
            // 接口字段: (Surface) -> Void
            // 方法签名: (Point, Surface) -> Void
            // 比较：去掉 self 参数后应该匹配
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации на этапе компиляции

Типы интерфейсов поддерживают прямое присваивание, компилятор автоматически выберет оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// 直接赋值具体类型 → 编译期可确定具体类型，零开销调用
d: Drawable = Circle(1)
d.draw(screen)  // 编译后：直接调用 circle_draw(screen)，无 vtable

// 函数返回值 → 编译期无法确定具体类型，使用 vtable
d: Drawable = get_shape()
d.draw(screen)  // 通过 vtable 查找方法

// 异构集合 → 使用 vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // 通过 vtable 查找方法
}
```

**Стратегии оптимизации на этапе компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                   |

**Правила**:

1. Когда правая часть является конструктором конкретного типа, известным на этапе компиляции,
   генерируется IR с прямым вызовом
2. Когда тип правой части не может быть определён на этапе компиляции, выполняется откат на механизм
   vtable
3. vtable как страховка обеспечивает корректность runtime-полиморфизма

### Изменения синтаксиса

| Ранее                                    | Далее                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |

### Устаревший синтаксис: варианты через `|`

> **Объявление об устаревании (2026-07-25)**: синтаксис вариантов через `|` официально устарел и
> удалён из реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ 废弃
type Result(T, E) = ok(T) | err(E)             # ❌ 废弃
type Option(T) = some(T) | none                # ❌ 废弃
```

Единообразно используются типы записей для выражения и типов суммы (sum type). Когда все поля типа
записи являются функциями, каждая из которых возвращает сам этот тип, он является типом суммы:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особого случая**: `|` — единственная в BNF форма синтаксиса, отличная от
   `name: type = value`. После удаления продукция `type_expr` полностью унифицирована, парсеру
   больше не нужно поддерживать отдельный путь и упреждающий откат для типов вариантов.
2. **Математическая эквивалентность**: в рамках изоморфизма Карри-Ховарда дизъюнкции P ⊕ Q
   соответствует тип суммы, эквивалентный типу записи «поля которого все являются функциями,
   возвращающими сам этот тип». Они выражают одну и ту же семантику и не требуют двух разных
   синтаксисов.
3. **Нулевая разрушительность**: до удаления синтаксис `|` в парсере поддерживался наполовину
   (варианты без аргументов могли быть разобраны, но типы аргументов терялись при мономорфизации),
   ни один пользовательский код на него не полагался.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все типы вариантов统一 идут по
   пути `Type::Struct`, все особые ветви в downstream-этапах (typecheck/mono/formatter) устранены.

> **Примечание**: семантические свойства типов суммы (такие как проверка полноты match, размещение в
> памяти tagged union) выводятся на слое typecheck из структуры `Type::Struct` и не зависят от
> отдельного узла AST.

### Логические операторы: `and` / `or` / `!` (авторитетное определение, в стиле Zig)

> **Объявление определения (2026-08-03)**: авторитетная форма логических операторов — ключевые слова
> `and` / `or` + символьный унарный `!` (согласно таблице приоритетов SPEC `syntax.md` §2.2). Этот
> дизайн согласован с Zig: **управление потоком с коротким замыканием — ключевыми словами, чистые
> унарные операции — символами**. Ранние реализации, дрейфующие к C, `&&` / `||` и промежуточное
> ключевое слово `not` — все удалены.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)                   | Ассоциативность | Семантика                                                    |
| -------- | --------------------------------------- | --------------- | ------------------------------------------------------------ |
| `!`      | 3 (унарный префикс, плотное связывание) | справа налево   | Логическое отрицание (чистая функция, без потока управления) |
| `and`    | 10                                      | слева направо   | Короткое замыкание логического И                             |
| `or`     | 10                                      | слева направо   | Короткое замыкание логического ИЛИ                           |

```yaoxiang
# 短路求值：and 左侧为 false / or 左侧为 true 时，右侧不执行
if x != 0 and y / x > 1 { ... }   # x == 0 时不会除零

# 紧绑定：!a == b ≡ (!a) == b（Zig 式；与 Python 的 not a == b ≡ not (a == b) 相反）
!3 == 4          # false：(!3) == 4 → false
!(3 == 4)        # true
!x != 0          # ≡ (!x) != 0
!list.is_empty(xs)   # ≡ !(list.is_empty(xs))，调用后取反
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке с подсказкой
соответствующей записи):

```
x && y     # ❌ 已移除，用 x and y
x || y     # ❌ 已移除，用 x or y
not x      # ❌ 已移除，用 !x（not 恢复为普通标识符；!= 不受影响）
```

**Обоснование дизайна** (согласовано с Zig, ziglang/zig#272 / #6625):

1. **Короткое замыкание — это поток управления → ключевое слово; чистая функция — это операция →
   символ**. `and` / `or` изменяют порядок вычисления (правая часть пропускается при необходимости),
   по природе аналогичны `if`, и используют ключевые слова; `!` выполняет чистое отрицание уже
   вычисленного операнда, по природе аналогично `-` `+`, и использует символ. Распространение ошибок
   в YaoXiang использует `?` (§2.11), `!` не конфликтует.
2. **Плотное связывание устраняет неоднозначность**: `!` визуально «плотно прилегает» к операнду,
   высокий приоритет очевиден; ключевое слово `not` вынуждено отделяться пробелом от операнда, и
   неясно, к чему оно привязывается (`not a == b`), что вызывает ментальную неоднозначность.
3. **Разделение смысла**: `&` несёт двойную функцию — токен заимствования (`&p` / `&mut p`, RFC-009)
   и побитовое И (SPEC §2.2 приоритет 8). Введение `&&` заставит один символ нести три значения.
   `and` / `or` / `!` визуально полностью разделяют заимствование, побитовые операции и логику.
4. **Прецедент**: Zig (системный язык того же экологического слота) именно комбинирует ключевые
   слова `and` / `or` и символ `!`; Python / Lua / Ada / SQL используют все ключевые слова (включая
   `not`), семейство C — все символы — YaoXiang берёт гибрид Zig, получая преимущества обоих
   подходов.
5. **Согласованность с Карри-Ховардом**: тип есть утверждение (см. раздел об изоморфизме выше),
   логические связки в уточняющих типах записываются как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`) — это естественное выражение утверждений; `!` как символ
   унарного отрицания соответствует ¬.

> **Реализация**: `and` / `or` раскрываются на уровне IR в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`), `!` разбирается с плотным унарным связыванием
> (операнд по `BP_UNARY + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Обоснование синтаксического дизайна: именованные функции — синтаксический сахар над лямбдами

### Ключевое понимание

**Именованная функция и лямбда-выражение — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// 这两者本质完全相同
add: (a: Int, b: Int) -> Int = a + b           // 具名函数（推荐）
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // Lambda 形式（完全等价）
```

### Модель синтаксического сахара

```
// 具名函数 = Lambda + 名字
name: (Params) -> ReturnType = body

// 本质上是
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, имена параметров в
заголовке лямбды становятся избыточными и могут быть опущены.

### Правила области видимости параметров

**Параметры затеняют внешние переменные**: область видимости параметров в сигнатуре перекрывает тело
функции, внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // 外层变量

double: (x: Int) -> Int = x * 2  // ✅ 参数 x 覆盖外层 x，结果为 20
```

### Гибкое расположение аннотаций

Аннотации типов могут располагаться в любом из следующих мест, **достаточно аннотации хотя бы в
одном**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ Рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ Допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ Избыточно, но разрешено |

### Полные примеры

```yaoxiang
// ✅ 推荐：签名完整，Lambda 头部省略
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ 合法：Lambda 头中标注类型
double = (x: Int) => x * 2

// ✅ 合法：两边都标注
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство            | Преимущество                                                                   |
| ------------------- | ------------------------------------------------------------------------------ |
| **Краткость**       | Не нужно повторять имена параметров, когда сигнатура полная                    |
| **Гибкость**        | Сохранена лямбда-форма, используйте то, что нравится                           |
| **Согласованность** | Соответствует унифицированному шаблону `x: Int = 42` для объявления переменных |
| **Интуитивность**   | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### БНФ грамматики

```bnf
program ::= statement*

statement ::= declaration | expression

# 统一声明：name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# 类型表达式
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # 类型应用
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # 函数类型
       | '{' type_field* '}'                       # 记录/接口类型
       | 'Type'                                    # 元类型

type_field ::= identifier ':' type_expr
             | identifier                           # 接口约束

# 泛型参数：作为函数类型的一部分，如 (T: Type, R: Type) -> (...)
# 无需独立的 BNF 规则——: Type 参数就是普通函数参数

# 表达式
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # 函数调用 / 构造器调用
              | '(' expression (',' expression)* ')'              # 元组
              | expression '.' identifier '(' arguments? ')'    # 方法调用
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                    | Определение                                                                                                                       |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Объявление                | Оператор присваивания в форме `name: type = value`                                                                                |
| Тип записи                | Тип `{ ... }` с именованными полями                                                                                               |
| Интерфейс                 | Тип записи, все поля которого являются типами функций                                                                             |
| Дженерик-тип              | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                             |
| Функция пространства имён | Функция в форме `Type.name`, принадлежащая пространству имён Type. Не подразумевает никакой привязки                              |
| Привязка метода           | `Type.name = func[n]`, привязка позиции n функции func в качестве вызывающей стороны, делает доступным синтаксис `obj.name(args)` |
| Дженерик-функция          | Функция, использующая синтаксис `(T: Type)`, параметры типа являются первой группой параметров                                    |
| Метатип                   | `Type`, единственный маркер уровня типа в языке                                                                                   |
