# RFC-010: Унифицированный синтаксис типов - модель name: type = value

## Резюме

Настоящий RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

YaoXiang имеет лишь одну форму объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
как ключевое слово мезотипа)**.

> **Ключевая идея**: `Type` сам по себе является обобщённым типом. `(T: Type) -> Type` означает
> «тип, принимающий параметр типа T».

| Понятие            | Запись кода                                                                  |
| ------------------ | ---------------------------------------------------------------------------- |
| Переменная         | `x: Int = 42`                                                                |
| Функция            | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи         | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс          | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Обобщённый тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Обобщённый тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод              | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Обобщённая функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово мезотипа в языке**.

> **Пространство имён vs привязка метода**: Префикс `Type.name` обозначает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` вида `p.draw(screen)` работал, необходима явная привязка: `Point.draw = draw[0]`.
> Подробности см. в разделе «Пространство имён и привязка метода» ниже. Он используется для
> маркировки уровня типов; компилятор автоматически обрабатывает различие Type0, Type1, Type2...,
> что прозрачно для пользователя.

```yaoxiang
// Основной синтаксис: унификация + различие

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Тип записи
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути — тип записи, все поля которого — функции)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (синтаксис Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    return "Point(${self.x}, ${self.y})"
}

// Обобщённый тип ((T: Type) -> Type = обобщённый тип, принимающий параметры типа)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурная подтипизация: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая система типов содержит несколько разрозненных концепций:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (различный синтаксис)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельное единство**: одно правило синтаксиса покрывает все случаи
2. **Кратсота и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих элементов синтаксиса
4. **Теоретическая элегантность**: сам тип также является значением типа Type
5. **Дружелюбие к обобщениям**: бесшовная интеграция с системой обобщений (RFC-011)

### Интеграция с системой обобщений

Унифицированная синтаксическая модель RFC-010 **органично сочетается** с дизайном системы обобщений
RFC-011, параметры обобщений бесшовно вписываются в унифицированную модель:

```yaoxiang
// Базовые обобщения (RFC-011 Phase 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Обобщённая функция (синтаксис RFC-023: позиция Type в сигнатуре может быть опущена, автовывод при вызове)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничения типа (RFC-011 Phase 2)
clone: (value: T) -> T = value.clone()  // Ограничение T: Clone переносится типом параметра

// Const-обобщения (RFC-011 Phase 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовые обобщения) — **сильная зависимость** для RFC-010
- Без базовых обобщений примеры обобщений в RFC-010 не скомпилируются
- Рекомендация: реализовать RFC-011 Phase 1 и RFC-010 синхронно

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила устранения неоднозначности синтаксиса:**

| Запись              | Значение               | Правило                                                  |
| ------------------- | ---------------------- | -------------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | Явное объявление `: Type` → принудительно тип            |
| **`f = ...`**       | Функция или переменная | Без `: Type` → HM активно выводит как функцию/переменную |

**Почему именно так?**

Синтаксис `{ ... }` сам по себе неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM активно интерпретирует `{ ... }` как блок кода, выводится как тип функции

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит как () -> Void
main = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может интерпретировать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит как функцию, а не как тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # Нет : Type, HM выводит как функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # Должно вернуть: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # Должно вернуть: Type
│
├── Обобщённый тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # Должно вернуть: Type
│
├── Обобщённый тип (несколько параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # Должно вернуть: Type
│
├── Функция пространства имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # Только после явной привязки появляется синтаксис вызова через точку
│
└── Обобщённая функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # Не возвращает Type, HM выводит как функцию
```

### Иерархия мезотипов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически может быть бесконечно расширена).

| Level    | Описание                               |
| -------- | -------------------------------------- |
| `Type0`  | Обычные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)   |
| `Type2+` | Конструкторы высшего порядка           |

**Пользователь никогда не видит этих чисел**, только `: Type`.

### Изоморфизм Карри-Ховарда: типы как утверждения, программы как доказательства

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он является прямым
отображением изоморфизма Карри-Ховарда (Curry-Howard correspondence). Этот изоморфизм раскрывает
глубокий факт: **система типов и логическая система — это две стороны одной и той же сущности**.

| Логика (утверждение)          | Система типов (YaoXiang)              | Пример                               |
| ----------------------------- | ------------------------------------- | ------------------------------------ |
| Утверждение P                 | Тип T                                 | `Int`, `Bool`                        |
| Доказательство истинности P   | Значение типа T                       | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | Тип функции `(P) -> Q`                | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | Тип записи `{ p: P, q: Q }`           | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Обобщённая функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | Перечисление / tagged union           | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в рамках Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int, с именем x, со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: даны доказательства a и b типа Int, можно сконструировать доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — это утверждение, доказательство которого требует одновременного предоставления доказательств типа Float x и типа Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = типобезопасность**: если система типов позволяет
   сконструировать значение типа `T` без какого-либо легитимного представления во время выполнения,
   это подобно тому, как логика позволяет доказать ложное утверждение — система рушится.
   Карри-Ховард говорит нам: **типобезопасный язык по своей природе является непротиворечивой
   логической системой**.

2. **Иерархия вселенной — необходимое условие**: как подробно описано ниже, разрешение `Type: Type`
   (т.е. «тип типа также является типом») привело бы к парадоксу Рассела (в теории типов проявляется
   как парадокс Жирара). Слоистая структура YaoXiang `Type₀ : Type₁ : Type₂ : ...` гарантирует, что
   каждый тип принадлежит только определённому уровню, формируя никогда не замыкающуюся восходящую
   цепочку, что фундаментально избегает парадоксов. Это означает, что система типов YaoXiang в
   смысле Карри-Ховарда **логически непротиворечива**.

3. **Теоретическое обоснование унифицированного синтаксиса**: `name: type = value` способен покрыть
   все концепции — переменные, функции, типы, интерфейсы, обобщения — одним синтаксисом именно
   потому, что в рамках Карри-Ховарда все они представляют собой одно и то же — **предоставление
   доказательства для утверждения**. Переменная — это свидетельство утверждения, функция —
   свидетельство импликации, запись — свидетельство конъюнкции, обобщение — свидетельство квантора
   всеобщности. Унифицированный синтаксис — не случайность дизайна, а естественное следствие
   изоморфизма Карри-Ховарда.

> **Дополнительная литература**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступным языком объясняет историю и значение изоморфизма
> Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типов (можно опустить)
y = 100  // выводится как Int
```

#### 2. Определение функций

```yaoxiang
// Одно-выражение форма (напрямую возвращает значение, return не нужен)
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Форма блока кода (return обязателен)
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

// Многострочный блок кода
calc: (x: Float, y: Float, op: String) -> Float = {
    return match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }
}

// Функция Void (return в блоке кода не нужен)
print: (msg: String) -> Void = {
    console.write(msg)
}
```

#### Правила возврата

Возвращаемое значение зависит от формы справа от `=`:

| Запись                             | Возвращаемое значение                        |
| ---------------------------------- | -------------------------------------------- |
| `= expr` (без фигурных скобок)     | Напрямую возвращает `expr`                   |
| `= { ... }` (с фигурными скобками) | `return` обязателен, иначе возвращает `Void` |

```yaoxiang
# Одно-выражение: напрямую возвращает значение, return не нужен
add: (a: Int, b: Int) -> Int = a + b

# Блок кода: return обязателен
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

# Функция Void: return не нужен
print: (msg: String) -> Void = {
    console.write(msg)
}
```

> **Обоснование дизайна**: `{ ... }` — это зависимо-управляемая вычислительная единица (см. ниже),
> её семантика возврата отличается от одно-выражения. Фигурные скобки вводят контекст нескольких
> операторов, поэтому необходим явный `return` для устранения неоднозначности «является ли последнее
> выражение возвращаемым значением».

#### Семантика `{}`: зависимо-управляемая вычислительная единица

`{ ... }` в YaoXiang — это не просто блок кода — это **зависимо-управляемая вычислительная
единица**. Эта семантика остаётся согласованной в телах функций, инициализации переменных и `spawn`:

**Основные правила**:

- Операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- Если зависимости готовы — выполняется немедленно, если нет — блокируется в ожидании
- Используйте `return` для явного возврата значения (см. правила возврата)

```yaoxiang
# Управление по зависимостям: b зависит от a, компилятор автоматически упорядочивает
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # без зависимостей → может выполниться первым
    return b       # возвращает 11
}
```

> **Отличие от одно-выражения**: `= expr` (без фигурных скобок) — это простая привязка, напрямую
> возвращающая значение; `= { ... }` (с фигурными скобками) вводит контекст зависимо-управляемых
> вычислений, разрешая многооператорные конструкции и явный `return`.

#### Блок `spawn`

`spawn { ... }` — единственная параллельная примитива в YaoXiang. Она использует
зависимо-управляемую семантику `{}` для автоматического распараллеливания:

- Прямые подприсваивания внутри `spawn { ... }` автоматически создают параллельные задачи
- Задачи с готовыми зависимостями немедленно выполняются конкурентно
- Вызывающая сторона блокируется до завершения всех подзадач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (нет зависимости от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ожидает завершения обоих
    return c
}
// Вызывающая сторона блокируется здесь до завершения всех задач внутри блока spawn
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> см. в `008-runtime-concurrency-model.md`.

#### Блок `unsafe`

`unsafe { ... }` используется для определения непрозрачных типов и операций с сырыми указателями. Он
использует семантику `return` в `{}` для возврата определения типа во внешнюю область видимости:

**Основные правила**:

- Внутри `unsafe {}` можно определять типы и оперировать сырыми указателями
- Используйте `return` для возврата определения типа во внешнюю область видимости
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует разрешения unsafe

```yaoxiang
# Определение непрозрачного типа в блоке unsafe
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    return SqliteDb
}

# SqliteDb доступен за пределами блока unsafe
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: доступ к полю handle требует разрешения unsafe
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение типов FFI и привязка методов см.
> в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализацию интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть любыми выражениями типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
```

##### Встроенные типы

Система идентификаторов YaoXiang имеет три уровня, распознаваемых на разных фазах компилятора:

1. **Ключевые слова** (отдельный токен парсера) — управляющие структуры и ключевые слова объявления,
   такие как `if`, `match`, `pub`, `return`
2. **Литеральные зарезервированные слова** (отдельный токен парсера) — `true`, `false`, `void`,
   `Type`, не могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные в проверке типов) — парсер
   обрабатывает как обычные идентификаторы, за разбор отвечает проверщик типов. **Не являются
   зарезервированными словами, могут быть затенены (не рекомендуется)**

Различие между `void` (нижний регистр, литеральное зарезервированное слово) и `Void` (верхний
регистр, имя встроенного типа): `void` — литерал значения (равен единственному значению Unit),
`Void` — имя типа (равен типу Unit, логически ⊤). `let x: Void = void` — допустимо.

Предустановленные имена встроенных типов:

| Тип      | Логический аналог   | Описание                                                                                                                                                                                                                                                                                                      |
| -------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Never`  | ⊥ (ложь/пустой тип) | Нулевой конструктор, никакое значение не может населять этот тип. Означает «невозможно» — расходимость, паника, мёртвый код. `Never <: T` для любого `T` (принцип взрыва). Функция, возвращающая `Never`, означает, что она никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)     | Ровно один обитатель (значение void по умолчанию). `x: Void = <default>` допустимо. Единица суммы соответствует единице произведения — `Void` — это произведение нуля полей (Unit), `Never` — сумма нуля вариантов.                                                                                           |
| `Int`    | —                   | Целое число со знаком                                                                                                                                                                                                                                                                                         |
| `Float`  | —                   | Число с плавающей точкой                                                                                                                                                                                                                                                                                      |
| `Bool`   | —                   | Булево значение: `true` / `false`                                                                                                                                                                                                                                                                             |
| `Char`   | —                   | Unicode-символ                                                                                                                                                                                                                                                                                                |
| `String` | —                   | Строка                                                                                                                                                                                                                                                                                                        |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела определения типа**

```yaoxiang

Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang

    y: Float = 0,

        dy = a.y - b.y

}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Префикс `Type.name` обозначает принадлежность к пространству имён**, и ничего более. Он не
вызывает никакой неявной привязки.

```yaoxiang
// Функция пространства имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {

}

Point.serialize: (p: &Point) -> String = {
    return "Point(${p.x}, ${p.y})"
}

// Вызов: это обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` не является ключевым словом, это лишь конвенциональное имя параметра.
> Запись `p`, `this`, `x` полностью эквивалентна. Компилятор смотрит на тип, а не на имя параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` вида `p.draw(screen)` работал, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции как «метода» (подробный
синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после неё появляется синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающей стороной

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // оба способа вызова эквивалентны

// Без [0] = без привязки. Point.draw — просто псевдоним обычной функции, без синтаксиса .
Point.draw = draw       // без привязки: только Point.draw(p, screen)
```

**Поведение по умолчанию**: без `[n]` = никакой параметр не привязывается. Пользователь должен явно
решить, какие параметры заполняются вызывающей стороной.

**Многопозиционная привязка**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (метод → обычная функция):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Обобщённые типы

```yaoxiang
// Базовые обобщения (RFC-011 Phase 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретизация (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    return (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // пример вызова

// Обобщённый метод (синтаксис RFC-023: параметры типа автоматически выводятся в месте вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 and index < self.length {
        return Maybe.Just(self.data[index])
    } else {
        return Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова обобщений

Вызов обобщённых типов и обобщённых функций унифицированно использует синтаксис `()`. `[]` не
используется ни в каком контексте обобщений.

**Основные правила**:

1. **`()` для всего**: применение типов, вызов функций, конструирование значений — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся из левой части
empty: List(Int) = List()

# Вызов обобщённой функции — типы автоматически передаются из аргументов
strings = map(numbers, f)
// T=Int приходит из numbers: List(Int)
// R=String приходит из f: (Int) -> String
```

2. **Type слева, значение справа**: `name: type = value` — параметры типа объявляются слева, справа
   всегда конкретные значения. T в пустом контейнере `List()` должен браться из левой аннотации
   типа.

3. **Информация о типе записывается только один раз** — в объявлении параметра, компилятор передаёт
   её дальше:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int записан один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически приходят из типов numbers и f
```

4. **Конструирование значений выводит тип из элементов**:

```yaoxiang
x = List(1, 2, 3)       // выводится как List(Int)
y = List("a", "b")      // выводится как List(String)
z = List()              // ❌ Ошибка компиляции: невозможно вывести T
z: List(Int) = List()   // ✅ T=Int берётся из левой аннотации
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис обобщений `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

### Алгоритм проверки интерфейсов

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (поля-функции)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, есть ли у типа метод с таким же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатуры метода
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: после удаления self-параметра должны совпадать
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизация на этапе компиляции

Тип интерфейса поддерживает прямое присваивание, компилятор автоматически выбирает оптимальную
стратегию вызова на основе типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип может быть определён на этапе компиляции, вызов с нулевыми накладными расходами
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возвращаемое значение функции → конкретный тип не может быть определён на этапе компиляции, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Гетерогенная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегия оптимизации на этапе компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                    |
| -------------------------------- | --------------------- | -------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные) |
| `d: Drawable = get_shape()`      | Неизвестен            | vtable                           |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                           |

**Правила**:

1. Когда правая часть является конструктором конкретного типа и может быть определена на этапе
   компиляции, генерируется IR с прямым вызовом
2. Когда тип правой части не может быть определён на этапе компиляции, происходит откат на механизм
   vtable
3. vtable служит страховкой для корректности полиморфизма во время выполнения

### Устаревший синтаксис: `|` для вариантов

> **Объявление об устаревании (2026-07-25, issue #203)**: синтаксис вариантов `|` официально устарел
> и удалён из реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Унифицированно используется тип записи для выражения суммы типов (sum type). Когда все поля типа
записи — функции, и все они возвращают сам этот тип, он и является суммой типов:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особых случаев**: `|` — единственный синтаксис в BNF, не соответствующий форме
   `name: type = value`. После его удаления продукция `type_expr` полностью унифицирована, парсеру
   больше не нужно поддерживать отдельные пути и предпросмотр с возвратом для типов-вариантов.
2. **Математическая эквивалентность**: в рамках изоморфизма Карри-Ховарда дизъюнкция P ⊕ Q,
   соответствующая сумме типов, эквивалентна типу записи «поля — все функции, возвращающие сам этот
   тип». Оба выражают одну и ту же семантику, две формы синтаксиса не нужны.
3. **Нулевая разрушительность**: до удаления синтаксис `|` был полуподдерживаем в парсере (варианты
   без параметров могли быть разобраны, но типы параметров терялись при мономорфизации), никакой
   пользовательский код на него не полагался.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все типы-варианты унифицированно
   идут по пути `Type::Struct`, все особые ветви в нижестоящих typecheck/mono/formatter устранены.

> **Примечание**: семантические свойства суммы типов (такие как проверка полноты match, размещение в
> памяти tagged union) выводятся на уровне typecheck из структуры `Type::Struct`, не полагаясь на
> отдельный узел AST.

### Логические операторы: `and` / `or` / `not` (авторитетное определение)

> **Объявление определения (2026-08-03, issue #251)**: авторитетная форма логических операторов —
> ключевые слова `and` / `or` / `not` (соответствует таблице приоритетов §2.2 SPEC `syntax.md`).
> C-подобные `&&` / `||` / `!` никогда не входили в SPEC, удалены из лексера, при записи напрямую
> сообщается об ошибке.

**Семантика**:

| Оператор | Приоритет (SPEC §2.2)         | Ассоциативность | Семантика                        |
| -------- | ----------------------------- | --------------- | -------------------------------- |
| `not`    | 9 (ниже операторов сравнения) | правая          | Логическое НЕ                    |
| `and`    | 10                            | левая           | Короткозамыкающее логическое И   |
| `or`     | 10                            | левая           | Короткозамыкающее логическое ИЛИ |

```yaoxiang
# Короткое замыкание: при and левая часть false / при or левая часть true правая часть не выполняется
if x != 0 and y / x > 1 { ... }   # при x == 0 не будет деления на ноль

# Приоритет: not ниже сравнения → not a == b ≡ not (a == b); and выше or
not 3 == 4          # true, эквивалентно not (3 == 4)
true or false and false   # true, эквивалентно true or (false and false)
```

Следующие записи **больше не поддерживаются** (лексер сообщает об ошибке и предлагает
соответствующее ключевое слово):

```
x && y     # ❌ удалено, используйте x and y
x || y     # ❌ удалено, используйте x or y
!x         # ❌ удалено, используйте not x (на != не влияет)
```

**Обоснование дизайна**:

1. **Устранение неоднозначности**: `&` в этом языке несёт двойную функцию — токен заимствования
   (`&p` / `&mut p`, RFC-009) и побитовое И (приоритет 7 в SPEC §2.2). Введение `&&` заставит один
   символ нести три значения. `and` / `or` / `not` визуально полностью разделяют заимствование,
   побитовые и логические операции.
2. **Цель естественного синтаксиса**: основная цель README — «читаемость как в Python, близость к
   естественному языку», форма ключевых слов читается вслух; это также согласуется с исходным
   определением таблицы приоритетов SPEC §2.2 (`&&` / `||` / `!` в реализации были ранним дрейфом к
   привычкам C, теперь исправлено).
3. **Прецеденты и контрпримеры**: Python / Zig / Lua / Ada / SQL используют ключевые слова для
   логических операторов (Zig — современный системный язык того же экологического ниши, что и наш);
   Ruby сохраняет и `&&`, и `and` (с разными приоритетами) — это известный footgun, доказывающий,
   что «обе формы» — наихудший вариант — этот язык сохраняет только одну.
4. **Согласованность с Карри-Ховардом**: типы как утверждения (см. раздел об изоморфизме выше),
   логические связки в уточняющих типах записываются как `and` / `or` (например,
   `{ 0 <= idx and idx < arr.len }`) — это естественное выражение утверждений, а не символьных
   операций.

> **Реализация**: `and` / `or` раскрываются на уровне IR в последовательность короткозамыкающих
> переходов (`a and b ≡ if a { b } else { false }`), `not` связывается слабее операторов сравнения
> (операнд разбирается по `BP_LOGICAL_AND + 1`). Регрессионные тесты:
> `tests/yaoxiang/01-syntax/basics/logical_ops.yx`, `logical_not.yx`.

## Пояснение дизайна синтаксиса: именованная функция по сути является синтаксическим сахаром для лямбды

### Основное понимание

**Именованная функция и лямбда-выражение — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// Эти две формы полностью эквивалентны
add: (a: Int, b: Int) -> Int = a + b           // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда в сигнатуре полностью объявлены типы параметров, имена параметров в
заголовке лямбды становятся избыточными и могут быть опущены.

### Правила области видимости параметров

**Параметры затеняют внешние переменные**: область видимости параметров в сигнатуре перекрывает тело
функции, внутренняя область видимости имеет более высокий приоритет.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x затеняет внешний x, результат 20
```

### Гибкость расположения аннотаций

Аннотация типа может находиться в любом из следующих мест, **достаточно хотя бы одного**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ допустимо               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но разрешено |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: сигнатура полная, заголовок лямбды опущен
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Допустимо: тип аннотирован в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Допустимо: аннотация в обоих местах
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство            | Преимущество                                                                   |
| ------------------- | ------------------------------------------------------------------------------ |
| **Краткость**       | Нет необходимости повторять имена параметров, когда сигнатура полная           |
| **Гибкость**        | Сохранена лямбда-форма, используйте ту, которая нравится                       |
| **Согласованность** | Соответствует паттерну объявления переменных `x: Int = 42`                     |
| **Интуитивность**   | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Приложение

### BNF синтаксиса

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражение типа
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # Применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # Тип функции
       | '{' type_field* '}'                       # Тип записи / интерфейса
       | 'Type'                                    # Мезотип

type_field ::= identifier ':' type_expr
             | identifier                           # Ограничение интерфейса

# Параметры обобщений: как часть типа функции, например (T: Type, R: Type) -> (...)
# Нет необходимости в отдельном правиле BNF — параметры : Type — это обычные параметры функции

# Выражение
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # Вызов функции / вызов конструктора
              | '(' expression (',' expression)* ')'              # Кортеж
              | expression '.' identifier '(' arguments? ')'    # Вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                    | Определение                                                                                                                  |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Объявление                | Оператор присваивания в форме `name: type = value`                                                                           |
| Тип записи                | Тип `{ ... }` с именованными полями                                                                                          |
| Интерфейс                 | Тип записи, все поля которого — типы функций                                                                                 |
| Обобщённый тип            | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                        |
| Функция пространства имён | Функция вида `Type.name`, принадлежащая пространству имён Type. Не подразумевает никакой привязки                            |
| Привязка метода           | `Type.name = func[n]`, привязывает позицию n функции func как вызывающую сторону, делая доступным синтаксис `obj.name(args)` |
| Обобщённая функция        | Функция, использующая синтаксис `(T: Type)`, параметры типа выступают как первая группа параметров                           |
| Мезотип                   | `Type`, единственный маркер уровня типов в языке                                                                             |
