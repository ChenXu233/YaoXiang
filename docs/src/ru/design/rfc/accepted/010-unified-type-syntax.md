# RFC-010: Унифицированный синтаксис типов — модель name: type = value

## Резюме

Данный RFC предлагает минималистичную унифицированную модель синтаксиса типов: **всё есть
`name: type = value`**.

В YaoXiang существует только одна форма объявления:

```
identifier : type = expression
```

где `type` может быть любым выражением типа, а `expression` — любым выражением значения. **Нет `fn`,
нет `struct`, нет `trait`, нет `impl`, нет ключевого слова `type` в нижнем регистре (но есть `Type`
как ключевое слово метайпа)**.

> **Ключевая идея**: `Type` сам по себе является обобщённым (generic) типом. `(T: Type) -> Type`
> означает «тип, принимающий параметр типа T».

| Понятие            | Способ записи                                                                |
| ------------------ | ---------------------------------------------------------------------------- |
| Переменная         | `x: Int = 42`                                                                |
| Функция            | `add: (a: Int, b: Int) -> Int = a + b`                                       |
| Тип записи         | `Point: Type = { x: Float, y: Float }`                                       |
| Интерфейс          | `Drawable: Type = { draw: (Surface) -> Void }`                               |
| Обобщённый тип     | `List: (T: Type) -> Type = { data: Array(T), length: Int }`                  |
| Обобщённый тип     | `Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }`     |
| Метод              | `Point.draw: (p: Point, s: Surface) -> Void = ...`<br>`Point.draw = draw[0]` |
| Обобщённая функция | `map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))`    |

**`Type` — единственное ключевое слово метайпа в языке**.

> **Пространство имён vs привязка метода**: префикс `Type.name` обозначает **принадлежность к
> пространству имён**, и ничего более. Он не вызывает никакой неявной привязки. Чтобы синтаксис
> вызова через `.` работал в виде `p.draw(screen)`, требуется явная привязка:
> `Point.draw = draw[0]`. Подробности см. в разделе «Пространства имён и привязка методов» ниже. Он
> используется для маркировки уровня типов; компилятор автоматически различает Type0, Type1,
> Type2... — это прозрачно для пользователя.

```yaoxiang
// Базовый синтаксис: унифицированный + различимый

// Переменная
x: Int = 42

// Функция (имена параметров в сигнатуре)
add: (a: Int, b: Int) -> Int = a + b

// Тип записи
Point: Type = {
    x: Float,
    y: Float,
    draw: (Surface) -> Void,
    serialize: () -> String
}

// Интерфейс (по сути — тип записи, все поля которой — функции)
Drawable: Type = {
    draw: (Surface) -> Void,
    bounding_box: () -> Rect
}

Serializable: Type = {
    serialize: () -> String
}

// Определение метода (синтаксис Type.method)
Point.draw: (self: Point, surface: Surface) -> Void = {
    surface.plot(self.x, self.y)
}

Point.serialize: (self: Point) -> String = {
    return "Point(${self.x}, ${self.y})"
}

// Обобщённый тип ((T: Type) -> Type = обобщённый тип, принимающий параметр типа)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int
}

Map: (K: Type, V: Type) -> Type = {
    keys: Array(K),
    values: Array(V)
}

// Использование
p: Point = Point(1.0, 2.0)
p.draw(screen)           // синтаксический сахар → Point.draw(p, screen)
s: Drawable = p           // структурная подтипизация: Point реализует Drawable
drawables: List(Drawable) = [p, r]
process_all(drawables)
```

## Мотивация

### Зачем нужна эта возможность?

Текущая система типов содержит несколько разрозненных концепций:

- Синтаксис объявления переменных
- Синтаксис определения функций
- Синтаксис определения типов (различный)
- Синтаксис определения интерфейсов
- Синтаксис привязки методов

Между этими концепциями отсутствует единство, что приводит к фрагментации синтаксиса и высокой
стоимости обучения.

### Цели проектирования

1. **Предельное единство**: одно правило синтаксиса покрывает все случаи
2. **Простота и элегантность**: симметричная эстетика `name: type = value`
3. **Без новых ключевых слов**: повторное использование существующих элементов синтаксиса
4. **Теоретическая элегантность**: сам тип является значением типа Type
5. **Дружелюбность к дженерикам**: бесшовная интеграция с системой дженериков (RFC-011)

### Интеграция с системой дженериков

Унифицированная синтаксическая модель RFC-010 **органично сочетается** с дизайном системы дженериков
из RFC-011, параметры дженериков естественно вписываются в унифицированную модель:

```yaoxiang
// Базовые дженерики (RFC-011 Phase 1)
List: (T: Type) -> Type = { data: Array(T), length: Int }

// Обобщённая функция (синтаксис RFC-023: Type в сигнатуре можно опускать, вывод автоматический)
map: (: Type, R: Type) -> (( list: List(T), f: (T) -> R) -> List(R)) = ...

// Ограничения типа (RFC-011 Phase 2)
clone: (value: T) -> T = value.clone()  // ограничение T: Clone несётся типом параметра

// Const-дженерики (RFC-011 Phase 4)
Array: (T: Type, N: Int) -> Type = { data: Array(T, N), length: N }
```

**Зависимости**:

- RFC-011 Phase 1 (базовые дженерики) — **сильная зависимость** для RFC-010
- Без базовых дженериков примеры с дженериками в RFC-010 не скомпилируются
- Рекомендация: реализовать RFC-011 Phase 1 одновременно с RFC-010

## Предложение

### Ключевой принцип: конструктор типа vs функция/переменная

**Это ключевой выбор дизайна, определяющий правила устранения неоднозначности:**

| Запись              | Значение               | Правило                                              |
| ------------------- | ---------------------- | ---------------------------------------------------- |
| **`x: Type = ...`** | Конструктор типа       | `: Type` явно объявлено → принудительно тип          |
| **`f = ...`**       | Функция или переменная | Без `: Type` → HM активно выводит функцию/переменную |

**Почему такое решение?**

Сам синтаксис `{ ... }` неоднозначен:

- `{ x: Float, y: Float }` может быть **литералом типа** (тип записи)
- `{ a = 1 + 1 }` может быть **блоком кода** (исполняемый оператор, возвращающий Void)

**Правила устранения неоднозначности**:

- **Есть** `: Type` → принудительно интерпретируется как конструктор типа, `{ ... }` — литерал типа
- **Нет** `: Type` → HM активно интерпретирует `{ ... }` как блок кода, выводится функциональный тип

```yaoxiang
# ✅ Конструктор типа: есть : Type
Point: Type = { x: Float, y: Float }

# ✅ Функция: нет : Type, HM выводит () -> Void
main = { println("Hello") }

# ❌ Ошибка: нет : Type, компилятор не может интерпретировать { ... } как тип
Point = { x: Float, y: Float }  // HM выводит функцию, а не тип!
```

---

**Унифицированная модель: identifier : type = expression**

```
├── Переменная
│   └── x: Int = 42
│
├── Функция
│   └── add: (a: Int, b: Int) -> Int = a + b  # нет : Type, HM выводит функцию
│
├── Тип записи
│   └── Point: Type = { x: Float, y: Float }  # должен вернуть: Type
│
├── Интерфейс
│   └── Drawable: Type = { draw: (Surface) -> Void }  # должен вернуть: Type
│
├── Обобщённый тип
│   └── List: (T: Type) -> Type = { data: Array(T), length: Int }  # должен вернуть: Type
│
├── Обобщённый тип (несколько параметров)
│   └── Map: (K: Type, V: Type) -> Type = { keys: Array(K), values: Array(V) }  # должен вернуть: Type
│
├── Функция в пространстве имён
│   └── draw: (p: Point, surface: Surface) -> Void = ...
│       Point.draw = draw[0]  # точечный синтаксис доступен только после явной привязки
│
└── Обобщённая функция
    └── map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R))  # не возвращает Type, HM выводит функцию
```

### Уровни метайпов (внутри компилятора)

**Внутри компилятора** поддерживается иерархия вселенной `level: selfpointnum` (хранится в виде
строки, теоретически бесконечно расширяемая).

| Уровень  | Описание                                    |
| -------- | ------------------------------------------- |
| `Type0`  | Повседневные типы (`Int`, `Float`, `Point`) |
| `Type1`  | Конструкторы типов (`List`, `Maybe`)        |
| `Type2+` | Конструкторы высшего порядка                |

**Пользователь никогда не видит эти числа**, только `: Type`.

### Изоморфизм Карри-Ховарда: типы как propositions, программы как доказательства

Унифицированный синтаксис YaoXiang `name: type = value` выбран не случайно — он представляет собой
прямое отображение изоморфизма Карри-Ховарда. Этот изоморфизм раскрывает глубокий факт: **система
типов и логическая система — это две стороны одной и той же сущности**.

| Логика (proposition)          | Система типов (YaoXiang)              | Пример                               |
| ----------------------------- | ------------------------------------- | ------------------------------------ |
| Proposition P                 | Тип T                                 | `Int`, `Bool`                        |
| Доказательство истинности P   | Значение типа T                       | `42: Int`, `true: Bool`              |
| P → Q (импликация)            | Функциональный тип `(P) -> Q`         | `(x: Int) -> Bool`                   |
| P ∧ Q (конъюнкция)            | Тип записи `{ p: P, q: Q }`           | `{ x: Int, y: Bool }`                |
| ∀x.P(x) (квантор всеобщности) | Обобщённая функция `(T: Type) -> ...` | `map: (T: Type, R: Type) -> ...`     |
| P ⊕ Q (дизъюнкция)            | Enum / tagged union                   | `Maybe: (T: Type) -> Type = { ... }` |

**Значение `name: type = value` в свете Карри-Ховарда**:

```yaoxiang
// "x: Int = 42" читается как: "существует доказательство типа Int по имени x со значением 42"
x: Int = 42

// "add: (a: Int, b: Int) -> Int = a + b" читается как:
// "существует доказательство импликации: даны доказательства a и b типа Int, можно построить доказательство типа Int"
add: (a: Int, b: Int) -> Int = a + b

// "Point: Type = { x: Float, y: Float }" читается как:
// "Point — это proposition, для доказательства которой необходимо одновременно предоставить доказательство Float x и доказательство Float y"
Point: Type = { x: Float, y: Float }
```

**Почему это важно?**

1. **Логическая непротиворечивость = безопасность типов**: если система типов позволяет
   конструировать значение типа `T` без какого-либо легитимного представления в runtime, это подобно
   тому, как в логике разрешают доказывать ложную proposition — система рушится. Карри-Ховард
   говорит нам: **язык с безопасной системой типов по своей природе является непротиворечивой
   логической системой**.

2. **Иерархия вселенных — необходимое условие**: как подробно описано ниже, если разрешить
   `Type: Type` (т.е. «тип типа тоже тип»), возникнет парадокс Рассела (в теории типов проявляющийся
   как парадокс Жирара). Слоистая структура YaoXiang `Type₀ : Type₁ : Type₂ : ...` гарантирует, что
   каждый тип принадлежит только одному уровню, формируя бесконечно восходящую цепочку, что
   фундаментально предотвращает парадоксы. Это означает, что система типов YaoXiang **логически
   непротиворечива** в смысле Карри-Ховарда.

3. **Теоретическое обоснование унифицированного синтаксиса**: то, что `name: type = value` способен
   одним синтаксисом покрыть переменные, функции, типы, интерфейсы и дженерики, объясняется тем, что
   в свете Карри-Ховарда все они — одно и то же: **предоставление доказательства для proposition**.
   Переменная — свидетельство proposition, функция — свидетельство импликации, запись —
   свидетельство конъюнкции, дженерик — свидетельство квантора всеобщности. Унифицированный
   синтаксис — не искусственно сконструированное совпадение, а естественное следствие изоморфизма
   Карри-Ховарда.

> **Дополнительное чтение**: Wadler, P. (2015). _"Propositions as Types."_ Communications of the
> ACM, 58(12), 75–84. Эта статья доступно объясняет историю и значение изоморфизма Карри-Ховарда.

### Определение синтаксиса

#### 1. Объявление переменных

```yaoxiang
// Базовый синтаксис
x: Int = 42
name: String = "Alice"
flag: Bool = true

// Вывод типа (можно опустить)
y = 100  // выводится как Int
```

#### 2. Определение функций

```yaoxiang
// Одновыраженческая форма (возвращает значение напрямую, return не нужен)
add: (a: Int, b: Int) -> Int = a + b
greet: (name: String) -> String = "Hello, ${name}!"

// Форма блока кода (для возврата значения необходим return)
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

// Многострочный блок кода
calc: (x: Float, y: Float, op: String) -> Float = {
    return match op {
        "+" -> x + y,
        "-" -> x - y,
        _ -> 0.0
    }
}

// Функция Void (return внутри блока не нужен)
print: (msg: String) -> Void = {
    console.write(msg)
}
```

#### Правила возврата

Возвращаемое значение зависит от формы справа от `=`:

| Запись                             | Возвращаемое значение                         |
| ---------------------------------- | --------------------------------------------- |
| `= expr` (без фигурных скобок)     | Возвращает `expr` напрямую                    |
| `= { ... }` (с фигурными скобками) | Необходим `return`, иначе возвращается `Void` |

```yaoxiang
# Одновыраженческая форма: возвращает значение напрямую, return не нужен
add: (a: Int, b: Int) -> Int = a + b

# Блок кода: для возврата значения необходим return
process: (x: Int) -> Int = {
    a = x * 2
    b = a + 1
    return b
}

# Функция Void: return не нужен
print: (msg: String) -> Void = {
    console.write(msg)
}
```

> **Обоснование дизайна**: `{ ... }` — это вычислительная единица, управляемая зависимостями (см.
> ниже), её семантика возврата отличается от одновыраженческой формы. Фигурные скобки вводят
> контекст множественных операторов, поэтому необходим явный `return` для устранения неоднозначности
> «является ли последнее выражение возвращаемым значением».

#### Семантика `{}`: вычислительная единица, управляемая зависимостями

`{ ... }` в YaoXiang — не просто блок кода, а **вычислительная единица, управляемая зависимостями**.
Эта семантика остаётся единообразной в телах функций, инициализации переменных и `spawn`:

**Основные правила**:

- Операторы присваивания внутри `{}` автоматически сортируются по зависимостям, а не по порядку
  записи
- Когда зависимости удовлетворены, выполнение происходит немедленно; при отсутствии — блокировка и
  ожидание
- Для явного возврата значения используется `return` (см. правила возврата)

```yaoxiang
# Управление зависимостями: b зависит от a, компилятор автоматически сортирует
result: Int = {
    b = a + 1      # зависит от a → автоматически после a
    a = 10         # нет зависимостей → может выполняться первым
    return b       # возвращает 11
}
```

> **Отличие от одновыраженческой формы**: `= expr` (без фигурных скобок) — простое связывание с
> прямым возвратом значения; `= { ... }` (с фигурными скобками) вводит контекст вычислений,
> управляемый зависимостями, допускающий множественные операторы и явный `return`.

#### `spawn` блок

`spawn { ... }` — единственная параллельная примитива YaoXiang. Она использует семантику
зависимостей `{}` для автоматического распараллеливания:

- Непосредственные дочерние присваивания внутри `spawn { ... }` автоматически создают параллельные
  задачи
- Задачи с удовлетворёнными зависимостями выполняются конкурентно
- Вызывающий блокируется до завершения всех подзадач

```yaoxiang
result = spawn {
    a = fetch_data("url1")    # задача 1
    b = fetch_data("url2")    # задача 2 (нет зависимости от a, выполняется параллельно)
    c = process(a, b)         # зависит от a, b → ожидает завершения обоих
    return c
}
// Вызывающий блокируется здесь до завершения всех задач внутри spawn блока
```

> **Подробное определение**: полная семантика `spawn`, правила создания задач и модель блокировки
> описаны в `008-runtime-concurrency-model.md`.

#### `unsafe` блок

`unsafe { ... }` используется для определения непрозрачных типов и операций с сырыми указателями. Он
использует семантику `return` блока `{}` для возврата определения типа во внешнюю область видимости:

**Основные правила**:

- В `unsafe {}` можно определять типы и оперировать сырыми указателями
- Используйте `return` для возврата определения типа во внешнюю область видимости
- Возвращённый тип доступен за пределами `unsafe {}`
- Доступ к полям типа требует привилегий unsafe

```yaoxiang
# Определение непрозрачного типа в unsafe блоке
SqliteDb = unsafe {
    SqliteDb: Type = {
        handle: *Void  # сырой указатель
    }
    return SqliteDb
}

# SqliteDb доступен за пределами unsafe блока
db = sqlite3_open("test.db")

# ❌ Ошибка компиляции: доступ к полю handle требует unsafe привилегий
handle = db.handle

# ✅ Через вызов метода
db.close()
```

> **Подробное определение**: полная семантика `unsafe`, определение FFI-типов и привязка методов
> описаны в `ffi.md`.

#### 3. Определение типов

Определение типов — ядро унифицированного синтаксиса YaoXiang, включающее поля, значения по
умолчанию, привязанные методы и реализацию интерфейсов:

##### Базовые типы

**Тип записи**: список полей, типы полей могут быть любыми выражениями типа.

```yaoxiang
Point: Type = {
    x: Float,
    y: Float
}
```

**Поля со значениями по умолчанию**: поля могут иметь значения по умолчанию, необязательные при
конструировании.

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0
}
```

Использование:

```yaoxiang
Point() → Point(x=0, y=0)
Point(x=1) → Point(x=1, y=0)
Point(x=1, y=2) → Point(x=1, y=2)
```

**Поля без значений по умолчанию**: должны быть предоставлены при конструировании.

```yaoxiang
Point2: Type = {
    x: Float,
    y: Float
}
```

Использование:

```yaoxiang
Point2(x=1, y=2) //✓
Point2() //✗
Point2(x=1) //✗
```

##### Встроенные типы

Система идентификаторов YaoXiang трёхуровневая, последовательно распознаваемая на разных этапах
компиляции:

1. **Ключевые слова** (отдельные токены парсера) — управляющие конструкции и ключевые слова
   объявления, такие как `if`, `match`, `pub`, `return`
2. **Зарезервированные слова для литералов** (отдельные токены парсера) — `true`, `false`, `void`,
   `Type`, не могут использоваться как обычные идентификаторы
3. **Имена встроенных типов** (предварительно зарегистрированные в проверке типов) — парсер
   обрабатывает их как обычные идентификаторы, интерпретацию выполняет проверщик типов. **Не
   являются зарезервированными словами, могут быть затенены (не рекомендуется)**

Различие между `void` (в нижнем регистре, зарезервированное слово для литерала) и `Void` (в верхнем
регистре, имя встроенного типа): `void` — литерал значения (равен единственному значению Unit),
`Void` — имя типа (равен типу Unit, логически ⊤). `let x: Void = void` — легитимная запись.

Предустановленные имена встроенных типов:

| Тип      | Логическое соответствие | Описание                                                                                                                                                                                                                                                                                               |
| -------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Never`  | ⊥ (ложь/пустой тип)     | Ноль конструкторов, ни одно значение не может населять этот тип. Означает «невозможно» — расходимость, паника, мёртвый код. `Never <: T` справедливо для любого `T` (принцип взрыва). Функция, возвращающая `Never`, никогда не возвращается нормально. **Не ключевое слово, а имя встроенного типа.** |
| `Void`   | ⊤ (истина/Unit)         | Ровно один обитатель (по умолчанию значение void). `x: Void = <по умолчанию>` легитимно. Единица суммы соответствует единице произведения — `Void` — это пустой тип произведения (Unit), `Never` — пустая сумма.                                                                                       |
| `Int`    | —                       | Целое число со знаком                                                                                                                                                                                                                                                                                  |
| `Float`  | —                       | Число с плавающей точкой                                                                                                                                                                                                                                                                               |
| `Bool`   | —                       | Логическое значение: `true` / `false`                                                                                                                                                                                                                                                                  |
| `Char`   | —                       | Unicode-символ                                                                                                                                                                                                                                                                                         |
| `String` | —                       | Строка                                                                                                                                                                                                                                                                                                 |

##### Привязка методов

**Способ 1: прямая привязка внешней функции внутри тела определения типа**

```yaoxiang
distance: (a: Point, b: Point) -> Float = { ... }
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance = distance[0]           // привязка к позиции 0, после каррирования method: (b: Point) -> Float
}
// Вызов: p1.distance(p2) → distance(p1, p2)
```

**Способ 2: анонимная функция + позиционная привязка**

```yaoxiang
Point: Type = {
    x: Float = 0,
    y: Float = 0,
    distance: ((a: Point, b: Point) -> Float)[0] = ((a, b) => {
        dx = a.x - b.x
        dy = a.y - b.y
        return (dx * dx + dy * dy).sqrt()
    })
}
// Синтаксис: ((params) => body)[position]
// Вызов: p1.distance(p2) → distance(p1, p2)
```

##### Определение функций в пространстве имён

**Префикс `Type.name` обозначает принадлежность к пространству имён**, и ничего более. Он не
вызывает никакой неявной привязки.

```yaoxiang
// Функция пространства имён: обычная функция в пространстве имён Point
Point.draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

Point.serialize: (p: &Point) -> String = {
    return "Point(${p.x}, ${p.y})"
}

// Вызов: это обычный вызов функции
Point.draw(p, screen)
Point.serialize(p)
```

> **Примечание**: `self` — не ключевое слово, а просто конвенциональное имя параметра. Запись `p`,
> `this`, `x` даст абсолютно тот же эффект. Компилятор смотрит на тип, а не на имя параметра.

##### Привязка метода (единственный способ)

Чтобы синтаксис вызова метода через `.` работал в виде `p.draw(screen)`, **необходима явная
привязка**. Синтаксис `[position]` — единственный механизм привязки функции как «метода» (подробный
синтаксис см. в RFC-004).

```yaoxiang
// Определение функции
draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

// Явная привязка — только после этого доступен синтаксис p.draw(screen)
Point.draw = draw[0]   // параметр на позиции 0 (&Point) заполняется вызывающим

// Использование
p.draw(screen)          // синтаксический сахар → draw(&p, screen)
Point.draw(p, screen)   // обе формы вызова эквивалентны

// Без [0] = без привязки. Point.draw — обычный псевдоним функции, без синтаксиса .
Point.draw = draw       // без привязки: только Point.draw(p, screen)
```

**Поведение по умолчанию**: без `[n]` = ни один параметр не привязан. Пользователь должен явно
решить, какие параметры заполняются вызывающим.

**Многопозиционная привязка**:

```yaoxiang
// Привязка нескольких позиций (автоматическое каррирование)
Point.transform = transform_points[0, 1]
// Вызов: p1.transform(p2)(2.0) → transform_points(p1, p2, 2.0)
```

**Обратная операция** (из метода в обычную функцию):

```yaoxiang
// Извлечение функции из привязки
draw_point: (p: &Point, surface: Surface) -> Void = Point.draw
```

#### 5. Обобщённые типы

```yaoxiang
// Базовые дженерики (RFC-011 Phase 1)
List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (T:Type)-((self: List(T), item: T) -> Void),
    get: (T:Type)->((self: List(T), index: Int) -> Maybe(T))
}

// Конкретизация (синтаксис RFC-023)
IntList: Type = List(Int)

IntList.push = {
    self.data.append(item)
    self.length = self.length + 1
}

List.push = (type: Type) -> {
    return (self: List(type), item: type) -> {
        self.data.append(item)
        self.length = self.length + 1
    }
}

IntList.push(Int)(self, item)  // пример вызова

// Обобщённые методы (синтаксис RFC-023: параметры типа выводятся автоматически в точке вызова)
List.push: (self: List(T), item: T) -> Void = {
    self.data.append(item)
    self.length = self.length + 1
}

List.get: (self: List(T), index: Int) -> Maybe(T) = {
    if index >= 0 && index < self.length {
        return Maybe.Just(self.data[index])
    } else {
        return Maybe.Nothing
    }
}
```

#### 6. Синтаксис вызова дженериков

Для вызова обобщённых типов и обобщённых функций единообразно используется синтаксис `()`. `[]`
нигде не используется в контексте дженериков.

**Основные правила**:

1. **`()` для всего**: применение типа, вызов функции, конструирование значения — всё через `()`

```yaoxiang
# Аннотация типа
numbers: List(Int) = List(1, 2, 3)

# Пустой контейнер: T берётся слева
empty: List(Int) = List()

# Вызов обобщённой функции — тип выводится из аргументов автоматически
strings = map(numbers, f)
// T=Int берётся из numbers: List(Int)
// R=String берётся из f: (Int) -> String
```

2. **Type слева, значение справа**: `name: type = value` — параметры Type объявляются слева, справа
   всегда конкретные значения. `T` в пустом контейнере `List()` должен браться из аннотации типа
   слева.

3. **Информацию о типе нужно записать один раз** — при объявлении параметра компилятор проносит её
   далее:

```yaoxiang
numbers: List(Int) = List(1, 2, 3)  // Int записывается один раз слева
f: (Int) -> String = (x) => x.to_string()
strings = map(numbers, f)   // T=Int, R=String автоматически из типов numbers и f
```

4. **Конструирование значения выводит тип из элементов**:

```yaoxiang
x = List(1, 2, 3)       // выводится как List(Int)
y = List("a", "b")      // выводится как List(String)
z = List()              // ❌ ошибка компиляции: невозможно вывести T
z: List(Int) = List()   // ✅ T=Int берётся из аннотации слева
```

5. **Псевдонимы типов**:

```yaoxiang
IntList: Type = List(Int)
StringToInt: Type = (String) -> Int
Matrix3x3: Type = Matrix(Float, 3, 3)
```

> **Сравнение со старым синтаксисом**: `List[Int]` → `List(Int)`, `List[Int]()` → `List()`,
> `List[Int](1,2,3)` → `List(1,2,3)`. Старый синтаксис дженериков с `[]` полностью удалён. `[]`
> используется только для литералов массивов/списков и доступа по индексу.

}

}

    scale: (factor: Float) -> Transformable
}

// ======== 2. Определения типов ========

Point: Type = {
    x: Float,
    y: Float,

    Transformable
}

    x: Float,
    y: Float,
    width: Float,
    height: Float,
    Drawable,
    Serializable,
    Transformable
}

// ======== 3. Реализация методов (обычные функции + явная привязка) ========

draw: (p: &Point, surface: Surface) -> Void = {
    surface.plot(p.x, p.y)
}

bounding_box: (p: &Point) -> Rect = {
    return Rect(p.x - 1, p.y - 1, 2, 2)
}

    return "Point(${p.x}, ${p.y})"
}

translate: (p: &Point, dx: Float, dy: Float) -> Point = {

}

    return Point(p.x * factor, p.y * factor)
}

distance: (p1: &Point, p2: &Point) -> Float = {

    dy = p1.y - p2.y
    return (dx * dx + dy * dy).sqrt()
}

// Явная привязка — точечный синтаксис доступен только после привязки

Point.bounding_box = bounding_box[0]
Point.serialize = serialize[0]
Point.translate = translate[0]
Point.scale = scale[0]
Point.distance = distance[0]

Rect.draw = draw[0]

Rect.bounding_box = bounding_box[0]

Rect.serialize = serialize[0]

}
Rect.translate = translate[0]

scale: (r: &Rect, factor: Float) -> Rect = {
    return Rect(r.x * factor, r.y * factor, r.width * factor, r.height * factor)
}
Rect.scale = scale[0]

// ======== 4. Использование ========

// Создание экземпляров

### Алгоритм проверки интерфейсов

```rust
fn check_type_implements_interface(
    typ: &Type,
    iface: &Type
) -> Result<(), TypeError> {
    // Для каждого поля интерфейса (функционального поля)
    for (field_name, iface_field) in &iface.fields {
        // Проверяем, есть ли в типе метод с тем же именем
        if let Some(method) = typ.methods.get(field_name) {
            // Проверяем совместимость сигнатур методов
            // Поле интерфейса: (Surface) -> Void
            // Сигнатура метода: (Point, Surface) -> Void
            // Сравнение: после удаления параметра self должно совпадать
            if !method_signature_matches(method, iface_field.type_) {
                return Err(TypeError::MethodSignatureMismatch {
                    type_name: typ.name,
                    interface_name: iface.name,
                    method_name: field_name,
                });
            }
        } else {
            return Err(TypeError::MissingMethod {
                type_name: typ.name,
                interface_name: iface.name,
                method_name: field_name,
            });
        }
    }
    Ok(())
}
```

### Прямое присваивание интерфейсу и оптимизации времени компиляции

Типы интерфейсов поддерживают прямое присваивание, компилятор автоматически выбирает оптимальную
стратегию вызова на основе конкретного типа правой части:

```yaoxiang
// Прямое присваивание конкретного типа → конкретный тип определяется во время компиляции, вызов без накладных расходов
d: Drawable = Circle(1)
d.draw(screen)  // после компиляции: прямой вызов circle_draw(screen), без vtable

// Возвращаемое значение функции → конкретный тип не может быть определён во время компиляции, используется vtable
d: Drawable = get_shape()
d.draw(screen)  // поиск метода через vtable

// Гетерогенная коллекция → используется vtable
shapes: List(Drawable) = [Circle(1), Rect(2, 3)]
for s in shapes {
    s.draw(screen)  // поиск метода через vtable
}
```

**Стратегии оптимизации времени компиляции**:

| Сценарий                         | Результат вывода      | Способ вызова                            |
| -------------------------------- | --------------------- | ---------------------------------------- |
| `d: Drawable = Circle(1)`        | Конкретный тип Circle | Прямой вызов (нулевые накладные расходы) |
| `d: Drawable = get_shape()`      | Неизвестно            | vtable                                   |
| `shapes: List(Drawable) = [...]` | Гетерогенный          | vtable                                   |

**Правила**:

1. Когда правая часть — конструктор конкретного типа и определяется во время компиляции,
   генерируется IR прямого вызова
2. Когда тип правой части не может быть определён во время компиляции, откат на механизм vtable
3. vtable как страховка обеспечивает корректность runtime-полиморфизма

### Изменения синтаксиса

| Ранее                                    | Теперь                                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |

| `type Result(T, E) = ok(T) \| err(E)`    | `Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }` |
| Требуется ключевое слово `impl`          | Ключевое слово не нужно, имена интерфейсов записываются после тела типа                      |

### Устаревший синтаксис: `|` для вариантов

> **Объявление об устаревании (2026-07-25, issue #203)**: синтаксис вариантов `|` официально устарел
> и удалён из реализации.

Следующие записи **больше не поддерживаются**:

```
type Color = red | green | blue                # ❌ устарело
type Result(T, E) = ok(T) | err(E)             # ❌ устарело
type Option(T) = some(T) | none                # ❌ устарело
```

Единообразно используются типы записей для выражения и суммы типов (sum type). Когда все поля типа
записи — функции, возвращающие сам этот тип, он является суммой типов:

```yaoxiang
Color: Type = {
    red: () -> Color,
    green: () -> Color,
    blue: () -> Color
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E)
}

Option: (T: Type) -> Type = {
    some: (T) -> Option(T),
    none: () -> Option(T)
}
```

**Обоснование дизайна**:

1. **Устранение особых случаев**: `|` — единственный нестандартный для `name: type = value`
   синтаксис в BNF. После удаления продукция `type_expr` полностью унифицирована, парсеру больше не
   нужно поддерживать отдельный путь и lookahead-backtrack для типов-вариантов.
2. **Математическая эквивалентность**: в изоморфизме Карри-Ховарда дизъюнкции P ⊕ Q соответствует
   тип суммы, эквивалентный типу записи «поля которого — функции, возвращающие сам этот тип». Они
   выражают одну и ту же семантику, и две системы синтаксиса не нужны.
3. **Нулевая разрушительность**: до удаления синтаксис `|` в парсере поддерживался лишь частично
   (варианты без параметров могли быть разобраны, но типы параметров терялись при мономорфизации),
   ни один пользовательский код не зависел от него.
4. **Упрощение AST**: узел `Type::Variant(Vec<VariantDef>)` удалён, все вариантные типы проходят
   через путь `Type::Struct`, специальные ветки в downstream-коде typecheck/mono/formatter полностью
   устранены.

> **Примечание**: семантические свойства типов суммы (такие как проверка полноты match, размещение в
> памяти tagged union) выводятся на уровне typecheck из структуры `Type::Struct` и не зависят от
> отдельного узла AST.

## Пояснение к дизайну синтаксиса: именованная функция — это синтаксический сахар для лямбды

### Ключевое понимание

**Именованная функция и лямбда-выражение — это одно и то же!** Единственное отличие: именованная
функция даёт лямбде имя.

```yaoxiang
// Эти две записи по сути полностью идентичны
add: (a: Int, b: Int) -> Int = a + b           // именованная функция (рекомендуется)
add: (a: Int, b: Int) -> Int = (a, b) => a + b        // лямбда-форма (полностью эквивалентна)
```

### Модель синтаксического сахара

```
// Именованная функция = Лямбда + имя
name: (Params) -> ReturnType = body

// По сути это
name: (Params) -> ReturnType = (params) => body
```

**Ключевой момент**: когда сигнатура полностью объявляет типы параметров, имена параметров в
заголовке лямбды становятся избыточными и могут быть опущены.

### Правила области видимости параметров

**Параметры затеняют внешние переменные**: область видимости параметров в сигнатуре перекрывает тело
функции, приоритет имеет внутренняя область видимости.

```yaoxiang
x = 10  // внешняя переменная

double: (x: Int) -> Int = x * 2  // ✅ параметр x затеняет внешний x, результат 20
```

### Гибкое расположение аннотаций

Аннотация типа может располагаться в любом из следующих мест, **достаточно аннотации хотя бы в
одном**:

| Расположение аннотации    | Форма                                    | Описание                   |
| ------------------------- | ---------------------------------------- | -------------------------- |
| Только в сигнатуре        | `double: (x: Int) -> Int = x * 2`        | ✅ рекомендуется           |
| Только в заголовке лямбды | `double = (x: Int) => x * 2`             | ✅ легитимно               |
| В обоих местах            | `double: (x: Int) -> Int = (x) => x * 2` | ✅ избыточно, но допустимо |

### Полный пример

```yaoxiang
// ✅ Рекомендуется: полная сигнатура, заголовок лямбды опущен
add: (a: Int, b: Int) -> Int = a + b
inc: (x: Int) -> Int = x + 1
main: () -> Void = { print("hi") }

// ✅ Легитимно: аннотация типов в заголовке лямбды
double = (x: Int) => x * 2

// ✅ Легитимно: аннотация в обоих местах
double: (x: Int) -> Int = (x) => x * 2
```

### Преимущества дизайна

| Свойство          | Преимущество                                                                   |
| ----------------- | ------------------------------------------------------------------------------ |
| **Краткость**     | При полной сигнатуре нет необходимости повторять имена параметров              |
| **Гибкость**      | Сохранена лямбда-форма, используйте ту, которая нравится                       |
| **Единообразие**  | Сохранён единый паттерн с объявлением переменных `x: Int = 42`                 |
| **Интуитивность** | `name: Type = body` напрямую соответствует «имя name, тип Type, значение body» |

## Пасхалка 🎮: Исток языка

> ✨ **Type: Type = Type** ✨

```yaoxiang
// Попытка определить тип типа...
Type: Type = Type
```

**Внимание**: это **невыразимая** сущность!

```
╔══════════════════════════════════════════════════════════════╗
║                                                              ║
║   Одно порождает два, два порождает три, три порождает тьму вещей. ║
║   Предел порождает Инь-Ян.                                   ║
║                                                              ║
║   Type: Type = Type                                          ║
║   Это исток ЯоXiang, граница языка.                          ║
║   Здесь компилятор безмолвствует, философия останавливается.  ║
║                                                              ║
║   Спасибо, что достигли философской границы языка.            ║
║                                                              ║
╚══════════════════════════════════════════════════════════════╝
```

> **Примечание**: компилятор не способен корректно обработать `Type: Type = Type` (это привело бы к
> парадоксу вселенной Type0/Type1), но мы намеренно сохранили эту «пасхалку» — когда вы попытаетесь
> её скомпилировать, вы получите дзен-сообщение от создателя языка. Это не только техническая
> граница, но и дань уважения YaoXiang философии типов.

## Приложение

### БНФ синтаксиса

```bnf
program ::= statement*

statement ::= declaration | expression

# Унифицированное объявление: name: Type = expression
declaration ::= identifier ':' type_expr '=' expression

# Выражения типов
type_expr ::= identifier
       | identifier '(' type_expr (',' type_expr)* ')'      # применение типа
       | '(' type_expr (',' type_expr)* ')' '->' type_expr       # функциональный тип
       | '{' type_field* '}'                       # тип записи / интерфейс
       | 'Type'                                    # метайп

type_field ::= identifier ':' type_expr
             | identifier                           # ограничение интерфейса

# Параметры дженериков: как часть функционального типа, например (T: Type, R: Type) -> (...)
# Не требуется отдельное правило БНФ — параметры : Type это обычные параметры функций

# Выражения
expression ::= literal
              | identifier
              | identifier '(' expression (',' expression)* ')'  # вызов функции / конструктор
              | '(' expression (',' expression)* ')'              # кортеж
              | expression '.' identifier '(' arguments? ')'    # вызов метода
              | lambda
              | '{' field ':' expression (',' field ':' expression)* '}'

arguments ::= expression (',' expression)*

lambda ::= '(' parameter_list? ')' '=>' block

block ::= expression | '{' expression* '}'
```

### Глоссарий

| Термин                    | Определение                                                                                                           |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Объявление                | Оператор присваивания в форме `name: type = value`                                                                    |
| Тип записи                | Тип `{ ... }` с именованными полями                                                                                   |
| Интерфейс                 | Тип записи, все поля которого имеют функциональный тип                                                                |
| Обобщённый тип            | Тип, определённый как `Name: (T: Type) -> Type = { ... }`, принимающий параметры типа                                 |
| Функция пространства имён | Функция в форме `Type.name`, принадлежащая пространству имён Type. Не подразумевает никакой привязки                  |
| Привязка метода           | `Type.name = func[n]`, привязка позиции n функции func как вызывающего, делающая доступным синтаксис `obj.name(args)` |
| Обобщённая функция        | Функция с использованием синтаксиса `(T: Type)`, параметры типа передаются как первая группа параметров               |
| Метайп                    | `Type`, единственный маркер уровня типов в языке                                                                      |
