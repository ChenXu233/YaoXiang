# RFC 013: Спецификация кодов ошибок

## Резюме

Настоящий RFC предлагает спецификацию классификации кодов ошибок компилятора YaoXiang, использующую
одноуровневую систему нумерации, аналогичную Rust, с поддержкой многоязычности через файлы ресурсов
JSON и предоставлением функции объяснения ошибок через команду `yaoxiang explain`.

## Мотивация

### Зачем нужны стандартизированные коды ошибок?

1. **Пользовательский опыт**: пользователь, видя код ошибки, может быстро определить тип и
   серьёзность ошибки
2. **Организация документации**: группировка по категориям упрощает написание и поддержку справочной
   документации по ошибкам
3. **Интеграция с инструментами**: IDE/LSP могут предоставлять предложения по быстрому исправлению и
   ссылки на документацию на основе кодов ошибок
4. **Поддержка интернационализации**: разделение сообщений об ошибках и кодов облегчает перевод на
   несколько языков

### Цели проектирования

- **Простота**: одноуровневая нумерация, пользователю не нужно запоминать сложные правила
  классификации
- **Дружелюбность**: формат сообщений об ошибках, аналогичный Rust, с вспомогательной информацией и
  примерами
- **Расширяемость**: управление через файлы ресурсов, легко добавлять новые ошибки и языки
- **Удобство для инструментов**: команда `explain` + JSON-вывод, поддержка интеграции с IDE/LSP

## Предложение

### Основной дизайн: Одноуровневая система нумерации

Используется четырёхзначная нумерация, сгруппированная по фазам компиляции:

```
Exxxx
││││
│││└── Порядковый номер (000-999)
││└─── Фаза компиляции (0-9)
└───── Фиксированный префикс 'E'
```

### Разделение по фазам

| Фаза  | Диапазон | Описание                            |
| ----- | -------- | ----------------------------------- |
| **0** | E0xxx    | Лексический и синтаксический анализ |
| **1** | E1xxx    | Проверка типов                      |
| **2** | E2xxx    | Семантический анализ                |
| **3** | E3xxx    | Генерация кода                      |
| **4** | E4xxx    | Дженерики и трейты                  |
| **5** | E5xxx    | Модули и импорт                     |
| **6** | E6xxx    | Ошибки времени выполнения           |
| **7** | E7xxx    | Ошибки ввода-вывода и системные     |
| **8** | E8xxx    | Внутренние ошибки компилятора       |
| **9** | E9xxx    | Зарезервировано/Экспериментальное   |

### Перечисление категорий ошибок

```rust
/// 错误类别
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ErrorCategory {
    Lexer,      // E0xxx: 词法和语法分析
    Parser,     // E0xxx: Parser errors
    TypeCheck,  // E1xxx: 类型检查
    Semantic,   // E2xxx: 语义分析
    Generic,    // E4xxx: 泛型与特质
    Module,     // E5xxx: 模块与导入
    Runtime,    // E6xxx: 运行时错误
    Io,         // E7xxx: I/O与系统错误
    Internal,   // E8xxx: 内部编译器错误

```

### Определение кода ошибки и универсальный Builder

**Основной принцип**: определение кода ошибки отделено от отображаемого текста

- `ErrorCodeDefinition`: метаданные кода ошибки (code, category, template), без отображаемого текста
- `locales/*.json`: отображаемый текст на разных языках (title, message, help, коды ошибок в виде
  вложенных объектов)
- `DiagnosticBuilder`: универсальный построитель, заменяющий дизайн trait-per-error

#### Определение кода ошибки

```rust
// diagnostic/codes/mod.rs

use crate::util::span::Span;
use crate::util::diagnostic::{Diagnostic, Severity};

/// 错误码定义（仅元数据，展示文案在 i18n 文件）
#[derive(Debug, Clone, Copy)]
pub struct ErrorCodeDefinition {
    pub code: &'static str,
    pub category: ErrorCategory,
    pub message_template: &'static str,  // 消息模板，支持 {param} 占位符
}

/// 通用诊断构建器
pub struct DiagnosticBuilder {
    code: &'static str,
    message_template: &'static str,
    params: Vec<(&'static str, String)>,
    span: Option<Span>,
}

impl DiagnosticBuilder {
    pub fn new(code: &'static str, template: &'static str) -> Self {
        Self {
            code,
            message_template: template,
            params: Vec::new(),
            span: None,
        }
    }

    /// 添加模板参数
    pub fn param(mut self, key: &'static str, value: impl Into<String>) -> Self {
        self.params.push((key, value.into()));
        self
    }

    /// 设置位置
    pub fn at(mut self, span: Span) -> Self {
        self.span = Some(span);
        self
    }

    /// 构建 Diagnostic（模板渲染在编译期完成）
    pub fn build(&self, i18n: &I18nRegistry) -> Diagnostic {
        // 检查模板中所有 {key} 都有对应参数
        self.validate_params();

        let message = i18n.render(self.message_template, &self.params);
        let help = self.help(i18n);

        Diagnostic {
            severity: Severity::Error,
            code: self.code.to_string(),
            message,
            help,
            span: self.span,
            related: Vec::new(),
        }
    }
}
```

#### Быстрые методы для каждого кода ошибки

```rust
// diagnostic/codes/e1xxx.rs

impl ErrorCodeDefinition {
    /// E1001 未知变量
    pub fn unknown_variable(name: &str) -> DiagnosticBuilder {
        let def = Self::find("E1001").unwrap();
        DiagnosticBuilder::new(def.code, def.message_template)
            .param("name", name)
    }

    /// E1002 类型不匹配
    pub fn type_mismatch(expected: &str, found: &str) -> DiagnosticBuilder {
        let def = Self::find("E1002").unwrap();
        DiagnosticBuilder::new(def.code, def.message_template)
            .param("expected", expected)
            .param("found", found)
    }
}
```

#### Пример использования

```rust
// checking/mod.rs

use crate::util::diagnostic::codes::{ErrorCodeDefinition, E1001};

// 简化方式
return Err(E1001::unknown_variable(&var_name)
    .at(span)
    .build(&i18n_registry));

// 手动方式
return Err(ErrorCodeDefinition::find("E1001")
    .builder()
    .param("name", var_name)
    .at(span)
    .build(&i18n_registry));
```

| Свойство                                         | Описание                                                      |

### Упрощение макросов ошибок

#### Макрос `error!` (автоматическая инъекция контекста)

```rust
/// 编译期自动获取 span 和 i18n 配置的宏
macro_rules! error {
    ($code:ident, $($key:ident = $value:expr),* $(,)?) => {
        $code()
            $(.$key($value))*
            .at(crate::util::span::Span::current())
            .build(crate::util::diagnostic::I18nRegistry::current())
    };
}

/// 使用：只需传参数，span 和 i18n 自动注入
return Err(error!(E1001, name = var_name));
return Err(error!(E1002, expected = "bool", found = cond_ty));
```

#### Ручное использование Builder

```rust
// 需要手动控制时
E1001::unknown_variable(&var_name)
    .at(my_span)           // 自定义 span
    .build(&custom_i18n)   // 自定义 i18n
```

> **Связь с RFC-011b (примечание от 2026-09-22)**:
> [RFC-011b: Перегрузка операторов](./011b-operator-overloading.md) При реализации будут затронуты
> три места в данном разделе: ① в формулировках `E1081` / `E1082` убрать слово "Result" (`?` будет
> проверяться по интерфейсу `Try`, без привязки к конкретному имени типа), синхронизировать с этапом
> 2 по процессу «трёхсторонней согласованности» этого документа (codes/*.rs ↔ locales ↔ таблица
> кодов); ② для отказа при неудовлетворении предварительного ограничения `Equal` (линейный токен)
> повторно использовать семейство `E1101` (тип не реализует интерфейс); ③ после подключения на этапе
> 1 `Struct == Struct` переходит из ошибки времени выполнения `E6007` в решение на этапе компиляции,
> поверхность срабатывания `E6007` сокращается. Зарегистрированные формулировки в таблице
> сохраняются до момента реализации.

> памяти Rust), обнаружение путей переполнения во время выполнения не реализовано. После калибровки:
>
> - E6002 удалён (исходный Assertion failed перенесён в E6005; исходная семантика нулевого указателя
>   не имеет языковой концепции)
> - E6003 изменён с Arithmetic overflow на Runtime index out of bounds (реальная поверхность
>   срабатывания)
> - E6005 изменён с Heap allocation failed на Assertion failed (реальный путь std.assert)
> - E6006 изменён с Runtime index out of bounds на Function not found (реализация уже давно такая)
> - E6007 изменён с Type cast failed на общий Runtime error (единая точка для немаркированных
>   вариантов ExecutorError)

> Правило расположения W-кодов: изоморфны E-кодам и сгруппированы по фазам (W + фаза в разряде
> тысяч), W1xxx = предупреждения фазы проверки типов.
>
> **Семантика мёртвого кода (решение B по #321)**: `pub` определения — это внешний интерфейс,
> никогда не сообщаются — выходит за рамки анализа одного файла, лучше молчать, чем ложно сообщать.
> W1001/W1002/W1004/W1005 нацелены только на **приватные (не `pub`) определения**: сообщается, если
> никогда не упоминается в анализе достижимости ссылок, исходящем из `main` и `pub` определений.
> Метод (W1005) сопоставляется по короткому имени в точке вызова. Семантика target bin/lib
> (неиспользуемый pub внутри bin) — будущее расширение (вариант A по #289), требует поддержки модели
> проекта.
>
> **Неиспользуемый импорт (W1003)**: обнаруживается use-elaboration в typecheck (pass2 регистрирует
> локальные имена импорта, попадание в разбор выражений и позиции аннотаций типов считается
> использованием), покрывает как импорты целиком (`use std.io` → псевдоним модуля), так и
> именованные импорты (`use std.io.{print}`).
>
> **Канал выдачи**: диагностика W-кодов по умолчанию маркируется builder с префиксом W как
> `Severity::Warning` (явное указание имеет приоритет), собирается и отображается по тем же
> правилам, что и ошибки (рендеринг с префиксом `warning[W####]`), но не блокирует компиляцию и не
> влияет на код успешного завершения. `yaoxiang check --deny-warnings` повышает предупреждения до
> сбоя (при наличии предупреждений выход с ненулевым кодом), используется в строгом режиме CI.
> Подавление per-code (атрибут allow и т.п.) — последующее расширение.

### Спецификация качества сообщений

> Этот раздел введён ревизией единства и качества сообщений (от 2026-09-03). Принудительно
> выполняется в CI скриптом `scripts/audit_diagnostics.py`.

1. **Единый канал сообщений**: все видимые пользователю диагностические сообщения должны проходить
   через быстрые методы авторитетного реестра + рендеринг шаблонов locales, код передаёт только
   структурированные параметры. Запрещается обходить реестр и напрямую создавать сырые значения
   вроде `Diagnostic::error(...)` — этот путь обходит проверку кода и i18n.
2. **Корректность кода**: запрещено использовать незарегистрированные и псевдо-коды (например,
   `E_INTERNAL`); литералы кода в точке использования должны быть определены в реестре. Внутренние
   ошибки всегда приводят к E8001 (`internal_error`).
3. **Отображение типов**: Display типа должен различать форму до и после инстанцирования (голые
   имена `Expected 'Container', found 'Container'` неразличимы).
4. **Изоляция внутреннего состояния решателя**: промежуточные TypeVar решателя (форма Display
   `t<N>`) не должны попадать в видимые пользователю сообщения. Тест-якорь:
   `test_type_error_message_no_solver_typevar_leak`.
5. **Граница E8xxx**: E8xxx предназначены только для проблем внутренней согласованности компилятора
   (ICE). Запрещается использовать E8001 как запасной вариант для ошибок, которые пользователь может
   исправить; сообщения ICE должны сопровождаться минимальной инструкцией по воспроизведению.

### Связь значений ошибок времени выполнения с кодами

> Этот раздел введён ревизией значений Error времени выполнения с кодами (от 2026-09-03).
> Семантическое пространство E6xxx/E7xxx одновременно обслуживает два канала, кодовое пространство
> общее, каналы представления различаются.

#### Два канала

| Канал                                  | Носитель                                                  | Способ представления                                          |
| -------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------- |
| Канал диагностики компилятора/CLI      | Аппаратные ошибки уровня хоста, такие как `ExecutorError` | stderr `error[E####]:` (уже подключены E6003/E6005/E6007)     |
| Канал значений ошибок внутри программы | Носитель Err `Error` из std-библиотеки `Result(T, Error)` | Значение языка, потребляется программой через match/сравнение |

#### Структура Error (начиная с v0.8, ломающее изменение)

```
Error { code: String, message: String }
```

- `code` повторно использует нумерацию E6xxx/E7xxx данной спецификации, в строковом виде (например,
  `"E6008"`).
- **Стабильный контракт**: семантика уже распределённых кодов не меняется между версиями; одна и та
  же семантика не использует повторно удалённый код (прецедент E6002).
- **Поверхность потребления**: сравнение `e.code == "E6xxx"` внутри программы — единственный
  программируемый контракт определения; документация `yaoxiang explain E6xxx` согласована; цепочка
  инструментов (LSP / DAP, см. RFC-034) использует код как `exceptionId`.
- **Аксессоры**: `std.result.code(e)` / `std.result.message(e)`.
- **Определяемые пользователем ошибки**: E в `Result(T, E)` является параметром дженерика, для
  серьёзного моделирования используются пользовательские типы; std `Error` — лишь удобный запасной
  носитель, его система кодов не ограничивает пользовательский тип E.

#### Правила распределения кодов

1. Коды значений ошибок времени выполнения и коды диагностики компилятора используют общее
   пространство E6xxx/E7xxx, новые коды распределяются по **реальной поверхности срабатывания**, не
   резервируются для воображаемых сценариев.
2. Сначала регистрация, потом использование: новые коды попадают в авторитетный реестр и проходят
   проверку трёхсторонней согласованности (codes/*.rs ↔ locales ↔ таблица кодов этого документа), и
   только после этого могут выдаваться. Источником регистрации кодов значений ошибок времени
   выполнения является таблица `RUNTIME_ERROR_CODES` в `src/std/result.rs` (как и диагностические
   коды, проверяется на этапе сборки через `build.rs` + `tools/code-tables`).
3. E7xxx зарезервированы для значений ошибок std.io / std.net (в настоящее время пустуют,
   активируются при превращении io/net в Result).
4. Точки выдачи: модули std создают значения Error через `error_new(code, message)`; на стороне
   потребления `std.result.unwrap_err` извлекает носитель Err, `std.result.code/message` читают
   поля.

#### Путь развития (ветка C, не реализован)

После завершения полного сопоставления с образцом (RFC-010b), `Error` может быть обновлён до
`{ kind: ErrorKind, message: String }`, `code` становится атрибутом, производным от kind
(определение варианта и есть реестр кодов). В период развития стабильный контракт `code` данного
раздела остаётся неизменным; это обновление — отдельное решение и не является обязательством этого
раздела.

#### Реализация I18nRegistry

```rust
// locales/*.json（错误码对象）

/// i18n 展示文案注册表（编译期从 JSON 加载，运行时零查表）
pub struct I18nRegistry {
    /// 标题
    titles: HashMap<&'static str, &'static str>,
    /// 描述
    messages: HashMap<&'static str, &'static str>,
    /// 帮助信息
    helps: HashMap<&'static str, &'static str>,
    /// 示例代码
    examples: HashMap<&'static str, &'static str>,
    /// 错误输出示例
    error_outputs: HashMap<&'static str, &'static str>,
}

/// 单个错误码信息
#[derive(Clone, Copy)]
pub struct ErrorInfo<'a> {
    pub title: &'a str,
    pub message: &'a str,
    pub help: &'a str,
    pub example: Option<&'a str>,
    pub error_output: Option<&'a str>,
}

impl I18nRegistry {
    /// 根据语言代码获取注册表
    pub fn new(lang: &str) -> Self {
        match lang {
            "zh" => Self::zh(),
            _ => Self::en(),
        }
    }

    /// 获取错误信息
    pub fn get_info(&self, code: &str) -> Option<ErrorInfo<'_>> {
        Some(ErrorInfo {
            title: self.titles.get(code)?,
            message: self.messages.get(code)?,
            help: self.helps.get(code)?,
            example: self.examples.get(code).copied(),
            error_output: self.error_outputs.get(code).copied(),
        })
    }

    /// 渲染模板（编译期完成，运行时零开销）
    pub fn render(&self, template: &'static str, params: &[(&str, String)]) -> String {
        let mut result = String::with_capacity(template.len() + 64);
        let mut chars = template.chars().peekable();

        while let Some(c) = chars.next() {
            if c == '{' {
                let mut key = String::new();
                while let Some(&c) = chars.peek() {
                    if c == '}' {
                        chars.next();
                        if let Some((_, value)) = params.iter().find(|(k, _)| k == &key) {
                            result.push_str(value);
                        } else {
                            result.push_str(&format!("{{{}}}", key));
                        }
                        break;
                    }
                    key.push(c);
                    chars.next();
                }
            } else {
                result.push(c);
            }
        }
        result
    }
}
```

##### Предопределённые плейсхолдеры (часто используемые)

| Плейсхолдер  | Назначение                        | Пример                              |
| ------------ | --------------------------------- | ----------------------------------- |
| `{name}`     | Имя переменной/типа/трейта и т.п. | `Unknown variable: '{name}'`        |
| `{expected}` | Ожидаемый тип                     | `Expected type '{expected}'`        |

##### Поддержка произвольных ключей

**params поддерживает любые ключи, не только предопределённые**. Вызывающая сторона может передать

// 使用任意 key
E1001::unknown_variable(&var_name)
    .param("location", "global scope")
    .param("hint", "try declaring it first")
    .at(span)
    .build(&i18n);

// 模板定义
"Unknown variable: '{name}' at {location}. {hint}"

#### Ключ к нулевым накладным расходам на поиск по таблицам

**Рендеринг происходит при компиляции пользовательского проекта, а не во время выполнения.**

```
┌─────────────────────────────────────────────────────────────────────────┐
│  阶段 1: Rust 编译 YaoXiang 编译器                                      │
│                                                                           │
│  JSON 打包进编译器二进制                                                 │
│  目的：explain 指令能直接读取 i18n 数据                                  │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  阶段 2: YaoXiang 编译用户项目（渲染发生在这里）                          │
│                                                                           │
│  error! 宏调用时：                                                       │
│  1. 读取 yaoxiang.toml 获取语言偏好                                      │
│  2. 从编译器二进制加载对应语言的 i18n JSON                                │
│  3. 模板 + 参数 → render() → "Unknown variable: 'x'"                    │
│  4. Diagnostic.message = 已渲染的字符串                                   │
│                                                                           │
│  AOT 二进制直接存储最终字符串，无模板，无查表                            │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  阶段 3: 用户程序运行时                                                  │
│                                                                           │
│  println!("{}", diagnostic.message)                                      │
│  // 直接输出最终字符串，无任何查表                                        │
└─────────────────────────────────────────────────────────────────────────┘
```

| Компонент                    | Обязанность                                    | Момент рендеринга                                |
| ---------------------------- | ---------------------------------------------- | ------------------------------------------------ |
| `I18nRegistry`               | Предоставление шаблонов и отображаемого текста | При компиляции пользовательского проекта         |
| `DiagnosticBuilder.render()` | Шаблон + параметры → итоговая строка           | При компиляции пользовательского проекта         |
| `Diagnostic.message`         | Отрендеренная строка                           | Хранит окончательный результат                   |
| AOT-бинарник                 | Содержит окончательную строку                  | Используется непосредственно во время выполнения |

### Уровни серьёзности

Уровень серьёзности ошибки управляется перечислением `DiagnosticLevel` и не зависит от номера кода
ошибки:

```rust
pub enum DiagnosticLevel {
    Error,    // 导致编译失败
    Warning,  // 不影响编译，但建议修复
    Note,     // 补充信息
    Help,     // 修复建议

```

| Уровень | Префикс           | Описание                   |
| ------- | ----------------- | -------------------------- |
| Error   | `error[E####]:`   | Приводит к сбою компиляции |
| Warning | `warning[E####]:` | Не влияет на компиляцию    |
| Note    | `note[E####]:`    | Дополнительная информация  |
| Help    | `help[E####]:`    | Предложение по исправлению |

### Обратная совместимость

Поскольку настоящий RFC проектирует систему кодов ошибок с нуля, проблемы обратной совместимости
отсутствуют.

**Стратегия будущей миграции** (для справки в последующих версиях):

1. Сохранять соответствие старых кодов ошибок новым
2. В период миграции одновременно отображать старые и новые коды
3. Предоставить график устаревания

## Стратегия внедрения

### Этап первый: Базовая инфраструктура кодов ошибок

1. Создать структуру каталога `src/diagnostics/`
2. Реализовать перечисление `ErrorCode`
3. Реализовать `Diagnostic` и `DiagnosticLevel`
4. Создать каталог файлов ресурсов и пример JSON

### Этап второй: Команда `explain`

1. Реализовать CLI-команду `yaoxiang explain`
2. Поддержать опции `--lang` и `--json`
3. Интегрировать загрузку файлов ресурсов
4. Реализовать рендеринг шаблонов параметров

### Этап третий: Интеграция во время компиляции

1. Обновить все точки сообщения об ошибках для использования новой системы
2. Реализовать инъекцию параметров шаблона сообщения
3. Добавить логику приоритета языков
4. Покрытие модульными тестами

### Этап четвёртый: Интеграция с IDE/LSP

1. Интеграция JSON-вывода `explain` в LSP-сервер
2. Отображение ссылок на коды ошибок в IDE
3. Показ объяснения ошибки при наведении
4. Предложения по быстрому исправлению
