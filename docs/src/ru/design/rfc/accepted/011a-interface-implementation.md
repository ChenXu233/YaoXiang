# RFC-011a: Реализация интерфейсов и динамическая диспетчеризация

> **Родительский RFC**:
> [RFC-011: Проект системы обобщений (generics)](../accepted/011-generic-type-system.md)
>
> **Настоящий RFC дополняет и заменяет разделы 2.1-2.4 RFC-011, посвящённые ограничениям
> интерфейсов.**

## Аннотация

RFC-011 определяет систему обобщений, но не детализирует механизм реализации интерфейсов. Настоящий
документ дополняет его:

1. **Объявление интерфейса**: интерфейс — это параметризованный тип — `(Self: Type) -> Type`, при
   реализации в него передаётся конкретный тип
2. **Реализация методов**: поддерживается как внутреннее, так и внешнее объявление
3. **Правила перегрузки**: разные сигнатуры разрешают перегрузку, одинаковые сигнатуры приводят к
   ошибке (переопределение запрещено)
4. **Значения по умолчанию**: после поля сразу пишется `= значение`
5. **Динамическая диспетчеризация**: сбор типов на этапе компиляции + сопоставление интерфейсов, без
   виртуальных таблиц

**Ключевые решения по дизайну**:

```yaoxiang
# Определение интерфейса (параметризованный тип, Self — явный параметр типа)
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

# Определение типа (внутреннее объявление)
Dog: Type = {
    x: Int = 10,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
    speak: (self: Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка)
Dog.speak: (self: Dog, volume: Int) -> String = "WOOF"

# Гетерогенный контейнер (динамическая диспетчеризация)
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
```

**Устранённые сложности**:

- ❌ Нет ключевого слова `impl`
- ❌ Нет магического ключевого слова `Self` (`Self` — это явный параметр типа, ничем не отличающийся
  от `T`)
- ❌ Нет аннотации `dyn Trait + 'a`
- ❌ Нет виртуальных таблиц (сбор типов на этапе компиляции + обёртка в enum)
- ❌ Нет переопределения (единые правила перегрузки)

## Мотивация

### Недостатки RFC-011

RFC-011 определяет систему обобщений, но не раскрывает подробно:

| Проблема                        | Пояснение                                  |
| ------------------------------- | ------------------------------------------ |
| Синтаксис объявления интерфейса | Как объявить, что тип реализует интерфейс? |
| Расположение реализации методов | Внутреннее или внешнее объявление?         |
| Правила перегрузки              | Как обрабатывать одноимённые методы?       |
| Синтаксис значений по умолчанию | Как задать значение по умолчанию для поля? |
| Динамическая диспетчеризация    | Как реализовать гетерогенные контейнеры?   |

### Цели проектирования

1. **Простота**: ключевое слово `impl` не требуется
2. **Гибкость**: реализация методов поддерживается как внутри, так и снаружи
3. **Единообразие**: согласованные правила перегрузки
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: без виртуальных таблиц, сбор типов на этапе компиляции

### Сравнение с Rust

| Свойство                     | Rust                                 | YaoXiang                              |
| ---------------------------- | ------------------------------------ | ------------------------------------- |
| Объявление интерфейса        | `impl Animal for Dog { ... }`        | `Dog: Type = { Animal(Dog), ... }`    |
| Реализация методов           | В блоке `impl`                       | Внутреннее или внешнее                |
| Перегрузка                   | Не поддерживается                    | Поддерживается (разные сигнатуры)     |
| Значения по умолчанию        | Требуется `#[default]`               | Прямая запись `= значение`            |
| Гетерогенный контейнер       | `Vec<Box<dyn Animal + 'a>>`          | `List(Animal)`                        |
| Динамическая диспетчеризация | Поиск в виртуальной таблице          | Сбор типов на этапе компиляции        |
| Ключевое слово Self          | Магическое, с неявной квантификацией | Явный параметр типа, равноправный с T |

## Предложение

### 1. Объявление интерфейса

**Ключевое правило**: интерфейс — это параметризованный тип `(Self: Type) -> Type`, где `Self`
является явным параметром типа, а не магическим ключевым словом. При реализации интерфейс вызывается
с передачей конкретного типа.

```yaoxiang
# Определение интерфейса (полностью совпадает с обобщёнными типами из RFC-011)
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

# Объявление типа, реализующего интерфейс
Dog: Type = {
    x: Int,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
}
```

**Обработка компилятором**:

1. Распознать `Animal(Dog)` как вызов инстанцирования `(Self: Type) -> Type`
2. Выполнить подстановку `Self ↦ Dog`: раскрыть `Animal(Dog)` → `{ speak: (self: Dog) -> String }`
3. Проверить, предоставляет ли `Dog` все требуемые методы (совпадение сигнатур)
4. В случае успеха → сгенерировать доказательство реализации
5. В случае неудачи → ошибка компиляции

**Эквивалент раскрытия**:

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),  # Раскрывается в методы Animal с сохранением метки источника
}

# Эквивалентно (с сохранением информации об источнике)
Dog: Type = {
    x: Int,
    speak: (self: Dog) -> String,  # Из Animal, Self заменён на Dog
}
```

**Зачем нужна метка источника**:

- Прямое раскрытие теряет информацию об источнике
- Метка источника используется для генерации доказательства реализации
- Во время выполнения по доказательству находится корректный метод

#### 1.1 Параметр типа Self и момент проверки типов

`Self` — это явный параметр типа интерфейса, а не магическое ключевое слово.
`Animal: (Self: Type) -> Type` и `List: (T: Type) -> Type` — это одно и то же: конструктор типа
`(Type) -> Type`.

**Момент проверки типов**:

- **При определении интерфейса**: `Self` в `{ speak: (self: Self) -> String }` является абстрактным
  параметром типа, выполняется только синтаксическая проверка.
- **В точке инстанцирования**: при `Animal(Dog)` выполняется подстановка `Self ↦ Dog`, после
  раскрытия проводится полная проверка типов (совпадение сигнатур, наличие методов).

Это позволяет избежать проблемы `Self` как неявного магического ключевого слова из RFC-011 — `Self`
не появляется в определении типа, он встречается только один раз в списке параметров интерфейса и
полностью равноправен с `T`.

#### 1.2 Пространство имён для имён полей и методов

Имена полей и методов типа разделяют одно общее пространство имён. Если после раскрытия интерфейса
имя метода интерфейса конфликтует с именем поля типа, **компиляция завершается с ошибкой**:

```yaoxiang
Drawable: (Self: Type) -> Type = {
    x: (self: Self) -> Int,    // Метод с именем x
}

Point: Type = {
    x: Int,                     // Поле тоже с именем x
    Drawable(Point),            // ❌ Ошибка компиляции: Drawable требует метод x, конфликт с полем x
}
```

Доступ к полю `point.x` и вызов метода `point.x()` синтаксически неразличимы. Единое пространство
имён устраняет неоднозначность.

### 2. Реализация методов

**Ключевое правило**: поддерживается как внутреннее, так и внешнее объявление методов.

#### 2.1 Внутреннее объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",  # Реализация метода внутри
}
```

#### 2.2 Внешнее объявление

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),
}

# Реализация метода снаружи
Dog.speak: (self: Dog) -> String = "Woof"
```

#### 2.3 Смешанное объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",  # Часть методов внутри
}

# Часть методов снаружи
Dog.play: (self: Dog) -> Void = { ... }
```

**Обработка компилятором**:

1. Собрать все определения (внутренние и внешние)
2. Сгруппировать по сигнатуре (перегрузка)
3. Проверить наличие переопределений (ошибка)
4. Проверить полноту интерфейса
5. Сгенерировать доказательство реализации

### 3. Перегрузка и переопределение

**Ключевое правило**:

- Разные сигнатуры → перегрузка → разрешена
- Одинаковые сигнатуры → переопределение → ошибка

#### 3.1 Перегрузка (разрешена)

```yaoxiang
# Разные типы параметров — перегрузка разрешена
Dog.speak: (self: Dog) -> String = "Woof"
Dog.speak: (self: Dog, volume: Int) -> String = "WOOF"
```

#### 3.2 Переопределение (запрещено)

```yaoxiang
# Полностью одинаковые сигнатуры — переопределение запрещено
Dog.speak: (self: Dog) -> String = "Woof"
Dog.speak: (self: Dog) -> String = "Bark"  # ❌ Ошибка: переопределение не разрешено
```

**Сообщение об ошибке**:

```
Ошибка: дублирующееся определение Dog.speak(self: Dog) -> String
  --> файл2:5:1
  |
5 | Dog.speak: (self: Dog) -> String = "Bark"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ Дублирующееся определение
  |
  --> файл1:3:1
  |
3 | Dog.speak: (self: Dog) -> String = "Woof"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ Первое определение
```

#### 3.3 Единые правила

**Внутренние и внешние объявления подчиняются одинаковым правилам перегрузки/переопределения**:

```yaoxiang
# Внутреннее объявление
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка, разрешена)
Dog.speak: (self: Dog, volume: Int) -> String = "WOOF"

# Внешнее объявление (переопределение, запрещено)
Dog.speak: (self: Dog) -> String = "Bark"  # ❌ Ошибка
```

### 4. Значения по умолчанию

**Ключевое правило**: после поля пишется `= значение`, что избавляет от необходимости в
конструкторе.

```yaoxiang
Dog: Type = {
    x: Int = 10,  # Значение по умолчанию
    y: Int = 20,  # Значение по умолчанию
    Animal(Dog),
}
```

**Сгенерированные компилятором конструкторы**:

```yaoxiang
# Все поля имеют значения по умолчанию → генерируется конструктор без параметров
Dog.new: () -> Dog = { x: 10, y: 20 }

# Часть полей имеет значения по умолчанию → генерируются частичные конструкторы
Dog.new: (x: Int) -> Dog = { x: x, y: 20 }
Dog.new: (y: Int) -> Dog = { x: 10, y: y }

# Полный конструктор
Dog.new: (x: Int, y: Int) -> Dog = { x: x, y: y }
```

**Внешнее объявление значений по умолчанию**:

```yaoxiang
Dog: Type = {
    x: Int,
    y: Int,
    Animal(Dog),
}

# Внешнее объявление значений по умолчанию
Dog.x: Int = 10
Dog.y: Int = 20
```

Эквивалентно внутреннему объявлению.

```

2. Для каждого инстанцирования интерфейса выполнить подстановку Self ↦ ConcreteType
3. Раскрыть сигнатуры методов интерфейса, проверить совпадение сигнатур

5. Сгруппировать по сигнатуре (перегрузка)
6. Проверить переопределения (ошибка)
7. Проверить полноту интерфейса
8. Сгенерировать доказательство реализации
```

### 6. Динамическая диспетчеризация

**Ключевой замысел**: сбор типов на этапе компиляции + сопоставление интерфейсов, без виртуальных
таблиц.

#### 6.1 Гетерогенный контейнер

`Animal` — это `(Self: Type) -> Type`. `List(Animal)` использует неинстанцированный конструктор типа
интерфейса как **экзистенциальный тип** (existential): `∃S. Animal(S)` — «существует некоторый тип
S, такой что S реализует Animal(S)».

```yaoxiang
# Определение интерфейса
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

# Определение типа
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: Dog) -> String = "Woof",
}

Cat: Type = {
    y: Int,
    Animal(Cat),
    speak: (self: Cat) -> String = "Meow",
}

# Гетерогенный контейнер — Animal не инстанцирован = экзистенциальный тип
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
animals[1].speak()  # "Meow"
```

**Семантика владения**: помещение в гетерогенный контейнер имеет семантику перемещения (Move,
согласно RFC-009). `Dog.new()` перемещается в вариант перечисления `AnimalGroup::Dog`, исходная
переменная становится недоступной.

```yaoxiang
dog = Dog.new()
animals: List(Animal) = [dog]
# dog.speak()  ← ❌ Ошибка компиляции: dog уже перемещён
```

#### 6.2 Сбор типов на этапе компиляции

**Ключевая стратегия: отслеживание владения с инкрементальным построением.** Вместо сканирования на
этапе компиляции всех типов, реализующих интерфейс, выполняется **инкрементальный сбор в каждой
точке операции владения** над `List(Animal)`:

```yaoxiang
// Точка конструирования
animals: List(Animal) = [Dog.new()]       // AnimalGroup = { Dog(Dog) }

// Точка append
animals.append(Cat.new())                  // Компилятор видит Cat в append → расширяет до { Dog, Cat }
animals.append(Bird.new())                 // Дальнейшее расширение { Dog, Cat, Bird }
```

**Обработка компилятором** (инкрементальная):

1. При первом конструировании `List(Animal)` → сгенерировать начальное перечисление (все
   типы-конструкторы, известные в текущей компиляционной единице)
2. Каждый `append` / `push` / присваивание по индексу → проверить, присутствует ли тип значения в
   перечислении; если нет — расширить перечисление новым вариантом
3. Для финального перечисления сгенерировать мономорфизированный `match` для диспетчеризации
4. Между компиляционными единицами: полагаться на LTO (Link-Time Optimization) для слияния вариантов
   перечисления. Когда `Animal` как экзистенциальный тип передаётся через границу компиляционной
   единицы, каждая единица генерирует частичный набор вариантов, а на этапе линковки они
   объединяются в полное перечисление.

**Автоматически сгенерированное перечисление**:

```yaoxiang
# Автоматически генерируется компилятором (невидимо для пользователя)
AnimalGroup: Type = {
    Dog(Dog),
    Cat(Cat),
    Bird(Bird),    # ← Добавлен из append(Bird.new())
}

# List(Animal) внутри эквивалентен List(AnimalGroup)
```

#### 6.3 Проверка соответствия интерфейсу

**Ключевое наблюдение**: проверка соответствия интерфейсу выполняется на этапе компиляции, даже если
типы поступают из динамически загружаемых плагинов.

```yaoxiang
# Система плагинов
plugin = load_plugin("bird.so")

# Проверка компилятора: возвращаемый тип plugin.create_bird() должен реализовывать Animal
bird: Animal = plugin.create_bird()  # Проверка на этапе компиляции, экзистенциальный тип

# Помещение в гетерогенный контейнер — точка append запускает расширение перечисления
animals: List(Animal) = [Dog.new(), Cat.new()]
animals.append(bird)                 # Компилятор: (1) проверяет, что bird реализует Animal (2) расширяет перечисление
```

**Обработка компилятором**:

1. Проверить возвращаемый тип аргумента `append`
2. Убедиться, что этот тип реализует целевой интерфейс
3. В случае успеха → расширить перечисление, разрешить помещение
4. В случае неудачи → ошибка компиляции

#### 6.4 Диспетчеризация во время выполнения

**Поток вызова (компиляционный match по перечислению, ImplementationProof стёрт):**

```
animals[0].speak()
  ↓
Сгенерированный компилятором match:
  match animals[0] {
    AnimalGroup.Dog(d) => d.speak(),
    AnimalGroup.Cat(c) => c.speak(),
    AnimalGroup.Bird(b) => b.speak(),
  }
```

**Проекция бренда** (взаимодействие с RFC-009a): привязка шаблона `AnimalGroup.Dog(d)` в match
порождает в дереве брендов дочерний бренд `#animals[0].Dog`, эквивалентный проекции поля
(`#42.field_x`). Цепочка брендов, создаваемая `d.speak()` как `ReadToken(d)`, выглядит как
`animals → animals[0] → d → ReadToken(d)`; проверка заимствований выполняет сопоставление по
префиксу дерева брендов.

**Тип результата индексации**: `animals[0]` возвращает `&AnimalGroup` (тип перечисления,
сгенерированный компилятором); пользователь не может напрямую получить `&mut Animal`. Изменяемый
доступ осуществляется опосредованно через методы интерфейса (например, `animals[0].mutate()` внутри
раскрывается в `AnimalGroup::Dog(d) => d.mutate()`).

**Сравнение с виртуальными таблицами**:

|                               | Виртуальная таблица (Rust)          | Компиляционное перечисление (YaoXiang)               |
| ----------------------------- | ----------------------------------- | ---------------------------------------------------- |
| Способ поиска                 | Указатель vtable → указатель метода | match по enum → прямой вызов                         |
| Накладные расходы в runtime   | Одно косвенное обращение            | Ветвление (предсказуемо CPU)                         |
| Генерация на этапе компиляции | Виртуальная таблица                 | Enum + match                                         |
| Аннотации пользователя        | Требуется `dyn Trait + 'a`          | Не требуются                                         |
| ImplementationProof           | Не применимо                        | Стирается на этапе компиляции, отсутствует в runtime |

**Преимущества YaoXiang**:

- Не нужны аннотации брендов
- Безопасность типов на этапе компиляции
- Прозрачно для пользователя (не нужно писать `dyn Animal`)
- ImplementationProof — чисто компиляционная концепция, нулевые накладные расходы в runtime

#### 6.5 Ограничения и область применения

**В пределах одной компиляционной единицы:** полная поддержка. Отслеживание владения покрывает все
точки `append`/конструирования, перечисление строится инкрементально.

**Между компиляционными единицами:** Полагаемся на LTO (Link-Time Optimization) для слияния
вариантов перечисления. `Animal` как экзистенциальный тип (`∃S. Animal(S)`) передаётся через границу
компиляционной единицы. Каждая единица генерирует частичный набор вариантов, на этапе линковки они
объединяются.

**Не поддерживается:** полностью динамические типы времени выполнения (чистый утиный тип). Набор
типов должен быть полностью известен на этапе компиляции.

## Компромиссы

### Преимущества

1. **Простота**: ключевое слово `impl` не требуется
2. **Гибкость**: реализация методов поддерживается как внутри, так и снаружи
3. **Единообразие**: согласованные правила перегрузки
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: без виртуальных таблиц, сбор типов на этапе компиляции
6. **Безопасность типов**: соответствие интерфейсу проверяется на этапе компиляции
7. **Прозрачно для пользователя**: не нужно писать `dyn Animal + 'a`

### Недостатки

1. **Ограничение**: полностью динамические типы времени выполнения не поддерживаются (чистый утиный
   тип)
2. **Накладные расходы на этапе компиляции**: для каждого интерфейса необходимо сгенерировать
   варианты перечисления и код диспетчеризации match
3. **Набор типов**: должен быть полностью известен на этапе компиляции (в пределах одной
   компиляционной единицы)

### Меры по смягчению

1. **Система плагинов**: поддерживается через проверку соответствия интерфейсу на этапе компиляции
2. **Набор типов**: отслеживание владения с инкрементальным построением — сбор в каждой точке
   `append`/конструирования, а не глобальное сканирование
3. **Между компиляционными единицами**: слияние наборов вариантов перечисления на этапе линковки,
   общий механизм с мономорфизацией на этапе линковки

## Связь с RFC-009

**Бренды и реализация интерфейсов**:

- Реализация интерфейса находится на уровне типов и не затрагивает бренды
- Бренды находятся на уровне доказательств заимствования (RFC-009a)
- Эти два механизма ортогональны и не влияют друг на друга

**Динамическая диспетчеризация и бренды**:

- Динамическая диспетчеризация использует доказательство реализации, не требует аннотаций брендов
- Доказательство реализации генерируется на этапе компиляции, нулевой поиск в runtime
- Устраняется сложность `dyn Trait + 'a`

**Владение в гетерогенном контейнере**:

- Помещение в `List(Animal)` имеет семантику перемещения (Move, согласно RFC-009), исходная
  переменная становится недоступной
- Индексация `animals[0]` возвращает `&AnimalGroup` (сгенерированное компилятором перечисление);
  цепочка проекции бренда: `animals → animals[0] → enum_variant → field`
- Изменяемый доступ осуществляется опосредованно через методы интерфейса, `&mut AnimalGroup` не
  предоставляется пользователю напрямую

## Наследование интерфейсов

Интерфейс может содержать другой интерфейс. **Новый синтаксис не вводится** — используется та же
самая синтаксическая позиция, что и для объявления интерфейса типом:

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                       # Pet наследует Animal — без новых ключевых слов
    name: (self: Self) -> String,
}

# Когда Dog реализует Pet, он должен удовлетворять методам и Animal, и Pet
Dog: Type = {
    x: Int,
    Pet(Dog),
    speak: (self: Dog) -> String = "Woof",  # Из Animal
    name: (self: Dog) -> String = "Buddy",  # Из Pet
}
```

**Принцип проектирования:** Наследование существует, но злоупотреблять им не рекомендуется. Основной
способ композиции — через инстанцирование нескольких интерфейсов
(`Dog: Type = { Animal(Dog), Pet(Dog), ... }`). Тип может напрямую объявить все интерфейсы, которые
он удовлетворяет, без необходимости выражать это через дерево наследования. Наследование интерфейсов
используется только при наличии явной иерархии «is-a».

**Обработка компилятором:** раскрытие цепочки наследования. `Pet(Self)` раскрывается в
`{ все методы Animal(Self), name: ... }`. Когда `Dog` объявляет `Pet(Dog)`, выполняется
`Self ↦ Dog`, и компилятор проверяет, что `Dog` удовлетворяет всем методам как `Animal(Dog)`, так и
`Pet(Dog)`.

**Подстановка Self в наследовании интерфейсов**: в
`Pet: (Self: Type) -> Type = { Animal(Self), ... }` параметр `Self` в `Animal(Self)` — это параметр
`Self` интерфейса `Pet` — его подстановка отложена. Когда `Dog` реализует `Pet(Dog)`, выполняется
`Self ↦ Dog`, и `Animal(Self)` превращается в `Animal(Dog)`. Это полностью совпадает с семантикой
передачи параметров в обобщённых функциях.

## Реализация методов по умолчанию

Интерфейс может предоставлять реализации методов по умолчанию. Реализующий тип может выбрать
переопределение или наследование реализации по умолчанию:

```yaoxiang
fmt: (Self: Type) -> Type = {
    display: (self: Self) -> String,                      # Должен быть реализован
    debug: (self: Self) -> String = self.display(),       # ✅ Ссылается на метод того же интерфейса
    summary: (self: Self) -> String = f"<{self.name}>",  # ❌ Ошибка компиляции: self.name отсутствует в fmt
}
```

**Ключевое ограничение: интерфейс не может предполагать наличие вышестоящих реализаций.** Метод по
умолчанию может ссылаться только на методы, уже объявленные в том же интерфейсе. Поля конкретного
типа или методы других интерфейсов недоступны для метода по умолчанию — интерфейс представляет собой
замкнутый контракт и не может «лезть в карман» реализующего типа. Нарушение этого ограничения
приводит к **немедленной ошибке на этапе определения интерфейса**.

**Наследование может предполагать наличие нижестоящих реализаций:** когда интерфейс `Pet(Self)`
наследует `Animal(Self)`, методы по умолчанию `Pet` могут использовать методы, объявленные в
`Animal` — поскольку наследование гарантирует их наличие.

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                                              # Наследование
    name: (self: Self) -> String,
    introduce: (self: Self) -> String = self.name() + " говорит " + self.speak(),  # ✅ speak приходит из унаследованного Animal
}
```

**Поведение на этапе компиляции:** при реализации типа для каждого метода:

1. Тип предоставил метод → используется метод типа
2. Тип не предоставил, интерфейс имеет реализацию по умолчанию → компилятор встраивает реализацию по
   умолчанию в тип (нулевые накладные расходы на vtable)
3. Тип не предоставил, интерфейс не имеет реализации по умолчанию → ошибка компиляции

**Принцип проектирования:** методы по умолчанию похожи на механизм автоматического вывода `Copy`/`Clone`
— компилятор автоматически генерирует их при необходимости, пользователь может их переопределить.
Ключевые слова `virtual`/`override`/`super` не вводятся.

## Открытые вопросы

- [x] ~~Наследование интерфейсов (интерфейс может наследовать другие интерфейсы)~~ → Поддерживается,
      без нового синтаксиса. `Pet: (Self: Type) -> Type = { Animal(Self), ... }`
- [x] ~~Реализация методов по умолчанию (интерфейс может предоставлять реализацию по умолчанию)~~ →
      Поддерживается, аналогично автовыводу Copy. Интерфейс предоставляет тело, компилятор по
      необходимости встраивает его
- [x] ~~`Self` как неявное магическое ключевое слово~~ → Устранено. `Self` — явный параметр типа,
      интерфейс — это `(Self: Type) -> Type`
- [ ] Продвинутые случаи ограничений интерфейсов (ассоциированные типы, GAT) — ассоциированные типы
      реализуются через параметры обобщённого интерфейса

      замыкания не поддерживают прямую реализацию интерфейсов, требуется тип-обёртка. Реализация
      интерфейсов анонимными типами — для последующих RFC
