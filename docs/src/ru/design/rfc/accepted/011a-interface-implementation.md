# RFC-011a: Реализация интерфейсов и динамическая диспетчеризация

> **Родительский RFC**: [RFC-011: Дизайн системы обобщений](../accepted/011-generic-type-system.md)
>
> **Настоящий RFC дополняет и заменяет раздел RFC-011 §2.1-2.4, посвящённый ограничениям
> интерфейсов.**

## Резюме

RFC-011 определяет систему обобщений, но не детализирует механизм реализации интерфейсов. Настоящий
документ дополняет:

1. **Объявление интерфейса**: интерфейс — это параметризованный тип — `(Self: Type) -> Type`, при
   реализации в него передаётся конкретный тип
2. **Реализация методов**: поддерживаются как внутренние, так и внешние объявления
3. **Правила перегрузки**: разные сигнатуры разрешают перегрузку, одинаковые сигнатуры приводят к
   ошибке (перекрытие запрещено)
4. **Значения по умолчанию**: после поля пишется `= value`
5. **Динамическая диспетчеризация**: сбор типов на этапе компиляции + сопоставление интерфейсов, без
   виртуальных таблиц

**Основной дизайн**:

```yaoxiang
# Определение интерфейса (параметризованный тип, Self — явный параметр типа)
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# Определение типа (внутреннее объявление)
Dog: Type = {
    x: Int = 10,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
    speak: (self: &Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка)
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# Гетерогенный контейнер (динамическая диспетчеризация)
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
```

**Соглашение о записи получателя** (исправление от 30.08.2026, согласовано с семантикой владения из
RFC-009):

- Получатель метода следует семантике сигнатуры: `&Self` = заимствование (соглашение интерфейса по
  умолчанию — вызов метода не потребляет получателя), `&mut Self` = изменяемое заимствование, по
  значению `Self` = потребление получателя (Move, RFC-009).
- `Self` в сигнатуре на стороне impl — это псевдоним типа impl: интерфейс `speak: (self: &Self)`
  совпадает с impl `(self: &Dog)` / `(self: &Self)` (после подстановки Self↦тип impl полностью
  совпадают, §3).
- Запись получателя по значению в исторических примерах (`(self: Self)`) означала заимствование; в
  настоящем документе она унифицирована в явную `&Self`; запись по значению отныне сохраняет
  семантику «потребления» и больше не смешивается.

**Устранённая сложность**:

- ❌ Нет ключевого слова `impl`
- ❌ Нет магического ключевого слова `Self` (`Self` — явный параметр типа, ничем не отличается от
  `T`)
- ❌ Нет аннотации `dyn Trait + 'a`
- ❌ Нет виртуальных таблиц (сбор типов на этапе компиляции + обёртка в перечисление)
- ❌ Нет перекрытия (правила перегрузки унифицированы)

## Мотивация

### Недостатки RFC-011

RFC-011 определяет систему обобщений, но не детализирует:

| Проблема                        | Описание                                   |
| ------------------------------- | ------------------------------------------ |
| Синтаксис объявления интерфейса | Как объявить, что тип реализует интерфейс? |
| Расположение реализации метода  | Внутреннее или внешнее объявление?         |
| Правила перегрузки              | Как обрабатывать одноимённые методы?       |
| Синтаксис значений по умолчанию | Как задать полю значение по умолчанию?     |
| Динамическая диспетчеризация    | Как реализовать гетерогенные контейнеры?   |

### Цели дизайна

1. **Простота**: не нужно ключевое слово `impl`
2. **Гибкость**: реализация методов поддерживается и внутри, и снаружи
3. **Единообразие**: согласованные правила перегрузки
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: нет виртуальных таблиц, сбор типов на этапе компиляции

### Сравнение с Rust

| Характеристика               | Rust                                             | YaoXiang                           |
| ---------------------------- | ------------------------------------------------ | ---------------------------------- |
| Объявление интерфейса        | `impl Animal for Dog { ... }`                    | `Dog: Type = { Animal(Dog), ... }` |
| Реализация метода            | В блоке `impl`                                   | Внутри или снаружи                 |
| Перегрузка                   | Не поддерживается                                | Поддерживается (разные сигнатуры)  |
| Значение по умолчанию        | Нужен `#[default]`                               | Просто пишется `= value`           |
| Гетерогенный контейнер       | `Vec<Box<dyn Animal + 'a>>`                      | `List(Animal)`                     |
| Динамическая диспетчеризация | Поиск по виртуальной таблице                     | Сбор типов на этапе компиляции     |
| Ключевое слово Self          | Магическое ключевое слово, неявная квантификация | Явный параметр типа, равен T       |

## Предложение

### 1. Объявление интерфейса

**Ключевое правило**: интерфейс — это параметризованный тип `(Self: Type) -> Type`, где `Self` —
явный параметр типа, а не магическое ключевое слово. При реализации интерфейс вызывается с передачей
конкретного типа.

```yaoxiang
# Определение интерфейса (полностью соответствует обобщённым типам из RFC-011)
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# Объявление типа, реализующего интерфейс
Dog: Type = {
    x: Int,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
}
```

**Обработка компилятором**:

1. Распознать, что `Animal(Dog)` — это вызов инстанцирования `(Self: Type) -> Type`
2. Выполнить подстановку `Self ↦ Dog`: развернуть `Animal(Dog)` →
   `{ speak: (self: &Dog) -> String }`
3. Проверить, предоставляет ли `Dog` все требуемые методы (совпадение сигнатур)
4. При успехе → сгенерировать доказательство реализации
5. При неудаче → ошибка компиляции

**Эквивалентность развёртывания**:

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),  # Разворачивается в методы Animal с сохранением метки источника
}

# Эквивалентно (с сохранением информации об источнике)
Dog: Type = {
    x: Int,
    speak: (self: &Dog) -> String,  # Из Animal, Self заменён на Dog
}
```

**Зачем нужна метка источника**:

- Прямое развёртывание теряет информацию об источнике
- Метка источника используется для генерации доказательства реализации
- Во время выполнения по доказательству находится нужный метод

#### 1.1 Параметр типа Self и момент проверки типов

`Self` — это явный параметр типа интерфейса, а не магическое ключевое слово.
`Animal: (Self: Type) -> Type` и `List: (T: Type) -> Type` — это одно и то же — конструктор типа
`(Type) -> Type`.

**Момент проверки типов**:

- **При определении интерфейса**: `Self` в `{ speak: (self: &Self) -> String }` — это абстрактный
  параметр типа, выполняется только синтаксическая проверка.
- **В точке инстанцирования**: при `Animal(Dog)` выполняется подстановка `Self ↦ Dog`, после чего
  выполняется полная проверка типов (совпадение сигнатур, существование методов).

Это позволяет избежать проблемы `Self` как неявного магического ключевого слова из RFC-011 — `Self`
не появляется в определении типа, он встречается лишь однажды в списке параметров интерфейса и
полностью равен `T`.

#### 1.2 Пространство имён полей и методов

Имена полей и методов типа разделяют одно пространство имён. Если после развёртывания интерфейса имя
метода интерфейса конфликтует с именем поля типа, **компиляция завершается с ошибкой**:

```yaoxiang
Drawable: (Self: Type) -> Type = {
    x: (self: &Self) -> Int,    # Метод с именем x
}

Point: Type = {
    x: Int,                     # Поле с именем x
    Drawable(Point),            # ❌ Ошибка компиляции: Drawable требует метод x, конфликт с полем x
}
```

Доступ к полю `point.x` и вызов метода `point.x()` синтаксически неразличимы. Единое пространство
имён устраняет неоднозначность.

### 2. Реализация методов

**Ключевое правило**: поддерживаются как внутренние, так и внешние объявления реализации методов.

#### 2.1 Внутреннее объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Реализация метода внутри
}
```

#### 2.2 Внешнее объявление

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),
}

# Реализация метода снаружи
Dog.speak: (self: &Dog) -> String = "Woof"
```

#### 2.3 Смешанное объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Часть методов внутри
}

# Часть методов снаружи
Dog.play: (self: &Dog) -> Void = { ... }
```

**Обработка компилятором**:

1. Собрать все определения (внутренние и внешние)
2. Сгруппировать по сигнатуре (перегрузка)
3. Проверить наличие перекрытий (сообщить об ошибке)
4. Проверить полноту интерфейса
5. Сгенерировать доказательство реализации

### 3. Перегрузка и перекрытие

**Ключевое правило**:

- Разные сигнатуры → перегрузка → разрешена
- Одинаковые сигнатуры → перекрытие → ошибка

#### 3.1 Перегрузка (разрешена)

```yaoxiang
# Разные типы параметров — перегрузка разрешена
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"
```

#### 3.2 Перекрытие (запрещено)

```yaoxiang
# Полностью одинаковые сигнатуры — перекрытие запрещено
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ Ошибка: перекрытие не разрешено
```

**Сообщение об ошибке**:

```
Ошибка: повторное определение Dog.speak(self: &Dog) -> String
  --> файл2:5:1
  |
5 | Dog.speak: (self: &Dog) -> String = "Bark"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ повторное определение
  |
  --> файл1:3:1
  |
3 | Dog.speak: (self: &Dog) -> String = "Woof"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ первое определение
```

#### 3.3 Единообразие правил

**Внутренние и внешние объявления подчиняются одинаковым правилам перегрузки/перекрытия**:

```yaoxiang
# Внутреннее объявление
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка, разрешена)
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# Внешнее объявление (перекрытие, запрещено)
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ Ошибка
```

### 4. Значения по умолчанию

**Ключевое правило**: после поля пишется `= value`, что избавляет от необходимости в конструкторе.

```yaoxiang
Dog: Type = {
    x: Int = 10,  # Значение по умолчанию
    y: Int = 20,  # Значение по умолчанию
    Animal(Dog),
}
```

**Сгенерированный компилятором конструктор**:

```yaoxiang
# Все поля имеют значения по умолчанию → генерируется конструктор без аргументов
Dog.new: () -> Dog = { x: 10, y: 20 }

# Часть полей имеет значения по умолчанию → генерируется конструктор с частичными параметрами
Dog.new: (x: Int) -> Dog = { x: x, y: 20 }
Dog.new: (y: Int) -> Dog = { x: 10, y: y }

# Конструктор со всеми параметрами
Dog.new: (x: Int, y: Int) -> Dog = { x: x, y: y }
```

**Внешнее объявление значений по умолчанию**:

```yaoxiang
Dog: Type = {
    x: Int,
    y: Int,
    Animal(Dog),
}

# Внешнее объявление значений по умолчанию
Dog.x: Int = 10
Dog.y: Int = 20
```

**Эквивалентно внутреннему объявлению**.

```
1. Разобрать определения типов, собрать объявления инстанцирования интерфейсов (Animal(Dog))
2. Для каждого инстанцирования интерфейса выполнить подстановку Self ↦ ConcreteType
3. Развернуть сигнатуры методов интерфейса, проверить совпадение сигнатур

5. Сгруппировать по сигнатуре (перегрузка)
6. Проверить перекрытия (сообщить об ошибке)
7. Проверить полноту интерфейса
8. Сгенерировать доказательство реализации
```

### 6. Динамическая диспетчеризация

**Основной дизайн**: сбор типов на этапе компиляции + сопоставление интерфейсов, без виртуальных
таблиц.

#### 6.1 Гетерогенный контейнер

`Animal` — это `(Self: Type) -> Type`. `List(Animal)` использует неинстанцированный конструктор типа
интерфейса как **экзистенциальный тип** (existential): `∃S. Animal(S)` — «существует некоторый тип
S, такой что S реализует Animal(S)».

```yaoxiang
# Определение интерфейса
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# Определение типа
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

Cat: Type = {
    y: Int,
    Animal(Cat),
    speak: (self: &Cat) -> String = "Meow",
}

# Гетерогенный контейнер — Animal не инстанцирован = экзистенциальный тип
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
animals[1].speak()  # "Meow"
```

**Семантика владения**: помещение в гетерогенный контейнер — это семантика Move (RFC-009).
`Dog.new()` перемещается в вариант перечисления `AnimalGroup::Dog`, исходная переменная становится
недоступной.

```yaoxiang
dog = Dog.new()
animals: List(Animal) = [dog]
# dog.speak()  ← ❌ Ошибка компиляции: dog уже перемещён
```

#### 6.2 Сбор типов на этапе компиляции

**Основная стратегия: отслеживание владения, инкрементальное построение.** Это не сканирование на
этапе компиляции всех типов, реализующих интерфейс, — а инкрементальный сбор в **точках операций
владения** каждого `List(Animal)`:

```yaoxiang
// Точка конструирования
animals: List(Animal) = [Dog.new()]       // AnimalGroup = { Dog(Dog) }

// Точка append
animals.append(Cat.new())                  // Компилятор видит Cat в append → расширяет до { Dog, Cat }
animals.append(Bird.new())                 // Расширяет до { Dog, Cat, Bird }
```

**Обработка компилятором** (инкрементально):

1. При первом конструировании `List(Animal)` → сгенерировать начальное перечисление (все известные
   на текущий момент типы конструирования в компилируемой единице)
2. При каждом `append` / `push` / присваивании по индексу → проверить, присутствует ли тип значения
   в перечислении; если нет — добавить вариант
3. Для итогового перечисления сгенерировать мономорфизированный `match` для диспетчеризации
4. Между компилируемыми единицами: полагаемся на LTO (Link-Time Optimization) для объединения
   вариантов перечисления. Когда `Animal` как экзистенциальный тип передаётся через границу
   компилируемой единицы, каждая единица генерирует частичные варианты, на этапе линковки они
   объединяются в полное перечисление.

**Автоматически сгенерированное перечисление**:

```yaoxiang
# Автоматически сгенерировано компилятором (невидимо для пользователя)
AnimalGroup: Type = {
    Dog(Dog),
    Cat(Cat),
    Bird(Bird),    # ← append(Bird.new()) запускает инкрементальное расширение
}

# List(Animal) внутри эквивалентен List(AnimalGroup)
```

#### 6.3 Проверка соответствия интерфейсу

**Ключевое наблюдение**: проверка соответствия интерфейсу выполняется на этапе компиляции, даже если
тип поступает из динамически загружаемого плагина.

```yaoxiang
# Система плагинов
plugin = load_plugin("bird.so")

# Проверка компилятора: возвращаемый тип plugin.create_bird() должен реализовывать Animal
bird: Animal = plugin.create_bird()  # Проверка на этапе компиляции, экзистенциальный тип

# Помещение в гетерогенный контейнер — точка append запускает расширение перечисления
animals: List(Animal) = [Dog.new(), Cat.new()]
animals.append(bird)                 // Компилятор: (1) проверяет, что bird реализует Animal (2) расширяет перечисление
```

**Обработка компилятором**:

1. Проверить возвращаемый тип аргумента `append`
2. Проверить, реализует ли этот тип целевой интерфейс
3. При успехе → расширить перечисление, разрешить помещение
4. При неудаче → ошибка компиляции

#### 6.4 Диспетчеризация во время выполнения

**Поток вызова (match по перечислению на этапе компиляции, ImplementationProof стёрт)**:

```
animals[0].speak()
  ↓
match, сгенерированный компилятором:
  match animals[0] {
    AnimalGroup.Dog(d) => d.speak(),
    AnimalGroup.Cat(c) => c.speak(),
    AnimalGroup.Bird(b) => b.speak(),
  }
```

**Проекция бренда** (взаимодействие с RFC-009a): привязка шаблона match `AnimalGroup.Dog(d)`
порождает в дереве брендов дочерний бренд `#animals[0].Dog`, эквивалентный проекции поля
(`#42.field_x`). Цепочка брендов `ReadToken(d)`, созданная `d.speak()`, имеет вид
`animals → animals[0] → d → ReadToken(d)`, заимствующий проверяющий (borrow checker) верифицирует
конфликты через сопоставление префиксов в дереве брендов.

**Тип при доступе по индексу**: `animals[0]` возвращает `&AnimalGroup` (сгенерированный компилятором
тип перечисления); пользователь не может напрямую получить `&mut Animal`. Изменяемый доступ
реализуется косвенно через методы интерфейса (например, `animals[0].mutate()` внутри разворачивается
в `AnimalGroup::Dog(d) => d.mutate()`).

**Сравнение с виртуальными таблицами**:

|                                       | Виртуальная таблица (Rust)               | Перечисление на этапе компиляции (YaoXiang)                    |
| ------------------------------------- | ---------------------------------------- | -------------------------------------------------------------- |
| Способ поиска                         | Указатель на vtable → указатель на метод | match по перечислению → прямой вызов                           |
| Накладные расходы во время выполнения | Одно косвенное обращение                 | branch (может быть оптимизирован предсказателем переходов CPU) |
| Генерация на этапе компиляции         | Виртуальная таблица                      | Перечисление + match                                           |
| Аннотации пользователя                | Требуется `dyn Trait + 'a`               | Не требуются                                                   |
| ImplementationProof                   | Неприменимо                              | Стирается на этапе компиляции, отсутствует во время выполнения |

**Преимущества YaoXiang**:

- Не требуется аннотация бренда
- Типобезопасность на этапе компиляции
- Прозрачно для пользователя (не нужно писать `dyn Animal`)
- ImplementationProof — чисто компиляционная концепция, нулевые накладные расходы во время
  выполнения

#### 6.5 Ограничения и область применимости

**В пределах одной компилируемой единицы**: полная поддержка. Отслеживание владения охватывает все
точки `append`/конструирования, перечисление строится инкрементально.

**Между компилируемыми единицами**: полагаемся на LTO (Link-Time Optimization) для объединения
вариантов перечисления. `Animal` как экзистенциальный тип (`∃S. Animal(S)`) передаётся через границу
компилируемой единицы. Каждая единица генерирует частичные варианты, на этапе линковки они
объединяются.

**Не поддерживается**: динамические типы во время выполнения (полностью утиная типизация). Набор
типов полностью известен на этапе компиляции.

#### 6.6 Заметки о реализации (этап 3 задачи #307, v1 уже реализован)

Семантика §6 (гетерогенные контейнеры, проверка членов на этапе компиляции, диспетчеризация по
фактическому типу, замкнутость набора типов на этапе компиляции) полностью реализована; форма
реализации конкретизирована на уровне механизмов следующим образом:

- **Сбор типов**: разовый сбор набора реализующих типов по `ImplementationProof` для всей
  компилируемой единицы, вместо «инкрементального сбора по точкам операций владения» из §6.2. Внутри
  одной компилируемой единицы оба варианта семантически эквивалентны (лишние мёртвые варианты
  безвредны); ценность инкрементального сбора проявляется в межъединичных сценариях и относится к v2
  (см. ниже).
- **Представление**: компилятор синтезирует тип-группу вариантов `Animal$Group`, как чистый артефакт
  IR/байт-кода/среды выполнения (инструкции `CreateVariant`/`VariantTag`/`VariantPayload`, значение
  во время выполнения `RuntimeValue::Enum`), MonoType ничего об этом не знает — на уровне проверки
  типов видимый для пользователя тип остаётся именем интерфейса. Каждое конкретное значение,
  попадающее в позицию экзистенциального типа, автоматически оборачивается в значение-вариант
  (единое непрозрачное представление, семантика §6.4).
- **Точки обёртывания**: typecheck выполняет направленный обход в местах определения «конкретный vs
  экзистенциальный» (аннотированный let/аргумент вызова/return/элемент литерала списка), порождая
  таблицу принудительного применения с ключом span; генерация IR внедряет обёртывание по span.
  Пропущенные обёртывания отвергаются громко защитными проверками среды выполнения (валидация
  `VariantTag`/`VariantPayload` требует, чтобы значение было вариантом именованной группы), в худшем
  случае — явная ошибка во время выполнения на этапе тестирования, никогда не тихое порождение
  неверных данных.
- **Диспетчеризация**: цепочка переходов по сравнению номера варианта, каждая ветвь распаковывает
  полезную нагрузку и статически вызывает конкретный метод; форма перепривязки из RFC-004
  (`Type.method = fn[n]`) после перестановки по позиции привязки также участвует в диспетчеризации.
- **Изоляция**: устаревшие ограничения trait (стиль `Drawable: Type = {..}`, без параметров
  обобщения) не проходят через диспетчеризацию вариантов, поведение не меняется.

**Границы v1 (последующие этапы)**: межъединичное слияние вариантов через LTO (§6.5); сопоставление
шаблонов значений Group (зависит от поддержки match с IR для шаблонов вариантов); взаимодействие с
рефлексией; семантика Move в контейнер; поток `Any`/переменных типа и границы лямбб с выводом типов
(резерв — защитные проверки среды выполнения).

## Компромиссы

### Преимущества

1. **Простота**: не нужно ключевое слово `impl`
2. **Гибкость**: реализация методов поддерживается и внутри, и снаружи
3. **Единообразие**: согласованные правила перегрузки
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: нет виртуальных таблиц, сбор типов на этапе компиляции
6. **Типобезопасность**: проверка соответствия интерфейсу на этапе компиляции
7. **Прозрачно для пользователя**: не нужно писать `dyn Animal + 'a`

### Недостатки

1. **Ограничение**: не поддерживаются динамические типы во время выполнения (полностью утиная
   типизация)
2. **Затраты на этапе компиляции**: для каждого интерфейса необходимо сгенерировать варианты
   перечисления и код диспетчеризации match
3. **Набор типов**: должен быть полностью известен на этапе компиляции (в пределах одной
   компилируемой единицы)

### Меры по смягчению

1. **Система плагинов**: поддерживается через проверку соответствия интерфейсу на этапе компиляции
2. **Набор типов**: отслеживание владения, инкрементальное построение — сбор в каждой точке
   `append`/конструирования, а не глобальное сканирование
3. **Между компилируемыми единицами**: объединение наборов вариантов перечисления на этапе линковки,
   общий механизм с мономорфизацией на этапе линковки

## Связь с RFC-009

**Бренды и реализация интерфейсов**:

- Реализация интерфейсов находится на уровне типов, не затрагивает бренды
- Бренды находятся на уровне доказательств заимствования (RFC-009a)
- Обе концепции ортогональны и не влияют друг на друга

**Динамическая диспетчеризация и бренды**:

- Динамическая диспетчеризация использует доказательство реализации, не требует аннотации бренда
- Доказательство реализации генерируется на этапе компиляции, нулевой поиск во время выполнения
- Устраняет сложность `dyn Trait + 'a`

**Владение в гетерогенном контейнере**:

- Помещение в `List(Animal)` — это семантика Move (RFC-009), исходная переменная становится
  недоступной
- Доступ по индексу `animals[0]` возвращает `&AnimalGroup` (сгенерированное компилятором
  перечисление), цепочка проекции брендов: `animals → animals[0] → enum_variant → field`
- Изменяемый доступ реализуется косвенно через методы интерфейса, `&mut AnimalGroup` не
  предоставляется пользователю

## Наследование интерфейсов

Интерфейс может включать другой интерфейс. **Никакого нового синтаксиса** — используется та же
синтаксическая позиция, что и для объявления интерфейса типом:

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                       # Pet наследует Animal — без новых ключевых слов
    name: (self: &Self) -> String,
}

# Когда Dog реализует Pet, он должен удовлетворять всем методам Animal и Pet
Dog: Type = {
    x: Int,
    Pet(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Из Animal
    name: (self: &Dog) -> String = "Buddy",  # Из Pet
}
```

**Принципы дизайна**: Наследование существует, но не поощряется его чрезмерное использование.
Основной способ композиции — множественное инстанцирование интерфейсов
(`Dog: Type = { Animal(Dog), Pet(Dog), ... }`). Тип может напрямую объявить все интерфейсы, которым
он удовлетворяет, без необходимости выражать это через дерево наследования. Наследование интерфейсов
используется только при наличии явной иерархии «is-a».

**Обработка компилятором**: развернуть цепочку наследования. `Pet(Self)` разворачивается в
`{ все методы Animal(Self), name: ... }`. Когда `Dog` объявляет `Pet(Dog)`, выполняется
`Self ↦ Dog`, и компилятор проверяет, что `Dog` одновременно удовлетворяет всем методам
`Animal(Dog)` и `Pet(Dog)`.

**Подстановка Self в наследовании интерфейсов**: в
`Pet: (Self: Type) -> Type = { Animal(Self), ... }` `Self` в `Animal(Self)` — это параметр `Self`
интерфейса `Pet` — его подстановка откладывается. Когда `Dog` реализует `Pet(Dog)`, выполняется
`Self ↦ Dog`, и `Animal(Self)` становится `Animal(Dog)`. Это полностью соответствует семантике
передачи параметров в обобщённых функциях.

## Реализации методов по умолчанию

Интерфейс может предоставлять реализации методов по умолчанию. Реализующий тип может выбрать:
переопределить или унаследовать реализацию по умолчанию:

```yaoxiang
fmt: (Self: Type) -> Type = {
    display: (self: &Self) -> String,                      # Должен быть реализован
    debug: (self: &Self) -> String = self.display(),       # ✅ Ссылается на метод того же интерфейса
    summary: (self: &Self) -> String = f"<{self.name}>",  # ❌ Ошибка компиляции: self.name отсутствует в fmt
}
```

**Ключевое ограничение: интерфейс не может предполагать реализацию вышестоящего уровня.** Метод по
умолчанию может ссылаться только на методы, уже объявленные в том же интерфейсе. Поля конкретного
типа или методы других интерфейсов невидимы для метода по умолчанию — интерфейс является замкнутым
контрактом, он не может «лезть в карман» реализующего типа. Нарушение этого ограничения вызывает
**немедленную ошибку на этапе определения интерфейса**.

**Наследование может предполагать реализацию нижестоящего уровня**: когда интерфейс `Pet(Self)`
наследует `Animal(Self)`, методы по умолчанию `Pet` могут использовать методы, объявленные в
`Animal` — поскольку они унаследованы, гарантируется их наличие.

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                                              # Наследование
    name: (self: &Self) -> String,
    introduce: (self: &Self) -> String = self.name() + " says " + self.speak(),  # ✅ speak приходит из унаследованного Animal
}
```

**Поведение на этапе компиляции**: при реализации типа для каждого метода:

1. Тип предоставляет свой метод → используется метод типа
2. Тип не предоставляет, интерфейс имеет реализацию по умолчанию → компилятор встраивает реализацию
   по умолчанию в тип (нулевые накладные расходы на виртуальные таблицы)
3. Тип не предоставляет, интерфейс не имеет реализации по умолчанию → ошибка компиляции

**Принципы дизайна**: метод по умолчанию аналогичен механизму автоматического вывода `Copy`/`Clone`
— компилятор автоматически генерирует его при необходимости, пользователь может переопределить. Не
вводятся ключевые слова `virtual`/`override`/`super`.

Не вводятся virtual/override                        | 2026-07-03 |
| Ограничения метода по умолчанию    | Проверка на этапе определения интерфейса: может ссылаться только на методы того же интерфейса, не может предполагать реализацию вышестоящего уровня | Интерфейс — замкнутый контракт. Наследование может предполагать реализацию нижестоящего уровня, но интерфейс не может предполагать поля/методы реализующего типа                    | 2026-07-03 |

## Открытые вопросы

- [x] ~~Наследование интерфейсов (интерфейс может наследовать другие интерфейсы)~~ → Поддерживается,
      без нового синтаксиса. `Pet: (Self: Type) -> Type = { Animal(Self), ... }`
- [x] ~~Реализации методов по умолчанию (интерфейс может предоставлять реализации по умолчанию)~~ →
      Поддерживается, аналогично автоматическому выводу Copy. Интерфейс предоставляет тело,
      компилятор встраивает его при необходимости
- [x] ~~Self как неявное магическое ключевое слово~~ → Устранено. `Self` — явный параметр типа,
      интерфейс — это `(Self: Type) -> Type`
- [ ] Продвинутые случаи ограничений интерфейсов (ассоциированные типы, GAT) — ассоциированные типы
      реализуются через параметры обобщённого интерфейса
      (`Container: (Self: Type, T: Type) -> Type`), GAT требует дополнительного проектирования
- [ ] Взаимодействие с замыканиями (замыкания реализуют интерфейсы) — начальная стратегия: замыкания
      не поддерживают прямую реализацию интерфейсов, требуется тип-обёртка. Реализация интерфейсов
      анонимными типами — предмет последующих RFC
