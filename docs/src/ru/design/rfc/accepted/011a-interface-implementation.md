# RFC-011a: Реализация интерфейсов и динамическая диспетчеризация

> **Родительский RFC**:
> [RFC-011: Проект системы обобщений (generics)](../accepted/011-generic-type-system.md)
>
> **Настоящий RFC дополняет и заменяет разделы §2.1-2.4 RFC-011, посвящённые ограничениям
> интерфейсов.**

## Резюме

RFC-011 определяет систему обобщений (generics), но не детализирует механизм реализации интерфейсов.
Настоящий документ дополняет его:

1. **Объявление интерфейса**: интерфейс — это параметризованный тип — `(Self: Type) -> Type`, при
   реализации в него передаётся конкретный тип
2. **Реализация методов**: поддерживаются и внутренние, и внешние объявления
3. **Правила перегрузки**: разные сигнатуры разрешают перегрузку, одинаковые сигнатуры приводят к
   ошибке (перекрытие запрещено)
4. **Значения по умолчанию**: после поля сразу пишется `= value`
5. **Динамическая диспетчеризация**: сбор типов на этапе компиляции + сопоставление интерфейсов, без
   виртуальных таблиц

**Основной дизайн**:

```yaoxiang
# Определение интерфейса (параметризованный тип, Self — явный параметр типа)
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# Определение типа (внутреннее объявление)
Dog: Type = {
    x: Int = 10,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
    speak: (self: &Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка)
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# Гетерогенный контейнер (динамическая диспетчеризация)
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
```

**Соглашение о записи приёмника** (исправление от 30.08.2026, согласовано с семантикой владения из
RFC-009):

- Запись приёмника метода следует семантике сигнатуры: `&Self` = заимствование (соглашение
  интерфейса по умолчанию — вызов метода не потребляет приёмник), `&mut Self` = изменяемое
  заимствование, по значению `Self` = потребление приёмника (Move, RFC-009).
- `Self` в сигнатуре на стороне impl — это псевдоним для типа impl: интерфейс `speak: (self: &Self)`
  сопоставляется и с impl `(self: &Dog)`, и с `(self: &Self)` (после подстановки Self↦тип impl
  становятся полностью эквивалентны, §3).
- Историческая запись приёмника по значению (`(self: Self)`) означала заимствование; в настоящем
  документе она унифицирована в явную форму `&Self`; запись по значению отныне сохраняет только
  семантику «потребления» и больше не используется двояко.

**Устранённая сложность**:

- ❌ Нет ключевого слова `impl`
- ❌ Нет магического ключевого слова `Self` (`Self` — явный параметр типа, ничем не отличается от
  `T`)
- ❌ Нет аннотации `dyn Trait + 'a`
- ❌ Нет виртуальных таблиц (сбор типов на этапе компиляции + обёртка в enum)
- ❌ Нет перекрытия (единые правила перегрузки)

## Мотивация

### Недостатки RFC-011

RFC-011 определяет систему обобщений, но не детализирует следующее:

| Проблема                        | Описание                                   |
| ------------------------------- | ------------------------------------------ |
| Синтаксис объявления интерфейса | Как объявить, что тип реализует интерфейс? |
| Расположение реализации метода  | Внутреннее или внешнее объявление?         |
| Правила перегрузки              | Как обрабатывать одноимённые методы?       |
| Синтаксис значений по умолчанию | Как задать значение поля по умолчанию?     |
| Динамическая диспетчеризация    | Как реализовать гетерогенный контейнер?    |

### Цели дизайна

1. **Простота**: не нужно ключевое слово `impl`
2. **Гибкость**: поддержка как внутренней, так и внешней реализации методов
3. **Единообразие**: согласованные правила перегрузки
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: без виртуальных таблиц, сбор типов на этапе компиляции

### Сравнение с Rust

| Возможность                  | Rust                                  | YaoXiang                              |
| ---------------------------- | ------------------------------------- | ------------------------------------- |
| Объявление интерфейса        | `impl Animal for Dog { ... }`         | `Dog: Type = { Animal(Dog), ... }`    |
| Реализация метода            | В блоке `impl`                        | Внутреннее или внешнее                |
| Перегрузка                   | Не поддерживается                     | Поддерживается (разные сигнатуры)     |
| Значение по умолчанию        | Требуется `#[default]`                | Просто `= value`                      |
| Гетерогенный контейнер       | `Vec<Box<dyn Animal + 'a>>`           | `List(Animal)`                        |
| Динамическая диспетчеризация | Поиск по виртуальной таблице          | Сбор типов на этапе компиляции        |
| Ключевое слово `Self`        | Магическое, неявно квантифицированное | Явный параметр типа, равноправный с T |

## Предложение

### 1. Объявление интерфейса

**Ключевое правило**: интерфейс — это параметризованный тип `(Self: Type) -> Type`, где `Self` —
явный параметр типа, а не магическое ключевое слово. При реализации интерфейс вызывается с передачей
конкретного типа.

```yaoxiang
# Определение интерфейса (полностью соответствует обобщённым типам из RFC-011)
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# Объявление типа, реализующего интерфейс
Dog: Type = {
    x: Int,
    Animal(Dog),  # Инстанцирование интерфейса, Self ↦ Dog
}
```

**Обработка компилятором**:

1. Распознать `Animal(Dog)` как вызов инстанцирования `(Self: Type) -> Type`
2. Выполнить подстановку `Self ↦ Dog`: развернуть `Animal(Dog)` →
   `{ speak: (self: &Dog) -> String }`
3. Проверить, что `Dog` предоставляет все требуемые методы (сопоставление сигнатур)
4. В случае успеха → сгенерировать доказательство реализации
5. В случае неудачи → ошибка компиляции

**Семантика развёртывания**:

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),  # Разворачивается в методы Animal, сохраняя метку источника
}

# Эквивалентно (с сохранённой информацией об источнике)
Dog: Type = {
    x: Int,
    speak: (self: &Dog) -> String,  # Из Animal, Self заменён на Dog
}
```

**Зачем нужна метка источника**:

- Прямое развёртывание теряет информацию об источнике
- Метка источника используется для генерации доказательства реализации
- Во время выполнения по доказательству находится нужный метод

#### 1.1 Параметр типа Self и момент проверки типов

`Self` — это явный параметр типа интерфейса, а не магическое ключевое слово.
`Animal: (Self: Type) -> Type` и `List: (T: Type) -> Type` — сущности одного рода: конструкторы типа
`(Type) -> Type`.

**Момент проверки типов**:

- **При определении интерфейса**: `Self` в `{ speak: (self: &Self) -> String }` — это абстрактный
  параметр типа, выполняется только синтаксическая проверка.
- **В точке инстанцирования**: при `Animal(Dog)` выполняется подстановка `Self ↦ Dog`, после чего
  выполняется полная проверка типов (сопоставление сигнатур, существование методов).

Это устраняет проблему `Self` как неявного магического ключевого слова из RFC-011 — `Self` не
появляется в определении типа, он встречается лишь однажды в списке параметров интерфейса и
полностью равноправен с `T`.

#### 1.2 Пространство имён полей и методов

Имена полей и методов типа разделяют одно общее пространство имён. После развёртывания интерфейса,
если имя метода интерфейса конфликтует с именем поля типа, **компилятор сообщает об ошибке**:

```yaoxiang
Drawable: (Self: Type) -> Type = {
    x: (self: &Self) -> Int,    // Метод с именем x
}

Point: Type = {
    x: Int,                     // Поле тоже с именем x
    Drawable(Point),            // ❌ Ошибка компиляции: Drawable требует метод x, конфликтует с полем x
}
```

Синтаксически невозможно отличить обращение к полю `point.x` от вызова метода `point.x()`. Единое
пространство имён устраняет неоднозначность.

### 2. Реализация методов

**Ключевое правило**: поддерживается как внутреннее, так и внешнее объявление методов.

#### 2.1 Внутреннее объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Реализация метода внутри
}
```

#### 2.2 Внешнее объявление

```yaoxiang
Dog: Type = {
    x: Int,
    Animal(Dog),
}

# Реализация метода снаружи
Dog.speak: (self: &Dog) -> String = "Woof"
```

#### 2.3 Смешанное объявление

```yaoxiang
Dog: Type = {
    x: Int = 10,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Часть методов внутри
}

# Часть методов снаружи
Dog.play: (self: &Dog) -> Void = { ... }
```

**Обработка компилятором**:

1. Собрать все определения (внутренние и внешние)
2. Сгруппировать по сигнатуре (перегрузка)
3. Проверить наличие перекрытия (ошибка)
4. Проверить полноту реализации интерфейса
5. Сгенерировать доказательство реализации

### 3. Перегрузка и перекрытие

**Ключевое правило**:

- Разные сигнатуры → перегрузка → разрешена
- Одинаковые сигнатуры → перекрытие → ошибка

#### 3.1 Перегрузка (разрешена)

```yaoxiang
# Типы параметров различаются, перегрузка разрешена
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"
```

#### 3.2 Перекрытие (запрещено)

```yaoxiang
# Сигнатуры полностью совпадают, перекрытие запрещено
Dog.speak: (self: &Dog) -> String = "Woof"
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ Ошибка: перекрытие не разрешено
```

**Сообщение об ошибке**:

```
Ошибка: повторное определение Dog.speak(self: &Dog) -> String
  --> файл2:5:1
  |
5 | Dog.speak: (self: &Dog) -> String = "Bark"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ повторное определение
  |
  --> файл1:3:1
  |
3 | Dog.speak: (self: &Dog) -> String = "Woof"
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ первое определение
```

#### 3.3 Единые правила

**Внутренние и внешние объявления подчиняются одинаковым правилам перегрузки/перекрытия**:

```yaoxiang
# Внутреннее объявление
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

# Внешнее объявление (перегрузка, разрешена)
Dog.speak: (self: &Dog, volume: Int) -> String = "WOOF"

# Внешнее объявление (перекрытие, запрещено)
Dog.speak: (self: &Dog) -> String = "Bark"  # ❌ Ошибка
```

### 4. Значения по умолчанию

**Ключевое правило**: после поля сразу пишется `= value`, что избавляет от необходимости в
конструкторе.

```yaoxiang
Dog: Type = {
    x: Int = 10,  # Значение по умолчанию
    y: Int = 20,  # Значение по умолчанию
    Animal(Dog),
}
```

**Конструкторы, генерируемые компилятором**:

```yaoxiang
# Все поля имеют значения по умолчанию → генерируется конструктор без аргументов
Dog.new: () -> Dog = { x: 10, y: 20 }

# Часть полей имеет значения по умолчанию → генерируются частично параметризованные конструкторы
Dog.new: (x: Int) -> Dog = { x: x, y: 20 }
Dog.new: (y: Int) -> Dog = { x: 10, y: y }

# Полностью параметризованный конструктор
Dog.new: (x: Int, y: Int) -> Dog = { x: x, y: y }
```

**Внешнее объявление значений по умолчанию**:

```yaoxiang
Dog: Type = {
    x: Int,
    y: Int,
    Animal(Dog),
}

# Внешнее объявление значений по умолчанию
Dog.x: Int = 10
Dog.y: Int = 20
```

Эквивалентно внутреннему объявлению.

#### 5.4 Процесс компиляции

```
1. Разобрать определения типов, собрать объявления инстанцирования интерфейсов (Animal(Dog))
2. Для каждого инстанцирования интерфейса выполнить подстановку Self ↦ ConcreteType
3. Развернуть сигнатуры методов интерфейса, проверить сопоставление сигнатур

5. Сгруппировать по сигнатуре (перегрузка)
6. Проверить перекрытие (ошибка)
7. Проверить полноту реализации интерфейса
8. Сгенерировать доказательство реализации
```

### 6. Динамическая диспетчеризация

**Основной дизайн**: сбор типов на этапе компиляции + сопоставление интерфейсов, без виртуальных
таблиц.

#### 6.1 Гетерогенный контейнер

`Animal` — это `(Self: Type) -> Type`. `List(Animal)` использует неинстанцированный конструктор типа
интерфейса в качестве **экзистенциального типа** (existential): `∃S. Animal(S)` — «существует
некоторый тип S, такой что S реализует Animal(S)».

```yaoxiang
# Определение интерфейса
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

# Определения типов
Dog: Type = {
    x: Int,
    Animal(Dog),
    speak: (self: &Dog) -> String = "Woof",
}

Cat: Type = {
    y: Int,
    Animal(Cat),
    speak: (self: &Cat) -> String = "Meow",
}

# Гетерогенный контейнер — Animal не инстанцирован = экзистенциальный тип
animals: List(Animal) = [Dog.new(), Cat.new()]
animals[0].speak()  # "Woof"
animals[1].speak()  # "Meow"
```

**Семантика владения**: помещение в гетерогенный контейнер имеет семантику Move (RFC-009).
`Dog.new()` перемещается в вариант перечисления `AnimalGroup::Dog`, исходная переменная становится
недоступной.

```yaoxiang
dog = Dog.new()
animals: List(Animal) = [dog]
# dog.speak()  ← ❌ Ошибка компиляции: dog перемещён (move)
```

#### 6.2 Сбор типов на этапе компиляции

**Ключевая стратегия: отслеживание владения с инкрементальным построением.** Вместо сканирования
всех типов, реализующих интерфейс, на этапе компиляции — инкрементальный сбор в **каждой точке
операции владения** для `List(Animal)`:

```yaoxiang
// Точка конструирования
animals: List(Animal) = [Dog.new()]       // AnimalGroup = { Dog(Dog) }

// Точка append
animals.append(Cat.new())                  // Компилятор видит Cat в append → расширяет до { Dog, Cat }
animals.append(Bird.new())                 // Расширяется до { Dog, Cat, Bird }
```

**Обработка компилятором** (инкрементально):

1. При первом конструировании `List(Animal)` → генерируется начальное перечисление (все известные в
   текущей компилируемой единице типы-конструкторы)
2. На каждом `append` / `push` / присваивании по индексу → проверяется, присутствует ли тип значения
   в перечислении; если нет — вариант перечисления расширяется
3. Для итогового перечисления генерируется мономорфизированный `match` для диспетчеризации
4. Между компилируемыми единицами: для объединения вариантов перечисления используется LTO
   (Link-Time Optimization). Когда `Animal` как экзистенциальный тип передаётся через границу
   компилируемой единицы, каждая единица генерирует частичный набор вариантов, а на этапе линковки
   они объединяются в полное перечисление.

**Автоматически генерируемое перечисление**:

```yaoxiang
# Автоматически генерируется компилятором (невидимо для пользователя)
AnimalGroup: Type = {
    Dog(Dog),
    Cat(Cat),
    Bird(Bird),    # ← добавлен расширением из append(Bird.new())
}

# List(Animal) внутри эквивалентен List(AnimalGroup)
```

#### 6.3 Проверка соответствия интерфейсу

**Ключевое наблюдение**: проверка соответствия интерфейсу выполняется на этапе компиляции, даже если
типы поступают из динамически загружаемых плагинов.

```yaoxiang
# Система плагинов
plugin = load_plugin("bird.so")

# Проверка компилятора: возвращаемый тип plugin.create_bird() должен реализовывать Animal
bird: Animal = plugin.create_bird()  # Проверка на этапе компиляции, экзистенциальный тип

# Помещение в гетерогенный контейнер — точка append запускает расширение перечисления
animals: List(Animal) = [Dog.new(), Cat.new()]
animals.append(bird)                 // Компилятор: (1) проверить, что bird реализует Animal (2) расширить перечисление
```

**Обработка компилятором**:

1. Проверить возвращаемый тип аргумента `append`
2. Убедиться, что этот тип реализует целевой интерфейс
3. В случае успеха → расширить перечисление, разрешить помещение
4. В случае неудачи → ошибка компиляции

#### 6.4 Диспетчеризация во время выполнения

**Поток вызова (компиляционный match по перечислению, ImplementationProof стёрт):**

```
animals[0].speak()
  ↓
Сгенерированный компилятором match:
  match animals[0] {
    AnimalGroup.Dog(d) => d.speak(),
    AnimalGroup.Cat(c) => c.speak(),
    AnimalGroup.Bird(b) => b.speak(),
  }
```

**Проекция бренда** (взаимодействие с RFC-009a): привязка шаблона `AnimalGroup.Dog(d)` в match
порождает в дереве брендов дочерний бренд `#animals[0].Dog`, эквивалентный проекции поля
(`#42.field_x`). Цепочка брендов `ReadToken(d)`, созданная при `d.speak()`, имеет вид
`animals → animals[0] → d → ReadToken(d)`, а проверщик заимствований валидирует конфликты через
сопоставление префиксов в дереве брендов.

**Тип, возвращаемый индексацией**: `animals[0]` возвращает `&AnimalGroup` (сгенерированный
компилятором тип перечисления); пользователь не может напрямую получить `&mut Animal`. Изменяемый
доступ реализуется косвенно через методы интерфейса (например, `animals[0].mutate()` разворачивается
внутри в `AnimalGroup::Dog(d) => d.mutate()`).

**Сравнение с виртуальной таблицей**:

|                                       | Виртуальная таблица (Rust)               | Компиляционное перечисление (YaoXiang)                     |
| ------------------------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| Способ поиска                         | Указатель на vtable → указатель на метод | match по перечислению → прямой вызов                       |
| Накладные расходы во время выполнения | Одно косвенное обращение                 | Ветвление (оптимизируется предсказателем переходов CPU)    |
| Генерация на этапе компиляции         | Виртуальная таблица                      | Перечисление + match                                       |
| Аннотации пользователя                | Требуется `dyn Trait + 'a`               | Не требуются                                               |
| ImplementationProof                   | Не применимо                             | Полностью стёрт на этапе компиляции, отсутствует в runtime |

**Преимущества YaoXiang**:

- Не нужны аннотации брендов
- Безопасность типов на этапе компиляции
- Прозрачно для пользователя (не нужно писать `dyn Animal`)
- ImplementationProof — чисто компиляционная концепция, нулевые накладные расходы в runtime

#### 6.5 Ограничения и область применимости

**Внутри компилируемой единицы**: полная поддержка. Отслеживание владения покрывает все точки
`append`/конструирования, перечисление строится инкрементально.

**Между компилируемыми единицами**: объединение вариантов перечисления возлагается на LTO (Link-Time
Optimization). `Animal` как экзистенциальный тип (`∃S. Animal(S)`) передаётся через границу
компилируемой единицы. Каждая единица генерирует частичный набор вариантов, на этапе линковки они
объединяются.

**Не поддерживается**: полностью динамические типы во время выполнения (полностью утиная типизация).
Множество типов должно быть полностью известно на этапе компиляции.

#### 6.6 Заметки по реализации (этап 3, в версии v1 уже введено)

Семантика §6 (гетерогенный контейнер, компиляционная проверка членства, диспетчеризация по
фактическому типу, замкнутое на этапе компиляции множество типов) полностью реализована; на уровне
механизмов конкретизация выглядит следующим образом:

- **Сбор типов**: вместо «инкрементального сбора по точкам операций владения» из §6.2 выполняется
  одноразовый сбор всех реализующих типов во всей компилируемой единице по `ImplementationProof`.
  Внутри одной компилируемой единицы оба подхода семантически эквивалентны (лишние мёртвые варианты
  безвредны); ценность инкрементального сбора проявляется в кросс-единичных сценариях и отнесена к
  v2 (см. ниже).
- **Представление**: компилятор синтезирует тип-вариант `Animal$Group` — это чистый
  IR/байт-код/артефакт runtime (инструкции `CreateVariant`/`VariantTag`/`VariantPayload`, значение
  runtime `RuntimeValue::Enum`); MonoType о нём не знает — на уровне проверки типов пользователь
  видит имя интерфейса. Каждое конкретное значение, попадающее в позицию экзистенциального типа,
  автоматически оборачивается в значение-вариант (единое непрозрачное представление, семантика
  §6.4).
- **Точки обёртывания**: проверщик типов в позициях, где принимается решение «конкретный vs
  экзистенциальный» (аннотированный let/аргумент вызова/return/элемент литерала списка), выполняет
  направленное обследование и выдаёт таблицу принудительных обёртываний с ключом span; генерация IR
  вставляет обёртывания в соответствии с span. Пропущенные обёртывания отлавливаются runtime-стражем
  (проверка `VariantTag`/`VariantPayload` требует, чтобы значение было вариантом именованной группы)
  с громким отказом; в худшем случае — явная ошибка runtime на этапе тестирования, никогда не
  «тихое» порождение некорректных данных.
- **Диспетчеризация**: цепочка переходов по номерам вариантов, в каждой ветке распаковка полезной
  нагрузки и статический вызов конкретного метода; форма перепривязки из RFC-004
  (`Type.method = fn[n]`) после переупорядочения по позиции привязки также участвует в
  диспетчеризации.
- **Изоляция**: унаследованные ограничения trait (форма `Drawable: Type = {..}` без параметров
  обобщений) идут не через диспетчеризацию по вариантам, их поведение не меняется.

**Границы v1 (последующие этапы)**: кросс-единичное слияние вариантов через LTO (§6.5);
сопоставление с образцом значений Group (зависит от IR-поддержки match по образцам вариантов);
взаимодействие с рефлексией; семантика Move при попадании в контейнер; поток через `Any`/переменные
типа и границы лямбд с выводом типов (страховка = runtime-страж).

## Компромиссы

### Преимущества

1. **Простота**: не нужно ключевое слово `impl`
2. **Гибкость**: поддержка как внутренней, так и внешней реализации методов
3. **Единообразие**: согласованные правила перегрузки
4. **Удобство**: лаконичный синтаксис значений по умолчанию
5. **Нулевые накладные расходы**: без виртуальных таблиц, сбор типов на этапе компиляции
6. **Безопасность типов**: соответствие интерфейсу проверяется на этапе компиляции
7. **Прозрачность для пользователя**: не нужно писать `dyn Animal + 'a`

### Недостатки

1. **Ограничение**: динамические типы во время выполнения не поддерживаются (полностью утиная
   типизация)
2. **Накладные расходы на этапе компиляции**: для каждого интерфейса требуется сгенерировать
   варианты перечисления и код match-диспетчеризации
3. **Множество типов**: должно быть полностью известно на этапе компиляции (внутри одной
   компилируемой единицы)

### Меры по смягчению

1. **Система плагинов**: поддерживается через проверку соответствия интерфейсу на этапе компиляции
2. **Множество типов**: отслеживание владения с инкрементальным построением — сбор в каждой точке
   `append`/конструирования, а не глобальное сканирование
3. **Между компилируемыми единицами**: объединение наборов вариантов перечисления на этапе линковки
   — общий механизм с мономорфизацией в момент линковки

## Связь с RFC-009

**Бренд и реализация интерфейса**:

- Реализация интерфейса находится на уровне типов и не затрагивает бренды
- Бренды — на уровне доказательства заимствования (RFC-009a)
- Эти два аспекта ортогональны и не влияют друг на друга

**Динамическая диспетчеризация и бренды**:

- Динамическая диспетчеризация использует доказательство реализации, аннотации бренда не нужны
- Доказательство реализации генерируется на этапе компиляции, поиск в runtime отсутствует
- Устраняется сложность, связанная с `dyn Trait + 'a`

**Владение в гетерогенном контейнере**:

- Помещение в `List(Animal)` имеет семантику Move (RFC-009), после чего исходная переменная
  недоступна
- Индексация `animals[0]` возвращает `&AnimalGroup` (сгенерированный компилятором enum), цепочка
  проекции бренда: `animals → animals[0] → вариант_enum → поле`
- Изменяемый доступ реализуется косвенно через методы интерфейса; `&mut AnimalGroup` не
  предоставляется пользователю

## Наследование интерфейсов

Интерфейс может включать другой интерфейс. **Новый синтаксис не вводится** — используется та же
синтаксическая позиция, что и при объявлении типа, реализующего интерфейс:

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                       # Pet наследует Animal — никаких новых ключевых слов
    name: (self: &Self) -> String,
}

# Когда Dog реализует Pet, он должен одновременно удовлетворять всем методам Animal и Pet
Dog: Type = {
    x: Int,
    Pet(Dog),
    speak: (self: &Dog) -> String = "Woof",  # Из Animal
    name: (self: &Dog) -> String = "Buddy",  # Из Pet
}
```

**Принцип дизайна:** Наследование существует, но его чрезмерное использование не поощряется.
Основной способ композиции — множественное инстанцирование интерфейсов
(`Dog: Type = { Animal(Dog), Pet(Dog), ... }`). Тип может напрямую объявить все интерфейсы, которым
он удовлетворяет, без необходимости выражать это через дерево наследования. Наследование интерфейсов
используется только при наличии явной иерархии «is-a».

**Обработка компилятором:** разворачивается цепочка наследования. `Pet(Self)` разворачивается в
`{ все методы из Animal(Self), name: ... }`. Когда `Dog` объявляет `Pet(Dog)`, выполняется
`Self ↦ Dog`, и компилятор проверяет, что `Dog` одновременно удовлетворяет всем методам
`Animal(Dog)` и `Pet(Dog)`.

**Подстановка Self при наследовании интерфейсов**: в
`Pet: (Self: Type) -> Type = { Animal(Self), ... }` `Self` в `Animal(Self)` — это параметр `Self`
интерфейса `Pet`; его подстановка откладывается. Когда `Dog` реализует `Pet(Dog)`, выполняется
`Self ↦ Dog`, и `Animal(Self)` становится `Animal(Dog)`. Это полностью соответствует семантике
передачи параметров в обобщённых функциях.

## Реализация методов по умолчанию

Интерфейс может предоставлять реализации методов по умолчанию. Реализующий тип может выбрать
переопределение или наследование реализации по умолчанию:

```yaoxiang
fmt: (Self: Type) -> Type = {
    display: (self: &Self) -> String,                      # Должен быть реализован
    debug: (self: &Self) -> String = self.display(),       # ✅ Ссылается на метод того же интерфейса
    summary: (self: &Self) -> String = f"<{self.name}>",  # ❌ Ошибка компиляции: self.name не входит в fmt
}
```

**Ключевое ограничение: интерфейс не может полагаться на реализацию вышестоящего уровня.** Метод по
умолчанию может ссылаться только на методы, объявленные в том же интерфейсе. Поля конкретного типа
или методы других интерфейсов недоступны методу по умолчанию — интерфейс является замкнутым
контрактом и не может «лезть в карман» к реализующему типу. Нарушение этого ограничения приводит к
**немедленной ошибке на этапе определения интерфейса**.

**Наследование может полагаться на реализацию нижестоящего уровня:** когда интерфейс `Pet(Self)`
наследует `Animal(Self)`, метод по умолчанию в `Pet` может использовать методы, объявленные в
`Animal` — поскольку они унаследованы, их наличие гарантировано.

```yaoxiang
Animal: (Self: Type) -> Type = {
    speak: (self: &Self) -> String,
}

Pet: (Self: Type) -> Type = {
    Animal(Self),                                              # Наследование
    name: (self: &Self) -> String,
    introduce: (self: &Self) -> String = self.name() + " says " + self.speak(),  # ✅ speak приходит из унаследованного Animal
}
```

**Поведение на этапе компиляции:** когда тип реализует интерфейс, для каждого метода:

1. Тип предоставил метод → используется метод типа
2. Тип не предоставил, интерфейс имеет реализацию по умолчанию → компилятор встраивает реализацию по
   умолчанию в тип (нулевые накладные расходы, без виртуальной таблицы)
3. Тип не предоставил, у интерфейса нет реализации по умолчанию → ошибка компиляции

**Принцип дизайна:** методы по умолчанию аналогичны механизму автоматического вывода `Copy`/`Clone`
— компилятор генерирует их автоматически при необходимости, пользователь может их переопределить.
Ключевые слова `virtual`/`override`/`super` не вводятся.

## Открытые вопросы

- [x] ~~Наследование интерфейсов (интерфейс может наследовать другие интерфейсы)~~ → Поддерживается,
      без нового синтаксиса. `Pet: (Self: Type) -> Type = { Animal(Self), ... }`
- [x] ~~Реализация методов по умолчанию (интерфейс может предоставлять реализацию по умолчанию)~~ →
      Поддерживается, аналогично автоматическому выводу Copy. Интерфейс предоставляет тело,
      компилятор встраивает его при необходимости
- [x] ~~`Self` как неявное магическое ключевое слово~~ → Устранено. `Self` — явный параметр типа,
      интерфейс — это `(Self: Type) -> Type`
- [ ] Продвинутое использование ограничений интерфейсов (ассоциированные типы, GAT) —
      ассоциированные типы реализуются через параметры обобщённого интерфейса
      (`Container: (Self: Type, T: Type) -> Type`), GAT требует дополнительной проработки
- [ ] Взаимодействие с замыканиями (замыкания, реализующие интерфейс) — начальная стратегия:
      замыкания не поддерживают прямую реализацию интерфейсов, требуется тип-обёртка. Реализация
      интерфейсов анонимными типами — предмет последующих RFC
