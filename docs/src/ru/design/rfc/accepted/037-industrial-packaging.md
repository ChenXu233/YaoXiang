# RFC-037: Промышленная схема дистрибуции — упаковка компилятора/тулчейна на основе cargo-dist

> Данный RFC дополняет
> [RFC-014b: Система сборки и бинарная дистрибуция](../review/014b-build-system.md). RFC-014b
> определяет, как **менеджер пакетов YaoXiang** собирает и распространяет сторонние пакеты; данный
> RFC определяет, как **сам компилятор/тулчейн YaoXiang** упаковывается и распространяется.

## Резюме

Использовать `cargo-dist` (инструмент бинарной дистрибуции из экосистемы Rust) для
кроссплатформенной оркестрации сборки, а собственные скрипты — для структуры релизного пакета. Два
ключевых обязательства: релизный пакет **физически содержит каталог исходников стандартной
библиотеки** (пользователь читает его напрямую, как каталог `Lib/` в Python), а динамически
линкуемая общая библиотека Z3 поставляется вместе с пакетом на всех платформах. Модель команд —
**разделение «парадная дверь» / движок**: повседневная команда `yx` (маленькая парадная дверь со
встроенным управлением версиями — аналог rustup / Go GOTOOLCHAIN), движок `yaoxiang-rs` (текущий
монолит `yaoxiang` переименовывается), что позволяет избежать постфактум «латания» экосистемы
скриптами nvm/pdm, как это происходит в Python/Node. Двухуровневая установка: стандартный канал
выравнивается с Go/Zig — **релизный пакет и есть продукт**, распаковка + PATH; дружелюбный канал —
установка одной командой (Linux `apt` / `curl | sh`, Windows `irm | iex` / мастер Inno exe). Решает
проблемы отсутствия `libz3.dll`, невидимости стандартной библиотеки для пользователя, повторного
сопровождения CI-скриптов.

## Мотивация

### Зачем нужна эта возможность?

Пользователь, скачивающий YaoXiang, должен иметь возможность **сразу начать работу** без каких-либо
дополнительных шагов; стандартная библиотека должна быть **напрямую читаемой** для пользователя, а
не «чёрным ящиком», спрятанным в бинарнике.

### Текущие проблемы

#### Проблема 1: Пользователи Windows не могут запустить после скачивания

Текущий Release загружает только `yaoxiang.exe`, но `libz3.dll` не упаковывается. Двойной клик в
Windows приводит к ошибке:

```
The code execution cannot proceed because libz3.dll was not found.
```

Это **блокирующий баг** — пользователь не может пройти даже первый шаг.

#### Проблема 2: Артефакт Release содержит только одиночный exe, стандартная библиотека невидима для пользователя

Текущее состояние — тройной разрыв:

- Артефакт Release содержит только «голый» бинарник, стандартная библиотека не поставляется с
  релизом
- Цепочка поиска интерфейсных файлов в LSP фактически разорвана: при вызове
  `find_std_interface_file` не передаётся каталог проекта (проверяется только глобальный
  `~/.yaoxiang/std/`, который никто не заполняет); `package init` записывает в `.yaoxiang/std`,
  которого нет в цепочке поиска
- Исходники стандартной библиотеки (слой `.yx`) и представление интерфейсов (нативный слой) —
  полностью чёрный ящик для пользователя

Индустриальный подход: пользователь, как при чтении `Lib/` в Python, просто открывает каталог
стандартной библиотеки и читает исходники — **физическое наличие каталога std в релизном пакете —
жёсткое требование данного решения** (решение принято).

#### Проблема 3: Повторное сопровождение CI-скриптов вручную

В настоящее время сопровождается несколько конвейеров сборки:

| Файл                      | Назначение                | Строк          |
| ------------------------- | ------------------------- | -------------- |
| `_build-platforms.yml`    | Кроссплатформенная сборка | ~255 строк     |
| `release.yml`             | Релиз версии              | ~189 строк     |
| `nightly.yml`             | Ежедневная сборка         | ~173 строки    |
| `scripts/build/setup.iss` | Установщик Inno Setup     | ~250 строк     |
| **Итого**                 |                           | **~870 строк** |

Большая часть — повторяющиеся действия (установка Rust → кэш → сборка → переименование → загрузка),
написанные отдельно для каждой платформы.

#### Проблема 4: Номер версии Inno Setup захардкожен

В `setup.iss` параметр `MyAppVersion` зашит как `0.7.0`, при сборке подменяется через `sed`. Рано
или поздно это приведёт к провалу.

#### Проблема 5: Размытие границ с RFC-014b

RFC-014b определяет «механизм сборки и дистрибуции пакетов YaoXiang» (конфигурации `[build]` и
`[binaries]` в `yaoxiang.toml`), но **не покрывает вопрос «как публикуется сам компилятор
YaoXiang»**. Данный RFC восполняет этот пробел.

## Предложение

### Основной дизайн

cargo-dist берёт на себя только **слой оркестрации сборки**; структура пакета и установщики —
полностью свои. Разделение ответственности:

```
Ответственность cargo-dist (слой оркестрации сборки):
  ├── Кроссплатформенная компиляция (5 таргетов)
  └── Генерация архивов и контрольных сумм
  (Родные установщики и npm-обёртки отброшены — их предположение о плоском бинарнике конфликтует со структурой bin/+lib/)

build.rs продолжает отвечать за:
  └── Загрузку/линковку Z3 (динамически на всех платформах + rpath)

Собственные скрипты YaoXiang:
  ├── package-dist.sh — реорганизация структуры пакета (bin/ + lib/), включение общей библиотеки,
  │   заполнение каталога std (предгенерируемое представление интерфейсов + исходники слоя .yx из репозитория), пересчёт контрольных сумм
  └── Inno Setup — мастер установки для Windows (существующий актив; развёртывает полную структуру каталогов)

Модель команд (разделение «парадная дверь» / движок):
  ├── yx — парадная дверь (новый маленький крейт): разбор версии + диспетчеризация; зарезервированные глаголы только toolchain/self, остальные прозрачно транслируются
  └── yaoxiang-rs — движок (текущий монолит yaoxiang переименовывается): подкоманды компиляции/запуска/управления пакетами/fmt/lsp

Способы установки (двухуровневые):
  ├── Стандартный канал (модель Go/Zig): релизный пакет и есть продукт, распаковка + PATH
  └── Дружелюбный канал (модель Rust): установка одной командой + управление версиями (встроено в парадную дверь yx)
      ├── Linux: apt (собственный deb-репозиторий, системная плоская установка) / curl … | sh (установка всего пакета одной командой)
      ├── Windows: irm … | iex (установка всего пакета одной командой) / мастер Inno Setup (существующий актив, системная плоская установка)
      └── macOS: curl … | sh (brew оставлен на усмотрение сообщества homebrew-core)
```

### Структура каталогов релиза (решение принято: физическое наличие исходников стандартной библиотеки)

Пользователь должен иметь возможность, как при чтении `Lib/` в Python, напрямую читать стандартную
библиотеку — наличие каталога std в релизном пакете — жёсткое требование, а не деталь упаковки. То
же относится к Z3: как к внешней системе, каталожная дистрибуция общей библиотеки — её естественная
форма; засовывание `.so` внутрь exe и размещение снаружи при динамической линковке эквивалентны по
критерию «всё равно идёт в комплекте с релизом», причём второй вариант сохраняет заменяемость.

Релизный пакет для каждой платформы реорганизуется `package-dist.sh` после сборки через cargo-dist:

```
yaoxiang-{version}-{target}.tar.gz / .zip     (переносимый: после распаковки bin/ сразу работает)
├── bin/
│   ├── yx                            # Парадная дверь (или yx.exe)
│   ├── yaoxiang-rs                   # Движок (или yaoxiang-rs.exe)
│   └── libz3.so / libz3.dylib / libz3.dll
├── lib/
│   └── yaoxiang/
│       └── std/                      # Пользователь может читать напрямую (модель Python Lib/)
│           ├── io.yx                 # нативный модуль: предгенерируемое представление интерфейса из репозитория
│           ├── math.yx
│           ├── test.yx               # слой .yx: реальные исходники из репозитория копируются как есть
│           └── ...
├── README.md
└── LICENSE
```

Установка = распаковка в любой каталог + добавление `bin/` в PATH (модель Go `/usr/local/go/bin`;
распаковка в `~/.yaoxiang/` — типичный выбор). На Windows мастер Inno Setup делает то же самое (по
умолчанию Program Files). При переносимой распаковке у парадной двери `yx` нет состояния
`~/.yaoxiang`, происходит откат на соседний `yaoxiang-rs` — поведение совпадает с управляемой
установкой; rpath движка и относительный поиск std от exe не меняются из-за наличия парадной двери.

### Поддержка платформ

| Платформа      | target triple               | Описание              |
| -------------- | --------------------------- | --------------------- |
| Linux x86_64   | `x86_64-unknown-linux-gnu`  | Основная платформа    |
| Linux ARM64    | `aarch64-unknown-linux-gnu` | Кросс-компиляция в CI |
| macOS x86_64   | `x86_64-apple-darwin`       | Intel Mac             |
| macOS ARM64    | `aarch64-apple-darwin`      | Apple Silicon         |
| Windows x86_64 | `x86_64-pc-windows-msvc`    | Основная платформа    |

Всего 5 таргетов. Windows ARM64 временно не поддерживается (Z3 не предоставляет официальных
прекомпилированных пакетов для ARM64).

### Стратегия дистрибуции Z3

**Динамическая линковка на всех платформах** (решение подтверждено):

| Платформа | Изменение                           | Артефакт        |
| --------- | ----------------------------------- | --------------- |
| Linux     | **Была статической → динамическая** | `libz3.so`      |
| macOS     | **Была статической → динамическая** | `libz3.dylib`   |
| Windows   | Без изменений                       | `libz3.dll`     |
| wasm32    | Без изменений (статическая)         | Встроенный `.a` |

Обоснование:

- **Согласованность** — единое поведение на трёх платформах, больше никаких особых случаев
- **Это внешняя библиотека, её и нужно распространять как общую.** Python
  (`python3.dll`+`DLLs/lib*.dll`), Node (`node`+`lib/`) делают именно так
- **Пользователю не нужно ждать новой версии компилятора для обновления Z3** — достаточно заменить
  `.so`/`.dylib`/`.dll`
- **Меньший размер бинарника** — Z3 немаленькая, статическая линковка раздула бы exe на несколько
  мегабайт

У динамической линковки есть **необходимое дополнение**: динамический линковщик на Linux/macOS по
умолчанию не ищет каталог с бинарником, необходимо инжектировать rpath, иначе «распакуй и работай»
не работает (Windows по умолчанию ищет каталог exe, ничего не требуется). Соответствующее изменение
`build.rs`:

```rust
// Унифицированная динамическая линковка + rpath
fn link_z3(z3_dir: &Path) {
    let target_os = env::var("CARGO_CFG_TARGET_OS").unwrap();
    // Раскладка пакета Z3 неоднородна, двойной поиск в lib/bin
    println!("cargo:rustc-link-search=native={}", lib_dir.display());
    // RFC-037: динамическая линковка на всех платформах. Общая библиотека поставляется с bin/ релизного пакета, пользователь может заменить её для обновления Z3
    if target_os == "windows" {
        // MSVC import lib именуется как libz3.lib
        println!("cargo:rustc-link-lib=libz3");
    } else {
        println!("cargo:rustc-link-lib=z3");
        // Динамический линковщик по умолчанию не ищет каталог с бинарником, необходимо инжектировать rpath, чтобы «распакуй и работай» работало
        // (в релизном пакете exe и libz3 находятся в одном bin/; Windows по умолчанию ищет каталог exe, ничего не требуется)
        match target_os.as_str() {
            "linux" => println!("cargo:rustc-link-arg=-Wl,-rpath,$ORIGIN"),
            "macos" => println!("cargo:rustc-link-arg=-Wl,-rpath,@loader_path"),
            _ => {}
        }
        let cxx = if target_os == "macos" {
            "c++".to_string()
        } else {
            env::var("CXXSTDLIB").unwrap_or_else(|_| "stdc++".into())
        };
        println!("cargo:rustc-link-lib={}", cxx);
    }
}
```

**«Полная статическая линковка на всех платформах» не рассматривается как цель.** Это не устранение
особого случая, а неправильный способ устранения обоснованного случая. Общая библиотека — нормальный
способ распространения внешней библиотеки.

### Поддержка установщиков

Сравнение способов распространения основных языковых тулчейнов (исследование 2026-09):

| Язык     | Официальный релиз             | Официальный способ установки                              | Кто поддерживает установщик           |
| -------- | ----------------------------- | --------------------------------------------------------- | ------------------------------------- |
| Go       | `go/{bin,src,pkg}` tarball    | Официальная документация = «скачать → распаковать → PATH» | Нет (brew/apt от сообщества)          |
| Zig      | `zig/{bin,lib/std}` tarball   | То же, официальных скриптов установки нет                 | Нет (сообщество homebrew-core)        |
| Node     | `{bin,lib,include}` tarball   | tar + официальный pkg/msi                                 | Команда пишет сама                    |
| Rust     | Многокомпонентный tarball     | rustup                                                    | Команда пишет сама                    |
| Crystal  | `{bin,src,embedded}` tarball  | deb/rpm/tar                                               | Команда + сообщество brew             |
| Deno/Bun | Одиночный бинарник zip        | Официальный curl-скрипт                                   | Команда пишет сама (скрипт минимален) |
| Gleam    | Одиночный бинарник cargo-dist | Скрипт, сгенерированный cargo-dist                        | cargo-dist                            |

Три закономерности:

- **Ни одна компания, распространяющая многофайловые тулчейны, не использует сторонние генераторы
  для установщиков** — установщики cargo-dist заточены под одиночный бинарник (Gleam может их
  использовать именно потому, что это одиночный бинарник Rust без внешних зависимостей)
- Простейшая модель — **«релизный пакет и есть продукт» в стиле Go/Zig**: официальная инструкция по
  установке — распаковка + PATH, ноль кода установщика; релизный пакет содержит читаемые исходники
  std (Go `src/`, Zig `lib/std/`, Crystal `src/`) — это норма
- Те, кому нужна установка curl-скриптом (Deno/Bun/rustup), пишут **скрипты сами** и они почти не
  развиваются; формулы brew всегда поддерживаются сообществом в homebrew-core, языковые команды не
  создают собственные tap (команда Crystal явно говорит, что формула — дело сообщества)

YaoXiang применяет двухуровневую модель:

| Канал                                                     | Слой        | Статус | Описание                                                                                                                             |
| --------------------------------------------------------- | ----------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| zip / tar.gz                                              | Стандарт    | ✅     | Распакуй и работай (rpath + общая библиотека в том же каталоге), extract + PATH — официальная инструкция                             |
| `yx` (парадная дверь со встроенным управлением версиями)  | Дружелюбный | ✅     | Аналог rustup / Go GOTOOLCHAIN: установка/переключение/обновление нескольких версий + project pin                                    |
| `curl ... \| sh` (install.sh)                             | Дружелюбный | ✅     | Linux / macOS: скачивает реорганизованный пакет в `versions/`, размещает `bin/yx` в корне установки и записывает версию по умолчанию |
| `irm ... \| iex` (install.ps1)                            | Дружелюбный | ✅     | Windows: та же логика                                                                                                                |
| `apt install yaoxiang`                                    | Дружелюбный | ✅     | `.deb` (amd64/arm64) + статический apt-репозиторий на GitHub Pages; системная плоская установка, `apt upgrade` отслеживает версии    |
| Inno Setup exe                                            | Дружелюбный | ✅     | Мастер для Windows (существующий актив), системная плоская установка, развёртывает полную структуру bin/+lib/                        |
| winget / `.rpm` / homebrew-core / npm                     | —           | ⏸      | Возможные доработки: winget и brew-core поддерживаются сообществом, rpm и deb однородны                                              |
| MSI / родной установщик cargo-dist / собственный brew tap | —           | ❌     | См. «Альтернативы»                                                                                                                   |

**Дружелюбный канал берёт пример с Rust, управление версиями встроено в парадную дверь.**
Декомпозиция Rust — «загрузочный скрипт (sh.rustup.rs) → rustup → пакеты тулчейна», rustup с самого
начала взял на себя управление несколькими версиями, переключение, обновление; официальные
установщики Python/Node не сделали этот слой, экосистема постфактум обросла pyenv/nvm/pdm каждый
по-своему. YaoXiang применяет **разделение «парадная дверь» / движок** (Go с `go` в качестве
парадной двери + GOTOOLCHAIN, rustup с прокси-диспетчеризацией — изоморфная форма): повседневная
команда — `yx`, движок — `yaoxiang-rs` —

```
~/.yaoxiang/
├── bin/yx                  # Парадная дверь: маленький бинарник, разбор версии + диспетчеризация (project pin > default > соседний движок)
├── settings.toml           # Версия по умолчанию, зеркала
└── versions/               # Версия — концепция первого уровня; <ver>/ — корневой каталог распаковки релиза этой версии
    └── 0.7.14/
        ├── bin/
        │   ├── yaoxiang-rs      # Движок: подкоманды компиляции/запуска/управления пакетами/fmt/lsp
        │   └── libz3.so
        └── lib/yaoxiang/std/
```

- Корень установки `~/.yaoxiang/` соответствует общепринятым конвенциям (pyenv `~/.pyenv`, nvm
  `~/.nvm`, deno `~/.deno`, bun `~/.bun`, volta `~/.volta` — у всех один корень; rustup с
  `~/.cargo`+`~/.rustup` — историческое наследие того, что cargo существовал до rustup, не
  копируем), и `~/.yaoxiang` уже является существующим пространством имён в кодовой базе (глобальный
  слот отката std); поддерживает переменную окружения `YAOXIANG_HOME` для переопределения (прецедент
  RUSTUP_HOME / DENO_INSTALL, для CI и контейнеров); на Windows — `%USERPROFILE%\.yaoxiang`
- **Каталог версии = корневой каталог распаковки релиза**: `versions/<ver>/` полностью изоморфен
  переносимой распаковке и дереву установки deb — установка версии = распаковка релиза — нулевое
  расхождение структур между тремя каналами
- Командный интерфейс (аналог rustup): `yx toolchain install / default / update / list / uninstall`,
  включая `yx self update`; остальные глаголы прозрачно транслируются движку
- **Блокировка версий — структурная гарантия**: fmt и другие инструменты эволюционируют вместе с
  синтаксисом одной версии (старый fmt не понимает новый синтаксис), разбор версии выполняется один
  раз у парадной двери, переключение атомарно — не существует комбинации «новый движок со старым
  fmt»; в будущем, если выделить fmt/LSP в отдельные бинарники, они тоже окажутся в `bin/` той же
  версии
- Project-level pin: `yx-toolchain.toml` (прецедент rust-toolchain.toml, следует имени команды; не в
  `yaoxiang.toml` — манифест пакета не должен навязывать версию тулчейна пользователям библиотеки)
- Загрузочный вход (`curl | sh` / `irm | iex`) устанавливает весь последний stable пакет за раз:
  распаковка в `versions/`, размещение `bin/yx` в корне установки, запись версии по умолчанию в
  `settings.toml` (эквивалентная конвергенция декомпозиции «загрузочный скрипт устанавливает
  менеджер» в rustup — парадная дверь и движок в одном пакете, не нужны два шага)
- Зеркала настраиваются (settings.toml), продолжая учёт пользователей внутри Китая (та же проблема с
  сетью, что и при загрузке Z3)
- **Управление версиями не нарушает инвариант самодостаточности**: каждая версия — это полное дерево
  релиза, rpath и относительный поиск std от exe самосогласованы внутри дерева, парадная дверь
  только диспетчеризует, не меняя структуру

`.deb` и Inno — **каналы системной плоской установки** (root / Program Files, одна версия,
обновляется через `apt upgrade` / панель управления), для серверов, CI, чисто новичковых сценариев;
сосуществование с менеджером — через порядок PATH (прецедент: rustc из apt и rustup сосуществуют).
Все каналы используют одно и то же дерево продуктов.

Раскладка `.deb` повторно использует то же дерево каталогов: `/usr/lib/yaoxiang/` (полное дерево
релиза: `bin/{yx,yaoxiang-rs,libz3.so}` + `lib/yaoxiang/std/`) + символическая ссылка `/usr/bin/yx`
на `/usr/lib/yaoxiang/bin/yx` — `$ORIGIN` вычисляется по **реальному пути** после резолва ссылки,
попадает в тот же каталог `libz3.so`, изоморфно структуре распакованного пакета. Полное название
бренда остаётся в имени пакета и названии продукта (`apt install yaoxiang`, название продукта Inno —
YaoXiang), командный интерфейс унифицирован `yx` — как в Go: имя пакета `golang-go`, команда `go`.
Репозиторий apt статически хостится на GitHub Pages (метаданные Packages/Release/InRelease подписаны
GPG, публикуются релизным CI); в перспективе — заявка на включение в официальные репозитории
Debian/Ubuntu (долгий цикл, отстающая версия, не основной путь).

### Каталог стандартной библиотеки

Содержимое `lib/yaoxiang/std/` полностью берётся из статических файлов репозитория, упаковка —
**чистое копирование**, без точек входа в runtime-генерацию:

| Слой                                      | Источник                                                                              | Природа                                                          |
| ----------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Нативные модули (io/math/…)               | Предгенерируемые представления интерфейсов из `src/std/interfaces/*.yx` в репозитории | Представление сигнатур интерфейсов (реализация внутри бинарника) |
| Модули слоя .yx (test/… в процессе роста) | Исходники `src/std/*.yx` копируются как есть                                          | Реальные исходники                                               |

Предгенерируемые представления выводятся из `StdModule::exports()` (`generate_all_interfaces()` в
`src/std/gen_interfaces.rs`), **runtime-подкоманды генерации не предусматриваются** (решение
2026-09-10: после того как упаковка сформирована, подкоманды — лишняя поверхность интерфейса).
Синхронизация по модели «генерируемые артефакты в репозитории + тестовый шлагбаум» (аналогично
таблице кодировок в RFC-013): `test_committed_interface_files_match_generation` побайтово сравнивает
предгенерированные файлы с текущей генерацией, расхождение — красный; лечение через точку входа
bless `cargo test update_committed_interface_files -- --ignored`. Логика генерации зависит от
внутренней реализации `StdModule` в крейте и не может быть опущена в build.rs, поэтому шлагбаум
стоит на уровне тестов, а не сборки.

**Цепочка поиска в runtime** — добавление в `find_std_interface_file` ещё одного уровня,
относительного к exe:

1. `<project>/.yaoxiang/vendor/std/<name>.yx` (переопределение проектом, текущее поведение)
2. **`<exe_dir>/../lib/yaoxiang/std/<name>.yx` (новое)**: переносимая распаковка, управляемая
   установка (`versions/<ver>/`), deb-плоская установка — все попадают сюда
3. `~/.yaoxiang/std/<name>.yx` (глобальный откат, оставлен как слот ручного переопределения)

В текущем состоянии эта цепочка фактически разорвана (вызов LSP не передаёт каталог проекта,
`package init` пишет в `.yaoxiang/std`, которого нет в цепочке), в рамках данной работы это починим
заодно, а вывод `package init` унифицируем с `.yaoxiang/vendor/std` (соответствует каталогу vendor
менеджера пакетов).

**Компилирующий авторитет не меняется**: слой `.yx` по-прежнему встраивается через `include_str!`
(инвариант RFC-036 «std жёстко привязан к версии бинарника» сохраняется). Каталог релиза
предназначен для **читаемого представления + источника для LSP-разрешения**, а не для ввода
компилятора — ручное изменение `.yx` в каталоге релиза не будет принято компилятором (открыть
семантику в стиле Python «правка `Lib/` вступает в силу» — см. открытые вопросы).

### Сборка Wasm

**Остаётся отдельной, не переносится в cargo-dist.**

cargo-dist занимается «доставкой компилятора пользователю», wasm — «встраиваемый онлайн-playground в
сайт документации» — это совершенно разные продукты.

| Аспект            | Подход                                                        |
| ----------------- | ------------------------------------------------------------- |
| Инструмент сборки | Остаётся `wasm-pack build`                                    |
| CI workflow       | Сохраняется отдельный job `_build-wasm.yml`                   |
| Триггер           | Параллельный независимый job в том же tag push, что и release |
| Цель публикации   | `docs/public/wasm/` → GitHub Pages                            |

### Публикация в npm

| Пакет                  | Содержимое                              | Статус                                                                                                                                                                                                                                                       |
| ---------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `@yaoxiang/cli`        | Обёртка для скачивания релизного пакета | Отложено: npm-обёртки cargo-dist также основаны на предположении плоского артефакта, отбрасываются вместе с установщиками; если нужен канал npm, пишется своя обёртка (скачивает и распаковывает реорганизованный пакет, та же логика, что и при распаковке) |
| `@yaoxiang/playground` | wasm-библиотека (JS + .wasm)            | Опционально, сейчас только docs                                                                                                                                                                                                                              |

Между собой не конфликтуют, имена не пересекаются.

### Интеграция с существующим релизным процессом

Текущий `release.yml`: push main → check-version (пропускает, только если тег `v{version}` не
существует) → build / build-wasm / security / test → release job (создаёт и пушит тег +
`generate-commit-list.mjs` генерирует тело с @mentions + загрузка артефактов).

Конвейер, сгенерированный cargo-dist, запускается тегом,自带 announce/publish, и не содержит шлюзов
fmt/clippy/test/audit, формат release notes не может вместить changelog из merge-коммитов. **Прямая
полная замена разобьёт существующий релизный ритуал** (PR → CI всё зелёное → bump → merge-коммит как
changelog).

Принцип интеграции: **триггер и шлюзы остаются как есть, сборка передаётся `cargo dist build`,
публикация — как есть.**

1. Job-ы check-version / security / test остаются (триггер — push main, шлюз перед созданием тега)
2. После прохождения всех job, release job создаёт и пушит тег `v{version}` (как сейчас)
3. Push тега триггерит новый `dist-release.yml`: plan job от dist вычисляет матрицу runner/системных
   зависимостей → `cargo dist build` (5 таргетов) → `package-dist.sh` реорганизует для каждого
   таргета → job Inno Setup (берёт реорганизованный Windows-пакет, собирает мастер, версия
   инжектируется через `/DMyAppVersion=`, без повторной компиляции) → `_build-wasm.yml`
   (параллельный job)
4. Job publish: `generate-commit-list.mjs` генерирует тело (текущий скрипт переиспользуется) →
   дополнительно загружает реорганизованные пакеты + `.sha256` + `.deb` + wasm + Setup exe;
   отдельный job `publish-apt` публикует метаданные apt-репозитория на GitHub Pages (если
   `secrets.APT_GPG_KEY` не настроен — автоматически пропускается, не влияя на остальные каналы)

### Nightly-релизы

cargo-dist не имеет встроенной поддержки nightly
([axodotdev#1143](https://github.com/axodotdev/cargo-dist/issues/1143), всё ещё открытый feature
request).

Сохраняем текущую схему cron + перезапись тега, часть сборки меняется с `_build-platforms.yml` на
`cargo dist build` — это по сути одна cargo-команда, можно вызвать напрямую в nightly.yml. Без
переиспользования workflow (предполагаемое `uses: ./release.yml` нереализуемо: переиспользуемому
нужен триггер `workflow_call`, а workflow cargo-dist привязан к тегу и связывает сборку с
публикацией):

```yaml
# nightly.yml (после миграции)
on:
  schedule:
    - cron: '17 22 * * *'
jobs:
  build: # cargo dist build + package-dist.sh (тот же набор, что и для стабильной версии)
  publish: # Сохраняется: создание/перемещение nightly тега → перезапись GitHub Pre-release
```

### Конфигурация cargo-dist (уже внесена в dist-workspace.toml)

```toml
[workspace]
members = ["cargo:.", "cargo:tools/yx"]

# Config for 'dist'
[dist]
# Версия dist зафиксирована (синтаксис SemVer из Cargo.toml)
cargo-dist-version = "0.32.0"
ci = "github"
# Установщики все свои, cargo-dist только собирает + архивы + контрольные суммы
installers = []
targets = ["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "x86_64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
# Сгенерированный workflow был намеренно изменён (реорганизация package-dist.sh + собственный этап публикации, RFC-037),
# не отказываемся от сборки из-за расхождения с шаблоном generate
allow-dirty = ["ci"]
```

Выше — фактическая конфигурация, зафиксированная в репозитории (сгенерирована `cargo dist init` с
последующими правками); `cargo-dist-version` зафиксирован на 0.32.0, сгенерированный workflow
зафиксирован в репозитории для review, не подтягивается в runtime. Профиль сборки init инжектирует
`[profile.dist]` в корневой Cargo.toml (inherits release, lto=thin), двойной бинарник размещается в
`target/<triple>/dist/` для скрипта реорганизации.

### package-dist.sh (уже внесён)

Ориентируемся на `scripts/release/package-dist.sh` в репозитории, ключевые моменты:

- Двойной бинарник берётся напрямую из каталога вывода сборки `target/<triple>/dist/` (profile=dist)
  `cargo dist build` — плоский одиночно-бинарный архив, сгенерированный самим cargo-dist, не
  является поставкой; одноимённый реорганизованный пакет в `target/distrib/` просто перезаписывается
- Общая библиотека Z3 также берётся из каталога вывода сборки — build.rs при линковке уже выбрал
  общую библиотеку для соответствующей платформы и скопировал её на диск (`copy_shared_lib`),
  **единый источник**: скрипт упаковки не знает и не должен знать версию Z3 и именование каталогов
  платформы; текст лицензии Z3 сохраняется на диск вместе с библиотекой и включается в пакет
  (обязательство MIT по распространению), на стороне macOS при упаковке install_name dylib
  нормализуется до `@rpath` и бинарник повторно подписывается ad-hoc
- Каталог std — чистое копирование: `src/std/interfaces/*.yx` (предгенерируемые представления
  интерфейсов) + `src/std/*.yx` (реальные исходники слоя .yx)
- Приложить README/LICENSE; переупаковка (Windows zip / остальные tar.gz; если в Git Bash нет zip —
  трёхуровневый откат: zip → System32 bsdtar → PowerShell) и пересчёт `.sha256`
- На Linux при доступности `dpkg-deb` дополнительно вызвать `build-deb.sh` для получения `.deb`
  (дерево плоской установки `/usr/lib/yaoxiang` + символическая ссылка `/usr/bin/yx`)

### Критерии приёмки

«Из коробки» — тестируемо, миграция считается завершённой не по критерию «новые и старые артефакты
совпадают», а по прохождению всех следующих пунктов:

- На чистой машине (без Rust / без Z3 / без `~/.yaoxiang`) распаковать архив любой платформы,
  выполнить `bin/yaoxiang-rs --version` — без `LD_LIBRARY_PATH` (rpath работает)
- `lib/yaoxiang/std/*.yx` в распакованном каталоге полностью читаемы: нативные модули —
  представления сигнатур интерфейсов, слой `.yx` — реальные исходники
- LSP, запущенный на примере проекта в распакованном каталоге, обеспечивает автодополнение членов
  std / переход к определению (относительный поиск от exe работает)
- Согласно официальной инструкции, после распаковки в `/usr/local` (или `~/.yaoxiang`) и добавления
  в PATH, `yx --version` в любом каталоге завершается успешно
- `apt install yaoxiang` (собственный репозиторий) даёт работающую установку, `apt upgrade`
  отслеживает версии; под символической ссылкой `/usr/bin/yx` `$ORIGIN` движка (с резолвом по
  реальному пути) попадает в `bin/libz3.so`
- `curl ... | sh` и `irm ... | iex` в чистом окружении после выполнения — `yx` работает, PATH
  настроен
- `yx toolchain install <ver>` / `default` / `update` работают: сосуществование нескольких версий,
  `yx-toolchain.toml` (project pin) приоритетнее версии по умолчанию, парадная дверь диспетчеризует
  в правильную версию (rpath и поиск std в дереве версий самосогласованы, нет комбинации «новый
  движок со старым fmt»)
- При переносимой распаковке `yx` откатывается на соседний `yaoxiang-rs`, поведение совпадает с
  управляемой установкой
- После установки Inno Setup структура каталогов полная, PATH работает, возможно удаление
- Релизные ассеты полные: 5 платформ реорганизованных пакетов + `.sha256` соответствуют фактическому
  содержимому
- Тело релиза — вывод `generate-commit-list.mjs` (полный changelog из merge-коммитов)
- Nightly-артефакт — Pre-release, не затрагивает последний стабильный тег

## Компромиссы

### Преимущества

- **Из коробки** — переносимая распаковка и сразу работает (rpath + общая библиотека в том же
  каталоге), установщик разворачивает полную структуру каталогов
- **Стандартная библиотека читаема** — пользователь читает std напрямую, как `Lib/` в Python
  (жёсткое требование выполнено)
- **Снижение затрат на сопровождение** — ~600 строк рукописных YAML сборки заменены на cargo-dist +
  ~80 строк собственных скриптов
- **Кроссплатформенная согласованность** — динамическая линковка на всех платформах + общая
  библиотека в том же каталоге, без особых случаев
- **Двухуровневая установка** — стандартный канал с нулевым новым кодом (модель Go/Zig); дружелюбный
  канал по примеру Rust, четыре входа apt / curl / iex / exe используют одну структуру продуктов
- **Управление версиями встроено** — парадная дверь `yx` — аналог rustup / Go GOTOOLCHAIN, без
  постфактум «латания» экосистемы скриптами pyenv/nvm/pdm; блокировка версий инструментов —
  структурная гарантия, а не договорённость

### Недостатки и риски

- **Поверхность сопровождения дружелюбного канала** — install.sh / install.ps1 (однострочные
  скрипты, почти не развиваются) + `.deb` и публикация метаданных apt-репозитория (автоматизировано
  в release CI) + крейт парадной двери `yx`
- **Волна переименования движка** — `yaoxiang` → `yaoxiang-rs` требует однократной миграции имён
  артефактов CI, Inno, тестов и документации (в рамках этапа 5)
- **Затраты на обучение** — команде нужно освоить конфигурацию cargo-dist
- **Риски upstream cargo-dist** — в середине 2025 была пауза, связанная с Axo, в сентябре того же
  года оригинальный автор возобновил работу и продолжает релизы (0.29 → 0.32+); митигируется
  фиксацией `dist-version` + фиксацией сгенерированных артефактов в репозитории для review
- **У cargo-dist нет встроенного nightly** — часть nightly-публикации по-прежнему пишется вручную

### Связь с RFC-014b

|                      | RFC-014b                               | RFC-037                                       |
| -------------------- | -------------------------------------- | --------------------------------------------- |
| **Область**          | Сборка и дистрибуция сторонних пакетов | Упаковка и дистрибуция самого компилятора     |
| **Инструменты**      | `yaoxiang build` / `yaoxiang publish`  | `cargo-dist` + собственные скрипты            |
| **Артефакты**        | FFI-библиотеки сторонних пакетов       | Компилятор + стандартная библиотека + тулчейн |
| **Взаимоисключение** | Нет, дополняют друг друга              | Нет, дополняют друг друга                     |

## Альтернативы

| Альтернатива                                      | Почему не выбрана                                                                                                                                                                                                                                              |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Продолжать писать CI вручную**                  | Уже написано ~870 строк, повторяющаяся работа, легко забыть DLL                                                                                                                                                                                                |
| **Писать свой инструмент упаковки**               | Не изобретать велосипед, cargo-dist уже зрелый                                                                                                                                                                                                                 |
| **Только tar.gz без установщиков**                | Единственный официальный канал — распаковка + PATH; Inno только обслуживает привычку мастера на Windows (решение по китайским пользователям — оставить)                                                                                                        |
| **Дистрибуция через Docker**                      | Компилятору и языковому тулчейну нужны нативные бинарники, не контейнерный сценарий                                                                                                                                                                            |
| **Собственный Homebrew tap**                      | tap всегда поддерживается сообществом (homebrew-core), собственный — преждевременная потребность; вход macOS для дружелюбного канала — curl-скрипт                                                                                                             |
| **Отдельный бинарник `yaoxiangup` для менеджера** | Точный аналог rustup, выполнимо; но создаёт второй пользовательский глагол и вызывает симметричный вопрос «должны ли пакетный менеджер/fmt тоже быть отдельными» — разделение «парадная дверь / движок» снимает это разом (отклонено на обсуждении 2026-09-09) |
| **Только самообновление, без нескольких версий**  | Самообновление одной версии не решает потребность в разных версиях для разных проектов; в Python/Node нет официального управления версиями, экосистема вынуждена была породить pyenv/nvm/pdm — решение встроить (2026-09-09)                                   |
| **Полная статическая линковка Z3**                | Решение отклонено — каталожная дистрибуция общей библиотеки для внешних систем — естественная форма; засовывание в exe и размещение снаружи эквивалентны по «всё равно идёт в комплекте», причём второе теряет заменяемость                                    |
| **Отказ от Inno Setup**                           | Решение отклонено — сохранён как мастер для Windows (дополнительный канал)                                                                                                                                                                                     |
| **Родной установщик cargo-dist**                  | Предположение о плоском бинарнике конфликтует со структурой bin/+lib/, после установки библиотеки не хватает                                                                                                                                                   |
| **Самостоятельное сопровождение WiX/MSI**         | Потеря генератора cargo-dist обходится дороже ценности, уже покрытой Inno                                                                                                                                                                                      |

## Стратегия реализации

### Этап 1: Изменения на стороне языка (P0)

1. `build.rs`: унифицированная динамическая линковка на всех платформах + rpath link-arg;
   `copy_dll()` расширяется до `copy_shared_lib()` (so/dylib/dll)
2. Предгенерировать в репозитории представления нативных интерфейсов (`src/std/interfaces/`),
   тестовый шлагбаум форсирует синхронизацию с `StdModule::exports()` (подкоманда gen-std отменена
   по решению)
3. `find_std_interface_file` — добавить ветку относительного поиска от exe; `package init` — вывод
   унифицирован с `.yaoxiang/vendor/std`

### Этап 2: Подключение cargo-dist (P0)

1. Запустить `cargo dist init` для генерации начальной конфигурации (`installers = []`,
   зафиксировать dist-version)
2. Написать `package-dist.sh` (реорганизация + копирование исходников .yx + пересчёт контрольных
   сумм)
3. Создать `dist-release.yml` (триггер по тегу: dist build → реорганизация → wasm параллельно →
   собственный publish); `release.yml` сжать до шлюза + создания тега
4. Параллельно прогнать старый и новый конвейеры, сверить по критериям приёмки

### Этап 3: Вывод старого CI (P1)

1. После подтверждения — удалить `_build-platforms.yml`
2. В `nightly.yml` заменить сборку на `cargo dist build`
3. `setup.iss` подключить к новой структуре продуктов (Inno становится штатным; версия берётся из
   Cargo.toml, подмена через sed ликвидируется)

### Этап 4: Дружелюбный канал (P2)

1. `install.sh` / `install.ps1` (определение платформы → скачивание последнего реорганизованного
   пакета → распаковка в `versions/` → размещение `bin/yx` в корне установки → запись версии по
   умолчанию в `settings.toml` → подсказка/запись PATH; реализуется в одной итерации с этапом 5,
   сразу до финального состояния)
2. Упаковка `.deb` (повторное использование того же дерева каталогов, что и в `package-dist.sh` +
   символическая ссылка `/usr/bin`) + статический apt-репозиторий на GitHub Pages (метаданные
   подписаны GPG, публикуются релизным CI)

### Этап 5: Парадная дверь yx и переименование движка (P2)

1. Текущий монолит переименовывается в `yaoxiang-rs` (CI артефакты, Inno, тесты и документация
   проходятся полностью, однократная миграция)
2. Новый маленький крейт парадной двери `yx` (член workspace): разбор версии, скачивание релизных
   артефактов, распаковка tar/zip, settings.toml, диспетчеризация (зарезервированные глаголы только
   toolchain/self, остальные прозрачно транслируются, ручная диспетчеризация без clap для гарантии
   побуквенной передачи аргументов); индекс версий — из GitHub Releases latest API (зеркала —
   конкатенация префикса в стиле ghproxy); имя команды `yx` проверено на коллизии (в основных
   дистрибутивах / Homebrew нет одноимённой популярной команды, только один нишевый инструмент с yx
   как псевдонимом)
3. `yx toolchain install/default/update/list/uninstall` + project pin через `yx-toolchain.toml` +
   зеркала + `yx self update`
4. Загрузочные скрипты: `curl | sh` / `irm | iex` → скачивает реорганизованный пакет, за один раз
   устанавливает парадную дверь и stable по умолчанию (реализуется в одной итерации с этапом 4 как
   финальное состояние)

### Этап 6: Возможные доработки (все неблокирующие)

1. winget submission (указывает на Inno exe, поддерживается сообществом, симметрично модели
   homebrew-core)
2. `.rpm` (для пользователей dnf, однородно с `.deb`)
3. Homebrew: после достижения порога известности для принятия в homebrew-core — от сообщества
4. npm `@yaoxiang/cli` — собственная обёртка (имя сейчас свободно)

## Открытые вопросы

### Нерешённые

- **Предоставлять ли слою .yx семантику в стиле Python «ручное изменение каталога релиза принимается
  компилятором»?** По умолчанию — нет — компилирующий авторитет остаётся встроенным по RFC-036 (std
  жёстко привязан к версии бинарника), каталог релиза — читаемое представление + источник для
  LSP-разрешения. Если в будущем открыть — потребуется пересмотр инварианта привязки версии.

### Закрытые

Следующие вопросы были решены в ходе обсуждения дизайна:

- ~~Возможность статической линковки Z3 на Windows?~~ → **Не делать статическую линковку,
  динамическая на всех платформах** (подтверждено 2026-09-09)
- ~~Именование подкоманды gen-std-interfaces?~~ → **Подкоманду не делать** (решение 2026-09-10:
  после того как нормальная упаковка сформирована, подкоманды — лишняя поверхность; представления
  нативных интерфейсов переводятся в предгенерированный `src/std/interfaces/` в репозитории +
  тестовый шлагбаум синхронизации, упаковка — чистое копирование)
- ~~Сохранять ли Inno Setup?~~ → **Сохранить как мастер для Windows (дополнительный канал)**
- ~~Физически ли содержит релизный пакет исходники стандартной библиотеки?~~ → **Обязательно**
  (читаемость для пользователя соответствует Python `Lib/`, решение 2026-09-09)
- ~~Родные установщики cargo-dist (shell/powershell/homebrew/msi/npm)?~~ → **Все отбрасываются**,
  установщики свои (предположение о плоской структуре конфликтует с bin/+lib/)
- ~~Стратегия установщиков?~~ → **Двухуровневая** (окончательное решение 2026-09-09): стандартный
  канал = релизный пакет и есть продукт (модель Go/Zig, распаковка + PATH); дружелюбный канал по
  примеру Rust — установка одной командой — Linux `apt` (собственный deb-репозиторий) / `curl | sh`,
  Windows `irm | iex` / Inno exe. Не делать: MSI, родные установщики cargo-dist, собственный brew
  tap
- ~~Включать ли менеджер версий?~~ → **Обязательно, часть системы установщиков** (решение
  2026-09-09, отменяет более раннюю границу того же дня «отдельный RFC в перспективе»): мотивация —
  в Python/Node нет официального управления версиями, экосистема вынуждена была обзавестись
  pyenv/nvm/pdm, что привело к расколу
- ~~Форма менеджера версий: отдельный бинарник или подкоманда?~~ → **Разделение «парадная дверь /
  движок»** (окончательное решение 2026-09-09, сходимость за три раунда A → C → инверсия
  именования): повседневная команда `yx` = парадная дверь (маленький бинарник, встроенные глаголы
  toolchain/self), движок `yaoxiang-rs` = текущий монолит `yaoxiang` переименовывается; структура
  каталогов `versions/<ver>/` — версия — концепция первого уровня, каталог версии = корневой каталог
  распаковки релиза, инструменты блокируются вместе с версией атомарно (старый fmt не понимает новый
  синтаксис; предполагавшийся внутренний `toolchains/` отменён как избыточный). Прецеденты: Go с
  `go` в качестве парадной двери + GOTOOLCHAIN, прокси-диспетчеризация rustup
- ~~Условное выполнение extra-artifacts в cargo-dist?~~ → **Обработка скриптом `package-dist.sh`,
  через case-ветвления в shell**
- ~~Совместимость версий интерфейсов стандартной библиотеки?~~ → **Публикуется вместе с версией
  компилятора, в одном архиве**
