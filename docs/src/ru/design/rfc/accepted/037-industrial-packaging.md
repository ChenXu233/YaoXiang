# RFC-037: Индустриальная схема дистрибуции — упаковка компилятора/тулчейна на основе cargo-dist

> Настоящий RFC дополняет
> [RFC-014b: Система сборки и бинарная дистрибуция](../review/014b-build-system.md). RFC-014b
> определяет, как **менеджер пакетов YaoXiang** собирает и распространяет сторонние пакеты; данный
> RFC определяет, как **сам компилятор/тулчейн YaoXiang** упаковывается и распространяется.

## Резюме

Использовать `cargo-dist` (инструмент бинарной дистрибуции из экосистемы Rust) для оркестрации
кроссплатформенной сборки, при этом собственные скрипты отвечают за структуру дистрибутивного
пакета. Два ключевых обязательства: дистрибутивный пакет **физически содержит каталог исходного кода
стандартной библиотеки** (пользователь читает его так же, как Python `Lib/`), а также полностью
динамически слинкованная разделяемая библиотека Z3 распространяется вместе с пакетом для всех
платформ. Модель команд — **разделение «парадной двери» и движка**: частая команда `yx` (маленькая
парадная дверь со встроенным управлением версиями — аналог rustup/Go GOTOOLCHAIN), движок
`yaoxiang-rs` (бывший монолит `yaoxiang`, переименован), что позволяет избежать фрагментации
экосистемы по типу Python/Node, которые задним числом вынуждены наращивать nvm/pdm. Двухуровневая
установка: стандартный канал в духе Go/Zig — **дистрибутивный пакет и есть продукт**, распаковка +
PATH; чайниковый канал — однострочная команда (Linux `apt` / `curl | sh`, Windows `irm | iex` / Inno
exe-визард). Решает проблемы отсутствия `libz3.dll`, невидимости стандартной библиотеки для
пользователя, повторного сопровождения CI-скриптов.

## Мотивация

### Зачем нужна эта возможность?

Пользователь, скачивающий YaoXiang, должен иметь возможность **сразу начать работу** без каких-либо
дополнительных действий; стандартная библиотека должна быть **напрямую читаема** для пользователя, а
не скрыта в бинарнике как чёрный ящик.

### Текущие проблемы

#### Проблема 1: Пользователь Windows не может запустить скачанное

Текущий Release выкладывает только `yaoxiang.exe`, но `libz3.dll` не упаковывается. Пользователь на
Windows при двойном клике получает ошибку:

```
The code execution cannot proceed because libz3.dll was not found.
```

Это **критический баг** — пользователь не может пройти даже первый шаг.

#### Проблема 2: Артефакт Release — только одиночный exe, стандартная библиотека невидима для пользователя

Ситуация характеризуется тройным разрывом:

- Артефакт Release содержит только голый бинарник, стандартная библиотека не поставляется
- Цепочка поиска интерфейсных файлов LSP фактически разорвана: при вызове `find_std_interface_file`
  не передаётся каталог проекта (ищется только глобальный `~/.yaoxiang/std/`, и никто его не
  заполняет); `package init` записывает в `.yaoxiang/std`, что не входит в цепочку поиска
- Исходный код стандартной библиотеки (уровень `.yx`) и интерфейсное представление (уровень native)
  — полностью чёрный ящик для пользователя

Индустриальный подход: пользователь, как в случае с Python `Lib/`, просто открывает каталог
стандартной библиотеки и читает исходный код — **физическое наличие каталога std в дистрибутивном
пакете является жёстким требованием данной схемы** (уже решено).

#### Проблема 3: Дублирование ручных CI-скриптов

В настоящий момент сопровождается несколько конвейеров сборки:

| Файл                      | Ответственность           | Строк          |
| ------------------------- | ------------------------- | -------------- |
| `_build-platforms.yml`    | Кроссплатформенная сборка | ~255 строк     |
| `release.yml`             | Релиз версий              | ~189 строк     |
| `nightly.yml`             | Ежедневная сборка         | ~173 строки    |
| `scripts/build/setup.iss` | Inno Setup-инсталлятор    | ~250 строк     |
| **Итого**                 |                           | **~870 строк** |

Большая часть — повторяющиеся действия (установка Rust → кэш → сборка → переименование → загрузка),
прописываемые для каждой платформы отдельно.

#### Проблема 4: Хардкод номера версии в Inno Setup

В `setup.iss` `MyAppVersion` жёстко записано как `0.7.0`, при сборке подменяется через `sed`. Рано
или поздно это выстрелит.

#### Проблема 5: Размытость границ с RFC-014b

RFC-014b определяет «механизмы сборки и дистрибуции пакетов YaoXiang» (конфигурации `[build]` и
`[binaries]` в `yaoxiang.toml`), но **не покрывает вопрос о том, как публикуется сам компилятор
YaoXiang**. Данный RFC закрывает этот пробел.

## Предложение

### Основной дизайн

cargo-dist берёт на себя только **слой оркестрации сборки**; структура пакета и инсталляторы —
собственные. Разделение ответственности:

```
Ответственность cargo-dist (слой оркестрации сборки):
  ├── Кроссплатформенная компиляция (5 target'ов)
  └── Генерация архивов и checksum
  (Родные инсталляторы и npm wrapper отброшены — их допущение о плоском
   бинарнике конфликтует со структурой bin/+lib/)

build.rs продолжает отвечать за:
  └── Загрузку/линковку Z3 (динамически на всех платформах + rpath)

Собственные скрипты YaoXiang:
  ├── package-dist.sh — реорганизация структуры пакета (bin/ + lib/),
  │   добавление разделяемой библиотеки, заполнение каталога std
  │   (предгенерируемое интерфейсное представление из репозитория +
  │   исходный код уровня .yx), пересчёт checksum
  └── Inno Setup — визард установки для Windows (имеющийся актив;
      раскладывает полную структуру каталогов)

Модель команд (разделение «парадной двери» и движка):
  ├── yx — парадная дверь (новый маленький crate): разбор версии + диспетчеризация;
  │   сохраняет только команды toolchain/self, остальные пробрасывает
  └── yaoxiang-rs — движок (бывший монолит yaoxiang, переименован):
      подкоманды компиляции/запуска/менеджера пакетов/fmt/lsp

Способы установки (двухуровневые):
  ├── Стандартный канал (модель Go/Zig): дистрибутивный пакет и есть продукт,
  │   распаковка + PATH
  └── Чайниковый канал (модель Rust): однострочная команда + управление версиями
      (встроено в парадную дверь yx)
      ├── Linux: apt (собственный deb-репозиторий, системная установка) /
      │   curl … | sh (установка всего пакета одной командой)
      ├── Windows: irm … | iex (установка всего пакета одной командой) /
      │   Inno Setup-визард (имеющийся актив, системная установка)
      └── macOS: curl … | sh (brew — на усмотрение homebrew-core-сообщества)
```

### Структура каталога релиза (решено: физически несёт исходный код стандартной библиотеки)

Пользователь должен иметь возможность читать стандартную библиотеку так же, как Python `Lib/` —
наличие каталога std в дистрибутивном пакете является жёстким требованием, а не деталью упаковки. С
Z3 то же самое: для внешней системы каталожная дистрибуция разделяемой библиотеки — естественный для
неё способ; засунуть `.so` в exe или положить рядом с динамической линковкой — в плане «всё равно
идёт с пакетом» эквивалентно, но второй вариант сохраняет заменяемость.

Каждый платформенный дистрибутивный пакет реорганизуется `package-dist.sh` после сборки cargo-dist:

```
yaoxiang-{version}-{target}.tar.gz / .zip     (портативный, готов к использованию:
                                               распакуй и сразу запускай из bin/)
├── bin/
│   ├── yx                            # парадная дверь (или yx.exe)
│   ├── yaoxiang-rs                   # движок (или yaoxiang-rs.exe)
│   └── libz3.so / libz3.dylib / libz3.dll
├── lib/
│   └── yaoxiang/
│       └── std/                      # пользователь может читать напрямую (модель Python Lib/)
│           ├── io.yx                 # native-модуль: предгенерируемое интерфейсное представление
│           ├── math.yx
│           ├── test.yx               # уровень .yx: реальный исходный код копируется из репозитория
│           └── ...
├── README.md
└── LICENSE
```

Установка = распаковка в любой каталог + добавление `bin/` в PATH (модель Go `/usr/local/go/bin`;
часто выбирают `~/.yaoxiang/`). На Windows визард Inno Setup делает то же самое (по умолчанию
Program Files). При портативной распаковке у парадной двери `yx` нет состояния `~/.yaoxiang`,
происходит откат на соседний `yaoxiang-rs` — поведение идентично управляемой установке; rpath движка
и относительный поиск std относительно exe не меняются из-за наличия парадной двери.

### Поддержка платформ

| Платформа      | target triple               | Примечание            |
| -------------- | --------------------------- | --------------------- |
| Linux x86_64   | `x86_64-unknown-linux-gnu`  | Основная платформа    |
| Linux ARM64    | `aarch64-unknown-linux-gnu` | Кросс-компиляция в CI |
| macOS x86_64   | `x86_64-apple-darwin`       | Intel Mac             |
| macOS ARM64    | `aarch64-apple-darwin`      | Apple Silicon         |
| Windows x86_64 | `x86_64-pc-windows-msvc`    | Основная платформа    |

Всего 5 target'ов. Windows ARM64 временно не поддерживается (у Z3 нет официального
прекомпилированного пакета для ARM64).

### Стратегия дистрибуции Z3

**Динамическая линковка на всех платформах** (пересмотрено, оставлено как есть):

| Платформа | Изменение               | Артефакт      |
| --------- | ----------------------- | ------------- |
| Linux     | **статика → динамика**  | `libz3.so`    |
| macOS     | **статика → динамика**  | `libz3.dylib` |
| Windows   | без изменений           | `libz3.dll`   |
| wasm32    | без изменений (статика) | встроен `.a`  |

Обоснование:

- **Единообразие** — поведение на трёх платформах одинаково, больше нет исключений
- **Это внешняя библиотека, и её распространение через разделяемую библиотеку естественно**. Так
  делают Python (`python3.dll`+`DLLs/lib*.dll`) и Node (`node`+`lib/`)
- **Пользователь может обновить Z3, не дожидаясь новой версии компилятора** — достаточно заменить
  `.so`/`.dylib`/`.dll`
- **Меньший размер бинарника** — Z3 не маленькая, статическая линковка раздует exe на несколько
  мегабайт

У динамической линковки есть **необходимое сопровождение**: динамический линковщик в Linux/macOS по
умолчанию не ищет в каталоге бинарника, поэтому нужно встроить rpath, иначе «распакуй и пользуйся»
не сработает (Windows по умолчанию ищет в каталоге exe, ничего делать не нужно). Соответствующее
изменение в `build.rs`:

```rust
// Унифицированная динамическая линковка + rpath
fn link_z3(z3_dir: &Path) {
    let target_os = env::var("CARGO_CFG_TARGET_OS").unwrap();
    // Структура дистрибутива Z3 неединообразна, двойной поиск lib/bin
    println!("cargo:rustc-link-search=native={}", lib_dir.display());
    // RFC-037: динамическая линковка на всех платформах. Разделяемая библиотека
    // идёт с пакетом в bin/, пользователь может заменить/обновить Z3 целиком
    if target_os == "windows" {
        // MSVC import lib именуется libz3.lib
        println!("cargo:rustc-link-lib=libz3");
    } else {
        println!("cargo:rustc-link-lib=z3");
        // Динамический линковщик по умолчанию не ищет в каталоге бинарника,
        // нужно встроить rpath, иначе «распакуй и пользуйся» не сработает
        // (exe и libz3 оба лежат в bin/; Windows по умолчанию ищет в каталоге exe)
        match target_os.as_str() {
            "linux" => println!("cargo:rustc-link-arg=-Wl,-rpath,$ORIGIN"),
            "macos" => println!("cargo:rustc-link-arg=-Wl,-rpath,@loader_path"),
            _ => {}
        }
        let cxx = if target_os == "macos" {
            "c++".to_string()
        } else {
            env::var("CXXSTDLIB").unwrap_or_else(|_| "stdc++".into())
        };
        println!("cargo:rustc-link-lib={}", cxx);
    }
}
```

**«Статическая линковка Z3 на всех платформах» не является целью.** Это не устранение особого
случая, а попытка убрать правильный случай неправильным способом. Разделяемая библиотека —
нормальный способ дистрибуции внешней библиотеки.

### Поддержка инсталляторов

Сравнение способов дистрибуции основных языковых тулчейнов (обзор от 2026-09):

| Язык     | Официальные дистрибутивы         | Официальный способ установки                            | Кто поддерживает инсталлятор                |
| -------- | -------------------------------- | ------------------------------------------------------- | ------------------------------------------- |
| Go       | `go/{bin,src,pkg}` tarball       | Официальная докуменация: «скачать → распаковать → PATH» | Нет (brew/apt — сообщество)                 |
| Zig      | `zig/{bin,lib/std}` tarball      | То же, без официального скрипта установки               | Нет (homebrew-core — сообщество)            |
| Node     | `{bin,lib,include}` tarball      | tar + официальный pkg/msi                               | Команда пишет сама                          |
| Rust     | tarball с множеством компонентов | rustup                                                  | Команда пишет сама                          |
| Crystal  | `{bin,src,embedded}` tarball     | deb/rpm/tar                                             | Команда + brew-сообщество                   |
| Deno/Bun | zip с одним бинарником           | Официальный curl-скрипт                                 | Команда пишет сама (скрипт очень маленький) |
| Gleam    | cargo-dist с одним бинарником    | Скрипт, генерируемый cargo-dist                         | cargo-dist                                  |

Три закономерности:

- **Ни один многофайловый тулчейн не использует сторонний генератор для инсталлятора** — инсталлятор
  cargo-dist рассчитан только на сценарий с одним бинарником (Gleam может его использовать именно
  потому, что это один Rust-бинарник без внешних зависимостей)
- Простейшая модель — **«дистрибутивный пакет и есть продукт» из Go/Zig**: официальная инструкция —
  распаковка + PATH, ноль кода инсталлятора; дистрибутив с читаемым исходным кодом std — норма (Go
  `src/`, Zig `lib/std/`, Crystal `src/`)
- Те, кому нужна установка одной командой curl (Deno/Bun/rustup), пишут **скрипты сами**, и они
  почти не эволюционируют; формулы brew всегда поддерживаются сообществом в homebrew-core, языковая
  команда не делает свой tap (команда Crystal явно говорит, что formula — дело сообщества)

YaoXiang использует двухуровневую модель:

| Канал                                                 | Уровень    | Статус | Описание                                                                                                                                 |
| ----------------------------------------------------- | ---------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| zip / tar.gz                                          | стандарт   | ✅     | Распакуй и пользуйся (rpath + разделяемая библиотека в том же каталоге), extract + PATH — официальная инструкция                         |
| `yx` (парадная дверь, встроенное управление версиями) | чайниковый | ✅     | Аналог rustup/Go GOTOOLCHAIN: установка/переключение/обновление нескольких версий + project pin                                          |
| `curl ... \| sh` (install.sh)                         | чайниковый | ✅     | Linux / macOS: скачивает перепакованный пакет, кладёт в `versions/`, `bin/yx` встаёт в корень установки, прописывает версию по умолчанию |
| `irm ... \| iex` (install.ps1)                        | чайниковый | ✅     | Windows: та же логика                                                                                                                    |
| `apt install yaoxiang`                                | чайниковый | ✅     | `.deb` (amd64/arm64) + статический apt-репозиторий на GitHub Pages; системная установка, `apt upgrade` отслеживает версию                |
| Inno Setup exe                                        | чайниковый | ✅     | Windows-визард (имеющийся актив), системная установка, раскладывает полную структуру bin/+lib/                                           |
| winget / `.rpm` / homebrew-core / npm                 | —          | ⏸      | Возможное будущее: winget и brew-core — сообществом, rpm симметричен deb                                                                 |
| MSI / родной инсталлятор cargo-dist / свой brew tap   | —          | ❌     | См. «Альтернативы»                                                                                                                       |

**Чайниковый канал — по образцу Rust, управление версиями встроено в парадную дверь.** Разделение в
Rust — «скрипт-бутстрап (sh.rustup.rs) → rustup → пакет тулчейна»; rustup с самого начала берёт на
себя несколько версий, переключение, обновление. В Python/Node официальный инсталлятор не сделал
этого слоя, и экосистема задним числом породила pyenv/nvm/pdm, каждый по-своему. YaoXiang использует
**разделение «парадной двери» и движка** (Go: `go` как парадная дверь + GOTOOLCHAIN; rustup:
прокси-диспетчеризация — обе структуры изоморфны): частая команда — `yx`, движок — `yaoxiang-rs` —

```
~/.yaoxiang/
├── bin/yx                  # парадная дверь: маленький бинарник, разбор версии + диспетчеризация
│                           # (project pin > по умолчанию > соседний движок)
├── settings.toml           # версия по умолчанию, источники зеркал
└── versions/               # версия — понятие первого уровня; <ver>/ — корень распаковки
                            # дистрибутивного пакета этой версии
    └── 0.7.14/
        ├── bin/
        │   ├── yaoxiang-rs      # движок: подкоманды компиляции/запуска/менеджера пакетов/fmt/lsp
        │   └── libz3.so
        └── lib/yaoxiang/std/
```

- Корень установки `~/.yaoxiang/` соответствует индустриальной практике (pyenv `~/.pyenv`, nvm
  `~/.nvm`, deno `~/.deno`, bun `~/.bun`, volta `~/.volta` — все с одним корнем; rustup с
  `~/.cargo`+`~/.rustup` — историческое наследие того, что cargo появился раньше rustup, не
  повторяем), и `~/.yaoxiang` — это уже существующее пространство имён в кодовой базе (резервный
  слот std на глобальном уровне); поддерживается переопределение переменной окружения
  `YAOXIANG_HOME` (прецеденты RUSTUP_HOME / DENO_INSTALL, для CI и контейнеров); на Windows —
  `%USERPROFILE%\.yaoxiang`
- **Каталог версии = корень распаковки дистрибутивного пакета**: `versions/<ver>/` полностью
  изоморфен дереву портативной распаковки и deb-установки — установка версии = распаковка
  дистрибутивного пакета, три канала без структурного расхождения
- Командная поверхность (аналог rustup):
  `yx toolchain install / default / update / list / uninstall`, включая `yx self update`; остальные
  команды пробрасываются движку as is
- **Версионная привязка — структурная гарантия**: fmt и подобные инструменты эволюционируют вместе с
  синтаксисом (старый fmt не понимает новый синтаксис), разбор версии делается один раз перед
  парадной дверью, вся группа переключается — нет пространства комбинаций «новый движок со старым
  fmt»; если в будущем fmt/LSP выделятся в отдельные бинарники, они тоже окажутся в `bin/` той же
  версии
- Проектный pin: `yx-toolchain.toml` (прецедент rust-toolchain.toml, следует за именем команды; не в
  `yaoxiang.toml` — манифест пакета не должен навязывать версию тулчейна пользователю библиотеки)
- Бутстрап (`curl | sh` / `irm | iex`) разом ставит последний стабильный пакет целиком: распаковка в
  `versions/`, `bin/yx` встаёт в корень установки, прописывает `settings.toml` с версией по
  умолчанию (сходится к декомпозиции «бутстрап ставит менеджер» из rustup — парадная дверь и движок
  в одном пакете, двух шагов не нужно)
- Источники зеркал настраиваются (settings.toml), продолжая заботу о пользователях из Китая (та же
  сетевая проблема, что и с загрузкой Z3)
- **Управление версиями не нарушает инвариант самодостаточности**: каждая версия — это полное дерево
  дистрибутива, rpath и поиск std относительно exe согласованы внутри дерева, парадная дверь только
  диспетчеризует, не меняя структуру

`.deb` и Inno — каналы **системной установки** (root / Program Files, одна версия, обновляется через
`apt upgrade` / панель управления), для серверов, CI, новичков; сосуществование с менеджером — через
порядок PATH (прецедент: rustc из apt и rustup сосуществуют). Все каналы используют одно и то же
дерево артефактов.

Раскладка `.deb` повторно использует то же дерево: `/usr/lib/yaoxiang/` (всё дерево дистрибутива:
`bin/{yx,yaoxiang-rs,libz3.so}` + `lib/yaoxiang/std/`) + символическая ссылка `/usr/bin/yx` →
`/usr/lib/yaoxiang/bin/yx` — `$ORIGIN` вычисляется по **реальному пути** после резолва ссылок, всё
равно попадает на `libz3.so` в том же каталоге, изоморфно структуре распаковки. Полное брендовое имя
остаётся в имени пакета и продукта (`apt install yaoxiang`, имя продукта Inno — YaoXiang), командная
поверхность — единая `yx` — как Go: имя пакета `golang-go`, команда `go`. Репозиторий apt статически
хостится на GitHub Pages (метаданные Packages/Release/InRelease подписаны GPG, публикуются release
CI); в перспективе — подача заявки на официальное включение в Debian/Ubuntu (долгий цикл, отстающие
версии, не основной путь).

### Каталог стандартной библиотеки

Содержимое `lib/yaoxiang/std/` полностью берётся из статических файлов репозитория, упаковка —
**чистое копирование**, без точки входа в рантайме:

| Слой                       | Источник                                                                               | Природа                                                         |
| -------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| native-модули (io/math/…)  | Предгенерируемые интерфейсные представления из `src/std/interfaces/*.yx` в репозитории | Представление сигнатур интерфейса (реализация внутри бинарника) |
| .yx-модули (test/… растут) | Копируются as is из `src/std/*.yx`                                                     | Реальный исходный код                                           |

Предгенерируемое представление порождается из `StdModule::exports()` (`generate_all_interfaces()` в
`src/std/gen_interfaces.rs`), **подкоманда в рантайме не вводится** (решение от 2026-09-10: после
того как упаковка сформирована, подкоманда — лишняя поверхность интерфейса). Применяется модель
«генерат в репозитории + тестовый шлагбаум» (аналог таблице кодов из RFC-013):
`test_committed_interface_files_match_generation` побайтово сравнивает предгенерированные файлы с
текущей генерацией, расхождение — красный свет; лечение через bless-вход
`cargo test update_committed_interface_files -- --ignored`. Логика генерации зависит от внутренней
реализации `StdModule` в crate, её нельзя спустить в build.rs, поэтому шлагбаум стоит в тестах, а не
на этапе сборки.

**Цепочка поиска в рантайме** — в `find_std_interface_file` добавляется ещё один уровень:
относительный поиск относительно exe:

1. Проект `.yaoxiang/vendor/std/<name>.yx` (переопределение проектом, текущее)
2. **Каталог exe `../lib/yaoxiang/std/<name>.yx` (новое)**: портативная распаковка, управляемая
   установка (`versions/<ver>/`), deb-установка — все попадают сюда
3. `~/.yaoxiang/std/<name>.yx` (глобальный откат, оставлен как место для ручного переопределения)

Сейчас эта цепочка фактически разорвана (LSP вызывается без передачи каталога проекта,
`package init` пишет в `.yaoxiang/std`, чего в цепочке нет) — по ходу подключаем, а заодно
унифицируем вывод `package init` в `.yaoxiang/vendor/std` (соответствует каталогу vendor менеджера
пакетов).

**Авторитет компиляции не меняется**: уровень `.yx` по-прежнему встраивается через `include_str!`
(инвариант «версия std жёстко привязана к бинарнику» из RFC-036 сохраняется). Раскладка в
дистрибутиве — **читаемое представление + источник резолва LSP**, а не вход компиляции —
пользовательская правка `.yx` в каталоге дистрибутива не будет принята компилятором (открывать ли
Python-семантику «правлю `Lib/` — работает» — см. открытый вопрос).

### Сборка Wasm

**Остаётся отдельной, в cargo-dist не мигрирует.**

cargo-dist занимается «доставкой компилятора пользователю», wasm — «встраивание онлайн-playground в
сайт документации» — это совершенно разные артефакты.

| Аспект            | Подход                                      |
| ----------------- | ------------------------------------------- |
| Инструмент сборки | Остаётся `wasm-pack build`                  |
| CI workflow       | Сохраняется отдельный job `_build-wasm.yml` |
| Триггер           | Параллельно с release при том же push тега  |
| Цель публикации   | `docs/public/wasm/` → GitHub Pages          |

### npm-публикация

| Пакет                  | Содержимое                       | Статус                                                                                                                                                                                                                                |
| ---------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@yaoxiang/cli`        | wrapper, скачивающий дистрибутив | Отложено: npm-wrapper из cargo-dist тоже исходит из допущения плоского артефакта, отброшен вместе с инсталляторами; если нужен канал npm, написать wrapper самим (скачать перепакованный пакет, распаковать, логика как у распаковки) |
| `@yaoxiang/playground` | wasm-библиотека (JS + .wasm)     | Опционально, сейчас публикуется только в docs                                                                                                                                                                                         |

Конфликта нет, конфликта имён нет.

### Интеграция с существующим процессом релиза

Текущий `release.yml`: push main → check-version (пропускает, только если тег `v{version}` не
существует) → четыре ветки build / build-wasm / security / test → release-job (создаёт и пушит тег +
`generate-commit-list.mjs` генерирует body с @mentions + загрузка артефактов).

Конвейер от cargo-dist запускается по тегу, имеет собственный announce/publish, и не содержит шлюзов
fmt/clippy/test/audit, формат release notes не вмещает changelog из merge-коммитов. **Полная замена
сломала бы существующий релизный ритуал** (PR → CI зелёный → bump → merge-коммит = changelog).

Принцип интеграции: **триггеры и шлюзы остаются как есть, сборку отдаём `cargo dist build`,
публикация остаётся как есть.**

1. check-version / security / test — три job остаются как есть (триггер push main, шлюзы перед
   созданием тега)
2. После прохождения release-job создаёт и пушит тег `v{version}` (без изменений)
3. Push тега запускает новый `dist-release.yml`: plan-job — dist считает матрицу runner/системных
   зависимостей → `cargo dist build` (5 target'ов) → `package-dist.sh` реорганизует по каждому
   target → Inno Setup-job (берёт перепакованный Windows-пакет и строит визард, версия инжектируется
   через `/DMyAppVersion=`, повторной компиляции нет) → `_build-wasm.yml` (параллельный job)
4. publish-job: `generate-commit-list.mjs` генерирует body (переиспользование текущего скрипта) →
   догружает перепакованные пакеты + `.sha256` + `.deb` + wasm + Setup exe; отдельный
   `publish-apt`-job публикует метаданные apt-репозитория на GitHub Pages (при отсутствии
   `secrets.APT_GPG_KEY` автоматически пропускается, не влияя на остальные каналы)

### Nightly-релизы

У cargo-dist нет нативной поддержки nightly
([axodotdev#1143](https://github.com/axodotdev/cargo-dist/issues/1143), до сих пор open feature
request).

Сохраняем текущую схему cron + перезапись тега, в части сборки меняем `_build-platforms.yml` на
`cargo dist build` — по сути это cargo-команда, её можно вызвать прямо из nightly.yml. Без
переиспользования workflow (предполагаемое `uses: ./release.yml` не сработает: у переиспользуемого
нужен триггер `workflow_call`, а workflow от cargo-dist — tag-driven, сборка и публикация связаны):

```yaml
# nightly.yml (после миграции)
on:
  schedule:
    - cron: '17 22 * * *'
jobs:
  build: # cargo dist build + package-dist.sh (тот же набор, что и у официального релиза)
  publish: # сохраняем текущее: создать/перенести nightly-тег → перезаписать GitHub Pre-release
```

### Конфигурация cargo-dist (уже внедрена в dist-workspace.toml)

```toml
[workspace]
members = ["cargo:.", "cargo:tools/yx"]

# Конфигурация 'dist'
[dist]
# Фиксируем версию dist (синтаксис SemVer из Cargo.toml)
cargo-dist-version = "0.32.0"
ci = "github"
# Все инсталляторы — свои, cargo-dist делает только сборку + архивы + checksum
installers = []
targets = ["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "x86_64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
# Сгенерированный workflow преднамеренно модифицирован (реорганизация package-dist.sh +
# собственная секция publish, RFC-037), не отказываемся от сборки из-за дриффа с шаблоном generate
allow-dirty = ["ci"]
```

Это реальная конфигурация, вендорённая в репозиторий (после `cargo dist init` отредактирована по
месту); `cargo-dist-version` зафиксирована на 0.32.0, сгенерированный workflow вендорится в
репозиторий и проходит review, не подтягивается в рантайме. Профиль сборки инжектируется init'ом в
корневой Cargo.toml как `[profile.dist]` (inherits release, lto=thin), оба бинарника кладутся в
`target/<triple>/dist/` для дальнейшей переупаковки.

### package-dist.sh (уже внедрён)

Взять за основу `scripts/release/package-dist.sh` из репозитория, ключевые моменты:

- Оба бинарника берутся напрямую из выходного каталога сборки `cargo dist build` —
  `target/<triple>/dist/` (profile=dist) — собственные плоские однофайловые архивы от cargo-dist не
  поставляются, одноимённый перепакованный пакет прямо перезаписывается в `target/distrib/`
- Разделяемая библиотека Z3 копируется из `.z3/z3-<ver>-<tag>/` (двойной поиск lib → bin) в `bin/`;
  `<tag>` согласован с именованием дистрибутива в `build.rs::detect_target()` (поддерживается в двух
  местах, см. риски)
- Каталог std — чистое копирование: `src/std/interfaces/*.yx` (предгенерируемые интерфейсные
  представления) + `src/std/*.yx` (реальный исходный код уровня .yx)
- Прикладываются README/LICENSE; переупаковка (Windows zip / остальные tar.gz; если в Git Bash нет
  zip — fallback zip → System32 bsdtar → PowerShell, три уровня) и пересчёт `.sha256`
- На Linux при наличии `dpkg-deb` — попутно вызывается `build-deb.sh` для получения `.deb`
  (раскладка `/usr/lib/yaoxiang` + символическая ссылка `/usr/bin/yx`)

### Критерии приёмки

«Из коробки» — это тестируемо; признаком завершения миграции является не «совпадение старых и новых
артефактов», а прохождение всех следующих пунктов:

- На чистой машине (без Rust / без Z3 / без `~/.yaoxiang`) распаковать архив любой платформы и
  выполнить `bin/yaoxiang-rs --version` — без установки `LD_LIBRARY_PATH` (rpath работает)
- Все `lib/yaoxiang/std/*.yx` в каталоге распаковки читаемы: native-модули как представление
  сигнатур интерфейса, .yx-слой как реальный исходный код
- В примере проекта из каталога распаковки запустить LSP, автодополнение членов std / переход к
  определению работают (относительный поиск от exe работает)
- После распаковки в `/usr/local` (или `~/.yaoxiang`) по официальной инструкции и добавления в PATH,
  в любом каталоге `yx --version` успешно
- `apt install yaoxiang` (из собственного репозитория) — запускается, `apt upgrade` отслеживает
  версию; под символической ссылкой `/usr/bin/yx` движок видит `bin/libz3.so` по `$ORIGIN` (с учётом
  реального пути после резолва ссылок)
- `curl ... | sh` и `irm ... | iex` на чистой среде после выполнения — `yx` запускается, PATH
  настроен
- `yx toolchain install <ver>` / `default` / `update` работают: сосуществование нескольких версий,
  `yx-toolchain.toml` имеет приоритет над версией по умолчанию, парадная дверь диспетчеризует в
  правильную версию (rpath и поиск std внутри дерева версии согласованы, нет комбинации «новый
  движок со старым fmt»)
- При портативной распаковке `yx` откатывается на соседний `yaoxiang-rs`, поведение совпадает с
  управляемой установкой
- После установки через Inno Setup структура каталогов полная, PATH работает, деинсталляция возможна
- Релизные артефакты полные: перепакованные пакеты 5 платформ + `.sha256` совпадают с реальным
  содержимым
- Тело релиза — вывод `generate-commit-list.mjs` (merge-коммит changelog полный)
- Nightly-артефакт — Pre-release, не влияет на последний официальный тег

## Компромиссы

### Преимущества

- **Из коробки** — портативная распаковка и сразу работает (rpath + разделяемая библиотека в том же
  каталоге), инсталляторы раскладывают полную структуру каталогов
- **Стандартная библиотека читаема** — пользователь читает std как Python `Lib/` (жёсткое требование
  выполнено)
- **Снижение стоимости сопровождения** — ~600 строк ручного YAML сборки заменены на cargo-dist + ~80
  строк собственных скриптов
- **Кроссплатформенное единообразие** — динамическая линковка + разделяемая библиотека в том же
  каталоге на всех платформах, без исключений
- **Двухуровневая установка** — стандартный канал без нового кода (модель Go/Zig); чайниковый канал
  по образцу Rust, четыре входа — apt / curl / iex / exe — делят одну структуру артефактов
- **Управление версиями встроено** — парадная дверь `yx` на месте rustup/Go GOTOOLCHAIN, избавляет
  от фрагментации, как у Python/Node, вынужденных задним числом добавлять pyenv/nvm/pdm; версионная
  привязка инструментов — структурная гарантия, а не договорённость

### Недостатки и риски

- **Поверхность сопровождения чайникового канала** — install.sh / install.ps1 (однострочные скрипты,
  почти не эволюционируют) + `.deb` и публикация метаданных apt-репозитория (автоматизировано в
  release CI) + crate парадной двери `yx`
- **Переименование движка затрагивает много мест** — `yaoxiang` → `yaoxiang-rs` требует разовой
  миграции имён артефактов CI, Inno, тестов и документации (выполняется в рамках этапа 5)
- **Стоимость обучения** — команде нужно изучить конфигурацию cargo-dist
- **Риски upstream cargo-dist** — в середине 2025 проект ненадолго встал из-за приостановки Axo, в
  сентябре того же года оригинальный автор возобновил работу и продолжает релизы (0.29 → 0.32+);
  митигируется фиксацией `dist-version` + вендорингом генерата в репозиторий для review
- **У cargo-dist нет нативного nightly** — часть ночного релиза всё равно пишется вручную
- **Именование каталога Z3 поддерживается в двух местах** — `package-dist.sh` и
  `build.rs::detect_target()` должны быть согласованы (следует свести к единому источнику)

### Связь с RFC-014b

|                      | RFC-014b                               | RFC-037                                       |
| -------------------- | -------------------------------------- | --------------------------------------------- |
| **Область**          | Сборка и дистрибуция сторонних пакетов | Упаковка и дистрибуция самого компилятора     |
| **Инструмент**       | `yaoxiang build` / `yaoxiang publish`  | `cargo-dist` + собственные скрипты            |
| **Артефакт**         | FFI-библиотеки сторонних пакетов       | Компилятор + стандартная библиотека + тулчейн |
| **Взаимоисключение** | Нет, дополняют                         | Нет, дополняют                                |

| **Продолжать писать CI вручную**                  | Уже написано ~870 строк, повторяющийся труд, легко забыть DLL                                                                                                                                                                                                  |
| **Самописный инструмент упаковки**                | Не изобретать колесо, cargo-dist уже зрелый                                                                                                                                                                                                                    |
| **Только tar.gz, без инсталляторов**              | Единственный официальный канал — распаковка + PATH; Inno только для привычки Windows-визарда (уже решено сохранить)                                                                                                                                            |
| **Дистрибуция через Docker**                      | Компилятору и языковому тулчейну нужны нативные бинарники, не контейнерный сценарий                                                                                                                                                                            |
| **Свой Homebrew tap**                             | tap'ы всегда на сопровождении сообщества (homebrew-core), заводить свой — преждевременно; вход macOS для чайникового канала — curl-скрипт                                                                                                                      |
| **Отдельный бинарник `yaoxiangup` для менеджера** | Прямой прецедент rustup, осуществимо; но создаёт второй глагол пользователя и провоцирует симметричный вопрос «а менеджеру пакетов/fmt тоже отдельный?» — разделение «парадной двери» и движка снимает оба вопроса (отклонено по итогам обсуждения 2026-09-09) |
| **Только самообновление, без нескольких версий**  | Самообновление одной версии не закрывает потребность в pin'е разных версий разными проектами; в Python/Node нет официального управления версиями, и экосистема вынужденно породила pyenv/nvm/pdm — уже решено встраивать (2026-09-09)                          |
| **Полностью статическая линковка Z3**             | Уже отклонено — для внешней системы каталожная дистрибуция разделяемой библиотеки естественна; засунуть в exe или положить рядом в плане «всё равно идёт с пакетом» эквивалентно, но теряется заменяемость                                                     |
| **Отказ от Inno Setup**                           | Уже отклонено — сохраняется как Windows-визард (дополнительный канал)                                                                                                                                                                                          |
| **Родной инсталлятор cargo-dist**                 | Допущение плоского бинарника конфликтует со структурой bin/+lib/, после установки библиотеки не хватает                                                                                                                                                        |
| **Самостоятельное сопровождение WiX/MSI**         | Без генератора cargo-dist стоимость выше, чем ценность, уже покрытая Inno                                                                                                                                                                                      |

## Стратегия реализации

### Этап 1: Изменения на стороне языка (P0)

1. `build.rs`: унифицированная динамическая линковка + rpath link-arg; `copy_dll()` расширяется до
   `copy_shared_lib()` (so/dylib/dll)
2. Предгенерировать native-интерфейсные представления в репозитории (`src/std/interfaces/`),
   тестовый шлагбаум обеспечивает синхронизацию с `StdModule::exports()` (подкоманда gen-std уже
   отменена решением)
3. В `find_std_interface_file` добавляется ветка относительного поиска от exe; вывод `package init`
   унифицируется в `.yaoxiang/vendor/std`

### Этап 2: Подключение cargo-dist (P0)

1. Запустить `cargo dist init` для генерации начальной конфигурации (`installers = []`,
   зафиксировать dist-version)
2. Написать `package-dist.sh` (реорганизация + копирование исходников .yx + пересчёт checksum)
3. Создать `dist-release.yml` (tag-driven: dist build → реорганизация → wasm параллельно →
   собственный publish); `release.yml` сокращается до шлюзов + создания тега
4. Прогнать старый и новый конвейеры параллельно, пройтись по критериям приёмки

### Этап 3: Вывод старого CI (P1)

1. После подтверждения корректности удалить `_build-platforms.yml`
2. В `nightly.yml` секция сборки меняется на `cargo dist build`
3. `setup.iss` подключается к новой структуре артефактов (Inno в каноне; версия берётся из
   Cargo.toml, sed-замена устраняется)

### Этап 4: Чайниковый канал (P2)

1. `install.sh` / `install.ps1` (определить платформу → скачать последний перепакованный пакет →
   распаковать в `versions/` → `bin/yx` встаёт в корень установки → записать `settings.toml` с
   версией по умолчанию → подсказка/запись PATH; лендятся в одной итерации с этапом 5, один шаг до
   финального состояния)
2. Упаковка `.deb` (повторно использует то же дерево каталогов из `package-dist.sh` + символическая
   ссылка `/usr/bin`) + статический apt-репозиторий на GitHub Pages (метаданные подписаны GPG,
   публикуются release CI)

### Этап 5: Парадная дверь yx и переименование движка (P2)

1. Текущий монолит переименовывается в `yaoxiang-rs` (полный проход по именам артефактов CI, Inno,
   тестам и документации, разовая миграция)
2. Новый маленький crate парадной двери `yx` (член workspace): разбор версии, скачивание релизных
   артефактов, распаковка tar/zip, settings.toml, диспетчеризация (сохраняет только команды
   toolchain/self, остальные пробрасывает, ручная диспетчеризация без clap для гарантии побуквенной
   передачи аргументов); индекс версий из GitHub Releases latest API (источники зеркал — префиксы в
   стиле ghproxy); имя команды `yx` проверено на коллизии (в основных дистрибутивах/Homebrew нет
   распространённых однофамильцев, только один нишевый инструмент использует yx как псевдоним)
3. `yx toolchain install/default/update/list/uninstall` + `yx-toolchain.toml` для проектного pin +
   источники зеркал + `yx self update`
4. Скрипты-бутстрапы: `curl | sh` / `irm | iex` → скачивают перепакованный пакет и разом ставят
   парадную дверь и актуальный stable (лендятся в одной итерации с этапом 4 как финальное состояние)

### Этап 6: Возможные доработки (ни на что не блокируют)

1. Подача в winget (указывает на Inno exe, сопровождает сообщество — симметрично модели
   homebrew-core)
2. `.rpm` (для пользователей dnf, симметрично `.deb`)
3. Homebrew: после достижения порога известности для принятия в homebrew-core — сообществом
4. Самописный npm wrapper для `@yaoxiang/cli` (имя сейчас свободно)

## Открытые вопросы

### Нерешённые

- **Должен ли .yx-слой поддерживать Python-семантику «правка в каталоге дистрибутива подхватывается
  компилятором»?** По умолчанию нет — авторитет компиляции остаётся встроенным в соответствии с
  RFC-036 (версия std жёстко привязана к бинарнику), раскладка в дистрибутиве — читаемое
  представление + источник резолва LSP. Если в будущем открывать — нужно пересмотреть инвариант
  версионной привязки.

### Закрытые

Следующие вопросы решены в ходе проектного обсуждения:

- ~~Возможна ли статическая линковка Z3 на Windows?~~ → **Не делаем статическую линковку, динамика
  на всех платформах** (пересмотрено 2026-09-09, оставлено)
- ~~Имя подкоманды gen-std-interfaces?~~ → **Подкоманды нет** (решение 2026-09-10: после
  формирования упаковки поверхность подкоманды лишняя; native-интерфейсные представления переводятся
  в предгенерируемые в репозитории `src/std/interfaces/` + тестовый шлагбаум для синхронизации,
  упаковка — чистое копирование)
- ~~Сохранять ли Inno Setup?~~ → **Сохраняем как Windows-визард** (дополнительный канал)
- ~~Несёт ли дистрибутив физически исходный код стандартной библиотеки?~~ → **Обязательно**
  (читаемость для пользователя по аналогии с Python `Lib/`, решение 2026-09-09)
- ~~Родные инсталляторы cargo-dist (shell/powershell/homebrew/msi/npm)?~~ → **Все отбрасываются**,
  инсталляторы — свои (допущение плоского бинарника конфликтует с bin/+lib/)
- ~~Стратегия инсталляторов?~~ → **Двухуровневая** (окончательное решение 2026-09-09): стандартный
  канал = дистрибутивный пакет и есть продукт (модель Go/Zig, распаковка + PATH); чайниковый канал —
  по образцу Rust, однострочная команда: Linux `apt` (собственный deb-репозиторий) / `curl | sh`,
  Windows `irm | iex` / Inno exe. Не делаем: MSI, родной инсталлятор cargo-dist, свой brew tap
- ~~Включать ли менеджер версий?~~ → **Обязательно, в составе системы инсталляции** (решение
  2026-09-09, пересмотр границы «отдельного RFC в далёкой перспективе» в тот же день): мотивация —
  отсутствие официального управления версиями в Python/Node привело к фрагментации экосистемы с
  pyenv/nvm/pdm
- ~~Форма менеджера версий: отдельный бинарник или подкоманда?~~ → **Разделение «парадной двери» и
  движка** (окончательное решение 2026-09-09, три итерации сходимости A→C→инверсия именования):
  частая команда `yx` = парадная дверь (маленький бинарник, встроенные команды toolchain/self),
  движок `yaoxiang-rs` = переименованный монолит `yaoxiang`; структура каталогов `versions/<ver>/` —
  версия это понятие первого уровня, каталог версии = корень распаковки дистрибутивного пакета,
  инструменты жёстко привязаны к версии (старый fmt не понимает новый синтаксис; внутренний
  `toolchains/` из ранних вариантов отменён как избыточный). Прецеденты: Go `go` как парадная
  дверь + GOTOOLCHAIN, прокси-диспетчеризация rustup
- ~~Условное выполнение extra-artifacts в cargo-dist?~~ → **Обрабатывается shell-скриптом
  `package-dist.sh` через case-ветвление**
- ~~Совместимость версий интерфейсов стандартной библиотеки?~~ → **Поставляются вместе с версией
  компилятора, в одном архиве**
