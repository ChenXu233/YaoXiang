# RFC-037: Промышленная схема дистрибуции — упаковка компилятора/тулчейна на базе cargo-dist

> Данный RFC дополняет
> [RFC-014b: Система сборки и дистрибуция бинарников](../accepted/014b-build-system.md). RFC-014b
> определяет, как **менеджер пакетов YaoXiang** собирает и распространяет сторонние пакеты; данный
> RFC определяет, как упаковывается и распространяется **сам компилятор/тулчейн YaoXiang**.

## Резюме

Использовать `cargo-dist` (инструмент дистрибуции бинарников из экосистемы Rust) для оркестрации
кроссплатформенной сборки; собственные скрипты отвечают за структуру дистрибутивного пакета. Два
ключевых обязательства: дистрибутивный пакет **физически содержит каталог исходников стандартной
библиотеки** (пользователь читает его так же, как Python `Lib/`), а динамически линкуемая Z3
поставляется в комплекте на всех платформах. Модель команд — **разделение фасада и ядра**:
повседневная команда `yx` (лёгкий фасад со встроенным управлением версиями — аналог rustup/Go
GOTOOLCHAIN), ядро `yaoxiang-rs` (переименование существующего монолита `yaoxiang`), что позволяет
избежать фрагментации экосистемы по типу Python/Node, где постфактум появляются nvm/pdm. Установка
двухуровневая: стандартный канал выравнен с Go/Zig — **дистрибутивный пакет и есть продукт**,
распаковка + PATH; «глупый» канал — установка одной командой (Linux `apt` / `curl | sh`, Windows
`irm | iex` / Inno exe визард). Решаются проблемы отсутствия `libz3.dll`, недоступности стандартной
библиотеки для пользователя, повторного сопровождения CI-скриптов и т.п.

## Мотивация

### Зачем нужна эта функциональность?

Скачавший YaoXiang пользователь должен иметь возможность **сразу начать работать**, без каких-либо
дополнительных шагов; стандартная библиотека должна быть **напрямую читаема** для пользователя, а не
быть чёрным ящиком внутри бинарника.

### Текущие проблемы

#### Проблема 1: пользователь Windows не может запустить после скачивания

Текущий Release загружает только `yaoxiang.exe`, но `libz3.dll` не упаковывается. Двойной клик в
Windows приводит к ошибке:

```
The code execution cannot proceed because libz3.dll was not found.
```

Это **блокирующий баг** — пользователь не может пройти даже первый шаг.

#### Проблема 2: Release-артефакт — только одиночный exe, стандартная библиотека недоступна пользователю

Ситуация — тройной разрыв:

- Release-артефакт содержит лишь голый бинарник, стандартная библиотека не поставляется с
  дистрибутивом
- Цепочка поиска интерфейсных файлов LSP фактически разорвана: при вызове `find_std_interface_file`
  не передаётся каталог проекта (ищется только в глобальном `~/.yaoxiang/std/`, но никто его не
  заполняет); `package init` пишет в `.yaoxiang/std`, что не входит в цепочку поиска
- Исходники стандартной библиотеки (уровень `.yx`) и представление интерфейсов (уровень native)
  полностью скрыты от пользователя

Индустриальный подход: пользователь открывает каталог стандартной библиотеки и читает исходники
напрямую, как Python `Lib/` — **физическое присутствие каталога std в дистрибутивном пакете является
жёстким требованием данного решения** (уже решено).

#### Проблема 3: повторное сопровождение ручных CI-скриптов

В настоящее время поддерживается несколько сборочных пайплайнов:

| Файл                      | Ответственность           | Строк          |
| ------------------------- | ------------------------- | -------------- |
| `_build-platforms.yml`    | Кроссплатформенная сборка | ~255           |
| `release.yml`             | Выпуск версии             | ~189           |
| `nightly.yml`             | Ежедневная сборка         | ~173           |
| `scripts/build/setup.iss` | Inno Setup инсталлятор    | ~250           |
| **Итого**                 |                           | **~870 строк** |

Большая часть — повторяющаяся (установка Rust → кеш → сборка → переименование → загрузка), и для
каждой платформы пишется заново.

#### Проблема 4: жёстко зашитый номер версии в Inno Setup

В `setup.iss` параметр `MyAppVersion` захардкожен как `0.7.0`, при сборке подменяется через `sed`.
Рано или поздно это приведёт к провалу.

#### Проблема 5: размытость границ с RFC-014b

RFC-014b определяет «механизм сборки и дистрибуции пакетов YaoXiang» (т.е. конфигурацию `[build]` и
`[binaries]` в `yaoxiang.toml`), но **не покрывает вопрос «как публикуется сам компилятор
YaoXiang»**. Данный RFC заполняет этот пробел.

## Предложение

### Основной дизайн

cargo-dist берёт на себя только **уровень оркестрации сборки**; структура пакета и инсталляторы —
собственные. Разделение ответственности:

```
Обязанности cargo-dist (уровень оркестрации сборки):
  ├── Кроссплатформенная компиляция (5 target)
  └── Генерация архивов и контрольных сумм
  (Родные инсталляторы и npm wrapper отброшены — их допущение
   о плоском бинарнике конфликтует со структурой bin/+lib/)

build.rs продолжает отвечать за:
  └── Загрузку/линковку Z3 (динамика на всех платформах + rpath)

Собственные скрипты YaoXiang:
  ├── package-dist.sh — реорганизация структуры пакета (bin/ + lib/),
  │   включение общих библиотек, заполнение каталога std (предгенерируемые
  │   интерфейсные представления из репозитория + исходники уровня .yx),
  │   пересчёт контрольных сумм
  └── Inno Setup — Windows-визард установки (имеющийся актив;
       разворачивает полную структуру каталогов)

Модель команд (разделение фасада и ядра):
  ├── yx — фасад (новый малый crate): разбор версий + диспетчеризация;
  │   только toolchain/self сохраняются как глаголы, остальное — прозрачная передача
  └── yaoxiang-rs — ядро (переименование существующего монолита yaoxiang):
      подкоманды compile/run/package/fmt/lsp

Способы установки (двухуровневые):
  ├── Стандартный канал (модель Go/Zig): дистрибутивный пакет и есть продукт,
  │   распаковка + PATH
  └── «Глупый» канал (модель Rust): установка одной командой + управление
      версиями (встроено в фасад yx)
      ├── Linux: apt (собственный deb-репозиторий, системная установка)
      │           / curl … | sh (установка всего пакета одной командой)
      ├── Windows: irm … | iex (установка всего пакета одной командой)
      │            / Inno Setup визард (имеющийся актив, системная установка)
      └── macOS: curl … | sh (brew оставлен на усмотрение homebrew-core сообщества)
```

### Структура каталогов дистрибутива (решено: физическое наличие исходников стандартной библиотеки)

Пользователь должен иметь возможность открыть каталог стандартной библиотеки и читать исходники, как
Python `Lib/` — наличие каталога std в дистрибутиве является жёстким требованием, а не деталью
упаковки. С Z3 аналогично: как внешняя система, она естественно распространяется через каталог общих
библиотек — запихнуть `.so` внутрь exe или положить рядом с динамической линковкой в плане «всё
равно идёт с пакетом» эквивалентно, причём второй вариант сохраняет заменяемость.

Дистрибутивный пакет для каждой платформы реорганизуется скриптом `package-dist.sh` после сборки
cargo-dist:

```
yaoxiang-{version}-{target}.tar.gz / .zip     (портативный, готов к использованию:
                                                после распаковки запускается прямо из bin/)
├── bin/
│   ├── yx                            # фасад (или yx.exe)
│   ├── yaoxiang-rs                   # ядро (или yaoxiang-rs.exe)
│   └── libz3.so / libz3.dylib / libz3.dll
├── lib/
│   └── yaoxiang/
│       └── std/                      # пользователь может читать напрямую (модель Python Lib/)
│           ├── io.yx                 # native-модули: предгенерируемые интерфейсные представления
│           ├── math.yx
│           ├── test.yx               # уровень .yx: реальные исходники из репозитория копируются как есть
│           └── ...
├── README.md
└── LICENSE
```

Установка = распаковка в любой каталог + добавление `bin/` в PATH (модель Go с `/usr/local/go/bin`;
распаковка в `~/.yaoxiang/` — типичный выбор). На Windows ту же работу делает Inno Setup визард (по
умолчанию Program Files). При портативной распаковке фасад `yx` без состояния `~/.yaoxiang`
откатывается на соседний `yaoxiang-rs` — поведение совпадает с управляемой установкой; rpath ядра и
относительный поиск std относительно exe не меняются из-за наличия фасада.

### Поддержка платформ

| Платформа      | target triple               | Примечание            |
| -------------- | --------------------------- | --------------------- |
| Linux x86_64   | `x86_64-unknown-linux-gnu`  | Основная              |
| Linux ARM64    | `aarch64-unknown-linux-gnu` | Кросс-компиляция в CI |
| macOS x86_64   | `x86_64-apple-darwin`       | Intel Mac             |
| macOS ARM64    | `aarch64-apple-darwin`      | Apple Silicon         |
| Windows x86_64 | `x86_64-pc-windows-msvc`    | Основная              |

Всего 5 target. Windows ARM64 временно не поддерживается (у Z3 нет официальных прекомпилированных
пакетов для ARM64).

### Стратегия распространения Z3

**Динамическая линковка на всех платформах** (подтверждено пересмотром):

| Платформа | Изменение                            | Результат     |
| --------- | ------------------------------------ | ------------- |
| Linux     | **Была статика → стала динамика**    | `libz3.so`    |
| macOS     | **Была статика → стала динамика**    | `libz3.dylib` |
| Windows   | Без изменений                        | `libz3.dll`   |
| wasm32    | Без изменений (статическая линковка) | Встроен `.a`  |

Обоснование:

- **Единообразие** — одинаковое поведение на трёх платформах, без особых случаев
- **Это внешняя библиотека, её и нужно распространять как общую.** Python
  (`python3.dll`+`DLLs/lib*.dll`), Node (`node`+`lib/`) делают именно так
- **Пользователю не нужно ждать новой версии компилятора для обновления Z3** — достаточно заменить
  `.so`/`.dylib`/`.dll`
- **Меньший размер бинарника** — Z3 не мала, статическая линковка раздула бы exe на несколько
  мегабайт

У динамической линковки есть **необходимое сопровождение**: динамический линковщик Linux/macOS по
умолчанию не ищет в каталоге бинарника, нужно инжектировать rpath, иначе «распаковал и работай» не
состоится (Windows по умолчанию ищет в каталоге exe, обработка не нужна). Соответствующее изменение
`build.rs`:

```rust
// Унифицированная динамическая линковка + rpath
fn link_z3(z3_dir: &Path) {
    let target_os = env::var("CARGO_CFG_TARGET_OS").unwrap();
    // Структура дистрибутива Z3 неоднородна, двойной поиск по lib/bin
    println!("cargo:rustc-link-search=native={}", lib_dir.display());
    // RFC-037: динамическая линковка на всех платформах. Общая библиотека
    // поставляется в bin/ дистрибутива, пользователь может заменить её для обновления Z3
    if target_os == "windows" {
        // MSVC import lib именуется как libz3.lib
        println!("cargo:rustc-link-lib=libz3");
    } else {
        println!("cargo:rustc-link-lib=z3");
        // Динамический линковщик по умолчанию не ищет в каталоге бинарника,
        // нужно инжектировать rpath, иначе «распаковал и работай» не сработает
        // (в дистрибутиве exe и libz3 лежат вместе в bin/; Windows по умолчанию
        // ищет в каталоге exe, обработка не нужна)
        match target_os.as_str() {
            "linux" => println!("cargo:rustc-link-arg=-Wl,-rpath,$ORIGIN"),
            "macos" => println!("cargo:rustc-link-arg=-Wl,-rpath,@loader_path"),
            _ => {}
        }
        let cxx = if target_os == "macos" {
            "c++".to_string()
        } else {
            env::var("CXXSTDLIB").unwrap_or_else(|_| "stdc++".into())
        };
        println!("cargo:rustc-link-lib={}", cxx);
    }
}
```

**«Полная статическая линковка Z3» не ставится целью.** Это не устранение особого случая, а
устранение правильного случая неправильным способом. Общая библиотека — нормальный способ
распространения внешней библиотеки.

### Поддержка инсталляторов

Сравнение способов распространения основных языковых тулчейнов (исследование 2026-09):

| Язык     | Официальный дистрибутив       | Официальный способ установки                              | Кто поддерживает инсталлятор          |
| -------- | ----------------------------- | --------------------------------------------------------- | ------------------------------------- |
| Go       | `go/{bin,src,pkg}` tarball    | Официальная документация = «скачать → распаковать → PATH» | Нет (brew/apt — сообщество)           |
| Zig      | `zig/{bin,lib/std}` tarball   | То же, без официального скрипта установки                 | Нет (homebrew-core сообщество)        |
| Node     | `{bin,lib,include}` tarball   | tar + официальные pkg/msi                                 | Команда пишет сама                    |
| Rust     | Многокомпонентный tarball     | rustup                                                    | Команда пишет сама                    |
| Crystal  | `{bin,src,embedded}` tarball  | deb/rpm/tar                                               | Команда + brew сообщество             |
| Deno/Bun | Одиночный бинарник zip        | Официальный curl-скрипт                                   | Команда пишет сама (скрипт минимален) |
| Gleam    | cargo-dist одиночный бинарник | Скрипт, генерируемый cargo-dist                           | cargo-dist                            |

Три закономерности:

- **Ни один многофайловый тулчейн не использует сторонний генератор для инсталляторов** —
  инсталляторы cargo-dist рассчитаны только на сценарий с одиночным бинарником (Gleam подходит
  именно потому, что это единый Rust-бинарник без внешних зависимостей)
- Простейшая модель — **«дистрибутивный пакет и есть продукт» у Go/Zig**: официальная инструкция —
  распаковать + PATH, ноль кода инсталлятора; дистрибутив содержит читаемые исходники std (Go
  `src/`, Zig `lib/std/`, Crystal `src/`) — это норма
- Те, кому нужна установка через curl одной строкой (Deno/Bun/rustup), пишут **собственные скрипты**
  и почти их не развивают; формулы brew всегда поддерживаются сообществом в homebrew-core, языковая
  команда не делает свой tap (команда Crystal прямо говорит, что formula — дело сообщества)

YaoXiang использует двухуровневую модель:

| Канал                                                      | Уровень  | Статус | Описание                                                                                                                                   |
| ---------------------------------------------------------- | -------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| zip / tar.gz                                               | Стандарт | ✅     | Распаковал и работай (rpath + общая библиотека в том же каталоге), extract + PATH — официальная инструкция                                 |
| `yx` (фасад, встроенное управление версиями)               | «Глупый» | ✅     | Аналог rustup/Go GOTOOLCHAIN: установка/переключение/обновление нескольких версий + pin проекта                                            |
| `curl ... \| sh` (install.sh)                              | «Глупый» | ✅     | Linux / macOS: скачать реорганизованный пакет, распаковать в `versions/`, `bin/yx` встаёт в корень установки, записать версию по умолчанию |
| `irm ... \| iex` (install.ps1)                             | «Глупый» | ✅     | Windows: та же логика                                                                                                                      |
| `apt install yaoxiang`                                     | «Глупый» | ✅     | `.deb` (amd64/arm64) + статический apt-репозиторий на GitHub Pages; системная установка, обновление через `apt upgrade`                    |
| Inno Setup exe                                             | «Глупый» | ✅     | Windows-визард (имеющийся актив), системная установка, разворачивает полную структуру bin/+lib/                                            |
| winget / `.rpm` / homebrew-core / npm                      | —        | ⏸      | Возможное долевое участие: winget и brew-core поддерживаются сообществом, rpm аналогичен deb                                               |
| MSI / родной инсталлятор cargo-dist / собственный brew tap | —        | ❌     | См. «Альтернативы»                                                                                                                         |

**«Глупый» канал ориентируется на Rust, управление версиями встроено в фасад.** Разбиение Rust:
«скрипт-загрузчик (sh.rustup.rs) → rustup → пакет тулчейна», rustup сразу берёт на себя несколько
версий, переключение, обновления; официальные инсталляторы Python/Node этого не делают, и экосистема
постфактум выращивает pyenv/nvm/pdm, каждый по-своему. YaoXiang использует **разделение фасада и
ядра** (Go с фасадом `go` + GOTOOLCHAIN, rustup с прокси-диспетчеризацией — изоморфные формы у
обоих): повседневная команда — `yx`, ядро — `yaoxiang-rs` —

```
~/.yaoxiang/
├── bin/yx                  # фасад: малый бинарник, разбор версий + диспетчеризация
│                           # (pin проекта > по умолчанию > соседнее ядро)
├── settings.toml           # версия по умолчанию, зеркала
└── versions/               # версия — понятие первого уровня; <ver>/ — корень распаковки
                            # дистрибутива этой версии
    └── 0.7.14/
        ├── bin/
        │   ├── yaoxiang-rs      # ядро: подкоманды compile/run/package/fmt/lsp
        │   └── libz3.so
        └── lib/yaoxiang/std/
```

- Корень установки `~/.yaoxiang/` выровнен с индустриальной практикой (pyenv `~/.pyenv`, nvm
  `~/.nvm`, deno `~/.deno`, bun `~/.bun`, volta `~/.volta` — все с одним корнем; у rustup
  `~/.cargo`+`~/.rustup` — двойной корень из-за того, что cargo появился раньше rustup, историческое
  наследие, не повторяем), и `~/.yaoxiang` уже существующее пространство имён в кодовой базе
  (глобальный fallback-слот std); поддерживается переопределение через переменную окружения
  `YAOXIANG_HOME` (прецеденты RUSTUP_HOME / DENO_INSTALL, обслуживает CI и контейнерные сценарии);
  на Windows — `%USERPROFILE%\.yaoxiang`
- **Каталог версии = корень распаковки дистрибутива**: `versions/<ver>/` полностью изоморфен
  переносной распаковке и дереву deb-установки — установка версии это распаковка дистрибутива,
  нулевое структурное расхождение между тремя каналами
- Командный интерфейс (аналог rustup): `yx toolchain install / default / update / list / uninstall`,
  включая `yx self update`; остальные глаголы прозрачно передаются ядру
- **Блокировка версий — структурная гарантия**: fmt и подобные инструменты эволюционируют вместе с
  синтаксисом той же версии (старый fmt не понимает новый синтаксис), разбор версий выполняется один
  раз на фасаде, переключается вся группа — не существует комбинации «новое ядро со старым fmt»;
  если в будущем fmt/LSP выделяются в отдельные бинарники, они также ложатся в `bin/` той же версии
- Pin на уровне проекта: `yx-toolchain.toml` (прецедент rust-toolchain.toml, следует за именем
  команды; не в `yaoxiang.toml` — манифест пакета не должен навязывать версию тулчейна потребителям
  библиотек)
- Точка входа для загрузки (`curl | sh` / `irm | iex`) — однократная установка всего актуального
  stable-пакета: распаковка в `versions/`, `bin/yx` встаёт в корень установки, запись
  `settings.toml` с версией по умолчанию (эквивалентная сходимость разбиения «rustup-загрузчик
  устанавливает менеджер» — фасад и ядро в одном пакете, двух шагов не нужно)
- Зеркала настраиваются (settings.toml), продолжает учитываться ситуация с сетью для китайских
  пользователей (та же проблема, что и с загрузкой Z3)
- **Управление версиями не нарушает инвариант самодостаточности**: каждая версия — это полное дерево
  дистрибутива, rpath и относительный поиск std относительно exe самосогласованы внутри дерева,
  фасад только диспетчеризирует и не меняет структуру

`.deb` и Inno — **каналы системной установки** (root / Program Files, одна версия, обновляется через
`apt upgrade` / панель управления), обслуживают серверы, CI, сценарии чистых новичков;
сосуществование с менеджером — через порядок PATH (прецедент: rustc из apt и rustup сосуществуют).
Все каналы используют одно и то же дерево продуктов.

Раскладка `.deb` повторно использует то же дерево каталогов: `/usr/lib/yaoxiang/` (полное дерево
дистрибутива: `bin/{yx,yaoxiang-rs,libz3.so}` + `lib/yaoxiang/std/`) + символическая ссылка
`/usr/bin/yx` → `/usr/lib/yaoxiang/bin/yx` — `$ORIGIN` вычисляется по **реальному пути после резолва
ссылки**, после подмены попадает в `libz3.so` того же каталога, изоморфно структуре распакованного
пакета. Полное брендовое имя остаётся в имени пакета и названии продукта (`apt install yaoxiang`,
продукт Inno YaoXiang), командный интерфейс унифицирован `yx` — по аналогии с Go: пакет `golang-go`,
команда `go`. Статический apt-репозиторий хостится на GitHub Pages (метаданные
Packages/Release/InRelease с GPG-подписью, публикуются release CI); в перспективе возможно включение
в официальные репозитории Debian/Ubuntu (долгий цикл, отставание версий, не основной путь).

### Каталог стандартной библиотеки

Содержимое `lib/yaoxiang/std/` полностью берётся из статических файлов репозитория, упаковка —
**чистое копирование**, без точек генерации в runtime:

| Уровень                           | Источник                                                                            | Природа                                                    |
| --------------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| native-модули (io/math/…)         | Репозиторий `src/std/interfaces/*.yx` — предгенерируемые интерфейсные представления | Представление сигнатур интерфейса (реализация в бинарнике) |
| Модули уровня .yx (test/… растут) | Репозиторий `src/std/*.yx` — копируются как есть                                    | Реальные исходники                                         |

Предгенерируемые представления выводятся из `StdModule::exports()` (`generate_all_interfaces()` в
`src/std/gen_interfaces.rs`), **подкоманда генерации в runtime не предусматривается** (решено
2026-09-10: после формирования упаковки подкоманда — лишняя поверхность интерфейса). Синхронизация
по схеме «генерат в репозиторий + тестовый гард» (аналог кодовой таблицы из RFC-013):
`test_committed_interface_files_match_generation` побайтно сравнивает предгенерированные файлы с
текущей генерацией, расхождение — красный тест; исправление через точку входа bless
`cargo test update_committed_interface_files -- --ignored`. Логика генерации зависит от внутренней
реализации `StdModule` в crate, её нельзя опустить в build.rs, поэтому гард стоит на уровне тестов,
а не сборки.

**Цепочка поиска в runtime** — `find_std_interface_file` дополняется уровнем относительного поиска
относительно exe:

1. Проект `.yaoxiang/vendor/std/<name>.yx` (переопределение проектом, существующее)
2. **Каталог exe `../lib/yaoxiang/std/<name>.yx` (новое)**: переносная распаковка, управляемая
   установка (`versions/<ver>/`), deb-установка — все попадают
3. `~/.yaoxiang/std/<name>.yx` (глобальный fallback, оставлен как слот для ручного переопределения)

Сейчас эта цепочка практически разорвана (вызов LSP не передаёт каталог проекта, `package init`
пишет в `.yaoxiang/std`, чего нет в цепочке), в этом RFC она заодно чинится, и вывод `package init`
унифицируется в `.yaoxiang/vendor/std` (соответствует каталогу vendor менеджера пакетов).

**Авторитет компиляции не меняется**: уровень `.yx` по-прежнему встраивается через `include_str!`
(инвариант RFC-036 «std жёстко привязан к версии бинарника» сохраняется). Позиционирование каталога
дистрибутива — **читаемое представление + источник для LSP-резолва**, а не вход компиляции — ручное
изменение пользователем `.yx` в каталоге дистрибутива не подхватывается компилятором (открывать ли
Python-семантику «правка `Lib/` = вступает в силу» — см. открытые вопросы).

### Сборка Wasm

**Остаётся отдельной, не переносится в cargo-dist.**

cargo-dist занимается «доставкой компилятора пользователю», wasm — «онлайн-playground, встраиваемый
в сайт документации» — два совершенно разных продукта поставки.

| Аспект            | Подход                                                              |
| ----------------- | ------------------------------------------------------------------- |
| Инструмент сборки | Сохраняем `wasm-pack build`                                         |
| CI workflow       | Оставляем отдельный job `_build-wasm.yml`                           |
| Момент запуска    | Вместе с release, по тому же tag push, параллельный независимый job |
| Цель публикации   | `docs/public/wasm/` → GitHub Pages                                  |

### npm-публикация

| Пакет                  | Содержимое                       | Статус                                                                                                                                                                                                                                                                             |
| ---------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@yaoxiang/cli`        | wrapper, скачивающий дистрибутив | Отложено: npm wrapper от cargo-dist также основан на допущении плоского артефакта, отброшен вместе с инсталляторами; при необходимости npm-канала пишется собственный wrapper (скачивает реорганизованный пакет и распаковывает, та же логика, что и при распаковке для установки) |

### Интеграция с существующим процессом выпуска версий

Текущий `release.yml`: push main → check-version (пропускает, только если tag `v{version}` не
существует) → четыре ветки build / build-wasm / security / test → job release (создание tag push +
`generate-commit-list.ts` генерирует body с @mentions + загрузка артефактов).

Сгенерированный cargo-dist пайплайн — tag-driven, с собственным announce/publish, без гардов
fmt/clippy/test/audit, формат release notes не вмещает changelog по merge commit'ам. **Прямая полная
замена разобьёт существующую церемонию выпуска** (PR → CI полностью зелёный → bump → merge commit =
changelog).

Принцип интеграции: **триггер и гарды сохраняем как есть, сборку отдаём `cargo dist build`,
публикацию сохраняем как есть.**

1. check-version / security / test вместе с созданием tag переезжают в job `gate` / `security` /
   `test` / `tag` файла `dist-release.yml`, триггер остаётся push main (**tag-driven невозможно**:
   tag, push'нутый через `GITHUB_TOKEN` workflow'а, не запускает другие workflow; старый
   `release.yml` поэтому выпускал только плоские бинарники самостоятельно, удалён вместе с
   `_build-platforms.yml`, выпуск — единая точка в данном файле)
2. Сборка только после появления tag: job `plan` через dist вычисляет матрицу runner/системных
   зависимостей → `cargo dist build` (5 target) → `package-dist.sh` реорганизует для каждого target
   → job Inno Setup (берёт реорганизованный пакет Windows, собирает визард, версия через
   `/DMyAppVersion=`, без повторной компиляции) → `_build-wasm.yml` (параллельный job)
3. Job publish: `generate-commit-list.ts` генерирует body (повторное использование существующего
   скрипта) → загрузка реорганизованных пакетов + `.sha256` + `.deb` + wasm + Setup exe,
   `action-gh-release` создаёт Release собственными силами; отдельный job `publish-apt` публикует
   метаданные apt-репозитория на GitHub Pages (при отсутствии `secrets.APT_GPG_KEY` автоматически
   пропускается, не влияет на остальные каналы)
4. Перевыпуск/пересборка: `workflow_dispatch` с указанием существующего tag (тогда `gate` пропускает
   шаг создания tag)

### Nightly-публикация

cargo-dist не имеет встроенной поддержки nightly
([axodotdev#1143](https://github.com/axodotdev/cargo-dist/issues/1143), всё ещё открытый feature
request).

Сохраняем текущую схему cron + перезапись tag, часть сборки меняется с `_build-platforms.yml` на
`cargo dist build` — это по сути одна cargo-команда, вызывается напрямую в nightly.yml. Повторное
использование workflow не делаем (задуманное `uses: ./release.yml` невозможно: вызываемый должен
иметь триггер `workflow_call`, а workflow cargo-dist — tag-driven, сборка и публикация связаны):

```yaml
# nightly.yml (после миграции)
on:
  schedule:
    - cron: '17 22 * * *'
jobs:
  build: # cargo dist build + package-dist.sh (та же цепочка, что и для стабильной)
  publish: # оставлено как есть: создать/переместить nightly tag → перезаписать GitHub Pre-release
```

### Конфигурация cargo-dist (уже в репозитории как dist-workspace.toml)

```toml
[workspace]
members = ["cargo:.", "cargo:tools/yx"]

# Config for 'dist'
[dist]
# Фиксируем версию dist (синтаксис SemVer из Cargo.toml)
cargo-dist-version = "0.32.0"
ci = "github"
# Все инсталляторы собственные, cargo-dist делает только сборку + архивы + контрольные суммы
installers = []
targets = ["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "x86_64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
# Сгенерированный workflow намеренно модифицирован (реорганизация package-dist.sh +
# собственная секция publish, RFC-037), не отказываем в сборке при отклонении от шаблона generate
allow-dirty = ["ci"]
```

Это фактическая конфигурация, вендорная в репозиторий (сгенерирована `cargo dist init` и
доработана); `cargo-dist-version` зафиксирована на 0.32.0, сгенерированный workflow вендорится в
репозиторий для review, в runtime не подтягивается. Профиль сборки инжектируется init'ом в
`[profile.dist]` корневого Cargo.toml (inherits release, lto=thin), двойной бинарник попадает в
`target/<triple>/dist/` для забора скриптом реорганизации.

### package-dist.sh (уже в репозитории)

Опираемся на `scripts/release/package-dist.sh` в репозитории, основные моменты:

- Двойной бинарник берётся напрямую из каталога сборки `cargo dist build` — `target/<triple>/dist/`
  (profile=dist) — плоский одиночный архив, который сам генерирует cargo-dist, не является продуктом
  поставки, одноимённый реорганизованный пакет в `target/distrib/` перезаписывается напрямую
- Общая библиотека Z3 также берётся из каталога сборки — `build.rs` при линковке уже выбрал
  соответствующую платформе общую библиотеку и скопировал её на диск (`copy_shared_lib`),
  **единственный источник**: скрипт упаковки не знает и не должен знать версию Z3 и именование
  каталогов платформы; текст лицензии Z3 сохраняется на диск рядом с библиотекой и подхватывается
  упаковкой (обязательство MIT по дистрибуции), на стороне macOS во время упаковки install_name
  dylib приводится к `@rpath` и бинарник ad-hoc переподписывается
- Каталог std — чистое копирование: `src/std/interfaces/*.yx` (предгенерированные интерфейсные
  представления) + `src/std/*.yx` (реальные исходники уровня .yx)
- Прикладываются README/LICENSE; переупаковка (Windows zip / остальные tar.gz; трёхуровневый откат
  при отсутствии zip в Git Bash: zip → System32 bsdtar → PowerShell) и пересчёт `.sha256`
- На Linux при наличии `dpkg-deb` заодно вызывается `build-deb.sh` для получения `.deb` (дерево
  системной установки `/usr/lib/yaoxiang` + символическая ссылка `/usr/bin/yx`)

### Критерии приёмки

«Распаковал и работай» — тестируемо; готовность миграции определяется не «совпадением старого и
нового артефакта», а прохождением всех пунктов ниже:

- На чистой машине (без Rust / без Z3 / без `~/.yaoxiang`) после распаковки любого платформенного
  архива прямой запуск `bin/yaoxiang-rs --version` успешен — без `LD_LIBRARY_PATH` (rpath работает)
- Все `lib/yaoxiang/std/*.yx` в распакованном каталоге читаемы: native-модули — представления
  сигнатур интерфейсов, уровень `.yx` — реальные исходники
- В примере проекта из распакованного каталога запуск LSP даёт рабочее автодополнение /
  go-to-definition по std (относительный поиск exe работает)
- После распаковки по официальной инструкции в `/usr/local` (или `~/.yaoxiang`) и добавления в PATH
  в любом каталоге `yx --version` успешен
- `apt install yaoxiang` (собственный репозиторий) — запускается, `apt upgrade` отслеживает версию;
  `$ORIGIN` ядра под символической ссылкой `/usr/bin/yx` (вычисляется по реальному пути) попадает в
  `bin/libz3.so`
- `curl ... | sh` и `irm ... | iex` на чистой среде после выполнения — `yx` запускается, PATH
  настроен
- `yx toolchain install <ver>` / `default` / `update` работают: сосуществование нескольких версий,
  pin проекта в `yx-toolchain.toml` приоритетнее версии по умолчанию, фасад диспетчеризирует в
  правильную версию (внутри дерева версий rpath и поиск std самосогласованы, нет комбинации «новое
  ядро со старым fmt»)
- После переносной распаковки `yx` откатывается на соседний `yaoxiang-rs`, поведение совпадает с
  управляемой установкой
- После установки через Inno Setup структура каталогов полная, PATH работает, удаление возможно
- Ассеты Release полные: реорганизованные пакеты для 5 платформ + `.sha256` совпадают с фактическим
  содержимым
- Тело Release — вывод `generate-commit-list.ts` (полный changelog по merge commit'ам)
- Артефакт nightly — Pre-release, не затрагивает последний стабильный tag

## Компромиссы

### Преимущества

- **Распаковал и работай** — переносная распаковка сразу работает (rpath + общая библиотека в том же
  каталоге), инсталлятор разворачивает полную структуру каталогов
- **Стандартная библиотека читаема** — пользователь читает std как Python `Lib/` (жёсткое требование
  выполнено)
- **Снижение стоимости сопровождения** — ~600 строк ручного YAML сборки заменены на cargo-dist + ~80
  строк собственных скриптов
- **Кроссплатформенная согласованность** — динамическая линковка на всех платформах + общая
  библиотека в том же каталоге, без особых случаев
- **Двухуровневая установка** — стандартный канал с нулевым новым кодом (модель Go/Zig); «глупый»
  канал по аналогии с Rust, apt / curl / iex / exe — четыре входа с общей структурой продуктов
- **Управление версиями встроено** — фасад `yx` — аналог rustup/Go GOTOOLCHAIN, не придётся
  наверстывать фрагментацию экосистемы через pyenv/nvm/pdm постфактум, как в Python/Node; блокировка
  версий инструментов — структурная гарантия, а не договорённость

### Недостатки и риски

- **Поверхность сопровождения «глупых» каналов** — install.sh / install.ps1 (однострочные скрипты,
  почти не развиваются) + `.deb` и публикация метаданных apt-репозитория (автоматизирована release
  CI) + crate фасада `yx`
- **Переименование ядра затрагивает смежные области** — `yaoxiang` → `yaoxiang-rs` требует
  однократной миграции имён CI-артефактов, Inno, тестов и документации (выполняется в рамках фазы 5)
- **Порог входа** — команде нужно освоить конфигурацию cargo-dist
- **Риск апстрима cargo-dist** — в середине 2025 была приостановка вместе с Axo, в сентябре того же
  года оригинальный автор возобновил работу и продолжает релизы (0.29 → 0.32+); смягчается фиксацией
  `dist-version` + вендорингом генерата в репозиторий для review
- **cargo-dist без встроенной поддержки nightly** — часть публикации nightly всё ещё ручная

### Связь с RFC-014b

|                      | RFC-014b                               | RFC-037                                       |
| -------------------- | -------------------------------------- | --------------------------------------------- |
| **Область**          | Сборка и дистрибуция сторонних пакетов | Упаковка и дистрибуция самого компилятора     |
| **Инструмент**       | `yaoxiang build` / `yaoxiang publish`  | `cargo-dist` + собственные скрипты            |
| **Продукт**          | FFI-библиотеки сторонних пакетов       | Компилятор + стандартная библиотека + тулчейн |
| **Взаимоисключение** | Нет, дополняют                         | Нет, дополняют                                |

## Альтернативы

| Вариант                                          | Почему не выбран                                                                                                                                                                                                                                               |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Продолжать писать CI вручную**                 | Уже написано ~870 строк, повторяющийся труд, легко упустить DLL                                                                                                                                                                                                |
| **Писать свой инструмент упаковки**              | Не изобретать колесо, cargo-dist уже зрелый                                                                                                                                                                                                                    |
| **Только tar.gz, без инсталляторов**             | Единственный официальный канал — распаковка + PATH; Inno только для Windows-привычки визарда (по решению для китайских пользователей оставлено)                                                                                                                |
| **Распространение через Docker**                 | Компилятор и языковой тулчейн требуют нативных бинарников, не контейнерный сценарий                                                                                                                                                                            |
| **Собственный Homebrew tap**                     | tap всегда поддерживается сообществом (homebrew-core), собственный — преждевременная потребность; вход macOS для «глупого» канала — curl-скрипт                                                                                                                |
| **Отдельный менеджер `yaoxiangup`**              | Прецедент rustup в чистом виде, выполнимо; но создаёт второй пользовательский глагол и порождает симметричный вопрос «а менеджер пакетов/fmt тоже должен быть отдельным?» — разделение фасада и ядра снимает оба вопроса (отвергнуто на обсуждении 2026-09-09) |
| **Только самообновление, без нескольких версий** | Самообновление одной версии не покрывает потребность в разных версиях для разных проектов; в Python/Node нет официального управления версиями, экосистема вынуждена выращивать pyenv/nvm/pdm — решено встроить (2026-09-09)                                    |
| **Полная статическая линковка Z3**               | Решено отвергнуть — для внешней системы каталожное распространение через общие библиотеки естественно; запихнуть в exe и положить рядом в плане «всё равно идёт с пакетом» эквивалентно, при этом теряется заменяемость                                        |
| **Удалить Inno Setup**                           | Решено отвергнуть — оставлен как Windows-визард (дополнительный канал)                                                                                                                                                                                         |
| **Родные инсталляторы cargo-dist**               | Допущение плоского бинарника конфликтует со структурой bin/+lib/, после установки не хватает библиотек                                                                                                                                                         |
| **Собственный WiX/MSI**                          | Без генератора cargo-dist стоимость выше, чем уже покрытое Inno                                                                                                                                                                                                |

## Стратегия реализации

### Фаза 1: изменения на стороне языка (P0)

1. `build.rs`: унифицированная динамическая линковка + link-arg для rpath на всех платформах;
   `copy_dll()` расширяется до `copy_shared_lib()` (so/dylib/dll)
2. Предгенерация native-интерфейсов в репозитории (`src/std/interfaces/`), тестовый гард
   обеспечивает синхронизацию с `StdModule::exports()` (подкоманда gen-std решено отменить)
3. В `find_std_interface_file` добавляется ветвь относительного поиска относительно exe; вывод
   `package init` унифицируется в `.yaoxiang/vendor/std`

### Фаза 2: подключение cargo-dist (P0)

1. Прогнать `cargo dist init` для генерации начальной конфигурации (`installers = []`, фиксация
   dist-version)
2. Написать `package-dist.sh` (реорганизация + копирование исходников .yx + пересчёт контрольных
   сумм)
3. `dist-release.yml` несёт всё: push main → gate версии → гарды (audit / fmt / clippy / test) →
   создание tag → dist build → реорганизация → wasm параллельно → собственные publish + apt;
   `release.yml` и `_build-platforms.yml` удаляются
4. Параллельный прогон старого и нового пайплайнов, пошаговая проверка по критериям приёмки

### Фаза 3: вывод старого CI (P1)

1. `_build-platforms.yml` и `release.yml` удаляются (единая точка выпуска: `dist-release.yml`)
2. Сборочная часть `nightly.yml` заменяется на `cargo dist build`
3. `setup.iss` подключается к новой структуре продуктов (Inno узаконивается; версия инжектируется из
   Cargo.toml, подмена через sed ликвидируется)

### Фаза 4: «глупые» каналы (P2)

1. `install.sh` / `install.ps1` (определение платформы → скачивание актуального реорганизованного
   пакета → распаковка в `versions/` → `bin/yx` встаёт в корень установки → запись `settings.toml` с
   версией по умолчанию → подсказка/запись PATH; вместе с фазой 5, единым шагом к финальному
   состоянию)
2. Упаковка `.deb` (повторное использование того же дерева каталогов из `package-dist.sh` +
   символическая ссылка `/usr/bin`) + статический apt-репозиторий на GitHub Pages (метаданные с
   GPG-подписью, публикуются release CI)

### Фаза 5: фасад yx и переименование ядра (P2)

1. Переименование существующего монолита в `yaoxiang-rs` (CI-артефакты, Inno, тесты и документация —
   полный проход, однократная миграция)
2. Новый малый crate `yx` (член workspace): разбор версий, скачивание release-артефактов, распаковка
   tar/zip, settings.toml, диспетчеризация (только toolchain/self сохраняются как глаголы, остальное
   — прозрачная передача, ручная диспетчеризация без clap для гарантии побайтовой пересылки
   аргументов); индекс версий — GitHub Releases latest API (зеркало — префиксная склейка в стиле
   ghproxy); имя команды `yx` проверено на коллизии (в основных дистрибутивах/Homebrew нет
   распространённой команды с таким именем, только одна малоизвестная утилита использует yx как
   алиас)
3. `yx toolchain install/default/update/list/uninstall` + pin проекта в `yx-toolchain.toml` +
   зеркала + `yx self update`
4. Загрузочные скрипты: `curl | sh` / `irm | iex` → скачивание реорганизованного пакета с
   однократной установкой фасада и stable по умолчанию (вместе с фазой 4 как финальное состояние)

### Фаза 6: опциональное долевое участие (всё неблокирующее)

1. Сабмит в winget (указывает на Inno exe, поддерживается сообществом, симметрично модели
   homebrew-core)
2. `.rpm` (для пользователей dnf, аналогично `.deb`)
3. Homebrew: после достижения порога известности для допуска в homebrew-core — сообщество подаёт
   формулу
4. npm `@yaoxiang/cli` — собственный wrapper (имя сейчас свободно)

## Открытые вопросы

### Нерешённые

- **Предоставлять ли уровню .yx Python-семантику «ручное изменение каталога дистрибутива =
  подхватывается компиляцией»?** По умолчанию нет — авторитет компиляции остаётся встроенным через
  RFC-036 (std жёстко привязан к версии бинарника), каталог дистрибутива — читаемое представление +
  источник для LSP-резолва. В случае открытия в будущем потребуется пересмотр инварианта привязки
  версий.

### Закрытые

Следующие вопросы решены в ходе обсуждения дизайна:

- ~~Возможность статической линковки Z3 на Windows?~~ → **Статическую линковку не делаем, динамика
  на всех платформах** (подтверждено пересмотром 2026-09-09)
- ~~Имя подкоманды gen-std-interfaces?~~ → **Подкоманду не делаем** (решено 2026-09-10: после
  формирования упаковки подкоманда — лишняя поверхность; native-интерфейсы переводятся на
  предгенерацию в репозитории `src/std/interfaces/` + тестовый гард синхронизации, упаковка — чистое
  копирование)
- ~~Сохранять ли Inno Setup?~~ → **Сохраняется как Windows-визард (дополнительный канал)**
- ~~Физически ли дистрибутив содержит исходники стандартной библиотеки?~~ → **Обязательно**
  (читаемость как у Python `Lib/`, решено 2026-09-09)
- ~~Родные инсталляторы cargo-dist (shell/powershell/homebrew/msi/npm)?~~ → **Все отбрасываются**,
  инсталляторы собственные (допущение плоского бинарника конфликтует со структурой bin/+lib/)
- ~~Стратегия инсталляторов?~~ → **Двухуровневая** (окончательное решение 2026-09-09): стандартный
  канал = дистрибутивный пакет и есть продукт (модель Go/Zig, распаковка + PATH); «глупый» канал по
  аналогии с Rust, установка одной командой — Linux `apt` (собственный deb-репозиторий) /
  `curl | sh`, Windows `irm | iex` / Inno exe. Не делаем: MSI, родные инсталляторы cargo-dist,
  собственный brew tap
- ~~Включать ли менеджер версий?~~ → **Обязательно, часть системы инсталляции** (решено 2026-09-09,
  пересмотр границы «отдельного RFC в перспективе» от того же дня): мотивация — отсутствие
  официального управления версиями в Python/Node ведёт к фрагментации экосистемы через pyenv/nvm/pdm
- ~~Форма менеджера версий: отдельный бинарник или подкоманда?~~ → **Разделение фасада и ядра**
  (окончательное решение 2026-09-09, трёхступенчатая сходимость A→C→обращение имён): повседневная
  команда `yx` = фасад (малый бинарник, встроенные глаголы toolchain/self), ядро `yaoxiang-rs` =
  переименование существующего монолита `yaoxiang`; структура каталогов `versions/<ver>/` — версия —
  понятие первого уровня, каталог версии — корень распаковки дистрибутива, инструменты блокируются
  версией целиком (старый fmt не понимает новый синтаксис; задуманный внутренний `toolchains/`
  отменён из-за избыточности). Прецеденты: Go с фасадом `go` + GOTOOLCHAIN, прокси-диспетчеризация
  rustup
- ~~Условное выполнение extra-artifacts в cargo-dist?~~ → **Обрабатывается скриптом
  `package-dist.sh` через case-ветвления в shell**
- ~~Совместимость версий интерфейсов стандартной библиотеки?~~ → **Поставляется вместе с версией
  компилятора, в одном архиве**
