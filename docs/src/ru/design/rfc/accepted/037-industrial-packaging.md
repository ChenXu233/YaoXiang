# RFC-037: Промышленная схема распространения — упаковка компилятора/инструментария на основе cargo-dist

> Настоящий RFC дополняет
> [RFC-014b: Система сборки и распространения бинарных файлов](../review/014b-build-system.md).
> RFC-014b определяет, как **менеджер пакетов YaoXiang** собирает и распространяет сторонние пакеты;
> настоящий RFC определяет, как **сам компилятор/инструментарий YaoXiang** упаковывается и
> распространяется.

## Резюме

Использовать `cargo-dist` (инструмент распространения бинарных файлов из экосистемы Rust) для
оркестрации кроссплатформенной сборки, при этом собственные скрипты отвечают за структуру
дистрибутива. Два ключевых обязательства: дистрибутив **физически содержит каталог исходников
стандартной библиотеки** (пользователь читает его напрямую, как каталог `Lib/` в Python), и
динамически линкуемая разделяемая библиотека Z3 для всех платформ поставляется в комплекте. Модель
команд строится на **разделении фасада и движка**: повседневная команда `yx` (маленький фасад со
встроенным управлением версиями — аналог rustup/Go GOTOOLCHAIN), движок `yaoxiang-rs` (текущий
монолит `yaoxiang`, переименованный), что позволяет избежать фрагментации экосистемы на манер
Python/Node, где事后 (post factum) приходится доставлять nvm/pdm. Установка двухуровневая:
стандартный канал выравнен по Go/Zig — **дистрибутив и есть продукт**, распаковка + PATH; канал для
чайников — установка одной командой (Linux `apt` / `curl | sh`, Windows `irm | iex` / мастер Inno
exe). Решает проблемы отсутствия `libz3.dll`, недоступности стандартной библиотеки для пользователя,
дублирования сценариев CI и т. д.

## Мотивация

### Зачем нужна эта возможность?

Пользователь, скачавший YaoXiang, должен иметь возможность работать **прямо из коробки**, без
каких-либо дополнительных шагов; стандартная библиотека должна быть **напрямую читаема** для
пользователя, а не скрыта в чёрном ящике бинарника.

### Текущие проблемы

#### Проблема 1: Пользователи Windows не могут запустить после скачивания

Текущий релиз содержит только `yaoxiang.exe`, но `libz3.dll` не включён в пакет. Двойной клик в
Windows приводит к ошибке:

```
The code execution cannot proceed because libz3.dll was not found.
```

Это **критический баг** — пользователь не может пройти даже первый шаг.

#### Проблема 2: Артефакт релиза — только одиночный exe, стандартная библиотека недоступна пользователю

Текущая ситуация — тройной разрыв:

- Артефакт релиза содержит только голый бинарник, стандартная библиотека не поставляется
- Цепочка поиска файлов интерфейсов в LSP почти не работает: при вызове `find_std_interface_file` не
  передаётся каталог проекта (ищется только глобально в `~/.yaoxiang/std/`, а никто его не
  заполняет); `package init` записывает в `.yaoxiang/std`, которого нет в цепочке поиска
- Исходники стандартной библиотеки (слой `.yx`) и представления интерфейсов (нативный слой) — полный
  чёрный ящик для пользователя

Индустриальный подход: пользователь открывает каталог стандартной библиотеки и читает исходники
напрямую, как Python `Lib/` — **физическое наличие каталога std в дистрибутиве является жёстким
требованием настоящей схемы** (решено).

#### Проблема 3: Дублирование рукописных сценариев CI

В настоящий момент поддерживается несколько сборочных конвейеров:

| Файл                      | Назначение                | Строк    |
| ------------------------- | ------------------------- | -------- |
| `_build-platforms.yml`    | Кроссплатформенная сборка | ~255     |
| `release.yml`             | Публикация версий         | ~189     |
| `nightly.yml`             | Ежедневные сборки         | ~173     |
| `scripts/build/setup.iss` | Установщик Inno Setup     | ~250     |
| **Итого**                 |                           | **~870** |

Бо́льшая часть — дублирование (установка Rust → кеширование → сборка → переименование → загрузка),
для каждой платформы приходится писать заново.

#### Проблема 4: Жёстко зашитый номер версии в Inno Setup

В `setup.iss` поле `MyAppVersion` зашито как `0.7.0`, при сборке подменяется через `sed`. Рано или
поздно это выстрелит.

#### Проблема 5: Размытие границ с RFC-014b

RFC-014b определяет «механизм сборки и распространения пакетов YaoXiang» (то есть секции `[build]` и
`[binaries]` в `yaoxiang.toml`), но **не покрывает то, как публикуется сам компилятор YaoXiang**.
Настоящий RFC заполняет этот пробел.

## Предложение

### Основной дизайн

cargo-dist берёт на себя только **оркестрацию сборки**; структура пакета и установщики —
собственные. Разделение ответственности:

```
Обязанности cargo-dist (оркестрация сборки):
  ├── Кроссплатформенная компиляция (5 target)
  └── Генерация архивов и контрольных сумм
  (Родные установщики и npm-обёртки отброшены — их предположение о плоском бинарнике
   конфликтует со структурой bin/+lib/)

build.rs продолжает отвечать за:
  └── Загрузку/линковку Z3 (динамическая линковка + rpath для всех платформ)

Собственные скрипты YaoXiang:
  ├── package-dist.sh — пересборка структуры пакета (bin/ + lib/),
  │   добавление разделяемой библиотеки, наполнение каталога std
  │   (предварительно сгенерированные представления интерфейсов + исходники слоя .yx
  │   из репозитория), пересчёт контрольных сумм
  └── Inno Setup — мастер установки Windows (существующий актив; раскладывает
      полную структуру каталогов)

Модель команд (разделение фасада и движка):
  ├── yx — фасад (новый маленький crate): разбор версии + диспетчеризация;
  │   сохраняет только глаголы toolchain/self, остальные пробрасываются
  └── yaoxiang-rs — движок (текущий монолит yaoxiang, переименованный):
      подкоманды компиляции/запуска/управления пакетами/fmt/lsp

Способы установки (двухуровневые):
  ├── Стандартный канал (модель Go/Zig): дистрибутив и есть продукт,
  │   распаковка + PATH
  └── Канал для чайников (модель Rust): установка одной командой + управление
      версиями (встроено в фасад yx)
      ├── Linux: apt (собственный deb-репозиторий, системная плоская установка) /
      │   curl … | sh (установка всего пакета одной командой)
      ├── Windows: irm … | iex (установка всего пакета одной командой) /
      │   мастер Inno Setup (существующий актив, системная плоская установка)
      └── macOS: curl … | sh (brew отложен до сообщества homebrew-core)
```

### Структура каталогов дистрибутива (решено: физическое наличие исходников стандартной библиотеки)

Пользователь должен иметь возможность читать стандартную библиотеку напрямую, как Python `Lib/` —
наличие каталога std в дистрибутиве является жёстким требованием, а не деталью упаковки. С Z3 то же
самое: как внешняя система, она естественным образом распространяется как разделяемая библиотека в
каталоге; запихнуть `.so` в exe или положить рядом и линковать динамически — в плане «всё равно идёт
в комплекте» эквивалентно, но второй вариант сохраняет заменяемость.

Каждый платформенный дистрибутив пересобирается `package-dist.sh` после сборки cargo-dist:

```
yaoxiang-{version}-{target}.tar.gz / .zip     (переносимый и готовый к работе:
                                                после распаковки bin/ запускается сразу)
├── bin/
│   ├── yx                            # фасад (или yx.exe)
│   ├── yaoxiang-rs                   # движок (или yaoxiang-rs.exe)
│   └── libz3.so / libz3.dylib / libz3.dll
├── lib/
│   └── yaoxiang/
│       └── std/                      # пользователь может читать напрямую (модель Python Lib/)
│           ├── io.yx                 # нативный модуль: предварительно сгенерированное
│           │                         #   представление интерфейса из репозитория
│           ├── math.yx
│           ├── test.yx               # слой .yx: реальный исходник, скопированный из репозитория
│           └── ...
├── README.md
└── LICENSE
```

Установка = распаковать в любой каталог + добавить `bin/` в PATH (модель Go `/usr/local/go/bin`;
распаковка в `~/.yaoxiang/` — распространённый выбор). В Windows тот же результат даёт мастер Inno
Setup (по умолчанию Program Files). При переносимой распаковке у фасада `yx` нет состояния
`~/.yaoxiang`, он откатывается на соседний `yaoxiang-rs` — поведение совпадает с управляемой
установкой; rpath движка и относительный к exe поиск std не меняются от присутствия фасада.

### Поддержка платформ

| Платформа      | target triple               | Примечание            |
| -------------- | --------------------------- | --------------------- |
| Linux x86_64   | `x86_64-unknown-linux-gnu`  | Основная платформа    |
| Linux ARM64    | `aarch64-unknown-linux-gnu` | Кросс-компиляция в CI |
| macOS x86_64   | `x86_64-apple-darwin`       | Intel Mac             |
| macOS ARM64    | `aarch64-apple-darwin`      | Apple Silicon         |
| Windows x86_64 | `x86_64-pc-windows-msvc`    | Основная платформа    |

Всего 5 target. Windows ARM64 временно не поддерживается (у Z3 нет официального прекомпилированного
пакета для ARM64).

### Стратегия распространения Z3

**Динамическая линковка на всех платформах** (решение подтверждено):

| Платформа | Изменение                         | Артефакт        |
| --------- | --------------------------------- | --------------- |
| Linux     | **Со статической → динамическую** | `libz3.so`      |
| macOS     | **Со статической → динамическую** | `libz3.dylib`   |
| Windows   | Без изменений                     | `libz3.dll`     |
| wasm32    | Без изменений (статическая)       | Встроенный `.a` |

Обоснование:

- **Единообразие** — поведение на трёх платформах одинаковое, без особых случаев
- **Это внешняя библиотека, её и нужно распространять как разделяемую**. Python
  (`python3.dll`+`DLLs/lib*.dll`), Node (`node`+`lib/`) делают именно так
- **Обновление Z3 не требует ожидания новой версии компилятора** — достаточно заменить
  `.so`/`.dylib`/`.dll`
- **Меньший размер бинарника** — Z3 не маленький, статическая линковка раздувает exe на несколько
  мегабайт

У динамической линковки есть **необходимое сопровождение**: динамический линковщик в Linux/macOS по
умолчанию не ищет в каталоге бинарника, нужно инжектировать rpath, иначе «распакуй и работай» не
сработает (в Windows по умолчанию поиск идёт в каталоге exe, ничего делать не нужно).
Соответствующее изменение в `build.rs`:

```rust
// Унифицированная динамическая линковка + rpath
fn link_z3(z3_dir: &Path) {
    let target_os = env::var("CARGO_CFG_TARGET_OS").unwrap();
    // Раскладка пакетов Z3 неоднородна, двойное определение каталогов lib/bin
    println!("cargo:rustc-link-search=native={}", lib_dir.display());
    // RFC-037: динамическая линковка на всех платформах. Разделяемая библиотека
    // поставляется в bin/ дистрибутива, пользователь может заменить её для обновления Z3
    if target_os == "windows" {
        // MSVC import lib именуется как libz3.lib
        println!("cargo:rustc-link-lib=libz3");
    } else {
        println!("cargo:rustc-link-lib=z3");
        // Динамический линковщик по умолчанию не ищет в каталоге бинарника,
        // нужно инжектировать rpath, иначе «распакуй и работай» не сработает
        // (в дистрибутиве exe и libz3 лежат вместе в bin/; в Windows поиск по умолчанию
        // идёт в каталоге exe, обработка не нужна)
        match target_os.as_str() {
            "linux" => println!("cargo:rustc-link-arg=-Wl,-rpath,$ORIGIN"),
            "macos" => println!("cargo:rustc-link-arg=-Wl,-rpath,@loader_path"),
            _ => {}
        }
        let cxx = if target_os == "macos" {
            "c++".to_string()
        } else {
            env::var("CXXSTDLIB").unwrap_or_else(|_| "stdc++".into())
        };
        println!("cargo:rustc-link-lib={}", cxx);
    }
}
```

**«Статическая линковка на всех платформах» не рассматривается как цель.** Это не устранение особого
случая, а попытка устранить его неправильным способом. Разделяемая библиотека — нормальный способ
распространения внешней библиотеки.

### Поддержка установщиков

Сравнение способов распространения основных языковых инструментариев (исследование 2026-09):

| Язык     | Официальный дистрибутив       | Официальный способ установки                             | Кто поддерживает установщик           |
| -------- | ----------------------------- | -------------------------------------------------------- | ------------------------------------- |
| Go       | `go/{bin,src,pkg}` tarball    | Официальная документация: «скачать → распаковать → PATH» | Нет (brew/apt — сообщество)           |
| Zig      | `zig/{bin,lib/std}` tarball   | То же, без официального скрипта установки                | Нет (сообщество homebrew-core)        |
| Node     | `{bin,lib,include}` tarball   | tar + официальный pkg/msi                                | Команда пишет сама                    |
| Rust     | Многокомпонентный tarball     | rustup                                                   | Команда пишет сама                    |
| Crystal  | `{bin,src,embedded}` tarball  | deb/rpm/tar                                              | Команда + сообщество brew             |
| Deno/Bun | Одиночный бинарник в zip      | Официальный curl-скрипт                                  | Команда пишет сама (скрипт крошечный) |
| Gleam    | cargo-dist одиночный бинарник | Скрипты, генерируемые cargo-dist                         | cargo-dist                            |

Три закономерности:

- **Ни один многофайловый инструментарий не использует сторонний генератор для установщиков** —
  установщик cargo-dist рассчитан только на одиночный бинарник (Gleam может его использовать именно
  потому, что это единый Rust-бинарник без внешних зависимостей)
- Самая простая модель — **«дистрибутив как продукт» у Go/Zig**: официальная инструкция —
  распаковать + PATH, ноль кода установщика; наличие читаемых исходников std в дистрибутиве (Go
  `src/`, Zig `lib/std/`, Crystal `src/`) — норма
- Те, кому нужна установка через curl (Deno/Bun/rustup), пишут **скрипты сами**, и они почти не
  развиваются; формулы brew всегда поддерживаются сообществом в homebrew-core, языковые команды не
  делают собственные tap (команда Crystal явно говорит, что formula — дело сообщества)

YaoXiang использует двухуровневую модель:

| Канал                                                     | Уровень     | Статус | Примечание                                                                                                                             |
| --------------------------------------------------------- | ----------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| zip / tar.gz                                              | Стандартный | ✅     | Распакуй и работай (rpath + разделяемая библиотека в том же каталоге), extract + PATH — официальная инструкция                         |
| `yx` (фасад, встроенное управление версиями)              | Чайник      | ✅     | Аналог rustup/Go GOTOOLCHAIN: установка/переключение/обновление нескольких версий + pin в проекте                                      |
| `curl ... \| sh` (install.sh)                             | Чайник      | ✅     | Linux / macOS: скачать пересобранный пакет, разложить в `versions/`, `bin/yx` встаёт в корень установки, прописать версию по умолчанию |
| `irm ... \| iex` (install.ps1)                            | Чайник      | ✅     | Windows: та же логика                                                                                                                  |
| `apt install yaoxiang`                                    | Чайник      | ✅     | `.deb` (amd64/arm64) + статический apt-репозиторий на GitHub Pages; системная плоская установка, `apt upgrade` отслеживает версии      |
| Inno Setup exe                                            | Чайник      | ✅     | Мастер Windows (существующий актив), системная плоская установка, раскладывает полную структуру bin/+lib/                              |
| winget / `.rpm` / homebrew-core / npm                     | —           | ⏸      | Опциональное продолжение: winget и brew-core поддерживаются сообществом, rpm симметричен deb                                           |
| MSI / родной установщик cargo-dist / собственный brew tap | —           | ❌     | См. «Альтернативы»                                                                                                                     |

**Канал для чайников ориентируется на Rust, управление версиями встроено в фасад.** Декомпозиция
Rust — «скрипт-бутстрап (sh.rustup.rs) → rustup → пакет инструментария»; rustup с самого начала
берёт на себя несколько версий, переключение, обновление; официальные установщики Python/Node этого
не делают, и экосистема事后 выращивает pyenv/nvm/pdm, каждый по-своему. YaoXiang применяет
**разделение фасада и движка** (фасад `go` в Go + GOTOOLCHAIN, проксирующая диспетчеризация rustup —
обе модели структурно одинаковы): повседневная команда — `yx`, движок — `yaoxiang-rs` —

```
~/.yaoxiang/
├── bin/yx                  # фасад: маленький бинарник, разбор версии + диспетчеризация
│                            #   (pin проекта > по умолчанию > соседний движок)
├── settings.toml           # версия по умолчанию, зеркала
└── versions/               # версия — понятие первого уровня; <ver>/ —
                              #   каталог распаковки дистрибутива этой версии
    └── 0.7.14/
        ├── bin/
        │   ├── yaoxiang-rs      # движок: подкоманды компиляции/запуска/fmt/lsp
        │   └── libz3.so
        └── lib/yaoxiang/std/
```

- Корень установки `~/.yaoxiang/` соответствует отраслевым конвенциям (pyenv `~/.pyenv`, nvm
  `~/.nvm`, deno `~/.deno`, bun `~/.bun`, volta `~/.volta` — все с одним корнем; двойной корень
  rustup — `~/.cargo`+`~/.rustup` — историческое наследие того, что cargo существовал до rustup, и
  мы его не копируем); к тому же `~/.yaoxiang` уже занято кодовой базой как пространство имён
  (резервный слот для глобального std); поддерживается переменная окружения `YAOXIANG_HOME` для
  переопределения (прецеденты RUSTUP_HOME / DENO_INSTALL, обслуживает сценарии CI и контейнеров); в
  Windows это `%USERPROFILE%\.yaoxiang`
- **Каталог версии = каталог распаковки дистрибутива**: `versions/<ver>/` структурно идентичен
  переносимой распаковке и дереву установки deb — установка версии = распаковка дистрибутива, ноль
  расхождений в структуре между тремя каналами
- Командный интерфейс (аналог rustup): `yx toolchain install / default / update / list / uninstall`,
  включая `yx self update`; остальные глаголы пробрасываются в движок как есть
- **Блокировка версий — структурная гарантия**: fmt и подобные инструменты развиваются вместе с
  синтаксисом в рамках одной версии (старый fmt не понимает новый синтаксис), разбор версии
  выполняется один раз на фасаде с переключением всего набора — нет пространства сочетаний «новый
  движок со старым fmt»; если в будущем fmt/LSP выделяются в отдельные бинарники, они лежат в `bin/`
  той же версии
- Pin на уровне проекта: `yx-toolchain.toml` (прецедент `rust-toolchain.toml`, следует имени
  команды; не в `yaoxiang.toml` — манифест пакета не должен навязывать версию инструментария
  потребителям библиотеки)
- Точка входа бутстрапа (`curl | sh` / `irm | iex`) одним махом устанавливает актуальный stable
  целиком: распаковка в `versions/`, `bin/yx` встаёт в корень установки, прописывается версия по
  умолчанию в `settings.toml` (эквивалентное схождение с декомпозицией rustup «бутстрап
  устанавливает менеджер» — фасад и движок идут одним пакетом, два шага не нужны)
- Зеркала настраиваются (settings.toml), продолжая заботу о китайских пользователях (та же сетевая
  проблема, что и с загрузкой Z3)
- **Управление версиями не нарушает инвариант самодостаточности**: каждая версия — полное дерево
  дистрибутива, rpath и относительный к exe поиск std согласованы внутри дерева, фасад только
  диспетчеризует и не меняет структуру

`.deb` и Inno — каналы **системной плоской установки** (root / Program Files, одна версия,
обновляется через `apt upgrade` / панель управления), обслуживают серверы, CI, чисто любительские
сценарии; сосуществование с менеджером — за счёт порядка PATH (прецедент: rustc из apt и rustup
сосуществуют). Все каналы используют одно и то же дерево продуктов.

Раскладка `.deb` повторно использует то же дерево каталогов: `/usr/lib/yaoxiang/` (всё дерево
дистрибутива: `bin/{yx,yaoxiang-rs,libz3.so}` + `lib/yaoxiang/std/`) + символическая ссылка
`/usr/bin/yx` → `/usr/lib/yaoxiang/bin/yx` — `$ORIGIN` вычисляется по **реальному пути** после
разыменования ссылки, и всё равно попадает на `libz3.so` в том же каталоге, структурно идентично
распакованному пакету. Полное брендовое имя остаётся в имени пакета и названии продукта
(`apt install yaoxiang`, продукт Inno — YaoXiang), командный интерфейс унифицирован как `yx` — как в
Go: пакет `golang-go`, команда `go`. Репозиторий apt статически хостится на GitHub Pages (метаданные
Packages/Release/InRelease с GPG-подписью, публикуются release CI); в перспективе можно подавать
заявку на включение в официальные Debian/Ubuntu (долгий цикл, отставание версий, не основной путь).

### Каталог стандартной библиотеки

Содержимое `lib/yaoxiang/std/` целиком берётся из статических файлов репозитория, упаковка —
**чистое копирование**, никакой генерации в рантайме:

| Слой                             | Источник                                                                              | Характер                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Нативные модули (io/math/…)      | Предварительно сгенерированные представления интерфейсов из `src/std/interfaces/*.yx` | Представление сигнатур интерфейсов (реализация внутри бинарника) |
| Модули слоя .yx (test/…, растёт) | Исходники из `src/std/*.yx`, копируются как есть                                      | Реальный исходный код                                            |

Предварительно сгенерированные представления порождаются из `StdModule::exports()`
(`generate_all_interfaces()` в `src/std/gen_interfaces.rs`), **подкоманда генерации в рантайме не
предусматривается** (решение 2026-09-10: после того как упаковка устоялась, подкоманда — лишняя
поверхность интерфейса). Применяется модель «генерат в репозитории + тестовый шлагбаум» (как таблица
кодов в RFC-013): `test_committed_interface_files_match_generation` побайтово сверяет предварительно
сгенерированные файлы с текущей генерацией, дрейф — красный тест; исправление через bless-вход
`cargo test update_committed_interface_files -- --ignored`. Логика генерации зависит от внутренней
реализации `StdModule` в crate, её нельзя спустить в build.rs, поэтому шлагбаум стоит на уровне
тестов, а не сборки.

**Цепочка поиска в рантайме** — `find_std_interface_file` получает дополнительный уровень
относительного к exe поиска:

1. `.yaoxiang/vendor/std/<name>.yx` в проекте (покрытие проекта, текущее поведение)
2. **`<каталог exe>/../lib/yaoxiang/std/<name>.yx` (новое)**: переносимая распаковка, управляемая
   установка (`versions/<ver>/`), deb-плоская установка — все попадают одинаково
3. `~/.yaoxiang/std/<name>.yx` (глобальный откат, сохранён как слот для ручного покрытия)

Сейчас эта цепочка почти не работает (вызов LSP не передаёт каталог проекта, `package init` пишет в
`.yaoxiang/std`, которого нет в цепочке), этот RFC по дороге чинит и заодно унифицирует вывод
`package init` в `.yaoxiang/vendor/std` (согласуется с каталогом vendor менеджера пакетов).

**Авторитет компиляции не меняется**: слой `.yx` по-прежнему встраивается через `include_str!`
(инвариант RFC-036 «версия std жёстко связана с бинарником» сохраняется). Каталог в дистрибутиве —
это **читаемое представление + источник для LSP-разрешения**, а не вход компиляции — ручные
изменения `.yx` в каталоге дистрибутива не будут подхвачены компилятором (открытие семантики «правка
`Lib/` в стиле Python сразу вступает в силу» — см. открытые вопросы).

### Сборка Wasm

**Остаётся отдельной, не встраивается в cargo-dist.**

cargo-dist отвечает за «доставить компилятор пользователю», wasm — за «встраивание онлайн-playground
в сайт документации» — это две совершенно разные поставки.

| Аспект            | Подход                                          |
| ----------------- | ----------------------------------------------- |
| Инструмент сборки | Сохраняется `wasm-pack build`                   |
| CI workflow       | Сохраняется `_build-wasm.yml` как отдельный job |
| Момент запуска    | Параллельно с release по тому же tag push       |
| Цель публикации   | `docs/public/wasm/` → GitHub Pages              |

### Публикация в npm

| Пакет                  | Содержимое                       | Статус                                                                                                                                                                                                                                   |
| ---------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@yaoxiang/cli`        | Обёртка, скачивающая дистрибутив | Отложено: npm-обёртка cargo-dist опирается на то же предположение о плоском артефакте, отброшено вместе с установщиками; если нужен канал npm — своя обёртка (скачать пересобранный пакет, распаковать, та же логика что и у распаковки) |
| `@yaoxiang/playground` | wasm-библиотека (JS + .wasm)     | Опционально, сейчас только docs                                                                                                                                                                                                          |

Конфликта нет, имена тоже не пересекаются.

### Интеграция с существующим процессом выпуска

Текущий `release.yml`: push main → check-version (пропускает, только если tag `v{version}` не
существует) → четыре ветки build / build-wasm / security / test → job release (создание и push tag +
`generate-commit-list.ts` генерирует тело с @mentions + загрузка артефактов).

Конвейер, генерируемый cargo-dist, — tag-управляемый, со своим announce/publish, и не содержит
шлюзов fmt/clippy/test/audit; формат release notes также не может нести changelog из merge-коммитов.
**Прямая полная замена сломает существующую процедуру выпуска** (PR → CI полностью зелёный → bump →
merge-коммит как changelog).

Принцип интеграции: **триггер и шлюзы остаются как есть, сборка передаётся `cargo dist build`,
публикация остаётся как есть.**

1. check-version / security / test вместе с созданием tag переезжают в jobs `gate` / `security` /
   `test` / `tag` файла `dist-release.yml`, триггер остаётся push main (**tag-управление не
   работает**: tag, который workflow пушит с `GITHUB_TOKEN`, не запускает другие workflow; старый
   `release.yml` поэтому был вынужден сам публиковать плоский бинарник, удалён вместе с
   `_build-platforms.yml`, единственная точка выпуска — этот файл)
2. Сборка запускается только после создания tag: job `plan` через dist вычисляет матрицу
   runner/системных зависимостей → `cargo dist build` (5 target) → `package-dist.sh` пересобирает
   каждый target → job Inno Setup (берёт пересобранный Windows-пакет, собирает мастер, версия
   инжектируется через `/DMyAppVersion=`, без повторной компиляции) → `_build-wasm.yml`
   (параллельный job)
3. Job publish: `generate-commit-list.ts` генерирует тело (текущий скрипт переиспользуется) →
   загружает пересобранные пакеты + `.sha256` + `.deb` + wasm + Setup exe, `action-gh-release` сам
   создаёт Release; отдельный job `publish-apt` публикует метаданные apt-репозитория на GitHub Pages
   (если `secrets.APT_GPG_KEY` не настроен, автоматически пропускается, не влияя на остальные
   каналы)
4. Повторная публикация/повторная сборка: `workflow_dispatch` с указанием существующего tag (тогда
   `gate` пропускает шаг создания tag)

### Nightly-релизы

cargo-dist не имеет нативной поддержки nightly
([axodotdev#1143](https://github.com/axodotdev/cargo-dist/issues/1143), до сих пор открытый feature
request).

Сохраняется текущая схема cron + перезапись tag, секция сборки заменяется с `_build-platforms.yml`
на `cargo dist build` — это просто cargo-команда, её можно вызвать напрямую в nightly.yml. Не через
переиспользование workflow (предполагаемое `uses: ./release.yml` не работает: вызываемый должен
иметь триггер `workflow_call`, а workflow cargo-dist — tag-управляемый, сборка и публикация в нём
связаны):

```yaml
# nightly.yml (после миграции)
on:
  schedule:
    - cron: '17 22 * * *'
jobs:
  build: # cargo dist build + package-dist.sh (тот же набор, что и для стабильного релиза)
  publish: # текущее сохранено: создать/сдвинуть nightly tag → перезаписать GitHub Pre-release
```

### Конфигурация cargo-dist (уже в репозитории как dist-workspace.toml)

```toml
[workspace]
members = ["cargo:.", "cargo:tools/yx"]

# Config for 'dist'
[dist]
# Зафиксировать версию dist (синтаксис SemVer из Cargo.toml)
cargo-dist-version = "0.32.0"
ci = "github"
# Установщики все свои, cargo-dist только сборка + архивы + контрольные суммы
installers = []
targets = ["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "x86_64-apple-darwin", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
# Сгенерированный workflow намеренно модифицирован (пересборка через package-dist.sh +
# собственный сегмент публикации, RFC-037), не отказывать в сборке из-за расхождения
# с шаблоном generate
allow-dirty = ["ci"]
```

Это реальная конфигурация, вендоренная в репозиторий (сгенерирована `cargo dist init` и доработана);
`cargo-dist-version` зафиксирован на 0.32.0, сгенерированный workflow вендорится в репозиторий и
проходит review, не подтягивается в рантайме. Профиль сборки init вписывает в корневой Cargo.toml
как `[profile.dist]` (inherits release, lto=thin), оба бинарника сохраняются в
`target/<triple>/dist/` для скрипта пересборки.

### package-dist.sh (уже в репозитории)

Согласно `scripts/release/package-dist.sh` в репозитории, основные моменты:

- Оба бинарника берутся напрямую из каталога вывода сборки `cargo dist build` —
  `target/<triple>/dist/` (profile=dist) — плоский одиночный архив, который сам cargo-dist
  производит, не является поставкой; одноимённый пересобранный пакет в `target/distrib/` просто
  перезаписывается
- Разделяемая библиотека Z3 тоже берётся из каталога вывода сборки — build.rs при линковке уже
  выбрал подходящую платформенную разделяемую библиотеку и скопировал её на диск
  (`copy_shared_lib`), **единственный источник**: скрипт упаковки не знает и не должен знать версию
  Z3 и соглашения об именовании платформенных каталогов; текст лицензии Z3 сохраняется на диск рядом
  с библиотекой и подхватывается упаковкой (обязательство по MIT-распространению), на стороне macOS
  при упаковке install_name dylib приводится к `@rpath` и бинарник ad-hoc переподписывается
- Каталог std — чистое копирование: `src/std/interfaces/*.yx` (предварительно сгенерированные
  представления интерфейсов) + `src/std/*.yx` (реальные исходники слоя .yx)
- Прикладываются README/LICENSE; переупаковка (Windows zip / остальные tar.gz; в Git Bash без zip —
  трёхуровневый откат zip → System32 bsdtar → PowerShell) с пересчётом `.sha256`
- На Linux при наличии `dpkg-deb` параллельно вызывается `build-deb.sh` для получения `.deb` (дерево
  плоской установки `/usr/lib/yaoxiang` + символическая ссылка `/usr/bin/yx`)

### Критерии приёмки

«Из коробки» — это тестируемо; критерий завершения миграции — не «совпадение старого и нового
продукта», а прохождение всех пунктов ниже:

- На чистой машине (без Rust / без Z3 / без `~/.yaoxiang`) после распаковки архива любой платформы
  прямой запуск `bin/yaoxiang-rs --version` успешен — без `LD_LIBRARY_PATH` (rpath работает)
- Все `lib/yaoxiang/std/*.yx` в каталоге распаковки читаемы: нативные модули — представления
  сигнатур интерфейсов, слой `.yx` — реальный исходный код
- На примерном проекте в каталоге распаковки запуск LSP даёт работающие автодополнение членов std /
  переход к определению (относительный к exe поиск работает)
- После распаковки по официальной инструкции в `/usr/local` (или `~/.yaoxiang`) и добавления в PATH
  в любом каталоге `yx --version` успешен
- После `apt install yaoxiang` (собственный репозиторий) запускается, `apt upgrade` отслеживает
  версии; под символической ссылкой `/usr/bin/yx` `$ORIGIN` движка (вычисленный по реальному пути)
  попадает на `bin/libz3.so`
- `curl ... | sh` и `irm ... | iex` в чистой среде после выполнения дают рабочий `yx` с настроенным
  PATH
- `yx toolchain install <ver>` / `default` / `update` работают: сосуществование нескольких версий,
  pin в `yx-toolchain.toml` имеет приоритет над версией по умолчанию, фасад диспетчеризует в
  правильную версию (rpath и поиск std внутри дерева версии согласованы, нет сочетания «новый движок
  со старым fmt»)
- При переносимой распаковке `yx` откатывается на соседний `yaoxiang-rs`, поведение совпадает с
  управляемой установкой
- После установки Inno Setup структура каталогов полная, PATH работает, удаление возможно
- Релиз полон: пересобранные пакеты 5 платформ + `.sha256` совпадают с фактическим содержимым
- Тело релиза — вывод `generate-commit-list.ts` (changelog из merge-коммитов полный)
- Артефакт nightly — Pre-release, не влияет на последний стабильный tag

## Компромиссы

### Преимущества

- **Работает из коробки** — переносимая распаковка (rpath + разделяемая библиотека в том же
  каталоге), установщики раскладывают полную структуру каталогов
- **Стандартная библиотека читаема** — пользователь читает std напрямую, как Python `Lib/` (жёсткое
  требование выполнено)
- **Снижение стоимости поддержки** — ~600 строк рукописного YAML сборки заменены на cargo-dist + ~80
  строк собственных скриптов
- **Кроссплатформенное единообразие** — динамическая линковка на всех платформах + разделяемая
  библиотека в том же каталоге, без особых случаев
- **Двухуровневая установка** — стандартный канал без нового кода (модель Go/Zig); канал для
  чайников по модели Rust, четыре входа (apt / curl / iex / exe) используют одну и ту же структуру
  продукта
- **Управление версиями встроено** — фасад `yx` аналогичен rustup/Go GOTOOLCHAIN, не
  нужно事后 доставлять pyenv/nvm/pdm, как в Python/Node; блокировка версий инструментов —
  структурная гарантия, а не договорённость

### Недостатки и риски

- **Поверхность поддержки канала для чайников** — install.sh / install.ps1 (однострочные скрипты,
  почти не развиваются) + `.deb` и публикация метаданных apt-репозитория (автоматизировано в release
  CI) + crate фасада `yx`
- **Масштаб изменений от переименования движка** — `yaoxiang` → `yaoxiang-rs` требует однократной
  миграции имён CI-артефактов, Inno, тестов и документации (выполняется в рамках этапа 5)
- **Стоимость обучения** — команде нужно освоить конфигурацию cargo-dist
- **Риски со стороны cargo-dist** — в середине 2025 проект приостанавливался вместе с Axo, в
  сентябре того же года оригинальный автор возродил проект и продолжает выпускать версии (0.29 →
  0.32+); митигируется фиксацией `dist-version` + вендорингом генерата в репозиторий для review
- **У cargo-dist нет нативного nightly** — часть про nightly-релизы по-прежнему пишется вручную

### Связь с RFC-014b

|                 | RFC-014b                                   | RFC-037                                              |
| --------------- | ------------------------------------------ | ---------------------------------------------------- |
| **Область**     | Сборка и распространение сторонних пакетов | Упаковка и распространение самого компилятора        |
| **Инструменты** | `yaoxiang build` / `yaoxiang publish`      | `cargo-dist` + собственные скрипты                   |
| **Продукты**    | FFI-библиотеки сторонних пакетов           | Компилятор + стандартная библиотека + инструментарий |
| **Исключение**  | Нет, дополняют друг друга                  | Нет, дополняют друг друга                            |

## Альтернативы

| Вариант                                     | Почему не выбран                                                                                                                                                                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Продолжать писать CI вручную**            | Уже написано ~870 строк, повторяющийся труд, легко забыть DLL                                                                                                                                                                                                       |
| **Собственный инструмент упаковки**         | Не изобретать велосипед, cargo-dist уже зрелый                                                                                                                                                                                                                      |
| **Только tar.gz без установщиков**          | Единственный официальный канал — распаковка + PATH; Inno только обслуживает привычку мастера Windows (сохранено по решению для китайских пользователей)                                                                                                             |
| **Распространение через Docker**            | Компилятору и языковому инструментарию нужны нативные бинарники, это не сценарий для контейнеров                                                                                                                                                                    |
| **Собственный Homebrew tap**                | tap всегда поддерживается сообществом (homebrew-core), собственный — преждевременная потребность; macOS-вход канала для чайников — curl-скрипт                                                                                                                      |
| **Отдельный бинарник `yaoxiangup`**         | Прецедент rustup как есть, выполнимо; но создаёт второй пользовательский глагол и вызывает симметричный вопрос «должны ли менеджер пакетов / fmt тоже быть отдельными» — разделение фасада и движка снимает оба вопроса (отклонено по итогам обсуждения 2026-09-09) |
| **Только самообновление, без мультиверсии** | Самообновление одной версии не решает потребность в разных версиях для разных проектов; в Python/Node нет официального управления версиями, и экосистема вынужденно порождает pyenv/nvm/pdm — решено встроить (2026-09-09)                                          |
| **Полностью статическая линковка Z3**       | Отклонено — каталожное распространение разделяемой библиотеки — естественная форма для внешней системы; запихнуть в exe или положить снаружи в плане «всё равно идёт в пакете» эквивалентно, но теряется заменяемость                                               |
| **Удалить Inno Setup**                      | Отклонено — сохранён как мастер Windows (дополнительный канал)                                                                                                                                                                                                      |
| **Родной установщик cargo-dist**            | Предположение о плоском бинарнике конфликтует со структурой bin/+lib/, после установки библиотеки не хватает                                                                                                                                                        |
| **Самостоятельная поддержка WiX/MSI**       | Потеря генератора cargo-dist обходится дороже, чем ценность, уже покрытая Inno                                                                                                                                                                                      |

## Стратегия реализации

### Этап 1: Изменения на стороне языка (P0)

1. `build.rs`: унифицированная динамическая линковка + link-arg rpath на всех платформах;
   `copy_dll()` расширяется до `copy_shared_lib()` (so/dylib/dll)
2. Предварительная генерация нативных представлений интерфейсов в репозитории
   (`src/std/interfaces/`), тестовый шлагбаум обеспечивает синхронизацию с `StdModule::exports()`
   (подкоманда gen-std отменена по решению)
3. `find_std_interface_file` получает дополнительную ветвь относительного к exe поиска; вывод
   `package init` унифицируется в `.yaoxiang/vendor/std`

### Этап 2: Подключение cargo-dist (P0)

1. Запустить `cargo dist init` для генерации начальной конфигурации (`installers = []`,
   зафиксировать dist-version)
2. Написать `package-dist.sh` (пересборка + копирование исходников .yx + пересчёт контрольных сумм)
3. `dist-release.yml` несёт всё: триггер push main → gate версии → шлюзы (audit / fmt / clippy /
   test) → создание tag → dist build → пересборка → параллельный wasm → собственные publish + apt;
   `release.yml` и `_build-platforms.yml` удаляются
4. Параллельный прогон старого и нового конвейеров, проверка по критериям приёмки

### Этап 3: Вывод старого CI (P1)

1. `_build-platforms.yml` и `release.yml` удаляются вместе (единственная точка выпуска:
   `dist-release.yml`)
2. В `nightly.yml` секция сборки заменяется на `cargo dist build`
3. `setup.iss` подключается к новой структуре продукта (Inno приводится в порядок; версия
   инжектируется из Cargo.toml, sed-замена устраняется)

### Этап 4: Канал для чайников (P2)

1. `install.sh` / `install.ps1` (определить платформу → скачать свежий пересобранный пакет →
   распаковать в `versions/` → `bin/yx` встаёт в корень установки → прописать версию по умолчанию в
   `settings.toml` → подсказка/запись PATH; выкатывается в один приём с этапом 5 как финальное
   состояние)
2. Упаковка `.deb` (то же дерево каталогов, что у `package-dist.sh` + символическая ссылка в
   `/usr/bin`) + статический apt-репозиторий на GitHub Pages (метаданные с GPG-подписью, публикуются
   release CI)

### Этап 5: Фасад yx и переименование движка (P2)

1. Текущий монолит переименовывается в `yaoxiang-rs` (CI-артефакты, Inno, тесты и документация —
   полный проход, однократная миграция)
2. Новый маленький crate `yx` (член workspace): разбор версии, скачивание артефактов релиза,
   распаковка tar/zip, settings.toml, диспетчеризация (сохраняет глаголы только toolchain/self,
   остальные пробрасывает, ручная диспетчеризация без clap для гарантии побайтовой передачи
   аргументов); индекс версий — GitHub Releases latest API (зеркала — префиксы в стиле ghproxy); имя
   команды `yx` проверено на коллизии (в основных дистрибутивах/Homebrew нет распространённой
   команды с таким именем, только в одном нишевом инструменте `yx` — псевдоним)
3. `yx toolchain install/default/update/list/uninstall` + pin проекта `yx-toolchain.toml` +
   зеркала + `yx self update`
4. Скрипты бутстрапа: `curl | sh` / `irm | iex` → скачать пересобранный пакет и одним махом
   установить фасад и stable по умолчанию (выкатывается в один приём с этапом 4 как финальное
   состояние)

### Этап 6: Опциональные продолжения (ни одно не блокирует)

1. Подача в winget (указывает на Inno exe, поддерживается сообществом, симметрично модели
   homebrew-core)
2. `.rpm` (для пользователей dnf, симметричен `.deb`)
3. Homebrew: после достижения порога известности для homebrew-core — сообщество подаёт
4. Самостоятельная npm-обёртка `@yaoxiang/cli` (имя сейчас свободно)

## Открытые вопросы

### Не решённые

- **Предоставлять ли слою .yx семантику «правка каталога дистрибутива сразу подхватывается
  компиляцией» в стиле Python?** По умолчанию нет — авторитет компиляции остаётся встроенным через
  include_str! (жёсткая привязка версии std к бинарнику), каталог в дистрибутиве — читаемое
  представление + источник для LSP-разрешения. Если в будущем открыть, нужно будет пересмотреть
  инвариант привязки версий.

### Закрытые

Следующие вопросы решены в ходе обсуждения дизайна:

- ~~Возможна ли статическая линковка Z3 на Windows?~~ → **Не делать статическую линковку,
  динамическая на всех платформах** (подтверждено 2026-09-09)
- ~~Имя подкоманды gen-std-interfaces?~~ → **Подкоманды не будет** (решение 2026-09-10: после
  устоявшейся упаковки подкоманда — лишняя поверхность; нативные представления интерфейсов
  переведены в предварительно сгенерированные `src/std/interfaces/` в репозитории + тестовый
  шлагбаум, упаковка — чистое копирование)
- ~~Сохранять ли Inno Setup?~~ → **Сохранить как мастер Windows (дополнительный канал)**
- ~~Физически ли дистрибутив содержит исходники стандартной библиотеки?~~ → **Обязательно**
  (читаемость пользователем по аналогии с Python `Lib/`, решение 2026-09-09)
- ~~Родные установщики cargo-dist (shell/powershell/homebrew/msi/npm)?~~ → **Все отброшены**,
  установщики свои (предположение о плоском артефакте конфликтует со структурой bin/+lib/)
- ~~Стратегия установщиков?~~ → **Двухуровневая** (окончательное решение 2026-09-09): стандартный
  канал = дистрибутив и есть продукт (модель Go/Zig, распаковка + PATH); канал для чайников по
  модели Rust, установка одной командой — Linux `apt` (собственный deb-репозиторий) / `curl | sh`,
  Windows `irm | iex` / Inno exe. Не делается: MSI, родные установщики cargo-dist, собственный brew
  tap
- ~~Включать ли менеджер версий?~~ → **Обязательно, в составе системы установки** (решение
  2026-09-09, отменяет границу «отдельный RFC в перспективе» от того же дня): мотивация — отсутствие
  официального управления версиями в Python/Node привело к фрагментации экосистемы с pyenv/nvm/pdm
- ~~Форма менеджера версий: отдельный бинарник или подкоманда?~~ → **Разделение фасада и движка**
  (окончательное решение 2026-09-09, три итерации сходятся A→C→обратное переименование):
  повседневная команда `yx` = фасад (маленький бинарник, встроенные глаголы toolchain/self), движок
  `yaoxiang-rs` = текущий монолит `yaoxiang`, переименованный; структура каталогов `versions/<ver>/`
  — версия становится понятием первого уровня, каталог версии есть каталог распаковки дистрибутива,
  инструменты блокируются по версии целиком (старый fmt не понимает новый синтаксис;
  предполагавшийся внутренний `toolchains/` отменён как избыточный). Прецеденты: фасад `go` в Go +
  GOTOOLCHAIN, проксирующая диспетчеризация rustup
- ~~Условное выполнение extra-artifacts в cargo-dist?~~ → **Обрабатывается скриптом
  `package-dist.sh` через case-ветвление в shell**
- ~~Совместимость версий интерфейсов стандартной библиотеки?~~ → **Поставляются вместе с версией
  компилятора, в одном архиве**
