# RFC-010b: Полнота сопоставления с образцом (деконструкция вариантов и полнота)

> Настоящий документ является дочерним RFC для [RFC-010](../accepted/010-unified-type-syntax.md)
> (Унифицированный синтаксис типов). Объявление вариантов, формы вызова конструкторов и
> представление tagged union во время выполнения (включая порядок объявления `variant_id` — входные
> данные множества вариантов для проверки полноты в данном RFC) определены в разделе RFC-010
> «Конструкция вариантов в стиле записи и в стиле типа (авторитетное определение)»; настоящий RFC
> несёт зеркальную сторону: деконструкцию `match` и проверку полноты. Конструкция и деконструкция
> должны быть парными, поэтому они отнесены к одному RFC-010.
>
> Исходный номер RFC-039 (создан 2026-09-03); 2026-09-25 по решению владельца объединён в дочерний
> RFC-010 и перенумерован в RFC-010b, отслеживающий issue остаётся #330. Текст дополнен 2026-09-27 и
> закреплён в реализации (head e368958f); в тот же день подтверждён владельцем как принятый
> (accepted).

## Аннотация

Расширение сопоставления с образцом `match` от «только литералы + wildcard» до полноценной
возможности: деконструкция вариантов (включая нулевую и множественную нагрузку), образцы
структур/кортежей, или-образцы и охранники, фиксация семантики связывания идентификаторов, а также
проверка полноты (E1030/E1031 из неактивных зарегистрированных кодов превращаются в реально
испускаемые). Настоящий RFC является предварительным условием для направления развития
`Error { kind: ErrorKind, message }` (раздел эволюции RFC-013 «Сквозные значения и коды ошибок
времени выполнения»), но мотивация независима — сопоставление с образцом является общеязыковой
возможностью, обслуживающей все типы с вариантами.

## Мотивация

### Свидетельства текущего состояния (2026-09-03, код v0.7.12; 2026-09-27 всё устранено)

1. **На уровне IR только литеральные образцы являются реальными**. AST определяет полный набор
   образцов, но генерация IR реализует только ветвь `Literal`, остальные образцы попадают в заглушку
   — загружается константа 0 для сравнения на равенство, никогда не совпадает; и когда scrutinee
   равно ровно 0, оно ошибочно попадает в arm заглушки.
2. **Примеры `match ok(v)/err(e)` в stdlib.md — бумажные возможности**.
3. **Проверка полноты пустая**. E1030/E1031 зарегистрированы в кодовой таблице, но без точек
   испускания.
4. **Развитие обработки ошибок заблокировано** (структурное моделирование ошибок в RFC-013 зависит
   от деконструкции вариантов).

### Цели проектирования

- **Деконструкция вариантов доступна**: деконструкция `match r { ok(v) => ..., err(e) => ... }` и
  пользовательских множеств вариантов семантически согласована на всех путях выполнения.
- **Полнота надёжна**: E1030/E1031 испускаются реально, пропуск ветви в match является ошибкой
  компиляции.
- **Заглушки устранены**: неподдерживаемые образцы сообщают об ошибке во время компиляции, а не
  молча идут по неверному пути (защитная сетка #330 — эта переходная стратегия поэтапно заменяется
  реальным кодированием в период реализации, в итоге все заглушки устранены).

## Предложение (зафиксировано и реализовано 2026-09-27)

| Возможность                        | Статус | Описание                                                                                                                     |
| ---------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Образцы вариантов Union            | ✅     | `Variant` / `Variant(binding)` / множественная нагрузка `make(a, b)` + связывание нагрузки в область видимости arm           |
| Образцы Struct / Tuple             | ✅     | Образцы полей (сокращённое связывание / `имя: подобразец`), образцы кортежей; объявленные поля должны быть полностью покрыты |
| Или-образцы и охранник             | ✅     | `p1 \| p2` и `pat if cond`: цепочка отказов на уровне альтернатив, отказ охранника переходит к следующему arm                |
| Проверка полноты                   | ✅     | E1030 пропуск ветви, E1031 недостижимость, область видимости покрывает множество вариантов                                   |
| Подтверждение семантики Identifier | ✅     | Зафиксировано как **связывание** (см. следующий раздел)                                                                      |

## Проектные решения

### Образец Identifier: связывание, а не присваивание и не сравнение

Голый идентификатор `y` в `match x { y => ... }` зафиксирован как **связывание** — вводится новое
имя для захвата сопоставляемого значения, всегда совпадает (эквивалентно wildcard с именем). Три
основания:

1. **Структурный аргумент**: в позиции образца идентификатор естественно имеет две роли — позицию
   дискриминатора (`ok` в `ok(v)`, сверяется с таблицей вариантов) и позицию листа (`v` в `ok(v)`,
   связывание). Список параметров (лямбда) имеет только позицию листа, поэтому неоднозначности нет;
   голый идентификатор стоит и в позиции дискриминатора, и выглядит как позиция листа — отсюда
   неоднозначность. YaoXiang имеет статическую таблицу вариантов: имя дискриминатора разрешается
   «попаданием в таблицу» (если заголовок образца — это имя из множества вариантов scrutinee или
   литерал → дискриминатор; голое имя, не попавшее в таблицу → связывание), без необходимости в
   соглашении о регистре как в Rust.
2. **Вырождение сравнения значений**: «связанное имя в образце означает равенство» (семантика
   унификации) — продукт традиции единственного присваивания; в мутабельном языке статически
   невозможно определить, «было ли оно связано», эта семантика не работает. Переменные YaoXiang
   допускают повторное присваивание (`mut`), следуем законодательству Rust.
3. **Потребность в сопоставлении существующего значения относится к охранникам**:
   `n if n == threshold` (до внедрения охранников пишется цепочка if).

**Связывание — это не присваивание** (согласованная с владельцем формулировка от 2026-09-27):
связывание в образце вводит **новое имя**, действительное в области видимости arm, затеняющее
одноимённую внешнюю переменную, исчезающее при выходе из arm (проверка: внешнее `v = 999` остаётся
неизменным после попадания в `some(v)`); присваивание — это перезапись уже существующего имени
(законодательство E2010/`mut`). Они сосуществуют и концептуально разделены в данном языке, `=`
направляет поток в зависимости от того, существует ли имя (приоритет присваивания по spec §4.3),
позиция образца относится только к стороне связывания.

### match — это выражение, а не оператор присваивания

`match` выдаёт значение попавшего arm (значение всего выражения), `v = match ...` — это просто
обычный синтаксис связывания, захватывающий его. Зубы проверки полноты происходят из «arm должен
выдавать значение»: пропуск формы = присваивающая сторона не получает значения = ошибка компиляции
(E1030); операторная форма switch с пропуском ветви может только молчать.

### Семантическая модель и реализация arm

Arm = **одноаргументная функция с меткой**: `some(v) => body` ≈ `λv.body`, вызывается только тогда,
когда фактический аргумент имеет форму some; семантика связывания происходит из «слева — позиция
параметра». Имеет общий источник `=>` с лямбдой. В реализации arm **не является замыканием**:
рекурсивный компилятор образцов IR (`compile_pattern`) встроенно испускает цепочку проверок
(VariantTag/LoadField/Eq + JmpIfNot) и извлечение нагрузки (VariantPayload), при попадании сразу
переходит к телу arm, при отказе переходит к следующему arm — нулевые накладные расходы на вызов.

### Или-образцы и охранники

- `p1 | p2`: альтернативы пробуются по порядку; не последняя альтернатива при отказе → следующая
  альтернатива, при попадании → после извлечения нагрузки сразу в тело arm; последняя альтернатива
  при отказе → следующий arm. **Наборы имён связывания всех альтернатив должны быть согласованы**
  (E1033), одноимённые связывания разделяют предварительно выделенный регистр уровня arm (тело
  читает значение, обязательно записанное попавшей альтернативой).
- `pat if cond`: после попадания образца вычисляется `cond` (**связывания образца видны
  охраннику**), если ложь — переход к следующему arm. Условие охранника должно выдавать `Bool`.
  **Arm с охранником не учитывается в покрытии полноты** (охранник может не сработать, как в Rust),
  но arm с охранником для повторяющегося варианта достижим (является уточнением предыдущего arm).

### Образцы структур

`Point { x, y: b }`: сокращённое связывание поля с тем же именем, `имя: подобразец` рекурсивно.
**Объявленные поля должны быть полностью покрыты** (E1034 отсутствующее поле), неизвестные поля
отвергаются (E1042), повторное появление того же поля сообщает E1032. Сокращение `..` и образцы
обобщённых структур пока не поддерживаются (см. открытые вопросы).

### Деконструкция вариантов (симметрично конструкции RFC-010)

| Конструкция                        | Деконструкция      | Представление нагрузки                                                                                          |
| ---------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------- |
| `Result(Int, String).ok(5)`        | `ok(v)`            | Одна нагрузка: прямое связывание                                                                                |
| `Pair.make(3, 4)`                  | `make(a, b)`       | Множественная нагрузка: упаковка в кортеж, распаковка по позициям                                               |
| `Color.red()` / `Option(T).none()` | `red()` / `none()` | Нулевая нагрузка: `pattern: None`, проверка арности (запись `ok()` для варианта с нагрузкой сообщает об ошибке) |

Тип нагрузки = параметры варианта с заменой на аргументы типа scrutinee (в порядке объявления);
вложенные образцы (`ok(some(v))` через сумму типов, `Point { pos: Tuple(a, b) }` через структуры)
рекурсивно по подтипам.

### Полнота и достижимость

- **E1030 (пропуск ветви)**: только для scrutinee суммы типов. При отсутствии fallback arm множество
  вариантов должно быть полностью покрыто Union-arm без охранников. Arm с охранниками не учитываются
  (охранник может не сработать).
- **E1031 (недостижимость)**: любой arm после fallback arm (неопровержимые образцы безусловного
  срабатывания: Identifier/Wildcard/Tuple/Struct, без охранника); arm для повторяющегося варианта
  без охранника, arm для повторяющегося литерала.
- **Scrutinee не суммы типов**: область значений открыта, E1030 не выдаётся (допускается свободная
  семантика из полностью литеральных arm без fallback, сохранена текущая); E1031 как обычно.

### Диагностика

| Код   | Значение                                                                                         |
| ----- | ------------------------------------------------------------------------------------------------ |
| E1030 | Неполный перебор образцов (перечислены пропущенные варианты)                                     |
| E1031 | Недостижимый образец (после fallback arm / повторяющийся вариант / повторяющийся литерал)        |
| E1032 | Повторяющееся связывание в образце (то же имя связывания появляется многократно в одном образце) |
| E1033 | Несогласованность связывания в или-образце (наборы имён связывания альтернатив различаются)      |
| E1034 | Пропущено поле в образце структуры                                                               |
| E3008 | Защитная сетка уровня IR сохранена (защитная ветвь, недостижима для нормальных программ)         |

### Границы с присваиванием/лямбдой (памятка во избежание путаницы)

- Связывание в образце ≠ присваивание: введение нового имени vs перезапись существующего
  (E2010/`mut`);
- Или-образец ≈ расширение применения лямбды (семантическая модель), но реализован как встроенный
  переход, не как вызов замыкания;
- Литеральный образец компилируется в Eq + цепочку условных переходов — интуиция «оптимизированной
  формы if/elif» верна для литералов, приращение match состоит в проверке формы и
  распаковке-связывании.

## Точки реализации

- parser: `parse_pattern` (реорганизация вызова варианта / ветвь образца структуры `Ident { .. }` /
  восстановление вложенного или-образца), `parse_match` сборка или-образца в цепочку + охранник
  (флаг `no_fat_arrow` делает `=>` не инфиксом лямбды)
- typecheck: `check_match_expr` унифицированный цикл arm + `check_pattern` рекурсивный проверяющий
  (регистрация связывания, проверка `Bool` охранника, учёт полноты)
- ir_gen: `compile_pattern` рекурсивный компилятор образцов + `sum_type_variants` зеркало несёт типы
  нагрузки и `sum_type_param_names` (тип нагрузки с заменой по аргументам типа scrutinee)
- Корпус примеров: `02-type-system/pattern_destructure.yx`, `pattern_or_guard.yx`; юнит-тесты
  E1030/E1031/E1032/E1033/E1034 (rfc011b.rs)

## Открытые вопросы

- [x] Образец Identifier: связывать новую переменную или сопоставлять существующее значение? →
      **Связывание** (позиция дискриминатора разрешается попаданием в таблицу вариантов, без
      соглашения о регистре); сопоставление существующего значения относится к охранникам.
- [x] Границы применимости полноты: → полнота множества вариантов только для суммы типов; для не
      суммы типов область значений открыта и E1030 не выдаётся.
- [x] Сообщать ли об ошибке компиляции в переходный период до исправления ошибочного совпадения
      заглушки с загрузкой 0? → Да (защитная сетка #330), всё заменено реальным кодированием.
- [ ] Нужно ли сокращение `..` в образцах структур (часть полей + fallback)? (влияет на правила
      покрытия полей)
- [ ] Образцы обобщённых структур (`Box { v, n }` для значения `Box(Int)`) — под вопросом — в данный
      момент предварительно отвергается проверкой типов.
- [ ] Атрибут класса non_exhaustive (радиус разрушения расширения множества вариантов std для
      пользовательского match) — под вопросом.
