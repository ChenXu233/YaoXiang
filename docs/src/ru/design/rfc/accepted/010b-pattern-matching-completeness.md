# RFC-010b: Завершение сопоставления с образцом (деконструкция вариантов и полнота)

> Настоящий документ является под-RFC к [RFC-010](../accepted/010-unified-type-syntax.md)
> (унифицированный синтаксис типов). Объявление вариантов, форма вызова конструктора и представление
> tagged union во время выполнения (включая порядок объявления `variant_id` — входные данные для
> набора вариантов, используемого проверкой полноты в данном документе) определены в разделе RFC-010
> «Конструкция вариантов для record-like и типов (авторитетное определение)»; настоящий документ
> несёт зеркальную сторону: деконструкцию `match` и проверку полноты. Конструкция и деконструкция
> должны быть парными, поэтому они оба отнесены к RFC-010.
>
> Первоначальный номер RFC-039 (создан 2026-09-03); 2026-09-25 по решению владельца объединён в
> под-RFC к RFC-010 и переименован в RFC-010b, отслеживающий issue остаётся #330. Основной текст
> дополнен 2026-09-27 и реализован (head e368958f); в тот же день подтверждён владельцем как
> принятый (accepted).

## Резюме

Дополнение возможностей сопоставления с образцом `match` от «только литералы + шаблон-джокер» до
полного набора: деконструкция вариантов (включая нулевую и множественную нагрузку), образцы
структур/кортежей, или-образцы и стражи, утверждение семантики связывания идентификаторов, а также
проверка полноты (E1030/E1031 переходят от пустого挂码 к реальной эмиссии). Настоящий RFC является
предварительным условием для направления развития `Error { kind: ErrorKind, message }` (раздел
эволюции RFC-013 «Сквозные значения и коды ошибок времени выполнения»), но мотивация независима —
сопоставление с образцом является общеязыковой возможностью, обслуживающей все типы с вариантами.

## Мотивация

### Текущее положение дел (2026-09-03, код v0.7.12; 2026-09-27 всё устранено)

1. **На уровне IR реальны только образцы литералов**. AST определяет полный набор образцов, но
   IR-генерация реализует только ветку `Literal`, остальные образцы попадают в stub — загружают
   константу 0 для сравнения на равенство, никогда не совпадают; и при scrutinee, равном 0, ошибочно
   попадают в stub-ветку.
2. **Пример `match ok(v)/err(e)` в stdlib.md — бумажная возможность**.
3. **Проверка полноты пуста**. E1030/E1031 зарегистрированы в кодовой таблице, но не имеют точек
   эмиссии.
4. **Эволюция обработки ошибок заблокирована** (структурное моделирование ошибок в RFC-013 зависит
   от деконструкции вариантов).

### Цели проектирования

- **Деконструкция вариантов пригодна к использованию**: `match r { ok(v) => ..., err(e) => ... }` и
  деконструкция пользовательских наборов вариантов семантически согласованы на всех путях
  исполнения.
- **На полноту можно полагаться**: E1030/E1031 реально эмитируются, пропуск ветки в match является
  ошибкой компиляции.
- **Stub устранён**: неподдерживаемые образцы приводят к ошибке компиляции, а не молча идут по
  неверному пути (предохранитель #330 — эта переходная стратегия поэтапно замещается реальным
  кодированием в период реализации, и в конечном счёте все stub полностью устранены).

## Предложение (утверждено и реализовано 2026-09-27)

| Возможность                                  | Статус | Описание                                                                                                                     |
| -------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Union-образцы вариантов                      | ✅     | `Variant` / `Variant(binding)` / многонагрузочный `make(a, b)` + связывание нагрузки в область видимости ветки               |
| Образцы Struct / Tuple                       | ✅     | Образцы полей (сокращённое связывание / `имя: подобразец`), образцы кортежей; объявленные поля должны быть полностью покрыты |
| Или-образцы и страж                          | ✅     | `p1 \| p2` и `pat if cond`: цепочка отказов уровня альтернатив, отказ стража переходит к следующей ветке                     |
| Проверка полноты                             | ✅     | E1030 пропущенная ветка, E1031 недостижимая, область видимости покрывает набор вариантов                                     |
| Утверждение семантики образца-идентификатора | ✅     | Утверждено как **связывание** (см. раздел ниже)                                                                              |

## Проектные решения

### Образец-идентификатор: связывание, а не присваивание и не сравнение

Голый идентификатор `y` в `match x { y => ... }` утверждён как **связывание** — вводит новое имя,
принимающее сопоставленное значение, всегда совпадает (эквивалентно именованному шаблону-джокеру).
Три основания:

1. **Структурный аргумент**: в позиции образца идентификатор естественно имеет две роли — позиция
   дискриминатора (`ok` в `ok(v)`, сверяется с таблицей вариантов) и позиция листа (`v` в `ok(v)`,
   связывание). В таблице параметров (лямбда) есть только позиция листа, поэтому двусмысленности
   нет; голый идентификатор одновременно стоит в позиции дискриминатора и выглядит как лист — отсюда
   двусмысленность. В YaoXiang имеется статическая таблица вариантов: имя дискриминатора разрешается
   по «попаданию в таблицу» (голова образца — это имя или литерал из набора вариантов scrutinee →
   дискриминатор; непопадающее голое имя → связывание), соглашение о регистре в стиле Rust не
   требуется.
2. **Вырожденность сравнения значений**: «уже связанное имя в образце означает равенство» (семантика
   унификации) — наследие традиции однократного присваивания; в изменяемом языке невозможно
   статически определить «связано ли уже», такая семантика не работает. В YaoXiang переменные
   допускают переприсваивание (`mut`), следуем законодательству Rust.
3. **Необходимость сопоставления с уже имеющимся значением относится к стражу**:
   `n if n == threshold` (перед посадкой стража пишется цепочка if).

**Связывание — не присваивание** (согласованная с владельцем формулировка от 2026-09-27): связывание
в образце вводит **новое имя**, действующее в пределах ветки, затеняющее одноимённую переменную во
внешней области и исчезающее при выходе из ветки (проба: внешний `v = 999` после попадания в
`some(v)` остаётся неизменным); присваивание — это перезапись уже существующего имени
(законодательство E2010/`mut`). Оба сосуществуют в языке как раздельные понятия, `=`
маршрутизируется по наличию имени (spec §4.3, приоритет присваивания), позиция образца принадлежит
только стороне связывания.

### match — выражение, а не оператор присваивания

`match` выдаёт значение попавшей ветки (значение всего выражения), `v = match ...` — это лишь
обычный синтаксис связывания, принимающий его. Зубы проверки полноты происходят из «ветвь обязана
выдавать значение»: пропущенная форма = принимающая сторона не получает значения = ошибка компиляции
(E1030); операторный switch с пропущенной веткой может лишь молчать.

### Семантическая модель и реализация ветки

Ветка = **одноаргументная функция с табличкой**: `some(v) => body` ≈ `λv.body`, вызывается только
когда фактический аргумент имеет форму `some`; семантика связывания происходит из «слева — позиция
параметра». Разделяет с лямбдой общий источник `=>`. В реализации ветка **не является замыканием**:
рекурсивный IR-компилятор образцов (`compile_pattern`) инлайном испускает цепочку тестов
(VariantTag/LoadField/Eq + JmpIfNot) и извлечение нагрузки (VariantPayload), при попадании — падает
в тело ветки, при отказе — переходит к следующей ветке — нулевые накладные расходы на вызов.

### Или-образцы и стражи

- `p1 | p2`: альтернативы пробуются по порядку; неуспех неконечной альтернативы → следующая
  альтернатива, успех → извлечение нагрузки и прямой переход к телу ветки; неуспех конечной
  альтернативы → следующая ветка. **Наборы имён связывания каждой альтернативы должны совпадать**
  (E1033), одноимённые связывания разделяют предварительно выделенный регистр уровня ветки (тело
  всегда читает значение, записанное попавшей альтернативой).
- `pat if cond`: после попадания образца вычисляется `cond` (**связывания образца видимы для
  стража**), ложь — переход к следующей ветке. Условие стража должно давать `Bool`. **Ветвь со
  стражем не учитывается в покрытии полноты** (страж может не сработать, то же правило в Rust), но
  повторяющиеся ветви вариантов со стражем достижимы (это уточнение предыдущей ветви).

### Образцы структур

`Point { x, y: b }`: сокращённое связывание поля тем же именем, `имя: подобразец` рекурсивно.
**Объявленные поля должны быть полностью покрыты** (E1034 недостающие поля), неизвестные поля
отвергаются (E1042), повторное появление того же поля даёт E1032. Опускание имён через `..` и
образцы обобщённых структур пока не поддерживаются (см. открытые вопросы).

### Деконструкция вариантов (симметрично конструкции в RFC-010)

| Конструкция                        | Деконструкция      | Представление нагрузки                                                                                   |
| ---------------------------------- | ------------------ | -------------------------------------------------------------------------------------------------------- |
| `Result(Int, String).ok(5)`        | `ok(v)`            | Одна нагрузка: прямое связывание                                                                         |
| `Pair.make(3, 4)`                  | `make(a, b)`       | Множественная нагрузка: упаковка в кортеж, распаковка по позициям                                        |
| `Color.red()` / `Option(T).none()` | `red()` / `none()` | Нулевая нагрузка: `pattern: None`, проверка арности (запись `ok()` для варианта с нагрузкой даёт ошибку) |

Тип нагрузки = параметры варианта с заменой на аргументы типа scrutinee (порядок объявления);
вложенные образцы (`ok(some(v))` через sum-типы, `Point { pos: Tuple(a, b) }` через структуры)
рекурсивны по подтипам.

### Полнота и достижимость

- **E1030 (недостаточное покрытие, полная полнота)**: scrutinee **любого типа** — нет резервной
  ветки, проверяется покрытие. Sum-типы: набор вариантов должен быть полностью покрыт безстражными
  Union-ветвями (ветви со стражем не учитываются, страж может не сработать); не-sum-типы: область
  значений открыта (Int/String/Char и т.д.), литеральные ветви не могут быть полными, **требуется
  резервная ветка**. Перечислимые исключения: две литеральные ветки `true`+`false` для Bool
  исчерпывают; Void не имеет обитаемых значений, vacuously полон. (Утверждено владельцем 2026-09-27:
  match без резервной ветки — это неявное предположение «остальные значения не возникают» — там, где
  неявное неуместно, не неявно; предположение должно быть записано как `_`.)
- **E1031 (недостижимая)**: любая ветвь после резервной ветки (безусловно срабатывающие
  неопровержимые образцы: Identifier/Wildcard/Tuple/Struct, без стража); безстражные повторяющиеся
  ветви вариантов, повторяющиеся литеральные ветви.

### Диагностика

| Код   | Значение                                                                                  |
| ----- | ----------------------------------------------------------------------------------------- |
| E1030 | Неполный перебор образцов (перечисляет отсутствующие варианты)                            |
| E1031 | Недостижимый образец (после резервной ветки / повтор варианта / повтор литерала)          |
| E1032 | Повторное связывание в образце (то же имя встречается многократно в одном образце)        |
| E1033 | Несогласованные связывания в или-образце (наборы имён связывания альтернатив различаются) |
| E1034 | Отсутствует поле в образце структуры                                                      |
| E3008 | Предохранитель уровня IR сохранён (защитная ветвь, нормальная программа недостижима)      |

### Границы с присваиванием/лямбдой (памятка против путаницы)

- Связывание в образце ≠ присваивание: вводит новое имя против перезаписи существующего
  (E2010/`mut`);
- Или-образец ≈ расширение лямбда-применения (семантическая модель), но реализован как
  инлайн-переход, а не вызов замыкания;
- Литеральный образец компилируется в Eq + цепочку условных переходов — интуиция «оптимизированной
  формы if/elif» работает для литералов, приращение match состоит в распознавании формы и распаковке
  связывания.

## Точки реализации

- parser: `parse_pattern` (реконструкция вызова варианта / ветвь `Ident { .. }` для образцов
  структур / восстановление вложенных или-образцов), флаг `no_fat_arrow` в `parse_match` для сборки
  или-образцов и стражей (чтобы `=>` не выступал лямбда-инфиксом)
- typecheck: унифицированный цикл ветвей в `check_match_expr` + рекурсивный проверщик
  `check_pattern` (регистрация связываний, проверка Bool для стража, учёт полноты)
- ir_gen: рекурсивный компилятор образцов `compile_pattern` + зеркало `sum_type_variants`, несущее
  типы нагрузок и `sum_type_param_names` (типы нагрузок заменяются аргументами типа scrutinee)
- Корпус: `02-type-system/pattern_destructure.yx`, `pattern_or_guard.yx`; модульные тесты
  E1030/E1031/E1032/E1033/E1034 (rfc011b.rs)

## Открытые вопросы

- [x] Образец-идентификатор: связывание новой переменной или сопоставление с уже существующим
      значением? → **Связывание** (позиция дискриминатора разрешается поиском в таблице вариантов,
      без соглашения о регистре); сопоставление с уже существующим значением относится к стражу.
- [x] Границы применимости полноты: → **Полная полнота** (утверждено владельцем 2026-09-27) — для
      не-sum-типов match без резервной ветки также даёт E1030, перечислимые исключения только
      двойной литерал Bool и Void.
- [x] Переходный период перед исправлением: давать ли сначала ошибку компиляции на ошибочное
      совпадение stub-загрузки 0? → Да (предохранитель #330), всё уже замещено реальным
      кодированием.
- [ ] Нужно ли опускание имён `..` в образцах структур (часть полей + резерв)? (Влияет на правило
