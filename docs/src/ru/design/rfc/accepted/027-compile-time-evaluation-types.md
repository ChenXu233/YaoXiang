# RFC-027: Предикаты времени компиляции и унифицированная статическая верификация

>
> - [RFC-009: Модель владения](../accepted/009-ownership-model.md)
> - [RFC-010: Унифицированный синтаксис типов — модель name: type = value](../accepted/010-unified-type-syntax.md)
> - [RFC-011: Проект системы обобщённых типов](../accepted/011-generic-type-system.md)
> - [RFC-024: Модель параллелизма на основе блоков spawn](../accepted/024-concurrency-model.md)
>
> **Заменяет**:

> — устарел

## Резюме

Данный документ предлагает ввести в YaoXiang **предикаты времени компиляции** как полноправных
граждан первого класса, унифицируя всю статическую верификацию времени компиляции в единый
**конвейер доказательств**. Предикат времени компиляции — это не внешняя спецификационная аннотация
— это функция. Функция, возвращающая Type, может использоваться в позиции типа, и компилятор
вызывает её во время компиляции и проверяет возвращаемое значение. Тип — это утверждение, вычисление
во время компиляции — это доказательство.

**Центральный тезис**: единственная задача проверки типов во время компиляции — построить и
верифицировать терм доказательства. Равенство типов, конфликты токенов, редукция зависимых типов,
вычисление предикатов времени компиляции, импликации логики Хоара — всё это разные проверки типов в
конвейере доказательств времени компиляции, разделяющие один конвейер. SMT-решатель — это ускоряющий
модуль проверщика типов, а не независимый корень доверия. Когда компилятор возвращает Unproven,
программист пишет функцию на YaoXiang в качестве доказательства — проверщик типов верифицирует её
точно так же, как верифицирует возвращаемый тип любой функции. Всё — код на YaoXiang, всё
верифицируется проверщиком типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это аннотация, отдельная от типов
    //! ensures: ExistsMax(result, arr[0..n])   ← это аннотация, отдельная от типов
}
```

Это совершает фундаментальную ошибку изоморфизма Карри-Ховарда: **разделяет спецификации и типы на
два слоя**. Аннотация — это не тип. Аннотация не участвует в проверке типов. Аннотация — это
ментальная модель «внешнего инструмента».

Белая книга говорит ясно:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Аннотации `//!` из RFC-022 — это внешний синтаксис, отдельный от системы типов
- Спецификационные типы и обычные типы — это две системы, что приводит к концептуальной избыточности
- Модель расщепления «Debug Build верифицирует / Release Build игнорирует» подрывает унификацию
- SMT-решатель в традиционном восприятии позиционируется как внешний инструмент — YaoXiang
  встраивает его как ускоряющий модуль проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов идут по разным путям

### Корректная ментальная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — являются подзадачами этой функции. Они разделяют один
конвейер доказательств и отличаются только сложностью терма доказательства и стратегией построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство —
возвращаемый тип этой функции равен доказываемому утверждению. Проверщик типов верифицирует её. Это
та же операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип как утверждение, верификация как проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри — это утверждение, и
компилятор гарантирует истинность каждого элемента — либо автоматическим доказательством, либо
предоставлением функции-доказательства программистом.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  компилятор гарантирует, что data — Array(T)
```

**Обобщённые типы — частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в сигнатуре    {} содержит только утверждения
#          компилятор верифицирует x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре   компилятор верифицирует type_of(T) == Type, type_of(data) == Array(T)
```

Та же модель: `name: (params) -> Type = { утверждения }`. Компилятор не различает «утверждения о
типах» и «утверждения о значениях» — всё это цели вычисления в конвейере доказательств.

**Инварианты цикла не нужно записывать отдельно. Аннотация типа на переменной — это инвариант
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # компилятор верифицирует: s_new == sum(arr[0..i+1])
        i += 1       # i изменён → запускает повторную верификацию зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. Когда конвейер
доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически. Не нужно
`: decreases`, не нужно `: Invariant`, не нужно индуктивное доказательство — компилятор
декомпозирует индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции на типах параметров и возвращаемого значения

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции выступают как
аннотации типов параметров или возвращаемого значения.

**На стороне параметров это вызов функции.** Предикат времени компиляции — это функция, возвращающая
Type, и её использование на стороне параметра — это её вызов — точно так же, как `factorial(5)`.
Сторона возвращаемого значения вводит новое понятие: формальный параметр возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive как аргумент
#                       компилятор в точке вызова извлекает значение аргумента, подставляет в b, верифицирует Positive(аргумент)
#                       Пример: divide(10, 2) → верифицирует Positive(2) = { 2 > 0 } → True
#                       Пример: divide(10, 0) → верифицирует Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возвращаемого значения, значение предоставляется return
#                                            компилятор в точке return подставляет возвращаемое значение, верифицирует постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **На стороне параметров**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся
  в `Positive` как аргумент. Синтаксис вызова функции, ноль неявностей.
- **На стороне возвращаемого значения**: `-> (result: IsMax(T, arr, result))` — `result` —
  формальный параметр возвращаемого значения, значение предоставляется оператором `return`. `result`
  существует только в сигнатуре типа, на него ссылаются только предикаты, не попадает в область
  видимости тела функции, не появляется у вызывающего.
- **Формальный параметр возвращаемого значения опционален**: при отсутствии постусловия не пишется,
  сигнатура полностью совпадает с обычной функцией (`-> Int`).
- **Унификация**: параметры и формальные параметры возвращаемого значения — одно и то же понятие —
  `имя: вызов_предиката(имя)`, отличие только в том, предоставляется ли значение вызывающей стороной
  или оператором `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно. Когда значение времени выполнения попадает в параметр уточнённого типа,
компилятор завершает верификацию путём сбора путевых условий и проверки импликации через SMT — без
явной передачи доказательства программистом.

#### 3.1 Явный вызов функции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно — это вызов функции, ноль неявностей.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предиката времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, возвращаемый тип),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — вызов функции
// после нормализации: b: { b > 0 }
```

Компилятор не должен неявно заполнять аргументы — `b: Positive(b)` подобно `f(5)`, это вызов
функции. `b` связывается как имя параметра, и его аннотация типа `Positive(b)` ссылается на сам `b`
— это стандартная модель зависимых типов, а не правило неявного раскрытия.

**Унификация с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а просто
конвенциональное имя параметра («написать `p`, `this`, `x` — совершенно одинаковый эффект»).
`b: Positive(b)` разделяет тот же механизм — имя параметра может использоваться в аннотации типа.
`self` появляется в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, и обе
аннотации типа ссылаются на сам параметр. Различие только в сложности аннотации типа, механизм
полностью идентичен — после привязки имени тип может зависеть от этого имени.

Возвращаемый тип также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возвращаемого значения, Sorted(result) — вызов функции
//                        компилятор в точке return подставляет возвращаемое значение в result, верифицирует Sorted(возвращаемое_значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевые условия, формируя **множество гипотез** текущей области видимости. Эти гипотезы участвуют в
верификации как фоновые знания для вычисления Bool во время компиляции.

```yaoxiang
if y > 0 {
    // компилятор автоматически получает гипотезу в этой ветви: { y > 0 }
    let result = divide(x, y)
    // условие верификации: (y > 0) ⇒ (y > 0)
    // конвейер доказательств устанавливает импликацию → Proved
} else {
// гипотеза в этой ветви: { !(y > 0) }
// если вызвать divide(x, y), условие верификации: !(y > 0) ⇒ y > 0
    // конвейер доказательств устанавливает, что импликация не выполняется → Disproved
}
```

Это не зашитые в компилятор специальные шаблоны — это естественное поведение конвейера доказательств
времени компиляции. Каждая точка проверки типов отправляет в конвейер:

```
{фоновые_гипотезы} ⇒ {цель_верификации}
```

Конвейер доказательств устанавливает импликацию. Proved → проходит, Disproved → ошибка компиляции +
контрпример, Unproven → ошибка компиляции + нерешённое утверждение. Фоновые гипотезы берутся из
путевых условий текущей точки программы.

#### 3.3 Стек гипотез

Компилятор при анализе потока управления поддерживает множество гипотез для каждого базового блока:

- **if-guard**: `if y > 0` → истинная ветвь помещает `y > 0`, ложная ветвь помещает `!(y > 0)` (при
  наличии else)
- **match-паттерн**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **логические связки**: `if x > 0 and y < 10` → в ветвь помещаются `x > 0` и `y < 10`
- **предусловие функции**: при вызове `divide(a, b)`, `b` должен удовлетворять `Positive`, причём
  доказательство берётся либо из текущих гипотез, либо из самой аннотации уточнённого типа аргумента
  (если `b` уже аннотирован как `Positive`, то его тип несёт `b > 0`)
- **присваивание**: при `let z = y` существующие уточнённые условия `y` передаются `z`

Все гипотезы поступают в конвейер доказательств времени компиляции. При входе в путь SMT-ускорения
они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Без статического доказательства — ошибка компиляции

Если программист пишет прямо:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей точке программы нет гипотезы `y > 0`, и сам аргумент `y` не имеет аннотации типа
`Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация не выполняется) → ошибка компиляции:

> Невозможно доказать, что параметр `b` в вызове `divide` удовлетворяет `Positive`. `y` приходит из
> ввода функции, без доказанных границ. Рассмотрите охрану вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не принимает значения времени выполнения, напрямую попадающие в параметры уточнённого типа,
без предоставления статического доказательства. Это не ограничение — это ядро философии жёсткой
безопасности. Код, который компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Связь с унифицированным конвейером

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
доказательств времени компиляции на анализ потока управления:

| Этап                                 | Обязанность                                                                                                                                                                         |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий                 | Этап анализа потока управления компилятора, аннотирует множество гипотез для каждого базового блока                                                                                 |
| Генерация условий верификации        | При обнаружении ограничения типа, требующего верификации, объединяет путевые условия + информацию о типе аргумента                                                                  |
| Вычисление в конвейере доказательств | Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven                                                                                                          |
| Результат                            | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + нерешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновые знания
конвейера доказательств — разделяют один конвейер и одну систему бюджета с равенством типов и
ограничениями заимствований.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции разделяют один конвейер. Основная операция конвейера — **проверка
типов** — проверка, равен ли тип терма доказательства доказываемому утверждению. Всё — проверка
типов.

```
Во время компиляции встречается выражение Bool, требующее вычисления (т.е. требующее построения терма доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → компилятор выносит прямое решение (структурная эквивалентность)
        │
        ├── Условие конфликта токенов (!conflicting(tokens))
        │   → потокочувствительный анализ живости (отслеживание свойств Dup/Linear)
        │
        ├── Редукция зависимых типов (n + m упрощение)
        │   → система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикат времени компиляции (x > 0, forall...)
        │   → ядро компилятора + ускоряющий модуль SMT
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → ядро компилятора + ускоряющий модуль SMT
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → компиляция проходит
             │ Disproved│  → ошибка компиляции + контрпример
             │ Unproven │  → ошибка компиляции + нерешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код на YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ──→ Proved ──→ компиляция проходит
                  │
                  ▼
            Верификация не прошла → ошибка компиляции: «доказательство не установлено»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — это неизбежное следствие проблемы
остановки и естественное разбиение теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → остановка, терм доказательства построен, проверка типов прошла. Компиляция
  продолжается.
- **Disproved(M)** → остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → в пределах данного лимита ресурсов терм доказательства не построен. Ошибка
  компиляции + нерешённое утверждение + отчёт о потреблении бюджета.

**Unproven ≠ False.** Когда компилятор говорит «я не могу это доказать», это не эквивалентно
ложности утверждения — это просто превышение возможностей текущего автоматического доказательства.
Это честность, а не дефект.

Жёсткий лимит бюджета — инженерное решение проблемы остановки. Никаких ручек — дать ручку значит
спросить пользователя «как вы думаете, остановится ли ваша программа», пользователь не знает,
компилятор тоже не знает.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция на YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверщик типов
верифицирует эту функцию — точно так же, как верифицирует `add(a, b): Int`.

```
утверждение = тип
доказательство = программа (значение этого типа)
верификация = проверка типов (единственный корень доверия)
```

SMT-решатель — не независимый корень доверия — это **ускоряющий модуль проверщика типов**. SMT
помогает найти доказательство, но верифицирует доказательство всегда проверщик типов. Когда SMT
возвращает `unsat`, компилятор реконструирует его результат как терм доказательства, верифицируемый
проверщиком типов. Если реконструкция не удалась (шаги вывода SMT выходят за правила вывода ядра
компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: уточнённое свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, возвращаемый тип которой — вышеуказанное утверждение
# Проверщик типов верифицирует эту функцию — точно так же, как верифицирует add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # компилятор здесь верифицирует: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Никакого ИИ, никакого экспорта в Coq, никаких новых концепций. **Свойства, которые компилятор не
может доказать автоматически → программист пишет доказательство в коде YaoXiang → проверщик типов
верифицирует.** Весь процесс — плавный градиент — компилятор берёт на себя простые доказательства,
оставляя сложные вам.

#### 4.3 Многоуровневые зависимости внутри конвейера

Вышеуказанные вычислители разделяют один интерфейс, но имеют порядок вычисления. Равенство типов —
предпосылка для всего последующего анализа; проверка владения/токенов зависит от информации о типах;
верификация уточняющих предикатов зависит от результатов предыдущих двух слоёв. Компилятор вычисляет
по слоям — выражения, не прошедшие нижний слой, не поступают на верхний — избегая траты бюджета
решения на программу с ошибками типов.

```
Порядок вычисления (один конвейер, многоуровневая диспетчеризация)
├── Слой 0: равенство типов (T1 == T2)
│   └── структурная унификация → при неудаче остальное бессмысленно, сразу Disproved
├── Слой 1: конфликты владения/токенов
│   └── потокочувствительный анализ живости → при неудаче безопасность памяти не установлена, сразу Disproved
└── Слой 2: уточняющие предикаты / импликации Хоара
    └── ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя один интерфейс и одну
систему бюджета.

### 5. Унификация трёх слоёв функций

| Слой                        | Время выполнения | Вход          | Выход    | Пример                                         |
| --------------------------- | ---------------- | ------------- | -------- | ---------------------------------------------- |
| Функция уровня значений     | Время выполнения | Значения      | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типов           | Время компиляции | Типы/значения | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат времени компиляции | Время компиляции | Значения      | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют одинаковый синтаксис `name: type = value`. Предикаты времени компиляции и
конструкторы типов идут по одному конвейеру доказательств времени компиляции — `{}` — это
пространство доказательств.

### 6. Циклы: генерация условий верификации Флойда-Хоара

Для циклов не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Уточняющие
предикаты на переменных определяют утверждения в стиле Флойда-Хоара — компилятор генерирует условия
верификации из аннотаций типов, а конвейер доказательств проверяет, сохраняет ли каждое присваивание
тип.

Основной механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует одно условие верификации для тела цикла — когда
конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i; при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # верификация: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # компилятор генерирует одну VC для тела цикла. Посылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не меняется)
        #   Подставляя s_new = s_old + arr[i]:
        #     требуется s_old + arr[i] == sum(arr[0..i+1])
        #     из индуктивной гипотезы s_old == sum(arr[0..i]), прибавляя arr[i] к обеим сторонам:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменён → в графе зависимостей аннотация типа s ссылается на i → запускается повторная верификация
        #   Новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   Т.е. s == sum(arr[0..i_new]), гарантируется предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # в этой точке s: SumUpTo(arr, arr.len), т.е. s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант и не нужно «автоматически проводить
индукцию» — он декомпозирует индуктивное доказательство на локальные условия верификации для каждой
операции присваивания, передавая их в конвейер доказательств по принципу «разделяй и властвуй».

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеуказанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i` — когда `i` изменяется, ограничение типа `s` также изменяется. Это требует, чтобы
компилятор поддерживал **граф зависимостей типов между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# Ключ — зависимая переменная, значение — множество переменных, на которые ссылается аннотация типа
# Пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: при обработке `mut v: Pred(... x ...) = init` проверщик типов анализирует свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылка на другую изменяемую переменную
`x` в текущей области видимости, в графе зависимостей записывается `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает значение путём присваивания, компилятор:

1. Ищет в графе зависимостей все переменные, зависящие от `x`: `{v₁, v₂, ...}`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательств

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественно принудительно
обеспечивает правильный порядок присваивания. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменён → повторная верификация: s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отклоняет
i += 1        # i изменён → повторная верификация: s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Комбинированные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` зависит одновременно от `x` и `y` — изменение любой из них запускает
повторную верификацию.

**Связь с конвейером доказательств**: отслеживание зависимостей — триггер генерации VC, а не
независимый механизм верификации. Оно отвечает на вопрос «когда нужно генерировать VC» — конвейер
доказательств отвечает на вопрос «выполняется ли VC».

### 7. Проверка завершения

Полная автоматизация времени компиляции как приоритет. Циклы, которые компилятор может доказать,
проходят; циклы, которые автоматическая стратегия не может доказать, сразу вызывают ошибку
компиляции — программист должен позволить компилятору автоматически анализировать завершение цикла.
Никаких лазеек через **аннотационный синтаксис** (не вводится аннотация вроде `decreases`;
неподдерживаемое всегда остаётся синтаксической позицией, а не функцией).

> **Поправка (RFC-027a, 2026-09-14)**: для обязательств завершения, которые автоматическая стратегия
> не может доказать, программист может предоставить функцию-меру и функцию-доказательство завершения
> (`Terminates`) в качестве подстраховки — обе являются обычными функциями YaoXiang, ноль нового
> синтаксиса, верифицируются проверщиком типов. Принцип приоритета полной автоматизации не меняется,
> подстраховка происходит только после Unproven. См.
> [RFC-027a: Подстраховка функцией-доказательством для проверки завершения](../draft/027a-termination-proof-fallback.md).

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершения, из двух
источников:

1. **Аннотации типов переменных**: ограничения границ в уточнённых типах (например, `UpTo(n)` даёт
   верхнюю границу `n` и нижнюю `0`)
2. **Операции в теле цикла**: операции, применяемые к переменным на каждой итерации

Компилятор пытается применить четыре стратегии синтеза мер в порядке приоритета; найдя подходящую,
останавливается.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменные имеют аннотации линейных границ, компилятор перебирает кандидаты линейных мер и
верифицирует через SMT.

```
Вход:
  Переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с верхней и нижней границами)
  Условие цикла cond
  Множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типов: [low_i, high_i]
  2. Перебрать кандидаты мер: v_i, u_i - v_i, v_i - v_j и т.д., линейные комбинации
  3. Для каждого кандидата m:
     - SMT верифицирует m ≥ 0 (из границ типов)
     - Для каждого пути выполнения в теле цикла SMT верифицирует m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершение доказано
```

Покрытие: циклы, в которых переменные получают значения через линейные выражения (`v = a·v + b`) и
имеют аннотации ограниченных типов. Включая `i += const`, `i -= const`, а также сокращение
интервалов в стиле двоичного поиска:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# Мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: подсчёт нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, при реализации Фазы 3 будет решено о включении
> на основе реальной выполнимости.** Эта стратегия работает для операций обмена соседних элементов
> (сортировка пузырьком, сортировка вставками), но не может автоматически доказать не соседние
> операции (быстрая сортировка partition, пирамидальная сортировка sift-down). Границы покрытия см.
> в таблице ниже. Если на Фазе 3 верификация покажет невыполнимость, эта стратегия будет удалена или
> понижена до будущей работы.

Ключевое наблюдение: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  Целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  Операции в теле цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операции на меру:
     - Обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - Затрагивает только пары с индексами j-1, j, j+1
     - Если arr[j] > arr[j+1] (нарушение предиката), после обмена пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя: 0
  → Завершение доказано
```

**Текущее покрытие**:

| Алгоритм                 | Шаблон операции      | Стратегия 2 доказуема? | Причина                                               |
| ------------------------ | -------------------- | :--------------------: | ----------------------------------------------------- |
| Сортировка пузырьком     | Обмен соседних       |           ✅           | violation_count строго убывает при каждом обмене      |
| Сортировка вставками     | Перемещение соседних |           ✅           | Каждое перемещение устраняет одну нарушающую пару     |
| Сортировка выбором       | Несоседний обмен     |           ❌           | Один обмен может увеличить violation_count            |
| Быстрая сортировка       | Разбиение partition  |           ❌           | Несоседний обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌           | Древовидная операция, violation_count не монотонна    |

**Комплементарные стратегии**: для быстрой сортировки сокращение интервала `low < high` покрывается
Стратегией 1 (линейная ранговая функция) — рекурсия partition на внешнем уровне, интервал каждый раз
уменьшается вдвое. Стратегии 1 и 2 дополняют друг друга, и завершение большинства практических
алгоритмов может быть доказано одной из них. Однако обобщение Стратегии 2 (несмежные операции,
древовидные операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: ограниченные шаблоны инкремента/декремента

`v += const` (const > 0), переменная имеет аннотацию верхней границы → мера `upper_bound - v`
убывает на `const` каждую итерацию, нижняя граница 0. Это вырожденный случай Стратегии 1, компилятор
обрабатывает его первым делом.

#### 6.5 Стратегия 4: шаблон меры с мультипликативным масштабированием

`v *= const` (const > 1), переменная имеет аннотации верхней и нижней границ. Компилятор имеет
встроенный шаблон логарифмической меры `ceil(log_const(upper/v))`, мера убывает на 1 при каждом
умножении на const.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # компилятор автоматически выводит: мера ceil(log₂(n/i)), при каждом умножении на 2 мера убывает на 1
    i *= 2
}
```

#### 6.6 Разделение завершения и корректности

Доказательство завершения и доказательство корректности независимы:

- **Завершение**: четыре вышеуказанные стратегии автоматически доказывают, что цикл завершается за
  конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  времени компиляции через условия верификации

Оба проходят → компиляция проходит. Завершение доказано, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершение не может быть доказано → ошибка
компиляции с указанием переменной или операции, которую не удалось проанализировать. Оба не прошли →
ошибка компиляции с раздельным указанием причин обеих неудач.

#### 6.7 Проверка завершения рекурсивных функций

Для рекурсивных функций, которые необходимо вычислить во время компиляции, компилятор проверяет
убывание аргумента:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # компилятор анализирует: n-1 < n → убывание → завершение
}

# Использование во время компиляции — компилятор гарантирует завершение factorial во время компиляции
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, завершается во время компиляции
```

| Сценарий                                                                 | Поведение                        |
| ------------------------------------------------------------------------ | -------------------------------- |
| Компилятор может проанализировать рекурсивное убывание (например, `n-1`) | Вычисление во время компиляции   |
| Не убывает / невозможно определить убывание                              | Ошибка компиляции                |
| Вызов во время выполнения (не в позиции типа)                            | Проверка завершения не требуется |

#### 6.8 Жёсткая граница

`i = f(i)`, где `f` необратима, незамкнута и не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершение. Ошибка компиляции:

> Этот цикл не может быть автоматически доказан как завершающийся. Переменная цикла зависит от
> неанализируемой функции `f`. Пожалуйста, используйте шаблон итерации, анализируемый компилятором,
> или предоставьте функцию-меру и функцию-доказательство завершения (см. RFC-027a).

Это не провал компилятора. Код, который невозможно статически доказать как безопасный, не проходит
компиляцию.

### 8. SMT-решатель: ускоряющий модуль проверщика типов

В традиционных языках SMT-решатель — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang — это **ускоряющий модуль проверщика типов** — вызывается только тогда, когда ядро
компилятора не может вынести решение напрямую. SMT помогает найти доказательство, но верифицирует
доказательство — проверщик типов.

**Модель доверия**: проверщик типов — единственный корень доверия. SMT-решатель — ускоряющий модуль
— он помогает найти доказательство, но SMT не является независимым корнем доверия. Компилятор
доверяет результату `unsat` от Z3 (согласуется с подходом F\*/Dafny — вероятность ошибки Z3 ниже
частоты багов самого компилятора, что является инженерно прагматичным выбором). Истинная
ненадёжность контролируется на уровне трансляции в SMT — если в трансляции есть баг, компилятор
проявит его в других тестах.

**Интерфейс**: внутренняя трансляция компилятора — в стандартный формат SMT-LIB 2.6, без привязки к
API конкретного решателя. SMT-LIB — стандарт ISO, Z3, CVC5, MathSAT, Yices все поддерживают его
нативно.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, самая широкая документация и валидация сообществом). CVC5
как SMT-LIB-совместимая альтернатива — пользователь может переключать через флаги компилятора.

Не делаем «универсальный слой абстракции решателя» — SMT-LIB и есть слой абстракции. В будущем, если
CVC5 добьётся прорыва в определённой теории, переключение потребует только замены бинарника, без
изменения кода компилятора.

```
Выражение Bool времени компиляции
        │
        ├── Ядро компилятора может вынести решение напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → сразу возвращает Proved / Disproved
        │
        └── Ядро компилятора не может вынести решение напрямую (кванторы, символьные переменные)
            → предварительная редукция зависимых типов (factorial(5) → 120)
            → трансляция в формат SMT-LIB
            → отправка в Z3/CVC5 (с ограничением бюджета)
            → возвращаемое значение: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткое ограничение, как глубина стека**:

| Измерение бюджета                 | Значение по умолчанию | Пояснение                                                                                                                                                       |
| --------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10 000                | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывают 99% реальных предикатов.                                                   |
| Время                             | 100 мс                | Один предикат более 100 мс = пользователь пишет программу времени компиляции, а не аннотацию типа. 100 мс × 50 предикатов = верхний предел 5 секунд компиляции. |
| Глубина инстанцирования кванторов | 3                     | Три уровня вложенных кванторов покрывают практические шаблоны. Более трёх уровней — скорее всего, логические упражнения.                                        |

Превышение бюджета → Unproven, ошибка компиляции + позиция предиката + объём потребления. Никакой
деградации, никаких проверок времени выполнения, никакого тихого прохода.

**Почему это практически выполнимо**: в инженерной практике 95% реальных предикатов — линейная
арифметика — `x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в пределах разрешимого фрагмента,
SMT-решатель для таких задач возвращается за миллисекунды. При столкновении с редкими сложными
предикатами, превышающими бюджет, программист пишет функцию-доказательство.

Зависимые типы проходят предварительную редукцию перед вызовом SMT: `factorial(5)` напрямую
вычисляется во время компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти
детерминированные вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Ментальная модель: **компилятор может доказать —
проходит, не может — сообщает об ошибке — если компилятор не умеет, вы можете написать
функцию-доказательство и показать ему.**

### 9. Композиция предикатов времени компиляции

Предикаты времени компиляции — это функции, возвращающие Type, и композиция реализуется естественно
через композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ компилятор верифицирует Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ компилятор верифицирует Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ компилятор верифицирует InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ компилятор верифицирует InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: унификация диспетчеризации времени компиляции и времени выполнения

`assert` и `Assert` — это две стороны одного примитива уточнённого типа. Конвейер диспетчеризации
`dispatch` автоматически решает, идти ли по пути доказательства во время компиляции или проверки во
время выполнения, на основе **доступности свободных переменных предиката во время компиляции**:

| Критерий                                                                                                         | Режим           | Поведение                                                                                                       |
| ---------------------------------------------------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры обобщённых типов, константы времени компиляции) | **CompileTime** | В конвейер доказательств: Proved → стирается, Disproved → ошибка компиляции, Unknown → требуется доказательство |
| Существуют свободные переменные из времени выполнения (параметры функций, внешний ввод, переменные `mut`)        | **Runtime**     | Вставляется проверка времени выполнения, и уточняющий факт инжектируется в потокочувствительный Γ               |

**Ключевое**: «Не удаётся определить» ≠ «Опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихой деградации), в режиме Runtime утверждение во время компиляции вообще не
имеет значения истинности — никакой prover, каким бы сильным он ни был, не сможет написать
общезначимое доказательство для «пользователь мог ввести отрицательное число», проверка времени
выполнения — единственный soundness-выбор. Это не слабость prover'а, а теоретическая неизбежность.

### 12. Потокочувствительный Γ: распространение сильнейшего постусловия

Компилятор поддерживает потокочувствительный (flow-sensitive) Γ — множество гипотез, отслеживающее
истинные утверждения в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← распространение SP
```

**Kill set для переменных `mut`**: после присваивания `mut` все гипотезы, включающие эту переменную,
удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убит
```

Это жёсткое требование soundness — значение переменной изменилось, старые гипотезы недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match, Γ берёт пересечение гипотез ветвей. Только
утверждения, истинные на всех путях, выносятся из ветви.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 о том, что «уточнённые типы полностью стираются во время выполнения», относится
к **proof witness (токену доказательства)** — терм доказательства, верифицированный во время
компиляции, не порождает кода времени выполнения. Но проверки времени выполнения, вставленные
dispatch в режиме Runtime, сохраняются — это проверка Bool на уровне значений, а не witness на
уровне типов.

Резюме: witness стираются, check сохраняются. Эти две вещи не конфликтуют, исходное утверждение
RFC-027 остаётся в силе.

## Подробное проектирование

### Изменения синтаксиса

| До (RFC-022)                          | После (данный RFC)                                                                                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Предикат времени компиляции как тип параметра `(b: Positive(b))`                                            |
| `//! ensures: ExistsMax(result, arr)` | Возвращаемый тип использует формальный параметр возвращаемого значения `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Уточняющие аннотации типов на переменных — инварианты Флойда-Хоара                                          |
| `//! decreases: n`                    | Компилятор полностью автоматически выводит функцию-меру                                                     |
| Спецификации — комментарии            | Спецификации — система типов                                                                                |

### Синтаксис

**Для предикатов времени компиляции нет новых ключевых слов.** `{}` — пространство доказательств,
полностью совпадающее с существующим синтаксисом определения типов. Предикат времени компиляции —
это функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. Использование — это
вызов функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Предикат времени компиляции = функция, возвращающая Type, {} содержит утверждения, верифицируемые компилятором
# Использует существующий синтаксис функций/типов, не требует новых правил BNF
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы применения предиката должны быть в форме констант времени компиляции** — литералы,
переменные (связанные по имени) или применения типов с одним аргументом (рекурсивное извлечение).
Непреобразуемые в константное выражение аргументы дают ошибку **E1092**, несоответствие числа
аргументов предиката — ошибку **E1093** — уточняющие ограничения **никогда не отбрасываются молча**
(ранее непреобразуемые аргументы приводили к молчаливому исчезновению ограничений, и связывание,
нарушающее ограничение, молча проходило).

**Новое синтаксическое понятие: формальный параметр возвращаемого значения** — в `-> (name: Type)`
`name` — формальный параметр возвращаемого значения.

Формальный параметр возвращаемого значения — это **единственное новое синтаксическое понятие**,
вводимое YaoXiang в существующий синтаксис функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылаются предикаты постусловий (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не попадает в область видимости тела функции, не появляется у вызывающего
- Формальный параметр возвращаемого значения **опционален** — при отсутствии постусловия сигнатура
  полностью совпадает с обычной функцией (`-> Int`), не вводя никакой дополнительной нагрузки

Причина его введения: постусловие должно ссылаться на «значение, которое функция собирается
вернуть». Без формального параметра возвращаемого значения компилятор может позволить предикату
ссылаться на возвращаемое значение только через специальные правила (например, неявная переменная
`$result` или `__retval__`). Формальный параметр возвращаемого значения делает такую ссылку явной —
это просто формальный параметр, только значение предоставляется `return`, а не вызывающей стороной.

**Функция-доказательство** — не новое понятие — это просто функция на YaoXiang, чей возвращаемый тип
является доказываемым утверждением. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверщик типов верифицирует её точно так же, как верифицирует
возвращаемый тип любой функции. Не нужно нового синтаксиса, новых ключевых слов, новых правил.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функция, принимающая
  значения и возвращающая Type, на том же уровне, что и конструктор типов
- **Взаимодействие с обобщёнными типами**: предикаты времени компиляции могут иметь параметры
  обобщённых типов, например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения, только чтение, не запись
- **Вывод типов**: аргументы предикатов времени компиляции участвуют в выводе типов HM

### Представление во время выполнения

Предикаты времени компиляции обрабатываются во время выполнения **по результату диспетчеризации
dispatch**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): токен-свидетельство
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представляется как `Int`. Уточняющее условие `{ 5 > 0 }` уже верифицировано, стирается.
- **Режим Runtime** (существуют свободные переменные времени выполнения): сохраняется проверка
  времени выполнения — выполняется проверка Bool на уровне значений, инжектируемая в
  потокочувствительный Γ. Подробности см. в §11 Конвейер диспетчеризации dispatch и §13 Уточнение
  модели стирания.

Помещение предиката времени компиляции в позицию типа (например, `f(x: Positive(x))`) не порождает
обёрточного типа, не выделяет дополнительную память. Но когда `x` приходит из ввода времени
выполнения, **будет** вставлена проверка Bool времени выполнения.

**Ограничения взаимодействия с `ref`**: предикаты времени компиляции могут ссылаться только на
неизменяемые заимствования или значения с переданным владением. На предикат времени компиляции,
ссылающийся на значение по изменяемому заимствованию, компилятор не может гарантировать во время
компиляции, что результат верификации останется действительным во время выполнения — такое
использование напрямую даёт ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, не требуют
   дополнительных правил разбора
2. **Конвейер доказательств времени компиляции**: унифицированный интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **Ускоряющий модуль SMT**: уровень трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, альтернатива
   CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/элиминация кванторов всеобщности. Это единственный корень доверия, SMT и доказательства
   программиста верифицируются через него
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёт о нерешённых утверждениях + привязка
   к позициям в исходном коде

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, совершенно не меняется
- ✅ Предикаты времени компиляции в режиме CompileTime дают нулевые накладные расходы во время
  выполнения, в режиме Runtime сохраняются только необходимые проверки Bool
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но RFC-022 никогда не был реализован, нет
  бремени миграции

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Ховарда**: тип — утверждение, программа — доказательство,
  `name: Proposition = Proof`
- **Унификация**: предикаты времени компиляции и обычные функции используют совершенно одинаковый
  синтаксис, без концептуального расщепления
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, ментальная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции и постепенно
  расширять покрытие
- **Минимальные накладные расходы во время выполнения**: режим CompileTime даёт нулевые накладные
  расходы, режим Runtime сохраняет только необходимые проверки Bool

### Недостатки

- **Время компиляции**: решение SMT увеличивает время компиляции, но жёсткое ограничение бюджета
  гарантирует контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами линейной арифметики
  первого порядка могут потребовать от программиста написания функций-доказательств. Это не дефект
  языка — это неизбежное следствие проблемы остановки. Компилятор честно сообщает Unproven, а не
  ложно объявляет True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Ховарда
- **Сложность реализации**: унификация конвейера доказательств времени компиляции требует
  тщательного проектирования

### Снижение рисков

- Жёсткое ограничение бюджета SMT (10 000 шагов / 100 мс / 3 уровня инстанцирования), превышение —
  Unproven
- Предварительная редукция зависимых типов: детерминированные вычисления значений съедаются первыми,
  SMT получает только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверщик типов
  верифицирует — точно так же, как верифицирует возвращаемый тип любой функции
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + отображение контрпримеров + отчёт о потреблении бюджета + нерешённые
  утверждения + предложения (если компилятор может их дать)

## Альтернативы

| Альтернатива                                                                             | Почему не выбрана                                                                                                                                                                |
| ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-022: спецификации как комментарии `//!`                                              | Спецификации и типы расщеплены, нарушает изоморфизм Карри-Ховарда                                                                                                                |
| Отдельные файлы спецификаций (например, CVL)                                             | Спецификации отделены от кода, увеличивает стоимость сопровождения                                                                                                               |

| Внешний помощник доказательств (например, Coq)                                           | Отрезан от компилятора, требует отдельного языка доказательств и корня доверия. Выбор YaoXiang: доказательство — это код YaoXiang, проверщик типов — единственный корень доверия |
| **Данный подход: предикаты времени компиляции как полноправные граждане первого класса** | ✅                                                                                                                                                                               |

## Стратегия реализации

### Разделение на фазы

| Фаза       | Содержание                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Фаза 1** | Ядро компилятора: структурная эквивалентность + βδι-редукция + введение/элиминация кванторов всеобщности. Поддержка простых арифметических предикатов (`x > 0`, `arr.len > 0`) |
| **Фаза 2** | Уровень трансляции в SMT-LIB + интеграция Z3/CVC5. Конвейер возвращает Proved/Disproved/Unproven. При Unproven поддерживается написание функций-доказательств программистом    |
| **Фаза 3** | Генерация VC инвариантов цикла + проверка завершения (линейная ранговая функция + подсчёт нарушений предиката + ограниченные шаблоны + контроль комбинаторного взрыва)         |
| **Фаза 4** | Инкрементальная верификация + кэширование + поддержка IDE                                                                                                                      |

## Открытые вопросы

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, самая широкая валидация). CVC5 как
      SMT-LIB-совместимая альтернатива, переключение через флаги компилятора. Внутренняя трансляция
      компилятора — в стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, не делаем
      собственный универсальный интерфейс решателя.
- [x] **Конкретные значения бюджета решения**: 10 000 шагов / 100 мс / 3 уровня глубины
      инстанцирования кванторов. Фиксированы внутри компилятора, без ручек. Если в реальном
      использовании окажется, что их недостаточно (а не «пользователь ошибся»), скорректируем.
- [x] **Диапазон поддержки кванторов**: язык не ограничивает порядок кванторов. Предикат времени
      компиляции принимает параметры Type — Type включает функциональные типы — поэтому кванторы
      высшего порядка — естественное следствие системы типов, не требуют специального синтаксиса.
      SMT-решатель может автоматически разрешать кванторы первого порядка (forall/exists, с
      поддержкой чередующейся вложенности, ограничено бюджетом глубины 3). Кванторы высшего порядка:
      SMT возвращает Unproven, компилятор предлагает «этот предикат выходит за пределы
      автоматического доказательства, предоставьте функцию-доказательство». Программист пишет
      функцию на YaoXiang, чей возвращаемый тип равен этому утверждению — проверщик типов
      верифицирует эту функцию. Не нужно внешнего экспорта, не нужно ИИ, не нужно интерактивного
      режима доказательства. Всё — код на YaoXiang, всё верифицируется проверщиком типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода используются напрямую как
      имена SMT-переменных (с префиксом модуля во избежание конфликтов). При возврате модели Z3
      выполняется обратный поиск по именам переменных. Формат вывода: имя переменной = конкретное
      значение + позиция в исходном коде + позиция определения предиката. Без сложного уровня
      отображения.
- [x] ~~**Взаимодействие предикатов времени компиляции с умными указателями `ref`?**~~ → Решено:
      предикаты времени компиляции допускают только неизменяемые заимствования или значения с
      переданным владением. Значения по изменяемому заимствованию не могут出现在 в предикате времени
      компиляции.
- [x] **Расширение меры подсчёта нарушений `forall` на несоседние операции?** → Не расширять.
      Текущее покрытие (обмен соседних, перемещение соседних) дополняется Стратегией 1 (линейная
      ранговая функция) — сокращение интервала во внешнем слое быстрой сортировки покрывается
      Стратегией 1, пирамидальная сортировка покрывается Стратегией 1 (шаблон индексов массива).
      Циклы, завершение которых не может доказать ни одна стратегия, вызывают прямую ошибку
      компилятора — это философия жёсткой безопасности, а не дефект. Если в будущем появится
      реальный сценарий (не академическая конструкция), в котором алгоритм не покрывается всеми
      четырьмя стратегиями, обсудим заново. → **Повторное обсуждение инициировано (2026-09-14,
      #318)**: неструктурная рекурсия (нода вроде gcd с непрямым убыванием, взаимная рекурсия,
      разбиение при слиянии) — это именно те реальные сценарии, которые ожидались в данном пункте —
      текущий конвейер не может автоматически доказать их завершение, и их невозможно переписать в
      анализируемый итеративный шаблон без ущерба читаемости. Заключение: приоритет полной
      автоматизации сохраняется; после Unproven добавляется подстраховка функцией-доказательством —
      мера и доказательство завершения являются обычными функциями YaoXiang, ноль нового синтаксиса,
      верифицируются проверщиком типов. Реализация в
      [RFC-027a: Подстраховка функцией-доказательством для проверки завершения](../draft/027a-termination-proof-fallback.md).
- [x] **Комбинаторный взрыв перебора линейных ранговых функций**: верхний предел числа переменных
      для перебора — 3 переменные с границами. ≤3 перебираем все линейные комбинации и верифицируем
      каждую через SMT. >3 пробуем только однопеременные меры (`v_i`, `u_i - v_i`), при неудаче
      сразу сообщаем об ошибке компиляции — подсказываем программисту «цикл имеет >3 переменных с
      границами, компилятор не может автоматически синтезировать многопеременную меру». Это не
      инженерный компромисс — это принуждение программиста писать более простые циклы.
