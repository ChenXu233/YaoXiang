## Резюме

Настоящий документ предлагает ввести в YaoXiang **компиляционные предикаты** как полноправных
граждан первого класса, объединив всю статическую верификацию на этапе компиляции в единый
**конвейер доказательства**. Компиляционный предикат — это не внешняя спецификационная аннотация —
это функция. Функция, возвращающая Type, может использоваться в позиции типа; компилятор вызывает её
на этапе компиляции и проверяет возвращаемое значение. Тип — это утверждение, вычисление на этапе
компиляции — это доказательство.

**Ключевой тезис**: единственная задача проверки типов во время компиляции — построить и
верифицировать терм доказательства. Равенство типов, конфликты токенов, редукция зависимых типов,
вычисление компиляционных предикатов, импликации логики Хоара — всё это разные проверки типов в
конвейере компиляционного доказательства, разделяющие единый конвейер. Решатель SMT — ускоритель
проверки типов, а не независимая граница доверия. Когда компилятор возвращает Unproven, программист
пишет функцию YaoXiang в качестве доказательства — проверка типов верифицирует её точно так же, как
верифицирует любой возвращаемый тип функции. Всё — код YaoXiang, всё проверяется проверкой типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это аннотация, отдельная от типа
    //! ensures: ExistsMax(result, arr[0..n])   ← это аннотация, отдельная от типа
}
```

Это фундаментальная ошибка изоморфизма Карри-Ховарда: **разделение спецификаций и типов на два
слоя**. Аннотации — это не типы. Аннотации не участвуют в проверке типов. Аннотации — это мысленная
модель «внешнего инструмента».

В белой книге сказано прямо:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Аннотации `//!` из RFC-022 — это внешний синтаксис, отделённый от системы типов
- Спецификационные типы и обычные типы — это две системы, что порождает концептуальную избыточность
- Режим «Debug Build верифицирует / Release Build игнорирует» нарушает единство
- Решатель SMT в традиционном понимании позиционируется как внешний инструмент — YaoXiang встраивает
  его как ускоритель проверки типов
- Проверка типов, верификация заимствований, проверка компиляционных предикатов, раскрытие макросов
  — каждая идёт своим путём

### Правильная мысленная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все компиляционные проверки — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация компиляционных предикатов — являются подзадачами этой функции. Они разделяют единый
конвейер доказательства, различаясь лишь сложностью терма доказательства и стратегией построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство —
возвращаемый тип которой равен доказываемому утверждению. Проверка типов верифицирует её. Это та же
операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип — это утверждение, верификация — это проверка типов

`{}` в YaoXiang — это пространство доказательств на этапе компиляции. Всё внутри — утверждения, и
компилятор гарантирует, что каждый элемент равен True — либо доказывается автоматически, либо
программист предоставляет функцию-доказательство.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  компилятор гарантирует, что data — Array(T)
```

**Дженерики — частный случай компиляционных предикатов.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в сигнатуре  внутри {} только утверждения
#          компилятор проверяет x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре  компилятор проверяет type_of(T) == Type, type_of(data) == Array(T)
```

Один и тот же паттерн: `name: (params) -> Type = { утверждения }`. Компилятор не различает
«утверждения о типах» и «утверждения о значениях» — всё это цели вычисления в конвейере
доказательства.

**Инварианты цикла не нужно записывать отдельно. Аннотация типа на переменной — это инвариант
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # компилятор проверяет: s_new == sum(arr[0..i+1])
        i += 1       # i изменяется → срабатывает ре-валидация зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. После того как
конвейер доказательства верифицирует индуктивный шаг, все итерации покрываются автоматически. Не
нужно `: decreases`, не нужно `: Invariant`, не нужно доказательство индукции — компилятор разбивает
индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: компиляционные предикаты на типах параметров и возвращаемого значения

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Компиляционные предикаты выступают в роли
аннотаций типа параметра или возвращаемого значения.

**На стороне параметров — это вызов функции.** Компиляционный предикат — это функция, возвращающая
Type, и её использование в позиции параметра — это её вызов — как и `factorial(5)`. На стороне
возвращаемого значения вводится новая концепция: параметр возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов компиляционного предиката в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive как аргумент
#                       компилятор в точке вызова извлекает значение фактического параметра, подставляет b, проверяет Positive(факт. параметр)
#                       пример: divide(10, 2) → проверка Positive(2) = { 2 > 0 } → True
#                       пример: divide(10, 0) → проверка Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: параметр возвращаемого значения + компиляционный предикат
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — параметр возвращаемого значения, значение предоставляется return
#                                            компилятор в точке return подставляет возвращаемое значение, проверяет постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **На стороне параметров**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся
  в `Positive` как аргумент. Синтаксис вызова функции, ноль неявного.
- **На стороне возвращаемого значения**: `-> (result: IsMax(T, arr, result))` — `result` — параметр
  возвращаемого значения, значение предоставляется оператором `return`. `result` существует только в
  сигнатуре типа, на него ссылается только предикат, не входит в область видимости тела функции, не
  появляется у вызывающего.
- **Параметр возвращаемого значения опционален**: если постусловия нет, не пишется, сигнатура
  полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: параметры и параметры возвращаемого значения — одна и та же концепция —
  `имя_параметра: вызов_предиката(имя_параметра)`, различие только в том, предоставляется значение
  вызывающим или через `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения на этапе компиляции

Когда компиляционный предикат используется в позиции связывания, аргументы передаются программистом
явно. Когда значение времени выполнения попадает в параметр уточнённого типа, компилятор завершает
верификацию через сбор путевых условий и проверку импликации SMT — без явной передачи доказательства
программистом.

#### 3.1 Явный вызов функции

Когда компиляционный предикат используется в позиции связывания, аргументы передаются программистом
явно — это вызов функции, ноль неявного.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор компиляционного предиката. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, возвращаемый тип),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — вызов функции
// после нормализации: b: { b > 0 }
```

Компилятору не нужно неявно подставлять аргументы — `b: Positive(b)` и `f(5)` — это одно и то же,
вызов функции. `b` связан как имя параметра, его аннотация типа `Positive(b)` ссылается на сам `b` —
это стандартный паттерн зависимых типов, а не неявное правило раскрытия.

**Единство с `self` из RFC-010**: RFC-010 устанавливает, что `self` не ключевое слово, а просто
конвенциональное имя параметра («написать `p`, `this`, `x` — эффект полностью одинаков»).
`b: Positive(b)` разделяет тот же механизм — имя параметра может использоваться в аннотации типа.
`self` появляется в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, обе аннотации
типа ссылаются на сам параметр. Различие только в сложности аннотации типа, механизм полностью
одинаков — после связывания имени тип может зависеть от этого имени.

Возвращаемый тип также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — параметр возвращаемого значения, Sorted(result) — вызов функции
//                        компилятор в точке return подставляет возвращаемое значение в result, проверяет Sorted(возвращ. значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевые условия, формируя **множество гипотез** текущей области видимости. Эти гипотезы участвуют в
верификации как фоновые знания для вычисления Bool на этапе компиляции.

```yaoxiang
if y > 0 {
    // компилятор автоматически получает гипотезу в этой ветви: { y > 0 }
    let result = divide(x, y)
    // условие верификации: (y > 0) ⇒ (y > 0)
    // конвейер доказательства: импликация верна → Proved
} else {
// гипотеза в этой ветви: { !(y > 0) }
// при вызове divide(x, y) условие верификации: !(y > 0) ⇒ y > 0
    // конвейер доказательства: импликация неверна → Disproved
}
```

Это не зашитый в компилятор специальный паттерн — это естественное поведение конвейера
компиляционного доказательства. Каждая проверка типа в точке вызова отправляет в конвейер:

```
{фоновые гипотезы} ⇒ {цель верификации}
```

Конвейер доказательства определяет импликацию. Proved → проходит, Disproved → ошибка компиляции +
контрпример, Unproven → ошибка компиляции + неразрешённое утверждение. Фоновые гипотезы берутся из
путевых условий текущей точки программы.

#### 3.3 Стек гипотез

Компилятор при анализе потока управления поддерживает множество гипотез для каждого базового блока:

- **if-guard**: `if y > 0` → true-ветвь помещает `y > 0`, false-ветвь помещает `!(y > 0)` (если есть
  else)
- **паттерн match**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **логическая связка**: `if x > 0 and y < 10` → в ветвь помещаются `x > 0` и `y < 10`
- **предусловие функции**: при вызове `divide(a, b)` свидетельство того, что `b` удовлетворяет
  `Positive`, берётся либо из текущих гипотез, либо из аннотации уточнённого типа самого
  фактического параметра (если `b` уже аннотирован как `Positive`, его тип несёт `b > 0`)
- **присваивание**: при `let z = y` уже имеющееся у `y` условие уточнения передаётся в `z`

Все гипотезы поступают в конвейер компиляционного доказательства. При входе в ускоренный SMT-путь
они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Нет статического свидетельства — ошибка компиляции

Если программист пишет напрямую:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей точке программы нет гипотезы `y > 0`, сам фактический параметр `y` также не имеет
аннотации типа `Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация неверна) → ошибка компиляции:

> Не удаётся доказать, что параметр `b` удовлетворяет `Positive` при вызове `divide`. `y` поступает
> из ввода функции, не имеет доказанной границы. Рассмотрите охрану вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не допускает прямого попадания значений времени выполнения в параметр уточнённого типа без
предоставления статического свидетельства. Это не ограничение — это ядро философии жёсткой
безопасности. Код, который компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Отношение с унифицированным конвейером

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
компиляционного доказательства на анализ потока управления:

| Этап                                  | Ответственность                                                                                                                                                                        |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий                  | Фаза анализа потока управления компилятора, аннотирующая каждый базовый блок множеством гипотез                                                                                        |
| Генерация условий верификации         | При встрече ограничения типа, требующего проверки, объединение путевых условий + информация о типе фактического параметра                                                              |
| Вычисление в конвейере доказательства | Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven                                                                                                             |
| Результат                             | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + неразрешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновые знания
конвейера доказательства — разделяют один конвейер и одну систему бюджета с равенством типов и
ограничениями заимствования.

### 4. Конвейер компиляционного доказательства

Все компиляционные проверки разделяют единый конвейер. Основная операция конвейера — **проверка
типов** — проверка того, равен ли тип терма доказательства доказываемому утверждению. Всё есть
проверка типов.

```
Компиляция встречает выражение Bool, требующее вычисления (т.е. требующее построения терма доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → компилятор определяет напрямую (структурная эквивалентность)
        │
        ├── Условие конфликта токенов (!conflicting(tokens))
        │   → потокочувствительный анализ живости (отслеживание атрибутов Dup/Linear)
        │
        ├── Редукция зависимых типов (редукция n + m)
        │   → система переписывания термов на этапе компиляции (βδι-редукция)
        │
        ├── Компиляционный предикат (x > 0, forall...)
        │   → ядро компилятора + SMT-ускоритель
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → ядро компилятора + SMT-ускоритель
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → компиляция проходит
             │ Disproved│  → ошибка компиляции + контрпример
             │ Unproven │  → ошибка компиляции + неразрешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код YaoXiang)
                  │
                  ▼
         Проверка типов верифицирует ──→ Proved ──→ компиляция проходит
                  │
                  ▼
            Верификация не прошла → ошибка компиляции: «доказательство неверно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление на этапе компиляции возвращает три результата — это неизбежное следствие проблемы
остановки и естественное разделение теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → завершается, терм доказательства построен, проверка типа проходит. Компиляция
  продолжается.
- **Disproved(M)** → завершается, существует контрпример M. Ошибка компиляции + контрпример +
  позиция в исходном коде.
- **Unproven** → в пределах заданного ресурсного лимита терм доказательства не построен. Ошибка
  компиляции + неразрешённое утверждение + отчёт о потреблении бюджета.

**Unproven ≠ False.** Когда компилятор говорит «я не могу доказать», это не эквивалентно ложности
утверждения — это просто превышение возможностей текущего автоматического доказательства. Это
честность, а не дефект.

Жёсткое ограничение бюджета — инженерное решение проблемы остановки. Без ручки настройки — дать её
означало бы спросить пользователя «думаете ли вы, что ваша программа остановится», пользователь не
знает, и компилятор тоже не знает.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверка типов
верифицирует эту функцию — тем же механизмом, что и верификацию `add(a, b): Int`.

```
утверждение  = тип
доказательство  = программа (значение этого типа)
верификация  = проверка типов (единственный корень доверия)
```

Решатель SMT — не независимая граница доверия — это **ускоритель проверки типов**. SMT помогает
найти доказательство, но доказательство всегда верифицируется проверкой типов. Когда SMT возвращает
`unsat`, компилятор реконструирует результат как терм доказательства, верифицируемый проверкой
типов. Если реконструкция не удалась (шаги вывода SMT выходят за пределы правил вывода ядра
компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: уточнённое свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип — вышеуказанное утверждение
# Проверка типов верифицирует эту функцию — полностью аналогично верификации add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # компилятор верифицирует здесь: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Не нужен ИИ, не нужен экспорт в Coq, не нужны новые концепции. **Свойство, которое нельзя доказать
автоматически на этапе компиляции → программист пишет доказательство кодом YaoXiang → проверка типов
верифицирует.** Весь процесс — плавный градиент — компилятор делает за вас простые доказательства,
оставляя мозг для сложных.

#### 4.3 Стратифицированные зависимости внутри конвейера

Вышеуказанные вычислители разделяют один интерфейс, но имеют порядок вычисления. Равенство типов —
необходимое условие для всего последующего анализа; проверка владения/токенов зависит от информации
о типах; верификация уточнённых предикатов зависит от результатов первых двух слоёв. Компилятор
вычисляет по слоям, выражения, не прошедшие нижний слой, не поступают в верхний — избегая траты
бюджета решения на типово-некорректных программах.

```
Порядок вычисления (один конвейер, стратифицированная диспетчеризация)
├── Слой 0: равенство типов (T1 == T2)
│   └── структурная унификация → при неудаче последующее бессмысленно, сразу Disproved
├── Слой 1: конфликты владения/токенов
│   └── потокочувствительный анализ живости → при неудаче безопасность памяти не соблюдается, сразу Disproved
└── Слой 2: уточнённые предикаты / импликации Хоара
    └── ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя один интерфейс и одну
систему бюджета.

### 5. Единство трёх слоёв функций

| Слой                    | Момент выполнения | Вход          | Выход    | Пример                                         |
| ----------------------- | ----------------- | ------------- | -------- | ---------------------------------------------- |
| Функция-значение        | Runtime           | Значения      | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типов       | Compile-time      | Типы/Значения | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Компиляционный предикат | Compile-time      | Значения      | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют один и тот же синтаксис `name: type = value`. Компиляционные предикаты и конструкторы
типов идут по одному конвейеру компиляционного доказательства — `{}` — это пространство
доказательств.

### 6. Циклы: генерация условий верификации Флойда-Хоара

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Аннотация
компиляционного предиката на переменной определяет утверждение в стиле Флойда-Хоара — компилятор
генерирует условия верификации из аннотации типа, конвейер доказательства проверяет, сохраняет ли
каждое присваивание тип.

Ключевой механизм: каждая операция присваивания соответствует тройке Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует одно условие верификации для тела цикла — после
того как конвейер доказательства верифицирует индуктивный шаг, все итерации покрываются
автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i; при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # проверка: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует одно VC для тела цикла. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не изменился)
        #   Подставляя s_new = s_old + arr[i]:
        #     требуется s_old + arr[i] == sum(arr[0..i+1])
        #     из индуктивной гипотезы s_old == sum(arr[0..i]), прибавляя arr[i] с обеих сторон:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменяется → в графе зависимостей аннотация типа s ссылается на i → срабатывает ре-валидация
        #   новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   т.е. s == sum(arr[0..i_new]), гарантировано предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # в этот момент s: SumUpTo(arr, arr.len), т.е. s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант или «автоматически выполнять
индукцию» — он разбивает индуктивное доказательство на локальные условия верификации для каждой
операции присваивания и передаёт их в конвейер доказательства.

#### 6.1 Отслеживание зависимостей: зависимые типы на мутируемых переменных

Предпосылка вышеуказанного механизма: компилятор знает, что аннотация типа `s`, а именно
`SumUpTo(arr, i)`, ссылается на `i` — когда `i` изменяется, ограничение типа `s` также изменяется.
Это требует от компилятора поддерживать **граф зависимостей типов между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# ключ — зависимая переменная, значение — множество переменных, на которые ссылается аннотация типа
# пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: проверка типов при обработке `mut v: Pred(... x ...) = init` разбирает свободные
ссылки на переменные в аргументах `Pred(...)`. Если в аргументах есть ссылка на другую мутируемую
переменную `x` в текущей области видимости, в графе зависимостей регистрируется `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает присваивание, компилятор:

1. Ищет в графе зависимостей все переменные, зависящие от `x`: `{v₁, v₂, ...}`
2. Для каждой `v` генерирует условие верификации: удовлетворяет ли текущее значение `v` обновлённому
   типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательства

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественно обеспечивает
правильный порядок присваивания. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменяется → ре-валидация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # i изменяется → ре-валидация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Составные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` зависит одновременно от `x` и `y` — изменение любой запускает ре-валидацию.

**Отношение с конвейером доказательства**: отслеживание зависимостей — триггер генерации VC, а не
независимый механизм верификации. Он отвечает на вопрос «когда нужно генерировать VC» — конвейер
доказательства отвечает на вопрос «верно ли VC».

### 7. Проверка завершения

**Область применения: компиляционное вычисление.** Проверка завершения нацелена только на циклы и
рекурсию, задействованные в компиляционном вычислении (запускаемые отслеживанием зависимостей) —
компилятор должен доказать полноту для кода, который он сам должен выполнить; код времени выполнения
не требует доказательства завершения (см. таблицу областей применения §6.7). Внутри области
компиляционного вычисления приоритет у полной автоматизации: циклы, которые компилятор может
доказать, проходят; циклы, которые автоматическая стратегия не может доказать, приводят к прямой
ошибке компиляции — программист обязан сделать цикл анализируемым для компилятора. Нет лазейки в
виде **синтаксиса аннотаций** (не вводится аннотация типа `decreases`, неподдерживаемое всегда
остаётся синтаксической позицией, а не функцией).

> **Поправка (RFC-027a, 2026-09-14)**: ① Область применения уточнена до компиляционного вычисления —
> исходный текст не ограничивал «циклы» по позиции, что порождало неоднозначность с таблицей
> областей применения §6.7; безусловная полная проверка на уровне реализации сужается согласно этому
> уточнению. ② Для обязательств завершения, которые не может доказать автоматическая стратегия,
> программист может предоставить функцию-меру и функцию-доказательство завершения (`Terminates`) в
> качестве запасного варианта — обе являются обычными функциями YaoXiang, ноль нового синтаксиса,
> проверка типов верифицирует. Принцип приоритета полной автоматизации остаётся неизменным, запасной
> вариант применяется только после Unproven. См.
> [RFC-027a: Запасной вариант доказательства для проверки завершения](../draft/027a-termination-proof-fallback.md).

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершения, из двух
источников:

1. **Аннотации типов переменных**: граничные ограничения в уточнённых типах (например, `UpTo(n)`
   даёт верхнюю границу `n` и нижнюю `0`)
2. **Операции в теле цикла**: операции, применяемые к переменным на каждой итерации

Компилятор пытается применить четыре стратегии синтеза меры в порядке приоритета, останавливаясь при
нахождении подходящей.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию линейной границы, компилятор перечисляет кандидатов на линейную
меру и верифицирует через SMT.

```
Вход:
  переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с границами)
  условие цикла cond
  множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типов: [low_i, high_i]
  2. Перечислить кандидатов мер: v_i, u_i - v_i, v_i - v_j, и т.д. линейные комбинации
  3. Для каждого кандидата m:
     - SMT проверяет m ≥ 0 (из границ типа)
     - для каждого пути выполнения тела цикла SMT проверяет m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершение доказано
```

Покрытие: циклы, в которых любая переменная присваивается линейным выражением (`v = a·v + b`) и
имеет аннотацию ограниченного типа. Включает `i += const`, `i -= const`, а также сокращение
интервала в стиле двоичного поиска:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: подсчёт нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, решение о включении принимается на этапе 3 на
> основе фактической осуществимости.** Эта стратегия работает для операций соседнего обмена
> (сортировка пузырьком, сортировка вставками), но не может автоматически доказать для не соседних
> операций (partition быстрой сортировки, sift-down пирамидальной сортировки). Границы покрытия см.
> в таблице ниже. Если на этапе 3 верификация покажет нецелесообразность, эта стратегия будет
> удалена или понижена до будущей работы.

Ключевое наблюдение: **спецификация, написанная пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  операции тела цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операции на меру:
     - обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - затрагивает только пары индексов j-1, j, j+1
     - если arr[j] > arr[j+1] (нарушение предиката), после обмена пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя: 0
  → завершение доказано
```

**Текущее покрытие**:

| Алгоритм                 | Паттерн операции     | Доказуемо стратегией 2? | Причина                                               |
| ------------------------ | -------------------- | :---------------------: | ----------------------------------------------------- |
| Сортировка пузырьком     | Соседний обмен       |           ✅            | violation_count строго убывает при каждом обмене      |
| Сортировка вставками     | Соседнее перемещение |           ✅            | Каждое перемещение устраняет одну нарушающую пару     |
| Сортировка выбором       | Несоседний обмен     |           ❌            | Один обмен может увеличить violation_count            |
| Быстрая сортировка       | Разбиение partition  |           ❌            | Несоседний обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌            | Древовидная операция, violation_count не монотонен    |

**Взаимодополняющие стратегии**: для быстрой сортировки сокращение интервала `low < high`
покрывается стратегией 1 (линейная ранговая функция) — рекурсия partition внешнего уровня, интервал
каждый раз сокращается вдвое. Стратегии 1 и 2 взаимно дополняют друг друга, завершение большинства
практических алгоритмов доказуемо одной из них. Однако обобщение стратегии 2 (несоседние операции,
древовидные операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: паттерн ограниченного возрастания/убывания

`v += const` (положительная константа), переменная имеет аннотацию верхней границы → мера
`upper_bound - v` убывает на `const` каждый раз, нижняя граница 0. Это вырожденный случай стратегии
1, компилятор обрабатывает его первым для скорости.

#### 6.5 Стратегия 4: шаблон мультипликативной меры

`v *= const` (const > 1), переменная имеет аннотацию верхней и нижней границ. Компилятор имеет
встроенный логарифмический шаблон меры `ceil(log_const(upper/v))`, при каждом умножении на const
мера уменьшается на 1.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # компилятор автоматически выводит: мера ceil(log₂(n/i)), при каждом умножении на 2 мера уменьшается на 1
    i *= 2
}
```

#### 6.6 Разделение завершения и корректности

Доказательство завершения и доказательство корректности независимы:

- **Завершение**: четыре вышеуказанные стратегии автоматически доказывают, что цикл завершается за
  конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером
  компиляционного доказательства через условия верификации

Оба проходят → компиляция проходит. Завершение доказано, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершение не доказуемо → ошибка компиляции с
указанием переменной или операции, которые не удаётся проанализировать. Оба не прошли → ошибка
компиляции с раздельным указанием причин обоих сбоев.

#### 6.7 Проверка завершения для рекурсивных функций

Для рекурсивных функций, которые требуется вычислить на этапе компиляции, компилятор проверяет
убывание аргументов:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # компилятор анализирует: n-1 < n → убывает → завершается
}

# Компиляционное использование — компилятор гарантирует завершение factorial на этапе компиляции
arr: Array(Int, factorial(5)) = Array(Int, 120)()  # 5! = 120, выполняется на этапе компиляции
```

| Сценарий                                                                 | Поведение                        |
| ------------------------------------------------------------------------ | -------------------------------- |
| Компилятор может проанализировать рекурсивное убывание (например, `n-1`) | Вычисление на этапе компиляции   |
| Не убывает / не удаётся определить убывание                              | Ошибка компиляции                |
| Вызов в Runtime (не в позиции типа)                                      | Проверка завершения не требуется |

#### 6.8 Жёсткая граница

`i = f(i)`, где `f` необратима, незамкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершение. Ошибка компиляции:

> Этот цикл не может быть автоматически доказан как завершающийся. Переменная цикла зависит от
> неанализируемой функции `f`. Используйте итеративный паттерн, анализируемый компилятором, или
> предоставьте функцию-меру и функцию-доказательство завершения (см. RFC-027a).

Это не сбой компилятора. Код, который нельзя статически доказать как безопасный, не проходит
компиляцию.

### 8. Решатель SMT: ускоритель проверки типов

Решатель SMT в традиционных языках — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang это **ускоритель проверки типов** — вызывается только тогда, когда ядро компилятора
само не может определить напрямую. SMT помогает найти доказательство, но доказательство
верифицируется проверкой типов.

**Модель доверия**: проверка типов — единственный корень доверия. Решатель SMT — ускоритель — он
помогает найти доказательство, но SMT не является независимой границей доверия. Компилятор доверяет
результату Z3 `unsat` (согласуется с подходом F\*/Dafny — вероятность ошибки Z3 ниже, чем частота
ошибок в самом компиляторе, это прагматичный инженерный выбор). Реальный контроль ненадёжности
находится на уровне трансляции в SMT — если в трансляции есть баг, компилятор обнаружит его через
другие тесты.

**Интерфейс**: внутренняя трансляция компилятора — в стандартный формат SMT-LIB 2.6, а не привязка к
API конкретного решателя. SMT-LIB — стандарт ISO, Z3, CVC5, MathSAT, Yices — все имеют нативную
поддержку.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, наиболее широкая документация и общественная валидация).
CVC5 как SMT-LIB-совместимая альтернатива — пользователь может переключать флагом компилятора.

Никакого «универсального слоя абстракции решателя» — SMT-LIB и есть слой абстракции. В будущем, если
CVC5 добьётся прорыва в определённой теории, переключение требует только замены бинарника, без
изменения кода компилятора.

```
Выражение Bool на этапе компиляции
        │
        ├── Ядро компилятора может определить напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → напрямую вернуть Proved / Disproved
        │
        └── Ядро компилятора не может определить напрямую (кванторы, символьные переменные)
            → предварительная редукция зависимых типов (factorial(5) → 120)
            → трансляция в формат SMT-LIB
            → отправка в Z3/CVC5 (с ограничением бюджета)
            → возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткое ограничение, как глубина стека**:

| Измерение бюджета                 | Значение по умолчанию | Описание                                                                                                                                                    |
| --------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10 000                | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывает 99% практических предикатов.                                           |
| Время                             | 100 мс                | Один предикат свыше 100 мс = пользователь пишет компиляционную программу, а не аннотацию типа. 100 мс × 50 предикатов = верхний предел 5 секунд компиляции. |
| Глубина инстанцирования кванторов | 3                     | Три уровня вложенных кванторов покрывают практические паттерны. Свыше трёх — скорее всего, пишется логическая задача.                                       |

При превышении бюджета возвращается Unproven, ошибка компиляции + позиция предиката + объём
потребления. Никакой деградации, никаких runtime-проверок, никакого silent pass.

**Почему это практически работает**: 95% практических предикатов в инженерии — линейная арифметика —
`x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в пределах разрешимого фрагмента, решатель SMT
возвращает для таких задач за миллисекунды. Для редких сложных предикатов, превышающих бюджет,
программист пишет функцию-доказательство.

Зависимые типы перед вызовом SMT проходят слой предварительной редукции: `factorial(5)` напрямую
вычисляется в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти детерминированные
вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Мысленная модель: **компилятор может доказать —
проходит, не может — сообщает об ошибке — если компилятор не умеет, можно написать функцию, которая
докажет ему.**

### 9. Композиция компиляционных предикатов

Компиляционные предикаты — это функции, возвращающие Type, композиция естественно реализуется через
композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ компилятор проверяет Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ компилятор проверяет Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ компилятор проверяет InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ компилятор проверяет InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: единство диспетчеризации на этапе компиляции и в Runtime

`assert` и `Assert` — две стороны одного примитива уточнённого типа. Конвейер диспетчеризации
`dispatch` автоматически решает, идти ли по пути доказательства на этапе компиляции или
runtime-проверки, по критерию **достижимости свободных переменных предиката на этапе компиляции**:

| Критерий                                                                                              | Режим           | Поведение                                                                                                             |
| ----------------------------------------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны на этапе компиляции (параметры-дженерики, компиляционные константы) | **CompileTime** | Вход в конвейер доказательства: Proved → стирание, Disproved → ошибка компиляции, Unknown → требование доказательства |
| Существуют свободные переменные из Runtime (параметры функций, внешний ввод, mut-переменные)          | **Runtime**     | Вставка runtime check и инъекция уточнённого факта в потокочувствительное множество гипотез Γ                         |

**Ключевое**: «не удаётся определить» ≠ «опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихой деградации), в режиме Runtime утверждение в принципе не имеет истинности
на этапе компиляции — никакой prover не напишет тавтологически истинного доказательства для
«пользователь мог ввести отрицательное число», runtime check — единственный sound-выбор. Это не
слабость prover'а, это теоретическая неизбежность.

### 12. Потокочувствительное множество гипотез Γ: распространение сильнейшего постусловия

Компилятор поддерживает потокочувствительное (flow-sensitive) множество гипотез Γ, отслеживающее
утверждения, известные истинными в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← распространение SP
```

**Kill set для mut-переменных**: после переприсваивания mut-переменной все гипотезы, затрагивающие
эту переменную, удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые гипотезы недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение гипотез ветвей. Через
границу ветви проносятся только утверждения, истинные на всех путях.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточнённые типы полностью стираются в Runtime» относится к **proof witness
(токену доказательства)** — терм доказательства, верифицированный на этапе компиляции, не порождает
runtime-кода. Но **runtime check**, вставленный dispatch'ем в режиме Runtime, сохраняется — это
проверка Bool на уровне значений, а не witness на уровне типов.

Итог: witness стирается, check сохраняется. Эти две вещи не конфликтуют, исходное утверждение
RFC-027 остаётся в силе.

## Детальное проектирование

### Синтаксические изменения

| Ранее (RFC-022)                       | После (настоящий RFC)                                                                     |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Компиляционный предикат как тип параметра `(b: Positive(b))`                              |
| `//! ensures: ExistsMax(result, arr)` | Возвращаемый тип с параметром возвращаемого значения `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Аннотация компиляционного предиката на переменной — инвариант Флойда-Хоара                |
| `//! decreases: n`                    | Компилятор полностью автоматически выводит функцию-меру                                   |
| Спецификация — комментарий            | Спецификация — система типов                                                              |

### Синтаксис

**У компиляционных предикатов нет новых ключевых слов.** `{}` — пространство доказательств,
полностью совместимо с существующим синтаксисом определения типов. Компиляционный предикат — это
функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. При использовании это вызов
функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Компиляционный предикат = функция, возвращающая Type, внутри {} — утверждения, верифицируемые компилятором
# Используется существующий синтаксис функций/типов, не требуется новых правил BNF
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы применения предиката должны иметь форму компиляционных констант** — литералы, переменные
(связанные по имени) или одноаргументные применения типов (рекурсивное извлечение). Если форма
аргумента не может быть преобразована в константное выражение — ошибка **E1092**; если число
аргументов не совпадает с числом параметров предиката — ошибка **E1093** — уточнённые ограничения
**никогда не отбрасываются молча** (ранее неконвертируемые аргументы приводили к беззвучному
исчезновению ограничений, и связывание, нарушающее ограничение, молча проходило).

**Новая синтаксическая концепция: параметр возвращаемого значения** — в `-> (name: Type)` `name` —
параметр возвращаемого значения.

Параметр возвращаемого значения — это **единственная новая синтаксическая концепция**, вводимая
YaoXiang в существующий синтаксис функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается постусловие-предикат (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не входит в область видимости тела функции, не появляется у вызывающего
- Параметр возвращаемого значения **опционален** — при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), не внося никакой дополнительной нагрузки

Причина его введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть».
Без параметра возвращаемого значения компилятор мог бы только через специальные правила (например,
неявная переменная `$result` или `__retval__`) позволить предикату ссылаться на возвращаемое
значение. Параметр возвращаемого значения делает эту ссылку явной — это просто параметр, только
значение предоставляется через `return`, а не вызывающим.

**Функция-доказательство** — не новая концепция — это просто функция YaoXiang, чей возвращаемый тип
— доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверка типов верифицирует её точно так же, как верифицирует возвращаемый
тип любой функции. Не требуется нового синтаксиса, новых ключевых слов, новых правил.

### Влияние на систему типов

- **Вселенная типов**: компиляционные предикаты находятся на уровне Type₂ — функция, принимающая
  значения и возвращающая Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с дженериками**: компиляционные предикаты могут иметь параметры-дженерики,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в компиляционных предикатах подчиняются правилам
  владения, могут только читать, не писать
- **Вывод типов**: аргументы компиляционных предикатов участвуют в HM-выводе типов

### Представление в Runtime

Компиляционные предикаты в Runtime **обрабатываются в зависимости от результата диспетчеризации
dispatch**:

- **Режим CompileTime** (все свободные переменные известны на этапе компиляции): токен-свидетельство
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` в Runtime представлен как
  `Int`. Уточнённое условие `{ 5 > 0 }` пройдено, стирается.
- **Режим Runtime** (существуют свободные переменные из Runtime): сохраняется runtime check —
  проверка Bool на уровне значений, инъекция в потокочувствительное множество гипотез Γ. Подробности
  см. в §11 конвейер диспетчеризации dispatch и §13 уточнение модели стирания.

Помещение компиляционного предиката в позицию типа (например, `f(x: Positive(x))`) не порождает
обёрточного типа, не выделяет дополнительную память. Но когда `x` поступает из runtime-ввода,
**выполняется** вставка runtime-проверки Bool.

**Ограничения взаимодействия с `ref`**: компиляционные предикаты могут ссылаться только на
неизменяемые заимствования или значения с переданным владением. Компиляционные предикаты,
ссылающиеся на изменяемые заимствования, не могут гарантировать на этапе компиляции, что результат
верификации останется верным в Runtime — такое использование напрямую приводит к ошибке компиляции.

### Изменения в компиляторе

1. **Парсер**: компиляционные предикаты используют стандартный синтаксис функций, дополнительных
   правил парсинга не требуется
2. **Конвейер компиляционного доказательства**: унифицированный интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **SMT-ускоритель**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, CVC5 как альтернатива
4. **Ядро проверки типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение квантора всеобщности. Это единственный корень доверия, SMT и доказательства
   программиста верифицируются через него
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёты о неразрешённых утверждениях +
   привязка к позициям в исходном коде

### Обратная совместимость

- ✅ Код, не использующий компиляционные предикаты, остаётся полностью неизменным
- ✅ Компиляционные предикаты в режиме CompileTime имеют нулевые накладные расходы в Runtime, в
  режиме Runtime сохраняются только необходимые проверки Bool
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован, бремя
  миграции отсутствует

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Ховарда**: тип — утверждение, программа — доказательство,
  `name: Proposition = Proof`
- **Единство**: компиляционные предикаты и обычные функции используют полностью идентичный
  синтаксис, без концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, мысленная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного компиляционного предиката, постепенно расширяя
  покрытие
- **Минимальные накладные расходы в Runtime**: режим CompileTime — нулевые накладные расходы, режим
  Runtime — только необходимые проверки Bool

### Недостатки

- **Время компиляции**: решение SMT увеличивает время компиляции, но жёсткое ограничение бюджета
  гарантирует контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами линейной арифметики
  первого порядка могут потребовать от программиста функции-доказательства. Это не дефект языка —
  это неизбежное следствие проблемы остановки. Компилятор честно сообщает Unproven, а не ложно
  сообщает True/False
- **Кривая обучения**: написание эффективных компиляционных предикатов и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Ховарда
- **Сложность реализации**: единство конвейера компиляционного доказательства требует тщательного
  проектирования

### Снижение рисков

- Жёсткое ограничение бюджета решения SMT (шаги 10 000 / время 100 мс / глубина инстанцирования 3),
  при превышении — Unproven
- Предварительная редукция зависимых типов: детерминированные вычисления значений поглощаются
  первыми, SMT кусает только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверка типов
  верифицирует — как и для любого возвращаемого типа функции
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + отображение контрпримеров + отчёт о потреблении бюджета +
  неразрешённые утверждения + предложения (если компилятор может их дать)

## Альтернативы

| Альтернатива                                                                                 | Почему не выбрана                                                                                                                                                                 |
| -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-022: спецификации как комментарии `//!`                                                  | Спецификации и типы разделены, нарушает изоморфизм Карри-Ховарда                                                                                                                  |
| Файлы отдельных спецификаций (например, CVL)                                                 | Спецификации и код разделены, увеличивает стоимость сопровождения                                                                                                                 |
| Только runtime-утверждения                                                                   | Не может статически гарантировать корректность                                                                                                                                    |
| Внешний помощник доказательства (например, Coq)                                              | Отделён от компилятора, требует отдельного языка доказательств и границы доверия. Выбор YaoXiang: доказательство — это код YaoXiang, проверка типов — единственный корень доверия |
| **Настоящее предложение: компиляционные предикаты как полноправные граждане первого класса** | ✅                                                                                                                                                                                |

## Стратегия реализации

### Разбиение на этапы

| Этап       | Содержание                                                                                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Этап 1** | Ядро компилятора: структурная эквивалентность + βδι-редукция + введение/устранение квантора всеобщности. Поддержка простых арифметических предикатов (`x > 0`, `arr.len > 0`) |
| **Этап 2** | Слой трансляции в SMT-LIB + интеграция Z3/CVC5. Конвейер возвращает Proved/Disproved/Unproven. При Unproven поддержка функции-доказательства программиста                     |
| **Этап 3** | Генерация VC инвариантов цикла + проверка завершения (линейная ранговая функция + подсчёт нарушений предиката + паттерн ограниченности + контроль комбинаторного взрыва)      |
| **Этап 4** | Инкрементальная верификация + кэширование + поддержка IDE                                                                                                                     |

### Зависимости

- RFC-010: Унифицированный синтаксис типов — компиляционные предикаты основаны на
  `name: type = value`
- RFC-011: Система дженериков — компиляционные предикаты могут иметь параметры-дженерики
- RFC-009: Модель владения — выражения компиляционных предикатов подчиняются правилам владения

## Открытые вопросы

- [x] **Выбор решателя SMT**: по умолчанию Z3 (лицензия MIT, наиболее валидированный). CVC5 как
      SMT-LIB-совместимая альтернатива, переключение флагом компилятора. Внутренняя цель трансляции
      компилятора — стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, без
      специального универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решения**: шаги 10 000 / время 100 мс / глубина инстанцирования
      кванторов 3. Жёстко зафиксировано внутри компилятора, без ручек настройки. При появлении в
      практике реальных случаев, доказывающих недостаточность (не «пользователь ошибся»), значения
      будут скорректированы.
- [x] **Область поддержки кванторов**: язык не ограничивает порядок кванторов. Компиляционные
      предикаты принимают параметры Type — Type включает типы функций — поэтому кванторы высшего
      порядка — естественное следствие системы типов, специальный синтаксис не нужен. Решатель SMT
      может автоматически разрешать кванторы первого порядка (forall/exists, поддерживается
      чередующееся вложение, ограничено глубиной бюджета 3). Кванторы высшего порядка: SMT
      возвращает Unproven, компилятор предлагает «этот предикат за пределами автоматического
      доказательства, предоставьте функцию-доказательство». Программист пишет функцию YaoXiang, чей
      возвращаемый тип равен этому утверждению — проверка типов верифицирует эту функцию. Не нужен
      внешний экспорт, не нужен ИИ, не нужен интерактивный режим доказательства. Всё — код YaoXiang,
      всё проверяется проверкой типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена SMT-переменных (с префиксом модуля для избежания конфликтов). При возврате модели Z3
      выполняется обратный поиск по именам переменных. Формат вывода: имя переменной = конкретное
      значение + позиция в исходном коде + позиция определения предиката. Сложного слоя отображения
      нет.
- [x] ~~**Взаимодействие компиляционных предикатов со смарт-указателями `ref`?**~~ → Решено:
      компиляционные предикаты допускают только неизменяемые заимствования или значения с переданным
      владением. Изменяемые заимствованные значения не могут出现在 в компиляционных предикатах.
- [x] **Расширение меры подсчёта нарушений предиката `forall` на несоседние операции?** → Не
      расширяется. Текущее покрытие (соседний обмен, соседнее перемещение) взаимно дополняется
      стратегией 1 (линейная ранговая функция) — сокращение внешнего интервала быстрой сортировки
      покрывается стратегией 1, пирамидальная сортировка покрывается стратегией 1 (паттерн
      индексации массива). Циклы, чьё завершение не может доказать ни одна стратегия, приводят к
      прямой ошибке компилятора — это философия жёсткой безопасности, а не дефект. Если в будущем
      возникнут реальные сценарии (не академические конструкции), для которых все четыре стратегии
      не работают, обсуждение будет возобновлено. → **Обсуждение возобновлено (2026-09-14, #318)**:
      неструктурная рекурсия (ненапрямую убывающие типа gcd, взаимная рекурсия, слияние разделов) —
      это именно те реальные сценарии, которые предвидел данный пункт — текущий конвейер не может
      автоматически доказать их завершение, и их невозможно переписать в анализируемый итеративный
      паттерн без потери читаемости. Заключение: приоритет полной автоматизации сохраняется; после
      Unproven добавляется запасной вариант функции-доказательства — мера и доказательство
      завершения обе являются обычными функциями YaoXiang, ноль нового синтаксиса, проверка типов
      верифицирует. Реализовано в
      [RFC-027a: Запасной вариант доказательства для проверки завершения](../draft/027a-termination-proof-fallback.md).
- [x] **Комбинаторный взрыв при перечислении линейных ранговых функций**: верхний предел
      перечисления кандидатов — 3 переменные с границами. ≤3 — перечисляются все линейные комбинации
      и верифицируются через SMT по одной. >3 — пробуются только однопеременные меры (`v_i`,
      `u_i - v_i`), при неудаче — прямая ошибка компиляции — с подсказкой программисту «цикл
      имеет >3 переменных с границами, компилятор не может автоматически синтезировать
      многопеременную меру». Это не инженерный компромисс — это принуждение программиста к написанию
      более простых циклов.
