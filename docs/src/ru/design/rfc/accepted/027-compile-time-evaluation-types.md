## Резюме

В данном документе предлагается ввести в YaoXiang **предикаты времени компиляции** как первоклассные
сущности и унифицировать всю статическую верификацию времени компиляции в единый **конвейер
доказательств**. Предикаты времени компиляции — это не внешние аннотации спецификаций — это функции.
Функция, возвращающая Type, которую можно использовать в позиции типа, компилятор вызывает её во
время компиляции и проверяет возвращаемое значение. Тип — это утверждение (пропозиция), а вычисление
во время компиляции — это доказательство.

**Ключевой тезис**: Единственная задача проверки типов во время компиляции — это конструирование и
верификация доказательств. Типовые равенства, конфликты токенов, редукция зависимых типов,
вычисление предикатов времени компиляции, импликации логики Хоара — всё это различные проверки типов
в едином конвейере доказательств времени компиляции, использующие одну и ту же трубу. SMT-решатель —
это ускорительный модуль проверщика типов, а не отдельная граница доверия. Когда компилятор
возвращает Unproven, программист пишет функцию YaoXiang в качестве доказательства — проверщик типов
верифицирует её точно так же, как и любую другую функцию с типом возврата. Всё — это код YaoXiang,
всё верифицируется проверщиком типов.

## Мотивация

### Почему упраздняется RFC-022?

RFC-022 проектировала спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это независимый от типа комментарий
    //! ensures: ExistsMax(result, arr[0..n])   ← это независимый от типа комментарий
}
```

Здесь допущена фундаментальная ошибка изоморфизма Карри-Ховарда: **спецификации и типы разделены на
два слоя**. Комментарии — это не типы. Комментарии не участвуют в проверке типов. Комментарии — это
ментальная модель «внешнего инструмента».

Белая книга чётко говорит:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Комментарии `//!` из RFC-022 — это внешний синтаксис, не интегрированный в систему типов
- Типы спецификаций и обычные типы — это две разные системы, создающие концептуальную избыточность
- Разделение на Debug Build (верификация) / Release Build (игнорирование) нарушает унификацию
- SMT-решатель в традиционном понимании позиционируется как внешний инструмент — YaoXiang встраивает
  его как ускорительный модуль проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов идут разными путями

### Правильная ментальная модель

Проверка типов может быть абстрагирована как функция:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — все они являются подзадачами этой функции. Они
используют один конвейер доказательств, отличаясь лишь сложностью доказательства и стратегией
конструирования.

Когда компилятор возвращает Unproven, программист предоставляет доказательную функцию — тип возврата
этой функции равен доказываемому утверждению. Проверщик типов верифицирует её. Это та же операция,
что и обычная проверка типов.

## Предложение

### 1. `{}` — это пространство доказательств: тип — это утверждение, верификация — это проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри — утверждения,
которые компилятор гарантирует истинными — либо автоматически доказанные, либо предоставленные
программистом через доказательную функцию.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  Компилятор гарантирует, что x — это Float, y — это Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  Компилятор гарантирует, что data — это Array(T)
```

**Обобщения — это частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в сигнатуре  внутри {} только утверждение
#          компилятор верифицирует x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре   компилятор верифицирует type_of(T) == Type, type_of(data) == Array(T)
```

Одна и та же схема: `name: (params) -> Type = { утверждения }`. Компилятор не различает «типовые
утверждения» и «утверждения о значениях» — всё это цели вычисления в конвейере доказательств.

**Инварианты цикла не нужно писать отдельно. Типовые аннотации на переменных — это инварианты
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # компилятор верифицирует: s_new == sum(arr[0..i+1])
        i += 1       # i изменяется → триггер повторной верификации зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует условия верификации для тела цикла один раз — индуктивная гипотеза (типовая
аннотация) → операция присваивания → удовлетворяет ли новое значение типовой аннотации. После того
как конвейер доказательств подтвердит индуктивный шаг, все итерации автоматически покрываются. Не
нужно `: decreases`, не нужно `: Invariant`, не нужно индуктивное доказательство — компилятор
разлагает индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции в типах параметров и возврата

Отказ от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции выступают как типы
параметров или возвращаемого типа.

**Сторона параметров — это вызов функции.** Предикат времени компиляции — это функция, возвращающая
Type, и использование на стороне параметров — это просто её вызов, как и `factorial(5)`. На стороне
возвращаемого значения вводится новая концепция: параметр возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — это имя текущего формального параметра, передаётся в Positive
#                       компилятор на точке вызова извлекает фактическое значение, подставляет в b, верифицирует Positive(фактическое)
#                       пример: divide(10, 2) → верификация Positive(2) = { 2 > 0 } → True
#                       пример: divide(10, 0) → верификация Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — параметр возвращаемого значения, значение предоставляется return
#                                            компилятор на точке return подставляет возвращаемое значение, верифицирует постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **Сторона параметров**: `b: Positive(b)` — `b` — это имя текущего формального параметра,
  передаётся в `Positive`. Синтаксис вызова функции, ноль неявности.
- **Сторона возврата**: `-> (result: IsMax(T, arr, result))` — `result` — параметр возвращаемого
  значения, значение предоставляется оператором `return`. `result` существует только в сигнатуре
  типа, только предикат постусловия его упоминает, не входит в область видимости тела функции, не
  появляется у вызывающей стороны.
- **Параметр возвращаемого значения опционален**: при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`).
- **Унификация**: параметры и параметры возвращаемого значения — это одна концепция —
  `имя_параметра: вызов_предиката(имя_параметра)`, разница лишь в том, кто предоставляет значение —
  вызывающая сторона или `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

При использовании предикатов времени компиляции в позиции связывания параметры явно передаются
программистом. Когда значения времени выполнения попадают в параметры уточнённого типа, компилятор
завершает верификацию через сбор путевых условий и определение SMT-импликации — без явной передачи
доказательства программистом.

#### 3.1 Явные вызовы функций

При использовании предикатов времени компиляции в позиции связывания параметры явно передаются
программистом — это просто вызов функции, ноль неявности.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предиката времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — это вызов функции
// после нормализации: b: { b > 0 }
```

Не нужно, чтобы компилятор неявно подставлял параметры — `b: Positive(b)` — это то же самое, что и
`f(5)`, просто вызов функции. `b` как имя параметра связывается, его типовая аннотация `Positive(b)`
ссылается на самого себя — это стандартный паттерн зависимых типов, а не правило неявного раскрытия.

**Унификация с `self` из RFC-010**: RFC-010 устанавливает, что `self` — это не ключевое слово, а
лишь соглашение об именовании параметров («написав `p`, `this`, `x` получишь тот же эффект»).
`b: Positive(b)` использует тот же механизм — имя параметра может упоминаться в его типовой
аннотации. `self` появляется в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, обе
типовые аннотации ссылаются на параметр. Разница только в сложности типовой аннотации, механизм
полностью идентичен — после связывания имени тип может зависеть от этого имени.

Тип возврата также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — параметр возвращаемого значения, Sorted(result) — вызов функции
//                        компилятор на точке return подставляет возвращаемое значение в result, верифицирует Sorted(возвращаемое)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значения времени выполнения появляются в условных ветвлениях, компилятор автоматически
собирает путевые условия, формируя **множество предположений** для текущей области видимости. Эти
предположения участвуют в верификации как фоновое знание при вычислении Bool выражений времени
компиляции.

```yaoxiang
if y > 0 {
    // компилятор автоматически получает в этой ветке предположение: { y > 0 }
    let result = divide(x, y)
    // условие верификации: (y > 0) ⇒ (y > 0)
    // конвейер доказательств определяет импликацию верной → Proved
} else {
// в этой ветке предположение: { !(y > 0) }
// при вызове divide(x, y) условие верификации: !(y > 0) ⇒ y > 0
    // конвейер доказательств определяет импликацию неверной → Disproved
}
```

Это не встроенный в компилятор специальный паттерн — это естественное поведение конвейера
доказательств времени компиляции. При каждой проверке типа на точке вызова конвейеру отправляется:

```
{фоновые предположения} ⇒ {цель верификации}
```

Конвейер доказательств определяет импликацию. Proved → проходит, Disproved → ошибка компиляции +
контрпример, Unproven → ошибка компиляции + недоказанная пропозиция. Фоновые предположения
происходят из путевых условий текущей программной точки.

#### 3.3 Стек предположений

Компилятор при анализе потока управления поддерживает для каждого базового блока множество
предположений:

- **if-guard**: `if y > 0` → в true-ветку добавляется `y > 0`, в false-ветку добавляется `!(y > 0)`
  (если есть else)
- **match-паттерн**: `if let Some(v) = opt` → в ветке добавляется `opt == Some(v)`
- **Логические связки**: `if x > 0 and y < 10` → в ветке добавляются `x > 0` и `y < 10`
- **Предусловия функции**: при вызове `divide(a, b)` значение `b` должно удовлетворять `Positive` —
  доказательство либо из текущих предположений, либо из собственного уточнённого типа фактического
  аргумента (`b` аннотирован как `Positive`, значит его тип несёт `b > 0`)
- **Присваивание**: при `let z = y` уточнённые условия с `y` передаются на `z`

Все предположения попадают в конвейер доказательств времени компиляции. При входе на путь с
SMT-ускорением переводятся в SMT-LIB фоновые утверждения.

#### 3.4 Без статического доказательства — ошибка компиляции

Если программист напишет напрямую:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей программной точке нет предположения `y > 0`, у фактического аргумента `y` самого по себе
также нет типовой аннотации `Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (не имплицирует) → ошибка компиляции:

> Не удаётся доказать, что параметр `b` удовлетворяет `Positive` при вызове `divide`. `y` происходит
> из ввода функции, нет доказанных границ. Рассмотрите вызов с охранением ветки:
> `if y > 0 { divide(x, y) }`.

YaoXiang не принимает значения времени выполнения, напрямую попадающие в параметры уточнённого типа
без предоставления статического доказательства. Это не ограничение — это ядро философии жёсткой
безопасности. Код, который компилятор не может статически доказать, не должен проходить компиляцию.

#### 3.5 Связь с унифицированным конвейером

Распространение путевых условий — это не дополнительный механизм. Это прямое расширение конвейера
доказательств времени компиляции на анализ потока управления:

| Фаза                   | Ответственность                                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий   | фаза анализа потока управления компилятора, аннотирование каждого базового блока множеством предположений         |
| Генерация VC           | при необходимости верификации типапового ограничения, объединение путевых условий + информации о типах аргументов |
| Вычисление в конвейере | ядро компилятора → SMT-ускорение → результат Proved / Disproved / Unproven                                        |
| Результат              | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка + недоказанная пропозиция |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновое знание
конвейера доказательств — как типовые равенства и ограничения заимствования, используют ту же трубу
и ту же бюджетную систему.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции используют единый конвейер. Ядро конвейера — это **проверка типов**
— проверка, равен ли тип доказательства доказываемому утверждению. Всё — проверка типов.

```
Компилятор встречает Bool-выражение, требующее вычисления (т.е. требуется сконструировать доказательство)
        │
        ├── Типовое равенство (T1 == T2)
        │   → компилятор определяет напрямую (структурная эквивалентность)
        │
        ├── Условия конфликта токенов (!conflicting(tokens))
        │   → потоково-чувствительный анализ активности (отслеживание атрибутов Dup/Linear)
        │
        ├── Редукция зависимых типов (n + m упрощается)
        │   → система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикаты времени компиляции (x > 0, forall...)
        │   → сам компилятор + модуль SMT-ускорения
        │
        └── Импликации логики Хоара (P ⇒ Q)
            → компилятор + модуль SMT-ускорения
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → компиляция успешна
             │ Disproved│  → ошибка компиляции + контрпример
             │ Unproven │  → ошибка компиляции + недоказанная пропозиция
             └────┬─────┘
                  │
                  ▼
         Программист пишет доказательную функцию (код YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ─→ Proved ─→ компиляция успешна
                  │
                  ▼
            Верификация неудачна → ошибка компиляции: "доказательство не выполняется"
```

#### 4.1 Результаты доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — это неизбежный вывод из проблемы
остановки, а также естественное разделение в теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → остановка, доказательство сконструировано, проверка типов пройдена. Компиляция
  продолжается.
- **Disproved(M)** → остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → доказательство не сконструировано в пределах данного лимита ресурсов. Ошибка
  компиляции + недоказанная пропозиция + отчёт о потреблении бюджета.

**Unproven ≠ False.** Когда компилятор говорит «я не могу доказать» — это не эквивалентно тому, что
утверждение ложно — просто это выходит за рамки текущих возможностей автоматического доказательства.
Это честность, а не дефект.

Жёсткие бюджетные ограничения — это инженерное решение проблемы остановки. Никаких ручек — их
наличие означало бы вопрос к пользователю «как вы думаете, остановится ли ваша программа», на
который не знает ответа ни пользователь, ни компилятор.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **доказательную функцию** — просто
функцию YaoXiang, тип возврата которой равен доказываемому утверждению. Проверщик типов верифицирует
эту функцию — это тот же механизм, что и верификация `add(a, b): Int`.

```
Пропозиция = тип
Доказательство = программа (значение этого типа)
Верификация = проверка типов (единственный корень доверия)
```

SMT-решатель — это не отдельная граница доверия — это **ускорительный модуль проверщика типов**. SMT
помогает найти доказательство, но верифицирует доказательство всегда проверщик типов. Когда SMT
возвращает `unsat`, компилятор реконструирует результат в доказательство, верифицируемое проверщиком
типов. Если реконструкция не удаётся (шаги вывода SMT выходят за рамки правил вывода ядра
компилятора), происходит откат к Unproven — программист может вручную написать доказательную
функцию.

```yaoxiang
# Пропозиция: уточнённое свойство, которое компилятор не может автоматически доказать
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, тип возврата которой — приведённая выше пропозиция
# Проверщик типов верифицирует эту функцию — точно так же, как и add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # компилятор здесь верифицирует: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Не нужно AI, не нужно экспорта в Coq, не нужны новые концепции. **Свойства, которые не могут быть
автоматически доказаны во время компиляции → программист пишет доказательство кодом YaoXiang →
проверщик типов верифицирует.** Весь процесс — это плавный градиент — компилятор делает простые
доказательства за вас, оставляя сложные для человека.

#### 4.3 Слоёная зависимость внутри конвейера

Вышеупомянутые вычислители совместно используют один интерфейс, но существует порядок вычисления.
Типовое равенство — это предпосылка для всего последующего анализа; проверка владения/токенов
зависит от информации о типах; верификация уточнённых предикатов зависит от результатов двух
предыдущих слоёв. Компилятор вычисляет послойно, выражения с неудавшимся нижним слоем не попадают в
верхний — чтобы не тратить бюджет решателя на программы с ошибками типов.

```
Порядок вычисления (один конвейер, послойное планирование)
├── Слой 0: Типовое равенство (T1 == T2)
│   └── структурная унификация → при неудаче дальнейшее бессмысленно, сразу возвращается Disproved
├── Слой 1: Владение/конфликт токенов
│   └── потоково-чувствительный анализ активности → при неудаче безопасность памяти не выполняется, сразу возвращается Disproved
└── Слой 2: Уточнённые предикаты/импликации Хоара
    └── сам компилятор → SMT-ускорение → результат Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, совместно используя тот же интерфейс
и ту же бюджетную систему.

### 5. Унификация трёх уровней функций

| Уровень                     | Время выполнения | Вход         | Выход    | Пример                                         |
| --------------------------- | ---------------- | ------------ | -------- | ---------------------------------------------- |
| Функция значения            | Время выполнения | Значение     | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типа            | Время компиляции | Тип/значение | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат времени компиляции | Время компиляции | Значение     | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют идентичный синтаксис `name: type = value`. Предикаты времени компиляции и
конструкторы типов идут по одному конвейеру доказательств времени компиляции — `{}` — это
пространство доказательств.

### 6. Циклы: генерация условий верификации по Флойду-Хоару

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Типовые аннотации с
предикатами времени компиляции на переменных определяют утверждения в стиле Флойда-Хоара —
компилятор из типовых аннотаций генерирует условия верификации, конвейер доказательств проверяет,
сохраняет ли каждое присваивание тип.

Основной механизм: каждая операция присваивания соответствует тройке Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует условие верификации для тела цикла один раз —
после того как конвейер доказательств подтвердит индуктивный шаг, все итерации автоматически
покрываются.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i; при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # верификация: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # компилятор генерирует VC для тела цикла один раз. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   обязательство по верификации: s_new удовлетворяет SumUpTo(arr, i) (текущее i не меняется)
        #   подстановка s_new = s_old + arr[i]:
        #     требуется s_old + arr[i] == sum(arr[0..i+1])
        #     из индуктивной гипотезы s_old == sum(arr[0..i]), прибавив arr[i] к обеим сторонам:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменяется → в графе зависимостей типовая аннотация s ссылается на i → триггер повторной верификации
        #   новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   т.е. s == sum(arr[0..i_new]), гарантируется предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # В этот момент s: SumUpTo(arr, arr.len), т.е. s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это типовая аннотация на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант и не нужно «автоматически проводить
индукцию» — он разлагает индуктивное доказательство на локальные условия верификации для каждой
операции присваивания, передавая их в конвейер доказательств для покомпонентного решения.

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеописанного механизма: компилятор знает, что типовая аннотация `SumUpTo(arr, i)`
переменной `s` ссылается на `i` — когда `i` изменяется, типовое ограничение `s` также должно
измениться. Это требует от компилятора поддержания **графа типовых зависимостей между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# ключ — зависимая переменная, значение — множество переменных, на которые ссылается её типовая аннотация
# пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: при обработке `mut v: Pred(... x ...) = init` проверщик типов анализирует свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылка на другую изменяемую переменную
`x` из текущей области видимости, в графе зависимостей записывается `x → v`.

**Триггер**: когда зависимой переменной `x` присваивается значение, компилятор:

1. Находит в графе зависимостей все переменные, зависящие от `x` — `{v₁, v₂, ...}`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательств

**Чувствительность к порядку присваиваний**: отслеживание зависимостей естественным образом
обеспечивает правильный порядок присваиваний. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменяется → повторная верификация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отклоняет
i += 1        # i изменяется → повторная верификация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлена, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Комбинированные зависимости**: переменная может зависеть от нескольких переменных. Типовая
аннотация `{ v: Int; v == x + y }` одновременно зависит от `x` и `y` — изменение любой из них
триггерит повторную верификацию.

**Связь с конвейером доказательств**: отслеживание зависимостей — это триггер генерации VC, а не
отдельный верификационный механизм. Оно отвечает на вопрос «когда нужно генерировать VC» — конвейер
доказательств отвечает на вопрос «выполняется ли VC».

### 7. Проверка завершения

**Область применения: уточнённые типы.** Завершаемость — это не отдельный переключатель, а часть
**режима верификации**: как только тип уточняется (`Refined { base, constraint }`), вычисление,
которое он аннотирует, входит в режим верификации, где требуется завершаемость; обычные неуточнённые
типы не входят в режим верификации, для них не генерируются обязательства по завершаемости.

Из этого следуют два вывода:

- **Циклы**: «голый» `while` не входит в режим верификации; когда переменная-счётчик аннотируется
  уточнением (например `i: UpTo(n)`), цикл входит в режим верификации, требуется доказать
  завершение.
- **Рекурсия**: когда сигнатура функции уточнена (уточнение параметра или уточнение в типе
  возвращаемого значения), функция входит в режим верификации, требуется доказать строгое убывание
  меры на каждой точке рекурсивного вызова.

Приоритет — автоматическое в режиме верификации: компилятор сначала автоматически исследует меры,
что доказуемо — проходит; если автоматическое исследование не дало результата и мера не указана явно
— ошибка компиляции. **Никаких синтаксических лазеек для аннотаций** — мера и утверждение о
завершаемости пишутся в типовой позиции, без введения нового синтаксиса вроде `decreases`. Формы
меры и явного резервного варианта см. в §6.9.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершаемости, из двух
источников:

1. **Типовые аннотации переменных**: граничные ограничения в уточнённых типах (например `UpTo(n)`
   даёт верхнюю границу `n` и нижнюю границу `0`)
2. **Операции в теле цикла**: операции, применяемые к переменной при каждой итерации

Компилятор пытается применить четыре стратегии синтеза меры в порядке приоритета, останавливаясь на
первой подходящей. Четыре стратегии — это **ограниченная последовательность шаблонов для
исследования меры**, входом являются уточнённые ограничения (стратегии 1–4 начинают с «переменной с
ограниченным типом»), а не «код, вычисляемый во время компиляции»; они являются автоматической и
ручной сторонами одного и того же механизма, описанного в §6.9.

> **Исследование меры — это исследование, а не вывод.** Исследование только перечисляет шаблоны
> (линейный ранг, счётчик нарушений, ограниченный паттерн, мультипликативное масштабирование), не
> гарантируя наличия решения — общий вывод меры, как правило, неразрешим (сводится к проблеме
> остановки). Поэтому для случаев за пределами шаблонов программист должен явно указать меру (§6.9),
> иначе — ошибка компиляции.

#### 6.2 Стратегия 1: Автоматический синтез линейной ранговой функции

Когда переменная имеет линейную граничную аннотацию, компилятор перечисляет кандидатов линейных мер
и верифицирует их через SMT.

```
Вход:
  переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с верхней и нижней границами)
  условие цикла cond
  множество присваиваний в теле цикла

Алгоритм:
  1. Извлечение границ каждой переменной из типовой аннотации: [low_i, high_i]
  2. Перечисление кандидатов меры: v_i, u_i - v_i, v_i - v_j и другие линейные комбинации
  3. Для каждого кандидата меры m:
     - SMT-верификация m ≥ 0 (выводится из типовых границ)
     - Для каждого пути выполнения в теле цикла SMT-верификация m' < m (строгое убывание)
  4. Найдена подходящая линейная комбинация → завершаемость доказана
```

Покрытие: циклы, где произвольная переменная получает линейное выражение (`v = a·v + b`) и имеет
ограниченную типовую аннотацию. Включает `i += const`, `i -= const`, а также сжатие интервала в
стиле бинарного поиска:

```yaoxiang
# Бинарный поиск: low = mid + 1 или high = mid
# Мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: Счётчик нарушений предиката — мера автоматически извлекается из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущее состояние: экспериментальная стратегия, решение о включении принимается при
> реализации этапа 3 на основе практической осуществимости.** Данная стратегия эффективна для
> операций соседнего обмена (пузырьковая сортировка, сортировка вставкой), но не может автоматически
> доказать для операций не соседнего обмена (разделение в быстрой сортировке, sift-down в
> пирамидальной сортировке). Таблицу границ покрытия см. ниже. Если на этапе 3 верификация окажется
> неосуществимой, стратегия будет удалена или понижена до будущей работы.

Ключевая идея: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted`, автоматически извлекает меру из определения.

```
Вход:
  целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  операции в теле цикла: обмен соседних элементов

Алгоритм:
  1. Разбор определения предиката: forall i in range: cond(i, arr)
  2. Автогенерация меры: violation_count = |{ i | ¬cond(i, arr) }|
  3. Анализ влияния операций на меру:
     - соседний обмен arr[j], arr[j+1] = arr[j+1], arr[j]
     - затрагивает только три пары индексов j-1, j, j+1
     - если arr[j] > arr[j+1] (нарушение предиката), после обмена эта пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя граница: 0
  → завершаемость доказана
```

**Текущая область покрытия**:

| Алгоритм            | Паттерн операций     | Стратегия 2 доказывает? | Причина                                              |
| ------------------- | -------------------- | :---------------------: | ---------------------------------------------------- |
| Пузырьковая         | соседний обмен       |           ✅            | violation_count при каждном обмене строго убывает    |
| Сортировка вставкой | соседнее перемещение |           ✅            | каждое перемещение устраняет одно нарушение          |
| Сортировка выбором  | обмен не соседних    |           ❌            | один обмен может увеличить violation_count           |
| Быстрая             | partition-разделение |           ❌            | обмен не соседних, нет гарантии монотонного убывания |
| Пирамидальная       | sift-down            |           ❌            | древовидные операции, violation_count не монотонен   |

**Дополняющие стратегии**: для быстрой сортировки сжатие интервала `low < high` покрывается
стратегией 1 (линейная ранговая функция) — внешний рекурсивный partition, каждый раз интервал
уменьшается вдвое. Стратегии 1 и 2 взаимно дополняют друг друга, завершаемость большинства реальных
алгоритмов может быть доказана одной из них. Но обобщение стратегии 2 (операции не соседние,
древовидные операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: Ограниченный паттерн возрастания/убывания

`v += const` (нормальное число), переменная имеет верхнюю граничную типовую аннотацию → мера
`upper_bound - v` убывает на `const` при каждом шаге, нижняя граница 0. Это вырожденный случай
стратегии 1, компилятор обрабатывает его в первую очередь.

#### 6.5 Стратегия 4: Шаблон мультипликативной масштабируемой меры

`v *= const` (const > 1), переменная имеет верхнюю и нижнюю граничные типовые аннотации. Компилятор
имеет встроенный шаблон логарифмической меры `ceil(log_const(upper/v))`, при каждом умножении на
const мера уменьшается на 1.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # Компилятор автоматически выводит: мера ceil(log₂(n/i)), каждое умножение на 2 уменьшает меру на 1
    i *= 2
}
```

#### 6.6 Разделение завершаемости и корректности

Доказательство завершаемости и доказательство корректности независимы:

- **Завершаемость**: четыре вышеописанные стратегии автоматически доказывают, что цикл завершится за
  конечное число шагов; при неудаче автоматического исследования программист указывает меру в
  типовой позиции (§6.9)
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  через условия верификации

Оба проходят → компиляция успешна. Завершаемость доказана, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершаемость не может быть доказана → ошибка
компиляции с указанием неанализируемой переменной или операции. Оба не прошли → ошибка компиляции с
отдельными отчётами о двух неудачах.

#### 6.7 Проверка завершения рекурсивных функций

Для рекурсивных функций с уточнёнными сигнатурами компилятор проверяет убывание формальных
параметров на каждой точке рекурсивного вызова:

```yaoxiang
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)  // компилятор исследует: мера (b, a % b) в правильном порядке убывает → завершаемость
}
```

Убывание формальных параметров — это самый мощный автоматический путь (структурная рекурсия). При
неудаче автоматического исследования программист явно указывает меру в типовой позиции (§6.9).

#### 6.8 Жёсткие границы

`i = f(i)` и `f` необратима, не замкнута, не сохраняет монотонность — математически невозможно
автоматически доказать завершаемость. Ошибка компиляции:

> Данный цикл невозможно автоматически доказать завершаемым. Цикловая переменная зависит от
> неанализируемой функции `f`. Используйте итерационный паттерн, анализируемый компилятором, либо
> привяжите имя к этому циклу и предоставьте меру в типовой позиции (§6.9).

Это не неудача компилятора. Код, безопасность которого не может быть статически доказана, не должен
проходить компиляцию. Даже при предоставлении явной меры она должна быть определена через SMT как
истинная, иначе — ошибка; человек может не суметь доказать, но не может доказать неверно.

#### 6.9 Явная мера: `Terminates`

Когда автоматическое исследование не находит меру, программист пишет меру в **типовой позиции** —
тот же механизм, что `Positive(b)`, `IsMax(T, arr, result)` (применение предиката), ноль нового
синтаксиса:

```yaoxiang
// Мера: обычная функция, тестируемая, переиспользуемая, не участвует во время выполнения
gcd_measure: (a: Int, b: Int) -> Int = { b }

// Компонент завершаемости — в типовой позиции самой функции
gcd: Terminates((a: Int, b: Int) -> Int, gcd_measure) = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

// Цикл: имя привязки — это точка якоря, мера получает значение из области видимости по имени
loop: (n: Int) -> Int = {
    mut i = 0
    acc: Terminates(n - i) = while i < n {
        i = i + 1
    }
    return acc
}
```

Обоснование для цикла: `Terminates(m)` уточняет тип выражения в позиции хвоста цикла, точка якоря
предоставляется именем привязки `acc` — цикл таким образом становится идентифицируемым, устраняется
слепая зона «анонимная конструкция не может быть идентифицирована».

**`Terminates` — это встроенный предикат**, наряду с `Int`, `Never` — это примитив ядра. Это
единственный предикат, **тело которого генерируется компилятором** — его утверждение («мера строго
убывает на каждой точке рекурсивного вызова/обратной связи цикла») встроено в структуру вычисления,
пользовательский предикат не может обратиться к телу функции или циклу, поэтому его нельзя выразить
синтаксисом «определение предиката» из раздела «Синтаксис». Встроенная часть сводится к этому
единственному имени.

**Арность**. `Terminates(FnType, m)` и `Terminates(m)` — это один и тот же предикат с двумя
арностями, а не две разные конструкции:

| Форма                   | Якорь             | Назначение                                             |
| ----------------------- | ----------------- | ------------------------------------------------------ |
| `Terminates(m)`         | имя привязки      | саморекурсивные функции, циклы — форма по умолчанию    |
| `Terminates(FnType, m)` | явный тип функции | взаимная рекурсия и др. случаи с неединственным якорем |

Оба по сути одно: обязательство по завершаемости всегда привязано к «тому вычислению, которое
аннотировано уточнением в типовой позиции».

**Мера не ограничивает тип возврата.** Мера может быть выражением произвольного типа (не обязательно
натуральное число); «строгое убывание» на ней определяется через доступный на этом типе правильный
порядок. Является ли мера фундированной (например, при возврате `Int` должна быть `>= 0`) — это
**отдельное обязательство**, которое так же передаётся уточнённому выводу или SMT; когда оба не
выводятся, диагностика **не отклоняет напрямую**, а рекомендует проверить направление (нижняя ли
граница у меры, действительно ли рекурсивные параметры движутся в этом направлении).

**Связь с автоматическим исследованием**: явная мера — это не отдельный конвейер, а вход после
неудачи исследования. После предоставления меры всё равно идёт по тому же SMT для верификации
убывания и фундированности; если не выполняется — ошибка с контрпримером.

Подробности механизмов генерации обязательств, конвейера определения, направлений диагностики, общих
мер для взаимной рекурсии (SCC) и др. — см.
[RFC-027a: Явная мера для проверки завершаемости](../review/027a-termination-explicit-measure.md).

### 8. SMT-решатель: ускорительный модуль проверщика типов

В традиционных языках SMT-решатель — это внешний инструмент (F\* вызывает Z3, Dafny вызывает Z3). В
YaoXiang это **ускорительный модуль проверщика типов** — вызывается только когда само ядро
компилятора не может напрямую определить результат. SMT помогает найти доказательство, но
верифицирует доказательство проверщик типов.

**Модель доверия**: проверщик типов — единственный корень доверия. SMT-решатель — ускорительный
модуль — он помогает найти доказательство, но SMT — это не отдельная граница доверия. Компилятор
доверяет результату `unsat` от Z3 (согласуется с подходом F*/Dafny — вероятность ошибки Z3 ниже
вероятности бага самого компилятора, это прагматичный инженерный выбор). Реальный контроль
надёжности — на уровне перевода в SMT; если в переводе есть баг, он проявится в других тестах
компилятора.

**Интерфейс**: компилятор внутренне переводит в стандартный формат SMT-LIB 2.6, а не в API
конкретного решателя. SMT-LIB — это стандарт ISO, Z3, CVC5, MathSAT, Yices все поддерживают нативно.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, наиболее широко документирован и проверен сообществом).
CVC5 как SMT-LIB-совместимая альтернатива — пользователь может переключить через флаг компиляции.

Никакого «универсального слоя абстракции решателя» — SMT-LIB и есть этот слой. Если в будущем CVC5
покажет прорыв в определённых теориях, переключение — это просто замена бинарника, без изменения
кода компилятора.

```
Bool-выражение времени компиляции
        │
        ├── Ядро компилятора может определить напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после константной свёртки)
        │   → напрямую возвращает Proved / Disproved
        │
        └── Ядро компилятора не может определить (кванторы, символьные переменные)
            → предредукция зависимых типов (factorial(5) → 120)
            → перевод в формат SMT-LIB
            → отправка в Z3/CVC5 (с лимитом бюджета)
            → возвращаемое значение: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткое ограничение, как глубина стека**:

| Измерение бюджета           | Значение по умолчанию | Описание                                                                                                                                                                                     |
| --------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения         | 10 000                | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 покрывает 99% практических предикатов.                                                                                  |
| Время                       | 100 мс                | Если один предикат вычисляется дольше 100 мс = пользователь пишет программу времени компиляции, а не типовую аннотацию. 100 мс × 50 предикатов = верхний предел времени компиляции 5 секунд. |
| Глубина инстанции кванторов | 3                     | Три уровня вложенности кванторов покрывают практические паттерны. Глубже — скорее всего логические упражнения.                                                                               |

При превышении бюджета возвращается Unproven, ошибка компиляции + позиция предиката + потреблённый
бюджет. Никакой деградации, никаких проверок во время выполнения, никакого тихого прохождения.

**Почему это практически работает**: в инженерной практике 95% реальных предикатов — это линейная
арифметика — `x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в разрешимом фрагменте, SMT-решатель
возвращает за миллисекунды. Для редких сложных предикатов, превышающих бюджет, программист просто
пишет доказательную функцию.

Перед вызовом SMT выполняется предредукция зависимых типов: `factorial(5)` вычисляется напрямую во
время компиляции и даёт `120`, `append([1,2], [3])` напрямую вычисляется и даёт `[1,2,3]`. Эти
детерминированные вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Ментальная модель: **компилятор может доказать —
проходит, не может — ошибка; если компилятор не может, ты можешь написать функцию и доказать ему.**

### 9. Комбинирование предикатов времени компиляции

Предикаты времени компиляции — это функции, возвращающие Type, комбинирование естественно
достигается через функциональную композицию:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасное деление

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ компилятор верифицирует Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ компилятор верифицирует Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ компилятор верифицирует InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ компилятор верифицирует InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Циклы: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: унифицированная диспетчеризация времени компиляции и выполнения

`assert` и `Assert` — это две стороны одного примитива уточнённого типа. Конвейер диспетчеризации
`dispatch` автоматически решает — идти в compile-time доказательство или runtime проверку — по
критерию **свободны ли переменные предиката доступны во время компиляции**:

| Критерий                                                                                                | Режим           | Поведение                                                                                                            |
| ------------------------------------------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры обобщения, константы компиляции)       | **CompileTime** | идёт в конвейер доказательств: Proved → стирание, Disproved → ошибка компиляции, Unknown → требование доказательства |
| Существуют свободные переменные из времени выполнения (параметры функций, внешний ввод, mut-переменные) | **Runtime**     | вставка runtime check и инъекция уточнённого факта в потоково-чувствительное множество предположений Γ               |

**Ключевое**: «не могу определить» ≠ «опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихой деградации), в режиме Runtime утверждение во время компиляции вообще не
имеет истинностного значения — никакой, даже самый мощный, решатель не может написать тавтологию для
«пользователь мог ввести отрицательное число», runtime check — единственный sound выбор. Это не
слабость решателя, а теоретическая неизбежность.

### 12. Потоково-чувствительное множество предположений Γ: распространение наисильнейшего постусловия

Компилятор поддерживает потоково-чувствительное (flow-sensitive) множество предположений Γ,
отслеживающее известные истинные пропозиции в каждой точке потока управления.

**SP (наисильнейшее постусловие) распространение**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP распространение
```

**Kill set для mut-переменных**: после переприсваивания mut-переменной все предположения,
затрагивающие эту переменную, удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые предположения
недействительны.

**Слияние веток**: при слиянии IF/ELSE или match-веток Γ берёт пересечение предположений всех веток.
Только пропозиции, истинные на всех путях, выходят за пределы ветки.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 о том, что «уточнённые типы **полностью стираются** во время выполнения»,
относится к **proof witness (токенам доказательства)** — доказательства, верифицированные во время
компиляции, не генерируют рантайм-код. Но **runtime check**, вставляемый dispatch в режиме Runtime,
сохраняется — это Bool-проверка на уровне значений, а не witness на уровне типов.

Итого: witness стирается, check сохраняется. Две вещи не конфликтуют, исходное утверждение RFC-027
остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| До (RFC-022)                          | После (данный RFC)                                                                                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | предикат времени компиляции как тип параметра `(b: Positive(b))`                                                                          |
| `//! ensures: ExistsMax(result, arr)` | тип возврата с параметром возвращаемого значения `-> (result: IsMax(T, arr, result))`                                                     |
| `/*! invariant: ... !*/`              | типовые аннотации с предикатами времени компиляции на переменных — инварианты Флойда-Хоара                                                |
| `//! decreases: n`                    | мера пишется в типовой позиции уточнения (`Terminates`); компилятор сначала исследует автоматически, при неудаче требуется явное указание |
| спецификации — это комментарии        | спецификации — это система типов                                                                                                          |

### Синтаксис

**Для предикатов времени компиляции нет новых ключевых слов.** `{}` — это пространство
доказательств, полностью согласованное с существующим синтаксисом определения типов. Предикат
времени компиляции — это функция, возвращающая Type — `name: (params) -> Type = { утверждения }`.
При использовании — это вызов функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# предикат времени компиляции = функция, возвращающая Type, {} — это утверждения, верифицируемые компилятором
# используется существующий синтаксис функций/типов, новые BNF-правила не требуются
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Фактические аргументы при применении предиката должны быть в форме compile-time констант** —
литералы, переменные (связывание по имени), применения типов (рекурсивное извлечение) или **ссылки
на функции, идентифицируемые во время компиляции** (имена функций). Форма фактического аргумента, не
преобразуемая в константное выражение, вызывает **E1092**, несоответствие числа фактических и
формальных аргументов вызывает **E1093**. Фактические аргументы связываются с формальными по
позиции, арность предиката определяется его объявлением — `Positive(x)` унарный,
`IsMax(T, arr, result)` тернарный, `Terminates(m)` и `Terminates(FnType, m)` унарная и бинарная —
уточнённые ограничения **никогда не отбрасываются молча** (ранее неконвертируемый фактический
аргумент приводил к тихому исчезновению ограничения, связывание, нарушающее ограничение, проходило
молча).

**Новая синтаксическая концепция: параметр возвращаемого значения** — в `-> (name: Type)` `name` —
это параметр возвращаемого значения.

Параметр возвращаемого значения — это **единственная синтаксическая концепция**, которую YaoXiang
вводит сверх существующего синтаксиса функций. Его семантика:

- значение `name` предоставляется оператором `return`
- `name` существует только в типовой сигнатуре, упоминается предикатом постусловия (например
  `-> (result: IsMax(T, arr, result))`)
- `name` не входит в область видимости тела функции, не появляется у вызывающей стороны
- параметр возвращаемого значения **опционален** — при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), никакой дополнительной нагрузки

Причина введения: постусловию нужно ссылаться на «значение, которое функция вернёт». Без параметра
возвращаемого значения компилятор мог бы только через специальные правила (неявные переменные вроде
`$result` или `__retval__`) позволить предикату ссылаться на возвращаемое значение. Параметр
возвращаемого значения делает такую ссылку явной — это просто параметр, только значение
предоставляется `return`, а не вызывающей стороной.

**Доказательная функция** — это не новая концепция — это просто функция YaoXiang, тип возврата
которой равен утверждаемой пропозиции. Когда компилятор возвращает Unproven, программист
предоставляет доказательную функцию, проверщик типов верифицирует её точно так же, как и любую
другую функцию. Никакого нового синтаксиса, новых ключевых слов, новых правил.

> **Граница между ними.** В области корректности (предикат Unproven) доказательство дополняется в
> **теле**: пишется функция, тип возврата которой — доказываемая пропозиция. В области завершаемости
> (§6.9) мера дополняется в **типовой позиции**: пишется `Terminates(мера)` как тип связывания или
> сигнатуры функции. Механизм един (всё — применение уточнённого типа), различие в точке применения.
> В области завершаемости **не нужно** писать функцию `_proof`.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функции, принимающие
  значения и возвращающие Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с обобщениями**: предикаты времени компиляции могут иметь обобщённые параметры,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения, могут только читать, не могут писать
- **Вывод типов**: параметры предикатов времени компиляции участвуют в HM-выводе типов

### Представление во время выполнения

Предикаты времени компиляции во время выполнения обрабатываются согласно результату dispatch:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): после подтверждения
  доказательства witness полностью стирается. `Positive: (x: Int) -> Type = { x > 0 }` — параметр
  `b: Positive(5)` во время выполнения представляется просто как `Int`. Уточнённое условие
  `{ 5 > 0 }` уже проверено, стёрто.
- **Режим Runtime** (существуют свободные переменные времени выполнения): сохраняется runtime check
  — Bool-проверка на уровне значений, инъекция в потоково-чувствительное множество предположений Γ.
  Подробности см. в §11 конвейер диспетчеризации dispatch и §13 уточнение модели стирания.

Размещение предиката времени компиляции в типовой позиции (например `f(x: Positive(x))`) не создаёт
обёрточного типа, не выделяет дополнительную память. Но когда `x` происходит из ввода времени
выполнения, **вставляется** runtime Bool-проверка.

**Ограничение взаимодействия с `ref`**: предикаты времени компиляции могут ссылаться только на
неизменяемые заимствования или значения с переданным владением. Если предикат времени компиляции
ссылается на изменяемое заимствование, компилятор не может гарантировать во время компиляции, что
результат верификации останется верным во время выполнения — такое использование вызывает ошибку
компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, дополнительные
   правила парсинга не требуются
2. **Конвейер доказательств времени компиляции**: унифицированный интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **Модуль SMT-ускорения**: уровень перевода в SMT-LIB 2.6 + интеграция Z3/CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/удаление универсальных кванторов. Это единственный корень доверия, через него
   верифицируются и SMT, и доказательства программиста
5. **Генерация условий верификации**: исчисление WP/SP + обязательства по доказательству инвариантов
   циклов
6. **Сообщения об ошибках**: форматирование контрпримеров + отчёты о недоказанных пропозициях +
   привязка к позициям исходного кода

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, полностью неизменен
- ✅ Предикаты времени компиляции в режиме CompileTime имеют нулевые накладные расходы во время
  выполнения, в режиме Runtime сохраняют только необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 более не поддерживается — но 022 никогда не был реализован,
  миграционная нагрузка отсутствует

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Ховарда**: тип — это пропозиция, программа — это
  доказательство, `name: Proposition = Proof`
- **Унификация**: предикаты времени компиляции и обычные функции используют полностью идентичный
  синтаксис, нет концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, ментальная модель
  согласована с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции и постепенно
  расширять покрытие
- **Минимальные накладные расходы во время выполнения**: режим CompileTime имеет нулевые накладные
  расходы, режим Runtime сохраняет только необходимые Bool-проверки

### Недостатки

- **Время компиляции**: SMT-решение увеличивает время компиляции, но жёсткие бюджетные ограничения
  гарантируют контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами теории первого порядка
  линейной арифметики могут требовать от программиста написания доказательной функции. Это не
  недостаток языка — это неизбежный вывод из проблемы остановки. Компилятор честно сообщает
  Unproven, а не притворяется True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и доказательных функций
  требует понимания базовых интуиций изоморфизма Карри-Ховарда
- **Сложность реализации**: унификация конвейера доказательств времени компиляции требует
  тщательного проектирования

### Снижение рисков

- Жёсткие бюджетные ограничения SMT-решения (шагов 10 000 / времени 100 мс / глубины инстанции 3),
  при превышении возвращается Unproven
- Предредукция зависимых типов: детерминированные вычисления значений обрабатываются заранее, SMT
  занимается только недетерминированной частью
- Unproven — не тупик: в области корректности пишется доказательная функция (тип возврата =
  пропозиция), в области завершаемости в типовой позиции указывается мера (§6.9) — оба
  верифицируются проверщиком типов
- Инкрементная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках +展示 контрпримеров + отчёты о потреблении бюджета + недоказанные
  пропозиции + рекомендации (если компилятор может их дать)

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, наиболее широко проверен). CVC5 как
      SMT-LIB-совместимая альтернатива, переключение через флаг компилятора. Внутренний перевод
      компилятора — в стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, никакого
      самописного универсального интерфейса решателя.
- [x] **Конкретные数值 бюджета решения**: шагов 10 000 / времени 100 мс / глубины инстанции
      кванторов 3. Фиксированы внутри компилятора, без ручек. Если на практике окажется недостаточно
      (доказуемо реальными случаями использования, а не «пользователь ошибся»), скорректировать.
- [x] **Область поддержки кванторов**: на уровне языка ограничений на порядок кванторов нет.
      Предикаты времени компиляции принимают параметры типа Type — Type включает типы функций —
      следовательно, кванторы высших порядков — естественное следствие системы типов, не требует
      специального синтаксиса. SMT-решатель может автоматически определять кванторы первого порядка
      (forall/exists, поддерживает чередующуюся вложенность, ограничено глубиной 3). Кванторы высших
      порядков: SMT возвращает Unproven, компилятор подсказывает «данный предикат выходит за рамки
      автоматического доказательства, предоставьте доказательную функцию». Программист пишет
      функцию, тип возврата которой равен этой пропозиции — проверщик типов верифицирует. Никакого
      внешнего экспорта, никакого AI, никакого интерактивного режима доказательства. Всё — код
      YaoXiang, всё верифицируется проверщиком типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      SMT-имена переменных (с префиксом модуля во избежание конфликтов). При возврате модели Z3 —
      обратный поиск по имени переменной. Формат вывода: имя переменной = конкретное значение +
      позиция в исходном коде + позиция определения предиката. Никаких сложных слоёв отображения.
- [x] ~~**Взаимодействие предикатов времени компиляции с интеллектуальными указателями `ref`?**~~ →
      Решено: предикаты времени компиляции допускают только неизменяемые заимствования или значения
      с переданным владением. Значения с изменяемым заимствованием не могут появляться в предикатах
      времени компиляции.
- [x] **Расширение меры счётчика нарушений forall-предиката на операции не соседнего обмена?** → Не
      расширять. Текущее покрытие (соседний обмен, соседнее перемещение) взаимно дополняется

      — это именно тот реальный сценарий, который данный пункт призван предвосхитить — шаблонная
      последовательность исследования меры не может автоматически справиться с ними, и они не могут
      быть переписаны в анализируемый итерационный паттерн без ущерба для читаемости. Вывод:
      философия жёсткой безопасности остаётся в силе (неправильно написанная мера всё равно будет
      отклонена SMT с контрпримером, человек может не суметь доказать, но не может доказать
      неверно), но «при неудаче исследования — отклонение» смягчается до «при неудаче исследования
      программист может явно указать меру в типовой позиции» — см. §6.9.
- [x] **Взрыв комбинаций при перечислении линейных ранговых функций**: верхний предел перечисления
      кандидатов — 3 ограниченные переменные. ≤3: перечисление всех линейных комбинаций и
      SMT-верификация каждой. >3: только попытка однопеременных мер (`v_i`, `u_i - v_i`), при
      неудаче — ошибка компиляции с подсказкой «в цикле >3 ограниченных переменных, компилятор не
      может автоматически синтезировать многопеременную меру». Это не инженерный компромисс — это
      вынуждение программиста писать более простые циклы.
