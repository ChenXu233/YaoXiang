# RFC-027: Предикаты времени компиляции и унифицированная статическая верификация

> - [RFC-024: Модель параллелизма на основе spawn-блоков](../accepted/024-concurrency-model.md)

> — устарел

## Резюме

Данный документ предлагает ввести в YaoXiang **предикаты времени компиляции** как полноправных
граждан, унифицировав всю статическую верификацию времени компиляции в единый **конвейер
доказательств**. Предикат времени компиляции — это не внешняя спецификационная аннотация — это
функция. Это функция, возвращающая Type, которую можно использовать в позиции типа; компилятор
вызывает её во время компиляции и проверяет возвращаемое значение. Тип есть утверждение, вычисление
во время компиляции есть доказательство.

**Центральный тезис**: единственная задача проверки типов во время компиляции — построить и
верифицировать термы доказательств. Равенство типов, конфликты токенов, редукция зависимых типов,
вычисление предикатов времени компиляции, импликации логики Хоара — всё это различные проверки типов
в едином конвейере доказательств времени компиляции. SMT-решатель — это ускоряющий модуль проверщика
типов, а не отдельный корень доверия. Когда компилятор возвращает Unproven, программист пишет
функцию на YaoXiang в качестве доказательства — проверщик типов верифицирует её ровно так же, как он
верифицирует возвращаемый тип любой функции. Всё — это код на YaoXiang, всё проверяется проверщиком
типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это аннотация, отдельная от типа
    //! ensures: ExistsMax(result, arr[0..n])   ← это аннотация, отдельная от типа
}
```

Это фундаментальная ошибка соответствия Карри–Ховарда: **разделение спецификаций и типов на два
слоя**. Аннотация — это не тип. Аннотация не участвует в проверке типов. Аннотация — это мысленная
модель «внешнего инструмента».

В техническом описании сказано прямо:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Комментарии `//!` из RFC-022 — это внешний синтаксис, отдельный от системы типов
- Спецификационные типы и обычные типы — это две разные системы, что порождает концептуальную
  избыточность
- Разделение «Debug Build верифицирует / Release Build игнорирует» разрушает унификацию
- SMT-решатель в традиционном восприятии позиционируется как внешний инструмент — YaoXiang делает
  его встроенным ускоряющим модулем проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов — каждое идёт своим путём

### Правильная мысленная модель

Проверку типов можно абстрагировать в виде функции:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — сопоставление простых типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — это подзадачи этой функции. Они разделяют единый
конвейер доказательств, отличаясь лишь сложностью терма доказательства и стратегией его построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство —
возвращаемый тип этой функции равен доказываемому утверждению. Проверщик типов верифицирует её. Это
та же самая операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — это пространство доказательств: тип есть утверждение, верификация есть проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри — это утверждения;
компилятор гарантирует, что каждый элемент — True — либо автоматическим доказательством, либо
предоставленной программистом функцией-доказательством.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  компилятор гарантирует, что data — Array(T)
```

**Дженерики — это частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в сигнатуре      внутри {} только утверждения
#          компилятор верифицирует x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре   компилятор верифицирует type_of(T) == Type, type_of(data) == Array(T)
```

Один и тот же шаблон: `name: (params) -> Type = { утверждения }`. Компилятор не различает
«утверждения о типах» и «утверждения о значениях» — всё это цели вычисления в конвейере
доказательств.

**Циклические инварианты не нужно записывать отдельно. Аннотация типа на переменной — это и есть
инвариант Флойда–Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i — компилятору сообщается, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # компилятор верифицирует: s_new == sum(arr[0..i+1])
        i += 1       # i изменяется → срабатывает реверификация зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует для тела цикла одно условие верификации — индуктивное предположение (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. Когда конвейер
доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически. Не нужно
`: decreases`, не нужно `: Invariant`, не нужно индуктивное доказательство — компилятор разбивает
индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции как аннотации параметров и возвращаемого типа

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции становятся
аннотациями типов параметров или возвращаемого значения.

**На стороне параметров — это вызов функции.** Предикат времени компиляции — это функция,
возвращающая Type, и её использование на стороне параметра — это её вызов — точно так же, как
`factorial(5)`. На стороне возвращаемого значения вводится новое понятие: формальный параметр
возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive как аргумент
#                       компилятор в точке вызова извлекает значение аргумента, подставляет в b, верифицирует Positive(аргумент)
#                       пример: divide(10, 2) → верификация Positive(2) = { 2 > 0 } → True
#                       пример: divide(10, 0) → верификация Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возвращаемого значения, значение предоставляется return
#                                            компилятор в точке return подставляет возвращаемое значение, верифицирует постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **Сторона параметров**: `b: Positive(b)` — `b` — это имя текущего формального параметра,
  передаваемое в `Positive` как аргумент. Синтаксис вызова функции, никакой неявности.
- **Сторона возврата**: `-> (result: IsMax(T, arr, result))` — `result` — это формальный параметр
  возвращаемого значения, значение предоставляется оператором `return`. `result` существует только в
  сигнатуре типа, на него ссылается только предикат, он не попадает в область видимости тела функции
  и не виден вызывающему.
- **Формальный параметр возвращаемого значения необязателен**: при отсутствии постусловия он не
  записывается, сигнатура полностью совпадает с обычной функцией (`-> Int`).
- **Унификация**: параметры и формальные параметры возвращаемого значения — это одно и то же понятие
  — `имя_параметра: вызов_предиката(имя_параметра)`, различие лишь в том, предоставляется значение
  вызывающим или оператором `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно. Когда значение времени выполнения попадает в параметр уточняющего типа,
компилятор выполняет верификацию через сбор путевых условий и импликацию SMT — без необходимости
явной передачи доказательства программистом.

#### 3.1 Явный вызов функции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно — это вызов функции, никакой неявности.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предикатов времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, возвращаемый тип),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — это вызов функции
// после нормализации: b: { b > 0 }
```

Никакого неявного заполнения аргументов компилятором — `b: Positive(b)` — это точно такой же вызов
функции, как `f(5)`. `b` связывается как имя параметра, и его аннотация типа `Positive(b)` ссылается
на самого `b` — это стандартный паттерн зависимых типов, а не правило неявного разворачивания.

**Унификация с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а лишь
конвенциональное имя параметра («написать `p`, `this`, `x` — совершенно эквивалентно»).
`b: Positive(b)` использует тот же механизм — имя параметра может быть использовано в аннотации
типа. `self` появляется в позиции `self: Point`, `b` — в позиции `b: Positive(b)`, обе аннотации
типа ссылаются на сам параметр. Различие лишь в сложности аннотации, механизм полностью одинаков —
после связывания имени тип может зависеть от этого имени.

Возвращаемый тип также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возвращаемого значения, Sorted(result) — вызов функции
//                        компилятор в точке return подставляет возвращаемое значение в result, верифицирует Sorted(возвр. значение)
```

Аналогично для объявлений локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевые условия, формируя **множество предположений** текущей области видимости. Эти предположения
участвуют в верификации как фоновые знания для вычисления Bool во время компиляции.

```yaoxiang
if y > 0 {
    // компилятор автоматически получает предположение в этой ветви: { y > 0 }
    let result = divide(x, y)
    // условие верификации: (y > 0) ⇒ (y > 0)
    // конвейер доказательств устанавливает истинность импликации → Proved
} else {
// в этой ветви предположение: { !(y > 0) }
// при попытке вызвать divide(x, y), условие верификации: !(y > 0) ⇒ y > 0
    // конвейер доказательств устанавливает ложность импликации → Disproved
}
```

Это не специальный паттерн, вшитый в компилятор, — это естественное поведение конвейера
доказательств времени компиляции. При каждой проверке типа в точке вызова в конвейер отправляется:

```
{фоновые предположения} ⇒ {цель верификации}
```

Конвейер доказательств проверяет истинность импликации. Proved → проходит, Disproved → ошибка
компиляции + контрпример, Unproven → ошибка компиляции + неразрешённое утверждение. Фоновые
предположения берутся из путевых условий текущей программной точки.

#### 3.3 Стек предположений

При анализе потока управления компилятор поддерживает для каждого базового блока множество
предположений:

- **if-guard**: `if y > 0` → в true-ветвь помещается `y > 0`, в false-ветвь помещается `!(y > 0)`
  (при наличии else)
- **match-паттерн**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **логические связки**: `if x > 0 and y < 10` → в ветвь помещаются `x > 0` и `y < 10`
- **предусловие функции**: при вызове `divide(a, b)` свидетельство того, что `b` удовлетворяет
  `Positive`, берётся либо из текущих предположений, либо из аннотации уточняющего типа самого
  аргумента (если `b` уже аннотирован как `Positive`, его тип несёт `b > 0`)
- **присваивание**: при `let z = y` уже имеющееся уточняющее условие `y` передаётся в `z`

Все предположения поступают в конвейер доказательств времени компиляции. При входе в ускоренный
SMT-путь они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Отсутствие статического свидетельства — ошибка компиляции

Если программист просто пишет:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей программной точке нет предположения `y > 0`, сам аргумент `y` также не имеет аннотации
типа `Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация не выполняется) → ошибка компиляции:

> Невозможно доказать, что параметр `b` в вызове `divide` удовлетворяет `Positive`. `y` приходит из
> входных данных функции, доказанных границ не имеет. Рассмотрите защиту вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не допускает прямого попадания значений времени выполнения в параметры уточняющих типов без
предоставления статического свидетельства. Это не ограничение — это ядро философии полной
безопасности. Любой код, который компилятор не может статически верифицировать, не проходит
компиляцию.

#### 3.5 Связь с унифицированным конвейером

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
доказательств времени компиляции на анализ потока управления:

| Фаза                                 | Ответственность                                                                                                                                                                        |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий                 | Фаза анализа потока управления компилятора; аннотирование каждого базового блока множеством предположений                                                                              |
| Генерация условий верификации        | При столкновении с ограничением типа, требующим верификации, объединение путевых условий + информация о типе аргумента                                                                 |
| Вычисление в конвейере доказательств | Ядро компилятора → ускорение SMT → результат Proved / Disproved / Unproven                                                                                                             |
| Результат                            | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + неразрешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновые знания
конвейера доказательств, разделяющие с равенством типов и ограничениями заимствования один конвейер
и одну систему бюджетов.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции разделяют единый конвейер. Основная операция конвейера — **проверка
типов** — проверка, равен ли тип терма доказательства доказываемому утверждению. Всё — это проверка
типов.

```
Во время компиляции встречается Bool-выражение, требующее вычисления (то есть: требуется построить терм доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → прямое решение компилятора (структурная эквивалентность)
        │
        ├── Условие конфликта токенов (!conflicting(tokens))
        │   → потокочувствительный анализ живости (отслеживание Dup/Linear)
        │
        ├── Редукция зависимых типов (n + m упрощение)
        │   → система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикат времени компиляции (x > 0, forall...)
        │   → ядро компилятора + ускоряющий модуль SMT
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → ядро компилятора + ускоряющий модуль SMT
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → компиляция проходит
             │ Disproved│  → ошибка компиляции + контрпример
             │ Unproven │  → ошибка компиляции + неразрешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код на YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ──→ Proved ──→ компиляция проходит
                  │
                  ▼
            Верификация не прошла → ошибка компиляции: «доказательство неверно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — это неизбежное следствие проблемы
остановки и естественное разбиение теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → остановка, терм доказательства построен, проверка типов прошла. Компиляция
  продолжается.
- **Disproved(M)** → остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → в пределах заданного ресурсного лимита терм доказательства не построен. Ошибка
  компиляции + неразрешённое утверждение + отчёт о потреблении бюджета.

**Unproven ≠ False.** «Компилятор не смог доказать» не эквивалентно ложности утверждения — это лишь
превышение возможностей текущего автоматического доказательства. Это честность, а не дефект.

Жёсткое ограничение бюджета — инженерное решение проблемы остановки. Без ручек — давать ручку значит
спрашивать пользователя «你觉得你的程序会不会停机» («как вы думаете, ваша программа остановится?»),
а пользователь не знает, и компилятор тоже не знает.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция на YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверщик типов
верифицирует эту функцию — тем же механизмом, которым он верифицирует `add(a, b): Int`.

```
утверждение = тип
доказательство = программа (значение этого типа)
верификация = проверка типов (единственный корень доверия)
```

SMT-решатель — не отдельный корень доверия — это **ускоряющий модуль проверщика типов**. SMT
помогает искать доказательство, но верифицирует доказательство всегда проверщик типов. Когда SMT
возвращает `unsat`, компилятор реконструирует его результат в терм доказательства, верифицируемый
проверщиком типов. Если реконструкция не удалась (шаги вывода SMT выходят за правила вывода ядра
компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: уточняющее свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип — вышеуказанное утверждение
# Проверщик типов верифицирует эту функцию — совершенно так же, как верифицирует add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # компилятор здесь верифицирует: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Не нужен ИИ, не нужен экспорт в Coq, не нужны новые концепции. **Свойство, которое компилятор не
может доказать автоматически → программист пишет доказательство на YaoXiang → проверщик типов
верифицирует.** Весь процесс — плавный градиент — компилятор берёт на себя простые доказательства,
оставляя мозгу сложные.

#### 4.3 Слоистые зависимости внутри конвейера

Вышеописанные вычислители используют один интерфейс, но имеют порядок вычисления. Равенство типов —
предпосылка для всего последующего анализа; проверки владения/токенов зависят от информации о типах;
верификация уточняющих предикатов зависит от результатов первых двух слоёв. Компилятор вычисляет
послойно; выражения, не прошедшие нижний слой, не попадают в верхний — это исключает трату бюджета
решения на типово-некорректных программах.

```
Порядок вычисления (один конвейер, слоистая диспетчеризация)
├── Слой 0: Равенство типов (T1 == T2)
│   └── структурная унификация → при неудаче дальнейшее бессмысленно, сразу Disproved
├── Слой 1: Конфликты владения/токенов
│   └── потокочувствительный анализ живости → при неудаче безопасность памяти не выполняется, сразу Disproved
└── Слой 2: Уточняющие предикаты / импликации Хоара
    └── ядро компилятора → ускорение SMT → результат Proved / Disproved / Unproven
```

Каждый слой возвращает `Proved/Disproved/Unproven`, разделяя единый интерфейс и единую систему
бюджетов.

### 5. Унификация трёх слоёв функций

| Слой                        | Момент выполнения | Вход         | Выход    | Пример                                         |
| --------------------------- | ----------------- | ------------ | -------- | ---------------------------------------------- |
| Функция уровня значений     | Время выполнения  | значение     | значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типа            | Время компиляции  | тип/значение | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат времени компиляции | Время компиляции  | значение     | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют единый синтаксис `name: type = value`. Предикаты времени компиляции и конструкторы
типов идут по единому конвейеру доказательств времени компиляции — `{}` — это пространство
доказательств.

### 6. Циклы: генерация условий верификации Флойда–Хоара

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточняющих
типов на переменных определяют утверждения в стиле Флойда–Хоара — компилятор генерирует условия
верификации из аннотаций типа, а конвейер доказательств проверяет, сохраняет ли каждое присваивание
тип.

Ключевой механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует для тела цикла одно условие верификации — когда
конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i; при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # верификация: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # компилятор генерирует для тела цикла одно VC. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не изменился)
        #   подставляя s_new = s_old + arr[i]:
        #     требуется s_old + arr[i] == sum(arr[0..i+1])
        #     из индуктивного предположения s_old == sum(arr[0..i]), прибавляя arr[i] к обеим частям:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменяется → в графе зависимостей аннотация типа s ссылается на i → срабатывает реверификация
        #   новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   то есть s == sum(arr[0..i_new]), гарантировано предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # в этот момент s: SumUpTo(arr, arr.len), то есть s == sum(arr[0..arr.len])
}
```

Циклический инвариант — это аннотация типа на переменной — программист пишет тип, компилятор
проверяет индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант и не нужно «автоматически
проводить индукцию» — он разбивает индуктивное доказательство на локальные условия верификации для
каждого присваивания и раздаёт их конвейеру доказательств.

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеописанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i` — когда `i` изменяется, ограничение типа `s` также изменяется. Это требует от
компилятора поддерживать **граф типовых зависимостей между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# ключ — зависимая переменная, значение — множество переменных, чей тип на неё ссылается
# пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: проверщик типов при обработке `mut v: Pred(... x ...) = init` разбирает свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылка на другую изменяемую переменную
`x` текущей области видимости, в графе зависимостей записывается `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает присваивание, компилятор:

1. Ищет в графе зависимостей все переменные, зависящие от `x` — `{v₁, v₂, ...}`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательств

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественным образом
форсирует правильный порядок присваивания. Для `SumUpTo(arr, i)`:

```yaoxiang
# правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменяется → реверификация s на SumUpTo(arr, i_new) → True

# неправильный порядок — компилятор отвергает
i += 1        # i изменяется → реверификация s на SumUpTo(arr, i_new)
              # s ещё не обновлено, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Составные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` зависит одновременно от `x` и `y` — изменение любой из них инициирует
реверификацию.

**Связь с конвейером доказательств**: отслеживание зависимостей — триггер генерации VC, а не
самостоятельный механизм верификации. Он отвечает на вопрос «когда нужно сгенерировать VC» —
конвейер доказательств отвечает на вопрос «выполняется ли VC».

### 7. Проверка завершаемости

Полностью автоматическая во время компиляции. Циклы, которые компилятор может доказать, проходят;
циклы, которые компилятор не может доказать, сразу вызывают ошибку компиляции — программист обязан
сделать цикл таким, чтобы компилятор мог его автоматически проанализировать. Никаких лазеек для
полуавтоматических аннотаций.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершаемости, из двух
источников:

1. **Аннотации типов переменных**: ограничения границ в уточняющих типах (например, `UpTo(n)` даёт
   верхнюю границу `n` и нижнюю `0`)
2. **Операции тела цикла**: операции, применяемые к переменным на каждой итерации

Компилятор пробует четыре стратегии синтеза меры в порядке приоритета и останавливается на первой
подходящей.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда у переменной есть аннотация линейной границы, компилятор перебирает кандидаты линейных мер и
верифицирует их через SMT.

```
Вход:
  переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с границами)
  условие цикла cond
  множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типа: [low_i, high_i]
  2. Перебрать кандидаты мер: v_i, u_i - v_i, v_i - v_j и другие линейные комбинации
  3. Для каждого кандидата m:
     - SMT верифицирует m ≥ 0 (из границ типа)
     - для каждого пути исполнения в теле цикла SMT верифицирует m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершаемость доказана
```

Покрытие: циклы, в которых любая переменная получает линейное выражение (`v = a·v + b`) и имеет
аннотацию ограниченного типа. Включает `i += const`, `i -= const`, а также сокращение интервала в
стиле бинарного поиска:

```yaoxiang
# Бинарный поиск: low = mid + 1 или high = mid
# мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: подсчёт нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущее состояние: экспериментальная стратегия, при реализации фазы 3 решение о включении
> принимается по фактической реализуемости.** Эта стратегия работает для операций соседнего обмена
> (сортировка пузырьком, сортировка вставками), но не может автоматически доказать несмежные
> операции (partition быстрой сортировки, sift-down пирамидальной сортировки). Границы покрытия см.
> в таблице ниже. Если на фазе 3 верификация покажет нереализуемость, стратегия будет удалена или
> переведена в будущую работу.

Центральная идея: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое отсортированность» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  операции тела цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операции на меру:
     - обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - затрагивает только пары с индексами j-1, j, j+1
     - если arr[j] > arr[j+1] (нарушение предиката), после обмена пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимум соседних инверсий), нижняя граница: 0
  → завершаемость доказана
```

**Текущее покрытие**:

| Алгоритм                 | Паттерн операции     | Стратегия 2 доказуема? | Причина                                              |
| ------------------------ | -------------------- | :--------------------: | ---------------------------------------------------- |
| Сортировка пузырьком     | Соседний обмен       |           ✅           | violation_count строго убывает при каждом обмене     |
| Сортировка вставками     | Соседнее перемещение |           ✅           | Каждое перемещение устраняет одну нарушающую пару    |
| Сортировка выбором       | Несмежный обмен      |           ❌           | Одиночный обмен может увеличить violation_count      |
| Быстрая сортировка       | partition            |           ❌           | Несмежный обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌           | Древовидная операция, violation_count немонотонен    |

**Дополняющие стратегии**: для быстрой сортировки сокращение интервала `low < high` покрывается
стратегией 1 (линейная ранговая функция) — внешняя partition-рекурсия, каждый раз интервал делится
пополам. Стратегии 1 и 2 дополняют друг друга; завершаемость большинства практических алгоритмов
доказуема одной из них. Однако обобщение стратегии 2 (несмежные операции, древовидные операции)
остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: паттерн ограниченного инкремента/декремента

`v += const` (const > 0), у переменной есть аннотация верхней границы → мера `upper_bound - v`
убывает на `const` каждую итерацию, нижняя граница 0. Это вырожденный случай стратегии 1; компилятор
обрабатывает его первым.

#### 6.5 Стратегия 4: шаблон мультипликативной меры

`v *= const` (const > 1), у переменной есть аннотация нижней и верхней границы. Компилятор имеет
встроенный логарифмический шаблон меры `ceil(log_const(upper/v))`, мера убывает на 1 при каждом
умножении на const.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # компилятор автоматически выводит: мера ceil(log₂(n/i)), убывает на 1 при каждом умножении на 2
    i *= 2
}
```

#### 6.6 Разделение завершаемости и корректности

Доказательство завершаемости и доказательство корректности независимы:

- **Завершаемость**: четыре вышеописанные стратегии автоматически доказывают, что цикл завершается
  за конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  времени компиляции через проверку условий верификации

Оба проходят → компиляция проходит. Завершаемость доказана, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершаемость не доказуема → ошибка компиляции с
указанием переменных или операций, которые не удалось проанализировать. Оба не прошли → ошибка
компиляции с раздельным отчётом по обеим причинам.

#### 6.7 Проверка завершаемости рекурсивных функций

Для рекурсивных функций, которые требуется вычислить во время компиляции, компилятор проверяет
убывание аргументов:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # компилятор анализирует: n-1 < n → убывание → завершаемость
}

# Использование во время компиляции — компилятор гарантирует завершаемость factorial во время компиляции
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, вычисляется во время компиляции
```

| Сценарий                                                              | Поведение                           |
| --------------------------------------------------------------------- | ----------------------------------- |
| Компилятор может проанализировать убывание рекурсии (например, `n-1`) | Вычисление во время компиляции      |
| Не убывает / убывание неразрешимо                                     | Ошибка компиляции                   |
| Вызов во время выполнения (не в позиции типа)                         | Проверка завершаемости не требуется |

#### 6.8 Жёсткая граница

`i = f(i)`, где `f` необратима, незамкнута и не сохраняет никакой монотонности, — математически
невозможно автоматически доказать завершаемость. Ошибка компиляции:

> Этот цикл не может быть автоматически доказан как завершающийся. Переменная цикла зависит от
> неанализируемой функции `f`. Пожалуйста, используйте итеративный паттерн, доступный для анализа
> компилятором.

Это не поражение компилятора. Любой код, безопасность которого нельзя статически доказать, не
проходит компиляцию.

### 8. SMT-решатель: ускоряющий модуль проверщика типов

SMT-решатель в традиционных языках — внешний инструмент (как F\* вызывает Z3, Dafny вызывает Z3). В
YaoXiang это **ускоряющий модуль проверщика типов** — вызывается только тогда, когда ядро
компилятора само не может непосредственно решить задачу. SMT помогает искать доказательство, но
доказательство верифицирует проверщик типов.

**Модель доверия**: проверщик типов — единственный корень доверия. SMT-решатель — ускоряющий модуль:
он помогает искать доказательство, но SMT — не отдельный корень доверия. Компилятор доверяет
результату `unsat` от Z3 (как и в подходе F\*/Dafny — вероятность ошибки Z3 ниже вероятности бага в
самом компиляторе, это прагматичный инженерный выбор). Реальная ненадёжность контролируется на
уровне трансляции в SMT — если в трансляторе есть баг, он проявится в других тестах.

**Интерфейс**: внутренняя трансляция компилятора — в стандартный формат SMT-LIB 2.6, без привязки к
API конкретного решателя. SMT-LIB — стандарт ISO, нативно поддерживается Z3, CVC5, MathSAT, Yices.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, самая обширная документация и валидация сообществом).
CVC5 как совместимый с SMT-LIB резерв — пользователь может переключаться флагом компилятора.

Без «универсального слоя абстракции решателя» — SMT-LIB и есть слой абстракции. Если в будущем CVC5
добьётся прорыва в определённой теории, переключение — это смена бинарника, без изменения кода
компилятора.

```
Bool-выражение времени компиляции
        │
        ├── Ядро компилятора может решить непосредственно (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → напрямую возвращает Proved / Disproved
        │
        └── Ядро компилятора не может решить непосредственно (кванторы, символьные переменные)
            → предварительная редукция зависимых типов (factorial(5) → 120)
            → трансляция в формат SMT-LIB
            → отправка в Z3/CVC5 (с ограничением бюджета)
            → возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткое ограничение, как глубина стека**:

| Измерение бюджета                 | Значение по умолчанию | Пояснение                                                                                                                                                        |
| --------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10 000                | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывают 99% практических предикатов.                                                |
| Время                             | 100 мс                | Один предикат свыше 100 мс = пользователь пишет программу времени компиляции, а не аннотацию типа. 100 мс × 50 предикатов = 5 секунд верхней границы компиляции. |
| Глубина инстанцирования кванторов | 3                     | Три уровня вложенных кванторов покрывают практические паттерны. Свыше трёх — скорее всего, логическая головоломка.                                               |

При превышении бюджета возвращается Unproven, ошибка компиляции + позиция предиката + расход. Без
понижения, без проверок во время выполнения, без тихого прохода.

**Почему это практически работает**: в инженерной практике 95% реальных предикатов — линейная
арифметика — `x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в разрешимом фрагменте, SMT-решатель
для таких задач возвращается за миллисекунды. При встрече с редкими сложными предикатами,
превышающими бюджет, программист пишет функцию-доказательство.

Зависимые типы перед вызовом SMT проходят предварительную редукцию: `factorial(5)` напрямую
вычисляется во время компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти
детерминированные вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Мысленная модель: **компилятор может доказать —
проходит, не может — ошибка; если компилятор не умеет, можно написать функцию и показать ему
доказательство.**

### 9. Композиция предикатов времени компиляции

Предикат времени компиляции — это функция, возвращающая Type; композиция естественно реализуется
через композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ компилятор верифицирует Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ компилятор верифицирует Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ компилятор верифицирует InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ компилятор верифицирует InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации `dispatch`: унификация времени компиляции и времени выполнения

`assert` и `Assert` — это две стороны одного уточняющего типового примитива. Конвейер
диспетчеризации `dispatch` автоматически решает — идти по пути доказательства времени компиляции или
проверки времени выполнения — по тому, **достижимы ли свободные переменные предиката во время
компиляции**:

| Критерий                                                                                                  | Режим           | Поведение                                                                                                         |
| --------------------------------------------------------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры-дженерики, константы времени компиляции) | **CompileTime** | В конвейер доказательств: Proved → стирается, Disproved → ошибка компиляции, Unknown → требуется доказательство   |
| Есть свободные переменные из времени выполнения (параметры функций, внешний ввод, mut-переменные)         | **Runtime**     | Вставка проверки времени выполнения и инъекция уточняющего факта в потокочувствительное множество предположений Γ |

**Ключевое**: «Не удалось решить» ≠ «Ложь». В режиме CompileTime Unknown требует доказательства (без
тихого понижения); в режиме Runtime у утверждения во время компиляции вообще нет истинности —
никакой prover не напишет тавтологически истинное доказательство для «пользователь мог ввести
отрицательное число», проверка времени выполнения — единственный sound-выбор. Это не слабость
prover'а, это теоретическая неизбежность.

### 12. Потокочувствительное множество предположений Γ: распространение сильнейшего постусловия

Компилятор поддерживает потокочувствительное (flow-sensitive) множество предположений Γ,
отслеживающее утверждения, истинные в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← распространение SP
```

**Kill set для mut-переменных**: после повторного присваивания `mut`-переменной все предположения,
относящиеся к этой переменной, удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые предположения
недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение предположений ветвей.
Из ветви выносится только то утверждение, которое истинно на всех путях.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточняющие типы полностью стираются во время выполнения» относится к **proof
witness (токену доказательства)** — терм доказательства, верифицированный во время компиляции, не
порождает кода времени выполнения. Но проверка времени выполнения (runtime check), вставленная
диспетчеризацией в режиме Runtime, сохраняется — это Bool-проверка на уровне значений, а не witness
на уровне типов.

Резюме: witness стирается, check сохраняется. Эти две вещи не противоречат друг другу, исходное
утверждение RFC-027 остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| До (RFC-022)                          | После (данный RFC)                                                                                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Предикат времени компиляции как тип параметра `(b: Positive(b))`                                            |
| `//! ensures: ExistsMax(result, arr)` | Возвращаемый тип использует формальный параметр возвращаемого значения `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Аннотации уточняющих типов на переменных — инварианты Флойда–Хоара                                          |
| `//! decreases: n`                    | Полностью автоматический вывод меры компилятором                                                            |
| Спецификация — это комментарий        | Спецификация — это система типов                                                                            |

### Синтаксис

**У предикатов времени компиляции нет новых ключевых слов.** `{}` — это пространство доказательств,
полностью совместимое с существующим синтаксисом определения типов. Предикат времени компиляции —
это функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. Использование — это
вызов функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Предикат времени компиляции = функция, возвращающая Type; внутри {} — утверждения, верифицируемые компилятором
# Используется существующий синтаксис функций/типов, новых BNF-правил не требуется
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Новое синтаксическое понятие: формальный параметр возвращаемого значения** — в `-> (name: Type)`
имя `name` — это формальный параметр возвращаемого значения.

Формальный параметр возвращаемого значения — это **единственное синтаксическое понятие**, вводимое
YaoXiang в существующий синтаксис функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается предикат постусловия (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не попадает в область видимости тела функции и не виден вызывающему
- Формальный параметр возвращаемого значения **необязателен** — при отсутствии постусловия сигнатура
  полностью совпадает с обычной функцией (`-> Int`), без какой-либо дополнительной нагрузки

Причина его введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть».
Без формального параметра возвращаемого значения компилятор мог бы ссылаться на возвращаемое
значение в предикате только через специальные правила (например, неявная переменная `$result` или
`__retval__`). Формальный параметр возвращаемого значения делает эту ссылку явной — это просто
формальный параметр, только значение предоставляется `return`, а не вызывающим.

**Функция-доказательство** — не новое понятие — это просто функция на YaoXiang, чей возвращаемый тип
— доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство; проверщик типов верифицирует её точно так же, как верифицирует возвращаемый
тип любой функции. Не нужны новый синтаксис, новые ключевые слова, новые правила.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функции, принимающие
  значения и возвращающие Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с дженериками**: предикаты времени компиляции могут иметь параметры-дженерики,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения, только чтение, без записи
- **Вывод типов**: аргументы предикатов времени компиляции участвуют в HM-выводе типов

### Представление во время выполнения

Предикат времени компиляции во время выполнения **обрабатывается по результату диспетчеризации
dispatch**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): после прохождения
  доказательства токен свидетельства (witness) полностью стирается.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представляется как `Int`. Уточняющее условие `{ 5 > 0 }` уже верифицировано, стирается.
- **Режим Runtime** (есть свободные переменные времени выполнения): сохраняется проверка времени
  выполнения — Bool-проверка на уровне значений, инъекция в потокочувствительное множество
  предположений Γ. Подробности см. в §11 «Конвейер диспетчеризации dispatch» и §13 «Уточнение модели
  стирания».

Использование предиката времени компиляции в позиции типа (например, `f(x: Positive(x))`) не
порождает обёрточного типа и не выделяет дополнительной памяти. Но когда `x` приходит из ввода
времени выполнения, **выполняется** вставка Bool-проверки времени выполнения.

**Ограничения взаимодействия с `ref`**: предикат времени компиляции может ссылаться только на
неизменяемые заимствования или на значения с переданным владением. Предикат времени компиляции,
ссылающийся на изменяемое заимствование, не может быть гарантированно верифицирован компилятором на
сохранение результата во время выполнения — такое использование сразу вызывает ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, дополнительных
   правил разбора не требуется
2. **Конвейер доказательств времени компиляции**: унифицированный интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **Ускоряющий модуль SMT**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, резерв CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение кванторов всеобщности. Это единственный корень доверия; SMT и доказательства
   программиста верифицируются через него
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства циклических
   инвариантов
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёт о неразрешённых утверждениях +
   привязка к позиции в исходном коде

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, остаётся без изменений
- ✅ Предикаты времени компиляции в режиме CompileTime дают нулевые накладные расходы времени
  выполнения; в режиме Runtime сохраняются лишь необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован,
  миграционной нагрузки нет

## Компромиссы

### Преимущества

- **Полная реализация соответствия Карри–Ховарда**: тип есть утверждение, программа есть
  доказательство, `name: Proposition = Proof`
- **Унификация**: предикаты времени компиляции и обычные функции используют полностью идентичный
  синтаксис, без концептуального расщепления
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, мысленная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции и постепенно
  расширять покрытие
- **Минимальные накладные расходы времени выполнения**: режим CompileTime даёт нулевые накладные
  расходы; режим Runtime сохраняет лишь необходимые Bool-проверки

### Недостатки

- **Время компиляции**: SMT-решение увеличивает время компиляции, но жёсткое ограничение бюджета
  гарантирует контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами линейной арифметики
  первого порядка могут потребовать от программиста написания функций-доказательств. Это не дефект
  языка — это неизбежное следствие проблемы остановки. Компилятор честно сообщает Unproven, а не
  ложно объявляет True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и функций-доказательств
  требует понимания базовой интуиции соответствия Карри–Ховарда
- **Сложность реализации**: унификация конвейера доказательств времени компиляции требует
  тщательного проектирования

### Снижение рисков

- Жёсткое ограничение бюджета SMT (шаги 10 000 / время 100 мс / глубина инстанцирования 3), при
  превышении возвращается Unproven
- Предварительная редукция зависимых типов: детерминированные вычисления значений поглощаются
  первыми, SMT кусает только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверщик типов
  верифицирует — как и любой возвращаемый тип функции
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + показ контрпримеров + отчёт о потреблении бюджета + неразрешённое
  утверждение + предложение (если компилятор может дать)

## Альтернативы

| Решение                                                                    | Почему не выбрано                                                                                                                                                              |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RFC-022: спецификации как комментарии `//!`                                | Расщепление спецификаций и типов, нарушение соответствия Карри–Ховарда                                                                                                         |
| Отдельные файлы спецификаций (как CVL)                                     | Разделение спецификаций и кода, увеличение стоимости сопровождения                                                                                                             |
| Только утверждения времени выполнения                                      | Невозможно статически гарантировать корректность                                                                                                                               |
| Внешний ассистент доказательства (как Coq)                                 | Отрыв от компилятора, нужен отдельный язык доказательств и корень доверия. Выбор YaoXiang: доказательство — это код на YaoXiang, проверщик типов — единственный корень доверия |
| **Данное решение: предикаты времени компиляции как полноправные граждане** | ✅                                                                                                                                                                             |

## Стратегия реализации

### Разбивка на фазы

| Фаза       | Содержание                                                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **Фаза 3** | Генерация VC для циклических инвариантов + проверка завершаемости (линейная ранговая функция + подсчёт нарушений предиката + паттерн ограниченности + контроль комбинаторного взрыва) |

## Открытые вопросы

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, самая обширная валидация). CVC5 как
      совместимый с SMT-LIB резерв, переключение флагом компилятора. Внутренняя цель трансляции
      компилятора — стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, без
      собственного универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решения**: шаги 10 000 / время 100 мс / глубина инстанцирования
      кванторов 3. Фиксированы внутри компилятора, без ручек. Если в реальной практике встретятся
      подтверждённые случаи нехватки (не «пользователь написал неправильно»), значения будут
      скорректированы.
- [x] **Диапазон поддержки кванторов**: язык не ограничивает порядок кванторов. Предикат времени
      компиляции принимает параметр Type — Type включает функциональные типы — поэтому кванторы
      высокого порядка — естественное следствие системы типов, специального синтаксиса не требуется.
      SMT-решатель может автоматически разрешать кванторы первого порядка (forall/exists, включая
      чередующееся вложение, ограничено бюджетом глубины 3). Кванторы высокого порядка: SMT
      возвращает Unproven, компилятор предлагает «этот предикат выходит за пределы автоматического
      доказательства, предоставьте функцию-доказательство». Программист пишет функцию на YaoXiang,
      чей возвращаемый тип равен этому утверждению — проверщик типов верифицирует эту функцию.
      Никакого внешнего экспорта, никакого ИИ, никакого интерактивного режима доказательства. Всё —
      код на YaoXiang, всё проверяется проверщиком типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена SMT-переменных (с префиксом модуля для предотвращения коллизий). При возврате модели Z3
      выполняется обратный поиск по именам. Формат вывода: имя переменной = конкретное значение +
      позиция в исходном коде + позиция определения предиката. Без сложного слоя отображения.
- [x] ~~**Взаимодействие предикатов времени компиляции с умным указателем `ref`?**~~ → Решено:
      предикаты времени компиляции допускают только неизменяемые заимствования или значения с
      переданным владением. Значения по изменяемому заимствованию не могут появляться в предикатах
      времени компиляции.
- [x] **Расширение меры подсчёта нарушений `forall`-предиката на несмежные операции?** → Не
      расширяется. Текущее покрытие (соседний обмен, соседнее перемещение) дополняется стратегией 1
      (линейная ранговая функция) — для быстрой сортировки сокращение внешнего интервала покрывается
      стратегией 1, пирамидальная сортировка покрывается стратегией 1 (паттерн индексов массива).
      Циклы, завершаемость которых не доказуема ни одной из стратегий, компилятор сразу отвергает —
      это философия полной безопасности, а не дефект. Если в будущем появится реальный сценарий (не
      академическая конструкция), в котором ни одна из четырёх стратегий не срабатывает, вопрос
      будет пересмотрен.
- [x] **Комбинаторный взрыв перебора линейных ранговых функций**: верхний предел числа переменных в
      переборе — 3 переменные с границами. При ≤3 перебираются все линейные комбинации и
      верифицируются через SMT по одной. При >3 пробуются только однопеременные меры (`v_i`,
      `u_i - v_i`), при неудаче сразу ошибка компиляции — с сообщением программисту «в цикле >3
      переменных с границами, компилятор не может автоматически синтезировать многопеременную меру».
      Это не инженерный компромисс — это принуждение программиста писать более простые циклы.
