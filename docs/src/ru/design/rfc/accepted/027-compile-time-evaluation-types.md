# RFC-027: Предикаты времени компиляции и унифицированная статическая верификация

> **Ссылки**:
>
> - [RFC-009: Модель владения](../accepted/009-ownership-model.md)
> - [RFC-010: Унифицированный синтаксис типов — модель name: type = value](../accepted/010-unified-type-syntax.md)
> - [RFC-011: Проект системы дженериков](../accepted/011-generic-type-system.md)
> - [RFC-024: Модель конкурентности на основе блоков spawn](../accepted/024-concurrency-model.md)
>
> **Заменяет**:
> [RFC-022: Поддержка статической верификации логикой Хоара (спецификационные комментарии и спецификационные типы)](../deprecated/022-hoare-logic-static-verification.md)
> — устарел

## Резюме

Настоящий документ предлагает ввести в YaoXiang **предикаты времени компиляции** как полноправных
граждан первого класса, объединив всю статическую верификацию времени компиляции в единый **конвейер
доказательств**. Предикат времени компиляции — это не навесная спецификация-комментарий — это
функция. Функция, возвращающая Type, может использоваться в позиции типа, и компилятор вызывает её
во время компиляции и проверяет возвращаемое значение. Тип есть утверждение, вычисление времени
компиляции есть доказательство.

**Ключевой тезис**: единственная работа проверки типов во время компиляции — построение и валидация
доказательств. Равенство типов, конфликты токенов, редукция зависимых типов, вычисление предикатов
времени компиляции, импликации логики Хоара — всё это различные проверки типов в одном конвейере
доказательств времени компиляции. SMT-решатель — это ускоряющий модуль проверщика типов, а не
отдельный доверенный корень. Когда компилятор возвращает Unproven, программист пишет функцию
YaoXiang как доказательство — проверщик типов верифицирует её точно так же, как он верифицирует
возвращаемый тип любой функции. Всё — код YaoXiang, всё проверяется проверщиком типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это комментарий, отдельный от типа
    //! ensures: ExistsMax(result, arr[0..n])   ← это комментарий, отдельный от типа
}
```

Это совершает фундаментальную ошибку изоморфизма Карри-Ховарда: **разделяет спецификации и типы на
два слоя**. Комментарии — не типы. Комментарии не участвуют в проверке типов. Комментарии — это
мысленная модель «внешнего инструмента».

Белая книга говорит прямо:

> «Никаких комментариев `//!`. Никакого отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Комментарии `//!` из RFC-022 — это навесной синтаксис, отдельный от системы типов
- Спецификационные типы и обычные типы — две разные системы, что создаёт концептуальную избыточность
- Разделение «Debug Build верифицирует / Release Build игнорирует» разрушает единство
- SMT-решатель в традиционном восприятии позиционируется как внешний инструмент — YaoXiang
  встраивает его как ускоряющий модуль проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов идут каждая своим путём

### Правильная мысленная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — являются подзадачами этой функции. Они разделяют один
конвейер доказательств, отличаясь лишь сложностью терма доказательства и стратегией его построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство —
возвращаемый тип этой функции равен доказываемому утверждению. Проверщик типов верифицирует её. Это
та же самая операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип есть утверждение, верификация есть проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри — утверждения, и
компилятор гарантирует, что каждый элемент равен True — либо автоматическим доказательством, либо
предоставленной программистом функцией-доказательством.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  компилятор гарантирует, что x — Float, а y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  компилятор гарантирует, что data — Array(T)
```

**Дженерики — частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметры в сигнатуре  внутри {} только утверждения
#          компилятор проверяет x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметры в сигнатуре   компилятор проверяет type_of(T) == Type, type_of(data) == Array(T)
```

Один и тот же шаблон: `name: (params) -> Type = { утверждения }`. Компилятор не различает
«утверждения о типе» и «утверждения о значении» — все они являются целями вычисления в конвейере
доказательств.

**Инварианты цикла не нужно записывать отдельно. Аннотация типа на переменной — это инвариант
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # компилятор проверяет: s_new == sum(arr[0..i+1])
        i += 1       # i изменён → вызывает ревалидацию зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. После того как
конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически. Никаких
`: decreases`, никаких `: Invariant`, никаких индуктивных доказательств не требуется — компилятор
разбивает индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции на типах параметров и возврата

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции выступают
аннотациями типов параметров или возврата.

**Сторона параметра — это вызов функции.** Предикат времени компиляции — это функция, возвращающая
Type, и её использование на стороне параметра — это просто её вызов — как `factorial(5)`. На стороне
возвращаемого значения вводится новая концепция: формальный параметр возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive как аргумент
#                       компилятор в точке вызова извлекает значение аргумента, подставляет b, проверяет Positive(аргумент)
#                       напр.: divide(10, 2) → проверяет Positive(2) = { 2 > 0 } → True
#                       напр.: divide(10, 0) → проверяет Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возврата, значение предоставляется return
#                                            компилятор в точке return подставляет возвращаемое значение, проверяет постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **Сторона параметра**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся в
  `Positive` как аргумент. Синтаксис вызова функции, ноль неявности.
- **Сторона возврата**: `-> (result: IsMax(T, arr, result))` — `result` — формальный параметр
  возврата, значение предоставляется оператором `return`. `result` существует только в сигнатуре
  типа, на него ссылается только предикат, не входит в область видимости тела функции, не появляется
  у вызывающего.
- **Формальный параметр возврата опционален**: при отсутствии постусловия не пишется, сигнатура
  полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: параметры и формальный параметр возврата — одна и та же концепция —
  `имя_параметра: вызов_предиката(имя_параметра)`, различие лишь в том, предоставляется ли значение
  вызывающим или оператором `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно. Когда значение времени выполнения попадает в параметр уточнённого типа,
компилятор завершает верификацию через сбор путевых условий и SMT-импликацию — без явной передачи
доказательства программистом.

#### 3.1 Явный вызов функции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно — это просто вызов функции, ноль неявности.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предиката времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — вызов функции
// после нормализации: b: { b > 0 }
```

Компилятору не нужно неявно подставлять аргументы — `b: Positive(b)`, как и `f(5)`, — это просто
вызов функции. `b` связан как имя параметра, и его аннотация типа `Positive(b)` ссылается на сам `b`
— это стандартный шаблон зависимых типов, а не неявное правило раскрытия.

**Единство с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а лишь
общепринятое имя параметра («написать `p`, `this` или `x` — совершенно одинаково»). `b: Positive(b)`
использует тот же механизм — имя параметра может быть упомянуто в аннотации типа. `self` появляется
в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)` — обе аннотации типа ссылаются на
сам параметр. Различие лишь в сложности аннотации типа, механизм полностью идентичен — после
связывания имени тип может зависеть от этого имени.

Возвращаемый тип также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возврата, Sorted(result) — вызов функции
//                        компилятор в точке return подставляет возвращаемое значение в result, проверяет Sorted(значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связан с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связан с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевые условия, формируя **множество гипотез** текущей области видимости. Эти гипотезы выступают
фоновыми знаниями для вычисления Bool времени компиляции, участвуя в верификации.

```yaoxiang
if y > 0 {
    // компилятор автоматически получает в этой ветви гипотезу: { y > 0 }
    let result = divide(x, y)
    // условие верификации: (y > 0) ⇒ (y > 0)
    // конвейер доказательств устанавливает импликацию → Proved
} else {
// гипотеза в этой ветви: { !(y > 0) }
// при вызове divide(x, y) условие верификации: !(y > 0) ⇒ y > 0
    // конвейер доказательств устанавливает, что импликация не выполняется → Disproved
}
```

Это не зашитый в компилятор специальный шаблон — это естественное поведение конвейера доказательств
времени компиляции. Каждая точка проверки типов отправляет в конвейер:

```
{фоновые_гипотезы} ⇒ {цель_верификации}
```

Конвейер доказательств устанавливает истинность импликации. Proved → проходит, Disproved → ошибка
компиляции + контрпример, Unproven → ошибка компиляции + нерешённое утверждение. Фоновые гипотезы
берутся из путевых условий текущей программной точки.

#### 3.3 Стек гипотез

При анализе потока управления компилятор поддерживает для каждого базового блока множество гипотез:

- **if-guard**: `if y > 0` → в true-ветвь помещается `y > 0`, в false-ветвь помещается `!(y > 0)`
  (при наличии else)
- **match-шаблон**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **логическая связка**: `if x > 0 and y < 10` → в ветвь помещаются `x > 0` и `y < 10`
- **предусловие функции**: при вызове `divide(a, b)` для `b` требуется свидетельство `Positive` либо
  из текущих гипотез, либо из аннотации уточнённого типа самого аргумента (если `b` аннотирован как
  `Positive`, его тип несёт `b > 0`)
- **присваивание**: при `let z = y` уже имеющееся у `y` уточнённое условие переносится на `z`

Все гипотезы поступают в конвейер доказательств времени компиляции. При переходе на путь
SMT-ускорения они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Нет статического свидетельства — ошибка компиляции

Если программист пишет напрямую:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей программной точке нет гипотезы `y > 0`, и сам аргумент `y` не имеет аннотации типа
`Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация не выполняется) → ошибка компиляции:

> Не удаётся доказать, что параметр `b` в вызове `divide` удовлетворяет `Positive`. `y` поступает из
> ввода функции, у него нет доказанной границы. Рассмотрите защиту вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не принимает прямое попадание значений времени выполнения в параметры уточнённого типа без
предоставления статического свидетельства. Это не ограничение — это ядро философии жёсткой
безопасности. Любой код, который компилятор не может статически доказать, не должен проходить
компиляцию.

#### 3.5 Связь с унифицированным конвейером

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
доказательств времени компиляции на анализ потока управления:

| Этап                          | Ответственность                                                                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Сбор путевых условий          | Этап анализа потока управления компилятора, аннотирующий каждый базовый блок множеством гипотез                                                                          |
| Генерация условий верификации | При встрече требующей верификации типовой аннотации объединяет путевые условия + информацию о типе аргумента                                                             |
| Вычисление в конвейере        | Ядро компилятора → SMT-ускорение → выдача Proved / Disproved / Unproven                                                                                                  |
| Результат                     | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка + нерешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновые знания
конвейера доказательств, разделяющие с равенством типов, ограничениями заимствования и проч. один
конвейер и единую систему бюджетов.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции разделяют один конвейер. Основная операция конвейера — **проверка
типов** — проверка, равен ли тип терма доказательства доказываемому утверждению. Всё есть проверка
типов.

```
Во время компиляции встречается выражение Bool, требующее вычисления (т.е. требующее построения терма доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → компилятор проверяет напрямую (структурная эквивалентность)
        │
        ├── Условия конфликта токенов (!conflicting(tokens))
        │   → потокочувствительный анализ живучести (отслеживание атрибутов Dup/Linear)
        │
        ├── Редукция зависимых типов (редукция n + m)
        │   → система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикат времени компиляции (x > 0, forall...)
        │   → ядро компилятора + SMT-модуль ускорения
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → ядро компилятора + SMT-модуль ускорения
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → компиляция проходит
             │ Disproved│  → ошибка компиляции + контрпример
             │ Unproven │  → ошибка компиляции + нерешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ──→ Proved ──→ компиляция проходит
                  │
                  ▼
            Верификация не прошла → ошибка компиляции: «доказательство неверно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — неизбежное следствие проблемы остановки и
естественное расчленение теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → остановка, терм доказательства построен, проверка типов пройдена. Компиляция
  продолжается.
- **Disproved(M)** → остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → в пределах заданного ресурсного лимита терм доказательства не построен. Ошибка
  компиляции + нерешённое утверждение + отчёт о потреблении бюджета.

**Unproven ≠ False.** Утверждение компилятора «я не могу доказать» не эквивалентно ложности
утверждения — оно лишь выходит за пределы текущих возможностей автоматического доказательства. Это
честность, а не дефект.

Жёсткий лимит бюджета — инженерное решение проблемы остановки. Никаких ручек — дать ручку означало
бы спросить пользователя «как вы думаете, остановится ли ваша программа», пользователь не знает,
компилятор тоже не знает.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверщик типов
верифицирует эту функцию — тем же механизмом, которым он верифицирует `add(a, b): Int`.

```
утверждение = тип
доказательство = программа (значение этого типа)
верификация  = проверка типов (единственный доверенный корень)
```

SMT-решатель — не отдельный доверенный корень — это **ускоряющий модуль проверщика типов**. SMT
помогает искать доказательство, но проверяет доказательство всегда проверщик типов. Когда SMT
возвращает `unsat`, компилятор реконструирует его результат в терм доказательства, верифицируемый
проверщиком типов. Если реконструкция не удаётся (шаги вывода SMT выходят за правила вывода ядра
компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: атрибут уточнения, который компилятор не может автоматически доказать
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип и есть вышеуказанное утверждение
# Проверщик типов верифицирует эту функцию — полностью аналогично верификации add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # компилятор здесь верифицирует: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Никакого ИИ, никакого экспорта в Coq, никаких новых концепций. **Атрибуты, которые компилятор не
может автоматически доказать → программист пишет доказательство в коде YaoXiang → проверщик типов
верифицирует.** Весь процесс — плавный градиент: компилятор берёт на себя простые доказательства,
оставляя сложные вам.

#### 4.3 Стратифицированные зависимости внутри конвейера

Вышеуказанные вычислители используют один и тот же интерфейс, но имеют порядок вычисления. Равенство
типов — предпосылка для всего последующего анализа; проверки владения/токенов зависят от информации
о типах; верификация уточняющих предикатов зависит от результатов двух предыдущих слоёв. Компилятор
вычисляет по слоям; выражения, не прошедшие нижний слой, не попадают в верхний — избегая траты
бюджета решения на типово-ошибочных программах.

```
Порядок вычисления (один конвейер, стратифицированная диспетчеризация)
├── Слой 0: равенство типов (T1 == T2)
│   └── структурная унификация → при неудаче дальнейшее бессмысленно, сразу Disproved
├── Слой 1: конфликты владения/токенов
│   └── потокочувствительный анализ живучести → при неудаче безопасность памяти не доказана, сразу Disproved
└── Слой 2: уточняющие предикаты / импликации Хоара
    └── ядро компилятора → SMT-ускорение → Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя один интерфейс и единую
систему бюджетов.

### 5. Единство трёх слоёв функций

| Слой                | Момент выполнения | Вход         | Выход    | Пример                                         |
| ------------------- | ----------------- | ------------ | -------- | ---------------------------------------------- |
| Функция значений    | Runtime           | Значения     | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типа    | Compile-time      | Тип/значение | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат компиляции | Compile-time      | Значения     | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют одинаковый синтаксис `name: type = value`. Предикат времени компиляции и конструктор
типа идут по одному конвейеру доказательств — `{}` есть пространство доказательств.

### 6. Циклы: генерация условий верификации по Флойду-Хоару

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Уточняющие
предикатные аннотации типов на переменных определяют утверждения в стиле Флойда-Хоара — компилятор
генерирует условия верификации из аннотаций типов, конвейер доказательств проверяет, сохраняет ли
каждое присваивание тип.

Ключевой механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует одно условие верификации для тела цикла — после
верификации конвейером индуктивного шага все итерации покрываются автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i; при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # проверка: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует одну VC для тела цикла. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не изменён)
        #   подставляя s_new = s_old + arr[i]:
        #     требуется s_old + arr[i] == sum(arr[0..i+1])
        #     из индуктивной гипотезы s_old == sum(arr[0..i]), прибавив arr[i] к обеим сторонам:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменён → в графе зависимостей аннотация типа s ссылается на i → вызывает ревалидацию
        #   новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   т.е. s == sum(arr[0..i_new]), гарантировано предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # здесь s: SumUpTo(arr, arr.len), т.е. s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант, не нужно «автоматически делать
индукцию» — он разбивает индуктивное доказательство на локальные условия верификации для каждого
присваивания и передаёт их в конвейер доказательств.

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеизложенного механизма: компилятор знает, что аннотация типа `s`, а именно
`SumUpTo(arr, i)`, ссылается на `i` — когда `i` изменяется, типовое ограничение `s` также
изменяется. Это требует от компилятора поддерживать **граф типовых зависимостей между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# ключ — зависимая переменная, значение — множество переменных, чьи аннотации типа ссылаются на эту переменную
# напр.: { i: {s}, j: {s, t}, ... }
```

**Построение**: при обработке `mut v: Pred(... x ...) = init` проверщик типов анализирует свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылки на другие изменяемые переменные
`x` текущей области видимости, в графе зависимостей регистрируется `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает присваивание, компилятор:

1. Ищет в графе зависимостей все переменные, зависящие от `x`: `{v₁, v₂, ...}`
2. Для каждой `v` генерирует условие верификации: удовлетворяет ли текущее значение `v` обновлённому
   типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательств

**Чувствительность к порядку присваиваний**: отслеживание зависимостей естественным образом
форсирует корректный порядок присваиваний. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменён → ревалидация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # i изменён → ревалидация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Составные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` зависит одновременно от `x` и `y` — изменение любой из них вызывает
ревалидацию.

**Связь с конвейером доказательств**: отслеживание зависимостей — триггер генерации VC, а не
отдельный механизм верификации. Оно отвечает на вопрос «когда нужно генерировать VC» — конвейер
доказательств отвечает на вопрос «выполняется ли VC».

### 7. Проверка завершения

Полностью автоматическая во время компиляции. Циклы, которые компилятор может доказать, проходят;
те, которые не может — сразу выдают ошибку компиляции — программист обязан сделать цикл доступным
для автоматического анализа завершаемости. Никаких полуавтоматических аннотаций.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершения, из двух
источников:

1. **Аннотации типов переменных**: граничные ограничения в уточнённых типах (например, `UpTo(n)`
   даёт верхнюю грань `n` и нижнюю `0`)
2. **Операции тела цикла**: операции, применяемые к переменным на каждой итерации

Компилятор перебирает четыре стратегии синтеза метрик по приоритету и останавливается, как только
находит подходящую.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию линейной границы, компилятор перечисляет кандидатов линейных метрик
и верифицирует их через SMT.

```
Вход:
  переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с границами)
  условие цикла cond
  множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типа: [low_i, high_i]
  2. Перечислить кандидатов метрик: v_i, u_i - v_i, v_i - v_j, и т.д. (линейные комбинации)
  3. Для каждого кандидата m:
     - SMT-проверка m ≥ 0 (из типовых границ)
     - для каждого пути выполнения тела цикла SMT-проверка m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершение доказано
```

Покрытие: любой цикл, в котором переменной присваивается линейное выражение (`v = a·v + b`) с
аннотацией ограниченного типа. Включает `i += const`, `i -= const`, а также сужение интервала в
стиле бинарного поиска:

```yaoxiang
# Бинарный поиск: low = mid + 1 или high = mid
# метрика high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: счётчик нарушений предиката — автоматическое извлечение метрики из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, реализация в Фазе 3 будет решаться по
> фактической осуществимости.** Эта стратегия работает для обменов соседних элементов (сортировка
> пузырьком, сортировка вставками), но не может автоматически доказать для не соседних операций
> (partition быстрой сортировки, sift-down пирамидальной сортировки). Границы покрытия см. в таблице
> ниже. Если в Фазе 3 осуществимость не подтвердится, эта стратегия будет удалена или отложена.

Ключевое наблюдение: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted` и автоматически извлекает из него метрику.

```
Вход:
  целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  операции тела цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать метрику: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операции на метрику:
     - обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - затрагивает только пары с индексами j-1, j, j+1
     - если arr[j] > arr[j+1] (нарушение предиката), после обмена пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя грань: n·(n-1)/2 (максимум соседних инверсий), нижняя грань: 0
  → завершение доказано
```

**Текущий охват**:

| Алгоритм                 | Шаблон операции      | Стратегия 2 доказуема? | Причина                                               |
| ------------------------ | -------------------- | :--------------------: | ----------------------------------------------------- |
| Пузырьковая сортировка   | Соседний обмен       |           ✅           | violation_count строго убывает при каждом обмене      |
| Сортировка вставками     | Соседнее перемещение |           ✅           | Каждое перемещение устраняет одну нарушенную пару     |
| Сортировка выбором       | Несоседний обмен     |           ❌           | Один обмен может увеличить violation_count            |
| Быстрая сортировка       | разбиение partition  |           ❌           | Несоседний обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌           | Древовидная операция, violation_count немонотонна     |

**Взаимодополняющие стратегии**: для быстрой сортировки сужение интервала `low < high` покрывается
Стратегией 1 (линейная ранговая функция) — внешняя рекурсия partition, каждый интервал делится
пополам. Стратегии 1 и 2 взаимно дополняют друг друга, и завершаемость большинства реальных
алгоритмов может быть доказана одной из них. Однако обобщение Стратегии 2 (на несоседние операции,
древовидные операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: шаблоны ограниченного возрастания/убывания

`v += const` (с положительной константой), переменная с аннотацией верхней границы → метрика
`upper_bound - v` убывает на `const` каждую итерацию, нижняя грань 0. Это вырожденный случай
Стратегии 1, компилятор обрабатывает его в первую очередь.

#### 6.5 Стратегия 4: шаблоны метрик мультипликативного масштабирования

`v *= const` (const > 1), переменная с аннотацией нижней и верхней границы. Компилятор имеет
встроенный шаблон логарифмической метрики `ceil(log_const(upper/v))`, при каждом умножении на const
метрика уменьшается на 1.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # компилятор автоматически выводит: метрика ceil(log₂(n/i)), при каждом умножении на 2 метрика уменьшается на 1
    i *= 2
}
```

#### 6.6 Разделение завершаемости и корректности

Доказательство завершаемости и доказательство корректности независимы:

- **Завершаемость**: четыре вышеуказанные стратегии автоматически доказывают, что цикл завершается
  за конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  через условия верификации

Оба прошли → компиляция проходит. Завершаемость доказана, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершаемость не доказуема → ошибка компиляции с
указанием переменной или операции, которую не удалось проанализировать. Оба не прошли → ошибка
компиляции с раздельным указанием причин обоих отказов.

#### 6.7 Проверка завершения рекурсивных функций

Для рекурсивных функций, которые должны вычисляться во время компиляции, компилятор проверяет
убывание аргументов:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # компилятор анализирует: n-1 < n → убывание → завершение
}

# Использование во время компиляции — компилятор гарантирует завершение factorial во время компиляции
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, вычисляется во время компиляции
```

| Сценарий                                                                 | Поведение                        |
| ------------------------------------------------------------------------ | -------------------------------- |
| Компилятор может проанализировать рекурсивное убывание (например, `n-1`) | Вычисление во время компиляции   |
| Не убывает / не удаётся установить убывание                              | Ошибка компиляции                |
| Вызов во время выполнения (не в позиции типа)                            | Проверка завершения не требуется |

#### 6.8 Жёсткие границы

`i = f(i)`, где `f` необратима, незамкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершение. Ошибка компиляции:

> Не удаётся автоматически доказать завершение этого цикла. Переменная цикла зависит от
> неанализируемой функции `f`. Пожалуйста, используйте шаблон итерации, доступный для анализа
> компилятором.

Это не провал компилятора. Любой код, который нельзя статически доказать как безопасный, не должен
проходить компиляцию.

### 8. SMT-решатель: ускоряющий модуль проверщика типов

SMT-решатель в традиционных языках — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang это **ускоряющий модуль проверщика типов** — вызывается только тогда, когда ядро
компилятора само не может вынести заключение напрямую. SMT помогает искать доказательство, но
проверяет доказательство проверщик типов.

**Модель доверия**: проверщик типов — единственный доверенный корень. SMT-решатель — ускоряющий
модуль — он помогает искать доказательство, но SMT не является отдельным доверенным корнем.
Компилятор доверяет результату `unsat` от Z3 (в соответствии с подходом F\*/Dafny — вероятность
ошибки Z3 ниже частоты багов самого компилятора, что является инженерно прагматичным выбором).
Истинная ненадёжность контролируется на уровне трансляции в SMT — если в трансляции есть баг,
компилятор обнажит её в других тестах.

**Интерфейс**: внутренняя трансляция компилятора — в стандартный формат SMT-LIB 2.6, без привязки к
API конкретного решателя. SMT-LIB — стандарт ISO, нативно поддерживается Z3, CVC5, MathSAT, Yices.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, самая широкая документация и общественная валидация).
CVC5 как SMT-LIB-совместимая альтернатива — пользователь может переключаться флагом компилятора.

Не делаем «уровень абстракции универсального решателя» — SMT-LIB и есть уровень абстракции. Если в
будущем CVC5 добьётся прорыва в определённой теории, переключение требует лишь замены бинарника, без
изменения кода компилятора.

```
Выражение Bool времени компиляции
        │
        ├── Ядро компилятора может судить напрямую (структурная эквивалентность,
        │   простая арифметика, тривиальные формулы после свёртки констант)
        │   → напрямую возвращает Proved / Disproved
        │
        └── Ядро компилятора не может судить напрямую (кванторы, символьные переменные)
            → предварительная редукция зависимых типов (factorial(5) → 120)
            → трансляция в формат SMT-LIB
            → отправка в Z3/CVC5 (с лимитом бюджета)
            → возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткий лимит, как глубина стека**:

| Измерение бюджета                 | По умолчанию | Пояснение                                                                                                                                                         |
| --------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10 000       | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывают 99% реальных предикатов.                                                     |
| Время                             | 100 мс       | Один предикат более 100 мс = пользователь пишет программу времени компиляции вместо аннотации типа. 100 мс × 50 предикатов = 5 секунд верхней границы компиляции. |
| Глубина инстанцирования кванторов | 3            | Три уровня вложенных кванторов покрывают реальные шаблоны. Свыше трёх уровней — скорее всего, логическая задача.                                                  |

Превышение бюджета возвращает Unproven, ошибка компиляции + позиция предиката + потребление.
Никакого понижения, никаких проверок времени выполнения, никаких silent pass.

**Почему это практически осуществимо**: 95% реальных предикатов в инженерии — линейная арифметика —
`x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в пределах разрешимого фрагмента, SMT-решатель
для таких задач возвращает за миллисекунды. Для редких сложных предикатов, превышающих бюджет,
программист пишет функцию-доказательство.

Зависимые типы перед вызовом SMT проходят слой предварительной редукции: `factorial(5)` напрямую
вычисляется во время компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти
детерминированные вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Мысленная модель: **компилятор может доказать —
проходит, не может — сообщает об ошибке; если компилятор не умеет, можно написать функцию,
доказывающую ему**.

### 9. Композиция предикатов времени компиляции

Предикат времени компиляции — это функция, возвращающая Type, и композиция реализуется естественно
через композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ компилятор проверяет Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ компилятор проверяет Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ компилятор проверяет InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ компилятор проверяет InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации `dispatch`: единая диспетчеризация для времени компиляции и времени выполнения

`assert` и `Assert` — это две стороны одного примитива уточнённого типа. Конвейер диспетчеризации
`dispatch` автоматически решает, идти ли по пути доказательства во время компиляции или проверки во
время выполнения, в зависимости от **достижимости свободных переменных предиката во время
компиляции**:

| Критерий                                                                                                   | Режим           | Поведение                                                                                                       |
| ---------------------------------------------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры дженериков, константы времени компиляции) | **CompileTime** | В конвейер доказательств: Proved → стирается, Disproved → ошибка компиляции, Unknown → требуется доказательство |
| Есть свободные переменные из времени выполнения (параметры функций, внешний ввод, mut-переменные)          | **Runtime**     | Вставляется runtime check, в потокочувствительное множество гипотез Γ инжектируется уточняющий факт             |

**Ключевое**: «не удаётся определить» ≠ «опровергнуто». Unknown в режиме CompileTime требует
доказательства (без тихой деградации), в режиме Runtime утверждение во время компиляции в принципе
не имеет истинности — никакой prover, каким бы сильным он ни был, не может написать тавтологию для
«пользователь мог ввести отрицательное число», runtime check — единственный sound выбор. Это не
слабость prover'а, а теоретическая необходимость.

### 12. Потокочувствительное множество гипотез Γ: распространение сильнейшего постусловия

Компилятор поддерживает потокочувствительное (flow-sensitive) множество гипотез Γ, отслеживающее
истинные утверждения в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← распространение SP
```

**kill set для mut-переменных**: после переприсваивания `mut`-переменной все гипотезы с её участием
удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые гипотезы недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение гипотез ветвей. Выходят
из ветви только те утверждения, которые истинны на всех путях.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточнённые типы полностью стираются во время выполнения» относится к **proof
witness (токен доказательства)** — терм доказательства, верифицированный во время компиляции, не
порождает runtime-кода. Но runtime check, вставленный dispatch'ем в режиме Runtime, сохраняется —
это Bool-проверка, выполняемая на уровне значений, а не witness на уровне типов.

Итог: witness стирается, check сохраняется. Эти два не противоречат друг другу, исходное утверждение
RFC-027 остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| Ранее (RFC-022)                       | Далее (настоящий RFC)                                                                     |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Предикат времени компиляции как тип параметра `(b: Positive(b))`                          |
| `//! ensures: ExistsMax(result, arr)` | Тип возврата использует формальный параметр возврата `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Уточняющая предикатная аннотация типа на переменной — инвариант Флойда-Хоара              |
| `//! decreases: n`                    | Компилятор полностью автоматически выводит функцию-меру                                   |
| Спецификация — комментарий            | Спецификация — система типов                                                              |

### Синтаксис

**У предикатов времени компиляции нет новых ключевых слов.** `{}` — пространство доказательств,
полностью соответствующее существующему синтаксису определения типов. Предикат времени компиляции —
это функция, возвращающая Type: `name: (params) -> Type = { утверждения }`. При использовании — это
вызов функции: `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Предикат времени компиляции = функция, возвращающая Type; внутри {} — верифицируемые компилятором утверждения
# Используется существующий синтаксис функций/типов, новые правила BNF не нужны
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы приложения предиката должны иметь форму констант времени компиляции** — литералы,
переменные (по имени) или однопараметрические типовые приложения (рекурсивное извлечение). Когда
аргументы не могут быть приведены к константному выражению, или число аргументов не совпадает с
параметрами предиката, выдаётся ошибка компиляции **E1092** — уточняющие ограничения **никогда не
отбрасываются молча** (#263: ранее непреобразуемые аргументы приводили к беззвучному исчезновению
ограничения, и связывание с нарушением ограничения молча проходило).

**Новая синтаксическая концепция: формальный параметр возврата** — в `-> (name: Type)` `name`
является формальным параметром возврата.

Формальный параметр возврата — это **единственная** новая синтаксическая концепция, вводимая
YaoXiang поверх существующего синтаксиса функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается постусловие-предикат (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не входит в область видимости тела функции, не появляется у вызывающего
- Формальный параметр возврата **опционален** — при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), без какой-либо дополнительной нагрузки

Причина его введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть».
Без формального параметра возврата компилятор мог бы ссылаться на возвращаемое значение только через
специальные правила (например, неявная переменная `$result` или `__retval__`). Формальный параметр
возврата делает эту ссылку явной — это просто параметр, значение которого предоставляется через
`return`, а не вызывающим.

**Функция-доказательство** — не новая концепция — это просто функция YaoXiang, чей возвращаемый тип
равен доказываемому утверждению. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверщик типов верифицирует её точно так же, как он верифицирует
возвращаемый тип любой функции. Никакого нового синтаксиса, новых ключевых слов, новых правил.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функции, принимающие
  значения и возвращающие Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с дженериками**: предикаты времени компиляции могут иметь параметры-дженерики,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения — только чтение, без записи
- **Вывод типов**: параметры предикатов времени компиляции участвуют в HM-выводе типов

### Представление во время выполнения

Предикат времени компиляции обрабатывается во время выполнения **в соответствии с результатом
диспетчеризации**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): токен свидетельства
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представляется как `Int`. Условие уточнения `{ 5 > 0 }` уже проверено, стирается.
- **Режим Runtime** (есть свободные переменные времени выполнения): сохраняется runtime check —
  Bool-проверка на уровне значений, инжектируемая в потокочувствительное множество гипотез Γ.
  Подробности см. в §11 конвейер диспетчеризации и §13 уточнение модели стирания.

Использование предиката времени компиляции в позиции типа (например, `f(x: Positive(x))`) не
порождает обёрточного типа, не выделяет дополнительной памяти. Но когда `x` поступает из ввода
времени выполнения, **будет** вставлена runtime Bool-проверка.

**Ограничение взаимодействия с `ref`**: предикат времени компиляции может ссылаться только на
значения с неизменяемым заимствованием или с уже переданным владением. Предикат времени компиляции,
ссылающийся на значение с изменяемым заимствованием, — компилятор не может гарантировать во время
компиляции, что результат верификации останется истинным во время выполнения; такое использование
сразу выдаёт ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, дополнительные
   правила разбора не нужны
2. **Конвейер доказательств времени компиляции**: единый интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **SMT-модуль ускорения**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, альтернатива
   CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение квантора всеобщности. Это единственный доверенный корень; SMT и
   доказательства программиста проходят верификацию через него
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёт о нерешённых утверждениях + привязка
   к позициям в исходном коде

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, остаётся полностью неизменным
- ✅ Предикаты времени компиляции в режиме CompileTime имеют нулевые накладные расходы во время
  выполнения; в режиме Runtime сохраняются лишь необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но RFC-022 никогда не был реализован,
  бремя миграции отсутствует

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Ховарда**: тип есть утверждение, программа есть
  доказательство, `name: Proposition = Proof`
- **Единство**: предикаты времени компиляции и обычные функции используют полностью идентичный
  синтаксис, без концептуального расщепления
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, мысленная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции, постепенно расширяя
  покрытие
- **Минимальные накладные расходы во время выполнения**: режим CompileTime — нулевые расходы, режим
  Runtime — только необходимые Bool-проверки

### Недостатки

- **Время компиляции**: SMT-решение увеличивает время компиляции, но жёсткий лимит бюджета
  гарантирует контролируемую верхнюю границу
- **Границы автоматического доказательства**: сложные предикаты, выходящие за пределы линейной
  арифметики первого порядка, могут потребовать от программиста написания функций-доказательств. Это
  не дефект языка — это неизбежное следствие проблемы остановки. Компилятор честно сообщает Unproven
  вместо ложного True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Ховарда
- **Сложность реализации**: единство конвейера доказательств времени компиляции требует тщательного
  проектирования

### Снижение рисков

- Жёсткий лимит бюджета SMT (шаги 10 000 / время 100 мс / глубина инстанцирования 3), превышение
  возвращает Unproven
- Предварительная редукция зависимых типов: сначала съедаются детерминированные вычисления значений,
  SMT жуёт только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверщик типов
  верифицирует — аналогично верификации возвращаемого типа любой функции
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + демонстрация контрпримеров + отчёт о потреблении бюджета +
  нерешённые утверждения + предложения (если компилятор может их дать)

## Альтернативы

| Альтернатива                                                                                     | Почему не выбрана                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-022: спецификации в форме комментариев `//!`                                                 | Спецификации и типы расщеплены, нарушение изоморфизма Карри-Ховарда                                                                                                                     |
| Отдельные файлы спецификаций (например, CVL)                                                     | Спецификации отделены от кода, увеличивается стоимость сопровождения                                                                                                                    |

| **Настоящее предложение: предикаты времени компиляции как полноправные граждане первого класса** | ✅                                                                                                                                                                                      |

## Стратегия реализации

### Разбиение на фазы

| Фаза       | Содержимое                                                                                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фаза 1** | Ядро компилятора: структурная эквивалентность + βδι-редукция + введение/устранение квантора всеобщности. Поддержка простых арифметических предикатов (`x > 0`, `arr.len > 0`) |
| **Фаза 2** | Слой трансляции в SMT-LIB + интеграция Z3/CVC5. Конвейер возвращает Proved/Disproved/Unproven. При Unproven поддерживается написание функций-доказательств программистом      |
| **Фаза 3** | Генерация VC инвариантов цикла + проверка завершения (линейная ранговая функция + счётчик нарушений предиката + ограниченные шаблоны + контроль комбинаторного взрыва)        |
| **Фаза 4** | Инкрементальная верификация + кэширование + поддержка IDE                                                                                                                     |

### Зависимости

- RFC-010: Унифицированный синтаксис типов — предикаты времени компиляции основаны на
  `name: type = value`

- RFC-009: Модель владения — выражения предикатов времени компиляции подчиняются правилам владения

## Открытые вопросы

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, самая широкая валидация). CVC5 как
      SMT-LIB-совместимая альтернатива, переключение флагом компилятора. Внутренняя трансляция
      компилятора направлена на стандартный формат SMT-LIB 2.6 — SMT-LIB и есть уровень абстракции,
      никакого самодельного универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решения**: шаги 10 000 / время 100 мс / глубина инстанцирования
      кванторов 3. Зафиксированы внутри компилятора, без ручек. Если в реальном использовании
      встретятся настоящие случаи, доказывающие недостаточность (не «пользователь ошибся»), значения
      будут скорректированы.
- [x] **Область поддержки кванторов**: язык не ограничивает порядок кванторов. Предикаты времени
      компиляции принимают параметры Type — Type включает функциональные типы — поэтому кванторы
      высшего порядка — естественное следствие системы типов, специальный синтаксис не нужен.
      SMT-решатель может автоматически разрешать кванторы первого порядка (forall/exists,
      поддерживается чередующееся вложение, ограничено глубиной бюджета 3). Кванторы высшего
      порядка: SMT возвращает Unproven, компилятор предлагает «этот предикат выходит за пределы
      автоматического доказательства, предоставьте функцию-доказательство». Программист пишет
      функцию YaoXiang, чей возвращаемый тип равен этому утверждению — проверщик типов верифицирует
      эту функцию. Никакого внешнего экспорта, никакого ИИ, никакого интерактивного режима
      доказательства. Всё — код YaoXiang, всё проверяется проверщиком типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена SMT-переменных (с префиксом модуля во избежание конфликтов). При возврате модели Z3
      выполняется обратный поиск по именам переменных. Формат вывода: имя переменной = конкретное
      значение + позиция в исходном коде + позиция определения предиката. Никакого сложного слоя
      отображения.
- [x] ~~**Взаимодействие предикатов времени компиляции с умными указателями `ref`?**~~ → Решено:
      предикаты времени компиляции допускают только неизменяемые заимствования или значения с
      переданным владением. Значения с изменяемым заимствованием не могут появляться в предикатах
      времени компиляции.
- [x] **Расширение метрики счётчика нарушений `forall`-предиката на несоседние операции?** → Не
      расширяется. Текущий охват (соседние обмены, соседние перемещения) дополнительно покрывается
      Стратегией 1 (линейная ранговая функция) — сужение интервала во внешнем слое быстрой
      сортировки покрывается Стратегией 1, пирамидальная сортировка покрывается Стратегией 1 (шаблон
      индексации массива). Циклы, для которых ни одна стратегия не может доказать завершение,
      компилятор сразу отвергает — это философия жёсткой безопасности, а не дефект. Если в будущем
      появится реальный сценарий (не академическая конструкция) с алгоритмом, который не покрывается
      ни одной из четырёх стратегий, вопрос будет пересмотрен.
- [x] **Комбинаторный взрыв при перечислении линейной ранговой функции**: верхний предел числа
      переменных с границами для перечисления — 3. При ≤3 перечисляются все линейные комбинации,
      каждая верифицируется через SMT. При >3 проверяются только метрики по одной переменной (`v_i`,
      `u_i - v_i`), при неудаче сразу выдаётся ошибка компиляции — с подсказкой программисту «в
      цикле >3 переменных с границами, компилятор не может автоматически синтезировать многомерную
      метрику». Это не инженерный компромисс — это принуждение программиста к написанию более
      простых циклов.
