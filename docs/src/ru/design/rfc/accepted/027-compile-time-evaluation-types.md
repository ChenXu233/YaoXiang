> — устарел

## Резюме

В данном документе предлагается ввести в YaoXiang **предикаты времени компиляции** как полноправных
граждан, объединив всю статическую верификацию времени компиляции в единый **конвейер
доказательств**. Предикат времени компиляции — это не внешний спецификационный комментарий, а сама
функция. Функция, возвращающая Type, может использоваться в позиции типа, и компилятор вызывает её
во время компиляции и проверяет возвращаемое значение. Тип — это утверждение, вычисление во время
компиляции — это доказательство.

**Основной тезис**: единственная задача проверки типов во время компиляции — построить и
верифицировать терм доказательства. Равенство типов, конфликты токенов, редукция зависимых типов,
вычисление предикатов времени компиляции, импликации логики Хоара — всё это различные проверки типов
в конвейере доказательств времени компиляции, разделяющие один и тот же конвейер. Решатель SMT — это
ускоряющий модуль проверщика типов, а не независимый доверенный корень. Когда компилятор возвращает
Unproven, программист пишет функцию на YaoXiang в качестве доказательства — проверщик типов
верифицирует её ровно так же, как он верифицирует возвращаемый тип любой функции. Всё — это код на
YaoXiang, всё верифицируется проверщиком типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← Это комментарий, отдельный от типа
    //! ensures: ExistsMax(result, arr[0..n])   ← Это комментарий, отдельный от типа
}
```

Это совершает фундаментальную ошибку соответствия Карри–Ховарда: **разделяет спецификации и типы на
два слоя**. Комментарий — это не тип. Комментарий не участвует в проверке типов. Комментарий — это
мысленная модель «внешнего инструмента».

Белая книга выражается ясно:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов».

### Текущие проблемы

- Комментарии `//!` из RFC-022 — это внешний синтаксис, отделённый от системы типов
- Спецификационные типы и обычные типы — это две разные системы, что создаёт концептуальную
  избыточность
- Модель разделения «Debug Build верифицирует / Release Build игнорирует» нарушает единство
- Решатель SMT в традиционном понимании позиционируется как внешний инструмент — YaoXiang встраивает
  его как ускоряющий модуль проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов — каждое идёт своим путём

### Правильная мысленная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — являются подзадачами этой функции. Они разделяют один и
тот же конвейер доказательств, различаясь лишь сложностью терма доказательства и стратегией его
построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство — её
возвращаемый тип равен доказываемому утверждению. Проверщик типов верифицирует её. Это та же
операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип есть утверждение, верификация есть проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри есть утверждение, и
компилятор гарантирует истинность каждого — либо автоматическим доказательством, либо
предоставленной программистом функцией-доказательством.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  Компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  Компилятор гарантирует, что data — Array(T)
```

**Обобщённые типы — это частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          Параметр в сигнатуре   Внутри {} только утверждения
#          Компилятор верифицирует x > 0 при вызове времени компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      Параметр в сигнатуре  Компилятор верифицирует type_of(T) == Type, type_of(data) == Array(T)
```

Один и тот же шаблон: `name: (params) -> Type = { утверждения }`. Компилятор не различает
«утверждения типов» и «утверждения значений» — все они являются целями вычисления в конвейере
доказательств.

**Инварианты цикла не нужно записывать отдельно. Аннотации типа на переменных — это и есть
инварианты Флойда–Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # При инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # Компилятор верифицирует: s_new == sum(arr[0..i+1])
        i += 1       # Изменение i → запускает повторную верификацию зависимостей s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. После того, как
конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически. Не
нужно `: decreases`, не нужно `: Invariant`, не нужно индуктивное доказательство — компилятор
разбивает индукцию на локальные УВ для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции на типах параметров и возвращаемого значения

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции становятся
аннотациями типов параметров или возвращаемого значения.

**На стороне параметров — вызов функции.** Предикат времени компиляции — это функция, возвращающая
Type, а её использование на стороне параметра — это вызов этой функции — ровно как `factorial(5)`.
На стороне возвращаемого значения вводится новое понятие: формальный параметр возвращаемого
значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive
#                       Компилятор извлекает значение аргумента в точке вызова, подставляет в b, верифицирует Positive(аргумент)
#                       Пример: divide(10, 2) → верифицирует Positive(2) = { 2 > 0 } → True
#                       Пример: divide(10, 0) → верифицирует Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возвращаемого значения, значение предоставляется return
#                                            Компилятор подставляет возвращаемое значение в точке return, верифицирует постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **На стороне параметров**: `b: Positive(b)` — `b` — имя текущего формального параметра,
  передаваемое в `Positive` в качестве аргумента. Синтаксис вызова функции, ноль неявного.
- **На стороне возврата**: `-> (result: IsMax(T, arr, result))` — `result` — формальный параметр
  возвращаемого значения, значение предоставляется оператором `return`. `result` существует только в
  сигнатуре типа, на него ссылается только предикат, он не попадает в область видимости тела
  функции, не виден вызывающему.
- **Формальный параметр возвращаемого значения необязателен**: при отсутствии постусловия не
  пишется, сигнатура полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: параметр и формальный параметр возвращаемого значения — одно и то же понятие —
  `имя_параметра: вызов_предиката(имя_параметра)`, различие лишь в том, предоставляется ли значение
  вызывающим или оператором `return`.

### 3. Распространение условий пути: верификация значений времени выполнения во время компиляции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно. Когда значение времени выполнения попадает в параметр уточнённого типа,
компилятор завершает верификацию посредством сбора условий пути и SMT-импликации — без необходимости
явной передачи доказательства программистом.

#### 3.1 Явный вызов функции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно — это вызов функции, ноль неявного.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предикатов времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт уже связанное имя переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — это вызов функции
// После нормализации: b: { b > 0 }
```

Компилятору не нужно неявно заполнять аргумент — `b: Positive(b)` и `f(5)` — это одно и то же, вызов
функции. `b` связывается как имя параметра, и его аннотация типа `Positive(b)` ссылается на `b` сам
— это стандартный шаблон зависимых типов, а не правило неявного раскрытия.

**Единство с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а просто
конвенциональное имя параметра («написать `p`, `this`, `x` — эффект абсолютно одинаковый»).
`b: Positive(b)` использует тот же механизм — имя параметра может использоваться в аннотации типа.
`self` появляется в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, обе аннотации
типа ссылаются на сам параметр. Различие лишь в сложности аннотации типа, механизм абсолютно тот же
— после связывания имени тип может зависеть от этого имени.

Тип возврата также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возвращаемого значения, Sorted(result) — вызов функции
//                        Компилятор подставляет возвращаемое значение в result в точке return, верифицирует Sorted(возвращаемое_значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор условий пути

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
условия пути, формируя **набор предположений** текущей области видимости. Эти предположения
участвуют в верификации как фоновые знания при вычислении Bool во время компиляции.

```yaoxiang
if y > 0 {
    // Компилятор автоматически получает предположение в этой ветви: { y > 0 }
    let result = divide(x, y)
    // Условие верификации: (y > 0) ⇒ (y > 0)
    // Конвейер доказательств решает, что импликация выполняется → Proved
} else {
// В этой ветви предположение: { !(y > 0) }
// Если вызвать divide(x, y), условие верификации: !(y > 0) ⇒ y > 0
    // Конвейер доказательств решает, что импликация не выполняется → Disproved
}
```

Это не зашитый в компилятор специальный шаблон — это естественное поведение конвейера доказательств
времени компиляции. Каждая проверка типа в точке вызова отправляет в конвейер:

```
{фоновые_предположения} ⇒ {цель_верификации}
```

Конвейер доказательств определяет импликацию. Proved → проходит, Disproved → ошибка компиляции +
контрпример, Unproven → ошибка компиляции + нерешённое утверждение. Фоновые предположения берутся из
условий пути текущей точки программы.

#### 3.3 Стек предположений

Во время анализа потока управления компилятор поддерживает набор предположений для каждого базового
блока:

- **if-guard**: `if y > 0` → в true-ветвь помещается `y > 0`, в false-ветвь помещается `!(y > 0)`
  (если используется else)
- **Паттерн match**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **Логическая связка**: `if x > 0 and y < 10` → в ветвь помещаются `x > 0` и `y < 10`
- **Предусловие функции**: при вызове `divide(a, b)` доказательство того, что `b` удовлетворяет
  `Positive`, должно приходить либо из текущих предположений, либо из аннотации уточнённого типа
  самого аргумента (если `b` аннотирован как `Positive`, его тип несёт `b > 0`)
- **Присваивание**: при `let z = y` уточнённые условия, уже имеющиеся у `y`, передаются `z`

Все предположения поступают в конвейер доказательств времени компиляции. При переходе на путь
SMT-ускорения они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Без статического доказательства — ошибка компиляции

Если программист пишет прямо:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей точке программы нет предположения `y > 0`, и сам аргумент `y` не имеет аннотации типа
`Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация не выполняется) → ошибка компиляции:

> Не удаётся доказать, что параметр `b` удовлетворяет `Positive` в вызове `divide`. `y` приходит из
> ввода функции, без доказанных границ. Рассмотрите защиту вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не принимает прямого попадания значений времени выполнения в параметры уточнённого типа без
предоставления статического доказательства. Это не ограничение — это ядро философии жёсткой
безопасности. Любой код, который компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Связь с унифицированным конвейером

Распространение условий пути — не дополнительный механизм. Это прямое продолжение конвейера
доказательств времени компиляции в анализе потока управления:

| Этап                                 | Ответственность                                                                                                                                                                     |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор условий пути                    | Этап анализа потока управления компилятора, аннотирует набор предположений для каждого базового блока                                                                               |
| Генерация условий верификации        | При столкновении с ограничением типа, требующим верификации, объединяет условия пути + информацию о типе аргумента                                                                  |
| Вычисление в конвейере доказательств | Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven                                                                                                          |
| Результат                            | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + нерешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Условия пути — это фоновые знания конвейера
доказательств, разделяющие один конвейер и одну систему бюджета с равенством типов и ограничениями
заимствования.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции разделяют один конвейер. Ключевая операция конвейера — **проверка
типов** — проверка, равен ли тип терма доказательства доказываемому утверждению. Всё — это проверка
типов.

```
Во время компиляции встречается выражение Bool, требующее вычисления (то есть: требуется построить терм доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → Компилятор решает напрямую (структурная эквивалентность)
        │
        ├── Конфликт токенов (!conflicting(tokens))
        │   → Потокочувствительный анализ живучести (отслеживание свойств Dup/Linear)
        │
        ├── Редукция зависимых типов (упрощение n + m)
        │   → Система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикат времени компиляции (x > 0, forall...)
        │   → Ядро компилятора + модуль SMT-ускорения
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → Ядро компилятора + модуль SMT-ускорения
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → Компиляция проходит
             │ Disproved│  → Ошибка компиляции + контрпример
             │ Unproven │  → Ошибка компиляции + нерешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код на YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ──→ Proved ──→ Компиляция проходит
                  │
                  ▼
            Верификация не прошла → Ошибка компиляции: «Доказательство не установлено»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — это неизбежное следствие проблемы
остановки и естественное деление в теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → Остановка, терм доказательства построен, проверка типов прошла. Компиляция
  продолжается.
- **Disproved(M)** → Остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → В пределах данного лимита ресурсов терм доказательства не построен. Ошибка
  компиляции + нерешённое утверждение + отчёт о расходе бюджета.

**Unproven ≠ False.** Когда компилятор говорит «я не могу это доказать», это не означает ложность
утверждения — просто это за пределами текущих возможностей автоматического доказательства. Это
честность, а не дефект.

Жёсткое ограничение бюджета — это инженерное решение проблемы остановки. Без ручек настройки —
давать их означало бы спрашивать пользователя «как вы думаете, ваша программа остановится?», чего не
знает ни пользователь, ни компилятор.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция на YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверщик типов
верифицирует эту функцию — тем же механизмом, что и `add(a, b): Int`.

```
Утверждение = Тип
Доказательство = Программа (значение этого типа)
Верификация = Проверка типов (единственный доверенный корень)
```

Решатель SMT — не независимый доверенный корень — это **ускоряющий модуль проверщика типов**. SMT
помогает найти доказательство, но верифицирует доказательство всегда проверщик типов. Когда SMT
возвращает `unsat`, компилятор реконструирует его результат в терм доказательства, верифицируемый
проверщиком типов. Если реконструкция не удалась (шаги вывода SMT выходят за правила вывода ядра
компилятора), происходит откат к Unproven — программист может написать функцию-доказательство
вручную.

```yaoxiang
# Утверждение: уточнённое свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип — это утверждение выше
# Проверщик типов верифицирует эту функцию — точно так же, как верифицирует add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # Компилятор здесь верифицирует: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Не нужен ИИ, не нужен экспорт в Coq, не нужны новые концепции. **Свойства, которые нельзя доказать
автоматически во время компиляции → программист пишет доказательство в коде на YaoXiang → проверщик
типов верифицирует.** Весь процесс — плавный градиент — компилятор берёт на себя простые
доказательства, оставляя мозг для сложных.

#### 4.3 Слоистые зависимости внутри конвейера

Вышеописанные вычислители разделяют один интерфейс, но имеют порядок вычисления. Равенство типов —
необходимое условие для всего последующего анализа; проверки владения/токенов зависят от информации
о типах; верификация уточняющих предикатов зависит от результатов первых двух слоёв. Компилятор
вычисляет послойно; выражения, не прошедшие нижний слой, не поступают на верхний — это исключает
трату бюджета решателя на типоневерных программах.

```
Порядок вычисления (один конвейер, послойная диспетчеризация)
├── Слой 0: Равенство типов (T1 == T2)
│   └── Структурная унификация → при неудаче дальнейшее бессмысленно, сразу возврат Disproved
├── Слой 1: Конфликты владения/токенов
│   └── Потокочувствительный анализ живучести → при неудаче безопасность памяти не выполняется, сразу возврат Disproved
└── Слой 2: Уточняющие предикаты / импликации Хоара
    └── Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя один интерфейс и одну
систему бюджета.

### 5. Единство трёх слоёв функций

| Слой                        | Момент запуска   | Вход         | Выход    | Пример                                         |
| --------------------------- | ---------------- | ------------ | -------- | ---------------------------------------------- |
| Функция-значение            | Время выполнения | Значения     | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типа            | Время компиляции | Тип/значение | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат времени компиляции | Время компиляции | Значение     | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют один и тот же синтаксис `name: type = value`. Предикаты времени компиляции и
конструкторы типов идут по одному конвейеру доказательств времени компиляции — `{}` — это
пространство доказательств.

### 6. Циклы: генерация условий верификации Флойда–Хоара

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточняющего
типа на переменных определяют утверждения в стиле Флойда–Хоара — компилятор генерирует условия
верификации из аннотаций типов, и конвейер доказательств проверяет, сохраняет ли каждое присваивание
тип.

Ключевой механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует одно условие верификации для тела цикла — после
того, как конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются
автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i; при инициализации i=0, верификация: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # Верификация: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует одно УВ для тела цикла. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не меняется)
        #   Подставляя s_new = s_old + arr[i]:
        #     Требуется s_old + arr[i] == sum(arr[0..i+1])
        #     Из индуктивной гипотезы s_old == sum(arr[0..i]), прибавив arr[i] к обеим частям:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменяется → граф зависимостей, тип s ссылается на i → запускает повторную верификацию
        #   Новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   То есть s == sum(arr[0..i_new]), гарантировано предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # В этот момент s: SumUpTo(arr, arr.len), то есть s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант и не нужно «автоматически делать
индукцию» — он разбивает индуктивное доказательство на локальные условия верификации для каждой
операции присваивания, передавая их в конвейер доказательств по принципу «разделяй и властвуй».

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеописанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i` — когда `i` изменяется, ограничение типа `s` также изменяется. Это требует от
компилятора поддерживать **граф зависимостей типов между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# Ключ — зависимая переменная, значение — множество переменных, чьи аннотации типа ссылаются на эту переменную
# Пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: проверщик типов при обработке `mut v: Pred(... x ...) = init` разбирает свободные
переменные в аргументах `Pred(...)`. Если аргументы ссылаются на другую изменяемую переменную `x` в
текущей области видимости, в графе зависимостей записывается `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает новое значение, компилятор:

1. Ищет в графе зависимостей все переменные `{v₁, v₂, ...}`, зависящие от `x`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Отправляет УВ в конвейер доказательств

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественно обеспечивает
правильный порядок присваивания. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменяется → повторная верификация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # i изменяется → повторная верификация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → Ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # Недостижимо
```

**Комбинированные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` одновременно зависит от `x` и `y` — изменение любой из них запускает
повторную верификацию.

**Связь с конвейером доказательств**: отслеживание зависимостей — это триггер генерации УВ, а не
независимый механизм верификации. Оно отвечает на вопрос «когда нужно генерировать УВ» — конвейер
доказательств отвечает на вопрос «выполняется ли УВ».

### 7. Проверка завершаемости

Полностью автоматическая во время компиляции. Циклы, которые компилятор может доказать, проходят;
которые не может — сразу выдают ошибку компиляции — программист должен сделать цикл анализируемым
для автоматического вывода завершаемости. Никаких лазеек для полуавтоматических аннотаций.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершаемости, из двух
мест:

1. **Аннотации типов переменных**: граничные ограничения в уточняющих типах (например, `UpTo(n)`
   даёт верхнюю границу `n` и нижнюю `0`)
2. **Операции в теле цикла**: операции, применяемые к переменным на каждой итерации

Компилятор пробует четыре стратегии синтеза меры в порядке приоритета и останавливается, как только
находит подходящую.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию линейной границы, компилятор перечисляет кандидатов на линейную
меру и верифицирует их с помощью SMT.

```
Вход:
  Переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с границами)
  Условие цикла cond
  Набор присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типов: [low_i, high_i]
  2. Перечислить кандидатов на меру: v_i, u_i - v_i, v_i - v_j и т.д. (линейные комбинации)
  3. Для каждого кандидата m:
     - SMT-верификация m ≥ 0 (из границ типов)
     - Для каждого пути выполнения в теле цикла SMT-верификация m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершаемость доказана
```

Покрытие: циклы, в которых переменная получает значение линейного выражения (`v = a·v + b`) и имеет
аннотацию ограниченного типа. Включает `i += const`, `i -= const`, а также сжатие интервалов в стиле
двоичного поиска:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# Мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: счётчик нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, при реализации фазы 3 решение о включении
> принимается по фактической реализуемости.** Эта стратегия работает для операций соседнего обмена
> (сортировка пузырьком, сортировка вставками) и не может автоматически доказать несмежные операции
> (partition быстрой сортировки, sift-down пирамидальной сортировки). Границы покрытия см. в таблице
> ниже. Если на фазе 3 верификация покажет нереализуемость, эта стратегия будет удалена или отложена
> как будущая работа.

Ключевое наблюдение: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  Целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  Операции в теле цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операций на меру:
     - Обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - Затрагивает только пары с индексами j-1, j, j+1
     - Если arr[j] > arr[j+1] (нарушение предиката), после обмена пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя граница: 0
  → Завершаемость доказана
```

**Текущее покрытие**:

| Алгоритм                 | Шаблон операции | Стратегия 2 доказуема? | Причина                                              |
| ------------------------ | --------------- | :--------------------: | ---------------------------------------------------- |
| Сортировка пузырьком     | Соседний обмен  |           ✅           | violation_count строго убывает при каждом обмене     |
| Сортировка вставками     | Соседний сдвиг  |           ✅           | Каждый сдвиг устраняет одну нарушающую пару          |
| Сортировка выбором       | Несмежный обмен |           ❌           | Один обмен может увеличить violation_count           |
| Быстрая сортировка       | partition       |           ❌           | Несмежный обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down       |           ❌           | Древовидная операция, violation_count немонотонен    |

**Дополняющие стратегии**: для быстрой сортировки сжатие интервала `low < high` покрывается
стратегией 1 (линейная ранговая функция) — внешняя partition-рекурсия, при которой интервал каждый
раз уменьшается вдвое. Стратегии 1 и 2 дополняют друг друга, и завершаемость большинства
практических алгоритмов может быть доказана одной из них. Однако обобщение стратегии 2 (несмежные
операции, древовидные операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: шаблон ограниченного возрастания/убывания

`v += const` (const — положительное число), переменная имеет аннотацию верхней границы → мера
`upper_bound - v` убывает на `const` каждую итерацию, нижняя граница 0. Это вырожденный случай
стратегии 1, компилятор обрабатывает его первым делом.

#### 6.5 Стратегия 4: шаблон меры с мультипликативным масштабированием

`v *= const` (const > 1), переменная имеет аннотацию верхней и нижней границ. Компилятор имеет
встроенный логарифмический шаблон меры `ceil(log_const(upper/v))`, при каждом умножении на const
мера убывает на 1.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # Компилятор автоматически выводит: мера ceil(log₂(n/i)), при каждом умножении на 2 мера убывает на 1
    i *= 2
}
```

#### 6.6 Разделение завершаемости и корректности

Доказательство завершаемости и доказательство корректности независимы:

- **Завершаемость**: четыре вышеописанные стратегии автоматически доказывают, что цикл завершается
  за конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  времени компиляции через условия верификации

Оба проходят → компиляция успешна. Завершаемость доказана, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершаемость не доказуема → ошибка компиляции с
указанием переменной или операции, которые не удаётся проанализировать. Оба не прошли → ошибка
компиляции с раздельным отчётом по обоим пунктам.

#### 6.7 Проверка завершаемости рекурсивных функций

Для рекурсивных функций, требующих вычисления во время компиляции, компилятор проверяет убывание
аргументов:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Анализ компилятора: n-1 < n → убывание → завершение
}

# Использование во время компиляции — компилятор гарантирует завершение factorial во время компиляции
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, выполняется во время компиляции
```

| Сценарий                                                                 | Поведение                           |
| ------------------------------------------------------------------------ | ----------------------------------- |
| Компилятор может проанализировать рекурсивное убывание (например, `n-1`) | Вычисление во время компиляции      |
| Не убывает / не удаётся определить убывание                              | Ошибка компиляции                   |
| Вызов во время выполнения (не в позиции типа)                            | Проверка завершаемости не требуется |

#### 6.8 Жёсткая граница

`i = f(i)`, где `f` необратима, не замкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершаемость. Ошибка компиляции:

> Не удаётся автоматически доказать завершаемость этого цикла. Переменная цикла зависит от
> неанализируемой функции `f`. Пожалуйста, используйте шаблон итерации, анализируемый компилятором.

Это не провал компилятора. Любой код, безопасность которого нельзя статически доказать, не проходит
компиляцию.

### 8. Решатель SMT: ускоряющий модуль проверщика типов

Решатель SMT в традиционных языках — внешний инструмент (F\* вызывает Z3, Dafny вызывает Z3). В
YaoXiang это **ускоряющий модуль проверщика типов** — вызывается только тогда, когда ядро
компилятора само не может принять решение. SMT помогает найти доказательство, но верифицирует
доказательство проверщик типов.

**Модель доверия**: проверщик типов — единственный доверенный корень. Решатель SMT — ускоряющий
модуль — он помогает найти доказательство, но SMT не является независимым доверенным корнем.
Компилятор доверяет результату `unsat` от Z3 (в соответствии с подходом F\*/Dafny — вероятность
ошибки Z3 ниже, чем частота багов самого компилятора, что является прагматичным инженерным выбором).
Реальный контроль ненадёжности сосредоточен на уровне трансляции в SMT — если в трансляции есть баг,
компилятор обнаружит его в других тестах.

**Интерфейс**: внутренняя трансляция компилятора выполняется в стандартный формат SMT-LIB 2.6, а не
в API конкретного решателя. SMT-LIB — стандарт ISO, нативно поддерживаемый Z3, CVC5, MathSAT, Yices.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, наиболее широкая документация и валидация сообщества).
CVC5 как совместимый с SMT-LIB запасной вариант — пользователь может переключаться флагом
компилятора.

Не делаем «универсальный слой абстракции решателя» — SMT-LIB и есть слой абстракции. В будущем, если
CVC5 добьётся прорыва в определённой теории, переключение потребует лишь замены бинарника, без
изменения кода компилятора.

```
Выражение Bool времени компиляции
        │
        ├── Ядро компилятора может решить напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → Сразу вернуть Proved / Disproved
        │
        └── Ядро компилятора не может решить напрямую (кванторы, символьные переменные)
            → Прередукция зависимых типов (factorial(5) → 120)
            → Трансляция в формат SMT-LIB
            → Отправка в Z3/CVC5 (с ограничением бюджета)
            → Возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решателя — жёсткое ограничение, как глубина стека**:

| Измерение бюджета                 | Значение по умолчанию | Пояснение                                                                                                                                                     |
| --------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10 000                | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывают 99% практических предикатов.                                             |
| Время                             | 100 мс                | Один предикат более 100 мс = пользователь пишет программу времени компиляции, а не аннотацию типа. 100 мс × 50 предикатов = верхний предел 5 с на компиляцию. |
| Глубина инстанцирования кванторов | 3                     | Три уровня вложенных кванторов покрывают практические шаблоны. Больше трёх уровней — скорее всего, логическая головоломка.                                    |

Превышение бюджета возвращает Unproven, ошибка компиляции + позиция предиката + расход. Никаких
деградаций, никаких проверок времени выполнения, никакого молчаливого прохода.

**Почему это практически реализуемо**: в инженерии 95% практических предикатов — это линейная
арифметика — `x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в пределах разрешимого фрагмента,
SMT-решатель возвращает ответ за миллисекунды. При столкновении с редкими сложными предикатами,
превышающими бюджет, программист пишет функцию-доказательство.

Зависимые типы проходят слой прередукции до вызова SMT: `factorial(5)` напрямую вычисляется во время
компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти детерминированные
вычисления значений не расходуют бюджет SMT.

Программисту не нужно знать о существовании SMT. Мысленная модель такая: **компилятор может доказать
— проходит, не может — сообщает об ошибке — если компилятор не умеет, можно написать функцию,
которая ему это докажет.**

### 9. Композиция предикатов времени компиляции

Предикат времени компиляции — это функция, возвращающая Type, композиция реализуется естественно
через композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ Компилятор верифицирует Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ Компилятор верифицирует Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ Компилятор верифицирует InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ Компилятор верифицирует InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Циклы: генерация УВ компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: единство времени компиляции и времени выполнения

`assert` и `Assert` — это две стороны одного и того же примитива уточняющего типа. Конвейер
диспетчеризации `dispatch` автоматически решает, идти ли по пути доказательства времени компиляции
или проверки времени выполнения, в зависимости от того, **достижимы ли свободные переменные
предиката во время компиляции**:

| Критерий                                                                                                         | Режим           | Поведение                                                                                                            |
| ---------------------------------------------------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры обобщённых типов, константы времени компиляции) | **CompileTime** | Вход в конвейер доказательств: Proved → стирание, Disproved → ошибка компиляции, Unknown → требование доказательства |
| Существуют свободные переменные из времени выполнения (параметры функций, внешний ввод, mut-переменные)          | **Runtime**     | Вставка проверки времени выполнения и инъекция уточняющего факта в потокочувствительный набор предположений Γ        |

**Ключевое**: «Не удаётся решить» ≠ «Опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихой деградации); в режиме Runtime утверждение во время компиляции вообще не
имеет истинностного значения — никакой prover, каким бы сильным он ни был, не может написать
тавтологически истинное доказательство для «пользователь мог ввести отрицательное число»; проверка
времени выполнения — единственный sound-выбор. Это не слабость prover'а, а теоретическая
неизбежность.

### 12. Потокочувствительный набор предположений Γ: распространение сильнейшего постусловия

Компилятор поддерживает потокочувствительный (flow-sensitive) набор предположений Γ, отслеживающий
утверждения, истинные в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← Распространение SP
```

**Kill set для mut-переменных**: после нового присваивания mut-переменной все предположения,
затрагивающие эту переменную, удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые предположения
недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или ветвей match Γ берёт пересечение предположений
ветвей. Только утверждения, истинные на всех путях, выносятся из ветви.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 о том, что «уточняющие типы полностью стираются во время выполнения», относится
к **proof witness (токену доказательства)** — терм доказательства, верифицированный во время
компиляции, не порождает кода времени выполнения. Но проверки времени выполнения, вставленные
диспетчеризацией в режиме Runtime, сохраняются — это Bool-проверки на уровне значений, а не witness
на уровне типов.

Резюме: witness стираются, check сохраняются. Эти две вещи не конфликтуют, исходное утверждение
RFC-027 остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| До (RFC-022)                          | После (данный RFC)                                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Предикат времени компиляции как тип параметра `(b: Positive(b))`                          |
| `//! ensures: ExistsMax(result, arr)` | Тип возврата использует формальный параметр возврата `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Аннотации уточняющего типа на переменных — инварианты Флойда–Хоара                        |
| `//! decreases: n`                    | Полностью автоматический вывод функций меры компилятором                                  |
| Спецификации — комментарии            | Спецификации — система типов                                                              |

### Синтаксис

**У предикатов времени компиляции нет новых ключевых слов.** `{}` — это пространство доказательств,
полностью совпадающее с существующим синтаксисом определения типов. Предикат времени компиляции —
это функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. Использование — вызов
функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Предикат времени компиляции = функция, возвращающая Type, внутри {} — утверждения, верифицируемые компилятором
# Используется существующий синтаксис функций/типов, новые правила BNF не требуются
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы применения предиката должны быть формой констант времени компиляции** — литералы,
переменные (связывание по имени) или одноаргументные типовые применения (рекурсивное извлечение).
Неконвертируемые в константные выражения аргументы приводят к ошибке **E1092**, несовпадение числа
аргументов с числом параметров предиката приводит к ошибке **E1093** — ограничения уточнения
**никогда не отбрасываются молча** (#263: ранее неконвертируемые аргументы приводили к беззвучному
исчезновению ограничений, и связывания, нарушающие ограничения, молча проходили).

**Новое синтаксическое понятие: формальный параметр возврата** — в `-> (name: Type)` `name` — это
формальный параметр возврата.

Формальный параметр возврата — это **единственное синтаксическое понятие**, вводимое YaoXiang поверх
существующего синтаксиса функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается предикат постусловия (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не попадает в область видимости тела функции, не виден вызывающему
- Формальный параметр возврата **необязателен** — при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), без какой-либо дополнительной нагрузки

Причина введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть». Без
формального параметра возврата компилятор мог бы ссылаться на возвращаемое значение только через
специальные правила (например, неявная переменная `$result` или `__retval__`). Формальный параметр
возврата делает эту ссылку явной — это просто формальный параметр, значение которого предоставляется
`return`, а не вызывающим.

**Функция-доказательство** — не новое понятие — это просто функция на YaoXiang, чей возвращаемый тип
— доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверщик типов верифицирует её тем же способом, что и возвращаемый тип
любой функции. Не нужны новый синтаксис, новые ключевые слова, новые правила.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функции, принимающие
  значения и возвращающие Type, тот же уровень, что и конструкторы типов
- **Взаимодействие с обобщёнными типами**: предикаты времени компиляции могут иметь параметры
  обобщённых типов, например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения, только чтение, без записи
- **Вывод типов**: параметры предикатов времени компиляции участвуют в выводе типов Хиндли–Милнера

### Представление во время выполнения

Предикаты времени компиляции обрабатываются во время выполнения **в соответствии с результатом
диспетчеризации dispatch**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): токен свидетельства
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представлен просто как `Int`. Уточняющее условие `{ 5 > 0 }` уже проверено, стирается.
- **Режим Runtime** (существуют свободные переменные времени выполнения): сохраняется проверка
  времени выполнения — выполняется Bool-проверка на уровне значений, инъекция в потокочувствительный
  набор предположений Γ. Подробности см. в §11 Конвейер диспетчеризации dispatch и §13 Уточнение
  модели стирания.

Помещение предиката времени компиляции в позицию типа (например, `f(x: Positive(x))`) не порождает
обёрточного типа, не выделяет дополнительную память. Но когда `x` поступает из ввода времени
выполнения, **выполняется** вставка Bool-проверки времени выполнения.

**Ограничения взаимодействия с `ref`**: предикаты времени компиляции могут ссылаться только на
неизменяемые заимствования или значения с переданным владением. Предикаты времени компиляции,
ссылающиеся на значения с изменяемым заимствованием, не позволяют компилятору гарантировать во время
компиляции, что результат верификации останется действительным во время выполнения — такое
использование сразу выдаёт ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, дополнительные
   правила разбора не нужны
2. **Конвейер доказательств времени компиляции**: унифицированный интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **Модуль SMT-ускорения**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, запасной CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение кванторов всеобщности. Это единственный доверенный корень, через него
   верифицируются и SMT, и доказательства программиста
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёты о нерешённых утверждениях + привязка
   к позициям в исходном коде

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, остаётся без изменений
- ✅ Предикаты времени компиляции в режиме CompileTime имеют нулевые накладные расходы во время
  выполнения; в режиме Runtime сохраняются только необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован, бремя
  миграции отсутствует

## Компромиссы

### Преимущества

- **Полное воплощение соответствия Карри–Ховарда**: тип — утверждение, программа — доказательство,
  `name: Proposition = Proof`
- **Единство**: предикаты времени компиляции и обычные функции используют полностью идентичный
  синтаксис, без концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, мысленная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции, постепенно расширяя
  покрытие
- **Минимальные накладные расходы во время выполнения**: режим CompileTime — нулевые расходы, режим
  Runtime — только необходимые Bool-проверки

### Недостатки

- **Время компиляции**: решение SMT увеличивает время компиляции, но жёсткие ограничения бюджета
  гарантируют контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты, выходящие за пределы линейной
  арифметики первого порядка, могут потребовать от программиста написания функций-доказательств. Это
  не дефект языка — это неизбежное следствие проблемы остановки. Компилятор честно сообщает
  Unproven, а не ложно сообщает True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и функций-доказательств
  требует понимания базовой интуиции соответствия Карри–Ховарда
- **Сложность реализации**: унификация конвейера доказательств времени компиляции требует
  тщательного проектирования

### Снижение рисков

- Жёсткие ограничения бюджета решателя SMT (10 000 шагов / 100 мс / глубина инстанцирования 3),
  превышение возвращает Unproven
- Прередукция зависимых типов: детерминированные вычисления значений поглощаются первыми, SMT кусает
  только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверщик типов
  верифицирует — как и любой возвращаемый тип
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + отображение контрпримеров + отчёт о расходе бюджета + нерешённые
  утверждения + предложения (если компилятор может их дать)

## Открытые вопросы

- [x] **Выбор решателя SMT**: по умолчанию Z3 (лицензия MIT, наиболее валидирован). CVC5 как
      совместимый с SMT-LIB запасной вариант, переключение флагом компилятора. Внутренняя цель
      трансляции компилятора — стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, без
      собственного универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решателя**: 10 000 шагов / 100 мс / глубина инстанцирования
      кванторов 3. Жёстко зашиты в компиляторе, без ручек настройки. Если реальные случаи
      использования докажут, что этого недостаточно (а не «пользователь ошибся»), значения будут
      скорректированы.
- [x] **Диапазон поддержки кванторов**: язык не ограничивает порядок кванторов. Предикат времени
      компиляции принимает параметр Type — Type включает функциональные типы — поэтому кванторы
      высшего порядка — естественное следствие системы типов, специальный синтаксис не нужен.
      Решатель SMT может автоматически решать кванторы первого порядка (forall/exists, поддержка
      чередующейся вложенности, ограничена бюджетом глубины 3). Кванторы высшего порядка: SMT
      возвращает Unproven, компилятор подсказывает «этот предикат за пределами автоматического
      доказательства, предоставьте функцию-доказательство». Программист пишет функцию на YaoXiang с
      возвращаемым типом, равным утверждению, — проверщик типов верифицирует эту функцию. Не нужен
      внешний экспорт, не нужен ИИ, не нужен интерактивный режим доказательства. Всё — код на
      YaoXiang, всё верифицируется проверщиком типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена переменных SMT (с префиксом модуля для предотвращения конфликтов). Модель Z3
      возвращается с обратным поиском по именам переменных. Формат вывода: имя переменной =
      конкретное значение + позиция в исходном коде + позиция определения предиката. Без сложного
      слоя отображения.
- [x] ~~**Взаимодействие предикатов времени компиляции с интеллектуальными указателями `ref`?**~~ →
      Принятое решение: предикаты времени компиляции разрешают только неизменяемые заимствования или
      значения с переданным владением. Значения с изменяемым заимствованием не могут появляться в
      предикатах времени компиляции.
- [x] **Расширение счётчика нарушений предиката `forall` на несмежные операции?** → Не расширяется.
      Текущее покрытие (соседний обмен, соседний сдвиг) дополняется стратегией 1 (линейная ранговая
      функция) — внешнее сжатие интервала быстрой сортировки покрывается стратегией 1, пирамидальная
      сортировка покрывается стратегией 1 (шаблон индексов массива). Циклы, чью завершаемость не
      может доказать ни одна стратегия, компилятор сразу отвергает — это философия жёсткой
      безопасности, а не дефект. Если в будущем появятся реальные сценарии (а не академические
      конструкции), которые не покрываются ни одной из четырёх стратегий, вопрос будет пересмотрен.
- [x] **Комбинаторный взрыв при перечислении линейных ранговых функций**: верхний предел
      перечисления — 3 ограниченные переменные. При ≤3 перечисляются все линейные комбинации и
      каждая верифицируется через SMT. При >3 пробуются только однопеременные меры (`v_i`,
      `u_i - v_i`), при неудаче сразу ошибка компиляции — подсказка программисту «в цикле >3
      ограниченных переменных, компилятор не может автоматически синтезировать многопеременную
      меру». Это не инженерный компромисс — это принуждение программиста к написанию более простых
      циклов.
