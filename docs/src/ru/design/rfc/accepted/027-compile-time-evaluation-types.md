## Резюме

В данном документе предлагается ввести в YaoXiang **компиляционные предикаты** как граждан первого
класса, объединив всю статическую верификацию времени компиляции в единый **конвейер
доказательств**. Компиляционный предикат — не внешняя спецификационная аннотация — это функция.
Функция, возвращающая Type, может использоваться в позиции типа; компилятор вызывает её во время
компиляции и проверяет возвращаемое значение. Тип — это утверждение, вычисление во время компиляции
— это доказательство.

**Ключевой тезис**: единственная работа проверки типов во время компиляции — строить и
верифицировать доказательные свидетельства. Равенство типов, конфликты токенов, редукция зависимых
типов, вычисление компиляционных предикатов, импликации логики Хоара — всё это разные проверки типов
в конвейере доказательств времени компиляции, разделяющие один и тот же конвейер. SMT-решатель —
ускоритель проверки типов, а не отдельный доверенный компонент. Когда компилятор возвращает
Unproven, программист пишет функцию на YaoXiang в качестве доказательства — проверка типов
верифицирует её ровно тем же способом, что и проверку возвращаемого типа любой функции. Всё — код на
YaoXiang, всё верифицируется проверкой типов.

## Мотивация

### Почему устарел RFC-022?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← Это аннотация, отдельная от типа
    //! ensures: ExistsMax(result, arr[0..n])   ← Это аннотация, отдельная от типа
}
```

Это совершает фундаментальную ошибку изоморфизма Карри-Говарда: **разделяет спецификации и типы на
два слоя**. Аннотация — не тип. Аннотация не участвует в проверке типов. Аннотация — это ментальная
модель «внешнего инструмента».

В белой книге сказано прямо:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Комментарии `//!` из RFC-022 — внешний синтаксис, отдельный от системы типов
- Спецификационные типы и обычные типы — две системы, что создаёт концептуальную избыточность
- Разделение режимов Debug Build с верификацией / Release Build без верификации разрушает единство
- SMT-решатель в традиционном понимании позиционируется как внешний инструмент — YaoXiang делает его
  встроенным ускорителем проверки типов
- Проверка типов, верификация заимствований, проверка компиляционных предикатов, раскрытие макросов
  идут по разным путям

### Корректная ментальная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация компиляционных предикатов — суть подзадачи этой функции. Они разделяют один и тот же
конвейер доказательств, различаясь лишь сложностью доказательных свидетельств и стратегиями их
построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство — её
возвращаемый тип равен доказываемому утверждению. Проверка типов верифицирует её. Это та же самая
операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — это пространство доказательств: тип как утверждение, верификация как проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри — утверждения,
компилятор гарантирует, что каждый элемент истинен — либо автоматическим доказательством, либо
предоставленной программистом функцией-доказательством.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  Компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  Компилятор гарантирует, что data — Array(T)
```

**Дженерики — частный случай компиляционных предикатов.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в            {} содержит только утверждения
#          сигнатуре
#          компилятор верифицирует x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре  компилятор верифицирует type_of(T) == Type, type_of(data) == Array(T)
```

Один и тот же паттерн: `name: (params) -> Type = { утверждения }`. Компилятор не различает
«утверждения о типе» и «утверждения о значении» — все они цели вычисления в конвейере доказательств.

**Инварианты цикла не нужно записывать отдельно. Аннотации типа на переменных — это инварианты
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # При инициализации i=0, верифицируется: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # Компилятор верифицирует: s_new == sum(arr[0..i+1])
        i += 1       # Изменение i → запускает реверификацию зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. Конвейер
доказательств верифицирует индуктивный шаг, после чего все итерации покрываются автоматически. Не
нужен `: decreases`, не нужен `: Invariant`, не нужно индуктивное доказательство — компилятор
разлагает индукцию на локальные УВ для каждого присваивания.

### 2. Предусловия/постусловия: компиляционные предикаты на типах параметров и возвращаемого значения

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Компиляционные предикаты становятся
аннотациями типов на параметрах или возвращаемом значении.

**Сторона параметра — это вызов функции.** Компиляционный предикат — это функция, возвращающая Type,
и её использование на стороне параметра — это её вызов — в точности как `factorial(5)`. Сторона
возвращаемого значения вводит новое понятие: параметр возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов компиляционного предиката в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive
#                       Компилятор в точке вызова извлекает значение аргумента, подставляет в b, верифицирует Positive(аргумент)
#                       Пример: divide(10, 2) → верифицирует Positive(2) = { 2 > 0 } → True
#                       Пример: divide(10, 0) → верифицирует Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: параметр возвращаемого значения + компиляционный предикат
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — параметр возвращаемого значения, значение предоставляется return
#                                            Компилятор в точке return подставляет возвращаемое значение, верифицирует постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **Сторона параметра**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся в
  `Positive` как аргумент. Синтаксис вызова функции, никакой неявности.
- **Сторона возврата**: `-> (result: IsMax(T, arr, result))` — `result` — параметр возвращаемого
  значения, значение предоставляется оператором `return`. `result` существует только в сигнатуре
  типа, на него ссылается только предикат, он не попадает в область видимости тела функции, не
  появляется у вызывающего.
- **Параметр возвращаемого значения опционален**: при отсутствии постусловия не пишется, сигнатура
  полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: параметр и параметр возвращаемого значения — одно и то же понятие —
  `имя_параметра: вызов_предиката(имя_параметра)`, различие лишь в том, предоставляется значение
  вызывающей стороной или оператором `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

Когда компиляционный предикат используется в позиции связывания, аргументы передаются программистом
явно. Когда значение времени выполнения попадает в аргумент уточнённого типа, компилятор завершает
верификацию через сбор путевых условий и SMT-импликацию — без явной передачи доказательства от
программиста.

#### 3.1 Явный вызов функции

Когда компиляционный предикат используется в позиции связывания, аргументы передаются программистом
явно — это вызов функции, никакой неявности.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор компиляционного предиката. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — вызов функции
// После нормализации: b: { b > 0 }
```

Никакого неявного заполнения аргументов компилятором не требуется — `b: Positive(b)` — такой же
вызов функции, как `f(5)`. `b` связывается как имя параметра, его аннотация типа `Positive(b)`
ссылается на сам `b` — это стандартный паттерн зависимых типов, а не правило неявного раскрытия.

**Единство с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а лишь
общепринятое имя параметра («написать `p`, `this`, `x` — совершенно то же самое»). `b: Positive(b)`
использует тот же механизм — имя параметра может упоминаться в аннотации типа. `self` появляется в
позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, обе аннотации типа ссылаются на
сам параметр. Различие лишь в сложности аннотации типа, механизм полностью одинаков — после
связывания имени тип может зависеть от этого имени.

Тип возврата также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — параметр возвращаемого значения, Sorted(result) — вызов функции
//                        Компилятор в точке return подставляет возвращаемое значение в result, верифицирует Sorted(возвращаемое_значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → пройдено

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевые условия, формируя **множество гипотез** текущей области видимости. Эти гипотезы участвуют в
верификации как фоновые знания для вычисления Bool во время компиляции.

```yaoxiang
if y > 0 {
    // Компилятор в этой ветви автоматически получает гипотезу: { y > 0 }
    let result = divide(x, y)
    // Условие верификации: (y > 0) ⇒ (y > 0)
    // Конвейер доказательств устанавливает истинность импликации → Proved
} else {
// В этой ветви гипотеза: { !(y > 0) }
// При вызове divide(x, y) условие верификации: !(y > 0) ⇒ y > 0
    // Конвейер доказательств устанавливает ложность импликации → Disproved
}
```

Это не зашитый в компилятор специальный паттерн — это естественное поведение конвейера доказательств
времени компиляции. Каждая точка проверки типов отправляет в конвейер:

```
{фоновые_гипотезы} ⇒ {цель_верификации}
```

Конвейер доказательств проверяет импликацию. Proved → пройдено, Disproved → ошибка компиляции +
контрпример, Unproven → ошибка компиляции + недоказанное утверждение. Фоновые гипотезы берутся из
путевых условий текущей точки программы.

#### 3.3 Стек гипотез

Компилятор при анализе потока управления поддерживает для каждого базового блока множество гипотез:

- **if-guard**: `if y > 0` → в истинной ветви помещается `y > 0`, в ложной ветви помещается
  `!(y > 0)` (если используется else)
- **match-паттерн**: `if let Some(v) = opt` → в ветви помещается `opt == Some(v)`
- **Логические связки**: `if x > 0 and y < 10` → в ветви помещаются `x > 0` и `y < 10`
- **Предусловие функции**: при вызове `divide(a, b)` свидетельство того, что `b` удовлетворяет
  `Positive`, берётся либо из текущих гипотез, либо из аннотации уточнения самого аргумента (`b`
  помечен как `Positive`, значит его тип несёт `b > 0`)
- **Присваивание**: при `let z = y` уже имеющиеся уточнения `y` передаются `z`

Все гипотезы поступают в конвейер доказательств времени компиляции. При входе на путь SMT-ускорения
они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Нет статического свидетельства — ошибка компиляции

Если программист просто пишет:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей точке программы нет гипотезы `y > 0`, сам аргумент `y` тоже не имеет аннотации `Positive`.
Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация не доказана) → ошибка компиляции:

> Не удаётся доказать, что аргумент `b` удовлетворяет `Positive` в вызове `divide`. `y` приходит из
> входных данных функции, у него нет доказанных границ. Рассмотрите охрану вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не принимает прямое попадание значений времени выполнения в аргументы уточнённого типа без
предоставления статического свидетельства. Это не ограничение — это ядро философии жёсткой
безопасности. Код, который компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Отношение к единому конвейеру

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
доказательств времени компиляции на анализ потока управления:

| Этап                   | Ответственность                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий   | Этап анализа потока управления компилятора, аннотирующий каждый базовый блок множеством гипотез                                                                                       |
| Генерация УВ           | При встрече ограничения типа, требующего верификации, объединяются путевые условия + информация о типе аргумента                                                                      |
| Вычисление в конвейере | Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven                                                                                                            |
| Результат              | `Proved` → пройдено; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + недоказанное утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновые знания
конвейера доказательств — разделяющие один конвейер и одну систему бюджета с равенством типов и
ограничениями заимствования.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции разделяют один конвейер. Центральная операция конвейера — **проверка
типов** — проверить, равен ли тип доказательного свидетельства доказываемому утверждению. Всё —
проверка типов.

```
При вычислении Bool-выражения во время компиляции (т.е. когда требуется построить доказательное свидетельство)
        │
        ├── Равенство типов (T1 == T2)
        │   → Прямое решение компилятора (структурная эквивалентность)
        │
        ├── Условие конфликта токенов (!conflicting(tokens))
        │   → Потокочувствительный анализ живучести (отслеживание Dup/Linear)
        │
        ├── Редукция зависимых типов (редукция n + m)
        │   → Система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Компиляционный предикат (x > 0, forall...)
        │   → Ядро компилятора + SMT-модуль ускорения
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → Ядро компилятора + SMT-модуль ускорения
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → Компиляция проходит
             │ Disproved│  → Ошибка компиляции + контрпример
             │ Unproven │  → Ошибка компиляции + недоказанное утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код на YaoXiang)
                  │
                  ▼
         Проверка типов верифицирует ──→ Proved ──→ Компиляция проходит
                  │
                  ▼
            Верификация не прошла → Ошибка компиляции: «доказательство неверно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — это неизбежное следствие проблемы
остановки и естественное деление в теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → Остановка, доказательное свидетельство построено, проверка типов прошла. Компиляция
  продолжается.
- **Disproved(M)** → Остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → В пределах заданного ресурсного лимита доказательное свидетельство не построено.
  Ошибка компиляции + недоказанное утверждение + отчёт о потреблении бюджета.

**Unproven ≠ False.** Когда компилятор говорит «я не могу это доказать», это не равнозначно ложности
утверждения — просто это превышает возможности текущего автоматического доказателя. Это честность, а
не дефект.

Жёсткий лимит бюджета — инженерное решение проблемы остановки. Без настраиваемых параметров — их
наличие равнозначно вопросу пользователю «как вы думаете, ваша программа остановится?», пользователь
не знает, компилятор тоже не знает.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** —
функцию на YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверка типов
верифицирует эту функцию — тем же механизмом, что и верификация `add(a, b): Int`.

```
Утверждение  = Тип
Доказательство  = Программа (значение этого типа)
Верификация  = Проверка типов (единственный корень доверия)
```

SMT-решатель — не отдельный корень доверия — это **модуль ускорения проверки типов**. SMT помогает
находить доказательства, но верифицирует доказательства проверка типов. Когда SMT возвращает
`unsat`, компилятор реконструирует его результат в доказательное свидетельство, верифицируемое
проверкой типов. Если реконструкция не удалась (шаги вывода SMT выходят за пределы правил вывода
ядра компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: уточнённое свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип — вышеуказанное утверждение
# Проверка типов верифицирует эту функцию — совершенно так же, как верифицирует add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # Компилятор здесь верифицирует: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Не нужен ИИ, не нужен экспорт в Coq, не нужны новые концепции. **Свойство, которое компилятор не
может доказать автоматически → программист пишет доказательство на YaoXiang → проверка типов
верифицирует.** Весь процесс — плавный градиент — компилятор берёт на себя простые доказательства,
оставляя мозг для сложных.

#### 4.3 Слоистые зависимости внутри конвейера

Вышеописанные вычислители разделяют один интерфейс, но имеют порядок вычисления. Равенство типов —
предпосылка для всего последующего анализа; проверка владения/токенов зависит от информации о типах;
верификация уточнённых предикатов зависит от результатов первых двух слоёв. Компилятор вычисляет по
слоям, выражения, провалившиеся на нижнем слое, не поступают на верхний — это позволяет не тратить
бюджет решателя на типонеправильных программах.

```
Порядок вычисления (один конвейер, слоистая диспетчеризация)
├── Слой 0: Равенство типов (T1 == T2)
│   └── Структурная унификация → при провале последующее бессмысленно, сразу Disproved
├── Слой 1: Конфликт владения/токенов
│   └── Потокочувствительный анализ живучести → при провале безопасность памяти не установлена, сразу Disproved
└── Слой 2: Уточнённые предикаты/импликации Хоара
    └── Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя один интерфейс и одну
систему бюджета.

### 5. Унификация трёх слоёв функций

| Слой                    | Момент выполнения | Вход         | Выход    | Пример                                         |
| ----------------------- | ----------------- | ------------ | -------- | ---------------------------------------------- |
| Функция значений        | Время выполнения  | Значения     | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типов       | Время компиляции  | Тип/значение | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Компиляционный предикат | Время компиляции  | Значение     | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют одинаковый синтаксис `name: type = value`. Компиляционные предикаты и конструкторы
типов идут по одному конвейеру доказательств времени компиляции — `{}` — это пространство
доказательств.

### 6. Циклы: генерация условий верификации по Флойду-Хоару

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации
компиляционного предиката на переменных определяют утверждения в стиле Флойда-Хоара — компилятор
генерирует условия верификации из аннотаций типа, а конвейер доказательств проверяет, сохраняет ли
каждое присваивание тип.

Центральный механизм: каждая операция присваивания соответствует тройке Хоара `{P} x := e {Q}`,
условие верификации — `P ⇒ Q[e/x]`. Компилятор генерирует одно УВ для тела цикла — после того, как
конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i; при инициализации i=0, верифицируется: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # Верифицируется: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует одно УВ для тела цикла. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не меняется)
        #   Подставляя s_new = s_old + arr[i]:
        #     Требуется s_old + arr[i] == sum(arr[0..i+1])
        #     Из индуктивной гипотезы s_old == sum(arr[0..i]), прибавив arr[i] к обеим сторонам:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   Изменение i → в графе зависимостей аннотация типа s ссылается на i → запускает реверификацию
        #   Новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   То есть s == sum(arr[0..i_new]), гарантируется предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # В этот момент s: SumUpTo(arr, arr.len), то есть s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант и не нужно «делать индукцию
автоматически» — он раскладывает индуктивное доказательство на локальные условия верификации для
каждой операции присваивания и передаёт их в конвейер доказательств для разделения и властвования.

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеописанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i` — при изменении `i` ограничение типа `s` также меняется. Это требует от компилятора
вести **граф зависимостей типов между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# Ключ — зависимая переменная, значение — множество переменных, чьи аннотации типа ссылаются на эту переменную
# Пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: при обработке `mut v: Pred(... x ...) = init` проверка типов разбирает свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылки на другую изменяемую переменную
`x` из текущей области видимости, в графе зависимостей записывается `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает значение, компилятор:

1. Ищет в графе зависимостей все переменные, зависящие от `x`: `{v₁, v₂, ...}`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Отправляет УВ в конвейер доказательств

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественным образом
обеспечивает правильный порядок присваивания. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # Изменение i → реверификация s на SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # Изменение i → реверификация s на SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → Ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # Недостижимо
```

**Комбинированные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` одновременно зависит от `x` и `y` — изменение любой из них запускает
реверификацию.

**Отношение к конвейеру доказательств**: отслеживание зависимостей — триггер генерации УВ, а не
самостоятельный механизм верификации. Оно отвечает на вопрос «когда нужно генерировать УВ» —
конвейер доказательств отвечает на вопрос «выполнено ли УВ».

### 7. Проверка завершения

**Область применения: уточнённые типы.** Завершаемость — не отдельный переключатель, а часть
**режима верификации**: как только тип уточнён (`Refined { base, constraint }), вычисление,
помеченное этим типом, входит в режим верификации, внутри которого требуется завершаемость;
неуточнённые обычные типы не входят в режим верификации и не порождают обязательств по завершению.

Отсюда два следствия:

- **Циклы**: голый `while` не входит в режим верификации; когда переменная-мера имеет уточнённую
  аннотацию (например, `i: UpTo(n)`), входит в режим верификации, требуется доказать завершение.
- **Рекурсия**: когда сигнатура функции уточнена (уточнён параметр или возвращаемый тип содержит
  уточнение), входит в режим верификации, требуется доказать строгое убывание меры в каждой точке
  рекурсивного вызова.

Внутри режима полный приоритет автоматики: компилятор сначала пробует автоматически исследовать
меру, доказуемое проходит; если исследование не дало результата и мера не дана явно — ошибка
компиляции. Нет лазейки в виде **аннотационного синтаксиса** — и мера, и утверждение о завершении
записываются в позиции типа, без введения нового синтаксиса типа `decreases`. Формы меры и явного
фоллбэка см. в §6.9.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершения, из двух
источников:

1. **Аннотации типа переменных**: ограничения в уточнённом типе (например, `UpTo(n)` даёт верхнюю
   границу `n` и нижнюю `0`)
2. **Операции тела цикла**: операции, применяемые к переменным на каждой итерации

Компилятор перебирает четыре стратегии синтеза меры по приоритету, останавливаясь на первой
подходящей. Четыре стратегии — это **ограниченная последовательность шаблонов исследования меры**,
вход — уточнённые ограничения (стратегии 1–4 стартуют от «переменных с ограниченным типом»), а не
«вычисляемый во время компиляции код»; они — две стороны одной вещи (автоматическая и ручная) с
явной мерой из §6.9.

> **Исследование меры — это поиск, а не вывод.** Поиск только перечисляет шаблоны (линейный ранг,
> счётчик нарушений, ограниченный паттерн, мультипликативное сжатие), не гарантируя существования
> решения — общий вывод меры в общем случае неразрешим (сводится к проблеме остановки). Поэтому
> случаи за пределами шаблонов должны допускать явное задание меры программистом (§6.9), иначе —
> ошибка компиляции.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию линейной границы, компилятор перечисляет кандидатов на линейную
меру и верифицирует их через SMT.

```
Вход:
  Переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с верхней и нижней границами)
  Условие цикла cond
  Множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типа: [low_i, high_i]
  2. Перечислить кандидатов на меру: v_i, u_i - v_i, v_i - v_j, и т.д. — линейные комбинации
  3. Для каждого кандидата m:
     - SMT верифицирует m ≥ 0 (из границ типа)
     - Для каждого пути выполнения тела цикла SMT верифицирует m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершение доказано
```

Область покрытия: любой цикл, в котором переменной присваивается линейное выражение (`v = a·v + b`)
и она имеет аннотацию ограниченного типа. Включает `i += const`, `i -= const`, а также сжатие
интервалов в стиле двоичного поиска:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# Мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: счётчик нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, на этапе 3 реализации будет принято решение о
> включении по фактической реализуемости.** Эта стратегия работает для операций обмена соседних
> элементов (сортировка пузырьком, сортировка вставками), но не может автоматически доказать
> завершение для не соседних операций (разбиение быстрой сортировки, просеивание вниз в
> пирамидальной сортировке). Границы покрытия см. в таблице ниже. Если на этапе 3 верификация
> окажется нереализуемой, эта стратегия будет удалена или перенесена в будущие работы.

Ключевое наблюдение: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое отсортированность» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  Целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  Операции тела цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операций на меру:
     - Обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - Затрагивает только пары с индексами j-1, j, j+1
     - Если arr[j] > arr[j+1] (нарушение предиката), после обмена эта пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя: 0
  → Завершение доказано
```

**Текущая область покрытия**:

| Алгоритм                 | Паттерн операций     | Стратегия 2 доказуема? | Причина                                               |
| ------------------------ | -------------------- | :--------------------: | ----------------------------------------------------- |
| Сортировка пузырьком     | Обмен соседних       |           ✅           | violation_count строго убывает при каждом обмене      |
| Сортировка вставками     | Соседние перемещения |           ✅           | Каждое перемещение устраняет одну нарушенную пару     |
| Сортировка выбором       | Несоседний обмен     |           ❌           | Один обмен может увеличить violation_count            |
| Быстрая сортировка       | Разбиение partition  |           ❌           | Несоседний обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌           | Древовидная операция, violation_count не монотонна    |

**Взаимодополняющие стратегии**: для быстрой сортировки сжатие интервала `low < high` может быть
покрыто стратегией 1 (линейная ранговая функция) — внешняя рекурсия partition, каждый интервал
уменьшается вдвое. Стратегии 1 и 2 дополняют друг друга, и завершаемость большинства реальных
алгоритмов может быть доказана одной из них. Однако обобщение стратегии 2 (несоседние операции,
древовидные операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: паттерн ограниченного инкремента/декремента

`v += const` (положительная константа), переменная имеет аннотацию верхней границы → мера
`upper_bound - v` убывает на `const` каждую итерацию, нижняя граница 0. Это вырожденный случай
стратегии 1, компилятор обрабатывает его первым для скорости.

#### 6.5 Стратегия 4: шаблон меры мультипликативного сжатия

`v *= const` (const > 1), переменная имеет аннотацию верхней и нижней границ. Компилятор имеет
встроенный шаблон логарифмической меры `ceil(log_const(upper/v))`, убывающей на 1 при каждом
умножении на const.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # Компилятор автоматически выводит: мера ceil(log₂(n/i)), убывающая на 1 при каждом умножении на 2
    i *= 2
}
```

#### 6.6 Разделение завершаемости и корректности

Доказательство завершаемости и доказательство корректности независимы:

- **Завершаемость**: четыре стратегии выше автоматически доказывают, что цикл завершается за
  конечное число шагов; при неудаче исследования программист задаёт меру в позиции типа (§6.9)
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  через условия верификации

Оба проходят → компиляция проходит. Завершаемость доказана, но корректность провалена → ошибка
компиляции + контрпример. Корректность доказана, но завершаемость не доказуема → ошибка компиляции с
указанием переменных или операций, которые не удаётся проанализировать. Оба провалились → ошибка
компиляции с раздельным указанием причин обоих провалов.

#### 6.7 Проверка завершения рекурсивных функций

Для рекурсивных функций с уточнённой сигнатурой компилятор проверяет убывание формальных параметров
в каждой точке рекурсивного вызова:

```yaoxiang
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)  // Компилятор исследует: (b, a % b) имеет убывающую меру по подходящему порядку → завершение
}
```

Убывание формальных параметров — сильнейший автоматический путь (структурная рекурсия). При неудаче
исследования программист задаёт меру явно в позиции типа (§6.9).

#### 6.8 Жёсткие границы

`i = f(i)`, где `f` необратима, незамкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершение. Ошибка компиляции:

> Этот цикл не может быть автоматически доказан как завершающийся. Переменная цикла зависит от
> неанализируемой функции `f`. Используйте шаблон итерации, анализируемый компилятором, либо
> привяжите к этому циклу имя и задайте меру в позиции типа (§6.9).

Это не провал компилятора. Код, который невозможно статически доказать как безопасный, не проходит
компиляцию. Даже при явной мере она должна быть признана SMT истинной, иначе — отказ с
контрпримером: человек может не суметь доказать, но не может доказать неверно.

#### 6.9 Явная мера: `Terminates`

Когда автоматическое исследование не находит меры, программист записывает меру в **позиции типа** —
тем же механизмом (применение предиката), что и `Positive(b)`, `IsMax(T, arr, result)`, без нового
синтаксиса:

```yaoxiang
// Мера: обычная функция, тестируемая, переиспользуемая, не участвующая во времени выполнения
gcd_measure: (a: Int, b: Int) -> Int = { b }

// Компонента завершения встроена в тип самой функции
gcd: Terminates((a: Int, b: Int) -> Int, gcd_measure) = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

// Цикл: имя привязки — точка опоры, мера получает величины из своей области видимости по имени
loop: (n: Int) -> Int = {
    mut i = 0
    acc: Terminates(n - i) = while i < n {
        i = i + 1
    }
    return acc
}
```

Обоснование для цикла: `Terminates(m)` уточняет тип значения хвостового выражения тела цикла, точка
опоры предоставляется именем привязки `acc` — благодаря этому цикл становится денотационно
адресуемым, без «тупиков анонимных конструкций, к которым нельзя обратиться».

**`Terminates` — встроенный предикат**, наряду с `Int`, `Never` относится к базовым примитивам. Это
единственный предикат, **чьё тело функции пишет компилятор** — его утверждение («мера строго убывает
в каждой точке рекурсивного вызова / обратной рёберной точке цикла») живёт в вычислительной
структуре, к телу функции или телу цикла пользовательские предикаты обратиться не могут, поэтому его
невозможно выразить через синтаксис определения предиката из раздела «Синтаксис». Встроенная
поверхность сходится к этому одному имени.

**Арность**. `Terminates(FnType, m)` и `Terminates(m)` — это один и тот же предикат в двух арностях,
а не два разных конструктора:

| Форма                   | Точка опоры              | Назначение                                                 |
| ----------------------- | ------------------------ | ---------------------------------------------------------- |
| `Terminates(m)`         | Имя текущей привязки     | Самоссылающиеся функции, циклы — форма по умолчанию        |
| `Terminates(FnType, m)` | Явный функциональный тип | Взаимная рекурсия и подобные случаи без единой точки опоры |

По сути это одно и то же: обязательство завершения всегда ложится на «вычисление, помеченное типом в
позиции уточнения».

**Мера не ограничивает тип возврата.** Мера может быть выражением произвольного типа (не обязательно
натуральным числом); «строгое убывание» на ней задаётся доступным подходящим порядком на этом типе.
Является ли мера обоснованной (например, для возврата `Int` — выполняется ли `>= 0`) — это
**отдельное обязательство**, так же передаваемое уточнённому выводу или SMT; если ни то, ни другое
не выводится, диагностика **не отказывает напрямую**, а подсказывает направление проверки
(установлена ли нижняя граница меры, действительно ли рекурсивный аргумент движется в эту сторону).

**Отношение к автоматическому исследованию**: явная мера — не отдельный конвейер, а вход после
неудачи исследования. После задания меры та же SMT верифицирует убывание и обоснованность; если они
не выполняются — сообщение об ошибке с контрпримером.

Детали реализации — генерация обязательств, конвейер верификации, направления диагностики,
разделение мер взаимной рекурсии (SCC) — см. в
[RFC-027a: Явные меры проверки завершения](../review/027a-termination-explicit-measure.md).

### 8. SMT-решатель: модуль ускорения проверки типов

SMT-решатель в традиционных языках — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang это **модуль ускорения проверки типов** — вызывается только тогда, когда ядро
компилятора само не может вынести решение. SMT помогает находить доказательства, но верифицирует
доказательства проверка типов.

**Модель доверия**: проверка типов — единственный корень доверия. SMT-решатель — модуль ускорения —
он помогает находить доказательства, но SMT — не отдельный корень доверия. Компилятор доверяет
результату `unsat` от Z3 (в духе подхода F\*/Dafny — вероятность ошибки Z3 ниже частоты багов самого
компилятора, это инженерный прагматизм). Реальный контроль ненадёжности находится на уровне
трансляции в SMT — при наличии бага в трансляции компилятор обнажит его в других тестах.

**Интерфейс**: внутренняя трансляция компилятора происходит в стандартный формат SMT-LIB 2.6, а не в
API конкретного решателя. SMT-LIB — стандарт ISO, Z3, CVC5, MathSAT, Yices поддерживают его нативно.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, наиболее широкая документация и подтверждение
сообществом). CVC5 как SMT-LIB-совместимая альтернатива — пользователь может переключаться флагом
компилятора.

Никакого «универсального слоя абстракции решателя» — SMT-LIB сам и есть слой абстракции. В будущем,
если CVC5 добьётся прорыва в определённой теории, переключение потребует лишь смены бинарника, без
изменения кода компилятора.

```
Bool-выражение времени компиляции
        │
        ├── Ядро компилятора может решить напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → Сразу возвращает Proved / Disproved
        │
        └── Ядро компилятора не может решить напрямую (кванторы, символьные переменные)
            → Предварительная редукция зависимых типов (factorial(5) → 120)
            → Трансляция в формат SMT-LIB
            → Отправка в Z3/CVC5 (с лимитом бюджета)
            → Возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решателя — жёсткий лимит, как глубина стека**:

| Измерение бюджета                 | По умолчанию | Пояснение                                                                                                                                                       |
| --------------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Шаги решения                      | 10,000       | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывают 99% реальных предикатов.                                                   |
| Время                             | 100ms        | Один предикат больше 100ms = пользователь пишет программу времени компиляции, а не аннотацию типа. 100ms × 50 предикатов = верхняя граница 5 секунд компиляции. |
| Глубина инстанцирования кванторов | 3            | Три уровня вложенности кванторов покрывают реальные паттерны. Больше трёх — скорее всего упражнение по логике.                                                  |

Превышение бюджета возвращает Unproven, ошибка компиляции + позиция предиката + потребление. Никакой
деградации, никаких проверок времени выполнения, никакого тихого прохода.

**Почему это практически реализуемо**: в инженерии 95% реальных предикатов — линейная арифметика —
`x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в разрешимом фрагменте, SMT-решатель для таких
задач возвращает за миллисекунды. При встрече с немногими сложными предикатами, превышающими бюджет,
программист пишет функцию-доказательство.

Зависимые типы перед вызовом SMT проходят предварительную редукцию: `factorial(5)` напрямую
вычисляется во время компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти
детерминированные вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Ментальная модель: **компилятор может доказать —
проходит, не может — сообщает об ошибке — если компилятор не умеет, можно написать функцию, которая
докажет ему**.

### 9. Композиция компиляционных предикатов

Компиляционные предикаты — это функции, возвращающие Type; композиция реализуется естественно через
композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ Компилятор верифицирует Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ Компилятор верифицирует Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ Компилятор верифицирует InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ Компилятор верифицирует InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... Реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация УВ компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации `dispatch`: единая диспетчеризация времени компиляции и времени выполнения

`assert` и `Assert` — две стороны одного примитива уточнённого типа. Конвейер диспетчеризации
`dispatch` автоматически решает, идти ли по пути доказательства во время компиляции или по пути
проверки во время выполнения, по критерию **достижимости свободных переменных предиката во время
компиляции**:

| Критерий                                                                                                      | Режим           | Поведение                                                                                                           |
| ------------------------------------------------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры дженериков, константы времени компиляции)    | **CompileTime** | Вход в конвейер доказательств: Proved → стирание, Disproved → ошибка компиляции, Unknown → требуется доказательство |
| Есть свободные переменные, приходящие из времени выполнения (параметры функции, внешний ввод, mut-переменные) | **Runtime**     | Вставка проверки времени выполнения и инъекция уточнённого факта в потокочувствительный Γ                           |

**Ключевое**: «не удаётся решить» ≠ «опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихой деградации), в режиме Runtime у утверждения в принципе нет истинности во
время компиляции — никакой prover не способен вывести тавтологию для «пользователь мог ввести
отрицательное число», проверка времени выполнения — единственный sound выбор. Это не слабость
prover'а, это теоретическая неизбежность.

### 12. Потокочувствительное множество гипотез Γ: распространение сильнейшего постусловия

Компилятор поддерживает потокочувствительное множество гипотез Γ, отслеживающее утверждения,
известные истинными в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← Распространение SP
```

**Kill set для mut-переменных**: после повторного присваивания `mut`-переменной все связанные с ней
гипотезы удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убит
```

Это жёсткое требование soundness — значение переменной изменилось, старая гипотеза недействительна.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение гипотез ветвей. Только
утверждения, истинные на всех путях, выносятся из ветви.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточнённые типы полностью стираются во время выполнения» относится к **proof
witness (токену доказательства)** — построенное во время компиляции доказательное свидетельство не
порождает кода времени выполнения. Но вставленные в режиме Runtime **проверки времени выполнения**
конвейера dispatch сохраняются — это Bool-проверки на уровне значений, а не witness на уровне типов.

Резюме: witness стирается, check сохраняется. Эти две вещи не конфликтуют, исходное утверждение
RFC-027 остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| Ранее (RFC-022)                       | После (данный RFC)                                                                                                                                    |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Компиляционный предикат как тип параметра `(b: Positive(b))`                                                                                          |
| `//! ensures: ExistsMax(result, arr)` | Тип возврата использует параметр возвращаемого значения `-> (result: IsMax(T, arr, result))`                                                          |
| `/*! invariant: ... !*/`              | Аннотация компиляционного предиката на переменной — инвариант Флойда-Хоара                                                                            |
| `//! decreases: n`                    | Мера записывается в позиции уточнённого типа (`Terminates`); компилятор сначала пробует автоматическое исследование, требует явную только при неудаче |
| Спецификация — комментарий            | Спецификация — система типов                                                                                                                          |

### Синтаксис

**У компиляционных предикатов нет новых ключевых слов.** `{}` — это пространство доказательств,
полностью совпадающее с существующим синтаксисом определения типов. Компиляционный предикат — это
функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. Использование — вызов
функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Компиляционный предикат = функция, возвращающая Type, в {} — утверждения, верифицируемые компилятором
# Используется существующий синтаксис функций/типов, без новых правил BNF
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы применения предиката должны иметь форму, приводимую к константе времени компиляции** —
литералы, переменные (связываемые по имени), типовые применения (с рекурсивным извлечением) или
**адресуемые во время компиляции ссылки на функции** (имя функции). Неприводимость аргумента к
константному выражению — ошибка **E1092**, несовпадение числа аргументов с числом формальных
параметров предиката — ошибка **E1093**. Аргументы связываются по позиции со списком формальных
параметров, арность предиката определяется его объявлением — `Positive(x)` — унарный,
`IsMax(T, arr, result)` — тернарный, `Terminates(m)` и `Terminates(FnType, m)` — унарный и бинарный
— ограничения уточнения **никогда не отбрасываются молча** (ранее неприводимый аргумент приводил к
тихому исчезновению ограничения, а нарушающее связывание молча проходило).

**Новое синтаксическое понятие: параметр возвращаемого значения** — в `-> (name: Type)` `name` — это
параметр возвращаемого значения.

Параметр возвращаемого значения — это **единственное синтаксическое понятие**, вводимое YaoXiang в
существующий синтаксис функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается постусловие (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не попадает в область видимости тела функции, не появляется у вызывающего
- Параметр возвращаемого значения **опционален** — при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), не вводя никакой дополнительной нагрузки

Причина его введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть».
Без параметра возвращаемого значения компилятор мог бы позволить предикату ссылаться на возвращаемое
значение только через специальные правила (например, неявная переменная `$result` или `__retval__`).
Параметр возвращаемого значения делает эту ссылку явной — это просто параметр, только значение
предоставляется `return`, а не вызывающей стороной.

**Функция-доказательство** — не новое понятие — это функция на YaoXiang, чей возвращаемый тип — это
доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверка типов верифицирует её точно так же, как верифицирует возвращаемый
тип любой функции. Никакого нового синтаксиса, ключевых слов, правил.

> **Граница двух доменов.** Домен корректности (Unproven предиката) дополняется доказательством в
> **теле**: написать функцию, чей возвращаемый тип — доказываемое утверждение. Домен завершения
> (§6.9) дополняется мерой в **позиции типа**: написать `Terminates(мера)` как тип привязки или
> сигнатуры функции. Первое — «для недоказуемого утверждения пишется доказательство», второе — «для
> неисследимой меры она объявляется явно» — механизм один (применение уточнённого типа), точки опоры
> разные. Домену завершения **не нужно** писать функцию `_proof`.

### Влияние на систему типов

- **Вселенная типов**: компиляционные предикаты находятся на слое Type₂ — функции, принимающие
  значения и возвращающие Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с дженериками**: компиляционные предикаты могут иметь параметры-дженерики,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения внутри компиляционных предикатов подчиняются правилам
  владения, только чтение, без записи
- **Вывод типов**: аргументы компиляционных предикатов участвуют в HM-выводе типов

### Представление во время выполнения

Компиляционные предикаты во время выполнения обрабатываются **в соответствии с результатом
диспетчеризации**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): токен свидетельства
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представляется просто как `Int`. Уточнённое условие `{ 5 > 0 }` верифицировано, стирается.
- **Режим Runtime** (есть свободные переменные времени выполнения): сохраняется проверка времени
  выполнения — Bool-проверка на уровне значений с инъекцией в потокочувствительный Γ. Подробности
  см. в §11 конвейере диспетчеризации dispatch и §13 уточнении модели стирания.

Помещение компиляционного предиката в позицию типа (например, `f(x: Positive(x))`) не порождает
оборачивающего типа, не выделяет дополнительной памяти. Но когда `x` приходит из ввода времени
выполнения, **будет** вставлена Bool-проверка времени выполнения.

**Ограничение взаимодействия с `ref`**: компиляционные предикаты могут ссылаться только на
неизменяемые заимствования или значения с переданным владением. Компиляционный предикат, ссылающийся
на значение по изменяемому заимствованию, не может гарантировать компилятору, что результат
верификации останется действительным во время выполнения — такое использование даёт прямую ошибку
компиляции.

### Изменения в компиляторе

1. **Парсер**: компиляционные предикаты используют стандартный синтаксис функций, дополнительные
   правила разбора не нужны
2. **Конвейер доказательств времени компиляции**: единый интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **SMT-модуль ускорения**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, альтернатива
   CVC5
4. **Ядро проверки типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/исключение кванторов всеобщности. Это единственный корень доверия, через него
   верифицируются и результаты SMT, и программистские доказательства
5. **Генерация условий верификации**: WP/SP-исчисление + генерация обязательств инвариантов цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёт о недоказанных утверждениях +
   привязка к позициям в исходном коде

### Обратная совместимость

- ✅ Код, не использующий компиляционные предикаты, остаётся полностью без изменений
- ✅ Компиляционные предикаты в режиме CompileTime дают нулевые накладные расходы во время
  выполнения, в режиме Runtime сохраняются только необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован, бремя
  миграции отсутствует

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Говарда**: тип — утверждение, программа — доказательство,
  `name: Утверждение = Доказательство`
- **Единство**: компиляционные предикаты и обычные функции используют полностью идентичный
  синтаксис, без концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, ментальная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного компиляционного предиката, постепенно расширяя
  покрытие
- **Минимальные накладные расходы во время выполнения**: режим CompileTime — ноль накладных
  расходов, режим Runtime — только необходимые Bool-проверки

### Недостатки

- **Время компиляции**: SMT-решение увеличивает время компиляции, но жёсткий лимит бюджета
  гарантирует контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами линейной арифметики
  первого порядка могут потребовать от программиста написания функций-доказательств. Это не дефект
  языка — это неизбежное следствие проблемы остановки. Компилятор честно сообщает Unproven, а не
  ложно объявляет True/False
- **Кривая обучения**: написание эффективных компиляционных предикатов и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Говарда
- **Сложность реализации**: единство конвейера доказательств времени компиляции требует тщательного
  проектирования

### Снижение рисков

- Жёсткий лимит бюджета SMT (шаги 10 000 / время 100ms / глубина инстанцирования 3), превышение
  возвращает Unproven
- Предварительная редукция зависимых типов: детерминированные вычисления значений поглощаются
  первыми, SMT жуёт только недетерминированную часть
- Unproven — не тупик: в домене корректности пишется функция-доказательство (возвращаемый тип —
  утверждение), в домене завершения в позиции типа задаётся мера (§6.9) — оба верифицируются
  проверкой типов
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + показ контрпримеров + отчёт о потреблении бюджета + недоказанные
  утверждения + подсказки (если компилятор может их дать)

## Открытые вопросы

- [x] **Доступность Z3 для цели wasm32**: под wasm нет Z3 (весь SMT-код исключён через
      `cfg(not(target_arch = "wasm32"))`). Область воздействия и направление деградации: -
      `ownership.rs` `smt_cut` всегда возвращает `false` → прохождение обратной рёберной точки →
      **консервативный отказ** (sound-направление, лишь меньше сужений) - Стратегия 1 проверки
      завершения, уровни предикатов 2b/3 пропускаются целиком В настоящее время **недостижимо**:
      `TypeEnvironment::predicate_defs` в production никогда не заполняется (только в тестах),
      `parser` не порождает `MonoType::Refined`, поэтому путь уточнённых предикатов в production не
      существует; точка инъекции стратегии 1 проверки завершения (`TerminationChecker::with_solver`)
      в production никогда не вызывается, native также не выполняется. Поэтому фактическое различие
      поведения wasm и native — лишь **в точности `smt_cut`**, не затрагивает soundness. Если в
      будущем потребуется включить Z3 для wasm, варианты и стоимость см. в issue #376 (вывод:
      предпочтительно использовать экземпляр Z3 на стороне JS, а не линковать Z3 в основной wasm —
      последнее требует смены системы сборки emcc и раздувает артефакт с 3 MB до ~20 MB).
- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, наиболее широко проверен). CVC5 как
      SMT-LIB-совместимая альтернатива, переключение флагом компилятора. Внутренняя цель трансляции
      компилятора — стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, без
      специального универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решателя**: шаги 10 000 / время 100ms / глубина инстанцирования
      кванторов 3. Зафиксировано внутри компилятора, без настраиваемых параметров. Если в реальном
      использовании найдётся подтверждённый случай нехватки (не «пользователь написал неправильно»),
      значения будут скорректированы.
- [x] **Область поддержки кванторов**: язык не ограничивает порядок кванторов. Компиляционные
      предикаты принимают параметры типа — Type включает функциональные типы — поэтому кванторы
      высокого порядка — естественное следствие системы типов, без специального синтаксиса.
      SMT-решатель может автоматически разрешать кванторы первого порядка (forall/exists,
      поддерживается чередующееся вложение, ограничено глубиной бюджета 3). Кванторы высокого
      порядка: SMT возвращает Unproven, компилятор предлагает «этот предикат выходит за пределы
      автоматического доказательства, предоставьте функцию-доказательство». Программист пишет
      функцию на YaoXiang, чей возвращаемый тип равен утверждению — проверка типов верифицирует
      функцию. Никакого внешнего экспорта, никакого ИИ, никакого интерактивного режима
      доказательства. Всё — код на YaoXiang, всё верифицируется проверкой типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена SMT-переменных (с префиксом модуля во избежание конфликтов). Модель Z3 возвращается с
      обратным поиском по именам. Формат вывода: имя_переменной = конкретное_значение + позиция в
      исходном коде + позиция определения предиката. Без сложного слоя отображения.
- [x] ~~**Взаимодействие компиляционных предикатов со смарт-указателем `ref`?**~~ → Решено:
      компиляционные предикаты допускают только неизменяемые заимствования или значения с переданным
      владением. Значения по изменяемому заимствованию не могут появляться в компиляционных
      предикатах.
- [x] **Расширение счётчика нарушений `forall` на несоседние операции?** → Не расширяется. Текущая
      область покрытия (соседний обмен, соседние перемещения) дополняется стратегией 1 (линейная
      ранговая функция) — сжатие внешнего интервала быстрой сортировки покрывается стратегией 1,
      пирамидальная сортировка — стратегией 1 (паттерн индексов массива). Циклы, завершаемость
      которых не доказуема ни одной стратегией, компилятор отвергает напрямую — это философия
      жёсткой безопасности, а не дефект. Если в будущем появится реальный сценарий (не академическая
      конструкция), для которого недостаточно всех четырёх стратегий, вопрос будет пересмотрен. →
      **Пересмотр инициирован (2026-09-14, #318)**: неструктурная рекурсия (gcd-подобные случаи с не
      непосредственным убыванием, взаимная рекурсия, слияние разделения) — именно тот реальный
      сценарий, который предвидело данное положение — последовательность шаблонов исследования меры
      не может автоматически справиться с ними, и они не могут быть переписаны в анализируемые
      шаблоны итерации без потери читаемости. Вывод: философия жёсткой безопасности остаётся
      (неправильная мера по-прежнему отвергается SMT-контрпримером, человек может не суметь
      доказать, но не может доказать неверно), но «не нашёл — отвергаю» смягчается до «не нашёл —
      программист может задать меру явно в позиции типа» — см. §6.9.
- [x] **Комбинаторный взрыв при перечислении линейной ранговой функции**: верхний предел
      перечисления кандидатов — 3 переменные с границами. ≤3 — перечисляются все линейные комбинации
      с индивидуальной SMT-верификацией. >3 — только однофакторные меры (`v_i`, `u_i - v_i`), при
      неудаче — прямая ошибка компиляции — подсказка программисту «в цикле более 3 переменных с
      границами, компилятор не может автоматически синтезировать многомерную меру». Это не
      инженерный компромисс — это принуждение программиста к более простым циклам.
