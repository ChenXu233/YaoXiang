# RFC-027: Компиляционные предикаты и единая статическая верификация

> — устарел

## Резюме

В данном документе предлагается ввести в YaoXiang **компиляционные предикаты** как полноправных
граждан, объединив всю статическую верификацию времени компиляции в единый **конвейер
доказательств**. Компиляционный предикат — это не внешний спецификационный комментарий, это функция.
Функция, возвращающая Type, может использоваться в позиции типа, и компилятор вызывает её во время
компиляции и проверяет возвращаемое значение. Тип есть утверждение, вычисление во время компиляции
есть доказательство.

**Ключевой тезис**: единственная задача проверки типов во время компиляции — построить и проверить
термы доказательств. Равенство типов, конфликты токенов, редукция зависимых типов, вычисление
компиляционных предикатов, импликации логики Хоара — всё это разные проверки типов в конвейере
доказательств, разделяющие один путь. SMT-решатель является ускорителем проверки типов, а не
независимым корнем доверия. Когда компилятор возвращает Unproven, программист пишет функцию YaoXiang
в качестве доказательства — проверка типов верифицирует её точно так же, как верифицирует любой
возвращаемый тип функции. Всё есть код YaoXiang, всё верифицируется проверкой типов.

## Мотивация

### Почему RFC-022 устарел?

В RFC-022 спецификации были оформлены в виде комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это комментарий, отдельный от типа
    //! ensures: ExistsMax(result, arr[0..n])   ← это комментарий, отдельный от типа
}
```

Здесь была допущена фундаментальная ошибка относительно изоморфизма Карри-Ховарда: **разделение
спецификации и типа на два слоя**. Комментарий — это не тип. Комментарий не участвует в проверке
типов. Комментарии — это ментальная модель «внешнего инструмента».

В белой книге чётко сказано:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Комментарии `//!` из RFC-022 — это внешний синтаксис, отделённый от системы типов
- Спецификационные типы и обычные типы образуют две раздельные системы, порождая концептуальную
  избыточность
- Разделение «Debug Build с верификацией / Release Build без верификации» нарушает единство
- SMT-решатель в традиционном восприятии позиционируется как внешний инструмент — в YaoXiang он
  встроен как ускоритель проверки типов
- Проверка типов, верификация заимствований, проверка компиляционных предикатов, раскрытие макросов
  идут каждый своим путём

### Корректная ментальная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация компиляционных предикатов — являются подзадачами этой функции. Они разделяют один
конвейер доказательств и различаются только сложностью терма доказательства и стратегией его
построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство, чей
возвращаемый тип равен доказываемому утверждению. Проверка типов верифицирует её. Это та же
операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип есть утверждение, верификация есть проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри есть утверждения, и
компилятор гарантирует, что каждое из них истинно — либо автоматически доказывает, либо программист
предоставляет функцию-доказательство.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  Компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  Компилятор гарантирует, что data — Array(T)
```

**Дженерики — частный случай компиляционных предикатов.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в сигнатуре   внутри {} только утверждения
#          компилятор при вызове во время компиляции верифицирует x > 0

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре  компилятор верифицирует type_of(T) == Type, type_of(data) == Array(T)
```

Тот же шаблон: `name: (params) -> Type = { утверждения }`. Компилятор не различает «утверждения о
типе» и «утверждения о значении» — всё это цели вычисления в конвейере доказательств.

**Инварианты цикла не нужно записывать отдельно. Аннотация типа на переменной — это инвариант
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i — компилятору: тип s зависит от i
    mut i: UpTo(arr.len) = 0     # При инициализации i=0, верифицируется: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # Компилятор верифицирует: s_new == sum(arr[0..i+1])
        i += 1       # i изменён → запускается ре-валидация зависимостей s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует для тела цикла одно условие верификации — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. Конвейер
доказательств верифицирует индуктивный шаг, после чего все итерации покрываются автоматически. Не
нужны ни `: decreases`, ни `: Invariant`, ни индуктивное доказательство — компилятор разбивает
индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: компиляционные предикаты в типах параметров и возвращаемого значения

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Компиляционные предикаты становятся
аннотациями типов параметров или возвращаемого значения.

**На стороне параметров это вызов функции.** Компиляционный предикат — это функция, возвращающая
Type; использование на стороне параметра есть её вызов — как и `factorial(5)`. На стороне
возвращаемого значения вводится новое понятие: формальный параметр возвращаемого значения.

```yaoxiang
# Предусловие: компиляционный предикат явно вызывается в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive
#                       Компилятор в точке вызова извлекает значение аргумента, подставляет b, верифицирует Positive(аргумент)
#                       Пример: divide(10, 2) → верифицирует Positive(2) = { 2 > 0 } → True
#                       Пример: divide(10, 0) → верифицирует Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + компиляционный предикат
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возвращаемого значения, значение задаётся return
#                                            Компилятор в точке return подставляет возвращаемое значение, верифицирует постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **Сторона параметров**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся в
  `Positive` как аргумент. Синтаксис вызова функции, никаких неявностей.
- **Сторона возврата**: `-> (result: IsMax(T, arr, result))` — `result` — формальный параметр
  возвращаемого значения, значение задаётся оператором `return`. `result` существует только в
  сигнатуре типа, только упоминается в предикатах, не попадает в область видимости тела функции, не
  виден вызывающему.
- **Формальный параметр возврата необязателен**: при отсутствии постусловия он не пишется, сигнатура
  полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: формальные параметры параметров и возвращаемого значения — одно и то же понятие —
  `имя: вызов_предиката(имя)`, различающееся лишь тем, кто задаёт значение — вызывающий или
  `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

Когда компиляционный предикат используется в позиции связывания, аргументы передаются программистом
явно. Когда значение времени выполнения попадает в параметр уточняющего типа, компилятор завершает
верификацию посредством сбора путевых условий и импликации в SMT — без явной передачи доказательства
от программиста.

#### 3.1 Явный вызов функции

Когда компиляционный предикат используется в позиции связывания, аргументы передаются программистом
явно — это вызов функции, без неявностей.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор компиляционного предиката. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — это вызов функции
// После нормализации: b: { b > 0 }
```

Компилятору не нужно неявно подставлять аргументы — `b: Positive(b)`, как и `f(5)`, — это вызов
функции. `b` связывается как имя параметра, и его аннотация типа `Positive(b)` ссылается на сам `b`
— это стандартный паттерн зависимых типов, а не неявное правило раскрытия.

**Единство с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а лишь имя
параметра по соглашению («написать `p`, `this`, `x` — эффект тот же»). `b: Positive(b)` использует
тот же механизм — имя параметра может упоминаться в аннотации типа. `self` появляется в позиции
`self: Point`, `b` — в позиции `b: Positive(b)`, обе аннотации ссылаются на сам параметр. Различие
только в сложности аннотации, механизм полностью идентичен — после связывания имени тип может
зависеть от этого имени.

Возвращаемый тип также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возврата, Sorted(result) — вызов функции
//                        Компилятор в точке return подставляет возвращаемое значение в result, верифицирует Sorted(значение)
```

Аналогично для объявлений локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевое условие, формируя **множество гипотез** для текущей области видимости. Эти гипотезы
выступают фоновыми знаниями при вычислении Bool во время компиляции.

```yaoxiang
if y > 0 {
    // Компилятор автоматически получает в этой ветви гипотезу: { y > 0 }
    let result = divide(x, y)
    // Условие верификации: (y > 0) ⇒ (y > 0)
    // Конвейер доказательств устанавливает импликацию → Proved
} else {
// В этой ветви гипотеза: { not (y > 0) }
// При вызове divide(x, y) условие верификации: not (y > 0) ⇒ y > 0
    // Конвейер устанавливает, что импликация неверна → Disproved
}
```

Это не зашитое в компилятор специальное правило — это естественное поведение конвейера
доказательств. Каждая проверка типа в точке вызова отправляет в конвейер:

```
{фоновые гипотезы} ⇒ {цель верификации}
```

Конвейер доказательств устанавливает истинность импликации. Proved → пройдено, Disproved → ошибка
компиляции + контрпример, Unproven → ошибка компиляции + неразрешённое утверждение. Фоновые гипотезы
берутся из путевого условия текущей программной точки.

#### 3.3 Стек гипотез

Компилятор при анализе потока управления поддерживает для каждого базового блока множество гипотез:

- **if-guard**: `if y > 0` → в true-ветвь помещается `y > 0`, в false-ветвь помещается `not (y > 0)`
  (если есть else)
- **паттерн match**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **логические связки**: `if x > 0 and y < 10` → в ветвь помещаются `x > 0` и `y < 10`
- **предусловие функции**: при вызове `divide(a, b)` доказательство того, что `b` удовлетворяет
  `Positive`, берётся либо из текущих гипотез, либо из самой аннотации уточняющего типа аргумента
  (если `b` аннотирован как `Positive`, его тип несёт `b > 0`)
- **присваивание**: при `let z = y` существующие уточняющие условия `y` переносятся на `z`

Все гипотезы поступают в конвейер доказательств. При переходе на ускоренный SMT-путь они
транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Без статического свидетельства — ошибка компиляции

Если программист просто напишет:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей программной точке нет гипотезы `y > 0`, и сам аргумент `y` не имеет аннотации `Positive`.
Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация неверна) → ошибка компиляции:

> Невозможно доказать, что параметр `b` в вызове `divide` удовлетворяет `Positive`. `y` поступает из
> входных данных функции, доказанных границ не имеет. Рассмотрите охрану вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не допускает прямого попадания значений времени выполнения в параметры уточняющего типа без
статического свидетельства. Это не ограничение — это ядро философии жёсткой безопасности. Всё, что
компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Связь с единым конвейером

Распространение путевых условий — не дополнительный механизм. Это прямое продолжение конвейера
доказательств в анализе потока управления:

| Этап                          | Обязанности                                                                                                                                                      |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий          | Фаза анализа потока управления компилятора, аннотирующая каждый базовый блок множеством гипотез                                                                  |
| Генерация условий верификации | При столкновении с ограничением типа, требующим верификации, объединяет путевые условия и информацию о типе аргумента                                            |
| Вычисление в конвейере        | Ядро компилятора → SMT-ускорение → Proved / Disproved / Unproven                                                                                                 |
| Результат                     | `Proved` → пройдено; `Disproved` → ошибка + контрпример; `Unproven` → ошибка + неразрешённое утверждение (программист может предоставить функцию-доказательство) |

Новых компонентов нет. Особых правил нет. Путевое условие — это фоновые знания конвейера
доказательств, разделяющие с равенством типов и ограничениями заимствования один путь и одну систему
бюджетов.

### 4. Конвейер доказательств времени компиляции

Все проверки времени компиляции разделяют единый конвейер. Центральная операция конвейера —
**проверка типа**: проверка равенства типа терма доказательства доказываемому утверждению. Всё есть
проверка типа.

```
При компиляции встречается выражение Bool, требующее вычисления (т.е. требуется построить терм доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → Компилятор решает напрямую (структурная эквивалентность)
        │
        ├── Условие конфликта токенов (!conflicting(tokens))
        │   → Потоково-чувствительный анализ живучести (отслеживание Dup/Linear)
        │
        ├── Редукция зависимых типов (n + m упрощается)
        │   → Система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Компиляционный предикат (x > 0, forall...)
        │   → Ядро компилятора + SMT-модуль ускорения
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → Ядро компилятора + SMT-модуль ускорения
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → Компиляция проходит
             │ Disproved│  → Ошибка компиляции + контрпример
             │ Unproven │  → Ошибка компиляции + неразрешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код YaoXiang)
                  │
                  ▼
         Проверка типов верифицирует ──→ Proved ──→ Компиляция проходит
                  │
                  ▼
            Верификация не прошла → Ошибка компиляции: «Доказательство несостоятельно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — неизбежное следствие проблемы остановки и
естественное деление теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → остановка, терм доказательства построен, проверка типов пройдена. Компиляция
  продолжается.
- **Disproved(M)** → остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходнике.
- **Unproven** → в пределах заданного ресурсного лимита терм доказательства не построен. Ошибка
  компиляции + неразрешённое утверждение + отчёт о потреблённом бюджете.

**Unproven ≠ False.** Когда компилятор говорит «я не могу это доказать», это не означает ложность
утверждения — лишь то, что оно выходит за пределы текущих возможностей автоматического
доказательства. Это честность, а не дефект.

Жёсткое ограничение бюджета — инженерное решение проблемы остановки. Без ручек — наличие ручки
означало бы вопрос пользователю «как вы думаете, ваша программа остановится?», а пользователь не
знает, и компилятор тоже.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверка типов
верифицирует эту функцию — тем же механизмом, что и `add(a, b): Int`.

```
Утверждение = Тип
Доказательство = Программа (значение этого типа)
Верификация = Проверка типов (единственный корень доверия)
```

SMT-решатель — не независимый корень доверия, а **ускоритель проверки типов**. SMT помогает найти
доказательство, но верифицирует его проверка типов. Когда SMT возвращает `unsat`, компилятор
реконструирует результат в виде терма доказательства, верифицируемого проверкой типов. Если
реконструкция не удалась (шаги вывода SMT выходят за пределы правил вывода ядра компилятора),
происходит откат к Unproven — программист может вручную написать функцию-доказательство.

```yaoxiang
# Утверждение: уточняющее свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип — утверждение выше
# Проверка типов верифицирует эту функцию — точно так же, как верифицирует add(a, b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # Компилятор верифицирует здесь: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Никакого ИИ, никакого экспорта в Coq, никаких новых концепций. **Свойства, которые не удаётся
доказать автоматически во время компиляции → программист пишет доказательство в коде YaoXiang →
проверка типов верифицирует.** Весь процесс — плавный градиент: компилятор берёт на себя простые
доказательства, оставляя сложные программисту.

#### 4.3 Слоистая зависимость внутри конвейера

Перечисленные вычислители используют общий интерфейс, но упорядочены по вычислению. Равенство типов
— предпосылка всего последующего анализа; проверка владения/токенов зависит от информации о типах;
верификация уточняющих предикатов зависит от результатов первых двух слоёв. Компилятор вычисляет по
слоям: выражения, не прошедшие нижний слой, не попадают в верхний — это избавляет от расхода бюджета
решения на типобезошибочных программах.

```
Порядок вычисления (один конвейер, слоистая диспетчеризация)
├── Слой 0: равенство типов (T1 == T2)
│   └── Структурная унификация → при провале дальнейшее бессмысленно, сразу Disproved
├── Слой 1: конфликты владения/токенов
│   └── Потоково-чувствительный анализ живучести → при провале безопасность памяти не выполняется, сразу Disproved
└── Слой 2: уточняющие предикаты / импликации Хоара
    └── Ядро компилятора → SMT-ускорение → Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя общий интерфейс и общую
систему бюджетов.

### 5. Единство трёх слоёв функций

| Слой                    | Момент выполнения | Вход         | Выход    | Пример                                         |
| ----------------------- | ----------------- | ------------ | -------- | ---------------------------------------------- |
| Функция-значение        | Время выполнения  | значения     | значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типов       | Время компиляции  | тип/значение | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Компиляционный предикат | Время компиляции  | значение     | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют одинаковый синтаксис `name: type = value`. Компиляционные предикаты и конструкторы
типов идут по одному конвейеру доказательств — `{}` есть пространство доказательств.

### 6. Циклы: генерация условий верификации Флойда-Хоара

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Компиляционный
предикат в аннотации типа переменной задаёт утверждение в стиле Флойда-Хоара — компилятор генерирует
из аннотации типа условия верификации, а конвейер доказательств проверяет, сохраняет ли каждое
присваивание тип.

Ключевой механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`, условие
верификации — `P ⇒ Q[e/x]`. Компилятор генерирует для тела цикла одно условие верификации — после
того, как конвейер доказательств верифицирует индуктивный шаг, все итерации покрываются
автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i; при инициализации i=0, верифицируется: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # Верифицируется: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует для тела цикла одно VC. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не меняется)
        #   Подставляя s_new = s_old + arr[i]:
        #     Нужно s_old + arr[i] == sum(arr[0..i+1])
        #     Из индуктивной гипотезы s_old == sum(arr[0..i]), прибавив к обеим сторонам arr[i]:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменён → в графе зависимостей аннотация типа s ссылается на i → запускается ре-валидация
        #   Новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   То есть s == sum(arr[0..i_new]), гарантируется предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # В этот момент s: SumUpTo(arr, arr.len), то есть s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной: программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант и не нужно «делать индукцию
автоматически» — он разбивает индуктивное доказательство на локальные условия верификации для
каждого присваивания, передавая их в конвейер доказательств по принципу «разделяй и властвуй».

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка описанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i`; когда `i` меняется, ограничение типа `s` тоже меняется. Это требует от компилятора
поддерживать **граф зависимостей типов между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# Ключ — зависимая переменная, значение — множество переменных, чьи аннотации типа ссылаются на эту переменную
# Пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: при обработке `mut v: Pred(... x ...) = init` проверка типов разбирает свободные
переменные в аргументах `Pred(...)`. Если в аргументах встречается ссылка на другую изменяемую
переменную `x` из текущей области видимости, в графе зависимостей регистрируется `x → v`.

**Срабатывание**: когда зависимая переменная `x` получает присваивание, компилятор:

1. Находит в графе зависимостей все переменные `{v₁, v₂, ...}`, зависящие от `x`
2. Для каждой `v` генерирует условие верификации: удовлетворяет ли текущее значение `v` обновлённому
   типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательств

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественным образом требует
корректного порядка присваиваний. Для `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменён → ре-валидация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # i изменён → ре-валидация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Составные зависимости**: переменная может зависеть от нескольких переменных. Аннотация
`{ v: Int; v == x + y }` одновременно зависит от `x` и `y` — изменение любой из них запускает
ре-валидацию.

**Связь с конвейером доказательств**: отслеживание зависимостей — триггер генерации VC, а не
самостоятельный механизм верификации. Оно отвечает на вопрос «когда нужно генерировать VC», конвейер
доказательств — на вопрос «выполняется ли VC».

### 7. Проверка завершаемости

Полностью автоматически во время компиляции. Циклы, которые компилятор может доказать, проходят; те,
которые доказать не может, сразу дают ошибку компиляции — программист обязан сделать цикл
анализируемым компилятором. Полуавтоматических аннотаций не предусмотрено.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершаемости, из двух
источников:

1. **Аннотации типов переменных**: граничные ограничения в уточняющих типах (например, `UpTo(n)`
   даёт верхнюю границу `n` и нижнюю `0`)
2. **Операции в теле цикла**: операции, применяемые к переменным на каждой итерации

Компилятор перебирает четыре стратегии синтеза меры в порядке приоритета и останавливается на первой
успешной.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию с линейной границей, компилятор перечисляет кандидатов линейных мер
и верифицирует их в SMT.

```
Вход:
  Переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с верхней и нижней границами)
  Условие цикла cond
  Множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типа: [low_i, high_i]
  2. Перечислить кандидатов мер: v_i, u_i - v_i, v_i - v_j и т.д. (линейные комбинации)
  3. Для каждого кандидата m:
     - SMT верифицирует m ≥ 0 (из типовых границ)
     - Для каждого пути исполнения в теле цикла SMT верифицирует m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершаемость доказана
```

Покрытие: любой цикл, в котором переменной присваивается линейное выражение (`v = a·v + b`) и есть
аннотация граничного типа. Включает `i += const`, `i -= const`, а также сжатие интервалов в двоичном
поиске:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# Мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: счётчик нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия; решение о включении принимается по результатам
> реализации фазы 3.** Стратегия работает для соседних обменов (сортировка пузырьком, сортировка
> вставками), но не работает автоматически для несоседних операций (partition быстрой сортировки,
> sift-down пирамидальной). Границы покрытия — в таблице ниже. Если фаза 3 покажет невозможность,
> стратегия будет удалена или отложена.

Ключевое наблюдение: **спецификация, написанная пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  Целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  Операции в теле цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операции на меру:
     - Обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - Затрагивает только пары с индексами j-1, j, j+1
     - Если arr[j] > arr[j+1] (нарушение предиката), после обмена пара удовлетворяет предикату
     - violation_count уменьшается минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя: 0
  → Завершаемость доказана
```

**Текущее покрытие**:

| Алгоритм                 | Паттерн операции | Стратегия 2 доказуема? | Причина                                               |
| ------------------------ | ---------------- | :--------------------: | ----------------------------------------------------- |
| Сортировка пузырьком     | Обмен соседних   |           ✅           | violation_count строго убывает на каждом обмене       |
| Сортировка вставками     | Соседние сдвиги  |           ✅           | Каждый сдвиг устраняет одну нарушающую пару           |
| Сортировка выбором       | Несоседний обмен |           ❌           | Один обмен может увеличить violation_count            |
| Быстрая сортировка       | Partition        |           ❌           | Несоседний обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | Sift-down        |           ❌           | Древовидная операция, violation_count немонотонна     |

**Дополняющие стратегии**: для быстрой сортировки сжатие интервала `low < high` покрывается
стратегией 1 (линейная ранговая функция) — внешняя partition-рекурсия каждый раз сжимает интервал
вдвое. Стратегии 1 и 2 дополняют друг друга, и завершаемость большинства реальных алгоритмов
доказуема одной из них. Но обобщение стратегии 2 (несоседние операции, древовидные операции)
остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: паттерн ограниченного инкремента/декремента

`v += const` (с положительной const), у переменной есть аннотация верхней границы → мера
`upper_bound - v` уменьшается на `const` за итерацию, нижняя граница 0. Это вырожденный случай
стратегии 1, обрабатывается компилятором в первую очередь.

#### 6.5 Стратегия 4: шаблон меры с мультипликативным масштабированием

`v *= const` (const > 1), у переменной есть аннотации верхней и нижней границ. Компилятор использует
встроенный логарифмический шаблон `ceil(log_const(upper/v))`, мера уменьшается на 1 за каждое
умножение на const.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # Компилятор автоматически выводит: мера ceil(log₂(n/i)), каждое умножение на 2 уменьшает меру на 1
    i *= 2
}
```

#### 6.6 Разделение завершаемости и корректности

Доказательство завершаемости и доказательство корректности независимы:

- **Завершаемость**: четыре стратегии выше автоматически доказывают, что цикл завершается за
  конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером доказательств
  через условия верификации

Оба пройдены → компиляция успешна. Завершаемость доказана, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершаемость не доказуема → ошибка компиляции с
указанием переменной или операции, которую не удалось проанализировать. Оба не пройдены → ошибка
компиляции с раздельным указанием обеих причин.

#### 6.7 Проверка завершаемости рекурсивных функций

Для рекурсивных функций, вычисляемых во время компиляции, компилятор проверяет убывание аргумента:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Компилятор анализирует: n-1 < n → убывает → завершается
}

# Использование во время компиляции — компилятор гарантирует, что factorial завершится на этапе компиляции
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, вычисляется во время компиляции
```

| Сценарий                                                           | Поведение                           |
| ------------------------------------------------------------------ | ----------------------------------- |
| Компилятор может установить рекурсивное убывание (например, `n-1`) | Вычисление во время компиляции      |
| Не убывает / убывание неразрешимо                                  | Ошибка компиляции                   |
| Вызов во время выполнения (не в позиции типа)                      | Проверка завершаемости не требуется |

#### 6.8 Жёсткая граница

`i = f(i)`, где `f` необратима, не замкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершаемость. Ошибка компиляции:

> Не удаётся автоматически доказать завершаемость этого цикла. Переменная цикла зависит от
> неанализируемой функции `f`. Используйте шаблон итерации, доступный для анализа компилятором.

Это не провал компилятора. Всё, что нельзя статически доказать безопасным, не проходит компиляцию.

### 8. SMT-решатель: ускоритель проверки типов

В традиционных языках SMT-решатель — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang он — **ускоритель проверки типов**, вызываемый только тогда, когда ядро компилятора
не может принять решение напрямую. SMT помогает найти доказательство, но верифицирует его проверка
типов.

**Модель доверия**: проверка типов — единственный корень доверия. SMT-решатель — модуль ускорения,
он помогает находить доказательства, но SMT не является независимым корнем доверия. Компилятор
доверяет результату Z3 `unsat` (как и в подходе F\*/Dafny — вероятность ошибки Z3 ниже вероятности
ошибки в самом компиляторе, что инженерно оправдано). Реальная ненадёжность контролируется на уровне
трансляции в SMT — баг в трансляции проявится в других тестах компилятора.

**Интерфейс**: внутри компилятор транслирует в стандартный формат SMT-LIB 2.6, не привязываясь к API
конкретного решателя. SMT-LIB — стандарт ISO, Z3, CVC5, MathSAT, Yices поддерживают его нативно.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, самая обширная документация и валидация сообществом).
CVC5 — совместимая с SMT-LIB альтернатива; переключение через флаг компилятора.

Не делаем «универсальный слой абстракции решателя» — SMT-LIB и есть слой абстракции. Если в будущем
CVC5 добьётся прорыва в определённой теории, переключение — это смена бинарника, без правок в коде
компилятора.

```
Выражение Bool времени компиляции
        │
        ├── Ядро компилятора может решить напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → Сразу возвращает Proved / Disproved
        │
        └── Ядро компилятора не может решить напрямую (кванторы, символьные переменные)
            → Пре-редукция зависимых типов (factorial(5) → 120)
            → Трансляция в формат SMT-LIB
            → Отправка в Z3/CVC5 (с лимитом бюджета)
            → Возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткое ограничение, как глубина стека**:

| Измерение бюджета                 | Значение по умолчанию | Описание                                                                                                                                                          |
| --------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10 000                | Z3 обычно укладывается в сотни шагов для линейной арифметики. 10 000 шагов покрывают 99% реальных предикатов.                                                     |
| Время                             | 100 мс                | Один предикат дольше 100 мс = пользователь пишет программу времени компиляции, а не аннотацию типа. 100 мс × 50 предикатов = 5 секунд верхней границы компиляции. |
| Глубина инстанцирования кванторов | 3                     | Три уровня вложенных кванторов покрывают реальные паттерны. Свыше трёх — скорее всего, логическая головоломка.                                                    |

Превышение бюджета → Unproven, ошибка компиляции + позиция предиката + потребление. Никаких
понижений, никаких проверок времени выполнения, никакого silent pass.

**Почему это практически работает**: 95% реальных предикатов — линейная арифметика: `x > 0`,
`arr.len > 0`, `0 <= idx < arr.len` — всё в разрешимом фрагменте, SMT-решатели возвращают за
миллисекунды. Для редких сложных предикатов, превышающих бюджет, программист пишет
функцию-доказательство.

Зависимые типы перед вызовом SMT проходят пре-редукцию: `factorial(5)` вычисляется во время
компиляции в `120`, `append([1,2], [3])` — в `[1,2,3]`. Эти детерминированные вычисления не
расходуют бюджет SMT.

Программисту не нужно знать о существовании SMT. Ментальная модель: **если компилятор может доказать
— проходит; если не может — сообщает об ошибке; если компилятор не умеет, можно написать
функцию-доказательство.**

### 9. Композиция компиляционных предикатов

Компиляционный предикат — это функция, возвращающая Type; композиция естественно реализуется через
композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ Компилятор верифицирует Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ Компилятор верифицирует Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ Компилятор верифицирует InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ Компилятор верифицирует InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Циклы: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: единство компиляции и времени выполнения

`assert` и `Assert` — две стороны одного уточняющего примитива. Конвейер диспетчеризации `dispatch`
автоматически решает, идти ли по пути доказательства во время компиляции или по пути проверки во
время выполнения, в зависимости от **достижимости свободных переменных предиката во время
компиляции**:

| Критерий                                                                                                   | Режим           | Поведение                                                                                                          |
| ---------------------------------------------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------ |
| Все свободные переменные известны во время компиляции (параметры дженериков, константы времени компиляции) | **CompileTime** | В конвейер доказательств: Proved → стирается, Disproved → ошибка компиляции, Unknown → требуется доказательство    |
| Есть свободные переменные из времени выполнения (параметры функции, внешний ввод, mut-переменные)          | **Runtime**     | Вставляется проверка времени выполнения, в потоково-чувствительное множество гипотез Γ добавляется уточняющий факт |

**Ключевое**: «не удалось различить» ≠ «опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихого понижения); в режиме Runtime утверждение во время компиляции вообще не
имеет истинностного значения — никакой prover не напишет общезначимого доказательства для
«пользователь мог ввести отрицательное число», проверка времени выполнения — единственный
soundness-выбор. Это не слабость prover, а теоретическая неизбежность.

### 12. Потоково-чувствительное множество гипотез Γ: распространение сильнейшего постусловия

Компилятор поддерживает потоково-чувствительное (flow-sensitive) множество гипотез Γ, отслеживающее
истинные утверждения в каждой точке потока управления.

**SP-распространение (сильнейшее постусловие)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP-распространение
```

**kill set для mut-переменных**: после повторного присваивания `mut`-переменной все гипотезы,
относящиеся к ней, удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 удалено
```

Это жёсткое требование soundness — значение переменной изменилось, старые гипотезы недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение гипотез ветвей. Из
ветви выносятся только те утверждения, которые истинны на всех путях.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточняющие типы полностью стираются во время выполнения» относится к **proof
witness (свидетельству доказательства)** — термы доказательства, верифицированные во время
компиляции, не порождают кода времени выполнения. Но проверки времени выполнения, вставленные
dispatch в режиме Runtime, сохраняются — это Bool-проверки на уровне значений, а не witness на
уровне типов.

Резюме: witness стирается, check сохраняется. Эти две вещи не противоречат друг другу, исходный
тезис RFC-027 остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| Ранее (RFC-022)                       | Теперь (данный RFC)                                                                           |
| ------------------------------------- | --------------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Компиляционный предикат как тип параметра `(b: Positive(b))`                                  |
| `//! ensures: ExistsMax(result, arr)` | Возвращаемый тип использует формальный параметр возврата `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Аннотация типа переменной компиляционным предикатом — инвариант Флойда-Хоара                  |
| `//! decreases: n`                    | Компилятор полностью автоматически выводит функцию меры                                       |
| Спецификация — комментарий            | Спецификация — система типов                                                                  |

### Синтаксис

**Для компиляционных предикатов нет новых ключевых слов.** `{}` — пространство доказательств,
полностью совместимо с существующим синтаксисом определения типов. Компиляционный предикат — это
функция, возвращающая Type: `name: (params) -> Type = { утверждения }`. Использование — вызов
функции: `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Компиляционный предикат = функция, возвращающая Type, внутри {} — верифицируемые компилятором утверждения
# Используется существующий синтаксис функций/типов, новые правила BNF не нужны
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Новое синтаксическое понятие: формальный параметр возвращаемого значения** — в `-> (name: Type)`
`name` является формальным параметром возврата.

Формальный параметр возвращаемого значения — **единственное** синтаксическое понятие, вводимое в
YaoXiang поверх существующего синтаксиса функций. Его семантика:

- Значение `name` задаётся оператором `return`
- `name` существует только в сигнатуре типа, на него ссылаются постусловия (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не попадает в область видимости тела функции, не виден вызывающему
- Формальный параметр возврата **необязателен** — при отсутствии постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), без дополнительной нагрузки

Причина введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть». Без
формального параметра возврата компилятор мог бы использовать лишь специальные правила (неявная
переменная `$result` или `__retval__`). Формальный параметр возврата делает эту ссылку явной — это
просто формальный параметр, значение которого задаётся `return`, а не вызывающим.

**Функция-доказательство** — не новое понятие, это функция YaoXiang, чей возвращаемый тип —
доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверка типов верифицирует её тем же способом, что и любой возвращаемый
тип. Никакого нового синтаксиса, ключевых слов, правил.

### Влияние на систему типов

- **Вселенная типов**: компиляционные предикаты располагаются на уровне Type₂ — функции, принимающие
  значения и возвращающие Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с дженериками**: компиляционные предикаты могут принимать параметры дженериков,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в компиляционных предикатах подчиняются правилам
  владения, только чтение, не запись
- **Вывод типов**: аргументы компиляционных предикатов участвуют в выводе типов по Хиндли-Милнеру

### Представление во время выполнения

Компиляционные предикаты во время выполнения обрабатываются **по результату диспетчеризации
dispatch**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): после прохождения
  доказательства свидетельство (witness) полностью стирается.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представляется как `Int`. Уточняющее условие `{ 5 > 0 }` уже проверено, стирается.
- **Режим Runtime** (есть свободные переменные времени выполнения): сохраняется проверка времени
  выполнения — Bool-проверка на уровне значений, добавляемая в потоково-чувствительное множество
  гипотез Γ. См. §11 конвейер диспетчеризации dispatch и §13 уточнение модели стирания.

Использование компиляционного предиката в позиции типа (например, `f(x: Positive(x))`) не порождает
обёрточного типа, не выделяет дополнительной памяти. Но если `x` поступает из ввода времени
выполнения, **выполняется** вставка Bool-проверки времени выполнения.

**Ограничения взаимодействия с `ref`**: компиляционные предикаты могут ссылаться только на
неизменяемые заимствования или значения, владение которыми уже передано. Ссылки на значения,
находящиеся под изменяемым заимствованием, недопустимы в компиляционных предикатах — компилятор не
может гарантировать во время компиляции, что результат верификации останется корректным во время
выполнения. Подобное использование сразу даёт ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: компиляционные предикаты используют стандартный синтаксис функций, дополнительные
   правила разбора не нужны
2. **Конвейер доказательств**: единый интерфейс возврата Proved/Disproved/Unproven, автоматический
   выбор стратегии
3. **SMT-модуль ускорения**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, альтернатива
   CVC5
4. **Ядро проверки типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение квантора всеобщности. Это единственный корень доверия; и SMT, и
   доказательства программиста проходят через него
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёт о неразрешённых утверждениях +
   привязка к позициям в исходнике

### Обратная совместимость

- ✅ Код, не использующий компиляционные предикаты, остаётся полностью без изменений
- ✅ Компиляционные предикаты в режиме CompileTime дают нулевую нагрузку во время выполнения, в
  режиме Runtime сохраняются лишь необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован, бремя
  миграции отсутствует

## Компромиссы

### Преимущества

- **Полное воплощение изоморфизма Карри-Ховарда**: тип есть утверждение, программа есть
  доказательство, `name: Proposition = Proof`
- **Единство**: компиляционные предикаты и обычные функции используют полностью идентичный
  синтаксис, без концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, ментальная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного компиляционного предиката, постепенно расширяя
  покрытие
- **Минимальная нагрузка во время выполнения**: режим CompileTime — ноль накладных расходов, режим
  Runtime — только необходимые Bool-проверки

### Недостатки

- **Время компиляции**: решение SMT увеличивает время компиляции, но жёсткое ограничение бюджета
  удерживает верхнюю границу
- **Границы автоматического доказательства**: сложные предикаты за пределами линейной арифметики
  первого порядка могут потребовать от программиста функции-доказательства. Это не дефект языка —
  неизбежное следствие проблемы остановки. Компилятор честно сообщает Unproven, а не ложно выдаёт
  True/False
- **Кривая обучения**: написание эффективных компиляционных предикатов и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Ховарда
- **Сложность реализации**: единство конвейера доказательств требует тщательного проектирования

### Снижение рисков

- Жёсткое ограничение бюджета решения SMT (10 000 шагов / 100 мс / глубина инстанцирования 3), при
  превышении — Unproven
- Пре-редукция зависимых типов: сначала поглощаются детерминированные вычисления, SMT получает
  только недетерминированную часть
- Unproven — не тупик: программист пишет функцию-доказательство, проверка типов верифицирует — так
  же, как любой возвращаемый тип
- Инкрементальная верификация: верифицируются только изменённые модули
- Понятные сообщения об ошибках + вывод контрпримеров + отчёт о потреблении бюджета + неразрешённые
  утверждения + подсказки (если компилятор может их дать)

## Альтернативы

| Альтернатива                                                          | Почему не выбрана                                                                                                                                                                |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-022: спецификации-комментарии `//!`                               | Разделение спецификации и типа, нарушение изоморфизма Карри-Ховарда                                                                                                              |
| Отдельный файл спецификаций (например, CVL)                           | Спецификация отделена от кода, увеличивает стоимость сопровождения                                                                                                               |
| Только утверждения времени выполнения                                 | Невозможно статически гарантировать корректность                                                                                                                                 |
| Внешний помощник доказательств (например, Coq)                        | Отделено от компилятора, требует отдельного языка доказательств и корня доверия. Выбор YaoXiang: доказательство — это код YaoXiang, проверка типов — единственный корень доверия |
| **Данный подход: компиляционные предикаты как полноправные граждане** | ✅                                                                                                                                                                               |

## Стратегия реализации

### Разбиение по фазам

| Фаза       | Содержимое                                                                                                                                                                                |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фаза 1** | Ядро компилятора: структурная эквивалентность + βδι-редукция + введение/устранение квантора всеобщности. Поддержка простых арифметических предикатов (`x > 0`, `arr.len > 0`)             |
| **Фаза 2** | Слой трансляции в SMT-LIB + интеграция Z3/CVC5. Конвейер возвращает Proved/Disproved/Unproven. При Unproven поддерживается функция-доказательство от программиста                         |
| **Фаза 3** | Генерация VC для инвариантов цикла + проверка завершаемости (линейная ранговая функция + счётчик нарушений предиката + паттерн ограниченного инкремента + контроль комбинаторного взрыва) |
| **Фаза 4** | Инкрементальная верификация + кэширование + поддержка IDE                                                                                                                                 |

### Зависимости

- RFC-010: Унифицированный синтаксис типов — компиляционные предикаты основаны на
  `name: type = value`
- RFC-011: Система дженериков — компиляционные предикаты могут принимать параметры дженериков
- RFC-009: Модель владения — выражения в компиляционных предикатах подчиняются правилам владения

## Открытые вопросы

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, наибольшая валидация). CVC5 как
      совместимая с SMT-LIB альтернатива, переключение флагом компилятора. Внутри компилятор
      транслирует в стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, никакого
      собственного универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решения**: 10 000 шагов / 100 мс / глубина инстанцирования
      кванторов 3. Жёстко зашито в компилятор, без ручек. При наличии реального случая,
      показывающего, что значений недостаточно (не из-за ошибки пользователя), — корректировка.
- [x] **Объём поддержки кванторов**: на уровне языка порядок кванторов не ограничивается.
      Компиляционные предикаты принимают параметры Type — Type включает функциональные типы —
      поэтому кванторы высшего порядка являются естественным следствием системы типов и не требуют
      специального синтаксиса. SMT-решатель может автоматически разрешать кванторы первого порядка
      (forall/exists, поддерживается чередующееся вложение, ограничено бюджетом глубины 3). Кванторы
      высшего порядка: SMT возвращает Unproven, компилятор сообщает «этот предикат выходит за
      пределы автоматического доказательства, предоставьте функцию-доказательство». Программист
      пишет функцию YaoXiang, чей возвращаемый тип равен этому утверждению, — проверка типов
      верифицирует её. Никакого внешнего экспорта, никакого ИИ, никакого интерактивного режима
      доказательств. Всё — код YaoXiang, всё верифицируется проверкой типов.
- [x] **Форматирование контрпримеров**: имена переменных исходника используются непосредственно как
      имена SMT-переменных (с префиксом модуля для предотвращения коллизий). Модель Z3 возвращается
      с обратным поиском по имени. Формат вывода: имя переменной = конкретное значение + позиция в
      исходнике + позиция определения предиката. Без сложного слоя отображения.
- [x] ~~**Взаимодействие компиляционных предикатов с интеллектуальным указателем `ref`?**~~ →
      Решено: компиляционные предикаты допускают только неизменяемые заимствования или значения с
      уже переданным владением. Значения, находящиеся под изменяемым заимствованием, не могут
      появляться в компиляционных предикатах.
- [x] **Расширение счётчика нарушений `forall` на несоседние операции?** → Не расширяется. Текущее
      покрытие (соседние обмены, соседние сдвиги) дополняется стратегией 1 (линейная ранговая
      функция) — для быстрой сортировки внешнее сжатие интервала покрывается стратегией 1, для
      пирамидальной сортировки — стратегией 1 (паттерн индексации массива). Циклы, для которых ни
      одна стратегия не может доказать завершаемость, сразу дают ошибку компиляции — это философия
      жёсткой безопасности, а не дефект. Если в будущем появится реальный сценарий (не академическая
      конструкция) с алгоритмом, не покрываемым ни одной из четырёх стратегий, вопрос будет
      пересмотрен.
- [x] **Комбинаторный взрыв при перечислении линейной ранговой функции**: верхний предел числа
      перечисляемых переменных — 3 переменные с границами. ≤3 — перебираются все линейные комбинации
      с SMT-верификацией каждой. >3 — проверяются только однопеременные меры (`v_i`, `u_i - v_i`),
      при неудаче сразу ошибка компиляции с подсказкой «в цикле >3 переменных с границами,
      компилятор не может синтезировать многомерную меру». Это не инженерный компромисс — это
      побуждение программиста писать более простые циклы.
