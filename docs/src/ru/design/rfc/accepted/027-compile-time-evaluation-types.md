# RFC-027: Предикаты времени компиляции и унифицированная статическая верификация

> - [RFC-024: Модель конкурентности на основе блоков spawn](../accepted/024-concurrency-model.md)
>

> — устарел

## Резюме

В данном документе предлагается ввести в YaoXiang **предикаты времени компиляции** как полноправных
граждан, унифицировав всю статическую верификацию времени компиляции в единый **конвейер
доказательства**. Предикаты времени компиляции — это не внешние спецификационные комментарии — это
функции. Функция, возвращающая Type, может использоваться в позиции типа; компилятор вызывает её во
время компиляции и проверяет возвращаемое значение. Тип — это утверждение, вычисление времени
компиляции — это доказательство.

**Центральный тезис**: единственная задача проверки типов во время компиляции — построение и
верификация термов доказательства. Равенство типов, конфликты токенов, редукция зависимых типов,
вычисление предикатов времени компиляции, импликации логики Хоара — всё это различные проверки типов
в конвейере доказательства времени компиляции, разделяющие один и тот же конвейер. SMT-решатель —
это ускоряющий модуль проверщика типов, а не независимый доверенный компонент. Когда компилятор
возвращает Unproven, программист пишет функцию YaoXiang в качестве доказательства — проверщик типов
верифицирует её точно так же, как верифицирует возвращаемый тип любой функции. Всё — это код
YaoXiang, всё проверяется проверщиком типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации в форме комментариев `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это комментарий вне системы типов
    //! ensures: ExistsMax(result, arr[0..n])   ← это комментарий вне системы типов
}
```

Это совершает фундаментальную ошибку изоморфизма Карри-Ховарда: **разделяет спецификации и типы на
два слоя**. Комментарии — это не типы. Комментарии не участвуют в проверке типов. Комментарии — это
ментальная модель «внешнего инструмента».

В белой книге сказано прямо:

> «Нет комментариев `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Комментарии `//!` из RFC-022 — это внешний синтаксис, отдельный от системы типов
- Спецификационные типы и обычные типы — это две разные системы, что создаёт концептуальную
  избыточность
- Разделение на Debug Build с верификацией / Release Build без верификации разрушает единство
- SMT-решатель в традиционном восприятии позиционируется как внешний инструмент — YaoXiang
  встраивает его как ускоряющий модуль проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов — каждое идёт своим путём

### Правильная ментальная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — являются подзадачами этой функции. Они разделяют один
конвейер доказательства, различаясь только сложностью терма доказательства и стратегией построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство — её
возвращаемый тип равен доказываемому утверждению. Проверщик типов верифицирует её. Это та же самая
операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип как утверждение, верификация как проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри — это утверждения, и
компилятор гарантирует истинность каждого — либо автоматическим доказательством, либо
предоставлением программистом функции-доказательства.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  компилятор гарантирует, что x — это Float, y — это Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  компилятор гарантирует, что data — это Array(T)
```

**Дженерики — это частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          параметр в сигнатуре  в {} только утверждения
#          компилятор проверяет x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      параметр в сигнатуре  компилятор проверяет type_of(T) == Type, type_of(data) == Array(T)
```

Тот же шаблон: `name: (params) -> Type = { утверждения }`. Компилятор не различает «утверждения о
типах» и «утверждения о значениях» — все они являются целями вычисления в конвейере доказательства.

**Инварианты цикла не нужно записывать отдельно. Аннотации типов на переменных — это инварианты
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # компилятор проверяет: s_new == sum(arr[0..i+1])
        i += 1       # i изменён → запускается повторная верификация зависимости s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. После того, как
конвейер доказательства верифицирует индуктивный шаг, все итерации покрываются автоматически. Не
нужны `: decreases`, не нужны `: Invariant`, не нужны индуктивные доказательства — компилятор
разбивает индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции в типах параметров и возвращаемого значения

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции выступают как
аннотации типов параметров или возвращаемого значения.

**На стороне параметров это вызов функции.** Предикат времени компиляции — это функция, возвращающая
Type; его использование на стороне параметра — это вызов его — точно так же, как `factorial(5)`. На
стороне возвращаемого значения вводится новое понятие: формальный параметр возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive как аргумент
#                       компилятор в точке вызова извлекает значение аргумента, подставляет b, проверяет Positive(аргумент)
#                       пример: divide(10, 2) → проверка Positive(2) = { 2 > 0 } → True
#                       пример: divide(10, 0) → проверка Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возвращаемого значения, значение предоставляется return
#                                            компилятор в точке return подставляет возвращаемое значение, проверяет постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **Сторона параметров**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся в
  `Positive` как аргумент. Синтаксис вызова функции, ноль неявного.
- **Сторона возврата**: `-> (result: IsMax(T, arr, result))` — `result` — формальный параметр
  возвращаемого значения, значение предоставляется оператором `return`. `result` существует только в
  сигнатуре типа, только ссылается на предикат, не входит в область видимости тела функции, не
  появляется у вызывающего.
- **Формальный параметр возвращаемого значения необязателен**: при отсутствии постусловия не
  пишется, сигнатура полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: формальные параметры параметра и возвращаемого значения — одно и то же понятие —
  `имя_параметра: вызов_предиката(имя_параметра)`, различающееся лишь тем, предоставляется ли
  значение вызывающей стороной или оператором `return`.

### 3. Распространение путевых условий: верификация времени компиляции значений времени выполнения

Когда предикаты времени компиляции используются в позиции связывания, аргументы передаются
программистом явно. Когда значения времени выполнения попадают в параметры уточняющего типа,
компилятор завершает верификацию посредством сбора путевых условий и SMT-импликации — без явной
передачи доказательства от программиста.

#### 3.1 Явный вызов функции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно — это просто вызов функции, ноль неявного.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предикатов времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — это вызов функции
// после нормализации: b: { b > 0 }
```

Не требуется, чтобы компилятор неявно заполнял аргументы — `b: Positive(b)` — это точно такой же
вызов функции, как `f(5)`. `b` связывается как имя параметра, и его аннотация типа `Positive(b)`
ссылается на сам `b` — это стандартный шаблон зависимых типов, а не правило неявного раскрытия.

**Единство с `self` из RFC-010**: RFC-010 устанавливает, что `self` — не ключевое слово, а просто
соглашение об имени параметра («написано ли `p`, `this`, `x` — эффект совершенно одинаков»).
`b: Positive(b)` использует тот же механизм — имя параметра может быть использовано в аннотации
типа. `self` появляется в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, обе
аннотации типа ссылаются на сам параметр. Различие только в сложности аннотации типа, механизм
полностью одинаков — после связывания имени тип может зависеть от этого имени.

Тип возврата также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возвращаемого значения, Sorted(result) — вызов функции
//                        компилятор в точке return подставляет возвращаемое значение в result, проверяет Sorted(возвращаемое_значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → пройдено

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значения времени выполнения появляются в условных ветвях, компилятор автоматически собирает
путевые условия, формируя **множество гипотез** для текущей области видимости. Эти гипотезы
участвуют в верификации как фоновые знания для вычисления Bool времени компиляции.

```yaoxiang
if y > 0 {
    // компилятор автоматически получает в этой ветви гипотезу: { y > 0 }
    let result = divide(x, y)
    // условие верификации: (y > 0) ⇒ (y > 0)
    // конвейер доказательства определяет, что импликация истинна → Proved
} else {
// гипотеза этой ветви: { !(y > 0) }
// если вызвать divide(x, y), условие верификации: !(y > 0) ⇒ y > 0
    // конвейер доказательства определяет, что импликация ложна → Disproved
}
```

Это не специальный шаблон, зашитый компилятором — это естественное поведение конвейера
доказательства времени компиляции. При каждой проверке типов в точке вызова конвейер отправляет:

```
{фоновые_гипотезы} ⇒ {цель_верификации}
```

Конвейер доказательства определяет импликационность. Proved → пройдено, Disproved → ошибка
компиляции + контрпример, Unproven → ошибка компиляции + нерешённое утверждение. Фоновые гипотезы
берутся из путевых условий текущей программной точки.

#### 3.3 Стек гипотез

Компилятор при анализе потока управления поддерживает множество гипотез для каждого базового блока:

- **if-guard**: `if y > 0` → истинная ветвь помещает `y > 0`, ложная ветвь помещает `!(y > 0)` (если
  используется else)
- **match-шаблоны**: `if let Some(v) = opt` → внутри ветви помещается `opt == Some(v)`
- **логические связки**: `if x > 0 and y < 10` → внутри ветви помещаются `x > 0` и `y < 10`
- **предусловия функций**: при вызове `divide(a, b)`, `b` должен удовлетворять `Positive` —
  свидетельство берётся либо из текущих гипотез, либо из аннотации уточняющего типа самого аргумента
  (если `b` уже аннотирован как `Positive`, его тип несёт `b > 0`)
- **присваивание**: при `let z = y` уже имеющиеся у `y` условия уточнения передаются `z`

Все гипотезы поступают в конвейер доказательства времени компиляции. При входе на путь ускорения SMT
они переводятся в фоновые утверждения SMT-LIB.

#### 3.4 Отсутствие статического свидетельства — ошибка компиляции

Если программист пишет напрямую:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей программной точке нет гипотезы `y > 0`, и сам аргумент `y` не имеет аннотации типа
`Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (не следует) → ошибка компиляции:

> Не удаётся доказать, что параметр `b` в вызове `divide` удовлетворяет `Positive`. `y` приходит из
> ввода функции, нет доказанной границы. Рассмотрите охрану вызова ветвью if:
> `if y > 0 { divide(x, y) }`.

YaoXiang не допускает, чтобы значения времени выполнения напрямую попадали в параметры уточняющего
типа без предоставления статического свидетельства. Это не ограничение — это ядро философии жёсткой
безопасности. Всё, что компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Отношение к единому конвейеру

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
доказательства времени компиляции на анализ потока управления:

| Этап                                  | Ответственность                                                                                                                                                                     |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий                  | Этап анализа потока управления компилятора, аннотирующий множество гипотез для каждого базового блока                                                                               |
| Генерация условий верификации         | При встрече ограничения типа, подлежащего проверке, объединяет путевые условия + информацию о типе аргумента                                                                        |
| Вычисление в конвейере доказательства | Ядро компилятора → ускорение SMT → получение Proved / Disproved / Unproven                                                                                                          |
| Результат                             | `Proved` → пройдено; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + нерешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновые знания
конвейера доказательства — разделяющие один конвейер и одну систему бюджета с равенством типов и
ограничениями заимствования.

### 4. Конвейер доказательства времени компиляции

Все проверки времени компиляции разделяют один конвейер. Центральная операция конвейера — **проверка
типов** — проверка, равен ли тип терма доказательства доказываемому утверждению. Всё — это проверка
типов.

```
Время компиляции встречает Bool-выражение, требующее вычисления (т.е. нужно построить терм доказательства)
        │
        ├── Равенство типов (T1 == T2)
        │   → компилятор выносит прямое суждение (структурная эквивалентность)
        │
        ├── Условия конфликта токенов (!conflicting(tokens))
        │   → потокочувствительный анализ живучести (отслеживание атрибутов Dup/Linear)
        │
        ├── Редукция зависимых типов (упрощение n + m)
        │   → система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикат времени компиляции (x > 0, forall...)
        │   → собственное ядро компилятора + ускоряющий модуль SMT
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → ядро компилятора + ускоряющий модуль SMT
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → компиляция проходит
             │ Disproved│  → ошибка компиляции + контрпример
             │ Unproven │  → ошибка компиляции + нерешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ──→ Proved ──→ компиляция проходит
                  │
                  ▼
            Верификация не прошла → ошибка компиляции: «доказательство неверно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — это неизбежное следствие проблемы
остановки и естественное разбиение теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → остановка, терм доказательства построен, проверка типов прошла. Компиляция
  продолжается.
- **Disproved(M)** → остановка, существует контрпример M. Ошибка компиляции + контрпример + позиция
  в исходном коде.
- **Unproven** → в пределах данного ресурсного лимита терм доказательства не построен. Ошибка
  компиляции + нерешённое утверждение + отчёт о потреблении бюджета.

**Unproven ≠ False.** Когда компилятор говорит «я не могу доказать», это не эквивалентно ложности
утверждения — просто превышены возможности текущего автоматического доказательства. Это честность, а
не дефект.

Жёсткий лимит бюджета — это инженерное решение проблемы остановки. Без ручек — давать их означает
спрашивать пользователя «как вы думаете, ваша программа остановится», пользователь не знает, и
компилятор тоже не знает.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — просто
функцию YaoXiang, чей возвращаемый тип равен доказываемому утверждению. Проверщик типов верифицирует
эту функцию — тем же механизмом, которым он верифицирует, что `add(a, b): Int`.

```
Утверждение  = Тип
Доказательство = Программа (значение этого типа)
Верификация = Проверка типов (единственный корень доверия)
```

SMT-решатель — не независимый доверенный компонент — это **ускоряющий модуль проверщика типов**. SMT
помогает найти доказательство, но доказательство всегда верифицирует проверщик типов. Когда SMT
возвращает `unsat`, компилятор реконструирует его результат в терм доказательства, верифицируемый
проверщиком типов. Если реконструкция не удалась (шаги вывода SMT выходят за правила вывода ядра
компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: уточняющее свойство, которое компилятор не может автоматически доказать
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, чей возвращаемый тип — утверждение выше
# Проверщик типов верифицирует эту функцию — полностью так же, как верифицирует add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # компилятор здесь проверяет: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Не нужен ИИ, не нужен экспорт в Coq, не нужны новые понятия. **Свойства, которые компилятор не может
автоматически доказать → программист пишет доказательство в коде YaoXiang → проверщик типов
верифицирует.** Весь процесс — плавный градиент — компилятор берёт на себя простые доказательства,
оставляя сложные вам.

#### 4.3 Многослойная зависимость внутри конвейера

Вышеописанные вычислители используют один и тот же интерфейс, но имеют порядок вычисления. Равенство
типов — необходимое условие для всего последующего анализа; проверки владения/токенов зависят от
информации о типах; верификация уточняющих предикатов зависит от результатов первых двух слоёв.
Компилятор вычисляет послойно, выражения, не прошедшие нижние слои, не поступают на верхние —
избегая траты бюджета решателя на типоневерные программы.

```
Порядок вычисления (один конвейер, послойная диспетчеризация)
├── Слой 0: Равенство типов (T1 == T2)
│   └── структурная унификация → при неудаче дальнейшее бессмысленно, сразу Disproved
├── Слой 1: Конфликты владения/токенов
│   └── потокочувствительный анализ живучести → при неудаче безопасность памяти не установлена, сразу Disproved
└── Слой 2: Уточняющие предикаты/импликации Хоара
    └── ядро компилятора → ускорение SMT → получение Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя один интерфейс и одну
систему бюджета.

### 5. Единство трёх слоёв функций

| Слой                        | Время выполнения | Вход          | Выход    | Пример                                         |
| --------------------------- | ---------------- | ------------- | -------- | ---------------------------------------------- |
| Функция значений            | Время выполнения | значения      | значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типов           | Время компиляции | типы/значения | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат времени компиляции | Время компиляции | значения      | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют одинаковый синтаксис `name: type = value`. Предикаты времени компиляции и
конструкторы типов идут по одному конвейеру доказательства времени компиляции — `{}` — это
пространство доказательств.

### 6. Циклы: генерация условий верификации в стиле Флойда-Хоара

Циклам не нужны отдельные аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточняющих
типов на переменных определяют утверждения в стиле Флойда-Хоара — компилятор генерирует условия
верификации из аннотаций типов, конвейер доказательства проверяет, сохраняет ли каждое присваивание
тип.

Центральный механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`,
условием верификации является `P ⇒ Q[e/x]`. Компилятор генерирует одно условие верификации для тела
цикла — после того, как конвейер доказательства верифицирует индуктивный шаг, все итерации
покрываются автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # аннотация ссылается на i; при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # проверка: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует одну VC для тела цикла. Предпосылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i не изменяется)
        #   Подставляя s_new = s_old + arr[i]:
        #     требуется s_old + arr[i] == sum(arr[0..i+1])
        #     из индуктивной гипотезы s_old == sum(arr[0..i]), прибавляя arr[i] к обеим сторонам:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменён → в графе зависимостей аннотация типа s ссылается на i → запускается повторная верификация
        #   Новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   то есть s == sum(arr[0..i_new]), гарантировано предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # в этот момент s: SumUpTo(arr, arr.len), то есть s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотации типа на переменных — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант, не нужно «делать индукцию
автоматически» — он разбивает индуктивное доказательство на локальные условия верификации для каждой
операции присваивания и передаёт их в конвейер доказательства по принципу «разделяй и властвуй».

#### 6.1 Отслеживание зависимостей: зависимые типы на изменяемых переменных

Предпосылка вышеописанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i` — когда `i` изменяется, ограничение типа `s` также изменяется. Это требует от
компилятора вести **граф типовых зависимостей между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# ключ — зависимая переменная, значение — множество переменных, чьи аннотации типа ссылаются на эту переменную
# пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: проверщик типов при обработке `mut v: Pred(... x ...) = init` разбирает свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылка на другую изменяемую переменную
`x` в текущей области видимости, в графе зависимостей записывается `x → v`.

**Триггер**: когда зависимая переменная `x` присваивается, компилятор:

1. Ищет в графе зависимостей все переменные, зависящие от `x` — `{v₁, v₂, ...}`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Передаёт VC в конвейер доказательства

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественным образом
форсирует правильный порядок присваивания. На примере `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменён → повторная верификация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # i изменён → повторная верификация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлено, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # недостижимо
```

**Составные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` одновременно зависит от `x` и `y` — изменение любой из них запускает
повторную верификацию.

**Отношение к конвейеру доказательства**: отслеживание зависимостей — триггер генерации VC, а не
независимый механизм верификации. Он отвечает на вопрос «когда нужно генерировать VC» — конвейер
доказательства отвечает на вопрос «выполняется ли VC».

### 7. Проверка завершения

**Область применения: вычисление времени компиляции.** Проверка завершения применяется только к
циклам и рекурсии, задействованным в вычислении времени компиляции (запускаемым отслеживанием
зависимостей) — код, который должен выполнить сам компилятор, должен быть полностью доказуемо
завершаемым; от кода времени выполнения не требуется доказательство завершения (см. таблицу областей
применения в §6.7). В пределах области полная автоматизация компиляции предпочтительна: циклы,
которые компилятор может доказать, проходят, циклы, которые автоматическая стратегия не может
доказать, сразу вызывают ошибку компиляции — программист должен сделать так, чтобы компилятор мог
автоматически проанализировать завершение цикла. Нет лазеек в виде **аннотационного синтаксиса** (не
вводится аннотация типа `decreases`, неподдерживаемое навсегда остаётся синтаксической позицией, а
не функцией).

> **Поправка (RFC-027a, 2026-09-14)**: ① Область применения уточнена до вычисления времени
> компиляции — исходный текст не ограничивал «циклы» позицией, что создавало неоднозначность с
> таблицей областей применения в §6.7; безусловная полная проверка на уровне реализации сужена
> согласно этому. ② Для обязательств завершения, которые автоматическая стратегия не может доказать,
> программист может предоставить функцию-меру и функцию-доказательство завершения (`Terminates`) в
> качестве запасного варианта — обе являются обычными функциями YaoXiang, ноль нового синтаксиса,
> проверщик типов верифицирует. Принцип полной автоматизации остаётся неизменным, запасной вариант
> применяется только после Unproven. См.
> [RFC-027a: Запасной вариант функции-доказательства для проверки завершения](../draft/027a-termination-proof-fallback.md).

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию, необходимую для доказательства завершения, из двух
мест:

1. **Аннотации типов переменных**: граничные ограничения в уточняющих типах (например, `UpTo(n)`
   даёт верхнюю границу `n` и нижнюю `0`)
2. **Операции в теле цикла**: операции, применяемые к переменным на каждой итерации

Компилятор пробует четыре стратегии синтеза метрики в порядке приоритета и останавливается, как
только находит подходящую.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию линейной границы, компилятор перебирает кандидатов линейной метрики
и верифицирует через SMT.

```
Вход:
  Переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с границами)
  Условие цикла cond
  Множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типов: [low_i, high_i]
  2. Перебрать кандидатов метрик: v_i, u_i - v_i, v_i - v_j, и другие линейные комбинации
  3. Для каждого кандидата m:
     - SMT проверяет m ≥ 0 (из типовых границ)
     - Для каждого пути выполнения тела цикла SMT проверяет m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершение доказано
```

Область покрытия: любой цикл, в котором переменной присваивается линейное выражение (`v = a·v + b`)
и имеется аннотация ограниченного типа. Включая `i += const`, `i -= const`, а также сжатие интервала
в стиле двоичного поиска:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# метрика high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: счётчик нарушений предиката — автоматическое извлечение метрики из целевого типа <span style="color:orange">【Экспериментальная стратегия】</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, на этапе 3 реализации решается по фактической
> осуществимости, включать ли её.** Эта стратегия работает для операций соседнего обмена (сортировка
> пузырьком, сортировка вставками), но не может автоматически доказать несмежные операции (partition
> быстрой сортировки, sift-down пирамидальной сортировки). Границы покрытия см. в таблице ниже. Если
> на этапе 3 верификация покажет неосуществимость, эта стратегия будет удалена или понижена до
> будущей работы.

Ключевая идея: **спецификация, написанная пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое сортировка» — он читает определение
`Sorted` и автоматически извлекает из него метрику.

```
Вход:
  Целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  Операции в теле цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать метрику: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операций на метрику:
     - обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - влияет только на пары с индексами j-1, j, j+1
     - если arr[j] > arr[j+1] (нарушение предиката), после обмена эта пара удовлетворяет предикату
     - violation_count уменьшается как минимум на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя: 0
  → завершение доказано
```

**Текущая область покрытия**:

| Алгоритм                 | Шаблон операции      | Стратегия 2 доказуема? | Причина                                              |
| ------------------------ | -------------------- | :--------------------: | ---------------------------------------------------- |
| Сортировка пузырьком     | соседний обмен       |           ✅           | violation_count строго убывает при каждом обмене     |
| Сортировка вставками     | соседнее перемещение |           ✅           | каждое перемещение устраняет одну пару нарушений     |
| Сортировка выбором       | несмежный обмен      |           ❌           | одиночный обмен может увеличить violation_count      |
| Быстрая сортировка       | разбиение partition  |           ❌           | несмежный обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌           | древовидная операция, violation_count немонотонна    |

**Дополняющие стратегии**: для быстрой сортировки сжатие интервала `low < high` покрывается
стратегией 1 (линейная ранговая функция) — рекурсия внешнего partition, на каждом шаге интервал
сокращается вдвое. Стратегии 1 и 2 дополняют друг друга, завершение большинства практических
алгоритмов доказуемо одной из них. Однако обобщение стратегии 2 (несмежные операции, древовидные
операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: шаблон ограниченного возрастания/убывания

`v += const` (const — положительное число), переменная имеет аннотацию верхней границы → метрика
`upper_bound - v` убывает на `const` каждый раз, нижняя граница 0. Это вырожденный случай стратегии
1, компилятор обрабатывает его первым для скорости.

#### 6.5 Стратегия 4: шаблон метрики мультипликативного масштабирования

`v *= const` (const > 1), переменная имеет аннотацию верхней и нижней границ. Компилятор встраивает
шаблон логарифмической метрики `ceil(log_const(upper/v))`, метрика убывает на 1 при каждом умножении
на const.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # компилятор автоматически выводит: метрика ceil(log₂(n/i)), убывает на 1 при каждом умножении на 2
    i *= 2
}
```

#### 6.6 Разделение завершения и корректности

Доказательство завершения и доказательство корректности независимы:

- **Завершение**: четыре вышеописанные стратегии автоматически доказывают, что цикл завершается за
  конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу — проверяется конвейером
  доказательства времени компиляции через условия верификации

Оба проходят → компиляция проходит. Завершение доказано, но корректность не прошла → ошибка
компиляции + контрпример. Корректность доказана, но завершение не доказуемо → ошибка компиляции с
указанием переменной или операции, которые не удалось проанализировать. Оба не прошли → ошибка
компиляции с раздельным указанием причин обоих отказов.

#### 6.7 Проверка завершения рекурсивных функций

Для рекурсивных функций, которые должны вычисляться во время компиляции, компилятор проверяет
убывание аргументов:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # анализ компилятора: n-1 < n → убывание → завершение
}

# Использование времени компиляции — компилятор гарантирует завершение factorial во время компиляции
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, выполняется во время компиляции
```

| Сценарий                                                              | Поведение                        |
| --------------------------------------------------------------------- | -------------------------------- |
| Компилятор может проанализировать убывание рекурсии (например, `n-1`) | Вычисление времени компиляции    |
| Не убывает / убывание неопределимо                                    | Ошибка компиляции                |
| Вызов во время выполнения (не в позиции типа)                         | Проверка завершения не требуется |

#### 6.8 Жёсткая граница

`i = f(i)`, где `f` необратима, незамкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершение. Ошибка компиляции:

> Этот цикл не может быть автоматически доказан как завершающийся. Переменная цикла зависит от
> неанализируемой функции `f`. Пожалуйста, используйте итерационный шаблон, анализируемый
> компилятором, или предоставьте функцию-меру и функцию-доказательство завершения (см. RFC-027a).

Это не провал компилятора. Всё, что нельзя статически доказать как безопасное, не проходит
компиляцию.

### 8. SMT-решатель: ускоряющий модуль проверщика типов

SMT-решатель в традиционных языках — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang это **ускоряющий модуль проверщика типов** — вызывается только тогда, когда
собственное ядро компилятора не может вынести прямое суждение. SMT помогает найти доказательство, но
доказательство верифицирует проверщик типов.

**Модель доверия**: проверщик типов — единственный корень доверия. SMT-решатель — ускоряющий модуль
— он помогает найти доказательство, но SMT не является независимым доверенным компонентом.
Компилятор доверяет результату `unsat` от Z3 (согласуется с подходом F\*/Dafny — вероятность ошибки
Z3 ниже, чем частота багов в самом компиляторе, это прагматичный инженерный выбор). Реальная
ненадёжность контролируется на уровне трансляции в SMT — если в трансляции есть баг, компилятор
обнаружит его в других тестах.

**Интерфейс**: внутренний перевод компилятора осуществляется в стандартный формат SMT-LIB 2.6, а не
в привязку к API конкретного решателя. SMT-LIB — стандарт ISO, нативно поддерживается Z3, CVC5,
MathSAT, Yices.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, самая широкая документация и валидация сообществом). CVC5
в качестве совместимого с SMT-LIB запасного варианта — пользователь может переключаться флагом
компилятора.

Не делаем «универсальный слой абстракции решателя» — SMT-LIB и есть слой абстракции. В будущем, если
CVC5 добьётся прорыва в определённой теории, переключение потребует только смены бинарника, без
изменения кода компилятора.

```
Bool-выражение времени компиляции
        │
        ├── Ядро компилятора может вынести прямое суждение (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → сразу возвращает Proved / Disproved
        │
        └── Ядро компилятора не может вынести прямое суждение (кванторы, символьные переменные)
            → предварительная редукция зависимых типов (factorial(5) → 120)
            → трансляция в формат SMT-LIB
            → отправка в Z3/CVC5 (с лимитом бюджета)
            → возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решателя — жёсткий лимит, как глубина стека**:

| Измерение бюджета                 | По умолчанию | Описание                                                                                                                                                       |
| --------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10,000       | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10 000 шагов покрывают 99% реальных предикатов.                                                  |
| Время                             | 100ms        | Один предикат свыше 100ms = пользователь пишет программу времени компиляции, а не аннотацию типа. 100ms × 50 предикатов = 5 секунд верхней границы компиляции. |
| Глубина инстанцирования кванторов | 3            | Три уровня вложенных кванторов покрывают реальные шаблоны. Свыше трёх — скорее всего, пишется логическая задача.                                               |

Превышение бюджета возвращает Unproven, ошибку компиляции + позицию предиката + потребление. Без
деградации, без проверок времени выполнения, без тихого пропуска.

**Почему это практически осуществимо**: 95% реальных предикатов в инженерии — линейная арифметика —
`x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в пределах разрешимого фрагмента, SMT-решатель
для таких задач возвращается за миллисекунды. Для редких предикатов, превышающих бюджет, программист
пишет функцию-доказательство.

Зависимые типы перед вызовом SMT проходят предварительную редукцию: `factorial(5)` напрямую
вычисляется во время компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти
детерминированные вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Ментальная модель: **компилятор может доказать —
проходит, не может — сообщает об ошибке — если компилятор не умеет, вы можете написать функцию,
чтобы доказать ему.**

### 9. Композиция предикатов времени компиляции

Предикаты времени компиляции — это функции, возвращающие Type, композиция реализуется естественно
через композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ Компилятор проверяет Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ Компилятор проверяет Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ Компилятор проверяет InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ Компилятор проверяет InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: единство диспетчеризации времени компиляции и времени выполнения

`assert` и `Assert` — две стороны одного уточняющего типового примитива. Конвейер диспетчеризации
`dispatch` автоматически решает, идти ли по пути доказательства времени компиляции или по проверке
времени выполнения, по тому, **достижимы ли свободные переменные предиката во время компиляции**:

| Критерий                                                                                                   | Режим           | Поведение                                                                                                            |
| ---------------------------------------------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры дженериков, константы времени компиляции) | **CompileTime** | Вход в конвейер доказательства: Proved → стирание, Disproved → ошибка компиляции, Unknown → требуется доказательство |
| Существуют свободные переменные из времени выполнения (параметры функций, внешний ввод, mut-переменные)    | **Runtime**     | Вставка проверки времени выполнения и инъекция уточняющего факта в потокочувствительное множество гипотез Γ          |

**Ключевой момент**: «не удаётся определить» ≠ «опровергнуто». В режиме CompileTime Unknown требует
доказательства (без тихой деградации), в режиме Runtime утверждение во время компиляции вообще не
имеет истинности — никакой prover не напишет тавтологически истинного доказательства для
«пользователь мог ввести отрицательное число», проверка времени выполнения — единственный sound
выбор. Это не слабость prover, а теоретическая неизбежность.

### 12. Потокочувствительное множество гипотез Γ: сильнейшее распространение постусловия

Компилятор поддерживает потокочувствительное (flow-sensitive) множество гипотез Γ, отслеживающее
истинные утверждения в каждой точке потока управления.

**Распространение SP (сильнейшего постусловия)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← распространение SP
```

**Kill set для mut-переменных**: после переприсваивания `mut`-переменной все гипотезы с её участием
удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые гипотезы недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение гипотез ветвей. Из
ветви выносится только то, что истинно на всех путях.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточняющие типы полностью стираются во время выполнения» относится к **proof
witness (токену доказательства)** — терм доказательства, верифицированный во время компиляции, не
порождает кода времени выполнения. Но **проверки времени выполнения**, вставленные диспетчеризацией
в режиме Runtime, сохраняются — это Bool-проверки на уровне значений, а не witness на уровне типов.

Резюме: witness стирается, check сохраняется. Эти две вещи не конфликтуют, исходное утверждение
RFC-027 остаётся неизменным.

## Детальное проектирование

### Изменения синтаксиса

| До (RFC-022)                          | После (этот RFC)                                                                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Предикат времени компиляции как тип параметра `(b: Positive(b))`                          |
| `//! ensures: ExistsMax(result, arr)` | Тип возврата использует формальный параметр возврата `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Аннотации уточняющих типов на переменных — инварианты Флойда-Хоара                        |
| `//! decreases: n`                    | Компилятор полностью автоматически выводит функцию-меру                                   |
| Спецификация — это комментарий        | Спецификация — это система типов                                                          |

### Синтаксис

**У предикатов времени компиляции нет новых ключевых слов.** `{}` — это пространство доказательств,
полностью совпадающее с существующим синтаксисом определения типов. Предикат времени компиляции —
это просто функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. Использование —
это вызов функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Предикат времени компиляции = функция, возвращающая Type, в {} — утверждения, верифицируемые компилятором
# Используется существующий синтаксис функций/типов, новые правила BNF не требуются
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы применения предиката должны иметь форму констант времени компиляции** — литералы,
переменные (связанные по имени) или одноаргументные типовые применения (рекурсивное извлечение).
Невозможность преобразования аргумента в константное выражение — ошибка **E1092**, несоответствие
числа аргументов числу параметров предиката — ошибка **E1093** — ограничения уточнения **никогда не
отбрасываются молча** (ранее непреобразуемые аргументы приводили к тихому исчезновению ограничения,
нарушающие ограничения связывания молча проходили).

**Новое синтаксическое понятие: формальный параметр возвращаемого значения** — в `-> (name: Type)`
`name` — формальный параметр возвращаемого значения.

Формальный параметр возвращаемого значения — **единственное** синтаксическое понятие, вводимое
YaoXiang в существующий синтаксис функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается предикат постусловия (например,
  `-> (result: IsMax(T, arr, result))`)
- `name` не входит в область видимости тела функции, не появляется у вызывающего
- Формальный параметр возвращаемого значения **необязателен** — при отсутствии постусловия сигнатура
  полностью совпадает с обычной функцией (`-> Int`), не вводя никакой дополнительной нагрузки

Причина его введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть».
Без формального параметра возвращаемого значения компилятор может позволить предикату ссылаться на
возвращаемое значение только через специальные правила (например, неявная переменная `$result` или
`__retval__`). Формальный параметр возвращаемого значения делает эту ссылку явной — это просто
формальный параметр, только значение предоставляется `return`, а не вызывающей стороной.

**Функция-доказательство** — не новое понятие — это просто функция YaoXiang, чей возвращаемый тип —
доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверщик типов верифицирует её точно так же, как верифицирует
возвращаемый тип любой функции. Никакого нового синтаксиса, ключевых слов, правил не требуется.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функции, принимающие
  значения и возвращающие Type, на том же уровне, что и конструкторы типов
- **Взаимодействие с дженериками**: предикаты времени компиляции могут иметь параметры дженериков,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения, могут только читать, не могут писать
- **Вывод типов**: параметры предикатов времени компиляции участвуют в HM-выводе типов

### Представление во время выполнения

Предикаты времени компиляции обрабатываются **по результату диспетчеризации dispatch** во время
выполнения:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): токен-свидетельство
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представлен как `Int`. Условие уточнения `{ 5 > 0 }` уже пройдено, стирается.
- **Режим Runtime** (существуют свободные переменные времени выполнения): сохраняется проверка
  времени выполнения — Bool-проверка на уровне значений с инъекцией в потокочувствительное множество
  гипотез Γ. Подробности см. в §11 конвейер диспетчеризации dispatch и §13 уточнение модели
  стирания.

Помещение предиката времени компиляции в позицию типа (например, `f(x: Positive(x))`) не порождает
обёрточного типа, не выделяет дополнительную память. Но когда `x` приходит из ввода времени
выполнения, **будет** вставлена Bool-проверка времени выполнения.

**Ограничения взаимодействия с `ref`**: предикаты времени компиляции могут ссылаться только на
значения с неизменяемым заимствованием или с уже переданным владением. Предикаты времени компиляции,
ссылающиеся на значения с изменяемым заимствованием, не могут быть гарантированы компилятором как
действующие во время выполнения — такое использование напрямую вызывает ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, дополнительные
   правила разбора не нужны
2. **Конвейер доказательства времени компиляции**: единый интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **Ускоряющий модуль SMT**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, запасной CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение кванторов всеобщности. Это единственный корень доверия, SMT и доказательства
   программиста верифицируются через него
5. **Генерация условий верификации**: WP/SP-исчисление + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёты о нерешённых утверждениях + привязка
   к позициям в исходном коде

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, остаётся полностью неизменным
- ✅ Предикаты времени компиляции в режиме CompileTime не имеют накладных расходов во время
  выполнения, в режиме Runtime сохраняются только необходимые Bool-проверки
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован, нет
  нагрузки миграции

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Ховарда**: тип — утверждение, программа — доказательство,
  `name: Proposition = Proof`
- **Единство**: предикаты времени компиляции и обычные функции используют полностью идентичный
  синтаксис, без концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, ментальная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции, постепенно расширяя
  покрытие
- **Минимальные накладные расходы времени выполнения**: режим CompileTime — ноль накладных расходов,
  режим Runtime — только необходимые Bool-проверки

### Недостатки

- **Время компиляции**: решение SMT увеличивает время компиляции, но жёсткий лимит бюджета
  гарантирует контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами логики линейной
  арифметики первого порядка могут потребовать от программиста написания функций-доказательств. Это
  не дефект языка — это неизбежный вывод из проблемы остановки. Компилятор честно сообщает Unproven,
  а не ложно сообщает True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Ховарда
- **Сложность реализации**: единство конвейера доказательства времени компиляции требует тщательного
  проектирования

### Снижение рисков

- Жёсткий лимит бюджета SMT-решателя (шаги 10 000 / время 100ms / глубина инстанцирования 3),
  превышение возвращает Unproven
- Предварительная редукция зависимых типов: детерминированные вычисления значений съедаются первыми,
  SMT кусает только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверщик типов
  верифицирует — согласовано с верификацией любого возвращаемого типа функции
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + демонстрация контрпримеров + отчёт о потреблении бюджета +
  нерешённые утверждения + предложения (если компилятор может дать)

## Альтернативы

| Альтернатива                                                                   | Почему не выбрана                                                                                                                                                                |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RFC-022: спецификации в форме комментариев `//!`                               | Спецификации и типы разделены, нарушает изоморфизм Карри-Ховарда                                                                                                                 |
| Отдельные файлы спецификаций (например, CVL)                                   | Спецификации и код разделены, увеличивает стоимость сопровождения                                                                                                                |
| Только утверждения времени выполнения                                          | Не может статически гарантировать корректность                                                                                                                                   |
| Внешний помощник доказательства (например, Coq)                                | Отрезан от компилятора, требует отдельного языка доказательств и корня доверия. Выбор YaoXiang: доказательство — это код YaoXiang, проверщик типов — единственный корень доверия |
| **Данное предложение: предикаты времени компиляции как полноправные граждане** | ✅                                                                                                                                                                               |

## Стратегия реализации

### Разбиение на этапы

| Этап       | Содержание                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Этап 1** | Ядро компилятора: структурная эквивалентность + βδι-редукция + введение/устранение кванторов всеобщности. Поддержка простых арифметических предикатов (`x > 0`, `arr.len > 0`) |
| **Этап 2** | Слой трансляции в SMT-LIB + интеграция Z3/CVC5. Конвейер возвращает Proved/Disproved/Unproven. При Unproven поддержка функций-доказательств от программиста                    |
| **Этап 3** | Генерация VC для инвариантов циклов + проверка завершения (линейная ранговая функция + счётчик нарушений предиката + ограниченные шаблоны + контроль комбинаторного взрыва)    |
| **Этап 4** | Инкрементальная верификация + кэширование + поддержка IDE                                                                                                                      |

- RFC-009: Модель владения — выражения предикатов времени компиляции подчиняются правилам владения

## Открытые вопросы

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, самая широкая валидация). CVC5 как
      совместимый с SMT-LIB запасной вариант, переключение флагом компилятора. Внутренний перевод
      компилятора осуществляется в стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции,
      без специального универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решателя**: шаги 10 000 / время 100ms / глубина инстанцирования
      кванторов 3. Фиксированы внутри компилятора, без ручек. Если реальные сценарии использования
      докажут, что этого недостаточно (не «пользователь ошибся»), тогда корректируем.
- [x] **Область поддержки кванторов**: язык не ограничивает порядок кванторов. Предикаты времени
      компиляции принимают параметры Type — Type включает функциональные типы — поэтому кванторы
      высшего порядка — естественное следствие системы типов, специальный синтаксис не нужен.
      SMT-решатель может автоматически разрешать кванторы первого порядка (forall/exists,
      поддерживается чередующееся вложение, ограничено глубиной бюджета 3). Кванторы высшего
      порядка: SMT возвращает Unproven, компилятор подсказывает «этот предикат выходит за пределы
      автоматического доказательства, предоставьте функцию-доказательство». Программист пишет
      функцию YaoXiang, чей возвращаемый тип равен этому утверждению — проверщик типов верифицирует
      эту функцию. Не нужен внешний экспорт, не нужен ИИ, не нужен интерактивный режим
      доказательства. Всё — код YaoXiang, всё верифицирует проверщик типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена SMT-переменных (с префиксом модуля во избежание конфликтов). При возврате модели Z3
      выполняется обратный поиск по именам переменных. Формат вывода: имя_переменной =
      конкретное_значение + позиция в исходном коде + позиция определения предиката. Сложный слой
      отображения не делается.
- [x] ~~**Взаимодействие предикатов времени компиляции с умными указателями `ref`?**~~ → Решено:
      предикаты времени компиляции допускают только значения с неизменяемым заимствованием или с
      переданным владением. Значения с изменяемым заимствованием не могут появляться в предикатах
      времени компиляции.
- [x] **Расширение метрики счётчика нарушений предиката `forall` на несмежные операции?** → Не
      расширяется. Текущая область покрытия (соседний обмен, соседнее перемещение) дополняется
      стратегией 1 (линейная ранговая функция) — сжатие внешнего интервала быстрой сортировки
      покрывается стратегией 1, пирамидальная сортировка покрывается стратегией 1 (шаблон индексации
      массива). Циклы, завершение которых не может доказать ни одна стратегия, компилятор сразу
      отвергает с ошибкой — это философия жёсткой безопасности, а не дефект. Если в будущем появится
      реальный сценарий (не академическая конструкция), который не покрывается ни одной из четырёх
      стратегий, обсуждение будет возобновлено. → **Обсуждение возобновлено (2026-09-14, #318)**:
      неструктурная рекурсия (ненапрямую убывающие, как gcd, взаимная рекурсия, разбиение слиянием)
      — это как раз реальный сценарий, предвиденный этим пунктом — текущий конвейер не может
      автоматически доказать их завершение, и их невозможно переписать в анализируемый итерационный
      шаблон без ущерба читаемости. Заключение: приоритет полной автоматизации сохраняется; после
      Unproven добавляется запасной вариант функции-доказательства — мера и доказательство
      завершения обе являются обычными функциями YaoXiang, ноль нового синтаксиса, проверщик типов
      верифицирует. Реализовано в
      [RFC-027a: Запасной вариант функции-доказательства для проверки завершения](../draft/027a-termination-proof-fallback.md).
- [x] **Комбинаторный взрыв при переборе линейной ранговой функции**: верхний предел перебора
      кандидатов — 3 переменные с границами. При ≤3 перебираются все линейные комбинации с
      верификацией через SMT по одной. При >3 пробуются только метрики с одной переменной (`v_i`,
      `u_i - v_i`), при неудаче сразу ошибка компиляции — подсказка программисту «в цикле более 3
      переменных с границами, компилятор не может автоматически синтезировать многомерную метрику».
      Это не инженерный компромисс — это принуждение к написанию более простых циклов.
