# RFC-027: Предикаты времени компиляции и унифицированная статическая верификация

> — устарел

## Резюме

В данном документе предлагается ввести в YaoXiang **предикаты времени компиляции** как полноправных
граждан первого класса, объединив всю статическую верификацию времени компиляции в единый **конвейер
доказательства**. Предикат времени компиляции — это не внешняя аннотация спецификации — это функция.
Функция, возвращающая Type, может использоваться в позиции типа, и компилятор вызывает её во время
компиляции и проверяет возвращаемое значение. Тип есть утверждение, вычисление во время компиляции
есть доказательство.

**Ключевой тезис**: единственная работа проверки типов во время компиляции — построение и валидация
доказательств. Равенство типов, конфликты токенов, редукция зависимых типов, вычисление предикатов
времени компиляции, импликации логики Хоара — всё это различные проверки типов в конвейере
доказательства времени компиляции, разделяющие один и тот же конвейер. SMT-решатель — это модуль
ускорения проверки типов, а не отдельный доверенный рубеж. Когда компилятор возвращает Unproven,
программист пишет функцию YaoXiang в качестве доказательства — проверщик типов верифицирует её точно
так же, как верифицирует тип возврата любой функции. Всё есть код YaoXiang, всё проверяется
проверщиком типов.

## Мотивация

### Почему RFC-022 устарел?

RFC-022 проектировал спецификации как аннотации `//!`:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0          ← это аннотация, отдельная от типов
    //! ensures: ExistsMax(result, arr[0..n])   ← это аннотация, отдельная от типов
}
```

Это фундаментальная ошибка изоморфизма Карри-Ховарда: **разделение спецификаций и типов на два
слоя**. Аннотации не являются типами. Аннотации не участвуют в проверке типов. Аннотации — это
ментальная модель «внешнего инструмента».

В whitepaper сказано прямо:

> «Нет аннотаций `//!`. Нет отдельного языка спецификаций. Всё внутри системы типов.»

### Текущие проблемы

- Аннотации `//!` из RFC-022 — это внешний синтаксис, отдельный от системы типов
- Типы спецификаций и обычные типы — это две разные системы, что приводит к концептуальной
  избыточности
- Модель разделения «Debug Build — верификация, Release Build — игнорирование» нарушает единство
- SMT-решатель в традиционном понимании позиционируется как внешний инструмент — YaoXiang встраивает
  его как модуль ускорения проверщика типов
- Проверка типов, верификация заимствований, проверка предикатов времени компиляции, раскрытие
  макросов — каждая идёт своим путём

### Правильная ментальная модель

Проверку типов можно абстрагировать как функцию:

```
verify : Program → Proved | Disproved(Model) | Unproven
```

Все проверки времени компиляции — простое сопоставление типов, обнаружение конфликтов заимствований,
верификация предикатов времени компиляции — являются подзадачами этой функции. Они разделяют один и
тот же конвейер доказательства, отличаясь лишь сложностью доказательств и стратегиями построения.

Когда компилятор возвращает Unproven, программист предоставляет функцию-доказательство — тип
возврата этой функции равен доказываемому утверждению. Проверщик типов верифицирует её. Это та же
самая операция, что и обычная проверка типов.

## Предложение

### 1. `{}` — пространство доказательств: тип есть утверждение, верификация есть проверка типов

`{}` в YaoXiang — это пространство доказательств времени компиляции. Всё внутри является
утверждением, и компилятор гарантирует, что каждый элемент истинен — либо автоматически доказан,
либо предоставлен программистом как функция-доказательство.

```
Point: Type = { x: Float, y: Float }
#               ^^^^^^^^^^^^^^^^^^^^^  Компилятор гарантирует, что x — Float, y — Float

List: (T: Type) -> Type = { data: Array(T) }
#                           ^^^^^^^^^^^^^^^  Компилятор гарантирует, что data — Array(T)
```

**Дженерики — частный случай предикатов времени компиляции.**

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }
#          ^^^^^^              ^^^^^^
#          Параметр в сигнатуре      Внутри {} только утверждения
#          Компилятор проверяет x > 0 при вызове во время компиляции

List: (T: Type) -> Type = { data: Array(T) }
#      ^^^^^^^^              ^^^^^^^^^^^^^^^
#      Параметр в сигнатуре   Компилятор проверяет type_of(T) == Type, type_of(data) == Array(T)
```

Один и тот же паттерн: `name: (params) -> Type = { утверждения }`. Компилятор не различает
«утверждения о типах» и «утверждения о значениях» — все они являются целями вычисления в конвейере
доказательства.

**Инварианты цикла не нужно записывать отдельно. Аннотация типа на переменной — это инвариант
Флойда-Хоара.**

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i — сообщает компилятору, что тип s зависит от i
    mut i: UpTo(arr.len) = 0     # При инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    while i < arr.len {
        s += arr[i]  # Компилятор проверяет: s_new == sum(arr[0..i+1])
        i += 1       # Изменение i → запускает повторную верификацию s: s удовлетворяет SumUpTo(arr, i_new)
    }
    return s  # s: SumUpTo(arr, arr.len) = sum(arr[0..arr.len])
}
```

Компилятор генерирует одно условие верификации для тела цикла — индуктивная гипотеза (аннотация
типа) → операция присваивания → удовлетворяет ли новое значение аннотации типа. После того как
конвейер доказательства подтвердит индуктивный шаг, все итерации покрываются автоматически. Не нужно
`: decreases`, не нужно `: Invariant`, не нужно индуктивное доказательство — компилятор разбивает
индукцию на локальные VC для каждого присваивания.

### 2. Предусловия/постусловия: предикаты времени компиляции в типах параметров и возврата

Отказываемся от `//! requires`/`//! ensures` из RFC-022. Предикаты времени компиляции выступают как
аннотации типов параметров или возврата.

**На стороне параметров — это вызов функции.** Предикат времени компиляции — это функция,
возвращающая Type, и использование на стороне параметров — это её вызов — точно так же, как
`factorial(5)`. На стороне возвращаемого значения вводится новое понятие: формальный параметр
возвращаемого значения.

```yaoxiang
# Предусловие: явный вызов предиката времени компиляции в типе параметра
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b
#                       ^^^^^^^^^^  b — имя текущего формального параметра, передаётся в Positive
#                       Компилятор извлекает значение аргумента в точке вызова, подставляет b, проверяет Positive(аргумент)
#                       Пример: divide(10, 2) → проверка Positive(2) = { 2 > 0 } → True
#                       Пример: divide(10, 0) → проверка Positive(0) = { 0 > 0 } → False → ошибка компиляции

# Постусловие: формальный параметр возвращаемого значения + предикат времени компиляции
IsMax: (T: Ord, arr: Array(T), result: T) -> Type = {
    forall j in 0..arr.len: result >= arr[j]
}

NonEmpty: (arr: Array(T)) -> Type = { arr.len > 0 }

max: (T: Ord) -> ((arr: NonEmpty(arr))) -> (result: IsMax(T, arr, result)) = {
#                                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                                            result — формальный параметр возвращаемого значения, значение предоставляется оператором return
#                                            Компилятор подставляет возвращаемое значение в точке return, проверяет постусловие
    candidate = arr[0]
    for i in 1..arr.len {
        if arr[i] > candidate { candidate = arr[i] }
    }
    return candidate
}
```

**Ключевые правила**:

- **На стороне параметров**: `b: Positive(b)` — `b` — имя текущего формального параметра, передаётся
  в `Positive` в качестве аргумента. Синтаксис вызова функции, ноль неявного.
- **На стороне возврата**: `-> (result: IsMax(T, arr, result))` — `result` — формальный параметр
  возвращаемого значения, значение предоставляется оператором `return`. `result` существует только в
  сигнатуре типа, на него ссылается только предикат, он не попадает в область видимости тела функции
  и не появляется у вызывающего.
- **Формальный параметр возвращаемого значения необязателен**: если нет постусловия, он не пишется,
  и сигнатура полностью совпадает с обычной функцией (`-> Int`).
- **Единство**: параметры и формальные параметры возвращаемого значения — одно и то же понятие —
  `имя_параметра: вызов_предиката(имя_параметра)`, разница лишь в том, предоставляется ли значение
  вызывающим или оператором `return`.

### 3. Распространение путевых условий: верификация значений времени выполнения во время компиляции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно. Когда значения времени выполнения попадают в параметры уточнённого типа,
компилятор выполняет верификацию путём сбора путевых условий и проверки импликации SMT — без явной
передачи доказательства от программиста.

#### 3.1 Явный вызов функции

Когда предикат времени компиляции используется в позиции связывания, аргументы передаются
программистом явно — это вызов функции, ноль неявного.

`Positive: (x: Int) -> Type = { x > 0 }` — это конструктор предиката времени компиляции. Когда он
появляется в позиции связывания (объявление параметра, объявление переменной, тип возврата),
программист явно передаёт имя уже связанной переменной:

```yaoxiang
b: Positive(b)
// b уже объявлен как текущий формальный параметр, Positive(b) — вызов функции
// После нормализации: b: { b > 0 }
```

Компилятору не нужно неявно подставлять аргументы — `b: Positive(b)` работает так же, как `f(5)`.
Это просто вызов функции. `b` связывается как имя параметра, и его аннотация типа `Positive(b)`
ссылается на `b` сам — это стандартный паттерн зависимых типов, а не неявное правило раскрытия.

**Единство с `self` из RFC-010**: RFC-010 установил, что `self` — не ключевое слово, а просто
конвенциональное имя параметра («написать `p`, `this`, `x` — совершенно одинаково»).
`b: Positive(b)` использует тот же механизм — имя параметра может быть использовано в аннотации
типа. `self` появляется в позиции `self: Point`, `b` появляется в позиции `b: Positive(b)`, обе
аннотации ссылаются на сам параметр. Разница лишь в сложности аннотации типа, механизм полностью
одинаков — после связывания имени тип может зависеть от этого имени.

Тип возврата также использует явный вызов функции:

```yaoxiang
Sorted: (arr: Array(T)) -> Type = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }

sort: (arr: Array(T)) -> (result: Sorted(result)) = { ... }
//                        ^^^^^^^^^^^^^^^^^^^^^^^
//                        result — формальный параметр возвращаемого значения, Sorted(result) — вызов функции
//                        Компилятор в точке return подставляет возвращаемое значение в result, проверяет Sorted(возвращаемое_значение)
```

То же применимо к объявлениям локальных переменных:

```yaoxiang
let x: Positive(x) = 5
// x связывается с 5, Positive(5) → { 5 > 0 } → True → проходит

// let y: Positive(y) = 0
// y связывается с 0, Positive(0) → { 0 > 0 } → False → ошибка компиляции
```

#### 3.2 Сбор путевых условий

Когда значение времени выполнения появляется в условной ветви, компилятор автоматически собирает
путевые условия, формируя **множество предположений** текущей области видимости. Эти предположения
участвуют в верификации как фоновое знание для вычисления Bool во время компиляции.

```yaoxiang
if y > 0 {
    // Компилятор автоматически получает в этой ветви предположение: { y > 0 }
    let result = divide(x, y)
    // Условие верификации: (y > 0) ⇒ (y > 0)
    // Конвейер доказательства устанавливает истинность импликации → Proved
} else {
// В этой ветви предположение: { !(y > 0) }
// Если вызвать divide(x, y), условие верификации: !(y > 0) ⇒ y > 0
    // Конвейер доказательства устанавливает ложность импликации → Disproved
}
```

Это не зашитый в компилятор специальный паттерн — это естественное поведение конвейера
доказательства времени компиляции. При каждой проверке типов в точке вызова в конвейер отправляется:

```
{фоновые предположения} ⇒ {цель верификации}
```

Конвейер доказательства проверяет импликацию. Proved → проходит, Disproved → ошибка компиляции +
контрпример, Unproven → ошибка компиляции + неразрешённое утверждение. Фоновые предположения берутся
из путевых условий текущей программной точки.

#### 3.3 Стек предположений

Компилятор при анализе потока управления поддерживает для каждого базового блока множество
предположений:

- **if-guard**: `if y > 0` → true-ветвь добавляет `y > 0`, false-ветвь (если есть else) добавляет
  `!(y > 0)`
- **паттерны match**: `if let Some(v) = opt` → в ветви добавляется `opt == Some(v)`
- **логические связки**: `if x > 0 and y < 10` → в ветви добавляются `x > 0` и `y < 10`
- **предусловия функций**: при вызове `divide(a, b)` свидетельство того, что `b` удовлетворяет
  `Positive`, должно прийти либо из текущих предположений, либо из аннотации уточнённого типа самого
  аргумента (если `b` уже аннотирован как `Positive`, то его тип несёт `b > 0`)
- **присваивание**: при `let z = y` существующие уточняющие условия на `y` переносятся на `z`

Все предположения поступают в конвейер доказательства времени компиляции. При переходе на путь
SMT-ускорения они транслируются в фоновые утверждения SMT-LIB.

#### 3.4 Без статического свидетельства — ошибка компиляции

Если программист пишет напрямую:

```yaoxiang
divide_user_input: (x: Int, y: Int) -> Int = divide(x, y)
```

В текущей программной точке нет предположения `y > 0`, и сам аргумент `y` не имеет аннотации типа
`Positive`. Условие верификации:

```
{} ⇒ { y > 0 }
```

Конвейер возвращает `Disproved` (импликация не держится) → ошибка компиляции:

> Невозможно доказать, что параметр `b` удовлетворяет `Positive` в вызове `divide`. `y` приходит из
> ввода функции, без доказанных границ. Рассмотрите использование if-ветви для защиты вызова:
> `if y > 0 { divide(x, y) }`.

YaoXiang не допускает попадания значений времени выполнения в параметры уточнённого типа без
предоставления статического свидетельства. Это не ограничение — это ядро философии жёсткой
безопасности. Всё, что компилятор не может статически доказать, не проходит компиляцию.

#### 3.5 Связь с единым конвейером

Распространение путевых условий — не дополнительный механизм. Это прямое расширение конвейера
доказательства времени компиляции на анализ потока управления:

| Этап                                  | Обязанность                                                                                                                                                                            |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор путевых условий                  | Фаза анализа потока управления компилятора, аннотирующая каждый базовый блок множеством предположений                                                                                  |
| Генерация условий верификации         | При обнаружении ограничения типа, требующего проверки, объединение путевых условий + информации о типах аргументов                                                                     |
| Вычисление в конвейере доказательства | Ядро компилятора → SMT-ускорение → получение Proved / Disproved / Unproven                                                                                                             |
| Результат                             | `Proved` → проходит; `Disproved` → ошибка компиляции + контрпример; `Unproven` → ошибка компиляции + неразрешённое утверждение (программист может предоставить функцию-доказательство) |

Никаких новых компонентов. Никаких специальных правил. Путевые условия — это фоновое знание
конвейера доказательства, разделяющее один конвейер и систему бюджета с равенством типов и
ограничениями заимствования.

### 4. Конвейер доказательства времени компиляции

Все проверки времени компиляции разделяют один конвейер. Центральная операция конвейера — **проверка
типов** — проверка того, равен ли тип доказательства доказываемому утверждению. Всё есть проверка
типов.

```
Во время компиляции встречается выражение Bool, требующее вычисления (т.е. нужно построить доказательство)
        │
        ├── Равенство типов (T1 == T2)
        │   → Компилятор выносит решение напрямую (структурная эквивалентность)
        │
        ├── Условие конфликта токенов (!conflicting(tokens))
        │   → Потоко-чувствительный анализ живучести (отслеживание Dup/Linear)
        │
        ├── Редукция зависимых типов (n + m упрощение)
        │   → Система переписывания термов времени компиляции (βδι-редукция)
        │
        ├── Предикат времени компиляции (x > 0, forall...)
        │   → Собственно компилятор + модуль SMT-ускорения
        │
        └── Импликация логики Хоара (P ⇒ Q)
            → Компилятор + модуль SMT-ускорения
                    │
                    ▼
             ┌──────────┐
             │ Proved   │  → Компиляция проходит
             │ Disproved│  → Ошибка компиляции + контрпример
             │ Unproven │  → Ошибка компиляции + неразрешённое утверждение
             └────┬─────┘
                  │
                  ▼
         Программист пишет функцию-доказательство (код YaoXiang)
                  │
                  ▼
         Проверщик типов верифицирует ──→ Proved ──→ Компиляция проходит
                  │
                  ▼
            Верификация не прошла → Ошибка компиляции: «Доказательство неверно»
```

#### 4.1 Результат доказательства: трёхзначная алгебра

Вычисление времени компиляции возвращает три результата — неизбежное следствие проблемы останова и
естественное деление теории доказательств:

```
eval_compile_time : BoolExpr → Proved | Disproved(Model) | Unproven
```

- **Proved** → Останов, доказательство построено, проверка типов пройдена. Компиляция продолжается.
- **Disproved(M)** → Останов, существует контрпример M. Ошибка компиляции + контрпример + позиция в
  исходнике.
- **Unproven** → В пределах данного лимита ресурсов доказательство не построено. Ошибка компиляции +
  неразрешённое утверждение + отчёт о расходе бюджета.

**Unproven ≠ False.** «Я не могу доказать» от компилятора не означает ложность утверждения — это
лишь за пределами текущих возможностей автоматического доказательства. Это честность, не дефект.

Жёсткое ограничение бюджета — инженерное решение проблемы останова. Без ручек — давать ручку
означает спрашивать у пользователя «думаете ли вы, остановится ли ваша программа», пользователь не
знает, компилятор тоже.

#### 4.2 После Unproven: программист пишет доказательство

Когда компилятор возвращает Unproven, программист может написать **функцию-доказательство** — это
просто функция YaoXiang, тип возврата которой равен доказываемому утверждению. Проверщик типов
верифицирует эту функцию — точно так же, как он верифицирует, что `add(a, b): Int`.

```
Утверждение  = Тип
Доказательство = Программа (значение этого типа)
Верификация = Проверка типов (единственный корень доверия)
```

SMT-решатель — не отдельный доверенный рубеж — это **модуль ускорения проверщика типов**. SMT
помогает найти доказательство, но верифицирует доказательство всегда проверщик типов. Когда SMT
возвращает `unsat`, компилятор перестраивает его результат в доказательство, верифицируемое
проверщиком типов. Если перестроение не удаётся (шаги рассуждения SMT выходят за рамки правил вывода
ядра компилятора), происходит откат к Unproven — программист может вручную написать
функцию-доказательство.

```yaoxiang
# Утверждение: уточнённое свойство, которое компилятор не может доказать автоматически
FirstIsMin: (T: Ord, arr: Sorted(T)) -> Type = {
    forall i in 0..arr.len: arr[0] <= arr[i]
}

# Доказательство: программист пишет функцию, тип возврата которой — указанное выше утверждение
# Проверщик типов верифицирует эту функцию — точно так же, как верифицирует add(a,b): Int
first_is_min: (T: Ord, arr: Sorted(T)) -> FirstIsMin(T, arr) = {
    # Компилятор здесь проверяет: тип тела функции = FirstIsMin(T, arr)
    ...
}
```

Никакого ИИ, никакого экспорта в Coq, никаких новых концепций. **Свойства, которые компилятор не
может доказать автоматически → программист пишет доказательство на YaoXiang → проверщик типов
верифицирует.** Весь процесс — плавный градиент — компилятор делает за вас простые доказательства,
оставляя мозг для сложных.

#### 4.3 Слоистые зависимости внутри конвейера

Вышеуказанные вычислители используют общий интерфейс, но имеют порядок вычисления. Равенство типов —
предпосылка для всего последующего анализа; проверка владения/токенов зависит от информации о типах;
верификация уточняющих предикатов зависит от результатов предыдущих двух слоёв. Компилятор вычисляет
по слоям, выражения с неудачей на нижнем слое не попадают на верхний — избегая траты бюджета решения
на программу с ошибками типов.

```
Порядок вычисления (один конвейер, послойная диспетчеризация)
├── Слой 0: Равенство типов (T1 == T2)
│   └── Структурная унификация → при неудаче дальнейшее бессмысленно, прямой возврат Disproved
├── Слой 1: Конфликты владения/токенов
│   └── Потоко-чувствительный анализ живучести → при неудаче безопасность памяти не держится, прямой возврат Disproved
└── Слой 2: Уточняющие предикаты / импликации Хоара
    └── Собственно компилятор → SMT-ускорение → получение Proved / Disproved / Unproven
```

Каждый слой по-прежнему возвращает `Proved/Disproved/Unproven`, разделяя общий интерфейс и общую
систему бюджета.

### 5. Единство трёх слоёв функций

| Слой                        | Время выполнения | Вход          | Выход    | Пример                                         |
| --------------------------- | ---------------- | ------------- | -------- | ---------------------------------------------- |
| Функция-значение            | Runtime          | Значения      | Значение | `add: (a: Int, b: Int) -> Int = a + b`         |
| Конструктор типов           | Compile-time     | Типы/значения | Type     | `List: (T: Type) -> Type = { data: Array(T) }` |
| Предикат времени компиляции | Compile-time     | Значения      | Type     | `Positive: (x: Int) -> Type = { x > 0 }`       |

Все используют одинаковый синтаксис `name: type = value`. Предикаты времени компиляции и
конструкторы типов идут по одному конвейеру доказательства времени компиляции — `{}` — пространство
доказательств.

### 6. Циклы: генерация условий верификации Флойда-Хоара

Циклы не требуют отдельных аннотаций `: Invariant(...)` или `: decreases(...)`. Аннотации
уточняющего типа на переменных определяют утверждения в стиле Флойда-Хоара — компилятор генерирует
условия верификации из аннотаций типов, а конвейер доказательства проверяет, сохраняет ли каждое
присваивание тип.

Центральный механизм: каждой операции присваивания соответствует тройка Хоара `{P} x := e {Q}`,
условие верификации — `P ⇒ Q[e/x]`. Компилятор генерирует одно условие верификации для тела цикла —
после того как конвейер доказательства подтвердит индуктивный шаг, все итерации покрываются
автоматически.

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0   # Аннотация ссылается на i; при инициализации i=0, проверка: 0 == sum(arr[0..0]) → True
    mut i: UpTo(arr.len) = 0     # Проверка: 0 <= 0 <= arr.len → True
    while i < arr.len {
        # Компилятор генерирует одно VC для тела цикла. Посылка: s удовлетворяет SumUpTo(arr, i), i удовлетворяет UpTo(arr.len).
        #
        # s += arr[i]:
        #   Обязательство верификации: s_new удовлетворяет SumUpTo(arr, i) (текущий i неизменен)
        #   Подставляя s_new = s_old + arr[i]:
        #     Нужно s_old + arr[i] == sum(arr[0..i+1])
        #     Из индуктивной гипотезы s_old == sum(arr[0..i]), прибавив arr[i] к обеим сторонам:
        #     sum(arr[0..i]) + arr[i] == sum(arr[0..i+1])
        #   Компилятор + SMT: линейная арифметика, миллисекунды → Proved
        #
        # i += 1:
        #   i изменён → в графе зависимостей аннотация типа s ссылается на i → запуск повторной верификации
        #   Новая цель верификации: s удовлетворяет SumUpTo(arr, i_new)
        #   Т.е. s == sum(arr[0..i_new]), что гарантировано предыдущим шагом → Proved
        s += arr[i]
        i += 1
    }
    return s  # В этот момент s: SumUpTo(arr, arr.len), т.е. s == sum(arr[0..arr.len])
}
```

Инвариант цикла — это аннотация типа на переменной — программист пишет тип, компилятор проверяет
индуктивный шаг. Компилятору не нужно «обнаруживать» инвариант или «автоматически делать индукцию» —
он разбивает индуктивное доказательство на локальные условия верификации для каждой операции
присваивания и передаёт их в конвейер доказательства.

#### 6.1 Отслеживание зависимостей: зависимые типы на мутабельных переменных

Предпосылка вышеуказанного механизма: компилятор знает, что аннотация типа `s` — `SumUpTo(arr, i)` —
ссылается на `i` — когда `i` изменяется, ограничение типа `s` также изменяется. Это требует от
компилятора поддерживать **граф зависимостей типов между переменными**.

**Структура данных**:

```
TypeDepGraph: Map<VarName, Set<VarName>>
# Ключ — зависимая переменная, значение — множество переменных, на которые ссылается аннотация типа
# Пример: { i: {s}, j: {s, t}, ... }
```

**Построение**: при обработке `mut v: Pred(... x ...) = init` проверщик типов разбирает свободные
переменные в аргументах `Pred(...)`. Если в аргументах есть ссылка на другую мутабельную переменную
`x` в текущей области видимости, в графе зависимостей записывается `x → v`.

**Запуск**: когда зависимая переменная `x` получает присваивание, компилятор:

1. Находит в графе зависимостей все переменные `{v₁, v₂, ...}`, зависящие от `x`
2. Для каждого `v` генерирует условие верификации: удовлетворяет ли текущее значение `v`
   обновлённому типу `Pred(... x_new ...)`
3. Отправляет VC в конвейер доказательства

**Чувствительность к порядку присваивания**: отслеживание зависимостей естественным образом
форсирует правильный порядок присваивания. Для `SumUpTo(arr, i)`:

```yaoxiang
# Правильный порядок
s += arr[i]   # s_new удовлетворяет SumUpTo(arr, i+1)
i += 1        # i изменён → повторная верификация s удовлетворяет SumUpTo(arr, i_new) → True

# Неправильный порядок — компилятор отвергает
i += 1        # i изменён → повторная верификация s удовлетворяет SumUpTo(arr, i_new)
              # s ещё не обновлён, s_old == sum(arr[0..i_old]) ≠ sum(arr[0..i_new])
              # → Ошибка компиляции: переменная s не удовлетворяет типу SumUpTo(arr, i_new)
s += arr[i]   # Недостижимо
```

**Комбинированные зависимости**: переменная может зависеть от нескольких переменных. Аннотация типа
`{ v: Int; v == x + y }` одновременно зависит от `x` и `y` — изменение любой из них запускает
повторную верификацию.

**Связь с конвейером доказательства**: отслеживание зависимостей — триггер генерации VC, не
отдельный механизм верификации. Он отвечает на вопрос «когда нужно генерировать VC» — конвейер
доказательства отвечает на вопрос «выполняется ли VC».

### 7. Проверка завершимости

Полностью автоматически во время компиляции. Циклы, которые компилятор может доказать, проходят;
циклы, которые не может, сразу дают ошибку компиляции — программист обязан сделать так, чтобы
компилятор мог автоматически анализировать завершимость. Без полуавтоматических аннотаций.

#### 6.1 Принципы проектирования

Компилятор автоматически извлекает информацию для доказательства завершимости из двух мест:

1. **Аннотации типов переменных**: граничные ограничения в уточнённых типах (например, `UpTo(n)`
   даёт верхнюю границу `n` и нижнюю `0`)
2. **Операции в теле цикла**: операции, применяемые к переменным на каждой итерации

Компилятор по приоритету пробует четыре стратегии синтеза меры, останавливаясь на первой успешной.

#### 6.2 Стратегия 1: автоматический синтез линейной ранговой функции

Когда переменная имеет аннотацию линейной границы, компилятор перебирает кандидатов линейной меры и
проверяет SMT.

```
Вход:
  Переменные v₁: UpTo(u₁), v₂: UpTo(u₂), ... (переменные с границами)
  Условие цикла cond
  Множество присваиваний в теле цикла

Алгоритм:
  1. Извлечь границы каждой переменной из аннотаций типов: [low_i, high_i]
  2. Перебрать кандидатов мер: v_i, u_i - v_i, v_i - v_j, и т.п. линейные комбинации
  3. Для каждого кандидата m:
     - SMT-проверка m ≥ 0 (из границ типа)
     - Для каждого пути выполнения тела цикла SMT-проверка m' < m (строгое убывание)
  4. Найти подходящую линейную комбинацию → завершимость доказана
```

Покрытие: циклы, где переменной присваивается линейное выражение (`v = a·v + b`) и есть аннотация
ограниченного типа. Включает `i += const`, `i -= const`, а также сокращение интервала в стиле
двоичного поиска:

```yaoxiang
# Двоичный поиск: low = mid + 1 или high = mid
# Мера high - low строго убывает на обоих путях
binary_search: (arr: Sorted(Int, arr), key: Int) -> Option(Int) = {
    mut low: UpTo(arr.len) = 0
    mut high: UpTo(arr.len) = arr.len
    while low < high {
        let mid = (low + high) / 2
        if arr.data[mid] < key { low = mid + 1 }
        else if arr.data[mid] > key { high = mid }
        else { return Some(mid) }
    }
    return None
}
```

#### 6.3 Стратегия 2: подсчёт нарушений предиката — автоматическое извлечение меры из целевого типа <span style="color:orange">[Экспериментальная стратегия]</span>

> ⚠️ **Текущий статус: экспериментальная стратегия, решение о включении принимается на Фазе 3 на
> основе реальной выполнимости.** Эта стратегия работает для соседних обменов (сортировка пузырьком,
> сортировка вставками), но не может автоматически доказать несмежные операции (partition быстрой
> сортировки, sift-down пирамидальной сортировки). Границы покрытия в таблице ниже. Если на Фазе 3
> проверка покажет невыполнимость, эта стратегия будет удалена или переведена в будущую работу.

Центральная интуиция: **спецификации, написанные пользователем, — это материал для рассуждений
компилятора.** Компилятору не нужно встраивать «что такое отсортированность» — он читает определение
`Sorted` и автоматически извлекает из него меру.

```
Вход:
  Целевой тип: Sorted(arr) = { forall i in 0..arr.len-1: arr[i] <= arr[i+1] }
  Операция в теле цикла: обмен соседних элементов

Алгоритм:
  1. Разобрать определение предиката: forall i in range: cond(i, arr)
  2. Автоматически сгенерировать меру: violation_count = |{ i | ¬cond(i, arr) }|
  3. Проанализировать влияние операции на меру:
     - Обмен соседних arr[j], arr[j+1] = arr[j+1], arr[j]
     - Влияет только на пары с индексами j-1, j, j+1
     - Если arr[j] > arr[j+1] (нарушение предиката), после обмена эта пара удовлетворяет предикату
     - violation_count уменьшается хотя бы на 1
  4. Верхняя граница: n·(n-1)/2 (максимальное число соседних инверсий), нижняя: 0
  → Завершимость доказана
```

**Текущее покрытие**:

| Алгоритм                 | Паттерн операции     | Стратегия 2 доказуема? | Причина                                              |
| ------------------------ | -------------------- | :--------------------: | ---------------------------------------------------- |
| Сортировка пузырьком     | Соседний обмен       |           ✅           | violation_count строго убывает при каждом обмене     |
| Сортировка вставками     | Соседнее перемещение |           ✅           | Каждое перемещение устраняет одну нарушающую пару    |
| Сортировка выбором       | Несмежный обмен      |           ❌           | Один обмен может увеличить violation_count           |
| Быстрая сортировка       | partition            |           ❌           | Несмежный обмен, не гарантирует монотонного убывания |
| Пирамидальная сортировка | sift-down            |           ❌           | Древовидная операция, violation_count не монотонен   |

**Дополняющие стратегии**: для быстрой сортировки сокращение интервала `low < high` покрывается
стратегией 1 (линейная ранговая функция) — внешняя partition-рекурсия, интервал каждый раз
уменьшается вдвое. Стратегии 1 и 2 дополняют друг друга, завершимость большинства практических
алгоритмов доказуема одной из них. Но обобщение стратегии 2 (несмежные операции, древовидные
операции) остаётся открытой проблемой.

```yaoxiang
sort: (arr: Array(Int)) -> (result: Sorted(result)) = {
    mut i: UpTo(arr.len) = 0
    while i < arr.len - 1 {
        mut j: UpTo(arr.len - i - 1) = 0
        while j < arr.len - i - 1 {
            if arr.data[j] > arr.data[j+1] {
                arr.data[j], arr.data[j+1] = arr.data[j+1], arr.data[j]
            }
            j += 1
        }
        i += 1
    }
    return arr
}
```

#### 6.4 Стратегия 3: паттерн ограниченного инкремента/декремента

`v += const` (const — положительное число), переменная имеет аннотацию верхней границы → мера
`upper_bound - v` убывает на `const` каждый раз, нижняя граница 0. Это вырожденный случай стратегии
1, компилятор обрабатывает его в первую очередь.

#### 6.5 Стратегия 4: шаблон меры мультипликативного сжатия

`v *= const` (const > 1), переменная имеет аннотацию верхней и нижней границ. Компилятор имеет
встроенный логарифмический шаблон меры `ceil(log_const(upper/v))`, при каждом умножении на const
мера уменьшается на 1.

```yaoxiang
mut i: Positive(i) = 1
while i < n {
    # Компилятор автоматически выводит: мера ceil(log₂(n/i)), при каждом умножении на 2 мера уменьшается на 1
    i *= 2
}
```

#### 6.6 Разделение завершимости и корректности

Доказательство завершимости и доказательство корректности независимы:

- **Завершимость**: четыре вышеуказанные стратегии автоматически доказывают, что цикл завершается за
  конечное число шагов
- **Корректность**: продвигается ли тело цикла к целевому типу, проверяется конвейером
  доказательства времени компиляции через условия верификации

Оба проходят → компиляция проходит. Завершимость доказана, но корректность не доказана → ошибка
компиляции + контрпример. Корректность доказана, но завершимость не доказуема → ошибка компиляции с
указанием переменной или операции, которую не удалось проанализировать. Оба не доказаны → ошибка
компиляции с отдельным указанием обеих причин.

#### 6.7 Проверка завершимости рекурсивных функций

Для рекурсивных функций, требующих вычисления во время компиляции, компилятор проверяет убывание
аргументов:

```yaoxiang
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Компилятор анализирует: n-1 < n → убывает → завершается
}

# Использование во время компиляции — компилятор гарантирует завершимость factorial
vec: Vec(factorial(5)) = Vec(120)()  # 5! = 120, вычисление во время компиляции
```

| Сценарий                                                           | Поведение                          |
| ------------------------------------------------------------------ | ---------------------------------- |
| Компилятор может проанализировать рекурсивное убывание (как `n-1`) | Вычисление во время компиляции     |
| Не убывает / невозможно определить убывание                        | Ошибка компиляции                  |
| Вызов во время выполнения (вне позиции типа)                       | Проверка завершимости не требуется |

#### 6.8 Жёсткие границы

`i = f(i)`, где `f` необратима, не замкнута, не сохраняет никакой монотонности — математически
невозможно автоматически доказать завершимость. Ошибка компиляции:

> Завершимость этого цикла не может быть доказана автоматически. Переменная цикла зависит от
> неанализируемой функции `f`. Пожалуйста, используйте паттерн итерации, который может быть
> проанализирован компилятором.

Это не провал компилятора. Всё, что не может быть статически доказано как безопасное, не проходит
компиляцию.

### 8. SMT-решатель: модуль ускорения проверщика типов

SMT-решатель в традиционных языках — внешний инструмент (например, F\* вызывает Z3, Dafny вызывает
Z3). В YaoXiang — это **модуль ускорения проверщика типов** — вызывается только тогда, когда ядро
компилятора само не может вынести решение. SMT помогает найти доказательство, но доказательство
верифицирует проверщик типов.

**Модель доверия**: проверщик типов — единственный корень доверия. SMT-решатель — модуль ускорения —
он помогает найти доказательство, но SMT не является отдельным доверенным рубежом. Компилятор
доверяет результату `unsat` от Z3 (как и путь F\*/Dafny — вероятность ошибки Z3 ниже вероятности
бага в самом компиляторе, это инженерно прагматичный выбор). Реальная ненадёжность контролируется на
уровне трансляции в SMT — если в трансляции баг, компилятор обнажит его в других тестах.

**Интерфейс**: внутренняя трансляция компилятора — в стандартный формат SMT-LIB 2.6, а не привязка к
API конкретного решателя. SMT-LIB — стандарт ISO, Z3, CVC5, MathSAT, Yices — все поддерживают его
нативно.

**Бэкенд по умолчанию**: Z3 (лицензия MIT, самая обширная документация и валидация сообществом).
CVC5 как SMT-LIB-совместимая альтернатива — пользователь может переключаться флагом компилятора.

Без «универсального слоя абстракции решателя» — SMT-LIB и есть слой абстракции. В будущем, если CVC5
добьётся прорыва в определённой теории, переключение потребует только смены бинарника, без изменения
кода компилятора.

```
Выражение Bool времени компиляции
        │
        ├── Ядро компилятора может решить напрямую (структурная эквивалентность, простая арифметика,
        │   тривиальные формулы после свёртки констант)
        │   → Прямой возврат Proved / Disproved
        │
        └── Ядро компилятора не может решить напрямую (кванторы, символьные переменные)
            → Пре-редукция зависимых типов (factorial(5) → 120)
            → Трансляция в формат SMT-LIB
            → Отправка в Z3/CVC5 (с ограничением бюджета)
            → Возврат: unsat → Proved  │  sat + модель → Disproved  │  unknown → Unproven
```

**Бюджет решения — жёсткое ограничение, как глубина стека**:

| Измерение бюджета                 | По умолчанию | Описание                                                                                                                                                      |
| --------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Число шагов решения               | 10,000       | Z3 для линейной арифметики обычно укладывается в сотни шагов. 10,000 шагов покрывает 99% практических предикатов.                                             |
| Время                             | 100ms        | Один предикат свыше 100ms = пользователь пишет программу времени компиляции, а не аннотацию типа. 100ms × 50 предикатов = верхний предел 5 секунд компиляции. |
| Глубина инстанцирования кванторов | 3            | Три уровня вложенных кванторов покрывают практические паттерны. Свыше трёх уровней — скорее всего, логическая головоломка.                                    |

Превышение бюджета возвращает Unproven, ошибка компиляции + позиция предиката + расход. Без
деградации, без проверок во время выполнения, без silent pass.

**Почему это практически реализуемо**: в инженерии 95% практических предикатов — линейная арифметика
— `x > 0`, `arr.len > 0`, `0 <= idx < arr.len` — всё в пределах разрешимого фрагмента, SMT-решатель
для таких задач возвращает за миллисекунды. При встрече с редкими сложными предикатами, превышающими
бюджет, программист пишет функцию-доказательство.

Зависимые типы перед вызовом SMT проходят пре-редукцию: `factorial(5)` напрямую вычисляется во время
компиляции в `120`, `append([1,2], [3])` напрямую вычисляется в `[1,2,3]`. Эти детерминированные
вычисления значений не потребляют бюджет SMT.

Программисту не нужно знать о существовании SMT. Ментальная модель: **компилятор может доказать —
проходит, не может — ошибка — если компилятор не умеет, можно написать функцию, которая докажет
ему**.

### 9. Композиция предикатов времени компиляции

Предикаты времени компиляции — это функции, возвращающие Type, композиция реализуется естественно
через композицию функций:

```yaoxiang
SortedNonEmpty: (T: Ord, arr: Array(T)) -> Type = {
    Sorted(T, arr) and NonEmpty(arr)
}
```

### 10. Примеры кода

#### 9.1 Безопасность деления

```yaoxiang
Positive: (x: Int) -> Type = { x > 0 }

divide: (a: Int, b: Positive(b)) -> Int = a / b

result = divide(10, 2)   # ✅ Компилятор проверяет Positive(2) = { 2 > 0 } → True
# result = divide(10, 0)  # ❌ Компилятор проверяет Positive(0) = { 0 > 0 } → False
```

#### 9.2 Безопасность доступа к массиву

```yaoxiang
InBounds: (idx: Int, arr: Array(T)) -> Type = { 0 <= idx and idx < arr.len }

get: (arr: Array(T), idx: InBounds(idx, arr)) -> T = arr.data[idx]

arr = Array(Int)(1, 2, 3)
x = get(arr, 1)   # ✅ Компилятор проверяет InBounds(1, arr) = { 0 <= 1 and 1 < 3 } → True
# y = get(arr, 5)  # ❌ Компилятор проверяет InBounds(5, arr) = { 0 <= 5 and 5 < 3 } → False
```

#### 9.3 Корректность сортировки

```yaoxiang
Sorted: (T: Ord, arr: Array(T)) -> Type = {
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

sort: (T: Ord) -> ((arr: Array(T))) -> (result: Sorted(T, result)) = {
    result = arr.clone()
    # ... реализация алгоритма сортировки ...
    return result
}
```

#### 9.4 Цикл: генерация VC компилятором

```yaoxiang
SumUpTo: (arr: Array(Int), i: Int) -> Type = { s: Int; s == sum(arr[0..i]) }
UpTo: (n: Int) -> Type = { i: Int; 0 <= i <= n }

sum: (arr: Array(Int)) -> Int = {
    mut s: SumUpTo(arr, i) = 0
    mut i: UpTo(arr.len) = 0
    while i < arr.len {
        s += arr[i]
        i += 1
    }
    return s
}
```

### 11. Конвейер диспетчеризации dispatch: единство компиляции и выполнения

`assert` и `Assert` — это две стороны одного примитива уточнённого типа. Конвейер диспетчеризации
`dispatch` по **достижимости свободных переменных предиката во время компиляции** автоматически
решает, идти ли по пути доказательства во время компиляции или проверке во время выполнения:

| Критерий                                                                                                   | Режим           | Поведение                                                                                                           |
| ---------------------------------------------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------- |
| Все свободные переменные известны во время компиляции (параметры дженериков, константы времени компиляции) | **CompileTime** | В конвейер доказательства: Proved → стирается, Disproved → ошибка компиляции, Unknown → требуется доказательство    |
| Существуют свободные переменные из времени выполнения (параметры функций, внешний ввод, mut-переменные)    | **Runtime**     | Вставка проверки во время выполнения и инъекция уточняющего факта в потоко-чувствительное множество предположений Γ |

**Ключевое**: «Не удаётся определить» ≠ «Ложь». В режиме CompileTime Unknown требует доказательства
(без тихой деградации), в режиме Runtime утверждение во время компиляции вообще не имеет истинности
— никакой prover не напишет тождественно истинного доказательства для «пользователь мог ввести
отрицательное число», проверка во время выполнения — единственный soundness-выбор. Это не слабость
prover-а, это теоретическая неизбежность.

### 12. Потоко-чувствительное множество предположений Γ: распространение сильнейшего постусловия

Компилятор поддерживает потоко-чувствительное множество предположений Γ, отслеживающее истинные
утверждения в каждой точке потока управления.

**SP-распространение (сильнейшее постусловие)**:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
y = x + 1           // Γ = {x > 0, y > 1}  ← SP-распространение
```

**Kill set для mut-переменных**: после переприсваивания `mut`-переменной все предположения
относительно этой переменной удаляются из Γ:

```yaoxiang
assert(x > 0)       // Γ = {x > 0}
mut x = x - 5       // Γ = {}  ← x > 0 убито
```

Это жёсткое требование soundness — значение переменной изменилось, старые предположения
недействительны.

**Слияние ветвей**: при слиянии ветвей IF/ELSE или match Γ берёт пересечение предположений ветвей.
Только утверждения, истинные на всех путях, выносятся из ветви.

### 13. Уточнение модели стирания: стирание witness ≠ стирание check

Утверждение RFC-027 «уточнённые типы полностью стираются во время выполнения» относится к **proof
witness (токену доказательства)** — доказательства, верифицированные во время компиляции, не
порождают кода времени выполнения. Но проверка во время выполнения, вставленная диспетчеризацией в
режиме Runtime, сохраняется — это проверка Bool на уровне значений, а не witness на уровне типов.

Резюме: witness стирается, check сохраняется. Эти две вещи не конфликтуют, исходный тезис RFC-027
остаётся в силе.

## Детальное проектирование

### Изменения синтаксиса

| До (RFC-022)                          | После (данный RFC)                                                        |
| ------------------------------------- | ------------------------------------------------------------------------- |
| `//! requires: NonEmpty(n) = n > 0`   | Предикат времени компиляции как тип параметра `(b: Positive(b))`          |
| `//! ensures: ExistsMax(result, arr)` | Тип возврата с формальным параметром `-> (result: IsMax(T, arr, result))` |
| `/*! invariant: ... !*/`              | Аннотация уточняющего типа на переменной — инвариант Флойда-Хоара         |
| `//! decreases: n`                    | Полностью автоматический вывод функции меры компилятором                  |
| Спецификации — аннотации              | Спецификации — система типов                                              |

### Синтаксис

**У предикатов времени компиляции нет новых ключевых слов.** `{}` — пространство доказательств,
полностью совпадает с существующим синтаксисом определения типов. Предикат времени компиляции — это
функция, возвращающая Type — `name: (params) -> Type = { утверждения }`. Использование — вызов
функции — `Positive(b)`, `IsMax(T, arr, result)`.

```bnf
# Предикат времени компиляции = функция, возвращающая Type, внутри {} утверждения, верифицируемые компилятором
# Используется существующий синтаксис функций/типов, новые правила BNF не нужны
predicate ::= identifier ':' params '->' 'Type' '=' '{' assertions '}'
```

**Аргументы применения предиката должны быть в форме констант времени компиляции** — литералы,
переменные (связанные по имени) или однопараметрические применения типов (рекурсивное извлечение).
Непреобразуемые в константные выражения аргументы дают **E1092**, несовпадение числа аргументов с
параметрами предиката — **E1093** — уточняющие ограничения **никогда не отбрасываются молча** (ранее
непреобразуемый аргумент приводил к беззвучному исчезновению ограничения, и связывание, нарушающее
ограничение, молча проходило).

**Новое синтаксическое понятие: формальный параметр возвращаемого значения** — в `-> (name: Type)`
`name` — формальный параметр возвращаемого значения.

Формальный параметр возвращаемого значения — это **единственное синтаксическое понятие**, вводимое
YaoXiang в существующий синтаксис функций. Его семантика:

- Значение `name` предоставляется оператором `return`
- `name` существует только в сигнатуре типа, на него ссылается только постусловие-предикат
  (например, `-> (result: IsMax(T, arr, result))`)
- `name` не попадает в область видимости тела функции, не появляется у вызывающего
- Формальный параметр возвращаемого значения **необязателен** — без постусловия сигнатура полностью
  совпадает с обычной функцией (`-> Int`), не внося никакой дополнительной нагрузки

Причина введения: постусловию нужно ссылаться на «значение, которое функция собирается вернуть». Без
формального параметра возвращаемого значения компилятор мог бы ссылаться на возвращаемое значение в
предикате только через специальные правила (например, неявная переменная `$result` или
`__retval__`). Формальный параметр возвращаемого значения делает эту ссылку явной — это просто
формальный параметр, только значение предоставляется `return`, а не вызывающим.

**Функция-доказательство** — не новое понятие — это просто функция YaoXiang, тип возврата которой —
доказываемое утверждение. Когда компилятор возвращает Unproven, программист предоставляет
функцию-доказательство, и проверщик типов верифицирует её точно так же, как верифицирует тип
возврата любой функции. Никакого нового синтаксиса, новых ключевых слов, новых правил.

### Влияние на систему типов

- **Вселенная типов**: предикаты времени компиляции находятся на уровне Type₂ — функция, принимающая
  значения и возвращающая Type, на том же уровне, что и конструктор типов
- **Взаимодействие с дженериками**: предикаты времени компиляции могут иметь параметры дженериков,
  например `NonEmpty: (T: Type) -> (arr: Array(T)) -> Type`
- **Взаимодействие с владением**: выражения в предикатах времени компиляции подчиняются правилам
  владения, только чтение, не запись
- **Вывод типов**: аргументы предикатов времени компиляции участвуют в HM-выводе типов

### Представление во время выполнения

Предикаты времени компиляции обрабатываются во время выполнения **в соответствии с результатом
диспетчеризации dispatch**:

- **Режим CompileTime** (все свободные переменные известны во время компиляции): токен-свидетельство
  (witness) полностью стирается после прохождения доказательства.
  `Positive: (x: Int) -> Type = { x > 0 }` — параметр `b: Positive(5)` во время выполнения
  представлен как `Int`. Уточняющее условие `{ 5 > 0 }` пройдено, стирается.
- **Режим Runtime** (существуют свободные переменные времени выполнения): сохраняется проверка во
  время выполнения — выполняется проверка Bool на уровне значений, инъекция в потоко-чувствительное
  множество предположений Γ. Подробности в §11 конвейер диспетчеризации dispatch и §13 уточнение
  модели стирания.

Помещение предиката времени компиляции в позицию типа (например, `f(x: Positive(x))`) не порождает
обёрточного типа, не выделяет дополнительной памяти. Но когда `x` приходит из ввода времени
выполнения, **будет** вставлена проверка Bool во время выполнения.

**Ограничения взаимодействия с `ref`**: предикат времени компиляции может ссылаться только на
неизменяемые заимствования или значения с переданным владением. Предикат времени компиляции,
ссылающийся на значение по изменяемому заимствованию, не может быть гарантированно верифицирован во
время компиляции с сохранением результата во время выполнения — такое использование сразу даёт
ошибку компиляции.

### Изменения в компиляторе

1. **Парсер**: предикаты времени компиляции используют стандартный синтаксис функций, дополнительные
   правила разбора не нужны
2. **Конвейер доказательства времени компиляции**: единый интерфейс возврата
   Proved/Disproved/Unproven, автоматический выбор стратегии
3. **Модуль SMT-ускорения**: слой трансляции в SMT-LIB 2.6, бэкенд по умолчанию Z3, альтернатива
   CVC5
4. **Ядро проверщика типов**: реализация правил вывода — структурная эквивалентность, βδι-редукция,
   введение/устранение кванторов всеобщности. Это единственный корень доверия, SMT и доказательства
   программиста проходят верификацию через него
5. **Генерация условий верификации**: исчисление WP/SP + обязательства доказательства инвариантов
   цикла
6. **Отчёты об ошибках**: форматирование контрпримеров + отчёт о неразрешённых утверждениях +
   привязка к позициям в исходнике

### Обратная совместимость

- ✅ Код, не использующий предикаты времени компиляции, полностью не меняется
- ✅ Предикаты времени компиляции в режиме CompileTime имеют нулевой расход во время выполнения, в
  режиме Runtime сохраняются только необходимые проверки Bool
- ⚠️ Синтаксис `//!` из RFC-022 больше не поддерживается — но 022 никогда не был реализован, бремя
  миграции отсутствует

## Компромиссы

### Преимущества

- **Полная реализация изоморфизма Карри-Ховарда**: тип есть утверждение, программа есть
  доказательство, `name: Утверждение = Доказательство`
- **Единство**: предикаты времени компиляции и обычные функции используют полностью одинаковый
  синтаксис, без концептуального разделения
- **Прозрачность SMT**: программисту не нужно знать о существовании SMT, ментальная модель совпадает
  с проверкой типов
- **Постепенное внедрение**: можно начать с одного предиката времени компиляции, постепенно
  увеличивая покрытие
- **Минимальный расход во время выполнения**: режим CompileTime имеет нулевой расход, режим Runtime
  сохраняет только необходимые проверки Bool

### Недостатки

- **Время компиляции**: решение SMT увеличивает время компиляции, но жёсткое ограничение бюджета
  гарантирует контролируемый верхний предел
- **Границы автоматического доказательства**: сложные предикаты за пределами линейной арифметики
  первого порядка могут потребовать от программиста написания функции-доказательства. Это не дефект
  языка — это неизбежное следствие проблемы останова. Компилятор честно сообщает Unproven, а не
  ложно объявляет True/False
- **Кривая обучения**: написание эффективных предикатов времени компиляции и функций-доказательств
  требует понимания базовой интуиции изоморфизма Карри-Ховарда
- **Сложность реализации**: единство конвейера доказательства времени компиляции требует тщательного
  проектирования

### Снижение рисков

- Жёсткое ограничение бюджета решения SMT (шаги 10,000 / время 100ms / глубина инстанцирования 3),
  превышение возвращает Unproven
- Пре-редукция зависимых типов: детерминированные вычисления значений поглощаются первыми, SMT
  грызёт только недетерминированную часть
- Unproven — не тупик: программист может написать функцию-доказательство, проверщик типов
  верифицирует — как и любой тип возврата функции
- Инкрементальная верификация: верифицируются только изменённые модули
- Чёткие сообщения об ошибках + отображение контрпримеров + отчёт о расходе бюджета + неразрешённые
  утверждения + предложения (если компилятор может дать)

| Альтернатива                                                                     | Почему не выбрана                                                                                                                                                                     |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Стратегия реализации

### Разбиение на фазы

| Фаза       | Содержание                                                                                                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фаза 1** | Ядро компилятора: структурная эквивалентность + βδι-редукция + введение/устранение кванторов всеобщности. Поддержка простых арифметических предикатов (`x > 0`, `arr.len > 0`)          |
| **Фаза 2** | Слой трансляции в SMT-LIB + интеграция Z3/CVC5. Конвейер возвращает Proved/Disproved/Unproven. При Unproven поддержка функций-доказательств от программиста                             |
| **Фаза 3** | Генерация VC для инвариантов цикла + проверка завершимости (линейная ранговая функция + подсчёт нарушений предиката + паттерн ограниченного изменения + контроль комбинаторного взрыва) |
| **Фаза 4** | Инкрементальная верификация + кэширование + поддержка IDE                                                                                                                               |

## Открытые вопросы

- [x] **Выбор SMT-решателя**: по умолчанию Z3 (лицензия MIT, самая широкая валидация). CVC5 как
      SMT-LIB-совместимая альтернатива, переключение флагом компилятора. Внутренняя цель трансляции
      компилятора — стандартный формат SMT-LIB 2.6 — SMT-LIB и есть слой абстракции, без
      специального универсального интерфейса решателя.
- [x] **Конкретные значения бюджета решения**: шаги 10,000 / время 100ms / глубина инстанцирования
      кванторов 3. Фиксированы внутри компилятора, без ручек. Если в реальном использовании появятся
      реальные случаи, доказывающие недостаточность (не «пользователь ошибся»), корректируем.
- [x] **Диапазон поддержки кванторов**: язык не ограничивает порядок кванторов на уровне языка.
      Предикаты времени компиляции принимают параметры Type — Type включает функциональные типы —
      поэтому кванторы высокого порядка — естественное следствие системы типов, специальный
      синтаксис не нужен. SMT-решатель может автоматически проверять кванторы первого порядка
      (forall/exists, поддерживает чередующееся вложение, ограничено глубиной бюджета 3). Кванторы
      высокого порядка: SMT возвращает Unproven, компилятор подсказывает «этот предикат за пределами
      автоматического доказательства, пожалуйста, предоставьте функцию-доказательство». Программист
      пишет функцию, тип возврата которой равен утверждению — проверщик типов верифицирует эту
      функцию. Без внешнего экспорта, без ИИ, без интерактивного режима доказательства. Всё есть код
      YaoXiang, всё проверяется проверщиком типов.
- [x] **Форматирование контрпримеров**: имена переменных исходного кода напрямую используются как
      имена SMT-переменных (с префиксом модуля для избежания конфликтов). При возврате модели Z3
      поиск по именам переменных. Формат вывода: имя_переменной = конкретное_значение + позиция в
      исходнике + позиция определения предиката. Без сложного слоя отображения.
- [x] ~~**Взаимодействие предикатов времени компиляции с умными указателями `ref`?**~~ → Решено:
      предикаты времени компиляции допускают только неизменяемые заимствования или значения с
      переданным владением. Значения по изменяемому заимствованию не могут появляться в предикатах
      времени компиляции.
- [x] **Расширение меры подсчёта нарушений `forall`-предиката на несмежные операции?** → Не
      расширяется. Текущее покрытие (соседний обмен, соседнее перемещение) дополняется стратегией 1
      (линейная ранговая функция) — внешнее сокращение интервала быстрой сортировки покрывается
      стратегией 1, пирамидальная сортировка покрывается стратегией 1 (паттерн индексации массива).
      Циклы, чью завершимость не может доказать ни одна стратегия, сразу дают ошибку компилятора —
      это философия жёсткой безопасности, не дефект. Если в будущем появится реальный сценарий (не
      академическая конструкция), для которого все четыре стратегии бессильны, обсудим заново.
- [x] **Комбинаторный взрыв перебора линейной ранговой функции**: верхний предел перебора кандидатов
      — 3 переменные с границами. При ≤3 перебираются все линейные комбинации и каждая проверяется
      SMT. При >3 пробуются только однопеременные меры (`v_i`, `u_i - v_i`), при неудаче сразу
      ошибка компиляции — подсказка программисту «цикл имеет >3 переменных с границами, компилятор
      не может синтезировать многопеременную меру». Это не инженерный компромисс — это принуждение
      программиста писать более простые циклы.
