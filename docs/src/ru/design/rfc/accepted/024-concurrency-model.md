# RFC-024：Семантика среды выполнения параллелизма на основе spawn

> **В этом документе определяется семантика поведения `spawn` во время выполнения.** Ортогональность синтаксиса, рефакторинг AST/IR, расширение системы типов см.
> [RFC-032](../review/032-spawn-unified-expression.md).
>
> Оба RFC совместно определяют `spawn` — 024 отвечает на вопрос "что делать", 032 — "как выразить".

> **Справочные материалы**:
>
> - [Спецификация модели параллелизма](../../../../reference/language-spec/concurrency.md)
> - [RFC-008: Деклаплинг модели параллелизма среды выполнения и планировщика](./008-runtime-concurrency-model.md)
> - [RFC-009: Проектирование модели владения](./009-ownership-model.md)

## Аннотация

В этом документе определяется **семантика поведения `spawn` во время выполнения** для языка программирования YaoXiang: `spawn <expr>`
является единственным примитивом параллелизма, может модифицировать любое выражение, вызывающая сторона синхронно блокируется. Форма выражения определяет гранулярность разбиения задач, среда выполнения планирует по модели GMP — независимые задачи помещаются в рабочую очередь, воркеры соревнуются за их выполнение.

**Основной замысел — одна примитива, один набор правил**:

```
spawn <expr>               ← единственный примитив параллелизма
Разбиение задач определяется формой выражения    ← единственное правило
Синхронная блокировка ожидания результата            ← единственное поведение
```

**Устранённая сложность**:

- ❌ Нет аннотаций `@block`/`@eager`/`@auto`
- ❌ Нет `Send`/`Sync` trait
- ❌ Нет `Mutex`/`RwLock`/`Atomic`
- ❌ Нет `future`/неблокирующих дескрипторов
- ❌ Нет анализа DAG по всей программе
- ❌ Нет «окрашивания функций» (async/await)

> **Ментальная модель пользователя**: Ваш обычный код выполняется последовательно. Когда вы хотите, чтобы несколько вещей выполнялись одновременно, поместите их в `spawn <expr>`.
> Никаких колбэков, никаких `await`, никаких странных аннотаций.

## Мотивация

### Зачем нужен этот проект?

Текущие модели параллелизма в мейнстримных языках имеют очевидные недостатки:

| Язык       | Модель параллелизма            | Проблема                             |
| ---------- | ------------------- | ------------------------------------ |
| Rust       | async/await + tokio | Асинхронное заражение, окрашивание функций, крутая кривая обучения |
| Go         | goroutine           | Нет безопасности типов, трудно обнаружить гонки данных     |
| Python     | asyncio             | Ограничения GIL, окрашивание функций               |
| JavaScript | Promise/async       | Callback hell, окрашивание функций               |

### Проблемы старого проекта (RFC-001)

Предложенная в RFC-001 трёхуровневая архитектура параллелизма (L1/L2/L3) имеет следующие проблемы:

| Проблема         | Описание                                         |
| ------------ | -------------------------------------------- |
| Сложная ментальная модель | Три уровня абстракции L1/L2/L3 увеличивают нагрузку на обучение              |
| Избыточные аннотации     | Аннотации `@block`/`@eager`/`@auto` делают код шумным |
| Высокая сложность анализа | Накладные расходы времени компиляции на анализ DAG для всей программы              |
| Сложные ограничения типов | `Send`/`Sync` trait увеличивают когнитивную нагрузку           |
| Неконтролируемость       | Автоматическое распараллеливание трудно предсказать и отладить                   |

### Цели проектирования

1. **Простота**: только один примитив параллелизма (`spawn`), может модифицировать любое выражение
2. **Явность**: пользователь точно знает, где параллелизм, а где последовательность
3. **Безопасность**: правила владения естественно расширяются, без дополнительных ограничений типов
4. **Контролируемость**: нет неявного параллелизма, нет неожиданного параллельного поведения
5. **Синхронность**: вызывающая сторона синхронно блокируется, без колбэков и `await`

## Предложение

### 1. Природа блока `{}`: вычислительная единица на основе зависимостей

В YaoXiang `{}` является **вычислительной единицей, управляемой зависимостями**.

| Атрибут       | Описание                                                               |
| ---------- | ------------------------------------------------------------------ |
| Управление зависимостями   | При выполнении блок проверяет готовность всех внутренних переменных; если все готовы — немедленно выполняется, иначе блокируется |
| Время выполнения   | Определяется зависимостями, не связано с "немедленностью" или "отложенностью"                                   |
| Возвращаемое значение     | Используйте `return` для явного возврата значения; без `return` по умолчанию возвращается `Void`            |
| Унифицированный синтаксис   | Независимо от появления в теле функции, инициализации переменной или после `spawn`, семантика一致              |
| Изоляция области видимости | Переменные строго ограничены внутри `{}`, не проникают во внешнюю область видимости                         |

```yaoxiang
// Пример управления зависимостями
x = compute_x()        // x готов
y = compute_y()        // y готов
result = {
    // Зависит от x и y; выполняется немедленно, когда оба готовы
    return x + y
}
```

### 2. Семантика выражений spawn

`spawn <expr>` является **единственным примитивом параллелизма** в YaoXiang. Может модифицировать любое выражение, форма выражения определяет гранулярность разбиения задач.

#### 2.1 Правила создания задач

| Форма выражения                      | Разбиение задач                                 | Синхронная семантика         |
| ------------------------------- | ---------------------------------------- | ---------------- |
| `spawn { a, b, c }`             | Непосредственные подвыражения → N независимых задач              | Ожидание завершения всех задач |
| `spawn for x in items { body }` | Каждая итерация → 1 задача                      | Ожидание завершения всех итераций |
| `spawn while cond { body }`     | Каждый виток итерации → 1 задача (межитерационное условие управляет)    | Ожидание условия false |
| `spawn if c { a } else { b }`   | Условие c вычисляется последовательно, выбранная ветвь целиком → 1 задача | Ожидание завершения выбранной ветви |
| `spawn call(x)`                 | Сам вызов → 1 задача                      | Ожидание завершения вызова     |
| `spawn expr`（любое выражение）      | Само выражение → 1 задача                    | Ожидание завершения выражения   |

> **Мотивация дизайна**: Почему spawn может модифицировать любое выражение? Подробнее см.
> [RFC-032 §Основной дизайн](../review/032-spawn-unified-expression.md).
>
> **Ортогональность управления потоком**: Семантическая разница между
> `spawn <expr>` (spawn спереди) и
> `<expr> spawn { body }` (spawn сзади), подробнее см.
> [RFC-032 §Ортогональность управления потоком](../review/032-spawn-unified-expression.md)（основное определение）. Семантика времени выполнения всех обратных комбинаций (`for ... spawn { }`
> / `while ... spawn { }` /
> `if ... spawn { }`) — распространение ошибок, типы ресурсов, правила вложенности — наследуют правила §2.4 / §2.5 /
> §2.6 настоящего документа.

```yaoxiang
// spawn блок: непосредственные подвыражения параллельно
(a, b) = spawn {
    t1 = fetch("url1")   // Непосредственное подвыражение → параллельная задача 1
    t2 = fetch("url2")   // Непосредственное подвыражение → параллельная задача 2
    return (t1, t2)      // Явный возврат кортежа
}

// spawn for: каждая итерация параллельна
results = spawn for item in items {
    process(item)        // каждая итерация → независимая задача
}

// spawn while: каждый виток итерации параллельно
spawn while has_next() {
    step()               // Каждый виток → независимая задача
}

// spawn if: выбранная ветвь целиком как задача
result = spawn if cond {
    branch_a()
} else {
    branch_b()
}
```

#### 2.2 Изоляция области видимости

Выражение `spawn` создаёт независимую область видимости; внутренние переменные не влияют на внешнюю:

```yaoxiang
x = 10
result = spawn {
    x = 20              // это локальный x внутри выражения spawn
    compute(x)
}
// x всё ещё 10

result = spawn for item in items {
    item = item + 1     // Итерационная локальная item, каждая итерация имеет независимую копию
    process(item)
}
// внешний item не затронут
```

**Итерационные переменные** (x в for) имеют независимую копию в каждом витке и автоматически уничтожаются после завершения итерации.

#### 2.3 Правила владения

После того как переменная входит в выражение spawn, она больше не может использоваться извне (семантика Move):

```yaoxiang
data = load_data()
result = spawn {
    process(data)       // владение data перемещается в выражение spawn
}
// data здесь недоступен (перемещён)
```

Если необходимо разделять между несколькими задачами, используйте `ref`:

```yaoxiang
data = load_data()
shared = ref data       // компилятор автоматически выбирает Rc или Arc

result = spawn {
    process_a(shared),  // Разделяемая ссылка
    process_b(shared)   // Разделяемая ссылка
}
```

**Разделение между итерациями**: используйте `ref` для захвата во внешнюю область, между итерациями разделяется одна ссылка.

#### 2.4 Правила распространения ошибок

##### `spawn { a, b, c }`（блок）

1. Ожидание завершения всех задач (даже если некоторые уже завершились неудачно)
2. Распространение первой встреченной ошибки
3. Используйте `?` для явного обозначения точки распространения ошибки

```yaoxiang
(a, b) = spawn {
    fetch("url1")?,     // может завершиться ошибкой
    fetch("url2")?      // может завершиться ошибкой
}
// если любая задача завершается ошибкой, всё выражение spawn распространяет первую ошибку
```

##### `spawn for x in items { body? }`

- Возвращает первую ошибку после завершения всех итераций
- После неудачной итерации оставшиеся итерации **продолжают выполняться** (не отменяются)
- Используйте `?` для явного обозначения точки распространения ошибки

```yaoxiang
results = spawn for item in items {
    process(item)?      // ошибка любой итерации → ждём завершения всех → распространяем первую ошибку
}
```

##### `spawn while cond { body? }`

Наследует собственную семантику ошибок `while`:

- step использует `?` для распространения ошибки → весь spawn while завершается с ошибкой, следующий виток не начинается
- step не распространяет ошибку (ошибка поглощается) → переход к следующему витку итерации

```yaoxiang
spawn while has_next() {
    item = next()       // Без распространения ошибки, неудача тоже ведёт к следующему витку
    process(item)
}
```

##### `spawn if c { a } else { b }`

- Условие c **вычисляется последовательно**
- Ошибка при вычислении c → общая ошибка
- Ошибка в выбранной ветви → общая ошибка

```yaoxiang
result = spawn if cond()? {  // cond вычисляется последовательно, ошибка → общая ошибка
    fetch_a()?
} else {
    fetch_b()?
}
```

#### 2.5 Правила для типов ресурсов

Компилятор отслеживает использование типов ресурсов, обеспечивая безопасность параллелизма:

| Тип ресурса   | Описание         | Поведение компилятора                |
| ---------- | ------------ | ------------------------- |
| `FilePath` | Путь к файловой системе | Операции с одним путём автоматически сериализуются        |
| `HttpUrl`  | HTTP endpoint    | Операции с одним URL автоматически сериализуются       |
| `DBUrl`    | Подключение к БД   | Операции с одним подключением автоматически сериализуются        |
| `Console`  | Стандартный вывод     | Все операции Console автоматически сериализуются |

##### Внутри блока `spawn { ... }`

```yaoxiang
// Операции с одним файлом автоматически сериализуются
(a, b) = spawn {
    read_file("data.txt"),      // Выполняется первым
    write_file("data.txt", x)   // Ожидание завершения чтения
}
```

##### Межитерационные конфликты в `spawn for ... { ... }` при использовании одного ресурса

Когда все итерации работают с одним типом ресурса, компилятор **автоматически понижает до последовательного выполнения** (spawn деградирует до последовательного for, без ошибок):

```yaoxiang
// Все итерации записывают в один файл → автоматическое понижение до последовательного
results = spawn for item in items {
    write_file("data.txt", item)
}
// компилятор автоматически сериализует все итерации
```

> **Обоснование дизайна**: Ключевое слово spawn всё ещё выражает намерение параллелизма; автоматическое понижение компилятором при конфликте ресурсов — более соответствует принципу наименьшего удивления, чем прямой отказ.

##### `spawn while ... { ... }` захват `&mut`

**Ошибка времени компиляции**: `spawn while` не допускает захват внешних переменных типа `&mut`:

```yaoxiang
iter = make_iter()
spawn while iter.has_next() {       // Ошибка времени компиляции
    item = iter.next()              // iter имеет тип &mut, межитерационное разделение изменяемости = гонка данных
}
```

> **Не повторное введение `Sync` trait**: Соответствует обещанию RFC-024 "без Send/Sync". Требуется от пользователя использовать `ref` или альтернативную запись без spawn.

##### `spawn if c { ... } else { ... }` обе ветви используют один ресурс

**Легально без предупреждений**: Условия if взаимоисключающие, максимум одна ветвь выполняется, конфликта параллелизма не существует:

```yaoxiang
result = spawn if use_cache {
    load_from_cache(key)            // Ветвь 1: чтение из кэша
} else {
    fetch(key)                      // ветвь 2: чтение по URL
}
```

#### 2.6 Вложенный spawn

Выражения spawn могут быть вложенными; внутренний spawn создаёт **независимую параллельную область**:

```yaoxiang
(a, b) = spawn {
    x = spawn {
        fetch("url1"),
        fetch("url2")
    },
    y = compute(x)
}
```

**Семантика вложенности**:

- Внутренний spawn является независимой параллельной областью (независимая очередь задач, независимое распространение ошибок)
- Внутренние ошибки распространяются независимо во внешнюю область (внешняя задача получает ошибку при ожидании завершения внутренней)
- Правила типов ресурсов внутреннего уровня отслеживаются независимо (не проверяются совместно с внешним уровнем)

```yaoxiang
// spawn for с вложенным spawn while
results = spawn for x in items {
    inner = spawn while has_more(x) {
        step(x)
    }
    process(inner)
}
```

### 3. Разрыв со старым проектом

| Старый дизайн（RFC-001）              | Новый дизайн（RFC-024 + RFC-032）          |
| ------------------------------ | ------------------------------------ |
| Автоматический анализ DAG для всей программы            | Анализ только внутри выражений spawn                |
| Аннотации `@block`/`@eager`/`@auto` | Без аннотаций, управление зависимостями                     |
| `Send`/`Sync` trait            | Не требуются, владение + ref автоматически обрабатываются          |
| `future`/неблокирующие дескрипторы            | Синхронная блокировка, без колбэков                     |
| `Mutex`/`RwLock`/`Atomic`      | `ref` автоматически выбирает Rc/Arc                |
| Трёхуровневая ментальная модель L1/L2/L3          | Обычный код последовательный, выражения spawn параллельны       |
| Окрашивание функций（async/await）        | Без окрашивания функций                           |
| `spawn` модифицирует только блок `{}`         | `spawn` модифицирует любое выражение（см. RFC-032） |

### 4. Правила возврата

Правила возврата в YaoXiang единообразны и ясны:

| Запись                    | Возвращаемое значение                           | Описание           |
| ----------------------- | -------------------------------- | -------------- |
| `= expr`（без фигурных скобок）    | Непосредственный возврат `expr`                  | Выражение является значением     |
| `= { ... }`（с фигурными скобками） | Обязательно использовать `return`, иначе возврат `Void` | Блок требует явного возврата |

```yaoxiang
// Без фигурных скобок: прямой возврат
add: (a: Int, b: Int) -> Int = a + b

// С фигурными скобками: обязательно использовать return
process: (data: Data) -> Result = {
    validated = validate(data)?
    return ok(transform(validated))
}

// С фигурными скобками, но без return: возвращается Void
log: (message: String) -> Void = {
    print(message)  // без return, возвращается Void
}
```

### 5. Пользовательская ментальная модель

> **Обычный код, который вы пишете, выполняется последовательно.**
>
> **Когда вы хотите, чтобы несколько вещей выполнялись одновременно, поместите их в `spawn <expr>`.**
>
> Форма выражения определяет, как разбиваются задачи: каждое непосредственное подвыражение в блоке параллельно; каждая итерация for параллельно; выбранная ветвь if как одна задача.
>
> **Всё выражение `spawn` блокирует выполнение синхронно, ожидая завершения всех задач.**
>
> **Никаких колбэков, никаких `await`, никаких странных аннотаций.**

```yaoxiang
// Обычный код: последовательное выполнение
a = compute_a()         // выполняется сначала
b = compute_b(a)        // зависит от a; выполняется после завершения a
c = compute_c(b)        // зависит от b; выполняется после завершения b

// Когда нужен параллелизм: используйте spawn
(x, y, z) = spawn {
    fetch("url1"),      // параллельно
    fetch("url2"),      // параллельно
    fetch("url3")       // параллельно
}
// Продолжение после завершения всех
process(x, y, z)

// Параллелизм данных: spawn for
results = spawn for item in items {
    process(item)
}
```

## Компромиссы

### Преимущества

1. **Простота**: только один примитив параллелизма (`spawn`), может модифицировать любое выражение
2. **Явность**: пользователь точно знает, где параллелизм, а где последовательность; нет неявного параллелизма
3. **Безопасность**: правила владения естественно расширяются, без дополнительных ограничений типов вроде `Send`/`Sync`
4. **Контролируемость**: нет автоматического распараллеливания, избегаются неожиданные проблемы параллелизма
5. **Синхронность**: вызывающая сторона синхронно блокируется, код легко понимать и отлаживать
6. **Без окрашивания функций**: не существует проблем окрашивания функций async/await
7. **Эффективность компиляции**: анализ DAG только внутри выражений spawn, время компиляции контролируемо
8. **Ортогональность**: spawn естественно комбинируется с любыми конструкциями управления потоком (подробнее см. RFC-032)

### Недостатки

1. **Требуется явный spawn**: автоматическое распараллеливание невозможно; пользователь должен вручную помечать точки параллелизма
2. **Анализ DAG внутри выражений spawn**: компилятору необходимо выполнять анализ зависимостей внутри выражений spawn
3. **Несовместимость со старым кодом**: код, использующий старый паттерн RFC-001, требует миграции

## Альтернативы

| Решение                      | Почему не выбрано                                   |
| ------------------------- | ---------------------------------------------- |
| Автоматический DAG для всей программы（RFC-001） | Высокая сложность, долгое время компиляции, неконтролируемое поведение               |
| async/await               | Окрашивание функций, крутая кривая обучения, плохая читаемость кода           |
| goroutine                 | Нет безопасности типов, трудно обнаружить гонки данных                   |
| Модель Actor              | Сложность передачи сообщений, трудности отладки                         |
| CSP（Go channel）         | Нет безопасности типов, трудно обнаружить взаимоблокировки                       |
| `spawn` модифицирует только `{}` блок    | Нарушает ортогональность, `spawn for` становится特例（см. RFC-032） |

## Стратегия реализации

### Анализ на этапе компиляции

1. **Распознавание формы выражения**: в зависимости от формы выражения после spawn определяется разбиение задач (подробнее см. RFC-032 §Анализ DAG)
2. **Построение DAG**: анализ зависимостей внутри выражения spawn
3. **Топологическая сортировка**: определение порядка выполнения внутри выражения spawn
4. **Распознавание параллелизма**: распознавание поддеревьев без зависимостей внутри выражения spawn
5. **Анализ побега**: `ref` → Rc или Arc
6. **Обнаружение конфликтов ресурсов**: обнаружение потенциальных конфликтов типов ресурсов

### Организация модулей

Код, связанный с `spawn`, единообразно размещается в `frontend/core/spawn/`:

```
frontend/core/spawn/
├── mod.rs           # Входная точка модуля spawn
├── placement.rs     # Проверка легитимности позиций появления spawn
└── analysis.rs      # Распознавание задач, анализ зависимостей, обнаружение конфликтов ресурсов
```

> **Инструкция по миграции**（2026-06-11）: Существующий `frontend/core/typecheck/passes/spawn_placement.rs` будет перемещён в
> `frontend/core/spawn/placement.rs`. Объявление модуля `spawn_placement`
> в каталоге `typecheck/passes/` необходимо同步но удалить.

### Выполнение во время выполнения

См. архитектуру среды выполнения из [RFC-008](./008-runtime-concurrency-model.md):

- **Embedded Runtime**：Без поддержки spawn, немедленное выполнение
- **Standard Runtime**：Поддержка выражений spawn
- **Full Runtime**：Standard + WorkStealer балансировка нагрузки

### Зависимости

- RFC-008（Архитектура среды выполнения）→ Завершено
- RFC-009（Модель владения）→ Завершено
- RFC-010（Унифицированный синтаксис типов）→ Завершено
- RFC-011（Обобщённая система）→ Завершено
- RFC-032（Рефакторинг AST/IR）→ Совместно с настоящим определяет spawn
