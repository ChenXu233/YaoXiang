# RFC-024: Семантика исполняющей среды параллелизма на основе spawn

> **Этот документ определяет семантику поведения `spawn` во время исполнения.** Синтаксическая
> ортогональность, рефакторинг AST/IR и расширения системы типов описаны в
> [RFC-032](../review/032-spawn-unified-expression.md).
>
> Два RFC совместно определяют `spawn` — 024 отвечает на вопрос «что делать», 032 — «как
> представить».

> **Ссылки**:
>
> - [Спецификация модели параллелизма](../../../reference/language-spec/concurrency.md)
> - [RFC-008: Разделение модели параллелизма Runtime и планировщика](./008-runtime-concurrency-model.md)
> - [RFC-009: Проект модели владения](./009-ownership-model.md)
> - [RFC-010: Унифицированный синтаксис типов](./010-unified-type-syntax.md)
> - [RFC-032: Унифицированный модификатор выражения spawn — рефакторинг AST/IR](../review/032-spawn-unified-expression.md)

## Резюме

Этот документ определяет **семантику поведения во время исполнения** ключевого слова `spawn` в языке
программирования YaoXiang: `spawn <expr>` является единственной примитивой параллелизма, может
модифицировать произвольное выражение, вызывающая сторона синхронно блокируется. Форма выражения
определяет гранулярность декомпозиции задач, исполняющая среда использует модель планирования GMP —
задачи без зависимостей помещаются в очередь работ, worker-ы конкурируют за их выполнение.

**Основной проект — одна примитива, один набор правил**:

```
spawn <expr>               ← единственная примитива параллелизма
декомпозиция задач по форме выражения  ← единственное правило
синхронное блокирование в ожидании результата  ← единственное поведение
```

**Устранённая сложность**:

- ❌ Нет аннотаций `@block`/`@eager`/`@auto`
- ❌ Нет trait `Send`/`Sync`
- ❌ Нет `Mutex`/`RwLock`/`Atomic`
- ❌ Нет `future`/неблокирующих дескрипторов
- ❌ Нет анализа DAG по всей программе
- ❌ Нет окрашивания функций (async/await)

> **Ментальная модель пользователя**: ваш обычный код выполняется последовательно. Когда вы хотите,
> чтобы несколько вещей выполнялись одновременно, поместите их в `spawn <expr>`. Никаких обратных
> вызовов, никакого `await`, никаких странных аннотаций.

## Мотивация

### Зачем нужен этот проект?

Существующие модели параллелизма в主流 языках имеют явные недостатки:

| Язык       | Модель параллелизма | Проблемы                                                              |
| ---------- | ------------------- | --------------------------------------------------------------------- |
| Rust       | async/await + tokio | Заражение асинхронностью, окрашивание функций, крутая кривая обучения |
| Go         | goroutine           | Отсутствие типобезопасности, сложность обнаружения гонок данных       |
| Python     | asyncio             | Ограничение GIL, окрашивание функций                                  |
| JavaScript | Promise/async       | Ад обратных вызовов, окрашивание функций                              |

### Проблемы старого проекта (RFC-001)

Трёхуровневая архитектура параллелизма (L1/L2/L3), предложенная в RFC-001, имеет следующие проблемы:

| Проблема                  | Описание                                                              |
| ------------------------- | --------------------------------------------------------------------- |
| Сложная ментальная модель | L1/L2/L3 — три уровня абстракции увеличивают нагрузку на обучение     |
| Избыточные аннотации      | Аннотации `@block`/`@eager`/`@auto` делают код шумным                 |
| Высокая сложность анализа | Большие затраты времени компиляции на анализ DAG всей программы       |
| Сложные ограничения типов | trait `Send`/`Sync` увеличивают когнитивную нагрузку                  |
| Непредсказуемость         | Автоматическое параллельное поведение трудно предсказать и отлаживать |

### Цели проекта

1. **Простота**: только одна примитива параллелизма (`spawn`), может модифицировать произвольное
   выражение
2. **Явность**: пользователь чётко знает, где параллелизм, а где последовательность
3. **Безопасность**: правила владения естественно расширяются, без дополнительных ограничений типов
4. **Контролируемость**: нет неявного параллелизма, нет неожиданного параллельного поведения
5. **Синхронность**: вызывающая сторона синхронно блокируется, без обратных вызовов и `await`

## Предложение

### 1. Сущность блока {}: вычислительная единица, управляемая зависимостями

В YaoXiang `{}` — это **вычислительная единица, управляемая зависимостями**.

| Атрибут                    | Описание                                                                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Управление зависимостями   | При выполнении блок проверяет готовность всех внутренних переменных; если все готовы — немедленно выполняется, иначе блокируется в ожидании |
| Момент выполнения          | Определяется зависимостями, не связан с «немедленным» или «отложенным» выполнением                                                          |
| Возвращаемое значение      | Для явного возврата значения используется `return`; без `return` по умолчанию возвращается `Void`                                           |
| Единый синтаксис           | Семантика одинакова независимо от того, появляется блок в теле функции, при инициализации переменной или после `spawn`                      |
| Изоляция области видимости | Переменные строго ограничены внутренней областью `{}`, не проникают во внешнюю область видимости                                            |

```yaoxiang
// Пример управления зависимостями
x = compute_x()        // x готово
y = compute_y()        // y готово
result = {
    // Зависит от x и y; после готовности обоих выполняется немедленно
    return x + y
}
```

### 2. Семантика выражения spawn

`spawn <expr>` — **единственная примитива параллелизма** в YaoXiang. Может модифицировать
произвольное выражение; форма выражения определяет гранулярность декомпозиции задач.

#### 2.1 Правила создания задач

| Форма выражения                       | Декомпозиция задач                                                        | Семантика синхронизации                |
| ------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------- |
| `spawn { a, b, c }`                   | Непосредственные подвыражения → N независимых задач                       | Ожидание завершения всех задач         |
| `spawn for x in items { body }`       | Каждая итерация → 1 задача                                                | Ожидание завершения всех итераций      |
| `spawn while cond { body }`           | Каждый цикл итерации → 1 задача (условие управляет между итерациями)      | Ожидание, пока условие не станет false |
| `spawn if c { a } else { b }`         | Условие c вычисляется последовательно, выбранная ветвь целиком → 1 задача | Ожидание завершения выбранной ветви    |
| `spawn call(x)`                       | Сам вызов → 1 задача                                                      | Ожидание завершения вызова             |
| `spawn expr` (произвольное выражение) | Само выражение → 1 задача                                                 | Ожидание завершения выражения          |

> **Мотивация проекта**: почему spawn может модифицировать произвольное выражение? См.
> [RFC-032 §Основной проект](../review/032-spawn-unified-expression.md).
>
> **Ортогональность потока управления**: семантические различия между `spawn <expr>` (spawn спереди)
> и `<expr> spawn { body }` (spawn сзади) подробно описаны в
> [RFC-032 §Ортогональность потока управления](../review/032-spawn-unified-expression.md) (основное
> определение). Поведение во время исполнения всех обратных комбинаций (`for ... spawn { }` /
> `while ... spawn { }` / `if ... spawn { }`) — распространение ошибок, типы ресурсов, правила
> вложенности — наследует правила §2.4 / §2.5 / §2.6 данного документа.

```yaoxiang
// spawn-блок: непосредственные подвыражения выполняются параллельно
(a, b) = spawn {
    t1 = fetch("url1")   // непосредственное подвыражение → параллельная задача 1
    t2 = fetch("url2")   // непосредственное подвыражение → параллельная задача 2
    return (t1, t2)      // явный возврат кортежа
}

// spawn for: каждая итерация параллельна
results = spawn for item in items {
    process(item)        // каждая итерация → независимая задача
}

// spawn while: каждая итерация параллельна
spawn while has_next() {
    step()               // каждая итерация → независимая задача
}

// spawn if: выбранная ветвь целиком как задача
result = spawn if cond {
    branch_a()
} else {
    branch_b()
}
```

#### 2.2 Изоляция области видимости

Выражение spawn создаёт независимую область видимости; внутренние переменные не влияют на внешнюю:

```yaoxiang
x = 10
result = spawn {
    x = 20              // это локальный x внутри выражения spawn
    compute(x)
}
// x по-прежнему равен 10

result = spawn for item in items {
    item = item + 1     // итерационная локальная item, независимая копия для каждой итерации
    process(item)
}
// внешняя item не затронута
```

**Итерационная переменная** (x в for) — независимая копия для каждой итерации, автоматически
уничтожается после завершения итерации.

#### 2.3 Правила владения

После того как переменная входит в выражение spawn, её нельзя использовать снаружи (семантика Move):

```yaoxiang
data = load_data()
result = spawn {
    process(data)       // право владения data перемещается в выражение spawn
}
// data здесь недоступна (уже перемещена)
```

Если необходимо разделить между несколькими задачами, используйте `ref`:

```yaoxiang
data = load_data()
shared = ref data       // компилятор автоматически выбирает Rc или Arc

result = spawn {
    process_a(shared),  // общая ссылка
    process_b(shared)   // общая ссылка
}
```

**Совместное использование между итерациями**: захватите `ref` во внешнюю область; между итерациями
используется одна и та же ссылка.

#### 2.4 Правила распространения ошибок

##### `spawn { a, b, c }` (блок)

1. Ожидание завершения всех задач (даже если некоторые задачи завершились неудачно)
2. Распространение первой встреченной ошибки
3. Используйте `?` для явной отметки точек распространения ошибки

```yaoxiang
(a, b) = spawn {
    fetch("url1")?,     // может завершиться неудачей
    fetch("url2")?      // может завершиться неудачей
}
// если какая-либо задача завершается неудачей, всё выражение spawn распространяет первую ошибку
```

##### `spawn for x in items { body? }`

- Дождаться завершения всех итераций, затем вернуть первую ошибку
- После неудачной итерации оставшиеся итерации **продолжают выполняться** (не отменяются)
- Используйте `?` для явной отметки точек распространения ошибки

```yaoxiang
results = spawn for item in items {
    process(item)?      // неудача любой итерации → ожидание завершения всех → распространение первой ошибки
}
```

##### `spawn while cond { body? }`

Наследует собственную семантику ошибок while:

- step использует `?` для распространения ошибки → весь spawn while завершается неудачей, не входит
  в следующий цикл
- step не распространяет ошибку (ошибка поглощается) → переход к следующей итерации

```yaoxiang
spawn while has_next() {
    item = next()       // если ошибка не распространяется, при сбое также переходит к следующей итерации
    process(item)
}
```

##### `spawn if c { a } else { b }`

- Условие c **вычисляется последовательно**
- Ошибка при вычислении c → общая ошибка
- Ошибка внутри выбранной ветви → общая ошибка

```yaoxiang
result = spawn if cond()? {  // c вычисляется последовательно, сбой → общая ошибка
    fetch_a()?
} else {
    fetch_b()?
}
```

#### 2.5 Правила для типов ресурсов

Компилятор отслеживает использование типов ресурсов, обеспечивая безопасность параллелизма:

| Тип ресурса | Описание                  | Поведение компилятора                                    |
| ----------- | ------------------------- | -------------------------------------------------------- |
| `FilePath`  | Путь файловой системы     | Операции с одним путём автоматически сериализуются       |
| `HttpUrl`   | Конечная точка HTTP       | Операции с одним URL автоматически сериализуются         |
| `DBUrl`     | Соединение с базой данных | Операции с одним соединением автоматически сериализуются |
| `Console`   | Стандартный вывод         | Все операции с Console автоматически сериализуются       |

##### Внутри блока `spawn { ... }`

```yaoxiang
// Операции с одним файлом автоматически сериализуются
(a, b) = spawn {
    read_file("data.txt"),      // выполняется первой
    write_file("data.txt", x)   // ожидает завершения чтения
}
```

##### `spawn for ... { ... }` — один ресурс между итерациями

Когда все итерации работают с одним и тем же типом ресурса, компилятор **автоматически понижает до
последовательного** выполнения (spawn вырождается в последовательный for, без ошибок):

```yaoxiang
// Все итерации записывают в один и тот же путь файла → автоматическое понижение до последовательного
results = spawn for item in items {
    write_file("data.txt", item)
}
// компилятор автоматически сериализует все итерации
```

> **Обоснование проекта**: ключевое слово spawn по-прежнему выражает намерение параллелизма; при
> конфликте ресурсов компилятор автоматически понижает, что лучше соответствует принципу наименьшего
> удивления, чем прямой отказ.

##### `spawn while ... { ... }` захватывает `&mut`

**Ошибка времени компиляции**: `spawn while` не позволяет захватывать внешние переменные типа
`&mut`:

```yaoxiang
iter = make_iter()
spawn while iter.has_next() {       // ошибка компиляции
    item = iter.next()              // iter — &mut, общий изменяемый между итерациями = гонка данных
}
```

> **Повторное введение trait `Sync` исключено**: согласуется с обязательством RFC-024 «без
> Send/Sync». Требуется, чтобы пользователь перешёл на `ref` или использовал запись без spawn.

##### `spawn if c { ... } else { ... }` — один ресурс в обеих ветвях

**Допустимо без предупреждений**: условия if взаимоисключающие, выполняется не более одной ветви,
конфликта параллелизма нет:

```yaoxiang
result = spawn if use_cache {
    load_from_cache(key)            // ветвь 1: чтение из кэша
} else {
    fetch(key)                      // ветвь 2: чтение по URL
}
```

#### 2.6 Вложенный spawn

Выражения spawn могут быть вложенными; внутренний уровень создаёт **независимый домен
параллелизма**:

```yaoxiang
(a, b) = spawn {
    x = spawn {
        fetch("url1"),
        fetch("url2")
    },
    y = compute(x)
}
```

**Семантика вложенности**:

- Внутренний spawn является независимым доменом параллелизма (независимая очередь задач, независимое
  распространение ошибок)
- Внутренние ошибки независимо распространяются наружу (внешняя задача получает ошибку при ожидании
  завершения внутренней)
- Правила типов ресурсов внутреннего уровня отслеживаются независимо (не объединяются с внешним
  уровнем)

```yaoxiang
// spawn for вложен в spawn while
results = spawn for x in items {
    inner = spawn while has_more(x) {
        step(x)
    }
    process(inner)
}
```

### 3. Разрыв со старым проектом

| Старый проект (RFC-001)                     | Новый проект (RFC-024 + RFC-032)                          |
| ------------------------------------------- | --------------------------------------------------------- |
| Автоматический анализ DAG по всей программе | Анализ только внутри выражений spawn                      |
| Аннотации `@block`/`@eager`/`@auto`         | Без аннотаций, управление зависимостями                   |
| Trait `Send`/`Sync`                         | Не требуются, владение + ref обрабатывают автоматически   |
| `future`/неблокирующий дескриптор           | Синхронная блокировка, без обратных вызовов               |
| `Mutex`/`RwLock`/`Atomic`                   | `ref` автоматически выбирает Rc/Arc                       |
| Трёхуровневая ментальная модель L1/L2/L3    | Обычный код последовательно, выражения spawn параллельно  |
| Окрашивание функций (async/await)           | Без окрашивания функций                                   |
| `spawn` модифицирует только блок `{}`       | `spawn` модифицирует произвольное выражение (см. RFC-032) |

### 4. Правила возврата

Правила возврата в YaoXiang единообразны и ясны:

| Запись                             | Возвращаемое значение                                        | Описание                     |
| ---------------------------------- | ------------------------------------------------------------ | ---------------------------- |
| `= expr` (без фигурных скобок)     | Возвращается `expr` напрямую                                 | Выражение — это значение     |
| `= { ... }` (с фигурными скобками) | Обязательно использовать `return`, иначе возвращается `Void` | Блок требует явного возврата |

```yaoxiang
// Без фигурных скобок: прямой возврат
add: (a: Int, b: Int) -> Int = a + b

// С фигурными скобками: обязательно использовать return
process: (data: Data) -> Result = {
    validated = validate(data)?
    return ok(transform(validated))
}

// С фигурными скобками, но без return: возвращается Void
log: (message: String) -> Void = {
    print(message)  // без return, возвращается Void
}
```

### 5. Ментальная модель пользователя

> **Ваш обычный код выполняется последовательно.**
>
> **Когда вы хотите, чтобы несколько вещей выполнялись одновременно, поместите их в
> `spawn <expr>`.**
>
> Форма выражения определяет, как декомпозировать задачи: каждое непосредственное подвыражение в
> блоке параллельно; каждая итерация в for параллельна; выбранная ветвь в if — как одна задача.
>
> **Всё выражение spawn синхронно блокируется, ожидая завершения всех задач.**
>
> **Никаких обратных вызовов, никакого `await`, никаких странных аннотаций.**

```yaoxiang
// Обычный код: последовательное выполнение
a = compute_a()         // выполняется первой
b = compute_b(a)        // зависит от a, выполняется после завершения a
c = compute_c(b)        // зависит от b, выполняется после завершения b

// При необходимости параллелизма: используйте spawn
(x, y, z) = spawn {
    fetch("url1"),      // параллельно
    fetch("url2"),      // параллельно
    fetch("url3")       // параллельно
}
// продолжение после ожидания завершения всех
process(x, y, z)

// Параллелизм данных: spawn for
results = spawn for item in items {
    process(item)
}
```

## Компромиссы

### Преимущества

1. **Простота**: только одна примитива параллелизма (`spawn`), может модифицировать произвольное
   выражение
2. **Явность**: пользователь чётко знает, где параллелизм, а где последовательность, нет неявного
   параллелизма
3. **Безопасность**: правила владения естественно расширяются, без необходимости в дополнительных
   ограничениях типов вроде `Send`/`Sync`
4. **Контролируемость**: нет автоматического параллельного поведения, что позволяет избежать
   неожиданных проблем с параллелизмом
5. **Синхронность**: вызывающая сторона синхронно блокируется, код легко понимать и отлаживать
6. **Без окрашивания функций**: нет проблемы окрашивания функций из async/await
7. **Эффективная компиляция**: анализ DAG ограничен выражениями spawn, время компиляции
   контролируемо
8. **Ортогональность**: spawn естественно сочетается с произвольными конструкциями потока управления
   (подробнее см. RFC-032)

### Недостатки

1. **Требуется явный spawn**: нельзя автоматически распараллелить, пользователь должен вручную
   отмечать точки параллелизма
2. **Анализ DAG внутри выражений spawn**: компилятор должен выполнять анализ зависимостей внутри
   выражений spawn
3. **Несовместимость со старым кодом**: код, использующий старую модель RFC-001, требует миграции

## Альтернативы

| Альтернатива                                   | Почему не выбрана                                                             |
| ---------------------------------------------- | ----------------------------------------------------------------------------- |
| Автоматический DAG по всей программе (RFC-001) | Высокая сложность, длительная компиляция, непредсказуемое поведение           |
| async/await                                    | Окрашивание функций, крутая кривая обучения, плохая читаемость кода           |
| goroutine                                      | Отсутствие типобезопасности, сложность обнаружения гонок данных               |
| Модель акторов                                 | Сложная передача сообщений, трудности отладки                                 |
| CSP (каналы Go)                                | Отсутствие типобезопасности, сложность обнаружения взаимоблокировок           |
| `spawn` модифицирует только блок `{}`          | Нарушает ортогональность, `spawn for` становится особым случаем (см. RFC-032) |

## Стратегия реализации

### Анализ времени компиляции

1. **Распознавание формы выражения**: форма выражения после spawn определяет декомпозицию задач
   (подробнее см. RFC-032 §Анализ DAG)
2. **Построение DAG**: анализ зависимостей внутри выражений spawn
3. **Топологическая сортировка**: определение порядка выполнения внутри выражений spawn
4. **Идентификация параллелизма**: распознавание поддеревьев без зависимостей внутри выражений spawn
5. **Анализ побега**: `ref` → Rc или Arc
6. **Обнаружение конфликтов ресурсов**: обнаружение потенциальных конфликтов типов ресурсов

### Организация модулей

Код, связанный со spawn, единообразно размещается в `frontend/core/spawn/`:

```
frontend/core/spawn/
├── mod.rs           # точка входа модуля spawn
├── placement.rs     # проверка допустимости позиции появления spawn
└── analysis.rs      # распознавание задач, анализ зависимостей, обнаружение конфликтов ресурсов
```

> **Заметка о миграции** (2026-06-11): существующий
> `frontend/core/typecheck/passes/spawn_placement.rs` будет перенесён в
> `frontend/core/spawn/placement.rs`. Объявление модуля `spawn_placement` в каталоге
> `typecheck/passes/` должно быть синхронно удалено.

### Выполнение в исполняющей среде

Ссылаясь на архитектуру Runtime из [RFC-008](./008-runtime-concurrency-model.md):

- **Embedded Runtime**: без поддержки spawn, немедленное выполнение
- **Standard Runtime**: поддержка выражений spawn
- **Full Runtime**: Standard + балансировка нагрузки WorkStealer

### Зависимости

- RFC-008 (Архитектура Runtime) → завершён
- RFC-009 (Модель владения) → завершён
- RFC-010 (Унифицированный синтаксис типов) → завершён
- RFC-011 (Система дженериков) → завершён
- RFC-032 (Рефакторинг AST/IR) → совместно с данным документом определяет spawn

| future/дескрипторы                 | Удалены                                                 | Синхронная блокировка проще                                          | 2026-06-05 |
