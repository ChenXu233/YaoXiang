# RFC-009: Модель владения

## Резюме

Данный документ определяет **модель владения (Ownership Model)** языка программирования YaoXiang.

**Ключевой дизайн — пять концепций, один градиент**:

```
Взглянуть/изменить     Забрать        Совместное владение     Скопировать         Системный уровень
    │                    │                   │                    │                    │
   &T                  Move                ref                clone()            unsafe
  &mut T             Нулевая копия     Авто выбор компилятора   Явное глубокое       *T
  Токен нулевого       По умолчанию      Rc/Arc                   копирование     Пользователь
  размера                                                 Дубликат   отвечает сам
  Атрибут типа
  естественно
  выводит права
```

- **Move (по умолчанию)**: присваивание / передача параметра / возврат = передача владения, нулевая
  копия, автоматическое освобождение через RAII
- **`&T` / `&mut T` (токены заимствования)**: токеновые типы нулевого размера на этапе компиляции.
  `&T` дублируем (разделяемое только чтение), `&mut T` линеен (исключительное изменение). Права
  естественно выводятся из атрибутов типа, никаких специальных правил не требуется. Можно возвращать
  и хранить в структурах.
- **Ключевое слово `ref`**: разделяемое владение между областями видимости. Компилятор автоматически
  выбирает Rc (без пересечения задач) или Arc (с пересечением задач)
- **`clone()`**: явное глубокое копирование
- **`unsafe` + `*T`**: сырые указатели, системный аварийный выход

**Устранённая сложность**:

- ❌ Нет времени жизни `'a`
- ❌ Нет отдельного фреймворка проверки заимствований (конфликты заимствования сводятся к
  утверждениям Хоара и разделяют конвейер доказательства с проверкой типов)
- ❌ Нет GC
- ❌ Нет специальных правил вроде «запрет на выход за пределы» (токен — это обычный тип, область
  видимости обрабатывается системой типов единообразно)
- ❌ Пользователю не нужно знать разницу между Rc/Arc (компилятор выбирает автоматически)

> **Бремя программирования**: `&T` дублируем, `&mut T` не дублируем — два атрибута типа, ноль
> специальных правил, полная автоматизация компилятора. **Гарантия производительности**: Move —
> нулевые накладные расходы, токены — нулевые накладные расходы (типы нулевого размера, исчезают
> после компиляции), `ref` — оплата по необходимости, без пауз GC.

## Мотивация

### Зачем нужна модель владения?

| Язык         | Управление памятью                | Проблема                                                            |
| ------------ | --------------------------------- | ------------------------------------------------------------------- |
| C/C++        | Ручное управление                 | Утечки памяти, висячие указатели, двойное освобождение              |
| Java/Python  | GC                                | Колебания задержек, накладные расходы памяти, непредсказуемые паузы |
| Rust         | Владение + проверка заимствований | Крутая кривая обучения из-за времени жизни `'a`                     |
| **YaoXiang** | **Move + Token + ref**            | **Простота, детерминизм, без GC**                                   |

### Цели дизайна

```yaoxiang
# 1. Move по умолчанию (нулевая копия)
p = Point(1.0, 2.0)
p2 = p                         # Move, p больше нельзя читать

# 2. Токены заимствования &T / &mut T (нулевые накладные расходы, права естественно выводятся из атрибутов типа)
print_info(p2)                 # Компилятор автоматически создаёт токен &Point, освобождается после использования
shift(p2, 1.0, 1.0)           # Компилятор автоматически создаёт токен &mut Point

# 3. ref = совместное использование (компилятор автоматически выбирает Rc/Arc)
shared = ref p2                # Владение между областями видимости
spawn { use(shared) }          # Компилятор: пересечение задач → Arc

# 4. clone() = явное копирование
backup = p2.clone()            # Глубокая копия, независимая

# 5. unsafe + *T = системный уровень
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Ключевые отличия от Rust

| Возможность            | Rust                                            | YaoXiang                                                                                                        |
| ---------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Семантика по умолчанию | Заимствование `&T` (требуется явный `.clone()`) | **Move (передача значения, нулевая копия)**                                                                     |
| Заимствование          | `&T`/`&mut T`, можно вернуть, нужно время жизни | **Токены `&T`/`&mut T` нулевого размера, права естественно выводятся из атрибутов типа Dup/Linear**             |
| Механизм разделения    | `Arc::new()` + ручной Weak                      | **Ключевое слово `ref` (компилятор автоматически выбирает Rc/Arc)**                                             |
| Копирование            | `clone()`                                       | `clone()`                                                                                                       |
| Сырые указатели        | `*T`                                            | `*T`                                                                                                            |
| Время жизни            | `'a                                             | ❌ Отсутствует                                                                                                  |
| Проверка заимствований | Глобальный вывод                                | **Генератор проверки типов автоматически создаёт утверждения о заимствованиях, единый конвейер доказательства** |
| Циклические ссылки     | Ручной Weak                                     | **Единое освобождение при завершении задачи / lint для пересечения задач / стандартная библиотека Weak**        |

## Предложение

### 1. Move (передача владения по умолчанию)

```yaoxiang
# Правило: присваивание / передача параметра / возврат = Move, нулевая копия

p: Point = Point(1.0, 2.0)
p2 = p                           # Move, p больше нельзя читать

# Переменную можно присвоить заново (стиль Python, без затенения)
p = Point(3.0, 4.0)              # p перепривязывается, тип должен совпадать

# Параметр функции: Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Move возврат
}

# Возврат функции: Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Move возврат, нулевая копия
}
```

**Особенности**:

- Нулевая копия (компилятор перемещает указатель)
- После перемещения исходная привязка недоступна для чтения (ошибка компиляции)
- RAII: автоматическое освобождение при выходе из области видимости
- Сигнатура функции `(T) -> T` сама по себе является документацией — потребляет T, возвращает T

### 2. &T / &mut T (токены заимствования)

**Ключевой принцип: `&T` и `&mut T` — это токеновые типы нулевого размера на этапе компиляции. Это
не «ссылки», а «доказательства прав доступа на уровне типов».**

#### 2.1 Два атрибута типа

```
&T      →  Нулевой размер, замораживает исходные данные (пока живёт ReadToken, запрещён WriteToken),
          Множественные представления только для чтения безопасны при заморозке → Дублируем (Dup)
&mut T  →  Нулевой размер, исключительное чтение-запись (пока живёт WriteToken, запрещены любые другие токены),
          Копирование бессмысленно при исключительном доступе → Линеен (не Dup)
```

**Причинно-следственная связь не обратима: заморозка — причина, Dup — следствие.** Не потому что
`&T` реализует Dup, поэтому может сосуществовать — а потому что данные заморожены (мутация
невозможна), множественные представления только для чтения безопасны, и Dup становится реализуемым.
Если принять Dup за определение, а проверку конфликтов за «дополнительную заплатку», дизайн
ошибочен.

#### 2.2 Базовое использование

```yaoxiang
# На стороне метода: объявляем тип параметра, определяем необходимые права
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # Токен &Point даёт право чтения
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # Токен &mut Point даёт право записи
    self.y = self.y + dy
}

# На стороне вызова: компилятор автоматически выбирает заимствование или Move
p = Point(1.0, 2.0)
p.print()                          # Компилятор автоматически создаёт токен &Point
p.shift(1.0, 1.0)                  # Компилятор автоматически создаёт токен &mut Point
p.print()                          # OK, предыдущий токен уже освобождён вместе с вызовом shift

# Свободные функции работают аналогично
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # Два токена &Point сосуществуют — тип Dup
}
d = distance(p, p2)
```

#### 2.3 Почему не нужно «запрещать выход за пределы»

RFC-009 v8 накладывал на `&T`/`&mut T` три специальных правила — только как параметр, нельзя
возвращать, нельзя хранить в структуре. Это были заплатки к концепции «заимствования».

Система токенов в таких правилах не нуждается. Токен — это **обычный тип**, подчиняющийся тем же
правилам областей видимости, что и все остальные типы.

**Возврат ссылки — естественно поддерживается**:

```yaoxiang
# ✅ Токен распространяется вместе с возвращаемым значением
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # Подтокен и родительский токен возвращаются вместе
}

# Использование
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # Токен возвращается вызывающему
print(px_ref)               # OK, токен всё ещё в области видимости
```

**Хранение в структуре — естественно поддерживается**:

```yaoxiang
# ✅ Структура несёт токен в качестве поля
Window: Type = {
    target: Point,
    view: &Point,      # Поле-токен — содержит представление target только для чтения
}

# Токен view порождён из target, Window владеет обоими
# Пока Window существует, токен view валиден
```

#### 2.3 Замыкания и Lambda с явными параметрами

Lambda — это значение функции — его можно вернуть, сохранить, передать за пределы текущей области
видимости. Поэтому Lambda **не захватывает неявно внешние локальные переменные**. Если нужны внешние
данные, их следует передать через явные параметры:

```yaoxiang
# ✅ Lambda использует явные параметры
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } это правило не затрагивает — spawn — это немедленно выполняемый параллельный блок, родительская задача блокируется в ожидании
shared = ref data
spawn { use(shared) }

# ❌ Lambda не может неявно захватывать внешние переменные
x = 42
f = () => { x + 1 }  # Ошибка компиляции: x не в области видимости

# ✅ Правильный способ: явная передача параметра
f = (x) => { x + 1 }
f(x)

# ✅ Правильный способ два: контекст фиксируется в точке создания (каррирование) — замыкание принимает только параметры, не захватывает
gt: (t: Int) -> (x: Int) -> Bool = (x) => x > t
evens = list.filter(nums, gt(threshold))
```

> Дополнение (2026-08-17): правильное решение для зависимости от контекста — фиксация через
> каррирование, а не захват. Область видимости определения замыкания может уже не существовать после
> выхода замыкания, поэтому неявный захват недопустим; однако область видимости точки вызова (точки
> создания) гарантированно жива, и фиксация контекста как значения в этой точке безопасна. См. SPEC
> §12.3.

**`spawn { }` — это не значение функции.** Блок, помеченный spawn, как и тело if/while — выполняется
немедленно, завершается пока жив родительский стековый кадр. Тело spawn нормально обращается к
внешним переменным.

**Пересечение задач — токены не могут пересекать границу**:

```yaoxiang
# ❌ Токены не могут пересекать границу задач
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ Ошибка компиляции: токен не может пересекать границу задач
}

# Это не специальное правило — токен является доказательством прав на этапе компиляции, для совместного использования между задачами используйте ref
# Если нужно совместное использование между задачами, используйте ref
```

**Токен нельзя обернуть в `ref`**:

```yaoxiang
# ❌ Токен — это доказательство прав, а не владение
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ Ошибка компиляции: &T не является владеющим типом
}
```

#### 2.4 Жизненный цикл токена

Жизненный цикл токена определяется **обычными правилами областей видимости**, параметры времени
жизни не нужны:

- Токен в параметре функции: живёт во время вызова, освобождается после вызова
- Возвращаемый токен: владение передаётся вызывающему
- Токен, хранящийся в структуре: живёт вместе со структурой

Компилятору не нужна аннотация `'a`, потому что токен — это **значение**, чей жизненный цикл
управляется системой владения (Move/RAII) единообразно. **Сведение задачи заимствования к задаче
владения.**

#### 2.5 Обнаружение конфликтов токенов

Обнаружение конфликтов токенов — это **утверждение логики Хоара**, а не отдельный
потоко-чувствительный анализ.

```
{Все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}
```

Разделяет конвейер доказательства из RFC-027 с проверкой типов и верификацией пользовательских
предикатов. Компилятор автоматически генерирует утверждения о заимствованиях (`borrow_conflict`,
`use_after_move`, `use_after_drop`, `mut_violation`) и отправляет их в конвейер. Конвейер возвращает
Proved / Disproved / Unproven.

```yaoxiang
# ❌ Токен &mut линеен, его нельзя дублировать
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move, p больше нельзя читать
    p.x = 10.0                      # ❌ Ошибка компиляции: WriteToken уже перемещён
}

# ✅ Токен &T является типом Dup, его можно свободно дублировать
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK, &T — это тип Dup
    print(p.x)                      # OK
    print(p2.x)                     # OK, два токена только для чтения сосуществуют
}
```

**Проверка заимствований не исчезла — она была понижена в размерности.** Существующий
`BorrowChecker` становится `BorrowPredicateEmitter` (генератором утверждений), генерируемые
утверждения о заимствованиях разделяют тот же конвейер доказательства, что и другие типовые
утверждения. Это полностью параллельно концепции проверщика типов: проверщик типов генерирует
утверждения о равенстве типов, генератор утверждений о заимствованиях генерирует утверждения о
заимствованиях, тот же конвейер верифицирует. Подробности см. в
[RFC-009a](../accepted/009a-borrow-proof-pipeline.md).

#### 2.7 Внутреннее устройство компилятора: механизм брендов

Пользователь никогда не взаимодействует с брендами. Компилятор внутри присваивает каждому токену
уникальный идентификатор на этапе компиляции:

```
Видимое пользователю       Внутреннее представление компилятора
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #N — уникальное целое число этапа компиляции
&mut Point     →  WriteToken(Point, #M)   // #M — уникальное целое число этапа компиляции
```

Назначение брендов:

- **Защита от подделки**: токен может быть получен только из капсулы владельца, не может быть
  сконструирован из ничего
- **Отслеживание связей**: при порождении `&Float` из `&Point` (доступ к полю) `&Float` несёт
  производный бренд (`#N.field_x`), компилятор может отследить родительский токен
- **Обнаружение конфликтов**: однородные `WriteToken` и порождённые `ReadToken` не могут быть
  активны одновременно

Бренды полностью исчезают после мономорфизации и инлайнинга, в сгенерированном машинном коде их нет.
**Нулевые накладные расходы во время выполнения.**

#### 2.8 Правила автоматического выбора заимствования

На стороне вызова компилятор автоматически выбирает по следующему приоритету:

```
1. Если аргумент используется далее → сначала создаётся токен (&T или &mut T, согласно сигнатуре метода)
2. Если аргумент далее не используется → Move
3. Приоритет соответствия: &T < &mut T < Move
```

```yaoxiang
# Пример: автоматический выбор
p = Point(1.0, 2.0)
p.print()        # print объявляет &self → компилятор создаёт токен &Point
p.shift(1.0, 1.0) # shift объявляет &mut self → компилятор создаёт токен &mut Point
p2 = p           # Move, p больше не используется
```

#### 2.9 Сравнение с упрощённым заимствованием RFC-009 v8

| Возможность                           | Упрощённое заимствование (v8)                            | Токены заимствования (v9)                                  |
| ------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| Возврат ссылки                        | ❌ Жёстко запрещено                                      | ✅ Токен распространяется с возвращаемым значением         |
| Хранение в структуре                  | ❌ Жёстко запрещено                                      | ✅ Токен как поле структуры                                |
| Явные параметры Lambda                | ❌ Жёстко запрещено                                      | ✅ Lambda использует явные параметры                       |
| Специальные правила                   | 3 (только параметр / нельзя возвращать / нельзя хранить) | 0 — естественный вывод из атрибутов типа                   |
| Проверка заимствований                | Специализированная перекрёстная проверка                 | Потоко-чувствительный анализ активности в проверщике типов |
| Аннотации времени жизни               | Не нужны                                                 | Не нужны                                                   |
| Накладные расходы во время выполнения | Нулевые                                                  | Нулевые (типы нулевого размера, исчезают после компиляции) |
| Сообщения об ошибках                  | «Заимствование не может выйти»                           | «WriteToken(#3) уже перемещён» (обычная ошибка типа)       |
| Ментальная модель пользователя        | Понимание особого статуса «заимствования»                | `&T` дублируем, `&mut T` не дублируем                      |

### 3. Ключевое слово `ref` (автоматическая оптимизация компилятора)

`ref` — единственный способ совместного владения между областями видимости. Что под капотом — Rc или
Arc — пользователю знать не нужно.

#### 3.1 Базовое использование

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # Совместное использование, компилятор автоматически выбирает реализацию

# Совместное использование между задачами
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # Компилятор: пересечение задач → Arc
    spawn { use(data) }           # Компилятор: пересечение задач → Arc
}

# Совместное использование в одной задаче
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # Компилятор: без пересечения задач → Rc
}
```

**Ментальная модель пользователя**: `ref` = совместное владение. Достаточно.

#### 3.2 Анализ выхода компилятора: Rc vs Arc

```
Анализ потока данных ref:

Не выходит за пределы других задач → Rc (неатомарный подсчёт ссылок, низкие накладные расходы)
Выходит за пределы других задач  → Arc (атомарный подсчёт ссылок, потокобезопасный)
```

#### 3.3 Стратегия обнаружения циклов

```
Цикл внутри задачи → допускается молча.
  ├── Каждая задача имеет чёткую границу жизненного цикла — при завершении задачи все ресурсы (включая циклы ref) освобождаются единообразно.
  ├── Долгоживущие сервисы должны создавать дочерние задачи для каждого запроса/соединения — дочерние задачи автоматически освобождаются, накопления утечек не происходит.
  ├── ref всегда сохраняет жизнь, семантика не разбавляется.
  └── Пользователь имеет право строить двунаправленные сильные ссылки внутри задачи (например, промежуточные состояния графовых вычислений).

Цикл между задачами → lint (по умолчанию warn, настраивается).
  ├── Поведение программы корректно, реальной утечки нет (при завершении родительской задачи все ресурсы дочерних освобождаются).
  ├── Но сильные ссылки между задачами означают размытие границ владения, что стоит пересмотреть.
  ├── По умолчанию уровень warn, компиляция проходит с предупреждением.
  └── Команда может установить deny в конфигурации проекта, включив в контроль качества CI.
```

**Уровни Lint** (аналогично Rust clippy):

| Уровень               | Поведение                                | Сценарий                               |
| --------------------- | ---------------------------------------- | -------------------------------------- |
| `allow`               | Не проверять                             | Личный проект                          |
| `warn` (по умолчанию) | Компиляция проходит, есть предупреждение | Этап разработки                        |
| `deny`                | Ошибка компиляции                        | Контроль качества команды в CI         |
| `forbid`              | Ошибка компиляции, нельзя переопределить | Организационное принудительное правило |

```yaoxiang
# Цикл внутри задачи: молча допускается, двунаправленные сильные ссылки
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # Цикл. Единообразно освобождается при завершении задачи.
}

# Цикл между задачами: lint (по умолчанию warn)
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: циклическая ссылка между задачами
    }
}
```

**Пример конфигурации проекта**:

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # Циклы между задачами сразу отклоняются в CI
```

| Тип цикла               | Поведение                | Причина                                                              |
| ----------------------- | ------------------------ | -------------------------------------------------------------------- |
| Цикл ref внутри задачи  | Проверка не выполняется  | Право пользователя, единообразное освобождение при завершении задачи |
| Цикл ref между задачами | lint (по умолчанию warn) | Предупреждение для пересмотра, настраивается на deny                 |

#### 3.4 Weak: предоставляется стандартной библиотекой

```yaoxiang
use std.weak

# Продвинутый пользователь делает явный выбор
a.next = ref b
b.prev = std.weak.new(a.next)   # Пользователь явно контролирует, какое направление слабое
```

**`Weak` — не встроен в язык, а тип стандартной библиотеки.** Для повседневного использования
достаточно `ref`. Продвинутые пользователи, которым нужен тонкий контроль над памятью, вручную
подключают `Weak`.

> Редакция от 2026-08-03: реализовано как отдельный модуль `std.weak` (модуль `std.rc` не существует
> — `ref` является ключевым словом языка, а не модулем; путь модуля унифицирован как `std.weak`,
> точки входа для создания/обновления — `std.weak.new` / `std.weak.upgrade`). Задуманный в черновике
> `std.rc.Weak` не был реализован, руководствуйтесь данной редакцией.

#### 3.5 Токены заимствования vs `ref`

|                   | `&T` / `&mut T`                                                                            | `ref`                                                  |
| ----------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| Что делает        | Взглянуть / изменить на месте                                                              | Совместное владение                                    |
| Область           | С областью видимости значения токена                                                       | Между областями видимости                              |
| Стоимость         | Нулевые накладные расходы (типы нулевого размера)                                          | Rc или Arc (выбирает компилятор)                       |
| Выход             | Возможен (токен распространяется с возвратом / структурой / замыканием)                    | Именно для этого и предназначен                        |
| Пересечение задач | Невозможно (токен — доказательство прав на этапе компиляции, не передаётся между задачами) | Возможно (компилятор автоматически выбирает Arc)       |
| Циклы             | Не затрагивает                                                                             | Внутри задачи молча допускаются, между задачами — lint |

### 4. `clone()` — явное копирование

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # Глубокая копия
# p и p2 независимы и не влияют друг на друга
```

**Когда использовать**: когда нужно сохранить исходное значение, и Move или совместное использование
не подходят.

### 5. `unsafe` + сырые указатели (системное программирование)

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # Сырой указатель
    (*ptr).x = 0.0                # Разыменование (пользователь гарантирует безопасность)
    ptr2 = ptr + 1                # Арифметика указателей
}
```

**Ограничения**:

- Можно использовать только в блоке `unsafe`
- Пользователь гарантирует отсутствие висячих указателей и использования после освобождения
- Используется для FFI, операций с памятью и другого системного программирования

### 6. Обзор градиента владения

```
  Токены заимствования    Move           Совместное        Копирование
  (нулевые накладные)  (нулевые накладные)   (оплата по необходимости)
   │                      │                  │                │
  &T дублируемый токен   Передача владения ref Rc/Arc        clone()
  &mut T линейный токен  по умолчанию      Компилятор        Явное глубокое
   │                      │              выбирает сам        копирование
  Область видимости     Цепное           │
  значения токена       потребление/     ref между задачами → Arc
  Можно возвращать /    возврат          ref внутри задачи → Rc
  хранить в структуре
  Исчезает после         T -> T возврат   Циклы внутри задачи —
  компиляции (нулевой    T -> Void        молча допускаются
  размер)                потребление      Циклы между задачами — lint
                                         Стандартная библиотека Weak — аварийный выход
```

## Комплексный пример

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T: токен только для чтения
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T: токен для изменения
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move: потребление с возвратом
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # Забрать, изменить, вернуть
    }

    # Возврат ссылки: токен распространяется с возвращаемым значением
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Lambda с явными параметрами
double: (x: Int) -> Int = (x) => x * 2

# Комплексное использование
p = Point(1.0, 2.0)
p.print()                           # Токен &Point
p.shift(1.0, 1.0)                   # Токен &mut Point
p = p.scale(2.0)                    # Move → возврат
shared = ref p                      # Совместное использование через ref
spawn { use(shared) }

# Независимая копия через clone
backup = p.clone()

# Цикл внутри задачи: молча допускается
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # Цикл, единообразно освобождается при завершении задачи

# unsafe на системном уровне
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## Ограничения системы типов

### Атрибут типа Dup

`Dup` (Duplicable) — атрибут типа, автоматически управляемый компилятором, означающий
**поверхностное копирование**: при присваивании / передаче параметра копируется дескриптор / токен,
базовые данные разделяются. Это образует трёхуровневый градиент с Move (передача владения) и Clone
(явное глубокое копирование, создание независимой копии).

**Dup и Clone — ортогональные концепции** — Dup копирует дескриптор с разделением данных, Clone
создаёт независимую копию. Тип может одновременно поддерживать Dup и Clone, а может только один из
них.

| Тип           | Dup                                                                             | Clone | Пояснение                                        |
| ------------- | ------------------------------------------------------------------------------- | ----- | ------------------------------------------------ |
| `&T`          | ✅ (копирование токена, несколько представлений указывают на одни данные)       | ✅    | Токен только для чтения                          |
| `ref T`       | ✅ (подсчёт ссылок +1, разделяет данные в куче)                                 | ✅    | Совместное владение (компилятор выбирает Rc/Arc) |
| String, Bytes | ✅ (внутренний подсчёт ссылок, копирование дескриптора разделяет базовый буфер) | ✅    | Строка / байты                                   |
| `&mut T`      | ❌ (линеен, исключителен)                                                       | ❌    | Токен для изменения                              |
| `*T`          | ❌                                                                              | ❌    | Сырой указатель                                  |
| struct        | Производный (автоматически, если все поля Dup)                                  | ✅    | Структура                                        |

**Примитивные типы значений** (Int, Float, Bool, Char) при присваивании обрабатываются встроенным в
компилятор копированием значения — два значения полностью независимы, это не поверхностное
копирование. Они не принадлежат атрибуту типа Dup, а обрабатываются компилятором нативно.

| ----------------------------- | --------------- | ----------------------------------------------------------------------------------------------- |
| Move                          | Ноль            | Перемещение указателя                                                                           |

| `unsafe + *T`                 | Ноль            | Прямые операции с памятью                                                                       |

## Компромиссы

### Преимущества

1. **Единообразие**: `&T`/`&mut T` — обычные типы, а не специальные возможности языка. Полностью
   согласуется с `name: type = value` из RFC-010
2. **Простота**: нет времени жизни, проверка заимствований сводится к утверждениям системы типов.
   `&T` дублируем, `&mut T` не дублируем — два атрибута типа
3. **Мощность**: можно возвращать ссылки, хранить в структурах, захватывать в замыканиях —
   выразительность на уровне Rust
4. **Умный компилятор**: `ref` автоматически выбирает Rc/Arc, на стороне вызова автоматически
   выбирается заимствование
5. **Детерминизм**: `ref` означает сохранение жизни, не превращается молча в слабую ссылку
6. **Высокая производительность**: Move — нулевая копия, токены — нулевые накладные расходы (типы
   нулевого размера, исчезают после компиляции)
7. **Гибкость**: `unsafe + *T` поддерживает системное программирование

### Недостатки

1. **Заражение параметров бренда в дженериках**: токены несут идентификаторы брендов, в сигнатурах
   функций, возвращающих ссылки, проявляются дополнительные параметры дженериков
2. **Накладные расходы `ref` во время выполнения**: атомарные операции имеют стоимость (но это
   неизбежная цена совместного использования)
3. **Риск `unsafe`**: пользователь должен гарантировать корректность
4. **Циклы между задачами — lint, а не ошибка компиляции**: в отличие от Rust, по умолчанию warn,
   требуется настройка команды на `deny` для использования в качестве контроля качества

### Обнаружение конфликтов токенов: утверждения логики Хоара

Полное решение по обнаружению конфликтов токенов см. в
[RFC-009a: Анализ жизненного цикла токенов — на основе конвейера доказательства Хоара](../accepted/009a-borrow-proof-pipeline.md).
Ключевые моменты:

**Активность токенов — это утверждение логики Хоара.**
`{Все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}` — разделяет
конвейер доказательства из RFC-027 с проверкой типов и верификацией пользовательских предикатов.
Компилятор автоматически генерирует утверждения о заимствованиях (`borrow_conflict`,
`use_after_move`, `use_after_drop`, `mut_violation`), конвейер возвращает Proved / Disproved /
Unproven.

**Проверка заимствований не исчезла — она была понижена в размерности.** `BorrowChecker` становится
`BorrowPredicateEmitter`, генерирующим утверждения, а не выполняющим проверку. Это полностью
параллельно концепции «проверщика типов»: проверщик типов генерирует утверждения о равенстве типов,
генератор утверждений о заимствованиях генерирует утверждения о заимствованиях, тот же конвейер
верифицирует.

**Идентификатор бренда (`#42`) — это и есть `'a`.** Информация полностью идентична, различается
кодирование. `'a` виден в сигнатуре типа, `#42` — внутри компилятора. Никакого нового анализа не
изобретено — время жизни перенесено с уровня типов на уровень доказательств.

**Краткое описание алгоритма** (подробности в RFC-009a):

- Сопоставление префиксов дерева брендов → определение конфликтующих токенов (O(глубина), глубина
  ≤ 3)
- Обратный BFS → от потребителя, break обрезает обратные рёбра, структурный анализ покрывает 95%+
  сценариев (быстрый канал)
- Логическое отсечение SMT → вызывается только при сочетании while + условий пути (медленный канал,
  крайне редко)
