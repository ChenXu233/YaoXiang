# RFC-009: Дизайн модели владения

## Резюме

Этот документ определяет **модель владения (Ownership Model)** языка программирования YaoXiang.

**Основная идея — пять концепций, один градиент**:

```
Взглянуть/изменить     Забрать           Разделить        Скопировать     Системный
  на месте                              владение         копию           уровень
    │              │              │              │              │
   &T            Move           ref          clone()        unsafe
  &mut T         нулевая       автоматический  явное глубокое   *T
  жетон          копия         выбор          копирование
  нулевого        по            Rc/Arc       пользователь
  размера         умолчанию                   отвечает сам
  атрибут типа
  естественный
  вывод прав
```

- **Move (по умолчанию)**: присваивание/передача параметра/возврат = передача владения, нулевая
  копия, автоматическое освобождение через RAII
- **`&T` / `&mut T` (жетоны заимствования)**: токены компиляции нулевого размера. `&T` дублируем
  (разделяемое чтение), `&mut T` линеен (исключительное изменение). Права естественно выводятся из
  атрибутов типа, никаких особых правил не требуется. Можно возвращать и хранить в структурах.
- **Ключевое слово `ref`**: разделяемое владение между областями видимости. Компилятор автоматически
  выбирает Rc (без пересечения задач) или Arc (пересекает задачи)
- **`clone()`**: явное глубокое копирование
- **`unsafe` + `*T`**: сырые указатели, системный аварийный выход

**Устранённая сложность**:

- ❌ Нет времени жизни `'a`
- ❌ Нет отдельного фреймворка проверки заимствований (конфликты заимствований сводятся к
  утверждениям Хоара и используют общий конвейер доказательств с проверкой типов)
- ❌ Нет GC
- ❌ Нет особых правил вроде «запрет на побег» (токены — обычные типы, область видимости
  обрабатывается системой типов единообразно)
- ❌ Пользователю не нужно знать разницу между Rc/Arc (компилятор выбирает автоматически)

> **Бремя программиста**: `&T` дублируем, `&mut T` не дублируем — два атрибута типа, ноль особых
> правил, всё полностью автоматизировано. **Гарантия производительности**: Move — без накладных
> расходов, токены — без накладных расходов (тип нулевого размера, исчезает после компиляции), `ref`
> оплачивается по необходимости, без пауз GC.

## Мотивация

### Зачем нужна модель владения?

| Язык         | Управление памятью                | Проблема                                                            |
| ------------ | --------------------------------- | ------------------------------------------------------------------- |
| C/C++        | Ручное управление                 | Утечки памяти, висячие указатели, двойное освобождение              |
| Java/Python  | GC                                | Колебания задержки, накладные расходы памяти, непредсказуемые паузы |
| Rust         | Владение + проверка заимствований | Крутая кривая обучения для времени жизни `'a`                       |
| **YaoXiang** | **Move + Token + ref**            | **Простота, детерминизм, без GC**                                   |

### Цели дизайна

```yaoxiang
# 1. Move по умолчанию (нулевая копия)
p = Point(1.0, 2.0)
p2 = p                         # Move, p больше нельзя читать

# 2. &T / &mut T токены заимствования (нулевые накладные расходы, атрибуты типа естественно выводят права)
print_info(p2)                 # компилятор автоматически создаёт токен &Point, освобождается после использования
shift(p2, 1.0, 1.0)           # компилятор автоматически создаёт токен &mut Point

# 3. ref = разделяемое владение (компилятор автоматически выбирает Rc/Arc)
shared = ref p2                # удержание между областями видимости
spawn { use(shared) }          # компилятор: пересекает задачи → Arc

# 4. clone() = явное копирование
backup = p2.clone()            # глубокая копия, независимая

# 5. unsafe + *T = системный уровень
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Ключевые отличия от Rust

| Особенность                    | Rust                                              | YaoXiang                                                                                                    |
| ------------------------------ | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Семантика по умолчанию         | Заимствование `&T` (требует явного `.clone()`)    | **Move (передача значения, нулевая копия)**                                                                 |
| Заимствование                  | `&T`/`&mut T`, можно вернуть, требует время жизни | **Токены `&T`/`&mut T` нулевого размера, права естественно выводятся из атрибутов типа Dup/Linear**         |
| Механизм разделяемого владения | `Arc::new()` + ручной Weak                        | **Ключевое слово `ref` (компилятор автоматически выбирает Rc/Arc)**                                         |
| Копирование                    | `clone()`                                         | `clone()`                                                                                                   |
| Сырой указатель                | `*T`                                              | `*T`                                                                                                        |
| Время жизни                    | `'a`                                              | ❌ Отсутствует                                                                                              |
| Проверка заимствований         | Глобальный вывод                                  | **Проверщик типов автоматически генерирует утверждения заимствования, единый конвейер доказательств**       |
| Циклические ссылки             | Ручной Weak                                       | **Единое освобождение при завершении задачи / lint для пересечения задач / Weak из стандартной библиотеки** |

## Предложение

### 1. Move (передача владения по умолчанию)

```yaoxiang
# Правило: присваивание / передача параметра / возврат = Move, нулевая копия

p: Point = Point(1.0, 2.0)
p2 = p                           # Move, p больше нельзя читать

# Переменную можно присвоить заново (стиль Python, без затенения)
p = Point(3.0, 4.0)              # p перепривязывается, тип должен совпадать

# Параметр функции: Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # возврат через Move
}

# Возврат из функции: Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # возврат через Move, нулевая копия
}
```

**Особенности**:

- Нулевая копия (компилятор перемещает указатель)
- После перемещения исходная привязка недоступна для чтения (ошибка компиляции)
- RAII: автоматическое освобождение при выходе из области видимости
- Сигнатура функции `(T) -> T` сама по себе является документацией — потребляет T, возвращает T

### 2. &T / &mut T (токены заимствования)

**Ключевой принцип: `&T` и `&mut T` — это токены компиляции нулевого размера. Это не «ссылки», а
«доказательство на уровне типа, предоставляющее права доступа».**

#### 2.1 Два атрибута типа

```
&T      →  нулевой размер, замораживает исходные данные (пока ReadToken живёт, WriteToken запрещён),
          под гарантией заморозки множественные представления только для чтения безопасны → дублируемый (Dup)
&mut T  →  нулевой размер, исключительное чтение-запись (пока WriteToken живёт, любой другой токен запрещён),
          при исключительном доступе копирование бессмысленно → линейный (не Dup)
```

**Причинно-следственная связь не может быть обратной: заморозка — причина, Dup — следствие.** Не
потому, что `&T` реализует Dup, поэтому может сосуществовать — а потому что данные заморожены
(мутация невозможна), множественные представления только для чтения безопасны, и Dup становится
возможным. Если взять Dup за определение, а проверку конфликтов за «дополнительную заплатку», дизайн
ошибочен.

#### 2.2 Базовое использование

```yaoxiang
# Сторона метода: объявление типа параметра определяет требуемые права
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # токен &Point даёт право на чтение
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # токен &mut Point даёт право на запись
    self.y = self.y + dy
}

# Сторона вызова: компилятор автоматически выбирает заимствование или Move
p = Point(1.0, 2.0)
p.print()                          # компилятор автоматически создаёт токен &Point
p.shift(1.0, 1.0)                  # компилятор автоматически создаёт токен &mut Point
p.print()                          # OK, предыдущий токен уже освобождён после завершения shift

# То же для свободных функций
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # два токена &Point сосуществуют — тип Dup
}
d = distance(p, p2)
```

#### 2.3 Почему не нужно «запрещать побег»

RFC-009 v8 наложил на `&T`/`&mut T` три особых правила — можно использовать только как параметр,
нельзя возвращать, нельзя хранить в структуре. Это заплатки к концепции «заимствования».

Система токенов в таких правилах не нуждается. Токены — это **обычные типы**, подчиняющиеся тем же
правилам области видимости, что и все остальные типы.

**Возврат ссылки — естественная поддержка**:

```yaoxiang
# ✅ Токен распространяется вместе с возвращаемым значением
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # дочерний и родительский токены возвращаются вместе
}

# Использование
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # токен возвращён вызывающему коду
print(px_ref)               # OK, токен всё ещё в области видимости
```

**Хранение в структурах — естественная поддержка**:

```yaoxiang
# ✅ Структура несёт токен как поле
Window: Type = {
    target: Point,
    view: &Point,      # поле-токен — содержит представление target только для чтения
}

# view наследуется от target, Window владеет обоими
# Пока Window существует, токен view действителен
```

#### 2.3 Замыкания и лямбды с явными параметрами

Лямбда — это значение функции — его можно возвращать, хранить и передавать за пределы текущей
области видимости. Поэтому лямбда **не захватывает неявно переменные внешней области**. Если нужны
внешние данные, передавайте их через явные параметры:

```yaoxiang
# ✅ Лямбда использует явные параметры
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } на это правило не распространяется — spawn выполняет блок немедленно, родительская задача блокируется в ожидании
shared = ref data
spawn { use(shared) }

# ❌ Лямбда не может неявно захватывать внешние переменные
x = 42
f = () => { x + 1 }  # ошибка компиляции: x не в области видимости

# ✅ Правильный способ: явная передача параметра
f = (x) => { x + 1 }
f(x)

# ✅ Второй правильный способ: контекст фиксируется в точке создания (каррирование) — замыкание принимает только параметры, не захватывает
gt: (t: Int) -> (x: Int) -> Bool = (x) => x > t
evens = list.filter(nums, gt(threshold))
```

> Дополнение (2026-08-17): правильное решение для контекстной зависимости — фиксация через
> каррирование, а не захват. После побега замыкания область видимости в точке его определения может
> уже не существовать, поэтому неявный захват запрещён; однако область видимости в точке вызова
> (создания) гарантированно жива, и фиксация контекста в этой точке как значения, входящего в
> замыкание, безопасна. См. SPEC §12.3.

**`spawn { }` — это не значение функции.** Блок, помеченный `spawn`, как и тело `if/while` —
выполняется немедленно, пока родительский кадр стека жив. Тело `spawn` может нормально обращаться к
внешним переменным.

**Пересечение задач — токены не могут пересекать границу потока**:

```yaoxiang
# ❌ Токены не могут пересекать границу задач
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ ошибка компиляции: токен не может пересекать задачи
}

# Это не особое правило — токен является доказательством прав компиляции, для разделяемого владения между задачами используйте ref
# Если нужно разделяемое владение между задачами, используйте ref
```

**Токены не могут быть ref**:

```yaoxiang
# ❌ Токен — это доказательство прав, а не владение
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ ошибка компиляции: &T не является владеющим типом
}
```

#### 2.4 Жизненный цикл токена

Жизненный цикл токена определяется **обычными правилами области видимости**, без необходимости в
параметрах времени жизни:

- Токены в параметрах функции: живут во время вызова, освобождаются после его завершения
- Возвращённые токены: владение передаётся вызывающему коду
- Токены, хранящиеся в структурах: живут вместе со структурой

Компилятору не нужна аннотация `'a`, потому что токен — это **значение**, и его жизненный цикл
управляется системой владения (Move/RAII) единообразно. **Сведение проблемы заимствования к проблеме
владения.**

#### 2.5 Обнаружение конфликтов токенов

Обнаружение конфликтов токенов — это **утверждение логики Хоара**, а не отдельный
потоко-чувствительный анализ.

```
{все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}
```

Разделяет конвейер доказательств из RFC-027 с проверкой типов и пользовательскими предикатами.
Компилятор автоматически генерирует утверждения заимствования (`borrow_conflict`, `use_after_move`,
`use_after_drop`, `mut_violation`) и отправляет их в конвейер для верификации. Конвейер возвращает
Proved / Disproved / Unproven.

```yaoxiang
# ❌ &mut токен линеен, нельзя копировать
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move, p больше нельзя читать
    p.x = 10.0                      # ❌ ошибка компиляции: WriteToken уже перемещён
}

# ✅ &T токен имеет тип Dup, можно свободно копировать
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK, &T имеет тип Dup
    print(p.x)                      # OK
    print(p2.x)                     # OK, два токена только для чтения сосуществуют
}
```

**Проверка заимствований не исчезла — она понижена в размерности.** Существующий `BorrowChecker`
становится `BorrowPredicateEmitter` (генератором утверждений), генерируемые утверждения
заимствования разделяют тот же конвейер доказательств с другими утверждениями типов. Это полностью
параллельно концепции проверщика типов: проверщик типов генерирует утверждения о равенстве типов,
генератор утверждений заимствования генерирует утверждения заимствования, и тот же конвейер
верифицирует их. Подробный дизайн см. в [RFC-009a](../accepted/009a-borrow-proof-pipeline.md).

#### 2.7 Внутреннее устройство компилятора: механизм брендов

Пользователь никогда не сталкивается с брендами. Компилятор внутренне присваивает каждому токену
уникальный идентификатор на этапе компиляции:

```
Видимое пользователю         Внутреннее представление компилятора
────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #N — уникальное целое число на этапе компиляции
&mut Point     →  WriteToken(Point, #M)   // #M — уникальное целое число на этапе компиляции
```

Назначение брендов:

- **Защита от подделки**: токен может быть получен только из капсулы владельца, не может быть
  сконструирован из воздуха
- **Отслеживание связей**: при получении `&Float` из `&Point` (доступ к полю) `&Float` несёт
  производный бренд (`#N.field_x`), и компилятор может отследить его до родительского токена
- **Обнаружение конфликтов**: `WriteToken` того же источника и производный `ReadToken` не могут быть
  активны одновременно

Бренды полностью исчезают после мономорфизации и инлайнинга, в сгенерированном машинном коде их не
существует. **Нулевые накладные расходы во время выполнения.**

#### 2.8 Правила автоматического выбора заимствования

На стороне вызова компилятор автоматически выбирает по следующему приоритету:

```
1. Если аргумент используется далее → предпочтительно создать токен (&T или &mut T, согласно сигнатуре метода)
2. Если аргумент далее не используется → Move
3. Приоритет соответствия: &T < &mut T < Move
```

```yaoxiang
# Пример: автоматический выбор
p = Point(1.0, 2.0)
p.print()        # print объявляет &self → компилятор создаёт токен &Point
p.shift(1.0, 1.0) # shift объявляет &mut self → компилятор создаёт токен &mut Point
p2 = p           # Move, p больше не используется
```

#### 2.9 Сравнение с упрощённым заимствованием RFC-009 v8

| Особенность                           | Упрощённое заимствование (v8)                            | Токены заимствования (v9)                                 |
| ------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------- |
| Возврат ссылки                        | ❌ Жёстко запрещено                                      | ✅ Токен распространяется с возвращаемым значением        |
| Хранение в структуре                  | ❌ Жёстко запрещено                                      | ✅ Токен как поле структуры                               |
| Явные параметры лямбды                | ❌ Жёстко запрещено                                      | ✅ Лямбда использует явные параметры                      |
| Особые правила                        | 3 (только параметр / нельзя возвращать / нельзя хранить) | 0 — естественный вывод из атрибутов типа                  |
| Проверка заимствований                | Выделенная перекрёстная проверка заимствований           | Потоко-чувствительный анализ живости в проверщике типов   |
| Аннотации времени жизни               | Не нужны                                                 | Не нужны                                                  |
| Накладные расходы во время выполнения | Нулевые                                                  | Нулевые (тип нулевого размера, исчезает после компиляции) |
| Сообщение об ошибке                   | «Заимствование не может убежать»                         | «WriteToken(#3) уже перемещён» (обычная ошибка типа)      |
| Ментальная модель пользователя        | Понимание особого статуса «заимствования»                | `&T` дублируем, `&mut T` не дублируем                     |

### 3. Ключевое слово ref (автоматическая оптимизация компилятора)

`ref` — единственный способ разделяемого владения между областями видимости. Под капотом Rc или Arc
— пользователю не нужно об этом заботиться.

#### 3.1 Базовое использование

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # разделяемое владение, компилятор автоматически выбирает реализацию

# Разделяемое владение между задачами
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # компилятор: пересекает задачи → Arc
    spawn { use(data) }           # компилятор: пересекает задачи → Arc
}

# Разделяемое владение в одной задаче
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # компилятор: не пересекает задачи → Rc
}
```

**Ментальная модель пользователя**: `ref` = разделяемое удержание. Этого достаточно.

#### 3.2 Анализ побегов компилятора: Rc vs Arc

```
Анализ потоков данных для ref:

Не убегает в другие задачи → Rc (неатомарный подсчёт ссылок, низкие накладные расходы)
Убегает в другие задачи   → Arc (атомарный подсчёт ссылок, потокобезопасный)
```

#### 3.3 Стратегия обнаружения циклов

```
Цикл внутри задачи → допускается без предупреждений.
  ├── Каждая задача имеет чёткие границы жизненного цикла — при завершении задачи все ресурсы (включая циклы ref) освобождаются единообразно.
  ├── Долгоживущие сервисы должны создавать подзадачи для каждого запроса/соединения — подзадачи освобождаются автоматически, утечки не накапливаются.
  ├── ref всегда поддерживает жизнь, семантика не разбавляется.
  └── Пользователь имеет право строить двунаправленные сильные ссылки внутри задачи (например, промежуточные состояния графовых вычислений).

Цикл между задачами → lint (по умолчанию warn, настраивается).
  ├── Поведение программы корректно, реальной утечки нет (при завершении родительской задачи все ресурсы подзадач освобождаются).
  ├── Но сильные ссылки между задачами означают размытые границы владения, стоит остановиться и пересмотреть дизайн.
  ├── По умолчанию уровень warn — компиляция проходит, но с подсказкой.
  └── Команда может установить deny в конфигурации проекта как врата качества CI.
```

**Уровни Lint** (аналогично Rust clippy):

| Уровень               | Поведение                                | Сценарий                             |
| --------------------- | ---------------------------------------- | ------------------------------------ |
| `allow`               | Без проверки                             | Личный проект                        |
| `warn` (по умолчанию) | Компиляция проходит, с подсказкой        | Этап разработки                      |
| `deny`                | Ошибка компиляции                        | Врата качества командного CI         |
| `forbid`              | Ошибка компиляции, нельзя переопределить | Организационные обязательные правила |

```yaoxiang
# Цикл внутри задачи: допускается без предупреждений, двунаправленные сильные ссылки
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # цикл. Единообразное освобождение при завершении задачи.
}

# Цикл между задачами: lint (по умолчанию warn)
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: циклическая ссылка между задачами
    }
}
```

**Пример конфигурации проекта**:

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # циклы между задачами сразу отклоняются в CI
```

| Тип цикла               | Поведение                | Причина                                                              |
| ----------------------- | ------------------------ | -------------------------------------------------------------------- |
| Цикл ref внутри задачи  | Без проверки             | Право пользователя, единообразное освобождение при завершении задачи |
| Цикл ref между задачами | lint (по умолчанию warn) | Подсказка пересмотреть дизайн, настраивается на deny                 |

#### 3.4 Weak: предоставляется стандартной библиотекой

```yaoxiang
use std.weak

# Продвинутый пользователь делает явный выбор
a.next = ref b
b.prev = std.weak.new(a.next)   # пользователь явно контролирует, какое направление слабое
```

**`Weak` — не встроен в язык, это тип стандартной библиотеки.** Для повседневного использования
достаточно `ref`. Продвинутые пользователи, которым нужен тонкий контроль над памятью, импортируют
`Weak` вручную.

> Редакция 2026-08-03: реализовано как отдельный модуль `std.weak` (`std.rc` не существует — `ref`
> является ключевым словом языка, а не модулем; путь модуля унифицирован как `std.weak`, точки входа
> для конструирования/обновления — `std.weak.new` / `std.weak.upgrade`). Первоначальный набросок
> `std.rc.Weak` не был реализован, руководствуйтесь данной редакцией.

#### 3.5 Токены заимствования vs ref

|                    | `&T` / `&mut T`                                                                       | `ref`                                                             |
| ------------------ | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Назначение         | Взглянуть / изменить на месте                                                         | Разделяемое удержание                                             |
| Область            | В пределах области видимости значения токена                                          | Между областями видимости                                         |
| Стоимость          | Нулевые накладные расходы (тип нулевого размера)                                      | Rc или Arc (выбирает компилятор)                                  |
| Побег              | Возможен (токен распространяется через возвращаемое значение / структуру / замыкание) | Для этого и предназначен                                          |
| Пересечение задач  | Невозможно (токен — доказательство прав компиляции, не может пересекать задачи)       | Возможно (компилятор автоматически выбирает Arc)                  |
| Образование циклов | Не задействовано                                                                      | Внутри задачи допускается без предупреждений, между задачами lint |

### 4. clone() — явное копирование

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # глубокая копия
# p и p2 независимы, не влияют друг на друга
```

**Когда использовать**: когда нужно сохранить исходное значение, и при этом не подходит ни Move, ни
разделяемое владение.

### 5. unsafe + сырые указатели (системное программирование)

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # сырой указатель
    (*ptr).x = 0.0                # разыменование (безопасность гарантирует пользователь)
    ptr2 = ptr + 1                # арифметика указателей
}
```

**Ограничения**:

- Можно использовать только в блоках `unsafe`
- Пользователь гарантирует отсутствие висячих указателей и использования после освобождения
- Для FFI, операций с памятью и другого системного программирования

## Комплексный пример

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T: токен только для чтения
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T: токен для изменения
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move: потребление с возвратом
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # забрать, изменить, вернуть
    }

    # Возврат ссылки: токен распространяется с возвращаемым значением
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Лямбда с явными параметрами
double: (x: Int) -> Int = (x) => x * 2

# Комплексное использование
p = Point(1.0, 2.0)
p.print()                           # токен &Point
p.shift(1.0, 1.0)                   # токен &mut Point
p = p.scale(2.0)                    # Move → возврат
shared = ref p                      # разделяемое владение через ref
spawn { use(shared) }

# Независимая копия через clone
backup = p.clone()

# Цикл внутри задачи: допускается без предупреждений
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # цикл, единообразное освобождение при завершении задачи

# unsafe на системном уровне
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## Ограничения системы типов

### Атрибут типа Dup

`Dup` (Duplicable) — это атрибут типа, автоматически управляемый компилятором, означающий
**поверхностное копирование**: при присваивании/передаче параметра копируется дескриптор/токен,
базовые данные разделяются. Это образует трёхступенчатый градиент с Move (передача владения) и Clone
(явное глубокое копирование, создающее независимую копию).

**Dup и Clone — ортогональные концепции** — Dup копирует дескриптор, разделяя данные, Clone создаёт
независимую копию. Тип может одновременно поддерживать и Dup, и Clone, либо только одно из них.

| Тип           | Dup                                                                             | Clone | Описание                                                         |
| ------------- | ------------------------------------------------------------------------------- | ----- | ---------------------------------------------------------------- |
| `&T`          | ✅ (копирование токена, множество представлений указывают на те же данные)      | ✅    | Токен только для чтения                                          |
| `ref T`       | ✅ (счётчик ссылок +1, разделяемые данные в куче)                               | ✅    | Разделяемое удержание (компилятор автоматически выбирает Rc/Arc) |
| String, Bytes | ✅ (внутренний подсчёт ссылок, копирование дескриптора разделяет базовый буфер) | ✅    | Строка/байты                                                     |
| `&mut T`      | ❌ (линейный, исключительный)                                                   | ❌    | Токен для изменения                                              |
| `*T`          | ❌                                                                              | ❌    | Сырой указатель                                                  |
| struct        | Производный (автоматически, если все поля Dup)                                  | ✅    | Структура                                                        |

**Примитивные типы значений** (Int, Float, Bool, Char) при присваивании подвергаются встроенному
копированию значений компилятором — два значения полностью независимы, это не поверхностное
копирование. Они не относятся к атрибуту типа Dup, а обрабатываются компилятором нативно.

## Компромиссы

### Преимущества

1. **Единообразие**: `&T`/`&mut T` — обычные типы, не особые языковые конструкции. Полностью
   соответствует `name: type = value` из RFC-010
2. **Простота**: нет времени жизни, проверка заимствований сводится к утверждениям системы типов.
   `&T` дублируем, `&mut T` не дублируем — два атрибута типа
3. **Мощность**: можно возвращать ссылки, хранить в структурах, захватывать замыканиями —
   выразительность на уровне Rust
4. **Интеллект компилятора**: ref автоматически выбирает Rc/Arc, сторона вызова автоматически
   выбирает заимствование
5. **Детерминизм**: ref — это гарантия жизни, не превращается молча в слабую ссылку
6. **Высокая производительность**: Move — нулевая копия, токены — нулевые накладные расходы (тип
   нулевого размера, исчезает после компиляции)
7. **Гибкость**: `unsafe + *T` поддерживает системное программирование

### Недостатки

1. **Распространение параметров бренда в generics**: токены несут идентификаторы брендов, в
   сигнатурах функций, возвращающих ссылки, видны дополнительные параметры generics
2. **Накладные расходы ref во время выполнения**: атомарные операции имеют стоимость (но это
   неизбежная плата за разделяемое владение)
3. **Риск unsafe**: пользователь должен гарантировать корректность
4. **Циклы между задачами — lint, а не ошибка компиляции**: в отличие от Rust, по умолчанию warn,
   для использования в качестве ворот качества требуется настройка командой deny

| Вариант                           | Почему не выбран                                                                                   |

### Обнаружение конфликтов токенов: утверждения логики Хоара

Полное решение для обнаружения конфликтов токенов см. в
[RFC-009a: Анализ жизненного цикла токенов — на основе конвейера доказательств Хоара](../accepted/009a-borrow-proof-pipeline.md).
Ключевые моменты:

**Живость токенов — это утверждение логики Хоара.**
`{все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}` — разделяет
конвейер доказательств из RFC-027 с проверкой типов и пользовательскими предикатами. Компилятор
автоматически генерирует утверждения заимствования (`borrow_conflict`, `use_after_move`,
`use_after_drop`, `mut_violation`), конвейер возвращает Proved / Disproved / Unproven.

**Проверка заимствований не исчезла — она понижена в размерности.** `BorrowChecker` становится
`BorrowPredicateEmitter`, генерирующим утверждения, а не выполняющим проверки. Это полностью
параллельно концепции «проверщика типов»: проверщик типов генерирует утверждения равенства типов,
генератор утверждений заимствования генерирует утверждения заимствования, и тот же конвейер
верифицирует их.

**Идентификатор бренда (`#42`) — это и есть `'a`.** Информация полностью идентична, кодирование
различно. `'a` виден в сигнатуре типа, `#42` — внутри компилятора. Никакого нового анализа — время
жизни перенесено с уровня типов на уровень доказательств.

**Схема алгоритма** (подробности в RFC-009a):

- Префиксное сопоставление по дереву брендов → определение конфликтующих токенов (O(depth), глубина
  ≤ 3)
- Обратный BFS → от потребителя, break обрезает обратные рёбра, структурный анализ покрывает 95%+
  сценариев (быстрый канал)
- Логическое отсечение SMT → вызывается только при `while` + условиях пути (медленный канал, крайне
  редко)
