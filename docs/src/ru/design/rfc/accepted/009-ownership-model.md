# RFC-009: Модель владения

## Резюме

Данный документ определяет **модель владения (Ownership Model)** языка программирования YaoXiang.

**Основная идея — пять концепций, один градиент**:

```
Взглянуть/изменить      Забрать          Совместное владение   Скопировать     Системный
на месте                                                          экземпляр       уровень
    │                   │                   │                   │               │
   &T                 Move              ref                clone()         unsafe
  &mut T              без копий        компилятор          явное          *T
  токен              по умолчанию     выбирает Rc/Arc    глубокое       пользователь
  нулевого                              автоматически     копирование    несёт
  размера                                                                       ответственность
  атрибут типа
  естественный
  вывод прав
```

- **Move (по умолчанию)**: присваивание / передача параметра / возврат = передача владения, без
  копий, автоматическое освобождение по RAII
- **`&T` / `&mut T` (токены заимствования)**: токенные типы нулевого размера на этапе компиляции.
  `&T` — дублируемый (разделяемое неизменяемое владение), `&mut T` — линейный (исключительное
  изменяемое владение). Права естественно выводятся из атрибутов типа, никаких специальных правил не
  требуется. Можно возвращать, можно хранить в структурах.
- **Ключевое слово `ref`**: разделяемое владение через границы областей видимости. Компилятор
  автоматически выбирает Rc (без пересечения задач) или Arc (с пересечением задач).
- **`clone()`**: явное глубокое копирование
- **`unsafe` + `*T`**: сырые указатели, системный аварийный выход

**Устранённая сложность**:

- ❌ Нет времён жизни `'a`
- ❌ Нет отдельного фреймворка проверки заимствований (конфликты заимствований сводятся к логическим
  утверждениям Хоара и разделяют конвейер доказательства с проверкой типов)
- ❌ Нет GC
- ❌ Нет специальных правил вроде «запрет на выход» (токены — обычные типы, области видимости
  обрабатываются единообразно системой типов)
- ❌ Пользователю не нужно знать разницу между Rc/Arc (компилятор выбирает автоматически)

> **Бремя программиста**: `&T` — дублируемый, `&mut T` — недублируемый — два атрибута типа, ноль
> специальных правил, всё автоматизировано компилятором. **Гарантии производительности**: Move —
> нулевые накладные расходы, токены — нулевые накладные расходы (типы нулевого размера, исчезают
> после компиляции), `ref` — оплата по мере необходимости, без пауз GC.

## Мотивация

### Зачем нужна модель владения?

| Язык         | Управление памятью                | Проблема                                                  |
| ------------ | --------------------------------- | --------------------------------------------------------- |
| C/C++        | Ручное                            | Утечки памяти, висячие указатели, двойное освобождение    |
| Java/Python  | GC                                | Флуктуации задержек, расход памяти, непредсказуемые паузы |
| Rust         | Владение + проверка заимствований | Крутая кривая обучения из-за времён жизни `'a`            |
| **YaoXiang** | **Move + Token + ref**            | **Просто, детерминированно, без GC**                      |

### Цели проектирования

```yaoxiang
# 1. Move по умолчанию (без копий)
p = Point(1.0, 2.0)
p2 = p                         # Move, p больше нельзя читать

# 2. &T / &mut T — токены заимствования (нулевые накладные расходы, права естественно выводятся из атрибутов типа)
print_info(p2)                 # Компилятор автоматически создаёт токен &Point, освобождается после использования
shift(p2, 1.0, 1.0)           # Компилятор автоматически создаёт токен &mut Point

# 3. ref = совместное владение (компилятор автоматически выбирает Rc/Arc)
shared = ref p2                # Удержание через границы областей видимости
spawn { use(shared) }          # Компилятор: пересечение задач → Arc

# 4. clone() = явное копирование
backup = p2.clone()            # Глубокое копирование, независимый экземпляр

# 5. unsafe + *T = системный уровень
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Ключевые отличия от Rust

| Свойство                      | Rust                                                  | YaoXiang                                                                                              |
| ----------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Семантика по умолчанию        | Заимствование `&T` (требуется явный `.clone()`)       | **Move (передача значения, без копий)**                                                               |
| Заимствование                 | `&T`/`&mut T`, можно возвращать, требует времён жизни | **`&T`/`&mut T` — токены нулевого размера, права естественно выводятся из атрибутов типа Dup/Linear** |
| Механизм совместного владения | `Arc::new()` + ручной Weak                            | **Ключевое слово `ref` (компилятор автоматически выбирает Rc/Arc)**                                   |
| Копирование                   | `clone()`                                             | `clone()`                                                                                             |
| Сырые указатели               | `*T`                                                  | `*T`                                                                                                  |
| Времена жизни                 | `'a`                                                  | ❌ Отсутствуют                                                                                        |
| Проверка заимствований        | Глобальный вывод                                      | **Генератор утверждений о заимствованиях встроен в проверщик типов, единый конвейер верификации**     |
| Циклические ссылки            | Ручной Weak                                           | **Единое освобождение по завершении задачи / lint для межзадачных / Weak из стандартной библиотеки**  |

## Предложение

### 1. Move (передача владения по умолчанию)

```yaoxiang
# Правило: присваивание / передача параметра / возврат = Move, без копий

p: Point = Point(1.0, 2.0)
p2 = p                           # Move, p больше нельзя читать

# Переменную можно переприсвоить (стиль Python, без затенения)
p = Point(3.0, 4.0)              # p перепривязывается, тип должен совпадать

# Параметр функции: Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Возврат через Move
}

# Возврат из функции: Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Возврат через Move, без копий
}
```

**Особенности**:

- Без копий (компилятор перемещает указатель)
- После перемещения исходная привязка недоступна для чтения (ошибка компиляции)
- RAII: автоматическое освобождение при выходе из области видимости
- Сигнатура функции `(T) -> T` сама по себе является документацией — потребляет T, возвращает T

### 2. &T / &mut T (токены заимствования)

**Ключевой принцип: `&T` и `&mut T` — это токенные типы нулевого размера на этапе компиляции. Это не
«ссылки», а «доказательство права доступа на уровне типов».**

#### 2.1 Два атрибута типа

```
&T      →  нулевой размер, замораживает исходные данные (пока живёт ReadToken, WriteToken запрещён),
          под гарантией заморозки множественные неизменяемые представления безопасны → дублируемый (Dup)
&mut T  →  нулевой размер, исключительное чтение-запись (пока живёт WriteToken, любые другие токены запрещены),
          дублирование бессмысленно при исключительном доступе → линейный (не Dup)
```

**Причинно-следственная связь не может быть обратной: заморозка — причина, Dup — следствие.** Не
потому, что `&T` реализует Dup и потому может сосуществовать, — а потому, что данные заморожены
(мутация невозможна), множественные неизменяемые представления безопасны, и Dup может быть
реализован. Если считать Dup определением, а проверку конфликтов — «дополнительной заплаткой»,
проектирование ошибочно.

#### 2.2 Базовое использование

```yaoxiang
# На стороне метода: объявляем типы параметров, определяем требуемые права
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # Токен &Point даёт право чтения
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # Токен &mut Point даёт право записи
    self.y = self.y + dy
}

# На стороне вызова: компилятор автоматически выбирает заимствование или Move
p = Point(1.0, 2.0)
p.print()                          # Компилятор автоматически создаёт токен &Point
p.shift(1.0, 1.0)                  # Компилятор автоматически создаёт токен &mut Point
p.print()                          # OK, предыдущий токен уже освобождён по завершении вызова shift

# Свободные функции работают аналогично
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # Два токена &Point сосуществуют — Dup-тип
}
d = distance(p, p2)
```

#### 2.3 Почему не нужно правило «запрет на выход»

В RFC-009 v8 для `&T`/`&mut T` были заданы три специальных правила — можно использовать только как
параметр, нельзя возвращать, нельзя хранить в структурах. Это было «заплатками» к концепции
«заимствования».

Система токенов не нуждается в этих правилах. Токены — **обычные типы**, подчиняющиеся тем же
правилам областей видимости, что и все остальные типы.

**Возврат ссылки — естественная поддержка**:

```yaoxiang
# ✅ Токен распространяется вместе с возвращаемым значением
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # Дочерний токен и родительский токен возвращаются вместе
}

# Использование
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # Токен возвращается вызывающему коду
print(px_ref)               # OK, токен всё ещё в области видимости
```

**Хранение в структурах — естественная поддержка**:

```yaoxiang
# ✅ Структура содержит токен в качестве поля
Window: Type = {
    target: Point,
    view: &Point,      # Поле-токен — удерживает неизменяемое представление target
}

# Токен view порождён из target, Window владеет обоими
# Пока Window существует, токен view действителен
```

#### 2.3 Замыкания и лямбды с явными параметрами

Лямбда — это значение-функция — оно может быть возвращено, сохранено, передано за пределы текущей
области видимости. Поэтому лямбда **не захватывает неявно переменные внешней области видимости**.
Когда нужны внешние данные, их передают через явные параметры:

```yaoxiang
# ✅ Лямбда использует явные параметры
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } не подчиняется этому правилу — spawn немедленно выполняет параллельный блок, родительская задача блокируется в ожидании
shared = ref data
spawn { use(shared) }

# ❌ Лямбда не может неявно захватывать переменные внешней области видимости
x = 42
f = () => { x + 1 }  # Ошибка компиляции: x не в области видимости

# ✅ Правильный способ: явная передача параметра
f = (x) => { x + 1 }
f(x)
```

**`spawn { }` — не значение-функция.** Блок, помеченный `spawn`, подобен телу `if`/`while` —
выполняется немедленно, завершается пока жив родительский стековый кадр. Тело `spawn` имеет
нормальный доступ к переменным внешней области видимости.

**Между задачами — токен не пересекает границу**:

```yaoxiang
# ❌ Токен не может пересекать границу задач
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ Ошибка компиляции: токен не может передаваться между задачами
}

# Это не специальное правило — токен является доказательством права на этапе компиляции; для совместного владения между задачами используйте ref
# Если требуется совместное владение между задачами, используйте ref
```

**Токен не может быть `ref`**:

```yaoxiang
# ❌ Токен — это доказательство права, а не владение
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ Ошибка компиляции: &T не является владеющим типом
}
```

#### 2.4 Время жизни токена

Время жизни токена определяется **обычными правилами областей видимости**, без параметров времени
жизни:

- Токен в параметре функции: живёт во время вызова, освобождается после вызова
- Возвращаемый токен: владение передаётся вызывающему коду
- Токен, хранящийся в структуре: живёт вместе со структурой

Компилятору не нужны аннотации `'a`, потому что токены — это **значения**, и их время жизни
единообразно управляется системой владения (Move/RAII). **Сведение проблемы заимствования к проблеме
владения.**

#### 2.5 Обнаружение конфликтов токенов

Обнаружение конфликтов токенов — это **логическое утверждение Хоара**, а не отдельный
потоко-чувствительный анализ.

```
{Все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}
```

Разделяет конвейер доказательства из RFC-027 с проверкой типов и проверкой пользовательских
предикатов. Компилятор автоматически генерирует утверждения о заимствованиях (`borrow_conflict`,
`use_after_move`, `use_after_drop`, `mut_violation`) и отправляет их в конвейер. Конвейер возвращает
Proved / Disproved / Unproven.

```yaoxiang
# ❌ Токен &mut линеен, не может быть скопирован
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move, p больше нельзя читать
    p.x = 10.0                      # ❌ Ошибка компиляции: WriteToken уже перемещён
}

# ✅ Токен &T — Dup-тип, может свободно копироваться
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK, &T — Dup-тип
    print(p.x)                      # OK
    print(p2.x)                     # OK, два неизменяемых токена сосуществуют
}
```

**Проверка заимствований не исчезла — она понижена в размерности.** Существующий `BorrowChecker`
становится `BorrowPredicateEmitter` (генератором утверждений), который генерирует утверждения о
заимствованиях и разделяет с другими типовыми утверждениями единый конвейер доказательства. Это
полностью параллельно концепции проверщика типов: проверщик типов генерирует утверждения о равенстве
типов, генератор утверждений о заимствованиях генерирует утверждения о заимствованиях, и один
конвейер верифицирует их. Подробное проектирование см. в
[RFC-009a](../accepted/009a-borrow-proof-pipeline.md).

#### 2.7 Внутри компилятора: механизм брендов

Пользователь никогда не взаимодействует с брендами напрямую. Компилятор внутри назначает каждому
токену уникальный идентификатор на этапе компиляции:

```
Что видит пользователь       Внутреннее представление компилятора
────────────────────────────────────────────────────────
&Point         →  ReadToken(Point, #N)    // #N — уникальное целое на этапе компиляции
&mut Point     →  WriteToken(Point, #M)   // #M — уникальное целое на этапе компиляции
```

Назначение брендов:

- **Защита от подделки**: токен может быть получен только из капсулы владельца, не может быть
  сконструирован из воздуха
- **Отслеживание связей**: при порождении `&Float` из `&Point` (доступ к полю) `&Float` несёт
  производный бренд (`#N.field_x`), компилятор может отследить его до родительского токена
- **Обнаружение конфликтов**: одноимённые `WriteToken` и порождённые `ReadToken` не могут быть
  одновременно активны

Бренды полностью исчезают после мономорфизации и инлайнинга, в генерируемом машинном коде их нет.
**Нулевые накладные расходы в рантайме.**

#### 2.8 Правила автоматического выбора заимствования

На стороне вызова компилятор автоматически выбирает в следующем порядке приоритета:

```
1. Если аргумент используется далее → предпочтительно создать токен (&T или &mut T, согласно сигнатуре метода)
2. Если аргумент далее не используется → Move
3. Порядок предпочтения: &T < &mut T < Move
```

```yaoxiang
# Пример: автоматический выбор
p = Point(1.0, 2.0)
p.print()        # print объявляет &self → компилятор создаёт токен &Point
p.shift(1.0, 1.0) # shift объявляет &mut self → компилятор создаёт токен &mut Point
p2 = p           # Move, p более не используется
```

#### 2.9 Сравнение с упрощённым заимствованием RFC-009 v8

| Свойство                       | Упрощённое заимствование (v8)                                | Токены заимствования (v9)                                  |
| ------------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------- |
| Возврат ссылки                 | ❌ Жёстко запрещено                                          | ✅ Токен распространяется с возвращаемым значением         |
| Хранение в структурах          | ❌ Жёстко запрещено                                          | ✅ Токен как поле структуры                                |
| Явные параметры лямбды         | ❌ Жёстко запрещено                                          | ✅ Лямбда использует явные параметры                       |
| Специальные правила            | 3 (только как параметр / нельзя возвращать / нельзя хранить) | 0 — естественный вывод из атрибутов типа                   |
| Проверка заимствований         | Специальный перекрёстный проверщик                           | Потоко-чувствительный анализ активности в проверщике типов |
| Аннотации времён жизни         | Не требуются                                                 | Не требуются                                               |
| Накладные расходы в рантайме   | Нулевые                                                      | Нулевые (типы нулевого размера, исчезают после компиляции) |
| Сообщение об ошибке            | «Заимствование не может выйти»                               | «WriteToken(#3) уже перемещён» (обычная ошибка типа)       |
| Ментальная модель пользователя | Особый статус «заимствования»                                | `&T` дублируемый, `&mut T` недублируемый                   |

### 3. Ключевое слово `ref` (автоматическая оптимизация компилятора)

`ref` — единственный способ совместного владения через границы областей видимости. В основе лежит Rc
или Arc, о выборе пользователю заботиться не нужно.

#### 3.1 Базовое использование

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # Совместное владение, компилятор автоматически выбирает реализацию

# Совместное владение между задачами
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # Компилятор: пересечение задач → Arc
    spawn { use(data) }           # Компилятор: пересечение задач → Arc
}

# Совместное владение в пределах задачи
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # Компилятор: без пересечения задач → Rc
}
```

**Ментальная модель пользователя**: `ref` = совместное удержание. Достаточно.

#### 3.2 Анализ побега компилятора: Rc против Arc

```
Анализ потоков данных ref:

Не выходит за пределы других задач → Rc (неатомарный подсчёт ссылок, низкие накладные расходы)
Выходит за пределы других задач   → Arc (атомарный подсчёт ссылок, потокобезопасный)
```

#### 3.3 Стратегия обнаружения циклов

```
Циклы внутри задачи → допускаются молча.
  ├── Каждая задача имеет чёткую границу времени жизни — по завершении задачи все ресурсы (включая циклы ref) освобождаются единообразно.
  ├── Долгоживущие сервисы должны создавать подзадачи по запросу/соединению — подзадачи освобождаются автоматически, накопления утечек не происходит.
  ├── ref всегда поддерживает жизнь, семантика без примесей.
  └── Пользователь имеет право строить двусторонние сильные ссылки внутри задачи (например, промежуточные состояния графовых вычислений).

Межзадачные циклы → lint (по умолчанию warn, настраивается).
  ├── Поведение программы корректно, реальной утечки нет (по завершении родительской задачи все ресурсы подзадач освобождаются).
  ├── Но межзадачные сильные ссылки размывают границы владения, что заслуживает пересмотра.
  ├── По умолчанию уровень warn — компиляция проходит, но с предупреждением.
  └── Команда может установить deny в конфигурации проекта как часть CI-качества.
```

**Уровни lint** (аналогично Rust clippy):

| Уровень               | Поведение                                | Сценарий                             |
| --------------------- | ---------------------------------------- | ------------------------------------ |
| `allow`               | Без проверки                             | Личный проект                        |
| `warn` (по умолчанию) | Компиляция проходит, с предупреждением   | Этап разработки                      |
| `deny`                | Ошибка компиляции                        | Ворота качества CI команды           |
| `forbid`              | Ошибка компиляции, нельзя переопределить | Организационные обязательные правила |

```yaoxiang
# Цикл внутри задачи: допускается молча, двусторонние сильные ссылки
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # Цикл. По завершении задачи освобождается единообразно.
}

# Межзадачный цикл: lint (по умолчанию warn)
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: межзадачная циклическая ссылка
    }
}
```

**Пример конфигурации проекта**:

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # Межзадачные циклы отклоняются прямо на CI
```

| Тип цикла              | Поведение                | Причина                                                             |
| ---------------------- | ------------------------ | ------------------------------------------------------------------- |
| Цикл ref внутри задачи | Без проверки             | Право пользователя, единообразное освобождение по завершении задачи |
| Межзадачный цикл ref   | lint (по умолчанию warn) | Предупреждение для пересмотра, можно настроить deny                 |

#### 3.4 Weak: предоставляется стандартной библиотекой

```yaoxiang
use std.weak

# Продвинутый пользователь делает явный выбор
a.next = ref b
b.prev = std.weak.new(a.next)   # Пользователь явно контролирует, какое направление слабое
```

**`Weak` — не встроен в язык, это тип стандартной библиотеки.** Для повседневного использования
достаточно `ref`. Продвинутые пользователи, которым нужен тонкий контроль памяти, вводят `Weak`
вручную.

> является ключевым словом языка, а не модулем; путь модуля унифицирован как `std.weak`,

#### 3.5 Токены заимствования против `ref`

|                   | `&T` / `&mut T`                                                                             | `ref`                                            |
| ----------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Назначение        | Взглянуть / изменить на месте                                                               | Совместное удержание                             |
| Область           | С областью видимости значения токена                                                        | Через границы областей видимости                 |
| Стоимость         | Нулевая (типы нулевого размера)                                                             | Rc или Arc (компилятор выбирает)                 |
| Выход за пределы  | Возможен (токен распространяется с возвратом / структурой / замыканием)                     | Для этого и предназначен                         |
| Пересечение задач | Невозможно (токен — доказательство права на этапе компиляции, не передаётся между задачами) | Возможно (компилятор автоматически выбирает Arc) |
| Циклы             | Не задействовано                                                                            | Внутри задачи — молча, между задачами — lint     |

### 4. `clone()` — явное копирование

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # Глубокое копирование
# p и p2 независимы, не влияют друг на друга
```

**Когда использовать**: когда нужно сохранить исходное значение и при этом Move или совместное
владение не подходят.

### 5. `unsafe` + сырые указатели (системное программирование)

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # Сырой указатель
    (*ptr).x = 0.0                # Разыменование (безопасность гарантирует пользователь)
    ptr2 = ptr + 1                # Арифметика указателей
}
```

**Ограничения**:

- Можно использовать только в блоках `unsafe`
- Пользователь гарантирует отсутствие висячих указателей и использования после освобождения
- Предназначено для FFI, операций с памятью и другого системного программирования

```

   │                      │                  │ по необходимости)         │
```

## Комплексный пример

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T: неизменяемый токен
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T: изменяемый токен
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move: потребление с возвратом
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # Забрать, изменить, вернуть
    }

    # Возврат ссылки: токен распространяется с возвращаемым значением
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Лямбда с явными параметрами
double: (x: Int) -> Int = (x) => x * 2

# Комплексное использование
p = Point(1.0, 2.0)
p.print()                           # Токен &Point
p.shift(1.0, 1.0)                   # Токен &mut Point
p = p.scale(2.0)                    # Move → возврат
shared = ref p                      # Совместное владение через ref
spawn { use(shared) }

# Независимая копия через clone
backup = p.clone()

# Цикл внутри задачи: допускается молча
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # Цикл, единообразно освобождается по завершении задачи

# Системный уровень через unsafe
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## Ограничения системы типов

### Атрибут типа Dup

`Dup` (Duplicable) — атрибут типа, автоматически управляемый компилятором, означающий
**поверхностное копирование**: при присваивании / передаче параметра копируется дескриптор/токен, а
нижележащие данные разделяются. Это образует трёхуровневый градиент с Move (передача владения) и
Clone (явное глубокое копирование, создание независимой копии).

**Dup и Clone — ортогональные концепции** — Dup копирует дескриптор с разделением данных, Clone
создаёт независимую копию. Тип может одновременно поддерживать и Dup, и Clone, либо только одно из
них.

| Тип           | Dup                                                                             | Clone | Пояснение                                         |
| ------------- | ------------------------------------------------------------------------------- | ----- | ------------------------------------------------- |
| `&T`          | ✅ (копирование токена, несколько представлений указывают на одни данные)       | ✅    | Неизменяемый токен                                |
| `ref T`       | ✅ (подсчёт ссылок +1, разделяет данные в куче)                                 | ✅    | Совместное удержание (компилятор выбирает Rc/Arc) |
| String, Bytes | ✅ (внутренний подсчёт ссылок, копирование дескриптора разделяет базовый буфер) | ✅    | Строки / байты                                    |
| `&mut T`      | ❌ (линейный, исключительный)                                                   | ❌    | Изменяемый токен                                  |
| `*T`          | ❌                                                                              | ❌    | Сырой указатель                                   |
| struct        | Производный (автоматически, когда все поля являются Dup)                        | ✅    | Структура                                         |

**Примитивные типы значений** (Int, Float, Bool, Char) при присваивании подчиняются встроенному в
компилятор копированию значений — два значения полностью независимы, это не поверхностное
копирование. Они не относятся к атрибуту Dup, а обрабатываются компилятором изначально.

| ----------------------------- | --------------- | -------------------------------------------------------------------------------------- |
| Move                          | Ноль            | Перемещение указателя                                                                  |
| `&T` / `&mut T`               | Ноль            | Типы нулевого размера, исчезают после компиляции, нулевые накладные расходы в рантайме |

| `unsafe + *T`                 | Ноль            | Прямые операции с памятью                                                              |

## Компромиссы

### Преимущества

1. **Единообразие**: `&T`/`&mut T` — обычные типы, а не специальные языковые конструкции. Полностью
   согласуется с `name: type = value` из RFC-010
2. **Простота**: нет времён жизни, проверка заимствований сводится к утверждениям системы типов.
   `&T` дублируемый, `&mut T` недублируемый — два атрибута типа
3. **Мощность**: можно возвращать ссылки, хранить в структурах, захватывать замыканиями —
   выразительность на уровне Rust
4. **Интеллект компилятора**: `ref` автоматически выбирает Rc/Arc, на стороне вызова автоматически
   выбирается заимствование
5. **Детерминированность**: `ref` — это поддержание жизни, без тихого превращения в слабую ссылку
6. **Высокая производительность**: Move без копий, токены без накладных расходов (типы нулевого
   размера, исчезают после компиляции)
7. **Гибкость**: `unsafe + *T` поддерживает системное программирование

### Недостатки

1. **Заражение параметрами бренда**: токены несут идентификатор бренда, в сигнатурах функций,
   возвращающих ссылки, проявляются дополнительные параметры-генерики
2. **Накладные расходы `ref` в рантайме**: атомарные операции имеют стоимость (но это неизбежная
   плата за совместное владение)
3. **Риски `unsafe`**: пользователь должен гарантировать корректность
4. **Межзадачные циклы — lint, а не ошибка компиляции**: в отличие от Rust, по умолчанию warn,
   требуется настройка команды до deny, чтобы быть воротами качества

## Альтернативы

| Альтернатива                  | Почему не выбрана                                                                                                     |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------- |

| Алгоритм анализа побега        | Реализация обнаружения пересечения задач для `ref` | К обсуждению                       |

### Обнаружение конфликтов токенов: логические утверждения Хоара

Полная схема обнаружения конфликтов токенов описана в
[RFC-009a: Анализ времени жизни токенов — на основе конвейера доказательств Хоара](../accepted/009a-borrow-proof-pipeline.md).
Основные моменты:

**Активность токенов — это логическое утверждение Хоара.**
`{Все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}` — разделяет
конвейер доказательства из RFC-027 с проверкой типов и проверкой пользовательских предикатов.
Компилятор автоматически генерирует утверждения о заимствованиях (`borrow_conflict`,
`use_after_move`, `use_after_drop`, `mut_violation`), конвейер возвращает Proved / Disproved /
Unproven.

**Проверка заимствований не исчезла — она понижена в размерности.** `BorrowChecker` становится
`BorrowPredicateEmitter`, генерирующим утверждения, а не выполняющим проверку. Это полностью
параллельно концепции «проверщика типов»: проверщик типов генерирует утверждения о равенстве типов,
генератор утверждений о заимствованиях генерирует утверждения о заимствованиях, один конвейер
верифицирует.

**Идентификатор бренда (`#42`) — это и есть `'a`.** Информация полностью идентична, кодирование
различается. `'a` виден в сигнатурах типов, `#42` находится внутри компилятора. Никакого нового
анализа не изобретено — время жизни перенесено с уровня типов на уровень доказательств.

**Схема алгоритма** (подробности в RFC-009a):

- Префиксное сопоставление дерева брендов → определение конфликтующих токенов (O(глубина), глубина
  ≤ 3)
- Обратный BFS → от потребителя, break для разрыва обратных рёбер, структурный анализ покрывает 95%+
  сценариев (быстрый путь)
- Логическое отсечение SMT → вызывается только при `while` + путевых условиях (медленный путь,
  крайне редко)
