# RFC-009: Проектирование модели владения

## Аннотация

В данном документе определяется **модель владения (Ownership Model)** языка программирования YaoXiang.

**Основной дизайн — пять концепций, один градиент**:

```
Взглянуть/Изменить на месте   Забрать          Общее владение         Скопировать          Системный уровень
      │                          │                  │                     │                    │
     &T                        Move              ref                  clone()             unsafe
    &mut T                     Нулевое          Компилятор             Явное               *T
    Токен                      копирование       автоматически         глубокое            Пользователь
    нулевого                   По умолчанию      выбирает              копирование          отвечает
    размера                    RAII              Rc/Arc                                    за безопасность
    Тип свойства
    естественно
    выводит права
```

- **Move (по умолчанию)**: присваивание/передача параметров/возврат = передача владения, нулевое копирование, автоматическое освобождение RAII
- **`&T` / `&mut T` (токены заимствования)**: компиляторные токены нулевого размера. `&T` копируемый (общее чтение), `&mut T` линейный (исключительная мутация). Права естественно выводятся из атрибутов типа, без специальных правил. Можно возвращать, можно хранить в структурах.
- **`ref` ключевое слово**: совместное использование за пределами области видимости. Компилятор автоматически выбирает Rc (не межзадачно) или Arc (межзадачно)
- **`clone()`**: явное глубокое копирование
- **`unsafe` + `*T`**: голые указатели, системный аварийный выход

**Устранённая сложность**:

- ❌ Нет времени жизни `'a`
- ❌ Нет отдельной системы проверки заимствований (конфликт заимствований сводится к холловским предложениям, общая система доказательств с проверкой типов)
- ❌ Нет GC
- ❌ Нет специальных правил вроде "запрет на побег" (токены — обычные типы, области видимости обрабатываются единой системой типов)
- ❌ Пользователю не нужно знать разницу между Rc и Arc (компилятор выбирает автоматически)

> **Нагрузка на программиста**: `&T` копируемый, `&mut T` не копируемый — два атрибута типа, ноль специальных правил, полная автоматизация компилятора.
> **Гарантия производительности**: Move с нулевыми накладными расходами, токены с нулевыми накладными расходами (типы нулевого размера, исчезают после компиляции), ref по требованию, без пауз GC.

## Мотивация

### Зачем нужна модель владения?

| Язык         | Управление памятью          | Проблемы                                         |
| ------------ | --------------------------- | ------------------------------------------------ |
| C/C++        | Ручное управление           | Утечки памяти, висячие указатели, двойное освобождение |
| Java/Python  | GC                          | Задержки, накладные расходы памяти, непредсказуемые паузы |
| Rust         | Владение + проверка заимствований | Кривая изучения времени жизни `'a` крутая       |
| **YaoXiang** | **Move + Token + ref**      | **Просто, детерминировано, без GC**             |

### Цели проектирования

```yaoxiang
# 1. Move по умолчанию (нулевое копирование)
p = Point(1.0, 2.0)
p2 = p                         # Move, p больше не читается

# 2. &T / &mut T токены заимствования (нулевые накладные расходы, атрибуты типа естественно выводят права)
print_info(p2)                 # Компилятор автоматически создаёт токен &Point, освобождается после использования
shift(p2, 1.0, 1.0)            # Компилятор автоматически создаёт токен &mut Point

# 3. ref = совместное использование (компилятор автоматически выбирает Rc/Arc)
shared = ref p2                 # Владение за пределами области видимости
spawn { use(shared) }          # Компилятор: межзадачно → Arc

# 4. clone() = явное копирование
backup = p2.clone()            # Глубокое копирование, независимая копия

# 5. unsafe + *T = 系统级
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

### Ключевые отличия от Rust

| Характеристика | Rust                                   | YaoXiang                                                   |
| -------------- | -------------------------------------- | --------------------------------------------------------- |
| Семантика по умолчанию | Заимствование `&T` (нужен явный `.clone()`) | **Move (передача значения, нулевое копирование)**         |
| Заимствование  | `&T`/`&mut T`, можно возвращать, нужны lifetimes | **`&T`/`&mut T` токены нулевого размера, атрибуты Dup/Linear естественно выводят** |
| Механизм совместного использования | `Arc::new()` + ручной Weak | **`ref` ключевое слово (компилятор автоматически выбирает Rc/Arc)** |
| Копирование    | `clone()`                              | `clone()`                                                 |
| Голые указатели | `*T`                                   | `*T`                                                      |
| Время жизни    | `'a`                                   | ❌ Нет                                                    |
| Проверка заимствований | Глобальный вывод                | **Генерация холловских предложений проверщиком типов, унифицированная верификация** |
| Циклические ссылки | Ручной Weak                           | **Освобождение при завершении задачи / lint межзадачных / стандартный Weak** |

## Предложение

### 1. Move (передача владения по умолчанию)

```yaoxiang
# Правило: присваивание / передача параметров / возврат = Move, нулевое копирование

p: Point = Point(1.0, 2.0)
p2 = p                           # Move, p больше не читается

# Переменные можно переприсваивать (стиль Python, без затенения)
p = Point(3.0, 4.0)              # Перепривязка p, тип должен совпадать

# Параметры функции: Move
process: (p: Point) -> Point = {
    p.transform()
    p                            # Move при возврате
}

# 函数返回：Move
create: () -> Point = {
    p = Point(1.0, 2.0)
    p                            # Move при возврате, нулевое копирование
}
```

**Характеристики**:

- Нулевое копирование (компилятор перемещает указатели)
- После Move связывание недоступно для чтения (ошибка компиляции)
- RAII: автоматическое освобождение при выходе из области видимости
- Сигнатура функции `(T) -> T` сама по себе документация — потребляет T, возвращает T

### 2. &T / &mut T (токены заимствования)

**Основной принцип: `&T` и `&mut T` — это компиляторные токены нулевого размера. Это не "ссылки", а "типизированные доказательства прав доступа".**

#### 2.1 Два свойства типа

```
&T      →  Нулевой размер, замораживает данные (ReadToken запрещает WriteToken на время жизни),
          благодаря заморозке несколько只读视图 безопасны → Копируемый (Dup)
&mut T  →  Нулевой размер, исключительный доступ (WriteToken запрещает любые другие токены на время жизни),
          при исключительном доступе копирование бессмысленно → Линейный (не Dup)
```

**Причинно-следственная связь необратима: заморозка — причина, Dup — следствие.**
Не потому что `&T` реализует Dup, что его можно копировать — а потому что данные заморожены (нет возможности мутации), несколько只读视图 безопасны, и Dup реализуем. Если считать Dup определением, а проверку конфликтов "дополнительным патчем" — это ошибка в дизайне.

#### 2.2 Базовое использование

```yaoxiang
# На стороне метода: объявление типа параметра, определяющее требуемые права
Point.print: (self: &Point) -> Void = {
    print(self.x)                  # Токен &Point предоставляет право на чтение
    print(self.y)
}

Point.shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
    self.x = self.x + dx           # Токен &mut Point предоставляет право на запись
    self.y = self.y + dy
}

# На стороне вызова: компилятор автоматически выбирает заимствование или Move
p = Point(1.0, 2.0)
p.print()                          # Компилятор автоматически создаёт токен &Point
p.shift(1.0, 1.0)                  # Компилятор автоматически создаёт токен &mut Point
p.print()                          # OK, предыдущий токен освобождён после вызова shift

# 自由函数同理
distance: (a: &Point, b: &Point) -> Float = {
    sqrt((a.x - b.x)**2 + (a.y - b.y)**2)  # Два токена &Point сосуществуют — тип Dup
}
d = distance(p, p2)
```

#### 2.3 Почему не нужен "запрет на побег"

RFC-009 v8 применял три специальных правила к `&T`/`&mut T` — только параметры, нельзя возвращать, нельзя хранить в структурах. Это патч для концепции "заимствования".

Система токенов не нуждается в этих правилах. Токены — **обычные типы**, следующие тем же правилам области видимости, что и все остальные типы.

**Возврат ссылок — естественно поддерживается**:

```yaoxiang
# ✅ 令牌随返回值一起传播
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)  # Дочерний токен и родительский токен возвращаются вместе
}

# 使用
p = Point(1.0, 2.0)
(px_ref, p) = p.get_x()    # Токен возвращается вызывающему
print(px_ref)               # OK, токен всё ещё в области видимости
```

**Хранение в структурах — естественно поддерживается**:

```yaoxiang
# ✅ Структура переносит токен как поле
Window: Type = {
    target: Point,
    view: &Point,      # Поле токена — держит只读 представление target
}

# Токен view производен от target, Window владеет обоими
# Пока Window существует, токен view валиден
```

#### 2.3 Замыкания и Lambda с явными параметрами

Lambda — это значение-функция — может быть возвращена, сохранена, вынесена за пределы текущей области видимости. Поэтому Lambda **не неявно захватывает внешние локальные переменные**. Когда нужны внешние данные, они передаются как явные параметры:

```yaoxiang
# ✅ Lambda использует явные параметры
double: (x: Int) -> Int = (x) => x * 2
filter_by: (items: List(Int), f: (Int) -> Bool) -> List(Int) = { ... }

# ✅ spawn { } не подчиняется этому правилу — spawn это немедленно выполняемый параллельный блок, родительская задача блокируется в ожидании
shared = ref data
spawn { use(shared) }

# ❌ Lambda не может неявно захватывать внешние переменные
x = 42
f = () => { x + 1 }  # Ошибка компиляции: x не в области видимости

# ✅ 正确方式：显式传参
f = (x) => { x + 1 }
f(x)

# ✅ Правильный способ два: контекст фиксируется в точке создания (каррирование) — замыкание берёт только параметры, без захвата
gt: (t: Int) -> (x: Int) -> Bool = (x) => x > t
evens = list.filter(nums, gt(threshold))
```

> Дополнение (2026-08-17): Правильное решение для контекстной зависимости — это фиксация через каррирование, не захват. После побега замыкания его область видимости в точке определения может быть мертва, поэтому неявный захват запрещён; но область видимости в точке вызова (точке создания) всегда жива, фиксация контекста как значения в замыкании в этой точке безопасна. См. SPEC §12.3.

**spawn { } не является значением-функцией.** Блок, помеченный spawn, как и body if/while — выполняется немедленно, завершается пока жив родительский стековый кадр. Тело spawn может нормально обращаться к внешним переменным.

**Межзадачность — токены не проходят через потоки**:

```yaoxiang
# ❌ Токены не могут пересекать границы задач
bad_task: (p: &Point) -> Void = {
    spawn { print(p.x) }          # ❌ Ошибка компиляции: токен нельзя передавать между задачами
}

# Это не специальное правило — токен это компиляторное доказательство прав, для межзадачного совместного использования используйте ref
# Если нужно межзадачное совместное использование, используйте ref
```

**Токены нельзя оборачивать в ref**:

```yaoxiang
# ❌ Токен это доказательство прав, не владение
bad_ref: (p: &Point) -> Void = {
    shared = ref p                # ❌ Ошибка компиляции: &T не владеющий тип
}
```

#### 2.4 Жизненный цикл токенов

Жизненный цикл токенов определяется **обычными правилами области видимости**, без параметров времени жизни:

- Токены в параметрах функции: живут во время вызова, освобождаются после
- Возвращённые токены: владение передаётся вызывающему
- Токены, хранящиеся в структурах: живут вместе со структурой

Компилятору не нужны пометки `'a`, потому что токены — **значения**, жизненный цикл значений управляется системой владения (Move/RAII) унифицированно. **Сведение проблемы заимствований к проблеме владения.**

#### 2.5 Обнаружение конфликтов токенов

Обнаружение конфликтов токенов — это **холловские логические предложения**, не независимый потоково-чувствительный анализ.

```
{Все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}
```

Разделяет доказательную систему RFC-027 с проверкой типов и пользовательскими предикатами. Компилятор автоматически генерирует предложения о заимствовании (`borrow_conflict`, `use_after_move`, `use_after_drop`, `mut_violation`), отправляет в систему верификации. Система возвращает Proved / Disproved / Unproven.

```yaoxiang
# ❌ Токен &mut линейный, не копируемый
bad_dup: (p: &mut Point) -> Void = {
    p2: &mut Point = p              # Move, p больше не читается
    p.x = 10.0                      # ❌ Ошибка компиляции: WriteToken уже перемещён
}

# ✅ Токен &T типа Dup, можно свободно копировать
good_dup: (p: &Point) -> Void = {
    p2: &Point = p                  # OK, &T типа Dup
    print(p.x)                      # OK
    print(p2.x)                     # OK, два只读 токена сосуществуют
}
```

**Проверка заимствований не исчезла — она свелась.** Существующий `BorrowChecker` становится `BorrowPredicateEmitter` (генератор предложений), генерируемые предложения о заимствовании и другие типы предложений разделяют одну доказательную систему. Это полностью параллельно концепции проверщика типов: проверщик типов генерирует предложения о равенстве типов, генератор предложений о заимствовании генерирует предложения о заимствовании, одна система верифицирует. Подробный дизайн см. [RFC-009a](../accepted/009a-borrow-proof-pipeline.md).

#### 2.7 Внутренняя реализация компилятора: механизм брендов

Пользователь никогда не сталкивается с брендами. Компилятор внутренне назначает каждому токену компиляторно-уникальный идентификатор:

```
Видимое пользователю      Внутреннее представление компилятора
──────────────────────────────────────────────────────────────
&Point                  →  ReadToken(Point, #N)    // #N компиляторно-уникальное целое
&mut Point              →  WriteToken(Point, #M)   // #M компиляторно-уникальное целое
```

Назначение брендов:

- **Защита от подделки**: токен можно получить только от владеющего capsule, нельзя создать из воздуха
- **Отслеживание производности**: при получении `&Float` из `&Point` (доступ к полю), `&Float` несёт производный бренд (`#N.field_x`), компилятор может отследить до родительского токена
- **Обнаружение конфликтов**: одноисходный `WriteToken` и производный `ReadToken` не могут быть активны одновременно

Бренды полностью исчезают после мономорфизации и инлайнинга, в сгенерированном машинном коде их нет. **Нулевые накладные расходы во время выполнения.**

#### 2.8 Правила автоматического выбора заимствования

Компилятор на стороне вызова автоматически выбирает по следующему приоритету:

```
1. Если фактический аргумент ещё будет использоваться далее → Приоритет создания токена (&T или &mut T, согласно сигнатуре метода)
2. Если фактический аргумент далее не используется → Move
3. Приоритет匹配: &T < &mut T < Move
```

```yaoxiang
# 示例：自动选择
p = Point(1.0, 2.0)
p.print()        # print 声明 &self → 编译器创建 &Point 令牌
p.shift(1.0, 1.0) # shift 声明 &mut self → 编译器创建 &mut Point 令牌
p2 = p           # Move，p 不再使用
```

#### 2.9 Сравнение с упрощённым заимствованием в RFC-009 v8

| Характеристика          | Упрощённое заимствование (v8)              | Токены заимствования (v9)                       |
| ----------------------- | ------------------------------------------- | ----------------------------------------------- |
| Возврат ссылок          | ❌ Жёсткий запрет                          | ✅ Токен распространяется с возвращаемым значением |
| Хранение в структурах   | ❌ Жёсткий запрет                          | ✅ Токен как поле структуры                     |
| Lambda с явными параметрами | ❌ Жёсткий запрет                          | ✅ Lambda использует явные параметры            |
| Специальные правила      | 3 (только параметр/нельзя возвращать/нельзя хранить) | 0 — атрибуты типа естественно выводят         |
| Проверка заимствований  | Специальная кросс-проверка заимствований   | Потоково-чувствительный анализ живности проверщика типов |
| Аннотации времени жизни | Не нужны                                   | Не нужны                                        |
| Накладные расходы выполнения | Ноль                                   | Ноль (типы нулевого размера, исчезают после компиляции) |
| Сообщения об ошибках    | "Заимствование не может покинуть область"  | "WriteToken(#3) уже перемещён" (обычная ошибка типа) |
| Ментальная модель пользователя | Понимание "особого статуса заимствования" | `&T` копируемый, `&mut T` не копируемый        |

### 3. Ключевое слово ref (автооптимизация компилятора)

`ref` — единственный способ совместного использования за пределами области видимости. Внутри Rc или Arc — пользователю не нужно об этом думать.

#### 3.1 Базовое использование

```yaoxiang
p: Point = Point(1.0, 2.0)
shared = ref p                   # Совместное использование, компилятор автоматически выбирает реализацию

# Межзадачное совместное использование
@block
main: () -> Void = {
    data = ref heavy_data
    spawn { use(data) }           # Компилятор: межзадачно → Arc
    spawn { use(data) }          # Компилятор: межзадачно → Arc
}

# Совместное использование в рамках одной задачи
@block
main: () -> Void = {
    data = ref heavy_data
    use(data)                     # Компилятор: не межзадачно → Rc
}
```

**Ментальная модель пользователя**: `ref` = совместное владение. Достаточно.

#### 3.2 Анализ побега компилятора: Rc vs Arc

```
Анализ потока данных ref:

Не побегает в другие задачи → Rc (неатомарный подсчёт ссылок, низкие накладные)
Побегает в другие задачи   → Arc (атомарный подсчёт ссылок, потокобезопасно)
```

#### 3.3 Стратегия обнаружения циклов

```
Цикл внутри задачи → Молча允许.
  ├── У каждой задачи чёткие границы жизненного цикла — при завершении задачи все ресурсы (включая ref-циклы) освобождаются унифицированно.
  ├── Долгоработающие сервисы должны создавать подзадачи по запросу/соединению — подзадача завершается, ресурсы автоматически回收, не накапливаются.
  ├── ref всегда жив, семантика чистая.
  └── Пользователь имеет право создавать двунаправленные сильные ссылки внутри задачи (например, промежуточные состояния графовых вычислений).

Межзадачный цикл → lint (по умолчанию warn, конфигурируемо).
  ├── Программа работает корректно, настоящих утечек не будет (при завершении родительской задачи ресурсы подзадач освобождаются).
  ├── Но межзадачные сильные ссылки означают размытые границы владения, стоит остановиться и переосмыслить.
  ├── По умолчанию warn, компиляция проходит с подсказкой.
  └── Команда может установить deny в конфигурации проекта, включить в CI quality gate.
```

**Уровни lint** (аналогично Rust clippy):

| Уровень            | Поведение              | Сценарий                |
| ------------------ | ---------------------- | ----------------------- |
| `allow`            | Не проверять          | Личные проекты          |
| `warn` (по умолч.) | Компиляция проходит, предупреждение | Этап разработки  |
| `deny`             | Компиляция не проходит | Командный CI quality gate |
| `forbid`           | Компиляция не проходит, нельзя переопределить | Организационное обязательное правило |

```yaoxiang
# Цикл внутри задачи: молча允许, двунаправленные сильные ссылки
build_graph: () -> Void = {
    a = Node("a")
    b = Node("b")
    a.next = ref b
    b.prev = ref a                # Цикл. При завершении задачи освобождается унифицированно.
}

# Межзадачный цикл: lint (по умолчанию warn)
@block
parent_task: () -> Void = {
    shared_a = ref a
    shared_b = ref b
    spawn {
        shared_a.child = ref shared_b   # ⚠️ warn: межзадачный циклический reference
    }
}
```

**Пример конфигурации проекта**:

```toml
# yaoxiang.toml
[lints]
cross-task-cycle = "deny"    # Межзадачные циклы отклоняются в CI напрямую
```

| Тип цикла              | Поведение                  | Причина                          |
| ---------------------- | -------------------------- | --------------------------------- |
| Внутризадачный ref-цикл | Не проверять               | Право пользователя, освобождение при завершении задачи |
| Межзадачный ref-цикл    | lint (по умолчанию warn)   | Напоминание для переосмысления, можно настроить deny |

#### 3.4 Weak: предоставляется стандартной библиотекой

```yaoxiang
use std.weak

# Продвинутые пользователи делают явный выбор
a.next = ref b
b.prev = std.weak.new(a.next)   # Пользователь явно контролирует, какое направление слабое
```

**`Weak` не встроен в язык, это тип стандартной библиотеки.** Повседневного использования `ref` достаточно. Продвинутые пользователи, желающие тонко контролировать память, вручную используют `Weak`.

#### 3.5 Токены заимствования против `ref`

|            | `&T` / `&mut T`                               | `ref`                              |
| ---------- | --------------------------------------------- | ---------------------------------- |
| Что делает | Взглянуть / изменить на месте                 | Совместное владение               |
| Область    | Область видимости значения токена            | За пределами области видимости     |
| Стоимость  | Ноль накладных (типы нулевого размера)       | Rc или Arc (выбирает компилятор)   |
| Побег      | Возможен (токен распространяется с возвратом/структурой/замыканием) | Изначально для побега и создан    |
| Межзадачно | Невозможно (токен — компиляторное доказательство прав, нельзя передавать между задачами) | Возможно (компилятор автоматически выбирает Arc) |
| Циклы      | Не применимо                                  | Внутри задачи允许, межзадачно lint |

### 4. clone() —— Явное копирование

```yaoxiang
p: Point = Point(1.0, 2.0)
p2 = p.clone()                   # Глубокое копирование
# p и p2 независимы, не влияют друг на друга
```

**Когда использовать**: когда нужно сохранить оригинальное значение и не подходят Move или совместное использование.

### 5. unsafe + Голые указатели (системное программирование)

```yaoxiang
p: Point = Point(1.0, 2.0)

unsafe {
    ptr: *Point = &p              # Голый указатель
    (*ptr).x = 0.0                # Разыменование (пользователь гарантирует безопасность)
    ptr2 = ptr + 1                # Арифметика указателей
}
```

**Ограничения**:

- Только в блоках `unsafe`
- Пользователь гарантирует отсутствие висячих указателей и использования после освобождения
- Применяется для FFI, операций с памятью и другого системного программирования

## Комплексный пример

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,

    # &T:只读 токен
    print: (self: &Point) -> Void = {
        print(self.x)
        print(self.y)
    }

    # &mut T: изменяемый токен
    shift: (self: &mut Point, dx: Float, dy: Float) -> Void = {
        self.x = self.x + dx
        self.y = self.y + dy
    }

    # Move → Move：消费回流
    scale: (self: Point, f: Float) -> Point = {
        self.x = self.x * f
        self.y = self.y * f
        self                            # Забрать, изменить, вернуть
    }

    # 返回引用：令牌随返回值传播
    get_x: (self: &Point) -> (&Float, &Point) = {
        return (&self.x, self)
    }
}

# Lambda с явными параметрами
double: (x: Int) -> Int = (x) => x * 2

# 综合使用
p = Point(1.0, 2.0)
p.print()                           # Токен &Point
p.shift(1.0, 1.0)                   # Токен &mut Point
p = p.scale(2.0)                    # Move → возврат
shared = ref p                      # ref совместное владение
spawn { use(shared) }

# clone независимая копия
backup = p.clone()

# Цикл внутри задачи: молча允许
a = Node("a")
b = Node("b")
a.next = ref b
b.prev = ref a                      # Цикл, при завершении задачи освобождается унифицированно

# unsafe системный уровень
unsafe {
    ptr: *Point = &p
    (*ptr).x = 0.0
}
```

## Ограничения системы типов

### Свойство типа Dup

`Dup` (Duplicable) — это атрибут типа, автоматически управляемый компилятором, означает **поверхностное копирование**: при присваивании/передаче параметров копируются дескрипторы/токены, базовые данные общие. Это образует трёхуровневый градиент с Move (передача владения) и Clone (явное глубокое копирование, создание независимых копий).

**Dup и Clone — ортогональные концепции** — Dup копирует дескрипторы с общим доступом к данным, Clone создаёт независимые копии. Тип может одновременно поддерживать Dup и Clone, или только один из них.

| Тип            | Dup                                              | Clone | Описание                                    |
| -------------- | ------------------------------------------------ | ----- | ------------------------------------------- |
| `&T`           | ✅ (копирование токена, несколько представлений указывают на одни данные) | ✅ |只读 токен                                |
| `ref T`        | ✅ (счётчик ссылок +1, общие кучевые данные)    | ✅ | Совместное владение (компилятор автоматически выбирает Rc/Arc) |
| String, Bytes  | ✅ (внутренний счётчик ссылок, копирование дескриптора с общим буфером) | ✅ | Строки/байты                              |
| `&mut T`       | ❌ (линейный, исключительный)                    | ❌ | Изменяемый токен                          |
| `*T`           | ❌                                               | ❌ | Голый указатель                           |
| struct         | Наследуется (автоматически наследуется, когда все поля Dup) | ✅ | Структура                                 |

**Примитивные типы значений** (Int, Float, Bool, Char) при присваивании ведут себя как встроенное копирование значений компилятором — два полностью независимых значения. Они не являются атрибутом типа Dup, а являются нативной обработкой компилятора.

| ------------------- | --------- | ---------------------------------------- |

| `unsafe + *T`       | Ноль      | Прямые операции с памятью                 |

## Компромиссы

### Достоинства

1. **Единообразие**: `&T`/`&mut T` — обычные типы, не специальная языковая конструкция. Полностью согласовано с `name: type = value` из RFC-010
2. **Простота**: без времени жизни, проверка заимствований сводится к предложениям системы типов. `&T` копируемый, `&mut T` не копируемый — два атрибута типа
3. **Мощность**: можно возвращать ссылки, хранить в структурах, захватывать в замыканиях — выразительность на уровне Rust
4. **Интеллектуальность компилятора**: ref автоматически выбирает Rc/Arc, сторона вызова автоматически выбирает заимствование
5. **Детерминированность**: ref это гарантированное сохранение жизни, не станет тихо слабой ссылкой
6. **Высокая производительность**: Move с нулевым копированием, токены с нулевыми накладными (типы нулевого размера, исчезают после компиляции)
7. **Гибкость**: `unsafe + *T` поддерживает системное программирование

### Недостатки

1. **Заражение универсальными параметрами брендов**: токены несут идентификаторы брендов, сигнатуры функций, возвращающих ссылки, будут содержать дополнительные универсальные параметры
2. **Накладные расходы ref во время выполнения**: атомарные операции имеют стоимость (но это неизбежная плата за совместное использование)
3. **Риски unsafe**: пользователь должен гарантировать корректность
4. **Межзадачные циклы — lint, не ошибка компиляции**: в отличие от Rust с ошибкой компиляции, по умолчанию warn, нужна командная настройка deny для quality gate

## Альтернативные решения

| Решение              | Почему не выбрано                                 |
| ------------------- | ------------------------------------------------- |

### Обнаружение конфликтов токенов: холловские логические предложения

Полное решение обнаружения конфликтов токенов см. в [RFC-009a: Анализ жизненного цикла токенов — на основе холловской доказательной системы](../accepted/009a-borrow-proof-pipeline.md). Ключевые моменты:

**Жизненность токена — это холловское логическое предложение.**
`{Все конфликтующие ReadToken мертвы} write(data) {WriteToken безопасно получен}` — разделяет доказательную систему RFC-027 с проверкой типов и пользовательскими предикатами. Компилятор автоматически генерирует предложения о заимствовании (`borrow_conflict`, `use_after_move`, `use_after_drop`, `mut_violation`), система возвращает Proved / Disproved / Unproven.

**Проверка заимствований не исчезла — она свелась.** `BorrowChecker` становится `BorrowPredicateEmitter`, генерирует предложения вместо выполнения проверок. Это полностью параллельно концепции "проверщика типов": проверщик типов генерирует предложения о равенстве типов, генератор предложений о заимствовании генерирует предложения о заимствовании, одна система верифицирует.

**Бренд ID (`#42`) и есть `'a`.** Информация полностью идентична, различается кодировка. `'a` виден в сигнатуре типа, `#42` внутри компилятора. Никакого нового анализа не изобретено — время жизни опущено с уровня типов на уровень доказательств.

**Краткое описание алгоритма** (подробности в RFC-009a):

- Префиксное сопоставление дерева брендов → определение конфликтующих токенов (O(depth), глубина ≤ 3)
- Обратный BFS → от потребителя, разрыв обратных рёбер, структурный анализ покрывает 95%+ сценариев (быстрый путь)
- Отсечение SMT-логикой → только при while + условиях пути (медленный путь, крайне редко)
