# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Для YaoXiang вводятся стандартный фреймворк тестирования — модуль `std.test` — и подкоманда CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`; общий результат
прохождения/провала определяется по коду выхода (exit code) дочернего процесса; внутри файла
поддерживается несколько тестовых функций — неудачи утверждений выражаются значением `Err`
(семантика значений), а набор (suite) собирает per-test оценки (§7). Модуль `std.test` реализован на
чистом YaoXiang и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не
функция компилятора — никаких изменений в парсере, IR, байт-коде или исполнителе.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время покрытие тестами YaoXiang зависит от `#[test]` на стороне Rust и интеграционных
тестов в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. Задача `#117 Модульное покрытие тестами модулей стандартной библиотеки` заблокирована из-за
   отсутствия доступной тестовой инфраструктуры
3. Регрессионное тестирование языковых возможностей (например, изменение семантики spawn в RFC-032)
   лишено средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения в компиляторе**: не трогать парсер, IR, байт-код, исполнитель
- **Приоритет самохостинга (self-hosting)**: тестовая библиотека пишется на YaoXiang — это первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI 层:  yaoxiang test [--filter --fail-fast --json ...]    │
│              │                                               │
│  发现层:    读取 yaoxiang.toml → [tool.test] patterns         │
│              默认: tests/**/*.yx                              │
│              │                                               │
│  执行层:    对每个文件: yaoxiang run <file>                    │
│              检查 exit code → 串行执行                        │
│              │                                               │
│  报告层:    PASS/FAIL → 汇总                                  │
│              支持 --json / --verbose / --fail-fast            │
│                                                              │
│  断言层:    std.test (纯 YaoXiang，自举)                      │
│              底层: std.assert.assert                          │
│              诊断: f"Expected {expected}, got {actual}"       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — это не функция компилятора, а инструмент CLI** — `yaoxiang run` уже
   способен «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения в компиляторе** — без сканирования аннотаций `@test`, без секций метаданных в
   байт-коде, без специальных точек входа в исполнителе
3. **Самохостинг** — модуль `std.test` реализован на чистом YaoXiang; базовые возможности берутся из
   `std.assert` / `std.result`
4. **Тестовые файлы — обычные файлы `.yx`** — файл выполняется как дочерний процесс, общий результат
   прохождения/провала определяется по коду выхода
5. **Неудача утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, неудача утверждения выражается через `Err`, набор собирает per-test оценки (§7);
   процессный abort относится только к runtime-guard'ам и не используется для тестовых утверждений

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      指定测试文件或目录（默认: 从 yaoxiang.toml 读取，否则 tests/）

Options:
  --filter <NAME>     只跑文件名包含 <NAME> 的测试
  --fail-fast         遇到第一个失败就停止
  --verbose, -v       显示每个测试的详细 stdout/stderr
  --list              只列出测试文件，不跑
  --no-progress       不显示进度输出（表头与 PASS 行）；FAIL 明细与汇总保留（CI 场景）
  --json              输出 JSON 格式结果（CI 集成用）
```

#### Формат вывода

**Вывод по умолчанию** (per-test оценки поступают от внутрифайлового набора, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**Вывод JSON** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы с ошибками дополнительно несут `exit_code` и `stderr` (диагностика дочернего процесса с
  удалёнными ANSI-кодами — для сбора улик в CI); при комбинации `--verbose` и `--json` все файлы
  несут `stdout` / `stderr`
- `--no-progress` лишь подавляет вывод прогресса (заголовок и строки PASS) — детали FAIL и итоговая
  сводка выводятся всегда; провалы не могут быть скрыты; `--list` выводит по одной строке с путём к
  тестовому файлу без выполнения
- Каждый файл сопровождается `kind` (behavior / compile-error / runtime-error / invalid, §8.2); к
  summary прилагается `by_kind` — счётчик выполнений (фиксированные четыре ключа, без skipped); к
  человеческой сводке прилагается строка распределения по категориям `Categories:`
- Внутрифайловый массив per-test `tests` поступает из сбора набора в §7 и вступает в силу с
  внедрением модели значений (#319)

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]`, что соответствует конвенции сторонних расширений `[tool.*]` из
RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# 未来可扩展:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочую конфигурацию из
  коробки без настроек
- В режиме одного файла (`yaoxiang test foo.yx`) файл запускается напрямую, конфигурация не читается
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` не изменится)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — 纯 YaoXiang 测试断言库（值语义标准形态，2026-09-03 落地）
// 第一个 dogfooding 库：YaoXiang 的测试库用 YaoXiang 写。

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not 与 assert_false 同体；assert_err / assert_err_code 见 §8.1
```

- Функции утверждений имеют **семантику значений**: возвращают `Result(Void, String)`, неудача
  выражается как `Err(диагностика)`, без аварийного завершения процесса — набор в §7 собирает на
  этом основании per-test оценки. Процессная семантика abort у `std.assert.assert` сохраняется за
  runtime-guard'ами и не входит в путь тестовых утверждений. Полезной нагрузкой Ok является `Void`
  (согласно type-system.md, это unit; `()` — пустой Tuple, и они не смешиваются — закреплено
  2026-09-03)
- **Семейство из 7 функций (поставлено 2026-09-03, переходная abort-версия удалена)**: value-версии
  `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (синоним assert_false,
  зарезервировано для `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (§8.1 — утверждение кода ошибки)
- `assert_eq` / `assert_ne` используют **параметры с аннотацией Any** — `==`/`!=` и интерполяция
  f-string работают на Any, без зависимости от системы дженериков. Заметьте: параметры **должны быть
  аннотированы явно** — параметры без аннотаций не проходят проверку вызовов для нативного дженерика
  `&Result(T, E)` (подтверждено пробником R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный синтаксис `not`
  ещё не реализован, после стабилизации возможна миграция; унарная форма `!assert` имеет ту же
  зависимость, см. §8.1)
- Форма с блочным телом и явным `return`: тип then-ветви if-выражения отбрасывается при проверке,
  if-выражение с двумя Result-ветвями — слепая зона проверки, реализация обходит это
- `std.test` не зависит ни от какого нативного кода; реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (а в будущем — все модули стандартной библиотеки, написанные на YaoXiang) встраиваются
в бинарник во время сборки:

```rust
// build.rs 或构建脚本，自动生成
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // 源代码文本
    // 未来更多
];
```

Модульная система (RFC-029, полностью реализована 2026-08-02) предоставляет точку интеграции:
Registry одновременно содержит нативные модули и модули-источники, а orchestrator отвечает за
оркестровку нескольких файлов. Порядок разрешения `use std.test`:

1. Сначала ищем нативный модуль Rust (существующий механизм, как `std.assert`)
2. Если не найден — ищем во встроенных `STD_YX_FILES`; при попадании — инъекция в orchestrator как
   модуля-затравки с **виртуальным путём** (например, `<std>/test.yx`), проходящего через обычный
   front-end конвейер (parse → typecheck → IR)
3. Если не найден — переходим к обнаружению через файловую систему (пользовательские модули)

`use std.assert` внутри встроенного модуля-источника нормально разрешается resolver'ом в нативный
registry — нативные и source-модули сосуществуют в Registry, и межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импорте.

Преимущества:

- `use std.test` работает и в режиме одного файла
- Версия стандартной библиотеки строго привязана к бинарнику, рассогласование версий исключено
- Пользователю не нужно настраивать путь к стандартной библиотеке

**Будущее: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлениях RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение ревью от 2026-08-02)**: CLI `run` подключается к orchestrator. В настоящее
время CLI `run` идёт по однокадровому конвейеру (`run_file_with_diagnostics`) и не способен
разрешать импорты пользовательских модулей; однако модель дочерних процессов `yaoxiang test`
наследует возможности CLI, и импорт проектных модулей тестовыми файлами — ключевой сценарий. Поэтому
в Фазе 1 сначала делегируем ветвь исходного кода `Run` в CLI команде `run_project` (orchestrator,
рекурсивное обнаружение по каталогу); #247 (обнаружение по `use` по требованию) после этого
наслаивается как чистая оптимизация производительности. Поведение однокадрового сценария без
импортов через orchestrator эквивалентно, ветвь байт-кода не меняется.

**Фаза обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читаются `patterns` из `[tool.test]` в `yaoxiang.toml`
3. Если конфигурации нет — по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению в имя файла)
5. Область обнаружения — это и есть тестовая стратификация (§9): стандартные patterns покрывают
   только корпус языковой доступности; уровень библиотечных тестов (например, `src/std/tests/`)
   обнаруживается через явный путь или конфигурацию пакета, в стандартное сканирование не
   подмешивается

**Фаза выполнения**:

1. Для каждого файла — выполнение с разветвлением по заголовочным директивам (грамматика директив
   см. §8.2, парсится через `src/util/test_markers.rs`, общий с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run --debug-info <file>` (`--debug-info`
     добавляет к runtime-ошибкам информацию о позиции в исходнике — подтверждено 2026-08-02, stack
     trace выдаёт `file:line:col`); `// mode:` объявляет режим `--runtime` для дочернего процесса
   - Класс отказа на этапе компиляции: один шаг `yaoxiang check <file>`
   - Класс сбоя на этапе выполнения: два шага — `check` (обязан пройти) + `run` (обязан провалиться)
2. Файлы с `// skip: <причина>` пропускаются при выполнении и учитываются как skipped в отчёте
3. Сравнение оценки с ожидаемыми кодами — по матрице оценок §8.2; ошибка разбора директивы — без
   выполнения, сразу FAIL (отказ на этапе построения)
4. Перехват stdout/stderr для отчёта
5. На Фазе 1 — только последовательное выполнение, в будущем поддержка `--parallel`
6. При `--fail-fast` — немедленная остановка на первом FAIL

### 6. Изоляция тестов

Изоляция тестов естественным образом обеспечивается границами на уровне процессов:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственные Heap, Frame, NativeContext
- panic в одном тестовом файле не влияет на другие
- Никаких дополнительных механизмов отдельного контекста Heap не требуется

### 7. Наборы и множественные тесты (модель на основе значений)

Один тестовый файл может содержать несколько тестов. Организация внутри файла (реализовано
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — это функция без аргументов, возвращающая `Result(Void, String)`; неудача утверждения
  выражается через `Err` (семейство утверждений с семантикой значений §3), процесс не прерывается —
  последующие тесты продолжают выполняться
- `test.suite` вызывает по очереди и собирает: для не-Ok теста записывает имя и диагностику, Ok —
  молча; после прогона всех, при наличии любого Err — аварийное завершение через `std.assert.assert`
  с приложенными деталями провалов (`N of M test(s) failed` + для каждого `[FAIL] имя: диагностика`)
  — код выхода файла не 0 (правило оценки §5 не меняется). Этот abort — runtime-guard тестового
  бинарника, а не путь утверждений; полный Ok — тихий выход с кодом 0
- Тестовые функции верхнего уровня включаются в список **в виде замыканий**
  (`("name", () => test_fn())`): ссылка на имя функции верхнего уровня как значение пока не
  поддерживается (ограничение уровня IR, `E3006`) — вызов глобальной функции из тела замыкания не
  затронут
- Runner видит только файл, не выполняет сканирования на уровне функций: per-test оценки полностью
  поступают из сбора внутри набора, внутренняя структура файла для runner прозрачна — принцип
  нулевых изменений в компиляторе не нарушается
- Явно не используется: границы catch внутри процесса (железное правило 17 ключевых слов);
  runner-вызовы по функциям как точкам входа (только во внутренних сценариях наподобие §8.2 «ошибка
  компиляции»)
- Форма API закреплена (2026-09-03, #319):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дубликаты имён не проверяются
  (имя служит только для отображения в отчёте); `--filter` фильтрует по имени файла и не различает
  имена тестов внутри набора

### 8. Трёхуровневая организация негативных тестов (ожидаемый провал)

Негативные тесты разнесены по слоям возникновения сбоя, у каждого слоя своё место:

#### 8.1 Реверс на уровне значений (универсальный, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый провал обычным утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// 或一句封装（码只存在于 std Error 载体上，E 钉死为 Error）：
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с value-семантикой (2026-09-03,
  §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса `not` (то же
  ограничение, что у `cond == false` в `assert_false`)
- Утверждение кода ошибки полагается на то, что значение `Error` несёт машиночитаемое поле `code` —
  реализовано в M4 задачи #323: `Error = { code, message }` (нативный `error_new(code, message)`);
  чтение — через `result.unwrap_err(r)` для извлечения носителя и аксессоров `result.code(e)` /
  `result.message(e)` (предполагавшиеся на этапе проектирования именование `error_new_with_code`,
  экспорт кодовых констант и доступ к полю `err.code` не были приняты — в языке нет доступа к полям
  Struct, а кодовые константы не экспортируются)
- По мере продвижения Result-изации (#301, #316) операции, которые могут провалиться, по одной
  начнут возвращать `Result`, а файловые негативные метки в корпусе будут переводиться во
  внутрифайловые утверждения

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это «всё или ничего» на уровне файла, и выразить «эта строка не должна компилироваться»
внутри файла невозможно; провалы во время выполнения тоже требуют файлового выражения (например,
набор содержит обязательно провальный тест). Ожидания объявляются в заголовке файла
**структурированными директивами**, runner выполняет **разветвление оценки** по категории ожидания
(разветвление закреплено 2026-09-03; грамматика директив закреплена и реализована 2026-09-06).

Грамматика заголовочных директив (`// key: value`, в пределах первых 16 строк, строгое
токен-соответствие):

```text
// expect: compile-error E1002 [E1003 ...]   编译期拒绝测试
// expect: runtime-error E6003 [...]         运行期失败测试
// skip: <原因>                              跳过执行，计入 skipped
// mode: embedded|standard|full              子进程 --runtime 模式（仅 run 步消费）
```

- Нет директивы `expect:` = поведенческий тест. `expect:` — это **единственный способ** объявления
  ожидания — 2026-09-06 закреплено, что булев маркер `[test:error]` и китайский «散文-код» `预期:`
  отбрасываются: булев маркер и строка ожидания — два слабо связанных факта, поддержание их
  согласованности дисциплиной неизбежно расходится; английская строгая токен-грамматика позволяет
  runner парсить механически (kind + коды — фиксированные токены, любой посторонний токен после кода
  — ошибка разбора), ошибка разбора = без выполнения, сразу FAIL — тихого канала деградации при
  ошибочно объявленной директиве не существует (отказ на этапе построения)
- **Класс ошибок компиляции**: один шаг `check` — обязан провалиться, и вывод должен содержать все
  `[EXXXX]`; успешная компиляция = FAIL (должны были сообщить, но не сообщили), отказ с
  несоответствующими кодами = FAIL. Синтаксические ошибки (участок парсера E1xxx) и семантические
  ошибки (E2xxx+) не выделяются в отдельные категории — фаза фиксируется самим ожидаемым кодом
- **Класс ошибок времени выполнения**: двухшаговая оценка — `check` обязан **успешно пройти**
  (компиляция чиста), `run` обязан провалиться, и вывод должен содержать все `[EXXXX]`. Если взрыв
  происходит уже на этапе компиляции = FAIL (ключевая проверка, направленная противоположно классу
  ошибок компиляции — защита от пропуска случая «компиляция случайно прошла, а на выполнении повезло
  провалиться»)
- Согласовано с индустрией: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`,
  Clang `expected-error` — все объявляют ожидания в комментариях фикстур и проводят двустороннее
  сравнение через harness; в них используется привязка к строкам, потому что мультидиагностические
  компиляторы должны различать несколько ожиданий в одном файле; наш компилятор останавливается на
  первой ошибке, в файле — одна диагностика, файловый уровень согласован с реальностью компилятора —
  после реализации восстановления ошибок грамматику можно дополнить формами с привязкой к строкам
  (заголовочные директивы файла + ожидания на уровне функций в Cranelift filetests — тот же
  смешанный формат)
- Известный долг рендеринга: парсерные диагностики сейчас выводятся в Debug-форме (`code: "E0012"`
  вместо `[E0012]`), сканер кодов принимает обе формы; после унификации рендеринга диагностик
  строгая форма будет возвращена
- **Служит только корпусу этого репозитория, не является частью пользовательского фреймворка
  тестирования**; соглашение об оценке для двух runner'ов закрыто (2026-09-03, #319): yx_runner
  (cargo test) и `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора
  заголовочных директив, каталоговое соглашение 06-compile-errors упразднено. Слой отчёта даёт
  подсчёт по категориям: к человеческой сводке прилагается строка `Categories:`, к JSON summary
  прилагается `by_kind` (behavior / compile-error / runtime-error / invalid, skipped учитывается
  отдельно), каждый файл сопровождается `kind`

#### 8.3 Жёсткие провалы во время выполнения (вписываются в Result-изацию)

Отдельный механизм не предусматривается — операции, которые могут провалиться, по направлению
развития языка возвращают `Result` (#301, #316), тесты единообразно выражаются по §8.1. Процессные
abort (например, нарушение утверждений, несоответствие параметров во время выполнения) по мере
Result-изации постепенно сворачиваются в значения, фреймворк тестирования не предоставляет для них
специальной семантики. (Замечание: «класс ошибок времени выполнения» из §8.2 — это файловый канал
верификации runner'а для **операций, которые пока нельзя Result-изировать**, и он не противоречит
семантическому направлению данного раздела — последний является конечной целью, первый — переходным
каналом)

### 9. Стратификация тестовой системы: языковой корпус и библиотечные тесты (закреплено 2026-09-03)

Тесты разделяются на два уровня по **объекту тестирования**, у каждого своя принадлежность и
сопровождающие; системы маркировки (§8.2) и библиотека утверждений (§3) являются общими для обоих
уровней:

**Первый уровень: корпус языковой доступности (`tests/yaoxiang/`)**

- Объектом тестирования является **сам язык** — парсер, система типов, модули, конкурентность,
  ownership, отказы на этапе компиляции, семантика времени выполнения; каталоги организованы по
  разделам языковой спецификации
- std в корпусе выступает только как **инструмент утверждений** (`std.assert` / `std.test`) и
  никогда не тестируется — поведение API библиотек не относится к языковой доступности
- Внутри корпуса по §8 происходит разветвление на три класса оценок: поведенческие тесты / тесты
  отказа на этапе компиляции / тесты сбоя на этапе выполнения

**Второй уровень: библиотечные тесты (идут вместе с библиотекой)**

- Объектом тестирования является **контракт публичного API библиотеки** (например, поведение
  `list.push`, семантика `result.code`)
- Тесты пишутся **в собственном пакете библиотеки**: пакет std — это `src/std/`, его yx-уровневые
  тесты относятся к `src/std/tests/` (рядом с реализацией); тесты самого `std.test` тоже находятся
  здесь (тестируем std.test через std.test — замыкание цикла самохостинга)
- Будущие пользовательские пакеты следуют той же конвенции: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (тестовая раскладка из управления пакетами RFC-014 репетируется таким
  образом)
- Обнаружение не входит в стандартные patterns (стандартные `tests/**/*.yx` покрывают только
  языковой уровень): уровень библиотечных тестов обнаруживается через явный путь
  (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI запускает их послойно

Замечание о миграции: библиотечные тесты, ныне находящиеся в `tests/yaoxiang/07-std/`, по этой
модели переезжают в `src/std/tests/`; при переезде каждый отбирается индивидуально — чисто
API-поведение переезжает, объекты тестирования, фактически являющиеся границами языка (например,
нативное автоматическое заимствование `&T`), остаются на уровне корпуса и относятся к
соответствующим разделам спецификации.

### Фаза 1: основная функциональность

- [x] Корректно ли разрешаются ссылки `use std.assert` в `std/test.yx`? — **Решено (2026-08-02)**.
      После реализации модульной системы (RFC-029) нативные и source-модули сосуществуют в Registry,

- [x] Вносит ли дженерик-`to_string` для `f"..."` в выводе тестов новые ограничения типов? —
      **Решено (2026-08-02)**. Подтверждено, что на параметрах без аннотаций (Any) `==`/`!=` и
      интерполяция f-string работают (проверено на Int/String), новые ограничения не вводятся
- [x] Возможен ли дженерик-параметр `?`? — **Решено (2026-08-02)**: синтаксиса типа `?` в настоящее

      функции утверждений Фазы 1 используют параметры без аннотаций и не зависят от системы
      дженериков
