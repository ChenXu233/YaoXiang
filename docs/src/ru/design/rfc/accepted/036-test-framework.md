# RFC-036: Тестовый фреймворк std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного тестового фреймворка — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`; общий результат
прохождения/провала определяется по коду выхода (exit code) дочернего процесса; внутри файла
поддерживается несколько тестовых функций — сбои утверждений выражаются значением `Err` (знаковая
семантика), набор собирает пока тестовые суждения per-test (§7). Модуль `std.test` реализован на
чистом YaoXiang и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не
функция компилятора — никаких изменений в парсере, IR, байткоде или исполнителе не требуется.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` на стороне Rust и интеграционные
тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang
2. Покрытие модульными тестами стандартной библиотеки заблокировано из-за отсутствия доступной
   тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) лишены
   средств автоматизации

### Ключевые ограничения

- **17-ключевое железное правило**: никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения компилятора**: парсер, IR, байткод и исполнитель не затрагиваются
- **Приоритет самозагрузки**: тестовая библиотека написана на YaoXiang, первая dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:    yaoxiang test [--filter --fail-fast --json ...]│
│              │                                               │
│  Уровень обнаружения:  читает yaoxiang.toml → [tool.test] patterns│
│              по умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Уровень выполнения:   для каждого файла: yaoxiang run <file> │
│              проверка exit code → последовательное выполнение│
│              │                                               │
│  Уровень отчётов:  PASS/FAIL → сводка                        │
│              поддержка --json / --verbose / --fail-fast      │
│              │                                               │
│  Уровень утверждений:   std.test (чистый YaoXiang, самозагрузка)│
│              низкий уровень: std.assert.assert               │
│              диагностика: f"Expected {expected}, got {actual}"│
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — не функция компилятора, а инструмент CLI** — `yaoxiang run` уже способен
   «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводится сканирование аннотаций `@test`, секций метаданных
   в байткоде, специальных точек входа в исполнителе
3. **Самозагрузка** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности опираются
   на `std.assert` / `std.result`
4. **Тестовые файлы — обычные файлы `.yx`** — файл запускается как дочерний процесс, exit code
   определяет общий результат прохождения/провала
5. **Сбой утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, сбой утверждения выражается через `Err`, набор собирает суждения per-test (§7);
   аварийное завершение на уровне процесса относится только к runtime-стражам, не к тестовым
   утверждениям

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Аргументы:
  [PATHS]...      Указанные тестовые файлы или каталоги (по умолчанию: читается из yaoxiang.toml, иначе tests/)

Опции:
  --filter <NAME>     Запускать только тесты, имя файла которых содержит <NAME>
  --fail-fast         Остановиться при первом сбое
  --verbose, -v       Показывать подробный stdout/stderr каждого теста
  --list              Только перечислить тестовые файлы, не запускать
  --no-progress       Не показывать вывод прогресса (заголовок и строки PASS); подробности FAIL и сводка сохраняются (сценарий CI)
  --json              Вывод результатов в формате JSON (для интеграции с CI)
  --parallel          Параллельное выполнение (по одному worker на ядро; объединяется с [tool.test].parallel через ИЛИ)
```

#### Формат вывода

**Вывод по умолчанию** (суждения per-test поступают из сбора набора внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**Вывод JSON** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы со сбоем дополнительно несут `exit_code` и `stderr` (диагностика дочернего процесса после
  удаления ANSI, для криминалистики в CI); в комбинации `--verbose` и `--json` все файлы несут
  `stdout` / `stderr`
- `--no-progress` подавляет только вывод прогресса (заголовок и строки PASS) — подробности FAIL и
  сводка всегда выводятся, сбой не может быть скрыт; `--list` выводит по одному пути тестового файла
  в строке, без выполнения
- Каждый файл снабжён `kind` (behavior / compile-error / runtime-error / invalid, §8.2), сводка
  содержит `by_kind` со счётчиками выполнения (фиксированные четыре ключа, без skipped);
  человеческая сводка содержит строку `Categories:` с распределением по категориям
- В режиме `--parallel` строки человеческого прогресса выводятся потоково **по порядку завершения**
  (блоками без чередования), JSON-массив `files` сортируется по пути `file` для стабильности вывода
  (дружественно к diff в CI)
- Массив per-test `tests` внутри файла поступает из сбора набора §7, вступает в силу с реализацией
  модели значения
- Официальный CI (`.github/workflows/ci.yml`, задача test) потребляет именно так: со стороны cargo
  запускается `--test integration` (интеграция CLI) и `--test yx_runner` (двухкорневой страж
  корпуса), затем `yaoxiang test --json --parallel` — послойный реальный прогон — режим по умолчанию
  (языковой корпус) и явный `src/std/tests` (уровень библиотек) производят каждый свой отчёт;
  сводная таблица (total / passed / failed / skipped / time_secs и by_kind) записывается в job
  summary, для файлов со сбоем печатаются `kind` / `exit_code` / `stderr` для криминалистики,
  ненулевой выход любого набора — красный статус

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
exclude = ["tests/fixtures/**"]   # совпадения исключаются из набора обнаружения (--list также исключает)
parallel = true                   # параллельное выполнение (объединяется с флагом --parallel через ИЛИ)
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочую конфигурацию из
  коробки
- `exclude` имеет ту же форму, что и `patterns` (литеральный путь или `root/**…`, всегда по
  совпадению префикса пути); исключённое означает «не тест», фикстуры, требующие проверки
  runtime-поведения, запускаются напрямую через `yaoxiang run`
- **Однофайловый режим (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации** —
  при явных paths ключи `exclude`/`parallel` не действуют (кроме флага)
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — библиотека утверждений на чистом YaoXiang (стандартная форма знаковой семантики, реализовано 2026-09-03)
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang написана на YaoXiang.

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not и assert_false — одно и то же тело; assert_err / assert_err_code см. §8.1
```

- Функции утверждений имеют **знаковую семантику**: возвращают `Result(Void, String)`, сбой
  выражается через `Err(диагностика)`, без аварийного завершения процесса — набор §7 собирает на
  этой основе суждения per-test. Семантика аварийного завершения `std.assert.assert` сохраняется для
  runtime-стражей и не попадает в путь тестовых утверждений. Полезная нагрузка Ok — `Void`
  (нормативный unit из type-system.md; `()` — пустой Tuple, они не смешиваются — решение от
  2026-09-03)
- **Семейство функций из 7 штук (поставлено 2026-09-03, переходная версия с abort удалена)**:
  знаковые `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (одно тело с
  assert_false, зарезервировано под форму `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (утверждение кода ошибки, §8.1)
  - `assert_approx_eq(a: Float, b: Float, eps: Float)` (Фаза 3, поставка 2026-09-07): суждение
    `|a - b| <= eps`, eps задаётся вызывающей стороной **явно** — допуск является частью тестового
    контракта, скрытого значения по умолчанию нет; отрицательный eps даёт Err уже в точке
    объявления, NaN — всегда Err
- `assert_eq` / `assert_ne` используют **Any в аннотации параметров** — `==`/`!=` и интерполяция
  f-string работают с Any, не полагаясь на систему дженериков. Обратите внимание: параметры **должны
  быть явно аннотированы**: без аннотации параметры не проходят проверку вызова для native-дженерика
  `&Result(T, E)` (эмпирически подтверждено пробником R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный синтаксис `not` не
  реализован, можно мигрировать после стабилизации; унарная форма `!assert` зависит от того же, см.
  §8.1)
- Форма тела блока + явный `return`: тип then-ветви if-выражения отбрасывается при проверке,
  if-выражение с Result в обеих ветвях — слепая зона проверки, реализация обходит её
- `std.test` не зависит от какого-либо native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое проектное решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраиваются в
бинарник во время сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // далее больше
];
```

Модульная система (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения:
Registry содержит одновременно native-модули и исходные модули, orchestrator отвечает за
многофайловую оркестровку. Порядок разрешения `use std.test`:

1. Сначала проверка Rust native-модулей (существующий механизм, например `std.assert`)
2. При отсутствии — проверка встроенных `STD_YX_FILES` — при совпадении исходный модуль
   инжектируется в orchestrator под **виртуальным путём** (например `<std>/test.yx`) в качестве
   начального и проходит обычный фронтенд-конвейер (parse → typecheck → IR)
3. При отсутствии — обнаружение через файловую систему (пользовательские модули)

Ссылки `use std.assert` внутри встроенного исходного модуля нормально разрешаются resolver'ом в
native-registry — native и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импорте.

Преимущества:

- В однофайловом режиме `use std.test` также работает
- Версия стандартной библиотеки строго привязана к бинарнику, рассинхронизации версий не будет
- Пользователю не нужно настраивать путь к стандартной библиотеке

**В будущем: стандартная библиотека в файловой системе**

После того как режим проекта YaoXiang созреет, стандартная библиотека будет переведена в форму
файловой системы. Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение ревизии 2026-08-02)**: CLI `run` подключается к orchestrator. В
текущем состоянии CLI `run` использует однофайловый конвейер (`run_file_with_diagnostics`) и не
может разрешать импорты пользовательских модулей; но модель дочернего процесса `yaoxiang test`
наследует возможности CLI, а импорт тестовыми файлами модулей проекта — ключевой сценарий. Поэтому
на Фазе 1 сначала исходная ветвь CLI `Run` делегируется `run_project` (orchestrator, рекурсивное
обнаружение по каталогу); обнаружение по use по требованию позже накладывается как чистая
оптимизация производительности. Однофайловый случай без импортов через orchestrator ведёт себя
эквивалентно, ветвь байткода не меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет — по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению в имя файла)
5. Область обнаружения — это слои тестирования (§9): patterns по умолчанию покрывают только корпус
   языковой доступности; уровень библиотечных тестов (например `src/std/tests/`) обнаруживается
   через явный путь или конфигурацию пакета, не подмешивается в сканирование по умолчанию

**Этап выполнения**:

1. Для каждого файла — маршрутизация выполнения по заголовочной директиве (грамматика директив см.
   §8.2, разбирается через `src/util/test_markers.rs`, используется совместно с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run <file>` (ошибки runtime по умолчанию несут
     позицию в исходнике и кадр стека — debug_map генерируется по умолчанию, трассировка стека
     выводит `file:line:col`); директива `// mode:` объявляет режим `--runtime` дочернего процесса
   - Класс отказа на этапе компиляции: одношаговый `yaoxiang check <file>`
   - Класс сбоя на этапе выполнения: `check` (должен пройти) + `run` (должен сбоить) — два шага
2. Файлы с `// skip: <причина>` пропускаются, засчитываются в skipped отчёта
3. Сравнение суждения с ожидаемым кодом — по матрице суждений §8.2; сбой разбора директив — не
   выполнять, сразу FAIL (отказ на этапе построения)
4. Захват stdout/stderr для отчёта
5. По умолчанию последовательно; `--parallel` (или `[tool.test].parallel`) запускает пул worker'ов
   по числу доступных ядер, каждый файл по-прежнему — отдельный дочерний процесс — skip/invalid
   обрабатываются первыми по порядку обнаружения, результаты выполнения выводятся потоково по
   порядку завершения, JSON сортируется по пути (Фаза 3, поставка 2026-09-07)
6. При `--fail-fast` — остановить планирование новых файлов при первом FAIL; в параллельном режиме
   уже запущенные файлы завершаются и засчитываются

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей уровня процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственный Heap, Frame, NativeContext
- Паника одного тестового файла не влияет на другие
- Никакого дополнительного механизма изолированного контекста Heap не требуется
- **Параллельное выполнение (Фаза 3) не расширяет границу изоляции**: рабочий каталог (CWD) дочерних
  процессов — общий, параллельные тесты не должны занимать файлы по одинаковому пути в CWD — тесты с
  файловым I/O используют уникальные имена файлов и очищают их по завершении

### 7. Наборы и множественные тесты (модель значения)

Один тестовый файл может содержать несколько тестов. Способ организации внутри файла (реализовано
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main: () -> Void = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — функция без аргументов, возвращающая `Result(Void, String)`; сбой утверждения
  выражается через `Err` (знаковое семейство §3), не прерывает процесс — последующие тесты
  продолжают выполняться
- `test.suite` вызывает по очереди и собирает: не-Ok для какого-либо теста — записываются имя и
  диагностика, Ok — тишина; после прогона всех при наличии любого Err — аварийное завершение через
  `std.assert.assert` с подробностями сбоя (`N of M test(s) failed` + по каждой строке
  `[FAIL] имя: диагностика`) — exit code файла ненулевой (суждение §5 не меняется). Этот abort здесь
  — runtime-страж тестового бинарника, а не путь утверждения; все Ok — тихий выход 0
- Тестовые функции верхнего уровня вносятся в список **в форме замыканий**
  (`("name", () => test_fn())`): ссылка на имя функции верхнего уровня как значение временно не
  поддерживается (ограничение уровня IR, `E3006`) — вызов глобальной функции из тела замыкания не
  затронут
- Runner видит только файл, сканирования на уровне функций не делает: суждения per-test целиком
  поступают из сбора внутри набора, внутренняя структура файла прозрачна для runner — принцип
  нулевых изменений компилятора не нарушается
- Явно не принято: граница catch внутри процесса (17-ключевое железное правило); вызовы runner'а
  поточечно по функциям (допустимо только для внутренних сценариев наподобие сбоя компиляции в §8.2)
- Форма API решена (2026-09-03): `suite(tests: List((String, () -> Result(Void, String)))) -> Void`;
  дубликаты имён не обнаруживаются (имя используется только для отображения в отчёте); `--filter`
  фильтрует по имени файла, не различает имена тестов внутри набора

### 8. Трёхуровневое проектирование негативных тестов (ожидаемый сбой)

Негативные тесты разделяются по слою возникновения сбоя, каждый уровень на своём месте:

#### 8.1 Отрицание на уровне значений (универсальное, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый сбой обычным утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// или в одну обёртку (код существует только на носителе Error, E жёстко закреплён за Error):
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с семейством знаковой семантики
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса not (то
  же ограничение, что и `cond == false` в `assert_false`)
- Утверждение кода ошибки зависит от того, что значение `Error` несёт машиночитаемое поле `code` —
  уже реализовано: `Error = { code, message }` (native `error_new(code, message)`), чтение через
  `result.unwrap_err(r)` для получения носителя и `result.code(e)` / `result.message(e)` — аксессоры
  (предполагавшиеся на этапе проектирования именование `error_new_with_code`, экспорт констант кодов
  и доступ к полю `err.code` не приняты — в языке нет доступа к полям Struct, константы кодов не
  экспортированы)
- По мере продвижения Result-изации операции, которые могут сбоить, постепенно возвращают `Result`,
  и файловые негативные метки в корпусе переносятся в утверждения внутри файла

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это «всё или ничего» для всего файла, невозможно выразить внутри файла «эта строка не
должна компилироваться»; сбой runtime также требует файлового выражения (например, набор содержит
обязательно падающие тесты). Заголовок файла объявляет ожидание **структурированной директивой**,
runner маршрутизирует суждение по категории ожидания (маршрутизация решена 2026-09-03; грамматика
директив решена и реализована 2026-09-06).

Грамматика заголовочных директив (`// key: value`, в пределах первых 16 строк, строгое
токен-совпадение):

```text
// expect: compile-error E1002 [E1003 ...]   Тест отказа на этапе компиляции
// expect: runtime-error E6003 [...]         Тест сбоя на этапе выполнения
// skip: <причина>                           Пропустить выполнение, засчитать в skipped
// mode: embedded|standard|full              Режим --runtime дочернего процесса (потребляется только шагом run)
```

- Отсутствие директивы `expect:` = поведенческий тест. `expect:` — **единственное объявление**
  ожидания — 2026-09-06 решено отказаться от булевых меток `[test:error]` и
  китайских散文抠码 «预期:»: булева метка и строка ожидания — два слабо связанных факта, которые при
  дисциплинарном поддержании неизбежно расходятся; строгая английская токен-грамматика позволяет
  runner'у механически разбирать (kind + код — фиксированные токены, любой лишний токен после кода —
  сбой разбора), сбой разбора = не выполнять, сразу FAIL — канал тихой деградации из-за ошибочного
  объявления директивы не существует (отказ на этапе построения)
- **Класс ошибки компиляции**: одношаговый `check` — должен сбоить, и вывод содержит все `[EXXXX]`;
  успешная компиляция = FAIL (то, что должно было быть сообщено, не сообщено), отказ с несовпадающим
  кодом = FAIL. Синтаксические (E1xxx, этап разбора) и семантические (E2xxx+) ошибки не выделяются в
  отдельные категории — сам ожидаемый код закрепляет этап
- **Класс ошибки выполнения**: двухшаговое суждение — `check` должен **пройти** (этап компиляции
  чист), `run` должен сбоить, и вывод содержит все `[EXXXX]`. Сбой уже на этапе компиляции = FAIL
  (суждение, противоположное по направлению классу ошибки компиляции, предотвращающее пропуск случая
  «компиляция случайно прошла, выполнение случайно упало»)
- Изоморфно отраслевому опыту: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`,
  Clang `expected-error` — все объявляют ожидания в комментариях фикстуры с двусторонним сравнением
  через harness; они используют построчную привязку из-за того, что многоиагностическим компиляторам
  нужно различать множественные ожидания в одном файле; наш компилятор останавливается на первой
  ошибке, одна диагностика на файл, файловый уровень изоморфен реальности компилятора — после
  реализации восстановления после ошибок в грамматику можно добавить построчную привязку
  (заголовочные директивы + ожидания на уровне функций в Cranelift filetests — та же гибридная
  форма)
- Известный долг по рендерингу: диагностика этапа parse сейчас выводится в форме Debug
  (`code: "E0012"` вместо `[E0012]`), сканирование кодов принимает обе формы; после унификации
  рендеринга диагностики строгая форма будет возвращена
- **Служит только корпусу данного репозитория, не является частью пользовательского тестового
  фреймворка**; соглашение о двойном суждении runner'ов закрыто (2026-09-03): yx_runner (cargo test)
  и `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора заголовочных
  директив, соглашение о каталоге 06-compile-errors упразднено. Уровень отчёта выдаёт счётчики по
  категориям: человеческая сводка содержит строку `Categories:`, JSON-сводка содержит `by_kind`
  (behavior / compile-error / runtime-error / invalid, skipped учитывается отдельно), каждый файл
  содержит `kind`

#### 8.3 Жёсткие сбои runtime (отнесены к Result-изации)

Отдельный механизм не предусматривается — операции, которые могут сбоить, по направлению языка
возвращают `Result`, тесты единообразно идут через §8.1. Аварийное завершение уровня процесса
(например, нарушение утверждения, ошибка параметров runtime) по мере Result-изации постепенно
сворачивается в значение, тестовый фреймворк не предоставляет для него специальной семантики.
(Замечание: маркер «класс ошибки выполнения» из §8.2 — это канал файлового уровня для runner'а для
верификации **операций, пока не поддающихся Result-изации**, он не противоречит семантическому
направлению данного раздела — последний является конечной точкой, первый — каналом переходного
периода)

### 9. Слои тестовой системы: языковой корпус и библиотечные тесты (решено 2026-09-03)

Тесты разделяются на два слоя **по объекту тестирования**, у каждого своё место и сопровождающий;
система меток (§8.2) и библиотека утверждений (§3) — общие для обоих уровней:

**Первый слой: корпус языковой доступности (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык** — парсер, система типов, модули, конкурентность, владение,
  отказы на этапе компиляции, семантика выполнения; каталог организован по главам языковой
  спецификации
- std в корпусе выступает только **инструментом утверждений** (`std.assert` / `std.test`), никогда
  не тестируется — поведение API библиотек не относится к языковой доступности
- Внутри корпуса по §8 происходит маршрутизация на три класса суждений: поведенческие тесты / тесты
  отказа на этапе компиляции / тесты сбоя на этапе выполнения

**Второй слой: библиотечные тесты (идут вместе с библиотекой)**

- Объект тестирования — **публичный API-контракт библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся **в собственном пакете библиотеки**: пакет std — это `src/std/`, его yx-уровневые
  тесты относятся к `src/std/tests/` (вместе с реализацией; каталог сосуществует с модульными
  тестами Rust, типы файлов не пересекаются); тесты самого `std.test` также здесь (использовать
  std.test для тестирования std.test, самозамыкание)
- Будущие пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (макет раскладки тестов пакетного менеджера из RFC-014 репетируется
  этим)
- Обнаружение не входит в patterns по умолчанию (по умолчанию `tests/**/*.yx` покрывает только
  языковой уровень): уровень библиотечных тестов обнаруживается через явный путь
  (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI запускает послойно

Заметка о миграции: **мигрировано (2026-09-06)** — исходные 19 файлов из `tests/yaoxiang/07-std/`
после индивидуального рассмотрения все оказались библиотечными тестами (объекты тестирования —
API-контракты модулей std; роль языковых возможностей наподобие распространения `?`,
автозаимствования, инстанциации дженериков в них — носитель, а не объект тестирования), полностью
перенесены в `src/std/tests/` и каталог 07-std удалён; yx_runner переведён на двухкорневое
обнаружение (`tests/yaoxiang/` + `src/std/tests/`), patterns по умолчанию не содержат уровень
библиотек (интеграционные тесты фиксируют этот контракт). Языковой корпус с тех пор не содержит
тестов API std.

## Открытые вопросы

- [x] Может ли ссылка `use std.assert` в `std/test.yx` корректно разрешаться? — **Решено
      (2026-08-02)**. После реализации модульной системы (RFC-029) native и исходные модули
      сосуществуют в Registry, resolver разрешает единообразно, межвидовые зависимости работают
      естественно
- [x] Вносит ли дженерик `to_string` в `f"..."` в выводе тестов новые ограничения типов? — **Решено
      (2026-08-02)**. Подтверждено, что `==`/`!=` и интерполяция f-string работают на параметрах без
      аннотации (Any) (проверено на Int/String), новых ограничений не вводится
- [x] Осуществимость параметра-дженерика `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в
      настоящее время не существует (и будет молча проглочен, отслеживается отдельным issue),
      функции утверждений Фазы 1 используют параметры без аннотации, не полагаясь на систему
      дженериков
