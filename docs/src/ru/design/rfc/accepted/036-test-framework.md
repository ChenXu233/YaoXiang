# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Ввести в YaoXiang стандартный фреймворк тестирования — модуль `std.test` и подкоманду CLI
`yaoxiang test`. Тестовые файлы — это обычные файлы `.yx`, прохождение/провалы определяются через
`std.assert.assert` + exit code. Модуль `std.test` реализован на чистом YaoXiang и является первой
dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не особенность компилятора: не
затрагиваются parser, IR, байт-код или исполнитель.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` на стороне Rust и интеграционные
тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang
2. `#117 Модульное тестовое покрытие стандартной библиотеки` заблокирован, поскольку нет доступной
   тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) лишены
   автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения компилятора**: не трогать parser, IR, байт-код, исполнитель
- **Приоритет самобутстрапа (self-hosting)**: тестовая библиотека написана на YaoXiang — первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:  yaoxiang test [--filter --fail-fast --json ...]│
│              │                                               │
│  Уровень обнаружения: чтение yaoxiang.toml → [tool.test]     │
│              patterns                                        │
│              По умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Уровень выполнения: для каждого файла: yaoxiang run <file>  │
│              Проверка exit code → последовательное выполнение │
│              │                                               │
│  Уровень отчётов: PASS/FAIL → сводка                         │
│              Поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Уровень утверждений: std.test (чистый YaoXiang, самобутстрап)│
│              Ниже: std.assert.assert                         │
│              Диагностика: f"Expected {expected}, got {actual}"│
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — не особенность компилятора, а инструмент CLI** — `yaoxiang run` уже
   способен «выполнять тесты», `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводятся сканирование аннотаций `@test`, сегменты
   метаданных в байт-коде, специальные точки входа в исполнитель
3. **Самобутстрап** — модуль `std.test` реализован на чистом YaoXiang, внизу вызывает
   `std.assert.assert`
4. **Тестовые файлы — обычные файлы `.yx`** — прохождение/провал определяется по exit code

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Аргументы:
  [PATHS]...      Указанные тестовые файлы или каталоги (по умолчанию: читается из yaoxiang.toml, иначе tests/)

Параметры:
  --filter <NAME>     Запускать только тесты, имя файла которых содержит <NAME>
  --fail-fast         Остановиться при первом провале
  --verbose, -v       Показывать подробный stdout/stderr каждого теста
  --list              Только перечислить тестовые файлы, не запускать
  --no-progress       Не показывать индикатор прогресса (для CI)
  --json              Выводить результаты в формате JSON (для интеграции с CI)
```

#### Формат вывода

**Вывод по умолчанию**:

```
Running 5 tests from 3 files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ PASS (0.001s)
tests/string_test.yx ...................... FAIL (0.003s)
  `-- Expected "hello", got "world"
      at tests/string_test.yx:12:5

Results: 2 passed, 1 failed, 0 skipped (0.006s)
```

**Вывод JSON** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "tests": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/string_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "error": "Expected \"hello\", got \"world\"",
      "exit_code": 1
    }
  ]
}
```

### 2. Конфигурация yaoxiang.toml

Располагается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях
`[tool.*]` из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# Возможные будущие расширения:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — работает «из коробки» без настройки
- В режиме одного файла (`yaoxiang test foo.yx`) запуск происходит напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Pure YaoXiang test assertion library
// First dogfooding library: YaoXiang's test library written in YaoXiang

use std.assert

assert_eq = (a, b) => {
    assert.assert(a == b, f"Expected {b}, got {a}")
}

assert_ne = (a, b) => {
    assert.assert(a != b, f"Expected not equal to {b}, got {a}")
}

assert_true = (cond: Bool) => {
    assert.assert(cond, f"Expected true, got {cond}")
}

assert_false = (cond: Bool) => {
    assert.assert(cond == false, f"Expected false, got {cond}")
}
```

- 4 функции утверждений, все используют `f"..."` для диагностических сообщений
- `assert_eq` / `assert_ne` используют **параметры без аннотаций** (`Any`) — 2026-08-02
  подтверждено: `==`/`!=` и интерполяция f-string корректно работают на Any (проверено для
  Int/String), **не зависят от системы generics**. В будущем, когда generics будут готовы, можно
  добавить аннотации
- `assert_true` / `assert_false` аннотируют параметры как `Bool`; `assert_false` использует
  `cond == false` для выражения отрицания (унарный синтаксис `not` авторизуется в рамках #251, после
  стабилизации можно мигрировать)
- `std.test` не зависит от какого-либо native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраиваются в
бинарник на этапе сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // в будущем — больше
];
```

Система модулей (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения:
Registry одновременно хранит native-модули и исходные модули, orchestrator отвечает за оркестровку
нескольких файлов. Порядок разрешения `use std.test`:

1. Сначала поиск среди Rust native-модулей (существующий механизм, например `std.assert`)
2. При ненахождении — поиск во встроенных `STD_YX_FILES` — при попадании модуль внедряется в
   orchestrator с **виртуальным путём** (например, `<std>/test.yx`) в качестве затравочного модуля,
   проходит по обычному фронтенд-конвейеру (parse → typecheck → IR)
3. При ненахождении — обнаружение через файловую систему (пользовательские модули)

Внутренний `use std.assert` внутри встроенного исходного модуля нормально разрешается resolver'ом в
native registry — native и исходные модули сосуществуют в Registry, межтиповая зависимость работает
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импорте.

Преимущества:

- В режиме одного файла `use std.test` тоже работает
- Версия стандартной библиотеки строго привязана к бинарнику, рассинхронизация версий невозможна
- Пользователю не нужно настраивать пути к стандартной библиотеке

**Будущее: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение аудита 2026-08-02)**: CLI `run` подключается к orchestrator. В текущем
состоянии CLI `run` идёт по конвейеру одного файла (`run_file_with_diagnostics`) и не может
разрешать импорты пользовательских модулей; между тем модель подпроцессов `yaoxiang test` наследует
возможности CLI, а импорт тестовыми файлами модулей проекта — основной сценарий. Поэтому в Фазе 1
исходная ветка CLI `Run` сначала делегируется в `run_project` (orchestrator, рекурсивное обнаружение
по каталогам); #247 (обнаружение по `use` по требованию) впоследствии накладывается как чистая
оптимизация производительности. Однофайловый путь без импортов через orchestrator ведёт себя
эквивалентно, ветка байт-кода не меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по имени файла)

**Этап выполнения**:

1. Для каждого файла: запуск подпроцесса `yaoxiang run --debug-info <file>` (`--debug-info`
   обеспечивает наличие позиции в исходнике в ошибках времени выполнения — 2026-08-02 подтверждено,
   stack trace выводит `file:line:col`)
2. Проверка exit code: 0 — PASS, ненулевой — FAIL
3. Захват stdout/stderr для отчёта
4. Только последовательное выполнение (Фаза 1), в будущем — поддержка `--parallel`
5. При `--fail-fast` немедленная остановка на первом FAIL

### 6. Изоляция тестов

Изоляция тестов естественным образом обеспечивается границей уровня процессов:

- Каждый тестовый файл выполняется в отдельном подпроцессе
- Каждый подпроцесс имеет собственный Heap, Frame, NativeContext
- Panic в одном тестовом файле не влияет на другие тестовые файлы
- Дополнительный механизм изолированного контекста Heap не требуется

## Связи с существующими системами

| Элемент                                                     | Связь                                                                                                                   |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Rust `#[test]`                                              | Не трогаем; внутренние тесты компилятора остаются на Rust                                                               |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются `yaoxiang test`                                                                            |
| `std.assert.assert(cond)`                                   | Сохраняется, `std.test` опирается на него                                                                               |
| Система модулей (RFC-029)                                   | Встроенные исходные модули подключаются через Registry/orchestrator; подключение CLI `run` к orchestrator — предусловие |
| `#200` рефакторинг (`io.println` → `assert.assert`)         | Полностью совпадает по направлению с `yaoxiang test`                                                                    |
| Аннотации `@`                                               | Не используются, `@test` не вводится                                                                                    |

## Стратегия реализации

### Фаза 1: базовая функциональность

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — делегирование исходной ветки CLI `Run` в
  `run_project` (предусловие для многофайлового запуска)
- `src/main.rs` — добавление подкоманды `Test`
- `src/std/test.yx` — новый модуль на чистом YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарник
- orchestrator / Registry — поддержка загрузки `.yx` модулей из встроенных источников по
  виртуальному пути
- Парсинг конфигурации RFC-015 — секция `[tool.test]`
- Выполнение через подпроцессы (`--debug-info`) + отчёт

Поставка:

- Базовая работоспособность `yaoxiang test`
- 4 функции утверждений `std.test`
- Обнаружение по умолчанию `tests/**/*.yx`
- Последовательное выполнение + формат вывода по умолчанию

### Фаза 2: доработка

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Фаза 3: расширенные возможности

- Параллельное выполнение `--parallel` (зависит от завершения модели параллелизма spawn)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции утверждений (например, `assert_approx_eq` для Float)

## Риски и их снижение

| Риск                                                               | Вероятность | Снижение                                                                                 |
| ------------------------------------------------------------------ | ----------- | ---------------------------------------------------------------------------------------- |
| Сбой интерполяции `f"..."` на Any                                  | Нет         | 2026-08-02 подтверждено (Int/String работают нормально)                                  |
| Накладные расходы на запуск подпроцессов влияют на скорость тестов | Средняя     | Фаза 1 — последовательное выполнение, приемлемо; Фаза 3 — параллелизм смягчает           |
| Парсинг конфигурации `yaoxiang.toml` не в текущем CLI              | Низкая      | Простое расширение, не влияет на ядро                                                    |
| Подключение CLI `run` к orchestrator вызывает регрессию поведения  | Низкая      | Однофайловый путь без импортов эквивалентен; интеграционные тесты покрывают orchestrator |
| Встраивание исходных файлов `.yx` в бинарник увеличивает размер    | Низкая      | Исходные `.yx` очень малы, пренебрежимо                                                  |

## Открытые вопросы

- [x] Может ли ссылка `use std.assert` в `std/test.yx` корректно разрешаться? — **Решено
      (2026-08-02)**. После реализации системы модулей (RFC-029) native и исходные модули
      сосуществуют в Registry, resolver разрешает единообразно, межтиповая зависимость работает
      естественно
- [x] Вводит ли обобщённый `to_string` в `f"..."` в выводе тестов новые ограничения типов? —
      **Решено (2026-08-02)**. Подтверждено, что на параметрах без аннотаций (Any) `==`/`!=` и
      интерполяция f-string работают (проверено на Int/String), новые ограничения не вводятся
- [x] Возможность параметра-дженерика `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в настоящее
      время не существует (и будет молча проглатываться, отслеживается отдельным issue), в Фазе 1
      функции утверждений используют параметры без аннотаций и не зависят от системы generics
