# RFC-036: Тестовый фреймворк std.test и команда yaoxiang test

## Резюме

Внедрение в YaoXiang стандартного тестового фреймворка — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы — обычные `.yx` файлы, общий результат прохождения/провала
определяется по коду выхода дочернего процесса; внутри файла поддерживается несколько тестовых
функций — сбой утверждения выражается значением `Err` (семантика значений), а набор собирает
per-test вердикты (§7). Модуль `std.test` реализован на чистом YaoXiang и является первой
dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не возможность компилятора — никаких
изменений в парсере, IR, байткоде или исполнителе не требуется.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` на стороне Rust и интеграционные
тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. `#117 Покрытие модульными тестами каждого модуля стандартной библиотеки` заблокировано, так как
   отсутствует тестовая инфраструктура
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) не
   имеют автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения компилятора**: не трогать парсер, IR, байткод, исполнитель
- **Приоритет самобутстрапа**: тестовая библиотека написана на YaoXiang, первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Слой CLI:    yaoxiang test [--filter --fail-fast --json ...]│
│                  │                                           │
│  Слой обнаружения: чтение yaoxiang.toml → [tool.test]        │
│                  patterns                                    │
│                  по умолчанию: tests/**/*.yx                  │
│                  │                                           │
│  Слой выполнения: для каждого файла: yaoxiang run <file>     │
│                  проверка кода выхода → последовательное      │
│                  выполнение                                  │
│                  │                                           │
│  Слой отчёта:  PASS/FAIL → сводка                            │
│                  поддержка --json / --verbose / --fail-fast   │
│                  │                                           │
│  Слой утверждений: std.test (чистый YaoXiang, самобутстрап)  │
│                  низкий уровень: std.assert.assert            │
│                  диагностика: f"Expected {expected}, got      │
│                  {actual}"                                   │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — не возможность компилятора, а инструмент CLI** — `yaoxiang run` уже умеет
   «выполнять тесты», `yaoxiang test` лишь запускает все файлы и показывает отчёт
2. **Нулевые изменения компилятора** — не вводится сканирование аннотаций `@test`, секции метаданных
   в байткоде, специальных точек входа в исполнителе
3. **Самобутстрап** — модуль `std.test` реализован на чистом YaoXiang, низкоуровневые возможности
   берутся из `std.assert` / `std.result`
4. **Тестовые файлы — обычные `.yx` файлы** — файл запускается как дочерний процесс, общий результат
   определяется по коду выхода
5. **Сбой утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, сбой утверждения выражается через `Err`, набор собирает per-test вердикты поштучно
   (§7); аварийное завершение на уровне процесса относится только к рантайм-guard'ам, не к тестовым
   утверждениям

## Детальное проектирование

### 1. Дизайн CLI

```
yaoxiang test [ОПЦИИ] [ПУТИ]

Аргументы:
  [ПУТИ]...        Указанные тестовые файлы или каталоги (по умолчанию: чтение из
                   yaoxiang.toml, иначе tests/)

Опции:
  --filter <ИМЯ>   Запускать только тестовые файлы, имя которых содержит <ИМЯ>
  --fail-fast      Остановиться при первом сбое
  --verbose, -v    Показывать подробный stdout/stderr каждого теста
  --list           Только перечислить тестовые файлы, не запускать
  --no-progress    Не выводить индикатор прогресса (заголовок и строки PASS);
                   подробности FAIL и сводка сохраняются (сценарий CI)
  --json           Вывод результатов в формате JSON (для интеграции с CI)
```

#### Формат вывода

**Вывод по умолчанию** (per-test вердикты поступают от сбора набора внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**Вывод JSON** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы со сбоем дополнительно несут `exit_code` и `stderr` (диагностика дочернего процесса после
  удаления ANSI-кодов, для сбора улик в CI); при комбинации `--verbose` и `--json` все файлы несут
  `stdout` / `stderr`
- `--no-progress` подавляет только индикатор прогресса (заголовок и строки PASS) — подробности FAIL
  и сводка выводятся всегда, сбой не замалчивается; `--list` выводит по одному пути тестового файла
  на строку, без выполнения
- К каждому файлу приписывается `kind` (behavior / compile-error / runtime-error / invalid, §8.2), в
  сводку добавляется `by_kind` со счётчиками выполнения (фиксированные четыре ключа, без skipped); в
  человекочитаемой сводке — строка `Categories:` с распределением по категориям
- Массив `tests` с per-test вердиктами внутри файла поступает из сбора набора согласно §7, вступает
  в силу по мере закрепления модели на значениях (#319)

### 2. Конфигурация yaoxiang.toml

Располагается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях
`[tool.*]` из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# Возможные будущие расширения:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочую конфигурацию из
  коробки
- Одиночный файл (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` сохраняется)

### 3. Модуль `std.test` (чистый YaoXiang)

```yaoxiang
// std/test.yx — библиотека тестовых утверждений на чистом YaoXiang (стандартная форма
// семантики значений, закреплено 2026-09-03)
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang написана на YaoXiang.

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not и assert_false — одно и то же; assert_err / assert_err_code см. §8.1
```

- Функции утверждений имеют **семантику значений**: возвращают `Result(Void, String)`, сбой
  выражается через `Err(диагностика)`, без аварийного завершения процесса — набор в §7 опирается на
  это для сбора per-test вердиктов. Семантика аварийного завершения `std.assert.assert` сохраняется
  для рантайм-guard'ов и не входит в путь тестовых утверждений. Полезная нагрузка Ok — `Void`
  (согласно type-system.md это unit; `()` — это пустой Tuple, они не смешиваются — закреплено
  2026-09-03)
- **Семейство из 7 функций (поставлено 2026-09-03, переходная версия с abort удалена)**:
  value-семантика `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (одно
  тело с assert_false, зарезервировано для формы `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (утверждение кода ошибки, §8.1)
- `assert_eq` / `assert_ne` используют аннотацию параметров **Any** — `==`/`!=` и интерполяция
  f-string работают на Any корректно, без зависимости от системы дженериков. Обратите внимание:
  параметры **должны быть аннотированы явно**: неаннотированные параметры не проходят проверку
  вызова native-дженерика `&Result(T, E)` (подтверждено пробником R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный синтаксис `not` не
  закреплён; после стабилизации возможна миграция; унарная форма `!assert` имеет ту же зависимость,
  см. §8.1)
- Форма с блочным телом и явным `return`: тип then-ветки if-выражения отбрасывается при проверке,
  if-выражение с Result в обеих ветках — слепая зона проверки, реализация обходит это
- `std.test` не зависит от какого-либо native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое проектное решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраиваются в
бинарник на этапе сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // в будущем — больше
];
```

Точкой подключения служит модульная система (RFC-029, полностью закреплено 2026-08-02): Registry
одновременно хранит native-модули и исходные модули, оркестратор отвечает за оркестровку нескольких
файлов. Порядок разрешения `use std.test`:

1. Сначала поиск native-модуля Rust (существующий механизм, например `std.assert`)
2. Если не найдено — поиск во встроенных `STD_YX_FILES`; при попадании модуль внедряется в
   оркестратор по **виртуальному пути** (например, `<std>/test.yx`) в качестве затравочного и
   проходит обычный фронтенд-конвейер (parse → typecheck → IR)
3. Если не найдено — обнаружение в файловой системе (пользовательские модули)

`use std.assert` внутри встроенного исходного модуля нормально разрешается resolver'ом в native
registry — native и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: в конвейер попадают только при
импорте.

Преимущества:

- В одиночном режиме `use std.test` тоже работает
- Версия стандартной библиотеки строго привязана к бинарнику, рассинхронизации не будет
- Пользователю не нужно настраивать путь к стандартной библиотеке

**Будущее: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в форму файловой
системы. Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение ревью 2026-08-02)**: CLI `run` подключается к оркестратору. В
текущем виде CLI `run` идёт по одноп file-конвейеру (`run_file_with_diagnostics`) и не может
разрешать импорты пользовательских модулей; а модель дочерних процессов `yaoxiang test` наследует
возможности CLI, импорт проектных модулей из тестовых файлов — ключевой сценарий. Поэтому на Фазе 1
ветвь исходного кода CLI `Run` сначала делегируется `run_project` (оркестратор, рекурсивное
обнаружение каталога); #247 (обнаружение по use по требованию) впоследствии накладывается как чистая
оптимизация производительности. Одиночные файлы без импортов через оркестратор ведут себя
эквивалентно, ветвь байткода не меняется.

**Фаза обнаружения**:

1. Если указаны `[ПУТИ]`, используются они напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению в имя файла)
5. Область обнаружения совпадает с тестовой стратификацией (§9): patterns по умолчанию покрывают
   только корпус языковой применимости; уровень тестов библиотек (например, `src/std/tests/`)
   обнаруживается по явному пути или конфигурации пакета и не подмешивается в сканирование по
   умолчанию

**Фаза выполнения**:

1. Для каждого файла выполнение ветвится по заголовочной директиве (грамматика директив см. §8.2,
   разбирается через `src/util/test_markers.rs`, общий с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run --debug-info <file>` (`--debug-info`
     заставляет рантайм-ошибки нести позицию в исходнике — подтверждено 2026-08-02, stack trace
     выдаёт `file:line:col`); директива `// mode:` объявляет режим `--runtime` дочернего процесса
   - Класс отказа на этапе компиляции: один шаг `yaoxiang check <file>`
   - Класс отказа в рантайме: два шага — `check` (обязан пройти) + `run` (обязан провалиться)
2. Файлы с `// skip: <причина>` пропускаются, учитываются в skipped отчёта
3. Вердикт сверяется с ожидаемым кодом по матрице §8.2; сбой разбора директивы — выполнение не
   запускается, сразу FAIL (отказ на этапе конструирования)
4. Захват stdout/stderr для отчёта
5. Только последовательное выполнение (Фаза 1), в будущем — `--parallel`
6. При `--fail-fast` останов сразу при первом FAIL

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственные Heap, Frame, NativeContext
- Паника одного тестового файла не влияет на другие тестовые файлы
- Дополнительный механизм изолированных Heap-контекстов не требуется

### 7. Набор тестов и множественные тесты (модель на значениях)

Тестовый файл может содержать несколько тестов. Способ организации внутри файла (закреплено
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — функция без параметров, возвращающая `Result(Void, String)`; сбой утверждения
  выражается через `Err` (семантика значений семейства утверждений из §3) и не прерывает процесс —
  последующие тесты выполняются как обычно
- `test.suite` вызывает поочерёдно и собирает: если тест не Ok, записывается имя и диагностика; Ok —
  молча. После прогона всех тестов при наличии любого Err — аварийное завершение через
  `std.assert.assert` с подробностями сбоев (`N of M test(s) failed` + по каждой
  `[FAIL] имя: диагностика`) — код выхода файла не 0 (вердикт из §5 не меняется). Это abort здесь —
  рантайм-guard тестового бинарника, а не путь утверждений; все Ok — тихий выход с кодом 0
- Тестовые функции верхнего уровня попадают в набор **в форме замыканий**
  (`("имя", () => test_fn())`): имя функции верхнего уровня как ссылка на значение пока не
  поддерживается (ограничение IR, `E3006`) — вызов глобальной функции из тела замыкания не затронут
- Runner видит только файл, не сканирует функции: per-test вердикты поступают исключительно из сбора
  внутри набора, внутренняя структура файла прозрачна для runner'а — принцип нулевых изменений
  компилятора не нарушается
- Явно не применяются: граница catch внутри процесса (железное правило 17 ключевых слов); вызов на
  уровне отдельных функций в runner'е (только внутренние сценарии вроде §8.2 — ошибки компиляции)
- Форма API закреплена (2026-09-03, #319):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дубликаты имён не
  обнаруживаются (имя используется только для отображения в отчёте); `--filter` фильтрует по имени
  файла и не различает имена тестов внутри набора

### 8. Трёхуровневая схема негативных тестов (ожидаемый сбой)

Негативные тесты стратифицируются по уровню возникновения сбоя, каждый уровень занимает своё место:

#### 8.1 Обращение значения (универсально, для пользователей)

Тестируемая операция возвращает `Result`, тест обычным утверждением выражает ожидаемый сбой:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// либо одной обёрткой (код существует только в Error-носителе,
// E строго закреплён за Error):
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с семейством семантики значений
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после закрепления синтаксиса `not`
  (то же ограничение, что и `cond == false` у `assert_false`)
- Утверждение кода ошибки опирается на то, что значение `Error` несёт машиночитаемое поле `code` —
  закреплено в M4 по #323: `Error = { code, message }` (native `error_new(code, message)`), чтение
  идёт через `result.unwrap_err(r)` для получения носителя и аксессоров `result.code(e)` /
  `result.message(e)` (предполагавшиеся на этапе проектирования имена `error_new_with_code`, экспорт
  констант кодов и доступ к полю через `err.code` — не приняты: в языке нет доступа к полям Struct,
  константы кодов не экспортируются)
- По мере продвижения Result-изации (#301, #316) операции, которые могут провалиться, одна за другой
  возвращают `Result`, файловые негативные пометки в корпусе мигрируют во внутренние утверждения

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это «всё или ничего» для файла, выразить «эта строка не должна компилироваться» внутри
файла невозможно; рантайм-сбои также требуют файлового выражения (например, набор содержит
обязательно проваливающиеся тесты). Заголовок файла объявляет ожидание **структурированной
директивой**, runner выполняет **ветвящийся вердикт** по ожидаемой категории (ветвление закреплено
2026-09-03; грамматика директив закреплена и реализована 2026-09-06).

Грамматика заголовочных директив (`// ключ: значение`, в пределах первых 16 строк, строгое
токен-сопоставление):

```text
// expect: compile-error E1002 [E1003 ...]   тест отказа на этапе компиляции
// expect: runtime-error E6003 [...]         тест отказа в рантайме
// skip: <причина>                            пропустить выполнение, учесть в skipped
// mode: embedded|standard|full               режим --runtime дочернего процесса
//                                            (потребляется только шагом run)
```

- Отсутствие директивы `expect:` означает поведенческий тест. `expect:` — это **единственное
  объявление ожидания** — 2026-09-06 закреплён отказ от булевой пометки `[test:error]` и от
  китайского «预期:» вольного извлечения кодов: булева пометка и строка ожидания — два слабо
  связанных факта, и поддержание их согласованности дисциплиной неизбежно дрейфует; строгая
  английская токен-грамматика позволяет runner'у разбирать механически (kind и коды — фиксированные
  токены, любой лишний токен после кода — сбой разбора), сбой разбора = не выполнять, сразу FAIL —
  тихого канала деградации при ошибочно объявленной директиве не существует (отказ на этапе
  конструирования)
- **Класс ошибок компиляции**: один шаг `check` — обязан провалиться, причём вывод должен содержать
  все `[EXXXX]`; прохождение компиляции = FAIL (ожидаемое не сообщилось), отказ с несоответствующим
  кодом = FAIL. Синтаксические (E1xxx на этапе разбора) и семантические (E2xxx+) ошибки не
  выделяются в отдельные категории — ожидаемый код сам привязывает стадию
- **Класс рантайм-ошибок**: двухшаговый вердикт — `check` обязан **пройти** (безвинный на этапе
  компиляции), `run` обязан провалиться, причём вывод должен содержать все `[EXXXX]`. Взрыв уже на
  этапе компиляции = FAIL (ключевой вердикт, противоположный классу ошибок компиляции, предотвращает
  пропуск «компиляция случайно прошла, рантайм случайно упал»)
- Изоморфно практике отрасли: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`,
  Clang `expected-error` — все объявляют ожидания в комментариях фикстуры и проводят двустороннее
  сравнение через harness; они используют построчную привязку, потому что у мультидиагностических
  компиляторов нужно различать несколько ожиданий в одном файле, а наш компилятор останавливается на
  первой ошибке и выдаёт одну диагностику на файл — файловый уровень изоморфен его реалиям; после
  закрепления восстановления после ошибок в грамматику можно добавить построчную привязку (файловые
  заголовочные директивы + ожидания на уровне функций у Cranelift filetests — та же смешанная форма)
- Известный долг по рендерингу: диагностика на этапе разбора сейчас выводится в форме Debug
  (`code: "E0012"` вместо `[E0012]`); сканирование кодов принимает обе формы; после унификации
  рендеринга диагностики строгая форма будет ужесточена
- **Служит только корпусу данного репозитория, не является частью пользовательского тестового
  фреймворка**; соглашение о двойном runner'е закрыто (2026-09-03, #319): yx_runner (cargo test) и
  `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора заголовочных директив,
  соглашение о каталоге 06-compile-errors упразднено. Слой отчёта выдаёт счётчики по категориям: в
  человекочитаемой сводке строка `Categories:`, в JSON-сводке `by_kind` (behavior / compile-error /
  runtime-error / invalid, skipped учитывается отдельно), к каждому файлу приписывается `kind`

#### 8.3 Жёсткий рантайм-сбой (относится к Result-изации)

Отдельный механизм не вводится — операции, которые могут провалиться, по направлению развития языка
возвращают `Result` (#301, #316), и тесты единообразно оформляются по §8.1. Аварийное завершение на
уровне процесса (например, нарушение утверждения, ошибка позиционности параметра в рантайме) по мере
Result-изации постепенно сворачивается в значения, тестовый фреймворк не предоставляет для него
специальной семантики. (Замечание: «класс рантайм-ошибок» из §8.2 с маркерной верификацией — это
канал runner'а на уровне файла для **операций, которые пока нельзя Result-изировать**, что не
противоречит семантическому направлению данного раздела — последний это конечная цель, первый —
переходный канал)

### 9. Стратификация тестовой системы: языковой корпус и тесты библиотек (закреплено 2026-09-03)

Тесты стратифицируются по **объекту тестирования** на два уровня, у каждого своя принадлежность и
сопровождающие; система пометок (§8.2) и библиотека утверждений (§3) общие для обоих уровней:

**Первый уровень: корпус языковой применимости (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык** — парсер, система типов, модули, конкурентность, владение,
  отказы на этапе компиляции, рантайм-семантика; каталоги организованы по главам языковой
  спецификации
- std в корпусе выступает только **инструментом утверждений** (`std.assert` / `std.test`), он
  никогда не тестируется — поведение API библиотеки не относится к языковой применимости
- Внутри корпуса потоки по §8: поведенческие тесты / тесты отказа на этапе компиляции / тесты сбоя в
  рантайме — три категории вердиктов

**Второй уровень: тесты библиотек (рядом с библиотекой)**

- Объект тестирования — **публичный API-контракт библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся **в собственном пакете библиотеки**: пакет std — это `src/std/`, его тесты уровня yx
  относятся к `src/std/tests/` (в одном месте с реализацией; каталог сосуществует с модульными
  тестами Rust, типы файлов не пересекаются); тесты самого `std.test` тоже находятся здесь
  (тестируем std.test через std.test — самобутстрап замкнут)
- Будущие пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (макет тестовой раскладки из RFC-014 про управление пакетами
  предвосхищается этим)
- Обнаружение не входит в patterns по умолчанию (по умолчанию `tests/**/*.yx` покрывает только
  языковой уровень): уровень тестов библиотек обнаруживается по явному пути
  (`yaoxiang test src/std/tests`) или конфигурации пакета; CI запускает по уровням

**Заметка о миграции: миграция завершена (2026-09-06)** — все 19 файлов из `tests/yaoxiang/07-std/`,
после индивидуального разбора, оказались тестами библиотек (объектом тестирования в каждом случае
был API-контракт модуля std; роль `?`-проброса, авто- borrow, инстанциации дженериков и подобных
языковых средств в них — носитель, а не объект тестирования); целиком перенесены в `src/std/tests/`
с удалением каталога 07-std; yx_runner переведён на обнаружение с двумя корнями (`tests/yaoxiang/` +
`src/std/tests/`), patterns по умолчанию не включают уровень библиотек (интеграционные тесты
фиксируют этот контракт). Языковой корпус с этих пор не содержит тестов std-API.
