# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

В YaoXiang вводится стандартный фреймворк тестирования — модуль `std.test` и подкоманда CLI
`yaoxiang test`. Тестовые файлы — это обычные файлы `.yx`, общий вердикт «пройден/провален»
определяется по коду выхода дочернего процесса; внутри файла может быть несколько тестовых функций —
неудача утверждения выражается значением `Err` (семантика значений), набор тестов собирает
потестовые вердикты (§7). Модуль `std.test` реализован на чистом YaoXiang и является первой
dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не свойство компилятора — никаких
изменений в парсер, IR, байт-код или исполнитель не вносится.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` на стороне Rust и интеграционные
тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. `#117 Модульное тестовое покрытие стандартной библиотеки` заблокировано из-за отсутствия
   доступной тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) не
   имеют средств автоматизации

### Ключевые ограничения

- **Незыблемое правило 17 ключевых слов**: никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения компилятора**: не трогать парсер, IR, байт-код, исполнитель
- **Приоритет самозагрузки**: тестовая библиотека написана на YaoXiang — первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI 层:  yaoxiang test [--filter --fail-fast --json ...]    │
│              │                                               │
│  发现层:    读取 yaoxiang.toml → [tool.test] patterns         │
│              默认: tests/**/*.yx                              │
│              │                                               │
│  执行层:    对每个文件: yaoxiang run <file>                    │
│              检查 exit code → 串行执行                        │
│              │                                               │
│  报告层:    PASS/FAIL → 汇总                                  │
│              支持 --json / --verbose / --fail-fast            │
│                                                              │
│  断言层:    std.test (纯 YaoXiang，自举)                      │
│              底层: std.assert.assert                          │
│              诊断: f"Expected {expected}, got {actual}"       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — не свойство компилятора, а инструмент CLI** — `yaoxiang run` уже умеет
   «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводится сканирование аннотаций `@test`, сегменты
   метаданных в байт-коде, специальные точки входа в исполнитель
3. **Самозагрузка** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности берутся
   из `std.assert` / `std.result`
4. **Тестовые файлы — обычные файлы `.yx`** — файл запускается как дочерний процесс, общий вердикт
   определяется по коду выхода
5. **Неудача утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, неудача утверждения выражается как `Err`, набор тестов собирает потестовые вердикты
   (§7); аварийное завершение на уровне процесса относится только к стражу времени выполнения и не
   используется для тестовых утверждений

## Детальное проектирование

### 1. Дизайн CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      指定测试文件或目录（默认: 从 yaoxiang.toml 读取，否则 tests/）

Options:
  --filter <NAME>     只跑文件名包含 <NAME> 的测试
  --fail-fast         遇到第一个失败就停止
  --verbose, -v       显示每个测试的详细 stdout/stderr
  --list              只列出测试文件，不跑
  --no-progress       不显示进度输出（表头与 PASS 行）；FAIL 明细与汇总保留（CI 场景）
  --json              输出 JSON 格式结果（CI 集成用）
  --parallel          并行执行（每核一个 worker；与 [tool.test].parallel 取或）
```

#### Формат вывода

**Вывод по умолчанию** (потестовые вердикты собираются из набора внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**Вывод JSON** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Для проваленных файлов дополнительно передаются `exit_code` и `stderr` (диагностика дочернего
  процесса с удалёнными ANSI-последовательностями, для CI-разбора); при комбинации `--verbose` и
  `--json` все файлы содержат `stdout` / `stderr`
- `--no-progress` подавляет только вывод прогресса (заголовок и строки PASS) — детали FAIL и сводка
  всегда выводятся, провал не может быть заглушён; `--list` выводит по одному пути тестового файла в
  строке, без выполнения
- К каждому файлу прикрепляется `kind` (behavior / compile-error / runtime-error / invalid, §8.2), к
  сводке — `by_kind` со счётчиками выполнения (фиксированные четыре ключа, без skipped); в
  человеческой сводке — строка распределения `Categories:`
- При `--parallel` человеческие строки прогресса потоково выводятся **по порядку завершения** (без
  чередования блоков), JSON-`files` сортируются по пути `file` для стабильности вывода (дружественно
  к diff в CI)
- Внутрифайловый массив `tests` поступает из набора §7, вступает в силу по мере реализации модели
  значений (#319)
- Официальный CI (job `test` в `.github/workflows/ci.yml`) потребляет именно этот формат: на стороне
  cargo запускаются `--test integration` (интеграция CLI) и `--test yx_runner` (двухкорневой страж
  корпуса), затем `yaoxiang test --json --parallel` иерархически выполняет тесты — режим по
  умолчанию (языковой корпус) и явный `src/std/tests` (уровень библиотек) дают каждый свой отчёт;
  сводка (total / passed / failed / skipped / time_secs и by_kind) записывается в job summary, для
  проваленных файлов печатаются `kind` / `exit_code` / `stderr` для разбора, ненулевой выход любого
  набора — красный статус

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]`, согласно соглашению о сторонних расширениях `[tool.*]` из
RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
exclude = ["tests/fixtures/**"]   # 命中者从发现集剔除（--list 同样剔除）
parallel = true                   # 并行执行（与 --parallel flag 取或）
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает работающее решение без
  настройки
- `exclude` имеет ту же форму, что и `patterns` (буквальный путь или `root/**…`, всегда по префиксу
  пути); excluded означает «не тест» — фикстуры, требующие проверки поведения во время выполнения,
  запускаются напрямую через `yaoxiang run`
- **Однофайловый режим (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации** —
  при явных путях ключи `exclude`/`parallel` не действуют (кроме flag)
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — 纯 YaoXiang 测试断言库（值语义标准形态，2026-09-03 落地）
// 第一个 dogfooding 库：YaoXiang 的测试库用 YaoXiang 写。

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not 与 assert_false 同体；assert_err / assert_err_code 见 §8.1
```

- Функции утверждений работают **через значения**: возвращают `Result(Void, String)`, неудача
  выражается как `Err(диагностика)`, без аварийного завершения процесса — набор тестов из §7
  собирает потестовые вердикты на их основе. Семантика аварийного завершения `std.assert.assert`
  сохраняется для стражей времени выполнения и не входит в путь тестовых утверждений. Полезная
  нагрузка Ok — `Void` (стандартный unit по type-system.md; `()` — пустой Tuple, они не смешиваются
  — зафиксировано 2026-09-03)
- **Семейство из 7 функций (поставлено 2026-09-03, переходная abort-версия удалена)**: на основе
  значений `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (одно тело с
  assert_false, под переодевание `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (утверждение кода ошибки, §8.1)
  - `assert_approx_eq(a: Float, b: Float, eps: Float)` (Фаза 3, поставлено 2026-09-07): проверка
    `|a - b| <= eps`, eps **явно задаётся вызывающим** — допуск является частью контракта теста, без
    скрытых значений по умолчанию; отрицательный eps на месте объявления даёт Err, NaN всегда даёт
    Err
- `assert_eq` / `assert_ne` используют **параметры с аннотацией Any** — `==`/`!=` и интерполяция
  f-string корректно работают на Any и не зависят от системы дженериков. Обратите внимание:
  параметры **должны быть явно аннотированы** — неаннотированные параметры не проходят проверку
  вызова с нативным обобщённым `&Result(T, E)` (подтверждено пробой R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный `not` не
  реализован, после стабилизации возможен переход; унарная форма `!assert` имеет то же ограничение,
  см. §8.1)
- Форма тело-блока + явный `return`: тип then-ветки if-выражения отбрасывается при проверке,
  if-выражение с двумя Result-ветками — слепая зона проверки, в реализации это обходится
- `std.test` не зависит от какого-либо нативного кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевой дизайн)

**Фаза 1: Встраивание в бинарник**

`std/test.yx` (а в будущем и все модули стандартной библиотеки, написанные на YaoXiang) встраивается
в бинарник во время сборки:

```rust
// build.rs 或构建脚本，自动生成
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // 源代码文本
    // 未来更多
];
```

Модульная система (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения:
Registry одновременно содержит нативные модули и исходные модули, orchestrator отвечает за
оркестровку нескольких файлов. Порядок разрешения `use std.test`:

1. Сначала поиск нативного модуля Rust (существующий механизм, например `std.assert`)
2. При отсутствии — поиск во встроенных `STD_YX_FILES` — при попадании исходный модуль инжектируется
   в orchestrator по **виртуальному пути** (например `<std>/test.yx`) как затравочный и проходит
   обычный конвейер фронтенда (parse → typecheck → IR)
3. При отсутствии — обнаружение в файловой системе (модули пользователя)

`use std.assert` внутри встроенного исходного модуля нормально разрешается resolver-ом в нативный
registry — нативные и исходные модули сосуществуют в Registry, кросс-видовая зависимость работает
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импорте.

Преимущества:

- В однофайловом режиме `use std.test` тоже работает
- Версия стандартной библиотеки строго привязана к бинарнику, несоответствие версий невозможно
- Не требуется настраивать путь к стандартной библиотеке

**Будущее: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение проверки 2026-08-02)**: CLI `run` подключается к orchestrator. В настоящее
время CLI `run` использует однофайловый конвейер (`run_file_with_diagnostics`) и не может разрешать
импорты модулей пользователя; модель дочерних процессов `yaoxiang test` наследует возможности CLI, а
импорт файлом тестов проектных модулей — ключевой сценарий. Поэтому в Фазе 1 ветка исходного кода
CLI `Run` сначала делегируется в `run_project` (orchestrator, рекурсивное обнаружение по каталогам);
#247 (обнаружение по `use` по требованию) затем накладывается как чистая оптимизация
производительности. Однофайловый путь без импортов эквивалентен по поведению при прохождении через
orchestrator, ветвь байт-кода не меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению подстроки в имя файла)
5. Область обнаружения — это и есть расслоение тестов (§9): patterns по умолчанию покрывают только
   языковой корпус; уровень тестов библиотек (например `src/std/tests/`) обнаруживается через явные
   пути или конфигурацию пакета, не подмешивается в сканирование по умолчанию

**Этап выполнения**:

1. Для каждого файла выполнение разветвляется по заголовочной директиве (грамматика директив см.
   §8.2, разбирается через `src/util/test_markers.rs`, общий с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run <file>` (начиная с #327 ошибки времени
     выполнения по умолчанию содержат позицию в исходном коде и кадры стека — debug_map генерируется
     по умолчанию, трассировка стека выводит `file:line:col`); объявление `// mode:` задаёт режим
     `--runtime` дочернего процесса
   - Класс отказа компиляции: одношаговый `yaoxiang check <file>`
   - Класс отказа времени выполнения: два шага — `check` (должен пройти) + `run` (должен
     провалиться)
2. Файлы с `// skip: <причина>` пропускаются и учитываются как skipped в отчёте
3. Сравнение вердикта с ожидаемым кодом — по матрице §8.2; ошибка разбора директивы означает
   невыполнение и прямой FAIL (отказ на стадии построения)
4. Захват stdout/stderr для отчёта
5. По умолчанию последовательное выполнение; `--parallel` (или `[tool.test].parallel`) запускает пул
   обработчиков по числу доступных ядер, каждый файл по-прежнему отдельный дочерний процесс —
   skip/invalid обрабатываются предварительно по порядку обнаружения, результаты выполнения потоково
   выводятся по порядку завершения, JSON сортируется по пути (Фаза 3, поставлено 2026-09-07)
6. При `--fail-fast` при первом FAIL немедленно прекращается планирование новых файлов; при
   параллельном режиме файлы в работе дожидаются и учитываются

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- У каждого дочернего процесса собственные Heap, Frame, NativeContext
- Паника в одном тестовом файле не влияет на другие
- Никаких дополнительных механизмов контекста изолированной кучи не требуется
- **Параллельное выполнение (Фаза 3) не расширяет границу изоляции**: рабочий каталог (CWD) дочерних
  процессов разделяется, параллельные тесты не должны занимать файлы с одинаковыми путями внутри CWD
  — тесты с файловым I/O используют уникальные имена файлов и очищают их по завершении

### 7. Набор тестов и множественные тесты (модель значений)

Один тестовый файл может содержать несколько тестов. Внутрифайловая организация (реализовано
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — функция без аргументов, возвращающая `Result(Void, String)`; неудача утверждения
  выражается как `Err` (семейство утверждений через значения из §3), не прерывает процесс —
  последующие тесты выполняются как обычно
- `test.suite` вызывает по очереди и собирает: для не-Ok теста записываются имя и диагностика, для
  Ok — тишина; после прогона при наличии любого Err процесс останавливается через
  `std.assert.assert` с детализацией провала (`N of M test(s) failed` + по строке
  `[FAIL] имя: диагностика`) — код выхода файла не 0 (§5, вердикт не меняется). Здесь abort — это
  страж времени выполнения тестового бинарника, а не путь утверждения; при полном Ok — тихий выход с
  кодом 0
- Тестовые функции верхнего уровня заносятся в список **в форме замыканий**
  (`("name", () => test_fn())`): имя функции верхнего уровня как значение пока не поддерживается
  (ограничение уровня IR, `E3006`) — вызов глобальной функции из тела замыкания не затрагивается
- Runner видит только файл, сканирования на уровне функций не делает: потестовые вердикты полностью
  поступают из сбора внутри набора, внутренняя структура файла для runner прозрачна — принцип
  нулевых изменений компилятора не нарушается
- Явно не применяется: граница catch в процессе (правило 17 ключевых слов); пофункциональный входной
  вызов из runner (только для внутренних сценариев вроде отказа компиляции в §8.2)
- Форма API зафиксирована (2026-09-03, #319):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дублирование имён не
  проверяется (имя используется только для отображения в отчёте); `--filter` фильтрует по имени
  файла и не знает об именах тестов в наборе

### 8. Трёхуровневый дизайн негативных тестов (ожидаемый отказ)

Негативные тесты разнесены по слоям возникновения отказа, каждый на своём месте:

#### 8.1 Знаковый реверс (универсальный, для пользователя)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый отказ обычным утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// 或一句封装（码只存在于 std Error 载体上，E 钉死为 Error）：
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с семейством через значения
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса `not`
  (то же ограничение, что и `cond == false` у `assert_false`)
- Утверждение кода ошибки опирается на то, что значение `Error` несёт машиночитаемое поле `code` —
  реализовано в M4 #323: `Error = { code, message }` (нативное `error_new(code, message)`), чтение
  через `result.unwrap_err(r)` для получения носителя и `result.code(e)` / `result.message(e)` как
  аксессоров (предполагавшиеся на этапе проектирования имена `error_new_with_code`, экспорт констант
  кодов и доступ к полю `err.code` не приняты — в языке нет доступа к полям Struct, константы кодов
  не экспортируются)
- По мере продвижения Result-фикации (#301, #316) операции, которые могут отказать, по одной
  возвращают `Result`; файловые негативные метки в корпусе мигрируют на внутрифайловые утверждения

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это «всё или ничего» для всего файла, невозможно выразить внутри файла «эта строка не
должна компилироваться»; отказы времени выполнения тоже требуют файлового выражения (например, набор
содержит заведомо провальный тест). В заголовке файла **структурированной директивой** объявляется
ожидание, runner выполняет **разветвлённый вердикт** по категории ожидания (разветвление
зафиксировано 2026-09-03; грамматика директив зафиксирована и реализована 2026-09-06).

Грамматика заголовочных директив (`// key: value`, в пределах первых 16 строк, строгое совпадение
токенов):

```text
// expect: compile-error E1002 [E1003 ...]   编译期拒绝测试
// expect: runtime-error E6003 [...]         运行期失败测试
// skip: <原因>                              跳过执行，计入 skipped
// mode: embedded|standard|full              子进程 --runtime 模式（仅 run 步消费）
```

- Отсутствие директивы `expect:` = поведенческий тест. `expect:` — единственное объявление ожидания
  — зафиксировано 2026-09-06: логическая метка `[test:error]` и китайская散文抠码 `预期:` отброшены.
  Логическая метка и строка ожидания — два слабо связанных факта, и удержать их согласованность
  дисциплиной неизбежно разъедется; строгая токенная грамматика на английском позволяет runner-у
  разбирать механически (kind и код — фиксированные токены, любой лишний токен после кода — ошибка
  разбора), ошибка разбора = невыполнение и прямой FAIL — канал тихой деградации при ошибочном
  объявлении директивы отсутствует (отказ на стадии построения)
- **Класс ошибки компиляции**: одношаговый `check` — должен провалиться, причём вывод содержит все
  `[EXXXX]`; успешная компиляция = FAIL (то, что должно было быть сообщено, не сообщено), отказ с
  несовпадением кода = FAIL. Синтаксические ошибки (E1xxx на этапе разбора) и семантические ошибки
  (E2xxx+) не выделяются в отдельные категории — сам ожидаемый код фиксирует стадию
- **Класс ошибки времени выполнения**: двухшаговый вердикт — `check` должен **успешно** пройти
  (безвинна на этапе компиляции), `run` должен провалиться, причём вывод содержит все `[EXXXX]`.
  Падение уже на этапе компиляции = FAIL (ключевое суждение, противоположное классу ошибки
  компиляции, предотвращает пропуск «компиляция случайно прошла, выполнение случайно провалилось»)
- Гомологично с индустрией: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`,
  Clang `expected-error` — все объявляют ожидания в комментариях фикстуры и сравнивают двусторонне
  через harness; они используют построчную привязку, потому что многодиагностическим компиляторам
  нужно различать несколько ожиданий в одном файле, наш компилятор останавливается на первой ошибке
  и выдаёт одну диагностику на файл — файловый уровень гомологичен реальности компилятора; после
  реализации восстановления после ошибки можно добавить в грамматику построчную привязку
  (заголовочные директивы + ожидания на уровне функций в Cranelift filetests — аналогичная гибридная
  форма)
- Известный долг по рендерингу: текущая диагностика на этапе parse выводится в Debug-форме
  (`code: "E0012"` вместо `[E0012]`); сканер кода принимает обе формы; после унификации рендеринга
  диагностики строгая форма будет возвращена
- **Служит только корпусу данного репозитория, не является частью пользовательского тестового
  фреймворка**; соглашение о вердикте между двумя runner-ами закрыто (2026-09-03, #319): yx_runner
  (cargo test) и `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора
  заголовочных директив, соглашение о каталоге 06-compile-errors упразднено. Слой отчёта выдаёт
  счётчики категорий: в человеческой сводке — строка `Categories:`, в JSON-сводке — `by_kind`
  (behavior / compile-error / runtime-error / invalid, skipped учитывается отдельно), к каждому
  файлу прикрепляется `kind`

#### 8.3 Аппаратные отказы времени выполнения (отнесены к Result-фикации)

Никакого отдельного механизма не заводится — операции, которые могут отказать, по направлению языка
возвращают `Result` (#301, #316), и тесты единообразно выражаются через §8.1. Аварийное завершение
на уровне процесса (например, нарушение утверждения, неверный параметр рантайма) по мере
Result-фикации постепенно сворачивается в значения, тестовый фреймворк не предоставляет для него
специальной семантики. (Примечание: помеченный вердикт «ошибка времени выполнения» из §8.2 — это
файловый канал проверки для runner-а **пока ещё не Result-фицируемых операций**, он не противоречит
семантическому направлению данного раздела — последний является конечной точкой, первый — каналом
миграционного периода)

### 9. Расслоение системы тестирования: языковой корпус и тесты библиотек (зафиксировано 2026-09-03)

Тесты делятся на два слоя **по объекту тестирования**, у каждого своё место и свой сопровождающий;
система меток (§8.2) и библиотека утверждений (§3) — общие для обоих слоёв:

**Первый слой: языковой корпус пригодности (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык** — парсер, система типов, модули, конкурентность, владение,
  отказы компиляции, семантика времени выполнения; каталоги организованы по разделам языковой
  спецификации
- std в корпусе выступает только **инструментом утверждений** (`std.assert` / `std.test`), он
  никогда не тестируется — поведение API библиотек не относится к пригодности языка
- Внутри корпус по §8 разветвляется на три класса вердиктов: поведенческие тесты / тесты отказа
  компиляции / тесты отказа времени выполнения

**Второй слой: тесты библиотек (вместе с библиотекой)**

- Объект тестирования — **публичный контракт API библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся **в самом пакете библиотеки**: пакет std — это `src/std/`, его тесты уровня yx лежат
  в `src/std/tests/` (рядом с реализацией; каталог сосуществует с модульными тестами Rust, типы
  файлов не пересекаются); тесты самого `std.test` тоже здесь (тестируем std.test через std.test,
  самозагрузка замыкается)
- Будущие пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (предваряет раскладку тестов в управлении пакетами RFC-014)
- Обнаружение не входит в patterns по умолчанию (по умолчанию `tests/**/*.yx` покрывает только
  языковой слой): уровень тестов библиотек обнаруживается через явный путь
  (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI выполняет иерархически

**Заметка о миграции: миграция завершена (2026-09-06)** — после разбора 19 файлов из прежнего
`tests/yaoxiang/07-std/` все они оказались тестами библиотек (объект тестирования — контракт API
модуля std; роль языковых возможств вроде распространения `?`, автоматического заимствования,
инстанциации дженериков — носитель, а не объект тестирования), целиком перенесены в
`src/std/tests/`, каталог 07-std отменён; yx_runner переведён на обнаружение с двумя корнями
(`tests/yaoxiang/` + `src/std/tests/`), patterns по умолчанию не включают уровень библиотек
(интеграционные тесты закрепляют этот контракт). Языковой корпус отныне не содержит тестов std-API.

## Открытые вопросы

- [x] Корректно ли разрешается ссылка `use std.assert` в `std/test.yx`? — **Решено (2026-08-02)**.
      После реализации модульной системы (RFC-029) нативные и исходные модули сосуществуют в
      Registry, resolver разрешает единообразно, кросс-видовая зависимость работает естественно
- [x] Вносит ли обобщённый `to_string` в `f"..."` в выводе теста новые ограничения типов? — **Решено
      (2026-08-02)**. Подтверждено, что на неаннотированных параметрах (Any) `==`/`!=` и
      интерполяция f-string работают (проверено на Int/String), новые ограничения не вводятся
- [x] Осуществимость параметра `?` для дженериков? — **Решено (2026-08-02)**: синтаксис типа `?` в
      настоящее время не существует (и будет молча проглочен, для этого открыт отдельный issue),
      функции утверждений Фазы 1 используют неаннотированные параметры и не зависят от системы
      дженериков
