# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

В YaoXiang вводятся стандартный фреймворк тестирования — модуль `std.test` и подкоманда CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`; прохождение/сбой
определяется через `std.assert.assert` + код возврата. Модуль `std.test` реализован на чистом
YaoXiang и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не
особенность компилятора — никаких изменений в парсере, IR, байткоде или исполнителе не требуется.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время покрытие тестами в YaoXiang опирается на `#[test]` на стороне Rust и
интеграционные тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. Задача `#117 Покрытие модульными тестами модулей стандартной библиотеки` заблокирована из-за
   отсутствия доступной тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) лишены
   средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения компилятора**: не трогать парсер, IR, байткод, исполнитель
- **Приоритет самостоятельной реализации**: тестовая библиотека пишется на YaoXiang, первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI 层:  yaoxiang test [--filter --fail-fast --json ...]    │
│              │                                               │
│  发现层:    读取 yaoxiang.toml → [tool.test] patterns         │
│              默认: tests/**/*.yx                              │
│              │                                               │
│  执行层:    对每个文件: yaoxiang run <file>                    │
│              检查 exit code → 串行执行                        │
│              │                                               │
│  报告层:    PASS/FAIL → 汇总                                  │
│              支持 --json / --verbose / --fail-fast            │
│                                                              │
│  断言层:    std.test (纯 YaoXiang，自举)                      │
│              底层: std.assert.assert                          │
│              诊断: f"Expected {expected}, got {actual}"       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — не особенность компилятора, а инструмент CLI** — `yaoxiang run` уже
   способен «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводятся сканирование аннотаций `@test`, секция метаданных
   в байткоде, специальная точка входа в исполнителе
3. **Самостоятельная реализация** — модуль `std.test` написан на чистом YaoXiang, в основе лежит
   `std.assert.assert`
4. **Тестовые файлы — обычные файлы `.yx`** — прохождение/сбой определяется по коду возврата

## Подробное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      指定测试文件或目录（默认: 从 yaoxiang.toml 读取，否则 tests/）

Options:
  --filter <NAME>     只跑文件名包含 <NAME> 的测试
  --fail-fast         遇到第一个失败就停止
  --verbose, -v       显示每个测试的详细 stdout/stderr
  --list              只列出测试文件，不跑
  --no-progress       不显示进度条（CI 场景）
  --json              输出 JSON 格式结果（CI 集成用）
```

#### Формат вывода

**Вывод по умолчанию**:

```
Running 5 tests from 3 files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ PASS (0.001s)
tests/string_test.yx ...................... FAIL (0.003s)
  `-- Expected "hello", got "world"
      at tests/string_test.yx:12:5

Results: 2 passed, 1 failed, 0 skipped (0.006s)
```

**Вывод в JSON** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "tests": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/string_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "error": "Expected \"hello\", got \"world\"",
      "exit_code": 1
    }
  ]
}
```

### 2. Конфигурация в yaoxiang.toml

Размещается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# 未来可扩展:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочий вариант без настроек
- Однопроцессный режим (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` сохраняется)

### 3. Модуль std.test (на чистом YaoXiang)

```yaoxiang
// std/test.yx — Pure YaoXiang test assertion library
// First dogfooding library: YaoXiang's test library written in YaoXiang

use std.assert

assert_eq = (a, b) => {
    assert.assert(a == b, f"Expected {b}, got {a}")
}

assert_ne = (a, b) => {
    assert.assert(a != b, f"Expected not equal to {b}, got {a}")
}

assert_true = (cond: Bool) => {
    assert.assert(cond, f"Expected true, got {cond}")
}

assert_false = (cond: Bool) => {
    assert.assert(cond == false, f"Expected false, got {cond}")
}
```

- 4 функции утверждений, все используют `f"..."` для диагностических сообщений
- `assert_eq` / `assert_ne` используют **параметры без аннотаций** (`Any`) — на 2026-08-02
  эмпирически подтверждено: `==`/`!=` и интерполяция f-string работают на Any (проверено на
  Int/String), **без зависимости от системы обобщений**. Когда обобщения будут готовы, аннотации
  можно добавить
- `assert_true` / `assert_false` имеют аннотацию `Bool`; `assert_false` выражает отрицание через
  `cond == false` (унарный синтаксис `not` ожидает авторизации в #251, после стабилизации возможна
  миграция)
- `std.test` не зависит от какого-либо нативного кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраивается в
бинарник на этапе сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // в будущем — больше
];
```

Точку интеграции даёт модульная система (RFC-029, полностью реализована 2026-08-02): реестр
одновременно хранит нативные и исходные модули, оркестратор отвечает за многопроцессную композицию.
Порядок разрешения `use std.test`:

1. Сначала поиск нативного модуля в Rust (существующий механизм, например `std.assert`)
2. Если не найден — поиск во встроенных `STD_YX_FILES`; при попадании модуль инжектируется в
   оркестратор по **виртуальному пути** (например, `<std>/test.yx`) в качестве модуля-затравки и
   проходит штатный внешний конвейер (parse → typecheck → IR)
3. Если не найден — обнаружение через файловую систему (пользовательские модули)

Разрешение `use std.assert` внутри встроенного исходного модуля штатно работает через нативный
реестр — нативные и исходные модули сосуществуют в реестре, межвидовые зависимости выполняются
естественным образом. Встроенные модули **компилируются по требованию**: попадают в конвейер только
при импорте.

Преимущества:

- `use std.test` работает и в однопроцессном режиме
- Версия стандартной библиотеки строго привязана к бинарнику — рассогласование версий исключено
- Пользователю не нужно настраивать пути к стандартной библиотеке

**Будущее: стандартная библиотека в файловой системе**

Когда режим проектов в YaoXiang созреет, стандартная библиотека будет переведена в форму файловой
системы. Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение по итогам ревью 2026-08-02)**: CLI `run` подключается к
оркестратору. В текущем виде CLI `run` использует однопроцессный конвейер
(`run_file_with_diagnostics`) и не способен разрешать импорты пользовательских модулей; а
подпроцессная модель `yaoxiang test` наследует возможности CLI, и импорт модулей проекта из тестовых
файлов — основной сценарий. Поэтому на Фазе 1 ветка исходного кода CLI `Run` сначала делегируется
`run_project` (оркестратор, рекурсивное обнаружение каталогов); #247 (обнаружение по требованию
вдоль use) после этого накладывается как чистая оптимизация производительности. Однопроцессный файл
без импорта через оркестратор ведёт себя эквивалентно, ветка байткода остаётся без изменений.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читаются `patterns` из `[tool.test]` в `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению подстроки в имя файла)

**Этап выполнения**:

1. Для каждого файла запускается подпроцесс: `yaoxiang run --debug-info <file>` (`--debug-info`
   обеспечивает вывод позиции в исходном коде в ошибках времени выполнения — на 2026-08-02
   эмпирически подтверждён вывод `file:line:col` в stack trace)
2. Проверяется код возврата: 0 — PASS, ненулевой — FAIL
3. Захватываются stdout/stderr для отчёта
4. Только последовательное выполнение (Фаза 1), в будущем — `--parallel`
5. При `--fail-fast` останов сразу после первого FAIL

### 6. Изоляция тестов

Изоляция тестов естественным образом обеспечивается межпроцессной границей:

- Каждый тестовый файл выполняется в отдельном подпроцессе
- У каждого подпроцесса собственные куча, кадры и NativeContext
- Паника в одном тестовом файле не влияет на другие
- Дополнительный механизм изолированного контекста кучи не требуется

## Связь с существующими системами

| Компонент                                                   | Связь                                                                                                                            |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Rust `#[test]`                                              | Не трогаем; внутренние тесты компилятора остаются на Rust                                                                        |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются через `yaoxiang test`                                                                               |
| `std.assert.assert(cond)`                                   | Сохраняется; `std.test` опирается на него                                                                                        |
| Модульная система (RFC-029)                                 | Встроенные исходные модули подключаются через реестр/оркестратор; подключение CLI `run` к оркестратору — предварительное условие |
| Рефакторинг `#200` (`io.println` → `assert.assert`)         | Полностью совпадает с направлением `yaoxiang test`                                                                               |
| Аннотации `@`                                               | Не используются; `@test` не вводится                                                                                             |

## Стратегия реализации

### Фаза 1: базовая функциональность

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — делегирование ветки исходного кода CLI `Run` в
  `run_project` (предварительное условие для многопроцессного запуска)
- `src/main.rs` — новая подкоманда `Test`
- `src/std/test.yx` — новый модуль на чистом YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарник
- orchestrator / реестр — поддержка загрузки модулей `.yx` по виртуальному пути из встроенного
  источника
- Разбор конфигурации RFC-015 — секция `[tool.test]`
- Запуск подпроцессов (`--debug-info`) + отчёт

Поставка:

- `yaoxiang test` базово работоспособен
- 4 функции утверждений в `std.test`
- Обнаружение по умолчанию `tests/**/*.yx`
- Последовательное выполнение + формат вывода по умолчанию

### Фаза 2: доработка

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Фаза 3: продвинутые возможности

- Параллельное выполнение `--parallel` (зависит от завершения модели spawn-конкурентности)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции утверждений (например, `assert_approx_eq` для Float)

## Риски и их смягчение

| Риск                                                                | Вероятность | Смягчение                                                                                      |
| ------------------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------- |
| Сбой интерполяции `f"..."` на Any                                   | нет         | Эмпирически подтверждено 2026-08-02 (Int/String работают)                                      |
| Накладные расходы на запуск подпроцессов влияют на скорость тестов  | средняя     | Фаза 1 — последовательное выполнение, приемлемо; Фаза 3 — параллелизм                          |
| Разбор `yaoxiang.toml` отсутствует в текущем CLI                    | низкая      | Простое расширение, не затрагивает базовую функциональность                                    |
| Подключение CLI run к оркестратору вызывает регрессию поведения     | низкая      | Путь однопроцессного файла без импорта эквивалентен; интеграционные тесты оркестратора покрыты |
| Встраивание исходных файлов `.yx` в бинарник увеличивает его размер | низкая      | Размер исходных `.yx` крайне мал, пренебрежимо                                                 |

## Открытые вопросы

- [x] Ссылка `use std.assert` в `std/test.yx` корректно разрешается? — **Решено (2026-08-02)**.
      После реализации модульной системы (RFC-029) нативные и исходные модули сосуществуют в
      реестре, разрешение унифицировано, межвидовые зависимости выполняются естественным образом
- [x] Вводит ли обобщённый `to_string` в `f"..."` новые ограничения типов? — **Решено
      (2026-08-02)**. Эмпирически подтверждено: на параметрах без аннотаций (Any) `==`/`!=` и
      интерполяция f-string работают (проверено на Int/String), новые ограничения не вводятся
- [x] Допустим ли `?` как параметр обобщения? — **Решено (2026-08-02)**: синтаксис типа `?` в
      настоящее время не существует (и молча поглощается, отслеживается отдельным issue); на Фазе 1
      функции утверждений используют параметры без аннотаций и не зависят от системы обобщений
