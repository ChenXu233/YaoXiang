# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного фреймворка тестирования — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные `.yx`-файлы, общий результат
прохождения/провала определяется по коду выхода дочернего процесса; внутри файла поддерживается
несколько тестовых функций — ошибки утверждений выражаются значением `Err` (value-семантика), а
набор (suite) собирает per-test вердикты (§7). Модуль `std.test` реализован на чистом YaoXiang и
является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не особенность
компилятора — никаких изменений в parser, IR, байт-коде или исполнителе не требуется.

## Мотивация

### Зачем нужна среда тестирования?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` на стороне Rust и интеграционные
тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang
2. `#117 Покрытие модульными тестами модулей стандартной библиотеки` заблокировано, так как
   отсутствует доступная тестовая инфраструктура
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) лишены
   средств автоматизации

### Ключевые ограничения

- **Закон 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения компилятора**: не трогать parser, IR, байт-код, исполнитель
- **Приоритет самозагрузки**: тестовая библиотека пишется на YaoXiang — первая dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:  yaoxiang test [--filter --fail-fast --json ...]│
│              │                                               │
│  Уровень обнаружения:  чтение yaoxiang.toml → [tool.test]    │
│              patterns                                       │
│              по умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Уровень выполнения:  для каждого файла:                     │
│              yaoxiang run <file>                              │
│              проверка exit code → последовательное            │
│              выполнение                                      │
│              │                                               │
│  Уровень отчёта:  PASS/FAIL → сводка                         │
│              поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Уровень утверждений:  std.test (чистый YaoXiang,             │
│              самозагрузка)                                   │
│              низкий уровень: std.assert.assert                │
│              диагностика: f"Expected {expected}, got          │
│              {actual}"                                       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — не особенность компилятора, а инструмент CLI** — `yaoxiang run` уже
   умеет «выполнять тесты», `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводится сканирование аннотаций `@test`, сегмент
   метаданных в байт-коде, специальная точка входа исполнителя
3. **Самозагрузка** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности
   предоставляются `std.assert` / `std.result`
4. **Тестовый файл — обычный `.yx`-файл** — файл запускается как дочерний процесс, exit code
   определяет общий результат прохождения/провала
5. **Провал утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, провал утверждения выражается `Err`, suite собирает per-test вердикты (§7); аварийное
   завершение на уровне процесса относится только к runtime-guard'ам, а не к тестовым утверждениям

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [ОПЦИИ] [ПУТИ]

Аргументы:
  [ПУТИ]...         Указанные тестовые файлы или каталоги
                    (по умолчанию: читаются из yaoxiang.toml,
                    иначе tests/)

Опции:
  --filter <ИМЯ>    Запускать только тестовые файлы, имя
                    которых содержит <ИМЯ>
  --fail-fast       Остановиться при первом провале
  --verbose, -v     Показывать подробный stdout/stderr каждого
                    теста
  --list            Только вывести список тестовых файлов,
                    не запускать
  --no-progress     Не выводить прогресс (заголовок и строки
                    PASS); подробности FAIL и сводка
                    сохраняются (для CI)
  --json            Выводить результат в формате JSON
                    (для интеграции с CI)
```

#### Формат вывода

**Стандартный вывод** (per-test вердикты поступают из сбора внутри файлового suite, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
```

**Вывод в JSON** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "files": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файл с провалом дополнительно несёт `exit_code` и `stderr` (диагностика дочернего процесса с
  удалёнными ANSI-кодами, для разбора в CI); при комбинации `--verbose` и `--json` все файлы несут
  `stdout` / `stderr`
- `--no-progress` подавляет только вывод прогресса (заголовок и строки PASS) — подробности FAIL и
  сводка выводятся всегда, провал не может быть скрыт; `--list` выводит по одному пути тестового
  файла на строку без выполнения
- Внутрифайловый массив per-test `tests` поступает из сбора suite согласно §7 и вступает в силу
  вместе с value-моделью (#319)

### 2. Конфигурация yaoxiang.toml

Располагается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях
`[tool.*]` из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# Возможные расширения в будущем:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочий вариант без какой-либо
  настройки
- Режим одного файла (`yaoxiang test foo.yx`) выполняется напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` не меняется)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Pure YaoXiang test assertion library
// First dogfooding library: YaoXiang's test library written in YaoXiang

use std.result

assert_eq = (a, b) => {
    if a == b { result.ok(()) } else { result.err(f"Expected {b}, got {a}") }
}

assert_ne = (a, b) => {
    if a != b { result.ok(()) } else { result.err(f"Expected not equal to {b}, got {a}") }
}

assert_true = (cond: Bool) => {
    if cond { result.ok(()) } else { result.err(f"Expected true, got {cond}") }
}

assert_false = (cond: Bool) => {
    if cond == false { result.ok(()) } else { result.err(f"Expected false, got {cond}") }
}
```

- Функции утверждений имеют **value-семантику**: возвращают `Result((), String)`, провал выражается
  как `Err(диагностическое_сообщение)` и не вызывает аварийное завершение процесса — §7 suite на
  этом основании собирает per-test вердикты. Семантика аварийного завершения `std.assert.assert`
  сохраняется для runtime-guard'ов и не используется в пути тестовых утверждений
- Пояснение о переходе: 4 функции, поставляемые в Phase 1, опираются на `std.assert.assert`
  (семантика abort) и являются переходной реализацией самозагрузки; семейство value-семантики
  представляет стандартную форму настоящего RFC и заменяет их после поставки (#319)
- `assert_eq` / `assert_ne` используют **параметры без аннотаций** (`Any`) — по результатам проверки
  от 2026-08-02 операторы `==`/`!=` и интерполяция f-string корректно работают на `Any` (проверено
  для Int/String) и **не зависят от системы дженериков**. После готовности дженериков аннотации
  могут быть добавлены
- `assert_false` использует форму `cond == false` для отрицания (унарный синтаксис `not` ещё не
  реализован и может быть перенесён после стабилизации; унарная форма `!assert` имеет ту же
  зависимость, см. §8.1)
- Утверждения кода ошибки (`assert(err.code == "E3017")`) зависят от того, что значение `Error`
  несёт машиночитаемое поле `code` (§8.1)
- `std.test` не зависит от какого-либо нативного кода и полностью реализован на YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Phase 1: Встраивание в бинарник**

`std/test.yx` (а в будущем — все модули стандартной библиотеки, написанные на YaoXiang) встраиваются
в бинарник на этапе сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // в будущем — больше
];
```

Точкой подключения служит модульная система (RFC-029, полностью реализована к 2026-08-02): Registry
одновременно содержит нативные и исходные модули, orchestrator отвечает за оркестровку нескольких
файлов. Порядок разрешения `use std.test`:

1. Сначала поиск нативного модуля на стороне Rust (существующий механизм, например `std.assert`)
2. При отсутствии — поиск во встроенных `STD_YX_FILES` — при попадании модуль инжектируется в
   orchestrator по **виртуальному пути** (например, `<std>/test.yx`) как зерно и проходит
   стандартный front-end конвейер (parse → typecheck → IR)
3. При отсутствии — обнаружение в файловой системе (пользовательские модули)

Внутренний `use std.assert` встроенного исходного модуля нормально разрешается resolver'ом в
нативный registry — нативные и исходные модули сосуществуют в Registry, межвидовые зависимости
работают естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только
при импортировании.

Преимущества:

- Режим одного файла также поддерживает `use std.test`
- Версия стандартной библиотеки строго привязана к бинарнику — рассинхронизации версий не будет
- Пользователю не нужно настраивать пути к стандартной библиотеке

**Будущее: Файловая стандартная библиотека**

Когда проектный режим YaoXiang будет成熟的, стандартная библиотека перейдёт на файловую форму.
Подробности см. в обновлениях RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение от 2026-08-02)**: CLI `run` подключается к orchestrator. В
настоящее время CLI `run` идёт по однfile-конвейеру (`run_file_with_diagnostics`) и не может
разрешать импорты пользовательских модулей; но модель дочерних процессов `yaoxiang test` наследует
возможности CLI, и импорт тестовыми файлами модулей проекта — основной сценарий. Поэтому в Phase 1
исходная ветвь CLI `Run` сначала делегируется в `run_project` (orchestrator, рекурсивное обнаружение
по каталогу); #247 (обнаружение по `use` по требованию) после этого накладывается как чистая
оптимизация производительности. Однофайловый путь без импортов поведенчески эквивалентен через
orchestrator, ветвь байт-кода не меняется.

**Фаза обнаружения**:

1. Если указаны `[ПУТИ]`, используются они напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению в имя файла)

**Фаза выполнения**:

1. Для каждого файла запускается дочерний процесс `yaoxiang run --debug-info <file>` (благодаря
   `--debug-info` ошибки рантайма содержат позиции в исходном коде — по проверке от 2026-08-02 stack
   trace выводит `file:line:col`)
2. Проверяется exit code: 0 — PASS, ненулевой — FAIL
3. Захватываются stdout/stderr для отчёта
4. Выполнение только последовательное (Phase 1), в будущем возможен `--parallel`
5. При `--fail-fast` остановка сразу после первого FAIL

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- У каждого дочернего процесса — собственные Heap, Frame, NativeContext
- Паника в одном тестовом файле не влияет на другие тестовые файлы
- Никакого дополнительного механизма изоляции Heap не требуется

### 7. Suite и множественные тесты (value-модель)

Один тестовый файл может содержать несколько тестов. Внутрифайловое устройство:

```yaoxiang
// tests/list_test.yx
use std.test
use std.list

push_grows_len = () => {
    xs = []
    list.append(xs, 1)
    test.assert_eq(list.len(xs), 1)
}

pop_returns_last = () => {
    xs = [1, 2]
    test.assert_eq(list.pop(xs), 2)
}

main = {
    test.suite([
        ("push_grows_len", push_grows_len),
        ("pop_returns_last", pop_returns_last),
    ])
}
```

- Каждый тест — функция без аргументов, возвращающая `Result((), String)`; провалы утверждений
  выражаются `Err` (семейство value-семантики §3) и не прерывают процесс — последующие тесты
  выполняются как обычно
- `test.suite` вызывает каждую функцию и собирает результаты: для не-Ok печатает имя теста и
  диагностическое сообщение, для Ok — молча
- Exit code файла: все тесты в suite Ok → 0; любой Err → ненулевой (правило проверки exit code из §5
  фазы выполнения остаётся)
- Runner видит только файл, не выполняет сканирования на уровне функций: per-test вердикты полностью
  поступают из сбора внутри suite, внутренняя структура файла прозрачна для runner'а — принцип
  нулевых изменений компилятора не нарушается
- Явно не применяются: внутрипроцессные catch-границы (закон 17 ключевых слов); поэлементный вход в
  функции со стороны runner'а (допустимо только во внутренних сценариях вроде §8.2 — ошибка
  компиляции)
- Конкретный API-формы `test.suite` (сигнатура, обработка повторяющихся имён, взаимодействие
  `--filter` с именами suite) — деталь реализации, финализируется в #319

### 8. Трёхуровневое проектирование отрицательных тестов (ожидаемый провал)

Отрицательные тесты распределяются по слоям возникновения провала, каждый слой занимает своё место:

#### 8.1 Value-уровень: инверсия (универсально, для пользователя)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый провал обычным утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
test.assert_eq(result.err_code(r), "E3017")
```

- В std.test добавляется семейство функций `assert_not` / `assert_err`; унарная форма `!assert`
  будет предоставлена после реализации синтаксиса `not` (то же ограничение, что и у `assert_false` с
  `cond == false`)
- Утверждения кода ошибки зависят от расширения значения `Error` машиночитаемым полем `code`: с
  `Struct { message }` до `{ code, message }` (нативный `error_new_with_code`, экспортируемые
  std-константы кодов), чтобы было возможно `err.code == "E3017"`
- По мере продвижения Result-изации (#301, #316) операции, которые могут провалиться, одна за другой
  возвращают `Result`, а файловые отрицательные маркеры в корпусе переносятся во внутрифайловые
  утверждения

#### 8.2 Провал компиляции (только для внутреннего использования разработчиками языка)

Компиляция — всё или ничего для всего файла, «эта строка не должна компилироваться» внутри файла
выразить нельзя. Сохраняется файловый специальный маркер:

- Маркер `[test:error]` читается runner'ом и инвертирует вердикт (run-процесс завершился с ненулевым
  кодом = PASS)
- Маркер обновляется до **структурированного кода ожидания**: runner разбирает в заголовке
  `预期: 编译错误 EXXXX` (ожидаемая ошибка EXXXX) и сравнивает с реальным `[EXXXX]`, который
  компилятор выводит в stderr; несовпадение кода = FAIL (лёгкая версия идеи trybuild-снапшотов
  stderr, без изменений компилятора)
- **Служит только корпусу настоящего репозитория, не является частью пользовательского фреймворка
  тестирования**; на стороне реализации необходимо унифицировать соглашения о двойном суждении
  runner'а (соглашение каталога vs заголовок), см. #319

#### 8.3 Жёсткий провал рантайма (относится к Result-изации)

Отдельный механизм не предусмотрен — операции, которые могут провалиться, по направлению языка
возвращают `Result` (#301, #316), тесты единообразно выражаются через §8.1. Аварийное завершение на
уровне процесса (например, нарушение утверждения, ошибка параметров рантайма) постепенно
сворачивается в значение по мере Result-изации; тестовый фреймворк не предоставляет для него
специальной семантики.

| Rust `#[test]`                                              | Не трогается, внутренние тесты компилятора остаются на Rust                                                                         |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются `yaoxiang test`                                                                                        |
| `std.assert.assert(cond)`                                   | Сохраняется для runtime-guard'ов; семейство value-семантики `std.test` переводится на `std.result` (§3, §7)                         |
| Модульная система (RFC-029)                                 | Встроенные исходные модули подключаются через Registry/orchestrator; подключение CLI `run` к orchestrator — предварительное условие |
| `#200` рефакторинг (`io.println` → `assert.assert`)         | Полностью соответствует направлению `yaoxiang test`                                                                                 |
| Аннотации `@`                                               | Не используются, `@test` не вводится                                                                                                |

## Стратегия реализации

### Phase 1: Основная функциональность

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — делегирование исходной ветви CLI `Run` в
  `run_project` (предварительное условие для многофайлового запуска)
- `src/main.rs` — новая подкоманда `Test`
- `src/std/test.yx` — новый модуль на чистом YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарник
- orchestrator / Registry — поддержка загрузки `.yx`-модулей из встроенного источника по
  виртуальному пути
- Разбор конфигурации RFC-015 — секция `[tool.test]`
- Выполнение в дочернем процессе (`--debug-info`) + отчёт

Поставка:

- `yaoxiang test` базово работает
- 4 функции утверждений в `std.test`
- Обнаружение по умолчанию `tests/**/*.yx`
- Последовательное выполнение + формат вывода по умолчанию

### Phase 2: Доработка

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Phase 3: Продвинутый уровень

- Параллельное выполнение `--parallel` (зависит от доработки модели конкурентности spawn)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции утверждений (например, `assert_approx_eq` для Float)

## Риски и их снижение

| Риск                                                        | Вероятность | Снижение                                                                                                                                                                                                                                       |
| ----------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `f"..."` не интерполирует на Any                            | Нет         | Проверено 2026-08-02 (Int/String работают)                                                                                                                                                                                                     |
| Разбор `yaoxiang.toml` не встроен в текущий CLI             | Низкая      | Простое расширение, не затрагивает ядро                                                                                                                                                                                                        |
| Подключение CLI run к orchestrator вносит регресс поведения | Низкая      | Однофайловый путь без импорта эквивалентен; интеграционные тесты покрывают orchestrator                                                                                                                                                        |
| Встраивание `.yx`-исходников в бинарник увеличивает размер  | Низкая      | `.yx`-исходники очень малы, пренебрежимо                                                                                                                                                                                                       |
| Время тестового цикла растёт с ростом корпуса               | Высокая     | Основной вклад — полная компиляция каждого файла (185 файлов — 11.3 с по замерам), а не запуск дочернего процесса; `--parallel` снимает только процессную сторону, затраты на компиляцию требуют кеширования тестового цикла (срезы #251/#293) |

## Открытые вопросы

- [x] Корректно ли разрешается ссылка `use std.assert` в `std/test.yx`? — **Решено (2026-08-02)**.
      После реализации модульной системы (RFC-029) нативные и исходные модули сосуществуют в
      Registry, resolver разрешает их единообразно, межвидовые зависимости работают естественно
- [x] Вводит ли дженерик `to_string` в `f"..."` в тестовом выводе новое ограничение типов? —
      **Решено (2026-08-02)**. Проверено, что на параметрах без аннотаций (Any) `==`/`!=` и
      интерполяция f-string работают (проверено для Int/String), новые ограничения не вводятся
- [x] Возможен ли дженерик-параметр `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в настоящее
      время не существует (и будет молча проглатываться, заведён отдельный issue), функции
      утверждений Phase 1 используют параметры без аннотаций и не зависят от системы дженериков
