# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Сводка

Вводит для YaoXiang стандартный тестовый фреймворк — модуль `std.test` и подкоманду CLI
`yaoxiang test`. Тестовые файлы — обычные файлы `.yx`, общий результат pass/fail определяется кодом
выхода подпроцесса; внутри файла поддерживается несколько тестовых функций — сбой утверждения
выражается значением `Err` (семантика значений), набор собирает per-test решения (§7). Модуль
`std.test` реализован на чистом YaoXiang и является первой dogfooding-библиотекой. `yaoxiang test` —
это инструмент CLI, а не возможность компилятора — никаких изменений в parser, IR, байт-коде или
исполнителе не требуется.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время покрытие тестами YaoXiang опирается на `#[test]` со стороны Rust и интеграционные
тесты в `tests/`. Это означает:

1. Юнит-тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. Задача `#117 Покрытие юнит-тестами модулей стандартной библиотеки` заблокирована из-за отсутствия
   доступной тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) не
   имеют средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения компилятора**: не трогать parser, IR, байт-код, исполнитель
- **Приоритет bootstrap**: тестовая библиотека пишется на YaoXiang — первая dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI 层:  yaoxiang test [--filter --fail-fast --json ...]    │
│              │                                               │
│  发现层:    读取 yaoxiang.toml → [tool.test] patterns         │
│              默认: tests/**/*.yx                              │
│              │                                               │
│  执行层:    对每个文件: yaoxiang run <file>                    │
│              检查 exit code → 串行执行                        │
│              │                                               │
│  报告层:    PASS/FAIL → 汇总                                  │
│              支持 --json / --verbose / --fail-fast            │
│                                                              │
│  断言层:    std.test (纯 YaoXiang，自举)                      │
│              底层: std.assert.assert                          │
│              诊断: f"Expected {expected}, got {actual}"       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — это не возможность компилятора, а инструмент CLI** — `yaoxiang run` уже
   способен «выполнять тесты»; `yaoxiang test` лишь запускает все файлы и показывает отчёт
2. **Нулевые изменения компилятора** — не вводятся сканирование аннотаций `@test`, секции метаданных
   в байт-коде, специальные точки входа в исполнителе
3. **Bootstrap** — модуль `std.test` реализован на чистом YaoXiang; базовые возможности опираются на
   `std.assert` / `std.result`
4. **Тестовый файл — обычный файл `.yx`** — файл выполняется как подпроцесс, общий pass/fail
   определяется кодом выхода
5. **Сбой утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, сбой утверждения выражается как `Err`, набор собирает решения по каждому тесту (§7);
   process-level abort относится только к runtime-стражам, а не к тестовым утверждениям

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      指定测试文件或目录（默认: 从 yaoxiang.toml 读取，否则 tests/）

Options:
  --filter <NAME>     只跑文件名包含 <NAME> 的测试
  --fail-fast         遇到第一个失败就停止
  --verbose, -v       显示每个测试的详细 stdout/stderr
  --list              只列出测试文件，不跑
  --no-progress       不显示进度输出（表头与 PASS 行）；FAIL 明细与汇总保留（CI 场景）
  --json              输出 JSON 格式结果（CI 集成用）
```

#### Формат вывода

**Стандартный вывод** (per-test решения собираются набором внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
```

**JSON-вывод** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "files": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Для упавших файлов дополнительно передаются `exit_code` и `stderr` (диагностика подпроцесса с
  удалёнными ANSI-кодами — для форензики в CI); при комбинации `--verbose` и `--json` все файлы
  получают `stdout` / `stderr`
- `--no-progress` подавляет только прогресс-вывод (заголовок и строки PASS) — детали FAIL и сводка
  всегда выводятся: сбой не может пройти молча; `--list` выводит по одной строке на путь тестового
  файла без выполнения
- Массив per-test `tests` внутри файла поступает из сбора набором §7 и вступает в силу по мере
  реализации модели на значениях (#319)

### 2. Конфигурация в yaoxiang.toml

Располагается в секции `[tool.test]` в соответствии с соглашением о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# 未来可扩展:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочий вариант без какой-либо
  настройки
- Одиночный режим файла (`yaoxiang test foo.yx`) запускает его напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` сохраняется)

### 3. Модуль `std.test` (чистый YaoXiang)

```yaoxiang
// std/test.yx — 纯 YaoXiang 测试断言库（值语义标准形态，2026-09-03 落地）
// 第一个 dogfooding 库：YaoXiang 的测试库用 YaoXiang 写。

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not 与 assert_false 同体；assert_err / assert_err_code 见 §8.1
```

- Функции утверждений имеют **семантику значений**: возвращают `Result(Void, String)`; сбой
  выражается как `Err(диагностическое_сообщение)`, процесс не аварийно завершается — набор §7
  собирает per-test решения на этой основе. process-level abort в `std.assert.assert` сохраняется
  для runtime-стражей и не используется на пути тестовых утверждений. Полезная нагрузка Ok — `Void`
  (согласно type-system.md, это unit; `()` — пустой Tuple, эти два не смешиваются — зафиксировано
  2026-09-03)
- **Семейство из 7 функций (поставлено 2026-09-03, переходная версия с abort удалена)**: value-based
  `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (синоним `assert_false`,
  зарезервировано для будущей формы `!assert`)
  - `assert_err` (§8.1)
  - `assert_err_code` (утверждение по коду ошибки из §8.1)
- `assert_eq` / `assert_ne` используют аннотацию параметров **Any** — `==`/`!=` и интерполяция в
  f-string корректно работают на Any и не зависят от системы дженериков. Обратите внимание, что
  **аннотация параметров обязательна**: неаннотированные параметры не проходят проверку вызова
  native-дженерика `&Result(T, E)` (подтверждено зондом R1)
- `assert_false` / `assert_not` используют форму `cond == false` для инверсии (унарный синтаксис
  `not` ещё не реализован; после стабилизации возможна миграция; унарная форма `!assert` зависит от
  того же, см. §8.1)
- Форма с телом блока и явным `return`: тип then-ветки if-выражения отбрасывается при проверке, а
  совместимость if-выражения с Result в обеих ветках — слепая зона проверки; реализация обходит её
- `std.test` не зависит ни от какого native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраиваются в
бинарник во время сборки:

```rust
// build.rs 或构建脚本，自动生成
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // 源代码文本
    // 未来更多
];
```

Точкой подключения служит система модулей (RFC-029, полностью реализована 2026-08-02): Registry
одновременно хранит native-модули и исходные модули, за оркестрацию многофайловой работы отвечает
orchestrator. Порядок разрешения для `use std.test`:

1. Сначала поиск среди native-модулей Rust (текущий механизм, например `std.assert`)
2. При отсутствии — поиск среди встроенных `STD_YX_FILES` — при совпадении модуль внедряется в
   orchestrator по **виртуальному пути** (например, `<std>/test.yx`) в качестве начального и
   проходит стандартный конвейер front-end (parse → typecheck → IR)
3. При отсутствии — обнаружение в файловой системе (пользовательский модуль)

`use std.assert` внутри встроенного исходного модуля нормально разрешается resolver'ом в
native-registry — native и исходные модули сосуществуют в Registry, кросс-видовая зависимость
работает естественно. Встроенные модули **компилируются по требованию**: в конвейер они попадают
только при импортировании.

Преимущества:

- В одиночном режиме файла `use std.test` тоже работает
- Версия стандартной библиотеки строго привязана к бинарнику — рассогласование версий исключено
- Пользователю не нужно настраивать пути к стандартной библиотеке

**Будущее: файловая стандартная библиотека**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение ревью 2026-08-02)**: CLI `run` подключается к orchestrator. В настоящий
момент CLI `run` использует однопроходный конвейер (`run_file_with_diagnostics`) и не может
разрешать импорты пользовательских модулей; однако модель подпроцессов `yaoxiang test` наследует
возможности CLI, а импорт проектных модулей из тестовых файлов — ключевой сценарий. Поэтому на Фазе
1 сначала исходная ветка CLI `Run` делегируется в `run_project` (orchestrator, рекурсивное
обнаружение по каталогам); #247 (обнаружение по `use` по требованию) после этого укладывается как
чистая оптимизация производительности. Одиночный файл без импортов через orchestrator ведёт себя
эквивалентно, ветка байт-кода не меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читаются `patterns` из `[tool.test]` в `yaoxiang.toml`
3. При отсутствии конфигурации — по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению подстроки в имя файла)
5. Область обнаружения — это и есть слои тестирования (§9): patterns по умолчанию покрывают только
   языковой корпус; слой тестов библиотек (например, `src/std/tests/`) обнаруживается через явный
   путь или конфигурацию пакета и не подмешивается в сканирование по умолчанию

**Этап выполнения**:

1. Для каждого файла: запуск подпроцесса `yaoxiang run --debug-info <file>` (с `--debug-info` ошибки
   runtime содержат позиции в исходнике — 2026-08-02 подтверждено, что stack trace выдаёт
   `file:line:col`); заголовок `[test:runtime]` объявляет режим `--runtime` подпроцесса
   (зафиксировано 2026-09-03)
2. Файлы с заголовком `[test:ignore]: <причина>` пропускаются и учитываются как `skipped` в отчёте
   (зафиксировано 2026-09-03)
3. Проверяется код выхода: 0 — PASS, ненулевой — FAIL; для файлов `[test:error]` применяется
   обратное решение с проверкой ожидаемого кода согласно §8.2
4. Захватываются stdout/stderr для отчёта
5. Пока только последовательное выполнение (Фаза 1), в будущем — `--parallel`
6. При `--fail-fast` — остановка на первом FAIL

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процессов:

- Каждый тестовый файл выполняется в отдельном подпроцессе
- Каждый подпроцесс имеет собственный Heap, Frame, NativeContext
- Паника в одном тестовом файле не влияет на другие
- Дополнительный механизм изолированного контекста Heap не требуется

### 7. Набор тестов и множество тестов (модель на значениях)

Тестовый файл может содержать несколько тестов. Способ организации внутри файла (реализовано
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — это функция без параметров, возвращающая `Result(Void, String)`; сбой утверждения
  выражается как `Err` (семейство утверждений на значениях из §3) и не прерывает процесс —
  последующие тесты продолжают выполняться
- `test.suite` вызывает по очереди и собирает результаты: если результат теста — не Ok, фиксируются
  имя и диагностика; Ok — молчание; после прохождения всех тестов при наличии любого Err процесс
  аварийно завершается через `std.assert.assert` с детализацией (`N of M test(s) failed` + по строке
  `[FAIL] имя: диагностика`) — код выхода файла ненулевой (правило §5 не меняется). Этот abort —
  runtime-страж тестового бинарника, а не путь утверждения; при всех Ok — тихий выход с кодом 0
- Тестовые функции верхнего уровня вносятся в список **в форме замыканий**
  (`("name", () => test_fn())`): ссылка на имя функции верхнего уровня как на значение пока не
  поддерживается (ограничение IR, `E3006`) — вызов глобальной функции из тела замыкания работает без
  ограничений
- Runner видит только файл и не выполняет сканирования на уровне функций: per-test решения полностью
  поступают из сбора внутри набора, внутренняя структура файла прозрачна для runner — принцип
  нулевых изменений компилятора не нарушается
- Явно не принято: граница catch внутри процесса (железное правило 17 ключевых слов); покастовый
  вход runner в каждую функцию (только внутренние сценарии §8.2)
- Форма API зафиксирована (2026-09-03, #319):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дубликаты имён не
  обнаруживаются (имя служит только для отчёта); `--filter` фильтрует по имени файла, не зная имён
  тестов внутри набора

### 8. Трёхуровневое проектирование негативных тестов (ожидаемый сбой)

Негативные тесты разнесены по слоям, на которых происходит сбой:

#### 8.1 Обращение на уровне значений (универсально, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый сбой обычным утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// 或一句封装（码只存在于 std Error 载体上，E 钉死为 Error）：
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с семейством на значениях
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса `not`
  (то же ограничение, что и `cond == false` в `assert_false`)
- Утверждение по коду ошибки опирается на то, что значение `Error` несёт машиночитаемое поле `code`
  — реализовано в M4 задачи #323: `Error = { code, message }` (native `error_new(code, message)`);
  чтение — через `result.unwrap_err(r)` для получения носителя + аксессоры `result.code(e)` /
  `result.message(e)` (предполагавшиеся на этапе проектирования имена `error_new_with_code`, экспорт
  констант кодов и доступ к полю `err.code` не приняты — в языке нет доступа к полям Struct,
  константы кодов не экспортируются)
- По мере продвижения Result-изации (#301, #316) операции, которые могут завершиться сбоем, по одной
  начинают возвращать `Result`; файловые негативные метки в корпусе переводятся в файловые
  утверждения

#### 8.2 Файловые негативные метки (только для внутреннего использования разработчиками языка)

Компиляция — всё или ничего на уровне файла, выразить «эта строка не должна компилироваться» внутри
файла невозможно; сбой на этапе выполнения также требует файлового выражения (например, набор
содержит тесты, которые обязаны падать). Сохраняются файловые специальные метки, runner **разделяет
решение по ожидаемой категории** (зафиксировано 2026-09-03, реализация в работе):

- Метка `[test:error]` читается runner'ом; строка `预期: 编译错误 EXXXX` / `预期: 运行时错误 EXXXX`
  объявляет категорию и ожидаемый код
- **Категория ошибки компиляции**: runner запускает `yaoxiang check` — должен завершиться сбоем, и в
  выводе должен присутствовать `[EXXXX]`; прохождение компиляции = FAIL, отказ без совпадения кода =
  FAIL. Отдельные категории для синтаксических (E1xxx, секция парсера) и семантических (E2xxx+)
  ошибок не выделяются — сам ожидаемый код фиксирует стадию
- **Категория ошибки выполнения**: двухшаговое решение — `check` обязан **успешно** пройти
  (compile-time ни при чём), `run` обязан упасть, и в выводе должен быть `[EXXXX]`. Сбой уже на
  compile-time = FAIL (ключевое правило, противоположное категории ошибки компиляции; защита от
  пропуска случаев «компиляция случайно прошла, выполнение случайно упало»)
- `[test:error]` без строки `预期:` откатывается к решению по exit≠0 (неклассифицированная форма,
  для нового корпуса не поощряется)
- **Служит только корпусу данного репозитория, не часть пользовательского тестового фреймворка**;
  соглашение о двух runner'ах зафиксировано (2026-09-03, #319): yx_runner (cargo test) и
  `yaoxiang test` совместно используют парсер `src/util/test_markers.rs` для разбора заголовков
  (`[test:error]`/`[test:ignore]`/`[test:runtime]`/`预期: EXXXX`, первые 16 строк); соглашение о
  каталоге `06-compile-errors` упразднено. После реализации разнесённого решения слой отчёта также
  выдаёт счётчики по категориям (behavior / compile-error / runtime-error / skipped)

#### 8.3 Аппаратные сбои выполнения (относятся к Result-изации)

Отдельный механизм не предусмотрен — операции, которые могут упасть, по направлению языка возвращают
`Result` (#301, #316), и тесты единообразно выражаются через §8.1. process-level abort (например,
нарушение утверждения, ошибка параметров runtime) по мере Result-изации постепенно сворачивается в
значение; тестовый фреймворк для них не предоставляет специальной семантики. (Замечание: метка
«ошибка выполнения» в §8.2 — это runner'овский канал файловой проверки **для операций, которые пока
нельзя Result-изировать**, что не противоречит семантическому направлению данного раздела —
последний является конечной точкой, а первый — переходным каналом)

### 9. Слои тестовой системы: языковой корпус и тесты библиотек (зафиксировано 2026-09-03)

Тесты делятся на **два слоя по объекту тестирования**, у каждого своя принадлежность и
сопровождающие; система меток (§8.2) и библиотека утверждений (§3) — общие для обоих слоёв:

**Слой первый: языковой корпус пригодности (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык**: парсер, type system, модули, конкурентность, ownership, отказы
  на compile-time, семантика runtime; структура каталогов соответствует разделам языковой
  спецификации
- std в корпусе выступает только как **инструмент утверждений** (`std.assert` / `std.test`) и
  никогда не тестируется — API-поведение библиотеки не относится к пригодности языка
- Внутри корпуса по §8 решения делятся на три категории: поведенческие тесты, compile-time отказы,
  runtime сбои

**Слой второй: тесты библиотек (живут рядом с библиотекой)**

- Объект тестирования — **публичный API-контракт библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся **в пакете самой библиотеки**: пакет std — это `src/std/`, его yx-уровневые тесты
  относятся к `src/std/tests/` (рядом с реализацией); тесты самого `std.test` тоже там (тестируем
  std.test через std.test — самозамыкание)
- В будущем пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (что является репетицией раскладки тестов из RFC-014 по управлению
  пакетами)
- В patterns по умолчанию этот слой не попадает (дефолт `tests/**/*.yx` покрывает только языковой
  слой): слой тестов библиотек обнаруживается по явному пути (`yaoxiang test src/std/tests`) или
  через конфигурацию пакета; CI запускает слои раздельно

Заметка о миграции: библиотечные тесты, ныне расположенные в `tests/yaoxiang/07-std/`, по данной
модели переносятся в `src/std/tests/`; при миграции каждый случай разбирается индивидуально — тесты
чистого API-поведения уезжают, те, чей объект — граница языка (например, native-автозаимствование
`&T`), остаются в корпусе и относятся к соответствующему разделу спецификации.

## Открытые вопросы

- [x] Корректно ли разрешается ссылка `use std.assert` в `std/test.yx`? — **Решено (2026-08-02)**.
      После реализации системы модулей (RFC-029) native и исходные модули сосуществуют в Registry,
      resolver разрешает их единообразно, кросс-видовые зависимости работают естественно
- [x] Вносит ли дженерик-`to_string` в `f"..."` новые ограничения типов? — **Решено (2026-08-02)**.
      Подтверждено, что на неаннотированных параметрах (Any) `==`/`!=` и интерполяция f-string
      работают (проверено на Int/String), новые ограничения не вводятся
- [x] Возможен ли параметр-дженерик `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в настоящий
      момент не существует (и будет молча проглатываться, под него заведён отдельный issue); функции
      утверждений Фазы 1 используют неаннотированные параметры и не зависят от системы дженериков
