# RFC-036: Тестовый фреймворк std.test и команда yaoxiang test

## Резюме

В YaoXiang вводятся стандартный тестовый фреймворк — модуль `std.test` и подкоманда CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные `.yx`-файлы, прохождение/провал
определяется через `std.assert.assert` и код выхода. Модуль `std.test` реализован на чистом YaoXiang
и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не функция
компилятора: никаких изменений в парсере, IR, байткоде или исполнителе не требуется.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` со стороны Rust и интеграционные
тесты в `tests/`. Это означает, что:

1. Модульные тесты для стандартной библиотеки (std.math / std.list / std.dict / std.convert /
   std.io) невозможно писать на YaoXiang
2. Задача `#117 Модульное тестовое покрытие для модулей стандартной библиотеки` заблокирована из-за
   отсутствия доступной тестовой инфраструктуры
3. У регрессионных тестов языковых возможностей (например, изменение семантики spawn в RFC-032) нет
   средств автоматизации

### Ключевые ограничения

- **Непреложное правило 17 ключевых слов**: никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения в компиляторе**: парсер, IR, байткод и исполнитель не затрагиваются
- **Приоритет самобутстрапа**: тестовая библиотека пишется на YaoXiang — первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI 层:  yaoxiang test [--filter --fail-fast --json ...]    │
│              │                                               │
│  发现层:    读取 yaoxiang.toml → [tool.test] patterns         │
│              默认: tests/**/*.yx                              │
│              │                                               │
│  执行层:    对每个文件: yaoxiang run <file>                    │
│              检查 exit code → 串行执行                        │
│              │                                               │
│  报告层:    PASS/FAIL → 汇总                                  │
│              支持 --json / --verbose / --fail-fast            │
│                                                              │
│  断言层:    std.test (纯 YaoXiang，自举)                      │
│              底层: std.assert.assert                          │
│              诊断: f"Expected {expected}, got {actual}"       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — не функция компилятора, а инструмент CLI** — `yaoxiang run` уже способен
   «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения в компиляторе** — не вводятся сканирование аннотаций `@test`, секции
   метаданных в байткоде, специальные точки входа в исполнитель
3. **Самобутстрап** — модуль `std.test` реализован на чистом YaoXiang, опирается на
   `std.assert.assert`
4. **Тестовые файлы — обычные `.yx`-файлы** — прохождение/провал определяется по коду выхода

## Подробное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      指定测试文件或目录（默认: 从 yaoxiang.toml 读取，否则 tests/）

Options:
  --filter <NAME>     只跑文件名包含 <NAME> 的测试
  --fail-fast         遇到第一个失败就停止
  --verbose, -v       显示每个测试的详细 stdout/stderr
  --list              只列出测试文件，不跑
  --no-progress       不显示进度条（CI 场景）
  --json              输出 JSON 格式结果（CI 集成用）
```

#### Формат вывода

**Вывод по умолчанию**:

```
Running 5 tests from 3 files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ PASS (0.001s)
tests/string_test.yx ...................... FAIL (0.003s)
  `-- Expected "hello", got "world"
      at tests/string_test.yx:12:5

Results: 2 passed, 1 failed, 0 skipped (0.006s)
```

**JSON-вывод** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "tests": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/string_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "error": "Expected \"hello\", got \"world\"",
      "exit_code": 1
    }
  ]
}
```

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]` в соответствии с соглашением о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# 未来可扩展:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает работающее решение без
  какой-либо настройки
- В режиме одиночного файла (`yaoxiang test foo.yx`) конфигурация не читается
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` не изменится)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Pure YaoXiang test assertion library
// First dogfooding library: YaoXiang's test library written in YaoXiang

use std.assert

assert_eq = (a, b) => {
    assert.assert(a == b, f"Expected {b}, got {a}")
}

assert_ne = (a, b) => {
    assert.assert(a != b, f"Expected not equal to {b}, got {a}")
}

assert_true = (cond: Bool) => {
    assert.assert(cond, f"Expected true, got {cond}")
}

assert_false = (cond: Bool) => {
    assert.assert(cond == false, f"Expected false, got {cond}")
}
```

- 4 функции-утверждения, все используют `f"..."` для диагностических сообщений
- `assert_eq` / `assert_ne` используют **параметры без аннотации** (`Any`) — по эмпирическим данным
  от 2026-08-02: `==`/`!=` и интерполяция f-string корректно работают на Any (проверено на
  Int/String), **не зависят от системы типов**. Когда generics будут готовы, аннотации можно будет
  добавить
- `assert_true` / `assert_false` имеют аннотацию `Bool`; в `assert_false` отрицание выражается через
  `cond == false` (унарный синтаксис `not` утверждается в #251, после стабилизации можно будет
  перевести)
- `std.test` не зависит от какого-либо native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое проектирование)

**Фаза 1: встраивание в бинарный файл**

`std/test.yx` (а также все будущие модули стандартной библиотеки, написанные на YaoXiang)
встраиваются в бинарный файл на этапе сборки:

```rust
// build.rs или构建脚本，自动生成
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // 源代码文本
    // 未来更多
];
```

Точкой подключения служит модульная система (RFC-029, полностью реализована 2026-08-02): Registry
одновременно хранит native-модули и исходные модули, а оркестратор отвечает за координацию
нескольких файлов. Порядок разрешения `use std.test`:

1. Сначала поиск в native-модулях Rust (существующий механизм, например `std.assert`)
2. Если не найдено — поиск во встроенных `STD_YX_FILES` — при совпадении исходный модуль
   инжектируется в оркестратор по **виртуальному пути** (например, `<std>/test.yx`) и проходит
   обычный фронтенд-конвейер (parse → typecheck → IR)
3. Если не найдено — обнаружение в файловой системе (пользовательские модули)

`use std.assert` внутри встроенного исходного модуля нормально разрешается резолвером в native
registry — native- и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импортировании.

Преимущества:

- В режиме одиночного файла `use std.test` также работает
- Версия стандартной библиотеки строго привязана к бинарному файлу, несоответствие версий исключено
- Пользователю не нужно настраивать путь к стандартной библиотеке

**В будущем: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang достигнет зрелости, стандартная библиотека будет переведена в форму
файловой системы. Подробнее см. обновления RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение ревью от 2026-08-02)**: CLI `run` подключается к оркестратору. В текущем
состоянии CLI `run` использует однопроходный конвейер (`run_file_with_diagnostics`) и не способен
разрешать импорты пользовательских модулей; а модель дочерних процессов `yaoxiang test` наследует
возможности CLI, и импорт тестовыми файлами модулей проекта — ключевой сценарий. Поэтому на Фазе 1
исходная ветвь CLI `Run` сначала делегируется в `run_project` (оркестратор, рекурсивное обнаружение
по каталогам); после #247 (обнаружение по `use` по требованию) это наложится как чистая оптимизация
производительности. Одиночные файлы без импортов ведут себя эквивалентно через оркестратор, ветвь
байткода не меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурация отсутствует, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (имя файла содержит подстроку)

**Этап выполнения**:

1. Для каждого файла: запуск дочернего процесса `yaoxiang run --debug-info <file>` (`--debug-info`
   заставляет ошибки времени выполнения содержать позицию в исходном коде — по эмпирическим данным
   от 2026-08-02, трассировка стека выводит `file:line:col`)
2. Проверка кода выхода: 0 — PASS, ненулевой — FAIL
3. Захват stdout/stderr для отчёта
4. Только последовательное выполнение (Фаза 1), в будущем — поддержка `--parallel`
5. При `--fail-fast` останов сразу после первого FAIL

### 6. Изоляция тестов

Изоляция тестов естественным образом обеспечивается границей на уровне процессов:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственные кучу, стековые кадры и NativeContext
- Паника в одном тестовом файле не влияет на другие
- Дополнительный механизм изолированного контекста кучи не требуется

## Отношения с существующими системами

| Проект                                                      | Отношение                                                                                                              |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Rust `#[test]`                                              | Не затрагивается, внутренние тесты компилятора остаются на Rust                                                        |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются `yaoxiang test`                                                                           |

| Модульная система (RFC-029)                                 | Встроенные исходные модули подключаются через Registry/оркестратор; CLI `run` подключение к оркестратору — предусловие |
| Рефакторинг `#200` (`io.println` → `assert.assert`)         | Полностью согласован с направлением `yaoxiang test`                                                                    |
| `@`-аннотации                                               | Не используются, `@test` не вводится                                                                                   |

## Стратегия реализации

### Фаза 1: Основная функциональность

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — исходная ветвь CLI `Run` делегирует `run_project`
  (предусловие для многофайлового запуска)
- `src/main.rs` — добавление подкоманды `Test`
- `src/std/test.yx` — добавление модуля на чистом YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарный файл
- оркестратор / Registry — поддержка загрузки `.yx`-модулей из встроенных исходников по виртуальному
  пути
- Разбор конфигурации RFC-015 — секция `[tool.test]`
- Выполнение через дочерний процесс (`--debug-info`) и отчёт

Поставляемые результаты:

- `yaoxiang test` базово работает
- 4 функции-утверждения в `std.test`
- Обнаружение по умолчанию `tests/**/*.yx`
- Последовательное выполнение + формат вывода по умолчанию

### Фаза 2: Улучшения

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Фаза 3: Продвинутые возможности

- Параллельное выполнение `--parallel` (зависит от завершения модели конкурентности spawn)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции-утверждения (например, `assert_approx_eq` для Float)

- [x] Возможность использования generic-параметра `?`? — **Решено (2026-08-02)**: синтаксис типа `?`

## Изменения: Утверждение модели тестирования (2026-09-02, #319)

По итогам обсуждения с сопровождающими утверждены следующие четыре пункта. При конфликте основного
текста с настоящим разделом приоритет имеет данный раздел.

### R1. Утверждение трёх уровней негативных тестов (вместо неявного соглашения [test:error])

Негативные тесты («ожидаемый сбой») разделяются по уровню возникновения сбоя, каждый уровень
занимает своё место:

1. **Значение-уровень обратной проверки (общий, для пользователя)**: тестируемая операция возвращает
   `Result`, тест выражает ожидаемый сбой обычным утверждением (`assert(r.is_err())`, утверждение
   кода ошибки). По мере продвижения Result-фикации (#301, #316) файлы с меткой `[test:error]` в
   корпусе постепенно переводятся во внутрифайловые утверждения, и метка в заголовке файла отмирает.
   В `std.test` предварительно добавляются семейства функций `assert_not` / `assert_err` (унарная
   форма `!assert` будет добавлена после стабилизации синтаксиса `not` — в настоящее время
   префиксный синтаксис `!` не существует, см. аналогичное ограничение в §3 для `assert_false` с
   `cond == false`).
2. **Ошибка компиляции (только для внутреннего использования разработчиками языка)**: компиляция —
   это «всё или ничего» для файла, невозможно выразить внутри файла «эта строка не должна
   компилироваться». Сохраняется файловый специальный маркер (`[test:error]`), который читается
   runner-ом и проверяется обратным образом, и служит исключительно корпусу настоящего репозитория,
   **не является частью пользовательского тестового фреймворка**. Маркер обновлён до
   структурированного ожидаемого кода: runner разбирает в заголовке `预期: 编译错误 EXXXX` и
   сравнивает с фактическим `[EXXXX]` из stderr компилятора, несовпадение кодов = FAIL (лёгкая
   версия идеи снапшотов stderr из trybuild, без изменений в компиляторе).
3. **Аппаратный сбой времени выполнения (относится к Result-фикации, отдельный механизм не
   вводится)**: операции, которые могут завершиться сбоем, по направлению языка возвращают `Result`
   (#301, #316), тесты единообразно выражаются на уровне 1.

### R2. Несколько тестов в файле: стандартная модель через значения

Один тестовый файл может содержать несколько тестов. Стандартная модель — **через значения**:
тестовые функции возвращают `Result`, сбой утверждения выражается значением `Err`, а не аварийным
завершением процесса; сюита последовательно собирает `Result` каждого теста, формирует сводный
per-test отчёт, любое значение, отличное от Ok, приводит к ненулевому коду выхода файла.
Соответствующее семейство утверждений `std.test` предоставляет **значение-семантическую** форму
(возвращает диагностическое сообщение в виде `Err`, не аварийно завершает); семантика аварийного
завершения `std.assert.assert` сохраняется для стражей времени выполнения и не используется для
тестовых утверждений. Граница catch не применяется (непреложное правило 17 ключевых слов), входной
вызов функций в runner не используется (только во внутренних сценариях, таких как ошибка компиляции,
см. R1.2).

### R3. Значение Error получает поле code

Поддержка утверждений кода ошибки: `Error` расширяется из `Struct { message }` до формы, содержащей
машиночитаемый `code` (нативная `error_new_with_code`, константы кодов экспортируются из std), что
делает возможным `assert(err.code == "E3017")`. Проверка кода ошибки времени компиляции идёт не по
этому пути — процесс с ошибкой компиляции не запускается, её обеспечивает сравнение в runner из R1.2
(stderr компилятора уже содержит `[EXXXX]`).

### R4. Корректировки отчёта и производительности

- Пример вывода «Running 5 tests from 3 files» — остаток старой модели: в файловой модели один файл
  = один тестовый процесс; после введения R2 per-test решения поступают из сбора внутри сюиты, а не
  из сканирования тестовых функций runner-ом.
- Главная составляющая производительности — полная компиляция каждого файла (185 файлов за 11,3 с по
  замерам), а не запуск дочернего процесса; `--parallel` Фазы 3 не устраняет стоимость компиляции,
  кеширование тестового цикла — см. срезы #251 / #293.
- Трассировка места сбоя утверждения сквозь встроенные модули (по замерам
  `at std.test.assert_eq (ip: 9)`, пользователь не получает номера строки своего файла) не относится
  к данному RFC — принадлежность кадра стека — это вопрос пользовательского опыта #289 + область
  проектирования отладочных метаданных (RFC-034, `get_frames`).
