# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного фреймворка тестирования — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`, прохождение/провал
определяется через `std.assert.assert` и код выхода. Модуль `std.test` реализован на чистом YaoXiang
и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не возможность
компилятора: он не затрагивает parser, IR, байт-код или исполнитель.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время тестовое покрытие YaoXiang зависит от `#[test]` на стороне Rust и интеграционных
тестов в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang
2. Задача `#117 Модульное тестовое покрытие модулей стандартной библиотеки` заблокирована из-за
   отсутствия доступной тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) лишены
   средств автоматизации

### Ключевые ограничения

- **Нерушимое правило 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения компилятора**: не трогать parser, IR, байт-код, исполнитель
- **Приоритет самодостаточности (self-hosting)**: тестовая библиотека написана на YaoXiang, первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:  yaoxiang test [--filter --fail-fast --json ...]│
│              │                                               │
│  Уровень обнаружения: чтение yaoxiang.toml → [tool.test]     │
│              patterns                                       │
│              По умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Уровень выполнения: для каждого файла: yaoxiang run <file>   │
│              Проверка кода выхода → последовательное          │
│              выполнение                                     │
│              │                                               │
│  Уровень отчёта: PASS/FAIL → сводка                          │
│              Поддержка --json / --verbose / --fail-fast      │
│                                                              │
│  Уровень утверждений: std.test (чистый YaoXiang,              │
│              самодостаточный)                                │
│              Основа: std.assert.assert                        │
│              Диагностика: f"Expected {expected}, got          │
│              {actual}"                                       │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — не возможность компилятора, а инструмент CLI** — `yaoxiang run` уже
   умеет «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводится сканирование аннотаций `@test`, сегментов
   метаданных в байт-коде, специальных точек входа в исполнитель
3. **Самодостаточность** — модуль `std.test` реализован на чистом YaoXiang, в основе лежит вызов
   `std.assert.assert`
4. **Тестовые файлы — обычные файлы `.yx`** — прохождение/провал определяется по коду выхода

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Аргументы:
  [PATHS]...      Указанные тестовые файлы или каталоги
                  (по умолчанию: читается из yaoxiang.toml,
                  иначе tests/)

Опции:
  --filter <NAME>     Запускать только тесты, имя файла которых
                      содержит <NAME>
  --fail-fast         Остановиться на первом сбое
  --verbose, -v       Показывать подробный stdout/stderr каждого
                      теста
  --list              Только перечислить тестовые файлы без запуска
  --no-progress       Не показывать индикатор прогресса (для CI)
  --json              Вывод результатов в формате JSON
                      (для интеграции с CI)
```

#### Формат вывода

**Вывод по умолчанию**:

```
Running 5 tests from 3 files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ PASS (0.001s)
tests/string_test.yx ...................... FAIL (0.003s)
  `-- Expected "hello", got "world"
      at tests/string_test.yx:12:5

Results: 2 passed, 1 failed, 0 skipped (0.006s)
```

**Вывод JSON** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "tests": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/string_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "error": "Expected \"hello\", got \"world\"",
      "exit_code": 1
    }
  ]
}
```

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]` в соответствии с соглашением о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# Возможные расширения в будущем:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочую конфигурацию «из
  коробки» без настроек
- Однофайловый режим (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Чистая библиотека утверждений тестирования на YaoXiang
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang,
// написанная на YaoXiang

use std.assert

assert_eq = (a, b) => {
    assert.assert(a == b, f"Expected {b}, got {a}")
}

assert_ne = (a, b) => {
    assert.assert(a != b, f"Expected not equal to {b}, got {a}")
}

assert_true = (cond: Bool) => {
    assert.assert(cond, f"Expected true, got {cond}")
}

assert_false = (cond: Bool) => {
    assert.assert(!cond, f"Expected false, got {cond}")
}
```

- 4 функции утверждений, все используют `f"..."` для диагностических сообщений
- `assert_eq` / `assert_ne` используют **параметры без аннотаций** (`Any`) — по состоянию на
  2026-08-02 подтверждено: `==`/`!=` и интерполяция f-string корректно работают на Any (проверено
  для Int/String), **не зависят от системы дженериков**. Когда дженерики будут готовы, можно
  добавить аннотации
- `std.test` не зависит от какого-либо нативного кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Фаза 1: Встраивание в бинарный файл**

`std/test.yx` (а также все будущие модули стандартной библиотеки, написанные на YaoXiang)
встраиваются в бинарный файл во время сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // в будущем — больше
];
```

Система модулей (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения:
Registry одновременно хранит нативные и исходные модули, orchestrator отвечает за многофайловую
оркестровку. Порядок разрешения `use std.test`:

1. Сначала поиск среди нативных модулей Rust (существующий механизм, например `std.assert`)
2. Если не найдено — поиск среди встроенных `STD_YX_FILES`; при попадании модуль инжектируется в
   orchestrator по **виртуальному пути** (например, `<std>/test.yx`) в качестве начального и
   проходит через стандартный фронтенд-конвейер (parse → typecheck → IR)
3. Если не найдено — обнаружение в файловой системе (пользовательские модули)

Внутренние `use std.assert` внутри встроенного исходного модуля нормально разрешаются resolver'ом в
нативный registry — нативные и исходные модули сосуществуют в Registry, кросс-категорийные
зависимости работают естественно. Встроенные модули **компилируются по требованию**: попадают в
конвейер только при импорте.

Преимущества:

- `use std.test` работает и в однофайловом режиме
- Версия стандартной библиотеки строго привязана к бинарному файлу, рассинхронизация версий
  невозможна
- Пользователю не нужно настраивать пути к стандартной библиотеке

**В будущем: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение от 2026-08-02)**: CLI `run` подключается к orchestrator. В текущем виде CLI
`run` использует однофайловый конвейер (`run_file_with_diagnostics`) и не может разрешать
импортируемые пользовательские модули; а модель дочерних процессов `yaoxiang test` наследует
возможности CLI, и импорт тестовыми файлами модулей проекта — ключевой сценарий. Поэтому на Фазе 1
исходная ветка CLI `Run` сначала делегируется в `run_project` (orchestrator, рекурсивное обнаружение
в каталоге); #247 (ленивое обнаружение по use) впоследствии станет чистой оптимизацией
производительности. Однофайловый путь без import ведёт себя через orchestrator эквивалентно, ветка
байт-кода не меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, использовать их напрямую
2. Иначе — прочитать `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет — по умолчанию `tests/**/*.yx`
4. Применить фильтр `--filter` (по вхождению в имя файла)

**Этап выполнения**:

1. Для каждого файла: запуск дочернего процесса `yaoxiang run --debug-info <file>` (`--debug-info`
   обеспечивает указание позиции в исходном коде в ошибках времени выполнения — по состоянию на
   2026-08-02 подтверждено, что stack trace выводит `file:line:col`)
2. Проверка кода выхода: 0 — PASS, ненулевой — FAIL
3. Захват stdout/stderr для отчёта
4. Только последовательное выполнение (Фаза 1), в будущем — поддержка `--parallel`
5. При `--fail-fast` немедленная остановка на первом FAIL

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процессов:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственные Heap, Frame, NativeContext
- Panic в одном тестовом файле не влияет на другие тестовые файлы
- Дополнительный механизм изолированного контекста Heap не требуется

## Связь с существующими системами

| Элемент                                                     | Связь                                                                                                                   |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Rust `#[test]`                                              | Не трогается, внутренние тесты компилятора остаются на Rust                                                             |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются `yaoxiang test`                                                                            |
| `std.assert.assert(cond)`                                   | Сохраняется, `std.test` опирается на него                                                                               |
| Система модулей (RFC-029)                                   | Встроенные исходные модули подключаются через Registry/orchestrator; подключение CLI `run` к orchestrator — предусловие |
| Рефакторинг `#200` (`io.println` → `assert.assert`)         | Полностью совпадает по направлению с `yaoxiang test`                                                                    |
| Аннотации `@`                                               | Не используются, `@test` не вводится                                                                                    |

## Стратегия реализации

### Фаза 1: Базовая функциональность

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — исходная ветка CLI `Run` делегируется в
  `run_project` (предусловие для многофайлового запуска)
- `src/main.rs` — добавление подкоманды `Test`
- `src/std/test.yx` — новый чистый модуль YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарный файл
- orchestrator / Registry — поддержка загрузки `.yx`-модулей из встроенного источника по
  виртуальному пути
- Разбор конфигурации RFC-015 — секция `[tool.test]`
- Выполнение через дочерний процесс (`--debug-info`) + отчёт

Поставляемые результаты:

- `yaoxiang test` базово работоспособен
- 4 функции утверждений в `std.test`
- Обнаружение по умолчанию `tests/**/*.yx`
- Последовательное выполнение + формат вывода по умолчанию

### Фаза 2: Доработка

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Фаза 3: Расширенные возможности

- Параллельное выполнение `--parallel` (зависит от развития модели конкурентности spawn)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции утверждений (например, `assert_approx_eq` для Float)

## Риски и их снижение

| Риск                                                                 | Вероятность | Снижение                                                                                            |
| -------------------------------------------------------------------- | ----------- | --------------------------------------------------------------------------------------------------- |
| Сбой интерполяции `f"..."` на Any                                    | Нет         | Подтверждено 2026-08-02 (Int/String работают корректно)                                             |
| Затраты на запуск дочерних процессов замедляют тесты                 | Средняя     | На Фазе 1 — последовательное выполнение, приемлемо; Фаза 3 смягчает через параллелизм               |
| Разбор `yaoxiang.toml` отсутствует в текущем CLI                     | Низкая      | Простое расширение, не влияет на основную функциональность                                          |
| Регрессия от подключения CLI run к orchestrator                      | Низкая      | Путь для однофайлового запуска без import эквивалентен; интеграционные тесты покрывают orchestrator |
| Увеличение размера бинарного файла из-за встроенных `.yx`-исходников | Низкая      | `.yx`-исходники очень малы, пренебрежимо                                                            |

## Открытые вопросы

- [x] Корректно ли разрешается ссылка `use std.assert` в `std/test.yx`? — **Решено (2026-08-02)**.
      После реализации системы модулей (RFC-029) нативные и исходные модули сосуществуют в Registry,
      resolver разрешает их единообразно, кросс-категорийные зависимости работают естественно
- [x] Вносит ли обобщённый `to_string` в `f"..."` новые ограничения типов? — **Решено
      (2026-08-02)**. Подтверждено, что `==`/`!=` и интерполяция f-string работают на параметрах без
      аннотаций (Any) (проверено для Int/String), новые ограничения не вводятся
- [x] Возможность использования `?` в параметрах дженериков? — **Решено (2026-08-02)**: синтаксис
      типа `?` в настоящее время не существует (и молча проглатывается, отслеживается отдельной
      задачей), на Фазе 1 функции утверждений используют параметры без аннотаций и не зависят от
      системы дженериков
