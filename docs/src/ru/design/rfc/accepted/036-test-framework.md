# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Краткое описание

Введение стандартного фреймворка тестирования `std.test` и подкоманды CLI `yaoxiang test` для YaoXiang. Тестовые файлы представляют собой обычные файлы `.yx`, где общий статус pass/fail определяется по exit code дочернего процесса; внутри файла поддерживается несколько тестовых функций — сбой assertions выражается значением `Err` (семантика значения), а набор тестов собирает per-test вердикты (§7). Модуль `std.test` реализован на чистом YaoXiang — первая библиотека для dogfooding. Команда `yaoxiang test` — это инструмент CLI, а не функциональность компилятора — не затрагивает никаких изменений в parser, IR, байткоде или executor.

## Мотивация

### Зачем нужен фреймворк тестирования?

Текущее тестовое покрытие YaoXiang опирается на `#[test]` со стороны Rust и интеграционные тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) невозможно писать на YaoXiang
2. Покрытие модульных тестов стандартной библиотеки заблокировано из-за отсутствия доступной тестовой инфраструктуры
3. Регрессионное тестирование языковых возможностей (например, изменение семантики spawn в RFC-032) лишено автоматизации

### Ключевые ограничения

- **17 ключевых слов — железный закон**: не вводить новых ключевых слов или синтаксических конструкций
- **Ноль изменений в компиляторе**: не трогать parser, IR, байткод, executor
- **Self-hosting первым делом**: библиотека тестирования пишется на YaoXiang, первая библиотека для dogfooding

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  CLI слой:  yaoxiang test [--filter --fail-fast --json ...]  │
│              │                                               │
│  Слой обнаружения: чтение yaoxiang.toml → patterns [tool.test] │
│              По умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Слой выполнения: для каждого файла: yaoxiang run <file>    │
│              проверка exit code → последовательное выполнение │
│              │                                               │
│  Слой отчётности: PASS/FAIL → агрегация                       │
│              поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Слой assertions: std.test (чистый YaoXiang, self-hosted)    │
│              Нижний уровень: std.assert.assert                │
│              Диагностика: f"Expected {expected}, got {actual}" │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — это не функциональность компилятора, а инструмент CLI** — `yaoxiang run` уже может «выполнять тесты», `yaoxiang test` просто помогает запустить все файлы и показать отчёт
2. **Ноль изменений в компиляторе** — без введения сканирования аннотации `@test`, метаданных в байткоде, специальных точек входа в executor
3. **Self-hosting** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности поступают из `std.assert` / `std.result`
4. **Тестовые файлы — это обычные файлы `.yx`** — файлы выполняются как дочерние процессы, общий pass/fail определяется по exit code
5. **Сбой assertions — это значение, а не событие процесса** — тестовые функции возвращают `Result`, сбой assertions выражается через `Err`, набор тестов собирает per-test вердикты (§7); abort на уровне процесса принадлежит только runtime guards, не используется для assertions в тестах

## Детальный проект

### 1. Дизайн CLI

```
yaoxiang test [ОПЦИИ] [ПУТИ]

Arguments:
  [PATHS]...      указать тестовые файлы или директории (по умолчанию: из yaoxiang.toml, иначе tests/)

Options:
  --filter <NAME>     запускать только тесты с именем файла, содержащим <NAME>
  --fail-fast         остановиться при первом сбое
  --verbose, -v       показывать подробный stdout/stderr для каждого теста
  --list              только список тестовых файлов, без запуска
  --no-progress       не показывать прогресс (заголовок и строки PASS); детали FAIL и сводка сохраняются (CI сценарий)
  --json              вывод в формате JSON (для CI интеграции)
  --parallel          параллельное выполнение (один worker на ядро; объединяется с [tool.test].parallel через ИЛИ)
```

#### Формат вывода

**Вывод по умолчанию** (per-test вердикты из внутрифайлового набора, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**JSON вывод** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 }, "time_secs": 0.006 },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы со сбоями дополнительно содержат `exit_code` и `stderr` (диагностика дочернего процесса с удалёнными ANSI-кодами, для取证 в CI); при комбинации `--verbose` и `--json` все файлы содержат `stdout` / `stderr`
- `--no-progress` подавляет только вывод прогресса (заголовок и строки PASS) — детали FAIL и сводка всегда выводятся, сбой не может быть скрыт; `--list` выводит по одному пути к тестовому файлу в строке, без выполнения
- Каждый файл содержит `kind` (behavior / compile-error / runtime-error / invalid, §8.2), сводка содержит `by_kind` с подсчётом выполнений (фиксированные четыре ключа, без skipped); человеческая сводка содержит строку распределения по категориям `Categories:`
- При `--parallel` человеческие строки прогресса выводятся потоком в порядке завершения (целые блоки без перемешивания), JSON `files` сортируются по пути `file` для стабильности вывода (удобно для diff в CI)
- Внутрифайловый массив per-test `tests` получается из сбора набора в §7, с внедрением модели value semantics
- Официальный CI (`.github/workflows/ci.yml` test job) потребляет следующим образом: cargo запускает `--test integration` (CLI интеграция) и `--test yx_runner` (двойные корневые corpus guards), затем `yaoxiang test --json --parallel` для многоуровневого реального запуска — режим по умолчанию (языковой corpus) и явный `src/std/tests` (библиотечный уровень) каждый производят отчёт; сводная таблица (total / passed / failed / skipped / time_secs и by_kind) записывается в job summary, файлы со сбоями печатают `kind` / `exit_code` / `stderr` для取证, любой ненулевой exit code набора делает job красным

### 2. Конфигурация yaoxiang.toml

Размещается под `[tool.test]`, соответствует соглашению о сторонних расширениях `[tool.*]` из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
exclude = ["tests/fixtures/**"]   # совпавшие исключаются из набора обнаружения (--list также исключает)
parallel = true                   # параллельное выполнение (объединяется с флагом --parallel через ИЛИ)
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — нулевая конфигурация, работает из коробки
- `exclude` имеет ту же форму, что и `patterns` (буквальные пути или `root/**…`, все совпадают по префиксу пути); excluded означает «не тест», fixtures, требующие проверки runtime-поведения, запускаются напрямую через `yaoxiang run`
- **Режим одиночного файла (`yaoxiang test foo.yx`) запускает напрямую, не читая конфигурацию** — при явных путях ключи конфигурации `exclude`/`parallel` не действуют (кроме флагов)
- В будущем может быть вынесен в отдельный репозиторий (позиция `[tool.test]` останется прежней)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — библиотека assertions для тестирования на чистом YaoXiang (standard form value semantics, реализована 2026-09-03)
// Первая библиотека dogfooding: тестовая библиотека YaoXiang написана на YaoXiang.

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not и assert_false идентичны; assert_err / assert_err_code см. §8.1
```

- Функции assertions имеют **семантику значения**: возвращают `Result(Void, String)`, сбой выражается через `Err(диагностическое сообщение)`, не abort — §7 набор тестов собирает per-test вердикты на этом основании. Семантика abort на уровне процесса из `std.assert.assert`保留给运行时守卫, не входит в путь assertions тестов. Payload Ok — `Void` (spec unit из type-system.md; `()` — пустой Tuple, они не смешиваются — решение 2026-09-03)
- **Семейство из 7 функций (реализовано 2026-09-03, abort transitional version удалена)**: value semantics
  `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not`
  (идентичен assert_false, зарезервирован для формы `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (§8.1 assertion ошибок кодов)
  - `assert_approx_eq(a: Float, b: Float, eps: Float)` (Phase 3, реализовано 2026-09-07): проверка `|a - b| <= eps`, eps **явно передаётся** вызывающей стороной — допуск является частью контракта теста, скрытых значений по умолчанию нет; отрицательный eps → Err в точке объявления, NaN всегда → Err
- `assert_eq` / `assert_ne` используют **параметры с аннотацией Any** — `==`/`!=` и интерполяция в f-string работают на Any нормально, без зависимости от системы generics. Обратите внимание: параметры **должны быть явно аннотированы**: параметры без аннотаций не проходят проверку вызова native generics `&Result(T, E)` (подтверждено зондом R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный синтаксис `not` ещё не реализован, после стабилизации возможна миграция; унарная форма `!assert` имеет ту же зависимость, см. §8.1)
- Тело функции + явный `return`: тип then-ветки if-выражения отбрасывается при проверке, if-выражение с двумя Result arms является слепой зоной проверки, реализация это обходит
- `std.test` не зависит от нативного кода, реализован полностью на YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевой дизайн)

**Phase 1: Встраивание в бинарник**

`std/test.yx` (а также все будущие модули стандартной библиотеки на YaoXiang) встраиваются в бинарник при сборке:

```rust
// build.rs или скрипт сборки, автогенерация
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // исходный текст
    // будущие модули
];
```

Система модулей (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения: Registry хранит одновременно native-модули и source-модули, orchestrator отвечает за многофайловую организацию. Порядок разрешения `use std.test`:

1. Сначала проверяется Rust native модуль (существующий механизм, например `std.assert`)
2. Не найден — проверяются встроенные `STD_YX_FILES` — найден → инъекция в orchestrator с **виртуальным путём** (например `<std>/test.yx`) в качестве seed модуля, проходит через обычный frontend pipeline (parse → typecheck → IR)
3. Не найден — поиск в файловой системе (пользовательские модули)

Внутренний `use std.assert` встроенного source модуля нормально разрешается resolver'ом в native registry — native и source модули сосуществуют в Registry, кросс-вид зависимости работают естественно. Встроенные модули **компилируются по требованию**: попадают в pipeline только при импорте.

Преимущества:

- В режиме одиночного файла `use std.test` также работает
- Версия стандартной библиотеки жёстко привязана к бинарнику, исключается mismatch версий
- Не требуется конфигурация пути к стандартной библиотеке пользователем

**Будущее: стандартная библиотека в файловой системе**

Когда модель проектов YaoXiang созреет, стандартная библиотека перейдёт на файловую форму. Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение аудита 2026-08-02)**: CLI `run` подключается к orchestrator. Текущий CLI `run` идёт по однофайловому pipeline (`run_file_with_diagnostics`), не может разрешать пользовательские import'ы; а модель дочернего процесса `yaoxiang test` наследует возможности CLI, импорт проекта модулей в тестовых файлах — ключевой сценарий. Поэтому Phase 1 сначала передаёт исходную ветку CLI `Run` в `run_project` (orchestrator, рекурсивное обнаружение директорий); обнаружение по мере использования use как чистая оптимизация производительности добавляется позже. Однофайловые файлы без import через orchestrator эквивалентны по поведению, ветка байткода неизменна.

**Фаза обнаружения**:

1. Если указаны `[PATHS]`, используются указанные пути напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтрация `--filter` (имя файла содержит)
5. Область обнаружения — это分层 тестирования (§9): паттерны по умолчанию покрывают только языковой corpus; библиотечный тестовый уровень (например `src/std/tests/`) обнаруживается через явные пути или конфигурацию пакета, не смешивается с умолчательным сканированием

**Фаза выполнения**:

1. Для каждого файла маршрутизация выполняется по заголовку (грамматика инструкций в §8.2,解析 через `src/util/test_markers.rs`,共用 с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run <file>`
     (runtime ошибки по умолчанию несут позицию исходного кода и stack frame — debug_map генерируется по умолчанию,
     stack trace выводит `file:line:col`); объявление `// mode:` направляет дочерний процесс в режим `--runtime`
   - Compile-error классы: один шаг `yaoxiang check <file>`
   - Runtime-error классы: два шага — `check` (должен пройти) + `run` (должен упасть)
2. Файлы с `// skip: <причина>` пропускаются, учитываются в skipped
3. Сопоставление вердикта с ожидаемым кодом по判定矩阵 §8.2; ошибка解析 инструкции → FAIL без выполнения (конструктивный отказ)
4. Захват stdout/stderr для отчётности
5. По умолчанию последовательно; `--parallel` (или `[tool.test].parallel`) создаёт пул workers по числу ядер,
   каждый файл остаётся独立ным дочерним процессом — skip/invalid обрабатываются первыми в порядке обнаружения, результаты выполнения выводятся потоком в порядке завершения, JSON сортируется по пути (Phase 3, реализовано 2026-09-07)
6. При `--fail-fast` при первом FAIL немедленно останавливается планирование новых файлов; в параллельном режиме файлы в процессе завершаются и учитываются

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процессов:

- Каждый тестовый файл выполняется в独立ном дочернем процессе
- Каждый дочерний процесс имеет独立ный Heap, Frame, NativeContext
- Panic одного тестового файла не влияет на другие
- Не требуется дополнительный механизм独立ных Heap contexts
- **Параллельное выполнение (Phase 3) не расширяет границы изоляции**: рабочие директории (CWD) дочерних процессов общие,
  параллельные тесты не должны занимать файлы по одинаковым путям в CWD — файловые I/O тесты используют独立ные имена файлов и очищают их по завершении

### 7. Набор тестов и мультитесты (модель value semantics)

Один тестовый файл может содержать несколько тестов. Организация внутри файла (реализовано 2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main: () -> Void = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — функция без параметров, возвращающая `Result(Void, String)`; сбой assertions выражается через `Err` (§3 семейство value semantics assertions), не прерывает процесс — следующие тесты выполняются как обычно
- `test.suite` вызывает по очереди и собирает: не-Ok тест записывает имя и диагностику, Ok молча; после завершения всех при любом Err выполняется abort через `std.assert.assert` с деталями сбоя (`N of M test(s) failed` + каждая строка `[FAIL] имя: диагностика`) — exit code файла не 0 (判定 §5 остаётся). Этот abort — runtime guard тестового бинарника, не путь assertions; полностью Ok → молчаливый exit 0
- Тестовые функции верхнего уровня регистрируются **в форме замыкания** (`("name", () => test_fn())`): прямое использование имени функции верхнего уровня как значения пока не поддерживается (ограничение IR слоя, `E3006`) — вызов глобальной функции из тела замыкания не затрагивается
- Runner видит только файл, не сканирует на уровне функций: per-test вердикты полностью из внутринаборного сбора, внутренняя структура файла прозрачна для runner — принцип «ноль изменений в компиляторе» не нарушен
- Явно не принято: границы catch внутри процесса (закон 17 ключевых слов); вызовы runner по функции (только для внутренних сценариев вроде compile-fail в §8.2)
- API形态已定案 (реализовано 2026-09-03): `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дубликаты имён не检测 (имена только для отображения в отчёте); `--filter` фильтрует по имени файла, не видит имена тестов внутри набора

### 8. Негативное тестирование (ожидаемые сбои) — трёхуровневая архитектура

Негативное тестирование разделено по уровню возникновения сбоя, каждый уровень на своём месте:

#### 8.1 Value-level обратное (общее, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый сбой обычным assertion:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// или одно выражение-обёртка (код существует только на носителе std Error, E зафиксирован как Error):
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` уже реализованы с семейством value semantics (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса `not` (то же ограничение, что и у `assert_false` с `cond == false`)
- Assertion кодов ошибок依赖于 значения `Error`, несущие машиночитаемое поле `code` — уже реализовано:
  `Error = { code, message }` (native `error_new(code, message)`), доступ через
  `result.unwrap_err(r)` для получения носителя + accessors `result.code(e)` / `result.message(e)`
  (предполагавшееся при проектировании именование `error_new_with_code`, экспорт констант кодов и доступ `err.code`
  не приняты — в языке нет доступа к полям Struct, константы кодов не экспортируются)
- По мере продвижения Result化, операции с возможностью сбоя возвращают `Result` по одной, файловые
  негативные маркеры в corpus мигрируют во внутрифайловые assertions

#### 8.2 Файловые негативные инструкции (только для внутреннего использования разработчиками языка)

Компиляция — это всё или ничего для файла, невозможно выразить «эта строка не должна компилироваться» внутри файла; runtime сбои同样 требуют файлового表达 (например, набор содержит обязательно падающий тест). Заголовок файла объявляет ожидания через **структурированные инструкции**, runner **маршрутизирует判定** по ожидаемой категории (маршрутизация определена 2026-09-03; грамматика инструкций определена и реализована 2026-09-06).

Грамматика инструкций в заголовке (`// key: value`, в первых 16 строках, строгое соответствие токенов):

```text
// expect: compile-error E1002 [E1003 ...]   compile-time rejection тест
// expect: runtime-error E6003 [...]         runtime failure тест
// skip: <причина>                          пропустить выполнение, учесть в skipped
// mode: embedded|standard|full              режим --runtime дочернего процесса (потребляется только шагом run)
```

- Нет инструкции `expect:` = поведенческий тест. `expect:` — **единственное объявление** ожидания — решение 2026-09-06 отвергло булев флаг `[test:error]` и китайское прозаическое `预期:` как костыль: булев флаг и строка ожидания — два слабо связанных факта, поддерживать их консистентность по дисциплине必然会漂移; английская грамматика со строгим соответствием токенов позволяет runner'у парсить механически (kind + код — все фиксированные токены, после кода любой лишний токен = парсинг неудачен), парсинг неудачен = FAIL без выполнения — деградация при ошибочном объявлении инструкции невозможна (конструктивный отказ)
- **Класс compile-error**: один шаг `check` — должен упасть и вывод должен содержать все `[EXXXX]`; успешная компиляция = FAIL (что должно было быть отвергнуто — не отвергнуто), отказ но код не совпадает = FAIL. Синтаксические ошибки (E1xxx парсинг) и семантические ошибки (E2xxx+) не имеют отдельных категорий — ожидаемый код сам фиксирует этап
- **Класс runtime-error**: два шага判定 — `check` должен **успешно пройти** (compile-time невиновен), `run` должен упасть и вывод должен содержать все `[EXXXX]`. Компиляция уже падает = FAIL (ключевое判定 в противоположном направлении от класса compile-error, предотвращает утечку «компиляция неожиданно прошла, выполнение случайно упало»)
- Изоморфно индустрии: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`, Clang `expected-error` все объявляют ожидания в fixture комментариях и harness делает двунаправленное сравнение; они используют построчную привязку потому что multi-diagnostic компиляторам нужно различать несколько ожиданий в одном файле, наш компилятор останавливается на первой ошибке, один файл — одна диагностика, файловый уровень изоморфен реальности компилятора — после реализации восстановления после ошибок можно добавить построчную привязку в语法ку (Cranelift filetests смешивает файловые заголовки и построчные ожидания в том же стиле)
- Известный долг рендеринга: диагностика в период парсинга сейчас выводится в Debug форме (`code: "E0012"` вместо `[E0012]`), сканер кодов принимает обе формы; после унификации рендеринга диагностик будет принята строгая форма
- **Обслуживает только корпус этого репозитория, не является частью пользовательского тестового фреймворка**; соглашение о判定 двумя runner'ами закрыто (2026-09-03): yx_runner (cargo test) и `yaoxiang test` совместно используют `src/util/test_markers.rs` для解析 заголовков инструкций, соглашение о директории для 06-compile-errors упразднено. Уровень отчётности даёт подсчёт по категориям: человеческая сводка содержит строку `Categories:`, JSON summary содержит `by_kind` (behavior / compile-error / runtime-error / invalid, skipped отдельно), каждый файл содержит `kind`

#### 8.3 Runtime hard failure (относится к Result化)

Специального механизма нет — операции, которые будут падать, возвращают `Result` согласно направлению языка, тесты统一 выражаются через §8.1. Process-level abort (например, нарушение assertion, runtime mismatch параметров) по мере Result化 постепенно конвергирует к значениям, тестовый фреймворк не предоставляет для него специальной семантики. (Примечание: маркировка判定 «runtime-error класса» в §8.2 — это файловый проверочный通道 для операций, которые пока нельзя Result化ровать, не противоречит семантическому направлению этого раздела — последнее является终点, первое — переходный通道)

### 9. Многоуровневая система тестирования: языковой corpus и библиотечные тесты (решение 2026-09-03)

Тесты разделены на два уровня по **тестируемому объекту**, у каждого свой владелец и maintenance:

**Первый уровень: языковой corpus доступности (`tests/yaoxiang/`)**

- Тестируемый объект — **сам язык** — парсер, система типов, модули, concurrency, ownership, compile-time отклонения, runtime семантика; директории организованы по главам спецификации языка
- std в corpus служит только **инструментом assertions** (`std.assert` / `std.test`), никогда не является тестируемым — поведение API библиотек не относится к доступности языка
- Corpus分流руется внутри через §8 на три категории判定: поведенческие тесты / compile-time rejection тесты / runtime failure тесты

**Второй уровень: библиотечные тесты (идут с библиотекой)**

- Тестируемый объект — **публичный API контракт библиотеки** (например, поведение `list.push`, семантика `result.code`)
- Тесты пишутся **в собственном пакете библиотеки**: пакет std — это `src/std/`, его yx-уровневые тесты находятся в `src/std/tests/`
  (в том же месте, что и реализация; директория сосуществует с Rust модульными тестами, типы файлов не пересекаются); тесты самого `std.test` также там (тестируем std.test через std.test,闭环 self-hosting)
- Будущие пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаружение по `[tool.test]` пакета (это preview раскладки тестов RFC-014 package management)
- Обнаружение не входит в умолчательные patterns (умолчательные `tests/**/*.yx` покрывают только языковой уровень): библиотечный тестовый уровень обнаруживается через явные пути (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI запускает уровни раздельно

Миграция: **перенесено (2026-09-06)** — 19 файлов из原 `tests/yaoxiang/07-std/` после逐一甄别全部 оказались библиотечными тестами (тестируемый объект — API контракты std модулей; `?` propagation, auto borrow, generic instantiation как языковые особенности играют роль носителя, а не тестируемого объекта),全部迁移рованы в `src/std/tests/`, директория 07-std撤销; yx_runner переключён на двойное корневое обнаружение (`tests/yaoxiang/` + `src/std/tests/`), умолчательные patterns не включают библиотечный уровень (интеграционные тесты фиксируют этот контракт). Языковой corpus с тех пор содержит ноль std-API тестов.

## Отношение к существующим системам

| Компонент                                       | Отношение                                      |
| ----------------------------------------------- | ---------------------------------------------- |
| Rust `#[test]`                                  | Не трогаем, внутренние тесты компилятора остаются на Rust |
| Существующие `.yx` интеграционные тесты (`tests/yaoxiang/`) | Обнаруживаются и выполняются `yaoxiang test`  |
| `std.assert.assert(cond)`                       | Сохраняется для runtime guards; семейство value semantics assertions в `std.test` теперь基于 `std.result` (§3、§7) |
| Система модулей (RFC-029)                       | Встроенные source модули подключаются через Registry/orchestrator; подключение CLI `run` к orchestrator является предварительным условием |
| Рефакторинг corpus (`io.println` → `assert.assert`) | Полностью согласовано с направлением `yaoxiang test` |
| Аннотация `@`                                   | Не используется, `@test` не вводится           |

## Риски и митигация

| Риск                                          | Вероятность | Митигация                                      |
| --------------------------------------------- | ----------- | ---------------------------------------------- |
| `f"..."` интерполяция на Any не работает     | Нет         | Подтверждено 2026-08-02 (Int/String работают нормально) |
| Парсинг конфигурации `yaoxiang.toml` отсутствует в текущем CLI | Низкая      | Простое расширение, не влияет на core functionality |

## Открытые вопросы

- [x] Может ли ссылка `use std.assert` в `std/test.yx` правильно разрешаться? — **Решено (2026-08-02)**. После реализации системы модулей (RFC-029) native и source модули сосуществуют в Registry, resolver的统一 разрешает, кросс-вид зависимости работают естественно
- [x] Вводит ли generic `to_string` в `f"..."` новые тип constraints в выводе тестов? — **Решено (2026-08-02)**.实证 параметры без аннотаций (Any) на `==`/`!=` и f-string интерполяция работают ( проверено на Int/String), новых constraints не вводит
- [x] Целесообразность `?` generic параметров? — **Решено (2026-08-02)**: синтаксис типа `?` сейчас не существует (и будет silenciosamente удалён, открыт отдельный issue для отслеживания), Phase 1 использует параметры без аннотаций, не依赖于 систему generics
