# RFC-036: Тестовый фреймворк std.test и команда yaoxiang test

## Резюме

Ввести в YaoXiang стандартный тестовый фреймворк — модуль `std.test` и подкоманду CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`; общий результат
прохождения/провала определяется по коду выхода (exit code) дочернего процесса. Внутри файла
допускается наличие нескольких тестовых функций — провал утверждения выражается значением `Err`
(значимая семантика), а набор (suite) собирает per-test вердикты (§7). Модуль `std.test` реализован
на чистом YaoXiang и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а
не возможность компилятора — никаких изменений в parser, IR, байт-код или исполнителе.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang опирается на атрибуты `#[test]` на стороне Rust и
интеграционные тесты в `tests/`. Это означает:

1. Юнит-тесты для стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. Задача `#117 Покрытие юнит-тестами модулей стандартной библиотеки` заблокирована из-за отсутствия
   доступной тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) не
   имеют автоматизированных средств

### Ключевые ограничения

- **Закон 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения компилятора**: не трогать parser, IR, байт-код, исполнитель
- **Приоритет самохостинга**: тестовая библиотека пишется на YaoXiang и является первой
  dogfooding-библиотекой

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Слой CLI:  yaoxiang test [--filter --fail-fast --json ...]  │
│              │                                               │
│  Слой обнаружения:  читает yaoxiang.toml → [tool.test] patterns│
│              по умолчанию: tests/**/*.yx                       │
│              │                                               │
│  Слой выполнения:  для каждого файла: yaoxiang run <file>      │
│              проверка exit code → последовательное выполнение  │
│              │                                               │
│  Слой отчётов:  PASS/FAIL → сводка                            │
│              поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Слой утверждений:  std.test (чистый YaoXiang, самохостинг)    │
│              нижний уровень: std.assert.assert                │
│              диагностика: f"Expected {expected}, got {actual}" │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — не возможность компилятора, а инструмент CLI** — `yaoxiang run` уже
   способен "выполнять тесты"; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводятся сканирование аннотаций `@test`, секции метаданных
   в байт-коде, специальные точки входа в исполнитель
3. **Самохостинг** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности берутся из
   `std.assert` / `std.result`
4. **Тестовые файлы — обычные файлы `.yx`** — файл выполняется в дочернем процессе, общий результат
   прохождения/провала определяется по exit code
5. **Провал утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`; провал утверждения выражается через `Err`, suite собирает per-test вердикты поочерёдно
   (§7). Процессный abort относится только к runtime-стражам и не используется для тестовых
   утверждений

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Аргументы:
  [PATHS]...         Указывает тестовые файлы или каталоги (по умолчанию:
                     читается из yaoxiang.toml, иначе tests/)

Опции:
  --filter <NAME>    Запускать только тесты, в имени файла которых
                     содержится <NAME>
  --fail-fast        Остановиться на первом провале
  --verbose, -v      Показывать подробный stdout/stderr каждого теста
  --list             Только перечислить тестовые файлы, не запускать
  --no-progress      Не показывать вывод прогресса (заголовок и строки
                     PASS); детали FAIL и сводка сохраняются (для CI)
  --json             Выводить результат в формате JSON (для интеграции
                     с CI)
```

#### Формат вывода

**Вывод по умолчанию** (per-test вердикты поступают из сбора suite внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
```

**Вывод JSON** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "files": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы с провалом дополнительно содержат `exit_code` и `stderr` (диагностика дочернего процесса с
  удалёнными ANSI-кодами, для разбора в CI); при комбинации `--verbose` и `--json` все файлы
  содержат `stdout` / `stderr`
- `--no-progress` лишь подавляет вывод прогресса (заголовок и строки PASS) — детали FAIL и сводка
  всегда выводятся, провал не может быть скрыт; `--list` выводит по одной строке с путём к каждому
  тестовому файлу без выполнения
- Per-test массив `tests` внутри файла поступает из сбора suite в §7, вступает в силу по мере
  реализации модели на значениях (#319)

### 2. Конфигурация yaoxiang.toml

Располагается в секции `[tool.test]`, соответствует соглашению о сторонних расширениях `[tool.*]` из
RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# Будущие расширения:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает работающую конфигурацию без
  настроек
- В режиме одного файла (`yaoxiang test foo.yx`) выполняется напрямую, без чтения конфигурации
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Библиотека утверждений на чистом YaoXiang
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang, написанная на YaoXiang

use std.result

assert_eq = (a, b) => {
    if a == b { result.ok(()) } else { result.err(f"Expected {b}, got {a}") }
}

assert_ne = (a, b) => {
    if a != b { result.ok(()) } else { result.err(f"Expected not equal to {b}, got {a}") }
}

assert_true = (cond: Bool) => {
    if cond { result.ok(()) } else { result.err(f"Expected true, got {cond}") }
}

assert_false = (cond: Bool) => {
    if cond == false { result.ok(()) } else { result.err(f"Expected false, got {cond}") }
}
```

- Функции утверждений имеют **значимую семантику**: возвращают `Result((), String)`, провал
  выражается через `Err(диагностика)`, без аварийного завершения процесса — §7 suite использует это
  для сбора per-test вердиктов. Процессная семантика abort у `std.assert.assert` сохраняется для
  runtime-стражей и не входит в путь тестовых утверждений
- Пояснение о переходе: 4 функции, реализуемые в Phase 1, основаны на `std.assert.assert` (семантика
  abort) и являются переходной реализацией для самохостинга; семейство со значимой семантикой
  является стандартной формой данного RFC и заменит их после реализации (#319)
- `assert_eq` / `assert_ne` используют **параметры без аннотаций** (`Any`) — по состоянию на
  2026-08-02 подтверждено: `==`/`!=` и интерполяция f-string работают на Any (проверено на Int и
  String), **не зависят от системы обобщений (generics)**. В будущем, когда обобщения будут готовы,
  аннотации можно добавить
- `assert_false` использует `cond == false` для отрицания (унарный синтаксис `not` ещё не
  реализован; после стабилизации можно перейти; унарная форма `!assert` имеет ту же зависимость, см.
  §8.1)
- Утверждения кода ошибки (`assert(err.code == "E3017")`) зависят от того, что значение `Error`
  несёт машиночитаемое поле `code` (§8.1)
- `std.test` не зависит ни от какого native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Phase 1: встраивание в бинарник**

`std/test.yx` (а также все будущие модули стандартной библиотеки, написанные на YaoXiang)
встраиваются в бинарник на этапе сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // текст исходного кода
    // в будущем — больше
];
```

Модульная система (RFC-029, полностью реализована к 2026-08-02) предоставляет точку подключения:
Registry одновременно содержит native-модули и исходные модули, а orchestrator отвечает за
многофайловую оркестровку. Порядок разрешения `use std.test`:

1. Сначала поиск в native-модулях Rust (существующий механизм, например `std.assert`)
2. При ненахождении — поиск во встроенных `STD_YX_FILES`; при попадании модуль с **виртуальным
   путём** (например `<std>/test.yx`) инжектируется в orchestrator как начальный и проходит
   стандартный frontend-конвейер (parse → typecheck → IR)
3. При ненахождении — обнаружение через файловую систему (пользовательские модули)

Операторы `use std.assert` внутри встроенных исходных модулей нормально разрешаются resolver'ом в
native registry — native- и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: в конвейер попадают только при
import.

Преимущества:

- В режиме одного файла `use std.test` также работает
- Версия стандартной библиотеки строго привязана к бинарнику, рассогласования версий исключены
- Пользователю не нужно настраивать путь к стандартной библиотеке

**Будущее: стандартная библиотека в файловой системе**

После того как в YaoXiang созреет проектный режим, стандартная библиотека перейдёт на форму в
файловой системе. Подробности см. в обновлениях RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение ревью от 2026-08-02)**: CLI `run` подключается к orchestrator. В
настоящее время CLI `run` идёт по однофайловому конвейеру (`run_file_with_diagnostics`) и не может
разрешать импорты пользовательских модулей; однако модель дочерних процессов `yaoxiang test`
наследует возможности CLI, а импорт тестовым файлом модулей проекта — ключевой сценарий. Поэтому в
Phase 1 ветвь исходного кода CLI `Run` делегируется `run_project` (orchestrator, рекурсивное
обнаружение в каталоге); #247 (обнаружение по `use` по требованию) накладывается позже как чистая
оптимизация производительности. Для однофайлового случая без import поведение через orchestrator
эквивалентно, ветвь байт-кода не меняется.

**Этап обнаружения:**

1. Если указаны `[PATHS]`, использовать их напрямую
2. Иначе читать `patterns` из секции `[tool.test]` в `yaoxiang.toml`
3. Если конфигурации нет — по умолчанию `tests/**/*.yx`
4. Применить фильтр `--filter` (по вхождению подстроки в имя файла)

**Этап выполнения:**

1. Для каждого файла: запускается дочерний процесс `yaoxiang run --debug-info <file>`
   (`--debug-info` включает указание позиции в исходнике в ошибках времени выполнения — по состоянию
   на 2026-08-02 подтверждено, что stack trace выводит `file:line:col`); заголовок `[test:runtime]`
   объявляет режим `--runtime` дочернего процесса (зафиксировано 2026-09-03)
2. Файлы с заголовком `[test:ignore]: <причина>` пропускаются и учитываются как skipped в отчёте
   (зафиксировано 2026-09-03)
3. Проверка exit code: 0 — PASS, ненулевой — FAIL; для файлов с `[test:error]` вердикт инвертируется
   и сверяется с ожидаемым кодом по §8.2
4. Захват stdout/stderr для отчёта
5. Только последовательное выполнение (Phase 1); в будущем будет поддержан `--parallel`
6. При `--fail-fast` — немедленная остановка на первом FAIL

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей процессов:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственный Heap, Frame, NativeContext
- panic в одном тестовом файле не влияет на другие тестовые файлы
- Дополнительный механизм отдельного Heap-контекста не требуется

### 7. Suite и несколько тестов (модель на значениях)

Тестовый файл может содержать несколько тестов. Организация внутри файла:

```yaoxiang
// tests/list_test.yx
use std.test
use std.list

push_grows_len = () => {
    xs = []
    list.append(xs, 1)
    test.assert_eq(list.len(xs), 1)
}

pop_returns_last = () => {
    xs = [1, 2]
    test.assert_eq(list.pop(xs), 2)
}

main = {
    test.suite([
        ("push_grows_len", push_grows_len),
        ("pop_returns_last", pop_returns_last),
    ])
}
```

- Каждый тест — функция без параметров, возвращающая `Result((), String)`; провал утверждения
  выражается через `Err` (семейство утверждений со значимой семантикой из §3) и не прерывает процесс
  — последующие тесты выполняются как обычно
- `test.suite` вызывает их поочерёдно и собирает результаты: если тест не Ok, выводятся его имя и
  диагностика; при Ok — вывод отсутствует
- Код выхода файла: все Ok в suite → 0; хотя бы один Err → ненулевой (правило определения exit code
  из §5 этапа выполнения сохраняется)
- Runner видит только файл и не выполняет сканирование на уровне функций: per-test вердикты целиком
  поступают из сбора внутри suite, внутренняя структура файла для runner прозрачна — принцип нулевых
  изменений компилятора не нарушается
- Явно не используются: внутрипроцессные catch-границы (закон 17 ключевых слов); вызов отдельных
  функций как точек входа из runner (допустимо только во внутренних сценариях вроде §8.2 — провал
  компиляции)
- Конкретная форма API `test.suite` (сигнатура, обработка дубликатов имён, взаимодействие `--filter`
  с именами suite) — деталь реализации, финализируется в #319

### 8. Трёхслойное проектирование негативных тестов (ожидаемый провал)

Негативные тесты разделяются по слою, в котором происходит провал; каждый слой получает своё место:

#### 8.1 Инверсия на уровне значений (общего назначения, для пользователя)

Тестируемая операция возвращает `Result`; тест обычным утверждением выражает ожидаемый провал:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
test.assert_eq(result.err_code(r), "E3017")
```

- std.test пополняется семейством функций `assert_not` / `assert_err`; унарная форма `!assert` будет
  предоставлена после реализации синтаксиса `not` (та же зависимость, что и `cond == false` в
  `assert_false`)
- Утверждения кода ошибки опираются на расширение значения `Error` машиночитаемым полем `code`:
  `Struct { message }` расширяется до `{ code, message }` (native-функция `error_new_with_code`,
  экспортируемые в std константы кодов), что позволяет проверять `err.code == "E3017"`
- По мере продвижения перевода на Result (#301, #316) операции, которые могут провалиться,
  поочерёдно возвращают `Result`, и файл-уровневые негативные метки в корпусе тестов мигрируют во
  внутрифайловые утверждения

#### 8.2 Провал компиляции (только для внутреннего использования разработчиками языка)

Компиляция — операция над целым файлом по принципу "всё или ничего", поэтому выразить внутри файла
"эта строка не должна компилироваться" невозможно. Сохраняются специальные файл-уровневые метки:

- Метка `[test:error]` читается runner'ом и вердикт инвертируется (ненулевой exit code run = PASS)
- Метка обновляется до **структурированного ожидаемого кода**: runner разбирает заголовок
  `预期: 编译错误 EXXXX` и сверяет его с фактическим `[EXXXX]` из stderr компилятора; несовпадение
  кода = FAIL (лёгкая версия идеи снапшотов stderr из trybuild; нулевые изменения компилятора)
- **Служит исключительно для корпуса тестов данного репозитория, а не для пользовательского
  тестового фреймворка**; соглашение о двух runner'ах зафиксировано (2026-09-03, #319): yx_runner
  (cargo test) и `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора меток в
  заголовке (`[test:error]` / `[test:ignore]` / `[test:runtime]` / `预期: EXXXX`, первые 16 строк);
  соглашение о каталоге 06-compile-errors упразднено

#### 8.3 Жёсткий провал в runtime (относится к переходу на Result)

Отдельный механизм не предусматривается — операции, которые могут провалиться, по направлению
развития языка возвращают `Result` (#301, #316), и тесты единообразно используют форму из §8.1.
Процессный abort (например, нарушение утверждения, ошибка параметров в runtime) по мере перехода на
Result постепенно сворачивается в значение; тестовый фреймворк не предоставляет для него специальной
семантики

## Связь с существующими системами

| Элемент                                                     | Связь                                                                                                                               |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Rust `#[test]`                                              | не затрагивается; внутренние тесты компилятора продолжают использовать Rust                                                         |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | обнаруживаются и выполняются `yaoxiang test`                                                                                        |
| `std.assert.assert(cond)`                                   | сохраняется для runtime-стражей; семейство утверждений `std.test` со значимой семантикой переводится на базу `std.result` (§3, §7)  |
| Модульная система (RFC-029)                                 | встроенные исходные модули подключаются через Registry/orchestrator; подключение CLI `run` к orchestrator — предварительное условие |
| Рефакторинг `#200` (`io.println` → `assert.assert`)         | полностью совпадает с направлением `yaoxiang test`                                                                                  |
| Аннотации `@`                                               | не используются; `@test` не вводится                                                                                                |

## Стратегия реализации

### Phase 1: ядро функциональности

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — ветвь исходного кода CLI `Run` делегирует
  `run_project` (предварительное условие для многофайлового запуска)
- `src/main.rs` — добавление подкоманды `Test`
- `src/std/test.yx` — добавление модуля на чистом YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарник
- orchestrator / Registry — поддержка загрузки `.yx`-модулей из встроенных источников по
  виртуальному пути
- Парсинг конфигурации RFC-015 — секция `[tool.test]`
- Выполнение в дочернем процессе (`--debug-info`) + отчёт

Результаты:

- `yaoxiang test` в основном готов
- 4 функции утверждений в `std.test`
- Обнаружение `tests/**/*.yx` по умолчанию
- Последовательное выполнение + формат вывода по умолчанию

### Phase 2: доработки

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Phase 3: расширения

- `--parallel` параллельное выполнение (зависит от доработки concurrency-модели spawn)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции утверждений (например, `assert_approx_eq` для Float)

## Риски и меры по их снижению

| Риск                                                           | Вероятность | Мера по снижению                                                                                                                                                                                                                                  |
| -------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбой интерполяции `f"..."` на Any                              | Отсутствует | Подтверждено 2026-08-02 (Int и String работают)                                                                                                                                                                                                   |
| Парсинг конфигурации `yaoxiang.toml` отсутствует в текущем CLI | Низкая      | Простое расширение, не затрагивает ядро                                                                                                                                                                                                           |
| Регрессия поведения при подключении CLI `run` к orchestrator   | Низкая      | Однофайловый путь без import эквивалентен; orchestrator покрыт интеграционными тестами                                                                                                                                                            |
| Встраивание `.yx` источников в бинарник увеличивает размер     | Низкая      | Файлы `.yx` очень малы, влияние пренебрежимо                                                                                                                                                                                                      |
| Время тестового цикла растёт с увеличением корпуса             | Высокая     | Главный фактор — полная перекомпиляция каждого файла (по замерам 11.3 с на 185 файлов), а не запуск дочернего процесса; `--parallel` снимает только процессную часть; стоимость компиляции требует кэширования тестового цикла (слайсы #251/#293) |

## Открытые вопросы

- [x] Корректно ли разрешается ссылка `use std.assert` в `std/test.yx`? — **Решено (2026-08-02)**.
      После реализации модульной системы (RFC-029) native- и исходные модули сосуществуют в
      Registry, resolver разрешает их единообразно, межвидовые зависимости работают естественно
- [x] Вводит ли обобщённый `to_string` в `f"..."` новые ограничения типов для тестового вывода? —
      **Решено (2026-08-02)**. Подтверждено, что на параметрах без аннотаций (Any) `==`/`!=` и
      интерполяция f-string работают (проверено на Int и String); новые ограничения не вводятся
- [x] Допустим ли обобщённый параметр `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в настоящее
      время не существует (и молча поглощается, открыт отдельный issue для отслеживания); функции
      утверждений в Phase 1 используют параметры без аннотаций и не зависят от системы обобщений
