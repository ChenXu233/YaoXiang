# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

В YaoXiang вводятся стандартный фреймворк тестирования в виде модуля `std.test` и подкоманда CLI
`yaoxiang test`. Тестовые файлы — это обычные файлы `.yx`; общий результат прохождения/провала
определяется кодом выхода дочернего процесса; внутри файла поддерживается несколько тестовых функций
— сбой утверждения выражается значением `Err` (семантика значений), набор тестов собирает
индивидуальные результаты каждого теста (§7). Модуль `std.test` реализован на чистом YaoXiang и
является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не возможность
компилятора — никаких изменений парсера, IR, байт-кода или исполнителя.

## Мотивация

### Зачем нужна среда тестирования?

Текущее покрытие тестами YaoXiang зависит от Rust-стороны `#[test]` и интеграционных тестов в
`tests/`. Это означает, что:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang
2. `#117 Модульные тесты стандартной библиотеки по модулям` блокируется, так как отсутствует
   доступная инфраструктура тестирования
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) не
   имеют средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: не вводить никаких новых ключевых слов или синтаксических
  конструкций
- **Нулевые изменения компилятора**: не трогать парсер, IR, байт-код, исполнитель
- **Приоритет self-hosting**: тестовая библиотека написана на YaoXiang, первая dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:  yaoxiang test [--filter --fail-fast --json ...]│
│              │                                               │
│  Уровень обнаружения: чтение yaoxiang.toml → [tool.test]     │
│              patterns                                       │
│              по умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Уровень выполнения: для каждого файла: yaoxiang run <file>  │
│              проверка кода выхода → последовательное         │
│              │                                               │
│  Уровень отчёта: PASS/FAIL → сводка                          │
│              поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Уровень утверждений: std.test (чистый YaoXiang, self-hosting)│
│              нижний уровень: std.assert.assert                │
│              диагностика: f"Expected {expected}, got {actual}"│
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Среда тестирования — не возможность компилятора, а инструмент CLI** — `yaoxiang run` уже умеет
   "выполнять тесты", `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводить сканирование аннотаций `@test`, секцию метаданных
   в байт-коде, специальную точку входа в исполнитель
3. **Self-hosting** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности берутся
   из `std.assert` / `std.result`
4. **Тестовый файл — обычный файл `.yx`** — файл запускается в дочернем процессе, код выхода
   определяет общий результат: пройден/провален
5. **Сбой утверждения — значение, а не событие процесса** — тестовая функция возвращает `Result`,
   сбой утверждения выражается через `Err`, набор тестов собирает индивидуальные результаты (§7);
   abort на уровне процесса относится только к стражам времени выполнения и не используется для
   тестовых утверждений

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      指定测试文件或目录（默认: 从 yaoxiang.toml 读取，否则 tests/）

Options:
  --filter <NAME>     只跑文件名包含 <NAME> 的测试
  --fail-fast         遇到第一个失败就停止
  --verbose, -v       显示每个测试的详细 stdout/stderr
  --list              只列出测试文件，不跑
  --no-progress       不显示进度输出（表头与 PASS 行）；FAIL 明细与汇总保留（CI 场景）
  --json              输出 JSON 格式结果（CI 集成用）
  --parallel          并行执行（每核一个 worker；与 [tool.test].parallel 取或）
```

#### Формат вывода

**Вывод по умолчанию** (индивидуальные результаты тестов берутся из сбора внутри набора в файле, см.
§7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**JSON-вывод** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы со сбоями дополнительно несут `exit_code` и `stderr` (диагностика дочернего процесса с
  удалёнными ANSI-кодами, для сбора доказательств в CI); при комбинации `--verbose` и `--json` все
  файлы содержат `stdout` / `stderr`
- `--no-progress` подавляет только вывод прогресса (заголовок и строки PASS) — детали FAIL и сводка
  всегда выводятся, сбои не замалчиваются; `--list` выводит по одному пути тестового файла на
  строку, без выполнения
- Каждый файл содержит `kind` (behavior / compile-error / runtime-error / invalid, §8.2), сводка
  содержит счётчик выполнения `by_kind` (фиксированные четыре ключа, без skipped); сводка для
  человека содержит строку распределения по категориям `Categories:`
- При `--parallel` строки прогресса для человека выводятся потоково в **порядке завершения**
  (блоками без чередования), JSON `files` сортируется по пути `file` для стабильности вывода
  (дружественно к diff в CI)
- Внутрифайловый массив per-test `tests` берётся из сбора набора тестов §7, вступает в силу с
  реализацией модели значений (#319)
- Официальный CI (`.github/workflows/ci.yml`, задача test) потребляет именно так: на стороне cargo
  запускается `--test integration` (интеграция CLI) и `--test yx_runner` (двойной страж корпуса),
  затем `yaoxiang test --json --parallel` запускается послойно — режим по умолчанию (языковой
  корпус) и явный `src/std/tests` (слой библиотеки) каждый производят отчёт; сводная таблица (total
  / passed / failed / skipped / time_secs и by_kind) записывается в сводку задания, для файлов со
  сбоями печатаются `kind` / `exit_code` / `stderr` для сбора доказательств, ненулевой выход любого
  набора — красный статус

### 2. Конфигурация yaoxiang.toml

Размещается в `[tool.test]`, соответствует соглашению о сторонних расширениях `[tool.*]` из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
exclude = ["tests/fixtures/**"]   # 命中者从发现集剔除（--list 同样剔除）
parallel = true                   # 并行执行（与 --parallel flag 取或）
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочее решение из коробки без
  настройки
- `exclude` и `patterns` одной формы (литеральный путь или `root/**…`, всегда совпадают по префиксу
  пути); исключённое означает, что это не тест, фикстуры, требующие проверки поведения во время
  выполнения, запускаются напрямую через `yaoxiang run`
- **Однофайловый режим** (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации —
  при явных путях ключи конфигурации `exclude`/`parallel` не действуют (кроме флага)
- В будущем может быть выделен в отдельный репозиторий (положение `[tool.test]` не меняется)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — 纯 YaoXiang 测试断言库（值语义标准形态，2026-09-03 落地）
// 第一个 dogfooding 库：YaoXiang 的测试库用 YaoXiang 写。

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not 与 assert_false 同体；assert_err / assert_err_code 见 §8.1
```

- Функции утверждений имеют **семантику значений**: возвращают `Result(Void, String)`, сбой
  выражается через `Err(диагностическое сообщение)` и не аварийно завершает процесс — набор тестов
  §7 на этом основании собирает индивидуальные результаты. Семантика аварийного завершения на уровне
  процесса `std.assert.assert` сохранена для стражей времени выполнения и не входит в путь тестовых
  утверждений. Полезная нагрузка `Ok` — `Void` (единичный тип по спецификации type-system.md; `()` —
  это пустой `Tuple`, оба не смешиваются — утверждено 2026-09-03)
- **Семейство из 7 функций (поставлено 2026-09-03, переходная версия с abort удалена)**: основанные
  на значениях `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (одно тело
  с `assert_false`, зарезервировано для переоформления `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (утверждение кода ошибки, §8.1)
  - `assert_approx_eq(a: Float, b: Float, eps: Float)` (Фаза 3, поставлено 2026-09-07): проверка
    `|a - b| <= eps`, `eps` задаётся вызывающей стороной **явно** — допуск является частью контракта
    тестирования, без скрытого значения по умолчанию; отрицательный `eps` — сразу `Err` в месте
    объявления, `NaN` всегда `Err`
- `assert_eq` / `assert_ne` используют **параметры с аннотацией `Any`** — `==`/`!=` и интерполяция
  f-string работают на `Any` нормально, без зависимости от системы дженериков. Обратите внимание,
  что параметры **должны быть аннотированы явно**: параметры без аннотации не проходят проверку
  вызова нативного дженерика `&Result(T, E)` (подтверждено зондом R1)
- `assert_false` / `assert_not` используют `cond == false` для отрицания (унарный синтаксис `not` не
  реализован, можно мигрировать после стабилизации; унарная форма `!assert` имеет ту же зависимость,
  см. §8.1)
- Форма блочного тела + явный `return`: тип then-ветви if-выражения отбрасывается при проверке,
  if-выражение с `Result` в обеих ветвях — слепое пятно проверки, реализация обходит это
- `std.test` не зависит от нативного кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевой проект)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (а также все будущие модули стандартной библиотеки, написанные на YaoXiang)
встраиваются в бинарник во время сборки:

```rust
// build.rs 或构建脚本，自动生成
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // 源代码文本
    // 未来更多
];
```

Модульная система (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения:
Registry одновременно содержит нативные и исходные модули, orchestrator отвечает за многофайловую
оркестровку. Порядок разрешения `use std.test`:

1. Сначала ищется нативный модуль Rust (существующий механизм, например `std.assert`)
2. Не найдено — ищется во встроенном `STD_YX_FILES`; при совпадении — **виртуальный путь**
   (например, `<std>/test.yx`) как начальный модуль инжектируется в orchestrator и проходит через
   обычный фронтенд-конвейер (parse → typecheck → IR)
3. Не найдено — идёт обнаружение в файловой системе (пользовательский модуль)

`use std.assert` внутри встроенного исходного модуля нормально разрешается resolver-ом в нативный
registry — нативные и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импорте.

Преимущества:

- В однофайловом режиме `use std.test` также работает
- Версия стандартной библиотеки строго связана с бинарником, несоответствие версий невозможно
- Не требует настройки пути к стандартной библиотеке пользователем

**Будущее: стандартная библиотека в файловой системе**

Когда режим проекта YaoXiang созреет, стандартная библиотека перейдёт в форму файловой системы.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение ревью 2026-08-02)**: CLI `run` подключается к orchestrator. Текущий CLI `run`
идёт через однофайловый конвейер (`run_file_with_diagnostics`) и не может разрешать импорт
пользовательских модулей; а модель дочернего процесса `yaoxiang test` наследует возможности CLI,
импорт проектных модулей тестовыми файлами — ключевой сценарий. Поэтому в Фазе 1 сначала делегируем
ветвь исходного кода CLI `Run` в `run_project` (orchestrator, рекурсивное обнаружение каталога);
#247 (обнаружение по `use` по требованию) после — как чистая оптимизация производительности.
Однофайловый режим без `import` через orchestrator ведёт себя эквивалентно, ветвь байт-кода не
меняется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, использовать указанные пути напрямую
2. Иначе читать `patterns` из `[tool.test]` в `yaoxiang.toml`
3. Если не настроено, по умолчанию `tests/**/*.yx`
4. Применить фильтр `--filter` (содержит имя файла)
5. Область обнаружения — это расслоение тестов (§9): паттерны по умолчанию покрывают только языковой
   корпус; слой тестов библиотек (например, `src/std/tests/`) обнаруживается через явные пути или
   конфигурацию пакета, не смешиваясь со сканированием по умолчанию

**Этап выполнения**:

1. Для каждого файла — маршрутизация выполнения по директивам заголовка (грамматика директив см. в
   §8.2, разбирается через `src/util/test_markers.rs`, общий с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run --debug-info <file>` (`--debug-info`
     заставляет ошибки времени выполнения содержать позиции в исходнике — 2026-08-02 подтверждено:
     трассировка стека выводит `file:line:col`); `// mode:` объявляет режим `--runtime` дочернего
     процесса
   - Категория отказа на этапе компиляции: одношаговый `yaoxiang check <file>`
   - Категория сбоя на этапе выполнения: два шага — `check` (должен пройти) + `run` (должен
     провалиться)
2. Файлы с `// skip: <причина>` пропускаются и учитываются как `skipped` в отчёте
3. Решение и сравнение с ожидаемыми кодами — по матрице решений §8.2; ошибка разбора директив —
   сразу `FAIL` без выполнения (отказ на этапе построения)
4. Захват `stdout`/`stderr` для отчёта
5. По умолчанию последовательно; `--parallel` (или `[tool.test].parallel`) запускает пул воркеров по
   числу ядер, каждый файл — всё ещё отдельный дочерний процесс — `skip`/`invalid` обрабатываются
   сначала в порядке обнаружения, результаты выполнения выводятся потоково в порядке завершения,
   JSON сортируется по пути (Фаза 3, поставлено 2026-09-07)
6. При `--fail-fast` — остановить диспетчеризацию новых файлов при первом `FAIL`; в параллельном
   режиме выполняемые файлы завершаются и учитываются

### 6. Изоляция тестов

Изоляция тестов естественно реализуется через границу на уровне процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет независимые Heap, Frame, NativeContext
- `panic` в одном тестовом файле не влияет на другие тестовые файлы
- Не требуется дополнительный механизм изолированного контекста Heap
- **Параллельное выполнение (Фаза 3) не расширяет границу изоляции**: рабочая директория (CWD) между
  дочерними процессами общая, параллельные тесты не должны занимать файлы с одинаковым путём в CWD —
  тесты с файловым I/O используют уникальные имена файлов и очищают их по завершении

### 7. Набор тестов и множественные тесты (модель значений)

Один тестовый файл может содержать несколько тестов. Внутрифайловая организация (реализована
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — функция без аргументов, возвращающая `Result(Void, String)`; сбой утверждения
  выражается через `Err` (семейство утверждений §3 с семантикой значений) и не прерывает процесс —
  последующие тесты продолжают выполняться
- `test.suite` вызывает по очереди и собирает: если тест не `Ok` — записываются имя и диагностика,
  `Ok` молча; после прогона всех при любом `Err` — аварийное завершение через `std.assert.assert` с
  деталями сбоев (`N of M test(s) failed` + для каждого `[FAIL] имя: диагностика`) — код выхода
  файла не 0 (решение §5 не меняется). Здесь `abort` — это страж времени выполнения тестового
  бинарника, а не путь утверждений; все `Ok` — тихий выход 0
- Тестовые функции верхнего уровня добавляются **в виде замыканий** (`("name", () => test_fn())`):
  имя функции верхнего уровня как ссылка на значение пока не поддерживается (ограничение уровня IR,
  `E3006`) — тело замыкания, вызывающее глобальные функции, не затронуто
- Runner видит только файл, не сканирует на уровне функций: индивидуальные результаты тестов
  полностью берутся из сбора внутри набора, внутренняя структура файла прозрачна для runner —
  принцип нулевых изменений компилятора не нарушается
- Явно не используется: внутрипроцессная граница `catch` (железное правило 17 ключевых слов); вызов
  функций по одной через точку входа runner (только для внутренних сценариев вроде ошибок компиляции
  в §8.2)
- Форма API утверждена (2026-09-03, #319):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дубликаты имён не
  обнаруживаются (имя используется только для отображения в отчёте); `--filter` фильтрует по имени
  файла, не видит имена тестов внутри набора

### 8. Трёхуровневое проектирование негативных тестов (ожидаемый сбой)

Негативные тесты разделяются по уровню возникновения сбоя, каждый уровень — на своём месте:

#### 8.1 Реверс на уровне значений (общий, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемый сбой обычными утверждениями:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// 或一句封装（码只存在于 std Error 载体上，E 钉死为 Error）：
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с семейством семантики значений
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса `not`
  (то же ограничение, что и `cond == false` у `assert_false`)
- Утверждение кода ошибки зависит от того, что значение `Error` несёт машиночитаемое поле `code` —
  реализовано #323 M4: `Error = { code, message }` (нативное `error_new(code, message)`); чтение
  через `result.unwrap_err(r)` для получения носителя + аксессоры `result.code(e)` /
  `result.message(e)` (предполагавшиеся на этапе проектирования именование `error_new_with_code`,
  экспорт констант кодов и доступ к полю `err.code` не приняты — в языке нет доступа к полям Struct,
  константы кодов не экспортированы)
- С продвижением Result-изации (#301, #316) операции, которые могут провалиться, постепенно
  возвращают `Result`, файловые негативные маркеры в корпусе мигрируют во внутрифайловые утверждения

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это «всё или ничего» для всего файла, невозможно выразить внутри файла «эта строка не
должна компилироваться»; для сбоев во время выполнения также требуется выражение на уровне файла
(например, набор тестов содержит заведомо провальный тест). В заголовке файла ожидания объявляются
**структурированными директивами**, runner маршрутизирует решение по категории ожидания
(маршрутизация утверждена 2026-09-03; грамматика директив утверждена и реализована 2026-09-06).

Грамматика директив заголовка (`// key: value`, в пределах первых 16 строк, строгое совпадение
токенов):

```text
// expect: compile-error E1002 [E1003 ...]   编译期拒绝测试
// expect: runtime-error E6003 [...]         运行期失败测试
// skip: <原因>                              跳过执行，计入 skipped
// mode: embedded|standard|full              子进程 --runtime 模式（仅 run 步消费）
```

- Отсутствие директивы `expect:` = поведенческий тест. `expect:` — **единственное объявление**
  ожидания — 2026-09-06 утверждён отказ от булевых маркеров `[test:error]` и прозаического
  извлечения кодов из китайского `预期:`: булевый маркер и строка ожидания — два слабо связанных
  факта, поддержание согласованности дисциплиной неизбежно дрейфует; строгая токенная грамматика на
  английском позволяет runner механически разбирать (`kind` + коды — все фиксированные токены, любой
  лишний токен после кода — ошибка разбора), ошибка разбора = сразу `FAIL` без выполнения — тихий
  канал деградации для ошибочных директив не существует (отказ на этапе построения)
- **Категория ошибки компиляции**: одношаговый `check` — должен провалиться и вывод должен содержать
  все `[EXXXX]`; компиляция прошла = `FAIL` (должны были сообщить, но не сообщили), отказ, но код не
  совпал = `FAIL`. Синтаксические ошибки (E1xxx, секция разбора) и семантические ошибки (E2xxx+) не
  выделяются в отдельные категории — ожидаемый код сам фиксирует фазу
- **Категория ошибки времени выполнения**: двухшаговое решение — `check` должен **пройти**
  (компиляция невиновна), `run` должен провалиться и вывод должен содержать все `[EXXXX]`. Взрыв на
  этапе компиляции = `FAIL` — ключевое решение, противоположное по направлению категории ошибки
  компиляции, предотвращающее пропуск «компиляция случайно прошла, выполнение случайно провалилось»
- Идентично индустрии: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`, Clang
  `expected-error` — все объявляют ожидания в комментариях фикстуры и сравнивают двусторонне через
  harness; они используют привязку на уровне строк, потому что мультидиагностические компиляторы
  должны различать несколько ожиданий в одном файле, а наш компилятор останавливается на первой
  ошибке (одна диагностика на файл) — уровень файла — это и есть реальность компилятора; после
  реализации восстановления после ошибок можно добавить форму привязки к строке (файловые директивы
  заголовка + ожидания уровня функций в Cranelift filetests — та же смешанная форма)
- Известный долг рендеринга: диагностика на этапе разбора сейчас выводится в форме Debug
  (`code: "E0012"` вместо `[E0012]`), сканер кодов принимает обе формы; после унификации рендеринга
  диагностики строгая форма будет восстановлена
- **Обслуживает только корпус этого репозитория, не часть пользовательского фреймворка
  тестирования**; соглашение о решении между двумя runner закрыто (2026-09-03, #319): yx_runner
  (cargo test) и `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора
  директив заголовка, соглашение о каталоге 06-compile-errors упразднено. Уровень отчёта выдаёт
  счётчики по категориям: сводка для человека содержит строку `Categories:`, JSON-сводка содержит
  `by_kind` (behavior / compile-error / runtime-error / invalid, `skipped` считается отдельно),
  каждый файл содержит `kind`

#### 8.3 Аппаратные сбои времени выполнения (отнесены к Result-изации)

Отдельный механизм не заводится — операции, которые могут провалиться, возвращают `Result` по
направлению языка (#301, #316), тесты унифицированно выражаются через §8.1. `Abort` на уровне
процесса (например, нарушение утверждения, ошибка параметра времени выполнения) постепенно
сворачивается в значения с Result-изацией, фреймворк тестирования не предоставляет для них
специальной семантики. (Внимание: маркерное решение «категории ошибки времени выполнения» в §8.2 —
это канал проверки runner на уровне файла для **операций, ещё не поддающихся Result-изации**, и не
противоречит семантическому направлению этого раздела — второе есть конечная цель, первое — канал
переходного периода)

### 9. Расслоение системы тестирования: языковой корпус и тесты библиотек (утверждено 2026-09-03)

Тесты разделяются на два слоя по **объекту тестирования**, у каждого своя принадлежность и
сопровождающий; система маркеров (§8.2) и библиотека утверждений (§3) — общие для обоих уровней:

**Слой 1: языковой корпус (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык** — парсер, система типов, модули, конкурентность, ownership,
  отказы на этапе компиляции, семантика времени выполнения; каталог организован по главам
  спецификации языка
- `std` в корпусе выступает только как **инструмент утверждений** (`std.assert` / `std.test`),
  никогда не тестируется — поведение API библиотеки не относится к языковой доступности
- Внутри корпуса маршрутизация по §8 на три категории решений: поведенческие тесты / отказы на этапе
  компиляции / сбои на этапе выполнения

**Слой 2: тесты библиотек (вместе с библиотекой)**

- Объект тестирования — **публичный контракт API библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся в **собственном пакете библиотеки**: пакет `std` — это `src/std/`, его тесты уровня
  `yx` идут в `src/std/tests/` (в одном месте с реализацией; каталог сосуществует с модульными
  тестами Rust, типы файлов не пересекаются); тесты самого `std.test` тоже там — `std.test`
  тестируется через `std.test` (замкнутый цикл self-hosting)
- Будущие пользовательские пакеты следуют той же конвенции: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (тестовая компоновка пакетного менеджера RFC-014 предварительно
  отработана)
- Обнаружение не входит в patterns по умолчанию (паттерн по умолчанию `tests/**/*.yx` покрывает
  только языковой слой): слой тестов библиотек обнаруживается через явный путь
  (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI запускается по слоям

Заметка о миграции: **мигрировано (2026-09-06)** — 19 файлов из исходного `tests/yaoxiang/07-std/`,
после индивидуального отбора все оказались тестами библиотек (объекты тестирования — API-контракты
модулей `std`; языковые возможности вроде распространения `?`, автоматического заимствования,
инстанцирования дженериков играют там роль носителей, а не объектов тестирования), целиком
перенесены в `src/std/tests/`, каталог 07-std удалён; yx_runner переключён на обнаружение с двумя
корнями (`tests/yaoxiang/` + `src/std/tests/`), patterns по умолчанию не содержат слой библиотек
(интеграционные тесты фиксируют этот контракт). Языковой корпус отныне не содержит тестов std-API.
