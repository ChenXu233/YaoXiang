# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Внедрение в YaoXiang стандартного фреймворка тестирования — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы — обычные файлы `.yx`, общий результат pass/fail определяется по
коду выхода дочернего процесса; внутри файла поддерживается несколько тестовых функций —
непрохождение утверждения выражается значением `Err` (value-семантика), а набор собирает per-test
вердикты (§7). Модуль `std.test` реализован на чистом YaoXiang и является первой
dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не возможность компилятора — никаких
изменений в парсере, IR, байткоде или исполнителе.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время тестовое покрытие YaoXiang полагается на `#[test]` со стороны Rust и
интеграционные тесты в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   нельзя писать на YaoXiang
2. Покрытие модульными тестами стандартной библиотеки заблокировано из-за отсутствия доступной
   тестовой инфраструктуры
3. Регрессионное тестирование возможностей языка (например, изменение семантики spawn в RFC-032) не
   имеет средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения в компиляторе**: парсер, IR, байткод и исполнитель не затрагиваются
- **Приоритет самобутстрэпа**: тестовая библиотека пишется на YaoXiang — первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Слой CLI:    yaoxiang test [--filter --fail-fast --json ...]│
│                │                                             │
│  Слой обнаружения:  чтение yaoxiang.toml → [tool.test] patterns│
│                по умолчанию: tests/**/*.yx                    │
│                │                                             │
│  Слой исполнения:  для каждого файла: yaoxiang run <file>     │
│                проверка кода выхода → последовательное       │
│                выполнение                                    │
│                │                                             │
│  Слой отчёта:  PASS/FAIL → сводка                            │
│                поддержка --json / --verbose / --fail-fast    │
│                                                              │
│  Слой утверждений: std.test (чистый YaoXiang, самобутстрэп)  │
│                низкий уровень: std.assert.assert              │
│                диагностика: f"Expected {expected}, got {actual}"│
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — не возможность компилятора, а инструмент CLI** — `yaoxiang run` уже
   умеет «выполнять тесты», `yaoxiang test` лишь запускает все файлы и показывает отчёт
2. **Нулевые изменения в компиляторе** — не вводятся сканирование аннотаций `@test`, сегмент
   метаданных в байткоде, специальная точка входа в исполнителе
3. **Самобутстрэп** — модуль `std.test` реализован на чистом YaoXiang, низкоуровневые возможности
   берутся из `std.assert` / `std.result`
4. **Тестовые файлы — обычные файлы `.yx`** — файл запускается как дочерний процесс, общий результат
   pass/fail определяется по коду выхода
5. **Непрохождение утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, непрохождение выражается как `Err`, набор собирает per-test вердикты поочерёдно (§7);
   аварийное завершение на уровне процесса относится только к рантайм-стражам и не используется для
   тестовых утверждений

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [ОПЦИИ] [ПУТИ]

Аргументы:
  [ПУТИ]...         Указанные тестовые файлы или каталоги (по умолчанию: читается из yaoxiang.toml, иначе tests/)

Опции:
  --filter <ИМЯ>     Запускать только тесты, имя файла которых содержит <ИМЯ>
  --fail-fast        Остановиться при первом непрохождении
  --verbose, -v      Показывать подробный stdout/stderr каждого теста
  --list             Только перечислить тестовые файлы, не запускать
  --no-progress      Не показывать индикатор прогресса (заголовок и строки PASS);
                     подробности FAIL и сводка сохраняются (сценарий CI)
  --json             Вывод результатов в формате JSON (для интеграции с CI)
  --parallel         Параллельное выполнение (по одному воркеру на ядро; логическое ИЛИ с [tool.test].parallel)
```

#### Формат вывода

**Вывод по умолчанию** (per-test вердикты поступают из сбора набором внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**Вывод JSON** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Файлы с непрохождением дополнительно несут `exit_code` и `stderr` (диагностика дочернего процесса
  с удалёнными ANSI-кодами, для разбора в CI); при комбинации `--verbose` и `--json` все файлы несут
  `stdout` / `stderr`
- `--no-progress` подавляет только индикатор прогресса (заголовок и строки PASS) — подробности FAIL
  и сводка выводятся всегда, непрохождение не может быть скрыто; `--list` выводит по одной строке с
  путём тестового файла без выполнения
- Каждый файл снабжён `kind` (behavior / compile-error / runtime-error / invalid, §8.2), сводка
  снабжена `by_kind` с количеством выполнений (фиксированные четыре ключа, без skipped);
  человеческая сводка содержит строку распределения `Categories:`
- В режиме `--parallel` строки человеческого прогресса выводятся потоково **по порядку завершения**
  (блоками без чередования), JSON-массив `files` сортируется по пути `file` для стабильности вывода
  (дружелюбно к diff в CI)
- Массив `tests` внутри файла с per-test вердиктами поступает из сбора набором согласно §7 и
  вступает в силу по мере реализации value-модели
- Официальный CI (`.github/workflows/ci.yml`, job test) потребляет именно так: на стороне cargo
  запускаются `--test integration` (интеграция CLI) и `--test yx_runner` (двухкорневой страж
  корпуса), затем `yaoxiang test --json --parallel` выполняет послойный прогон — режим по умолчанию
  (языковой корпус) и явный `src/std/tests` (слой библиотек) выдают каждый свой отчёт; сводная
  таблица (total / passed / failed / skipped / time_secs и by_kind) записывается в job summary, для
  файлов с непрохождением печатаются `kind` / `exit_code` / `stderr` для разбора, ненулевой выход
  любого набора означает красный статус

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
exclude = ["tests/fixtures/**"]   # попадающие под exclude исключаются из набора обнаружения (--list также исключает)
parallel = true                   # параллельное выполнение (логическое ИЛИ с флагом --parallel)
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает рабочую конфигурацию из
  коробки
- `exclude` имеет ту же форму, что и `patterns` (литеральный путь или `root/**…`, всегда совпадение
  по префиксу пути); исключённое означает не тест — фикстуры, требующие проверки поведения во время
  выполнения, запускаются напрямую через `yaoxiang run`
- **Одиночный файловый режим (`yaoxiang test foo.yx`) запускается напрямую, конфигурация не
  читается** — при явных путях ключи конфигурации `exclude`/`parallel` не действуют (за исключением
  флагов)
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль `std.test` (чистый YaoXiang)

```yaoxiang
// std/test.yx — чистая YaoXiang библиотека утверждений для тестов (value-семантика, стандартная форма, реализована 2026-09-03)
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang написана на YaoXiang.

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not и assert_false той же формы; assert_err / assert_err_code см. §8.1
```

- Функции утверждений имеют **value-семантику**: возвращают `Result(Void, String)`, непрохождение
  выражается как `Err(диагностическое_сообщение)`, без аварийного завершения процесса — набор в §7
  собирает на этой основе per-test вердикты. Процессная семантика аварийного завершения
  `std.assert.assert` сохранена для рантайм-стражей и не попадает в путь тестовых утверждений.
  Полезная нагрузка Ok — `Void` (согласно type-system.md — это unit; `()` — пустой Tuple, эти две
  сущности не смешиваются — закреплено 2026-09-03)
- **Семейство функций — 7 (доставлены 2026-09-03, переходная abort-версия удалена)**: value-варианты
  `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not` (той же формы, что и
  assert_false, зарезервировано для будущей формы `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (утверждение кода ошибки, §8.1)
  - `assert_approx_eq(a: Float, b: Float, eps: Float)` (Фаза 3, доставка 2026-09-07): предикат
    `|a - b| <= eps`, eps задаётся вызывающей стороной **явно** — допуск является частью контракта
    теста, без скрытых значений по умолчанию; отрицательный eps в месте объявления сразу даёт Err,
    NaN всегда даёт Err
- `assert_eq` / `assert_ne` используют **параметры с аннотацией Any** — `==`/`!=` и f-string
  интерполяция корректно работают на Any без зависимости от системы дженериков. Обратите внимание:
  **параметры должны иметь явную аннотацию** — параметры без аннотации не проходят проверку вызова
  для native-дженериков `&Result(T, E)` (подтверждено пробником R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный синтаксис `not`
  пока не реализован, перенос возможен после стабилизации; унарная форма `!assert` имеет ту же
  зависимость, см. §8.1)
- Форма тело-блока + явный `return`: тип then-ветви if-выражения отбрасывается при проверке,
  if-выражение с Result в обеих ветвях является слепой зоной проверки, реализация обходит это
- `std.test` не зависит от какого-либо native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое решение)

**Фаза 1: встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраиваются в
бинарник во время сборки:

```rust
// build.rs или скрипт сборки, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // текст исходного кода
    // далее больше
];
```

Модульная система (RFC-029, полностью реализована 2026-08-02) предоставляет точку подключения:
Registry одновременно содержит native-модули и исходные модули, orchestrator отвечает за оркестровку
многих файлов. Порядок разрешения `use std.test`:

1. Сначала ищется native-модуль на стороне Rust (существующий механизм, например `std.assert`)
2. Если не найдено — поиск во встроенных `STD_YX_FILES` — при попадании исходный модуль
   инжектируется в orchestrator как **виртуальный путь** (например, `<std>/test.yx`) в качестве
   начального модуля, проходя через обычный фронтенд-конвейер (parse → typecheck → IR)
3. Если не найдено — обнаружение через файловую систему (пользовательские модули)

`use std.assert` внутри встроенного исходного модуля нормально разрешается резолвером в
native-реестр — native и исходные модули сосуществуют в Registry, кросс-родовая зависимость работает
естественно. Встроенные модули **компилируются по требованию**: попадают в конвейер только при
импорте.

Преимущества:

- В одиночном файловом режиме `use std.test` также работает
- Версия стандартной библиотеки строго привязана к бинарнику, рассогласования версий невозможны
- Не требуется конфигурация пути стандартной библиотеки пользователем

**В будущем: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предварительное условие (решение ревью 2026-08-02)**: CLI `run` подключается к orchestrator. В
текущем виде CLI `run` идёт через одиночный файловый конвейер (`run_file_with_diagnostics`) и не
может разрешать импорты пользовательских модулей; тогда как модель дочерних процессов
`yaoxiang test` наследует возможности CLI, а импорт тестовыми файлами проектных модулей — ключевой
сценарий. Поэтому в Фазе 1 исходная ветвь CLI `Run` сначала делегируется в `run_project`
(orchestrator, рекурсивное обнаружение по каталогу); обнаружение по use по требованию остаётся как
чистая оптимизация производительности. Одиночный файл без импортов через orchestrator ведёт себя
эквивалентно, байткодовая ветвь не меняется.

**Этап обнаружения**:

1. Если указаны `[ПУТИ]`, используются они напрямую
2. Иначе читаются `patterns` из `[tool.test]` в `yaoxiang.toml`
3. При отсутствии конфигурации — по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (имя файла содержит подстроку)
5. Область обнаружения соответствует тестовой стратификации (§9): patterns по умолчанию покрывают
   только корпус языковой доступности; слой библиотечных тестов (например, `src/std/tests/`)
   обнаруживается через явные пути или конфигурацию пакета и не подмешивается в сканирование по
   умолчанию

**Этап выполнения**:

1. Для каждого файла выполняется маршрутизация по заголовочной директиве (грамматика директив см.
   §8.2, разбирается через `src/util/test_markers.rs`, общий с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run <file>` (ошибки времени выполнения по
     умолчанию несут позицию в исходнике и кадр стека — debug_map генерируется по умолчанию, stack
     trace выводит `file:line:col`); `// mode:` объявляет режим `--runtime` дочернего процесса
   - Класс отказа на этапе компиляции: один шаг `yaoxiang check <file>`
   - Класс сбоя на этапе выполнения: два шага — `check` (должен пройти) + `run` (должен провалиться)
2. Файлы с `// skip: <причина>` пропускаются и учитываются в skipped отчёта
3. Сравнение вердикта с ожидаемым кодом выполняется по матрице §8.2; ошибка разбора директивы
   приводит к немедленному FAIL без выполнения (отказ на этапе конструирования)
4. Захватываются stdout/stderr для отчёта
5. По умолчанию — последовательно; при `--parallel` (или `[tool.test].parallel`) запускается пул
   воркеров по числу доступных ядер, каждый файл по-прежнему — отдельный дочерний процесс —
   skip/invalid обрабатываются первыми в порядке обнаружения, результаты выполнения выводятся
   потоково по порядку завершения, JSON сортируется по пути (Фаза 3, доставка 2026-09-07)
6. При `--fail-fast` планирование новых файлов останавливается сразу при первом FAIL; в параллельном
   режиме уже выполняющиеся файлы завершаются и учитываются

### 6. Изоляция тестов

Изоляция тестов естественным образом обеспечивается границей на уровне процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственный Heap, Frame, NativeContext
- Паника одного тестового файла не влияет на другие
- Не требуется дополнительный механизм отдельного Heap-контекста
- **Параллельное выполнение (Фаза 3) не расширяет границу изоляции**: рабочий каталог (CWD) дочерних
  процессов общий, параллельные тесты не должны занимать файлы с одинаковым путём в CWD — тесты с
  файловым I/O используют уникальные имена файлов и очищают их по завершении

### 7. Наборы и множество тестов (value-модель)

Один тестовый файл может содержать несколько тестов. Способ организации внутри файла (реализовано
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — это функция без аргументов, возвращающая `Result(Void, String)`; непрохождение
  утверждения выражается как `Err` (value-семантика семейства утверждений из §3), процесс не
  прерывается — последующие тесты продолжают выполняться
- `test.suite` вызывает поочерёдно и собирает: не-Ok тест записывает имя и диагностику, Ok молча;
  после прогона при наличии любого Err происходит останов через `std.assert.assert` с подробностями
  непрохождения (`N of M test(s) failed` + каждый элемент `[FAIL] имя: диагностика`) — код выхода
  файла ненулевой (правило §5 не меняется). Здесь abort — это рантайм-страж тестового бинарника, а
  не путь утверждения; при всех Ok — тихий выход с кодом 0
- Тестовые функции верхнего уровня вносятся в список **в форме замыканий**
  (`("name", () => test_fn())`): ссылка на имя функции верхнего уровня как значение пока не
  поддерживается (ограничение уровня IR, `E3006`) — вызов глобальной функции из тела замыкания не
  затронут
- Runner видит только файл, сканирования на уровне функций не выполняет: per-test вердикты поступают
  целиком из сбора внутри набора, внутренняя структура файла прозрачна для runner — принцип нулевых
  изменений в компиляторе не нарушается
- Явно не применяется: границы перехвата внутри процесса (железное правило 17 ключевых слов); вызов
  runner-ом поточечно по точкам входа функций (только для внутренних сценариев §8.2 вроде отказа
  компиляции)
- Форма API закреплена (2026-09-03):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дубликаты имён не
  обнаруживаются (имя используется только для отображения в отчёте); `--filter` фильтрует по имени
  файла и не различает имена тестов внутри набора

### 8. Трёхуровневое проектирование негативных тестов (ожидаемое непрохождение)

Негативные тесты разделяются по слою возникновения непрохождения, каждый уровень имеет своё место:

#### 8.1 Value-уровень обратного (универсальный, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемое непрохождение обычным
утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// или однострочная обёртка (код существует только на носителе Error в std, E закреплено как Error):
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` доставлены вместе с value-семантическим семейством
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса `not`
  (та же зависимость, что и `cond == false` для `assert_false`)
- Утверждение кода ошибки зависит от того, что значение `Error` несёт машиночитаемое поле `code` —
  уже реализовано: `Error = { code, message }` (native `error_new(code, message)`), чтение через
  `result.unwrap_err(r)` для извлечения носителя и аксессоры `result.code(e)` / `result.message(e)`
  (на этапе проектирования предполагавшиеся именование `error_new_with_code`, экспорт констант кодов
  и доступ к полю `err.code` не были приняты — в языке нет доступа к полям Struct, константы кодов
  не экспортируются)
- По мере продвижения Result-изации операции, которые могут провалиться, по одной начинают
  возвращать `Result`, и файловые негативные маркеры в корпусе мигрируют в файловые утверждения

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это «всё или ничего» для всего файла, невозможно выразить внутри файла «эта строка не
должна компилироваться»; непрохождение во время выполнения также требует файлового выражения
(например, набор содержит обязательно проваливающийся тест). Заголовок файла объявляет ожидание
**структурированной директивой**, runner выполняет **маршрутизацию и вынесение вердикта** по
ожидаемой категории (маршрутизация закреплена 2026-09-03; грамматика директив закреплена и
реализована 2026-09-06).

Грамматика заголовочных директив (`// key: value`, в пределах первых 16 строк, строгое совпадение
токенов):

```text
// expect: compile-error E1002 [E1003 ...]   тест отказа на этапе компиляции
// expect: runtime-error E6003 [...]         тест сбоя на этапе выполнения
// skip: <причина>                            пропуск выполнения, учитывается в skipped
// mode: embedded|standard|full              режим --runtime дочернего процесса (только для шага run)
```

- Отсутствие директивы `expect:` = поведенческий тест. `expect:` — это **единственное объявление**
  ожидания — 2026-09-06 закреплён отказ от булевого маркера `[test:error]` и прозаического
  вытаскивания китайского `预期:`: булевый маркер и строка ожидания — два слабо связанных факта,
  удерживаемых дисциплиной, неизбежно расходятся; строгая токенная грамматика на английском
  позволяет runner разбирать механически (kind + коды — фиксированные токены, любой посторонний
  токен после кода приводит к ошибке разбора), ошибка разбора = не выполнять, сразу FAIL — канал
  тихой деградации при ошибочном объявлении директивы отсутствует (отказ на этапе конструирования)
- **Класс ошибки компиляции**: один шаг `check` — должен провалиться, и вывод должен содержать все
  `[EXXXX]`; успешная компиляция = FAIL (ожидаемая ошибка не выдана), отказ с несоответствующим
  кодом = FAIL. Синтаксические ошибки (E1xxx, этап парсинга) и семантические (E2xxx+) не выделяются
  в отдельные категории — сам ожидаемый код закрепляет этап
- **Класс ошибки времени выполнения**: двухшаговый вердикт — `check` должен **пройти** (невиновен на
  этапе компиляции), `run` должен провалиться, и вывод должен содержать все `[EXXXX]`. Сбой уже на
  этапе компиляции = FAIL (ключевой вердикт, противоположный классу ошибки компиляции, предотвращает
  пропуск случая «компиляция случайно прошла, выполнение с натяжкой провалилось»)
- Изоморфно индустрии: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`, Clang
  `expected-error` — все объявляют ожидания в комментариях фикстуры и двусторонне сверяются
  harness-ом; они используют построчные якоря потому, что многодиагностическому компилятору нужно
  различать многие ожидания в одном файле, наш компилятор останавливается на первой ошибке, один
  файл — одна диагностика, файловый уровень изоморфен реальности компилятора — после внедрения
  восстановления ошибок в грамматику можно добавить построчную якорную форму (смешанная форма из
  заголовка файла + ожиданий уровня функций в Cranelift filetests — та же)
- Известный долг рендеринга: диагностика на этапе parse сейчас выводится в форме Debug
  (`code: "E0012"` вместо `[E0012]`), сканер кодов принимает обе формы; после унификации рендеринга
  диагностики строгая форма возвращается
- **Служит только корпусу данного репозитория, не является частью пользовательского фреймворка
  тестирования**; соглашение о двух runner закреплено (2026-09-03): yx_runner (cargo test) и
  `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора заголовочных директив,
  соглашение о каталоге 06-compile-errors упразднено. Слой отчёта выдаёт подсчёт по категориям:
  человеческая сводка содержит строку `Categories:`, JSON-сводка содержит `by_kind` (behavior /
  compile-error / runtime-error / invalid, skipped учитывается отдельно), каждый файл содержит
  `kind`

#### 8.3 Жёсткий сбой времени выполнения (отнесён к Result-изации)

Отдельный механизм не вводится — операции, которые могут провалиться, по направлению языка
возвращают `Result`, тесты единообразно выражаются через §8.1. Аварийное завершение на уровне
процесса (например, нарушение утверждения, неверная позиция рантайм-параметра) по мере Result-изации
постепенно сворачивается в значение, фреймворк тестирования не предоставляет для него специальной
семантики. (Замечание: маркер «класс ошибки времени выполнения» из §8.2 — это канал runner-а для
файловой проверки операций, ещё не поддающихся Result-изации, и не противоречит семантическому
направлению данного раздела — последний является конечной точкой, первый — миграционным каналом)

### 9. Стратификация системы тестирования: языковой корпус и библиотечные тесты (закреплено 2026-09-03)

Тесты делятся на **два слоя по объекту тестирования**, каждый со своей принадлежностью и
сопровождающим; система маркеров (§8.2) и библиотека утверждений (§3) — общие для обоих уровней:

**Первый слой: корпус языковой доступности (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык** — парсер, система типов, модули, конкурентность, ownership,
  отказы на этапе компиляции, семантика времени выполнения; каталоги организованы по разделам
  языковой спецификации
- std в корпусе выступает только **инструментом утверждений** (`std.assert` / `std.test`), никогда
  не тестируется — поведение API библиотеки не относится к языковой доступности
- Внутри корпуса согласно §8 разделяется на три категории вердиктов: поведенческие тесты / тесты
  отказа на этапе компиляции / тесты сбоя на этапе выполнения

**Второй слой: библиотечные тесты (рядом с библиотекой)**

- Объект тестирования — **публичный API-контракт библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся **внутри пакета самой библиотеки**: пакет std — это `src/std/`, его yx-уровневые
  тесты относятся к `src/std/tests/` (вместе с реализацией; каталог сосуществует с модульными
  тестами на Rust, типы файлов не пересекаются); тесты самого `std.test` также находятся здесь
  (тестирование std.test через std.test, замыкание самобутстрэпа)
- В будущем пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (макет тестового размещения в пакетах — репетиция для управления
  пакетами из RFC-014)
- Обнаружение не входит в patterns по умолчанию (по умолчанию `tests/**/*.yx` покрывает только
  языковой слой): слой библиотечных тестов обнаруживается через явные пути
  (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI выполняет послойно

Миграционная заметка: **миграция выполнена (2026-09-06)** — 19 файлов из бывшего
`tests/yaoxiang/07-std/` после индивидуального разбора оказались целиком библиотечными тестами
(объекты тестирования — API-контракты модулей std; роль языковых возможностей наподобие
распространения `?`, автоматического заимствования, инстанцирования дженериков в них — носители, а
не объекты тестирования), полностью перенесены в `src/std/tests/`, каталог 07-std упразднён;
yx_runner переведён на двухкорневое обнаружение (`tests/yaoxiang/` + `src/std/tests/`), patterns по
умолчанию не содержат слой библиотек (интеграционные тесты закрепляют этот контракт). Языковой
корпус с тех пор не содержит тестов API std.

## Открытые вопросы

- [x] Может ли ссылка `use std.assert` в `std/test.yx` корректно разрешаться? — **Решено
      (2026-08-02)**. После реализации модульной системы (RFC-029) native и исходные модули
      сосуществуют в Registry, резолвер разрешает единообразно, кросс-родовая зависимость работает
      естественно
- [x] Вносит ли обобщённый `to_string` из `f"..."` в выводе тестов новые ограничения типов? —
      **Решено (2026-08-02)**. Подтверждено, что на параметрах без аннотации (Any) `==`/`!=` и
      f-string интерполяция работают (проверено на Int/String), новых ограничений не вводится
- [x] Осуществимость параметра-дженерика `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в
      настоящее время не существует (и молча поглощается, отслеживается отдельным issue), функции
      утверждений Фазы 1 используют параметры без аннотации, не полагаясь на систему дженериков
