# RFC-036: Тестовый фреймворк std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного тестового фреймворка — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`; общий результат
прохождения/провала определяется по exit code дочернего процесса. Внутри файла поддерживается
несколько тестовых функций — сбой утверждения выражается значением `Err` (value-семантика), а набор
(suite) собирает per-test решения (§7). Модуль `std.test` реализован на чистом YaoXiang и является
первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не функция компилятора: не
затрагивает parser, IR, байт-код или исполнитель (executor).

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang опирается на `#[test]` на стороне Rust и интеграционные
тесты в `tests/`. Это означает следующее:

1. Юнит-тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang.
2. Задача `#117 Покрытие юнит-тестами модулей стандартной библиотеки` заблокирована из-за отсутствия
   доступной тестовой инфраструктуры.
3. Регрессионное тестирование языковых возможностей (например, изменение семантики spawn в RFC-032)
   не имеет автоматизированных средств.

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: не вводятся никакие новые ключевые слова или синтаксические
  конструкции.
- **Нулевые изменения в компиляторе**: не затрагиваются parser, IR, байт-код, исполнитель.
- **Приоритет самобутстрапа**: тестовая библиотека пишется на YaoXiang — это первая
  dogfooding-библиотека.

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:    yaoxiang test [--filter --fail-fast --json ...] │
│                    │                                          │
│  Уровень обнаружения: чтение yaoxiang.toml → [tool.test] patterns│
│                    по умолчанию: tests/**/*.yx                 │
│                    │                                          │
│  Уровень выполнения: для каждого файла: yaoxiang run <file>   │
│                    проверка exit code → последовательное      │
│                    выполнение                                 │
│                    │                                          │
│  Уровень отчёта:  PASS/FAIL → сводка                          │
│                    поддержка --json / --verbose / --fail-fast │
│                                                              │
│  Уровень утверждений: std.test (чистый YaoXiang, самобутстрап)│
│                    низкий уровень: std.assert.assert           │
│                    диагностика: f"Expected {expected}, got {actual}" │
└──────────────────────────────────────────────────────────────┘
```

### Базовые принципы

1. **Тестовый фреймворк — не функция компилятора, а инструмент CLI.** `yaoxiang run` уже способен
   «выполнять тесты»; `yaoxiang test` лишь помогает запустить все файлы и показать отчёт.
2. **Нулевые изменения в компиляторе.** Не вводятся сканирование аннотации `@test`, секции
   метаданных в байт-коде, специальные точки входа в исполнителе.
3. **Самобутстрап.** Модуль `std.test` реализован на чистом YaoXiang, базовые возможности опираются
   на `std.assert` / `std.result`.
4. **Тестовые файлы — обычные `.yx`-файлы.** Файл запускается как дочерний процесс, exit code
   определяет общий результат.
5. **Сбой утверждения — значение, а не событие процесса.** Тестовая функция возвращает `Result`;
   сбой утверждения выражается через `Err`; suite собирает per-test решения по каждому тесту (§7).
   Abort на уровне процесса относится только к runtime-guard'ам и не используется для тестовых
   утверждений.

## Детальный дизайн

### 1. Дизайн CLI

```
yaoxiang test [OPTIONS] [PATHS]

Аргументы:
  [PATHS]...      Указанные тестовые файлы или каталоги (по умолчанию: читаются
                  из yaoxiang.toml, иначе tests/)

Параметры:
  --filter <NAME>     Запускать только тесты, имя файла которых содержит <NAME>
  --fail-fast         Остановиться при первом сбое
  --verbose, -v       Показывать подробный stdout/stderr каждого теста
  --list              Только перечислить тестовые файлы, не запускать
  --no-progress       Не показывать индикатор прогресса (сценарий CI)
  --json              Выводить результаты в формате JSON (для интеграции с CI)
```

### 2. Конфигурация yaoxiang.toml

Размещается в секции `[tool.test]`, что соответствует соглашению о сторонних расширениях `[tool.*]`
из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# В будущем возможно расширение:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает работу из коробки без
  какой-либо настройки.
- Однофайловый режим (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации.
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся).

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Pure YaoXiang test assertion library
// First dogfooding library: YaoXiang's test library written in YaoXiang

use std.result

assert_eq = (a, b) => {
    if a == b { result.ok(()) } else { result.err(f"Expected {b}, got {a}") }
}

assert_ne = (a, b) => {
    if a != b { result.ok(()) } else { result.err(f"Expected not equal to {b}, got {a}") }
}

assert_true = (cond: Bool) => {
    if cond { result.ok(()) } else { result.err(f"Expected true, got {cond}") }
}

assert_false = (cond: Bool) => {
    if cond == false { result.ok(()) } else { result.err(f"Expected false, got {cond}") }
}
```

- Функции утверждений имеют **value-семантику**: возвращают `Result((), String)`, сбой выражается
  через `Err(диагностическая информация)` и не вызывает abort процесса — на этом основании suite
  собирает per-test решения. Процессная семантика abort `std.assert.assert` сохраняется за
  runtime-guard'ами и не входит в путь тестовых утверждений.
- **Пояснение о переходе:** 4 функции, реализованные в Phase 1, основаны на `std.assert.assert`
  (семантика abort) и являются переходной реализацией самобутстрапа. Семейство value-семантики
  представляет собой стандартную форму данного RFC и заменяет их после реализации (#319).
- `assert_eq` / `assert_ne` используют **непомеченные параметры** (`Any`) — эмпирически подтверждено
  2026-08-02, что `==`/`!=` и интерполяция f-string на Any работают корректно (Int/String оба
  проверены), без зависимости от системы дженериков. Когда дженерики будут готовы, аннотации можно
  добавить.
- `assert_false` выражает отрицание через `cond == false` (унарный синтаксис `not` ещё не
  реализован; после стабилизации можно мигрировать). Унарная форма `!assert` имеет ту же зависимость
  (см. §8.1).
- Утверждения кода ошибки (`assert(err.code == "E3017")`) зависят от того, что значение `Error`
  несёт машиночитаемое поле `code` (см. §8.1).
- `std.test` не зависит от native-кода, реализован на чистом YaoXiang.

### 4. Механизм загрузки стандартной библиотеки (ключевой дизайн)

**Phase 1: встраивание в бинарник**

`std/test.yx` (а также все будущие модули стандартной библиотеки, написанные на YaoXiang)
встраиваются в бинарник во время сборки:

```rust
// build.rs или скрипт сборки, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // текст исходного кода
    // в будущем — больше
];
```

Система модулей (RFC-029, полностью реализована 2026-08-02) предоставляет точки подключения:
Registry одновременно хранит native-модули и исходные модули; orchestrator отвечает за многофайловую
оркестровку. Порядок разрешения `use std.test`:

1. Сначала поиск в Rust native-модулях (существующий механизм, например `std.assert`).
2. При отсутствии — поиск во встроенных `STD_YX_FILES`; при попадании seed-модуль с виртуальным
   путём (например `<std>/test.yx`) внедряется в orchestrator и проходит через обычный
   frontend-конвейер (parse → typecheck → IR).
3. При отсутствии — обнаружение через файловую систему (пользовательские модули).

`use std.assert` внутри встроенного исходного модуля нормально разрешается resolver'ом в native
registry — native- и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули компилируются по требованию: попадают в конвейер только при import.

Преимущества:

- `use std.test` работает и в однофайловом режиме.
- Версия стандартной библиотеки строго привязана к бинарнику — рассогласование версий невозможно.
- Пользователю не нужно настраивать путь к стандартной библиотеке.

**Будущее: стандартная библиотека в виде файлов**

Когда режим проекта в YaoXiang созреет, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение от 2026-08-02):** CLI `run` подключается к orchestrator. В текущем состоянии
CLI `run` идёт через однофайловый конвейер (`run_file_with_diagnostics`) и не может разрешать
импорты пользовательских модулей; однако модель дочерних процессов `yaoxiang test` наследует
возможности CLI, а импорт модулей проекта из тестовых файлов — ключевой сценарий. Поэтому в Phase 1
сначала делегируется исходная ветвь CLI `Run` функции `run_project` (orchestrator, рекурсивное
обнаружение каталогов); #247 (обнаружение по `use` по требованию) впоследствии накладывается как
чистая оптимизация производительности. Однофайловый случай без import ведёт себя через orchestrator
эквивалентно, ветка байт-кода не меняется.

**Фаза обнаружения:**

1. Если указаны `[PATHS]`, используются указанные пути напрямую.
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`.
3. Если конфигурации нет — по умолчанию `tests/**/*.yx`.
4. Применяется фильтр `--filter` (имя файла содержит).

**Фаза выполнения:**

1. Для каждого файла: запускается дочерний процесс `yaoxiang run --debug-info <file>`
   (`--debug-info` добавляет к runtime-ошибкам позиции в исходном коде — эмпирически подтверждено
   2026-08-02, что stack trace выводит `file:line:col`).
2. Проверяется exit code: 0 — PASS, не 0 — FAIL.
3. Перехватываются stdout/stderr для отчёта.
4. Только последовательное выполнение (Phase 1); в будущем поддержка `--parallel`.
5. Если указан `--fail-fast`, остановка сразу при первом FAIL.

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границами на уровне процессов:

- Каждый тестовый файл выполняется в отдельном дочернем процессе.
- Каждый дочерний процесс имеет независимые Heap, Frame, NativeContext.
- panic в одном тестовом файле не влияет на другие тестовые файлы.
- Дополнительный механизм независимого Heap-контекста не требуется.

### 7. Suite и множество тестов (value-модель)

Один тестовый файл может содержать несколько тестов. Организация внутри файла:

```yaoxiang
// tests/list_test.yx
use std.test
use std.list

push_grows_len = () => {
    xs = []
    list.append(xs, 1)
    test.assert_eq(list.len(xs), 1)
}

pop_returns_last = () => {
    xs = [1, 2]
    test.assert_eq(list.pop(xs), 2)
}

main = {
    test.suite([
        ("push_grows_len", push_grows_len),
        ("pop_returns_last", pop_returns_last),
    ])
}
```

- Каждый тест — функция без аргументов, возвращающая `Result((), String)`; сбой утверждения
  выражается через `Err` (value-семантика из §3) и не прерывает процесс — последующие тесты
  выполняются как обычно.
- `test.suite` вызывает по очереди и собирает: если тест не Ok, печатается имя теста и
  диагностическая информация; Ok — тихо.
- Exit code файла: все тесты в suite вернули Ok → 0; любой Err → не 0 (определение по exit code в §5
  не меняется).
- Runner видит только файл, не выполняет сканирование на уровне функций: per-test решения полностью
  поступают из сбора внутри suite, внутренняя структура файла прозрачна для runner — принцип нулевых
  изменений в компиляторе не затрагивается.
- Явно не применяются: in-process catch-границы (железное правило 17 ключевых слов); вызов функций
  по одной через entry point runner'а (только для внутренних сценариев, таких как сбой компиляции в
  §8.2).
- Конкретная форма API `test.suite` (сигнатура, обработка повторяющихся имён, взаимодействие
  `--filter` с именами suite) — деталь реализации, окончательно решается в #319 при реализации.

### 8. Негативные тесты (ожидаемый сбой) — трёхуровневый дизайн

Негативные тесты разделяются по слою возникновения сбоя, каждый слой — на своём месте.

#### 8.1 Value-уровень обратный (универсальный, для пользователя)

Тестируемая операция возвращает `Result`; тест выражает ожидаемый сбой обычными утверждениями:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
test.assert_eq(result.err_code(r), "E3017")
```

- std.test дополняется семейством функций `assert_not` / `assert_err`; унарная форма `!assert`
  появится после реализации синтаксиса `not` (то же ограничение, что и `cond == false` в
  `assert_false`).
- Утверждения кода ошибки зависят от того, что значение `Error` расширено машиночитаемым полем
  `code`: расширено с `Struct { message }` до `{ code, message }` (native `error_new_with_code`, std
  экспортирует константы кодов), чтобы `err.code == "E3017"` можно было утверждать.
- По мере продвижения Result-изации (#301, #316) операции, которые могут провалиться, постепенно
  начнут возвращать `Result`; файловые негативные маркеры в корпусе мигрируют во внутрифайловые
  утверждения.

#### 8.2 Сбой компиляции (только для внутреннего использования разработчиками языка)

Компиляция — всё или ничего для всего файла, поэтому выразить внутри файла «эта строка не должна
компилироваться» невозможно. Сохраняется специальный файловый маркер:

- Маркер `[test:error]` считывается runner'ом и интерпретируется обратным образом (run с exit code
  не 0 = PASS).
- Маркер обновляется до **структурированного ожидаемого кода**: runner разбирает заголовок
  `预期: 编译错误 EXXXX` и фактически сравнивает его с `[EXXXX]` в stderr компилятора; несовпадение
  кода = FAIL (облегчённая версия идеи снапшотов stderr из trybuild при нулевых изменениях в
  компиляторе).
- Служит только для корпуса данного репозитория, не является частью пользовательского тестового
  фреймворка. Со стороны реализации необходимо унифицировать соглашение о двух вариантах определения
  runner (соглашение о каталоге vs маркер в заголовке), см. #319.

#### 8.3 Жёсткие сбои runtime (включены в Result-изацию)

Отдельный механизм не предусматривается: операции, которые могут провалиться, в соответствии с
направлением языка возвращают `Result` (#301, #316), а тесты единообразно выражаются через §8.1.
Процессный abort (например, нарушение утверждения, несоответствие параметров в runtime) постепенно
сворачивается в значение по мере Result-изации; тестовый фреймворк не предоставляет для них
специальной семантики.

## Связь с существующими системами

| Проект                                                      | Связь                                                                                                                   |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Rust `#[test]`                                              | Не затрагивается; внутренние тесты компилятора продолжают использовать Rust                                             |
| Существующие интеграционные тесты `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются `yaoxiang test`                                                                            |
| `std.assert.assert(cond)`                                   | Сохраняется за runtime-guard'ами; семейство value-семантики `std.test` теперь основано на `std.result` (§3, §7)         |
| Система модулей (RFC-029)                                   | Встроенные исходные модули подключаются через Registry/orchestrator; подключение CLI `run` к orchestrator — предусловие |
| Рефакторинг `#200` (`io.println` → `assert.assert`)         | Полностью соответствует направлению `yaoxiang test`                                                                     |
| Аннотации `@`                                               | Не используются; `@test` не вводится                                                                                    |

## Стратегия реализации

### Phase 1: основной функционал

Объём изменений:

- `src/util/diagnostic/mod.rs` / `src/main.rs` — делегирование исходной ветви CLI `Run` функции
  `run_project` (предусловие для многофайлового запуска).
- `src/main.rs` — добавление подкоманды `Test`.
- `src/std/test.yx` — добавление чистого модуля на YaoXiang.
- `build.rs` — встраивание `std/*.yx` в бинарник.

## Открытые вопросы

- [x] Ссылка `use std.assert` в `std/test.yx` разрешается корректно? — **Решено (2026-08-02)**.
      После реализации системы модулей (RFC-029) native- и исходные модули сосуществуют в Registry,
      resolver разрешает единообразно, межвидовые зависимости работают естественно.
- [x] Вводит ли дженерик `to_string` в `f"..."` тестового вывода новые ограничения типов? — **Решено
      (2026-08-02)**. Эмпирически подтверждено: `==`/`!=` и интерполяция f-string работают на
      непомеченных параметрах (Any) (Int/String проверены), новые ограничения не вводятся.
- [x] Осуществим ли дженерик-параметр `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в настоящее
      время не существует (и будет молча проглочен; открыт отдельный issue для отслеживания);
      функции утверждений Phase 1 используют непомеченные параметры и не зависят от системы
      дженериков.
