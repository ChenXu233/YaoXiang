# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного фреймворка тестирования — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`, общий результат
прохождения/провала определяется по коду выхода дочернего процесса; внутри файла поддерживается
несколько тестовых функций — неудачные утверждения выражаются значением `Err` (семантика значений),
а набор собирает per-test результаты (§7). Модуль `std.test` реализован на чистом YaoXiang и
является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не функция
компилятора — не затрагивает парсер, IR, байт-код или исполняющую систему.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время покрытие тестами YaoXiang зависит от `#[test]` на стороне Rust и интеграционных
тестов в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io) не
   могут быть написаны на YaoXiang
2. `#117 Покрытие модульными тестами модулей стандартной библиотеки` заблокирован, поскольку
   отсутствует доступная инфраструктура тестирования
3. Регрессионное тестирование языковых возможностей (например, изменение семантики spawn в RFC-032)
   не имеет средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения компилятора**: парсер, IR, байт-код, исполнитель не затрагиваются
- **Приоритет самозагрузки**: тестовая библиотека написана на YaoXiang, первая dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Уровень CLI:  yaoxiang test [--filter --fail-fast --json ...]│
│              │                                               │
│  Уровень обнаружения:  чтение yaoxiang.toml → [tool.test] patterns│
│              По умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Уровень выполнения:  для каждого файла: yaoxiang run <file>  │
│              Проверка кода выхода → последовательное выполнение│
│              │                                               │
│  Уровень отчёта:  PASS/FAIL → сводка                         │
│              Поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Уровень утверждений:  std.test (чистый YaoXiang, самозагрузка)│
│              Основа: std.assert.assert                       │
│              Диагностика: f"Expected {expected}, got {actual}" │
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Фреймворк тестирования — не функция компилятора, а инструмент CLI** — `yaoxiang run` уже умеет
   "выполнять тесты", `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводятся сканирование аннотаций `@test`, сегмент
   метаданных в байт-коде, специальная точка входа исполнителя
3. **Самозагрузка** — модуль `std.test` реализован на чистом YaoXiang, базовые возможности берутся
   из `std.assert` / `std.result`
4. **Тестовый файл — это обычный файл `.yx`** — файл запускается как дочерний процесс, общий
   результат определяется по коду выхода
5. **Неудача утверждения — это значение, а не событие процесса** — тестовая функция возвращает
   `Result`, неудача утверждения выражается как `Err`, набор собирает per-test результаты (§7);
   аварийное завершение на уровне процесса относится только к охранникам среды выполнения, не к
   тестовым утверждениям

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Аргументы:
  [PATHS]...      Указанные тестовые файлы или каталоги (по умолчанию: чтение из yaoxiang.toml, иначе tests/)

Опции:
  --filter <NAME>     Запускать только тесты, имя файла которых содержит <NAME>
  --fail-fast         Остановиться при первой неудаче
  --verbose, -v       Показывать подробный stdout/stderr каждого теста
  --list              Только вывести список тестовых файлов, не запускать
  --no-progress       Не показывать вывод прогресса (заголовок и строки PASS); подробности FAIL и сводка сохраняются (для CI)
  --json              Выводить результат в формате JSON (для интеграции с CI)
  --parallel          Параллельное выполнение (по одному worker на ядро; объединение через ИЛИ с [tool.test].parallel)
```

#### Формат вывода

**Вывод по умолчанию** (per-test результаты собираются из набора внутри файла, см. §7):

```
Running 3 test files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ FAIL (0.003s)
  `-- [FAIL] push_grows_len: Expected 3, got 2
  `-- [ ok ] pop_returns_last
Results: 2 files passed, 1 file failed, 0 skipped (0.006s)
Categories: 2 behavior, 0 compile-error, 0 runtime-error
```

**JSON-вывод** (`--json`):

```json
{
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "by_kind": { "behavior": 3, "compile-error": 0, "runtime-error": 0, "invalid": 0 },
    "time_secs": 0.006
  },
  "files": [
    { "file": "tests/math_test.yx", "kind": "behavior", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/list_test.yx",
      "kind": "behavior",
      "passed": false,
      "time_secs": 0.003,
      "exit_code": 1,
      "stderr": "error [E1024]: one is not two",
      "tests": [
        { "name": "push_grows_len", "passed": false, "error": "Expected 3, got 2" },
        { "name": "pop_returns_last", "passed": true }
      ]
    }
  ]
}
```

- Неудачные файлы дополнительно содержат `exit_code` и `stderr` (диагностика дочернего процесса с
  удалёнными ANSI-кодами, для разбора в CI); при комбинации `--verbose` и `--json` все файлы
  содержат `stdout` / `stderr`
- `--no-progress` подавляет только вывод прогресса (заголовок и строки PASS) — подробности FAIL и
  сводка выводятся всегда, неудачи не могут быть скрыты; `--list` выводит по одному пути тестового
  файла на строку без выполнения
- Каждый файл содержит `kind` (behavior / compile-error / runtime-error / invalid, §8.2), сводка
  содержит счётчик выполнений `by_kind` (фиксированные четыре ключа, без skipped); человеческая
  сводка содержит строку распределения по категориям `Categories:`
- При `--parallel` строки прогресса для человека выводятся потоково **в порядке завершения** (без
  чередования), JSON `files` сортируется по пути `file` для стабильности вывода (дружественно к diff
  в CI)
- Массив per-test `tests` внутри файла поступает из сбора набора в §7, вступает в силу по модели
  значения (#319)

### 2. Конфигурация yaoxiang.toml

Размещается в `[tool.test]`, в соответствии с соглашением о сторонних расширениях `[tool.*]` из
RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
exclude = ["tests/fixtures/**"]   # Совпадения исключаются из набора обнаружения (также удаляются --list)
parallel = true                   # Параллельное выполнение (объединение через ИЛИ с флагом --parallel)
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — работает из коробки без настройки
- `exclude` имеет ту же форму, что и `patterns` (литеральный путь или `root/**…`, всегда по
  совпадению префикса пути); исключённое означает, что это не тест; фикстуры, требующие проверки
  поведения во время выполнения, запускаются напрямую через `yaoxiang run`
- **Однофайловый режим (`yaoxiang test foo.yx`) запускается напрямую, без чтения конфигурации** —
  при явных путях ключи `exclude`/`parallel` не действуют (кроме флага)
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Библиотека тестовых утверждений на чистом YaoXiang (стандартная форма семантики значений, введено 2026-09-03)
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang написана на YaoXiang.

use std.result

assert_eq: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a == b { return result.ok(void) }
    return result.err(f"Expected {b}, got {a}")
}

assert_ne: (a: Any, b: Any) -> Result(Void, String) = (a, b) => {
    if a != b { return result.ok(void) }
    return result.err(f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Result(Void, String) = (cond) => {
    if cond { return result.ok(void) }
    return result.err(f"Expected true, got {cond}")
}

// assert_not и assert_false — одно и то же тело; assert_err / assert_err_code см. §8.1
```

- Функции утверждений имеют **семантику значений**: возвращают `Result(Void, String)`, неудача
  выражается как `Err(диагностика)`, без аварийного завершения процесса — набор в §7 собирает на
  этой основе per-test результаты. Семантика аварийного завершения на уровне процесса у
  `std.assert.assert` сохраняется для охранников среды выполнения и не входит в путь тестовых
  утверждений. Полезная нагрузка Ok — `Void` (единичный тип по спецификации type-system.md; `()` —
  пустой Tuple, не путать — решение 2026-09-03)
- **Семейство из 7 функций (поставлено 2026-09-03, переходная версия с abort удалена)**: с
  семантикой значений `assert_eq` / `assert_ne` / `assert_true` / `assert_false` + `assert_not`
  (одно тело с assert_false, зарезервировано для формы `!assert`) + `assert_err` (§8.1)
  - `assert_err_code` (утверждение кода ошибки, §8.1)
  - `assert_approx_eq(a: Float, b: Float, eps: Float)` (Фаза 3, поставка 2026-09-07): проверка
    `|a - b| <= eps`, eps задаётся вызывающей стороной **явно** — допуск является частью контракта
    теста, скрытых значений по умолчанию нет; отрицательный eps означает Err в точке объявления, NaN
    всегда Err
- `assert_eq` / `assert_ne` используют **Any для аннотации параметров** — `==`/`!=` и интерполяция
  f-string работают на Any нормально, без зависимости от системы дженериков. Обратите внимание, что
  параметры **должны быть аннотированы явно**: неаннотированные параметры не проходят проверку
  вызова native-дженерика `&Result(T, E)` (эмпирически проверено пробником R1)
- `assert_false` / `assert_not` выражают отрицание через `cond == false` (унарный синтаксис `not` не
  реализован, может быть перенесён после стабилизации; унарная форма `!assert` имеет ту же
  зависимость, см. §8.1)
- Форма с телом блока + явным `return`: тип then-ветви if-выражения отбрасывается при проверке,
  if-выражение с Result в обеих ветвях — слепая зона проверки, реализация обходит это
- `std.test` не зависит от native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое проектирование)

**Фаза 1: Встраивание в бинарник**

`std/test.yx` (и все будущие модули стандартной библиотеки, написанные на YaoXiang) встраиваются в
бинарник во время сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // Текст исходного кода
    // Будущие модули
];
```

Модульная система (RFC-029, полностью реализовано 2026-08-02) предоставляет точку интеграции:
Registry одновременно содержит native-модули и исходные модули, orchestrator отвечает за оркестровку
нескольких файлов. Порядок разрешения `use std.test`:

1. Сначала поиск native-модулей Rust (существующий механизм, например `std.assert`)
2. Если не найдено — поиск во встроенных `STD_YX_FILES` — при совпадении инъекция в orchestrator как
   **виртуальный путь** (например, `<std>/test.yx`) в качестве начального модуля, проходит по
   обычному фронтенд-конвейеру (parse → typecheck → IR)
3. Если не найдено — обнаружение в файловой системе (пользовательские модули)

`use std.assert` внутри встроенного исходного модуля нормально разрешается resolver-ом в native
registry — native и исходные модули сосуществуют в Registry, межвидовые зависимости работают
естественно. Встроенные модули **компилируются по требованию**: входят в конвейер только при
импорте.

Преимущества:

- В однофайловом режиме `use std.test` тоже работает
- Версия стандартной библиотеки строго привязана к бинарнику, несоответствие версий невозможно
- Не требуется настройка путей к стандартной библиотеке пользователем

**Будущее: стандартная библиотека в файловой системе**

Когда проектный режим YaoXiang созреет, стандартная библиотека будет переведена в форму файловой
системы. Подробности см. в обновлении RFC-014.

### 5. Обнаружение и выполнение

**Предусловие (решение ревью 2026-08-02)**: CLI `run` подключается к orchestrator. В настоящее время
CLI `run` использует однофайловый конвейер (`run_file_with_diagnostics`), неспособный разрешать
импорты пользовательских модулей; а модель дочернего процесса `yaoxiang test` наследует возможности
CLI, импорт тестовыми файлами модулей проекта — ключевой сценарий. Поэтому в Фазе 1 сначала
делегируется ветвь исходного кода CLI `Run` в `run_project` (orchestrator, рекурсивное обнаружение в
каталогах); #247 (обнаружение по требованию через use) после этого накладывается как чистая
оптимизация производительности. Однофайловый режим без импортов ведёт себя эквивалентно через
orchestrator, ветвь байт-кода не изменяется.

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читаются `patterns` из `[tool.test]` в `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтрация `--filter` (по вхождению в имя файла)
5. Область обнаружения — это и есть тестовая стратификация (§9): patterns по умолчанию покрывают
   только корпус языковой доступности; уровень тестов библиотек (например, `src/std/tests/`)
   обнаруживается через явные пути или конфигурацию пакета, не подмешивается в сканирование по
   умолчанию

**Этап выполнения**:

1. Для каждого файла маршрутизация выполнения по заголовочным директивам (грамматика директив см.
   §8.2, разбирается через `src/util/test_markers.rs`, используется совместно с yx_runner):
   - Поведенческие тесты: дочерний процесс `yaoxiang run --debug-info <file>` (`--debug-info`
     заставляет ошибки среды выполнения содержать позиции в исходном коде — эмпирически подтверждено
     2026-08-02, stack trace выводит `file:line:col`); `// mode:` объявляет режим `--runtime`
     дочернего процесса
   - Класс отказа на этапе компиляции: одношаговый `yaoxiang check <file>`
   - Класс отказа на этапе выполнения: два шага — `check` (должен пройти) + `run` (должен
     провалиться)
2. Файлы с `// skip: <причина>` пропускаются, засчитываются в skipped отчёта
3. Сравнение результата с ожидаемым кодом по матрице §8.2; ошибка разбора директив — не выполняется,
   сразу FAIL (отказ на этапе построения)
4. Захват stdout/stderr для отчёта
5. По умолчанию последовательно; `--parallel` (или `[tool.test].parallel`) запускает пул worker-ов
   по числу доступных ядер, каждый файл по-прежнему — отдельный дочерний процесс — skip/invalid
   обрабатываются первыми в порядке обнаружения, результаты выполнения выводятся потоково в порядке
   завершения, JSON сортируется по пути (Фаза 3, поставка 2026-09-07)
6. При `--fail-fast` при первом FAIL немедленно прекращается планирование новых файлов; в
   параллельном режиме файлы в работе завершаются и засчитываются

### 6. Изоляция тестов

Изоляция тестов естественно обеспечивается границей на уровне процесса:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственные Heap, Frame, NativeContext
- Panic одного тестового файла не влияет на другие
- Не требуется дополнительный механизм изоляции контекстов Heap
- **Параллельное выполнение (Фаза 3) не расширяет границу изоляции**: рабочие каталоги (CWD) между
  дочерними процессами являются общими, параллельные тесты не должны занимать файлы по одинаковым
  путям внутри CWD — тесты с файловым I/O используют уникальные имена файлов и очищают их по
  завершении

### 7. Набор и множественные тесты (модель значений)

Тестовый файл может содержать несколько тестов. Способ организации внутри файла (реализовано
2026-09-03):

```yaoxiang
// tests/list_test.yx
use std.list
use std.result
use std.test

push_grows_len: () -> Result(Void, String) = () => {
    xs = [1]
    extended = list.push(xs, 2)
    test.assert_eq(list.len(extended), 2)
}

pop_returns_last: () -> Result(Void, String) = () => {
    mut xs = [1, 2]
    last = list.pop(xs)
    test.assert_eq(last, 2)
}

main = {
    test.suite([
        ("push_grows_len", () => push_grows_len()),
        ("pop_returns_last", () => pop_returns_last()),
    ])
}
```

- Каждый тест — это функция без аргументов, возвращающая `Result(Void, String)`; неудача утверждения
  выражается как `Err` (семантика значений семейства из §3), не прерывает процесс — последующие
  тесты продолжают выполняться
- `test.suite` вызывает по очереди и собирает: если тест не Ok — записывает имя и диагностику, Ok
  молча; после прогона всех тестов при наличии любого Err завершает через `std.assert.assert` с
  подробностями неудач (`N of M test(s) failed` + каждый `[FAIL] имя: диагностика`) — код выхода
  файла ненулевой (§5 без изменений). Здесь abort — это охранник среды выполнения тестового
  бинарника, а не путь утверждений; все Ok — тихий выход с кодом 0
- Тестовые функции верхнего уровня заносятся в список **в форме замыканий**
  (`("name", () => test_fn())`): ссылки на имена функций верхнего уровня как на значения пока не
  поддерживаются (ограничение IR, `E3006`) — вызов глобальной функции в теле замыкания не затронут
- Runner видит только файл, не выполняет сканирования на уровне функций: per-test результаты
  полностью поступают из сбора внутри набора, внутренняя структура файла прозрачна для runner —
  принцип нулевых изменений компилятора не нарушается
- Явно не используется: граница перехвата внутри процесса (железное правило 17 ключевых слов); вызов
  runner-ом по точкам входа функций (только для внутренних сценариев вроде отказа компиляции в §8.2)
- Форма API утверждена (2026-09-03, #319):
  `suite(tests: List((String, () -> Result(Void, String)))) -> Void`; дублирование имён не
  проверяется (имя используется только для отображения в отчёте); `--filter` фильтрует по имени
  файла, не по именам тестов внутри набора

### 8. Трёхуровневое проектирование негативных тестов (ожидаемый отказ)

Негативные тесты разделяются по слою возникновения отказа, каждый уровень на своём месте:

#### 8.1 Реверс на уровне значений (универсальный, для пользователей)

Тестируемая операция возвращает `Result`, тест выражает ожидаемую неудачу обычным утверждением:

```yaoxiang
r = range.iter(invalid_range)
test.assert_err(r)
e = result.unwrap_err(r)
test.assert_eq(result.code(e), "E6009")
// Или в одну строку (код существует только на носителе std Error, E жёстко закреплён за Error):
test.assert_err_code(r, "E6009")
```

- `assert_not` / `assert_err` / `assert_err_code` поставлены вместе с семейством семантики значений
  (2026-09-03, §3); унарная форма `!assert` будет предоставлена после реализации синтаксиса not (то
  же ограничение, что и `cond == false` в `assert_false`)
- Утверждение кода ошибки зависит от того, что значение `Error` несёт машиночитаемое поле `code` —
  реализовано в M4 #323: `Error = { code, message }` (native `error_new(code, message)`), чтение
  через `result.unwrap_err(r)` для получения носителя + аксессоры `result.code(e)` /
  `result.message(e)` (предполагавшиеся на этапе проектирования именование `error_new_with_code`,
  экспорт констант кодов и доступ к полю `err.code` не были приняты — в языке нет доступа к полям
  Struct, константы кодов не экспортируются)
- По мере продвижения Result-ификации (#301, #316) операции, которые могут провалиться, по одной
  возвращают `Result`, файловые негативные метки в корпусе мигрируют во внутрифайловые утверждения

#### 8.2 Файловые негативные директивы (только для внутреннего использования разработчиками языка)

Компиляция — это "всё или ничего" для всего файла, невозможно выразить "эта строка не должна
компилироваться" внутри файла; отказы среды выполнения также требуют файлового выражения (например,
набор содержит обязательно проваливающийся тест). Ожидание объявляется **структурированной
директивой** в заголовке файла, runner выполняет **маршрутизированную проверку** по ожидаемой
категории (маршрутизация утверждена 2026-09-03; грамматика директив утверждена и реализована
2026-09-06).

Грамматика заголовочных директив (`// key: value`, в пределах первых 16 строк, строгое
токен-совпадение):

```text
// expect: compile-error E1002 [E1003 ...]   Тест отказа на этапе компиляции
// expect: runtime-error E6003 [...]         Тест отказа на этапе выполнения
// skip: <причина>                           Пропустить выполнение, засчитать в skipped
// mode: embedded|standard|full              Режим --runtime дочернего процесса (потребляется только на шаге run)
```

- Отсутствие директивы `expect:` = поведенческий тест. `expect:` — это **единственное объявление**
  ожидания — 2026-09-06 утверждено отбрасывание булевых меток `[test:error]` и китайского
  прозаического `预期:`-извлечения: булева метка и строка ожидания — это два слабо связанных факта,
  поддержание согласованности дисциплиной неизбежно приведёт к расхождению; строгая английская
  токен-грамматика позволяет runner-у механически разбирать (kind + код — фиксированные токены,
  любой лишний токен после кода — ошибка разбора), ошибка разбора = не выполнять, сразу FAIL — канал
  тихой деградации при ошибочном объявлении директивы отсутствует (отказ на этапе построения)
- **Класс ошибки компиляции**: одношаговый `check` — должен провалиться, и вывод содержит все
  `[EXXXX]`; прохождение компиляции = FAIL (то, что должно было быть сообщено, не сообщено), отказ с
  несоответствующим кодом = FAIL. Синтаксические (E1xxx парсинг) и семантические (E2xxx+) ошибки не
  выделяются в отдельные категории — сам ожидаемый код закрепляет фазу
- **Класс ошибки среды выполнения**: двухшаговая проверка — `check` должен **пройти** (невиновен на
  этапе компиляции), `run` должен провалиться, и вывод содержит все `[EXXXX]`. Взрыв на этапе
  компиляции = FAIL (ключевая проверка, противоположная классу ошибок компиляции, предотвращает
  пропуск случая "компиляция случайно прошла, среда выполнения случайно провалилась")
- Изоморфно индустрии: Rust compiletest `//~ ERROR`, Go `// ERROR "regexp"`, GCC `dg-error`, Clang
  `expected-error` — все объявляют ожидание в комментариях фикстуры с двусторонним сравнением в
  harness; они используют построчные якоря, потому что много диагностик в компиляторе требует
  различения нескольких ожиданий в одном файле, наш компилятор останавливается на первой ошибке,
  одна диагностика на файл — файловый уровень изоморфен реалиям компилятора — после реализации
  восстановления ошибок в грамматику может быть добавлена форма построчных якорей (заголовочные
  директивы + ожидания на уровне функций в Cranelift filetests — тот же гибрид)
- Известный долг рендеринга: диагностика на этапе parse в настоящее время выводится в форме Debug
  (`code: "E0012"` вместо `[E0012]`), сканирование кода принимает обе формы; после унификации
  рендеринга диагностики строгая форма будет возвращена
- **Служит только корпусу этого репозитория, не является частью фреймворка тестирования
  пользователя**; соглашение о двух runner-ах закрыто (2026-09-03, #319): yx_runner (cargo test) и
  `yaoxiang test` совместно используют `src/util/test_markers.rs` для разбора заголовочных директив,
  соглашение о каталоге 06-compile-errors упразднено. Уровень отчёта выдаёт счётчики категорий:
  человеческая сводка содержит строку `Categories:`, JSON-сводка содержит `by_kind` (behavior /
  compile-error / runtime-error / invalid, skipped считается отдельно), каждый файл содержит `kind`

#### 8.3 Аппаратные отказы среды выполнения (относятся к Result-ификации)

Отдельный механизм не вводится — операции, которые могут провалиться, по направлению языка
возвращают `Result` (#301, #316), тесты унифицированно выражаются через §8.1. Аварийное завершение
на уровне процесса (например, нарушение утверждения, ошибки параметров среды выполнения) постепенно
сворачивается в значения по мере Result-ификации, фреймворк тестирования не предоставляет для них
специальной семантики. (Примечание: маркер «класс ошибки среды выполнения» в §8.2 — это канал
файловой проверки runner-ом для **операций, которые пока не могут быть Result-ифицированы**, что не
противоречит семантическому направлению данного раздела — последний является конечной точкой, первый
— переходным каналом)

### 9. Стратификация тестовой системы: языковой корпус и тесты библиотек (утверждено 2026-09-03)

Тесты делятся на два уровня по **объекту тестирования**, у каждого своё место и сопровождающий;
система маркеров (§8.2) и библиотека утверждений (§3) — общие для обоих уровней:

**Первый уровень: языковой корпус доступности (`tests/yaoxiang/`)**

- Объект тестирования — **сам язык** — парсер, система типов, модули, конкурентность, владение,
  отказы на этапе компиляции, семантика среды выполнения; каталоги организованы по главам
  спецификации языка
- std в корпусе выступает только **инструментом утверждений** (`std.assert` / `std.test`), никогда
  не тестируется — API-поведение библиотек не относится к языковой доступности
- Внутри корпуса по §8 происходит маршрутизация на три класса: поведенческие тесты / тесты отказа на
  этапе компиляции / тесты отказа на этапе выполнения

**Второй уровень: тесты библиотек (вместе с библиотеками)**

- Объект тестирования — **публичный API-контракт библиотеки** (например, поведение `list.push`,
  семантика `result.code`)
- Тесты пишутся **в собственном пакете библиотеки**: пакет std — это `src/std/`, его yx-уровневые
  тесты относятся к `src/std/tests/` (вместе с реализацией; каталог сосуществует с модульными
  тестами Rust, типы файлов не пересекаются); тесты самого `std.test` также там (тестирование
  std.test через std.test, самозагрузочный цикл)
- В будущем пользовательские пакеты следуют тому же соглашению: тесты внутри пакета, обнаруживаются
  через `[tool.test]` пакета (макет тестовой раскладки пакета из RFC-014 репетируется этим)
- Обнаружение не входит в patterns по умолчанию (по умолчанию `tests/**/*.yx` покрывает только
  языковой уровень): уровень тестов библиотек обнаруживается через явные пути
  (`yaoxiang test src/std/tests`) или конфигурацию пакета; CI запускается по уровням

Заметка о миграции: **мигрировано (2026-09-06)** — 19 файлов из бывшего `tests/yaoxiang/07-std/`
после индивидуального рассмотрения оказались полностью тестами библиотек (объекты тестирования —
API-контракты модулей std; роль языковых возможностей вроде распространения `?`, автоматического
заимствования, инстанциации дженериков в них — носители, а не объекты тестирования), целиком
перенесены в `src/std/tests/` с удалением каталога 07-std; yx_runner изменён на обнаружение с двумя
корнями (`tests/yaoxiang/` + `src/std/tests/`), patterns по умолчанию не содержат уровень библиотек
(интеграционные тесты фиксируют этот контракт). Языковой корпус отныне не содержит тестов std API.

## Открытые вопросы

- [x] Может ли ссылка `use std.assert` в `std/test.yx` корректно разрешаться? — **Решено
      (2026-08-02)**. После реализации модульной системы (RFC-029) native и исходные модули
      сосуществуют в Registry, resolver разрешает единообразно, межвидовые зависимости работают
      естественно
- [x] Вводит ли обобщённый `to_string` в `f"..."` тестового вывода новые ограничения типов? —
      **Решено (2026-08-02)**. Эмпирически подтверждено, что `==`/`!=` и интерполяция f-string
      работают на неаннотированных параметрах (Any) (проверено на Int/String), новые ограничения не
      вводятся
- [x] Возможность параметра-дженерика `?`? — **Решено (2026-08-02)**: синтаксис типа `?` в настоящее
      время не существует (и молча проглатывается, отслеживается отдельным issue), функции
      утверждений Фазы 1 используют неаннотированные параметры, не зависят от системы дженериков
