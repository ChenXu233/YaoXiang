# RFC-029: Семантика модулей

## Резюме

Подключение системы модулей к конвейеру компиляции для реализации многофайловой сборки.

**Основное определение**: модуль = все связывания верхнего уровня в одном `.yx`-файле. Тип модуля =
типы этих связываний (выводимые). `use` = деструктуризация record. Никаких `pub`, `private`,
`export`, никакого механизма видимости.

**Основные принципы**:

- Проверщик типов обращается только к предварительно собранному ModuleRegistry, не трогает диск
- Файлы внутри пакета объединяются в единую единицу компиляции (склейка AST), циклические ссылки
  внутри пакета естественно допускаются
- Registry загружается по требованию: только модули, достижимые из точки входа по `use`

**Не включено**: кэширование, отслеживание файлов, горячая перезагрузка, инкрементальная
перекомпиляция, обработка межпакетных циклических зависимостей.

## Мотивация

### Текущие проблемы

1. **Компилятор поддерживает только один файл**: `Pipeline::run(name, source)` принимает одну строку
   и не может обрабатывать межфайловые зависимости
2. **`use` может разрешать только модули std**: `use` между локальными файлами всегда выдаёт
   "Unknown variable"
3. **Резолвер модулей расположен не там**: единственная логика разрешения путей находится в
   `package/source/module_resolver.rs`, а `frontend/module/resolver.rs` на самом деле занимается
   компиляционной нормализацией предикатов (RFC-027)

### Цели проектирования

- Проект может компилировать несколько `.yx`-файлов
- Ясная семантика `use`: деструктуризация record, а не специальный механизм
- Один файл продолжает работать без обязательного `yaoxiang.toml`
- Конвейер (`Pipeline`) не меняется, поддержка многофайловых проектов — задача уровня оркестрации
- Без новых ключевых слов, новых узлов AST, новых концепций

## Предложение

### 1. Модуль = record связываний

**Модуль** — это все связывания верхнего уровня в одном `.yx`-файле.

```yaoxiang
// math/geometry.yx
Point: Type = { x: Float, y: Float }
distance: (a: Point, b: Point) -> Float = { ... }
```

Содержимое этого модуля — `{ Point: Type, distance: (Point, Point) -> Float }`.

Модуль — не специальная сущность. Это экземпляр модели `name: type = value` — record, определённый
на границе файла. Тип модуля выводится из связываний; явные аннотации никогда не требуются.

Связывания, внесённые через `use`, **тоже** являются частью содержимого модуля:

```yaoxiang
// math/mod.yx
use geometry.{Point, distance}
```

Содержимое модуля `math` = `{ Point: Type, distance: (Point, Point) -> Float }`. `use math.{Point}`
снаружи работает. `use math.geometry.{Point}` тоже работает. Оба пути указывают на одно и то же
связывание.

### 2. use = деструктуризация record

Все формы `use` — это доступ к полям record + связывание:

```yaoxiang
use math.geometry.{Point, distance}
```

эквивалентно:

```yaoxiang
Point = math.geometry.Point
distance = math.geometry.distance
```

| Синтаксис           | Семантика                                                                |
| ------------------- | ------------------------------------------------------------------------ |
| `use path.{item}`   | Взять поле `item` из record `path`, связать с текущей областью видимости |
| `use path.{a, b}`   | Взять несколько полей                                                    |
| `use path`          | Взять сам record `path`, связать с именем последнего сегмента            |
| `use path as alias` | Взять сам record `path`, связать с `alias`                               |

#### Несуществующий синтаксис

- ~~`use path.*`~~: импорт по шаблону. Не нужен, связывания перечисляются явно.
- ~~`from path use item`~~: в стиле Python. Не принят.
- ~~`use path.{item as alias}`~~: псевдоним внутри фигурных скобок. Опционально для Фазы 4, не
  блокирует основной путь.

#### Конфликты импорта

Одноимённые связывания дают прямую ошибку:

```
Конфликт имени `Point`:
  math.geometry.Point
  graphics.shapes.Point
Используйте разные имена или псевдоним модуля.
```

### 3. Видимость: не существует

**Настоящий RFC не вводит никакого механизма видимости.** Все связывания верхнего уровня видны
любому коду, способному записать путь к ним.

Это осознанное проектное решение, а не упущение.

#### Обоснование проектирования

| Что выразить         | Как сделать                    | Механизм          |
| -------------------- | ------------------------------ | ----------------- |
| "Это API"            | Положить в публикуемый пакет   | Распространение   |
| "Это внутреннее"     | Положить в непубликуемый пакет | Распространение   |
| "Это внутри функции" | Написать в теле функции        | Область видимости |

Все три уровня — уже существующие механизмы: пакет, файл, область видимости. Ничего нового не нужно.

#### Почему не нужен `pub`

- То, что не должно использоваться другими, не следует размещать на верхнем уровне (поместите в
  локальную область видимости)
- Вспомогательные функции, общие для нескольких файлов, размещаются в отдельном непубликуемом пакете
- "Можно ли защитить" и "нужен ли сигнал" — разные вещи. На текущем этапе нет сторонней экосистемы,
  сигнал бессмысленен
- Дверь не заперта. Войти через дверь — вежливость, перелезть через забор — свобода. Язык не
  занимается вежливостью

#### В будущем

Когда экосистема созреет и потребуются жёсткие границы, их можно ввести отдельным RFC. Добавление
ограничений обратно совместимо (по умолчанию публично → явная пометка как внутреннее). Но настоящий
RFC не предрешает это направление и не обещает, что оно появится.

### 4. Разрешение путей

#### Путь модуля → файл

```
use math.geometry.{Point}
```

Порядок поиска:

1. **Зарегистрированные модули в Registry**: `math.geometry` уже в Registry → использовать напрямую
2. **Стандартная библиотека**: `std` или `std.*` → встроенные модули
3. **Каталог импортирующего файла**: `<importer_dir>/math/geometry.yx` (локальные модули в
   приоритете)
4. **Корень проекта** (ближайший предок `yaoxiang.toml`): `<project_root>/math/geometry.yx`
5. **Каталог vendor**: `.yaoxiang/vendor/<pkg>-*/src/` (в будущем)

Порядок попыток локализации файла:

```
base/name.yx
base/name/mod.yx
```

Остановиться на первом найденном. Если существуют оба — ошибка:

```
Неоднозначность пути модуля: `math.geometry` соответствует одновременно:
  src/math/geometry.yx
  src/math/geometry/mod.yx
Удалите один из них.
```

Если один и тот же ключ модуля в **двух корнях** даёт по файлу, и оба используются (например,
`tests/lib.yx` и `<root>/lib.yx` используются точками входа `tests/` и корня соответственно) — такая
же ошибка неоднозначности, а не молчаливое затенение.

> Редакция 2026-08-03 (вызвана RFC-036): обнаружение и разрешение реализованы согласно их реальному
> воплощению. Обнаружение следует по `use` (протокол, установленный в §5 настоящего RFC), заменяя
> рекурсию каталогов из первоначальной реализации — ошибки компиляции несвязанных файлов больше не
> блокируют выполнение, и только тогда работает изоляция тестовых файлов `yaoxiang test`. Правило
> двух корней «каталог импортирующего файла в приоритете» сохраняет поведение проекта в одном
> каталоге неизменным; «резервный поиск в корне проекта» позволяет точкам входа в подкаталогах
> (например, `tests/foo_test.yx`) импортировать модули из корня проекта. Раскладка `src/` (пакет по
> RFC-014) обрабатывается на уровне vendor, не затрагивая локальные два корня.

#### mod.yx = точка входа каталога (соглашение)

`mod.yx` — файл точки входа каталога. `use math` загружает `src/math/mod.yx`.

Это **соглашение, а не принуждение**. Пользователь может напрямую `use math.geometry` проникнуть в
подфайл. `mod.yx` — «рекомендуемая точка входа» (указатель), а не «единственная точка входа»
(замок).

#### Унифицированный резолвер

Единственная существующая логика разрешения путей находится в `package/source/module_resolver.rs`.
Переместить её в `frontend/module/resolver.rs` (заменив текущий файл, который неправильно назван и
занимается нормализацией предикатов; нормализация предикатов переносится в
`frontend/core/types/eval/`).

### 5. Процесс компиляции проекта

#### Путь A: объединение AST

Все файлы внутри пакета объединяются в **единую единицу компиляции**. Конвейер не меняется.

```
Оркестратор (над Pipeline):
  1. Определить файл точки входа
  2. Разобрать операторы use в файле точки входа (только строки use, не тела функций)
  3. Обнаруживать файлы по путям use, добавлять в очередь
  4. Для файлов в очереди разобрать их операторы use
  5. Повторять 3-4, пока очередь не опустеет (обнаружение по требованию)
  6. Полностью разобрать все обнаруженные файлы по очереди → несколько AST
  7. Объединить в один Module (конкатенация всех элементов верхнего уровня, Span сохраняет исходный файл)
  8. Передать в Pipeline::run() (конвейер не знает, что файлов несколько)
```

#### Внутрипакетные циклические ссылки: разрешены

Поскольку все файлы объединяются в один AST, взаимные `use` внутри пакета эквивалентны взаимным
ссылкам внутри одного файла:

```yaoxiang
// tree.yx
use node.{Node}
Tree: Type = { root: Node }

// node.yx
use tree.{Tree}
Node: Type = { value: Int, parent: Tree }
```

После объединения это один AST с двумя взаимно ссылающимися определениями типов. Компилятор и так
это поддерживает.

#### Межпакетные циклы: отложено

Пакет — единица распространения, между пакетами нужен топологический порядок. Сейчас нет экосистемы
сторонних пакетов, не обрабатывается. При обнаружении — прямая ошибка.

#### Выбор файла точки входа

Приоритет:

1. `[run].main` (yaoxiang.toml)
2. `path` первого `[[bin]]`
3. `src/main.yx` (соглашение по умолчанию)

Без `yaoxiang.toml`: компилировать указанный файл напрямую. В Registry только std. Это не «режим
одного файла» — это «естественный результат, когда обнаружение пусто».

#### Загрузка Registry по требованию

Содержимое Registry = все модули, достижимые из точки входа по `use`. Недостижимые модули не
разбираются, не регистрируются, не существуют. **Это не оптимизация, это определение.**

### 6. Модули std и пользовательские модули однородны

Для проверки типов `use std.io.{println}` и `use math.geometry.{Point}` работают совершенно
одинаково:

1. Найти record модуля в Registry
2. Взять поле
3. Связать с текущей областью видимости

Источник (Std / User / Vendor) — метаданные, не влияющие на логику разрешения. Специальная обработка
native-функций откладывается до уровня IR gen / codegen.

## Стратегия реализации

### Фаза 1: Унифицированное разрешение путей

1. Перенести нормализацию предикатов из `frontend/module/resolver.rs` в `frontend/core/types/eval/`
2. Перенести логику разрешения путей из `package/source/module_resolver.rs` в
   `frontend/module/resolver.rs`
3. Обнаружение неоднозначностей модулей (одновременное существование `name.yx` и `name/mod.yx` →
   ошибка)

### Фаза 2: Многофайловый оркестратор

4. Создать `frontend/module/orchestrator.rs`
5. Реализовать обнаружение по требованию (рекурсия по `use` от точки входа)
6. Реализовать объединение AST (конкатенация элементов многофайлового проекта, Span несёт исходный
   файл)
7. Добавить в `compiler.rs` вызов `compile_project(project_root)`, обращающийся к оркестратору

### Фаза 3: Разрешение имён use

8. `process_use_stmt` в проверщике типов переключается на Registry (больше не только std)
9. Обнаружение конфликтов импорта (ошибка при совпадении имён)
10. E2E-тесты: многофайловый проект, `use` локальных модулей

### Фаза 4 (опционально, не блокирует основную линию)

11. Псевдоним внутри фигурных скобок: `use path.{item as alias}`
12. Разрешение каталога vendor (совместно с RFC-014)

### Зависимости

- RFC-014 (менеджер пакетов) — поля `yaoxiang.toml`, структура каталога vendor (нужны только для
  Фазы 4)
- Других предварительных зависимостей нет
