# RFC-029: Модульная семантическая система

## Резюме

Подключение модульной системы к конвейеру компиляции, реализация многофайловой компиляции.

**Основное определение**: Модуль = все верхнеуровневые привязки одного файла `.yx`. Тип модуля =
типы этих привязок (выведенные). `use` = деструктуризация record. Нет `pub`, нет `private`, нет
`export`, нет механизма видимости.

**Основные принципы**:

- Проверщик типов запрашивает только предварительно собранный ModuleRegistry, не обращается к диску
- Файлы внутри пакета объединяются в единую единицу компиляции (склейка AST), циклические ссылки
  внутри пакета естественно допускаются
- Registry загружается по требованию: загружаются только модули, достижимые из точки входа по `use`

**Не включено**: кэширование, отслеживание файлов, горячая перезагрузка, инкрементальная
перекомпиляция, обработка межпакетных циклических зависимостей.

## Мотивация

### Текущие проблемы

1. **Компилятор поддерживает только один файл**: `Pipeline::run(name, source)` принимает строку, не
   может обрабатывать межфайловые зависимости
2. **`use` может разрешать только модули std**: `use` между локальными файлами все выдают "Unknown
   variable" (#232)
3. **Резолвер модулей находится не на своём месте**: единственная логика разрешения путей находится
   в `package/source/module_resolver.rs`, `frontend/module/resolver.rs` фактически является
   нормализацией предикатов времени компиляции (RFC-027)

### Цели проектирования

- Проект может компилировать несколько `.yx` файлов
- Ясная семантика операторов `use`: деструктуризация record, не специальный механизм
- Один файл продолжает работать, не требует `yaoxiang.toml`
- Конвейер (`Pipeline`) без изменений, поддержка многофайлов — дело уровня оркестрации
- Не вводить новые ключевые слова, новые узлы AST, новые концепции

## Предложение

### 1. Модуль = record привязок

**Модуль** — это все верхнеуровневые привязки одного файла `.yx`.

```yaoxiang
// math/geometry.yx
Point: Type = { x: Float, y: Float }
distance: (a: Point, b: Point) -> Float = { ... }
```

Содержимое этого модуля — `{ Point: Type, distance: (Point, Point) -> Float }`.

Модуль — не специальная сущность. Это экземпляр модели `name: type = value` — record, определённый
на границе файла. Тип модуля выводится из привязок, никогда не требует явной аннотации.

Привязки, введённые через `use`, **тоже** являются частью содержимого модуля:

```yaoxiang
// math/mod.yx
use geometry.{Point, distance}
```

Содержимое модуля `math` = `{ Point: Type, distance: (Point, Point) -> Float }`. Снаружи
`use math.{Point}` можно получить. `use math.geometry.{Point}` тоже можно получить. Оба пути
указывают на одну и ту же привязку.

### 2. use = деструктуризация record

Все формы `use` — это доступ к полю record + привязка:

```yaoxiang
use math.geometry.{Point, distance}
```

эквивалентно:

```yaoxiang
Point = math.geometry.Point
distance = math.geometry.distance
```

| Синтаксис           | Семантика                                                              |
| ------------------- | ---------------------------------------------------------------------- |
| `use path.{item}`   | Взять поле `item` record `path`, привязать к текущей области видимости |
| `use path.{a, b}`   | Взять несколько полей                                                  |
| `use path`          | Взять сам record `path`, привязать к последнему сегменту имени         |
| `use path as alias` | Взять сам record `path`, привязать к `alias`                           |

#### Несуществующий синтаксис

- ~~`use path.*`~~: импорт по шаблону. Не нужен, явно перечислите привязки.
- ~~`from path use item`~~: Python-стиль. Не принят.
- ~~`use path.{item as alias}`~~: псевдоним внутри фигурных скобок. Опционально в Фазе 4, не
  блокирует #232.

#### Конфликты импорта

Одноимённые привязки сразу выдают ошибку:

```
Имя `Point` конфликтует:
  math.geometry.Point
  graphics.shapes.Point
Пожалуйста, используйте разные имена или псевдоним модуля.
```

### 3. Видимость: не существует

**Данный RFC не вводит никакого механизма видимости.** Все верхнеуровневые привязки видимы всему
коду, который может записать путь.

Это намеренное проектное решение, а не упущение.

#### Основания проектирования

| Что хочется выразить | Как сделать                    | Механизм          |
| -------------------- | ------------------------------ | ----------------- |
| "Это API"            | Положить в публикуемый пакет   | Распространение   |
| "Это внутреннее"     | Положить в непубликуемый пакет | Распространение   |
| "Это внутри функции" | Написать в теле функции        | Область видимости |

Все три уровня — уже существующие механизмы: пакет, файл, область видимости. Ничего нового не нужно.

#### Почему не `pub`

- То, что не хочется показывать другим, не должно лежать на верхнем уровне (поместите в локальную
  область видимости)
- Вспомогательные функции, разделяемые несколькими файлами, помещаются в отдельный непубликуемый
  пакет
- "Можно ли защитить" и "должен ли быть сигнал" — это две разные вещи. На текущем этапе нет
  сторонней экосистемы, сигнал бессмысленен
- Дверь не запирается. Входить через дверь — вежливо, перелезать через стену — свобода. Язык не
  занимается вежливостью

#### В будущем

Когда экосистема созреет и потребуются принудительные границы, их можно ввести через отдельный RFC.
Добавление ограничений обратно совместимо (публично по умолчанию → явно помечено как внутреннее). Но
этот RFC не предопределяет это направление и не обещает, что оно наступит.

### 4. Разрешение путей

#### Путь модуля → файл

```
use math.geometry.{Point}
```

Порядок поиска (единственное правило):

1. **Зарегистрированный в Registry модуль**: `math.geometry` уже в Registry → использовать напрямую
2. **Стандартная библиотека**: `std` или `std.*` → встроенные модули
3. **Каталог src проекта**: `<project_root>/src/math/geometry.yx`
4. **Каталог vendor**: `.yaoxiang/vendor/<pkg>-*/src/` (в будущем)

Порядок попыток расположения файла:

```
base/name.yx
base/name/mod.yx
```

Остановиться на первом найденном. Оба существуют одновременно → ошибка:

```
Двусмысленность пути модуля: `math.geometry` одновременно соответствует:
  src/math/geometry.yx
  src/math/geometry/mod.yx
Пожалуйста, удалите один из них.
```

#### mod.yx = точка входа каталога (соглашение)

`mod.yx` — это файл точки входа каталога. При `use math` загружается `src/math/mod.yx`.

Это **соглашение, не принуждение**. Пользователь может напрямую `use math.geometry` пройти к
дочернему файлу. `mod.yx` — это "рекомендуемая точка входа" (номер дома), не "единственная точка
входа" (замок).

#### Единый резолвер

Текущая единственная логика разрешения путей находится в `package/source/module_resolver.rs`.
Переместить её в `frontend/module/resolver.rs` (заменив текущий неточно названный файл нормализации
предикатов, нормализация предикатов перемещается в `frontend/core/types/eval/`).

### 5. Процесс компиляции проекта

#### Путь A: Слияние AST

Все файлы внутри пакета объединяются в **единую единицу компиляции**. Конвейер без изменений.

```
Оркестратор (над Pipeline):
  1. Определить файл точки входа
  2. Разобрать операторы use файла точки входа (только чтение строк use, не разбор тел функций)
  3. Обнаруживать файлы по путям use, добавлять в очередь
  4. Для файлов в очереди разобрать их операторы use
  5. Повторять 3-4 пока очередь не опустеет (обнаружение по требованию)
  6. Последовательно полностью разобрать все обнаруженные файлы → несколько AST
  7. Объединить в один Module (склейка всех верхнеуровневых items, Span сохраняет исходный файл)
  8. Передать в Pipeline::run() (конвейер не знает о нескольких файлах)
```

#### Внутрипакетные циклические ссылки: разрешены

Поскольку все файлы объединяются в один AST, взаимный `use` файлов внутри пакета эквивалентен
взаимной ссылке внутри одного файла:

```yaoxiang
// tree.yx
use node.{Node}
Tree: Type = { root: Node }

// node.yx
use tree.{Tree}
Node: Type = { value: Int, parent: Tree }
```

После слияния это два взаимно ссылающихся определения типов в одном AST. Компилятор это и так
поддерживает.

#### Межпакетные циклы: потом

Пакет — единица распространения, между пакетами нужен топологический порядок. Сейчас нет экосистемы
сторонних пакетов, не обрабатывается. При встрече просто выдавать ошибку.

#### Выбор файла точки входа

Приоритет:

1. `[run].main` (yaoxiang.toml)
2. `path` первого элемента `[[bin]]`
3. `src/main.yx` (соглашение по умолчанию)

Без `yaoxiang.toml`: компилировать данный файл напрямую. В Registry только std. Это не "однофайловый
режим" — это "естественный результат пустого обнаружения".

#### Загрузка Registry по требованию

Содержимое Registry = все модули, достижимые из точки входа по `use`. Недостижимые модули не
разбираются, не регистрируются, не существуют. **Это не оптимизация, это определение.**

### 6. std модули и пользовательские модули гомогенны

Для typecheck операции `use std.io.{println}` и `use math.geometry.{Point}` совершенно одинаковы:

1. Найти record модуля в Registry
2. Взять поле
3. Привязать к текущей области видимости

Источник (Std / User / Vendor) — это метаданные, не влияют на логику разрешения. Особая обработка
native-функций откладывается до уровня IR gen / codegen.

## Стратегия реализации

### Фаза 1: Унификация разрешения путей

1. Переместить нормализацию предикатов из `frontend/module/resolver.rs` в
   `frontend/core/types/eval/`
2. Перенести логику разрешения путей из `package/source/module_resolver.rs` в
   `frontend/module/resolver.rs`
3. Обнаружение двусмысленности путей модулей (`name.yx` и `name/mod.yx` существуют одновременно →
   ошибка)

### Фаза 2: Оркестратор многофайловой компиляции

4. Создать `frontend/module/orchestrator.rs`
5. Реализовать обнаружение по требованию (рекурсия из точки входа по use)
6. Реализовать слияние AST (склейка items нескольких файлов, Span с исходным файлом)
7. Добавить в `compiler.rs` `compile_project(project_root)`, вызывающий оркестратор

### Фаза 3: Разрешение имён use

8. `process_use_stmt` в typecheck переключается на запросы к Registry (больше не только std)
9. Обнаружение конфликтов импорта (ошибка при одинаковых именах)
10. E2E тесты: многофайловый проект `use` локальных модулей

### Фаза 4 (опционально, не блокирует #232)

11. `use path.{item as alias}` — псевдоним внутри фигурных скобок
12. Разрешение каталога vendor (совместно с RFC-014)

### Зависимости

- RFC-014 (менеджер пакетов) — поля `yaoxiang.toml`, структура каталога vendor (нужно только в
  Фазе 4)
- Никаких других предварительных зависимостей
