# RFC-029: Модульная семантическая система

## Резюме

Подключение модульной системы к конвейеру компиляции, реализация многофайловой компиляции.

**Основное определение**: Модуль = все привязки верхнего уровня одного файла `.yx`. Тип модуля =
типы этих привязок (выведенные). `use` = деструктуризация record. Нет `pub`, нет `private`, нет
`export`, нет механизма видимости.

**Основные принципы**:

- Проверщик типов запрашивает только предварительно собранный ModuleRegistry, не обращается к диску
- Файлы внутри пакета объединяются в единую единицу компиляции (склейка AST), циклические ссылки
  внутри пакета естественно допускаются
- Registry загружается по требованию: загружаются только модули, достижимые из точки входа по `use`

**Не включает**: кэширование, наблюдение за файлами, горячую перезагрузку, инкрементальную
перекомпиляцию, обработку межпакетных циклических зависимостей.

## Мотивация

### Текущие проблемы

1. **Компилятор поддерживает только один файл**: `Pipeline::run(name, source)` принимает одну
   строку, не может обрабатывать межфайловые зависимости
2. **`use` может разрешать только модули std**: `use` между локальными файлами все сообщают "Unknown
   variable" (#232)
3. **Резолвер модулей в неправильном месте**: единственная логика разрешения путей находится в
   `package/source/module_resolver.rs`, `frontend/module/resolver.rs` фактически является
   нормализацией предикатов времени компиляции (RFC-027)

### Цели проектирования

- Проект может компилировать несколько файлов `.yx`
- Чёткая семантика операторов `use`: деструктуризация record, не специальный механизм
- Один файл продолжает работать, не требуется `yaoxiang.toml`
- Конвейер (`Pipeline`) без изменений, поддержка нескольких файлов — дело уровня оркестрации
- Не вводятся новые ключевые слова, новые узлы AST, новые концепции

## Предложение

### 1. Модуль = record of bindings

**Модуль** — это все привязки верхнего уровня одного файла `.yx`.

```yaoxiang
// math/geometry.yx
Point: Type = { x: Float, y: Float }
distance: (a: Point, b: Point) -> Float = { ... }
```

Содержимое этого модуля — `{ Point: Type, distance: (Point, Point) -> Float }`.

Модуль не является специальной сущностью. Это экземпляр модели `name: type = value` — record,
определённый на границе файла. Тип модуля выводится из привязок, явные аннотации никогда не
требуются.

Привязки, введённые через `use`, **также** являются частью содержимого модуля:

```yaoxiang
// math/mod.yx
use geometry.{Point, distance}
```

Содержимое модуля `math` = `{ Point: Type, distance: (Point, Point) -> Float }`. Снаружи
`use math.{Point}` может получить это. `use math.geometry.{Point}` также может получить. Два пути
указывают на одну и ту же привязку.

### 2. use = деструктуризация record

Все формы `use` — это доступ к полю record + привязка:

```yaoxiang
use math.geometry.{Point, distance}
```

эквивалентно:

```yaoxiang
Point = math.geometry.Point
distance = math.geometry.distance
```

| Синтаксис           | Семантика                                                              |
| ------------------- | ---------------------------------------------------------------------- |
| `use path.{item}`   | Взять поле `item` record `path`, привязать к текущей области видимости |
| `use path.{a, b}`   | Взять несколько полей                                                  |
| `use path`          | Взять сам record `path`, привязать к последнему сегменту имени         |
| `use path as alias` | Взять сам record `path`, привязать к `alias`                           |

#### Несуществующий синтаксис

- ~~`use path.*`~~: подстановочный импорт. Не нужен, явно перечислите привязки.
- ~~`from path use item`~~: Python-стиль. Не принят.
- ~~`use path.{item as alias}`~~: псевдоним внутри фигурных скобок. Опционально в Phase 4, не
  блокирует #232.

#### Конфликты импорта

Привязки с одинаковым именем сразу сообщают об ошибке:

```
Имя `Point` конфликтует:
  math.geometry.Point
  graphics.shapes.Point
Пожалуйста, используйте разные имена или псевдоним модуля.
```

### 3. Видимость: не существует

**Этот RFC не вводит никакого механизма видимости.** Все привязки верхнего уровня видимы всему коду,
который может записать путь.

Это намеренное проектное решение, а не упущение.

#### Обоснование дизайна

| Что выразить         | Как сделать                        | Механизм          |
| -------------------- | ---------------------------------- | ----------------- |
| "Это API"            | Поместить в опубликованный пакет   | Распространение   |
| "Это внутреннее"     | Поместить в неопубликованный пакет | Распространение   |
| "Это внутри функции" | Написать в теле функции            | Область видимости |

Все три уровня — это уже существующие механизмы: пакет, файл, область видимости. Нового не нужно.

#### Почему не `pub`

- То, что вы не хотите использовать другим, не должно находиться на верхнем уровне (поместите в
  локальную область видимости)
- Вспомогательные функции, разделяемые между файлами, помещаются в отдельный неопубликованный пакет
- "Может ли это предотвратить" и "должен ли быть сигнал" — это две разные вещи. На текущем этапе нет
  сторонней экосистемы, сигнал бессмысленен
- Дверь не запирается. Пройти через дверь — вежливо, перелезть через стену — свобода. Язык не
  занимается вежливостью

#### В будущем

Когда экосистема созреет и потребуются принудительные границы, их можно будет ввести через отдельный
RFC. Добавление ограничений обратно совместимо (по умолчанию публично → явно отмечено как
внутреннее). Но этот RFC не предопределяет это направление и не обещает, что оно наступит.

### 4. Разрешение путей

#### Путь модуля → файл

```
use math.geometry.{Point}
```

Порядок поиска:

1. **Зарегистрированный модуль в Registry**: `math.geometry` уже в Registry → использовать напрямую
2. **Стандартная библиотека**: `std` или `std.*` → встроенный модуль
3. **Каталог импортёра**: `<importer_dir>/math/geometry.yx` (локальный модуль имеет приоритет)
4. **Корень проекта** (ближайший предок `yaoxiang.toml`): `<project_root>/math/geometry.yx`
5. **Каталог vendor**: `.yaoxiang/vendor/<pkg>-*/src/` (в будущем)

Порядок попыток локализации файла:

```
base/name.yx
base/name/mod.yx
```

Останавливается на первом найденном. Если оба существуют одновременно → ошибка:

```
Неоднозначность пути модуля: `math.geometry` соответствует одновременно:
  src/math/geometry.yx
  src/math/geometry/mod.yx
Пожалуйста, удалите один из них.
```

Один и тот же ключ модуля попадает в файл в **двух корнях** и оба используются (например,
`tests/lib.yx` и `<root>/lib.yx` используются точкой входа tests/ и корневой точкой входа
соответственно) → аналогично сообщается об ошибке неоднозначности, а не молчаливом затенении.

> Редакция от 2026-08-03 (вызвана #247 / RFC-036): обнаружение и разрешение реализуются согласно
> реализации. Обнаружение отслеживается по `use` (установленный протокол §5 этого RFC), заменяя
> рекурсию каталогов из первоначальной реализации — ошибки компиляции несвязанных файлов больше не
> блокируют запуск, изоляция тестовых файлов `yaoxiang test` становится работоспособной. Правило
> «приоритет каталога импортёра» в правиле двух корней гарантирует неизменность поведения для
> однокаталоговых проектов; «резерв в корне проекта» позволяет точкам входа в подкаталогах
> (например, `tests/foo_test.yx`) импортировать модули корня проекта. Разметка `src/` (пакет
> RFC-014) реализуется на уровне vendor, не влияет на локальные два корня.

#### mod.yx = точка входа каталога (соглашение)

`mod.yx` — это файл точки входа каталога. При `use math` загружается `src/math/mod.yx`.

Это **соглашение, а не требование**. Пользователь может напрямую `use math.geometry` для
проникновения в подфайл. `mod.yx` — это "рекомендуемая точка входа" (номер дома), а не "единственная
точка входа" (замок).

#### Единый резолвер

Текущая единственная логика разрешения путей находится в `package/source/module_resolver.rs`.
Перенесите её в `frontend/module/resolver.rs` (заменив текущий файл с неверным названием для
нормализации предикатов, нормализация предикатов перемещается в `frontend/core/types/eval/`).

### 5. Процесс компиляции проекта

#### Путь A: объединение AST

Все файлы внутри пакета объединяются в **единую единицу компиляции**. Конвейер без изменений.

```
Оркестратор (поверх Pipeline):
  1. Определить файл точки входа
  2. Разобрать операторы use файла точки входа (только чтение строк use, не разбирать тела функций)
  3. Обнаружить файлы по путям use, добавить в очередь
  4. Для файлов в очереди, разобрать их операторы use
  5. Повторять 3-4, пока очередь не опустеет (обнаружение по требованию)
  6. Полностью разобрать все обнаруженные файлы по одному → несколько AST
  7. Объединить в один Module (склейка всех items верхнего уровня, Span сохраняет исходный файл)
  8. Передать в Pipeline::run() (конвейер не знает о нескольких файлах)
```

#### Циклические ссылки внутри пакета: допускаются

Поскольку все файлы объединяются в один AST, взаимный `use` между файлами внутри пакета эквивалентен
взаимной ссылке в одном файле:

```yaoxiang
// tree.yx
use node.{Node}
Tree: Type = { root: Node }

// node.yx
use tree.{Tree}
Node: Type = { value: Int, parent: Tree }
```

После объединения это два определения типов в одном AST, ссылающихся друг на друга. Компилятор уже
это поддерживает.

#### Циклы между пакетами: позже

Пакет — это единица распространения, между пакетами требуется топологический порядок. В настоящее
время нет экосистемы сторонних пакетов, пока не обрабатывается. При обнаружении просто сообщить об
ошибке.

#### Выбор файла точки входа

Приоритет:

1. `[run].main` (yaoxiang.toml)
2. `path` первого элемента `[[bin]]`
3. `src/main.yx` (соглашение по умолчанию)

Без `yaoxiang.toml`: скомпилировать данный файл напрямую. В Registry только std. Это не
"однофайловый режим" — это "естественный результат с пустым обнаружением".

#### Загрузка Registry по требованию

Содержимое Registry = все модули, достижимые из точки входа по `use`. Недостижимые модули не
разбираются, не регистрируются, не существуют. **Это не оптимизация, это определение.**

### 6. std-модуль и пользовательский модуль однородны

Для проверки типов `use std.io.{println}` и `use math.geometry.{Point}` полностью идентичны:

1. Найти record модуля в Registry
2. Взять поле
3. Привязать к текущей области видимости

Источник (Std / User / Vendor) — это метаданные, не влияют на логику разрешения. Специальная
обработка native-функций откладывается до уровня IR gen / codegen.

## Стратегия реализации

### Phase 1: Единое разрешение путей

1. Переместить нормализацию предикатов из `frontend/module/resolver.rs` в
   `frontend/core/types/eval/`
2. Перенести логику разрешения путей из `package/source/module_resolver.rs` в
   `frontend/module/resolver.rs`
3. Обнаружение неоднозначности пути модуля (`name.yx` и `name/mod.yx` существуют одновременно →
   ошибка)

### Phase 2: Оркестратор нескольких файлов

4. Создать `frontend/module/orchestrator.rs`
5. Реализовать обнаружение по требованию (рекурсивно от точки входа по use)
6. Реализовать объединение AST (склейка items нескольких файлов, Span с исходным файлом)
7. Добавить `compile_project(project_root)` в `compiler.rs`, вызывающий оркестратор

### Phase 3: Разрешение имён use

8. `process_use_stmt` проверки типов изменить на запрос к Registry (больше не только std)
9. Обнаружение конфликтов импорта (одно имя → ошибка)
10. E2E-тестирование: `use` локального модуля в многофайловом проекте

### Phase 4 (опционально, не блокирует #232)

11. `use path.{item as alias}` псевдоним внутри фигурных скобок
12. Разрешение каталога vendor (совместно с RFC-014)

### Зависимости

- RFC-014 (менеджер пакетов) — поля `yaoxiang.toml`, структура каталога vendor (нужно только в
  Phase 4)
- Других предварительных зависимостей нет
