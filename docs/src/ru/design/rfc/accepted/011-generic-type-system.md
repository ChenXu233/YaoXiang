# RFC-011: Дизайн системы дженериков — абстракции с нулевой стоимостью и замена макросов

## Резюме

Этот документ определяет **дизайн системы дженериков** языка YaoXiang, который реализует абстракции
с нулевой стоимостью посредством мощных возможностей дженериков, снижает зависимость от макросов за
счёт оптимизаций compile-time и предоставляет механизм устранения мёртвого кода.

**Ключевые дизайнерские решения**:

- **Унифицированный синтаксис сигнатур**: `(T: Type, R: Type) -> ...` — параметры дженериков и
  обычные параметры унифицированы
- **Механизм самоописания Type**: `Type` — это специальная сущность языкового уровня; позиция `Type`
  в сигнатуре автоматически заполняется путём вывода
- **type constraint**: `T: Dup + Add` — множественные type constraint, ограничения на типы функций
- **associated type**:
  `Iterator: (Item: Type) -> Type = { next: () -> Option(Item), has_next: () -> Bool }`
- **Дженерики compile-time**: `N: Int` — параметры-значения дженериков, инстанциация константами
  compile-time
- **conditional type**: `If: (C: Bool, T: Type, E: Type) -> Type` — вычисления на уровне типов, type
  family

**Ценность**:

- Абстракции с нулевой стоимостью: мономорфизация compile-time, без накладных расходов в runtime
- Устранение мёртвого кода: анализ графа инстанциации + оптимизации LLVM
- Замена макросов: дженерики заменяют 90% сценариев использования макросов
- Безопасность типов: проверки compile-time, удобно для IDE
- **Явное лучше неявного**: самоописание `Type`, автоматический вывод компилятором

## Идея вселенной типов и value-dependent типы

Система дженериков YaoXiang построена на **идее вселенной типов** — ментальной модели, унифицирующей
все концепции языка в многоуровневую структуру. Ключевая инновация заключается в повышении
**value-dependent типов** до граждан первого класса на уровне Type2.

### Что такое value-dependent типы?

**Value-dependent тип** — это тип, зависящий от одного или нескольких **значений** (а не только от
других типов). Эти значения могут быть вычислены compile-time, обеспечивая гарантии безопасности
типов уже на этапе компиляции.

```yaoxiang
# Традиционные дженерики: параметры-типы
List: (T: Type) -> Type

# Value-dependent типы: параметры-значения
Vec: (n: Int) -> Type  # тип вектора зависит от значения длины n
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type  # тип матрицы зависит от числа строк и столбцов
```

### Ключевые преимущества value-dependent типов

По сравнению с традиционными дженериками, value-dependent типы YaoXiang обладают следующими
ключевыми преимуществами:

| Свойство                         | Традиционные дженерики (C++/Rust)                     | value-dependent типы YaoXiang                                        |
| -------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------- |
| Значения, от которых зависит тип | Только параметры-типы                                 | Любые значения, включая результаты вызовов функций                   |
| Вычисление compile-time          | Ручная специализация шаблонов C++, отсутствует в Rust | Автоматическое вычисление compile-time с гарантией завершения        |
| Вычисления на уровне типов       | Метапрограммирование шаблонов (сложно/опасно)         | Унифицированный движок вычислений на уровне типов                    |
| Безопасность типов               | Отсутствует в C++, ограничена в Rust                  | Полная безопасность типов, проверки compile-time                     |
| Проверка размерностей            | Проверка в runtime или ручная специализация           | Проверка размерностей compile-time, без накладных расходов в runtime |

### Уровни вселенной типов и value-dependent типы

Идея вселенной типов разделяет концепции языка по семантическим ролям на разные уровни.
value-dependent типы расположены на **уровне Type2**:

| Уровень   | Роль                                                | Примеры                                                                                              |
| --------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Type-1    | Значения                                            | `42`, `factorial(5)`, сами функции                                                                   |
| Type0     | Ключевое слово мета-типа                            | `Type`                                                                                               |
| Type1     | Конкретные типы                                     | `Int`, `String`, `Vec(3)`                                                                            |
| **Type2** | **Функции/конструкторы типов/value-dependent типы** | `add: (Int, Int) -> Int`, `Vec: (n: Int) -> Type`, `Matrix: (T: Type, Rows: Int, Cols: Int) -> Type` |

**Ключевое дизайнерское решение**: функции, конструкторы типов и value-dependent типы уровня Type2
имеют **унифицированный синтаксис** — все они имеют форму `(params) -> result`:

- Обычная функция: `(Int, Int) -> Int` → результат — значение
- Конструктор типа: `(T: Type) -> Type` → результат — тип
- Value-dependent тип: `(n: Int) -> Type` → результат — тип, но зависящий от параметров-значений

> **Изоморфизм Карри-Ховарда**: это унифицирование — не совпадение. Изоморфизм Карри-Ховарда
> утверждает «типы суть утверждения, программы суть доказательства» — тип функции `A → B`
> соответствует логической импликации «если A, то B», дженерик `(T: Type) -> Type` соответствует
> квантору всеобщности «для всех типов T», а value-dependent тип `(n: Int) -> Type` соответствует
> «для каждого целого n существует тип». YaoXiang унифицирует функции, конструкторы типов и
> value-dependent типы на уровне Type2, по сути объединяя «доказательство» и «вычисление» в одну
> концепцию — **конструктивное доказательство**. Это прямое воплощение изоморфизма Карри-Ховарда в
> дизайне языка: одна форма (`(params) -> result`) одновременно несёт логические утверждения и
> процесс вычисления.

### Гарантия детерминированности compile-time

Идея вселенной типов YaoXiang требует: **всё на уровне Type должно быть определено compile-time**.

```yaoxiang
# Пример проверки размерностей compile-time
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
    # Проверка compile-time: размерности должны быть положительными
    _assert: Assert(Rows > 0),
    _assert: Assert(Cols > 0),
}

# Создание единичной матрицы 3x3 — выполняется compile-time
identity: (T: Add + Zero + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    # ...
}

# Вычисление compile-time: factorial(3) = 6, размер вектора определяется compile-time
vec: Vec(factorial(3)) = Vec(6)()
```

Компилятор автоматически:

1. Обнаруживает вызовы функций в позиции типа
2. Выполняет проверку завершения функции compile-time (см. механизм проверки завершения ниже)
3. Выполняет вычисление compile-time
4. Встраивает результат в генерируемый тип

### Сценарии применения value-dependent типов

#### Проверка размерностей compile-time

```yaoxiang
# Умножение матриц: проверка совпадения размерностей compile-time
multiply: (T: Add + Multiply + Zero,
           Rows: Int, Cols: Int, M: Int) -> ((
    a: Matrix(T, Rows, Cols),
    b: Matrix(T, Cols, M)
) -> Matrix(T, Rows, M)) = {
    # Проверка compile-time: a.Cols == b.Rows, иначе ошибка компиляции
    result = Matrix(T, Rows, M)()
    # ...
}

# Ошибка перехватывается compile-time:
# multiply(matrix_2x3, matrix_4x2)  # Ошибка компиляции: 2 != 4
```

#### Типобезопасный размер массива

```yaoxiang
# Размер массива — константа compile-time
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    length: N,
}

# N — константа compile-time, может использоваться в вычислениях на уровне типов
first_three: Array(Int, 3) = Array(Int, 3)(1, 2, 3)
# first_three.length == 3 (известно compile-time)
```

#### Цель покрытия сбоев границ compile-time (направление #299)

> **Пояснение о состоянии реализации** (#299): типы контейнеров деспециализированы — `Array(T, N)`
> теперь является конструктором const-дженериков; точки привязки литерального контекста и предикат
> `in` membership уже реализованы. (#300): в точке привязки литерала `Array(T, N)` значение N и тип
> элементов уже принудительно проверяются compile-time (E1002), **N является доверенным** —
> механизмы данного раздела могут основываться на утверждении «аннотация N == длина в runtime».
> Текущие `[]` выход за границы индекса (E6003) и отсутствие ключа Dict (E6008) находятся в
> **переходном состоянии ошибок runtime**; value-dependent типы в данном разделе — это целевой
> механизм переноса этих сбоев границ в **compile-time**:
>
> - const-индексация: `a[5]` (5 — константа compile-time) при `a: Array(Int, 3)` сразу отвергается
>   compile-time;
> - индексация значением: `a[i]` требует предусловия `i < len(a)`, доказываемого контрактом
>   value-dependent типа;
> - предикат `in` — основа предусловий логики Хоара: `n in 1..10`, `x in some_set` — это доказуемые
>   compile-time утверждения.
>
> Полный дизайн refinement-типов будет дополнен данным разделом при реализации.

#### Дженерик-функции

```yaoxiang
# map: дженерик-функция, параметры-типы T, R определяются compile-time
map: (T: Type, R: Type) -> (
    (list: List(T), f: (x: T) -> R) -> List(R)
) = (list, f) => {
    result = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Использование полностью прозрачно, типы выводятся автоматически
numbers = List(Int)()   # Исправление: двухслойная форма конструирования значений (см. §9.1); элементы заполняются через push
numbers.push(1)
numbers.push(2)
numbers.push(3)
doubled = map(numbers, (x) => x * 2)  # Выводится как map[Int, Int]
```

### Механизм проверки завершения (унифицирован с RFC-027)

Вычисление compile-time для value-dependent типов должно **гарантировать завершение**, иначе type
system попадёт в бесконечный цикл. Проверка завершения выполняется **полностью автоматически**
конвейером доказательств compile-time из RFC-027 — компилятор автоматически синтезирует метрики;
доказуемые рекурсии/циклы проходят, недоказуемые сразу дают ошибку компиляции. **Полуавтоматическим
аннотациям не оставлено лазеек**: `//! decreases` и `/*! invariant !*/` из RFC-022 отменены вместе с
RFC-022, спецификация — это сама аннотация типа.

#### Проверка завершения рекурсивных функций

Перед вычислением compile-time компилятор проверяет, что аргументы рекурсивных вызовов строго
убывают на каждом пути рекурсии (RFC-027 §6.7). Никаких аннотаций спецификации не требуется:

```yaoxiang
# Факториал compile-time: без //! requires/ensures/decreases, компилятор анализирует автоматически
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Анализ компилятора: n-1 < n → убывает → завершается
}

# Использование: вызов в позиции типа, компилятор сначала проверяет завершение, затем вычисляет
vec: Vec(factorial(5)) = Vec(120)()  # Вычисление compile-time factorial(5) = 120
```

| Сценарий                                                              | Поведение                        |
| --------------------------------------------------------------------- | -------------------------------- |
| Компилятор может проанализировать убывание рекурсии (например, `n-1`) | Вычисление compile-time          |
| Не убывает / убывание неопределимо                                    | Ошибка компиляции                |
| Вызов в runtime (не в позиции типа)                                   | Проверка завершения не требуется |

#### Проверка завершения циклов

Циклы не требуют аннотаций `: Invariant(...)` или `: decreases(...)`. Аннотации refinement-типов на
переменных (например, `UpTo(n)`) одновременно задают инвариант цикла и границу метрики. Компилятор
перебирает четыре стратегии синтеза метрик по приоритету и останавливается на первой успешной
(RFC-027 §7):

1. **Автоматический синтез линейной ранговой функции** — извлечение границ переменных из аннотаций
   типов, перебор линейных комбинаций, верификация SMT: m ≥ 0 и m' < m на всех путях
2. **Подсчёт нарушений предиката** (экспериментально) — извлечение violation_count из определения
   целевого типа (например, `Sorted`), покрытие соседних обменов/перемещений
3. **Шаблон ограниченного возрастания/убывания** — `v += const` → метрика `upper - v` (вырождение
   стратегии 1, самый быстрый путь)
4. **Шаблон метрики с мультипликативным масштабированием** — `v *= const` (const > 1) → метрика
   `ceil(log_const(upper / v))`

```yaoxiang
sum: (arr: Array(Int, n)) -> Int = {
    mut i: UpTo(arr.len) = 0   # Аннотация типа даёт верхнюю границу arr.len и нижнюю 0
    while i < arr.len {
        # Автоматический вывод компилятора: метрика arr.len - i, на каждой итерации строго убывает на 1 → завершение доказано
        s += arr[i]; i += 1
    }
    return s
}
```

#### Рабочий процесс проверки завершения

```
┌─────────────────────────────────────────────────────────────┐
│  Фаза проверки типов                                       │
│  Встречается вызов функции в позиции типа (например, Vec(factorial(5))) │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  1. Проверка завершения (конвейер доказательств RFC-027, полностью автоматический) │
│     - Рекурсивные функции: проверка строгого убывания аргументов на каждом пути рекурсии │
│     - Циклы: четыре стратегии синтеза метрик (линейный ранг/подсчёт нарушений/ограниченный шаблон/ │
│       мультипликативное масштабирование), верификация SMT убывания                                │
│     - Невозможно доказать → ошибка компиляции (жёсткая граница, без полуавтоматических аннотаций) │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  2. Вычисление compile-time (выполняется встроенным интерпретатором) │
│     - Чистые функции: непосредственное вычисление          │
│     - Побочные эффекты: ошибка компиляции (позиция типа должна быть без побочных эффектов) │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  3. Встраивание результата в тип                            │
│     - Vec(factorial(5)) → Vec(120)                          │
│     - Matrix(Float, 3, 3) → конкретный тип                  │
└─────────────────────────────────────────────────────────────┘
```

#### Преимущества

- **Безопасность**: гарантия того, что вычисление compile-time обязательно завершится, тип-система
  не попадёт в бесконечный цикл
- **Унифицированность**: проверка завершения и верификация корректности (генерация VC) используют
  общий конвейер доказательств compile-time (RFC-027), без отдельного синтаксиса спецификаций
- **Полная автоматизация**: компилятор автоматически синтезирует метрики из аннотаций типов;
  доказуемое проходит, недоказуемое — ошибка — без необходимости ручного `decreases` от программиста

## Мотивация

### Зачем нужна сильная система дженериков?

Существующие mainstream языки имеют ограничения в дженериках:

| Язык         | Возможности дженериков   | Проблема                                                                                    |
| ------------ | ------------------------ | ------------------------------------------------------------------------------------------- |
| Java         | Граничные типы           | Мономорфизация compile-time, без специализации дженериков                                   |
| C#           | Ограничения дженериков   | Проверка типов в runtime, накладные расходы                                                 |
| Rust         | Дженерики + Trait        | Сложная система Trait, крутая кривая обучения                                               |
| C++          | Шаблоны                  | Сложная специализация шаблонов, плохие сообщения об ошибках                                 |
| **YaoXiang** | **value-dependent типы** | **Тип может зависеть от значений, проверка размерностей compile-time, гарантия завершения** |

### Ключевые противоречия

1. **Производительность vs гибкость**: гибкость в runtime vs оптимизации compile-time
2. **Сложность vs простота**: мощная type system vs удобство использования
3. **Макросы vs дженерики**: генерация кода макросами vs безопасность типов дженериков
4. **Зависимость от значений vs безопасность типов**: традиционные дженерики не могут проверять
   размерности compile-time

### Ключевые преимущества value-dependent типов

**value-dependent типы** YaoXiang — это ключевое преимущество по сравнению с традиционными
дженериками:

| Преимущество                   | Описание                                                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **Тип зависит от значения**    | `Vec: (n: Int) -> Type` позволяет типу зависеть от конкретного значения                                                         |
| **Вычисление compile-time**    | Вызовы функций в позиции типа вычисляются compile-time, результат непосредственно встраивается в тип                            |
| **Проверка размерностей**      | `Matrix(Float, 3, 3)` проверяет размерности матрицы compile-time                                                                |
| **Вычисления на уровне типов** | Условные типы `If`, `Match` поддерживают вычисления на уровне типов                                                             |
| **Гарантия завершения**        | Проверка завершения compile-time (автоматический синтез метрик) гарантирует, что вычисление compile-time обязательно завершится |

```yaoxiang
# Проверка compile-time, невозможная в C++/Rust
matrix: Matrix(Float, factorial(3), factorial(2)) = ...
# Вычисление compile-time: factorial(3) = 6, factorial(2) = 2
# Тип: Matrix(Float, 6, 2)

# Несовпадение размерностей перехватывается compile-time
identity: Matrix(Float, 3, 3) = ...
# multiply(matrix_2x3, identity_3x3)  # Ошибка компиляции: 2 != 3
```

### Ценность системы дженериков

```yaoxiang
# Пример: унифицированный дизайн API
# Операция map для разных типов контейнеров

# Традиционный подход: отдельная реализация для каждого типа
map_int_array: (array: Array(Int), f: Fn(Int) -> Int) -> Array(Int) = ...
map_string_array: (array: Array(String), f: Fn(String) -> String) -> Array(String) = ...
map_int_list: (list: List(Int), f: Fn(Int) -> Int) -> List(Int) = ...
map_string_list: (list: List(String), f: Fn(String) -> String) -> List(String) = ...

# Подход с дженериками: одна дженерик-функция покрывает все типы
map: (T: Type, R: Type)(container: Container(T), f: Fn(T) -> R) -> Container(R) = {
    for item in container {
        result.push(f(item))
    }
    result
}
```

## Цели дизайна

### Основные цели

1. **Абстракции с нулевой стоимостью** — вызов дженерика эквивалентен вызову конкретного типа
2. **Устранение мёртвого кода** — анализ compile-time, инстанциация только используемых дженериков
3. **Замена макросов** — дженерики заменяют 90% сценариев использования макросов
4. **Безопасность типов** — проверки compile-time, без накладных расходов типов в runtime
5. **Удобно для IDE** — интеллектуальные подсказки, понятные сообщения об ошибках
6. **value-dependent типы** — тип может зависеть от значений, поддержка проверки размерностей
   compile-time
7. **Безопасность вычислений compile-time** — гарантия завершения вычислений compile-time через
   проверку завершения (автоматический синтез метрик из RFC-027)

### Принципы дизайна

- **Определённость compile-time**: параметры дженериков определяются compile-time
- **Приоритет мономорфизации**: генерация конкретного кода, избежание вызовов виртуальных функций
- **Управление через ограничения**: type constraint направляют инстанциацию
- **Платформенные оптимизации**: специализация для поддержки платформенно-специфичных оптимизаций
- **Унификация вселенной типов**: функции/конструкторы типов/value-dependent типы унифицированы на
  уровне Type2
- **Гарантия завершения**: вызовы функций в позиции типа должны доказуемо завершаться

## Предложение

### 1. Базовые дженерики

#### 1.1 Параметры-типы дженериков

> **Ключевое правило**: определение дженерик-типа **должно явно аннотироваться как `: Type`**, иначе
> оно будет выведено HM как функция.
>
> | Запись                            | Значение                                |
> | --------------------------------- | --------------------------------------- |
> | `List: (T: Type) -> Type = {...}` | ✅ Конструктор типа                     |
> | `List = {...}`                    | ❌ HM выводит как функцию, а не как тип |

```yaoxiang
# Определение дженерик-типа (должно иметь : Type)
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self
}

List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (self: List(T), item: T) -> Void,   # self — лишь имя по соглашению, не ключевое слово
    get: (self: List(T), index: Int) -> Option(T),
}

# Дженерик-функция (без : Type, HM выводит как функцию)
map: (T: Type, R: Type) -> ((opt: Option(T), f: Fn(T) -> R) -> Option(R)) = {
    return match opt {
        some => Option.some(f(some)),
        none => Option.none(),
    }
}

# Ограничение дженерика (прямое выражение, return в одной строке можно опустить)
clone: (T: Clone)(value: T) -> T = value.clone()

# Несколько параметров-типов
combine: (T: Type, U: Type) -> ((a: T, b: U) -> (T, U)) = (a, b)
```

#### 2.4 Встроенные marker trait: Dup и Clone

**Три типа семантики копирования**:

| Тип                                  | Значение                                                                                | Способ срабатывания                                | Сценарий применения                |
| ------------------------------------ | --------------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------- |
| **Копирование примитивных значений** | При присваивании автоматическое копирование значения, два значения полностью независимы | Автоматически при присваивании/передаче параметров | Int, Float, Bool, Char             |
| **Dup**                              | Мелкая копия: копирование handle/токена, базовые данные разделяются                     | Автоматически при присваивании/передаче параметров | токены `&T`, `ref T`, String/Bytes |
| **Clone**                            | Глубокая копия: создание полностью независимой копии                                    | `value.clone()`                                    | Любой тип, реализующий Clone       |

**Семантика Dup**: для типа, реализующего Dup, при присваивании/передаче параметров ownership не
передаётся — компилятор копирует handle/токен, и несколько владельцев указывают на одни и те же
базовые данные. Это дополняет семантику Move по умолчанию из модели ownership в RFC-009.

**Dup и Clone — ортогональные концепции**:

```
Dup = копирование handle, разделяемые данные (изменения влияют друг на друга)
Clone = копирование данных, копия независима (изменения не влияют друг на друга)
```

**Правила**:

```
1. Примитивные типы значений (Int, Float, Bool, Char) — встроенное в компилятор копирование значений, не относятся к Dup
2. Dup — применимо только к типам ссылок/токенов и типам с внутренним подсчётом ссылок
3. Clone — явное глубокое копирование, может быть реализовано любым типом
4. Move по умолчанию — остальные типы сохраняют семантику Move по умолчанию
```

**Какие типы являются Dup**:

| Тип                           | Dup         | Причина                                                                                       |
| ----------------------------- | ----------- | --------------------------------------------------------------------------------------------- |
| `&T` (токен заимствования)    | ✅          | Токен нулевого размера, копирование токена = несколько представлений указывают на одни данные |
| `ref T`                       | ✅          | Копирование Rc/Arc = счётчик ссылок +1, разделяемые данные в куче                             |
| String, Bytes                 | ✅          | Внутренний подсчёт ссылок, копирование handle разделяет базовый буфер                         |
| `&mut T` (токен изменяемости) | ❌          | Линейная эксклюзивность, копирование невозможно                                               |
| struct                        | Производный | Все поля Dup → struct Dup                                                                     |
| enum                          | Производный | Все поля всех вариантов Dup → enum Dup                                                        |
| tuple                         | Производный | Все элементы Dup → tuple Dup                                                                  |
| Fn (замыкание)                | ❌          | Захваченное окружение может быть не Dup                                                       |
| `*T` (сырой указатель)        | ❌          | unsafe, не участвует в системе ownership                                                      |

**Int/Float/Bool/Char не являются Dup** — это типы значений; при присваивании компилятор
автоматически копирует значение (два значения полностью независимы). Это не «мелкая копия», а
встроенная в компилятор обработка примитивов; её не нужно и не следует выражать через атрибут типа
Dup.

```yaoxiang
# Примитивные типы значений: компилятор автоматически копирует значение (не Dup)
x: Int = 42
y = x          # Копирование значения, x и y полностью независимы
print(x)       # ✅

# Dup: мелкая копия, копирование handle разделяет данные
view: &Point = &point
view2 = view    # ✅ Dup: копирование токена, оба указывают на один и тот же point
print(view.x)   # ✅

# Clone: явное глубокое копирование, создание независимой копии
backup = big_struct.clone()  # Явный вызов

# Ограничения дженериков
dup_use: (T: Dup) -> T = x         # T: Dup → можно мелко копировать
clone_use: (T: Clone) -> T = x.clone()  # T: Clone → можно глубоко копировать
```

> **Примечание**: `Send`/`Sync` не являются видимыми пользователю trait. Безопасность межзадачного
> доступа обеспечивается ключевым словом `ref` и полностью автоматической обработкой компилятором —
> `ref` автоматически выбирает Rc или Arc, пользователю не нужно понимать Send/Sync.

Iterator: (Item: Type) -> Type = {

        }

# Используется синтаксический сахар методов: Array.Item, Array.next, Array.has_next
Array.has_next: (T: Type)(self: Array(T)) -> Bool = {
    return self.index < self.length
}

Array.next: (T: Type)(self: Array(T)) -> Option(T) = {
    if has_next(self) {
        item = self.data[self.index]
        self.index = self.index + 1
        return Option.some(item)
    } else {
        return Option.none()
    }
}

    return arr.data[0]
}

### 4. Дженерики compile-time

#### 4.1 Параметры-значения compile-time

> **Исправление (#296)**: в исходной формулировке говорилось, что «параметры-значения вроде `Int` в
> контексте дженериков по умолчанию определены compile-time» — эта формулировка **строго неверна**:
> в `add: (a: Int, b: Int) -> Int = a + b` `a`/`b` — параметры-значения runtime. Только параметры
> **конкретного типа, на которые ссылаются в позиции типа**, являются параметрами-значениями
> compile-time. Правильное определение приведено ниже.

**Ключевое дизайнерское решение**: параметр типа `Type` в сигнатуре дженерика помечает параметр-тип;
параметры, аннотированные конкретными типами (`Int`/`Bool`/`Float` и т.д.), рассматриваются как
**кандидаты в параметры-значения compile-time**. Станут ли они таковыми, зависит от того,
**ссылаются ли на их значение в позиции типа** (value-dependent). Ключевое слово `const` не
требуется.

**Правило определения (два шага)**:

1. **Грубая фильтрация по форме**: параметр, аннотированный конкретным типом (не `Type`), например
   `Int` → рассматривается как кандидат.
2. **Тонкая фильтрация по использованию**: имя кандидата появляется в **позиции типа** (тип поля
   тела типа, тип параметра внутренней `Fn`, предикат `Assert`, позиция аргумента конструктора типа
   вроде `Array(T, N)` и т.п.) → подтверждается как параметр-значение compile-time; иначе
   рассматривается как **параметр-значение runtime**.

| Запись                                                     | Определение                        | Причина                                                                   |
| ---------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------- |
| `add: (a: Int, b: Int) -> Int = a + b`                     | a/b — параметры-значения runtime   | Появляются только в позиции значения, не участвуют в конструировании типа |
| `Array: (T: Type, N: Int) -> Type = { data: Array(T, N) }` | N — параметр-значение compile-time | N появляется в позиции аргумента конструктора типа `Array(T, N)`          |
| `factorial: (N: Int) -> (k: N) -> Int`                     | N — параметр-значение compile-time | N выступает типом внутреннего параметра `k`                               |
| `Foo: (T: Type, N: Int) -> Type = { x: T }`                | N проваливается (см. ниже)         | N не упомянут в теле типа → вырождается в параметр-значение runtime       |

> **Суть value-dependent**: параметр-значение compile-time — это и есть value-dependent тип — только
> когда значение используется для **конструирования типа**, его нужно определять compile-time. Форма
> (`: Int`) определяет лишь кандидатство, использование (появление в позиции типа) определяет,
> является ли он параметром-значением compile-time. Это тот же критерий, что и в разделе «Гарантия
> детерминированности compile-time»: «вызовы функций в позиции типа вычисляются compile-time».

```yaoxiang
# ════════════════════════════════════════════════════════
# Параметр-значение compile-time: N упоминается в позиции типа (слот длины Array)
# ════════════════════════════════════════════════════════
StaticArray: (T: Type, N: Int) -> Type = {
    data: Array(T, N),  # N в позиции аргумента конструктора типа → параметр-значение compile-time
    length: N,
}

# Использование: factorial(5) вычисляется в позиции типа (compile-time), результат 120 встраивается в тип
arr: StaticArray(Int, factorial(5))  # StaticArray(Int, 120)

# ════════════════════════════════════════════════════════
# Value-dependent: N выступает типом внутреннего параметра k
# ════════════════════════════════════════════════════════
# N — параметр-значение compile-time (появляется в позиции типа (k: N));
# k — параметр-значение runtime, его тип — литеральный тип N (однозначный тип).
factorial: (N: Int) -> (k: N) -> Int = {
    return match k {
        0 => 1,
        _ => k * factorial(k - 1)
    }
}
```

> **Обработка провалившихся кандидатов**: кандидаты, аннотированные конкретным типом, но не
> упомянутые в позиции типа (например, `N` из `Foo` в таблице выше), вырождаются в
> параметры-значения runtime (путь уровня функции). Провалившиеся кандидаты на пути конструктора
> типа не могут занять слоты runtime (конструктор типа вычисляется compile-time), и сторона
> объявления сразу получает ошибку [E1094]: «N объявлен как параметр-значение compile-time, но не
> упомянут в теле типа» — ранее они тихо отбрасывались, что приводило к несогласованности arity
> инстанциации, см. issue [#297](https://github.com/ChenXu233/YaoXiang/issues/297).

### Never и Void: ⊥ и ⊤ в type system

Type system языка YaoXiang в изоморфизме Карри-Ховарда одновременно обладает ⊥ (ложь/пустой тип) и ⊤
(истина/Unit), представленными двумя встроенными именами типов: `Never` и `Void`.

**Never (⊥)** — три безоговорочных ядерных свойства:

1. **Нулевой конструктор**: ни один литерал или выражение не может породить значение типа `Never`.
   Это мета-свойство, оно должно быть встроенным.
2. **Принцип взрыва**: `Never <: T` для любого типа `T`. Значение `Never` может использоваться как
   значение любого типа — именно поэтому код после `assert(false)` проходит проверку типов (хотя
   никогда не выполнится).
3. **Маркер расходимости**: `f: (...) -> Never` означает, что `f` гарантированно не возвращается.
   Компилятор использует это для анализа мёртвого кода.

`Never` — встроенное имя типа, а не ключевое слово, parser его не выделяет. Синтаксис пустого
AND-типа литерала не открывается.

**Void (⊤, т.е. Unit)** — ровно один обитатель (значение void по умолчанию), носитель истинного
утверждения «всегда истинно». `Void` — это единица пустого типового произведения, `Never` — единица
пустого типового суммирования — они двойственны. `x: Void = <по умолчанию>` легально,
`x: Never = ...` не имеет правой части.

#### 4.3 Верификация compile-time (реализация стандартной библиотеки)

```yaoxiang
# ════════════════════════════════════════════════════════
# Реализация стандартной библиотеки: с использованием условных типов
# ════════════════════════════════════════════════════════

# Определения стандартной библиотеки
# IsTrue: мост от вселенной значений к вселенной типов — истинное значение Bool отображается в тип
IsTrue: (b: Bool) -> Type = match b {
    true => Void,      # ⊤, имеет значение, программа продолжается
    false => Never,    # ⊥, значения нет, расходимость
}

# Assert: примитив refinement-типа compile-time — типовое выражение предиката Bool
Assert: (cond: Bool) -> Type = IsTrue(cond)
#
# cond == true  → Assert(true)  = Void    (всегда истинно, стирается)
# cond == false → Assert(false) = Never   (всегда ложно, ошибка компиляции/расходимость)
# cond неразрешимо → конвейер доказательств решает по режиму dispatch:
#                    CompileTime → Unknown, требует prove
#                    Runtime     → вставка check, инъекция предположения в Γ

# Способ использования 1: как ограничение в определении типа
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    # Проверка compile-time: N должно быть > 0 (Assert в позиции типа)
    length: Assert(N > 0),
}

# Способ использования 2: в выражениях
IntArray: (N: Int) -> Type = StaticArray(Int, N)
# Верификация: размер IntArray(10) равен sizeof(Int) * 10
Assert(size_of(IntArray(10)) == sizeof(Int) * 10)
```

### 5. Условные типы

> **Изоморфизм Карри-Ховарда**: условные типы с точки зрения Карри-Ховарда — это **case-анализ** в
> логике. Тип `Bool` соответствует утверждению с двумя возможными значениями (True/False), `If`
> выбирает разные результаты в зависимости от истинности утверждения — это и есть логический
> case-дизъюнкт. `match C { True => T, False => E }` фактически выражает: «утверждение C истинно
> даёт заключение T, C ложно даёт заключение E».

#### 5.1 Условный тип If

```yaoxiang
# If на уровне типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Пример: ветвление compile-time
NonEmpty: (T: Type) -> Type = If(T != Void, T, Never)

Optional: (T: Type) -> Type = If(T != Void, T, Void)

# Верификация compile-time (унифицирована с определением Assert из §4.3)
# Assert: (cond: Bool) -> Type = IsTrue(cond)

# Использование
# Вычисление типа: If(True, Int, String) => Int
# Вычисление типа: If(False, Int, String) => String
```

#### 5.2 Семейства типов

> **Изоморфизм Карри-Ховарда**: семейства типов — самое прямое воплощение «утверждения суть типы».
> `Add: (A: Type, B: Type) -> Type` — это не «функция сложения, записанная на уровне типов», а
> **конструирование утверждения о сложении натуральных чисел**. `(Zero, B) => B` говорит
> «утверждение Add(Zero, B) эквивалентно B», `(Succ(A'), B) => Succ(Add(A', B))` говорит «если
> Add(A', B) истинно, то Add(Succ(A'), B) тоже истинно». Это и есть определение сложения из аксиом
> Пеано. Проверка типов подтверждает, что это выражение match проходит — что эквивалентно
> подтверждению логической непротиворечивости этого определения.

```yaoxiang
# Преобразование типа compile-time
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,  # по умолчанию
}

# Вычисление на уровне типов
Length: (T: Type) -> Type = match T.length {
    0 => Zero,
    1 => Succ(Zero),
    2 => Succ(Succ(Zero)),
    _ => TooLong,
}

# Сложение на уровне типов (Карри-Ховард: case-анализ + рекурсивный вызов; для полноценной индукции требуется проверка завершения)
Add: (A: Type, B: Type) -> Type = match (A, B) {
    (Zero, B) => B,
    (Succ(A'), B) => Succ(Add(A', B)),
}

# Пример: вычисление compile-time 2 + 3
Two: Type = Succ(Succ(Zero))
Three: Type = Succ(Succ(Succ(Zero)))
Five: Type = Add[Two, Three]  # Succ(Succ(Succ(Succ(Succ(Zero)))))
```

#### 6.3 Идеальное сочетание перегрузки функций и инлайнинга

**Ключевое свойство**: перегрузка функций естественно сочетается с оптимизацией инлайнинга,
обеспечивая абстракции с нулевой стоимостью.

```yaoxiang
# ======== Исходный код ========
sum: (arr: Array(Int)) -> Int = {
    return native_sum_int(arr.data, arr.length)
}

sum: (arr: Array(Float)) -> Float = {
    return simd_sum_float(arr.data, arr.length)
}

sum: (T: Type) -> ((arr: Array(T)) -> T) = {
    result = Zero::zero()
    for item in arr {
        result = result + item
    }
    return result
}

# Использование
int_arr = Array(Int)(1, 2, 3, 4, 5)
result = sum(int_arr)

# ======== После компиляции (эквивалентный код) ========
# Компилятор автоматически выбирает оптимальную специализацию, затем инлайнит
result = native_sum_int(int_arr.data, int_arr.length)

# Полностью эквивалентно ручному оптимизированному коду, без накладных расходов на вызов функции!
```

**Ключевые преимущества**:

1. **Интеллектуальный выбор компилятора**

   ```yaoxiang
   sum(int_arr)      # Автоматически выбирает sum: (Array(Int)) -> Int
   sum(float_arr)    # Автоматически выбирает sum: (Array(Float)) -> Float
   sum(custom_arr)  # Автоматически выбирает sum: (T: Type) -> ((arr: Array(T)) -> T)
   ```

2. **Оптимизация инлайнинга**
   - Малые функции автоматически инлайнятся в точку вызова
   - Нулевые накладные расходы на вызов функции
   - Полностью эквивалентно ручному оптимизированному коду

3. **Безопасность типов**
   - Проверка типов compile-time
   - Нулевые накладные расходы в runtime
   - Без таблиц виртуальных функций

4. **Идеально соответствует RFC-010**

   ```yaoxiang
   # Полностью использует унифицированный синтаксис
   name: type = value
   # Без новых ключевых слов вроде impl, where
   ```

**Практические примеры**:

```yaoxiang
# Чувствительные к производительности численные вычисления
fibonacci: (n: Int) -> Int = {
    if n <= 1 { return n }
    return fibonacci(n - 1) + fibonacci(n - 2)
}

fibonacci: (n: Float) -> Float = {
    # Использование формулы Бине
    phi = (1.0 + 5.0.sqrt()) / 2.0
    return (phi.pow(n) - (-phi).pow(-n)) / 5.0.sqrt()
}

# Компилятор автоматически выбирает и инлайнит

```

**Что это означает?**

- ✅ **Специализация дженериков** → естественно решается перегрузкой функций
- ✅ **Оптимизация производительности** → инлайнинг выполняется автоматически
- ✅ **Повторное использование кода** → одно имя функции, несколько реализаций
- ✅ **Абстракции с нулевой стоимостью** → полиморфизм compile-time, нулевые накладные расходы в
  runtime
- ✅ **Без новых ключевых слов** → полностью соответствует унифицированному синтаксису RFC-010

````

### 7. Механизм устранения мёртвого кода

#### 7.1 Анализ графа инстанциации

```rust
// Внутри компилятора: построение графа зависимостей инстанциации дженериков
struct InstantiationGraph {
    // Узлы: инстанциации дженериков
    nodes: HashMap<InstanceKey, InstanceNode>,

    // Рёбра: отношения использования
    edges: HashMap<InstanceKey, Vec<InstanceKey>>,
}

struct InstanceKey {
    generic: FunctionId,  // ID дженерик-функции
    type_args: Vec<TypeId>,  // Параметры-типы
    const_args: Vec<ConstId>,  // Параметры-константы
}

// Алгоритм: анализ достижимости
fn eliminate_dead_instantiations(graph: &InstantiationGraph) {
    let mut reachable = HashSet::new();

    // Начинаем с точек входа (main, экспортируемые функции и т.д.)
    let entry_points = find_entry_points();
    for entry in entry_points {
        dfs_visit(entry, &graph, &mut reachable);
    }

    // Не посещённые инстанциации — мёртвый код
    for node in &graph.nodes {
        if !reachable.contains(node.key) {
            eliminate(node);
        }
    }
}
````

#### 9.1 Полный пример дженерик-контейнера

```yaoxiang
# ======== 1. Определение дженерик-контейнера ========
# Используется синтаксис (T: Type) -> Type
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,

    # Дженерик-методы (T автоматически попадает в область видимости из внешнего List(T))
    push: (self: List(T), item: T) -> Void,
    pop: (self: List(T)) -> Option(T),
    map: (R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)),
    filter: (self: List(T), predicate: (T) -> Bool) -> List(T),
    fold: (U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U),
}

# ======== 2. Реализация дженерик-методов ========
# Определения функций находятся в пространстве имён List (префикс List. = принадлежность пространству имён)
# Чтобы . вызывающий синтаксис вроде list.push(item) работал, нужно явное связывание: List.push = push[0]
# self — лишь имя параметра по соглашению, компилятор смотрит на тип, а не на имя

List.push: (T: Type) -> ((self: List(T), item: T) -> Void) = {
    if self.length >= self.data.length {
        # Расширение
        new_data = Array(T)(self.data.length * 2)
        for i in 0..self.length {
            new_data[i] = self.data[i]
        }
        self.data = new_data
    }
    self.data[self.length] = item
    self.length = self.length + 1
}

List.pop: (T: Type) -> ((self: List(T)) -> Option(T)) = {
    if self.length > 0 {
        self.length = self.length - 1
        return Option.some(self.data[self.length])
    } else {
        return Option.none()
    }
}

List.map: (T: Type, R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)) = {
    result = List(R)()
    for i in 0..self.length {
        result.push(f(self.data[i]))
    }
    return result
}

List.filter: (T: Type) -> ((self: List(T), predicate: (T) -> Bool) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        if predicate(self.data[i]) {
            result.push(self.data[i])
        }
    }
    return result
}

List.fold: (T: Type, U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U) = {
    result = initial
    for i in 0..self.length {
        result = f(result, self.data[i])
    }
    return result
}

# ======== 3. Использование type constraint ========
# Реализация Clone для List
List.clone: (T: Clone) -> ((self: List(T)) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        result.push(self.data[i].clone())
    }
    return result
}

# ======== 4. Пример использования ========
# Создание дженерик-List
numbers = List(Int)()
numbers.push(1)
numbers.push(2)
numbers.push(3)

# Использование дженерик-методов
doubled = numbers.map((x) => x * 2)
evens = numbers.filter((x) => x % 2 == 0)

# Использование fold для вычисления
sum = numbers.fold(0, (acc, x) => acc + x)  # sum = 6

# Композиция дженериков
sum_of_evens = numbers
    .filter((x) => x % 2 == 0)
    .map((x) => x * 2)
    .fold(0, (acc, x) => acc + x)  # sum_of_evens = 8
```

#### 9.2 Пример дженерик-алгоритма

```yaoxiang
# ======== 1. Дженерик-алгоритм сортировки ========
Comparator: (T: Type) -> Type = {
    compare: (T, T) -> Int,  # -1 if a < b, 0 if a == b, 1 if a > b
}

# Дженерик quicksort
quicksort: (T: Clone) -> ((array: Array(T), cmp: Comparator(T)) -> Array(T)) = {
    if array.length <= 1 {
        return array.clone()
    }

    pivot = array[array.length / 2]
    left = Array(T)()
    right = Array(T)()

    for i in 0..array.length {
        if i == array.length / 2 {
            continue
        }
        item = array[i]
        comparison = cmp.compare(item, pivot)
        if comparison < 0 {
            left.push(item)
        } else {
            right.push(item)
        }
    }

    sorted_left = quicksort(left, cmp)
    sorted_right = quicksort(right, cmp)

    result = sorted_left.clone()
    result.push(pivot)
    result.extend(sorted_right)
    return result
}

# ======== 2. Реализация IntComparator ========
# Реализация через перегрузку функций
compare: (a: Int, b: Int) -> Int = {
    if a < b {
        return -1
    } else if a > b {
        return 1
    } else {
        return 0
    }
}

# ======== 3. Примеры использования ========
# Сортировка массива Int
numbers = Array(Int)(3, 1, 4, 1, 5, 9, 2, 6)
sorted = quicksort(numbers, Comparator(Int)())

# Сортировка массива String (требуется StringComparator)
strings = Array(String)("hello", "world", "foo", "bar")
sorted_strings = quicksort(strings, Comparator(String)())
```

# ======== 1. Тип матрицы compile-time ========
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),

    # Проверка размерностей compile-time: используется Assert из стандартной библиотеки
    _assert: Assert(Rows > 0),  # Rows > 0, иначе ошибка компиляции
    _assert: Assert(Cols > 0),  # Cols > 0, иначе ошибка компиляции

    # Операции над матрицами
    multiply: (M: Int) -> ((self: Matrix(T, Rows, Cols), other: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)) = {
        result = Matrix(T, Rows, M)()
        for i in 0..Rows {
            for j in 0..M {
                sum = Zero::zero()
                for k in 0..Cols {
                    sum = sum + self.data[i][k] * other.data[k][j]
                }
                result.data[i][j] = sum
            }
        }
        return result
    }
}

# ======== 2. Создание матрицы compile-time ========
identity: (T: Add + Multiply + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    for i in 0..N {
        for j in 0..N {
            if i == j {
                matrix.data[i][j] = One::one()
            } else {
                matrix.data[i][j] = Zero::zero()
            }
        }
    }
    return matrix
}

## Компромиссы

### Преимущества

1. **Абстракции с нулевой стоимостью**
   - Мономорфизация compile-time, без накладных расходов в runtime
   - Без виртуальных функций, без RTTI

2. **Устранение мёртвого кода**
   - Анализ compile-time, инстанциация только используемых дженериков
   - Раздувание кода контролируемо

3. **Замена макросов**
   - Типобезопасная кодогенерация
   - Удобно для IDE, понятные сообщения об ошибках

4. **Вычисления compile-time**
   - Дженерики compile-time поддерживают вычисления compile-time
   - Возможности вроде проверки размерностей
   - Без ключевого слова `const`, чистые ограничения типов

### Недостатки

1. **Время компиляции**
   - Инстанциация дженериков увеличивает время компиляции
   - Решение ограничений может быть медленным

2. **Потребление памяти**
   - Увеличение потребления памяти компилятором
   - Механизмы кэширования требуют памяти

3. **Сложность реализации**
   - Сложный решатель ограничений
   - Сложный движок вычислений на уровне типов

4. **Диагностика ошибок**
   - Ошибки дженериков могут быть сложными
   - Требуются понятные подсказки об ошибках

### Меры по смягчению

1. **Стратегия кэширования**
   - Кэширование результатов инстанциации
   - LRU-кэш для ограничения памяти

2. **Инкрементальная компиляция**
   - Кэширование результатов компиляции
   - Инкрементальная инстанциация

3. **Сообщения об ошибках**
   - Понятные сообщения об ошибках
   - Подсказки по выводу параметров дженериков

4. **Параллельная компиляция**
   - Параллельная инстанциация дженериков
   - Многопоточное решение ограничений

## Альтернативы

| Альтернатива                    | Почему не выбрана                                   |

### Синтаксис BNF

```bnf
# Параметры дженериков используют унифицированный синтаксис () как часть типа функции
# Например: map: (T: Type, R: Type) -> ((list: List(T), f: (T) -> R) -> List(R))

# Type constraint (в параметрах дженерика)
type_bound ::= identifier
             | identifier '+' identifier ('+' identifier)*

# Объявление параметра (тип + имя)
parameter ::= identifier ':' type

parameters ::= parameter (',' parameter)*

# Объявление функции: name: type = expression
# Параметры дженерика — первая группа параметров типа функции: (T: Type) -> ((params) -> return)
function ::= identifier ':' type '=' (expression | block)

# Объявление метода: Type.method: type = expression
method ::= identifier '.' identifier ':' type '=' (expression | block)

# Определение типа (унифицированный синтаксис Binding)
# Дженерик-тип вроде List: (T: Type) -> Type = { ... }
generic_type ::= identifier ':' type '=' type_expression

# Type в параметрах дженерика автоматически заполняется компилятором из типов фактических аргументов
# Например, map(numbers, f): T извлекается из numbers: List(Int), R — из f: (Int) -> String
```
