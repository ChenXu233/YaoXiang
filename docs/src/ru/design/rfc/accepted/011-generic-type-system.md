# RFC-011: Проектирование системы обобщений — абстракции с нулевой стоимостью и замена макросов

## Резюме

Настоящий документ определяет **проектирование системы обобщений** языка YaoXiang, обеспечивающее
абстракции с нулевой стоимостью за счёт мощного механизма обобщений, снижение зависимости от
макросов благодаря оптимизациям времени компиляции, а также механизм удаления мёртвого кода.

**Основные положения проектирования**:

- **Унифицированный синтаксис сигнатур**: `(T: Type, R: Type) -> ...` — параметры обобщений и
  обычные параметры записаны единообразно
- **Механизм самоописания Type**: `Type` — особая сущность уровня языка; позиции `Type` в сигнатуре
  заполняются автоматически посредством вывода
- **Ограничения типов**: `T: Dup + Add` — множественные ограничения, ограничения на типы функций
- **Ассоциированные типы**:
  `Iterator: (Item: Type) -> Type = { next: () -> Option(Item), has_next: () -> Bool }`
- **Обобщения времени компиляции**: `N: Int` — параметры-значения обобщений, инстанцирование
  константами времени компиляции
- **Условные типы**: `If: (C: Bool, T: Type, E: Type) -> Type` — вычисления на уровне типов,
  семейства типов

**Ценность**:

- Абстракции с нулевой стоимостью: мономорфизация на этапе компиляции, без накладных расходов во
  время выполнения
- Удаление мёртвого кода: анализ графа инстанцирования + оптимизации LLVM
- Замена макросов: обобщения покрывают 90% сценариев использования макросов
- Безопасность типов: проверка на этапе компиляции, дружелюбность к IDE
- **Явное лучше неявного**: самоописание `Type`, автоматический вывод компилятора

## Идея вселенной типов и типы, зависящие от значений

Система обобщений YaoXiang построена на **идее вселенной типов** — ментальной модели, которая
унифицирует все концепции языка в виде иерархической структуры; ключевая инновация состоит в
возведении **типов, зависящих от значений**, в полноправные сущности уровня Type2.

### Что такое тип, зависящий от значений?

**Тип, зависящий от значений** — это тип, зависящий от одного или нескольких **значений** (а не
только от других типов). Эти значения могут быть вычислены на этапе компиляции, обеспечивая тем
самым гарантии безопасности типов ещё на стадии компиляции.

```yaoxiang
# Традиционные обобщения: параметр-тип
List: (T: Type) -> Type

# Тип, зависящий от значения: параметр-значение
Vec: (n: Int) -> Type  # Тип вектора зависит от значения длины n
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type  # Тип матрицы зависит от числа строк и столбцов
```

### Ключевые преимущества типов, зависящих от значений

По сравнению с традиционными обобщениями, типы, зависящие от значений в YaoXiang, обладают
следующими ключевыми преимуществами:

| Свойство                         | Традиционные обобщения (C++/Rust)               | Типы, зависящие от значений, в YaoXiang                                |
| -------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| Значения, от которых зависит тип | Только параметры-типы                           | Любые значения, включая результаты вызовов функций                     |
| Вычисление на этапе компиляции   | Ручная специализация шаблонов в C++, нет в Rust | Автоматическое вычисление на этапе компиляции с гарантией завершимости |
| Вычисления на уровне типов       | Метапрограммирование шаблонов (сложно/опасно)   | Единый движок вычислений на уровне типов                               |
| Безопасность типов               | Нет в C++, ограниченная в Rust                  | Полная безопасность типов, проверка на этапе компиляции                |
| Проверка размерностей            | Проверка в runtime или ручная специализация     | Проверка размерностей на этапе компиляции, без накладных расходов      |

### Иерархия вселенной типов и типы, зависящие от значений

Идея вселенной типов разделяет концепции языка по семантической роли на разные уровни; типы,
зависящие от значений, расположены на **уровне Type2**:

| Уровень   | Роль                                                       | Примеры                                                                                              |
| --------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Type-1    | Значения                                                   | `42`, `factorial(5)`, сама функция                                                                   |
| Type0     | Метатип-ключевое слово                                     | `Type`                                                                                               |
| Type1     | Конкретные типы                                            | `Int`, `String`, `Vec(3)`                                                                            |
| **Type2** | **Функции/конструкторы типов/типы, зависящие от значений** | `add: (Int, Int) -> Int`, `Vec: (n: Int) -> Type`, `Matrix: (T: Type, Rows: Int, Cols: Int) -> Type` |

**Ключевое проектное решение**: функции, конструкторы типов и типы, зависящие от значений, на уровне
Type2 имеют **единый синтаксис** — форму `(params) -> result`:

- Обычная функция: `(Int, Int) -> Int` → результатом является значение
- Конструктор типа: `(T: Type) -> Type` → результатом является тип
- Тип, зависящий от значений: `(n: Int) -> Type` → результатом является тип, зависящий от
  параметра-значения

> **Изоморфизм Карри-Ховарда**: это единство — не случайность. Изоморфизм Карри-Ховарда утверждает
> «типы суть утверждения, программы суть доказательства» — функциональный тип `A → B` соответствует
> логической импликации «если A, то B», обобщение `(T: Type) -> Type` соответствует квантору
> всеобщности «для всех типов T», тип, зависящий от значений, `(n: Int) -> Type` соответствует «для
> каждого целого n существует тип». YaoXiang объединяет функции, конструкторы типов и типы,
> зависящие от значений, на уровне Type2, по сути объединяя «доказательство» и «вычисление» в единое
> понятие — **конструктивное доказательство**. Это прямое воплощение изоморфизма Карри-Ховарда в
> проектировании языка: единая форма `(params) -> result` одновременно несёт логическое утверждение
> и вычислительный процесс.

### Гарантия детерминированности на этапе компиляции

Идея вселенной типов в YaoXiang требует: **всё на уровне Type определено на этапе компиляции**.

```yaoxiang
# Пример проверки размерности на этапе компиляции
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
    # Проверка на этапе компиляции: размерности должны быть положительными
    _assert: Assert(Rows > 0),
    _assert: Assert(Cols > 0),
}

# Создание единичной матрицы 3x3 — выполняется на этапе компиляции
identity: (T: Add + Zero + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    # ...
}

# Вычисление на этапе компиляции: factorial(3) = 6, размер вектора известен на этапе компиляции
vec: Vec(factorial(3)) = Vec(6)()
```

Компилятор автоматически:

1. Обнаруживает вызовы функций в позиции типа
2. Выполняет проверку завершимости для функции (см. механизм проверки завершимости ниже)
3. Производит вычисление на этапе компиляции
4. Встраивает результат в порождаемый тип

### Сценарии применения типов, зависящих от значений

#### Проверка размерностей на этапе компиляции

```yaoxiang
# Умножение матриц: проверка соответствия размерностей на этапе компиляции
multiply: (T: Add + Multiply + Zero,
           Rows: Int, Cols: Int, M: Int) -> ((
    a: Matrix(T, Rows, Cols),
    b: Matrix(T, Cols, M)
) -> Matrix(T, Rows, M)) = {
    # Проверка на этапе компиляции: a.Cols == b.Rows, иначе ошибка компиляции
    result = Matrix(T, Rows, M)()
    # ...
}

# Ошибка перехватывается на этапе компиляции:
# multiply(matrix_2x3, matrix_4x2)  # Ошибка компиляции: 2 != 4
```

#### Типобезопасный размер массива

```yaoxiang
# Размер массива — константа времени компиляции
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    length: N,
}

# N — константа времени компиляции, может использоваться в вычислениях на уровне типов
first_three: Array(Int, 3) = Array(Int, 3)(1, 2, 3)
# first_three.length == 3 (известно на этапе компиляции)
```

#### Условные типы

```yaoxiang
# If на уровне типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Семейства типов
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,
}
```

#### Обобщённые функции

```yaoxiang
# map: обобщённая функция, параметры типов T, R определяются на этапе компиляции
map: (T: Type, R: Type) -> (
    (list: List(T), f: (x: T) -> R) -> List(R)
) = (list, f) => {
    result = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Использование полностью прозрачно, типы выводятся автоматически
numbers = List(Int)()   # Примечание: двухслойная форма значения-конструктора (см. §9.1); элементы добавляются через push
numbers.push(1)
numbers.push(2)
numbers.push(3)
doubled = map(numbers, (x) => x * 2)  # Выводится как map[Int, Int]
```

### Механизм проверки завершимости (в соответствии с RFC-027)

Вычисление на этапе компиляции для типов, зависящих от значений, должно быть **гарантированно
завершимым**, иначе система типов уйдёт в бесконечный цикл. Проверка завершимости выполняется
**полностью автоматически** конвейером доказательств времени компиляции из RFC-027 — компилятор
автоматически синтезирует меры; доказуемые рекурсии/циклы проходят, недоказуемые — сразу дают ошибку
компиляции. **Полуавтоматическим аннотациям — билет в один конец не оставлен**: `//! decreases` и
`/*! invariant !*/` из RFC-022 упразднены вместе с RFC-022; спецификации — это сами аннотации типов.

#### Проверка завершимости рекурсивных функций

Перед вычислением на этапе компиляции компилятор проверяет, что аргументы рекурсивного вызова строго
убывают на каждой рекурсивной ветви (RFC-027 §6.7). Какие-либо аннотации спецификации не требуются:

```yaoxiang
# Факториал на этапе компиляции: без //! requires/ensures/decreases, компилятор анализирует автоматически
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Анализ компилятора: n-1 < n → убывает → завершимость доказана
}

# Использование: вызов в позиции типа — компилятор сначала проверяет завершимость, затем вычисляет
vec: Vec(factorial(5)) = Vec(120)()  # Вычисление на этапе компиляции factorial(5) = 120
```

| Сценарий                                               | Поведение                          |
| ------------------------------------------------------ | ---------------------------------- |
| Компилятор может установить убывание (например, `n-1`) | Вычисление на этапе компиляции     |
| Не убывает / убывание неразрешимо                      | Ошибка компиляции                  |
| Вызов в runtime (не в позиции типа)                    | Проверка завершимости не требуется |

#### Проверка завершимости циклов

Для циклов не нужны аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточнения на
переменных (например, `UpTo(n)`) одновременно задают инвариант цикла и границу меры; компилятор
перебирает четыре стратегии синтеза меры в порядке приоритета и останавливается на первой успешной
(RFC-027 §7):

1. **Автоматический синтез линейной ранговой функции** — извлечение границ переменных из аннотаций
   типов, перебор линейных комбинаций, SMT-верификация m ≥ 0 и m' < m на всех путях
2. **Подсчёт нарушений предиката** (экспериментально) — извлечение violation_count из определения
   целевого типа (например, `Sorted`), покрытие соседних обменов/перемещений
3. **Паттерны ограниченного инкремента/декремента** — `v += const` → мера `upper - v` (вырождение
   стратегии 1, самый быстрый путь)
4. **Шаблон меры с мультипликативным масштабированием** — `v *= const` (const > 1) → мера
   `ceil(log_const(upper / v))`

```yaoxiang
sum: (arr: Array(Int, n)) -> Int = {
    mut i: UpTo(arr.len) = 0   # Аннотация типа даёт верхнюю границу arr.len и нижнюю 0
    while i < arr.len {
        # Компилятор автоматически выводит: мера arr.len - i, на каждой итерации строго убывает на 1 → завершимость доказана
        s += arr[i]; i += 1
    }
    return s
}
```

```
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  1. Проверка завершимости (конвейер доказательств RFC-027, полностью автоматический) │

│     - Циклы: четыре стратегии синтеза мер (линейная ранговая/подсчёт нарушений/ │

└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  2. Вычисление на этапе компиляции (выполняется встроенным интерпретатором) │
│     - Чистые функции: прямое вычисление                     │
│     - Побочные эффекты: ошибка компиляции (в позиции типа побочных эффектов быть не должно) │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  3. Встраивание результата в тип                            │
│     - Vec(factorial(5)) → Vec(120)                          │
│     - Matrix(Float, 3, 3) → конкретный тип                  │
└─────────────────────────────────────────────────────────────┘
```

#### Преимущества

- **Безопасность**: гарантируется, что вычисление на этапе компиляции обязательно завершится, и
  система типов не уйдёт в бесконечный цикл
- **Единообразие**: проверка завершимости и верификация корректности (генерация VC) разделяют единый
  конвейер доказательств времени компиляции (RFC-027), без отдельного синтаксиса спецификаций
- **Полная автоматизация**: компилятор автоматически синтезирует меры из аннотаций типов; доказуемое
  — проходит, недоказуемое — сразу ошибка, без опоры на рукописные `decreases` от программиста

## Мотивация

### Зачем нужна мощная система обобщений?

Существующие системы обобщений в主流 языках имеют ограничения:

| Язык         | Возможности обобщений           | Проблема                                                                                             |
| ------------ | ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Java         | Граничные типы                  | Мономорфизация на этапе компиляции, без специализации обобщений                                      |
| C#           | Ограничения обобщений           | Проверка типов в runtime, накладные расходы на производительность                                    |
| Rust         | Обобщения + Trait               | Сложная система Trait, крутая кривая обучения                                                        |
| C++          | Шаблоны                         | Сложная специализация шаблонов, плохие сообщения об ошибках компиляции                               |
| **YaoXiang** | **Типы, зависящие от значений** | **Тип может зависеть от значения, проверка размерностей на этапе компиляции, гарантия завершимости** |

### Ключевые противоречия

1. **Производительность vs гибкость**: гибкость в runtime vs оптимизации на этапе компиляции
2. **Сложность vs простота**: мощная система типов vs удобство использования
3. **Макросы vs обобщения**: кодогенерация макросами vs типобезопасность обобщений
4. **Зависимость от значений vs безопасность типов**: традиционные обобщения не могут проверять
   размерности на этапе компиляции

### Ключевые преимущества типов, зависящих от значений

**Типы, зависящие от значений** в YaoXiang — это ключевое преимущество по сравнению с традиционными
обобщениями:

| Преимущество                       | Описание                                                                                                                                     |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Тип зависит от значения**        | `Vec: (n: Int) -> Type` позволяет типу зависеть от конкретного значения                                                                      |
| **Вычисление на этапе компиляции** | Вызовы функций в позиции типа вычисляются на этапе компиляции, результат напрямую встраивается в тип                                         |
| **Проверка размерностей**          | `Matrix(Float, 3, 3)` проверяет размерности матрицы на этапе компиляции                                                                      |
| **Вычисления на уровне типов**     | Условные типы `If`, `Match` поддерживают вычисления на уровне типов                                                                          |
| **Гарантия завершимости**          | Проверка завершимости на этапе компиляции (автоматический синтез мер) гарантирует, что вычисление на этапе компиляции обязательно завершится |

```yaoxiang
# Проверка на этапе компиляции, невозможная в C++/Rust
matrix: Matrix(Float, factorial(3), factorial(2)) = ...
# Вычисление на этапе компиляции: factorial(3) = 6, factorial(2) = 2
# Тип: Matrix(Float, 6, 2)

# Несоответствие размерностей перехватывается на этапе компиляции
identity: Matrix(Float, 3, 3) = ...
# multiply(matrix_2x3, identity_3x3)  # Ошибка компиляции: 2 != 3
```

### Ценность системы обобщений

```yaoxiang
# Пример: унифицированный дизайн API
# Операция map для разных типов контейнеров

# Традиционный подход: отдельная реализация для каждого типа
map_int_array: (array: Array(Int), f: Fn(Int) -> Int) -> Array(Int) = ...
map_string_array: (array: Array(String), f: Fn(String) -> String) -> Array(String) = ...
map_int_list: (list: List(Int), f: Fn(Int) -> Int) -> List(Int) = ...
map_string_list: (list: List(String), f: Fn(String) -> String) -> List(String) = ...

# Подход с обобщениями: одна обобщённая функция покрывает все типы
map: (T: Type, R: Type)(container: Container(T), f: Fn(T) -> R) -> Container(R) = {
    for item in container {
        result.push(f(item))
    }
    result
}
```

## Цели проектирования

### Основные цели

1. **Абстракции с нулевой стоимостью** — вызов обобщений эквивалентен вызову конкретного типа
2. **Удаление мёртвого кода** — анализ на этапе компиляции, инстанцируются только используемые
   обобщения
3. **Замена макросов** — обобщения заменяют 90% сценариев использования макросов
4. **Безопасность типов** — проверка на этапе компиляции, без накладных расходов на проверку типов в
   runtime
5. **Дружелюбность к IDE** — интеллектуальные подсказки, понятные сообщения об ошибках
6. **Типы, зависящие от значений** — тип может зависеть от значений, поддержка проверки размерностей
   на этапе компиляции
7. **Безопасность вычислений на этапе компиляции** — гарантируется проверкой завершимости
   (автоматический синтез мер по RFC-027)

### Принципы проектирования

- **Определённость на этапе компиляции**: параметры обобщений определяются на этапе компиляции
- **Приоритет мономорфизации**: генерация конкретного кода, без вызовов через виртуальные функции
- **Управление через ограничения**: ограничения типов направляют инстанцирование
- **Платформенные оптимизации**: специализация для поддержки платформенно-специфичных оптимизаций
- **Единая вселенная типов**: функции/конструкторы типов/типы, зависящие от значений, объединены на
  уровне Type2
- **Гарантия завершимости**: вызовы функций в позиции типа должны иметь доказанную завершимость

## Предложение

### 1. Базовые обобщения

#### 1.1 Параметры обобщённых типов

> **Ключевое правило**: определение обобщённого типа **должно явно аннотироваться `: Type`**, иначе
> HM выведет его как функцию.
>
> | Запись                            | Значение                              |
> | --------------------------------- | ------------------------------------- |
> | `List: (T: Type) -> Type = {...}` | ✅ Конструктор типа                   |
> | `List = {...}`                    | ❌ HM выводит как функцию, не как тип |

```yaoxiang
# Определение обобщённого типа (обязательно : Type)
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self
}

List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (self: List(T), item: T) -> Void,   # self — лишь имя по соглашению, не ключевое слово
    get: (self: List(T), index: Int) -> Option(T),
}

# Обобщённая функция (без : Type, HM выводит как функцию)
map: (T: Type, R: Type) -> ((opt: Option(T), f: Fn(T) -> R) -> Option(R)) = {
    return match opt {
        some => Option.some(f(some)),
        none => Option.none(),
    }
}

# Ограничение обобщения (прямое выражение, в одной строке return можно опустить)
clone: (T: Clone)(value: T) -> T = value.clone()

# Несколько параметров-типов
combine: (T: Type, U: Type) -> ((a: T, b: U) -> (T, U)) = (a, b)
```

#### 2.4 Встроенные маркерные trait: Dup и Clone

**Три вида семантики копирования**:

| Вид                                  | Значение                                                                                | Способ срабатывания                     | Сценарий применения                |
| ------------------------------------ | --------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------- |
| **Копирование примитивных значений** | При присваивании автоматическое копирование значения, два значения полностью независимы | Автоматически при присваивании/передаче | Int, Float, Bool, Char             |
| **Dup**                              | Поверхностное копирование: копируется дескриптор/токен, нижележащие данные разделяются  | Автоматически при присваивании/передаче | токены `&T`, `ref T`, String/Bytes |
| **Clone**                            | Глубокое копирование: создаётся полная независимая копия                                | `value.clone()`                         | Любой тип, реализующий Clone       |

**Семантика Dup**: для типа, реализующего Dup, при присваивании/передаче владение не передаётся —
компилятор копирует дескриптор/токен, и несколько владельцев указывают на одни и те же нижележащие
данные. Это дополняет семантику Move по умолчанию из модели владения RFC-009.

**Dup и Clone — ортогональные понятия**:

```
Dup  = копируется дескриптор, данные разделяются (изменения влияют друг на друга)
Clone = копируются данные, копии независимы (изменения не влияют друг на друга)
```

**Правила**:

```
1. Примитивные типы значений (Int, Float, Bool, Char) — встроенное в компилятор копирование значений, не относятся к Dup
2. Dup — применимо только к ссылочным/токенным типам и типам с внутренним подсчётом ссылок
3. Clone — явное глубокое копирование, может реализовать любой тип
4. По умолчанию Move — остальные типы сохраняют семантику Move по умолчанию
```

**Какие типы являются Dup**:

| Тип                                        | Dup         | Причина                                                                           |
| ------------------------------------------ | ----------- | --------------------------------------------------------------------------------- |
| `&T` (токен заимствования)                 | ✅          | Токен нулевого размера, копирование токена = несколько представлений одних данных |
| `ref T`                                    | ✅          | Копирование Rc/Arc = +1 к счётчику ссылок, разделяемые данные в куче              |
| String, Bytes                              | ✅          | Внутренний подсчёт ссылок, копирование дескриптора разделяет буфер                |
| `&mut T` (токен изменяемого заимствования) | ❌          | Линейная исключительность, копировать нельзя                                      |
| struct                                     | Производное | Все поля Dup → struct Dup                                                         |
| enum                                       | Производное | Все поля всех вариантов Dup → enum Dup                                            |
| tuple                                      | Производное | Все элементы Dup → tuple Dup                                                      |
| Fn (замыкание)                             | ❌          | Захватываемая среда может быть не Dup                                             |
| `*T` (сырой указатель)                     | ❌          | unsafe, не участвует в системе владения                                           |

**Int/Float/Bool/Char — не Dup** — они являются типами значений; при присваивании компилятор
автоматически копирует значение (два значения полностью независимы). Это не «поверхностное
копирование», а встроенная в компилятор обработка примитивов, которая не нуждается (и не должна)
выражаться через атрибут типа Dup.

```yaoxiang
# Примитивные типы значений: компилятор автоматически копирует значение (это не Dup)
x: Int = 42
y = x          # Копирование значения, x и y полностью независимы
print(x)       # ✅

# Dup: поверхностное копирование, дескриптор разделяет данные
view: &Point = &point
view2 = view    # ✅ Dup: копирование токена, оба указывают на один и тот же point
print(view.x)   # ✅

# Clone: явное глубокое копирование, создаётся независимая копия
backup = big_struct.clone()  # Явный вызов

# Ограничения обобщений
dup_use: (T: Dup) -> T = x         # T: Dup → можно поверхностно копировать
clone_use: (T: Clone) -> T = x.clone()  # T: Clone → можно глубоко копировать
```

> **Примечание**: `Send`/`Sync` не являются видимыми пользователю trait. Безопасность передачи между
> задачами обеспечивается ключевым словом `ref` и полностью автоматической обработкой компилятором —
> `ref` автоматически выбирает Rc или Arc, от пользователя не требуется понимание Send/Sync.

#### 3.1 Определение ассоциированного типа

```yaoxiang
# Trait Iterator (используется синтаксис (Item: Type) -> Type)
Iterator: (Item: Type) -> Type = {
    next: (Self) -> Option(Item),
    has_next: (Self) -> Bool,
    collect: (T: Type)(Self) -> List(T),
}

# Использование
collect_all: (T: Type, I: Iterator(T))(iter: I) -> List(T) = {
    result: List(T) = List(T)
    while iter.has_next() {
        if let Some(item) = iter.next() {
            result.push(item)
        }
    }
    return result
}

# Реализация Iterator для Array
# Используется синтаксический сахар методов: Array.Item, Array.next, Array.has_next
Array.has_next: (T: Type)(self: Array(T)) -> Bool = {
    return self.index < self.length
}

Array.next: (T: Type)(self: Array(T)) -> Option(T) = {
    if has_next(self) {
        item = self.data[self.index]
        self.index = self.index + 1
        return Option.some(item)
    } else {
        return Option.none()
    }
}

Array.Item: (T: Type)(arr: Array(T)) -> T = {
    return arr.data[0]
}
```

### 4. Обобщения времени компиляции

#### 4.1 Параметры-значения времени компиляции

> **Поправка (#296)**: в исходном тексте было написано «`Int` и другие параметры-значения в
> контексте обобщений по умолчанию определимы на этапе компиляции» — это утверждение **строго
> неверно**: в `add: (a: Int, b: Int) -> Int = a + b` `a`/`b` — параметры-значения времени
> выполнения. Только **конкретные параметры, на которые ссылаются в позиции типа**, являются
> параметрами-значениями времени компиляции. Корректное определение см. ниже.

**Ключевое проектное решение**: параметр-тип в сигнатуре обобщения помечается как `Type`; параметры,
аннотированные конкретными типами (`Int`/`Bool`/`Float` и т.д.), рассматриваются как **кандидаты в
параметры-значения времени компиляции**; становится ли параметр таковым, зависит от того,
**ссылаются ли на его значение в позиции типа** (зависимость от значения). Ключевое слово `const` не
требуется.

**Правило определения (в два шага)**:

1. **Грубая фильтрация по форме**: параметр, аннотированный не `Type`, а конкретным типом (например,
   `Int`) → в список кандидатов.
2. **Тонкая фильтрация по использованию**: имя кандидата встречается **в позиции типа** (тип поля
   тела типа, тип параметра вложенной `Fn`, предикат `Assert`, позиции аргументов конструктора типа
   вроде `Array(T, N)`) → признаётся параметром-значением времени компиляции; иначе считается
   **параметром-значением времени выполнения**.

| Запись                                                     | Определение                                 | Причина                                                                       |
| ---------------------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------- |
| `add: (a: Int, b: Int) -> Int = a + b`                     | a/b — параметры-значения времени выполнения | Появляются только в позиции значения, не участвуют в конструировании типа     |
| `Array: (T: Type, N: Int) -> Type = { data: Array(T, N) }` | N — параметр-значение времени компиляции    | N появляется в позиции аргумента конструктора типа `Array(T, N)`              |
| `factorial: (N: Int) -> (k: N) -> Int`                     | N — параметр-значение времени компиляции    | N выступает типом вложенного параметра `k`                                    |
| `Foo: (T: Type, N: Int) -> Type = { x: T }`                | N «проваливается» (см. ниже)                | N не упомянут в теле типа, вырождается в параметр-значение времени выполнения |

> **Суть зависимости от значения**: параметр-значение времени компиляции — это и есть тип, зависящий
> от значения. Только когда значение используется для **конструирования типа**, требуется его
> определённость на этапе компиляции. Форма (`: Int`) задаёт лишь право на кандидатство;
> использование (появление в позиции типа) определяет, является ли он параметром-значением времени
> компиляции. Это тот же критерий, что и в §«Гарантия детерминированности на этапе компиляции» о
> том, что «вызовы функций в позиции типа вычисляются на этапе компиляции».

```yaoxiang
# ════════════════════════════════════════════════════════
# Параметр-значение времени компиляции: N упоминается в позиции типа (слот длины Array)
# ════════════════════════════════════════════════════════
StaticArray: (T: Type, N: Int) -> Type = {
    data: Array(T, N),  # N появляется в позиции аргумента конструктора типа → параметр-значение времени компиляции
    length: N,
}

# Использование: factorial(5) вычисляется в позиции типа (этап компиляции), результат 120 встраивается в тип
arr: StaticArray(Int, factorial(5))  # StaticArray(Int, 120)

# ════════════════════════════════════════════════════════
# Зависимость от значения: N выступает типом вложенного параметра k
# ════════════════════════════════════════════════════════
# N — параметр-значение времени компиляции (появляется в позиции типа (k: N));
# k — параметр-значение времени выполнения, тип которого — литеральный тип N (однозначный тип).
factorial: (N: Int) -> (k: N) -> Int = {
    return match k {
        0 => 1,
        _ => k * factorial(k - 1)
    }
}
```

> **Обработка «провалившихся» кандидатов**: кандидат, аннотированный конкретным типом, но не
> упомянутый в позиции типа (например, `N` в `Foo` выше), вырождается в параметр-значение времени
> выполнения (на уровне функции). Провалившийся кандидат на пути конструктора типа не может занять
> слот времени выполнения (конструктор типа вычисляется на этапе компиляции), и на стороне
> объявления сразу выдаётся ошибка [E1094]: «N объявлен как параметр-значение времени компиляции, но
> не упомянут в теле типа» — ранее такое молча отбрасывалось, что приводило к несоответствию арности
> инстанцирования, см. issue [#297](https://github.com/ChenXu233/YaoXiang/issues/297).

### Never и Void: ⊥ и ⊤ в системе типов

Система типов YaoXiang в рамках изоморфизма Карри-Ховарда одновременно обладает ⊥ (ложь/пустой тип)
и ⊤ (истина/Unit), которые представлены встроенными именами типов `Never` и `Void`:

**Never (⊥)** — три безусловных внутренних свойства:

1. **Нулевой конструктор**: ни один литерал или выражение не может породить значение типа `Never`.
   Это метасвойство, которое должно быть встроено.
2. **Принцип взрыва**: `Never <: T` для любого типа `T`. Значение `Never` может использоваться как
   значение любого типа — именно поэтому код после `assert(false)` проходит проверку типов (хотя он
   никогда не будет выполнен).
3. **Маркер расходимости**: `f: (...) -> Never` означает, что `f` гарантированно не возвращается.
   Компилятор использует это для анализа мёртвого кода.

`Never` — это встроенное имя типа, а не ключевое слово; парсер не делает для него особого случая.
Синтаксис для пустого и литерала типа не предоставляется.

**Void (⊤, т.е. Unit)** — ровно один обитатель (значение void по умолчанию), носитель истинного
утверждения «всегда истинно». `Void` — единичный элемент для типов-пустых произведений, `Never` —
единичный элемент для типов-пустых сумм — они двойственны друг другу. `x: Void = <по умолчанию>`
допустимо, `x: Never = ...` — справа писать нечего.

#### 4.3 Проверка на этапе компиляции (реализация стандартной библиотеки)

```yaoxiang
# ════════════════════════════════════════════════════════
# Реализация стандартной библиотеки: с использованием условных типов
# ════════════════════════════════════════════════════════

# Определения стандартной библиотеки
# IsTrue: мост из вселенной значений во вселенную типов — истинность Bool отображается в тип
IsTrue: (b: Bool) -> Type = match b {
    true => Void,      # ⊤, имеет значение, программа продолжается
    false => Never,    # ⊥, нет значения, расходимость
}

# Assert: примитив уточнения типа на этапе компиляции — типовое выражение утверждения о Bool
Assert: (cond: Bool) -> Type = IsTrue(cond)
#
# cond == true  → Assert(true)  = Void    (всегда истинно, стирается)
# cond == false → Assert(false) = Never   (всегда ложно, ошибка компиляции / расходимость)
# cond неразрешимо → конвейер доказательств решает по режиму dispatch:
#                    CompileTime → Unknown, требуется prove
#                    Runtime     → вставка check, инъекция предположения в Γ

# Способ использования 1: ограничение в определении типа
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    # Проверка на этапе компиляции: N должно быть больше 0 (Assert в позиции типа)
    length: Assert(N > 0),
}

# Способ использования 2: использование в выражении
IntArray: (N: Int) -> Type = StaticArray(Int, N)
# Проверка: размер IntArray(10) равен sizeof(Int) * 10
Assert(size_of(IntArray(10)) == sizeof(Int) * 10)
```

### 5. Условные типы

> **Изоморфизм Карри-Ховарда**: условные типы с точки зрения Карри-Ховарда представляют собой
> **case-анализ** в логике. Тип `Bool` соответствует утверждению с двумя возможными исходами
> (True/False); `If` выбирает тот или иной результат в зависимости от истинности утверждения — это и
> есть логический case-анализ дизъюнкции. Выражение `match C { True => T, False => E }` фактически
> выражает: «если известно, что утверждение C истинно, заключение — T; если ложно — заключение — E».

#### 5.1 Условный тип If

```yaoxiang
# If на уровне типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Пример: ветвление на этапе компиляции
NonEmpty: (T: Type) -> Type = If(T != Void, T, Never)

Optional: (T: Type) -> Type = If(T != Void, T, Void)

# Проверка на этапе компиляции (сведено к определению Assert из §4.3)
# Assert: (cond: Bool) -> Type = IsTrue(cond)

# Использование
# Вычисление типа: If(True, Int, String) => Int
# Вычисление типа: If(False, Int, String) => String
```

#### 5.2 Семейства типов

> **Изоморфизм Карри-Ховарда**: семейства типов — самое прямое воплощение принципа «утверждения суть
> типы». `Add: (A: Type, B: Type) -> Type` — это не «функция сложения, написанная на уровне типов»,
> а **конструирование утверждения о сложении натуральных чисел**. `(Zero, B) => B` означает
> «утверждение Add(Zero, B) эквивалентно B»; `(Succ(A'), B) => Succ(Add(A', B))` означает «если
> Add(A', B) выполняется, то и Add(Succ(A'), B) выполняется». Это и есть само определение сложения
> по аксиомам Пеано. То, что проверка типов подтверждает прохождение этого match-выражения,
> эквивалентно проверке логической непротиворечивости данного определения.

```yaoxiang
# Преобразование типов на этапе компиляции
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,  # По умолчанию
}

# Вычисления на уровне типов
Length: (T: Type) -> Type = match T.length {
    0 => Zero,
    1 => Succ(Zero),
    2 => Succ(Succ(Zero)),
    _ => TooLong,
}

# Сложение на уровне типов (Карри-Ховард: case-анализ + рекурсивный вызов, требует проверки завершимости для полноты индукции)
Add: (A: Type, B: Type) -> Type = match (A, B) {
    (Zero, B) => B,
    (Succ(A'), B) => Succ(Add(A', B)),
}

# Пример: вычисление 2 + 3 на этапе компиляции
Two: Type = Succ(Succ(Zero))
Three: Type = Succ(Succ(Succ(Zero)))
Five: Type = Add[Two, Three]  # Succ(Succ(Succ(Succ(Succ(Zero)))))
```

1. **Интеллектуальный выбор компилятора**

   - Полностью эквивалентно вручную написанному оптимизированному коду

3. **Безопасность типов**
   - Проверка типов на этапе компиляции
   - Нулевые накладные расходы в runtime
   - Не требуется таблица виртуальных функций

4. **Идеально вписывается в RFC-010**

   ```yaoxiang

   # Не нужны новые ключевые слова вроде impl, where
   ```

**Практические примеры применения**:


- ✅ **Повторное использование кода** → одно имя функции, множество реализаций
- ✅ **Абстракции с нулевой стоимостью** → полиморфизм на этапе компиляции, нулевые накладные

````
### 7. Механизм удаления мёртвого кода

#### 7.1 Анализ графа инстанцирования

```rust
// Внутри компилятора: построение графа зависимостей инстанцирования обобщений
struct InstantiationGraph {
    // Узлы: инстанцирования обобщений
    nodes: HashMap<InstanceKey, InstanceNode>,

    // Рёбра: отношения использования
    edges: HashMap<InstanceKey, Vec<InstanceKey>>,
}

struct InstanceKey {
    generic: FunctionId,  // ID обобщённой функции
    type_args: Vec<TypeId>,  // Аргументы-типы
    const_args: Vec<ConstId>,  // Аргументы-константы
}

// Алгоритм: анализ достижимости
fn eliminate_dead_instantiations(graph: &InstantiationGraph) {
    let mut reachable = HashSet::new();

    // Начинаем с точек входа (main, экспортируемые функции и т.д.)
    let entry_points = find_entry_points();
    for entry in entry_points {
        dfs_visit(entry, &graph, &mut reachable);
    }

    // Не посещённые инстанцирования — мёртвый код
    for node in &graph.nodes {
        if !reachable.contains(node.key) {
            eliminate(node);
        }
    }
}
````

### 9. Примеры

#### 9.1 Полный пример обобщённого контейнера

```yaoxiang
# ======== 1. Определение обобщённого контейнера ========
# Используется синтаксис (T: Type) -> Type
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,

    # Обобщённые методы (T автоматически попадает в область видимости из внешнего List(T))
    push: (self: List(T), item: T) -> Void,
    pop: (self: List(T)) -> Option(T),
    map: (R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)),
    filter: (self: List(T), predicate: (T) -> Bool) -> List(T),
    fold: (U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U),
}

# ======== 2. Реализация обобщённых методов ========
# Функции определяются в пространстве имён List (префикс List. = принадлежность пространству имён)
# Чтобы синтаксис вызова через . работал (list.push(item)), требуется явное связывание: List.push = push[0]
# self — лишь имя параметра по соглашению, компилятор смотрит на тип, а не на имя

List.push: (T: Type) -> ((self: List(T), item: T) -> Void) = {
    if self.length >= self.data.length {
        # Расширение
        new_data = Array(T)(self.data.length * 2)
        for i in 0..self.length {
            new_data[i] = self.data[i]
        }
        self.data = new_data
    }
    self.data[self.length] = item
    self.length = self.length + 1
}

List.pop: (T: Type) -> ((self: List(T)) -> Option(T)) = {
    if self.length > 0 {
        self.length = self.length - 1
        return Option.some(self.data[self.length])
    } else {
        return Option.none()
    }
}

List.map: (T: Type, R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)) = {
    result = List(R)()
    for i in 0..self.length {
        result.push(f(self.data[i]))
    }
    return result
}

List.filter: (T: Type) -> ((self: List(T), predicate: (T) -> Bool) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        if predicate(self.data[i]) {
            result.push(self.data[i])
        }
    }
    return result
}

List.fold: (T: Type, U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U) = {
    result = initial
    for i in 0..self.length {
        result = f(result, self.data[i])
    }
    return result
}

# ======== 3. Использование ограничений типов ========
# Реализация Clone для List
List.clone: (T: Clone) -> ((self: List(T)) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        result.push(self.data[i].clone())
    }
    return result
}

# ======== 4. Примеры использования ========
# Создание обобщённого List
numbers = List(Int)()
numbers.push(1)
numbers.push(2)
numbers.push(3)

# Использование обобщённых методов
doubled = numbers.map((x) => x * 2)
evens = numbers.filter((x) => x % 2 == 0)

# Использование fold для вычисления суммы
sum = numbers.fold(0, (acc, x) => acc + x)  # sum = 6

# Композиция обобщений
sum_of_evens = numbers
    .filter((x) => x % 2 == 0)
    .map((x) => x * 2)
    .fold(0, (acc, x) => acc + x)  # sum_of_evens = 8
```

#### 9.2 Пример обобщённого алгоритма

```yaoxiang
# ======== 1. Обобщённый алгоритм сортировки ========
Comparator: (T: Type) -> Type = {
    compare: (T, T) -> Int,  # -1 если a < b, 0 если a == b, 1 если a > b
}

# Обобщённая быстрая сортировка
quicksort: (T: Clone) -> ((array: Array(T), cmp: Comparator(T)) -> Array(T)) = {
    if array.length <= 1 {
        return array.clone()
    }

    pivot = array[array.length / 2]
    left = Array(T)()
    right = Array(T)()

    for i in 0..array.length {
        if i == array.length / 2 {
            continue
        }
        item = array[i]
        comparison = cmp.compare(item, pivot)
        if comparison < 0 {
            left.push(item)
        } else {
            right.push(item)
        }
    }

    sorted_left = quicksort(left, cmp)
    sorted_right = quicksort(right, cmp)

    result = sorted_left.clone()
    result.push(pivot)
    result.extend(sorted_right)
    return result
}

# ======== 2. Реализация IntComparator ========
# Реализуется через перегрузку функций
compare: (a: Int, b: Int) -> Int = {
    if a < b {
        return -1
    } else if a > b {
        return 1
    } else {
        return 0
    }
}

# ======== 3. Примеры использования ========
# Сортировка массива Int
numbers = Array(Int)(3, 1, 4, 1, 5, 9, 2, 6)
sorted = quicksort(numbers, Comparator(Int)())

# Сортировка массива String (требуется StringComparator)
strings = Array(String)("hello", "world", "foo", "bar")
sorted_strings = quicksort(strings, Comparator(String)())
```

```yaoxiang
# ======== 1. Тип Matrix с известными на этапе компиляции размерностями ========
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),

    # Проверка размерностей на этапе компиляции: с использованием типа Assert стандартной библиотеки
    _assert: Assert(Rows > 0),  # Rows > 0, иначе ошибка компиляции
    _assert: Assert(Cols > 0),  # Cols > 0, иначе ошибка компиляции

    # Операции над матрицами
    multiply: (M: Int) -> ((self: Matrix(T, Rows, Cols), other: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)) = {
        result = Matrix(T, Rows, M)()
        for i in 0..Rows {
            for j in 0..M {
                sum = Zero::zero()
                for k in 0..Cols {
                    sum = sum + self.data[i][k] * other.data[k][j]
                }
                result.data[i][j] = sum
            }
        }
        return result
    }
}

# ======== 2. Создание матрицы на этапе компиляции ========
identity: (T: Add + Multiply + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    for i in 0..N {
        for j in 0..N {
            if i == j {
                matrix.data[i][j] = One::one()
            } else {
                matrix.data[i][j] = Zero::zero()
            }
        }
    }
    return matrix
}

# ======== 3. Примеры использования ========
# Создание матрицы с размером, известным на этапе компиляции
# Матрица 2x3
matrix_2x3 = Matrix(Float, 2, 3)()
matrix_2x3.data[0][0] = 1.0

matrix_2x3.data[0][2] = 3.0
matrix_2x3.data[1][0] = 4.0
matrix_2x3.data[1][1] = 5.0
matrix_2x3.data[1][2] = 6.0

# Матрица 3x2
matrix_3x2 = Matrix(Float, 3, 2)()
matrix_3x2.data[0][0] = 7.0
matrix_3x2.data[0][1] = 8.0
matrix_3x2.data[1][0] = 9.0
matrix_3x2.data[1][1] = 10.0
matrix_3x2.data[2][0] = 11.0
matrix_3x2.data[2][1] = 12.0

# Умножение матриц: 2x3 * 3x2 = 2x2
result = matrix_2x3.multiply(matrix_3x2)

# Проверка на этапе компиляции: типом result является Matrix(Float, 2, 2)
# Единичная матрица 2x2
identity_3x3 = identity(Float, 3)()

# Несоответствие размерностей: ошибка компиляции
```

## Компромиссы

### Преимущества

1. **Абстракции с нулевой стоимостью**
   - Мономорфизация на этапе компиляции, без накладных расходов в runtime
   - Не нужны виртуальные функции, RTTI не требуется

2. **Удаление мёртвого кода**
   - Анализ на этапе компиляции, инстанцируются только используемые обобщения
   - Раздувание кода контролируемо

3. **Замена макросов**
   - Типобезопасная кодогенерация
   - Дружелюбность к IDE, понятные сообщения об ошибках

4. **Вычисления на этапе компиляции**
   - Обобщения времени компиляции поддерживают вычисления на этапе компиляции
   - Возможности вроде проверки размерностей
   - Ключевое слово `const` не требуется, только ограничения типов

### Недостатки

1. **Время компиляции**
   - Инстанцирование обобщений увеличивает время компиляции
   - Решение ограничений может быть медленным

2. **Потребление памяти**
   - Возрастает потребление памяти компилятором
   - Механизмам кэширования требуется память

3. **Сложность реализации**
   - Сложный решатель ограничений
   - Сложный движок вычислений на уровне типов

4. **Диагностика ошибок**
   - Ошибки обобщений могут быть сложными
   - Нужны понятные подсказки об ошибках

### Меры по смягчению

1. **Стратегии кэширования**
   - Кэширование результатов инстанцирования
   - LRU-кэш для ограничения памяти

2. **Инкрементальная компиляция**
   - Кэширование результатов компиляции
   - Инкрементальное инстанцирование

3. **Подсказки об ошибках**
   - Понятные сообщения об ошибках
   - Подсказки по выводу параметров обобщений

4. **Параллельная компиляция**
   - Параллельное инстанцирование обобщений
   - Многопоточное решение ограничений

## Альтернативные варианты

| Вариант                        | Почему не выбран                                    |
| ------------------------------ | --------------------------------------------------- |
| Только базовые обобщения       | Не могут заменить сложные макросы                   |
| Чисто макросистема             | Нет безопасности типов, плохие сообщения об ошибках |
| Только ограничения-зависимости | Недостаточная гибкость                              |
| Обобщения в runtime            | Накладные расходы на производительность             |

### Риски

| Риск                          | Влияние                      | Мера по смягчению                     |
| ----------------------------- | ---------------------------- | ------------------------------------- |

| Раздувание кода               | Большой размер бинарника     | DCE + пороговый контроль              |
| Сложность реализации          | Увеличение сроков разработки | Поэтапная реализация                  |
| Диагностика ошибок            | Плохой пользовательский опыт | Подробные сообщения об ошибках        |

## Приложение

### BNF-грамматика

```bnf
# Параметры обобщений используют унифицированный синтаксис () как часть функционального типа
# Например, map: (T: Type, R: Type) -> ((list: List(T), f: (T) -> R) -> List(R))

# Ограничение типа (в параметрах обобщения)
type_bound ::= identifier
             | identifier '+' identifier ('+' identifier)*

# Объявление параметра (тип + имя)
parameter ::= identifier ':' type

parameters ::= parameter (',' parameter)*

# Объявление функции: name: type = expression
# Параметры обобщений — первая группа параметров в функциональном типе: (T: Type) -> ((params) -> return)
function ::= identifier ':' type '=' (expression | block)

# Объявление метода: Type.method: type = expression
method ::= identifier '.' identifier ':' type '=' (expression | block)

# Определение типа (унифицированный синтаксис Binding)
# Обобщённый тип вроде List: (T: Type) -> Type = { ... }
generic_type ::= identifier ':' type '=' type_expression

# Type в параметрах обобщений автоматически заполняется компилятором из типов фактических аргументов
# Например, map(numbers, f), T извлекается из numbers: List(Int), R — из f: (Int) -> String
```
