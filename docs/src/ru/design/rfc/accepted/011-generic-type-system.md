# RFC-011: Система generics - абстракции с нулевой стоимостью и замена макросов

## Резюме

Этот документ определяет **дизайн системы generics** языка YaoXiang, реализующей абстракции с
нулевой стоимостью посредством мощных возможностей generics, использующей оптимизации на этапе
компиляции для снижения зависимости от макросов и предоставляющей механизм устранения мёртвого кода.

**Ключевые принципы дизайна**:

- **Унифицированный синтаксис сигнатур**: `(T: Type, R: Type) -> ...` параметры generics и обычные
  параметры унифицированы
- **Механизм самоописания `Type`**: `Type` — особая сущность уровня языка, позиции `Type` в
  сигнатуре автоматически заполняются выводимыми значениями
- **Ограничения типов**: `T: Dup + Add` — множественные ограничения, ограничения на функции
- **Ассоциированные типы**:
  `Iterator: (Item: Type) -> Type = { next: () -> Option(Item), has_next: () -> Bool }`
- **Generics времени компиляции**: `N: Int` — параметры-значения generics, инстанциация константами
  на этапе компиляции
- **Условные типы**: `If: (C: Bool, T: Type, E: Type) -> Type` — вычисления на уровне типов,
  семейства типов

**Ценность**:

- Абстракции с нулевой стоимостью: мономорфизация на этапе компиляции, без накладных расходов во
  время выполнения
- Устранение мёртвого кода: анализ графа инстанциации + оптимизации LLVM
- Замена макросов: generics заменяют 90% сценариев использования макросов
- Безопасность типов: проверка на этапе компиляции, удобство для IDE
- **Явное лучше неявного**: самоописание `Type`, автоматический вывод компилятора

## Концепция вселенной типов и зависимые от значений типы

Система generics YaoXiang построена на **концепции вселенной типов** — ментальной модели, которая
унифицирует все концепции языка в многоуровневую структуру. Ключевая инновация заключается в
возведении **зависимых от значений типов** в полноправные граждане уровня Type2.

### Что такое зависимые от значений типы?

**Зависимый от значения тип** — это тип, зависящий от одного или нескольких **значений** (а не
только от других типов). Эти значения могут быть вычислены на этапе компиляции, обеспечивая гарантии
безопасности типов уже на стадии компиляции.

```yaoxiang
# Традиционные generics: параметр-тип
List: (T: Type) -> Type

# Зависимый от значения тип: параметр-значение
Vec: (n: Int) -> Type  # тип вектора зависит от значения длины n
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type  # тип матрицы зависит от количества строк и столбцов
```

### Ключевые преимущества зависимых от значений типов

По сравнению с традиционными generics, зависимые от значений типы YaoXiang обладают следующими
ключевыми преимуществами:

| Характеристика                   | Традиционные generics (C++/Rust)                      | Зависимые от значений типы YaoXiang                               |
| -------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------- |
| Значения, от которых зависит тип | Только параметры-типы                                 | Любые значения, включая результаты вызова функций                 |
| Вычисление на этапе компиляции   | C++ шаблоны: ручная специализация; Rust: нет          | Автоматическое вычисление с гарантией завершения                  |
| Вычисления на уровне типов       | Метапрограммирование шаблонов (сложно/опасно)         | Единый движок вычислений на уровне типов                          |
| Безопасность типов               | C++: нет, Rust: ограниченная                          | Полная безопасность типов, проверка на этапе компиляции           |
| Проверка размерностей            | Проверка во время выполнения или ручная специализация | Проверка размерностей на этапе компиляции, без накладных расходов |

### Иерархия вселенной типов и зависимые от значений типы

Концепция вселенной типов разделяет концепции языка по семантической роли на разные уровни.
Зависимые от значений типы располагаются на **уровне Type2**:

| Уровень   | Роль                                                      | Примеры                                                                                              |
| --------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Type-1    | Значения                                                  | `42`, `factorial(5)`, сама функция                                                                   |
| Type0     | Ключевые слова метатипов                                  | `Type`                                                                                               |
| Type1     | Конкретные типы                                           | `Int`, `String`, `Vec(3)`                                                                            |
| **Type2** | **Функции/конструкторы типов/зависимые от значений типы** | `add: (Int, Int) -> Int`, `Vec: (n: Int) -> Type`, `Matrix: (T: Type, Rows: Int, Cols: Int) -> Type` |

**Ключевой дизайн**: функции, конструкторы типов и зависимые от значений типы уровня Type2 имеют
**унифицированный синтаксис** — все имеют форму `(params) -> result`:

- Обычная функция: `(Int, Int) -> Int` → результат — значение
- Конструктор типа: `(T: Type) -> Type` → результат — тип
- Зависимый от значения тип: `(n: Int) -> Type` → результат — тип, но зависящий от
  параметра-значения

> **Изоморфизм Карри-Ховарда**: это единство — не совпадение. Изоморфизм Карри-Ховарда утверждает
> «тип — это утверждение, программа — это доказательство» — тип функции `A → B` соответствует
> логической импликации «если A, то B», generics `(T: Type) -> Type` соответствуют квантору
> всеобщности «для всех типов T», а зависимый от значения тип `(n: Int) -> Type` соответствует «для
> каждого целого n существует тип». YaoXiang унифицирует функции, конструкторы типов и зависимые от
> значений типы на уровне Type2, по сути объединяя «доказательство» и «вычисление» в одну концепцию
> — **конструктивное доказательство**. Это прямое воплощение изоморфизма Карри-Ховарда в дизайне
> языка: одна форма (`(params) -> result`) одновременно несёт логическое утверждение и процесс
> вычисления.

### Гарантия детерминированности на этапе компиляции

Концепция вселенной типов YaoXiang требует: **всё на уровне Type должно быть определено на этапе
компиляции**.

```yaoxiang
# Пример проверки размерностей на этапе компиляции
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
    # Проверка на этапе компиляции: размерности должны быть положительными
    _assert: Assert(Rows > 0),
    _assert: Assert(Cols > 0),
}

# Создание единичной матрицы 3x3 - выполняется на этапе компиляции
identity: (T: Add + Zero + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    # ...
}

# Вычисление на этапе компиляции: factorial(3) = 6, размер вектора известен при компиляции
vec: Vec(factorial(3)) = Vec(6)()
```

Компилятор автоматически:

1. Обнаруживает вызовы функций в позициях типов
2. Выполняет проверку завершения для функций на этапе компиляции (см. механизм проверки завершения
   ниже)
3. Выполняет вычисление на этапе компиляции
4. Встраивает результат в порождаемый тип

### Сценарии применения зависимых от значений типов

#### Проверка размерностей на этапе компиляции

```yaoxiang
# Умножение матриц: проверка соответствия размерностей на этапе компиляции
multiply: (T: Add + Multiply + Zero,
           Rows: Int, Cols: Int, M: Int) -> ((
    a: Matrix(T, Rows, Cols),
    b: Matrix(T, Cols, M)
) -> Matrix(T, Rows, M)) = {
    # Проверка на этапе компиляции: a.Cols == b.Rows, иначе ошибка компиляции
    result = Matrix(T, Rows, M)()
    # ...
}

# Ошибка обнаруживается на этапе компиляции:
# multiply(matrix_2x3, matrix_4x2)  # Ошибка компиляции: 2 != 4
```

#### Типобезопасный размер массива

```yaoxiang
# Размер массива — константа времени компиляции
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    length: N,
}

# N — константа времени компиляции, может использоваться в вычислениях на уровне типов
first_three: Array(Int, 3) = Array(Int, 3)(1, 2, 3)
# first_three.length == 3 (известно на этапе компиляции)
```

#### Целевой механизм покрытия ошибок границ на этапе компиляции (якорь направления #299)

> **Пояснение о состоянии реализации** (#299): типы-контейнеры деспециализированы — `Array(T, N)`
> является конструктором с const-параметрами, точка привязки литерального контекста и предикат
> membership `in` уже реализованы. В текущей версии выход за границы при индексации `[]` (E6003) и
> отсутствующий ключ Dict (E6008) являются **переходным состоянием с ошибками во время выполнения**;
> данный раздел о зависимых от значениях типах описывает целевой механизм переноса этих граничных
> ошибок на **этап компиляции**:
>
> - индексация const: `a[5]` (5 — константа времени компиляции) при `a: Array(Int, 3)` напрямую
>   отвергается на этапе компиляции;
> - индексация значением: `a[i]` требует предусловия `i < len(a)`, доказываемого контрактом
>   зависимого от значения типа;
> - предикат `in` — основа предусловий логики Хоара: `n in 1..10`, `x in some_set` являются
>   доказуемыми на этапе компиляции утверждениями.
>
> Полный дизайн уточнённых типов будет дополнен в данном разделе при реализации.

#### Условные типы

```yaoxiang
# Условный тип уровня типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Семейства типов
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,
}
```

#### Обобщённые функции

```yaoxiang
# map: обобщённая функция, параметры-типы T, R определяются на этапе компиляции
map: (T: Type, R: Type) -> (
    (list: List(T), f: (x: T) -> R) -> List(R)
) = (list, f) => {
    result = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Использование полностью прозрачно, типы выводятся автоматически
numbers = List(Int)()   # Уточнение: двухуровневая форма конструирования значения (см. §9.1); элементы добавляются через push
numbers.push(1)
numbers.push(2)
numbers.push(3)
doubled = map(numbers, (x) => x * 2)  # Выводится как map[Int, Int]
```

### Механизм проверки завершения (унифицирован с RFC-027)

Вычисление зависимых от значений типов на этапе компиляции должно **гарантировать завершение**,
иначе система типов попадёт в бесконечный цикл. Проверка завершения выполняется **полностью
автоматически** конвейером доказательств из RFC-027 — компилятор автоматически синтезирует метрики,
рекурсия/цикл, которые удаётся доказать, проходят, не удаётся — компилируются с ошибкой.
**Полуавтоматическим аннотациям не оставлено лазеек**: аннотации `//! decreases` и
`/*! invariant !*/` из RFC-022 устарели вместе с RFC-022, спецификации — это сами аннотации типов.

#### Проверка завершения рекурсивных функций

Перед вычислением на этапе компиляции компилятор проверяет, что аргументы рекурсивных вызовов строго
убывают на каждом пути рекурсии (RFC-027 §6.7). Никакие спецификационные комментарии не требуются:

```yaoxiang
# Факториал на этапе компиляции: без //! requires/ensures/decreases, компилятор анализирует автоматически
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Анализ компилятора: n-1 < n → убывает → завершается
}

# Использование: вызов в позиции типа, компилятор сначала проверяет завершение, затем вычисляет
vec: Vec(factorial(5)) = Vec(120)()  # Вычисление на этапе компиляции: factorial(5) = 120
```

| Сценарий                                                              | Поведение                        |
| --------------------------------------------------------------------- | -------------------------------- |
| Компилятор может проанализировать убывание рекурсии (например, `n-1`) | Вычисление на этапе компиляции   |
| Убывание не наблюдается / не удаётся определить                       | Ошибка компиляции                |
| Вызов во время выполнения (не в позиции типа)                         | Проверка завершения не требуется |

#### Проверка завершения циклов

Циклам не нужны аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточнённых типов на
переменных (например, `UpTo(n)`) одновременно задают инвариант цикла и границу метрики. Компилятор
по приоритету перебирает четыре стратегии синтеза метрик и останавливается на первой успешной
(RFC-027 §7):

1. **Автоматический синтез линейной ранговой функции** — извлечение границ переменных из аннотаций
   типов, перебор линейных комбинаций, проверка условий m ≥ 0 и m' < m на всех путях с помощью SMT
2. **Счётчик нарушений предиката** (экспериментальный) — извлечение violation_count из определения
   целевого типа (например, `Sorted`), покрытие соседних обменов/перемещений
3. **Шаблон ограниченного инкремента/декремента** — `v += const` → метрика `upper - v` (вырождение
   стратегии 1, самый быстрый путь)
4. **Шаблон метрики с мультипликативным масштабированием** — `v *= const` (const > 1) → метрика
   `ceil(log_const(upper / v))`

```yaoxiang
sum: (arr: Array(Int, n)) -> Int = {
    mut i: UpTo(arr.len) = 0   # Аннотация типа даёт верхнюю границу arr.len и нижнюю 0
    while i < arr.len {
        # Автоматический вывод компилятора: метрика arr.len - i, на каждой итерации строго убывает на 1 → завершение доказано
        s += arr[i]; i += 1
    }
    return s
}
```

#### Рабочий процесс проверки завершения

```

│  Фаза проверки типов                                        │
│  Встречается вызов функции в позиции типа (например, Vec(factorial(5))) │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  1. Проверка завершения (конвейер доказательств RFC-027, полностью автоматический) │
│     - Рекурсивные функции: проверка строгого убывания аргументов │
│       на каждом пути рекурсии                                │
│     - Циклы: четыре стратегии синтеза метрик (линейный ранг/ │
│       счётчик нарушений/ограниченный шаблон/                  │
│       мультипликативное масштабирование), проверка убывания  │
│       с помощью SMT                                          │
│     - Не удаётся доказать → ошибка компиляции (жёсткая       │
│       граница, без полуавтоматических аннотаций в качестве    │
│       запасного варианта)                                    │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  2. Вычисление на этапе компиляции (встроенным интерпретатором) │
│     - Чистые функции: прямое вычисление                     │
│     - Побочные эффекты: ошибка компиляции (позиция типа     │
│       должна быть без побочных эффектов)                     │
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  3. Встраивание результата в тип                            │
│     - Vec(factorial(5)) → Vec(120)                          │
│     - Matrix(Float, 3, 3) → конкретный тип                  │
└─────────────────────────────────────────────────────────────┘
```

#### Преимущества

- **Безопасность**: гарантируется завершение вычислений на этапе компиляции, что предотвращает
  попадание системы типов в бесконечный цикл
- **Единообразие**: проверка завершения и верификация корректности (генерация VC) используют общий
  конвейер доказательств (RFC-027), без отдельного синтаксиса спецификаций
- **Полная автоматизация**: компилятор автоматически синтезирует метрики из аннотаций типов,
  доказуемые проходят, недоказуемые — ошибка компиляции, не полагаясь на ручные аннотации
  `decreases` от программиста

## Мотивация

### Зачем нужна мощная система generics?

Существующие mainstream-языки имеют ограничения в generics:

| Язык         | Возможности generics           | Проблема                                                                                            |
| ------------ | ------------------------------ | --------------------------------------------------------------------------------------------------- |
| Java         | Граничные типы                 | Мономорфизация на этапе компиляции, без специализации generics                                      |
| C#           | Ограничения типов              | Проверка типов во время выполнения, накладные расходы                                               |
| Rust         | Generics + Trait               | Сложная система Trait, крутая кривая обучения                                                       |
| C++          | Шаблоны                        | Сложная специализация шаблонов, плохие сообщения об ошибках                                         |
| **YaoXiang** | **Зависимые от значений типы** | **Типы могут зависеть от значений, проверка размерностей на этапе компиляции, гарантия завершения** |

### Ключевые противоречия

1. **Производительность vs гибкость**: гибкость во время выполнения vs оптимизации на этапе
   компиляции
2. **Сложность vs простота**: мощная система типов vs удобство использования
3. **Макросы vs generics**: кодогенерация макросами vs типобезопасность generics
4. **Зависимость от значений vs безопасность типов**: традиционные generics не могут проверять
   размерности на этапе компиляции

### Ключевые преимущества зависимых от значений типов

**Зависимые от значениях типы** YaoXiang — ключевое преимущество по сравнению с традиционными
generics:

| Преимущество                       | Описание                                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Типы зависят от значений**       | `Vec: (n: Int) -> Type` позволяет типам зависеть от конкретных значений                                  |
| **Вычисление на этапе компиляции** | Вызовы функций в позициях типов вычисляются на этапе компиляции, результат встраивается в тип            |
| **Проверка размерностей**          | `Matrix(Float, 3, 3)` проверяет размерности матрицы на этапе компиляции                                  |
| **Вычисления на уровне типов**     | Условные типы `If`, `Match` поддерживают вычисления на уровне типов                                      |
| **Гарантия завершения**            | Проверка завершения на этапе компиляции (автоматический синтез метрик) гарантирует завершение вычислений |

```yaoxiang
# Проверки на этапе компиляции, невозможные в C++/Rust
matrix: Matrix(Float, factorial(3), factorial(2)) = ...
# Вычисление на этапе компиляции: factorial(3) = 6, factorial(2) = 2
# Тип: Matrix(Float, 6, 2)

# Несоответствие размерностей обнаруживается на этапе компиляции
identity: Matrix(Float, 3, 3) = ...
# multiply(matrix_2x3, identity_3x3)  # Ошибка компиляции: 2 != 3
```

### Ценность системы generics

```yaoxiang
# Пример: унифицированный дизайн API
# операция map для разных типов контейнеров

# Традиционный подход: отдельная реализация для каждого типа
map_int_array: (array: Array(Int), f: Fn(Int) -> Int) -> Array(Int) = ...
map_string_array: (array: Array(String), f: Fn(String) -> String) -> Array(String) = ...
map_int_list: (list: List(Int), f: Fn(Int) -> Int) -> List(Int) = ...
map_string_list: (list: List(String), f: Fn(String) -> String) -> List(String) = ...

# Подход с generics: одна обобщённая функция покрывает все типы
map: (T: Type, R: Type)(container: Container(T), f: Fn(T) -> R) -> Container(R) = {
    for item in container {
        result.push(f(item))
    }
    result
}
```

## Цели дизайна

### Ключевые цели

1. **Абстракции с нулевой стоимостью** — вызов generics эквивалентен вызову конкретного типа
2. **Устранение мёртвого кода** — анализ на этапе компиляции, инстанциация только используемых
   generics
3. **Замена макросов** — generics заменяют 90% сценариев использования макросов
4. **Безопасность типов** — проверка на этапе компиляции, без накладных расходов на типы во время
   выполнения
5. **Удобство для IDE** — интеллектуальные подсказки, понятные сообщения об ошибках
6. **Зависимые от значений типы** — типы могут зависеть от значений, поддержка проверки размерностей
   на этапе компиляции
7. **Безопасность вычислений на этапе компиляции** — гарантия завершения через проверку завершения
   (автоматический синтез метрик по RFC-027)

### Принципы дизайна

- **Определённость на этапе компиляции**: параметры generics определяются на этапе компиляции
- **Приоритет мономорфизации**: генерация конкретного кода, избегание вызовов виртуальных функций
- **Ограничения как управляющий фактор**: ограничения типов направляют инстанциацию
- **Платформенные оптимизации**: специализация для поддержки платформенно-специфичных оптимизаций
- **Единая вселенная типов**: функции/конструкторы типов/зависимые от значений типы унифицированы на
  уровне Type2
- **Гарантия завершения**: вызовы функций в позициях типов должны быть доказуемо завершающимися

## Предложение

### 1. Базовые generics

#### 1.1 Параметры-типы generics

> **Ключевое правило**: определения обобщённых типов **должны иметь явную аннотацию `: Type`**,
> иначе будут выведены HM как функции.
>
> | Запись                            | Значение                          |
> | --------------------------------- | --------------------------------- |
> | `List: (T: Type) -> Type = {...}` | ✅ Конструктор типа               |
> | `List = {...}`                    | ❌ HM выводит как функцию, не тип |

```yaoxiang
# Определение обобщённого типа (должно иметь : Type)
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self
}

List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,
    push: (self: List(T), item: T) -> Void,   # self — лишь соглашение об именовании, не ключевое слово
    get: (self: List(T), index: Int) -> Option(T),
}

# Обобщённая функция (без : Type, HM выводит как функцию)
map: (T: Type, R: Type) -> ((opt: Option(T), f: Fn(T) -> R) -> Option(R)) = {
    return match opt {
        some => Option.some(f(some)),
        none => Option.none(),
    }
}

# Ограничение generics (прямое выражение, в одну строку можно опустить return)
clone: (T: Clone)(value: T) -> T = value.clone()

# Множественные параметры-типы
combine: (T: Type, U: Type) -> ((a: T, b: U) -> (T, U)) = (a, b)
```

#### 2.4 Встроенные marker trait: Dup и Clone

**Три категории семантики копирования**:

| Тип                                | Значение                                                                           | Способ срабатывания                     | Сценарий использования             |
| ---------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------- |
| **Копирование значения-примитива** | Копия значения при присваивании, два значения полностью независимы                 | Автоматически при присваивании/передаче | Int, Float, Bool, Char             |
| **Dup**                            | Поверхностное копирование: копируется дескриптор/токен, базовые данные разделяются | Автоматически при присваивании/передаче | Токены `&T`, `ref T`, String/Bytes |
| **Clone**                          | Глубокое копирование: создание полностью независимой копии                         | `value.clone()`                         | Любой тип, реализующий Clone       |

**Семантика Dup**: для типов, реализующих Dup, при присваивании/передаче владение не передаётся —
компилятор копирует дескриптор/токен, несколько владельцев указывают на одни и те же базовые данные.
Это дополняет семантику Move по умолчанию из модели владения RFC-009.

**Dup и Clone — ортогональные концепции**:

```
Dup = копирование дескриптора, общие данные (изменения влияют друг на друга)
Clone = копирование данных, копии независимы (изменения не влияют друг на друга)
```

**Правила**:

```
1. Типы-примитивы (Int, Float, Bool, Char) — встроенное копирование значения компилятором, не относятся к Dup
2. Dup  — только для ссылочных/токен-типов и типов со внутренним подсчётом ссылок
3. Clone — явное глубокое копирование, любой тип может реализовать
4. Move по умолчанию — остальные типы сохраняют семантику Move по умолчанию
```

**Какие типы являются Dup**:

| Тип                                | Dup       | Причина                                                                             |
| ---------------------------------- | --------- | ----------------------------------------------------------------------------------- |
| `&T` (токен заимствования)         | ✅        | Токен нулевого размера, копирование токена = несколько представлений на одни данные |
| `ref T`                            | ✅        | Копирование Rc/Arc = счётчик ссылок + 1, разделяет данные в куче                    |
| String, Bytes                      | ✅        | Внутренний подсчёт ссылок, копирование дескриптора разделяет буфер                  |
| `&mut T` (токен изменяемой ссылки) | ❌        | Линейно-эксклюзивный, не копируется                                                 |
| struct                             | Выводится | Все поля Dup → struct Dup                                                           |
| enum                               | Выводится | Все поля всех вариантов Dup → enum Dup                                              |
| tuple                              | Выводится | Все элементы Dup → tuple Dup                                                        |
| Fn (замыкание)                     | ❌        | Захватываемая среда может не быть Dup                                               |
| `*T` (сырой указатель)             | ❌        | unsafe, не участвует в системе владения                                             |

**Int/Float/Bool/Char не являются Dup** — они являются типами-значениями, при присваивании
компилятор автоматически выполняет копирование значения (два значения полностью независимы). Это не
«поверхностное копирование», а встроенная обработка примитивов компилятором, и она не нуждается (и
не должна) в выражении через атрибут типа Dup.

```yaoxiang
# Типы-примитивы: компилятор автоматически копирует значение (не Dup)
x: Int = 42
y = x          # Копирование значения, x и y полностью независимы
print(x)       # ✅

# Dup: поверхностное копирование, копия дескриптора разделяет данные
view: &Point = &point
view2 = view    # ✅ Dup: копируется токен, оба указывают на один и тот же point
print(view.x)   # ✅

# Clone: явное глубокое копирование, создание независимой копии
backup = big_struct.clone()  # Явный вызов

# Ограничения generics
dup_use: (T: Dup) -> T = x         # T: Dup → можно поверхностно копировать
clone_use: (T: Clone) -> T = x.clone()  # T: Clone → можно глубоко копировать
```

> **Примечание**: `Send`/`Sync` не предоставляются как видимые пользователю trait. Безопасность
> межзадачных операций обеспечивается ключевым словом `ref` и полностью автоматической обработкой
> компилятором — `ref` автоматически выбирает Rc или Arc, пользователю не нужно понимать Send/Sync.

#### 3.1 Определение ассоциированного типа

```yaoxiang
# trait Iterator (с использованием синтаксиса (Item: Type) -> Type)
Iterator: (Item: Type) -> Type = {
    next: (Self) -> Option(Item),
    has_next: (Self) -> Bool,
    collect: (T: Type)(Self) -> List(T),
}

# Использование
collect_all: (T: Type, I: Iterator(T))(iter: I) -> List(T) = {
    result: List(T) = List(T)
    while iter.has_next() {
        if let Some(item) = iter.next() {
            result.push(item)
        }
    }
    return result
}

# Реализация Iterator для Array
# С использованием синтаксического сахара для методов: Array.Item, Array.next, Array.has_next
Array.has_next: (T: Type)(self: Array(T)) -> Bool = {
    return self.index < self.length
}

Array.next: (T: Type)(self: Array(T)) -> Option(T) = {
    if has_next(self) {
        item = self.data[self.index]
        self.index = self.index + 1
        return Option.some(item)
    } else {
        return Option.none()
    }
}

Array.Item: (T: Type)(arr: Array(T)) -> T = {
    return arr.data[0]
}
```

### 4. Generics времени компиляции

#### 4.1 Параметры-значения времени компиляции

> **Уточнение (#296)**: в исходном тексте говорилось «параметры-значения, такие как `Int`, в
> контексте generics по умолчанию определяются на этапе компиляции» — эта формулировка **строго
> неверна** — в `add: (a: Int, b: Int) -> Int = a + b` параметры `a`/`b` являются
> параметрами-значениями во время выполнения. Только **упоминаемые в позиции типа** конкретные
> параметры-типы являются параметрами-значениями времени компиляции. Корректное определение см.
> ниже.

**Ключевой дизайн**: `Type` в сигнатуре generics помечает параметр-тип; параметры, аннотированные
конкретными типами (`Int`/`Bool`/`Float` и т.д.), являются **кандидатами в параметры-значения
времени компиляции** — становятся ли они таковыми, зависит от того, упоминаются ли их значения **в
позиции типа** (зависимость от значений). Ключевое слово `const` не требуется.

**Правило определения (два шага)**:

1. **Грубая фильтрация по форме**: параметр, аннотированный не-`Type` конкретным типом (например,
   `Int`) → становится кандидатом.
2. **Точная фильтрация по использованию**: имя кандидата появляется в **позиции типа** (тип поля
   тела типа, тип параметра внутренней `Fn`, предикат `Assert`, позиция аргумента конструкции типа
   вроде `Array(T, N)`) → подтверждается как параметр-значение времени компиляции; иначе
   рассматривается как **параметр-значение во время выполнения**.

| Запись                                                     | Определение                                  | Причина                                                                        |
| ---------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------ |
| `add: (a: Int, b: Int) -> Int = a + b`                     | a/b — параметры-значения во время выполнения | Появляются только в позиции значения, не участвуют в конструировании типа      |
| `Array: (T: Type, N: Int) -> Type = { data: Array(T, N) }` | N — параметр-значение времени компиляции     | N появляется в позиции аргумента конструкции типа `Array(T, N)`                |
| `factorial: (N: Int) -> (k: N) -> Int`                     | N — параметр-значение времени компиляции     | N выступает типом внутреннего параметра `k`                                    |
| `Foo: (T: Type, N: Int) -> Type = { x: T }`                | N — провал (см. ниже)                        | N не упомянут в теле типа, вырождается в параметр-значение во время выполнения |

> **Суть зависимости от значений**: параметр-значение времени компиляции — это и есть зависимый от
> значения тип — только когда значение используется для **конструирования типа**, требуется его
> определённость на этапе компиляции. Форма (`: Int`) определяет лишь кандидатуру, использование
> (появление в позиции типа) определяет, является ли он параметром-значением времени компиляции. Это
> тот же критерий, что и «вызовы функций в позициях типов вычисляются на этапе компиляции» из
> раздела «Гарантия детерминированности на этапе компиляции».

```yaoxiang
# ════════════════════════════════════════════════════════
# Параметр-значение времени компиляции: N упоминается в позиции типа (слот длины Array)
# ════════════════════════════════════════════════════════
StaticArray: (T: Type, N: Int) -> Type = {
    data: Array(T, N),  # N появляется в позиции аргумента конструкции типа → параметр-значение времени компиляции
    length: N,
}

# Способ использования: factorial(5) вычисляется в позиции типа (на этапе компиляции), результат 120 встраивается в тип
arr: StaticArray(Int, factorial(5))  # StaticArray(Int, 120)

# ════════════════════════════════════════════════════════
# Зависимость от значения: N выступает типом внутреннего параметра k
# ════════════════════════════════════════════════════════
# N — параметр-значение времени компиляции (появляется в позиции типа (k: N));
# k — параметр-значение во время выполнения, его тип — литеральный тип N (однозначный тип).
factorial: (N: Int) -> (k: N) -> Int = {
    return match k {
        0 => 1,
        _ => k * factorial(k - 1)
    }
}
```

> **Обработка провалившихся кандидатов**: кандидаты, аннотированные конкретным типом, но не
> упомянутые в позиции типа (например, `N` в `Foo` выше) вырождаются в параметры-значения во время
> выполнения (путь уровня функции). Провалившиеся кандидаты на пути конструктора типа не могут
> занять слот во время выполнения (конструктор типа вычисляется на этапе компиляции), на стороне
> объявления сразу выдаётся ошибка [E1094]: «N объявлен как параметр-значение времени компиляции, но
> не упомянут в теле типа» — ранее тихое отбрасывание приводило к несогласованности arity
> инстанциации, см. issue [#297](https://github.com/ChenXu233/YaoXiang/issues/297).

### Never и Void: ⊥ и ⊤ в системе типов

Система типов YaoXiang в изоморфизме Карри-Ховарда одновременно обладает ⊥ (ложь/пустой тип) и ⊤
(истина/Unit), представленными двумя встроенными именами типов: `Never` и `Void`:

**Never (⊥)** — три неоспоримых ядерных свойства:

1. **Нулевой конструктор**: ни один литерал или выражение не может породить значение типа `Never`.
   Это метауровневое свойство, должно быть встроенным.
2. **Принцип взрыва**: `Never <: T` выполняется для любого типа `T`. Значение `Never` может
   использоваться как значение любого типа — именно поэтому код после `assert(false)` проходит
   проверку типов (хотя никогда не достигает выполнения).
3. **Маркер расходимости**: `f: (...) -> Never` означает, что `f` гарантированно не возвращается.
   Компилятор использует это для анализа мёртвого кода.

`Never` — встроенное имя типа, не ключевое слово, парсеру безразлично. Синтаксис пустых и
литеральных типов не открывается.

**Void (⊤, т.е. Unit)** — ровно один обитатель (значение void по умолчанию), носитель истинного
утверждения «всегда истинно». `Void` — единичный элемент для типов-пустых произведений, `Never` —
единичный элемент для типов-пустых сумм — они двойственны. `x: Void = <по умолчанию>` допустимо,
`x: Never = ...` не имеет правой части.

#### 4.3 Проверки на этапе компиляции (реализация стандартной библиотеки)

```yaoxiang
# ════════════════════════════════════════════════════════
# Реализация стандартной библиотеки: с использованием условных типов
# ════════════════════════════════════════════════════════

# Определения стандартной библиотеки
# IsTrue: мост от вселенной значений к вселенной типов — отображение истинности Bool в тип
IsTrue: (b: Bool) -> Type = match b {
    true => Void,      # ⊤, имеет значение, программа продолжается
    false => Never,    # ⊥, нет значения, расходимость
}

# Assert: примитив уточнённого типа на этапе компиляции — типовое выражение утверждения Bool
Assert: (cond: Bool) -> Type = IsTrue(cond)
#
# cond = true  → Assert(true)  = Void    (всегда истинно, стирается)
# cond = false → Assert(false) = Never   (всегда ложно, ошибка компиляции/расходимость)
# cond неразрешимо → конвейер доказательств решает по режиму dispatch:
#                  CompileTime → Unknown, требуется prove
#                  Runtime     → вставляется check, инъекция в предположения Γ

# Способ использования 1: как ограничение в определении типа
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    # Проверка на этапе компиляции: N должно быть больше 0 (Assert в позиции типа)
    length: Assert(N > 0),
}

# Способ использования 2: в выражении
IntArray: (N: Int) -> Type = StaticArray(Int, N)
# Проверка: размер IntArray(10) равен sizeof(Int) * 10
Assert(size_of(IntArray(10)) == sizeof(Int) * 10)
```

### 5. Условные типы

> **Изоморфизм Карри-Ховарда**: условные типы с точки зрения Карри-Ховарда являются логическим
> **case-анализом**. Тип `Bool` соответствует утверждению с двумя возможными значениями
> (True/False), а `If` в зависимости от истинности утверждения выбирает различные результаты — это в
> точности логическая дизъюнкция через case-анализ. `match C { True => T, False => E }` фактически
> выражает: «если известно, что утверждение C истинно, заключение — T, если ложно — E».

#### 5.1 Условный тип If

```yaoxiang
# Условный тип уровня типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Пример: ветвление на этапе компиляции
NonEmpty: (T: Type) -> Type = If(T != Void, T, Never)

Optional: (T: Type) -> Type = If(T != Void, T, Void)

# Проверка на этапе компиляции (унифицирована с определением Assert из §4.3)
# Assert: (cond: Bool) -> Type = IsTrue(cond)

# Использование
# Вычисление типа: If(True, Int, String) => Int
# Вычисление типа: If(False, Int, String) => String
```

#### 5.2 Семейства типов

> **Изоморфизм Карри-Ховарда**: семейства типов — самое прямое воплощение принципа «утверждение как
> тип». `Add: (A: Type, B: Type) -> Type` — это не «функция сложения на уровне типов», а
> **построение утверждения о сложении натуральных чисел**. `(Zero, B) => B` говорит «утверждение
> Add(Zero, B) эквивалентно B», `(Succ(A'), B) => Succ(Add(A', B))` говорит «если Add(A', B)
> выполняется, то и Add(Succ(A'), B) выполняется». Это и есть само определение сложения по аксиомам
> Пеано. То, что проверка типов подтверждает прохождение этого match-выражения, эквивалентно
> проверке логической согласованности этого определения.

```yaoxiang
# Преобразование типов на этапе компиляции
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,  # по умолчанию
}

# Вычисления на уровне типов
Length: (T: Type) -> Type = match T.length {
    0 => Zero,
    1 => Succ(Zero),
    2 => Succ(Succ(Zero)),
    _ => TooLong,
}

# Сложение на уровне типов (Карри-Ховард: case-анализ + рекурсивный вызов, требует проверки завершения для полной индукции)
Add: (A: Type, B: Type) -> Type = match (A, B) {
    (Zero, B) => B,
    (Succ(A'), B) => Succ(Add(A', B)),
}

# Пример: вычисление 2 + 3 на этапе компиляции
Two: Type = Succ(Succ(Zero))
Three: Type = Succ(Succ(Succ(Zero)))
Five: Type = Add[Two, Three]  # Succ(Succ(Succ(Succ(Succ(Zero)))))
```

**Ключевая особенность**: перегрузка функций и оптимизация инлайнинга естественно сочетаются,
обеспечивая абстракции с нулевой стоимостью.

```yaoxiang
    }
    return result
}

result = native_sum_int(int_arr.data, int_arr.length)

# Полностью эквивалентно вручную написанному оптимизированному коду, без накладных расходов на вызов функции!
```

1. **Интеллектуальный выбор компилятора**

2. **Оптимизация инлайнинга**
   - Маленькие функции автоматически встраиваются в точку вызова
   - Нулевые накладные расходы на вызов функции
   - Полностью эквивалентно вручную написанному оптимизированному коду

3. **Безопасность типов**
   - Проверка типов на этапе компиляции
   - Нулевые накладные расходы во время выполнения
   - Таблица виртуальных функций не требуется

4. **Идеальное соответствие RFC-010**

   ```yaoxiang

   # Новые ключевые слова вроде impl, where не требуются
   ```

````
### 7. Механизм устранения мёртвого кода

#### 7.1 Анализ графа инстанциации

```rust
// Внутри компилятора: построение графа зависимостей инстанциации generics
struct InstantiationGraph {
    // Узлы: инстанциации generics
    nodes: HashMap<InstanceKey, InstanceNode>,

    // Рёбра: отношения использования
    edges: HashMap<InstanceKey, Vec<InstanceKey>>,
}

struct InstanceKey {
    generic: FunctionId,  // ID обобщённой функции
    type_args: Vec<TypeId>,  // аргументы-типы
    const_args: Vec<ConstId>,  // аргументы-константы
}

// Алгоритм: анализ достижимости
fn eliminate_dead_instantiations(graph: &InstantiationGraph) {
    let mut reachable = HashSet::new();

    // Начинаем с точек входа (main, экспортируемые функции и т.д.)
    let entry_points = find_entry_points();
    for entry in entry_points {
        dfs_visit(entry, &graph, &mut reachable);
    }

    // Не посещённые инстанциации — мёртвый код
    for node in &graph.nodes {
        if !reachable.contains(node.key) {
            eliminate(node);
        }
    }
}
````

### 9. Примеры

#### 9.1 Полный пример обобщённого контейнера

```yaoxiang
# ======== 1. Определение обобщённого контейнера ========
# Используется синтаксис (T: Type) -> Type
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

List: (T: Type) -> Type = {
    data: Array(T),
    length: Int,

    # Обобщённые методы (T автоматически попадает в область видимости из внешнего List(T))
    push: (self: List(T), item: T) -> Void,
    pop: (self: List(T)) -> Option(T),
    map: (R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)),
    filter: (self: List(T), predicate: (T) -> Bool) -> List(T),
    fold: (U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U),
}

# ======== 2. Реализация обобщённых методов ========
# Определения функций в пространстве имён List (префикс List. = принадлежность пространству имён)
# Чтобы синтаксис вызова через . вроде list.push(item) работал, требуется явная привязка: List.push = push[0]
# self — лишь соглашение об именовании, компилятор смотрит на тип, а не на имя

List.push: (T: Type) -> ((self: List(T), item: T) -> Void) = {
    if self.length >= self.data.length {
        # Расширение
        new_data = Array(T)(self.data.length * 2)
        for i in 0..self.length {
            new_data[i] = self.data[i]
        }
        self.data = new_data
    }
    self.data[self.length] = item
    self.length = self.length + 1
}

List.pop: (T: Type) -> ((self: List(T)) -> Option(T)) = {
    if self.length > 0 {
        self.length = self.length - 1
        return Option.some(self.data[self.length])
    } else {
        return Option.none()
    }
}

List.map: (T: Type, R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)) = {
    result = List(R)()
    for i in 0..self.length {
        result.push(f(self.data[i]))
    }
    return result
}

List.filter: (T: Type) -> ((self: List(T), predicate: (T) -> Bool) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        if predicate(self.data[i]) {
            result.push(self.data[i])
        }
    }
    return result
}

List.fold: (T: Type, U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U) = {
    result = initial
    for i in 0..self.length {
        result = f(result, self.data[i])
    }
    return result
}

# ======== 3. Использование ограничений типов ========
# Реализация Clone для List
List.clone: (T: Clone) -> ((self: List(T)) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        result.push(self.data[i].clone())
    }
    return result
}

# ======== 4. Примеры использования ========
# Создание обобщённого List
numbers = List(Int)()
numbers.push(1)
numbers.push(2)
numbers.push(3)

# Использование обобщённых методов
doubled = numbers.map((x) => x * 2)
evens = numbers.filter((x) => x % 2 == 0)

# Использование fold
sum = numbers.fold(0, (acc, x) => acc + x)  # sum = 6

# Композиция generics
sum_of_evens = numbers
    .filter((x) => x % 2 == 0)
    .map((x) => x * 2)
    .fold(0, (acc, x) => acc + x)  # sum_of_evens = 8
```

#### 9.2 Пример обобщённого алгоритма

```yaoxiang
# ======== 1. Обобщённый алгоритм сортировки ========
Comparator: (T: Type) -> Type = {
    compare: (T, T) -> Int,  # -1 if a < b, 0 if a == b, 1 if a > b
}

# Обобщённая быстрая сортировка
quicksort: (T: Clone) -> ((array: Array(T), cmp: Comparator(T)) -> Array(T)) = {
    if array.length <= 1 {
        return array.clone()
    }

    pivot = array[array.length / 2]
    left = Array(T)()
    right = Array(T)()

    for i in 0..array.length {
        if i == array.length / 2 {
            continue
        }
        item = array[i]
        comparison = cmp.compare(item, pivot)
        if comparison < 0 {
            left.push(item)
        } else {
            right.push(item)
        }
    }

    sorted_left = quicksort(left, cmp)
    sorted_right = quicksort(right, cmp)

    result = sorted_left.clone()
    result.push(pivot)
    result.extend(sorted_right)
    return result
}

# ======== 2. Реализация IntComparator ========
# Реализация через перегрузку функций
compare: (a: Int, b: Int) -> Int = {
    if a < b {
        return -1
    } else if a > b {
        return 1
    } else {
        return 0
    }
}

# ======== 3. Примеры использования ========
# Сортировка массива Int
numbers = Array(Int)(3, 1, 4, 1, 5, 9, 2, 6)
sorted = quicksort(numbers, Comparator(Int)())

# Сортировка массива String (требует StringComparator)
strings = Array(String)("hello", "world", "foo", "bar")
sorted_strings = quicksort(strings, Comparator(String)())
```

#### 9.3 Пример generics на этапе компиляции

```yaoxiang
# ======== 1. Тип матрицы с известными на этапе компиляции размерностями ========
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),

    # Проверка размерностей на этапе компиляции: с использованием типа Assert стандартной библиотеки
    _assert: Assert(Rows > 0),  # Rows > 0, иначе ошибка компиляции
    _assert: Assert(Cols > 0),  # Cols > 0, иначе ошибка компиляции

    # Операции над матрицами
    multiply: (M: Int) -> ((self: Matrix(T, Rows, Cols), other: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)) = {
        result = Matrix(T, Rows, M)()
        for i in 0..Rows {
            for j in 0..M {
                sum = Zero::zero()
                for k in 0..Cols {
                    sum = sum + self.data[i][k] * other.data[k][j]
                }
                result.data[i][j] = sum
            }
        }
        return result
    }
}

# ======== 2. Создание матрицы на этапе компиляции ========
identity: (T: Add + Multiply + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    for i in 0..N {
        for j in 0..N {
            if i == j {
                matrix.data[i][j] = One::one()
            } else {
                matrix.data[i][j] = Zero::zero()
            }
        }
    }
    return matrix
}

# ======== 3. Примеры использования ========
# Создание матрицы с размером, известным на этапе компиляции
# Матрица 2x3
matrix_2x3 = Matrix(Float, 2, 3)()
matrix_2x3.data[0][0] = 1.0
matrix_2x3.data[0][1] = 2.0
matrix_2x3.data[0][2] = 3.0
matrix_2x3.data[1][0] = 4.0
matrix_2x3.data[1][1] = 5.0
matrix_2x3.data[1][2] = 6.0

# Матрица 3x2
matrix_3x2 = Matrix(Float, 3, 2)()
matrix_3x2.data[0][0] = 7.0
matrix_3x2.data[0][1] = 8.0
matrix_3x2.data[1][0] = 9.0
matrix_3x2.data[1][1] = 10.0
matrix_3x2.data[2][0] = 11.0
matrix_3x2.data[2][1] = 12.0

# Умножение матриц: 2x3 * 3x2 = 2x2
result = matrix_2x3.multiply(matrix_3x2)

# Проверка на этапе компиляции: тип result — Matrix(Float, 2, 2)
# Единичная матрица 2x2
identity_3x3 = identity(Float, 3)()

# Несоответствие размерностей: ошибка компиляции
```

## Компромиссы

### Преимущества

1. **Абстракции с нулевой стоимостью**
   - Мономорфизация на этапе компиляции, без накладных расходов во время выполнения
   - Виртуальные функции не нужны, RTTI не нужен

2. **Устранение мёртвого кода**
   - Анализ на этапе компиляции, инстанциация только используемых generics
   - Раздувание кода контролируемо

3. **Замена макросов**
   - Типобезопасная кодогенерация
   - Удобство для IDE, понятные сообщения об ошибках

4. **Вычисления на этапе компиляции**
   - Generics времени компиляции поддерживают вычисления на этапе компиляции
   - Возможности вроде проверки размерностей
   - Ключевое слово `const` не нужно, чистые ограничения типов

### Недостатки

1. **Время компиляции**
   - Инстанциация generics увеличивает время компиляции
   - Решение ограничений может быть медленным

2. **Потребление памяти**
   - Потребление памяти компилятором увеличивается
   - Механизмы кеширования требуют памяти

3. **Сложность реализации**
   - Решатель ограничений сложен
   - Движок вычислений на уровне типов сложен

4. **Диагностика ошибок**
   - Ошибки generics могут быть сложными
   - Требуются понятные подсказки об ошибках

### Меры по смягчению

1. **Стратегии кеширования**
   - Кеширование результатов инстанциации
   - LRU-кеш для ограничения памяти

2. **Инкрементальная компиляция**
   - Кеширование результатов компиляции
   - Инкрементальная инстанциация

3. **Подсказки об ошибках**
   - Понятные сообщения об ошибках
   - Подсказки по выводу параметров generics

4. **Параллельная компиляция**
   - Параллельная инстанциация generics
   - Многопоточное решение ограничений

## Альтернативы

| Подход                          | Почему не выбран                                    |
| ------------------------------- | --------------------------------------------------- |
| Только базовые generics         | Не может заменить сложные макросы                   |
| Чистая система макросов         | Нет безопасности типов, плохие сообщения об ошибках |
| Только ограничения зависимостей | Недостаточная гибкость                              |
| Generics во время выполнения    | Накладные расходы на производительность             |

### БНФ грамматики

```bnf
# Параметры generics используют унифицированный синтаксис () как часть типа функции
# Например: map: (T: Type, R: Type) -> ((list: List(T), f: (T) -> R) -> List(R))

# Ограничение типа (в параметре generics)
type_bound ::= identifier
             | identifier '+' identifier ('+' identifier)*

# Объявление параметра (тип + имя)
parameter ::= identifier ':' type

parameters ::= parameter (',' parameter)*

# Объявление функции: name: type = expression
# Параметры generics — первая группа параметров в типе функции: (T: Type) -> ((params) -> return)
function ::= identifier ':' type '=' (expression | block)

# Объявление метода: Type.method: type = expression
method ::= identifier '.' identifier ':' type '=' (expression | block)

# Определение типа (унифицированный синтаксис Binding)
# Обобщённый тип, например: List: (T: Type) -> Type = { ... }
generic_type ::= identifier ':' type '=' type_expression

# Type в параметре generics автоматически заполняется компилятором из типов фактических аргументов
# Например, для map(numbers, f) T извлекается из numbers: List(Int), R — из f: (Int) -> String
```
