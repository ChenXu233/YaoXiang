# RFC-011: Дизайн системы дженериков - абстракции с нулевой стоимостью и замена макросов

## Резюме

Данный документ определяет **дизайн системы дженериков** языка YaoXiang, реализующий абстракции с
нулевой стоимостью за счёт мощных возможностей дженериков, снижающий зависимость от макросов
посредством оптимизаций на этапе компиляции и предоставляющий механизм удаления мёртвого кода.

**Основные положения дизайна**:

- **Унифицированный синтаксис сигнатур**: `(T: Type, R: Type) -> ...` — параметры дженериков
  унифицированы с обычными параметрами
- **Механизм самоописания Type**: `Type` — это языковой особый объект, позиции `Type` в сигнатуре
  могут автоматически выводиться и заполняться
- **Ограничения типа**: `T: Dup + Add` — множественные ограничения, ограничения на типы функций
- **Ассоциированные типы**:
  `Iterator: (Item: Type) -> Type = { next: () -> Option(Item), has_next: () -> Bool }`
- **Дженерики времени компиляции**: `N: Int` — параметры-значения дженериков, инстанциация
  константами времени компиляции
- **Условные типы**: `If: (C: Bool, T: Type, E: Type) -> Type` — вычисления на уровне типов,
  семейства типов

**Ценность**:

- Абстракции с нулевой стоимостью: мономорфизация на этапе компиляции, без накладных расходов в
  runtime
- Удаление мёртвого кода: анализ графа инстанциации + оптимизации LLVM
- Замена макросов: дженерики заменяют 90% сценариев использования макросов
- Безопасность типов: проверка на этапе компиляции, удобно для IDE
- **Явное лучше неявного**: `Type` самоописывающий, компилятор выполняет автоматический вывод

## Идея вселенной типов и типы, зависящие от значений

Система дженериков YaoXiang построена на **идее вселенной типов** — ментальной модели, унифицирующей
все концепции языка в иерархическую структуру, ключевой инновацией которой является возведение
**типов, зависящих от значений**, в ранг объектов первого класса на уровне Type2.

### Что такое типы, зависящие от значений?

**Тип, зависящий от значений** — это тип, который зависит от одного или нескольких **значений** (а
не только от других типов). Эти значения могут вычисляться на этапе компиляции, обеспечивая гарантии
безопасности типов уже на стадии компиляции.

```yaoxiang
# Традиционные дженерики: параметры типа
List: (T: Type) -> Type

# Типы, зависящие от значений: параметры-значения
Array: (T: Type, N: Int) -> Type  # тип массива зависит от значения длины N
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type  # тип матрицы зависит от числа строк и столбцов
```

### Слои именования контейнерных типов

На языковом уровне существует три концепции контейнеров, и принадлежность информации о длине — их
фундаментальное различие:

| Тип           | Длина            | Семантика                                        | Базовая реализация                             |
| ------------- | ---------------- | ------------------------------------------------ | ---------------------------------------------- |
| `Array(T, N)` | Тип              | **Фиксированной длины** массив, N в типе         | Базовая примитивная (стек/инлайн-приоритет)    |
| `Vec(T)`      | Значение runtime | **Примитивный буфер runtime-длины**, может расти | Базовая примитивная (непрерывный буфер в куче) |
| `List(T)`     | Значение runtime | Тип стандартной библиотеки                       | Библиотека: `{ data: Vec(T), length: Int }`    |

Принципы разделения:

- **`Array(T, N)` — единственная форма, помещающая длину в тип** — длина является константой времени
  компиляции, поэтому возможен отказ на этапе компиляции при выходе за границы (для `a[5]` при
  `a: Array(Int, 3)` — прямая ошибка компиляции, см. ниже «Проверка измерений на этапе компиляции»).
- **`Vec(T)` — минимальный фундамент runtime-длины** — предоставляет только четыре возможности:
  «выделить, получить длину, читать/писать, расширить». Никакой стратегии ёмкости, фактора роста,
  сжатия. Это сырьё для построения других контейнеров.
- **`List(T)` — тип библиотеки, не примитив** — определяется самим YaoXiang в `std.list`
  (`{ data: Vec(T), length: Int }`) наравне с пользовательскими обобщёнными записями. Вся стратегия
  расширяемой семантики (когда расширять, насколько, возможно ли разделение владения) находится в
  библиотеке, компилятор не участвует.

Форма конструктора `Vec(T)` (двухслойная: сначала параметры типа, затем параметры конструктора):

```yaoxiang
# Пустая конструкция — длина 0, элементы добавляются позже
v = Vec(Int)()

# Конструкция с элементами — длина определяется числом элементов
w = Vec(Int)(1, 2, 3)          # длина 3

# Распределение слотов — выделение n нулевых слотов
buf = Vec(Int)(len=64)         # длина 64, все элементы — нулевые значения
```

> Распределение слотов использует **именованную форму** (`len=`), а не позиционную: позиционная
> форма с одним целым числом неоднозначна с «одноэлементным вектором» (`Vec(Int)(64)` нельзя
> отличить от «длина 64» и «содержит один элемент 64»). Это согласуется с унифицированным правилом
> конструкторов дженериков: именованные аргументы связываются по имени и не зависят от позиционного
> вывода.
>
> Это единственная примитивная операция, необходимая для расширения `List` — `List` при
> необходимости выделяет новые слоты и перемещает элементы:
>
> ```yaoxiang
> new_data = Vec(T)(len=self.data.length * 2)
> ```
>
> Когда расширять, насколько, сжимать ли — всё решает `List`. `Vec` не реализует стратегию ёмкости.

Снизу вверх производительность убывает, гибкость возрастает: `Array` > `Vec` > `List`.

> Обоснование именования: `Vec`/`vector` в основных языках (Rust/C++) обозначают расширяемую
> последовательность runtime-длины; `Array` — фиксированной длины.

### Ключевые преимущества типов, зависящих от значений

По сравнению с традиционными дженериками, типы YaoXiang, зависящие от значений, обладают следующими
ключевыми преимуществами:

| Характеристика                   | Традиционные дженерики (C++/Rust)                     | Типы YaoXiang, зависящие от значений                                                    |
| -------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Значения, от которых зависит тип | Только параметры типа                                 | Любые значения, включая результаты вызовов функций                                      |
| Вычисление на этапе компиляции   | Ручная специализация шаблонов C++, отсутствует в Rust | Автоматическое вычисление на этапе компиляции с гарантией завершимости                  |
| Вычисления на уровне типов       | Метапрограммирование шаблонов (сложно/опасно)         | Унифицированный движок вычислений на уровне типов                                       |
| Безопасность типов               | Отсутствует в C++, ограничена в Rust                  | Полная безопасность типов, проверка на этапе компиляции                                 |
| Проверка измерений               | Проверка в runtime или ручная специализация           | Автоматическая проверка измерений на этапе компиляции, без накладных расходов в runtime |

### Иерархия вселенных типов и типы, зависящие от значений

Идея вселенной типов разделяет концепции языка по семантической роли на разные уровни, причём типы,
зависящие от значений, расположены на **уровне Type2**:

| Уровень   | Роль                                                       | Примеры                                                                                                         |
| --------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Type-1    | Значения                                                   | `42`, `factorial(5)`, сама функция                                                                              |
| Type0     | Ключевое слово метатипа                                    | `Type`                                                                                                          |
| Type1     | Конкретные типы                                            | `Int`, `String`, `Array(Int, 3)`                                                                                |
| **Type2** | **Функции/конструкторы типов/типы, зависящие от значений** | `add: (Int, Int) -> Int`, `Array: (T: Type, N: Int) -> Type`, `Matrix: (T: Type, Rows: Int, Cols: Int) -> Type` |

**Ключевой дизайн**: функции уровня Type2, конструкторы типов и типы, зависящие от значений, имеют
**унифицированный синтаксис** — форму `(params) -> result`:

- Обычная функция: `(Int, Int) -> Int` → результат — значение
- Конструктор типа: `(T: Type) -> Type` → результат — тип
- Тип, зависящий от значений: `(T: Type, N: Int) -> Type` → результат — тип, и он зависит от
  параметра-значения N

> **Изоморфизм Карри-Ховарда**: это единство не случайно. Изоморфизм Карри-Ховарда утверждает «типы
> суть propositions, программы суть доказательства» — тип функции `A → B` соответствует логической
> импликации «если A, то B», дженерик `(T: Type) -> Type` соответствует квантору всеобщности «для
> всех типов T», тип, зависящий от значений `(n: Int) -> Type` соответствует «для каждого целого n
> существует тип». YaoXiang объединяет функции, конструкторы типов и типы, зависящие от значений, на
> уровне Type2, что по сути объединяет «доказательство» и «вычисление» в единое понятие —
> **конструктивное доказательство**. Это прямое проявление изоморфизма Карри-Ховарда в дизайне
> языка: одна форма (`(params) -> result`) одновременно несёт логическое proposition и процесс
> вычисления.

### Гарантия детерминированности на этапе компиляции

Идея вселенной типов YaoXiang требует: **всё на уровне Type определено на этапе компиляции**.

```yaoxiang
# Пример проверки измерений на этапе компиляции
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
    # Проверка на этапе компиляции: измерения должны быть положительными
    _assert: Assert(Rows > 0),
    _assert: Assert(Cols > 0),
}

# Создание единичной матрицы 3x3 — выполняется на этапе компиляции
identity: (T: Add + Zero + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    # ...
}

# Вычисление на этапе компиляции: factorial(3) = 6, размер массива определён на этапе компиляции
arr: Array(Int, factorial(3)) = Array(Int, 6)()
```

Компилятор автоматически:

1. Обнаруживает вызовы функций в позициях типа
2. Выполняет проверку завершимости функции на этапе компиляции (см. механизм проверки завершимости
   ниже)
3. Выполняет вычисление на этапе компиляции
4. Встраивает результат в порождаемый тип

### Сценарии применения типов, зависящих от значений

#### Проверка измерений на этапе компиляции

```yaoxiang
# Умножение матриц: проверка соответствия измерений на этапе компиляции
multiply: (T: Add + Multiply + Zero,
           Rows: Int, Cols: Int, M: Int) -> ((
    a: Matrix(T, Rows, Cols),
    b: Matrix(T, Cols, M)
) -> Matrix(T, Rows, M)) = {
    # Проверка на этапе компиляции: a.Cols == b.Rows, иначе ошибка компиляции
    result = Matrix(T, Rows, M)()
    # ...
}

# Ошибка обнаруживается на этапе компиляции:
# multiply(matrix_2x3, matrix_4x2)  # Ошибка компиляции: 2 != 4
```

#### Типобезопасный размер массива

```yaoxiang
# Размер массива — константа времени компиляции
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    length: N,
}

# N — константа времени компиляции, может использоваться в вычислениях на уровне типов
first_three: Array(Int, 3) = Array(Int, 3)(1, 2, 3)
# first_three.length == 3 (известно на этапе компиляции)
```

#### Цель покрытия ошибок границ на этапе компиляции

> **Примечание о состоянии реализации**: типы контейнеров деспециализированы — `Array(T, N)`
> является конструктором const-дженериков, литеральный контекст привязки и предикат членства `in`
> уже реализованы. N и тип элементов в литеральной привязке `Array(T, N)` уже принудительно
> проверены на этапе компиляции (E1002), **N достоверен** — механизмы данного раздела могут
> основываться на утверждении «аннотация N == runtime-длина». В настоящее время выход за границы при
> индексации `[]` (E6003) и отсутствие ключа в Dict (E6008) являются **переходным состоянием с
> runtime-ошибками**; данный раздел о типах, зависящих от значений, представляет целевой механизм
> переноса этих ошибок границ на **этап компиляции**:
>
> - const-индексация: `a[5]` (5 — константа времени компиляции) при `a: Array(Int, 3)` напрямую
>   отвергается на этапе компиляции;
> - индексация значением: `a[i]` требует предварительного условия `i < len(a)`, доказываемого
>   контрактом типов, зависящих от значений;
> - предикат `in` является базисом предусловий логики Хоара: `n in 1..10`, `x in some_set` —
>   доказуемые на этапе компиляции propositions.
>
> Полный дизайн уточнённых типов будет дополнен в данном разделе при реализации.

#### Условные типы

```yaoxiang
# If на уровне типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Семейства типов
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,
}
```

#### Обобщённые функции

```yaoxiang
# map: обобщённая функция, параметры типа T, R определяются на этапе компиляции
map: (T: Type, R: Type) -> (
    (list: List(T), f: (x: T) -> R) -> List(R)
) = (list, f) => {
    result = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Использование полностью прозрачно, типы выводятся автоматически
numbers = List(Int)()   # Двухслойная форма значения-конструктора (см. §9.1); элементы заполняются через push
numbers.push(1)
numbers.push(2)
numbers.push(3)
doubled = map(numbers, (x) => x * 2)  # Выводится как map[Int, Int]
```

### Механизм проверки завершимости (унифицирован с RFC-027)

Вычисление на этапе компиляции для типов, зависящих от значений, должно **гарантировать
завершимость**, иначе система типов зациклится. Проверка завершимости выполняется **полностью
автоматически** конвейером доказательства на этапе компиляции из RFC-027 — компилятор автоматически
синтезирует метрики, рекурсии/циклы, которые удаётся доказать, проходят, остальные сразу вызывают
ошибку компиляции. **Полуавтоматическим аннотациям не оставлено лазеек**: `//! decreases`,
`/*! invariant !*/` из RFC-022 отменены вместе с RFC-022, спецификация — это сама аннотация типа.

#### Проверка завершимости рекурсивных функций

Перед вычислением на этапе компиляции компилятор проверяет, что аргумент рекурсивного вызова строго
убывает на каждом пути рекурсии (RFC-027 §6.7). Никаких аннотаций спецификации не требуется:

```yaoxiang
# Факториал на этапе компиляции: без //! requires/ensures/decreases, компилятор анализирует автоматически
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Анализ компилятора: n-1 < n → убывает → завершимость доказана
}

# Использование: вызов в позиции типа, компилятор сначала проверяет завершимость, затем вычисляет
arr: Array(Int, factorial(5)) = Array(Int, 120)()  # Вычисление на этапе компиляции factorial(5) = 120
```

| Сценарий                                                              | Поведение                          |
| --------------------------------------------------------------------- | ---------------------------------- |
| Компилятор может проанализировать убывание рекурсии (например, `n-1`) | Вычисление на этапе компиляции     |
| Не убывает / не удаётся определить убывание                           | Ошибка компиляции                  |
| Вызов в runtime (не в позиции типа)                                   | Проверка завершимости не требуется |

#### Проверка завершимости циклов

Циклам не нужны аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточнённого типа на
переменных (например, `UpTo(n)`) одновременно задают инвариант цикла и границу метрики. Компилятор
по приоритету пробует четыре стратегии синтеза метрик, останавливаясь на первой успешной (RFC-027
§7):

1. **Автоматический синтез линейной ранговой функции** — извлечение границ переменных из аннотаций
   типа, перебор линейных комбинаций, SMT-проверка m ≥ 0 и m' < m на всех путях
2. **Подсчёт нарушений предиката** (экспериментальный) — извлечение violation_count из определения
   целевого типа (например, `Sorted`), покрытие соседних обменов/перемещений
3. **Паттерн ограниченного возрастания/убывания** — `v += const` → метрика `upper - v` (вырождение
   стратегии 1, самый быстрый путь)
4. **Шаблон метрики с мультипликативным масштабированием** — `v *= const` (const > 1) → метрика
   `ceil(log_const(upper / v))`

```yaoxiang
sum: (arr: Array(Int, n)) -> Int = {
    mut i: UpTo(arr.len) = 0   # Аннотация типа задаёт верхнюю границу arr.len и нижнюю 0
    while i < arr.len {
        # Компилятор автоматически выводит: метрика arr.len - i, на каждой итерации строго убывает на 1 → завершимость доказана
        s += arr[i]; i += 1
    }
    return s
}
```

#### Рабочий процесс проверки завершимости

```
┌─────────────────────────────────────────────────────────────┐
│  Фаза проверки типов                                        │
│  Встречается вызов функции в позиции типа (например, factorial(5))│
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  1. Проверка завершимости (конвейер доказательства RFC-027, полностью автоматический)│
│     - Рекурсивные функции: проверка строгого убывания аргумента на каждом пути│
│     - Циклы: четыре стратегии синтеза метрик (линейный ранг/подсчёт нарушений/ограниченный паттерн/│
│       мультипликативное масштабирование), SMT-проверка убывания│
│     - Не удаётся доказать → ошибка компиляции (жёсткая граница, без полуавтоматических аннотаций)│
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  2. Вычисление на этапе компиляции (выполняется встроенным интерпретатором)│
│     - Чистые функции: прямое вычисление                      │
│     - Побочные эффекты: ошибка компиляции (позиция типа должна быть без эффектов)│
└─────────────────────────┬───────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  3. Встраивание результата в тип                            │
│     - Array(Int, factorial(5)) → Array(Int, 120)             │
│     - Matrix(Float, 3, 3) → конкретный тип                   │
└─────────────────────────────────────────────────────────────┘
```

#### Преимущества

- **Безопасность**: гарантия завершимости вычислений на этапе компиляции, предотвращение
  зацикливания системы типов
- **Единообразие**: проверка завершимости и верификация корректности (генерация VC) используют общий
  конвейер доказательств на этапе компиляции (RFC-027), без отдельного синтаксиса спецификаций
- **Полная автоматизация**: компилятор автоматически синтезирует метрики из аннотаций типа,
  доказуемое проходит, недоказуемое — ошибка, без зависимости от рукописных `decreases`

## Мотивация

### Зачем нужна мощная система дженериков?

Существующие mainstream-языки имеют ограничения в дженериках:

| Язык         | Возможности дженериков          | Проблема                                                                                           |
| ------------ | ------------------------------- | -------------------------------------------------------------------------------------------------- |
| Java         | Граничные типы                  | Мономорфизация на этапе компиляции, без специализации                                              |
| C#           | Ограничения дженериков          | Проверка типов в runtime, накладные расходы                                                        |
| Rust         | Дженерики + Trait               | Сложная система Trait, крутая кривая обучения                                                      |
| C++          | Шаблоны                         | Сложная специализация шаблонов, плохие сообщения об ошибках                                        |
| **YaoXiang** | **Типы, зависящие от значений** | **Типы могут зависеть от значений, проверка измерений на этапе компиляции, гарантия завершимости** |

### Основные противоречия

1. **Производительность vs гибкость**: гибкость в runtime vs оптимизация на этапе компиляции
2. **Сложность vs простота**: мощная система типов vs удобство использования
3. **Макросы vs дженерики**: генерация кода макросами vs типобезопасность дженериков
4. **Зависимость от значений vs безопасность типов**: традиционные дженерики не могут проверять
   измерения на этапе компиляции

### Ключевые преимущества типов, зависящих от значений

**Типы YaoXiang, зависящие от значений**, — ключевое преимущество по сравнению с традиционными
дженериками:

| Преимущество                       | Описание                                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Зависимость типа от значения**   | `Array: (T: Type, N: Int) -> Type` позволяет типу зависеть от конкретного значения                           |
| **Вычисление на этапе компиляции** | Вызовы функций в позициях типа вычисляются на этапе компиляции, результат встраивается в тип                 |
| **Проверка измерений**             | `Matrix(Float, 3, 3)` проверяет измерения матрицы на этапе компиляции                                        |
| **Вычисления на уровне типов**     | Условные типы `If`, `Match` поддерживают вычисления на уровне типов                                          |
| **Гарантия завершимости**          | Проверка завершимости на этапе компиляции (автоматический синтез метрик) гарантирует завершимость вычислений |

```yaoxiang
# Проверка на этапе компиляции, невозможная в C++/Rust
matrix: Matrix(Float, factorial(3), factorial(2)) = ...
# Вычисление на этапе компиляции: factorial(3) = 6, factorial(2) = 2
# Тип — Matrix(Float, 6, 2)

# Несоответствие измерений обнаруживается на этапе компиляции
identity: Matrix(Float, 3, 3) = ...
# multiply(matrix_2x3, identity_3x3)  # Ошибка компиляции: 2 != 3
```

### Ценность системы дженериков

```yaoxiang
# Пример: унифицированный дизайн API
# Операция map для разных контейнерных типов

# Традиционный подход: отдельная реализация для каждого типа
map_int_array: (array: Vec(Int), f: Fn(Int) -> Int) -> Vec(Int) = ...
map_string_array: (array: Vec(String), f: Fn(String) -> String) -> Vec(String) = ...
map_int_list: (list: List(Int), f: Fn(Int) -> Int) -> List(Int) = ...
map_string_list: (list: List(String), f: Fn(String) -> String) -> List(String) = ...

# Подход с дженериками: одна обобщённая функция покрывает все типы
map: (T: Type, R: Type)(container: Container(T), f: Fn(T) -> R) -> Container(R) = {
    for item in container {
        result.push(f(item))
    }
    result
}
```

## Цели дизайна

### Основные цели

1. **Абстракции с нулевой стоимостью** — вызовы дженериков эквивалентны вызовам конкретных типов
2. **Удаление мёртвого кода** — анализ на этапе компиляции, инстанциация только используемых
   дженериков
3. **Замена макросов** — дженерики заменяют 90% сценариев использования макросов
4. **Безопасность типов** — проверка на этапе компиляции, без накладных расходов на типы в runtime
5. **Удобство IDE** — интеллектуальные подсказки, понятные сообщения об ошибках
6. **Типы, зависящие от значений** — типы могут зависеть от значений, поддержка проверки измерений
   на этапе компиляции
7. **Безопасность вычислений на этапе компиляции** — гарантия завершимости вычислений на этапе
   компиляции посредством проверки завершимости (автоматический синтез метрик RFC-027)

### Принципы дизайна

- **Детерминированность на этапе компиляции**: параметры дженериков определяются на этапе компиляции
- **Приоритет мономорфизации**: генерация конкретного кода, избежание вызовов виртуальных функций
- **Ограничения как движущая сила**: ограничения типа направляют инстанциацию
- **Платформенная оптимизация**: специализация для поддержки платформенно-специфичных оптимизаций
- **Единство вселенной типов**: функции/конструкторы типов/типы, зависящие от значений,
  унифицированы на уровне Type2
- **Гарантия завершимости**: вызовы функций в позициях типа должны доказывать завершимость

## Предложение

### 1. Базовые дженерики

#### 1.1 Параметры обобщённого типа

> **Ключевое правило**: определение обобщённого типа **должно явно аннотироваться `: Type`**, иначе
> будет выведено HM как функция.
>
> | Запись                            | Значение                          |
> | --------------------------------- | --------------------------------- |
> | `List: (T: Type) -> Type = {...}` | ✅ Конструктор типа               |
> | `List = {...}`                    | ❌ HM выводит как функцию, не тип |

```yaoxiang
# Определение обобщённого типа (обязательно : Type)
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self
}

List: (T: Type) -> Type = {
    data: Vec(T),
    length: Int,
    push: (self: List(T), item: T) -> Void,   # self — просто соглашение об именовании, не ключевое слово
    get: (self: List(T), index: Int) -> Option(T),
}

# Обобщённая функция (без : Type, HM выводит как функцию)
map: (T: Type, R: Type) -> ((opt: Option(T), f: Fn(T) -> R) -> Option(R)) = {
    return match opt {
        some => Option.some(f(some)),
        none => Option.none(),
    }
}

# Ограничение дженериков (прямое выражение, в одной строке можно опустить return)
clone: (T: Clone)(value: T) -> T = value.clone()

# Несколько параметров типа
combine: (T: Type, U: Type) -> ((a: T, b: U) -> (T, U)) = (a, b)
```

### Синтаксис вызова обобщённых функций

#### 1.1 Унифицированный синтаксис сигнатур

```yaoxiang
# Обобщённые функции используют унифицированный синтаксис сигнатур (T: Type, R: Type)
map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R)) = ...

# Несколько параметров типа
combine: (T: Type, U: Type) -> ((a: T, b: U) -> (T, U)) = (a, b)
```

#### 1.2 Механизм самоописания Type

`Type` — языковой особый объект, компилятор изначально способен распознавать позиции `Type` в
сигнатуре и автоматически выводить и заполнять их из типов фактических аргументов.

```yaoxiang
# Компилятор автоматически выводит параметры дженериков
numbers: List(Int) = List(Int)()
#         ^^^^^^^^   ^^^^^^^^
#         объявление типа   вызов конструктора: Int заполняет T, () — конструкция значения

# Вывод при вызове функции
numbers: List(Int) = List(Int)()
f: (x: Int) -> String = (x) => x.to_string()
strings: List(String) = map(numbers, f)
# Вывод компилятора: T=Int, R=String
```

#### 1.3 Мономорфизация

```yaoxiang
# Исходный код
map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R)) = {
    result: List(R) = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Точки использования
int_list: List(Int) = List(Int)()
doubled: List(Int) = map(int_list, (x: Int) => x * 2)  # Инстанциация map[Int, Int]

string_list: List(String) = List(String)()
uppercased: List(String) = map(string_list, (s: String) => s.to_uppercase())  # Инстанциация map[String, String]

# После компиляции (эквивалентный код)
map_Int_Int: (list: List(Int), f: (Int) -> Int) -> List(Int) = {
    result: List(Int) = List(Int)()
    for x in list {
        result.push(f(x))
    }
    return result
}

map_String_String: (list: List(String), f: (String) -> String) -> List(String) = {
    result: List(String) = List(String)
    for s in list {
        result.push(f(s))
    }
    return result
}
```

````yaoxiang
### 2. Система ограничений типов

#### 2.1 Одиночное ограничение

```yaoxiang
# Базовые определения trait (тип интерфейса)
Clone: Type = {
    clone: (Self) -> Self,
}

Display: Type = {
    fmt: (Self, Formatter) -> Result,
}

Debug: Type = {
    fmt: (Self, Formatter) -> Result,
}

# Использование ограничений: прямое объявление в сигнатуре
clone: (T: Clone) -> (value: T) -> T = value.clone()

debug_print: (T: Debug)(value: T) -> Void = {
    formatter = Formatter.new()
    value.fmt(formatter)
    print(formatter.to_string())
}
````

#### 2.2 Множественные ограничения

```yaoxiang
# Синтаксис множественных ограничений
combine: (T: Clone + Add)(a: T, b: T) -> T = {
    a.clone() + b
}

# Сортировка обобщённого контейнера
sort: (T: Clone + PartialOrd)(list: List(T)) -> List(T) = {
    # Реализация алгоритма сортировки
    result: List(T) = list.clone()
    quicksort(&mut result)
    return result
}

# Ограничения на типы функций
map: (T: Type, R: FnMut(T))(array: Vec(T), f: R) -> Vec(R) = {
    result: Vec(R) = Vec()
    for item in array {
        result.push(f(item))
    }
    return result
}

# Использование
doubled: Vec(Int) = map(Vec(1, 2, 3), (x: Int) => x * 2)  # Вывод компилятора
```

> **Источник имён ограничений (примечание от 2026-09-22)**: ограничения операторов `Add` /
> `Subtract` / `Multiply` / `Divide` / `Modulo` и т.д. определены и реализованы в
> [RFC-011b: Перегрузка операторов и операторы, управляемые интерфейсами](./011b-operator-overloading.md)
> — `T: Add` ≜ зарегистрированная инстанциация интерфейса `Add(T, T, T)` (три параметра типа, тип
> результата `O` явный). `Zero` / `One` / `PartialOrd` / `Fn` / `FnMut` в настоящее время **не имеют
> источника определения** и являются висячими именами ограничений, ожидающими соответствующих RFC
> для каждого; до этого примеры с этими именами — бумажные иллюстрации.

#### 2.3 Ограничения на типы функций

```yaoxiang
# Ограничения на функции высшего порядка
call_twice: (T: Type, F: Fn() -> T)(f: F) -> (T, T) = (f(), f())

call_with_arg: (T: Type, U: Type, F: Fn(T) -> U)(arg: T, f: F) -> U = f(arg)

compose: (A: Type, B: Type, C: Type, F: Fn(A) -> B, G: Fn(B) -> C)(a: A, f: F, g: G) -> C = g(f(a))

# Примеры использования
result: Int = call_with_arg(42, (x: Int) => x * 2)  # result = 84
composed: String = compose(
    "hello",
    (s: String) => s.to_uppercase(),
    (s: String) => s + " WORLD"
)  # composed = "HELLO WORLD"
```

#### 2.4 Встроенные marker trait: Dup и Clone

**Три вида семантики копирования**:

| Тип                                | Значение                                                                                | Способ срабатывания                     | Сценарий применения                |
| ---------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------- |
| **Копирование значения-примитива** | Автоматическое копирование значения при присваивании, два значения полностью независимы | Автоматически при присваивании/передаче | Int, Float, Bool, Char             |
| **Dup**                            | Поверхностное копирование: копирование дескриптора/токена, общие базовые данные         | Автоматически при присваивании/передаче | токены `&T`, `ref T`, String/Bytes |
| **Clone**                          | Глубокое копирование: создание полной независимой копии                                 | `value.clone()`                         | Любой тип, реализующий Clone       |

**Семантика Dup**: типы, реализующие Dup, при присваивании/передаче не передают владение —
компилятор копирует дескриптор/токен, несколько владельцев указывают на одни и те же базовые данные.
Это дополняет семантику Move по умолчанию в модели владения RFC-009.

**Dup и Clone — ортогональные концепции**:

```
Dup = копирование дескриптора, общие данные (изменения влияют друг на друга)
Clone = копирование данных, независимые копии (изменения не влияют друг на друга)
```

**Правила**:

```
1. Типы значений-примитивов (Int, Float, Bool, Char) — встроенное копирование значений компилятором, не Dup
2. Dup — применимо только к типам ссылок/токенов и типам с внутренним подсчётом ссылок
3. Clone — явное глубокое копирование, может реализовать любой тип
4. Move по умолчанию — остальные типы сохраняют семантику Move по умолчанию
```

**Какие типы являются Dup**:

| Тип                                        | Dup         | Причина                                                                             |
| ------------------------------------------ | ----------- | ----------------------------------------------------------------------------------- |
| `&T` (токен заимствования)                 | ✅          | Токен нулевого размера, копирование токена = несколько представлений на одни данные |
| `ref T`                                    | ✅          | Копирование Rc/Arc = счётчик ссылок +1, общие данные в куче                         |
| String, Bytes                              | ✅          | Внутренний подсчёт ссылок, копирование дескриптора разделяет базовый буфер          |
| `&mut T` (токен изменяемого заимствования) | ❌          | Линейная эксклюзивность, нельзя копировать                                          |
| struct                                     | Производное | Все поля Dup → struct Dup                                                           |
| enum                                       | Производное | Все поля всех вариантов Dup → enum Dup                                              |
| tuple                                      | Производное | Все элементы Dup → tuple Dup                                                        |
| Fn (замыкание)                             | ❌          | Захваченное окружение может быть не Dup                                             |
| `*T` (сырой указатель)                     | ❌          | unsafe, не участвует в системе владения                                             |

**Int/Float/Bool/Char не являются Dup** — они являются типами значений, при присваивании компилятор
автоматически копирует значение (два значения полностью независимы). Это не «поверхностное
копирование», а встроенная обработка примитивов компилятором, которая не нуждается и не должна
выражаться через атрибут типа Dup.

```yaoxiang
# Типы значений-примитивов: компилятор автоматически копирует значение (не Dup)
x: Int = 42
y = x          # Копирование значения, x и y полностью независимы
print(x)       # ✅

# Dup: поверхностное копирование, копирование дескриптора разделяет данные
view: &Point = &point
view2 = view    # ✅ Dup: копирование токена, оба указывают на одну и ту же point
print(view.x)   # ✅

# Clone: явное глубокое копирование, создание независимой копии
backup = big_struct.clone()  # Явный вызов

# Ограничения дженериков
dup_use: (T: Dup) -> T = x         # T: Dup → можно поверхностно скопировать
clone_use: (T: Clone) -> T = x.clone()  # T: Clone → можно глубоко скопировать
```

> **Примечание**: `Send`/`Sync` не являются видимыми для пользователя trait. Гарантия безопасности
> между задачами обеспечивается ключевым словом `ref` и полностью автоматической обработкой
> компилятором — `ref` автоматически выбирает Rc или Arc, пользователю не нужно понимать Send/Sync.

#### 3.1 Определение ассоциированного типа

```yaoxiang
# Trait Iterator (с использованием синтаксиса (Item: Type) -> Type)
Iterator: (Item: Type) -> Type = {
    next: (Self) -> Option(Item),
    has_next: (Self) -> Bool,
    collect: (T: Type)(Self) -> List(T),
}

# Использование
collect_all: (T: Type, I: Iterator(T))(iter: I) -> List(T) = {
    result: List(T) = List(T)
    while iter.has_next() {
        if let Some(item) = iter.next() {
            result.push(item)
        }
    }
    return result
}

# Реализация Iterator для Vec
# Используется синтаксический сахар метода: Vec.Item, Vec.next, Vec.has_next
# Позиция итерации переносится обёрточной записью (Vec сам по себе — примитивный буфер, без поля index)
VecIter: (T: Type) -> Type = {
    data: &Vec(T),
    index: Int,
}

VecIter.has_next: (T: Type)(self: &VecIter(T)) -> Bool = {
    return self.index < self.data.length
}

VecIter.next: (T: Type)(self: &mut VecIter(T)) -> Option(T) = {
    if self.index < self.data.length {
        item = self.data[self.index]
        self.index = self.index + 1
        return Option.some(item)
    } else {
        return Option.none()
    }
}

VecIter.Item: (T: Type)(arr: &VecIter(T)) -> T = {
    return arr.data[arr.index]
}
```

### 4. Дженерики времени компиляции

#### 4.1 Параметры-значения времени компиляции

**Основной дизайн**: `Type` в сигнатуре дженериков помечает параметры типа; параметры,
аннотированные конкретными типами (`Int`/`Bool`/`Float` и т.д.), рассматриваются как **кандидаты в
параметры-значения времени компиляции**. Станут ли они параметрами-значениями времени компиляции,
зависит от того, **упоминаются ли их значения в позиции типа** (зависимость от значения). Ключевое
слово `const` не требуется.

> Критерий — **упоминание в позиции типа**, а не «аннотация конкретного типа»: в
> `add: (a: Int, b: Int) -> Int = a + b` параметры `a`/`b` — параметры-значения runtime, так как они
> не встречаются ни в одной позиции типа.

**Правило определения (два шага)**:

1. **Грубая фильтрация по форме**: параметр аннотирован конкретным типом, отличным от `Type`
   (например, `Int`) → в список кандидатов.
2. **Точная фильтрация по использованию**: имя кандидата встречается в **позиции типа** (тип поля
   тела типа, тип параметра внутренней `Fn`, предикат `Assert`, позиция аргумента конструктора типа,
   такая как `Array(T, N)`) → подтверждается как параметр-значение времени компиляции; иначе
   рассматривается как **параметр-значение runtime**.

| Запись                                                     | Определение                              | Причина                                                                    |
| ---------------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| `add: (a: Int, b: Int) -> Int = a + b`                     | a/b — параметры-значения runtime         | Встречаются только в позиции значения, не участвуют в конструировании типа |
| `Array: (T: Type, N: Int) -> Type = { data: Array(T, N) }` | N — параметр-значение времени компиляции | N встречается в позиции аргумента конструктора типа `Array(T, N)`          |
| `factorial: (N: Int) -> (k: N) -> Int`                     | N — параметр-значение времени компиляции | N выступает типом внутреннего параметра `k`                                |
| `Foo: (T: Type, N: Int) -> Type = { x: T }`                | N пропадает (см. ниже)                   | N не упомянут в теле типа, вырождается в параметр-значение runtime         |

> **Суть зависимости от значения**: параметр-значение времени компиляции есть тип, зависящий от
> значения — только когда значение используется для **конструирования типа**, требуется его
> определённость на этапе компиляции. Форма (`: Int`) определяет лишь кандидатуру, использование
> (появление в позиции типа) определяет, является ли он параметром-значением времени компиляции. Это
> тот же критерий, что и в §«Гарантия детерминированности на этапе компиляции» — «вызовы функций в
> позициях типа вычисляются на этапе компиляции».

```yaoxiang
# ════════════════════════════════════════════════════════
# Параметр-значение времени компиляции: N упомянут в позиции типа (слот длины Measure)
# ════════════════════════════════════════════════════════
Measure: (T: Type, N: Int) -> Type = {
    data: Array(T, N),  # N встречается в позиции аргумента конструктора типа → параметр-значение времени компиляции
    length: N,
}

# Использование: factorial(5) вычисляется в позиции типа (этап компиляции), результат 120 встраивается в тип
m: Measure(Int, factorial(5))  # Measure(Int, 120)

# ════════════════════════════════════════════════════════
# Зависимость от значения: N выступает типом внутреннего параметра k
# ════════════════════════════════════════════════════════
# N — параметр-значение времени компиляции (встречается в позиции типа (k: N));
# k — параметр-значение runtime, его тип — литеральный тип N (однозначный тип).
factorial: (N: Int) -> (k: N) -> Int = {
    return match k {
        0 => 1,
        _ => k * factorial(k - 1)
    }
}
```

> **Обработка пропавших кандидатов**: кандидаты, аннотированные конкретным типом, но не упомянутые в
> позиции типа (например, `N` в `Foo` выше), вырождаются в параметры-значения runtime (путь уровня
> функции). Пропавшие кандидаты на пути конструктора типа не могут занять слот runtime (конструктор
> типа вычисляется на этапе компиляции), на стороне объявления сразу выдаётся ошибка [E1094]: «N
> объявлен как параметр-значение времени компиляции, но не упомянут в теле типа» — ранее тихое
> отбрасывание приводило к несогласованности arity инстанциации.

### Never и Void: ⊥ и ⊤ в системе типов

Система типов YaoXiang в изоморфизме Карри-Ховарда одновременно обладает ⊥ (ложь/пустой тип) и ⊤
(истина/Unit), выражаемыми двумя встроенными именами типов: `Never` и `Void`:

**Never (⊥)** — три непреложных ядерных свойства:

1. **Нулевой набор конструкторов**: ни один литерал или выражение не может породить значение типа
   `Never`. Это мета-свойство, должно быть встроенным.
2. **Принцип взрыва**: `Never <: T` выполняется для любого типа `T`. Значение `Never` может
   использоваться как значение любого типа — именно поэтому код после `assert(false)` проходит
   проверку типов (хотя никогда не выполнится).
3. **Маркер расходимости**: `f: (...) -> Never` означает, что `f` гарантированно не возвращается.
   Компилятор использует это для анализа мёртвого кода.

`Never` — встроенное имя типа, не ключевое слово, парсер не делает различий. Не открывается
синтаксис пустых и типовых литералов.

**Void (⊤, т.е. Unit)** — ровно один обитатель (значение void по умолчанию), носитель истинного
proposition «всегда истинно». `Void` является единицей для типов пустого произведения, `Never` —
единицей для типов пустого суммирования — они двойственны. `x: Void = <по умолчанию>` допустимо,
`x: Never = ...` не имеет правой части для записи.

#### 4.3 Проверки на этапе компиляции (реализация в стандартной библиотеке)

```yaoxiang
# ════════════════════════════════════════════════════════
# Реализация в стандартной библиотеке: использование условных типов
# ════════════════════════════════════════════════════════

# Определения в стандартной библиотеке
# IsTrue: мост от вселенной значений ко вселенной типов — истинностное значение Bool отображается в тип
IsTrue: (b: Bool) -> Type = match b {
    true => Void,      # ⊤, имеет значение, программа продолжается
    false => Never,    # ⊥, нет значения, расходимость
}

# Assert: примитив уточнённого типа на этапе компиляции — типовое выражение proposition Bool
Assert: (cond: Bool) -> Type = IsTrue(cond)
#
# cond = true  → Assert(true)  = Void    (всегда истинно, стирается)
# cond = false → Assert(false) = Never   (всегда ложно, ошибка компиляции/расходимость)
# cond неразрешимо → конвейер доказательства решает по режиму dispatch:
#                    CompileTime → Unknown, требуется prove
#                    Runtime     → вставляется check, добавляется предположение Γ

# Способ использования 1: как ограничение в определении типа
Bounded: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    # Проверка на этапе компиляции: N должно быть больше 0 (Assert в позиции типа)
    length: Assert(N > 0),
}

# Способ использования 2: в выражениях
IntArray: (N: Int) -> Type = Array(Int, N)
# Проверка: размер IntArray(10) равен sizeof(Int) * 10
Assert(size_of(IntArray(10)) == sizeof(Int) * 10)
```

### 5. Условные типы

> **Изоморфизм Карри-Ховарда**: условные типы с точки зрения Карри-Ховарда представляют
> **case-анализ** в логике. Тип `Bool` соответствует proposition с двумя возможными значениями
> (True/False), `If` в зависимости от истинности proposition выбирает разные результаты — это и есть
> дизъюнктный case-анализ в логике. `match C { True => T, False => E }` фактически выражает: «при
> известном proposition C = True заключение T, при C = False заключение E».

#### 5.1 Условный тип If

```yaoxiang
# If на уровне типов
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Пример: ветвление на этапе компиляции
NonEmpty: (T: Type) -> Type = If(T != Void, T, Never)

Optional: (T: Type) -> Type = If(T != Void, T, Void)

# Проверка на этапе компиляции (унифицирована с определением Assert из §4.3)
# Assert: (cond: Bool) -> Type = IsTrue(cond)

# Использование
# Вычисление типа: If(True, Int, String) => Int
# Вычисление типа: If(False, Int, String) => String
```

#### 5.2 Семейства типов

> **Изоморфизм Карри-Ховарда**: семейства типов — самое прямое проявление «proposition как тип».
> `Add: (A: Type, B: Type) -> Type` — это не «написали функцию сложения на уровне типов», а
> **конструирование proposition о сложении натуральных чисел**. `(Zero, B) => B` говорит
> «proposition Add(Zero, B) эквивалентно B», `(Succ(A'), B) => Succ(Add(A', B))` говорит «если
> Add(A', B) выполняется, то Add(Succ(A'), B) тоже выполняется». Это и есть определение сложения в
> аксиомах Пеано. Проверка типов, подтверждающая прохождение этого match-выражения, эквивалентна
> проверке логической согласованности этого определения.

```yaoxiang
# Преобразование типов на этапе компиляции
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,  # По умолчанию
}

# Вычисления на уровне типов
Length: (T: Type) -> Type = match T.length {
    0 => Zero,
    1 => Succ(Zero),
    2 => Succ(Succ(Zero)),
    _ => TooLong,
}

# Сложение на уровне типов (Карри-Ховард: case-анализ + рекурсивный вызов, требует проверки завершимости для полной индукции)
Add: (A: Type, B: Type) -> Type = match (A, B) {
    (Zero, B) => B,
    (Succ(A'), B) => Succ(Add(A', B)),
}

# Пример: вычисление 2 + 3 на этапе компиляции
Two: Type = Succ(Succ(Zero))
Three: Type = Succ(Succ(Succ(Zero)))
Five: Type = Add[Two, Three]  # Succ(Succ(Succ(Succ(Succ(Zero)))))
```

#### 6.3 Идеальное сочетание перегрузки функций и инлайнинга


**Ключевые преимущества**:

1. **Интеллектуальный выбор компилятора**

   ```yaoxiang

   sum(float_arr)    # Автоматически выбирает sum: (Vec(Float)) -> Float
   sum(custom_arr)  # Автоматически выбирает sum: (T: Type) -> ((arr: Vec(T)) -> T)
   ```

2. **Оптимизация инлайнинга**
   - Малые функции автоматически инлайнятся в точку вызова
   - Нулевые накладные расходы на вызов функции
   - Полностью эквивалентно ручному оптимизированному коду

3. **Безопасность типов**
   - Проверка типов на этапе компиляции
   - Нулевые накладные расходы в runtime
   - Таблица виртуальных функций не требуется

4. **Идеально соответствует RFC-010**

   ```yaoxiang

   name: type = value
   # Новые ключевые слова, такие как impl, where, не нужны
   ```

````
#### 7.1 Анализ графа инстанциации

```rust
// Внутри компилятора: построение графа зависимостей инстанциации дженериков
struct InstantiationGraph {
    // Узлы: инстанциации дженериков
    nodes: HashMap<InstanceKey, InstanceNode>,

    // Рёбра: отношения использования
    edges: HashMap<InstanceKey, Vec<InstanceKey>>,
}

struct InstanceKey {
    generic: FunctionId,  // ID обобщённой функции
    type_args: Vec<TypeId>,  // Аргументы типа
    const_args: Vec<ConstId>,  // Аргументы Const
}

// Алгоритм: анализ достижимости
fn eliminate_dead_instantiations(graph: &InstantiationGraph) {
    let mut reachable = HashSet::new();

    // Начинаем с точек входа (main, экспортируемые функции и т.д.)
    let entry_points = find_entry_points();
    for entry in entry_points {
        dfs_visit(entry, &graph, &mut reachable);
    }

    // Не посещённые инстанциации — мёртвый код
    for node in &graph.nodes {
        if !reachable.contains(node.key) {
            eliminate(node);
        }
    }
}
````

> [RFC-011b](./011b-operator-overloading.md) — основная запись `Add(Int, Float, Float)` и запись
> `(Int, Float) => Float` в этой таблице — одно и то же правило, каждая инстанциация интерфейса
> пользователем добавляет строку в эту таблицу. `Add` Пеано на уровне типов из §5.2 — чисто
> вычислительный на уровне типов (однофамилец, но другой объект), не взаимодействующий с
> интерфейсами операторов на уровне значений — запрос оператора обращается к реестру реализаций,
> минуя разрешение имён.

#### 9.1 Полный пример обобщённого контейнера

```yaoxiang
# ======== 1. Определение обобщённого контейнера ========
# Использование синтаксиса (T: Type) -> Type
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

List: (T: Type) -> Type = {
    data: Vec(T),
    length: Int,

    # Обобщённые методы (T автоматически попадает в область видимости из внешнего List(T))
    push: (self: List(T), item: T) -> Void,
    pop: (self: List(T)) -> Option(T),
    map: (R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)),
    filter: (self: List(T), predicate: (T) -> Bool) -> List(T),
    fold: (U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U),
}

# ======== 2. Реализация обобщённых методов ========
# Определения функций находятся в пространстве имён List (префикс List. = принадлежность пространству имён)
# Чтобы синтаксис вызова через . работал для list.push(item), требуется явная привязка: List.push = push[0]
# self — просто соглашение об именовании параметра, компилятор смотрит на тип, а не на имя

List.push: (T: Type) -> ((self: List(T), item: T) -> Void) = {
    if self.length >= self.data.length {
        # Расширение
        new_data = Vec(T)(len=self.data.length * 2)
        for i in 0..self.length {
            new_data[i] = self.data[i]
        }
        self.data = new_data
    }
    self.data[self.length] = item
    self.length = self.length + 1
}

List.pop: (T: Type) -> ((self: List(T)) -> Option(T)) = {
    if self.length > 0 {
        self.length = self.length - 1
        return Option.some(self.data[self.length])
    } else {
        return Option.none()
    }
}

List.map: (T: Type, R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)) = {
    result = List(R)()
    for i in 0..self.length {
        result.push(f(self.data[i]))
    }
    return result
}

List.filter: (T: Type) -> ((self: List(T), predicate: (T) -> Bool) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        if predicate(self.data[i]) {
            result.push(self.data[i])
        }
    }
    return result
}

List.fold: (T: Type, U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U) = {
    result = initial
    for i in 0..self.length {
        result = f(result, self.data[i])
    }
    return result
}

# ======== 3. Использование ограничений типа ========
# Реализация Clone для List
List.clone: (T: Clone) -> ((self: List(T)) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        result.push(self.data[i].clone())
    }
    return result
}

# ======== 4. Примеры использования ========
# Создание обобщённого List
numbers = List(Int)()
numbers.push(1)
numbers.push(2)
numbers.push(3)

# Использование обобщённых методов

evens = numbers.filter((x) => x % 2 == 0)

# Использование fold для вычисления

# Композиция обобщённых методов

    .filter((x) => x % 2 == 0)
    .map((x) => x * 2)
    .fold(0, (acc, x) => acc + x)  # sum_of_evens = 8
```

```yaoxiang
# ======== 1. Обобщённый алгоритм сортировки ========
Comparator: (T: Type) -> Type = {
    compare: (T, T) -> Int,  # -1 if a < b, 0 if a == b, 1 if a > b
}

# Обобщённая быстрая сортировка
quicksort: (T: Clone) -> ((array: Vec(T), cmp: Comparator(T)) -> Vec(T)) = {
    if array.length <= 1 {
        return array.clone()
    }

    pivot = array[array.length / 2]
    left = Vec(T)()
    right = Vec(T)()

    for i in 0..array.length {
        if i == array.length / 2 {
            continue
        }
        item = array[i]
        comparison = cmp.compare(item, pivot)
        if comparison < 0 {
            left.push(item)
        } else {
            right.push(item)
        }
    }

    sorted_left = quicksort(left, cmp)
    sorted_right = quicksort(right, cmp)

    result = sorted_left.clone()
    result.push(pivot)
    result.extend(sorted_right)
    return result
}

# ======== 2. Реализация IntComparator ========
# Реализация через перегрузку функций
compare: (a: Int, b: Int) -> Int = {
    if a < b {
        return -1
    } else if a > b {
        return 1
    } else {
        return 0
    }
}

# ======== 3. Примеры использования ========
# Сортировка массива Int

# Сортировка массива String (требует StringComparator)
```

```yaoxiang
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),

    # Проверка измерений на этапе компиляции: с использованием типа Assert стандартной библиотеки
    _assert: Assert(Rows > 0),  # Rows > 0, иначе ошибка компиляции
    _assert: Assert(Cols > 0),  # Cols > 0, иначе ошибка компиляции

    # Операции над матрицами
    multiply: (M: Int) -> ((self: Matrix(T, Rows, Cols), other: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)) = {
        result = Matrix(T, Rows, M)()
        for i in 0..Rows {

                for k in 0..Cols {

                }
                result.data[i][j] = sum
            }
        }
        return result
    }
}

            if i == j {

            } else {

            }
```

## Компромиссы

### Преимущества

1. **Абстракции с нулевой стоимостью**
   - Мономорфизация на этапе компиляции, без накладных расходов в runtime
   - Виртуальные функции не нужны, RTTI не нужен

2. **Удаление мёртвого кода**
   - Анализ на этапе компиляции, инстанциация только используемых дженериков
   - Раздувание кода контролируемо

3. **Замена макросов**
   - Генерация типобезопасного кода
   - Удобно для IDE, понятные сообщения об ошибках

4. **Вычисления на этапе компиляции**
   - Дженерики на этапе компиляции поддерживают вычисления на этапе компиляции
   - Возможности вроде проверки измерений
   - Ключевое слово `const` не нужно, только ограничения типа

### Недостатки

1. **Время компиляции**
   - Инстанциация дженериков увеличивает время компиляции
   - Решение ограничений может быть медленным

2. **Потребление памяти**
   - Увеличивается потребление памяти компилятором
   - Механизмы кеширования требуют памяти

3. **Сложность реализации**
   - Решатель ограничений сложен
   - Движок вычислений на уровне типов сложен

4. **Диагностика ошибок**
   - Ошибки дженериков могут быть сложными
   - Требуются понятные подсказки об ошибках

### Меры по смягчению

1. **Стратегия кеширования**
   - Кеширование результатов инстанциации
   - LRU-кеш для ограничения памяти

2. **Инкрементальная компиляция**
   - Кеширование результатов компиляции
   - Инкрементальная инстанциация

3. **Подсказки об ошибках**
   - Понятные сообщения об ошибках
   - Подсказки для вывода параметров дженериков

4. **Параллельная компиляция**
   - Параллельная инстанциация дженериков
   - Многопоточное решение ограничений

## Альтернативы

| Альтернатива                   | Почему не выбрана                                   |
| ------------------------------ | --------------------------------------------------- |
| Только базовые дженерики       | Невозможно заменить сложные макросы                 |
| Чисто макросная система        | Нет безопасности типов, плохие сообщения об ошибках |
| Только ограничения-зависимости | Недостаточная гибкость                              |
| Дженерики в runtime            | Накладные расходы на производительность             |

### Риски

| Риск                          | Воздействие                  | Мера по смягчению              |
| ----------------------------- | ---------------------------- | ------------------------------ |
| Сложность решения ограничений | Слишком долгая компиляция    | Инкрементальное решение + кеш  |
| Раздувание кода               | Слишком большой бинарник     | DCE + управление порогом       |
| Сложность реализации          | Удлинение цикла разработки   | Поэтапная реализация           |
| Диагностика ошибок            | Плохой пользовательский опыт | Подробные сообщения об ошибках |

## Приложение

### BNF синтаксиса

```bnf
# Параметры дженериков используют унифицированный синтаксис () как часть типа функции
# Например, map: (T: Type, R: Type) -> ((list: List(T), f: (T) -> R) -> List(R))

# Ограничение типа (в параметрах дженериков)
type_bound ::= identifier
             | identifier '+' identifier ('+' identifier)*

# Объявление параметра (тип + имя)
parameter ::= identifier ':' type

parameters ::= parameter (',' parameter)*

# Объявление функции: name: type = expression
# Параметры дженериков — первая группа параметров типа функции: (T: Type) -> ((params) -> return)
function ::= identifier ':' type '=' (expression | block)

# Объявление метода: Type.method: type = expression
method ::= identifier '.' identifier ':' type '=' (expression | block)

# Определение типа (унифицированный синтаксис Binding)
# Обобщённый тип, например List: (T: Type) -> Type = { ... }
generic_type ::= identifier ':' type '=' type_expression

# Type в параметрах дженериков автоматически заполняется компилятором из типов фактических аргументов
# Например, в map(numbers, f), T извлекается из numbers: List(Int), R — из f: (Int) -> String
```
