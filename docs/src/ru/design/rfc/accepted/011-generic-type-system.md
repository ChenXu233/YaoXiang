# RFC-011: Система дженериков — абстракции с нулевой стоимостью и замена макросов

## Резюме

Документ определяет **дизайн системы дженериков** языка YaoXiang, реализующей абстракции с нулевой
стоимостью за счёт мощных возможностей дженериков, использующей оптимизации времени компиляции для
снижения зависимости от макросов и предоставляющей механизм устранения мёртвого кода.

**Ключевые решения**：

- **Единый синтаксис сигнатур**：`(T: Type, R: Type) -> ...` — параметры дженериков и обычные
  параметры унифицированы
- **Механизм самоописания `Type`**：`Type` — это языковой особый объект, позиции `Type` в сигнатуре
  могут быть автоматически выведены и заполнены
- **Ограничения типов**：`T: Dup + Add` — множественные ограничения, ограничения функциональных
  типов
- **Ассоциированные
  типы**：`Iterator: (Item: Type) -> Type = { next: () -> Option(Item), has_next: () -> Bool }`
- **Дженерики времени компиляции**：значение-параметр дженериков `N: Int`, инстанцирование
  константами времени компиляции
- **Условные типы**：`If: (C: Bool, T: Type, E: Type) -> Type` — вычисления на уровне типов,
  семейства типов

**Ценность**：

- Абстракции с нулевой стоимостью: мономорфизация на этапе компиляции, без накладных расходов в
  runtime
- Устранение мёртвого кода: анализ графа инстанцирования + оптимизации LLVM
- Замена макросов: дженерики заменяют 90% сценариев использования макросов
- Безопасность типов: проверка на этапе компиляции, удобство для IDE
- **Явное лучше неявного**: `Type` самоописывающий, компилятор выполняет автоматический вывод

## Идея вселенной типов и зависимые от значений типы

Система дженериков YaoXiang построена на **идее вселенной типов**. Эта ментальная модель объединяет
все концепции языка в иерархическую структуру; ключевая инновация — превращение **зависимых от
значений типов** (value-dependent types) в полноправных граждан уровня Type2.

### Что такое зависимые от значений типы?

**Зависимый от значения тип** — это тип, который зависит от одного или нескольких **значений** (а не
только от других типов). Эти значения могут быть вычислены на этапе компиляции, тем самым
обеспечивая гарантии безопасности типов уже на стадии компиляции.

```yaoxiang
# Традиционные дженерики: параметр-тип
List: (T: Type) -> Type

# Зависимый от значения тип: значение-параметр
Array: (T: Type, N: Int) -> Type  # Тип массива зависит от значения длины N
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type  # Тип матрицы зависит от числа строк и столбцов
```

### Именование контейнерных типов по уровням

На уровне языка существуют три контейнерные концепции, и место хранения информации о длине — их
фундаментальное различие：

| Тип           | Длина            | Семантика                                                   | Базовая реализация                          |
| ------------- | ---------------- | ----------------------------------------------------------- | ------------------------------------------- |
| `Array(T, N)` | Тип              | **Фиксированной длины** массив, N содержится в типе         | Базовый примитив (стек/инлайн в приоритете) |
| `Vec(T)`      | Значение runtime | **Буфер сырого размера, известного в runtime**, может расти | Базовый примитив (непрерывный буфер в куче) |
| `List(T)`     | Значение runtime | Стандартный библиотечный тип                                | Библиотека: `{ data: Vec(T), length: Int }` |

Принципы разделения ответственности：

- **`Array(T, N)` — единственная форма, помещающая длину в тип** — длина является константой времени
  компиляции, поэтому возможен отказ на этапе компиляции при ошибке границы (`a[5]` при
  `a: Array(Int, 3)` напрямую даёт ошибку компиляции, см. раздел «Верификация измерений времени
  компиляции» ниже).
- **`Vec(T)` — минимальный фундамент длины, известной в runtime** — предоставляет только четыре
  вещи: «уметь выделить, уметь получить длину, уметь читать/писать, уметь расширить». Никакой
  политики ёмкости, фактора роста, сжатия. Это сырьё для построения других контейнеров.
- **`List(T)` — библиотечный тип, а не примитив** — определяется на самом YaoXiang в `std.list`
  (`{ data: Vec(T), length: Int }`) наравне с пользовательскими дженерик-записями. Вся политика
  расширяемой семантики (когда расширять, на сколько, можно ли разделять) находится в библиотеке;
  компилятор не участвует.

Конструктивные формы `Vec(T)` (двухуровневые: сначала параметры типа, затем параметры конструкции)：

```yaoxiang
# Пустая конструкция — длина 0, элементы добавляются позже
v = Vec(Int)()

# Элементная конструкция — длина определяется числом элементов
w = Vec(Int)(1, 2, 3)          # Длина 3

# Слотовое выделение — выделяет n нулевых слотов
buf = Vec(Int)(len=64)         # Длина 64, все элементы — нулевые значения
```

> Слотовое выделение использует **форму с именем поля** (`len=`), а не позиционную: позиционная
> форма с одним целым неоднозначна с «одноэлементным вектором» (`Vec(Int)(64)` неотличимо от «длина
> 64» и «один элемент 64»). Это согласуется с единым правилом дженерик-конструкции: именованные
> аргументы связываются по имени и не зависят от позиционного вывода.
>
> Это единственный примитив, необходимый `List` для расширения — `List` при необходимости выделяет
> новые слоты и перемещает элементы：
>
> ```yaoxiang
> new_data = Vec(T)(len=self.data.length * 2)
> ```
>
> Когда расширять, на сколько, сжимать ли — всё решает `List`. `Vec` не занимается политикой
> ёмкости.

Снизу вверх производительность убывает, гибкость возрастает：`Array` > `Vec` > `List`.

> Обоснование имён：`Vec`/`vector` в основных языках (Rust/C++) обозначают расширяемую
> последовательность, длина которой известна в runtime; `Array` обозначает фиксированную длину.

### Ключевые преимущества зависимых от значений типов

По сравнению с традиционными дженериками, зависимые от значений типы YaoXiang обладают следующими
ключевыми преимуществами：

| Свойство                          | Традиционные дженерики (C++/Rust)               | Зависимые от значений типы YaoXiang                                    |
| --------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| Значения, от которых зависят типы | Только параметры-типы                           | Любые значения, включая результаты вызовов функций                     |
| Вычисление времени компиляции     | C++ — ручная специализация шаблонов, Rust — нет | Автоматическое вычисление, гарантированная завершимость                |
| Вычисления на уровне типов        | Метапрограммирование шаблонов (сложно/опасно)   | Единый движок вычислений на уровне типов                               |
| Безопасность типов                | C++ — нет, Rust — ограниченная                  | Полная безопасность типов, проверка на этапе компиляции                |
| Верификация измерений             | Проверка в runtime или ручная специализация     | Автоматическая верификация на этапе компиляции, без накладных расходов |

### Уровни вселенной типов и зависимые от значений типы

Идея вселенной типов разделяет языковые концепции по семантической роли на разные уровни. Зависимые
от значений типы расположены на **уровне Type2**：

| Уровень   | Роль                                                          | Примеры                                                                                                         |
| --------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Type-1    | Значения                                                      | `42`, `factorial(5)`, сама функция                                                                              |
| Type0     | Ключевое слово метатипа                                       | `Type`                                                                                                          |
| Type1     | Конкретные типы                                               | `Int`, `String`, `Array(Int, 3)`                                                                                |
| **Type2** | **Функции / конструкторы типов / зависимые от значений типы** | `add: (Int, Int) -> Int`, `Array: (T: Type, N: Int) -> Type`, `Matrix: (T: Type, Rows: Int, Cols: Int) -> Type` |

**Ключевое решение**：функции, конструкторы типов и зависимые от значений типы на уровне Type2 имеют
**единый синтаксис** — форму `(params) -> result`：

- Обычная функция：`(Int, Int) -> Int` → результат — значение
- Конструктор типа：`(T: Type) -> Type` → результат — тип
- Зависимый от значения тип：`(T: Type, N: Int) -> Type` → результат — тип, зависящий от
  значение-параметра N

> **Изоморфизм Карри — Ховарда**：это единство не случайно. Изоморфизм Карри — Ховарда утверждает
> «типы суть propositions, программы суть доказательства» — функциональный тип `A → B` соответствует
> логической импликации «если A, то B»; дженерики `(T: Type) -> Type` соответствуют квантору
> всеобщности «для всех типов T»; зависимый от значения тип `(n: Int) -> Type` соответствует «для
> каждого целого n существует тип». YaoXiang объединяет функции, конструкторы типов и зависимые от
> значений типы на уровне Type2, по существу объединяя «доказательство» и «вычисление» в одну
> концепцию — **конструктивное доказательство**. Это прямое воплощение изоморфизма Карри — Ховарда в
> дизайне языка: одна форма (`(params) -> result`) одновременно несёт логические propositions и
> вычислительный процесс.

### Гарантия определённости времени компиляции

Идея вселенной типов YaoXiang требует：**всё на уровне Type определено на этапе компиляции**.

```yaoxiang
# Пример верификации измерений времени компиляции
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),
    # Проверка времени компиляции: измерения должны быть положительными
    _assert: Assert(Rows > 0),
    _assert: Assert(Cols > 0),
}

# Создание единичной матрицы 3x3 — выполняется на этапе компиляции
identity: (T: Add + Zero + One, N: Int) -> ((size: N) -> Matrix(T, N, N)) = {
    matrix = Matrix(T, N, N)()
    # ...
}

# Вычисление времени компиляции: factorial(3) = 6, размер массива определён на этапе компиляции
arr: Array(Int, factorial(3)) = Array(Int, 6)()
```

Компилятор автоматически：

1. Обнаруживает вызовы функций в позиции типа
2. Выполняет проверку завершимости на этапе компиляции (см. механизм проверки завершимости ниже)
3. Выполняет вычисление на этапе компиляции
4. Встраивает результат в порождаемый тип

### Сценарии применения зависимых от значений типов

#### Верификация измерений времени компиляции

```yaoxiang
# Умножение матриц: верификация совпадения измерений на этапе компиляции
multiply: (T: Add + Multiply + Zero,
           Rows: Int, Cols: Int, M: Int) -> ((
    a: Matrix(T, Rows, Cols),
    b: Matrix(T, Cols, M)
) -> Matrix(T, Rows, M)) = {
    # Проверка времени компиляции: a.Cols == b.Rows, иначе ошибка компиляции
    result = Matrix(T, Rows, M)()
    # ...
}

# Ошибка перехватывается на этапе компиляции：
# multiply(matrix_2x3, matrix_4x2)  # Ошибка компиляции: 2 != 4
```

#### Типобезопасный размер массива

```yaoxiang
# Размер массива — константа времени компиляции
Array: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    length: N,
}

# N — константа времени компиляции, может использоваться в вычислениях уровня типов
first_three: Array(Int, 3) = Array(Int, 3)(1, 2, 3)
# first_three.length == 3 (известно на этапе компиляции)
```

#### Целевой механизм покрытия ошибок границ на этапе компиляции

> **Пояснение о состоянии реализации**：контейнерные типы уже деспециализированы — `Array(T, N)` —
> это конструктор-конст-дженерик, точка привязки литерального контекста и предикат членства `in` уже
> реализованы. N и тип элементов в точке привязки литерала `Array(T, N)` уже принудительно
> проверяются на этапе компиляции (E1002), **N считается достоверным** — механизмы этой главы могут
> строиться на аннотации «N == длина в runtime». Текущие выход за границы при индексации `[]`
> (E6003) и отсутствующий ключ Dict (E6008) находятся в **переходном состоянии ошибок runtime**;
> Цель зависимых от значений типов в этом разделе — перенести эти ошибки границ на **этап
> компиляции**：
>
> - конст-индексация：`a[5]` (5 — константа времени компиляции) при `a: Array(Int, 3)` напрямую
>   отвергается на этапе компиляции；
> - значение-индексация：`a[i]` требует предусловия `i < len(a)`, доказуемого по контракту
>   зависимого от значения типа；
> - предикат `in` — основа предусловий логики Хоара：`n in 1..10`, `x in some_set` — это
>   propositions, доказуемые на этапе компиляции.
>
> Полный дизайн уточнённых типов будет дополнен этим разделом при его конкретизации.

#### Условные типы

```yaoxiang
# Уровневый If
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Семейства типов
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,
}
```

#### Дженерик-функции

```yaoxiang
# map: дженерик-функция, параметры типов T, R определяются на этапе компиляции
map: (T: Type, R: Type) -> (
    (list: List(T), f: (x: T) -> R) -> List(R)
) = (list, f) => {
    result = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Использование полностью прозрачно, типы выводятся автоматически
numbers = List(Int)()   # Двухуровневая форма конструкции значения (см. §9.1); элементы заполняются через push
numbers.push(1)
numbers.push(2)
numbers.push(3)
doubled = map(numbers, (x) => x * 2)  # Выводится как map[Int, Int]
```

### Механизм проверки завершимости (унифицирован с RFC-027)

Вычисление на этапе компиляции для зависимых от значений типов должно **гарантировать
завершимость**, иначе система типов попадёт в бесконечный цикл. Проверка завершимости выполняется
**полностью автоматически** конвейером доказательств времени компиляции RFC-027 — компилятор
автоматически синтезирует меры; рекурсии/циклы, которые удаётся доказать, проходят, не поддающиеся
доказательству сразу дают ошибку компиляции. **Полуавтоматическим аннотациям лазеек не
оставляется**：`//! decreases`, `/*! invariant !*/` из RFC-022 отменены вместе с RFC-022;
спецификация — это сама аннотация типа.

#### Проверка завершимости рекурсивных функций

Перед вычислением времени компиляции компилятор проверяет, что аргументы рекурсивных вызовов строго
убывают на каждом пути рекурсии (RFC-027 §6.7). Никаких комментариев спецификации не требуется：

```yaoxiang
# Факториал времени компиляции: без //! requires/ensures/decreases, компилятор анализирует автоматически
factorial: (n: Int) -> Int = {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)  # Компилятор анализирует: n-1 < n → убывает → завершается
}

# Использование: вызов в позиции типа, компилятор сначала проверяет завершимость, затем вычисляет
arr: Array(Int, factorial(5)) = Array(Int, 120)()  # Вычисление времени компиляции factorial(5) = 120
```

| Сценарий                                                              | Поведение                          |
| --------------------------------------------------------------------- | ---------------------------------- |
| Компилятор может проанализировать убывание рекурсии (например, `n-1`) | Вычисление времени компиляции      |
| Не убывает / не удаётся определить убывание                           | Ошибка компиляции                  |
| Вызов в runtime (не в позиции типа)                                   | Проверка завершимости не требуется |

#### Проверка завершимости циклов

Циклам не нужны аннотации `: Invariant(...)` или `: decreases(...)`. Аннотации уточнённых типов на
переменных (например, `UpTo(n)`) одновременно задают инвариант цикла и границу меры. Компилятор по
приоритету пробует четыре стратегии синтеза мер и останавливается на первой успешной (RFC-027 §7)：

1. **Автоматический синтез линейной ранговой функции** — извлечение границ переменных из аннотаций
   типов, перебор линейных комбинаций, SMT-верификация m ≥ 0 и m' < m на всех путях
2. **Подсчёт нарушений предиката** (экспериментально) — извлечение violation_count из определения
   целевого типа (например, `Sorted`), покрытие соседних обменов/перемещений
3. **Шаблон ограниченного инкремента/декремента** — `v += const` → мера `upper - v` (вырождение
   стратегии 1, самый быстрый путь)
4. **Шаблон мультипликативной меры** — `v *= const` (const > 1) → мера `ceil(log_const(upper / v))`

```yaoxiang
sum: (arr: Array(Int, n)) -> Int = {
    mut i: UpTo(arr.len) = 0   # Аннотация типа задаёт верхнюю arr.len и нижнюю 0 границы
    while i < arr.len {
        # Компилятор автоматически выводит: мера arr.len - i, на каждой итерации строго убывает на 1 → завершимость доказана
        s += arr[i]; i += 1
    }
    return s
}
```

#### Преимущества

- **Безопасность**：гарантированная завершимость вычислений времени компиляции, защита системы типов
  от бесконечных циклов
- **Единообразие**：проверка завершимости и верификация корректности (генерация VC) используют общий
  конвейер доказательств времени компиляции (RFC-027), без отдельного синтаксиса спецификаций
- **Полная автоматизация**：компилятор автоматически синтезирует меры из аннотаций типов; доказуемое
  — проходит, недоказуемое — выдаёт ошибку — без необходимости в `decreases` от программиста

## Мотивация

### Зачем нужна мощная система дженериков?

Существующие системы дженериков в mainstream-языках имеют ограничения：

| Язык         | Возможности дженериков         | Проблема                                                                                              |
| ------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Java         | Ограниченные типы              | Мономорфизация на этапе компиляции, нет специализации                                                 |
| C#           | Ограничения дженериков         | Проверка типов в runtime, накладные расходы по производительности                                     |
| Rust         | Дженерики + Trait              | Сложная система Trait, крутая кривая обучения                                                         |
| C++          | Шаблоны                        | Сложная специализация шаблонов, плохие сообщения об ошибках                                           |
| **YaoXiang** | **Зависимые от значений типы** | **Типы могут зависеть от значений, верификация измерений на этапе компиляции, гарантия завершимости** |

### Ключевые противоречия

1. **Производительность vs гибкость**：гибкость runtime vs оптимизации времени компиляции
2. **Сложность vs простота**：мощная система типов vs удобство использования
3. **Макросы vs дженерики**：генерация кода макросами vs типобезопасность дженериков
4. **Зависимость от значений vs безопасность типов**：традиционные дженерики не могут верифицировать
   измерения на этапе компиляции

### Ключевые преимущества зависимых от значений типов

**Зависимые от значений типы** YaoXiang — это ключевое преимущество по сравнению с традиционными
дженериками：

| Преимущество                      | Описание                                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Типы зависят от значений**      | `Array: (T: Type, N: Int) -> Type` позволяет типу зависеть от конкретного значения                       |
| **Вычисление времени компиляции** | Вызовы функций в позиции типа вычисляются на этапе компиляции, результат встраивается в тип              |
| **Верификация измерений**         | `Matrix(Float, 3, 3)` верифицирует измерения матрицы на этапе компиляции                                 |
| **Вычисления на уровне типов**    | Условные типы `If`, `Match` поддерживают вычисления на уровне типов                                      |
| **Гарантия завершимости**         | Проверка завершимости времени компиляции (автоматический синтез мер) гарантирует завершимость вычислений |

```yaoxiang
matrix: Matrix(Float, factorial(3), factorial(2)) = ...
# Вычисление времени компиляции: factorial(3) = 6, factorial(2) = 2
```

### Ценность системы дженериков

```yaoxiang
# Пример: единый дизайн API
# Операция map для разных контейнерных типов

# Традиционный подход: отдельная реализация для каждого типа
map_int_array: (array: Vec(Int), f: Fn(Int) -> Int) -> Vec(Int) = ...
map_string_array: (array: Vec(String), f: Fn(String) -> String) -> Vec(String) = ...
map_int_list: (list: List(Int), f: Fn(Int) -> Int) -> List(Int) = ...

# Подход с дженериками: одна дженерик-функция покрывает все типы

    }

}
```

## Цели дизайна

### Основные цели

1. **Абстракции с нулевой стоимостью** — вызов дженерика эквивалентен вызову конкретного типа
2. **Устранение мёртвого кода** — анализ времени компиляции, инстанцируются только используемые
   дженерики
3. **Замена макросов** — дженерики заменяют 90% сценариев использования макросов
4. **Безопасность типов** — проверка на этапе компиляции, без накладных расходов на типы в runtime
5. **Удобство для IDE** — интеллектуальные подсказки, ясные сообщения об ошибках
6. **Зависимые от значений типы** — типы могут зависеть от значений, поддержка верификации измерений
   времени компиляции
7. **Безопасность вычислений времени компиляции** — через проверку завершимости (автоматический
   синтез мер RFC-027) гарантируется завершимость вычислений

### Принципы дизайна

- **Определённость времени компиляции**：параметры дженериков определяются на этапе компиляции
- **Приоритет мономорфизации**：генерация конкретного кода, без вызовов виртуальных функций
- **Управление через ограничения**：ограничения типов руководят инстанцированием
- **Платформенные оптимизации**：специализация для платформенно-специфичных оптимизаций
- **Единая вселенная типов**：функции / конструкторы типов / зависимые от значений типы
  унифицируются на уровне Type2
- **Гарантия завершимости**：вызовы функций в позиции типа должны иметь доказанную завершимость

## Предложение

### 1. Базовые дженерики

#### 1.1 Параметры типов в дженериках

> **Ключевое правило**：определение дженерик-типа **должно явно аннотироваться `: Type`**, иначе
> будет выведено HM как функция.
>
> | Запись                            | Значение                            |
> | --------------------------------- | ----------------------------------- |
> | `List: (T: Type) -> Type = {...}` | ✅ Конструктор типа                 |
> | `List = {...}`                    | ❌ HM выводит как функцию, а не тип |

```yaoxiang
# Определение дженерик-типа (должно иметь : Type)
Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self
}

Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self
}

List: (T: Type) -> Type = {
    data: Vec(T),
    length: Int,
    push: (self: List(T), item: T) -> Void,   # self — лишь имя по соглашению, не ключевое слово
    get: (self: List(T), index: Int) -> Option(T),
}

# Дженерик-функция (без : Type, HM выводит как функцию)
map: (T: Type, R: Type) -> ((opt: Option(T), f: Fn(T) -> R) -> Option(R)) = {
    return match opt {
        some => Option.some(f(some)),
        none => Option.none(),
    }
}

# Ограничение дженерика (прямое выражение, в одну строку return можно опустить)
clone: (T: Clone)(value: T) -> T = value.clone()

# Несколько параметров типов
combine: (T: Type, U: Type) -> ((a: T, b: U) -> (T, U)) = (a, b)
```

#### 1.2 Механизм самоописания `Type`

`Type` — это языковой особый объект; компилятор по природе распознаёт позиции `Type` в сигнатуре и
автоматически выводит и заполняет их из типов фактических аргументов.

```yaoxiang

#         ^^^^^^^^   ^^^^^^^^
#         объявление типа  вызов конструктора: Int заполняет T, () — конструкция значения

f: (x: Int) -> String = (x) => x.to_string()

# Вывод компилятора: T=Int, R=String
```

#### 1.3 Мономорфизация

```yaoxiang
# Исходный код
map: (T: Type, R: Type) -> ((list: List(T), f: (x: T) -> R) -> List(R)) = {
    result: List(R) = List(R)()
    for x in list {
        result.push(f(x))
    }
    return result
}

# Точки использования
int_list: List(Int) = List(Int)()
doubled: List(Int) = map(int_list, (x: Int) => x * 2)  # Инстанцирование map[Int, Int]

string_list: List(String) = List(String)()
uppercased: List(String) = map(string_list, (s: String) => s.to_uppercase())  # Инстанцирование map[String, String]

# После компиляции (эквивалентный код)
map_Int_Int: (list: List(Int), f: (Int) -> Int) -> List(Int) = {
    result: List(Int) = List(Int)()
    for x in list {
        result.push(f(x))
    }
    return result
}

map_String_String: (list: List(String), f: (String) -> String) -> List(String) = {
    result: List(String) = List(String)
    for s in list {
        result.push(f(s))
    }
    return result
}
```

#### 2.4 Встроенные marker-trait：`Dup` и `Clone`

**Три вида семантики копирования**：

| Тип                                | Значение                                                                                | Способ срабатывания                     | Сценарий применения                |
| ---------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------- |
| **Копирование значения-примитива** | При присваивании автоматическое копирование значения, два значения полностью независимы | Автоматически при присваивании/передаче | Int, Float, Bool, Char             |
| **Dup**                            | Поверхностное копирование: копирование дескриптора/токена, базовые данные разделяются   | Автоматически при присваивании/передаче | токены `&T`, `ref T`, String/Bytes |
| **Clone**                          | Глубокое копирование: создание полной независимой копии                                 | `value.clone()`                         | Любой тип, реализующий Clone       |

**Семантика `Dup`**：типы, реализующие `Dup`, при присваивании/передаче не передают владение —
компилятор копирует дескриптор/токен, и несколько владельцев указывают на одни и те же базовые
данные. Это дополняет семантику Move по умолчанию из модели владения RFC-009.

**`Dup` и `Clone` — ортогональные концепции**：

```
Dup = копирование дескриптора, разделяемые данные (изменения влияют друг на друга)
Clone = копирование данных, копия независима (изменения не влияют друг на друга)
```

**Правила**：

```
1. Типы-примитивы значений (Int, Float, Bool, Char) — встроенное копирование значений компилятором, не относится к Dup
2. Dup  — применимо только к ссылочным/токен-типам и типам с внутренним подсчётом ссылок
3. Clone — явное глубокое копирование, любой тип может его реализовать
4. По умолчанию Move — остальные типы сохраняют семантику Move по умолчанию
```

**Какие типы являются `Dup`**：

| Тип                            | Dup         | Причина                                                                     |
| ------------------------------ | ----------- | --------------------------------------------------------------------------- |
| `&T` (токен заимствования)     | ✅          | Токен нулевого размера, копирование токена = несколько видов на одни данные |
| `ref T`                        | ✅          | Копирование Rc/Arc = счётчик ссылок+1, разделяемые данные в куче            |
| String, Bytes                  | ✅          | Внутренний подсчёт ссылок, копирование дескриптора разделяет базовый буфер  |
| `&mut T` (токен мутабельности) | ❌          | Линейная эксклюзивность, копировать нельзя                                  |
| struct                         | Производное | Все поля Dup → struct Dup                                                   |
| enum                           | Производное | Все поля всех вариантов Dup → enum Dup                                      |
| tuple                          | Производное | Все элементы Dup → tuple Dup                                                |
| Fn (замыкание)                 | ❌          | Захваченное окружение может быть не Dup                                     |
| `*T` (сырой указатель)         | ❌          | unsafe, не участвует в системе владения                                     |

**Int/Float/Bool/Char — это не `Dup`** — они являются типами-значениями, и компилятор автоматически
копирует значение при присваивании (два значения полностью независимы). Это не «поверхностное
копирование», а встроенная обработка примитивов компилятором, и её не нужно (и не следует) выражать
через атрибут типа `Dup`.

```yaoxiang
# Тип-примитив значения: компилятор автоматически копирует значение (не Dup)
x: Int = 42
y = x          # Копирование значения, x и y полностью независимы
print(x)       # ✅

# Dup: поверхностное копирование, дескриптор копируется, данные разделяются
view: &Point = &point
view2 = view    # ✅ Dup: токен копируется, оба указывают на один и тот же point
print(view.x)   # ✅

# Clone: явное глубокое копирование, создание независимой копии
backup = big_struct.clone()  # Явный вызов

# Ограничения дженериков
dup_use: (T: Dup) -> T = x         # T: Dup → можно поверхностно копировать
clone_use: (T: Clone) -> T = x.clone()  # T: Clone → можно глубоко копировать
```

> **Примечание**：`Send`/`Sync` не являются видимыми пользователю trait. Безопасность межзадачного
> взаимодействия обеспечивается ключевым словом `ref` и полностью автоматической обработкой
> компилятором — `ref` автоматически выбирает Rc или Arc, пользователю не нужно понимать Send/Sync.

```yaoxiang

Iterator: (Item: Type) -> Type = {
    next: (Self) -> Option(Item),
    has_next: (Self) -> Bool,
    collect: (T: Type)(Self) -> List(T),
}

# Использование
collect_all: (T: Type, I: Iterator(T))(iter: I) -> List(T) = {
    result: List(T) = List(T)
    while iter.has_next() {
        if let Some(item) = iter.next() {
            result.push(item)
        }
    }
    return result
}

# Реализация Iterator для Vec
# Используется синтаксический сахар метода: Vec.Item, Vec.next, Vec.has_next
# Позиция итерации переносится обёрточной записью (сам Vec — сырой буфер, без поля index)
VecIter: (T: Type) -> Type = {
    data: &Vec(T),
    index: Int,
}

VecIter.has_next: (T: Type)(self: &VecIter(T)) -> Bool = {
    return self.index < self.data.length
}

VecIter.next: (T: Type)(self: &mut VecIter(T)) -> Option(T) = {
    if self.index < self.data.length {
        item = self.data[self.index]
        self.index = self.index + 1
        return Option.some(item)
    } else {
        return Option.none()
    }
}

VecIter.Item: (T: Type)(arr: &VecIter(T)) -> T = {
    return arr.data[arr.index]
}
```

### 4. Дженерики времени компиляции

#### 4.1 Значение-параметры времени компиляции

**Ключевое решение**：маркер `Type` в сигнатуре дженерика обозначает параметр-тип; параметры,
аннотированные конкретным типом (`Int`/`Bool`/`Float` и т.д.), рассматриваются как **кандидаты в
значение-параметры времени компиляции**; становятся они таковыми или нет, определяется тем,
**используется ли их значение в позиции типа** (зависимость от значения). Ключевое слово `const` не
требуется.

> Критерий — **использование в позиции типа**, а не «аннотация конкретным типом»: в
> `add: (a: Int, b: Int) -> Int = a + b` `a`/`b` — это значение-параметры runtime, потому что оба не
> встречаются ни в одной позиции типа.

**Правило определения (двухшаговое)**：

1. **Грубая фильтрация по форме**：параметр аннотирован не-`Type` конкретным типом (например, `Int`)
   → считается кандидатом.
2. **Точная фильтрация по использованию**：имя кандидата появляется в **позиции типа** (тип поля
   тела типа, тип внутреннего параметра `Fn`, предикат `Assert`, позиция аргумента конструкции типа
   вроде `Array(T, N)`) → подтверждается как значение-параметр времени компиляции; иначе считается
   **значение-параметром runtime**.

| Запись                                                     | Определение                              | Причина                                                                   |
| ---------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------- |
| `add: (a: Int, b: Int) -> Int = a + b`                     | a/b — значение-параметры runtime         | Появляются только в позиции значения, не участвуют в конструировании типа |
| `Array: (T: Type, N: Int) -> Type = { data: Array(T, N) }` | N — значение-параметр времени компиляции | N появляется в позиции аргумента конструкции типа `Array(T, N)`           |
| `factorial: (N: Int) -> (k: N) -> Int`                     | N — значение-параметр времени компиляции | N выступает типом внутреннего параметра `k`                               |
| `Foo: (T: Type, N: Int) -> Type = { x: T }`                | N не используется (см. ниже)             | N не упомянут в теле типа, вырождается в значение-параметр runtime        |

> **Суть зависимости от значения**：значение-параметр времени компиляции — это зависимый от значения
> тип — только когда значение используется для **конструирования типа**, требуется его
> определённость на этапе компиляции. Форма (`: Int`) лишь определяет кандидатуру, использование
> (появление в позиции типа) определяет, является ли он значение-параметром времени компиляции. Это
> тот же критерий, что и в разделе «Гарантия определённости времени компиляции» — «вызовы функций в
> позиции типа вычисляются на этапе компиляции».

```yaoxiang
# ════════════════════════════════════════════════════════
# Значение-параметр времени компиляции: N используется в позиции типа (слот длины Measure)
# ════════════════════════════════════════════════════════
Measure: (T: Type, N: Int) -> Type = {
    data: Array(T, N),  # N появляется в позиции аргумента конструкции типа → значение-параметр времени компиляции
    length: N,
}

# Использование: factorial(5) вычисляется в позиции типа (время компиляции), результат 120 встраивается в тип
m: Measure(Int, factorial(5))  # Measure(Int, 120)

# ════════════════════════════════════════════════════════
# Зависимость от значения: N выступает типом внутреннего параметра k
# ════════════════════════════════════════════════════════
# N — значение-параметр времени компиляции (появляется в позиции типа (k: N));
# k — значение-параметр runtime, его тип — литеральный тип N (однозначный тип).
factorial: (N: Int) -> (k: N) -> Int = {
    return match k {
        0 => 1,
        _ => k * factorial(k - 1)
    }
}
```

> **Обработка неиспользуемых кандидатов**：кандидат, аннотированный конкретным типом, но не
> упомянутый в позиции типа (например, `N` в `Foo` выше) вырождается в значение-параметр runtime
> (уровень функции). Неиспользуемый кандидат на пути конструктора типа не может занять слот runtime
> (конструктор типа вычисляется на этапе компиляции), и на стороне объявления сразу выдаётся ошибка
> [E1094]：«N объявлен как значение-параметр времени компиляции, но не упомянут в теле типа» — ранее
> тихое отбрасывание приводило к несогласованности арности инстанцирования.

### `Never` и `Void`：⊥ и ⊤ в системе типов

Система типов YaoXiang в изоморфизме Карри — Ховарда обладает и ⊥ (ложь/пустой тип), и ⊤
(истина/Unit), представленными двумя встроенными именами типов：`Never` и `Void`：

**`Never` (⊥)** — три не подлежащих обсуждению ядерных свойства：

1. **Нулевые конструкторы**：никакой литерал или выражение не может породить значение типа `Never`.
   Это метауровневое свойство, оно должно быть встроенным.
2. **Принцип взрыва**：`Never <: T` выполняется для любого типа `T`. Значение `Never` может
   использоваться как значение любого типа — именно поэтому код после `assert(false)` всё ещё
   проходит проверку типов (хотя никогда не выполнится).
3. **Маркер расходимости**：`f: (...) -> Never` означает, что `f` гарантированно не возвращается.
   Компилятор использует это для анализа мёртвого кода.

`Never` — встроенное имя типа, а не ключевое слово, парсер не делает специальной обработки.
Синтаксис литералов пустого и типового значений не открывается.

**`Void` (⊤, т.е. Unit)** — ровно один обитатель (значение `void` по умолчанию), носитель истинной
propositions «всегда истинно». `Void` — единица для типов-пустых-произведений, `Never` — единица для
типов-пустых-сумм — они двойственны. `x: Void = <default>` допустимо, `x: Never = ...` не имеет
правой части.

#### 4.3 Верификация времени компиляции (реализация стандартной библиотеки)

```yaoxiang
# ════════════════════════════════════════════════════════
# Реализация стандартной библиотеки: с использованием условных типов
# ════════════════════════════════════════════════════════

# Определения стандартной библиотеки
# IsTrue: мост из вселенной значений во вселенную типов — истинное значение Bool отображается в тип
IsTrue: (b: Bool) -> Type = match b {
    true => Void,      # ⊤, имеет значение, программа продолжается
    false => Never,    # ⊥, нет значения, расходимость
}

# Assert: примитив уточнённого типа времени компиляции — типовое выражение propositions для Bool
Assert: (cond: Bool) -> Type = IsTrue(cond)
#
# cond == true  → Assert(true)  = Void    (всегда истинно, стирается)
# cond == false → Assert(false) = Never   (всегда ложно, ошибка компиляции / расходимость)
# cond неразрешимо → конвейер доказательств решает по режиму dispatch:
#                    CompileTime → Unknown, требуется prove
#                    Runtime     → вставляет check, вводит предположение Γ

# Способ использования 1: ограничение в определении типа
Bounded: (T: Type, N: Int) -> Type = {
    data: Array(T, N),
    # Проверка времени компиляции: N должно быть > 0 (Assert в позиции типа)
    length: Assert(N > 0),
}

# Способ использования 2: использование в выражениях
IntArray: (N: Int) -> Type = Array(Int, N)
# Верификация: размер IntArray(10) равен sizeof(Int) * 10
Assert(size_of(IntArray(10)) == sizeof(Int) * 10)
```

### 5. Условные типы

> **Изоморфизм Карри — Ховарда**：условные типы с точки зрения Карри — Ховарда — это **case-анализ**
> в логике. Тип `Bool` соответствует propositions с двумя возможными значениями (True/False); `If` в
> зависимости от истинности этой propositions выбирает разные результаты — это и есть логический
> case-дизъюнкт. `match C { True => T, False => E }` по существу выражает: «известно, что если
> propositions C истинна, заключение — T, а если C ложна — заключение E».

#### 5.1 Условный тип `If`

```yaoxiang
# Уровневый If
If: (C: Bool, T: Type, E: Type) -> Type = match C {
    True => T,
    False => E,
}

# Пример: ветвление времени компиляции
NonEmpty: (T: Type) -> Type = If(T != Void, T, Never)

Optional: (T: Type) -> Type = If(T != Void, T, Void)

# Верификация времени компиляции (унифицирована с определением Assert в §4.3)
# Assert: (cond: Bool) -> Type = IsTrue(cond)

# Использование
# Вычисление типа: If(True, Int, String) => Int
# Вычисление типа: If(False, Int, String) => String
```

#### 5.2 Семейства типов

> **Изоморфизм Карри — Ховарда**：семейства типов — самое прямое воплощение «propositions как
> типов». `Add: (A: Type, B: Type) -> Type` — это не «функция сложения, записанная на уровне типов»,
> а **построение propositions о сложении натуральных чисел**. `(Zero, B) => B` говорит:
> «propositions Add(Zero, B) эквивалентна B»; `(Succ(A'), B) => Succ(Add(A', B))` говорит: «если
> Add(A', B) выполняется, то и Add(Succ(A'), B) выполняется». Это и есть само определение сложения
> по аксиомам Пеано. То, что проверка типов подтверждает корректность этого match-выражения,
> эквивалентно проверке логической согласованности этого определения.

```yaoxiang
# Преобразование типов времени компиляции
AsString: (T: Type) -> Type = match T {
    Int => String,
    Float => String,
    Bool => String,
    _ => String,  # По умолчанию
}

# Вычисления на уровне типов
Length: (T: Type) -> Type = match T.length {
    0 => Zero,
    1 => Succ(Zero),
    2 => Succ(Succ(Zero)),
    _ => TooLong,
}

# Сложение на уровне типов (Карри — Ховард: case-анализ + рекурсивный вызов; для полной индукции требуется проверка завершимости)
Add: (A: Type, B: Type) -> Type = match (A, B) {
    (Zero, B) => B,
    (Succ(A'), B) => Succ(Add(A', B)),
}

# Пример: вычисление 2 + 3 времени компиляции
Two: Type = Succ(Succ(Zero))
Three: Type = Succ(Succ(Succ(Zero)))
Five: Type = Add[Two, Three]  # Succ(Succ(Succ(Succ(Succ(Zero)))))
```

#### 6.3 Идеальное сочетание перегрузки функций и инлайнинга

```yaoxiang
    }

```

1. **Интеллектуальный выбор компилятора**

````
struct InstantiationGraph {
    // Узлы: инстанцирования дженериков
    nodes: HashMap<InstanceKey, InstanceNode>,

    // Рёбра: отношения использования
    edges: HashMap<InstanceKey, Vec<InstanceKey>>,
}

    generic: FunctionId,  // ID дженерик-функции
    type_args: Vec<TypeId>,  // Аргументы типов
    const_args: Vec<ConstId>,  // Аргументы Const
}

// Алгоритм: анализ достижимости
fn eliminate_dead_instantiations(graph: &InstantiationGraph) {
    let mut reachable = HashSet::new();

    // Начинаем с точек входа (main, экспортируемые функции и т.д.)
    let entry_points = find_entry_points();
    for entry in entry_points {
        dfs_visit(entry, &graph, &mut reachable);
    }

    // Не посещённые инстанцирования — мёртвый код
    for node in &graph.nodes {
        if !reachable.contains(node.key) {
            eliminate(node);
        }
    }
}
````

#### 9.1 Полный пример дженерик-контейнера

```yaoxiang
# ======== 1. Определение дженерик-контейнера ========
# Используется синтаксис (T: Type) -> Type
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Self,
    err: (E) -> Self,
}

Option: (T: Type) -> Type = {
    some: (T) -> Self,
    none: () -> Self,
}

List: (T: Type) -> Type = {
    data: Vec(T),
    length: Int,

    # Дженерик-методы (T автоматически попадает в область видимости из внешнего List(T))
    push: (self: List(T), item: T) -> Void,
    pop: (self: List(T)) -> Option(T),
    map: (R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)),
    filter: (self: List(T), predicate: (T) -> Bool) -> List(T),
    fold: (U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U),
}

# ======== 2. Реализация дженерик-методов ========
# Функции определяются в пространстве имён List (префикс List. = принадлежность пространству имён)
# Чтобы работал синтаксис вызова через точку list.push(item), требуется явное связывание: List.push = push[0]
# self — лишь имя параметра по соглашению, компилятор смотрит на тип, а не на имя

List.push: (T: Type) -> ((self: List(T), item: T) -> Void) = {
    if self.length >= self.data.length {
        # Расширение
        new_data = Vec(T)(len=self.data.length * 2)
        for i in 0..self.length {
            new_data[i] = self.data[i]
        }
        self.data = new_data
    }
    self.data[self.length] = item
    self.length = self.length + 1
}

List.pop: (T: Type) -> ((self: List(T)) -> Option(T)) = {
    if self.length > 0 {
        self.length = self.length - 1
        return Option.some(self.data[self.length])
    } else {
        return Option.none()
    }
}

List.map: (T: Type, R: Type) -> ((self: List(T), f: (T) -> R) -> List(R)) = {
    result = List(R)()
    for i in 0..self.length {
        result.push(f(self.data[i]))
    }
    return result
}

List.filter: (T: Type) -> ((self: List(T), predicate: (T) -> Bool) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        if predicate(self.data[i]) {
            result.push(self.data[i])
        }
    }
    return result
}

List.fold: (T: Type, U: Type) -> ((self: List(T), initial: U, f: (U, T) -> U) -> U) = {
    result = initial
    for i in 0..self.length {
        result = f(result, self.data[i])
    }
    return result
}

# ======== 3. Использование ограничений типов ========
# Реализация Clone для List
List.clone: (T: Clone) -> ((self: List(T)) -> List(T)) = {
    result = List(T)()
    for i in 0..self.length {
        result.push(self.data[i].clone())
    }
    return result
}

# ======== 4. Примеры использования ========
# Создание дженерик-List
numbers = List(Int)()

numbers.push(2)
numbers.push(3)

# Использование дженерик-методов

evens = numbers.filter((x) => x % 2 == 0)

# Вычисление через fold

# Композиция дженериков

    .filter((x) => x % 2 == 0)
    .map((x) => x * 2)
    .fold(0, (acc, x) => acc + x)  # sum_of_evens = 8
```

```yaoxiang
# ======== 1. Дженерик-алгоритм сортировки ========
Comparator: (T: Type) -> Type = {
    compare: (T, T) -> Int,  # -1 if a < b, 0 if a == b, 1 if a > b
}

# Дженерик quicksort
quicksort: (T: Clone) -> ((array: Vec(T), cmp: Comparator(T)) -> Vec(T)) = {
    if array.length <= 1 {
        return array.clone()
    }

    pivot = array[array.length / 2]
    left = Vec(T)()
    right = Vec(T)()

    for i in 0..array.length {
        if i == array.length / 2 {
            continue
        }
        item = array[i]
        comparison = cmp.compare(item, pivot)
        if comparison < 0 {
            left.push(item)
        } else {
            right.push(item)
        }
    }

    sorted_left = quicksort(left, cmp)
    sorted_right = quicksort(right, cmp)

    result = sorted_left.clone()
    result.push(pivot)
    result.extend(sorted_right)
    return result
}

# ======== 2. Реализация IntComparator ========
# Реализация через перегрузку функций
compare: (a: Int, b: Int) -> Int = {
    if a < b {
        return -1
    } else if a > b {
        return 1
    } else {
        return 0
    }
}

# ======== 3. Примеры использования ========
# Сортировка массива Int

# Сортировка массива String (требуется StringComparator)
```

```yaoxiang
Matrix: (T: Type, Rows: Int, Cols: Int) -> Type = {
    data: Array(Array(T, Cols), Rows),

    # Верификация измерений времени компиляции: используется стандартный библиотечный тип Assert
    _assert: Assert(Rows > 0),  # Rows > 0, иначе ошибка компиляции
    _assert: Assert(Cols > 0),  # Cols > 0, иначе ошибка компиляции

    # Операции над матрицами
    multiply: (M: Int) -> ((self: Matrix(T, Rows, Cols), other: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)) = {
        result = Matrix(T, Rows, M)()
        for i in 0..Rows {
            for j in 0..M {
                sum = Zero::zero()
                for k in 0..Cols {
                    sum = sum + self.data[i][k] * other.data[k][j]
                }
                result.data[i][j] = sum
            }
        }
        return result
    }
}

            } else {
                matrix.data[i][j] = Zero::zero()
            }
        }
    }
    return matrix
```

## Компромиссы

### Преимущества

1. **Абстракции с нулевой стоимостью**
   - Мономорфизация на этапе компиляции, без накладных расходов в runtime
   - Не требуются виртуальные функции, нет RTTI

2. **Устранение мёртвого кода**
   - Анализ на этапе компиляции, инстанцируются только используемые дженерики
   - Управляемое раздувание кода

3. **Замена макросов**
   - Типобезопасная генерация кода
   - Удобство для IDE, ясные сообщения об ошибках

4. **Вычисления времени компиляции**
   - Дженерики времени компиляции поддерживают вычисления времени компиляции
   - Такие возможности, как верификация измерений
   - Без ключевого слова `const`, чистые ограничения типов

### Недостатки

1. **Время компиляции**
   - Инстанцирование дженериков увеличивает время компиляции
   - Решение ограничений может быть медленным

2. **Потребление памяти**
   - Увеличивается потребление памяти компилятором
   - Механизмы кеширования требуют памяти

3. **Сложность реализации**
   - Сложный решатель ограничений
   - Сложный движок вычислений на уровне типов

4. **Диагностика ошибок**
   - Ошибки дженериков могут быть сложными
   - Требуются ясные подсказки об ошибках

### Меры по смягчению

1. **Стратегии кеширования**
   - Кеширование результатов инстанцирования
   - LRU-кеш с ограничением памяти

2. **Инкрементальная компиляция**
   - Кеширование результатов компиляции
   - Инкрементальное инстанцирование

3. **Сообщения об ошибках**
   - Ясные сообщения об ошибках
   - Подсказки по выводу параметров дженериков

4. **Параллельная компиляция**
   - Параллельное инстанцирование дженериков
   - Многопоточный решатель ограничений

## Приложение

### БНФ грамматики

```bnf
# Параметры дженериков используют единый синтаксис () как часть функционального типа
# Например, map: (T: Type, R: Type) -> ((list: List(T), f: (T) -> R) -> List(R))

# Ограничение типа (в параметрах дженерика)
type_bound ::= identifier
             | identifier '+' identifier ('+' identifier)*

# Объявление параметра (тип + имя)
parameter ::= identifier ':' type

parameters ::= parameter (',' parameter)*

# Объявление функции: name: type = expression
# Параметры дженерика — первая группа параметров в функциональном типе: (T: Type) -> ((params) -> return)
function ::= identifier ':' type '=' (expression | block)

# Объявление метода: Type.method: type = expression
method ::= identifier '.' identifier ':' type '=' (expression | block)

# Определение типа (единый синтаксис Binding)
# Дженерик-тип, такой как List: (T: Type) -> Type = { ... }
generic_type ::= identifier ':' type '=' type_expression

# Параметры Type в дженериках автоматически заполняются компилятором из типов фактических аргументов
# Например, в map(numbers, f) T извлекается из numbers: List(Int), R — из f: (Int) -> String
```
