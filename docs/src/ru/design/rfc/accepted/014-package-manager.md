# RFC-014: Дизайн системы управления пакетами (общий документ)

> **Дочерние RFC:**
>
> - [RFC-014a: Спецификация протокола реестра](../accepted/014a-registry-protocol.md)
> - [RFC-014b: Система сборки и распространение бинарников](../accepted/014b-build-system.md)
> - [RFC-014c: Поддержка рабочих пространств](../accepted/014c-workspace.md)

## Резюме

Проектирование системы управления пакетами языка YaoXiang с поддержкой семантического
версионирования, локальных и GitHub-зависимостей, единого синтаксиса импорта, файла конфигурации
`yaoxiang.toml` и файла блокировки `yaoxiang.lock`.

## Мотивация

### Зачем нужна эта функция/изменение?

Управление пакетами — инфраструктура, лежащая в основе современной экосистемы языков
программирования. Текущий язык YaoXiang не имеет:

- Механизма объявления зависимостей
- Возможностей управления версиями
- Стандартного канала распространения

### Текущая проблема

```
my-project/
├── src/
│   └── main.yx          # код зависит от других модулей
├── lib/                  # скопированные вручную модули
│   ├── foo.yx
│   └── bar.yx
└── ???                   # нет стандартного управления зависимостями
```

## Предложение

### Основной дизайн

**Многоуровневая архитектура**:

```
┌─────────────────────────────────────────────┐
│           Resolution Engine                  │ ← разрешение зависимостей
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│            Global Cache                      │ ← ~/.yaoxiang/cache/
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│              Source Trait                    │ ← расширяемые источники
├──────────┬──────────┬──────────┬────────────┤
│  Local   │   Git    │ Registry │   GitHub   │
│ (локал.) │  (VCS)   │ (открыт.)│ (Release)  │
└──────────┴──────────┴──────────┴────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│           Vendor Directory                   │ ← .yaoxiang/vendor/
└─────────────────────────────────────────────┘
```

**Механизм расширения**: добавление нового типа Source требует только реализации trait, без
изменения движка разрешения.

### Пример

```bash
# 1. Создание проекта
yaoxiang init my-project

# 2. Редактирование yaoxiang.toml для добавления зависимостей
[dependencies]
foo = "^1.0.0"
bar = { git = "https://github.com/user/bar", version = "0.5.0" }

# 3. Установка зависимостей
yaoxiang add foo

# 4. Использование в коде
use foo;
use bar.baz;
```

### Структура проекта

```
my-project/
├── yaoxiang.toml        # конфигурация пакета
├── yaoxiang.lock        # файл блокировки (генерируется автоматически)
├── src/
│   └── main.yx
└── .yaoxiang/
    └── vendor/              # локальные зависимости
        ├── foo-1.2.3/
        └── bar-0.5.0/
```

## Подробный дизайн

### Формат файла конфигурации

**yaoxiang.toml**:

```toml
[package]
name = "my-package"
version = "0.1.0"
description = "A short description"
license = "MIT"
authors = ["Your Name <you@example.com>"]
repository = "https://github.com/you/my-package"
keywords = ["cli", "utility"]

[dependencies]
foo = "1.2.3"           # точная версия
bar = "^1.0.0"          # совместимая версия
baz = "~1.2.0"          # патч-версия
qux = { git = "...", version = "0.5.0" }
local_pkg = { path = "./local-module" }

[dev-dependencies]
test-utils = "0.1.0"

[build]
strategy = "none"       # none | cargo | cmake | custom

[binaries]
"linux-x86_64" = { url = "...", sha256 = "..." }

[workspace.members]     # только корень рабочего пространства
core = "packages/core/yaoxiang.toml"
```

**yaoxiang.lock**:

```toml
version = 1

[[package]]
name = "foo"
version = "1.2.3"
source = "git"
resolved = "https://github.com/user/foo?tag=v1.2.3"
integrity = "sha256-xxxx"
```

### Порядок разрешения модулей

> **Решение от 2026-09-15: семантика взаимного исключения для основного источника пакетов (стиль
> Python venv / Node node_modules).** Отменяется прежнее описание «5-уровневой сквозной цепочки
> поиска» — vendor и глобальный кэш **выбираются один из двух** как единственный основной источник
> пакетов; std встроен в основной источник; локальные модули могут перекрывать всё остальное.

**Определение основного источника пакетов (взаимно исключающее, никогда не смешивается)**:

- В проекте существует `.yaoxiang/vendor/` → **vendor является единственным основным источником
  пакетов**. Все `use` для нелокальных модулей разрешаются только из vendor; отсутствие пакета в
  vendor приводит к ошибке (с подсказкой `yaoxiang install`), **глобальный откат не выполняется**.
- Иначе → **глобальный кэш является основным источником пакетов** (каталог установки std +
  глобальный кэш).

Не существует «прохождения насквозь» в стиле «нет в vendor — откат к глобальному кэшу» — смешивание
двух источников как раз и является корнем дрейфа версий и проблемы «у меня на машине работает».

#### Режим проекта (с yaoxiang.toml)

```
use foo.bar.baz;

Порядок поиска:
1. ./src/foo/bar/baz.yx     локальный модуль — наивысший приоритет, может перекрывать одноимённые модули в основном источнике
2. <основной источник>/foo/bar/baz.yx
   · режим vendor: .yaoxiang/vendor/<pkg>-<ver>/src/foo/bar/baz.yx (пересмотр от 2026-09-28: std не находится в vendor, см. правила режима проекта)
   · глобальный режим: <install-dir>/yx/<ver>/std/foo/bar/baz.yx + ~/.yaoxiang/cache/...
3. Резерв для std.*: встроенный бинарник (только пространство имён std.*; пересмотр от 2026-09-28: официальный механизм, см. правила режима проекта)
4. Ошибка (модуль не существует); в режиме vendor при отсутствии пакета — подсказка `yaoxiang install`
```

**Правила режима проекта**:

- Когда vendor существует, но не соответствует `yaoxiang.lock`, `run`/`build` возвращают ошибку с
  подсказкой `yaoxiang install` (семантика Node: не устанавливать автоматически молча)
- Когда локальный модуль перекрывает одноимённый модуль в основном источнике, по умолчанию выдаётся
  диагностика уровня W о затенении (`--deny-shadowing` может повысить до ошибки)
- Зависимости `path` рассматриваются как продолжение локальных модулей и разрешаются напрямую по
  пути, без обращения к основному источнику пакетов

> **Пересмотр от 2026-09-28: std не пакетизируется (отменяет часть решения от 2026-09-15 о
> пакетизации std).** Встроенный бинарник std переходит из «переходного резерва» в **официальный
> механизм**: std тесно связан с компилятором на уровне ABI (встроенные в native-слой/runtime должны
> соответствовать макету VM), блокировка версии std в пакете создаёт скрытые ошибки вида
> «std-1.0.1 + компилятор 1.0.2»; правильным решением проблемы дрейфа std является фиксация
> инструментария на уровне проекта (если требуется — отдельное обсуждение), а не std как пакет.
> Прецеденты Go/Rust/Python едины — поставляемая с языком std следует за инструментарием. Команда
> `yaoxiang add std@<ver>` недоступна; `std.*` — зарезервированное пространство имён, локальные
> модули не могут его затенять (у встроенного std нет файловой формы, затенение невозможно); каталог
> файлов интерфейса `.yaoxiang/vendor/std/` (первый уровень цепочки поиска LSP) из RFC-037
> сохраняется и продолжает выполнять роль «просмотра исходного кода». Попутное уточнение: область
> диагностики затенения локального модуля — только пакеты зависимостей, без специального текста о
> std.*.

#### Однофайловый режим (без yaoxiang.toml)

```
use foo.bar.baz;

Порядок поиска:
1. ./src/foo/bar/baz.yx     локальный модуль
2. Глобальный основной источник пакетов: <install-dir>/yx/<version>/std/foo/bar/baz.yx
3. Резерв — встроенный бинарник std
4. $YXPATH/foo/bar/baz.yx   (глобальный путь, зарезервировано)
```

**Правила однофайлового режима**:

- Понятие проектных зависимостей отсутствует; std берётся напрямую из глобального; путь глобальной
  стандартной библиотеки привязан к версии компилятора: `<install-dir>/yx/<version>/std/`
- Однофайловый режим никогда не читает `.yaoxiang/` (понятие vendor отсутствует)

### Структура каталога установки стандартной библиотеки

#### Глобальная стандартная библиотека

```
<yaoxiang-install-dir>/
├── yx/                          # каталог языка YaoXiang
│   ├── 1.0.1/                   # каталог версии
│   │   ├── std/
│   │   │   ├── test.yx          # чистый модуль стандартной библиотеки YaoXiang
│   │   │   ├── math.yx          # будущий самозагружаемый модуль
│   │   │   └── ...
│   │   └── ...
│   └── 1.1.0/
│       └── std/
│           └── ...
└── bin/
    └── yaoxiang                 # бинарник компилятора
```

#### Проектная стандартная библиотека

> **Решение от 2026-09-15: отдельный каталог `.yaoxiang/std/` больше не создаётся.** **Пересмотр от
> 2026-09-28: std не пакетизируется** (обоснование см. в конце «Правил режима проекта») — std
> остаётся встроенным бинарником + каталогом файлов интерфейса из RFC-037, `add std@<ver>`
> недоступно, `std.*` зарезервировано и не может быть затенено. Вывод о взаимоисключающем каталоге
> (отсутствие отдельного `.yaoxiang/std/`) остаётся в силе.

```
my-project/
├── yaoxiang.toml
├── yaoxiang.lock
├── .yaoxiang/
│   └── vendor/
│       ├── std-1.0.1/           # std как обычный пакет vendor
│       └── foo-1.2.3/
├── src/
│   └── main.yx
```

**Ключевые моменты дизайна**:

- Встроенный бинарник как слой совместимости: пока файловая стандартная библиотека полностью не
  развёрнута, модули std предоставляются через встроенный бинарник
- Изоляция по версиям: `yx/<version>/std/` позволяет сосуществовать разным версиям стандартной
  библиотеки без взаимного влияния
- std и обычные зависимости используют один механизм (add/lock/vendor), без специального каталога и
  специального слоя поиска
- Однофайловый режим откатывается к глобальной std; при наличии vendor std также берётся из
  встроенного бинарника/каталога интерфейса (пересмотр от 2026-09-28: std не пакетизируется, не
  поставляется с vendor)

### Основные структуры данных

```rust
// Источник зависимости (расширяемый)
enum Source {
    Local { path: PathBuf },
    Git { url: Url, version: Option<VersionConstraint> },
    Registry { registry: String, namespace: Option<String> },
    GitHub { owner: String, repo: String, ref_: GitRef },  // нативный GitHub
}

enum GitRef {
    Tag(String),
    Branch(String),
    Rev(String),
    DefaultBranch,
}

// Объявление зависимости
enum DependencySpec {
    Version(VersionConstraint),
    Git { url: Url, version: Option<VersionConstraint> },
    Local { path: PathBuf },
    Workspace { member: String },  // ссылка на члена рабочего пространства
}

// Разрешённая зависимость (решение от 2026-09-15: целостность только через одно поле integrity, формат "sha256-<hex>", без дублирующего checksum)
struct ResolvedDependency {
    name: String,
    version: Version,
    source: Source,
    integrity: Option<String>,
}

// Стратегия сборки
enum BuildStrategy {
    None,          // чистый пакет .yx
    Cargo,         // вызов cargo build
    Cmake,         // вызов cmake
    Custom,        // выполнение скрипта build.yx
    Precompiled,   // 直接用预编译产物
}
```

### Обратная совместимость

- ✅ Существующий синтаксис `use` полностью сохраняется
- ✅ Существующая логика разрешения модулей не меняется
- ✅ Добавление каталога `.yaoxiang/vendor` не влияет на существующие проекты

### Глобальный кэш

Все загруженные зависимости кэшируются в `~/.yaoxiang/cache/`, проектный каталог vendor копируется
из кэша.

```
~/.yaoxiang/
├── cache/
│   ├── registry/
│   │   └── foo-1.2.3/
│   ├── git/
│   │   └── github.com-user-bar-abc123/
│   └── binaries/
│       └── foo-1.2.3-linux-x86_64.tar.gz
├── credentials.toml
└── config.toml
```

```toml
# ~/.yaoxiang/config.toml
[cache]
dir = "~/.yaoxiang/cache"
max_size = "2GB"
ttl = "30d"
```

Правила инвалидации кэша:

- Пакеты реестра: номер версии неизменяем, инвалидация не требуется
- Git-зависимости: кэшируются по tag/rev, при неизменном tag не инвалидируются
- Ручная очистка: `yaoxiang cache clean`

### Аутентификация

```toml
# ~/.yaoxiang/credentials.toml
[github]
token = "ghp_xxxx"

[registries.my-company]
url = "https://yxreg.my-company.com"
token = "xxx"
```

- Приоритет переменных среды: `$YX_GITHUB_TOKEN`, `$YX_REGISTRY_TOKEN`
- Токен никогда не записывается в `yaoxiang.toml` или `yaoxiang.lock`
- Права на файл: 600

### Семантика yank

`yaoxiang yank foo@1.2.3` выполняет **удаление + блокировку номера версии**:

- Пакет полностью удаляется, восстановление невозможно
- Номер версии занят навсегда, повторная публикация с тем же номером запрещена
- Проекты, в чьих lock-файлах уже есть ссылка на эту версию, будут падать с ошибкой и должны
  обновиться
- **Цель безопасности**: предотвращение атак на цепочку поставок в стиле npm (когда злоумышленник
  перехватывает удалённый номер версии и внедряет вредоносный код)

### Протокол Registry

Подробности см. в [RFC-014a: Спецификация протокола реестра](../accepted/014a-registry-protocol.md).

Основной дизайн: открытый протокол + адаптер. Официальный реестр — основной канал, GitHub
Release/main ветка — вспомогательный, поддерживаются пользовательские реестры.

### Система сборки

Подробности см. в
[RFC-014b: Система сборки и распространение бинарников](../accepted/014b-build-system.md).

Основной дизайн: декларативная конфигурация `[build]`, приоритет предкомпиляции / исходный код как
резерв, поддержка стратегий cargo/cmake/custom.

### Рабочее пространство

Подробности см. в [RFC-014c: Поддержка рабочих пространств](../accepted/014c-workspace.md).

Основной дизайн: декларация members в виде словаря, общий lock-файл, путевые зависимости, интеграция
с Cargo workspace.

## Компромиссы

### Преимущества

- Единый синтаксис импорта — пользователю не нужно думать об источнике зависимости
- Детерминированная сборка — lock-файл гарантирует воспроизводимость
- Оффлайн-поддержка — после загрузки можно работать без сети
- Source trait упрощает последующее расширение

### Недостатки

- Требуется дополнительное дисковое пространство (каталог `.yaoxiang/vendor`)
- Конфликты версий требуют ручного разрешения пользователем

## Альтернативы

| Подход                                    | Почему не выбран                                           |
| ----------------------------------------- | ---------------------------------------------------------- |
| Прямой доступ к GitHub в реальном времени | Сложно гарантировать безопасность и переиспользование кэша |
| Только глобальный кэш ($HOME/.yaoxiang)   | Плохая изоляция, сложные конфликты версий                  |
| Только поддержка реестра                  | GitHub — текущая主流-платформа хостинга кода               |

## Стратегия реализации

### Разбивка по этапам

| Этап          | Содержание                                                                                                                      | Статус                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Phase 1**   | Парсинг toml, локальные зависимости, генерация lock, базовые алгоритмы                                                          | ✅ Завершено                                              |
| **Phase 2**   | Поддержка GitHub, управление `.yaoxiang/vendor`, инструмент загрузки                                                            | ✅ Завершено                                              |
| **Phase 3**   | Глобальный кэш, замена semver crate, доработка CLI                                                                              | ✅ Завершено                                              |
| **Phase 3.5** | Диспетчеризация Source через enum + нативный async (решение 4 из 014a, без async-trait)                                         | ✅ Завершено                                              |
| **Phase 4**   | Адаптер GitHub, упаковка `.yxpkg`, publish --github (сокращённый объём после RFC-014a; официальные Registry/auth/yank отложены) | ✅ Завершено                                              |
| **Phase 5**   | Система сборки, предкомпилированные бинарники (RFC-014b)                                                                        | ✅ Завершено                                              |
| **Phase 6**   | Поддержка рабочих пространств (RFC-014c)                                                                                        | ✅ 6a-c + управление членами + 6d завершено (6e отложено) |

**Корректировка порядка выполнения (2026-09-15)**: `3 → 3.5 → 6 → 4 → 5`.

- Рабочие пространства (Phase 6) подняты выше системы сборки — они не зависят от сети и системы
  сборки (чисто локальное разрешение путей + общий lock-файл) и дают максимально прямой выигрыш для
  мультипакетной разработки.
- Объём Phase 4 сокращён: **сервер официального Registry, а также auth/yank отложены на
  неопределённый срок**; сначала поставляются адаптер GitHub Release/Git + упаковка `.yxpkg` +
  `publish --github`. Для холодного старта экосистемы достаточно каналов git/GitHub (на ранней
  стадии Go использовал такой же подход), а затраты на эксплуатацию и управление сервером Registry
  на этапе, когда сторонних пакетов ещё нет, — чистый долг.
- Сопутствующее ограничение: до запуска официального Registry команда
  `yaoxiang add <голое имя пакета>` недоступна; добавление зависимостей требует явного указания
  источника (`--git` / `--path`).

**Описание реализации Phase 3 (2026-09-28)**:

- Глобальный кэш сначала покрывает **git-канал** (`cache/git/<url>-<tag|rev|commit>/`, ветки
  разрешаются через `ls-remote` в commit и записываются в кэш с указательным файлом для автономного
  отката); `cache/registry/`, `cache/binaries/` — каталоги зарезервированы. Копия vendor исключает
  `.git`, имя каталога — реальная версия, обнаруженная по манифесту зависимости (vendor/lock/очистка
  имеют общий источник).
- Крейты `semver` и `sha2` заменяют самописные реализации согласно таблице зависимостей;
  `is_compatible` изменён с перебора 100 тыс. вариантов на проверку пересечения интервалов.
- В CLI добавлены `outdated` / `clean` / `cache clean`, а для `add` добавлены явные источники
  `--git` / `--path` (реализация вышеуказанного ограничения). `clean` помимо `.yaoxiang/build/`
  также обрезает остаточные пакеты в vendor, на которые нет ссылок в lock.
- Конфигурация `[cache] dir` кэша объединена с существующей системой пользовательской конфигурации
  `~/.config/yaoxiang/config.toml` (на момент черновика RFC файл `~/.yaoxiang/config.toml` не
  существовал), расположение данных кэша по умолчанию остаётся `~/.yaoxiang/cache`.

**Описание реализации Phase 3.5 (2026-09-29)**: диспетчеризация Source по решению 4 использует
закрытое множество `AnySource` из четырёх источников (Local/Git/Registry/GitHub, последние два —
заполнители для Phase 4); `resolve`/`download` trait'а `Source` — нативные `async fn in trait`,
уровень команд управляется через `futures::executor::block_on` (без рантайма, подпроцессы Git
остаются `std::process`; в Phase 4 при подключении reqwest заменить на настоящий исполнитель);
добавлена зависимость `futures` (совместима с wasm32). Параллельная загрузка в install отложена до
введения настоящего рантайма.

**Описание реализации Phase 4 (2026-09-29, коммиты 234dfea5/e1873133/5ffee636)**:

- **Адаптер GitHub** (4a): git-зависимости с github.com направляются в `GitHubSource` — разрешение
  версий идёт через REST API (эндпоинт releases, при пустом результате — откат к tags), загрузка в
  первую очередь с Release в виде актива `.yxpkg` (после распаковки и проверки — в `cache/github/`,
  затем копирование в vendor), при отсутствии актива — откат к клонированию git, при этом SourceKind
  честно сообщает `Git`. Доступ к API — с экспоненциальным откатом (1с/2с/4с, приоритет
  Retry-After) + **кэш условных запросов ETag** (`cache/github/*.etag|body`, ответ 304 не
  учитывается в квоте скорости GitHub); 403 + `x-ratelimit-remaining: 0` распознаётся как основное
  ограничение скорости, без повторных попыток.
- **Формат пакета `.yxpkg`** (4b): tar.gz + манифест `SHA256SUMS` (формат coreutils с двойным
  пробелом), детерминированная упаковка (сортировка записей, обнуление mtime/uid/gid);
  принудительная проверка при распаковке (отсутствие/подделка манифеста, файлы вне манифеста, выход
  за пределы пути, превышение общего объёма распаковки — всё приводит к ошибке); общий объём
  содержимого ограничен 20 МиБ (решение 7). Исключения задаются чёрным списком (`.git` / `.yaoxiang`
  / `target` / `node_modules` / `*.yxpkg` и т.д.), а не белым — `[exports]` позволяет включать файлы
  за пределами `src/` в поверхность экспорта, а белый список молча пропустил бы их.
- **`publish`** (4c): голый `publish` возвращает ошибку с указанием направления (Registry отложен);
  `--dry-run` выполняет «валидация (description обязательно) → упаковка → SHA-256»; `--github` затем
  проверяет наличие Release → проверяет существование тега (семантика как в Cargo: создание тега —
  дело пользователя) → создаёт Release → загружает актив. Целевой репозиторий берётся из
  `[package].repository`, откат — к `git remote origin`; аутентификация читает `$YX_GITHUB_TOKEN`
  (`credentials.toml` будет реализован вместе с официальным Registry). HTTP-стек — reqwest
  (rustls) + собственный рантайм tokio current_thread для управления пакетами
  (`package::runtime::drive`), зависимость `futures` удалена.
- Тестовый прогон перед publish (пункт 3 контрольного списка валидации 014a) подключён вместе с
  Phase 5 (03929ffa).

**Описание реализации Phase 5 (2026-09-30, feat/rfc014)**:

- **Подключение дерева решений установки** (вокруг b6a5b98f и далее): после загрузки зависимостей
  `install/update` для пакетов с `[build]`/`[binaries]` вызывает `build::run_install_build` —
  приоритет предкомпиляции (SHA-256 всего пакета + безопасная распаковка) → заголовки (до 026b —
  явная ошибка) → выполнение стратегии (cargo — реальная реализация / cmake — ожидает реализации /
  custom — шлюз доверия). Пакеты без объявления сборки проходят без затрат.
- **Стратегия cargo**: `[build.cargo]` — формирование команды + слияние переопределений платформы;
  scratch изолирован через `CARGO_TARGET_DIR` в `.yaoxiang/build/`, FFI-артефакты копируются в
  vendor `build/native/<triple>/`; семантика целостности vendor явно определена как целостность
  дерева исходного кода (`build/` не входит в контрольную сумму).
- **Шлюз доверия** (решение 1 из 014b): записи доверия хранятся в пользовательской конфигурации
  `[trust] build-scripts`; `--trust` разрешает и сразу сохраняет; в неинтерактивной среде по
  умолчанию отклоняется.
- Перед publish по умолчанию запускаются тесты (механизм обнаружения из RFC-036), `--no-test`
  пропускает.
- Выполнение cmake и генератор yx-bindgen (RFC-026b) — отложено; остальное см. в описании реализации
  014b.

### Зависимости

- Без предварительных зависимостей
- Требуется интеграция с `ModuleGraph` (`middle/passes/module/`)

### Риски

| Риск                                        | Мера смягчения                                       |
| ------------------------------------------- | ---------------------------------------------------- |
| Сложность алгоритма разрешения зависимостей | Сначала простая версия, затем обнаружение конфликтов |
| Нестабильность загрузки из Git              | Механизмы повторных попыток и кэширования            |
| Проблемы с производительностью              | Ленивая загрузка, инкрементальный парсинг            |
