# RFC-008: Модель параллелизма Runtime и дизайн с развязкой от планировщика

> **⚠️ Примечание о согласовании**: Этот документ согласован с
> [RFC-024: Новая модель параллелизма](../../../reference/language-spec/concurrency.md). Прежний
> анализ DAG для всей программы, аннотации `@block`/`@eager` и иерархическая модель L1/L2/L3 были
> заменены примитивом параллелизма блоков `spawn {}`. Анализ DAG теперь применяется только внутри
> блоков `spawn {}`.

> **Ссылки**:
>
> - [RFC-011: Дизайн системы дженериков](./011-generic-type-system.md)
> - [Спецификация модели параллелизма (RFC-024)](../../../reference/language-spec/concurrency.md)

## Резюме

Этот документ определяет ключевые аспекты дизайна архитектуры Runtime:

1. **Трёхуровневая архитектура Runtime**: Embedded (немедленное выполнение) → Standard (spawn +
   планирование DAG) → Full (work stealing)
2. **Разделение компиляции и выполнения**: фаза компиляции полностью идентична, различия только в
   способе выполнения
3. **Модель с двумя бэкендами**: VM (разработка и отладка) и LLVM AOT (производственный релиз),
   поведение полностью согласовано
4. **Планировщик = статическая библиотека**: при AOT-компиляции планировщик линкуется в exe,
   примерно 200-500KB, без GC
5. **Синхронность — лишь частный случай планирования**: num_workers=1 — это синхронный режим

### Ключевое уточнение: это не Java

```
Java:   .java → .class → JVM（解释/JIT + GC）        ← 永远需要虚拟机
YaoXiang 开发: .yx → IR → VM 执行（快速迭代、步进调试）
YaoXiang 生产: .yx → IR → LLVM → 原生 exe（调度器链接进去）

VM 是开发工具，不是运行时本质。跟 Go 的 go run vs go build 一样。
最终 exe = 你的原生代码 + 调度器静态库 + 反射元数据。没有解释器，没有 JIT，没有 GC。
```

## Мотивация

### Основные противоречия

| Противоречие                  | Описание                                                                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Прозрачность vs контроль      | блок `spawn {}` обеспечивает явное управление параллелизмом, обычный код выполняется последовательно             |
| Ядро vs опциональность        | `spawn` — базовый примитив параллелизма, WorkStealing — расширенная возможность при `num_workers > 1`            |
| Однопоточность vs параллелизм | в однопоточном режиме параллелизм проявляется как асинхронность; синхронность — лишь частный случай планирования |

## Предложение

### 1. Трёхуровневая архитектура Runtime

```
┌──────────────────────────────────────────────────────────────────┐
│                    编译阶段（所有模式相同）                        │
│                                                                  │
│  Source Code → Lexer → Parser → TypeCheck → Codegen → IR        │
│                                                                  │
│  ⚠️ 同一套语法解析、类型检查、代码生成、IR 输出                    │
└──────────────────────────────────────────────────────────────────┘
                               │
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
┌──────────────────┐ ┌───────────────┐ ┌──────────────────┐
│ 🟢 Embedded      │ │ 🔵 Standard   │ │ 🟣 Full          │
│ 即时执行器        │ │ spawn + DAG   │ │ Full 调度器      │
│ 同步执行         │ │ spawn 块内并发 │ │ 并行优化         │
│ 无 spawn 支持    │ │ 自动并发      │ │ 工作窃取         │
└──────────────────┘ └───────────────┘ └──────────────────┘
```

| Фаза                     | Embedded   | Standard                             | Full                                   |
| ------------------------ | ---------- | ------------------------------------ | -------------------------------------- |
| Компиляция               | одинакова  | одинакова                            | одинакова                              |
| Режим выполнения         | синхронный | параллелизм внутри `spawn {}` блоков | параллельный                           |
| Потребление памяти       | низкое     | среднее                              | высокое                                |
| Возможности параллелизма | нет        | внутри `spawn {}` блоков             | внутри `spawn {}` блоков + параллелизм |
| Поддержка `spawn`        | ❌         | ✅                                   | ✅                                     |
| Анализ DAG               | нет        | внутри `spawn {}` блоков             | внутри `spawn {}` блоков               |
| WorkStealer              | нет        | нет                                  | ✅                                     |

**Embedded Runtime**: целевые сценарии — WASM/игровые скрипты/правило-движки. Интерпретатор
немедленного выполнения, без поддержки `spawn`, высокая производительность и низкое потребление
памяти.

**Standard Runtime**: целевые сценарии — веб-сервисы/конвейеры данных. Поддерживает блоки
`spawn {}`, внутри которых выполняется анализ DAG и автоматический параллелизм. `num_workers=1` —
однопоточная асинхронность.

**Full Runtime**: целевые сценарии — научные вычисления/масштабный параллелизм. Standard +
WorkStealer для балансировки нагрузки.

### 2. Развязка планировщика: дженерики + инъекция

Ключевой принцип: VM не зависит напрямую от конкретного планировщика, а вызывается через
параметр-дженерик `[S]`.

```yaoxiang
# 调度器接口定义
Scheduler: Type = {
    spawn: (Task) -> TaskId,
    await: (TaskId) -> Result,
    spawn_with_deps: (Task, List(TaskId)) -> TaskId,
    await_all: (List(TaskId)) -> List(Result),
    stats: () -> SchedulerStats,
}

# 单线程调度器
SingleThreadScheduler: Scheduler = {
    spawn: (task) => { task_queue.push(task); generate_task_id() },
    await: (task_id) => { ... },
    spawn_with_deps: (task, deps) => { ... },
    await_all: (task_ids) => { ... },
    stats: () => { queue_size: task_queue.len() },
}

# 多线程调度器
MultiThreadScheduler: Scheduler = {
    spawn: (task) => { work_queue.push(task); generate_task_id() },
    await: (task_id) => { wait_for_completion(task_id) },
    spawn_with_deps: (task, deps) => { ... },
    await_all: (task_ids) => { ... },
    stats: () => { workers: get_worker_stats() },
}

# VM 通过泛型使用调度器
create_vm: [S: Scheduler](scheduler: S) -> VM = (scheduler) => {
    VM(scheduler: scheduler, memory: create_memory(), dag: create_dag())
}
```

**Ключевые моменты**:

- Полиморфизм на этапе компиляции, нулевые накладные расходы во время выполнения
- Не требуются объекты trait'ов
- Ограничение типа-дженерика `[S: Scheduler]` уже определено в RFC-011

### 3. Синхронность = частный случай планирования

```
❌ 误解：禁用调度器
✅ 正确：使用单 worker 的调度器

num_workers = 1 → 单线程异步调度
num_workers > 1 → 多线程并行调度

同一个调度器接口，只是配置不同。消除特殊情况。
```

### 4. Роль DAG

> **Важное изменение**: анализ DAG больше не применяется ко всей программе, а выполняется только
> внутри блоков `spawn {}`. Обычный код (за пределами блоков `spawn {}`) выполняется последовательно
> и не требует анализа DAG.

| Уровень          | Поддержка `spawn` | Область анализа DAG      | Описание                                 |
| ---------------- | ----------------- | ------------------------ | ---------------------------------------- |
| Core Runtime     | ✅                | внутри `spawn {}` блоков | ядро параллелизма                        |
| Standard Runtime | ✅                | внутри `spawn {}` блоков | `spawn` + планирование DAG               |
| Embedded Runtime | ❌                | нет                      | немедленное выполнение, без параллелизма |

### 5. Модель выполнения снизу-вверх (внутри блоков `spawn {}`)

> **Важное изменение**: восходящий анализ DAG теперь выполняется только внутри блоков `spawn {}` и
> больше не применяется ко всей программе.

```
用户代码（spawn 块内并发）：
    (a, b) = spawn {
        fetch(url0),
        fetch(url1)
    }
    print(a)

编译时分析（spawn 块内自底向上）：
    fetch(url0) 和 fetch(url1) 无相互依赖 → 可并行执行
    spawn 块外的 print(a) → 顺序执行，等待 spawn 完成

运行时调度（spawn 块内从叶子开始）：
    fetch(url0) ┐
                ├→ 并行执行
    fetch(url1) ┘
    print(a)                       ← spawn 块外，顺序执行
```

**Ключевые моменты**:

- Восходящий анализ зависимостей ограничен только внутренней частью блоков `spawn {}`
- Задачи внутри `spawn {}` блоков без зависимостей выполняются параллельно
- Код за пределами `spawn {}` блоков выполняется последовательно, ожидая их завершения

### 6. Модель компиляции: два бэкенда + статическая линковка среды выполнения

#### 6.1 Два бэкенда, одно поведение

```
                      ┌─────────────────────┐
                      │   编译前端（统一）     │
                      │   Lexer → Parser     │
                      │   → TypeCheck        │
                      │   → spawn 块内 DAG 分析│
                      │   → 逃逸分析          │
                      │   → 环检测            │
                      └──────────┬──────────┘
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
        ┌───────────────────┐     ┌───────────────────┐
        │   VM 后端（开发）   │     │  LLVM 后端（生产）  │
        │                   │     │                   │
        │  生成 IR/字节码    │     │  生成原生代码       │
        │  VM 解释执行       │     │  链接运行时静态库   │
        │  支持步进调试       │     │  输出 .exe         │
        │  快速迭代          │     │  零解释开销         │
        └───────────────────┘     └───────────────────┘
                 │                         │
                 ▼                         ▼
           行为完全一致                 行为完全一致
```

**Бэкенд VM**: используется при разработке. Изменить код → запустить мгновенно → пошаговая отладка →
быстрая итерация. Поведение полностью совпадает с финальным exe.

**Бэкенд LLVM**: используется при выпуске. AOT-компиляция в нативный код, планировщик линкуется как
статическая библиотека. Никакого интерпретатора, никакого JIT.

#### 6.2 Планировщик = статическая библиотека, а не виртуальная машина

```
最终 exe 的内部结构：

┌────────────────────────────────────────────┐
│  你的代码（原生机器码）                       │
│  ├── 编译期已确定的 DAG 执行计划              │
│  ├── 内联的 Move/ref/clone 操作              │
│  └── RAII 释放代码                          │
├────────────────────────────────────────────┤
│  运行时静态库（~200-500KB）                   │
│  ├── 线程池（固定大小 = num_workers）         │
│  ├── 事件循环（libuv / io_uring）            │
│  ├── 工作窃取队列（仅 Full Runtime）          │
│  ├── 内存分配器（jemalloc / mimalloc）       │
│  └── 反射元数据（按需加载，不常驻内存）         │
├────────────────────────────────────────────┤
│  没有：                                      │
│  ❌ 字节码解释器                             │
│  ❌ JIT 编译器                               │
│  ❌ GC                                      │
│  ❌ 虚拟机                                    │
└────────────────────────────────────────────┘
```

Сравнение:

| Язык                    | Java                    | Go                  | YaoXiang                                         |
| ----------------------- | ----------------------- | ------------------- | ------------------------------------------------ |
| Артефакт компиляции     | байт-код                | нативный код        | нативный код                                     |
| Способ выполнения       | интерпретация/JIT в JVM | прямое выполнение   | прямое выполнение                                |
| Размер среды выполнения | ~200MB (JVM)            | ~1-2MB (включая GC) | **~200-500KB (без GC)**                          |
| Управление памятью      | GC                      | GC                  | **RAII (детерминированно)**                      |
| Рефлексия               | постоянно в памяти      | постоянно в памяти  | **хранится в exe, загружается по необходимости** |

#### 6.3 Почему производительность планировщика постоянна

**Ключевое наблюдение**: бо́льшая часть работы выполняется на этапе компиляции, во время выполнения
происходит только «выполнение».

```
编译期（一次性，不进入运行时）：
    ├── 分析 spawn 块内 DAG：谁依赖谁
    ├── 拓扑排序：确定 spawn 块内执行顺序
    ├── 识别可并行任务：spawn 块内无依赖的子树
    ├── 逃逸分析：ref → Rc 还是 Arc
    ├── 环检测：自动降级 Weak 或报错
    └── 内联：小函数直接展开

运行时（每次执行，数据结构固定）：
    ├── 按编译期确定的 spawn 块 DAG 顺序分发任务到线程池
    ├── 遇到 I/O → 挂起当前任务，事件循环接管
    ├── 任务就绪 → 放回就绪队列
    └── 就这些。
```

**Сам планировщик — это структура данных фиксированного размера**: пул потоков, цикл событий,
очереди задач. Никакого динамического роста, никакой адаптивной реоптимизации, никакого сканирования
GC. Поведение полностью предсказуемо.

На этапе компиляции уже рассчитано, что именно «планировать» внутри `spawn {}` блоков; во время
выполнения происходит только «выполнение». Это отличается от tokio — tokio динамически строит
цепочки `Future` во время выполнения. DAG в YaoXiang статический и ограничен только внутренней
частью `spawn {}` блоков.

#### 6.4 Рефлексия: хранится, но не находится постоянно в памяти

Метаданные рефлексии генерируются на этапе компиляции и хранятся в отдельной секции exe. При запуске
программы они не загружаются. При первом запросе рефлексии они подгружаются в память через `mmap` по
необходимости. Аналогия:

```
exe 布局：
  .text     ← 你的代码
  .rodata   ← 常量
  .reflect  ← 反射元数据（类型信息、函数签名等）
              mmap 按需加载，不访问不占内存
```

**Компромисс**: размер exe увеличивается (включая данные рефлексии), но при отсутствии обращений во
время выполнения — нулевые расходы памяти. При первом обращении есть задержка загрузки (аналог
прогрева JIT), далее — нулевые накладные расходы.

## Компромиссы

### Преимущества

- **Чёткое разделение на уровни**: три уровня Embedded / Standard / Full
- **Повторное использование при компиляции**: код фронтенда полностью общий
- **Развязка через дженерики**: полиморфизм на этапе компиляции, нулевые накладные расходы
- **Согласованность**: синхронность — лишь частный случай планирования
- **Дружественность к встраиваемым системам**: высокая производительность + низкое потребление
  памяти + быстрый запуск

### Недостатки

- **Начальная сложность**: необходимо определить интерфейс планировщика и несколько вариантов среды
  выполнения
- **Привязка на этапе компиляции**: тип планировщика определяется во время компиляции

| WorkStealer                           | Расширенная возможность Full Runtime                                   | 2025-01-05 |
| Дизайн встраиваемой системы           | Немедленное выполнение, без планирования DAG                           | 2025-01-05 |
| Фаза компиляции                       | Все среды выполнения используют общий фронтенд                         | 2025-01-05 |
| Разделение среды выполнения на уровни | Embedded / Standard / Full                                             | 2025-01-05 |
| Ограничение типа                      | Уже определено в RFC-011                                               | 2025-01-25 |
| Построение графа зависимостей         | Статический граф зависимостей, определяется на этапе компиляции        | 2025-01-05 |
| Модель с двумя бэкендами              | VM (разработка и отладка) + LLVM AOT (продакшн), поведение согласовано | 2026-05-11 |
| Форма планировщика                    | Статическая библиотека, слинкованная в exe, ~200-500KB, без GC         | 2026-05-11 |
| Метаданные рефлексии                  | Компилируются в отдельную секцию exe, `mmap` по необходимости          | 2026-05-11 |
| Производительность планировщика       | Анализ DAG на этапе компиляции, на этапе выполнения только выполнение  | 2026-05-11 |
| Согласование области DAG              | Анализ DAG только внутри `spawn {}` блоков, согласовано с RFC-024      | 2026-06-05 |
| Обновление трёхуровневой архитектуры  | Embedded без `spawn`, Standard поддерживает `spawn`                    | 2026-06-05 |
