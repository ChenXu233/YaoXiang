# RFC-009a: Анализ времени жизни токенов — на основе конвейера доказательств Хоара

> **Родительский RFC**: [RFC-009: Дизайн модели владения](../accepted/009-ownership-model.md)
>
> **Зависимости**:
> [RFC-027: Предикаты времени компиляции и унифицированная статическая верификация](../accepted/027-compile-time-evaluation-types.md)
>
> **Предварительные условия**: RFC-027 должен быть принят. Все механизмы настоящего RFC (конвейер
> доказательств, SMT-fallback, сбор условий пути) зависят от реализации RFC-027.
>
> **Настоящий RFC исправляет и заменяет раздел RFC-009 §«Обнаружение конфликтов токенов:
> потоково-чувствительный анализ живости» (строки 663-684).**

## Резюме

Строка 684 RFC-009 утверждает, что обнаружение конфликтов токенов «не нуждается в……NLL». Вывод
верен, аргумент ошибочен.

Дело не в том, что «поскольку токены — это значения, достаточно линейного отслеживания». Дело в том,
что: **живость токена — это логическое утверждение Хоара, а не специальный потоково-чувствительный
анализ.**

`{все conflicting_tokens мертвы} op {WriteToken безопасно получен}` — то же самое `{P} op {Q}`,
разделяющее конвейер доказательств RFC-027 с проверкой типов и верификацией предикатов. Никаких
новых аналитических фреймворков. Один конвейер, множество утверждений.

---

## Мотивация

### Путаница в RFC-009

RFC-009 смешивает две задачи:

1. **Линейное отслеживание** (недоступно после Move) — `{v не перемещён} use(v) {тип совпадает}`.
   Уже есть в проверщике типов.
2. **Взаимодействие времён жизни токенов** (дочерний токен жив → родительский токен приостановлен →
   дочерний токен умер → родительский токен возрождён) —
   `{все conflicting_tokens мертвы} write(data) {безопасно}`. Требуется **анализ живости**, а не
   линейное отслеживание.

### Текущее состояние кода

| Компонент                                  | Состояние                                                                                               |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `BorrowChecker`                            | Линейное сканирование IR, пассивное реагирование на явные инструкции `Borrow`/`Release`                 |
| `ControlFlowAnalyzer::analyze_instruction` | Пустая реализация (`control_flow.rs:145-153`)                                                           |
| `liveness_analysis`                        | Существует, но используется только для вставки Drop, не подключён к конфликтам токенов                  |
| Вставка Release                            | Жёстко закодирована после инструкции Call — чисто лексическая область видимости (`ir_gen.rs:2734-2736`) |

**Видимые пользователю последствия**:

```yaoxiang
data = vec![1, 2, 3]
view = &data              # Создание ReadToken
x = view.total_count      # Последнее использование view
data.push(4)              # ❌ Release(view) ещё не выполнен, ReadToken «жив»
```

### Почему требуется переписать

Предыдущая версия (009a v1) использовала нарратив «DAG вместо NLL», вводя ненужные новые концепции
(консервативные правила ветвления, специальная обработка циклов). Основное противоречие не было
прояснено: **проверка заимствований — это не независимая система — она является одним из утверждений
Хоара.**

## Основной дизайн

### Всё есть Хоар

```
проверка типов:               { x: Int }        x + 1        { result: Int }
проверка заимствований:       { view мёртв }    data.push(4)  { WriteToken успешно получен }
верификация предикатов:       { y > 0 }         divide(x, y)  { result: Int }
разрезание обратного ребра:   { i == n }        следующая итерация цикла     { cond == false }
```

Та же форма `{P} op {Q}`. Компилятор для каждой операции генерирует предусловие P и отправляет его в
конвейер доказательств для верификации.

**Проверка заимствований и пользовательские предикаты разделяют один конвейер.** Различие только в
том, кто генерирует утверждение и что происходит, когда его не удаётся доказать.

### Два типа предикатов, один конвейер

|                               | Пользовательский предикат                                 | Системный предикат (заимствование)                   |
| ----------------------------- | --------------------------------------------------------- | ---------------------------------------------------- |
| Генерация утверждения         | Программист (аннотации типов)                             | Компилятор (дерево брендов + правила владения)       |
| Предоставление доказательства | Компилятор + программист                                  | **Полностью автоматически компилятором**             |
| Не доказывается               | Написать функцию доказательства или выполнить рефакторинг | Рефакторинг кода (дверь есть, но нужна крайне редко) |
| Видимость                     | Виден в сигнатуре                                         | Неявный, не загрязняет сигнатуру типа                |
| Стоимость обучения            | Учите, если хотите использовать                           | Ноль                                                 |

**Доказательство системного предиката не открывает программисту функцию доказательства — компилятор
полностью автоматический.** При недоказуемости пользователь рефакторит код.

**Три режима отказа, один движок верификации.** Утверждение типа не доказывается → ошибка компиляции
(необходимо обойти). Утверждение заимствования не доказывается → ошибка компиляции, рефакторинг кода
(необходимо обойти). Пользовательский предикат не доказывается → ошибка компиляции, можно написать
функцию доказательства (можно обйтти). Стратегии отказа различаются, но движок верификации один и
тот же — решатель SMT + правила вывода ядра компилятора. Различие только в том, «кто отвечает за
дополнение доказательства, когда оно не получается» — компилятор отказывается писать за программиста
доказательство заимствования (стратегия доказательства утверждений заимствования — структурный
анализ + SMT, вмешательство программиста не требуется), но принимает функции доказательства
пользовательских предикатов, написанные программистом. Это не противоречие в конвейере — это
различие границ ответственности для разных категорий утверждений.

Это отличается от Rust `'a`: `'a` — обязательный курс, а функция доказательства — факультативный;
подавляющее большинство пользователей за всю жизнь так и не открывают эту факультативную дверь.

### Предикат заимствования: автоматически генерируется компилятором

Пользователь пишет `data.push(4)`. Компилятор автоматически генерирует утверждение:

```
WriteToken(data, node) может быть получен
  = forall t в conflicting_tokens(data): t мёртв в node
  = forall t в brand_tree.children(data): forward_reachable(node) ∩ consumers(t) == ∅
```

**Три правила, ноль особых случаев:**

1. **Дерево брендов** (RFC-009 §2.7) отвечает на вопрос «кто с кем конфликтует»: сопоставление
   префиксов, O(depth), глубина ≤ 3
2. **Список потребителей** (автоматически собирается при построении DAG) отвечает на вопрос «кто
   последним потребляет токен»
3. **Прямая достижимость** отвечает на вопрос «может ли потребитель ещё быть выполнен»: структурное
   обрезание + логическое обрезание

### Прямая достижимость: обратный обход от потребителей

Для каждого потребителя C токена T:

```
Из C выполняем обратный BFS по DAG.
Ребро обрезается, если:
  1. Это break (структурное обрезание)
  2. Условие пути ⇒ !loop_cond доказано SMT как истинное (логическое обрезание, конвейер RFC-027)

Распространяемся в обратном направлении по всем необрезанным рёбрам (включая обратные рёбра, обратное ребро переносит живость в предыдущую итерацию).
Помечаем все достижимые узлы → unsafe.
```

Запрос: операция записи в узле W → W ∉ unsafe → безопасно.

**Не нужно изобретать «консервативные правила ветвления». Не нужно «консервативной живости в цикле».
Один обратный BFS + два правила обрезания.**

### Стратегия доказательства: быстрый путь в приоритете, SMT как страховка

```
Каждая операция записи, требующая токена
  │
  ├→ Быстрый путь: структурный анализ DAG (покрывает 95%+ сценариев)
  │     │
  │     ├→ Сопоставление префиксов дерева брендов → поиск конфликтующих токенов (O(depth))
  │     ├→ Обратный BFS, break обрезает обратные рёбра
  │     └→ Нет проходимых обратных рёбер → прямое решение Proved / Disproved
  │
  └→ Медленный путь: логическое обрезание SMT (только когда быстрый путь встречает проходимое обратное ребро)
        │
        ├→ Начало обратного ребра имеет условие пути → SMT проверяет path_cond ⇒ !loop_cond
        │     ├→ Proved → логическое обрезание → возврат на быстрый путь
        │     └→ Disproved / Unproven → пересечение обратного ребра → пометить как unsafe
        │
        └→ Начало обратного ребра не имеет условия пути → прямое пересечение обратного ребра
```

**Покрытие быстрого пути**: линейный код, if/else, loop + break, while без условий пути. **Покрытие
медленного пути**: тело цикла while, когда условия пути указывают на выход из цикла. **Не
покрывает**: условия времени выполнения не могут быть статически доказаны → пересечение обратного
ребра → unsafe → ошибка компиляции (рефакторинг пользователем).

SMT — не основной инструмент, а страховочная сетка. В отличие от пользовательских предикатов
RFC-027: пользовательские предикаты полагаются на SMT как на основной инструмент; системные
предикаты заимствования полагаются на структурный анализ как на основной инструмент, SMT лишь
дополняет углы, недоступные структурному анализу.

> **Исправление (2026-08-17, уточнение позиции SMT)**: SMT — это **уровень точности, а не
> зависимость от soundness**. Sound-решение для системных предикатов заимствований полностью
> обеспечивается быстрым путём (интервалы + обратный BFS + обрезание break); логическое обрезание
> SMT лишь определяет, «пропускать ли корректные программы с границами циклов». Когда SMT недоступен
> / истекает время ожидания / не реализован (RFC-027 impl: in_progress), fallback = пересечение
> обратного ребра = консервативный отказ, всё, что должно быть отклонено, по-прежнему будет
> отклонено. **Консервативность без SMT = заимствование + запись внутри цикла всегда отклоняется, на
> одном уровне с Rust NLL** (производственная проверка заимствований в Rust также обходится без
> SMT). Внедрение SMT — это чистый прирост точности, не блокирующее поставку sound-основной линии.

## Анализ вариантов использования

### Линейный код

```yaoxiang
data = vec![1, 2, 3]        # Узел 1
view = &data                # Узел 2: потребляет data, производит ReadToken(#1)
x = view.total_count        # Узел 3: потребляет view (= последний потребитель #1)
data.push(4)                # Узел 4: требует WriteToken(data)
```

Обратный BFS из `view.total_count` (узел 3) → узел 3 — последний потребитель #1 → узел 4 > узел 3 →
узел 4 не в unsafe → ✅

### if/else: без специальных правил

```yaoxiang
view = &data
if cond {
    use(view)               # then-ветвь потребляет view
} else {
    do_something_else()     # не трогает view
}
data.push(4)                # Последний потребитель view в if → после if нет потребителей → ✅
```

if/else — составной узел DAG. Внутреннее потребление приписывается этому узлу. Состояния ветвей не
объединяются. Консервативного голосования нет. **Есть ли потребитель после — целочисленное
сравнение.**

> **Уточнение (после #264)**: «состояния ветвей не объединяются» относится только к **живости
> заимствований** (обратный BFS потребителей бренда). **Состояние move** (владение переменной) — это
> отдельный анализ: прямой поток данных по узлам CFG (#264, в стиле NLL/Polonius), при слиянии
> ветвей **консервативный meet** (если хотя бы в одной ветви Moved → в точке слияния Moved),
> недостижимые литерально ветви (`if false`) не участвуют. Два слоя: живость заимствований смотрит
> «есть ли последующий потребитель», анализ move смотрит «возможно ли переменная уже перемещена».

### if/else с побегом возвращаемого значения

```yaoxiang
view = &data
result = if cond {
    view                     # view убегает в result
} else {
    something_else
}
use(result)                  # Косвенное потребление view
data.push(4)                 # у view ещё есть потребитель (use(result))
                             # → push в unsafe → ❌ Корректная ошибка
```

view убегает через возвращаемое значение → `use(result)` — потребитель view → из `push` обратный
обход достигает `use(result)` → unsafe.

### Цикл: break обрезает обратное ребро

```yaoxiang
view = &data
loop {
    use(view)                # consumer
    if is_last {
        data.push(4)         # операция записи
        break                # ← структурное обрезание
    }
}
```

Обратный BFS из `use(view)` → обратное ребро → проход вперёд к `data.push(4)` → встречает `break` →
**обрезание** → `data.push(4)` не в unsafe → ✅

Без break:

```yaoxiang
view = &data
loop {
    use(view)
    data.push(4)             # Нет обрезания break → обратное ребро проходимо → следующий use(view) достижим
                             # → push в unsafe → ❌ Корректная ошибка
}
```

### while: логическое обрезание SMT

```yaoxiang
view = &data
mut i: UpTo(n) = 0
while i < n {
    use(view)                # consumer
    i += 1
    if i == n {
        data.push(4)         # условие пути: i == n
    }
}
```

Обратный BFS из `use(view)` → обратное ребро → проход к `data.push(4)` → проверка условия пути
`i == n` → SMT-запрос: `i == n ⇒ !(i < n)`? → Proved → **логическое обрезание** → `data.push(4)` не
в unsafe → ✅

> Исправление (2026-08-17): `i == n` — это условие пути самого узла записи (операция `data.push(4)`
> внутри ветви if), цель решения — условие самого узла записи (см. §Правила сбора условий пути,
> правило 1).

## Суть: ID бренда — это и есть `'a`

Не говорим «нам не нужен `'a`». Говорим «`#42` — это и есть `'42`».

| Rust                                        | YaoXiang                                     | Эквивалентность                                              |
| ------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| `'a`                                        | `#42`                                        | Идентификатор времени жизни, известный во время компиляции   |
| Ограничение `'a: 'b` outlives               | `#42` — префикс `#42.field_x`                | Сравнение строковых префиксов = отношение частичного порядка |
| Распространение живости NLL (фикспоинт CFG) | Обратный BFS (DAG)                           | Оба вычисляют достижимость                                   |
| Факты Polonius                              | Логическое обрезание SMT                     | Оба рассуждают об условиях пути                              |
| Решение фикспоинта системы ограничений      | Сопоставление префиксов дерева брендов + BFS | Разная кодировка, одна задача                                |

**Мы не изобретаем новый анализ. Мы лишь переместили `'a` с уровня сигнатур типов на уровень
доказательств.** ID бренда делает то же, что и `'a` — помечает идентичность заимствования,
отслеживает отношения наследования, определяет конфликты. Различие только одно: `'a` находится в
сигнатуре типа, написанной пользователем; `#42` — внутри компилятора.

**В этом нет ничего зазорного.** Curry-Howard говорит, что тип — это утверждение, программа — это
доказательство. `'a` не является частью утверждения — оно является частью стратегии доказательства.
Rust вписал стратегию доказательства в сигнатуру утверждения. Мы вернули его туда, где ему и место.

### Что устраняют ограничения дизайна языка

| Источник сложности                                      | Устранено? | Причина                                                                          |
| ------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------- |
| Затенение переменных                                    | ✅         | Запрещено языком — одно имя всегда указывает на одно и то же                     |
| Межитерационное заимствование в for                     | ✅         | Новое связывание в каждой итерации — естественная изоляция между итерациями      |
| Аннотации времени жизни `'a`                            | ✅         | Путь бренда = `#42.field_x`, выводится компилятором                              |
| Именованные времена жизни + распространение ограничений | ✅         | Сравнение префиксов пути бренда заменяет явный набор ограничений                 |
| Решение ограничений графа заимствований (Polonius)      | ✅         | Сопоставление префиксов дерева брендов + запрос потребителей DAG                 |
| Распространение живости заимствований в теле цикла      | ❌         | Как и в Rust, требует обработки — используем обратный BFS + логическое обрезание |
| Консерватизм условных ветвей                            | ❌         | Как и в Rust — SMT покрывает доказуемое, остальное консервативно отклоняется     |

### Почему DAG работоспособен

Три ограничения дизайна языка YaoXiang делают анализ DAG работоспособным:

- **Отсутствие затенения переменных** — одно имя всегда указывает на одно и то же, не нужно
  отслеживать межсвязывающие назначения
- **Новое связывание в каждой итерации for** — естественная изоляция между итерациями,
  межитерационное заимствование отсутствует
- **Структурированная конкурентность** — чёткие границы задач, не нужно распространять живость между
  задачами

Эти ограничения устраняют основные источники сложности итераций фикспоинта CFG в Rust. Не DAG «более
продвинутый», чем CFG — более простой дизайн языка позволяет более простой анализ.

## Детальный дизайн

### Список системных предикатов

Компилятор автоматически генерирует следующие утверждения и отправляет их в конвейер доказательств
RFC-027:

| Системный предикат | Момент срабатывания                | Форма утверждения                             |
| ------------------ | ---------------------------------- | --------------------------------------------- |
| `borrow_conflict`  | Требуется WriteToken(v)            | `forall t ∈ conflicting(v): dead_at(t, node)` |
| `use_after_move`   | Использование переменной v         | `¬moved(v)`                                   |
| `use_after_drop`   | Использование переменной v         | `¬dropped(v)`                                 |
| `double_drop`      | Drop(v)                            | `¬dropped(v)`                                 |
| `mut_violation`    | Запись в неизменяемую переменную v | `is_mut(v)`                                   |

Существующие `BorrowChecker`, `MoveChecker`, `DropChecker`, `MutChecker` **становятся генераторами
утверждений** — не исчезают, а меняют роль. Они генерируют утверждения, конвейер верифицирует
утверждения.

### Дерево брендов

Механизм брендов из RFC-009 §2.7 формализуется как дерево брендов.

**Семантика токенов — заморозка первична, не копирование**:

Сущностное различие между `&T` и `&mut T` не в том, «можно ли копировать», а в том, «разрешено ли
одновременное наличие записи»:

```
ReadToken(T): Предоставляет право только на чтение, одновременно замораживая
             исходные данные T — любой WriteToken(T) в этот период
             не может быть получен. Заморозка — первичная семантика ReadToken.
             Dup (копируемость) — следствие заморозки: поскольку данные
             уже заморожены (мутация невозможна), несколько представлений
             только для чтения по природе своей безопасны.

WriteToken(T): Предоставляет исключительное право на чтение и запись.
              Поскольку возможна запись, никакой другой токен (чтения
              или записи) не может сосуществовать. Отсутствие Dup
              (линейный тип) — следствие исключительности.
```

**Причинно-следственная связь**:

```
ReadToken существует → исходные данные заморожены → несколько представлений только для чтения безопасны → Dup
                       ↓
               WriteToken отклонён (принуждается системным предикатом borrow_conflict)
```

А не:

```
ReadToken имеет Dup → может быть несколько → заодно проверяем конфликт  ← инверсия причинности
```

```
BrandTree:
  nodes: Map<BrandId, BrandNode>

BrandNode:
  id: BrandId               # "#42", "#42.field_x"
  kind: ReadToken | WriteToken
  source_var: Operand
  parent: Option<BrandId>   # Родительский узел в отношении наследования
  children: Set<BrandId>    # Производные дочерние токены
  consumers: Set<NodeId>    # Узлы DAG, потребляющие этот токен
  ref_count: usize          # Число безопасных копий во время заморозки ReadToken
```

**Определение конфликта — механизм принуждения через заморозку**:

```rust
fn conflicts(a: &BrandId, b: &BrandId) -> bool {
    // Условие конфликта: один источник + хотя бы один пишущий + перекрытие путей бренда
    // Это означает:
    //   1. ReadToken vs ReadToken → нет конфликта (оба только для чтения, мутации нет)
    //   2. WriteToken vs ReadToken → конфликт (запись нарушает гарантию заморозки чтения)
    //   3. WriteToken vs WriteToken → конфликт (два пишущих не могут сосуществовать)
    a.source() == b.source()
        && (a.is_write() || b.is_write())
        && (a.is_prefix_of(b) || b.is_prefix_of(a))
}
```

Сравнение строковых префиксов O(depth), глубина ≤ 3. Константный уровень.

### Анализ живости обратным BFS

> **Исправление (2026-08-17, аудит #251 P0-6)**: приведённый ниже алгоритм дополнен измерением
> «времени создания токена». Исходный текст полагался на полный порядок узлов DAG, неявно
> подразумевая «заимствование предшествует записи», и не покрывал корректный порядок «сначала
> запись, затем заимствование» (семантика §2.4: токен-параметр освобождается в конце вызова) — аудит
> выявил ложное срабатывание в этом сценарии (#290). Живость токена — это **интервал**
> `[created_at, last_use]`, а не множество обратной достижимости; операция записи конфликтует с
> токеном только в пределах его интервала живости.

```
Алгоритм: check_borrow(token, node, dag, brand_tree)

Вход:
  token: WriteToken, который нужно проверить
  node:  Узел DAG, в котором происходит операция записи

Выход: Proved | Disproved

Алгоритм:
  # Быстрый путь: обратный BFS
  unsafe = empty_set
  queue = brand_tree.consumers(token)

  while queue not empty:
    cur = queue.pop()
    unsafe.add(cur)

    for each pred in dag.predecessors(cur):
      # Структурное обрезание: break не пересекается
      if pred является ребром break:
        continue

      # Обратное ребро → проверить, нужен ли SMT fallback
      if pred является обратным ребром:
        path_cond = условие пути узла записи node   # Исправление: цель решения — условие самого узла записи
        loop_cond = условие цикла
        # Сначала проверить, возможно ли структурное обрезание (соответствующий break уже обрезал путь → сюда не дойдём)
        # Затем проверить условие пути
        if path_cond непусто:
          result = smt_fallback(path_cond, loop_cond)   # ← медленный путь
          if result == Proved:
            continue                    # логическое обрезание
        # Нет условия пути или SMT не доказал → пересечь обратное ребро
        # fall through

      if pred ∉ unsafe:
        queue.push(pred)

  # Решение (исправление: добавлен интервал времени создания)
  # Сначала запись, затем заимствование: node < created_at(token) → во время записи токен ещё не существовал → Safe
  if node ∈ unsafe and created_at(token) ≤ node:
    return Disproved
  else:
    return Proved


smt_fallback(path_cond, loop_cond):
  # Вызывается только при обратном ребре + наличии условия пути
  # Использует конвейер доказательств RFC-027, разделяя тот же решатель SMT и тот же бюджет
  return smt.prove(path_cond ⇒ !loop_cond)
  # Proved → логическое обрезание
  # Disproved / Unproven → не обрезать, пересечь обратное ребро (консервативный отказ)
  # Исправление (2026-08-17): SMT недоступен/истёк таймаут/не реализован = ветвь Disproved —
  # SMT влияет только на точность (пропускаются ли корректные программы), не на soundness
  # (всё, что должно быть отклонено, отклоняется); консервативность без SMT = заимствование
  # + запись внутри цикла всегда отклоняется, на одном уровне с Rust NLL.
```

В BrandNode добавляется поле (исправление):

```
BrandNode:
  ...
  created_at: NodeId         # Узел создания токена (исправление: левый конец интервала заимствования)
```

O(N), где число вызовов SMT = число обратных рёбер × доля обратных рёбер с условиями пути. В
реальном коде вызовы SMT крайне редки — срабатывают только в теле цикла `while` при наличии
переменных уточнённого типа в условиях пути.

### Сбор условий пути

Предоставляется уже существующими механизмами RFC-027 §3.2-3.3:

- **if guard**: `if y > 0` → в true-ветвь помещается `y > 0`
- **match паттерн**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **Присваивание**: `i += 1`, компилятор поддерживает информацию о диапазоне значений переменной
- **while cond**: внутри тела цикла помещается `cond == true`

Каждый узел DAG несёт набор условий пути. При обратном BFS на обратном ребре берётся условие пути
начала обратного ребра, SMT определяет, исключает ли оно условие входа в следующую итерацию цикла.

> **Исправление (2026-08-17, дополнение правил распространения)**: исходный текст не определял, как
> условия пути распространяются до начала обратного ребра, что делало вариант использования «while +
> логическое обрезание SMT» с `i == n` невоспроизводимым. Дополненные правила:
>
> 1. **Условие пути прикреплено к самому узлу записи**: операция записи W внутри ветви несёт условие
>    этой ветви (`if i == n { W }` → path_cond(W) = `i == n`). При пересечении обратного ребра
>    обратным BFS SMT определяет `path_cond(W) ⇒ !loop_cond` (путь, ведущий к W, неизбежно выходит
>    из цикла → следующий consumer недостижим → обрезание), а не условие пути узла обратного ребра.
> 2. **Консервативная очистка при слиянии**: точка слияния if/else не несёт условий пути из ветвей
>    (дизъюнкция условий ветвей обычно неразрешима, очищается напрямую). Операции записи после точки
>    слияния имеют пустое path_cond → пересечение обратного ребра.
> 3. **Семантизация условий пути**: path_cond — это ConstExpr (семантика RFC-027 §3.2), а не текст
>    исходного кода; smt_cut переводит его в ограничения SMT и затем решает.
> 4. **Нет условия пути → прямое пересечение обратного ребра** (unsafe), без вызова SMT.

### Интерфейс с RFC-027

Системные предикаты заимствований и пользовательские предикаты разделяют один конвейер доказательств
— различие в **основной стратегии доказательства**:

| Тип запроса               | Источник утверждения         | Основная стратегия                        | Fallback                            |
| ------------------------- | ---------------------------- | ----------------------------------------- | ----------------------------------- |
| Равенство типов           | Проверщик типов              | Структурная эквивалентность               | —                                   |
| Пользовательский предикат | Аннотации типов программиста | SMT                                       | Функция доказательства программиста |
| Конфликт заимствований    | Автогенерация компилятором   | **Структурный анализ DAG (быстрый путь)** | Логическое обрезание SMT            |

Роль решателя SMT в проверке заимствований: **не основной инструмент, а страховочная сетка.**
Вызывается только тогда, когда требуется логическое обрезание обратного ребра while. Подавляющее
большинство проверок заимствований завершается на быстром пути — обратный BFS O(N), нулевые затраты
SMT.

### Отношения с существующим кодом

| Существующий компонент        | Обработка                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| `BorrowChecker`               | Становится `BorrowPredicateEmitter` — генерирует утверждения Хоара для заимствований |
| `MoveChecker`                 | Становится `MovePredicateEmitter` — генерирует утверждения `¬moved(v)`               |
| `DropChecker`                 | То же — генерирует утверждения, связанные с Drop                                     |
| `MutChecker`                  | То же — генерирует утверждения `is_mut(v)`                                           |
| `ControlFlowAnalyzer`         | Больше не нужен — конвейер обрабатывает унифицированно                               |
| `liveness_analysis`           | Сохраняется — вставка Drop по-прежнему требует информации о живости переменных       |
| Хардкод Release в `ir_gen.rs` | Удаляется — позиция Release определяется анализом потребителей DAG                   |

### NLL и границы итераций

> **Исправление (2026-08-17, дополнение модели интервалов)**: живость токена — это **интервал**
> `[created_at, last_use]`, а не множество обратной достижимости. `created_at` = узел создания
> токена; `last_use` = максимальный узел потребления из анализа потребителей. Достаточное и
> необходимое условие конфликта операции записи W с токеном T:
> `conflicts(T, W) ∧ created_at(T) ≤ node(W)` `∧ node(W) может пройти вперёд к last_use(T)`
> (определяется обратным BFS). Корректный порядок «сначала запись, затем заимствование» (§2.4:
> токен-параметр освобождается в конце вызова) напрямую исключается условием
> `created_at(T) ≤ node(W)` без каких-либо специальных правил. Эта модель делает заявление
> §Преимущества 5 «алгоритм не консервативен» справедливым для всех порядков.

**Момент смерти токена = точка последнего использования (NLL), а не конец лексической области
видимости.**

Это естественное следствие анализа потребителей: позиция потребителя определяет последнее
использование токена. `use(v)` — потребитель `v` → `v` умирает сразу после `use(v)`. Не нужны
дополнительные `{}` или `drop()` для досрочного завершения жизни токена.

**Граница итерации цикла — линия смерти копий токена.** Три правила:

```
Правило 1: Переменные, объявленные внутри цикла, автоматически умирают в конце каждой итерации.
           for в каждой итерации даёт новое связывание (гарантируется дизайном языка), loop — аналогично.

Правило 2: ref_count дерева брендов в заголовке цикла учитывает только копии, созданные снаружи цикла.
           Новые копии, созданные Dup внутри цикла, обнуляют ref_count на границе итерации.

Правило 3: При пересечении обратного ребра обратным BFS информация о живости текущей итерации не переносится.
           Переносится только ref_count на момент заголовка цикла (т.е. копии снаружи цикла).
```

Пример:

```yaoxiang
view = &data                          # Заголовок цикла: ref_count = 1, consumer = use(view)
loop {
    v2: &Point = view                 # Dup внутри цикла → ref_count = 2
    use(v2)                           # consumer: последнее использование v2 → v2 умирает → ref_count = 1
    data.push(4)                      # ✅ Безопасно! v2 мёртв, остался только view (ref_count = 1, не конфликт записи)
    # Граница итерации: правило 3 — v2 не переносится в следующую итерацию. В начале следующей итерации v2 пересоздаётся через новое связывание.
}
```

Этот дизайн не требует дополнительного правила «консервативной живости в цикле». Обратный BFS
начинается от потребителя, потребитель внутри тела цикла → живость ограничена текущей итерацией →
обратное ребро не пересекается. Полностью согласуется с примером цикла в §Анализ вариантов
использования.

### `?` распространение ошибок и Release под управлением области видимости

`?` — это досрочный возврат — за пределами нормального выхода из области видимости появляется
дополнительный путь выхода. Токен должен быть освобождён на этом пути, неправильный порядок
освобождения — UB.

**Инструкция Release генерируется анализом областей видимости, а не жёстко закодирована после
Call.**

Компилятор поддерживает список точек выхода для каждой области видимости:

- `}` (нормальное окончание области видимости)
- `?` (распространение ошибки, досрочный return)
- Явный `return`

В каждой точке выхода в обратном порядке объявления (LIFO) вставляются инструкции Release для всех
активных токенов этой области видимости. Отношения родитель-потомок в дереве брендов автоматически
обрабатывают каскадное освобождение производных токенов:

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)    # Возвращает дочерний токен &Float + родительский токен &Point
}

fn use_case(p: Point) -> Result<(), Error> = {
    (x_ref, p_ref) = p.get_x()?   # Если ? распространяет:
    # Дерево брендов знает, что x_ref — производный от p_ref (#42.field_x — префикс #42)
    # Порядок освобождения: x_ref (потомок) → p_ref (родитель) → LIFO выполняется автоматически
    p.modify()                     # WriteToken — все ReadToken уже освобождены
    Ok(())
}
```

Место реализации: остаётся в `ir_gen.rs`, изменяется на управляемое областью видимости — без
введения нового прохода компилятора.

| Определение конфликта | O(1) | Каждый раз, когда требуется токен | | Запрос потребителей DAG |
O(1) | Каждый раз, когда требуется токен | | Обратный BFS (быстрый путь) | O(N) | Каждый раз, когда
требуется токен, N = число узлов в блоке | | Логическое обрезание SMT (fallback) | ~1ms | **Крайне
редко** — только while + условие пути |

> Исправление (2026-08-17): приведённая выше таблица сложности — проектная оценка, не измеренная;
> «~1ms» и «крайне редко» следует рассматривать как ожидания порядка величины, а не измеренные
> значения; после реализации они калибруются по данным наблюдаемости.

**Условия срабатывания SMT fallback крайне жёсткие**: одновременно должны выполняться (1) цикл
while, (2) операция записи внутри тела цикла, (3) после операции записи есть условие пути, по
которому можно судить о завершении цикла, (4) компилятору нужно полагаться на это условие для
обрезания обратного ребра. В реальном коде доля таких случаев значительно ниже 1%. Все остальные
проверки заимствований завершаются на быстром пути.

Отношения с пользовательскими предикатами RFC-027: пользовательские предикаты полагаются на SMT как
на основной инструмент, системные предикаты заимствования — на структурный анализ. Оба разделяют
один решатель SMT и верхний предел бюджета (RFC-027 §8), но системные предикаты заимствований почти
не потребляют бюджет SMT.

Линейный код → нет обратных рёбер → слой 1 O(N) мгновенно. Цикл + условие пути → вызов SMT, линейная
арифметика порядка миллисекунд (бюджет RFC-027 100ms). Результат одного BFS может кэшироваться для
повторных запросов того же токена.

### Дизайн сообщений об ошибках

**Основной принцип: в сообщениях об ошибках встречаются только символы, написанные пользователем.**

Ошибки Rust, связанные с заимствованием, делятся на две категории:

**Ошибки уровня переменных**: E0597 (живёт недостаточно долго), E0502 (одновременное изменяемое +
неизменяемое заимствование), E0499 (множественные изменяемые заимствования). Rust уже является
эталоном — имя переменной + номер строки, без `'a`. Точность YaoXiang на том же уровне. Вся
информация в дереве брендов: точка создания токена, позиция потребителя, точка запроса.

**Ошибки уровня сигнатур**: E0623 (несовпадение времён жизни), E0106 (отсутствует спецификатор
времени жизни), E0477 (не выполнено требуемое время жизни). Разворачиваются вокруг `'a`. В YaoXiang
**такие ошибки отсутствуют** — в сигнатуре нет `'a`. Не «невозможно сообщить», а то, что
пользователь не писал, не нужно сообщать.

Пример конфликта внутри функции:

```
Ошибка: `data` заморожен, невозможно получить изменяемые права
 --> src/main.yx:5:9
2 |     view = &data
  |            ----- `data` заморожен (токен только для чтения создан здесь)
4 |         use(view)
  |             ---- `view` всё ещё используется здесь, заморозка не снята
5 |         data.push(4)
  |         ^^^^ здесь требуются изменяемые права
```

(На одном уровне точности с Rust E0499 — имя переменной + номер строки, без ID бренда.)

Пример межфункционального побега:

```
Ошибка: один из источников данных, удерживаемых `num` (строка 4), — это `default_str` (строка 3),
но `default_str` становится недействительным в строке 6, а `num` всё ещё используется в строке 5.

Рекомендация: переместите объявление `default_str` в вызывающую сторону, либо используйте `ref default_str` для совместного владения.
```

(На одном уровне точности с Rust E0597. Сводка брендов знает, что у `num` два пути источника — это
уже есть в компиляторе, формулировка ошибки может это использовать.)

## Исправление в основном тексте RFC-009

Раздел RFC-009 §«Обнаружение конфликтов токенов: потоково-чувствительный анализ живости» обновлён:

1. Удалено «то, что не нужно:……NLL» — не потому что вывод неверен, а потому что аргумент неверен
   («токены — это значения, достаточно линейного отслеживания»)
2. Переходный план слой 1/слой 2 сохранён, полный план указывает на настоящий RFC
3. Уточнено: ID бренда (`#42`) — это и есть `'a` — информация полностью та же, кодировка другая. Не
   изобретён новый анализ — время жизни перенесено с уровня типов на уровень доказательств

---

## Компромиссы

### Преимущества

1. **Сигнатура типа не содержит времён жизни**: `#42` — это и есть `'42` — та же информация,
   закодированная в дереве брендов, не выставленная в сигнатуре типа. Этот пункт нефальсифицируем:
   посчитайте, сколько параметров `'a` нужно в Rust для обобщённого типа с 3 параметрами-ссылками, и
   сколько нужно в YaoXiang. Ответ: 3 против 0.

2. **Концептуальное единство**: проверка заимствований и пользовательские предикаты разделяют один
   конвейер доказательств — `{P} op {Q}`, конвейер верифицирует P. Согласуется с Curry-Howard.

3. **Ноль новых аналитических фреймворков**: не вводится новый аналитический фреймворк. Пользователь
   не осознаёт существования «проверщика заимствований» — как пользователь не осознаёт деталей
   реализации «проверщика типов».

4. **Сообщения об ошибках содержат только символы, написанные пользователем**: исчезает целое
   измерение категорий ошибок (E0623, E0106, E0477 — все вокруг `'a`). Ошибки уровня переменных на
   одном уровне точности с Rust.

5. **Алгоритм не консервативен**: обратный BFS + обрезание break + логическое обрезание SMT. Не
   нужна «консервативная живость внутри цикла». Не нужно «консервативное слияние ветвей».

### Недостатки

1. **Не новое изобретение**: ID бренда делает то же, что и `'a` — сложность решения ограничений
   внутри компилятора не исчезла, только способ кодирования изменился с «имя переменной + набор
   ограничений» на «путь бренда + сопоставление префиксов». Для конечного пользователя различие
   только в том, что в сигнатуре не пишется `'a`.

2. **Полностью новая реализация**: дерево брендов существует в коде только как концепция, требует
   реализации с нуля. BorrowChecker, ControlFlowAnalyzer заменяются.

3. **Зависимость от SMT**: логическое обрезание зависит от Z3 (уже введено в RFC-027, новых
   зависимостей не добавляется). Но проверка заимствований почти не срабатывает — вызывается только
   при while + условиях пути.

4. **Крайне редкие паттерны требуют рефакторинга**: межветвевые заимствования, не покрываемые
   автоматическим доказательством компилятора, пользователь должен отрефакторить. В отличие от
   страховки Rust `'a`: в Rust есть `'a` как инструмент (аннотация — и проходит); страховка YaoXiang
   (функция доказательства) не входит в MVP.

## Альтернативы

| Решение                             | Почему не выбрано                                                                                                                             |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Реализовать полный Rust NLL         | Ограничения дизайна YaoXiang (отсутствие затенения, новое связывание в for) устраняют основной источник сложности NLL, фикспоинт CFG не нужен |
| Сохранить текущее (хардкод Release) | Недостаточно — пользователь должен вручную управлять областями видимости токенов                                                              |
| Анализировать только блоки spawn    | Недостаточно — использование токенов вне spawn-кода преобладает                                                                               |
| GC вместо проверки заимствований    | Нарушает принципы дизайна языка — в YaoXiang нет GC                                                                                           |

## Открытые вопросы

- [x] **Семантика `ref_count` дерева брендов при раскрутке цикла через итерации** — по пути NLL:
      токен умирает после последнего использования. Копии, связанные внутри цикла, умирают на
      границе итерации, обратный BFS не переносит живость между итерациями. См. §NLL и границы
      итераций.
- [x] **Порядок освобождения токенов на пути распространения ошибки `?`** — Release управляется
      анализом областей видимости (остаётся в ir_gen.rs). Каждая точка выхода области видимости
      (`}`, `?`, явный return) освобождает активные токены по LIFO. Отношения родитель-потомок в
      дереве брендов автоматически обрабатывают каскадное освобождение. См. §`?` распространение
      ошибок и Release под управлением области видимости.
- [ ] Синтаксис функции доказательства (долгосрочно, не входит в MVP — не блокирует ни одну фазу)
