# RFC-009a: Анализ времени жизни токенов — конвейер доказательств на основе логики Хоара

> **Родительский RFC**: [RFC-009: Проект модели владения](../accepted/009-ownership-model.md)
>
> **Зависимость**:
> [RFC-027: Предикаты времени компиляции и унифицированная статическая верификация](../accepted/027-compile-time-evaluation-types.md)
>
> **Предварительное условие**: RFC-027 должен быть принят. Все механизмы настоящего RFC (конвейер
> доказательств, SMT-fallback, сбор условий пути) зависят от реализации RFC-027.
>
> **Настоящий RFC исправляет и заменяет раздел RFC-009 §«Обнаружение конфликтов токенов:
> потокочувствительный анализ живучести» (строки 663–684).**

## Резюме

В строке 684 RFC-009 утверждается, что обнаружение конфликтов токенов «не требует……NLL». Вывод
верен, аргумент — нет.

Не потому, что «токен — это значение, и линейного отслеживания достаточно». А потому, что
**живучесть токена — это утверждение логики Хоара, а не специальный потокочувствительный анализ.**

`{все конфликтующие токены мертвы} op {WriteToken безопасно получен}` — та же самая форма
`{P} op {Q}`, разделяющая конвейер доказательств RFC-027 с проверкой типов и верификацией
предикатов. Никакого нового аналитического фреймворка. Один конвейер, разные утверждения.

---

## Мотивация

### Путаница в RFC-009

RFC-009 смешивает две задачи:

1. **Линейное отслеживание** (после Move значение недоступно) —
   `{v не перемещён} use(v) {тип совпадает}`. Уже есть в контролёре типов.
2. **Взаимодействие времён жизни токенов** (дочерний токен жив → родительский приостановлен →
   дочерний умирает → родительский оживает) —
   `{все конфликтующие токены мертвы} write(data) {безопасно}`. Требуется **анализ живучести**, а не
   линейное отслеживание.

### Текущее состояние кода

| Компонент                                  | Состояние                                                                                               |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `BorrowChecker`                            | Линейное сканирование IR, пассивная реакция на явные `Borrow`/`Release`                                 |
| `ControlFlowAnalyzer::analyze_instruction` | Пустая реализация (`control_flow.rs:145-153`)                                                           |
| `liveness_analysis`                        | Существует, но используется только для вставки Drop, не для конфликтов токенов                          |
| Вставка Release                            | Жёстко закодирована после инструкции Call — чисто лексическая область видимости (`ir_gen.rs:2734-2736`) |

**Видимые пользователю последствия**:

```yaoxiang
data = vec![1, 2, 3]
view = &data              # Создаёт ReadToken
x = view.total_count      # Последнее использование view
data.push(4)              # ❌ Release(view) ещё не выполнен, ReadToken «жив»
```

### Почему нужна переработка

Предыдущая версия (009a v1) использовала нарратив «DAG вместо NLL», вводя ненужные новые концепции
(консервативные правила ветвления, специальная обработка циклов). Главное противоречие не было
сформулировано ясно: **проверка заимствований — не отдельная система, а разновидность утверждения
Хоара.**

## Основной проект

### Всё — утверждение Хоара

```
Проверка типов:        { x: Int }        x + 1        { result: Int }
Проверка заимствований: { view мёртв }   data.push(4) { WriteToken получен }
Верификация предикатов: { y > 0 }        divide(x, y) { result: Int }
Отсечение обратного ребра: { i == n }    след. итерация { cond == false }
```

Одна и та же форма `{P} op {Q}`. Компилятор для каждой операции порождает предусловие P и отправляет
его в конвейер доказательств на верификацию.

**Проверка заимствований и пользовательские предикаты разделяют один конвейер.** Различие только в
том, кто порождает утверждение и что происходит при невозможности доказать.

### Два вида предикатов, один конвейер

|                               | Пользовательский предикат                         | Системный предикат (заимствование)                        |
| ----------------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| Порождение утверждения        | Программист (аннотация типа)                      | Компилятор (дерево брендов + правила владения)            |
| Предоставление доказательства | Компилятор + программист                          | **Полностью автоматически компилятором**                  |
| При невозможности доказать    | Написать функцию-доказательство или отрефакторить | Отрефакторить код (дверь остаётся, но нужна крайне редко) |
| Видимость                     | Видна в сигнатуре                                 | Неявная, не загрязняет сигнатуру типа                     |
| Стоимость обучения            | Изучается по желанию                              | Ноль                                                      |

**Доказательство системных предикатов не открывает программисту функцию-доказательство — компилятор
делает это полностью автоматически.** При невозможности доказать пользователь рефакторит код.

**Три режима отказа, один движок верификации.** Утверждение типа не доказывается → ошибка компиляции
(нельзя обойти). Утверждение заимствования не доказывается → ошибка компиляции, рефакторинг кода
(нельзя обойти). Пользовательский предикат не доказывается → ошибка компиляции, можно написать
функцию-доказательство (можно обойти). Стратегии отказа различаются, но движок верификации один и
тот же — SMT-решатель + правила вывода ядра компилятора. Различие только в том, «кто отвечает за
восполнение доказательства при невозможности построить его автоматически» — компилятор отказывается
писать за программиста доказательство заимствования (стратегия доказательства утверждений
заимствования — структурный анализ + SMT, вмешательство программиста не требуется), но принимает
функции-доказательства пользовательских предикатов. Это не противоречие в конвейере — это разные
границы ответственности для разных категорий утверждений.

Это отличается от Rust `'a`: `'a` — обязательный курс, функция-доказательство — факультативный;
подавляющее большинство пользователей за всю жизнь не подойдут к двери факультатива.

### Утверждения заимствования: автоматическая генерация компилятором

Пользователь пишет `data.push(4)`. Компилятор автоматически генерирует утверждение:

```
WriteToken(data, node) может быть получен
  = forall t in conflicting_tokens(data): t в node уже мёртв
  = forall t in brand_tree.children(data): forward_reachable(node) ∩ consumers(t) == ∅
```

**Три правила, ноль особых случаев:**

1. **Дерево брендов** (RFC-009 §2.7) отвечает на вопрос «кто с кем конфликтует»: сопоставление
   префиксов, O(глубина), глубина ≤ 3
2. **Список потребителей** (автоматически собирается при построении DAG) отвечает на вопрос «кто
   последним потребил токен»
3. **Прямая достижимость** отвечает на вопрос «может ли потребитель ещё быть выполнен»: структурное
   отсечение + логическое отсечение

### Прямая достижимость: обратный обход от потребителя

Для каждого потребителя C токена T:

```
Из C пройти в обратном направлении BFS по DAG.
Ребро отсекается, если:
  1. Это break (структурное отсечение)
  2. Условие пути ⇒ !loop_cond доказано SMT как истинное (логическое отсечение, конвейер RFC-027)

Распространять в обратном направлении по всем неотсечённым рёбрам (включая обратные; обратное ребро распространяет живучесть в предыдущий раунд итерации).
Пометить все достижимые узлы → unsafe.
```

Запрос: операция записи в узле W → W ∉ unsafe → безопасно.

**Не нужно изобретать «консервативное правило ветвления». Не нужно «консервативного выживания в
цикле». Один обратный BFS + два правила отсечения.**

### Стратегия доказательства: приоритет быстрому каналу, SMT как резерв

```
Каждая операция записи, требующая токена
  │
  ├→ Быстрый канал: структурный анализ DAG (покрывает >95% сценариев)
  │     │
  │     ├→ Сопоставление префиксов дерева брендов → найти конфликтующие токены (O(глубина))
  │     ├→ Обратный BFS, break отсекает обратные рёбра
  │     └→ Нет проходимых обратных рёбер → прямое решение Proved / Disproved
  │
  └→ Медленный канал: логическое отсечение SMT (только когда быстрый канал встречает проходимое обратное ребро)
        │
        ├→ Начало обратного ребра имеет условие пути → SMT решает path_cond ⇒ !loop_cond
        │     ├→ Proved → логическое отсечение → возврат к быстрому каналу
        │     └→ Disproved / Unproven → проход через обратное ребро → пометить как unsafe
        │
        └→ Начало обратного ребра не имеет условия пути → прямое прохождение через обратное ребро
```

**Покрытие быстрого канала**: линейный код, if/else, loop + break, while без условий пути.
**Покрытие медленного канала**: внутри тела цикла while, когда условие пути подразумевает выход из
цикла. **Не покрывает**: условия времени выполнения, которые нельзя статически доказать → проход
через обратное ребро → unsafe → ошибка компиляции (пользовательский рефакторинг).

SMT — не основной инструмент, а страховочная сетка. В отличие от пользовательских предикатов
RFC-027, где SMT — основной инструмент; в системных предикатах заимствования основной инструмент —
структурный анализ, а SMT дополняет только те угловые случаи, до которых структурный анализ не
дотягивается.

## Анализ случаев использования

### Линейный код

```yaoxiang
data = vec![1, 2, 3]        # Узел 1
view = &data                # Узел 2: потребляет data, производит ReadToken(#1)
x = view.total_count        # Узел 3: потребляет view (= последний потребитель #1)
data.push(4)                # Узел 4: требует WriteToken(data)
```

Обратный BFS от `view.total_count` (узел 3) → узел 3 — последний потребитель #1 → узел 4 > узла 3 →
узел 4 не в unsafe → ✅

### if/else: без особых правил

```yaoxiang
view = &data
if cond {
    use(view)               # then-ветвь потребляет view
} else {
    do_something_else()     # Не трогает view
}
data.push(4)                # Последний потребитель view внутри if → после if потребителей нет → ✅
```

if/else — составной узел DAG. Внутреннее потребление приписывается этому узлу. Состояния ветвей не
объединяются. Консервативного усреднения нет. **Есть ли последующие потребители — целочисленное
сравнение.**

> **Уточнение (после #264)**: «не объединять состояния ветвей» относится только к **живучести
> заимствований** (обратный BFS потребителей бренда). **move-состояние** (владение переменной) —
> отдельный анализ: прямой поток данных по узлам CFG (#264, в стиле NLL/Polonius), с
> **консервативным объединением** на слиянии ветвей (если в любой ветви Moved → на слиянии Moved),
> недостижимые литеральные ветви (`if false`) не участвуют. Анализы расслоены: анализ живучести
> заимствований смотрит «есть ли последующие потребители», move-анализ смотрит «возможно ли
> переменная уже перемещена».

### if/else с утечкой возвращаемого значения

```yaoxiang
view = &data
result = if cond {
    view                     # view утекает в result
} else {
    something_else
}
use(result)                  # Косвенно потребляет view
data.push(4)                 # У view всё ещё есть потребитель (use(result))
                             # → push в unsafe → ❌ Корректная ошибка
```

view утекает через возвращаемое значение → `use(result)` — потребитель view → обратный проход от
`push` может достичь `use(result)` → unsafe.

### Цикл: break отсекает обратное ребро

```yaoxiang
view = &data
loop {
    use(view)                # consumer
    if is_last {
        data.push(4)         # Операция записи
        break                # ← Структурное отсечение
    }
}
```

Обратный BFS от `use(view)` → обратное ребро → проход вперёд к `data.push(4)` → встречается `break`
→ **отсечено** → `data.push(4)` не в unsafe → ✅

Без break:

```yaoxiang
view = &data
loop {
    use(view)
    data.push(4)             # Нет отсечения break → обратное ребро проходимо → в следующем раунде use(view) достижим
                             # → push в unsafe → ❌ Корректная ошибка
}
```

### while: логическое отсечение SMT

```yaoxiang
view = &data
mut i: UpTo(n) = 0
while i < n {
    use(view)                # consumer
    i += 1
    if i == n {
        data.push(4)         # Условие пути: i == n
    }
}
```

Обратный BFS от `use(view)` → обратное ребро → проход к `data.push(4)` → проверка условия пути
`i == n` → SMT-запрос: `i == n ⇒ !(i < n)`? → Proved → **логическое отсечение** → `data.push(4)` не
в unsafe → ✅

## Суть: идентификатор бренда — это и есть `'a`

Мы не говорим «нам не нужен `'a`». Мы говорим: «`#42` — это и есть `'42`».

| Rust                                                  | YaoXiang                                     | Эквивалентность                                              |
| ----------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| `'a`                                                  | `#42`                                        | Идентификатор времени жизни на этапе компиляции              |
| Ограничение outlives `'a: 'b`                         | `#42` — префикс `#42.field_x`                | Сравнение строковых префиксов = отношение частичного порядка |
| Распространение живучести NLL (неподвижная точка CFG) | Обратный BFS (DAG)                           | Обе вычисляют достижимость                                   |
| Факты Polonius                                        | Логическое отсечение SMT                     | Оба выполняют логический вывод по условиям пути              |
| Решение неподвижной точки системы ограничений         | Сопоставление префиксов дерева брендов + BFS | Различное кодирование, одна и та же задача                   |

**Мы не изобрели новый анализ. Мы лишь перенесли `'a` с уровня сигнатур типов на уровень
доказательств.** Идентификатор бренда делает то же самое, что и `'a` — маркирует идентичность
заимствования, отслеживает отношение порождения, определяет конфликт. Различие одно: `'a` находится
в сигнатуре типа, написанной пользователем; `#42` — внутри компилятора.

В этом нет ничего зазорного. Карри–Ховард говорит: типы — это утверждения, программы — это
доказательства. `'a` — не часть утверждения; он — часть стратегии доказательства. Rust вписывает
стратегию доказательства в сигнатуру утверждения. Мы вернули её туда, где ей и положено быть.

### Что устраняют ограничения проектирования языка

| Источник сложности                                    | Удалось избежать? | Причина                                                                             |
| ----------------------------------------------------- | ----------------- | ----------------------------------------------------------------------------------- |
| Затенение переменных                                  | ✅                | Язык запрещает — одно имя всегда указывает на одно и то же                          |
| Заимствование через итерации в for                    | ✅                | Каждая итерация — новое связывание — естественная изоляция между итерациями         |
| Аннотация времени жизни `'a`                          | ✅                | Путь бренда = `#42.field_x`, вывод компилятором                                     |
| Именованное время жизни + распространение ограничений | ✅                | Сравнение префиксов пути бренда вместо явного набора ограничений                    |
| Решение ограничений на графе заимствований (Polonius) | ✅                | Сопоставление префиксов дерева брендов + запрос потребителей DAG                    |
| Распространение живучести заимствований в теле цикла  | ❌                | Нужно обрабатывать, как и в Rust — через обратный BFS + логическое отсечение        |
| Консервативность условных ветвей                      | ❌                | Как и в Rust — SMT покрывает доказуемые случаи, остальные консервативно отвергаются |

### Почему DAG оказывается достаточным

Три ограничения проектирования YaoXiang делают анализ DAG возможным:

- **Отсутствие затенения переменных** — одно имя всегда указывает на одно и то же, не нужно
  отслеживание через пересвязывание
- **Новое связывание в каждой итерации for** — естественная изоляция между итерациями,
  межитерационных заимствований не существует
- **Структурированная конкурентность** — чёткие границы задач, не нужно распространение живучести
  между задачами

Эти ограничения устраняют основной источник сложности итераций неподвижной точки CFG в Rust. DAG не
«более продвинут», чем CFG — более простой дизайн языка позволяет более простой анализ.

## Детальный проект

### Список системных предикатов

Компилятор автоматически генерирует следующие утверждения и отправляет их в конвейер доказательств
RFC-027:

| Системный предикат | Момент срабатывания        | Форма утверждения                             |
| ------------------ | -------------------------- | --------------------------------------------- |
| `borrow_conflict`  | Требуется WriteToken(v)    | `forall t ∈ conflicting(v): dead_at(t, node)` |
| `use_after_move`   | Использование переменной v | `¬moved(v)`                                   |
| `use_after_drop`   | Использование переменной v | `¬dropped(v)`                                 |
| `double_drop`      | Drop(v)                    | `¬dropped(v)`                                 |
| `mut_violation`    | Запись в неизменяемую v    | `is_mut(v)`                                   |

Существующие `BorrowChecker`, `MoveChecker`, `DropChecker`, `MutChecker` **становятся генераторами
утверждений** — не исчезают, а меняют роль. Они порождают утверждения, конвейер их верифицирует.

### Дерево брендов

Механизм брендов из RFC-009 §2.7 формализован как дерево брендов.

**Семантика токена — заморозка первична, не дублирование**:

Суть различия между `&T` и `&mut T` — не «можно ли копировать», а «допускается ли одновременная
запись»:

```
ReadToken(T):  Предоставляет право только на чтение, одновременно замораживая
              исходные данные T — любой WriteToken(T) в этот период
              недоступен. Заморозка — главная семантика ReadToken. Dup
              (возможность копирования) — следствие заморозки: поскольку данные
              уже заморожены (мутация невозможна), несколько представлений только
              для чтения по своей природе безопасны.

WriteToken(T): Предоставляет исключительное право на чтение и запись. Из-за
              наличия записи любой другой токен (чтение или запись) не может
              сосуществовать. Отсутствие Dup (линейный тип) — следствие
              исключительности.
```

**Причинно-следственная связь**:

```
ReadToken существует → данные заморожены → несколько представлений только для чтения безопасны → Dup
                                  ↓
                        WriteToken отвергается (системный предикат borrow_conflict)
```

А не:

```
ReadToken имеет Dup → может быть несколько → заодно проверим конфликт  ← Обратная причинность
```

```
BrandTree:
  nodes: Map<BrandId, BrandNode>

BrandNode:
  id: BrandId               # "#42", "#42.field_x"
  kind: ReadToken | WriteToken
  source_var: Operand
  parent: Option<BrandId>   # Родительский узел в отношении порождения
  children: Set<BrandId>    # Порождённые дочерние токены
  consumers: Set<NodeId>    # DAG-узлы, потребляющие токен
  ref_count: usize          # Количество безопасных копий во время заморозки ReadToken
```

**Определение конфликта — механизм исполнения гарантии заморозки**:

```rust
fn conflicts(a: &BrandId, b: &BrandId) -> bool {
    // Условие конфликта: общий источник + хотя бы одна запись + перекрытие путей бренда
    // Это означает:
    //   1. ReadToken vs ReadToken → нет конфликта (оба только для чтения, мутации нет)
    //   2. WriteToken vs ReadToken → конфликт (запись нарушает гарантию заморозки для чтения)
    //   3. WriteToken vs WriteToken → конфликт (две записи не могут сосуществовать)
    a.source() == b.source()
        && (a.is_write() || b.is_write())
        && (a.is_prefix_of(b) || b.is_prefix_of(a))
}
```

O(глубина) сравнение строковых префиксов, глубина ≤ 3. Константного порядка.

### Анализ живучести обратным BFS

```
Алгоритм: check_borrow(token, node, dag, brand_tree)

Вход:
  token: WriteToken, который нужно проверить
  node:  Узел DAG, в котором находится операция записи

Выход: Proved | Disproved

Алгоритм:
  # Быстрый канал: обратный BFS
  unsafe = empty_set
  queue = brand_tree.consumers(token)

  while queue not empty:
    cur = queue.pop()
    unsafe.add(cur)

    for each pred in dag.predecessors(cur):
      # Структурное отсечение: break не проходится
      if pred является break-ребром:
        continue

      # Обратное ребро → проверка необходимости SMT-fallback
      if pred является обратным ребром:
        path_cond = условие пути в pred
        loop_cond = условие цикла
        # Сначала проверим, возможно ли структурное отсечение (соответствующий break уже отсёк путь → сюда не дойдём)
        # Затем проверим условие пути
        if path_cond не пусто:
          result = smt_fallback(path_cond, loop_cond)   # ← Медленный канал
          if result == Proved:
            continue                    # Логическое отсечение
        # Нет условия пути или SMT не доказал → проход через обратное ребро
        # fall through

      if pred ∉ unsafe:
        queue.push(pred)

  # Решение
  if node ∈ unsafe:
    return Disproved
  else:
    return Proved


smt_fallback(path_cond, loop_cond):
  # Вызывается только при обратном ребре + наличии условия пути
  # Использует конвейер доказательств RFC-027, общий SMT-решатель, общий бюджет
  return smt.prove(path_cond ⇒ !loop_cond)
  # Proved → логическое отсечение
  # Disproved / Unproven → не отсекаем, проход через обратное ребро
```

O(N), где число вызовов SMT = число обратных рёбер × доля обратных рёбер с условием пути. В реальном
коде вызовы SMT крайне редки — срабатывают только в теле цикла `while` при наличии условия пути с
уточнёнными переменными типа.

### Сбор условий пути

Предоставляется существующим механизмом RFC-027 §3.2-3.3:

- **if-guard**: `if y > 0` → в true-ветвь помещается `y > 0`
- **match-образец**: `if let Some(v) = opt` → в ветвь помещается `opt == Some(v)`
- **Присваивание**: `i += 1` — компилятор поддерживает информацию о диапазоне значений переменной
- **while cond**: в тело цикла помещается `cond == true`

Каждый узел DAG несёт набор условий пути. При обратном BFS на обратном ребре берётся условие пути
начала ребра, SMT определяет, исключает ли оно условие входа в следующий раунд цикла.

### Интерфейс с RFC-027

Системные утверждения заимствования и пользовательские предикаты разделяют один конвейер
доказательств — различие в основной стратегии доказательства:

| Тип запроса               | Источник утверждения        | Основная стратегия                         | Резерв                              |
| ------------------------- | --------------------------- | ------------------------------------------ | ----------------------------------- |
| Равенство типов           | Контролёр типов             | Структурная эквивалентность                | —                                   |
| Пользовательский предикат | Аннотация типа программиста | SMT                                        | Функция-доказательство программиста |
| Конфликт заимствований    | Автогенерация компилятора   | **Структурный анализ DAG (быстрый канал)** | Логическое отсечение SMT            |

Роль SMT-решателя в проверке заимствований: **не основной, а страховочная сетка.** Вызывается только
при необходимости логического отсечения обратного ребра `while`. Подавляющее большинство проверок
заимствований выполняется в быстром канале — O(N) обратный BFS, нулевые накладные расходы на SMT.

### Связь с существующим кодом

| Существующий компонент                      | Обработка                                                                            |
| ------------------------------------------- | ------------------------------------------------------------------------------------ |
| `BorrowChecker`                             | Становится `BorrowPredicateEmitter` — порождает хоаровские утверждения заимствования |
| `MoveChecker`                               | Становится `MovePredicateEmitter` — порождает утверждения `¬moved(v)`                |
| `DropChecker`                               | Аналогично — порождает утверждения, связанные с Drop                                 |
| `MutChecker`                                | Аналогично — порождает утверждения `is_mut(v)`                                       |
| `ControlFlowAnalyzer`                       | Больше не нужен — конвейер обрабатывает единообразно                                 |
| `liveness_analysis`                         | Сохраняется — вставка Drop всё ещё нуждается в информации о живучести переменных     |
| Жёстко закодированный Release в `ir_gen.rs` | Удаляется — позиция Release определяется анализом потребителей DAG                   |

### NLL и границы итерации

**Момент смерти токена = точка последнего использования (NLL), а не конец лексической области
видимости.**

Это естественное следствие анализа потребителей: позиция потребителя определяет последнее
использование токена. `use(v)` — потребитель `v` → `v` умирает сразу после `use(v)`. Не нужны
дополнительные `{}` или `drop()` для досрочного завершения жизни токена.

**Граница итерации цикла — линия смерти копий токена.** Три правила:

```
Правило 1: Переменные, объявленные внутри цикла, автоматически умирают в конце каждой итерации.
        Каждая итерация for — новое связывание (гарантия проектирования языка), то же для loop.

Правило 2: ref_count дерева брендов в заголовке цикла учитывает только копии, созданные вне цикла.
        Новые копии, созданные Dup внутри цикла, обнуляют ref_count на границе итерации.

Правило 3: При прохождении обратного ребра обратным BFS не переносится информация о живучести текущей итерации.
        Переносится только ref_count в заголовке цикла (т.е. копии вне цикла).
```

Пример:

```yaoxiang
view = &data                          # Заголовок цикла: ref_count = 1, consumer = use(view)
loop {
    v2: &Point = view                 # Dup внутри цикла → ref_count = 2
    use(v2)                           # consumer: последнее использование v2 → v2 умирает → ref_count = 1
    data.push(4)                      # ✅ Безопасно! v2 мёртв, остался только view (ref_count = 1, конфликта записи нет)
    # Граница итерации: правило 3 — v2 не переносится в следующий раунд. В начале следующей итерации v2 пересоздаётся новым связыванием.
}
```

Этот проект не нуждается в дополнительном правиле «консервативного выживания в цикле». Обратный BFS
идёт от потребителя, потребитель находится в теле цикла → живучесть ограничена текущей итерацией →
обратное ребро не проходится. Полностью согласуется с примером цикла из RFC-009a §Анализ случаев
использования.

### `?` распространение ошибки и Release, управляемый областью видимости

`?` — это досрочный возврат: помимо нормального выхода из области видимости, существует
дополнительный путь выхода. Токены должны быть освобождены на этом пути; неправильный порядок
освобождения — UB.

**Инструкции Release генерируются анализом области видимости, а не жёстко закодированы после Call.**

Компилятор поддерживает список точек выхода для каждой области видимости:

- `}` (нормальное завершение области видимости)
- `?` (распространение ошибки, досрочный return)
- Явный `return`

В каждой точке выхода в порядке, обратном объявлению (LIFO), вставляются инструкции Release для всех
активных токенов в данной области видимости. Отношения родитель-потомок в дереве брендов
автоматически обрабатывают каскадное освобождение порождённых токенов:

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)    # Возвращает дочерний токен &Float + родительский токен &Point
}

fn use_case(p: Point) -> Result<(), Error> = {
    (x_ref, p_ref) = p.get_x()?   # Если ? распространяется:
    # Дерево брендов знает, что x_ref — порождение p_ref (#42.field_x — префикс #42)
    # Порядок освобождения: x_ref (потомок) → p_ref (родитель) → LIFO выполняется автоматически
    p.modify()                     # WriteToken — все ReadToken уже освобождены
    Ok(())
}
```

Расположение реализации: остаётся в `ir_gen.rs`, переводится на управление областью видимости — без
нового прохода компилятора.

| Операция                               | Сложность | Частота срабатывания                               |
| -------------------------------------- | --------- | -------------------------------------------------- |
| Определение конфликта в дереве брендов | O(1)      | При каждом запросе токена                          |
| Запрос потребителей DAG                | O(1)      | При каждом запросе токена                          |
| Обратный BFS (быстрый канал)           | O(N)      | При каждом запросе токена, N = число узлов в блоке |
| Логическое отсечение SMT (fallback)    | ~1мс      | **Крайне редко** — только while + условие пути     |

**Условия срабатывания SMT fallback крайне жёсткие**: одновременно (1) цикл `while` (2) в теле цикла
есть операция записи (3) после операции записи есть условие пути, позволяющее судить о завершении
цикла (4) компилятору нужно полагаться на это условие для отсечения обратного ребра. В реальном коде
доля значительно ниже 1%. Остальные проверки заимствований полностью выполняются в быстром канале.

Связь с пользовательскими предикатами RFC-027: в пользовательских предикатах SMT — основной
инструмент, в системных утверждениях заимствования основной инструмент — структурный анализ. Оба
разделяют один SMT-решатель и верхний предел бюджета (RFC-027 §8), но системные утверждения
заимствования почти не расходуют бюджет SMT.

Линейный код → нет обратных рёбер → слой 1 O(N) за секунды. Цикл + условие пути → вызов SMT,
линейная арифметика — миллисекунды (бюджет RFC-027 100мс). Результат одного BFS может кэшироваться
для повторного использования при множественных запросах того же токена.

### Дизайн сообщений об ошибках

**Основной принцип: в сообщениях об ошибках присутствуют только символы, написанные пользователем.**

Ошибки Rust, связанные с заимствованием, делятся на две категории:

**Ошибки на уровне переменных**: E0597 (не живёт достаточно долго), E0502 (одновременное
изменяемое + неизменяемое заимствование), E0499 (многократное изменяемое заимствование). Rust уже
является эталоном — имя переменной + номер строки, без `'a`. YaoXiang — одинаковая точность. Вся
информация содержится в дереве брендов: точка создания токена, позиция потребителя, точка запроса.

**Ошибки на уровне сигнатур**: E0623 (lifetime mismatch), E0106 (missing lifetime specifier), E0477
(не выполнен required lifetime). Строятся вокруг `'a`. В YaoXiang **таких ошибок нет** — в сигнатуре
нет `'a`. Не «невозможно сообщить», а то, что пользователь не писал, не нужно сообщать.

Пример конфликта внутри функции:

```
Ошибка: `data` заморожен, невозможно получить изменяемое право
 --> src/main.yx:5:9
2 |     view = &data
  |            ----- `data` заморожен (токен только для чтения создан здесь)
4 |         use(view)
  |             ---- `view` всё ещё используется здесь, заморозка не снята
5 |         data.push(4)
  |         ^^^^ Здесь требуется изменяемое право
```

(Точность соответствует Rust E0499 — имя переменной + номер строки, идентификатор бренда не
появляется.)

Пример утечки между функциями:

```
Ошибка: один из источников удерживаемых `num` (строка 4) данных — `default_str` (строка 3),
но `default_str` становится недействительным в строке 6, а `num` всё ещё используется в строке 5.

Рекомендация: переместите объявление `default_str` в вызывающую сторону или используйте `ref default_str` для совместного владения.
```

(Точность соответствует Rust E0597. Сводка бренда знает, что у `num` два пути источника — уже есть в
компиляторе, формулировка ошибки доступна.)

## Корректировка основного текста RFC-009

Раздел RFC-009 §«Обнаружение конфликтов токенов: потокочувствительный анализ живучести» обновлён:

1. Удалено «Ненужное:……NLL» — не потому что вывод неверен, а потому что аргумент неверен («токен —
   это значение, и линейного отслеживания достаточно»)
2. Переходный план слоя 1/слоя 2 сохраняется, полный план ссылается на настоящий RFC
3. Уточнено: идентификатор бренда (`#42`) — это и есть `'a` — информация полностью идентична,
   кодирование различается. Не изобретён новый анализ — время жизни перенесено с уровня типов на
   уровень доказательств

## Компромиссы

### Преимущества

1. **Сигнатура типа не содержит время жизни**: `#42` — это и есть `'42` — та же информация,
   закодированная в дереве брендов, не выставленная в сигнатуре типа. Этот пункт нефальсифицируем:
   посчитайте, сколько параметров `'a` требуется для обобщённого типа с 3 параметрами-ссылками в
   Rust, и сколько требуется в YaoXiang. Ответ: 3 против 0.

2. **Единообразие концепций**: проверка заимствований и пользовательские предикаты разделяют один
   конвейер доказательств — `{P} op {Q}`, конвейер верифицирует P. Карри–Ховард — согласованно.

3. **Ноль новых аналитических фреймворков**: новые аналитические фреймворки не вводятся.
   Пользователь не знает о существовании «проверщика заимствований» — как пользователь не знает о
   деталях реализации «проверщика типов».

4. **Сообщения об ошибках содержат только символы, написанные пользователем**: устраняет целое
   измерение категорий ошибок (E0623, E0106, E0477 — все построены вокруг `'a`). Точность ошибок на
   уровне переменных соответствует Rust.

5. **Алгоритм не консервативен**: обратный BFS + отсечение `break` + логическое отсечение SMT. Не
   нужно «консервативного выживания в цикле». Не нужно «консервативного слияния ветвей».

### Недостатки

1. **Не новое изобретение**: идентификатор бренда делает то же, что и `'a` — сложность решения
   ограничений внутри компилятора не исчезла, только способ кодирования изменился с «имя
   переменной + набор ограничений» на «путь бренда + сопоставление префиксов». Различие для
   конечного пользователя лишь в том, что в сигнатуре не пишется `'a`.

2. **Полностью новая реализация**: дерево брендов в коде существует лишь как концепция, требует
   реализации с нуля. BorrowChecker, ControlFlowAnalyzer заменяются.

3. **Зависимость от SMT**: логическое отсечение зависит от Z3 (уже введён в RFC-027, новых
   зависимостей нет). Но проверка заимствований почти не срабатывает — вызывается только при
   `while` + условие пути.

4. **Крайне редкие паттерны требуют рефакторинга**: межветвевые заимствования, не покрываемые
   автоматическим доказательством компилятора, требуют от пользователя рефакторинга кода. Отличается
   от fallback в Rust с `'a`: в Rust `'a` — это ручка (аннотация — и проходит); fallback в YaoXiang
   (функция-доказательство) не входит в MVP.

| Фаза 4 | Сбор условий пути + логическое отсечение SMT (слой 2)                | Фаза 3 + RFC-027 Фаза 2 |
| Фаза 5 | Перевод инструкций Release на управление потребителями DAG           | Фаза 3                  |
| Фаза 6 | Удаление ControlFlowAnalyzer, рефакторинг BorrowChecker              | Фаза 4                  |

## Открытые вопросы

- [x] **Семантика `ref_count` дерева брендов через итерации при развёртке цикла** — идём через NLL:
      токен умирает после последнего использования. Копии, связанные внутри цикла, умирают на
      границе итерации; обратный BFS не переносит межитерационную живучесть. Подробности в §NLL и
      границы итерации.
- [x] **Порядок освобождения токенов на пути распространения ошибки `?`** — Release управляется
      анализом области видимости (остаётся в `ir_gen.rs`). Каждая точка выхода области видимости
      (`}`, `?`, явный `return`) освобождает активные токены по LIFO. Отношения родитель-потомок в
      дереве брендов автоматически обрабатывают каскадное освобождение. Подробности в §`?`
      распространение ошибки и Release, управляемый областью видимости.
- [ ] Синтаксис функции-доказательства (далёкая перспектива, не MVP — не блокирует ни одну фазу)
