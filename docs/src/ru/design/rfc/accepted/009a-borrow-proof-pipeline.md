# RFC-009a: Анализ времени жизни токенов — конвейер доказательств на основе Хоара

> **Родительский RFC**: [RFC-009: Проект модели владения](../accepted/009-ownership-model.md)
>
> **Зависимости**:
> [RFC-027: Предикаты времени компиляции и унифицированная статическая верификация](../accepted/027-compile-time-evaluation-types.md)
>
> **Предусловие**: RFC-027 должен быть принят. Все механизмы данного RFC (конвейер доказательств,
> fallback SMT, сбор условий пути) зависят от реализации RFC-027.
>
> **Данный RFC исправляет и заменяет RFC-009 §"Обнаружение конфликтов токенов:
> потоково-чувствительный анализ живучести" (строки 663-684).**

## Резюме

Строка 684 RFC-009 утверждает, что обнаружение конфликтов токенов "не требует……NLL". Вывод верен,
аргументация ошибочна.

Дело не в том, что "потому что токены — это значения, и линейного отслеживания достаточно". Дело в
том, что: **живучесть токенов — это утверждение логики Хоара, а не специальный
потоково-чувствительный анализ.**

`{все конфликтующие_токены мертвы} op {WriteToken безопасно получен}` — та же самая форма
`{P} op {Q}`, разделяющая конвейер доказательств RFC-027 с проверкой типов и верификацией
предикатов. Никаких новых фреймворков анализа. Один конвейер, множество утверждений.

---

## Мотивация

### Путаница в RFC-009

RFC-009 смешивает две проблемы:

1. **Линейное отслеживание** (после Move недоступно) — `{v не перемещён} use(v) {тип совпадает}`.
   Уже есть в проверщике типов.
2. **Взаимодействие времён жизни токенов** (дочерний токен жив → родительский токен приостановлен →
   дочерний токен мёртв → родительский токен возобновлён) —
   `{все конфликтующие_токены мертвы} write(data) {безопасно}`. Требуется **анализ живучести**, а не
   линейное отслеживание.

### Текущее состояние кода

| Компонент                                  | Состояние                                                                                               |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `BorrowChecker`                            | Линейное сканирование IR, пассивная реакция на явные инструкции `Borrow`/`Release`                      |
| `ControlFlowAnalyzer::analyze_instruction` | Пустая реализация (`control_flow.rs:145-153`)                                                           |
| `liveness_analysis`                        | Существует, но используется только для вставки Drop, не подключён к конфликтам токенов                  |
| Вставка Release                            | Жёстко закодирована после инструкций Call — чисто лексическая область видимости (`ir_gen.rs:2734-2736`) |

**Последствия для пользователя**:

```yaoxiang
data = vec![1, 2, 3]
view = &data              # создание ReadToken
x = view.total_count      # последнее использование view
data.push(4)              # ❌ Release(view) ещё не выполнен, ReadToken "жив"
```

### Почему нужна переработка

Предыдущая версия (009a v1) использовала нарратив "DAG вместо NLL", вводя ненужные новые концепции
(консервативные правила ветвления, специальная обработка циклов). Ключевое противоречие не было
прояснено: **проверка заимствований — это не отдельная система — это один из видов утверждений
Хоара.**

## Основной дизайн

### Всё есть Хоар

```
Проверка типов:              { x: Int }        x + 1        { result: Int }
Проверка заимствований:      { view мёртв }    data.push(4) { WriteToken успешно получен }
Верификация предикатов:      { y > 0 }         divide(x, y) { result: Int }
Отсечение обратной дуги:     { i == n }        следующая итерация     { cond == false }
```

Та же форма `{P} op {Q}`. Компилятор генерирует предусловие P для каждой операции и отправляет его в
конвейер доказательств для верификации.

**Проверка заимствований и пользовательские предикаты разделяют один конвейер.** Различие только в
том, кто генерирует утверждение и что происходит, когда доказательство не получается.

### Два типа предикатов, один конвейер

|                               | Пользовательские предикаты                    | Системные предикаты (заимствования)                     |
| ----------------------------- | --------------------------------------------- | ------------------------------------------------------- |
| Генерация утверждений         | Программист (аннотации типов)                 | Компилятор (дерево брендов + правила владения)          |
| Предоставление доказательства | Компилятор + программист                      | **Полностью автоматически компилятором**                |
| Не удаётся доказать           | Писать функцию-доказательство или рефакторить | Рефакторить код (двери остаются, но нужны крайне редко) |
| Видимость                     | Видно в сигнатуре                             | Неявное, не загрязняет сигнатуру типа                   |
| Стоимость обучения            | Изучается при необходимости                   | Нулевая                                                 |

**Доказательство системных предикатов не предполагает функций-доказательств от программиста —
компилятор делает это полностью автоматически.** Когда доказать не удаётся, пользователь рефакторит
код.

**Три режима отказа, один движок верификации.** Утверждение типа не доказывается → ошибка компиляции
(не обойти). Утверждение заимствования не доказывается → ошибка компиляции, рефакторинг (не обойти).
Пользовательский предикат не доказывается → ошибка компиляции, можно написать функцию-доказательство
(обходимо). Стратегии отказа различаются, но движок верификации один и тот же — SMT-решатель +
правила вывода ядра компилятора. Различие только в том, "кто отвечает за дополнение доказательства,
когда оно не получается" — компилятор отказывается писать доказательства заимствований за
программиста (стратегия доказательства утверждений заимствований — структурный анализ + SMT,
вмешательство программиста не требуется), но принимает функции-доказательства пользовательских
предикатов от программиста. Это не несоответствие конвейера — это разные границы ответственности для
разных категорий утверждений.

Это отличается от Rust `'a`: `'a` — обязательный курс, функция-доказательство — факультатив —
подавляющее большинство пользователей никогда в жизни не столкнутся с дверью факультатива.

### Утверждения заимствований: автоматически генерируются компилятором

Пользователь пишет `data.push(4)`. Компилятор автоматически генерирует утверждение:

```
WriteToken(data, node) может быть получен
  = forall t ∈ conflicting_tokens(data): t в узле node мёртв
  = forall t ∈ brand_tree.children(data): forward_reachable(node) ∩ consumers(t) == ∅
```

**Три правила, ноль специальных случаев:**

1. **Дерево брендов** (RFC-009 §2.7) отвечает на вопрос "кто с кем конфликтует": сопоставление
   префиксов, O(depth), глубина ≤ 3
2. **Список потребителей** (автоматически собирается при построении DAG) отвечает на вопрос "кто
   последним потребил токен"
3. **Прямая достижимость** отвечает на вопрос "может ли потребитель быть выполнен": структурное
   отсечение + логическое отсечение

### Прямая достижимость: обратный обход DAG от потребителей

Для каждого потребителя C токена T:

```
Из C запускается обратный BFS по DAG.
Ребро отсекается, если:
  1. Это break (структурное отсечение)
  2. Условие пути ⇒ !loop_cond доказано SMT как истинное (логическое отсечение, конвейер RFC-027)

Живучесть распространяется обратно по всем неотсечённым рёбрам (включая обратные рёбра, обратные рёбра
распространяют живучесть на предыдущую итерацию).
Все достижимые узлы помечаются → unsafe.
```

Запрос: операция записи в узле W → W ∉ unsafe → безопасно.

**Не нужно изобретать "консервативные правила ветвления". Не нужна "консервативная живучесть в
цикле". Один обратный BFS + два правила отсечения.**

### Стратегия доказательства: быстрый канал в приоритете, SMT как подстраховка

```
Каждая операция записи, требующая токен
  │
  ├→ Быстрый канал: структурный анализ DAG (покрывает 95%+ сценариев)
  │     │
  │     ├→ Сопоставление префиксов в дереве брендов → найти конфликтующие токены (O(depth))
  │     ├→ Обратный BFS, break отсекает обратные рёбра
  │     └→ Нет проходимых обратных рёбер → прямое решение Proved / Disproved
  │
  └→ Медленный канал: логическое отсечение SMT (только когда быстрый канал встречает проходимое обратное ребро)
        │
        ├→ Начало обратного ребра имеет условие пути → SMT решает path_cond ⇒ !loop_cond
        │     ├→ Proved → логическое отсечение → возврат к быстрому каналу
        │     └→ Disproved / Unproven → проход через обратное ребро → пометить unsafe
        │
        └→ Начало обратного ребра не имеет условия пути → проход через обратное ребро напрямую
```

**Покрытие быстрого канала**: линейный код, if/else, loop + break, while без условий пути.
**Покрытие медленного канала**: когда тело цикла while имеет условие пути, указывающее на выход из
цикла. **Не покрывается**: условия времени выполнения, которые нельзя статически доказать → проход
через обратное ребро → unsafe → ошибка компиляции (пользователь рефакторит).

SMT — не основная сила — это страховочная сетка. В отличие от пользовательских предикатов RFC-027:
пользовательские предикаты используют SMT как основную силу; системные предикаты заимствований
используют структурный анализ как основную силу, SMT дополняет только те углы, до которых
структурный анализ не дотягивается.

> **Исправление (2026-08-17, коррекция позиционирования SMT)**: SMT — это **слой точности, а не
> зависимость soundness**. Звуковое (sound) решение системных предикатов заимствований полностью
> обеспечивается быстрым каналом (интервалы + обратный BFS + отсечение break); логическое отсечение
> SMT только определяет «могут ли быть пропущены легитимные программы на границах циклов». Когда SMT
> недоступен / тайм-аут / не реализован (RFC-027 impl: in_progress), fallback = проход через
> обратное ребро = консервативный отказ, то, что должно быть отвергнуто, всё равно будет отвергнуто.
> **Консервативность без SMT = заимствование+запись в цикле всегда отвергается, на одном уровне с
> Rust NLL** (производственная проверка заимствований Rust также без SMT). Реализация SMT — это
> чистый прирост точности, не блокирует поставку sound основной линии.

## Анализ примеров использования

### Линейный код

```yaoxiang
data = vec![1, 2, 3]        # узел 1
view = &data                # узел 2: потребляет data, производит ReadToken(#1)
x = view.total_count        # узел 3: потребляет view (= последний потребитель #1)
data.push(4)                # узел 4: требует WriteToken(data)
```

Обратный BFS от `view.total_count` (узел 3) → узел 3 — последний потребитель #1 → узел 4 > узел 3 →
узел 4 не в unsafe → ✅

### if/else: без специальных правил

```yaoxiang
view = &data
if cond {
    use(view)               # then-ветка потребляет view
} else {
    do_something_else()     # не трогает view
}
data.push(4)                # последний потребитель view в if → после if нет потребителей → ✅
```

if/else — это составной узел DAG. Внутреннее потребление приписывается этому узлу. Не объединяет
состояние ветвей. Не консервативный арбитраж. **Есть ли позже потребители — целочисленное
сравнение.**

> **Уточнение**: "не объединяет состояние ветвей" относится только к **живучести заимствований**
> (обратный BFS потребителей бренда). **Состояние move** (владение переменной) — это отдельный
> анализ: прямой поток данных по узлам CFG (стиль NLL/Polonius), при слиянии ветвей **консервативная
> встреча** (любая ветвь Moved → слияние Moved), недостижимые по тексту ветви (`if false`) не
> участвуют. Два слоя разделены: живучесть заимствований смотрит на "есть ли последующие
> потребители", анализ move смотрит на "возможно ли, что переменная уже была перемещена".

### if/else с возвратом значения (escape)

```yaoxiang
view = &data
result = if cond {
    view                     # view убегает в result
} else {
    something_else
}
use(result)                  # косвенное потребление view
data.push(4)                 # view всё ещё имеет потребителя (use(result))
                             # → push в unsafe → ❌ правильная ошибка
```

view убегает через возвращаемое значение → `use(result)` — потребитель view → обратное обхождение от
`push` достигает `use(result)` → unsafe.

### Цикл: break отсекает обратное ребро

```yaoxiang
view = &data
loop {
    use(view)                # consumer
    if is_last {
        data.push(4)         # операция записи
        break                # ← структурное отсечение
    }
}
```

Обратный BFS от `use(view)` → обратное ребро → вперёд к `data.push(4)` → встречает `break` →
**отсечение** → `data.push(4)` не в unsafe → ✅

Без break:

```yaoxiang
view = &data
loop {
    use(view)
    data.push(4)             # нет break для отсечения → обратное ребро проходимо → следующая итерация use(view) достижима
                             # → push в unsafe → ❌ правильная ошибка
}
```

### while: логическое отсечение SMT

```yaoxiang
view = &data
mut i: UpTo(n) = 0
while i < n {
    use(view)                # consumer
    i += 1
    if i == n {
        data.push(4)         # условие пути: i == n
    }
}
```

Обратный BFS от `use(view)` → обратное ребро → к `data.push(4)` → проверка условия пути `i == n` →
SMT-запрос: `i == n ⇒ !(i < n)`? → Proved → **логическое отсечение** → `data.push(4)` не в unsafe →
✅

> Исправление (2026-08-17): `i == n` — это условие пути самого узла записи (запись `data.push(4)`
> внутри ветки if), цель решения — узел записи (см. §Правила исправления сбора условий пути 1).

## Суть: ID бренда — это и есть `'a`

Не "нам не нужно `'a`". Скажем "`#42` — это и есть `'42`".

| Rust                                                  | YaoXiang                                       | Эквивалентность                                              |
| ----------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| `'a`                                                  | `#42`                                          | Идентификатор времени жизни на этапе компиляции              |
| `'a: 'b` ограничение outlives                         | `#42` — префикс для `#42.field_x`              | Сравнение строковых префиксов = отношение частичного порядка |
| Распространение живучести NLL (неподвижная точка CFG) | Обратный BFS (DAG)                             | Оба являются вычислениями достижимости                       |
| Факты Polonius                                        | Логическое отсечение SMT                       | Оба являются рассуждениями об условиях пути                  |
| Решение системы ограничений неподвижной точки         | Сопоставление префиксов в дереве брендов + BFS | Различное кодирование, та же проблема                        |

**Мы не изобрели новый анализ. Мы просто перенесли `'a` из уровня сигнатур типов на уровень
доказательств.** ID бренда делает точно то же, что и `'a` — отмечает идентичность заимствования,
отслеживает отношения наследования, определяет конфликты. Различие только одно: `'a` находится в
сигнатуре типа, написанной пользователем; `#42` — внутри компилятора.

В этом нет ничего постыдного. Curry-Howard говорит, что типы — это утверждения, программы —
доказательства. `'a` — не часть утверждения — это часть стратегии доказательства. Rust помещает
стратегию доказательства в сигнатуру утверждения. Мы вернули её туда, где ей место.

### Что устраняют ограничения дизайна языка

| Источник сложности                                    | Обойдено? | Причина                                                                         |
| ----------------------------------------------------- | --------- | ------------------------------------------------------------------------------- |
| Затенение переменной                                  | ✅        | Язык запрещает — одно имя всегда указывает на одно и то же                      |
| Заимствование между итерациями for                    | ✅        | Каждая итерация — новое связывание — естественная изоляция между итерациями     |
| Аннотация времени жизни `'a`                          | ✅        | Путь бренда = `#42.field_x`, выводится компилятором                             |
| Именованное время жизни + распространение ограничений | ✅        | Сравнение префиксов пути бренда заменяет явный набор ограничений                |
| Решение ограничений графа заимствований (Polonius)    | ✅        | Сопоставление префиксов в дереве брендов + запрос потребителей DAG              |
| Распространение живучести заимствований в теле цикла  | ❌        | Нужно обрабатывать как в Rust — с помощью обратного BFS + логического отсечения |
| Консервативность условных ветвей                      | ❌        | Как в Rust — SMT покрывает доказуемое, остальное консервативно отвергается      |

### Почему DAG выполнимо

Три ограничения дизайна языка YaoXiang делают анализ DAG выполнимым:

- **Нет затенения переменных** — одно имя всегда указывает на одно и то же, не нужно отслеживать
  пересвязывания
- **for связывает заново каждую итерацию** — естественная изоляция между итерациями, нет
  заимствований между итерациями
- **Структурированная конкурентность** — чёткие границы задач, не нужно распространение живучести
  между задачами

Эти ограничения устраняют основные источники сложности итераций неподвижной точки CFG в Rust. Не
потому что DAG "более продвинут" чем CFG — а потому что более простой дизайн языка позволяет более
простой анализ.

## Детальный дизайн

### Список системных предикатов

Компилятор автоматически генерирует следующие утверждения и отправляет их в конвейер доказательств
RFC-027:

| Системный предикат | Время срабатывания                 | Форма утверждения                             |
| ------------------ | ---------------------------------- | --------------------------------------------- |
| `borrow_conflict`  | Требуется WriteToken(v)            | `forall t ∈ conflicting(v): dead_at(t, node)` |
| `use_after_move`   | Использование переменной v         | `¬moved(v)`                                   |
| `use_after_drop`   | Использование переменной v         | `¬dropped(v)`                                 |
| `double_drop`      | Drop(v)                            | `¬dropped(v)`                                 |
| `mut_violation`    | Запись в неизменяемую переменную v | `is_mut(v)`                                   |

Существующие `BorrowChecker`, `MoveChecker`, `DropChecker`, `MutChecker` **становятся генераторами
утверждений** — не исчезают, а меняют роль. Они генерируют утверждения, конвейер верифицирует
утверждения.

### Дерево брендов

Механизм брендов из RFC-009 §2.7 формализуется как дерево брендов.

**Семантика токенов — заморозка первична, не копирование первично**:

Сущностное различие между `&T` и `&mut T` не в том, "можно ли копировать", а в том, "разрешена ли
одновременная запись":

```
ReadToken(T):  Предоставляет право только на чтение, одновременно замораживая исходные данные T — любой
               WriteToken(T) в этот период не может быть получен. Заморозка — основная семантика ReadToken.
               Dup (копируемость) — следствие заморозки: поскольку данные уже заморожены (мутация невозможна),
               множественные представления только для чтения естественно безопасны.

WriteToken(T): Предоставляет исключительное право на чтение и запись. Поскольку запись возможна, никакой
               другой токен (чтение или запись) не может сосуществовать. Отсутствие Dup (линейный тип) — следствие исключительности.
```

**Причинно-следственная связь**:

```
ReadToken существует → исходные данные заморожены → множественные только-для-чтения безопасны → Dup
                      ↓
              WriteToken отвергается (системный предикат borrow_conflict принудительно)
```

Не так:

```
ReadToken имеет Dup → может быть несколько → заодно проверим конфликты  ← обратная причинность
```

```
BrandTree:
  nodes: Map<BrandId, BrandNode>

BrandNode:
  id: BrandId               # "#42", "#42.field_x"
  kind: ReadToken | WriteToken
  source_var: Operand
  parent: Option<BrandId>   # родительский узел в отношении наследования
  children: Set<BrandId>    # производные дочерние токены
  consumers: Set<NodeId>    # узлы DAG, потребляющие этот токен
  ref_count: usize          # количество безопасных копий во время заморозки ReadToken
```

**Определение конфликта** — механизм выполнения, гарантированный заморозкой:

```rust
fn conflicts(a: &BrandId, b: &BrandId) -> bool {
    // Условие конфликта: один источник + хотя бы один — запись + перекрытие путей бренда
    // Это означает:
    //   1. ReadToken vs ReadToken → нет конфликта (оба только чтение, мутации нет)
    //   2. WriteToken vs ReadToken → конфликт (запись нарушает гарантию заморозки чтения)
    //   3. WriteToken vs WriteToken → конфликт (два записывающих не могут сосуществовать)
    a.source() == b.source()
        && (a.is_write() || b.is_write())
        && (a.is_prefix_of(b) || b.is_prefix_of(a))
}
```

Сравнение строковых префиксов O(depth), глубина ≤ 3. Константный уровень.

### Анализ живучести обратным BFS

> **Исправление (аудит 2026-08-17)**: следующий алгоритм дополняется измерением «время создания
> токена». Оригинал зависел от полного порядка узлов DAG, неявно подразумевая предположение
> «заимствование до записи», не покрывая легитимный порядок «запись сначала, заимствование потом»
> (§2.4 семантика: токен параметра освобождается по окончании вызова) — аудит выявил, что этот
> сценарий ложно отвергался. Живучесть токена — это **интервал** `[created_at, last_use]`, а не
> обратное достижимое множество; операция записи составляет конфликт только в пределах интервала
> живучести токена.

```
Алгоритм: check_borrow(token, node, dag, brand_tree)

Вход:
  token: WriteToken, который нужно проверить
  node:  узел DAG, в котором находится операция записи

Выход: Proved | Disproved

Алгоритм:
  # Быстрый канал: обратный BFS
  unsafe = empty_set
  queue = brand_tree.consumers(token)

  while queue not empty:
    cur = queue.pop()
    unsafe.add(cur)

    for each pred in dag.predecessors(cur):
      # Структурное отсечение: break не пересекается
      if pred является break ребром:
        continue

      # Обратное ребро → проверить, нужен ли fallback SMT
      if pred является обратным ребром:
        path_cond = условие пути узла записи node   # Исправление: цель решения — собственное условие узла записи
        loop_cond = условие цикла
        # Сначала посмотрим, можно ли отсечь структурно (соответствующий break уже отсёк путь → сюда не дойдёт)
        # Затем посмотрим на условие пути
        if path_cond не пусто:
          result = smt_fallback(path_cond, loop_cond)   # ← медленный канал
          if result == Proved:
            continue                    # логическое отсечение
        # Нет условия пути или SMT не доказал → проход через обратное ребро
        # fall through

      if pred ∉ unsafe:
        queue.push(pred)

  # Решение (исправление: добавить интервал времени создания)
  # Запись сначала, заимствование потом: node < created_at(token) → во время записи токен ещё не существовал → Safe
  if node ∈ unsafe and created_at(token) ≤ node:
    return Disproved
  else:
    return Proved


smt_fallback(path_cond, loop_cond):
  # Вызывается только при обратном ребре + наличии условия пути
  # Использует конвейер доказательств RFC-027, разделяет тот же SMT-решатель, тот же бюджет
  return smt.prove(path_cond ⇒ !loop_cond)
  # Proved → логическое отсечение
  # Disproved / Unproven → не отсекать, проход через обратное ребро (консервативный отказ)
  # Исправление (2026-08-17): SMT недоступен/тайм-аут/не реализован = ветвь Disproved —
  # SMT влияет только на точность (могут ли легитимные программы пройти), не на soundness (то, что должно быть отвергнуто, обязательно отвергается);
  # консервативность без SMT = заимствование+запись в цикле всегда отвергается, на одном уровне с Rust NLL.
```

BrandNode добавляет поле (исправление):

```
BrandNode:
  ...
  created_at: NodeId         # узел создания токена (исправление: левая граница интервала заимствования)
```

O(N), где количество вызовов SMT = количество обратных рёбер × доля обратных рёбер с условиями пути.
В реальном коде вызовы SMT крайне редки — срабатывают только при `while`-циклах с переменными
уточнённых типов в условиях пути.

### Сбор условий пути

Предоставляется существующими механизмами RFC-027 §3.2-3.3:

- **if-защита**: `if y > 0` → в true-ветку помещается `y > 0`
- **match-паттерн**: `if let Some(v) = opt` → в ветку помещается `opt == Some(v)`
- **Присваивание**: `i += 1`, компилятор поддерживает информацию о диапазоне значений переменной
- **while cond**: в тело цикла помещается `cond == true`

Каждый узел DAG несёт набор условий пути. При обратном BFS через обратное ребро берётся условие пути
начала обратного ребра, SMT определяет, исключает ли оно условие входа в следующую итерацию.

> **Исправление (2026-08-17, дополнение правил распространения)**: оригинал не определял, как
> условия пути распространяются к началу обратного ребра, пример «while + логическое отсечение SMT»
> с `i == n` был невоспроизводим по исходному алгоритму. Дополнительные правила:
>
> 1. **Условие пути привязано к самому узлу записи**: операция записи W внутри ветки несёт условие
>    ветки (`if i == n { W }` → path_cond(W) = `i == n`). Когда обратный BFS проходит через обратное
>    ребро, SMT определяет `path_cond(W) ⇒ !loop_cond` (путь, ведущий к W, обязательно выходит из
>    цикла → потребитель следующей итерации недостижим → отсечение), а не условие пути узла
>    обратного ребра.
> 2. **Консервативная очистка на слиянии**: точка слияния if/else не несёт условий пути внутри веток
>    (дизъюнкция условий двух веток обычно неразрешима, очищается напрямую). path_cond для операций
>    записи после точки слияния пуст → проход через обратное ребро.
> 3. **Семантизация условий пути**: path_cond — это ConstExpr (семантика RFC-027 §3.2), а не текст
>    исходного кода; smt_cut переводит его в ограничение SMT и решает.
> 4. **Нет условия пути → прямой проход через обратное ребро** (unsafe), SMT не вызывается.

### Интерфейс с RFC-027

Системные предикаты заимствований и пользовательские предикаты разделяют один конвейер доказательств
— различие в **основной стратегии доказательства**:

| Тип запроса                | Источник утверждения                    | Основная стратегия                         | Fallback                            |
| -------------------------- | --------------------------------------- | ------------------------------------------ | ----------------------------------- |
| Равенство типов            | Проверщик типов                         | Структурная эквивалентность                | —                                   |
| Пользовательские предикаты | Аннотации типов программиста            | SMT                                        | Функция-доказательство программиста |
| Конфликт заимствований     | Автоматически генерируется компилятором | **Структурный анализ DAG (быстрый канал)** | Логическое отсечение SMT            |

Роль SMT-решателя в проверке заимствований: **не основная сила, а страховочная сетка.** Вызывается
только при необходимости логического отсечения обратных рёбер while. Подавляющее большинство
проверок заимствований завершается на быстром канале — O(N) обратный BFS, нулевые затраты SMT.

### NLL и границы итераций

> **Исправление (2026-08-17, дополнение модели интервалов)**: живучесть токена — это **интервал**
> `[created_at, last_use]`, а не обратное достижимое множество. `created_at` = узел создания токена;
> `last_use` = максимальный узел потребления по анализу потребителей. Необходимое и достаточное
> условие конфликта операции записи W с токеном T:
> `conflicts(T, W) ∧ created_at(T) ≤ node(W) ∧ node(W) может быть прямо достигнут до last_use(T)`
> (определяется обратным BFS). Легитимный порядок «запись сначала, заимствование потом» (§2.4: токен
> параметра освобождается по окончании вызова) напрямую исключается через `created_at(T) ≤ node(W)`,
> без каких-либо специальных правил. Эта модель делает утверждение §Преимущества 5 «алгоритм не
> консервативен» верным для всех порядков.

**Момент смерти токена = точка последнего использования (NLL), а не конец лексической области
видимости.**

Это естественное следствие анализа потребителей: позиция потребителя определяет последнее
использование токена. `use(v)` — потребитель `v` → `v` умирает сразу после `use(v)`. Не нужны
дополнительные `{}` или `drop()` для досрочного завершения жизни токена.

**Граница итерации цикла — линия смерти копий токена.** Три правила:

```
Правило 1: Переменные, объявленные внутри цикла, автоматически умирают в конце каждой итерации.
          Каждая итерация for — это новое связывание (гарантируется дизайном языка), то же для loop.

Правило 2: ref_count дерева брендов на заголовке цикла учитывает только копии, созданные вне цикла.
          Новые копии от Dup внутри цикла, ref_count обнуляется на границе итерации.

Правило 3: Когда обратный BFS проходит через обратное ребро, он не несёт информацию о живучести текущей итерации.
          Несёт только ref_count в заголовке цикла (т.е.: копии вне цикла).
```

Пример:

```yaoxiang
view = &data                          # заголовок цикла: ref_count = 1, consumer = use(view)
loop {
    v2: &Point = view                 # Dup внутри цикла → ref_count = 2
    use(v2)                           # consumer: последнее использование v2 → v2 умирает → ref_count = 1
    data.push(4)                      # ✅ безопасно! v2 мёртв, остался только view (ref_count = 1, конфликта записи нет)
    # граница итерации: правило 3 — не несёт v2 в следующую итерацию. В начале следующей итерации v2 пересоздаётся через новое связывание.
}
```

Этот дизайн не требует дополнительных правил «консервативной живучести в цикле». Обратный BFS
запускается от потребителя, потребитель находится в теле цикла → живучесть ограничена текущей
итерацией → обратное ребро не пересекается. Полностью согласуется с примером цикла в §Анализ
примеров использования RFC-009a.

### Распространение ошибок `?` и Release, управляемый областью видимости

`?` — это досрочный возврат — помимо нормального выхода из области видимости есть ещё один путь
выхода. Токены должны быть освобождены на этом пути, неправильный порядок освобождения — UB.

**Инструкции Release генерируются анализом области видимости, а не жёстко закодированы после Call.**

Компилятор поддерживает список точек выхода для каждой области видимости:

- `}` (нормальное завершение области видимости)
- `?` (распространение ошибки, досрочный return)
- Явный `return`

В каждой точке выхода в обратном порядке объявления (LIFO) вставляются инструкции Release для всех
активных токенов этой области видимости. Отношения родитель-потомок в дереве брендов автоматически
обрабатывают каскадное освобождение производных токенов:

```yaoxiang
Point.get_x: (self: &Point) -> (&Float, &Point) = {
    return (&self.x, self)    # возврат дочернего токена &Float + родительского токена &Point
}

fn use_case(p: Point) -> Result<(), Error> = {
    (x_ref, p_ref) = p.get_x()?   # если ? распространяет:
    # дерево брендов знает, что x_ref — производный от p_ref (#42.field_x — префикс #42)
    # порядок освобождения: x_ref (дочерний) → p_ref (родительский) → LIFO автоматически удовлетворяется
    p.modify()                     # WriteToken — все ReadToken уже освобождены
    Ok(())
}
```

Расположение реализации: остаётся в `ir_gen.rs`, изменён на управляемый областью видимости — без
введения нового прохода компилятора.

| Определение конфликта | O(1) | Каждый запрос токена | | Запрос потребителей DAG | O(1) | Каждый
запрос токена | | Обратный BFS (быстрый канал) | O(N) | Каждый запрос токена, N = количество узлов в
блоке | | Логическое отсечение SMT (fallback) | ~1ms | **Крайне редко** — только while + условие
пути |

> Исправление (2026-08-17): сложности в таблице выше — проектные оценки, не измеренные; "~1ms" и
> "крайне редко" следует рассматривать как ожидания порядка величины, а не измеренные значения,
> после реализации калибруются по наблюдаемым данным.

**Условия срабатывания fallback SMT крайне строгие**: должны одновременно выполняться (1) цикл while
(2) в теле цикла есть операция записи (3) после операции записи есть условие пути, по которому можно
судить о завершении цикла (4) компилятору нужно полагаться на это условие для отсечения обратного
ребра. В реальном коде доля значительно ниже 1%. Остальные проверки заимствований полностью
завершаются на быстром канале.

Отношение к пользовательским предикатам RFC-027: пользовательские предикаты используют SMT как
основную силу, системные предикаты заимствований используют структурный анализ как основную силу.
Оба разделяют один и тот же SMT-решатель и верхний предел бюджета (RFC-027 §8), но системные
предикаты заимствований почти не потребляют бюджет SMT.

Линейный код → нет обратных рёбер → уровень 1 O(N) за секунды. Цикл + условие пути → вызов SMT,
линейная арифметика миллисекунды (бюджет RFC-027 100ms). Результат одного BFS может кэшироваться для
повторного использования в нескольких запросах того же токена.

### Дизайн сообщений об ошибках

**Ключевой принцип: сообщения об ошибках содержат только символы, написанные пользователем.**

Ошибки Rust, связанные с заимствованиями, делятся на две категории:

**Ошибки уровня переменных**: E0597 (живёт недостаточно долго), E0502 (одновременное изменяемое +
неизменяемое заимствование), E0499 (множественные изменяемые заимствования). Rust уже является
эталоном — имя переменной + номер строки, без `'a`. YaoXiang имеет сопоставимую точность. Вся
информация в дереве брендов: точка создания токена, позиция потребителя, точка запроса.

**Ошибки уровня сигнатур**: E0623 (несоответствие времени жизни), E0106 (отсутствующий спецификатор
времени жизни), E0477 (не удовлетворено требуемое время жизни). Вокруг `'a`. YaoXiang **не имеет
таких ошибок** — в сигнатуре нет `'a`. Не "нельзя сообщить", а то, что пользователь не писал, не
нужно сообщать.

Пример конфликта внутри функции:

```
ошибка: `data` заморожен, невозможно получить изменяемое право
 --> src/main.yx:5:9
2 |     view = &data
  |            ----- `data` заморожен (токен только-для-чтения создан здесь)
4 |         use(view)
  |             ---- `view` всё ещё используется здесь, заморозка не снята
5 |         data.push(4)
  |         ^^^^ здесь требуется изменяемое право
```

(Сопоставимая с Rust E0499 точность — имя переменной + номер строки, без ID бренда.)

Пример межфункционального побега:

```
ошибка: один из источников данных, удерживаемых `num` (строка 4), — это `default_str` (строка 3),
но `default_str` становится недействительным в строке 6, а `num` всё ещё используется в строке 5.

Рассмотрите: переместите объявление `default_str` выше к вызывающему коду, или используйте `ref default_str` для общего владения.
```

(Сопоставимая с Rust E0597 точность. Сводка брендов знает, что у `num` есть два пути источника — уже
есть в компиляторе, формулировка ошибки доступна.)

## Исправления к основному тексту RFC-009

RFC-009 §"Обнаружение конфликтов токенов: потоково-чувствительный анализ живучести" обновлён:

1. Удалено "не нужно: ……NLL" — не потому что вывод неверен, а потому что причина неверна ("токены —
   это значения, линейного отслеживания достаточно")
2. Промежуточные решения уровня 1/уровня 2 сохранены, полное решение указывает на данный RFC
3. Уточнено: ID бренда (`#42`) — это и есть `'a` — информация полностью та же, кодирование
   отличается. Не изобретён новый анализ — время жизни перенесено с уровня типов на уровень
   доказательств

## Компромиссы

### Преимущества

1. **Сигнатура типа не содержит времени жизни**: `#42` — это `'42` — та же информация,
   закодированная в дереве брендов, не выставленная в сигнатуре типа. Это нельзя опровергнуть:
   посчитайте, сколько параметров `'a` нужно для обобщённого типа с 3 параметрами-ссылками в Rust, и
   сколько в YaoXiang. Ответ: 3 против 0.

2. **Концептуальное единство**: проверка заимствований и пользовательские предикаты разделяют один
   конвейер доказательств — `{P} op {Q}`, конвейер верифицирует P. Согласованность с Curry-Howard.

3. **Ноль новых фреймворков анализа**: не вводится новый фреймворк анализа. Пользователь не
   воспринимает существование «проверщика заимствований» — как пользователь не воспринимает детали
   реализации «проверщика типов».

4. **Сообщения об ошибках содержат только символы, написанные пользователем**: минус целое измерение
   категорий ошибок (E0623, E0106, E0477 — все вокруг `'a`). Ошибки уровня переменных — сопоставимая
   с Rust точность.

5. **Алгоритм не консервативен**: обратный BFS + отсечение break + логическое отсечение SMT. Не
   нужна «консервативная живучесть в цикле». Не нужно «консервативное слияние ветвей».

### Недостатки

1. **Не новое изобретение**: ID бренда делает точно то же, что и `'a` — сложность решения
   ограничений внутри компилятора не исчезла, просто способ кодирования изменился с «имя
   переменной + набор ограничений» на «путь бренда + сопоставление префиксов». Для конечного
   пользователя различие только в том, что в сигнатуре не пишется `'a`.

2. **Полностью новая реализация**: дерево брендов в коде существует только как концепция, требует
   реализации с нуля. BorrowChecker, ControlFlowAnalyzer заменяются.

3. **Зависимость от SMT**: логическое отсечение зависит от Z3 (уже введён в RFC-027, новых
   зависимостей не добавляется). Но проверка заимствований почти не срабатывает — только при while +
   условии пути.

4. **Крайне редкие паттерны требуют рефакторинга**: автоматическое доказательство компилятора не
   покрывает межветвевые заимствования, пользователю нужно рефакторить код. Отличается от
   подстраховки Rust `'a`: в Rust есть `'a` как инструмент (аннотация — и проходит); подстраховка
   YaoXiang (функция-доказательство) не входит в MVP.

## Альтернативы

| Альтернатива                                      | Почему не выбрана                                                                                                                                   |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Реализовать полный Rust NLL                       | Ограничения дизайна YaoXiang (нет затенения, for — новое связывание) уже устранили основные источники сложности NLL, неподвижная точка CFG не нужна |
| Сохранить текущее (жёстко закодированный Release) | Недостаточно — пользователь должен вручную управлять областью видимости токенов                                                                     |
| Анализ только в spawn-блоках                      | Недостаточно — использование токенов в не-spawn коде составляет большинство                                                                         |
| GC вместо проверки заимствований                  | Нарушает принципы дизайна языка — в YaoXiang нет GC                                                                                                 |

## Открытые вопросы

- [x] **Семантика ref_count дерева брендов между итерациями при развёртке цикла** — выбран NLL:
      токен умирает после последнего использования. Копии, связанные внутри цикла, умирают на
      границе итерации, обратный BFS не несёт живучесть между итерациями. Подробности в §NLL и
      границы итераций.
- [x] **Порядок освобождения токенов на пути распространения ошибок `?`** — Release управляется
      анализом области видимости (остаётся в ir_gen.rs). Каждая точка выхода области видимости (`}`,
      `?`, явный return) освобождает активные токены по LIFO. Отношения родитель-потомок в дереве
      брендов автоматически обрабатывают каскадное освобождение. Подробности в §Распространение
      ошибок `?` и Release, управляемый областью видимости.
- [ ] Синтаксис функций-доказательств (долгосрочно, не входит в MVP — не блокирует ни одну фазу)
