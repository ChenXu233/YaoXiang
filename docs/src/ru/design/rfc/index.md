## Жизненный цикл RFC

```
Черновик → На рассмотрении → Принят → Устарел (заменён)
                              ↓
                          Отклонён (не прошёл)
```

### Описание статусов

| Статус              | Расположение      | Описание                                                                   |
| ------------------- | ----------------- | -------------------------------------------------------------------------- |
| **Черновик**        | `rfc/draft/`      | Черновик автора, ожидает отправки на рассмотрение                          |
| **На рассмотрении** | `rfc/review/`     | Открыто для обсуждения сообществом и обратной связи                        |
| **Принят**          | `rfc/accepted/`   | Становится официальным проектным документом, переходит в стадию реализации |
| **Устарел**         | `rfc/deprecated/` | Ранее принятый, заменён новым дизайном                                     |
| **Отклонён**        | `rfc/rejected/`   | Отклонённый документ RFC                                                   |

## Правила редактирования документации

**Документ RFC должен содержать только корректную информацию.** При изменении дизайна следует
напрямую изменять исходный текст, чтобы он выражал текущую корректную семантику; **запрещается
сохранять ошибочное содержимое и добавлять блок «исправлений» для его корректировки**.

Сохранение «оригинала + исправлений» — наихудший вариант: читатель, прочитав половину документа,
обнаруживает, что всё предыдущее устарело, затраты на чтение тратятся впустую, и легко ошибочно
принять отменённые абзацы за текущую семантику. Блок исправлений выглядит осторожным, но на деле
перекладывает затраты на оформление на читателя.

### Правильный подход

| Ситуация                                                                 | Действие                                                                                                                                 |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Реализация не соответствует исходному тексту, исходный текст пересмотрен | Переписать этот абзац непосредственно в корректный вид, удалив исходную формулировку                                                     |
| Пример кода больше не может быть выполнен                                | Изменить его в исполняемый вид, не сохраняя старый пример                                                                                |
| Необходимо дать читателю понять, «как было раньше»                       | Сохранять ошибочное содержимое только при **намеренном сравнении ошибок**, и сразу же отмечать «эта запись ошибочна» с указанием причины |
| Необходимо отследить эволюцию дизайна                                    | Записывать в сообщениях коммитов Git или issue, не вносить в основной текст RFC                                                          |

### Исключения

Следующая ошибочная информация может быть сохранена:

- **Намеренные сравнительные примеры для обучения**: явно обозначены как сравнение правильного и
  неправильного, при этом ошибочная сторона сразу же сопровождается объяснением «почему это
  неправильно»
- **Устаревшие RFC** (`rfc/deprecated/`): сохраняются как историческая запись, но должны быть
  помечены тем, кем они заменены

### Вспомогательные приёмы

- Поля `status` / `updated` в верхней части RFC отражают время последнего изменения, нет
  необходимости писать в основном тексте «что было пересмотрено в этот раз»
- Статус реализации выражается с помощью ✅ / ❌ в таблицах, избегайте переплетения описаний статуса
  в основном тексте
- Полную историю изменений можно просмотреть с помощью `git log -- <файл>`

## Отправка RFC

1. Прочтите [RFC_TEMPLATE.md](RFC_TEMPLATE.md) для понимания требований к формату
2. Обратитесь к [EXAMPLE_full_feature_proposal.md](EXAMPLE_full_feature_proposal.md) для изучения
   стиля написания
3. Создайте новый файл с именем `номер-описательное-название.md`
4. Поместите файл в каталог `docs/reference/rfc/draft/`
5. Обновите данный индексный файл, добавив новую запись RFC
6. Отправьте PR для перехода в процесс рассмотрения
