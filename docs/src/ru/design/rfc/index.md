## Жизненный цикл RFC

```
Черновик → На рассмотрении → Принят → Устарел (заменён)
                              ↓
                          Отклонён (не прошёл)
```

### Описание статусов

| Статус         | Расположение            | Описание                                      |
| -------------- | ----------------------- | --------------------------------------------- |
| **Черновик**   | `rfc/draft/`            | Авторский черновик, ожидает подачи на рассмотрение |
| **На рассмотрении** | `rfc/review/`       | Открыто для обсуждения сообщества и обратной связи |
| **Принят**     | `rfc/accepted/`         | Становится официальным документом, переходит в стадию реализации |
| **Устарел**     | `rfc/deprecated/`       | Был принят, заменён новым дизайном            |
| **Отклонён**   | `rfc/rejected/`         | Документ RFC с отказом                        |

## Правила редактирования документации

**RFC документы могут содержать только корректную информацию.** При изменении дизайна напрямую переписывайте оригинал, чтобы он отражал текущую корректную семантику;
**запрещено сохранять устаревшее содержимое и добавлять блоки «исправлений»**.

Сохранение «оригинала + исправлений» — наихудший подход: читатель доходит до середины и обнаруживает, что всё прочитанное недействительно, время на чтение потрачено впустую, а устаревшие абзацы легко принять за действующую семантику. Блок исправлений выглядит осторожным решением, но фактически перекладывает стоимость упорядочивания на читателя.

### Правильный подход

| Ситуация                              | Действие                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Реализация не соответствует тексту    | Перепишите абзац в соответствии с корректным содержанием, удалите старое утверждение             |
| Пример кода больше не работает       | Приведите его к работающему виду, не сохраняйте старый пример                                     |
| Нужно показать «как было раньше»     | Сохраняйте устаревшее содержимое только при **намеренном сравнительном обучении**, с пометкой «это неверный подход» рядом с объяснением почему |
| Нужен трек эволюции дизайна          | Указывайте в сообщениях коммитов Git или в issue, не в основном тексте RFC                      |

### Исключения

Следующая ошибочная информация может быть сохранена:

- **Намеренное сравнительное обучение**: чётко обозначено как сравнение правильного и неправильного подходов, с объяснением «почему неверно» рядом с ошибочным вариантом
- **Устаревшие RFC** (`rfc/deprecated/`): в качестве исторической справки, но с указанием кем заменены

### Вспомогательные средства

- Поля `status` / `updated` в заголовке RFC отражают дату последнего обновления, не нужно писать в тексте «что было исправлено»
- Состояние реализации выражается в таблице через ✅ / ❌, избегайте вставки описаний статуса в текст
- Полную историю изменений смотрите через `git log -- <файл>`

## Подача RFC

1. Прочитайте [RFC_TEMPLATE.md](RFC_TEMPLATE.md) для понимания требований к формату
2. Изучите [EXAMPLE_full_feature_proposal.md](EXAMPLE_full_feature_proposal.md) для изучения стиля написания
3. Создайте новый файл с именем `номер-описательное-название.md`
4. Поместите файл в директорию `docs/reference/rfc/draft/`
5. Обновите этот индексный файл, добавив новую запись RFC
6. Отправьте PR для прохождения процесса рассмотрения
