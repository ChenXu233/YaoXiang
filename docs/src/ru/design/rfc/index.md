## Жизненный цикл RFC

```
Черновик → На рассмотрении → Принят → Устарел (заменён)
                                  ↓
                              Отклонён (не прошёл)
```

### Описание статусов

| Статус              | Расположение      | Описание                                                                   |
| ------------------- | ----------------- | -------------------------------------------------------------------------- |
| **Черновик**        | `rfc/draft/`      | Черновик автора, ожидает отправки на рассмотрение                          |
| **На рассмотрении** | `rfc/review/`     | Открыто для обсуждения и обратной связи от сообщества                      |
| **Принят**          | `rfc/accepted/`   | Становится официальным проектным документом, переходит в стадию реализации |
| **Устарел**         | `rfc/deprecated/` | Был принят, но заменён новым дизайном                                      |
| **Отклонён**        | `rfc/rejected/`   | Документ отклонённого RFC                                                  |

## Правила редактирования документации

**Документ RFC должен содержать только корректную информацию.** При изменении дизайна следует
непосредственно изменять исходный текст так, чтобы он отражал текущую корректную семантику; **нельзя
сохранять ошибочное содержание и добавлять блок «исправлений» (errata)**.

Сохранение «исходного текста + исправлений» — наихудший подход: читатель, дойдя до определённого
места, обнаруживает, что всё предыдущее стало недействительным, потраченное на чтение время
оказывается напрасным, и возникает риск ошибочного цитирования уже отменённых абзацев как
действующей семантики. Блок исправлений выглядит осторожным, но фактически перекладывает затраты на
упорядочивание на читателя.

### Правильный подход

| Ситуация                                                             | Действие                                                                                                                          |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Реализация не соответствует исходному тексту, исходный текст отменён | Непосредственно переписать абзац в корректный вид, удалив прежнюю формулировку                                                    |
| Пример кода больше не может быть запущен                             | Непосредственно привести его в запускаемый вид, не сохраняя старый пример                                                         |
| Необходимо дать читателю понять «как было раньше»                    | Сохранять ошибочное содержание только при **намеренном сравнении ошибок**, сразу отмечая «эта запись ошибочна» и указывая причину |
| Необходимо отследить эволюцию дизайна                                | Описывать в сообщениях коммитов Git или в issue, а не в основном тексте RFC                                                       |

### Исключения

Допускается сохранение следующей ошибочной информации:

- **Намеренные обучающие сравнения**: явно обозначены как сравнение правильного и ошибочного, при
  этом ошибочная сторона сразу же сопровождается пояснением «почему это неверно».
- **Устаревшие RFC** (`rfc/deprecated/`): служат исторической записью, но должны содержать пометку о
  том, кем они заменены.

### Вспомогательные средства

- Поля `status` / `updated` в начале RFC отражают время последней ревизии, нет необходимости писать
  в основном тексте «что было отредактировано в этот раз».
- Статус реализации выражайте с помощью таблиц ✅ / ❌, избегая включения описаний статуса в
  основной текст.
- Полную историю ревизий можно посмотреть командой `git log -- <файл>`.

## Отправка RFC

1. Прочитайте [RFC_TEMPLATE.md](RFC_TEMPLATE.md), чтобы ознакомиться с требованиями к формату.
2. Изучите [EXAMPLE_full_feature_proposal.md](EXAMPLE_full_feature_proposal.md) в качестве образца
   написания.
3. Создайте новый файл с именем `номер-описательный-заголовок.md`.
4. Поместите файл в каталог `docs/reference/rfc/draft/`.
5. Обновите данный индексный файл, добавив новую запись RFC.
6. Отправьте PR для перехода к процессу рассмотрения.
