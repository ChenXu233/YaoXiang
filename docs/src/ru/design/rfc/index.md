## Жизненный цикл RFC

```
Черновик → На рассмотрении → Принято → Устарело (заменено)
                              ↓
                          Отклонено (не прошло)
```

### Описание статусов

| Статус              | Расположение      | Описание                                                           |
| ------------------- | ----------------- | ------------------------------------------------------------------ |
| **Черновик**        | `rfc/draft/`      | Черновик автора, ожидает отправки на рассмотрение                  |
| **На рассмотрении** | `rfc/review/`     | Открыто для обсуждения сообществом и обратной связи                |
| **Принято**         | `rfc/accepted/`   | Стал официальным проектным документом, переходит в фазу реализации |
| **Устарело**        | `rfc/deprecated/` | Был принят, но заменён новым дизайном                              |
| **Отклонено**       | `rfc/rejected/`   | Документ отклонённого RFC                                          |

## Правила ревизии документов

**Документ RFC может содержать только корректную информацию.** При изменении дизайна просто измените
исходный текст, чтобы он отражал текущую правильную семантику; **не сохраняйте ошибочное содержимое
с добавлением блока «исправлений»**.

Сохранение «оригинала + исправления» — наихудший подход: читатель, дойдя до середины, обнаруживает,
что всё ранее написанное устарело, потраченное на чтение время оказывается напрасным, а отменённые
абзацы легко ошибочно принять за действующую семантику. Блок исправлений выглядит осторожным, но на
деле перекладывает затраты на упорядочивание на читателя.

### Правильный подход

| Ситуация                                                  | Действие                                                                                                                               |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Реализация не соответствует оригиналу, оригинал отвергнут | Перепишите абзац правильным содержанием, удалите исходную формулировку                                                                 |
| Примеры кода больше не запускаются                        | Измените их на запускаемую форму, не сохраняйте старые примеры                                                                         |
| Нужно дать читателю знать, «как было раньше»              | Сохраняйте ошибочное содержимое только при **намеренном сравнении ошибок** и сразу помечайте «эта запись ошибочна» с указанием причины |
| Нужно отследить эволюцию дизайна                          | Записывайте это в сообщениях Git-коммитов или issues, а не в основном тексте RFC                                                       |

### Исключения

Следующая ошибочная информация может быть сохранена:

- **Намеренные обучающие сравнения**: явно помечены как сопоставление правильного и неправильного,
  при этом ошибочная сторона сопровождается объяснением «почему неправильно»
- **Устаревшие RFC** (`rfc/deprecated/`): как историческая запись, но должно быть указано, кем
  заменён

### Вспомогательные средства

- Поля `status` / `updated` в верхней части RFC отражают время последней ревизии; нет необходимости
  писать в основном тексте «что было изменено в этой ревизии»
- Статус реализации выражайте с помощью таблиц ✅ / ❌, избегайте вплетения описаний статуса в
  основной текст
- Полную историю ревизий смотрите через `git log -- <файл>`

## Подача RFC

1. Прочитайте [RFC_TEMPLATE.md](RFC_TEMPLATE.md), чтобы узнать требования к формату
2. Обратитесь к [EXAMPLE_full_feature_proposal.md](EXAMPLE_full_feature_proposal.md), чтобы изучить
   стиль написания
3. Создайте новый файл с именем `номер-описательное-название.md`
4. Поместите файл в каталог `docs/reference/rfc/draft/`
5. Обновите этот индексный файл, добавив новую запись RFC
6. Отправьте PR для входа в процесс рассмотрения
