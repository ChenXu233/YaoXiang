## Жизненный цикл RFC

```
草案 → 审核中 → 已接受 → 已废弃（被取代）
                  ↓
               已拒绝（不通过）
```

### Описание статусов

| Статус              | Расположение      | Описание                                                                   |
| ------------------- | ----------------- | -------------------------------------------------------------------------- |
| **Черновик**        | `rfc/draft/`      | Черновик автора, ожидает отправки на рассмотрение                          |
| **На рассмотрении** | `rfc/review/`     | Открыто для обсуждения и обратной связи от сообщества                      |
| **Принято**         | `rfc/accepted/`   | Становится официальным проектным документом, переходит в стадию реализации |
| **Устарело**        | `rfc/deprecated/` | Ранее было принято, заменено новым дизайном                                |
| **Отклонено**       | `rfc/rejected/`   | Документ RFC, который был отклонён                                         |

## Правила редактирования документа

**Документы RFC должны содержать только корректную информацию.** При изменении дизайна напрямую
изменяйте исходный текст, чтобы он отражал текущую правильную семантику; **недопустимо сохранять
ошибочный контент и добавлять блок «ошибок» (勘误) для исправления**.

Сохранение «оригинал + ошибки» — наихудший подход: читатель, прочитав половину, обнаруживает, что
всё предыдущее устарело, затраты на чтение были потрачены впустую, и есть риск ошибочно принять
отменённый раздел за актуальную семантику. Блок ошибок выглядит осторожным, но на деле перекладывает
затраты на структурирование на читателя.

### Правильный подход

| Ситуация                                                  | Действие                                                                                                                                        |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Реализация не соответствует оригиналу, оригинал отвергнут | Напрямую перепишите раздел, чтобы он содержал корректное содержимое, удалите исходную формулировку                                              |
| Пример кода больше не запускается                         | Напрямую измените на работоспособный вид, не сохраняйте старый пример                                                                           |
| Нужно дать читателю понять «как было раньше»              | Сохраняйте ошибочный контент только при **намеренном сравнении ошибок**, и сразу же отмечайте «этот способ записи ошибочен» с указанием причины |
| Нужно отследить эволюцию дизайна                          | Записывайте в сообщениях коммитов Git или в issue, не включайте в основной текст RFC                                                            |

### Исключения

Следующая ошибочная информация может быть сохранена:

- **Намеренное обучающее сравнение**: явно обозначено как сравнение правильного и неправильного, при
  этом неправильная сторона сопровождается объяснением «почему это неправильно»
- **Устаревшие RFC** (`rfc/deprecated/`): как историческая запись, но должно быть указано, чем они
  заменены

### Вспомогательные средства

- Поля `status` / `updated` в начале RFC отражают время последней правки, нет необходимости писать в
  основном тексте «что было изменено в этот раз»
- Статус реализации выражается с помощью ✅ / ❌ в таблице, избегайте включения описания статуса в
  основной текст
- Полную историю изменений можно просмотреть с помощью `git log -- <файл>`

## Отправка RFC

1. Прочтите [RFC_TEMPLATE.md](RFC_TEMPLATE.md) для ознакомления с требованиями к формату
2. Обратитесь к [EXAMPLE_full_feature_proposal.md](EXAMPLE_full_feature_proposal.md) для изучения
   стиля написания
3. Создайте новый файл с именем `номер-описательное-название.md`
4. Поместите файл в каталог `docs/reference/rfc/draft/`
5. Обновите этот файл индекса, добавив новую запись RFC
6. Отправьте PR для входа в процесс рассмотрения
