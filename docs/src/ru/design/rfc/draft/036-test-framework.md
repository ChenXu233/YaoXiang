# RFC-036: Фреймворк тестирования std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного фреймворка тестирования — модуля `std.test` и подкоманды CLI `yaoxiang test`. Обнаружение тестов основано на существующей аннотации `@test` для маркировки функций (**ноль нового синтаксиса**), для утверждений используются чистые функции, экспортируемые модулем std.test (`assert_eq`, `assert_ne`, `assert_ok`, `assert_err`), а выполнение тестов осуществляется компилятором путём сканирования аннотаций и диспетчеризации во время выполнения. Не вводится ни новых ключевых слов, ни зарезервированных слов, ни синтаксических конструкций.

## Мотивация

### Зачем нужен фреймворк тестирования?

В настоящее время тесты YaoXiang разбросаны по `#[test]` на стороне Rust и интеграционным тестам в `tests/`, а покрытие тестами самого языка YaoXiang зависит от кода на Rust. Это означает:

1. Модульные тесты стандартной библиотеки YaoXiang (std.math / std.list / std.dict / std.convert / std.io) невозможно писать на YaoXiang
2. Задача `#117 Покрытие модульными тестами каждого модуля стандартной библиотеки` заблокирована из-за отсутствия доступной инфраструктуры тестирования
3. Регрессионное тестирование языковых возможностей (например, изменение семантики spawn в RFC-032) не имеет автоматизированных средств

### Ключевое ограничение: ноль нового синтаксиса

YaoXiang сохраняет только 17 базовых ключевых слов (`pub`, `use`, `spawn`, `if`, `else`, `match`, `for`, `in`, `while`, `return`, `break`, `continue`, `as`, `ref`, `true`, `false`, `None`) — это явно заявленный бескомпромиссный принцип в дизайн-манифесте.

**Фреймворк тестирования ни в коем случае не должен вводить новые ключевые слова (например, ключевые слова `test`, `assert`) или новые синтаксические конструкции (например, блоки кода `test`).**

## Предложение

### Основной дизайн

```
┌─────────────────────────────────────────────────────────────────┐
│                    Архитектура тестирования (три уровня)         │
│                                                                 │
│  ① Уровень обнаружения: компилятор сканирует аннотацию @test    │
│     → генерирует список тестов                                   │
│      Новый синтаксис не добавляется, @ аннотация уже существует   │
│                                                                 │
│  ② Уровень выполнения: подкоманда yaoxiang test                  │
│      обнаружение → компиляция → параллельное выполнение → отчёт  │
│                                                                 │
│  ③ Уровень утверждений: чистые функции модуля std.test           │
│      assert_eq / assert_ne / assert_ok / assert_err              │
│      Ноль нового синтаксиса, вызов чистых функций                │
└─────────────────────────────────────────────────────────────────┘
```

### Пример использования

```yaoxiang
# Файл тестов: math_test.yx
use std.test
use std.math

# Аннотация @test маркирует тестовую функцию (@ — существующий Token, не новый синтаксис)
@test
fn test_add() -> Void = {
    test.assert_eq(2 + 3, 5)
    test.assert_eq(-1 + 1, 0)
    test.assert_eq(0 + 0, 0)
}

@test
fn test_subtract() -> Void = {
    test.assert_eq(10 - 3, 7)
    test.assert_ne(10 - 3, 8)
}

@test
fn test_divide_by_zero() -> Void = {
    test.assert_err(1 / 0)
}
```

```bash
# Запуск всех тестов
yaoxiang test

# Запуск одного файла
yaoxiang test math_test.yx

# Запуск тестов, соответствующих имени
yaoxiang test --filter "add"
```

### Изменения синтаксиса

**Отсутствуют.** Настоящее предложение не вводит никаких новых синтаксических конструкций.

| Пункт | Состояние |
|------|------|
| Новые ключевые слова | ❌ Нет |
| Новые зарезервированные слова | ❌ Нет |
| Новые синтаксические конструкции | ❌ Нет |
| Аннотация `@test` | ✅ Повторное использование существующего токена `@` |
| Модуль `std.test` | ✅ Новый модуль, чистые функции |

## Детальное проектирование

### 1. Механизм обнаружения тестов

#### 1.1 Аннотация `@test`

`@test` использует уже существующий в YaoXiang синтаксис аннотаций `@`. Механизм аннотаций уже поддерживается на уровне парсера (использование аннотаций `@block`/`@eager` в RFC-008 доказывает работоспособность механизма).

**Формат аннотации**:

```yaoxiang
@test
fn test_name() -> Void = { ... }
```

**Правила**:
- `@test` располагается непосредственно перед определением функции
- Аннотированная функция должна иметь сигнатуру `() -> void`
- Аннотация только маркирует и не изменяет поведение функции — функция с `@test` остаётся обычной вызываемой функцией при обычном `run` (но не вызывается автоматически)
- Обнаружение тестов активируется только подкомандой `yaoxiang test`

#### 1.2 Процесс обнаружения тестов

```
yaoxiang test
```

### 2. Проектирование модуля `std.test`

#### 2.1 Структура модуля

```
src/std/test.rs
    ├── assert_eq(actual, expected)     → void
    ├── assert_ne(actual, expected)     → void
    ├── assert_ok(value)                → void
    ├── assert_err(value)               → void
    ├── assert_true(cond)               → void
    ├── assert_false(cond)              → void
    ├── assert_passes()                 → void
    └── assert_fails()                  → void (явный провал)
```

#### 2.2 Спецификация функций утверждений

Все функции утверждений в случае провала выбрасывают `ExecutorError::TestAssertionFailed`, содержащее:
- Путь к файлу (полученный из позиции исходного кода аннотированной функции)
- Номер строки
- Информацию об ошибке (actual vs expected)
- Имя тестовой функции

```yaoxiang
# Псевдокод реализации std.test.assert_eq
fn assert_eq(actual, expected) -> Void = {
    if actual == expected {
        return
    }
    raise TestAssertionFailed(
        "assertion failed: {actual} != {expected}",
        file, line, test_name
    )
}
```

#### 2.3 Регистрация модуля

Регистрация через существующий trait `StdModule`, полностью аналогично модулям `std.io` / `std.math` и т.д.:

```rust
impl StdModule for TestModule {
    fn module_path(&self) -> &str { "std.test" }

    fn exports(&self) -> Vec<NativeExport> {
        vec![
            NativeExport::new("assert_eq",  "std.test.assert_eq",  "(a: T, b: T) -> Void", native_assert_eq),
            NativeExport::new("assert_ne",  "std.test.assert_ne",  "(a: T, b: T) -> Void", native_assert_ne),
            NativeExport::new("assert_ok",  "std.test.assert_ok",  "(r: Result(T)) -> Void", native_assert_ok),
            NativeExport::new("assert_err", "std.test.assert_err", "(r: Result(T)) -> Void", native_assert_err),
            NativeExport::new("assert_true", "std.test.assert_true", "(b: Bool) -> Void", native_assert_true),
            NativeExport::new("assert_false","std.test.assert_false","(b: Bool) -> Void", native_assert_false),
            NativeExport::new("fail",       "std.test.fail",       "(msg: String) -> Void", native_fail),
        ]
    }
}
```

**Ключевой момент**: `T` в `assert_eq` / `assert_ne` требует поддержки generics. В текущем компиляторе уже имеется инфраструктура для runtime-диспетчеризации обобщённых функций (RFC-011). Если диспетчеризация generics ещё не завершена, первая версия может быть ограничена явными перегрузками для `Int` / `Float` / `String` / `Bool`, с последующим обновлением.

### 3. Подкоманда `yaoxiang test`

#### 3.1 Аргументы CLI

Добавление в перечисление `Commands`:

```rust
/// Run YaoXiang tests
Test {
    /// Source files or directories to test (default: all .yx files in src/ and tests/)
    #[arg(value_name = "PATH", num_args = 0..)]
    paths: Vec<PathBuf>,

    /// Filter test names (substring match)
    #[arg(short, long, value_name = "PATTERN")]
    filter: Option<String>,

    /// Run tests serially (disable parallel execution)
    #[arg(long)]
    serial: bool,

    /// Number of parallel workers (0 = auto)
    #[arg(long, default_value = "0")]
    workers: usize,

    /// Output JUnit XML report
    #[arg(long, value_name = "FILE")]
    junit: Option<PathBuf>,

    /// Stop on first failure
    #[arg(long)]
    fail_fast: bool,
}
```

#### 3.2 Процесс выполнения

```rust
match command {
    Commands::Test { paths, filter, serial, workers, junit, fail_fast } => {
        // 1. Обнаружение тестовых файлов
        let test_files = discover_test_files(&paths);

        // 2. Сканирование аннотаций @test, сбор тестовых функций
        let test_cases = scan_test_functions(&test_files, &filter);

        // 3. Компиляция каждого тестового файла (повторное использование compiler.compile)
        let compiled = compile_tests(&test_cases);

        // 4. Параллельное выполнение тестов (повторное использование runtime spawn)
        let results = execute_tests(&compiled, serial, workers);

        // 5. Генерация отчёта
        print_test_report(&results, junit);
    }
}
```

#### 3.3 Изоляция тестов

Каждая тестовая функция выполняется в изолированном контексте runtime:
- Изолированная куча (Heap) (списки/словари не загрязняются между тестами)
- Изолированный файл регистров
- Изолированный снимок FFI Registry (состояние стандартной библиотеки не загрязняется между тестами)

Способ реализации: при каждом `execute_function` создаётся новый `Frame` + `Heap`, повторно используя существующий механизм изоляции (см. `src/backends/interpreter/executor/tests/execute.rs`).

### 4. Изменения на уровне байт-кода

#### 4.1 Метаданные тестов

При сканировании аннотаций `@test` компилятор добавляет секцию метаданных тестов в заголовок сгенерированного файла байт-кода:

```
[Bytecode Header]
    ...
[Test Metadata Section]
    test_count: u16
    tests: [
        { name: str, file: str, line: u32, param_count: u8 }
    ]
```

#### 4.2 Изменения исполнителя (Executor)

Добавление точки входа для выполнения тестов в `Executor`:

```rust
impl Executor<'_> {
    /// Выполнение функции, помеченной как тест
    fn run_test(&mut self, test: &TestMeta) -> TestResult {
        let start = Instant::now();
        match self.execute_function(&self.func_by_name(&test.name), &[]) {
            Ok(RuntimeValue::Unit) => TestResult { name: test.name.clone(), passed: true, elapsed, error: None },
            Ok(_) => TestResult { name: test.name.clone(), passed: false, elapsed, error: Some("test returned non-Void".to_string()) },
            Err(e) if is_assertion_error(&e) => TestResult { name: test.name.clone(), passed: false, elapsed, error: Some(e.to_string()) },
            Err(e) => TestResult { name: test.name.clone(), passed: false, elapsed, error: Some(format!("unexpected: {}", e)) },
        }
    }
}
```

## Влияние на систему типов

**Отсутствует.** Фреймворк тестирования не вводит новых типов, ограничений типов или изменений в системе типов. Все функции утверждений возвращают `void`, параметры используют существующую инфраструктуру generics.

## Поведение во время выполнения

- Функции с аннотацией `@test` ведут себя неизменно под `yaoxiang run` — они остаются обычными функциями
- Обнаружение тестов и автоматический вызов срабатывают только при подкоманде `yaoxiang test`
- `TestAssertionFailed`, выбрасываемое при провале теста, разделяет общий конвейер обработки ошибок с обычными `ExecutorError`

## Изменения в компиляторе

| Модуль | Изменения |
|------|------|
| `src/frontend/core/parser/` | Повторное использование существующего разбора аннотаций (токен `@`), изменений не требуется |
| `src/middle/core/ir_gen.rs` | Сканирование аннотаций `@test`, маркировка узлов AST |
| `src/middle/passes/codegen/` | Запись секции метаданных тестов в заголовок байт-кода |
| `src/backends/interpreter/executor/` | Добавление точки входа `run_test` |
| `src/std/test.rs` | Реализация нового модуля `std.test` |
| `src/main.rs` | Добавление ветки подкоманды `Test` |

## Обратная совместимость

- ✅ **Полная обратная совместимость**: добавление подкоманды `yaoxiang test` не изменяет поведение ни одной из существующих подкоманд
- ✅ **Существующий код не затрагивается**: аннотация `@test` является опциональной, на незатронутые функции не оказывается никакого влияния
- ✅ **Регистрация модулей std изолирована**: `std.test` регистрируется как новый `StdModule`, не затрагивая существующие модули

## Компромиссы

### Преимущества

1. **Ноль нового синтаксиса**: полностью соответствует ограничению в 17 ключевых слов YaoXiang
2. **Использование существующих механизмов**: повторно используются аннотация `@`, trait `StdModule`, `NativeExport`, модель конкурентности spawn
3. **Соответствие опыту тестирования в Rust**: `#[test]` → `@test`, `assert_eq!` → `test.assert_eq()`
4. **Расширяемость**: в дальнейшем можно добавить аннотации `@benchmark`, `@ignore` и т.д. без изменения синтаксиса

### Недостатки

1. `assert_eq(a, b)` — это вызов функции, а не макрос — в отличие от Rust невозможно напечатать точные значения вроде `a = 42, b = 43` (требуется захват значений в нативной реализации)
2. Универсальные утверждения (`assert_eq<T>`) зависят от runtime-диспетчеризации generics; если эта возможность не завершена, первая версия требует специализации типов
3. Сканирование аннотаций выполняется на этапе компиляции, динамическая регистрация тестов невозможна

## Альтернативы

| Вариант | Описание | Преимущества | Недостатки |
|------|------|------|------|
| **A: Настоящее предложение (@test + модуль std.test)** | Аннотация + чистые функции | Ноль нового синтаксиса, использование существующих механизмов | Вызов функции, а не макрос; диагностика чуть слабее |
| **B: Синтаксис тестового блока `test { }`** | Введение нового ключевого слова `test` | Синтаксис лаконичен | ❌ Нарушает ограничение в 17 ключевых слов, требует серьёзной переработки парсера |
| **C: Соглашение об именовании (префикс `test_`)** | Чистое соглашение об именовании, сканирование функций с префиксом `test_` | Ноль изменений в аннотациях | Загрязнение пространства имён, лёгкие ложные срабатывания, отсутствие явной маркировки |
| **D: Внешний тестовый раннер** | Отдельный инструмент на Rust для компиляции и выполнения .yx тестов | Без изменений в компиляторе | Разделение архитектуры, два конвейера компиляции |

**Выбор A**: при соблюдении ограничения «ноль нового синтаксиса» аннотация является наиболее явным способом маркировки, одновременно минимизируя загрязнение пространства имён.

## Стратегия реализации

### Фаза 1: Инфраструктура (v0.7.8)

- Модуль `std.test`: `assert_eq` / `assert_ne` / `assert_ok` / `assert_err` / `fail`
- Начальная версия ограничена специализациями `Int` / `Float` / `String` / `Bool`
- Подтверждение разбора аннотаций (обеспечение корректной передачи `@` в AST на уровне парсера)

### Фаза 2: Обнаружение и выполнение тестов (v0.7.8)

- Сканирование аннотаций `@test` на уровне IR и маркировка
- Секция метаданных тестов в байт-коде
- Каркас подкоманды `yaoxiang test`
- Базовое выполнение тестов + вывод по умолчанию

### Фаза 3: Доработка (v0.7.9)

- `assert_true` / `assert_false`
- Параметры `--filter` / `--serial` / `--fail-fast`
- Вывод JUnit XML
- Изоляция тестов (независимый контекст Heap)
- Поддержка универсальных утверждений (если runtime-диспетчеризация generics завершена)

### Зависимости

| Зависимость | Состояние | Описание |
|------|------|------|
| Разбор аннотации `@` | ✅ Имеется | Лексер уже имеет `TokenKind::At`, парсер должен подтвердить передачу |
| Trait `StdModule` | ✅ Имеется | Полная реализация в `src/std/mod.rs` |
| `NativeExport` | ✅ Имеется | Механизм регистрации функций стандартной библиотеки |
| Runtime-диспетчеризация generics | ⚠️ Частично реализовано | Влияет на универсальную версию `assert_eq<T>`; в Фазе 1 можно обойти специализацией типов |
| CLI `yaoxiang` (clap) | ✅ Имеется | Перечисление `Commands` может быть напрямую расширено |
| Модель конкурентного выполнения | ⚠️ Черновик | RFC-024 принят, но находится в процессе реализации; в Фазе 2 может использоваться однопоточная реализация |

### Риски

1. **Неполный разбор аннотаций**: если обработка `@test` на уровне парсера неполна (распознаются только `@block`/`@eager`), потребуется расширение разбора аннотаций. **Смягчение**: по сути аннотация — это `@` + идентификатор, расширение до общего разбора аннотаций требует небольшого объёма работы
2. **Незрелость диспетчеризации generics**: `assert_eq<T>` требует поддержки generics во время выполнения. **Смягчение**: в Фазе 1 используются четыре явные функции `Int` / `Float` / `String` / `Bool`, не зависящие от диспетчеризации generics
3. **Недостаточная изоляция тестов**: если глобальное состояние модуля `std` загрязняется между тестами. **Смягчение**: при каждом выполнении теста создаётся новый `NativeContext` + `Heap`

## Открытые вопросы

- [ ] Поддерживает ли аннотация `@test` параметры (например, `@test(reason = "flaky")`)? В настоящий момент не поддерживается, остаётся простой
- [ ] Соглашение об именовании тестовых модулей? Рекомендуется следующее: имя тестового файла совпадает с именем исходного файла плюс суффикс `_test`, например `math.rs` → `math_test.yx`
- [ ] Поддерживать ли аннотацию `@ignore` для пропуска определённых тестов? В Фазе 1 не делается, в Фазе 3 может быть рассмотрено
- [ ] Формат диагностической информации утверждений? Необходимо определить способ отображения `actual` / `expected` (в настоящее время `RuntimeValue` уже поддерживает `format_value_with_prefix`)

## Приложение A: Связь с существующей инфраструктурой тестирования

| Пункт | Существующее | Настоящий RFC | Связь |
|------|------|--------|------|
| Rust `#[test]` | каталог `src/**/tests/` | Не затрагивается | Внутренние тесты компилятора продолжают использовать Rust |
| Интеграционные тесты YaoXiang `.yx` | `tests/yaoxiang/` | Не затрагивается | Существующие файлы регрессионных тестов .yx продолжают быть интеграционными тестами |
| `std.assert.assert(cond)` | Имеется | Не затрагивается | Сохраняется для использования в обычном коде |
| Ошибка `TestAssertionFailed` | Отсутствует | Добавляется | Новый тип ошибки, соответствующий спецификации кодов ошибок (RFC-013) |
