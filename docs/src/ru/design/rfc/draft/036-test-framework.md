# RFC-036: Тестовый фреймворк std.test и команда yaoxiang test

## Резюме

Введение в YaoXiang стандартного тестового фреймворка — модуля `std.test` и подкоманды CLI
`yaoxiang test`. Тестовые файлы представляют собой обычные файлы `.yx`, прохождение/провал
определяется через `std.assert.assert` и код выхода. Модуль `std.test` реализован на чистом YaoXiang
и является первой dogfooding-библиотекой. `yaoxiang test` — это инструмент CLI, а не функция
компилятора: никаких изменений в parser, IR, байт-коде или исполнителе не требуется.

## Мотивация

### Зачем нужен тестовый фреймворк?

В настоящее время тестовое покрытие YaoXiang зависит от Rust-овских `#[test]` и интеграционных
тестов в `tests/`. Это означает:

1. Модульные тесты стандартной библиотеки (std.math / std.list / std.dict / std.convert / std.io)
   невозможно писать на YaoXiang
2. Задача `#117 Покрытие модульными тестами модулей стандартной библиотеки` заблокирована из-за
   отсутствия доступной тестовой инфраструктуры
3. Регрессионные тесты языковых возможностей (например, изменение семантики spawn в RFC-032) лишены
   средств автоматизации

### Ключевые ограничения

- **Железное правило 17 ключевых слов**: никаких новых ключевых слов или синтаксических конструкций
- **Нулевые изменения компилятора**: не трогаем parser, IR, байт-код, исполнитель
- **Приоритет самобутстрапа**: тестовая библиотека пишется на YaoXiang — первая
  dogfooding-библиотека

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│                    yaoxiang test                              │
│                                                              │
│  Слой CLI:  yaoxiang test [--filter --fail-fast --json ...]   │
│              │                                               │
│  Слой обнаружения:  читает yaoxiang.toml → [tool.test]       │
│                     patterns                                  │
│              По умолчанию: tests/**/*.yx                      │
│              │                                               │
│  Слой выполнения:  для каждого файла: yaoxiang run <file>     │
│              Проверка кода выхода → последовательное          │
│              выполнение                                       │
│              │                                               │
│  Слой отчётов:   PASS/FAIL → сводка                          │
│              Поддержка --json / --verbose / --fail-fast       │
│                                                              │
│  Слой утверждений:  std.test (чистый YaoXiang, самобутстрап)  │
│              Основа: std.assert.assert                        │
│              Диагностика: f"Expected {expected}, got {actual}"│
└──────────────────────────────────────────────────────────────┘
```

### Основные принципы

1. **Тестовый фреймворк — не функция компилятора, а инструмент CLI** — `yaoxiang run` уже умеет
   «выполнять тесты», `yaoxiang test` лишь помогает запустить все файлы и показать отчёт
2. **Нулевые изменения компилятора** — не вводится сканирование аннотаций `@test`, сегменты
   метаданных в байт-коде, специальные точки входа в исполнителе
3. **Самобутстрап** — модуль `std.test` реализован на чистом YaoXiang, в основе лежит вызов
   `std.assert.assert`
4. **Тестовые файлы — обычные файлы `.yx`** — прохождение/провал определяется по коду выхода

## Детальное проектирование

### 1. Проектирование CLI

```
yaoxiang test [OPTIONS] [PATHS]

Arguments:
  [PATHS]...      Указанные тестовые файлы или каталоги (по умолчанию: читается
                  из yaoxiang.toml, иначе tests/)

Options:
  --filter <NAME>     Запускать только тесты, в имени файла которых содержится <NAME>
  --fail-fast         Остановиться при первом провале
  --verbose, -v       Показывать подробный stdout/stderr каждого теста
  --list              Только перечислить тестовые файлы, не запускать
  --no-progress       Не показывать индикатор прогресса (для CI)
  --json              Выводить результаты в формате JSON (для интеграции с CI)
```

#### Формат вывода

**Вывод по умолчанию**:

```
Running 5 tests from 3 files...

tests/math_test.yx ........................ PASS (0.002s)
tests/list_test.yx ........................ PASS (0.001s)
tests/string_test.yx ...................... FAIL (0.003s)
  `-- Expected "hello", got "world"
      at tests/string_test.yx:12:5

Results: 2 passed, 1 failed, 0 skipped (0.006s)
```

**Вывод в JSON** (`--json`):

```json
{
  "summary": { "total": 3, "passed": 2, "failed": 1, "skipped": 0, "time_secs": 0.006 },
  "tests": [
    { "file": "tests/math_test.yx", "passed": true, "time_secs": 0.002 },
    {
      "file": "tests/string_test.yx",
      "passed": false,
      "time_secs": 0.003,
      "error": "Expected \"hello\", got \"world\"",
      "exit_code": 1
    }
  ]
}
```

### 2. Конфигурация yaoxiang.toml

Располагается в секции `[tool.test]`, в соответствии с соглашением о сторонних расширениях
`[tool.*]` из RFC-015:

```toml
[project]
name = "my-project"

[tool.test]
patterns = ["tests/**/*.yx"]
# Возможные расширения в будущем:
# exclude = ["tests/fixtures/**"]
# parallel = true
```

- По умолчанию `patterns = ["tests/**/*.yx"]` — пользователь получает работающий инструмент без
  настройки
- В режиме одиночного файла (`yaoxiang test foo.yx`) файл запускается напрямую, конфигурация не
  читается
- В будущем возможно выделение в отдельный репозиторий (расположение `[tool.test]` остаётся)

### 3. Модуль std.test (чистый YaoXiang)

```yaoxiang
// std/test.yx — Тестовая библиотека утверждений на чистом YaoXiang
// Первая dogfooding-библиотека: тестовая библиотека YaoXiang написана на YaoXiang

use std.assert

assert_eq: (a: ?, b: ?) -> Void = (a, b) => {
    assert.assert(a == b, f"Expected {b}, got {a}")
}

assert_ne: (a: ?, b: ?) -> Void = (a, b) => {
    assert.assert(a != b, f"Expected not equal to {b}, got {a}")
}

assert_true: (cond: Bool) -> Void = (cond) => {
    assert.assert(cond, f"Expected true, got {cond}")
}

assert_false: (cond: Bool) -> Void = (cond) => {
    assert.assert(!cond, f"Expected false, got {cond}")
}
```

- 4 функции утверждений, все используют `f"..."` для формирования диагностических сообщений
- Параметр `?` (generics) в `assert_eq` / `assert_ne` зависит от системы generics
- `std.test` не зависит от какого-либо native-кода, реализован на чистом YaoXiang

### 4. Механизм загрузки стандартной библиотеки (ключевое проектное решение)

**Фаза 1: Встраивание в бинарник**

`std/test.yx` (а в будущем и все модули стандартной библиотеки, написанные на YaoXiang) встраивается
в бинарник во время сборки:

```rust
// build.rs или сборочный скрипт, генерируется автоматически
pub const STD_YX_FILES: &[(&str, &str)] = &[
    ("std/test.yx", r#"..."#),  // Исходный текст
    // В будущем больше
];
```

Когда загрузчик модулей разрешает `use std.test`:

1. Сначала ищется Rust native-модуль (существующий механизм, например `std.assert`)
2. Если не найдено — ищется во встроенных `STD_YX_FILES`, находится исходный код `std/test.yx`
3. Исходный код компилируется и регистрируется в системе модулей

Преимущества:

- В режиме одиночного файла `use std.test` тоже работает
- Версия стандартной библиотеки строго привязана к бинарнику — несоответствие версий невозможно
- Пользователю не нужно настраивать пути к стандартной библиотеке

**В будущем: стандартная библиотека в виде файлов на диске**

Когда в YaoXiang созреет режим проектов, стандартная библиотека будет переведена в файловую форму.
Подробности см. в обновлении к RFC-014.

### 5. Обнаружение и выполнение

**Этап обнаружения**:

1. Если указаны `[PATHS]`, используются они напрямую
2. Иначе читается `[tool.test].patterns` из `yaoxiang.toml`
3. Если конфигурации нет, по умолчанию `tests/**/*.yx`
4. Применяется фильтр `--filter` (по вхождению в имя файла)

**Этап выполнения**:

1. Для каждого файла: запускается дочерний процесс `yaoxiang run <file>`
2. Проверяется код выхода: 0 — PASS, ненулевой — FAIL
3. Перехватываются stdout/stderr для отчёта
4. Только последовательное выполнение (Фаза 1), в будущем поддержка `--parallel`
5. При `--fail-fast` останов происходит сразу после первого FAIL

### 6. Изоляция тестов

Изоляция тестов естественным образом обеспечивается границами на уровне процессов:

- Каждый тестовый файл выполняется в отдельном дочернем процессе
- Каждый дочерний процесс имеет собственные Heap, Frame, NativeContext
- Паника в одном тестовом файле не влияет на другие
- Не требуется дополнительных механизмов изоляции Heap

## Связь с существующими системами

| Элемент                                                        | Связь                                                           |
| -------------------------------------------------------------- | --------------------------------------------------------------- |
| Rust `#[test]`                                                 | Не затрагивается; внутренние тесты компилятора остаются на Rust |
| Существующие интеграционные тесты на `.yx` (`tests/yaoxiang/`) | Обнаруживаются и выполняются через `yaoxiang test`              |
| `std.assert.assert(cond)`                                      | Сохраняется; `std.test` опирается на неё снизу                  |
| Рефакторинг `#200` (`io.println` → `assert.assert`)            | Полностью совпадает по направлению с `yaoxiang test`            |
| Аннотации `@`                                                  | Не используются; `@test` не вводится                            |

## Стратегия реализации

### Фаза 1: Основная функциональность

Объём изменений:

- `src/main.rs` — добавление подкоманды `Test`
- `src/std/test.yx` — новый модуль на чистом YaoXiang
- `build.rs` — встраивание `std/*.yx` в бинарник
- Загрузчик модулей — поддержка загрузки модулей `.yx` из встроенного источника
- Разбор конфигурации RFC-015 — секция `[tool.test]`
- Выполнение через дочерние процессы + отчёт

Поставляемые артефакты:

- `yaoxiang test` базово работоспособен
- 4 функции утверждений в `std.test`
- Обнаружение `tests/**/*.yx` по умолчанию
- Последовательное выполнение + формат вывода по умолчанию

### Фаза 2: Доработка

- Параметры `--filter` / `--fail-fast` / `--verbose`
- Вывод `--json` (интеграция с CI)
- Опция `--list`
- Опция `--no-progress`

### Фаза 3: Продвинутые возможности

- Параллельное выполнение `--parallel` (зависит от зрелости модели concurrency в spawn)
- Конфигурация `[tool.test].exclude`
- Дополнительные функции утверждений (например, `assert_approx_eq` для Float)

## Риски и их снижение

| Риск                                                                     | Вероятность | Снижение                                                                              |
| ------------------------------------------------------------------------ | ----------- | ------------------------------------------------------------------------------------- |
| `f"..."` не сможет интерполировать обобщённые типы                       | Низкая      | Базовые типы уже проверены в `std.assert.assert`                                      |
| Накладные расходы на запуск дочерних процессов влияют на скорость тестов | Средняя     | На Фазе 1 — последовательное выполнение, приемлемо; Фаза 3 смягчает через параллелизм |
| Разбор конфигурации `yaoxiang.toml` отсутствует в текущем CLI            | Низкая      | Простое расширение, не затрагивает ядро функциональности                              |
| Обобщённый `?` недоступен в `std.test`                                   | Низкая      | Возможна деградация до типа `Any` или специализация типов                             |
| Встраивание исходников `.yx` в бинарник увеличивает его размер           | Низкая      | Исходники `.yx` крайне малы, влияние пренебрежимо                                     |
