# RFC-028：JIT-компилятор — многоуровневый движок выполнения в ВМ

> **Ссылки**:
>
> - [RFC-018：Проектирование LLVM AOT-компилятора](../accepted/018-llvm-aot-compiler.md)
> - [RFC-024：Модель параллелизма на основе спавн-блоков](../accepted/024-concurrency-model.md)
> - [RFC-008：Архитектура параллелизма Runtime и разделение планировщика](../accepted/008-runtime-concurrency-model.md)

## Аннотация

В данном документе предлагается интегрировать Cranelift JIT-компилятор в бэкенд VM YaoXiang, что позволит перевести VM от чистого интерпретатора к **многоуровневому движку выполнения**: холодный код выполняется интерпретатором, горячие функции компилируются Cranelift в нативный код. JIT-путь использует общие с LLVM AOT (RFC-018) IR-нормализационные проходы, Cranelift отвечает за быструю JIT-компиляцию, LLVM — за глубокую AOT-оптимизацию, каждый делает своё дело.

**Основная позиционирование: JIT обслуживает VM, а не заменяет её.**

## Мотивация

### Зачем нужен JIT?

Текущий бэкенд VM — чистый интерпретатор, скорость выполнения которого в 10-100 раз ниже нативного кода. При разработке часто запускаются тесты, скрипты, локальная отладка — в этих сценариях не нужна предельная AOT-оптимизация, но требуется заметно более высокая скорость выполнения по сравнению с интерпретатором.

### Почему не только LLVM AOT?

LLVM
AOT-компиляция занимает много времени (секунды), что не подходит для итеративной разработки. При разработке нужен опыт «изменил — сразу запустил»: изменил строку кода → перезапустил → почти мгновенно видишь результат. Cranelift
JIT компилирует одну функцию за 1-5 мс, пользователь не ощущает задержки компиляции.

### Почему Cranelift, а не LLVM ORC JIT?

| Измерение      | Cranelift JIT       | LLVM ORC JIT           |
| -------------- | ------------------- | ---------------------- |
| Скорость компиляции | 1-5 мс/функция      | 10-100 мс/функция     |
| Размер зависимостей | Малый               | Большой (нужен полный LLVM) |
| Качество кода  | 70-80% от LLVM -O2  | Очень высокое          |
| Подходящий сценарий | Разработка и отладка, быстрая итерация | Не подходит (см. компромиссы в документе) |

Cranelift быстро компилирует, качество кода достаточное. LLVM оставим для AOT глубокой офлайн-оптимизации. Один инструмент хорошо делает одну работу.

## Предложение

### Базовая архитектура

```
Движок выполнения VM
├── Слой интерпретатора
│   ├── Выполняет байткод-инструкции
│   ├── Собирает данные о популярности (счётчик вызовов + счётчик обратных переходов цикла)
│   └── При достижении порогового значения → отправляет задачу компиляции
│
├── Слой JIT-компиляции (Cranelift Backend)
│   ├── Очередь компиляции (фоновый поток, не блокирует интерпретатор)
│   ├── IR → нормализация → Cranelift IR → нативный код
│   └── Повторно использует IR-нормализационный проход из RFC-018 §4.0 (стек→SSA)
│
├── Кэш кода
│   ├── Таблица функций: ID функции → {вход интерпретатора, вход JIT (опционально)}
│   ├── Атомарная замена входов скомпилированных функций
│   └── Группировка по модулям (заготовка для горячей перезагрузки)
│
└── Анализ популярности
    ├── Счётчик вызовов на функцию + счётчик обратных переходов цикла
    ├── Периодическое затухание (чтобы избежать компиляции от разового разогрева)
    └── Три уровня популярности: Cold → Warm → Hot → Compiled
```

### Сопряжение с существующей архитектурой

```
Исходный код → Фронтенд (общий) → IR → ┬→ Генерация байткода → VM интерпретатор → [горячие функции] → Cranelift JIT
                                        │
                                        └→ LLVM AOT кодогенерация → .o → Линковка → exe (продакшен)
```

JIT и AOT совместно используют
**IR-нормализационный проход** (`middle/passes/ir_normalize.rs`), нижний кодогенератор заменён с LLVM на Cranelift.

### Процесс выполнения

```
Вызов функции
  → fn_entry.code_ptr.load()
  → ┬─ Stub интерпретатора (холодное состояние): построчная интерпретация байткода
    └─ JIT нативный код (горячее состояние): прямое выполнение машинного кода
  → Возврат
```

## Детальное проектирование

### 1. Структура каталогов

```
src/
├── backends/
│   ├── interpreter/              # существующий — интерпретатор VM
│   │   └── executor/
│   │       ├── engine.rs         # Изменения — точка входа теперь распределяет через FunctionEntry вместо прямой интерпретации
│   │       └── ...
│   │
│   ├── jit/                      # Новый — Слой JIT-компиляции
│   │   ├── mod.rs                # Вход модуля JIT, инициализация контекста Cranelift
│   │   ├── profiler.rs           # Счётчик популярности + затухание + пороговое решение
│   │   ├── entry.rs              # FunctionEntry + управление AtomicPtr
│   │   ├── cache.rs              # Кэш кода (управление исполняемыми страницами mmap)
│   │   ├── compiler.rs           # IR → Cranelift IR → нативный код
│   │   ├── types.rs              # Маппинг типов YaoXiang → Cranelift
│   │   └── abi.rs                # Соглашение о вызовах функций (System V / Microsoft x64)
│   │
│   ├── llvm/                     # В планах — LLVM AOT (RFC-018)
│   ├── common/                   # Существующий
│   └── runtime/                  # Существующий
│
└── middle/
    └── passes/
        └── ir_normalize.rs       # Новый — Общий IR-нормализатор (стек→SSA)
                                  #   Используется JIT и LLVM AOT совместно
```

**Ключевые ограничения**:

- `backends/jit/` зависит только от `middle/` (определения IR, нормализационные проходы), стандартной библиотеки и crates Cranelift
- `backends/jit/` не зависит от `backends/llvm/`, оба являются параллельными бэкендами
- `backends/jit/` не зависит от `backends/interpreter/`, взаимодействует через интерфейс `FunctionEntry`

### 2. Анализ популярности и многоуровневый триггер

#### 2.1 Автомат состояний популярности

```
Cold ──(вызовов > 50 или обратных переходов > 500)──→ Warm
Warm ──(вызовов > 200)────────────────────→ Hot
Hot ──(отправка в очередь компиляции, компиляция завершена)──────────────────→ Compiled
```

> Пороговые значения настраиваются, выше указаны значения по умолчанию. Ориентиры из LuaJIT, JVM C1, V8 Sparkplug (50-1000).

#### 2.2 Счётчики

Каждая функция в `FunctionEntry` (подробнее в §4.1) поддерживает два атомарных счётчика:

```rust
// Поля популярности FunctionEntry (полное определение в §4.1)
invocation_count: AtomicU32,   // Количество вызовов функции
backedge_count: AtomicU32,     // Количество обратных переходов цикла
state: AtomicU8,              // Cold | Warm | Hot | Compiled
```

#### 2.3 Механизм затухания

Каждые 5 секунд все счётчики сдвигаются вправо на 1 бит (умножаются на 0.5). Предотвращает бесполезную JIT-компиляцию кода, который часто вызывается только при запуске (например, инициализационный обход).

```rust
fn decay(entry: &FunctionEntry) {
    entry.invocation_count.fetch_update(Ordering::Relaxed, Ordering::Relaxed, |v| Some(v >> 1));
    entry.backedge_count.fetch_update(Ordering::Relaxed, Ordering::Relaxed, |v| Some(v >> 1));
}
```

Используются побитовые операции — нулевые накладные расходы на деление.

#### 2.4 Очередь компиляции

```
Поток интерпретатора                    Фоновый JIT-поток
    │                                        │
    ├─ Популярность достигла Hot              │
    ├─ Отправка запроса компиляции ─────────→  │
    │  (не блокирует интерпретатор)            ├─ Извлечение IR функции
    │                                        ├─ Нормализация IR (стек→SSA)
    │                                        ├─ Компиляция Cranelift
    │                                        ├─ Запись в кэш кода
    │                                        └─ Атомарное обновление указателя входа функции
    │  Следующий вызов этой функции ←─────────  │
    │  Напрямую выполняет нативный код          │
```

Во время компиляции функция продолжает выполняться через интерпретатор. После завершения компиляции при следующем вызове происходит атомарное переключение на JIT-код.

### 3. Конвейер компиляции IR → Cranelift

#### 3.1 Конвейер

```
YaoXiang IR (стековая форма)
  → IR-нормализационный проход (стек → регистры/SSA)    ← Повторное использование RFC-018 §4.0
  → Построение Cranelift IR
  → Оптимизации Cranelift + генерация машинного кода
  → Запись в кэш кода
```

#### 3.2 Маппинг типов YaoXiang → Cranelift

| Тип YaoXiang | Тип Cranelift          | Примечание                     |
| ------------- | ---------------------- | ------------------------------ |
| `Int`         | `i64`                  |                                |
| `Int32`       | `i32`                  |                                |
| `Float`       | `f64`                  |                                |
| `Float32`     | `f32`                  |                                |
| `Bool`        | `i8`                   | Cranelift не имеет `i1`, используется `i8` |
| `Char`        | `i32`                  | Unicode кодовая точка          |
| `String`      | `{ i64, i64 }`         | Указатель + длина              |
| `Void`        | Пустой кортеж          |                                |
| `&T`          | —                      | Нулевой размер, исчезает после компиляции |
| `&mut T`      | —                      | Нулевой размер, исчезает после компиляции |
| `ref T`       | `{ i64, i64 }`         | Указатель счётчика ссылок + указатель данных |
| `*T`          | `i64`                  | Голый указатель                |
| `List(T)`     | `{ i64, i64, i64 }`    | Указатель данных + длина + ёмкость |
| Структура     | Cranelift struct       |                                |
| Запись enum   | `{ i64, [max_payload] }` | Тег + union                   |
| `?T`          | `{ i8, T }`            | Флаг наличия значения + данные |

> Сравнение с таблицей типов LLVM из RFC-018 §3: Cranelift не различает типы указателей, нет `i1`, в целом проще.

#### 3.3 Трансляция ключевых инструкций

| Инструкция IR              | Cranelift IR                            |
| -------------------------- | --------------------------------------- |
| `Add { dst, lhs, rhs }`    | `iadd` (целое) / `fadd` (с плавающей точкой) |
| `Sub { dst, lhs, rhs }`    | `isub` / `fsub`                         |
| `Mul { dst, lhs, rhs }`    | `imul` / `fmul`                         |
| `Div { dst, lhs, rhs }`    | `sdiv` / `udiv` / `fdiv`                |
| `Eq { dst, lhs, rhs }`     | `icmp eq` / `fcmp eq`                   |
| `Jmp(label)`               | `jump`                                  |
| `JmpIf(cond, label)`       | `brnz`                                  |
| `Ret(Some(v))`             | `return`                                |
| `Call { dst, func, args }` | `call`                                  |
| `Load { dst, src }`        | `load`                                  |
| `Store { dst, src }`       | `store`                                 |
| `Spawn { ... }`            | Вызов runtime `task_spawn` + `task_wait_all` |

> Полная таблица перевода в основном тексте RFC. Ключевой принцип: набор инструкций Cranelift покрывает все операции YaoXiang IR, семантических пробелов нет.

#### 3.4 Сосуществование двух видов нормализации

VM-интерпретатору нужна стековая семантика (`Push`/`Pop`/`Dup`/`Swap`), Cranelift JIT и LLVM
AOT нужны регистры/SSA. IR-нормализационный проход выполняет одно преобразование (RFC-018
§4.0), JIT и AOT совместно используют его, не меняя само представление IR. Каждый бэкенд потребляет один и тот же IR согласно своим потребностям.

### 4. Таблица входов функций и атомарная замена

#### 4.1 FunctionEntry

```rust
struct FunctionEntry {
    /// 原子可替换的执行目标
    code_ptr: AtomicPtr<u8>,
    /// Неизменяемые метаданные
    bytecode: &'static [u8],        // Fallback интерпретатора
    ir: &'static FunctionIR,        // Входные данные для JIT-компиляции
    /// Статистика времени выполнения
    invocation_count: AtomicU32,
    backedge_count: AtomicU32,
    state: AtomicU8,                // Cold | Warm | Hot | Compiled
}
```

#### 4.2 Диспетчеризация входов

```
Вызывающий код
  → fn_entry.code_ptr.load(Ordering::Acquire)
  → ┬─ Адрес stub интерпретатора → Выполнение через интерпретатор, построчная интерпретация байткода
    └─ Адрес JIT-кода           → Прямой переход на нативный код
```

Одно разыменование указателя. Обработка косвенных переходов современными CPU-предикторами ветвлений: первое предсказание неверное, далее всё правильно. Накладные расходы ~1 такт.

#### 4.3 Атомарное переключение

После завершения компиляции — одна CAS-операция:

```rust
fn install_jit_code(entry: &FunctionEntry, jit_code: *mut u8) -> bool {
    entry.code_ptr.compare_exchange(
        INTERPRETER_STUB,      // Ожидание: всё ещё указывает на интерпретатор
        jit_code,              // Замена на: JIT-код
        Ordering::AcqRel,
        Ordering::Acquire,
    ).is_ok()
}
```

Без паузы интерпретатора, без ожидания точек безопасности, без обхода точек вызова. Один атомарный оператор завершает переключение.

### 5. Кэш кода

#### 5.1 Структура

```
CodeCache:
  modules:
    "main.yao":
      functions:
        "compute"    → FunctionEntry (state: Compiled)
        "process"    → FunctionEntry (state: Cold)
        "init"       → FunctionEntry (state: Compiled)
      native_pages:   [ Исполняемые страницы памяти, отображённые через mmap ]
    "lib.yao":
      functions:
        "helper"     → FunctionEntry (state: Compiled)
      native_pages:   [ Исполняемые страницы памяти, отображённые через mmap ]
```

#### 5.2 Управление исполняемой памятью

```rust
struct NativePage {
    ptr: *mut u8,
    size: usize,
    used: AtomicUsize,     // 已用字节数
    remaining: usize,       // 剩余容量
}

impl CodeCache {
    fn allocate(&self, code_size: usize) -> *mut u8;
    fn deallocate(&self, ptr: *mut u8, code_size: usize);  // Вызывается только при инвалидации модуля
}
```

Каждый модуль выделяет непрерывные исполняемые страницы mmap, все JIT-функции внутри модуля выделяются из одной страницы. При инвалидации модуля страница освобождается целиком, не нужно освобождать функцию за функцией.

### 6. Зарезервированные точки расширения для горячей перезагрузки

Следующие интерфейсы компилируются, но не вызываются до реализации горячей перезагрузки. Принцип проектирования интерфейсов: **при реализации JIT нужно только `insert` и `compare_exchange` для одной функции, модульные операции оставляются для горячей перезагрузки.**

```rust
/// Расширенный интерфейс кэша кода (зарезервирован, не реализован)
trait CodeCacheExt {
    /// Инвалидировать весь JIT-код модуля, вернуться к интерпретатору
    fn invalidate_module(&self, module_path: &str);

    /// Инвалидировать конкретные функции по диапазону исходных позиций
    fn invalidate_range(&self, file: &str, start: u32, end: u32);

    /// Атомарно заменить всю таблицу функций модуля
    fn swap_module(&self, module_path: &str, new_functions: HashMap<String, FunctionEntry>);
}

/// Расширенный интерфейс очереди компиляции (зарезервирован, не реализован)
trait CompileQueueExt {
    /// Приоритетная вставка в очередь (горячая перезагрузка компилируется с более высоким приоритетом, чем обычный JIT)
    fn submit_priority(&self, task: CompileTask);
}
```

**Почему группировка по модулям?**
JIT сам по себе требует только функции. Группировка по модулям полностью服务于 горячей перезагрузки: после перекомпиляции модуля можно атомарно заменить всю таблицу функций модуля, а не делать CAS функция за функцией — последнее при наличии циклических зависимостей между функциями приводит к несогласованному состоянию.

## Компромиссы

### Преимущества

1. **Неощутимая задержка компиляции**: Cranelift 1-5 мс/функция, компиляция в фоновом потоке, интерпретатор не приостанавливается
2. **Общая инфраструктура**: JIT и AOT совместно используют IR-нормализационный проход (RFC-018 §4.0), не создаём дублирующий код
3. **Без разрушений**: Полностью инкрементальная функциональность. VM не меняется, интерпретатор не меняется, просто добавляется более быстрый горячий путь
4. **Без зависимости от LLVM**: VM не подтягивает LLVM, остаётся лёгкой
5. **Естественная кроссплатформенность**: Cranelift нативно поддерживает x86_64 и ARM64, покрывает все целевые платформы
6. **Заготовка для горячей перезагрузки**: Кэш кода группируется по модулям + косвенные переходы через входы функций — структурная основа для будущей горячей перезагрузки

### Недостатки

1. **Новая зависимость Cranelift**: Вводится новый внешний crate, требуется изучение его API
2. **Сложность отладки**: Стековые фреймы кода, сгенерированного JIT, должны быть совместимы со стековыми фреймами интерпретатора, маппинг отладочной информации требует дополнительной обработки
3. **Задержка популярности при холодном старте**: В первые секунды после запуска программы JIT-ускорения нет, требуется накопление популярности
4. **Платформенный ABI**: mmap и соглашения о вызовах на разных платформах (Linux/macOS/Windows) требуют отдельной адаптации

### Согласованность со связанными RFC

| RFC                  | Согласованность                                               |
| -------------------- | ------------------------------------------------------------- |
| RFC-018 LLVM AOT     | ✅ Совместное использование IR-нормализационного прохода, JIT и AOT — параллельные бэкенды |
| RFC-024 спавн-блоки  | ✅ Спавн-блоки компилируются в вызовы runtime-функций         |
| RFC-008 архитектура Runtime | ✅ Все три уровня runtime (Embedded/Standard/Full) поддерживают JIT |

## Альтернативы

| Решение                   | Почему не выбрано                                            |
| ------------------------- | ------------------------------------------------------------- |
| Только LLVM AOT, без JIT  | При разработке требуется перекомпиляция всей программы, теряется быстрая итерация |
| LLVM ORC JIT              | Высокая задержка компиляции (10-100 мс), большая зависимость от LLVM, не подходит для встраивания в VM |
| Собственный лёгкий JIT (dynasm) | Высокая стоимость поддержки ручного написания бэкенда, Cranelift более зрелый |
| Шаблонный JIT            | Нулевая оптимизация, низкое качество кода, зря тратится время JIT-компиляции |
| Полнопрограммный JIT (без интерпретатора) | Медленный холодный старт, простые скрипты не стоят компиляции |
