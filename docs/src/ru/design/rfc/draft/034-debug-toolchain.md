# RFC-034: Унифицированный инструментарий отладки

## Резюме

Введение единого инструментария отладки для YaoXiang. Ключевая идея — **один источник, три
потребителя**: компилятор-фронтенд встраивает позиции исходного кода, имена переменных и информацию
о типах как полноправных граждан в YaoXiang IR, а три бэкенда — интерпретатор, JIT и LLVM — каждый
потребляют один и тот же набор метаданных. Пользователь запускает DAP (Debug Adapter Protocol)
сервер через `yaoxiang run --debug`, VS Code подключается по stdio и получает единый опыт работы с
точками останова, пошаговым выполнением, просмотром переменных, стеком вызовов, вычислением
выражений и отладкой конкурентности — независимо от того, какой движок исполнения используется под
капотом.

## Мотивация

### Зачем нужна эта функциональность?

Текущие средства диагностики ошибок в программах на YaoXiang крайне примитивны:

```yaoxiang
io.println("DEBUG: x = " + x.to_string())
io.println("DEBUG: entered branch A")
```

Три критические проблемы:

1. **Бутстрап компилятора затруднён**: компилятор YaoXiang пишется на самом YaoXiang, но разработчик
   компилятора не может отлаживать собственный код. Отсутствие интерактивных средств отладки на
   стадии бутстрапа — это тупик.
2. **Три движка, ноль отладки**: интерпретатор, JIT и LLVM работают каждый по-своему, и при
   возникновении проблемы пользователь может лишь проверить, появилось ли `ALL TESTS PASSED` в
   stdout. Утверждение упало? Неизвестно, на какой строке и каково значение переменной.
3. **Конкурентность — чёрный ящик**: `spawn` создаёт несколько задач — какая из них зависла? Кто
   переместил (`move`) переменную? Всё приходится угадывать наугад.

### Цели проектирования

- **Единый опыт**: точка останова, работающая в интерпретаторе, должна работать и в JIT, и в LLVM с
  согласованным отображением на исходный код. Пользователь не должен ощущать разницу между движками.
- **Один источник**: отладочные метаданные текут вместе с IR, не дублируются и не требуют двух
  наборов отображений.
- **Нулевое вмешательство**: один параметр `yaoxiang run --debug`; без него поведение компиляции и
  выполнения полностью не меняется.
- **Стандарт DAP**: прямое подключение к экосистеме VS Code, без изобретения собственного протокола
  редактора.

## Предложение

### Основная архитектура

Общий обзор архитектуры:

```
┌──────────────────────────────────────────────────────┐
│                    VS Code / редактор                  │
│              DAP Client (launch.json)                 │
└────────────────────────┬─────────────────────────────┘
                         │ stdio
┌────────────────────────▼─────────────────────────────┐
│              DAP-сервер (yx-core)                      │
│  ┌─────────┐  ┌──────────┐  ┌───────────────────┐    │
│  │ Управление│  │ Управление│  │ Движок вычисления │    │
│  │ сессиями │  │ точками   │  │ выражений         │    │
│  └─────────┘  └──────────┘  └───────────────────┘    │
└────────────────────────┬─────────────────────────────┘
                         │ запросы/управление
┌────────────────────────▼─────────────────────────────┐
│           Интерфейс отладки runtime (trait)            │
│  pause / resume / step / get_frames / eval / ...     │
└────┬──────────────────┬──────────────────┬──────────┘
     │                  │                  │
┌────▼────┐    ┌───────▼───────┐    ┌─────▼──────┐
│Интерпр. │    │ JIT (RFC-028)│    │ LLVM AOT   │
│прямое   │    │ генерация    │    │ метаданные │
│потребл. │    │ облегчённых  │    │ IR         │
│метаданн.│    │ таблиц отлад.│    │ → DWARF    │
│ IR      │    │              │    │            │
└─────────┘    └───────────────┘    └────────────┘
```

**Ключевые проектные решения**:

1. **DAP-сервер и runtime разделены через trait**. Серверу безразлично, что внизу — интерпретатор
   или JIT — он лишь отдаёт команды через trait `DebugEngine`. Каждый движок независимо реализует
   один и тот же trait.
2. **`yaoxiang run --debug` принудительно использует интерпретатор**. Отладка требует
   контролируемости, а не производительности. В режиме LLVM только генерируется DWARF для
   посмертного анализа (core dump / crash report), интерактивная отладка не выполняется.
3. **Повторное использование логики обнаружения точки входа из `yaoxiang run`**. Новая подкоманда не
   вводится — ментальная модель остаётся «запустить мою программу в режиме отладки».

### Отладочные метаданные в IR

К существующему YaoXiang IR добавляются метаданные без введения новых видов IR. Все метаданные
генерируются в **одном месте — фронтенде компилятора**, а бэкенды потребляют их только для чтения:

| Метаданные       | Точка прикрепления                    | Описание                                        |
| ---------------- | ------------------------------------- | ----------------------------------------------- |
| `SourceLocation` | каждый узел IR                        | исходный файл:строка:столбец                    |
| `VarName`        | узлы объявления/связывания переменной | имя переменной в исходном коде                  |
| `TypeAnnotation` | узлы переменных/выражений             | выведенный тип (включая предикаты compile-time) |
| `ScopeBoundary`  | вход/выход блока/функции              | жизненный цикл области видимости переменной     |
| `SpanInfo`       | узлы spawn                            | границы задач внутри spawn-блока                |

### Процесс запуска

```
yaoxiang run --debug file.yx
    │
    ├── Фаза 1: Компиляция (с отладочными метаданными)
    │   ├── Разбор → AST
    │   ├── Проверка типов + верификация предикатов compile-time
    │   └── Понижение до IR (с прикреплением отладочных метаданных)
    │
    ├── Фаза 2: Использование движка-интерпретатора
    │   └── В режиме --debug всегда используется интерпретатор, независимо от --release
    │
    ├── Фаза 3: Запуск DAP-сервера
    │   ├── Инициализация транспортного канала stdio
    │   ├── Ожидание подключения VS Code
    │   ├── После успешного attach — пауза на точке входа в программу
    │   └── Переход в интерактивный цикл отладки
    │
    └── Фаза 4: Завершение программы / сессии отладки → выход
```

### Различия между режимами

| Режим                    | Способ отладки                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------- |
| `yaoxiang run --debug`   | Принудительный интерпретатор, полнофункциональная интерактивная DAP-отладка            |
| `yaoxiang run --release` | Генерация DWARF для посмертного анализа (core dump / crash report), DAP не запускается |
| `yaoxiang run` (обычный) | Без отладочных метаданных, без поддержки отладки                                       |

## Детальное проектирование

### 1. Точки останова

```
Типы точек останова:
├── Точки останова на строке исходного кода  → фронтенд генерирует метаданные позиций, бэкенд сопоставляет их
├── Точки останова на входе в функцию        → срабатывают при вызове функции (Фаза 2)
├── Условные точки останова                  → срабатывают, когда выражение вычисляется в true
└── Точки останова по данным                 → срабатывают при изменении переменной (Фаза 2)
```

**Основная логика точек останова на строке исходного кода**:

```
VS Code отправляет: "Установить точку останова в file.yx:42"
    │
DAP-сервер:
    ├── Находит все узлы IR с SourceLocation == (file.yx, 42)
    ├── Передаёт runtime: "Пауза на этих адресах IR"
    └── Runtime возвращает: идентификатор точки останова

Выполнение программы доходит до узла IR → runtime проверяет: есть ли этот узел в списке точек останова?
    ├── Обычная точка останова → пауза, уведомление DAP-сервера
    └── Условная точка останова → вычисление условного выражения → пауза только при true
```

**Реализация в трёх движках**:

|                                    | Интерпретатор                                  | JIT                                          | LLVM                                                 |
| ---------------------------------- | ---------------------------------------------- | -------------------------------------------- | ---------------------------------------------------- |
| Способ вставки точек останова      | Проверка ID узла IR в цикле выполнения         | Вставка `int3` в машинный код в JIT          | Использование LLVM DWARF + аппаратные точки останова |
| Вычисление условной точки останова | Прямая интерпретация выражения                 | Временная JIT-компиляция условного выражения | Стек выражений DWARF + вычисление                    |
| Накладные расходы                  | Одна дополнительная проверка на каждый узел IR | Накладные расходы только в точках останова   | Почти нулевые (аппаратные точки останова)            |

### 2. Пошаговое выполнение

```
Step Over    → Выполнить текущую строку, пропустить тело вызываемой функции, остановиться на следующей строке
Step Into    → Войти внутрь вызываемой функции на текущей строке
Step Out     → Выполнять до возврата из текущей функции
Continue     → Возобновить выполнение до следующей точки останова или завершения программы
```

**Логика реализации**: по сути пошаговая операция — это **временная точка останова**. Она разделяет
единый механизм с явно установленными пользователем точками, а не образует две параллельные системы.

```
Step Over:
    Текущий номер строки исходного кода = query_line(frame)
    → Установить временную точку останова на следующей строке
    → Если текущая строка — вызов функции: установить временную точку останова после точки вызова
    → Continue → попадание во временную точку останова → удалить её → пауза

Step Into:
    Первая исполняемая позиция в цели вызова
    → Найти позицию исходного кода первого узла IR в теле функции
    → Установить временную точку останова → Continue → попадание → пауза

Step Out:
    Адрес возврата текущего кадра стека
    → Найти следующую строку вызывающего (caller)
    → Установить временную точку останова → Continue → попадание → пауза
```

**Обработка четырёх пограничных случаев временных точек останова**:

1. **Принадлежность к конкурентному контексту**: временная точка останова привязывается к
   идентификатору текущей задачи; попадания в неё от других задач просто игнорируются.
2. **Step Over над spawn-блоком**: Step Over за пределами `spawn` эквивалентен выполнению всего
   spawn-блока и переходу дальше. Для входа внутрь `spawn` для отладки следует использовать Step
   Into.
3. **Временная точка останова не сработала**: установить сторожевой таймаут (30 секунд без
   срабатывания) → принудительная пауза → уведомление VS Code. Параллельно слушать событие
   завершения программы → немедленная очистка.
4. **Несколько узлов IR на одной строке**: временная точка останова Step Over помечается флагом
   `ignore_current_line`; при попадании, если номер строки исходного кода равен текущему номеру
   строки → игнорировать и продолжить.

### 3. Просмотр переменных и областей видимости

```
VS Code запрашивает: "Список переменных текущего кадра"
    │
DAP-сервер:
    ├── Находит узел IR текущей точки паузы
    ├── Обходит все связывания переменных внутри текущего ScopeBoundary
    │   └── Каждое связывание возвращает: (имя, тип, ссылка на значение во время выполнения)
    └── Собирает VariablesResponse → VS Code
```

**Слои областей видимости**:

```
┌─ Globals ───────────────────────────┐
│  Связывания уровня модуля: константы, │
│  псевдонимы типов, глобальные        │
├─ Locals ────────────────────────────┤
│  Локальные переменные, видимые в     │
│  текущей функции                     │
│  ├── Параметры (аргументы функции)   │
│  └── Локальные связывания (let / присваивание)
├─ Captured ──────────────────────────┤
│  Внешние переменные, захваченные     │
│  spawn-блоком / замыканием           │
│  Отображение состояния владения:     │
│  перемещено (moved) / ref-разделяемо  │
└─────────────────────────────────────┘
```

**Различия между движками**:

| Движок        | Получение значений переменных                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Интерпретатор | Прямое чтение кадра стека и кучи VM. Каждое значение имеет явное представление в памяти                                          |
| JIT           | Значения в регистрах и на стеке → требуется построенная при JIT-компиляции таблица отображения «переменная → регистр/слот стека» |
| LLVM          | Секция `.debug_info` DWARF → `DW_AT_location` → нативная поддержка LLDB                                                          |

**Отображение специальных типов**: уточнение типов с помощью предикатов compile-time даёт полезную
для отладки информацию:

```
x: Positive(x)  →  Отображается как "Int (x > 0 = True)"
y: Sorted(y)    →  Отображается как "Array(Int) (гарантия сортировки)"
result: T       →  Отображается конкретный тип во время выполнения
```

### 4. Стек вызовов

```
DAP-запрос: StackTrace
    │
Возвращается:
┌──────────────────────────────────┐
│ #0  process_item()  file.yx:42  │  ← Текущая точка паузы
│     locals: item = "hello"      │
│     spawn ID задачи: task-3     │
├──────────────────────────────────┤
│ #1  main()          file.yx:67  │  ← вызывающий (caller)
│     locals: data = ["hello", ...]│
├──────────────────────────────────┤
│ #2  <entry>         file.yx:1   │  ← корень
└──────────────────────────────────┘
```

Каждый кадр записывает: сигнатуру функции, позицию вызова (исходный файл + номер строки), локальные
переменные (ленивое вычисление), контекст spawn (идентификатор задачи).

Интерпретатор и JIT поддерживают собственные списки кадров. Получение кадров не бесплатно — но режим
отладки не стремится к нулевым накладным расходам.

### 5. Вычисление выражений (Watch / REPL)

Пользователь вводит произвольное выражение YaoXiang в точке останова:

```
Watch: x + y         → Возвращает результат вычисления
Watch: items[2].name → Доступ к сложной структуре
Watch: f(x)          → Вызов функции (риск побочных эффектов)
```

**Стратегия вычисления**:

```
Пользователь вводит выражение
    │
    ├── Фронтенд компилятора разбирает выражение
    ├── Проверка типов в контексте текущего кадра
    ├── Значения переменных берутся из текущего кадра (read-only ссылки)
    ├── Выражение выполняется как отдельная микропрограмма
    │   └── Изменение внешних переменных запрещено
    │   └── spawn запрещён
    │   └── IO запрещено (или опционально разрешаемо)
    └── Возврат результирующего значения → исходное состояние кадра полностью неизменно
```

**Естественная «песочница» интерпретатора**: вычисление выражений не создаёт новую песочницу — сам
интерпретатор и есть песочница. Вычисление выражения лишь временно помещает кадр в стек и уничтожает
его после использования. Оно разделяет одну и ту же VM с обычным выполнением, но не фиксирует
никаких побочных эффектов.

**Вычисление вызовов функций**: по умолчанию разрешено, но пользователь предупреждается о том, что
«выражение может иметь побочные эффекты», и выполнение требует подтверждения.

**Различия между движками**:

| Движок        | Вычисление выражений                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| Интерпретатор | Повторное использование существующего пути кода eval, инъекция окружения текущего кадра                |
| JIT           | Временная компиляция выражения → линковка с текущим кадром → выполнение → отбрасывание временного кода |
| LLVM          | Не поддерживается — в режиме LLVM интерактивная отладка не выполняется                                 |

### 6. Отладка конкурентности

**Видимость модели задач**:

Понятие `threads` в DAP отображается на задачи `spawn` в YaoXiang. Каждая задача имеет собственный
список кадров стека и состояние выполнения.

```
┌─ Threads ───────────────────────────┐
│  ● task-1  main()     file.yx:10   │ ← текущая в фокусе
│  ▶ task-2  fetch()    file.yx:34   │ ← выполняется
│  ⏸ task-3  process()  file.yx:56   │ ← пауза на точке останова
│  ◼ task-4  write()    завершена    │
└─────────────────────────────────────┘
```

**Точки останова в контексте конкурентности**:

| Режим паузы               | Поведение                                              | Применимо для                               |
| ------------------------- | ------------------------------------------------------ | ------------------------------------------- |
| `stop-all` (по умолчанию) | Одна задача попала в останов → пауза всех задач        | Отладка гонок данных, глобального состояния |
| `stop-this-only`          | Пауза только для попавшей задачи, остальные продолжают | Отладка логики отдельной задачи             |

**Семантика пошагового выполнения для spawn-блоков**:

```
spawn {          // Step Over → выполнить весь spawn-блок
    task_a()     // Step Into → войти в task_a
    task_b()     // Выполняется параллельно, не затрагивается отдельным step
}
```

### 7. Отображение протокола DAP

#### Фаза 1: Базовые запросы

| DAP-запрос          | Семантика YaoXiang                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `initialize`        | Согласование возможностей: поддержка точек останова, пошагового выполнения, переменных, кадров стека |
| `launch` / `attach` | Запуск/присоединение к программе на YaoXiang (режим `--debug` идёт через attach)                     |
| `setBreakpoints`    | Установка точек останова на строках исходного кода                                                   |
| `configurationDone` | Точки останова готовы, начало выполнения                                                             |
| `threads`           | Возвращает список всех активных задач spawn                                                          |
| `stackTrace`        | Возвращает список кадров стека для указанной задачи                                                  |
| `scopes`            | Возвращает области видимости переменных текущего кадра                                               |
| `variables`         | Возвращает список переменных в указанной области видимости                                           |
| `continue`          | Возобновление выполнения                                                                             |
| `next`              | Step Over                                                                                            |
| `stepIn`            | Step Into                                                                                            |
| `stepOut`           | Step Out                                                                                             |
| `pause`             | Прерывание всех задач                                                                                |
| `evaluate`          | Вычисление выражения в текущем кадре                                                                 |
| `disconnect`        | Завершение сессии отладки                                                                            |

#### Фаза 2: Расширенные запросы

| DAP-запрос                | Семантика YaoXiang                                              |
| ------------------------- | --------------------------------------------------------------- |
| `setFunctionBreakpoints`  | Точки останова по имени функции                                 |
| `setExceptionBreakpoints` | Пауза при ошибке / panic                                        |
| `dataBreakpointInfo`      | Точки останова по данным (срабатывают при изменении переменной) |

## Стратегия реализации

### Фаза 0: Инфраструктура (предшествует всем остальным фазам)

**Цель**: фронтенд компилятора прикрепляет отладочные метаданные к IR.

| Компонент      | Изменения                                                                       |
| -------------- | ------------------------------------------------------------------------------- |
| Определение IR | Добавление полей метаданных `SourceLocation`, `VarName`, `TypeAnnotation` и др. |
| Parser         | Каждый узел AST записывает свою позицию в исходном коде                         |
| TypeChecker    | Информация о типах прикрепляется к узлам IR                                     |
| Тестирование   | Проверка того, что дамп IR содержит позиции и информацию о переменных           |

**Не затрагивает runtime.**

**Ход реализации (2026-09-17)**:

| Поставка                | Статус    | Форма реализации                                                                                                                                                                                                                      |
| ----------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Позиции в исходном коде | Выполнено | Все 76 вариантов `Instruction` несут поле `span`; метод `span()` намеренно не имеет wildcard-ветви, так что новый вариант без span приводит к ошибке компиляции. Покрытие позиций 40/41 инструкций                                    |
| Имена переменных        | Выполнено | `LocalSlot { name, ty, scope_depth }` подвешен к `FunctionBody::Code::locals`; `register_local` инкрементально фиксирует записи на этапе генерации. Отладочная секция `.42` v2 несёт имена, продукты v1 обратно совместимы при чтении |
| Информация о типах      | Частично  | Слот уже содержит `ty`; отдельные метаданные `TypeAnnotation` не реализованы                                                                                                                                                          |
| Видимость в дампе       | Выполнено | `dump` построчно выводит `; <file>:<line>:<col>` и перечисляет `locals: имя@слот`                                                                                                                                                     |

Форматы данных, закреплённые в таблице выше, напрямую стыкуются с Фазой 1: разрешение точек останова
DAP потребляет `debug_map`, панель переменных потребляет `local_names` (имена) и `locals` (типы).

### Фаза 1: Интерпретатор DAP MVP

**Цель**: `yaoxiang run --debug file.yx` позволяет устанавливать точки останова, выполнять код
пошагово и просматривать переменные.

| Компонент                         | Изменения                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| DAP-сервер (новый модуль yx-core) | Транспортный уровень stdio, обработка базовых запросов, менеджер точек останова (отображение строки исходного кода → узел IR)        |
| Trait отладки runtime (yx-core)   | Определение trait `DebugEngine` (pause, resume, step, get_frames, eval, get_variables)                                               |
| Интерпретатор                     | Проверка точек останова в цикле выполнения, механизм паузы/возобновления, ведение списка кадров, реализация `InterpreterDebugEngine` |
| CLI                               | Параметр `yaoxiang run --debug`                                                                                                      |

**Критерии приёмки**: для любого файла `.yx` из `tests/yaoxiang/` должна быть возможность через VS
Code устанавливать точки останова, выполнять Step Over и просматривать значения переменных.

### Фаза 2: Расширенные возможности отладки

**Цель**: вычисление выражений, точки останова на функциях, отладка конкурентности, точки останова
на исключениях.

| Компонент                              | Изменения                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Движок вычисления выражений            | Микрокомпиляция программы (повторное использование parser + typechecker), временный push кадра в VM, изоляция побочных эффектов |
| Отладка конкурентности                 | Отображение списка задач spawn, привязка точек останова к идентификатору задачи, стратегия паузы stop-all / stop-this-only      |
| Точки останова на функциях/исключениях | Отображение `setFunctionBreakpoints`, `setExceptionBreakpoints`                                                                 |
| Расширение VS Code                     | Предоставление шаблона `launch.json` по умолчанию                                                                               |

### Фаза 3: Отладка JIT и LLVM DWARF

**Цель**: движок JIT повторно использует DAP, LLVM выпускает DWARF для посмертного анализа.

| Компонент | Изменения                                                                                                                                                    |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| JIT       | Реализация trait `DebugEngine`, генерация при компиляции таблицы отображения «переменная → регистр», список кадров в runtime, временная компиляция выражений |
| LLVM      | Отладочные метаданные IR → LLVM `DILocation` / `DISubprogram` → DWARF (без интерактивного DAP)                                                               |

### Зависимости между фазами

```
Фаза 0 (метаданные в IR)
    ↓
Фаза 1 (MVP DAP для интерпретатора)  ← начиная с этого момента уже можно пользоваться
    ↓
Фаза 2 (расширенные возможности)
    ↓
Фаза 3 (JIT + LLVM DWARF)
```

### Риски

| Риск                                                                    | Смягчение                                                                                                                          |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Сложность механизма паузы в интерпретаторе                              | Использование простых channel/signal вместо сложного конечного автомата; пауза — это просто запрет на выборку следующей инструкции |
| Типобезопасность вычисления выражений                                   | Повторное использование существующего typechecker, read-only ссылки, без фиксации побочных эффектов                                |
| Тонкости протокола DAP                                                  | Следовать реализациям debugpy / delve, протокол хорошо обкатан                                                                     |
| Активационная блокировка (livelock) stop-all при отладке конкурентности | Механизм таймаута + принудительная пауза                                                                                           |

## Компромиссы

### Преимущества

- **Один источник**: отладочные метаданные генерируются один раз, используются тремя движками. Не
  возникнет ситуации «в интерпретаторе отладочная информация корректна, а в LLVM — нет»
- **Нулевое вмешательство**: один параметр `--debug`, без него поведение полностью неизменно
- **Стандарт DAP**: прямое подключение к экосистеме VS Code, не требуется собственный протокол
  редактора или интерфейс отладчика
- **Интерпретатор в приоритете**: отладка естественно ложится на интерпретатор — гибкость,
  контролируемость, простота вычисления выражений. Отсутствие интерактивной отладки в режиме LLVM —
  наиболее прагматичный выбор

### Недостатки

- **Низкая производительность в режиме отладки**: интерпретатор значительно медленнее JIT/LLVM. Но
  отладка не требует производительности — никто не ожидает запуска production-нагрузки в
  debug-режиме
- **Ограниченная отладка в LLVM**: AOT-компиляция не допускает интерактивной отладки, доступен
  только GDB/LLDB + DWARF. Но это компромисс: в режиме LLVM не должно быть расхождений в поведении
  отладки
- **Сложность паузы при конкурентности**: реализация семантики stop-all в интерпретаторе требует
  обхода всех активных задач

### Альтернативные варианты

| Вариант                                  | Почему отвергнут                                                                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Три движка с собственной реализацией DAP | Тройной объём работы, тройной набор багов. Нарушает «хороший вкус»                                                                 |
| Только DWARF, без собственного DAP       | В интерпретаторе и JIT нет понятия DWARF, LLDB не проникнет внутрь VM                                                              |
| Командный отладчик на манер Python pdb   | Опыт VS Code на порядок превосходит командный отладчик                                                                             |
| Размещение DAP внутри процесса LSP       | Жизненные циклы принципиально различны: LSP следует за проектом, DAP — за сессией отладки. Изоляция процессов — жёсткое требование |
