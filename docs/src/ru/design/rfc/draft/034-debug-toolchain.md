# RFC-034: Единая отладочная инструментальная цепочка

## Краткое описание

Введение единой отладочной инструментальной цепочки для YaoXiang. Ключевая идея — **один источник, три потребителя**: компиляторный фронтенд встраивает информацию о расположении исходного кода, имена переменных и сведения о типах как объекты первого класса в YaoXiang IR, а три бэкенда — интерпретатор, JIT и LLVM — все потребляют один и тот же набор метаданных. Пользователь запускает DAP-сервер (Debug Adapter Protocol) с помощью `yaoxiang run --debug`, VS Code подключается через stdio и получает единообразный опыт отладки с точками останова, пошаговым выполнением, просмотром переменных, стеком вызовов, вычислением выражений и отладкой параллельных процессов — независимо от того, какой движок выполнения работает под капотом.

## Мотивация

### Зачем нужна эта функция?

Текущие средства поиска ошибок в YaoXiang-программах крайне примитивны:

```yaoxiang
io.println("DEBUG: x = " + x.to_string())
io.println("DEBUG: entered branch A")
```

Три критических проблемы:

1. **Самостоятельная разработка компилятора заблокирована**: YaoXiang используется для написания компилятора YaoXiang, но те, кто пишет компилятор, не могут отлаживать свой собственный код. Отсутствие интерактивных средств отладки на этапе самокомпиляции — это тупик.
2. **Три движка, ноль отладки**: Интерпретатор, JIT и LLVM работают независимо друг от друга; когда что-то идёт не так, пользователь может лишь проверить, появилась ли строка `ALL TESTS PASSED` в stdout. Ошибка утверждения? Непонятно, в какой строке, какие значения переменных.
3. **Параллелизм — чёрный ящик**: `spawn` создаёт несколько задач; какая задача завершилась с ошибкой? Какая переменная была перемещена (move)? Всё сводится к угадыванию.

### Цели проектирования

- **Единообразный опыт**: Точка останова, которая работает в интерпретаторе, работает и в JIT, и в LLVM с согласованным отображением исходного кода. Пользователь не должен замечать различий в底层 engine.
- **Один источник**: Отладочные метаданные перемещаются вместе с IR, без дублирования определений и без поддержки двух наборов маппингов.
- **Нулевое влияние**: Один параметр `yaoxiang run --debug`; без этого параметра компиляция и выполнение полностью идентичны.
- **Стандарт DAP**: Прямое подключение к экосистеме VS Code без изобретения нового редакторного протокола.

## Предложение

### Основное проектирование

Общая архитектура:

```
┌──────────────────────────────────────────────────────┐
│                    VS Code / Редактор                │
│              DAP-клиент (launch.json)                │
└────────────────────────┬─────────────────────────────┘
                         │ stdio
┌────────────────────────▼─────────────────────────────┐
│                 DAP-сервер (yx-core)                 │
│  ┌─────────┐  ┌──────────┐  ┌───────────────────┐    │
│  │ Управление│  │Управление │  │ Движок вычисления  │    │
│  │сессиями │  │точками   │  │  выражений        │    │
│  └─────────┘  └──────────┘  └───────────────────┘    │
└────────────────────────┬─────────────────────────────┘
                         │ Запросы/управление
┌────────────────────────▼─────────────────────────────┐
│            Отладочный интерфейс runtime (trait)      │
│  pause / resume / step / get_frames / eval / ...     │
└────┬──────────────────┬──────────────────┬──────────┘
     │                  │                  │
┌────▼────┐    ┌───────▼───────┐    ┌─────▼──────┐
│Интерпре-│    │ JIT (RFC-028) │    │ LLVM AOT   │
│татор    │    │ Генерирует    │    │ Метаданные │
│Прямое   │    │ лёгкие        │    │ IR → DWARF│
│потребле-│    │ отладочные    │    │            │
│ние IR   │    │ таблицы       │    │            │
└─────────┘    └───────────────┘    └────────────┘
```

**Ключевые проектные решения**:

1. **DAP-сервер и runtime разделены через trait**. Серверу безразлично, что underneath — интерпретатор или JIT. Он отдаёт команды только через trait `DebugEngine`. Каждый движок независимо реализует один и тот же trait.
2. **`yaoxiang run --debug` принудительно использует интерпретатор**. Для отладки нужна управляемость, а не производительность. В режиме LLVM только генерируется DWARF для посмертной отладки (core dump / crash report), интерактивная отладка не выполняется.
3. **Повторное использование логики обнаружения точек входа из `yaoxiang run`**. Новых подкоманд не вводится; ментальная модель — "запустить мою программу в режиме отладки".

### Отладочные метаданные IR

Метаданные добавляются к существующему YaoXiang IR без создания новых видов IR. Все метаданные генерируются **в одном месте — компиляторном фронтенде**, бэкенды потребляют их только для чтения:

| Метаданные           | Точка прикрепления       | Описание                           |
| -------------------- | ------------------------ | ---------------------------------- |
| `SourceLocation`     | Каждый IR-узел           | Файл:строка:столбец               |
| `VarName`            | Узлы объявления/связыв. | Имя переменной в исходном коде     |
| `TypeAnnotation`     | Узлы переменных/выражений| Выведенный тип (с compile-time предикатами) |
| `ScopeBoundary`      | Входы/выходы блоков/функц.| Жизненный цикл области видимости   |
| `SpanInfo`           | Узлы spawn              | Границы задач внутри spawn-блока   |

### Процесс запуска

```
yaoxiang run --debug file.yx
    │
    ├── Фаза 1: Компиляция (с отладочными метаданными)
    │   ├── Парсинг → AST
    │   ├── Проверка типов + валидация compile-time предикатов
    │   └── Понижение до IR (с附加 отладочными метаданными)
    │
    ├── Фаза 2: Использование интерпретаторного движка
    │   └── В режиме --debug всегда используется интерпретатор, независимо от --release
    │
    ├── Фаза 3: Запуск DAP-сервера
    │   ├── Инициализация stdio-транспорта
    │   ├── Ожидание attach от VS Code
    │   ├── После attach — пауза на точке входа программы
    │   └── Переход в интерактивный цикл отладки
    │
    └── Фаза 4: Завершение программы / завершение сессии отладки → Выход
```

### Различия режимов

| Режим                    | Способ отладки                                                      |
| ------------------------ | ------------------------------------------------------------------- |
| `yaoxiang run --debug`   | Принудительный интерпретатор, полнофункциональная интерактивная DAP-отладка |
| `yaoxiang run --release` | Генерация DWARF для посмертной отладки (core dump / crash report), DAP не запускается |
| `yaoxiang run` (обычный) | Без отладочных метаданных, без поддержки отладки                     |

## Детальное проектирование

### 1. Точки останова

```
Типы точек останова:
├── Точка останова на строке исходника → Компиляторный фронтенд генерирует метаданные позиций, бэкенд запрашивает и сопоставляет
├── Точка останова на входе в функцию  → Срабатывает при вызове функции (вторая фаза)
├── Условная точка останова            → Срабатывает, когда выражение вычисляется в true
└── Точка останова на данных            → Срабатывает при изменении переменной (вторая фаза)
```

**Основная логика точек останова на строке**:

```
VS Code отправляет: "Установить точку останова на file.yx:42"
    │
DAP-сервер:
    ├── Запросить из IR все узлы с SourceLocation == (file.yx, 42)
    ├── Переслать runtime: "Приостановить на этих IR-адресах"
    └── Runtime возвращает: ID точки останова

Программа выполняется до IR-узла → Runtime проверяет: этот узел в списке точек останова?
    ├── Обычная точка останова → Приостановить, уведомить DAP-сервер
    └── Условная точка останова → Вычислить условное выражение → только если true — приостановить
```

**Реализация для трёх движков**:

|                  | Интерпретатор               | JIT                          | LLVM                            |
| ---------------- | ---------------------------- | ---------------------------- | ------------------------------- |
| Метод вставки    | Проверка ID IR-узла в цикле выполнения | JIT вставляет `int3` в машинный код | Использование LLVM DWARF + аппаратные точки останова |
| Вычисление услов.точки | Прямое интерпретирование выражения | Временная JIT-компиляция условного выражения | DWARF-стек выражений + вычисление |
| Накладные расходы | Дополнительная проверка таблицы на каждом IR-узле | Только на точках останова | Почти нулевые (аппаратные точки) |

### 2. Пошаговое выполнение

```
Step Over    → Выполнить текущую строку, пропустить внутренности вызова функции, остановиться на следующей строке
Step Into    → Войти внутрь вызова функции текущей строки
Step Out     → Выполнить до возврата из текущей функции
Continue     → Возобновить выполнение до следующей точки останова или конца программы
```

**Логика реализации**: Пошаговые операции по сути являются **временными точками останова**. Они используют тот же механизм, что и явно заданные пользователем точки останова, — не две отдельные системы, а две формы использования одной системы.

```
Step Over:
    Текущий номер строки = query_line(frame)
    → Установить временную точку останова на следующей строке
    → Если текущая строка содержит вызов функции: установить временную точку останова после точки вызова
    → Continue → Попадание во временную точку → Удалить → Пауза

Step Into:
    Первая исполняемая позиция текущей цели вызова
    → Найти исходную позицию первого IR-узла тела функции
    → Установить временную точку останова → Continue → Попадание → Пауза

Step Out:
    Адрес возврата текущего стекового кадра
    → Найти следующую строку caller'а
    → Установить временную точку останова → Continue → Попадание → Пауза
```

**Обработка четырёх граничных случаев временных точек останова**:

1. **Принадлежность к并发**: Временная точка останова привязана к ID текущей задачи; попадание другими задачами игнорируется.
2. **Step Over spawn-блока**: Снаружи spawn-блока Step Over эквивалентен выполнению всего spawn-блока и переходу к следующему после него. Для отладки внутри spawn следует использовать Step Into.
3. **Промах временной точки останова**: Установка сторожевого таймера (30 секунд без попадания в любую точку останова) → принудительная пауза → уведомление VS Code. Одновременно прослушивание события завершения программы → немедленная очистка.
4. **Несколько IR-узлов на одной строке**: Временная точка останова Step Over помечается флагом `ignore_current_line`; при попадании, если номер исходной строки равен текущему → игнорировать, продолжить.

### 3. Просмотр переменных и областей видимости

```
VS Code запрашивает: "Список переменных текущего кадра"
    │
DAP-сервер:
    ├── Запросить IR-узел текущей точки паузы
    ├── Обойти все bindings переменных внутри текущего ScopeBoundary
    │   └── Для каждого binding вернуть: (имя, тип, ссылка на значение в runtime)
    └── Собрать VariablesResponse → VS Code
```

**Уровни области видимости**:

```
┌─ Globals ───────────────────────────┐
│  Модульные bindings: константы, псевдонимы типов, глобалы │
├─ Locals ────────────────────────────┤
│  Локальные переменные, видимые в текущей функции         │
│  ├── Параметры (аргументы функции) │
│  └── Локальные bindings (let / присваивание)             │
├─ Captured ──────────────────────────┤
│  Внешние переменные, захваченные spawn-блоком / замыканием │
│  Показывать статус владения: move выполнен / ref разделяемый │
└─────────────────────────────────────┘
```

**Различия движков**:

| Движок | Получение значений переменных                                               |
| ------ | ---------------------------------------------------------------------------- |
| Интерпретатор | Прямое чтение стековых кадров и кучи VM. Каждое значение имеет чёткое представление в памяти |
| JIT    | Значения в регистрах и на стеке → 需要 JIT-компилятор записывал "переменная → регистр/стековый слот" маппинг-таблицу |
| LLVM   | Секция `.debug_info` DWARF → `DW_AT_location` → нативная поддержка LLDB    |

**Отображение специальных типов**: Уточнение типов через compile-time предикаты предоставляет ценную отладочную информацию:

```
x: Positive(x)  →  Показывать "Int (x > 0 = True)"
y: Sorted(y)    →  Показывать "Array(Int) (гарантия сортировки)"
result: T       →  Показывать конкретный тип в runtime
```

### 4. Стек вызовов

```
Запрос DAP: StackTrace
    │
Ответ:
┌──────────────────────────────────┐
│ #0  process_item()  file.yx:42  │  ← Текущая точка паузы
│     locals: item = "hello"       │
│     spawn ID задачи: task-3      │
├──────────────────────────────────┤
│ #1  main()          file.yx:67  │  ← caller
│     locals: data = ["hello", ...]│
├──────────────────────────────────┤
│ #2  <entry>         file.yx:1   │  ← корень
└──────────────────────────────────┘
```

Каждый кадр содержит: сигнатуру функции, позицию вызова (файл+строка), локальные переменные (lazy evaluation), контекст spawn (ID задачи).

Интерпретатор и JIT各自 поддерживают список кадров. Получение кадров не является бесплатным — но в режиме отладки это не критично.

### 5. Вычисление выражений (Watch / REPL)

Пользователь вводит произвольное YaoXiang-выражение в точке останова:

```
Watch: x + y         → Возвращает результат вычисления
Watch: items[2].name → Доступ к сложной структуре
Watch: f(x)          → Вызов функции (риск побочных эффектов)
```

**Стратегия вычисления**:

```
Пользовательский ввод выражения
    │
├── Парсинг выражения компиляторным фронтендом
├── Проверка типов в контексте текущего кадра
├── Значения переменных берутся из текущего кадра (только для чтения)
├── Выражение выполняется как независимая микропрограмма
│   └── Изменение внешних переменных запрещено
│   └── spawn запрещён
│   └── IO запрещён (или опционально разрешён)
└── Возврат результата → Исходное состояние кадра полностью сохранено
```

**Интерпретатор естественно изолирован**: Вычисление выражений — это не создание новой песочницы. Интерпретатор сам является песочницей. Вычисление выражений — это просто временный push кадра, который уничтожается после использования. Выполнение разделяет тот же VM, но не фиксирует побочные эффекты.

**Вычисление вызовов функций**: По умолчанию разрешено, но с предупреждением пользователю "это выражение может иметь побочные эффекты", требующим подтверждения.

**Различия движков**:

| Движок | Вычисление выражений                                         |
| ------ | ------------------------------------------------------------ |
| Интерпретатор | Повторное использование существующего eval-кода с инъекцией контекста текущего кадра |
| JIT    | Временная компиляция выражения → линковка к текущему кадру → выполнение → отмена временного кода |
| LLVM   | Не поддерживается — в режиме LLVM нет интерактивной отладки  |

### 6. Отладка конкурентности

**Видимость модели задач**:

Концепция DAP `threads` отображается на задачи `spawn` в YaoXiang. Каждая задача имеет собственный список стековых кадров и состояние выполнения.

```
┌─ Threads ───────────────────────────┐
│  ● task-1  main()     file.yx:10   │ ← Текущий фокус
│  ▶ task-2  fetch()    file.yx:34   │ ← Выполняется
│  ⏸ task-3  process()  file.yx:56   │ ← Пауза на точке останова
│  ◼ task-4  write()    завершено     │
└─────────────────────────────────────┘
```

**Точки останова в контексте конкурентности**:

| Режим паузы           | Поведение                             | Сценарий использования               |
| --------------------- | ------------------------------------- | ------------------------------------- |
| `stop-all` (по умолч.)| Одна задача попала → все задачи останавливаются | Отладка гонки данных, глобального состояния |
| `stop-this-only`      | Пауза только попавшей задачи, остальные продолжают | Отладка логики независимых задач      |

**Семантика Step Inside spawn-блока**:

```
spawn {          // Step Over → выполняет весь spawn-блок
    task_a()     // Step Into → вход в task_a
    task_b()     // Параллельное выполнение, не зависит от отдельного step
}
```

### 7. Маппинг протокола DAP

#### Первая фаза: Основные запросы

| DAP-запрос           | Семантика YaoXiang                                           |
| -------------------- | ------------------------------------------------------------ |
| `initialize`         | Согласование возможностей: точки останова, пошаговое выполнение, переменные, кадры |
| `launch` / `attach`  | Запуск/присоединение к YaoXiang-программе (`--debug` через режим attach) |
| `setBreakpoints`     | Установка точек останова на строках исходника                |
| `configurationDone`  | Точки останова готовы, начало выполнения                     |
| `threads`            | Возврат списка всех активных spawn-задач                     |
| `stackTrace`         | Возврат списка стековых кадров указанной задачи              |
| `scopes`             | Возврат областей видимости переменных текущего кадра         |
| `variables`          | Возврат списка переменных указанной области видимости        |
| `continue`           | Возобновление выполнения                                     |
| `next`               | Step Over                                                    |
| `stepIn`             | Step Into                                                    |
| `stepOut`            | Step Out                                                     |
| `pause`              | Прерывание всех задач                                        |
| `evaluate`           | Вычисление выражения в текущем кадре                        |
| `disconnect`         | Завершение сессии отладки                                    |

#### Вторая фаза: Расширенные запросы

| DAP-запрос                 | Семантика YaoXiang                |
| -------------------------- | --------------------------------- |
| `setFunctionBreakpoints`   | Точки останова по имени функции   |
| `setExceptionBreakpoints`  | Пауза при ошибке/panic            |
| `dataBreakpointInfo`       | Точки останова на данных (триггер изменения переменной) |

## Стратегия реализации

### Фаза ноль: Инфраструктура (предшествует всем фазам)

**Цель**: Компиляторный фронтенд附加 отладочные метаданные к IR.

| Компонент    | Изменения                                                             |
| ------------ | --------------------------------------------------------------------- |
| Определение IR | Новые поля метаданных: `SourceLocation`, `VarName`, `TypeAnnotation` |
| Parser       | Каждый AST-узел записывает исходную позицию                          |
| TypeChecker  | Информация о типах прикрепляется к IR-узлам                          |
| Тестирование | Верификация включения позиций и информации о переменных в IR dump    |

**Runtime не затрагивается.**

**Статус реализации (2026-09-17)**:

| Deliverable | Статус | Форма реализации |
| --- | --- | --- |
| Исходная позиция | Выполнено | Все 76 вариантов `Instruction` содержат поле `span`; метод `span()` намеренно не имеет catch-all, добавление нового варианта без span приводит к ошибке компиляции. Покрытие позиций: 40/41 инструкций |
| Имена переменных | Выполнено | `LocalSlot { name, ty, scope_depth }` в `FunctionBody::Code::locals`; `register_local` записывает на этапе генерации. Секция `.42` v2 содержит имена, v1-артефакты обратно совместимы при чтении |
| Имена глобальных слотов | Выполнено | Секция `.42` v3 содержит таблицу «номер слота → имя топа level binding». Top-level binding идёт через `Operand::Global`, не в локальной таблице функции; без этой таблицы можно показать только число, но не имя переменной. v1/v2 артефакты читают пустую таблицу |
| Информация о типах | Частично | Слоты содержат `ty`; отдельные метаданные `TypeAnnotation` ещё не реализованы |
| Видимость в dump | Выполнено | `dump` выводит для каждой инструкции `; <file>:<line>:<col>`, плюс `locals: имя@слот` |

Данные из таблицы выше непосредственно совместимы с фазой один: DAP-парсинг точек останова потребляет `debug_map`, панель переменных потребляет `local_names` (имена) и `locals` (типы).

### Первая фаза: Интерпретаторный DAP MVP

**Цель**: `yaoxiang run --debug file.yx` позволяет устанавливать точки останова, пошаговое выполнение, просмотр переменных.

| Компонент                       | Изменения                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| DAP-сервер (новый модуль yx-core) | Уровень stdio-транспорта, обработка основных запросов, менеджер точек останова (исходная строка → IR-узел) |
| Runtime debug trait (yx-core)   | Определение trait `DebugEngine` (pause, resume, step, get_frames, eval, get_variables) |
| Интерпретатор                   | Проверка точек останова в цикле выполнения, механизм паузы/возобновления, поддержка списка кадров, реализация `InterpreterDebugEngine` |
| CLI                             | Параметр `yaoxiang run --debug`                                                    |

**Критерии приёмки**: Для любого файла `.yx` в `tests/yaoxiang/` возможность установить точку останова в VS Code, Step Over и просмотреть значения переменных.

### Вторая фаза: Продвинутые возможности отладки

**Цель**: Вычисление выражений, точки останова на функциях, отладка параллелизма, точки останова на исключениях.

| Компонент           | Изменения                                                                  |
| ------------------- | --------------------------------------------------------------------------- |
| Движок вычисления выражений | Компиляция микропрограмм (повторное использование parser + typechecker), временный push кадра в VM, изоляция побочных эффектов |
| Отладка параллелизма | Маппинг списка spawn-задач, привязка ID задачи к точкам останова, стратегии паузы stop-all / stop-this-only |
| Точки останова на функциях/исключениях | Маппинг `setFunctionBreakpoints`, `setExceptionBreakpoints` |
| VS Code расширение  | Предоставление шаблона `launch.json` по умолчанию                          |

### Третья фаза: JIT-отладка и LLVM DWARF

**Цель**: JIT-движок использует DAP, LLVM генерирует DWARF для崩溃回溯.

| Компонент | Изменения                                                                      |
| --------- | ------------------------------------------------------------------------------ |
| JIT       | Реализация trait `DebugEngine`, генерация таблицы "переменная → регистр/стек" при компиляции, список кадров в runtime, временная компиляция выражений |
| LLVM      | Метаданные отладки IR → LLVM `DILocation` / `DISubprogram` → DWARF (без DAP-взаимодействия) |

### Зависимости

```
Фаза ноль (метаданные IR)
    ↓
Фаза один (интерпретаторный DAP MVP)  ←从这里开始就能用了
    ↓
Фаза два (продвинутые возможности)
    ↓
Фаза три (JIT + LLVM DWARF)
```

### Риски

| Риск                        | Смягчение                                                                     |
| --------------------------- | ------------------------------------------------------------------------------ |
| Сложность механизма паузы интерпретатора | Использование простого channel/signal вместо сложного конечного автомата; пауза — это просто запрет fetch следующей инструкции |
| Типобезопасность вычисления выражений | Повторное использование существующего typechecker, только для чтения, без фиксации побочных эффектов |
| Детали протокола DAP        | Ссылка на реализации debugpy / delve; протокол зрелый                         |
| Livelock stop-all при отладке параллелизма | Таймаут-механизм + принудительная пауза                                        |

## Компромиссы

### Достоинства

- **Один источник**: Отладочные метаданные генерируются один раз, три движка используют совместно. Не возникнет ситуации "в интерпретаторе отладочная информация правильная, а в LLVM — нет"
- **Нулевое влияние**: Один параметр `--debug`; поведение без этого параметра полностью идентично
- **Стандарт DAP**: Прямое подключение к экосистеме VS Code без собственного редакторного протокола или UI отладчика
- **Приоритет интерпретатора**: Отладка естественно подходит интерпретатору — гибкость, управляемость, простое вычисление выражений. Отказ от интерактивной отладки в режиме LLVM — наиболее прагматичный выбор

### Недостатки

- **Низкая производительность в режиме отладки**: Интерпретатор намного медленнее JIT/LLVM. Но для отладки производительность не нужна — никто не ожидает, что debug-режим будет работать с production-нагрузкой
- **Ограниченная отладка LLVM**: AOT-компиляция не позволяет интерактивную отладку, только GDB/LLDB + DWARF. Но это компромисс: в режиме LLVM и не должно быть различий в поведении отладки
- **Сложность паузы параллелизма**: Семантика stop-all требует обхода всех активных задач в интерпретаторе

### Альтернативные решения

| Решение                          | Почему не выбрано                                                       |
| -------------------------------- | ------------------------------------------------------------------------ |
| Три движка各自 реализуют DAP     | Втрое больше работы, три набора багов. Противоречит "хорошему вкусу"    |
| Только DWARF, без собственного DAP | У интерпретатора и JIT нет понятия DWARF, LLDB не может 进入 VM внутренности |
| Командная отладка а-ля Python pdb | VS Code опыт значительно превосходит командную отладку                  |
| DAP внутри LSP-процесса         | Жизненные циклы полностью разные — LSP привязан к проекту, DAP к сессии отладки. Изоляция процессов — жёсткое требование |
