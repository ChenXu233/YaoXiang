# RFC-034: Унифицированный инструментарий отладки

## Резюме

Введение в YaoXiang унифицированного инструментария отладки. Ключевая идея — **единый источник, три
потребителя**: фронтенд компилятора встраивает позиции в исходном коде, имена переменных и
информацию о типах как полноправных членов в YaoXiang IR; три бэкенда — интерпретатор, JIT и LLVM —
каждый потребляют одни и те же метаданные. Пользователь запускает DAP-сервер (Debug Adapter
Protocol) через `yaoxiang run --debug`, VS Code подключается по stdio и получает единообразный опыт:
точки останова, пошаговое выполнение, просмотр переменных, стек вызовов, вычисление выражений,
отладку параллелизма — независимо от того, какой исполнительный движок находится внизу.

## Мотивация

### Зачем нужна эта возможность?

В настоящее время средства отладки программ на YaoXiang крайне примитивны:

```yaoxiang
io.println("DEBUG: x = " + x.to_string())
io.println("DEBUG: entered branch A")
```

Три критические проблемы:

1. **Самозагрузка разработки компилятора затруднена**: YaoXiang-компилятор пишется на самом
   YaoXiang, но человек, пишущий компилятор, не может отлаживать собственный код. Отсутствие средств
   интерактивной отладки на этапе самозагрузки — это тупик.
2. **Три движка, ноль отладки**: интерпретатор, JIT и LLVM работают каждый по-своему, и в случае
   проблемы пользователь может лишь проверить, появилось ли `ALL TESTS PASSED` в stdout. Утверждение
   не прошло? Неизвестно, на какой строке, неизвестно значение переменной.
3. **Параллелизм — чёрный ящик**: `spawn` создаёт несколько задач — какая задача зависла? Кто
   переместил переменную? Всё приходится угадывать наугад.

### Цели проектирования

- **Единообразный опыт**: точка останова, срабатывающая в интерпретаторе, должна срабатывать и в
  JIT, и в LLVM с согласованным отображением на исходный код. Пользователь не должен ощущать разницу
  между движками.
- **Единый источник**: метаданные отладки текут вместе с IR, без дублирования, без двух комплектов
  отображений.
- **Нулевое вторжение**: один параметр `yaoxiang run --debug`; без этого параметра поведение
  компиляции и выполнения полностью не меняется.
- **Стандарт DAP**: подключение напрямую к экосистеме VS Code, без изобретения собственного
  протокола редактора.

## Предложение

### Основной дизайн

Обзор архитектуры:

```
┌──────────────────────────────────────────────────────┐
│                    VS Code / редактор                  │
│              DAP-клиент (launch.json)                 │
└────────────────────────┬─────────────────────────────┘
                         │ stdio
┌────────────────────────▼─────────────────────────────┐
│                 DAP-сервер (yx-core)                  │
│  ┌─────────┐  ┌──────────┐  ┌───────────────────┐    │
│  │ управление│  │ управление│  │ движок вычисления │    │
│  │ сессиями │  │ точками  │  │ выражений         │    │
│  └─────────┘  │ останова │  └───────────────────┘    │
│               └──────────┘                            │
└────────────────────────┬─────────────────────────────┘
                         │ запрос/управление
┌────────────────────────▼─────────────────────────────┐
│          Интерфейс отладки среды выполнения (trait)    │
│  pause / resume / step / get_frames / eval / ...     │
└────┬──────────────────┬──────────────────┬──────────┘
     │                  │                  │
┌────▼────┐    ┌───────▼───────┐    ┌─────▼──────┐
│Интерпре-│    │ JIT (RFC-028) │    │  LLVM AOT  │
│татор    │    │ генерация     │    │ метаданные  │
│прямое   │    │ лёгкой        │    │ IR         │
│потребле-│    │ таблицы       │    │ → DWARF    │
│ние мета-│    │ отладки       │    │            │
│данных IR│    │               │    │            │
└─────────┘    └───────────────┘    └────────────┘
```

**Ключевые проектные решения**:

1. **DAP-сервер и среда выполнения разделены через trait**. Серверу безразлично, что внизу —
   интерпретатор или JIT: он лишь отдаёт команды через trait `DebugEngine`. Каждый движок независимо
   реализует один и тот же trait.
2. **`yaoxiang run --debug` принудительно использует интерпретатор**. Отладке нужна управляемость, а
   не производительность. В режиме LLVM только генерируется DWARF для последующего анализа (core
   dump / crash report); интерактивная отладка не выполняется.
3. **Повторное использование логики обнаружения точки входа из `yaoxiang run`**. Без введения новых
   подкоманд: ментальная модель — «запустить мою программу в режиме отладки».

### Метаданные отладки в IR

Метаданные прикрепляются к существующему YaoXiang IR, без добавления новых разновидностей IR. Все
метаданные генерируются в **одном месте — фронтенде компилятора**, а для бэкендов они доступны
только для чтения:

| Метаданные       | Точка присоединения       | Описание                                              |
| ---------------- | ------------------------- | ----------------------------------------------------- |
| `SourceLocation` | каждый IR-узел            | исходный файл:строка:столбец                          |
| `VarName`        | узел объявления/привязки  | имя переменной в исходном коде                        |
| `TypeAnnotation` | узел переменной/выражения | выведенный тип (включая предикаты времени компиляции) |
| `ScopeBoundary`  | вход/выход блока/функции  | жизненный цикл области видимости переменной           |
| `SpanInfo`       | узел `spawn`              | границы задач внутри блока `spawn`                    |

### Процедура запуска

```
yaoxiang run --debug file.yx
    │
    ├── Фаза 1: Компиляция (с метаданными отладки)
    │   ├── разбор → AST
    │   ├── проверка типов + верификация предикатов времени компиляции
    │   └── понижение до IR (с присоединением метаданных отладки)
    │
    ├── Фаза 2: Использование движка интерпретатора
    │   └── в режиме --debug используется интерпретатор вне зависимости от --release
    │
    ├── Фаза 3: Запуск DAP-сервера
    │   ├── инициализация канала передачи stdio
    │   ├── ожидание подключения (attach) VS Code
    │   ├── после успешного attach — приостановка на входе в программу
    │   └── переход в цикл интерактивной отладки
    │
    └── Фаза 4: Завершение программы / завершение сессии отладки → выход
```

### Различия между режимами

| Режим                    | Способ отладки                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `yaoxiang run --debug`   | принудительный интерпретатор, полнофункциональная интерактивная отладка через DAP       |
| `yaoxiang run --release` | генерация DWARF для последующего анализа (core dump / crash report), DAP не запускается |
| `yaoxiang run` (обычный) | без метаданных отладки, без поддержки отладки                                           |

## Детальный дизайн

### 1. Точки останова

```
Типы точек останова:
├── Точка останова на строке исходного кода
│       → фронтенд компилятора генерирует метаданные позиции,
│         бэкенд выполняет запрос и сопоставление
├── Точка останова на входе в функцию
│       → срабатывает при вызове функции (вторая фаза)
├── Условная точка останова
│       → срабатывает, когда выражение вычисляется в true
└── Точка останова по данным
        → срабатывает при изменении переменной (вторая фаза)
```

**Ключевая логика точки останова на строке исходного кода**:

```
VS Code отправляет: «Установить точку останова в file.yx:42»
    │
DAP-сервер:
    ├── запрос всех узлов в IR, у которых SourceLocation == (file.yx, 42)
    ├── передача среде выполнения: «Приостановить на этих IR-адресах»
    └── среда выполнения возвращает: ID точки останова

Программа выполняется до IR-узла → среда выполнения проверяет:
    есть ли этот узел в списке точек останова?
    ├── обычная точка останова → приостановка, уведомление DAP-сервера
    └── условная точка останова → вычисление условного выражения
                                    → приостановка только при true
```

**Реализация в трёх движках**:

|                            | Интерпретатор                                              | JIT                                          | LLVM                                                 |
| -------------------------- | ---------------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------- |
| Способ установки           | проверка ID IR-узла в цикле выполнения                     | JIT вставляет `int3` в машинный код          | использование LLVM DWARF + аппаратные точки останова |
| Вычисление условной        | прямая интерпретация выражения                             | временная JIT-компиляция условного выражения | стек выражений DWARF + вычисление                    |
| Затраты производительности | одна дополнительная табличная проверка для каждого IR-узла | затраты только в точках останова             | почти нулевые затраты (аппаратные точки останова)    |

### 2. Пошаговое выполнение

```
Step Over    → выполняет текущую строку, пропускает внутренности
               вызова функции, останавливается на следующей строке
Step Into    → входит во внутренности вызова функции
               в текущей строке
Step Out     → выполняет до возврата из текущей функции
Continue     → возобновляет выполнение до следующей точки останова
               или до завершения программы
```

**Логика реализации**: пошаговые операции по своей сути являются **временными точками останова**.
Они разделяют один и тот же механизм с явно установленными пользователем точками останова — это не
две системы, а два способа использования одной.

```
Step Over:
    текущий номер строки исходного кода = query_line(frame)
    → установить временную точку останова на следующей строке
    → если текущая строка — вызов функции:
       установить временную точку останова после точки вызова
    → Continue → срабатывание временной точки останова
              → удаление → приостановка

Step Into:
    первая исполнимая позиция текущего вызова
    → найти позицию в исходном коде первого IR-узла тела функции
    → установить временную точку останова → Continue
                                     → срабатывание → приостановка

Step Out:
    адрес возврата текущего кадра стека
    → найти следующую строку вызывающего кода (caller)
    → установить временную точку останова → Continue
                                     → срабатывание → приостановка
```

**Обработка четырёх граничных случаев временных точек останова**:

1. **Принадлежность к параллельному контексту**: временная точка останова привязывается к ID текущей
   задачи; срабатывания в других задачах просто игнорируются.
2. **Step Over блока `spawn`**: Step Over за пределами `spawn` означает выполнение всего блока
   `spawn` и переход дальше. Для входа во внутренности `spawn` следует использовать Step Into.
3. **Несрабатывание временной точки останова**: устанавливается тайм-аут сторожевого таймера (30
   секунд без срабатывания какой-либо точки останова) → принудительная приостановка → уведомление VS
   Code. Параллельно отслеживается событие выхода из программы → немедленная очистка.
4. **Несколько IR-узлов на одной строке**: временная точка останова Step Over помечается флагом
   `ignore_current_line`; при срабатывании, если номер строки в исходном коде равен текущему номеру
   строки, выполняется игнорирование и продолжение.

### 3. Просмотр переменных и области видимости

```
VS Code запрашивает: «Список переменных текущего кадра»
    │
DAP-сервер:
    ├── запрос IR-узла текущей точки приостановки
    ├── обход привязок переменных внутри текущего ScopeBoundary
    │   └── каждая привязка возвращает:
    │       (имя, тип, ссылка на значение во время выполнения)
    └── формирование VariablesResponse → VS Code
```

**Слои областей видимости**:

```
┌─ Globals ──────────────────────────────────┐
│  Привязки уровня модуля:                   │
│  константы, псевдонимы типов, глобальные   │
├─ Locals ───────────────────────────────────┤
│  Локальные переменные, видимые в           │
│  текущей функции                           │
│  ├── Аргументы (параметры функции)         │
│  └── Локальные привязки (let / присваивание)│
├─ Captured ─────────────────────────────────┤
│  Внешние переменные, захваченные блоком    │
│  spawn / замыканием                        │
│  Отображает состояние владения:            │
│  перемещено / совместное использование по ref│
└────────────────────────────────────────────┘
```

**Различия между движками**:

| Движок        | Получение значения переменной                                                                                                 |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Интерпретатор | прямое чтение кадров стека и кучи VM. Каждое значение имеет явное представление в памяти                                      |
| JIT           | значения в регистрах и стеке → необходимо при JIT-компиляции записывать таблицу отображения «переменная → регистр/слот стека» |
| LLVM          | секция `.debug_info` в DWARF → `DW_AT_location` → встроенная поддержка LLDB                                                   |

**Отображение специальных типов**: уточнённые предикатами времени компиляции типы отображают
информацию, ценную для отладки:

```
x: Positive(x)  →  отображает "Int (x > 0 = True)"
y: Sorted(y)    →  отображает "Array(Int) (гарантия сортировки)"
result: T       →  отображает конкретный тип во время выполнения
```

### 4. Стек вызовов

```
DAP-запрос: StackTrace
    │
Возврат:
┌──────────────────────────────────┐
│ #0  process_item()  file.yx:42  │  ← текущая точка приостановки
│     locals: item = "hello"      │
│     ID задачи spawn: task-3     │
├──────────────────────────────────┤
│ #1  main()          file.yx:67  │  ← вызывающий код
│     locals: data = ["hello", ...]│
├──────────────────────────────────┤
│ #2  <entry>         file.yx:1   │  ← корень
└──────────────────────────────────┘
```

Каждый кадр записывает: сигнатуру функции, позицию вызова (исходный файл + номер строки), локальные
переменные (отложенное вычисление), контекст `spawn` (ID задачи).

Интерпретатор и JIT независимо ведут списки кадров. Получение кадров не является бесплатным — но
режим отладки не стремится к нулевым накладным расходам.

### 5. Вычисление выражений (Watch / REPL)

Пользователь вводит произвольное выражение YaoXiang в точке останова:

```
Watch: x + y         → возвращает результат вычисления
Watch: items[2].name → доступ к сложной структуре
Watch: f(x)          → вызов функции (риск побочных эффектов)
```

**Стратегия вычисления**:

```
Пользователь вводит выражение
    │
├── фронтенд компилятора разбирает выражение
├── выполняет проверку типов в контексте текущего кадра
├── значения переменных получаются из текущего кадра
│   (ссылки только для чтения)
├── выражение выполняется как независимая микропрограмма
│   └── запрещено изменять внешние переменные
│   └── запрещён spawn
│   └── запрещён IO (или опционально разрешается)
└── возврат результирующего значения
    → состояние исходного кадра полностью неизменно
```

**Интерпретатор как естественная песочница**: вычисление выражений — это не создание новой
песочницы: сам интерпретатор и есть песочница. Вычисление выражений лишь временно помещает кадр,
который уничтожается после использования. Совместно используется та же VM, что и при обычном
выполнении, но никакие побочные эффекты не применяются.

**Вычисление вызовов функций**: разрешено по умолчанию, но с предупреждением пользователя «это
выражение может иметь побочные эффекты» и требует подтверждения перед выполнением.

**Различия между движками**:

| Движок        | Вычисление выражений                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| Интерпретатор | повторное использование существующего пути кода eval с инъекцией окружения текущего кадра                |
| JIT           | временная компиляция выражения → компоновка с текущим кадром → выполнение → отбрасывание временного кода |
| LLVM          | не поддерживается — режим LLVM не выполняет интерактивную отладку                                        |

### 6. Отладка параллелизма

**Видимость модели задач**:

концепция `threads` в DAP отображается на задачи `spawn` в YaoXiang. Каждая задача имеет собственный
список кадров стека и состояние выполнения.

```
┌─ Threads ───────────────────────────┐
│  ● task-1  main()     file.yx:10   │ ← текущий в фокусе
│  ▶ task-2  fetch()    file.yx:34   │ ← выполняется
│  ⏸ task-3  process()  file.yx:56   │ ← приостановлена в точке останова
│  ◼ task-4  write()    завершена     │
└────────────────────────────────────┘
```

**Точки останова в параллельном контексте**:

| Режим приостановки        | Поведение                                                    | Сценарий применения                         |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------- |
| `stop-all` (по умолчанию) | срабатывание в одной задаче → приостановка всех задач        | отладка гонок данных, глобального состояния |
| `stop-this-only`          | приостановка только сработавшей задачи, остальные продолжают | отладка логики независимых задач            |

**Семантика пошагового выполнения для блока `spawn`**:

```
spawn {          // Step Over → выполняет весь блок spawn
    task_a()     // Step Into → входит в task_a
    task_b()     // выполняется параллельно,
                 // не подвержено влиянию отдельных шагов
}
```

### 7. Отображение протокола DAP

#### Фаза 1: Основные запросы

| DAP-запрос          | Семантика YaoXiang                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `initialize`        | согласование возможностей: поддержка точек останова, пошагового выполнения, переменных, кадров стека |
| `launch` / `attach` | запуск/подключение к программе YaoXiang (режим `--debug` идёт по attach)                             |
| `setBreakpoints`    | установка точек останова на строках исходного кода                                                   |
| `configurationDone` | точки останова готовы, начало выполнения                                                             |
| `threads`           | возврат списка всех активных задач `spawn`                                                           |
| `stackTrace`        | возврат списка кадров стека указанной задачи                                                         |
| `scopes`            | возврат областей видимости переменных текущего кадра                                                 |
| `variables`         | возврат списка переменных указанной области видимости                                                |
| `continue`          | возобновление выполнения                                                                             |
| `next`              | Step Over                                                                                            |
| `stepIn`            | Step Into                                                                                            |
| `stepOut`           | Step Out                                                                                             |
| `pause`             | прерывание всех задач                                                                                |
| `evaluate`          | вычисление выражения в текущем кадре                                                                 |
| `disconnect`        | завершение сессии отладки                                                                            |

#### Фаза 2: Расширенные запросы

| DAP-запрос                | Семантика YaoXiang                                              |
| ------------------------- | --------------------------------------------------------------- |
| `setFunctionBreakpoints`  | точка останова по имени функции                                 |
| `setExceptionBreakpoints` | приостановка при ошибке / panic                                 |
| `dataBreakpointInfo`      | точка останова по данным (срабатывает при изменении переменной) |

## Стратегия реализации

### Фаза 0: Инфраструктура (предшествует всем фазам)

**Цель**: фронтенд компилятора присоединяет метаданные отладки к IR.

| Компонент      | Изменения                                                                        |
| -------------- | -------------------------------------------------------------------------------- |
| Определение IR | добавление полей метаданных `SourceLocation`, `VarName`, `TypeAnnotation` и т.д. |
| Parser         | запись позиции в исходном коде для каждого узла AST                              |
| TypeChecker    | присоединение информации о типах к IR-узлам                                      |
| Тесты          | проверка, что dump IR содержит информацию о позициях и переменных                |

**Не затрагивает среду выполнения.**

**Ход реализации (2026-09-17)**:

| Поставка                | Статус      | Форма реализации                                                                                                                                                                                                                                                                                                                           |
| ----------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Позиция в исходном коде | Реализовано | Все 76 вариантов `Instruction` несут поле `span`; метод `span()` намеренно не имеет ветки по умолчанию, добавление нового варианта без `span` приводит к ошибке компиляции. Позиции покрывают 40/41 инструкцию                                                                                                                             |
| Имя переменной          | Реализовано | `LocalSlot { name, ty, scope_depth }` привязан к `FunctionBody::Code::locals`; `register_local` записывает значения на месте во время генерации. Отладочная секция `.42` v2 содержит имена, артефакты v1 читаются с обратной совместимостью.                                                                                               |
| Имя глобального слота   | Реализовано | Отладочная секция `.42` v3 содержит таблицу «номер слота → имя привязки верхнего уровня». Привязки верхнего уровня проходят через `Operand::Global` и отсутствуют в таблице локальных имён какой-либо функции; без этой таблицы можно сообщить только числовое значение, но не имя переменной. Артефакты v1/v2 читаются с пустой таблицей. |
| Информация о типах      | Частично    | Слот уже содержит `ty`; отдельные метаданные `TypeAnnotation` не реализованы                                                                                                                                                                                                                                                               |
| Видимость в dump        | Реализовано | `dump` выводит для каждой инструкции `; <file>:<line>:<col>` и перечисляет `locals: имя@слот`                                                                                                                                                                                                                                              |

Форма данных, реализованных в приведённой выше таблице, напрямую стыкуется с фазой 1: разбор точек
останова в DAP использует `debug_map`, панель переменных использует `local_names` (имена) и `locals`
(типы).

### Фаза 1: MVP DAP для интерпретатора

**Цель**: `yaoxiang run --debug file.yx` позволяет устанавливать точки останова, выполнять пошагово,
просматривать переменные.

| Компонент                                | Изменения                                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| DAP-сервер (новый модуль yx-core)        | транспортный уровень stdio, обработка основных запросов, менеджер точек останова (отображение строки исходного кода → IR-узел)              |
| Trait отладки среды выполнения (yx-core) | определение trait `DebugEngine` (pause, resume, step, get_frames, eval, get_variables)                                                      |
| Интерпретатор                            | проверка точек останова в цикле выполнения, механизм приостановки/возобновления, ведение списка кадров, реализация `InterpreterDebugEngine` |
| CLI                                      | параметр `yaoxiang run --debug`                                                                                                             |

**Критерии приёмки**: для любого файла `.yx` в `tests/yaoxiang/` можно установить точки останова
через VS Code, выполнить Step Over, просмотреть значения переменных.

### Фаза 2: Расширенные возможности отладки

**Цель**: вычисление выражений, точки останова на функциях, отладка параллелизма, точки останова на
исключениях.

| Компонент                              | Изменения                                                                                                                          |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Движок вычисления выражений            | компиляция микропрограмм (повторное использование parser + typechecker), временная загрузка кадра в VM, изоляция побочных эффектов |
| Отладка параллелизма                   | отображение списка задач `spawn`, привязка точек останова к ID задачи, стратегия приостановки `stop-all` / `stop-this-only`        |
| Точки останова на функциях/исключениях | отображение `setFunctionBreakpoints`, `setExceptionBreakpoints`                                                                    |
| Расширение VS Code                     | предоставление шаблона `launch.json` по умолчанию                                                                                  |

### Фаза 3: Отладка JIT и DWARF для LLVM

**Цель**: повторное использование DAP движком JIT, генерация DWARF LLVM для анализа сбоев.

| Компонент | Изменения                                                                                                                                                                      |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| JIT       | реализация trait `DebugEngine`, генерация таблицы отображения переменная→регистр во время компиляции, ведение списка кадров в среде выполнения, временная компиляция выражений |
| LLVM      | метаданные отладки IR → LLVM `DILocation` / `DISubprogram` → DWARF (без интерактивности DAP)                                                                                   |

### Зависимости между фазами

```
Фаза 0 (метаданные IR)
    ↓
Фаза 1 (MVP DAP для интерпретатора)  ← с этого момента уже можно использовать
    ↓
Фаза 2 (расширенные возможности)
    ↓
Фаза 3 (JIT + DWARF для LLVM)
```

### Риски

| Риск                                            | Смягчение                                                                                                                                  |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Сложность механизма приостановки интерпретатора | использование простого канала/сигнала вместо сложного конечного автомата; приостановка — это просто запрет на выборку следующей инструкции |
| Типобезопасность вычисления выражений           | повторное использование существующего typechecker, только чтение ссылок, без применения побочных эффектов                                  |
| Детали протокола DAP                            | обращение к реализациям debugpy / delve, протокол зрелый                                                                                   |
| Livelock при `stop-all` в отладке параллелизма  | механизм тайм-аута + принудительная приостановка                                                                                           |

## Компромиссы

### Преимущества

- **Единый источник**: метаданные отладки генерируются лишь единожды и разделяются между тремя
  движками. Исключается ситуация «отладочная информация в интерпретаторе правильная, а в LLVM —
  нет».
- **Нулевое вторжение**: один параметр `--debug`; без него поведение полностью не меняется.
- **Стандарт DAP**: прямое подключение к экосистеме VS Code, без необходимости в собственном
  протоколе редактора или UI отладчика.
- **Приоритет интерпретатора**: отладка по своей природе подходит интерпретатору — он гибок,
  управляем, прост для вычисления выражений. Отсутствие интерактивной отладки в режиме LLVM —
  наиболее прагматичный выбор.

### Недостатки

- **Низкая производительность в режиме отладки**: интерпретатор значительно медленнее JIT/LLVM. Но
  отладка не требует производительности — никто не ожидает запуска производственных нагрузок в
  режиме отладки.
- **Ограниченная отладка в LLVM**: AOT-компиляция не поддерживает интерактивную отладку, можно
  использовать только GDB/LLDB + DWARF. Но это осознанный компромисс: в режиме LLVM и не должно быть
  различий в поведении отладки.
- **Сложность приостановки параллелизма**: реализация семантики `stop-all` на интерпретаторе требует
  обхода всех активных задач.

### Альтернативные варианты

| Вариант                                             | Почему не выбран                                                                                                              |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Каждый из трёх движков реализует DAP самостоятельно | тройной объём работы, тройной набор ошибок. Нарушает «хороший вкус»                                                           |
| Только DWARF, без собственного DAP                  | у интерпретатора и JIT нет концепции DWARF, LLDB не может проникнуть внутрь VM                                                |
| Командный отладчик по аналогии с Python pdb         | возможности VS Code намного превосходят командный отладчик                                                                    |
| Встраивание DAP в процесс LSP                       | жизненные циклы совершенно различны — LSP привязан к проекту, DAP — к сессии отладки. Изоляция процессов — жёсткое требование |
