# RFC-011b: Перегрузка операторов и операторы на основе интерфейсов

## Резюме

Дополнение YaoXiang возможностью **перегрузки операторов**, чтобы `a + b` / `a == b` / `a[i]` / `e?`
могли быть реализованы для пользовательских типов, а ограничения `T: Add + Multiply + Zero`, уже
записанные в RFC-011, превратились из **бумажной возможности** в работающий механизм.

Дизайн использует **разделение ответственности на три уровня**: фиксированная таблица соответствия
оператор→метод (Layer 0), базовая диспетчеризация по имени (Layer 1, переиспользует существующий
`method_bindings`), слой контракта интерфейса (Layer 2, для ограничений обобщений). **Приоритет и
ассоциативность операторов остаются фиксированными** в языке, пользователь перегружает только
семантику.

Первая партия: восемь интерфейсов `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
`Try`. Никаких новых ключевых слов, никаких новых синтаксических конструкций.

## Мотивация

### Почему нужна эта возможность

#### 1. Ключевой пример RFC-011 зависит от неё, но пока это бумажная возможность

RFC-011 (уже принят) использует имена операторов в качестве ограничений типа в 8 местах:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

Это показательный пример RFC-011 «типы, зависящие от значений + проверка размерностей на этапе
компиляции». Однако **ни в одном RFC из всего набора не определено, откуда берутся `Add` /
`Multiply` и как `+` связывается с ними**. `T: Add` сейчас — это невыполнимое утверждение.

#### 2. Пользовательские типы не могут участвовать в базовых операциях (проверено)

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

Сопутствующее последствие: `list.contains(list_of_structs, p)` **полностью недоступен** — внутри он
зависит от `==`.

#### 3. `?` приваривает имя типа к компилятору, блокируя перенос `Result` в std

Реализация `?` одновременно жёстко кодирует имя типа и номера вариантов:

```rust
// typecheck: жёстко закодированное конструирование типа Result
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen: жёстко закодированные имя группы и номера вариантов
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

Это вынуждает `Result` оставаться в core. Если `?` сделать **управляемым интерфейсом**, любой тип,
реализующий этот интерфейс (включая пользовательские), сможет использоваться с `?`, и тогда `Result`
сможет перейти в std.

#### 4. Пользовательские контейнеры не могут индексироваться

Проверка типов `Index` представляет собой жёстко закодированный белый список:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// иначе → "контейнеры, не знакомые на уровне типов, молча отвергаются"
```

Для любого пользовательского контейнера `c[0]` всегда выдаёт ошибку.

### Существующий полуфабрикат

Исследование показало, что механизмы **в основном уже есть**, не хватает только проводки:

| Механизм                                                              | Расположение                              | Состояние                                 |
| --------------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------- |
| Объявление интерфейса `(Self: Type) -> Type`                          | RFC-011a Phase 1                          | ✅ Работает                               |
| Инстанцирование интерфейса `Animal(Dog)` + внешние объявления методов | RFC-011a Phase 2–3                        | ✅ Работает                               |
| Диспетчеризация методов `method_bindings["Type.method"]`              | `expressions.rs:1299`                     | ✅ Работает                               |
| Ассоциированные типы (= параметры типа интерфейса)                    | RFC-011 §3.1; RFC-011a принял это решение | ✅ Механизм определён                     |
| Вычисление семейств типов `AssociatedTypeDef`                         | `dependent_types.rs`                      | ✅ Рабочий пример `IsTrue` в `std.assert` |
| trait `Equal` / `Dup` / `Clone` / `Debug`                             | Зарегистрированы в `trait_data.rs`        | ⚠️ `Equal` — **ноль точек потребления**   |
| Соответствие оператор → имя метода                                    | —                                         | ❌ Отсутствует                            |

**Вывод**: это не создание функции с нуля, а проводка и документирование существующих деталей.

## Предложение

### Основной дизайн: разделение ответственности на три уровня

```
Layer 0  Фиксированная таблица соответствия (константа уровня языка, не изменяемая пользователем)
         + → add    == → equal    [] → index    ? → residual
         │  Встроена на этапе компиляции, не участвует в выводе типов, не видна пользователю
         ▼
Layer 1  База диспетчеризации (поиск метода по имени и вызов)  ← Переиспользует существующий механизм
         method_bindings["Point.add"]
         ▼
Layer 2  Контракт интерфейса (для ограничений обобщений)
         Add / Equal / Index / Try …
         Делает ограничение T: Add работоспособным и служит шлюзом для оператора
```

**Обоснование разделения**:

- **Layer 0 и 1 делают оператор «работающим»**, Layer 2 делает оператор «поддающимся ограничению».
  Объединение привело бы к тому, что любой метод с именем `add` вызывался бы через `+`, и
  ограничение RFC-011 `T: Add` разошлось бы с оператором.
- **Layer 1 не создаётся заново**: `method_bindings` уже ищет по ключу `Type.method` (путь fallback
  после неудачного поиска поля), оператору достаточно пройти тем же путём.
- **Layer 2 — это шлюз**: перед пропуском оператора **обязательно** проверяется, что тип реализует
  соответствующий интерфейс (см. §«Почему необходима реализация интерфейса»).

### Layer 0: фиксированная таблица соответствия

| Оператор          | Интерфейс                                                  | Метод      | Первая партия |
| ----------------- | ---------------------------------------------------------- | ---------- | ------------- |
| `+`               | `Add`                                                      | `add`      | ✅            |
| `-`               | `Subtract`                                                 | `subtract` | ✅            |
| `*`               | `Multiply`                                                 | `multiply` | ✅            |
| `/`               | `Divide`                                                   | `divide`   | ✅            |
| `%`               | `Modulo`                                                   | `modulo`   | ✅            |
| `==` `!=`         | `Equal`                                                    | `equal`    | ✅            |
| `[]`              | `Index`                                                    | `index`    | ✅            |
| `?`               | `Try`                                                      | `residual` | ✅            |
| `<` `<=` `>` `>=` | — (сохраняем нативные инструкции)                          | —          | ❌            |
| `and` `or`        | — (короткое замыкание — семантика языка, не перегружается) | —          | ❌            |
| 5 побитовых       | —                                                          | —          | ❌            |
| Унарные `-` `!`   | —                                                          | —          | ❌            |

**Имена интерфейсов пишутся полностью, а не сокращённо** (`Multiply`, а не `Mul`): для соответствия
тексту RFC-011 с `T: Add + Multiply + Zero` — **без изменения уже принятого RFC**.

**`%` принимает семантику `Modulo`** (математический остаток, знак результата следует за делителем),
а не текущую реализацию remainder (`-7 % 3` сейчас возвращает `-1`). Это **намеренное исправление
семантики** — имя прибивает семантику к математическому modulo.

### Layer 2: определения интерфейсов

#### Арифметические интерфейсы

```yaoxiang
Add: (Self: Type, R: Type) -> Type = {
    add: (self: &Self, other: &R) -> Self
}

Subtract: (Self: Type, R: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> Self
}

Multiply: (Self: Type, R: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> Self
}

Divide: (Self: Type, R: Type) -> Type = {
    divide: (self: &Self, other: &R) -> Self
}

Modulo: (Self: Type, R: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> Self
}
```

`R` — тип правого операнда, допускающий разные типы слева и справа (например, `Int + Float`). Тип
возврата фиксирован как `Self` (получатель по `&Self`, см. RFC-009 о токенах заимствования и
RFC-011a о соглашениях получателя).

#### Интерфейс равенства

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` неявно требует `Dup`**: семантика `==` — «сравнить два значения», обе стороны должны быть
читаемы. Линейное (не `Dup`) значение может быть прочитано только один раз и не может участвовать в
сравнении. RFC-009 уже установил причинную цепочку:

> **Причинность нельзя обращать: заморозка — причина, Dup — следствие.**

Поэтому условием реализации `Equal` является наличие у `Self` атрибута `Dup`; при его отсутствии
компилятор отвергает инстанцирование `Equal`.

#### Интерфейс индексации

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` является параметром типа, а не членом ассоциированного типа**: открытый вопрос RFC-011a
был решён принятием варианта «ассоциированный тип через параметр обобщённого интерфейса»
(`Iterator: (Item: Type) -> Type` — изоморфный прецедент), без введения синтаксиса членов `type`.

**Многопозиционная индексация реализуется через упаковку в кортеж + перегрузку**, без введения
вариативных интерфейсов:

```yaoxiang
// Одномерный контейнер
List(T) инстанцирует Index(List(T), Int, T)              → arr[0]

// Многомерный контейнер
Grid    инстанцирует Index(Grid, Tuple(Int, Int), Float)  → g[0, 1]
//                   └─ Key является кортежем

// Два инстанцирования с разными сигнатурами → сосуществуют по правилам перегрузки RFC-011a
```

#### Интерфейс распространения

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    residual: (self: &Self) -> E
}
```

`T` (тип успеха) и `E` (тип ошибки) оба являются параметрами типа интерфейса.

**Правила типов для `?`**:

```yaoxiang
// f: () -> Result(T, E)
// Остаток тела функции требует Result(U, E) (тип ошибки должен совпадать)
x = f()?        // x: T, эквивалентно:
                //   match f() {
                //       ok(v)  => v
                //       err(e) => return err(e)
                //   }
```

При несовпадении типов ошибки выдаётся ошибка компиляции (соответствующая существующей `E1083`);
если тип возврата внешней функции не является распространяемым — `E1081`; если выражение не
реализует `Try` — заменить текст `E1082` (больше не упоминать конкретное имя "Result").

### Примеры

#### Арифметика и равенство для пользовательского типа

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point),
    Equal(Point, Point)
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

Point.equal: (self: &Point, other: &Point) -> Bool =
    self.x == other.x and self.y == other.y

main = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   // Point(4.0, 6.0)
    println(a == b)             // false
    println(a == a)             // true
}
```

#### Индексация пользовательского контейнера

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### Перенос `Result` в std (цель дизайна)

После того как `Result` реализует `Try`, `?` больше не зависит от жёсткого кодирования имени типа:

```yaoxiang
// В std.result (больше не нужны особые случаи в core)
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E),
    Try(Result(T, E), T, E)
}

Result.residual: (T: Type, E: Type)(self: &Result(T, E)) -> E =
    match self {
        ok(_) => abort_invalid_residual(),   // путь ok не должен приводить к residual
        err(e) => e
    }
}
```

#### Ограничения обобщений наконец-то реализуемы

```yaoxiang
// Пример из RFC-011 теперь можно воплотить
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

### Синтаксические изменения

**Никакого нового синтаксиса, никаких новых ключевых слов**. Все возможности складываются из
существующих механизмов:

| Возможность                 | Переиспользуемый существующий механизм                              |
| --------------------------- | ------------------------------------------------------------------- |
| Объявление интерфейса       | RFC-011a Phase 1                                                    |
| Инстанцирование интерфейса  | RFC-011a Phase 2 (`Dog: { Animal(Dog) }`)                           |
| Реализация метода           | RFC-011a Phase 3 (внешнее объявление `Point.add`)                   |
| Ассоциированный тип         | RFC-011 §3.1 (параметр типа интерфейса)                             |
| Многопозиционная индексация | Существующий разбор упаковки в кортеж + правила перегрузки RFC-011a |
| Приоритет операторов        | **Фиксирован языком**, пользовательская настройка не открыта        |

## Детальный дизайн

### Влияние на систему типов

**Новые интерфейсы** (Layer 2): `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index` `Try`.

**Переиспользование зарегистрированных trait**: `Equal` уже зарегистрирован в `trait_data.rs`, но
**не имеет точек потребления** (сейчас `==` только делает `unify` и жёстко возвращает `Bool`). Этот
RFC подключает его в качестве реального контракта для `==`.

**Предварительное ограничение `Dup`**: при инстанцировании `Equal` проверяется, является ли `Self`
`Dup`. Атрибуты `Dup` / `Linear` выводятся согласно RFC-009 (`&T` замораживает ⇒ Dup; `&mut T`
исключительное ⇒ Linear).

**Решение ограничений**: решение `T: Add` = проверка, инстанцирует ли `T` интерфейс `Add`. Механизм
переиспользует сбор типов на этапе компиляции из RFC-011a, нового решателя не требуется.

### Поведение во время выполнения

**Нулевые накладные расходы во время выполнения**: целевой метод оператора определяется на этапе
компиляции (статическая диспетчеризация). Для базовых типов (`Int`/`Float`/`String`/`List`)
сохраняется **быстрый путь нативных инструкций**, минуя диспетчеризацию через интерфейс.

Поведение `?` во время выполнения не меняется (распаковка + досрочный возврат), меняется только
основание для проверки: с «имя типа == "Result"» на «тип реализует `Try`».

### Изменения в компиляторе

| Компонент                            | Изменение                                                                                                                                             |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `typecheck/inference/expressions.rs` | Белый список `infer_binary` заменяется на двойной путь «нативный быстрый + запрос интерфейса»; добавлены ветки запроса интерфейса для `Index` / `Try` |
| Там же (ветка `Try`)                 | Удалить жёсткое кодирование `MonoType::make_result`, заменить на запрос инстанцирования `Try`                                                         |
| `middle/core/ir_gen.rs`              | Удалить жёсткое кодирование `group: "Result"` в `Expr::Try`; добавить ветку диспетчеризации через интерфейс в `Expr::Index`                           |
| `typecheck/types/trait_data.rs`      | Зарегистрировать инстанцирования по умолчанию для 8 интерфейсов (для `Int` / `Float` / `String` / `List` и т.д.)                                      |
| Новое                                | Константа таблицы соответствия Layer 0 + функция запроса оператор→интерфейс                                                                           |
| Диагностика                          | Текст `E1082` изменён с "requires Result" на "requires Try" (`E1081`/`E1083` оставлены)                                                               |

### Обратная совместимость

**Операции над базовыми типами не меняются**: `1 + 2`, `"a" + "b"`, `[1] + [2]`, `1 < 2` — все
сохраняют нативный путь, поведение и производительность не меняются.

**Изменение семантики `%`**: `-7 % 3` меняется с `-1` (remainder) на `2` (modulo). Это **намеренное
исправление**, которое должно быть отмечено в инструкции по миграции; в существующих тестовых
материалах нет случаев зависимости от `%` с отрицательными числами (проверено).

**Позиционное связывание `f[0]` не меняется**: `distance[0]` — встроенная в компилятор возможность
из RFC-004, **не проходит через интерфейс `Index`**, не затрагивается.

**`?` прозрачен для существующего кода**: после добавления к `Result` инстанцирования `Try`
существующие применения `?` ведут себя полностью идентично.

## Компромиссы

### Преимущества

- **Реализует обещанное RFC-011**: `T: Add + Multiply + Zero` из бумажного становится воплотимым,
  без изменения уже принятого текста RFC
- **Снимает привязку `Result` к core**: интерфейсизация `?` позволяет перенести `Result` в std,
  продолжая цель расслоения
- **Исправляет обнаруженный дефект**: `Point == Point` становится доступным, попутно устраняется
  недоступность `list.contains` для структур
- **Нулевой новый синтаксис**: полностью переиспользует механизмы RFC-011a, не затрагивает правила
  грамматики парсера (соблюдает принцип «нулевых синтаксических изменений» RFC-036)
- **Нулевые накладные расходы во время выполнения**: статическая диспетчеризация + нативный быстрый
  путь для базовых типов
- **Пользовательские контейнеры доступны**: `Box(T)[0]` из «всегда ошибка» становится доступным

### Недостатки

- **Изменение семантики `%` — ломающее изменение**: несмотря на реальное смысловое обоснование,
  требуется инструкция по миграции
- **`Equal` неявно требует `Dup` — отвергает часть типов**: значения линейных типов не могут
  использовать `==`, что является ценой семантической корректности, но может удивить пользователя —
  необходима чёткая диагностика
- **Инстанцирование интерфейса — явная стоимость**: для каждого оператора нужно написать строку
  инстанцирования интерфейса + один метод. Синтаксис RFC-011a не допускает неявного вывода (за что
  получаем «без магии» для параметра типа `Self`)

## Альтернативы

### Вариант A: только Layer 1 (диспетчеризация по имени метода), без слоя интерфейса

`+` просто проверяет наличие метода с именем `add`, не требуя реализации интерфейса `Add`.

**Причина отклонения**: ограничение RFC-011 `T: Add` разойдётся с оператором — ограничение проверяет
интерфейс, оператор — имя метода, и они могут давать противоречивые ответы. Кроме того, невозможно
дать точную диагностику для «`+` применён к типу, не поддерживающему сложение» на этапе компиляции.

### Вариант B: введение синтаксиса конструкторов `Ok(x)` / `Some(x)` для решения проблемы `?`

Не интерфейсизировать `?`, а добавить синтаксис конструкторов для типов-сумм.

**Причина отклонения**: конфликт с RFC-010 (уже принят). RFC-010 явно устанавливает «единообразное
использование record-типов для выражения типов-сумм, **без двух наборов синтаксиса**» и явно
отвергает синтаксис `|`. Введение конструкторов — это введение второго набора выражений. К тому же
он решает только `?`, но не решает `Point == Point` и индексацию пользовательских контейнеров.

### Вариант C: в первой партии сделать интерфейсными и операторы сравнения (с введением `Ordering`)

`<` `<=` `>` `>=` пойдут через интерфейс `Compare` и будут возвращать трёхзначное `Ordering`.

**Причина отклонения**: `<` в YaoXiang уже является **инструкцией IR первого класса**
(`Instruction::Lt/Le/Gt/Ge`); интерфейсизация вынудит базовые типы идти в обход. К тому же введение
`Ordering` потянет за собой сравнение/сортировку самого `Ordering`, `PartialOrd` vs `Ord` для `NaN`
с плавающей точкой — целый отдельный комплекс вопросов, заслуживающий отдельного RFC. Реально
выявленные потребности (`Point == Point`, `list.contains`) **требуют только `Equal`**.

### Вариант D: сокращённые имена операторов (метод интерфейса `Add` называется `add`, а интерфейс — `Mul`)

**Причина отклонения**: в тексте RFC-011 уже написано `T: Add + Multiply + Zero`; использование
сокращений потребует изменения уже принятого RFC.

## Стратегия реализации

### Зависимости

| Зависимость                                  | Состояние        | Влияние на данный RFC                                                                                               |
| -------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| Механизм интерфейсов RFC-011a Phase 1–3      | ✅ Реализован    | Фундамент Layer 2 (проверено в работе)                                                                              |
| Путь конструирования через record из RFC-010 | ❌ Не реализован | **Сторона конструирования `?`** (если `Result` нельзя сконструировать, `Try` не получится полностью протестировать) |
| Деструктуризация вариантов из RFC-039        | ❌ Бумажный      | Синтаксис `match` для `Result.residual`                                                                             |
| Вывод `Dup`/`Linear` из RFC-009              | Частично         | Проверка предварительного ограничения `Equal`                                                                       |

### По фазам

По **зависимостям от интерфейсов** (ограничение дизайна, а не расписание) выделяются две группы:

**Фаза 1 — не зависит от RFC-010/039**:

- Таблица соответствия Layer 0 + проводка диспетчеризации Layer 1
- Семь интерфейсов: `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
- Предварительное ограничение `Equal` ⇒ `Dup`
- Сохранение нативного быстрого пути для базовых типов
- **Результат**: `Point + Point`, `Point == Point`, `Box(T)[0]` — всё становится доступным

**Фаза 2 — зависит от RFC-010 / RFC-039**:

- Интерфейс `Try` + интерфейсизация `?`
- Перенос `Result` из core в std
- **Причина блокировки**: требуется возможность конструировать значения `Result` (RFC-010) и
  деструктурировать их (RFC-039)

### Риски

| Риск                                                                  | Смягчение                                                                                              |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Изменение семантики `%` ломает существующий код пользователей         | Инструкция по миграции + проверено отсутствие зависимости от `%` с отрицательными числами в тестах     |
| Явная стоимость инстанцирования интерфейса раздражает пользователей   | Диагностика с подсказкой «нужно реализовать интерфейс X» и примером инстанцирования                    |
| Двойной путь для базовых типов (нативный + интерфейс) может разойтись | Контроль: `Int` и др. реализуют интерфейс, но семантика метода должна совпадать с нативной инструкцией |
| Шлюз Layer 2 приводит к ошибкам компиляции в существующем коде        | `Equal` сейчас не имеет точек потребления, проводка затронет только те случаи, которые и так ошибались |

## Согласование с другими RFC

Данный RFC позиционируется как **инициатор требований со стороны потребителя**; для согласованности
необходимо параллельно обновить следующие RFC (получено разрешение на правку):

| RFC                    | Что нужно обновить                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **RFC-011** (принят)   | В §«Ограничения» указать, что `Add` / `Multiply` и др. определены и реализованы в RFC-011b                       |
| **RFC-010** (принят)   | Уточнить требования к реализации «поле record — это и есть конструктор» — это предпосылка фазы 2 для `?`         |
| **RFC-039** (черновик) | Конструирование и деструктуризация должны быть парными; обработка проверки полноты для набора вариантов из `std` |
| **RFC-009** (принят)   | Перекрёстная ссылка на `Equal` ⇒ `Dup` в §«Атрибуты типов»                                                       |
