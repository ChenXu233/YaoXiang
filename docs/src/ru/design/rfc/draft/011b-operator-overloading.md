## Резюме

Дополнение YaoXiang возможностью **перегрузки операторов**, чтобы `a + b` / `a == b` / `a[i]` / `e?`
могли быть реализованы пользовательскими типами, и чтобы записанные в RFC-011 ограничения
`T: Add + Multiply + Zero` из **возможности на бумаге** превратились в реализуемый механизм.

Дизайн использует **разделение ответственности на три уровня**: фиксированная таблица соответствия
оператор→метод (уровень 0), база диспетчеризации по имени (уровень 1, повторно использует
существующий `method_bindings`), уровень контрактов интерфейсов (уровень 2, для ограничений
дженериков). **Приоритет и ассоциативность операторов остаются фиксированными на уровне языка**,
пользователь перегружает только семантику.

Первая партия: восемь интерфейсов — `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
`Try`. Никаких новых ключевых слов, никаких новых синтаксических конструкций.

## Мотивация

### Зачем нужна эта возможность

#### 1. Ключевой пример RFC-011 зависит от неё, но в настоящее время это лишь бумажная возможность

RFC-011 (уже принят) в 8 местах использует имена операторов как ограничения типов:

```yaoxiang
multiply: (T: Add + Multiply + Zero, Rows: Int, Cols: Int, M: Int) -> (
    (a: Matrix(T, Rows, Cols), b: Matrix(T, Cols, M)) -> Matrix(T, Rows, M)
)
```

Это визитная карточка RFC-011 «типы с зависимостью от значений + проверка размерностей во время
компиляции». Но **ни в одном RFC из всего набора не определено, откуда берутся `Add` / `Multiply`,
как `+` привязывается к ним**. `T: Add` в настоящее время — невыполнимое утверждение.

#### 2. Пользовательские типы не могут участвовать в базовых операциях (проверено)

```
Point: Type = { x: Int, y: Int }
a = Point(1, 2)
b = Point(1, 2)
a == b
```

```
error [E6007] Runtime error: type mismatch in comparison Eq:
    Struct { type_id: TypeId(0), ... } vs Struct { type_id: TypeId(0), ... }
```

Сопутствующее последствие: `list.contains(list_of_structs, p)` **полностью неработоспособно** —
внутри оно зависит от `==`.

#### 3. `?` намертво вшивает имя типа в компилятор, блокируя перенос `Result` в std

Реализация `?` одновременно жёстко кодирует имя типа и номер варианта:

```rust
// typecheck: жёстко закодированное конструирование типа Result
let expected_result = MonoType::make_result(ok_ty, expected_err);

// ir_gen: жёстко закодированное имя группы и номер варианта
Instruction::VariantTag { group: "Result".to_string(), .. }
variant 0 = ok, variant 1 = err
```

Это заставляет `Result` оставаться в core. Если сделать `?` **управляемым интерфейсом**, любой тип,
реализовавший этот интерфейс (включая пользовательские), сможет использоваться с `?`, и `Result`
можно будет перенести в std.

#### 4. Пользовательские контейнеры не индексируются

Проверка типов для `Index` — это жёстко закодированный белый список:

```rust
// expressions.rs
MonoType::Generic { name, args } if name == "List"  => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Array" => Ok(args[0].clone()),
MonoType::Generic { name, args } if name == "Dict"  => Ok(args[1].clone()),
// остальное → "контейнеры, не признанные на уровне типов, лучше отвергнуть, чем промолчать"
```

Любой определяемый пользователем тип контейнера — `c[0]` всегда выдаёт ошибку.

### Существующая полуфабрикатная база

Исследование показало, что **большая часть механизма уже существует**, не хватает лишь подключения:

| Механизм                                                      | Расположение                              | Статус                                    |
| ------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------- |
| Объявление интерфейса `(Self: Type) -> Type`                  | RFC-011a Phase 1                          | ✅ Работает                               |
| Создание экземпляра `Animal(Dog)` + внешнее объявление метода | RFC-011a Phase 2–3                        | ✅ Работает                               |
| Диспетчеризация методов `method_bindings["Type.method"]`      | `expressions.rs:1299`                     | ✅ Работает                               |
| Ассоциированные типы (= параметры типа интерфейса)            | RFC-011 §3.1; RFC-011a принял это решение | ✅ Механизм определён                     |
| Вычисление семейств типов `AssociatedTypeDef`                 | `dependent_types.rs`                      | ✅ Рабочий пример `std.assert` → `IsTrue` |
| Trait'ы `Equal` / `Dup` / `Clone` / `Debug`                   | Зарегистрированы в `trait_data.rs`        | ⚠️ `Equal` — **ноль точек потребления**   |
| Отображение оператор → имя метода                             | —                                         | ❌ Не существует                          |

**Вывод**: это не создание возможности с нуля, а подключение уже существующих деталей и оформление
их документально.

## Предложение

### Основной дизайн: разделение ответственности на три уровня

```
Уровень 0  Фиксированная таблица соответствия (константа уровня языка, неизменяемая пользователем)
           + → add    == → equal    [] → index    ? → residual
           │  Встроена во время компиляции, не участвует в выводе типов, не видна пользователю
           ▼
Уровень 1  База диспетчеризации (поиск метода по имени и вызов)  ← повторное использование существующего механизма
           method_bindings["Point.add"]
           ▼
Уровень 2  Контракт интерфейса (для ограничений дженериков)
           Add / Equal / Index / Try …
           Обеспечивает работоспособность ограничения T: Add и служит шлюзом для операторов
```

**Обоснование разделения**:

- **Уровни 0 и 1 делают операторы «работоспособными»**, уровень 2 делает их «поддающимися
  ограничению». Слияние привело бы к тому, что любой метод с именем `add` вызывался бы через `+`, и
  ограничение `T: Add` из RFC-011 оторвалось бы от оператора.
- **Уровень 1 не создаётся заново**: `method_bindings` уже выполняет поиск по ключу `Type.method`
  (fallback-путь после неудачного поиска поля), операторы идут тем же путём.
- **Уровень 2 — это шлюз**: перед допуском оператора **необходимо** убедиться, что тип реализует
  соответствующий интерфейс (см. § «Почему необходимо реализовать интерфейс»).

### Уровень 0: фиксированная таблица соответствия

| Оператор          | Интерфейс                                                  | Метод      | Первая партия |
| ----------------- | ---------------------------------------------------------- | ---------- | ------------- |
| `+`               | `Add`                                                      | `add`      | ✅            |
| `-`               | `Subtract`                                                 | `subtract` | ✅            |
| `*`               | `Multiply`                                                 | `multiply` | ✅            |
| `/`               | `Divide`                                                   | `divide`   | ✅            |
| `%`               | `Modulo`                                                   | `modulo`   | ✅            |
| `==` `!=`         | `Equal`                                                    | `equal`    | ✅            |
| `[]`              | `Index`                                                    | `index`    | ✅            |
| `?`               | `Try`                                                      | `residual` | ✅            |
| `<` `<=` `>` `>=` | — (сохраняем нативные инструкции)                          | —          | ❌            |
| `and` `or`        | — (короткое замыкание — семантика языка, не перегружается) | —          | ❌            |
| 5 побитовых       | —                                                          | —          | ❌            |
| Унарные `-` `!`   | —                                                          | —          | ❌            |

**Имена интерфейсов — полные, без сокращений** (`Multiply`, а не `Mul`): для соответствия основному
тексту RFC-011 `T: Add + Multiply + Zero`, **без изменения уже принятого RFC**.

**`%` использует семантику `Modulo`** (математический остаток, знак результата совпадает с
делителем), а не текущее поведение remainder (`-7 % 3` сейчас возвращает `-1`). Это **намеренное
исправление семантики** — имя прибивает семантику к математическому modulo.

### Уровень 2: определения интерфейсов

#### Арифметические интерфейсы

```yaoxiang
Add: (Self: Type, R: Type) -> Type = {
    add: (self: &Self, other: &R) -> Self
}

Subtract: (Self: Type, R: Type) -> Type = {
    subtract: (self: &Self, other: &R) -> Self
}

Multiply: (Self: Type, R: Type) -> Type = {
    multiply: (self: &Self, other: &R) -> Self
}

Divide: (Self: Type, R: Type) -> Type = {
    divide: (self: &Self, other: &R) -> Self
}

Modulo: (Self: Type, R: Type) -> Type = {
    modulo: (self: &Self, other: &R) -> Self
}
```

`R` — тип правого операнда, допускается различие типов слева и справа (например, `Int + Float`).
Возвращаемое значение фиксировано как `Self` (получатель `&Self` — заимствование, см. RFC-009 о
токенах заимствования и RFC-011a о соглашениях получателя).

#### Интерфейс равенства

```yaoxiang
Equal: (Self: Type, R: Type) -> Type = {
    equal: (self: &Self, other: &R) -> Bool
}
```

**`Equal` неявно требует `Dup`**: семантика `==` — «сравнить два значения», обе стороны должны быть
читаемы. Значение линейного (не `Dup`) типа можно прочитать лишь один раз, оно не может участвовать
в сравнении. RFC-009 уже задал причинную цепочку:

> **Причинность нельзя обратить: заморозка — причина, Dup — следствие.**

Поэтому предпосылка реализации `Equal` — наличие у `Self` атрибута `Dup`; при его отсутствии
компилятор отвергает создание экземпляра `Equal`.

#### Интерфейс индексации

```yaoxiang
Index: (Self: Type, Key: Type, Value: Type) -> Type = {
    index: (self: &Self, key: &Key) -> Value
}
```

**`Value` как параметр типа, а не как член ассоциированного типа**: открытый вопрос из RFC-011a
закрыт решением «ассоциированные типы реализуются через параметризованные интерфейсы»
(`Iterator: (Item: Type) -> Type` — изоморфный прецедент), нет необходимости вводить синтаксис
членов `type`.

**Многопозиционная индексация — через упаковку в кортеж + перегрузку**, без введения интерфейсов с
переменным числом аргументов:

```yaoxiang
// Одномерный контейнер
List(T) создаёт экземпляр Index(List(T), Int, T)                   → arr[0]

// Многомерный контейнер
Grid    создаёт экземпляр Index(Grid, Tuple(Int, Int), Float)       → g[0, 1]
//                    └─ Key — это кортеж

// Две сигнатуры создания экземпляра различаются → сосуществуют по правилам перегрузки RFC-011a
```

#### Интерфейс распространения ошибок

```yaoxiang
Try: (Self: Type, T: Type, E: Type) -> Type = {
    residual: (self: &Self) -> E
}
```

`T` (тип успеха) и `E` (тип ошибки) — параметры типа интерфейса.

**Правила типов для `?`**:

```yaoxiang
// f: () -> Result(T, E)
// Остаток тела функции требует Result(U, E) (тип ошибки должен совпадать)
x = f()?        // x: T, эквивалентно:
                //   match f() {
                //       ok(v)  => v
                //       err(e) => return err(e)
                //   }
```

При несовпадении типа ошибки — ошибка компиляции (соответствующая существующей `E1083`); если тип
возврата внешней функции не является распространяемым — `E1081`; если выражение не реализует `Try` —
заменить формулировку `E1082` (больше не упоминать конкретное имя «Result»).

### Примеры

#### Арифметика и равенство для пользовательских типов

```yaoxiang
Point: Type = {
    x: Float,
    y: Float,
    Add(Point, Point),
    Equal(Point, Point)
}

Point.add: (self: &Point, other: &Point) -> Point =
    Point(self.x + other.x, self.y + other.y)

Point.equal: (self: &Point, other: &Point) -> Bool =
    self.x == other.x and self.y == other.y

main: () -> Void = {
    a = Point(1.0, 2.0)
    b = Point(3.0, 4.0)
    c = a + b                   // Point(4.0, 6.0)
    println(a == b)             // false
    println(a == a)             // true
}
```

#### Индексация пользовательского контейнера

```yaoxiang
Box: (T: Type) -> Type = {
    data: List(T),
    Index(Box(T), Int, T)
}

Box.index: (T: Type)(self: &Box(T), key: &Int) -> T =
    list.get(self.data, key)

main: () -> Void = {
    b = Box([10, 20, 30])
    println(b[1])               // 20
}
```

#### Перенос `Result` в std (цель дизайна)

Когда `Result` реализует `Try`, `?` больше не зависит от жёстко закодированного имени типа:

```yaoxiang
// В std.result (специальная обработка в core больше не нужна)
Result: (T: Type, E: Type) -> Type = {
    ok: (T) -> Result(T, E),
    err: (E) -> Result(T, E),
    Try(Result(T, E), T, E)
}

Result.residual: (T: Type, E: Type)(self: &Result(T, E)) -> E =
    match self {
        ok(_) => abort_invalid_residual(),   // ok-путь не должен приводить к residual
        err(e) => e
    }
}
```

#### Ограничения дженериков наконец-то реализуемы

```yaoxiang
// Пример из RFC-011 теперь можно реализовать
combine: (T: Add + Multiply)(a: T, b: T, c: T) -> T =
    a * b + c
```

### Изменения синтаксиса

**Никакого нового синтаксиса, никаких новых ключевых слов**. Все возможности — комбинация
существующих механизмов:

| Возможность                 | Используемый существующий механизм                                  |
| --------------------------- | ------------------------------------------------------------------- |
| Объявление интерфейса       | RFC-011a Phase 1                                                    |
| Создание экземпляра         | RFC-011a Phase 2 (`Dog: { Animal(Dog) }`)                           |
| Реализация метода           | RFC-011a Phase 3 (внешнее объявление `Point.add`)                   |
| Ассоциированные типы        | RFC-011 §3.1 (параметры типа интерфейса)                            |
| Многопозиционная индексация | Существующий разбор упаковки в кортеж + правила перегрузки RFC-011a |
| Приоритет операторов        | **Фиксирован языком**, не допускает пользовательскую настройку      |

## Детальный дизайн

### Влияние на систему типов

**Новые интерфейсы** (уровень 2): `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
`Try`.

**Использование уже зарегистрированных trait'ов**: `Equal` уже зарегистрирован в `trait_data.rs`, но
**имеет ноль точек потребления** (в настоящее время `==` лишь выполняет `unify` и жёстко возвращает
`Bool`). Этот RFC подключает его как реальный контракт для `==`.

**Предварительное ограничение `Dup`**: при создании экземпляра `Equal` проверяется, является ли
`Self` типом `Dup`. Атрибуты `Dup` / `Linear` выводятся согласно RFC-009 (`&T` замораживает ⇒ Dup;
`&mut T` эксклюзивен ⇒ Linear).

**Разрешение ограничений**: разрешение `T: Add` = проверка, создан ли для `T` экземпляр интерфейса
`Add`. Механизм повторно использует сбор типов на этапе компиляции из RFC-011a, нового солвера не
добавляется.

### Поведение во время выполнения

**Нулевые накладные расходы во время выполнения**: цель вызова для оператора определяется во время
компиляции (статическая диспетчеризация). Для базовых типов (`Int`/`Float`/`String`/`List`)
сохраняется **быстрый путь нативных инструкций**, минуя диспетчеризацию через интерфейс.

Поведение `?` во время выполнения не меняется (распаковка + досрочный возврат), лишь критерий
изменяется с «имя типа == "Result"» на «тип реализует `Try`».

### Изменения в компиляторе

| Компонент                            | Изменение                                                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `typecheck/inference/expressions.rs` | Белый список в `infer_binary` заменяется на двойной путь «нативный быстрый путь + запрос интерфейса»; добавлены запросы интерфейса для `Index` / `Try` |
| Там же (ветка `Try`)                 | Удаление жёсткого кодирования `MonoType::make_result`, замена на запрос экземпляра `Try`                                                               |
| `middle/core/ir_gen.rs`              | Удаление жёсткого кодирования `group: "Result"` в `Expr::Try`; добавление ветви диспетчеризации через интерфейс в `Expr::Index`                        |
| `typecheck/types/trait_data.rs`      | Регистрация экземпляров по умолчанию для 8 интерфейсов (`Int` / `Float` / `String` / `List` и т.д.)                                                    |
| Новое                                | Константа таблицы соответствия уровня 0 + функция запроса «оператор → интерфейс»                                                                       |
| Диагностика                          | Формулировка `E1082` с «requires Result» на «requires Try» (для `E1081`/`E1083` остаётся прежней)                                                      |

### Обратная совместимость

**Операции с базовыми типами не меняются**: `1 + 2`, `"a" + "b"`, `[1] + [2]`, `1 < 2` — все
сохраняют нативный путь, поведение и производительность неизменны.

**Изменение семантики `%`**: `-7 % 3` с `-1` (remainder) на `2` (modulo). Это **намеренное
исправление**, его нужно отметить в инструкциях по миграции; в существующих тестовых материалах нет
случаев зависимости от `%` с отрицательными числами (проверено).

**Позиционное связывание `f[0]` не меняется**: `distance[0]` — встроенная возможность компилятора из
RFC-004, **не проходит через интерфейс `Index`**, не затрагивается.

**`?` прозрачен для существующего кода**: после добавления `Try`-экземпляра для `Result` поведение
всех существующих использований `?` остаётся полностью идентичным.

## Компромиссы

### Преимущества

- **Реализация RFC-011**: `T: Add + Multiply + Zero` переходит с бумаги в реальность, без изменения
  основного текста уже принятого RFC
- **Снятие привязки `Result` к core**: после превращения `?` в интерфейс `Result` можно перенести в
  std, продолжая цель разделения по слоям
- **Исправление наблюдаемого дефекта**: `Point == Point` становится работоспособным, попутно
  исправляется неработоспособность `list.contains` для структур
- **Нулевой новый синтаксис**: полное повторное использование существующих механизмов RFC-011a, без
  затрагивания правил грамматики парсера (соблюдение принципа нулевых изменений синтаксиса из
  RFC-036)
- **Нулевые накладные расходы во время выполнения**: статическая диспетчеризация + нативный быстрый
  путь для базовых типов
- **Пользовательские контейнеры работают**: `Box(T)[0]` меняется с «всегда ошибка» на
  работоспособное

### Недостатки

- **Изменение семантики `%` — ломающее изменение**: несмотря на реальные семантические основания,
  требуются инструкции по миграции
- **`Equal` с неявным `Dup` отвергает часть типов**: значения линейных типов не могут участвовать в
  `==`, что является ценой семантической корректности, но может удивить пользователей — необходимы
  чёткие диагностические сообщения
- **Создание экземпляра интерфейса — явная стоимость**: для каждого оператора нужно написать строку
  создания экземпляра + метод. Синтаксис RFC-011a определяет, что неявный вывод невозможен (ценой
  чего является отсутствие магии в параметре типа `Self`)

## Альтернативы

### Вариант A: только уровень 1 (диспетчеризация по имени метода), без уровня интерфейсов

`+` лишь проверяет наличие метода с именем `add`, не требуя реализации интерфейса `Add`.

**Причина отклонения**: ограничение `T: Add` из RFC-011 оторвётся от оператора — ограничение
проверяет интерфейс, оператор проверяет имя метода, и они могут давать несогласованные ответы. И
невозможно во время компиляции дать точную диагностику для «`+` применён к типу, не поддерживающему
сложение».

### Вариант B: введение синтаксиса конструкторов `Ok(x)` / `Some(x)` для решения проблемы `?`

Не превращать `?` в интерфейс, а добавить к типам-суммам синтаксис конструкторов.

**Причина отклонения**: конфликтует с RFC-010 (уже принят). RFC-010 явно устанавливает
«унифицированное использование record type для выражения типов-сумм, **без необходимости в двух
наборах синтаксиса**» и явно отвергает синтаксис `|`. Введение конструкторов — это введение второго
способа выражения. И это решает только `?`, но не решает `Point == Point` и индексацию
пользовательских контейнеров.

### Вариант C: операторы сравнения также в первую партию как интерфейсы (с введением `Ordering`)

`<` `<=` `>` `>=` идут через интерфейс `Compare`, возвращающий трёхзначный `Ordering`.

**Причина отклонения**: `<` в YaoXiang уже является **инструкцией первого класса в IR**
(`Instruction::Lt/Le/Gt/Ge`); превращение в интерфейс заставит базовые типы идти обходным путём. А
введение `Ordering` потянет за собой целый набор вопросов — собственно сравнение/сортировка самого
`Ordering`, `PartialOrd` vs `Ord` для `NaN` чисел с плавающей точкой и т.д., что соответствует
объёму отдельного RFC. Наблюдаемые потребности (`Point == Point`, `list.contains`) **требуют только
`Equal`**.

### Вариант D: сокращённые имена операторов (интерфейс `Add`, но метод называется `add`, а интерфейс — `Mul`)

**Причина отклонения**: в основном тексте RFC-011 уже записано `T: Add + Multiply + Zero`,
использование сокращений потребует изменения уже принятого RFC.

## Стратегия реализации

### Зависимости

| Зависимость                                  | Статус           | Влияние на данный RFC                                                                                              |
| -------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| Механизм интерфейсов RFC-011a Phase 1–3      | ✅ Реализован    | Фундамент уровня 2 (проверено в работе)                                                                            |
| Путь конструирования через record из RFC-010 | ❌ Не реализован | **Сторона конструирования для `?`** (если нельзя создать значение `Result`, нельзя полностью протестировать `Try`) |
| Деструктуризация вариантов из RFC-039        | ❌ На бумаге     | Запись `match` в `Result.residual`                                                                                 |
| Вывод `Dup`/`Linear` из RFC-009              | Частично         | Проверка предварительного ограничения для `Equal`                                                                  |

### По фазам

Разделение по **зависимостям интерфейсов** (ограничение дизайна, а не сроки) на две группы:

**Фаза 1 — без зависимости от RFC-010/039**:

- Таблица соответствия уровня 0 + подключение диспетчеризации уровня 1
- Семь интерфейсов: `Add` `Subtract` `Multiply` `Divide` `Modulo` `Equal` `Index`
- Предварительное ограничение `Equal` ⇒ `Dup`
- Сохранение нативного быстрого пути для базовых типов
- **Результат**: `Point + Point`, `Point == Point`, `Box(T)[0]` — всё становится работоспособным

**Фаза 2 — зависит от RFC-010 / RFC-039**:

- Интерфейс `Try` + превращение `?` в интерфейс
- Перенос `Result` из core в std
- **Причина блокировки**: требуется возможность создавать значения `Result` (RFC-010) и
  деструктурировать их (RFC-039)

### Риски

| Риск                                                                     | Смягчение                                                                                                                |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Изменение семантики `%` ломает существующий код пользователей            | Инструкции по миграции + подтверждённое отсутствие зависимости от `%` с отрицательными числами в тестовых материалах     |
| Явная стоимость создания экземпляра интерфейса раздражает пользователей  | Диагностическое сообщение с подсказкой «нужно реализовать интерфейс X» и примером создания экземпляра                    |
| Несогласованность двойного пути (нативный + интерфейс) для базовых типов | Контроль: `Int` и т.д. реализуют интерфейсы, но семантика их методов должна совпадать с нативными инструкциями           |
| Шлюз уровня 2 приводит к ошибкам компиляции в существующем коде          | У `Equal` сейчас ноль точек потребления, после подключения затрагивается только тот код, который и раньше выдавал ошибки |

## Согласование с другими RFC

Данный RFC позиционируется как **инициатор потребности со стороны потребителя**, требуется
синхронное обновление следующих RFC для согласованности (правки разрешены):

| RFC                    | Что нужно обновить                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **RFC-011** (принят)   | В § «Ограничения» указать, что `Add` / `Multiply` и т.д. определяются и реализуются в RFC-011b                            |
| **RFC-010** (принят)   | Уточнить требования к реализации «поле record'а = конструктор» — это предпосылка для фазы 2 `?`                           |
| **RFC-039** (черновик) | Конструирование и деструктуризация должны быть парными; обработка исчерпывающей проверки для множества вариантов из `std` |
| **RFC-009** (принят)   | Перекрёстная ссылка на `Equal` ⇒ предварительное `Dup` в § «Атрибуты типов»                                               |
