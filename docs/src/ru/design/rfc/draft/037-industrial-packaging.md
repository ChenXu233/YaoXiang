# RFC-037: Промышленная схема дистрибуции — упаковка компилятора/тулчейна на основе cargo-dist

> Настоящий RFC дополняет [RFC-014b: Система сборки и дистрибуция бинарных файлов](../review/014b-build-system.md).
> RFC-014b определяет, как **менеджер пакетов YaoXiang** собирает и распространяет сторонние пакеты;
> настоящий RFC определяет, как **сам компилятор/тулчейн YaoXiang** упаковывается и распространяется.

## Резюме

Замена существующей логики сборки/упаковки CI, написанной вручную, на `cargo-dist` (стандартный инструмент дистрибуции бинарных файлов в экосистеме Rust) для автоматизированного кроссплатформенного релиза. Решает проблемы отсутствия `libz3.dll`, неупакованных файлов интерфейсов стандартной библиотеки, беспорядочной структуры каталогов и повторного сопровождения CI-скриптов.

## Мотивация

### Зачем нужна эта возможность?

Пользователи, скачивающие YaoXiang, должны иметь возможность работать **из коробки**, без каких-либо дополнительных шагов.

### Текущие проблемы

#### Проблема 1: Пользователи Windows не могут запустить после скачивания

Текущий релиз загружает только `yaoxiang.exe`, но `libz3.dll` не включён в пакет. Двойной клик в Windows приводит к ошибке:

```
The code execution cannot proceed because libz3.dll was not found.
```

Это **блокирующий баг** — пользователь не может пройти даже первый шаг.

#### Проблема 2: Артефакт релиза содержит только один exe-файл

```
yaoxiang-v0.7.10-x86_64-pc-windows-msvc.zip
└── yaoxiang.exe
```

Файлы интерфейсов стандартной библиотеки (`.yx` файлы, необходимые LSP) не включены в дистрибутив, пользователю нужно выполнить `yaoxiang package init` для их генерации. Промышленный подход должен быть таким:

```
yaoxiang-0.7.10-x86_64-pc-windows-msvc.zip
├── bin/
│   ├── yaoxiang.exe
│   └── libz3.dll
└── lib/
    └── std/
        ├── io.yx
        ├── math.yx
        ├── ...
        └── mod.yx
```

#### Проблема 3: Повторное сопровождение CI-скриптов, написанных вручную

В настоящее время поддерживаются 3 конвейера сборки:

| Файл | Ответственность | Строк |
|------|----------------|------|
| `_build-platforms.yml` | Кроссплатформенная сборка (Linux/macOS/Windows) | ~250 строк |
| `release.yml` | Процесс выпуска версии | ~170 строк |
| `nightly.yml` | Ежедневная сборка | ~170 строк |

**Итого ~600 строк YAML, написанных вручную.** Большая часть этих скриптов дублируется (установка Rust → кэширование → сборка → переименование → загрузка), для каждой платформы приходится писать отдельно. `cargo-dist` одной командой генерирует эквивалентный конвейер.

#### Проблема 4: Жёстко зашитый номер версии в Inno Setup

В `setup.iss` поле `MyAppVersion` жёстко прописано как `0.7.0`, при сборке подставляется через `sed`. Рано или поздно это приведёт к сбою.

#### Проблема 5: Размытие границ с RFC-014b

RFC-014b определяет «механизм сборки и дистрибуции пакетов YaoXiang» (т.е. конфигурации `[build]` и `[binaries]` в `yaoxiang.toml`), но **не охватывает «как публикуется сам компилятор YaoXiang»**. Настоящий RFC заполняет этот пробел.

## Предложение

### Основной дизайн

Использование **cargo-dist** в качестве релизного конвейера в сочетании с пользовательскими post-build скриптами для обработки Z3 DLL и файлов интерфейсов стандартной библиотеки.

```
cargo-dist отвечает за:
  ├── Кроссплатформенную сборку (6 платформ)
  ├── Генерацию tar.gz/zip архивов
  ├── Генерацию установочных скриптов (shell/powershell)
  ├── Генерацию Windows MSI установщика
  ├── Автоматический выпуск GitHub Release
  └── Автоматическую генерацию changelog

build.rs продолжает отвечать за:
  └── Загрузку/линковку Z3 (существующая логика, требует лишь небольшой корректировки)

Пользовательские скрипты отвечают за:
  ├── Копирование libz3.dll в каталог упаковки после сборки
  └── Предварительную генерацию .yx файлов интерфейсов стандартной библиотеки
```

### Структура каталогов релиза

Архив релиза для каждой платформы:

```
yaoxiang-{version}-{target}.tar.gz / .zip
├── bin/
│   ├── yaoxiang                      # или yaoxiang.exe
│   └── libz3.dll                     # только Windows, на других платформах статическая линковка
├── lib/
│   └── std/                          # Предварительно сгенерированные файлы интерфейсов стандартной библиотеки
│       ├── io.yx
│       ├── math.yx
│       ├── string.yx
│       ├── ...
│       └── mod.yx
└── README.md                         # Краткая инструкция по установке
```

### Поддержка платформ

| Платформа | target triple | Описание |
|------|-------------|------|
| Linux x86_64 | `x86_64-unknown-linux-gnu` | Основная платформа |
| Linux ARM64 | `aarch64-unknown-linux-gnu` | Кросс-компиляция в CI |
| macOS x86_64 | `x86_64-apple-darwin` | Intel Mac |
| macOS ARM64 | `aarch64-apple-darwin` | Apple Silicon |
| Windows x86_64 | `x86_64-pc-windows-msvc` | Основная платформа |
| Windows ARM64 | `aarch64-pc-windows-msvc` | Опционально, в дальнейшем |

### Стратегия дистрибуции Z3

| Платформа | Стратегия | Причина |
|------|------|------|
| Linux | Статическая линковка `libz3.a` | Уже есть, сохраняем |
| macOS | Статическая линковка `libz3.a` | Уже есть, сохраняем |
| Windows | Упаковка `libz3.dll` | Официальные Windows-сборки Z3 доступны только в виде DLL |
| wasm32 | Статическая линковка `libz3.a` | Уже есть, сохраняем |

**Windows `libz3.dll` загружается build.rs во время сборки в каталог `.z3/`, затем упаковывается в архив механизмом `extra-artifacts` cargo-dist.**

Долгосрочная цель: самостоятельно компилировать статическую библиотеку Z3 для Windows (`-DZ3_BUILD_LIBZ3_SHARED=OFF`) для достижения однофайловой дистрибуции со статической линковкой на всех платформах.

### Поддержка установщиков

| Установщик | Поддержка | Описание |
|--------|------|------|
| tar.gz / zip | ✅ По умолчанию | Все платформы |
| shell установочный скрипт | ✅ Встроен в cargo-dist | Unix-платформы |
| powershell установочный скрипт | ✅ Встроен в cargo-dist | Windows |
| Homebrew formula | ✅ Встроен в cargo-dist | macOS |
| Windows MSI | ✅ Встроен в cargo-dist | Замена Inno Setup |
| Inno Setup | ❌ Устарел | Миграция на MSI из cargo-dist |

## Детальный дизайн

### Конфигурация cargo-dist

Создание `dist-workspace.toml` в корне проекта:

```toml
[workspace]
# Указывает на Cargo workspace, все binary пакеты обнаруживаются автоматически
members = ["cargo:."]

[dist]
# Артефакты сборки
package-libraries = ["cdylib"]

# Установщики
installers = [
    "shell",           # Unix shell установочный скрипт
    "powershell",      # Windows powershell установочный скрипт
    "homebrew",        # macOS Homebrew
    "msi",             # Windows MSI установщик
]

# Скрипты дополнительной обработки после сборки
extra-artifacts = [
    "scripts/build/package-z3.sh",   # Копирование libz3.dll + файлов интерфейсов стандартной библиотеки
]

# Конфигурация CI
ci = "github"
ci.github.create-release = true
ci.github.pr-run-mode = "plan"
```

### Скрипт пост-обработки сборки

`scripts/build/package-z3.sh` (кроссплатформенный, выполняется после сборки cargo-dist):

```bash
#!/bin/bash
# После сборки cargo-dist копирует libz3.dll и файлы интерфейсов стандартной библиотеки в каталог упаковки

set -euo pipefail

# 1. Копирование Z3 DLL (только Windows)
if [ "$CARGO_DIST_TARGET" = "x86_64-pc-windows-msvc" ]; then
    Z3_DIR=".z3/z3-4.16.0-x64-win"
    cp "$Z3_DIR/bin/libz3.dll" "$DIST_DIR/bin/"
fi

# 2. Генерация файлов интерфейсов стандартной библиотеки
yaoxiang package gen-std-interfaces --out-dir "$DIST_DIR/lib/std/"
```

### Изменения в конвейере CI

#### До миграции (текущее состояние):

```
release.yml (170 строк) ──→ _build-platforms.yml (250 строк) ──→ сборка → загрузка
                  └──→ wasm сборка
                  └──→ аудит безопасности
                  └──→ тестирование
                  └──→ релиз

nightly.yml (170 строк) ──→ то же самое (дублирование)
```

#### После миграции:

```
release.yml, сгенерированный cargo-dist (~100 строк, авто-сопровождение)
  └──→ Параллельная сборка 6 платформ
  └──→ Генерация архивов + установочных скриптов
  └──→ Создание GitHub Release
  └──→ Загрузка в Homebrew / npm

pr.yml, сгенерированный cargo-dist (~50 строк, авто-сопровождение)
  └──→ Запуск dist plan при PR
```

### Генерация файлов интерфейсов стандартной библиотеки

Текущий `src/std/gen_interfaces.rs` уже реализует функциональность генерации `.yx` файлов интерфейсов (`write_interfaces_to_dir`), команда `package init` также вызывает её.

Требуется лишь:

1. Добавить новую подкоманду `yaoxiang package gen-std-interfaces` в `main.rs` (или отдельный скрипт)
2. Вызвать эту команду в скрипте упаковки для генерации в `lib/std/`

### Устаревший CI, написанный вручную

После завершения миграции удалить следующие файлы:

| Файл | Замена |
|------|------|
| `.github/workflows/_build-platforms.yml` | Автогенерация cargo-dist |
| `.github/workflows/release.yml` | Автогенерация cargo-dist |
| `.github/workflows/nightly.yml` | Триггер по расписанию cargo-dist |
| `scripts/build/setup.iss` | MSI установщик cargo-dist |
| `scripts/build/ChineseSimplified.isl` | То же самое |

## Компромиссы

### Преимущества

- **Работа из коробки** — пользователь скачивает архив, распаковывает и сразу запускает, без проблем с отсутствующими DLL
- **Снижение затрат на сопровождение** — удаление ~600 строк YAML CI, написанных вручную, cargo-dist сопровождает автоматически
- **Стандартизация** — отраслевой стандартный инструмент, проверенный сотнями проектов
- **Кроссплатформенная консистентность** — единый конвейер для 6 платформ
- **Автоматический changelog** — встроенная генерация changelog и описания релиза
- **Покрытие установщиками** — полная поддержка shell/powershell/homebrew/msi

### Недостатки

- **Изучение конфигурации cargo-dist** — команде необходимо изучить новый инструмент
- **Затраты на сопровождение пользовательской обработки** — скрипты для Z3 DLL и файлов интерфейсов стандартной библиотеки требуют сопровождения
- **Итерации версий cargo-dist** — необходимо следить за обновлениями upstream
- **Поддержка Windows ARM64** — cargo-dist поддерживает по умолчанию, но Z3 может не иметь предкомпилированной ARM64 DLL

### Связь с RFC-014b

| | RFC-014b | RFC-037 |
|--|----------|---------|
| **Область** | Сборка и дистрибуция сторонних пакетов | Упаковка и дистрибуция самого компилятора |
| **Инструмент** | `yaoxiang build` / `yaoxiang publish` | `cargo-dist` |
| **Артефакт** | FFI-библиотеки сторонних пакетов | Компилятор + стандартная библиотека + тулчейн |
| **Взаимоисключение** | Нет, дополняют | Нет, дополняют |

## Альтернативы

| Альтернатива | Почему не выбрана |
|------|-----------|
| **Продолжать писать CI вручную** | Уже написано ~600 строк, повторяющийся труд, легко пропустить DLL |
| **Написать свой инструмент упаковки** | Не изобретайте велосипед, cargo-dist уже зрелый |
| **Только tar.gz без установщиков** | Пользователям нужны более удобные способы установки (Homebrew/MSI) |
| **Дистрибуция через Docker** | Компилятору и языковому тулчейну нужны нативные бинарные файлы, это не сценарий для контейнеров |
| **Полная статическая линковка Z3** | Идеальное решение, но статическая компиляция Z3 для Windows требует дополнительных шагов CI, можно оптимизировать позже |

## Стратегия реализации

### Фаза 1: Базовая миграция (высокий приоритет)

1. Исследовать и подтвердить последнюю версию cargo-dist и формат конфигурации
2. Установить cargo-dist, выполнить `dist init` для генерации начальной конфигурации
3. Сконфигурировать `dist-workspace.toml`, указать целевые платформы
4. Использовать crate `cc` для замены логики внешней загрузки Z3 в build.rs (опционально)

### Фаза 2: Пользовательская упаковка (средний приоритет)

1. Написать скрипт пост-обработки сборки `package-z3.sh`
2. Добавить подкоманду `gen-std-interfaces` в `main.rs`
3. Вызвать команду генерации файлов интерфейсов стандартной библиотеки в скрипте упаковки
4. Проверить корректность структуры сгенерированного архива

### Фаза 3: Устаревание старого CI (высокий приоритет)

1. Интегрировать конвейер cargo-dist в `release.yml`
2. Параллельно запустить старый и новый CI, сравнить консистентность артефактов
3. После подтверждения корректности удалить старые файлы CI
4. Удалить `setup.iss` и связанные скрипты

### Фаза 4: Оптимизация (низкий приоритет)

1. Исследовать осуществимость статической компиляции Z3 для Windows
2. Добавить автоматическую публикацию Homebrew formula
3. Добавить MSI установщик
4. Рассмотреть поддержку Windows ARM64

### Зависимости

- Нет зависимостей от внешних инструментов (cargo-dist устанавливается через cargo install)
- Требуется GitHub Actions для запуска CI
- Требуется учётная запись мейнтейнера Homebrew (опционально)

### Риски

- **Обновление версии cargo-dist**: формат конфигурации может измениться, необходимо следить за changelog
- **Изменения официальных релизов Z3**: расположение или формат предкомпилированных пакетов Z3 может измениться
- **Статическая линковка в Windows**: статическая библиотека Z3 на Windows может потребовать дополнительной обработки (например, зависимость от среды исполнения C++)

## Открытые вопросы

- [ ] Осуществимость статической линковки Z3 на Windows? Необходимо проверить поведение `-DZ3_BUILD_LIBZ3_SHARED=OFF` под MSVC на практике
- [ ] Конкретное именование и дизайн интерфейса подкоманды `gen-std-interfaces`?
- [ ] Сохранять ли Inno Setup установщик как дополнение к MSI? Китайские пользователи могут быть более привычны к exe-мастеру установки
- [ ] Поддерживает ли `extra-artifacts` в cargo-dist кроссплатформенное условное выполнение (например, копирование DLL только в Windows)?
- [ ] Есть ли гарантия обратной совместимости для файлов интерфейсов стандартной библиотеки? Нужно ли их публиковать вместе с версией компилятора?
