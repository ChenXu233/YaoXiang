# RFC-037: Промышленная схема распространения — упаковка компилятора/тулчейна на основе cargo-dist

> Данный RFC дополняет [RFC-014b: Система сборки и распространения бинарных файлов](../review/014b-build-system.md).
> RFC-014b определяет, как **менеджер пакетов YaoXiang** собирает и распространяет сторонние пакеты;
> данный RFC определяет, как **сам компилятор/тулчейн YaoXiang** упаковывается и распространяется.

## Резюме

Замена существующей вручную написанной логики CI-сборки/упаковки на `cargo-dist` (стандартный инструмент распространения бинарных файлов в экосистеме Rust) для автоматизации кросс-платформенных релизов. Решает проблемы отсутствия `libz3.dll`, неупакованных файлов интерфейсов стандартной библиотеки, беспорядочной структуры каталогов, дублирующего сопровождения CI-скриптов и т. д.

## Мотивация

### Зачем нужна эта функциональность?

Пользователи, скачивающие YaoXiang, должны иметь возможность **сразу приступить к работе** без каких-либо дополнительных шагов.

### Текущие проблемы

#### Проблема 1: Пользователи Windows не могут запустить после скачивания

Текущий релиз загружает только `yaoxiang.exe`, но `libz3.dll` не упаковывается. Двойной клик в Windows приводит к ошибке:

```
The code execution cannot proceed because libz3.dll was not found.
```

Это **критический баг** — пользователь не может пройти даже первый шаг.

#### Проблема 2: Артефакт релиза — только одиночный exe-файл

```
yaoxiang-v0.7.10-x86_64-pc-windows-msvc.zip
└── yaoxiang.exe
```

Файлы интерфейсов стандартной библиотеки (файлы `.yx`, необходимые LSP) не включены в дистрибутив. Пользователю нужно запустить `yaoxiang package init`, чтобы их сгенерировать. Промышленный подход — поставлять стандартную библиотеку вместе с дистрибутивом.

#### Проблема 3: Дублирование сопровождения CI-скриптов, написанных вручную

В настоящее время поддерживается 4 конвейера сборки:

| Файл | Назначение | Кол-во строк |
|------|------|------|
| `_build-platforms.yml` | Кросс-платформенная сборка | ~255 строк |
| `release.yml` | Выпуск версий | ~176 строк |
| `nightly.yml` | Ежедневная сборка | ~145 строк |
| `_build-wasm.yml` | Сборка Wasm | ~75 строк |
| `scripts/build/setup.iss` | Inno Setup установщик | ~250 строк |
| **Итого** | | **~900 строк** |

Большая часть — дублирование (установка Rust → кеширование → сборка → переименование → загрузка), и для каждой платформы пишется заново. `cargo-dist` одной командой генерирует эквивалентный конвейер.

#### Проблема 4: Жёстко зашитый номер версии в Inno Setup

В `setup.iss` поле `MyAppVersion` жёстко прописано как `0.7.0`, при сборке подменяется через `sed`. Рано или поздно это приведёт к сбою.

#### Проблема 5: Размытие границ с RFC-014b

RFC-014b определяет «механизм сборки и распространения пакетов YaoXiang» (т. е. конфигурации `[build]` и `[binaries]` в `yaoxiang.toml`), но **не покрывает вопрос «как публикуется сам компилятор YaoXiang»**. Данный RFC заполняет этот пробел.

## Предложение

### Основная архитектура

Использование **cargo-dist** в качестве скелета конвейера релиза, совместно с кастомными post-build скриптами для обработки структуры пакета и дополнительных файлов.

```
Обязанности cargo-dist:
  ├── Кросс-платформенная компиляция (6 таргетов)
  ├── Генерация CI-конвейера (заменяет ~900 строк YAML, написанных вручную)
  ├── Генерация установщиков (MSI / shell / powershell / homebrew)
  ├── Публикация npm (@yaoxiang/cli — wrapper для скачивания бинарников)
  ├── Контрольные суммы + подписи
  └── Загрузка в GitHub Release

build.rs продолжает отвечать за:
  └── Скачивание/линковку Z3 (существующая логика, изменена на полную динамическую линковку)

Кастомный скрипт YaoXiang (package-dist.sh) отвечает за:
  ├── Реорганизацию структуры zip после сборки (bin/ + lib/)
  ├── Включение общих библиотек (libz3.so / dylib / dll)
  └── Предварительную генерацию .yx файлов интерфейсов стандартной библиотеки
```

### Структура каталога релиза

Каждый архив релиза для платформы реорганизуется скриптом `package-dist.sh` после сборки cargo-dist:

```
yaoxiang-{version}-{target}.tar.gz / .zip
├── bin/
│   ├── yaoxiang                      # или yaoxiang.exe
│   └── libz3.so / libz3.dylib / libz3.dll
├── lib/
│   └── yaoxiang/
│       └── std/                      # Предварительно сгенерированные файлы интерфейсов стандартной библиотеки
│           ├── io.yx
│           ├── math.yx
│           ├── string.yx
│           ├── ...
│           └── mod.yx
├── README.md
└── LICENSE
```

Стандартный zip cargo-dist — плоский (бинарник + автоматически включённые README/LICENSE в корневом каталоге).
Это не проблема — чёткое разделение: cargo-dist отвечает за компиляцию + CI + установщики, YaoXiang использует 50-строчный `package-dist.sh` для структуры zip.

### Поддержка платформ

| Платформа | target triple | Описание |
|------|-------------|------|
| Linux x86_64 | `x86_64-unknown-linux-gnu` | Основная платформа |
| Linux ARM64 | `aarch64-unknown-linux-gnu` | Кросс-компиляция в CI |
| macOS x86_64 | `x86_64-apple-darwin` | Intel Mac |
| macOS ARM64 | `aarch64-apple-darwin` | Apple Silicon |
| Windows x86_64 | `x86_64-pc-windows-msvc` | Основная платформа |

Windows ARM64 временно не поддерживается (у Z3 нет официальных прекомпилированных пакетов для ARM64).

### Стратегия распространения Z3

**Единообразный переход на полную динамическую линковку на всех платформах.**

| Платформа | Изменение | Артефакт |
|------|------|------|
| Linux | **Была статической → стала динамической** | `libz3.so` |
| macOS | **Была статической → стала динамической** | `libz3.dylib` |
| Windows | Без изменений | `libz3.dll` |
| wasm32 | Без изменений (статическая линковка) | Встроенный `.a` |

Обоснование:
- **Единообразие** — три платформы ведут себя одинаково, без спецслучаев
- **Это внешняя библиотека, и её следует распространять как общую**. Python (`python3.dll`+`DLLs/lib*.dll`), Node (`node`+`lib/`) делают именно так
- **Пользователю не нужно ждать новой версии компилятора для обновления Z3** — достаточно заменить `.so`/`.dylib`/`.dll`
- **Меньший размер бинарника** — Z3 немаленький, статическая линковка раздувает exe на несколько мегабайт

Соответствующее изменение в `build.rs`:

```rust
// Единая динамическая линковка
fn link_z3(z3_dir: &Path) {
    println!("cargo:rustc-link-lib=z3");     // Больше нет разделения Windows/не-Windows
    // Линковка стандартной библиотеки C++ остаётся без изменений
    let cxx = if target_os == "macos" { "c++" } else { "stdc++" };
    println!("cargo:rustc-link-lib={}", cxx);
}
```

**«Полная статическая линковка на всех платформах» больше не является целью.** Это не устранение особого случая, а устранение правильной ситуации неправильным способом. Общая библиотека — нормальный способ распространения внешних библиотек.

### Поддержка установщиков

| Установщик | Статус | Описание |
|--------|------|------|
| zip / tar.gz | ✅ По умолчанию | Все платформы, ручная загрузка |
| shell-скрипт | ✅ cargo-dist | Unix: `curl ... \| sh` |
| powershell-скрипт | ✅ cargo-dist | Windows: `irm ... \| iex` |
| Homebrew formula | ✅ cargo-dist | macOS: `brew install yaoxiang` |
| Windows MSI | ✅ cargo-dist | На базе WiX, основной Windows-установщик |
| **Inno Setup** | **✅ Сохраняется как вспомогательный** | Резерв для пользователей из Китая, не удаляется |

**Причины сохранения Inno Setup:**
- Пользователи Windows из Китая привыкли к exe-мастеру установки (далее → далее → готово)
- MSI блокируется в некоторых корпоративных/школьных сетях
- Затраты на сопровождение дополнительного `setup.iss` значительно меньше, чем потеря части пользователей

### Генерация файлов интерфейсов стандартной библиотеки

Имя подкоманды: **`yaoxiang package gen-std`** (в рамках существующей системы `package init`/`add`/`install`)

Текущий `src/std/gen_interfaces.rs` уже содержит полную реализацию (`generate_all_interfaces()`, `write_interfaces_to_dir()`), нужно лишь добавить точку входа подкоманды в `main.rs`, а затем вызвать её в `package-dist.sh`:

```bash
yaoxiang package gen-std --out-dir "$PKG_ROOT/lib/yaoxiang/std/"
```

### Сборка Wasm

**Остаётся независимой, не переносится в cargo-dist.**

cargo-dist отвечает за «доставку компилятора пользователю», Wasm — за «встраивание онлайн-playground в сайт документации» — два совершенно разных артефакта.

| Аспект | Подход |
|------|------|
| Инструмент сборки | Остаётся `wasm-pack build` |
| CI workflow | Сохраняется независимый job `_build-wasm.yml` |
| Триггер | Параллельно с push релиза, как параллельный независимый job |
| Цель публикации | `docs/public/wasm/` → GitHub Pages |

### Публикация npm

Два разных npm-пакета, независимых друг от друга:

| Пакет | Содержимое | Инструмент | Статус |
|----|------|------|------|
| `@yaoxiang/cli` | Скачивание CLI-бинарника (wrapper) | Генерируется cargo-dist нативно | Готов из коробки с конфигурацией cargo-dist |
| `@yaoxiang/playground` | wasm-библиотека (JS + .wasm) | wasm-pack + `npm publish` | Опционально, в настоящее время только для docs |

Они не конфликтуют, имена также не конфликтуют.

### Nightly-релизы

cargo-dist не имеет нативной поддержки nightly ([#1143](https://github.com/axodotdev/cargo-dist/issues/1143), всё ещё открытый feature request).

**Сохраняется существующая схема cron + tag**, часть сборки заменяется на cargo-dist:

```yaml
# nightly.yml (после миграции, около 50 строк)
on: schedule: "17 22 * * *"
jobs:
  build:
    # Переиспользование возможностей сборки cargo-dist, но без его release-процесса
    uses: ./.github/workflows/release.yml  # job сборки, сгенерированный cargo-dist
  publish:
    # По аналогии с существующим: тег nightly → перезапись GitHub Pre-release
```

### Конфигурация cargo-dist (черновик)

Базовая конфигурация, генерируемая `cargo dist init`, ожидаемое ядро:

```toml
[workspace]
members = ["cargo:."]

[dist]
targets = [
  "x86_64-unknown-linux-gnu",
  "aarch64-unknown-linux-gnu",
  "x86_64-apple-darwin",
  "aarch64-apple-darwin",
  "x86_64-pc-windows-msvc",
]
installers = [
  "shell",
  "powershell",
  "homebrew",
  "msi",
]
```

Конкретные параметры конфигурации определяются фактическим результатом `cargo dist init`.

### package-dist.sh (черновик)

```bash
#!/bin/bash
# Выполняется после сборки cargo-dist, реорганизует структуру дистрибутива
# Вызывается через extra-artifacts cargo-dist или как отдельный шаг CI
set -euo pipefail

VERSION="$1"
TARGET="$2"
DIST_DIR="target/distrib"
PKG_ROOT="$DIST_DIR/yaoxiang-$VERSION-$TARGET"

mkdir -p "$PKG_ROOT/bin" "$PKG_ROOT/lib/yaoxiang/std"

# бинарник
mv "$DIST_DIR/yaoxiang" "$PKG_ROOT/bin/"

# Общие библиотеки
Z3_DIR=".z3/z3-4.16.0-..."
case "$TARGET" in
  *windows*)   cp "$Z3_DIR/bin/libz3.dll"   "$PKG_ROOT/bin/" ;;
  *linux*)     cp "$Z3_DIR/lib/libz3.so"    "$PKG_ROOT/bin/" ;;
  *apple*)     cp "$Z3_DIR/lib/libz3.dylib" "$PKG_ROOT/bin/" ;;
esac

# Файлы интерфейсов стандартной библиотеки
yaoxiang package gen-std --out-dir "$PKG_ROOT/lib/yaoxiang/std/"

# README + LICENSE
cp README.md LICENSE "$PKG_ROOT/"

# Переупаковка
cd "$DIST_DIR"
tar czf "yaoxiang-$VERSION-$TARGET.tar.gz" "yaoxiang-$VERSION-$TARGET"
```

### Генерация файлов интерфейсов стандартной библиотеки

Текущий `src/std/gen_interfaces.rs` уже реализует функциональность генерации `.yx` файлов интерфейсов (`write_interfaces_to_dir`), команда `package init` также вызывает её.

Требуется лишь добавить точку входа подкоманды в `main.rs`, а затем вызвать её в скрипте упаковки.

### Устаревший CI, написанный вручную

После завершения миграции удаляются следующие файлы:

| Файл | Кол-во строк | Замена |
|------|------|------|
| `.github/workflows/_build-platforms.yml` | 255 | Автогенерация cargo-dist |
| `.github/workflows/release.yml` | 176 | Автогенерация cargo-dist |
| `.github/workflows/nightly.yml` | 145 | cargo-dist для сборки + сохранение логики публикации |
| `scripts/build/setup.iss` | ~250 | **Сохраняется** (для Китая) |
| **Итого удалено** | **~600 строк** | |

Сохраняются:
- `ci.yml` (ежедневный fmt + clippy + test + MSRV, не относится к процессу релиза)
- `nightly.yml` (логика публикации сохраняется)
- `_build-wasm.yml` (независимый конвейер сборки)
- `_build-z3-wasm.yml` (Z3 для wasm)
- `setup.iss` (вспомогательный установщик для Китая)
- `docs-deploy.yml` (деплой документации)

## Компромиссы

### Преимущества

- **Готовность к использованию из коробки** — пользователь скачивает, распаковывает и сразу запускает, без проблем с отсутствующими DLL
- **Снижение затрат на сопровождение** — удаление ~600 строк YAML, написанных вручную, cargo-dist поддерживается автоматически
- **Стандартизация** — отраслевой стандартный инструмент, проверенный сотнями проектов
- **Кросс-платформенное единообразие** — динамическая линковка на всех платформах, единое поведение
- **Покрытие установщиками** — полная поддержка shell/powershell/homebrew/msi/inno setup

### Недостатки

- **Необходимо изучить конфигурацию cargo-dist** — команде нужно освоить новый инструмент
- **Затраты на сопровождение кастомного скрипта упаковки** — скрипт для структуры пакета и файлов интерфейсов стандартной библиотеки требует сопровождения
- **Итерации версий cargo-dist** — необходимо следить за изменениями upstream
- **Отсутствие нативного nightly в cargo-dist** — часть логики nightly-релизов всё ещё пишется вручную

### Связь с RFC-014b

| | RFC-014b | RFC-037 |
|--|----------|---------|
| **Область** | Сборка и распространение сторонних пакетов | Упаковка и распространение самого компилятора |
| **Инструмент** | `yaoxiang build` / `yaoxiang publish` | `cargo-dist` |
| **Артефакт** | FFI-библиотеки сторонних пакетов | Компилятор + стандартная библиотека + тулчейн |
| **Взаимоисключение** | Нет, дополняют друг друга | Нет, дополняют друг друга |

## Альтернативы

| Альтернатива | Почему не выбрана |
|------|-----------|
| **Продолжить написание CI вручную** | Уже написано ~900 строк, дублирующийся труд, легко упустить DLL |
| **Написать собственный инструмент упаковки** | Не нужно изобретать велосипед, cargo-dist уже зрелый |
| **Использовать только tar.gz без установщиков** | Пользователям нужны более дружелюбные способы установки (Homebrew/MSI) |
| **Распространение через Docker** | Компилятор и языковой тулчейн требуют нативных бинарников, это не сценарий контейнеров |
| **Полная статическая линковка Z3** | Внешние библиотеки нормально распространять как общие, не стремимся к статике |
| **Удаление Inno Setup** | У пользователей из Китая другие привычки, затраты на сохранение минимальны |

## Стратегия реализации

### Этап 1: Изменение build.rs + подкоманда gen-std (P0)

1. Изменить `build.rs`: единая динамическая линковка на всех платформах, расширение `copy_dll()` до `copy_shared_lib()`
2. Добавить подкоманду `yaoxiang package gen-std` в `main.rs` (переиспользование `gen_interfaces.rs`)

### Этап 2: Подключение cargo-dist (P0)

1. Запустить `cargo dist init` для генерации начальной конфигурации
2. Написать скрипт упаковки `package-dist.sh`
3. Интеграция в `release.yml`: сборка cargo-dist → реорганизация `package-dist.sh` → загрузка
4. Проверка корректности структуры и содержимого сгенерированных архивов

### Этап 3: Вывод из эксплуатации старого CI (P1)

1. Параллельный запуск старого и нового CI, сравнение артефактов
2. После подтверждения корректности удалить `_build-platforms.yml`
3. Упростить `nightly.yml` (часть сборки заменить на cargo-dist)
4. Убедиться, что `setup.iss` всё ещё работает

### Этап 4: Включение установщиков (P2)

1. Настройка автоматической публикации Homebrew tap
2. Настройка генерации MSI-установщика
3. Настройка npm-публикации (`@yaoxiang/cli`)

## Открытые вопросы (закрыты)

Следующие вопросы были решены в ходе обсуждения дизайна:

- ~~Возможность статической линковки Z3 на Windows?~~ → **Статическую линковку не делаем, динамическая на всех платформах**
- ~~Именование подкоманды gen-std-interfaces?~~ → **`yaoxiang package gen-std`**
- ~~Сохранять ли Inno Setup?~~ → **Сохраняется**
- ~~Условное выполнение extra-artifacts в cargo-dist?~~ → **Обрабатывается скриптом `package-dist.sh` через case-ветвление в shell**
- ~~Совместимость версий интерфейсов стандартной библиотеки?~~ → **Публикуется вместе с версией компилятора, в одном архиве**
