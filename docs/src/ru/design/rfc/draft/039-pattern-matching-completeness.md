# RFC-039: Завершение сопоставления с образцом

## Резюме

Расширение сопоставления с образцом в `match` с текущего уровня «только литералы + подстановочный
знак» до полноценных возможностей: образцы вариантов Union (включая привязку полезной нагрузки),
образцы структур/кортежей, реализация или-образцов и образцов с условием-guard на уровне IR, а также
проверка полноты (E1030/E1031 переходят от пустого стаба к реальной эмиссии). Настоящий RFC является
предварительным условием для дорожной карты развития `Error { kind: ErrorKind, message }` (раздел
развития RFC-013 «Сквозные значения и коды ошибок времени выполнения»), однако его мотивация
самостоятельна — сопоставление с образцом представляет собой общую языковую возможность,
обслуживающую все типы с вариантами.

## Мотивация

### Эмпирическое обоснование текущего состояния (03.09.2026, код v0.7.12)

1. **На уровне IR реально реализованы только образцы-литералы**. AST уже определяет полный набор
   образцов (`src/frontend/core/parser/ast.rs:578`: Wildcard / Identifier / Literal / Tuple / Struct
   / Union / Or / Guard), парсер способен разбирать образцы вариантов вроде `ok(v)`, `err(e)`
   (`Pattern::Union`); однако генерация IR (начиная с `src/middle/core/ir_gen.rs:5330`) реализует
   только ветку `Literal`, остальные образцы попадают в заглушку — загружается константа 0 для
   сравнения на равенство, **никогда не совпадает**; при этом, когда scrutinee оказывается равным 0,
   происходит **ложное совпадение** с веткой-заглушкой (потенциально некорректное поведение).
2. **Пример `match ok(v)/err(e)` в stdlib.md — бумажная возможность**. Синтаксис деконструкции
   вариантов, приведённый в спецификации (§1.3 Result), на практике неработоспособен; реализация
   оператора `?` идёт в обход десахаризации match, что маскирует данный факт. В тестовом корпусе
   отсутствуют случаи деконструкции вариантов (`match.yx` / `pattern_matching.yx` покрывают только
   литералы и подстановочный знак).
3. **Проверка полноты висит в воздухе**. E1030 (Pattern non-exhaustive) и E1031 (Unreachable
   pattern) зарегистрированы в таблице кодов, но не имеют точек эмиссии — семантика match не
   определена окончательно.
4. **Развитие обработки ошибок заблокировано**. В настоящее время значение `Error` времени
   выполнения использует строковый код `{code, message}` как единственный программируемый контракт
   проверки (RFC-013); структурное моделирование (`match e.kind { file_not_found(path) => ... }`)
   зависит от деконструкции вариантов и привязки полезной нагрузки, вводимых настоящим RFC.

### Цели проектирования

- **Деконструкция вариантов должна быть работоспособной**: `match r { ok(v) => ..., err(e) => ... }`
  и деконструкция пользовательских множеств вариантов (sum type в стиле записей) должны иметь
  согласованную семантику во всех трёх путях исполнения.
- **Проверка полноты должна быть надёжной**: E1030/E1031 эмитируются реально, пропуск ветви в match
  является ошибкой компиляции.
- **Заглушки должны быть устранены**: удалить поведение-заглушку «загрузка 0 никогда не совпадает /
  ложно совпадает»; неподдерживаемые образцы должны вызывать ошибку компиляции, а не молча приводить
  к неверной ветви.

## Предложение (уровень скелета, подлежит наполнению в основном тексте)

| Возможность                            | Описание                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Образцы вариантов Union                | Сопоставление `VariantName` / `VariantName(привязка)` + привязка полезной нагрузки в область видимости ветки                                           |
| Образцы Struct / Tuple                 | Реализация образцов полей и кортежей (уже есть в AST, дополняется в IR)                                                                                |
| Или-образцы и Guard                    | Порядок вычисления и правила привязки для `p1 \| p2` и `p if cond`                                                                                     |
| Проверка полноты                       | E1030 для пропущенной ветви, E1031 для недостижимого образца; область действия охватывает множества вариантов (включая встроенные Result/Option)       |
| Уточнение семантики образца Identifier | Необходимо определиться, является ли голый идентификатор в текущем синтаксисе привязкой или сравнением с вариантом (связь с подстановочным знаком `_`) |

### Открытые вопросы

- [ ] Образец Identifier: привязка новой переменной или сопоставление с существующим значением?
      (Семантика Rust против существующего поведения в корпусе YaoXiang)
- [ ] Границы применимости проверки полноты: как множества вариантов, возвращаемые из динамически
      импортируемых/интерфейсных методов, участвуют в проверке полноты?
- [ ] Нужен ли атрибут типа `non_exhaustive` (влияет на масштаб поломки пользовательского match при
      расширении множеств вариантов в std)?
- [ ] Должна ли в переходный период ложное совпадение заглушки «загрузка 0» сначала выдавать ошибку
      компиляции, до полного исправления?
