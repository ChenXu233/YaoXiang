# RFC-039: Завершение сопоставления с образцом

## Резюме

Дополнение сопоставления с образцом `match` от текущего состояния «только литералы + подстановочный
знак» до полноценных возможностей: образцы вариантов объединения (включая привязку полезной
нагрузки), образцы структур/кортежей, IR-реализация образцов или и охранных выражений, а также
проверка полноты (E1030/E1031 переходят от пустого挂码 к реальному порождению). Данный RFC является
предварительным условием для маршрута развития `Error { kind: ErrorKind, message }` (раздел развития
RFC-013 «Сквозное использование значений и кодов ошибок времени выполнения»), но имеет
самостоятельную мотивацию — сопоставление с образцом является общеязыковой возможностью,
обслуживающей все типы с вариантами.

## Мотивация

### Свидетельства текущего состояния (2026-09-03, код v0.7.12)

1. **На уровне IR только литеральные образцы реализованы по-настоящему**. AST уже определяет полный
   набор образцов (`src/frontend/core/parser/ast.rs:578`: Wildcard / Identifier / Literal / Tuple /
   Struct / Union / Or / Guard), и парсер способен разбирать образцы вариантов вроде `ok(v)`,
   `err(e)` (`Pattern::Union`); однако генерация IR (начиная с `src/middle/core/ir_gen.rs:5330`)
   реализует только ветвь `Literal`, а остальные образцы попадают в stub — загружают константу 0 для
   сравнения на равенство и **никогда не совпадают**; более того, при scrutinee, равном 0,
   происходит **ложное совпадение** с ветвью stub (потенциально некорректное поведение).
2. **Пример `match ok(v)/err(e)` из stdlib.md — бумажная возможность**. Документ спецификации (§1.3
   Result) описывает синтаксис деструктурирования вариантов, который фактически не работает во время
   выполнения; реализация оператора `?` обходит десахаризацию через match, маскируя эту проблему. В
   тестовом корпусе нет случаев деструктурирования вариантов (`match.yx` / `pattern_matching.yx`
   покрывают только литералы и подстановочный знак).
3. **Проверка полноты — пустой挂код**. E1030 (Pattern non-exhaustive) и E1031 (Unreachable pattern)
   зарегистрированы в таблице кодов, но не имеют точек порождения — семантика match не определена.
4. **Развитие обработки ошибок заблокировано**. Значение `Error` времени выполнения в настоящее
   время использует строковый код `{code, message}` как единственный программируемый контракт для
   проверки (RFC-013); структурированное моделирование
   (`match e.kind { file_not_found(path) => ... }`) зависит от деструктурирования вариантов и
   привязки полезной нагрузки из данного RFC.

### Цели проектирования

- **Деструктурирование вариантов должно быть работоспособным**:
  `match r { ok(v) => ..., err(e) => ... }` и деструктурирование пользовательских наборов вариантов
  (sum type в стиле записей) должны иметь согласованную семантику во всех трёх путях выполнения.
- **Полнота должна быть надёжной**: E1030/E1031 должны реально порождаться, и пропуск ветви в match
  является ошибкой компиляции.
- **Удаление stub'а**: устранить поведение-заглушку «загрузка 0 никогда не совпадает / ложно
  совпадает»; неподдерживаемые образцы должны приводить к ошибке компиляции, а не молча выбирать
  неверную ветвь.

## Предложение (уровень каркаса, подлежит наполнению)

| Возможность                    | Описание                                                                                                                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Образцы вариантов Union        | Сопоставление `VariantName` / `VariantName(binding)` + привязка полезной нагрузки в область видимости ветви                                                                                      |
| Образцы Struct / Tuple         | Реализация образцов полей и кортежей (AST уже есть, IR дополняется)                                                                                                                              |
| Образцы Or и Guard             | Порядок вычисления и правила привязки для `p1 \| p2` и `p if cond`                                                                                                                               |
| Проверка полноты               | E1030 для пропущенных ветвей, E1031 для недостижимых; область покрытия — набор вариантов (Result/Option сейчас в core; проверка не зависит от принадлежности, см. RFC-011b этап 2, миграция std) |
| Уточнение семантики Identifier | Голый идентификатор в текущем синтаксисе — это привязка или сравнение вариантов; требуется решение (связь с подстановочным знаком `_`)                                                           |

### Открытые вопросы

- [ ] Образец Identifier: привязка новой переменной или сопоставление с существующим значением?
      (семантика Rust vs текущее поведение в корпусе кода YaoXiang)
- [ ] Границы применимости проверки полноты: как наборы вариантов, возвращаемые из динамически
      импортируемых/интерфейсных методов, участвуют в проверке полноты?
- [ ] Нужен ли атрибут типа `non_exhaustive` (влияет на радиус поломки пользовательских match при
      расширении наборов вариантов std)?
- [ ] Следует ли в переходный период до исправления stub'а с ложным совпадением при загрузке 0
      сначала выдавать ошибку компиляции?
