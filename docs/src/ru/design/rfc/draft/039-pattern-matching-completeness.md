# RFC-039: Завершение сопоставления с образцом

## Резюме

Расширение сопоставления с образцом в `match` от текущего «только литералы + подстановочный знак» до
полноценной функциональности: образцы вариантов Union (включая привязку полезной нагрузки), образцы
структур/кортежей, образцы Or и охрана, реализованные в IR, а также проверка полноты (E1030/E1031 —
переход от пустых заглушек к реальной эмиссии). Данный RFC является предварительным условием для
дорожной карты развития `Error { kind: ErrorKind, message }` (раздел развития RFC-013 «Сквозные
значения и коды ошибок времени выполнения»), но имеет самостоятельную мотивацию — сопоставление с
образцом является общей языковой возможностью, обслуживающей все типы с вариантами.

## Мотивация

### Текущее состояние по фактам (на 03.09.2026, код v0.7.12)

1. **На уровне IR реально работают только образцы литералов**. AST определяет полный набор образцов
   (`src/frontend/core/parser/ast.rs:578`: Wildcard / Identifier / Literal / Tuple / Struct / Union
   / Or / Guard); парсер способен разбирать образцы вариантов наподобие `ok(v)`, `err(e)`
   (`Pattern::Union`); однако генерация IR (начиная с `src/middle/core/ir_gen.rs:5330`) реализует
   только ветвь `Literal`, а остальные образцы попадают в заглушку — загружается константа 0 для
   сравнения на равенство, которая **никогда не совпадает**; и когда scrutinee оказывается равным 0,
   происходит **ошибочное совпадение** с ветвью-заглушкой (потенциально некорректное поведение).
2. **Пример `match ok(v)/err(e)` в stdlib.md — бумажная возможность**. Документ спецификации (§1.3
   Result) приводит синтаксис деструктурирования вариантов, который в действительности не работает;
   реализация оператора `?` не проходит через десахаризацию match, что маскирует данный факт. В
   тестовом корпусе нет случаев деструктурирования вариантов (`match.yx` / `pattern_matching.yx`
   покрывают только литералы и подстановочный знак).
3. **Проверка полноты — пустой挂код**. E1030 (Pattern non-exhaustive) и E1031 (Unreachable pattern)
   зарегистрированы в таблице кодов, но не имеют точек эмиссии — семантика match не определена.
4. **Заблокировано развитие обработки ошибок**. Значения `Error` времени выполнения в настоящее
   время используют строковый код `{code, message}` в качестве единственного программируемого
   контракта для проверки (RFC-013); структурное моделирование
   (`match e.kind { file_not_found(path) => ... }`) зависит от деструктурирования вариантов и
   привязки полезной нагрузки в данном RFC.

### Цели проектирования

- **Доступность деструктурирования вариантов**: `match r { ok(v) => ..., err(e) => ... }` и
  деструктурирование пользовательских наборов вариантов (sum type в стиле record) имеют
  согласованную семантику во всех трёх путях исполнения.
- **Надёжность проверки полноты**: E1030/E1031 эмитируются реально, пропуск ветви в match является
  ошибкой компиляции.
- **Удаление заглушек**: устранить поведение «загрузка 0 никогда не совпадает/ошибочно совпадает»;
  неподдерживаемые образцы должны приводить к ошибке компиляции, а не молча идти по неверному пути.

## Предложение (уровень скелета, требует наполнения в основном тексте)

| Возможность                    | Описание                                                                                                                              |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| Образцы вариантов Union        | Сопоставление `VariantName` / `VariantName(binding)` + привязка полезной нагрузки в область видимости ветви                           |
| Образцы Struct / Tuple         | Реализация образцов полей и кортежей (есть в AST, дополняется в IR)                                                                   |
| Образцы Or и Guard             | Порядок вычисления и правила привязки для `p1 \| p2` и `p if cond`                                                                    |
| Проверка полноты               | E1030 для пропущенных ветвей, E1031 для недостижимых, область покрытия охватывает наборы вариантов (включая встроенные Result/Option) |
| Уточнение семантики Identifier | В текущем синтаксисе голый идентификатор — привязка или сравнение с вариантом; требуется фиксация (связь с подстановочным знаком `_`) |

### Открытые вопросы

- [ ] Образец Identifier: привязка новой переменной или сопоставление с существующим значением?
      (Семантика Rust против существующего поведения корпуса YaoXiang)
- [ ] Границы применимости полноты: как наборы вариантов, возвращаемые динамически
      импортируемыми/интерфейсными методами, участвуют в проверке полноты?
- [ ] Нужен ли атрибут типа `non_exhaustive` (влияет на радиус разрушения расширения наборов
      вариантов std для пользовательских match)?
- [ ] Должна ли ошибочная заглушка с загрузкой 0 до исправления на переходный период сначала
      вызывать ошибку компиляции?
