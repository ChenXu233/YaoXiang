# RFC-002: Уровень реализации IO ресурсных типов на основе libuv

> **Ссылка**:
>
> - [RFC-024: Модель параллелизма на основе блоков spawn](../accepted/024-concurrency-model.md)

## Аннотация

В данном документе определяется уровень реализации IO в YaoXiang: кроссплатформенные IO возможности на основе libuv, выступающие в качестве низкоуровневой реализации системы ресурсных типов из RFC-024.

**Основное назначение**:

```
RFC-024: Определение ресурсных типов (FilePath, HttpUrl, DBUrl, Console)
    ↓ использует
RFC-002: Реализация IO ресурсных типов (на основе libuv)
    ↓ низкий уровень
libuv: Кроссплатформенный IO движок (событийный цикл + пул потоков)
```

**Чем это НЕ является**:

- ❌ Не "прозрачная асинхронность" — пользователь явно управляет параллелизмом через блоки spawn
- ❌ Не "автоматическая асинхронизация" — IO операции необходимо явно вызывать внутри блоков spawn
- ❌ Не "разработчику не нужно заботиться о низкоуровневых деталях" — система ресурсных типов обеспечивает безопасность параллелизма

**Чем это ЯВЛЯЕТСЯ**:

- ✅ Уровень реализации IO для ресурсных типов (FilePath, HttpUrl, DBUrl, Console)
- ✅ Унифицированный кроссплатформенный IO (libuv обрабатывает различия Windows/Linux/macOS)
- ✅ Архитектура с общим событийным циклом (один событийный цикл libuv обрабатывает весь IO)
- ✅ Интеграция с системой ресурсных типов RFC-024

## Мотивация

### Зачем нужен libuv?

RFC-024 определяет систему ресурсных типов:

- `FilePath` - путь в файловой системе
- `HttpUrl` - HTTP конечная точка
- `DBUrl` - подключение к базе данных
- `Console` - стандартный вывод

Этим ресурсным типам необходима низкоуровневая реализация IO. libuv предоставляет:

| Потребность     | Что предоставляет libuv                         |
| --------------- | ----------------------------------------------- |
| Кроссплатформенный IO | Единый API для Windows/Linux/macOS           |
| Асинхронность   | Общий событийный цикл, весь IO worker'ов обрабатывается централизованно |
| Пул потоков     | Выделенный пул потоков для блокирующих операций |
| Безопасность параллелизма | Однопоточный событийный цикл, естественно без конкуренции |

### Связь с RFC-024

## Предложение

### 1. Архитектура libuv

#### 1.1 Архитектура с общим событийным циклом

```
┌─────────────────────────────────────────────────────────┐
│                    Runtime                               │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐    │
│  │  Worker 0   │  │  Worker 1   │  │  Worker N   │    │
│  │  вычисления  │  │  вычисления  │  │  вычисления  │    │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘    │
│         │                │                │            │
│         └────────────────┼────────────────┘            │
│                          ↓                              │
│  ┌─────────────────────────────────────────────────┐  │
│  │          Событийный цикл libuv (выделенный поток) │  │
│  │          Обрабатывает все IO операции            │  │
│  └─────────────────────────────────────────────────┘  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**Ключевые характеристики**:

- Один общий событийный цикл libuv (запущен в выделенном потоке)
- Все IO операции всех worker'ов отправляются в этот общий событийный цикл
- Однопоточный событийный цикл естественно избегает конкуренции
- Высокая эффективность использования ресурсов, нет необходимости создавать событийный цикл для каждого worker'а

#### 1.2 Механизмы безопасности параллелизма

| Характеристика libuv   | Соответствие в YaoXiang    | Безопасность параллелизма |
| ---------------------- | -------------------------- | ------------------------- |
| Однопоточный событийный цикл | Последовательное выполнение внутри блоков spawn | Естественно без конкуренции |
| Изоляция пула потоков | Блокирующие операции не блокируют главный поток | Нет разделяемого состояния |
| Асинхронные колбэки   | DAG планировщик управляет зависимостями | Детерминированное выполнение |

### 2. Маппинг IO ресурсных типов

#### 2.1 FilePath → файловый IO через libuv

```rust
// модуль std.io (на основе libuv)
pub struct IoModule;

impl StdModule for IoModule {
    fn exports(&self) -> Vec<NativeExport> {
        vec![
            // операции с файлами → libuv fs_* API
            NativeExport::new("read_file", "std.io.read_file",
                "(path: FilePath) -> String", native_read_file),
            NativeExport::new("write_file", "std.io.write_file",
                "(path: FilePath, content: String) -> Bool", native_write_file),
            NativeExport::new("append_file", "std.io.append_file",
                "(path: FilePath, content: String) -> Bool", native_append_file),
            // операции Console → libuv tty API
            NativeExport::new("print", "std.io.print",
                "(...args) -> ()", native_print),
            NativeExport::new("println", "std.io.println",
                "(...args) -> ()", native_println),
        ]
    }
}

// реализация файлового IO libuv
fn native_read_file(args: &[RuntimeValue], ctx: &mut NativeContext) -> Result<RuntimeValue, ExecutorError> {
    let path = extract_file_path(args)?;

    // отправка в событийный цикл libuv
    // libuv асинхронное чтение файла
    // возврат результата
    ctx.uv_loop.fs_read(path)
}
```

#### 2.2 HttpUrl → сетевой IO через libuv

```rust
// модуль std.net (на основе libuv)
pub struct NetModule;

impl StdModule for NetModule {
    fn exports(&self) -> Vec<NativeExport> {
        vec![
            // HTTP операции → libuv http API

            NativeExport::new("http_post", "std.net.http_post",
                "(url: HttpUrl, body: String) -> Response", native_http_post),
        ]
    }
}

// реализация сетевого IO libuv
fn native_http_get(args: &[RuntimeValue], ctx: &mut NativeContext) -> Result<RuntimeValue, ExecutorError> {
    let url = extract_http_url(args)?;

    // отправка в событийный цикл libuv
    // libuv асинхронный HTTP запрос
    // возврат результата
    ctx.uv_loop.http_get(url)
}
```

#### 2.3 DBUrl → пул подключений к БД

```rust
// модуль std.db (на основе libuv)
pub struct DbModule;

impl StdModule for DbModule {
    fn exports(&self) -> Vec<NativeExport> {
        vec![
            // операции с БД → пул потоков libuv
            NativeExport::new("query", "std.db.query",
                "(url: DBUrl, sql: String) -> Rows", native_query),
        ]
    }
}

// реализация IO БД через libuv
fn native_query(args: &[RuntimeValue], ctx: &mut NativeContext) -> Result<RuntimeValue, ExecutorError> {
    let url = extract_db_url(args)?;
    let sql = extract_sql(args)?;

    // отправка в пул потоков libuv
    // запрос к БД выполняется в пуле потоков
    // после завершения колбэк уведомляет главный поток
    ctx.uv_loop.db_query(url, sql)
}
```

#### 2.4 Console → сериализация стандартного вывода

```rust
// операции Console автоматически сериализуются (правила системы ресурсных типов RFC-024)
// все операции Console выполняются последовательно в одном потоке
fn native_print(args: &[RuntimeValue], ctx: &mut NativeContext) -> Result<RuntimeValue, ExecutorError> {
    let output = format_args(args);

    // сериализация операций Console
    // libuv tty запись
    ctx.uv_loop.tty_write(output)
}
```

### 3. Интеграция со spawn-блоками

#### 3.1 С точки зрения пользователя

```yaoxiang
# определение ресурсных типов (RFC-024)
FilePath: Resource
HttpUrl: Resource

# IO операции (реализация RFC-002)
File.read: (FilePath) -> String
HTTP.get: (HttpUrl) -> Response

# явный параллелизм пользователя (RFC-024)
(a, b) = spawn {
    read_file("data.txt"),      # ресурсный тип FilePath, низкий уровень libuv
    fetch("http://example.com") # ресурсный тип HttpUrl, низкий уровень libuv
}
# компилятор: FilePath и HttpUrl не конфликтуют, можно параллельно
```

#### 3.2 Компиляционный анализ

```
Компилятор анализирует блок spawn:
1. распознает операции с ресурсными типами
2. обнаруживает конфликты ресурсов (автоматическая сериализация при одинаковом пути/URL)
3. генерирует план выполнения DAG
4. помечает IO узлы (отправка в libuv)
```

#### 3.3 Выполнение в runtime

```
Runtime выполняет блок spawn:
1. Worker 0 отправляет IO задачу → общий событийный цикл
2. Worker 1 отправляет IO задачу → общий событийный цикл
3. событийный цикл унифицированно обрабатывает все IO операции
4. после завершения IO уведомляется соответствующий Worker
5. Worker продолжает выполнение последующих задач
```

### 4. Трёхуровневая архитектура Runtime и libuv

| Уровень             | Использование libuv | Асинхронность        | Сценарии использования              |
| ------------------- | ------------------- | -------------------- | ----------------------------------- |
| Embedded Runtime    | без libuv           | без асинхронности    | WASM, игровые скрипты              |
| Standard Runtime    | общий событийный цикл | асинхронный IO     | веб-сервисы, конвейеры данных      |
| Full Runtime        | общий событийный цикл | асинхронный IO + параллелизм | научные вычисления, крупномасштабный параллелизм |

**Embedded Runtime**: без libuv, синхронное выполнение, без асинхронных возможностей.

**Standard Runtime**: общий событийный цикл libuv, все IO операции асинхронны.

**Full Runtime**: общий событийный цикл libuv, многопоточный параллелизм + асинхронный IO.

## Детальный проект

### 1. Структура Rust-привязок

```rust
// модуль привязок libuv
pub mod uv {
    // событийный цикл
    pub struct UvLoop {
        loop_handle: *mut uv_loop_t,
    }

    // файловые операции
    pub trait FileOps {
        fn fs_read(&self, path: &str) -> Result<String, UvError>;
        fn fs_write(&self, path: &str, content: &str) -> Result<(), UvError>;
        fn fs_append(&self, path: &str, content: &str) -> Result<(), UvError>;
    }

    // сетевые операции
    pub trait NetOps {
        fn http_get(&self, url: &str) -> Result<Response, UvError>;
        fn http_post(&self, url: &str, body: &str) -> Result<Response, UvError>;
    }

    // операции с БД
    pub trait DbOps {
        fn db_query(&self, url: &str, sql: &str) -> Result<Rows, UvError>;
    }

    // операции Console
    pub trait ConsoleOps {
        fn tty_write(&self, data: &str) -> Result<(), UvError>;
    }
}
```

### 3. Интеграция с DAG планировщиком

```rust
// интерфейс IO узла (определён в RFC-008)
trait IoScheduler {
    // отправить IO задачу, вернуть дескриптор
    fn submit_io(&self, task: IoTask) -> IoHandle;

    // вызывается libuv при завершении IO, пробуждает DAG узел
    fn on_io_complete(&self, handle: IoHandle);
}

// реализация через libuv
impl IoScheduler for UvLoop {
    fn submit_io(&self, task: IoTask) -> IoHandle {
        match task.resource_type {
            ResourceType::FilePath => self.fs_read(task.path),
            ResourceType::HttpUrl => self.http_get(task.url),
            ResourceType::DBUrl => self.db_query(task.url, task.sql),
            ResourceType::Console => self.tty_write(task.data),
        }
    }

    fn on_io_complete(&self, handle: IoHandle) {
        // уведомить DAG планировщик о пробуждении зависимых узлов
        self.dag_scheduler.wake_dependents(handle.node_id);
    }
}
```

## Компромиссы

### Преимущества

1. **Унификация кроссплатформенности**: libuv обрабатывает различия Windows/Linux/macOS
2. **Асинхронные IO возможности**: общий событийный цикл обрабатывает весь IO, без async/await
3. **Безопасность параллелизма**: однопоточный событийный цикл естественно без конкуренции
4. **Эффективность использования ресурсов**: один событийный цикл, низкие затраты памяти
5. **Соответствие RFC-024**: система ресурсных типов обеспечивает безопасность параллелизма
6. **Зрелость и стабильность**: libuv проверен в Node.js при масштабном использовании

### Недостатки

1. **Зависимость от C библиотеки**: необходима привязка к C библиотеке libuv
2. **Ограничения бутстрэппинга**: после бутстрэппинга может потребоваться замена на нативную реализацию YaoXiang
3. **Поддержка WASM**: требуется дополнительная адаптация

## Альтернативные решения

| Решение       | Почему не выбрано                                      |
| ------------- | -------------------------------------------------------- |
| Rust std::io  | Синхронная блокировка, невозможна асинхронность с блоками spawn |
| tokio         | Спроектирован для Rust async/await, не соответствует модели явного параллелизма YaoXiang |
| mio           | Предоставляет только низкоуровневые асинхронные примитивы, отсутствуют высокоуровневые IO функции |
| Реализация с нуля | Сложно и подвержено ошибкам, невозможно сравнить со зрелостью libuv |

## Стратегия реализации

### Фазы

1. **Фаза 1 (v0.3)**: привязки libuv, базовый файловый IO
2. **Фаза 2 (v0.5)**: сетевой IO, поддержка HTTP
3. **Фаза 3 (v0.7)**: IO базы данных, пул подключений
4. **Фаза 4 (v1.0)**: адаптация WASM, оптимизация производительности

### Зависимости

- RFC-024 (модель параллелизма) → завершено
- RFC-008 (архитектура Runtime) → завершено
- RFC-009 (модель владения) → завершено
- RFC-011 (обобщённые типы) → завершено
