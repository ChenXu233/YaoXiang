# RFC-035: Поддержка MCP Server (интеграция AI Agent)

## Резюме

Для YaoXiang добавляется сервер MCP (Model Context Protocol), позволяющий AI-агентам (Claude Code,
Continue, Cody, Zed и др.) напрямую запрашивать у исходного кода YaoXiang **AST, ошибки разбора,
типы, символы, ссылки и результаты форматирования**. Используется уже реализованный в RFC-017 бэкенд
`World`, добавляется подкоманда `yaoxiang mcp`, один бинарник в двух режимах, отдельные `World` для
каждого процесса.

## Мотивация

### Зачем нужна эта возможность?

RFC-017 позволяет редакторам **понимать** YaoXiang (hover / goto-def / completion). Однако LSP — это
протокол, **управляемый позициями**:

- каждый запрос сильно зависит от `textDocument` URI + `Position`
- редактор должен сначала открыть файл, сохранить и поддерживать длительное соединение с
  LSP-сервером
- рабочий процесс AI-агента — это **фрагменты кода**: «вставить кусок кода» в диалоге и задать
  вопрос, **без** предварительного сохранения на диск

Реально доступные AI-агентам LSP-клиенты (vscode-langservers-extracted, проекты типа
`mcp-lsp-bridge`) переводят **только L1**: goto-def, hover. Чего AI хочет:

- «правильно ли **разобран** этот код» — требуется parse + полный поток диагностики
- «как **используется** этот символ в файле» — требуется `lookup_symbol` по имени
- «как выглядит этот код **после форматирования**» — требуется `format_source`
- «**где все** ошибки типов» — требуется `typecheck` по всей рабочей области

Эти возможности перевода L1 LSP **не справляются**, так как LSP по своей конструкции их не
поддерживает.

### Текущие проблемы

1. AI-агенту неудобно вызывать LSP: требуются mock-документы, JSON огромен, сильная зависимость от
   URI
2. В проекте YaoXiang отсутствует интерфейсный слой «AI-First»: люди используют LSP в IDE, AI-агенты
   не могут использовать LSP
3. Такие основные AI-агенты, как Claude Code / Continue, уже по умолчанию поддерживают MCP, а для
   YaoXiang это пустая экосистема

### Что такое MCP?

MCP (Model Context Protocol) — это протокол вызова инструментов для AI-агентов, опубликованный и
открытый в 2024-2025 годах компанией Anthropic, ставший фактическим стандартом (поддерживается
OpenAI, Google, Microsoft, Zed, Continue, Cody и др.). Особенности:

- основан на JSON-RPC 2.0 (родственен LSP)
- три основные примитивы: **Tools** (действия), Resources (данные), Prompts (шаблоны)
- транспорт: `stdio` (дочерний процесс) / streamable `HTTP` / SSE
- входы и выходы инструментов имеют строгую типизацию по **JSON Schema** (удобно для LLM)
- в 2025-06+ опубликована спецификация streamable HTTP, данный RFC также совместим со старым SSE

**В данном RFC используется только примитив Tools** — выровнено с «предоставлением сервиса» в LSP,
не вводится сложность файловой модели Resources.

## Предложение

### Основной дизайн

Один бинарник в двух режимах:

```text
┌─────────────────────────────────────────────────────────┐
│                    yaoxiang（v0.7.7+）                  │
│  ┌─────────────────┐      ┌──────────────────────────┐  │
│  │ yaoxiang lsp    │      │   yaoxiang mcp           │  │
│  │ (stdio JSON-RPC)│      │   (stdio default         │  │
│  │ RFC-017 已实现  │      │    + HTTP 可选)          │  │
│  └────────┬────────┘      └──────────┬───────────────┘  │
│           │                         │                   │
│           ▼                         ▼                   │
│  ┌──────────────────────────────────────────────────┐  │
│  │  共享 lib crate（`yaoxiang`）                      │  │
│  │  src/lsp/{server,session,world}.rs                │  │
│  │  src/frontend/{lexer,parser,core}/...             │  │
│  │  src/middle/...                                   │  │
│  └──────────────────────────────────────────────────┘  │
│                                                          │
│  ┌──────────────────────────────────────────────────┐  │
│  │            src/mcp/  ← 新增                       │  │
│  │  ├── mod.rs          （模块入口 + 启动函数）       │  │
│  │  ├── transport/      （stdio + HTTP/SSE）         │  │
│  │  ├── server.rs       （JSON-RPC 消息循环）         │  │
│  │  ├── tools/          （6 个 tool handler）        │  │
│  │  ├── schema.rs       （输入输出 JSON Schema）     │  │
│  │  └── project.rs      （项目根识别 + 路径解析）    │  │
│  └──────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

**Ключевые решения**:

- **один и тот же бинарник**: `yaoxiang` переключается через подкоманды; процессы LSP и MCP **не
  сосуществуют** в одной среде исполнения
- **отдельные World для каждого процесса**: каждый процесс `yaoxiang mcp` владеет одним `World`; не
  влияет на процессы LSP и другие процессы MCP (без конкуренции за блокировки, независимая изоляция
  от сбоев)
- **stdio по умолчанию**: позволяет избежать конфликтов портов, нулевая сетевая конфигурация; HTTP
  как опциональный запасной вариант
- **повторное использование вместо дублирования**: прямой вызов lib API `yaoxiang::frontend` /
  `yaoxiang::middle` / `yaoxiang::lsp::handlers`, **без** прохода через LSP-клиент

### Набор инструментов (8 инструментов, поставляются в 3 этапа)

Спроектировано по принципу «устранения особых случаев + поэтапность»: сначала чистые
stateless-инструменты для исходного кода, затем инструменты рабочей области, использующие LSP World,
и независимо добавляются инструменты для перезаписи AST.

| Имя инструмента      | Вход                                                                                            | Выход                                                        | Повторное использование                                                               | Этап        |
| -------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------- | ----------- |
| `parse_source`       | `source: String`, `tab_size?: u32`                                                              | `{ast: Node, diagnostics: Diagnostic[]}`                     | прямой вызов `frontend::parse`                                                        | v0.8.x      |
| `format_source`      | `source: String`, `tab_size?: u32`                                                              | `{formatted: String, diff: Hunk[]}`                          | прямой вызов `formatter::format`                                                      | v0.8.x      |
| `lookup_symbol`      | `query: String`, `workspace_root?: String`, `kind?: SymbolKind[]`                               | `{symbols: Symbol[]}`                                        | повторное использование `lsp::handlers::workspace_symbol` (нечёткий поиск по `query`) | v0.8.x      |
| `find_references`    | `query: String`, `workspace_root?: String`                                                      | `{locations: Location[]}`                                    | повторное использование `lsp::handlers::references` (по `query`, а не по позиции)     | v0.8.x      |
| `typecheck`          | `file_paths: String[]`, `project_root: String`                                                  | `{diagnostics: Diagnostic[], summary: Counts}`               | повторное использование `lsp::world::typecheck_full`                                  | v0.8.x      |
| `explain_diagnostic` | `code: String` (например, `E0001`), `lang?: String`                                             | `{code, category, title, description, example, help}`        | **прямой вызов** `util::diagnostic::command::render_explain_output`                   | **v0.9.x**  |
| `list_imports`       | `file_path: String`, `project_root?: String`                                                    | `{imports: [{module, items, source_file}]}`                  | повторное использование `middle::passes::module::ModuleGraph::validate_imports`       | **v0.9.x**  |
| `rename_symbol`      | `source: String`, `old_name: String`, `new_name: String`, `scope?: "module" \| "function:name"` | `{source: String, edits: Edit[], diagnostics: Diagnostic[]}` | **новое** `src/middle/rename.rs` (перезапись AST)                                     | **v0.10.x** |

**Границы 8 инструментов**:

- `parse_source` / `format_source` — **чистые stateless для исходного кода**, не загружаются в World
- `lookup_symbol` / `find_references` — принимают `workspace_root` (если не передан, используется
  `--project-root` из запуска)
- `typecheck` — **обязательный** `file_paths`, обеспечивает полноту рабочей области
- `explain_diagnostic` — **нулевая зависимость от файлов**, чисто строковый запрос к реестру кодов
  ошибок
- `list_imports` — `file_path` — физический файл, выводит результат разбора import этого файла
- `rename_symbol` — **перезапись AST чистого исходного кода**, без запросов по позициям в стиле LSP
  (семантика отличается от существующего `lsp::handlers::rename`)
- ~~`hover` / `completion` / `signature_help`~~ — **все отброшены**: AI-агент не использует
  семантику, «чувствительную к позициям», вместо этого поиск по имени через `lookup_symbol`

**Момент загрузки World**: при запуске сервера по `--project-root` сканируются `yaoxiang.toml` и
`src/**/*.yx`, используется уже реализованный в LSP-017 API `World::load_*` для однократной загрузки
в `World.documents`. **Никаких** новых API в lib не добавляется.

### Контракт инструментов

**Вход**: описывается через JSON Schema, каждое поле имеет `description` + `examples` (LLM читает
автоматически).

**Выход**: структурированный JSON, единообразно содержит поле `schemaVersion: "1.0"`:

```jsonc
// 成功响应
{
  "schemaVersion": "1.0",
  "isError": false,
  "content": [
    { "type": "json", "json": { /* 工具特定数据 */ } }
  ]
}

// 诊断被结构化返回（不视作 tool 错误）
{
  "schemaVersion": "1.0",
  "isError": false,
  "content": [{ "type": "json", "json": {
    "ast": {...},
    "diagnostics": [
      { "code": "E0001", "severity": "error", "message": "...", "span": [12, 4, 12, 18] }
    ]
  }}]
}

// 工具级错误（如 parse_source 接收非法 UTF-8）
{
  "schemaVersion": "1.0",
  "isError": true,
  "content": [{ "type": "text", "text": "MCP-INVALID-INPUT: source 不是合法 UTF-8" }],
  "errorCode": "MCP-INVALID-INPUT"
}
```

**Система ошибок**:

- **Диагностика (diagnostic)**: ошибки разбора/типов, по RFC-013 (`E0001` и т.д.) — **не считается
  ошибкой tool**
- **Ошибки уровня инструмента**: с префиксом `MCP-` (`MCP-INVALID-INPUT`, `MCP-PROJECT-NOT-FOUND`,
  `MCP-INTERNAL`) — считается `isError: true`
- **panic/crash**: JSON-RPC `-32603 Internal error`, сервер **не завершается**

**Правила разрешения путей** (применяются к `workspace_root` для `lookup_symbol` /
`find_references`, `file_paths` для `typecheck`):

1. Параметр командной строки `--project-root <dir>` имеет наивысший приоритет (перекрывает
   умолчание)
2. Иначе: от cwd вверх ищется `yaoxiang.toml` до корня файловой системы (по RFC-015)
3. Иначе: сам cwd
4. `file_paths` должны находиться внутри корня проекта (защита от обхода); за пределами →
   `MCP-PATH-OUTSIDE-PROJECT`

### Транспортный уровень

**stdio (по умолчанию)**:

```bash
yaoxiang mcp
# 启动后从 stdin 读 JSON-RPC，写 stdout，stderr 用于日志
```

Конфигурация AI-агента (`.mcp.json` для Claude Code / `config.json` для Continue):

```jsonc
{
  "mcpServers": {
    "yaoxiang": {
      "command": "yaoxiang",
      "args": ["mcp", "--project-root", "${workspaceFolder}"],
    },
  },
}
```

**streamable HTTP (опционально)**:

```bash
yaoxiang mcp --http --addr 127.0.0.1:7325  # 单 HTTP 端口，新 MCP 规范
yaoxiang mcp --http --sse --addr 127.0.0.1:7325  # 兼容旧 SSE（v0.10）
```

**Ограничения безопасности**:

- **слушает только loopback** (127.0.0.1 / ::1); привязка к публичному адресу явно отвергается с
  выходом по ошибке
- HTTP **без аутентификации** (loopback по умолчанию доверенный); в будущем добавляется поле
  `--require-token <hex>`
- режим stdio с дочерним процессом **изолирован по своей природе** (родительский процесс
  контролирует права)

### Многопроцессность и параллелизм

Каждый процесс `yaoxiang mcp` владеет одним `World`, не делятся между собой:

```text
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ yaoxiang    │   │ yaoxiang    │   │ yaoxiang    │
│   lsp       │   │   mcp       │   │   mcp       │
│ (Editor 1)  │   │ (Claude 1)  │   │ (Claude 2)  │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │ stdio/stdout    │ stdio          │ stdio
   ┌───┴────┐        ┌───┴────┐        ┌───┴────┐
   │ Editor │        │ Claude │        │ Claude │
   └────────┘        └────────┘        └────────┘
```

**Конфликты портов**: конфигурация AI-агента «запуск дочернего процесса» — естественное отсутствие
конфликтов портов. В режиме HTTP пользователь сам управляет распределением портов. **Изоляция
World**: каждый процесс имеет независимое состояние синхронизации LSP — сбой одного процесса MCP
**не влияет** на LSP/другие процессы MCP. **future Sessions**: распределение по нескольким рабочим
областям (несколько `Session` в одном процессе) рассматривается в v2, **в данном RFC не делается**.

## Подробный дизайн

### Структуры данных

Добавляется `src/mcp/project.rs`:

```rust
pub struct ProjectRoot {
    /// 绝对路径
    pub root: PathBuf,
    /// 加载时识别项目根的策略来源
    pub source: ProjectRootSource,
}

pub enum ProjectRootSource {
    CliFlag,           // yaoxiang mcp --project-root
    AutoDetected,      // 向上找 yaoxiang.toml
    FallbackCwd,       // fallback 到 cwd
}

pub struct ResolvedPath {
    /// 相对项目根的相对路径（推荐给 AI 读）
    pub relative: String,
    /// 解析后的绝对路径（用于 World 操作）
    pub absolute: PathBuf,
}

impl ProjectRoot {
    /// 把"file_path"解析为安全路径——防穿越
    pub fn resolve(&self, file_path: &str) -> Result<ResolvedPath, McpError>;
}
```

Синглтон `ProjectRoot` + автоматическая генерация схем инструментов в `src/mcp/schema.rs`:

```rust
pub struct ProjectRoot {
    /// 绝对路径（必含 `yaoxiang.toml` 或向下兼容回退）
    pub root: PathBuf,
    pub source: ProjectRootSource,
}

impl ProjectRoot {
    /// CLI 启动时识别一次，结果缓存在 `McpServer` 上下文里——所有工具复用
    pub fn detect(cli_override: Option<PathBuf>) -> Result<Self, McpError>;
}
```

Схемы инструментов автоматически генерируются из input-структур с помощью crate `schemars`, чтобы
избежать дрейфа рукописной JSON Schema:

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ParseSourceInput {
    /// 完整 YaoXiang 源码片段——**不**保存到磁盘，纯 transient
    pub source: String,
    pub tab_size: Option<u32>,
}
```

**В схемах инструментов `parse_source` / `format_source` нет поля `file_path`** — эти инструменты
принимают только строковый исходный код и не участвуют в семантике проекта. `lookup_symbol` /
`find_references` / `typecheck` принимают `workspace_root` или `file_paths` (обязательность — см.
таблицу инструментов).

### Изменения в компиляторе

| Модуль                                 | Изменения                                                                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `src/lsp/world.rs`                     | **Нулевые изменения** — MCP при запуске вызывает уже существующий в LSP API `World::load_*` для однократной загрузки рабочей области |
| `src/lsp/handlers/workspace_symbol.rs` | **Нулевые изменения** — `mcp/tools/lookup.rs` оборачивает, преобразуя `query` в параметры LSP                                        |
| `src/lsp/handlers/references.rs`       | **Нулевые изменения** — аналогично                                                                                                   |
| `src/lsp/handlers/formatter.rs`        | **Нулевые изменения** — `format_source` вызывается напрямую                                                                          |
| `src/main.rs`                          | Добавляется ветвь подкоманды `Mcp`                                                                                                   |
| `Cargo.toml`                           | Добавляется feature `mcp-server` (или всегда присутствует в основном бинарнике)                                                      |
| `src/util/diagnostic/`                 | **Нулевые изменения** (уже реализовано в RFC-017)                                                                                    |

**Ключевое ограничение**: `src/mcp/` **не** должен обратно зависеть от приватных символов `src/lsp/`
— handlers можно вызывать только через публичный API `crate::lsp::`.

### Обратная совместимость

- ✅ **Полная обратная совместимость**: новая подкоманда `yaoxiang mcp`, не изменяет никакое текущее
  поведение `yaoxiang` / `yaoxiang lsp`
- ✅ **LSP-сервер не изменяется**: все возможности, API и внутреннее состояние, реализованные в
  RFC-017, остаются без изменений
- ✅ **Публичный API crate lib не изменяется**: все пути `pub` остаются; MCP только потребляет
  существующий API — **ноль** новых `pub` методов

### Обработка ошибок

| Источник                                           | Обработка                                                                                        |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Ошибка разбора                                     | `Diagnostic{code:"E0xxx", severity, message, span}` (**не ошибка tool**, возвращается в content) |
| Ошибка типа                                        | Аналогично                                                                                       |
| `file_paths` за пределами (инструмент `typecheck`) | ошибка уровня tool `MCP-PATH-OUTSIDE-PROJECT`                                                    |
| `source` — нелегальный UTF-8                       | ошибка уровня tool `MCP-INVALID-INPUT`                                                           |
| panic инструмента                                  | JSON-RPC `-32603 Internal error`; сервер **не завершается**                                      |
| Клиент отправляет не-JSON-RPC                      | поток разрывается (stdio EOF), перезапуск — новая сессия                                         |

Уровни серьёзности диагностики берутся из уже реализованного в RFC-017
`enum ErrorKind { Error, Warning, Note }`.

| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **Unit**        | `src/mcp/project.rs::resolve` — обход пути, `src/mcp/schema.rs` — проверка схемы                                                         |
| **Integration** | mock stdio: запускается сервер, в stdin подаётся JSON-RPC, из stdout читаются ответы, сверяются с фикстурой                              |
| **E2E**         | запускается настоящий процесс `yaoxiang mcp`, цепочка вызовов инструментов в стиле Claude Code: parse → исправление → format → typecheck |
| **Fuzz**        | `cargo-fuzz` для разбора MCP JSON-RPC (libFuzzer harness)                                                                                |

Каждый tool должен иметь как минимум 1 happy path + 1 сценарий с диагностикой + 1 сценарий с
tool-ошибкой в integration-тестах.

## Компромиссы

### Преимущества

- **Крайне низкая стоимость повторного использования**: `World` / `Session` / `handlers` / сбор
  диагностики уже реализованы (RFC-017), данный RFC — это «добавление MCP-оболочки»
- **Интерфейс AI-First**: контракт инструмента в 3-5 раз интуитивнее LSP; LLM читает схему напрямую
- **Многопроцессная изоляция**: отделено от сессии редактора LSP и от других процессов MCP, **ноль
  конкуренции за блокировки**
- **Дружественность к stdio**: все основные AI-агенты по умолчанию используют режим дочернего
  процесса, нулевая конфигурация для подключения
- **YAGNI соблюдён**: в данном RFC отброшены Resources, Sessions, межпроцессное состояние, удалённый
  MCP — откроется в v2

### Недостатки

- **Разделение протоколов**: в будущем LSP / MCP / DAP будут развиваться каждый по-своему, затраты
  на поддержание согласованности
- **Режим HTTP — гражданин второго сорта**: ограничение loopback позиционирует его как локальный
  инструмент, удалённые сценарии потребуют перепроектирования в v2
- **Затраты на повторный разбор**: AI многократно корректирует исходный код и многократно вызывает
  `parse_source`, что приводит к повторному lexer+parser. **Смягчение**: `DocumentCache` из RFC-017
  всё ещё может ускорить повторный разбор того же source с диска; для чисто временного source
  однократный разбор неизбежен
- **Затраты на покрытие тестами**: 5 инструментов × 3 сценария = минимум 15 integration-тестов

## Альтернативы

| Вариант                                                                           | Почему не выбран                                                                                                          |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Встраивание двух протоколов в процесс** (сосуществование LSP+MCPlistener)       | stdin/stdout может иметь только одного потребителя; HTTP также должен сосуществовать — сложность > выгода                 |
| **MCP как мост к LSP-клиенту**                                                    | дополнительный уровень IPC; LSP по дизайну не поддерживает поиск символов по имени — возможности, нужные MCP, LSP не даёт |
| **Использование gRPC / собственного протокола**                                   | отход от фактического стандарта; в сообществе уже есть MCP SDK (TypeScript, Python, Rust) со своей экосистемой            |
| **Повторное использование всех возможностей LSP handler (L3 набор инструментов)** | большая работа по адаптации position↔intent; убывающая предельная отдача                                                  |
| **Первая версия только HTTP (без stdio)**                                         | Claude Code / Continue и др. по умолчанию stdio, порог слишком высок                                                      |

## Стратегия реализации

### Зависимости

- **Сильная зависимость**: реализация LSP из RFC-017 (уже выполнена)
- **Сильная зависимость**: система кодов ошибок из RFC-013 (уже выполнена)
- **Сильная зависимость**: распознавание корня проекта из RFC-014 / RFC-015 (частично выполнено)
- **Новые зависимости** (Rust crate):
  - `mcp-rust-sdk` (ожидает оценки, см.
    [modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk))
  - `tokio` (**уже есть**, optional feature)
  - `axum` (режим HTTP) или `hyper` напрямую — ожидает оценки
- **Нулевые изменения в спецификации языка**: чистое инкрементальное расширение инструментария

### Этапы (синхронизированы с #154)

| Этап                               | Содержание                                                                                                                                                                                                                                     | Оценка длительности |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| **v0.8.x (MVP)**                   | `src/mcp/{mod.rs, server.rs, transport/stdio.rs, project.rs, schema.rs}` + `parse_source` + `format_source` + `lookup_symbol` + `find_references` + `typecheck` (**5 инструментов**) + подкоманда `yaoxiang mcp` + `World::load_*` при запуске | **3-4 недели**      |
| **v0.9.x (YaoXiang Intelligence)** | `+ explain_diagnostic` (**прямой вызов** `render_explain_output`) + `+ list_imports` (оборачивает `ModuleGraph::validate_imports`) + юнит/интеграционные тесты                                                                                 | **1-2 недели**      |
| **v0.10.x (AST + HTTP)**           | `+ rename_symbol` (**новое** `src/middle/rename.rs`, перезапись AST) + streamable HTTP-транспорт + оптимизация производительности (parse_source P99 < 100ms)                                                                                   | **2-3 недели**      |

**Почему 3 этапа**: MVP сначала запускает stdio + 5 инструментов для проверки обоснованности дизайна
интерфейса; v0.9.x добавляет низкорисковые, не требующие адаптации «специфичные для YaoXiang»
инструменты для проверки корректности интеграции; v0.10.x открывает высокорисковый новый модуль
«перезаписи AST» (независимое ревью PR более сфокусировано).

### Риски

1. **Активность поддержки `mcp-rust-sdk`**: выпущен только в 2025 году, API может резко меняться.
   **Смягчение**: при нестабильности — написать лёгкий JSON-RPC 2.0 + tool dispatcher самостоятельно
   (< 500 строк)
2. **Затраты на повторный разбор**: AI многократно корректирует исходный код и многократно вызывает
   `parse_source`, что приводит к повторному lexer+parser. **Смягчение**: `DocumentCache` из RFC-017
   всё ещё может ускорить повторный разбор того же source с диска; для чисто временного source
   однократный разбор неизбежен
3. **Совместимость схем AI-агентов**: разные агенты имеют разную строгость MCP schema.
   **Смягчение**: использование crate `schemars` для автоматической генерации схем из Rust
   input-структур, ноль дрейфа рукописного кода
4. **Кроссплатформенное разрешение путей**: в Windows пути нечувствительны к регистру, UNC-пути,
   границы `\\`. **Смягчение**: для разрешения путей использовать `camino::Utf8Path` вместо
   `std::path`
5. **Схема инструмента MCP и входные параметры LSP не 1:1**: LSP `workspace_symbol` принимает
   `(query)`; для передачи внутрь LSP нужно обернуть в позицию+URI, чтобы существующий handler мог
   быть повторно использован. **Смягчение**: сделать слой адаптации в `mcp/tools/lookup.rs`,
   инкапсулируя детали на стороне MCP
6. **Семантика перезаписи AST в `rename_symbol` отличается от LSP `rename`**: LSP
   `textDocument/rename` — это URI + позиция + new_name → WorkspaceEdit; MCP `rename_symbol` — это
   source + old_name + new_name → новый source. **Не может быть повторно использован напрямую**.
   **Смягчение**: отдельная реализация `src/middle/rename.rs`, scope-aware перезапись ссылок,
   реализация не мешает LSP handler
