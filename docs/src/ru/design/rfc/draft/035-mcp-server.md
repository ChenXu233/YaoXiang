# RFC-035: Поддержка MCP Server (интеграция с AI Agent)

## Резюме

Добавить в YaoXiang сервер MCP (Model Context Protocol), чтобы AI-агенты (Claude Code, Continue,
Cody, Zed и др.) могли напрямую запрашивать **AST, ошибки разбора, типы, символы, ссылки, результаты
форматирования** исходного кода YaoXiang. Используя уже реализованный в RFC-017 бэкенд `World`,
добавить подкоманду `yaoxiang mcp` — единый бинарник с двумя режимами, отдельный `World` на процесс.

## Мотивация

### Зачем нужна эта возможность?

RFC-017 сделал так, что YaoXiang **может** быть понят редакторами (hover / goto-def / completion).
Но LSP — это **позиционно-ориентированный** протокол:

- Каждый запрос жёстко зависит от `textDocument` URI + `Position`
- Редактор должен сначала открыть файл, сохранить, поддерживать долгое соединение с LSP-сервером
- Рабочий процесс AI-агента — это **фрагменты кода**: «вставить кусок кода» в диалоге и задать
  вопрос, **не** сохраняя на диск

Реально доступные LSP-клиенты для AI-агентов (vscode-langservers-extracted, проекты вроде
`mcp-lsp-bridge`) **переводят только L1**: goto-def, hover. Чего хочет AI:

- «Этот код **разбирается правильно**?» — нужен parse + полный поток диагностики
- «Как этот символ **используется в файле**?» — нужен lookup_symbol по имени
- «Как выглядит этот код **после форматирования**?» — нужен format_source
- «Где **все** ошибки типов?» — нужен typecheck по всему рабочему пространству

Существующие L1-трансляции LSP **не справляются** — LSP по дизайну этого не поддерживает.

### Текущая проблема

1. Плохой опыт AI-агента при вызове LSP: нужны mock-документы, огромный JSON, жёсткая зависимость от
   URI
2. В проекте YaoXiang отсутствует «AI-First» интерфейсный слой: человек использует IDE с LSP,
   AI-агент не может работать с LSP
3. Главные AI-агенты — Claude Code / Continue и др. — по умолчанию поддерживают MCP; для YaoXiang
   эта экосистема — белые пятна

### Что такое MCP?

MCP (Model Context Protocol) — опубликованный и открытый в 2024–2025 годах под руководством
Anthropic протокол вызова инструментов для AI-агентов, ставший де-факто стандартом (подключились
OpenAI, Google, Microsoft, Zed, Continue, Cody и др.). Особенности:

- На основе JSON-RPC 2.0 (общие корни с LSP)
- Три примитива: **Tools** (действия), Resources (данные), Prompts (шаблоны)
- Транспорт: `stdio` (подпроцесс) / streamable `HTTP` / SSE
- Входы и выходы инструментов имеют строгую **JSON Schema** типизацию (удобно для LLM)
- В 2025-06+ опубликована спецификация streamable HTTP, данный RFC одновременно совместим со старым
  SSE

**Данный RFC использует только примитив Tools** — выравниваясь с «предоставлением сервисов» в LSP и
не вводя сложности файловой модели Resources.

## Предложение

### Основной дизайн

Единый бинарник с двумя режимами:

```text
┌─────────────────────────────────────────────────────────┐
│                    yaoxiang (v0.7.7+)                   │
│  ┌─────────────────┐      ┌──────────────────────────┐  │
│  │ yaoxiang lsp    │      │   yaoxiang mcp           │  │
│  │ (stdio JSON-RPC)│      │   (stdio default         │  │
│  │ RFC-017 уже     │      │    + HTTP опционально)   │  │
│  │ реализован      │      │                          │  │
│  └────────┬────────┘      └──────────┬───────────────┘  │
│           │                         │                   │
│           ▼                         ▼                   │
│  ┌──────────────────────────────────────────────────┐  │
│  │  Общий lib crate (`yaoxiang`)                     │  │
│  │  src/lsp/{server,session,world}.rs                │  │
│  │  src/frontend/{lexer,parser,core}/...             │  │
│  │  src/middle/...                                   │  │
│  └──────────────────────────────────────────────────┘  │
│                                                          │
│  ┌──────────────────────────────────────────────────┐  │
│  │            src/mcp/  ← новое                      │  │
│  │  ├── mod.rs          (вход модуля + запуск)       │  │
│  │  ├── transport/      (stdio + HTTP/SSE)          │  │
│  │  ├── server.rs       (цикл сообщений JSON-RPC)    │  │
│  │  ├── tools/          (обработчики 6 инструментов) │  │
│  │  ├── schema.rs       (JSON Schema входов/выходов) │  │
│  │  └── project.rs      (определение корня проекта + │  │
│  │                       разрешение путей)            │  │
│  └──────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

**Ключевые решения**:

- **Один бинарник**: `yaoxiang` переключается через подкоманду; процессы LSP и MCP **не
  сосуществуют** в одном рантайме
- **Изолированный World на процесс**: каждый процесс `yaoxiang mcp` владеет одним `World`; не
  взаимодействует с LSP-процессом и другими MCP-процессами (без конкуренции за блокировки,
  независимая изоляция падений)
- **stdio по умолчанию**: исключает конфликты портов, не требует сетевой настройки; HTTP —
  опциональный запасной вариант
- **Переиспользование, а не дублирование**: напрямую вызывает API lib `yaoxiang::frontend` /
  `yaoxiang::middle` / `yaoxiang::lsp::handlers`, **не** через LSP-клиентскую прослойку

### Набор инструментов (8 инструментов, доставка в 3 этапа)

Спроектировано по принципу «устранения особых случаев + поэтапность»: stateless-инструменты для
чистого исходного кода идут первыми, инструменты рабочего пространства разделяют World из LSP,
инструменты AST-перезаписи добавляются отдельно.

| Имя инструмента      | Вход                                                                                            | Выход                                                        | Переиспользование                                                            | Этап        |
| -------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------- | ----------- |
| `parse_source`       | `source: String`, `tab_size?: u32`                                                              | `{ast: Node, diagnostics: Diagnostic[]}`                     | напрямую `frontend::parse`                                                   | v0.8.x      |
| `format_source`      | `source: String`, `tab_size?: u32`                                                              | `{formatted: String, diff: Hunk[]}`                          | напрямую `formatter::format`                                                 | v0.8.x      |
| `lookup_symbol`      | `query: String`, `workspace_root?: String`, `kind?: SymbolKind[]`                               | `{symbols: Symbol[]}`                                        | переиспользует `lsp::handlers::workspace_symbol` (нечёткий поиск по `query`) | v0.8.x      |
| `find_references`    | `query: String`, `workspace_root?: String`                                                      | `{locations: Location[]}`                                    | переиспользует `lsp::handlers::references` (по `query`, не позиции)          | v0.8.x      |
| `typecheck`          | `file_paths: String[]`, `project_root: String`                                                  | `{diagnostics: Diagnostic[], summary: Counts}`               | переиспользует `lsp::world::typecheck_full`                                  | v0.8.x      |
| `explain_diagnostic` | `code: String` (например, `E0001`), `lang?: String`                                             | `{code, category, title, description, example, help}`        | **напрямую** `util::diagnostic::command::render_explain_output`              | **v0.9.x**  |
| `list_imports`       | `file_path: String`, `project_root?: String`                                                    | `{imports: [{module, items, source_file}]}`                  | переиспользует `middle::passes::module::ModuleGraph::validate_imports`       | **v0.9.x**  |
| `rename_symbol`      | `source: String`, `old_name: String`, `new_name: String`, `scope?: "module" \| "function:name"` | `{source: String, edits: Edit[], diagnostics: Diagnostic[]}` | **новое** `src/middle/rename.rs` (AST-перезапись)                            | **v0.10.x** |

**Границы 8 инструментов**:

- `parse_source` / `format_source` — **stateless для чистого исходного кода**, не трогают World
- `lookup_symbol` / `find_references` — принимают `workspace_root` (если не передан — используется
  `--project-root` при запуске)
- `typecheck` — **`file_paths` обязателен**, обеспечивает полноту рабочего пространства
- `explain_diagnostic` — **нулевая зависимость от файлов**, чисто строковый запрос к реестру кодов
  ошибок
- `list_imports` — `file_path` — физический файл, выдаёт результат разбора импортов этого файла
- `rename_symbol` — **AST-перезапись чистого исходного кода**, без позиционного запроса в стиле LSP
  (семантика отличается от существующего `lsp::handlers::rename`)
- ~~`hover` / `completion` / `signature_help`~~ — **все вырезаны**: AI-агент не выполняет
  «позиционно-чувствительную» семантику, вместо этого используется `lookup_symbol` по имени

**Время загрузки World**: при старте сервера по `--project-root` сканируются `yaoxiang.toml` и
`src/**/*.yx`, переиспользуется API `World::load_*` из LSP-017 для однократной загрузки в
`World.documents`. **Никаких** новых API в lib не добавляется.

### Контракт инструмента

**Вход**: описывается JSON Schema, каждое поле имеет `description` + `examples` (LLM читает
автоматически).

**Выход**: структурированный JSON, единообразно содержит поле `schemaVersion: "1.0"`:

```jsonc
// Успешный ответ
{
  "schemaVersion": "1.0",
  "isError": false,
  "content": [
    { "type": "json", "json": { /* специфичные данные инструмента */ } }
  ]
}

// Диагностика возвращается структурированно (не считается ошибкой инструмента)
{
  "schemaVersion": "1.0",
  "isError": false,
  "content": [{ "type": "json", "json": {
    "ast": {...},
    "diagnostics": [
      { "code": "E0001", "severity": "error", "message": "...", "span": [12, 4, 12, 18] }
    ]
  }}]
}

// Ошибка уровня инструмента (например, parse_source получил невалидный UTF-8)
{
  "schemaVersion": "1.0",
  "isError": true,
  "content": [{ "type": "text", "text": "MCP-INVALID-INPUT: source не является валидным UTF-8" }],
  "errorCode": "MCP-INVALID-INPUT"
}
```

**Система ошибок**:

- **Диагностика**: ошибки разбора/типизации, продолжает RFC-013 (`E0001` и др.) — **не считается**
  ошибкой инструмента
- **Ошибки уровня инструмента**: используют префикс `MCP-` (`MCP-INVALID-INPUT`,
  `MCP-PROJECT-NOT-FOUND`, `MCP-INTERNAL`) — рассматриваются как `isError: true`
- **panic/crash**: JSON-RPC `-32603 Internal error`, сервер не завершается

**Правила разрешения путей** (применяются к `workspace_root` для `lookup_symbol` /
`find_references`, к `file_paths` для `typecheck`):

1. CLI-флаг `--project-root <dir>` имеет наивысший приоритет (перекрывает умолчание)
2. Иначе: от cwd вверх ищется `yaoxiang.toml` до корня файловой системы (как в RFC-015)
3. Иначе: сам cwd
4. `file_paths` должны находиться внутри корня проекта (защита от выхода наружу); выход за пределы →
   `MCP-PATH-OUTSIDE-PROJECT`

### Транспортный уровень

**stdio (по умолчанию)**:

```bash
yaoxiang mcp
# после запуска читает JSON-RPC из stdin, пишет в stdout, stderr для логов
```

Конфигурация AI-агента (Claude Code `.mcp.json` / Continue `config.json`):

```jsonc
{
  "mcpServers": {
    "yaoxiang": {
      "command": "yaoxiang",
      "args": ["mcp", "--project-root", "${workspaceFolder}"],
    },
  },
}
```

**streamable HTTP (опционально)**:

```bash
yaoxiang mcp --http --addr 127.0.0.1:7325  # один HTTP-порт, новая спецификация MCP
yaoxiang mcp --http --sse --addr 127.0.0.1:7325  # совместимость со старым SSE (v0.10)
```

**Ограничения безопасности**:

- **Слушать только loopback** (127.0.0.1 / ::1); привязка к публичному адресу явно отвергается с
  ошибкой и завершением
- HTTP **без аутентификации** (loopback по умолчанию доверяется); в будущем — поле
  `--require-token <hex>`
- stdio-режим подпроцесса изолирован по своей природе (parent-процесс управляет правами)

### Многопроцессность и параллелизм

Каждый процесс `yaoxiang mcp` владеет одним `World`, без общего доступа:

```text
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ yaoxiang    │   │ yaoxiang    │   │ yaoxiang    │
│   lsp       │   │   mcp       │   │   mcp       │
│ (Editor 1)  │   │ (Claude 1)  │   │ (Claude 2)  │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │ stdio/stdout    │ stdio          │ stdio
   ┌───┴────┐        ┌───┴────┐        ┌───┴────┐
   │ Editor │        │ Claude │        │ Claude │
   └────────┘        └────────┘        └────────┘
```

**Конфликты портов**: AI-агенты настроены на «запуск подпроцесса» — конфликты портов исключены по
природе. В HTTP-режиме пользователь сам управляет распределением портов. **Изоляция World**: каждый
процесс имеет независимое состояние синхронизации LSP — падение одного MCP-процесса **не влияет** на
LSP/другие MCP-процессы. **Будущие Sessions**: распределение по нескольким рабочим пространствам
(несколько `Session` в одном процессе) рассматривается только в v2, **данный RFC этого не делает**.

## Детальный дизайн

### Структуры данных

Новое в `src/mcp/project.rs`:

```rust
pub struct ProjectRoot {
    /// абсолютный путь
    pub root: PathBuf,
    /// источник стратегии определения корня проекта при загрузке
    pub source: ProjectRootSource,
}

pub enum ProjectRootSource {
    CliFlag,           // yaoxiang mcp --project-root
    AutoDetected,      // поиск yaoxiang.toml вверх
    FallbackCwd,       // откат на cwd
}

pub struct ResolvedPath {
    /// путь относительно корня проекта (рекомендуется для чтения AI)
    pub relative: String,
    /// абсолютный путь после разрешения (для операций с World)
    pub absolute: PathBuf,
}

impl ProjectRoot {
    /// Разрешает "file_path" в безопасный путь — защита от выхода наружу
    pub fn resolve(&self, file_path: &str) -> Result<ResolvedPath, McpError>;
}
```

`ProjectRoot` — singleton + автоматическая генерация schema инструментов в `src/mcp/schema.rs`:

```rust
pub struct ProjectRoot {
    /// абсолютный путь (должен содержать `yaoxiang.toml` или совместимый откат)
    pub root: PathBuf,
    pub source: ProjectRootSource,
}

impl ProjectRoot {
    /// Однократное определение при старте CLI, результат кэшируется в
    /// контексте `McpServer` — используется всеми инструментами
    pub fn detect(cli_override: Option<PathBuf>) -> Result<Self, McpError>;
}
```

Schema инструментов автоматически генерируется из input struct через crate `schemars`, исключая
дрейф рукописной JSON Schema:

```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ParseSourceInput {
    /// Полный фрагмент исходного кода YaoXiang — **не** сохраняется на диск,
    /// чисто transient
    pub source: String,
    pub tab_size: Option<u32>,
}
```

**В schema инструментов `parse_source` / `format_source` нет поля `file_path`** — эти два
инструмента принимают только строковый источник и не участвуют в семантике проекта. `lookup_symbol`
/ `find_references` / `typecheck` принимают `workspace_root` или `file_paths` (обязательность — см.
таблицу инструментов).

### Изменения в компиляторе

| Модуль                                 | Изменение                                                                                                                     |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `src/lsp/world.rs`                     | **Нет изменений** — при старте MCP вызывается существующий API `World::load_*` для однократной загрузки рабочего пространства |
| `src/lsp/handlers/workspace_symbol.rs` | **Нет изменений** — `mcp/tools/lookup.rs` оборачивает `query` в LSP-вход                                                      |
| `src/lsp/handlers/references.rs`       | **Нет изменений** — то же                                                                                                     |
| `src/lsp/handlers/formatter.rs`        | **Нет изменений** — format_source вызывается напрямую                                                                         |
| `src/main.rs`                          | добавить ветку подкоманды `Mcp`                                                                                               |
| `Cargo.toml`                           | добавить feature `mcp-server` (или всегда в основном бинарнике)                                                               |
| `src/util/diagnostic/`                 | **Нет изменений** (реализовано в RFC-017)                                                                                     |

**Ключевое ограничение**: `src/mcp/` **не** должен обратно зависеть от приватных символов `src/lsp/`
— только через публичный API `crate::lsp::` вызывать handlers.

### Обратная совместимость

- ✅ **Полная обратная совместимость**: новая подкоманда `yaoxiang mcp`, не меняет никакого
  существующего поведения `yaoxiang` / `yaoxiang lsp`
- ✅ **LSP-сервер не меняется**: все возможности, API, внутреннее состояние, реализованные в
  RFC-017, остаются без изменений
- ✅ **Публичный API lib crate не меняется**: все `pub`-пути неизменны; MCP только потребляет
  существующий API — **ноль** новых `pub`-методов

| Существующий модуль                       | Способ интеграции MCP                                                                                  |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |

| `src/lsp/world.rs`                        | при старте вызывает API `World::load_*` (уже есть); World **не** принимает «виртуальные документы»     |
| `src/lsp/handlers/workspace_symbol.rs`    | `mcp/tools/lookup.rs` оборачивает, превращая `query: String` в LSP-вход (поиск по имени)               |

### Обработка ошибок

| Источник                                               | Обработка                                                                                               |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| Ошибки разбора                                         | `Diagnostic{code:"E0xxx", severity, message, span}` (**не ошибка инструмента**, возвращается в content) |
| Ошибки типов                                           | То же                                                                                                   |
| Выход `file_paths` за пределы (инструмент `typecheck`) | ошибка уровня инструмента `MCP-PATH-OUTSIDE-PROJECT`                                                    |
| Невалидный UTF-8 в `source`                            | ошибка уровня инструмента `MCP-INVALID-INPUT`                                                           |
| Panic инструмента                                      | JSON-RPC `-32603 Internal error`; сервер **не завершается**                                             |
| Клиент отправляет не JSON-RPC                          | Немедленный разрыв потока (stdio EOF), перезапуск = новая сессия                                        |

Уровни серьёзности диагностики продолжают `enum ErrorKind { Error, Warning, Note }` из RFC-017 (уже
реализован).

### Стратегия тестирования

| Уровень         | Тест                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Unit**        | `src/mcp/project.rs::resolve` — выход за пределы пути; `src/mcp/schema.rs` — валидация schema                                       |
| **Integration** | mock stdio: запустить сервер, подать JSON-RPC в stdin, прочитать ответ из stdout, сравнить с fixture                                |
| **E2E**         | запустить реальный процесс `yaoxiang mcp`, цепочка вызовов инструментов в стиле Claude Code: parse → исправить → format → typecheck |
| **Fuzz**        | `cargo-fuzz` для разбора JSON-RPC в MCP (harness на libFuzzer)                                                                      |

Для каждого инструмента должно быть как минимум 1 happy path + 1 сценарий с диагностикой + 1
сценарий с ошибкой инструмента в integration-тестах.

## Компромиссы

### Преимущества

- **Минимальная стоимость переиспользования**: `World` / `Session` / `handlers` / сбор диагностики —
  всё уже реализовано (RFC-017), данный RFC — это «добавление MCP-оболочки»
- **AI-First интерфейс**: контракт инструмента в 3–5 раз интуитивнее LSP; LLM читает schema напрямую
- **Многопроцессная изоляция**: отделено от LSP-сессии редактора и других MCP-процессов, **ноль
  конкуренции за блокировки**
- **stdio-дружественность**: все основные AI-агенты по умолчанию работают в режиме подпроцесса,
  подключение без настройки
- **YAGNI соблюдён**: данный RFC отрезает Resources, Sessions, межпроцессное состояние, удалённый
  MCP — это для v2

### Недостатки

- **Фрагментация протоколов**: в будущем LSP / MCP / DAP три протокола развиваются каждый по-своему,
  затраты на поддержание согласованности
- **HTTP-режим — второй сорт**: ограничение loopback позиционирует его как локальный инструмент, для
  удалённых сценариев нужен редизайн в v2
- **Накладные расходы на повторный разбор**: AI постоянно подправляет исходный код и вызывает
  `parse_source` → повторные lexer+parser. **Смягчение**: `DocumentCache` из RFC-017 всё ещё
  ускоряет повторный разбор **дискового** source с тем же содержимым; для чисто transient source
  однократный разбор неизбежен
- **Затраты на тестовое покрытие**: 5 инструментов × 3 сценария = минимум 15 integration-тестов

## Альтернативы

| Альтернатива                                                                    | Почему не выбрана                                                                                                    |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Внутрипроцессное встраивание двух протоколов** (LSP+MCPlistener сосуществуют) | stdin/stdout может иметь только одного потребителя; HTTP тоже должен сосуществовать — сложность > выгода             |
| **MCP как мост к LSP-клиенту**                                                  | Дополнительный слой IPC; LSP по дизайну не поддерживает поиск символов по имени — нужные MCP возможности LSP не даёт |
| **gRPC / собственный протокол**                                                 | Отход от де-факто стандарта; у сообщества уже есть MCP SDK (TypeScript, Python, Rust) с готовой экосистемой          |
| **Переиспользовать все возможности LSP handler** (набор L3-инструментов)        | Много адаптационной работы position↔intent; убывающая предельная отдача                                              |
| **Первая версия только HTTP** (без stdio)                                       | Claude Code / Continue и др. по умолчанию используют stdio — слишком высокий порог входа                             |

## Стратегия реализации

### Зависимости

- **Сильные зависимости**: реализация LSP из RFC-017 (уже готова)
- **Сильные зависимости**: система кодов ошибок из RFC-013 (уже готова)
- **Сильные зависимости**: определение корня проекта из RFC-014 / RFC-015 (частично готово)
- **Новые зависимости** (Rust crate):
  - `mcp-rust-sdk` (к оценке, см.
    [modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk))
  - `tokio` (**уже есть**, optional feature)
  - `axum` (для HTTP-режима) или напрямую `hyper` — к оценке
- **Нулевые изменения языковой спецификации**: чистый инкремент в инструментарии

### Этапы внедрения

| Этап                               | Содержание                                                                                                                                                                                                                                    | Оценка срока   |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| **v0.8.x (MVP)**                   | `src/mcp/{mod.rs, server.rs, transport/stdio.rs, project.rs, schema.rs}` + `parse_source` + `format_source` + `lookup_symbol` + `find_references` + `typecheck` (**5 инструментов**) + подкоманда `yaoxiang mcp` + `World::load_*` при старте | **3–4 недели** |
| **v0.9.x (YaoXiang Intelligence)** | `+ explain_diagnostic` (**напрямую** `render_explain_output`) + `+ list_imports` (обёртка `ModuleGraph::validate_imports`) + unit/integration-тесты                                                                                           | **1–2 недели** |
| **v0.10.x (AST + HTTP)**           | `+ rename_symbol` (**новое** `src/middle/rename.rs`, AST-перезапись) + streamable HTTP-транспорт + оптимизация производительности (parse_source P99 < 100 мс)                                                                                 | **2–3 недели** |

**Почему 3 этапа**: MVP сначала запускает stdio + 5 инструментов для проверки разумности дизайна
интерфейса; v0.9.x добавляет низкорисковые «YaoXiang-специфичные» инструменты без адаптации для
проверки корректности интеграции; v0.10.x открывает высокорисковый модуль «AST-перезаписи»
(независимое ревью PR более сфокусировано).

### Риски

1. **Активность поддержки `mcp-rust-sdk`**: выпущен только в 2025 году, API может резко меняться.
   **Смягчение**: если нестабилен — написать свой лёгкий JSON-RPC 2.0
   - tool dispatcher (< 500 строк)
2. **Накладные расходы на повторный разбор**: AI постоянно подправляет исходный код и вызывает
   `parse_source` → повторные lexer+parser. **Смягчение**: `DocumentCache` из RFC-017 всё ещё
   ускоряет повторный разбор **дискового** source с тем же содержимым; для чисто transient source
   однократный разбор неизбежен
3. **Совместимость schema у AI-агентов**: разные агенты по-разному строги к MCP schema.
   **Смягчение**: автоматическая генерация schema из Rust input-структур через `schemars`, нулевой
   дрейф рукописного кода
4. **Многоплатформенное разрешение путей**: нечувствительность к регистру в Windows, UNC-пути,
   граница `\\`. **Смягчение**: использовать `camino::Utf8Path` вместо `std::path` для разрешения
   путей
5. **Не 1:1 соответствие schema инструмента MCP и входов LSP**: LSP `workspace_symbol` принимает
   `(query)`; для переиспользования существующего handler нужно обернуть в позицию+URI.
   **Смягчение**: адаптер в `mcp/tools/lookup.rs`, инкапсулирующий детали на стороне MCP
6. **`rename_symbol` AST-перезапись и LSP `rename` — разная семантика**: LSP `textDocument/rename`
   это URI + позиция + new_name → WorkspaceEdit; MCP `rename_symbol` это source + old_name +
   new_name → новый source. **Нельзя переиспользовать напрямую**. **Смягчение**: отдельная
   реализация `src/middle/rename.rs`, scope-aware перезапись ссылок, без помех реализации LSP
   handler
