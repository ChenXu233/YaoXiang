# RFC-027a: Фолбэк через доказательственные функции при проверке завершимости

## Резюме

Реализация пункта о повторном обсуждении, зарезервированного в протоколе решений RFC-027: для
**неструктурной рекурсии** (класс gcd — не непосредственно убывающая, взаимная рекурсия), которую не
покрывают четыре автоматические стратегии доказательства завершимости, предоставляется **фолбэк
через доказательственные функции** — мера и доказательство являются обычными функциями YaoXiang, без
нового синтаксиса, верифицируемыми проверщиком типов. Механизм позиционируется как **одно из
применений протокола доказательств уточняющих типов**: со стороны доказательства — ноль новых
механизмов (существующий канал фолбэка Unproven из RFC-027 используется как есть), новым является
только порождение обязательств в точке вызова на стороне компилятора и один пропозициональный якорь.
Принцип приоритета полной автоматизации остаётся неизменным: автоматические стратегии по-прежнему
являются первым путём, вмешательство пользователя происходит только после Unproven.

## Мотивация

### Право на существование и область пересмотра

RFC-027 не зарезервировал слот под-RFC (в отличие от модели RFC-029, зарезервировавшего 029a). Право
на существование данного под-RFC вытекает из самого пункта о повторном обсуждении в протоколе
решений RFC-027:

> Циклы, завершимость которых не может доказать ни одна стратегия, компилятор отвергает сразу — это
> философия жёсткой безопасности, а не дефект. **Если в будущем в реальном сценарии (не
> академической конструкции) встретится алгоритм, который не покрывают все четыре стратегии, вопрос
> будет обсуждён повторно.** — Протокол решений RFC-027

Данный RFC и является формальным носителем этого «повторного обсуждения». Он **не отменяет**
зафиксированное решение — сам пункт является частью решения, и его срабатывание — это работа решения
по задумке; это предполагаемое осуществление пункта.

Область пересмотра RFC-027 точно ограничена тремя точками:

| Точка пересмотра                                          | Исходная запись                                                       | После пересмотра                                                                                                                                                                                                                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| §7 «Не оставлять лазеек для полуавтоматических аннотаций» | Проверка завершимости полностью закрыта                               | Сужено до «нет лазеек для **синтаксиса аннотаций**» — фолбэк через доказательственную функцию не является аннотацией (нет нового синтаксического слота, не挂在 определении функции), что соответствует тому же мировоззрению, что и «у предикатов времени компиляции нет новых ключевых слов» |
| Запись решения «Unproven → ошибка сразу»                  | Единственный домен доказательств без фолбэка                          | Изменено на «Unproven → можно предоставить доказательственную функцию» — поведение согласовано с доменом корректности (Unproven предиката → доказательственная функция, RFC-027 §Доказательственные функции)                                                                                  |
| §6.8 Текст сообщения об ошибке                            | «Пожалуйста, используйте шаблон итерации, анализируемый компилятором» | Добавлено «или предоставьте функцию-меру и доказательственную функцию завершимости»                                                                                                                                                                                                           |

**Не пересматривается**: приоритет четырёх автоматических стратегий, принцип приоритета полной
автоматизации, остальное содержание философии жёсткой безопасности (Disproved по-прежнему является
ошибкой компиляции + контрпример; поведение домена корректности не меняется).

### Текущая проблема (замеры от 2026-09-14, dev после v0.7.14)

1. **TerminationChecker способен доказать только структурную рекурсию.** `termination.rs` сейчас на
   Фазе 1: стратегия 3 (ограниченное возрастание/убывание), непосредственное убывание рекурсивного
   аргумента (`factorial(n-1)`), естественная завершимость цикла `for`. Стратегии 1/2/4 ещё не
   реализованы (запланировано в RFC-027). Неструктурная рекурсия сразу даёт сбой компиляции:

   ```yaoxiang
   gcd: (a: Int, b: Int) -> Int = {
       if b == 0 { return a }
       return gcd(b, a % b)
   }
   ```

   Рекурсивные аргументы `(b, a % b)` не являются непосредственным убыванием аргумента — сейчас
   выдаётся ошибка с требованием переписать в итеративный шаблон. gcd нельзя переписать в
   «анализируемый итеративный шаблон», не разрушив читаемость; то же относится к разбиению в
   сортировке слиянием, взаимной рекурсии (проверка чётности/нечётности), обходу дерева. Это
   реальные алгоритмы, а не академические конструкции — **условие срабатывания пункта о повторном
   обсуждении выполнено**.

2. **Асимметрия фолбэка в доменах доказательств.** В корректностных пропозициях RFC-027 (предикаты
   `Positive(b)`, `IsMax` и т.п.) при Unproven есть фолбэк через доказательственную функцию;
   завершимость — единственный из всех доменов доказательств, где Unproven означает тупик. В рамках
   того же мировоззрения у этой асимметрии нет принципиального основания.

3. **Инфраструктура готова.** #292 уже реально подключил бэкенд Z3 (цепочка `ConstExpr` → SMTLib →
   решение Unsat/Sat). Обязательство убывания меры в точке рекурсивного вызова
   `measure(args') < measure(args)` — это пропозиция линейной арифметики первого порядка, попадающая
   точно в уже налаженный разрешимый фрагмент — повторно используется та же цепочка, без нового
   бэкенда.

## Предложение

### Основной замысел

**Позиционирование: данный RFC не вводит нового механизма доказательств, это одно из применений
протокола доказательств уточняющих типов.** RFC-027 уже установил «доказательственная функция — это
функция YaoXiang, чей возвращаемый тип является пропозицией» — пропозиция есть применение предиката,
применение предиката есть уточняющий тип. Вся человеческая сторона доказательства завершимости идёт
по этому существующему каналу (Unproven → написать доказательственную функцию → проверка проверщиком
типов → стирание witness), полностью по тому же протоколу, что и в домене корректности. Новая
поверхность сводится к трём вещам:

1. **Функция-мера** — обычная функция времени компиляции, с той же сигнатурой аргументов, что и
   измеряемая функция, возвращающая `Int` или кортеж `Int` (лексикографический порядок). Это не
   аннотация, не挂在 определении функции, это функция первого класса, которую можно ссылаться и
   тестировать изолированно.
2. **Порождение обязательств в точке вызова** — компилятор извлекает из тела `f` обязательства
   убывания для каждой точки рекурсивного вызова. Это единственная новая логика компилятора:
   фактические аргументы в точке вызова живут внутри тела функции, обязательства (семантические
   ограничения) должны генерироваться компилятором, человек не может их подменять — иначе
   доказательство больше не привязано к реальному коду (см. пункт 3 философии дизайна).
3. **Пропозиция завершимости `Terminates(f, m)`** — **предикат уточнения, тело которого пишет
   компилятор**: его «содержание ограничений» есть указанный набор обязательств, его сигнатура —
   лишь якорь, связывающий `(f, m)` воедино. Необходимость встроенности только в этом; механически
   ничего нового нет. В сигнатуру входят и функция, и мера, а не только мера: при взаимной рекурсии
   `is_even`/`is_odd` имеют одинаковые сигнатуры, и только обнаружение по мере порождает
   неоднозначность (см. пример).

Три роли доказательственной функции естественно выводятся из позиционирования: явное связывание меры
`m` с `f` (якорь обнаружения, заменяющий любой синтаксис аннотаций); место для разрядки остаточных
обязательств (тело = пространство доказательств); универсальная квантификация по именам параметров
`f` (в теле можно ссылаться на `a`, `b` для записи фактов). Синтаксис по точкам см. в «Детальном
синтаксисе», полный разбор — в разделе «Примеры».

### Примеры

#### Подробный разбор от начала до конца: gcd

```yaoxiang
-- Измеряемая функция (домен корректности как обычно: уточнение аргументов, гард, рекурсивный вызов)
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

-- Мера: обычная функция (можно тестировать изолированно, можно переиспользовать)
gcd_measure: (a: Int, b: Int) -> Int = { b }

-- Доказательственная функция: пустое тело — все обязательства автоматически закрыты SMT
gcd_proof: (a: Int, b: Int) -> Terminates(gcd, gcd_measure) = { }
```

Полный путь обработки компилятором `gcd_proof`:

1. **Валидация сигнатуры**: параметры доказательственной функции сопоставляются по одному с
   формальными параметрами `gcd` по **базовым типам** (`Int`, `Int`). Уточнения формальных
   параметров (`b >= 0`) не повторяются в сигнатуре доказательственной функции — они уже
   удерживаются компилятором как контекст обязательств, и тело доказательственной функции, и
   обязательства проверяются в этом контексте.
2. **Обязательство обоснованности**: `gcd_measure(a, b) >= 0`, т.е. `b >= 0` — выводится
   непосредственно из уточнения формального параметра `NonNegative(b)`. Граница меры не требует
   нового механизма, это уточняющее ограничение аргумента (реализация семантических условий
   уточняющих типов на обоснованности).
3. **Порождение обязательств в точке вызова**: единственная точка рекурсивного вызова
   `gcd(b, a % b)`, гард пути `b != 0`, порождает `gcd_measure(b, a % b) < gcd_measure(a, b)`;
   подстановка тела меры раскрывается в `a % b < b`.
4. **Решение SMT**: проверка отрицания обязательства `b != 0 ∧ a % b >= b` невыполнима — линейная
   арифметика + аксиомы деления по модулю, миллисекунды → Proved.
5. **Принятие**: тело пусто, остаточных обязательств для разрядки нет. Завершимость `gcd` доказана;
   мера и доказательственная функция стираются как witness, не попадают в бинарник.

#### Непустое тело: ссылка на остаточные обязательства через доказанные леммы

Когда убывание в точке вызова зависит от фактов, невидимых компилятору (в примере ниже тело `step`
находится в модуле зависимости и является чёрным ящиком для порождения обязательств), человек
записывает этот факт в тело как **ссылку на доказанный предикат** — голое выражение, а не оператор
Assert:

```yaoxiang
step: (n: Int) -> Int = { ... }

loop_x: (n: NonNegative(n)) -> Void = {
    if n == 0 { return () }
    return loop_x(step(n))
}

x_measure: (n: Int) -> Int = { n }

-- Экспортируемое доказанное постусловие в модуле определения step (домен корректности, обычный предикат, доказан в месте определения):
step_decreases: (n: Int) -> Type = { n >= 1 ==> step(n) < n }

-- Доказательство завершимости = ссылка на эту лемму (ссылка на доказанный предикат = применение его установленного доказательства, Карри-Ховард):
x_proof: (n: Int) -> Terminates(loop_x, x_measure) = {
    step_decreases(n)
}
```

Ход проверки: обязательство `x_measure(step(n)) < x_measure(n)` (гард `n != 0`, контекст `n >= 0`)
не может быть самостоятельно закрыто в модуле `loop_x` → обнаружено непустое тело → утверждается,
что `step_decreases(n)` — экземпляр доказанного предиката, проверка проходит → закрывает остаточное
обязательство как лемма. Если в теле просто так написать `step(n) < n`, валидатор честно сообщит
Unproven — факт должен происходить из прослеживаемого доказанного источника.

#### Взаимная рекурсия: сбор обязательств по SCC

```yaoxiang
is_even: (n: NonNegative(n)) -> Bool = { if n == 0 { return true }  return is_odd(n - 1) }
is_odd:  (n: NonNegative(n)) -> Bool = { if n == 0 { return false } return is_even(n - 1) }

nat: (n: Int) -> Int = { n }

is_even_proof: (n: Int) -> Terminates(is_even, nat) = { }
is_odd_proof:  (n: Int) -> Terminates(is_odd, nat) = { }
```

Обязательства собираются по SCC, обязательства на межфункциональных рёбрах:
`m_callee(callee_args) < m_caller(caller_args)` — здесь `nat(n - 1) < nat(n)`, гард `n != 0`, обе
функции замыкаются по отдельности. Обе функции имеют одинаковые сигнатуры, и только обнаружение по
мере не различает цель — это прямое основание для двух аргументов `Terminates(f, m)`.

#### Отрицательный пример: мера не является строго убывающей

```yaoxiang
loop_forever: (n: Int) -> Int = { return loop_forever(n) }
loop_proof: (n: Int) -> Terminates(loop_forever, nat) = { }
```

Обязательство `nat(n) < nat(n)`, т.е. `n < n`, его отрицание всегда выполнимо (Sat, модель `n = 0`)
→ ошибка компиляции **E4022** (мера не является строго убывающей), контрпример указывает на
`loop_proof`. Если удалить `loop_proof`, автоматические стратегии не справляются и
доказательственной функции нет → **E4021** (завершимость не доказуема, предлагается предоставить
доказательственную функцию `Terminates`).

### Изменения синтаксиса

**Никаких.** Данный RFC не вводит никакого нового синтаксиса, ключевых слов, слотов для аннотаций.
Сопоставление с существующей родословной:

| Поколение           | Выражение со стороны пользователя                      | Синтаксический носитель                       |
| ------------------- | ------------------------------------------------------ | --------------------------------------------- |
| RFC-022 (отменён)   | Аннотация-комментарий `//! decreases: n`               | Соглашение о комментариях, без проверки типов |
| RFC-027 действующий | Нет (полная автоматизация, если не доказуемо — ошибка) | ——                                            |

## Философия дизайна: разделение обнаружения и верификации

Выбор механизма в данном RFC выводится из одного принципа: **проверка завершимости = обнаружение
свидетельства + верификация свидетельства; эти две задачи резко различаются по сложности и должны
быть разделены.**

| Роль                                                                                  | На ком лежит                                                                                                                 | Сложность                                                                                                             |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Обнаружение (синтез меры и доказательства)                                            | Четыре автоматические стратегии (машина, ограниченные шаблоны) или человеческая доказательственная функция (без ограничений) | В общем случае **неразрешимо** (сводится к проблеме остановки) — не существует алгоритма, который всегда находит меру |
| Верификация (для фиксированного кандидата — поточечная проверка `m(args') < m(args)`) | SMT (конвейер RFC-009a)                                                                                                      | Разрешимо (линейная арифметика первого порядка), миллисекунды                                                         |

«Неразрешимо искать, разрешимо проверять» — структурно изоморфно разделению witness/verifier в P/NP,
но ещё более экстремально: сторона обнаружения не просто сложна, математически у неё не всегда есть
решение; сторона верификации для фиксированного кандидата полностью механична. Отсюда «честное
сообщение об Unproven» в RFC-027 и человеческий фолбэк — не инженерный компромисс, а прямое
следствие этой границы.

Три следствия образуют проектные ограничения данного RFC:

1. **Доказывающему нельзя доверять, и это неважно.** soundness целиком живёт в верификаторе: мера
   или утверждение записаны неверно, SMT выдаёт Sat, E4022 возвращает с контрпримером — человек
   может не доказать, но не может доказать неверно. Disproved остаётся конструктивным (даёт модель
   контрпримера): верификатор делает на полшага больше, чем верификатор NP, опровержение тоже даёт с
   доказательством.
2. **Инсайт замораживается в проверяемом артефакте.** Интеллектуальный труд человека, будучи записан
   в доказательственную функцию, становится машинно-проверяемым сертификатом, перепроверяемым при
   каждой компиляции, навсегда защищённым от регрессий (proof-carrying).
3. **Пропозиции — компилятору, доказательства — человеку.** Обязательства («что считается
   доказанным») должны генерироваться компилятором из тела функции; если человек пишет и
   ограничения, он сам себе пишет стандарт приёмки, и сертификат больше не доказывает фактически
   написанный код.

Четыре автоматические стратегии получают здесь единое объяснение: это **ограниченная
последовательность шаблонов синтеза свидетельств** — автоматический синтез меры в литературе и есть
перечисление шаблонов под решением ограничений (синтез линейных ранговых функций как прецедент).
Расширение стратегий = расширение шаблонов; обнаружение за пределами шаблонов — за человеком;
верификатор всегда один и тот же SMT. Теоретическая форма не-цели «не делать вывод меры» тоже здесь:
общий вывод меры принадлежит неразрешимой стороне обнаружения, можно лишь договориться о её границах
(шаблоны), нельзя обещать её полноту.

## Детальный дизайн

### Детальный синтаксис

У доказательственной функции нет специального синтаксиса — это «определение предиката времени
компиляции», применённое иначе. Три точки закрепляются поочерёдно:

**Возвращаемый тип: применение предиката, фактический аргумент — ссылка на функцию.**
`Terminates(gcd, gcd_measure)` изоморфно существующим применениям уточнений в позиции типа
(`f(x: Positive(x))`, `-> (result: IsMax(T, arr, result))`); имя функции — обычное связывание по
имени (RFC-010), попадающее в существующее правило фактических аргументов предикатов «литералы,
переменные (связывание по имени), применение типов». Единственное дополнение на уровне правил: к
определению формы фактических аргументов E1092 добавляется «**ссылка на функцию относится к форме
констант времени компиляции**» — изменяется текст правила, грамматика не трогается.

**Параметры: зеркалят базовые типы `f`, универсальная квантификация.** Имена параметров и базовые
типы поочерёдно сопоставляются с формальными параметрами `f`, несовпадение — ошибка компиляции
(повторно используется семейство E1093 или новая регистрация, решается на этапе реализации).
Уточнения формальных параметров не повторяются — уточнения и допущения гардов внедряются
компилятором как контекст обязательств. Универсальная квантификация — это и есть параметрическая
семантика самого определения предиката (`x` в `Positive: (x: Int) -> Type = { x > 0 }` тоже
универсально квантифицирован). Беспараметрическая форма отвергнута: остаточные обязательства
ссылаются на имена параметров `f`, в теле имена должны быть доступны для записи.

**Тело: пространство доказательств, голые булевы выражения.** Тот же протокол, что и в теле
определения предиката `{ x > 0 }` — каждый элемент тела — голое выражение, утверждаемое истинным.
Пустое тело законно и является большинством сценариев (все обязательства закрываются SMT); непустые
утверждения после проверки скармливаются остаточным обязательствам как леммы; законным источником
утверждений является применение доказанных предикатов (см. пример «Непустое тело»).

**Обнаружение и связывание.** Компилятор для функции `f`, для которой не удался автоматический
синтез, в том же модуле и видимых импортах сканирует функции с возвращаемым типом вида
`Terminates(f, _)`; обнаружение идёт по возвращаемому типу, от имён не зависит (`f_proof` — лишь
естественное соглашение). Из нескольких кандидатов берётся первый, у которого все обязательства
зелёные (порядок объявления), при общем провале сообщается первый контрпример. Прямые ссылки
законны: обнаружение происходит на этапе проверки, от порядка объявления не зависит.

**Представление во время выполнения.** Доказательственная функция — чисто компиляционная сущность,
по модели CompileTime из RFC-027 со стиранием witness — ни мера, ни доказательственная функция не
попадают в бинарник.

### Порождение обязательств

Для функции `f` и меры `m` компилятор порождает два набора обязательств линейной арифметики первого
порядка, раскрываемых по каждой точке рекурсивного вызова (включая межфункциональные вызовы внутри
SCC); обязательство на межфункциональном ребре: `m_callee(callee_args) < m_caller(caller_args)`, при
общей мере у участников вырождается в убывание по одной и той же мере:

1. **Обоснованность**: `m(args) >= 0` — мера лежит в натуральных числах, выводится из границ типа
   аргумента; если не выводится, переходит в остаточные обязательства.
2. **Строгое убывание**: в каждой точке вызова `m(callee_args) < m(caller_args)`, оценивается при
   **гарде пути** (гард берётся из условия ветви, в которой находится точка вызова, повторно
   используется сбор путевых условий из RFC-009a).

**Раскрытие лексикографического порядка**: когда `m` возвращает кортеж `(m₁, …, mₖ)`, обязательство
по лексикографическому сравнению раскрывается в цепочку дизъюнкций:
`(m₁' < m₁) ∨ (m₁' == m₁ ∧ m₂' < m₂) ∨ …`. Раскрытие выполняется на стороне порождения обязательств,
на стороне SMT остаётся линейный фрагмент, без зависимости от нативной поддержки лексикографического
порядка решателем.

**Ограниченность самой функции-меры**: `m` должна быть вычислима во время компиляции (свёртка
констант) или доказуемо структурно рекурсивна — запрещено рекурсивно перекладывать проблему
завершимости на другую недоказанную функцию (защита от бесконечной регрессии). Патологические меры
отсекаются существующими E4012 (слишком глубокая константная рекурсия) и структурными проверками.

### Конвейер решения

`TerminationChecker` расширяется до пяти уровней; первые три — действующие/запланированные пути
RFC-027, данный RFC добавляет только последние два:

```
1. Структурная рекурсия непосредственно доказуема (действующая логика, без регрессии)
2. Автоматический синтез меры: четыре стратегии перебираются поочерёдно (стратегии 1/2/4 реализуются по плану RFC-027, данный RFC резервирует интерфейс)
3. Синтез успешен → SMT-решение обязательств → Proved
4. Синтез не удался (Unproven) → поиск доказательственной функции (возвращаемый тип вида Terminates(f, _)):
     a. Найдена → берётся её мера m, порождаются обязательства → SMT-решение
     b. Остаточные обязательства → проверяются как утверждения в теле доказательственной функции (тот же протокол, что для доказательственных функций в домене корректности)
5. Доказательственной функции нет / обязательства доказательственной функции всё равно не выполняются → ошибка компиляции (E4021 / E4022)
```

**Домен обнаружения доказательственных функций**: определённые в том же модуле, либо
экспортированные и видимые через `import` — следует существующим правилам видимости, без глобального
магического поиска. При нескольких кандидатах `Terminates(f, _)` для одной `f` берётся первый, у
которого все обязательства зелёные, при общем провале — первый контрпример (детерминированный
порядок: порядок объявления).

**Объявление встроенности `Terminates`**: для системы предикатов это особый случай — его
«утверждения» порождаются компилятором из тела `f` и не могут быть выражены синтаксисом предикатов
RFC-027. Это единственная намеренно встроенная пропозиция; обоснование зафиксировано в разделе
«Компромиссы».

### Коды ошибок

Согласованы с семейством ошибок доказательств E4xxx (E4018 нарушение уточняющего предиката, E4020
требуется доказательственная функция):

| Предложенный код | Имя                               | Срабатывание                                                                                                                         |

| E4021            | Завершимость не доказуема         | Автоматический синтез не удался и доказательственной функции нет (предлагается предоставить доказательственную функцию `Terminates`) |
| E4022            | Мера не является строго убывающей | Обязательства доказательственной функции признаны SMT как Sat (с входным контрпримером)                                              |

(легитимность диапазона гарантируется порогом build.rs); W1080 (деградация доказательства времени
компиляции) семантически с данным RFC не связан, не трогается.

### Обратная совместимость

- Программы, ранее проходившие компиляцию: поведение не меняется (первые три уровня конвейера
  выполняются раньше фолбэка).
- Программы, ранее не проходившие компиляцию: после добавления меры и доказательственной функции
  проходят — это разрешённое пунктом о повторном обсуждении ослабление, и затрагивает только «и так
  не компилировавшиеся» программы.
- Существующий тестовый корпус (положительные примеры структурной рекурсии, отрицательные
  неструктурные) — ожидаемый вывод не меняется, только коды/тексты ошибок для отрицательных
  неструктурных примеров обновляются под новые коды.

## Компромиссы

### Достоинства

- **Нулевой новый синтаксис**: в отличие от встроенной аннотации `decreases` в Dafny, данный дизайн
  не занимает синтаксического пространства; мера — функция первого класса, которую можно тестировать
  изолированно.
- **Согласованность поведения доменов доказательств**: в домене завершимости появляется фолбэк
  Unproven, согласующийся с доменом корректности; «философия жёсткой безопасности» эволюционирует от
  «не доказал — отвергаем» к «не доказал — передаём программисту» — что согласуется с мировоззрением
  всего RFC-027.
- **Повторное использование инфраструктуры**: обязательства — линейная арифметика, идут по уже
  налаженному конвейеру #292, без нового бэкенда, без нового семейства логик решения.
- **Реализация пункта = управление**: повторное обсуждение оставляет след в форме под-RFC, протокол
  решений остаётся аудитируемым.

### Недостатки и риски

- **Бремя написания**: связка из двух сущностей (мера + доказательственная функция) многословнее,
  чем одна встроенная аннотация. Принято — фолбэк это маловероятный путь, и в обмен получаем
  переиспользуемость и тестируемость меры.
- **`Terminates` — единственный предикат с телом, которое пишет компилятор**: отступление от чистоты
  «все тела предикатов пишутся пользователем». Обоснование: фактические аргументы в точке вызова
  живут в теле функции, библиотечный предикат в принципе не может на них ссылаться; встроенная
  поверхность сводится к одному имени пропозиции, механически ничего нового (см. «Основной замысел»
  и «Философия дизайна»).
- **Пока стратегии 1/2/4 не реализованы, фолбэк может срабатывать слишком рано**: на Фазе 1
  автоматическая поверхность узка, больше функций попадёт на путь доказательственной функции.
  Смягчение: после реализации четырёх стратегий поверхность фолбэка автоматически сужается;
  предварительное написание доказательственных функций не впустую — после обновления стратегий они
  продолжат служить носителями разрядки остаточных обязательств.
- **Качество контрпримеров**: Sat-контрпримеры для нелинейных гардов могут быть неинтуитивны.
  Зафиксировано как известное ограничение, представление контрпримеров итерируется по спецификации
  диагностических сообщений RFC-013.

## Не-цели

- Не вводить синтаксис/ключевые слова/слоты для аннотаций.
- Не делать обобщающего расширения автоматического синтеза меры (четыре стратегии сохраняют план
  RFC-027, за пределами射程 — через фолбэк).
- Не использовать совместное решение пропозиций с RFC-009a (каждый решает независимо, общий бэкенд).
- Не делать верификацию тотальности на уровне зависимых типов (totality checking).
- Не реализовывать вывод меры (угадывание меры из тела функции принадлежит射程 стратегий 1/2/4,
  данный RFC только потребляет явные меры — см. теоретическую границу в конце «Философии дизайна»).
