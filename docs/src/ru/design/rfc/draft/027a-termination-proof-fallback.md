# RFC-027a: Фолбэк через доказательственные функции для проверки завершимости

## Резюме

Реализация пункта о повторном обсуждении, зарезервированного в протоколе решений RFC-027: для
**неструктурной рекурсии** (непрямое убывание в стиле gcd, взаимная рекурсия), которую не покрывают
четыре автоматические стратегии, предоставляется **фолбэк через доказательственную функцию** — и
мера, и доказательство суть обычные функции YaoXiang, без нового синтаксиса, с верификацией на
уровне проверки типов. Принцип приоритета полной автоматизации остаётся неизменным: автоматические
стратегии по-прежнему являются первым путём, вмешательство пользователя происходит только после
Unproven.

## Мотивация

### Право на существование и объём правок

RFC-027 не зарезервировал слот под дочерний RFC (в отличие от модели RFC-029, зарезервировавшего
029a). Право на существование данного дочернего RFC проистекает из самого пункта о повторном
обсуждении в протоколе решений RFC-027:

> Циклы, завершимость которых не может быть доказана ни одной стратегией, приводят к прямой ошибке
> компилятора — это философия жёсткой безопасности, а не дефект. **Если в будущем появится реальный
> сценарий (а не академическая конструкция), в котором ни одна из четырёх стратегий не сможет
> покрыть алгоритм, вопрос будет обсуждён заново.** — Протокол решений RFC-027

Настоящий RFC и является формальным носителем этого «повторного обсуждения». Он **не отменяет**
зафиксированное решение — сам пункт является частью решения, и его срабатывание — это работа решения
по задумке; это ожидаемое применение пункта.

Объём правок в RFC-027 точно ограничен тремя местами:

| Точка правки                                              | Исходная запись                                           | После правки                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| §7 «Не оставлять лазеек для полуавтоматических аннотаций» | Проверка завершимости полностью замкнута                  | Сужение до «отсутствие лазеек в виде **синтаксиса аннотаций**» — фолбэк через доказательственную функцию не является аннотацией (нет новой синтаксической позиции, не привязан к определению функции), что соответствует тому же мировоззрению, что и «для предикатов времени компиляции нет новых ключевых слов» |
| Протокол решений «Unproven → прямая ошибка»               | Единственный домен доказательства без фолбэка             | Заменяется на «Unproven → можно предоставить доказательственную функцию» — поведение выравнивается с доменом корректности (Unproven предиката → доказательственная функция, RFC-027 §Доказательственные функции)                                                                                                  |
| §6.8 Текст сообщения об ошибке                            | «Используйте шаблон итерации, анализируемый компилятором» | Дополняется «или предоставьте функцию меры и функцию доказательства завершимости»                                                                                                                                                                                                                                 |

**Не подвергается правке:** приоритет четырёх автоматических стратегий, принцип приоритета полной
автоматизации, остальное содержание философии жёсткой безопасности (Disproved по-прежнему остаётся
ошибкой компиляции + контрпример; поведение домена корректности не меняется).

### Текущая проблема (замеры от 2026-09-14, после v0.7.14 в dev)

1. **TerminationChecker умеет доказывать только структурную рекурсию**. `termination.rs` сейчас
   находится в Phase 1: стратегия 3 (ограниченный рост/убывание), прямое убывание рекурсивного
   аргумента (`factorial(n-1)`), естественная завершимость `for` цикла. Стратегии 1/2/4 ещё не
   реализованы (запланированы в RFC-027). Неструктурная рекурсия приводит к прямому провалу
   компиляции:

   ```yaoxiang
   gcd: (a: Int, b: Int) -> Int = {
       if b == 0 { return a }
       return gcd(b, a % b)
   }
   ```

   Рекурсивные аргументы `(b, a % b)` — это не прямое убывание аргумента — текущая версия выдаёт
   ошибку и требует переписать в анализируемый шаблон итерации. Переписать gcd в «анализируемый
   шаблон итерации» без ущерба читаемости невозможно; то же касается разбиения при сортировке
   слиянием, взаимной рекурсии (проверка чётности/нечётности), обходов деревьев. Это реальные
   алгоритмы, а не академические конструкции — **условие срабатывания пункта о повторном обсуждении
   выполнено**.

2. **Асимметрия фолбэков в доменах доказательства**. Утверждения корректности из RFC-027 (предикаты
   `Positive(b)`, `IsMax` и т.п.) при Unproven имеют фолбэк через доказательственную функцию;
   завершимость — единственный из всех доменов доказательства, где Unproven ведёт в тупик. В рамках
   того же мировоззрения у этой асимметрии нет принципиального основания.

3. **Инфраструктура готова**. В #292 бэкенд Z3 уже реально подключён (цепочка `ConstExpr` → SMTLib →
   вердикт Unsat/Sat). Обязательство убывания меры в точке рекурсивного вызова
   `measure(args') < measure(args)` — это утверждение линейной арифметики первого порядка, аккуратно
   попадающее в уже открытый разрешимый фрагмент этой цепочки — повторно используется тот же
   конвейер, новый бэкенд не требуется.

## Предложение

### Ключевой дизайн

Три концепции, каждая из которых подчиняется принципу «всё есть функция YaoXiang»:

1. **Функция меры** — обычная функция времени компиляции, с сигнатурой аргументов, совпадающей с
   измеряемой функцией, возвращающая `Int` или кортеж `Int` (лексикографический порядок). Это не
   аннотация, не привязана к определению функции, это полноправная функция, на которую можно
   ссылаться и которую можно unit-тестировать.
2. **Утверждение завершимости `Terminates(f, m)`** — встроенное утверждение компилятора (не
   допускает переопределения пользователем): «функция `f` завершается относительно меры `m`». Его
   обязательства автоматически генерируются компилятором из тела `f` (см. детальный дизайн), поэтому
   выразить его как чисто библиотечный предикат невозможно.
3. **Функция доказательства завершимости** — функция времени компиляции с типом возврата
   `Terminates(f, m)`. У неё две роли: **явно связывает** меру `m` с `f` (единственная точка
   обнаружения и подключения, заменяющая любой синтаксис аннотаций); тело функции разряжает
   остаточные обязательства, которые SMT не закрыл (в большинстве сценариев тело пустое).

### Примеры

```yaoxiang
# Положительный пример 1: непрямое убывание — gcd
gcd: (a: Int, b: Int) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

gcd_measure: (a: Int, b: Int) -> Int = { b }

# Достаточно пустого тела: обязательство a % b < b (при условии охраны b ≠ 0) закрывается SMT напрямую
gcd_proof: () -> Terminates(gcd, gcd_measure) = { }
```

```yaoxiang
# Положительный пример 2: взаимная рекурсия — сбор обязательств по SCC
is_even: (n: Int) -> Bool = { if n == 0 { return true }  return is_odd(n - 1) }
is_odd:  (n: Int) -> Bool = { if n == 0 { return false } return is_even(n - 1) }

nat: (n: Int) -> Int = { n }

is_even_proof: () -> Terminates(is_even, nat) = { }
is_odd_proof:  () -> Terminates(is_odd,  nat) = { }
```

```yaoxiang
# Отрицательный пример: мера не убывает строго
loop_forever: (n: Int) -> Int = { return loop_forever(n) }
# Обязательство Terminates(loop_forever, nat) — это n < n — ложно —
# SMT выдаёт Sat → контрпример → ошибка компиляции E4022 (мера не убывает строго, с контрпримером)
```

### Изменения синтаксиса

**Никаких.** Настоящий RFC не вводит нового синтаксиса, ключевых слов, позиций для аннотаций.
Сопоставление с существующей родословной:

| Поколение           | Выражение со стороны пользователя                        | Синтаксический носитель                       |
| ------------------- | -------------------------------------------------------- | --------------------------------------------- |
| RFC-022 (отменён)   | Аннотация-комментарий `//! decreases: n`                 | Соглашение о комментариях, без проверки типов |
| Действующий RFC-027 | Отсутствует (полная автоматизация; не доказано — ошибка) | ——                                            |
| Настоящий RFC       | Мера + доказательство, обе — обычные функции             | Сам синтаксис определения функции             |

## Детальный дизайн

### Генерация обязательств

Для функции `f` и меры `m` компилятор генерирует две группы обязательств линейной арифметики первого
порядка, раскрывая по каждой точке рекурсивного вызова (включая межфункциональные вызовы внутри
SCC):

1. **Обоснованность (well-foundedness)**: `m(args) >= 0` — мера лежит в натуральных числах,
   выводится из границ типов аргументов; если вывести не удаётся, переходит в остаточные
   обязательства.
2. **Строгое убывание**: для каждой точки вызова `m(callee_args) < m(caller_args)`, проверяемое **в
   условиях пути** (условия берутся из охранных условий ветви, в которой находится точка вызова,
   повторно используется сбор путевых условий из RFC-009a).

**Раскрытие лексикографического порядка**: когда `m` возвращает кортеж `(m₁, …, mₖ)`, обязательство
раскрывается через лексикографическое сравнение в цепочку дизъюнкций —
`(m₁' < m₁) ∨ (m₁' == m₁ ∧ m₂' < m₂) ∨ …`. Раскрытие выполняется на стороне генерации обязательств,
на стороне SMT сохраняется линейный фрагмент, без зависимости от нативной поддержки
лексикографического порядка в решателе.

**Собственная ограниченность функции меры**: `m` должна вычисляться в период компиляции (свёртка
констант) либо быть доказуемо структурно рекурсивной — запрещается рекурсивно перекладывать задачу
завершимости на другую недоказанную функцию (защита от бесконечной регрессии). Патологические меры
отсекаются уже существующими E4012 (слишком глубокая константная рекурсия) и структурной проверкой.

### Конвейер верификации

`TerminationChecker` расширяется до пяти уровней; первые три — это действующие/запланированные пути
RFC-027, настоящий RFC добавляет только последние два:

```
1. Структурная рекурсия, прямо доказуемая (действующая логика, без регрессии)
2. Автоматический синтез меры: четыре стратегии, перебираемые по очереди (стратегии 1/2/4 реализуются по плану RFC-027, настоящий RFC резервирует интерфейс)
3. Синтез успешен → SMT-верификация обязательств → Proved
4. Синтез провалился (Unproven) → поиск доказательственной функции (тип возврата вида Terminates(f, _)):
     a. Найдена → берётся её мера m, генерируются обязательства → SMT-верификация
     b. Остаточные обязательства → верифицируются как утверждения в теле доказательственной функции (тот же протокол, что и для доказательственных функций домена корректности)
5. Доказательственной функции нет / обязательства доказательственной функции всё равно не проходят → ошибка компиляции (E4021 / E4022)
```

**Область обнаружения доказательственных функций**: определённые в том же модуле, либо
экспортированные и видимые через `import` — следуют существующим правилам видимости, никакого
глобального «магического» поиска. При наличии нескольких кандидатов `Terminates(f, _)` для одного
`f` берётся первый, у которого все обязательства зелёные; если несколько провалились, выдаётся
контрпример первого (детерминированный порядок: порядок объявления).

**Заявление о встроенности `Terminates`**: для системы предикатов это особый случай — её
«утверждения» генерируются компилятором из тела `f`, что невозможно выразить синтаксисом предикатов
из RFC-027. Это намеренно единственное встроенное утверждение, обоснование зафиксировано в разделе о
компромиссах.

### Коды ошибок

Выравнивание по семейству E4xxx ошибок доказательства (E4018 — нарушение уточнённого предиката,
E4020 — требуется доказательственная функция):

| Предлагаемый код | Имя                      | Срабатывание                                                                                                                           |
| ---------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| E4021            | Завершимость не доказана | Автоматический синтез провалился, и доказательственной функции нет (предлагается предоставить доказательственную функцию `Terminates`) |
| E4022            | Мера не убывает строго   | Обязательство доказательственной функции верифицировано SMT как Sat (с контрпримером на входе)                                         |

Финальная нумерация определяется фактическим состоянием реестра RFC-013 на момент реализации
(легальность диапазона гарантируется порогом build.rs); семантика W1080 (деградация доказательства
времени компиляции) к настоящему RFC отношения не имеет и не затрагивается.

### Обратная совместимость

- Программы, ранее успешно компилировавшиеся: поведение не меняется (первые три уровня конвейера
  выполняются до фолбэка).
- Программы, ранее проваливавшиеся при компиляции: после добавления меры и доказательственной
  функции могут пройти — это санкционированное пунктом о повторном обсуждении ослабление строгости,
  и затрагивает только «и так падавшие» программы.
- Существующий тестовый корпус (положительные примеры структурной рекурсии, отрицательные примеры
  неструктурной) — ожидаемые результаты не меняются, лишь коды/тексты ошибок для отрицательных
  неструктурных примеров обновляются под новые коды.

## Компромиссы

### Преимущества

- **Нулевой новый синтаксис**: в отличие от встроенной аннотации `decreases` в Dafny, данный дизайн
  не занимает синтаксического пространства; мера — это полноправная функция, которую можно
  unit-тестировать.
- **Выравнивание поведения доменов доказательства**: в домене завершимости появляется такой же
  фолбэк для Unproven, как в домене корректности; «философия жёсткой безопасности» эволюционирует от
  «не доказал — отвергаем» к «не доказал — передаём программисту» — что согласуется с мировоззрением
  RFC-027 в целом.
- **Повторное использование инфраструктуры**: обязательства — линейная арифметика, идут по уже
  подключённому в #292 конвейеру, без нового бэкенда, без нового семейства логики верификации.
- **Реализация пункта как управления**: повторное обсуждение оставляет след в форме дочернего RFC,
  протокол решений остаётся аудируемым.

### Недостатки и риски

- **Громоздкость записи**: пара сущностей (мера + доказательственная функция) многословнее одиночной
  встроенной аннотации. Принимаемо — фолбэк используется редко, а в обмен получаем
  переиспользуемость и тестируемость меры.
- **`Terminates` — единственное встроенное утверждение**: отступление от чистоты «все предикаты
  могут быть определены пользователем». Обоснование: обязательства порождаются внутренней структурой
  тела функции, в принципе невыразимы чисто библиотечным предикатом; это минимальная встроенная
  поверхность, необходимая системе.
- **До реализации стратегий 1/2/4 фолбэк может срабатывать слишком рано**: автоматическое покрытие
  Phase 1 узкое, больше функций попадает на путь доказательственных функций. Смягчение: после
  реализации четырёх стратегий область фолбэка автоматически сужается; предварительные
  доказательственные функции не пропадают — после апгрейда стратегий они продолжают служить
  носителями разряда остаточных обязательств.
- **Качество контрпримеров**: контрпримеры от Sat для нелинейных охран могут быть неинтуитивны.
  Зафиксировано как известное ограничение; представление контрпримеров итерируется по спецификации
  диагностических сообщений RFC-013.

## Не входит в цели

- Не вводится новый синтаксис/ключевые слова/позиции для аннотаций.
- Не делается обобщение автоматического синтеза меры (четыре стратегии остаются в рамках
  запланированного в RFC-027; за пределами этого — фолбэк).
- Не делается совместное решение с заимствованными утверждениями из RFC-009a (каждое верифицируется
  независимо, общий бэкенд).
- Не делается тотальная верификация на уровне типов-зависимостей (totality checking).
- Не реализуется вывод меры (угадывание меры по телу функции относится к области стратегий 1/2/4;
  настоящий RFC потребляет только явные меры).

## Этапы и приёмка

- [ ] Калибровка RFC-027 на месте (§7, протокол решений, текст §6.8, добавление указателя на 027a) —
      попадает в тот же коммит, что и данный черновик
- [ ] Сбор SCC + генерация обязательств (включая раскрытие лексикографического порядка, путевые
      охраны) + обнаружение доказательственных функций
- [ ] Подключение SMT-верификации (повторное использование конвейера из #292) + верификация двух
      вариантов: пустое тело / тело с содержимым
- [ ] Регистрация E4021/E4022 + локали на шести языках
- [ ] E2E: положительные примеры (gcd / разбиение при слиянии / взаимная рекурсия is_even-is_odd) /
      отрицательные примеры (мера не убывает → E4022; нет доказательственной функции → E4021) /
      нулевая регрессия структурной рекурсии и существующих тестов завершимости
- [ ] Демонстрация приёмки: умышленно написать доказательственную функцию с неубывающей мерой →
      провал компиляции с читаемым контрпримером; после исправления — успех
