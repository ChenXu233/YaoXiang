# RFC-027a: Резервный вариант с функцией доказательства для проверки завершимости

## Резюме

Реализация пункта о повторном обсуждении, зарезервированного в протоколе решений RFC-027: для
**неструктурной рекурсии** (ненапрямую убывающая рекурсия вроде gcd, взаимная рекурсия), которую не
покрывают четыре автоматические стратегии доказательства завершимости, предоставляется **резервный
вариант с функцией доказательства** — мера и доказательство суть обычные функции YaoXiang, ноль
нового синтаксиса, валидация проверяется контролером типов. Механизм позиционируется как **одно из
применений протокола доказательств уточняющих типов**: со стороны доказательства — ноль новых
механизмов (существующий в RFC-027 резервный канал Unproven задействуется как есть), нового — только
обязанность генерации точек вызова на стороне компилятора и один якорь утверждения. Принцип
приоритета полной автоматизации неизменен: автоматические стратегии остаются первым путём,
вмешательство пользователя происходит только после Unproven. Сфера применения урегулирована
синхронно (2026-09-14): проверка завершимости нацелена только на **вычисления на этапе компиляции**
(срабатывает при отслеживании зависимостей), код времени выполнения не требует доказательства
завершимости — принимается буквальный текст таблицы области действия из RFC-027 §6.7, текущая полная
проверка реализации сужается в соответствии с этим.

## Мотивация

### Право на внесение и масштаб правок

RFC-027 не зарезервировал слот для под-RFC (в отличие от шаблона RFC-029, зарезервировавшего 029a).
Право на размещение данного под-RFC проистекает из самого пункта о повторном обсуждении в протоколе
решений RFC-027:

> Циклы, завершимость которых не может быть доказана ни одной стратегией, приводят к прямой ошибке
> компилятора — это философия жёсткой безопасности, а не дефект. **Если в будущем в реальном
> сценарии (не в академической конструкции) обнаружится алгоритм, не покрываемый всеми четырьмя
> стратегиями, вопрос будет обсуждён повторно.** — Протокол решений RFC-027

Данный RFC и есть формальный носитель этого «повторного обсуждения». Он **не отменяет**
зафиксированное решение — сам пункт является частью решения, и его срабатывание есть именно работа
решения по замыслу; это ожидаемое осуществление пункта.

Масштаб правок RFC-027 точно ограничен четырьмя позициями:

| Позиция правки                                           | Исходная запись                                                                         | После правки                                                                                                                                                                                                                                                                               |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| §7 «Не оставлять лазеек для полуавтоматической разметки» | Проверка завершимости полностью закрыта                                                 | Сужено до «лазейки для **синтаксиса разметки** нет» — резервный вариант с функцией доказательства не является разметкой (нет новой синтаксической позиции, не привязан к определению функции), находится в одном мировоззрении с «для предикатов этапа компиляции нет новых ключевых слов» |
| Протокол решений «Unproven → прямая ошибка»              | Единственный домен доказательств без резерва в домене завершимости                      | Изменено на «Unproven → можно предоставить функцию доказательства» — выравнивание с поведением домена корректности (предикат Unproven → функция доказательства, RFC-027 §Функция доказательства)                                                                                           |
| §6.8 Текст сообщения об ошибке                           | «Используйте итерационный паттерн, анализируемый компилятором»                          | Дополнено «или предоставьте функцию меры и функцию доказательства завершимости»                                                                                                                                                                                                            |
| §7 Сфера применения                                      | «Цикл» без ограничения места, реализовано как безусловная проверка всей рекурсии/циклов | Уточнено как **вычисление на этапе компиляции** (срабатывает при отслеживании зависимостей), выровнено с таблицей области действия в §6.7; код времени выполнения не требует доказательства завершимости (проектное решение от 2026-09-14)                                                 |

**Не правятся:** приоритетное положение четырёх автоматических стратегий, принцип приоритета полной
автоматизации, прочее содержание философии жёсткой безопасности (Disproved по-прежнему остаётся
ошибкой компиляции + контрпример; поведение домена корректности не меняется в ноль).

### Текущие проблемы (замерено 2026-09-14, после v0.7.14 в dev)

1. **Расхождение области действия: в документации сказано «на этапе компиляции», реализация
   проверяет всё**. Таблица области действия в RFC-027 §6.7 прямо говорит «вызовы во время
   выполнения (не в типовых позициях) не требуют проверки завершимости»; текущий
   `TerminationChecker`, однако, безусловно обходит всю рекурсию и циклы (`checker.rs:405`) — чисто
   runtime-применение неструктурной рекурсии напрямую проваливает компиляцию, а `while` без
   анализируемой меры также отвергается. Данный RFC по проектному решению (2026-09-14) сужает:
   проверка завершимости обслуживает только вычисления на этапе компиляции, обязательство
   срабатывает от отслеживания зависимостей.

2. **Неструктурная рекурсия в компиляционных позициях без резерва**. `termination.rs` сейчас
   находится в Фазе 1: стратегия 3 (ограниченно возрастающая/убывающая), прямое убывание
   рекурсивного параметра (`factorial(n-1)`), естественная завершимость `for`-циклов. Стратегии
   1/2/4 ещё не реализованы (запланированные расширения RFC-027). Когда неструктурная рекурсия
   попадает в вычисление на этапе компиляции (например, вызов внутри тела предиката), обязательство
   не может замкнуться:

   ```yaoxiang
   gcd: (a: Int, b: Int) -> Int = {
       if b == 0 { return a }
       return gcd(b, a % b)
   }
   ```

   Рекурсивные аргументы `(b, a % b)` не являются прямым убыванием параметров — в настоящий момент
   выдаётся ошибка и предлагается переписать в итерационный паттерн. gcd нельзя переписать в
   «анализируемый итерационный паттерн», не разрушив читаемость; разделение в сортировке слиянием,
   взаимная рекурсия (проверка чётности/нечётности), обход дерева — то же самое. Это реальные
   алгоритмы, а не академические конструкции — **условие срабатывания пункта о повторном обсуждении
   выполнено**.

3. **Асимметрия резерва в домене доказательств**. Утверждения корректности RFC-027 (`Positive(b)`,
   `IsMax` и другие предикаты) при Unproven имеют резерв в виде функции доказательства; завершимость
   — единственный домен в компиляционных доказательствах, где Unproven означает тупик. В рамках того
   же мировоззрения эта асимметрия не имеет принципиального обоснования.

4. **Инфраструктура готова**. #292 уже реально подключил бэкенд Z3 (цепочка `ConstExpr` → SMTLib →
   решение Unsat/Sat). Обязательство убывания меры в точке рекурсивного вызова
   `measure(args') < measure(args)` есть утверждение первой линейной арифметики, аккуратно
   попадающее в уже открытый разрешимый фрагмент этой цепочки — повторно используется тот же
   конвейер, новый бэкенд не добавляется.

## Предложение

### Основной замысел

**Позиционирование: данный RFC не вводит нового механизма доказательств, это одно из применений
протокола доказательств уточняющих типов.** RFC-027 уже установил, что «функция доказательства — это
функция YaoXiang, тип возврата которой суть проверяемое утверждение» — утверждение есть применение
предиката, применение предиката есть уточняющий тип. Человеческая сторона доказательства
завершимости целиком идёт по этому существующему каналу (Unproven → написать функцию доказательства
→ контролёр типов валидирует → стирание witness), полностью единый протокол с доменом корректности.
Новое содержание сходится к трём вещам:

1. **Функция меры** — обычная функция этапа компиляции, параметры совпадают с сигнатурой измеряемой
   функции, возвращает `Int` или кортеж `Int` (лексикографический порядок). Не разметка, не
   привязана к определению функции, это полноценная функция, которую можно ссылаться и тестировать
   отдельно.
2. **Генерация обязательств в точках вызова** — компилятор извлекает из тела `f` обязательства
   убывания для каждой точки рекурсивного вызова. Это единственная новая логика компилятора:
   аргументы точки вызова живут в теле функции, обязательство (семантическое ограничение) должно
   генерироваться компилятором, человек не может его подменить — иначе доказательство больше не
   привязано к реальному коду (см. пункт 3 философии дизайна).
3. **Утверждение завершимости `Terminates(f, m)`** — **утончённый предикат, тело которого пишет
   компилятор**: его «содержание ограничения» есть указанный набор обязательств, его сигнатура —
   лишь якорь, связывающий `(f, m)` вместе. Необходимость встроенности только в этом; механически
   ничего нового нет. Функция и мера обе входят в тип, а не только мера: во взаимной рекурсии
   `is_even`/`is_odd` имеют одинаковые сигнатуры, и обнаружение только по мере породило бы
   неоднозначность (см. пример).

Три роли функции доказательства естественно выводятся из позиционирования: явно привязать меру `m` к
`f` (обнаружение якоря, заменяет любой синтаксис разметки); дать позицию discharge для остаточных
обязательств (тело = пространство доказательств); через квантор всеобщности удерживать имена
параметров `f` (в теле можно ссылаться на `a`, `b` для записи фактов). Синтаксис по точкам см. в
«Детальном синтаксисе», полный обход — в «Примерах».

### Примеры

#### Сквозной разбор: gcd

```yaoxiang
-- Измеряемая функция (домен корректности как обычно: уточнение параметров, гард, рекурсивный вызов)
gcd: (a: Int, b: NonNegative(b)) -> Int = {
    if b == 0 { return a }
    return gcd(b, a % b)
}

-- Мера: обычная функция (можно тестировать отдельно, можно переиспользовать)
gcd_measure: (a: Int, b: Int) -> Int = { b }

-- Функция доказательства: пустое тело — все обязательства автоматически замыкаются SMT
gcd_proof: (a: Int, b: Int) -> Terminates(gcd, gcd_measure) = { }
```

Предусловие срабатывания: следующие обязательства генерируются и потребляются только когда `gcd`
входит в вычисление на этапе компиляции (отслеживание зависимостей сработало, например, вызов из
тела предиката); когда `gcd` используется только как runtime-вызов, никакое доказательство
завершимости не требуется.

Полный путь обработки `gcd_proof` компилятором:

1. **Валидация сигнатуры**: параметры функции доказательства поочерёдно сопоставляются с формальными
   параметрами `gcd` по **базовым типам** (`Int`, `Int`). Уточнения формальных параметров (`b >= 0`)
   не дублируются в сигнатуре функции доказательства — они уже удерживаются компилятором как
   контекст обязательства; тело функции доказательства и обязательства валидируются в этом
   контексте.
2. **Обязательство обоснованности**: `gcd_measure(a, b) >= 0`, то есть `b >= 0` — прямо выводится из
   уточнения формального параметра `NonNegative(b)`. Граница меры не требует нового механизма, это
   уточняющее ограничение параметра (реализация семантического условия уточняющего типа в
   обоснованности).
3. **Генерация обязательств в точках вызова**: единственная точка рекурсивного вызова
   `gcd(b, a % b)`, гард пути `b != 0`, генерируется `gcd_measure(b, a % b) < gcd_measure(a, b)`;
   после подстановки тела меры разворачивается в `a % b < b`.
4. **Решение SMT**: проверка отрицания обязательства `b != 0 ∧ a % b >= b` на невыполнимость —
   линейная арифметика + аксиомы деления по модулю, миллисекунды → Proved.
5. **Принятие**: тело пусто, остаточных обязательств для discharge нет. Завершимость `gcd` доказана;
   мера и функция доказательства стираются как witness, не попадают в runtime-бинарник.

#### Непустое тело: ссылка на остаточные обязательства через доказанные леммы

Когда убывание в точке вызова зависит от фактов, невидимых компилятору (в примере ниже тело `step`
находится в зависимом модуле и чёрный ящик для генерации обязательств), человек записывает этот факт
в тело как **ссылку на доказанный предикат** — голое выражение, не Assert-инструкция:

```yaoxiang
step: (n: Int) -> Int = { ... }

loop_x: (n: NonNegative(n)) -> Void = {
    if n == 0 { return () }
    return loop_x(step(n))
}

x_measure: (n: Int) -> Int = { n }

-- Экспортируемое из модуля определения step доказанное постусловие (домен корректности, обычный предикат, доказан в точке определения):
step_decreases: (n: Int) -> Type = { n >= 1 ==> step(n) < n }

-- Доказательство завершимости = ссылка на эту лемму (ссылка на доказанный предикат = применение его установленного доказательства, Карри-Говард):
x_proof: (n: Int) -> Terminates(loop_x, x_measure) = {
    step_decreases(n)
}
```

Ход валидации: обязательство `x_measure(step(n)) < x_measure(n)` (гард `n != 0`, контекст `n >= 0`)
не может быть независимо замкнуто в модуле `loop_x` → обнаружено непустое тело → утверждается, что
`step_decreases(n)` есть экземпляр доказанного предиката, валидация проходит → служит леммой для
замыкания остаточного обязательства. Если в теле просто с потолка написать `step(n) < n`, валидатор
честно сообщит Unproven — факт должен происходить из прослеживаемого доказанного источника.

#### Взаимная рекурсия: сбор обязательств по SCC

```yaoxiang
is_even: (n: NonNegative(n)) -> Bool = { if n == 0 { return true }  return is_odd(n - 1) }
is_odd:  (n: NonNegative(n)) -> Bool = { if n == 0 { return false } return is_even(n - 1) }

nat: (n: Int) -> Int = { n }

is_even_proof: (n: Int) -> Terminates(is_even, nat) = { }
is_odd_proof:  (n: Int) -> Terminates(is_odd, nat) = { }
```

Обязательства собираются по SCC, обязательство через межфункциональные рёбра суть
`m_callee(callee_args) < m_caller(caller_args)` — здесь `nat(n - 1) < nat(n)`, гард `n != 0`, каждая
функция замыкается автономно. Две функции имеют одинаковые сигнатуры, и только обнаружение по мере
не сможет различить цели — это прямое обоснование наличия обоих параметров у `Terminates(f, m)`.

#### Отрицательный пример: мера не убывает строго

```yaoxiang
loop_forever: (n: Int) -> Int = { return loop_forever(n) }
loop_proof: (n: Int) -> Terminates(loop_forever, nat) = { }
```

Обязательство `nat(n) < nat(n)`, то есть `n < n`, его отрицание всегда выполнимо (Sat, модель
`n = 0`) → ошибка компиляции **E4022** (мера не убывает строго), контрпример указывает на
`loop_proof`. Если `loop_proof` удалить, автоматическая стратегия не срабатывает и функция
доказательства отсутствует → **E4021** (завершимость не доказуема, подсказка предоставить функцию
доказательства `Terminates`).

### Синтаксические изменения

**Никаких.** Данный RFC не вводит ни нового синтаксиса, ни ключевых слов, ни позиций разметки.
Сопоставление с существующей родословной:

| Поколение         | Выражение со стороны пользователя                  | Синтаксический носитель                       |
| ----------------- | -------------------------------------------------- | --------------------------------------------- |
| RFC-022 (отменён) | Разметка-комментарий `//! decreases: n`            | Соглашение о комментариях, без проверки типов |
| RFC-027 текущий   | Никакого (полная автоматика, не доказано — ошибка) | ——                                            |
| Данный RFC        | Мера + доказательство, обе — обычные функции       | Сам синтаксис определения функции             |

## Философия дизайна: разделение обнаружения и валидации

Выбор механизма в данном RFC выводится из одного принципа: **проверка завершимости = обнаружение
свидетельства + валидация свидетельства, их сложность радикально различна, и они должны быть
разделены.**

| Роль                                                                                         | Сторона                                                                                                                  | Сложность                                                                                                             |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| Обнаружение (синтез меры и доказательства)                                                   | Четыре автоматические стратегии (машина, ограниченные шаблоны) или человеческая функция доказательства (без ограничений) | В общем случае **неразрешимо** (сводится к проблеме остановки) — не существует алгоритма, который всегда находит меру |
| Валидация (для фиксированного кандидата проверка `m(args') < m(args)` в каждой точке вызова) | SMT (конвейер RFC-009a)                                                                                                  | Разрешимо (первая линейная арифметика), миллисекунды                                                                  |

«Неразрешимо найти, разрешимо проверить» — структурно изоморфно разделению witness/verifier в P/NP,
но ещё экстремальнее: сторона обнаружения не просто сложна, она математически не всегда имеет
решение; сторона валидации для фиксированного кандидата полностью механична. Отсюда «честное
сообщение Unproven» и человеческий резерв в RFC-027 суть не инженерный компромисс, а прямое
следствие этой границы.

Три следствия образуют проектные ограничения данного RFC:

1. **Доказывающему можно не доверять, и это нормально.** soundness целиком живёт в валидаторе: мера
   или утверждение написаны неверно — SMT выдаст Sat, E4022 с контрпримером отправляет назад —
   человек может не доказать, но не может доказать неверно. Disproved остаётся конструктивным (даёт
   модель контрпримера): валидатор делает на полшага больше, чем верификатор NP, и опровержение тоже
   даёт свидетельство.
2. **Инсайт замораживается в верифицируемый артефакт.** Интеллектуальный труд человека, будучи
   записан в функцию доказательства, становится машино-проверяемым сертификатом, перепроверяемым при
   каждой компиляции, навечно защищённым от регрессий (proof-carrying).
3. **Утверждение — компилятору, доказательство — человеку.** Обязательства («что считается
   доказанным») должны генерироваться компилятором из тела функции; если позволить человеку писать и
   ограничение, это эквивалентно тому, как человек пишет собственный критерий приёмки, и сертификат
   перестаёт доказывать фактически написанный код.

Четыре автоматические стратегии получают этим единое объяснение: они суть **ограниченная
последовательность шаблонов синтеза свидетельства** — автоматический синтез меры в литературе и есть
перечисление шаблонов под求解ом ограничений (синтез линейных ранговых функций как прецедент).
Расширение стратегий = расширение шаблонов; обнаружение за пределами шаблонов берёт на себя человек;
валидатор всегда один и тот же SMT. Теоретическая форма «отсутствия синтеза меры» как не-цели тоже
здесь: универсальный синтез меры лежит на неразрешимой стороне обнаружения, можно лишь зафиксировать
его границу (шаблоны), но нельзя обещать полноту.

## Детальный дизайн

### Детальный синтаксис

У функции доказательства нет специального синтаксиса — это просто «определение предиката этапа
компиляции» в ином применении. Три точки зафиксированы поочерёдно:

**Тип возврата: применение предиката, фактический аргумент — ссылка на функцию.**
`Terminates(gcd, gcd_measure)` изоморфно существующим применениям уточнений в типовых позициях
(`f(x: Positive(x))`, `-> (result: IsMax(T, arr, result))`); имя функции есть обычное связывание по
имени (RFC-010), укладывается в существующее правило фактических аргументов предикатов «литералы,
переменные (связывание по имени), применение типов». Единственное дополнение уровня правил: в
определение формы фактического аргумента E1092 добавляется «**ссылка на функцию принадлежит форме
константы этапа компиляции**» — меняется текст правила, грамматика не трогается.

**Параметры: зеркалят базовые типы `f`, квантор всеобщности.** Имена параметров и базовые типы
поочерёдно сопоставляются с формальными параметрами `f`, несовпадение даёт ошибку компиляции
(переиспользуется семейство E1093 или регистрируется новая по реестру, определяется при реализации).
Уточнения формальных параметров не дублируются — уточнения и гард-предположения инъецируются
компилятором как контекст обязательства. Квантор всеобщности — это и есть собственная
параметрическая семантика определения предиката (параметр `x` в
`Positive: (x: Int) -> Type = { x > 0 }` тоже под квантором всеобщности). Беcпараметрическая форма
отвергнута: остаточные обязательства ссылаются на имена параметров `f`, в теле имена должны быть
записываемыми.

**Тело: пространство доказательств, голые булевы выражения.** Тот же протокол, что и в теле
определения предиката `{ x > 0 }` — каждый элемент тела есть голое выражение, утверждаемое истинным.
Пустое тело допустимо и покрывает большинство сценариев (обязательства все замыкаются SMT); непустые
утверждения после валидации подаются как леммы для остаточных обязательств; легитимный источник
утверждений — применение доказанных предикатов (см. пример «Непустое тело»).

**Обнаружение и связывание.** Компилятор для `f`, не прошедших автоматический синтез, сканирует в
том же модуле и в видимых импортах функции, тип возврата которых имеет форму `Terminates(f, _)`;
обнаружение по типу возврата, без привязки к имени (`f_proof` — лишь естественное соглашение). Из
нескольких кандидатов выбирается первый, у которого все обязательства зелёные (порядок объявления),
при общем провале сообщается первый контрпример. Прямые ссылки допустимы: обнаружение происходит на
фазе проверки, не зависит от порядка объявления.

**Runtime-представление.** Функция доказательства — чисто компиляционная сущность, по модели RFC-027
CompileTime с стиранием witness — ни мера, ни функция доказательства не попадают в runtime-бинарник.

### Область срабатывания: уточнение позиций использования

**Когда** требуется обязательство завершимости, отвечает существующее в RFC-027 отслеживание
зависимостей (это триггер генерации VC, а не независимый механизм валидации):

- **Корень**: позиции этапа компиляции — типовые индексы, тела предикатов, вычисление констант.
  Компилятор должен сам выполнить этот код, полнота — несущая потребность.
- **Распространение**: по графу вызовов от корня наружу, задетая функция требует доказательства
  завершимости — автоматической стратегией или наличием в окружении сертификата `Terminates`.
- **Runtime-вызов никогда не срабатывает** — принимается буквальный текст таблицы области действия
  из RFC-027 §6.7; бесконечный цикл времени выполнения — это поведение пользовательской программы, а
  не граница безопасности компилятора.

Для потребителя это и есть точка приложения принципа «тип несёт завершимость»: в синтаксисе типа
функции нет позиции для атрибута в целом (позиции для параметров и возврата есть, для самой функции
— нет), поэтому «эта функция завершима» не записывается в тип в точке определения, а проверяется в
**каждой компиляционной точке использования** — наличия сертификата в окружении достаточно.
Проектное решение (2026-09-14): безусловная полная проверка текущей реализации сужается в
соответствии с этим.

### Генерация обязательств

Для функции `f` и меры `m` компилятор генерирует два набора обязательств первой линейной арифметики,
раскрывая каждую точку рекурсивного вызова (включая межфункциональные вызовы внутри SCC);
обязательство через межфункциональное ребро суть `m_callee(callee_args) < m_caller(caller_args)`,
при общей мере у участников деградирует до убывания по одной мере:

1. **Обоснованность**: `m(args) >= 0` — мера лежит в натуральных числах, выводится из границ типа
   параметра; при невозможности вывода переходит в остаточные обязательства.
2. **Строгое убывание**: для каждой точки вызова `m(callee_args) < m(caller_args)`, решение
   принимается **под гардом пути** (гард происходит из условия ветви, содержащей точку вызова,
   переиспользуется сбор условий пути из RFC-009a).

**Раскрытие лексикографического порядка**: когда `m` возвращает кортеж `(m₁, …, mₖ)`, обязательство
раскрывается по лексикографическому сравнению в цепочку дизъюнкций —
`(m₁' < m₁) ∨ (m₁' == m₁ ∧ m₂' < m₂) ∨ …`. Раскрытие выполняется на стороне генерации обязательств,
на стороне SMT сохраняется линейный фрагмент, без зависимости от нативной поддержки
лексикографического порядка решателем.

**Ограниченность самой функции меры**: `m` должна быть вычислима на этапе компиляции (свёртка
констант) или доказуемо структурно рекурсивна — запрещено рекурсивно перекладывать проблему
завершимости на другую недоказанную функцию (защита от бесконечной регрессии). Патологические меры
отсекаются существующими E4012 (слишком глубокая константная рекурсия) и структурными проверками.

### Конвейер решения

Конвейер запускается только при срабатывании отслеживания зависимостей (см. «Область срабатывания»);
код времени выполнения не входит в этот конвейер. `TerminationChecker` расширяется до пяти уровней;
первые три — существующие/запланированные в RFC-027 пути, данный RFC добавляет только последние два:

```
1. Структурная рекурсия напрямую доказуема (текущая логика, без регрессии)
2. Автоматический синтез меры: четыре стратегии перебираются поочерёдно (стратегии 1/2/4 реализуются по плану RFC-027, данный RFC резервирует интерфейс)
3. Синтез успешен → SMT-решение обязательств → Proved
4. Синтез не удался (Unproven) → поиск функции доказательства (тип возврата формы Terminates(f, _)):
     a. Найдена → взятие её меры m, генерация обязательств → SMT-решение
     b. Остаточные обязательства → валидация как утверждений в теле функции доказательства (тот же протокол, что и для функции доказательства в домене корректности)
5. Нет функции доказательства / обязательства функции доказательства всё ещё не срабатывают → ошибка компиляции (E4021 / E4022)
```

**Область обнаружения функции доказательства**: определена в том же модуле или экспортирована через
`import` — следует существующим правилам видимости, без глобального магического поиска. При
нескольких кандидатах `Terminates(f, _)` для одной `f` выбирается первый, у которого все
обязательства зелёные; при провале всех сообщается контрпример первого (детерминированный порядок:
порядок объявления).

**Заявление встроенности `Terminates`**: для системы предикатов это исключение — его «утверждения»
генерируются компилятором из тела `f` и не могут быть выражены синтаксисом предикатов RFC-027. Это
намеренно единственный встроенный предикат, основания зафиксированы в разделе о компромиссах.

### Обратная совместимость

- Программы, ранее проходившие компиляцию: поведение не меняется в ноль (первые три уровня конвейера
  выполняются до резерва).
- Программы, ранее не проходившие компиляцию: те, что проваливались из-за обязательств завершимости
  на этапе компиляции, пройдут после добавления меры и функции доказательства — это послабление,
  санкционированное пунктом о повторном обсуждении, и затрагивает только программы, «и так
  выдававшие ошибку».
- Влияние сужения области действия: программы **времени выполнения** (неструктурная рекурсия, циклы
  без анализируемой меры), ранее отвергавшиеся проверкой завершимости, при новой области действия
  компилируются напрямую — намеренное послабление (проектное решение от 2026-09-14), только
  расширение, не сужение; поверхность сбоев в компиляционных позициях неизменна (по-прежнему может
  быть спасена через резерв).
- Существующая тестовая корзина (положительные примеры структурной рекурсии, отрицательные примеры
  неструктурной) ожидаемые выходные данные не меняются, только коды/тексты ошибок в отрицательных
  неструктурных примерах обновляются по новым кодам.

## Компромиссы

### Достоинства

- **Ноль нового синтаксиса**: по сравнению с встроенной разметкой `decreases` в Dafny, данный дизайн
  не занимает синтаксического пространства; мера — полноценная функция, которую можно тестировать
  отдельно.
- **Поведение в домене доказательств выровнено**: домен завершимости получает резерв Unproven,
  согласованный с доменом корректности, «философия жёсткой безопасности» эволюционирует от «не
  доказал — отвергнуть» к «не доказал — передать программисту» — согласовано с мировоззрением всего
  RFC-027.
- **Переиспользование инфраструктуры**: обязательства — линейная арифметика, по уже подключённому
  конвейеру #292, без нового бэкенда, без нового семейства логики решения.
- **Реализация пункта как управление**: повторное обсуждение оставляет след в форме под-RFC,
  протокол решений остаётся аудируемым.

### Недостатки и риски

- **Бремя написания**: комплект из двух (мера + функция доказательства) многословнее единственной
  встроенной разметки. Принимается — резерв низкочастотен, и взамен получаем меру, которую можно
  переиспользовать и тестировать.
- **`Terminates` — единственный предикат с телом, которое пишет компилятор**: отступление от чистоты
  «все тела предикатов могут быть записаны пользователем». Основание: аргументы точки вызова живут в
  теле функции, библиотечный предикат в принципе не может на них сослаться; встроенная поверхность
  сходится к одному имени предиката, механически ноль нового (см. «Основной замысел» и «Философия
  дизайна»).
- **До реализации стратегий 1/2/4 резерв может срабатывать слишком рано**: в Фазе 1 автоматическая
  поверхность узка, больше функций попадёт на путь функции доказательства. Смягчение: после
  реализации четырёх стратегий поверхность резерва автоматически сужается; предваряющее наличие
  функций доказательства — не напрасный труд — после обновления стратегий они продолжат служить
  носителями discharge остаточных обязательств.
- **Качество контрпримеров**: контрпримеры Sat для нелинейных гардов могут быть неинтуитивны.
  Зафиксировано как известное ограничение, представление контрпримеров итерируется по спецификации
  диагностических сообщений RFC-013.

## Не-цели

- Не вводить синтаксис/ключевые слова/позиции разметки.
- Не делать обобщения автоматического синтеза меры (четыре стратегии сохраняются в запланированном
  RFC-027 объёме; сверх охвата — через резерв).
- Не заимствовать совместное решение утверждений с RFC-009a (каждый решает независимо, разделяя
  бэкенд).
- Не делать проверки тотальности (totality checking) на уровне зависимых типов.
- Не делать резервного варианта с функцией доказательства для циклов: цикл — анонимная конструкция,
  `Terminates(f, m)` не имеет точки привязки, и переменная меры цикла суть мутируемая локальная
  величина, а не параметр, так что правило зеркалирования параметров функции доказательства не
  работает. Циклы в области применения сохраняют автоматические стратегии — код этапа компиляции
  есть код, выполняемый самим компилятором, жёсткая линия остаётся на несущей точке. При появлении
  реальной потребности — отдельный под-RFC через синтаксис разметки циклов.
- Не реализовывать вывод меры (угадывание меры из тела функции относится к охвату стратегий 1/2/4,
  данный RFC потребляет только явную меру — см. теоретическую границу в конце «Философии дизайна»).
