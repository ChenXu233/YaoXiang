# RFC-029a: Кэш модулей и инкрементальная перекомпиляция

## Резюме

Реализация строки 029a, зарезервированной в RFC-029 «Планирование под-RFC»: поверх уже
стабилизированного оркестратора (`compile_project`) добавить компилятору **многоуровневое
кэширование и инкрементальную перекомпиляцию**. Ядро — трёхуровневая модель кэша — внутрипроцессные
результаты анализа (L1), модульный кэш в пределах сессии (L2), межпроцессный дисковый кэш (L3) — с
унифицированными ключами, принципами инвалидации и обязательными хуками метрик, чтобы свести воедино
четыре существующие разрозненные точки кэширования (обнаружено в аудите #251 P0-6).

## Мотивация

### Основания от хоста и границ

RFC-029 (принят) явно выносит данную тему за собственные границы и резервирует слот для этого
под-RFC:

> **Не включает**: кэширование, наблюдение за файлами, горячую перезагрузку, инкрементальную
> перекомпиляцию, обработку циклических зависимостей между пакетами. — RFC-029 §Основные принципы

| Под-RFC | Возможность                                  | Предусловие                |
| ------- | -------------------------------------------- | -------------------------- |
| 029a    | Кэш модулей и инкрементальная перекомпиляция | Оркестратор стабилизирован |

Предусловие «оркестратор стабилизирован» выполнено: оркестратор внедрён вместе с RFC-029 и проверен
поставками #232/#243/#244/#245.

### Текущие проблемы (аудит #251 P0-6 + эмпирика от 2026-09-07)

**Разрозненные точки кэширования не связаны между собой**:

| Существующий кэш                         | Слой             | Фактический потребитель | Проблема                                                       |
| ---------------------------------------- | ---------------- | ----------------------- | -------------------------------------------------------------- |
| `VALIDATE_CACHE` (validate.rs)           | Внутрипроцессный | Только formatter        | CLI `check`/`run` и оркестратор его не используют              |
| Кэш запросов Z3Backend                   | Сессия проверки  | Конвейер доказательств  | Нет правил инвалидации и бюджета (одно предложение в RFC-009a) |
| `DocumentCache` (util/cache.rs, RFC-017) | LSP-сессия       | LSP                     | Полностью изолирован от CLI-стороны компиляции                 |
| `~/.yaoxiang/cache` (RFC-014)            | Диск             | Загрузка пакетов        | Не относится к компиляции                                      |
| Кодовый кэш (RFC-028)                    | Время выполнения | JIT                     | Не является слоем времени компиляции                           |

**Повтор полного конвейера на нескольких входах (эмпирика)**:

- В цикле `check_files_with_diagnostics` **на каждый файл создаётся новый `Compiler`**
  (`src/util/diagnostic/mod.rs`): при проверке 19 файлов уровня библиотеки в том же процессе
  встроенная цепочка std повторно typecheck-ится 19 раз;
- Тестовые файлы класса runtime-error проходят через подпроцессы `check` + `run`, полный конвейер
  выполняется дважды;
- Быстрая проверка заимствований `fast_path_check` при каждой операции записи независимо выполняет
  BFS по всему графу, без кэширования результата (исходное наблюдение аудита #251 P0-6; в RFC-009a
  L611 — лишь одно предложение «результат однократного BFS можно кэшировать для повторных запросов
  того же токена», без проектного замысла).

### Анатомия стоимости (метод базовой линии `--version`, замеры 2026-09-07)

| Зонд                                   | Время  | Смысл разницы                       |
| -------------------------------------- | ------ | ----------------------------------- |
| `yaoxiang --version`                   | ~50 ms | Запуск процесса + инициализация CLI |
| `check` голого файла (без импорта std) | ~60 ms | Компиляция фронтенда ≈ 10 ms        |
| `check` файла цепочки `std.test`       | ~80 ms | Встраивание цепочки std ≈ +20 ms    |

Тестовый цикл из 170 файлов — измеренное время 9,8 с ≈ 58 мс/файл: **~85% приходится на жизненный
цикл процесса, сама компиляция — лишь ~10 мс, цепочка std добавляет +20 мс на файл**. Отсюда
определяется основное поле выигрыша данного RFC:

1. **Совместное использование нескольких входов в одном процессе** (L1/L2) — ликвидация повторного
   конвейера фронтенда и компиляции цепочки std;
2. **Исключение цепочки std между процессами** (L3) — единственный легитимный канал выигрыша от
   кэширования в модели подпроцессов;
3. **Стоимость запуска процесса ~50 мс/файл лежит вне зоны действия кэша** — изоляция подпроцессов
   является проектным выбором RFC-036 §6, данный RFC его не отменяет (см. не-цели).

## Предложение

### Основной замысел: трёхуровневая модель кэша

#### L1 — внутрипроцессный кэш результатов анализа (время жизни = одна сессия проверки)

- `validate_source` сводится в **единственную точку входа валидации фронтенда**:
  `check_files_with_diagnostics`, пофайловый typecheck оркестратора и LSP-диагностика — всё
  переводится на неё (сейчас её потребляет только formatter);
- Ключ = хеш содержимого FNV-1a (существующая реализация в validate.rs), значение = `ValidateResult`
  (диагностика + AST);
- Кэш множества unsafe BFS заимствований: реализация проектной фразы RFC-009a, время жизни = сессия
  проверки одной функции, согласовано с реализациями проверки заимствований #290/#292;
- Кэш запросов Z3 (RefCell + хеш запроса) включается в те же принципы, с добавлением инвалидации и
  бюджета.

#### L2 — модульный кэш сессии (время жизни = одна оркестрация)

- Registry оркестратора и результаты валидации модулей кэшируются по ключу **(путь модуля, хеш
  содержимого)**: второй `compile_project` в том же процессе попадает прямо в кэш;
- Встроенные источники std (`yx_sources` include_str!) имеют постоянное содержимое → компилируются
  один раз за процесс, разделяются между N импортирующими файлами;
- Инвалидация: изменение хеша источника модуля вызывает инвалидацию; изменения зависимостей
  распространяются по графу `use` (третья волна реализации).

#### L3 — межпроцессный дисковый кэш (время жизни = между запусками)

- Расположение `~/.yaoxiang/cache/compile/`, в общем корне с кэшем загрузок RFC-014, но в отдельном
  сегменте;
- Ключ = **(хеш содержимого, версия компилятора, отпечаток семантической конфигурации)**; продукт —
  байткод модуля (с повторным использованием формата магического числа `BytecodeFile`);
- Несовпадение версии или отпечатка = полный miss с перекомпиляцией — **распространение межмодульной
  инвалидации не выполняется** (консервативная инвалидация по целому ключу).

### Унифицированные принципы ключей и инвалидации (пробел 4 в #293)

- Сила ключа: хеш содержимого > структурный хеш > номер версии. L1/L2 используют хеш содержимого
  (исходный код есть идентичность), L3 поверх добавляет охрану версией компилятора и отпечатком
  конфигурации;
- Распространение инвалидации существует только внутри графа зависимостей L2; L3 выполняет
  инвалидацию по целому ключу, без отслеживания межмодульных зависимостей;
- **Отказ на этапе построения**: при неполном ключе (отсутствие хеша/версии) запись в кэш
  отклоняется, лучше miss, чем устаревший продукт — тот же принцип, что и отказ от компиляции при
  отсутствии перевода i18n диагностики.

### Хуки метрик (согласовано с #289)

```rust
pub struct CacheStats {
    pub hits: u64,
    pub misses: u64,
    pub cached_bytes: u64,
}
```

- В summary `check --json` и `test --json` добавляется поле `cache` (процент попаданий по уровням);
- **Обязательный порог: ненаблюдаемый кэш не подлежит слиянию** — защита от «тихого гниения» вида
  «кэшируем, но никто не попадает».

### Границы инкрементальной перекомпиляции (пробел 2 в #293)

- **Старт на уровне файлов**: грязные файлы определяются по графу `use`, перекомпилируются только
  грязные файлы и их нисходящие зависимости; унифицированная эволюция с файловым кэшем LSP из
  RFC-017 (DocumentCache мигрирует в потребителя L1+L2, а не существует как отдельная система);
- **Инкремент на уровне функций явно не делается** (это упрощение уже заявлено в RFC-017: несколько
  миллисекунд полного файлового разбора не стоят инкрементализации).

## Детальное проектирование

### Стыковка с процессом оркестрации RFC-029

```text
Процесс оркестрации RFC-029 (уже реализован):

  Обнаружение исходных файлов → Построение Registry → Пофайловый typecheck → Общая компиляция

Точки вставки данного RFC:

  Обнаружение исходных файлов → [L2] запрос Registry/кэша результатов валидации по (путь+хеш)
                                    ├─ Попадание → повторное использование
                                    └─ miss → построение (с обратным заполнением)
  Пофайловый typecheck → [L1] единственная точка входа validate_source (запрос/заполнение по хешу содержимого)
  Общая компиляция → Продукт → [L3] сериализация на диск (с охраной версией), загрузка напрямую при следующем процессе
```

### Ожидаемый выигрыш в тестовом цикле (квантификация)

| Сценарий                                                           | Сейчас                 | После 029a                       | Уровень |
| ------------------------------------------------------------------ | ---------------------- | -------------------------------- | ------- |
| Runner в одном процессе (режим yx_runner) для 19 файлов библиотеки | цепочка std 19×20 ms   | 1×20 ms + 19 попаданий           | L1+L2   |
| Runner в подпроцессе (`yaoxiang test`)                             | цепочка std 20 ms/файл | ≈ 0 после попадания              | L3      |
| Большая функция проверки заимствований                             | O(V²) BFS              | Повторное использование в сессии | L1      |
| Запуск процесса (~50 ms/файл)                                      | Без изменений          | Без изменений (не-цель)          | —       |

## Отношения с существующими системами

- **RFC-029**: хост. 029a — реализация строки таблицы «Планирование под-RFC»;
- **RFC-009a**: механизация проектной фразы L611 (кэш BFS, уровень L1);
- **RFC-017**: DocumentCache включается как потребитель L1+L2, единственный источник стратегии
  кэширования;
- **RFC-014**: разделение дискового каталога — сегмент `cache/` для загрузок против сегмента
  `cache/compile/` данного RFC;
- **RFC-028**: кэш кода JIT относится к уровню времени выполнения, вне юрисдикции данного RFC;
- **RFC-031**: диспетчеризация проходов оптимизации относится к менеджеру проходов; данный RFC
  кэширует входы/выходы цепочки проходов, эти вещи ортогональны;
- **RFC-036**: модель изоляции тестовых подпроцессов сохраняется, L3 — её единственный канал
  межпроцессного выигрыша;
- **#251/#290/#292**: источник аудита и реализации проверки заимствований (потребитель кэша BFS);
- **#289**: согласование наблюдаемости через хуки метрик;
- **#247**: обнаружение по `use` (обнаружение по требованию) накладывается поверх графа зависимостей
  L2, является чистой оптимизацией производительности.

## Стратегия реализации

1. **Первая волна (выгода сразу при внедрении)**: унификация точки входа `validate_source` (три
   потребителя: check/оркестратор/LSP), сессионный кэш BFS заимствований, минимальная версия хуков
   метрик;
2. **Вторая волна**: модульный кэш сессии L2 (однократная компиляция встроенной std + повторное
   использование Registry);
3. **Третья волна**: дисковый кэш L3 (приоритет std — встроенные источники стабильны, процент
   попаданий постоянен) + инкрементальная перекомпиляция на уровне файлов по графу `use` +
   унификация LSP-кэша.

## Не-цели

- Инкрементальный разбор на уровне функций (существующее решение RFC-017);
- Кэш JIT / времени выполнения (RFC-028);
- Отмена изоляции подпроцессов тестового цикла (проектный выбор RFC-036 §6);
- Распространение межпакетной инвалидации (за границами RFC-029);
- Оптимизация стоимости запуска процесса (не вопрос кэширования).
