# RFC-021: Библиотечно-управляемое расширение FFI и поддержка межъязыковых вызовов

> **⚠️ Заброшен**: Данный документ заброшен, содержимое объединено в [RFC-026: Основной механизм FFI](../accepted/026-ffi-core-mechanism.md).

> **Справочная информация**:
>
> - [RFC-001: 并作模型与错误处理系统](./001-concurrent-model-error-handling.md)
> - [RFC-008: Runtime 并发模型与调度器脱耦设计](../accepted/008-runtime-concurrency-model.md)
> - [RFC-026: FFI 核心机制](../accepted/026-ffi-core-mechanism.md)

## Аннотация

В данном документе предлагается **библиотечно-управляемая** схема расширения FFI (Foreign Function Interface — интерфейс внешних функций). Единственной точкой входа в FFI является объявление `native("symbol")` + таблица регистрации функций `FfiRegistry` времени выполнения; в ядре не вводится второй набор механизмов. На этой основе стандартная библиотека предоставляет возможности динамической загрузки библиотек, межъязыковых вызовов и привязок. Привязки вызовов для конкретных языков (таких как C, Python, JavaScript) автоматически генерируются официальным инструментарием или создаются проектами по мере необходимости.

## Мотивация

### Недостатки существующей реализации

Текущая реализация FFI уже обладает следующими возможностями:

- Синтаксис объявления `native("symbol")` для внешних функций
- Таблица регистрации функций `FfiRegistry`

Однако функциональность относительно ограничена:

- Отсутствует поддержка динамической загрузки библиотек
- Нет инфраструктуры для межъязыковых вызовов
- Отсутствуют инструменты автоматической генерации привязок

### Философия проектирования

YaoXiang следует принципу **«Ядро простое, сложность опускается в библиотеки»**:

> **Хороший вкус (Good Taste)**: Назначение языка — предоставлять атомарные возможности, а не универсальный функционал. Сложность должна решаться через библиотеки, а не накапливаться в компиляторе.

Поэтому данная схема:

- ✅ **Нулевые синтаксические изменения** — полная обратная совместимость, единственной точкой входа в FFI является `native("symbol")`
- ✅ **Библиотека как язык** — функциональность расширяется через стандартную библиотеку
- ✅ **Автоматизация инструментарием** — привязки генерируются `yx-bindgen`, а не поддерживаются вручную
- ✅ **Постепенное улучшение** — разработчики подключают функциональность по необходимости

## Предложение

### 1. Расширение основной библиотеки FFI

Расширение модуля `std.ffi`. Примечание: все вызовы внешних функций по-прежнему осуществляются через объявление `native("symbol")`, `std.ffi` предоставляет только вспомогательные возможности.

#### 1.1 Динамическая загрузка библиотек

```yaoxiang
import ffi

# Загрузка динамической библиотеки (.so/.dll/.dylib)
lib = ffi.load_library("./libmyext.so")

# Получение символов функций из библиотеки, возврат имени symbol для native
ffi.register_library_symbols(lib, [
    "my_function",
    "another_func",
])
```

`load_library` возвращает дескриптор `DynamicLibrary`, `register_library_symbols` регистрирует имена символов в известной таблице `FfiRegistry`. После этого пользователь по-прежнему использует объявление `native`:

```yaoxiang
my_func: (a: Int, b: Int) -> Int = native("my_function")
```

Нет второго набора синтаксиса вызова, нет обёрток `try_call`.

#### 1.2 Управление библиотеками

```yaoxiang
# Список загруженных библиотек
loaded = ffi.loaded_libraries()

# Выгрузка библиотеки
ffi.unload_library(lib)

# Проверка версии библиотеки
ffi.check_version(lib, "1.0.0")
```

#### 1.3 Разрешение символов

```yaoxiang
# Поиск символа по имени (возвращает структуру Symbol)
sin_sym = ffi.dlsym("libm.so", "sin")
```

Соглашения о межъязыковых вызовах и преобразование типов обрабатываются не через универсальные обёртки времени выполнения, а генерируются `yx-bindgen` на этапе компиляции.

### 2. Реализация динамической загрузки библиотек

#### 2.1 Основные структуры данных

```rust
pub struct DynamicLibrary {
    handle: *mut std::ffi::c_void,
    path: String,
}

impl DynamicLibrary {
    pub fn load(path: &str) -> Result<Self, FfiError>;
    pub fn get_symbol(&self, name: &str) -> Result<*mut std::ffi::c_void, FfiError>;
    pub fn unload(self) -> Result<(), FfiError>;
}
```

#### 2.2 Типы ошибок

```rust
pub enum FfiError {
    LibraryNotFound { name: String, os_error: Option<OsError> },
    SymbolNotFound { name: String, os_error: Option<OsError> },
    CallFailed { message: String, os_error: Option<OsError> },
    Timeout,
}

pub struct OsError {
    pub code: i32,
    pub message: String,
}
```

`OsError` содержит нативный код ошибки платформы (Linux: `dlerror()`, Windows: `GetLastError()`), что обеспечивает отладку.

### 3. Привязки для множества языков: решение на основе инструментария

Отказ от «фантазии» о том, что сопровождающие различных языков в сообществе будут писать библиотеки привязок. Вместо этого — автоматическая генерация официальным инструментарием.

#### 3.1 Архитектурный дизайн

```
┌───────────────────────────────────────────────┐
│  YaoXiang код                                 │
│                                               │
│  // Пользователь пишет только объявления native │
│  my_func: (a: Int) -> Int = native("my_func") │
└───────────────────────────────────────────────┘
         ↑                          ↑
         |  Время компиляции         |  Время выполнения
┌──────────────────┐   ┌────────────────────────┐
│  yx-bindgen       │   │  std.ffi + FfiRegistry  │
│  (C заголовочные │   │  - dlopen/dlsym         │
│   файлы → .yx)   │   │  - LoadLibrary/GetProc  │
└──────────────────┘   └────────────────────────┘
```

#### 3.2 Генератор привязок (`yx-bindgen`)

`yx-bindgen` — это автономный CLI-инструмент, который генерирует код привязок YaoXiang FFI из заголовочных файлов C:

```bash
yx-bindgen --header /usr/include/sqlite3.h --output sqlite3.yx
```

Пример сгенерированного результата:

```yaoxiang
# Автогенерировано, не редактировать вручную
# Source: /usr/include/sqlite3.h

sqlite3_open: (filename: *const u8, ppDb: *mut *mut opaque) -> Int
    = native("sqlite3_open")

sqlite3_close: (db: *mut opaque) -> Int
    = native("sqlite3_close")

sqlite3_exec: (
    db: *mut opaque,
    sql: *const u8,
    callback: *mut opaque,
    arg: *mut opaque,
    errmsg: *mut *mut u8,
) -> Int
    = native("sqlite3_exec")
```

`yx-bindgen` поддерживается официально, что гарантирует:

- Полноту маппинга типов (`int` → `Int`, `char*` → `*const u8`, `void*` → `*mut opaque`)
- Выравнивание раскладки структур (автоматический эквивалент `#[repr(C)]`)
- Преобразование сигнатур callback-функций

#### 3.3 Официально поддерживаемые пакеты привязок

Команда YaoXiang Core не обязуется поддерживать универсальные библиотеки привязок для всех языков, но предоставляет официальный пакет привязок `libc` (подмножество POSIX + Windows API) в качестве примера лучших практик FFI и базовых возможностей.

Привязки для других языков и библиотек:

- Генерируются самостоятельно с помощью `yx-bindgen`
- Могут публиковаться как пакеты YaoXiang (например, `libsqlite3`, `libcurl`, `libsdl2`)
- Команда core не несёт ответственности за поддержку, но предоставляет механизм публикации и управления версиями пакетов

### 4. Уровень преобразования типов

#### 4.1 Компиляционный маппинг типов

Преобразование типов выполняется не через обёртки времени выполнения, а статически определяется при генерации `yx-bindgen`:

| Тип C         | Тип YaoXiang       | Способ преобразования      |
| -------------- | ------------------- | -------------------------- |
| `int`          | `Int`               | Прямая передача значения   |
| `char*`        | `*const u8`         | Передача указателя         |
| `void*`        | `*mut opaque`       | Непрозрачный указатель     |
| `struct T`     | `extern struct T`    | Соответствие раскладки памяти |
| `int*`         | `*mut Int`          | Передача указателя (изменяемый) |
| `const int*`   | `*const Int`        | Передача указателя (только чтение) |

#### 4.2 Ручное преобразование (вспомогательные средства стандартной библиотеки)

```yaoxiang
# Явное преобразование
raw_ptr = ffi.to_pointer(my_bytes)
c_string = ffi.to_c_string(my_string)
```

### 5. Модель владения памятью

#### 5.1 Основные принципы

При каждом выделении памяти через границу FFI необходимо чётко ответить на два вопроса:

1. **Кто выделяет?** (C-сторона `malloc` / сторона YaoXiang runtime)
2. **Кто освобождает?** (C-сторона `free` / сторона YaoXiang runtime)

При генерации `yx-bindgen` добавляет аннотации для распространённых паттернов:

```yaoxiang
# Выделено C, вызывающая сторона должна освободить
sqlite3_exec: (...) -> Int
    = native("sqlite3_exec")
    # memory: C-allocated, caller must free errmsg via sqlite3_free

# Вызывающая сторона выделяет память под указатель
read: (fd: Int, buf: *mut u8, count: Int) -> Int
    = native("read")
    # memory: caller-allocated buf
```

Время выполнения не выполняет автоматическое управление памятью для ссылок на указатели через границу FFI — владение чётко возлагается на вызывающую сторону.

#### 5.2 Обработка строк

`char*`, возвращаемый C-функцией, при преобразовании в YaoXiang `String` немедленно копируется. Владение исходным указателем определяется C-функцией (декларируется через аннотации), автоматическое освобождение не выполняется.

### 6. Соображения безопасности

#### 6.1 Безопасность в многопоточном контексте

Вызовы FFI-функций **по умолчанию не участвуют в планировании DAG**, рассматриваются как блокирующие операции. C-функции, подтверждённые как reentrant, могут быть помечены как `@concurrent`:

```yaoxiang
# Чистая функция, без глобального состояния, может выполняться параллельно
sin_safe: (x: Float) -> Float = native("sin")
    # reentrant: true

# Имеет глобальное состояние, не может выполняться параллельно
strtok: (s: *const u8, delim: *const u8) -> *const u8 = native("strtok")
    # reentrant: false
```

`yx-bindgen` по возможности аннотирует информацию о реентабельности для стандартных C-библиотек (варианты `_r` для `strtok` и т.д.).

**Требования к асинхронным вызывающим сторонам:**
Перед вызовом FFI-функции вызывающая сторона должна убедиться, что целевая функция является реентабельной. Время выполнения не выполняет автоматическую проверку — это неразрешимая статическая задача.

#### 6.2 Изоляция ошибок

- Ошибки FFI-вызовов распространяются через тип `Result` (если функция объявила тип возврата Result)
- Механизм таймаута предотвращает взаимоблокировку внешних функций

```yaoxiang
# Вызов с таймаутом (реализуется на уровне FfiRegistry)
result = ffi.call_with_timeout("blocking_func", 5000)  # Таймаут 5 секунд
```

#### 6.3 Безопасность указателей

- Параметры-указатели требуют маркировки `unsafe` со стороны YaoXiang
- Время жизни указателей через границу FFI гарантируется вызывающей стороной

### 7. Изменения в компиляторе

**Нулевые синтаксические изменения** — требуется только объявление `native("symbol")`, которое уже реализовано в текущем компиляторе.

В интерпретаторе/времени выполнения добавляются:

- Инструкции динамической загрузки библиотек (привязки FFI для `DynamicLibrary`)
- Механизм таймаута

### 8. Функции, не прошедшие утверждение

Следующие функции после проверки явно исключены и больше не рассматриваются в RFC:

- **`ffi.try_call`**: Избыточно, уже есть `native` + тип возврата `Result`
- **`ffi.verify_signature`**: Время выполнения выполняет работу компилятора — неправильный уровень абстракции
- **`ffi.async_call`**: Требует уточнения модели контракта реентабельности перед рассмотрением
- **Таблица привязок, поддерживаемая сообществом**: Невыполнимо, переход к схеме инструментария `yx-bindgen`

## Компромиссы

### Преимущества

- ✅ **Нулевые синтаксические изменения** — точка входа в FFI только `native("symbol")`, полная обратная совместимость
- ✅ **Библиотека как язык** — функциональность постепенно вводится через стандартную библиотеку
- ✅ **Инструментарий как драйвер** — `yx-bindgen` автоматически обрабатывает генерацию привязок
- ✅ **Безопасность памяти** — модель владения чёткая, нет use-after-free из-за автоматической сборки мусора
- ✅ **Отладка** — ошибки содержат нативные коды ошибок ОС

### Недостатки

- ⚠️ Безопасность типов ограничена выразительностью заголовочных файлов C (`void*` невозможно статически различить)
- ⚠️ `yx-bindgen` требует постоянной поддержки для отслеживания эволюции стандарта C
- ⚠️ Привязки для языков, отличных от C (Python/JS/Java), требуют самостоятельной обработки проектами, без унифицированного решения

## Приложение B: Примеры кода

### Полный пример: использование C-библиотеки

```yaoxiang
# Загрузка C математической библиотеки
libm = ffi.load_library("libm.so")

# Регистрация C-символов в таблице времени выполнения (yx-bindgen делает это при компиляции)
ffi.register_library_symbols(libm, ["sin", "cos", "sqrt"])

# Использование через объявления native
sin_f: (x: Float) -> Float = native("sin")
cos_f: (x: Float) -> Float = native("cos")

# Прямой вызов
result = sin_f(3.14159 / 2)

# Для C-функций, которые могут завершиться неудачей, используется Result
file_open: (path: *const u8, mode: *const u8) -> Result(*mut opaque, Int)
    = native("fopen")
```

### Использование yx-bindgen

```bash
# Автогенерация всех объявлений, без ручного написания
yx-bindgen --header /usr/include/math.h --output math_bindings.yx

# Подключение в YaoXiang
import "math_bindings.yx"
# sin_f / cos_f и др. уже автоматически объявлены как native("sin") / native("cos")
```
