# RFC 022: Поддержка статической верификации на основе логики Хора (аннотации спецификаций и типы спецификаций) [Устарело]

> **Справочные материалы**:
>
> - [RFC-010: Унифицированный синтаксис типов](../accepted/010-unified-type-syntax.md)
> - [RFC-011: Проект системы обобщённых типов](../accepted/011-generic-type-system.md)
> - [RFC-009: Модель владения](../accepted/009-ownership-model.md)

## Краткое содержание

В данном документе предлагается внедрение **механизма статической верификации на основе логики
Хора** для языка YaoXiang, позволяющего разработчикам записывать предусловия, постусловия и
инварианты циклов в комментариях в формате `//!` или `/*! ... !*/`. При сборке Debug верификация
выполняется принудительно, и только после её успешного завершения возможна сборка Release; при
сборке Release аннотации спецификаций игнорируются (нулевые накладные расходы), а кэш верификации
очищается. Спецификации рассматриваются как часть системы типов, образуя «типы спецификаций» (такие
как `Requires(P)`, `Ensures(P)`), и могут быть расширены пользователем. Данная архитектура
направлена на сохранение простоты языка при обеспечении высокой надёжности критически важного кода и
идеально интегрируется с унифицированной моделью типов YaoXiang.

## Мотивация

### Зачем нужен данный функционал/изменение?

YaoXiang уже обеспечивает безопасность памяти и потоков через модель владения (RFC-009) и модель
параллелизма (RFC-001), однако логическая корректность по-прежнему зависит от тестирования. В
системном программировании и критически важных областях (аэрокосмическая отрасль, финансы, ядра
операционных систем) логические ошибки могут привести к катастрофическим последствиям. Существующие
решения (например, проверка заимствований в Rust) не способны обнаруживать такого рода ошибки.
Логика Хора предоставляет математический аппарат доказательств, однако традиционные инструменты
формальной верификации зачастую требуют отдельного языка спецификаций и характеризуются крутой
кривой обучения.

### Текущие проблемы

- Логическая корректность может быть проверена только тестами, без гарантий на этапе компиляции
- Отсутствуют средства формальной верификации для критически важного системного кода
- Существующие инструменты формальной верификации имеют крутую кривую обучения и отделены от主流ных
  языков программирования

## Предложение

### Основная архитектура

Наша цель — разработать **лёгкое, интегрированное с языком** решение для статической верификации:

- **Верификация при сборке Debug**: Разработчики записывают спецификации в модулях, требующих
  высокой надёжности; при сборке Debug верификация выполняется принудительно, и только после успеха
  возможна сборка Release
- **Элегантный синтаксис**: Использование комментариев `//!`, без введения новых ключевых слов, с
  возможностью подсветки синтаксиса в редакторах
- **Интеграция с системой типов**: Спецификации становятся частью типов, участвуют в проверке типов
  и поддерживают пользовательские типы спецификаций
- **Доказуемость и тестируемость**: Возможность как статического доказательства, так и понижения
  до运行时ных утверждений, что обеспечивает постепенное внедрение

### 1. Синтаксис спецификационных комментариев

В начале тела функции или цикла используются `//!` (однострочный) или `/*! ... !*/` (многострочный)
комментарии для записи спецификаций.

#### 1.1 Унифицированный синтаксис спецификаций

Спецификации используют унифицированную в YaoXiang модель синтаксиса `name: Type = expression`,
полностью интегрированную с системой типов:

```yaoxiang
max: (T: Ord) -> ((arr: Array(T, n)) -> T) = {
    //! requires: NonEmpty(n) = n > 0
    //! ensures: GreaterOrEqual(result, arr[0..n])
    //! ensures: ExistsMax(result, arr[0..n])
    // реализация...
}
```

- Спецификация по сути является **объявлением типа**, справа — логическое выражение
- Слева — экземпляр типа спецификации (с возможными параметрами типа)
- Доступна специальная переменная `result` для обозначения возвращаемого значения

#### 1.2 Спецификации циклов

```yaoxiang
while i < n {
    /*! invariant: Bounds[i, n] = 0 <= i <= n
                  && SumInvariant[s, arr[0..i]] !*/
    s = s + arr[i]
    i = i + 1
}
```

#### 1.3 Выражения спецификаций

Логические выражения справа от спецификаций используют синтаксис выражений YaoXiang и поддерживают:

- Арифметические, сравнительные и логические операции
- Кванторы: `forall i in 0..n: P(i)`, `exists i in 0..n: P(i)` — встроенные в язык логические
  конструкции
- Вызовы функций (только чистые функции)

### 2. Система типов спецификаций

Типы спецификаций по своей природе являются обычными типами YaoXiang и полностью соответствуют
унифицированной модели синтаксиса.

#### 2.1 Встроенные типы спецификаций

Компилятор предоставляет следующие часто используемые типы спецификаций (доступные для прямого
использования в спецификациях):

```yaoxiang
// Встроенные определения типов спецификаций
NonEmpty: (T: Type) -> Type = { len: T; len > 0 }
Positive: Type = { x: Int; x > 0 }
GreaterOrEqual: (T: Type) -> Type = { result: T, arr: Array(T); result >= arr[0] && forall i in 1..arr.len: result >= arr[i] }
Bounds: (T: Type) -> Type = { i: T, n: T; 0 <= i && i <= n }
SumInvariant: (T: Type) -> Type = { s: T, arr: Array(T); s == sum(arr[0..i]) }

// Конструкции кванторов (встроенные в язык, не функции)
forall: (start: Int, end: Int, pred: (Int) -> Bool) -> Bool
exists: (start: Int, end: Int, pred: (Int) -> Bool) -> Bool
```

#### 2.2 Пользовательские типы спецификаций

Полностью аналогично обычным определениям типов, пользователи могут определять собственные типы
спецификаций:

```yaoxiang
// Определение спецификации положительного целого числа
Positive: Type = { x: Int; x > 0 }

// Определение спецификации отсортированного массива
Sorted: (T: Ord) -> Type = {
    arr: Array(T);
    forall i in 0..arr.len-1: arr[i] <= arr[i+1]
}

// Определение спецификации максимального значения
ExistsMax: (T: Ord) -> Type = {
    result: T, arr: Array(T);
    exists i in 0..arr.len: result == arr[i]
    && forall j in 0..arr.len: result >= arr[j]
}
```

Использование пользовательских спецификаций:

```yaoxiang
sqrt: (x: Positive) -> Float = {
    //! ensures: SquareRootResult(result, x) = result * result <= x && (result+1)*(result+1) > x
    // реализация...
}

binary_search: (T: Ord) -> ((arr: Sorted(Array(T)), key: T) -> Option(Index)) = {
    //! ensures: SearchResult(result, arr, key)
    // реализация...
}
```

Типы спецификаций, как и другие типы, поддерживают параметры обобщённых типов, ограничения типов и
участвуют в выведении типов.

### 3. Режимы компиляции

| Режим                           | Поведение                                                                                                           | Опция                                         |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **Сборка Debug**                | Разбор спецификаций, генерация условий верификации, вызов SMT-решателя; верификация обязательна для сборки Release  | `yaoxiangc --debug source.yx`                 |
| **Сборка Release**              | Игнорирование всех комментариев `//!`, отсутствие генерации кода; очистка кэша верификации; агрессивная оптимизация | `yaoxiangc --release source.yx`               |
| **Проверки времени выполнения** | Преобразование спецификаций в утверждения времени выполнения, нарушение вызывает panic                              | `yaoxiangc --enable-runtime-checks source.yx` |

В режиме верификации, в случае неудачи доказательства, компилятор сообщит об ошибке и предоставит
возможные контрпримеры (например, входные значения).

### 4. Механизм верификации

Компилятор преобразует спецификации в условия верификации (Verification Conditions) и отправляет их
в интегрированный SMT-решатель (например, Z3). Процесс верификации приблизительно следующий:

1. Сбор `requires` и `ensures` для функций, `invariant` для циклов
2. Генерация обязательств по доказательству инварианта цикла для каждого цикла: выполнение перед
   входом в цикл, сохранение после каждой итерации, следствие постусловия при выходе из цикла
3. Преобразование тела функции в логические формулы, объединение со спецификациями, формирование
   условий верификации
4. Вызов SMT-решателя для проверки выполнимости

Если решатель возвращает `unsat` (невыполнимо), спецификация верна; в противном случае сообщается
контрпример.

### 5. Интеграция с тестированием

Режим проверок времени выполнения может преобразовывать спецификации в утверждения для тестирования.
Совместно с инструментами анализа покрытия спецификаций можно оценить степень покрытия тестами. В
перспективе возможны инструменты интеллектуального извлечения спецификаций, автоматически выводящие
кандидаты в спецификации из тестов.

### 6. Поддержка редакторов

`//!` и `/*! ... !*/` могут распознаваться редакторами как специальные комментарии, с отличной
подсветкой (например, фиолетовый цвет), отличающей их от обычных комментариев. Language Server может
предоставлять всплывающие подсказки, автодополнение и отчёты об ошибках верификации для
спецификаций.

## Детальный проект

### Изменения синтаксиса

| До                                           | После                                                  |
| -------------------------------------------- | ------------------------------------------------------ |
| Отсутствует синтаксис аннотаций спецификаций | Разрешены аннотации спецификаций `//!` и `/*! ... !*/` |

### 7.1 Расширение синтаксиса

На основе существующего синтаксиса (RFC-010) разрешено появление нуля или более комментариев `//!`
или `/*! ... !*/` в начале тела функции или цикла. Синтаксис спецификаций соответствует
унифицированному синтаксису типов:

```
spec_comment     ::= ('//!' spec_line) | ('/*!' spec_block '!*/')
spec_line        ::= spec_name ':' type_expr '=' expr
spec_name        ::= 'requires' | 'ensures' | 'invariant'
spec_block       ::= (spec_name ':' type_expr '=' expr ';')*
```

- Спецификация по сути является объявлением типа:
  `имя_спецификации: тип_спецификации = логическое_выражение`
- `type_expr` — выражение типа спецификации, может содержать параметры типа
- `expr` использует синтаксис выражений YaoXiang, поддерживает кванторы

### 7.2 Проверка типов

В режиме верификации компилятор преобразует аннотации спецификаций в соответствующие экземпляры
типов спецификаций и записывает их в метаданные функции или цикла.

### 7.3 Генерация условий верификации

Используется исчисление наиweakest precondition или strongest postcondition в сочетании с
инвариантами циклов для генерации формул первого порядка. Генерируемые VC используют формат SMT-LIB,
вызывается внешний решатель.

### 7.4 Сообщения об ошибках

В случае неудачи доказательства решатель может предоставить модель (контрпример). Компилятор должен
преобразовать эти контрпримеры в читаемую форму, например в виде конкретных входных значений,
помогая пользователю в отладке.

### 7.5 Проверки времени выполнения

В режиме `--enable-runtime-checks` компилятор преобразует спецификации в операторы `assert`:

- `requires`: вставка `assert(cond)` в начале функции
- `ensures`: вставка `assert(cond)` перед всеми точками возврата функции, где `result` заменён
  фактическим возвращаемым значением
- `invariant`: вставка `assert(cond)` в начале тела цикла

### 7.6 Интеграция с существующей архитектурой

- **Модель владения**: Выражения в спецификациях подчиняются правилам владения, доступны только для
  чтения (чистые функции), без побочных эффектов
- **Обобщённая система**: Типы спецификаций поддерживают параметры обобщённых типов (например,
  `Requires(P)`), могут комбинироваться с обобщёнными функциями/типами
- **Зависимые типы**: Значения, зависящие от типов в спецификациях (например, длина массива `n`),
  естественно доступны

### Влияние на систему типов

- Типы спецификаций являются обычными типами YaoXiang, соответствующими унифицированной модели
  синтаксиса
- Компилятор предоставляет встроенные типы спецификаций (`Positive`, `NonEmpty`, `GreaterOrEqual` и
  др.)
- Пользователи могут определять собственные типы спецификаций через обычные определения типов
- Типы спецификаций поддерживают параметры обобщённых типов и ограничения типов

### Поведение во время выполнения

- **Сборка Debug**: Вызов SMT-решателя для статической верификации, увеличение времени компиляции;
  после успешной верификации кэширование результатов
- **Сборка Release**: Аннотации спецификаций игнорируются, нулевые накладные расходы во время
  выполнения; очистка всего кэша верификации; агрессивные оптимизации, включая очистку Span-кэша
- **Режим проверок времени выполнения**: Генерация операторов assert, обнаружение нарушений во время
  выполнения

### Изменения в компиляторе

- Парсер: распознавание синтаксиса аннотаций спецификаций
- Семантический анализ: сбор спецификаций, преобразование в типы спецификаций
- Верификационный backend: генерация условий верификации, вызов SMT-решателя
- Генерация кода: поддержка режима проверок времени выполнения

### Обратная совместимость

- ✅ Полная обратная совместимость
- Аннотации спецификаций игнорируются при обычной компиляции, существующий код не затрагивается
- При сборке Release спецификации игнорируются, отсутствуют дополнительные накладные расходы

## Компромиссы

### Преимущества

- **Верификация при сборке Debug**: Обязательная верификация при сборке Debug обеспечивает
  логическую корректность
- **Элегантный синтаксис**: Чистые комментарии, без новых ключевых слов, удобство работы в
  редакторах
- **Интеграция с системой типов**: Спецификации являются типами, расширяемы
- **Постепенное внедрение**: Возможен переход от проверок времени выполнения к статической
  верификации
- **Повышение надёжности**: Обнаружение логических ошибок, трудно выявляемых тестированием

### Недостатки

- **Время компиляции**: Режим верификации может значительно увеличить время компиляции
- **Кривая обучения**: Необходимость изучения эффективного написания спецификаций и кванторов
- **Ограничения SMT-решателей**: Некоторые сложные свойства могут не поддаваться автоматическому
  доказательству

## Альтернативы

| Решение                                            | Преимущества                       | Недостатки                                            |
| -------------------------------------------------- | ---------------------------------- | ----------------------------------------------------- |
| Новые ключевые слова (например, `requires`)        | Интуитивный синтаксис              | Введение новых ключевых слов, нарушение простоты      |
| Отдельные файлы спецификаций (например, CVL)       | Разделение спецификаций и кода     | Увеличение количества файлов, сложность синхронизации |
| Только утверждения времени выполнения              | Простота реализации                | Отсутствие статических гарантий                       |
| **Наше решение (комментарии + типы спецификаций)** | Баланс простоты и функциональности | Необходимость поддержки редакторами                   |

## Стратегия реализации

### Этапы

| Фаза                                     | Содержание                                                                                                                                                                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фаза 1: Базовая поддержка**            | Расширение парсера для распознавания комментариев `//!` и `/*! ... !*/`, присоединение к узлам AST; в режиме верификации сбор спецификаций, генерация простых условий верификации (только арифметические сравнения); интеграция Z3-решателя |
| **Фаза 2: Поддержка кванторов**          | Поддержка выражений с кванторами, трансляция в `forall`/`exists` формата SMT-LIB; подсветка IDE и всплывающие подсказки для спецификаций                                                                                                    |
| **Фаза 3: Оптимизация и инструментарий** | Инкрементная верификация, кэширование проверенных модулей; отчёты о покрытии спецификаций; инструменты интеллектуального извлечения спецификаций (генерация кандидатов из тестов)                                                           |

### Зависимости

- RFC-009: Модель владения — выражения спецификаций требуют семантики чистых функций
- RFC-010: Унифицированный синтаксис типов — система типов спецификаций основана на системе типов
- RFC-011: Проектирование системы обобщённых типов — типы спецификаций поддерживают параметры
  обобщённых типов

### Риски

1. **Сложность интеграции SMT-решателя**: Интеграция Z3 и других решателей может столкнуться с
   техническими трудностями
   - Смягчение: Использование зрелых Rust-привязок к Z3, постепенное расширение поддерживаемых типов
     выражений

2. **Сложность отладки при сбое верификации**: Когда SMT-решатель не может доказать спецификацию,
   пользователю может быть трудно понять причину
   - Смягчение: Предоставление понятных сообщений об ошибках и объяснений контрпримеров

3. **Нагрузка на производительность**: Режим верификации может значительно увеличить время
   компиляции
   - Смягчение: Реализация инкрементной верификации и механизмов кэширования

### Описание статусов

| Статус        | Расположение            | Описание                                                          |
| ------------- | ----------------------- | ----------------------------------------------------------------- |
| **Черновик**  | `docs/design/rfc/`      | Авторский черновик, ожидает ревью                                 |
| **На ревью**  | `docs/design/rfc/`      | Открыто обсуждение и обратная связь сообщества                    |
| **Принято**   | `docs/design/accepted/` | Становится официальным документом дизайна, переходит к реализации |
| **Отклонено** | `docs/design/rfc/`      | Остаётся в директории RFC, статус обновлён                        |

### Действия после принятия

1. Переместить RFC в директорию `docs/design/accepted/`
2. Обновить имя файла на описательное (например, `hoare-logic-static-verification.md`)
3. Обновить статус на «Официальный»
4. Обновить статус на «Принят», добавить дату принятия

### Действия после отклонения

1. Оставить в директории `docs/design/rfc/`
2. Добавить в начало файла причину отклонения и дату
3. Обновить статус на «Отклонено»
