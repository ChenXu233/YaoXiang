# RFC-023: Модель захвата замыканий

> **Справка**:
>
> - [RFC-007: Унификация синтаксиса функций](../accepted/007-function-syntax-unification.md)
> - [RFC-009: Модель владения v9](../accepted/009-ownership-model.md)
> - [RFC-011: Дизайн обобщённой системы](../accepted/011-generic-type-system.md)
>   — Раздел 2.4: Встроенный marker trait Dup/Clone

## Аннотация

Данный RFC определяет **модель захвата замыканий** языка YaoXiang. Компилятор автоматически анализирует внешние переменные, на которые ссылается тело замыкания, и в зависимости от типа переменной (Dup/не-Dup) и от того, покидает ли замыкание область видимости, автоматически выбирает способ захвата — для типов Dup выполняется прямое копирование, для не-Dup без экранирования выполняется заимствование, для не-Dup с экранированием выполняется перемещение. Пользователю не требуются аннотации, используется единый набор правил с автоматическим выбором заимствования при вызове функций.

## Мотивация

### Зачем это нужно?

Текущая реализация захвата замыканий **отсутствует** — поле `env` инструкции `MakeClosure` всегда пустое, лямбды не могут ссылаться ни на какие внешние переменные. Система токенов заимствования требует, чтобы замыкания могли захватывать токены `&T` (нуль-стоимостное копирование), что является ключевым сценарием использования.

### Текущая проблема

```yaoxiang
# Такой код сейчас не компилируется — лямбда не может ссылаться на threshold
filter_by: (items: List(Point), threshold: &Float) -> List(Point) = {
    items.filter(|p| p.x > threshold)  # ❌ threshold невозможно захватить
}
```

## Предложение

### Основной дизайн

Захват замыканий полностью автоматически определяется компилятором. Правила **полностью идентичны** правилам автоматического выбора заимствования при вызове функций:

```
Тип переменной    Экранирует ли замыкание    Способ захвата
─────────────────────────────────────────────────────────────
Dup               Любой                      Копирование (побитовое или нуль-стоимостное)
Не-Dup            Не экранирует              Автоматическое заимствование (&T или &mut T)
Не-Dup            Экранирует                 Move (передача владения)
```

**Определение экранирования**:

```
spawn { || ... }           → Экранирует
return || ...              → Экранирует
let x = || ... ;  x  полe  → Экранирует
items.filter(|p| ...)      → Не экранирует (синхронный вызов функции высшего порядка)
||.method()                → Не экранирует (вызов на месте)
```

Консервативный принцип: при невозможности определения считать экранирующим.

### Примеры

```yaoxiang
# 1. Токен Dup — прямое копирование (нуль-стоимостное)
filter_by: (items: List(Point), threshold: &Float) -> List(Point) = {
    # threshold: &Float → Dup → компилятор копирует токен в замыкание
    # Токен нулевого размера, нулевые накладные расходы времени выполнения
    items.filter(|p| p.x > threshold)
}

# 2. Не-Dup + не экранирует — автоматическое заимствование
process: (buf: Buffer) -> Void = {
    # buf не является Dup, filter не экранирует → автоматическое создание токена &Buffer
    transform(|b| b.read())
    # После возврата замыкания токен освобождается, buf снова доступен
}

# 3. Замыкание экранирует — Move
spawn_worker: (data: Data) -> Void = {
    # data не является Dup, spawn → экранирует → Move
    spawn { use(data) }
}

# 4. Смешанный захват
complex: (items: List(Point), config: &Config, buf: Buffer) -> List(Point) = {
    # config: &Config → Dup → копирование токена
    # buf: Buffer → не Dup, не экранирует → заимствование &mut Buffer
    items.filter(|p| {
        let threshold = config.get_threshold()
        buf.update(p)
        p.x > threshold
    })
}

# 5. Обнаружение конфликта заимствования
bad: (buf: Buffer) -> Void = {
    closure = |b| b.write()
    buf.read()  # ❌ buf уже заимствован замыканием, конфликт
}
```

### Синтаксические изменения

**Нулевые синтаксические изменения**. Способ захвата определяется компилятором автоматически, пользователю не требуются аннотации.

## Подробный дизайн

### Влияние на систему типов

Сигнатура типа лямбды остаётся неизменной: `(params) -> Return`. Захваченные переменные не отражаются в сигнатуре типа, их обработка выполняется на этапе генерации IR компилятором.

### Изменения в компиляторе

| Компонент               | Изменение                              | Описание          |
| ----------------------- | -------------------------------------- | ----------------- |
| `capture.rs` (создать)  | Анализ захвата + анализ экранирования + выбор模式 | ~150 строк       |
| `expressions.rs`        | Вывод типа lambda вызывает анализ захвата      | ~10 строк        |
| `ir_gen.rs`             | Заполнение env в MakeClosure; пропуск ZST       | ~80 строк        |
| `ir.rs`                 | Возможно, нужна корректировка типа env в MakeClosure | ~5 строк    |

**Процесс анализа захвата**:

```
1. Обход AST тела лямбды
2. Сбор всех ссылок Expr::Var(name)
3. Фильтрация: только переменные из внешней области видимости замыкания
4. Классификация: Read (только чтение) / Write (чтение-запись) / Move (перемещён)
5. Проверка атрибутов типа: является ли Dup
6. Определение экранирования: способ использования замыкания
7. Выбор模式 захвата:
   Dup → Copy
   Не-Dup + не экранирует + Read → Borrow (&T)
   Не-Dup + не экранирует + Write → BorrowMut (&mut T)
   Не-Dup + экранирует → Move
```

**Генерация IR**:

```rust
// Текущее состояние (пусто)
Instruction::MakeClosure { dst, func, env: Vec::new() }

// Изменить на
Instruction::MakeClosure { dst, func, env: captured_env }

// Логика генерации captured_env:
for captured in captures {
    match captured.mode {
        Copy if is_zst(captured.ty) => {
            // Тип нулевого размера — не генерировать никаких инструкций
            // Тело замыкания напрямую ссылается на внешнюю переменную (устраняется на этапе компиляции)
        }
        Copy => {
            // Генерировать Move dst, src (поверхностное копирование типа Dup)
        }
        Borrow => {
            // Генерировать Borrow dst, src (создание ReadToken)
        }
        BorrowMut => {
            // Генерировать Borrow dst, src (создание WriteToken)
        }
        Move => {
            // Генерировать Move dst, src (передача владения)
        }
    }
}
```

### Поведение во время выполнения

Способ захвата не влияет на производительность во время выполнения:

- **Dup + ZST** (например, токен `&T`) → нуль-инструкций, тело замыкания напрямую ссылается на внешнюю переменную
- **Dup + не-ZST** (например, Int) → одно копирование регистра
- **Borrow/BorrowMut** → создание токена (концепция времени компиляции, нулевые накладные расходы)
- **Move** → та же стоимость, что и обычный Move

### Обратная совместимость

Полная совместимость. В данный момент все лямбды не могут захватывать внешние переменные, данный RFC только добавляет выразительность, не нарушая существующий код.

## Компромиссы

### Преимущества

1. **Нулевые аннотации**: пользователю не нужно писать никаких аннотаций захвата
2. **Единообразие с вызовами функций**: правила захвата = правила автоматического заимствования при вызове функций
3. **Нуль-стоимостность**: захват токенов Dup полностью устраняется на этапе компиляции
4. **Безопасность**: анализ экранирования предотвращает use-after-free

### Недостатки

1. **Консервативный анализ экранирования**: при невозможности определения выполняется экранирование, что может приводить к необязательному Move
2. **Неявность**: способ захвата не отражён в коде, при отладке требуется смотреть вывод компилятора

## Альтернативные решения

| Решение                    | Почему не выбрано                          |
| -------------------------- | ------------------------------------------ |
| Явное ключевое слово `move` в стиле Rust | Добавление нового синтаксиса, увеличение когнитивной нагрузки на пользователя |
| Всё через Move             | Невозможно выразить нуль-стоимостное заимствование токенов |
| Всё через заимствование   | Экранирование замыкания приведёт к висячим ссылкам |
| Ручные аннотации способа захвата | Противоречит философии проектирования «компилятор автоматизирует всё» |

## Стратегия реализации

### Фазы

1. **Фаза 1**: Анализ захвата (только идентификация ссылок на внешние переменные, без различия способов захвата)
2. **Фаза 2**: Анализ экранирования + выбор模式
3. **Фаза 3**: Генерация IR + оптимизация ZST
4. **Фаза 4**: Интеграция обнаружения конфликтов заимствования

### Зависимости

- Зависит от RFC-011 (обобщённая система, раздел 2.4 Dup/Clone trait) — требуется trait Dup для определения копируемости переменных
- Зависит от RFC-009 v9 (токены заимствования) — режимы захвата Borrow/BorrowMut требуют типов токенов
- После реализации RFC-023 и данного RFC можно приступать к реализации системы токенов заимствования (реализация RFC-009 v9)

### Риски

- Анализ экранирования может быть слишком консервативным, что приводит к необязательному Move; возможна последующая оптимизация
- Анализ захвата обобщённых замыканий может потребовать дополнительной обработки
