# RFC-001: Модель spawn и система обработки ошибок

## Источник проектирования

| Документ                                                   | Отношение                                   |
| ---------------------------------------------------------- | ------------------------------------------- |
| async-whitepaper                                           | Источник проектирования, теоретическая база |
| [language-spec](../../../reference/language-spec/index.md) | Целевая спецификация                        |

## Резюме

Предлагается модель spawn для YaoXiang: описание логики синхронным синтаксисом с автоматическим
параллельным выполнением во время исполнения. Ключевые механизмы: трёхуровневая архитектура
конкурентности + DAG-анализ зависимостей + система типов Result.

## Быстрый выбор

| Сценарий                  | Запись                       | Описание                                  |
| ------------------------- | ---------------------------- | ----------------------------------------- |
| Авто-параллелизм          | Без аннотаций (по умолчанию) | Максимальный параллелизм                  |
| Синхронное ожидание       | `@eager`                     | Ожидание завершения зависимостей          |
| Полностью последовательно | `@block`                     | Без конкурентности, для отладки           |
| Локальная конкурентность  | `spawn`                      | Конкурентность в области видимости @block |

## Мотивация

Современные модели конкурентности в mainstream-языках имеют явные недостатки:

| Язык       | Модель конкурентности | Проблема                                         |
| ---------- | --------------------- | ------------------------------------------------ |
| Rust       | async/await + tokio   | Заражение асинхронностью, крутая кривая обучения |
| Go         | goroutine             | Отсутствие типобезопасности                      |
| Python     | asyncio               | Ограничение GIL                                  |
| JavaScript | Promise/async         | Сложные обратные вызовы                          |

### Ключевые противоречия

1. **Прозрачность vs управляемость**: полная прозрачность без управляемости vs полная управляемость
   без прозрачности
2. **Конкурентность vs отлаживаемость**: конкурентные программы трудно отлаживать vs отлаживаемые
   программы трудно сделать конкурентными

## Предложение

### 1. Модель spawn: трёхуровневая архитектура конкурентности

> **Пояснение**: L1/L2/L3 — это ментальные модели, помогающие пользователю понять различные
> сценарии. Фактическая реализация использует единый механизм: автоматический DAG-анализ +
> управление аннотациями.

| Уровень | Ментальная модель            | Синтаксис                    | Способ выполнения                           | Параллелизм  |
| ------- | ---------------------------- | ---------------------------- | ------------------------------------------- | ------------ |
| **L1**  | Запрет конкурентности        | `@block`                     | Чисто последовательное выполнение           | ❌ Нет       |
| **L2**  | Конкурентность внутри @block | `spawn`                      | Управляемая конкурентность в области @block | ⚠️ Частичный |
| **L3**  | Полная конкурентность        | По умолчанию (без аннотаций) | Автоматический DAG-анализ                   | ✅ Полный    |

#### L1: Синхронный режим @block

```yaoxiang
main: () -> Void @block = {
    data1 = fetch_sync("api1")
    data2 = fetch_sync("api2")
    process(data1, data2)    # 严格顺序，无并发
}
```

#### L2: Управляемая конкурентность внутри @block

```yaoxiang
# spawn можно использовать только внутри функций с @block
main: () -> Void @block = {
    spawn { data1 = fetch_data("api1") }
    spawn { data2 = fetch_data("api2") }
    # 等待所有 spawn 完成（标准库控制）
    process(data1, data2)
}
```

#### L3: Полная прозрачность (по умолчанию)

```yaoxiang
# 不需要任何注解，编译器自动分析 DAG
heavy_calc: (n: Int) -> Int = fibonacci(n)

auto_parallel: (n: Int) -> Int = {
    a = heavy_calc(1)    # 自动并行
    b = heavy_calc(2)    # 自动并行
    c = heavy_calc(3)    # 自动并行
    a + b + c            # 需要值时等待所有结果
}
```

### 2. Полное сравнение аннотаций

| Измерение             | По умолчанию (без аннотаций) | `@eager`                         | `@block`              | `spawn`                      |
| --------------------- | ---------------------------- | -------------------------------- | --------------------- | ---------------------------- |
| **Способ выполнения** | Автоматический DAG-анализ    | Синхронное ожидание зависимостей | Чисто последовательно | Конкурентность внутри @block |
| **Параллелизм**       | ✅ Полный                    | ⚠️ По порядку зависимостей       | ❌ Нет                | ⚠️ Частичный                 |
| **Построение DAG**    | ✅                           | ✅                               | ❌                    | ✅                           |

**Руководство по выбору**:

- Максимальный параллелизм → без аннотаций (по умолчанию)
- Упорядоченные побочные эффекты → `@eager`
- Отладка / новички / критичный код → `@block`
- Конкурентность внутри @block → `spawn`

```yaoxiang
# 默认：最大化并行
calc_all: () -> Int = {
    a = heavy_calc(1)    # 自动并行
    b = heavy_calc(2)    # 自动并行
    a + b
}

# @eager：同步等待
calc_seq: () -> Int @eager = {
    a = heavy_calc(1)    # 同步执行
    b = heavy_calc(2)    # 同步执行
    a + b
}

# @block：纯顺序
calc_simple: () -> Int @block = {
    a = heavy_calc(1)    # 强制同步
    b = heavy_calc(2)    # 同步
    a + b
}

# spawn：@block 内并发
calc_mixed: () -> Int @block = {
    spawn { heavy_calc(1) }
    spawn { heavy_calc(2) }
    heavy_calc(3)        # 同步
}
```

### 3. DAG-анализ зависимостей

#### 3.1 Основной принцип: восходящее выполнение

```
用户代码（同步语法）：
    a = fetch(url0)
    b = fetch(url1)
    print(a)

编译时分析（自底向上）：
    print(a) 需要 a → 依赖 fetch(url0)
    fetch(url1) 没有人需要 → 孤岛 DAG

运行时调度（从叶子开始）：
    fetch(url0) → print(a)    ← 依赖链，按序
    fetch(url1)                ← 孤岛，独立并行
```

**Ключевое наблюдение**: не «сверху вниз» с генерацией Future, а «снизу вверх» — обратный анализ
зависимостей от результата.

#### 3.2 Изолированный DAG: независимый параллелизм

```
主流程：fetch(url0) → process → print
孤岛：  fetch(url1)  ← 没人要结果，独立并行

调度器：主流程按依赖链执行，孤岛用另一核心并行
```

#### 3.3 Типы ресурсов и побочные эффекты

**Основная идея**: операции с ресурсами помечаются типами, DAG автоматически строит зависимости.
Операции с одним и тем же ресурсом автоматически сериализуются, с разными — параллелятся.

**Границы типов ресурсов — строгое определение**:

Типы ресурсов — это типы, помеченные компилятором как встроенные. Следующие типы распознаются
компилятором как ресурсы:

| Тип ресурса | Описание                  | Поведение компилятора                                    |
| ----------- | ------------------------- | -------------------------------------------------------- |
| `FilePath`  | Путь в файловой системе   | Операции с одним путём автоматически сериализуются       |
| `HttpUrl`   | Конечная точка HTTP       | Операции с одним URL автоматически сериализуются         |
| `DBUrl`     | Соединение с базой данных | Операции с одним соединением автоматически сериализуются |
| `Console`   | Стандартный вывод         | Все операции Console автоматически сериализуются         |

Пользовательские типы ресурсов требуют явной пометки:

```yaoxiang
Database: Resource              # 显式标记为资源类型
query: (Database, String) -> Result(Row, Error)
# 参数 Database 是 Resource，自动识别为资源操作
```

Типы без пометки Resource не отслеживаются компилятором на предмет зависимостей по ресурсам.

**Правила использования**:

- Передача дескриптора ресурса через переменную — DAG автоматически управляет порядком
- Прямое использование одного и того же ресурса в литералах — вопрос проектирования пользователя, а
  не ответственность языка

```yaoxiang
# ✅ 正确：变量传递，DAG 自动串行
filename: String = "data.txt"
File.write(filename, x)
File.write(filename, y)    # DAG 串行

# ⚠️ 用户责任：字面量
File.write("data.txt", x)
File.write("data.txt", y)  # 可能并行，用户自己负责
```

#### 3.4 Обработка бесконечных циклов

```
1 个循环 → 直接同步执行，零调度开销
多个循环 → 调度器切片切换，真正并发
```

### 4. Тип Result и обработка ошибок

```yaoxiang
Result: (T: Type, E: Type) -> Type = { ok: (T) -> Self, err: (E) -> Self }

# ? 运算符透明传播
process: () -> Result(Data, Error) = {
    data = fetch_data()?
    processed = transform(data)?
    save(processed)?
}
```

### 5. Проектирование узлов DAG

```rust
enum NodeKind {
    Task,      // 任务节点
    Value,     // 值节点
    Control,   // 控制流节点
}

struct Node {
    id: NodeId,
    kind: NodeKind,
    inputs: Vec<ValueNodeId>,   // 输入依赖
    outputs: Vec<ValueNodeId>,  // 输出值
    span: Span,                 // 源码位置
}
```

| Тип ребра   | Символ | Семантика                                             |
| ----------- | ------ | ----------------------------------------------------- |
| DataEdge    | →      | Зависимость по данным (поток значений)                |
| ControlEdge | ●      | Управляющая зависимость (последовательное выполнение) |
| SpawnEdge   | ◎      | Точка входа в конкурентность (начало параллелизации)  |

### 6. Система типов

```
Send → 可安全跨线程传输
Sync → 可安全跨线程共享
Arc(T) 实现 Send + Sync（线程安全引用计数）
```

## Компромиссы

### Преимущества

1. **Постепенное внедрение**: трёхуровневая модель подходит для разного уровня навыков
2. **Естественный синтаксис**: параллельная производительность из синхронного кода
3. **Безопасность при компиляции**: ограничения Send/Sync устраняют гонки данных
4. **Отлаживаемость**: граф ошибок даёт чёткое представление распространения ошибок

### Недостатки

1. **Кривая обучения**: требуется понимание концепции DAG-зависимостей
2. **Время компиляции**: полный программный DAG-анализ может быть медленным
3. **Сложность инструментария**: требуются совершенно новые инструменты отладки и визуализации

## Альтернативы

| Подход                                     | Почему не выбран                                  |
| ------------------------------------------ | ------------------------------------------------- |
| Только явный async/await                   | Невозможно достичь прозрачной конкурентности      |
| Только полностью прозрачная конкурентность | Пользователь теряет управление                    |
| Go-подобный goroutine                      | Нет типобезопасности, нет проверок при компиляции |
| Только режим L1                            | Отказ от ключевой ценности модели spawn           |

## Стратегия реализации

### Разбивка на этапы

1. **Этап 1 (v0.1)**: синхронный режим @block, базовые типы
2. **Этап 2 (v0.2)**: планировщик FlowScheduler
3. **Этап 3 (v0.3)**: блоки spawn, явная конкурентность
4. **Этап 4 (v0.5)**: полная прозрачность L3, автоматический DAG-анализ
5. **Этап 5 (v0.6)**: граф ошибок, графический отладчик
6. **Этап 6 (v1.0)**: оптимизации, готовность к production

### Зависимости

- RFC-001 не имеет внешних зависимостей (базовое ядро)
- RFC-008 (модель конкурентности среды выполнения) → проектирование завершено
- RFC-011 (система генериков) → проектирование завершено

### Риски

1. **Производительность DAG-анализа**: полный программный анализ может быть O(n²), требуется
   оптимизация
2. **Отсутствие инструментария**: отладчик нужно разрабатывать с нуля
3. **Принятие пользователями**: прозрачная конкурентность требует качественной документации
