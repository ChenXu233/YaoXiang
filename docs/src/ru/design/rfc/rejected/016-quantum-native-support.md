# RFC 016: Квантовая встроенная поддержка и интеграция с множественными бэкендами

> **Причина отклонения**: Недостаточно предварительных зависимостей. Механизм Primitive::Extension ещё не реализован, компилятор языка не завершён, реальных пользовательских запросов нет. Квантовая поддержка должна быть переоценена как потребитель механизма Extension после созревания языка.

## Резюме

Данный документ определяет **квантовую нативную поддержку** и схему **интеграции с множественными бэкендами** для языка YaoXiang. Ключевая идея: **существующий дизайн YaoXiang (Move по умолчанию, возврат владения, непрозрачные типы, DAG-планировщик, константные параметры обобщений) естественным образом формирует полноценную основу для квантового языка программирования без введения какого-либо нового квантового специализированного синтаксиса**. Мы добавляем небольшое количество встроенных типов (`Qubit`, `Complex`, `Topology`) и встроенных функций (квантовые вентили, измерения, топологические ограничения), используя существующие механизмы языка для реализации квантовой нативной семантики, автоматического параллелизма для максимизации использования квантовых ресурсов, гибридного классического программирования и поддержки множественных бэкендов.

## Мотивация

### Зачем нужна квантовая встроенная поддержка?

Современная экосистема квантового программирования страдает от серьёзной фрагментации:

- **Низкоуровневые языки (QCIS, OpenQASM)**: напрямую управляют физическими квантовыми вентилями, но лишены системы типов и механизмов абстракции, что затрудняет написание сложных алгоритмов.
- **Высокоуровневые фреймворки (Qiskit, Cirq, Q#)**: построены на расширениях классических языков (Python, C#), квантовая семантика реализуется через библиотеки, что приводит к:
  - Правило неклонирования квантового состояния требует ручного соблюдения пользователем (или зависит от линейной системы типов).
  - Операции квантовых вентилей синтаксически отделены от классического кода, высокие затраты на обучение.
- **Гибридные вычисления**: квантовая и классическая части требуют явного разделения, отсутствует унифицированная модель потока данных.

### Текущие проблемы

Существующий дизайн YaoXiang恰好为解决这些问题提供了完备基础:

| Потребность квантовых вычислений | Существующий дизайн YaoXiang | Пояснение                                                    |
| -------------------------------- | ---------------------------- | ------------------------------------------------------------- |
| Неклонируемость квантового состояния | **Move-семантика по умолчанию** | Присваивание передаёт владение, без неявного копирования, естественно соответствует теореме о неклонировании |
| Квантовый вентиль как унитарное преобразование | **Возврат владения** | `q = H(q)` потребляет исходный кубит, возвращает новый кубит, точно соответствует семантике вентиля |
| Состояние запутывания | **Непрозрачные типы** | `BellPair` можно использовать только целиком, компилятор отслеживает время жизни, предотвращая ошибочное разложение |
| Физические топологические ограничения | **Константные параметры обобщений** | `Qubit(Topology, N)` — проверка соседства на этапе компиляции |
| Коллапс при измерении | **Повторное использование пустого состояния** | После измерения кубит становится пустым, может быть повторно инициализирован, имитируя коллапс квантового состояния |
| Автоматический параллелизм квантовых схем | **DAG-планировщик** | Операторы внутри функции автоматически параллелятся по зависимостям данных, не зависимые вентили естественно конкурируют |
| Гибридный классическо-квантовый поток управления | **Унифицированный синтаксис** | Квантовые и классические операции используют одну и ту же форму `name: type = value` |

**YaoXiang 不是"添加量子支持"，而是发现自己的设计已经量子原生。**

> **Пояснение семантики**: В данном документе используется **семантика владения** YaoXiang для выражения квантовых операций. На уровне компилятора обеспечивается неклонируемость (безопасность владения). На уровне языка "потребление-создание" является **синтаксическим выражением передачи владения** — потребление = получение владения, возврат = передача владения. Базовая реализация может использовать реальные обратимые квантовые вентили (модификация на месте), а не реальное "создание нового квантового состояния".

### Цели дизайна

1. **Ноль нового синтаксиса**: без введения ключевых слов вроде `quantum`, `circuit`, вся квантовая функциональность выражается через существующие механизмы языка.
2. **Типовая безопасность**: компилятор гарантирует, что квантовые состояния не копируются и не используются неправомерно.
3. **Компиляционная проверка топологических ограничений**: через константные параметры обобщений `Qubit(T, N)` проверка на этапе компиляции соответствия двухкубитных вентилей физической топологии.
4. **Прозрачная поддержка множественных бэкендов**: один и тот же квантовый код может компилироваться в QIR (универсальная экосистема) или QCIS (отечественный набор квантовых инструкций), переключение через командную строку.
5. **Бесшовное гибридное классическое**: квантовые вычисления могут свободно вызывать классические функции, классический код также может оперировать квантовыми данными (через `ref` совместное использование, но с ограничениями владения).

## Предложение

### Основной дизайн

#### 1. Отображение системы квантовых типов

**Базовые типы**:

```yaoxiang
Qubit: Type0 = primitive_qubit
Complex: Type0 = { re: Float, im: Float }
```

- `Qubit` — тип первого класса, следует правилам владения (Move, RAII).
- `Complex` используется для представления амплитуды, компилятор может выполнить встраивание и оптимизацию.

**Квантовые гейты как функции**:

```yaoxiang
# Сигнатуры встроенных функций
H: (Qubit) -> Qubit = builtin_hadamard
X: (Qubit) -> Qubit = builtin_pauli_x
Y: (Qubit) -> Qubit = builtin_pauli_y
Z: (Qubit) -> Qubit = builtin_pauli_z
CNOT: (control: Qubit, target: Qubit) -> { Qubit, Qubit } = builtin_cnot
```

- Все вентили потребляют входной кубит, возвращают новый кубит (или пару запутанных). Синтаксис возврата владения `q = H(q)` напрямую соответствует математической семантике.
- Многокубитные вентили возвращают структуры, результат получается через сопоставление с образцом или доступ к полям.

**Измерение**:

```yaoxiang
measure: (Qubit) -> Int = builtin_measure   # Потребляет кубит, возвращает классический бит
measure_all: (List(Qubit)) -> List(Int) = builtin_measure_all
```

- После измерения кубит потребляется (становится пустым), пользователь может повторно инициализировать через повторное использование пустого состояния.

**Инициализация**:

```yaoxiang
qubit: (Int) -> Qubit = builtin_qubit   # инициализация базисного состояния 0 или 1
```

#### 2. Запутанность и инкапсуляция через непрозрачные типы

Пара запутанных кубитов инкапсулируется как непрозрачный тип, предоставляются только комбинированные операции, разложение запрещено:

```yaoxiang
# Встроенный непрозрачный тип
BellPair: Type0 = primitive_bell_pair

# Встроенные функции - можно использовать только целиком
CNOT: (Qubit, Qubit) -> BellPair
measure_bell: (BellPair) -> { Int, Int }
split_bell: (BellPair) -> { Qubit, Qubit }  # Разделение пары запутанных кубитов (следует использовать осторожно)
apply_cnot_to_bell: (BellPair, Qubit) -> BellPair
```

**Ключевые решения дизайна**:

- Доступ к полям не предоставляется, разрешены только встроенные функции для работы целиком
- `measure_bell(bp)` потребляет всю пару запутанных кубитов за один раз, возвращает классические биты
- Компилятор может отслеживать полный жизненный цикл пары запутанных кубитов

**Сравнение с Python/Qiskit**:

```
Python (Qiskit): Схема строится во время выполнения, ошибки могут быть обнаружены только после отправки
YaoXiang:       Большинство логических ошибок перехватываются на этапе компиляции
```

**Оставшиеся 10%** (такие как физическая декогеренция, погрешности вентилей) — это проблемы оборудования, которые язык не может решить.

#### 3. Физические топологические ограничения

Квантовый чип представляет собой ограниченный топологический граф, **не любые два кубита могут выполнять двухкубитный вентиль**, они должны быть соседними. YaoXiang использует **константные параметры обобщений** для обеспечения топологических ограничений на этапе компиляции.

**Определение типов топологии**:

```yaoxiang
# Топология как тип, содержащий матрицу смежности
Topology: Type0 = primitive_topology

# Встроенные топологические константы
Linear8: Topology = topology(8)          # Линейные 8 бит: 0-1-2-3-4-5-6-7
Grid3x3: Topology = topology(3, 3)        # Сетка 3x3
Ring16: Topology = topology(16, ring)    # Кольцо из 16 бит
```

**Связывание Qubit с топологией и позицией**:

```yaoxiang
# Qubit(T, N) - T это тип топологии, N это константный позиционный параметр
q0: Qubit(Grid3x3, 0)   # Топология Grid3x3, позиция (0,0)
q1: Qubit(Grid3x3, 1)   # Топология Grid3x3, позиция (0,1)
q2: Qubit(Grid3x3, 2)   # Топология Grid3x3, позиция (0,2)
q3: Qubit(Grid3x3, 3)   # Топология Grid3x3, позиция (1,0)
```

**Автоматическое ограничение операций вентилей**:

```yaoxiang
# Сигнатура CNOT содержит топологическое ограничение
CNOT: (T: Topology, I: Int, J: Int) -> (
    (Qubit(T, I), Qubit(T, J)) -> { Qubit(T, I), Qubit(T, J) }
) when adjacent(T, I, J)

# Проверка на этапе компиляции
CNOT(q0, q1)  # ✅ В Grid3x3 (0,0) и (0,1) соседние
CNOT(q0, q2)  # ❌ Ошибка компиляции: (0,0) и (0,2) не соседние
```

**Компиляционное ограничение `adjacent`**:

- `adjacent` — это функция этапа компиляции, использующая матрицу смежности топологии для статической проверки
- При константных индексах — 100% верификация на этапе компиляции
- При динамических индексах — генерация кода проверки времени выполнения

**Виртуальное到物理映射**:

```yaoxiang
# Физическая позиция неизвестна на этапе компиляции? Используйте вывод типов
q = qubit(Grid3x3)  # Автоматическое распределение позиции 0, последующий вывод
```

#### 4. Ownership и линейное перемещение квантового состояния

Все квантовые операции следуют Move-семантике, гарантируя, что кубиты не копируются:

```yaoxiang
q = qubit(0)
q2 = q          # ❌ ошибка компиляции: q уже перемещён, не может использоваться
q = H(q)        # ✅ потребляет q, возвращает новый q
measure(q)      # ✅ потребляет q, далее q становится пустым
q = qubit(0)    # ✅ переиспользование пустого состояния
```

#### 4. Автоматический параллелизм и DAG-планировка

В Standard или Full Runtime DAG-планировщик автоматически анализирует квантовую программу:

```yaoxiang
apply_two_qubit_gates: () -> {Qubit, Qubit} = () => {
    q1 = H(qubit(0))
    q2 = H(qubit(0))
    # Вышеуказанные две строки не имеют зависимости по данным, DAG автоматически выполняет параллельно
    CNOT(q1, q2)   # Зависит от q1 и q2, автоматическое ожидание
}
```

- Планировщик использует конфигурацию `num_workers` (количество физических квантовых процессоров) для реального параллельного выполнения.
- Пользователю не нужно вручную упорядочивать вентили, достаточно описать поток данных.

#### 6. Гибридные классические вычисления

Классический и квантовый код полностью сливаются:

```yaoxiang
grover_search: (target: Int) -> Int = () => {
    n = 4
    qubits = List(Qubit)()
    for i in 0..n {
        qubits.append(H(qubit(0)))
    }
    # Смешивание классического цикла и квантовых операций
    oracle(qubits, target)   # oracle — последовательность квантовых гейтов
    qubits = diffusion(qubits)
    results = measure_all(qubits)
    return decode_result(results)   # классическая пост-обработка
}
```

- В одной функции можно произвольно смешивать квантовые вентили и классический поток управления.
- Система владения гарантирует, что квантовые переменные не будут ошибочно скопированы в классических ветвлениях.

#### 7. Архитектура поддержки множественных бэкендов

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   YaoXiang 源   │     │   类型检查      │     │   DAG 中间表示  │
│   (统一语法)     │────▶│   + 所有权分析   │────▶│   (数据流图)    │
└─────────────────┘     └─────────────────┘     └────────┬────────┘
                                                          │
                                                          ▼
                          ┌─────────────────────────────────────────────┐
                          │           代码生成后端 (可插拔)              │
                          ├─────────────────┬───────────────────────────┤
                          │  QIR 后端       │  QCIS 后端                │
                          │  (通用生态)      │  (国产量子指令集)         │
                          ├─────────────────┼───────────────────────────┤
                          │  - 输出 .ll 文件 │  - 输出 .qcis 文本        │
                          │  - 适配多种 QPU  │  - 适配中科院/国盾硬件    │
                          └─────────────────┴───────────────────────────┘
```

- **Процесс компиляции**: унифицированный фронтенд → построение DAG → выбор бэкенда → генерация целевого кода.
- **QIR бэкенд**: маппит узлы DAG на квантовые gate intrinsic QIR, генерирует LLVM bitcode с возможностью дальнейшей оптимизации LLVM.
- **QCIS бэкенд**: сериализует DAG в инструкции QCIS (например, `H q0`), поддерживает прямую отправку в консоль управления квантовым чипом.

### Примеры

#### Подготовка и измерение состояния Белла

```yaoxiang
bell_measure: () -> {Int, Int} = () => {
    q1 = H(qubit(0))
    q2 = H(qubit(0))
    bell = CNOT(q1, q2)  # Возвращает непрозрачный тип BellPair
    result = measure_bell(bell)  # Измеряет два бита за один раз
    return result
}
```

#### Квантовая телепортация (упрощённая)

```yaoxiang
teleport: (msg: Qubit, bell: BellPair) -> Qubit = (msg, bell) => {
    # Разделение пары запутанных кубитов для получения двух независимых кубитов
    (alice_qubit, bob_qubit) = split_bell(bell)

    # Операции Алисы
    (msg, alice_qubit) = CNOT(msg, alice_qubit)
    msg = H(msg)
    a1 = measure(msg)
    a2 = measure(alice_qubit)

    # Передача классической информации (автоматически обрабатывается планировщиком)
    # Операции Боба
    if a2 == 1 { bob_qubit = X(bob_qubit) }
    if a1 == 1 { bob_qubit = Z(bob_qubit) }
    return bob_qubit
}
```

## Детальный дизайн

### Определения встроенных типов и функций

В модуле `compiler/builtins` добавляется:

```rust
builtins.insert("Qubit", Ty::Primitive(Primitive::Qubit));
builtins.insert("Complex", Ty::Record(vec![
    ("re", Ty::Primitive(Primitive::Float)),
    ("im", Ty::Primitive(Primitive::Float)),
]));

// Квантовые гейты
for (name, sig) in GATES {
    builtins.insert(name, Ty::Function(vec![Ty::Qubit], Ty::Qubit));
}
builtins.insert("CNOT", Ty::Function(
    vec![Ty::Qubit, Ty::Qubit],
    Ty::Record(vec![
        ("q0", Ty::Qubit),
        ("q1", Ty::Qubit)
    ])
));
builtins.insert("measure", Ty::Function(vec![Ty::Qubit], Ty::Primitive(Primitive::Int)));
builtins.insert("qubit", Ty::Function(vec![Ty::Primitive(Primitive::Int)], Ty::Qubit));
```

### Особая обработка Qubit в проверке владения

- `Qubit` помечен как `!Copy` (Move по умолчанию), неявное копирование запрещено.
- Параметр функции измерения `measure` — `Qubit` (передача по значению), потребляет владение.
- В записях, возвращаемых многокубитными вентилями, все поля являются `Qubit`, требуется соблюдение правил владения.

### Оптимизация квантовых вентилей DAG-планировщиком

- Узлы квантовых вентилей рассматриваются как чистые функции (без побочных эффектов), планировщик может произвольно переупорядочивать не зависимые вентили.
- При выводе "последовательности квантовых инструкций" планировщик сохраняет зависимости по данным и группирует параллельные вентили (применимо для многокубитных процессоров).
- Поддержка конфигурации `--target-num-qubits` и `--target-topology` для последующего размещения и маршрутизации (будущее расширение).

### Детальной маппинг QIR бэкенда

| Операция YaoXiang  | Инструкция QIR                                                          |
| ------------------ | ----------------------------------------------------------------------- |
| `H(q)`             | `call void @__quantum__qis__h__body(%Qubit* %q)`                        |
| `CNOT(q1, q2)`     | `call void @__quantum__qis__cnot__body(%Qubit* %q1, %Qubit* %q2)`       |
| `measure(q)`       | `%result = call i1 @__quantum__qis__mz__body(%Qubit* %q)`               |
| `qubit(0)`         | `%q = call %Qubit* @__quantum__rt__qubit_allocate()`                    |

QIR бэкенд использует `-O2` LLVM для дальнейшей оптимизации и выводит bitcode, совместимый со стандартом QIR Alliance.

### Детальной маппинг QCIS бэкенда

| Операция YaoXiang                        | Инструкция QCIS                            |
| ---------------------------------------- | ------------------------------------------ |
| `H(q)` (q соответствует физическому биту 2) | `H 2`                                       |
| `CNOT(q1,q2)` (q1→бит 0, q2→бит 1)      | `CNOT 0 1`                                  |
| `measure(q)` (бит 0)                     | `M 0`                                       |
| Инициализация `qubit(0)`                 | Подразумевается в первой используемой инструкции, не требует дополнительной инструкции |

- Необходимо вести таблицу маппинга виртуальных кубитов (переменных YaoXiang) на физические биты.
- Поддержка проверки топологических ограничений (будущая реализация).

### Генерация гибридного классического кода

- Классическая часть (циклы, условия, целочисленные операции) генерирует нативный код как обычно (x86/ARM), через FFI или встроенные вызовы взаимодействует с квантовым бэкендом.
- В QIR бэкенде классическая часть может быть понижена до LLVM IR и смешанно компилироваться с QIR.

### Влияние на систему типов

- Добавлены примитивные типы `Qubit` и `Complex`.
- `Qubit` автоматически имеет Move-семантику, копирование запрещено.
- Сигнатуры функций квантовых вентилей должны быть зарегистрированы в системе типов.

### Обратная совместимость

- ✅ Полная обратная совместимость
- Новые встроенные типы и функции не влияют на существующий код
- Квантовая функциональность опциональна, при отключении нет дополнительных издержек

## Компромиссы

### Преимущества

- **Нет нового синтаксиса**: разработчикам нужно выучить только несколько встроенных функций для написания квантовых программ.
- **Типовая безопасность**: система владения автоматически предотвращает копирование кубитов, избегая распространённых ошибок квантового программирования.
- **Автоматический параллелизм**: DAG-планировщик бесплатно предоставляет параллелизм на уровне вентилей без дополнительной оптимизации компилятора.
- **Совместимость с экосистемой**: QIR бэкенд позволяет YaoXiang работать на нескольких квантовых облачных платформах; QCIS бэкенд обеспечивает технологическую независимость.
- **Гибридные возможности**: естественное слияние классического и квантового кода подходит для написания сложных квантовых алгоритмов (классическое управление в Shor, Grover).

### Недостатки

- **Статическое количество Qubit**: текущий дизайн предполагает, что количество кубитов известно на этапе компиляции, динамическое распределение через `List(Qubit)`, но кучевое выделение `List` может вносить дополнительные издержки (можно смягчить оптимизацией).
- **Повторное использование после измерения**: повторное использование пустого состояния позволяет переинициализировать кубит, но физические кубиты могут иметь время релаксации, требуется система времени выполнения (в данный момент ответственность пользователя).
- **Динамическое маппирование топологии**: когда физическая топология становится известна только во время выполнения, проверка на этапе компиляции не работает, требуется генерация кода проверки времени выполнения (текущая версия поддерживает только статическую проверку).

## Альтернативные решения

| Решение                                     | Почему не выбрано                                               |
| ------------------------------------------- | ---------------------------------------------------------------- |
| Введение ключевого слова `quantum` и типа `circuit` | Добавление нового синтаксиса, высокие затраты на обучение, противоречит принципу простоты дизайна YaoXiang |
| Реализация квантовой поддержки только как библиотеки | Невозможность использования компилятора для гарантии безопасности квантовых состояний, невозможность глубокой интеграции с DAG-планировщиком |
| Ожидание созревания квантового оборудования для поддержки | Упущение критического окна для дизайна языка квантового программирования |
| Повторное использование существующих квантовых фреймворков (например, Qiskit) | Квантовая семантика реализуется через библиотеку, невозможно получить гарантии безопасности системы типов и владения |
| Отдельный дизайн квантового подъязыка | Увеличение сложности языка, высокие затраты на поддержку |

## Стратегия реализации

### Этапы

| Этап    | Время    | Содержание                                                                                                   |
| ------- | -------- | ------------------------------------------------------------------------------------------------------------ |
| Phase 1 | 1 месяц  | Базовые квантовые типы и встроенные функции: добавление типов `Qubit`, `Complex` в компилятор, реализация проверки типов встроенных функций, расширение проверки владения |
| Phase 2 | 1 месяц  | DAG-планировщик распознаёт квантовые вентили: модификация логики построения DAG, пометка квантовых вентилей как чистых функций, реализация параллельной группировки вывода |
| Phase 3 | 2 месяца | QIR бэкенд прототип: реализация генератора кода DAG → QIR, интеграция LLVM, подключение QIR-симулятора для верификации |
| Phase 4 | 2 месяца | QCIS бэкенд прототип: реализация транслятора DAG → инструкции QCIS, дизайн маппинга виртуальных-физических битов, подключение отечественной квантовой платформы для верификации |
| Phase 5 | 2 месяца | Усиление гибридного классического: обеспечение корректной генерации кода при пересечении классического потока управления и квантовых вентилей, поддержка `List(Qubit)`, добавление примеров программ |
| Phase 6 | 2 месяца | Оптимизация и документация: реализация базового размещения и маршрутизации, написание руководства пользователя и учебника квантового программирования, выпуск предварительной версии |

### Риски

1. **Доступность квантового оборудования**: зависимость от доступности внешних квантовых симуляторов и реальных QPU.
   - **Смягчение**: приоритет подключения к открытым симуляторам (QIR runner, Qiskit Aer), реальные QPU как долгосрочная цель.

2. **Сложность реализации бэкендов**: спецификации QIR и QCIS могут изменяться.
   - **Смягчение**: абстракция интерфейса генерации кода, изоляция различий бэкендов для удобства последующей адаптации.

3. **Неопределённость производительности**: характеристики производительности квантовых программ отличаются от классических.
   - **Смягчение**: предоставление инструментов профилирования, чтобы пользователи понимали эффект параллелизма на уровне вентилей.

## Открытые вопросы

- [x] **Топологические ограничения**: реализованы через константные параметры обобщений `Qubit(Topology, N)` с проверкой на этапе компиляции.
- [ ] **Динамический квантовый регистр**: как `List(Qubit)` маппится в QCIS бэкенде? Можно генерировать соответствующее количество физических битов, но требуется механизм распределения времени выполнения.
- [ ] **Смягчение ошибок**: предоставлять ли встроенные конструкции смягчения ошибок (например, динамическая декoupling)? Можно сначала реализовать как библиотеку.
- [ ] **Взаимодействие с существующими квантовыми SDK**: можно ли импортировать модули QASM или QIR? В будущем можно рассмотреть FFI.
- [ ] **Автоматическое размещение и маршрутизация**: когда количество виртуальных кубитов превышает количество физических кубитов, как автоматически маппить?
