# RFC-003：Планирование версий

> **Дата отклонения**: 2026-06-01

## ⚠️ Причина отклонения

**Данный RFC не соответствует спецификациям RFC и был отклонён.**

### Анализ проблем

| Проблема             | Описание                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| **Неверный тип документа** | RFC — это документ решений о том, «почему так спроектировано», а данная статья — документ управления проектом о том, «где мы сейчас и куда идём» |
| **Отсутствие проектных решений** | Нет анализа компромиссов при выборе технологий, нет сравнения альтернативных вариантов, нет обоснования дизайна |
| **Избыточное планирование**     | Запланировано 9 версий (v0.1-v1.0), но выполнено только 1.5, всё после v0.3 — лишь предположения    |
| **Высокая стоимость поддержки** | Таблица показателей успеха содержит 50 состояний, что сложно поддерживать                             |
| **Путаница с номерами версий**  | Пропущен v0.8, объяснения нет                                                                    |

### Корректный тип документа

Данный документ следует вести как **дорожную карту проекта (Roadmap)**, а не RFC. Дорожная карта фиксирует факты и кракосрочные планы, а RFC записывает проектные решения.

## Аннотация

План выпуска версий YaoXiang, дорожная карта от v0.1 до v1.0.

**Ключевые цели**:

1. **Компиляция в байт-код**: поддержка REPL и поэтапной компиляции
2. **Самозагрузка (Bootstrap)**: написание компилятора YaoXiang на YaoXiang
3. **AOT-компиляция**: компиляция байт-кода в машинный код для целевой платформы

## 1. Мотивация

### Зачем нужно версионное планирование?

1. **Управление проектом**: разбиение целей на выполнимые вехи
2. **Ожидания пользователей**: информирование о стадиях развития языка
3. **Распределение ресурсов**: определение приоритетов на каждом этапе
4. **Контроль рисков**: своевременное выявление проблем и корректировка курса

### Основные проектные решения

- **Приоритет байт-кода**: сначала реализуем интерпретацию, затем AOT
- **Поэтапная поставка**: каждая версия содержит работающий функционал
- **Обратная совместимость**: до v1.0 API может изменяться, но с предварительным уведомлением
- **Верификация самозагрузкой**: доказательство выразительности языка через самозагрузку
- **Послойная оптимизация производительности**: сначала работает, потом оптимизируется

## 四、Трёхуровневая архитектура стратегии компиляции

| Уровень    | Версия  | Вход            | Выход           | Описание           |
| ---------- | ------- | --------------- | --------------- | ------------------ |
| L1: Байт-код | v0.1+ | Исходный код (.yx) | Байт-код (.yxb) | Интерпретация VM  |
| L2: Самозагрузка | v0.9+ | Исходный код YaoXiang | Байт-код    | Компилирует сам себя |
| L3: AOT    | v1.0+ | Исходный код/байт-код | Машинный код | Нативная производительность |

**Причины приоритета байткода**:

1. **Поддержка REPL**: немедленная компиляция введённого кода, интерактивная разработка
2. **Поэтапная компиляция**: изменение одной функции требует перекомпиляции только этой части
3. **Кроссплатформенность**: файлы .yxb работают на разных платформах, нужен только VM для целевой платформы

## 5. Стратегия зависимостей

**Краткосрочная перспектива**: Вызов библиотек Rust, повторное использование crates.io (Cargo как основа)

**Текущие зависимости**:

- Конкурентность: parking_lot, crossbeam, rayon
- Структуры данных: indexmap, hashbrown, smallvec
- Сети: tokio
- Сериализация: serde, ron

**Долгосрочная перспектива**: Собственные стандартная библиотека и менеджер пакетов
