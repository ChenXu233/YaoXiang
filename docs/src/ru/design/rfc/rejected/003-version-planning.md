# RFC-003: Версионное планирование

> **Дата отклонения**: 2026-06-01

## ⚠️ Причина отклонения

**Данный RFC не соответствует спецификациям RFC и был отклонён.**

### Анализ проблем

| Проблема                            | Описание                                                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Неверный тип документа**          | RFC — это документ о решениях вида «почему именно так», а данный текст — документ управления проектом вида «где мы сейчас и куда идём» |
| **Отсутствие проектных решений**    | Нет анализа компромиссов при техническом выборе, нет сравнения альтернатив, нет обоснования дизайна                                    |
| **Избыточное планирование**         | Запланировано 9 версий (v0.1–v1.0), но завершено лишь 1,5; всё после v0.3 — предположения                                              |
| **Высокая стоимость сопровождения** | Таблица показателей успеха содержит 50 состояний, её сложно поддерживать                                                               |
| **Путаница с номерами версий**      | Версия v0.8 пропущена без объяснения                                                                                                   |

### Корректный тип документа

Данный документ следует вести как **дорожную карту проекта (Roadmap)**, а не как RFC. Дорожная карта
фиксирует факты и краткосрочные планы, а RFC — проектные решения.

> **Ниже приведено исходное содержание, сохранённое для справки.**

## Аннотация

План выпуска версий YaoXiang, дорожная карта от v0.1 до v1.0.

**Основные цели**:

1. **Байткод-компиляция**: поддержка REPL и инкрементальной компиляции
2. **Самозагрузка (Bootstrap)**: написание компилятора YaoXiang на самом YaoXiang
3. **AOT-компиляция**: компиляция байткода в нативный машинный код

## 1. Мотивация

### Зачем нужно версионное планирование?

1. **Управление проектом**: разбиение целей на выполнимые этапы
2. **Ожидания пользователей**: информирование пользователей о стадии развития языка
3. **Распределение ресурсов**: определение приоритетов на каждом этапе
4. **Контроль рисков**: своевременное обнаружение проблем и корректировка курса

### Основные проектные решения

- **Приоритет байткода**: сначала интерпретация, затем AOT
- **Инкрементальная поставка**: каждая версия содержит пригодный к использованию функционал
- **Обратная совместимость**: до v1.0 API может меняться, но об этом будет объявлено заранее
- **Проверка самозагрузкой**: выразительность языка подтверждается через самозагрузку
- **Многоуровневая производительность**: сначала заставить работать, затем оптимизировать

## 4. Трёхуровневая архитектура стратегии компиляции

| Уровень          | Версия | Вход                     | Выход          | Описание                    |
| ---------------- | ------ | ------------------------ | -------------- | --------------------------- |
| L1: Байткод      | v0.1+  | Исходный код (.yx)       | Байткод (.yxb) | Интерпретация в VM          |
| L2: Самозагрузка | v0.9+  | Исходный код на YaoXiang | Байткод        | Компиляция самой себя       |
| L3: AOT          | v1.0+  | Исходный код / байткод   | Машинный код   | Нативная производительность |

**Причины приоритета байткода**:

1. **Поддержка REPL**: мгновенная компиляция вводимого кода для интерактивной разработки
2. **Инкрементальная компиляция**: при изменении одной функции перекомпилируется только она
3. **Платформонезависимость**: файлы .yxb запускаются на любой платформе, нужен лишь VM под эту
   платформу

## 5. Стратегия зависимостей

**Краткосрочно**: вызов библиотек Rust с crates.io (паразитирование на Cargo)

**Текущие зависимости**:

- Конкурентность: parking_lot, crossbeam, rayon
- Структуры данных: indexmap, hashbrown, smallvec
- Сеть: tokio
- Сериализация: serde, ron

**Долгосрочно**: собственная стандартная библиотека и пакетный менеджер
