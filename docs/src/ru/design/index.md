# Документация по дизайну YaoXiang

> Дао рождает одно, одно рождает два, два рождает три, три рождает все сущее.

В этом каталоге содержатся проектные решения, предложения и обсуждения языка программирования YaoXiang.

## Базовые принципы проектирования

| Принцип             | Описание                                                |
| ------------------- | ------------------------------------------------------- |
| **Всё является типом** | Значения, функции, модули — всё это типы; типы — объекты первого класса |
| **Естественный синтаксис** | Читаемость на уровне Python, приближённость к естественному языку |
| **Модель владения** | Абстракция с нулевой стоимостью, без GC, высокая производительность |
| **Модель параллелизма** | Синхронный синтаксис, асинхронная сущность, автоматический параллелизм |
| **Дружелюбие к ИИ** | Строгая структурированность, чёткий AST                |

## Участие в дизайн-обсуждениях

### Жизненный цикл RFC

Предложения RFC имеют 5 статусов:

| Статус          | Значение                                    |
| --------------- | ------------------------------------------- |
| Черновик        | Работа в процессе                           |
| На рассмотрении | Открытое обсуждение                         |
| Принято         | Дизайн одобрен                              |
| Устарело        | Было принято, заменено новым дизайном       |
| Отклонено       | Не одобрено                                 |

Полный жизненный цикл:

```
Черновик → На рассмотрении → Принято → Устарело (заменено)
                             ↓
                          Отклонено (не одобрено)
```

### Процесс предложения

```
1. Составление предложения (по шаблону RFC)
   → Помещается в rfc/draft/

2. Подача на рассмотрение
   → Перемещается в rfc/review/, открытое обсуждение сообществом

3. Рассмотрение основной командой
   → Принято → Перемещается в rfc/accepted/
   → Отклонено → Перемещается в rfc/rejected/

4. Последующее сопровождение
   → Заменено → Перемещается в rfc/deprecated/
```

### Принципы дизайна

- **Чёткие границы**: Каждое проектное решение должно иметь чёткую область применения
- **Практичность прежде всего**: Решаем реальные проблемы, а не воображаемые угрозы
- **Неизменность видимого поведения для пользователей**: Никогда не ломать пользовательское пространство

## Ключевые дизайн-решения

### 1. Система типов

- **Унифицированный синтаксис типов**: Отказ от `enum`, `struct`, `union`, унификация через `Name: Type = {...}`
- **Конструкторы являются типами**: Устранение разрыва между «типом» и «значением»
- **Поддержка обобщений**: Мономорфизация на этапе компиляции, нулевые накладные расходы во время выполнения

### 2. Модель параллелизма

```yaoxiang
// Модель параллелизма: последовательное выполнение по умолчанию, spawn вводит потоковый параллелизм

// Последовательное выполнение по умолчанию
compute: (Int) -> Int = (n) => {
    a = heavy_calc(1)
    b = heavy_calc(2)  // Последовательное выполнение, ожидание завершения a
    c = heavy_calc(3)  // Последовательное выполнение, ожидание завершения b
    a + b + c
}

// Блок spawn вводит потоковый параллелизм
process: () -> Void = () => {
    spawn {
        users = fetch_users()   // параллельно
        posts = fetch_posts()   // параллельно
    }
    // Вызывающая сторона синхронно блокируется, ожидая результат
    render(users, posts)
}
```

### 3. Обработка ошибок

```yaoxiang
Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }

process: () -> Result(Data, Error) = {
    data = fetch_data()?      // Оператор ? прозрачно распространяет ошибку
    transformed = transform(data)?
    save(transformed)?
}
```
