# YaoXiang Дизайн-документ

> Дао рождает единое, единое рождает двойственное, двойственное рождает тройственное, тройственное рождает все сущее.

Этот каталог содержит проектные решения, предложения и обсуждения для языка программирования YaoXiang.

## Основные принципы проектирования

| Принцип | Описание |
|------|------|
| **Всё есть тип** | Значения, функции, модули — всё это типы; типы являются сущностями первого класса |
| **Естественный синтаксис** | Читаемость на уровне Python, близость к естественному языку |
| **Модель владения** | Абстракции с нулевой стоимостью, без GC, высокая производительность |
| **Модель spawn** | Синхронный синтаксис, асинхронная сущность, автоматическое распараллеливание |
| **AI-дружественный** | Строго структурированный, ясный AST |

## Участие в обсуждении дизайна

### Жизненный цикл RFC

Предложения RFC имеют 5 состояний:

| Состояние | Значение |
|------|------|
| Черновик | Работа в процессе |
| На рассмотрении | Открытое обсуждение |
| Принято | Дизайн одобрен |
| Устарело | Было принято ранее, заменено новым дизайном |
| Отклонено | Не одобрено |

Полный жизненный цикл:
```
Черновик → На рассмотрении → Принято → Устарело (заменено)
                              ↓
                          Отклонено (не одобрено)
```

### Процесс подачи предложений

```
1. Подготовить предложение (используя шаблон RFC)
   → Поместить в rfc/draft/

2. Отправить на рассмотрение
   → Переместить в rfc/review/, открыть общественное обсуждение

3. Оценка основной командой
   → Принято → Переместить в rfc/accepted/
   → Отклонено → Переместить в rfc/rejected/

4. Последующая поддержка
   → Заменено → Переместить в rfc/deprecated/
```

### Принципы проектирования

- **Чёткие границы**: каждое проектное решение должно иметь ясную область применения
- **Практичность прежде всего**: решать реальные проблемы, а не воображаемые угрозы
- **Видимое поведение для пользователя не меняется**: Never break userspace

## Ключевые проектные решения

### 1. Система типов

- **Единый синтаксис типов**: отмена `enum`, `struct`, `union`, унификация через `Name: Type = {...}`
- **Конструктор как тип**: устранение разрыва между «типом» и «значением»
- **Поддержка обобщений**: мономорфизация на этапе компиляции, нулевые накладные расходы во время выполнения

### 2. Модель spawn

```yaoxiang
// Модель spawn: по умолчанию последовательное выполнение, spawn вводит параллелизм потоков данных

// Последовательное выполнение по умолчанию
compute: (Int) -> Int = (n) => {
    a = heavy_calc(1)
    b = heavy_calc(2)  // Последовательное выполнение, ожидание завершения a
    c = heavy_calc(3)  // Последовательное выполнение, ожидание завершения b
    a + b + c
}

// Блок spawn вводит параллелизм потоков данных
process: () -> Void = () => {
    spawn {
        users = fetch_users()   // Параллельно
        posts = fetch_posts()   // Параллельно
    }
    // Вызывающая сторона синхронно блокируется в ожидании результата
    render(users, posts)
}
```

### 3. Обработка ошибок

```yaoxiang
Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }

process: () -> Result(Data, Error) = {
    data = fetch_data()?      // Оператор ? прозрачно распространяет ошибку
    transformed = transform(data)?
    save(transformed)?
}
```
