# Дизайн-документ YaoXiang

> Дао рождает единое, единое рождает двойственное, двойственное рождает тройственное, тройственное
> рождает все сущее.

Данный каталог содержит дизайн-решения, предложения и обсуждения языка программирования YaoXiang.

## Основные дизайн-концепции

| Концепция                  | Описание                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------- |
| **Всё есть тип**           | Значения, функции, модули — всё это типы; типы — полноправные граждане первого класса |
| **Естественный синтаксис** | Читаемость как у Python, близость к естественному языку                               |
| **Модель ownership**       | Абстракции с нулевой стоимостью, без GC, высокая производительность                   |
| **Модель spawn**           | Синхронный синтаксис, асинхронная сущность, автоматический параллелизм                |
| **AI-дружественность**     | Строгая структурированность, чёткий AST                                               |

## Участие в дизайн-обсуждениях

### Жизненный цикл RFC

Предложения RFC имеют 5 состояний:

| Статус          | Значение                              |
| --------------- | ------------------------------------- |
| Черновик        | Работа в процессе                     |
| На рассмотрении | Открытое обсуждение                   |
| Принято         | Дизайн одобрен                        |
| Устарело        | Было принято, заменено новым дизайном |
| Отклонено       | Не одобрено                           |

Полный жизненный цикл:

```
Черновик → На рассмотрении → Принято → Устарело (заменено)
                                  ↓
                              Отклонено (не одобрено)
```

### Процесс предложения

```
1. Составление предложения (используя шаблон RFC)
   → Помещается в rfc/draft/

2. Отправка на рассмотрение
   → Перемещается в rfc/review/, открытое обсуждение сообщества

3. Рассмотрение основной командой
   → Принято → Перемещается в rfc/accepted/
   → Отклонено → Перемещается в rfc/rejected/

4. Последующее сопровождение
   → Заменено → Перемещается в rfc/deprecated/
```

### Принципы дизайна

- **Чёткие границы**: каждое дизайн-решение должно иметь чёткую область применения
- **Практичность прежде всего**: решать реальные проблемы, а не воображаемые угрозы
- **Поведение, наблюдаемое пользователем, не меняется**: Never break userspace

## Ключевые дизайн-решения

### 1. Система типов

- **Унифицированный синтаксис типов**: упразднение `enum`, `struct`, `union`, единообразное
  использование `Name: Type = {...}`
- **Конструктор — это тип**: устранение разрыва между «типом» и «значением»
- **Поддержка generics**: мономорфизация на этапе компиляции, нулевые накладные расходы в runtime

### 2. Модель spawn

```yaoxiang
// Модель spawn: по умолчанию последовательное выполнение, spawn вводит параллелизм потоков данных

// Последовательное выполнение по умолчанию
compute: (Int) -> Int = (n) => {
    a = heavy_calc(1)
    b = heavy_calc(2)  // Последовательно, ожидает завершения a
    c = heavy_calc(3)  // Последовательно, ожидает завершения b
    a + b + c
}

// spawn-блок вводит параллелизм потоков данных
process: () -> Void = () => {
    spawn {
        users = fetch_users()   // параллельно
        posts = fetch_posts()   // параллельно
    }
    // Вызывающая сторона синхронно блокируется в ожидании результата
    render(users, posts)
}
```

### 3. Обработка ошибок

```yaoxiang
Result: (T: Type, E: Type) -> Type = { ok: (T) -> Result(T, E), err: (E) -> Result(T, E) }

process: () -> Result(Data, Error) = {
    data = fetch_data()?      // Оператор ? обеспечивает прозрачное распространение
    transformed = transform(data)?
    save(transformed)?
}
```
