## Общие положения

### Область применения

Настоящие спецификации применяются ко всему тестовому коду Rust в проекте YaoXiang, включая:

| Тип теста              | Расположение                 | Фреймворк                  |
| ---------------------- | ---------------------------- | -------------------------- |
| Модульные тесты        | `src/<module>/tests/`        | `#[test]` + `#[cfg(test)]` |
| Интеграционные тесты   | `tests/`                     | `#[test]`                  |
| Нагрузочные тесты      | `benches/`                   | Criterion.rs               |
| Документационные тесты | Комментарии документации API | `cargo test --doc`         |
| Property-тесты         | Любое расположение тестов    | proptest / quickcheck      |

### Основные принципы

**Принцип 0: Авторитетным источником для тестов является спецификация, а не код.** Это самый важный
принцип данного документа. Тесты проверяют, соответствует ли код спецификации, а не "работает ли код
в текущей реализации". Когда тест обнаруживает несоответствие поведения кода спецификации,
**исправляйте код, никогда не исправляйте тест**.

Файлы спецификации расположены по адресам:

- `docs/src/design/language-spec.md` — базовая спецификация языка
- `docs/src/design/rfc/accepted/` — принятые дизайн-документы RFC

В верхней части каждого тестового файла должна быть ссылка на соответствующий раздел спецификации
(см. правило 2.1). Любой разработчик должен иметь возможность, взяв документ спецификации, проверить
на соответствие ему тесты и корректность реализации. И наоборот — если для некоторого кода нет
соответствующего описания в спецификации, он не должен существовать, и тем более не должен
тестироваться.

```rust
// 🟢 Хорошо — тест напрямую ссылается на спецификацию, проверяя соответствие кода
//! Тесты литералов — основаны на спецификации языка §2.6
//!
//! §2.6.1: Целые числа Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: Числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: Строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: F-String интерполяция

#[test]
fn test_decimal_literal_parsing() {
    // Спецификация §2.6.1: Decimal ::= [0-9][0-9_]*
    let result = parse_literal("42").unwrap();
    assert_eq!(result, Literal::Int(42));
}

// 🔴 Мусор — тест подстраивается под поведение текущей реализации, а не проверяет спецификацию
#[test]
fn test_literal_1() {
    // Неизвестно, какому разделу спецификации соответствует этот код
    // Если parse_literal вернёт неверное значение, этот тест "пропустит" его
    // потому что проверяет лишь то, что функция не паникует
    let result = parse_literal("42");
    assert!(result.is_ok());
}
```

**Сценарий**: вы написали тест и обнаружили, что поведение кода не соответствует спецификации. У вас
два варианта:

| Неправильный подход                                             | Правильный подход                                           |
| --------------------------------------------------------------- | ----------------------------------------------------------- |
| Изменить тест, чтобы он "прошёл"                                | Изменить код, чтобы поведение соответствовало спецификации  |
| Добавить в тест `#[ignore]`                                     | Немедленно исправить реализацию                             |
| Добавить в тест специальные ветвления, подстраивающиеся под код | Удалить ветвления, позволив тесту напрямую выявить проблему |

Запомните: **красный свет = код неправильный, а не тест.** (Если только в самом тесте нет бага — это
уже другое дело.)

**Принцип 1: Тесты — это документация.** Любой разработчик должен иметь возможность, прочитав тесты,
понять поведение тестируемого кода без дополнительных комментариев или внешней документации.

```rust
// 🟢 Хорошо — имя теста говорит, что тестируется и что ожидается
#[test]
fn test_tokenize_empty_input_returns_eof() {
    let tokens = tokenize("").unwrap();
    assert_eq!(tokens.len(), 1);
    assert!(matches!(tokens[0].kind, TokenKind::Eof));
}

// 🔴 Мусор — непонятно, что вообще тестируется
#[test]
fn test_tokenize_1() {
    let tokens = tokenize("").unwrap();
    assert!(tokens.len() > 0);
}
```

**Принцип 2: Нулевая терпимость к случайным сбоям.** Тесты должны быть повторяемыми в любом
окружении. Тесты, зависящие от случайных чисел, системного времени или порядка планирования потоков,
должны использовать фиксированные сиды или заменяться моками.

**Принцип 3: Один тест проверяет одну вещь.** Если имя теста требует союза "и" для соединения
нескольких поведений, разделите его на несколько тестов.

```rust
// 🟢 Хорошо — каждый тест проверяет один сценарий
#[test]
fn test_parse_int_positive() { /* ... */ }
#[test]
fn test_parse_int_zero() { /* ... */ }

// 🔴 Мусор — в одном тесте слишком много несвязанного
#[test]
fn test_parser() {
    // Тестирует tokenize, parse, typecheck, codegen...
}
```

**Принцип 4: Тестируйте поведение, а не реализацию.** Рефакторинг внутренней реализации не должен
приводить к падению тестов. Если изменение одной строки реализации приводит к падению 10 тестов,
ваши тесты написаны неправильно.

Но здесь есть ключевое различие: **определение "поведения" исходит из спецификации, а не из текущего
поведения кода.** Если код изменил поведение (то есть ввёл новое поведение, не соответствующее
спецификации), тест должен упасть. Если это не так, ваши тесты — "подстраивающиеся под код" — они
пропускают баги.

```
Спецификация (language-spec.md / RFC)  ──определяет──►  Ожидаемое поведение  ──управляет──►  Тесты
                                                │
Текущий код  ──реализует──►  Фактическое поведение  ──сравнивается──►  Результат теста

Если фактическое поведение ≠ ожидаемого:
  Тест должен упасть (красный)  ──►  Исправить код  ──►  Тест проходит (зелёный)

Если фактическое поведение = ожидаемому (но реализация ужасна):
  Тест проходит  ──►  Рефакторинг реализации  ──►  Тест по-прежнему проходит  ← Вот что означает принцип 4
```

**Принцип 5: Не пишите тестовый код для отката/совместимости/активации определённых режимов.**
Тестовое окружение — это среда, которую вы полностью контролируете. Если вам нужен
`#[cfg(not(ci))]`, чтобы пропустить какой-то тест, это указывает на фундаментальную проблему в
дизайне теста.

### Определения терминов

| Термин                | Определение                                                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------- |
| Модульный тест        | Тестирует поведение отдельной функции или модуля, без зависимости от внешних систем            |
| Интеграционный тест   | Тестирует взаимодействие нескольких модулей через публичный API или интерфейс командной строки |
| Нагрузочный тест      | Измеряет производительность кода, выявляет регрессии производительности                        |
| Документационный тест | Исполняемые примеры кода, встроенные в комментарии документации                                |
| Property-тест         | Тест, проверяющий инварианты (свойства) на основе случайных входных данных                     |

### Связь со спецификациями коммитов

Все коммиты, связанные с тестами, должны использовать тип `:white_check_mark: test:`, согласно
[спецификации коммитов](./commit-convention.md).

```
:white_check_mark: test(parser): добавить тесты инфиксных выражений парсера Pratt
:white_check_mark: test(codegen): дополнить тесты генерации IR для switch
```

## Уровни тестирования корпусов yx и библиотек

Настоящие спецификации ограничивают **тестовый код на стороне Rust**. Тесты самого языка YaoXiang
(корпуса `.yx` и тесты библиотек) делятся на два уровня по объекту тестирования; дизайн системы и
контракты оценки относятся к RFC-036 (§7 Сборка сьютов / §8 Три уровня негативных тестов / §9
Многоуровневая система тестирования), а детали по написанию корпусов — к
`tests/yaoxiang/TEST_STANDARDS.md`:

- **Корпуса пригодности языка** (`tests/yaoxiang/`) — объект тестирования — сам язык; std
  используется только как инструмент утверждений. Внутри корпуса по уровню возникновения сбоя
  выделяют три категории оценки: тесты поведения / тесты отказа на этапе компиляции / тесты сбоя на
  этапе выполнения
- **Тесты библиотек** (идут вместе с библиотекой) — объект тестирования — публичный API-контракт
  библиотеки; тесты std на уровне yx расположены в `src/std/tests/`, тесты будущих пользовательских
  пакетов обнаруживаются внутри пакетов через `[tool.test]`

Формат заголовка файлов тестов `.yx`, директивы заголовка (`// expect:` / `// skip:` / `// mode:`,
RFC-036 §8.2) и соглашения об утверждениях определяются TEST_STANDARDS.md; разбор суждений
реализован в `src/util/test_markers.rs` (сторона Rust, подчиняется настоящим спецификациям), общий
для двух runner-ов.

## Спецификации модульных тестов

### Организация файлов

**Правило 1.1**: Каталог `tests/` модульных тестов должен находиться **на одном уровне** с `mod.rs`
тестируемого модуля. `tests/` не агрегируется вверх и не суммируется через уровни.

```
src/frontend/core/parser/
├── mod.rs              # #[cfg(test)] mod tests; — объявляет однородный tests/
├── ast.rs
├── pratt/
│   ├── mod.rs          # #[cfg(test)] mod tests; — собственные тесты pratt
│   └── tests/
│       ├── mod.rs
│       ├── led.rs
│       ├── nud.rs
│       └── precedence.rs
└── tests/              # тесты уровня модуля parser (не включают содержимое подмодуля pratt)
    ├── mod.rs
    ├── ast.rs
    ├── expressions.rs
    ├── error_recovery.rs
    └── parser_state.rs
```

Ключевой критерий: **`tests/` располагается в том каталоге, чей `mod.rs` должен объявить его с
помощью `#[cfg(test)] mod tests;`.**

**Дополнение к правилу 1.1: Запрещена агрегация вверх.** Тесты модуля-подкаталога должны размещаться
в собственном `tests/` этого подкаталога; их нельзя агрегировать в родительский `tests/`.

| Тип модуля                         | Расположение тестов           | Пример                                       |
| ---------------------------------- | ----------------------------- | -------------------------------------------- |
| Каталог-модуль (с `mod.rs`)        | `tests/` в этом каталоге      | `emitter/tests/`, `codes/tests/`             |
| Однофайловый модуль (только `.rs`) | `tests/` родительского модуля | `session.rs` → `diagnostic/tests/session.rs` |

```text
# ✅ Правильно: тесты каждого модуля-каталога независимы
src/util/diagnostic/
├── codes/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ собственные тесты codes
│       ├── mod.rs
│       └── codes.rs
├── emitter/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ собственные тесты emitter
│       ├── mod.rs
│       ├── text.rs
│       └── ansi.rs
└── tests/                  # ✅ уровень diagnostic (однофайловые модули)
    ├── mod.rs
    ├── session.rs
    ├── suggest.rs
    └── collect.rs

# ❌ Неправильно: агрегация тестов emitter и codes в diagnostic/tests/
src/util/diagnostic/
└── tests/
    ├── mod.rs              # ❌ вынуждены объявлять mod emitter; mod codes;
    ├── emitter/            # ❌ должны быть в emitter/tests/
    └── codes/              # ❌ должны быть в codes/tests/
```

#### Правила размещения тестов для однофайловых модулей и модулей-каталогов

**Ключевое различие**: форма организации модуля определяет расположение его тестов.

| Тип модуля              | Критерий                                         | Расположение тестов           | Пример                                        |
| ----------------------- | ------------------------------------------------ | ----------------------------- | --------------------------------------------- |
| **Модуль-каталог**      | Имеет отдельный каталог и `mod.rs`               | `tests/` в этом каталоге      | `inference/tests/`                            |
| **Однофайловый модуль** | Имеет только файл `.rs`, без отдельного каталога | `tests/` родительского модуля | `overload.rs` → `typecheck/tests/overload.rs` |

**Подробное объяснение**:

```
src/frontend/core/typecheck/
├── mod.rs                          # mod.rs модуля typecheck
├── checker.rs                      # однофайловый модуль
├── environment.rs                  # однофайловый модуль
├── overload.rs                     # однофайловый модуль
├── type_eval.rs                    # однофайловый модуль
├── dead_code.rs                    # однофайловый модуль
├── spawn_placement.rs              # однофайловый модуль
├── signature.rs                    # однофайловый модуль
├── types.rs                        # однофайловый модуль
│
├── tests/                          # ✅ каталог тестов typecheck
│   ├── mod.rs                      # объявляет тесты однофайловых модулей
│   ├── checker.rs                  # тесты checker.rs
│   ├── environment.rs              # тесты environment.rs
│   ├── overload.rs                 # тесты overload.rs (однофайловый модуль)
│   ├── type_eval.rs                # тесты type_eval.rs
│   ├── dead_code.rs                # тесты dead_code.rs
│   ├── spawn_placement.rs          # тесты spawn_placement.rs
│   ├── signature.rs                # тесты signature.rs
│   └── types.rs                    # тесты types.rs
│
├── inference/                      # модуль-каталог (с mod.rs)
│   ├── mod.rs                      # #[cfg(test)] mod tests; — объявляет однородный tests/
│   ├── expressions.rs
│   ├── statements.rs
│   ├── patterns.rs
│   ├── bounds.rs
│   ├── subtyping.rs
│   ├── generics.rs
│   ├── compatibility.rs
│   ├── scope.rs
│   ├── assignment.rs
│   └── tests/                      # ✅ каталог тестов inference
│       ├── mod.rs
│       ├── expressions.rs          # тесты expressions.rs
│       ├── statements.rs           # тесты statements.rs
│       └── ...
│
└── traits/                         # удалён (логика объединена в types/trait_data.rs)
```

**Почему тесты однофайлового модуля располагаются в родительском `tests/`?**

Потому что однофайловый модуль (например, `overload.rs`) не имеет собственного `mod.rs`, и в нём
нельзя объявить `#[cfg(test)] mod tests;`. Согласно системе модулей Rust, тестовые файлы должны быть
объявлены каким-либо `mod.rs` для компиляции. Поэтому тесты однофайлового модуля могут быть
объявлены только `mod.rs` родительского модуля и расположены в родительском `tests/`.

**Алгоритм принятия решения**:

```
Встретился модуль, нужно определить, куда поместить тесты?
│
├── Модуль — каталог (есть mod.rs)?
│   └── Да → создать tests/ в этом каталоге, объявить через mod.rs каталога
│
├── Модуль — однофайловый (только .rs)?
│   └── Да → тесты помещаются в tests/ родительского модуля, объявляются через mod.rs родителя
│
└── Не уверены?
    └── Проверьте наличие отдельного каталога и mod.rs
```

**Частые ошибки**:

```
# ❌ Ошибка 1: создание отдельного каталога tests/ для однофайлового модуля
src/frontend/core/typecheck/
├── overload.rs
└── overload/                       # ❌ нельзя создавать каталог для однофайлового модуля
    └── tests/
        └── overload.rs

# ❌ Ошибка 2: объявление #[cfg(test)] mod tests; внутри однофайлового модуля
# overload.rs
#[cfg(test)]                        # ❌ однофайловый модуль не может так объявлять
mod tests;                          # потому что нет каталога overload/tests/

# ✅ Правильно: тесты помещаются в родительский tests/
src/frontend/core/typecheck/
├── overload.rs                     # исходный файл
└── tests/
    └── overload.rs                 # тестовый файл, объявленный через typecheck/mod.rs
```

⚠️ **Антипаттерн — не делайте так:**

```
# ❌ Неправильно: тесты подмодулей собраны на родительском уровне
src/frontend/core/types/
├── mod.rs              # должен объявлять только base и computation
├── base/
│   ├── mod.rs
│   └── var.rs
└── tests/              # ❌ родительский tests/ содержит тесты подмодулей
    ├── mod.rs          # ❌ вынуждены объявлять mod base; mod computation;
    ├── base/           # ❌ это должно быть в base/tests/
    │   └── var.rs
    └── computation/    # ❌ это должно быть в computation/tests/
        └── ...
```

```
# ✅ Правильный подход: тесты каждого модуля независимы
src/frontend/core/types/
├── mod.rs              # объявляет только pub mod base; pub mod computation;
├── base/
│   ├── mod.rs          # #[cfg(test)] mod tests; — объявляет однородный tests/
│   ├── var.rs
│   └── tests/
│       ├── mod.rs
│       └── var.rs
└── computation/
    ├── mod.rs          # #[cfg(test)] mod tests; — объявляет однородный tests/
    ├── operations.rs
    └── tests/
        ├── mod.rs
        └── operations.rs
```

**Почему нельзя агрегировать вверх?** Потому что система модулей Rust требует, чтобы
`#[cfg(test)] mod tests;` определял компиляцию тестовых файлов в точке объявления. Если
`types/mod.rs` объявляет `mod tests;`, то содержимое `types/tests/` является приватным содержимым
модуля `types` — оно не должно вторгаться на территорию `base` или `computation`. Тесты каждого
модуля должны быть деталями его внутренней реализации, а не родительского модуля. Это правило также
применимо к рефакторингу модулей: когда вы разделяете `types` на `base` и `computation`, тесты
должны следовать за новыми границами модулей, а не оставаться на прежнем месте. **Каталог тестов не
зеркалит структуру исходного кода, а следует за границами модулей.**

**Правило 1.2**: `tests/mod.rs` отвечает только за объявление модулей и re-export; в нём не
размещаются тестовые функции.

```rust
//! Тесты ядра парсера — зеркалит src/frontend/core/parser/
//!
//! Тесты для ast.rs, parser_state.rs и парсинга выражений/интеграции.

mod ast;
mod error_recovery;
mod expressions;
mod integration;
mod parser_state;
```

**Правило 1.3**: Каждый тестовый файл соответствует только одному исходному файлу. Не допускается
смешивание тестов нескольких исходных модулей в одном файле.

**Правило 1.4**: Объявление тестов должно использовать файловую форму `mod tests;` (с точкой с
запятой), указывающую на однородный каталог `tests/`. **Запрещена inline-форма `mod tests { ... }`,
при которой тестовый код пишется непосредственно в исходном файле.**

```rust
// ✅ Правильно — файловая форма объявления, тестовый код в отдельных файлах
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests;

// 🔴 Запрещено — inline-форма, тестовый код паразитирует в исходном файле
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_something() {
        // Тестовый код не должен находиться в исходном файле
    }
}
```

**Почему запрещён inline?**

1. Единственная ответственность исходного файла: исходный файл содержит только реализацию, тестовый
   файл — только тесты. Смешивание заставляет прокручивать к концу файла при правке тестов и
   пропускать тесты при правке реализации.
2. Чёткие границы модулей: каталог `tests/` — это физическая граница, сразу видно, какие модули
   имеют тесты, а какие нет.
3. Безопасность рефакторинга: при разделении модуля каталог `tests/` идёт вместе с ним; inline-тесты
   нужно вручную извлекать из исходных файлов.
4. Ревью кода: в PR diff изменения исходного кода и тестов находятся в разных файлах и не
   смешиваются.

### Спецификации объявления модулей

**Правило 2.1**: В верхней части всех тестовых файлов должен быть документационный комментарий
уровня модуля `//!`, описывающий источник спецификации, которую покрывают тесты (номер раздела
спецификации языка + номер RFC). Если какой-то тест не ссылается ни на один раздел спецификации, это
означает, что у кода нет спецификационного обоснования — он не должен существовать.

```rust
//! Тесты литералов — основаны на спецификации языка §2.6
//!
//! §2.6.1: Целые числа Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: Числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: Строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: F-String интерполяция
```

**Почему необходимо ссылаться на спецификацию?** Потому что ожидаемые значения тестов берутся из
спецификации, а не из "выходных данных текущего кода". Если однажды код изменит выходные данные и
тесты будут обновлены следом, тесты ничего не защищают. Только привязанные к спецификации тесты
могут отличить "намеренное breaking change" от "непреднамеренной регрессии".

**Правило 2.2**: Импорты `use` в тестовом модуле должны быть точными до конкретных типов/функций;
запрещён глобальный импорт `use super::*`.

```rust
// 🟢 Хорошо — точный импорт
use crate::frontend::core::lexer::{tokenize, TokenKind};
use crate::frontend::core::parser::{ParserState, ParseError};

// 🔴 Мусор — непонятно, что вы тестируете
use super::*;
```

### Спецификации именования

**Правило 3.1**: Формат имени тестовой функции: `test_<что>_<сценарий>`, полностью в нижнем регистре
с подчёркиваниями.

```rust
#[test]
fn test_tokenize_empty_string() { /* ... */ }
#[test]
fn test_parse_int_overflow() { /* ... */ }
#[test]
fn test_typecheck_fn_return_mismatch() { /* ... */ }
```

**Правило 3.2**: Имя тестовой функции должно быть самодокументируемым. Прочитав имя, должно быть
понятно, что тестируется и что ожидается. Запрещено именование с числовыми индексами.

```rust
// 🟢 Хорошо
fn test_skip_semicolon_success() { /* ... */ }
fn test_skip_semicolon_failure_when_identifier() { /* ... */ }

// 🔴 Мусор — совершенно непонятно, что тестируется
fn test_skip_1() { /* ... */ }
fn test_skip_2() { /* ... */ }
```

**Правило 3.3**: Вспомогательные функции не требуют префикса `test_`; они должны описывать своё
назначение глаголом или существительным.

```rust
fn parse_expr(source: &str) -> Expr { /* ... */ }
fn tokenize_single(source: &str) -> Token { /* ... */ }
fn setup_parser_with_tokens(tokens: &[Token]) -> ParserState { /* ... */ }
```

### Спецификации структуры тестов (Arrange-Act-Assert)

**Правило 4.1**: Каждая тестовая функция должна следовать трёхчастной структуре: подготовка
(Arrange) → выполнение (Act) → утверждение (Assert), три части разделяются пустыми строками.

```rust
#[test]
fn test_parse_binary_addition() {
    // Arrange
    let source = "1 + 2";

    // Act
    let expr = parse_expr(source);

    // Assert
    assert!(matches!(expr, Expr::Binary { op: BinOp::Add, .. }));
}
```

**Правило 4.2**: Простые тесты (один вызов + одно утверждение) могут не содержать
комментариев-разделителей частей, но не должны превышать 5 строк логического кода. Тесты длиннее 5
строк должны явно обозначать три части.

### Спецификации вспомогательных функций

**Правило 5.1**: Логика setup, повторяющаяся 3 раза и более, должна быть вынесена во вспомогательную
функцию.

```rust
// 🟢 Хорошо — общий setup вынесен
fn with_state<F>(source: &str, mut f: F)
where
    F: FnMut(&mut ParserState<'_>),
{
    let tokens = tokenize(source).unwrap();
    let mut state = ParserState::new(&tokens);
    f(&mut state);
}

#[test]
fn test_current_returns_first_token() {
    with_state("42", |state| {
        let tok = state.current();
        assert_eq!(&tok.unwrap().kind, &TokenKind::IntLiteral(42));
    });
}
```

**Правило 5.2**: `unwrap()` / `expect()` во вспомогательных функциях должны при panic выводить
достаточно контекста. Внутри тела тестовой функции (`#[test] fn ...`) можно использовать `unwrap()`
напрямую — при сбое Rust автоматически печатает номер строки; но при сбое во вспомогательной функции
номер строки указывает на определение вспомогательной функции, и контекст вызова не виден.

```rust
// 🟢 Хорошо — при сбое вспомогательной функции печатается содержимое исходного кода
fn run_ok(source: &str) {
    run(source).unwrap_or_else(|e| panic!("Execution failed:\nSource:\n{}\nError:\n{:?}", source, e));
}

// 🔴 Мусор — при сбое не видно, какой исходный файл вызвал проблему
fn run_ok(source: &str) {
    run(source).unwrap();
}
```

**Правило 5.3**: Вспомогательные функции размещаются в верхней части тестового файла, сразу после
импортов `use`. Если они разделяются между несколькими тестовыми модулями, их размещают в
`tests/mod.rs` с экспортом через `pub(crate)`.

### Стиль утверждений

**Правило 6.1**: Для сопоставления с вариантами перечисления предпочтительно использовать
`assert!(matches!(...))`; нельзя использовать `if let` + `panic!`.

```rust
// 🟢 Хорошо
assert!(matches!(tokens[0].kind, TokenKind::IntLiteral(42)));

// 🔴 Мусор
if let TokenKind::IntLiteral(v) = tokens[0].kind {
    assert_eq!(v, 42);
} else {
    panic!("Expected IntLiteral");
}
```

**Правило 6.2**: Для точного сравнения значений используйте `assert_eq!`, для булевых утверждений —
`assert!`. Запрещено использовать `assert!(a == b)` вместо `assert_eq!(a, b)`.

**Правило 6.3**: Все утверждения должны содержать собственные сообщения об ошибках, если только само
утверждение не описывает причину сбоя полностью.

```rust
// 🟢 Хорошо — при сбое можно быстро локализовать проблему
assert!(
    state.infix_info().is_some(),
    "infix_info should handle '{op}'"
);

// 🟢 Хорошо — при сбое assert_eq! автоматически печатает разницу значений, дополнительное сообщение не нужно
assert_eq!(error_count, 0);

// 🔴 Мусор — при сбое видно только "assertion failed"
assert!(state.infix_info().is_some());
```

**Правило 6.4**: Порядок аргументов утверждения должен быть `assert_eq!(actual, expected)` —
фактическое значение первым, ожидаемое — вторым.

### Список антипаттернов

Ниже приведены запрещённые приёмы и их замены:

| Антипаттерн                                         | Проблема                                                                    | Замена                                                                                    |
| --------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `#[cfg(test)] mod tests { ... }` inline-тесты       | Раздувание исходных файлов, размытие границ модулей, трудности рефакторинга | Тестовый код в отдельном каталоге `tests/`, объявлен через `mod tests;` (см. правило 1.4) |
| Тест подстраивается под ошибочное поведение кода    | Маскирует отклонения от спецификации, легализует баги                       | Исправлять код согласно спецификации, тесты оставлять неизменными                         |
| Вывод ожидаемых значений из вывода кода             | Тест превращается в "диктофон текущей реализации"                           | Выводить ожидаемые значения из спецификации                                               |
| Постоянная пометка `#[ignore]`                      | Скрывает гниющие тесты                                                      | Исправить или удалить                                                                     |
| Отладочный вывод через `println!`                   | Загрязняет вывод тестов                                                     | Использовать `assert!` с явным утверждением                                               |
| `thread::sleep`                                     | Случайные сбои + медленно                                                   | Использовать механизмы синхронизации или моки                                             |
| Операции с реальной файловой системой в тестах      | Медленно и неповторяемо                                                     | Использовать `tempfile`                                                                   |
| Зависимость от порядка выполнения тестов            | Случайные сбои                                                              | Независимый setup в каждом тесте                                                          |
| Тестовая функция длиннее 30 строк логики            | Никто не сможет разобраться                                                 | Разделить тест или использовать вспомогательные функции                                   |
| `unwrap()` во вспомогательной функции без контекста | Сложно локализовать                                                         | Использовать `expect("why")` или собственный panic (см. правило 5.2)                      |
| Copy-paste одинакового setup более 3 раз            | Высокая стоимость изменений                                                 | Вынести во вспомогательную функцию                                                        |

## Спецификации интеграционных тестов

### Организация тестов

**Правило 7.1**: Интеграционные тесты располагаются в каталоге `tests/` корня проекта. Входной файл
`tests/integration.rs` использует атрибут `#[path]` для подключения подмодулей.

```rust
// tests/integration.rs
#[path = "integration/backends.rs"]
mod backends;
#[path = "integration/codegen.rs"]
mod codegen;
#[path = "integration/execution.rs"]
mod execution;
```

**Правило 7.2**: Каждый файл `tests/integration/*.rs` соответствует одной теме тестирования (бэкенды
компилятора, кодогенерация, исполнитель и т.д.); смешивание запрещено.

**Правило 7.3**: Интеграционные тесты должны тестировать через публичный API проекта. Запрещено
напрямую ссылаться на внутренние модули `crate::` в интеграционных тестах. Используйте публичный
путь `yaoxiang::`.

```rust
// 🟢 Хорошо — через публичный API
use yaoxiang::run;

// 🔴 Мусор — обход границы публичного API
use yaoxiang::middle::codegen::bytecode::BytecodeFile;
```

### Управление тестовыми данными

**Правило 8.1**: Интеграционные тесты предпочитают встроенные строки исходного кода. Внешние файлы
fixture (размещаются в `tests/fixtures/`) используются только когда исходный код превышает 30 строк.

```rust
#[test]
fn test_fibonacci() {
    run_ok(
        r#"
        main: () -> Void = {
            mut a = 0
            mut b = 1
            while a < 100 {
                mut next = a + b
                a = b
                b = next
            }
        }
        "#,
    );
}
```

**Правило 8.2**: Файлы fixture должны иметь расширение `.yx`; имя файла описывает назначение теста.

### Принципы E2E покрытия

**Правило 9.1**: Интеграционные тесты для каждой возможности языка должны покрывать три пути:

| Путь       | Описание                                                                            |
| ---------- | ----------------------------------------------------------------------------------- |
| Happy path | Корректный ввод даёт ожидаемый вывод                                                |
| Error path | Некорректный ввод даёт понятное сообщение об ошибке (не panic)                      |
| Boundary   | Граничные значения (пустой ввод, максимальные значения, предел глубины вложенности) |

**Правило 9.2**: Интеграционные тесты не должны зависеть от сети, переменных окружения системы или
внешних сервисов.

## Спецификации нагрузочных тестов

### Спецификации использования Criterion.rs

**Правило 10.1**: Нагрузочные тесты единообразно располагаются в каталоге `benches/`, входной файл —
`benches/lib.rs`. Разделение по темам — по файлам.

```
benches/
├── lib.rs              # вход, определяет criterion_group/criterion_main
├── lang_compare/
│   └── fibonacci.rs    # кросс-языковые сравнительные тесты
├── parser.rs           # нагрузочные тесты парсера
└── codegen.rs          # нагрузочные тесты кодогенерации
```

**Правило 10.2**: Каждая функция бенчмарка должна содержать документационный комментарий уровня
модуля `//!` с описанием цели тестирования и измеряемых метрик.

```rust
//! Нагрузочные тесты производительности интерпретатора YaoXiang
//!
//! Измеряемая метрика: время одной итерации (wall time)
//! Базовая линия: нативная реализация на Rust
```

### Предотвращение оптимизаций компилятора

**Правило 11.1**: Выходные данные всех нагрузочных тестов должны быть обёрнуты в
`criterion::black_box`, чтобы компилятор не мог оптимизировать их удаление.

```rust
use criterion::{black_box, Criterion};

fn bench_parse(c: &mut Criterion) {
    c.bench_function("parse_fib", |b| {
        b.iter(|| {
            let result = parse(black_box(FIB_SOURCE));
            black_box(result)
        })
    });
}
```

**Правило 11.2**: Входные данные нагрузочных тестов должны быть `const` или `lazy_static`; запрещено
динамически генерировать их внутри замыкания `iter` — иначе измеряется суммарное время генерации
данных и тестируемой логики.

### Группировка и именование бенчмарков

**Правило 12.1**: Формат имени нагрузочного теста: `<тестируемый модуль>_<сценарий>`, полностью в
нижнем регистре с подчёркиваниями. Соответствует правилам именования модульных тестов.

**Правило 12.2**: Необходимо использовать `criterion_group!` для логической группировки связанных
бенчмарков. Запрещено размещать все бенчмарки в одной группе.

```rust
criterion_group!(parser, bench_parse_expr, bench_parse_stmt);
criterion_group!(codegen, bench_codegen_module, bench_codegen_switch);
criterion_main!(parser, codegen);
```

## Спецификации документационных тестов

### Сценарии использования

**Правило 13.1**: Все `pub` функции, типы и методы должны содержать в комментариях документации как
минимум один запускаемый пример кода. Этот пример выполняется через `cargo test --doc`.

````rust
/// Разбивает строку исходного кода на последовательность токенов.
///
/// ```
/// use yaoxiang::frontend::core::lexer::tokenize;
///
/// let tokens = tokenize("42").unwrap();
/// assert_eq!(tokens.len(), 2); // IntLiteral + Eof
/// ```
pub fn tokenize(source: &str) -> Result<Vec<Token>, LexError> {
    // ...
}
````

**Правило 13.2**: Примеры кода в документационных тестах должны компилироваться и иметь успешные
утверждения. Не допускаются примеры с пометкой `ignore`, если только они не демонстрируют ошибку
этапа компиляции.

````rust
/// ```ignore
/// // Демонстрация ошибки компиляции — допустимо ignore
/// let x: int = "string";
/// ```
````

### Требования к покрытию

**Правило 14.1**: Документационные тесты должны покрывать только happy path API. Граничные случаи и
пути ошибок покрываются модульными тестами.

**Правило 14.2**: Примеры кода в документационных тестах должны быть краткими — не более 10 строк.
Если пример требует более длинного контекста, это указывает на проблему в дизайне API.

## Спецификации property-тестов

### Сценарии использования

**Правило 15.1**: В следующих сценариях необходимо использовать property-тесты (proptest или
quickcheck) вместо ручного написания множества граничных случаев:

| Сценарий                                    | Пример                                 |
| ------------------------------------------- | -------------------------------------- |
| Round-trip парсера                          | `parse(pretty_print(ast)) == ast`      |
| Сериализация/десериализация                 | `deserialize(serialize(data)) == data` |
| Тождества математических операций           | `a + b == b + a`                       |
| Оптимизации компилятора не меняют семантику | `eval(code) == eval(optimize(code))`   |

**Правило 15.2**: В качестве основного фреймворка property-тестов используется `proptest` (уже
объявлен в `dev-dependencies` файла `Cargo.toml`).

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn test_roundtrip_serialize_deserialize(value: i64) {
        let serialized = serialize(&value);
        let deserialized: i64 = deserialize(&serialized).unwrap();
        prop_assert_eq!(deserialized, value);
    }
}
```

### Принципы определения свойств

**Правило 16.1**: Каждый property-тест должен иметь явное объявление свойства — в комментарии
необходимо указать проверяемый инвариант.

```rust
// Свойство: любой целочисленный литерал после tokenize → tokens_to_string даёт то же значение
proptest! {
    #[test]
    fn test_int_literal_roundtrip(n in any::<i64>()) {
        let source = n.to_string();
        let tokens = tokenize(&source).unwrap();
        // ...
    }
}
```

**Правило 16.2**: Если property-тест обнаруживает сбой, необходимо использовать механизм регрессий
`proptest` — добавить неудачные входные данные в каталог `proptest-regressions/`, а не заменять их
вручную написанным обычным тестом.

## Требования к покрытию

### Цели покрытия для нового кода

**Правило 17.1**: Требования к покрытию тестами для нового кода:

| Тип кода                                               | Покрытие строк | Покрытие ветвей |
| ------------------------------------------------------ | -------------- | --------------- |
| Основные модули компилятора (frontend/middle/backends) | ≥ 85%          | ≥ 80%           |
| Модули утилит/помощников (util)                        | ≥ 75%          | ≥ 70%           |
| Модули среды выполнения (vm/runtime)                   | ≥ 80%          | ≥ 75%           |
| Стандартная библиотека (std)                           | ≥ 75%          | ≥ 70%           |
| Обработка ошибок и диагностика                         | ≥ 90%          | ≥ 85%           |

**Правило 17.2**: Пути обработки ошибок (все ветки `Err`) должны быть покрыты на 100%. Сообщения об
ошибках, которые видит пользователь, должны быть проверены тестами.

### Контрольный список для ревью PR

**Правило 18.1**: Перед отправкой PR автор должен самостоятельно проверить следующие пункты:

- [ ] `cargo test` проходит полностью
- [ ] `cargo test --doc` проходит полностью
- [ ] `cargo bench` не показывает регрессий производительности (если затронуты горячие пути)
- [ ] Новый код соответствует целям по покрытию
- [ ] Именование тестов соответствует спецификациям именования
- [ ] Каждый тестовый файл объявляет соответствующий раздел спецификации (правило 2.1)
- [ ] Ожидаемые значения тестов берутся из определений спецификации, а не из "выходных данных
      текущего кода"
- [ ] Нет тестов с пометкой `#[ignore]` (если нет комментария с номером issue)
- [ ] Нет лишних `unwrap()` (следует использовать `expect` или собственные сообщения panic)
- [ ] Сообщение коммита использует тип `:white_check_mark: test:`
- [ ] **Ожидаемые значения тестов не были изменены из-за "несоответствия поведения кода
      спецификации" — изменения вносятся в код, а не в тесты**
- [ ] **Нет inline-тестов** (`#[cfg(test)] mod tests { ... }` необходимо заменить на `mod tests;` +
      отдельный файл, см. правило 1.4)

**Правило 18.2**: Ревьюер должен отклонить PR, содержащий следующие проблемы:

- Только тесты happy path, отсутствуют пути ошибок
- Использование `thread::sleep` в тестах или зависимость от порядка выполнения
- Скопированный тестовый код более 3 раз без вынесения во вспомогательную функцию
- Имена тестов не соответствуют спецификациям именования
- Существуют постоянно помеченные `#[ignore]` тесты
- **Тест подстраивается под ошибочное поведение кода** (когда код не соответствует спецификации,
  изменяется тест, а не код)
- **Тест не объявляет соответствующий раздел спецификации** (см. правило 2.1)
- **Ожидаемые значения тестов берутся из вывода кода, а не из определений спецификации** (выведенные
  задним числом тесты равносильны отсутствию тестов)
- **Существуют inline-тесты** (`#[cfg(test)] mod tests { ... }` вместо `mod tests;` + отдельный
  файл, см. правило 1.4)
- Тесты проверяют только "не было panic", не утверждая конкретного поведения
- Удаление падающих тестов, выявляющих баги в коде (вместо исправления кода, чтобы увидеть их
  зелёными)

## Приложения

### A. Шпаргалка по командам тестирования

```bash
# Запустить все тесты
cargo test

# Запустить только модульные тесты
cargo test --lib

# Запустить только интеграционные тесты
cargo test --test integration

# Запустить только документационные тесты
cargo test --doc

# Запустить конкретный тест (фильтр по имени)
cargo test test_parse_expr

# Запустить нагрузочные тесты
cargo bench

# Показать вывод тестов (по умолчанию stdout скрыт)
cargo test -- --nocapture

# Однопоточное выполнение (для отладки проблем конкурентности)
cargo test -- --test-threads=1

# Сгенерировать отчёт о покрытии (требуется cargo-llvm-cov)
cargo llvm-cov --html
```

### B. Шаблон сообщения коммита

Коммиты, связанные с тестами, должны следовать следующему шаблону:

```
:white_check_mark: test(<scope>): <краткое описание>

<опционально: список покрытых сценариев>
```

Пример:

```
:white_check_mark: test(parser): добавить тесты инфиксных операторов парсера Pratt

Покрытые сценарии:
- Приоритет арифметических операторов (+, -, *, /, %)
- Цепочки операторов сравнения (1 < x < 10)
- Короткое замыкание логических операторов
- Правосторонняя ассоциативность оператора присваивания
```

### C. Чек-лист для новых тестовых файлов

При создании нового тестового модуля убедитесь в наличии следующих файлов:

```
# Добавление тестов в src/<module>/
src/<module>/tests/
├── mod.rs          # объявление модуля + общие вспомогательные функции
└── <subject>.rs    # тестовый файл, названный по тестируемому исходному файлу

# Добавление интеграционных тестов в tests/
tests/
├── integration.rs   # обновление: добавить объявление #[path]
└── integration/
    └── <topic>.rs   # новый тестовый файл
```
