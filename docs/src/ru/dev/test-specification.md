## Общие положения

### Область применения

Настоящие правила распространяются на весь код тестов на Rust в проекте YaoXiang:

| Тип теста     | Расположение              | Фреймворк                        |
| ------------- | ------------------------- | ---------------------------------|
| Модульные тесты | `src/<module>/tests/`     | `#[test]` + `#[cfg(test)]`        |
| Интеграционные тесты | `tests/`            | `#[test]`                         |
| Бенчмарки      | `benches/`                | Criterion.rs                      |
| Документные тесты | API документация       | `cargo test --doc`                |
| Property-based тесты | Любое место        | proptest / quickcheck             |

### Ключевые принципы

**Принцип 0: Единственным авторитетным источником для тестов является спецификация, а не код.**
Это важнейший принцип данного документа. Тесты проверяют, соответствует ли код спецификации, а не то, «работает ли код с текущей реализацией». Когда тест обнаруживает расхождение между поведением кода и спецификацией, **исправляется код, тест не изменяется никогда**.

Файлы спецификаций расположены в:

- `docs/src/design/language-spec.md` —— Ядро языка, спецификация
- `docs/src/design/rfc/accepted/` —— Принятые RFC документы дизайна

В начале каждого файла тестов должна быть указана соответствующая глава спецификации (см. правило 2.1). Любой разработчик должен иметь возможность взять спецификацию, сверить её с тестами и убедиться в корректности реализации. Наоборот: если фрагмент кода не имеет соответствующего описания в спецификации, его не должно существовать, и он не должен тестироваться.

```rust
// 🟢 Хорошо——Тест напрямую ссылается на спецификацию, проверяя соответствие кода
//! Тесты литералов — на основе спецификации языка §2.6
//!
//! §2.6.1: Целые Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: Числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: Строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: Интерполяция F-String

#[test]
fn test_decimal_literal_parsing() {
    // Спецификация §2.6.1: Decimal ::= [0-9][0-9_]*
    let result = parse_literal("42").unwrap();
    assert_eq!(result, Literal::Int(42));
}

// 🔴 Мусор——Тест подстраивается под поведение текущего кода, а не под спецификацию
#[test]
fn test_literal_1() {
    // Неизвестно, к какой главе спецификации относится этот код
    // Если parse_literal вернёт неправильное значение, тест всё равно «пройдёт»
    // Потому что он лишь проверяет, что функция не паникует
    let result = parse_literal("42");
    assert!(result.is_ok());
}
```

**Ситуация**: Вы написали тест и обнаружили, что поведение кода не соответствует спецификации. У вас есть два варианта:

| Неправильный подход                | Правильный подход                |
| ---------------------------------- | ----------------------------------|
| Изменить тест, чтобы он «проходил» | Изменить код, чтобы он соответствовал спецификации |
| Добавить `#[ignore]` в тест        | Немедленно исправить реализацию   |
| Добавить в тест условные ветки, подстраивающиеся под код | Удалить ветки, чтобы тест явно показал проблему |

Запомните: **Красный = код неправильный, а не тест.** (Если только в вашем тесте нет бага — это другое дело.)

**Принцип 1: Тесты — это документация.** Любой разработчик должен понять поведение тестируемого кода, читая только тесты, без дополнительных комментариев или внешней документации.

```rust
// 🟢 Хорошо——Имя теста говорит, что тестируется и какой результат ожидается
#[test]
fn test_tokenize_empty_input_returns_eof() {
    let tokens = tokenize("").unwrap();
    assert_eq!(tokens.len(), 1);
    assert!(matches!(tokens[0].kind, TokenKind::Eof));
}

// 🔴 Мусор——Непонятно, что именно тестируется
#[test]
fn test_tokenize_1() {
    let tokens = tokenize("").unwrap();
    assert!(tokens.len() > 0);
}
```

**Принцип 2: Нулевая терпимость к случайным сбоям.**
Тесты должны выполняться повторяемо в любом окружении. Тесты, зависящие от случайных чисел, системного времени или порядка планирования потоков, должны использовать фиксированные seed-значения или mock-объекты.

**Принцип 3: Один тест — одна проверка.** Если в имени теста нужно использовать «и» для соединения нескольких действий, разделите их на несколько тестов.

```rust
// 🟢 Хорошо——Каждый тест проверяет только один сценарий
#[test]
fn test_parse_int_positive() { /* ... */ }
#[test]
fn test_parse_int_zero() { /* ... */ }

// 🔴 Мусор——В одном тесте слишком много разного
#[test]
fn test_parser() {
    // Тестируем tokenize, parse, typecheck, codegen...
}
```

**Принцип 4: Тестируем поведение, а не реализацию.**
Рефакторинг внутренней реализации не должен приводить к падению тестов. Если изменив одну строку реализации, у вас падает 10 тестов — тесты написаны неправильно.

Но здесь важное уточнение: **определение «поведения» берётся из спецификации, а не из текущего поведения кода.**
Если код изменил поведение (то есть появилось новое поведение, не соответствующее спецификации), тесты обязаны падать. Если вы не можете этого добиться — ваши тесты «подстраиваются под код» — они пропускают баги.

```
Спецификация (language-spec.md / RFC)  ──определяет──►  Ожидаемое поведение  ──управляет──►  Тесты
                                                          │
Текущий код  ──реализует──►  Фактическое поведение  ──сравнивается──►  Результат теста

Если фактическое ≠ ожидаемое:
  Тест должен упасть (красный)  ──►  Исправляем код  ──►  Тест проходит (зелёный)

Если фактическое = ожидаемое (но реализация плохая):
  Тест проходит  ──►  Рефакторим реализацию  ──►  Тест всё ещё проходит  ← Вот смысл принципа 4
```

**Принцип 5: Не писать fallback/совместимостный/условный тестовый код.** Тестовое окружение — это среда, которую вы полностью контролируете. Если вам нужен
`#[cfg(not(ci))]` для пропуска теста — у теста фундаментальная проблема в дизайне.

### Определения терминов

| Термин            | Определение                                                    |
| ----------------- | -------------------------------------------------------------- |
| Модульный тест    | Тестирование отдельной функции или модуля, без внешних зависимостей |
| Интеграционный тест | Тестирование взаимодействия нескольких модулей через публичный API или командную строку |
| Бенчмарк          | Измерение производительности кода, обнаружение регрессий       |
| Документный тест  | Исполняемые примеры кода, встроенные в документацию           |
| Property-based тест | Тестирование инвариантов (properties) на случайных входных данных |

### Связь с правилами коммитов

Все коммиты, связанные с тестами, должны использовать тип `:white_check_mark: test:`, согласно [правилам коммитов](./commit-convention.md).

```
:white_check_mark: test(parser): добавить тесты инфиксных выражений для Pratt-парсера
:white_check_mark: test(codegen): дополнить тесты генерации IR для switch
```

## Уровни тестирования yx корпусов и библиотек

Настоящие правила ограничивают **код тестов на стороне Rust**. Тесты для языка YaoXiang (`.yx` корпуса и тесты библиотек) делятся на два уровня в зависимости от объекта тестирования: архитектурный дизайн и контракт проверки описаны в RFC-036 (§7 сборник наборов / §8 трёхуровневый негативный / §9 многоуровневая система тестирования), а правила написания корпусов — в `tests/yaoxiang/TEST_STANDARDS.md`:

- **Корпуса проверки доступности языка** (`tests/yaoxiang/`) —— объектом тестирования является сам язык; std используется только как инструмент для проверок.
  Внутри корпуса три типа проверок по уровню возникновения сбоя: behavioral тесты / compile-time rejection тесты / runtime failure тесты
- **Тесты библиотек** (вместе с библиотекой) —— объектом тестирования является публичный API контракт библиотеки; тесты std уровня yx расположены в
  `src/std/tests/`, будущие тесты пользовательских пакетов — в пакете, найденные через `[tool.test]`

Формат заголовков файлов `.yx` тестов, директивы заголовка (`// expect:` / `// skip:` / `// mode:`,
RFC-036 §8.2) и соглашения по断言ам соответствуют TEST_STANDARDS.md; разбор маркеров реализован в общем для обоих runner'ов `src/util/test_markers.rs` (сторона Rust, подчиняется настоящим правилам).

## Правила модульных тестов

### Организация файлов

**Правило 1.1**: Каталог `tests/` для модульных тестов **обязательно** должен располагаться на одном уровне с `mod.rs` тестируемого модуля. `tests/`
не агрегируется вверх и не суммируется через уровни.

```
src/frontend/core/parser/
├── mod.rs              # #[cfg(test)] mod tests; ——объявляет tests/ на своём уровне
├── ast.rs
├── pratt/
│   ├── mod.rs          # #[cfg(test)] mod tests; ——тесты pratt'а в его каталоге
│   └── tests/
│       ├── mod.rs
│       ├── led.rs
│       ├── nud.rs
│       └── precedence.rs
└── tests/              # Тесты уровня модуля parser (не включают подмодули pratt)
    ├── mod.rs
    ├── ast.rs
    ├── expressions.rs
    ├── error_recovery.rs
    └── parser_state.rs
```

Ключевой критерий: **в каком каталоге находится `tests/`, в том же каталоге `mod.rs` должен объявить `#[cfg(test)] mod tests;`.**

**Правило 1.1 Дополнение: запрещено агрегирование вверх.** Тесты подкаталогов модулей должны располагаться в собственном `tests/` этого подкаталога, не агрегироваться в родительский
`tests/`.

| Тип модуля                   | Расположение тестов          | Пример                                       |
| ---------------------------- | ---------------------------- | -------------------------------------------- |
| Каталожный модуль (с `mod.rs`)  | `tests/` внутри каталога     | `emitter/tests/`, `codes/tests/`             |
| Однофайловый модуль (только `.rs`) | `tests/` родительского модуля | `session.rs` → `diagnostic/tests/session.rs` |

```text
# ✅ Правильно: тесты каждого каталожного модуля независимы
src/util/diagnostic/
├── codes/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ тесты codes
│       ├── mod.rs
│       └── codes.rs
├── emitter/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ тесты emitter
│       ├── mod.rs
│       ├── text.rs
│       └── ansi.rs
└── tests/                  # ✅ тесты уровня diagnostic (однофайловые модули)
    ├── mod.rs
    ├── session.rs
    ├── suggest.rs
    └── collect.rs

# ❌ Неправильно: тесты emitter и codes агрегированы в diagnostic/tests/
src/util/diagnostic/
└── tests/
    ├── mod.rs              # ❌ вынуждены объявлять mod emitter; mod codes;
    ├── emitter/            # ❌ должны быть в emitter/tests/
    └── codes/              # ❌ должны быть в codes/tests/
```

#### Правила размещения тестов для однофайловых vs каталожных модулей

**Ключевое различие**: форма организации модуля определяет место тестов.

| Тип модуля         | Критерий определения           | Расположение тестов           | Пример                                        |
| ------------------ | ------------------------------- | ----------------------------- | --------------------------------------------- |
| **Каталожный**     | Есть отдельный каталог и `mod.rs` | `tests/` в этом каталоге     | `inference/tests/`                            |
| **Однофайловый**   | Только `.rs` файлы, без отдельного каталога | `tests/` родительского модуля | `overload.rs` → `typecheck/tests/overload.rs` |

**Подробное объяснение**:

```
src/frontend/core/typecheck/
├── mod.rs                          # mod.rs модуля typecheck
├── checker.rs                      # Однофайловый модуль
├── environment.rs                  # Однофайловый модуль
├── overload.rs                     # Однофайловый модуль
├── type_eval.rs                    # Однофайловый модуль
├── dead_code.rs                    # Однофайловый модуль
├── spawn_placement.rs              # Однофайловый модуль
├── signature.rs                    # Однофайловый модуль
├── types.rs                        # Однофайловый модуль
│
├── tests/                          # ✅ каталог тестов typecheck
│   ├── mod.rs                      # Объявляет тесты однофайловых модулей
│   ├── checker.rs                  # Тесты checker.rs
│   ├── environment.rs              # Тесты environment.rs
│   ├── overload.rs                 # Тесты overload.rs (однофайловый модуль здесь)
│   ├── type_eval.rs                # Тесты type_eval.rs
│   ├── dead_code.rs                # Тесты dead_code.rs
│   ├── spawn_placement.rs          # Тесты spawn_placement.rs
│   ├── signature.rs                # Тесты signature.rs
│   └── types.rs                    # Тесты types.rs
│
├── inference/                      # Каталожный модуль (с mod.rs)
│   ├── mod.rs                      # #[cfg(test)] mod tests; ——объявляет tests/ на своём уровне
│   ├── expressions.rs
│   ├── statements.rs
│   ├── patterns.rs
│   ├── bounds.rs
│   ├── subtyping.rs
│   ├── generics.rs
│   ├── compatibility.rs
│   ├── scope.rs
│   ├── assignment.rs
│   └── tests/                      # ✅ каталог тестов inference
│       ├── mod.rs
│       ├── expressions.rs          # Тесты expressions.rs
│       ├── statements.rs           # Тесты statements.rs
│       └── ...
│
└── traits/                         # Удалён (логика перенесена в types/trait_data.rs)
```

**Почему тесты однофайловых модулей в родительском `tests/`?**

Потому что однофайловый модуль (например `overload.rs`) не имеет собственного `mod.rs`, поэтому он не может объявить
`#[cfg(test)] mod tests;`. Согласно системы модулей Rust, тестовые файлы должны быть объявлены в каком-либо `mod.rs`. Поэтому тесты однофайловых модулей могут быть объявлены только родительским модулем и расположены в родительском `tests/`.

**Алгоритм принятия решения**:

```
Встретили модуль — куда поместить тесты?
│
├── Это каталожный модуль (с mod.rs)?
│   └── Да → Создать tests/ в этом каталоге, объявить в mod.rs этого каталога
│
├── Это однофайловый модуль (только .rs)?
│   └── Да → Тесты в tests/ родительского модуля, объявить в родительском mod.rs
│
└── Не уверены?
    └── Проверить наличие отдельного каталога и mod.rs
```

**Типичные ошибки**:

```
# ❌ Ошибка 1: создание отдельного tests/ для однофайлового модуля
src/frontend/core/typecheck/
├── overload.rs
└── overload/                       # ❌ Не нужно создавать каталог для однофайлового модуля
    └── tests/
        └── overload.rs

# ❌ Ошибка 2: объявление #[cfg(test)] mod tests; в однофайловом модуле
# overload.rs
#[cfg(test)]                        # ❌ Однофайловый модуль не может так объявлять
mod tests;                          # Потому что нет каталога overload/tests/

# ✅ Правильно: тесты в родительском tests/
src/frontend/core/typecheck/
├── overload.rs                     # Исходный файл
└── tests/
    └── overload.rs                 # Тестовый файл, объявлен в typecheck/mod.rs
```

⚠️ **Антипаттерн — так не делать:**

```
# ❌ Неправильно: тесты подмодулей集中в родительском
src/frontend/core/types/
├── mod.rs              # Должен объявлять только base и computation
├── base/
│   ├── mod.rs
│   └── var.rs
└── tests/              # ❌ Родительский tests/ содержит тесты подмодулей
    ├── mod.rs          # ❌ Вынужден объявлять mod base; mod computation;
    ├── base/           # ❌ Это должно быть в base/tests/
    │   └── var.rs
    └── computation/    # ❌ Это должно быть в computation/tests/
        └── ...
```

```
# ✅ Правильно: тесты каждого модуля независимы
src/frontend/core/types/
├── mod.rs              # Объявляет только pub mod base; pub mod computation;
├── base/
│   ├── mod.rs          # #[cfg(test)] mod tests; ——объявляет tests/ на своём уровне
│   ├── var.rs
│   └── tests/
│       ├── mod.rs
│       └── var.rs
└── computation/
    ├── mod.rs          # #[cfg(test)] mod tests; ——объявляет tests/ на своём уровне
    ├── operations.rs
    └── tests/
        ├── mod.rs
        └── operations.rs
```

**Почему нельзя агрегировать вверх?** Потому что система модулей Rust требует, чтобы `#[cfg(test)] mod tests;`
решал вопрос компиляции тестовых файлов в месте объявления. Если `types/mod.rs` объявляет `mod tests;`, то содержимое `types/tests/` становится приватным содержимым модуля `types` — оно не должно заходить на территорию `base` или `computation`.
Тесты каждого модуля должны быть внутренним деталями реализации этого модуля, а не родительского. Это правило также применимо при рефакторинге модулей: когда вы разделяете `types` на `base` и `computation`,
тесты тоже должны следовать за разделёнными модулями, а не оставаться на месте. **Каталог тестов не отражает структуру исходного кода, а следует за границами модулей.**

**Правило 1.2**: `tests/mod.rs` отвечает только за объявление модулей и re-export, функции тестов не содержатся.

```rust
//! Тесты ядра парсера — зеркало src/frontend/core/parser/
//!
//! Тесты для ast.rs, parser_state.rs и парсинга выражений/интеграции.

mod ast;
mod error_recovery;
mod expressions;
mod integration;
mod parser_state;
```

**Правило 1.3**: Каждый тестовый файл соответствует только одному исходному файлу. Не допускается смешивание тестов нескольких исходных модулей в одном файле.

**Правило 1.4**: Объявление тестов должно использовать форму файла `mod tests;` (с точкой с запятой), указывающую на каталог `tests/` на том же уровне. **Запрещено использовать inline форму `mod tests { ... }` для размещения тестового кода внутри исходного файла.**

```rust
// ✅ Правильно——Объявление в форме файла, тестовый код в отдельном файле
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests;

// 🔴 Запрещено——Inline форма, тестовый код паразитирует в исходном файле
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_something() {
        // Тестовый код не должен появляться в исходном файле
    }
}
```

**Почему запрещён inline?**

1. Единая ответственность исходного файла: исходный файл содержит только реализацию, тестовый файл — только тесты. При смешивании для изменения тестов нужно прокручивать вниз файла, для изменения реализации — пропускать тесты.
2. Чёткие границы модулей: каталог `tests/` — это физическая граница, сразу видно какие модули имеют тесты, а какие нет.
3. Безопасность рефакторинга: при разделении модуля каталог `tests/` перемещается вместе с ним; inline тесты нужно вручную извлекать из исходного файла.
4. Просмотр кода: в PR diff изменения исходного кода и тестов — это отдельные файлы, они не смешиваются.

### Правила объявления модулей

**Правило 2.1**: В начале каждого тестового файла должен быть модульный doc-комментарий `//!`, указывающий источник спецификации (номер главы спецификации языка + номер RFC). Если тест не ссылается ни на одну главу спецификации — значит этот код не имеет обоснования в спецификации, его не должно существовать.

```rust
//! Тесты литералов — на основе спецификации языка §2.6
//!
//! §2.6.1: Целые Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: Числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: Строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: Интерполяция F-String
```

**Почему обязательна ссылка на спецификацию?**
Потому что ожидаемые значения в тестах берутся из спецификации, а не из «текущего вывода кода». Если有一天 код изменит вывод, а тест вслед за ним обновится — такой тест ничего не защищает. Только тесты, привязанные к спецификации, могут отличить «намеренное breaking change» от «случайной регрессии».

**Правило 2.2**: Импорты `use` в тестовых модулях должны быть точными до конкретного типа/функции, запрещены glob-импорты `use super::*`.

```rust
// 🟢 Хорошо——Точные импорты
use crate::frontend::core::lexer::{tokenize, TokenKind};
use crate::frontend::core::parser::{ParserState, ParseError};

// 🔴 Мусор——Непонятно, что именно тестируется
use super::*;
```

### Правила именования

**Правило 3.1**: Формат имени тестовой функции: `test_<что>_<сценарий>`, все строчные буквы, разделитель — подчёркивание.

```rust
#[test]
fn test_tokenize_empty_string() { /* ... */ }
#[test]
fn test_parse_int_overflow() { /* ... */ }
#[test]
fn test_typecheck_fn_return_mismatch() { /* ... */ }
```

**Правило 3.2**: Имя тестовой функции должно быть самодокументируемым. Прочитав имя, должно быть понятно, что тестируется и какой результат ожидается. Запрещено нумерационное именование.

```rust
// 🟢 Хорошо
fn test_skip_semicolon_success() { /* ... */ }
fn test_skip_semicolon_failure_when_identifier() { /* ... */ }

// 🔴 Мусор——Совершенно непонятно, что тестируется
fn test_skip_1() { /* ... */ }
fn test_skip_2() { /* ... */ }
```

**Правило 3.3**: Вспомогательным функциям не нужен префикс `test_`, следует использовать глаголы или существительные, описывающие их назначение.

```rust
fn parse_expr(source: &str) -> Expr { /* ... */ }
fn tokenize_single(source: &str) -> Token { /* ... */ }
fn setup_parser_with_tokens(tokens: &[Token]) -> ParserState { /* ... */ }
```

### Правила структуры тестов (Arrange-Act-Assert)

**Правило 4.1**: Каждая тестовая функция должна следовать трёхчастной структуре: Подготовка (Arrange) → Действие (Act) → Проверка (Assert), части разделяются пустой строкой.

```rust
#[test]
fn test_parse_binary_addition() {
    // Arrange
    let source = "1 + 2";

    // Act
    let expr = parse_expr(source);

    // Assert
    assert!(matches!(expr, Expr::Binary { op: BinOp::Add, .. }));
}
```

**Правило 4.2**: Простые тесты (один вызов + одно assert) могут не содержать комментариев разделов, но не более 5 строк логики. Тесты свыше 5 строк должны явно размечать три части.

### Правила вспомогательных функций

**Правило 5.1**: Повторяющийся 3 и более раз setup-код должен быть вынесен во вспомогательную функцию.

```rust
// 🟢 Хорошо——Общий setup вынесен
fn with_state<F>(source: &str, mut f: F)
where
    F: FnMut(&mut ParserState<'_>),
{
    let tokens = tokenize(source).unwrap();
    let mut state = ParserState::new(&tokens);
    f(&mut state);
}

#[test]
fn test_current_returns_first_token() {
    with_state("42", |state| {
        let tok = state.current();
        assert_eq!(&tok.unwrap().kind, &TokenKind::IntLiteral(42));
    });
}
```

**Правило 5.2**: `unwrap()` / `expect()` во вспомогательных функциях при панике должны выводить достаточный контекст. В теле тестовой функции (`#[test] fn ...`) можно напрямую
`unwrap()` — при падении Rust автоматически выводит номер строки; но при падении внутри вспомогательной функции номер строки указывает на определение вспомогательной функции, а не на место вызова.

```rust
// 🟢 Хорошо——При падении выводится содержимое исходного кода
fn run_ok(source: &str) {
    run(source).unwrap_or_else(|e| panic!("Execution failed:\nSource:\n{}\nError:\n{:?}", source, e));
}

// 🔴 Мусор——При падении непонятно, какой исходный файл вызвал проблему
fn run_ok(source: &str) {
    run(source).unwrap();
}
```

**Правило 5.3**: Вспомогательные функции располагаются в верхней части тестового файла, сразу после импортов `use`. Если используются несколькими тестовыми модулями — помещаются в
`tests/mod.rs` и экспортируются через `pub(crate)`.

### Стиль проверок (assertions)

**Правило 6.1**: Для сопоставления вариантов enum предпочтительно использовать `assert!(matches!(...))`, запрещено использовать `if let` + `panic!`.

```rust
// 🟢 Хорошо
assert!(matches!(tokens[0].kind, TokenKind::IntLiteral(42)));

// 🔴 Мусор
if let TokenKind::IntLiteral(v) = tokens[0].kind {
    assert_eq!(v, 42);
} else {
    panic!("Expected IntLiteral");
}
```

**Правило 6.2**: Точные сравнения значений используют `assert_eq!`, булевы проверки используют `assert!`. Запрещено использовать `assert!(a == b)` вместо
`assert_eq!(a, b)`.

**Правило 6.3**: Все assert'ы должны содержать пользовательское сообщение об ошибке, если только сам assert уже полностью описывает причину падения.

```rust
// 🟢 Хорошо——При падении можно быстро локализовать
assert!(
    state.infix_info().is_some(),
    "infix_info should handle '{op}'"
);

// 🟢 Хорошо——assert_eq! при падении автоматически показывает разницу значений, доп. сообщение не нужно
assert_eq!(error_count, 0);

// 🔴 Мусор——При падении只知道 "assertion failed"
assert!(state.infix_info().is_some());
```

**Правило 6.4**: Порядок в assert: `assert_eq!(actual, expected)` — фактическое значение первым, ожидаемое вторым.

### Чек-лист антипаттернов

Нижеперечисленные подходы запрещены, указаны замены:

| Антипаттерн                                 | Проблема                              | Замена                                                           |
| -------------------------------------------- | ------------------------------------- | ---------------------------------------------------------------- |
| `#[cfg(test)] mod tests { ... }` inline тест | Раздувание исходного файла, нечёткие границы модулей, сложный рефакторинг | Тестовый код в отдельном каталоге `tests/`, объявление `mod tests;` (см. правило 1.4) |
| Тест подстраивается под ошибочное поведение кода | Маскирует отклонение от спецификации, легитимизирует баги | Сверяться со спецификацией, исправлять код, тесты не менять |
| Обратный вывод ожидаемых значений теста из вывода кода | Тест становится «магнитофоном текущей реализации» | Выводить ожидаемые значения из спецификации |
| Постоянная метка `#[ignore]`                 | Скрывает устаревающие тесты           | Исправить или удалить                                           |
| Отладочный вывод `println!`                 | Загрязняет вывод тестов                | Использовать `assert!` для явных проверок                       |
| `thread::sleep`                              | Случайные сбои + медленно             | Использовать синхронизацию или mock                              |
| Работа с реальной файловой системой в тестах | Медленно и неповторяемо               | Использовать `tempfile`                                          |
| Зависимость от порядка выполнения тестов     | Случайные сбои                        | Независимый setup для каждого теста                              |
| Тестовая функция более 30 строк логики      | Никто не поймёт                       | Разделить тесты или использовать вспомогательные функции          |
| `unwrap()` без контекста во вспомогательных функциях | Сложно локализовать                  | Использовать `expect("почему")` или кастомный panic (см. правило 5.2) |
| copy-paste одинакового setup 3 и более раз   | Высокая стоимость изменений           | Вынести во вспомогательную функцию                               |

## Правила интеграционных тестов

### Организация тестов

**Правило 7.1**: Интеграционные тесты располагаются в каталоге `tests/` в корне проекта. Входной файл `tests/integration.rs` использует атрибут `#[path]` для подключения подмодулей.

```rust
// tests/integration.rs
#[path = "integration/backends.rs"]
mod backends;
#[path = "integration/codegen.rs"]
mod codegen;
#[path = "integration/execution.rs"]
mod execution;
```

**Правило 7.2**: Каждый файл `tests/integration/*.rs` соответствует одной теме тестирования (бэкенд компилятора, кодогенерация, исполнитель и т.д.), смешивание запрещено.

**Правило 7.3**: Интеграционные тесты должны тестировать через публичный API проекта. Запрещено в интеграционных тестах напрямую ссылаться на внутренние модули `crate::`.
Использовать публичный путь `yaoxiang::`.

```rust
// 🟢 Хорошо——Через публичный API
use yaoxiang::run;

// 🔴 Мусор——Обходим границу публичного API
use yaoxiang::middle::codegen::bytecode::BytecodeFile;
```

### Управление тестовыми данными

**Правило 8.1**: В интеграционных тестах предпочтителен inline строковый код. Внешние fixture-файлы используются только когда код превышает 30 строк (располагаются в
`tests/fixtures/`).

```rust
#[test]
fn test_fibonacci() {
    run_ok(
        r#"
        main: () -> Void = {
            mut a = 0
            mut b = 1
            while a < 100 {
                mut next = a + b
                a = b
                b = next
            }
        }
        "#,
    );
}
```

**Правило 8.2**: Fixture-файлы должны иметь расширение `.yx`, имя файла описывает намерение теста.

### Принципы E2E покрытия

**Правило 9.1**: Интеграционные тесты каждой языковой фичи должны покрывать три пути:

| Путь           | Описание                                        |
| -------------- | ----------------------------------------------- |
| Happy path     | Корректный вход даёт ожидаемый выход            |
| Error path     | Некорректный вход даёт чёткое сообщение об ошибе（非 panic） |
| Boundary       | Граничные значения (пустой ввод, максимальные значения, предел вложенности) |

**Правило 9.2**: Интеграционные тесты не должны зависеть от сети, системных переменных окружения или внешних сервисов.

## Правила бенчмарков

### Использование Criterion.rs

**Правило 10.1**: Бенчмарки统一располагаются в каталоге `benches/`, входной файл — `benches/lib.rs`. Разделение по темам тестирования.

```
benches/
├── lib.rs              # Входной, определяет criterion_group/criterion_main
├── lang_compare/
│   └── fibonacci.rs    # Межъязыковое сравнение бенчмарков
├── parser.rs           # Бенчмарк парсера
└── codegen.rs          # Бенчмарк кодогенерации
```

**Правило 10.2**: Каждая bench-функция должна содержать модульный doc-комментарий `//!` с описанием цели тестирования и измеряемых метрик.

```rust
//! Бенчмарки производительности интерпретатора YaoXiang
//!
//! Метрики: время одного iteration (wall time)
//! Baseline: нативная реализация на Rust
```

### Предотвращение оптимизаций компилятора

**Правило 11.1**: Все выходные данные бенчмарков должны пропускаться через `criterion::black_box` для предотвращения оптимизации компилятором.

```rust
use criterion::{black_box, Criterion};

fn bench_parse(c: &mut Criterion) {
    c.bench_function("parse_fib", |b| {
        b.iter(|| {
            let result = parse(black_box(FIB_SOURCE));
            black_box(result)
        })
    });
}
```

**Правило 11.2**: Входные данные бенчмарков должны быть `const` или `lazy_static`, не должны генерироваться внутри замыкания `iter` — иначе измеряется время генерации данных + время целевой логики.

### Группировка и именование бенчмарков

**Правило 12.1**: Формат имени bench-функции: `<тестируемый_модуль>_<сценарий>`, все строчные, разделитель — подчёркивание. Соответствует правилам именования модульных тестов.

**Правило 12.2**: Обязательно использовать `criterion_group!` для логической группировки связанных бенчмарков. Запрещено все бенчмарки放入одной группе.

```rust
criterion_group!(parser, bench_parse_expr, bench_parse_stmt);
criterion_group!(codegen, bench_codegen_module, bench_codegen_switch);
criterion_main!(parser, codegen);
```

## Правила документных тестов

### Сценарии использования

**Правило 13.1**: Все `pub` функции, типы, методы должны содержать в doc-комментариях хотя бы один исполняемый пример кода. Этот пример выполняется через
`cargo test --doc`.

````rust
/// Разбивает исходную строку на последовательность Token.
///
/// ```
/// use yaoxiang::frontend::core::lexer::tokenize;
///
/// let tokens = tokenize("42").unwrap();
/// assert_eq!(tokens.len(), 2); // IntLiteral + Eof
/// ```
pub fn tokenize(source: &str) -> Result<Vec<Token>, LexError> {
    // ...
}
````

**Правило 13.2**: Примеры кода в документных тестах должны компилироваться и успешно проходить проверки. Не должны содержать маркировку `ignore`
без необходимости, только если пример демонстрирует compile-time ошибку.

````rust
/// ```ignore
/// // Демонстрация compile-time ошибки — можно ignore
/// let x: int = "string";
/// ```
````

### Требования к покрытию

**Правило 14.1**: Документные тесты покрывают только happy path API. Граничные случаи и ошибочные пути покрываются модульными тестами.

**Правило 14.2**: Примеры кода в документных тестах должны быть краткими — не более 10 строк. Если пример требует более длинного контекста — проблема в дизайне API.

## Правила property-based тестов

### Сценарии использования

**Правило 15.1**: В следующих场景必须使用 property-based тесты (proptest или quickcheck) вместо ручного написания нескольких граничных случаев:

| Сценарий                 | Пример                                    |
| ------------------------ | ----------------------------------------- |
| Parser round-trip        | `parse(pretty_print(ast)) == ast`         |
| Сериализация/десериализация | `deserialize(serialize(data)) == data` |
| Тождества математических операций | `a + b == b + a`              |
| Оптимизация компилятора не меняет семантику | `eval(code) == eval(optimize(code))` |

**Правило 15.2**: Для property-based тестов используется `proptest` как основной фреймворк (уже объявлен в
`dev-dependencies` файла `Cargo.toml`).

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn test_roundtrip_serialize_deserialize(value: i64) {
        let serialized = serialize(&value);
        let deserialized: i64 = deserialize(&serialized).unwrap();
        prop_assert_eq!(deserialized, value);
    }
}
```

### Принципы определения properties

**Правило 16.1**: Каждый property-based тест должен иметь явное объявление property — в комментарии указывается проверяемый инвариант.

```rust
// Property: любой целочисленный literal после tokenize → tokens_to_string даёт то же значение
proptest! {
    #[test]
    fn test_int_literal_roundtrip(n in any::<i64>()) {
        let source = n.to_string();
        let tokens = tokenize(&source).unwrap();
        // ...
    }
}
```

**Правило 16.2**: Если property-based тест обнаруживает сбой, необходимо использовать регрессионный механизм `proptest` — добавить провалившийся ввод в
каталог `proptest-regressions/`, не заменять ручным обычным тестом.

## Требования к покрытию

### Цели покрытия для нового кода

**Правило 17.1**: Требования к покрытию тестами нового кода:

| Тип кода                                     | Покрытие строк | Покрытие веток |
| -------------------------------------------- | -------------- | -------------- |
| Основные модули компилятора (frontend/middle/backends) | ≥ 85%          | ≥ 80%           |
| Утилиты/вспомогательные модули (util)        | ≥ 75%          | ≥ 70%           |
| Runtime модули (vm/runtime)                   | ≥ 80%          | ≥ 75%           |
| Стандартная библиотека (std)                 | ≥ 75%          | ≥ 70%           |
| Обработка ошибок и диагностика               | ≥ 90%          | ≥ 85%           |

**Правило 17.2**: Пути обработки ошибок (все ветки `Err`) должны быть покрыты на 100%. Сообщения об ошибках, видимые пользователю, должны быть проверены тестами.

### Чек-лист для проверки PR

**Правило 18.1**: Перед отправкой PR автор должен проверить:

- [ ] `cargo test` все проходят
- [ ] `cargo test --doc` все проходят
- [ ] `cargo bench` нет регрессий производительности (если затронуты hot paths)
- [ ] Новый код соответствует целям покрытия
- [ ] Имена тестов соответствуют правилам именования
- [ ] Каждый тестовый файл объявляет соответствующую главу спецификации (правило 2.1)
- [ ] Ожидаемые значения в тестах взяты из определений спецификации, а не из «текущего вывода кода»
- [ ] Нет тестов с меткой `#[ignore]` (если только нет явного номера issue)
- [ ] Нет лишних `unwrap()` (должны использоваться `expect` или кастомные panic-сообщения)
- [ ] Сообщение коммита использует тип `:white_check_mark: test:`
- [ ] **Нет изменения ожидаемых значений тестов из-за «несоответствия кода спецификации» — меняется код, не тесты**
- [ ] **Нет inline тестов** (`#[cfg(test)] mod tests { ... }` должен быть заменён на
      `mod tests;` + отдельные файлы, см. правило 1.4)

**Правило 18.2**: Reviewer обязан отклонять PR с следующими проблемами:

- Только happy path тесты, нет ошибочных путей
- В тестах есть `thread::sleep` или зависимость от порядка выполнения
- Copy-paste тестового кода более 3 раз без вынесения во вспомогательную функцию
- Имена тестов не соответствуют правилам именования
- Есть постоянные `#[ignore]` тесты
- **Тесты подстраиваются под ошибочное поведение кода** (когда код не соответствует спецификации, меняют тесты, а не код)
- **Тесты не объявляют соответствующую главу спецификации** (см. правило 2.1)
- **Ожидаемые значения в тестах взяты из вывода кода, а не из спецификации** (выведенные тесты равноценны отсутствию тестов)
- **Есть inline тесты** (`#[cfg(test)] mod tests { ... }` вместо
  `mod tests;` + отдельные файлы, см. правило 1.4)
- Тесты проверяют только «не паникует», но не проверяют конкретное поведение
- Удалены проваливающиеся тесты, обнаруживающие баги в коде (а не исправлен код и потом увидели зелёный)

## Приложения

### A. Шпаргалка по командам тестирования

```bash
# Запустить все тесты
cargo test

# Только модульные тесты
cargo test --lib

# Только интеграционные тесты
cargo test --test integration

# Только документные тесты
cargo test --doc

# Запустить конкретный тест (фильтр по имени)
cargo test test_parse_expr

# Запустить бенчмарки
cargo bench

# Показать вывод тестов (по умолчанию stdout скрыт)
cargo test -- --nocapture

# Запустить в один поток (для отладки concurrency проблем)
cargo test -- --test-threads=1

# Сгенерировать отчёт покрытия (нужен cargo-llvm-cov)
cargo llvm-cov --html
```

### B. Шаблон сообщения коммита

Коммиты, связанные с тестами, должны следовать шаблону:

```
:white_check_mark: test(<scope>): <короткое описание>

<Опционально: список покрываемых сценариев>
```

Пример:

```
:white_check_mark: test(parser): добавить тесты инфиксных операторов для Pratt-парсера

Покрытые сценарии:
- Приоритет арифметических операторов (+, -, *, /, %)
- Связывание операторов сравнения (1 < x < 10)
- Short-circuit логических операторов
- Правоассоциативность операторов присваивания
```

### C. Чек-лист новых тестовых файлов

При создании нового тестового модуля убедитесь в наличии:

```
# В каталоге src/<module>/ добавляется тест
src/<module>/tests/
├── mod.rs          # Объявления модулей + общие вспомогательные функции
└── <subject>.rs    # Тестовый файл, имя соответствует тестируемому исходному файлу

# В каталоге tests/ добавляется интеграционный тест
tests/
├── integration.rs   # Обновить: добавить объявление #[path]
└── integration/
    └── <topic>.rs   # Новый тестовый файл
```
