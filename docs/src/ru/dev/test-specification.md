обязаны соблюдать следующие правила; при нарушении Code Review потребует внести исправления.

## Общие положения

### Область применения

Данный стандарт распространяется на весь тестовый код Rust в проекте YaoXiang, включая:

| Тип теста              | Расположение              | Фреймворк                  |
| ---------------------- | ------------------------- | -------------------------- |
| Модульный тест         | `src/<module>/tests/`     | `#[test]` + `#[cfg(test)]` |
| Интеграционный тест    | `tests/`                  | `#[test]`                  |
| Бенчмарк               | `benches/`                | Criterion.rs               |
| Документационный тест  | Doc-комментарии API       | `cargo test --doc`         |
| Тест на основе свойств | Любое расположение тестов | proptest / quickcheck      |

### Основные принципы

**Принцип 0: Авторитетным источником тестов является спецификация, а не код.** Это самый важный
принцип данного документа. Тесты проверяют, соответствует ли код спецификации, а не «работает ли он
в текущей реализации». Когда тест обнаруживает, что поведение кода не соответствует спецификации,
**исправляйте код, никогда не исправляйте тест**.

Спецификации расположены здесь:

- `docs/src/design/language-spec.md` — базовая спецификация языка
- `docs/src/design/rfc/accepted/` — принятые проектные RFC-документы

В начале каждого тестового файла должна быть ссылка на соответствующий раздел спецификации (см.
правило 2.1). Любой разработчик должен иметь возможность сверить реализацию с тестами, опираясь на
спецификацию. И наоборот — если для некоторого кода нет описания в спецификации, его не должно
существовать, и тем более его не нужно тестировать.

```rust
// 🟢 Хорошо — тест напрямую ссылается на спецификацию и проверяет соответствие кода ей
//! Тесты литералов — основаны на спецификации языка §2.6
//!
//! §2.6.1: Целые числа Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: Числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: Строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: F-String интерполяция

#[test]
fn test_decimal_literal_parsing() {
    // Спецификация §2.6.1: Decimal ::= [0-9][0-9_]*
    let result = parse_literal("42").unwrap();
    assert_eq!(result, Literal::Int(42));
}

// 🔴 Плохо — тест подстраивается под текущее поведение кода, а не под спецификацию
#[test]
fn test_literal_1() {
    // Непонятно, какому разделу спецификации соответствует этот код
    // Если parse_literal вернёт неверное значение, этот тест «пройдёт на зелёный»,
    // потому что он лишь проверяет, что функция не паникует
    let result = parse_literal("42");
    assert!(result.is_ok());
}
```

**Сценарий**: вы написали тест и обнаружили, что поведение кода не соответствует спецификации. У вас
есть два варианта:

| Неправильный подход                                         | Правильный подход                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------- |
| Изменить тест, чтобы он «прошёл»                            | Изменить код, чтобы поведение соответствовало спецификации |
| Пометить тест `#[ignore]`                                   | Немедленно исправить реализацию                            |
| Добавить в тест специальные условные ветви, угождающие коду | Удалить ветвь, позволив тесту напрямую вскрыть проблему    |

Помните: **падение теста = ошибка в коде, а не в тесте.** (Если только в самом тесте нет бага — это
уже другое дело.)

**Принцип 1: Тест — это документация.** Любой разработчик, прочитав тест, должен понять поведение
тестируемого кода без дополнительных комментариев или внешней документации.

```rust
// 🟢 Хорошо — имя теста говорит, что и при каких условиях проверяется
#[test]
fn test_tokenize_empty_input_returns_eof() {
    let tokens = tokenize("").unwrap();
    assert_eq!(tokens.len(), 1);
    assert!(matches!(tokens[0].kind, TokenKind::Eof));
}

// 🔴 Плохо — совершенно непонятно, что тестируется
#[test]
fn test_tokenize_1() {
    let tokens = tokenize("").unwrap();
    assert!(tokens.len() > 0);
}
```

**Принцип 2: Нулевая терпимость к случайным сбоям.** Тесты должны быть повторяемыми в любом
окружении. Тесты, зависящие от случайных чисел, системного времени или порядка планирования потоков,
обязаны использовать фиксированный seed или заменяться mock-объектами.

**Принцип 3: Один тест проверяет одну вещь.** Если в имени теста несколько поведений приходится
соединять союзом «и», разделите его на несколько тестов.

```rust
// 🟢 Хорошо — каждый тест проверяет ровно один сценарий
#[test]
fn test_parse_int_positive() { /* ... */ }
#[test]
fn test_parse_int_zero() { /* ... */ }

// 🔴 Плохо — один тест напичкан несвязанными проверками
#[test]
fn test_parser() {
    // Проверяет tokenize, parse, typecheck, codegen...
}
```

**Принцип 4: Тестируйте поведение, а не реализацию.** Рефакторинг внутренней реализации не должен
ломать тесты. Если из-за изменения одной строки реализации упало 10 тестов — тесты написаны
неправильно.

Однако здесь важно различать: **определение «поведения» приходит из спецификации, а не из текущего
поведения кода.** Если код изменил поведение (то есть новое поведение не соответствует
спецификации), тест обязан упасть. Если этого не происходит, ваш тест — «угождающий коду» — он
открывает двери багам.

```
Спецификация (language-spec.md / RFC)  ──определяет──►  Ожидаемое поведение  ──управляет──►  Тест
                                                │
Текущий код  ──реализует──►  Фактическое поведение  ──сравнивается──►  Результат теста

Если фактическое поведение ≠ ожидаемого:
  Тест обязан упасть (красный)  ──►  Исправляем код  ──►  Тест проходит (зелёный)

Если фактическое поведение = ожидаемому (но реализация ужасна):
  Тест проходит  ──►  Рефакторим реализацию  ──►  Тест по-прежнему проходит  ← именно это и есть принцип 4
```

**Принцип 5: Не пишите тестовый код, использующий обходные пути, режимы совместимости или
срабатывающий только в определённых режимах.** Тестовая среда — это среда, которой вы полностью
управляете. Если вам нужен `#[cfg(not(ci))]`, чтобы пропустить тест, значит, в дизайне этого теста
фундаментальная проблема.

### Определения терминов

| Термин                 | Определение                                                                                    |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| Модульный тест         | Тестирует поведение отдельной функции или модуля, не зависит от внешних систем                 |
| Интеграционный тест    | Тестирует взаимодействие нескольких модулей через публичный API или интерфейс командной строки |
| Бенчмарк               | Измеряет производительность кода, выявляет регрессии производительности                        |
| Документационный тест  | Исполняемые примеры кода, встроенные в doc-комментарии                                         |
| Тест на основе свойств | Тест, проверяющий инвариант (свойство) на случайных входных данных                             |

### Связь со стандартом коммитов

Все коммиты, связанные с тестами, должны использовать тип `:white_check_mark: test:`, см.
[Стандарт коммитов](./commit-convention.md).

```
:white_check_mark: test(parser): добавить тесты инфиксных выражений для Pratt-парсера
:white_check_mark: test(codegen): дополнить тесты генерации IR для switch-инструкции
```

## Уровни тестирования yx-корпуса и библиотек

Данный стандарт распространяется на **тестовый код на стороне Rust**. Тесты самого языка YaoXiang
(`.yx`-корпус и тесты библиотек) разделяются на два уровня по объекту тестирования. Системный дизайн
и контракт оценки отнесены к RFC-036 (§7 Сбор тестовых наборов / §8 Три уровня негативных сценариев
/ §9 Слои системы тестирования), а детали составления корпуса — к
`tests/yaoxiang/TEST_STANDARDS.md`:

- **Корпус доступности языка** (`tests/yaoxiang/`) — объектом тестирования является сам язык; std
  используется лишь как инструмент утверждений. Внутри корпуса по уровню возникновения сбоя
  выделяются три типа оценки: тест поведения / тест отказа компиляции / тест сбоя выполнения
- **Тесты библиотек** (идут вместе с библиотекой) — объектом тестирования является контракт
  публичного API библиотеки; yx-уровневые тесты std расположены в `src/std/tests/`, а тесты будущих
  пользовательских пакетов обнаруживаются внутри пакета через `[tool.test]`

Формат заголовка файла тестов `.yx`, директивы заголовка (`// expect:` / `// skip:` / `// mode:`,
RFC-036 §8.2) и соглашения об утверждениях определяются `TEST_STANDARDS.md`; разбор оценки
реализуется общим для двух runner'ов `src/util/test_markers.rs` (на стороне Rust, подчиняется
данному стандарту).

## Стандарты модульных тестов

### Организация файлов

**Правило 1.1**: Каталог `tests/` модульного теста должен располагаться **на одном уровне** с
`mod.rs` тестируемого модуля. `tests/` не агрегируется вверх и не сводится между уровнями.

```
src/frontend/core/parser/
├── mod.rs              # #[cfg(test)] mod tests; — объявляет tests/ на одном уровне
├── ast.rs
├── pratt/
│   ├── mod.rs          # #[cfg(test)] mod tests; — собственные тесты pratt
│   └── tests/
│       ├── mod.rs
│       ├── led.rs
│       ├── nud.rs
│       └── precedence.rs
└── tests/              # тесты уровня модуля parser (без содержимого подмодуля pratt)
    ├── mod.rs
    ├── ast.rs
    ├── expressions.rs
    ├── error_recovery.rs
    └── parser_state.rs
```

Ключевой критерий: **`tests/` располагается в том каталоге, чей `mod.rs` обязан объявить его через
`#[cfg(test)] mod tests;`.**

**Правило 1.1 (дополнение): запрещена агрегация вверх.** Тесты подмодуля должны находиться в
собственном `tests/` этого подмодуля и не должны сводиться в родительский `tests/`.

| Тип модуля                         | Расположение тестов            | Пример                                       |
| ---------------------------------- | ------------------------------ | -------------------------------------------- |
| Каталоговый модуль (с `mod.rs`)    | `tests/` внутри этого каталога | `emitter/tests/`, `codes/tests/`             |
| Однофайловый модуль (только `.rs`) | `tests/` родителя              | `session.rs` → `diagnostic/tests/session.rs` |

```text
# ✅ Правильно: тесты каждого каталогового модуля независимы
src/util/diagnostic/
├── codes/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ собственные тесты codes
│       ├── mod.rs
│       └── codes.rs
├── emitter/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ собственные тесты emitter
│       ├── mod.rs
│       ├── text.rs
│       └── ansi.rs
└── tests/                  # ✅ уровень diagnostic (однофайловые модули)
    ├── mod.rs
    ├── session.rs
    ├── suggest.rs
    └── collect.rs

# ❌ Неправильно: тесты emitter и codes агрегированы в diagnostic/tests/
src/util/diagnostic/
└── tests/
    ├── mod.rs              # ❌ вынуждены объявлять mod emitter; mod codes;
    ├── emitter/            # ❌ должно быть в emitter/tests/
    └── codes/              # ❌ должно быть в codes/tests/
```

#### Правила размещения тестов для однофайловых vs каталоговых модулей

**Ключевое различие**: организация модуля определяет место расположения тестов.

| Тип модуля              | Критерий                                     | Расположение тестов            | Пример                                        |
| ----------------------- | -------------------------------------------- | ------------------------------ | --------------------------------------------- |
| **Каталоговый модуль**  | Имеет собственный каталог и `mod.rs`         | `tests/` внутри этого каталога | `inference/tests/`                            |
| **Однофайловый модуль** | Только файл `.rs`, без собственного каталога | `tests/` родителя              | `overload.rs` → `typecheck/tests/overload.rs` |

**Подробное пояснение**:

```
src/frontend/core/typecheck/
├── mod.rs                          # mod.rs модуля typecheck
├── checker.rs                      # однофайловый модуль
├── environment.rs                  # однофайловый модуль
├── overload.rs                     # однофайловый модуль
├── type_eval.rs                    # однофайловый модуль
├── dead_code.rs                    # однофайловый модуль
├── spawn_placement.rs              # однофайловый модуль
├── signature.rs                    # однофайловый модуль
├── types.rs                        # однофайловый модуль
│
├── tests/                          # ✅ каталог тестов typecheck
│   ├── mod.rs                      # объявляет тесты однофайловых модулей
│   ├── checker.rs                  # тесты checker.rs
│   ├── environment.rs              # тесты environment.rs
│   ├── overload.rs                 # тесты overload.rs (тест однофайлового модуля здесь)
│   ├── type_eval.rs                # тесты type_eval.rs
│   ├── dead_code.rs                # тесты dead_code.rs
│   ├── spawn_placement.rs          # тесты spawn_placement.rs
│   ├── signature.rs                # тесты signature.rs
│   └── types.rs                    # тесты types.rs
│
├── inference/                      # каталоговый модуль (есть mod.rs)
│   ├── mod.rs                      # #[cfg(test)] mod tests; — объявляет tests/ на одном уровне
│   ├── expressions.rs
│   ├── statements.rs
│   ├── patterns.rs
│   ├── bounds.rs
│   ├── subtyping.rs
│   ├── generics.rs
│   ├── compatibility.rs
│   ├── scope.rs
│   ├── assignment.rs
│   └── tests/                      # ✅ каталог тестов inference
│       ├── mod.rs
│       ├── expressions.rs          # тесты expressions.rs
│       ├── statements.rs           # тесты statements.rs
│       └── ...
│
└── traits/                         # удалён (логика слита в types/trait_data.rs)
```

**Почему тесты однофайлового модуля помещаются в родительский `tests/`?** Потому что у однофайлового
модуля (например, `overload.rs`) нет собственного `mod.rs`, и он не может объявить
`#[cfg(test)] mod tests;`. Согласно системе модулей Rust, тестовые файлы должны быть объявлены
каким-либо `mod.rs`, чтобы скомпилироваться. Поэтому тесты однофайлового модуля могут быть объявлены
только родительским `mod.rs` и помещены в его каталог `tests/`.

**Алгоритм принятия решения**:

```
Встретили модуль, нужно решить, куда положить тест?
│
├── Модуль — каталоговый (есть mod.rs)?
│   └── Да → создать tests/ внутри этого каталога, объявить в mod.rs каталога
│
├── Модуль — однофайловый (только .rs)?
│   └── Да → тест кладётся в tests/ родителя, объявляется в mod.rs родителя
│
└── Не уверены?
    └── Проверьте наличие собственного каталога и mod.rs
```

**Частые ошибки**:

```
# ❌ Ошибка 1: создание отдельного каталога tests/ для однофайлового модуля
src/frontend/core/typecheck/
├── overload.rs
└── overload/                       # ❌ нельзя создавать каталог для однофайлового модуля
    └── tests/
        └── overload.rs

# ❌ Ошибка 2: объявление #[cfg(test)] mod tests; внутри однофайлового модуля
# overload.rs
#[cfg(test)]                        # ❌ однофайловый модуль не может так объявлять
mod tests;                          # потому что нет каталога overload/tests/

# ✅ Правильный подход: тесты в родительском tests/
src/frontend/core/typecheck/
├── overload.rs                     # исходный файл
└── tests/
    └── overload.rs                 # тестовый файл, объявленный в typecheck/mod.rs
```

⚠️ **Антипаттерн — так не делать:**

```
# ❌ Неправильно: тесты подмодулей собраны в родительский каталог
src/frontend/core/types/
├── mod.rs              # должен объявлять только base и computation
├── base/
│   ├── mod.rs
│   └── var.rs
└── tests/              # ❌ родительский tests/ содержит тесты подмодулей
    ├── mod.rs          # ❌ вынуждены объявлять mod base; mod computation;
    ├── base/           # ❌ должно быть в base/tests/
    │   └── var.rs
    └── computation/    # ❌ должно быть в computation/tests/
        └── ...
```

```
# ✅ Правильный подход: тесты каждого модуля независимы
src/frontend/core/types/
├── mod.rs              # объявляет только pub mod base; pub mod computation;
├── base/
│   ├── mod.rs          # #[cfg(test)] mod tests; — объявляет tests/ на одном уровне
│   ├── var.rs
│   └── tests/
│       ├── mod.rs
│       └── var.rs
└── computation/
    ├── mod.rs          # #[cfg(test)] mod tests; — объявляет tests/ на одном уровне
    ├── operations.rs
    └── tests/
        ├── mod.rs
        └── operations.rs
```

**Почему нельзя агрегировать вверх?** Потому что система модулей Rust требует, чтобы
`#[cfg(test)] mod tests;` в точке объявления определял компиляцию тестовых файлов. Если
`types/mod.rs` объявляет `mod tests;`, то содержимое `types/tests/` — это приватное содержимое
модуля `types`, и оно не должно вторгаться в область `base` или `computation`. Тесты каждого модуля
должны быть деталями его внутренней реализации, а не родительского модуля. То же правило действует
при рефакторинге модулей: когда вы разделяете `types` на `base` и `computation`, тесты также должны
следовать за разделёнными модулями, а не оставаться на месте. **Каталог тестов не отражает структуру
исходного кода — он следует границам модулей.**

**Правило 1.2**: `tests/mod.rs` отвечает только за объявление модулей и re-export, и не должен
содержать тестовые функции.

```rust
//! Тесты ядра парсера — зеркалирует src/frontend/core/parser/
//!
//! Тесты для ast.rs, parser_state.rs и парсинга выражений/интеграции.

mod ast;
mod error_recovery;
mod expressions;
mod integration;
mod parser_state;
```

**Правило 1.3**: Каждый тестовый файл соответствует ровно одному исходному файлу. Смешивание тестов
нескольких исходных модулей в одном файле запрещено.

**Правило 1.4**: Объявление тестов должно использовать файловую форму `mod tests;` (с точкой с
запятой), указывающую на каталог `tests/` на одном уровне. **Запрещена встроенная форма
`mod tests { ... }`, при которой тестовый код помещается непосредственно в исходный файл.**

```rust
// ✅ Правильно — файловое объявление, тестовый код в отдельных файлах
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests;

// 🔴 Запрещено — встроенная форма, тестовый код паразитирует в исходном файле
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_something() {
        // Тестовый код не должен находиться в исходном файле
    }
}
```

**Почему встроенная форма запрещена?**

1. Единственная ответственность исходного файла: в нём только реализация, в тестовых — только тесты.
   При смешивании правка тестов уезжает в конец файла, а правка реализации заставляет пролистывать
   тесты.
2. Чёткие границы модулей: каталог `tests/` — это физическая граница, по которой сразу видно, какие
   модули покрыты тестами, а какие нет.
3. Безопасность рефакторинга: при разделении модулей каталог `tests/` перемещается вместе с ними;
   встроенные тесты приходится вручную выдирать из исходных файлов.
4. Ревью кода: в PR diff изменения исходного кода и тестов оказываются в разных файлах и не
   перемешиваются.

### Соглашения об объявлении модулей

**Правило 2.1**: В начале каждого тестового файла должен быть doc-комментарий уровня модуля `//!`,
описывающий, какие разделы спецификации покрывает тест (номер раздела спецификации языка + номер
RFC). Если какой-либо тест не ссылается ни на один раздел спецификации — этот код не имеет
спецификационного обоснования и не должен существовать.

```rust
//! Тесты литералов — основаны на спецификации языка §2.6
//!
//! §2.6.1: Целые числа Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: Числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: Строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: F-String интерполяция
```

**Почему обязательна ссылка на спецификацию?** Потому что ожидаемые значения в тесте берутся из
спецификации, а не из «текущего вывода кода». Если однажды код изменит вывод и тест обновится вслед
за ним — тест ничего не защищает. Только привязанный к спецификации тест способен отличить
«намеренное ломающее изменение» от «непреднамеренной регрессии».

**Правило 2.2**: Импорты `use` в тестовом модуле должны быть точными — до конкретного типа/функции.
Glob-импорт `use super::*` запрещён.

```rust
// 🟢 Хорошо — точные импорты
use crate::frontend::core::lexer::{tokenize, TokenKind};
use crate::frontend::core::parser::{ParserState, ParseError};

// 🔴 Плохо — непонятно, что именно тестируется
use super::*;
```

### Соглашения об именовании

**Правило 3.1**: Имя тестовой функции имеет формат `test_<что>_<сценарий>`, полностью в нижнем
регистре, с подчёркиваниями.

```rust
#[test]
fn test_tokenize_empty_string() { /* ... */ }
#[test]
fn test_parse_int_overflow() { /* ... */ }
#[test]
fn test_typecheck_fn_return_mismatch() { /* ... */ }
```

**Правило 3.2**: Имя тестовой функции должно быть самодокументируемым. Прочитав имя, должно быть
понятно, что и при каких условиях тестируется. Именование с числовыми индексами запрещено.

```rust
// 🟢 Хорошо
fn test_skip_semicolon_success() { /* ... */ }
fn test_skip_semicolon_failure_when_identifier() { /* ... */ }

// 🔴 Плохо — совершенно непонятно, что тестируется
fn test_skip_1() { /* ... */ }
fn test_skip_2() { /* ... */ }
```

**Правило 3.3**: Вспомогательные функции не требуют префикса `test_` и должны описывать своё
назначение глаголом или существительным.

```rust
fn parse_expr(source: &str) -> Expr { /* ... */ }
fn tokenize_single(source: &str) -> Token { /* ... */ }
fn setup_parser_with_tokens(tokens: &[Token]) -> ParserState { /* ... */ }
```

### Структура теста (Arrange-Act-Assert)

**Правило 4.1**: Каждая тестовая функция обязана следовать трёхчастной структуре: Подготовка
(Arrange) → Действие (Act) → Проверка (Assert); части разделяются пустой строкой.

```rust
#[test]
fn test_parse_binary_addition() {
    // Arrange
    let source = "1 + 2";

    // Act
    let expr = parse_expr(source);

    // Assert
    assert!(matches!(expr, Expr::Binary { op: BinOp::Add, .. }));
}
```

**Правило 4.2**: Простые тесты (один вызов + одно утверждение) могут не сопровождаться разделяющими
комментариями, но не должны превышать 5 строк логики. Тесты длиннее 5 строк обязаны явно отмечать
все три части.

### Соглашения о вспомогательных функциях

**Правило 5.1**: Повторяющаяся 3 и более раз setup-логика должна быть вынесена во вспомогательную
функцию.

```rust
// 🟢 Хорошо — вынесли общий setup
fn with_state<F>(source: &str, mut f: F)
where
    F: FnMut(&mut ParserState<'_>),
{
    let tokens = tokenize(source).unwrap();
    let mut state = ParserState::new(&tokens);
    f(&mut state);
}

#[test]
fn test_current_returns_first_token() {
    with_state("42", |state| {
        let tok = state.current();
        assert_eq!(&tok.unwrap().kind, &TokenKind::IntLiteral(42));
    });
}
```

**Правило 5.2**: `unwrap()` / `expect()` во вспомогательных функциях обязаны при panic выводить
достаточно контекста. В теле тестовой функции (`#[test] fn ...`) можно напрямую вызывать `unwrap()`
— при сбое Rust автоматически печатает номер строки; но при сбое во вспомогательной функции номер
строки указывает на её определение, и контекст вызова теряется.

```rust
// 🟢 Хорошо — при сбое во вспомогательной функции выводится содержимое исходника
fn run_ok(source: &str) {
    run(source).unwrap_or_else(|e| panic!("Execution failed:\nSource:\n{}\nError:\n{:?}", source, e));
}

// 🔴 Плохо — при сбое непонятно, из-за какого исходника возникла проблема
fn run_ok(source: &str) {
    run(source).unwrap();
}
```

**Правило 5.3**: Вспомогательные функции размещаются в начале тестового файла, сразу после `use`.
Если они используются несколькими тестовыми модулями, их помещают в `tests/mod.rs` и экспортируют
как `pub(crate)`.

### Стиль утверждений

**Правило 6.1**: Для сопоставления с вариантами перечисления предпочтительно использовать
`assert!(matches!(...))`. Конструкция `if let` + `panic!` запрещена.

```rust
// 🟢 Хорошо
assert!(matches!(tokens[0].kind, TokenKind::IntLiteral(42)));

// 🔴 Плохо
if let TokenKind::IntLiteral(v) = tokens[0].kind {
    assert_eq!(v, 42);
} else {
    panic!("Expected IntLiteral");
}
```

**Правило 6.2**: Для сравнения точных значений используется `assert_eq!`, для булевых утверждений —
`assert!`. Запрещено использовать `assert!(a == b)` вместо `assert_eq!(a, b)`.

**Правило 6.3**: Все утверждения должны сопровождаться собственным сообщением об ошибке, кроме
случаев, когда само утверждение полностью описывает причину сбоя.

```rust
// 🟢 Хорошо — при сбое легко локализовать проблему
assert!(
    state.infix_info().is_some(),
    "infix_info should handle '{op}'"
);

// 🟢 Хорошо — assert_eq! при сбое автоматически печатает различие значений, дополнительное сообщение не нужно
assert_eq!(error_count, 0);

// 🔴 Плохо — при сбое видно только "assertion failed"
assert!(state.infix_info().is_some());
```

**Правило 6.4**: Порядок аргументов в утверждении: `assert_eq!(actual, expected)` — фактическое
значение первым, ожидаемое вторым.

### Список антипаттернов

Ниже приведены запрещённые приёмы и их замены:

| Антипаттерн                                           | Проблема                                                              | Замена                                                                                                 |
| ----------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `#[cfg(test)] mod tests { ... }` встроенные тесты     | Раздувание исходников, размытие границ модуля, трудности рефакторинга | Тестовый код выносится в отдельный каталог `tests/` и объявляется через `mod tests;` (см. правило 1.4) |
| Тест угождает ошибочному поведению кода               | Маскирует отклонения от спецификации, легализует баги                 | Сверяйтесь со спецификацией, исправляйте код, оставляя тест неизменным                                 |
| Ожидаемые значения в тесте подгоняются под вывод кода | Тест превращается в «диктофон текущей реализации»                     | Выводите ожидаемые значения из спецификации                                                            |
| Постоянная пометка `#[ignore]`                        | Прячет гниющие тесты                                                  | Исправьте или удалите                                                                                  |
| Отладочный вывод через `println!`                     | Засоряет вывод тестов                                                 | Используйте явные `assert!`                                                                            |
| `thread::sleep`                                       | Случайные сбои + медленно                                             | Используйте синхронизацию или mock-объекты                                                             |
| Операции с реальной файловой системой в тестах        | Медленно и не воспроизводимо                                          | Используйте `tempfile`                                                                                 |
| Зависимость от порядка выполнения тестов              | Случайные сбои                                                        | Независимый setup в каждом тесте                                                                       |
| Тестовая функция длиннее 30 строк логики              | Никто не может разобраться                                            | Разделите на несколько тестов или вынесите логику во вспомогательные функции                           |
| `unwrap()` во вспомогательной функции без контекста   | Трудно локализовать                                                   | Используйте `expect("причина")` или собственный panic (см. правило 5.2)                                |
| Copy-paste одинакового setup более 3 раз              | Высокая стоимость изменений                                           | Вынесите вспомогательную функцию                                                                       |

## Стандарты интеграционных тестов

### Организация тестов

**Правило 7.1**: Интеграционные тесты располагаются в каталоге `tests/` в корне проекта. Входной
файл `tests/integration.rs` подключает подмодули через атрибут `#[path]`.

```rust
// tests/integration.rs
#[path = "integration/backends.rs"]
mod backends;
#[path = "integration/codegen.rs"]
mod codegen;
#[path = "integration/execution.rs"]
mod execution;
```

**Правило 7.2**: Каждый файл `tests/integration/*.rs` соответствует одной теме тестирования (бэкенды
компилятора, кодогенерация, исполнитель и т. п.) и не должен смешивать темы.

**Правило 7.3**: Интеграционные тесты обязаны работать через публичный API проекта. В интеграционных
тестах запрещено напрямую обращаться к внутренним модулям `crate::`. Используйте публичный путь
`yaoxiang::`.

```rust
// 🟢 Хорошо — через публичный API
use yaoxiang::run;

// 🔴 Плохо — обход границы публичного API
use yaoxiang::middle::codegen::bytecode::BytecodeFile;
```

### Управление тестовыми данными

**Правило 8.1**: В интеграционных тестах предпочтительно использовать исходный код в виде строковой
константы. Внешние файлы фикстур (расположенные в `tests/fixtures/`) применяются только если
исходник превышает 30 строк.

```rust
#[test]
fn test_fibonacci() {
    run_ok(
        r#"
        main = {
            mut a = 0
            mut b = 1
            while a < 100 {
                mut next = a + b
                a = b
                b = next
            }
        }
        "#,
    );
}
```

**Правило 8.2**: Файлы фикстур обязаны иметь расширение `.yx`, имя файла должно описывать назначение
теста.

### Принципы покрытия E2E

**Правило 9.1**: Интеграционные тесты каждой возможности языка должны покрывать три пути:

| Путь        | Описание                                                                    |
| ----------- | --------------------------------------------------------------------------- |
| Happy path  | Корректный ввод даёт ожидаемый результат                                    |
| Путь ошибки | Некорректный ввод даёт понятное сообщение об ошибке (а не panic)            |
| Граничный   | Граничные значения (пустой ввод, максимальное значение, предел вложенности) |

**Правило 9.2**: Интеграционные тесты не должны зависеть от сети, переменных окружения или внешних
сервисов.

## Стандарты бенчмарков

### Использование Criterion.rs

**Правило 10.1**: Бенчмарки единообразно располагаются в каталоге `benches/`, входной файл —
`benches/lib.rs`. Файлы разделяются по темам тестирования.

```
benches/
├── lib.rs              # входной файл, определяет criterion_group/criterion_main
├── lang_compare/
│   └── fibonacci.rs    # межъязыковые сравнительные бенчмарки
├── parser.rs           # бенчмарки парсера
└── codegen.rs          # бенчмарки кодогенерации
```

**Правило 10.2**: Каждая бенчмарк-функция должна содержать doc-комментарий модуля `//!`, описывающий
цель тестирования и измеряемые метрики.

```rust
//! Бенчмарки производительности интерпретатора YaoXiang
//!
//! Измеряемая метрика: время одной итерации (wall time)
//! Базовый уровень: нативная реализация на Rust
```

### Защита от оптимизаций компилятора

**Правило 11.1**: Тестируемый вывод во всех бенчмарках должен быть обёрнут в `criterion::black_box`,
чтобы компилятор не мог удалить его оптимизацией.

```rust
use criterion::{black_box, Criterion};

fn bench_parse(c: &mut Criterion) {
    c.bench_function("parse_fib", |b| {
        b.iter(|| {
            let result = parse(black_box(FIB_SOURCE));
            black_box(result)
        })
    });
}
```

**Правило 11.2**: Входные данные бенчмарка должны быть `const` или `lazy_static`; динамическая
генерация внутри замыкания `iter` запрещена — иначе измеряется сумма времени генерации данных и
тестируемой логики.

### Группировка и именование бенчмарков

**Правило 12.1**: Имя бенчмарка имеет формат `<тестируемый_модуль>_<сценарий>`, полностью в нижнем
регистре с подчёркиваниями. Согласуется с правилами именования модульных тестов.

**Правило 12.2**: Логически связанные бенчмарки обязаны объединяться через `criterion_group!`.
Запрещено сваливать все бенчмарки в одну группу.

```rust
criterion_group!(parser, bench_parse_expr, bench_parse_stmt);
criterion_group!(codegen, bench_codegen_module, bench_codegen_switch);
criterion_main!(parser, codegen);
```

## Стандарты документационных тестов

### Сценарии использования

**Правило 13.1**: Все `pub` функции, типы и методы должны содержать в doc-комментариях как минимум
один запускаемый пример кода. Этот пример выполняется через `cargo test --doc`.

````rust
/// Разбивает строку исходного кода на последовательность токенов.
///
/// ```
/// use yaoxiang::frontend::core::lexer::tokenize;
///
/// let tokens = tokenize("42").unwrap();
/// assert_eq!(tokens.len(), 2); // IntLiteral + Eof
/// ```
pub fn tokenize(source: &str) -> Result<Vec<Token>, LexError> {
    // ...
}
````

**Правило 13.2**: Примеры кода в документационных тестах должны компилироваться и успешно проходить
утверждения. Пометка `ignore` запрещена, за исключением случаев, когда пример демонстрирует ошибку
этапа компиляции.

````rust
/// ```ignore
/// // Демонстрация ошибки компиляции — допустимо ignore
/// let x: int = "string";
/// ```
````

### Требования к покрытию

**Правило 14.1**: Документационные тесты покрывают только happy path API. Граничные случаи и пути
ошибок покрываются модульными тестами.

**Правило 14.2**: Примеры кода в документационных тестах должны быть краткими — не более 10 строк.
Если примеру требуется более длинный контекст, это указывает на проблему в дизайне API.

## Стандарты тестов на основе свойств

### Сценарии использования

**Правило 15.1**: В следующих сценариях обязательно использовать property-тесты (proptest или
quickcheck), а не серию граничных случаев, написанных вручную:

| Сценарий                                    | Пример                                 |
| ------------------------------------------- | -------------------------------------- |
| Round-trip парсера                          | `parse(pretty_print(ast)) == ast`      |
| Сериализация/десериализация                 | `deserialize(serialize(data)) == data` |
| Тождества математических операций           | `a + b == b + a`                       |
| Оптимизации компилятора не меняют семантику | `eval(code) == eval(optimize(code))`   |

**Правило 15.2**: В качестве основного фреймворка property-тестов используется `proptest` (уже
объявлен в `dev-dependencies` в `Cargo.toml`).

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn test_roundtrip_serialize_deserialize(value: i64) {
        let serialized = serialize(&value);
        let deserialized: i64 = deserialize(&serialized).unwrap();
        prop_assert_eq!(deserialized, value);
    }
}
```

### Принципы определения свойств

**Правило 16.1**: Каждый тест на основе свойств должен иметь явное объявление свойства — в
комментарии указать проверяемый инвариант.

```rust
// Свойство: произвольный целочисленный литерал после tokenize → tokens_to_string даёт то же значение
proptest! {
    #[test]
    fn test_int_literal_roundtrip(n in any::<i64>()) {
        let source = n.to_string();
        let tokens = tokenize(&source).unwrap();
        // ...
    }
}
```

**Правило 16.2**: Если property-тест обнаружил сбой, обязательно использовать механизм регрессий
`proptest` — добавить входные данные, на которых он упал, в каталог `proptest-regressions/`.
Заменять такой кейс обычным тестом, написанным вручную, запрещено.

## Требования к покрытию

### Целевые показатели покрытия нового кода

**Правило 17.1**: Требования к покрытию тестами для нового кода:

| Тип кода                                           | Покрытие строк | Покрытие ветвей |
| -------------------------------------------------- | -------------- | --------------- |
| Модули ядра компилятора (frontend/middle/backends) | ≥ 85%          | ≥ 80%           |
| Вспомогательные/утилитарные модули (util)          | ≥ 75%          | ≥ 70%           |
| Модули времени выполнения (vm/runtime)             | ≥ 80%          | ≥ 75%           |
| Стандартная библиотека (std)                       | ≥ 75%          | ≥ 70%           |
| Обработка ошибок и диагностика                     | ≥ 90%          | ≥ 85%           |

**Правило 17.2**: Пути обработки ошибок (все ветви `Err`) должны быть покрыты на 100%. Сообщения об
ошибках, которые видит пользователь, обязаны быть проверены тестами.

### Чек-лист ревью PR

**Правило 18.1**: Перед отправкой PR автор обязан самостоятельно проверить следующие пункты:

- [ ] `cargo test` — все тесты проходят
- [ ] `cargo test --doc` — все тесты проходят
- [ ] `cargo bench` — нет регрессий производительности (если затрагиваются горячие пути)
- [ ] Новый код соответствует целевым показателям покрытия
- [ ] Имена тестов соответствуют соглашениям об именовании
- [ ] В каждом тестовом файле объявлен соответствующий раздел спецификации (правило 2.1)
- [ ] Ожидаемые значения в тестах взяты из спецификации, а не из «текущего вывода кода»
- [ ] Нет тестов, помеченных `#[ignore]` (кроме случаев с явным комментарием-ссылкой на issue)
- [ ] Нет лишних `unwrap()` (следует использовать `expect` или собственный panic-сообщение)
- [ ] Сообщение коммита использует тип `:white_check_mark: test:`
- [ ] **Ожидаемые значения теста не были изменены из-за «несоответствия поведения кода спецификации»
      — исправлен код, а не тест**
- [ ] **Нет встроенных тестов** (`#[cfg(test)] mod tests { ... }` должно быть заменено на
      `mod tests;` + отдельные файлы, см. правило 1.4)

**Правило 18.2**: Ревьюер обязан отклонить PR, содержащий следующие проблемы:

- Только happy path, без путей ошибки
- В тестах используется `thread::sleep` или они зависят от порядка выполнения
- Copy-paste тестового кода более 3 раз без вынесения вспомогательной функции
- Имена тестов не соответствуют соглашениям
- Есть постоянно помеченные `#[ignore]` тесты
- **Тест угождает ошибочному поведению кода** (когда код не соответствует спецификации, исправлен
  тест, а не код)
- **В тесте не объявлен соответствующий раздел спецификации** (см. правило 2.1)
- **Ожидаемые значения теста взяты из вывода кода, а не из спецификации** (подогнанный тест равен
  отсутствию теста)
- **Есть встроенные тесты** (`#[cfg(test)] mod tests { ... }` вместо `mod tests;` + отдельные файлы,
  см. правило 1.4)
- Тест проверяет только «не падает», не утверждая конкретного поведения
- Удалён упавший тест, который вскрывал баг кода (вместо того, чтобы исправить код и дождаться его
  зелёного состояния)

## Приложения

### A. Шпаргалка по командам тестирования

```bash
# Запустить все тесты
cargo test

# Только модульные тесты
cargo test --lib

# Только интеграционные тесты
cargo test --test integration

# Только документационные тесты
cargo test --doc

# Запустить конкретный тест (фильтр по имени)
cargo test test_parse_expr

# Запустить бенчмарки
cargo bench

# Показать вывод тестов (по умолчанию stdout скрыт)
cargo test -- --nocapture

# Однопоточное выполнение (для диагностики проблем конкурентности)
cargo test -- --test-threads=1

# Сгенерировать отчёт о покрытии (требуется cargo-llvm-cov)
cargo llvm-cov --html
```

### B. Шаблон сообщения коммита

Коммиты, связанные с тестами, должны следовать следующему шаблону:

```
:white_check_mark: test(<область>): <краткое описание>

<опционально: список покрытых сценариев>
```

Пример:

```
:white_check_mark: test(parser): добавить тесты инфиксных операторов Pratt-парсера

Покрытые сценарии:
- Приоритет арифметических операторов (+, -, *, /, %)
- Цепочки операторов сравнения (1 < x < 10)
- Короткое замыкание логических операторов
- Правоассоциативность оператора присваивания
```

### C. Чек-лист для новых тестовых файлов

При создании нового тестового модуля убедитесь, что присутствуют следующие файлы:

```
# Новый тест в каталоге src/<module>/
src/<module>/tests/
├── mod.rs          # объявление модуля + общие вспомогательные функции
└── <тема>.rs       # тестовый файл, названный по тестируемому исходному файлу

# Новый интеграционный тест в каталоге tests/
tests/
├── integration.rs   # обновить: добавить объявление через #[path]
└── integration/
    └── <тема>.rs   # новый тестовый файл
```
