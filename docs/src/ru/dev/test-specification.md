В настоящем документе определены жёсткие стандарты написания тестов для проекта YaoXiang. Все
участники обязаны соблюдать следующие правила; нарушители будут обязаны внести исправления в ходе
Code Review.

## Общие положения

### Область применения

Настоящий стандарт распространяется на весь тестовый код на Rust в проекте YaoXiang, включая:

| Тип теста              | Расположение            | Фреймворк                  |
| ---------------------- | ----------------------- | -------------------------- |
| Модульные тесты        | `src/<module>/tests/`   | `#[test]` + `#[cfg(test)]` |
| Интеграционные тесты   | `tests/`                | `#[test]`                  |
| Бенчмарки              | `benches/`              | Criterion.rs               |
| Документационные тесты | Комментарии в API-доках | `cargo test --doc`         |
| Property-тесты         | Любая тестовая позиция  | proptest / quickcheck      |

### Основные принципы

**Принцип 0: Авторитетный источник для тестов — спецификация, а не код.** Это важнейший принцип
настоящего документа. Тесты проверяют, соответствует ли код спецификации, а не «работает ли код в
текущей реализации». Когда тест обнаруживает несоответствие поведения кода спецификации,
**исправляйте код, никогда не исправляйте тест**.

Файлы спецификации расположены по адресам:

- `docs/src/design/language-spec.md` — базовая спецификация языка
- `docs/src/design/rfc/accepted/` — принятые проектные документы RFC

В верхней части каждого тестового файла должна быть указана соответствующая секция спецификации (см.
правило 2.1). Любой разработчик должен иметь возможность, имея на руках документ спецификации,
сверить с ним тесты и проверить корректность реализации. И наоборот — если для некоторого кода нет
соответствующего описания в спецификации, его не должно существовать, и тем более его не нужно
тестировать.

```rust
// 🟢 Хорошо — тест напрямую ссылается на спецификацию, проверяя соответствие кода
//! Тесты литералов — на основе спецификации языка §2.6
//!
//! §2.6.1: целые числа Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: интерполяция F-String

#[test]
fn test_decimal_literal_parsing() {
    // Спецификация §2.6.1: Decimal ::= [0-9][0-9_]*
    let result = parse_literal("42").unwrap();
    assert_eq!(result, Literal::Int(42));
}

// 🔴 Мусор — тест подстраивается под текущее поведение кода, а не проверяет спецификацию
#[test]
fn test_literal_1() {
    // Непонятно, какой секции спецификации соответствует этот код
    // Если parse_literal вернёт неверное значение, этот тест «пропустит зелёным»,
    // потому что он только проверяет, что функция не паникует
    let result = parse_literal("42");
    assert!(result.is_ok());
}
```

**Сценарий**: вы написали тест и обнаружили, что поведение кода не соответствует спецификации. У вас
два выбора:

| Неправильно                                                 | Правильно                                                  |
| ----------------------------------------------------------- | ---------------------------------------------------------- |
| Изменить тест, чтобы он «прошёл»                            | Изменить код, чтобы поведение соответствовало спецификации |
| Добавить в тест `#[ignore]`                                 | Немедленно исправить реализацию кода                       |
| Добавить в тест особые ветви условий, подстраиваясь под код | Удалить ветвь, позволив тесту выявить проблему напрямую    |

Запомните: **красный = код неверен, а не тест**. (Если только в самом тесте нет бага — но это уже
другое дело.)

**Принцип 1: Тест — это документация.** Любой разработчик должен иметь возможность, прочитав тест,
понять поведение тестируемого кода без дополнительных комментариев или внешней документации.

```rust
// 🟢 Хорошо — имя теста говорит, что тестируется и что ожидается
#[test]
fn test_tokenize_empty_input_returns_eof() {
    let tokens = tokenize("").unwrap();
    assert_eq!(tokens.len(), 1);
    assert!(matches!(tokens[0].kind, TokenKind::Eof));
}

// 🔴 Мусор — никто не поймёт, что тестируется
#[test]
fn test_tokenize_1() {
    let tokens = tokenize("").unwrap();
    assert!(tokens.len() > 0);
}
```

**Принцип 2: Нулевая терпимость к случайным сбоям.** Тесты должны быть воспроизводимыми в любом
окружении. Тесты, зависящие от случайных чисел, системного времени или порядка планирования потоков,
должны использовать фиксированные seed-значения или заменяться mock-объектами.

**Принцип 3: Один тест проверяет одно.** Если в имени теста нужно соединить «и» несколько поведений,
разделите его на несколько тестов.

```rust
// 🟢 Хорошо — каждый тест проверяет только один сценарий
#[test]
fn test_parse_int_positive() { /* ... */ }
#[test]
fn test_parse_int_zero() { /* ... */ }

// 🔴 Мусор — в одном тесте слишком много несвязанного
#[test]
fn test_parser() {
    // тестирует tokenize, parse, typecheck, codegen...
}
```

**Принцип 4: Тестируйте поведение, а не реализацию.** Рефакторинг внутренней реализации не должен
приводить к падению тестов. Если из-за изменения одной строки реализации упало 10 тестов, ваши тесты
написаны неправильно.

Но здесь есть ключевое разграничение: **определение «поведения» исходит из спецификации, а не из
текущего поведения кода**. Если код изменил поведение (то есть ввёл новое поведение, несовместимое
со спецификацией), тест должен упасть. Если этого не происходит, ваш тест — «подстраивающийся под
код тест» — он впускает баги без сопротивления.

```
Спецификация (language-spec.md / RFC)  ──определяет──►  Ожидаемое поведение  ──управляет──►  Тест
                                              │
Текущий код  ──реализует──►  Фактическое поведение  ──сравнивается с──►  Результат теста

Если фактическое поведение ≠ ожидаемого:
  Тест должен упасть (красный)  ──►  Исправить код  ──►  Тест проходит (зелёный)

Если фактическое поведение = ожидаемому (но реализация ужасна):
  Тест проходит  ──►  Рефакторинг реализации  ──►  Тест всё ещё проходит  ← это и есть смысл принципа 4
```

**Принцип 5: Не пишите тестовый код для отката, совместимости или срабатывания специфических
режимов.** Тестовая среда — это среда, которой вы полностью управляете. Если вам нужен
`#[cfg(not(ci))]`, чтобы пропустить какой-то тест, значит, в дизайне теста есть фундаментальная
проблема.

### Терминология

| Термин                | Определение                                                                    |
| --------------------- | ------------------------------------------------------------------------------ |
| Модульный тест        | Тестирует поведение отдельной функции или модуля, не зависит от внешних систем |
| Интеграционный тест   | Тестирует взаимодействие нескольких модулей через публичный API или CLI-вход   |
| Бенчмарк              | Измеряет производительность кода, выявляет регрессии производительности        |
| Документационный тест | Исполняемый пример кода, встроенный в комментарии документации                 |
| Property-тест         | Тест, проверяющий инвариант (свойство) на случайных входных данных             |

### Связь со стандартами коммитов

Все коммиты, связанные с тестами, должны использовать тип `:white_check_mark: test:`, согласно
[стандарту коммитов](./commit-convention.md).

```
:white_check_mark: test(parser): добавить тесты инфиксных выражений парсера Pratt
:white_check_mark: test(codegen): дополнить тесты генерации IR для switch
```

## Уровни тестирования корпуса yx и библиотек

Настоящий стандарт регулирует **тестовый код на стороне Rust**. Тесты самого языка YaoXiang (корпус
`.yx` и тесты библиотек) делятся по объекту тестирования на два уровня; архитектура системы и
контракты верификации определены в RFC-036 (§7 сборка suite / §8 три уровня негативных тестов / §9
многоуровневая система тестирования), а правила составления корпуса — в
`tests/yaoxiang/TEST_STANDARDS.md`:

- **Корпус пригодности языка** (`tests/yaoxiang/`) — объектом тестирования является сам язык; std
  используется только как инструмент утверждений. Внутри корпуса верификация делится на три
  категории по слою возникновения ошибки: тесты поведения / тесты отклонения на этапе компиляции /
  тесты сбоя на этапе выполнения.
- **Тесты библиотек** (рядом с библиотекой) — объектом тестирования является публичный API-контракт
  библиотеки; тесты std уровня yx находятся в `src/std/tests/`, а будущие тесты пользовательских
  пакетов обнаруживаются внутри пакета через `[tool.test]`.

Формат заголовка тестовых файлов `.yx`, маркеры (`[test:error]` / `[test:ignore]` / `[test:runtime]`
/ `预期: EXXXX`) и соглашения об утверждениях определяются в TEST_STANDARDS.md; разбор маркеров
реализован в общей для обоих runner-ов утилите `src/util/test_markers.rs` (на стороне Rust,
подчиняется настоящему стандарту).

## Стандарты модульных тестов

### Организация файлов

**Правило 1.1**: каталог `tests/` модульных тестов должен находиться **на одном уровне** с `mod.rs`
тестируемого модуля. `tests/` не агрегируется вверх и не сводится через уровни.

```
src/frontend/core/parser/
├── mod.rs              # #[cfg(test)] mod tests; — объявляет tests/ того же уровня
├── ast.rs
├── pratt/
│   ├── mod.rs          # #[cfg(test)] mod tests; — собственные тесты pratt
│   └── tests/
│       ├── mod.rs
│       ├── led.rs
│       ├── nud.rs
│       └── precedence.rs
└── tests/              # тесты уровня модуля parser (не включают содержимое подмодуля pratt)
    ├── mod.rs
    ├── ast.rs
    ├── expressions.rs
    ├── error_recovery.rs
    └── parser_state.rs
```

Ключевой критерий: **в каком каталоге расположен `tests/`, в `mod.rs` этого каталога должна
присутствовать декларация `#[cfg(test)] mod tests;`**.

**Дополнение к правилу 1.1: запрещена агрегация вверх.** Тесты подмодулей из каталогов должны
размещаться в собственном `tests/` подмодуля, их нельзя сводить в родительский `tests/`.

| Тип модуля                         | Расположение тестов      | Пример                                       |
| ---------------------------------- | ------------------------ | -------------------------------------------- |
| Каталог-модуль (с `mod.rs`)        | `tests/` в этом каталоге | `emitter/tests/`, `codes/tests/`             |
| Однофайловый модуль (только `.rs`) | `tests/` родителя        | `session.rs` → `diagnostic/tests/session.rs` |

```text
# ✅ Правильно: тесты каждого каталога-модуля независимы
src/util/diagnostic/
├── codes/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ собственные тесты codes
│       ├── mod.rs
│       └── codes.rs
├── emitter/
│   ├── mod.rs              # #[cfg(test)] mod tests;
│   └── tests/              # ✅ собственные тесты emitter
│       ├── mod.rs
│       ├── text.rs
│       └── ansi.rs
└── tests/                  # ✅ уровень diagnostic (однофайловые модули)
    ├── mod.rs
    ├── session.rs
    ├── suggest.rs
    └── collect.rs

# ❌ Неправильно: тесты emitter и codes агрегированы в diagnostic/tests/
src/util/diagnostic/
└── tests/
    ├── mod.rs              # ❌ вынуждены объявлять mod emitter; mod codes;
    ├── emitter/            # ❌ должно быть в emitter/tests/
    └── codes/              # ❌ должно быть в codes/tests/
```

#### Правила размещения тестов для однофайловых и каталог-модулей

**Ключевое различие**: форма организации модуля определяет место размещения тестов.

| Тип модуля              | Критерий                                   | Расположение тестов           | Пример                                        |
| ----------------------- | ------------------------------------------ | ----------------------------- | --------------------------------------------- |
| **Каталог-модуль**      | Имеет отдельный каталог и `mod.rs`         | `tests/` в этом каталоге      | `inference/tests/`                            |
| **Однофайловый модуль** | Только файл `.rs`, без отдельного каталога | `tests/` родительского модуля | `overload.rs` → `typecheck/tests/overload.rs` |

**Подробное пояснение**:

```
src/frontend/core/typecheck/
├── mod.rs                          # mod.rs модуля typecheck
├── checker.rs                      # однофайловый модуль
├── environment.rs                  # однофайловый модуль
├── overload.rs                     # однофайловый модуль
├── type_eval.rs                    # однофайловый модуль
├── dead_code.rs                    # однофайловый модуль
├── spawn_placement.rs              # однофайловый модуль
├── signature.rs                    # однофайловый модуль
├── types.rs                        # однофайловый модуль
│
├── tests/                          # ✅ каталог тестов typecheck
│   ├── mod.rs                      # объявляет тесты однофайловых модулей
│   ├── checker.rs                  # тесты для checker.rs
│   ├── environment.rs              # тесты для environment.rs
│   ├── overload.rs                 # тесты для overload.rs (тесты однофайлового модуля здесь)
│   ├── type_eval.rs                # тесты для type_eval.rs
│   ├── dead_code.rs                # тесты для dead_code.rs
│   ├── spawn_placement.rs          # тесты для spawn_placement.rs
│   ├── signature.rs                # тесты для signature.rs
│   └── types.rs                    # тесты для types.rs
│
├── inference/                      # каталог-модуль (имеет mod.rs)
│   ├── mod.rs                      # #[cfg(test)] mod tests; — объявляет tests/ того же уровня
│   ├── expressions.rs
│   ├── statements.rs
│   ├── patterns.rs
│   ├── bounds.rs
│   ├── subtyping.rs
│   ├── generics.rs
│   ├── compatibility.rs
│   ├── scope.rs
│   ├── assignment.rs
│   └── tests/                      # ✅ каталог тестов inference
│       ├── mod.rs
│       ├── expressions.rs          # тесты для expressions.rs
│       ├── statements.rs           # тесты для statements.rs
│       └── ...
│
└── traits/                         # удалено (логика объединена в types/trait_data.rs)
```

**Почему тесты однофайлового модуля размещаются в родительском `tests/`?**

Потому что у однофайлового модуля (например, `overload.rs`) нет собственного `mod.rs`, и он не может
объявить `#[cfg(test)] mod tests;`. Согласно системе модулей Rust, тестовый файл должен быть
объявлен в каком-то `mod.rs` для компиляции. Поэтому тесты однофайлового модуля могут быть объявлены
только через `mod.rs` родительского модуля и размещены в его `tests/`.

**Алгоритм принятия решения**:

```
Встретился модуль — куда положить тесты?
│
├── Модуль — каталог (с mod.rs)?
│   └── Да → создать tests/ в этом каталоге, объявить через mod.rs каталога
│
├── Модуль — однофайловый (только .rs)?
│   └── Да → тесты положить в tests/ родителя, объявить через mod.rs родителя
│
└── Не уверены?
    └── Проверить наличие отдельного каталога и mod.rs
```

**Частые ошибки**:

```
# ❌ Ошибка 1: создание отдельного каталога tests/ для однофайлового модуля
src/frontend/core/typecheck/
├── overload.rs
└── overload/                       # ❌ для однофайлового модуля не нужно создавать каталог
    └── tests/
        └── overload.rs

# ❌ Ошибка 2: объявление #[cfg(test)] mod tests; внутри однофайлового модуля
# overload.rs
#[cfg(test)]                        # ❌ однофайловый модуль не может так объявлять
mod tests;                          # потому что нет каталога overload/tests/

# ✅ Правильный подход: тесты положить в родительский tests/
src/frontend/core/typecheck/
├── overload.rs                     # исходный файл
└── tests/
    └── overload.rs                 # тестовый файл, объявленный через typecheck/mod.rs
```

⚠️ **Антипаттерн — не пишите так:**

```
# ❌ Неправильно: тесты подмодулей собраны на уровне родителя
src/frontend/core/types/
├── mod.rs              # должен объявлять только base и computation
├── base/
│   ├── mod.rs
│   └── var.rs
└── tests/              # ❌ родительский tests/ содержит тесты подмодулей
    ├── mod.rs          # ❌ вынуждены объявлять mod base; mod computation;
    ├── base/           # ❌ это должно быть в base/tests/
    │   └── var.rs
    └── computation/    # ❌ это должно быть в computation/tests/
        └── ...
```

```
# ✅ Правильный подход: тесты каждого модуля независимы
src/frontend/core/types/
├── mod.rs              # объявляет только pub mod base; pub mod computation;
├── base/
│   ├── mod.rs          # #[cfg(test)] mod tests; — объявляет tests/ того же уровня
│   ├── var.rs
│   └── tests/
│       ├── mod.rs
│       └── var.rs
└── computation/
    ├── mod.rs          # #[cfg(test)] mod tests; — объявляет tests/ того же уровня
    ├── operations.rs
    └── tests/
        ├── mod.rs
        └── operations.rs
```

**Почему нельзя агрегировать вверх?** Потому что система модулей Rust требует, чтобы
`#[cfg(test)] mod tests;` в точке объявления определял компиляцию тестовых файлов. Если
`types/mod.rs` объявляет `mod tests;`, то содержимое `types/tests/` является приватным содержимым
модуля `types` — оно не должно вторгаться в территорию `base` или `computation`. Тесты каждого
модуля должны быть деталями его внутренней реализации, а не родительского модуля. Это правило также
применимо к рефакторингу модулей: когда вы разбиваете `types` на `base` и `computation`, тесты тоже
должны следовать за разделёнными модулями, а не оставаться на прежнем месте. **Каталог тестов не
зеркалит структуру исходников, а следует за границами модулей.**

**Правило 1.2**: `tests/mod.rs` отвечает только за объявление модулей и re-export, не содержит
тестовых функций.

```rust
//! Parser core tests — mirrors src/frontend/core/parser/
//!
//! Tests for ast.rs, parser_state.rs, and expression/integration parsing.

mod ast;
mod error_recovery;
mod expressions;
mod integration;
mod parser_state;
```

**Правило 1.3**: каждый тестовый файл соответствует только одному исходному файлу. Не допускается
смешивание тестов нескольких исходных модулей в одном файле.

**Правило 1.4**: объявление тестов должно использовать файловую форму `mod tests;` (с точкой с
запятой), указывающую на одноуровневый каталог `tests/`. **Запрещено использовать inline-форму
`mod tests { ... }` с размещением тестового кода непосредственно в исходном файле.**

```rust
// ✅ Правильно — объявление в файловой форме, тестовый код в отдельных файлах
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests;

// 🔴 Запрещено — inline-форма, тестовый код паразитирует в исходном файле
// src/frontend/core/parser/mod.rs
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_something() {
        // тестовый код не должен находиться в исходном файле
    }
}
```

**Почему inline-форма запрещена?**

1. Единая ответственность исходного файла: в исходном файле — только реализация, в тестовом — только
   тесты. При смешанном подходе для правки теста нужно прокручивать файл в конец, а для правки
   реализации — пропускать тесты.
2. Чёткие границы модулей: каталог `tests/` — это физическая граница, по которой сразу видно, какие
   модули имеют тесты, а какие нет.
3. Безопасный рефакторинг: при разделении модуля каталог `tests/` перемещается вместе с ним;
   inline-тесты нужно вручную извлекать из исходного файла.
4. Code review: в PR diff изменения исходного кода и тестов находятся в разных файлах и не
   смешиваются.

### Стандарты объявления модулей

**Правило 2.1**: в верхней части каждого тестового файла должен быть комментарий документации уровня
модуля `//!`, описывающий источник спецификации, которую покрывает тест (номер секции спецификации
языка + номер RFC). Если какой-то тест не ссылается ни на какую секцию спецификации, это означает,
что у этого кода нет спецификации — он не должен существовать.

```rust
//! Тесты литералов — на основе спецификации языка §2.6
//!
//! §2.6.1: целые числа Decimal, Octal(0o), Hex(0x), Binary(0b)
//! §2.6.2: числа с плавающей точкой (с десятичной точкой и экспонентой)
//! §2.6.3: строки (escape-последовательности \\nrt'"\\, \\x, \\u{})
//! RFC-012: интерполяция F-String
```

**Почему обязательна ссылка на спецификацию?** Потому что ожидаемые значения теста берутся из
спецификации, а не из «текущего вывода кода». Если однажды код изменит вывод и тест будет обновлён
вслед за ним, тест ничего не защищает. Только привязанный к спецификации тест может отличить
«преднамеренное breaking change» от «случайной регрессии».

**Правило 2.2**: импорты `use` в тестовом модуле должны быть точными до конкретных типов/функций,
запрещён glob-импорт `use super::*`.

```rust
// 🟢 Хорошо — точные импорты
use crate::frontend::core::lexer::{tokenize, TokenKind};
use crate::frontend::core::parser::{ParserState, ParseError};

// 🔴 Мусор — другим непонятно, что именно вы тестируете
use super::*;
```

### Стандарты именования

**Правило 3.1**: формат имени тестовой функции — `test_<что>_<сценарий>`, всё в нижнем регистре с
подчёркиваниями.

```rust
#[test]
fn test_tokenize_empty_string() { /* ... */ }
#[test]
fn test_parse_int_overflow() { /* ... */ }
#[test]
fn test_typecheck_fn_return_mismatch() { /* ... */ }
```

**Правило 3.2**: имя тестовой функции должно быть самодостаточным. Прочитав имя, должно быть
понятно, что тестируется и что ожидается. Запрещено использование числовых индексов.

```rust
// 🟢 Хорошо
fn test_skip_semicolon_success() { /* ... */ }
fn test_skip_semicolon_failure_when_identifier() { /* ... */ }

// 🔴 Мусор — совершенно непонятно, что тестируется
fn test_skip_1() { /* ... */ }
fn test_skip_2() { /* ... */ }
```

**Правило 3.3**: вспомогательные функции не требуют префикса `test_`, их имена должны описывать
назначение глаголом или существительным.

```rust
fn parse_expr(source: &str) -> Expr { /* ... */ }
fn tokenize_single(source: &str) -> Token { /* ... */ }
fn setup_parser_with_tokens(tokens: &[Token]) -> ParserState { /* ... */ }
```

### Стандарт структуры теста (Arrange-Act-Assert)

**Правило 4.1**: каждая тестовая функция должна следовать трёхчастной структуре: подготовка
(Arrange) → выполнение (Act) → проверка (Assert), части разделяются пустыми строками.

```rust
#[test]
fn test_parse_binary_addition() {
    // Arrange
    let source = "1 + 2";

    // Act
    let expr = parse_expr(source);

    // Assert
    assert!(matches!(expr, Expr::Binary { op: BinOp::Add, .. }));
}
```

**Правило 4.2**: для простых тестов (один вызов + одно утверждение) можно не писать
комментарии-разделители, но объём логического кода не должен превышать 5 строк. Если строк больше 5,
разделение на три части обязательно.

### Стандарты вспомогательных функций

**Правило 5.1**: повторяющаяся 3 и более раз логика setup должна выноситься во вспомогательную
функцию.

```rust
// 🟢 Хорошо — выделен общий setup
fn with_state<F>(source: &str, mut f: F)
where
    F: FnMut(&mut ParserState<'_>),
{
    let tokens = tokenize(source).unwrap();
    let mut state = ParserState::new(&tokens);
    f(&mut state);
}

#[test]
fn test_current_returns_first_token() {
    with_state("42", |state| {
        let tok = state.current();
        assert_eq!(&tok.unwrap().kind, &TokenKind::IntLiteral(42));
    });
}
```

**Правило 5.2**: `unwrap()` / `expect()` во вспомогательных функциях должны при panic выводить
достаточно контекста. В теле тестовой функции (`#[test] fn ...`) допускается прямой `unwrap()` — при
сбое Rust автоматически печатает номер строки; но при сбое во вспомогательной функции номер строки
указывает на место определения вспомогательной функции, и контекст вызова не виден.

```rust
// 🟢 Хорошо — при сбое вспомогательной функции печатается содержимое исходника
fn run_ok(source: &str) {
    run(source).unwrap_or_else(|e| panic!("Execution failed:\nSource:\n{}\nError:\n{:?}", source, e));
}

// 🔴 Мусор — при сбое не видно, какой исходный файл вызвал проблему
fn run_ok(source: &str) {
    run(source).unwrap();
}
```

**Правило 5.3**: вспомогательные функции следует размещать в верхней части тестового файла сразу
после импортов `use`. Если они разделяются между несколькими тестовыми модулями, их размещают в
`tests/mod.rs` и экспортируют через `pub(crate)`.

### Стиль утверждений

**Правило 6.1**: для сопоставления с вариантом перечисления предпочтительно использовать
`assert!(matches!(...))`, запрещено использовать `if let` + `panic!`.

```rust
// 🟢 Хорошо
assert!(matches!(tokens[0].kind, TokenKind::IntLiteral(42)));

// 🔴 Мусор
if let TokenKind::IntLiteral(v) = tokens[0].kind {
    assert_eq!(v, 42);
} else {
    panic!("Expected IntLiteral");
}
```

**Правило 6.2**: для точного сравнения значений используйте `assert_eq!`, для булевых утверждений —
`assert!`. Запрещено использовать `assert!(a == b)` вместо `assert_eq!(a, b)`.

**Правило 6.3**: все утверждения должны сопровождаться пользовательским сообщением об ошибке, кроме
случаев, когда само утверждение полностью описывает причину сбоя.

```rust
// 🟢 Хорошо — при сбое можно быстро локализовать проблему
assert!(
    state.infix_info().is_some(),
    "infix_info should handle '{op}'"
);

// 🟢 Хорошо — при сбое assert_eq! автоматически печатает разницу значений, дополнительное сообщение не нужно
assert_eq!(error_count, 0);

// 🔴 Мусор — при сбое видно только "assertion failed"
assert!(state.infix_info().is_some());
```

**Правило 6.4**: порядок аргументов утверждения должен быть `assert_eq!(actual, expected)`:
фактическое значение первым, ожидаемое — вторым.

### Список антипаттернов

Ниже приведены запрещённые приёмы и их замены:

| Антипаттерн                                         | Проблема                                                                       | Замена                                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `#[cfg(test)] mod tests { ... }` inline-тесты       | Раздувание исходного файла, размытие границ модулей, трудности с рефакторингом | Тестовый код в отдельном каталоге `tests/`, объявление через `mod tests;` (см. правило 1.4) |
| Тест, подстраивающийся под ошибочное поведение кода | Маскирует отклонения от спецификации, легитимизирует баги                      | Сверяясь со спецификацией, исправлять код, оставляя тест неизменным                         |
| Вывод ожидаемых значений теста из вывода кода       | Тест превращается в «диктофон текущей реализации»                              | Выводить ожидаемые значения из спецификации                                                 |
| Постоянная пометка `#[ignore]`                      | Скрывает гниющие тесты                                                         | Исправить или удалить                                                                       |
| Отладочный вывод через `println!`                   | Загрязняет вывод тестов                                                        | Использовать явные `assert!`                                                                |
| `thread::sleep`                                     | Случайные сбои + медленно                                                      | Использовать механизмы синхронизации или mock                                               |
| Операции с реальной файловой системой в тестах      | Медленно и не воспроизводимо                                                   | Использовать `tempfile`                                                                     |
| Зависимость от порядка выполнения тестов            | Случайные сбои                                                                 | Каждый тест с собственным setup                                                             |
| Тестовая функция длиннее 30 строк логики            | Никто не сможет разобраться                                                    | Разделить тест или вынести во вспомогательную функцию                                       |
| `unwrap()` во вспомогательной функции без контекста | Сложно локализовать                                                            | Использовать `expect("why")` или собственный panic (см. правило 5.2)                        |
| Копипаст setup более 3 раз                          | Высокая стоимость изменений                                                    | Вынести во вспомогательную функцию                                                          |

## Стандарты интеграционных тестов

### Организация тестов

**Правило 7.1**: интеграционные тесты размещаются в каталоге `tests/` в корне проекта. Входной файл
`tests/integration.rs` использует атрибут `#[path]` для подключения подмодулей.

```rust
// tests/integration.rs
#[path = "integration/backends.rs"]
mod backends;
#[path = "integration/codegen.rs"]
mod codegen;
#[path = "integration/execution.rs"]
mod execution;
```

**Правило 7.2**: каждый файл `tests/integration/*.rs` соответствует одной теме тестирования (бэкенды
компилятора, кодогенерация, исполнитель и т. п.); смешивание недопустимо.

**Правило 7.3**: интеграционные тесты должны выполняться через публичный API проекта. В
интеграционных тестах запрещено напрямую обращаться к внутренним модулям `crate::`. Следует
использовать публичный путь `yaoxiang::`.

```rust
// 🟢 Хорошо — через публичный API
use yaoxiang::run;

// 🔴 Мусор — обход границы публичного API
use yaoxiang::middle::codegen::bytecode::BytecodeFile;
```

### Управление тестовыми данными

**Правило 8.1**: в интеграционных тестах предпочтительно использовать inline-строки исходного кода.
Внешние fixture-файлы (в `tests/fixtures/`) используются только при объёме исходного кода свыше 30
строк.

```rust
#[test]
fn test_fibonacci() {
    run_ok(
        r#"
        main = {
            mut a = 0
            mut b = 1
            while a < 100 {
                mut next = a + b
                a = b
                b = next
            }
        }
        "#,
    );
}
```

**Правило 8.2**: файлы fixture должны иметь расширение `.yx`, имя файла должно описывать назначение
теста.

### Принципы E2E-покрытия

**Правило 9.1**: интеграционные тесты для каждой возможности языка должны покрывать три пути:

| Путь       | Описание                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------- |
| Happy path | Корректный ввод даёт ожидаемый вывод                                                        |
| Error path | Некорректный ввод даёт понятное сообщение об ошибке (не panic)                              |
| Boundary   | Граничные значения (пустой ввод, максимальное значение, верхний предел глубины вложенности) |

**Правило 9.2**: интеграционные тесты не должны зависеть от сети, переменных окружения или внешних
сервисов.

## Стандарты бенчмарков

### Правила использования Criterion.rs

**Правило 10.1**: бенчмарки единообразно размещаются в каталоге `benches/`, входной файл —
`benches/lib.rs`. По темам тестирования файлы разделяются.

```
benches/
├── lib.rs              # вход, определяет criterion_group/criterion_main
├── lang_compare/
│   └── fibonacci.rs    # кросс-языковые сравнительные бенчмарки
├── parser.rs           # бенчмарки парсера
└── codegen.rs          # бенчмарки кодогенерации
```

**Правило 10.2**: каждая функция бенчмарка должна содержать комментарий документации модуля `//!` с
описанием цели тестирования и измеряемой метрики.

```rust
//! Бенчмарки производительности интерпретатора YaoXiang
//!
//! Измеряемая метрика: время одной итерации (wall time)
//! Базовая линия: нативная реализация на Rust
```

### Предотвращение оптимизаций компилятора

**Правило 11.1**: во всех бенчмарках выход тестируемого кода должен проходить через
`criterion::black_box`, чтобы компилятор не оптимизировал его удаление.

```rust
use criterion::{black_box, Criterion};

fn bench_parse(c: &mut Criterion) {
    c.bench_function("parse_fib", |b| {
        b.iter(|| {
            let result = parse(black_box(FIB_SOURCE));
            black_box(result)
        })
    });
}
```

**Правило 11.2**: входные данные бенчмарка должны быть `const` или `lazy_static`; их нельзя
генерировать динамически внутри замыкания `iter` — иначе будет измерено суммарное время генерации
данных и тестируемой логики.

### Группировка и именование бенчмарков

**Правило 12.1**: формат имени бенчмарка — `<тестируемый модуль>_<сценарий>`, всё в нижнем регистре
с подчёркиваниями. Совпадает с правилами именования модульных тестов.

**Правило 12.2**: для логической группировки связанных бенчмарков необходимо использовать
`criterion_group!`. Запрещено размещать все бенчмарки в одной группе.

```rust
criterion_group!(parser, bench_parse_expr, bench_parse_stmt);
criterion_group!(codegen, bench_codegen_module, bench_codegen_switch);
criterion_main!(parser, codegen);
```

## Стандарты документационных тестов

### Сценарии использования

**Правило 13.1**: все `pub`-функции, типы и методы должны содержать как минимум один исполняемый
пример кода в комментариях документации. Этот пример выполняется через `cargo test --doc`.

````rust
/// Разбивает строку исходного кода на последовательность токенов.
///
/// ```
/// use yaoxiang::frontend::core::lexer::tokenize;
///
/// let tokens = tokenize("42").unwrap();
/// assert_eq!(tokens.len(), 2); // IntLiteral + Eof
/// ```
pub fn tokenize(source: &str) -> Result<Vec<Token>, LexError> {
    // ...
}
````

**Правило 13.2**: примеры кода в документационных тестах должны компилироваться и успешно проходить
проверки. Запрещено использовать примеры с пометкой `ignore`, если только пример не демонстрирует
ошибку этапа компиляции.

````rust
/// ```ignore
/// // Демонстрация ошибки компиляции — допускается ignore
/// let x: int = "string";
/// ```
````

### Требования к покрытию

**Правило 14.1**: документационные тесты должны покрывать happy path API. Граничные случаи и пути
ошибок покрываются модульными тестами.

**Правило 14.2**: примеры кода в документационных тестах должны быть лаконичными — не более 10
строк. Если пример требует более длинного контекста, значит, в дизайне API есть проблема.

## Стандарты property-тестов

### Сценарии использования

**Правило 15.1**: в следующих сценариях обязательно использование property-тестов (proptest или
quickcheck) вместо ручного написания множества граничных случаев:

| Сценарий                                    | Пример                                 |
| ------------------------------------------- | -------------------------------------- |
| Round-trip парсера                          | `parse(pretty_print(ast)) == ast`      |
| Сериализация/десериализация                 | `deserialize(serialize(data)) == data` |
| Тождества математических операций           | `a + b == b + a`                       |
| Оптимизации компилятора не меняют семантику | `eval(code) == eval(optimize(code))`   |

**Правило 15.2**: property-тесты используют `proptest` в качестве основного фреймворка (уже объявлен
в `dev-dependencies` в `Cargo.toml`).

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn test_roundtrip_serialize_deserialize(value: i64) {
        let serialized = serialize(&value);
        let deserialized: i64 = deserialize(&serialized).unwrap();
        prop_assert_eq!(deserialized, value);
    }
}
```

### Принципы определения свойств

**Правило 16.1**: каждый property-тест должен иметь явное объявление свойства — в комментарии
указывается проверяемый инвариант.

```rust
// Свойство: любой целочисленный литерал после tokenize → tokens_to_string даёт то же значение
proptest! {
    #[test]
    fn test_int_literal_roundtrip(n in any::<i64>()) {
        let source = n.to_string();
        let tokens = tokenize(&source).unwrap();
        // ...
    }
}
```

**Правило 16.2**: если property-тест обнаруживает сбой, необходимо использовать механизм регрессий
`proptest` — добавить входные данные, на которых тест упал, в каталог `proptest-regressions/`. Не
нужно вручную заменять его обычным тестом.

## Требования к покрытию

### Целевые показатели покрытия нового кода

**Правило 17.1**: требования к покрытию тестами для нового кода:

| Тип кода                                               | Покрытие строк | Покрытие ветвей |
| ------------------------------------------------------ | -------------- | --------------- |
| Основные модули компилятора (frontend/middle/backends) | ≥ 85%          | ≥ 80%           |
| Служебные/вспомогательные модули (util)                | ≥ 75%          | ≥ 70%           |
| Модули runtime (vm/runtime)                            | ≥ 80%          | ≥ 75%           |
| Стандартная библиотека (std)                           | ≥ 75%          | ≥ 70%           |
| Обработка ошибок и диагностика                         | ≥ 90%          | ≥ 85%           |

**Правило 17.2**: пути обработки ошибок (все ветки `Err`) должны быть покрыты на 100%. Сообщения об
ошибках, которые видит пользователь, должны быть проверены тестами.

### Контрольный список для ревью PR

**Правило 18.1**: перед отправкой PR автор обязан самостоятельно проверить следующие пункты:

- [ ] `cargo test` проходит полностью
- [ ] `cargo test --doc` проходит полностью
- [ ] `cargo bench` не показывает регрессий производительности (если затронуты горячие пути)
- [ ] Новый код соответствует целевым показателям покрытия
- [ ] Именование тестов соответствует стандартам именования
- [ ] В каждом тестовом файле объявлена соответствующая секция спецификации (правило 2.1)
- [ ] Ожидаемые значения тестов берутся из определения спецификации, а не из «текущего вывода кода»
- [ ] Нет тестов с пометкой `#[ignore]` (если нет комментария с номером issue)
- [ ] Нет бессмысленных `unwrap()` (следует использовать `expect` или собственный panic-сообщение)
- [ ] Сообщение коммита использует тип `:white_check_mark: test:`
- [ ] **Ожидаемые значения тестов не были изменены по причине «поведение кода не соответствует
      спецификации» — изменяется код, а не тест**
- [ ] **Нет inline-тестов** (`#[cfg(test)] mod tests { ... }` должно быть заменено на `mod tests;` +
      отдельные файлы, см. правило 1.4)

**Правило 18.2**: ревьюер обязан отклонить PR, содержащий следующие проблемы:

- Есть только happy path тесты, отсутствуют пути ошибок
- В тестах присутствует `thread::sleep` или зависимость от порядка выполнения
- Скопированный и вставленный тестовый код встречается более 3 раз без вынесения во вспомогательную
  функцию
- Имена тестов не соответствуют стандартам именования
- Существуют тесты с постоянной пометкой `#[ignore]`
- **Тест, подстраивающийся под ошибочное поведение кода** (когда код не соответствует спецификации,
  изменяется тест вместо кода)
- **Тест не объявляет соответствующую секцию спецификации** (см. правило 2.1)
- **Ожидаемые значения теста берутся из вывода кода, а не из определения спецификации** (выведенный
  из кода тест равен отсутствию теста)
- **Присутствуют inline-тесты** (`#[cfg(test)] mod tests { ... }` вместо `mod tests;` + отдельные
  файлы, см. правило 1.4)
- Тест проверяет только «отсутствие panic», но не утверждает конкретное поведение
- Удаление упавшего теста, который выявлял баг в коде (вместо того, чтобы исправить код и увидеть
  зелёный свет)

## Приложения

### A. Краткая справка по командам тестирования

```bash
# Запустить все тесты
cargo test

# Запустить только модульные тесты
cargo test --lib

# Запустить только интеграционные тесты
cargo test --test integration

# Запустить только документационные тесты
cargo test --doc

# Запустить конкретный тест (фильтр по имени)
cargo test test_parse_expr

# Запустить бенчмарки
cargo bench

# Показывать вывод тестов (по умолчанию stdout скрыт)
cargo test -- --nocapture

# Однопоточный запуск (для отладки проблем конкурентности)
cargo test -- --test-threads=1

# Сгенерировать отчёт о покрытии (требуется cargo-llvm-cov)
cargo llvm-cov --html
```

### B. Шаблон сообщения коммита

Коммиты, связанные с тестами, должны следовать шаблону:

```
:white_check_mark: test(<scope>): <краткое описание>

<необязательно: список покрытых сценариев>
```

Пример:

```
:white_check_mark: test(parser): добавить тесты инфиксных операторов парсера Pratt

Покрытые сценарии:
- приоритет арифметических операторов (+, -, *, /, %)
- цепочки операторов сравнения (1 < x < 10)
- короткое замыкание логических операторов
- правоассоциативность оператора присваивания
```

### C. Чек-лист для новых тестовых файлов

При создании нового тестового модуля убедитесь в наличии следующих файлов:

```
# Добавление тестов в src/<module>/
src/<module>/tests/
├── mod.rs          # объявление модуля + общие вспомогательные функции
└── <subject>.rs    # тестовый файл, названный по исходному файлу

# Добавление интеграционного теста в tests/
tests/
├── integration.rs   # обновить: добавить объявление #[path]
└── integration/
    └── <topic>.rs   # новый тестовый файл
```
