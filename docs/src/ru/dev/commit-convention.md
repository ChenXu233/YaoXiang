## Формат коммита

**ОЧЕНЬ ВАЖНО！！！！！！НЕ ЗАБЫВАЙТЕ！！！** Все сообщения коммитов должны соответствовать
следующему формату:

```
:emoji代码: type(scope): 主题（中文）

[可选的主体内容]

[可选的页脚]
```

> ⚠️ **Важно**: Необходимо использовать **emoji-коды** (например, `:sparkles:`) вместо
> непосредственного ввода символов emoji.
>
> **Рекомендуется использовать китайский язык в сообщениях коммитов** для обеспечения единообразия
> коммуникации в команде.

### Составные части

| Часть     | Описание                                                 | Обязательно |
| --------- | -------------------------------------------------------- | ----------- |
| emoji-код | Символ emoji, идентифицирующий тип коммита               | ✅          |
| type      | Тип коммита                                              | ✅          |
| scope     | Область влияния                                          | ✅          |
| subject   | Краткое описание (на китайском, до 50 символов)          | ✅          |
| body      | Подробное описание (необязательно)                       | ❌          |
| footer    | Критические изменения или закрытие задач (необязательно) | ❌          |

## Правила сообщений

### Управление версиями

Номер версии определяется в поле `version` файла `Cargo.toml` в корне проекта:

```toml
[package]
version = "0.7.2"
```

Используется семантическое версионирование `MAJOR.MINOR.PATCH`:

| Тип версии | Описание                                        | Пример        |
| ---------- | ----------------------------------------------- | ------------- |
| **major**  | Крупные обновления, несовместимые изменения API | 0.7.2 → 1.0.0 |
| **minor**  | Новая функциональность, обратно совместимая     | 0.7.2 → 0.8.0 |
| **patch**  | Исправление багов, обратно совместимое          | 0.7.2 → 0.7.3 |

> ⚠️ При выпуске релиза **обновите номер версии в `Cargo.toml` в ветке dev**, после слияния PR в
> main CI автоматически создаст тег и Release. **Не создавайте тег вручную**, иначе CI пропустит
> процесс релиза.

---

## Процесс релиза CI

Релиз выполняется автоматически через GitHub Actions (`dist-release.yml`), процесс выглядит
следующим образом:

```
1. В ветке dev обновите поле version в Cargo.toml
2. cargo build для обновления Cargo.lock
3. Сделайте коммит в формате релиза (см. 🔖 Коммит релиза ниже)
   - commit message должно содержать все изменения с момента предыдущего релиза (т.е. полное содержимое PR)
4. Создайте PR из dev в main
5. Слейте PR в main
6. Автоматическая проверка gate job:
   - Чтение версии из Cargo.toml → "v{version}"
   - Проверка существования данного тега
   - Не существует → запуск полного процесса релиза
   - Уже существует → пропуск (повторный релиз не выполняется)
7. Контрольные проверки: аудит безопасности + fmt/clippy/юнит-тесты/doc test пройдены
8. После прохождения всех проверок: создание и отправка тега
9. Сборка и публикация после тега:
   - Кросс-платформенная сборка cargo-dist (5 платформ: Linux/Windows/macOS) + переупаковка (bin/ + lib/) + wasm + Inno Setup
   - Публикация GitHub Release (body генерируется generate-commit-list.ts); apt-репозиторий публикуется отдельно через GitHub Pages
```

### Ключевые правила

| Правило                                     | Описание                                                                                                                                                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Не создавайте теги вручную**              | Релиз определяется только проверкой gate при push в main; теги, созданные вручную, не запустят релиз (для повторной публикации используйте `workflow_dispatch` в `dist-release.yml` с указанием тега) |
| **Версия обновляется в dev**                | Коммит релиза выполняется в dev и попадает в main через PR                                                                                                                                            |
| **Коммит релиза содержит полный changelog** | commit message должен включать все изменения данного релиза, так как оно является источником описания PR                                                                                              |
| **Не сливайте main обратно в dev**          | После слияния PR dev синхронизируется автоматически, обратное слияние не требуется                                                                                                                    |

## Правила сообщений

### Языковые правила

**Рекомендуется использовать китайский язык в сообщениях коммитов** для обеспечения единообразия
коммуникации в команде.

- Subject на китайском, кратко и ясно
- Body может содержать подробное описание на китайском
- Специальные технические термины можно оставить на английском

### Subject (Тема)

- Используйте китайский язык, кратко и ясно
- Длина не более 50 символов
- Без точки в конце

### Body (Содержание)

- Подробно опишите причину и способ изменений
- Каждая строка не более 72 символов
- Используйте `-` или `*` для маркированных списков

### Footer (Нижний колонтитул)

- **Критические изменения**: начинаются с `BREAKING CHANGE:`
- **Закрытие Issue**: используйте `关闭 #123` или `修复 #456`

## Примеры

### ✨ feat — Новая функциональность

```
:sparkles: feat(parser): 添加闭包语法解析支持

实现闭包表达式解析：
- 支持 |args| body 简写语法
- 支持 move 语义捕获
- 添加闭包类型推断

关闭 #42
```

### 🐛 fix — Исправление бага

```
:bug: fix(repl): 修复多行输入时补全器失效的问题

SessionREPL 在多行模式下未正确注册补全器，
导致 Tab 补全无法触发。

修复 #128
```

### 📝 docs — Обновление документации

```
:memo: docs(design): 更新所有权模型与类型系统规范

同步 RFC-009 和 RFC-011 的最新设计变更。
```

### ♻️ refactor — Рефакторинг

```
:recycle: refactor(typecheck): 分离原语值类型与 Dup 浅拷贝语义

将 MonoType 中的值类型和拷贝语义解耦，
消除 match 分支中的特殊情况。
```

### ⚡️ perf — Оптимизация производительности

```
:zap: perf(types): 优化 const generic 求值性能

为递归求值添加深度限制（默认 128），
避免恶意构造的类型表达式导致栈溢出。
```

### ✅ test — Тестирование

```
:white_check_mark: test(typecheck): 补充 scope VarInfo 可变性测试

覆盖场景：
- 不可变绑定的只读访问
- mut 绑定的可变性追踪
- 跨作用域的可变性传播
```

### 🔧 chore — Разное

```
:wrench: chore(build): bump rand, hashbrown, tempfile, ron, clap

升级 6 个生产依赖至最新稳定版本。
```

### 🚀 ci — Конфигурация CI

```
:rocket: ci: 修复 nightly 构建 Rust 版本过低的问题

将 RUST_TOOLCHAIN 从 1.91.0 更新至 1.96.0，
匹配 Cargo.toml 中的 rust-version 要求。
```

### 💄 style — Форматирование

```
:lipstick: style(frontend): 应用 cargo fmt 格式化

统一函数签名的换行风格。
```

```

## 📦 版本信息

**发布日期:** YYYY-MM-DD

**版本号:** <旧版本> → <新版本>

---

- :sparkles: feat(<scope>): <功能描述>

---

## ♻️ 重构优化

- :recycle: refactor(<scope>): <重构描述>

---

## 🐛 Bug 修复

- :bug: fix(<scope>): <修复描述>

---

## 🔧 其他变更

- :wrench: chore: <变更描述>

---

## 📦 新增文件

- `<文件路径>` - <文件说明>

---



### Требования к релизу

1. **Заголовок сообщения**: должен использовать формат `:bookmark:` + `V<номер_версии>`
2. **Номер версии**: следует семантическому версионированию
3. **Полнота содержимого**: должен содержать описание **всех коммитов** с момента последнего релиза
4. **Классификация по типу**: организовать по типам `feat`, `fix`, `refactor`, `chore` и т.д.
```

Файл `.gitmessage.txt` в корне проекта имеет следующий формат:

```
# emoji代码 type(scope): 主题（中文）

# 页脚（可选）

#
# 发版格式: 🔖 V1.0.0: 发版标题
```

## Часто задаваемые вопросы

### В: Как выбрать тип коммита?

- **feat**: изменения функциональности, видимые пользователю
- **fix**: исправление проблем, о которых сообщили пользователи
- **docs**: README, комментарии и другая документация
- **chore**: обновление зависимостей, конфигурационных файлов
- **refactor**: оптимизация кода без изменения поведения

### В: Когда следует разделять коммиты?

- Каждый коммит делает **только одно дело**
- Связанные функции коммитятся вместе, несвязанные — раздельно
- Следуйте принципу Atomic Commits
