## Формат коммита

**Очень важно！！！！Не забудьте！！！** Все сообщения коммитов должны соответствовать следующему формату:

```
:emoji-код: type(scope): тема (на китайском)

[Необязательное тело]

[Необязательный футер]
```

> ⚠️ **Важно**: Необходимо использовать **emoji-код** (например, `:sparkles:`) вместо прямого ввода emoji-символов.
>
> **Рекомендуется использовать китайский язык для сообщений коммитов**, чтобы обеспечить единообразие коммуникации в команде.

### Составные части

| Часть       | Описание                              | Обязательно |
| ----------- | ------------------------------------- | ----------- |
| emoji-код   | Идентификатор типа коммита            | ✅          |
| type        | Тип коммита                           | ✅          |
| scope       | Область влияния                       | ✅          |
| subject     | Краткое описание (на китайском, ≤50 символов) | ✅ |
| body        | Подробное описание (необязательно)    | ❌          |
| footer      | Breaking changes или закрытые issues (необязательно) | ❌ |

## Управление версиями

### Правила управления версиями

Версия проекта определена в поле `version` файла `Cargo.toml` в корневом каталоге:

```toml
[package]
version = "0.7.2"
```

Используется семантическое версионирование `MAJOR.MINOR.PATCH`:

| Тип версии  | Описание                                  | Пример          |
| ----------- | ----------------------------------------- | --------------- |
| **major**   | Крупное обновление, несовместимые изменения API | 0.7.2 → 1.0.0 |
| **minor**   | Новая функциональность, обратная совместимость | 0.7.2 → 0.8.0 |
| **patch**   | Исправление багов, обратная совместимость | 0.7.2 → 0.7.3 |

> ⚠️ При релизе **обновите номер версии в `Cargo.toml` на ветке dev**,
> после слияния PR в main CI автоматически создаст tag и Release. **Не создавайте теги вручную**, иначе CI пропустит процесс релиза.

---

### CI-процесс релиза

Релиз автоматически выполняется GitHub Actions (`release.yml`). Процесс:

```
1. На ветке dev обновить поле version в Cargo.toml
2. cargo build для обновления Cargo.lock
3. Создать коммит в формате релиза (см. ниже 🔖 Релизный коммит)
   - Сообщение коммита должно содержать ВСЕ изменения с последнего релиза (т.е. полное содержимое PR)
4. Создать PR из dev в main
5. Слить PR в main
6. CI автоматически проверяет:
   - Читает версию из Cargo.toml → "v{version}"
   - Проверяет существование тега
   - Не существует → запускает полный процесс релиза
   - Существует → пропускает (не публикует повторно)
7. CI автоматически выполняет:
   - Параллельно: кроссплатформенная сборка (Linux/Windows/macOS) + аудит безопасности + тесты
   - После успеха: создание тега, упаковка артефактов, публикация GitHub Release
```

### Ключевые правила

| Правило                                  | Описание                                                                   |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| **Не создавать теги вручную**           | CI определяет необходимость релиза по наличию тега; ручное создание тега приведёт к пропуску CI |
| **Версия bump на dev**                  | Релизный коммит создаётся на dev, через PR сливается в main               |
| **Релизный коммит содержит полный changelog** | Сообщение коммита должно содержать все изменения релиза, так как оно служит описанием PR |
| **Не сливать main обратно в dev**       | После слияния PR dev синхронизируется автоматически, обратный merge не нужен |

## Правила сообщений

### Языковые правила

**Рекомендуется использовать китайский язык для сообщений коммитов**, чтобы обеспечить единообразие коммуникации в команде.

- Subject на китайском, кратко и понятно
- Body на китайском с подробным описанием
- Специальные технические термины можно оставить на английском

### Subject (Тема)

- На китайском, кратко и понятно
- Не более 50 символов
- Без точки в конце

### Body (Тело)

- Подробное описание причин и способа изменений
- Каждая строка не более 72 символов
- Использовать - или * для списков

### Footer (Футер)

- **Breaking changes**: начинается с `BREAKING CHANGE:`
- **Закрытие Issue**: использовать `关闭 #123` или `修复 #456`

## Примеры

### ✨ feat — Новая функциональность

```
:sparkles: feat(parser): 添加闭包语法解析支持

实现闭包表达式解析：
- 支持 |args| body 简写语法
- 支持 move 语义捕获
- 添加闭包类型推断

关闭 #42
```

### 🐛 fix — Исправление бага

```
:bug: fix(repl): 修复多行输入时补全器失效的问题

SessionREPL 在多行模式下未正确注册补全器，
导致 Tab 补全无法触发。

修复 #128
```

### 📝 docs — Обновление документации

```
:memo: docs(design): 更新所有权模型与类型系统规范

同步 RFC-009 和 RFC-011 的最新设计变更。
```

### ♻️ refactor — Рефакторинг

```
:recycle: refactor(typecheck): 分离原语值类型与 Dup 浅拷贝语义

将 MonoType 中的值类型和拷贝语义解耦，
消除 match 分支中的特殊情况。
```

### ⚡️ perf — Оптимизация производительности

```
:zap: perf(types): 优化 const generic 求值性能

为递归求值添加深度限制（默认 128），
避免恶意构造的类型表达式导致栈溢出。
```

### ✅ test — Тестирование

```
:white_check_mark: test(typecheck): 补充 scope VarInfo 可变性测试

覆盖场景：
- 不可变绑定的只读访问
- mut 绑定的可变性追踪
- 跨作用域的可变性传播
```

### 🔧 chore — Разное

```
:wrench: chore(build): bump rand, hashbrown, tempfile, ron, clap

升级 6 个生产依赖至最新稳定版本。
```

### 🚀 ci — Конфигурация CI

```
:rocket: ci: 修复 nightly 构建 Rust 版本过低的问题

将 RUST_TOOLCHAIN 从 1.91.0 更新至 1.96.0，
匹配 Cargo.toml 中的 rust-version 要求。
```

### 💄 style — Форматирование

```
:lipstick: style(frontend): 应用 cargo fmt 格式化

统一函数签名的换行风格。
```

## 🔖 Релизный коммит

Когда коммит является **релизом (Release)**, необходимо следовать следующим правилам:

### Формат релизного коммита

```
:bookmark: V<номер-версии>: <заголовок-релиза>

## 📦 Информация о версии

**Дата выпуска:** YYYY-MM-DD

**Номер версии:** <старая-версия> → <новая-версия>

---

## ✨ Новая функциональность

### <модуль функциональности>
- :sparkles: feat(<scope>): <описание функции>

---

## ♻️ Рефакторинг и оптимизация

- :recycle: refactor(<scope>): <описание рефакторинга>

---

## 🐛 Исправления багов

- :bug: fix(<scope>): <описание исправления>

---

## 🔧 Другие изменения

- :wrench: chore: <описание изменения>

---

## 📦 Новые файлы

- `<путь-к-файлу>` - <описание файла>

---

```

### Требования к релизу

1. **Заголовок сообщения**: обязательно использовать `:bookmark:` + `V<номер-версии>`
2. **Номер версии**: соответствует семантическому версионированию
3. **Полнота содержимого**: необходимо включить описания **всех коммитов** с последнего релиза
4. **Классификация по типам**:整理 по типам `feat`, `fix`, `refactor`, `chore` и т.д.

```

## Часто задаваемые вопросы

### Q: Как выбрать тип коммита?

- **feat**: Изменения функциональности, видимые пользователю
- **fix**: Исправление проблем, о которых сообщили пользователи
- **docs**: README, комментарии и другая документация
- **chore**: Обновление зависимостей, конфигурационные файлы
- **refactor**: Оптимизация кода без изменения поведения

### Q: Когда следует разделять коммиты?

- Каждый коммит должен делать **только одно дело**
- Связанная функциональность коммитится вместе, несвязанная — отдельно
- Следуйте принципу Atomic Commits
