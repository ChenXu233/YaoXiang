# Warning Codes

This page is generated by `scripts/docs/gen-error-code-docs.py` from the `define_codes!` registry in
`src/util/diagnostic/codes/` and `locales/zh.json`. Do not edit it manually. To change the wording,
edit `locales/*.json`; to change the code table, edit `define_codes!`, then rerun
`python scripts/docs/gen-error-code-docs.py`.

Warning codes start with `W` and indicate potential problems in the code; their default emission
level is `warn`, which does not prevent compilation. Exception: `W1090` has an emission level of
`error` (the same-code promotion to E under the user ruling dated 2026-10-13; see its entry), and
triggering it counts toward error_count, changes the exit code, and prevents compilation. The
current registry contains **12** warning codes; for the complete index, see the
[Error Code index](../error-code/index.md).

## Configuration

You can configure dead-code warning behavior through `yaoxiang.toml`:

```toml
[lint]
# Dead-code warning level: off | warn | deny
dead-code = "warn"
```

- `off`: Disable the warning
- `warn`: Display the warning (default)
- `deny`: Treat the warning as an error and prevent compilation

### W1006: Local module shadows dependency package

- **Category**: `Warning`
- **span Exemption**: No
- **Template**: `Local module '{module}' shadows dependency package '{dependency}'`
- **Help**: Local modules have the highest resolution priority (RFC-014): './src/{module}' overrides
  the dependency package '{dependency}' in .yaoxiang/vendor/. If this shadowing is unintended,
  rename the local module; use --deny-shadowing to promote it to an error.
- **Emission Point**: `src/driver/arms.rs:676`, `src/util/diagnostic/command.rs:87`

### W1007: Module import cycle

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Module import cycle {cycle}: the initialization order within the cycle cannot be determined; ordering within the cycle follows only a deterministic convention based on lexicographic path order (not a semantic guarantee)`
- **Help**: The initialization order is determined by the topological order of `use` dependencies.
  Ordering within a cycle follows only the deterministic convention of “lexicographic ordering of
  paths within the cycle”; it is not a semantic guarantee. Breaking the cycle (moving one `use` on
  the cycle out of it, or changing it to deferred evaluation in a function body) makes the
  initialization order determinable. Division of responsibility with E3019: E3019 detects
  initialization cycles between top-level bindings within a unit, whereas this code detects import
  cycles between modules.
- **Emission Point**: `src/driver/arms.rs:1836`

### W1082: Ownership analysis downgraded

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Ownership analysis downgraded: this compilation has no function body checker (the type ledger and call-site ownership table are missing), so ownership decisions use an empty ledger and borrow conflicts are not detected`
- **Help**: This is a defect in the compiler's internal stage contract, not an error in your
  program: at runtime, the ownership layer cannot obtain the type ledger and call-site ownership
  table provided by the function body checker, so it allows everything through as though nothing
  conflicts—borrow conflict checking is skipped entirely. Please report this diagnostic, together
  with a minimal reproducer, as an issue.
- **Emission Point**: `src/frontend/core/sema/checker.rs:1267`

### W1090: Obligation produced without a consumer

- **Category**: `Warning`
- **span Exemption**: Yes
- **Template**: `Obligation field \`{field}\` was produced in {file} but never consumed: {detail}`
- **Help**: This is a defect in the compiler's internal stage contract, not an error in your
  program: an obligation field produced by one stage is not read by the next stage, so the effect of
  the obligation may have been silently discarded. Please report this diagnostic, together with the
  field name and file path, as an issue, and attach a minimal reproducer. This code belongs to the
  **W family** (code prefix W), but its **emission level is error**: under the user ruling dated
  2026-10-13 (WBS 4.3.2, the final state of RFC-039 D5), the **same code was promoted to E**—no new
  E code is added (using two codes for the same fact would create parallel representations), and the
  emission level is determined by the explicit severity; triggering it counts toward error_count and
  changes the exit code. Note: healthy programs produce zero emissions (no warning is reported when
  every obligation has a delivery marker), so this promotion affects the build only when the defect
  actually occurs.
- **Emission Point**: `src/driver/obligations.rs:105`, `src/driver/obligations.rs:535`

## Differences from Error Codes

- **Errors (`E` prefix)**: Prevent compilation and must be fixed.
- **Warnings (`W` prefix)**: Indicate potential problems; the default emission level is warn, and
  they can optionally be fixed. Exception: `W1090` has an emission level of error; triggering it
  counts toward error_count, changes the exit code, prevents compilation, and requires a fix (see
  its entry).

## Dead-Code Warning Criteria

`W1001`–`W1005` report **unused private** (non-`pub`) functions / types / variables / methods. A
`pub` declaration is part of the external interface, and the compiler has no way of knowing whether
an external consumer exists, so these warnings never trigger (decision B for #321). If you see an
“unused” warning, remove the corresponding `pub` to eliminate it; conversely, keep `pub` on
declarations that need to be called externally.
