# Warning Codes

This page is generated by `scripts/docs/gen-error-code-docs.py` from the `define_codes!` registry
under `src/util/diagnostic/codes/` and `locales/zh.json`. Do not edit it manually. To change the
wording, edit `locales/*.json`; to change the code table, edit `define_codes!`, then rerun
`python scripts/docs/gen-error-code-docs.py`.

Warning codes start with `W` and indicate potential problems in the code. Their default emission
severity is `warn`, which does not prevent compilation. The exception is `W1090`, whose emission
severity is `error` (the same code was promoted to E by the user ruling on 2026-10-13; see its entry
for details). When triggered, it counts toward `error_count`, changes the exit code, and prevents
compilation. The current registry contains **12** warning codes; see the
[Error Code Index](../error-code/index.md) for the complete list.

## Configuration

The behavior of dead-code warnings can be configured in `yaoxiang.toml`:

```toml
[lint]
# Dead-code warning level: off | warn | deny
dead-code = "warn"
```

- `off`: Disable the warning
- `warn`: Show the warning (default)
- `deny`: Treat the warning as an error and prevent compilation

## Detailed Descriptions

### W1001: Unused private function

- **Category**: `Warning`
- **span Exemption**: No
- **Template**: `Unused function: '{name}'`
- **Help**: The function is never referenced; consider removing it or adding a call. This warning is
  not emitted when the function is referenced by another file in the package.
- **Emission point**: `src/frontend/core/typecheck/passes/dead_code.rs:901`

### W1006: Local module shadows dependency package

- **Category**: `Warning`
- **span Exemption**: No
- **Template**: `Local module '{module}' shadows dependency package '{dependency}'`
- **Help**: Local module resolution has the highest precedence (RFC-014): `'./src/{module}'`
  overrides the dependency package '{dependency}' in .yaoxiang/vendor/. If the shadowing was
  unintended, rename the local module; you can use --deny-shadowing to promote it to an error.
- **Emission point**: `src/driver/arms.rs:660`, `src/util/diagnostic/command.rs:78`

### W1007: Module import cycle

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Module import cycle {cycle}: initialization order within the cycle cannot be determined; relative ordering within the cycle follows only a deterministic convention based on lexicographic path order (not a semantic guarantee)`
- **Help**: Initialization order is determined by the topological order of use dependencies. Within
  a cycle, the only deterministic convention for relative order is the lexicographic order of paths
  within the cycle; this is not a semantic guarantee. Breaking the cycle (moving one use in the
  cycle out of the cycle, or changing it to deferred evaluation in a function body) allows the
  initialization order to be determined. Division of responsibility with E3019: E3019 detects an
  initialization cycle among top-level bindings within a unit, whereas this code detects an import
  cycle between modules.
- **Emission point**: `src/driver/arms.rs:1759`

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `{count} termination measure obligation(s) could not be determined (SMT solver unavailable)`
- **Help**: Install the Z3 solver and re-run the check to obtain a termination decision.
  “Undetermined” does not mean “non-terminating,” but the obligation's decision was skipped.
- **Emission point**: `src/frontend/core/typecheck/checker.rs:1089`

### W1082: Ownership analysis downgraded

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Ownership analysis downgraded: this compilation has no function-body checker (the type ledger and call-site ownership table are missing), so ownership decisions use an empty ledger and borrow conflicts are not detected`
- **Help**: This is a flaw in the compiler's internal stage contract, not an error in your program:
  at runtime, the ownership layer cannot obtain the type ledger and call-site ownership table
  provided by the function-body checker, so it lets everything through as though nothing
  conflicts—the entire borrow-conflict check is skipped. Please report this diagnostic, together
  with a minimal reproducer, as an issue.
- **Emission point**: `src/frontend/core/typecheck/checker.rs:1175`

### W1090: Obligation produced but no consumer

- **Category**: `Warning`
- **span Exemption**: Yes
- **Template**: `Obligation field \`{field}\` has been produced in {file} but has never been
  consumed: {detail}`
- **Help**: This is a flaw in the compiler's internal stage contract, not an error in your program:
  an obligation field produced by one stage is never read by the next stage, so the effect of the
  obligation may have been silently discarded. Please report this diagnostic, together with the
  field name and file path, as an issue, and include a minimal reproducer. This code belongs to the
  **W family** (code prefix W), but its **emission severity is error**: the user ruling of
  2026-10-13 (WBS 4.3.2, the final state of RFC-039 D5) **promoted the same code to E**—no new E
  code was added (the same fact is represented in parallel by two codes), and the emission severity
  is determined by the explicit severity. When triggered, it counts toward `error_count` and changes
  the exit code. Note: healthy programs emit it zero times (it is not reported when all obligations
  have delivery markers), so the promotion affects the build result only when this defect actually
  occurs.
- **Emission point**: `src/driver/obligations.rs:105`, `src/driver/obligations.rs:535`

## Warning Severity Levels

| Level  | Effect                                                |
| ------ | ----------------------------------------------------- |

## Differences from Error Codes

- **Error (`E` prefix)**: Prevents compilation and must be fixed.
- **Warning (`W` prefix)**: Indicates a potential problem; the default emission severity is `warn`,
  and you can choose whether to fix it. The exception is `W1090`, whose emission severity is
  `error`. When triggered, it counts toward `error_count`, changes the exit code, prevents
  compilation, and must be fixed (see its entry for details).

## Criteria for Dead-Code Warnings

`W1001`–`W1005` report **unused private** (non-`pub`) functions / types / variables / methods. A
`pub` declaration is an external interface, and the compiler has no way of knowing whether an
external consumer exists, so it never triggers these warnings (decision B in #321). If you see an
“unused” warning, remove the corresponding `pub` to eliminate it; conversely, keep `pub` on
declarations that need to be called from outside.
