# Warning Codes

This page is generated by `scripts/docs/gen-error-code-docs.py` from the `define_codes!` registry in
`src/util/diagnostic/codes/` and `locales/zh.json`. Do not edit it manually. To change the wording,
edit `locales/*.json`; to change the code table, edit `define_codes!`, and then rerun
`python scripts/docs/gen-error-code-docs.py`.

Warning codes start with `W` and indicate potential problems in the code. Their default emission
level is `warn`, which does not prevent compilation. The exception is `W1090`, whose emission level
is `error` (the same-code promotion to E was ruled by the user on 2026-10-13; see its entry for
details). When triggered, it counts toward `error_count`, changes the exit code, and prevents
compilation. The current registry contains **12** warning codes in total. For the complete index,
see the [error code home page](../error-code/index.md).

## Configuration

The behavior of dead-code warnings can be configured in `yaoxiang.toml`:

```toml
[lint]
# Dead-code warning level: off | warn | deny
dead-code = "warn"
```

- `off`: Disable the warning
- `warn`: Display the warning (default)
- `deny`: Treat the warning as an error and prevent compilation

### W1006: Local Module Shadows Dependency Package

- **Category**: `Warning`
- **span Exemption**: No
- **Template**: `Local module '{module}' shadows dependency package '{dependency}'`
- **Help**: Local module resolution has the highest priority (RFC-014): `'./src/{module}'` overrides
  the dependency package `'{dependency}'` in `.yaoxiang/vendor/`. If the shadowing is unintended,
  rename the local module; use `--deny-shadowing` to promote it to an error.
- **Emission Points**: `src/driver/arms.rs:667`, `src/util/diagnostic/command.rs:78`

### W1007: Module Import Cycle

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Module import cycle {cycle}: initialization order within the cycle cannot be determined; ordering within the cycle follows only the deterministic convention of lexicographic path order (not a semantic guarantee)`
- **Help**: Initialization order is determined by the topological order of use dependencies.
  Ordering within a cycle follows only the deterministic convention of “lexicographic order of paths
  within the cycle,” which is not a semantic guarantee. Breaking the cycle, either by moving one use
  dependency out of the cycle or by switching to deferred evaluation in a function body, makes the
  initialization order determinable. Division of labor with E3019: E3019 detects initialization
  cycles among top-level bindings within a unit, whereas this code detects import cycles between
  modules.
- **Emission Points**: `src/driver/arms.rs:1799`

### W1082: Ownership Analysis Downgrade

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Ownership analysis downgrade: this compilation has no function-body checker (the type ledger and call-site ownership table are missing), so ownership is determined using an empty ledger and borrow conflicts are not detected`
- **Help**: This is a defect in the compiler's internal stage contract, not an error in your
  program: at runtime, the ownership layer cannot access the type ledger and call-site ownership
  table provided by the function-body checker, so it allows everything through as if nothing
  conflicts—the borrow-conflict check is skipped entirely. Please report this diagnostic together
  with a minimal reproducer as an issue.
- **Emission Points**: `src/frontend/core/typecheck/checker.rs:1176`

### W1090: Obligation Produced but Not Consumed

- **Category**: `Warning`
- **span Exemption**: Yes
- **Template**: `Obligation field \`{field}\` was produced in {file} but never consumed: {detail}`
- **Help**: This is a defect in the compiler's internal stage contract, not an error in your
  program: an obligation field produced by one stage is not read by the next stage, so the effect of
  the obligation may have been silently discarded. Please report this diagnostic as an issue,
  including the field name and file path, and attach a minimal reproducer. This code belongs to the
  **W family** (code prefix `W`), but its **emission level is `error`**: the user ruling of
  2026-10-13 (WBS 4.3.2, final state of RFC-039 D5) called for **promoting the same code to E**
  without adding a new E code (using two codes for the same fact would be parallel representations).
  Its emission level is determined by the explicit severity; when triggered, it counts toward
  `error_count`, changes the exit code, and prevents compilation. Note that healthy programs produce
  zero emissions (no warning is emitted when every obligation has a delivery marker), so the
  promotion affects the build result only when the defect actually occurs.
- **Emission Points**: `src/driver/obligations.rs:105`, `src/driver/obligations.rs:535`

## Difference from Error Codes

- **Errors (`E` prefix)**: Prevent compilation and must be fixed.
- **Warnings (`W` prefix)**: Indicate potential problems. Their default emission level is `warn`,
  and they may be fixed as desired. The exception is `W1090`, whose emission level is `error`. When
  triggered, it counts toward `error_count`, changes the exit code, prevents compilation, and must
  be fixed (see its entry for details).

## Dead-Code Warning Criteria

`W1001`–`W1005` report **unused private** functions, types, variables, and methods, meaning
declarations that are not `pub`. A `pub` declaration is a public interface, and the compiler cannot
know whether external consumers exist, so these warnings are never emitted for `pub` declarations
(as finalized by decision B of #321). If you see an “unused” warning, remove the corresponding `pub`
to suppress it. Conversely, keep `pub` on declarations that need to be called externally.
