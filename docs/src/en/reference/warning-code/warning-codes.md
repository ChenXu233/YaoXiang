# Warning Codes

This page is generated by `scripts/docs/gen-error-code-docs.py` from the `define_codes!` registry in
`src/util/diagnostic/codes/` and `locales/zh.json`. Do not edit it manually. To change the wording,
edit `locales/*.json`; to change the code table, edit `define_codes!`; then rerun
`python scripts/docs/gen-error-code-docs.py`.

Warning codes start with `W` and indicate potential problems in the code. Their default emission
level is `warn`, which does not prevent compilation. Exception: `W1090` has an emission level of
`error` (the same code was promoted to E by the user ruling of 2026-10-13; see its entry for
details). When triggered, it counts toward `error_count`, changes the exit code, and prevents
compilation. The current registry contains **12** warning codes. For the complete index, see the
[Error Code Home](../error-code/index.md).

## Configuration

The behavior of dead-code warnings can be configured in `yaoxiang.toml`:

```toml
[lint]
# Dead-code warning level: off | warn | deny
dead-code = "warn"
```

- `off`: Disable warnings
- `warn`: Display warnings (default)
- `deny`: Treat warnings as errors and prevent compilation

### W1006: Local module shadows dependency package

- **Category**: `Warning`
- **span Exemption**: No
- **Template**: `Local module '{module}' shadows dependency package '{dependency}'`
- **Help**: Local modules have the highest resolution priority (RFC-014): './src/{module}' overrides
  the dependency package '{dependency}' in .yaoxiang/vendor/. If the shadowing is unintended, rename
  the local module; use --deny-shadowing to promote it to an error.
- **Emission Point**: `src/driver/arms.rs:667`, `src/util/diagnostic/command.rs:78`

### W1007: Module import cycle

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Module import cycle {cycle}: initialization order within the cycle cannot be determined; ordering within the cycle follows only a deterministic convention based on lexicographic path order (not a semantic guarantee)`
- **Help**: The initialization order is determined by the topological order of `use` dependencies;
  ordering within a cycle follows only the deterministic convention of “lexicographic order of paths
  within the cycle” and is not a semantic guarantee. Breaking the cycle (moving one `use` in the
  cycle out of the cycle, or changing it to deferred evaluation in a function body) makes the
  initialization order determinable. Division of labor with E3019: E3019 detects an initialization
  cycle between top-level bindings within a unit, whereas this code detects an import cycle between
  modules.
- **Emission Point**: `src/driver/arms.rs:1799`

### W1082: Ownership analysis downgraded

- **Category**: `Warning`
- **span Exemption**: No
- **Template**:
  `Ownership analysis downgraded: this compilation had no function-body checker (the type ledger and call-site ownership table are missing), so ownership decisions were made using an empty ledger and borrow conflicts were not detected`
- **Help**: This is a defect in the compiler's internal stage contract, not a mistake in your
  program: at runtime, the ownership layer cannot obtain the type ledger and call-site ownership
  table supplied by the function-body checker, and therefore allows the program through on a
  “nothing conflicts” basis—skipping borrow-conflict checking altogether. Please report this
  diagnostic together with a minimal reproducer as an issue.
- **Emission Point**: `src/frontend/core/typecheck/checker.rs:1231`

### W1090: Obligation produced but has no consumer

- **Category**: `Warning`
- **span Exemption**: Yes
- **Template**: `Obligation field \`{field}\` was produced in {file} but never consumed: {detail}`
- **Help**: This is a defect in the compiler's internal stage contract, not a mistake in your
  program: an obligation field produced by one stage is not read by the next stage, so the
  obligation's effect may have been silently discarded. Please report this diagnostic together with
  the field name and file path as an issue and include a minimal reproducer. This code belongs to
  the **W family** (code prefix W), but its **emission level is error**: under the user ruling of
  2026-10-13 (WBS 4.3.2, final state of RFC-039 D5), the **same code is promoted to E**—no new E
  code is introduced (two codes for the same fact would be parallel representations)—and the
  emission level is determined by the explicit severity. When triggered, it counts toward
  `error_count` and changes the exit code. Note: healthy programs emit nothing (no diagnostic is
  emitted when every obligation has a delivery marker), so this promotion affects the build result
  only when the defect actually occurs.
- **Emission Point**: `src/driver/obligations.rs:105`, `src/driver/obligations.rs:535`

## Differences from Error Codes

- **Error (`E` prefix)**: Prevents compilation and must be fixed.
- **Warning (`W` prefix)**: Indicates a potential problem; the default emission level is `warn`, and
  you can choose to fix it. Exception: `W1090` has an emission level of `error`; when triggered, it
  counts toward `error_count`, changes the exit code, prevents compilation, and must be fixed (see
  its entry for details).

## Dead-Code Warning Criteria

`W1001`–`W1005` report **unused private** (non-`pub`) functions / types / variables / methods. A
`pub` declaration is an external interface, and the compiler has no way of knowing whether an
external consumer exists, so these warnings are never triggered (#321, finalized as B). If you see
an “unused” warning, remove the corresponding `pub` to eliminate it; conversely, retain `pub` for
declarations that need to be called externally.
