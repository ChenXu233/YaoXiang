# RFC-039: Compiler Architecture Refactoring

## Summary

This RFC proposes an architecture refactoring for the YaoXiang compiler (`src/` 160,002 lines / 509
`.rs` files): redrawing boundaries along a **four-layer model** (Orchestration / Frontend / IR /
Execution), establishing an **exhaustible compilation stage contract** and an **obligations
ledger**, and providing a matching set of **equivalence criteria** and **anti-regression gates**.

The detailed design is placed in nine companion documents under `docs/src/dev/architecture/`. This
RFC is responsible only for: the problem, root cause, four-layer model, acceptance criteria grading,
and execution stage sequence. **Reviewing this RFC alone is sufficient to decide whether to approve
the project; the companion documents are the construction blueprints after approval.**

## Motivation

### One: Boundaries exist, but have no enforcement

The directory-level layering (`frontend` / `middle` / `backends`) is clear. But **boundaries exist
only in people's self-awareness, with no mechanism to ensure they are not eroded**. Three direct
consequences.

#### 1.1 Compilation stages are wired manually across five entry points, producing 11 behavioral inconsistencies

| Stage                       | Single-file `run` | Multi-file `run` | `check` | LSP (in project) | LSP (single file) |
| --------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing            | yes               | yes              | yes     | yes              | yes               |
| typecheck                   | yes               | yes              | yes     | yes              | yes               |
| **proof_execution**         | **yes**           | **no**           | **no**  | **no**           | **no**            |
| dead code analysis          | yes               | no               | yes     | no               | no                |
| W1006 shadowing diagnostics | no                | no               | yes     | no               | no                |
| monomorphization            | yes               | no               | no      | no               | no                |
| IR generation / linking     | yes               | yes              | no      | no               | no                |

The five entry points: `src/frontend/pipeline.rs:141-227` (single file, 5 stages at `149` / `161` /
`173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `src/lib.rs`'s `run_file:140` /
`run_project:154`.

The most severe cell causes a **correctness vulnerability**. Proof function constraints like
`x: Sorted(3)` **silently pass** under the multi-file, check, and LSP paths. The evidence chain (all
verifiable):

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** place in the entire
   repository that constructs a non-empty `proof_calls`, with the semantics "this constraint
   requires executing a proof function".
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches handling `Unproven`:
   `5164` / `5306` / `5420` are `if calls.is_empty()` → push hard error; `5179` / `5318` / `5448`
   are `ctx.proof_calls.extend(...)` → **produces no diagnostics**. The comment at `5165` literally
   states "Unproven → compile error, no degradation, no silent pass… silent pass must not be
   revived".
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is **only** read in the entire repository at
   `src/frontend/pipeline.rs:187`.
4. The four entry points in `orchestrator.rs` **all do not read this field**.

That is: invariants the code itself declares are broken by architecture, not logic. The existence of
`compile_embedded_module` (`orchestrator.rs:1374`) means **the refinement obligations of embedded
std modules themselves also take this discarding path**.

**No test can catch it**: the 27 tests in `tests/integration/multifile.rs` have zero hits on
`Sorted` / `proof` / `refin`; RFC-027's unit tests directly call `check_module` and assert
"`proof_calls` is non-empty", **stopping right before the pipeline** — they verify "filled", but the
bug is "consumer end doesn't read".

#### 1.2 Module boundaries can be bypassed without trace

`src/frontend/core/typecheck/checker.rs:5618` is `include!("checker/semantic_tokens.rs");` — **the
only `include!` in the entire repository**. It splices 1547 lines of text into the `checker` module.
The file **is not declared as any module** (`grep 'mod semantic_tokens'` yields zero hits across the
repo), the first line is directly `impl TypeChecker {`, it has no own `use` header, and the
`checker/` directory contains only it as a single file.

Consequences: no module identity, visibility isolation fails, rust-analyzer's jump and symbol search
are ineffective on it, toolchain analysis counts it as part of `checker.rs`. **The true size of the
`checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618 lines shown by directory statistics.

#### 1.3 Test wiring relies on human memory; corruption happens silently

BFS reachability analysis from the two crate roots `src/lib.rs` / `src/main.rs`: **24 files / 2628
lines never participate in compilation**. Of these, 23 files / 1081 lines are true orphans.

| Orphan                                      | Size                 | Content                                                                              |
| ------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------ |
| Entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + `mod.rs` 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                  | 3 files / 14 lines   | all placeholder documentation comments                                               |
| `package/template/tests/`                   | 3 files / 65 lines   | 7 `#[test]`                                                                          |
| `parser/pratt/tests/precedence_inline.rs`   | 95 lines / 6 tests   | hidden in a live directory                                                           |
| `typecheck/passes/tests/overload_inline.rs` | 170 lines / 7 tests  | same as above                                                                        |
| `util/diagnostic/emitter/tests/json.rs`     | 46 lines / 3 tests   | same as above                                                                        |

`cargo test` cannot discover them: tests that have never run do not fail. CI
(`.github/workflows/ci.yml:140`) also has no test count baseline or wiring check.

**Real tests that have never run total 1005 lines / 78**. The lexical layer actually running has
only `fstring.rs` (wired in via `#[path]` attribute bypass).

### Two: Design capability is sufficient

It must be acknowledged at the same time: this project **already has** mature enforcement
mechanisms, they simply have not been extended.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are hard-gated at
build time by `build.rs:19-55` through `tools/code-tables` — parsing the registry, validating
uniqueness and segments, comparing item-by-item against RFC-013's markdown code table, **any
inconsistency directly `panic!` and refuses to compile**. RFC-013 documentation and code therefore
always match.

`src/package/` (76 files / 13,012 lines) is the most complete area: **tests 6,227 lines, accounting
for 47.9%**; 5 of 6 `tests/` directories are correctly wired (the only exception is
`template/tests/`, see Section A). Note that this positive sample holds at the **directory-level
wiring**, not at every file — of 76 `.rs` files, only 7 contain inline `#[cfg(test)]`, 5 contain
`mod tests;`. 5 RFCs match code item by item, multiple "not implemented" fall as explicit errors
rather than silent TODOs (cmake in `build/mod.rs:172-174`, `RegistryDeferred` in `error.rs:74-76`).
`.yxpkg` has five layers of safety protection and all are correct.

**The same repository, the same authors, `package/` gets test directory wiring right, while
`lexer/tests/` has never run once. The difference is not in capability, but in whether someone ran a
check.**

### Three: Empty designs

Three documents under `docs/src/dev/design/check/` describe an architecture that **never existed**:
`CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, `HotReloader` all yield zero hits across the repo; the
`traits/` directory does not exist; the `check_single_module` function does not exist (only lives in
test comments); even the `command.rs` busy-wait referenced in "known limitations" does not exist
(the file has neither `Instant` nor `recv_timeout`).

Cross-file analysis is actually implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, about 2670 lines) — the capability is real, the path is completely
different. **This document writes "possible future designs" as "defects of an implemented system".**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the cleanest physical evidence of "built test skeletons per design, found no corresponding
implementation in the pipeline, and shelved it".

Additionally, `RFC-018` (LLVM AOT, 1037 lines, status accepted) has 0 lines of implementation in
code — the 6 AOT-related hits in `backends/mod.rs` are **all comments**.

## Root Cause Diagnosis

Combining the three symptoms, the root cause is singular:

> **This project treats "design" as a documentation convention, not as an executable constraint.**

| Layer           | Missing enforcement                                              | Existing but un-extended example                                             |
| --------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Stage boundary  | A single decision point for "which stages this compilation ran"  | —                                                                            |
| Module boundary | Forbidding `include!`, limiting `pub(crate)` cross-layer leakage | —                                                                            |
| Cross-reference | Detectability of "field produced but never consumed"             | Error code gate in `build.rs`                                                |
| Test wiring     | Declared directory must have `mod` declarations                  | `src/package/`'s directory-level wiring convention (5 of 6 `tests/` correct) |

This RFC's position is therefore: **turn the three kinds of boundaries — stages, modules,
cross-references — from "documentation conventions" into "compile-time or test-time assertable
facts"**, and **establish a unique stage decision point at the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 Orchestration                                             │
│   Who decides which stages to run, how many times,          │
│   and how failures propagate                                 │
│   Current: pipeline.rs(740) + orchestrator.rs(1528)          │
│         + compiler.rs(267) = 5 entry points, 11 inconsistencies │
│   Target:  single Driver + exhaustible Stage enum            │
│           + Obligations ledger                               │
│   See: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ Compilation Unit
┌───────────────────────────▼─────────────────────────────────┐
│ L2 Frontend                                                  │
│   Lexical analysis, parsing, AST construction                │
│   Current: lexer/(3065) + parser/(6341)                     │
│         hand-rolled lexer + hand-rolled Pratt;              │
│         adding an operator requires changes in 6-7 places   │
│         within L2 + 17 production files downstream          │
│   Target:  lexical converges to a single implementation     │
│           + LALRPOP grammar-driven syntax                    │
│   See: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 Semantic & IR                                             │
│   Type checking, static analysis, IR construction            │
│   Current: typecheck/(29466 production) + ir.rs(905)         │
│         + ir_gen.rs(8448)                                    │
│         3 parallel type representations                      │
│         + 3 parallel operator enums;                         │
│         ir_gen single impl 7952 lines / 116 methods;         │
│         no IR-level validator                                │
│   Target:  unified type representation;                      │
│           IR satisfying SSA construction discipline          │
│   See: ../compiler-architecture/03-type-unification.md         │
│        ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 Execution                                                 │
│   Bytecode generation, interpreter, runtime, stdlib          │
│   Current: codegen/(3436) + bytecode.rs(2422)               │
│         + executor/(2000) + runtime/(1800) + std/(7543)     │
│   Target:  opcode as single source of truth                 │
│           + generation-time gate;                            │
│           execution layer unaware of L1-L3                   │
│   See: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (only consumes AST data, does not call parser); L4 only
depends on the product format of L3.

The known reverse dependencies and parallel definitions inventory is in the routing table C of
`../compiler-architecture/01-routing.md`.

### Equivalence Criteria Grading

**This is the safety net for all refactoring and must be established before any code changes.**
Detailed design in `07-equivalence-oracle.md`.

Core principle: **criteria are graded by refactoring category, because different categories require
different strengths of equivalence.** Using a single criterion (usually "IR snapshot byte-equal") to
cover all refactoring is wrong — some refactoring **inevitably changes IR form**.

| Category | Refactoring content                                             | Criterion type                                                 | Strength  |
| -------- | --------------------------------------------------------------- | -------------------------------------------------------------- | --------- |
| **C1**   | Pure move (split files, change directories, extract submodules) | IR normalized snapshot **zero-diff**                           | Strongest |
| **C2**   | Orchestration change (staging, unified Driver)                  | Same diagnostic set at each entry point + same corpus behavior | Strong    |
| **C3**   | Type representation convergence                                 | Same diagnostic **codes** (message wording will change)        | Strong    |
| **C4**   | IR form change (SSA-ization)                                    | **Behavioral equivalence** + IR structural invariants          | Medium    |
| **C5**   | Frontend paradigm change                                        | AST snapshot + diagnostics + behavior, all three               | Strong    |
| **C6**   | Pure deletion                                                   | No equivalence needed, just confirm no references              | —         |

**The distinction between C1 and C4 is key**: C1 requires IR byte-for-byte equality; C4 acknowledges
that IR will change, and instead uses "program behavior is the same + IR satisfies invariants".
Forcing C4 to use snapshots would induce the team to relax the criteria.

Three-layer criteria:

1. **IR static validator** — dominant use-before-def, jump targets exist, types consistent,
   inner-layer isolation. Far stronger than snapshots, covers defects like "IR self-consistent but
   values wrong" that snapshot tests cannot detect. Must **first run green on existing (non-SSA)
   IR**.
2. **Normalized IR snapshot** — strip `Span`, rename temporaries by occurrence order, relativize
   global slots, sort predecessors. Check in, manual review diff. **Known limitation**:
   normalization wipes out "which register the Nth argument used", so **alone insufficient to cover
   `arg_regs` semantic reshuffling**.
3. **End-to-end corpus diff** — diagnostic lists, exit codes, stdout/stderr item-by-item comparison.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml`** in the `tests/`
> directory (verified 0), therefore the **293** `.yx` corpora in `tests/yaoxiang/` **all take the
> single-file path** (standalone branch of `check_files_with_diagnostics` → `check_single_file` →
> `Pipeline::run`).
>
> **Consequence**: the third-layer criterion **can only verify changes on the single-file path**.
> For the multi-file side (4 entry points of `orchestrator`) and the multi-file behavior of
> types/SSA, **there is currently no corpus coverage**. P4 "Unified Driver" is the largest risk
> point in the entire plan, **the multi-file corpus layer must be unconditionally established in
> P2** (decision D40) — it is P4's only executable behavioral criterion source.

## Implementation Strategy

### Stage Sequence

```
P0  Repository maintenance mechanism     08        ← Establish rules first: 3 prohibitions + D0-D4 procedure
P1  Resurrect orphan tests and fix defects 06 §S1   ← Cheapest, highest return
P2  Establish equivalence criteria baseline 07 all
P3  Fix correctness vulnerability (minimum solution) 02 §Fix
P3.5 Delete pub and auto-binding RFC-029g / #399  ← Ordering constraint D56, must precede P4
P4  Stage contract and unified Driver 02
P5  checker file internal split 09 §P5 supplement
P6  Type representation unification 03
P7  IR SSA-ization 04     } parallel
P8  Frontend paradigm change 05     }
P9  Anti-regression gates (unified script list) 01 + 08
P10 Remaining cleanup and status correction 06 §S2-S6
```

**Core serial constraints (non-swappable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | Three prohibitions constrain every action in P1 — 1.2.x is adding `mod` declarations to `mod.rs`, which is exactly the cause of the `precedence_inline.rs` life-death conflict                                                                                                                                                                                                                      |
| P1 → P2      | Resurrecting tests will change test counts and corpus baselines. Establishing the baseline first will fail after P1                                                                                                                                                                                                                                                                                 |
| P2 → P3      | Vulnerability criteria must be **written red first** to prove the fix is effective. **Narrowing (D51)**: P3's prerequisites are only 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two red criteria); the rest of P2 can run in parallel with P3, but P4 must wait for P2 to fully complete — the hemostasis of correctness vulnerabilities is not blocked by criteria infrastructure construction |
| P3 → P4      | Fix bugs first, then refactor. Reversed order would solidify the bug as "established behavior" via the stage table                                                                                                                                                                                                                                                                                  |
| P3.5 → P4    | RFC-029g (#399)'s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8's respective rewrite targets (role dispatch within `check_project`, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer`+`parser`). Reversed order equals redoing the same batch of deletions on new grammar, new checker layout, new IR (D56)                                                                         |
| P4 → P5      | P5 opens with `include!` → real `mod` (09 §P5 5.1), the subsequent checker split acts on the same file, must proceed consecutively after P4                                                                                                                                                                                                                                                         |
| P5 → P6      | Continuous changes to the same file must be separated, otherwise regression cannot be bisected                                                                                                                                                                                                                                                                                                      |
| P6 → P7 / P8 | If type representation is not first converged, SSA's new IR will grow into a third representation                                                                                                                                                                                                                                                                                                   |
| P7/P8 → P9   | The initial baselines of each gate script (such as `pub(crate)` leakage count) only take final values after P7/P8                                                                                                                                                                                                                                                                                   |
| P7 ∥ P8      | File sets are disjoint, can run in parallel                                                                                                                                                                                                                                                                                                                                                         |

**Why P0 is a separate stage**: P9's CI scripts are **after-the-fact checks** that can only catch
already-written bad code; "should refactor but patched instead" is **before-the-fact judgment** that
only the D0–D4 decision procedure can catch. The two cannot replace each other.

### Definition of Done (DoD) for Each Stage

A stage is considered complete only when all of the following are satisfied:

1. All corresponding "Implementation Strategy" steps in the belonging document are submitted
2. The criterion for that category (C1-C6) in `07-equivalence-oracle.md` **is green in CI**
3. `cargo test` all green, and **test count is not lower than at the start of the stage**
   (preventing "delete tests for green light")
4. `cargo clippy --all --all-features -- -D warnings` clean
5. `python scripts/rfc/check_tracking.py` exit code 0
6. The stage has an independent revert unit — **if a stage cannot be reverted independently, it's
   too large and needs to be split further**
7. For stages touching the compilation pipeline or execution path (P4 / P6 / P7 / P8), the

## Trade-offs

### Advantages

- **Provides a landing point for all subsequent changes**. "Adding an operator requires changing a
  dozen places, with missing ones going unnoticed" cannot be improved by memory, only by routing
  tables + gates.
- **Single root cause**. The three symptoms (stage inconsistency, `include!`, test wiring breakage)
  all stem from "boundaries are conventions not constraints", solvable at once with the same kind of
  mechanism.
- **Non-blocking**. This RFC has zero code changes. The four-layer model is descriptive; after
  adoption, only a portion can be executed.
- **Criteria first**. P2 establishes before any code changes, and the graded design avoids the
  common failure of "snapshot too strict → induce relaxation".

### Disadvantages and Risks

- **Long serial chain**. P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly fully serial; later stages
  must wait for earlier ones.
- **P1 will introduce new bug workload**, and this is the step most easily skipped because "need to
  fix bugs so let's not do it" — but skipping it, the acceptance criteria of all subsequent stages
  are built on false coverage.
- **P4 is the largest single point of risk**: changing 5 entry points at once.
- **P6 has the widest impact surface**: touches common dependencies of parser, formatter, spawn,
  orchestrator.
- **P7's lines will net increase 900-1600 lines, not net decrease**. Splitting introduces
  boilerplate, `verify` 300-600 lines, register allocator 600-1000 lines. **If the success criterion
  at project approval is "code gets shorter", this stage will be judged as failure** — this must be
  aligned at project approval.

## Alternatives

### A. Only split files, do not change paradigm

Split 8448 lines into 10 files of 800 lines.

**Not adopted.** Splitting does not eliminate any root cause: the 6 hand-rolled save/restore points
are still scattered across 10 files, the `arg_regs` semantic reshuffling of `generate_call_expr_ir`
still requires manual reasoning, "adding an operator changes a dozen places" is still a dozen
places. Splitting improves navigation, not correctness.

### B. Only add gates, do not change structure (including line count ratchet)

**Not adopted as the only approach, but it is part of this RFC.** Gates can prevent regression, but
cannot fix the current state — `ir_gen.rs` already has 8448 lines, gates can only freeze it at this
number.

### C. Start over, write a new compiler skeleton

**Not adopted.** `src/package/` proves this team can get complex systems right. The problem is not
capability. Moreover, the existing 293 `.yx` corpora provide a ready source of equivalence criteria;
rewriting from scratch wastes this asset.

### D. Use an existing compiler framework (e.g., LLVM as the only backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) has reserved an abstraction point but
only one implementer. Introducing LLVM is the scope of `RFC-018` (1037 lines of design, 0 lines of
code), and should be **decided independently** — it changes "compile to what" rather than "how to
organize code".

## Appendix: Glossary

| Term                               | Definition                                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Stage**                          | An exhaustible step in a compilation. The set of stages must be an exhaustible enum, not registerable at runtime                     |
| **Orchestration Layer (L1)**       | The layer that decides which stages to run, how many times, and how failures propagate                                               |
| **Frontend Layer (L2)**            | Lexical and syntax, produces AST                                                                                                     |
| **IR Layer (L3)**                  | Type checking, static analysis, IR construction                                                                                      |
| **Execution Layer (L4)**           | Bytecode generation, interpreter, runtime, stdlib                                                                                    |
| **Obligation**                     | A contract item produced by a stage that must be consumed downstream, otherwise the compilation fails                                |
| **Obligations Ledger**             | The container of all obligations, settled uniformly at the end of the stage table                                                    |
| **Orphan**                         | A file never referenced by any `mod` declaration, therefore never participating in compilation                                       |
| **Shell**                          | A file that has been declared, entered the compilation product, but only has documentation comments or unused `use`, zero assertions |
| **Equivalence Oracle**             | An executable check that proves behavior is unchanged before and after refactoring                                                   |
| **C1-C6**                          | Refactoring category grading, determines criterion strength. **C5′ does not exist**                                                  |
| **Separation of Responsibilities** | The only solution to scale problems: a module only takes one kind of responsibility. **No line count / volume gates**                |
| **Decision Registry**              | The "Decision Registry" section of this RFC, the final ruling on all open items                                                      |
