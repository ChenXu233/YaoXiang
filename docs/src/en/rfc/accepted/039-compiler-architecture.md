# RFC-039: Compiler Architecture Refactoring

## Abstract

This RFC proposes an architectural refactoring of the YaoXiang compiler (`src/`, 160,002 lines / 509
`.rs` files): redefine its boundaries around a **four-layer model** (orchestration / frontend /
intermediate representation / execution), establish **exhaustively enumerable compilation-stage
contracts** and an **obligations ledger**, and pair them with a set of **equivalence criteria** and
**regression-prevention gates**.

The detailed design is provided in nine companion documents under `docs/src/dev/architecture/`. This
RFC is responsible only for the problem, root cause, four-layer model, tiered acceptance criteria,
and execution-stage order. **Reviewing this RFC is sufficient to decide whether to initiate the
project; the companion documents are the construction blueprints to be used after initiation.**

## Motivation

### I. Boundaries exist, but have no enforcement

The layering implied by directory names (`frontend` / `middle` / `backends`) is clear. However,
**the boundaries exist only in people's discipline, with no mechanism preventing their erosion**.
This has three direct consequences.

#### 1.1 Compilation stages are manually wired in five entry points, producing 11 behavioral inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (in-project) | LSP (single-file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing           | Yes               | Yes              | Yes     | Yes              | Yes               |
| typecheck                  | Yes               | Yes              | Yes     | Yes              | Yes               |
| **proof_execution**        | **Yes**           | **No**           | **No**  | **No**           | **No**            |
| Dead-code analysis         | Yes               | No               | Yes     | No               | No                |
| W1006 shadowing diagnostic | No                | No               | Yes     | No               | No                |
| Monomorphization           | Yes               | No               | No      | No               | No                |
| IR generation / linking    | Yes               | Yes              | No      | No               | No                |

Five entry points: `src/frontend/pipeline.rs:141-227` (single file; five stages at `149` / `161` /
`173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `run_file:140` /
`run_project:154` in `src/lib.rs`.

The most serious cell in the table exposes a **correctness vulnerability**. A proof-function
constraint such as `x: Sorted(3)` **silently passes** along the multi-file, check, and LSP paths.
The evidence chain, all independently verifiable, is as follows:

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a non-empty `proof_calls`; its semantics are “this constraint requires
   executing a proof function.”
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches that handle `Unproven`:
   `5164` / `5306` / `5420` test `if calls.is_empty()` and then emit a hard error; `5179` / `5318` /
   `5448` execute `ctx.proof_calls.extend(...)` and therefore **produce no diagnostic whatsoever**.
   The comment at `5165` states verbatim: “Unproven → compilation error, no fallback, no silent
   pass… silent pass must not return.”
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is read in **only one place** in the entire
   repository: `src/frontend/pipeline.rs:187`.
4. All four entry points in `orchestrator.rs` **do not read this field**.

In other words, an invariant explicitly declared by the code is violated by the architecture rather
than by its logic. The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means that
**the refinement obligations of the embedded std module itself also traverse this discard path**.

**No test can catch it**: none of the 27 tests in `tests/integration/multifile.rs` match `Sorted` /
`proof` / `refin`; RFC-027's unit tests directly call `check_module` and assert that “`proof_calls`
is non-empty,” **stopping exactly before the pipeline**—they verify that the field is “populated,”
whereas the bug is that the “consumer does not read it.”

#### 1.2 Module boundaries can be bypassed without leaving a trace

`src/frontend/core/typecheck/checker.rs:5618` is `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1,547 lines of text into the `checker`
module. The file **is not declared as any module** (`grep 'mod semantic_tokens'` has zero matches
across the repository); its first line is directly `impl TypeChecker {`, and it has no `use` header
of its own. It is the only file under the `checker/` directory.

The consequences are: no module identity, failed visibility isolation, ineffective go-to-definition
and symbol search in rust-analyzer, and analysis tools treating it as part of `checker.rs`. **The
true size of the `checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618 lines shown by
directory statistics.

#### 1.3 Test wiring depends on human memory, so corruption occurs silently

A BFS reachability analysis of the module graph from the two crate roots, `src/lib.rs` and
`src/main.rs`, shows that **24 files / 2,628 lines never participate in compilation**. Of these, 23
files / 1,081 lines are genuine orphans.

| Orphan                                          | Size                 | Contents                                                                              |
| ----------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------- |
| The entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + a 38-line `mod.rs` + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                      | 3 files / 14 lines   | All are placeholder documentation comments                                            |
| `package/template/tests/`                       | 3 files / 65 lines   | 7 `#[test]` functions                                                                 |
| `parser/pratt/tests/precedence_inline.rs`       | 95 lines / 6 tests   | Hidden in a live directory                                                            |
| `typecheck/passes/tests/overload_inline.rs`     | 170 lines / 7 tests  | Same as above                                                                         |
| `util/diagnostic/emitter/tests/json.rs`         | 46 lines / 3 tests   | Same as above                                                                         |

`cargo test` cannot discover them: tests that never run cannot fail. CI
(`.github/workflows/ci.yml:140`) likewise has no test-count baseline or wiring check.

**The real tests that have never run total 1,005 lines / 78 tests.** The only lexical-layer test
currently running is `fstring.rs`, which is connected through a `#[path]` attribute bypass.

### II. The project already has sufficient design capability

It must also be acknowledged that the project **already has** mature enforcement mechanisms; they
simply have not been extended to other areas.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subject to a
build-time hard gate through `build.rs:19-55` and `tools/code-tables`: the registry is parsed,
uniqueness and code tiers are validated, every entry is compared against RFC-013's Markdown code
table, and **any inconsistency directly triggers `panic!` and refuses compilation**. RFC-013 and the
code therefore remain consistent at all times.

`src/package/` (76 files / 13,012 lines) is the most complete area: **tests account for 6,227 lines,
or 47.9%**; 5 of the 6 `tests/` directories are correctly wired, with `template/tests/` as the sole
exception, as discussed in Section A. Note that this positive example depends on **directory-level
wiring**, not file-level wiring: of the 76 `.rs` files, only 7 contain inline `#[cfg(test)]`, and
only 5 contain `mod tests;`. Five RFCs correspond line by line with the code, with multiple “not
implemented” cases becoming explicit errors rather than silent TODOs (`build/mod.rs:172-174` for
cmake, `error.rs:74-76` for `RegistryDeferred`). The `.yxpkg` format has five layers of safety
protection, all correctly implemented.

**The same repository and the same authors wired the `package/` test directories correctly, while
`lexer/tests/` has never run even once. The difference is not capability; it is whether anyone runs
the check once.**

### III. Paper architecture

The three documents under `docs/src/dev/design/check/` describe an architecture that **has never
existed**: `CheckSession` (including a Rust code sketch in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, and `HotReloader` have zero matches across the repository;
the `traits/` directory does not exist; the `check_single_module` function does not exist (it
survives only in a test comment); even the busy-wait in `command.rs` cited under “known limitations”
does not exist (that file contains neither `Instant` nor `recv_timeout`).

Cross-file analysis is in fact implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1,528, approximately 2,670 lines)—the capability is real, but the path is
completely different. **This document presents “a potentially future design” as “a defect in an
implemented system.”**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the clearest evidence of “building a test skeleton to the design, discovering that the pipeline has
no corresponding implementation, and then setting it aside.”

In addition, `RFC-018` (LLVM AOT, 1,037 lines, status accepted) has zero lines of implementation in
the code—the six AOT-related matches in `backends/mod.rs` are **all comments**.

## Root-Cause Diagnosis

Taken together, the three classes of symptoms have a single root cause:

> **This project treats “design” as a documentation convention rather than as an executable
> constraint.**

| Layer             | Missing enforcement                                                   | Existing but unextended example                                                                       |
| ----------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Stage boundaries  | A single decision point for “which stages does this compilation run?” | —                                                                                                     |
| Module boundaries | Prohibit `include!`; restrict cross-layer `pub(crate)` leakage        | —                                                                                                     |
| Cross-references  | Detectable “a field is produced but never consumed” conditions        | The error-code gate in `build.rs`                                                                     |
| Test wiring       | If a directory is declared, it must have a `mod` declaration          | The directory-level wiring convention in `src/package/` (5 of 6 `tests/` directories correctly wired) |

The position of this RFC is therefore: **turn the three kinds of boundaries—stages, modules, and
cross-references—from “documentation conventions” into “facts assertable at compile time or test
time,”** and **establish a unique stage-decision point in the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 编排层 Orchestration                                      │
│   谁决定跑哪些阶段、跑几遍、失败如何传播                      │
│   现状: pipeline.rs(740) + orchestrator.rs(1528)             │
│         + compiler.rs(267) = 5 个入口, 11 处不一致           │
│   目标: 单一 Driver + 可穷举的 Stage 枚举 + Obligations 账本  │
│   详见: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 编译单元 (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 前端层 Frontend                                           │
│   词法、语法、AST 构造                                        │
│   现状: lexer/(3065) + parser/(6341)                        │
│         手工 lexer + 手工 Pratt; 加运算符要改 L2 内          │
│         6-7 处 + 下游 17 个生产文件                          │
│   目标: 词法收敛为唯一实现 + LALRPOP 文法驱动语法            │
│   详见: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 语义与中间表示 Semantic & IR                              │
│   类型检查、静态分析、IR 构造                                 │
│   现状: typecheck/(29466 生产) + ir.rs(905) + ir_gen.rs(8448) │
│         3 套平行类型表示 + 3 套平行运算符枚举;                │
│         ir_gen 单 impl 7952 行 / 116 方法; 无 IR 级校验器    │
│   目标: 类型表示单一化; IR 满足 SSA 构造纪律                  │
│   详见: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 执行层 Execution                                          │
│   字节码生成、解释器、运行时、标准库                          │
│   现状: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│         + runtime/(1800) + std/(7543)                         │
│   目标: opcode 事实单源化 + 生成期门禁; 执行层不感知 L1-L3    │
│   详见: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it only consumes AST data and does not call the parser);
and L4 depends only on L3's output format.

The list of known reverse dependencies and parallel definitions appears in routing table C in
`../compiler-architecture/01-routing.md`.

### Equivalence-Criteria Tiers

**This is the safety net for the entire refactoring and must be established before any code
change.** See `07-equivalence-oracle.md` for the detailed design.

The core principle is: **criteria are graded by refactoring category because different categories
require different strengths of equivalence.** Using a single criterion—usually “full IR snapshot
equality”—for all refactorings is incorrect; some refactorings **necessarily change the shape of the
IR**.

| Category | Refactoring content                                                            | Criterion type                                                            | Strength  |
| -------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | --------- |
| **C1**   | Pure relocation (splitting files, changing directories, extracting submodules) | Normalized IR snapshot **zero-diff**                                      | Strongest |
| **C2**   | Orchestration changes (staging, unified Driver)                                | Identical diagnostic sets across entry points + identical corpus behavior | Strong    |
| **C3**   | Type-representation convergence                                                | Identical diagnostic **codes** (message wording may change)               | Strong    |
| **C4**   | IR-shape changes (SSA conversion)                                              | **Behavioral equivalence** + IR structural invariants                     | Medium    |
| **C5**   | Frontend-paradigm changes                                                      | AST snapshot + diagnostics + behavior, all three                          | Strong    |
| **C6**   | Pure deletion                                                                  | No equivalence required; only confirmation that no references remain      | —         |

**The distinction between C1 and C4 is critical**: C1 requires byte-for-byte identical IR, while C4
acknowledges that the IR will change and instead requires “the same program behavior + IR satisfies
the invariants.” Forcing snapshot criteria onto C4 would encourage the team to weaken the criteria.

The three criterion layers are:

1. **IR static validator** — detects dominating use-before-def, missing jump targets, type
   inconsistencies, and inner-boundary violations. It is far stronger than snapshots and catches
   defects such as “the IR is internally consistent but the values are wrong,” which snapshots
   cannot detect. It must **first run green against the existing non-SSA IR**.
2. **Normalized IR snapshots** — strip `Span`, rename temporaries in occurrence order, relativize
   global slots, and sort predecessors. Check the snapshots into the repository and manually review
   diffs. **Known limitation**: normalization erases which register was used by the Nth actual
   argument and therefore **cannot independently cover `arg_regs` semantic reordering**.
3. **End-to-end corpus differential testing** — compare diagnostic lists, exit codes, and
   stdout/stderr item by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml` anywhere under the
> `tests/` directory** (measured: 0), so all **293** `.yx` corpus files under `tests/yaoxiang/`
> **take the single-file path** (`check_files_with_diagnostics`'s standalone branch →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third criterion layer can **validate only changes to the single-file path**.
> There is currently **no corpus coverage** for the multi-file side (the four `orchestrator` entry
> points) or for multi-file behavior involving types/SSA. P4, “Unified Driver,” is the highest-risk
> point in the entire plan, and **the multi-file corpus layer must be established unconditionally in
> P2** (Decision D40)—it is P4's only executable source of behavioral criteria.

## Implementation Strategy

### Stage Sequence

```
P0  仓库维护机制与代码放置规程 08        ← 先立规矩:三条禁令 + D0-D4 决策程序
P1  复活孤儿测试并修缺陷        06 §S1   ← 最便宜,收益最大
P2  建立等价性判据基线          07 全部
P3  修正确性漏洞(最小方案)      02 §修复
P3.5 删除 pub 与自动绑定        RFC-029g / #399  ← 排序约束 D56,必须先于 P4
P4  阶段契约与统一 Driver        02
P5  checker 文件内拆分          09 §P5 补齐
P6  类型表示单一化              03
P7  中间表示 SSA 化             04     } 可并行
P8  前端范式变更                05     }
P9  防反弹门禁(统一脚本清单)     01 + 08
P10 其余清理与状态修正          06 §S2-S6
```

**Core serial constraints (non-reorderable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every action in P1—1.2.x adds `mod` declarations to `mod.rs`, which is precisely the cause of the `precedence_inline.rs` keep-or-delete conflict                                                                                                                                                                                                                                   |
| P1 → P2      | Reviving tests changes the test count and corpus baseline. Establishing the baseline first would invalidate it after P1                                                                                                                                                                                                                                                                                             |
| P2 → P3      | The vulnerability criterion must **be written red first** to prove that the fix is effective. **Narrowing (D51)**: P3 has only two prerequisites, 2.3.2 (multi-file corpus layer) and 2.4.1/2.4.3 (two red criteria); the remainder of P2 may run in parallel with P3, but P4 must wait for all of P2—the containment of the correctness vulnerability must not be blocked by criterion-infrastructure construction |
| P3 → P4      | Fix the bug before refactoring. Reversing the order would cause the bug to be fossilized in the stage table as “established behavior”                                                                                                                                                                                                                                                                               |
| P3.5 → P4    | RFC-029g's (#399) deletion surface covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 respectively (role dispatch within `check_project`, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, and `lexer` + `parser`). Reversing the order means repeating the same deletions on the new grammar, checker layout, and IR                                                                                     |
| P4 → P5      | P5 opens by replacing `include!` with a real `mod` (09 §P5 5.1); the subsequent checker split touches the same file and must proceed continuously after P4                                                                                                                                                                                                                                                          |
| P5 → P6      | Consecutive changes to the same file must be separated so that regressions can be located by bisection                                                                                                                                                                                                                                                                                                              |
| P6 → P7 / P8 | If type representations are not unified first, the new SSA IR will grow into a third representation                                                                                                                                                                                                                                                                                                                 |
| P7/P8 → P9   | The initial baselines of the various gate scripts—such as the `pub(crate)` leakage count—are taken only after P7/P8                                                                                                                                                                                                                                                                                                 |
| P7 ∥ P8      | The file sets are disjoint and may proceed in parallel                                                                                                                                                                                                                                                                                                                                                              |

**Why P0 is an independent stage**: P9's CI scripts are **after-the-fact checks** and can only stop
bad code that has already been written; “patching what should have been refactored” is an **ex-ante
judgment** that only the D0–D4 decision procedure can prevent. The two cannot replace each other.

## Trade-offs

### Advantages

- **Provides a landing point for every subsequent change.** “Adding an operator requires changing a
  dozen places, and no one notices when one is missed” cannot be improved through memory; it
  requires a routing table + gates.
- **A single root cause.** All three classes of symptoms (stage inconsistencies, `include!`, and
  broken test wiring) arise from “boundaries are conventions, not constraints,” and can be addressed
  together using the same class of mechanism.
- **Non-blocking.** This RFC entails zero code changes. The four-layer model is descriptive; after
  adoption, only part of it may be executed.
- **Criteria first.** P2 establishes the baseline before any code change, and the graded design
  avoids the common failure mode of “snapshots are too strict → induce criterion weakening.”

### Disadvantages and Risks

- **The serial chain is long.** P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly a complete serial
  chain, so late stages must wait for earlier ones.
- **P1 introduces a new bug-fixing workload**, and it is the step most likely to be skipped because
  “bugs must be fixed, so let's not do this first.” Skipping it means that the acceptance criteria
  for every later stage are built on false coverage.
- **P4 is the largest single-point risk**: it changes 5 entry points at once.
- **P6 has the broadest impact**: it touches the common dependencies of the parser, formatter,
  spawn, and orchestrator.
- **P7 will increase the line count by a net 900–1,600 lines, rather than reduce it.** Splitting
  introduces boilerplate: 300–600 lines for `verify` and 600–1,000 lines for register allocation.
  **If “shorter code” is adopted as the success criterion when the project is initiated, this stage
  will be judged a failure**—this must be aligned at project-initiation time.

## Alternatives

### A. Split files only, without changing the paradigm

Split the 8,448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting eliminates none of the root causes: the 6 manual save/restore operations
remain dispersed across 10 files, the `arg_regs` semantic reordering in `generate_call_expr_ir`
still requires manual reasoning, and “adding an operator requires changing a dozen places” is still
a dozen places. Splitting improves navigation, not correctness.

### B. Add gates only, without changing the structure (including a line-count ratchet)

**Not adopted as the sole solution, but it is part of this RFC.** Gates can prevent degradation, but
they cannot fix the status quo—`ir_gen.rs` is already 8,448 lines, and gates can only freeze it at
that number.

### C. Start over with a new compiler skeleton

**Not adopted.** `src/package/` proves that this team can build a complex system correctly. The
problem is not capability. Moreover, the existing 293 `.yx` corpus files provide a ready source of
equivalence criteria, so rewriting from scratch would waste that asset.

### D. Use an existing compiler framework (for example, LLVM as the sole backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already provides an abstraction point,
but it has only one implementation. Introducing LLVM falls within the scope of `RFC-018` (1,037
lines of design, 0 lines of code) and should be **decided independently**—it changes “what to
compile to,” not “how to organize the code.”

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                                     |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustively enumerable step in a compilation. The set of stages must be an exhaustively enumerable enum and must not be registered at runtime              |
| **Orchestration Layer (L1)**               | The layer that determines which stages run, how many times they run, and how failures propagate                                                                |
| **Frontend Layer (L2)**                    | Lexing and parsing, producing the AST                                                                                                                          |
| **Intermediate-Representation Layer (L3)** | Type checking, static analysis, and IR construction                                                                                                            |
| **Execution Layer (L4)**                   | Bytecode generation, the interpreter, the runtime, and the standard library                                                                                    |
| **Obligation**                             | A contract item produced by one stage and required to be consumed downstream, or compilation fails                                                             |
| **Obligations Ledger**                     | The container for all obligations, settled uniformly at the end of the stage table                                                                             |
| **Orphan**                                 | A file never referenced by any `mod` declaration and therefore never participating in compilation                                                              |
| **Shell**                                  | A file that has been declared and included in the compilation artifact but contains only documentation comments or unused `use` statements and zero assertions |
| **Equivalence Oracle**                     | An executable check that proves behavior did not change before and after a refactoring                                                                         |
| **C1–C6**                                  | Refactoring-category grading that determines criterion strength. **No C5′ exists**                                                                             |
| **Separation of Responsibilities**         | The only solution to scale problems: one module bears one kind of responsibility. **No line-count / size gate**                                                |
| **Decision Registry**                      | This RFC's “Decision Registry” section, containing the final adjudication of every previously open item                                                        |
