# RFC-039: Compiler Architecture Refactor

## Summary

This RFC proposes an architectural refactor of the YaoXiang compiler (`src/` 160,002 lines / 509
`.rs` files): redrawing boundaries using a **four-layer model** (Orchestration / Frontend /
Intermediate Representation / Execution), establishing **exhaustible compilation stage contracts**
and an **obligations ledger**, accompanied by a set of **equivalence oracles** and
**rebound-prevention gates**.

The detailed design is placed in nine companion documents under `docs/src/dev/architecture/`. This
RFC is responsible only for: the problem, root cause, four-layer model, acceptance-criteria grading,
and execution stage sequence. **Reviewing this RFC is sufficient to decide whether to approve the
project; the companion documents are construction blueprints after approval.**

## Motivation

### I. Boundaries Exist, But Have No Force

The directory-based layering (`frontend` / `middle` / `backends`) is clear. But **boundaries exist
only in human awareness, with no mechanism to prevent erosion.** Three direct consequences.

#### 1.1 Compilation stages are hand-wired at five entry points, producing 11 behavioral inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (in-project) | LSP (single-file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing           | yes               | yes              | yes     | yes              | yes               |
| typecheck                  | yes               | yes              | yes     | yes              | yes               |
| **proof_execution**        | **yes**           | **no**           | **no**  | **no**           | **no**            |
| dead-code analysis         | yes               | no               | yes     | no               | no                |
| W1006 shadowing diagnostic | no                | no               | yes     | no               | no                |
| monomorphization           | yes               | no               | no      | no               | no                |
| IR generation / linking    | yes               | yes              | no      | no               | no                |

The five entry points: `src/frontend/pipeline.rs:141-227` (single-file, 5 stages at `149` / `161` /
`173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), plus `src/lib.rs`'s `run_file:140`
/ `run_project:154`.

The most serious cell leads to a **correctness vulnerability**. A proof function constraint shaped
like `x: Sorted(3)` **silently passes** on the multi-file, check, and LSP paths. Evidence chain (all
verifiable):

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a non-empty `proof_calls`, with semantics "this constraint requires
   executing the proof function."
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches handling `Unproven`:
   `5164` / `5306` / `5420` are `if calls.is_empty()` → hard error; `5179` / `5318` / `5448` are
   `ctx.proof_calls.extend(...)` → **produces no diagnostic**. The comment at `5165` reads literally
   "Unproven → compile error, no degradation, no silent pass... must not let silent pass revive."
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is **only read in one place in the entire
   repository**: `src/frontend/pipeline.rs:187`.
4. **None of the four entry points in `orchestrator.rs` read this field.**

That is: the invariants the code itself declares are violated by the architecture, not the logic.
The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means **even the refinement
obligations of the embedded std module itself take this discarded path**.

**No test can catch it**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit tests directly call `check_module` to assert
"`proof_calls` is non-empty," **stopping exactly before the pipeline**—they verify "it was filled,"
but the bug is "the consumer didn't read it."

#### 1.2 Module boundaries can be bypassed without a trace

`src/frontend/core/typecheck/checker.rs:5618` is `include!("checker/semantic_tokens.rs");`—**the
only `include!` in the entire repository**. It splices 1547 lines of text into the `checker` module.
The file **is not declared as any module** (`grep 'mod semantic_tokens'` returns zero hits in the
entire repo), its first line is directly `impl TypeChecker {`, it has no own `use` header, and the
`checker/` directory contains only this one file.

Consequences: no module identity, visibility isolation fails, rust-analyzer's jump and symbol search
fail on it, toolchain analysis counts it as part of `checker.rs`. **The true body of the `checker`
module is 5618 + 1547 ≈ 7165 lines**, not the 5618 lines the directory statistics show.

#### 1.3 Test wiring relies on human memory; corruption happens silently

Performing a BFS reachability analysis on the module graph from the two crate roots `src/lib.rs` /
`src/main.rs`: **24 files / 2628 lines never participate in compilation**. Among them are 23 real
orphans / 1081 lines.

| Orphan                                      | Scale                | Content                                                                               |
| ------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------- |
| Entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totalling 19 lines + `mod.rs` 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                  | 3 files / 14 lines   | All placeholder doc comments                                                          |
| `package/template/tests/`                   | 3 files / 65 lines   | 7 `#[test]`                                                                           |
| `parser/pratt/tests/precedence_inline.rs`   | 95 lines / 6 tests   | Hidden in a live directory                                                            |
| `typecheck/passes/tests/overload_inline.rs` | 170 lines / 7 tests  | Same as above                                                                         |
| `util/diagnostic/emitter/tests/json.rs`     | 46 lines / 3 tests   | Same as above                                                                         |

`cargo test` cannot discover them: tests that haven't run won't fail. CI
(`.github/workflows/ci.yml:140`) also has no test-count baseline or wiring check.

**Tests that have never run total 1005 lines / 78 tests.** The only thing actually running in the
lexer layer is `fstring.rs` (bypassed via `#[path]` attribute).

### II. Design Capability Is Sufficient

It must be acknowledged simultaneously: **this project already has** mature enforcement mechanisms,
they just haven't been generalized.

The error codes in `src/util/diagnostic/codes/` (137 E-codes + 8 W-codes = 145) are under hard
build-time gating by `build.rs:19-55` via `tools/code-tables`—parsing the registry, validating
uniqueness and section, comparing each one against RFC-013's markdown code table, **any
inconsistency directly `panic!`s and refuses compilation**. RFC-013's documentation and code are
therefore always consistent.

`src/package/` (76 files / 13,012 lines) is the most complete region: **tests are 6,227 lines,
accounting for 47.9%**; 5 of 6 `tests/` directories are correctly wired (the only exception is
`template/tests/`, see Section A). Note that this positive example stands at the **directory-level
wiring**, not at every file—of 76 `.rs` files, only 7 contain inline `#[cfg(test)]`, 5 contain
`mod tests;`. The 5 RFCs align line-by-line with the code, multiple "not implemented" lands as
explicit errors rather than silent TODOs (`build/mod.rs:172-174`'s cmake, `error.rs:74-76`'s
`RegistryDeferred`). `.yxpkg` has five layers of safety protection and all are correct.

**The same repository, the same author, `package/` got test-directory wiring right, `lexer/tests/`
has never run once. The difference isn't capability, it's whether someone runs the check.**

### III. Phantom Designs

The three documents under `docs/src/dev/design/check/` describe an **architecture that never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, `HotReloader`—all zero hits in the entire repository; the
`traits/` directory doesn't exist; `check_single_module` doesn't exist (only lives in test
comments); even the `command.rs` busy-wait cited in "known limitations" doesn't exist (the file has
neither `Instant` nor `recv_timeout`).

Cross-file analysis is actually implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, approximately 2670 lines)—the capability is real, the path is
completely different. **This documentation writes "possible future designs" as "defects in the
implemented system."**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the cleanest physical evidence of "test skeleton built per design, no corresponding implementation
found in the pipeline, so put it aside."

Furthermore, `RFC-018` (LLVM AOT, 1037 lines, status accepted) has 0 lines of implementation in the
code—the 6 AOT-related hits in `backends/mod.rs` are **all comments**.

## Root Cause Diagnosis

Combining the three symptoms, the root cause is singular:

> **This project treats "design" as a documentation convention, not as an executable constraint.**

| Layer           | Missing Enforcement                                                  | Existing But Ungeneralized Example                                                   |
| --------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Stage boundary  | A single decision point for "which stages did this compilation run"  | —                                                                                    |
| Module boundary | Prohibition on `include!`, limiting `pub(crate)` cross-layer leakage | —                                                                                    |
| Cross-reference | Detectability of "field produced but unconsumed"                     | `build.rs`'s error-code gate                                                         |
| Test wiring     | Declaring a directory must have a `mod` declaration                  | `src/package/`'s directory-level wiring convention (5 of 6 `tests/` correctly wired) |

This RFC's position is therefore: **transform the three types of boundaries—stages, modules,
cross-references—from "documentation convention" into "compile-time or test-time assertable
facts,"** and **establish a single stage decision point at the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 Orchestration Layer                                       │
│   Who decides which stages to run, how many times,           │
│   how failures propagate                                     │
│   Current: pipeline.rs(740) + orchestrator.rs(1528)          │
│         + compiler.rs(267) = 5 entry points, 11 inconsistencies │
│   Target: Single Driver + exhaustible Stage enum + Obligations ledger │
│   See: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ Compilation Unit
┌───────────────────────────▼─────────────────────────────────┐
│ L2 Frontend Layer                                            │
│   Lexing, parsing, AST construction                          │
│   Current: lexer/(3065) + parser/(6341)                     │
│         Manual lexer + manual Pratt; adding an operator      │
│         requires 6-7 changes within L2 + 17 downstream       │
│         production files                                     │
│   Target: Lexer converges to single implementation +         │
│         LALRPOP grammar-driven syntax                        │
│   See: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 Semantic & IR Layer                                       │
│   Type checking, static analysis, IR construction            │
│   Current: typecheck/(29466 production) + ir.rs(905)         │
│         + ir_gen.rs(8448); 3 parallel type representations   │
│         + 3 parallel operator enums; ir_gen single           │
│         impl 7952 lines / 116 methods; no IR-level verifier  │
│   Target: Type representation unified; IR satisfies SSA      │
│         construction discipline                              │
│   See: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 Execution Layer                                           │
│   Bytecode generation, interpreter, runtime, standard library │
│   Current: codegen/(3436) + bytecode.rs(2422) +              │
│         executor/(2000) + runtime/(1800) + std/(7543)        │
│   Target: opcode factual single source + generation-time     │
│         gate; execution layer unaware of L1-L3                │
│   See: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it only consumes AST data, does not call parser); L4
only depends on the product format of L3.

The known reverse dependencies and parallel definitions list is in routing table C of
`../compiler-architecture/01-routing.md`.

### Equivalence Oracle Grading

**This is the safety net for the entire refactor and must be established before any code changes.**
Detailed design in `07-equivalence-oracle.md`.

Core principle: **Oracles are graded by refactor category, because different categories require
different strengths of equivalence.** Using a single oracle (usually "IR snapshot full equality") to
cover all refactors is wrong—some refactors **necessarily change the IR form**.

| Category | Refactor Content                                                | Oracle Type                                               | Strength  |
| -------- | --------------------------------------------------------------- | --------------------------------------------------------- | --------- |
| **C1**   | Pure move (split files, change directories, extract submodules) | IR normalized snapshot **zero-diff**                      | Strongest |
| **C2**   | Orchestration change (staging, unified Driver)                  | Same diagnostic set at each entry + same corpus behavior  | Strong    |
| **C3**   | Type representation convergence                                 | Same diagnostic **codes** (message wording will change)   | Strong    |
| **C4**   | IR form change (SSA-ization)                                    | **Behavioral equivalence** + IR structural invariants     | Medium    |
| **C5**   | Frontend paradigm change                                        | AST snapshot + diagnostics + behavior, all three used     | Strong    |
| **C6**   | Pure deletion                                                   | No equivalence needed, only confirmation of no references | —         |

**The distinction between C1 and C4 is key**: C1 requires IR byte-for-byte equality; C4 acknowledges
IR will change, switching to "program behavior same + IR satisfies invariants." Forcing C4 to use
snapshots will induce the team to relax the oracle.

Three layers of oracles:

1. **IR Static Verifier** — dominance use-before-def, jump target existence, type consistency,
   inner-isolation. Far stronger than snapshots, covers defects like "IR self-consistent but value
   wrong" that snapshot tests can't detect. Must **first pass green on the existing (non-SSA) IR**.
2. **Normalized IR Snapshot** — strip `Span`, rename temporaries in appearance order, relativize
   global slots, sort predecessors. Commit, manually review diff. **Known limitation**:
   normalization erases "which register the Nth argument used," so **alone insufficient to cover
   `arg_regs` semantic reordering**.
3. **End-to-end Corpus Diff** — diagnostic list, exit code, stdout/stderr compared item by item.

> **⚠️ Structural Limitation of Corpus Coverage**: there is **no `yaoxiang.toml`** in the `tests/`
> directory (verified 0), so the **293** `.yx` corpora in `tests/yaoxiang/` **all take the
> single-file path** (standalone branch of `check_files_with_diagnostics` → `check_single_file` →
> `Pipeline::run`).
>
> **Consequence**: the third-layer oracle **can only verify single-file path changes**. For the
> multi-file side (the four entry points of `orchestrator`) and the multi-file performance of
> type/SSA, **there is currently no corpus coverage**. P4 "Unified Driver" is the largest risk point
> in the entire plan, **the multi-file corpus layer must be unconditionally established in P2**
> (Decision D40)—it is the sole executable behavioral oracle source for P4.

## Implementation Strategy

### Stage Sequence

```
P0  Repository maintenance mechanism and code placement regulation 08     ← Establish rules first: three prohibitions + D0-D4 decision procedure
P1  Revive orphan tests and fix defects        06 §S1                    ← Cheapest, highest return
P2  Establish equivalence oracle baseline      07 all
P3  Fix correctness vulnerability (minimal)    02 §Fix
P3.5 Delete pub and auto-binding                RFC-029g / #399          ← Ordering constraint D56, must precede P4
P4  Stage contract and unified Driver           02
P5  In-checker file split                      09 §P5 fill-in
P6  Type representation unification            03
P7  Intermediate representation SSA-ization    04                     } Parallel-able
P8  Frontend paradigm change                   05                     }
P9  Rebound-prevention gates (unified script list)  01 + 08
P10 Remaining cleanup and status correction    06 §S2-S6
```

**Core serial constraints (non-swappable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every action of P1—1.2.x is adding `mod` declarations to `mod.rs`, which is exactly what caused the `precedence_inline.rs` life-and-death conflict                                                                                                                                                                                                                           |
| P1 → P2      | Reviving tests will change test count and corpus baseline. Building the baseline first will fail after P1                                                                                                                                                                                                                                                                                                     |
| P2 → P3      | The vulnerability oracle must **first be written as failing** to prove the fix is effective. **Narrowing (D51)**: P3's prerequisite is only 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two failing oracles); the rest of P2 can run in parallel with P3, but P4 must wait for all of P2 to complete—the stop-bleeding of correctness vulnerabilities is not blocked by oracle infrastructure construction |
| P3 → P4      | Fix the bug first, then refactor. Reverse order will let the bug be solidified as "established behavior" by the stage table                                                                                                                                                                                                                                                                                   |
| P3.5 → P4    | RFC-029g (#399)'s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8's respective rewrite targets (`check_project`'s role assignment, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer`+`parser`). Reverse order equals redoing the same batch of deletions on new grammar, new checker layout, new IR (D56)                                                                                       |
| P4 → P5      | P5 opens with `include!` → real `mod` (09 §P5 5.1); the subsequent checker split works on the same file, must proceed consecutively after P4                                                                                                                                                                                                                                                                  |
| P5 → P6      | Continuous changes to the same file must be separated, otherwise regressions cannot be bisected                                                                                                                                                                                                                                                                                                               |
| P6 → P7 / P8 | If type representation isn't converged first, SSA's new IR will grow into a third representation                                                                                                                                                                                                                                                                                                              |
| P7/P8 → P9   | Initial baselines of various gate scripts (such as `pub(crate)` leakage count) take final values only after P7/P8                                                                                                                                                                                                                                                                                             |
| P7 ∥ P8      | File sets are disjoint, can be parallel                                                                                                                                                                                                                                                                                                                                                                       |

**Why P0 is an independent stage**: P9's CI scripts are **post-hoc checks**, they can only catch bad
code already written; "patched instead of refactored" is **pre-judgment**, only the D0–D4 decision
procedure can catch it. The two cannot substitute for each other.

### Definition of Done (DoD) for Each Stage

A stage is considered complete only when all the following are met simultaneously:

1. The corresponding "implementation strategy" steps in the belonging document are all committed
2. The oracle of that category (C1-C6) in `07-equivalence-oracle.md` **is green in CI**
3. `cargo test` is all green, and **test count is not lower than at the start of that stage**
   (preventing "delete tests to get green light")
4. `cargo clippy --all --all-features -- -D warnings` is clean
5. `python scripts/rfc/check_tracking.py` exit code 0
6. The stage has an independent revert unit—**if a stage cannot be reverted independently, it's too

## Trade-offs

### Advantages

- **Provides a landing point for all subsequent changes.** "Adding an operator requires changing a
  dozen places, missing one and no one knows" cannot be improved by memory, only by routing tables +
  gates.
- **Single root cause.** The three symptoms (stage inconsistency, `include!`, test wiring broken)
  all stem from "boundary is convention not constraint," and can be solved once with the same type
  of mechanism.
- **Non-blocking.** This RFC has zero code changes. The four-layer model is descriptive; after
  adoption, only a portion can still be executed.
- **Oracles first.** P2 is established before any code changes, and the graded design avoids the
  common failure of "snapshot too strict → induce relaxation."

### Disadvantages and Risks

- **The serial chain is long.** P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly fully serial; later
  stages must wait for earlier ones to complete.
- **P1 will introduce new bug workload**, and this is the most easily skipped step with the excuse
  "we have to fix bugs so let's not do it first"—but skipping it means all subsequent stages'
  acceptance oracles are built on false coverage.
- **P4 is the largest single-point risk**: one change touches 5 entry points.
- **P6 has the widest impact surface**: touches parser, formatter, spawn, orchestrator's shared
  dependencies.
- **P7's line count will net increase 900-1600 lines, not net decrease.** Splitting introduces
  boilerplate, `verify` 300-600 lines, register allocation 600-1000 lines. **If "shorter code" is
  the success criterion at project initiation, this stage will be judged as failed**—this must be
  aligned at project initiation.

## Alternatives

### A. Only Split Files, Don't Change Paradigm

Split 8448 lines into 10 files of 800 lines.

**Not adopted.** Splitting doesn't eliminate any root cause: 6 manual save/restore points still
scattered across 10 files, `generate_call_expr_ir`'s `arg_regs` semantic reordering still requires
human reasoning, "adding an operator changes a dozen places" is still a dozen places. Splitting
improves navigation, not correctness.

### B. Only Add Gates, Don't Change Structure (Including Line Count Ratchet)

**Not adopted as the only solution, but it is part of this RFC.** Gates prevent regression, they
can't fix the current state—`ir_gen.rs` is already 8448 lines; gates can only freeze it at that
number.

### C. Start Over, Write a New Compiler Skeleton

**Not adopted.** `src/package/` proves this team can get complex systems right. The problem isn't
capability. And the existing 293 `.yx` corpora provide ready-made equivalence oracle sources;
rewriting from scratch wastes this asset.

### D. Use Existing Compiler Frameworks (e.g., LLVM as Sole Backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already reserves an abstraction point
but has only one implementer. Introducing LLVM is the scope of `RFC-018` (1037 lines of design, 0
lines of code), should be **decided independently**—it changes "compile to what" rather than "how to
organize code."

## Appendix: Glossary

| Term                                       | Definition                                                                                                           |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustible step in a compilation. The stage set must be exhaustively enumerable, not runtime-registered          |
| **Orchestration Layer (L1)**               | The layer that decides which stages to run, how many times, how failures propagate                                   |
| **Frontend Layer (L2)**                    | Lexing and parsing, producing AST                                                                                    |
| **Intermediate Representation Layer (L3)** | Type checking, static analysis, IR construction                                                                      |
| **Execution Layer (L4)**                   | Bytecode generation, interpreter, runtime, standard library                                                          |
| **Obligation**                             | A contract item produced by some stage that must be consumed downstream or compilation fails                         |
| **Obligations Ledger**                     | Container of all obligations, settled uniformly at the end of the stage table                                        |
| **Orphan**                                 | A file never referenced by any `mod` declaration, therefore never participating in compilation                       |
| **Shell**                                  | A file already declared, in compilation product, but only has doc comments or unused `use`, zero assertions          |
| **Equivalence Oracle**                     | Executable check that proves behavior hasn't changed before and after refactor                                       |
| **C1-C6**                                  | Refactor category grading, determines oracle strength. **C5′ does not exist**                                        |
| **Separation of Responsibilities**         | The only solution to scale problems: a module only takes one kind of responsibility. **No line-count / volume gate** |
| **Decision Registry**                      | The "Decision Registry" section of this RFC, the final ruling on all open items                                      |
