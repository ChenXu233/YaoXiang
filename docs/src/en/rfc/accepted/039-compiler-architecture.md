# RFC-039: Compiler Architecture Refactoring

## Abstract

This RFC proposes an architectural refactoring of the YaoXiang compiler (`src/`, 160,002 lines / 509
`.rs` files): redraw the boundaries using a **four-layer model** (orchestration / frontend /
intermediate representation / execution), establish **exhaustively enumerable compilation-stage
contracts** and an **obligations ledger**, and provide an accompanying **equivalence oracle** and
**anti-regression gates**.

Detailed design is provided in nine companion documents under `docs/src/dev/architecture/`. This RFC
is responsible only for the problem, root cause, four-layer model, acceptance-oracle tiers, and
execution-stage ordering. **Reviewing this RFC is sufficient to decide whether to approve the
project; the companion documents are the construction blueprints to be used after approval.**

## Motivation

### I. The boundaries exist, but have no enforcing power

The layering expressed by directory names (`frontend` / `middle` / `backends`) is clear. However,
**the boundaries exist only in people's conscientiousness; no mechanism prevents them from being
eroded**. This has three direct consequences.

#### 1.1 Compilation stages are manually wired at five entry points, producing 11 behavioral inconsistencies

| Stage                       | Single-file `run` | Multi-file `run` | `check` | LSP (within a project) | LSP (single file) |
| --------------------------- | ----------------- | ---------------- | ------- | ---------------------- | ----------------- |
| lexing / parsing            | Yes               | Yes              | Yes     | Yes                    | Yes               |
| typecheck                   | Yes               | Yes              | Yes     | Yes                    | Yes               |
| **proof_execution**         | **Yes**           | **No**           | **No**  | **No**                 | **No**            |
| Dead-code analysis          | Yes               | No               | Yes     | No                     | No                |
| W1006 shadowing diagnostics | No                | No               | Yes     | No                     | No                |
| Monomorphization            | Yes               | No               | No      | No                     | No                |
| IR generation / linking     | Yes               | Yes              | No      | No                     | No                |

Five entry points: `src/frontend/pipeline.rs:141-227` (single file; five stages at `149` / `161` /
`173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), the four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `run_file:140` /
`run_project:154` in `src/lib.rs`.

The most severe cell in the table leads to a **correctness vulnerability**. A proof-function
constraint such as `x: Sorted(3)` **silently passes** on the multi-file, check, and LSP paths. The
evidence chain is entirely reproducible:

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a nonempty `proof_calls`, with the semantics “this constraint requires
   a proof function to be executed.”
2. `src/frontend/core/typecheck/checker.rs` contains three isomorphic branches that handle
   `Unproven`: `5164` / `5306` / `5420` perform `if calls.is_empty()` → infer a hard error; `5179` /
   `5318` / `5448` perform `ctx.proof_calls.extend(...)` → **produce no diagnostic whatsoever**. The
   comment at `5165` states verbatim: “Unproven → compile error, no degradation, no silent pass...
   silent pass must not be allowed to return.”
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is read in **only one place** in the entire
   repository: `src/frontend/pipeline.rs:187`.
4. **None of the four entry points** in `orchestrator.rs` reads this field.

In other words, an invariant explicitly declared by the code itself was broken by the architecture
rather than by its logic. The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means
that **the refinement obligations of the embedded std module itself also travel through this discard
path**.

**No test can catch it**: none of the 27 tests in `tests/integration/multifile.rs` mentions `Sorted`
/ `proof` / `refin`; RFC-027's unit tests directly call `check_module` and assert that `proof_calls`
is nonempty, **stopping exactly before the pipeline**—they verify that the field was “populated,”
while the bug is that the “consumer does not read it.”

#### 1.2 Module boundaries can be bypassed without leaving a trace

`src/frontend/core/typecheck/checker.rs:5618` contains `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1,547 lines of text into the `checker`
module. The file **is not declared as a module anywhere** (`grep 'mod semantic_tokens'` finds zero
matches across the repository), its first line is directly `impl TypeChecker {`, it has no `use`
header of its own, and it is the only file in the `checker/` directory.

Consequences: there is no module identity, visibility isolation is ineffective, rust-analyzer's
go-to-definition and symbol search do not work for it, and toolchain analysis counts it as part of
`checker.rs`. **The true size of the `checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618
lines shown by directory statistics.

#### 1.3 Test wiring relies on human memory, so corruption occurs silently

A module-graph BFS reachability analysis starting from the two crate roots, `src/lib.rs` /
`src/main.rs`, shows that **24 files / 2,628 lines never participate in compilation**. Of these, 23
files / 1,081 lines are genuine orphans.

| Orphan                                          | Size                 | Contents                                                                                |
| ----------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------- |
| The entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + `mod.rs` at 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                      | 3 files / 14 lines   | All placeholder documentation comments                                                  |
| `package/template/tests/`                       | 3 files / 65 lines   | 7 `#[test]` functions                                                                   |
| `parser/pratt/tests/precedence_inline.rs`       | 95 lines / 6 tests   | Hidden in a live directory                                                              |
| `typecheck/passes/tests/overload_inline.rs`     | 170 lines / 7 tests  | Same as above                                                                           |
| `util/diagnostic/emitter/tests/json.rs`         | 46 lines / 3 tests   | Same as above                                                                           |

`cargo test` cannot detect this: tests that never run do not fail. CI
(`.github/workflows/ci.yml:140`) has no test-count baseline or wiring check either.

**The real tests that have never run total 1,005 lines / 78 tests.** The only lexer tests actually
running are in `fstring.rs`, connected through a `#[path]` attribute bypass.

### II. The design capability is sufficient

At the same time, we must acknowledge that this project **already has** a mature enforcement
mechanism; it simply has not been generalized.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subject to a
build-time hard gate implemented by `build.rs:19-55` through `tools/code-tables`: it parses the
registry, validates uniqueness and code-segment assignments, and compares every entry against the
Markdown code table in RFC-013. **Any mismatch directly triggers `panic!` and rejects the build.**
RFC-013 and the code therefore remain consistent at all times.

`src/package/` (76 files / 13,012 lines) is the most complete area: **tests account for 6,227 lines,
or 47.9%**; 5 of the 6 `tests/` directories are wired correctly (the sole exception is
`template/tests/`, discussed in Section A). Note that this positive example works at the
**directory-level wiring** level, not at the individual-file level: of 76 `.rs` files, only 7
contain inline `#[cfg(test)]` and only 5 contain `mod tests;`. Five RFCs correspond to the code line
by line, with many instances where “not implemented” becomes an explicit error rather than a silent
TODO (`build/mod.rs:172-174` for cmake, `error.rs:74-76` for `RegistryDeferred`). `.yxpkg` has five
layers of safety protection, all implemented correctly.

**In the same repository, by the same author, `package/` gets test-directory wiring right, while
`lexer/tests/` has never run once. The difference is not capability; it is whether anyone runs the
check.**

### III. Empty-shell design

The three documents under `docs/src/dev/design/check/` describe an architecture that **has never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, and `HotReloader` have zero matches across the repository;
the `traits/` directory does not exist; the `check_single_module` function does not exist (it
survives only in test comments); even the busy-wait on `command.rs` cited under “known limitations”
does not exist (the file contains neither `Instant` nor `recv_timeout`).

Cross-file analysis is in fact implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, approximately 2,670 lines)—the capability is real, but the path is
completely different. **This document describes a “possible future design” as a defect in an already
implemented system.**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the cleanest physical evidence of “we built a test skeleton according to the design, discovered that
the pipeline had no corresponding implementation, and set it aside.”

In addition, `RFC-018` (LLVM AOT, 1,037 lines, status accepted) has 0 lines of implementation in the
code—all six AOT-related matches in `backends/mod.rs` are **comments**.

## Root-Cause Diagnosis

Combining the three classes of symptoms yields a single root cause:

> **This project treats “design” as a documentation convention rather than as an executable
> constraint.**

| Layer             | Missing enforcement                                                   | Existing but ungeneralized example                                                            |
| ----------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Stage boundaries  | A single decision point for “which stages does this compilation run?” | —                                                                                             |
| Module boundaries | Prohibit `include!`; restrict `pub(crate)` leakage across layers      | —                                                                                             |
| Cross-references  | Detectability for “a field is produced but never consumed”            | The error-code gate in `build.rs`                                                             |
| Test wiring       | If a directory is declared, it must have a `mod` declaration          | The directory-level wiring convention in `src/package/` (5 of 6 `tests/` directories correct) |

The position of this RFC is therefore: **turn the three classes of boundaries—stages, modules, and
cross-references—from “documentation conventions” into “facts assertable at compile time or test
time,”** and **establish a single stage-decision point in the orchestration layer**.

## Proposal

### The Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 编排层 Orchestration                                      │
│   谁决定跑哪些阶段、跑几遍、失败如何传播                      │
│   现状: pipeline.rs(740) + orchestrator.rs(1528)             │
│         + compiler.rs(267) = 5 个入口, 11 处不一致           │
│   目标: 单一 Driver + 可穷举的 Stage 枚举 + Obligations 账本  │
│   详见: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 编译单元 (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 前端层 Frontend                                           │
│   词法、语法、AST 构造                                        │
│   现状: lexer/(3065) + parser/(6341)                        │
│         手工 lexer + 手工 Pratt; 加运算符要改 L2 内          │
│         6-7 处 + 下游 17 个生产文件                          │
│   目标: 词法收敛为唯一实现 + LALRPOP 文法驱动语法            │
│   详见: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 语义与中间表示 Semantic & IR                              │
│   类型检查、静态分析、IR 构造                                 │
│   现状: typecheck/(29466 生产) + ir.rs(905) + ir_gen.rs(8448) │
│         3 套平行类型表示 + 3 套平行运算符枚举;                │
│         ir_gen 单 impl 7952 行 / 116 方法; 无 IR 级校验器    │
│   目标: 类型表示单一化; IR 满足 SSA 构造纪律                  │
│   详见: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 执行层 Execution                                          │
│   字节码生成、解释器、运行时、标准库                          │
│   现状: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│         + runtime/(1800) + std/(7543)                         │
│   目标: opcode 事实单源化 + 生成期门禁; 执行层不感知 L1-L3    │
│   详见: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it only consumes AST data and does not call the parser);
L4 depends only on the output format of L3.

The list of known reverse dependencies and parallel definitions is given in routing table C in
`../compiler-architecture/01-routing.md`.

### Equivalence-Oracle Tiers

**This is the safety net for the entire refactoring and must be established before any code
changes.** Detailed design is given in `07-equivalence-oracle.md`.

The core principle is: **criteria are graded by refactoring category because different categories
require different strengths of equivalence.** Using a single criterion (usually “byte-for-byte
identical IR snapshots”) for every refactoring is incorrect—some refactorings **necessarily change
the IR shape**.

| Category | Refactoring content                                                          | Criterion type                                                       | Strength  |
| -------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------- |
| **C1**   | Pure movement (splitting files, changing directories, extracting submodules) | Canonicalized IR snapshot **zero-diff**                              | Strongest |
| **C2**   | Orchestration changes (stage-based execution, unified Driver)                | Same diagnostic sets at every entry point + same corpus behavior     | Strong    |
| **C3**   | Type-representation convergence                                              | Same diagnostic **codes** (message wording may change)               | Strong    |
| **C4**   | IR-shape changes (SSA transformation)                                        | **Behavioral equivalence** + IR structural invariants                | Medium    |
| **C5**   | Frontend paradigm changes                                                    | AST snapshots + diagnostics + behavior, all three                    | Strong    |
| **C6**   | Pure deletion                                                                | No equivalence required; only confirmation that no references remain | —         |

**The distinction between C1 and C4 is critical**: C1 requires byte-for-byte identical IR; C4
acknowledges that the IR will change and instead requires “identical program behavior + IR satisfies
its invariants.” Forcing snapshot comparisons onto C4 will encourage the team to weaken the
criteria.

Three tiers of criteria:

1. **IR static validator** — dominance-based use-before-def, existence of jump targets, type
   consistency, inner isolation. Much stronger than snapshots, and capable of detecting defects such
   as “the IR is internally consistent but the values are wrong,” which snapshots cannot detect. It
   must **first pass on the existing (non-SSA) IR**.
2. **Canonicalized IR snapshots** — strip `Span`, rename temporaries in occurrence order, relativize
   global slots, and sort predecessors. Check these into the repository and manually review diffs.
   **Known limitation**: canonicalization erases “which register was used by the Nth argument,” so
   it is **insufficient on its own to cover `arg_regs` semantic reordering**.
3. **End-to-end corpus differential testing** — compare diagnostic lists, exit codes, and
   stdout/stderr item by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml`** anywhere under
> the `tests/` directory (0 found in practice), so all **293** `.yx` corpus files in
> `tests/yaoxiang/` take the single-file path (`check_files_with_diagnostics`'s standalone branch →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third tier of criteria can **only validate changes to the single-file path**.
> For the multi-file side (the four `orchestrator` entry points) and the multi-file behavior of the
> type system/SSA, **there is currently no corpus coverage**. P4, “Unified Driver,” is the largest
> risk in the entire plan, and **the multi-file corpus tier must be established unconditionally in
> P2** (Decision D40)—it is the only executable source of behavioral criteria for P4.

## Implementation Strategy

### Stage Sequence

```
P0  仓库维护机制与代码放置规程 08        ← 先立规矩:三条禁令 + D0-D4 决策程序
P1  复活孤儿测试并修缺陷        06 §S1   ← 最便宜,收益最大
P2  建立等价性判据基线          07 全部
P3  修正确性漏洞(最小方案)      02 §修复
P3.5 删除 pub 与自动绑定        RFC-029g / #399  ← 排序约束 D56,必须先于 P4
P4  阶段契约与统一 Driver        02
P5  checker 文件内拆分          09 §P5 补齐
P6  类型表示单一化              03
P7  中间表示 SSA 化             04     } 可并行
P8  前端范式变更                05     }
P9  防反弹门禁(统一脚本清单)     01 + 08
P10 其余清理与状态修正          06 §S2-S6
```

**Core serial constraints (not interchangeable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every P1 action—1.2.x adds `mod` declarations to `mod.rs`, which is precisely what caused the `precedence_inline.rs` keep-or-delete conflict                                                                                                                                                                                                                                          |
| P1 → P2      | Reviving tests changes the test count and corpus baseline. Establishing the baseline first would invalidate it after P1                                                                                                                                                                                                                                                                                                |
| P2 → P3      | The vulnerability criterion must **be written as red first** to prove that the fix works. **Narrowing (D51)**: P3 has only two prerequisites, 2.3.2 (multi-file corpus tier) and 2.4.1/2.4.3 (two red criteria); the rest of P2 may proceed in parallel with P3, but P4 must wait until all of P2 is complete—containment of the correctness vulnerability must not be blocked by criteria-infrastructure construction |
| P3 → P4      | Fix the bug before refactoring. Reversing the order would allow the bug to become固化 as “established behavior” in the stage table                                                                                                                                                                                                                                                                                     |
| P3.5 → P4    | The deletion surface of RFC-029g (#399) covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 (`check_project` role dispatch, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer` + `parser`). Reversing the order means repeating the same deletions under the new grammar, new checker layout, and new IR (D56)                                                                                          |
| P4 → P5      | P5 opens by replacing `include!` with a real `mod` (09 §P5 5.1), and the subsequent checker split touches the same file. It must proceed continuously after P4                                                                                                                                                                                                                                                         |
| P5 → P6      | Consecutive changes to the same file must be separated, or regressions cannot be bisected                                                                                                                                                                                                                                                                                                                              |
| P6 → P7 / P8 | If type representations are not converged first, the new SSA IR will grow into a third representation                                                                                                                                                                                                                                                                                                                  |
| P7/P8 → P9   | The initial baselines for the various gate scripts (such as the `pub(crate)` leakage count) can only be finalized after P7/P8                                                                                                                                                                                                                                                                                          |
| P7 ∥ P8      | The file sets are disjoint, so they may proceed in parallel                                                                                                                                                                                                                                                                                                                                                            |

**Why P0 is a separate stage**: P9's CI scripts are **post hoc checks** and can only stop bad code
that has already been written; “patching when a refactor is required” is an **ex ante judgment**,
and only the D0-D4 decision procedure can stop it. The two cannot substitute for each other.

### Definition of Done for Each Stage

A stage is complete only when all of the following are satisfied:

1. All corresponding “Implementation Strategy” steps in the owning document have been committed
2. The criteria for the applicable category (C1-C6) in `07-equivalence-oracle.md` **are green in
   CI**
3. `cargo test` is fully green, and the **test count is not lower than at the beginning of the
   stage** (preventing “delete tests to turn the build green”)
4. `cargo clippy --all --all-features -- -D warnings` is clean
5. `python scripts/rfc/check_tracking.py` exits with code 0

   large and must be split further**
7. For stages touching the compilation pipeline or execution path (P4 / P6 / P7 / P8), the

## Trade-offs

### Advantages

- **It gives every subsequent change a landing point.** “Adding an operator requires changing a
  dozen places, and nobody notices when one is missed” cannot be improved through memory; it can
  only be addressed through a routing table + gates.
- **There is a single root cause.** All three classes of symptoms—stage inconsistencies, `include!`,
  and broken test wiring—originate from “boundaries are conventions, not constraints” and can be
  solved at once through the same class of mechanism.
- **It does not block other work.** This RFC contains zero code changes. The four-layer model is
  descriptive, so after adoption it is still possible to execute only some of it.
- **Criteria come first.** P2 establishes the baseline before any code change, and the tiered design
  avoids the common failure mode of “snapshots are too strict → encourage weakening the criteria.”

### Disadvantages and Risks

- **The serial chain is long.** P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly a complete serial
  chain, and later stages must wait for earlier ones.
- **P1 introduces a new bug-fixing workload**, and it is the step most likely to be skipped with the
  rationale “because bugs need fixing, we will not do this first”—but skipping it means every later
  stage's acceptance criteria are built on false coverage.
- **P4 is the largest single-point risk**: it changes 5 entry points in one go.
- **P6 has the broadest impact**: it touches the shared dependencies of the parser, formatter,
  spawn, and orchestrator.
- **P7 will increase the line count by a net 900-1,600 lines, not decrease it.** Splitting
  introduces boilerplate; `verify` requires 300-600 lines, and register allocation requires
  600-1,000 lines. **If “shorter code” is adopted as the success criterion at project approval, this
  stage will be judged a failure**—this must be aligned at project approval.

## Alternatives

### A. Split files only, without changing the paradigm

Split the 8,448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting eliminates none of the root causes: the 6 manual save/restore sites
remain distributed across 10 files; the `arg_regs` semantic reordering in `generate_call_expr_ir`
still requires manual reasoning; and “adding an operator requires changing a dozen locations”
remains a dozen locations. Splitting improves navigation, not correctness.

### B. Add gates only, without changing the structure (including a line-count ratchet)

**Not adopted as the sole solution, but it is part of this RFC.** Gates can prevent regression but
cannot repair the current state—`ir_gen.rs` is already 8,448 lines, and a gate can only freeze it at
that number.

### C. Start over and write a new compiler skeleton

**Not adopted.** `src/package/` proves that this team can implement a complex system correctly. The
problem is not capability. Moreover, the existing 293 `.yx` corpus files provide a ready source of
equivalence criteria; rewriting from scratch would waste this asset.

### D. Use an existing compiler framework, such as making LLVM the sole backend

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already provides an abstraction point,
but it has only one implementor. Introducing LLVM belongs to the scope of `RFC-018` (1,037 lines of
design, 0 lines of code) and should be **decided independently**—it changes “what to compile to,”
not “how to organize the code.”

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                            |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustively enumerable step in a compilation. The set of stages must be an exhaustively enumerable enum and must not be registerable at runtime   |
| **Orchestration layer (L1)**               | The layer that determines which stages run, how many times they run, and how failures propagate                                                       |
| **Frontend layer (L2)**                    | Lexing and parsing, producing the AST                                                                                                                 |
| **Intermediate representation layer (L3)** | Type checking, static analysis, and IR construction                                                                                                   |
| **Execution layer (L4)**                   | Bytecode generation, interpreter, runtime, and standard library                                                                                       |
| **Obligation**                             | A contract item produced by one stage that must be consumed downstream or compilation must fail                                                       |
| **Obligations ledger**                     | The container for all obligations, settled uniformly at the end of the stage table                                                                    |
| **Orphan**                                 | A file never referenced by any `mod` declaration and therefore never participating in compilation                                                     |
| **Shell**                                  | A file that has been declared and enters the build artifact but contains only documentation comments or unused `use` statements, with zero assertions |
| **Equivalence Oracle**                     | An executable check that proves behavior did not change before and after refactoring                                                                  |
| **C1-C6**                                  | Refactoring-category tiers that determine the strength of the criteria. **No C5′ exists**                                                             |
| **Separation of responsibilities**         | The only solution to scale problems: one module bears only one kind of responsibility. **No line-count / size gates**                                 |
| **Decision registry**                      | This RFC's “Decision Registry” section, containing the final rulings on every open item                                                               |
