# RFC-039: Compiler Architecture Refactoring

## Summary

This RFC proposes an architectural refactoring of the YaoXiang compiler (`src/` 160,002 lines / 509
`.rs` files): redefine boundaries using a **four-layer model** (Orchestration / Frontend /
Intermediate Representation / Execution), establish an **exhaustible compilation stage contract**
and an **obligations ledger**, and provide an **equivalence oracle** together with an
**anti-regression gate**.

Detailed designs are placed in nine companion documents under `docs/src/dev/architecture/`. This RFC
is only responsible for: the problem, root causes, the four-layer model, the acceptance criteria
grading, and the execution stage sequence. **Reviewing this RFC alone is sufficient to decide
whether to initiate the project; the companion documents are the construction blueprints after
initiation.**

## Motivation

### 1. Boundaries Exist but Lack Enforceability

The layering in directory names (`frontend` / `middle` / `backends`) is clear. But **the boundary
only exists in people's awareness, with no mechanism guaranteeing it cannot be eroded**. Three
direct consequences.

#### 1.1 Compilation stages are wired by hand at five entry points, producing 11 behavioral inconsistencies

| Stage                       | Single-file `run` | Multi-file `run` | `check` | LSP (in-project) | LSP (single-file) |
| --------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing            | yes               | yes              | yes     | yes              | yes               |
| typecheck                   | yes               | yes              | yes     | yes              | yes               |
| **proof_execution**         | **yes**           | **no**           | **no**  | **no**           | **no**            |
| dead code analysis          | yes               | no               | yes     | no               | no                |
| W1006 shadowing diagnostics | no                | no               | yes     | no               | no                |
| monomorphization            | yes               | no               | no      | no               | no                |
| IR generation / linking     | yes               | yes              | no      | no               | no                |

The five entry points are: `src/frontend/pipeline.rs:141-227` (single file, the 5 stages at `149` /
`161` / `173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), the four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `src/lib.rs`'s `run_file:140` /
`run_project:154`.

The most severe cell causes a **correctness vulnerability**. Proof function constraints of the form
`x: Sorted(3)` **silently pass** on the multi-file, check, and LSP paths. The evidence chain (all
verifiable):

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** place in the entire
   repository that constructs a non-empty `proof_calls`, with the semantics of "this constraint
   requires executing the proof function."
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches handling `Unproven`:
   `5164` / `5306` / `5420` are `if calls.is_empty()` → push a hard error; `5179` / `5318` / `5448`
   are `ctx.proof_calls.extend(...)` → **produces no diagnostics whatsoever**. The comment at `5165`
   literally states "Unproven → compile error, no degradation, no silent pass... must not let silent
   pass return."
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is **read in only one place in the entire
   repository: `src/frontend/pipeline.rs:187`**.
4. All four entry points in `orchestrator.rs` **do not read this field**.

That is: an invariant the code itself declares is broken by the architecture, not the logic. The
existence of `compile_embedded_module` (`orchestrator.rs:1374`) means **the refinement obligations
of the embedded std module itself also take this discarded path**.

**No test can catch it**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit tests directly call `check_module` and assert
"`proof_calls` is non-empty," **stopping exactly before the pipeline** — they verify "it was
filled," but the bug is "the consumer never reads it."

#### 1.2 Module boundaries can be bypassed without leaving traces

`src/frontend/core/typecheck/checker.rs:5618` is `include!("checker/semantic_tokens.rs");` — **the
only `include!` in the entire repository**. It splices 1547 lines of text into the `checker` module.
This file **is not declared as any module** (`grep 'mod semantic_tokens'` returns zero hits in the
entire repo), its first line directly starts with `impl TypeChecker {`, has no `use` header of its
own, and the `checker/` directory contains only this one file.

Consequences: no module identity, visibility isolation fails, rust-analyzer's jump-to and symbol
search are broken for it, and toolchain analysis counts it as part of `checker.rs`. **The real size
of the `checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618 lines the directory statistics
show.

#### 1.3 Test wiring relies on human memory, corruption happens silently

A reachability analysis via BFS over the module graph from the two crate roots `src/lib.rs` /
`src/main.rs`: **24 files / 2628 lines never participate in compilation**. Of these, 23 files / 1081
lines are real orphans.

| Orphan                                      | Size                 | Content                                                                              |
| ------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------ |
| Entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + `mod.rs` 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                  | 3 files / 14 lines   | All placeholder documentation comments                                               |
| `package/template/tests/`                   | 3 files / 65 lines   | 7 `#[test]`                                                                          |
| `parser/pratt/tests/precedence_inline.rs`   | 95 lines / 6 tests   | Hidden in a live directory                                                           |
| `typecheck/passes/tests/overload_inline.rs` | 170 lines / 7 tests  | Same as above                                                                        |
| `util/diagnostic/emitter/tests/json.rs`     | 46 lines / 3 tests   | Same as above                                                                        |

`cargo test` cannot discover them: tests that have never run cannot fail. CI
(`.github/workflows/ci.yml:140`) also has no test count baseline or wiring check.

**A total of 1005 lines / 78 tests have never run.** The lexical layer's only actually running test
is `fstring.rs` (wired in via a `#[path]` attribute bypass).

### 2. Design Capability Is Sufficient

At the same time, it must be acknowledged: this project **already has** mature enforcement
mechanisms, they just have not been extended.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subjected to a
build-time hard gate by `build.rs:19-55` through `tools/code-tables` — parses the registry,
validates uniqueness and segment position, compares each entry against RFC-013's markdown code
table, **any inconsistency directly `panic!`s and refuses to compile**. RFC-013's documentation and
code are therefore always consistent.

`src/package/` (76 files / 13,012 lines) is the most complete area: **tests 6,227 lines, 47.9%**; 5
of 6 `tests/` directories are correctly wired (the sole exception is `template/tests/`, see Section
A). Note that this positive sample holds at the **directory-level wiring**, not at every file — of
76 `.rs` files, only 7 contain inline `#[cfg(test)]` and 5 contain `mod tests;`. The 5 RFCs match
the code item by item, and several "not implemented" entries materialize as explicit errors rather
than silent TODOs (cmake at `build/mod.rs:172-174`, `RegistryDeferred` at `error.rs:74-76`).
`.yxpkg` has five layers of safety protection, all correct.

**In the same repository, with the same authors, `package/` gets test directory wiring right, while
`lexer/tests/` has never run once. The difference is not in capability, but in whether anyone runs
the check.**

### 3. Empty-Design (Headless Design)

The three documents under `docs/src/dev/design/check/` describe an architecture that **never
existed**: `CheckSession` (including the Rust code draft at `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, `HotReloader` all have zero hits in the repo; the `traits/`
directory does not exist; the `check_single_module` function does not exist (only living in test
comments); even the `command.rs` busy-wait referenced in "known limitations" does not exist (the
file has neither `Instant` nor `recv_timeout`).

Cross-file analysis is actually implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, roughly 2670 lines) — the capability is real, the path is completely
different. **This document writes "designs that may exist in the future" as "defects of an
already-implemented system."**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the cleanest physical evidence of "test skeletons were built per design, but no corresponding
implementation exists in the pipeline, so they were left behind."

Additionally, `RFC-018` (LLVM AOT, 1037 lines, status: accepted) has 0 lines of implementation in
the code — the 6 hits in `backends/mod.rs` related to AOT **are all comments**.

## Root Cause Diagnosis

Combining the three categories of symptoms, the root cause is singular:

> **This project treats "design" as a documentation convention, not as an executable constraint.**

| Layer           | Missing Enforcement                                                 | Existing but Unextended Example                                              |
| --------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Stage boundary  | A single decision point for "which stages did this compilation run" | —                                                                            |
| Module boundary | Prohibit `include!`, restrict `pub(crate)` cross-layer leakage      | —                                                                            |
| Cross-reference | Detectability of "field produced but no one consumes"               | `build.rs`'s error code gate                                                 |
| Test wiring     | Declaring a directory must come with a `mod` declaration            | `src/package/`'s directory-level wiring convention (5 of 6 `tests/` correct) |

This RFC's stance is therefore: **turn stage, module, and cross-reference boundaries from
"documentation convention" into "assertable facts at compile-time or test-time"**, and **establish a
single stage decision point at the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 Orchestration                                              │
│   Who decides which stages run, how many times, how failures propagate │
│   Current: pipeline.rs(740) + orchestrator.rs(1528)             │
│           + compiler.rs(267) = 5 entry points, 11 inconsistencies │
│   Target:  Single Driver + exhaustible Stage enum + Obligations ledger │
│   See:     ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ Compilation Unit (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 Frontend                                                   │
│   Lexical, syntactic, AST construction                         │
│   Current: lexer/(3065) + parser/(6341)                        │
│           Hand-rolled lexer + hand-rolled Pratt; adding an operator requires │
│           6-7 changes inside L2 + 17 downstream production files │
│   Target:  Lexical converges to a single implementation + LALRPOP grammar-driven syntax │
│   See:     ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 Semantic & IR                                              │
│   Type checking, static analysis, IR construction              │
│   Current: typecheck/(29466 production) + ir.rs(905) + ir_gen.rs(8448) │
│           3 parallel type representations + 3 parallel operator enums;  │
│           ir_gen single impl 7952 lines / 116 methods; no IR-level validator │
│   Target:  Single type representation; IR satisfies SSA construction discipline │
│   See:     ../compiler-architecture/03-type-unification.md         │
│           ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 Execution                                                  │
│   Bytecode generation, interpreter, runtime, standard library   │
│   Current: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│           + runtime/(1800) + std/(7543)                         │
│   Target:  Opcode single source of truth + generation-time gate; Execution layer unaware of L1-L3 │
│   See:     ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (only consumes AST data, does not call parser); L4
depends only on L3's product format.

The list of known reverse dependencies and parallel definitions is in the routing table C of
`../compiler-architecture/01-routing.md`.

### Equivalence Oracle Grading

**This is the safety net for the entire refactoring and must be established before any code
change.** The detailed design is in `07-equivalence-oracle.md`.

Core principle: **criteria are graded by refactoring category, because different categories need
different strengths of equivalence.** Using a single criterion (usually "IR snapshot byte-equality")
to cover all refactorings is wrong — some refactorings **necessarily change the IR shape**.

| Category | Refactoring Content                                             | Criterion Type                                                          | Strength  |
| -------- | --------------------------------------------------------------- | ----------------------------------------------------------------------- | --------- |
| **C1**   | Pure move (split files, change directories, extract submodules) | IR normalized snapshot **zero-diff**                                    | Strongest |
| **C2**   | Orchestration changes (staging, unified Driver)                 | Each entry point's diagnostic set identical + corpus behavior identical | Strong    |
| **C3**   | Type representation convergence                                 | Diagnostic **code** identical (message wording may change)              | Strong    |
| **C4**   | IR shape change (SSA-ization)                                   | **Behavioral equivalence** + IR structural invariants                   | Medium    |
| **C5**   | Frontend paradigm change                                        | AST snapshot + diagnostics + behavior, all three used                   | Strong    |
| **C6**   | Pure deletion                                                   | No equivalence needed, only confirm no references                       | —         |

**The distinction between C1 and C4 is key**: C1 requires the IR to be byte-identical; C4
acknowledges the IR will change, switching to "program behavior identical + IR satisfies
invariants". Forcing snapshots on C4 will induce the team to relax the criteria.

Three-layer criteria:

1. **IR static validator** — Dominance use-before-def, jump targets exist, types consistent, inner
   isolation. Far stronger than snapshots, covers defects like "IR self-consistent but value wrong"
   that snapshots cannot detect. Must **first run green on the existing (non-SSA) IR**.
2. **Normalized IR snapshot** — Strip `Span`, rename temporaries in order of appearance, relativize
   global slots, sort predecessors. Checked in, manually review diff. **Known limitation**:
   normalization erases "which register the Nth argument used", therefore **alone insufficient to
   cover `arg_regs` semantic reshuffling**.
3. **End-to-end corpus diff** — Diagnostic list, exit code, stdout/stderr compared item by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml`** anywhere in the
> `tests/` directory (verified 0), therefore the **293** `.yx` corpus in `tests/yaoxiang/` **all
> take the single-file path** (the standalone branch of `check_files_with_diagnostics` →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third-layer criterion **can only validate changes on the single-file path**.
> For the multi-file side (the four entry points of `orchestrator`) and multi-file manifestations of
> types/SSA, **there is currently no corpus coverage at all**. P4 "Unified Driver" is the biggest
> risk point in the entire plan, **the multi-file corpus layer must be unconditionally established
> in P2** (Resolution D40) — it is the sole executable behavioral criterion source for P4.

## Implementation Strategy

### Stage Sequence

```
P0  Repository maintenance mechanism and code placement rules 08        ← Set rules first: three prohibitions + D0-D4 decision procedure
P1  Revive orphan tests and fix defects        06 §S1   ← Cheapest, highest payoff
P2  Establish equivalence oracle baseline          07 all
P3  Fix correctness vulnerability (minimal solution)      02 §Fix
P3.5 Delete pub and auto-binding        RFC-029g / #399  ← Ordering constraint D56, must precede P4
P4  Stage contract and unified Driver        02
P5  Split inside checker file          09 §P5 fill-in
P6  Type representation unification              03
P7  Intermediate representation SSA-ization             04     } parallelizable
P8  Frontend paradigm change                05     }
P9  Anti-regression gate (unified script inventory)     01 + 08
P10 Remaining cleanup and status correction          06 §S2-S6
```

**Core serial constraints (non-interchangeable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every action of P1 — 1.2.x is about adding `mod` declarations to `mod.rs`, which is precisely the cause of the `precedence_inline.rs` life-and-death conflict                                                                                                                                                                                                                |
| P1 → P2      | Reviving tests will change test counts and corpus baseline. Establishing baseline first will fail after P1                                                                                                                                                                                                                                                                                                    |
| P2 → P3      | The vulnerability criterion must **first be written as red** to prove the fix works. **Narrowing (D51)**: P3's prerequisites are only 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two red criteria); the rest of P2 can run in parallel with P3, but P4 must wait for P2 to complete in full — stopping the bleeding of the correctness vulnerability is not blocked by oracle infrastructure construction |
| P3 → P4      | Fix the bug first, then refactor. Reverse order will let the bug be固化 into "established behavior" by the stage table                                                                                                                                                                                                                                                                                        |
| P3.5 → P4    | RFC-029g (#399)'s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8 respective rewrite targets (role dispatch within `check_project`, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer`+`parser`). Reverse order equals redoing the same batch of deletions on new grammar, new checker layout, new IR (D56)                                                                                      |
| P4 → P5      | P5 starts with `include!` → real `mod` (09 §P5 5.1), subsequent checker split moves the same file, must be done consecutively after P4                                                                                                                                                                                                                                                                        |
| P5 → P6      | Consecutive changes to the same file must be separated, otherwise regressions cannot be binary-localized                                                                                                                                                                                                                                                                                                      |
| P6 → P7 / P8 | Without first unifying type representation, SSA's new IR will grow into a third representation                                                                                                                                                                                                                                                                                                                |
| P7/P8 → P9   | The initial baselines for each gate script (e.g. `pub(crate)` leakage count) only take their final values after P7/P8                                                                                                                                                                                                                                                                                         |
| P7 ∥ P8      | File sets are disjoint, can be parallel                                                                                                                                                                                                                                                                                                                                                                       |

**Why P0 is an independent stage**: P9's CI scripts are **after-the-fact checks** that can only
catch bad code already written; "should refactor but patched instead" is a **pre-judgment** that
only the D0–D4 decision procedure can catch. The two cannot replace each other.

### Each Stage's Definition of Done (DoD)

For a stage to be considered complete, all of the following must hold simultaneously:

1. All corresponding "implementation strategy" steps in the belonging document are committed
2. The criteria of that category (C1-C6) in `07-equivalence-oracle.md` **are green in CI**
3. `cargo test` all green, and **test count is not less than at the start of the stage** (prevent
   "delete tests for green light")
4. `cargo clippy --all --all-features -- -D warnings` clean
5. `python scripts/rfc/check_tracking.py` exit code 0
6. The stage has an independent revert unit — **if a stage cannot be independently reverted, it is

## Trade-offs

### Advantages

- **Provides a landing point for all subsequent changes.** "Adding an operator requires changing a
  dozen places, and no one knows when one is missed" cannot be improved by memory, only by routing
  tables + gates.
- **Single root cause.** Three categories of symptoms (stage inconsistency, `include!`, test wiring
  breakage) all stem from "boundaries are conventions not constraints" and can be solved at once
  with the same kind of mechanism.
- **Non-blocking.** This RFC has zero code changes. The four-layer model is descriptive; after
  adoption, only parts of it can still be executed.
- **Criteria first.** P2 is established before any code change, and the grading design avoids the
  common failure of "snapshot too strict → induced relaxation".

### Disadvantages and Risks

- **The serial chain is long.** P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly fully serial; later
  stages have to wait for earlier ones to complete.
- **P1 will introduce new bug workload**, and it is the step most likely to be skipped with "because
  we need to fix bugs, we won't do it first" — but skipping it, all subsequent stages' acceptance
  criteria are built on a false coverage.
- **P4 is the biggest single point of risk**: one change touching 5 entry points.
- **P6 has the widest impact surface**: touches common dependencies of parser, formatter, spawn,
  orchestrator.
- **P7's line count will net increase by 900-1600 lines, not net decrease.** Splitting introduces
  boilerplate, `verify` 300-600 lines, register allocation 600-1000 lines. **If the project is
  judged on "code becomes shorter" at initiation, this stage will be judged a failure** — this must
  be aligned at initiation.

## Alternatives

### A. Only split files, don't change paradigms

Split 8448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting does not eliminate any root cause: the 6 hand-rolled save/restore still
scatter across 10 files, `generate_call_expr_ir`'s `arg_regs` semantic reshuffling still requires
manual reasoning, "adding an operator changes a dozen places" is still a dozen places. Splitting
improves navigation, not correctness.

### B. Only add gates, don't change structure (including line count ratchet)

**Not adopted as the sole solution, but it is a part of this RFC.** Gates can prevent degradation,
but cannot fix the current state — `ir_gen.rs` already has 8448 lines, gates can only freeze it at
that number.

### C. Start over, write a new compiler skeleton

**Not adopted.** `src/package/` proves this team can get complex systems right. The problem is not
in capability. And the existing 293 `.yx` corpus provides a ready equivalence criterion source;
rewriting from scratch would waste this asset.

### D. Use an existing compiler framework (e.g. LLVM as the only backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) has reserved an abstraction point but
only has one implementer. Introducing LLVM is the scope of `RFC-018` (1037 lines of design, 0 lines
of code), should be **decided independently** — it changes "what to compile to" rather than "how to
organize code".

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustible step in a compilation. The stage set must be an exhaustible enumeration, not runtime-registered                            |
| **Orchestration Layer (L1)**               | The layer that decides which stages run, how many times, how failures propagate                                                           |
| **Frontend Layer (L2)**                    | Lexical and syntactic, producing AST                                                                                                      |
| **Intermediate Representation Layer (L3)** | Type checking, static analysis, IR construction                                                                                           |
| **Execution Layer (L4)**                   | Bytecode generation, interpreter, runtime, standard library                                                                               |
| **Obligation**                             | A contract item produced by some stage, must be consumed downstream or compilation fails                                                  |
| **Obligations Ledger**                     | Container of all obligations, uniformly settled at the end of the stage table                                                             |
| **Orphan**                                 | A file that has never been referenced by any `mod` declaration, and therefore has never participated in compilation                       |
| **Shell**                                  | A file that has been declared, entered the compilation product, but only has documentation comments or unused `use`, with zero assertions |
| **Equivalence Oracle**                     | An executable check that proves behavior has not changed before and after refactoring                                                     |
| **C1-C6**                                  | Refactoring category grading, determines criterion strength. **No C5′ exists**                                                            |
| **Responsibility Separation**              | The only solution to scale problems: a module takes only one category of responsibility. **No line count / volume gates**                 |
| **Decision Register**                      | This RFC's "Decision Register" section, final ruling on all open items                                                                    |
