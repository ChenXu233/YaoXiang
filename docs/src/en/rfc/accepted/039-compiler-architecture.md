# RFC-039: Compiler Architecture Refactoring

## Summary

This RFC proposes an architectural refactoring for the YaoXiang compiler (`src/` 160,002 lines / 509
`.rs` files): redraw boundaries with a **four-layer model** (Orchestration / Frontend / Intermediate
Representation / Execution), establish an **exhaustive compilation stage contract** and an
**obligations ledger**, and bundle a set of **equivalence criteria** and **rebound-prevention
gates**.

Detailed design is placed in nine companion documents under `docs/src/dev/architecture/`. This RFC
is responsible only for: the problem, root cause, the four-layer model, acceptance criteria grading,
and execution stage sequence. **Reviewing this RFC alone suffices to decide whether to approve the
project; the companion documents are the construction blueprint after approval.**

## Motivation

### I. Boundaries Exist, but Have No Enforceability

The layered naming in directories (`frontend` / `middle` / `backends`) is clear. But **boundaries
only exist in human self-discipline; there is no mechanism to guarantee they won't be eroded.**
Three direct consequences.

#### 1.1 Compilation stages are hand-wired at five entry points, producing 11 behavioral inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (in project) | LSP (single file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing           | yes               | yes              | yes     | yes              | yes               |
| typecheck                  | yes               | yes              | yes     | yes              | yes               |
| **proof_execution**        | **yes**           | **no**           | **no**  | **no**           | **no**            |
| dead code analysis         | yes               | no               | yes     | no               | no                |
| W1006 shadowing diagnostic | no                | no               | yes     | no               | no                |
| monomorphization           | yes               | no               | no      | no               | no                |
| IR generation / linking    | yes               | yes              | no      | no               | no                |

The five entry points: `src/frontend/pipeline.rs:141-227` (single file, 5 stages at `149` / `161` /
`173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `src/lib.rs`'s `run_file:140` /
`run_project:154`.

The most severe cell causes a **correctness vulnerability**. A proof function constraint of the form
`x: Sorted(3)` silently passes on three paths: multi-file, check, and LSP. Evidence chain (all
verifiable):

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a non-empty `proof_calls`, with the semantics "this constraint
   requires executing a proof function."
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches handling `Unproven`:
   `5164` / `5306` / `5420` are `if calls.is_empty()` → push hard error; `5179` / `5318` / `5448`
   are `ctx.proof_calls.extend(...)` → **produces no diagnostic at all**. The comment at `5165`
   reads: "Unproven → compile error, no degradation, no silent pass... must not let silent pass
   return."
3. `TypeCheckResult.proof_calls` (`types.rs:29`) has **only one read site in the entire
   repository**: `src/frontend/pipeline.rs:187`.
4. The four entry points in `orchestrator.rs` **all skip this field**.

That is: the invariant the code itself declares is broken by the architecture rather than by logic.
The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means **even the refinement
obligations of the std module itself take this discarded path**.

**No test can catch it**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit tests call `check_module` directly and assert
"`proof_calls` is non-empty", **stopping right before the pipeline**—they verify "was filled in",
while the bug is "the consumer didn't read it."

#### 1.2 Module boundaries can be bypassed without a trace

`src/frontend/core/typecheck/checker.rs:5618` is `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1547 lines of text into the `checker`
module. This file **is not declared as any module** (`grep 'mod semantic_tokens'` returns zero hits
in the entire repo), its first line is directly `impl TypeChecker {` with no `use` header of its
own, and the `checker/` directory contains only this one file.

Consequence: no module identity, visibility isolation fails, rust-analyzer's navigation and symbol
search fail on it, toolchain analysis counts it as part of `checker.rs`. **The true size of the
`checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618 lines shown by directory statistics.

#### 1.3 Test wiring relies on human memory; corruption happens silently

Running BFS reachability analysis on the module graph from the two crate roots `src/lib.rs` /
`src/main.rs`: **24 files / 2628 lines never participate in compilation**. Of these, 23 files / 1081
lines are true orphans.

| Orphan                                      | Size                 | Content                                                                               |
| ------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------- |
| Entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totalling 19 lines + `mod.rs` 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                  | 3 files / 14 lines   | All placeholder doc comments                                                          |
| `package/template/tests/`                   | 3 files / 65 lines   | 7 `#[test]`                                                                           |
| `parser/pratt/tests/precedence_inline.rs`   | 95 lines / 6 tests   | Hidden in a live directory                                                            |
| `typecheck/passes/tests/overload_inline.rs` | 170 lines / 7 tests  | Same as above                                                                         |
| `util/diagnostic/emitter/tests/json.rs`     | 46 lines / 3 tests   | Same as above                                                                         |

`cargo test` cannot discover them: tests that haven't been run cannot fail. CI
(`.github/workflows/ci.yml:140`) also has no test count baseline or wiring check.

**Tests that have never run total 1005 lines / 78 cases.** At the lexer layer, only `fstring.rs`
(wired in via `#[path]` attribute bypass) is actually running.

### II. Design Capability Is Sufficient

It must be acknowledged at the same time: this project **already has** mature enforcement
mechanisms; they just haven't been generalized.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subject to a
build-time hard gate by `build.rs:19-55` via `tools/code-tables`—it parses the registry, validates
uniqueness and severity bands, compares each entry against the RFC-013 markdown code table item by
item, and **`panic!`s to refuse compilation on any inconsistency**. The RFC-013 document and code
are therefore always in sync.

`src/package/` (76 files / 13,012 lines) is the most complete region: **tests are 6,227 lines,
47.9%**; 5 of 6 `tests/` directories are correctly wired (the only exception is `template/tests/`,
see Section A). Note this positive sample rests on **directory-level wiring**, not on every
file—among 76 `.rs` files, only 7 contain inline `#[cfg(test)]` and 5 contain `mod tests;`. The 5
RFCs match the code item by item, and many "not yet implemented" cases have landed as explicit
errors rather than silent TODOs (cmake in `build/mod.rs:172-174`, `RegistryDeferred` in
`error.rs:74-76`). `.yxpkg` has five layers of safety protection and all of them are correct.

**In the same repository, with the same author, `package/` got test directory wiring right, while
`lexer/tests/` has never been run. The difference is not in capability, but in whether someone runs
a check once.**

### III. Empty-Head Design

The three documents under `docs/src/dev/design/check/` describe an **architecture that never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, `HotReloader` all return zero hits in the entire repo; the
`traits/` directory does not exist; the `check_single_module` function does not exist (it lives only
in test comments); even the `command.rs` busy-wait cited in "known limitations" doesn't exist (the
file has neither `Instant` nor `recv_timeout`).

Cross-file analysis is actually implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, about 2670 lines)—the capability is real, the path is entirely
different. **This document writes "a possible future design" as "the defect of an
already-implemented system."**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the cleanest physical evidence of "built the test skeleton per design, discovered the pipeline has
no corresponding implementation, and just left it there."

Additionally, `RFC-018` (LLVM AOT, 1037 lines, status accepted) has 0 lines of implementation in the
code—the 6 AOT-related hits in `backends/mod.rs` are **all comments**.

## Root Cause Diagnosis

Combining the three symptom categories, the root cause is singular:

> **This project treats "design" as a documentation convention, not as an executable constraint.**

| Layer             | Missing enforcement                                              | Existing but ungeneralized example                                            |
| ----------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Stage boundaries  | A single decision point for "which stages this compilation runs" | —                                                                             |
| Module boundaries | Prohibit `include!`, restrict `pub(crate)` cross-layer leakage   | —                                                                             |
| Cross-references  | Detectability of "field produced but consumed by no one"         | Error code gate in `build.rs`                                                 |
| Test wiring       | Declaring a directory must come with a `mod` declaration         | Directory-level wiring convention in `src/package/` (5 of 6 `tests/` correct) |

The stance of this RFC is therefore: **promote stage, module, and cross-reference boundaries from
"documentation convention" to "facts assertable at compile-time or test-time"**, and **establish a
single stage decision point at the orchestration layer**.

## Proposal

### The Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 Orchestration Layer                                       │
│   Who decides which stages run, how many times,             │
│   how failures propagate                                     │
│   Current: pipeline.rs(740) + orchestrator.rs(1528)         │
│            + compiler.rs(267) = 5 entry points, 11 inconsistencies
│   Target:  Single Driver + exhaustible Stage enum +          │
│            Obligations ledger                                │
│   See:     ../compiler-architecture/02-stage-contract.md       │
└───────────────────────────┬─────────────────────────────────┘
                            │ Compilation Unit
┌───────────────────────────▼─────────────────────────────────┐
│ L2 Frontend Layer                                            │
│   Lexing, parsing, AST construction                          │
│   Current: lexer/(3065) + parser/(6341)                     │
│            Manual lexer + manual Pratt; adding an operator   │
│            requires changes in 6-7 places within L2 +        │
│            17 downstream production files                    │
│   Target:  Converge lexer to single implementation +         │
│            LALRPOP grammar-driven syntax                     │
│   See:     ../compiler-architecture/05-frontend-paradigm.md    │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 Semantic & Intermediate Representation                    │
│   Type checking, static analysis, IR construction            │
│   Current: typecheck/(29466 production) + ir.rs(905) +       │
│            ir_gen.rs(8448); 3 parallel type representations +│
│            3 parallel operator enums;                       │
│            ir_gen single impl 7952 lines / 116 methods;     │
│            no IR-level verifier                              │
│   Target:  Unify type representation; IR satisfies          │
│            SSA construction discipline                       │
│   See:     ../compiler-architecture/03-type-unification.md     │
│            ../compiler-architecture/04-ssa.md                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 Execution Layer                                           │
│   Bytecode generation, interpreter, runtime, std library     │
│   Current: codegen/(3436) + bytecode.rs(2422) + executor/(2000)
│            + runtime/(1800) + std/(7543)                    │
│   Target:  Single source of truth for opcodes + generation-  │
│            time gate; execution layer unaware of L1-L3       │
│   See:     ../compiler-architecture/06-cleanup-inventory.md    │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it only consumes AST data, never calls parser); L4
depends only on the L3 output format.

The known reverse dependencies and parallel definition inventory is in
`../compiler-architecture/01-routing.md` routing table C.

### Equivalence Criteria Grading

**This is the safety net for all refactoring and must be established before any code change.**
Detailed design is in `07-equivalence-oracle.md`.

Core principle: **criteria are graded by refactoring category, because different categories need
different strengths of equivalence.** Using a single criterion (usually "IR snapshot fully equal")
to cover all refactoring is wrong—some refactoring **inevitably changes the IR form**.

| Category | Refactoring content                                             | Criterion type                                         | Strength  |
| -------- | --------------------------------------------------------------- | ------------------------------------------------------ | --------- |
| **C1**   | Pure move (split files, change directories, extract submodules) | IR canonicalized snapshot **zero-diff**                | Strongest |
| **C2**   | Orchestration change (staging, unified Driver)                  | Same diagnostic set per entry + same corpus behavior   | Strong    |
| **C3**   | Type representation convergence                                 | Same diagnostic **codes** (message wording may change) | Strong    |
| **C4**   | IR form change (SSA-ification)                                  | **Behavioral equivalence** + IR structural invariants  | Medium    |
| **C5**   | Frontend paradigm change                                        | AST snapshot + diagnostic + behavior, all three used   | Strong    |
| **C6**   | Pure deletion                                                   | No equivalence needed, only confirm no references      | —         |

**The difference between C1 and C4 is the key**: C1 requires IR byte-for-byte equality; C4
acknowledges IR will change, switching to "same program behavior + IR satisfies invariants". Forcing
snapshots on C4 will induce the team to relax the criterion.

Three-layer criteria:

1. **IR static verifier** — dominating use-before-def, jump targets exist, type consistent,
   inner-layer isolation. Much stronger than snapshots, covers defects like "IR self-consistent but
   values wrong" that snapshot tests cannot catch. Must **run green on the current (non-SSA) IR
   first**.
2. **Canonicalized IR snapshot** — strip `Span`, rename temporaries by appearance order, relativize
   global slots, sort predecessors. Checked in, manual diff review. **Known limitation**:
   canonicalization erases "which register the Nth argument used", so it is **alone insufficient to
   cover `arg_regs` semantic reordering**.
3. **End-to-end corpus diff** — diagnostic list, exit code, stdout/stderr compared item by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml`** under the
> `tests/` directory (verified 0), so the **293** `.yx` corpora in `tests/yaoxiang/` **all go
> through the single-file path** (the standalone branch of `check_files_with_diagnostics` →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third-layer criterion **can only verify changes on the single-file path**.
> For the multi-file side (the four entry points in `orchestrator`) and the multi-file performance
> of types/SSA, **there is currently no corpus coverage**. P4 "Unify Driver" is the highest risk
> point in the entire plan; the **multi-file corpus layer must be unconditionally established in
> P2** (decision D40)—it is the only executable behavioral criterion source for P4.

## Implementation Strategy

### Stage Sequence

```
P0  Repository maintenance mechanism and code placement rules 08   ← Set rules first: 3 prohibitions + D0-D4 decision procedure
P1  Revive orphan tests and fix defects                06 §S1   ← Cheapest, highest payoff
P2  Establish equivalence criteria baseline            07 all
P3  Fix correctness vulnerability (minimal solution)   02 §fix
P3.5 Delete pub and auto-binding                RFC-029g / #399  ← Ordering constraint D56, must precede P4
P4  Stage contract and unified Driver                 02
P5  Split within checker file                         09 §P5 completion
P6  Type representation unification                   03
P7  Intermediate representation SSA-ification         04    } Parallel
P8  Frontend paradigm change                          05    }
P9  Rebound-prevention gates (unified script list)    01 + 08
P10 Remaining cleanup and status correction           06 §S2-S6
```

**Core serial constraints (non-swappable):**

| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every action of P1—1.2.x is precisely adding `mod` declarations to `mod.rs`, which is exactly what caused the life-and-death conflict with `precedence_inline.rs`                                                                                                                                                                                                    |
| P1 → P2      | Reviving tests will change the test count and corpus baseline. Establishing the baseline first will become invalid after P1                                                                                                                                                                                                                                                                           |
| P2 → P3      | The vulnerability criterion must be **written as red first** to prove the fix is effective. **Narrowing (D51)**: P3's prerequisites are only 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two red criteria); the rest of P2 can run in parallel with P3, but P4 must wait for all of P2—stopping the correctness vulnerability bleeding must not be blocked by criteria infrastructure construction |
| P3 → P4      | Fix bugs first, then refactor. Reversing would let the bug be solidified by the stage table as "established behavior"                                                                                                                                                                                                                                                                                 |
| P3.5 → P4    | The deletion surface of RFC-029g (#399) covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 respectively (`check_project`'s role dispatch, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer`+`parser`). | P4 → P5      | P5 opens with `include!` → real `mod` (09 §P5 5.1); the subsequent checker split moves the same file, must proceed consecutively after P4                                                                                                                                                                                                                                                             |

### Definition of Done (DoD) per Stage

A stage is complete only when all of the following are satisfied:

1. All corresponding "implementation strategy" steps in the attribution document are committed
2. The criteria (C1-C6) for that category in `07-equivalence-oracle.md` are **green in CI**
3. `cargo test` all green, and **test count is not lower than when this stage started** (prevent
   "delete tests to get green light")
4. `cargo clippy --all --all-features -- -D warnings` clean
5. `python scripts/rfc/check_tracking.py` exit code 0
6. The stage has an independent revert unit—**if a stage cannot be reverted alone, it is too large
   and needs further splitting**
7. For stages touching the compilation pipeline or execution path (P4 / P6 / P7 / P8), 07's
   performance baseline comparison shows no unexplained >10% regression

## Trade-offs

### Advantages

- **Provides a landing point for all subsequent changes**. "Adding an operator requires changes in a
  dozen places, missed changes go unnoticed" cannot be improved by memory, only by routing tables +
  gates.
- **Single root cause**. The three symptom categories (stage inconsistency, `include!`, test wiring
  break) all stem from "boundaries are conventions, not constraints", and can be solved with the
  same kind of mechanism in one shot.
- **Non-blocking**. This RFC has zero code changes. The four-layer model is descriptive; after
  adoption, only part of it can still be executed.
- **Criteria first**. P2 is established before any code change, and the graded design avoids the
  common failure of "snapshot too strict → induce relaxation".

### Disadvantages and Risks

- **Long serial chain**. P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is almost entirely serial; later stages
  wait for earlier ones to complete.
- **P1 will introduce new bug workload**, and this is the step most easily skipped by "because we
  need to fix bugs, do it later first"—but skipping it means the acceptance criteria for all
  subsequent stages rest on false coverage.
- **P4 is the biggest single point of risk**: one change to 5 entry points.
- **P6 has the widest impact**: touches the common dependencies of parser, formatter, spawn,
  orchestrator.
- **P7's line count will net increase by 900-1600 lines, not net decrease**. Splitting introduces
  boilerplate, `verify` 300-600 lines, register allocation 600-1000 lines. **If "shorter code" is
  used as the success criterion at project initiation, this stage will be judged as failed**—this
  must be aligned at project initiation.

## Alternatives

### A. Only Split Files, Don't Change Paradigm

Split 8448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting does not eliminate any root cause: the 6 manual save/restore sites are
still scattered across 10 files, the `arg_regs` semantic reordering in `generate_call_expr_ir` still
requires manual reasoning, and "adding an operator requires changes in a dozen places" is still a
dozen places. Splitting improves navigation, not correctness.

### B. Only Add Gates, Don't Change Structure (including line count ratchet)

**Not adopted as the sole approach, but it is part of this RFC.** Gates prevent regression but
cannot fix the current state—`ir_gen.rs` is already 8448 lines; the gate can only freeze it at this
number.

### C. Start Over, Write a New Compiler Skeleton

**Not adopted.** `src/package/` proves this team can build complex systems correctly. The problem is
not capability. And the existing 293 `.yx` corpora provide a ready source of equivalence criteria;
rewriting from scratch wastes this asset.

### D. Use an Existing Compiler Framework (e.g., LLVM as the sole backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already reserves an abstraction point
but has only one implementor. Introducing LLVM falls under the scope of `RFC-018` (1037 lines of
design, 0 lines of code), and should be **decided independently**—it changes "what to compile to"
rather than "how to organize code".

## Appendix: Glossary

| Term                                       | Definition                                                                                                                          |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustible step in a compilation. The stage set must be an exhaustible enum, not runtime-registered                             |
| **Orchestration Layer (L1)**               | The layer that decides which stages run, how many times, and how failures propagate                                                 |
| **Frontend Layer (L2)**                    | Lexing and syntax, producing AST                                                                                                    |
| **Intermediate Representation Layer (L3)** | Type checking, static analysis, IR construction                                                                                     |
| **Execution Layer (L4)**                   | Bytecode generation, interpreter, runtime, std library                                                                              |
| **Obligation**                             | A contract item produced by a stage that must be consumed by downstream or compilation fails                                        |
| **Obligations Ledger**                     | The container of all obligations, settled at the end of the stage table                                                             |
| **Orphan**                                 | A file never referenced by any `mod` declaration, therefore never participating in compilation                                      |
| **Shell**                                  | A file that has been declared, enters the compilation product, but contains only doc comments or unused `use`, with zero assertions |
| **Equivalence Oracle**                     | Executable checks that prove behavior is unchanged before and after refactoring                                                     |
| **C1-C6**                                  | Refactoring category grading, determining criterion strength. **C5′ does not exist**                                                |
| **Responsibility Separation**              | The only solution to size problems: one module carries only one kind of responsibility. **No line count / size gate**               |
| **Decision Registry**                      | The "Decision Registry" section of this RFC, the final adjudication of all open items                                               |
