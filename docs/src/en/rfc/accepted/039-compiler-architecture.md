# RFC-039: Compiler Architecture Refactoring

## Summary

This RFC proposes an architectural refactoring of the YaoXiang compiler (`src/`, 160,002 lines
across 509 `.rs` files): redefine the boundaries through a **four-layer model** (orchestration /
frontend / intermediate representation / execution), establish **exhaustively enumerable
compilation-stage contracts** and an **obligation ledger**, and provide a corresponding set of
**equivalence criteria** and **anti-regression gates**.

The detailed design is contained in nine companion documents under `docs/src/dev/architecture/`.
This RFC is responsible only for the problem, root cause, four-layer model, tiered acceptance
criteria, and execution-stage sequence. **Reviewing this RFC is sufficient to decide whether to
approve the project; the companion documents are the construction blueprint after approval.**

## Motivation

### I. Boundaries Exist, but Have No Enforcement

The layering expressed by directory names (`frontend` / `middle` / `backends`) is clear. However,
**the boundaries exist only in people's diligence, with no mechanism ensuring that they are not
eroded**. This has three direct consequences.

#### 1.1 Compilation Stages Are Wired Manually in Five Entry Points, Producing 11 Behavioral Inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (in-project) | LSP (single-file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing           | Yes               | Yes              | Yes     | Yes              | Yes               |
| typecheck                  | Yes               | Yes              | Yes     | Yes              | Yes               |
| **proof_execution**        | **Yes**           | **No**           | **No**  | **No**           | **No**            |
| Dead-code analysis         | Yes               | No               | Yes     | No               | No                |
| W1006 shadowing diagnostic | No                | No               | Yes     | No               | No                |
| Monomorphization           | Yes               | No               | No      | No               | No                |
| IR generation / linking    | Yes               | Yes              | No      | No               | No                |

The five entry points are: `src/frontend/pipeline.rs:141-227` (single-file; five stages at `149` /
`161` / `173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), the four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `src/lib.rs`'s `run_file:140` /
`run_project:154`.

The most serious cell exposes a **correctness vulnerability**. A proof-function constraint such as
`x: Sorted(3)` **silently passes** through the multi-file, check, and LSP paths. The evidence chain,
all of which can be independently verified, is as follows:

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a nonempty `proof_calls`; its semantics are “this constraint requires
   executing a proof function.”
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches handling `Unproven`:
   `5164` / `5306` / `5420` use `if calls.is_empty()` to raise a hard error; `5179` / `5318` /
   `5448` use `ctx.proof_calls.extend(...)` and **produce no diagnostic whatsoever**. The comment at
   `5165` originally states: “Unproven → compile error, no fallback, no silent pass… silent pass
   must not return.”
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is read in **only one place in the entire
   repository**: `src/frontend/pipeline.rs:187`.
4. **None** of the four entry points in `orchestrator.rs` reads this field.

In other words, an invariant explicitly declared by the code itself is broken by the architecture
rather than by its logic. The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means
that **the refinement obligations of the embedded std module itself also follow this discard path**.

**No test can catch it**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit test directly calls `check_module` and asserts that
"`proof_calls` is nonempty," **stopping immediately before the pipeline**—they verify that it was
“populated,” while the bug is that the “consumer does not read it.”

#### 1.2 Module Boundaries Can Be Bypassed Without Leaving a Trace

`src/frontend/core/typecheck/checker.rs:5618` is `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1,547 lines of text into the `checker`
module. The file **is not declared as any module** (`grep 'mod semantic_tokens'` has zero hits
across the repository), its first line is directly `impl TypeChecker {`, it has no `use` header of
its own, and it is the only file in the `checker/` directory.

Consequences: there is no module identity, visibility isolation is ineffective, rust-analyzer's
go-to-definition and symbol search fail for it, and toolchain analysis treats it as part of
`checker.rs`. **The true size of the `checker` module is 5618 + 1547 ≈ 7165 lines**, rather than the
5618 lines shown by directory statistics.

#### 1.3 Test Wiring Depends on Human Memory, and Corruption Occurs Silently

A module-graph BFS reachability analysis starting from the two crate roots, `src/lib.rs` and
`src/main.rs`, shows that **24 files / 2,628 lines never participate in compilation**. Of these, 23
files / 1,081 lines are genuine orphans.

| Orphan                                      | Size                 | Contents                                                                            |
| ------------------------------------------- | -------------------- | ----------------------------------------------------------------------------------- |
| Entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + 38-line `mod.rs` + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                  | 3 files / 14 lines   | All placeholder documentation comments                                              |
| `package/template/tests/`                   | 3 files / 65 lines   | 7 `#[test]` functions                                                               |
| `parser/pratt/tests/precedence_inline.rs`   | 95 lines / 6 tests   | Hidden in a live directory                                                          |
| `typecheck/passes/tests/overload_inline.rs` | 170 lines / 7 tests  | Same as above                                                                       |
| `util/diagnostic/emitter/tests/json.rs`     | 46 lines / 3 tests   | Same as above                                                                       |

`cargo test` cannot discover these: a test that has never run cannot fail. CI
(`.github/workflows/ci.yml:140`) likewise has no test-count baseline or wiring check.

**The never-run real tests total 1,005 lines / 78 tests.** The only lexer-level test currently
running is `fstring.rs`, connected as a bypass through a `#[path]` attribute.

### II. The Design Capability Is Sufficient

At the same time, we must acknowledge that this project **already has** mature enforcement
mechanisms; they simply have not been extended throughout the codebase.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subject to a
compile-time hard gate through `tools/code-tables` in `build.rs:19-55`: the registry is parsed,
uniqueness and code ranges are validated, every entry is compared against RFC-013's Markdown code
table, and **any discrepancy immediately triggers `panic!` and refuses to compile**. RFC-013's
documentation and the code therefore remain consistently aligned.

`src/package/` (76 files / 13,012 lines) is the most complete area: **6,227 lines of tests,
accounting for 47.9%**; 5 of the 6 `tests/` directories are wired correctly, with `template/tests/`
as the sole exception (see Section A). Note that this positive example relies on **directory-level
wiring**, not per-file wiring: of 76 `.rs` files, only 7 contain inline `#[cfg(test)]`, and only 5
contain `mod tests;`. Five RFCs align with the code line by line, and many instances of “not
implemented” become explicit errors rather than silent TODOs (cmake in `build/mod.rs:172-174`,
`RegistryDeferred` in `error.rs:74-76`). `.yxpkg` has five layers of safety protection, all
correctly implemented.

**In the same repository, with the same authors, `package/` got the test-directory wiring right,
while `lexer/tests/` has never run even once. The difference is not capability; it is whether anyone
ran a check.**

### III. Paper-Only Design

The three documents under `docs/src/dev/design/check/` describe an architecture that **has never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, and `HotReloader` have zero hits across the repository; the
`traits/` directory does not exist; the `check_single_module` function does not exist (it survives
only in test comments); and even the `command.rs` busy-wait cited under “Known Limitations” does not
exist (that file contains neither `Instant` nor `recv_timeout`).

Cross-file analysis is in fact implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, approximately 2,670 lines)—the capability is real, but the path is
entirely different. **This document described a “potentially future design” as a defect in an
already implemented system.**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the clearest physical evidence of “we created a test skeleton according to the design, discovered
that the pipeline had no corresponding implementation, and set it aside.”

In addition, `RFC-018` (LLVM AOT, 1,037 lines, status accepted) has 0 lines of implementation in the
code—all 6 AOT-related hits in `backends/mod.rs` are **comments**.

## Root-Cause Diagnosis

Taken together, the three classes of symptoms have a single root cause:

> **This project treats “design” as a documentation convention rather than an executable
> constraint.**

| Layer             | Missing Enforcement                                                   | Existing but Unextended Example                                                                   |
| ----------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Stage boundaries  | A single decision point for “which stages does this compilation run?” | —                                                                                                 |
| Module boundaries | Prohibit `include!`; prevent `pub(crate)` from leaking across layers  | —                                                                                                 |
| Cross-references  | Detectability for “a field is produced but never consumed”            | The error-code gate in `build.rs`                                                                 |
| Test wiring       | Declaring a directory requires a corresponding `mod` declaration      | The directory-level wiring convention in `src/package/` (5 of 6 `tests/` directories are correct) |

The position of this RFC is therefore: **turn the three boundary classes—stages, modules, and
cross-references—from “documentation conventions” into “facts assertable at compile time or test
time,”** and **establish a unique stage decision point in the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 编排层 Orchestration                                      │
│   谁决定跑哪些阶段、跑几遍、失败如何传播                      │
│   现状: pipeline.rs(740) + orchestrator.rs(1528)             │
│         + compiler.rs(267) = 5 个入口, 11 处不一致           │
│   目标: 单一 Driver + 可穷举的 Stage 枚举 + Obligations 账本  │
│   详见: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 编译单元 (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 前端层 Frontend                                           │
│   词法、语法、AST 构造                                        │
│   现状: lexer/(3065) + parser/(6341)                        │
│         手工 lexer + 手工 Pratt; 加运算符要改 L2 内          │
│         6-7 处 + 下游 17 个生产文件                          │
│   目标: 词法收敛为唯一实现 + LALRPOP 文法驱动语法            │
│   详见: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 语义与中间表示 Semantic & IR                              │
│   类型检查、静态分析、IR 构造                                 │
│   现状: typecheck/(29466 生产) + ir.rs(905) + ir_gen.rs(8448) │
│         3 套平行类型表示 + 3 套平行运算符枚举;                │
│         ir_gen 单 impl 7952 行 / 116 方法; 无 IR 级校验器    │
│   目标: 类型表示单一化; IR 满足 SSA 构造纪律                  │
│   详见: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 执行层 Execution                                          │
│   字节码生成、解释器、运行时、标准库                          │
│   现状: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│         + runtime/(1800) + std/(7543)                         │
│   目标: opcode 事实单源化 + 生成期门禁; 执行层不感知 L1-L3    │
│   详见: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it consumes AST data only and does not call the parser);
and L4 depends only on the output format of L3.

See Routing Table C for the list of known reverse dependencies and parallel definitions:
`../compiler-architecture/01-routing.md`.

### Equivalence-Criteria Tiers

**This is the safety net for the entire refactoring and must be established before any code
change.** See `07-equivalence-oracle.md` for the detailed design.

Core principle: **criteria are tiered by refactoring category because different categories require
different strengths of equivalence**. Using a single criterion—usually “full IR snapshot
equality”—for every refactoring is wrong; some refactorings **necessarily change the shape of the
IR**.

| Category | Refactoring                                                                    | Criterion Type                                                              | Strength  |
| -------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | --------- |
| **C1**   | Pure relocation (splitting files, changing directories, extracting submodules) | Normalized IR snapshot **zero-diff**                                        | Strongest |
| **C2**   | Orchestration changes (staging, unified Driver)                                | Identical diagnostic sets for every entry point + identical corpus behavior | Strong    |
| **C3**   | Type-representation convergence                                                | Identical diagnostic **codes** (message wording may change)                 | Strong    |
| **C4**   | IR shape changes (SSA conversion)                                              | **Behavioral equivalence** + IR structural invariants                       | Medium    |
| **C5**   | Frontend-paradigm changes                                                      | AST snapshot + diagnostics + behavior, all three                            | Strong    |
| **C6**   | Pure deletion                                                                  | No equivalence required; only confirmation of no references                 | —         |

**The distinction between C1 and C4 is critical**: C1 requires byte-for-byte identical IR; C4
acknowledges that the IR will change and instead requires “identical program behavior + IR
satisfying invariants.” Forcing snapshot equivalence onto C4 would encourage the team to weaken the
criteria.

The three-layer criteria are:

1. **IR static validator** — dominance-aware use-before-def, existence of jump targets, type
   consistency, inner-region isolation. This is much stronger than snapshots and covers defects such
   as “IR is internally consistent but semantically wrong,” which snapshots cannot detect. It must
   **first pass on the existing non-SSA IR**.
2. **Normalized IR snapshots** — strip `Span`, rename temporaries in order of appearance, relativize
   global slots, and sort predecessors. Check the results into the repository and manually review
   diffs. **Known limitation**: normalization erases “which register the Nth argument used,” and
   therefore **is insufficient on its own to cover semantic reshuffling of `arg_regs`**.
3. **End-to-end corpus differential** — compare diagnostic lists, exit codes, and stdout/stderr item
   by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml` anywhere under the
> `tests/` directory** (measured: 0), and therefore all **293** `.yx` corpus files under
> `tests/yaoxiang/` **use the single-file path** (`check_files_with_diagnostics`'s standalone branch
> → `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third-layer criterion can **only validate changes to the single-file path**.
> There is **currently no corpus coverage at all** for the multi-file side (the four `orchestrator`
> entry points) or for the multi-file behavior of types/SSA. P4 “Unified Driver” is the largest risk
> point in the entire plan, and **the multi-file corpus layer must be established unconditionally in
> P2** (Decision D40)—it is P4's only executable source of behavioral criteria.

## Implementation Strategy

### Stage Sequence

```
P0  仓库维护机制与代码放置规程 08        ← 先立规矩:三条禁令 + D0-D4 决策程序
P1  复活孤儿测试并修缺陷        06 §S1   ← 最便宜,收益最大
P2  建立等价性判据基线          07 全部
P3  修正确性漏洞(最小方案)      02 §修复
P3.5 删除 pub 与自动绑定        RFC-029g / #399  ← 排序约束 D56,必须先于 P4
P4  阶段契约与统一 Driver        02
P5  checker 文件内拆分          09 §P5 补齐
P6  类型表示单一化              03
P7  中间表示 SSA 化             04     } 可并行
P8  前端范式变更                05     }
P9  防反弹门禁(统一脚本清单)     01 + 08
P10 其余清理与状态修正          06 §S2-S6
```

**Core serial constraints (non-interchangeable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every P1 action—1.2.x consists of adding `mod` declarations to `mod.rs`, precisely the cause of the `precedence_inline.rs` keep-or-delete conflict                                                                                                                                                                                                                                                 |
| P1 → P2      | Reviving tests changes the test count and corpus baseline. Establishing the baseline first would make it invalid after P1                                                                                                                                                                                                                                                                                                           |
| P2 → P3      | The vulnerability criterion must **first be written in the failing state** to prove that the fix works. **Narrowing (D51)**: P3's only prerequisites are 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two failing criteria); the remainder of P2 may proceed in parallel with P3, but P4 must wait until all of P2 is complete—stopping the correctness vulnerability must not be blocked by criteria-infrastructure construction |
| P3 → P4      | Fix the bug before refactoring. Reversing the order would cause the bug to be cemented in the stage table as “established behavior”                                                                                                                                                                                                                                                                                                 |
| P3.5 → P4    | The deletion surface of RFC-029g (#399) covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 (`check_project`'s role dispatch, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer` + `parser`). Reversing the order means redoing the same deletions over the new grammar, new checker layout, and new IR (D56)                                                                                                        |
| P4 → P5      | P5 opens with `include!` → real `mod` (09 §P5 5.1), and the subsequent checker split touches the same file; it must proceed continuously after P4                                                                                                                                                                                                                                                                                   |
| P5 → P6      | Consecutive changes to the same file must be separated; otherwise regressions cannot be bisected                                                                                                                                                                                                                                                                                                                                    |
| P6 → P7 / P8 | If type representations are not converged first, the new SSA IR will grow into a third representation                                                                                                                                                                                                                                                                                                                               |
| P7/P8 → P9   | The initial baselines for each gate script—such as the `pub(crate)` leak count—can only be finalized after P7/P8                                                                                                                                                                                                                                                                                                                    |
| P7 ∥ P8      | The file sets are disjoint and can proceed in parallel                                                                                                                                                                                                                                                                                                                                                                              |

**Why P0 Is a Separate Stage**: P9's CI scripts are **post-hoc checks** and can only catch bad code
that has already been written; “patching when refactoring is required” is a **pre-hoc judgment**
that only the D0-D4 decision procedure can stop. The two cannot substitute for each other.

### Definition of Done for Each Stage

A stage is complete only when all of the following are satisfied:

1. Every corresponding “Implementation Strategy” step in its owning document has been committed
2. The criterion for that stage's category (C1-C6) in `07-equivalence-oracle.md` is **green in CI**
3. `cargo test` is fully green, and **the test count is no lower than at the start of the stage**
   (preventing “delete tests to obtain a green build”)
4. `cargo clippy --all --all-features -- -D warnings` is clean
5. `python scripts/rfc/check_tracking.py` exits with code 0
6. The stage has an independent revert unit—**if a stage cannot be reverted independently, it is too
   large and must be split further**
7. For stages that touch the compilation pipeline or execution path (P4 / P6 / P7 / P8), the
   performance-baseline comparison in 07 shows no unexplained >10% regression

## Trade-Offs

### Advantages

- **Provides a landing point for all subsequent changes.** “Adding an operator requires changing a
  dozen places, and nobody notices when one is missed” cannot be improved through memory; only a
  routing table + gates can address it.
- **A single root cause.** All three symptom classes—stage inconsistencies, `include!`, and broken
  test wiring—stem from “boundaries are conventions, not constraints” and can be addressed with one
  class of mechanism.
- **Non-blocking.** This RFC contains zero code changes. The four-layer model is descriptive, and
  after adoption it remains possible to execute only part of it.
- **Criteria first.** P2 establishes them before any code change, and the tiered design avoids the
  common failure mode of “snapshot too strict → inducing criterion relaxation.”

### Disadvantages and Risks

- **The serial chain is long.** P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly a complete serial
  chain, and later stages must wait for earlier ones.
- **P1 introduces additional bug-fix workload**, and it is the step most likely to be skipped with
  the rationale “we have to fix bugs anyway, so we will not do it now”—but skipping it means all
  later acceptance criteria are built on false coverage.
- **P4 is the largest single-point risk**: one change touches 5 entry points.
- **P6 has the broadest impact**: it touches the shared dependencies of the parser, formatter,
  spawn, and orchestrator.
- **P7 will have a net increase of 900-1,600 lines, not a net reduction.** Splitting introduces
  boilerplate: 300-600 lines of `verify` and 600-1,000 lines of register allocation. **If “shorter
  code” is used as the success criterion at project approval, this stage will be judged a
  failure**—this must be aligned at approval time.

## Alternatives

### A. Split Files Only, Without Changing the Paradigm

Split the 8,448-line file into 10 files of 800 lines each.

**Not adopted.** Splitting eliminates none of the root causes: 6 manual save/restore sites remain
scattered across 10 files; the semantic reshuffling of `arg_regs` in `generate_call_expr_ir` still
requires manual reasoning; and “adding an operator requires changing a dozen places” is still a
dozen places. Splitting improves navigation, not correctness.

### B. Add Gates Only, Without Changing the Structure (Including a Line-Count Ratchet)

**Not adopted as the sole solution, but it is part of this RFC.** Gates can prevent regression, but
they cannot repair the current state—`ir_gen.rs` is already 8,448 lines, and a gate can only freeze
it at that number.

### C. Start Over and Write a New Compiler Skeleton

**Not adopted.** `src/package/` proves that this team can build a complex system correctly. The
problem is not capability. Moreover, the existing 293 `.yx` corpus files provide a ready-made source
of equivalence criteria; rewriting from scratch would waste this asset.

### D. Use an Existing Compiler Framework (such as LLVM as the Sole Backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already provides an abstraction point,
but it has only one implementor. Introducing LLVM falls under `RFC-018` (1,037 lines of design, 0
lines of code) and should be **decided independently**—it changes “what to compile to,” not “how to
organize the code.”

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                                  |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustively enumerable step in a compilation. The set of stages must be an exhaustively enumerable enum and must not be registerable at runtime         |
| **Orchestration Layer (L1)**               | The layer that decides which stages run, how many times they run, and how failures propagate                                                                |
| **Frontend Layer (L2)**                    | Lexing and parsing, producing the AST                                                                                                                       |
| **Intermediate-Representation Layer (L3)** | Type checking, static analysis, and IR construction                                                                                                         |
| **Execution Layer (L4)**                   | Bytecode generation, interpreter, runtime, and standard library                                                                                             |
| **Obligation**                             | A contract item produced by one stage that must be consumed downstream or the compilation fails                                                             |
| **Obligation Ledger (Obligations)**        | A container for all obligations, settled uniformly at the end of the stage table                                                                            |
| **Orphan**                                 | A file never referenced by any `mod` declaration and therefore never participating in compilation                                                           |
| **Shell**                                  | A file that has been declared and included in the compiled output but contains only documentation comments or unused `use` declarations and zero assertions |
| **Equivalence Oracle**                     | An executable check proving that behavior has not changed across a refactoring                                                                              |
| **C1-C6**                                  | Refactoring-category tiers that determine criterion strength. **No C5′ exists**                                                                             |
| **Separation of Responsibilities**         | The only solution to size problems: one module bears one class of responsibility. **No line-count / size gate is imposed**                                  |
| **Resolution Registry**                    | This RFC's “Resolution Registry” section, containing the final decisions on all open items                                                                  |
