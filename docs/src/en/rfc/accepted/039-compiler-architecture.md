# RFC-039: Compiler Architecture Refactoring

## Abstract

This RFC proposes an architectural refactoring of the YaoXiang compiler (`src/` 160,002 lines / 509
`.rs` files): redraw its boundaries using a **four-layer model** (orchestration / frontend /
intermediate representation / execution), establish **exhaustively enumerable compile-stage
contracts** and an **obligation ledger**, and provide an accompanying set of **equivalence
criteria** and **anti-regression gates**.

The detailed design is presented in nine companion documents under `docs/src/dev/architecture/`.
This RFC is responsible only for the problem, root cause, four-layer model, tiered acceptance
criteria, and execution-phase order. **Reviewing this RFC is sufficient to decide whether to approve
the project; the companion documents are the construction blueprints after approval.**

## Motivation

### I. Boundaries Exist, but Have No Enforcement Power

The layering expressed by directory names (`frontend` / `middle` / `backends`) is clear. However,
**the boundaries exist only in people's diligence, and no mechanism guarantees that they will not
erode**. This has three direct consequences.

#### 1.1 Compile stages are manually wired at five entry points, producing 11 behavioral inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (within a project) | LSP (single file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------------- | ----------------- |
| lexing / parsing           | Yes               | Yes              | Yes     | Yes                    | Yes               |
| typecheck                  | Yes               | Yes              | Yes     | Yes                    | Yes               |
| **proof_execution**        | **Yes**           | **No**           | **No**  | **No**                 | **No**            |
| Dead-code analysis         | Yes               | No               | Yes     | No                     | No                |
| W1006 shadowing diagnostic | No                | No               | Yes     | No                     | No                |
| Monomorphization           | Yes               | No               | No      | No                     | No                |
| IR generation / linking    | Yes               | Yes              | No      | No                     | No                |

There are five entry points: `src/frontend/pipeline.rs:141-227` (single file; the five stages are at
`149` / `161` / `173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), the four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `src/lib.rs`'s `run_file:140` /
`run_project:154`.

The most serious cell in the table leads to a **correctness vulnerability**. A proof-function
constraint such as `x: Sorted(3)` **silently passes** along the multi-file, check, and LSP paths.
The evidence chain is fully reproducible:

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** place in the repository
   that constructs a non-empty `proof_calls`; its semantics are "this constraint requires executing
   a proof function."
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches that handle `Unproven`:
   `5164` / `5306` / `5420` use `if calls.is_empty()` and therefore produce a hard error; `5179` /
   `5318` / `5448` use `ctx.proof_calls.extend(...)` and therefore **produce no diagnostic**. The
   comment at `5165` originally states: "Unproven → compile error, no fallback, no silent pass……
   silent pass must not be allowed to return."
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is read in exactly **one place** in the entire
   repository: `src/frontend/pipeline.rs:187`.
4. None of the four entry points in `orchestrator.rs` reads that field.

In other words, an invariant declared by the code itself is broken by the architecture rather than
by the logic. The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means that **the
refinement obligations of the embedded std module itself also follow this discard path**.

**No test can stop it**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit tests directly invoke `check_module` and assert that
`proof_calls` is non-empty, **stopping exactly before the pipeline**. They verify that it was
"populated," whereas the bug is that the "consumer does not read it."

#### 1.2 Module boundaries can be bypassed without leaving any trace

`src/frontend/core/typecheck/checker.rs:5618` contains `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1,547 lines of text into the `checker`
module. That file **is not declared as a module anywhere** (`grep 'mod semantic_tokens'` has zero
hits across the repository); its first line is directly `impl TypeChecker {`, it has no `use` header
of its own, and it is the only file in the `checker/` directory.

The consequences are that there is no module identity, visibility isolation is ineffective,
rust-analyzer's navigation and symbol search do not work for it, and toolchain analysis treats it as
part of `checker.rs`. **The true size of the `checker` module is 5618 + 1547 ≈ 7165 lines**, not the
5618 lines shown by the directory statistics.

#### 1.3 Test wiring depends on people remembering, and corruption happens silently

A module-graph BFS reachability analysis from the two crate roots, `src/lib.rs` and `src/main.rs`,
shows that **24 files / 2,628 lines never participate in compilation**. Of these, 23 files / 1,081
lines are true orphans.

| Orphan                                          | Size                 | Contents                                                                              |
| ----------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------- |
| The entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + a 38-line `mod.rs` + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                      | 3 files / 14 lines   | All are placeholder documentation comments                                            |
| `package/template/tests/`                       | 3 files / 65 lines   | 7 `#[test]` functions                                                                 |
| `parser/pratt/tests/precedence_inline.rs`       | 95 lines / 6 tests   | Hidden in a live directory                                                            |
| `typecheck/passes/tests/overload_inline.rs`     | 170 lines / 7 tests  | Same as above                                                                         |
| `util/diagnostic/emitter/tests/json.rs`         | 46 lines / 3 tests   | Same as above                                                                         |

`cargo test` cannot discover these: tests that have never run cannot fail. CI
(`.github/workflows/ci.yml:140`) likewise has no test-count baseline or wiring check.

**The true tests that have never run total 1,005 lines / 78 tests.** The only lexer test actually
running is `fstring.rs`, which is attached through a `#[path]` bypass.

### II. The Design Capacity Is Sufficient

At the same time, we must acknowledge that this project **already has** mature enforcement
mechanisms; they simply have not been extended.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subject to a
build-time hard gate implemented by `build.rs:19-55` through `tools/code-tables`: it parses the
registry, validates uniqueness and code ranges, and compares it line by line with RFC-013's Markdown
code table. **Any discrepancy directly triggers `panic!` and rejects the build.** RFC-013's
documentation and the code therefore remain consistent.

`src/package/` (76 files / 13,012 lines) is the most complete area: **6,227 lines of tests,
accounting for 47.9%**; five of its six `tests/` directories are wired correctly, with
`template/tests/` as the sole exception (see Section A). Note that this positive example works
through **directory-level wiring**, not per-file wiring: among 76 `.rs` files, only 7 contain inline
`#[cfg(test)]`, and only 5 contain `mod tests;`. Five RFCs align with the code line by line, and
many instances of "not implemented" become explicit errors rather than silent TODOs (the cmake in
`build/mod.rs:172-174`, and `RegistryDeferred` in `error.rs:74-76`). `.yxpkg` has five layers of
safety protection, all correctly implemented.

**In the same repository, with the same authors, `package/` gets test-directory wiring right, while
`lexer/tests/` has never run even once. The difference is not capability; it is whether anyone runs
a check.**

### III. Paper-Only Design

The three documents under `docs/src/dev/design/check/` describe an architecture that **has never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, and `HotReloader` have zero hits across the repository; the
`traits/` directory does not exist; the `check_single_module` function does not exist (it survives
only in test comments); and even the busy-wait in `command.rs` cited under "Known Limitations" does
not exist (that file contains neither `Instant` nor `recv_timeout`).

Cross-file analysis is in fact implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, approximately 2,670 lines)—the capability is real, but the path is
entirely different. **This document presents "a design that might exist in the future" as "a defect
in an implemented system."**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the cleanest physical evidence of "we created a test skeleton according to the design, discovered
that the pipeline had no corresponding implementation, and then set it aside."

In addition, `RFC-018` (LLVM AOT, 1,037 lines, status accepted) has 0 lines of implementation in the
code—all 6 AOT-related hits in `backends/mod.rs` are **comments**.

## Root-Cause Diagnosis

Taken together, the three classes of symptoms have a single root cause:

> **This project treats "design" as a documentation convention rather than as an executable
> constraint.**

| Layer             | Missing enforcement                                                    | Existing example that has not been extended                                                            |
| ----------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Stage boundaries  | A single decision point for "which stages did this compilation run?"   | —                                                                                                      |
| Module boundaries | Prohibit `include!`; restrict cross-layer leakage through `pub(crate)` | —                                                                                                      |
| Cross-references  | Detectability for "a field is produced but never consumed"             | The error-code gate in `build.rs`                                                                      |
| Test wiring       | Declaring a directory requires a corresponding `mod` declaration       | The directory-level wiring convention in `src/package/` (five of six `tests/` directories are correct) |

The position of this RFC is therefore: **turn the three kinds of boundaries—stages, modules, and
cross-references—from "documentation conventions" into "facts that can be asserted at compile time
or test time"**, and **establish a single stage-decision point in the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 编排层 Orchestration                                      │
│   谁决定跑哪些阶段、跑几遍、失败如何传播                      │
│   现状: pipeline.rs(740) + orchestrator.rs(1528)             │
│         + compiler.rs(267) = 5 个入口, 11 处不一致           │
│   目标: 单一 Driver + 可穷举的 Stage 枚举 + Obligations 账本  │
│   详见: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 编译单元 (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 前端层 Frontend                                           │
│   词法、语法、AST 构造                                        │
│   现状: lexer/(3065) + parser/(6341)                        │
│         手工 lexer + 手工 Pratt; 加运算符要改 L2 内          │
│         6-7 处 + 下游 17 个生产文件                          │
│   目标: 词法收敛为唯一实现 + LALRPOP 文法驱动语法            │
│   详见: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 语义与中间表示 Semantic & IR                              │
│   类型检查、静态分析、IR 构造                                 │
│   现状: typecheck/(29466 生产) + ir.rs(905) + ir_gen.rs(8448) │
│         3 套平行类型表示 + 3 套平行运算符枚举;                │
│         ir_gen 单 impl 7952 行 / 116 方法; 无 IR 级校验器    │
│   目标: 类型表示单一化; IR 满足 SSA 构造纪律                  │
│   详见: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 执行层 Execution                                          │
│   字节码生成、解释器、运行时、标准库                          │
│   现状: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│         + runtime/(1800) + std/(7543)                         │
│   目标: opcode 事实单源化 + 生成期门禁; 执行层不感知 L1-L3    │
│   详见: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it only consumes AST data and does not invoke the
parser); L4 depends only on L3's output format.

The known reverse dependencies and parallel-definition inventory are listed in Table C of the
routing document at `../compiler-architecture/01-routing.md`.

### Equivalence Oracle Tiers

**This is the safety net for the entire refactoring and must be established before any code
change.** See `07-equivalence-oracle.md` for the detailed design.

The core principle is: **criteria are tiered by refactoring category because different categories
require different strengths of equivalence.** Using a single criterion (usually "full IR snapshot
equality") for every refactoring is wrong—some refactorings **necessarily change the shape of the
IR**.

| Category | Refactoring                                                                    | Criterion type                                                          | Strength  |
| -------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | --------- |
| **C1**   | Pure relocation (splitting files, changing directories, extracting submodules) | Normalized IR snapshot with **zero diff**                               | Strongest |
| **C2**   | Orchestration changes (staging, unified Driver)                                | Same diagnostic set at every entry point + same corpus behavior         | Strong    |
| **C3**   | Type-representation convergence                                                | Same diagnostic **codes** (message wording may change)                  | Strong    |
| **C4**   | IR shape changes (SSA transformation)                                          | **Behavioral equivalence** + IR structural invariants                   | Medium    |
| **C5**   | Frontend paradigm changes                                                      | AST snapshot + diagnostics + behavior, all three                        | Strong    |
| **C6**   | Pure deletion                                                                  | No equivalence required; only confirmation that there are no references | —         |

**The distinction between C1 and C4 is critical**: C1 requires byte-for-byte identical IR; C4
acknowledges that the IR will change and instead uses "the program behaves the same + the IR
satisfies invariants." Forcing snapshots onto C4 would induce the team to weaken the criteria.

The three layers of criteria are:

1. **IR static verifier** — dominance-aware use-before-def, existing jump targets, type consistency,
   inner isolation. Much stronger than snapshots, and covers defects that snapshots cannot detect,
   such as "the IR is internally consistent but the value is wrong." It must **first pass on the
   existing (non-SSA) IR**.
2. **Normalized IR snapshots** — strip `Span`, rename temporaries in order of appearance, relativize
   global slots, and sort predecessors. Commit these snapshots and manually review their diffs.
   **Known limitation**: normalization erases "which register the Nth actual argument used," and
   therefore **is insufficient on its own to cover `arg_regs` semantic reordering**.
3. **End-to-end corpus differential** — compare diagnostic lists, exit codes, and stdout/stderr item
   by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml` anywhere under the
> `tests/` directory** (measured: 0), so all **293** `.yx` corpus files under `tests/yaoxiang/`
> **take the single-file path** (`check_files_with_diagnostics`'s standalone branch →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third-layer criterion can **only validate changes to the single-file path**.
> For the multi-file side (the four `orchestrator` entry points) and the multi-file behavior of
> types/SSA, **there is currently no corpus coverage whatsoever**. P4, "Unified Driver," is the
> highest-risk point in the entire plan, and **the multi-file corpus layer must be established
> unconditionally in P2** (Decision D40)—it is the only executable source of behavioral criteria for
> P4.

## Implementation Strategy

### Phase Sequence

```
P0  仓库维护机制与代码放置规程 08        ← 先立规矩:三条禁令 + D0-D4 决策程序
P1  复活孤儿测试并修缺陷        06 §S1   ← 最便宜,收益最大
P2  建立等价性判据基线          07 全部
P3  修正确性漏洞(最小方案)      02 §修复
P3.5 删除 pub 与自动绑定        RFC-029g / #399  ← 排序约束 D56,必须先于 P4
P4  阶段契约与统一 Driver        02
P5  checker 文件内拆分          09 §P5 补齐
P6  类型表示单一化              03
P7  中间表示 SSA 化             04     } 可并行
P8  前端范式变更                05     }
P9  防反弹门禁(统一脚本清单)     01 + 08
P10 其余清理与状态修正          06 §S2-S6
```

**Core serial constraints (not interchangeable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P0 → P1      | The three prohibitions constrain every action in P1—1.2.x adds `mod` declarations to `mod.rs`, which is precisely the cause of the `precedence_inline.rs` life-or-death conflict                                                                                                                                                                                                                       |
| P1 → P2      | Reviving tests changes the test count and corpus baseline. Establishing the baseline first would invalidate it after P1                                                                                                                                                                                                                                                                                |
| P2 → P3      | The vulnerability criterion must **be written red first** to prove that the fix works. **Narrowing (D51)**: P3's only prerequisites are 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two red criteria); the rest of P2 may run in parallel with P3, but P4 must wait until all of P2 is complete—stopping the correctness vulnerability must not be blocked by criterion-infrastructure construction |
| P3 → P4      | Fix the bug before refactoring. Reversing the order would cause the bug to be frozen into the stage table as "established behavior"                                                                                                                                                                                                                                                                    |
| P3.5 → P4    | RFC-029g (#399)'s deletion surface covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 (`check_project`'s role dispatch, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, and `lexer`+`parser`). Reversing the order means repeating the same batch of deletions on the new grammar, new checker layout, and new IR (D56)                                                                     |
| P4 → P5      | P5 opens by replacing `include!` with real `mod`s (09 §P5 5.1). The subsequent checker split touches the same file and must proceed continuously after P4                                                                                                                                                                                                                                              |
| P5 → P6      | Consecutive changes to the same file must be separated; otherwise regressions cannot be bisected                                                                                                                                                                                                                                                                                                       |
| P6 → P7 / P8 | If type representations do not converge first, the new SSA IR will grow into a third representation                                                                                                                                                                                                                                                                                                    |
| P7/P8 → P9   | The initial baselines for the various gate scripts, such as the `pub(crate)` leakage count, can only be finalized after P7/P8                                                                                                                                                                                                                                                                          |
| P7 ∥ P8      | The file sets are disjoint and can proceed in parallel                                                                                                                                                                                                                                                                                                                                                 |

**Why P0 is an independent phase**: P9's CI scripts are **post-hoc checks** and can only stop bad
code that has already been written; "patching where refactoring is required" is an **ex ante
judgment**, and only the D0–D4 decision procedure can stop it. The two cannot replace each other.

### Definition of Done for Each Phase

A phase is complete only when all of the following hold:

1. All corresponding "Implementation Strategy" steps in its owning document have been committed.
2. The criteria for that category (C1–C6) in `07-equivalence-oracle.md` are **green in CI**.
3. `cargo test` is fully green, and **the test count is no lower than it was at the start of the
   phase** (preventing "delete tests to get a green build").
4. `cargo clippy --all --all-features -- -D warnings` is clean.
5. `python scripts/rfc/check_tracking.py` exits with code 0.
6. The phase has an independent revert unit—**if a phase cannot be reverted independently, it is too
   large and must be split further**.
7. For a phase that touches the compilation pipeline or execution path (P4 / P6 / P7 / P8), the
   performance-baseline comparison in 07 shows no unexplained >10% regression.

## Trade-offs

### Benefits

- **It gives every subsequent change a landing point.** "Adding an operator requires changing a
  dozen places, and nobody notices when one is missed" cannot be improved through memory; it
  requires a routing table + gates.
- **There is a single root cause.** All three symptom classes (stage inconsistencies, `include!`,
  and broken test wiring) arise because "boundaries are conventions rather than constraints," and
  can be addressed with the same class of mechanism.
- **It does not block other work.** This RFC contains zero code changes. The four-layer model is
  descriptive, and after adoption the project may still execute only a subset of it.
- **Criteria come first.** P2 establishes them before any code change, and the tiered design avoids
  the common failure mode of "snapshots are too strict → induce the team to relax the criteria."

### Drawbacks and Risks

- **The serial chain is long.** P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is almost a complete serial
  sequence, so later phases must wait for earlier ones.
- **P1 will introduce a new bug-fixing workload**, and it is the step most likely to be skipped with
  the rationale "we need to fix bugs first, so let's not do this"—but skipping it means every later
  phase's acceptance criteria are built on false coverage.
- **P4 is the largest single-point risk**: it changes 5 entry points at once.
- **P6 has the broadest impact**: it touches the shared dependencies of the parser, formatter,
  spawn, and orchestrator.
- **P7 will increase the line count by a net 900–1,600 lines, not reduce it.** Splitting introduces
  boilerplate; `verify` requires 300–600 lines, and register allocation requires 600–1,000 lines.
  **If "shorter code" is used as the success criterion when the project is approved, this phase will
  be judged a failure**—this point must be aligned at project-approval time.

## Alternatives

### A. Only Split Files, Without Changing the Paradigm

Split 8,448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting eliminates none of the root causes: the 6 manual save/restore sites
remain distributed across 10 files, the `arg_regs` semantic reordering in `generate_call_expr_ir`
still requires manual reasoning, and "adding an operator changes a dozen places" still changes a
dozen places. Splitting improves navigation, not correctness.

### B. Only Add Gates, Without Changing the Structure (Including a Line-Count Ratchet)

**Not adopted as the sole solution, but it is part of this RFC.** Gates can prevent regression but
cannot fix the status quo—`ir_gen.rs` is already 8,448 lines, and a gate can only freeze it at that
number.

### C. Start Over and Write a New Compiler Skeleton

**Not adopted.** `src/package/` proves that this team can build a complex system correctly. The
problem is not capability. Moreover, the existing 293 `.yx` corpus files provide a ready-made source
of equivalence criteria; rewriting from scratch would waste this asset.

### D. Use an Existing Compiler Framework (e.g., LLVM as the Sole Backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already provides an abstraction point,
but it has only one implementation. Introducing LLVM belongs to the scope of `RFC-018` (1,037 lines
of design, 0 lines of code) and should be **decided independently**—it changes "what to compile to,"
not "how to organize the code."

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustively enumerable step within one compilation. The set of stages must be an exhaustively enumerable enum and must not be registered at runtime |
| **Orchestration Layer (L1)**               | The layer that determines which stages run, how many times they run, and how failures propagate                                                         |
| **Frontend Layer (L2)**                    | Lexing and parsing, producing the AST                                                                                                                   |
| **Intermediate Representation Layer (L3)** | Type checking, static analysis, and IR construction                                                                                                     |
| **Execution Layer (L4)**                   | Bytecode generation, the interpreter, the runtime, and the standard library                                                                             |
| **Obligation**                             | A contract item produced by one stage that must be consumed downstream or the compilation fails                                                         |
| **Obligations Ledger**                     | A container for all obligations, settled uniformly at the end of the stage table                                                                        |
| **Orphan**                                 | A file never referenced by any `mod` declaration and therefore never participates in compilation                                                        |
| **Shell**                                  | A file that is declared, enters the build artifact, but contains only documentation comments or unused `use` statements and zero assertions             |
| **Equivalence Oracle**                     | An executable check that proves behavior has not changed before and after a refactoring                                                                 |
| **C1–C6**                                  | Refactoring-category tiers that determine criterion strength. **C5′ does not exist**                                                                    |
| **Separation of Responsibilities**         | The sole solution to scale problems: one module bears only one kind of responsibility. **There are no line-count / size gates**                         |
| **Decision Registry**                      | This RFC's "Decision Registry" section, containing the final adjudication of every open item                                                            |
