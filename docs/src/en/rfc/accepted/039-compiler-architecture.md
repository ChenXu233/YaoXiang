# RFC-039: Compiler Architecture Refactoring

## Abstract

This RFC proposes an architectural refactoring of the YaoXiang compiler (`src/`, 160,002 lines / 509
`.rs` files): redraw the boundaries around a **four-layer model** (orchestration / frontend /
intermediate representation / execution), establish **exhaustively enumerable compilation-stage
contracts** and an **obligations ledger**, and provide a matching set of **equivalence criteria**
and **anti-regression gates**.

Detailed design is provided in nine companion documents under `docs/src/dev/architecture/`. This RFC
is responsible only for the problem, root causes, four-layer model, tiered acceptance criteria, and
execution-stage ordering. **Reviewing this RFC is sufficient to decide whether to initiate the
project; the companion documents are the construction blueprints for work after approval.**

## Motivation

### I. The boundaries exist, but have no enforcement

The layering expressed by directory names (`frontend` / `middle` / `backends`) is clear. However,
**the boundaries exist only in people's conscious adherence, with no mechanism ensuring that they
cannot erode**. This has three direct consequences.

#### 1.1 Compilation stages are manually wired in five entry points, resulting in 11 behavioral inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (in-project) | LSP (single-file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing           | Yes               | Yes              | Yes     | Yes              | Yes               |
| typecheck                  | Yes               | Yes              | Yes     | Yes              | Yes               |
| **proof_execution**        | **Yes**           | **No**           | **No**  | **No**           | **No**            |
| dead-code analysis         | Yes               | No               | Yes     | No               | No                |
| W1006 shadowing diagnostic | No                | No               | Yes     | No               | No                |
| monomorphization           | Yes               | No               | No      | No               | No                |
| IR generation / linking    | Yes               | Yes              | No      | No               | No                |

Five entry points: `src/frontend/pipeline.rs:141-227` (single-file, with five stages at `149` /
`161` / `173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), the four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `src/lib.rs`'s `run_file:140` /
`run_project:154`.

The most serious cell leads to a **correctness bug**. A proof-function constraint such as
`x: Sorted(3)` **silently passes** on the multi-file, check, and LSP paths. The evidence chain, all
of which can be independently verified, is as follows:

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a non-empty `proof_calls`; its semantics are “this constraint requires
   executing a proof function.”
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches handling `Unproven`:
   `5164` / `5306` / `5420` contain `if calls.is_empty()` → report a hard error; `5179` / `5318` /
   `5448` contain `ctx.proof_calls.extend(...)` → **produce no diagnostic whatsoever**. The original
   comment at `5165` states: “Unproven → compile error, no downgrade, no silent pass… silent pass
   must not be resurrected.”
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is read in **only one place in the entire
   repository**: `src/frontend/pipeline.rs:187`.
4. None of the four entry points in `orchestrator.rs` **read that field**.

In other words, an invariant explicitly declared by the code itself is violated by the architecture
rather than by its logic. The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means
that **the refinement obligations of the embedded std module itself also follow this discard path**.

**No test can prevent this**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit tests directly invoke `check_module` and assert that
`proof_calls` is non-empty, **stopping exactly before the pipeline**—they verify that it was
“populated,” whereas the bug is that the “consumer” does not read it.

#### 1.2 Module boundaries can be bypassed without leaving a trace

`src/frontend/core/typecheck/checker.rs:5618` contains `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1,547 lines of text into the `checker`
module. That file **is not declared as a module** (`grep 'mod semantic_tokens'` has zero
repository-wide hits); its first line is directly `impl TypeChecker {`, and it has no `use` header
of its own. The `checker/` directory contains only that one file.

Consequences: there is no module identity, visibility isolation is ineffective, rust-analyzer's
go-to-definition and symbol search fail for it, and toolchain analysis treats it as part of
`checker.rs`. **The true size of the `checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618
lines shown by directory statistics.

#### 1.3 Test wiring depends on human memory, and corruption occurs silently

A module-graph BFS reachability analysis starting from the two crate roots, `src/lib.rs` and
`src/main.rs`, shows that **24 files / 2,628 lines never participate in compilation**. Among them
are 23 genuine orphan files totaling 1,081 lines.

| Orphan                                          | Size                 | Contents                                                                                |
| ----------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------- |
| The entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + `mod.rs` at 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                      | 3 files / 14 lines   | All are placeholder documentation comments                                              |
| `package/template/tests/`                       | 3 files / 65 lines   | 7 `#[test]` functions                                                                   |
| `parser/pratt/tests/precedence_inline.rs`       | 95 lines / 6 tests   | Hidden in a live directory                                                              |
| `typecheck/passes/tests/overload_inline.rs`     | 170 lines / 7 tests  | Same                                                                                    |
| `util/diagnostic/emitter/tests/json.rs`         | 46 lines / 3 tests   | Same                                                                                    |

`cargo test` cannot discover these problems: tests that have never run cannot fail. CI
(`.github/workflows/ci.yml:140`) likewise has no test-count baseline or wiring check.

**The real tests that have never run total 1,005 lines / 78 tests.** The only lexer-layer test
actually running is `fstring.rs`, connected through a `#[path]` attribute as a bypass.

### II. The design capability is sufficient

At the same time, we must acknowledge that this project **already has** mature enforcement
mechanisms; they simply have not been extended.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are subject to a
build-time hard gate in `build.rs:19-55` through `tools/code-tables`: it parses the registry,
validates uniqueness and code ranges, compares every entry against RFC-013's Markdown code table,
and **panics to reject compilation on any discrepancy**. RFC-013's documentation and code therefore
always remain consistent.

`src/package/` (76 files / 13,012 lines) is the most complete area: **6,227 test lines, accounting
for 47.9%**; 5 of its 6 `tests/` directories are correctly wired, with `template/tests/` as the sole
exception (see Section A). Note that this positive example relies on **directory-level wiring**, not
per-file wiring—only 7 of the 76 `.rs` files contain inline `#[cfg(test)]`, and only 5 contain
`mod tests;`. Five RFCs align with the code line by line, with many “not implemented” items becoming
explicit errors rather than silent TODOs (`build/mod.rs:172-174` for cmake, `error.rs:74-76` for
`RegistryDeferred`). `.yxpkg` has five layers of safety protection, all correctly implemented.

**In the same repository, with the same authors, `package/` got test-directory wiring right, while
`lexer/tests/` has never run even once. The difference is not capability; it is whether anyone runs
the check once.**

### III. Paper-Only Designs

The three documents under `docs/src/dev/design/check/` describe an architecture that **has never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, and `HotReloader` have zero repository-wide hits; the
`traits/` directory does not exist; the `check_single_module` function does not exist (it survives
only in test comments); even the busy-wait on `command.rs` cited under “known limitations” does not
exist (that file contains neither `Instant` nor `recv_timeout`).

Cross-file analysis is in fact implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, approximately 2,670 lines)—the capability is real, but the path is
entirely different. **This document describes a “possible future design” as a defect in an “already
implemented system.”**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (3 lines each) are
the clearest physical evidence of a pattern in which a test skeleton was “built according to the
design,” the corresponding implementation was found to be absent from the pipeline, and the skeleton
was then abandoned.

In addition, `RFC-018` (LLVM AOT, 1,037 lines, status accepted) has zero implementation lines in the
code—all six AOT-related hits in `backends/mod.rs` are **comments**.

## Root-Cause Diagnosis

Taken together, the three classes of symptoms have a single root cause:

> **This project treats “design” as a documentation convention rather than an executable
> constraint.**

| Layer             | Missing enforcement                                                   | Existing but unextended example                                                                       |
| ----------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Stage boundaries  | A single decision point for “which stages does this compilation run?” | —                                                                                                     |
| Module boundaries | Prohibit `include!`; restrict `pub(crate)` cross-layer leakage        | —                                                                                                     |
| Cross-references  | Detectability for “a field is produced but never consumed”            | The error-code gate in `build.rs`                                                                     |
| Test wiring       | Declaring a directory requires a `mod` declaration                    | The directory-level wiring convention in `src/package/` (5 of 6 `tests/` directories correctly wired) |

The position of this RFC is therefore: **turn the three boundary classes—stages, modules, and
cross-references—from “documentation conventions” into “facts assertable at compile time or test
time,”** and **establish a unique stage decision point in the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 编排层 Orchestration                                      │
│   谁决定跑哪些阶段、跑几遍、失败如何传播                      │
│   现状: pipeline.rs(740) + orchestrator.rs(1528)             │
│         + compiler.rs(267) = 5 个入口, 11 处不一致           │
│   目标: 单一 Driver + 可穷举的 Stage 枚举 + Obligations 账本  │
│   详见: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 编译单元 (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 前端层 Frontend                                           │
│   词法、语法、AST 构造                                        │
│   现状: lexer/(3065) + parser/(6341)                        │
│         手工 lexer + 手工 Pratt; 加运算符要改 L2 内          │
│         6-7 处 + 下游 17 个生产文件                          │
│   目标: 词法收敛为唯一实现 + LALRPOP 文法驱动语法            │
│   详见: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 语义与中间表示 Semantic & IR                              │
│   类型检查、静态分析、IR 构造                                 │
│   现状: typecheck/(29466 生产) + ir.rs(905) + ir_gen.rs(8448) │
│         3 套平行类型表示 + 3 套平行运算符枚举;                │
│         ir_gen 单 impl 7952 行 / 116 方法; 无 IR 级校验器    │
│   目标: 类型表示单一化; IR 满足 SSA 构造纪律                  │
│   详见: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 执行层 Execution                                          │
│   字节码生成、解释器、运行时、标准库                          │
│   现状: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│         + runtime/(1800) + std/(7543)                         │
│   目标: opcode 事实单源化 + 生成期门禁; 执行层不感知 L1-L3    │
│   详见: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it consumes AST data only and does not call the parser);
L4 depends only on L3's output format.

The inventory of known reverse dependencies and parallel definitions is given in routing table C in
`../compiler-architecture/01-routing.md`.

### Equivalence-Criteria Tiers

**This is the safety net for the entire refactoring and must be established before any code
changes.** Detailed design is given in `07-equivalence-oracle.md`.

Core principle: **criteria are tiered by refactoring category because different categories require
different strengths of equivalence**. Using a single criterion (usually “full IR snapshot equality”)
for every refactoring is wrong—some refactorings **necessarily change the shape of the IR**.

| Category | Refactoring content                                                            | Criterion type                                                       | Strength  |
| -------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------- | --------- |
| **C1**   | Pure relocation (splitting files, changing directories, extracting submodules) | Normalized IR snapshot **zero-diff**                                 | Strongest |
| **C2**   | Orchestration changes (staging, unified Driver)                                | Same diagnostic set for every entry point + same corpus behavior     | Strong    |
| **C3**   | Type-representation convergence                                                | Same diagnostic **codes** (message wording may change)               | Strong    |
| **C4**   | IR shape changes (SSA conversion)                                              | **Behavioral equivalence** + IR structural invariants                | Medium    |
| **C5**   | Frontend-paradigm changes                                                      | AST snapshot + diagnostics + behavior, all three                     | Strong    |
| **C6**   | Pure deletion                                                                  | No equivalence required; only confirmation that no references remain | —         |

**The distinction between C1 and C4 is critical**: C1 requires byte-for-byte identical IR, while C4
acknowledges that the IR will change and instead uses “identical program behavior + IR satisfies
invariants.” Forcing snapshot-based comparison onto C4 would encourage the team to weaken the
criteria.

Three layers of criteria:

1. **IR static validator** — dominance and use-before-def, valid jump targets, type consistency, and
   inner isolation. Much stronger than snapshots and capable of catching defects such as “the IR is
   internally consistent but the values are wrong,” which snapshots cannot detect. It must **first
   pass on the existing non-SSA IR**.
2. **Normalized IR snapshot** — strip `Span`, rename temporary values in occurrence order,
   relativize global slots, and sort predecessors. Commit the result and manually review diffs.
   **Known limitation**: normalization erases “which register the Nth argument used,” and therefore
   is **not sufficient on its own to cover `arg_regs` semantic reordering**.
3. **End-to-end corpus differential** — compare diagnostic lists, exit codes, and stdout/stderr item
   by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml` anywhere under the
> `tests/` directory** (measured: 0), so all **293** `.yx` corpus files under `tests/yaoxiang/`
> **take the single-file path** (`check_files_with_diagnostics`'s standalone branch →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third layer of criteria can **validate changes only on the single-file
> path**. On the multi-file side (the four `orchestrator` entry points), and for multi-file behavior
> involving types/SSA, **there is currently no corpus coverage**. P4, “Unified Driver,” is the
> largest risk point in the entire plan, and **the multi-file corpus layer must unconditionally be
> established in P2** (Decision D40)—it is the only executable source of behavioral criteria for P4.

## Implementation Strategy

### Stage Sequence

```
P0  仓库维护机制与代码放置规程 08        ← 先立规矩:三条禁令 + D0-D4 决策程序
P1  复活孤儿测试并修缺陷        06 §S1   ← 最便宜,收益最大
P2  建立等价性判据基线          07 全部
P3  修正确性漏洞(最小方案)      02 §修复
P3.5 删除 pub 与自动绑定        RFC-029g / #399  ← 排序约束 D56,必须先于 P4
P4  阶段契约与统一 Driver        02
P5  checker 文件内拆分          09 §P5 补齐
P6  类型表示单一化              03
P7  中间表示 SSA 化             04     } 可并行
P8  前端范式变更                05     }
P9  防反弹门禁(统一脚本清单)     01 + 08
P10 其余清理与状态修正          06 §S2-S6
```

**Core serial constraints (non-reorderable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every action in P1—1.2.x adds `mod` declarations to `mod.rs`, which is precisely the cause of the `precedence_inline.rs` life-or-death conflict                                                                                                                                                                                                             |
| P1 → P2      | Reviving tests changes the test count and corpus baseline. Establishing the baseline first would invalidate it after P1                                                                                                                                                                                                                                                                      |
| P2 → P3      | The bug criterion must **be written in the failing state first** to prove that the fix works. **Narrowing (D51)**: P3's prerequisites are only 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two failing criteria); the rest of P2 may proceed in parallel with P3, but P4 must wait for all of P2—stopping the correctness bug must not be blocked by criteria-infrastructure construction |
| P3 → P4      | Fix the bug before refactoring. Reversing the order would cause the bug to be codified as “established behavior” in the stage table                                                                                                                                                                                                                                                          |
| P3.5 → P4    | The deletion surface of RFC-029g (#399) covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 (`check_project` role dispatch, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, and `lexer` + `parser`). Reversing the order amounts to redoing the same batch of deletions over the new grammar, checker layout, and IR (D56)                                                         |
| P4 → P5      | P5 opens with `include!` → real `mod` (09 §P5 5.1), and the subsequent checker split touches the same file. It must proceed continuously after P4                                                                                                                                                                                                                                            |
| P5 → P6      | Consecutive changes to the same file must be separated; otherwise regressions cannot be bisected                                                                                                                                                                                                                                                                                             |
| P6 → P7 / P8 | If type representations do not converge first, the new SSA IR will grow into a third representation                                                                                                                                                                                                                                                                                          |
| P7/P8 → P9   | The initial baselines for the gate scripts, such as the `pub(crate)` leakage count, are not final until after P7/P8                                                                                                                                                                                                                                                                          |
| P7 ∥ P8      | The file sets are disjoint and may proceed in parallel                                                                                                                                                                                                                                                                                                                                       |

**Why P0 is an independent stage**: P9's CI scripts are **post-hoc checks** and can only catch bad
code that has already been written; “patching when a refactor is required” is an **up-front
judgment** that only the D0-D4 decision procedure can prevent. The two cannot replace one another.

### Definition of Done for Each Stage

A stage is complete only when all of the following are satisfied:

1. All corresponding “implementation strategy” steps in its ownership document have been committed.
2. The criteria for that category (C1-C6) in `07-equivalence-oracle.md` are **green in CI**.
3. `cargo test` is fully green, and **the test count is no lower than at the start of the stage**
   (preventing “delete tests for a green build”).
4. `cargo clippy --all --all-features -- -D warnings` is clean.
5. `python scripts/rfc/check_tracking.py` exits with code 0.
6. The stage has an independent revert unit—**if a stage cannot be reverted independently, it is too
   large and must be split further**.
7. For stages touching the compilation pipeline or execution path (P4 / P6 / P7 / P8), the
   performance-baseline comparison in 07 shows no unexplained regression greater than 10%.

## Trade-offs

### Advantages

- **Provides a landing point for every subsequent change**. “Adding an operator requires changing a
  dozen locations, and nobody notices when one is missed” cannot be improved through memory alone;
  it requires a routing table + gates.
- **A single root cause**. All three classes of symptoms—stage inconsistencies, `include!`, and
  broken test wiring—stem from “boundaries are conventions, not constraints,” and can be addressed
  at once through the same class of mechanism.
- **Non-blocking**. This RFC contains no code changes. The four-layer model is descriptive, and
  after adoption it remains possible to execute only part of it.
- **Criteria first**. P2 establishes the baseline before any code changes, and the tiered design
  avoids the common failure mode of “snapshots too strict → inducing criterion weakening.”

### Disadvantages and Risks

- **The serial chain is long**. P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly a complete serial
  chain, and later stages must wait for earlier ones.
- **P1 introduces a new defect-remediation workload**, and it is the step most likely to be skipped
  because “we have to fix defects first”—but skipping it means that every later stage's acceptance
  criteria are built on false coverage.
- **P4 is the largest single-point risk**: it changes five entry points at once.
- **P6 has the broadest impact**: it touches dependencies shared by the parser, formatter, spawn,
  and orchestrator.
- **P7 will produce a net increase of 900-1,600 lines, not a net reduction**. Splitting introduces
  boilerplate: 300-600 lines for `verify`, and 600-1,000 lines for register allocation. **If
  “shorter code” is adopted as the success criterion at project initiation, this stage will be
  judged a failure**—this must be aligned at project initiation.

## Alternatives

### A. Only split files, without changing the paradigm

Split the 8,448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting eliminates none of the root causes: the six manual save/restore sites
remain scattered across 10 files, the `arg_regs` semantic reordering in `generate_call_expr_ir`
still requires manual reasoning, and “adding an operator changes a dozen locations” is still a dozen
locations. Splitting improves navigation, not correctness.

### B. Only add gates, without changing the structure (including line-count ratchets)

**Not adopted as the sole solution, but it is part of this RFC.** Gates can prevent regression, but
cannot repair the current state—`ir_gen.rs` already has 8,448 lines, and gates can only freeze it at
that number.

### C. Start over and write a new compiler skeleton

**Not adopted.** `src/package/` proves that this team can build a complex system correctly. The
problem is not capability. Moreover, the existing 293 `.yx` corpus files provide an existing source
of equivalence criteria; rewriting from scratch would waste this asset.

### D. Use an existing compiler framework, such as making LLVM the sole backend

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already provides an abstraction point,
but has only one implementor. Introducing LLVM belongs to the scope of `RFC-018` (1,037 lines of
design, 0 lines of code) and should be **decided independently**—it changes “what to compile to,”
not “how to organize the code.”

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                                       |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage**                                  | An exhaustively enumerable step in a compilation. The set of stages must be an exhaustively enumerable enum and must not be registered at runtime                |
| **Orchestration layer (L1)**               | The layer that decides which stages run, how many times they run, and how failures propagate                                                                     |
| **Frontend layer (L2)**                    | Lexing and parsing, producing an AST                                                                                                                             |
| **Intermediate-representation layer (L3)** | Type checking, static analysis, and IR construction                                                                                                              |
| **Execution layer (L4)**                   | Bytecode generation, interpreter, runtime, and standard library                                                                                                  |
| **Obligation**                             | A contract item produced by one stage that must be consumed downstream or compilation fails                                                                      |
| **Obligations ledger**                     | A container for all obligations, settled uniformly at the end of the stage table                                                                                 |
| **Orphan**                                 | A file never referenced by any `mod` declaration and therefore never participating in compilation                                                                |
| **Shell**                                  | A file that has been declared and included in the compilation output but contains only documentation comments or unused `use` statements and has zero assertions |
| **Equivalence Oracle**                     | An executable check that proves behavior did not change before and after a refactoring                                                                           |
| **C1-C6**                                  | Refactoring-category tiers that determine criterion strength. **No C5′ exists**                                                                                  |
| **Separation of responsibilities**         | The sole solution to size problems: one module bears only one class of responsibility. **No line-count / size gates**                                            |
| **Decision Registry**                      | This RFC's “Decision Registry” section, containing the final rulings on all open items                                                                           |
