# RFC-039: Compiler Architecture Restructuring

## Abstract

This RFC proposes one architectural restructuring for the YaoXiang compiler (`src/`, 160,002 lines
across 509 `.rs` files): redefine the boundaries with a **four-layer model** (orchestration /
frontend / intermediate representation / execution), establish **exhaustively enumerable
compilation-stage contracts** and an **obligations ledger**, and provide a set of **equivalence
criteria** and **anti-regression gates**.

The detailed design is split across nine companion documents in `docs/src/dev/architecture/`. This
RFC is responsible only for the problem, root cause, four-layer model, tiered acceptance criteria,
and execution-stage order. **Reviewing this RFC is sufficient to decide whether to approve the
project; the companion documents are the construction blueprints after approval.**

## Motivation

### I. The boundaries exist, but have no enforcement

The layering in the directory names (`frontend` / `middle` / `backends`) is clear. However, **the
boundaries exist only in people's discipline; no mechanism prevents them from eroding**. This has
three direct consequences.

#### 1.1 Compilation stages are manually wired at five entry points, producing 11 behavioral inconsistencies

| Stage                      | Single-file `run` | Multi-file `run` | `check` | LSP (in-project) | LSP (single-file) |
| -------------------------- | ----------------- | ---------------- | ------- | ---------------- | ----------------- |
| lexing / parsing           | Yes               | Yes              | Yes     | Yes              | Yes               |
| typecheck                  | Yes               | Yes              | Yes     | Yes              | Yes               |
| **proof_execution**        | **Yes**           | **No**           | **No**  | **No**           | **No**            |
| Dead-code analysis         | Yes               | No               | Yes     | No               | No                |
| W1006 shadowing diagnostic | No                | No               | Yes     | No               | No                |
| Monomorphization           | Yes               | No               | No      | No               | No                |
| IR generation / linking    | Yes               | Yes              | No      | No               | No                |

The five entry points are: `src/frontend/pipeline.rs:141-227` (single-file; the five stages are at
`149` / `161` / `173` / `188` / `205`), `src/frontend/compiler.rs:106` (wrapper), the four in
`src/frontend/module/orchestrator.rs` (`compile_project:99` / `check_project:273` /
`check_source_in_project:450` / `compile_embedded_module:1374`), and `run_file:140` /
`run_project:154` in `src/lib.rs`.

The most serious cell in the table exposes a **correctness vulnerability**. A proof-function
constraint such as `x: Sorted(3)` **silently passes** through the multi-file, check, and LSP paths.
The evidence chain is fully reproducible:

1. `src/frontend/core/typecheck/layers/predicate.rs:232-239` is the **only** location in the entire
   repository that constructs a non-empty `proof_calls`; its meaning is “this constraint requires
   executing a proof function.”
2. `src/frontend/core/typecheck/checker.rs` has three isomorphic branches that handle `Unproven`:
   `5164` / `5306` / `5420` use `if calls.is_empty()` to emit a hard error; `5179` / `5318` / `5448`
   use `ctx.proof_calls.extend(...)` and **produce no diagnostic**. The comment at `5165` originally
   states: “Unproven → compilation error, no fallback, no silent pass……must not let silent pass
   return.”
3. `TypeCheckResult.proof_calls` (`types.rs:29`) is read in **only one place in the entire
   repository**: `src/frontend/pipeline.rs:187`.
4. **None of the four entry points in `orchestrator.rs` read this field.**

In other words, the invariant declared by the code itself is broken by the architecture rather than
by its logic. The existence of `compile_embedded_module` (`orchestrator.rs:1374`) means that **the
refinement obligations of the embedded std module itself also follow this discard path**.

**No test can catch it**: the 27 tests in `tests/integration/multifile.rs` have zero hits for
`Sorted` / `proof` / `refin`; RFC-027's unit tests directly call `check_module` and assert that
"`proof_calls` is non-empty," **stopping exactly before the pipeline**—they verify that it was
“populated,” while the bug is that the “consumer does not read it.”

#### 1.2 Module boundaries can be bypassed without leaving a trace

`src/frontend/core/typecheck/checker.rs:5618` contains `include!("checker/semantic_tokens.rs");`—the
**only `include!` in the entire repository**. It splices 1,547 lines of text into the `checker`
module. That file **is not declared as any module** (`grep 'mod semantic_tokens'` has zero hits
across the repository), begins directly with `impl TypeChecker {`, and has no `use` header of its
own; it is the only file in the `checker/` directory.

The consequences are: no module identity, failed visibility isolation, broken go-to-definition and
symbol search in rust-analyzer, and treatment as part of `checker.rs` by toolchain analysis. **The
real size of the `checker` module is 5618 + 1547 ≈ 7165 lines**, not the 5618 lines shown by
directory statistics.

#### 1.3 Test wiring depends on human memory, so corruption occurs silently

A BFS reachability analysis of the module graph from the two crate roots, `src/lib.rs` and
`src/main.rs`, finds that **24 files / 2,628 lines never participate in compilation**. Of these, 23
files / 1,081 lines are genuine orphans.

| Orphan                                          | Size                 | Contents                                                                                |
| ----------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------- |
| The entire `frontend/core/lexer/tests/` subtree | 13 files / 686 lines | 7 empty shells totaling 19 lines + `mod.rs` at 38 lines + **629 lines / 55 real tests** |
| `frontend/pipeline/tests/`                      | 3 files / 14 lines   | All are placeholder documentation comments                                              |
| `package/template/tests/`                       | 3 files / 65 lines   | 7 `#[test]` functions                                                                   |
| `parser/pratt/tests/precedence_inline.rs`       | 95 lines / 6 tests   | Hidden in a live directory                                                              |
| `typecheck/passes/tests/overload_inline.rs`     | 170 lines / 7 tests  | Same as above                                                                           |
| `util/diagnostic/emitter/tests/json.rs`         | 46 lines / 3 tests   | Same as above                                                                           |

`cargo test` cannot discover them: tests that never run cannot fail. CI
(`.github/workflows/ci.yml:140`) also has no test-count baseline or wiring check.

**The real tests that have never run total 1,005 lines / 78 tests.** The only lexer test currently
running is `fstring.rs` (wired in through a bypass using the `#[path]` attribute).

### II. The design capability is sufficient

It must also be acknowledged that this project **already has** a mature enforcement mechanism; it
simply has not been extended.

The error codes in `src/util/diagnostic/codes/` (137 E codes + 8 W codes = 145) are guarded at build
time by `build.rs:19-55` through `tools/code-tables`: it parses the registry, validates uniqueness
and segment placement, compares every entry against RFC-013's Markdown code table, and **panics and
rejects the build on any discrepancy**. RFC-013's documentation and the code therefore always remain
consistent.

`src/package/` (76 files / 13,012 lines) is the most complete area: **tests account for 6,227 lines,
or 47.9%**; 5 of the 6 `tests/` directories are wired correctly (the sole exception is
`template/tests/`, discussed in Section A). Note that this positive example works at the
**directory-wiring level**, not at the individual-file level—only 7 of the 76 `.rs` files contain
inline `#[cfg(test)]`, and only 5 contain `mod tests;`. Five RFCs match the code line by line, with
multiple “not implemented” cases turned into explicit errors rather than silent TODOs (the cmake
handling at `build/mod.rs:172-174` and `RegistryDeferred` at `error.rs:74-76`). `.yxpkg` has five
layers of safeguards, all implemented correctly.

**In the same repository, under the same authors, `package/` gets test-directory wiring right, while
`lexer/tests/` has never run even once. The difference is not capability; it is whether anyone runs
the check once.**

### III. Paper-Only Design

The three documents under `docs/src/dev/design/check/` describe an architecture that **has never
existed**: `CheckSession` (including the Rust code draft in `incremental-checking.md:31-41`),
`ModuleDependencyGraph`, `ModuleCache`, and `HotReloader` have zero hits across the repository; the
`traits/` directory does not exist; the `check_single_module` function does not exist (it survives
only in test comments); and even the busy-wait in `command.rs` cited under “known limitations” does
not exist (that file contains neither `Instant` nor `recv_timeout`).

Cross-file analysis is in fact implemented by `src/frontend/module/` (registry 439 + resolver 195 +
roles 388 + orchestrator 1528, approximately 2,670 lines)—the capability is real, but the path is
completely different. **This document presents a “potentially future design” as a defect in an
already implemented system.**

`src/frontend/pipeline/tests/compilation_cache.rs` and `incremental_scheduler.rs` (three lines each)
are the clearest physical evidence of “creating a test skeleton according to the design, discovering
that the pipeline has no corresponding implementation, and abandoning it.”

In addition, `RFC-018` (LLVM AOT, 1,037 lines, status accepted) has 0 lines of implementation in the
code—all six AOT-related hits in `backends/mod.rs` **are comments**.

## Root-Cause Diagnosis

Taken together, the three classes of symptoms have a single root cause:

> **This project treats “design” as a documentation convention rather than as an executable
> constraint.**

| Layer             | Missing enforcement                                                   | Existing example not yet extended                                                                 |
| ----------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Stage boundaries  | A single decision point for “which stages does this compilation run?” | —                                                                                                 |
| Module boundaries | Prohibit `include!`; restrict `pub(crate)` leakage across layers      | —                                                                                                 |
| Cross-references  | Detectability for “a field is produced but never consumed”            | The error-code gate in `build.rs`                                                                 |
| Test wiring       | If a directory is declared, it must have a `mod` declaration          | The directory-level wiring convention in `src/package/` (5 of 6 `tests/` directories are correct) |

The position of this RFC is therefore: **turn the three kinds of boundaries—stages, modules, and
cross-references—from “documentation conventions” into “facts assertable at compile time or test
time,”** and **establish a single stage-decision point at the orchestration layer**.

## Proposal

### Four-Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│ L1 编排层 Orchestration                                      │
│   谁决定跑哪些阶段、跑几遍、失败如何传播                      │
│   现状: pipeline.rs(740) + orchestrator.rs(1528)             │
│         + compiler.rs(267) = 5 个入口, 11 处不一致           │
│   目标: 单一 Driver + 可穷举的 Stage 枚举 + Obligations 账本  │
│   详见: ../compiler-architecture/02-stage-contract.md           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 编译单元 (Unit)
┌───────────────────────────▼─────────────────────────────────┐
│ L2 前端层 Frontend                                           │
│   词法、语法、AST 构造                                        │
│   现状: lexer/(3065) + parser/(6341)                        │
│         手工 lexer + 手工 Pratt; 加运算符要改 L2 内          │
│         6-7 处 + 下游 17 个生产文件                          │
│   目标: 词法收敛为唯一实现 + LALRPOP 文法驱动语法            │
│   详见: ../compiler-architecture/05-frontend-paradigm.md        │
└───────────────────────────┬─────────────────────────────────┘
                            │ Module (AST)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 语义与中间表示 Semantic & IR                              │
│   类型检查、静态分析、IR 构造                                 │
│   现状: typecheck/(29466 生产) + ir.rs(905) + ir_gen.rs(8448) │
│         3 套平行类型表示 + 3 套平行运算符枚举;                │
│         ir_gen 单 impl 7952 行 / 116 方法; 无 IR 级校验器    │
│   目标: 类型表示单一化; IR 满足 SSA 构造纪律                  │
│   详见: ../compiler-architecture/03-type-unification.md         │
│         ../compiler-architecture/04-ssa.md                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ ModuleIR
┌───────────────────────────▼─────────────────────────────────┐
│ L4 执行层 Execution                                          │
│   字节码生成、解释器、运行时、标准库                          │
│   现状: codegen/(3436) + bytecode.rs(2422) + executor/(2000)  │
│         + runtime/(1800) + std/(7543)                         │
│   目标: opcode 事实单源化 + 生成期门禁; 执行层不感知 L1-L3    │
│   详见: ../compiler-architecture/06-cleanup-inventory.md        │
└─────────────────────────────────────────────────────────────┘
```

**The four layers are strictly unidirectional**: L1 depends on the interfaces of L2/L3/L4; L2 does
not depend on L3; L3 does not depend on L2 (it only consumes AST data and does not call the parser);
L4 depends only on the output format of L3.

The list of known reverse dependencies and parallel definitions is given in the routing table in
`../compiler-architecture/01-routing.md`.

### Equivalence-Criteria Tiers

**This is the safety net for the entire refactoring and must be established before any code
change.** See `07-equivalence-oracle.md` for the detailed design.

The core principle is: **criteria are tiered by refactoring category because different categories
require different strengths of equivalence.** Using a single criterion (usually “full IR snapshot
equality”) for all refactorings is wrong—some refactorings **necessarily change the IR shape**.

| Category | Refactoring content                                                            | Criterion type                                                          | Strength  |
| -------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | --------- |
| **C1**   | Pure relocation (splitting files, changing directories, extracting submodules) | Normalized IR snapshot **zero-diff**                                    | Strongest |
| **C2**   | Orchestration changes (staging, unified Driver)                                | Same diagnostic set at every entry point + same corpus behavior         | Strong    |
| **C3**   | Type-representation convergence                                                | Same diagnostic **codes** (message wording may change)                  | Strong    |
| **C4**   | IR shape changes (SSA conversion)                                              | **Behavioral equivalence** + IR structural invariants                   | Medium    |
| **C5**   | Frontend paradigm changes                                                      | AST snapshot + diagnostics + behavior, all three                        | Strong    |
| **C6**   | Pure deletion                                                                  | No equivalence required; only confirmation that there are no references | —         |

**The distinction between C1 and C4 is critical**: C1 requires byte-for-byte identical IR; C4
acknowledges that the IR will change and instead requires “identical program behavior + IR satisfies
its invariants.” Forcing snapshot equality onto C4 would induce the team to weaken the criteria.

Three layers of criteria:

1. **IR static validator** — dominance violations such as use-before-def, jump targets exist, type
   consistency, inner isolation. It is much stronger than snapshots and covers defects that
   snapshots cannot detect, such as “the IR is internally consistent but the value is wrong.” It
   **must first pass on the existing (non-SSA) IR**.
2. **Normalized IR snapshots** — strip `Span`, rename temporaries in order of appearance, relativize
   global slots, order predecessors. Commit them and manually review diffs. **Known limitation**:
   normalization erases “which register the Nth actual argument used,” so it **is not sufficient by
   itself to cover `arg_regs` semantic reordering**.
3. **End-to-end corpus differential testing** — compare diagnostic lists, exit codes, and
   stdout/stderr item by item.

> **⚠️ Structural limitation of corpus coverage**: there is **no `yaoxiang.toml` anywhere under the
> `tests/` directory** (measured: 0), so all **293** `.yx` corpus files in `tests/yaoxiang/` take
> the single-file path (the standalone branch of `check_files_with_diagnostics` →
> `check_single_file` → `Pipeline::run`).
>
> **Consequence**: the third layer of criteria **can validate changes only on the single-file
> path**. For the multi-file side (the four `orchestrator` entry points) and multi-file behavior of
> types/SSA, **there is currently no corpus coverage**. P4, “Unified Driver,” is the largest risk
> point in the entire plan, and **the multi-file corpus layer must be established unconditionally in
> P2** (Decision D40)—it is P4's only executable source of behavioral criteria.

## Implementation Strategy

### Stage Sequence

```
P0  仓库维护机制与代码放置规程 08        ← 先立规矩:三条禁令 + D0-D4 决策程序
P1  复活孤儿测试并修缺陷        06 §S1   ← 最便宜,收益最大
P2  建立等价性判据基线          07 全部
P3  修正确性漏洞(最小方案)      02 §修复
P3.5 删除 pub 与自动绑定        RFC-029g / #399  ← 排序约束 D56,必须先于 P4
P4  阶段契约与统一 Driver        02
P5  checker 文件内拆分          09 §P5 补齐
P6  类型表示单一化              03
P7  中间表示 SSA 化             04     } 可并行
P8  前端范式变更                05     }
P9  防反弹门禁(统一脚本清单)     01 + 08
P10 其余清理与状态修正          06 §S2-S6
```

**Core serial constraints (not interchangeable):**

| Constraint   | Reason                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1      | The three prohibitions constrain every action in P1—1.2.x adds `mod` declarations to `mod.rs`, which is precisely the source of the life-or-death conflict over `precedence_inline.rs`                                                                                                                                                                                                                              |
| P1 → P2      | Reviving tests changes the test count and corpus baseline. Establishing the baseline first would invalidate it after P1                                                                                                                                                                                                                                                                                             |
| P2 → P3      | The vulnerability criterion **must first be written in red** to prove that the fix is effective. **Narrowing (D51)**: P3's prerequisites are only 2.3.2 (multi-file corpus layer) + 2.4.1/2.4.3 (two red criteria); the rest of P2 can proceed in parallel with P3, but P4 must wait until all of P2 is complete—stopping the correctness vulnerability must not be blocked by criteria-infrastructure construction |
| P3 → P4      | Fix the bug before refactoring. Reversing the order would cause the bug to be codified into the stage table as “established behavior”                                                                                                                                                                                                                                                                               |
| P3.5 → P4    | RFC-029g (#399)'s deletion surface covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 (`check_project`'s role dispatch, `checker.rs`, `ast.rs` and `src/std`, `ir_gen.rs`, `lexer` + `parser`). Reversing the order means repeating the same deletions on the new grammar, checker layout, and IR (D56)                                                                                                     |
| P4 → P5      | P5 begins by replacing `include!` with a real `mod` (09 §P5 5.1); the subsequent checker split touches the same file and must be performed continuously after P4                                                                                                                                                                                                                                                    |
| P5 → P6      | Consecutive changes to the same file must be separated, otherwise regressions cannot be bisected to a specific location                                                                                                                                                                                                                                                                                             |
| P6 → P7 / P8 | If type representations are not unified first, the new SSA IR will grow into a third representation                                                                                                                                                                                                                                                                                                                 |
| P7/P8 → P9   | The initial baselines for the gate scripts (such as the `pub(crate)` leakage count) are taken only after P7/P8                                                                                                                                                                                                                                                                                                      |
| P7 ∥ P8      | The file sets are disjoint and can proceed in parallel                                                                                                                                                                                                                                                                                                                                                              |

**Why P0 is a separate stage**: P9's CI scripts are **after-the-fact checks** and can only block bad
code that has already been written; “patching when a refactor is required” is an **up-front
judgment** that only the D0-D4 decision procedure can block. The two cannot replace each other.

### Definition of Done for Each Stage

A stage is complete only when all of the following are satisfied:

1. All corresponding “Implementation Strategy” steps in the owning document have been committed
2. The criteria for that category (C1-C6) in `07-equivalence-oracle.md` **pass in CI**
3. `cargo test` is fully green, and **the test count is no lower than at the start of that stage**
   (preventing “delete tests for a green build”)
4. `cargo clippy --all --all-features -- -D warnings` is clean
5. `python scripts/rfc/check_tracking.py` exits with code 0
6. The stage has an independent revert unit—**if a stage cannot be reverted independently, it is too
   large and must be split further**
7. For stages that touch the compilation pipeline or execution path (P4 / P6 / P7 / P8), the
   performance-baseline comparison in 07 shows no unexplained >10% regression

## Trade-offs

### Advantages

- **A landing point for all subsequent changes**. “Adding an operator requires changing a dozen
  places, and nobody notices when one is missed” cannot be improved through memory; it requires a
  routing table + gates.
- **A single root cause**. All three classes of symptoms (stage inconsistencies, `include!`, broken
  test wiring) arise because “boundaries are conventions, not constraints,” and can be solved at
  once with the same class of mechanism.
- **Non-blocking**. This RFC has zero code changes. The four-layer model is descriptive; after
  adoption, it remains possible to execute only part of it.
- **Criteria first**. P2 establishes the baseline before any code change, and the tiered design
  avoids the common failure mode of “overly strict snapshots → inducing teams to weaken the
  criteria.”

### Disadvantages and Risks

- **A long serial chain**. P1 → P2 → P3 → P4 → P5 → P6 → P7/P8 is nearly a complete serial chain, so
  later stages must wait for earlier ones.
- **P1 introduces additional bug-fixing work**, and it is the step most likely to be skipped on the
  grounds that “we need to fix bugs, so let's not do this yet”—but skipping it means that all later
  acceptance criteria are built on a false coverage baseline.
- **P4 is the largest single point of risk**: one change covers 5 entry points.
- **P6 has the broadest impact**: it touches the common dependencies of the parser, formatter,
  spawn, and orchestrator.
- **P7 will increase the line count by a net 900-1,600 lines, not reduce it**. Splitting introduces
  boilerplate, with `verify` at 300-600 lines and register allocation at 600-1,000 lines. **If
  “shorter code” is used as the success criterion at project approval, this stage will be judged a
  failure**—this must be aligned at project approval.

## Alternatives

### A. Split Files Only, Without Changing the Paradigm

Split the 8,448 lines into 10 files of 800 lines each.

**Not adopted.** Splitting eliminates none of the root causes: 6 manual save/restore sites remain
scattered across 10 files, the `arg_regs` semantic reordering in `generate_call_expr_ir` still
requires manual reasoning, and “adding an operator changes a dozen places” still changes a dozen
places. Splitting improves navigation, not correctness.

### B. Add Gates Only, Without Changing the Structure (Including a Line-Count Ratchet)

**Not adopted as the sole solution, but it is part of this RFC.** Gates can prevent regressions, but
they cannot fix the current state—`ir_gen.rs` already has 8,448 lines, and a gate can only freeze it
at that number.

### C. Start Over with a New Compiler Skeleton

**Not adopted.** `src/package/` demonstrates that this team can build a complex system correctly.
The problem is not capability. Moreover, the existing 293 `.yx` corpus files provide a ready-made
source of equivalence criteria, so a rewrite from scratch would waste this asset.

### D. Use an Existing Compiler Framework (e.g., LLVM as the Only Backend)

**Not adopted.** The `Executor` trait (`backends/mod.rs:356`) already provides an abstraction point,
but it has only one implementor. Introducing LLVM falls under `RFC-018` (1,037 lines of design, 0
lines of code) and should be **decided independently**—it changes “what to compile to,” not “how to
organize the code.”

## Appendix: Glossary

| Term                                       | Definition                                                                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Stage**                                  | An exhaustively enumerable step in a compilation. The set of stages must be an exhaustively enumerable enum and must not be registerable at runtime          |
| **Orchestration Layer (L1)**               | The layer that determines which stages run, how many times they run, and how failures propagate                                                              |
| **Frontend Layer (L2)**                    | Lexing and parsing, producing the AST                                                                                                                        |
| **Intermediate Representation Layer (L3)** | Type checking, static analysis, and IR construction                                                                                                          |
| **Execution Layer (L4)**                   | Bytecode generation, interpreter, runtime, and standard library                                                                                              |
| **Obligation**                             | A contract item produced by one stage that must be consumed downstream or compilation fails                                                                  |
| **Obligations Ledger**                     | A container for all obligations, settled uniformly at the end of the stage table                                                                             |
| **Orphan**                                 | A file that has never been referenced by any `mod` declaration and therefore has never participated in compilation                                           |
| **Shell**                                  | A file that has been declared and included in the compilation artifact but contains only documentation comments or unused `use` statements and no assertions |
| **Equivalence Oracle**                     | An executable check that proves behavior did not change before and after a refactoring                                                                       |
| **C1-C6**                                  | Refactoring-category tiers that determine criterion strength. **There is no C5′**                                                                            |
| **Separation of Responsibilities**         | The only solution to scale problems: one module bears one class of responsibility. **No line-count / size gates**                                            |
| **Decision Registry**                      | The “Decision Registry” section of this RFC, containing the final ruling on every open item                                                                  |
