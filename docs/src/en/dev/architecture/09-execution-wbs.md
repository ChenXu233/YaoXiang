**This document covers**: task breakdown, dependency relationships, parallel groupings, acceptance
criteria binding.

**This document does not cover**: task design rationale (see `02`–`08`), phase ordering
argumentation (see RFC-039).

**Registration convention (from 2026-10-12)**: newly registered level 2/3 rows **must include two
fields**—"**Owning Phase**" (which P it truly belongs to, may differ from the section) and
"**Whether Blocking Main Line**"; `registration pending scheduling` is no longer the default state,
unmarked means **not schedulable**. Numbers **must be unique** within the entire document
(cross-track tasks use track numbers, e.g., `029g.x`, must not occupy `N.x`).
**Checkmarks/completion registrations are based on "task id + evidence (gate value, run id, issue
number, file:line)"**, do not write commit hashes—`pull --rebase` will rewrite local hashes,
hardcoded numbers will inevitably fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Check commit
hashes with `git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement regulations     08        ← New, establish rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence criteria baseline        07 all
P3  Fix correctness vulnerabilities (minimum scheme)        02 §S3-Vulnerability half
P4  Phase contract and unified Driver          02
P5  checker file internal split             02 + supplemented by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ification                04      } Parallelizable
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gate (including unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status correction             06 §S2/S3/S4/S5/S6
```

**Reason for new P0**: The three prohibitions (no fabrication / no endless padding / patching
instead of refactoring) constrain every action of P1–P10. Rules must be established before work
starts, otherwise when P1 revives tests it's already adding `mod` declarations to
`tests/mod.rs`—that is exactly what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 independent as phase rather than merged into P9**——gate is "post-hoc check", regulation is
  "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as CI script's sole authoritative list**——original gap G3's three coexisting lists led to
  unable to close. After this table's merge 11 scripts each belong to one phase, report-only and
  turn-hard timing explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leave as "independent track, do after refactor"**——its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for
  post-refactor execution equals redo same batch of deletion on new grammar, new checker layout and
  new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status
  correction.
- **P5's steps supplemented by this document rather than merged into P4**——P4 is already the largest
  single point risk, stacking checker split will exceed rollback granularity.
- **5.3.2 uses "zero caller change" as hard acceptance**——split must be independently revertible.
