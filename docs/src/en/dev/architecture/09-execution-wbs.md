# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC’s phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates are governed solely by the main body of RFC-039; this
> document is responsible only for decomposing the work into executable granularity and recording
> conflicts that have not yet been adjudicated.

## Scope and Positioning

| Level       | Count       | Meaning                                                                                               |
| ----------- | ----------- | ----------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, in one-to-one correspondence with the phase sequence in RFC-039                               |
| **Level 2** | 73          | Task groups: work groups decomposed by phase, each of which can be staffed and archived independently |
| **Level 3** | 260         | Work units that can be committed and verified independently                                           |

**Numbering gaps (not reused)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three has
had a corresponding entry since the WBS was established—the full history of this document has zero
hits for the three headings `**4.7` / `**4.8` / `**8.1` (verifiable with
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and there are no
repository-wide references. The task corresponding to `8.1` is precisely phase 1 of `05` (test
revival and completion). That phase has been decomposed into P1 (`1.1`–`1.3`) and `8.8`; therefore,
P8’s numbering aligns with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered here**: task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: the design rationale for tasks (see `02`–`08`) or the rationale for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered Level 2/Level 3 row
**must contain two fields**—“**Owning phase**” (the P phase to which it truly belongs, which may
differ from the containing section) and “**Blocks the mainline**.” `登记待排期` (“pending
scheduling”) is no longer the default state; an unspecified state is treated as **not schedulable**.
Numbering must be **unique throughout the document** (cross-track tasks use the track number, such
as `029g.x`, and must not occupy an `N.x` identifier).

**Closure registration (effective 2026-11-24)**: a checked row contains only four items—the task ID,
status, **implementation commit short hash** (7 characters), and issue number, if any—on one line:
`- [x] **3.24.1 Completion of remaining pattern-matching work** ✅ 4d608df3 (issue #405)`. **Do not
record the fix, criterion chain, gate thresholds, file line numbers, test names, or review
conclusions**: those belong in the commit message (`git show <short-hash>`). This table is a kanban
board, not a process chronicle. **Do not record adjudication labels or repeat their conclusions**:
“user adjudication A/B/C,” “option A,” “final implementation is…” and similar statements do not
belong in this table—the board answers only “is it complete?” For adjudications and outcomes,
consult the commit messages and the RFC-039 decision register.

**The short hash is authoritative after the push**: a closure row contains the short hash on
`origin/dev` after the push has completed. The order is **push the implementation commit first, then
write the closure row** (see “commit hash is taken after push” in
[commit-convention](../commit-convention.md)). The closure commit itself does not carry a hash—a
self-reference is impossible.

**Count columns contain numbers only**: the Level 1/2/3 counts under “Scope and Positioning” contain
only the current values; increment/decrement history such as `+1 = …` does not belong in the table.

## Target Design: Phase Sequence

```
P0 仓库维护机制与代码放置规程 08 ← 新增，先立规矩
P1 复活孤儿测试并修缺陷 06 §S1
P2 建立等价性判据基线 07 全部
P3 修正确性漏洞（最小方案） 02 §S3-漏洞半部
P4 阶段契约与统一 Driver 02
P5 checker 文件内拆分 02 + 本文补齐
P6 类型表示单一化 03
P7 中间表示 SSA 化 04 } 可并行
P8 前端范式变更 05 }
P9 防反弹门禁（含统一脚本清单） 01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正 06 §S2/S3/S4/S5/S6
```

**Rationale for the new P0**: the three prohibitions—no fabrication, no endless filling, and no
patching when a refactoring is required—constrain every action in P1–P10. The rules must be
established before work begins; otherwise, work would already be adding `mod` declarations to
`tests/mod.rs` while reviving tests in P1, which is precisely the source of the G4 conflict.

## Implementation Highlights: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 stop-the-bleeding path (2026-10-05 adjudication)**: P3’s prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in
> parallel with P3. Stopping the bleeding from correctness defects is not blocked by
> criterion-infrastructure construction; however, **P4 must still wait for all of P2**—the unified
> Driver requires all three layers of criteria to be in place.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-implementation judgment.” P9’s scripts cannot prevent “patching when a refactoring is
  required”; only the D0–D4 review checklist can.
- **P9 as the canonical list of CI scripts**—the three concurrent lists in original gap G3 made
  closure impossible. This table merges them so that the 10 active scripts each belong to one phase
  (9.8 was cancelled by the user on 2026-11-24), and the report-only status and hard-failure timing
  are explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactoring”**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactoring means repeating the same deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341`
  into 7e and incorporating RFC status corrections into S4.
- **P5’s steps are filled in by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker decomposition would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the decomposition must be independently
  revertible.
