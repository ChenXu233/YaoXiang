> **Subordinate design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's stage sequence into **independently committable, independently verifiable**

> responsible solely for breaking down to executable granularity and registering unresolved
> conflicts.

**Numbering gaps (not recycled)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. These three have had no
corresponding entries since the WBS was established—this document's entire history shows zero hits
on `**4.7` / `**4.8` / `**8.1` titles (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), with no references in the
entire repository. `8.1` corresponds exactly to `05`'s stage 1 (test resurrection and completion):
that stage has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering aligns with its stage
numbers (stage 0 → `8.0`, stage 2 → `8.2`, and so on).

**This document covers**: Task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: Design rationale for tasks (see `02`–`08`), arguments for stage
ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered level-2/level-3 rows **must include
two fields**—"**Belonging Stage**" (which P it truly belongs to, may differ from its current
section) and "**Whether it blocks the mainline**"; `registered-awaiting-scheduling` is no longer the
default state, unmarked means **unschedulable**. Numbers must be **unique throughout the document**
(cross-track tasks use the track number, e.g. `029g.x`, must not occupy `N.x`).
**Checkmark/completion registration is based on "task id + evidence (gate value, run id, issue
number, file:line)"**, not commit numbers—`pull --rebase` rewrites local hashes, and hardcoded
numbers will definitely fail (2026-10-13 instance: `94ad03ce4`→`631eb3e3c`). For commit numbers,
check `git log`.

## Goal Design: Stage Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Regulations     08        ← New, establish rules first
P1  Resurrect Orphan Tests and Fix Defects           06 §S1
P2  Establish Equivalence Oracle Baseline             07 all
P3  Fix Correctness Vulnerabilities (Minimal Solution)  02 §S3-Vulnerability half
P4  Stage Contract and Unified Driver                 02
P5  Checker File-Internal Splitting                   02 + filled in here
P6  Type Representation Unification                   03
P7  Intermediate Representation SSA-ization            04      } Runnable in parallel
P8  Frontend Paradigm Change                           05      }
P9  Anti-Rebound Gates (incl. unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other Cleanup and State Correction                 06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (no fabrication / no endless padding / should
refactor but applied patches) constrain every action in P1–P10. Rules must be established before
construction begins, otherwise P1's test resurrection will already be adding `mod` declarations to
`tests/mod.rs`—which is exactly what caused conflict G4.

## Key Decisions and Rationale

- **P0 independent as stage rather than merged into P9**——gates are "after-the-fact checks",
  regulations are "before-the-fact judgments". P9's scripts cannot prevent "should refactor but
  applied patches", only D0–D4's review checklist can.
- **P9 as sole authoritative list of CI scripts**——original gap G3's three parallel lists led to
  inability to close. After this table merges, 11 scripts each assigned to one stage, report-only
  and to-hard timing explicit and queryable.
- **P3.5 incorporated RFC-029g rather than left as "independent track, do after refactor"**——its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Left for after
  refactor execution, equals redoing the same batch of deletion on new grammar, new checker layout
  and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC state
  correction.
- **P5's steps filled in by this document rather than merged into P4**——P4 is already the largest
  single point of risk, additionally stacking checker splitting would exceed rollback granularity.
- **5.3.2 takes "zero caller change" as hard acceptance**——splitting must be independently
  revertable.
