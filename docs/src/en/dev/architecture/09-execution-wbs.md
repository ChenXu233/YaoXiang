# Multi-Level Construction Task Table (WBS)

> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> Phase order and acceptance gates are governed exclusively by RFC-039's main text; this document is
> only responsible for breaking them down to executable granularity and registering unresolved
> conflicts.

**Numbering gaps (not reclaimed)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. The three have had no
corresponding entries since the WBS was established—this document's full history has zero hits on
the `**4.7` / `**4.8` / `**8.1` three headings (verifiable with
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the whole repository has
no references. `8.1` corresponds exactly to phase 1 of `05` (test resurrection and supplementation):
that phase has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering aligns with its phase
number (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**This document covers**: task breakdown, dependencies, parallel groups, acceptance criteria
binding.

**This document does not cover**: task design rationale (see `02`–`08`), phase order argumentation
(see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered level-2/level-3 rows **must carry
two fields**—"**Owning Phase**" (which P it truly belongs to, which may differ from the chapter it's
in) and "**Whether it blocks the main line**"; `Registration pending scheduling` is no longer a
default state, unmarked items are considered **not schedulable**. Numbers **must be unique** within
the whole document (for cross-track tasks, use the track number, e.g., `029g.x`, do not occupy
`N.x`). **Check-off/completion registration is based on "task id + evidence (gate value, run id,
issue number, file:line)", do not write commit hashes**—`pull --rebase` will rewrite local hashes,
hardcoded ones will definitely fail (2026-10-13 example: `94ad03cece`→`631eb3e3c`). Check `git log`
for commit hashes.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement regulations     08        ← New, establish rules first
P1  Resurrect orphan tests and fix defects                               06 §S1
P2  Establish equivalence criteria baseline                              07 all
P3  Fix correctness vulnerabilities (minimum solution)                   02 §S3-vulnerability half
P4  Phase contracts and unified Driver                                   02
P5  checker file internal split                                          02 + filled in by this document
P6  Type representation unification                                       03
P7  Intermediate representation SSA-ization                              04      } Parallelizable
P8  Frontend paradigm change                                              05      }
P9  Anti-rebound gates (including unified script list)                   01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status correction                                   06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (no fabrication / no endless padding / refactoring
needed but applied a patch) constrain every action in P1–P10. Rules must be established before
construction begins, otherwise when P1 resurrects tests it will already be adding `mod` declarations
to `tests/mod.rs`—which is exactly what caused the G4 conflict.

## Implementation Points: Dependencies and Parallelism

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 bleeding channel (2026-10-05 ruling)**: P3's prerequisite narrowed to **2.3.2 + 2.4.1 +
> 2.4.3** (multi-file corpus layer + two red criteria). P2's rest (2.1 IR verifier, 2.2 snapshot,

> vulnerability bleeding not blocked by criterion infrastructure construction; but **P4 still must
> wait for P2 all complete**—unified Driver needs three-layer criteria all in place.

## Key Decisions and Reasons

- **P0 independent as phase not merged into P9**—gate is "post-check", regulation is "pre-judgment".
  P9's script cannot prevent "refactoring needed but applied a patch", only D0–D4's review checklist
  can.
- **P9 as CI script's sole authoritative list**—original gap G3's three coexisting lists led to
  unable to close. After this table merges 11 scripts each belong to one phase, report-only and hard
  conversion timing explicit and queryable.
- **P3.5 incorporates RFC-029g not "independent track, wait for refactor"**—its deletion surface
  overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Deferred to after refactor execution
  equals doing the same batch of deletions on new grammar, new checker layout and new IR; this is
  the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status correction.
- **P5's steps filled in by this document not merged into P4**—P4 is already the largest single
  point risk, adding checker split on top will exceed rollback granularity.
- **5.3.2 with "zero caller change" as hard acceptance**—split must be independently revertible.
