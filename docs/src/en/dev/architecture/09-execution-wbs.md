# Multi-Level Work Breakdown Structure (WBS)

> **Supporting design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC's phase sequence into **level-three tasks that can be committed and verified
> independently**.
>
> The phase sequence and acceptance gates are governed solely by the body of RFC-039; this document
> only breaks the work down to executable granularity and records conflicts that have not yet been
> adjudicated.

**Unassigned numbers (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. All three have
had no corresponding entries since the WBS was established—the entire history of this document has
zero matches for the three headings `**4.7` / `**4.8` / `**8.1` (verifiable with
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and there are no references
to them anywhere in the repository. `8.1` corresponds precisely to phase 1 of `05` (test revival and
completion): that phase was split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering is aligned with
its phase number (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and
acceptance-criterion bindings.

**Not covered by this document**: the design rationale for the tasks (see `02`–`08`) or the
rationale for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered level-2/level-3 row
**must contain two fields**—**“Owning Phase”** (the P phase to which it truly belongs, which may
differ from the section in which it appears) and **“Blocks the Mainline”**; `Awaiting scheduling` is
no longer the default status, and an unmarked task is considered **not schedulable**. Numbers **must
be unique across the entire document** (cross-track tasks use their track number, such as `029g.x`,
and must not occupy an `N.x` number). **Checking off or registering completion is based on “task
ID + evidence (gate metrics, run ID, issue number, file:line),” not commit IDs**—`pull --rebase`
rewrites local hashes, so hard-coded IDs inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Look up commit IDs with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: the three prohibitions—no fabrication, no endless filling, and no patching
when a refactor is required—constrain every action in P1–P10. The rules must be established before
work begins; otherwise, while reviving tests in P1, work would already be adding `mod` declarations
to `tests/mod.rs`, which is precisely the source of the G4 conflict.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 hemorrhage-stopping path (decision on 2026-10-05)**: P3's prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in
> parallel with P3. Stopping the bleeding from correctness vulnerabilities is not blocked by
> criterion-infrastructure construction; however, **P4 must still wait for all of P2**—the unified
> Driver requires all three layers of criteria to be in place.

| Constraint                | Reason                                                                                                                                                                                                                                                               |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1                   | The three prohibitions constrain every P1 action (1.2.x is itself adding `mod` declarations to `mod.rs`)                                                                                                                                                             |
| P1 → P2                   | Reviving tests changes the test count and corpus baseline                                                                                                                                                                                                            |
| P2 (after narrowing) → P3 | The vulnerability criteria must be **written in red first** (2.4.1/2.4.3) + the multi-file corpus layer (2.3.2) must exist so that the red tests have somewhere to run                                                                                               |
| P3 → P4                   | Fix bugs before refactoring; reversing the order would cause bugs to become fixed into the stage table as “established behavior”                                                                                                                                     |
| P3.5 → P4                 | RFC-029g's (#399) removal surface covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 respectively (the inventory is in this document's §P3.5)—reversing the order means repeating the same removals on the new grammar, new checker layout, and new IR (D56) |
| P4 → P5                   | The `include!` conversion and checker split modify the same file                                                                                                                                                                                                     |
| P5 → P6                   | Consecutive changes to the same file must be separated; otherwise regressions cannot be binary-searched                                                                                                                                                              |
| P6 → P7 / P8              | If the type representation does not converge first, the new IR will grow into a third representation                                                                                                                                                                 |
| P7/P8 → P9                | 9.5's snapshot baseline and 9.3's `pub(crate)` leak count reach their final form only after P7/P8                                                                                                                                                                    |

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “after-the-fact checks,” while
  rules are “before-the-fact judgment.” P9's scripts cannot prevent “patching when a refactor was
  required”; only the D0–D4 review checklist can do that.
- **P9 is the sole authoritative inventory of CI scripts**—the original gap G3's three coexisting
  inventories made closure impossible. After this table merges them, all 11 scripts have one owning
  phase, and report-only status and strict-mode timing are explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to do after the
  refactor”**—its removal surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactor means repeating the same removals on the new grammar,
  new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  RFC status corrections into S4.
- **P5's steps are completed in this document rather than folded into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertable.
