**Number gaps (not reclaimed)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. The three have had no
corresponding entries since the WBS was established—this document's entire history shows zero hits
for the three titles `**4.7` / `**4.8` / `**8.1` (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and no references exist
throughout the repo. What `8.1` corresponds to is `05`'s stage 1 (test resurrection and completion):
that stage has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering aligns with its stage
numbers (stage 0 → `8.0`, stage 2 → `8.2`, etc.).

**This document covers**: task decomposition, dependency relationships, parallel grouping,
acceptance criterion binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), argumentation for
stage order (see RFC-039).

**Registration conventions (effective 2026-10-12)**: Newly registered level 2/3 rows **must carry
two fields**—"**Owning stage**" (which P it truly belongs to, which may differ from its section) and
"**Whether it blocks the main line**"; `registered-awaiting-scheduling` is no longer the default
state, and unmarked entries are deemed **unschedulable**. Numbers must be **unique throughout the
document** (for tasks across tracks, use track numbers, e.g. `029g.x`, must not occupy `N.x`).
**Check-off/completion registration is based on "task id + evidence (gate value, run id, issue
number, file:line)", not commit numbers**—`pull --rebase` will rewrite local hashes, so hardcoded
numbers are bound to fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). For commit numbers, check
`git log`.

## Target Design: Stage Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Regulations   08        ← New, establish rules first
P1  Resurrect Orphan Tests and Fix Defects   06 §S1
P2  Establish Equivalence Oracle Baseline    07 all
P3  Fix Correctness Vulnerabilities (Minimal Scheme)    02 §S3-Vulnerability Half
P4  Stage Contract and Unified Driver        02
P5  Checker File Internal Split              02 + supplemented by this document
P6  Type Representation Unification          03
P7  Intermediate Representation SSA-ification  04      } can run in parallel
P8  Frontend Paradigm Change                  05      }
P9  Anti-Rebound Gates (including unified script list)    01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Other Cleanup and Status Correction      06 §S2/S3/S4/S5/S6
```

**Reason for the new P0**: Three prohibitions (no fabrication / no endless padding / should refactor
but patched) constrain every action in P1–P10. Rules must be established before work starts,
otherwise when P1 resurrects tests, `mod` declarations are already being added to
`tests/mod.rs`—which is exactly the cause of the G4 conflict.

### P3 Fix Correctness Vulnerabilities (Minimal Scheme)

Source: [02](02-stage-contract.md) §Implementation Points S3 vulnerability fix half + **2026-10-07
silent drop point audit (3.4)**

> **Semantic correction triage (D59, 2026-10-11 user adjudication)**: If this track and subsequent
> stages discover defects where "old behavior doesn't count as success"—**A silent failure / B
> silent mismatch / C undefined behavior and resource runaway** (crash, stack overflow, silently
> giving wrong answer)—**may be fixed along with refactoring**, four conditions all required: ①
> Red-then-green first (red criterion exists first and is indeed red); ② Does not change the
> external behavior of "programs that could originally successfully compile and correctly run" (must
> not become failure, must not modify existing diagnostic codes/text/exit codes); ③ Same-commit
> registration (this row marks error type + that stage revision note + PR required block "error
> type" one line); ④ Baseline regenerated same commit + manual review diff. **D user-visible
> semantics / E external contract table / F RFC-level design change three categories still must
> first get user adjudication**. Criterion expansion and A–F whitelist see
> [07 §Semantic Correction Triage Criteria](07-equivalence-oracle.md); **does not adopt "default
> super-refactor + post-registration"** (reason see RFC-039 D59: zero red criterion cannot

## Key Decisions and Reasons

- **P0 is an independent stage rather than merged into P9**—gates are "post-hoc check", regulations
  are "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as the sole authoritative list of CI scripts**—original gap G3's three coexisting lists made
  closure impossible. After merging 11 scripts each attributed to one stage, report-only and
  switch-to-hard timing explicitly checkable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"**—its
  deletion face coincides with P4/P5/P6/P7/P8's rewrite face (RFC-039 D56). Leaving for after
  refactoring means redoing the same batch of deletions on new grammar, new checker layout, new IR;
  this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status correction.
- **P5's steps are supplemented by this document rather than merged into P4**—P4 is already the
  largest single-point risk, further adding checker split would exceed rollback-able granularity.
- **5.3.2 uses "zero caller changes" as hard acceptance**—split must be independently revertable.
