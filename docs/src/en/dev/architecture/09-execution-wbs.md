# Multi-level Construction Task Table (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The authoritative source for phase ordering and acceptance gates is the RFC-039 main text; this
> document only decomposes to executable granularity and registers conflicts not yet decided.

## Position and Scope

| Level       | Count       | Meaning                                                                                                                                                            |
| ----------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Level 1** | 11 (P0–P10) | Phases, one-to-one with the phase sequence in RFC-039                                                                                                              |
| **Level 2** | 50          | Task groups, from each document's "Implementation Points" + 2026-10-07 audit supplement (P3's 3.4) + 2026-10-10/11 ruling registrations (P3's 3.5/3.6/3.7/3.8/3.9) |
| **Level 3** | 140         | Independently committable actions                                                                                                                                  |

**This document covers**: task decomposition, dependencies, parallel groups, acceptance-criterion
binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), justification for
phase ordering (see RFC-039).

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← New, establish rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence criterion baseline       07 all
P3  Fix correctness vulnerabilities (minimum viable)  02 §S3-vulnerability half
P4  Stage contract and unified Driver             02
P5  In-file checker split                          02 + this document fills in
P6  Unify type representation                      03
P7  SSA-ify intermediate representation            04      } parallelizable
P8  Frontend paradigm change                       05      }
P9  Anti-rebound gates (including unified script inventory)  01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and state corrections            06 §S2/S3/S4/S5/S6
```

**Reason for new P0**: Three prohibitions (no fabrication / no endless filling / patch instead of
refactor) constrain every action in P1–P10. Rules must be established before work starts, otherwise
by P1's test revival we would already be adding `mod` declarations to `tests/mod.rs` — which is
exactly what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 is an independent stage rather than merged into P9** — gates are "post-hoc check", rules are
  "pre-judgment". P9's scripts cannot prevent "should have refactored but patched", only D0–D4's
  review checklist can.
- **P9 as the sole authoritative inventory of CI scripts** — original gap G3's three parallel
  inventories couldn't be closed. This table after merging 10 scripts each owned by one stage,
  report-only and harden timing explicitly checkable.
- **P3.5 absorbs RFC-029g rather than leaving it as "independent track, do after refactor"** — its
  removal surface coincides with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving it for
  post-refactor execution equals doing the same batch of removal on new grammar, new checker layout
  and new IR again; this is the same lesson as 7e absorbing `2315`/`2341`, S4 absorbing RFC state
  correction.
- **P5's steps are filled in by this document rather than merged into P4** — P4 is already the
  largest single point risk, stacking checker split would exceed rollback granularity.
- **5.3.2 takes "zero caller-side change" as hard acceptance** — split must be independently
  revertible.
