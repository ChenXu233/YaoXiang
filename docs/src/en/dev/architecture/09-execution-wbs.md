# Multi-Level Implementation Task Table (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC’s phase sequence into **three-level tasks that can be committed and verified
> independently**.
>
> The phase order and acceptance gates defined in the body of RFC-039 are the sole authority. This
> document is responsible only for breaking the work down to an executable granularity and recording
> conflicts that have not yet been adjudicated.

**Reserved numbers (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three
has had a corresponding entry since the WBS was established—the entire history of this document has
zero matches for the three headings `**4.7` / `**4.8` / `**8.1` (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and there are no
repository-wide references either. `8.1` corresponds precisely to phase 1 of `05` (test revival and
completion): that phase was split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s numbering remains aligned
with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered here**: task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: the design rationale for tasks (see `02`–`08`) or the justification for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered Level 2/Level 3 rows **must
include two fields**—“**owning phase**” (the P to which the task truly belongs, which may differ
from its current section) and “**blocks the mainline**.” `pending scheduling` is no longer the
default state; an unmarked task is considered **not schedulable**. Numbers must be **unique
throughout the document** (tasks on separate tracks use their track number, such as `029g.x`, and
must not occupy `N.x`). **Checkoff/completion registration is based on “task ID + evidence (gate
metric, run ID, issue number, file:line)” and does not record commit hashes**—`pull --rebase`
rewrites local hashes, so hard-coded hashes inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit hashes.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (do not invent constructs / do not pad
indefinitely / do not patch when a refactor is required) constrain every action in P1–P10. The rules
must be established before implementation begins; otherwise, while reviving tests in P1, work would
already begin adding `mod` declarations to `tests/mod.rs`—the very practice that caused conflict G4.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 emergency path (decision 2026-10-05)**: P3’s prerequisites are narrowed to **2.3.2 + 2.4.1 +
> 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR verifier, 2.2
> snapshots, 2.3.1/2.3.3 differential and performance baseline) may proceed in parallel with P3.
> Stopping the bleeding for correctness defects must not be blocked by criterion-infrastructure
> construction; however, **P4 must still wait for all of P2**—the unified Driver requires all three
> layers of criteria to be in place.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “after-the-fact checks,” whereas
  rules are “before-the-fact judgment.” P9’s scripts cannot prevent “patching when a refactor was
  required”; only the D0–D4 review checklist can.
- **P9 is the sole authoritative inventory of CI scripts**—the original G3’s three competing
  inventories made closeout impossible. This table merges them into 11 scripts, each owned by one
  phase, with report-only status and strict-transition timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to do after the
  refactor”**—its deletion surface overlaps with P4/P5/P6/P7/P8’s rewrite surfaces (RFC-039 D56).
  Deferring it until after the refactor would require repeating the same deletions on the new
  grammar, checker layout, and IR; this is the same lesson as incorporating `2315`/`2341` into 7e
  and RFC-status corrections into S4.
- **P5’s steps are filled in by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker decomposition would exceed revertible granularity.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the decomposition must be
  independently revertible.
