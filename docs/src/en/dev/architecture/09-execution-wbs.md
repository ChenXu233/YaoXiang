# Multi-level Work Breakdown Structure (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md); it
> expands the RFC's stage sequence into a three-level task list where each item can be independently
> committed and independently verified.
>
> The stage order and acceptance gates take RFC-039 itself as the sole authority; this document only
> breaks the work down to an executable granularity and records conflicts that have not yet been
> adjudicated.

## Position and Scope

| Level       | Count                                                               | Meaning                                                                                                                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                                         | Stages, one-to-one with the stage sequence in RFC-039                                                                                                                                                                                                                                                                       |
| **Level 2** | 56 (2026-10-13: 53 +2 = 3.13 / 3.14; 2026-10-14: +1 = 3.15)         | Task groups, drawn from each document's "implementation points" + the 2026-10-07 audit addendum (P3's 3.4) + the 2026-10-10/11 ruling additions (P3's 3.5/3.6/3.7/3.8/3.9) + the 2026-10-12 registration (P3's 3.10) + the 2026-10-12 discovery addition (P3's 3.11) + the 2026-10-12 second discovery addition (P3's 3.12) |
| **Level 3** | 147 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1; 2026-10-14: +1 = 3.15.1) | Independently committable actions                                                                                                                                                                                                                                                                                           |

**This document covers**: task breakdown, dependencies, parallel grouping, and binding of acceptance
criteria.

**This document does not cover**: the design rationale for the tasks (see `02`–`08`), or the
argument for the stage ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: newly registered Level 2/3 rows **must include two
fields** — "**Belonging stage**" (the actual P it belongs to, which may differ from the section it
appears in) and "**Whether it blocks the main line**"; `awaiting scheduling` is no longer the
default state — anything without that label is treated as **not schedulable**. Numbers **must be
unique across the whole document** (tasks crossing tracks use the track number, e.g. `029g.x`, and
must not occupy an `N.x` slot). **Check-off / completion registration uses "task id + evidence (gate
values, run id, issue number, file:line)" as the criterion, not commit hashes** — `pull --rebase`
rewrites local hashes, and hard-coded numbers will fail (2026-10-13 case: `94ad03ce4`→`631eb3e3c`).
Look up commit numbers in `git log`.

## Target Design: Stage Sequence

```
P0  Repository maintenance mechanism and code placement rules   08        ← Newly added, set rules first
P1  Resurrect orphan tests and fix defects                      06 §S1
P2  Establish equivalence-criterion baseline                    07 all
P3  Fix correctness vulnerabilities (minimum scheme)            02 §S3 vulnerability half
P4  Stage contract and unified Driver                           02
P5  Split checker inside the file                               02 + filled in by this document
P6  Unify type representation                                   03
P7  SSA-ify intermediate representation                         04      } parallelizable
P8  Frontend paradigm change                                     05      }
P9  Anti-rebound gates (with unified script list)               01 §Anti-rebound + 08 §Machine-checkable rules
P10 Remaining cleanup and state correction                      06 §S2/S3/S4/S5/S6
```

**Reason for the new P0**: the three prohibitions (no fabrication / no endless padding / patch when
refactor was needed) constrain every action in P1–P10. The rules must be in place before work
begins, otherwise by the time P1 resurrects tests we'll already be adding `mod` declarations to
`tests/mod.rs` — which is exactly what caused the G4 conflict.

### P3 Fix correctness vulnerabilities (minimum scheme)

Source: [02](02-stage-contract.md) §Implementation points S3's vulnerability-fix half + **2026-10-07
silent-drop-point audit (3.4)**

> **Semantic-correction branching (D59, user ruling on 2026-10-11)**: if this track and subsequent
> stages discover a defect where "old behavior is not a success" — **A silent failure / B silent
> mismatch / C undefined behavior and resource loss** (crash, stack overflow, silently giving the
> wrong answer) — **it may be fixed along the way during refactoring**, with all four conditions
> met: ① red-then-green (red criterion exists first and really is red); ② does not change the
> external behavior of programs that "previously compiled successfully and ran correctly" (must not
> become a failure, must not delete or change its existing diagnostic code/text/exit code); ③
> same-commit registration (this row labels the error type + that stage's revision note + the PR
> required block's "error type" line); ④ baseline regenerated in the same commit + manual review of

> super-refactor + post-registration" is not adopted** (reasoning in RFC-039 D59: zero red criteria

### Mandatory serial main chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

## Key Decisions and Reasoning

- **P0 is a separate stage, not merged into P9** — gates are "post-hoc checks", rules are
  "pre-judgment". P9's scripts cannot prevent "patching when refactor was needed"; only D0–D4's
  review checklist can.
- **P9 as the sole authoritative list of CI scripts** — the original G3's three parallel lists made
  it impossible to close. After this table's merge, 10 scripts are each assigned to one stage, with
  report-only and hard-switch timing explicit and queryable.
- **P3.5 incorporates RFC-029g rather than leaving it as an "independent track, do it after the
  refactor"** — its deletion surface overlaps with the rewrite surface of P4/P5/P6/P7/P8 (RFC-039
  D56). Leaving it for after the refactor means doing the same batch of deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341`
  and S4 incorporating RFC state correction.
- **P5's steps are filled in by this document, not merged into P4** — P4 is already the largest
  single-point risk; piling on checker splitting would exceed the revertable granularity.
- **5.3.2 takes "zero caller-side changes" as hard acceptance** — the split must be independently
  revertible.
