# Multi-level Work Breakdown Structure (WBS)

> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the phase sequence of the RFC into **independently committable, independently verifiable**
> three-level tasks.
>
> Phase order and acceptance gates are governed exclusively by RFC-039 itself; this document only
> breaks them down to executable granularity and registers conflicts that have not yet been
> adjudicated.

## Position and Scope

| Level       | Count       | Meaning                                                                                                                                                                                                                                                                                                                                                 |
| ----------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, corresponding one-to-one to the phase sequence in RFC-039                                                                                                                                                                                                                                                                                       |
| **Level 2** | 53          | Task groups, drawn from the "Implementation Points" sections of each document + the 2026-10-07 audit supplement (3.4 in P3) + the 2026-10-10/11 adjudication supplement (3.5/3.6/3.7/3.8/3.9 in P3) + the 2026-10-12 registration (3.10 in P3) + the 2026-10-12 discovery supplement (3.11 in P3) + the 2026-10-12 discovery re-supplement (3.12 in P3) |
| **Level 3** | 144         | Independently committable actions                                                                                                                                                                                                                                                                                                                       |

**This document covers**: task breakdown, dependencies, parallel groups, and binding of acceptance
criteria.

**This document does not cover**: the design rationale for each task (see `02`–`08`) or the argument
for the phase order (see RFC-039).

**Registration Convention (effective 2026-10-12)**: newly registered level-2/level-3 rows **must
carry two fields** — "**Owning Phase**" (which P it truly belongs to; may differ from the section it
appears in) and "**Whether It Blocks the Main Line**"; `Registered, awaiting scheduling` is no
longer a default state; unmarked items are considered **not schedulable**. Numbering **must be
unique** within the entire document (tasks spanning tracks use the track number, e.g. `029g.x`, and
must not occupy `N.x`).

## Target Design: Phase Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Rules     08        ← New, establish rules first
P1  Revive Orphan Tests and Fix Defects           06 §S1
P2  Establish Equivalence Criterion Baseline      07 All
P3  Fix Correctness Vulnerabilities (Minimal Solution)       02 §S3-Vulnerability Half
P4  Stage Contract and Unified Driver          02
P5  Split Within checker File             02 + Filled in by this document
P6  Type Representation Unification              03
P7  Intermediate Representation SSA-ization                04      } Parallelizable
P8  Frontend Paradigm Change                   05      }
P9  Anti-regression Gates (incl. Unified Script Inventory)     01 §Anti-regression + 08 §Machine-Checkable Rules
P10 Other Cleanup and Status Corrections             06 §S2/S3/S4/S5/S6
```

**Rationale for the New P0**: the three prohibitions (no fabrication / no endless padding / patch
instead of refactor when refactor is warranted) constrain every action in P1–P10. Rules must be
established before any work begins; otherwise, when P1 revives tests, `mod` declarations are already
being added to `tests/mod.rs` — which is exactly what caused the G4 conflict.

### P3 Fix Correctness Vulnerabilities (Minimal Solution)

Source: [02](02-stage-contract.md) §Implementation Points S3 vulnerability fix half + **2026-10-07
Silent Drop Point Audit (3.4)**

> **Semantic Correction Branching (D59, 2026-10-11 user adjudication)**: if this track and
> subsequent phases discover defects where "the old behavior does not count as success" — **A silent
> failure / B silent mismatch / C undefined behavior and resource runaway** (crash, stack overflow,
> silent wrong answer) — **they may be fixed along with the refactor**, with all four of the
> following requirements: ① red-before-green (the red criterion exists first and is indeed red); ②
> do not change the external behavior of programs that "could previously compile and run correctly"
> (must not become failures; must not change existing diagnostic codes / messages / exit codes); ③
> same-commit registration (this row annotated with error type + phase revision note + PR required
> block "Error Type" line); ④ baseline regenerated in the same commit + manual review of diff. **D

> user adjudication first. See

> the A–F whitelist; **"default super-refactor + after-the-fact registration" is not adopted**
> (rationale: RFC-039 D59 — zero red criteria cannot distinguish fixes from regressions, and

## Key Decisions and Rationale

- **P0 as a separate phase rather than merged into P9** — gates are "after-the-fact checks", rules
  are "before-the-fact judgments". P9's scripts cannot prevent "should refactor but instead
  patched", only the D0–D4 review checklist can.
- **P9 as the only authoritative inventory of CI scripts** — the original gap G3's three coexisting
  inventories led to an inability to close. After this table's merge, the 10 scripts each belong to
  one phase, and report-only vs. turned-hard timing is explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as "independent track, do after refactor"** —
  its deletion surface overlaps with the rewrite surface of P4/P5/P6/P7/P8 (RFC-039 D56). Leaving it
  for post-refactor execution means redoing the same batch of deletions on the new grammar, new
  checker layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4
  incorporating RFC status corrections.
- **P5's steps filled in here rather than merged into P4** — P4 is already the largest single-point
  risk; additionally overlaying the checker split exceeds revertible granularity.
- **5.3.2 takes "zero caller-side change" as hard acceptance** — the split must be independently
  revertible.
