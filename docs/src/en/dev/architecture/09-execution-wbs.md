# Multi-Level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence in the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> The phase order and acceptance gates use RFC-039 body text as the sole authority; this document is
> only responsible for breaking it down to an executable granularity and registering
> as-yet-undecided conflicts.

**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criterion
binding.

**This document does not cover**: rationale for task design (see `02`–`08`), arguments for phase
order (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields**—**"Belonging Phase"** (which P it truly belongs to, may differ from the chapter it's placed
in) and **"Whether it blocks the main line"**; `registered awaiting scheduling` is no longer the
default state, anything not labeled is considered **not schedulable**. Numbering **must be unique**
within the entire document (tasks across tracks use the track number, e.g., `029g.x`, must not
occupy `N.x`). **Check-off/completion registration is based on "task id + evidence (gate value, run
id, issue number, file:line)"**, do not write commit hashes—`pull --rebase` rewrites local hashes,
hardcoded ones will inevitably become invalid (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). To look
up commit hashes check `git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← New, rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence criterion baseline             07 all
P3  Fix correctness vulnerabilities (minimal solution)        02 §S3-vulnerability half
P4  Phase contract and unified Driver          02
P5  checker file internal split             02 + this document's supplement
P6  Unify type representation                 03
P7  Intermediate representation SSA-ization                04      } parallelizable
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gate (including unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and state correction             06 §S2/S3/S4/S5/S6
```

**Rationale for the new P0**: The three prohibitions (must not fabricate / must not endlessly pad /
should refactor but applied a patch) constrain every action from P1–P10. Rules must be established
before work starts, otherwise when P1 revives tests, `mod` declarations will already be added to
`tests/mod.rs`—which is exactly the cause of conflict G4.

## Key Decisions and Rationale

- **P0 independent phase not merged into P9**—gate is "post-hoc check", rules are "pre-judgment".
  P9's script cannot prevent "should refactor but applied patch", only D0–D4's review checklist can.
- **P9 as CI script's sole authority list**—original gap G3's three parallel coexisting lists made
  finalization impossible. After this table's merge, 10 scripts each belong to one phase,
  report-only and convert-to-hard timing explicit and queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, wait until after
  refactor"**—its deletion surface coincides with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56).
  Deferring to after refactor equals doing the same batch of deletion on new grammar, new checker
  layout and new IR; this is the same lesson as 7e absorbing `2315`/`2341`, S4 absorbing RFC state
  correction.
- **P5's steps filled in by this document rather than merged into P4**—P4 is already the largest
  single-point risk, further stacking checker split would exceed rollback granularity.
- **5.3.2 takes "zero caller changes" as hard acceptance**—split must be independently revertable.
