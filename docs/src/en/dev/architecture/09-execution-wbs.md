# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC's phase sequence into **three levels of tasks that can be committed and verified
> independently**.
>
> The phase order and acceptance gates are governed solely by the main body of RFC-039; this
> document is responsible only for decomposing the work into executable granularity and recording
> conflicts that have not yet been adjudicated.

## Scope and Positioning

| Level       | Count       | Meaning                                                                                      |
| ----------- | ----------- | -------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, in one-to-one correspondence with RFC-039's phase sequence                           |
| **Level 2** | 73          | Task groups: work groups decomposed by phase; each can be staffed and archived independently |
| **Level 3** | 260         | Work units that can be committed and verified independently                                  |

**Numbering gaps (not reused)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. These three numbers
have had no corresponding entries since the WBS was established—the three headings `**4.7` / `**4.8`
/ `**8.1` have never appeared anywhere in this document's history (this can be verified with
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and there are no
repository-wide references to them. `8.1` corresponds precisely to phase 1 of `05` (test revival and
completion): that phase was broken into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering is aligned
with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and binding
of acceptance criteria.

**Not covered by this document**: the design rationale for tasks (see `02`–`08`) or the rationale
for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered Level 2/Level 3 rows **must
contain two fields**—“**Owning phase**” (the P to which the task genuinely belongs, which may differ
from the current section) and “**Blocks mainline**.” `Pending scheduling registration` is no longer
the default state; an unmarked task is deemed **not schedulable**. Numbers must be **unique
throughout the document** (tasks on parallel tracks use the track number, such as `029g.x`, and must
not occupy an `N.x` number).

**Closure registration (effective 2026-11-24)**: a checked row contains only four items—task ID,
status, **implementation commit short hash** (7 characters), and issue number (only when present),
written on one line: `- [x] **3.24.1 Remaining pattern-matching work** ✅ 4d608df3 (issue #405)`.
**Do not write the fix, the criterion chain, gate thresholds, file line numbers, test names, or
review conclusions**: those belong in the commit message (`git show <short hash>`). This table is a
board, not a process chronicle. **Do not write adjudication labels or restate conclusions**: “user
adjudication A/B/C,” “Option A,” “Plan A,” and “the final implementation is…” must not appear
here—the board answers only “is it complete?”; consult commit messages and the RFC-039 decision
register for adjudications and outcomes.

**Short hashes are authoritative after push**: a closure row contains the short hash on `origin/dev`
after the push has completed. The order is **push the implementation commit first, then write the
closure row** (see “commit number is obtained after push” in
[commit-convention](../commit-convention.md)). The closure commit itself has no hash—self-reference
is impossible.

**Count columns contain numbers only**: the Level 1/2/3 counts under `Scope and Positioning` contain
only current values; increment/decrement history such as `+1 = …` does not belong in the table.

## Target Design: Phase Sequence

```
P0 仓库维护机制与代码放置规程 08 ← 新增，先立规矩
P1 复活孤儿测试并修缺陷 06 §S1
P2 建立等价性判据基线 07 全部
P3 修正确性漏洞（最小方案） 02 §S3-漏洞半部
P4 阶段契约与统一 Driver 02
P5 checker 文件内拆分 02 + 本文补齐
P6 类型表示单一化 03
P7 中间表示 SSA 化 04 } 可并行
P8 前端范式变更 05 }
P9 防反弹门禁（含统一脚本清单） 01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正 06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (do not invent / do not pad indefinitely / do
not patch when a refactor is required) constrain every action in P1–P10. The rules must be
established before work begins; otherwise, while reviving tests in P1, work would already begin
adding `mod` declarations to `tests/mod.rs`—precisely the cause of the G4 conflict.

### P3 Fix Correctness Defects (Minimal Approach)

Source: the defect-fix half of [02](02-stage-contract.md) §Implementation Points S3 ＋ **2026-10-07
silent-discard-point audit (3.4)**

> **Semantic-correction routing (D59, adjudicated 2026-10-11)**: if this track or a later phase
> discovers a defect for which **“the old behavior does not count as success”**—**A silent failure /
> B silent mismatch / C undefined behavior and resource loss** (crash, stack overflow, silently
> returning the wrong answer)—it **may be fixed in passing during the refactor**, provided all four
> requirements are met: ① red first, then green (the red criterion must exist first and genuinely
> fail); ② the externally observable behavior of programs that **previously compiled and ran
> correctly** must not change (they must not turn into failures, and their existing diagnostic
> codes/text/exit codes must not be removed or changed); ③ register it in the same commit (this row
> identifies the error type + the phase's revision note + the PR's required “Error Type” field); ④
> regenerate the baseline in the same commit + manually review the diff. **The three categories D
> user-visible semantics / E external contract table / F RFC-level design change must still be
> adjudicated first. See [07 §Semantic-Correction Routing Criteria](07-equivalence-oracle.md) for
> the detailed criteria and the A–F allowlist; the “default super-refactor + retroactive
> registration” approach is **not adopted** (the rationale is in RFC-039 D59: without a red
> criterion, fixes cannot be distinguished from regressions, and this conflicts with “no C5′” and
> “no relaxation whatsoever”).

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 stop-the-bleeding path (adjudicated 2026-10-05)**: P3's prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The remainder of P2 (2.1
> IR verifier, 2.2 snapshots, 2.3.1/2.3.3 differential testing and performance baseline) may proceed
> in parallel with P3. Stopping the bleeding from correctness defects is not blocked by
> criterion-infrastructure work; however, **P4 must still wait for all of P2**—the unified Driver
> requires all three layers of criteria to be in place.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “post-hoc checks,” whereas rules
  are “prior judgment.” P9's scripts cannot prevent “patching when a refactor was required”; only
  D0–D4's review checklist can.
- **P9 is the sole authoritative inventory of CI scripts**—the original G3 gap, with three
  coexisting inventories, made closure impossible. This table merges them and assigns the 10 active
  scripts to one phase each (9.8 was cancelled by the user on 2026-11-24), making report-only status
  and conversion timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56).
  Deferring execution until after the refactor means repeating the same deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341`
  into 7e and RFC status corrections into S4.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the granularity at which work can be
  rolled back.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertible.

  defects should not be rolled back” and lacks a requirement to record “what was fixed.” **Execution
  convention**: every 1.3.x fix's commit message must cite the fixed test name and defect
  description as evidence for later bisection.

  commits 7b.1a / 7b.1b under DoD 6.
