# Multi-Level Construction Task Table (WBS)

> **Subsidiary Design Document**. This document is a subsidiary to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates take RFC-039 itself as the sole authority; this document only
> handles decomposition to an executable granularity and registers any undecided conflicts.

## Positioning and Scope

| Level       | Count       | Meaning                                                                                                                                                                                                                                                                                                        |
| ----------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, corresponding one-to-one with RFC-039's phase sequence                                                                                                                                                                                                                                                 |
| **Level 2** | 53          | Task groups, from each document's "Implementation Essentials" + 2026-10-07 audit supplement (3.4 of P3) + 2026-10-10/11 ruling supplements (3.5/3.6/3.7/3.8/3.9 of P3) + 2026-10-12 registration (3.10 of P3) + 2026-10-12 discovery supplement (3.11 of P3) + 2026-10-12 discovery re-supplement (3.12 of P3) |
| **Level 3** | 144         | Independently committable actions                                                                                                                                                                                                                                                                              |

**This document covers**: task decomposition, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: task design rationale (see `02`–`08`), phase order justification
(see RFC-039).

**Registration Convention (from 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields** — "**Owning Phase**" (which P it truly belongs to; may differ from the containing section)
and "**Whether Blocks Main Line**"; `registered pending scheduling` is no longer the default state,
and without a label it is considered **not schedulable**. Numbers **must be unique** within the
entire document (cross-track tasks use the track number, e.g., `029g.x`, and must not occupy `N.x`).

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules   08        ← new, establish rules first
P1  Revive orphan tests and fix defects                         06 §S1
P2  Establish equivalence oracle baseline                       07 entire
P3  Fix correctness vulnerabilities (minimum solution)          02 §S3-vulnerability half
P4  Phase contracts and unified Driver                          02
P5  checker intra-file split                                    02 + this document supplements
P6  Unify type representation                                   03
P7  Intermediate representation SSA-ization                      04      } parallelizable
P8  Frontend paradigm change                                    05      }
P9  Anti-rebound gates (including unified script list)          01 §Anti-rebound + 08 §Machine-checkable rules
P10 Remaining cleanup and status corrections                    06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (must not invent / must not endlessly pad / should
refactor but applied a patch) constrain every action in P1–P10. Rules must be established before
construction begins, otherwise by P1's test revival we are already adding `mod` declarations to
`tests/mod.rs` — which is exactly the cause of the G4 conflict.

> phases discover defects where "old behavior does not count as success" — **A silent failure / B

## Key Decisions and Rationale

- **P0 is its own phase rather than merged into P9** — gates are "post-hoc check", rules are
  "pre-hoc judgment". P9's scripts cannot prevent "should refactor but applied a patch", only
  D0–D4's review checklist can.
- **P9 as the sole authoritative list of CI scripts** — the original gap G3's three parallel lists
  led to inability to close. After this table merges, 10 scripts each belong to one phase,
  report-only and hard-conversion timing explicit and queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"** — its
  deletion surface coincides with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for
  post-refactor execution equals redoing the same batch of deletion on new grammar, new checker
  layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341` and S4 incorporating
  RFC status corrections.
- **P5's steps supplemented by this document rather than merged into P4** — P4 is already the
  largest single-point risk, additionally stacking checker split will exceed the rollbackable
  granularity.
