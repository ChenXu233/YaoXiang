# Multi-level Construction Task List (WBS)

> **Subsidiary design document**. This document is a subsidiary to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence of the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> The phase order and acceptance gates are solely authoritative in RFC-039; this document is only
> responsible for breaking them down to an executable granularity and registering unresolved
> conflicts.

**Numbering left blank (not recycled)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. These three have
had no corresponding entries since the establishment of the WBS—the full history of this document
has zero hits on the three titles `**4.7` / `**4.8` / `**8.1` (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and no references throughout
the repository. `8.1` corresponds exactly to Phase 1 of `05` (test revival and completion): that
phase has been split into P1 (`1.1`–`1.3`) and `8.8`, so the numbering of P8 is aligned with its
phase number (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**This document covers**: task decomposition, dependency relationships, parallel grouping,
acceptance criterion binding.

**This document does not cover**: the design rationale of tasks (see `02`–`08`), the justification
of phase order (see RFC-039).

**Registration convention (from 2026-10-12)**: newly registered level-2/level-3 entries **must carry
two fields**—"**Owning Phase**" (which P it truly belongs to, which may differ from the section it
appears in) and "**Whether it blocks the main line**"; `registered awaiting scheduling` is no longer
the default state, unmarked entries are considered **unschedulable**. Numbers **must be unique**
within the entire document (tasks across tracks use the track number, such as `029g.x`, and must not
occupy `N.x`). **Check-off/completion registration is based on "task id + evidence (gate value, run
id, issue number, file:line)"**, **not commit numbers**—`pull --rebase` rewrites local hashes,
hardcoded numbers will definitely fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Check commit
numbers via `git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules    08        ← Newly added, set rules first
P1  Revive orphan tests and fix defects                          06 §S1
P2  Establish equivalence oracle baseline                        07 all
P3  Fix correctness vulnerabilities (minimal solution)            02 §S3-vulnerability half
P4  Phase contract and unified Driver                            02
P5  Checker file-internal split                                  02 + supplemented by this document
P6  Type representation unification                              03
P7  Intermediate representation SSA-ification                    04      } can run in parallel
P8  Frontend paradigm change                                      05      }
P9  Anti-regression gates (with unified script list)             01 §Anti-regression + 08 §Machine-checkable rules
P10 Other cleanup and status correction                           06 §S2/S3/S4/S5/S6
```

**Reason for newly added P0**: The three prohibitions (no fabrication / no endless padding /
patching when refactoring is needed) constrain every action of P1–P10. Rules must be set before
construction begins, otherwise when P1 revives tests, `mod` declarations will already be added to
`tests/mod.rs`—which is exactly the cause of the G4 conflict.

## Key Decisions and Reasons

- **P0 independently as phase not merged into P9**—gate is "post-check", rules are "pre-judgment".
  P9's scripts cannot prevent "should refactor but patched", only D0–D4 review checklist can.
- **P9 as only authoritative list of CI scripts**—original gap G3's three coexisting lists led to
  inability to close. After this table merges 11 scripts each attribute to one phase, report-only
  and transition to hard timing explicit and queryable.
- **P3.5 incorporates RFC-029g not "independent track, wait until after refactoring"**—its deletion
  surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Waiting until after
  refactoring to execute equals doing same batch of deletion again on new grammar, new checker
  layout and new IR; this is same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC
  status correction.
- **P5's steps supplemented by this document not merged into P4**—P4 is already the largest single
  point risk, additionally overlaying checker split will exceed rollable granularity.
- **5.3.2 "zero caller change" as hard acceptance**—split must be independently revertable.
