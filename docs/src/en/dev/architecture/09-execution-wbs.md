# Multi-Level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactor](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates take RFC-039 itself as the sole authority; this document only
> breaks them down to executable granularity and records conflicts yet to be adjudicated.

## Position and Scope

| Level       | Count                                                                              | Meaning                                                                                                                                                                                                                                                                                                   |
| ----------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                                                        | Phases, one-to-one with RFC-039's phase sequence                                                                                                                                                                                                                                                          |
| **Level 2** | 57 (2026-10-13: 53 +2 = 3.13 / 3.14; 2026-10-14: +1 = 3.15; 2026-10-14: +1 = 3.16) | Task groups, from each document's "Implementation Points" + 2026-10-07 audit supplement (P3's 3.4) + 2026-10-10/11 adjudication additions (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery addition (P3's 3.11) + 2026-10-12 second discovery addition (P3's 3.12) |
| **Level 3** | 148 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1; 2026-10-14: +2 = 3.15.1 / 3.16.1)       | Independently committable actions                                                                                                                                                                                                                                                                         |

**This document covers**: task breakdown, dependency relations, parallel groupings, acceptance
criteria binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), justification of the
phase order (see RFC-039).

**Registration convention (since 2026-10-12)**: Newly registered level-2/level-3 rows **must carry
two fields**—「**Belonging Phase**」(the P they truly belong to, which may differ from the section
in which they sit) and 「**Whether It Blocks the Main Line**」; `registration pending scheduling` is
no longer the default state, an unlabeled row is treated as **not schedulable**. Numbering must be
**unique within the whole document** (cross-track tasks use the track number, such as `029g.x`, and
must not occupy `N.x`). **Check-off/completion registration is by "task id + evidence (gate
numerical values, run id, issue number, file:line)", not by commit number**—`pull --rebase` rewrites
local hashes, and hard-coded numbers will inevitably fail (2026-10-13 instance:
`94ad03ce4`→`631eb3e3c`). Look up commit numbers via `git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement regulations     08        ← Newly added, establish rules first
P1  Revive orphan tests and fix defects         06 §S1
P2  Establish equivalence criterion baseline     07 entire
P3  Fix correctness vulnerabilities (minimal scheme)  02 §S3-vulnerability half
P4  Stage contract and unified Driver          02
P5  checker in-file split          02 + this document fills in
P6  Unify type representation                 03
P7  Intermediate representation SSA-ification                04      } can run in parallel
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gates (incl. unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Remaining cleanup and state correction     06 §S2/S3/S4/S5/S6
```

**Reason for newly added P0**: The three prohibitions (must not fabricate / must not endlessly fill
/ refactor-worthy but instead patched) constrain every action of P1–P10. The rules must be
established before construction starts, otherwise when P1 revives tests, it will already be adding
`mod` declarations to `tests/mod.rs`—which is exactly the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 independent phase rather than merged into P9**—gates are "post-hoc check", regulations are
  "pre-judgment". P9's scripts cannot prevent "refactor-worthy but patched", only D0–D4's review
  checklist can.
- **P9 as sole authority list of CI scripts**—original gap G3's three coexisting lists made closure
  impossible. After this table merges, 10 scripts each belong to one phase, report-only and
  hard-flip timing explicit and queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"**—its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving to
  post-refactor execution equals doing the same batch of deletions on new grammar, new checker
  layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating
  RFC state correction.
- **P5's steps filled in by this document rather than merged into P4**—P4 is already the largest
  single-point risk, additionally stacking checker split would exceed rollable granularity.
- **5.3.2 with "zero caller change" as hard acceptance**—split must be independently revertable.
