# Multi-Level Implementation Task Breakdown (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC's phase sequence into **three levels of tasks that can be committed and verified
> independently**.
>
> The phase sequence and acceptance gates in the body of RFC-039 are the sole authority. This
> document is responsible only for decomposing the work into executable granularity and recording
> conflicts that remain undecided.

**Reserved numbers (not reused)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three has
had a corresponding entry since the WBS was established—the full history of this document has zero
matches for the `**4.7` / `**4.8` / `**8.1` headings
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and there
are no repository-wide references. `8.1` corresponds precisely to phase 1 of `05` (test revival and
completion). That phase was split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering is aligned with
its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and binding
tasks to acceptance criteria.

**Not covered by this document**: the rationale for task design (see `02`–`08`) or the argument for
phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered Level-2/Level-3 entries **must
contain two fields**—"**Owning phase**" (the P phase to which the task actually belongs, which may
differ from the containing section)—and "**Blocks main line**". `Registered, awaiting scheduling` is
no longer the default; an unmarked entry is considered **not schedulable**. Numbers must be **unique
throughout the document** (cross-track tasks use their track number, such as `029g.x`, and must not
occupy `N.x`). **Check-off/completion records are based on "task id + evidence (gate metric, run id,
issue number, file:line)", not commit numbers**—`pull --rebase` rewrites local hashes, so hard-coded
numbers inevitably become invalid (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Use `git log` to
look up commit numbers.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions—no fabrication, no endless filling, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before work begins; otherwise, when P1 revives tests, it will already be adding `mod` declarations
to `tests/mod.rs`, which is precisely the source of the G4 conflict.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 stop-the-bleeding path (2026-10-05 adjudication)**: P3's prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in
> parallel with P3. Stop-the-bleeding work on correctness vulnerabilities is not blocked by
> criterion-infrastructure construction; however, **P4 must still wait for all of P2**—the unified
> Driver requires all three layers of criteria to be in place.

| Constraint                | Reason                                                                                                                                                                                                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1                   | The three prohibitions constrain every action in P1 (1.2.x is precisely the act of adding `mod` declarations to `mod.rs`)                                                                                                                                                                               |
| P1 → P2                   | Reviving tests changes the test count and the corpus baseline                                                                                                                                                                                                                                           |
| P2 (after narrowing) → P3 | The vulnerability criteria must be **written red first** (2.4.1/2.4.3), and the multi-file corpus layer (2.3.2) must exist so that the red tests have somewhere to run                                                                                                                                  |
| P3 → P4                   | Fix bugs before refactoring; reversing the order lets the stage table harden bugs into "established behavior"                                                                                                                                                                                           |
| P3.5 → P4                 | RFC-029g (#399)'s deletion surface covers the rewrite targets of P4 4.2.2 / P5 / P6 / P7 / P8 respectively (the list appears in §P3.5 of this document)—reversing the order means performing the same deletions again on the new grammar, new checker layout, and new IR (D56)                          |
| P4 → P5                   | The `include!` refactoring and checker decomposition modify the same file                                                                                                                                                                                                                               |
| P5 → P6                   | Consecutive changes to the same file must be separate, otherwise a regression cannot be bisected                                                                                                                                                                                                        |
| P6 → P7 / P8              | If type representations do not converge first, the new IR will grow into a third representation; P7's gate for the #529 implementation line is 6.9.1–6.9.4, while 6.9.5 does not block it, but P7 may only consume the quantity-derived views and defeq interface and must not create a parallel ledger |

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—gates are "post-hoc checks", while rules are
  "pre-hoc judgment". P9's scripts cannot prevent "patching when a refactor is required"; only the
  D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the original G3 gap's three coexisting lists
  made closure impossible. This table merges them into 11 scripts, each owned by one phase, with
  report-only status and hard-conversion timing made explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an "independent track to execute after the
  refactoring"**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactoring means repeating the same deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as incorporating 7e's
  `2315`/`2341` and S4's incorporation of RFC status corrections.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker decomposition would exceed a revertible granularity.
- **5.3.2 uses "zero call-site changes" as hard acceptance**—the decomposition must be independently
  revertible.

  should not be rolled back" and lacks a requirement to record what was fixed. **Execution
  convention**: every 1.3.x fix's commit message must reference the repaired test name and defect
  description, providing after-the-fact bisect evidence.

  7b.1a / 7b.1b, per DoD 6.
