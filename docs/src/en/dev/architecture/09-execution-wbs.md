# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC's stage sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The stage order and acceptance gates defined in the body of RFC-039 are the sole authority. This
> document is responsible only for decomposing the work to an executable granularity and recording
> conflicts that have not yet been adjudicated.

has had a corresponding entry since the WBS was established—the entire history of this document has
zero matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used for verification),
and there are no repository-wide references. `8.1` corresponds precisely to stage 1 of `05` (test
revival and completion): that stage was split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering is
aligned with its stage numbers (stage 0 → `8.0`, stage 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and binding
acceptance criteria.

**Not covered by this document**: the design rationale for the tasks (see `02`–`08`) or the
rationale for the stage order (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered level-2/level-3 rows **must
contain two fields**—“**Owning stage**” (the P stage to which the task actually belongs, which may
differ from the current section) and “**Blocks the mainline**”; `registered, awaiting scheduling` is
no longer the default state, and an unmarked task is considered **not schedulable**. Numbers **must
be unique across the entire document** (cross-track tasks use a track number such as `029g.x` and
must not occupy `N.x`). **Checkoff/completion registration is based on “task id + evidence (gate
metrics, run id, issue number, file:line)” and does not record commit hashes**—`pull --rebase`
rewrites local hashes, so hard-coded hashes inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to look up commit hashes.

## Target Design: Stage Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (do not invent constructs / do not fill
endlessly / do not patch when a refactor is required) constrain every action in P1–P10. The rules
must be established before work starts; otherwise, while reviving tests in P1, work would already be
adding `mod` declarations to `tests/mod.rs`—precisely the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 is a separate stage rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-work judgment.” P9's scripts cannot prevent “patching when a refactor is required”; only the
  D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the original gap G3's three coexisting lists
  prevented closure. This table merges them, with 11 scripts each owned by one stage and explicit
  report-only and hard-conversion points.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surfaces (RFC-039 D56).
  Deferring it until after the refactor would mean repeating the same batch of deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341`
  into 7e and incorporating RFC status corrections into S4.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertible.
