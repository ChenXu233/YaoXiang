# Multi-level Construction Task List (WBS)

> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding RFC's phase sequence into **independently submittable, independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates use RFC-039 as the sole authority; this document only breaks
> down to executable granularity and registers any unresolved conflicts.

| **Level 3** | 144         | Independently committable actions                                                                                                                                                                                                                                                                                                |

**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), justification for
phase ordering (see RFC-039).

**Registration Convention (from 2026-10-12)**: Newly registered Level 2/3 rows **must include two
fields**——"**Owning Phase**" (which P it truly belongs to, may differ from the section it sits in)
and "**Whether It Blocks the Mainline**"; `registered-pending-scheduling` is no longer the default
state, unmarked rows are considered **unschedulable**. Numbering **must be unique** across the
entire document (cross-track tasks use track numbers, e.g. `029g.x`, not occupying `N.x`).

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← Newly added, rules first
P1  Resurrect orphan tests and fix defects           06 §S1
P2  Build equivalence oracle baseline             07 all
P3  Fix correctness vulnerabilities (minimum solution)        02 §S3-vulnerability half
P4  Stage contract and unified Driver          02
P5  checker file-internal split             02 + this document's fill-in
P6  Type representation unification                 03
P7  Intermediate representation SSA-ification                04      } Can run in parallel
P8  Frontend paradigm change                   05      }
P9  Anti-regression gates (incl. unified script list)     01 §Anti-regression + 08 §Machine-checkable rules
P10 Remaining cleanup and status correction             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions (no fabrication / no endless padding / should
refactor but applied a patch) constrain every action in P1–P10. Rules must be established before
work begins, otherwise when P1 resurrects tests it will already be adding `mod` declarations to
`tests/mod.rs`——which is exactly what caused conflict G4.

## Key Decisions and Rationale

- **P0 independent phase rather than merged into P9**——gates are "post-hoc checks", rules are
  "pre-judgment". P9's scripts cannot prevent "should refactor but applied a patch", only D0–D4's
  review checklist can.
- **P9 as the sole authoritative list of CI scripts**——the three coexisting lists of original gap G3
  led to inability to close. After this table merges, 10 scripts each own one phase, report-only and
  hardening timing explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after
  refactoring"**——its deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56).
  Leaving for after refactoring execution equals redoing the same batch of deletions on new grammar,
  new checker layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4
  incorporating RFC status correction.
- **P5's steps filled in by this document rather than merged into P4**——P4 is already the largest
  single-point risk, additionally overlaying checker split will exceed rollback granularity.
- **5.3.2 uses "zero caller change" as hard acceptance**——split must be independently revertable.
