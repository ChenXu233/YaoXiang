# Multi-level Construction Task Table (WBS)

> **Ancillary Design Document**. This document is an annex to
> [RFC-039 Compiler Architecture Refactor](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's stage sequence into a **three-level task structure that can be independently
> committed and verified**.
>
> The stage order and acceptance gates are governed exclusively by RFC-039 body text; this document
> only decomposes tasks to an executable granularity and records unresolved conflicts.

**Numbering gaps (not reused)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. None of these three has had
a corresponding entry since the WBS was established—this document has zero hits for `**4.7` /
`**4.8` / `**8.1` headings in its full history (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), nor are they referenced
anywhere in the repository. `8.1` corresponds exactly to stage 1 of `05` (test revival and
completion): that stage has been split into P1 (`1.1`–`1.3`) and `8.8`, so the P8 numbering aligns
with its stage number (stage 0 → `8.0`, stage 2 → `8.2`, and so on).

**This document covers**: task decomposition, dependency relationships, parallel grouping, binding
to acceptance criteria.

**This document does not cover**: the design rationale for tasks (see `02`–`08`), the justification
of the stage order (see RFC-039).

**Registration convention (effective 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields**—"**Belonging Stage**" (which P it actually belongs to, which may differ from the section it
appears in) and "**Whether It Blocks the Main Line**"; `registration pending scheduling` is no
longer the default state; unmarked items are treated as **not schedulable**. Numbers must be
**unique within the entire document** (for cross-track tasks, use the track number, e.g., `029g.x`,
and do not occupy `N.x`). **Check-off/completion registration is based on "task id + evidence (gate
values, run id, issue number, file:line)", not commit hashes**—`pull --rebase` rewrites local
hashes, and hard-coded numbers will inevitably fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`).
To check commit hashes, use `git log`.

## Target Design: Stage Sequence

```
P0  Repository maintenance mechanism and code placement regulations     08        ← New, rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence oracle baseline          07 all
P3  Fix correctness vulnerabilities (minimal solution)        02 §S3-Vulnerability half
P4  Stage contract and unified Driver          02
P5  checker file-internal split             02 + supplemented by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ization                04      } Can run in parallel
P8  Frontend paradigm change                   05      }
P9  Anti-regression gates (including unified script list)     01 §Anti-regression + 08 §Machine-checkable rules
P10 Other cleanup and status corrections             06 §S2/S3/S4/S5/S6
```

**Rationale for the new P0**: The three prohibitions (no fabrication / no endless padding / patch
instead of refactor) constrain every action in P1–P10. Rules must be established before construction
begins; otherwise when P1 revives tests, it will already be adding `mod` declarations to
`tests/mod.rs`—which is exactly the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 as independent stage not merged into P9**——gates are "post-hoc check", regulations are
  "pre-judgment". P9's scripts cannot prevent "patch instead of refactor", only D0–D4's review
  checklist can.
- **P9 as the only authoritative list of CI scripts**——original gap G3's three parallel lists made
  closure impossible. After this table merges, 11 scripts each belong to one stage, report-only and
  convert-to-hard timing explicit and queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"**——its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor means redoing the same batch of deletion on new grammar, new checker layout and new IR;
  this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status correction.
- **P5's steps are supplemented in this document rather than merged into P4**——P4 is already the
  largest single-point risk, adding checker split would exceed rollable granularity.
- **5.3.2 takes "zero caller change" as hard acceptance**——split must be independently revertable.
