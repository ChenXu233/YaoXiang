# Multi-Level Construction Task Table (WBS)

> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's stage sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The stage order and acceptance gates take the body of RFC-039 as the sole authority; this document
> only handles the breakdown to executable granularity, and registers conflicts not yet adjudicated.

**This document covers**: task breakdown, dependencies, parallel grouping, and acceptance criterion
binding.

**This document does not cover**: the design rationale of tasks (see `02`–`08`), the justification
of stage order (see RFC-039).

**Registration convention (effective 2026-10-12)**: Newly registered level 2/3 entries **must carry
two fields** — "**Owning phase**" (which P it truly belongs to; may differ from the section it sits
in) and "**Whether it blocks the mainline**"; `registered-pending-scheduling` is no longer a default
state, and any entry without an explicit marking is treated as **not schedulable**. Numbers **must
be unique across the entire document** (cross-track tasks use the track number, e.g. `029g.x`, and
must not occupy `N.x`). **Checkmark / completion registration follows "task id + evidence (gate
metric, run id, issue number, file:line)"**, never a commit hash — `pull --rebase` rewrites local
hashes, and a hard-coded one will inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Look up commit hashes via `git log`.

## Goal Design: Stage Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← New, set rules first
P1  Resurrect orphan tests and fix defects           06 §S1
P2  Establish equivalence criterion baseline         07 all
P3  Fix correctness vulnerabilities (minimal plan)    02 §S3 - vulnerability half
P4  Stage contract and unified Driver                02
P5  Checker file-internal split                       02 + filled in by this document
P6  Type representation unification                   03
P7  Intermediate representation SSA-ification         04      } Parallelizable
P8  Frontend paradigm change                          05      }
P9  Anti-rebound gates (incl. unified script list)    01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status corrections             06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (must not fabricate / must not endlessly fill /
must refactor instead of patching) constrain every action in P1–P10. Rules must be set before
construction begins, otherwise P1's test resurrection would already be adding `mod` declarations to
`tests/mod.rs` — which is exactly what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 stands as an independent stage instead of being merged into P9** — gates are "post-hoc
  checks", rules are "pre-judgment". P9's scripts cannot prevent "should have refactored but patched
  instead", only the D0–D4 review checklist can.
- **P9 as the sole authoritative list of CI scripts** — the original gap G3's triple-coexisting
  lists prevented closure. After merging, 10 scripts each belong to one stage, report-only and
  hard-conversion timing is explicitly traceable.
- **P3.5 incorporates RFC-029g instead of leaving it as "independent track, do after refactor"** —
  its deletion surface overlaps the rewrite surface of P4/P5/P6/P7/P8 (RFC-039 D56). Leaving it for
  after the refactor equals redoing the same batch of deletions on the new grammar, new checker
  layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341` and S4 incorporating
  RFC status correction.
- **P5's steps are filled in by this document instead of being merged into P4** — P4 is already the
  largest single-point risk, stacking the checker split on top would exceed the rollback
  granularity.
- **5.3.2 takes "zero caller-side change" as hard acceptance** — the split must be independently
  revertible.
