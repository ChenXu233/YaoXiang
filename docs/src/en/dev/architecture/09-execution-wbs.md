# Multi-Level Work Breakdown Structure (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence in the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> Phase order and acceptance gates take the RFC-039 main text as the sole authority; this document
> is only responsible for breaking down to executable granularity and registering undecided
> conflicts.

## Positioning and Scope

| Level       | Count                                                                              | Meaning                                                                                                                                                                                                                                                                                            |
| ----------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                                                        | Phases, one-to-one correspondence with RFC-039's phase sequence                                                                                                                                                                                                                                    |
| **Level 2** | 57 (2026-10-13: 53 +2 = 3.13 / 3.14; 2026-10-14: +1 = 3.15; 2026-10-14: +1 = 3.16) | Task groups, from each document's "Implementation Points" + 2026-10-07 audit addendum (P3's 3.4) + 2026-10-10/11 ruling supplement (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery supplement (P3's 3.11) + 2026-10-12 discovery re-supplement (P3's 3.12) |
| **Level 3** | 148 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1; 2026-10-14: +2 = 3.15.1 / 3.16.1)       | Independently committable actions                                                                                                                                                                                                                                                                  |

**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: task design rationale (see `02`–`08`), phase order justification
(see RFC-039).

**Registration convention (from 2026-10-12)**: newly registered level 2/3 rows **must include two
fields** — "**Owning phase**" (which P it truly belongs to, may differ from the section) and
"**Whether it blocks the mainline**"; `registered pending scheduling` is no longer the default
state, unmarked is treated as **not schedulable**. Numbering must be **unique across the entire
document** (cross-track tasks use track numbers, such as `029g.x`, must not occupy `N.x`).
**Check-off/completion registration uses "task id + evidence (gate value, run id, issue number,
file:line)" as the standard, do not write commit hashes** — `pull --rebase` rewrites local hashes,
hard-coded numbers will fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Check commit numbers via
`git log`.

## Goal Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement regulations   08        ← new, rules first
P1  Resurrect orphan tests and fix defects                           06 §S1
P2  Build equivalence criterion baseline                             07 entire
P3  Fix correctness bugs (minimal scheme)                            02 §S3-vulnerability half
P4  Phase contract and unified Driver                                02
P5  Checker in-file split                                             02 + this document supplement
P6  Type representation unification                                  03
P7  Intermediate representation SSA-ization                          04      } parallelizable
P8  Frontend paradigm change                                          05      }
P9  Anti-rebound gates (including unified script list)                01 §Anti-rebound + 08 §machine-checkable rules
P10 Other cleanup and status corrections                              06 §S2/S3/S4/S5/S6
```

**Reason for newly added P0**: three prohibitions (must not fabricate / must not endlessly pad /
should refactor but applied a patch) constrain every action in P1–P10. Rules must be established
before construction begins, otherwise P1's test resurrection will already be adding `mod`
declarations to `tests/mod.rs` — which is exactly what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 independent as phase rather than merging into P9** — gate is "post-check", regulation is
  "pre-judgment". P9's scripts cannot prevent "should refactor but applied patch", only D0–D4's
  review checklist can.
- **P9 as CI script's sole authoritative list** — original gap G3's three coexisting lists led to
  inability to close. After this table merges 10 scripts each assigned to one phase, report-only and
  convert-to-hard timing explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, wait for refactor"** — its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor execution equals redo the same batch of deletion on new grammar, new checker layout and
  new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status
  correction.
- **P5's steps filled in by this document rather than merging into P4** — P4 is already the largest
  single-point risk, stacking checker split will exceed rollback granularity.
- **5.3.2 with "zero caller changes" as hard acceptance** — split must be independently revertable.
