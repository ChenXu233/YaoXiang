# Multi-Level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates are governed solely by the body of RFC-039; this document
> only handles the breakdown to an executable granularity and registers conflicts not yet
> adjudicated.

## Positioning and Scope

| Level       | Quantity                                                                           | Meaning                                                                                                                                                                                                                                                                                                                      |
| ----------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                                                        | Phases, corresponding one-to-one with the phase sequence in RFC-039                                                                                                                                                                                                                                                          |
| **Level 2** | 57 (2026-10-13: 53 +2 = 3.13 / 3.14; 2026-10-14: +1 = 3.15; 2026-10-14: +1 = 3.16) | Task groups, from "Implementation Points" sections of various documents + 2026-10-07 audit addendum (P3's 3.4) + 2026-10-10/11 adjudication registration (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery registration (P3's 3.11) + 2026-10-12 discovery re-registration (P3's 3.12) |
| **Level 3** | 148 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1; 2026-10-14: +2 = 3.15.1 / 3.16.1)       | Independently committable actions                                                                                                                                                                                                                                                                                            |

**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), justification for
phase ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields**—"**Owning Phase**" (which P it truly belongs to; may differ from the section it appears in)
and "**Whether it blocks the mainline**"; `Registered, awaiting scheduling` is no longer the default
state, and unmarked items are treated as **not schedulable**. Numbers **must be unique** across the
entire document (cross-track tasks use the track number, e.g. `029g.x`, and must not occupy `N.x`).
**Checkmark / completion registration is based on "task id + evidence (gate value, run id, issue
number, file:line)"—do not write commit numbers**—`pull --rebase` rewrites local hashes, hard-coded
numbers will become invalid (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). For commit numbers, check
`git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← Newly added, establish rules first
P1  Resurrect orphan tests and fix defects           06 §S1
P2  Establish equivalence criterion baseline             07 all
P3  Fix correctness vulnerabilities (minimal solution)        02 §S3-vulnerability half
P4  Stage contract and unified Driver          02
P5  checker file-internal splitting             02 + filled in by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ification                04      } Parallelizable
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gates (including unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Miscellaneous cleanup and state correction             06 §S2/S3/S4/S5/S6
```

**Rationale for the newly added P0**: The three prohibitions (no fabrication / no endless filler /
patches instead of required refactoring) constrain every action in P1–P10. Rules must be established
before construction begins; otherwise during P1's test resurrection, people are already adding `mod`
declarations to `tests/mod.rs`—which is exactly the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 as independent stage rather than merged into P9**—gates are "post-hoc checks", rules are
  "pre-judgment". P9's scripts cannot prevent "patching instead of required refactoring", only
  D0–D4's review list can.
- **P9 as sole authoritative list of CI scripts**—original gap G3's three coexisting lists made
  closure impossible. After this table merges, 10 scripts each attributed to one stage, report-only
  and harden timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"**—its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor means doing the same batch of deletion on new grammar, new checker layout, and new IR;
  this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC state correction.
- **P5's steps filled in by this document rather than merged into P4**—P4 is already the largest
  single-point risk, adding checker splitting would exceed revertable granularity.
- **5.3.2 with "zero call site changes" as hard acceptance**—splitting must be independently
  revertable.
