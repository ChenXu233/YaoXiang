# Multi-Level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's stage sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The stage order and acceptance gates are authoritative only in the body of RFC-039; this document
> is responsible solely for breaking down to executable granularity and registering conflicts that
> have not yet been adjudicated.

## Positioning and Scope

| Level       | Count       | Meaning                                                                                                                                                                             |
| ----------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Stages, corresponding one-to-one with the stage sequence in RFC-039                                                                                                                 |
| **Level 2** | 50          | Task groups, drawn from each document's "Implementation Essentials" + 2026-10-07 audit additions (3.4 in P3) + 2026-10-10/11 adjudication registrations (3.5/3.6/3.7/3.8/3.9 in P3) |

**This document covers**: task breakdown, dependencies, parallel groupings, and acceptance criterion
binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), argumentation for
stage ordering (see RFC-039).

## Target Design: Stage Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← new addition, set rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence criterion baseline             07 entire
P3  Fix correctness vulnerabilities (minimal plan)        02 §S3 vulnerability half
P4  Stage contract and unified Driver          02
P5  checker file internal split             02 + filled in by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ification                04      } parallel
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gates (including unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status correction             06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (no fabrication / no endless filling / patched
instead of refactored) constrain every action from P1–P10. Rules must be established before
construction begins; otherwise when P1 revives tests, additions to `mod` declarations in
`tests/mod.rs` would already be in progress — precisely the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 independent as stage rather than merged into P9** — gates are "post-hoc check", rules are
  "pre-judgment". P9's scripts cannot prevent "patched instead of refactored", only D0–D4's review
  list can.
- **P9 as sole authoritative list for CI scripts** — original gap G3's three coexisting lists led to
  inability to close. After this table's merge, 10 scripts each attributed to one stage, report-only
  and hard-turn timing explicit and traceable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"** — its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor means redoing same batch of deletions on new grammar, new checker layout and new IR; same
  lesson as 7e absorbing `2315`/`2341`, S4 absorbing RFC status corrections.
- **P5's steps filled in by this document rather than merged into P4** — P4 is already the largest
  single-point risk, layering checker split would exceed rollback granularity.
- **5.3.2 takes "zero caller change" as hard acceptance** — split must be independently revertible.
