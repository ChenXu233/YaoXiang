# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's phase sequence into **three levels of tasks that can be committed and verified
> independently**.
>
> RFC-039's body is the sole authority for phase order and acceptance gates. This document is
> responsible only for decomposing the work into an executable granularity and recording conflicts
> whose adjudication is still pending.

**Unallocated numbers (not recycled)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of these
three numbers has ever had a corresponding entry since the WBS was established: this document's
entire history has zero matches for the `**4.7` / `**4.8` / `**8.1` headings
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and the
repository contains no references to them either. `8.1` corresponds precisely to phase 1 of `05`
(test revival and completion). That phase has already been split into P1 (`1.1`–`1.3`) and `8.8`, so
P8's numbering is aligned with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**Covered here**: Task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: The design rationale for the tasks (see `02`–`08`) or the rationale for phase
order (see RFC-039).

**Registration convention (effective 2026-10-12)**: Every newly registered Level-2/Level-3 row
**must contain two fields**—**"Owning Phase"** (the P to which it truly belongs, which may differ
from its current section) and **"Blocks the Mainline"**. `Awaiting Scheduling` is no longer the
default state; an unmarked task is considered **not schedulable**. Numbers **must be unique
throughout the document** (tasks on different tracks use their track number, such as `029g.x`, and
must not occupy `N.x`). **Check-off/completion registration is based on "task ID + evidence (gate
values, run ID, issue number, file:line)," not commit hashes**—`pull --rebase` rewrites local
hashes, so a hard-coded hash will inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit hashes.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions (no fabrication / no endless filling / no
patching when a refactor is required) constrain every action in P1–P10. The rules must be
established before work begins; otherwise, when P1 revives tests, it will already be adding `mod`
declarations to `tests/mod.rs`—which is precisely the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are "post-hoc checks," while rules are
  "pre-hoc judgment." P9's scripts cannot prevent "patching when a refactor was required"; only the
  D0–D4 review checklist can.
- **P9 is the sole authoritative inventory of CI scripts**—the original gap G3's 3 coexisting
  inventories made closure impossible. This table merges them, assigns all 11 scripts to one phase
  each, and makes report-only status and conversion timing explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an "independent track to execute after the
  refactor"**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactor means redoing the same deletions on the new grammar,
  new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  correcting RFC status under S4.
- **P5's steps are supplied here rather than merged into P4**—P4 is already the largest single-point
  risk, and adding the checker split would exceed the granularity at which changes can be rolled
  back.
- **5.3.2 uses "zero caller changes" as its hard acceptance criterion**—the split must be
  independently revertable.
