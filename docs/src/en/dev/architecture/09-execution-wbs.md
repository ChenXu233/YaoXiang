# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document expands the phase sequence in
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) into
> **three levels of tasks that can be committed and verified independently**.
>
> RFC-039 is the sole authority for phase order and acceptance gates; this document only decomposes
> the work into an executable granularity and records conflicts that remain undecided.

has had a corresponding entry since the WBS was established: the history of this document has zero
hits for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and the
repository contains no references to them either. `8.1` corresponds exactly to phase 1 of `05` (test
revival and completion). That phase was split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbers align
with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**Covered here**: Task decomposition, dependencies, parallel groups, and binding of acceptance
criteria.

**Not covered here**: The design rationale for tasks (see `02`–`08`) or the rationale for phase
order (see RFC-039).

**Registration convention (effective 2026-10-12)**: Newly registered Level 2/3 rows **must contain
two fields**: “**Owning phase**” (the P phase to which the task truly belongs, which may differ from
the section containing it) and “**Blocks the mainline**”. `Registered, awaiting scheduling` is no
longer the default state; an unmarked task is deemed **not schedulable**. Numbers must be **unique
throughout the document** (cross-track tasks use their track number, such as `029g.x`, and must not
occupy `N.x`). **Check-off/completion registration is based on “task ID + evidence (gate metrics,
run ID, issue number, file:line)” and does not record commit hashes**—`pull --rebase` rewrites local
hashes, so hard-coded hashes inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit hashes.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions—no fabrication, no endless padding, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before work starts; otherwise, while P1 revives tests, it is already adding `mod` declarations to
`tests/mod.rs`, which is precisely the cause of the G4 conflict.

implementation not started), [#399](https://github.com/ChenXu233/YaoXiang/issues/399). **This track
is not a design item of the refactor itself; it is a specification-compliance deletion forced by an
ordering constraint.** It is distinct from P10 S5 “reduce the visibility of `pub` items” (narrowing
Rust's `pub(crate)`).

**Why it must be completed before P4**: RFC-029g's deletion surface overlaps the rewritten surfaces
of four refactor phases. Reversing the order means repeating the same deletions and baseline updates
on the new grammar / new checker layout / new SSA IR.

**Acceptance (behavior changes, red criteria first)**:

1. **Red-then-green**: each of the two behavior changes must first have a red criterion before code
   is changed—① `pub` changes from “silently accepted” to a parse error; ② unreferenced top-level
   bindings in Lib/Script roles newly report W1001 (pub items used to be absolutely exempt).
2. **The test count must not decrease**: when deleting the `exempt_pub` cases in
   `typecheck/passes/tests/dead_code.rs` and the `is_pub` fixtures, equivalent new cases must
   replace them.
3. **Baseline in the same commit**: diagnostic-set changes (new parse errors + new W1001) ⇒ update
   the corpus differential baseline (`tests/baselines/corpus-parity.jsonl`) and CHANGELOG in the
   same commit; the IR snapshot is expected to have zero diff, and any nonzero difference requires
   an explanation.
4. **Independent revert unit**: the entire batch occupies one commit group and must not be mixed
   with other phases (DoD 6).
5. `cargo test` / `clippy -D warnings` / `python scripts/rfc/check_tracking.py` all green.

**Ordering**: Overlaps with 3.4 files (`checker.rs`, `environment.rs`) ⇒ the two must be serialized
and cannot run in parallel; **the whole track precedes P4** (RFC-039 D56). RFC-029g does not depend
on 3.4; the implementer chooses the order based on available context.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “after-the-fact checks,” while
  rules are “before-the-fact judgment.” P9's scripts cannot prevent “patching when a refactor was
  required”; only the D0–D4 review checklist can.
- **P9 is the sole authoritative CI script list**—the original gap G3's three coexisting lists made
  closure impossible. This table merges them into 11 scripts, each owned by one phase, with
  report-only status and hardening points made explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps the rewritten surfaces of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactor means repeating the same deletions on the new grammar, new
  checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  correcting RFC status in S4.
- **P5's steps are supplied here rather than folded into P4**—P4 is already the largest single-point
  risk, and adding the checker split would exceed a revertible granularity.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertible.
