# Multi-Level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence of the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> Phase order and acceptance gates are solely authoritative in the RFC-039 body; this document only
> handles the decomposition to executable granularity, and registers conflicts not yet resolved.

## Positioning and Scope

| Level       | Count                                      | Meaning                                                                                                                                                                                                                                                                                                  |
| ----------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                | Phases, in one-to-one correspondence with the phase sequence of RFC-039                                                                                                                                                                                                                                  |
| **Level 2** | 55 (2026-10-13: 53 +2 = 3.13 / 3.14)       | Task groups, from the "Implementation Essentials" of each document + 2026-10-07 audit supplement (P3's 3.4) + 2026-10-10/11 ruling additions (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery addition (P3's 3.11) + 2026-10-12 discovery re-addition (P3's 3.12) |
| **Level 3** | 146 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1) | Actions that can be independently committed                                                                                                                                                                                                                                                              |

**This document covers**: task decomposition, dependencies, parallel grouping, and acceptance
criterion binding.

**This document does not cover**: the design rationale for tasks (see `02`–`08`), or the
justification of the phase order (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered level-2/level-3 rows **must
carry two fields**—「**Owning Phase**」(which P it truly belongs to, may differ from the containing
section) and 「**Whether it blocks the main line**」; `registered, awaiting scheduling` is no longer
the default state, an unmarked row is considered **unschedulable**. Numbers must be **unique within
the entire document** (tasks across tracks use the track number, such as `029g.x`, must not occupy
`N.x`). **Checkmark/completion registration is based on「task id + evidence (gate value, run id,
issue number, file:line)」**, do not write commit numbers — `pull --rebase` will rewrite local
hashes, hardcoded numbers will inevitably fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Check
`git log` for commit numbers.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules  08        ← New, rules first
P1  Resurrect orphan tests and fix defects                      06 §S1
P2  Establish equivalence criterion baseline                    07 entire
P3  Fix correctness vulnerabilities (minimum solution)           02 §S3-vulnerability half
P4  Phase contract and unified Driver                           02
P5  checker in-file split                                       02 + completed by this document
P6  Type representation unification                             03
P7  Intermediate representation SSA-ization                     04      } Parallelizable
P8  Frontend paradigm change                                    05      }
P9  Anti-rebound gates (including unified script list)          01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and state corrections                         06 §S2/S3/S4/S5/S6
```

**Reason for the newly added P0**: The three prohibitions (must not fabricate / must not endlessly
fill / should refactor but patched instead) constrain every action of P1–P10. Rules must be
established before construction begins, otherwise when P1 resurrects tests it's already adding `mod`
declarations to `tests/mod.rs` — which is exactly the cause of the G4 conflict.

## Key Decisions and Reasons

- **P0 independent as phase rather than merged into P9** — gate is "post-check", rules are
  "pre-judgment". P9's script cannot prevent "should refactor but patched instead", only D0–D4's
  review checklist can.
- **P9 as the only authoritative list of CI scripts** — original gap G3's three coexisting lists
  made closure impossible. After this table merge, 10 scripts each own one phase, report-only and
  harden timing explicit and checkable.
- **P3.5 consolidates RFC-029g rather than leaving as "independent track, wait for after refactor"**
  — its deletion face overlaps with P4/P5/P6/P7/P8's rewrite face (RFC-039 D56). Leaving for after
  refactor equals doing the same batch of deletion on new grammar, new checker layout and new IR;
  this is the same lesson as 7e collecting `2315`/`2341`, S4 collecting RFC state corrections.
- **P5's steps are completed by this document rather than merged into P4** — P4 is already the
  largest single-point risk, adding checker split exceeds revertable granularity.
- **5.3.2 takes "zero caller change" as hard acceptance** — split must be independently revertable.
