# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document.** This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into **three-level tasks that can be committed and verified
> independently**.
>
> The phase order and acceptance gates are governed solely by the main text of RFC-039; this
> document is responsible only for decomposing the work to an executable granularity and recording
> conflicts that have not yet been adjudicated.

three has had a corresponding entry since the WBS was established—the entire history of this
document has zero matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and there
are no repository-wide references. `8.1` corresponds precisely to phase 1 of `05` (test revival and
completion): that phase has already been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering
remains aligned with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**Covered here**: Task decomposition, dependency relationships, parallelization groups, and binding
of acceptance criteria.

**Not covered here**: The design rationale for tasks (see `02`–`08`) or the rationale for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: Every newly registered level-2/level-3 row
**must contain two fields**—“**Owning phase**” (the P phase to which it truly belongs, which may
differ from its containing section) and “**Blocks the mainline**”; `登记待排期` is no longer the
default state, and an unmarked item is deemed **not schedulable**. Numbering must be **unique across
the entire document** (tasks in separate tracks use their track number, such as `029g.x`, and must
not occupy `N.x`). **Checkbox/completion registration is based on “task ID + evidence (gate values,
run ID, issue number, file:line),” not commit numbers**—`pull --rebase` rewrites local hashes, so
hard-coded commit numbers inevitably become invalid (2026-10-13 example: `94ad03ce4`→`631eb3e3c`).
Use `git log` to look up commit numbers.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions—no fabrication, no endless padding, and no
patching where a refactor is required—constrain every action in P1–P10. The rules must be
established before work begins; otherwise, while reviving tests in P1, work would already be adding
`mod` declarations to `tests/mod.rs`, which is precisely what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 is independent rather than merged into P9**—gates are “post-hoc checks,” while rules are
  “pre-hoc judgment.” P9's scripts cannot prevent “patching where a refactor was required”; only
  D0–D4's review checklist can.
- **P9 is the sole authoritative CI script inventory**—the three concurrent inventories from
  original gap G3 made closure impossible. This table merges them, assigning each of the 11 scripts
  to exactly one phase and making the report-only status and hard-failure transition points
  explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactor means repeating the same deletions on the new grammar,
  new checker layout, and new IR; this is the same lesson as 7e absorbing `2315`/`2341` and S4
  absorbing RFC status corrections.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the split must be independently
  revertable.
