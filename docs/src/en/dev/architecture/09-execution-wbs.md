# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Restructuring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's stage sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The stage order and acceptance gates are governed solely by the main body of RFC-039. This
> document is responsible only for decomposing the work into an executable granularity and recording
> conflicts that have not yet been adjudicated.

**Reserved numbers (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three
has had a corresponding entry since the WBS was established: throughout the history of this
document, the three headings `**4.7` / `**4.8` / `**8.1` have zero matches (this can be verified
with `git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the repository
contains no references to them. `8.1` corresponds precisely to stage 1 of `05` (test revival and
completion). That stage has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering aligns
with its stage numbers: stage 0 → `8.0`, stage 2 → `8.2`, and so forth.

**Covered by this document**: Task decomposition, dependencies, parallelization groups, and binding
of acceptance criteria.

**Not covered by this document**: The design rationale for tasks (see `02`–`08`) or the argument for
the stage order (see RFC-039).

**Registration convention (effective 2026-10-12)**: Every newly registered level-2/level-3 row
**must contain two fields**: "**Owning stage**" (the P stage to which it genuinely belongs, which
may differ from its section) and "**Blocks the mainline**". `Pending scheduling` is no longer the
default state; an unmarked task is considered **not schedulable**. Numbers must be **unique
throughout the document** (cross-track tasks use their track number, such as `029g.x`, and must not
occupy an `N.x` number). **Checkoff/completion records are based on "task ID + evidence (gate value,
run ID, issue number, file:line)" rather than commit numbers**—`pull --rebase` rewrites local
hashes, so hard-coded numbers inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit numbers.

## Target Design: Stage Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions—no fabrication, no endless padding, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before work begins; otherwise, reviving tests in P1 would already involve adding `mod` declarations
to `tests/mod.rs`, which is precisely the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 is an independent stage rather than part of P9**—gates are "post-hoc checks"; rules are
  "prior judgment". P9's scripts cannot prevent "patching when a refactor is required"; only the
  D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the 3 coexisting lists arising from original
  gap G3 prevented closure. After this table merges them, all 11 scripts have exactly one owning
  stage, and report-only status and the point of conversion to hard failures are explicit.
- **P3.5 adopts RFC-029g rather than leaving it as an "independent track to be performed after the
  refactor"**—its deletion surface overlaps the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactor means redoing the same deletions on the new grammar, new
  checker layout, and new IR; this is the same lesson as adopting `2315`/`2341` in 7e and the
  RFC-status corrections in S4.
- **P5's steps are supplemented by this document rather than folded into P4**—P4 is already the
  largest single-point risk, and adding checker splitting would exceed the granularity at which the
  work can be rolled back.
- **5.3.2 uses "zero caller changes" as its hard acceptance criterion**—the split must be
  independently revertible.
