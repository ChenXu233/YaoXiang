# Multi-level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the phase sequence from the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> Phase ordering and acceptance gates are uniquely authoritative in the RFC-039 main text; this
> document only decomposes to an executable granularity and records conflicts that have not yet been
> adjudicated.

## Position and Scope

| Level       | Quantity    | Meaning                                                                                                                                                                                                                                                                                                        |
| ----------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, one-to-one correspondence with the phase sequence in RFC-039                                                                                                                                                                                                                                           |
| **Level 2** | 53          | Task groups, from each document's "Implementation Points" + 2026-10-07 audit addendum (P3's 3.4) + 2026-10-10/11 adjudication supplements (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery supplement (P3's 3.11) + 2026-10-12 discovery further supplement (P3's 3.12) |
| **Level 3** | 144         | Independently committable actions                                                                                                                                                                                                                                                                              |

**This document covers**: Task decomposition, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: The design rationale for tasks (see `02`–`08`), or the argument
for phase ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields** — "**Belonging Phase**" (which P it truly belongs to, may differ from the current section)
and "**Whether It Blocks the Main Line**"; `registered-pending-scheduling` is no longer the default
state, and unmarked items are considered **not schedulable**. Numbering must be **unique within the
document** (tasks across tracks use the track number, e.g., `029g.x`, not allowed to occupy `N.x`).
**Check-off/completion registration is based on "task id + evidence (gate value, run id, issue
number, file:line)"**, do not write commit hashes — `pull --rebase` will rewrite local hashes,
hard-coded numbers will inevitably fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). To check
commit hashes, use `git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← Newly added, set rules first
P1  Resurrect orphan tests and fix defects           06 §S1
P2  Establish equivalence criterion baseline             07 all
P3  Fix correctness vulnerabilities (minimum solution)        02 §S3-vulnerability half
P4  Phase contract and unified Driver          02
P5  In-file checker split             02 + filled in by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ization                04      } Can be parallel
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gates (including unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status correction             06 §S2/S3/S4/S5/S6
```

**Reason for newly added P0**: The three prohibitions (no fabrication / no endless padding /
patching when refactoring is needed) constrain every action in P1–P10. Rules must be established
before work begins; otherwise when P1 resurrects tests, `mod` declarations will be added to
`tests/mod.rs` — which is exactly the cause of the G4 conflict.

## Key Decisions and Reasons

- **P0 independent as a phase rather than merged into P9** — Gates are "post-hoc checks", rules are
  "prior judgment". P9's scripts cannot prevent "patching when refactoring is needed", only D0–D4's
  review checklist can.
- **P9 as the only authoritative list of CI scripts** — The three coexisting lists from original gap
  G3 led to inability to close. After this table merges, 10 scripts each attributed to one phase,
  report-only and hardening timing explicitly checkable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactoring"** —
  Its deletion surface overlaps with P4/P5/P6/P7/P8's rewriting surface (RFC-039 D56). Leaving to be
  executed after refactoring equals redoing the same batch of deletions on new grammar, new checker
  layout and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC
  status correction.
- **P5's steps are filled in by this document rather than merged into P4** — P4 is already the
  largest single-point risk, adding checker split would exceed rollable granularity.
- **5.3.2 takes "zero caller change" as hard acceptance** — Split must be independently revertable.
