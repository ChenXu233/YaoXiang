# Multi-Level Construction Task Table (WBS)

> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039: Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence from the RFC into a **three-level task list that can be independently
> committed and independently verified**.
>
> The phase order and acceptance gates are governed by the body of RFC-039 as the sole authority;
> this document only breaks tasks down to an executable granularity and registers unresolved
> conflicts.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← New, establish rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence oracle baseline             07 All
P3  Fix correctness vulnerabilities (minimum scheme)        02 §S3-Vulnerability half
P4  Stage contract and unified Driver          02
P5  In-file checker split             02 + Filled by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ification                04      } Parallelizable
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gates (with unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status corrections             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: Three prohibitions (no invention / no endless padding / patch instead
of refactor) constrain every action in P1–P10. Rules must be established before work begins;
otherwise, when P1 revives tests, it would already be adding `mod` declarations to `tests/mod.rs` —
that is exactly what caused the G4 conflict.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 hemostatic channel (decision 2026-10-05)**: P3's prerequisite narrowed to **2.3.2 + 2.4.1 +
> 2.4.3** (multi-file corpus layer + two red oracles). Rest of P2 (2.1 IR verifier, 2.2 snapshot,
> 2.3.1/2.3.3 diff and performance baseline) can advance in parallel with P3. Hemostasis of
> correctness vulnerabilities is not blocked by oracle infrastructure construction; but **P4 must
> still wait for P2 to fully complete** — unified Driver needs all three layers of oracles in place.

| Constraint         | Reason                                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P0 → P1            | Three prohibitions constrain every action of P1 (1.2.x is exactly adding `mod` declarations to `mod.rs`)                                                                                                                                   |
| P1 → P2            | Reviving tests will change test count and corpus baseline                                                                                                                                                                                  |
| P2 (narrowed) → P3 | Vulnerability oracles must **first be written as red** (2.4.1/2.4.3) + multi-file corpus layer (2.3.2) exists, red tests have place to run                                                                                                 |
| P3 → P4            | Fix bugs before refactoring; reverse order will let bugs be固化 as "established behavior" by stage table                                                                                                                                   |
| P3.5 → P4          | RFC-029g (#399)'s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8 respective rewrite objects (list in §P3.5 of this document) — reverse order equals redoing same batch of deletions on new grammar, new checker layout, new IR (D56) |

## Key Decisions and Rationale

- **P0 is its own phase, not merged into P9** — gates are "post-hoc check", rules are
  "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as sole authoritative list of CI scripts** — the three coexisting lists in original gap G3
  made closure impossible. After this table merges, 10 scripts each attributed to one phase,
  report-only and conversion-to-hard timing explicit and queryable.
- **P3.5 incorporates RFC-029g instead of leaving as "independent track, do after refactor"** — its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor equals redoing the same batch of deletions on new grammar, new checker layout, and new
  IR; this is the same lesson as 7e incorporating `2315`/`2341` and S4 incorporating RFC status
  correction.
- **P5's steps filled by this document instead of merged into P4** — P4 is already the largest
  single-point risk, adding checker split on top exceeds rollback granularity.
- **5.3.2 uses "zero caller change" as hard acceptance** — split must be independently revertable.
