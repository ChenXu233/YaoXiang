# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Restructuring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC’s phase sequence into **three-level tasks that can be committed and verified
> independently**.
>
> The phase order and acceptance gates in the body of RFC-039 are the sole authority. This document
> is responsible only for decomposing the work into executable granularity and recording conflicts
> that have not yet been adjudicated.

**Reserved gaps (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three has
had a corresponding entry since the WBS was established—this document has never matched the three
headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and there
are no references elsewhere in the repository. `8.1` corresponds precisely to stage 1 of `05` (test
revival and completion): that stage was split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s numbering
aligns with its phase number (stage 0 → `8.0`, stage 2 → `8.2`, and so on).

**Covered here**: task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: the design rationale for the tasks (see `02`–`08`) or the justification for
phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered Level 2/Level 3 row
**must contain two fields**—“**Owning stage**” (the P to which it truly belongs, which may differ
from the chapter in which it appears) and “**Blocks the mainline**.” `Pending scheduling` is no
longer the default state; an unmarked item is considered **not schedulable**. Numbers must be
**unique throughout the document** (tasks on separate tracks use their track number, such as
`029g.x`, and must not occupy `N.x`). **Checkoff/completion records must use “task ID + evidence
(gate metrics, run ID, issue number, file:line),” not commit hashes**—`pull --rebase` rewrites local
hashes, so hard-coded hashes inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Look up commit hashes with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions—no fabrication, no endless filling, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before work begins; otherwise, reviving tests in P1 would already involve adding `mod` declarations
to `tests/mod.rs`, which is precisely what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-hoc judgments.” P9’s scripts cannot prevent “patching when a refactor is required”; only the
  D0–D4 review checklist can.
- **P9 is the sole authoritative inventory of CI scripts**—the original gap G3’s three coexisting
  inventories prevented closure. This table merges them: all 11 scripts belong to one phase, and
  report-only status and strict-mode transition points are explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactoring”**—its deletion surface overlaps the rewrite surface of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactoring means repeating the same deletions on the new grammar,
  checker layout, and IR; this is the same lesson as incorporating `2315`/`2341` in 7e and
  RFC-status correction in S4.
- **P5’s steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker splitting would exceed independently revertible granularity.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the split must be independently
  revertible.
