**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: the design rationale for tasks (see `02`–`08`), the argumentation
for stage ordering (see RFC-039).

**Registration convention (from 2026-10-12 onwards)**: newly registered Level 2/3 rows **must carry
two fields**—**"Owning stage"** (which P it truly belongs to, may differ from the chapter it's in)
and **"Whether it blocks the main line"**; `登记待排期` (registration pending scheduling) is no
longer the default state, and unmarked ones are treated as **not schedulable**. Numbers **must be
unique** within the entire document (tasks across tracks use track numbers, e.g., `029g.x`, not
`N.x`). **Check-off/completion registration is based on "task id + evidence (gate numerical value,
run id, issue number, file:line)", not commit numbers**—`pull --rebase` rewrites local hashes,
hard-coded numbers will fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Look up commit numbers
via `git log`.

## Goal Design: Stage Sequence

```
P0  Repository maintenance mechanism and code placement rules  08        ← New, establish rules first
P1  Revive orphan tests and fix defects                       06 §S1
P2  Establish equivalence criterion baseline                  07 all
P3  Fix correctness vulnerabilities (minimum scheme)          02 §S3-vulnerability half
P4  Stage contract and unified Driver                        02
P5  checker file-internal split                              02 + completed by this document
P6  Type representation unification                          03
P7  Intermediate representation SSA-ization                   04      } Can be parallel
P8  Frontend paradigm change                                  05      }
P9  Anti-regression gates (including unified script list)    01 §Anti-regression + 08 §Machine-checkable rules
P10 Other cleanup and state corrections                       06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: the three prohibitions (no fabrication / no endless filling / should have
refactored but applied a patch) constrain every action from P1 to P10. Rules must be established
before work begins, otherwise by the time P1 revives tests, additional `mod` declarations will
already be added to `tests/mod.rs`—which is exactly the cause of the G4 conflict.

### P3 Fix Correctness Vulnerabilities (Minimum Scheme)

Source: [02](02-stage-contract.md) §Implementation Points S3 vulnerability fix half ＋ **2026-10-07
silent drop point audit (3.4)**

> **Semantic correction branching (D59, 2026-10-11 user ruling)**: If this track and its subsequent
> stages discover defects where "old behavior doesn't count as success"—**A silent failure / B
> silent mismatch / C undefined behavior and resource runaway** (crash, stack overflow, silently
> giving wrong answer)—**can be fixed along with the refactoring**, all four conditions must be met:
> ① red before green (red criterion exists first and is indeed red); ② does not change the external
> behavior of "programs that could previously compile successfully and run correctly" (cannot become
> failure, cannot delete or modify existing diagnostic codes/text/exit codes); ③ same commit
> registration (this line marks error type + revision note for that stage + PR required block "Error
> type" one line); ④ baseline regenerated in same commit + manual review diff. **D user-visible
> semantics / E external contract table / F RFC-level design changes still must first receive user
> ruling**. See [07 §Semantic Correction Branching Criteria](07-equivalence-oracle.md) for criterion
> expansion and A–F whitelist; **"default super refactoring + post-registration" is not adopted**
> (reasoning in RFC-039 D59: zero red criteria cannot distinguish fix from regression, and conflicts

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

## Key Decisions and Rationale

- **P0 is an independent stage rather than merged into P9**——gates are "post-hoc checks", rules are
  "pre-judgment". P9's scripts cannot prevent "should have refactored but applied a patch", only
  D0–D4's review checklist can.
- **P9 as the only authoritative list of CI scripts**——original gap G3's three coexisting lists made
  closure impossible. After this table merges, 11 scripts each attribute to one stage, report-only
  and hard conversion time points explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving it as "independent track, do after
  refactoring"**——its deletion surface coincides with P4/P5/P6/P7/P8's rewrite surface (RFC-039
  D56). Leaving it for after refactoring execution equals redo same batch of deletion on new
  grammar, new checker layout and new IR; this is the same lesson as 7e incorporating `2315`/`2341`,
  S4 incorporating RFC state correction.
- **P5's steps are completed by this document rather than merged into P4**——P4 is already the
  largest single point risk, additionally stacking checker split will exceed revertable granularity.
- **5.3.2 with "zero call site change" as hard acceptance**——split must be independently revertable.
