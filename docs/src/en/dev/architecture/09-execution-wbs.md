# Multi-Level Work Breakdown Structure (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the phase sequence of the RFC into **independently submittable, independently verifiable**
> three-level tasks.
>
> The phase ordering and acceptance gates are governed solely by the main text of RFC-039. This
> document is only responsible for breaking things down to an executable granularity and recording
> conflicts that have not yet been adjudicated.

## Position and Scope

| Level       | Count                                                                                                                                  | Meaning                                                                                                                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                                                                                                            | Phases, corresponding one-to-one with RFC-039's phase sequence                                                                                                                                                                                                                                 |
| **Level 2** | 59 (2026-10-13: 53 +2 = 3.13 / 3.14; 2026-10-14: +1 = 3.15; 2026-10-14: +1 = 3.16; 2026-10-15: +2 = 3.17 / 3.18)                       | Task groups, from each document's "Implementation Points" + 2026-10-07 audit addenda (P3's 3.4) + 2026-10-10/11 adjudication addenda (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery addenda (P3's 3.11) + 2026-10-12 discovery re-addenda (P3's 3.12) |
| **Level 3** | 151 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1; 2026-10-14: +2 = 3.15.1 / 3.16.1; 2026-10-15: +2 = 3.17.1 / 3.18.1; 2026-10-16: +1 = 4.6.2) | Independently committable actions                                                                                                                                                                                                                                                              |

**This document covers**: Task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: Design rationale for tasks (see `02`–`08`), justification of phase
ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields** — "**Owning Phase**" (which P it truly belongs to; may differ from the section it appears
in) and "**Whether It Blocks the Main Line**"; `registered-pending-scheduling` is no longer the
default state, and unmarked rows are considered **not schedulable**. Numbers must be **unique**
across the entire document (cross-track tasks use the track number, e.g., `029g.x`, and may not
occupy `N.x`). **Checkmark/completion registration uses "task id + evidence (gate numerical value,
run id, issue number, file:line)" as the criterion; do not write commit hashes** — `pull --rebase`
rewrites local hashes, and hard-coded numbers will inevitably fail (2026-10-13 instance:
`94ad03ce4`→`631eb3e3c`). Look up commit hashes in `git log`.

## Target Design: Phase Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Rules    08        ← Newly added, rules first
P1  Revive Orphan Tests and Fix Defects                          06 §S1
P2  Build Equivalence Criteria Baseline                          07  entire
P3  Fix Correctness Vulnerabilities (Minimal Solution)            02 §S3 - Vulnerability Half
P4  Stage Contracts and Unified Driver                           02
P5  Checker File-Internal Split                                  02 + Completed by this document
P6  Type Representation Unification                              03
P7  Intermediate Representation SSA-ification                    04      } Parallelizable
P8  Frontend Paradigm Change                                     05      }
P9  Anti-Rebound Gates (Including Unified Script List)           01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Other Cleanup and Status Corrections                         06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (must not fabricate / must not endlessly pad / must
not patch instead of refactoring) constrain every action in P1–P10. The rules must be established
before work begins; otherwise when P1 revives tests, someone will already be adding `mod`
declarations to `tests/mod.rs` — that is exactly what caused the G4 conflict.

## Key Decisions and Reasoning

- **P0 as independent stage rather than merged into P9** — Gates are "post-hoc check", rules are
  "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as the only authoritative list of CI scripts** — The original gap G3's three coexisting lists
  prevented closure. After this table merges, 10 scripts each attribute to one stage, report-only
  and hard conversion timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"** — Its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor equals redoing the same batch of deletions on the new grammar, new checker layout and new
  IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status
  correction.
- **P5's steps completed by this document rather than merged into P4** — P4 is already the largest
  single-point risk, adding checker split exceeds rollback granularity.
- **5.3.2 uses "zero call-site change" as hard acceptance** — Split must be independently
  revertable.
