# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Restructuring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's phase sequence into **independently committable and independently verifiable**
> level-3 tasks.
>
> The phase order and acceptance gates are governed solely by the main text of RFC-039. This
> document is responsible only for decomposing the work to an executable granularity and recording
> conflicts that have not yet been adjudicated.

three has had a corresponding entry since the WBS was established—the entire history of this
document has zero hits for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used to verify this),
and there are no repository-wide references. `8.1` corresponds precisely to phase 1 of `05` (test
revival and completion): that phase has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's
numbering is aligned with its phase number (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and binding
of acceptance criteria.

**Not covered by this document**: the design rationale for tasks (see `02`–`08`) and the rationale
for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered level-2/level-3 rows **must
contain two fields**—"**Owning phase**" (the P to which the task truly belongs, which may differ
from the containing section) and "**Blocks the mainline**"; `Pending scheduling` is no longer the
default state, and an unmarked task is deemed **not schedulable**. Numbers must be **unique across
the entire document** (cross-track tasks use their track number, such as `029g.x`, and must not
occupy `N.x`). **Checked/completed status is determined by "task id + evidence (gate metric, run id,
issue number, file:line)"**, not by a commit number—`pull --rebase` rewrites local hashes, so
hard-coded numbers inevitably become invalid (the 2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Look
up commit numbers with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (no fabrication / no endless filling / no
patching when a refactor is required) constrain every action in P1–P10. The rules must be
established before implementation begins; otherwise, while reviving tests in P1, work would already
begin adding `mod` declarations to `tests/mod.rs`—precisely the cause of the G4 conflict.

**6.9 Model and Invariants (first-principles rewrite, 2026-11-13)**

> **Model**: D62's terminal state is a **unified item world**—type positions and value positions
> share the same set of compile-time items. One strength declaration produces one quantifier reading
> `q ∈ {0,1,ω}`; `q` is the **sole input** to slot allocation, and the call-site argument view and

  original gap G3 made closure impossible. This table merges them, with 11 scripts each owned by one
  phase and with report-only status and hard-failure timing explicitly traceable. P2's 2.5, P4's
  4.3.2, and P7's 7c.1 refer to this table and do not establish separate lists.
- **P3.5 incorporates RFC-029g rather than leaving it as an "independent track to execute after the

  D56). Deferring execution until after the refactor means redoing the same batch of deletions on
  the new grammar, new checker layout, and new IR. This is the same lesson as incorporating
  `2315`/`2341` into 7e and RFC status correction into S4.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed independently revertible granularity.
- **5.3.2 uses "zero caller changes" as its hard acceptance criterion**—the split must be
  independently revertible.
