# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's phase sequence into **three-level tasks that can be committed and verified
> independently**.
>
> The phase order and acceptance gates are governed solely by the main body of RFC-039. This
> document is responsible only for breaking the work down into executable granularity and
> registering conflicts that remain undecided.

had corresponding entries from the inception of the WBS—the entire history of this document has zero
matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and there
are no repository-wide references either. `8.1` corresponds precisely to Stage 1 of `05` (test
resurrection and completion): that stage was split into P1 (`1.1`–`1.3`) and `8.8`, so P8's
numbering is aligned with its stage number (Stage 0 → `8.0`, Stage 2 → `8.2`, and so on).

**Covered here**: Task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: Rationale for task design (see `02`–`08`) and the argument for phase ordering
(see RFC-039).

**Registration convention (effective 2026-10-12)**: Newly registered level-2/level-3 rows **must
contain two fields**—“**Owning phase**” (the P to which the task truly belongs, which may differ
from its containing section) and “**Blocks the mainline**”. `Awaiting scheduling` is no longer the
default state; a task without an explicit state is deemed **not schedulable**. Numbers must be
**unique throughout the document** (cross-track tasks use their track number, such as `029g.x`, and
must not occupy an `N.x` number). **Check-off/completion registration is based on “task ID +
evidence (gate metrics, run ID, issue number, file:line)” and must not record commit
hashes**—`pull --rebase` rewrites local hashes, so hard-coded hashes inevitably become invalid
(2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Look up commit hashes with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions—no fabrication, no endless filling, and no
patching where a refactor is required—constrain every action in P1–P10. The rules must be
established before work starts; otherwise, restoring tests in P1 would already involve adding `mod`
declarations to `tests/mod.rs`, which is precisely what caused the G4 conflict.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 stop-the-bleeding path (decision on 2026-10-05)**: P3's prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in
> parallel with P3. Stopping correctness vulnerabilities is not blocked by criterion-infrastructure
> work; however, **P4 must still wait for all of P2**—the unified Driver requires all three layers
> of criteria to be in place.

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-hoc judgments.” P9's scripts cannot prevent “patching where a refactor was required”; only
  the D0–D4 review checklist can.
- **P9 is the sole canonical list of CI scripts**—the original gap G3's three coexisting lists made
  convergence impossible. This table merges them into 11 scripts, each owned by one phase, with
  report-only status and hard-failure timing made explicit.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactor means repeating the same deletions on the new grammar, new
  checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  incorporating RFC-status corrections into S4.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker decomposition would exceed the rollback granularity.
- **5.3.2 uses “zero consumer changes” as its hard acceptance criterion**—the decomposition must be
  independently revertible.
