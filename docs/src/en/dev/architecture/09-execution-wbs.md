# Multi-Level Work Breakdown Structure (WBS)

> **Supporting design document**. This document supports
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) by
> expanding the RFC phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The phase sequence and acceptance gates in the main RFC-039 text are the sole authority. This
> document only decomposes the work into an executable granularity and records conflicts that have
> not yet been adjudicated.

had corresponding entries from the WBS's inception—the entire history of this document has zero
matches for the `**4.7` / `**4.8` / `**8.1` headings

(test revival and completion): that phase was split into P1 (`1.1`–`1.3`) and `8.8`, so P8's
numbering remains aligned with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered here**: Task decomposition, dependencies, parallel groups, and binding of acceptance
criteria.

**Not covered here**: The design rationale for tasks (see `02`–`08`) or the justification for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: Every newly registered level-2/level-3 row
**must contain two fields**—“**Owning phase**” (the P phase to which it truly belongs, which may
differ from the containing section) and “**Blocks the mainline**.” `Pending scheduling` is no longer
the default state; an unannotated task is considered **not schedulable**. Numbers must be **unique
throughout the document** (tasks on different tracks use their track number, such as `029g.x`, and
must not occupy an `N.x` number). **Checkoff/completion registration is based on “task ID + evidence
(gate metric, run ID, issue number, file:line)” and must not record commit numbers**—`pull --rebase`
rewrites local hashes, so hard-coded numbers become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Look up commit numbers with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions (do not invent / do not pad indefinitely / do
not patch when a refactor is required) constrain every action in P1–P10. The rules must be
established before work starts; otherwise, reviving tests in P1 would already involve adding `mod`
declarations to `tests/mod.rs`, which is precisely the cause of the G4 conflict.

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “post-hoc checks,” whereas rules
  are “pre-hoc judgment.” P9's scripts cannot prevent “patching when a refactor is required”; only
  D0–D4's review checklist can.
- **P9 is the sole authoritative CI-script list**—the original G3's three coexisting lists made
  closure impossible. This table merges them into 11 scripts, each owned by one phase, with
  report-only status and hard-conversion timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56).
  Deferring it until after the refactor means repeating the same deletions across the new grammar,
  checker layout, and IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  RFC-status corrections into S4.
- **P5's steps are supplemented by this document rather than merged into P4**—P4 is already the
  largest single-point risk, and adding checker decomposition would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the decomposition must be independently
  revertable.
