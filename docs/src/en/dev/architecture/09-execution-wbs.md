# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC's phase sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates in the main body of RFC-039 are the sole authority. This
> document is responsible only for decomposing the work into executable granularity and recording
> conflicts that have not yet been adjudicated.

has ever had a corresponding entry since the WBS was established: this document's entire history has
zero matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and there
are no references anywhere in the repository. `8.1` corresponds precisely to phase 1 of `05` (test
revival and completion): that phase has already been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's
numbering is aligned with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**Covered here**: task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: the rationale for task design (see `02`–`08`) and the argument for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered Level 2/Level 3 rows **must
contain two fields**—“**Owning phase**” (the P to which the task genuinely belongs, which may differ
from its current section) and “**Blocks mainline**.” `Awaiting scheduling` is no longer the default
state; an unmarked task is considered **not schedulable**. Numbers **must be unique throughout the
document** (cross-track tasks use their track number, such as `029g.x`, and must not occupy an `N.x`
number). **Check-off/completion registration is based on “task ID + evidence (gate values, run ID,
issue number, file:line)” and does not record commit numbers**—`pull --rebase` rewrites local
hashes, so hard-coded numbers inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit numbers.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (do not invent constructs / do not fill
indefinitely / do not patch when a refactor is required) constrain every action in P1–P10. The rules
must be established before work begins; otherwise, while reviving tests in P1, work would already be
adding `mod` declarations to `tests/mod.rs`—precisely the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—a gate is an "after-the-fact check," whereas a
  rule is a "prior judgment." P9's scripts cannot prevent "patching when a refactor was required";
  only the D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the three coexisting lists that constituted
  original gap G3 prevented closure. This table merges all 11 scripts, each owned by one phase, with
  report-only status and hard-conversion timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactor”**—its deletion surface overlaps the rewrite surface of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring execution until after the refactor would repeat the same deletions on the new grammar,
  new checker layout, and new IR; this is the same lesson as absorbing `2315`/`2341` into 7e and
  RFC-status correction into S4.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker splitting would exceed the granularity at which changes can
  be rolled back.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the split must be independently
  revertible.
