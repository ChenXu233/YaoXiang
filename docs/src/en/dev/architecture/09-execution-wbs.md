# Multi-Level Work Breakdown Structure (WBS)

> **Supporting design document**. This document supports
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) by
> expanding the RFC’s phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates defined by the main body of RFC-039 are the sole authority.
> This document is responsible only for decomposing the work into an executable granularity and
> recording conflicts that have not yet been adjudicated.

**Unassigned numbers (not recycled)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three
has had a corresponding entry since the WBS was established: throughout this document’s history
there have been zero matches for the `**4.7` / `**4.8` / `**8.1` headings
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used to verify this),
and there are no references elsewhere in the repository. `8.1` corresponds precisely to stage 1 of
`05` (test resurrection and completion). That stage was split into P1 (`1.1`–`1.3`) and `8.8`, so
P8’s numbering is aligned with its phase numbers: phase 0 → `8.0`, phase 2 → `8.2`, and so forth.

**Covered by this document**: task decomposition, dependencies, parallelization groups, and binding
of acceptance criteria.

**Not covered by this document**: the design rationale for the tasks (see `02`–`08`) or the
rationale for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered Level 2/Level 3 row
**must contain two fields**—“**Owning Phase**” (the P to which it genuinely belongs, which may
differ from the containing section) and “**Blocks the Mainline**.” `登记待排期` is no longer the
default state; an unmarked entry is considered **not schedulable**. Numbers must be **unique
throughout the document** (cross-track tasks use their track number, such as `029g.x`, and must not
occupy an `N.x` number). **Checkoff/completion registration is based on “task ID + evidence (gate
values, run ID, issue number, file:line)” and does not record commit numbers**—`pull --rebase`
rewrites local hashes, so hard-coded numbers inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit numbers.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: the three prohibitions (no invention / no endless filling / no patching
when a refactor is required) constrain every action in P1–P10. The rules must be established before
work begins; otherwise, while resurrecting tests in P1, work would already be adding `mod`
declarations to `tests/mod.rs`, which is precisely the cause of the G4 conflict.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 emergency path (adjudicated on 2026-10-05)**: P3’s prerequisites are narrowed to **2.3.2 +
> 2.4.1 + 2.4.3** (the multi-file corpus layer + the two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) may proceed in
> parallel with P3. Stopping correctness defects must not be blocked by criterion-infrastructure
> construction; however, **P4 must still wait for all of P2**—the unified Driver requires all three
> layers of criteria to be in place.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-work judgment.” P9’s scripts cannot prevent “patching when a refactor was required”; only the
  D0–D4 review checklist can do so.
- **P9 is the sole authoritative list of CI scripts**—the three coexisting lists for original gap G3
  prevented closure. This table merges them into 11 scripts, each owned by one phase, with
  report-only status and hard-failure conversion points explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to do after the
  refactoring”**—its deletion surface overlaps the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactoring means repeating the same deletions on the new grammar,
  new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  incorporating RFC status corrections into S4.
- **P5’s steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the split must be independently
  revertible.
