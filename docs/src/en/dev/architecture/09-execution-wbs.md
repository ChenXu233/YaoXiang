# Multi-Level Construction Task Table (WBS)

> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence in the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> The phase order and acceptance gates use the body of RFC-039 as the sole authority; this document
> is only responsible for breaking down to executable granularity and registering conflicts that
> have not yet been adjudicated.

## Positioning and Scope

| Level       | Count       | Meaning                                                                                                                                                               |
| ----------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, in one-to-one correspondence with the phase sequence in RFC-039                                                                                               |
| **Level 2** | 48          | Task groups, drawn from "Implementation Points" in each document + the 2026-10-07 audit addendum (3.4 in P3) + the 2026-10-10 adjudication supplement (3.5/3.6 in P3) |
| **Level 3** | 134         | Independently committable actions                                                                                                                                     |

**This document covers**: task decomposition, dependencies, parallel groupings, acceptance criterion
binding.

**This document does not cover**: the design rationale for tasks (see `02`–`08`), the argumentation
for the phase order (see RFC-039).

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← new; rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence oracle baseline             07 all
P3  Fix correctness vulnerabilities (minimum solution)        02 §S3-vulnerability half
P4  Stage contract and unified Driver          02
P5  checker in-file split             02 + filled in by this document
P6  Type representation unification                 03
P7  Intermediate representation SSA-ification                04      } parallelizable
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gate (including unified script list)     01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Remaining cleanup and status corrections             06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (no fabrication / no endless padding / patching
instead of refactoring) constrain every action of P1–P10. The rules must be set up before work
begins; otherwise, when P1 revives tests, the very act of adding `mod` declarations to
`tests/mod.rs` is the cause of the G4 conflict.

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

## Key Decisions and Reasons

- **P0 as independent phase rather than merged into P9** — the gate is "post-hoc check", the rules
  are "prior judgment". P9's scripts cannot prevent "should refactor but patched instead", only the
  D0–D4 review checklist can.
- **P9 as the sole authority list of CI scripts** — the three coexisting lists from original gap G3
  made closure impossible. After this table's merger 10 scripts each attribute to a single phase,
  report-only and promote-to-hard timing explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"** — its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor equals doing the same batch of deletions on the new grammar, new checker layout and new
  IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status
  correction.
- **P5's steps filled in by this document rather than merged into P4** — P4 is already the largest
  single-point risk, adding checker split would exceed rollback granularity.
- **5.3.2 with "zero caller change" as hard acceptance** — split must be independently revertable.
