corresponding entries since the WBS was established — this document's full history has zero hits on
the `**4.7` / `**4.8` / `**8.1` headings (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the entire repo has no
references. `8.1` corresponds exactly to `05`'s Stage 1 (test resurrection and completion): that

(Stage 0 → `8.0`, Stage 2 → `8.2`, and so on).

**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criterion
binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), argumentation for
stage order (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered level-2/level-3 rows **must carry
two fields** — "**Owning Stage**" (which P it truly belongs to, may differ from the section it
appears in) and "**Whether it blocks the main line**"; `pending scheduling` is no longer a default
state, and unlabeled is treated as **not schedulable**. Numbering **must be unique across the entire
document** (tasks crossing tracks use the track number, e.g., `029g.x`, and must not occupy `N.x`).
**Checkmark / completion registration is governed by "task id + evidence (gate value, run id, issue
number, file:line)"** — commit numbers are not written down — `pull --rebase` rewrites local hashes,
and hardcoded numbers will certainly fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Check
commit numbers via `git log`.

## Target Design: Stage Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Regulations   08        ← New, establish rules first
P1  Resurrect Orphan Tests and Fix Defects   06 §S1
P2  Establish Equivalence Criterion Baseline   07 all
P3  Fix Correctness Vulnerabilities (Minimal Solution)   02 §S3-Vulnerability Half
P4  Stage Contracts and Unified Driver   02
P5  Checker File-Internal Split   02 + filled in by this document
P6  Type Representation Unification   03
P7  Intermediate Representation SSA-ification   04      } Parallelizable
P8  Frontend Paradigm Change   05      }
P9  Anti-Rebound Gates (Including Unified Script List)   01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Remaining Cleanup and Status Correction   06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (no fabrication / no endless filling / patch when
refactor is needed) constrain every action in P1–P10. The rules must be established before work
begins; otherwise, when P1 resurrects tests, it's already adding `mod` declarations to
`tests/mod.rs` — which is exactly the cause of the G4 conflict.

### P3 Fix Correctness Vulnerabilities (Minimal Solution)

Source: [02](02-stage-contract.md) §Implementation Points S3 vulnerability fix half + **2026-10-07
silent discard point audit (3.4)**

> **Semantic fix divergence (D59, 2026-10-11 user ruling)**: If this track or subsequent stages
> discover defects where "old behavior does not count as success" — **A silent failure / B silent
> mismatch / C undefined behavior and resource out-of-control** (crash, stack overflow, silently
> wrong answer) — **can be fixed along with the refactor**, with four conditions all required: ① Red
> before green (red criterion exists first and is indeed red); ② Does not change the external
> behavior of "programs that previously compiled and ran correctly" (must not become failure, must
> not modify existing diagnostic code/text/exit code); ③ Same-commit registration (this row labels
> error type + this stage revision note + PR required block "error type" one line); ④ Baseline
> regenerated in same commit + manual review diff. **D user-visible semantics / E external contract
> table / F RFC-level design changes three categories still must go through user ruling first**.
> Criterion expansion and A–F whitelist see
> [07 §Semantic Fix Divergence Criteria](07-equivalence-oracle.md); **"default super refactor +
> post-registration" not adopted** (reason see RFC-039 D59: zero red criterion cannot distinguish
> fix from regression, conflicts with "no C5′ exists" and "no relaxation set").

## Key Decisions and Reasons

- **P0 as independent stage rather than merged into P9** — gates are "post-hoc check", rules are
  "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as sole authoritative list of CI scripts** — original gap G3's three coexisting lists led to
  inability to close. After merging 11 scripts each attributed to one stage, report-only and
  switch-to-hard timing explicit and queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"** — its
  removal surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactor equals redoing same batch of deletion on new grammar, new checker layout, and new IR;
  this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status correction.
- **P5's steps filled in by this document rather than merged into P4** — P4 is already the largest
  single-point risk, further stacking checker split would exceed revertable granularity.
- **5.3.2 with "zero caller change" as hard acceptance** — split must be independently revertable.
