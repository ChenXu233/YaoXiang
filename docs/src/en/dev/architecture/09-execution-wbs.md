# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC’s phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates are governed solely by the body of RFC-039. This document is
> responsible only for decomposing the work into an executable granularity and recording conflicts
> that have not yet been adjudicated.

**Reserved numbers (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three
has had a corresponding entry since the WBS was established—the history of this document has zero
matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used to verify this),
and there are no repository-wide references. `8.1` corresponds precisely to stage 1 of `05` (test
revival and completion): that stage was split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s numbering is
aligned with its stage numbers (stage 0 → `8.0`, stage 2 → `8.2`, and so forth).

**Covered here**: Task decomposition, dependencies, parallelization groups, and binding of
acceptance criteria.

**Not covered here**: Design rationale for the tasks (see `02`–`08`) or the rationale for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: Every newly registered Level 2/Level 3 entry
**must contain two fields**—“**Owning phase**” (the P to which it truly belongs, which may differ
from the chapter in which it appears) and “**Blocks the mainline?**”; `Pending scheduling` is no
longer the default state, and an unmarked entry is considered **not schedulable**. Numbers must be
**unique across the entire document** (tasks on different tracks use the track number, such as
`029g.x`, and must not occupy `N.x`). **Checkoff/completion registration is based on “task id +
evidence (gate values, run id, issue number, file:line)” and must not record commit
numbers**—`pull --rebase` rewrites local hashes, so hard-coded numbers inevitably become invalid
(2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Look up commit numbers with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions—no fabrication, no endless filling, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before work begins; otherwise, while reviving tests in P1, work would already begin adding `mod`
declarations to `tests/mod.rs`, which is precisely the source of the G4 conflict.

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—gates are “after-the-fact checks,” while rules
  are “before-the-fact judgment.” P9’s scripts cannot prevent “patching when a refactor was
  required”; only the D0–D4 review checklist can do that.
- **P9 is the sole authoritative list of CI scripts**—the three coexisting lists that constituted
  gap G3 made convergence impossible. This table merges them into 11 scripts, each owned by one
  phase, with report-only status and the hard-failure conversion point explicitly traceable.
- **P3.5 adopts RFC-029g rather than leaving it as an “independent track to be done after the
  refactoring”**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactoring means redoing the same deletions on the new
  grammar, new checker layout, and new IR. This is the same lesson as 7e adopting `2315`/`2341` and
  S4 adopting RFC status corrections.
- **P5’s steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker splitting would exceed the granularity at which work can be
  rolled back.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertible.

## Known Limitations and Risks

- **1.3.x (fixing exposed defects) has no regression criterion**—it only says that “fixed defects
  must not be reverted” and lacks a requirement to record “what was fixed.” **Execution
