# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document.** This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC’s phase sequence into **independently committable and independently verifiable**
> level-3 tasks.
>
> The phase sequence and acceptance gates are governed solely by the main body of RFC-039. This
> document is responsible only for breaking the work down to an executable granularity and
> registering conflicts that have not yet been adjudicated.

**Unused numbers (not recycled)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three has
had a corresponding entry since the WBS was established: the full history of this document has zero
matches for the three headings `**4.7` / `**4.8` / `**8.1` (verifiable with
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the repository contains
no references to them. `8.1` corresponds precisely to phase 1 of `05` (test revival and completion).
That phase has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s numbering is aligned with its
phase number (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered here**: task breakdown, dependencies, parallelization groups, and binding of acceptance
criteria.

**Not covered here**: the design rationale for individual tasks (see `02`–`08`) or the justification
for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered level-2/level-3 row
**must contain two fields**—“**Owning phase**” (the P phase to which it truly belongs, which may
differ from the current section) and “**Blocks the mainline**.” `Awaiting scheduling` is no longer
the default state; an unmarked item is considered **not schedulable**. Numbers must be **unique
across the entire document** (cross-track tasks use their track number, such as `029g.x`, and must
not occupy `N.x`). **Checkoff/completion registration is based on “task ID + evidence (gate metrics,
run ID, issue number, file:line),” not a commit number**—`pull --rebase` rewrites local hashes, so a
hard-coded number will inevitably become invalid (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Look
up commit numbers with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: the three prohibitions—no fabrication, no endless padding, and no patching
when a refactor is required—constrain every action in P1–P10. The rules must be established before
work begins; otherwise, while reviving tests in P1, work has already begun adding `mod` declarations
to `tests/mod.rs`, which is precisely the cause of the G4 conflict.

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—gates are “after-the-fact checks,” whereas rules
  are “before-the-fact judgment.” P9’s scripts cannot prevent “patching when a refactor is
  required”; only the D0–D4 review checklist can.
- **P9 is the sole authoritative inventory of CI scripts**—the original gap G3’s three parallel
  inventories made closure impossible. This table merges them into 11 scripts, each owned by one
  phase, with report-only status and conversion timing explicitly traceable.
- **P3.5 brings RFC-029g under management rather than leaving it as an “independent track to do
  after the refactor”**—its deletion surface overlaps the rewrite surfaces of P4/P5/P6/P7/P8
  (RFC-039 D56). Deferring it until after the refactor means redoing the same deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as bringing 7e’s `2315`/`2341`
  under management and S4’s RFC-status corrections.
- **P5’s steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker splitting would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertible.
