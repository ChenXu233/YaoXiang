# Multi-Level Implementation Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC’s phase sequence into **level-3 tasks that can be committed and verified
> independently**.
>
> The phase order and acceptance gates in the body of RFC-039 are the sole authority. This document
> is responsible only for decomposing the work into executable granularity and recording conflicts
> that remain undecided.

**Numbering gaps (reserved, not reused)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the
three has had a corresponding entry since the WBS was established—the entire history of this
document has zero matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can verify this), and there
are no repository-wide references. `8.1` corresponds precisely to stage 1 of `05` (test revival and
completion): that stage has already been split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s numbering
aligns with its stage number (stage 0 → `8.0`, stage 2 → `8.2`, and so on).

**Covered here**: task decomposition, dependencies, parallelization groups, and acceptance-criterion
bindings.

**Not covered here**: the rationale for task design (see `02`–`08`) or the argument for phase order
(see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered level-2/level-3 row
**must contain two fields**—“**Owning stage**” (the P stage to which it truly belongs, which may
differ from the section in which it appears) and “**Blocks the critical path**”;
`Pending scheduling` is no longer the default state, and an unmarked item is considered **not
schedulable**. Numbers must be **unique throughout the document** (cross-track tasks use their track
number, such as `029g.x`, and must not occupy an `N.x` number). **Checkoff/completion registration
is based on “task ID + evidence (gate value, run ID, issue number, file:line)” and does not record
commit hashes**—`pull --rebase` rewrites local hashes, so hard-coded hashes inevitably become
invalid (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Consult `git log` for commit hashes.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions—no fabrication, no endless filling, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before work begins; otherwise, while reviving tests in P1, work would already be adding `mod`
declarations to `tests/mod.rs`, which is precisely the cause of the G4 conflict.

**Hard constraint**: `collect_used_in_type` is used across module boundaries by
`inference/statements.rs:16`. **If** the function is migrated with the annotation family in the
future, **then** `pub(crate) use annotations::*;` must be added in `checker.rs` so that the import
remains unchanged; 5.3 did **not** migrate it by measurement, so this batch did not add a re-export
(the criterion was already satisfied).

**Only split confirmed large blocks.** Do not split modules of only 200–400 lines—this adds
navigation cost, reduces cohesion, and yields no decoupling benefit. The remaining submodules
(signatures / type_defs / imports) will be split when the files grow back to 1,500 lines.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 stop-the-bleeding path (decision of 2026-10-05)**: P3’s prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in
> parallel with P3. Stopping correctness vulnerabilities must not be blocked by
> criterion-infrastructure construction; however, **P4 must still wait for all of P2**—the unified
> Driver needs all three layers of criteria in place.

## Key Decisions and Rationale

- **P0 is an independent stage rather than part of P9**—gates are “post-hoc checks,” whereas rules
  are “ex-ante judgment.” P9’s scripts cannot prevent “patching when a refactor was required”; only
  the D0–D4 review checklist can.
- **P9 is the sole authoritative inventory of CI scripts**—the three overlapping inventories from
  original gap G3 prevented closure. This table merges them into 11 scripts, each owned by one
  stage, with report-only status and conversion timing explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track after the
  refactor”**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactor would mean repeating the same deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341`
  into 7e and correcting RFC status in S4.
- **P5’s steps are supplied by this document rather than folded into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the granularity that can be rolled
  back.
- **5.3.2 uses “zero caller changes” as a hard acceptance criterion**—the split must be
  independently revertable.
