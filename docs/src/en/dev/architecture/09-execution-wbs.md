# Multi-Level Implementation Task Breakdown (WBS)

> **Companion design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates are governed solely by the body of RFC-039. This document is
> responsible only for breaking the work down to an executable granularity and recording conflicts
> that have not yet been adjudicated.

**Reserved numbering gaps (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the
three has had a corresponding entry since the WBS was established. The complete history of this
document has zero matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` is independently verifiable),
and the repository contains no references to them. `8.1` corresponds precisely to phase 1 of `05`
(test revival and completion). That phase has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s
numbering is aligned with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and binding
of acceptance criteria.

**Not covered by this document**: the design rationale for the tasks (see `02`–`08`) or the
rationale for the phase order (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered Level 2/Level 3 row
**must contain two fields**—“**Owning stage**” (the P phase to which it truly belongs, which may
differ from the current section) and “**Blocks mainline**.” `Awaiting scheduling` is no longer the
default state; an unmarked task is considered **not schedulable**. Numbering must be **unique across
the entire document** (tasks on separate tracks use the track number, such as `029g.x`, and must not
occupy an `N.x` number). **Checkoff/completion records are based on “task id + evidence (gate value,
run id, issue number, file:line)” and must not record commit hashes**—`pull --rebase` rewrites local
hashes, so hard-coded hashes will inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to find commit hashes.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (no invention / no endless filling / no patching
when a refactor is required) constrain every action in P1–P10. The rules must be established before
work begins; otherwise, when P1 revives the tests, work will already be adding `mod` declarations to
`tests/mod.rs`—which is precisely the cause of the G4 conflict.

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> (2.1 IR verifier, 2.2 snapshots, 2.3.1/2.3.3 differential testing and performance baseline) can

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—gates are “post-hoc checks,” whereas rules are
  “pre-hoc judgment.” P9’s scripts cannot prevent “patching when a refactor is required”; only the
  D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the three coexisting lists caused by original
  gap G3 made closure impossible. After this table merges them, all 11 scripts belong to exactly one
  phase, with report-only status and strict-transition timing explicitly traceable.
- **P3.5 adopts RFC-029g rather than leaving it as an “independent track to be done after the
  refactoring”**—its deletion surface overlaps the rewrite surface of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactoring means redoing the same deletions on the new grammar, new
  checker layout, and new IR; this is the same lesson as 7e adopting `2315`/`2341` and S4 adopting
  RFC status corrections.
- **P5’s steps are supplemented by this document rather than merged into P4**—P4 is already the
  largest single-point risk, and adding the checker split would exceed the granularity at which
  changes can be rolled back.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertible.
