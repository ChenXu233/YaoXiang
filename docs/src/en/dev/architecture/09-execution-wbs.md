# Multi-level Work Breakdown Structure (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC's phase sequence into a **three-level task structure that can be independently
> committed and independently verified**.
>
> Phase order and acceptance gates follow RFC-039's main text as the sole authority; this document
> only decomposes work into an executable granularity and registers unresolved conflicts.

## Positioning and Scope

| Level       | Count       | Meaning                                                                                                                                                                                                                                                                                                    |
| ----------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, corresponding one-to-one with RFC-039's phase sequence                                                                                                                                                                                                                                             |
| **Level 2** | 53          | Task groups, drawn from each document's "Implementation Points" + 2026-10-07 audit supplement (P3's 3.4) + 2026-10-10/11 ruling supplement (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery supplement (P3's 3.11) + 2026-10-12 discovery re-supplement (P3's 3.12) |
| **Level 3** | 144         | Independently committable actions                                                                                                                                                                                                                                                                          |

**This document covers**: task decomposition, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: rationale for the tasks (see `02`–`08`), justification of phase
order (see RFC-039).

**Registration convention (effective 2026-10-12)**: Newly registered Level 2/3 rows **must include
two fields**—「**Owning phase**」 (which P it truly belongs to; may differ from the section it
appears in) and 「**Whether it blocks the mainline**」; `registration pending scheduling` is no
longer the default state, and unannotated rows are treated as **not schedulable**. Numbering must be
**unique within the document** (tasks spanning tracks use the track number, e.g. `029g.x`, and must
not occupy `N.x`).

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules   08        ← New, set rules first
P1  Resurrect orphan tests and fix defects                       06 §S1
P2  Establish equivalence criterion baseline                     07 all
P3  Fix correctness vulnerabilities (minimal scheme)             02 §S3-vulnerability half
P4  Phase contract and unified Driver                            02
P5  Split checker file                                           02 + this document
P6  Type representation unification                              03
P7  Intermediate representation SSA-ification                    04      } Parallelizable
P8  Frontend paradigm change                                     05      }
P9  Anti-regression gates (with unified script inventory)        01 §Anti-regression + 08 §Machine-checkable rules
P10 Other cleanup and status corrections                         06 §S2/S3/S4/S5/S6
```

**Rationale for the new P0**: The three prohibitions (no fabrication / no endless padding / patched
instead of refactored) constrain every action in P1–P10. The rules must be established before work
begins; otherwise, P1's test resurrection will already be adding `mod` declarations to
`tests/mod.rs`—which is exactly what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 independent as stage not merged into P9**—gate is "post-hoc check", rules are "pre-judgment".
  P9's scripts cannot prevent "patched instead of refactored", only D0–D4's review checklist can.
- **P9 as the sole authoritative inventory of CI scripts**—the original gap G3's three parallel
  inventories led to inability to close. After this table merges, 10 scripts each own one phase,
  report-only and switch-to-hard timing explicitly queryable.
- **P3.5 consolidates RFC-029g instead of leaving as "independent track, wait for refactor"**—its
  deletion surface coincides with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for
  post-refactor execution means redoing the same batch of deletion on new grammar, new checker
  layout, and new IR; this is the same lesson as 7e consolidating `2315`/`2341`, S4 consolidating
  RFC status correction.
- **P5's steps supplemented by this document not merged into P4**—P4 is already the largest
  single-point risk, stacking checker split would exceed rollback granularity.
- **5.3.2 with "zero caller changes" as hard acceptance**—split must be independently revertable.
