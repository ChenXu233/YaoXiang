# Multi-level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence in the RFC into **independently committable, independently
> verifiable** three-level tasks.
>
> Phase ordering and acceptance gates are authoritative only in RFC-039 body; this document is
> responsible only for breaking down to executable granularity and registering unresolved conflicts.

## Positioning and Scope

| Level       | Count                                      | Meaning                                                                                                                                                                                                                                                                                                   |
| ----------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10)                                | Phases, one-to-one correspondence with the phase sequence in RFC-039                                                                                                                                                                                                                                      |
| **Level 2** | 55 (2026-10-13: 53 +2 = 3.13 / 3.14)       | Task groups, from each document's "Implementation Points" + 2026-10-07 audit supplement (P3's 3.4) + 2026-10-10/11 ruling supplement (P3's 3.5/3.6/3.7/3.8/3.9) + 2026-10-12 registration (P3's 3.10) + 2026-10-12 discovery supplement (P3's 3.11) + 2026-10-12 discovery further supplement (P3's 3.12) |
| **Level 3** | 146 (2026-10-13: 144 +2 = 3.13.1 / 3.14.1) | Independently committable actions                                                                                                                                                                                                                                                                         |

**This document covers**: Task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: Design rationale for tasks (see `02`–`08`), arguments for phase
ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered level-2/level-3 rows **must carry
two fields** — "**Owning Phase**" (which P it truly belongs to, may differ from the section it's in)
and "**Whether It Blocks the Main Line**"; `registered pending scheduling` is no longer the default
state, and unmarked entries are considered **not schedulable**. Numbers **must be unique** across
the entire document (cross-track tasks use track numbers, e.g., `029g.x`, must not occupy `N.x`).
**Checkoff/completion registration is based on "task id + evidence (gate value, run id, issue
number, file:line)"**, not commit numbers — `pull --rebase` will rewrite local hashes, and
hard-coded numbers will fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Look up commit numbers
in `git log`.

## Target Design: Phase Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Rules     08        ← New, establish rules first
P1  Revive Orphan Tests and Fix Defects           06 §S1
P2  Establish Equivalence Oracle Baseline             07 all
P3  Fix Correctness Vulnerabilities (Minimal Solution)        02 §S3-vulnerability half
P4  Stage Contract and Unified Driver          02
P5  Checker In-file Split             02 + filled in by this document
P6  Type Representation Unification                 03
P7  Intermediate Representation SSA-ization                04      } Can run in parallel
P8  Frontend Paradigm Change                   05      }
P9  Anti-regression Gates (incl. Unified Script List)     01 §Anti-regression + 08 §Machine-checkable Rules
P10 Remaining Cleanup and Status Correction             06 §S2/S3/S4/S5/S6
```

**Reason for the new P0**: The three prohibitions (must not invent / must not endlessly pad / should
refactor but patched) constrain every action in P1–P10. Rules must be established before
construction begins, otherwise when P1 revives tests, it will already be adding `mod` declarations
to `tests/mod.rs` — which is exactly the cause of the G4 conflict.

## Implementation Points: Dependencies and Parallelism

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 hemostasis channel (2026-10-05 ruling)**: P3's prerequisites narrowed to **2.3.2 + 2.4.1 +
> 2.4.3** (multi-file corpus layer + two red oracles). P2's rest (2.1 IR verifier, 2.2 snapshot,
> 2.3.1/2.3.3 diff and performance baseline) can advance in parallel with P3. Hemostasis of
> correctness vulnerability not blocked by oracle infrastructure construction; but **P4 still must
> wait for P2 fully completed** — unified Driver needs three-layer oracle all in place.

| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1            | Three prohibitions constrain every action of P1 (1.2.x is adding `mod` declarations to `mod.rs`)                                                                                                                                         |

| P2 (narrowed) → P3 | Vulnerability oracle must **first be written red** (2.4.1/2.4.3) + multi-file corpus layer (2.3.2) exist, red test has place to run                                                                                                      |

| P3.5 → P4          | RFC-029g (#399)'s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8 respective rewrite objects (list see this document §P3.5) — reverse order equals redo the same batch of deletion on new grammar, new checker layout, new IR (D56) |

## Key Decisions and Reasons

- **P0 independent as phase not merged into P9** — Gate is "after-the-fact check", rule is
  "pre-judgment". P9's script cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as sole authoritative list of CI scripts** — Original gap G3's three parallel lists couldn't
  be closed. After this table merges 10 scripts each attributed to one phase, report-only and
  to-hard time points explicitly checkable.
- **P3.5 incorporate RFC-029g not leave as "independent track, do after refactoring"** — Its
  deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for after
  refactoring equals redo the same batch of deletion on new grammar, new checker layout and new IR;
  this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC status correction.
- **P5's steps filled in by this document not merged into P4** — P4 is already the largest single
  point risk, adding checker split will exceed rollback granularity.
- **5.3.2 with "zero caller change" as hard acceptance** — Split must be independently revertible.
