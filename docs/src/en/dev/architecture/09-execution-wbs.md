> **Subsidiary Design Document**. This document is a subsidiary of
> [RFC-039: Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> which expands the phase sequence in the RFC into a **three-level task list** that can be

> responsible only for breaking it down to executable granularity and registering any unresolved

`**4.8` / `**8.1` headings throughout its history (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the entire repository has
no references to them. `8.1` corresponds to `05`'s Phase 1 (Test Revival and Completion): that phase

(Phase 0 → `8.0`, Phase 2 → `8.2`, and so on).

**Coverage of this document**: Task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**Not covered by this document**: Design rationale for tasks (see `02`–`08`), argumentation for
phase ordering (see RFC-039).

**Registration Convention (Effective 2026-10-12)**: Newly registered Level 2/3 rows **must carry two
fields** — "**Owning Phase**" (which P it truly belongs to, possibly different from the chapter it's
listed in) and "**Whether Blocking the Mainline**"; `registered, awaiting scheduling` is no longer
the default state, unmarked entries are treated as **not schedulable**. Numbers **must be unique**
within the entire document (tasks spanning tracks use the track number, e.g., `029g.x`, and may not
occupy `N.x`). **Check-off/completion registration is based on "task id + evidence (gate values, run
id, issue number, file:line)"** — do not write commit hashes. `pull --rebase` rewrites local hashes,
and any hardcoded hashes will inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Check `git log` for commit hashes.

## Target Design: Phase Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Rules   08        ← New, rules first
P1  Revive Orphan Tests and Fix Defects                          06 §S1
P2  Establish Equivalence Oracle Baseline                       07 All
P3  Fix Correctness Vulnerabilities (Minimum Solution)           02 §S3 - Vulnerability Half
P4  Phase Contract and Unified Driver                            02
P5  Checker File Split                                           02 + Supplemented by this document
P6  Type Representation Unification                              03
P7  Intermediate Representation SSA-ization                      04      } Parallelizable
P8  Frontend Paradigm Change                                     05      }
P9  Anti-Rebound Gates (including Unified Script List)           01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Other Cleanup and Status Correction                          06 §S2/S3/S4/S5/S6
```

**Reason for the new P0**: Three prohibitions (no fabrication / no endless padding / patched instead
of refactored) constrain every action in P1–P10. The rules must be established before work begins;
otherwise, by the time P1 revives tests, `mod` declarations will already be added to `tests/mod.rs`
— precisely the cause of the G4 conflict.

## Implementation Points: Dependencies and Parallelism

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 Bleeding Channel (2026-10-05 ruling)**: P3's prerequisites narrowed to **2.3.2 + 2.4.1 +
> 2.4.3** (multifile corpus layer + two red criteria). The rest of P2 (2.1 IR verifier, 2.2
> snapshot, 2.3.1/2.3.3 diff and performance baseline) can advance in parallel with P3. The bleeding
> of correctness vulnerabilities is not blocked by oracle infrastructure construction; but **P4
> still must wait for P2 to fully complete** — the unified Driver needs all three layers of criteria
> in place.

| Constraint         | Reason                                                                                                                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 → P1            | Three prohibitions constrain every action of P1 (1.2.x is exactly adding `mod` declarations to `mod.rs`)                                                                                                                                      |
| P1 → P2            | Reviving tests will change test count and corpus baseline                                                                                                                                                                                     |
| P2 (narrowed) → P3 | Vulnerability criteria must be **written red first** (2.4.1/2.4.3) + multifile corpus layer (2.3.2) exists, red tests have a place to run                                                                                                     |
| P3 → P4            | Fix bugs first then refactor; reverse order would let bugs be solidified into "established behavior" by the phase table                                                                                                                       |
| P3.5 → P4          | RFC-029g (#399)'s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8's respective rewrite targets (list in this document §P3.5) — reverse order equals redoing the same batch of deletions on new grammar, new checker layout, new IR (D56) |

## Key Decisions and Rationale

- **P0 independent phase rather than merged into P9** — gates are "after-the-fact checks", rules are
  "before-the-fact judgment". P9's scripts cannot prevent "patched instead of refactored", only
  D0–D4's review checklist can.
- **P9 as CI scripts' sole authoritative list** — the original Gap G3's three coexisting lists made
  closure impossible. After this table's merge, 11 scripts each owned by one phase, report-only and
  transition-to-hard timing explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactoring"** —
  its deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56). Leaving for
  post-refactoring execution equals redoing the same batch of deletions on new grammar, new checker
  layout and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating RFC
  status correction.
- **P5's steps supplemented by this document rather than merged into P4** — P4 is already the
  largest single-point risk, adding checker split on top would exceed rollback granularity.
- **5.3.2 takes "zero caller change" as hard acceptance** — split must be independently revertable.
