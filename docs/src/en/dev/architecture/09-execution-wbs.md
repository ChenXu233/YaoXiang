# Multi-level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the phase sequence of RFC-039 into **independently committable and independently
> verifiable** three-level tasks.
>
> The phase order and acceptance gates take RFC-039's main text as the sole authority; this document
> is only responsible for breaking it down to executable granularity, and registering unresolved
> conflicts.

**Numbering left blank (not reclaimed)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. These three have
had no corresponding entries since the WBS was established — this document's entire history has zero
hits for `**4.7` / `**4.8` / `**8.1` titles (can be verified with
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the entire repository has
no references. `8.1` corresponds to phase 1 of `05` (test revival and completion): that phase has
been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering aligns with its phase number (phase 0
→ `8.0`, phase 2 → `8.2`, and so on).

**This document covers**: task breakdown, dependency relationships, parallel grouping, acceptance
criteria binding.

**This document does not cover**: design rationale for tasks (see `02`–`08`), arguments for phase
ordering (see RFC-039).

**Registration convention (from 2026-10-12)**: Newly registered level 2/3 rows **must carry two
fields** — "**Owning phase**" (which P it truly belongs to, may differ from the chapter it appears
in) and "**Whether it blocks the main line**"; `registration pending scheduling` is no longer the
default state, unmarked entries are considered **unschedulable**. Numbers must be **unique**
throughout the document (cross-track tasks use track numbers, e.g., `029g.x`, must not occupy
`N.x`). **Checkoff/completion registration is based on "task id + evidence (gate value, run id,
issue number, file:line)"**, not commit numbers — `pull --rebase` will rewrite local hashes,
hard-coded numbers will inevitably fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Check commit
numbers with `git log`.

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules   08        ← New, establish rules first
P1  Revive orphan tests and fix defects                          06 §S1
P2  Establish equivalence criterion baseline                     07 all
P3  Fix correctness vulnerabilities (minimum solution)            02 §S3-vulnerability half
P4  Phase contract and unified Driver                            02
P5  checker in-file split                                        02 + completed in this document
P6  Type representation unification                              03
P7  Intermediate representation SSA-ization                       04      } Can be parallel
P8  Frontend paradigm change                                     05      }
P9  Anti-rebound gates (including unified script list)           01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status correction                          06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (no fabrication / no endless filling / patching
instead of refactoring when refactoring is needed) constrain every action of P1–P10. Rules must be
established before construction begins, otherwise when P1 revives tests, `mod` declarations are
already being added to `tests/mod.rs` — which is exactly the cause of the G4 conflict.
