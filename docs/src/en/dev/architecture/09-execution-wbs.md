**Reserved numbering (not recycled)**: P4 has no `4.7`/`4.8`, P8 has no `8.1`. These three have had
no corresponding entries since the WBS was established—this document's full history has zero hits
for `**4.7` / `**4.8` / `**8.1` headings (verifiable via
`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md`), and the whole repository has
no references. `8.1` corresponds to `05`'s phase 1 (test resurrection and completion): that phase
has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8's numbering aligns with its phase number
(phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**This document covers**: task breakdown, dependencies, parallel grouping, acceptance criteria
binding.

**This document does not cover**: task design rationale (see `02`–`08`), phase order justification
(see RFC-039).

**Registration convention (since 2026-10-12)**: Newly registered level 2/3 rows **must carry two
fields**—"**Belonging phase**" (which P it truly belongs to, may differ from the section it appears
in) and "**Whether it blocks the main line**"; `registration pending scheduling` is no longer the
default state, unmarked means **unschedulable**. Numbering must be **unique** within the entire
document (cross-track tasks use track numbers, e.g., `029g.x`, must not occupy `N.x`).
**Checkmarks/completion registration is based on "task id + evidence (gate value, run id, issue
number, file:line)"**, do not write commit hashes—`pull --rebase` rewrites local hashes, hardcoded
numbers will fail (2026-10-13 example: `94ad03ce4`→`631eb3e3c`). For commit hashes, check `git log`.

## Target Design: Phase Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Regulations  08        ← Newly added, establish rules first
P1  Resurrect Orphan Tests and Fix Defects          06 §S1
P2  Establish Equivalence Oracle Baseline           07 all
P3  Fix Correctness Vulnerabilities (Minimal Solution)  02 §S3-Vulnerability Half
P4  Stage Contract and Unified Driver               02
P5  checker File Internal Splitting                 02 + supplemented by this document
P6  Type Representation Unification                 03
P7  Intermediate Representation SSA-ification        04      } Can be parallel
P8  Frontend Paradigm Change                        05      }
P9  Anti-Rebound Gates (including Unified Script List)  01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Other Cleanup and State Correction              06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (must not fabricate / must not fill endlessly /
should refactor but instead patched) constrain every action in P1–P10. Rules must be established
before construction begins, otherwise when P1 resurrects tests, `mod` declarations are already being
added to `tests/mod.rs`—that is precisely the cause of the G4 conflict.

## Key Decisions and Reasons

- **P0 independent as phase not merged into P9**——gate is "post-check", regulation is
  "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as CI scripts' only authoritative list**——original gap G3's three coexisting lists led to
  unable to close. This table after merge 11 scripts each attributed to one phase, report-only and
  convert-to-hard timing explicitly queryable.
- **P3.5 incorporates RFC-029g instead of leaving as "independent track, wait until after
  refactoring"**——its deletion surface overlaps with P4/P5/P6/P7/P8's rewrite surface (RFC-039 D56).
  Leave until after refactoring, equals redo same batch of deletion on new grammar, new checker
  layout and new IR; this is the same lesson as 7e incorporates `2315`/`2341`, S4 incorporates RFC
  state correction.
- **P5's steps supplemented by this document not merged into P4**——P4 is already the largest
  single-point risk, further overlay checker split will exceed rollback granularity.
- **5.3.2 takes "zero caller change" as hard acceptance**——split must be independently revertible.
