> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding the RFC’s phase sequence into **three-level tasks that can be committed and verified
> independently**.
>
> RFC-039’s main text is the sole authority for phase ordering and acceptance gates. This document
> is responsible only for breaking the work down into an executable granularity and recording
> conflicts that remain undecided.

**Reserved numbers (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three
has had a corresponding entry since the WBS was established—the entire history of this document has
zero matches for the `**4.7` / `**4.8` / `**8.1` headings
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used for verification),
and the repository contains no references to them. `8.1` corresponds precisely to phase 1 of `05`
(test revival and completion): that phase has been split into P1 (`1.1`–`1.3`) and `8.8`, so P8’s
numbering is aligned with its phase number (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependencies, parallelization groups, and
acceptance-criterion bindings.

**Not covered by this document**: the design rationale for tasks (see `02`–`08`) or the rationale
for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: Every newly registered level-2/level-3 row
**must contain two fields**—“**Owning phase**” (the P to which it truly belongs, which may differ
from its section) and “**Blocks the mainline**”; `registered, awaiting scheduling` is no longer the
default state, and an unmarked task is deemed **not schedulable**. Numbers **must be unique
throughout the document** (tasks on different tracks use their track number, such as `029g.x`, and
must not occupy an `N.x` number). **Checkoff/completion registration is based on “task ID + evidence
(gate values, run ID, issue number, file:line),” not commit numbers**—`pull --rebase` rewrites local
hashes, so hard-coded numbers inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Look up commit numbers with `git log`.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions (do not invent; do not pad indefinitely; do not
patch what should be refactored) constrain every action in P1–P10. The rules must be established
before work begins; otherwise, while reviving tests in P1, people would already be adding `mod`
declarations to `tests/mod.rs`—precisely the cause of the G4 conflict.

## Implementation Points: Dependencies and Parallelization

### Mandatory Serial Main Chain

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 hemorrhage-stopping path (decision 2026-10-05)**: P3’s prerequisites are narrowed to
> **2.3.2 + 2.4.1 + 2.4.3** (multi-file corpus layer + two red criteria). The rest of P2 (2.1 IR
> verifier, 2.2 snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in
> parallel with P3. Stopping correctness vulnerabilities must not be blocked by
> criterion-infrastructure construction; however, **P4 must still wait for all of P2**—the unified
> Driver requires all three layers of criteria to be in place.

| Constraint                | Reason                                                                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P0 → P1                   | The three prohibitions constrain every P1 action (1.2.x adds `mod` declarations to `mod.rs`)                                                                                                                                                           |
| P1 → P2                   | Reviving tests changes the test count and corpus baseline                                                                                                                                                                                              |
| P2 (after narrowing) → P3 | Vulnerability criteria must be **written in red first** (2.4.1/2.4.3) + the multi-file corpus layer (2.3.2) must exist so the red tests have somewhere to run                                                                                          |
| P3 → P4                   | Fix bugs before refactoring; reversing the order would cause bugs to become固化 as “established behavior” in the phase table                                                                                                                           |
| P3.5 → P4                 | RFC-029g (#399)’s deletion surface covers P4 4.2.2 / P5 / P6 / P7 / P8’s respective rewrite targets (the list appears in §P3.5 of this document)—reversing the order means redoing the same deletions on the new grammar, checker layout, and IR (D56) |
| P4 → P5                   | The `include!` refactoring and checker decomposition modify the same file                                                                                                                                                                              |
| P5 → P6                   | Consecutive changes to the same file must be separated; otherwise regressions cannot be localized by bisection                                                                                                                                         |

| P7/P8 → P9                | The 9.5 snapshot baseline and 9.3 `pub(crate)` leak count reach their final form only after P7/P8                                                                                                                                                      |

## Key Decisions and Rationale

- **P0 is a separate phase rather than part of P9**—gates are “post-hoc checks,” while rules are
  “prior judgment.” P9’s scripts cannot prevent “patching what should have been refactored”; only
  D0–D4’s review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the three coexisting lists in original gap G3
  prevented closeout. This table merges them: 11 scripts, each owned by one phase, with report-only
  status and hard-failure conversion points explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after
  refactoring”**—its deletion surface overlaps P4/P5/P6/P7/P8’s rewrite surfaces (RFC-039 D56).
  Deferring it until after refactoring means redoing the same deletions on the new grammar, checker
  layout, and IR; this is the same lesson as incorporating `2315`/`2341` into 7e and RFC status
  corrections into S4.
- **P5’s steps are supplemented by this document rather than merged into P4**—P4 is already the
  largest single-point risk, and adding checker decomposition would exceed the granularity at which
  changes can be rolled back.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the decomposition must be
  independently revertible.
