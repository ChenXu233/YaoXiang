# Multi-level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the phase sequence of the RFC into **independently committable, independently verifiable**
> three-level tasks.
>
> The phase ordering and acceptance gates are governed solely by the body of RFC-039; this document
> is responsible only for breaking tasks down to an executable granularity and registering conflicts
> that have not yet been adjudicated.

## Position and Scope

| Level       | Quantity    | Meaning                                                                                                                                                                |
| ----------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Phases, corresponding one-to-one with the phase sequence in RFC-039                                                                                                    |
| **Level 2** | 48          | Task groups, drawn from the "Implementation Points" sections of each document + 2026-10-07 audit addendum (P3's 3.4) + 2026-10-10 adjudication addendum (P3's 3.5/3.6) |
| **Level 3** | 134         | Independently committable actions                                                                                                                                      |

**This document covers**: task decomposition, dependency relationships, parallel grouping, and
binding of acceptance criteria.

**This document does not cover**: the design rationale of the tasks (see `02`–`08`), or the
argumentation for the phase ordering (see RFC-039).

## Target Design: Phase Sequence

```
P0  Repository maintenance mechanism and code placement rules     08        ← New, set rules first
P1  Revive orphan tests and fix defects           06 §S1
P2  Establish equivalence oracle baseline             07 entire
P3  Fix correctness vulnerabilities (minimum solution)        02 §S3-vulnerability half
P4  Stage contract and unified Driver          02
P5  checker in-file split             02 + filled in by this document
P6  Unify type representation                 03
P7  SSA-ify intermediate representation                04      } Parallelizable
P8  Frontend paradigm change                   05      }
P9  Anti-rebound gates (including unified script list)     01 §Anti-rebound + 08 §Machine-checkable rules
P10 Other cleanup and status corrections             06 §S2/S3/S4/S5/S6
```

**Rationale for the new P0**: The three prohibitions (no invention / no endless padding / patching
when refactoring is warranted) constrain every action of P1–P10. The rules must be set before
construction begins; otherwise, when P1 revives tests, one will already be adding `mod` declarations
to `tests/mod.rs` — which is exactly what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 as independent phase rather than merged into P9** — gates are "post-hoc check", regulations
  are "ex-ante judgment". P9's scripts cannot prevent "patching when refactoring is warranted", only
  D0–D4's review checklist can.
- **P9 as sole authoritative list of CI scripts** — original gap G3's three parallel lists made
  closure impossible. After this table merges, 10 scripts each attributed to one phase, report-only
  and harden timing explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactoring"** —
  its deletion surface overlaps with P4/P5/P6/P7/P8's rewriting surface (RFC-039 D56). Leaving for
  post-refactoring execution equals redoing the same batch of deletion on new grammar, new checker
  layout, and new IR; this is the same lesson as 7e incorporating `2315`/`2341`, S4 incorporating
  RFC status corrections.
- **P5's steps filled in by this document rather than merged into P4** — P4 is already the largest
  single point of risk, stacking checker split would exceed revertible granularity.
- **5.3.2 uses "zero caller change" as hard acceptance** — split must be independently revertible.
