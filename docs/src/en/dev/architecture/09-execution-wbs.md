# Multi-Level Implementation Work Breakdown Structure (WBS)

> **Supporting design document**. This document accompanies
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md) and
> expands the RFC’s stage sequence into **three-level tasks that can be committed and validated
> independently**.
>
> RFC-039’s main text is the sole authority for stage order and acceptance gates. This document is
> responsible only for decomposing the work to an executable granularity and recording conflicts
> that have not yet been adjudicated.

**Unassigned numbers (not recycled)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the three
has had a corresponding entry since the WBS was established—the document’s entire history has zero
matches for the three headings `**4.7` / `**4.8` / `**8.1`
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used to verify this),
and there are no repository-wide references either. `8.1` corresponds precisely to stage 1 of `05`
(test revival and completion). That stage has been split into P1 (`1.1`–`1.3`) and `8.8`; therefore,
P8’s numbering aligns with its stage numbers (stage 0 → `8.0`, stage 2 → `8.2`, and so forth).

**Covered by this document**: task decomposition, dependency relationships, parallelization groups,
and binding of acceptance criteria.

**Not covered by this document**: the design rationale for tasks (see `02`–`08`) or the
justification for stage order (see RFC-039).

**Registration convention (effective 2026-10-12)**: every newly registered second-/third-level row
**must contain two fields**—“**Owning stage**” (the P stage to which it truly belongs, which may
differ from its containing section)—and “**Blocks the mainline**”; `pending scheduling` is no longer
the default state, and an unmarked item is deemed **not schedulable**. Numbers must be **unique
throughout the document** (tasks on different tracks use the track number, such as `029g.x`, and
must not occupy an `N.x` number). **Check-off/completion registration is based on “task ID +
evidence (gate value, run ID, issue number, file:line)” rather than a commit
number**—`pull --rebase` rewrites local hashes, so hard-coded numbers will inevitably become invalid
(2026-10-13 example: `94ad03ce4`→`631eb3e3c`). Use `git log` to look up commit numbers.

## Target Design: Stage Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions (do not invent; do not pad endlessly; do not
patch what should have been refactored) constrain every action in P1–P10. The rules must be
established before work begins; otherwise, P1 would already be adding `mod` declarations to
`tests/mod.rs` while reviving tests—which is precisely the cause of the G4 conflict.

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

## Key Decisions and Rationale

- **P0 is an independent stage rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-hoc judgment.” P9’s scripts cannot prevent “patching what should have been refactored”; only
  the D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the original gap G3’s three concurrent lists
  made closure impossible. This table merges them into 11 scripts, each owned by one stage, with
  report-only status and strict-mode timing explicitly visible.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to execute after the
  refactoring”**—its deletion surface overlaps the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactoring means repeating the same deletions on the new grammar,
  new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341` into 7e and
  RFC-status corrections into S4.
- **P5’s steps are filled in by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding checker decomposition would exceed the granularity at which work can
  be rolled back.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the decomposition must be
  independently revertible.
