# Multi-Level Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC’s phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> The phase order and acceptance gates are governed solely by the main body of RFC-039. This
> document is responsible only for decomposing the work into executable granularity and recording
> conflicts that have not yet been adjudicated.

has had a corresponding entry since the WBS was established: the full history of this document has

and there are no references anywhere else in the repository. `8.1` corresponds precisely to phase 1
of `05` (test resurrection and completion): that phase was split into P1 (`1.1`–`1.3`) and `8.8`, so
P8’s numbering aligns with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so forth).

**Covered here**: Task decomposition, dependencies, parallelization groups, and bindings to
acceptance criteria.

**Not covered here**: The design rationale for tasks (see `02`–`08`) or the rationale for phase
ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: Newly registered Level 2/3 rows **must contain
two fields**—“**Owning phase**” (the P to which the task truly belongs, which may differ from the
section containing it) and “**Blocks the main line**”; `Pending scheduling` is no longer the default
state, and an unmarked task is considered **not schedulable**. Numbers must be **unique throughout
the document** (tasks on different tracks use a track number, such as `029g.x`, and must not occupy
an `N.x` number). **Checkoff/completion registration is based on “task id + evidence (gate metric,
run id, issue number, file:line)” rather than commit hashes**—`pull --rebase` rewrites local hashes,
so hard-coded hashes inevitably become invalid (example from 2026-10-13: `94ad03ce4`→`631eb3e3c`).
Use `git log` to find commit hashes.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: The three prohibitions—no fabrication, no endless filling, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before implementation begins; otherwise, while resurrecting tests in P1, work would already be
adding `mod` declarations to `tests/mod.rs`, which is precisely the cause of the G4 conflict.

`P0 → P1 → P2 → P3 → P3.5 → P4 → P5 → P6 → (P7 ∥ P8) → P9 → P10`

> **P3 emergency path (decision on 2026-10-05)**: P3’s prerequisites are narrowed to **2.3.2 +

> snapshots, 2.3.1/2.3.3 differential and performance baseline) can proceed in parallel with P3.

## Key Decisions and Rationale

- **P0 is an independent phase rather than part of P9**—gates are “post-hoc checks,” while rules are
  “pre-implementation judgment.” P9’s scripts cannot prevent “patching when a refactor is required”;
  only the D0–D4 review checklist can.
- **P9 is the sole authoritative list of CI scripts**—original gap G3’s three coexisting lists
  prevented closure. This table merges them, with 11 scripts each owned by one phase and explicit
  report-only and hard-conversion timing.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to do after the
  refactor”**—its deletion surface overlaps the rewrite surface of P4/P5/P6/P7/P8 (RFC-039 D56).
  Deferring it until after the refactor means repeating the same deletions on the new grammar,
  checker layout, and IR; this is the same lesson as incorporating `2315`/`2341` into 7e and RFC
  status correction into S4.
- **P5’s steps are supplied by this document rather than folded into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the rollback granularity.
- **5.3.2 uses “zero caller changes” as hard acceptance**—the split must be independently
  revertible.
