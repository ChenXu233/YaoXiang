# Multi-Level Construction Task Table (WBS)

> **Subsidiary design document**. This document is a subsidiary of
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md),
> expanding RFC's stage sequence into **independently committable, independently verifiable**
> three-level tasks.
>
> Stage order and acceptance gates use RFC-039 body as the sole authority; this document is only
> responsible for breaking down to executable granularity, and registering unresolved conflicts.

| Level       | Quantity    | Meaning                                                                                                                                                       |
| ----------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Level 1** | 11 (P0–P10) | Stages, one-to-one correspondence with RFC-039's stage sequence                                                                                               |
| **Level 2** | 50          | Task groups, from each document's "Implementation Points" + 2026-10-07 audit additions (P3's 3.4) + 2026-10-10/11 ruling registrations (P3's 3.5/3.6/3.7/3.8) |

binding.

stage ordering (see RFC-039).

## Goal Design: Stage Sequence

```
P0  Repository Maintenance Mechanism and Code Placement Regulations  08        ← New, establish rules first
P1  Resurrect Orphan Tests and Fix Defects                            06 §S1
P2  Build Equivalence Oracle Baseline                                07 all
P3  Fix Correctness Vulnerabilities (Minimal Solution)               02 §S3-Vulnerability Half
P4  Stage Contract and Unified Driver                                02
P5  Checker File-Internal Split                                      02 + filled in by this document
P6  Type Representation Unification                                  03
P7  Intermediate Representation SSA-ization                           04      } Can be parallel
P8  Frontend Paradigm Change                                         05      }
P9  Anti-Rebound Gates (including unified script list)               01 §Anti-Rebound + 08 §Machine-Checkable Rules
P10 Other Cleanup and Status Correction                              06 §S2/S3/S4/S5/S6
```

**Reason for adding P0**: The three prohibitions (must not invent / must not fill endlessly / should
refactor but patched) constrain every action in P1–P10. Rules must be established before starting
work, otherwise when P1 resurrects tests, it will already be adding `mod` declarations to
`tests/mod.rs` — that is precisely the cause of G4's conflict.

## Key Decisions and Reasons

- **P0 independent as stage rather than merged into P9** — gates are "post-hoc check", regulations
  are "pre-judgment". P9's scripts cannot prevent "should refactor but patched", only D0–D4's review
  checklist can.
- **P9 as sole authority list of CI scripts** — original gap G3's three coexisting lists led to
  inability to close. This table after merge 10 scripts each attributed to one stage, report-only
  and hard-convert time point explicitly queryable.
- **P3.5 incorporates RFC-029g rather than leaving as "independent track, do after refactor"** — its
  deletion face overlaps with P4/P5/P6/P7/P8's rewrite face (RFC-039 D56). Leaving for after
  refactor execution, equals doing the same batch of deletion again on new grammar, new checker
  layout and new IR; this is the same lesson as 7e collecting `2315`/`2341`, S4 collecting RFC
  status correction.
- **P5's steps filled in by this document rather than merged into P4** — P4 is already the largest
  single point risk, additionally stacking checker split would exceed rollback granularity.
- **5.3.2 with "zero caller change" as hard acceptance** — split must be independently revertible.
