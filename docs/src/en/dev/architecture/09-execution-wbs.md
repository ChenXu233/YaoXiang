# Multi-Level Implementation Work Breakdown Structure (WBS)

> **Companion design document**. This document is a companion to
> [RFC-039 Compiler Architecture Restructuring](../../rfc/accepted/039-compiler-architecture.md). It
> expands the RFC's phase sequence into **independently committable and independently verifiable**
> three-level tasks.
>
> RFC-039 remains the sole authority for phase ordering and acceptance gates; this document is
> responsible only for decomposition to an executable granularity and registration of conflicts that
> have not yet been adjudicated.

**Unassigned numbers (not reclaimed)**: P4 has no `4.7`/`4.8`, and P8 has no `8.1`. None of the
three has had a corresponding entry since the WBS was established—the entire history of this
document has zero hits for the `**4.7` / `**4.8` / `**8.1` headings
(`git log -S'**4.7' -- docs/src/dev/architecture/09-execution-wbs.md` can be used to verify this),
and there are no repository-wide references either. `8.1` corresponds precisely to phase 1 of `05`
(test revival and completion): this phase was decomposed into P1 (`1.1`–`1.3`) and `8.8`, so P8's
numbering aligns with its phase numbers (phase 0 → `8.0`, phase 2 → `8.2`, and so on).

**Covered by this document**: task decomposition, dependency relationships, parallelization groups,
and binding of acceptance criteria.

**Not covered by this document**: the design rationale for tasks (see `02`–`08`) and the rationale
for phase ordering (see RFC-039).

**Registration convention (effective 2026-10-12)**: newly registered level-2/level-3 entries **must
contain two fields**—“**Owning phase**” (the P to which the task truly belongs, which may differ
from the containing section) and “**Blocks the mainline**”; `pending scheduling` is no longer the
default state, and an unmarked entry is deemed **not schedulable**. Numbers must be **unique
throughout the document** (tasks on different tracks use their track number, such as `029g.x`, and
must not occupy an `N.x` number). **Checkoff/completion registration is based on “task id + evidence
(gate values, run id, issue number, file:line)”**, not commit numbers—`pull --rebase` rewrites local
hashes, so hard-coded numbers inevitably become invalid (2026-10-13 example:
`94ad03ce4`→`631eb3e3c`). Use `git log` to look up commit numbers.

## Target Design: Phase Sequence

```
P0  仓库维护机制与代码放置规程     08        ← 新增，先立规矩
P1  复活孤儿测试并修缺陷           06 §S1
P2  建立等价性判据基线             07 全部
P3  修正确性漏洞（最小方案）        02 §S3-漏洞半部
P4  阶段契约与统一 Driver          02
P5  checker 文件内拆分             02 + 本文补齐
P6  类型表示单一化                 03
P7  中间表示 SSA 化                04      } 可并行
P8  前端范式变更                   05      }
P9  防反弹门禁（含统一脚本清单）     01 §防反弹 + 08 §可机检规则
P10 其余清理与状态修正             06 §S2/S3/S4/S5/S6
```

**Rationale for adding P0**: the three prohibitions—no invention, no endless filling, and no
patching when a refactor is required—constrain every action in P1–P10. The rules must be established
before implementation begins; otherwise, when P1 revives tests, it will already be adding `mod`
declarations to `tests/mod.rs`, which is precisely what caused the G4 conflict.

## Key Decisions and Rationale

- **P0 is established as an independent phase rather than merged into P9**—gates are “post-hoc
  checks,” while rules are “ex-ante judgment.” P9's scripts cannot prevent “patching when a refactor
  is required”; only D0–D4's review checklist can.
- **P9 is the sole authoritative list of CI scripts**—the three coexisting lists in original gap G3
  prevented closure. After this table merges them, each of the 11 scripts belongs to one phase, and
  the report-only status and hard-failure conversion points are explicitly traceable.
- **P3.5 incorporates RFC-029g rather than leaving it as an “independent track to be executed after
  the refactor”**—its deletion surface overlaps with the rewrite surfaces of P4/P5/P6/P7/P8 (RFC-039
  D56). Deferring it until after the refactor means repeating the same batch of deletions on the new
  grammar, new checker layout, and new IR; this is the same lesson as incorporating `2315`/`2341`
  into 7e and RFC status corrections into S4.
- **P5's steps are supplied by this document rather than merged into P4**—P4 is already the largest
  single-point risk, and adding the checker split would exceed the granularity at which changes can
  be rolled back.
- **5.3.2 uses “zero caller changes” as its hard acceptance criterion**—the split must be
  independently revertable.
