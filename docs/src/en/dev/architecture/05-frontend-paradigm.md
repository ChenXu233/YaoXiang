# Frontend Paradigm: Lexing and Parsing

> **Companion design document**. This article is a companion to
> [RFC-039 Compiler Architecture Refactoring](../../rfc/accepted/039-compiler-architecture.md). The
> four-layer model, acceptance-criteria tiers, and execution-stage order are defined in the main
> RFC-039 text; the positioning of each companion document is described in the
> [index for this directory](index.md).

## Positioning and Scope

This document covers the L2 frontend—**lexing (`src/frontend/core/lexer/`) and parsing
(`src/frontend/core/parser/`)**.

**Problem to solve:** Reduce the change surface for “adding a binary operator” from the current
**6–7 locations within L2 + 17 downstream production files**—of which the compiler enforces
approximately 8–9 locations while the rest require manual synchronization—to **1–2 declarations +
7–8 autogenerated locations**.

This document addresses the pain point identified for the “binary operator” row in RFC-039
functional routing table A. The refactoring category is **C5, frontend paradigm change**, as defined
in [07-equivalence-oracle.md](07-equivalence-oracle.md) (criteria: identical AST snapshots +
identical diagnostics + identical behavior, all three required), together with **C6, pure
deletion**, which requires no equivalence criteria beyond confirmation that there are no references.
C6 items are prerequisites for C5: delete 96 lines of dead code, eliminate three bare magic numbers,
and revive 629 lines of lexical tests that have never run.

**Scope boundary:** The disposition of `ast::Type` (26 variants) and the convergence of three
parallel type representations belong in [03-type-unification.md](03-type-unification.md). This
document does not duplicate that work; it only declares the interface boundary in the “Detailed
Design” section.

### Why This Is Worth Doing

“Adding an operator” is the most expensive change in the frontend. This tax has **three pathological
characteristics**:

**First, the cost does not decrease with experience.** Someone who has added an operator ten times
will not need to change one fewer location than someone who has added one only once, because there
is no inferable relationship among these locations. The `(6,7)` in `led.rs:40` and the `12` in
`nud.rs:1041` have no connection to each other, but they must agree or expression parsing will fail.

**Second, missed changes fall into two categories, and the compiler cannot catch the worst
category.** See the layered table in “The Change Surface for Adding an Operator”: an omitted arm in
an exhaustive `match` is caught by the compiler, whereas **the compiler can never catch a missed
update across enums**.

**Third, this tax is invisible in the ledger.** Almost every commit shown by
`git log --oneline -- src/frontend/core/parser/pratt/led.rs` touches 3–4 files simultaneously, but
no tool can identify which location a given commit failed to update.

### Correct Patterns Already Present in This Repository

The project already has two **correct solutions to the same class of problem**, both of which can be
reused directly:

- **Error codes:** `build.rs:19-55` uses `tools/code-tables` to parse the registry at **build
  time**, verify uniqueness, and compare every entry against RFC-013’s Markdown code table. **Any
  inconsistency immediately triggers `panic!` and rejects the build.** The cost of adding an error
  code is therefore constant at one location plus documentation.
- **Standard-library interfaces:** `gen_interfaces.rs` performs byte-for-byte comparisons, while
  `gen_docs.rs` provides marked-range drift detection (the last row of RFC-039 routing table B).

Both mechanisms share the same principle: **turn “changes that must be synchronized” from something
people must remember into an executable assertion**. The entire goal of this document can be reduced
to a single statement: make the relationships among the operator table, lexer rule table, and AST
variant table into executable assertions.

### Why “Only Deleting Dead Code” Is Not Enough

Dead code does exist (`precedence.rs`, 96 lines; the empty `skip_old_function_syntax` function; and
629 lines of orphan tests), but deleting it will not reduce the number of locations affected by
adding an operator by even one. Dead code is **legacy debt**, while the cross-file change surface is
a **structural cost**. The two must be handled separately; see “Key Decisions and Rationale” for
their disposition.

### Lexer Layer: Copy-and-Paste Evidence in `literals.rs`

`src/frontend/core/lexer/literals.rs` contains **1,568 lines** in total. This size does not come
from complexity; it comes from three structural duplications.

**Duplication 1: Four radix scanners are nearly identical line for line.**

| Scanner               | Line range            | Lines |
| --------------------- | --------------------- | ----- |
| `scan_hex_number`     | `literals.rs:77-161`  | 85    |
| `scan_octal_number`   | `literals.rs:164-247` | 84    |
| `scan_binary_number`  | `literals.rs:250-333` | 84    |
| `scan_decimal_number` | `literals.rs:336-516` | 181   |

The first three are each about 84 lines and have exactly the same structure: accumulate digit →
`has_digits` check → `overflow` flag → `checked_mul(base)` → `checked_add` → `try_into` → report
error. **The only differences are the base constant and the digit-extraction expression.** Across
three copies of roughly 84 lines, **about 250 lines are pure redundancy**. (`scan_decimal_number`
must be listed separately because it additionally handles decimal points and exponents and therefore
cannot be merged.)

A representative example is the overflow path in `scan_hex_number` (`literals.rs:134-141`):

```rust
if overflow {
    lexer.error = Some(crate::frontend::core::lexer::LexError::InvalidNumber(
        value,
        point(lexer),
    ));

    return Some(lexer.make_token(TokenKind::Error("Hex number too large".to_string())));
}
```

`scan_octal_number:220-227` and `scan_binary_number:306-313` are the same code with a different base
and message text.

**Duplication 2: Escape decoding is implemented three times.**

| Implementation               | Location                       | Length                                       |
| ---------------------------- | ------------------------------ | -------------------------------------------- |
| `\\` branch of `scan_string` | `literals.rs:694-827`          | 134 lines                                    |
| `\\` branch of `scan_char`   | `literals.rs:1015-1141`        | 127 lines                                    |
| `push_fstring_escape`        | Starting at `literals.rs:1374` | Already extracted into a standalone function |

The first two are near line-by-line copies of 127–134 lines (`'n'/'t'/'r'/'\\'/'"'/'\''/'0'` → same
push; identical `\x` / `\u{...}` logic; identical `c =>` error fallback), meaning **about 250 lines
have been written twice**.

One point deserves special mention: **the f-string version has already been extracted into a
standalone function** (`push_fstring_escape:1374`). This means **someone already recognized the
duplication and fixed it locally, but did not go back and converge the other two implementations**.
This is more noteworthy than “none of the three implementations recognized it”: it proves that the
problem is solvable and only lacks an enforcement mechanism.

**Duplication 3: Two implementations of multiline-string scanning.** `scan_multi_line_string:869`
and `scan_fstring_multi_line:1497` are two more implementations of the same kind.

**Anomalous formatting residue.** The two locations `literals.rs:777-787` and `1098-1108` each
contain 11 lines in which **three consecutive blank lines are inserted between every field of a
struct literal**. This is residue from an automated rewrite. Other fields in the same function
(`1111-1115`) have only one blank line between them, indicating that formatting was interrupted.

> This residue is harmless in itself, but it is a **diagnostic signal**: the same code was rewritten
> twice by different tools, meaning that someone once made a local patch here without pulling in the
> surrounding context.

**Conclusion:** Approximately 500 lines in `literals.rs` (250 lines of redundant radix scanning +
two copies totaling 250 lines of escape decoding) are **mechanical duplication**, not complexity.

**f-string interpolation triggers nested compilation.** This is **repeated compilation at runtime**,
not duplicate implementation, so it cannot be solved merely by merging functions.

`src/frontend/core/parser/pratt/nud.rs:441-446`:

```rust
let tokens_result = crate::frontend::core::lexer::tokenize(expr_str_trimmed);
match tokens_result {
    Ok(tokens) => {
        let mut parser = crate::frontend::core::parser::ParserState::new(&tokens);
        if let Some(expr) =
            parser.parse_expression(crate::frontend::core::parser::pratt::BP_LOWEST)
```

**The parser layer runs a complete `tokenize()` separately for every f-string interpolation at
runtime and creates a new `ParserState` for each one.**

Consequences: An f-string containing N interpolations **triggers N+1 complete lexical analyses** (N
interpolations + 1 outer scan). At the same time, each interpolation is an **independent parsing
context**, and therefore:

- Diagnostic spans inside an interpolation are relative to the interpolation text, so remapping them
  to source locations requires additional work.
- An interpolation cannot access any outer parser state. There is no current requirement for this,
  but the structure rules out future possibilities, such as referencing an outer implicit variable
  from within an interpolation.
- The locations at which lexical and syntactic errors are produced are split across two separate
  stages.

This is a **defect in both performance and structure**, and it must be addressed; see “Target Design
· Lexer”.

### Parser Layer: Two BP Ladders, Bare Magic Numbers, and Handwritten Dispatch Tables

#### The Two Ladders Are Not “One Live and One Dead”; They Are Interwoven

`src/frontend/core/parser/pratt/precedence.rs` contains **two binding-power ladders** whose
numbering overlaps extensively.

**The first ladder (`precedence.rs:6-17`)**: `BP_LOWEST=0` / `BP_ASSIGN=1` / `BP_LOGICAL_OR=2` /
`BP_LOGICAL_AND=3` / `BP_EQUALITY=4` / `BP_COMPARISON=5` / `BP_TERM=6` / `BP_FACTOR=7` /
`BP_UNARY=8` / `BP_CAST=8` / `BP_CALL=9` / `BP_HIGHEST=10`.

**The second ladder (`precedence.rs:22-31`)**: `BP_RANGE=7` / `BP_OR=1` / `BP_AND=2` / `BP_EQ=3` /
`BP_CMP=4` / `BP_BIT=5` / `BP_SHIFT=6` / `BP_ADD=7` / `BP_MUL=8`.

**The measured conclusion is that both ladders survive in production code and are already interwoven
inside `infix_info` itself.**

- `infix_info` (`led.rs:30-88`) references **five constants from the first ladder**: `BP_ASSIGN`
  (`:33`), `BP_CALL` (`:75` / `:77` / `:79` / `:83`), and `BP_CAST` (`:81`);
- It references **eight constants from the second ladder**: `BP_OR` (`:42`), `BP_AND` (`:44`),
  `BP_EQ` (`:47`), `BP_SHIFT` (`:51` / `:54`), `BP_BIT` (`:58`), `BP_CMP` (`:62` / `:65`), `BP_ADD`
  (`:68`), and `BP_MUL` (`:72`);
- **The only dead member of the second ladder is `BP_RANGE`**: `..` uses the bare literal `(6, 7)`
  in `led.rs:40` instead of `BP_RANGE`; in production code, `BP_RANGE` appears only in the comment

#### Numeric Collisions

The numbering in the overlapping portions of the two ladders corresponds almost digit for digit, so
**cross-ladder collisions occur in pairs**:

| Collision                 | Value    | Usage site A (first ladder)    | Usage site B (second ladder)   |
| ------------------------- | -------- | ------------------------------ | ------------------------------ |
| Assignment vs. logical OR | `1 == 1` | `BP_ASSIGN` (`led.rs:33`)      | `BP_OR` (`led.rs:42`)          |
| Cast vs. multiplication   | `8 == 8` | `BP_CAST` (`led.rs:81`)        | `BP_MUL` (`led.rs:72`)         |
| Shift vs. term            | `6 == 6` | `BP_TERM` (dead)               | `BP_SHIFT` (`led.rs:51`/`:54`) |
| Bitwise vs. comparison    | `5 == 5` | `BP_COMPARISON` (comment only) | `BP_BIT` (`led.rs:58`)         |

**The first ladder also collides internally:** `BP_UNARY=8` and `BP_CAST=8` (`precedence.rs:14` and
`:15`) give **two different meanings in the same ladder the same value**, and both are live, being
used respectively for prefix binding in `nud.rs` and for casts in `led.rs:81`. The second ladder
also collides internally: `BP_RANGE=7` and `BP_ADD=7`.

**The system does not currently fail because of an unwritten convention:** almost every infix
operator uses `bp_right = bp_left + 1`, causing the right operand to accept only operators with
**strictly higher** binding power. This actually produces **left associativity** (`a - b - c` →
`(a-b)-c`). Therefore, the only effective comparison, “compare `bp_left`,” will not fail merely
because two operators have equal binding power. `led.rs:85` uses `(11, 1)` for `FatArrow`; its
`bp_right` is lower than its `bp_left`, making it the only explicit implementation in which the
“right operand greedily consumes” (the lambda body is maximized to the right).

This is **accidentally correct**: it relies on the facts that “`infix_info` returns a unique
`bp_left`” and that “`parse_expression_internal:100` compares only `bp_left`.” If any location is
changed to use `bp_left == bp_right` to determine associativity, the collisions will immediately
become visible.

#### Three Bare Magic Numbers

| Magic number | Location                             | Problem                                                                                                                      |
| ------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `(6, 7)`     | `led.rs:40` `TokenKind::DotDot`      | A literal binding-power pair with no name; it also **does not use `BP_RANGE` from the same ladder**, making `BP_RANGE` dead. |
| `(11, 1)`    | `led.rs:85` `TokenKind::FatArrow`    | 11 **exceeds the upper bound of either ladder** (the first ladder has `BP_HIGHEST=10`).                                      |
| `12`         | `nud.rs:1041` `parse_expression(12)` | **Greater than `BP_HIGHEST=10`**, used for RFC-010b mode probing.                                                            |

The comment at `nud.rs:896-901` candidly explains the origin of the magic number: _“Lambda binding
power is 11, so we use 12 to stop before =>”_ and _“parse_expression(12) stops `ok` as a bare Var
and turns `(` into an unexpected token”_. In other words, **this 12 was found empirically rather
than derived**.

#### Dispatch Is a Handwritten `match`

**Dispatch mechanism:** Everything is a handwritten `match` returning a function pointer, **with no
macros, tables, or generators**.

- `parse_prefix` (`nud.rs:14-19`) obtains the `prefix_info()` closure;
- `parse_expression_internal` (`pratt/mod.rs:79-113`) loops over the
  `(bp_left, bp_right, parser_fn)` triples returned by `infix_info()`;
- Two handwritten tables exist: `infix_info` (`led.rs:30-88`) and `prefix_info` (`nud.rs:26-75`).

#### `parse_assign_after_target`: A Misleadingly Named, 507-Line General Dispatcher

`parse_assign_after_target` at `src/frontend/core/parser/statements/declarations.rs:136` has a
function body extending to `:642` (**507 lines**, in a file totaling 1,015 lines).

Despite its name, “assign after target” is **the general dispatcher for declaration forms**. It
contains eight independent responsibility sections: old-syntax probing / three-level nested
lookahead for annotation disambiguation / declaration legality / semantic side effects / type-body
parsing fallback / RFC-010 lambda signature parameter reconstruction / MetaType definition /
ordinary initialization.

Its growth has three overlapping causes.

**Cause 1: Approximately 120 lines for a dead language feature.**

`is_old_function_syntax` (`declarations.rs:82-117`), `skip_old_function_syntax`
(`declarations.rs:120-122`), and the supporting lookahead at `:145-167`.

The precise explanation is important: **these two functions are not unreferenced**. They are called
at `declarations.rs:719` and `:725` from `parse_identifier_stmt`. The path is “detect `identifier(`
followed by type parameters and `->` → report ‘old syntax is deprecated’ → skip → return None.”

The accurate description is therefore: **this is a still-running gate that rejects removed syntax**,
with approximately 120 lines of overhead spent performing a parenthesis-balancing scan for every
statement beginning with `identifier(`.

Specifically:

- The body of `skip_old_function_syntax` (`:120-122`) contains only the comment
  `// 旧语法已移除，此函数不再需要` and is a **pure empty function**;
- More importantly, after calling it (`:725-726`), the code directly executes `return None`
  **without consuming any token**. In other words, this “skip” **does not actually skip anything**:
  the subsequent tokens remain in the stream and can only be handled by the caller’s error recovery.
  This is an interface whose name does not match its behavior.

**Cause 2: Lookahead logic is not abstracted.** “Skipping balanced parentheses” is **handwritten
four times** in the same file:

| Location                           | Line range                |
| ---------------------------------- | ------------------------- |
| Inside `is_old_function_syntax`    | `declarations.rs:96-105`  |
| Inside `parse_assign_after_target` | `declarations.rs:147-156` |
| Same                               | `declarations.rs:191-200` |
| Same                               | `declarations.rs:224-233` |

Each implementation is about 12 lines and has the same structure: `paren_depth = 1` →
`while paren_depth > 0 && !at_end()` → increment on `LParen`, decrement on `RParen` → `bump()`. **No
code is shared among the four implementations.**

**Cause 3: Type-layer logic has leaked into the parser.** See RFC-039 routing table C:
`declarations.rs:27-80` calls the type-layer functions `is_type_param_annotation` /
`name_used_as_type`; `declarations.rs:498-509` hardcodes the `"Terminates"` string and calls
`typecheck::operator_interfaces::spec()`. **This belongs in 03-type-unification.md /
02-stage-contract.md.** This document does not duplicate that work; it only marks the boundary in
the “Detailed Design” section.

### The Change Surface for Adding an Operator

**The downstream change surface is much larger than expected.** `BinOp::` has **534 matches across
47 files** in the repository, including **17 production files**. More importantly, these files
consume **two unrelated `BinOp` enums**:

| Enum                | Definition                | Variant count                       | Production consumers (parentheses contain the number of `BinOp::` matches in that file)                                                                                                                                                                     |
| ------------------- | ------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ast::BinOp`        | `parser/ast.rs:191-213`   | 20                                  | `led.rs` (22), `nud.rs` (1), `checker.rs` (8), `inference/expressions.rs` (25), `inference/statements.rs` (5), `operator_interfaces.rs` (5), `ir_gen.rs` (23), `formatter/handlers/expr.rs` (25), `lsp/handlers/inlay_hint.rs` (4), `spawn/analysis.rs` (3) |
| `const_data::BinOp` | `types/const_data.rs:234` | Verified to exist (`Ne`, not `Neq`) | `const_data.rs` (36), `const_eval.rs` (64), `evaluator.rs` (13), `ownership.rs` (13), `termination.rs` (16), `proof/smt/translate.rs` (13), `proof/dep_graph.rs` (2)                                                                                        |

It has been verified that `src/backends/` has **zero matches** for either `BinOp` or `ast::`: the
interpreter consumes IR / bytecode and never sees the AST. All 17 production files therefore lie on
the L2 → L3 path.

**There is no `From`/`TryFrom` conversion between the two enums**—repository-wide searches for
`impl From<...BinOp`, `-> BinOp`, and `BinOp as` find no conversion implementation. The consequence
is that **every file that touches both must alias them at import time**: `const_eval.rs:19`
(`BinOp as AstBinOp`), `ir_gen.rs:2317` (`use ast::BinOp as B`), and `CEBinOp` / `ConstBinOp` in
test files.

> **This is the most important finding in this document.** When `ast::BinOp` gains a variant, **the
> compiler cannot remind us to update `const_data::BinOp`**, because they are independent types and
> each can compile successfully on its own. A missed update means that the constant-folding path
> does not understand the new operator while the type-checking and IR-generation paths do—**the same
> operator behaves differently in two subsystems, with no diagnostic whatsoever**.
>
> This is an order of magnitude more serious than missing an arm in a `match`. The latter is caught
> by exhaustive matching; the former cannot be caught.

**Whether “a missed update can go undetected” requires precise distinction**:

| Missed-update type                                      | Detected by the compiler? | Verified evidence                                                                                                                                                                       |
| ------------------------------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Missing arm in an exhaustive `match`                    | **Yes**                   | The `impl Display for BinOp` at `const_data.rs:291-317` is an 18-arm exhaustive match with no `_` fallback.                                                                             |
| Missing variant in a `matches!` macro enumeration       | **No**                    | The `is_arith` / `is_comparison` / `is_logical` / `is_bitwise` functions at `const_data.rs:263-288` are all partial `matches!` enumerations; adding a variant silently returns `false`. |
| Missing arm in a `match` with a `_` fallback            | **No**                    | The `_ => {}` at `ownership.rs:687` silently ignores a new variant.                                                                                                                     |
| Missed update across `ast::BinOp` / `const_data::BinOp` | **Never**                 | The two have no conversion and no common parent type, so the compiler cannot relate them.                                                                                               |

The accurate statement is therefore not “11 missed updates that nobody can detect,” but: **the
compiler covers the exhaustive-match portion; the cases that fail silently are `matches!` macros,
`_` fallbacks, and cross-enum updates.**

## Target Design

### Lexer: Declarative Design

#### Evaluation of Three Options

| Option                                                                | Cost of adding a token         | Can it eliminate the lexer’s three duplications? | Can it solve nested f-string compilation?   | Introduced dependency                                                          |
| --------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------ | ------------------------------------------- | ------------------------------------------------------------------------------ |
| **A. Generate a DFA with `logos`**                                    | 1 location (token declaration) | **Yes** (one copy each for escapes / numbers)    | No (interpolation requires manual handling) | Adds `logos`                                                                   |
| **B. Handwrite a DFA with `regex`**                                   | 1–2 locations                  | Partially                                        | No                                          | Adds `regex` (whether it is already a transitive dependency is **unverified**) |
| **C. Retain handwritten code and enforce convergence of duplication** | 1 location                     | **Yes** (manual extraction of common functions)  | **Yes** (requires explicit design)          | None                                                                           |

**Position: adopt C as the baseline, A as a conditional alternative, and reject B.**

Rationale:

1. **C can eliminate all approximately 500 lines of duplication in the lexer with zero new
   dependencies**, entirely within a controllable scope. The three escape decoders—`scan_string` /
   `scan_char` / `push_fstring_escape`—are merged into a **single**
   `decode_escape(lexer, &mut String, EscapeMode)`, and the four radix scanners into a **single**
   `scan_radix_number(lexer, Radix, String)`. This is a purely mechanical refactor whose criteria
   are C5’s “identical AST snapshots + identical diagnostics.”
2. **The capabilities of A (`logos`) are real**: it can converge escape decoding and number scanning
   to one implementation each. **However, it cannot solve nested f-string compilation**, which is
   the lexer’s most important defect. It also introduces a new dependency that changes the error
   type of `Literals` (the `InvalidEscape` / `InvalidNumber` variants of `LexError` must be
   remapped), which would **directly violate C5’s “identical diagnostics” criterion** unless an
   additional adapter layer were written—and that would introduce yet another manual synchronization
   point.
3. **B (a handwritten DFA using `regex`) is rejected**: it requires a handwritten state machine,
   with work comparable to A but far less control. If choosing between A and B, A must logically be
   selected; because this document advocates C first, there is no reason to select B.

> **Design judgment, not a verified fact**: A may be the better long-term form (a declarative token
> table is itself a form of enforcement that requires changing only one location). However, its
> migration cost and conflict with the “identical diagnostics” criterion make it unsuitable for this
> C5 change. If A is adopted later, it should be a separate proposal, using the test-revival results
> in this document as its safety net.

#### Nested f-String Compilation Must Be Addressed Explicitly

Regardless of whether A or C is selected, nested compilation must be solved. **Position: eliminate
runtime nested `tokenize()` calls and produce the result in a single lexical pass.**

The concrete approach is as follows: when `scan_string` encounters the `f"` prefix, it should
**within the same lexical scan** record the interpolation content as
`FStringSegment::RawText(String)` and **not** recursively call `tokenize()`. The actual tokenization
and parsing of the interpolation should be deferred until the parser first needs the f-string node,
and should:

- **Complete in one pass** (for N interpolations, perform one tokenization pass over the
  interpolation segments and cache the result as `Vec<Vec<Token>>`), reducing N+1 operations to 1;
- **Determine span mapping during lexing** by recording each interpolation’s absolute offset in the
  source file, rather than relying on the relative semantics of `Point`.

This change is **independent of the paradigm choice** and should be performed even if A is not
adopted.

### Parser: Complete Grammar-Driven Parsing (LALRPOP)

> **Decision (2026-10-03, ChenXu233): Adopt A (complete LALRPOP grammar-driven parsing); do not
> implement a partial lookup-table transformation.** A’s equivalence risk—the difference between
> LALRPOP’s error-recovery model and `synchronize()`, and whether the empirically discovered parsing
> behavior can be reproduced bit for bit—is resolved by the **double-parser differential** approach
> described below. Lookup-table transformation is an insufficient intermediate state.

#### Option Evaluation

| Option                        | Change surface for adding a binary operator | Can it eliminate BP conflicts?                                                                                       | Can it preserve `synchronize()` and error placeholders?                  | Conclusion                           |
| ----------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------ |
| **A. LALRPOP**                | 1 grammar location + 1 action location      | Yes (the LR table computes precedence automatically; conflicts are exposed at build time as grammar-conflict errors) | Requires a rewrite, but **error productions can be declared explicitly** | **Adopt**                            |
| **B. tree-sitter**            | 1 `grammar.js` location                     | Yes                                                                                                                  | Not applicable (produces a CST, not a domain AST)                        | **Reject**                           |
| C. Retain Pratt lookup tables | 2–3 locations                               | Yes                                                                                                                  | Yes                                                                      | **Reject** (insufficient; see below) |

**Reason for rejecting B, unchanged:** tree-sitter produces a general-purpose syntax tree, whereas
this project’s `Expr` / `StmtKind` are **domain ASTs carrying semantic information** (`Expr::Cast`
carries a target type, `Expr::FString` carries a segment list, and `Pattern::Struct` carries field
names). A CST → domain AST conversion still requires a complete mapping layer, so **tree-sitter
cannot eliminate it**. That would add a mapping layer of the same size as the existing 1,326-line
`nud.rs`.

**Reason for rejecting C:** Lookup-table transformation solves **synchronization**—one change
without omissions—but does not solve **maintainability**. The 22 variants of `Expr` would still
require 22 handwritten construction actions; merging the two BP ladders would still require changing
approximately 89 references; and structural problems such as using
`Expr::Lambda { body: empty Block }` as a parameter list (`nud.rs:505-514`) would remain entirely
untouched. **It is an unnecessary intermediate station between “fully handwritten” and “complete
grammar-driven.”**

#### Original Objections to A and How They Are Resolved

The original objection to A was **equivalence**, not insufficient capability:

- The “continue parsing as far as possible” semantics formed by `ParserState::synchronize()`
  (`parser_state.rs:170-186`) and the `Expr::Error` / `StmtKind::Error` placeholders use a different
  error-recovery model from LALRPOP (token insertion / deletion), so **the resulting diagnostic set
  must differ**.
- The `bp_left < min_bp` exit condition at `pratt/mod.rs:100-102` and the `parse_expression(12)`
  mode probe at `nud.rs:1041` are both **behaviors found empirically on particular inputs**, and
  reproducing them bit for bit requires proof for each one.

**Resolution: double-parser differential.** This does not rely on an argument that the criteria
“should be equivalent”; it relies on **running both parsers**:

| Step | Content                                                                                                                                                                               | What it proves                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 1    | Build the LALRPOP grammar and action code, **completely alongside the existing Pratt parser**, without changing any existing code                                                     | —                                                                                         |
| 2    | Run both parsers over 293 corpus files and everything under `src/std/tests`; normalize the AST according to the rules in [07](07-equivalence-oracle.md), then **compare bit for bit** | The AST equivalence of valid programs is demonstrated by measurement rather than argument |
| 3    | Switch traffic: change `parse()` in `parser/mod.rs` to invoke LALRPOP; retain Pratt as `parse_legacy()`                                                                               | —                                                                                         |
| 4    | Delete Pratt: `nud.rs` (1,326) + `led.rs` (495) + both BP ladders in `precedence.rs` + approximately 89 references                                                                    | —                                                                                         |
| 5    | Error recovery: reconstruct `synchronize()` and the `Expr::Error` / `StmtKind::Error` placeholders on the LALRPOP side using **explicit error productions**                           | See below                                                                                 |

**Step 2 is the core of the entire approach.** If any part of the AST for the 293 corpus files is
not equivalent, it will be discovered before traffic is switched. This is far stronger than manually
arguing case by case whether 89 references can reproduce the existing behavior, and its cost is
acceptable because it is run offline once.

#### Error Recovery: Fully Preserve C5 Without Relaxation

**Diagnostics must be identical entry by entry. This is a hard requirement, not negotiable.** The
approach is to **model the existing behavior explicitly in the grammar**:

| Existing behavior                                                                                                                          | LALRPOP equivalent                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ParserState::synchronize()` (`parser_state.rs:170-186`): after statement parsing fails, skip tokens forward until a synchronization point | Explicitly declare an “error → jump to synchronization-point set → continue” production in the grammar. **The skipped set must be identical token for token to the existing implementation.**  |
| `Expr::Error` / `StmtKind::Error` placeholders: allow the parser to continue constructing a “partial AST” after an error                   | Explicitly declare error-node productions. **The locations of downstream match arms remain unchanged** (if downstream code places `Error` in a wildcard arm, it will silently swallow errors). |
| Diagnostic code + span                                                                                                                     | **Identical entry by entry. Wording unchanged.**                                                                                                                                               |

**This is not “something that should be achievable.” It must be achieved.** LALRPOP permits explicit
error productions; the synchronization-point set from `synchronize()` can be written into the
grammar. If phases 3a/3b demonstrate that the existing diagnostics cannot be reproduced under
LALRPOP, **the correct action is to report that finding truthfully and reassess the approach,
including “retain Pratt,” not to modify the criteria.**

Migration destinations and dispositions:

| Item                                                          | Content                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Grammar file                                                  | `src/frontend/core/parser/grammar/yaoxiang.lalrpop` (new directory; see the target structure in [01](01-routing.md))                                                                                                                                              |
| Action code                                                   | `grammar/actions.rs`—move the construction of `Expr` / `StmtKind` from `nud.rs` / `led.rs`, **with one function per variant**                                                                                                                                     |

**Net effect:** Delete `nud.rs` (1,326) + `led.rs` (495) + both BP ladders in `precedence.rs` +

### Backward Compatibility

The aspect of lookup-table transformation most likely to break is **error recovery**. This project’s
recovery contract has three parts, each of which must be preserved.

**Contract 1: `ParserState::synchronize()` (`parser_state.rs:170-186`).** It skips tokens forward
until a synchronization point after statement parsing fails. **The C5 criteria require preserving it
and require its trigger timing and skipped set to remain exactly the same.** After migration to
LALRPOP, its call sites are driven by explicit error productions, while the function body and
synchronization-point set **remain unchanged line for line**. The semantics are reproduced by the
grammar, and the implementation is retained unchanged.

**Contract 2: The `Expr::Error` placeholder (`ast.rs:1048`, consumed by `pratt/mod.rs:72`) and the
`StmtKind::Error` placeholder (constructed by `parser/mod.rs:50`).** These placeholders allow the
parser to continue constructing a “partial AST” after an error, with downstream code skipping
through the `Error` branches. **The variants must be retained, and their positions in downstream
matches must also be retained**; if downstream code places `Expr::Error` in a wildcard arm, the
error will be silently swallowed.

**Contract 3: Diagnostic code, span, and order.** The comparison rules in the third layer of
07-equivalence-oracle.md sort the diagnostic list by `(code, span.file, span.line)` and **do not
include message text in the comparison**. This gives this document some latitude over wording, but
**code and span are immutable**.

**Special note on f-strings:** The interpolation refactoring changes spans from “relative to the
interpolation text” to “absolute offsets in the source file.” To satisfy Contract 3, **spans must be
recorded using absolute offsets during lexing** (Decision D25)—the `span.file/line` of diagnostics
inside an interpolation must not change as a result of this refactoring.

> **Disposition:** Before Phase 2, establish a baseline snapshot of “diagnostic spans inside
> f-string interpolations,” then compare it entry by entry after the refactoring. Any difference in
> `span.file/line` is an implementation defect that must be fixed; there is no option to “accept a
> span change.” (If measurement proves that the original interpolation spans were already wrong, the
> baseline-establishment phase will expose that fact. That is an independent pre-existing defect, to
> be fixed separately and not folded into this phase; it is not grounds for relaxing the criteria.)

## Key Decisions and Rationale

### Three Selected Decisions

| Decision                         | Selection                                                                                                       | Rationale                                                                                                                                                                                                                                                                                                                       |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lexer approach                   | Adopt “retain handwritten code + enforce convergence of duplication”; list `logos` as a conditional alternative | Eliminates approximately 500 lines of duplication with zero new dependencies; `logos` changes the `LexError` error type and cannot solve nested f-string compilation                                                                                                                                                            |
| **Parser approach**              | **Adopt complete LALRPOP grammar-driven parsing**; reject tree-sitter and “retain Pratt lookup tables”          | tree-sitter produces a CST, not a domain AST, and still requires a complete mapping layer; lookup-table transformation solves synchronization but not maintainability and is an insufficient intermediate state. ### Explanation of “Doing the Complete Thing”

Lookup-table transformation is an insufficient intermediate state: it solves synchronization, not
maintainability. “Waiting for the criteria to be relaxed and reassessing later” is passive waiting,
not an engineering decision. This document therefore adopts **complete grammar-driven parsing**,
with equivalence guaranteed by measurement through the double-parser differential described above.
**No relaxation is made at the diagnostic layer.**

**The cost of this change must be stated clearly**:

- Construction effort increases significantly: a grammar file must be built, the construction
  actions for 22 `Expr` variants moved, approximately 89 BP references consolidated, and error
  recovery rewritten.
- **The prerequisites become harder**: the 629 lines of frontend tests must be revived first (P1 in
  09), and normalized AST snapshots must be committed first (P2 in 09). Without both, the Step 2
  differential cannot begin.
- **One new dependency** (LALRPOP) is introduced, which is inconsistent with the lexer layer’s “zero
  new dependencies” direction.

**The benefit is certain**: “adding an operator” drops from 11 locations to 2, BP collisions change
from “accidentally correct” to “grammar-build-time errors,” and `Expr::Lambda` abuse, the
`parse_expression(12)` magic number, and approximately 120 lines of dead old-syntax probing
**disappear naturally**.

### Rejected or Downgraded Approaches

**A. Delete dead code only; make no paradigm change.** Verified as feasible, but insufficient to
solve the problem. Dead-code cleanup (approximately 130 lines + three magic numbers) can be
completed at **zero criterion cost** and should be done immediately. However, it does not reduce the
L2 change surface for “adding an operator” by even one location, and cross-enum missed updates
remain **completely untouched**. **Conclusion: adopt as Phases 0 and 1, but continue with
grammar-driven parsing. Treating A as the complete solution is false reassurance.**

**B. Retain Pratt and add tests only.** **Not adopted as a complete solution, but adopted as a
prerequisite.** Tests **cannot detect cross-enum missed updates**: the two enums can each compile
successfully, and whether the tests pass is unrelated to whether they are synchronized.
**Conclusion: adopt as Phase 1; reject as the complete solution.**

**C. Retain Pratt and transform it into lookup tables.** **Rejected** (2026-10-03). It is an
unnecessary intermediate station between “fully handwritten” and “complete grammar-driven”: the 22
variants of `Expr` still require 22 handwritten construction actions, the
`Expr::Lambda { body: empty Block }` abuse remains, the `parse_expression(12)` magic number remains,
and the 89 references required to merge the two BP ladders remain.

**D. Adopt tree-sitter.** **Rejected.** Tree-sitter’s incremental parsing offers no material benefit
for this project (full compilation on every run, 293-file corpus scale); it also produces a CST
rather than a domain AST and still requires a complete mapping layer, adding the same amount of code
outside `nud.rs`.

**E. Replace the handwritten lexer with `logos`.** **Conditionally not adopted.** **Prerequisites
for reassessment:** after Phase 2 completes and escape decoding has converged to a single
implementation, replacing that implementation with a `logos` callback will require substantially
less work.

### Net Benefit of the Approach

- **The change surface falls from “more than a dozen logic locations” to “1–2 declarative data
  locations + 7–8 generated locations.”** The compiler guarantees synchronization of the generated
  7–8 locations, so missed updates are no longer possible.
- **A class of defects that the compiler can never catch is eliminated.** Cross-enum missed updates
  (`ast::BinOp` vs. `const_data::BinOp`) are currently the only defect type for which **no tool can
  provide any detection**, because the two types are independent. Same-source generation eliminates
  them directly.
- **BP collisions change from “accidentally correct” to “compilation failure.”** The existing four
  cross-ladder collisions and two within-ladder self-collisions currently survive by chance through
  the unwritten `bp_right = bp_left + 1` convention. Within-layer uniqueness assertions ensure that
  such problems can never again exist silently.
- **Frontend testing changes from “one file running” to “everything running.”** Once the 629 lines
  of existing tests are revived, Phases 2–4 have a safety net. These tests **already existed**; only
  one `mod` declaration was missing.
- **Phases 0 and 1 carry zero risk and zero criterion cost.** Dead-code deletion and test revival
  can proceed immediately without blocking any other work.

## Known Limitations and Risks

### Design Risks

- **The operator table is a new “thing that must be maintained.”** It turns “change 11 locations”
  into “change one location and maintain a table.” **If the table’s fields are poorly designed, it
  can degenerate into a new centralized maintenance burden.** This is the primary risk of the
  approach; the mitigation is to protect every column of the table with compile-time assertions.
- **The risk of renumbering BP is asymmetric.** Merging the two ladders requires renaming
  approximately 89 production references. If any one is missed, **associativity may change
  silently**—there is no error, only a different expression parse result. This is the silent
  regression most likely to be introduced by this document and must be guarded by Phase 1’s
  layer-pair associativity cases.
- **The C5 criterion cost for Phases 2–4 is high.** Using all three layers means every commit must
  run the full corpus (293 `.yx` files) + AST snapshots + diagnostic comparison. This will make
  every Phase 2–4 commit relatively heavy.
- **The f-string span change may not be entirely avoidable.** See “Backward Compatibility”; it may
  be necessary to accept one known behavioral change and update the baseline.

   cross-file rename in the C5 category.
2. **The second ladder has a dead member of its own.** `BP_RANGE` (`precedence.rs:22`) has zero

Additional correction: `bp_right = bp_left + 1` produces **left associativity** (`a - b - c` →
`(a-b)-c`), not right associativity; `(11, 1)` at `led.rs:85` is the only explicit
right-operand-greedy implementation. There are also more than the two initially noted cross-ladder
collisions: `BP_UNARY=8 == BP_CAST=8` (a within-first-ladder self-collision; both are live) and
`BP_RANGE=7 == BP_ADD=7` (a within-second-ladder self-collision).
