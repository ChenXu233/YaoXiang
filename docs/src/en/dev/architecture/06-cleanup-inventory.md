## Positioning and Scope

This document provides the YaoXiang repository's dead code and hollow design inventory, judgment
methods, item-by-item disposition decisions, and execution order. There are four categories of
cleanup targets:

| Category                                                                | Scale                                                                      |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Files that never participated in compilation                            | 24 files / 2628 lines (of which 23 files / 1081 lines are genuine orphans) |
| Compiled but with zero calls — dead code                                | 1500+ lines                                                                |
| Design documents describing architectures that never existed            | 3 documents in `docs/src/dev/design/check/`                                |
| Features attached to the default entry, with zero tests and zero output | `src/repl/` 1152 lines                                                     |

**The authorization scope is "permitted to delete outright"** (decision of 2026-10-03). However,
this document gives **disposition recommendations contrary to "direct deletion"** for several items
— see [Key Decisions and Rationale](#key-decisions-and-rationale) for the reasons.

This document **does not cover**: module boundaries and dependency directions (see `01-routing.md`),
stage contracts (see `02-stage-contract.md`), and criterion design (see `07-equivalence-oracle.md`).
The B3-recorded `layers/dispatch.rs` entire chain is unwired; its deletion falls under S2.

## Current State

### Three Liability Forms of Dead Code

**Form 1: Placeholder.** The code exists, looks like it's doing something, but actually doesn't.

- The entire chain in `src/frontend/core/typecheck/layers/dispatch.rs` (`dispatch` /
  `dispatch_pipeline` / `DispatchMode` / `RuntimeOutcome::InsertCheck`) has **zero calls** in the
  compiler. It is the "runtime check insertion" mechanism designed in `RFC-027 §4.1`, and is
  **completely unwired**.
- `check_type_equivalence` at `src/frontend/core/typecheck/layers/equivalence.rs:216` (the
  `ProofContext` entry) is only called by tests. **Note** that `is_subtype` in the same file is used
  in production by `inference/assignment.rs:17`, so **the entire file cannot be deleted**.
- `src/backends/runtime/engine.rs` (1047 lines) is a pure DAG task scheduler, whose `pub` surface
  only includes `TaskPoll` / `ResourceKey` / `TaskMeta` / `TaskCancelReason` / `TaskOutcome` /
  `RuntimeStats` / `RuntimeError` / `LocalRuntime`. It is **not a second execution backend** — the
  `Executor` trait at `backends/mod.rs:356` currently has only one implementer (the interpreter).
  This needs clarification, because the directory name is misleading.

**Form 2: Remnant.** The upstream decision was made, but only half the deletion was carried out.

- `src/middle/passes/mono/instance.rs:416-830` (**415 lines**) has remnants of 6 types:
  `FunctionInstance` (416), `GenericClosureId` (562), `ClosureId` (628), `ClosureInstance` (724),
  `ClosureSpecializationKey` (760), `CaptureVariable`. **The source is clear**: when `RFC-023`
  deprecated the "closure capture model," it declared that "**approximately 850 lines of code would
  be deleted together with the closure model**." These 415 lines are the survivors of that 850-line
  deletion — **the deletion was only half done**. **Verification**: A whole-repo word-boundary
  search for these 6 types shows **zero hits** outside `instance.rs` (including tests). The
  `pub use passes::mono::instance::*;` at `middle/mod.rs:40` is merely a glob re-export and does not
  constitute consumption.

**Form 3: False Coverage.** This is the most dangerous kind — **it makes the repository look more
reliable than it actually is**.

`src/frontend/core/lexer/mod.rs` has only 5 `pub mod`s (`literals` / `state` / `symbols` /
`tokenizer` / `tokens`) plus a `#[cfg(test)] #[path = "tests/fstring.rs"] mod fstring_tests;`

| `rfc010_lexer.rs` | 167     | 12        |

### Hollow Design

The three documents under `docs/src/dev/design/check/` describe an architecture that **never
existed**. This is not "designed but not done" — it is that **the documents describe a different
system that never existed**, and wrote "possible future designs" as "deficiencies of an
already-implemented system."

## Methodology and Credibility Statement

### Reachability Analysis Method

Starting from the two crate roots `src/lib.rs` / `src/main.rs`, parse all 509 `.rs` files' `mod` /
`pub mod` / `#[path]` declarations, build the module graph, and perform BFS reachability analysis.
`include!` targets are judged separately (not counted in reachability).

**This method has known misjudgment patterns, and was actually triggered twice during the writing
process:**

1. `Split-Path` returns `\` on Windows, which doesn't match the forward-slash key → at one point
   misreported 499 orphans
2. **For non-`mod.rs` files, the submodule directory is `self_name/` rather than `parent_dir/`** →
   `orchestrator.rs`'s `mod tests` was resolved as `src/frontend/module/tests/`, nearly misjudging
   753 lines of live tests as dead code

Therefore **every conclusion was double-confirmed by "actually reading the file + actually searching
for references"**, and items that did not pass the second confirmation are not included in this
document.

### Line-Count Convention

All line counts in this document are counted using `(Get-Content).Count`. **Note that
`Measure-Object -Line` skips blank lines, systematically undercounting by about 5%** (e.g.,
`manifesto.md` reported 658 with `-Line`, but is actually 893). An earlier round of analysis in this
repo gave a lower total due to this convention; the correction is applied here.

### Known Limitations

- **Reachability analysis can only discover "unreachable", not "reachable but meaningless."** Forms
  other than Form 2 require case-by-case human judgment.
- **`pub` items in Rust do not trigger `dead_code` warnings**, so zero-call `pub` types need to be
  discovered by search; this method does not cover them.
- This document does not involve running the compiler, so all "never run" conclusions are static
  judgments.

### Directions Not Adopted

- **All handled by "delete outright", orphan tests also deleted** — 1005 lines of tests with real
  assertions are assets. The cost of deletion is a single `mod` declaration, the benefit is that CI
  regains coverage. The authorization is "may delete", not "should delete".
- **Only add gates without modifying code** — gates can prevent regression, but B1's 415 lines, the
  dispatch chain, and the 96 lines of dead ladder **already exist**, and gates will only freeze them
  at the baseline.
- **Keep the `accepted` status of RFC-018 / RFC-028 and only supplement the documentation** —
  `rfc/index.md:131` defines "accepted = entering the implementation phase", readers will reasonably
  assume implementation exists. `TRACKING.md` has precedent for the `impl_status` field (5 RFCs are
  using it), the cost of supplementing the field is far lower than the cost of status distortion.

## Known Limitations and Risks

- **S1 will expose real defects.** The four radix scanners in `literals.rs` have 4 isomorphic
  "continue consuming after overflow without erroring" branches, the entire `scan_leading_dot`
  function, and the `\x`/`\u` illegal escape paths, none of which have ever been tested. After the
  tests are revived, code fixes are highly likely, which will delay subsequent refactoring.
- **B9/B10 involve language behavior decisions.** Whether to "add construction sites" or "delete
  opcodes" for `Switch` and `UnaryOp::Not` requires considering whether they belong to the surface
  depended on by released corpus.
- **After C1-C3 are deleted, the capability documentation for cross-file analysis will be briefly
  absent**, until `check/cross-file-analysis.md` is rewritten to point to the actual architecture
  under `src/frontend/module/`.
- **Reachability analysis can only discover "unreachable", not "reachable but meaningless."**
  Judgments beyond Form 2 must be made case-by-case manually, and **this list does not constitute an
  exhaustive proof**.
- **`pub` items in Rust do not trigger `dead_code` warnings**, so zero-call `pub` types (B2, B4)
  will not be automatically discovered by the compiler, only by search.
- **Deleting the half-done remnant of RFC-023** (B1) can fulfill the decision that "closures have
  been deleted from the language"; **correcting status distortion** (C4/C5/F3) can restore the
  reference value of `TRACKING.md`.
